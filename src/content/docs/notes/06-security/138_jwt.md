## 답안 골격
```text
[JWT(JSON Web Token)] ◀━━ 머리: Ⅶ 내 의견 (자체 수용 토큰의 즉시 취소 불가 한계 극복 → 짧은 수명의 Access Token과 Redis 블랙리스트/Refresh Token 연계 아키텍처)
 ┃
 ┣━ Ⅰ 개요 ───── 당사자 간에 권한 및 사용자 상태 정보를 JSON 객체 형태로 안전하고 간결(Compact)하게 전송하기 위한 RFC 7519 국제 표준 기반의 전자서명 토큰
 ┣━ Ⅱ 특징 ───── 자체 수용적(Self-contained, 토큰 자체에 사용자 정보 포함) · 상태 비저장(Stateless, 서버 세션 메모리 불필요) · 마이크로서비스(MSA) 최적화 · 위·변조 방지(디지털 서명)
 ┣━ Ⅲ 구조 ───── 3단 구조(점 `.`으로 구분): Header(알고리즘, 토큰 타입) + Payload(클레임 Claim 데이터) + Signature(HMAC/RSA 서명)
 ┣━ Ⅳ 흐름 ───── 클라이언트 로그인 성공 → 서버가 비밀키로 JWT 서명 발급 → 클라이언트가 HTTP Header(`Authorization: Bearer <token>`)로 전송 → 백엔드 서버가 DB 조회 없이 로컬 서명만 검증 후 즉시 인가
 ┣━ Ⅴ 비교 ───── 전통적 서버 세션(Stateful, 중앙 세션 저장소 Redis/DB 조회 병목, 확장에 불리) vs JWT(Stateless, DB 조회 제로, 서버 무한 수평 확장 가능, 강제 무효화 난제)
 ┗━ Ⅵ 실무 ───── `alg: none` 서명 우회 공격 / 페이로드 평문 노출(민감정보 포함 금지) / 토큰 탈취 시 만료 시간(exp)까지 무단 사용
```
- 필수 키워드: JWT(JSON Web Token) · Header.Payload.Signature · 자체 수용적(Self-contained) · 무상태(Stateless) · `alg: none` 공격 · Access/Refresh Token · JWS/JWE
- 배점 전략: 10점 = Ⅰ JWT 정의 및 3단 구조 도식 → Ⅲ 클레임(Claim) 유형 요약 → Ⅴ 세션 vs JWT 비교표 / 25점 = Ⅰ~Ⅶ 전개, 제125회 3교시 기출(JASON Web Token) 완벽 대응, 3대 주요 보안 취약점(`alg: none`, 알고리즘 치환 공격, XSS 탈취)과 이에 대한 구체적 시큐어 코딩 대응책 심층 상술
- 기출: 제125회 3교시 5번: "JASON Web Token"

## 한 줄 본질
- 수백만 사용자의 로그인 세션을 중앙 DB에 저장하고 매 요청마다 조회하느라 서버가 뻗는 세션 병목 → 사용자 권한을 JSON에 담고 암호학적 서명을 붙여 클라이언트에 들려보냄으로써 서버 조회 없이 검증 → 서버 무한 확장성 확보 / 토큰 탈취 시 즉각적인 원격 로그아웃 처리 난제

## 핵심 그림
```text
[JWT(JSON Web Token)의 3단 구조 및 무상태(Stateless) 검증 메커니즘]

[JWT 토큰 구조 (Base64URL 인코딩)]:  Header . Payload . Signature
┌───────────────────────────┬───────────────────────────┬───────────────────────────┐
│       1. Header (헤더)    │     2. Payload (내용)     │    3. Signature (서명)    │
│ {                         │ {                         │                           │
│   "alg": "HS256",         │   "sub": "user_1234",     │ HMACSHA256(               │
│   "typ": "JWT"            │   "role": "admin",        │   base64Url(Header) + "." │
│ }                         │   "exp": 1774000000       │   base64Url(Payload),     │
│                           │ }                         │   secret_key              │
│                           │                           │ )                         │
└───────────────────────────┴───────────────────────────┴───────────────────────────┘
                                           │
                                           ▼
[마이크로서비스(MSA) 환경에서의 분산 검증]
  [클라이언트] ──(Authorization: Bearer <JWT>)──> [마이크로서비스 A] ──> [로컬 서명 검증 성공: 인가!]
                                            └─> [마이크로서비스 B] ──> [중앙 DB 조회 전혀 없음!]
```

## 핵심 용어
- 자체 수용적 (Self-contained): 토큰 자체에 사용자의 식별자(ID), 권한 목록(Roles), 만료 시각(exp) 등 필요한 모든 클레임 정보를 담고 있어, 서버가 사용자 검증을 위해 별도의 DB나 캐시 메모리를 조회할 필요가 없는 특성
- `alg: none` 공격: 공격자가 JWT 헤더의 알고리즘 필드를 `"none"`으로 조작하고 서명(Signature) 부분을 아예 지워 보냈을 때, 검증 로직이 서명 검사를 생략하고 변조된 관리자 권한 페이로드를 그대로 통과시키는 고전적 취약점

## 핵심 통찰
- 페이로드(Payload)는 "암호화된 것이 아니라 단순 Base64로 인코딩된 것"임 → 누구나 디코딩 사이트(jwt.io)에 넣으면 1초 만에 평문으로 열람할 수 있으므로, 주민등록번호나 비밀번호 같은 기밀 데이터를 절대 페이로드에 넣으면 안 됨
- JWT의 가장 큰 장점(Stateless)은 동시에 가장 큰 저주임 → 사용자가 로그아웃 버튼을 누르거나 스마트폰을 분실해도, 이미 발급된 유효기간 24시간짜리 토큰은 만료 시간까지 전 세계 모든 서버에서 여전히 정상 작동함
- 따라서 실무에서는 Access Token의 유효기간을 15분으로 극단적으로 짧게 잡고, 유효기간 2주일짜리 Refresh Token을 안전한 서버에 보관해 재발급받는 하이브리드 전략이 필수적임

## 이웃 토픽과 구분
- JWS(JSON Web Signature) vs JWE(JSON Web Encryption): JWS = 내용을 누구나 볼 수 있지만 위변조를 막는 전자서명 토큰(일반 JWT) / JWE = 내용 자체를 대칭키로 암호화하여 기밀성을 보장하는 암호화 토큰

## 문제·원인·대책
- 사례: 공격자가 공개키(RS256) 기반 JWT를 대칭키(HS256)로 알고리즘을 바꿔치기하여 공개키를 비밀키 삼아 서명 위조에 성공한 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 알고리즘 혼동 공격(Algorithm Confusion)을 통한 서명 위조 | 서버 검증 라이브러리가 헤더의 `alg` 값을 무조건 신뢰하여 처리 | 서버 코드에서 허용 알고리즘(Whitelist: 오직 RS256만) 엄격 강제 | 비인가 알고리즘으로 변조된 위조 토큰 즉각 거부 |
| XSS 스크립트를 통한 브라우저 로컬 스토리지 내 JWT 탈취 | 웹 브라우저의 `localStorage`나 `sessionStorage`에 JWT 보관 | `HttpOnly` 및 `Secure`, `SameSite` 쿠키에 토큰 보관 | 악성 자바스크립트의 토큰 접근 원천 차단 |

## 이렇게 출제된다
- 제125회 3교시 5번: "JASON Web Token" → 요구 포인트: Ⅰ JWT 개념 및 배경 + Ⅲ 3단 구조(Header, Payload, Signature) 상세 명세 + Ⅵ 핵심 보안 취약점 및 Access/Refresh 아키텍처

## 내 의견
- [토큰 취소 목록(Revocation List)의 분산 블룸 필터(Bloom Filter) 적용] 토큰의 즉시 무효화를 위해 매 요청마다 Redis를 조회하면 JWT의 본래 목적인 무상태(Stateless) 고속성이 퇴색됨 → 나라면: 평소에는 로컬 공개키 서명 검증만으로 100% 무상태 처리하고, 분실이나 로그아웃된 블랙리스트 토큰의 해시값만 인메모리 블룸 필터로 브로드캐스팅하여 메모리 낭비 없이 99.9% 확률로 탈취 토큰을 고속 적발하는 하이브리드 인가 계층 구축
