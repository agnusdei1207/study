## 답안 골격
```text
[개인정보 전송요구권] ◀━━ 머리: Ⅶ 내 의견 (FHIR 등 도메인 표준 스키마 수립과 API 게이트웨이 트래픽 쿼터제)
 ┃
 ┣━ Ⅰ 개요 ───── 금융 중심 마이데이터의 한계 탈피 → 전 분야 데이터 이동권의 법제화(PIPA 제35조의2)
 ┣━ Ⅱ 특징 ───── 본인 및 제3자 전송 · 계약/동의 기반 자동화 처리 정보 한정 · 사유재산화 방지
 ┣━ Ⅲ 구조 ───── 정보주체 + 전송의무자(기업) + 수신자(전문기관/타기업) + 마이데이터 종합지원 플랫폼
 ┣━ Ⅳ 흐름 ───── 정보주체 전송요구 → 인증 및 자격 검증 → 표준 API 전송 → 수신자 암호화 적재
 ┣━ Ⅴ 비교 ───── 금융 마이데이터(신용정보법) vs 전 분야 마이데이터(개인정보보호법)
 ┗━ Ⅵ 실무 ───── 의료·통신·유통 간 이종 데이터 스키마 불일치 / 시스템 구축 비용 분담 갈등
```
- 필수 키워드: PIPA 제35조의2 · 개인정보 전송요구권 · 전 분야 마이데이터 · 개인정보관리전문기관 · 표준 API · 데이터 이동권
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ 4대 주체 연계 구조도 → Ⅴ 금융 vs 전분야 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅲ 전송요구권 행사 요건과 Ⅵ 이종 산업 결합 이슈 집중

## 한 줄 본질
- 정보주체가 플랫폼 기업에 갇혀 있던 자기 데이터를 통신·의료·유통 등 다른 기업이나 기관으로 직접 이동시키는 법적 권리 → 소비자 락인(Lock-in) 타파 / 이종 산업 간 데이터 표준화 난제 및 인프라 구축 비용 발생

## 핵심 용어
- 데이터 이동권(Data Portability): GDPR 제20조에서 유래한 개념으로, 자신의 데이터를 기계 판독 가능한 형식으로 받아 다른 서비스로 옮길 수 있는 권리
- 개인정보관리전문기관: 정보주체를 대신하여 본인신용정보 및 개인정보를 관리하고 전송받아 분석·활용을 지원하도록 정부가 지정한 전문 기관
- 의미론적 상호운용성(Semantic Interoperability): 서로 다른 도메인의 데이터 필드가 시스템 간 이동 시에도 본래의 의미를 왜곡 없이 보존하는 기술적 성질

## 핵심 통찰
- 금융 마이데이터는 계좌·잔액 등 정형화된 수치 중심이었으나, 전 분야 마이데이터는 진료기록, 통신 로그, 쇼핑 장바구니 등 고도의 비정형·이종 데이터를 다룸
- 전송요구권은 "기업이 생성한 분석·파생 데이터"는 제외되고, "정보주체가 제공했거나 계약·동의에 의해 자동 수집된 원천 정보"에만 한정됨
- 성공의 열쇠는 API 규격이 아니라 의료(HL7 FHIR), 유통, 통신 간 공통 데이터 모델(CDM)을 얼마나 빠르게 합의하느냐에 달림

## 이웃 토픽과 구분
- 금융 마이데이터 vs 전 분야 마이데이터: 금융 마이데이터 = 신용정보법 근거, 신용자산 관리에 국한 / 전 분야 마이데이터 = 개인정보보호법 근거, 삶 전반의 생활·의료·통신 데이터를 아우르는 상위 개념

## 문제·원인·대책
- 사례: 병원-보험사 간 의료 마이데이터 전송 시 EMR 규격 상이로 인한 연계 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 의료기관마다 상이한 처방·진료 코드 체계 | 국가 표준 의료 데이터 용어·서식(HL7 FHIR) 미도입 | 보건의료 표준 FHIR API 변환 게이트웨이 도입 의무화 | 진료 데이터 상호운용성 확보 |
| 중소 병의원의 전송 서버 구축 비용 부담 | IT 예산 및 API 전송 인프라 개발 인력 부재 | 공공 중계 플랫폼(클라우드 기반 전송 중계기) 무상 지원 | 전송의무자 참여율 제고 |

## 이렇게 출제된다

## 내 의견
- [대기업 쏠림 현상과 데이터 주권 침해 방지를 위한 영세 데이터 수신 제한] 전송요구권이 빅테크 기업에 데이터가 일방적으로 빨려 들어가는 '역독점'을 초래할 위험 존재 → 나라면: 수신 사업자의 보안 관리체계(ISMS-P 준용) 인증을 전제 조건으로 강제하고, 정보주체에게 언제든 전송을 철회하고 기 수신된 데이터를 즉시 파기하도록 강제하는 '전송 철회 및 파기 검증 API'를 표준 사양에 의무화
