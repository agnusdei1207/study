## 지식 로드맵 내 현재 위치

지식 위치: IT 전략·관리 → 공공 디지털 혁신 → **공공부문 클라우드 네이티브 전환**

## 30초 인출

- 본질: **공공부문 클라우드 네이티브 전환은** 공공 정보시스템의 애플리케이션과 운영을 클라우드 환경에 맞게 현대화하는 전략이다.
- 메커니즘: 업무·보안 요건 확인 → 전환 방식 선택 → 경계가 분명한 서비스부터 이전·현대화 → 배포·운영 결과 검증.

<details>
<summary>핵심 용어</summary>

- **공공부문 클라우드 네이티브 전환**: 공공 정보시스템의 애플리케이션과 운영을 클라우드 환경에 맞게 현대화하는 전략
- **Cloud Native(클라우드 네이티브)** : 클라우드 환경을 고려해 애플리케이션을 개발·배포·운영하는 접근 방식이다.
- **Lift & Shift(Rehost)** : 기존 애플리케이션을 큰 구조 변경 없이 다른 인프라로 옮기는 이전 방식이다.
- **6R** : Rehost·Replatform·Repurchase·Refactor·Retain·Retire로 이전·현대화 방식을 분류하는 의사결정 기준이다.
- **MSA(Microservices Architecture)** : 애플리케이션을 업무 기능에 따라 독립 배포 가능한 서비스로 나누는 구조다.
- **CSAP(Cloud Security Assurance Program)** : 클라우드컴퓨팅서비스가 보안인증 기준에 적합한지 평가·인증하는 제도다.
- **Strangler Fig 패턴** : 기존 시스템을 유지하면서 기능을 새 시스템으로 점진적으로 옮기는 현대화 방식이다.

</details>

## 1교시 10점 답안

### Ⅰ. 정의·목적

| 구분 | 핵심 |
|---|---|
| 정의 | **공공부문 클라우드 네이티브 전환**은 공공 정보시스템의 애플리케이션과 운영을 클라우드 환경에 맞게 현대화하는 전략이다. |
| 목적 | 서비스 변경과 장애에 대응할 수 있도록 배포·운영 역량을 높인다. |

### Ⅱ. 구성체계 및 방법론

```mermaid
flowchart TD
    S1["업무·보안 요건 확인"] -->|"전환 제약 파악"| S2["전환 방식 선택"]
    S2 -->|"우선 대상 결정"| S3["서비스 단위 이전·현대화"]

    S4 -->|"운영 신호 확인"| S5["관측·운영"]
```

### Ⅲ. 공공 적용 통제

| 판단 대상 | 통제 |
|---|---|
| 전환 방식 | 업무 요건·기존 시스템 의존성을 기준으로 **6R** 중 선택 |
| 클라우드 보안 | 공공 이용 요건과 서비스 유형에 맞는 보안인증·보안 통제 확인 |
| 배포·운영 | 점진 배포와 롤백을 준비하고 서비스 신호로 변경 결과 확인 |

- 제언: 서비스 경계와 데이터 의존성을 확인한 뒤 독립적으로 배포·검증할 수 있는 업무부터 전환한다.

## Ⅲ. 클라우드 네이티브 구성 요소

> 구성 요소는 서비스 구조·실행환경·배포·운영을 나눠 보고, 시스템 요구에 맞춰 조합한다.

| 관점 | 핵심 구성 | 역할 |
|---|---|---|
| 서비스 구조 | **MSA** 등 서비스 경계 | 변경 가능한 업무 단위 구성 |
| 실행환경 | 컨테이너·오케스트레이션 | 일관된 배포·자원 관리 |
| 배포 | **CI/CD** | 빌드·시험·배포 반복 자동화 |
| 운영 | 관측성·신뢰성 관리 | 서비스 상태 확인과 장애 대응 |

## Ⅳ. 단순 이전과 현대화 비교

| 기준 | Lift & Shift | Cloud Native |
|---|---|---|
| 변경 범위 | 기존 애플리케이션을 큰 변경 없이 이전 | 애플리케이션 구조·배포·운영 방식까지 조정 가능 |
| 우선 목표 | 이전 기간·호환성 제약 대응 | 클라우드 기능을 활용한 변경·운영 개선 |
| 선택 고려 | 빠른 이전, 변경 여력 부족 | 서비스 분리·자동화 투자 여력과 필요성 |

## Ⅴ. 공공부문 전환 위험과 대응

| 위험 | 대책 | 효과 |
|---|---|---|
| 데이터·업무 경계 결합 | 서비스 경계를 먼저 확인하고 동기화·이행 계획을 검증 | 일괄 분리로 인한 데이터 불일치 위험을 줄임 |
| 단계적 전환과 계약 범위 불일치 | 단계별 책임·인터페이스·통합시험 기준을 계약·수행계획에 반영 | 단계별 인수와 통합 검증이 가능해짐 |
| 패키지 시스템의 변경 제약 | 패키지 변경 가능 범위를 확인하고 연계·이전 방식은 별도 결정 | 불필요한 재개발을 피하고 의존성을 관리 |

## Ⅵ. 기술사적 제언

| 문제 | 해결 방안 |
|---|---|
| 전환 우선순위를 장비 교체나 기술 유행으로만 정하면 업무 중단·데이터 이행 위험이 큰 서비스를 먼저 건드릴 수 있다. | 제언: 기존 업무와 데이터 의존성이 낮고 독립 배포·검증이 가능한 서비스를 먼저 시범 전환한다. 운영 결과를 확인한 뒤 다음 서비스 범위를 정한다. |
