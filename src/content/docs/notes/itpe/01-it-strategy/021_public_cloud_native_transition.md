## 답안 골격
```text
[공공부문 클라우드 네이티브 전환] ◀━━ 머리: Ⅶ 내 의견 (단순 리프트 앤 시프트 탈피, 컨테이너·MSA 기반 분할 발주 전환 체계 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 레거시 인프라 가상화(IaaS) 한계 및 서비스 중단 방지 → 마이크로서비스·컨테이너 기반 공공 시스템 전면 현대화
 ┣━ Ⅱ 특징 ───── MSA(마이크로서비스) 분할 · 컨테이너(K8s) 오케스트레이션 · CI/CD 무중단 배포 · 데브옵스(DevOps)
 ┣━ Ⅲ 구조 ───── 인프라 계층(민간/공공 클라우드) ──> 플랫폼 계층(K8s, 서비스 메시) ──> 애플리케이션 계층(MSA API)
 ┣━ Ⅳ 흐름 ───── ① 공공 정보시스템 등급 진단 → ② MSA 분할 설계(DDD) → ③ 컨테이너화 및 파이프라인 구축 → ④ 점진적 카나리 배포
 ┣━ Ⅴ 비교 ───── 단순 클라우드 이전(Lift & Shift) vs 클라우드 네이티브 전환(Cloud Native)
 ┗━ Ⅵ 실무 ───── 상용 COTS 패키지의 컨테이너화 불가 / 공공 조달 제도의 분할 발주 기피 / 운영 인력의 K8s 역량 부족
```
- 필수 키워드: 클라우드 네이티브 · MSA(마이크로서비스) · 컨테이너(Docker/K8s) · CI/CD 자동화 · 데브옵스 · 공공 클라우드 전환 로드맵
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ 4대 핵심 기술 요소(컨테이너, MSA, CI/CD, 데브옵스) 도식 → 단순 이전과 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅲ 공공 표준 아키텍처와 Ⅵ 조달 제도 개선안 집중
- 기출: 미출제. 예상: "정부의 공공부문 클라우드 네이티브 전환 로드맵에 따른 4대 핵심 기술 요소와 공공 정보시스템 전환 시 직면하는 기술적·제도적 장애요인 및 대응방안을 설명하시오."

## 한 줄 본질
- 서버 가상화(IaaS) 중심의 1차 공공 클라우드 이전이 트래픽 폭증 시 스케일아웃 불가와 전체 서비스 동반 다운 한계 노출 → 마이크로서비스(MSA), 컨테이너, CI/CD 자동화를 결합하여 개별 단위 기능의 독립 배포와 탄력적 확장을 구현 → 고가용성 무중단 대국민 서비스 달성 / 시스템 복잡도 급증 및 분산 환경 모니터링 난제

## 핵심 그림
```text
┌───────────────────────────────── [ 공공 클라우드 네이티브 4대 핵심 기둥 ] ─────────────────────────────────┐
│                                                                                                             │
│  [ 마이크로서비스 (MSA) ]                 [ 컨테이너 가상화 (Container) ]                                   │

│  - 장애 격리(Fault Isolation) 및 독립 배포 - 쿠버네티스(K8s) 기반 자동 복구/오토스케일링                     │
│                                                                                                             │
│  [ 지속적 통합/배포 (CI/CD) ]             [ 데브옵스 및 관측가능성 (DevOps) ]                              │
│  - 코드 커밋부터 배포까지 파이프라인 자동화 - 개발과 운영의 조직적 결합                                      │
│  - 무중단 배포 (Blue/Green, Canary)        - 분산 추적 (OpenTelemetry, Prometheus, Grafana)                  │

                                                      │
                       ┌──────────────────────────────┴──────────────────────────────┐
                       ▼                                                             ▼
         [ 기반 인프라: 민간 공공존(CSAP) 및 국가정보자원관리원 클라우드 ]            [ 표준 프레임워크: 전자정부 MSA 표준 ]
```

## 핵심 용어
- 리프트 앤 시프트(Lift & Shift): 기존 레거시 온프레미스 서버의 가상머신(VM)을 소스코드나 아키텍처 변경 없이 그대로 클라우드 IaaS로 복사해 올리는 단순 이전 방식
- CSAP(Cloud Security Assurance Program): 공공기관에 안전성이 검증된 민간 클라우드 서비스를 공급하기 위해 한국인터넷진흥원(KISA)이 평가·인증하는 클라우드 보안인증 제도

## 핵심 통찰
- 레거시 모놀리식 소프트웨어를 가상머신(VM)에 올린 것은 '클라우드 이전'이지 '클라우드 네이티브'가 아님 → 단일 장애점(SPOF)과 스케일링 불가능 문제는 그대로 유지됨
- 클라우드 네이티브의 성패는 인프라가 아니라 '도메인 주도 설계(DDD)를 통한 비즈니스 로직의 분할'에 있음 → 데이터베이스가 하나로 묶여 있으면 컨테이너를 아무리 띄워도 무중단 배포가 불가능함
- 공공부문에서 클라우드 네이티브를 성공시키려면 1개 대형 SI 사업자가 턴키로 구축하는 방식을 탈피하여 기능 단위별 분할 계약 제도가 뒷받침되어야 함

## 이웃 토픽과 구분
- IaaS 클라우드 vs 클라우드 네이티브: IaaS = 인프라(서버, 스토리지)만 빌려 쓰는 가상화 / 클라우드 네이티브 = 소프트웨어 설계부터 배포, 운영까지 클라우드 탄력성을 극대화하도록 애플리케이션 구조를 근본 변경

## 문제·원인·대책
- 사례: 연말정산이나 백신 예약 시 트래픽 폭증으로 공공 포털 전체가 마비된 사례(로그인 인증 모듈의 병목이 전체 대민 포털 다운타임으로 확산)
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 인증 트래픽 폭증 시 전산망 전체 다운 | 인증과 조회가 모놀리식으로 묶여 자원 고갈 전파 | 인증 모듈만 분리하여 독립 컨테이너 Pod로 격리하고 HPA(오토스케일링) 적용 | 특정 기능 장애의 전사 확산 차단 |
| 수작업 야간 배포로 인한 서비스 중단 | 파이프라인 자동화 부재 및 DB 스키마 락 발생 | Blue/Green 및 카나리 점진적 트래픽 롤아웃과 하위 호환 스키마 마이그레이션 | 24/365 대민 무중단 서비스 실현 |

## 이렇게 출제된다
- 미출제. 예상: "공공부문 클라우드 네이티브 전환의 개념과 4대 핵심 기술요소(MSA, Container, CI/CD, DevOps)를 설명하고, 성공적인 전환을 위한 단계별 이행 전략을 제시하시오." → 요구 포인트: Ⅲ 4대 기술 요소 상세 + Ⅳ 전환 단계별 활동(진단->설계->구축->운영)

## 내 의견
- [단순 인프라 전환에서 데이터베이스 분리 및 전자정부 클라우드 플랫폼 표준화 선행] 수많은 공공기관이 껍데기만 컨테이너로 감싸고 중앙 단일 오라클 DB에 모든 트랜잭션을 몰아주어 실질적인 클라우드 탄력성을 전혀 확보하지 못함 → 나라면: 전자정부 표준프레임워크 최신 버전에 내장된 분산 트랜잭션(Saga 패턴) 라이브러리를 의무 적용하고, 공공 조달 발주 시 '데이터베이스 샤딩 및 서비스별 독립 DB 분리'를 설계 감리 필수 통과 기준으로 제정
