## 지식 로드맵 내 현재 위치

IT 전략·관리 → 공공 디지털 혁신 → **공공부문 클라우드 네이티브 전환**

## 30초 인출

- 본질: 공공부문 클라우드 네이티브 전환은 단일 대형 시스템으로 구축하던 공공 정보시스템을 작은 서비스의 묶음으로 나누어 클라우드 환경에서 구축·운영하도록 바꾸는 정부 정책
- 메커니즘: 신규 구축·고도화 사업에서 민간 클라우드와 클라우드 네이티브를 우선 검토하고, 마이크로서비스·컨테이너·API 게이트웨이·서비스 메시·CI/CD·통합 관제의 기술 기준으로 시스템별 전환 방식을 결정
- 통찰: Refactor는 가장 복잡하고 비용이 크며 Rehost는 클라우드 최적화 없이 이전되므로 시스템별 확장·배포 속도 요구로 이전 방식을 판정하고 이전 뒤 현대화 단계를 사업 범위에 정의

<details>
<summary>핵심 용어</summary>

- **공공부문 클라우드 네이티브 전환** : 단일 대형 시스템 방식의 공공 정보시스템을 작은 서비스의 묶음으로 나누어 클라우드에서 구축·운영하도록 바꾸는 정부 정책
- **클라우드 네이티브(Cloud Native)** : 퍼블릭·프라이빗·하이브리드 클라우드에서 확장 가능한 워크로드를 프로그램 방식으로 반복해 개발·배포하도록 하며, 느슨하게 결합된 시스템이 안전하고 탄력적이며 관리·관측이 가능하게 동작하는 접근
- **마이크로서비스(Microservices)** : 애플리케이션을 각자 특정 기능에 집중하는 독립적인 작은 서비스로 나누는 아키텍처
- **컨테이너(Container)** : 운영체제가 자원과 권한을 제한해 관리하는 실행 중인 프로세스로, 같은 장비에서 서로 격리된 채 동시에 동작
- **API 게이트웨이(API Gateway)** : 여러 애플리케이션의 API를 한곳에 모으고 인증·인가·호출 제한 같은 공통 기능을 적용하는 진입점
- **서비스 메시(Service Mesh)** : 마이크로서비스 간 통신을 관리하는 전용 인프라 계층으로, 코드 변경 없이 신뢰성·관측성·보안을 서비스 전체에 일괄 적용
- **CI/CD(Continuous Integration/Continuous Delivery)** : 코드 변경을 자동으로 통합·테스트해 운영 반영 준비 상태로 만드는 개발 방식
- **Rehost·Replatform·Refactor** : 클라우드 이전 방식으로 각각 변경 없이 이전, 일부 최적화 후 이전, 클라우드 네이티브 기능을 활용하도록 아키텍처 변경

## 2~4교시 25점 답안

## Ⅰ. 공공부문 클라우드 네이티브 전환의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **공공부문 클라우드 네이티브 전환** 은 단일 대형 시스템 방식의 공공 정보시스템을 작은 서비스의 묶음으로 나누어 클라우드에서 구축·운영하도록 바꾸는 정부 정책 |
| 목적 | 공공 서비스의 개선 속도·안정성 향상과 클라우드 기반 운영 체계 확립 |

## Ⅱ. 정부 정책으로 추진되는 클라우드 네이티브 전환의 특징

| 특징 | 의미 |
|---|---|
| 작은 서비스의 묶음 | 단일 대형 시스템 대신 **마이크로서비스** 로 구성 |
| 클라우드 기술의 조합 | 컨테이너·서비스 메시·마이크로서비스·불변 인프라·선언형 API 활용 |
| 자동화와 반복성 | 프로그램 방식으로 반복해 배포하고 변경을 자주 예측 가능하게 수행 |
| 우선 적용 검토 원칙 | 신규 구축과 기존 시스템 고도화에서 불가피한 사유가 없으면 민간 클라우드와 클라우드 네이티브를 우선 적용 검토 |
| 단계적 추진 | 2025년까지 행정안전부 전환 지원 중심, 이후 기관 주도 |

## Ⅲ. 전환 정책 체계와 기술 기준

```text
클라우드 네이티브 중심 공공부문 정보자원 클라우드 전환계획 (2023.10.24, 행정안전부·디지털플랫폼정부위원회)
    │
    ├─ 적용 원칙 ── 신규 구축·기존 고도화 시 민간 클라우드와 클라우드 네이티브 우선 적용 검토
    │
    ├─ 추진 과제 ── 시범전환, 전환 기준·절차·가이드라인, 정부-민간 클라우드 연계기반, 기술 교육, 컨설팅
    │
    └─ 전환 목표 ── 2026년부터 신규 전환물량의 70% 이상, 기존 시스템의 50% 이상을 클라우드 네이티브 방식으로 전환
```

### 기술 기준 확대: 클라우드 네이티브 구축·운영 상세 가이드

```text
마이크로서비스 분리 설계
    ↓
데이터베이스 분산 구조 설계
    ↓
컨테이너 구현
    ↓
API 게이트웨이 → 서비스 메시
    ↓
CI/CD 자동화
    ↓
통합 관제 체계
```

## Ⅳ. 클라우드 이전 방식 비교

| 이전 방식 | 애플리케이션 변경 | 적합 조건 | 유의점 |
|---|---|---|---|
| **Rehost** | 변경 없이 이전 | 다수 서버를 짧은 컷오버로 이전 | 클라우드 최적화 없음, 이전 뒤 현대화 필요 |
| **Replatform** | 관리형 서비스·컨테이너 등 일부 최적화 | 비용 절감·성능 개선이 필요한 시스템 | 변경 범위가 목표 플랫폼에 따라 달라짐 |
| **Refactor** | 클라우드 네이티브 기능을 활용하도록 아키텍처 변경 | 확장·릴리스 속도 요구가 크거나 모놀리스가 전달을 막는 시스템 | 가장 복잡하고 비용이 큼 |
| Repurchase | 제품·SaaS로 대체 | 기존 제품을 SaaS로 대체할 수 있는 시스템 | 구매 전 보안·규정 준수 평가 필요 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| Refactor는 가장 복잡하고 비용이 커서 모든 시스템에 적용하기 어려움 | 확장·배포 속도 요구가 커서 서비스 분리가 필요한 시스템에만 Refactor 적용 |
| Rehost는 클라우드 최적화 없이 이전되어 이전 뒤 현대화가 필요 | 나머지 시스템은 Rehost·Replatform으로 이전하고 현대화 단계를 전환 사업 범위에 포함 |
## Ⅵ. 제언

시스템별 확장·배포 속도 요구로 Refactor 대상을 먼저 판정하고, 나머지는 Rehost·Replatform으로 이전한 뒤 현대화 단계를 사업 범위에 정의

### 이전 방식 판정과 현대화 단계

```text
시스템별 이전 방식 판정
    ↓
확장·배포 속도 요구가 크고 모놀리스가 전달을 막는가
    ├─ 예 → Refactor: 서비스 분리 설계
    └─ 아니오 → Rehost·Replatform으로 이전
                    ↓
                이전 뒤 현대화 단계 (사업 범위에 포함)
```

### 현대화 단계 정의 확대

```text
이전 뒤 현대화 단계
    │
    ├─ 대상 ── Rehost로 이전해 클라우드 최적화가 없는 부분
    │
    ├─ 방식 ── Replatform·Refactor 중 선택
    │
    └─ 반영 위치 ── 전환 사업의 후속 단계
```

| 구분 | 전 시스템 Refactor 적용 | 제언: 판정 후 선택 |
|---|---|---|
| Refactor 적용 대상 | 모든 시스템 | 확장·배포 속도 요구가 큰 시스템 |
| 복잡도·비용 | 가장 복잡하고 비용이 큰 방식이 전체에 발생 | 필요한 시스템에만 발생 |
| Rehost 이전 뒤 | 해당 없음 | 현대화 단계를 사업 범위에 포함 |
