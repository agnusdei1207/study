## 연관 키워드

- 공공 클라우드 네이티브, Cloud Native, MSA
- 컨테이너, Kubernetes(K8s), CI/CD, DevOps, Lift & Shift, CSAP

## Ⅰ. 공공부문 클라우드 네이티브 전환의 개요

- 핵심 요약 : 설계 단계부터 MSA·컨테이너·CI/CD·데브옵스를 적용해 클라우드 장점을 끌어내는 행정 혁신 전략.
- 개념 : 공공 정보시스템을 인프라만 옮기는 **단순 이전** (Lift & Shift) 방식이 아니라, 설계 단계부터 **클라우드 네이티브** (Cloud Native)를 적용해 **마이크로서비스 아키텍처** (MSA, Microservice Architecture), 컨테이너, CI(Continuous Integration)/CD(Continuous Delivery), 데브옵스 체계로 바꾸는 행정 혁신 전략.
- 배경 및 필요성 : 대국민 서비스 장애 재발을 막아야 하고, 트래픽 급증 시 자원을 신속히 늘려야 하며, 노후한 모놀리식 시스템의 유지보수 한계를 넘어야 하는 상황.
- 주요 목적 : 무중단 대국민 서비스 구현, 개발·배포 주기 단축, 장애 격리와 복원력 확보, 클라우드 자원 활용 효율화.

## Ⅱ. 클라우드 네이티브의 특징 및 장점

- 핵심 요약 : MSA·컨테이너·CI/CD·선언적 인프라의 4대 기술 요소가 변경 영향 축소와 배포 속도 향상으로 이어짐.

1. 마이크로서비스(MSA) : 기능별로 독립 배포·확장 → 변경의 영향 범위 축소.
2. 컨테이너와 Kubernetes : 실행 환경을 표준화하고 수요에 맞춰 자원을 탄력 배치 → 자원 활용률 향상.
3. CI/CD와 DevOps(Development and Operations, 개발과 운영) : 자동 시험·배포와 개발·운영 협업 → 출시 주기 단축과 수작업 오류 감소.
4. 선언적 API와 GitOps(Git Operations, Git 기반 운영) : 인프라 목표 상태와 변경 이력을 코드로 관리 → 재현성과 감사 가능성 향상.

## Ⅲ. 공공 클라우드 네이티브의 구조 (흐름)

- 핵심 요약 : 4대 기술 요소가 맞물리는 구조와, 레거시 시스템에서 무중단 서비스로 이어지는 전환 흐름.
- 4대 요소는 **마이크로서비스**, **컨테이너**, **CI/CD**, **선언적 인프라**(GitOps, Git Operations)로 나뉜다. 선언적 인프라는 코드로 관리하는 IaC(Infrastructure as Code)를 기반으로 한다.

```text
[클라우드 네이티브 4대 요소]
클라우드 네이티브
   - MSA: 독립 배포·확장 단위 분할
   - 컨테이너·Kubernetes: 환경 일관성
   - CI/CD·DevOps(Development and Operations, 개발과 운영): 자동화 파이프라인
   - 선언적 API·GitOps(Git Operations, Git 기반 운영): 코드 기반 인프라
```

```text
[공공 전환 흐름]
레거시 모놀리식 시스템
        ↓
대국민 접점 서비스부터 분리
        ↓
컨테이너화·MSA 전환
        ↓
CI/CD 파이프라인 구축
        ↓
무중단·오토스케일링 서비스
```

## Ⅳ. 단순 이전(Lift & Shift)과 클라우드 네이티브의 비교

- 핵심 요약 : VM 단위 수동 확장과 모놀리식 구조를 유지하는 단순 이전에 비해, 클라우드 네이티브는 서비스 단위 확장과 장애 격리를 제공.

| 비교 항목 | 단순 이전 (Lift & Shift) | 클라우드 네이티브 (Cloud Native) |
| --- | --- | --- |
| 시스템 구조 | 단일 모놀리식 구조 유지 | 도메인 기준으로 나눈 마이크로서비스 |
| 배포와 확장 | VM 단위의 수동 확장, 정기 배포 시 서비스 중단 | 컨테이너 단위 자동 확장, 점진적 배포 |
| 장애 영향 | 한 모듈 장애가 전체 중단으로 번질 수 있음 | 장애 격리와 우회 설계로 영향 범위 제한 |
| 데이터베이스 | 단일 대용량 RDBMS(Relational Database Management System)에 집중 | 서비스별 독립 데이터베이스와 분산 정합성 관리 |
| 과금 방식 | 서버·스토리지 구매 규격 기준 | 사용량 기반 클라우드 서비스 이용료 계약 |

## Ⅴ. 공공 클라우드 네이티브 전환의 한계와 방안

- 핵심 요약 : 보안 요건, 단순 이전의 비효율, 운영 역량 부족을 서비스 특성별 전환 설계로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 보안 요건 충족 어려움 | 공공 데이터의 **보안 요건**을 일률적 구성으로 충족하기 어려움 | 데이터 등급별 적용 지침에 맞춰 접근 통제·인증·감사 설계를 검증 | 보안 점검 항목 통과율 |
| 단순 이전의 비효율 | **Lift & Shift**만으로는 탄력성과 비용 효과를 얻기 어려움 | 서비스별 적합성을 평가해 필요한 부분부터 리팩토링과 자동 확장 적용 | 서비스별 전환 적합성 점수 |
| 운영 역량 부족 | 발주 기관의 운영 역량 부족과 특정 공급자 의존 위험 | 표준 인터페이스, 운영 지식 이전, 계약상 이식성 요건 마련 | 운영 인력 확보율, 이식성 검증 건수 |

## Ⅵ. 공공 클라우드 네이티브 전환에 대한 기술사적 제언

- 핵심 요약 : 점진적 전환, 분산 데이터 정합성 확보, 보안 기준의 현실화.

대규모 공공시스템을 한 번에 옮기는 빅뱅 전환은 장애 위험이 크므로, 대국민 접점이면서 트래픽 변동이 큰 서비스부터 Strangler Fig 패턴으로 순차 분리하는 방식이 현실적이다. 분리 순서를 정할 때는 업무 영향도와 재사용 가능성을 함께 검토해야 한다.

서비스별로 데이터베이스가 나뉘면 분산 트랜잭션의 정합성 문제가 생긴다. 2단계 커밋(2PC, Two-Phase Commit)은 장애 시 잠금이 길어질 수 있으므로, 사가 패턴(Saga Pattern)과 이벤트 기반 아키텍처로 보상 처리를 설계하는 편이 바람직하다.

보안 측면에서는 클라우드 보안인증제(CSAP, Cloud Security Assurance Program)의 등급 기준과 망분리 규제를 함께 검토하고, 제로 트러스트(Zero Trust) 원칙에 따라 서비스 간 상호 인증을 적용하는 것이 필요하다. 규제 완화는 데이터 등급을 나눈 뒤 그 위에서 판단해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 공공 클라우드 네이티브 전환은 MSA·컨테이너·CI/CD에 기반한 행정 혁신 전략.
- 시사점 : 망분리 기준의 합리화와 분산 데이터 정합성 확보가 전환의 성패를 가름.
