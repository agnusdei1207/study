## 30초 인출

- 본질: 공공부문 클라우드 네이티브 전환은 공공 정보시스템의 애플리케이션 구조·배포·운영을 클라우드 특성에 맞게 바꾸는 현대화 전략
- 메커니즘: 시스템별 업무·보안 요건과 의존성에 따라 이전 방식을 고르고, 컨테이너·MSA·DevOps(CI/CD)를 서비스 단위로 적용하는 점진 전환
- 통찰: 인프라만 옮기면 운영 방식이 그대로이므로 변경이 잦은 서비스의 Refactor 시범 전환 후 확대

<details>
<summary>핵심 용어</summary>

- **공공부문 클라우드 네이티브 전환** : 공공 정보시스템의 애플리케이션 구조·배포·운영을 클라우드 특성에 맞게 바꾸는 현대화 전략
- **클라우드 네이티브(Cloud Native)** : 컨테이너·마이크로서비스·선언적 API 등으로 클라우드에서 탄력적으로 확장·변경·복구되도록 만든 애플리케이션 구성 방식
- **이전 방식(AWS 전환 전략)** : AWS가 시스템별 이전·현대화 방식으로 제시한 Rehost·Replatform·Repurchase·Refactor·Retain·Retire 분류. 시험 공식 용어가 아닌 벤더 분류
- **MSA(Microservices Architecture)** : 애플리케이션을 업무 기능별로 독립 배포 가능한 작은 서비스로 나눈 구조
- **DevOps** : 개발과 운영의 협업으로 변경을 자주·안전하게 반영하는 문화와 방법
- **CI/CD(Continuous Integration/Continuous Delivery)** : 코드 변경의 빌드·시험·배포를 자동화해 자주 반영하는 방식
- **관측성(Observability)** : 로그·지표·추적 자료로 서비스 내부 상태와 장애 원인을 파악하는 운영 역량
- **Strangler Fig 패턴** : 기존 시스템을 유지한 채 기능을 하나씩 새 서비스로 옮기고 옛 기능을 걷어내는 점진 전환 방식
- **CSAP(Cloud Security Assurance Program)** : 「클라우드컴퓨팅 발전 및 이용자 보호에 관한 법률」 제23조의2에 따라 클라우드 서비스의 보안인증기준 적합성을 평가·인증하는 제도

## 2~4교시 25점 답안

## Ⅰ. 공공부문 클라우드 네이티브 전환의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **공공부문 클라우드 네이티브 전환** 은 공공 정보시스템의 애플리케이션 구조·배포·운영을 클라우드 특성에 맞게 바꾸는 현대화 전략 |
| 목적 | 행정서비스의 배포 주기 단축과 장애 복구 시간 감소 |

## Ⅱ. 단순 이전과 구별되는 특징

| 특징 | 의미 |
|---|---|
| 구조 현대화 | 서버 위치 이동이 아닌 서비스 구조의 변경 |
| 독립 배포 | 업무 기능별 서비스의 개별 변경·배포·확장 |
| 운영 자동화 | 배포·확장·복구의 자동화, 관측성 기반 장애 대응 |
| 공공 보안 요건 | 시스템 중요도와 **CSAP** 인증 기준에 따른 클라우드 선택 |

## Ⅲ. 클라우드 네이티브 전환 구성 체계와 점진 전환 절차

### 클라우드 네이티브 전환 구성 체계

```text
공공부문 클라우드 네이티브 전환
    │
    ├─ 전제 ── 업무 중요도·보안 요건·인증 클라우드
    │
    ├─ 애플리케이션 구조 ── MSA·API 기반 서비스 경계
    │
    ├─ 실행 환경 ── 컨테이너·오케스트레이션
    │
    ├─ 배포 ── DevOps·CI/CD 자동화
    │
    └─ 운영 ── 관측성·자동 복구
```

### 애플리케이션 구조 확대: Strangler Fig 점진 전환 절차

```text
업무 기능·데이터 의존성 분석
    ↓
의존성이 낮은 기능 선정
    ↓
신규 서비스 구축과 API 게이트웨이의 요청 전환
    ↓
운영 결과 확인
    ├─ 문제 발생 → 기존 시스템으로 요청 환원
    └─ 안정 확인 → 다음 기능 전환·기존 기능 폐기
```

## Ⅳ. 이전 방식별 클라우드 네이티브 도달 범위

| 방식 | 변경 범위 | 배포·운영 방식의 변화 |
|---|---|---|
| Rehost | 인프라만 이전 | 없음 |
| Replatform | DB·미들웨어의 관리형 서비스 교체 | 운영 부담 일부 감소 |
| Repurchase | 상용 SaaS로 교체 | 제공사가 운영 |
| **Refactor** | MSA·컨테이너 기반 재설계 | 독립 배포·자동화 적용 |
| Retain | 현행 유지 | 없음 |
| Retire | 폐기 | 해당 없음 |

## Ⅴ. 공공부문 전환의 한계와 방안

| 한계 | 방안 |
|---|---|
| Rehost 후 배포·운영 방식이 그대로 남는 단순 이전 | 변경이 잦은 대국민 서비스는 Refactor, 변경이 드문 내부 시스템은 Rehost·Replatform 선택 |
| 업무·데이터 결합에 따른 서비스 분리 곤란 | 데이터 의존성 분석 후 경계가 분명한 기능부터 분리하고 공유 DB는 API 경유 접근으로 단계 전환 |
| 패키지·상용 SW의 구조 변경 제약 | Repurchase 가능 여부 검토, 불가 시 Retain 후 API 연계 |

## Ⅵ. 제언

변경이 잦고 의존성이 낮은 대국민 서비스 하나의 Refactor 시범 전환과, 배포 주기·장애 복구 시간 개선 확인 후의 단계적 확대

### 시범 전환 기반 확대 흐름

```text
전환 후보 시스템
    ↓ 변경 빈도·의존성·보안 요건 평가
시범 서비스 선정: 변경이 잦고 의존성이 낮은 서비스
    ↓
Refactor 시범 전환
    ↓
배포 주기·장애 복구 시간의 전환 전 대비 확인
    ├─ 개선 확인 → 같은 파이프라인으로 다음 서비스 확대
    └─ 개선 미흡 → 서비스 경계·운영 역량 보완 후 재확인
```

### 선택 근거: 일괄 이전과의 비교

| 구분 | 일괄 이전 | 제언: 시범 전환 후 확대 |
|---|---|---|
| 우선 대상 | 전체 시스템 동시 | 변경이 잦고 의존성이 낮은 서비스 |
| 확대 판단 | 이전 완료 여부 | 배포 주기·장애 복구 시간 개선 |
| 실패 시 처리 | 전체 일정 지연 | 해당 기능의 기존 시스템 환원 |
