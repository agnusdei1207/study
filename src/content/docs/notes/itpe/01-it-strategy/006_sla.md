## 답안 골격
```text
[SLA] ◀━━ 머리: Ⅶ 내 의견 (정적 가용성 % 중심에서 탈피한 사용자 체감 성능 기반 동적 SLA 계약 체결)
 ┃
 ┣━ Ⅰ 개요 ───── IT 서비스 품질 기준 모호로 인한 발주자-공급자 분쟁 → 서비스 정량 지표 명문화 및 계약 체결
 ┣━ Ⅱ 특징 ───── 정량적 지표 기반(SLI/SLO) · 상호 합의 계약 · 페널티/인센티브 연계 · 지속적 모니터링
 ┣━ Ⅲ 구조 ───── SLA(고객 계약) ↔ OLA(사내 부서 협약) ↔ UC(외부 벤더 계약) 3계층 서비스 협약 체계
 ┣━ Ⅳ 흐름 ───── ① 서비스 카탈로그 정의 → ② SLI(측정지표) 선정 → ③ SLO(목표수준) 합의 → ④ SLA 계약 체결 → ⑤ 상시 측정 및 정산
 ┣━ Ⅴ 비교 ───── SLA vs SLO vs SLI / SLA vs OLA vs UC
 ┗━ Ⅵ 실무 ───── 달성 불가능한 99.999% 요구로 인한 비용 폭증 / 유지보수 업체의 책임 회피 / 클라우드 장애 보상 한계
```
- 필수 키워드: 서비스 카탈로그 · SLI(지표) · SLO(목표) · OLA · UC · 가용성(99.9%) · 페널티/보상
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ SLA/OLA/UC 3계층 구조도 → SLI/SLO/SLA 관계 / 25점 = Ⅰ~Ⅶ 전개, Ⅲ 구성요소와 Ⅵ 공공 SLA 의무화 제도 집중
- 기출: 130회 3교시 `금융 클라우드 환경 SLA 수립 고려사항` → Ⅵ, 134회 2교시 `IT 서비스 관리 체계와 SLA 지표` → Ⅲ·Ⅳ, 139회 2교시 `공공 정보시스템 등급제 및 공공 SLA 표준 의무화` → Ⅵ

## 한 줄 본질
- 주관적이고 모호한 IT 서비스 운영 평가로 인한 위수탁 갈등 심화 → 서비스 항목별 정량 지표(가용률, 응답속도, 장애복구시간)와 미달 시 페널티를 명시한 서비스 수준 협약 체결 → 객관적 품질 통제 및 서비스 연속성 확보 / 목표 수준 상향 시 인프라 이중화 및 유지보수 비용 급증

## 핵심 그림
```text
┌───────────────────────────────── [ 고객 / 발주기관 ] ─────────────────────────────────┐
│                                          ▲                                            │
│                                          │  SLA (Service Level Agreement: 공식 서비스 계약)
│                                          ▼                                            │
│                              [ IT 서비스 제공자 (원청) ]                              │
│                                   │             │                                     │
│      OLA (Operation Level Agreement)            │ UC (Underpinning Contract: 외부 벤더 계약)
│      (사내 인프라/DB/보안팀 간 협약)              │ (서버 벤더, IDC, 회선 통신사 계약)  │
│                                   ▼             ▼                                     │
│                            [ 사내 지원 부서 ] [ 외부 공급업체 ]                       │
└───────────────────────────────────────────────────────────────────────────────────────┘
  * 지표 체계: SLI (Service Level Indicator: 실제 측정치, 예: 응답시간 200ms)
              ──> SLO (Service Level Objective: 내부 목표치, 예: 99% 요청 < 300ms)
              ──> SLA (Service Level Agreement: 미달 시 금전 배상 약정, 예: 월 가용성 < 99.9% 시 10% 환불)
```

## 핵심 용어
- SLI(Service Level Indicator): 서비스 수준을 판단하기 위해 실측한 정량적 수치(예: 성공 요청 비율, 지연시간 p99)
- SLO(Service Level Objective): 서비스 제공자가 내부적으로 지키고자 하는 정량적 목표치로 통상 SLA보다 엄격하게 설정
- OLA(Operational Level Agreement): 원청 IT 조직 내부의 인프라팀, 네트워크팀, 애플리케이션팀 간 서비스 지원 약정

## 핵심 통찰
- SLA는 공급자를 징벌하기 위한 수단이 아니라 '비즈니스 허용 오차 한도'를 규정하는 합의 문서임
- 가용성 목표를 99.9%(연간 허용 장애 8.7시간)에서 99.99%(연간 52분)로 올리는 데 필요한 인프라 비용은 지수적으로 증가하므로 업무 등급별 차등 SLA가 필수적임
- 클라우드 공급자(CSP)의 SLA는 순수 인프라 다운타임만 인정하므로, 애플리케이션 계층 장애까지 포괄하는 자체 복구(Failover) 아키텍처가 선행되어야 함

## 딸려 나오는 하위 토픽

| 하위 토픽 | 상위 구조 속 위치 | 한 줄 (정의 → 메커니즘 → 구분축) |
|---|---|---|
| OLA(Operation Level Agreement) | Ⅲ 구조 / 내부 협약 계층 | 고객 대상 SLA 목표를 달성하기 위해 IT 운영 조직 내부 단위 팀(인프라, DB, 보안, 네트워크) 간의 업무 책임과 처리 시한을 정의한 내부 지원 협약 (대고객 외적 계약 SLA vs 조직 내부 연계 OLA) |

## 이웃 토픽과 구분
- SLA vs OLA: SLA = 고객(발주자)과 서비스 제공자 간의 대외적 법적 계약 / OLA = 고객 SLA를 달성하기 위해 사내 지원 부서(DB팀, 보안팀 등) 간에 체결하는 대내적 운영 협약

## 문제·원인·대책
- 사례: 139회 기출 공공 전산망 장애 사태 이후 전자정부법 개정에 따른 공공 정보시스템 등급제 및 공공 SLA 의무화 정책 추진
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 장애 발생 시 시스템 간 책임 떠넘기기(핑퐁) | 종합 SLA만 존재하고 세부 컴포넌트별 OLA 및 UC 연계 부재 | 단위 인터페이스별 OLA 체결 및 외부 클라우드/HW 벤더 계약(UC)과 SLA 정합 | 장애 원인 규명 및 복구 책임 명확화 |
| 명목상 가용률 99.9% 달성에도 사용자 불만 폭주 | 백엔드 서버는 살았으나 화면 응답 지연이 10초 이상 발생하는 기능 장애 누락 | 단순 핑(Ping) 체크 탈피, 합성 트랜잭션(Synthetic Monitoring) 및 APM 지표 도입 | 사용자 체감 관점의 품질 모니터링 달성 |

## 이렇게 출제된다
- 제130회 3교시 6번: "금융 클라우드 서비스를 받는 금융회사의 데이터는 가장 중요한 자산이며 민감정보를 다룬다. 금융 클라우드 SLA(Service Level Agreement) 수립 시 고려사항을 설명하시오." → 요구 포인트: Ⅲ 보안·가용성 특화 SLA 지표 + Ⅵ 침해사고 시 배상 및 감사 권한
- 제139회 2교시 5번: "행정ㆍ공공기관의 반복적인 전산망 장애를 계기로, 정부는 「전자정부법」개정을 통해 정보시스템 등급제와 공공 SLA(행정ㆍ공공기관 정보시스템 서비스수준협약) 표준을 도입하고 있다. 도입 배경과 주요 표준 지표 및 이행 방안을 설명하시오." → 요구 포인트: Ⅰ 법 개정 배경 + Ⅲ 공공 표준 지표(등급별 RTO/RPO 및 서비스 복구) + Ⅵ 이행 방안

## 내 의견
- [인프라 핑 기반 SLA에서 트랜잭션 성공률 기반 SRE SLA로 진화] 대규모 장애가 나도 서버 포트가 열려 있으면 가용성 100%로 집계되어 배상받지 못하는 모순 발생 → 나라면: Google SRE의 오류 예산(Error Budget) 개념을 SLA에 도입하여, 비즈니스 핵심 API(로그인, 결제, 발급)의 성공률과 지연시간(p95)을 기준으로 SLA 지표를 전면 재편하고 분기별 잔여 오류 예산 초과 시 신규 기능 배포를 자동 중단하는 엔지니어링 통제를 수립
