## 지식 로드맵 내 현재 위치

IT 전략·관리 → 디지털 정책·공급망 → **기술 주권**

## 30초 인출

- 본질: 기술 주권은 핵심 기술과 서비스를 스스로 선택·운영하고 특정 국가·공급자에 대한 의존 위험을 통제할 수 있는 국가·조직의 역량
- 메커니즘: 핵심 기능 식별 → 기술·공급 의존관계 분석 → 내재화·다변화·개방 표준·전환 계약 중 전략 선택 → 전환 시험으로 실제 선택권 확인
- 통찰: 시험하지 않은 전환 권리는 공급 중단 때 작동하지 않으므로 핵심 기능별 전환 시험과 전략 선택

<details>
<summary>핵심 용어</summary>

- **기술 주권(Technology Sovereignty)** : 핵심 기술의 개발·조달·운영을 특정 외부 주체에 종속되지 않고 선택·통제할 수 있는 역량
- **전략적 자율성(Strategic Autonomy)** : 외부 충격 속에서도 필요한 정책과 전략을 스스로 선택·지속하는 능력. 기술 주권의 상위 정책 개념
- **Lock-in(종속)** : 전환 비용·기술 제약 때문에 특정 공급자에서 벗어나기 어려운 상태
- **Exit Plan(전환 계획)** : 공급자 계약 종료·중단 시 데이터 반환, 대체 환경 이전, 서비스 전환의 절차와 책임을 정한 계획
- **SBOM(Software Bill of Materials)** : 소프트웨어를 구성하는 컴포넌트·오픈소스·버전·종속성을 나열한 소프트웨어 자재명세서
- **개방 표준(Open Standard)** : 누구나 구현할 수 있게 공개된 기술 규격. 공급자 교체 가능성의 기반

## 2~4교시 25점 답안

## Ⅰ. 기술 주권의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **기술 주권(Technology Sovereignty)** 은 핵심 기술·서비스의 선택과 운영을 스스로 결정하고 외부 의존 위험을 통제하는 국가·조직의 역량 |
| 목적 | 공급 충격 시 핵심 기능의 연속성과 기술 선택권의 유지 |

## Ⅱ. 자급자족과 구별되는 기술 주권의 특징

| 특징 | 의미 |
|---|---|
| 선택권 중심 | 모든 기술의 자체 개발이 아닌, 대안을 고를 수 있는 상태의 확보 |
| 기능별 차등 대응 | 대체 불가능한 병목 기능과 대체 가능한 범용 기능의 구분 |
| 실증 가능한 통제 | 계약·규정상 권리가 아닌 실제 전환·복구 가능 여부로 판단 |

## Ⅲ. 기술 주권 확보 체계와 절차

### 기술 주권 확보 체계

```text
핵심 기능의 연속성·선택권
    │
    ├─ 대상 계층
    │     ├─ 반도체·가속기
    │     ├─ 클라우드·데이터
    │     ├─ AI 모델·소프트웨어
    │     └─ 인재·지식재산
    │
    ├─ 확보 전략 ── 내재화·다변화·개방 표준·전환 계약
    │
    └─ 검증 ── 전환 시험·의존도 감시
```

### 확보 전략 확대: 전략 선택 절차

```text
핵심 기능 식별
    ↓
기능별 기술·공급 의존관계 분석
    ↓
대체 가능성과 전환 소요 시간 판정
    ├─ 대체 불가 병목 → 내재화·공동 R&D
    └─ 대체 가능 → 다변화·개방 표준·전환 계약
    ↓
전환 시험과 의존도 재평가
```

## Ⅳ. 기술 주권 확보 전략의 비교

| 전략 | 적합 조건 | 대가·위험 |
|---|---|---|
| 내재화 | 대체 공급이 없는 병목 기술 | 장기 투자·시장성 부족 |
| 다변화 | 복수·우방 공급자가 존재하는 기술 | 조달 비용 증가·관리 부담 |
| 개방 표준·오픈소스 | 소프트웨어·인터페이스 계층 | 독자 유지보수 역량 필요 |
| 전환 계약 | 외부 서비스를 계속 쓰는 영역 | 실제 전환 미시험 시 무력화 |

## Ⅴ. 기술 주권 확보의 한계와 방안

| 한계 | 방안 |
|---|---|
| 전면 국산화 추진으로 투자 자원 분산 | 내재화는 대체 공급이 없는 병목 기술에만 선택 |
| 단일 공급자 의존에 따른 Lock-in | 대체 공급자가 있으면 다변화와 **Exit Plan** 계약 병행 |
| 독자 규격 채택으로 국제 생태계와 단절 | 소프트웨어·인터페이스 계층은 개방 표준 선택 |
| 전환 권리만 확보하고 실제 전환 경로 미확인 | 핵심 기능별 전환 시험으로 소요 시간 실측 |
| 소프트웨어 구성요소의 숨은 의존 | **SBOM** 으로 오픈소스·외부 컴포넌트 의존 파악 |

## Ⅵ. 제언

핵심 기능마다 허용 전환 시간을 정하고, 전환 시험 실측값이 이를 넘는 의존부터 확보 전략을 선택

### 전환 시간 기준 우선순위 구조

```text
핵심 기능별 허용 전환 시간
    │
    ├─ 실측 전환 시간 ── 전환 시험 결과
    │
    ├─ 대체 가능성 ── 공급자·표준 존재 여부
    │
    └─ 우선 대상 ── 허용 시간을 넘는 의존
```

### 우선 대상 확대: 전환 시험 흐름

```text
데이터 반출과 대체 환경 배포
    ↓
서비스 접속 전환과 소요 시간 측정
    ↓
허용 전환 시간과 대조
    ├─ 초과 → 다변화 또는 내재화 전략 재선택
    └─ 충족 → 다음 조달 계약의 전환 조건 유지
```

### 선택 근거: 비용 중심 조달과의 비교

| 구분 | 비용 중심 조달 | 제언: 전환 시간 기준 확보 |
|---|---|---|
| 우선 기준 | 단기 가격·성능 | 허용 전환 시간 초과 여부 |
| 공급 구조 | 최적 단일 공급자 | 기능별 다변화·내재화 선택 |
| 전환 능력 확인 | 계약 조항 존재 여부 | 전환 시험의 실측 소요 시간 |
