## 지식 로드맵 내 현재 위치

IT 전략·관리 → 인간중심 혁신·문제해결 → **디자인 씽킹**

## 30초 인출

- 본질: 디자인 씽킹(Design Thinking)은 사용자를 관찰해 해결할 문제를 다시 정의하고 시제품으로 해법을 시험하는 인간 중심 문제 해결 방법
- 메커니즘: 공감·문제 정의로 문제 공간을 좁히고 아이디어·시제품·시험으로 해법을 검증하며, 시험 결과에 따라 앞 단계로 복귀
- 통찰: 워크숍 결과가 개발로 이어지지 않으면 해법이 추측으로 돌아가므로 관찰한 사용자 행동의 백로그 연결

<details>
<summary>핵심 용어</summary>

- **디자인 씽킹(Design Thinking)** : 사용자 관찰로 문제를 재정의하고 시제품 시험으로 해법을 검증하는 인간 중심 문제 해결 방법
- **Empathize(공감)** : 관찰·인터뷰로 사용자의 맥락과 드러나지 않은 필요를 파악하는 단계
- **Define(문제 정의)** : 관찰 결과를 종합해 해결할 문제를 사용자·필요·통찰의 한 문장으로 좁히는 단계
- **POV(Point of View)** : 사용자·필요·통찰을 결합해 해결할 문제를 표현한 관점 진술문
- **HMW(How Might We)** : POV를 "어떻게 하면 …할 수 있을까"라는 질문으로 바꿔 아이디어 발산을 여는 기법
- **Prototype(시제품)** : 검증할 가정 하나를 사용자가 체험할 수 있게 만든 저비용 시험물
- **린 스타트업(Lean Startup)** : 해법 가설을 MVP로 시장에 내놓고 측정 결과로 유지·전환을 결정하는 제품 개발 방식
- **MVP(Minimum Viable Product)** : 핵심 가설을 실제 사용자에게 검증할 수 있는 최소 기능 제품
- **제품 백로그(Product Backlog)** : 애자일 개발에서 구현할 항목을 우선순위대로 정리한 목록

## 2~4교시 25점 답안

## Ⅰ. 디자인 씽킹의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **디자인 씽킹(Design Thinking)** 은 사용자 관찰로 해결할 문제를 재정의하고 시제품 시험으로 해법을 검증하는 인간 중심 문제 해결 방법 |
| 목적 | 사용자가 실제로 겪는 문제에 맞는 해법 도출과 개발 전 잘못된 가정의 조기 발견 |

## Ⅱ. 기능 중심 기획과 구별되는 디자인 씽킹의 특징

| 특징 | 의미 |
|---|---|
| 사용자 맥락 중심 | 내부 추측보다 관찰·인터뷰로 확인한 행동 근거 우선 |
| 문제 재정의 | 해법 결정 전 사용자 필요와 원인의 재확인 |
| 발산과 수렴의 반복 | 문제·해법 공간마다 대안을 넓힌 뒤 하나로 좁히는 사고 |
| 시제품 기반 검증 | 완성품 이전 저비용 시험물로 가정의 조기 확인 |

## Ⅲ. 디자인 씽킹의 5단계와 시험 판정

### 디자인 씽킹 수행 체계

```text
문제 공간
    Empathize(공감) ── 관찰·인터뷰
        ↓
    Define(문제 정의) ── POV
        ↓
해법 공간
    Ideate(아이디어) ── HMW 기반 발산·선정
        ↓
    Prototype(시제품) ── 검증 가정별 시험물
        ↓
    Test(시험) ── 사용자 과업 관찰
        ↓
    결과에 따라 필요한 앞 단계로 복귀
```

Stanford d.school의 5단계 구분이며, 단계는 고정 순서가 아니라 시험 결과에 따라 앞뒤로 오가는 반복 구조

### Test 확대: 시제품 시험 결과의 판정

```text
사용자 과업 수행 관찰
    ↓
검증 가정의 성립 여부 확인
    ├─ 문제 정의 오류 → Empathize·Define 재수행
    ├─ 해법의 과업 지원 실패 → Ideate·Prototype 재수행
    └─ 가정 성립 → 개발 대상 확정
```

## Ⅳ. 디자인 씽킹·린 스타트업·애자일의 선택 기준

| 구분 | 디자인 씽킹 | 린 스타트업 | 애자일 |
|---|---|---|---|
| 줄이는 불확실성 | 어떤 문제를 풀지 | 해법이 시장에서 통할지 | 확정된 해법을 어떻게 만들지 |
| 적용 조건 | 사용자 문제가 불명확 | 문제는 확인, 수요·지불 의사 불확실 | 요구가 정해졌으나 변경 가능 |
| 검증 수단 | **Prototype(시제품)** 시험 | **MVP** 의 시장 지표 측정 | 반복 주기별 동작하는 제품 |
| 산출 | 재정의된 문제와 검증된 해법 개념 | 유지·전환 결정 | 출시 가능한 기능 증분 |

세 방식은 대체 관계가 아니라 문제 탐색 → 시장 검증 → 반복 개발로 이어지는 연속 선택이며, 불확실성의 종류에 따라 시작 지점 결정

## Ⅴ. 디자인 씽킹 적용의 한계와 방안

| 한계 | 방안 |
|---|---|
| 내부 담당자의 추측으로 사용자 문제 정의 | 실제 사용자·극단 사용자의 현장 관찰과 인터뷰 |
| 해법을 먼저 정한 채 형식적으로 단계 수행 | Define 완료 전 해법 논의 보류와 **POV** 기준의 아이디어 평가 |
| 문제는 확인됐으나 수요·지불 의사가 불확실 | 린 스타트업 선택: MVP로 시장 지표 측정 후 유지·전환 판단 |
| 워크숍 산출물과 개발 항목의 단절 | 애자일 인계: 시험을 통과한 해법의 **제품 백로그(Product Backlog)** 항목 전환 |

## Ⅵ. 제언

시제품 시험에서 관찰한 사용자 행동을 문제 정의와 개발 백로그 항목에 연결해 해법 결정의 근거로 유지

### 시험 증거의 연결 구조

```text
시제품 시험의 관찰 기록
    │
    ├─ POV ── 어떤 사용자의 어떤 문제인지
    │
    ├─ 검증 가정 ── 성립·기각 결과
    │
    └─ 개발 백로그 항목 ── 가정이 성립한 해법만 등록
```

### 개발 백로그 확대: 시험 결과의 개발 인계 절차

```text
가정 성립 해법 선정
    ↓
관찰 근거와 인수 조건을 붙여 백로그 등록
    ↓
출시 후 같은 과업의 사용자 행동 재관찰
    ↓
문제 재발 시 POV 재검토
```

### 선택 근거: 워크숍 중심 운영과의 비교

| 구분 | 워크숍 중심 운영 | 제언: 시험 증거 연결 운영 |
|---|---|---|
| 해법 결정 근거 | 참여자 합의·선호 | 사용자 과업 관찰 결과 |
| 개발 인계 대상 | 아이디어 목록 | 가정이 성립한 해법과 관찰 근거 |
| 출시 후 처리 | 활동 종료 | 같은 과업의 재관찰과 POV 재검토 |
