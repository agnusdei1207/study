## 지식 로드맵 내 현재 위치

IT 전략·관리 → IT 서비스 지속성·재해복구 → **DRS**

## 30초 인출

- 본질: DRS(Disaster Recovery System)는 주 전산센터가 멈췄을 때 대체 센터에서 IT 서비스를 되살리고 다시 원래 센터로 돌려놓기 위한 시스템·절차 체계
- 메커니즘: 업무별 복구 목표에 맞춰 대체 센터 유형과 데이터 준비 방식을 정하고, 장애 시 재해 선포 → 복구 → 전환(Failover), 정상화 후 역동기화 → 복귀(Failback)
- 통찰: 주 센터 변경이 DR에 반영되지 않으면 절체가 실패하므로 변경 승인 시 DR 형상·Runbook 반영의 완료 조건화

<details>
<summary>핵심 용어</summary>

- **DRS(Disaster Recovery System)** : 재해·장애로 주 센터가 멈췄을 때 대체 센터에서 서비스·데이터를 복구하고 원래 센터로 복귀시키는 시스템·절차 체계
- **RTO(Recovery Time Objective)** : 서비스 중단 후 재개까지 허용하는 목표 시간
- **RPO(Recovery Point Objective)** : 복구 시 되돌아갈 수 있는 데이터 시점의 한계, 곧 허용 데이터 손실 범위
- **Mirror Site** : 주 센터와 같은 환경을 상시 가동하며 데이터를 실시간 반영하는 대체 센터
- **Hot Site** : 장비·네트워크·데이터 복제가 준비되어 짧은 시간 안에 기동할 수 있는 대체 센터
- **Warm Site** : 일부 장비와 통신만 준비되어 장비 보강·데이터 복원 뒤 기동하는 대체 센터
- **Cold Site** : 공간·전력·냉방 등 기반 시설만 갖추고 장비 반입부터 시작하는 대체 센터
- **Failover** : 장애 시 서비스 처리 주체와 트래픽을 대체 센터로 넘기는 전환
- **Failback** : 주 센터 정상화 후 대체 센터의 변경 데이터를 역동기화하고 서비스를 원래 센터로 되돌리는 복귀
- **Runbook** : 재해 선포부터 전환·복귀까지 역할별 수행 순서와 명령을 적은 복구 절차서
- **형상 동기화** : 주 센터의 서버·소프트웨어·설정 변경을 대체 센터에 같은 상태로 반영하는 관리 활동

## 2~4교시 25점 답안

## Ⅰ. DRS의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **DRS(Disaster Recovery System)** 는 주 센터 중단 시 대체 센터에서 IT 서비스를 복구하고 원래 센터로 복귀시키는 시스템·절차 체계 |
| 목적 | 업무별 허용 중단 시간·데이터 손실 범위 안의 서비스 재개 |

## Ⅱ. 단순 백업과 구별되는 DRS의 특징

| 특징 | 의미 |
|---|---|
| 목표 기반 설계 | **RTO** 와 **RPO** 에 따른 대체 센터 수준과 데이터 준비 방식의 결정 |
| 다계층 복구 | 데이터뿐 아니라 시스템·네트워크·인증 등 공통서비스의 함께 기동 |
| 양방향 전환 | 대체 센터로의 **Failover** 와 원래 센터로의 **Failback** 을 모두 포함 |
| 상시 동기화 | 주 센터 변경을 대체 센터에 계속 반영해야 유지되는 준비 상태 |

## Ⅲ. DRS 구성 체계와 복구·복귀 절차

### DRS 구성 체계

```text
DRS
    │
    ├─ 복구 목표 ── 업무별 RTO·RPO
    │
    ├─ 대체 센터 ── Mirror·Hot·Warm·Cold Site
    │
    ├─ 복구 대상 계층
    │     ├─ 데이터 ── 복제·백업
    │     ├─ 시스템 ── 서버·가상화·용량
    │     ├─ 네트워크 ── 회선·DNS·GSLB
    │     └─ 공통서비스 ── 인증·키 관리
    │
    └─ 운영 체계 ── 재해 선포 기준·Runbook·훈련
```

### 운영 체계 확대: 전환·복귀 절차

```text
재해 선포와 복구 결정
    ↓
데이터·시스템·공통서비스 기동
    ↓
업무 확인 후 트래픽 전환(Failover)
    ↓
주 센터 정상화와 변경 데이터 역동기화
    ↓
정합성 확인 후 원래 센터 복귀(Failback)
```

## Ⅳ. DRS 구축 유형 비교

| 구분 | Mirror Site | Hot Site | Warm Site | Cold Site |
|---|---|---|---|---|
| 대체 센터 준비 | 주 센터와 같은 환경 상시 가동 | 장비·통신 대기 | 일부 장비·통신 | 공간·전력 등 기반 시설 |
| 데이터 준비 | 실시간 반영 | 동기·비동기 복제 | 주기적 복제·백업 | 백업 매체 복원 |
| 복구 시간 수준 | 가장 짧음 | 짧음 | 중간 | 김 |
| 구축·운영 비용 | 가장 큼 | 큼 | 중간 | 작음 |
| 적합 업무 | 중단 허용이 거의 없는 핵심 업무 | 짧은 RTO의 주요 업무 | 수 시간~일 단위 허용 업무 | 장기 중단 허용 업무 |

복구 시간이 짧은 유형일수록 대체 센터를 주 센터와 같은 상태로 유지하는 부담 증가. NIST SP 800-34 Rev.1은 준비 수준에 따른 기본 3유형을 Cold·Warm·Hot Site로 두고, Mirrored Site(실시간 미러링의 완전 이중 시설)와 Mobile Site(이동형 설비)를 변형 유형으로 구분

## Ⅴ. DRS 구축·운영의 한계와 방안

| 한계 | 방안 |
|---|---|
| 전 업무에 같은 유형 적용으로 비용 과다 또는 목표 미달 | 짧은 RTO 업무만 Mirror·Hot Site, 나머지는 Warm·Cold Site 선택 |
| 데이터만 복제하고 인증·DNS 등 공통서비스 누락 | 복구 대상에 공통서비스를 포함하고 주 센터 단절 상태의 기동 시험 |
| 주 센터 변경 후 대체 센터 형상과 **Runbook** 의 불일치 | 변경 승인 시 DR 형상·Runbook 반영 여부의 확인 |
| 전환만 훈련하고 복귀 미검증 | 역동기화·정합성 확인을 포함한 Failback 리허설 |

## Ⅵ. 제언

주 센터의 변경 승인에 DR 형상과 Runbook 반영을 완료 조건으로 묶어, Hot Site 이상 업무부터 대체 센터의 준비 상태를 상시 유지

### DR 준비 상태 유지 구조

```text
주 센터 변경 요청
    │
    ├─ 운영 시스템 ── 서버·설정·소프트웨어 변경
    │
    ├─ 대체 센터 ── 같은 변경의 형상 동기화
    │
    └─ 복구 절차 ── Runbook·복구 대상 목록 갱신
```

### 형상 동기화 확대: 변경 완료 판정

```text
주 센터 변경 적용
    ↓
대체 센터 형상 비교
    ├─ 불일치 → 대체 센터 반영 후 재비교
    └─ 일치 → Runbook 갱신 확인
            ↓
        변경 완료 승인
```

### 선택 근거: 정기 훈련 중심 관리와의 비교

| 구분 | 정기 훈련 중심 관리 | 제언: 변경 연동 관리 |
|---|---|---|
| 불일치 발견 시점 | 연 1~2회 훈련 때 | 변경 승인 단계 |
| 대체 센터 상태 | 훈련 직후에만 최신 | 변경마다 최신 유지 |
| Runbook 갱신 주체 | DR 담당자 일괄 | 변경 담당자가 변경과 함께 |
| 훈련의 역할 | 불일치 발견 수단 | 유지 상태의 확인 수단 |
