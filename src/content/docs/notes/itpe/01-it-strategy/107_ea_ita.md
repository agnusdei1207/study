## 지식 로드맵 내 현재 위치

IT 전략·관리 → 정보화 기획·거버넌스 → **EA·ITA**

## 30초 인출

- 본질: EA·ITA는 조직의 업무·응용·데이터·기술·보안 구성요소와 그 관계를 전사 관점으로 정리하고, 이를 기준으로 정보화를 최적화하는 체계
- 메커니즘: 현행(As-Is)과 목표(To-Be) 아키텍처의 차이에서 이행 과제를 도출하고, 참조모형으로 기관 간 공통 분류를 맞춘 뒤 투자 심의에 적용
- 통찰: 투자 결정과 끊긴 EA는 곧 낡으므로 사업 심의의 EA 적합성 검토와 종료 시 현행화 의무화

<details>
<summary>핵심 용어</summary>

- **EA·ITA** : 조직 구성요소와 그 관계를 전사 관점에서 정리하고 정보화 최적화의 기준으로 쓰는 아키텍처 체계
- **EA(Enterprise Architecture)** : 전략·업무·데이터·응용·기술의 관계를 전사 관점에서 기술하는 전사 아키텍처
- **ITA(Information Technology Architecture)** : 「전자정부법」상 정보기술아키텍처. 업무·응용·데이터·기술·보안 등 조직 전체 구성요소의 관계를 구조적으로 정리한 체제와 그 최적화 방법
- **참조모형(Reference Model)** : 기관 간 아키텍처를 같은 기준으로 분류·비교하도록 범정부 차원에서 정한 공통 분류 체계
- **PRM·BRM·SRM·DRM·TRM** : 성과·업무·서비스·데이터·기술 참조모형
- **EAMS(Enterprise Architecture Management System)** : 아키텍처 산출물과 정보자원 정보를 등록·조회·활용하는 관리 시스템
- **Gap 분석** : 현행과 목표 아키텍처의 차이를 식별해 이행 과제를 도출하는 분석

## 2~4교시 25점 답안

## Ⅰ. EA·ITA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **EA·ITA** 는 조직의 업무·응용·데이터·기술·보안 구성요소의 관계를 전사 관점에서 정리하고 정보화 최적화에 쓰는 아키텍처 체계 |
| 목적 | 정보화 중복 투자 방지와 시스템 간 상호운용성 확보 |

## Ⅱ. 전사 관점의 구조 기준이라는 EA·ITA의 특징

| 특징 | 의미 |
|---|---|
| 전사 관점 | 개별 시스템이 아닌 조직 전체 구성요소의 관계 기술 |
| 현행·목표 연결 | **Gap 분석** 으로 이행 과제와 순서 도출 |
| 법정 제도 | 공공부문은 「전자정부법」에 따른 도입·운영 의무(대상 기관) |
| 의사결정 기준 | 정보화 투자·사업 심의의 적합성 판단 근거 |

## Ⅲ. EA·ITA 구성 체계와 수립 절차

### 구성 체계

```text
EA·ITA
    │
    ├─ 방향 ── 비전·원칙·범위·프레임워크
    │
    ├─ 아키텍처
    │     ├─ 업무 ── 업무 기능·프로세스
    │     ├─ 응용 ── 응용 시스템·서비스
    │     ├─ 데이터 ── 데이터 구조·흐름
    │     ├─ 기술 ── 인프라·표준
    │     └─ 보안 ── 보안 구조·통제
    │
    ├─ 참조모형 ── 기관 간 공통 분류 기준
    │
    └─ 관리 ── 조직·절차·EAMS·현행화
```

### 아키텍처 확대: 현행에서 목표로의 이행 절차

```text
현행(As-Is) 아키텍처 조사
    ↓
목표(To-Be) 아키텍처 설계
    ↓
영역별 Gap 분석 ── 업무·응용·데이터·기술·보안
    ↓
이행 과제 도출과 의존성·우선순위 결정
    ↓
이행계획 수립과 투자 심의 반영
```

## Ⅳ. 범정부 참조모형과 기관 아키텍처의 관계

| 참조모형 | 분류 대상 | 대응하는 기관 아키텍처 |
|---|---|---|
| PRM(성과) | 정보화 성과 지표 | 전 영역의 성과 측정 |
| BRM(업무) | 기관과 무관한 업무 기능 | 업무 아키텍처 |
| SRM(서비스) | 응용 서비스·컴포넌트 | 응용 아키텍처 |
| DRM(데이터) | 데이터 분류·구조·교환 | 데이터 아키텍처 |
| TRM(기술) | 기술·표준 | 기술 아키텍처 |

참조모형은 기관별 아키텍처를 같은 분류로 비교하게 해 기관 간 중복 시스템과 재사용 대상을 식별하는 기준

## Ⅴ. EA·ITA 운영의 한계와 방안

| 한계 | 방안 |
|---|---|
| 산출물 작성 자체가 목적이 되어 투자 결정과 단절 | 정보화 사업 심의에 EA 적합성 검토를 필수 관문으로 지정 |
| 시스템 변경 후 산출물 미갱신으로 현행 정보 노후화 | 사업 종료·변경 시 EAMS 현행화를 완료 조건으로 지정 |
| 기관별 분류 차이로 기관 간 중복 식별 곤란 | 범정부 참조모형 분류 체계로 기관 아키텍처 매핑 |
| 모든 영역의 상세 산출물 작성으로 유지 부담 증가 | 투자 심의에 쓰는 핵심 산출물부터 우선 관리 |

## Ⅵ. 제언

정보화 사업 심의에 EA 적합성 검토를 관문으로 두고, 사업 종료 시 EAMS 현행화를 완료 조건으로 연결

### EA 연계 사업 관리 구조

```text
EA·ITA 기준
    │
    ├─ 사업 심의 ── 목표 아키텍처·참조모형 적합성
    │
    ├─ 사업 수행 ── 승인된 아키텍처 기준의 설계·구축
    │
    └─ 사업 종료 ── EAMS 현행화와 이행 과제 갱신
```

### 사업 심의 확대: EA 적합성 검토 절차

```text
신규 사업의 기능·데이터·기술 식별
    ↓
참조모형 기준 기존 시스템과의 중복 확인
    ├─ 중복 있음 → 기존 시스템 재사용·통합 검토
    └─ 중복 없음 → 목표 아키텍처와의 부합 확인
                      ↓
                 예외 시 사유·기한 기록 후 승인
```

### 선택 근거: 문서 중심 운영과의 비교

| 구분 | 문서 중심 운영 | 제언: 사업 심의·종료 연계 |
|---|---|---|
| EA 활용 시점 | 수립·정기 갱신 시 | 개별 사업의 심의·종료 시 |
| 현행화 계기 | 정기 갱신 주기 | 사업 종료·변경 |
| 중복 투자 식별 | 사후 점검 | 심의 단계에서 사전 차단 |
