## 큰 그림과 30초 인출

```text
         [GSLB / Anycast DNS] (트래픽 동시 분산 및 헬스체크)
            ┌───────────────┴───────────────┐
            ▼                               ▼
    [제1 센터 (Active)]             [제2 센터 (Active)]
     ├─ 웹/WAS 풀 (동시 처리)        ├─ 웹/WAS 풀 (동시 처리)
     └─ 스토리지 (Primary)           └─ 스토리지 (Secondary/Active)
            │                               │
            └── 양방향 동기/비동기 블록 복제 ──┘
                            │
            [제3 거점: 쿼럼 위트니스 (Split-Brain 방지)]
```

- 본질: 2개 이상의 독립된 원격 데이터센터가 평상시에 트래픽을 동시 분산 처리하다가, 단일 센터 전멸 시 무중단(RTO≈0, RPO=0)으로 연속성을 보장하는 고가용 인프라 아키텍처
- 위치: `재해복구전략 → Active-Standby 한계 극복 → Active-Active 전환 → 스토리지 미러링 및 쿼럼 통제`
- 핵심: GSLB 기반 트래픽 제어 + 스토리지 간 동기식 미러링 + 스플릿 브레인 방지를 위한 제3 거점 쿼럼(Quorum) 배치
- 트레이드오프: 무중단 가용성을 확보하는 대가로 센터 간 네트워크 지연(Latency)과 막대한 인프라 TCO 발생

## 예상문제

> 다중 거점 기반 액티브-액티브(Active-Active) 데이터센터 및 스토리지 DR의 구성 메커니즘을 설명하고, 동기/비동기 복제 방식의 특징과 스플릿 브레인(Split-Brain) 방지 대책을 논하시오. (25점)

## Ⅰ. 무중단 서비스 연속성을 위한 액티브-액티브 DR 개요

- 정의: 둘 이상의 물리적으로 격리된 데이터센터에 서버와 스토리지를 상시 가동(Active) 상태로 배치하여 부하를 분산하고, 한 거점 상실 시에도 잔여 거점이 서비스 중단 없이 워크로드를 승계하는 재해복구 체계
- 배경: 기존 Active-Standby 구조는 재해 발생 시 대기계 부팅, IP 변경, 데이터 검증에 따른 RTO 지연과 유휴 자원의 낭비 한계 노출
- 목적: 핵심 비즈니스 및 국가 행정 서비스의 목표복구시간(RTO≈0) 및 목표복구시점(RPO=0) 동시 달성

#### 한줄 요약
- 상시 분산 가동과 실시간 스토리지 동기화를 통해 재해 발생 시 전환 지연을 원천 제거하는 구조임

## Ⅱ. 4대 핵심 설계 원칙과 기술적 전제조건

| 설계 원칙 | 공학적 메커니즘 | 보장 효과 |
|---|---|---|
| **물리적 장애격리** | 전력망, 통신 사업자, 공조 시스템의 완전 독립 거점 배치 | 대규모 화재·정전의 동시 전파 차단 |
| **애플리케이션 무상태화** | 세션을 로컬 메모리에 두지 않고 분산 캐시(Redis)에 저장 | 트래픽 전환 시 사용자 재로그인 방지 |
| **데이터 정합성 보장** | 분산 트랜잭션의 2PC 또는 분산 합의 알고리즘(Raft) 적용 | 양 센터 동시 쓰기 시 데이터 충돌 방지 |
| **스플릿 브레인 방지** | 제3 거점에 독립적인 쿼럼 위트니스(Witness) 배치 | 네트워크 단절 시 양 센터 동시 쓰기 차단 |

#### 한줄 요약
- 무상태 애플리케이션과 독립 쿼럼 배치를 통해 분산 환경의 정합성과 생존성을 확보함

## Ⅲ. 계층별 시스템 아키텍처

```text
[글로벌 사용자 및 연계망]
           │
           ▼
[GSLB / DNS 트래픽 분산 레이어]
   ┌───────┴───────┐ (RTT 기반 근접 라우팅)
   ▼               ▼
[제1 데이터센터]  [제2 데이터센터]
 ├─ L4/L7 로드밸런서├─ L4/L7 로드밸런서
 ├─ 웹/WAS 클러스터  ├─ 웹/WAS 클러스터
 ├─ 분산 세션 캐시   ├─ 분산 세션 캐시
 └─ 스토리지 엔진    └─ 스토리지 엔진
   │               │
   └── 스토리지 볼륨 미러링 (광채널 ISL) ──┘
           │
           ▼
 [제3 사이드 쿼럼 중재자 (Witness)]
```

| 계층 | 핵심 구성요소 | 역할 및 통제 기능 |
|---|---|---|
| **트래픽 제어 계층** | GSLB (Global Server Load Balancing) | 센터 헬스체크, 지리적 근접성 및 가중치 기반 트래픽 분산 |
| **애플리케이션 계층** | 컨테이너 오케스트레이션(K8s) | 거점 간 파드(Pod) 분산 배치 및 수평 자동 확장(HPA) |
| **세션·캐시 계층** | 글로벌 분산 인메모리 DB | 양 센터 간 실시간 사용자 세션 상태 동기화 |
| **스토리지 계층** | 스토리지 가상화, Metro Mirror | 블록 레벨 동기식 미러링, 단일 가상 볼륨 제공 |
| **중재 계층** | 쿼럼 위트니스(Quorum Witness) | 센터 간 하트비트 단절 시 생존 센터 판정 및 I/O 펜싱 |

#### 한줄 요약
- GSLB부터 스토리지까지 전 계층이 이원화되어 작동하며 쿼럼이 단절 시 쓰기 권한을 통제함

## Ⅳ. 스토리지 데이터 복제 방식과 절체 흐름

```text
동기 복제:   App 쓰기 ──> 주 스토리지 ──(미러링 전송)──> 원격 스토리지 ──(ACK)──> 완료 반환
비동기 복제: App 쓰기 ──> 주 스토리지 ──(즉시 ACK)──> 완료 반환 / ──(백그라운드 전송)──> 원격 스토리지
```

| 구분 | 동기식 복제 (Synchronous) | 비동기식 복제 (Asynchronous) |
|---|---|---|
| **동작 메커니즘** | 양쪽 스토리지에 모두 쓰기가 완료된 후 호스트에 응답 | 로컬 스토리지에 쓴 뒤 호스트에 즉시 응답하고 원격지로 전송 |
| **데이터 손실 (RPO)** | **RPO = 0** (데이터 손실 없음) | **RPO > 0** (전송 지연 버퍼만큼 미세 손실 가능) |
| **거리 제약** | 광케이블 지연(RTT)으로 인해 **통상 수십 km 이내** 권장 | 거리 제약 없음 (대륙 간, 원거리 DR 구축 가능) |
| **트랜잭션 지연** | 네트워크 RTT가 애플리케이션 응답시간에 직접 누적 | 호스트 쓰기 성능에 영향 없음 |
| **주 적용 분야** | 계정계 금융 거래, 핵심 결제, 최상위 공공 행정 | 정보계, 빅데이터 저장소, 원거리 재해복구 백업 |

#### 한줄 요약
- 근거리는 동기 복제로 RPO=0을 달성하고, 장거리는 비동기 복제로 트랜잭션 지연을 방어함

## Ⅴ. Active-Active vs Active-Standby 구조 비교

| 비교 항목 | 액티브-액티브 (Active-Active) | 액티브-스탠바이 (Active-Standby) |
|---|---|---|
| **평시 운영 상태** | 양 센터 모두 실제 워크로드 동시 처리 | 주 센터만 운영, 대기 센터는 유휴 대기 |
| **목표 복구 시간** | **RTO ≈ 0** (트래픽 재라우팅만으로 수 초 내 전환) | **RTO 수십 분 ~ 수 시간** (대기계 기동 및 DB 승격 필요) |
| **목표 복구 시점** | **RPO = 0** (동기 복제 기반 완전 무손실) | **RPO 수 분 ~ 수 시간** (비동기 복제 및 백업 주기 의존) |
| **자원 활용률** | 투자된 인프라 자원을 100% 실무에 활용 | 대기 센터 자원이 유휴화되어 TCO 효율 저하 |
| **기술적 복잡도** | 스플릿 브레인, 세션 동기화, 이중 쓰기 충돌 방지 고도화 | 단순 단방향 복제로 구조가 상대적으로 명확함 |
| **전환 리스크** | 자동 절체로 인적 개입 최소화 | 절체 매뉴얼 불일치, DB 기동 실패 등 인적 오류 위험 |

#### 한줄 요약
- Active-Active는 높은 복잡도와 비용을 감수하고 절대적 RTO=0/RPO=0을 달성하는 구조임

## Ⅵ. 실무 실패 모드와 공학적 대응 방안

- 적용 상황: 금융 거래 시스템 및 대국민 행정 포털의 1등급 재해복구 아키텍처 구축

| 실패 모드 | 발생 원인 | 공학적 해결 대책 | 기대 효과 |
|---|---|---|---|
| **스플릿 브레인 (Split-Brain)** | 센터 간 네트워크 전용선 단절 시 양 센터가 독립 마스터로 승격 | 제3 거점 독립 쿼럼 위트니스 배치 및 다수결 기반 I/O 펜싱(Fencing) | 양방향 동시 쓰기로 인한 데이터 오염 원천 방지 |
| **N-1 용량 초과 장애** | 한 센터 상실 시 단일 센터의 CPU·메모리가 전체 트래픽 수용 불가 | 평시 센터당 최대 사용률을 50% 이하로 통제(N-1 설계) 및 HPA 연계 | 장애 센터 절체 시 잔여 센터 연쇄 다운 차단 |
| **복제 지연에 따른 병목** | 피크 타임 스토리지 I/O 급증 및 광선로 패킷 손실 | DWDM 고속 전용선 대역폭 증설 및 스토리지 캐시 버퍼 최적화 | 애플리케이션 응답 지연(Latency) 방어 |
| **논리적 데이터 손상 전파** | 애플리케이션 버그나 악의적 쿼리가 양 센터에 실시간 동기화 | 실시간 복제 외에 제3 거점에 스냅샷 기반 격리 불변 백업 병행 | 논리적 데이터 오염 시 시점 복구(PITR) 가능 |

#### 한줄 요약
- 제3 거점 쿼럼으로 스플릿 브레인을 막고, 50% 이하 부하 관리(N-1)로 연쇄 붕괴를 차단함

## Ⅶ. SLA와 RTO/RPO 정합성 중심의 결론

- **[인프라 스펙이 아닌 실제 복구 검증이 핵심]**: 액티브-액티브 구성은 장비 도입만으로 완결되지 않으며, 회선 장애, 쿼럼 판정, 잔여 용량 한계 등 실무 실패 모드를 통제해야만 진정한 회복탄력성이 입증됨
- 나라면: 아키텍처 설계 시 `센터 간 RTT 지연 5ms 이내 전용선 확보 → 제3 거점 클라우드 쿼럼 구성 → 분기별 1회 센터 강제 셧다운 모의 절체 훈련`을 운영 SLA에 명시하여 무중단 복구 체계를 실증

#### 한줄 요약
- 기술적 화려함보다 지연 시간 통제와 정기적 실전 절체 검증이 액티브-액티브의 성패를 가름

## 1교시 10점 답안 발췌

### 1. 액티브-액티브(Active-Active) 스토리지 DR의 정의
- 2개 이상의 지리적 거점에 스토리지와 서버를 동시에 활성화하여 트래픽을 분산 처리하고, 센터 재난 시 트래픽 재라우팅을 통해 RTO≈0, RPO=0을 달성하는 무중단 DR 아키텍처

### 2. 핵심 아키텍처 및 쿼럼 메커니즘
```text
[GSLB 트래픽 분산] ──> [Center A (Active) <──동기 복제──> Center B (Active)]
                                   │                           │
                                   └───────> [Quorum (제3 거점)] <───────┘
```

| 복제 방식 | RPO 수준 | 거리 한계 | 핵심 메커니즘 |
|---|---|---|---|
| 동기식 복제 | RPO = 0 | 통상 50km 이내 | 양 스토리지 쓰기 완료 후 Host 응답, RTT 지연 누적 |
| 비동기식 복제 | RPO > 0 | 무제한 | 로컬 완료 후 백그라운드 전송, 장거리 재해복구 적합 |

### 3. 차별화 제언
- 회선 단절 시 양 센터가 독자 마스터가 되는 스플릿 브레인을 방지하기 위해 반드시 제3 거점 쿼럼 위트니스를 배치하고, 단일 센터 상실에 대비한 N-1 용량 설계를 엄수해야 함
