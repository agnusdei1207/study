## 지식 로드맵 내 현재 위치

IT 전략·관리 → 재해복구·서비스 연속성 → **액티브-액티브 이중화와 스토리지 DR**

## 30초 인출

- 본질: 액티브-액티브 이중화와 스토리지 DR은 재해복구시스템의 구축 방식으로, 액티브-액티브는 서로 다른 데이터센터의 시스템이 동시에 서비스하고 스토리지 DR은 데이터만 다른 데이터센터에 복제해 두는 방식
- 메커니즘: 정보시스템 등급별 복구 목표(RTO·RPO)에 따라 A1 Active-Active, A2 Active-Standby, A3 스토리지 DR, A4 원격지 소산을 고르며, 복구 목표가 엄격할수록 보조 시스템을 미리 갖춤
- 통찰: 연속 복제는 데이터 손상·악의적 삭제에 시점 백업만큼 대응하지 못하고 복구점도 발견 이전 시점에 머물므로, 복제 경로와 분리한 시점 복구용 백업을 다른 계정·원격지에 보관

<details>
<summary>핵심 용어</summary>

- **액티브-액티브 이중화와 스토리지 DR** : 등급별 재해복구 목표에 맞춰 보조 시스템을 동시 서비스로 운영하거나 데이터만 원격 복제하는 재해복구 구축 방식
- **DR(Disaster Recovery)·재해복구시스템** : 재해로 정보시스템이 중단됐을 때 서비스를 신속히 복구하고 업무 연속성을 유지하도록 구축한 시스템
- **Active-Active(액티브-액티브)** : 주 시스템과 같은 기능의 보조 시스템을 다른 데이터센터에 미리 구성해 두 시스템이 동시에 서비스하는 구축 방식
- **Active-Standby(액티브-스탠바이)** : 보조 시스템을 미리 구성하고 주 시스템 데이터를 실시간 동기화해 두었다가 주 시스템 중단 시 대체하는 구축 방식
- **스토리지 DR** : 보조 시스템 없이 주 시스템 데이터만 다른 데이터센터에 실시간 복제해 두었다가 중단 시 정보자원을 새로 구성해 서비스하는 구축 방식
- **원격지 소산** : 주기적으로 백업한 보존매체를 원격지에 보관하는 방식. 백업 주기에 따라 일부 데이터 손실 가능
- **RTO(Recovery Time Objective)** : 복구시간목표. 재해 선포 시점부터 재해복구시스템을 가동하고 핵심 기능이 정상임을 확인한 시점까지의 목표
- **RPO(Recovery Point Objective)** : 복구시점목표. 데이터를 어느 시점까지 복구할지의 목표
- **Multi-Region Active-Active** : 서로 다른 리전에 같은 워크로드를 배포해 모든 리전이 트래픽을 처리하는 구성
- **Pilot Light(파일럿 라이트)** : 데이터를 복제하고 핵심 인프라 사본은 두되 애플리케이션 서버는 꺼 두었다가 재해 때 켜는 방식
- **Warm Standby(웜 스탠바이)** : 축소한 규모의 완전한 사본을 다른 리전에서 상시 가동하는 방식
- **정보시스템 등급(A1~A4)** : 정보시스템의 중요도·영향도에 따른 등급. 재해복구 목표와 구축 방식의 기준

## 2~4교시 25점 답안

## Ⅰ. 액티브-액티브 이중화와 스토리지 DR의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **액티브-액티브 이중화와 스토리지 DR** 은 등급별 재해복구 목표에 맞춰 보조 시스템을 동시 서비스로 운영하거나 데이터만 원격 복제하는 재해복구 구축 방식 |
| 목적 | 재해 시 **RTO** (복구시간목표)와 **RPO** (복구시점목표)의 등급별 목표 충족 |

## Ⅱ. 복구 시간이 짧은 대신 복잡한 구성의 특징

| 특징 | 의미 |
|---|---|
| 동시 서비스 | 다른 데이터센터의 보조 시스템이 주 시스템과 동시에 서비스 |
| 전환 절차 없는 복구 | 여러 리전이 서비스를 제공하므로 한 리전을 잃으면 다른 리전으로 트래픽을 재분배 |
| 복구 시간 근접 0 | 올바른 기술 선택·구현으로 대부분의 재해에서 복구 시간을 0에 가깝게 단축 |
| 최고 수준의 복잡도·비용 | 재해복구 방식 중 가장 복잡하고 비용이 큼 |
| 스토리지 DR의 단순한 구성 | 보조 시스템 없이 데이터만 복제, 복구 때 정보자원을 새로 구성 |
| 데이터 재해에 취약 | 연속 복제는 데이터 손상·악의적 삭제에 시점 백업만큼 대응하지 못하며, 데이터 재해의 복구점은 발견 이전 시점 |

## Ⅲ. 재해복구 구축 체계

### 등급별 재해복구 목표와 구축 방식

```text
A1  RTO 실시간~1시간 · RPO 0(실시간)  ▶ Active-Active
     ↓ 복구 목표 완화, 보조 시스템 구성 축소
A2  RTO 3~12시간 · RPO 수 분           ▶ Active-Standby
     ↓
A3  RTO 1~5일 · RPO 수 분              ▶ 스토리지 DR
     ↓
A4  RTO 3주 · RPO 1~7일                ▶ 원격지 소산
```

A1은 재해복구 목표를 충족할 수 있으면 Active-Standby로 구축 가능.

### Active-Active 확대: Multi-Region 구성

```text
사용자 요청
    ↓ 트래픽 분배 (DNS·애니캐스트 기반, 지연·지리·가중치 정책)
    ├─ 리전 A: 애플리케이션 + 데이터베이스 ─┐
    └─ 리전 B: 애플리케이션 + 데이터베이스 ─┤
                                            └ 리전 간 비동기 데이터 복제 → RPO 0에 근접
리전 손실 시: 전환 절차 없이 남은 리전으로 트래픽 재분배
```

### 쓰기 처리 방식

| 쓰기 전략 (AWS 표기) | 방식 | 충돌 처리 |
|---|---|---|
| write global | 모든 쓰기를 한 리전으로 전달, 장애 시 다른 리전을 승격 | 단일 쓰기 리전이라 충돌 없음 |
| write local | 가까운 리전에서 쓰기 | 동시 갱신은 마지막 쓰기 우선으로 조정 |
| write partitioned | 파티션 키(사용자 ID 등)별로 쓰기 리전을 지정 | 키가 리전별로 나뉘어 충돌 회피 |

### 스토리지 DR 확대: 데이터 복제와 복구 순서

```text
평시: 주 시스템 데이터 ── 실시간 동기화(복제) ──▶ 다른 데이터센터의 스토리지
      (재해복구를 위한 최소한의 서비스 환경 사전 구성)
    ↓ 주 시스템 중단
재해: 정보자원을 새로 구성 → 복제된 데이터로 서비스 제공
```

## Ⅳ. 재해복구 방식의 비교

| 방식 | 보조 사이트 상태 | 평시 트래픽 | 전환 시 조치 |
|---|---|---|---|
| Active-Active | 모든 사이트에 배포, 동시 서비스 | 모든 사이트가 처리 | 전환 개념 없음, 사이트 손실 시 트래픽 재라우팅 |
| Active-Passive: Hot Standby | 충분한 용량으로 배포, 서비스 안 함 | 한 사이트만 처리 | 트래픽 전환 |
| Active-Passive: Warm Standby | 축소한 완전한 사본 상시 가동 | 주 사이트만 처리 | 용량 확장 뒤 전환 |
| Active-Passive: Pilot Light | 데이터 복제, 핵심 인프라 사본, 애플리케이션 서버는 꺼짐 | 주 사이트만 처리 | 서버 기동·확장 뒤 전환 |
| 스토리지 DR (고시 A3) | 보조 시스템 미구성, 데이터만 복제 | 주 시스템만 처리 | 정보자원 새로 구성 |
| 원격지 소산 (고시 A4) | 백업 보존매체를 원격지에 보관 | 주 시스템만 처리 | 백업으로 복구, 백업 주기에 따른 일부 데이터 손실 |

Active-Passive는 클라우드 재해복구 문서의 표기이고, 고시의 A2 구축 방식은 Active-Standby로 표기.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 두 사이트가 동시에 쓰기를 받으면 같은 데이터의 갱신이 충돌 | 쓰기 전략을 정해 충돌 차단: 단일 쓰기 리전(write global) 또는 키별 쓰기 리전 분할(write partitioned) |
| 연속 복제의 데이터 손상·악의적 삭제 대응 한계, RPO가 0에 가까워도 데이터 재해의 복구점은 발견 이전 시점 | 시점 복구용 백업을 복제 경로와 분리해 다른 계정·원격지에 보관 |
| Active-Active는 가장 복잡하고 비용이 큼 | 복구 목표가 가장 엄격한 A1에 적용하고, 목표를 충족하면 Active-Standby 허용. 나머지 등급은 등급별 방식 |
| 스토리지 DR은 보조 시스템이 없어 복구 때 정보자원을 새로 구성, 복구 시간 1~5일 | 최소한의 서비스 환경 사전 구성과 재해복구훈련(A3: 연 1회 이상 도상훈련, 3년에 1회 이상 모의훈련)으로 복구 절차 점검 |

## Ⅵ. 제언

복제 경로와 분리한 시점 복구용 백업을 다른 계정·원격지에 보관해, 사이트 장애는 복제로 대응하고 데이터 손상·삭제는 백업으로 복구

### 복제 경로와 백업 경로의 분리

```text
주 사이트 (운영 데이터)
    ├─ 복제 경로 ──▶ 보조 사이트 (사이트 장애 시 전환 또는 동시 서비스)
    └─ 백업 경로 ──▶ 다른 계정·원격지의 시점 복구용 백업
```

### 복구 경로 판단 확대: 장애 유형별 대응

```text
장애 발견
    ├─ 사이트 손실·중단 ──▶ 보조 사이트로 전환, 또는 남은 사이트로 트래픽 재분배
    └─ 데이터 손상·삭제 ──▶ 손상 이전 시점의 백업으로 복구
                              (복구점은 발견 이전 시점)
```

| 구분 | 복제만 구성 | 제언: 복제 + 분리된 시점 백업 |
|---|---|---|
| 사이트 장애 | 보조 사이트로 전환 | 동일 |
| 데이터 손상·삭제 | 복제본에도 손상이 반영될 수 있어 복구점 확보 곤란 | 손상 이전 시점 백업으로 복구 |
| 계정·자격 증명 탈취 | 같은 계정을 쓰면 두 사이트가 함께 영향 | 백업이 다른 계정에 있어 영향 분리 |
