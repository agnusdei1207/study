## 30초 인출

- 본질: 머신러닝·애플리케이션 개발 같은 기술 전문성과 영업 프로세스·경제 분석 같은 업무 전문성을 광범위한 교육 없이 비전문가도 쓰게 하는 흐름. Gartner의 2020년 전략 기술 트렌드 `Democratization of Expertise`
- 메커니즘: 데이터·분석, 개발, 설계, 지식 네 영역에서 로코드·노코드, AI 도구, 전문가 시스템이 전문가의 작업을 단순화된 경험으로 감싸 업무 담당자에게 제공
- 통찰: 업무 담당자가 만든 앱이 조직 데이터를 의도치 않게 외부로 내보낼 수 있으므로 접근을 열기 전에 승인된 플랫폼, 환경 분리, 커넥터 데이터 정책을 플랫폼 수준의 가드레일로 먼저 설정

<summary>핵심 용어</summary>

- **전문성의 민주화(Democratization of Expertise)** : 기술 전문성이나 업무 도메인 전문성을 단순화된 경험으로 광범위한 교육 없이 비전문가에게 열어 주는 흐름
- **시민 개발자(Citizen Developer)** : IT 부서나 사업 부서가 적극적으로 금지하지 않은 도구로, 자신이나 다른 사람이 쓸 애플리케이션 기능을 만드는 직원
- **로코드·노코드(Low-code·No-code)** : 코드를 거의 쓰지 않거나 전혀 쓰지 않고 시각적 구성으로 앱과 자동화를 만드는 개발 방식
- **커넥터(Connector)** : 앱·플로우가 외부 서비스와 데이터에 접근하도록 API를 감싼 구성요소
- **데이터 정책(Data Policy)** : 커넥터를 업무 데이터용·비업무용·차단으로 분류해 한 앱에서 함께 쓸 수 있는 조합을 제한하는 통제. 사용자가 조직 데이터를 의도치 않게 노출하는 위험을 줄이는 가드레일
- **환경(Environment)** : 앱·플로우·데이터를 담아 접근 권한과 정책을 나누어 적용하는 관리 단위. 개발·시험·운영 구분에 사용

## 2~4교시 25점 답안

## Ⅰ. 전문성의 민주화의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **전문성의 민주화(Democratization of Expertise)** 는 기술·업무 전문성을 단순화된 경험으로 광범위한 교육 없이 비전문가에게 열어 주는 흐름 |
| 목적 | 고비용 전문 교육 없이 업무 담당자가 전문성을 활용하는 접근성 확대 |

## Ⅱ. 전문가 중심 방식과 구별되는 전문성의 민주화 특징

| 특징 | 의미 |
|---|---|
| 접근 문턱의 하락 | 광범위하고 비싼 교육 대신 단순화된 경험으로 제공 |
| 비전문가 주체 | 시민 개발자·시민 데이터 과학자처럼 업무 담당자가 직접 수행 |
| 도구 매개 | 로코드·노코드, AI 도구, 전문가 시스템이 전문성을 대신 감쌈 |
| IT 승인 밖의 도구 사용 | IT 부서가 금지하지 않은 도구는 업무 부서가 직접 선택해 사용 |

## Ⅲ. 네 영역 체계와 로코드 앱의 데이터 접근 경로

### 전문성의 민주화 네 영역

```text
전문성의 민주화
    │
    ├─ 데이터·분석 ── 데이터 과학자용 도구의 확산
    │
    ├─ 개발 ── 맞춤 개발 애플리케이션의 AI 도구 활용
    │
    ├─ 설계 ── 로코드·노코드의 개발 기능 자동화
    │
    └─ 지식 ── 비IT 전문가의 전문 도구·전문가 시스템 접근
```

### 개발·설계 영역 확대: 로코드 앱이 데이터에 닿는 경로

```text
업무 담당자(maker)
    ↓ 로코드·노코드 도구로 앱·플로우 작성
커넥터 선택 ── 작성 시 데이터 정책 검사
    ↓
커넥션 ── 저장된 자격 증명
    ↓
업무 데이터 접근 ── 실행 시 데이터 정책 재검사
```

## Ⅳ. 기술 전문성과 업무 전문성의 비교

| 비교축 | 기술 전문성 | 업무 도메인 전문성 |
|---|---|---|
| 예시 | 머신러닝, 애플리케이션 개발 도구 | 영업 프로세스, 경제 분석 |
| 해당 영역 | 데이터·분석, 개발, 설계 | 지식 |
| 개방 수단 | 로코드·노코드, AI 도구, 분석 도구 | 전문가 시스템, 전문 도구 |
| 주된 수행 주체 | 시민 개발자, 시민 데이터 과학자 | 비IT 전문가 |

## Ⅴ. 전문성의 민주화 도입의 한계와 방안

| 한계 | 방안 |
|---|---|
| IT가 금지하지 않은 도구는 업무 부서가 사용해 IT가 도구 현황을 파악하지 못함 | 사용 가능한 플랫폼을 승인 목록으로 관리 |
| 업무 담당자가 만든 앱이 조직 데이터를 의도치 않게 외부로 노출 | 커넥터를 업무용·비업무용·차단으로 분류하는 데이터 정책 |
| 일부 로코드 플랫폼은 기본 상태에서 데이터 정책이 없음(Power Platform) | 개방 전에 환경·테넌트 단위 기본 정책부터 설정 |
| 커넥터 통제는 연결 대상이 개발·시험·운영 중 어디인지 구분하지 못함 | 개발·시험·운영 환경의 분리와 환경별 접근 권한 |

## Ⅵ. 제언

전문성의 접근을 열기 전에 승인된 플랫폼, 환경 분리, 커넥터 데이터 정책의 가드레일을 먼저 설정하고 환경별로 개방 범위를 확대

### 가드레일 구조

```text
승인된 플랫폼
    │
    ├─ 환경 ── 개인·팀 생산성용 / 부서 업무용 / 운영
    │
    └─ 데이터 정책 ── 테넌트 단위 기본 정책 + 환경 단위 예외
```

### 정책 확대: 새 커넥터 요청의 예외 처리

```text
업무 담당자의 새 커넥터 요청
    ↓
관리자 검토
    ├─ 거절
    ├─ 기본 정책에 커넥터 추가
    └─ 전용 환경과 전용 정책 생성
```

### 선택 근거: 사후 회수 방식과의 비교

| 구분 | 도구 개방 후 사후 회수 | 제언: 가드레일 선설정 |
|---|---|---|
| 통제 시점 | 노출 사고 이후 | 앱 작성·실행 시점 |
| 통제 단위 | 앱별 개별 조치 | 환경·테넌트 단위 정책 |
| 예외 처리 | 임의 허용 | 요청 절차와 전용 환경 |
