## 큰 그림과 30초 인출

- 본질: **WBS(Work Breakdown Structure)**는 프로젝트가 해야 할 전체 범위를 빠짐없이 보이게 하고, 추정·배정·통제가 가능한 작업 패키지까지 인도물 중심으로 쪼갠 계층 구조

<details>
<summary>핵심 용어</summary>

- `WBS(Work Breakdown Structure)`: 전체 프로젝트 범위를 하위 인도물과 작업 패키지로 연결하는 계층 구조
- `100% Rule`: 하위 요소의 합이 상위 요소의 범위를 빠짐없이 포함하고 범위 밖 작업을 넣지 않게 하는 완전성 원칙
- `Work Package`: 비용·노력·기간·자원을 추정하고 관리하는 WBS 최하위 작업
- `Control Account`: 범위·예산·일정을 통합해 성과를 측정하는 관리 통제점
- `WBS Dictionary`: WBS 요소별 작업 내용·책임·가정·수락 기준을 구체화하는 보조 문서
- `Scope Baseline(범위 기준선)`: 승인된 범위 기술서·WBS·WBS 사전을 묶은 변경 비교 기준

</details>

## Ⅰ. 전체 범위를 관리 단위로 바꾸는 WBS

> WBS는 일정표가 아니라 프로젝트의 ‘무엇’을 정의하는 **인도물 중심 계층 분해**이며, 품질은 하위 작업의 개수가 아니라 전체 범위의 완전성과 관리 가능성으로 판정함

- 정의: **WBS(Work Breakdown Structure)**는 프로젝트 목표·필수 인도물을 만들 전체 범위를 **Work Package(작업 패키지)**까지 계층 분해한 범위관리 도구
- 목적: 범위 누락·중복과 무승인 작업의 예방

## Ⅱ. 범위 경계에서 Baseline까지의 WBS 작성방법

> 작성의 핵심은 작업을 잘게 나누는 행위가 아니라, 인도물마다 하위 범위를 완전하게 닫고 책임·추정·검수가 가능한 수준에서 분해를 멈추는 것임

## Ⅲ. WBS 품질을 가르는 분해·완료 기준

> 좋은 WBS는 모든 범위를 포함하되 범위 밖 작업은 넣지 않고, 최하위 작업마다 추정·책임 할당·완료 판정이 가능해야 함

| 기준 | 확인 항목 | 판정 |
|---|---|---|
| **100% Rule** | 하위 요소의 합이 상위 범위 전체 포함 | 누락·범위 밖 작업 없음 |
| **인도물 중심** | 명사형 결과물 기준 분해 | 일정 활동 목록과 구분 |
| **관리 가능성** | 비용·기간·자원 추정 가능 | 책임자·완료 기준 설정 가능 |

## Ⅳ. 범위 기준선 완전성 판정과 변경 통제

> WBS는 승인된 범위 기준선과 변경 절차가 연결될 때 통제 도구가 되며, 누락이 발견되면 승인하지 않고 상위 범위부터 다시 분해해야 함

- 변경 통제: 승인 후 추가·삭제된 범위는 변경 요청으로 식별하고 영향 분석·승인을 거쳐 Baseline에 반영

## Ⅴ. 형식적 WBS의 문제점·대응책

> WBS 실패는 세분화 부족보다 범위·책임·완료 증적이 서로 끊길 때 발생하므로, WBS 사전과 실행 데이터를 같은 코드로 연결해야 함

| 위험 | 대책 | 효과 |
|---|---|---|
| **Scope Creep** | 제외 범위 명시 · 변경 요청 승인 | 무승인 작업 식별 |
| 누락·중복 | 상위별 100% Rule 검토 · 담당자 교차 검증 | 범위 완전성 확보 |
| 분해 수준 부적정 | 추정·배정·완료 판정 가능 수준에서 중단 | 관리 과부하·통제 공백 완화 |

## Ⅵ. 결론 — 검수 증적과 연결하는 WBS 운영

> 성패는 WBS의 모양이 아니라 Work Package별 승인 범위와 실제 완료 증적이 추적되는지로 판정함

### 학습자 통찰 메모 — 답안 밖

- `[핵심 통찰]`: WBS는 일을 작게 쪼개는 목록이 아니라, 프로젝트 전체 범위를 추정·책임·검수 가능한 동일 언어로 바꾸는 구조다.
- `나라면`: 핵심 Work Package부터 WBS 코드와 일정·원가·검수 증적을 연결하고, 변경 요청이 승인되기 전에는 실행 항목으로 편입하지 않겠다.
