## 연관 키워드

- 소프트웨어 비용 산정(Software Cost Estimation), 불확실성의 원추(Cone of Uncertainty)
- 하향식 산정(Top-Down), 상향식 산정(Bottom-Up), 모형 기반 산정(Algorithmic)
- 기능점수(FP, Function Point), LOC(Lines of Code), COCOMO II(Constructive Cost Model II), Putnam 모형
- WBS(Work Breakdown Structure, 작업 분해 구조), TCO(Total Cost of Ownership, 총소유비용), 델파이 기법(Delphi)
- 벨로시티(Velocity), KSLOC(Thousand Source Lines of Code)

## Ⅰ. 소프트웨어 비용 산정의 개요

- 핵심 요약 : 노력·기간·비용을 알고리즘, 통계 모델, 전문가 판단으로 사전에 예측해 예산과 일정의 기준선을 세우는 소프트웨어 공학 활동.
- 개념 : 소프트웨어 프로젝트의 완수에 필요한 노력(Effort), 기간(Schedule), 인력과 비용을 공학적 알고리즘, 통계 모델, 전문가 판단으로 사전에 정량 예측하는 **소프트웨어 비용 산정** (Software Cost Estimation) 활동.
- 배경 및 필요성 : 부정확한 산정은 저가 수주, 납기 지연, 품질 저하로 이어지므로, 계약과 프로젝트 관리에 쓸 객관적 기준선이 있어야 함.
- 주요 목적 : 적정 예산 확보와 가격 경쟁력 판단, 현실적인 일정 계획, 자원 배분과 원가 통제.

## Ⅱ. 소프트웨어 비용 산정의 특징 및 장점

- 핵심 요약 : 산정 기법을 여러 관점에서 대조하고 모형 기반으로 정량화하며, 불확실성이 줄어드는 시점에 재산정하는 체계.

1. 하향식·상향식·모형 산정 병용 : 서로 다른 관점의 견적을 대조 → 단일 판단의 편향 감소.
2. 기능점수와 COCOMO II 기반 정량화 : 규모와 비용 동인을 수치화 → 예산 근거의 설명력 확보.
3. WBS 단위 분해 : 작업 패키지별 노력과 일정을 추적 → 누락된 비용 발견.
4. 조직 데이터 보정 : 과거 프로젝트 실적을 반영 → 조직에 맞는 산정 정확도 향상.
5. 단계별 재산정 : 요구사항이 구체화될 때 기준선 갱신 → 초기 불확실성 대응.

## Ⅲ. 소프트웨어 비용 산정의 구조 (흐름)

- 핵심 요약 : 기법을 하향식, 상향식, 모형 기반으로 분류하고, 모형 기반 산정을 규모 측정부터 재산정까지 단계로 수행하는 구조.
- 하향식 산정(Top-Down) : 전체 규모를 전문가 판단으로 잡고 델파이(Delphi) 기법으로 합의하는 방식.
- 상향식 산정(Bottom-Up) : WBS(Work Breakdown Structure) 작업 패키지별로 노력을 추정해 합산하는 방식.
- **기능점수** (FP, Function Point) : 사용자 관점의 입력, 출력, 파일, 조회, 대화 기능을 세어 규모를 재는 측정치.
- **COCOMO II** (Constructive Cost Model II) : 규모와 여러 비용 동인의 곱셈 계수로 노력을 추정하는 모형.
- LOC(Lines of Code) : 소스 코드 라인 수로 규모를 재는 방식.
- Putnam 모형 : 생명주기 곡선에 기반해 기간을 줄일수록 비용이 급증하는 관계를 나타내는 모형.

```text
[소프트웨어 비용 산정 기법]
  ├─ 하향식 산정 (Top-Down)
  │    전문가 판단, 델파이 기법
  ├─ 상향식 산정 (Bottom-Up)
  │    WBS 작업 패키지별 노력 합산
  └─ 모형 기반 산정 (Algorithmic)
       기능점수, COCOMO II, Putnam
```

```text
[비용 산정 프로세스]
  요구사항 분석
          ↓
  규모 측정 (FP, LOC)
          ↓
  비용 모형 선정
          ↓
  비용 동인 보정
          ↓
  노력·기간·비용 산출
          ↓
  단계별 재산정 (게이트웨이)
```

## Ⅳ. 주요 비용 산정 모형의 비교

- 핵심 요약 : LOC, 기능점수, COCOMO II, Putnam 모형은 규모 기준과 산식이 달라 적용 시점과 목적에 따라 선택해야 함.

| 산정 모형 | 산정 기준 | 핵심 산식 및 특징 | 장단점 |
| --- | --- | --- | --- |
| LOC | 소스 코드 라인 수 | 노력 = 라인 수 × 라인당 생산성 | 직관적이나 언어와 개발자 역량에 따라 편차가 큼 |
| COCOMO II | 천 라인 단위 소스 라인 수(KSLOC, Thousand Source Lines of Code) 또는 객체 점수 | 노력 = A × 규모^E × 노력 곱셈 계수의 곱 | 17개 비용 동인을 반영하나 초기 규모 추정이 어려움 |
| 기능점수 (FP) | 사용자 요구 기능 | 조정 FP = 미조정 FP × (0.65 + 0.01 × 영향도 합) | 구현 기술과 무관해 기획 단계 적용에 적합 |
| Putnam 모형 | 생명주기 곡선 | Man-Years = S³ ÷ (C³ × T⁴) | 기간 단축에 따른 비용 급증 분석에 적합 |

## Ⅴ. 소프트웨어 비용 산정의 한계와 방안

- 핵심 요약 : 초기 불확실성, 조직별 비용 동인의 차이, 운영비 누락을 재산정과 데이터 보정으로 관리해야 한다.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 초기 견적 오차 | 요구가 불명확해 규모 추정 편차가 큼 | 가정을 명시하고 설계·구현 단계마다 규모와 예산을 재산정 | 재산정 횟수, 오차율 |
| 범용 모형의 부정확성 | 비용 동인이 조직과 도메인마다 달라 계수가 맞지 않음 | 완료 프로젝트의 실제 공수와 규모를 축적해 모형 계수를 보정 | 추정 대비 실적 편차 |
| 운영비 누락 | 반복 개발과 운영 비용이 개발 견적에서 빠지기 쉬움 | 벨로시티와 변경 범위를 추적하고 운영비를 포함한 TCO(Total Cost of Ownership, 총소유비용)로 판단 | 변경 범위, TCO |

## Ⅵ. 과학적 비용 산정을 위한 기술사적 제언

- 핵심 요약 : 단계별 재산정, 비기능 요구사항의 대가 반영, 데이터 기반 보조 추정의 결합.

- 프로젝트 초기에는 추정 오차가 크다는 불확실성의 원추(Cone of Uncertainty)를 인정하고, 설계가 끝난 시점에 기능점수로 재산정하는 단계별 정산 방식을 계약에 반영하는 것이 바람직하다.
- 기능점수는 업무 트랜잭션 중심이라 인프라 고도화나 마이크로서비스 아키텍처(MSA, Microservice Architecture)의 분산 설계 노력을 과소평가하기 쉬우므로, 성능·보안·가용성 같은 비기능 요구사항에 별도의 보정 계수를 현실적으로 두어야 한다.
- 과거 완료 프로젝트의 아키텍처 속성과 실투입 공수를 학습한 머신러닝(ML, Machine Learning) 기반 추정 모델은 사람의 편향을 줄이는 보조 지표로 쓸 수 있으나, 학습 데이터 품질에 따라 결과가 크게 달라지므로 기존 모형과 병행 검증해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 소프트웨어 비용 산정은 모형과 파라미터에 기반한 정량 예측 활동이며, 단계별 재산정과 조직 데이터 보정이 정확도를 좌우.
- 산정 정확도는 모형 선택보다 실적 데이터의 축적과 재산정 절차를 얼마나 체계적으로 운영하는지에 달려 있다.
