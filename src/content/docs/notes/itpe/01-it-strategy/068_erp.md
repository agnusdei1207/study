## 지식 로드맵 내 현재 위치

IT 전략·관리 → 프로세스 혁신·정보시스템 통합 → **ERP**

## 30초 인출

- 본질: ERP는 재무·인사·제조·공급망·영업·구매 같은 핵심 업무를 하나의 통합 소프트웨어에서 공통 데이터로 처리하는 전사 업무 시스템
- 메커니즘: 업무 영역별 모듈이 같은 데이터베이스를 공유해 부서 간 데이터를 한 정보원으로 모으고, 외부 애플리케이션과는 API·ESB·iPaaS로 연계
- 통찰: 업무 맞춤을 위한 커스텀 코드가 표준 코어에 쌓이면 업그레이드가 어려워지므로, 표준 기능으로 충족되는 프로세스를 먼저 확정하고 표준으로 충족되지 않는 요구만 표준 코어와 분리된 확장으로 구현

<details>
<summary>핵심 용어</summary>

- **ERP(Enterprise Resource Planning)** : 재무·인사·제조·공급망·영업·구매 같은 핵심 업무 프로세스를 통합해 단일 정보원을 제공하는 소프트웨어 시스템
- **모듈(Module)** : 재무·물류·구매·인사처럼 한 업무 영역을 맡는 ERP의 기능 단위로, 다른 모듈과 같은 데이터를 사용
- **단일 정보원(Single Source of Truth)** : 조직의 데이터를 ERP에 모아 모든 부서가 같은 기준의 데이터를 보게 하는 상태
- **API(Application Programming Interface)** : 애플리케이션끼리 기능과 데이터를 주고받는 연결 규약
- **ESB(Enterprise Service Bus)** : 여러 시스템 사이의 메시지를 중계해 연계하는 통합 방식
- **iPaaS(integration Platform as a Service)** : 클라우드에서 시스템 간 연계를 제공하는 통합 플랫폼
- **SaaS(Software as a Service)** : 소프트웨어를 구독 형태로 인터넷을 통해 제공하는 서비스, 클라우드 ERP의 제공 방식
- **온프레미스(On-premises)** : 기업 자체 데이터센터에 소프트웨어를 설치해 운영하는 방식
- **커스텀 코드·확장(Extensibility)** : 표준 기능에 없는 요구를 충족하려고 추가하는 맞춤 개발 코드와 그 방식
- **TCO(Total Cost of Ownership)** : 도입 뒤 운영·유지까지 포함한 총 소유 비용
- **Clean Core** : 맞춤 확장을 표준 코어에서 분리해 ERP를 표준 상태로 유지하려는 SAP의 접근

</details>

## 2~4교시 25점 답안

## Ⅰ. ERP의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **ERP(Enterprise Resource Planning)** 는 재무·인사·제조·공급망·영업·구매 같은 핵심 업무를 하나의 통합 소프트웨어에서 공통 데이터로 처리하는 전사 업무 시스템 |
| 목적 | 분리된 업무 시스템의 중복 데이터와 업무 단절 해소, **단일 정보원** 확보 |

## Ⅱ. 공통 데이터로 모듈을 묶는 특징

| 특징 | 내용 |
|---|---|
| 모듈 통합 | 업무 영역별 **모듈** 이 공통 데이터베이스를 공유 |
| 데이터 표준화 | 단일 데이터 구조와 공통 정의로 같은 항목을 같은 이름·속성으로 관리 |
| 전사 가시성 | 재무·영업·물류·구매의 데이터를 한 정보원에서 조회 |
| 선택·확장 | 필요한 모듈을 골라 도입·추가하고 산업별 요구는 코어 기능 또는 확장 애플리케이션으로 충족 |
| 외부 연계 | CRM·공급망·인사 등 다른 애플리케이션과 연동해야 효과 발휘 |

## Ⅲ. ERP의 구성과 연계 방식

### ERP 구성

```text
전사 사용자: 재무 · 구매 · 생산 · 영업 · 인사 부서
    │
ERP 모듈: 재무 · 인사 · 제조 · 공급망 · 영업 · 구매
    │  같은 데이터를 사용
공통 데이터베이스: 단일 데이터 구조 · 공통 정의
    │
외부 연계 대상: CRM · 공급망 · 인사 · 산업별 솔루션
```

### 연계 방식 확대: 외부 애플리케이션과의 연결

```text
ERP ──┬─ 커넥터·어댑터: API
      ├─ ESB (Enterprise Service Bus)
      └─ iPaaS (integration Platform as a Service)
```

## Ⅳ. 배포 유형의 비교

| 유형 | 소프트웨어 위치 | 특징 |
|---|---|---|
| 클라우드 ERP | 원격 제3자 서버, **SaaS** 구독 | 공급사가 유지보수·업데이트·보안을 처리, 초기 비용 낮고 확장성 높음 |
| **온프레미스** ERP | 기업 자체 데이터센터 설치 | 통제 수준 최대, 설치·유지보수 책임 부담 |
| 2-Tier ERP | 본사는 온프레미스, 자회사는 클라우드 | 합병·확장 시 기능·조직 단위의 통제된 클라우드 이전 |
| 하이브리드 ERP | 온프레미스와 클라우드의 혼합 | 규제·보안 요구가 있는 애플리케이션은 온프레미스 유지 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 맞춤을 위한 **커스텀 코드** 가 표준 코어에 쌓여 업그레이드가 느려지고 **TCO** 증가 | 표준 프로세스를 우선 채택하고 맞춤 요구는 표준 코어와 분리된 확장으로 구현 |
| 다른 애플리케이션과 동기화가 어긋나면 단일 정보원 훼손 | **API** 등 표준 연계 방식과 공통 데이터 정의 적용 |
| 클라우드 ERP는 유지·보안을 공급사에 맡겨 규제·보안 요구가 있는 애플리케이션 배치 제약 | 해당 애플리케이션만 온프레미스에 두는 하이브리드 구성 |

## Ⅵ. 제언

도입 단계에서 표준 기능으로 충족되는 프로세스를 먼저 확정하고, 표준으로 충족되지 않는 요구만 표준 코어와 분리된 확장으로 구현

### 요구사항별 구현 방식 결정

```text
업무 요구사항
    ↓
표준 기능으로 충족되는가
    ├─ 충족 → 표준 기능 사용 (업무 프로세스를 표준에 맞춤)
    └─ 미충족 → 확장으로 구현: 표준 코어와 분리 · API로 연결
```

### 확장 구조 확대: 표준 코어와 확장의 분리

```text
확장(맞춤 기능) ──▶ 표준 API ──▶ 표준 코어
                                    │
                  업그레이드 때 코어를 갱신하고 확장은 API 호환성만 확인
```

| 구분 | 표준 코어에 직접 맞춤 개발 | 제언: 확장 분리 |
|---|---|---|
| 맞춤 코드 위치 | 표준 코어 안 | 표준 코어 밖의 확장 |
| 업그레이드 | 맞춤 코드가 섞여 복잡도 증가 | 분리된 확장으로 복잡도 최소화 |
| 연계 방식 | 코어 내부 수정 | 표준 API |
