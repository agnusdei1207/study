## 지식 로드맵 내 현재 위치

IT 전략·관리 → 개발 전략·방법론 → **애자일 대응 전략**

## 30초 인출

- 본질: 애자일(Agile)은 짧은 반복마다 사용 가능한 결과물을 만들고 사용자 피드백으로 다음 작업을 조정하는 개발 방식
- 메커니즘: Product Owner가 백로그 순서를 정하고, 1개월 이하의 Sprint마다 DoD를 충족한 Increment를 검토해 백로그를 갱신
- 통찰: 피드백이 우선순위에 반영되지 않으면 애자일이 형식화되므로 Product Owner의 백로그 결정권과 피드백 처리 기록

<details>
<summary>핵심 용어</summary>

- **애자일 대응 전략** : 요구 변화에 짧은 반복과 피드백으로 대응해 개발 우선순위와 결과물을 조정하는 개발·관리 전략
- **Agile Manifesto(애자일 선언)** : 개인과 상호작용, 작동하는 소프트웨어, 고객 협력, 변화 대응을 우선하는 2001년 선언
- **Scrum(스크럼)** : 책임·이벤트·산출물을 정해 짧은 반복으로 제품을 만드는 대표 애자일 프레임워크
- **Product Owner(제품 책임자)** : Product Backlog의 순서와 제품 가치에 책임을 지는 역할
- **Product Backlog(제품 백로그)** : 제품 개선에 필요한 항목을 가치 순서로 정렬한 목록
- **Sprint(스프린트)** : 1개월 이하의 고정 기간으로 증분을 만드는 반복 단위
- **Increment(증분)** : 이전 결과와 통합·검증되어 사용 가능한 상태의 산출물
- **DoD(Definition of Done, 완료 정의)** : 증분이 제품 품질 기준을 충족했는지 판단하는 공통 완료 기준
- **Sprint Review(스프린트 리뷰)** : 증분을 이해관계자에게 시연하고 피드백으로 다음 작업을 조정하는 이벤트

## 2~4교시 25점 답안

## Ⅰ. 애자일 대응 전략의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **애자일 대응 전략** 은 짧은 반복으로 사용 가능한 결과물을 만들고 피드백에 따라 우선순위를 조정하는 개발·관리 전략 |
| 목적 | 요구 변화에 대한 대응 속도 향상과 사용자 가치의 조기 전달 |

## Ⅱ. 계획 주도 개발과 구별되는 애자일의 특징

| 특징 | 의미 |
|---|---|
| 짧은 반복 | 1개월 이하 Sprint마다 사용 가능한 **Increment** 전달 |
| 변화 수용 | 초기 계획 고수보다 피드백에 따른 백로그 순서 조정 |
| 고객 협력 | 증분 시연으로 사용자·이해관계자의 판단을 반복 확인 |
| 완료 기준 공유 | **DoD** 를 충족한 결과만 완료로 인정 |

## Ⅲ. 스크럼 기반 반복 개발 체계와 Sprint 흐름

### 스크럼 기반 반복 개발 체계

```text
애자일 대응 전략 ── 애자일 선언의 가치·원칙
    │
    ├─ 책임
    │     ├─ Product Owner ── 백로그 순서·제품 가치
    │     ├─ Developers ── 증분 개발·품질
    │     └─ Scrum Master ── 스크럼 정착·장애 제거
    │
    ├─ 산출물
    │     ├─ Product Backlog ── Product Goal
    │     ├─ Sprint Backlog ── Sprint Goal
    │     └─ Increment ── DoD
    │
    └─ 반복 단위 ── 1개월 이하의 Sprint
```

**Scrum** 은 애자일을 구현하는 대표 프레임워크이며, 산출물마다 목표·완료 기준이 짝을 이루는 구조

### 반복 단위 확대: Sprint 이벤트 흐름

```text
Sprint Planning: Sprint Goal과 작업 선택
    ↓
Daily Scrum: 목표 대비 진행 점검
    ↓
Sprint Review: 증분 시연과 피드백 수집
    ↓
Sprint Retrospective: 작업 방식 개선
    ↓
Product Backlog 갱신 후 다음 Sprint
```

## Ⅳ. 계획 주도 개발과 애자일의 선택 기준

| 구분 | 계획 주도 개발(폭포수) | 애자일 |
|---|---|---|
| 요구 관리 | 초기 기준선 확정·변경 통제 | 백로그의 지속 정제·순서 조정 |
| 가치 전달 | 단계 종료 후 일괄 인도 | Sprint마다 증분 전달 |
| 품질 확인 | 후반부 통합 시험 | DoD에 따른 반복별 통합·시험 |
| 적합 조건 | 요구가 안정되고 규제·계약 범위가 고정된 사업 | 요구 불확실성이 크고 사용자 확인이 가능한 사업 |

두 방식은 우열이 아닌 요구 안정성에 따른 선택 대상이며, 한 조직 안에서 영역별 병행 가능

## Ⅴ. 애자일 적용의 한계와 방안

| 한계 | 방안 |
|---|---|
| 요구가 확정된 규제·핵심 시스템까지 일괄 적용 | 요구 변동이 큰 영역에 애자일, 안정 영역에 계획 주도 방식 병행 |
| 고정 범위 일괄 계약과 반복 조정의 충돌 | 목표·기간·예산 고정과 백로그 우선순위에 따른 범위 조정의 계약 명시 |
| 이벤트만 수행하고 피드백은 미반영하는 형식화 | **Product Owner** 의 백로그 순서 결정권과 피드백 처리 기록 |
| 일정 압박에 따른 기술 부채 누적 | DoD에 시험·보안·통합 기준 포함 |

## Ⅵ. 제언

Sprint Review 피드백을 백로그 순서에 반영하는 Product Owner의 결정권 확보와 처리 결과의 기록

### 피드백 반영 책임 구조

```text
Sprint Review 피드백 반영
    │
    ├─ 사용자·이해관계자 ── 증분 확인과 피드백 제공
    │
    ├─ Product Owner ── 수용 여부·백로그 순서 결정
    │
    └─ Developers ── DoD를 충족한 증분 개발
```

### Product Owner 결정 확대: 피드백 처리 절차

```text
Sprint Review 피드백 수집
    ↓
Product Goal 기여도 판단
    ├─ 수용 → 백로그 순서·인수 조건 갱신
    └─ 보류 → 보류 사유·재검토 시점 기록
    ↓
다음 Sprint Planning의 Sprint Goal에 반영
```

### 선택 근거: 형식적 애자일과의 비교

| 구분 | 형식적 애자일 | 제언: Product Owner 결정권 기반 |
|---|---|---|
| 우선순위 결정 | 상위 승인·위원회 대기 | Product Owner의 직접 결정 |
| 피드백 처리 | 회의록 기록으로 종료 | 수용·보류 사유와 백로그 변경 기록 |
| 성과 판단 | Sprint 이벤트 수행 횟수 | 피드백 반영 증분의 사용자 확인 |
| 범위 변경 처리 | 변경 요청마다 계약 협의 | 목표·기간 안의 백로그 순서 조정 |
