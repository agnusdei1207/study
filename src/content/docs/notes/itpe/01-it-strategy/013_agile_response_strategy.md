## 한 줄 본질
- 사전에 모든 요구사항을 완벽히 정의하려는 전통적 폭포수 모델이 급변하는 비즈니스 환경에서 대규모 납기 지연을 초래 → 핵심 가치를 빠르게 배포하고 고객 피드백을 반복 반영하는 애자일 체계를 조직·계약·문화 전반에 단계적으로 구축 → 시장 출시 속도(Time-to-Market) 단축 및 위험 조기 해소 / 대규모 엔터프라이즈의 기존 거버넌스와 마찰 발생

## 핵심 그림
```text
┌───────────────────────────────── [ 엔터프라이즈 바이모달(Bimodal) IT 전략 ] ─────────────────────────────────┐
│                                                                                                             │
│  [ Mode 1: 전통적 안정성 추구 (전통 코어) ]             [ Mode 2: 민첩한 혁신 추구 (디지털 서비스) ]        │
│  - 대상: 기간계 ERP, 회계, 코어 뱅킹, 공공 행정 망      - 대상: 대고객 모바일 앱, 생성형 AI 서비스, 신사업  │
│  - 방식: 폭포수(Waterfall), 철저한 사전 계획과 통제     - 방식: 애자일(Scrum/Kanban), 2주 단위 스프린트 배포 │
│  - 목표: 안정성, 데이터 무결성, 무장애 운영             - 목표: 빠른 출시(Time-to-Market), 사용자 경험 혁신 │
└─────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
                                                      │
                       ┌──────────────────────────────┴──────────────────────────────┐
                       ▼                                                             ▼
         [ 거버넌스: Agile PMO ]                                      [ 엔터프라이즈 확장: SAFe ]
         (통제자가 아닌 장애물 제거 및 임피던스 해소)                 (수십 개 스크럼 팀의 릴리즈 트레인(ART) 동기화)
```

## 핵심 용어
- 바이모달 IT(Bimodal IT): 가트너가 제시한 모델로, 예측 가능하고 안정적인 전통적 IT(Mode 1)와 불확실하고 속도가 핵심인 탐색적 IT(Mode 2)를 공존시키는 전략
- SAFe(Scaled Agile Framework): 엔터프라이즈 규모에서 수십~수백 명의 개발자가 다중 스크럼 팀을 이루어 제품을 릴리즈할 수 있도록 조율하는 대규모 애자일 프레임워크

## 핵심 통찰
- 애자일 전환의 가장 큰 걸림돌은 개발 기술이 아니라 '고정 금액·고정 납기·고정 범위'를 강제하는 전통적 구매·계약 제도임
- 모든 시스템을 100% 애자일로 전환하려는 시도는 실패함 → 금융의 원장이나 국방의 미사일 제어처럼 결함이 치명적인 영역은 Mode 1의 검증 절차를 유지해야 함
- 애자일에서 문서화는 '생략'하는 것이 아니라 '동작하는 소프트웨어와 자동화된 테스트 코드' 자체로 문서를 대체하는 것임

## 이웃 토픽과 구분
- 애자일 vs 폭포수: 폭포수 = 범위를 고정하고 비용과 일정을 추정(Plan-driven) / 애자일 = 비용과 일정을 고정(Time-boxing)하고 스프린트마다 고객 가치 우선순위대로 범위를 유연하게 조정(Value-driven)

## 문제·원인·대책
- 사례: 129회 기출 국내 대기업 제조사가 전사 개발방법론을 애자일로 전면 선포했으나, 현업의 요구사항 변경 거부와 구매팀의 고정가 계약 고수로 6개월 만에 와해된 사례
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 고정가 턴키 계약 체결로 인한 과업 변경 분쟁 | 범위가 사전에 확정되어야 발주하는 전통 조달 규정 | 스프린트 단위 인건비 정산(Time & Material) 또는 분할 발주 계약 도입 | 요구사항 변경에 따른 법적 마찰 해소 |
| 개발자만 스크럼을 돌고 현업 부서는 참여 거부 | 현업 담당자의 본인 업무 과다 및 애자일 무관심 | 전담 프로덕트 오너(PO)를 현업 부서에서 공식 파견하고 스프린트 리뷰 참여 의무화 | 비즈니스와 IT 간 실시간 피드백 루프 완성 |

## 이렇게 출제된다
- 예상문제: "기존 구조적 방법론 환경에 애자일을 도입하는 전략과 실무 고려사항을 설명하시오." → 요구 포인트: Ⅲ 적용대상 선별과 전환구조 + Ⅵ 조직·계약·문화적 장애물 극복방안
- 예상문제: "폭포수와 애자일의 특징·장단점을 비교하고 조직 적용전략을 설명하시오." → 요구 포인트: Ⅴ 범위·비용·일정·품질 관점 비교 매트릭스

## 내 의견
- [형식적 행사보다 전달 역량을 먼저 확보] 회의·티켓만 애자일로 바꾸고 테스트·배포가 수동이면 짧은 반복의 가치가 운영까지 전달되지 않음 → 나라면: 작은 변경을 자동 검증·단계 배포·롤백할 수 있는 CI/CD 안전망을 확보하고 제품 성과와 운영 안정성을 함께 회고

## Ⅰ. 고객가치를 반복 검증하는 애자일 대응전략 개요

- 정의: **애자일 대응전략**은 불확실성이 높은 업무를 작은 가치 단위로 나누고, 교차기능 팀이 짧은 반복에서 작동 증분과 고객 피드백을 통해 우선순위를 조정하는 조직 전환 방안
- 목적: 초기에 모든 요구를 고정하는 위험을 줄이고, 가치·위험이 높은 가정을 조기에 검증
- 범위: 개발 방법만이 아니라 제품책임·조직·거버넌스·계약·기술 전달체계를 함께 조정

## Ⅱ. 가치·피드백·자율팀 중심의 특징

| 특징 | 실천 | 효과 |
|---|---|---|
| **가치 우선** | 제품목표와 정렬된 백로그 순위 | 중요한 결과부터 전달 |
| **점진·반복** | 짧은 주기의 작동 증분 | 위험·오해 조기 발견 |
| **고객 피드백** | 리뷰·실사용 데이터 반영 | 요구 변화 수용 |
| **교차기능 팀** | 분석·개발·시험·운영 역량 결합 | 인수인계 대기 감소 |
| **투명·점검·적응** | 작업·품질·장애를 가시화하고 조정 | 지속 개선 |

## Ⅲ. 전략·조직·프로세스·기술의 전환구조

```text
[전략·거버넌스] 제품목표·가치·위험·투자
          │
[조직] 제품책임자 + 교차기능팀 + 지원 리더십
          │
[프로세스] Backlog → Sprint → Increment → Review·Retro
          │
[기술] 자동 테스트·CI/CD·관측·점진 배포
```

| 영역 | 핵심 전환 |
|---|---|
| **전략** | 프로젝트 산출물보다 제품 성과와 고객가치 중심 |
| **조직** | 기능부서 인수인계보다 안정된 교차기능 팀 |
| **계약** | 변경 불가 범위보다 목표·우선순위·검수 규칙 명확화 |
| **기술** | 반복 가능한 빌드·테스트·배포·롤백 확보 |

## Ⅳ. 대상선정에서 확산까지의 절차

```text
① 불확실성·의존성·규제 기준으로 대상 선정
 → ② 제품목표·성과지표·책임자 확정
 → ③ 파일럿 팀·백로그·완료정의 구성
 → ④ 짧은 반복에서 증분·피드백 검증
 → ⑤ 품질·운영·계약 장애 제거
 → ⑥ 팀 간 의존성·포트폴리오 조정 후 단계 확산
```

- 안정·규제·전환 제약이 큰 영역은 단계형 계획과 반복 개발을 혼합하고, 방법론 명칭보다 피드백 가능성을 기준으로 선택

## Ⅴ. 폭포수와 애자일 비교

| 기준 | 폭포수 | 애자일 |
|---|---|---|
| 요구 | 초기 상세화·기준선 | 우선순위화·점진 상세화 |
| 전달 | 단계 종료 후 통합 | 반복별 작동 증분 |
| 변경 | 변경통제 절차로 예외 처리 | 피드백에 따라 백로그 조정 |
| 고객 참여 | 주요 단계 승인 | 지속적 리뷰·검증 |
| 적합 | 요구·기술이 안정적이고 승인단계 명확 | 불확실성·학습 필요가 높음 |
| 위험 | 후반 통합·수용성 | 아키텍처 부채·범위·의존성 관리 |

## Ⅵ. 엔터프라이즈·공공 적용의 장애와 대책

| 문제 | 원인 | 대책 | 검증지표 |
|---|---|---|---|
| **고정 계약 충돌** | 범위·검수를 일괄 확정 | 목표·백로그 변경규칙·증분 검수 기준 명시 | 변경 리드타임·분쟁 수 |
| **형식적 행사** | 권한 없이 회의만 도입 | 제품책임자의 우선순위·수용 권한 보장 | 결정 대기시간 |
| **품질 저하** | 속도만 강조, 완료정의 부재 | 테스트·보안·운영 준비를 완료정의에 포함 | 결함 유출·변경 실패 |
| **팀 간 의존성** | 기능조직·공통시스템 결합 | 제품 경계·API 계약·통합계획 가시화 | 외부 대기·통합 실패 |
| **규모 확장 과잉** | 파일럿 학습 전 프레임워크 전사 적용 | 가치흐름 단위 단계 확산 | 성과·인지부하·회의시간 |

## Ⅶ. 행사보다 가치 전달 능력을 만드는 결론

- 애자일 전환은 스프린트 명칭 도입이 아니라 **가치 우선순위, 팀 권한, 작동 증분, 빠른 피드백**을 가능하게 하는 경영체계 변화
- 계약·품질·배포·운영 제약을 함께 제거하고 제품성과와 안정성으로 효과를 검증해야 함

## 1교시 10점 답안 발췌

```text
Vision → Backlog → Sprint → Increment → Feedback
전환축 = 전략·조직·프로세스·계약·기술
선택기준 = 요구 안정성·불확실성·규제·의존성·피드백 속도
```
