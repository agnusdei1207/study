## 지식 로드맵 내 현재 위치

지식 위치: IT 전략·관리 → 업무연속성·재해복구 → **RTO·RPO**

## 30초 인출

- 본질: **RTO(Recovery Time Objective)** 는 허용 가능한 서비스 중단시간, **RPO(Recovery Point Objective)** 는 허용 가능한 데이터 손실 시점이다.
- 메커니즘: **BIA** → 복구목표 설정 → 복제·대체환경 설계 → **전환·복귀** 훈련 → 실측 결과 환류한다.
- 산출물: 업무별 **RTO** · **RPO** 정의서 · **DRS** 설계 · **BCP** 절차 · 훈련 결과이다.

<details>
<summary>핵심 용어</summary>

- **RTO(Recovery Time Objective)** : 재해 발생 후 업무 및 서비스를 정상 재개하기까지 허용되는 최대 중단 시간
- **RPO(Recovery Point Objective)** : 재해 발생 시 복구 기준 시점으로 허용되는 최대 데이터 손실 시점
- **BIA(Business Impact Analysis)** : 업무 중단 시 발생하는 손실 영향을 시간대별로 분석하여 복구 우선순위를 결정하는 업무영향분석
- **BCP(Business Continuity Plan)** : 재해·재난 시 핵심 업무의 연속성을 유지하고 신속히 정상화하기 위한 종합 계획
- **DRS(Disaster Recovery System)** : 주 센터 재해 발생 시 서비스 연속성을 보장하기 위해 구축된 대체 재해복구시스템
- **Failover(장애 조치)** : 주 시스템 장애 시 대기 중인 보조 시스템으로 운영 권한과 트래픽을 자동·수동 전환하는 작업
- **Failback(복귀)** : 장애 복구 완료 후 보조 시스템의 운영 권한과 최신 데이터를 원래의 주 시스템으로 재전환하는 작업

</details>

## 예상문제

> RTO(Recovery Time Objective)와 RPO(Recovery Point Objective)를 비교하고, BIA 기반 수립절차와 DRS 적용 시 문제점·대응책을 설명하시오. (25점)

## Ⅰ. 서비스 중단과 데이터 손실의 목표선의 개요

> RTO와 RPO는 낮을수록 무조건 좋은 수치가 아니라 업무 중단 영향·기술 가능성·비용을 함께 반영한 복구 설계 기준임

- 정의: 재난·장애 시 허용 가능한 서비스 중단시간인 **RTO(Recovery Time Objective)** 와 데이터 손실 시점인 **RPO(Recovery Point Objective)** 를 정하는 복구목표
- 목적: **BIA(Business Impact Analysis)** 결과에 맞춰 복구 우선순위·복제방식·대체환경을 결정하는 것

## Ⅱ. BIA 기반 RTO·RPO 수립 흐름

> 업무 영향과 시스템 의존성을 먼저 분석하고 복구목표를 확정한 뒤 기술 대안을 매핑하며, 목표 달성은 전환훈련 실측으로 확인함

```mermaid
flowchart TD
    A["① 업무·의존성 식별"] -->|"업무·의존성 목록"| B["② BIA"]
    B -->|"영향도·복구 우선순위"| C["③ RTO·RPO 확정"]
    C -->|"업무별 복구목표"| D["④ DRS·BCP 설계"]
    D -->|"DRS 설계·BCP 절차"| E["⑤ 훈련·개선"]
    E -.->|"실측 결과·개선과제로 환류"| A
```

| 단계 | 활동 |
|---|---|
| ① 업무·의존성 식별 | 핵심 업무·시스템·외부 서비스 연결 |
| ② BIA | 중단 시간별 재무·운영·법적 영향 평가 |
| ③ RTO·RPO 확정 | 영향·규제·비용·기술 가능성 조정 |
| ④ DRS·BCP 설계 | 복제·대체환경·전환·복귀 절차 설계 |
| ⑤ 훈련·개선 | Failover·Failback·데이터 검증 |

## Ⅲ. RTO·RPO 비교

> RTO는 서비스를 언제 다시 열 것인지, RPO는 어느 시점의 데이터까지 되살릴 것인지를 결정하므로 구현 수단과 검증값이 다름

| 기준 | RTO | RPO |
|---|---|---|
| 통제 | 서비스 중단 | 데이터 손실 |
| 구간 | 재해 발생 → 서비스 재개 | 마지막 복구 가능 시점 → 재해 발생 |
| 수단 | 대체환경·Failover·복구절차 | Backup·Snapshot·복제 |
| 검증 | 실제 복구 소요시간 | 복구 데이터 시점·정합성 |

## Ⅳ. 복구전략 선택과 트레이드오프

> 짧은 복구목표일수록 준비된 대체환경·빈번한 복제·자동화가 필요해 비용과 운영 복잡성이 커지므로 업무별로 차등 설계함

```mermaid
flowchart TD
    O["RTO·RPO 목표"] --> H["Hot Site · 가동 대체환경"]
    O --> W["Warm Site · 일부 자원 준비"]
    O --> C["Cold Site · 기반시설 중심"]
    H --> T["짧은 복구시간 · 높은 비용"]
    W --> M["중간 복구시간 · 비용"]
    C --> L["긴 복구시간 · 낮은 상시 비용"]
```

- 사이트 명칭만으로 RTO·RPO가 보장되지 않으며 복제 지연·네트워크·의존 서비스·전환·복귀 절차를 함께 시험해야 함

## Ⅴ. RTO·RPO 운영의 문제점·대응책

> 문서상 목표와 실제 복구능력의 차이는 전환·복귀·데이터 정합성을 함께 실측해야 드러남

```mermaid
flowchart TD
    F["주 환경 장애"] --> S["Failover·서비스 검증·데이터 복구"]
    S --> Q{"실측 RTO·RPO가 목표 안인가?"}
    Q -->|예| P["통과 · 결과 기록·정기 재검증"]
    Q -->|아니오| R["미통과 · 병목·복제·절차 보완 후 재훈련"]
```

| 위험 | 대책 | 효과 |
|---|---|---|
| 짧은 RPO를 위한 복제 지연 | 핵심 업무만 동기·준동기 복제 검토 | 성능과 데이터 손실 목표 균형 |
| Failover·Failback 실패 | 전환·복귀·의존 서비스까지 훈련 | 실제 복구 가능성 확인 |
| 과잉 복구 투자 | BIA 기반 업무별 복구수준 차등화 | 중요도가 낮은 업무의 과잉 설계 감소 |

## Ⅵ. 결론 — 훈련 실측으로 닫는 복구목표

> RTO·RPO는 설계서의 숫자가 아니라 동일 시나리오를 반복 훈련해 달성해야 하는 운영 성능임

### 실전 답안용 기술사적 제언

- 문제: 문서상 수립된 RTO·RPO와 실제 재해 발생 시 복구 능력 간 괴리가 발생하고, 동기식 복제로 인한 상시 성능 저하 및 과잉 DRS 투자 비용이 초래됨.
- 해결 방안: BIA 기반 업무별 Tier 차등화(Tier 1은 실시간 복제·Active-Active, Tier 2 이하는 스냅샷·백업)를 적용하고, 불시 모의 Failover/Failback 훈련을 통해 실측 복구 시간과 데이터 정합성을 주기적으로 검증하여 개선 과제로 환류함.

```mermaid
flowchart TD
    subgraph Tiering["1. BIA 기반 업무 등급화 및 차등 설계"]
        T1["Tier 1 핵심업무: RTO 1h / RPO 0 (Active-Active · 동기 복제)"]
        T2["Tier 2 중요업무: RTO 4h / RPO 1h (Warm Site · 비동기 복제)"]
        T3["Tier 3 지원업무: RTO 24h / RPO 24h (Cold Site · 백업 테이프/클라우드)"]
    end
    subgraph Drill["2. 실전 불시 절체 및 복구 실측 (Drill)"]
        D1["모의 장애 주입 및 Failover 자동 전환"]
        D2["데이터 정합성(Lossless) 및 트랜잭션 무결성 검증"]
        D3["실측 복구 소요시간 vs 목표 RTO·RPO 대조"]
        D1 --> D2 --> D3
    end
    subgraph Feedback["3. 환류 및 개선 통제"]
        F1{"실측치 <= 목표치?"}
        F2["통과: 훈련 결과서 보존 및 기준 유지"]
        F3["미달: 병목 구간 아키텍처 재설계 및 절차 보완"]
        D3 --> F1
        F1 -->|Yes| F2
        F1 -->|No| F3
    end

    Tiering --> Drill
    F3 -.->|개선 과제 반영| Tiering
```

## 1교시 10점 답안 발췌

### 1. 정의·목적

- 정의: **RTO(Recovery Time Objective)** 는 재해 발생 후 서비스 재개까지 허용되는 목표 시간이며, **RPO(Recovery Point Objective)** 는 허용 가능한 데이터 손실 시점을 규정한 복구 목표선
- 목적: 업무 영향도(BIA)에 부합하는 복구 우선순위 확정 및 데이터 손실·서비스 중단 최소화

### 2. BIA 기반 수립절차

```mermaid
flowchart TD
    A["① 업무·의존성 식별"] -->|"업무·의존성 목록"| B["② BIA"]
    B -->|"영향도·복구 우선순위"| C["③ RTO·RPO 확정"]
    C -->|"업무별 복구목표"| D["④ DRS·BCP 설계"]
    D -->|"DRS 설계·BCP 절차"| E["⑤ 훈련·개선"]
    E -.->|"실측 결과·개선과제로 환류"| A
```

- 결론: 목표 달성은 문서가 아니라 전환·복귀 훈련의 실측 복구시간과 데이터 정합성으로 판정함
