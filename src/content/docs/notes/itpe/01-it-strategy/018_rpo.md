## 지식 로드맵 내 현재 위치

IT 전략·관리 → 업무연속성·재해복구 → **RTO·RPO**

## 30초 인출

- 본질: RTO(Recovery Time Objective)와 RPO(Recovery Point Objective)는 장애 뒤 복구에 허용하는 최대 중단 시간과, 복구할 데이터의 시점(허용 데이터 손실)을 정하는 복구 목표
- 메커니즘: 업무 영향 분석으로 업무별 허용 중단(MTD)과 데이터 손실 허용량을 정하고, RTO를 MTD 안에 두며 RPO를 데이터 보호 주기로 옮겨 복구 방식과 비용을 결정
- 통찰: 지속 복제로 RPO를 0에 가깝게 맞춰도 삭제·변조가 복제본에 그대로 반영되므로 RPO를 복제 지연과 손상 이전 시점으로 되돌리는 시점 복구의 두 목표로 나누어 정하고 시점 복구를 시험으로 확인

<details>
<summary>핵심 용어</summary>

- **RTO(Recovery Time Objective)** : 시스템 자원이 복구 중 사용 불가 상태로 머물러도 되는 최대 시간
- **RPO(Recovery Point Objective)** : 장애 이전 시점 가운데 최근 백업 사본으로 복구할 수 있는 데이터의 시점이며, 복구 과정에서 허용하는 데이터 손실량의 기준
- **MTD(Maximum Tolerable Downtime, 최대 허용 중단 시간)** : 시스템 소유자가 업무 프로세스의 중단에 대해 수용하는 총 시간
- **BIA(Business Impact Analysis, 업무 영향 분석)** : 서비스 중단이 업무에 미치는 영향을 정량화해 얼마나 빨리 복구해야 하고 얼마의 데이터 손실을 견딜 수 있는지 판단하는 분석
- **DR(Disaster Recovery, 재해 복구)** : 재해로 중단된 워크로드를 복구 목표에 맞게 되살리는 전략과 절차
- **Failover(장애 전환)** : 주 시스템 장애 시 복구 대상으로 트래픽을 넘기는 전환
- **Pilot Light** : 데이터 복제와 핵심 인프라는 켜 두고 애플리케이션 서버는 꺼 둔 복구 구성
- **Warm Standby** : 축소된 규모로 완전하게 동작하는 사본을 복구 리전에 상시 가동하는 복구 구성
- **Multi-site Active/Active** : 여러 리전이 동시에 트래픽을 처리하는 구성
- **시점 복구(Point-in-time Recovery)** : 백업에 담긴 특정 시점으로 데이터를 되돌리는 복구

</details>

## 2~4교시 25점 답안

## Ⅰ. RTO·RPO의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **RTO** 와 **RPO** 는 장애 뒤 허용하는 최대 복구 시간과 복구할 데이터 시점을 정하는 복구 목표 |
| 목적 | 복구 시간과 데이터 손실 허용치의 사전 합의, 복구 방식·비용 선택의 기준 확보 |

## Ⅱ. 시간과 데이터 시점을 나누는 RTO·RPO의 특징

| 특징 | 의미 |
|---|---|
| 두 축의 분리 | RTO는 복구에 걸리는 시간, RPO는 복구되는 데이터의 시점 |
| 별도 산정 | RPO는 **MTD** 에 포함되지 않고 복구 중 견딜 수 있는 데이터 손실량의 기준 |
| 백업 주기 의존 | 백업 실행 빈도가 달성 가능한 복구 시점을 결정 |
| 비용과 반비례 | RTO가 짧을수록 복구 방식의 구현 비용 증가 |
| 업무별 설정 | 워크로드별 영향·발생 확률·복구 비용을 따져 각각 결정 |

## Ⅲ. 장애 시점 기준의 복구 목표 체계

```text
마지막 복구 시점 ── 장애 발생 ── 서비스 재개
      │←─── RPO ───→│←──── RTO ────→│
      허용 데이터 손실     허용 복구 시간
```

### RTO와 MTD의 관계 확대

```text
업무 프로세스의 MTD (총 중단 허용 시간)
    │
    ├─ 시스템 복구 시간 ── RTO, 통상 MTD보다 짧게 설정
    │
    └─ 복구 후 데이터 재처리 시간 ── RTO에 더해 MTD 안에 수용

RPO ── MTD에 포함되지 않는 별도 기준, 허용 데이터 손실량
```

## Ⅳ. 복구 방식별 준비 상태와 비용

| 복구 방식 | 복구 사이트 준비 상태 | 장애 시 필요한 조치 | 비용·복잡도 |
|---|---|---|---|
| Backup and Restore | 데이터·설정·코드의 백업 보관 | 인프라·설정·코드 재배포와 데이터 복원 | 가장 낮음 |
| **Pilot Light** | 데이터 복제, 핵심 인프라 가동, 애플리케이션 서버 정지 | 서버 기동과 규모 확대 | 상시 가동 자원 최소화로 낮은 유지 비용 |
| **Warm Standby** | 축소된 완전 기능 사본 상시 가동 | 규모 확대만 수행, 축소 용량으로 즉시 처리 | Pilot Light보다 높고 복구 시간 단축 |
| **Multi-site Active/Active** | 여러 리전이 동시에 트래픽 처리 | Failover 없이 장애 리전의 트래픽 이탈 | 가장 복잡하고 고비용, 대부분의 재해에서 복구 시간 0에 가까움 |

Pilot Light와 Warm Standby는 평상시 복구 리전이 트래픽을 처리하지 않는 Active/Passive 방식.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 지속 복제로 RPO를 0에 가깝게 맞춰도 삭제·변조가 복제본에 그대로 반영 | 객체 버전 관리와 시점 복구 백업을 복제와 병행 |
| 침해된 계정의 권한으로 원본과 백업이 함께 삭제될 수 있음 | 백업을 별도 계정·리전으로 복사해 격리 |
| 문서상 목표와 실제 복구 성능의 차이가 시험 전에는 드러나지 않음 | 정기 복구 시험으로 실제 복구 시간과 복구 시점을 측정해 목표와 대조 |

## Ⅵ. 제언

RPO를 복제 지연 목표와 손상 이전 시점으로 되돌리는 시점 복구 목표로 나누어 정하고, 시점 복구 시험으로 두 목표의 충족을 확인

### RPO의 두 목표

```text
RPO
    │
    ├─ 복제 지연 목표 ── 사이트·리전 장애 시 최신 데이터 유실량
    │
    └─ 시점 복구 목표 ── 삭제·변조 이전 시점으로 되돌릴 수 있는 범위
```

### 시점 복구 시험 절차 확대

```text
삭제·변조 상황 가정
    ↓
발견 시점 이전의 마지막 정상 시점 식별
    ↓
해당 시점의 백업·버전으로 복구
    ↓
복구된 데이터의 정합 확인 후 실제 복구 시간·시점을 목표와 대조
```

| 구분 | 복제 지연만 기준 | 제언: 시점 복구 병행 |
|---|---|---|
| 대응 장애 | 사이트·리전 장애 | 사이트·리전 장애에 더해 삭제·변조 |
| 복구 시점 | 최신 시점에 가까움 | 손상 이전 정상 시점 |
| 확인 방법 | 복제 지연 모니터링 | 시점 복구 시험 |
