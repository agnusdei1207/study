## 지식 로드맵 내 현재 위치

IT 전략·관리 → 공공 정보화·조달관리 → **제안요청서(RFP)**

## 30초 인출

- 본질: RFP(Request for Proposal, 제안요청서)는 발주자가 사업자가 과업 규모를 산정할 수 있을 만큼 요구사항을 상세히 공개해 제안을 요청하는 문서
- 메커니즘: 요구사항 수집·분석·상세 작성 → 과업심의로 과업내용 확정 → RFP 반영·입찰공고 → 제안서 평가·계약 → 요구사항별 충족 여부 확인으로 인수
- 통찰: 산출정보는 작성 여부가 발주자 재량인 항목이라 성능·품질·보안 같은 비기능 요구사항의 검수 기준이 비기 쉬우므로, 요구사항마다 검수 때 확인할 산출정보를 명시한 뒤 RFP 확정

<details>
<summary>핵심 용어</summary>

- **RFP(Request for Proposal)** : 발주자가 사업 요구사항과 사업자 선정 조건을 공개해 사업자의 제안을 요청하는 문서
- **과업심의위원회** : 국가기관등이 두는 위원회로, 과업내용의 확정과 과업내용 변경의 확정 및 이에 따른 계약금액·계약기간 조정을 심의하는 기구
- **요구사항 고유번호** : 요구사항마다 부여해 계약·사업수행·검수 때까지 변경·삭제·수정을 관리하는 식별번호
- **산출정보** : 요구사항을 수행한 뒤 사업 완료 시점에 제출해야 할 산출물의 종류. 비기능 요구사항은 문서·보고서·화면 형태 가능
- **비기능 요구사항** : 기능 요구사항이 아닌, 성능·품질·보안처럼 시스템이 충족할 수준과 조건을 정한 요구사항
- **협상에 의한 계약** : 다수 공급자에게서 제안서를 받아 평가해 협상적격자를 선정하고, 협상으로 국가에 가장 유리한 자와 체결하는 계약 방식

## 2~4교시 25점 답안

## Ⅰ. 제안요청서(RFP)의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **제안요청서(RFP, Request for Proposal)** 는 발주자가 사업 요구사항을 상세하게 공개해 사업자의 제안을 요청하는 문서 |
| 목적 | 과업 규모의 산정 가능성 확보, 제안 평가·계약·검수의 공통 기준 마련 |

## Ⅱ. 과업 규모를 산정하게 하는 RFP의 특징

| 특징 | 내용 |
|---|---|
| 과업 규모 산정 가능한 상세도 | 국가기관등의 장은 사업자가 과업 규모를 산정할 수 있도록 요구사항을 상세하게 작성·공개 |
| 요구사항 단위 관리 | **요구사항 고유번호** 로 계약·수행·검수 때까지 변경·삭제·수정 관리 |
| 사전 확정된 과업 | **과업심의위원회** 가 확정한 과업내용을 발주 전까지 RFP에 반영 |
| 대가산정 방식과의 정합 | 기능점수 방식 또는 서비스수준협약 방식으로 사업대가를 산정하면 투입인력의 수·인적사항·투입기간 요구 불가 |
| 평가 기준의 사전 열람 | **협상에 의한 계약** 에서 계약을 체결하려는 자가 계약체결 세부기준을 열람하도록 조치 |

## Ⅲ. RFP 작성·확정 절차와 요구사항 상세화

### RFP 작성에서 인수까지의 절차

```text
요구사항 정의
  이해관계자 요구사항 수집 → 요구사항 분석·도출 → 상세내역 작성·검토
    ↓
과업심의: RFP(안)에 대한 과업내용 확정 (발주 전, 불가피하면 계약체결 전까지)
    ↓
확정 과업내용의 RFP 반영
    ↓
발주
  사업자 선정기준·절차 수립 → RFP 작성·법제도 요건 검토 → 입찰공고 → 제안서 평가·사업자 선정
    ↓
이행·관리
  사업수행계획서 검토·승인 → 요구사항별 충족 여부 확인 → 인수
```

### 상세 요구사항 작성표 확대: 요구사항 1건의 작성 항목

```text
요구사항 1건
    │
    ├─ 필수 작성 ── 분류 · 고유번호 · 명칭
    │
    ├─ 필수 작성 ── 상세설명: 정의 · 세부내용
    │
    ├─ 해당 시 작성 ── 산출정보 · 관련 요구사항
    │
    └─ 필수 작성 ── 요구사항 출처 (변경·관리용, RFP에는 미기재)
```

## Ⅳ. RFP 요구사항의 분류

| 분류 | 기술하는 내용 |
|---|---|
| 시스템 장비 구성 | 도입하는 하드웨어·소프트웨어·네트워크 장비 내역 |
| 기능 | 목표 시스템이 수행할 기능. 전체 시스템을 계층적으로 분해한 세부 기능별 작성 |
| 성능 | 처리속도·시간, 처리량, 동적·정적 용량, 가용성 |
| 인터페이스 | 외부 시스템 연계와 사용자 인터페이스 |
| 데이터 | 초기 자료 구축과 데이터 변환의 대상·방법, 보안이 필요한 데이터 |
| 테스트 | 도입 장비 성능 시험과 구축 시스템의 목표 대비 운영 점검 |
| 보안 | 정보 자산의 기밀성·무결성 확보를 위한 데이터·기능·운영 접근 통제 |
| 품질 | 품질 항목·평가 대상·목표. 신뢰성·사용성·유지관리성·이식성·보안성으로 구분 |
| 제약사항 | 사전에 파악된 기술·표준·업무·법제도 제약 |
| 프로젝트 관리 | 관리 방법과 추진 단계별 수행방안 |
| 프로젝트 지원 | 안정화·운영, 교육훈련·기술지원, 하자보수·유지관리 |

## Ⅴ. RFP 작성의 한계와 방안

| 한계 | 방안 |
|---|---|
| 기능 요구의 개략적 기술로 사업자의 과업 규모 산정 불가 | 전체 시스템을 계층적으로 분류하고 누락·중복 없는 세부 기능별로 요구사항 작성 |
| 산출정보가 해당 시 작성 항목이라 성능·품질·보안 요구사항의 검수 기준 공백 | 비기능 요구사항마다 문서·보고서·화면 형태의 산출정보 명시 |
| RFP 발주 뒤 과업 범위 다툼 발생 | 과업심의위원회가 확정한 과업내용을 발주 전까지 RFP에 반영 |
| 보안 요구의 작업장소·운영 접근 미반영 | 통제 대상별 보안 요구사항 작성, 작업장소 보안요건의 RFP 기재와 제시 장소의 준수 여부 확인 |

## Ⅵ. 제언

성능·품질·보안 요구사항의 산출정보 명시를 RFP 확정 조건으로 설정

### 산출정보 점검을 넣은 RFP 확정 흐름

```text
요구사항 상세 작성
    ↓
비기능 요구사항의 산출정보 작성 여부 점검
    ├─ 미작성 → 검수 때 확인할 문서·보고서·화면 추가
    └─ 작성 → 과업심의
    ↓
확정 과업내용 반영 → RFP 확정·입찰공고
```

### 보안 요구사항 확대: 통제 대상에서 인수 확인까지

```text
보안 요구사항 1건
    │
    ├─ 통제 대상 ── 데이터 · 기능 · 운영 접근
    │
    ├─ 산출정보 ── 검수 때 제출할 문서·보고서·화면
    │
    └─ 충족 확인 ── 요구사항별 충족 여부 확인 후 인수
```

| 구분 | 산출정보를 비워 둔 RFP | 제언: 산출정보 명시 후 확정 |
|---|---|---|
| 비기능·보안 요구의 검수 기준 | 서술 해석에 의존 | 문서·보고서·화면으로 확인 |
| 기준 확정 시점 | 계약 이후 협의 | RFP 확정 전 |
| 관리 단위 | 문서 전체의 서술 | 요구사항 고유번호별 산출정보 |

## 출제 이력과 검증 출처

- Q-net 제132~140회 문제지에서 RFP를 직접 묻는 문항은 확인되지 않음. 인접 문항은 제136회 4교시 3번(조달청 협상에 의한 계약 제안서평가 세부기준의 개정 주요 내용, 대형소프트웨어 사업 전문평가제도)
- 「소프트웨어 진흥법」 제44조(소프트웨어사업의 과업 범위)·제50조(소프트웨어사업 과업심의위원회) — 법률 제20476호, 2025.4.23. 시행 판본
- 「소프트웨어사업 계약 및 관리감독에 관한 지침」 제11조(제안요청서 작성)·제14조(작업장소 등)·제25조(과업내용의 확정 시기 및 기준 등)와 별표 2(소프트웨어사업 상세 요구사항 분석·적용기준) — 과학기술정보통신부고시 제2023-15호, 2023.5.15. 시행
- 「국가를 당사자로 하는 계약에 관한 법률 시행령」 제43조(협상에 의한 계약체결) — 대통령령 제36338호, 2026.6.3. 시행 판본
