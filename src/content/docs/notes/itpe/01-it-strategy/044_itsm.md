## 큰 그림과 30초 인출

```text
[비즈니스 사용자 / 고객]
          │ 서비스 요청 / 장애 신고 (단일 접점)
          ▼
[서비스 데스크 (Service Desk)]
 ├─ [인시던트 관리 (Incident)] ──> [신속 복구 (우회책/Workaround)]
 └─ [문제 관리 (Problem)]     ──> [근본 원인 규명 (Known Error DB)]
          │
          ▼ 변경 요청 (RFC)
[변경 관리 (Change / CAB)] ──> [릴리즈 및 배포 (Release)] ──> [CMDB 갱신]
          │
          ▼
[지속적 서비스 개선 (CSI)] ──(SLA/XLA 측정 및 피드백)──> [비즈니스 가치 창출]
```

- 본질: 기술 및 인프라 중심의 운영 방식에서 탈피하여, 사전에 합의된 서비스 수준(SLA)에 따라 고객과 비즈니스 관점에서 고품질 IT 서비스를 제공하고 지속적으로 개선하는 총체적 관리 체계
- 위치: `IT 전략 → ISO/IEC 20000 / ITIL 4 프레임워크 → ITSM 구축 → SLA/XLA 운영 → 지속적 개선(CSI)`
- 핵심 프로세스: `서비스 데스크(SPOC) · 인시던트 관리(신속 복구) · 문제 관리(근본 원인) · 변경 관리(CAB 통제) · CMDB(형상)`
- 표준 프레임워크: ISO/IEC 20000(국제 인증 규격) 및 ITIL 4(서비스 가치 시스템: SVS)

## 예상문제

> ISO/IEC 20000 및 ITIL 프레임워크 기반의 정보기술 서비스 관리체계(ITSM)의 개념을 설명하고, 인시던트·문제·변경 관리의 상호 연계 프로세스와 서비스 설계·구축·전환 활동 및 수박 효과(Watermelon Effect) 극복 방안을 논하시오. (25점)

## Ⅰ. 기술 중심 관리에서 고객 가치 창출로의 전환, ITSM 개요

- 정의: 정보시스템의 단순 하드웨어·소프트웨어 유지보수를 넘어, 고객과의 서비스 수준 협약(SLA)을 바탕으로 IT 서비스의 기획, 설계, 전환, 운영 및 개선을 전 수명주기에 걸쳐 체계화한 관리 체계
- 배경: 인프라 가동률 100%를 달성해도 현업 업무는 마비되는 기술과 비즈니스 간 괴리 해소, 잦은 장애와 무분별한 패치로 인한 운영 위험 통제
- 목적: IT 서비스의 안정성·가용성 극대화, 정량적 SLA 기반의 서비스 품질 가시화, IT 운영 비용 최적화 및 비즈니스 정렬

#### 한줄 요약
- 하드웨어가 아닌 고객 중심 서비스 관점에서 프로세스와 SLA로 IT 운영을 표준화한 체계임

## Ⅱ. ITSM 핵심 4대 운영 프로세스

| 프로세스 | 핵심 목표 | 주요 처리 메커니즘 | 핵심 산출물 |
|---|---|---|---|
| **인시던트 관리 (Incident)** | 서비스의 즉각적 정상 복구 | 단일 접점 접수, 우선순위 분류, 우회책(Workaround) 적용 | 인시던트 처리 티켓, 복구 시간 |
| **문제 관리 (Problem)** | 장애의 근본 원인(Root Cause) 제거 | 5-Why 원인 분석, 재발 방지 대책, 알려진 오류 등록 | 알려진 오류 DB (KEDB), 문제 분석서 |
| **변경 관리 (Change)** | 변경으로 인한 서비스 중단 최소화 | 변경 요청(RFC), 변경자문위원회(CAB) 영향도 심의 | 변경 승인서, 롤백 계획서 |
| **릴리즈 및 배포 (Release)** | 변경된 자산의 안전한 프로덕션 배포 | 스테이징 테스트, 무중단 배포(Blue/Green), CMDB 동기화 | 릴리즈 패키지, 배포 완료 보고서 |

#### 한줄 요약
- 인시던트로 불을 끄고, 문제 관리로 화재 원인을 없애며, 변경·릴리즈로 안전하게 시스템을 개선함

## Ⅲ. ITSM 참조 아키텍처 및 상호 연계 구조

```text
┌───────────────────────── [ 고객 / 현업 사용자 ] ─────────────────────────┐
│                                    │                                      │
│                       서비스 요청  │  단일 접점 (SPOC)                    │
│                       / 장애 신고  ▼                                      │
│       ┌─────────────────────────────────────────────────────────┐         │
│       │               서비스 데스크 (Service Desk)              │         │
│       └────────────────────────────┬────────────────────────────┘         │
│                                    │                                      │
│                ┌───────────────────┴───────────────────┐                  │
│                ▼ (장애 복구)                           ▼ (근본 원인)      │
│ ┌───────────────────────────────┐     ┌───────────────────────────────┐   │
│ │   인시던트 관리 (Incident)    │     │      문제 관리 (Problem)      │   │
│ │ - 빠른 업무 재개, 우회책 적용 │     │ - 근본 원인 분석, KEDB 등록   │   │
│ └──────────────┬────────────────┘     └───────────────┬───────────────┘   │
│                │                                      │                   │
│                └───────────────────┐ ┌────────────────┘                   │
│                                    ▼ ▼ RFC (변경 요청서)                  │
│       ┌─────────────────────────────────────────────────────────┐         │
│       │             변경 관리 (Change Mgmt / CAB)               │         │
│       │             - 리스크 및 영향도 평가, 승인               │         │
│       └────────────────────────────┬────────────────────────────┘         │
│                                    │                                      │
│                                    ▼                                      │
│       ┌─────────────────────────────────────────────────────────┐         │
│       │         릴리즈 및 배포 관리 (Release & Deployment)      │         │
│       │         - 무중단 배포 및 CMDB(형상 데이터베이스) 갱신   │         │
│       └─────────────────────────────────────────────────────────┘         │
└───────────────────────────────────────────────────────────────────────────┘
```

| 구성요소 | 주요 기능 및 역할 | 데이터 연계 |
|---|---|---|
| **서비스 데스크** | 사용자 접점 일원화(SPOC), 티켓 발행 및 1차 조치 | 인시던트 티켓 생성 및 사용자 피드백 접수 |
| **KEDB (Known Error)** | 문제 관리에서 규명한 기지 오류 및 공식 우회책 저장소 | 인시던트 발생 시 KEDB 참조로 즉각 해결 지원 |
| **CAB (변경자문위)** | 비즈니스 영향도, 일정 충돌, 보안 리스크 심의 기구 | 변경 승인, 보류, 반려 및 비상 변경 통제 |
| **CMDB (형상관리DB)**| 서버, DB, 네트워크, 서비스 간 의존성 관계 저장소 | 변경 영향도 분석 시 핵심 참조 기준선 |

#### 한줄 요약
- 단일 창구인 서비스 데스크를 통해 장애를 접수하고, KEDB와 CMDB를 참조하여 변경을 통제함

## Ⅳ. ISO/IEC 20000 기반 수명주기 4단계 프로세스

```text
① 서비스 전략 및 기획 → ② 서비스 설계 및 구축 → ③ 서비스 전환 및 릴리즈 → ④ 서비스 운영 및 지속적 개선
   └─ 비즈니스 요구 정렬    └─ 서비스 카탈로그, SLA   └─ 검증, 데이터 이행, 배포     └─ 인시던트/문제, CSI
```

| 수명주기 단계 | 주요 활동 내용 | 핵심 산출물 및 문서 |
|---|---|---|
| **1. 서비스 전략** | 고객 비즈니스 목표 분석, IT 서비스 포트폴리오 정의, 투자 타당성 검토 | 서비스 포트폴리오 명세서 |
| **2. 서비스 설계** | 서비스 카탈로그 작성, SLA/OLA 지표 확정, 보안 및 가용성·연속성 계획 설계 | 서비스 카탈로그, SLA 계약서 |
| **3. 서비스 전환** | 인수 테스트(UAT), 사용자 교육, 시스템 전환 및 롤백 계획 수립, 파일럿 릴리즈 | 전환 계획서, 릴리즈 패키지 |
| **4. 서비스 운영** | 서비스 데스크 가동, 인시던트/문제 해결, CMDB 형상 관리, 서비스 수준 평가 | 월간 SLA 보고서, CSI 개선 목록 |

#### 한줄 요약
- 전략에서 설계(SLA), 전환(릴리즈), 운영 및 지속적 개선(CSI)의 수명주기로 선순환함

## Ⅴ. 전통적 IT 관리 vs ITSM vs DevOps/SRE 비교

| 비교 항목 | 전통적 IT 관리 | ITSM (ITIL 기반) | DevOps / SRE |
|---|---|---|---|
| **초점 영역** | 인프라 및 애플리케이션 기술 | 고객 관점의 비즈니스 서비스 | 개발과 운영의 통합 및 지속적 배포 |
| **관리 방식** | 사후 장애 처리, 엔지니어 직관 | 프로세스 준수, SLA 계약, CAB 심의 | 자동화 파이프라인, 에러 예산(Error Budget) |
| **주요 지표** | 서버 가동률, CPU/MEM 점유율 | SLA 달성률, MTTR, 인시던트 해결률 | 배포 빈도, 리드 타임, 결함 복구 시간, SLO |
| **장점** | 구조가 단순하고 초기 도입 용이 | 서비스 품질 표준화 및 리스크 통제 | 빠른 비즈니스 변화 수용 및 민첩성 |
| **단점** | 비즈니스와 단절, 잦은 장애 | 프로세스 오버헤드로 인한 배포 지연 | 거버넌스 및 대외 규제 준수 미흡 위험 |

#### 한줄 요약
- 기술 중심에서 프로세스 중심(ITSM)을 거쳐 현대적 자동화 중심(DevOps/SRE)으로 발전함

## Ⅵ. 실무 실패 요인과 공학적 통제 방안

- 적용 상황: 대규모 엔터프라이즈의 차세대 시스템 오픈 후 ITSM 운영 체계 전환

| 실패 요인 | 근본 원인 | 공학적·관리적 해결 대책 | 기대 효과 |
|---|---|---|---|
| **수박 효과 (Watermelon Effect)** | SLA 지표는 99.9% 녹색(달성)이나 사용자는 불통으로 적색 | 기술 SLA 외에 사용자 체감 지표(XLA: 응답시간, 체감 오류) 결합 | 진정한 사용자 만족도 제고 |
| **CAB 심의 병목** | 모든 사소한 패치까지 주간 정기 CAB 심의를 거치며 배포 지연 | 리스크 평가 자동화로 저위험 '표준 변경'은 CI/CD 무심의 즉시 배포 | 릴리즈 민첩성 및 리드타임 단축 |
| **인시던트-문제 혼재** | 장애 처리 티켓 닫기에 급급하여 근본 원인 분석 방치 | 인시던트 담당자와 문제 관리자 분리 및 동일 장애 3회 시 문제 자동 등록 | 고질적 반복 장애 원천 차단 |
| **CMDB 데이터 노후화** | 수작업 입력으로 인해 실제 클라우드 인프라 구성과 불일치 | 인프라 자동 탐색(Discovery) 도구 및 IaC 파이프라인 연동 실시간 동기화 | 변경 영향도 분석의 정확성 확보 |

#### 한줄 요약
- XLA 도입, 표준 변경 자동화, Discovery 기반 CMDB 동기화로 프로세스 병목을 해소함

## Ⅶ. Site Reliability Engineering(SRE)과 결합한 현대적 결론

- **[무거운 프로세스에서 코드로 통제되는 서비스 신뢰성으로 진화]**: 전통적 ITSM의 가치(안정성, 서비스 정렬)는 여전히 유효하지만, 수작업 문서 승인은 민첩성을 저해하므로 SRE의 에러 예산(Error Budget)과 GitOps 자동 배포를 결합한 '스마트 ITSM'으로 진화해야 함
- 나라면: 엔터프라이즈 운영 거버넌스 구축 시 `SLI/SLO/SLA 3계층 지표 설계 → 에러 예산 소진 시에만 CAB 승인을 요구하는 정책 적용 → 클라우드 Discovery 연동 자동 CMDB 파이프라인 구축`을 서비스 사양서에 확정

#### 한줄 요약
- ITSM의 거버넌스 안정성과 SRE의 자동화 민첩성이 결합될 때 비즈니스 가치가 완성됨

## 1교시 10점 답안 발췌

### 1. ITSM(IT Service Management)의 정의
- IT 서비스를 고객과 비즈니스 관점에서 바라보고, 합의된 SLA에 따라 기획·설계·전환·운영·개선을 전 수명주기에 걸쳐 체계적으로 관리하는 서비스 중심 운영 체계

### 2. 핵심 운영 프로세스 루프
```text
[사용자 접점] ──> [서비스 데스크] ──> [인시던트 (신속 복구/우회책)]
                                          │ 근본 원인 해결 (RFC)
[지속 개선 (CSI)] <── [릴리즈/배포] <── [변경 관리 (CAB 심의)] <── [문제 관리 (KEDB)]
```

| 프로세스 | 핵심 목표 |
|---|---|
| 서비스 데스크 | 사용자 접점 일원화(SPOC) 및 신속한 1차 조치 |
| 인시던트 관리 | 우회책(Workaround)을 활용한 최단 시간 서비스 정상화 |
| 문제 관리 | 5-Why 분석을 통한 근본 원인 규명 및 KEDB 구축 |
| 변경 관리 | 변경자문위(CAB)를 통한 비즈니스 리스크 평가 및 승인 |

### 3. 차별화 제언
- 지표는 달성했으나 사용자는 불만족하는 '수박 효과'를 방지하기 위해 경험 수준 협약(XLA)을 도입하고, 저위험 표준 변경은 CI/CD 자동화로 전환하여 배포 민첩성을 확보해야 함
