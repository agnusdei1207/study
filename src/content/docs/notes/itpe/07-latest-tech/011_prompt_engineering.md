## 30초 인출

- 본질: **프롬프트 엔지니어링(Prompt Engineering)** 은 LLM의 가중치 수정 없이 입력 자연어 텍스트의 지시문, 문맥, 입출력 예시를 최적 설계하여 모델의 추론 정확도와 정형 출력 품질을 극대화하는 기법
- 메커니즘: 시스템 역할 정의, 제약조건 부과 후 Zero/Few-Shot 및 Chain-of-Thought(CoT) 단계적 사고를 유도하며, ReAct 패턴을 통해 외부 도구(API) 호출과 관찰을 반복 연계
- 통찰: 사소한 프롬프트 변경에 따른 성능 편차와 프롬프트 인젝션(Prompt Injection) 보안 위협이 상존하므로 DSPy 기반 프롬프트 자동 최적화 및 런타임 가드레일 결합 필수

<details><summary>핵심 용어</summary>

- **프롬프트 엔지니어링 (Prompt Engineering)** : 대규모 언어모델이 원하는 작업을 정확히 수행하도록 입력 컨텍스트를 구조화·최적화하는 공학적 방법론.
- **Zero-Shot / Few-Shot** : 예시 없이 지시문만 제공하는 방식(Zero-Shot)과 몇 가지 입출력 예시(Exemplars)를 제공하여 패턴을 모방시키는 방식(Few-Shot).
- **CoT (Chain-of-Thought)** : 복잡한 다단계 추론 문제에서 "단계별로 생각해보자(Let's think step by step)"와 같이 중간 추론 과정을 명시적으로 생성시키는 기법.
- **ReAct (Reasoning and Acting)** : 모델이 스스로 생각(Thought)하고, 외부 도구를 실행(Action)한 뒤, 그 결과(Observation)를 관찰하여 다음 단계를 결정하는 에이전트 루프.
- **프롬프트 인젝션 (Prompt Injection)** : 악의적 사용자가 입력 프롬프트를 조작하여 시스템의 원래 지시나 안전 제약조건을 무력화하고 권한을 탈취하는 공격.

</details>

## 2~4교시 25점 답안

## Ⅰ. 프롬프트 엔지니어링의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **프롬프트 엔지니어링(Prompt Engineering)** 은 모델의 사전학습 가중치를 동결(Freeze)한 상태에서 자연어 입력 구조, 문맥, 제약사항 및 예시를 체계적으로 설계하여 LLM의 출력 품질을 통제·최적화하는 기술 |
| 목적 | 값비싼 파인튜닝 비용 절감, 모델의 환각 억제, 정형화된 JSON/스키마 출력 유도 및 복잡한 추론 문제 해결 역량 확보 |

## Ⅱ. 프롬프트 엔지니어링의 4대 핵심 구성요소 및 특징

| 구분 | 4대 구성요소 | 세부 역할 및 특징 |
|---|---|---|
| **지시문 (Instruction)** | 핵심 작업 명세 | 모델이 수행해야 할 구체적 과업(요약, 번역, 분류, 코드 작성)을 명확한 동사형 명사구로 지정 |
| **문맥 (Context)** | 배경 지식 및 제약 | 외부 지식(RAG 검색 청크), 페르소나(역할 정의), 출력 포맷(JSON 스키마), 금지 규칙 설정 |
| **입력 데이터 (Input)** | 처리 대상 원문 | 사용자의 실제 질의 텍스트, 요약할 긴 문서, 분석 대상 로그 등 실제 입력 페이로드 |
| **출력 지시 (Output Indicator)** | 응답 형식 강제 | 원하는 응답 형식(예: `{"analysis": "", "score": 0}`)의 템플릿 마커 제시로 파싱 신뢰성 확보 |

## Ⅲ. 프롬프트 엔지니어링 기법 체계 및 에이전트 추론 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│               [ 고급 프롬프트 엔지니어링 추론 아키텍처 ]                 │
└────────────────────────────────────────────────────────────────────────┘
                                    │
 ┌──────────────────────────────────┴──────────────────────────────────┐
 │                                                                     │
 ▼                                                                     ▼
[ 정적 프롬프팅 기법 (Static) ]              [ 동적 에이전틱 프롬프팅 기법 (ReAct) ]
 1. Zero-Shot: 지시문 기반 직접 추론          1. 사용자 목표 입력 (Goal)
 2. Few-Shot: 입출력 예시 패턴 학습           2. Thought: 현재 상태 분석 및 계획 수립
 3. CoT: 단계적 추론 과정 유도                3. Action: 도구 호출 (Search, Calculator)
 4. ToT (Tree of Thoughts): 분기 탐색         4. Observation: 도구 반환 결과 관찰
                                             5. Loop: 목표 달성 시까지 2~4 반복 수행
 └──────────────────────────────────┬──────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ [ 출력 구조화 및 런타임 가드레일 (Output Structuring & Guardrails) ]   │
│  - Pydantic / JSON 스키마 유효성 검사 ──> 파싱 실패 시 자동 재시도      │
│  - 프롬프트 인젝션 및 유해성 차단 필터 ──> 안전한 정제 답변 최종 출력 │
└────────────────────────────────────────────────────────────────────────┘
```

| 기법 단계 | 핵심 메커니즘 | 대표 적용 사례 |
|---|---|---|
| **Zero-Shot CoT** | "단계별로 나누어 생각해 봅시다" 문구 주입 | 복잡한 산술 연산, 논리 퍼즐 문제 |
| **Self-Consistency CoT** | 여러 개의 CoT 추론 경로를 생성 후 다수결(Voting) 채택 | 수학적 증명, 정확도가 필수적인 의사결정 |
| **ReAct Loop** | 생각-행동-관찰의 연속적 사이클을 통한 실시간 외부 API 연계 | 실시간 주가 조회 에이전트, DB 쿼리 실행기 |

## Ⅳ. 주요 프롬프트 엔지니어링 기법 비교

| 비교 항목 | Zero-Shot | Few-Shot | Chain-of-Thought (CoT) | ReAct (에이전트) |
|---|---|---|---|---|
| **예시 제공 여부** | 0개 (지시문만) | 2~5개 입출력 예시 | 추론 단계가 포함된 예시 | 추론 + 도구 호출 명세 |
| **추론 복잡도** | 단순 분류, 요약 | 정형 포맷팅, 감성 분석 | 복잡한 수학, 다단계 논리 | 실시간 정보 탐색, 다단계 작업 |
| **토큰 소모량** | 극소 | 중간 | 높음 | 매우 높음 (반복 루프) |
| **외부 도구 연동** | 불가 (순수 생성) | 불가 (순수 생성) | 불가 (순수 추론) | 필수 (API, 검색기 결합) |
| **주요 한계** | 모호한 출력 가능성 | 컨텍스트 윈도우 점유 | 잘못된 중간 추론 시 오답 | 무한 루프 위험, API 비용 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 악의적 사용자가 입력 프롬프트 내에 탈옥(Jailbreak) 명령을 삽입하여 시스템 규칙을 무력화 | 시스템 지시문과 사용자 입력을 명확한 XML 구분자(`<user_input>`)로 분리하고 입출력 Llama-Guard 필터링 배치 |
| 사람이 수작업으로 작성한 프롬프트의 취약성과 모델 버전 업데이트 시 성능 퇴보(Regression) | DSPy 등 프롬프트 최적화 프레임워크를 도입하여 평가 데이터셋 기반 자동 퓨샷 선별 및 파이프라인 컴파일 |

## Ⅵ. 제언

수작업 프롬프팅의 한계를 탈피하여 프롬프트를 코드로 취급(Prompt-as-Code)하고, 자동화된 회귀 테스트와 가드레일을 결합한 LLMOps 운영 체계 구현.

```text
[ 프롬프트 템플릿 변경 (Git PR) ]
                 │
                 ▼
[ CI/CD 회귀 평가 파이프라인 (Promptfoo / DeepEval) ]
   ├── Step 1: 100개 골든 데이터셋 기반 정확도 및 F1-Score 측정
   ├── Step 2: 프롬프트 인젝션 모의 침투(Red Teaming) 자동 테스트
   └── Step 3: 지연 시간 및 토큰 비용 임계치 검증
                 │
                 ▼ (통과 시)
[ 프로덕션 게이트웨이 무중단 카나리 배포 ]
```

| 구분 | 기존 수작업 프롬프트 작성 | 제언: Prompt-as-Code 기반 자동화 |
|---|---|---|
| **작성 방식** | 엔지니어의 경험적 직관과 시행착오 | DSPy 기반 최적 프롬프트 자동 탐색 및 컴파일 |
| **버전 관리** | 소스코드 내 문자열 하드코딩 | Git 기반 템플릿 버전 관리 및 CI/CD 연동 |
| **품질 검증** | 1~2개 샘플 수기 테스트 | 골든 테스트셋 기반 자동 채점(LLM-as-a-Judge) |
