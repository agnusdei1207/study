## 연관 키워드

- 랭체인(LangChain), LLM(Large Language Model), RAG(Retrieval-Augmented Generation), 에이전트(Agent)
- LCEL(LangChain Expression Language), 랭그래프(LangGraph), 랭스미스(LangSmith), ReAct, 출력 파서(Output Parser), 휴먼 인 더 루프(HITL, Human-in-the-Loop)

## Ⅰ. 랭체인의 개요

- 핵심 요약 : 언어 모델 호출, 외부 지식 검색, 도구 실행, 대화 기억을 표준 인터페이스로 조립하는 오케스트레이션 프레임워크.
- 개념 : **거대 언어 모델**(LLM, Large Language Model)을 중심으로 프롬프트, 벡터 데이터베이스, API(Application Programming Interface) 도구, 대화 기록 메모리를 표준화된 인터페이스로 조립하는 **랭체인**(LangChain) 프레임워크.
- 배경 및 필요성 : LLM을 한 번 호출하는 것만으로는 최신 사내 지식을 반영하거나 여러 단계 작업을 수행하기 어렵다. 그렇다고 연결 코드를 직접 짜면 유지보수 비용이 커지므로, 외부 문서를 검색해 답변 근거로 덧붙이는 **RAG**(Retrieval-Augmented Generation, 검색 증강 생성) 같은 패턴을 표준 부품으로 묶어야 한다. 조립 추상화가 깊어질수록 디버깅이 어려워지므로 실행 추적 체계도 함께 필요하다.
- 주요 목적 : 단일 호출의 한계를 넘어, LLM이 도구를 스스로 골라 쓰는 **에이전트**(Agent)의 개발 생산성을 높이는 것.

## Ⅱ. 랭체인의 특징 및 장점

- 핵심 요약 : 표준 부품과 선언형 파이프라인이 연결되어 모델 교체와 흐름 구성을 빠르게 만드는 구조.

1. **LCEL**(LangChain Expression Language, 프롬프트·모델·파서를 파이프 연산자로 선언적으로 연결하는 문법) : 체인을 `|`로 이어 붙임 → 같은 코드로 비동기 실행, 스트리밍, 배치 처리를 지원.
2. 벤더 독립 인터페이스 : 여러 LLM 제공자를 같은 호출 방식으로 다룸 → 모델을 바꿔도 상위 로직 변경 범위가 줄어듦.
3. **출력 파서**(Output Parser, 모델 응답을 정해진 형식의 객체로 변환하는 구성요소) : 후속 로직이 값을 안정적으로 받아 쓸 수 있음.
4. 기억과 검색 부품 : 대화 메모리, 문서 로더, 분할기, 벡터 저장소를 제공 → 멀티턴 대화와 문서 검색을 짧은 코드로 구현.

## Ⅲ. 랭체인의 구조 (흐름)

- 핵심 요약 : 선형 흐름은 LCEL 체인으로, 반복과 분기가 필요한 에이전트는 상태 그래프로 구성하는 이중 구조.
- **랭그래프**(LangGraph, 상태를 공유하는 노드와 조건부 엣지로 에이전트 흐름을 표현하는 프레임워크) : 반복과 분기를 명시적으로 제어하고 중간 상태를 보존.
- **ReAct**(Reasoning and Acting, 추론과 도구 실행을 번갈아 수행하는 에이전트 패턴) : 생각, 도구 실행, 관찰 결과 반영을 완료 시점까지 반복.

```text
[ LCEL 선형 체인 ]

사용자 질문
   ↓
프롬프트 템플릿
   ↓
LLM 모델
   ↓
출력 파서
   ↓
최종 응답
```

```text
[ LangGraph 순환 구조 ]

시작: 상태 초기화
   ↓
에이전트 노드 (LLM 추론)
   ↓ 조건부 분기
도구 호출 필요 → 도구 실행 노드
   ↓ 관찰 결과를 상태에 추가
에이전트 노드로 복귀 (순환)
   ↓ 완료 시
최종 응답 노드
```

## Ⅳ. 랭체인의 비교

- 핵심 요약 : 랭체인은 범용 조립과 상태 제어에 강점이 있고, 검색 특화나 역할 기반 협업은 다른 프레임워크가 더 단순할 수 있다.

| 비교 축 | LangChain / LangGraph | LlamaIndex | AutoGen | CrewAI |
| --- | --- | --- | --- | --- |
| 핵심 강점 | 범용 조립, 상태 기반 그래프 제어 | 문서 인덱싱과 검색 특화 | 대화형 다중 에이전트 | 역할 기반 협업 에이전트 |
| 주요 적용처 | 복합 AI 앱, 에이전트 워크플로 | 사내 지식 검색 | 연구용 다자 대화, 자동 코딩 | 업무 자동화 흐름 |
| 학습 곡선 | 중간에서 높음 (API 변경이 잦음) | 중간 | 다소 높음 | 낮음 |

- 선택 기준 : 검색 중심 서비스인지, 복잡한 상태 제어가 필요한지, 역할 기반 협업으로 충분한지에 따라 프레임워크를 고른다.

## Ⅴ. 랭체인의 한계와 방안

- 핵심 요약 : 추상화와 잦은 변경, 에이전트의 무한 반복, 중간 단계의 추적 불가를 버전 고정, 반복 한도, 관측 체계로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 추상화 계층과 잦은 API 변경 | 래퍼 클래스가 많고 인터페이스가 자주 바뀌어 유지보수 난항 | 단순 호출은 공급자 SDK로 처리하고, 복합 흐름에만 LangChain을 쓰며 버전을 고정 | 버전 업그레이드 소요 시간 |
| 에이전트의 무한 반복과 도구 오류 | 도구 실행 실패나 반복 호출로 서버 자원과 API 토큰 낭비 | 최대 반복 횟수(Recursion Limit) 설정, 인자 검증, 예외 시 대체 체인 실행 | 평균 단계 수, 토큰 소비량 |
| 중간 단계 추적 불가 | 분산 실행에서 병목 지점과 프롬프트 인젝션 흔적을 찾기 어려움 | 랭스미스(LangSmith) 또는 OpenTelemetry로 단계별 입출력과 지연 시간을 기록 | 단계별 지연 시간, 오류율 |

## Ⅵ. 랭체인에 대한 기술사적 제언

- 핵심 요약 : 프레임워크를 블랙박스로 쓰지 않고, 상태 제어와 복구, 사람 개입을 설계 원칙으로 두어야 함.

1. 개발 조직은 단순 호출에는 프레임워크를 쓰지 않는 기준을 세워 과도한 추상화를 피하고, 복합 흐름에만 LangChain과 LangGraph를 적용해야 한다.
2. 플랫폼 조직은 노드마다 체크포인트를 남기는 상태 저장 구조를 공통 설계로 정해, 중간 실패 시 전체를 다시 실행하지 않고 해당 지점부터 재시도할 수 있게 해야 한다.
3. 업무 책임 부서는 결제나 외부 발송처럼 위험한 행동 앞에 **휴먼 인 더 루프**(HITL, Human-in-the-Loop, 사람이 승인해야 다음 단계로 넘어가는 구조)를 두어야 한다.

## Ⅶ. 결론

- 핵심 요약 : 랭체인은 LLM 기능을 부품으로 조립하는 오케스트레이션 프레임워크이며, 에이전트의 제어와 관측이 실무 성패를 가름.
- 시사점 : 조립의 편의보다 상태 제어와 추적 가능성을 얼마나 확보하느냐가 프로덕션 적용의 기준이 된다.
