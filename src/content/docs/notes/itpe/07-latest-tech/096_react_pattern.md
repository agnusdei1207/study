## 답안 골격
```text
[ReAct 패턴] ◀━━ 머리: Ⅶ 내 의견 (추론과 행동 루프의 교차 실행으로 환각을 외부 환경 관측으로 검증하는 자율 에이전트 인지 패러다임)
 ┃
 ┣━ Ⅰ 개요 ───── 순수 추론(CoT)의 외부 지식 단절과 순수 행동(Act-only)의 계획력 부재 극복 → 추론과 행동의 상호작용적 결합
 ┣━ Ⅱ 특징 ───── 생각-행동-관측(Thought-Action-Observation) 순환 루프 · 실시간 동적 계획 수립 · 외부 도구 연계 · 환각 자가 교정
 ┣━ Ⅲ 구조 ───── 추론 생성기(LLM) + 행동 실행기(Action Executor) + 환경/도구(Environment/Tools) + 관측 피드백(Observation)
 ┣━ Ⅳ 흐름 ───── ① 사용자 질문 수신 → ② Thought: 현 상황 분석 및 다음 행동 계획 → ③ Action: 외부 도구/API 호출 → ④ Observation: 도구 실행 결과 획득 → ⑤ 반복 후 Final Answer 산출
 ┣━ Ⅴ 비교 ───── CoT(생각 사슬) vs Act-only(단순 도구 호출) vs ReAct (내부 추론만 수행 vs 생각 없이 API 직행 vs 생각과 도구 관측의 유기적 결합)
 ┗━ Ⅵ 실무 ───── 반복 루프에 따른 토큰 누적 및 지연시간 증가 / 잘못된 관측 결과 해석에 따른 에러 전파 / 도구 스키마 환각
```
- 필수 키워드: ReAct · Thought(생각) · Action(행동) · Observation(관측) · 자율 에이전트 · 도구 연계(Tool Use) · 환각 억제
- 기출: 미출제. 예상: "자율 AI 에이전트의 문제 해결 능력을 고도화하기 위한 ReAct(Reasoning and Acting) 패턴의 개념, 동작 사이클 및 기존 CoT 대비 이점을 설명하시오." → Ⅰ~Ⅶ

## 한 줄 본질
- 언어 모델 혼자 생각만 하면(CoT) 최신 사실을 몰라 헛소리를 지어내고, 도구만 무작정 호출하면(Act) 왜 그 도구를 썼는지 모른 채 길을 잃음 → '생각(Thought)'으로 계획을 세우고, '행동(Action)'으로 도구를 실행하며, '관측(Observation)'으로 현실 데이터를 확인하는 3단계 루프 반복 → 환각 없는 현실 세계 문제 해결 / 다단계 호출에 따른 지연과 토큰 비용 발생

## 핵심 그림
```text
[ReAct(Reasoning and Acting)의 상호작용적 인지 순환 루프]

       [사용자 질의 (User Question)]
                    │
                    ▼
 ┌───> ┌──────────────────────────────────────────────┐
 │     │ 1. Thought (추론/계획)                        │
 │     │   - "현재 무엇을 알고 있는가?"                │
 │     │   - "다음에 어떤 도구를 호출해야 하는가?"     │
 │     └──────────────────────┬───────────────────────┘
 │                            │
 │                            ▼
 │     ┌──────────────────────────────────────────────┐
 │     │ 2. Action (행동/도구 호출)                   │
 │     │   - Search[API 키워드], Calculator[수식] 등   │
 │     └──────────────────────┬───────────────────────┘
 │                            │
 │                            ▼ (외부 환경/API 실행)
 │     ┌──────────────────────────────────────────────┐
 │     │ 3. Observation (관측/결과 반영)              │
 │     │   - API 반환값, 웹 문서 검색 결과 등         │
 │     └──────────────────────┬───────────────────────┘
 │                            │
 └── (목표 미달성 시 반복) ───┴───> [Final Answer: 최종 답변 도출]
```

## 핵심 용어
- Thought(추론): 다음 행동을 결정하기 위해 문제를 분해하고, 이전 관측 결과를 해석하며, 현재 상태를 점검하는 모델 내부의 자기 성찰적 텍스트
- Action(행동): 모델이 외부 환경과 상호작용하기 위해 출력하는 구조화된 명령(예: `Search[Query]`, `Python[Code]`, `DB_Query[SQL]`)
- Observation(관측): 모델이 실행한 Action에 대해 외부 실행 환경(Python 런타임, 웹 브라우저, DB 엔진)이 반환한 실제 데이터

## 핵심 통찰
- ReAct의 본질은 "인간의 문제 해결 방식의 모사": 요리사가 레시피를 보며(Thought), 냉장고를 열어 재료를 꺼내고(Action), 재료의 신선도를 확인한 뒤(Observation), 다음 조리법을 생각하는 과정과 동일
- 환각(Hallucination)의 실시간 교정: 모델이 "한국의 현재 인구는 6천만 명이다"라는 잘못된 사전 지식을 갖고 있더라도, Search Action 후 반환된 Observation(5,170만 명)을 보고 즉각 Thought 단계에서 자기 신념을 수정함
- 지연시간과 정확도의 트레이드오프: 일반적인 LLM 질의는 1회 생성으로 끝나지만, ReAct는 평균 3~5회의 왕복 호출이 발생하여 지연시간이 수초 이상 늘어나므로 고난도 복합 질의에 선별 적용해야 함

## 이웃 토픽과 구분
- ReAct vs Chain-of-Thought(CoT): CoT는 모델 내부 가중치만을 사용한 폐쇄형 단계별 추론 / ReAct는 외부 API 및 환경의 관측 결과를 실시간으로 받아들여 추론 경로를 유연하게 수정하는 개방형 루프

## 문제·원인·대책
- 적용 상황: 고객 주문 이력 및 재고 DB를 조회하여 클레임을 처리하는 ReAct 기반 상담 에이전트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 모델이 동일한 잘못된 검색 Action을 무한 반복하며 토큰과 시간 낭비 | 직전 Action의 실패 원인을 Thought 단계에서 제대로 성찰하지 못함 | 반복 탐지 알고리즘 및 3회 이상 동일 액션 시 대안 탐색 프롬프트 주입 | 무한 루프 100% 방지 |
| 외부 API 반환값이 수천 줄의 JSON 형태로 너무 길어 모델 컨텍스트 초과 | 원시 API 응답(Observation)을 필터링 없이 그대로 컨텍스트에 주입 | Observation 전처리 요약기 및 JSON 파싱 인터페이스(JMESPath) 적용 | 컨텍스트 토큰 소비량 70% 절감 |
| 모델이 정의되지 않은 가짜 도구 이름(Hallucinated Tool)을 Action으로 호출 | 도구 스키마의 모호성 및 모델의 엄격한 포맷 출력 제약 부재 | Pydantic 기반 함수 호출(Function Calling) 및 문법 강제(Outlines/CFG) 적용 | 유효하지 않은 도구 호출 제로화 |

## 내 의견
- [ReAct와 상태 그래프(StateGraph)를 결합한 결정론적 제어 아키텍처 도입] 순수 텍스트 기반 ReAct는 언어 모델의 비결정론적 특성으로 인해 프로덕션 환경에서 돌발 행동 위험이 큼 → 나라면: LangGraph와 결합하여 ReAct의 Thought는 허용된 상태 노드 안에서만 수행되도록 상태 머신 엣지를 강제하고, Action 단계에는 엄격한 JSON Schema 검증과 RBAC 권한 통제 레이어를 두어 엔터프라이즈 환경에 적합한 안전한 ReAct 런타임을 구축
