## 연관 키워드

- 텐서플로우(TensorFlow), 텐서(Tensor), 데이터 플로우 그래프, Eager 실행, tf.function
- Keras, tf.GradientTape, 자동 미분, XLA(Accelerated Linear Algebra)
- TFX(TensorFlow Extended), TF Serving, LiteRT, ONNX(Open Neural Network Exchange)
- PyTorch, MLOps, 연산자(Op) 호환성, SavedModel

## Ⅰ. 텐서플로우의 개요

- 핵심 요약 : 텐서의 흐름을 그래프로 표현해 CPU, GPU, TPU에서 학습과 추론을 가속하는 엔드투엔드 머신러닝 플랫폼.
- 개념 : 다차원 배열인 **텐서**(Tensor)의 연산을 데이터 플로우 그래프로 표현하고, CPU·GPU·TPU(Tensor Processing Unit) 환경에서 딥러닝 모델의 설계, 학습, 배포를 지원하는 오픈소스 플랫폼.
- 배경 및 필요성 : 연구 단계에서 쓰는 즉시 실행(Eager) 방식과 실서비스의 그래프 기반 실행 사이에는 연산자 지원과 수치 차이가 생기므로, 배포 대상별로 변환과 회귀 검증을 자동화하는 파이프라인이 필요함.
- 주요 목적 : 모델 설계부터 분산 학습, 서버와 기기 배포까지 하나의 생태계로 묶어 운영 비용을 줄이는 것.

## Ⅱ. 텐서플로우의 특징 및 장점

- 핵심 요약 : 하이브리드 실행, 자동 미분, 하드웨어 최적화, 배포 생태계가 결합되어 연구와 운영을 한 도구로 잇는 구조.

1. 하이브리드 실행 : 즉시 실행(Eager)으로 디버깅하고 **tf.function**으로 그래프를 컴파일 → 연구 편의와 배포 성능을 함께 확보.
2. 자동 미분 : **tf.GradientTape**가 순전파 연산을 기록하여 가중치에 대한 그래디언트를 자동 계산 → 역전파 코드 작성 부담 감소.
3. 하드웨어 최적화 : **XLA** 컴파일러가 연산을 융합 → 중간 결과의 메모리 입출력이 줄어 처리 효율 향상.
4. 배포 생태계 : TFX 파이프라인, TF Serving, LiteRT로 학습부터 서버와 기기 배포까지 연결 → 운영 전환 비용 절감.

## Ⅲ. 텐서플로우의 구조 (흐름)

- 핵심 요약 : 고수준 API, 실행 엔진, 컴파일러와 런타임, 하드웨어 추상화의 4계층 스택과 TFX 기반 운영 흐름.

```text
[ TensorFlow 소프트웨어 스택 ]

고수준 API (Keras 모델 정의)
        ↓
실행 엔진 (Eager, tf.function, GradientTape)
        ↓
컴파일러·런타임 (XLA, 분산 실행)
        ↓
하드웨어 추상화 (CPU, GPU, TPU)
```

```text
[ TFX 기반 MLOps 흐름 ]

데이터 검증 (TFDV)
        ↓
전처리 변환 (TF Transform)
        ↓
모델 학습과 평가
        ↓
서빙 배포 (TF Serving, LiteRT)
```

- **TFX**(TensorFlow Extended) : 데이터 검증, 전처리, 학습, 서빙을 파이프라인으로 묶은 운영 플랫폼.
- **LiteRT** : 기기 내부(온디바이스) 추론을 위한 런타임으로, 이전의 TensorFlow Lite 이름을 이어받음.

## Ⅳ. 텐서플로우와 PyTorch의 비교

- 핵심 요약 : TensorFlow는 배포와 운영 생태계, PyTorch는 연구 구현의 편의에서 강점이 있어 용도에 따라 선택이 갈림.

| 비교 항목 | TensorFlow (2.x) | PyTorch |
| --- | --- | --- |
| 계산 그래프 | 즉시 실행이 기본, tf.function으로 정적 그래프 컴파일 | 동적 그래프 중심 |
| 자동 미분 | tf.GradientTape로 연산 기록 | autograd로 텐서 연산 자동 추적 |
| 고수준 인터페이스 | Keras 중심 | 객체지향 Python 문법 중심 |
| 배포 생태계 | TF Serving, TFX, LiteRT로 운영 경로가 정리됨 | TorchServe, TorchScript, ONNX 연계 중심 |
| 주요 채택 분야 | 산업 현장의 대규모 MLOps 운영 | 학계 연구와 신규 모델 구현 |

- 선택 기준 : 연구 속도와 최신 모델 이식이 중요하면 PyTorch, 배포 안정성과 운영 파이프라인이 중요하면 TensorFlow가 유리함.

## Ⅴ. 텐서플로우의 한계와 방안

- 핵심 요약 : 버전 간 비호환, 온디바이스 연산자 누락, 연구 코드 이식 지연을 단계적 전환과 표준 포맷으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 버전 간 비호환 | 정적 세션 기반 TF 1.x 코드와 TF 2.x Keras 체계가 호환되지 않아 마이그레이션 부담 발생 | tf.compat.v1 모듈로 단계 전환, 공식 업그레이드 스크립트(tf_upgrade_v2) 활용 | 레거시 API 사용 비율 |
| 온디바이스 변환 시 연산자 미지원 | 서버에서 동작하던 특수 연산이 LiteRT 변환에서 누락되어 추론 오류 발생 | Select TF Ops 명시적 활성화, 커스텀 커널 등록 | 변환 실패율 |
| 최신 연구 구현의 도입 지연 | 연구 코드가 PyTorch 중심으로 공개되어 최신 모델 이식이 늦어짐 | ONNX 중간 표현을 활용한 모델 변환과 가중치 변환 절차 마련 | 모델 이식 소요 기간 |

## Ⅵ. 텐서플로우에 대한 기술사적 제언

- 핵심 요약 : 연구와 배포를 표준 포맷으로 분리하고, 변환 결과를 자동 검증하는 체계로 프레임워크 종속을 낮추는 방향.

1. 기술 조직은 모든 단계를 한 프레임워크에 묶기보다 연구 도구와 배포 포맷을 분리하여, 연구 생산성과 운영 안정성을 함께 얻는 구조를 설계해야 한다.
2. 서빙 인프라 팀은 모델 아티팩트를 표준 형식으로 보관하여, 프레임워크 업그레이드가 서빙 계층 전체의 변경으로 번지지 않게 해야 한다.
3. 플랫폼 팀은 모델 변환 후의 출력 차이를 허용 오차 기준으로 자동 비교하는 검증 단계를 배포 파이프라인에 포함해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 텐서플로우는 텐서 연산 그래프를 학습부터 기기 배포까지 잇는 엔드투엔드 머신러닝 플랫폼.
- 시사점 : 프레임워크의 가치는 기능 수보다 변환과 운영 경로의 안정성에서 드러나므로, 배포 표준과 검증 자동화가 도입 판단의 핵심 기준이 됨.
