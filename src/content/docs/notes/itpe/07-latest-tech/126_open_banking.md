## 연관 키워드

- 오픈뱅킹(Open Banking), 금융결제원, 표준 API, 마이데이터(MyData)
- OAuth 2.0, 액세스 토큰(Access Token), 동의 관리, 스크래핑
- 단일 장애점(SPOF), mTLS, FDS, FAPI(Financial-grade API)
- 거래 추적 ID, 서킷 브레이커, 분쟁 조정

## Ⅰ. 오픈뱅킹의 개요

- 핵심 요약 : 참가 금융기관의 조회와 이체 기능을 표준 API와 중계 허브로 개방하는 금융 공동 인프라.
- 개념 : 은행과 핀테크 기업이 기관별 개별 연동 없이 **표준 API**(Application Programming Interface) 하나로 참가 기관의 계좌 조회와 이체 기능을 이용하도록 하는 금융 공동 인프라로, 국내에서는 **금융결제원**이 중계 허브를 운영함.
- 배경 및 필요성 : 기관마다 연동 방식이 다르면 핀테크 기업의 개발 비용이 누적되고, 이용자 정보를 직접 수집하는 방식은 정보 노출 위험을 키우므로, 표준 규격과 토큰 기반 권한 위임 계층이 필요함.
- 주요 목적 : 결제망 접근을 개방해 경쟁을 넓히고, 스크래핑 방식을 대체해 개인정보 보호와 시스템 안정성을 확보하며, 금융 혁신 서비스의 출시 기간을 줄이는 것.

## Ⅱ. 오픈뱅킹의 특징 및 장점

- 핵심 요약 : 표준 API, 토큰 기반 권한 위임, 중계 허브 구조가 결합되어 연동 비용 절감과 정보 노출 축소로 이어지는 방식.

1. 표준 인터페이스 : **RESTful JSON**(JavaScript Object Notation) 규격의 API를 공통으로 사용 → 기관별 개별 개발이 줄어 연동 기간 단축.
2. 권한 위임 : **OAuth 2.0**(Open Authorization 2.0) 기반으로 이용자 동의 후 스코프별 액세스 토큰을 발급 → 비밀번호와 인증서를 이용기관이 직접 보관하지 않음.
3. 중계 허브 구조 : 금융결제원 중계망이 인증 확인, 라우팅, 감사 로그를 담당 → 참가 기관마다 다른 연결을 한 지점으로 모음.
4. 동의 기반 정보 제공 : 계좌 연결과 정보 제공 동의를 실시간으로 조회하고 철회 → 이용자가 정보 흐름을 통제.

## Ⅲ. 오픈뱅킹의 구조 (흐름)

- 핵심 요약 : 이용자 동의, 이용기관 토큰 호출, 중계 허브 검증, 참가 기관 원장 처리의 4단계 흐름.

```text
[ 오픈뱅킹 연계 흐름 ]

이용자 인증과 동의 (OAuth 2.0)
        ↓
이용기관 (핀테크 앱·서비스)
   액세스 토큰으로 표준 API 호출
        ↓
금융결제원 중계 허브
   인증 검증·라우팅·감사 로그
        ↓
참가 금융기관 (계좌 원장 처리)
```

```text
[ 토큰 기반 권한 위임 ]

이용자 동의 (조회·이체 범위 지정)
        ↓
인가 코드 발급
        ↓
액세스 토큰 발급 (만료 시 갱신 토큰 사용)
        ↓
표준 API 호출 (토큰 검증 후 응답)
```

| API 분류 | 대표 API | 처리 기능 |
| --- | --- | --- |
| 조회 서비스 | 잔액조회, 거래내역조회, 계좌실명조회 | 계좌 잔액과 거래 내역 조회, 수취 계좌 유효성 확인 |
| 이체 서비스 | 출금이체, 입금이체 | 동의 기반 출금과 참가 기관 계좌로의 송금 |
| 관리·보안 | 토큰 발급·갱신, 동의 해지 | 액세스 토큰 갱신, 이용자 동의 철회의 실시간 반영 |

## Ⅳ. 오픈뱅킹과 스크래핑, 기관별 개별 연동의 비교

- 핵심 요약 : 개별 연동은 기관 수만큼 비용이 늘고, 스크래핑은 비밀번호 노출 위험이 있어 표준 API 기반 오픈뱅킹이 두 방식의 한계를 보완함.

| 비교 축 | 기관별 개별 연동 | 스크래핑 | 오픈뱅킹 (표준 API) |
| --- | --- | --- | --- |
| 연동 방식 | 기관마다 별도 개발 | 이용자 계정 정보로 화면을 긁어옴 | 표준 API와 중계 허브 |
| 권한 모델 | 기관별 계약 기준 | 이용자 인증 정보를 직접 사용 | 동의 기반 토큰과 스코프 |
| 보안 통제 주체 | 각 기관 | 불명확 | 중계 허브와 참가 기관의 분담 |
| 확장성 | 기관 수에 비례해 비용 증가 | 화면 변경에 취약 | 규격 준수 시 연동 확장 용이 |

## Ⅴ. 오픈뱅킹의 한계와 방안

- 핵심 요약 : 중계 허브 장애, 토큰 탈취에 따른 부정 출금, 분쟁 시 책임 소재 불명확을 이중화, 보안 강화, 추적 체계로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 단일 장애점 (SPOF, Single Point of Failure) | 모든 거래가 중계 허브를 거쳐 허브 장애 시 연계 기관 전체에 영향 | 허브의 이중화, 기관 간 서킷 브레이커와 대체 경로 설계 | 허브 가용률, 장애 복구 시간 |
| 토큰 탈취와 앱 위변조에 따른 부정 출금 | 탈취된 토큰이나 위변조 앱으로 무단 거래 발생 | mTLS(Mutual TLS) 적용, 토큰 수명 관리, FDS 연계 이상 거래 차단 | 부정 거래 탐지율, 차단 건수 |
| 분쟁 시 책임 소재 불명확 | 여러 기관을 거치는 거래에서 사고 주체 규명이 어려움 | 거래 추적 ID를 전 구간에 부여, 감사 로그 보존, 분쟁 처리 절차 명문화 | 분쟁 처리 기간 |

## Ⅵ. 오픈뱅킹에 대한 기술사적 제언

- 핵심 요약 : 공동 거버넌스와 보안 프로파일, 동의 기반 데이터 원칙을 함께 세워 오픈뱅킹을 신뢰할 수 있는 금융 인프라로 운영하는 방향.

1. 금융 당국과 금융결제원은 사고 발생 시 기관 간 공조 절차와 책임 분담 기준을 공동으로 정해, 기술 장애와 분쟁을 같은 틀에서 다루어야 한다.
2. 이용기관과 참가 기관은 금융 전용 API 보안 프로파일(FAPI)과 같은 상위 보안 기준을 검토하여, 기관마다 다른 보안 수준의 격차를 줄여야 한다.
3. 금융 외 플랫폼과 결합할 때는 이용자 동의와 정보 최소 수집 원칙을 상위 정책으로 고정하여, 서비스 확장이 정보 통제 범위를 넘지 않도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 오픈뱅킹은 표준 API와 토큰 기반 권한 위임으로 금융 결제 접근을 개방하는 공동 인프라.
- 시사점 : 개방의 효과는 중계 허브의 안정성과 이용자 동의 체계가 뒷받침될 때만 유지되므로, 보안과 책임 체계가 확산 속도를 따라가야 함.
