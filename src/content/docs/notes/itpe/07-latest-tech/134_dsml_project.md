## 한 줄 본질
- DSML 프로젝트는 데이터 품질·모델 성능·업무 효과가 사전에 확정되지 않으므로, 가설·대표 데이터·업무 지표를 정의해 실험하고 배포 후에도 성능과 효과를 검증하는 관리가 필요

## 핵심 용어
- PoC 트랩(PoC Trap): 시험 환경의 성능이 좋아도 데이터 파이프라인·운영 시스템 연동·현업 활용이 부족해 실제 서비스로 전환되지 못하는 현상
- CRISP-DM(Cross-Industry Standard Process for Data Mining): 비즈니스 이해 → 데이터 이해 → 데이터 준비 → 모델링 → 평가 → 배포의 6단계를 반복 순환하는 데이터 마이닝/DSML의 글로벌 표준 프로세스
- 숨은 기술 부채(Hidden Technical Debt): 모델 코드 밖의 데이터 검증·피처·서빙·설정·모니터링 등에서 유지보수 부담이 커질 수 있다는 관점. 코드 비율은 시스템마다 다름

## 핵심 통찰
- "정확도(Accuracy)에 취하지 말고 비즈니스 화폐 가치(Dollar)로 환산하라": 데이터 과학자는 AUC가 0.92에서 0.94로 올랐다고 기뻐하지만, 경영진은 "그래서 고객 이탈이 몇 명 줄어들고 얼마가 절감되는가?"를 묻기 때문에 두 지표의 가교 설계가 프로젝트의 생사를 가름
- 애자일(Agile)과 데이터 탐색의 융합: 머신러닝은 3개월 뒤에 어떤 모델이 최고일지 사전에 알 수 없으므로, 2주 단위 스프린트로 가설을 검증하고 가망 없는 아이디어는 빠르게 폐기(Fail-fast)하는 애자일 접근이 필수적임
- 크로스 펑셔널 팀(Cross-functional Team) 구성: 데이터 과학자(알고리즘) 혼자서는 배포를 못 하고, 데이터 엔지니어(파이프라인)와 ML 엔지니어(서빙), 현업 도메인 전문가가 첫날부터 원팀으로 결합해야 성공함

## 이웃 토픽과 구분
- 일반 IT 프로젝트 vs DSML 프로젝트: 일반 IT는 요구사항을 정하고 코드를 짜면 결과가 결정론적으로 나옴 / DSML은 데이터 품질에 따라 모델 성능이 확률적으로 요동치므로 가설 검증과 연구개발(R&D) 성격이 짙음

## 1교시 10점 답안
- **정의:** 데이터로 해결할 업무 문제를 정하고 모델을 개발·운영하여 성과를 검증하는 프로젝트.
- **단계:** 문제·성과 지표 정의 → 데이터 수집·품질 점검 → 실험·검증 → 배포 → 성능·편향·데이터 변화 감시.
- **특징:** 데이터 품질과 실험 반복에 따른 불확실성이 크므로 PoC 성능과 운영 성능을 분리 관리.

## 2~4교시 25점 답안
### Ⅰ. 착수
- 업무 의사결정과 연결된 지표, 허용 오류·지연·비용, 데이터 사용 권한 및 기준선을 정의.
### Ⅱ. 개발
- 데이터 계보·품질·누수 점검 후 훈련/검증/시험 분리, 단순 기준 모델과 후보 모델 비교, 실험 이력 보존.
### Ⅲ. 운영 전환
- 추론 경로·서빙 용량·롤백·책임자 확정, 배포 전 운영 데이터 대표성과 보안 점검, 단계적 출시.
### Ⅳ. 사후 관리
- 성능 저하·드리프트·비용·피드백을 모니터링하고 재학습 승인과 폐기 기준 마련. 목표 수치는 업무별 실측.
