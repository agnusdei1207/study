## 연관 키워드

- DSML 프로젝트, 탐색적 데이터 분석(EDA, Exploratory Data Analysis), 피처 스토어(Feature Store)
- MLOps(Machine Learning Operations), CI/CD/CT, 데이터 드리프트(Data Drift), 개념 드리프트(Concept Drift)
- PoC(Proof of Concept), 학습-서빙 불일치(Training-Serving Skew), 데이터 버전 관리(DVC, Data Version Control), 모델 레지스트리(Model Registry)

## Ⅰ. DSML(Data Science and Machine Learning) 프로젝트의 개요

- 핵심 요약 : 데이터 분석, 모델링, 운영 자동화를 하나의 반복 생애주기로 묶어 비즈니스 가치를 지속적으로 만드는 엔지니어링 체계.
- 개념 : 정형·비정형 데이터를 분석하고 가설을 세워 머신러닝 모델을 만든 뒤, 배포와 재학습까지 운영하는 **DSML 프로젝트** (DSML, Data Science and Machine Learning 기반의 개발·운영 생애주기). 운영 단계는 **MLOps** (Machine Learning Operations, 모델 개발과 운영을 자동화·표준화하는 실천 체계)가 담당함.
- 배경 및 필요성 : 실험 환경에서 정확도만 높이는 데 머물면 운영 단계에서 서빙 장애와 기술 부채가 커짐. 그래서 **PoC** (Proof of Concept, 개념 검증) 이후 실제 서비스로 넘어가려면 **피처 스토어** (Feature Store, 학습과 서빙이 같은 입력 변수를 공유하도록 관리하는 저장소)와 **CI/CD/CT** (Continuous Integration, Continuous Delivery, Continuous Training)에 기반한 자동화 파이프라인이 필수임.
- 주요 목적 : 데이터 기반 의사결정 자동화, 수작업 프로세스의 지능화, 투자 대비 효과인 **ROI** (Return on Investment) 입증.

## Ⅱ. DSML(Data Science and Machine Learning) 프로젝트의 특징 및 장점

- 핵심 요약 : 가설과 실험을 반복하는 개발 방식과 데이터 품질 통제, 버전 관리가 결합되어 재현 가능한 운영 체계를 만드는 것이 장점.

1. 가설 기반 반복 : 고정된 요구 명세 대신 실험 결과로 목표를 갱신 → 성능이 점진적으로 수렴.
2. 데이터 종속성 관리 : 결측, 이상치, 클래스 불균형을 상시 통제 → 입력 품질에 따른 성능 편차 감소.
3. 다학제 협업 : 현업 도메인 전문가, 데이터 과학자, 머신러닝 엔지니어, 데이터 엔지니어가 공동 수행 → 실험에서 운영으로 넘어가는 인계 지연 감소.
4. 3원 거버넌스 : 코드, 데이터, 모델을 함께 버전 관리하는 **데이터 버전 관리** (DVC, Data Version Control, 데이터셋의 변경 이력을 추적하는 도구) → 실험 결과를 되짚어 재현 가능.

## Ⅲ. DSML(Data Science and Machine Learning) 프로젝트의 구조 (흐름)

- 핵심 요약 : 비즈니스 정의에서 운영 감시까지 4단계가 이어지고, 운영 중 드리프트가 재학습을 촉발하는 순환 구조.
- 1단계 : 정량적 KPI를 정하고, 예측 시점과 추론 지연 한계인 **SLA** (Service Level Agreement, 서비스 수준 협약)를 정의함.
- 2단계 : **탐색적 데이터 분석** (EDA, Exploratory Data Analysis, 분포, 결측, 이상치를 시각화와 통계로 살피는 단계)을 거친 뒤 수집, 정제, 인코딩, 스케일링으로 피처를 만들고 온라인과 오프라인에 함께 등록함.
- 3단계 : 복수 알고리즘을 비교하고, 실험 파라미터와 지표를 **실험 추적** (Experiment Tracking, 실험의 설정과 결과를 자동 기록하는 활동)으로 남긴 뒤 독립 테스트 셋으로 평가함.
- 4단계 : 점진 배포로 실무 트래픽을 검증하고, 드리프트를 감시하며, 임계치를 넘으면 재학습을 실행함.

```text
[1. 비즈니스 이해와 가설 정의]
  KPI 설정, 추론 지연 한계(SLA) 정의
        ↓
[2. 데이터 준비와 피처 엔지니어링]
  수집, 정제, 인코딩, 피처 스토어 등록
        ↓
[3. 모델링과 실험 추적]
  복수 알고리즘 비교, 실험 기록, 블라인드 평가
        ↓
[4. 배포와 지속적 학습]
  점진 배포, 드리프트 감시, 재학습
```

```text
운영 중 예측 결과 수집
        ↓
데이터 드리프트·개념 드리프트 감시
        ↓ 임계치 초과
재학습 파이프라인 실행
        ↓
검증 통과 시 모델 레지스트리 갱신
```

- **데이터 드리프트** (Data Drift, 입력 데이터 분포의 변화)와 **개념 드리프트** (Concept Drift, 입력과 정답의 관계 변화)을 구분해 감시함.
- **모델 레지스트리** (Model Registry, 학습된 모델의 버전과 승인 상태를 관리하는 저장소)에 등록된 모델만 배포 대상으로 삼음.

## Ⅳ. DSML(Data Science and Machine Learning) 프로젝트와 전통 소프트웨어 개발의 비교

- 핵심 요약 : 결정론적 코드 중심의 개발에서 확률적 결과와 데이터 중심의 개발로 전환되어, 테스트와 유지보수 기준이 달라짐.

| 비교 항목 | 전통적 소프트웨어 개발 | DSML 프로젝트 |
| --- | --- | --- |
| 동작 결정성 | 동일 입력이면 동일 출력 (결정론적) | 확률적 추론 결과 산출 (비결정론적) |
| 요구사항 확정 | 초기 분석 단계에서 기능 명세 확정 | 탐색적 분석과 실험 결과에 따라 변경 |
| 핵심 자산 | 소스 코드와 데이터베이스 스키마 | 데이터셋 버전, 피처 파이프라인, 모델 가중치 |
| 테스트 체계 | 단위, 통합, 시스템 테스트 | 오프라인 정밀도·재현율 평가, A/B 테스트, 드리프트 검출 |
| 유지보수 트리거 | 비즈니스 로직 변경, 소프트웨어 버그 | 데이터 분포 변화와 성능 저하 |

- 선택 기준 : 규칙으로 결과가 명확히 정해지면 전통 개발, 데이터 패턴을 학습해 예측과 분류를 해야 하면 DSML 프로젝트를 택함.

## Ⅴ. DSML(Data Science and Machine Learning) 프로젝트의 한계와 방안

- 핵심 요약 : PoC 정체, 학습과 서빙 불일치, 개념 드리프트를 표준 파이프라인, 공통 피처 관리, 드리프트 감시로 통제해야 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| PoC 이후 프로덕션 전환 실패 (Pilot Purgatory) | 노트북 실험 환경과 운영 인프라의 기술 격차로 상용화 중단 | 초기부터 컨테이너 기반 파이프라인과 모듈화된 코드 강제, Kubeflow, Vertex AI 같은 MLOps 플랫폼 표준화 | 전환 소요 기간, 노트북 의존 파이프라인 비율 |
| 학습-서빙 불일치(Training-Serving Skew)와 데이터 누출 | 학습과 서빙의 피처 계산 로직이 달라 운영 추론 오류 발생 | 온라인·오프라인 공통 피처 스토어(Feast 등)로 연산 로직 단일화, 시점 기준 누출 차단 | 학습·서빙 피처 값 불일치율 |
| 개념 드리프트에 따른 성능 저하 | 고객 행동과 시장 변화로 배포 초기의 정확도가 하락 | 콜모고로프-스미르노프(Kolmogorov-Smirnov) 검정 기반 드리프트 감시와 재학습 트리거 | 드리프트 검출 빈도, 재학습 주기 |

## Ⅵ. DSML(Data Science and Machine Learning) 프로젝트에 대한 기술사적 제언

- 핵심 요약 : 개인 노트북 중심의 모델링을 팀 단위 공동 책임과 승인 기반 배포 체계로 바꿔야 함.

1. 연구원 개인의 노트북 모델링에서 벗어나, 데이터 과학자, 머신러닝 엔지니어, 현업 분석가가 한 팀에서 공동 책임지는 구조로 전환해야 한다.
2. 소스 코드와 데이터셋, 모델 가중치를 한곳에서 버전 관리하고, 모델 레지스트리의 승인 절차를 거치지 않은 모델은 운영 환경에 배포하지 못하도록 절차를 묶는 것이 바람직하다.
3. 재학습과 배포를 사람이 직접 수행하는 수동 작업으로 두지 않고 주기적 자동 파이프라인으로 바꾸되, 그 전제로 모델 성능 기준을 사전에 합의해 두어야 한다.

## Ⅶ. 결론

- 핵심 요약 : DSML 프로젝트는 정확도를 만드는 실험과 그것을 운영 가치로 바꾸는 파이프라인이 함께 설계될 때 성과가 이어지는 생애주기 체계임.
- 시사점 : 모델 개발보다 운영 자동화와 데이터 품질 관리가 비즈니스 효과의 지속성을 좌우함.
