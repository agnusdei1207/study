## 연관 키워드

- 스마트 계약(Smart Contract), 튜링 완전(Turing-Complete), 가스(Gas), 이더리움 가상 머신(EVM)
- 탈중앙 오라클(Decentralized Oracle), 프록시 패턴(Proxy Pattern), 재진입 공격(Reentrancy), CEI 패턴
- 형식 검증(Formal Verification), 정적 분석(Static Analysis), 탈중앙화 금융(DeFi), 자율 조직(DAO)

## Ⅰ. 스마트 계약의 개요

- 핵심 요약 : 블록체인에서 조건이 충족되면 중개자 없이 자동 집행되는 프로그램이며, 배포 후 수정이 어려워 설계와 검증이 핵심.
- 개념 : 블록체인에 배포되어 사전에 정한 조건이 충족되면 계약 내용을 중개자 없이 자동 실행하는 프로그램 (**스마트 계약**, Smart Contract). 임의의 계산을 표현할 수 있는 **튜링 완전** (Turing-Complete) 연산 능력을 갖는 것이 특징.
- 배경 및 필요성 : 배포된 코드는 수정이 어렵고 기록된 거래는 되돌리기 어려워, 취약점이 공격으로 이어지면 자산 손실이 영구적으로 남음. 따라서 취약점 패턴을 설계 단계에서 막고 **형식 검증** (Formal Verification, 수학적 명세로 코드 성질을 증명하는 기법)을 병행할 필요가 있음.
- 주요 목적 : 중개 비용 절감, 집행의 즉시성과 투명성 확보, **탈중앙화 금융** (DeFi, Decentralized Finance)과 **자율 조직** (DAO, Decentralized Autonomous Organization) 같은 응용의 기반 제공.

## Ⅱ. 스마트 계약의 특징 및 장점

- 핵심 요약 : 자동 집행, 공개 원장, 자원 통제가 결합되어 중개 비용과 집행 지연을 줄이는 대신, 불변성에 따른 위험을 함께 떠안는 구조.

1. 자동 집행 : 조건이 충족되면 코드가 즉시 실행 → 중개 기관의 처리 지연과 수수료 감소.
2. 불변성과 투명성 : 배포 코드와 실행 기록이 공개 원장에 남음 → 사후 검증이 가능하지만 수정이 어려워 설계 오류의 파급이 큼.
3. 상태 기반 실행 : 계정의 저장소 변수가 계약 간에 공유됨 → 복합 금융 로직과 토큰 발행을 구현 가능.
4. 가스 기반 자원 통제 : 연산마다 **가스** (Gas, 연산 단위별 수수료 개념의 계량 단위)를 차감 → 무한 루프와 자원 남용을 억제.
5. 구성 가능성 : 계약끼리 서로 호출하며 **토큰 표준** (ERC-20, ERC-721) 위에 응용을 쌓음 → 조합형 생태계 형성.

## Ⅲ. 스마트 계약의 구조 (흐름)

- 핵심 요약 : 고수준 코드가 바이트코드로 컴파일되어 노드 합의를 거쳐 가상 머신에서 실행되고, 호출 순서는 CEI 원칙으로 고정되는 구조.
- **이더리움 가상 머신** (EVM, Ethereum Virtual Machine) : 모든 노드가 같은 결과를 내도록 바이트코드(옵코드)를 해석 실행하는 실행 환경.
- **ABI** (Application Binary Interface, 애플리케이션 이진 인터페이스) : 외부 호출 시 함수명과 인자를 바이트 단위로 인코딩·디코딩하는 규약.
- **가스 계량** (Gas Metering) : 단계마다 가스를 차감하고, 가스가 바닥나면 상태 변경을 되돌리는 방식.
- **머클 패트리샤 트라이** (Merkle Patricia Trie, 계정 상태를 해시 트리로 묶어 원장에 고정하는 자료 구조) : 상태 변경의 무결성을 해시 값으로 증명.
- **CEI 패턴** (Checks-Effects-Interactions, 검증 후 상태 변경, 외부 호출은 마지막에 수행하는 호출 순서 원칙) : 재진입 공격을 구조적으로 차단.

```text
[ 배포와 실행 흐름 ]

Solidity 코드 작성
        ↓ 컴파일
바이트코드와 ABI 생성
        ↓ 서명된 배포 트랜잭션
트랜잭션 풀 → P2P 전파 → 노드 검증
        ↓ 블록 합의
컨트랙트 계정 생성, EVM 상태 적재
```

```text
[ 호출 순서 원칙: CEI 패턴 ]

1. Checks : 권한, 인자, 잔액 검증
        ↓
2. Effects : 저장소 상태를 먼저 갱신
        ↓
3. Interactions : 외부 송금과 호출은 마지막
```

## Ⅳ. 비트코인 스크립트와 이더리움 스마트 계약의 비교

- 핵심 요약 : 비트코인 스크립트는 단순성으로 공격 표면을 줄이고, 이더리움 스마트 계약은 표현력을 얻는 대신 가스 제어와 취약점 관리가 필요.
- 비교 대상은 **비트코인 스크립트** (Bitcoin Script)와 EVM 기반 스마트 계약.

| 비교 축 | 비트코인 스크립트 | EVM 기반 스마트 계약 |
| --- | --- | --- |
| 언어 특성 | 튜링 불완전, 반복문 없음 | 튜링 완전, 반복문 지원 |
| 실행 모델 | 스택 기반 조건식 평가 | 가상 머신의 바이트코드 해석 |
| 상태 관리 | 무상태 UTXO 검증 모델 | 상태 기반 계정과 저장소 모델 |
| 자원 제약 | 연산자 수와 스크립트 크기 제한 | 가스 소비로 무한 루프 방지 |
| 활용 범위 | 단순 다중서명, 시간 잠금 지출 | 금융 로직, 토큰 발행, DAO 구현 |
| 공격 표면 | 논리가 단순해 작음 | 재진입 등 복잡한 로직에 따른 노출이 큼 |

- 선택 기준 : 지급 조건처럼 단순한 로직이면 제약이 큰 방식이 안전하고, 복합 금융이나 자율 조직이면 표현력과 검증 비용을 함께 따져 선택.

## Ⅴ. 스마트 계약의 한계와 방안

- 핵심 요약 : 외부 데이터 신뢰, 수정 불가, 재진입, 로직 결함, 중단 지연을 탈중앙 오라클, 프록시 업그레이드, CEI, 정적 분석, 일시 정지 체계로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **오라클 문제** (Oracle Problem) | 외부 데이터를 단일 출처에 의존하면 가짜 가격이나 결과 주입으로 자산이 탈취됨 | 독립 노드가 데이터를 모아 이상치를 제거하고 합의값을 제공하는 **탈중앙 오라클** (Decentralized Oracle Network) 채택 | 데이터 출처 수, 이상치 제거율 |
| 배포 후 수정 불가 | 로직 버그가 발견돼도 배포된 코드를 바꿀 수 없어 서비스 중단이나 자산 손실로 이어짐 | **프록시 패턴** (Proxy Pattern)으로 고정 주소를 두고 구현 계약으로 위임 호출, 다중서명 거버넌스 아래 구현체만 교체 | 업그레이드 승인 소요 시간, 구현체 교체 이력 |
| **재진입 공격** (Reentrancy) | 잔액을 갱신하기 전에 외부 호출을 허용해 같은 인출이 반복되어 자금이 고갈됨 (2016년 DAO 해킹이 대표 사례) | CEI 패턴 준수, 재진입 방지 잠금(ReentrancyGuard, `nonReentrant` 제어자) 적용 | 정적 분석 고위험 탐지 건수, 감사 지적 건수 |
| 로직 결함의 배포 전 누락 | 정수 오버플로우, 접근 제어 누락 같은 결함이 배포 전 발견되지 않음 | **정적 분석** (Static Analysis, 실행 없이 코드를 검사하는 기법) 도구 적용과 독립 감사 병행 | 고위험 취약점 잔존 건수 |
| 중단 대응의 지연 | 해킹 징후가 보여도 즉시 멈출 수단이 없으면 피해가 누적됨 | 일시 정지 기능을 두되 멀티시그 승인으로만 발동 | 탐지부터 정지까지 소요 시간 |

## Ⅵ. 스마트 계약에 대한 기술사적 제언

- 핵심 요약 : 검증, 거버넌스, 비상 대응을 배포 이전의 운영 기준으로 내재화해 불변성이 만드는 위험을 관리 가능한 수준으로 낮추는 것이 핵심.

1. 개발 조직은 배포 전 정적 분석과 독립 감사를 필수 단계로 두고, 핵심 불변식(Invariant)을 명세해 형식 검증 대상으로 삼을 필요가 있다.
2. 사업 조직은 업그레이드 가능성과 불변성 중 무엇을 택할지 명시적으로 결정하고, 업그레이드 권한은 다중서명 거버넌스 아래 두는 것이 바람직하다.
3. 운영 조직은 해킹 징후를 감지했을 때 즉시 중단할 수 있는 비상 절차와 권한 분리를 사전에 문서화하고 모의 훈련으로 검증할 필요가 있다.
4. 규제와 정책 조직은 자율 조직과 탈중앙화 금융의 책임 주체를 정의해, 이용자 피해가 발생했을 때 책임 소재를 가릴 기준을 마련하는 것이 필요하다.

## Ⅶ. 결론

- 핵심 요약 : 스마트 계약은 블록체인 위에서 중개 없이 집행되는 자동화 로직으로, 신뢰를 제도 대신 코드와 검증에 맡기는 구조.
- 집행의 투명성만큼 검증 체계의 완성도가 중요하므로, 설계와 검증을 함께 평가하는 시각이 필요하다.
