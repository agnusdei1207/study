## 연관 키워드

- 모듈러 RAG(Modular RAG), 나이브 RAG(Naive RAG), 고급 RAG(Advanced RAG)
- 검색 증강 생성(RAG), 오케스트레이션, 라우팅, 리랭킹(Re-ranking)
- 하이브리드 검색, BM25, 상호 순위 융합(RRF), 교차 인코더(Cross-Encoder)
- 근거성 검증, 단일 책임 원칙(SRP), 개방-폐쇄 원칙(OCP)

## Ⅰ. 모듈러 RAG의 개요

- 핵심 요약 : 고정 선형 파이프라인을 벗어나 검색·메모리·라우팅 등 기능을 교체 가능한 모듈로 나누고 질의에 맞게 조립하는 컴포넌트 기반 검색 증강 생성 구조.
- 개념 : 검색 증강 생성(RAG, Retrieval-Augmented Generation)의 흐름을 검색, 메모리, 라우팅, 융합, 정제, 검증의 독립 모듈로 분리하고, 질의 복잡도와 업무 요구에 따라 모듈 실행 그래프를 동적으로 구성하는 **모듈러 RAG** (Modular RAG) 아키텍처.
- 배경 및 필요성 : 검색 대상이 비정형 문서뿐 아니라 정형 DB, 지식 그래프, 실시간 웹 검색으로 넓어지고 도메인별 검색 품질과 지연 기준도 다르므로, 고정 단일 파이프라인으로는 대응이 어려워져 소프트웨어 공학의 모듈화가 필요해짐.
- 주요 목적 : 확장성과 유연성 확보, 모듈별 독립 교체와 최적화, 도메인별 검색 구성(레시피)의 동적 조합.

## Ⅱ. 모듈러 RAG의 특징 및 장점

- 핵심 요약 : 기능의 독립 교체와 질의별 동적 조립이 신규 기능 추가 비용 절감과 질의 적응성으로 이어지는 구조.

1. 기능 모듈화 : 검색, 메모리, 융합, 정제, 검증을 각각 독립 컴포넌트로 캡슐화 → 특정 모듈의 교체나 개선이 전체 시스템 재작성 없이 가능.
2. 질의 적응성 : 질의의 난이도에 따라 필요한 모듈만 실행 → 단순 질의의 처리 비용과 지연 감소.
3. 다중 소스 지원 : **하이브리드 검색** (벡터 검색과 키워드 검색을 결합해 의미 유사성과 정확 일치를 함께 반영)과 그래프·SQL 검색을 플러그인으로 연결 → 데이터 소스 확장의 부담 축소.
4. 설계 원칙의 적용 : 단일 책임 원칙(SRP, Single Responsibility Principle)과 개방-폐쇄 원칙(OCP, Open-Closed Principle)을 파이프라인 설계에 적용 → 신규 모듈 추가 시 기존 모듈 수정 최소화.

## Ⅲ. 모듈러 RAG의 구조 (흐름)

- 핵심 요약 : 라우팅 모듈이 실행 그래프를 만들고, 검색·메모리·융합 결과가 정제와 검증을 거쳐 생성기로 수렴하는 구조.
- **라우팅 및 오케스트레이션 모듈** (Routing & Orchestration Module) : 질의 의도를 분석해 태스크별로 모듈 실행 순서를 동적으로 구성하는 제어 계층.
- **검증 모듈** (Verification Module) : 생성 답변이 검색 문서에 근거하는지 점검하고, 실패하면 검색 모듈을 다시 호출하는 피드백 루프 수행.

```text
[ 모듈러 RAG 실행 흐름 ]

사용자 질의
      ↓
라우팅·오케스트레이션 (의도 분석)
      ↓
검색 / 메모리 / 융합 모듈 (선택 실행)
      ↓
정제·리랭킹 (문맥 압축, 중복 제거)
      ↓
검증 모듈 (근거성 점검)
      ↓ 실패 시: 검색 모듈 재호출
      ↓ 통과 시
생성 모듈 (LLM 또는 sLM, 출처 표기 답변)
```

```text
[ 모듈 구성 계층 ]

오케스트레이션 계층 (실행 그래프 조립)
  - 검색 모듈 : 벡터·BM25·그래프·SQL
  - 메모리 모듈 : 대화 요약, 사용자 선호
  - 융합 모듈 : 질의 확장, RRF 병합
  - 정제 모듈 : 교차 인코더 재정렬
  - 검증 모듈 : 근거성 자체 검증
```

## Ⅳ. 나이브 RAG·고급 RAG와의 비교

- 핵심 요약 : 고정 선형 구조에서 조정 가능한 파이프라인을 거쳐 독립 모듈의 동적 조립으로 진화하는 단계적 차이.

| 비교 항목 | **나이브 RAG** (Naive RAG) | 고급 RAG (Advanced RAG) | 모듈러 RAG (Modular RAG) |
| --- | --- | --- | --- |
| 파이프라인 구조 | 단순 고정 선형 | 전처리·후처리가 추가된 고정 선형 | 실행 그래프 기반 동적 조립 |
| 구성 요소 결합도 | 강결합, 수정이 어려움 | 일부 컴포넌트만 교체 가능 | 느슨한 결합, 독립 교체 |
| 질의 적응성 | 모든 질의에 동일한 절차 | 사전 규칙에 따른 튜닝 | 질의 난이도별 모듈 선택 |
| 데이터 소스 | 단일 벡터 저장소 | 벡터 검색과 키워드 검색의 결합 | 벡터·SQL·그래프·웹의 플러그인 연동 |
| 확장성·유지보수 | 낮음, 기능 추가 시 재작성 | 보통, 복잡도가 점차 증가 | 높음, 모듈 단위 추가와 A/B 테스트 |

- 선택 기준 : 데이터 소스가 하나이고 질의 유형이 단순하면 고급 RAG로 충분하고, 소스가 이질적이며 운영 중 기능 교체가 잦으면 모듈러 RAG가 유리함.

## Ⅴ. 모듈러 RAG의 한계와 방안

- 핵심 요약 : 모듈 경유에 따른 지연, 인터페이스 불일치, 원인 분석의 어려움을 조건부 실행, 공통 스키마, 분산 추적으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 종단간 응답 지연 | 검색·융합·리랭킹·검증을 모두 거쳐 대기 시간 누적 | 단순 질의는 정제·검증을 건너뛰는 조건부 패스스루 라우팅, 독립 모듈의 비동기 병렬 실행 | 종단간 응답 시간 |
| 모듈 간 인터페이스 불일치 | 모듈별 입출력 스키마 상이 → 연결 시 런타임 타입 오류 | **Pydantic** 기반 공통 스키마(Document, Query, Context Chunk) 표준화 | 스키마 검증 실패율 |
| 원인 모듈 식별 곤란 | 오답 시 검색, 리랭커, 생성 환각 중 원인 분별이 어려움 | **OpenTelemetry** 기반 분산 추적과 모듈별 단위 평가(**Ragas** 지표 분해) | 모듈별 검색 적중률, 근거성 점수 |

## Ⅵ. 모듈러 RAG에 대한 기술사적 제언

- 핵심 요약 : 그래프 기반 오케스트레이션, 업무별 레시피, 모듈 단위 배포 체계를 갖추어 모듈러 RAG를 일회성 구현이 아닌 운영 표준으로 정착.

1. 오케스트레이션 엔진은 상태 기반 그래프 방식(예: LangGraph)으로 표준화하여 모듈 간 흐름과 순환 피드백을 가시화하고 제어 가능성을 높이는 것이 좋다.
2. 법률 규정 검토, 단순 FAQ, 데이터 분석 등 업무별 검색 구성을 레시피로 자산화하면 같은 모듈을 업무 특성에 맞게 재조합할 수 있다.
3. 검색 엔진이나 리랭커를 교체할 때 특정 모듈만 카나리로 배포하고 회귀 평가를 수행하는 체계를 갖추면 서비스 중단 없이 변경을 검증할 수 있다.

## Ⅶ. 결론

- 핵심 요약 : 모듈러 RAG는 검색 증강 생성을 교체 가능한 부품의 조합으로 설계하는 컴포넌트 기반 방식.
- 시사점 : 질의 적응성과 확장성을 얻는 대신 지연과 운영 복잡도를 관리해야 하므로, 모듈 경계와 관측성을 함께 설계하는 것이 성패를 가른다.
