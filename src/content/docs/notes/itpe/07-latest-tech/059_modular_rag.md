## Ⅰ. 모듈러 RAG(Modular RAG)의 개요

- **개념** : 고정된 선형 파이프라인(검색 ──► 문맥 결합 ──► 답변 생성)으로 동작하는 기존 나이브 및 어드밴스드 RAG의 한계를 극복하고, RAG 시스템의 핵심 기능(검색, 메모리, 라우팅, 융합, 정제, 검증)을 독립적이고 교체 가능한 독립 모듈(Functional Modules)로 분리하여, 사용자의 질의 복잡도와 비즈니스 요구사항에 따라 유연하게 모듈들을 동적으로 재구성하고 조립(Chaining & Orchestration)하는 차세대 컴포넌트 기반 RAG 아키텍처.
- **배경 및 필요성** : 비정형 텍스트뿐만 아니라 정형 DB(SQL), 지식 그래프(Graph), 실시간 웹 검색 등 데이터 소스가 다양해지고, 도메인별로 요구되는 검색 품질과 레이턴시 기준이 상이하여 고정된 단일 파이프라인으로는 대응이 불가능해짐에 따라 소프트웨어 공학적 모듈화가 필연적이 됨.
- **핵심 목적** : RAG 시스템의 유연성 및 확장성 극대화, 모듈별 독립적 교체 및 최적화(플러그앤플레이), 도메인별 최적 검색 레시피(Recipe) 동적 조합.

## Ⅱ. 모듈러 RAG(Modular RAG)의 핵심 아키텍처 및 동작 메커니즘

모듈러 RAG는 6대 핵심 기능 모듈과 이를 사용자 의도에 따라 동적으로 조립하는 오케스트레이션 엔진으로 구성됨.

```text
[ 모듈러 RAG(Modular RAG) 플러그앤플레이 컴포넌트 아키텍처 ]

                  [ 사용자 질의 (User Query) ]
                               │
                               ▼
+-----------------------------------------------------------------+
| 오케스트레이션 및 라우팅 모듈 (Routing & Orchestration Module)   |
|  - 질의 의도 분석 ──► 태스크별 최적 모듈 실행 그래프 동적 생성   |
+------------------------------┬----------------------------------+
                               │ 조립된 모듈 파이프라인 실행
         ┌─────────────────────┼─────────────────────┐
         ▼                     ▼                     ▼
+-----------------+   +-----------------+   +-----------------+
| Search 모듈     |   | Memory 모듈     |   | Fusion 모듈     |
| - Vector DB     |   | - 대화 히스토리 |   | - 하이브리드 병합|
| - Sparse (BM25) |   | - 사용자 프로파일|   | - RRF 순위 융합 |
| - Graph Search  |   | - 장기 메모리   |   | - 다중 쿼리 확장|
+--------┬--------+   +--------┬--------+   +--------┬--------+
         │                     │                     │
         └─────────────────────┼─────────────────────┘
                               ▼
+-----------------------------------------------------------------+
| 정제 및 리랭킹 모듈 (Refinement & Re-rank Module)               |
|  - Cross-Encoder 재순위화, 청크 압축, 문맥 중복 제거            |
+------------------------------┬----------------------------------+
                               │
                               ▼
+-----------------------------------------------------------------+
| 검증 및 비평 모듈 (Verification Module)                         |
|  - 근거성(Groundedness) 자체 검증, 환각 감지 시 검색 모듈로 피드백|
+------------------------------┬----------------------------------+
                               │ 최종 합성
                               ▼
+-----------------------------------------------------------------+
| Generator 모듈 (Generation Engine : LLM / sLM)                 |
|  - 프롬프트 증강 및 출처가 표기된 신뢰성 답변 최종 생성         |
+-----------------------------------------------------------------+
```

- **Search 모듈** : 밀집 벡터 검색(Dense), 키워드 검색(BM25), 지식 그래프 검색(Graph), SQL 검색 등 다양한 검색 기술을 독립 플러그인으로 캡슐화.
- **Memory 모듈** : 이전 대화 턴의 문맥을 요약 보관하거나 사용자의 선호도를 지속 추적하여 검색 질의에 개인화 맥락 부여.
- **Fusion 모듈** : 사용자의 단일 질의를 다각도의 하위 질의로 확장(Query Expansion)한 후 각 검색 결과를 상호 순위 융합(RRF)으로 통합.
- **Refinement 모듈** : 검색된 긴 문서 청크에서 핵심 문장만 요약 압축하거나 Cross-Encoder로 정밀 재정렬하여 LLM 컨텍스트 낭비 제거.
- **Verification 모듈** : 생성된 답변이 검색된 문서에 기반하는지 자가 검증(Self-Correction)하고 실패 시 검색 모듈을 재호출하는 피드백 루프 수행.

## Ⅲ. 모듈러 RAG(Modular RAG)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 나이브 RAG (Naive RAG) | 고급 RAG (Advanced RAG) | 모듈러 RAG (Modular RAG) |
| --- | --- | --- | --- |
| **파이프라인 구조** | 단순 고정 선형 (Linear Pipeline) | 전처리/후처리가 추가된 고정 선형 파이프라인 | 유향 그래프 기반 동적 조립 구조 |
| **구성 요소 결합도** | 모놀리식 강결합 (수정 어려움) | 부분 모듈화 (일부 컴포넌트 교체 가능) | 완전한 마이크로서비스형 독립 결합 (Loose Coupling) |
| **질의 적응성** | 모든 질문에 동일한 검색 절차 수행 | 사전 설정된 규칙에 따라 튜닝 | 질의의 난이도에 따라 필요한 모듈만 동적 선택 |
| **다양한 소스 지원**| 단일 벡터 데이터베이스에 한정 | 벡터 DB + BM25 하이브리드 검색 | 벡터, SQL, 그래프, 웹 검색의 유연한 플러그인 연동 |
| **확장성 및 유지보수**| 낮음 (새 기능 추가 시 전체 재작성) | 보통 (컴포넌트 추가 시 파이프라인 복잡도 증가) | 최고 (신규 모듈 독립 추가 및 A/B 테스트 용이) |

- 모듈러 RAG는 소프트웨어 공학의 '단일 책임 원칙(SRP)'과 '개방-폐쇄 원칙(OCP)'을 생성형 AI 파이프라인에 완벽히 적용한 성숙한 아키텍처임.

## Ⅳ. 모듈러 RAG(Modular RAG)의 주요 한계점 및 해결 방안

- **다수 모듈 경유로 인한 종단간 응답 지연 시간(End-to-End Latency) 증가** :
  - **한계점** : 검색, 융합, 리랭킹, 검증 모듈을 모두 거치면서 사용자 응답 대기 시간이 5~10초 이상 지연.
  - **해결 방안** : 단순 질의는 정제/검증 모듈을 건너뛰는 조건부 패스스루(Pass-through) 라우팅 및 모듈 비동기 병렬화.
- **모듈 간 데이터 인터페이스 불일치 및 오케스트레이션 복잡도 급증** :
  - **한계점** : 모듈마다 입출력 데이터 스키마가 다를 경우 파이프라인 연결 시 잦은 런타임 타입 에러 발생.
  - **해결 방안** : Pydantic 기반의 엄격한 공통 데이터 스키마(Document, Query, Context Chunk) 인터페이스 표준화.
- **시스템 전체 성능 저하 시 원인 모듈 식별(Root-cause Analysis) 난제** :
  - **한계점** : 최종 답변이 잘못되었을 때 검색 모듈의 문제인지, 리랭커의 문제인지, 생성 모델의 환각인지 분별 곤란.
  - **해결 방안** : OpenTelemetry 기반 분산 추적 도입 및 각 모듈별 독립 단위 평가(Ragas 메트릭 분해) 파이프라인 구축.

## Ⅴ. 모듈러 RAG(Modular RAG) 적용 및 발전을 위한 기술사적 제언

- **LangGraph 기반 유향 그래프 오케스트레이션 엔진 표준화** : 모듈 간의 흐름과 순환 피드백을 상태 머신 그래프로 가시화하여 제어 가능성과 유지보수성 극대화.
- **도메인 업무별 '최적 모듈 레시피(RAG Recipe)' 템플릿 자산화** : 법률 규정 검토용(Graph+Re-rank), 콜센터 단순 FAQ용(Cache+Sparse), 데이터 분석용(Text-to-SQL) 레시피 분리 운영.
- **모듈별 독립적 A/B 테스팅 및 무중단 카나리 배포 체계 수립** : 검색 엔진이나 리랭커 모델을 교체할 때 전체 시스템 중단 없이 특정 모듈만 카나리로 배포하여 회귀 평가 수행.
