## 연관 키워드

- 하네스 엔지니어링(Harness Engineering), 가드레일(Guardrails), 샌드박스(Sandbox), 구조화된 출력(Structured Output)
- 제약 디코딩(Constrained Decoding), MCP(Model Context Protocol), 평가 하네스(Evaluation Harness), 관측 가능성(Observability)

## Ⅰ. 하네스 엔지니어링의 개요

- 핵심 요약 : 확률적으로 동작하는 AI 에이전트를 모델 바깥의 제어 계층으로 감싸 검증 가능하고 통제 가능하게 운영하는 엔지니어링 규율.
- 개념 : 거대언어모델(LLM, Large Language Model) 기반 에이전트의 입력 정제, 출력 검증, 도구 호출 중재, 상태 저장, 평가를 모델 외부 계층에서 설계·운영하는 소프트웨어 엔지니어링 규율 (**하네스 엔지니어링** (Harness Engineering)).
- 배경 및 필요성 : 모델 가중치의 정렬(Alignment)만으로는 우회 공격과 오답 위험을 충분히 줄이기 어려워, 사고 한 번의 피해를 막는 외부 통제 계층이 필요해짐.
- 주요 목적 : 비결정론적 출력에 결정론적 통제 지점을 두고, 평가와 검증을 배포 절차에 자동으로 편입.

## Ⅱ. 하네스 엔지니어링의 특징 및 장점

- 핵심 요약 : 모델과 분리된 계층에서 정책을 관리하므로, 모델을 바꾸지 않고도 통제 수준을 빠르게 조정할 수 있는 구조.

1. 모델 독립성 : 정책과 검증 규칙을 소프트웨어로 분리 → 백엔드 모델을 교체해도 하네스를 재사용.
2. 즉각적 정책 갱신 : 규칙 변경이 코드 배포로 끝남 → 재학습 없이 통제 수준을 조정.
3. 다층 검증 : 입력, 출력, 실행, 평가 단계마다 검사 → 한 층이 뚫려도 다음 층에서 차단.
4. 감사 가능성 : 전 과정을 하나의 추적 ID로 기록 → 사고 원인 추적이 쉬워짐.

하네스의 핵심 장치는 다음과 같다.

- **가드레일** (Guardrails) : 모델 추론 앞뒤에서 입력 탈옥 시도와 출력 규정 위반을 검사.
- **샌드박스** (Sandbox) : 생성된 코드와 셸 명령을 호스트와 격리된 환경에서만 실행.
- **구조화된 출력** (Structured Output) : 응답을 정해진 스키마에 맞춰 파싱 가능한 형태로 고정.
- **제약 디코딩** (Constrained Decoding) : 토큰 생성 단계에서 문법과 스키마를 강제하는 디코딩 기법.

## Ⅲ. 하네스 엔지니어링의 구조 (흐름)

- 핵심 요약 : 프롬프트, 가드레일, 실행 샌드박스, 평가 계층이 순차로 연결되고 피드백이 되돌아오는 4층 구조.

```text
[ 하네스 4계층 처리 흐름 ]

사용자 입력
   ↓
프롬프트·문맥 계층 (데이터 격리)
   ↓ 정제된 입력
가드레일 계층 (입출력 검증)
   ↓ 안전성 검증 통과
런타임 실행 계층 (샌드박스)
   ↓ 입출력과 트레이스 전송
평가·관측 계층
```

- 프롬프트 계층 : 원시 입력과 검색(RAG, Retrieval-Augmented Generation) 문맥을 실행 불가능한 데이터 블록으로 감싸 주입.
- 가드레일 계층 : 프롬프트 인젝션과 개인정보를 입력 단계에서 막고, 출력은 스키마와 유해성 기준으로 검사.
- 런타임 계층 : 도구 호출을 **MCP** (Model Context Protocol) 브로커로 중재하고, 서킷 브레이커와 상태 저장 장치로 장애 전파를 억제.
- 평가 계층 : **평가 하네스** (Evaluation Harness)로 배포 전후 회귀를 측정하고, **관측 가능성** (Observability)을 위해 트레이스를 수집.

```text
[ 도구 호출 중재 경로 ]

모델의 도구 호출 요청
   ↓
정책 검사 (허용 목록, 권한)
   ↓ 통과 시에만
격리 실행 (Wasm 또는 일회성 컨테이너)
   ↓
결과를 스키마 검증 후 모델에 반환
```

## Ⅳ. 하네스 엔지니어링과 내부 모델 정렬의 비교

- 핵심 요약 : 내부 정렬은 모델 파라미터를 바꾸고, 외부 하네스는 모델을 감싸는 소프트웨어로 통제하는 점에서 상호 보완적임.
- 내부 정렬의 대표 기법에는 **RLHF** (Reinforcement Learning from Human Feedback), DPO, SFT가 있다.

| 비교 축 | 내부 모델 정렬 | 외부 하네스 엔지니어링 |
| --- | --- | --- |
| 통제 위치 | 모델 파라미터(가중치) | 모델을 감싸는 소프트웨어 계층 |
| 주요 기법 | RLHF, DPO, SFT, 시스템 지침 | 가드레일, 스키마 검증기, 샌드박스, 프록시 |
| 결정론성 | 확률적이며 우회 가능성 잔존 | 규칙은 결정론적으로 실행되나 정책 누락과 구현 결함 잔존 |
| 변경 비용 | 재학습이 필요해 큼 | 규칙 배포로 즉시 변경 |
| 모델 종속성 | 특정 모델에 종속 | 백엔드 모델이 바뀌어도 재사용 가능 |

## Ⅴ. 하네스 엔지니어링의 한계와 방안

- 핵심 요약 : 지연, 출력 형식 불일치, 이기종 에이전트 간 인터페이스 충돌을 병렬화, 문법 강제, 표준 인터페이스로 해소.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 검증 지연 누적 | 입력 검사, 파싱, 출력 필터가 직렬로 실행되어 응답 체감 속도 저하 | 검사 작업 병렬화, 비동기 스트리밍 검증 | 종단간 응답 지연 |
| 출력 형식 불일치 | 마크다운 백틱이 섞인 JSON 등으로 파서 예외 발생 | 제약 디코딩을 적용해 생성 시점에 스키마 준수 강제 | 파싱 실패율 |
| 에이전트 간 인터페이스 충돌 | 프레임워크마다 다른 도구 명세로 통신 단절 | MCP와 OpenAPI 기반 표준 도구 명세로 단일화 | 도구 호출 성공률 |

## Ⅵ. 하네스 엔지니어링에 대한 기술사적 제언

- 핵심 요약 : 평가와 검증을 배포 절차의 관문으로 삼고, 하네스를 일회성 구축물이 아닌 상시 운영 자산으로 정착.

1. 모델이나 프롬프트를 바꾸는 변경은 회귀 평가를 통과해야 배포되도록 CI/CD 게이트에 편입하는 것이 바람직하다.
2. 모델 응답은 Pydantic과 같은 타입 정의로 바인딩해, 자연어 파싱에 기대지 않는 구조로 두는 것이 좋다.
3. 프롬프트 입력부터 가드레일, 도구 호출, 응답까지를 하나의 추적 ID로 묶어 감사에 쓸 수 있도록 관측 체계를 기본으로 갖추는 것이 필요하다.

## Ⅶ. 결론

- 핵심 요약 : 하네스 엔지니어링은 모델 성능 경쟁과 별개로 AI 운영의 통제 가능성을 보장하는 계층.
- 모델이 교체되어도 남는 검증과 통제 자산을 쌓는 조직이 안정적으로 AI 에이전트를 확장할 수 있음.
