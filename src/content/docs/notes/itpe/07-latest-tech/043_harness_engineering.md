## 30초 인출

- 본질: 비결정적인 인공지능 파운데이션 모델을 프로덕션 환경에서 안전하고 신뢰성 있게 구동하기 위해, 모델을 둘러싼 실행 환경·상태 관리·도구 오케스트레이션·가드레일 및 검증 체계를 설계·운영하는 시스템 엔지니어링
- 메커니즘: 요청 인터셉트 및 입력 가드레일 검사 → 컨텍스트 조립 및 상태 주입 → 모델 추론 및 함수/도구 호출(Tool Call) 격리 실행 → 출력 검증 및 안전 필터링 → 감사 로그 및 회귀 평가
- 통찰: 프롬프트 엔지니어링에만 의존한 시스템은 보안 취약점과 실행 불안정성을 해결할 수 없으므로 샌드박스 실행, 최소 권한 원칙(PoLP), 자동화된 회귀 테스트를 아우르는 하네스(Harness) 인프라 구축 필수

<details>
<summary>핵심 용어</summary>

- **하네스 엔지니어링(Harness Engineering)** : AI 모델 자체의 파라미터가 아닌, 모델 입출력 인터페이스, 도구 연동, 메모리 상태, 보안 가드레일을 감싸는 외벽 프레임워크를 설계하는 엔지니어링 기법
- **테스트 하네스(Test Harness)** : 소프트웨어 모듈이 정상 동작하는지 테스트하기 위해 모의 드라이버와 스텁(Stub) 등을 포함하여 구성된 자동화 실행 환경
- **가드레일(Guardrails)** : 모델의 입력(탈옥, 프롬프트 인젝션) 및 출력(유해성, PII 유출)을 정책에 따라 실시간 검증·차단하는 통제 계층
- **샌드박스 격리(Sandboxing)** : LLM이 생성한 코드 실행이나 외부 도구 호출 시 호스트 시스템 보호를 위해 가상화된 격리 컨테이너 환경에서 실행하는 기법
- **회귀 평가(Regression Evaluation)** : 모델 버전 변경이나 프롬프트 수정 시 기존 기능과 안전 기준이 깨지지 않았는지 점검하는 지속적 테스트 체계
</details>

## 2~4교시 예상문제 (25점)

## 2~4교시 25점 답안

## Ⅰ. AI 모델의 런타임 안전망, 하네스 엔지니어링의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 비결정적인 거대 언어 모델(LLM)을 엔터프라이즈 환경에서 안정적으로 동작시키기 위해, **모델 주변의 입력 제어, 도구 실행, 상태 보존, 출력 검증 및 관측 체계를 총체적으로 설계하는 시스템 공학** |
| 목적 | 프롬프트 인젝션 방어, 외부 시스템 안전 연동, 모델 비결정성 제어, 장애 격리 및 지속적 회귀 평가 보장 |

- 자동차나 우주선의 '배선 하네스(Wiring Harness)'나 낙하산의 안전벨트처럼, 불확실성을 가진 AI 모델 코어에 안전성과 통제력을 부여하는 소프트웨어 외벽 구조.

## Ⅱ. 하네스 엔지니어링의 대두 배경 및 주요 특징

### (1) 대두 배경: '프롬프트 만능주의'의 한계 극복

```text
[ 프롬프트 중심 접근의 한계 ]                 [ 하네스 엔지니어링 패러다임 ]
- "탈옥하지 마라" 프롬프트 작성           - 하네스 가드레일에서 인젝션 사전 차단
- "정확한 JSON만 출력하라" 요청          - 스키마 검증기(Parser)로 유효성 강제
- 모델이 DB 직접 삭제 등 오동작           - 격리된 샌드박스 및 권한 통제(IAM) 강제
- 모델 업데이트 시 시스템 회귀 발생        - CI/CD 파이프라인 내 자동 회귀 테스트
```

### (2) 하네스 엔지니어링의 주요 특징

| 특징 | 설명 | 세부 구현 요소 |
|---|---|---|
| **결정론적 래퍼(Deterministic Wrapper)** | 비결정적 LLM 출력을 정형화된 시스템 계약(Contract)으로 변환 | Pydantic 스키마 파서, 정규식 검증기 |
| **도구 샌드박싱(Tool Sandboxing)** | API 호출, SQL 실행, Bash 코드 실행을 안전한 가상 컨테이너에 격리 | gVisor, Firecracker 마이크로VM, Docker |
| **컨텍스트 격리(Context Boundary)** | 시스템 프롬프트, 도구 출력, 사용자 입력을 명확히 구분하여 오염 방지 | Semantic Cache, Context Window Allocator |
| **자동 회귀 가드(Regression Guard)** | 프롬프트나 기반 모델 업그레이드 시 서비스 품질 붕괴를 실시간 탐지 | LLM-as-a-Judge, Golden Test Dataset |

## Ⅲ. 하네스 엔지니어링 아키텍처 및 실행 파이프라인

### (2) 하네스 4대 핵심 구성요소 및 역할

| 구성요소 | 핵심 기능 | 구현 기술 및 도구 |
|---|---|---|
| **입력 가드레일 (Ingress)** | 악의적 프롬프트 인젝션 차단, 개인정보(PII) 난독화 | NeMo Guardrails, Presidio, Llama Guard |
| **상태 및 문맥 관리자** | 세션 상태 유지, 프롬프트 주입 방지, 히스토리 트리밍 | Redis Session Store, LangGraph StateGraph |
| **도구 샌드박스 (Execution)** | 위험 명령 필터링, 안전한 코드 및 SQL 실행 환경 격리 | Firecracker microVM, WASM Runtime, eBPF |
| **출력 검증 및 폴백 (Egress)** | 구조적 데이터 스키마 준수 강제, 환각 탐지 시 폴백 | Instructor, Outlines, JsonSchema, 서킷 브레이커 |

## Ⅳ. 프롬프트 엔지니어링 vs 하네스 엔지니어링 비교

### (1) 프롬프트 엔지니어링 vs 하네스 엔지니어링 다각적 비교

| 비교 항목 | 프롬프트 엔지니어링 (Prompt Engineering) | 하네스 엔지니어링 (Harness Engineering) |
|---|---|---|
| **초점 영역** | 모델에게 전달하는 지시문(텍스트) 최적화 | 모델을 둘러싼 실행 인프라, 도구, 상태 통제 |
| **주요 작업** | Few-shot 구성, CoT 유도, 역할 부여(Role) | 가드레일 구축, 샌드박싱, 스키마 검증, 회귀 테스트 |
| **결정론 수준** | 비결정론적 (확률적 생성에 전적으로 의존) | 결정론적 보장 (스키마 위반 시 재시도 또는 거절) |
| **보안 대응력** | 약함 (새로운 프롬프트 인젝션에 취약) | 강함 (네트워크 격리, 권한 통제, 정책 엔진 강제) |
| **테스트 방식** | 정성적 주관 평가, 임의 프롬프트 질의 | 정량적 회귀 평가셋(CI/CD), 벤치마크 자동화 |
| **엔지니어링 성격**| 프롬프트 작성 및 튜닝 (텍스트 기법) | 분산 시스템 아키텍처 및 소프트웨어 공학 |

### (2) AI 시스템 엔지니어링 계층 스택

```text
+-------------------------------------------------------------------+
| Business Logic / Application Interface                           |
+-------------------------------------------------------------------+
| [Harness Layer]  In/Out Guardrails, Tool Sandbox, Schema Parser   |
+-------------------------------------------------------------------+
| [Prompt Layer]   System Prompt, Few-shot Examples, Context Prompt |
+-------------------------------------------------------------------+
| [Model Layer]    Foundation Model (Weights, Architecture)         |
+-------------------------------------------------------------------+
| [Hardware Layer] GPU Cluster, High-Speed Interconnect, Storage     |
+-------------------------------------------------------------------+
```

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| **복잡한 래퍼로 인한 지연 시간(Latency) 증가**<br />- 가드레일 및 스키마 검증기 추가로 요청당 수백 밀리초 오버헤드 | **비동기 가드레일 및 경량 분류기 병렬화**<br />- 소형 SLM 기반 분류기 활용 및 입출력 검증 로직의 스트리밍 병렬 파이프라인 처리 |
| **외부 도구 연동 시 권한 오남용 위험**<br />- 모델의 잘못된 Tool Call로 인한 사내 DB 삭제 등 파괴적 행위 | **최소 권한 원칙(PoLP) 및 Human-in-the-Loop 적용**<br />- 쓰기·삭제 등 위험도가 높은 도구 호출 시 관리자 명시적 승인 게이트웨이 강제 |
| **하네스 자체의 구성 복잡도 및 유지보수 부담**<br />- 다양한 외부 API, 샌드박스, 모니터링 연동으로 아키텍처 비대화 | **표준 에이전트 인터페이스(MCP 등) 도입**<br />- Model Context Protocol(MCP) 등 표준 도구 호출 규격을 도입하여 모듈식 하네스 구현 |
| **모델 변경 시 하네스 로직 오작동**<br />- 기반 모델 교체 시 이전 도구 호출 형식 파싱 실패 | **합의 기반 자동 회귀 평가 파이프라인 구축**<br />- CI/CD 빌드 단계에서 1,000개 이상의 골든 테스트셋을 통과해야 배포 승인 |

## Ⅵ. 제언

생성형 AI의 성패는 모델 자체의 파라미터 성능보다 모델을 안전하게 통제하는 하네스 엔지니어링의 완성도에 달려 있으므로, 프로덕션 단계에서는 프롬프트 수정에 매달리기보다 견고한 하네스 인프라와 관측성(Observability) 체계 구축 필수.

```text
[엔터프라이즈 AI 신뢰성 확보 3대 핵심 체계]

        +-----------------------------------------------+
        |        Enterprise AI Production Harness       |
        +-----------------------------------------------+
                                |
        +-----------------------+-----------------------+
        |                       |                       |
        v                       v                       v
[ Ingress / Egress ]    [ Isolated Execution ]  [ Automated CI/CD ]
- 가드레일 정책 강제    - 마이크로 샌드박스     - 골든셋 회귀 테스트
- 스키마 파서 검증      - 최소 권한 IAM 통제    - 실시간 드리프트 감지
```

| 운영 통제 영역 | 세부 실천 방안 | 달성 지표 |
|---|---|---|
| **보안 및 규정 준수** | 샌드박스 컨테이너 격리 및 PII 자동 마스킹 | 외부 시스템 오동작 피해 및 데이터 유출 0건 |
| **서비스 품질 안정성**| 자동 재시도(Retry) 및 서킷 브레이커 구현 | 모델 응답 비정형 오류율 0.01% 이하 통제 |
