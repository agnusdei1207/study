## 연관 키워드

- LLM 도입 아키텍처, 엔터프라이즈 AI, 퍼블릭 LLM API, 프라이빗 RAG, 도메인 sLM 파인튜닝
- 시맨틱 캐시, 모델 라우터, PII 마스킹, FinOps, 벤더 종속(Vendor Lock-in), RBAC

## Ⅰ. LLM 도입 아키텍처·고려사항의 개요

- 핵심 요약 : 기밀성, 비용, 지연, 성능의 트레이드오프를 조율해 퍼블릭 API와 사내 모델을 배치하는 엔터프라이즈 AI 설계.
- 개념 : 기업이 **거대언어모델** (LLM, Large Language Model)을 업무와 고객 서비스에 도입할 때, 데이터 기밀성, **총소유비용** (TCO, Total Cost of Ownership), 응답 지연, 모델 성능을 함께 분석해 퍼블릭 API, 사내 sLM (small Language Model, 소형 언어 모델), **RAG** (Retrieval-Augmented Generation, 검색 증강 생성), 파인튜닝을 조합하는 아키텍처.
- 배경 및 필요성 : 민감한 사내 정보를 외부 API에 무분별하게 보내면 기밀 유출, 토큰 비용 누적, 특정 공급자 종속 문제가 생기므로, 보안과 비용을 함께 설계하는 공학적 접근이 필요함.
- 주요 목적 : 보안 규제 준수, 운영 비용의 지속 관리, 신뢰할 수 있는 답변 확보, 기존 엔터프라이즈 시스템과의 통합.

## Ⅱ. LLM 도입 아키텍처·고려사항의 특징 및 장점

- 핵심 요약 : 게이트웨이, 캐시, 라우터, 관측 계층을 분리해 비용과 보안을 동시에 통제하는 계층형 구조.

1. 보안 게이트웨이 : 입력 단계에서 **PII** (Personally Identifiable Information, 개인식별정보)를 마스킹하고 권한을 검증 → 기밀 정보가 외부 모델로 나가는 경로 차단.
2. **시맨틱 캐싱** (Semantic Caching, 의미가 유사한 질의의 기존 응답을 재사용하는 기법) : 임베딩 유사도가 임계치를 넘으면 모델 호출 없이 응답 반환 → 호출 비용과 지연 감소.
3. **모델 라우터** (Model Router, 질의 복잡도에 따라 모델을 배정하는 계층) : 단순 업무는 사내 sLM, 복합 추론은 상용 모델로 분기 → 비용 대비 성능 최적화.
4. 관측성 (Observability) : 부서별 토큰 사용량과 TTFT (Time to First Token, 첫 토큰 생성까지의 시간)를 계측 → 비용 통제의 근거 확보.

```text
[ 엔터프라이즈 LLM 처리 흐름 ]

사용자 질의 (업무 시스템 연동)
          ↓
[1] 보안 게이트웨이
    PII 마스킹, 권한 검증
          ↓
[2] 시맨틱 캐시 (유사 질의 즉시 응답)
          ↓
[3] 모델 라우터 (질의 복잡도 분류)
     ↓ 단순 업무        ↓ 복합 추론
  사내 sLM        RAG·에이전트 → 파운데이션 모델
```

## Ⅲ. LLM 도입 아키텍처·고려사항의 구조 (흐름)

- 핵심 요약 : 데이터 민감도와 근거 요구가 높아질수록 공개 API에서 사내 모델 쪽으로 도입 패턴이 이동.

```text
[ 도입 패턴 이동 방향 ]

퍼블릭 LLM API (공개 데이터)
          ↓ 사내 근거 문서 필요
프라이빗 RAG (검색 증강)
          ↓ 도메인 용어·저지연 필요
도메인 sLM 파인튜닝
```

## Ⅳ. LLM 도입 아키텍처·고려사항의 비교

- 핵심 요약 : 공개 API는 성능과 편의, 사내 구축은 통제와 격리를 얻는 대신 비용과 운영 부담을 떠안는 구도.

| 도입 패턴 | 구현 방식 | 장점 | 단점·리스크 | 적합 업무 |
| --- | --- | --- | --- | --- |
| 퍼블릭 LLM API | 클라우드 API 직접 호출 | 최상위 성능 즉시 활용, 인프라 부담 없음 | 데이터 유출 우려, 토큰 비용 누적, 외부 SLA (Service Level Agreement) 종속 | 공개 자료 분석, 문구 초안 작성 |
| 프라이빗 RAG | 사내 벡터 DB와 LLM 결합 | 최신 사내 지식 반영, 출처 제공 | 검색 파이프라인 튜닝, 데이터 동기화 부담 | 업무 매뉴얼 질의응답, 규정 검토 |
| 도메인 sLM 파인튜닝 | 오픈소스 모델에 경량 미세조정 적용 | 데이터 사내 격리, 도메인 용어 학습, 낮은 지연 | 초기 GPU 학습 비용, 모델 갱신 주기 관리 | 사내 코드 생성, 계약서 분석 |
| 사전 학습 (Scratch) | 대규모 데이터로 파운데이션 모델 직접 구축 | 기술 자립, 독자적 지식재산 확보 | 막대한 GPU 투자, 높은 실패 위험 | 국가 단위 AI, 초대형 플랫폼 |

- 엔터프라이즈 환경에서는 대다수 과제가 프라이빗 RAG와 도메인 sLM의 조합으로 수렴하는 추세임.

## Ⅴ. LLM 도입 아키텍처·고려사항의 한계와 방안

- 핵심 요약 : 연산 비용, 벤더 종속, 권한 불일치를 캐시, 추상화 계층, 권한 메타데이터로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 동시 사용 증가에 따른 비용·지연 증가 | 임직원 실시간 사용으로 호출량과 토큰 수 급증 | 시맨틱 캐시 전면 배치, 프롬프트 압축, 온프레미스 인스턴스 오토스케일링 | TTFT, 호출당 비용 |
| **벤더 종속** (Vendor Lock-in) | 특정 API 파라미터에 코드가 강결합되어 정책 변경 시 서비스 중단 위험 | LiteLLM 등 통합 인터페이스 계층을 두어 모델 교체 지원 | 모델 교체 소요 시간 |
| RAG와 사내 권한 체계의 불일치 | 비인가 직원이 대외비 문서를 우회 조회할 위험 | 벡터 DB 메타데이터에 **RBAC** (Role-Based Access Control, 역할 기반 접근 제어) 태그를 바인딩하여 권한 있는 청크만 검색 | 비인가 검색 차단 건수 |

## Ⅵ. LLM 도입 아키텍처·고려사항에 대한 기술사적 제언

- 핵심 요약 : 평가 체계, 토큰 쿼터, 단계적 에이전트 전환을 상위 방향으로 제시.

1. 골든 데이터셋 기반 평가 체계 : 주관적 품질 판단에서 벗어나, 도메인별 정답 데이터셋과 LLM-as-a-Judge 평가로 정확도를 정량 측정하는 체계를 먼저 마련함.
2. 부서별 토큰 쿼터와 비용 관리 : 클라우드 FinOps 체계와 연계해 부서 단위 사용 한도를 두고, 업무 효율 대비 ROI (Return on Investment, 투자 수익률)를 주기적으로 재검증하는 방식으로 운영함.
3. 단계적 에이전트 전환 로드맵 : 질의응답 챗봇으로 시작해 검증된 범위에서 사내 도구 실행 권한을 점진적으로 넓히고, 고위험 실행에는 사람의 승인을 거치도록 설계함.

## Ⅶ. 결론

- 핵심 요약 : 엔터프라이즈 LLM은 모델 성능보다 보안 게이트웨이와 비용 통제를 포함한 계층 설계로 완성되는 시스템.
- 시사점 : 퍼블릭 API와 사내 모델의 역할 분담이 명확할수록 기밀성과 비용을 함께 지킬 수 있음.
