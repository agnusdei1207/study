## 30초 인출

- 본질: **멀티에이전트 시스템(Multi-Agent System, MAS)** 은 특정 도메인에 특화된 다수의 자율 에이전트들이 상호 통신과 역할 분담을 통해 단일 에이전트의 한계를 초월하여 복잡한 대규모 문제를 협력적으로 해결하는 분산 인공지능 아키텍처
- 메커니즘: 중앙 오케스트레이터 또는 P2P 메시징을 통해 전체 목표를 서브 태스크로 분해(Decomposition)하고, 기획자·실행자·검증자(Critic) 에이전트 간 반복 피드백 루프를 거쳐 최종 결과물 통합
- 통찰: 에이전트 간 역할 충돌과 오류 전파로 인한 무한 루프 위험이 존재하므로 명확한 그래프 기반 워크플로우(LangGraph) 정의 및 독립 검증자(Evaluator) 게이트웨이 배치 필수

<details><summary>핵심 용어</summary>

- **멀티에이전트 시스템 (MAS)** : 고유한 목표, 지식, 도구를 가진 독립적 소프트웨어 에이전트들이 협력하여 문제를 해결하는 분산 인공지능 환경.
- **작업 분해 (Task Decomposition)** : 사용자 복합 명령을 독립적 혹은 의존적 하위 작업들로 쪼개어 최적의 전문 에이전트에 분배하는 기법.
- **오케스트레이터 (Orchestrator)** : 에이전트 간의 작업 흐름, 상태 전이, 메시지 라우팅, 종료 조건을 총괄 통제하는 관리자 컴포넌트.
- **크리틱 에이전트 (Critic Agent)** : 작업 수행 에이전트가 도출한 산출물의 논리적 오류, 코드 버그, 사실 여부를 독립적으로 교차 검증하고 수정을 요구하는 비평가.
- **공유 메모리 (Shared Memory)** : 다중 에이전트가 협업 과정에서 중간 산출물과 전체 컨텍스트를 일관되게 참조하고 갱신하는 공통 작업 공간 (블랙보드 아키텍처).

</details>

## 2~4교시 25점 답안

## Ⅰ. 멀티에이전트 시스템(MAS)의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **멀티에이전트 시스템(Multi-Agent System, MAS)** 은 자율적으로 판단하고 행동하는 다수의 소프트웨어 에이전트들이 통신 프로토콜과 공유 메모리를 통해 상호작용하며 복잡한 공동의 목표를 분업과 협업으로 달성하는 분산 인공지능 소프트웨어 체계 |
| 목적 | 단일 거대 모델의 컨텍스트 윈도우 한계 극복, 환각 전파 방지, 전문 도메인별 최적화된 도구 활용 및 인간 조직과 유사한 고도화된 자율 업무 자동화 구현 |

## Ⅱ. 멀티에이전트 시스템의 핵심 특징 및 협업 패러다임 속성

| 구분 | 핵심 특징 | 세부 공학적 메커니즘 및 속성 |
|---|---|---|
| **역할 분업화 (Specialization)** | 도메인별 전문 에이전트 구성 | 기획(Planner), 개발(Coder), 검색(Researcher), 검증(Reviewer)으로 역할을 분리하여 프롬프트 복잡도 최소화 |
| **상호작용 자율성 (Autonomy)** | 상황 인지 기반 능동 행동 | 사전에 고정된 파이프라인이 아닌, 이전 에이전트의 작업 결과에 따라 후속 에이전트가 자율적으로 도구 선택 |
| **반영적 교차 검증 (Self-Correction)** | Generator-Critic 루프 | 실행 에이전트의 초안을 검증자 에이전트가 비판적으로 평가하여 기준 미달 시 자동 재작업 지시 |
| **확장성 및 복원력 (Resilience)** | 모듈형 에이전트 교체 | 특정 에이전트 장애 시 대체 에이전트 투입 가능, 신규 전문 에이전트를 시스템 중단 없이 유연하게 플러그인 |

## Ⅲ. MAS 오케스트레이션 아키텍처 및 단계별 협업 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [ 멀티에이전트 시스템 계층형 협업 아키텍처 ]             │
└────────────────────────────────────────────────────────────────────────┘
                                    │
 [ 사용자 복합 목표 입력 (Goal) ] ──► [ 슈퍼바이저 / 오케스트레이터 (Supervisor) ]
                                    │ - 작업 분해 (Decomposition)
                                    │ - 상태 그래프 (StateGraph) 관리
                                    │
 ┌──────────────────────────────────┴──────────────────────────────────┐
 │                                                                     │
 ▼                                                                     ▼
[ 리서치 에이전트 (Researcher) ]                              [ 코딩 에이전트 (Developer) ]
 - 외부 웹/RAG 지식 검색 수행                                  - 코드 작성 및 환경 빌드 실행
 - 핵심 사실 데이터 수집 및 요약                                - 단위 테스트 코드 자율 실행
 └──────────────────────────────────┬──────────────────────────────────┘
                                    │
                                    ▼ (중간 산출물 인계)
┌────────────────────────────────────────────────────────────────────────┐
│ [ 검증 및 비평 에이전트 (Critic / Evaluator) ]                          │
│  - 코드 품질 린팅, 사실성 팩트체크, 보안 취약점 스캔                   │
│  ├── (불합격 판정 시) ──> 구체적 결함 피드백과 함께 이전 에이전트에 반려│
│  └── (합격 판정 시)   ──> 최종 통합 리포트 생성 및 사용자 승인 요청     │
└────────────────────────────────────────────────────────────────────────┘
```

| 협업 단계 | 주관 컴포넌트 | 핵심 공학 활동 |
|---|---|---|
| **1. 목표 분해** | Supervisor Agent | 사용자 자연어 지시를 Directed Acyclic Graph(DAG) 기반 하위 태스크로 변환 |
| **2. 병렬/순차 실행** | Worker Agents | 역할별 전용 프롬프트와 API 도구를 사용하여 중간 결과(Artifact) 생성 |
| **3. 공유 상태 동기화** | Shared State Machine | Redis/SQLite 기반 상태 저장소에 각 에이전트의 관찰 로그 및 상태 동기화 |
| **4. 피드백 및 검증** | Critic Agent | 품질 임계치(Threshold) 미달 시 재실행 트리거 및 최종 산출물 무결성 승인 |

## Ⅳ. 단일 에이전트 vs 멀티에이전트 시스템(MAS) 비교

| 비교 항목 | 단일 에이전트 (Single Agent) | 멀티에이전트 시스템 (Multi-Agent System) |
|---|---|---|
| **프롬프트 구조** | 수십 개 도구와 역할을 단일 프롬프트에 집중 | 역할별로 분리된 수백 자 내외의 간결한 전용 프롬프트 |
| **컨텍스트 효율** | 대화 및 추론이 길어질수록 환각 및 문맥 망각 | 서브태스크별 컨텍스트 분리로 토큰 절감 및 높은 집중도 |
| **복잡 문제 해결** | 3~4단계 이상 복합 작업 시 높은 실패율 | 10단계 이상의 장기 실행(Long-horizon) 과업 완수 가능 |
| **디버깅 가시성** | 어디서 논리적 오류가 발생했는지 추적 난망 | 에이전트 간 전달된 입출력 메시지 로그로 즉각 오류 식별 |
| **구축 복잡도** | 단순하며 구현 빠름 | 오케스트레이션, 통신 프로토콜, 동기화 설계 필요 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 에이전트 간 비판과 재작업 요구가 영구 반복되어 작업이 종료되지 않는 데드락(Deadlock) 및 토큰 낭비 | 최대 반복 루프 횟수(Max Iteration=3)를 하드코딩하고 진행률 정체 시 강제 사용자 개입(HITL) 루틴 전환 |
| 한 에이전트의 잘못된 환각 출력이 후속 에이전트의 입력으로 주입되어 전체 결과가 오염되는 오류 전파 | 에이전트 간 인계 지점마다 Pydantic 기반 구조화된 스키마 유효성 검사 및 독립된 사실성 평가기(Fact-checker) 강제 |

## Ⅵ. 제언

에이전트 간 무질서한 메시징을 방지하기 위해 유한 상태 기계(FSM) 기반의 방향성 비순환 그래프(DAG) 워크플로우를 채택하고, LangGraph 기반의 상태 관리 아키텍처 구축.

```text
[ 복합 프로젝트 요청 ] ──> [ Planner: 계획 수립 ]
                                  │
                                  ▼
                         [ Researcher: 자료 조사 ]
                                  │
                                  ▼
                         [ Coder: 소프트웨어 구현 ]
                                  │
                                  ▼
                         [ Critic: 자동 단위 테스트 ]
                           ├── (테스트 실패) ──> [ Coder로 피드백 전달 및 버그 수정 ]
                           └── (테스트 통과) ──> [ 최종 배포 및 프로젝트 완료 ]
```

| 구분 | 무정형 P2P 에이전트 대화 | 제언: LangGraph 기반 상태 머신 워크플로우 |
|---|---|---|
| **흐름 제어** | 에이전트가 임의로 대화하여 경로 예측 불가 | 사전 정의된 조건부 엣지(Conditional Edge)로 명확한 경로 제어 |
| **상태 관리** | 대화 히스토리가 길어져 컨텍스트 폭증 | 중앙 State 객체에 필수 데이터만 누적하여 메모리 최적화 |
| **재현성** | 실행할 때마다 결과와 실행 순서가 판이함 | 결정론적 워크플로우를 유지하면서 내부 추론만 자율성 부여 |
