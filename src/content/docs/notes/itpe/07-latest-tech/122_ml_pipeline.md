## 30초 인출

- 본질: **머신러닝 파이프라인 (Machine Learning Pipeline)** 은 데이터 수집, 검증, 전처리, 모델 학습, 평가, 배포 및 모니터링에 이르는 머신러닝 전주기 워크플로우를 방향성 비순환 그래프(DAG) 기반으로 표준화하고 자동화하는 MLOps 인프라 체계
- 메커니즘: 피처 스토어(Feature Store) 및 데이터 버전 관리(DVC) → 분산 모델 학습 및 하이퍼파라미터 튜닝 → 모델 레지스트리(Model Registry) 등록 및 카나리 배포 → 실시간 드리프트 감지 시 재학습(CT) 자동 트리거
- 통찰: 단순 코드 자동화만으로는 훈련-서빙 불일치(Skew)와 데이터 드리프트로 인한 성능 저하를 방어할 수 없으므로 피처 계보(Lineage) 추적과 통계적 드리프트 감시 기반 무중단 롤백 파이프라인 구축 필수

<details><summary>핵심 용어</summary>

- **머신러닝 파이프라인** : 머신러닝 모델의 라이프사이클 전체를 코드화하여 재현성(Reproducibility)과 운영 자동화를 보장하는 오케스트레이션 파이프라인.
- **MLOps (Machine Learning Operations)** : 머신러닝 모델의 신속한 개발과 안정적인 배포 및 지속적 운영을 지원하는 문화이자 기술 스택.
- **지속적 학습 (CT, Continuous Training)** : 프로덕션 환경의 데이터 분포 변화나 모델 성능 저하 감지 시 파이프라인이 스스로 모델을 재학습하는 MLOps 고유 개념.
- **데이터 드리프트 (Data Drift)** : 운영 시점에 입력되는 피처의 통계적 분포가 훈련 데이터의 분포와 달라져 모델 정확도가 급락하는 현상.
- **훈련-서빙 스큐 (Training-Serving Skew)** : 학습 단계의 데이터 전처리 로직과 실시간 서빙 단계의 전처리 로직 간 불일치로 인해 발생하는 치명적 예측 오류.

</details>

## 2~4교시 25점 답안

## Ⅰ. 머신러닝 파이프라인의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **머신러닝 파이프라인** 은 원천 데이터의 수집·가공부터 모델 학습, 검증, 배포 및 사후 모니터링까지의 전주기 단계를 모듈화하여 방향성 비순환 그래프(DAG)로 연결하고 자동화하는 MLOps 실행 체계 |
| 목적 | 데이터 과학자의 수작업 반복 실험 병목 해소, 실험 재현성(Reproducibility) 확보 및 지속적 통합·배포·학습(CI/CD/CT) 달성 |

## Ⅱ. 머신러닝 파이프라인의 핵심 구성 단계 및 특징

| 파이프라인 단계 | 주요 역할 및 세부 태스크 | 대표 도구 및 산출물 |
|---|---|---|
| **데이터 수집 및 검증** | 스키마 일치성, 결측치, 이상치 검증(Data Validation) | Great Expectations, TFDV |
| **피처 엔지니어링** | 정규화, 인코딩, 피처 스토어 등록 (온라인/오프라인 동기화) | Feast, Hopsworks |
| **분산 모델 학습** | GPU 분산 클러스터 기반 하이퍼파라미터 최적화(HPO) | Kubeflow, Ray, Optuna |
| **모델 검증 및 등록** | 챔피언-챌린저 모델 성능 검증 및 모델 레지스트리 패키징 | MLflow, WandB, Triton |
| **지속적 배포 (CD)** | 블루/그린, 카나리(Canary), 섀도우(Shadow) 무중단 배포 | Seldon Core, KServe, Argo |
| **모니터링 및 CT** | 데이터/개념 드리프트 감지 및 파이프라인 자동 재학습 | Evidently AI, Prometheus |

## Ⅲ. MLOps 수명주기 및 지속적 학습(CT) 자동화 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│             MLOps 엔드투엔드 파이프라인 및 지속적 학습(CT) 루프         │
└────────────────────────────────────────────────────────────────────────┘
 [ 1단계: Data Engineering ] ──> DVC / Feast 피처 스토어 저장
             │
             ▼
 [ 2단계: Model CI (Continuous Integration) ]
  - 소스코드 빌드, 단위 테스트, 데이터 검증 테스트
             │
             ▼
 [ 3단계: Automated Training & HPO Pipeline (DAG) ]
  - Kubeflow / Argo 기반 분산 GPU 클러스터 학습 수행
             │
             ▼
 [ 4단계: Model Evaluation & Governance ]
  - 임계 성능 검증 ──> [ 통과 시 MLflow Model Registry 승인 ]
             │
             ▼
 [ 5단계: Model CD (Continuous Delivery) ]
  - KServe 기반 카나리(Canary 10% ──> 100%) 점진적 서빙 배포
             │
             ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ [ 6단계: Model Monitoring & Continuous Training (CT) 루프 ]          │
 │                                                                      │
 │  [ 프로덕션 추론 로그 수집 ] ──> [ 실시간 통계 드리프트 분석 ]         │
 │                                        │                             │
 │            ┌───────────────────────────┴───────────────────────────┐ │
 │            ▼ (KS-Test: p < 0.05 / Accuracy Drop 감지)              │ │
 │  [ 데이터/개념 드리프트 경보 발생! ]                                 │ │
 │            │                                                       │ │
 │            ▼ 자동 재학습 파이프라인 트리거 (Trigger CT DAG)        │ │
 │  [ 신규 유입 데이터셋 결합 ──> 1단계 학습 파이프라인 자동 재가동 ]   │ │
 └──────────────────────────────────────────────────────────────────────┘
```

| MLOps 성숙도 수준 | 운영 방식 및 특징 | 자동화 범위 |
|---|---|---|
| **Level 0 (수동 프로세스)** | 주피터 노트북 스크립트 기반 수작업 학습 및 파일 전달 | 100% 수동, 배포 주기 수개월 |
| **Level 1 (ML 파이프라인)** | 새로운 데이터 유입 시 파이프라인이 자동 실행되는 CT 구현 | 모델 훈련 및 검증 자동화 |
| **Level 2 (완전 CI/CD/CT)** | 파이프라인 자체의 코드 변경까지 CI/CD로 배포되는 성숙 단계 | 수 분 이내 일일 다회 무중단 배포 |

## Ⅳ. 소프트웨어 CI/CD vs 머신러닝 CI/CD/CT 비교

| 비교 항목 | 전통적 소프트웨어 CI/CD | 머신러닝 CI/CD/CT (본 토픽) |
|---|---|---|
| **변경 관리 대상** | 오직 소스코드(Code) | 코드(Code) + 데이터(Data) + 모델 파라미터(Model) |
| **테스트 범위** | 단위 테스트, 통합 테스트 | 데이터 스키마 검증, 알고리즘 성능(AUPRC), 편향성 테스트 |
| **배포 산출물** | 실행 가능한 바이너리 / 컨테이너 이미지 | 모델 가중치 바이너리 + 전처리 파이프라인 + 서빙 런타임 |
| **품질 저하 원인** | 소프트웨어 버그, 서버 인프라 장애 | 환경 변화에 따른 데이터 드리프트(Data Drift) 발생 |
| **고유 운영 요소** | 지속적 통합 및 배포 (CI/CD) | 지속적 학습(CT) 및 피처 스토어 거버넌스 필수 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 학습 시점의 피처 추출 로직(Python Pandas)과 서빙 시점의 로직(C++/Java) 차이로 인한 훈련-서빙 스큐(Skew) 발생 | 온/오프라인 피처 저장소를 일원화하여 단일 소스 오브 트루스(SSOT)를 제공하는 중앙 피처 스토어(Feast) 강제화 |
| 시장 트렌드나 외부 환경 변화로 인해 데이터의 통계적 분포가 서서히 변하는 데이터 드리프트(Data Drift) 발생 | Kolmogorov-Smirnov(KS) 검정 및 PSI(Population Stability Index) 지표를 상시 모니터링하여 임계치 초과 시 알림 및 재학습 연계 |
| 재학습된 챌린저 모델이 예기치 못한 특정 세그먼트에서 성능이 폭락하여 전면 배포 시 비즈니스 장애 유발 | 트래픽의 10%만 신규 모델로 라우팅하는 카나리(Canary) 배포와 이상 감지 시 이전 모델로 1초 만에 롤백하는 서킷 브레이커 구축 |

## Ⅵ. 제언

데이터 과학자의 실험 코드와 프로덕션 운영 인프라의 간극을 해소하기 위해 쿠버네티스(Kubernetes) 기반 클라우드 네이티브 MLOps 표준 아키텍처 구축 권고.

```text
[ 데이터 엔지니어 / 데이터 과학자 ]
                 │ Git Commit & DVC Push
                 ▼
┌────────────────────────────────────────────────────────┐
│ MLOps 클라우드 네이티브 오케스트레이션 (Kubeflow)       │
│                                                        │
│  [ Step 1: 데이터 스키마 자동 검증 (Great Expectations)]│
│  [ Step 2: 분산 GPU 학습 & HPO (Ray on K8s) ]          │
│  [ Step 3: MLflow 모델 레지스트리 자동 스테이징 ]       │
│  [ Step 4: KServe 카나리 무중단 서빙 배포 ]            │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│ 지속적 감시 및 자동 CT 엔진 (Prometheus + Evidently)   │
│  - 실시간 PSI > 0.2 감지 시 Kubeflow 재학습 자동 호출  │
└────────────────────────────────────────────────────────┘
```

| 구분 | 레거시 노트북 기반 운영 | 제언: Kubeflow + MLflow 클라우드 파이프라인 |
|---|---|---|
| **실험 재현성** | 로컬 환경 차이로 재현 불가 | 컨테이너 이미지 및 DVC 해시로 100% 재현 |
| **배포 주기** | 모델당 수주일 소요 | 1클릭 파이프라인으로 당일 배포 완결 |
| **장애 대응** | 장애 발생 후 사후 수습 | 드리프트 조기 감지 및 1초 롤백 |
| **자원 효율성** | 온프레미스 GPU 유휴 낭비 | K8s 기반 오토스케일링(HPA)으로 비용 최적화 |
