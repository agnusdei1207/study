## 30초 인출

- 본질: **파일 vs DB vs 블록체인 저장** 은 데이터의 용량, 트랜잭션 빈도, 변경 가능성(CRUD), 신뢰 검증 요구에 따라 비정형 대용량 파일은 객체 스토리지, 고속 인덱싱·갱신 업무는 DBMS, 위변조 방지 감사 이력은 블록체인 온체인에 분계 배치하는 스토리지 티어링 기술
- 메커니즘: 원본 데이터는 오프체인 파일/오브젝트에 저장 → 검색 및 트랜잭션 상태는 관계형/NoSQL DB 관리 → 데이터 무결성 검증용 SHA-256 해시값과 타임스탬프만 블록체인 원장에 커밋
- 통찰: 대용량 원본 파일이나 개인정보를 불변 원장에 직접 기록할 경우 가스비 폭증 및 '잊힐 권리(GDPR 삭제권)' 위반이 발생하므로 오프체인 해시 앵커링(Anchoring) 및 영지식 증명 기반 하이브리드 연계 체계 구축 필요

<details><summary>핵심 용어</summary>

- **오프체인 저장 (Off-chain Storage)** : 블록체인 외부의 파일 시스템(S3, IPFS)이나 DBMS에 대용량 원본 및 개인정보를 보관하는 방식.
- **온체인 저장 (On-chain Storage)** : 모든 노드가 공유하는 분산원장에 데이터를 직접 기록하여 완전한 불변성과 투명성을 보장하는 방식.
- **해시 앵커링 (Hash Anchoring)** : 외부 데이터의 암호학적 해시값(SHA-256)만을 온체인 트랜잭션에 기록하여 원본의 시점과 무결성을 입증하는 기법.
- **잊힐 권리 (Right to be Forgotten)** : GDPR 및 개인정보보호법에 따라 정보주체가 자신의 개인정보 삭제를 요구할 수 있는 법적 권리.
- **IPFS (InterPlanetary File System)** : 분산 P2P 네트워크에서 파일의 콘텐츠 해시(CID) 주소 기반으로 데이터를 저장·공유하는 탈중앙 파일 시스템.

</details>

## 2~4교시 25점 답안

## Ⅰ. 파일 vs DB vs 블록체인 저장의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 비정형 대용량 객체(파일/오브젝트), 구조화된 고속 비즈니스 트랜잭션(DBMS), 다자간 신뢰 검증 및 위변조 방지 불변 이력(블록체인)의 기술적 특성을 상호 보완적으로 결합 배치하는 하이브리드 데이터 스토리지 아키텍처 |
| 목적 | 스토리지 비용 최적화, 밀리초 단위 고속 검색 보장, 규제 컴플라이언스(GDPR 삭제권) 준수 및 공증 수준의 무결성 확보 |

## Ⅱ. 세 저장 매체의 아키텍처 및 핵심 특징

| 저장 매체 | 핵심 아키텍처 및 기술 | 주요 장단점 특징 |
|---|---|---|
| **파일/객체 스토리지** | POSIX 파일시스템, 분산 객체 스토리지 (AWS S3, Ceph, IPFS) | 페타바이트급 비정형 대용량 수용 우수, 키 기반 고속 읽기 지원, 복합 쿼리 및 트랜잭션 ACID 미지원 |
| **데이터베이스 (DBMS)** | RDBMS (B-Tree, ACID, SQL), NoSQL (Document, KV 스토어) | 복잡한 조건 검색, 인덱싱, 빠른 수정/삭제(CRUD) 최적화, 관리자 권한 악용 시 위변조 탐지 취약 |
| **블록체인 (온체인)** | 머클 트리(Merkle Tree), 분산 합의(BFT/PoS), 불변 원장 | Append-only 불변성, 완전한 감사 추적성 보장, 극심한 용량 제약(수십 KB), 수정/삭제 불가, 고비용 |

## Ⅲ. 온체인-오프체인 하이브리드 데이터 파이프라인 및 저장 체계

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 엔터프라이즈 온체인-오프체인 하이브리드 스토리지 참조 아키텍처 ]     │
└────────────────────────────────────────────────────────────────────────┘

  [ 사용자 애플리케이션 및 전자문서 입력 (PDF, 계약서, 이미지) ]
                       │
                       ▼
  ┌──────────────────────────────────────────────────────────────────────┐
  │ [ 계층 1: 비정형 대용량 원본 저장소 (Off-chain Object Storage / IPFS) │
  │  - AES-256 파일 암호화 저장, 대용량 스트리밍 다운로드 지원          │
  └────────────────────────┬─────────────────────────────────────────────┘
                           │ 1. 원본 파일 저장 (File ID / CID 반환)
                           ├───────────────────────────────────┐
                           ▼                                   ▼
  ┌─────────────────────────────────┐ ┌──────────────────────────────────┐
  │ [ 계층 2: 업무 DBMS (RDBMS) ]   │ │ [ 계층 3: 무결성 검증 블록체인 ] │
  │  - 고객 마스터 정보 (개인정보)  │ │  (On-chain Distributed Ledger)   │
  │  - 파일 메타데이터 (File ID,    │ │                                  │
  │    업로드 일시, 권한, 상태)     │ │  - 기록 내용:                    │
  │  - CRUD 지원 (회원 탈퇴 시 삭제)│ │    <DocID, SHA-256(File),       │
  │                                 │ │     Issuer_Sign, Timestamp>      │
  └─────────────────────────────────┘ └──────────────────────────────────┘
                           │                                   │
                           └─────────────────┬─────────────────┘
                                             ▼ (무결성 검증 요청)
  [ 원본 파일 해시 재계산 == 온체인 해시 대조 (위변조 여부 100% 검증) ]
```

| 처리 단계 | 엔지니어링 수행 내용 | 데이터 흐름 및 저장 위치 |
|---|---|---|
| **1. 원본 보관** | 대용량 PDF/이미지를 암호화하여 스토리지 버킷에 보관 | 오브젝트 스토리지 (S3/IPFS) |
| **2. 메타데이터 색인** | 파일 크기, 작성자, 업로드 시간, 파일 경로를 DB에 저장 | 관계형 DBMS (PostgreSQL 등) |
| **3. 해시 앵커링** | 원본 파일의 SHA-256 다이제스트를 추출하여 트랜잭션 전송 | 블록체인 스마트 컨트랙트 (온체인) |
| **4. 진본 검증** | 파일 다운로드 시 실시간 해시값과 온체인 기록 해시값 비교 | 온체인 조회 쿼리 ($O(1)$) |
| **5. 데이터 파기** | 법적 보존 기한 만료 시 오브젝트 및 DB 레코드 완전 파기 | 오프체인 스토리지 및 DB |

## Ⅳ. 파일 시스템 vs DBMS vs 블록체인 저장소 비교

| 비교 항목 | 파일 / 객체 스토리지 | 데이터베이스 (DBMS) | 블록체인 (온체인 원장) |
|---|---|---|---|
| **저장 적합 데이터** | 이미지, 동영상, 대용량 PDF 문서 | 정형 업무 레코드, 통계, 검색 인덱스 | 계약 해시, 전자서명 증적, 소유권 토큰 |
| **데이터 변경(CRUD)**| 덮어쓰기 또는 버전 신규 생성 | 생성, 조회, 수정, 삭제(CRUD) 자유 | 추가만 가능(Append-only, 수정/삭제 불가) |
| **검색 능력** | 파일명/키 기반 단순 키-값 조회 | SQL 기반 다차원 조인, 복합 인덱싱 | 블록 번호, 트랜잭션 해시 기반 단순 조회 |
| **무결성 보장** | 스토리지 접근 제어(ACL)에 의존 | 백업 및 트랜잭션 로그(WAL) 의존 | 합의 알고리즘 및 머클 트리 암호학적 보장 |
| **저장 비용** | 매우 저렴 (GB당 수십 원) | 중간 (GB당 수백~수천 원) | 극도로 비쌈 (가스비 발생, KB당 수천 원) |
| **프라이버시 규제** | 암호화 파기 및 파일 삭제 용이 | 행(Row) 단위 개인정보 파기 용이 | 블록체인 불변성으로 인해 직접 삭제 불가 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 블록체인의 비가역적 불변성으로 인해 GDPR 및 개인정보보호법상 정보주체의 '개인정보 삭제권(잊힐 권리)' 충돌 | 모든 개인 식별 정보는 반드시 오프체인 DBMS에만 보관하고, 온체인에는 비가역적 솔트(Salt) 해시 또는 영지식 증명만 기록하여 오프체인 키 삭제 시 자동 파기 간주(Crypto-shredding) 적용 |
| 수 메가바이트(MB) 이상의 문서를 온체인에 직접 저장 시 블록 크기 초과 및 가스비 기하급수적 폭증 | 원본 문서는 분산 객체 스토리지(S3/IPFS)에 오프체인 저장하고 32바이트 크기의 SHA-256 해시값만 온체인에 기록하는 해시 앵커링 패턴 의무화 |
| 오프체인 파일 스토리지의 장애나 링크 단절(Link Rot) 발생 시 온체인 해시만 남고 원본이 유실되는 고아화 위험 | 다중 리전 오브젝트 복제(CRR) 구축 및 IPFS 파일 고정(Pinning) 클러스터와 정기 무결성 대사 배치 파이프라인 수립 |

## Ⅵ. 제언

전자계약 및 디지털 증빙 시스템 구축 시 비용 효율성과 규제 준수를 모두 만족하기 위해, '오프체인 데이터 레이크 + 온체인 무결성 공증'의 하이브리드 티어링 거버넌스 구축 필요.

```text
[ 데이터 수명주기 티어링 파이프라인 ]
  ┌──────────────────────────────────────────────────────────────────┐
  │ [ 활성 단계 (Active) ]                                           │
  │  - 업무 DBMS (빠른 조회/수정) + 원본 객체 스토리지 저장          │
  │  - 최초 생성 시 블록체인에 SHA-256 타임스탬프 앵커링 (공증 완료) │
  └──────────────────────────────┬───────────────────────────────────┘
                                 │ 계약 종료 및 보존 기간 경과
                                 ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │ [ 파기 단계 (Crypto-Shredding) ]                                │
  │  - 개인정보보호법에 의거 DBMS 개인정보 및 원본 파일 영구 삭제    │
  │  - 온체인 해시값은 남으나 원본 매핑 불가 (수학적 완전 익명화)   │
  └──────────────────────────────────────────────────────────────────┘
```

| 구분 | 온체인 직접 저장 방식 | 제언: 하이브리드 티어링 방식 |
|---|---|---|
| **저장 대상** | 문서 원본 전체를 블록에 기록 | 원본은 S3/DB, 해시(32바이트)만 온체인 |
| **트랜잭션 비용** | 수십만 원 이상의 가스비 발생 | 건당 1원 이하의 극소 비용 소모 |
| **개인정보 컴플라이언스**| 삭제 불가능하여 법률 위반 직면 | 오프체인 암호화 키 파기로 합법적 파기 인정 |
| **시스템 확장성** | 노드 스토리지 폭증으로 확장 한계 | 스토리지와 원장 분리로 무한 페타바이트 확장 |
