## 연관 키워드

- 객체 스토리지(Object Storage), DBMS(Database Management System), 블록체인(Blockchain), 하이브리드 스토리지(Hybrid Storage)
- 해시 앵커링(Hash Anchoring), SHA-256, 머클 트리(Merkle Tree), 불변 원장(Immutable Ledger), Append-only
- ACID, CRUD, GDPR, 잊힐 권리, 암호학적 소거(Crypto-shredding), IPFS, 가스비(Gas Fee)

## Ⅰ. 파일 vs DB vs 블록체인 저장의 개요

- 핵심 요약 : 대용량 원본은 객체 스토리지, 업무 데이터는 DBMS, 무결성 증명은 블록체인에 나누어 두는 하이브리드 저장 구조.
- 개념 : 비정형 대용량 객체인 파일, 구조화된 트랜잭션을 처리하는 **DBMS** (Database Management System), 위변조를 막는 **블록체인** (Blockchain)의 장점을 역할별로 나누어 결합한 하이브리드 스토리지 아키텍처.
- 배경 및 필요성 : 원본 파일이나 개인정보를 블록체인에 직접 기록하면 저장 비용이 크게 늘고 개인정보 삭제 요구와 충돌하므로, 원본은 외부에 두고 **해시 앵커링** (Hash Anchoring, 원본의 해시값만 기록하는 방식)을 쓰는 연계 체계가 필요해짐.
- 주요 목적 : 저장 비용 최적화, 빠른 검색 보장, 개인정보 삭제 규제 준수, 원본 위변조 여부의 검증 가능성 확보.

## Ⅱ. 파일 vs DB vs 블록체인 저장의 특징 및 장점

- 핵심 요약 : 각 저장소의 강점을 역할에 맞게 배치하면 비용, 검색, 무결성, 규제 대응을 동시에 충족하는 구조.

1. **객체 스토리지** (Object Storage) : 대용량 비정형 데이터를 키 기반으로 저장 → 방대한 원본을 낮은 단가로 보관하고 스트리밍 다운로드 지원.
2. 업무 DBMS : **ACID** (Atomicity, Consistency, Isolation, Durability) 트랜잭션과 SQL 질의 지원 → 복합 조건 검색과 개별 레코드 수정·삭제가 용이.
3. 무결성 증명 : 추가만 가능한 **불변 원장** (Append-only Ledger)과 머클 트리 기반 검증 → 기록 이후의 변조를 탐지할 수 있는 증적 확보.

- 세 저장소가 역할을 나누는 흐름은 다음과 같다.

```text
[ 원본 파일 ]
        ↓ 저장 (파일 ID 반환)
[ 객체 스토리지 ]
        ↓ 해시 계산
[ 블록체인: 해시 기록 ]
        ↑ 파일 ID·권한 연결
[ 업무 DBMS: 개인정보·메타데이터 ]
```

## Ⅲ. 파일 vs DB vs 블록체인 저장의 구조 (흐름)

- 핵심 요약 : 원본은 외부 저장소에 두고 블록체인에는 해시와 서명만 남겨, 검증 시 재계산한 해시와 대조하는 구조.
- 온체인과 오프체인 : 블록체인에 올라가는 데이터를 **온체인** (On-chain), 블록체인 외부에 저장하는 데이터를 **오프체인** (Off-chain)이라 한다. 블록체인에는 저장 용량 제약이 커서 원본 대신 32바이트 SHA(Secure Hash Algorithm)-256 해시와 문서 식별자만 기록한다.

```text
[ 제출된 원본 파일 ]
        ↓
[ 해시 재계산 (SHA-256) ]
        ↓
[ 블록체인 기록 해시와 대조 ]
        ↓
[ 일치: 무결성 확인 / 불일치: 변조 의심 ]
```

- 개인정보 처리 : 식별 정보는 DBMS에만 두고, 온체인에는 식별할 수 없는 값만 기록하여 삭제 요구 시 DBMS 데이터와 암호화 키를 제거하는 방식을 쓴다.

## Ⅳ. 파일 vs DB vs 블록체인 저장의 비교

- 핵심 요약 : 저장 비용과 검색 능력은 파일, DBMS, 블록체인 순으로 유리한 축이 다르고, 변경 가능성과 무결성 보장 방식이 가장 큰 차이를 만듦.

| 비교 축 | 파일 / 객체 스토리지 | DBMS | 블록체인 (온체인 원장) |
| --- | --- | --- | --- |
| 적합 데이터 | 이미지, 동영상, 대용량 문서 | 정형 업무 레코드, 검색 인덱스 | 해시, 전자서명 증적, 소유권 기록 |
| 데이터 변경 | 덮어쓰기 또는 새 버전 생성 | CRUD(Create, Read, Update, Delete) 자유 | 추가만 가능, 수정·삭제 불가 |
| 검색 능력 | 파일명과 키 기반 조회 | SQL 기반 다차원 조인과 복합 인덱스 | 블록 번호, 트랜잭션 해시 기반 조회 |
| 무결성 근거 | 접근 제어 목록(ACL)과 운영 통제 | 트랜잭션 로그와 백업 | 합의 알고리즘과 머클 트리 |
| 저장 비용 | 상대적으로 낮음 | 중간 | 가장 높음 (가스비(Gas Fee) 등 수수료 발생) |
| 개인정보 파기 | 파일 삭제 또는 키 파기로 용이 | 행 단위 삭제로 용이 | 불변성 때문에 직접 삭제 불가 |

- 선택 기준 : 데이터의 크기, 변경 빈도, 검색 요구, 법적 삭제 의무, 위변조 증명의 필요성을 순서대로 따져 저장소를 배정한다.

## Ⅴ. 파일 vs DB vs 블록체인 저장의 한계와 방안

- 핵심 요약 : 블록체인 불변성과 삭제권의 충돌, 대용량 온체인 저장의 비용, 오프체인 링크 단절을 기록 설계, 해시 앵커링, 복제와 대사 점검으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 불변성과 잊힐 권리 충돌 | 블록에 기록된 데이터는 지울 수 없어 GDPR(General Data Protection Regulation)의 삭제권, 국내 개인정보보호법상 정정·삭제 요구와 충돌 | 개인정보는 오프체인 DBMS에만 두고, 온체인에는 식별 불가능한 솔트 해시만 기록 후 **암호학적 소거** (Crypto-shredding)로 키 파기 | 삭제 요청 처리 기한 준수율 |
| 대용량 문서의 온체인 저장 | 블록 용량 제약과 높은 수수료로 저장이 현실적이지 않음 | 원본은 객체 스토리지에 두고 32바이트 해시만 온체인에 기록하는 해시 앵커링 적용 | 건당 기록 크기, 수수료 |
| 오프체인 장애와 링크 단절 | 원본이 유실되면 온체인 해시만 남는 고아 해시 발생 | 다중 리전 복제 구성, IPFS(InterPlanetary File System) 사용 시 고정(Pinning) 클러스터 운영, 정기 무결성 대사 배치 | 원본 복구 성공률, 대사 불일치 건수 |

## Ⅵ. 파일 vs DB vs 블록체인 저장에 대한 기술사적 제언

- 핵심 요약 : 원본과 해시를 분리하는 저장 원칙, 개인정보 파기 절차, 복제와 점검 체계를 함께 설계하여 하이브리드 구조를 운영 표준으로 삼아야 함.

1. 저장 원칙의 표준화 : 모든 문서 저장 설계에서 원본은 객체 스토리지나 DBMS에, 무결성 증명은 해시로만 블록체인에 두도록 정하여, 프로젝트마다 온체인 용량이 달라지는 일을 막아야 한다.
2. 파기 절차의 설계 : 개인정보 삭제 요구가 들어왔을 때 DBMS 레코드, 원본 파일, 암호화 키의 파기 순서와 증적을 미리 정의하여 규제 대응 시간을 단축해야 한다.
3. 복제와 대사 점검의 상시화 : 원본 저장소와 온체인 해시를 주기적으로 대조하는 배치를 운영 항목에 포함하여, 고아 해시를 조기에 발견할 수 있게 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 블록체인은 원본 저장소가 아니라 무결성 증명 장치이며, 실무 설계는 저장소의 역할을 나누는 데서 출발함.
- 시사점 : 불변성과 삭제권이 충돌하는 지점을 해시와 키 관리로 해결하는 설계가 법적 위험과 비용을 함께 줄이므로, 저장 기술 선택보다 데이터 분류 기준을 먼저 세워야 한다.
