## 30초 인출

- 본질: **프라이빗 블록체인(Private Blockchain)** 은 사전에 검증되고 인가된 단일 조직 또는 특정 참여자만이 원장 열람·기록·합의에 참여할 수 있는 폐쇄형 허가성(Permissioned) 분산원장
- 메커니즘: MSP 기반 신원 인증 → 클라이언트 트랜잭션 제안 → 보증 피어(Endorser) 실행 및 서명 → 오더링 서비스(Ordering) 블록 순서화 → 커밋 피어(Committer) 검증 및 원장 기록
- 통찰: 중앙화된 운영 주체로 인한 담합 위험과 프라이버시 누출 문제가 존재하므로 조직 간 다중 보증 정책과 프라이빗 데이터 컬렉션(PDC)을 결합한 신뢰 격리 아키텍처 수립

<details><summary>핵심 용어</summary>

- **프라이빗 블록체인(Private Blockchain)** : 특정 주체의 허가를 받은 노드만 접근 및 합의에 참여하는 엔터프라이즈 중심 블록체인.
- **멤버십 서비스 제공자(MSP)** : 조직 내 참여자의 디지털 인증서(X.509 PKI)를 기반으로 신원 및 역할 권한을 검증하는 컴포넌트.
- **실행-순서화-검증(Execute-Order-Validate)** : 트랜잭션을 먼저 시뮬레이션 실행한 뒤 순서를 확정하고 최종 유효성을 검증하는 하이퍼레저 아키텍처.
- **채널(Channel)** : 동일 네트워크 내에서 특정 참여 조직들만 공유하는 서브 분산원장 및 독립적 통신 경로.
- **프라이빗 데이터 컬렉션(PDC)** : 채널 참여자 중 인가된 특정 피어에게만 원본 데이터를 P2P 전송하고 온체인에는 해시만 기록하는 기밀 유지 기술.

</details>

## 2~4교시 25점 답안

## Ⅰ. 프라이빗 블록체인(Private Blockchain)의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **프라이빗 블록체인(Private Blockchain)** 은 중앙 운영 주체의 사전 승인을 받은 검증된 신원의 노드들만이 참여하여 분산 원장을 기록·검증하는 허가형(Permissioned) 블록체인 |
| 목적 | 고성능 트랜잭션 처리(초당 수천 TPS), 즉각적 완결성(Deterministic Finality) 확보 및 기업 간 영업비밀 보호 컴플라이언스 준수 |

## Ⅱ. 프라이빗 블록체인의 핵심 특징

| 구분 | 주요 특징 | 기술적 메커니즘 및 엔지니어링 구현 |
|---|---|---|
| **신원 통제** | 강력한 접근제어 (Permissioned) | PKI 기반 X.509 인증서 및 MSP를 통해 노드·사용자의 역할 기반 접근제어(RBAC) 강제 |
| **처리 성능** | 고속 처리 및 즉각 완결성 | 무거운 PoW/PoS 대신 CFT(Raft), BFT(PBFT) 기반 합의로 수천 TPS 및 무포크(No-Fork) 보장 |
| **기밀성 보장** | 다중 채널 및 데이터 격리 | 채널(Channel) 파티셔닝 및 프라이빗 데이터 컬렉션(PDC)을 통한 비공개 거래 지원 |
| **비용 구조** | 가스비(Gas) 부재 및 예측성 | 트랜잭션 수수료가 발생하지 않아 엔터프라이즈 시스템 운영 비용의 안정적 예측 가능 |

## Ⅲ. 프라이빗 블록체인의 체계 및 트랜잭션 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│      [ 프라이빗 블록체인 (Execute-Order-Validate) 3단계 트랜잭션 파이프라인 ]    │
└────────────────────────────────────────────────────────────────────────┘
      │
      ▼
 [ Phase 1: 트랜잭션 실행 (Execute) ]
   ├── 클라이언트가 체인코드(Smart Contract) 실행 제안(Proposal) 생성
   └── 보증 피어(Endorsing Peer)가 시뮬레이션 실행 후 Read/Write Set 서명 반환
      │
      ▼
 [ Phase 2: 순서화 서비스 (Order) ]
   ├── 클라이언트가 보증 응답을 취합하여 오더링 서비스(Ordering Service)로 전송
   └── Raft 분산 합의 노드가 트랜잭션들의 순서를 결정하여 블록(Block) 패키징
      │
      ▼
 [ Phase 3: 유효성 검증 및 반영 (Validate & Commit) ]
   ├── 오더링 노드가 채널 내 모든 커밋 피어(Committing Peer)로 블록 브로드캐스트
   ├── 피어가 보증 정책(Endorsement Policy) 충족 여부 및 MVCC 읽기 충돌 검증
   └── 유효 트랜잭션을 상태 DB(State DB, CouchDB/LevelDB) 및 블록체인 원장에 영구 커밋
```

| 처리 단계 | 세부 동작 및 기술 요소 | 공학적 중요성 |
|---|---|---|
| **제안 및 보증** | Endorsement Policy 기반 실행 | 비결정론적(Non-deterministic) 코드 사전 차단 및 다자간 합의 |
| **순서화(Ordering)** | Raft 기반 충돌 방지 블록 생성 | 스마트 계약 실행과 블록 합의의 디커플링으로 시스템 처리량 극대화 |
| **MVCC 검증** | Read-Set 버전 일치 여부 확인 | 동시 다발적 트랜잭션 간 상태 덮어쓰기(Race Condition) 원천 차단 |
| **상태 DB 반영** | Key-Value 상태 DB 인덱싱 | 복잡한 Rich Query(CouchDB JSON 쿼리) 지원 및 빠른 상태 조회 |

## Ⅳ. 프라이빗 블록체인, 퍼블릭 블록체인, RDBMS 비교

| 비교 항목 | 프라이빗 블록체인 | 퍼블릭 블록체인 | 전통 중앙집중식 RDBMS |
|---|---|---|---|
| **참여 권한** | 사전 인가된 노드 (Permissioned) | 완전 개방 (Permissionless) | 중앙 DBA 및 단일 조직 |
| **신뢰 모델** | 조직 간 상호 검증 및 컨소시엄 | 암호경제학 및 분산 합의 | 중앙 관리자 신뢰 (TTP) |
| **처리 성능** | 1,000 ~ 10,000+ TPS | 15 ~ 1,000 TPS | 100,000+ TPS 초고속 |
| **완결성 속도** | 즉각적 확정 (수백 ms 이내) | 확률적 완결 (수분 ~ 수십분) | 즉각적 커밋 (ACID 보장) |
| **데이터 수정** | 변경 불가 (단, 합의 시 롤백 가능) | 완전한 불변성 (Immutability) | UPDATE / DELETE 완전 자유 |
| **엔터프라이즈 적합성** | B2B 공급망, 금융 정산, 의료 데이터 | 암호화폐, DeFi, 웹 3.0 토큰 | 단일 기업 내부 ERP, 기간계 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 소수 허가된 노드 간 담합(Collusion) 및 관리자 권한 남용에 따른 원장 조작 위험 | Raft 오더링 클러스터 다변화, 외부 감사 노드(Auditor Peer) 의무 배치 및 조직별 필수 서명(Multi-Signature) 보증 정책 강제 |
| 동일 채널 내 피어 간 원장 전체 동기화로 인한 참여 기업 간 영업 비밀 및 가격 정보 유출 | 프라이빗 데이터 컬렉션(PDC)을 적용하여 원본 데이터는 당사자 피어 간 P2P 암호화 전송하고 온체인에는 데이터 해시값만 커밋 |
| 네트워크 초기 참여 노드 확장 시 복잡한 MSP 인증서 갱신 및 CA(Certificate Authority) 관리 병목 | 전사 공용 PKI 인프라와의 연동 자동화, 분산 신원 증명(DID) 기반 노드 자격 증명 및 GitOps 기반 네트워크 형상 배포 |

## Ⅵ. 제언

단일 중앙 DB 대비 다자간 신뢰 검증 실익이 존재하는 B2B 공급망 관리(SCM) 및 전자계약 영역에 프라이빗 데이터 컬렉션(PDC)을 결합한 하이브리드 기밀 보장 아키텍처 구축.

```text
[ B2B 참여 기업 (제조사 / 유통사 / 물류사) ]
                     │
                     ▼
[ 프라이빗 블록체인 채널 (공유 비즈니스 프로세스) ]
   ├── 공통 원장 (온체인): 트랜잭션 타임스탬프, 계약 상태, 데이터 해시(Hash) 기록
   │
   └── 프라이빗 데이터 컬렉션 (오프체인 P2P 암호화):
         ├── 제조사-유통사 간: 단가 및 발주 수량 원문 (거래 당사자만 조회)
         └── 유통사-물류사 간: 배송지 상세 및 운송 계약서 (물류 담당자만 조회)
```

| 구분 | 단순 RDBMS 기반 연계 | 제언: PDC 기반 프라이빗 블록체인 |
|---|---|---|
| **데이터 무결성** | 연계 기관별 DB 불일치 및 대사 비용 발생 | 암호학적 해시 검증을 통한 실시간 정합성 보장 |
| **정보 유출 통제** | API 연계 시 전체 데이터 노출 위험 | PDC 기반 거래 당사자 간 완벽한 데이터 격리 |
| **감사 추적성** | 관리자 로그 위변조 가능성 잔존 | 변경 불가 원장을 통한 법적 증거력 확보 |
