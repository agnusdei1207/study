## 연관 키워드

- MLOps, 지속적 통합(CI), 지속적 훈련(CT), 지속적 배포(CD), 모델 레지스트리(Model Registry), 모델 계보(Lineage)
- 드리프트(Drift), 침묵적 성능 저하, 학습-서빙 편향, 피처 스토어(Feature Store), 섀도 배포(Shadow Deployment)
- 품질 게이트(Quality Gate), DVC, MLflow, PSI

## Ⅰ. MLOps의 개요

- 핵심 요약 : 모델의 개발, 검증, 배포, 운영 전 과정을 자동화·표준화해 재현성과 지속 품질을 확보하는 엔지니어링 체계.
- 개념 : 데이터 준비, 모델 학습, 검증, 배포, 운영 모니터링을 하나의 흐름으로 자동화하는 엔지니어링 프레임워크인 **MLOps** (Machine Learning Operations, 머신러닝 모델의 개발과 운영을 통합하는 방법론).
- 배경 및 필요성 : 재학습 파이프라인만 자동화하면 데이터 분포 변화가 감지되지 않고 **침묵적 성능 저하** (Silent Failure, 오류 없이 예측 품질만 떨어지는 현상)가 쌓인다. 따라서 계보 추적과 **드리프트** (Drift, 입력 데이터나 입출력 관계의 통계적 변화) 감지 체계가 함께 필요하다.
- 주요 목적 : 데이터와 모델의 재현성 확보, 배포 주기 단축, 운영 중 드리프트 대응, 예측 서비스 품질의 지속 유지.

## Ⅱ. MLOps의 특징 및 장점

- 핵심 요약 : 버전 관리, 자동 학습, 승인 기반 배포가 하나의 순환 파이프라인으로 연결되어 품질과 속도를 함께 얻는 방식.

1. **버전 관리 확장** (코드뿐 아니라 데이터셋과 파이프라인까지 추적하는 방식) : DVC(Data Version Control) 같은 데이터 버전 도구 적용 → 학습 데이터 변경 이력을 재현 가능하게 관리.
2. **지속적 통합** (CI, Continuous Integration)과 **지속적 훈련** (CT, Continuous Training) : 코드 변경 시 자동 테스트, 운영 데이터 변화 시 자동 재학습 → 모델 갱신 주기 단축.
3. **모델 레지스트리** (Model Registry, 모델 버전, 메타데이터, 승인 상태를 저장하는 저장소) : 품질 게이트를 통과한 모델만 승인 → 검증되지 않은 모델의 운영 투입 방지.
4. **지속적 배포** (CD, Continuous Delivery)와 모니터링 : 카나리 또는 섀도 방식으로 배포하고 드리프트를 감시 → 이상 징후 시 이전 모델로 복귀.

```text
[ 데이터·코드·파이프라인 버전 관리 ]
          ↓
[ CI 테스트 · CT 자동 재학습 ]
          ↓
[ 모델 레지스트리 검증·승인 ]
          ↓
[ CD 배포 (카나리·섀도) ]
          ↓
[ 드리프트 모니터링 ]
          ↓  이상 감지 시 재학습 트리거
[ CT 재학습 루프로 복귀 ]
```

## Ⅲ. MLOps의 구조 (흐름)

- 핵심 요약 : 데이터 버전, 학습 파이프라인, 모델 계보, 드리프트 감시 네 요소가 자동 순환을 이루는 구조.
- 데이터·코드 결합 관리 : 학습 데이터셋과 피처를 코드와 함께 버전 관리하며, 학습과 서빙에서 같은 피처를 쓰도록 **피처 스토어** (Feature Store, 학습과 서빙이 공유하는 피처 저장소) 운영 → DVC, Feast.
- 학습 파이프라인 : 이벤트 트리거에 따라 학습, 평가를 자동 수행하는 워크플로 → Kubeflow Pipelines, Airflow.
- 모델 계보 기록 : 배포된 모델이 어떤 데이터, 코드, 하이퍼파라미터로 학습됐는지 역추적하는 **모델 계보** (Lineage) 메타데이터 → MLflow Tracking.
- 드리프트 모니터링 : 입력 분포와 예측 성능을 실시간 감시하고 임계치 초과 시 경보 → Evidently AI, Prometheus.

```text
[ 데이터 버전 ]    DVC, Feast(피처 스토어)
[ 학습 파이프라인 ] Kubeflow Pipelines, Airflow
[ 실험·계보 ]      MLflow Tracking
[ 배포·서빙 ]      KServe, Triton
[ 모니터링 ]       Evidently AI, Prometheus
```

## Ⅳ. MLOps 성숙도 단계의 비교

- 핵심 요약 : 수동 학습에서 CI, CD, CT가 통합된 파이프라인으로 올라갈수록 재현성과 배포 속도가 높아지는 3단계 성숙도 구분.

| 성숙도 단계 | 운영 방식 | 파이프라인 특징 | 자동화 수준 |
| --- | --- | --- | --- |
| Level 0 (수동 프로세스) | 데이터 과학자가 로컬에서 학습하고 모델 파일을 전달 | 배포가 수동이고 피드백 루프 부재 | 수동, 재현성 취약 |
| Level 1 (ML 파이프라인 자동화) | 학습 파이프라인을 자동화하고 CT 구현 | 자동 재학습과 데이터 검증 포함 | CT 자동화, 코드 배포는 수동 |
| Level 2 (CI/CD 파이프라인 자동화) | 파이프라인 코드 자체의 빌드, 테스트, 배포 자동화 | 모듈식 파이프라인과 자동 전환 | CI, CD, CT 통합 |

- 선택 기준 : 모델 수가 적고 재학습 빈도가 낮으면 Level 0에서 Level 1로, 모델이 많고 변경이 잦으면 Level 2 통합을 목표로 한다.

## Ⅴ. MLOps의 한계와 방안

- 핵심 요약 : 학습과 서빙의 불일치, 잘못된 재학습, 재현성 부족을 피처 일원화, 승인 게이트, 계보 관리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 학습-서빙 편향 (Training-Serving Skew)과 데이터 드리프트 | 학습과 서빙의 피처 계산이 달라 예측 품질이 조용히 하락 | 온·오프라인 피처를 단일 정의로 공유하는 피처 스토어 구축, **PSI** (Population Stability Index, 입력 분포 변화를 수치화한 지수) 기반 알람 | PSI 임계 초과 건수 |
| 재학습 트리거 오작동, 오염 데이터 학습 | 잘못된 트리거나 오염된 데이터로 모델 성능이 붕괴 | **섀도 배포** (Shadow Deployment, 운영 트래픽을 복제해 새 모델을 검증만 하는 방식) 후 **품질 게이트** (Quality Gate, 기준 미달 시 배포 차단)와 자동 롤백 | 롤백 발생 횟수 |
| 다차원 의존성으로 인한 재현성 결여 | 데이터, 코드, 가중치, 하이퍼파라미터가 얽혀 같은 결과를 재현하기 어려움 | 불변 스토리지 기반 메타데이터 계보 관리, 컨테이너화된 파이프라인 환경 고정 | 재현 성공률 |

## Ⅵ. MLOps 도입을 위한 기술사적 제언

- 핵심 요약 : 개별 도구 도입보다 데이터 거버넌스와 배포 신뢰성을 연결하는 조직 역량으로 MLOps를 정착시킬 필요.

1. 단계별 로드맵 : 단기에는 실험 추적과 모델 레지스트리를 표준화하고, 중장기에는 온·오프라인 통합 피처 스토어와 CI/CD/CT 자동화로 넓히는 순서가 안정적이다.
2. 역할 정의 : 데이터 과학자와 MLOps 엔지니어의 책임 범위(R&R, Roles and Responsibilities)를 나눠 정하고, 모델 승인 권한을 거버넌스 위원회에 두어 운영 책임을 분명히 한다.
3. 모델 거버넌스 : 공정성과 설명 가능성 점검을 품질 게이트 항목에 포함해, 성능과 신뢰성을 함께 검증하는 전사 기준을 운영한다.

## Ⅶ. 결론

- 핵심 요약 : MLOps는 모델을 한 번 만드는 기술이 아니라 운영 중에도 품질을 지키는 순환 체계.
- 시사점 : 재현성과 승인 게이트가 갖춰진 조직만 드리프트와 재학습 부담을 통제할 수 있으므로, 도구보다 프로세스와 역할 정의를 먼저 세우는 것이 필요.
