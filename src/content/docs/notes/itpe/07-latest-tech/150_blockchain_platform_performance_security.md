## 30초 인출

- 본질: **블록체인 플랫폼 성능·보안** 은 분산원장의 트릴레마(확장성·보안성·탈중앙성) 한계를 극복하기 위해 합의 지연, 직렬 실행, 상태 팽창(State Bloat) 병목을 개선하고 위협을 방어하는 공학적 최적화 체계
- 메커니즘: 합의 계층 통신 최적화 → 병렬 트랜잭션 실행(Block-STM) → L2 롤업(Rollup) 연산 분리 → 상태 가지치기(Pruning) 및 영지식 증명 기반 보안 검증
- 통찰: L2 롤업 도입 시 중앙화된 시퀀서(Sequencer)의 단일 실패점(SPOF) 및 검열 위험이 발생하므로 탈중앙화 공유 시퀀서 네트워크와 영지식 증명(ZK-Rollup) 강제 탈출구(Force Exit) 구축 필요

<details><summary>핵심 용어</summary>

- **블록체인 트릴레마 (Blockchain Trilemma)** : 확장성(Scalability), 탈중앙성(Decentralization), 보안성(Security)을 동시에 완벽히 만족하기 어렵다는 트레이드오프 이론.
- **최종성 (Finality)** : 블록에 기록된 트랜잭션이 이후 분기나 재구성(Reorganization)에 의해 취소되거나 변경될 수 없음을 확정하는 시점.
- **롤업 (Rollup)** : L1 메인넷 밖에서 대량의 트랜잭션을 실행하고, 그 결과 데이터와 암호화 증명(사기증명/영지식증명)만 L1에 롤업 저장하는 L2 확장 기술.
- **상태 팽창 (State Bloat)** : 누적된 계정 상태와 스마트 컨트랙트 데이터로 인해 풀 노드의 스토리지와 RAM 요구량이 급증하는 병목 현상.
- **재진입 공격 (Reentrancy Attack)** : 외부 컨트랙트 호출 시 상태 변수 변경 전 재귀적으로 잔액 인출 함수를 재호출하여 자금을 탈취하는 취약점.

</details>

## 2~4교시 25점 답안

## Ⅰ. 블록체인 플랫폼 성능·보안의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 분산 네트워크의 신뢰성과 무결성을 저해하지 않으면서, 트랜잭션 처리량(TPS)과 최종성 지연을 개선하고 스마트 컨트랙트 및 네트워크 공격을 방어하는 플랫폼 최적화 기술 체계 |
| 목적 | 대규모 상용 서비스 처리를 위한 초당 트랜잭션(TPS) 극대화, 가스 수수료 안정화, 포크(Fork) 및 자산 탈취 해킹 사고 방지 |

## Ⅱ. 블록체인 트릴레마와 성능·보안 아키텍처 특징

| 플랫폼 계층 | 성능 병목 요인 | 주요 보안 위협 및 설계 특징 |
|---|---|---|
| **네트워크 계층 (Network)** | P2P 노드 전파 지연, 블록 전파(Gossip) 병목 | 이클립스 공격(Eclipse), Sybil 공격, DDoS 유발 |
| **합의 계층 (Consensus)** | BFT 쿼럼 통신 복잡도 ($O(N^2)$), 작업증명 지연 | 51% 과반수 해시 장악, 롱레인지 공격, 포크 공격 |
| **실행 계층 (Execution)** | 단일 스레드 직렬 EVM 연산, 스마트 컨트랙트 병목 | 재진입 공격, 정수 오버플로우, 프론트러닝(MEV) |
| **스토리지 계층 (Storage)** | 머클 패트리샤 트리(MPT) I/O 오버헤드, 상태 팽창 | 디스크 I/O 고갈로 인한 노드 다운, 데이터 무결성 훼손 |

## Ⅲ. 블록체인 트랜잭션 수명주기 및 레이어별 병목 분석 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 블록체인 트랜잭션 처리 파이프라인 및 계층별 성능·보안 통제점 ]       │
└────────────────────────────────────────────────────────────────────────┘

  [ 클라이언트 트랜잭션 서명 (ECDSA) ]
                 │
                 ▼ (멤풀 전파: P2P Network Layer) ──> 위협: 멤풀 스나이핑 / MEV 공격
  [ 트랜잭션 검증 및 멤풀 대기 (Mempool) ]
                 │
                 ▼ (합의 및 순서화: Consensus Layer) ──> 병목: BFT 메시지 지연 ($O(N^2)$)
  [ 블록 생성 및 검증자 합의 (PBFT / PoS / PoW) ]
                 │
                 ▼ (가상머신 실행: Execution Layer) ──> 병목: 직렬 EVM 실행 지연
  [ 스마트 컨트랙트 병렬 실행 (Block-STM / Parallel EVM) ]
                 │
                 ▼ (원장 기록: Storage Layer) ──> 병목: 머클 트리 상태 I/O 팽창
  [ 로컬 상태 트리(State Trie) 갱신 및 디스크 Commit (LevelDB/RocksDB) ]
                 │
                 ▼ (최종 블록 확정: Finality)
  [ 비가역적 거래 확정 (Deterministic Finality 달성) ]
```

| 처리 구간 | 성능 병목 해소 방안 | 보안 통제 메커니즘 |
|---|---|---|
| **트랜잭션 수집** | 트랜잭션 압축 전송, 프라이빗 멤풀(Flashbots Protect) | 프론트러닝 및 샌드위치 공격 차단 |
| **합의 도출** | BLS 집계 서명 적용으로 통신 복잡도 $O(N)$ 축소 | 비잔틴 장애 허용(BFT) 2/3 이상 쿼럼 보장 |
| **컨트랙트 실행** | 낙관적 동시성 제어(OCC) 기반 다중 코어 병렬 실행 | 정적 분석(Slither), 형식 검증(Formal Verification) |
| **원장 저장** | 상태 가지치기(State Pruning), 플랫 KV 스토리지 전환 | 머클 증명(Merkle Proof) 기반 암호학적 무결성 |

## Ⅳ. 온체인 확장(L1) vs 오프체인 확장(L2 Rollup) 비교

| 비교 항목 | L1 온체인 확장 (샤딩, 병렬 EVM) | L2 옵티미스틱 롤업 (Arbitrum 등) | L2 영지식 롤업 (ZK-Rollup) |
|---|---|---|---|
| **확장 원리** | 메인넷 노드 자체의 처리 능력 및 파티셔닝 | 오프체인 실행 후 L1에 번들 제출 | 오프체인 실행 후 암호학적 ZK-Proof 제출 |
| **트랜잭션 검증** | L1 검증자가 직접 전수 재검증 | 7일간의 사기 증명(Fraud Proof) 분쟁 기간 | ZK-SNARK/STARK 수학적 즉각 검증 |
| **최종성 (Finality)** | L1 블록 확정 즉시 (수초~수분) | 분쟁 기간 완료 후 (약 7일 소요) | 증명 검증 완료 즉시 (수분~수십분) |
| **연산 복잡도** | L1 하드웨어 스펙 상향 요구 | L1 저장 비용만 소모 (낮음) | 증명 생성자(Prover)의 막대한 암호 연산 |
| **보안 상속** | L1 자체 합의 보안성에 종속 | L1의 데이터 가용성 및 보안 완전 상속 | L1의 암호학적 무결성 및 보안 완전 상속 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| L2 롤업의 중앙화된 시퀀서(Sequencer) 다운 시 전체 트랜잭션 중단 및 거래 검열(Censorship) 위험 | Espressso, Astria 등 탈중앙 공유 시퀀서 네트워크 도입 및 L1 비상 강제 트랜잭션 제출(Escape Hatch) 보장 |
| 원장 데이터 누적으로 인한 풀 노드 디스크 팽창(State Bloat)으로 일반 사용자의 검증 참여 불가 | EIP-4844 Blob 트랜잭션 기반의 18일 후 콜데이터 자동 폐기 및 히스토리 데이터 분산 저장(Portal Network) 적용 |
| 스마트 컨트랙트 내 플래시 론(Flash Loan) 기반 가격 오라클 조작 및 유동성 탈취 공격 빈발 | 단일 DEX 스팟 가격 대신 시간 가중 평균 가격(TWAP) 및 체인링크(Chainlink) 탈중앙 오라클 다중 교차 검증 적용 |

## Ⅵ. 제언

고성능 분산 서비스를 위해 L1은 고신뢰 합의·데이터 가용성(DA) 계층으로 특화하고, 실행은 모듈러 블록체인 기반의 ZK-Rollup 및 병렬 EVM으로 분리하는 계층화 아키텍처 구축 필요.

```text
[ 모듈러 블록체인 계층화 아키텍처 ]
  ┌──────────────────────────────────────────────────────────────────┐
  │ [ 실행 계층 (Execution Layer) ]                                  │
  │  - 병렬 EVM (Block-STM) 및 고속 ZK-Rollup 엔진 (TPS > 10,000)     │
  └──────────────────────────────┬───────────────────────────────────┘
                                 │ 트랜잭션 일괄 번들 및 ZK-SNARK 증명 전송
                                 ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │ [ 정산 및 보안 계층 (Settlement & Security: Ethereum L1) ]       │
  │  - 영지식 증명 온체인 검증 (Smart Contract Verifier)             │
  └──────────────────────────────┬───────────────────────────────────┘
                                 │
                                 ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │ [ 데이터 가용성 계층 (Data Availability: Celestia / EIP-4844 Blob) │
  │  - 데이터 가용성 샘플링(DAS)을 통한 초저비용 대용량 블롭 저장    │
  └──────────────────────────────────────────────────────────────────┘
```

| 구분 | 단일 모놀리식 블록체인 | 제언: 모듈러 ZK-Rollup 아키텍처 |
|---|---|---|
| **기능 구조** | 단일 L1이 합의·실행·저장 전담 | 실행, 합의, 데이터 가용성 완전 분리 |
| **확장성** | TPS 15~50 한계 (네트워크 병목) | TPS 10,000 이상 달성 및 수수료 99% 절감 |
| **보안 검증** | 모든 노드가 모든 트랜잭션 재실행 | 수학적 ZK 증명 하나로 전체 블록 검증 |
| **노드 부담** | 노드 하드웨어 요구량 폭증 | 경량 노드도 데이터 가용성 샘플링 참여 가능 |
