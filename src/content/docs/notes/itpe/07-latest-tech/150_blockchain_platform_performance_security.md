## 연관 키워드

- 트랜잭션 처리량(TPS), 롤업(Rollup), 옵티미스틱 롤업, ZK 롤업
- 시퀀서, 영지식 증명, 강제 탈출구, 상태 팽창
- 플래시 론, 시간 가중 평균 가격(TWAP), 탈중앙 오라클, 이클립스 공격

## Ⅰ. 블록체인 플랫폼 성능·보안의 개요

- 핵심 요약 : 신뢰와 무결성을 해치지 않으면서 처리량을 늘리고, 계층별 공격을 막는 플랫폼 최적화 체계.
- 개념 : 분산 네트워크의 무결성을 유지한 채 **트랜잭션 처리량** (TPS, Transactions Per Second)을 높이고, 스마트 컨트랙트와 네트워크 공격을 방어하는 기술 체계.
- 배경 및 필요성 : **롤업** (Rollup) 도입으로 실행은 L2로 옮겨졌지만, 중앙화된 **시퀀서** (Sequencer)가 멈추면 거래 전체가 정지하고 검열 위험도 생김. 따라서 탈중앙 시퀀서 구조와 L1에서 직접 거래를 제출하는 탈출 경로가 필요함.
- 주요 목적 : 대규모 서비스를 위한 처리량 확보, 수수료 변동 완화, 포크와 자산 탈취 방지.

## Ⅱ. 블록체인 플랫폼 성능·보안의 특징 및 장점

- 핵심 요약 : 합의, 실행, 저장, 네트워크의 각 계층이 서로 다른 병목과 공격 표면을 가지므로 계층별 통제가 필요함.

1. 네트워크 계층 : P2P 블록 전파 지연이 병목이며, **이클립스 공격** (Eclipse Attack)과 Sybil 공격에 노출 → 노드 연결을 다변화해 전파 안정성 확보.
2. 합의 계층 : 검증자 간 통신량이 노드 수의 제곱에 비례하는 BFT 구조가 병목이며, 과반 해시 장악 같은 공격이 존재 → 합의 방식에 맞는 노드 규모 설계.
3. 실행 계층 : 직렬 EVM 실행이 처리량을 제한하며, 재진입과 **프론트러닝** (Front-running)에 노출 → 병렬 실행과 컨트랙트 검증으로 완화.
4. 저장 계층 : 머클 패트리샤 트리(MPT) 갱신으로 디스크 입출력이 늘고 상태가 팽창 → 상태 정리와 데이터 분산 보관으로 노드 부담 완화.

## Ⅲ. 블록체인 플랫폼 성능·보안의 구조 (흐름)

- 핵심 요약 : 트랜잭션이 전파, 합의, 실행, 저장을 거쳐 확정되는 순서에 따라 각 단계의 병목과 위협이 정해짐.

```text
[ 트랜잭션 서명·전파 ] ← 멤풀 스나이핑, MEV
          ↓
[ 합의 (블록 순서 결정) ] ← 메시지 복잡도 병목
          ↓
[ 실행 (스마트 컨트랙트) ] ← 재진입, 플래시 론
          ↓
[ 저장 (상태 트리 갱신) ] ← 상태 팽창
          ↓
[ 최종성 (거래 확정) ]
```

```text
L2 롤업의 거래 흐름
[ L2에서 거래 실행 ]
          ↓
[ 배치 데이터를 L1에 제출 ]
          ↓
[ 사기 증명 또는 영지식 증명으로 검증 ]
```

## Ⅳ. 블록체인 플랫폼 성능·보안의 비교

- 핵심 요약 : L1 확장, 옵티미스틱 롤업, ZK 롤업은 검증 방식과 최종성에서 차이가 나며 보안 상속 정도가 같지 않음.

| 비교 축 | L1 온체인 확장 (샤딩, 병렬 실행) | 옵티미스틱 롤업 | ZK 롤업 |
| --- | --- | --- | --- |
| 확장 원리 | 메인넷 자체의 처리 능력과 분할 | 오프체인 실행 후 L1에 배치 제출 | 오프체인 실행 후 **영지식 증명** (ZK-Proof) 제출 |
| 검증 방식 | L1 검증자가 직접 재검증 | 사기 증명 기반 분쟁 기간 운영 | 수학적 증명을 즉시 검증 |
| 최종성 | L1 확정 즉시 | 분쟁 기간 종료 후 (통상 7일 설계) | 증명 검증 완료 시점 |
| 연산 부담 | L1 하드웨어 사양 상향 | L1 데이터 저장 비용 | 증명 생성 측의 암호 연산 부담 |
| 보안 상속 | L1 합의 보안에 종속 | L1의 데이터 가용성과 보안 상속 | L1의 암호학적 무결성 상속 |

## Ⅴ. 블록체인 플랫폼 성능·보안의 한계와 방안

- 핵심 요약 : 중앙 시퀀서, 상태 팽창, 가격 오라클 조작을 탈중앙 구조, 데이터 정리, 시간 평균 가격으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 중앙 시퀀서 장애와 검열 | 시퀀서 다운 시 거래 전체 중단, 특정 거래 배제 가능 | 탈중앙 공유 시퀀서 도입, L1 강제 제출 경로(Escape Hatch) 보장 | 시퀀서 가용률, 강제 제출 처리 완료 여부 |
| 상태 팽창 | 원장 누적으로 풀 노드 디스크 부담이 커져 검증 참여가 줄어듦 | EIP-4844 blob 데이터의 자동 폐기(약 18일 보관), 히스토리 분산 저장 | 노드 디스크 사용량, 검증 노드 수 |
| 플래시 론 기반 오라클 조작 | 단일 DEX의 현물 가격을 일시적으로 조작해 담보 평가 왜곡 | **시간 가중 평균 가격** (TWAP, Time-Weighted Average Price) 적용, 탈중앙 오라클 교차 검증 | 가격 편차율 |

## Ⅵ. 블록체인 플랫폼 성능·보안에 대한 기술사적 제언

- 핵심 요약 : 실행과 합의, 데이터 가용성을 분리하고 검증 부담을 증명 기반으로 낮추는 설계를 기본 원칙으로 삼는 방향.

1. 계층 분리 : 플랫폼 설계 조직은 실행, 합의, 데이터 가용성을 역할별로 분리하고, 각 계층의 장애가 전체 서비스 정지로 번지지 않도록 설계해야 한다.
2. 시퀀서 이중화 : L2 운영 기업은 시퀀서를 단일 주체에 맡기지 않고, 장애 시 L1에서 거래를 직접 제출하는 경로를 서비스 요건으로 명시해야 한다.
3. 오라클 검증 : 금융 서비스를 운영하는 기관은 가격 입력을 단일 출처에 의존하지 않도록 시간 평균 가격과 교차 검증 정책을 표준으로 두는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : 블록체인 성능 개선은 처리량 확대와 보안 상속을 함께 만족하는 계층 설계의 문제임.
- 시사점 : 롤업 확산으로 확장성은 높아졌으나 시퀀서와 오라클이 새로운 단일 실패점이 되므로, 보안 설계를 계층별로 검증하는 것이 전제 조건이다.
