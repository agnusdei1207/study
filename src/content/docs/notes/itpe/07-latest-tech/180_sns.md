## Ⅰ. 소셜네트워크서비스(SNS)의 개요

- 개념 : 웹과 모바일 환경에서 개인의 신원 프로필과 사용자 간의 연결선인 **소셜 그래프**를 기반으로 텍스트, 이미지, 비디오 등 콘텐츠를 생성·유통·소비하는 분산 소셜 플랫폼.
- 배경 및 필요성 : 수천만 팔로워를 보유한 유명 계정 발행 시 **쓰기 팬아웃** 병목이 발생하므로 계정 영향력에 따라 **푸시** (Push)와 **풀** (Pull)을 동적 분기하는 **하이브리드 타임라인** 아키텍처 구축 필수.
- 핵심 목적 : 시공간을 초월한 관계망 형성, 정보의 바이럴(Viral) 확산, 개인화된 관심사 피드 큐레이션 및 소셜 커머스 등 네트워크 경제 가치 창출.

## Ⅱ. 소셜네트워크서비스(SNS)의 핵심 아키텍처 및 동작 메커니즘

소셜네트워크서비스는 신뢰할 수 있는 데이터 파이프라인과 고도화된 추론 메커니즘을 기반으로 동작하며, 세부적인 아키텍처와 핵심 컴포넌트 간 상호작용 프로세스는 다음과 같음.

```text
[발행자] ──► [API 게이트웨이] ──► [게시물 서비스] ──► [Post DB 저장]
                                        │
                                        ▼ (팔로워 수 판별 분기)
                 +----------------------+----------------------+
                 │ (팔로워 적음)                           │ (팔로워 많음: 유명인)
                 ▼                                             ▼
     [Fan-out on Write (Push)]                    [Fan-out on Read (Pull)]
- 팔로워 목록 조회 (Graph DB)                - 사용자 타임라인 캐시 복제 생략
- 각 팔로워 Redis Inbox에 Post ID 복제       - 유명인 전용 Outbox 캐시에만 보관
                 │                                             │
                 └──────────────────────┬──────────────────────┘
                                        ▼
                                 [피드 조회 요청]
                                        │
        [타임라인 서비스: Redis Inbox 조회 + 유명인 Outbox 동적 병합]
                                        ▼
                        [ML 랭킹 모델: 최적 정렬]
                                        ▼
                               [클라이언트 피드 표출]
```

- **소셜 그래프 엔진** : Neo4j, JanusGraph, AWS(Amazon Web Services) Neptune - 팔로우, 맞팔로우, 차단, 그룹 관계의 정점/간선 초고속 인덱싱.
- **메시지 큐** : Apache Kafka, RabbitMQ - 게시물 작성 이벤트를 비동기 분산 수신하여 팬아웃 워커 풀로 발행.
- **인메모리 타임라인 캐시** : Redis Cluster, Memcached - 각 사용자의 피드 상위 800개 게시물 ID(Identifier)를 **Sorted Set** 구조로 저장.
- **개인화 랭킹 엔진** : DLRM, GNN(Graph Neural Network), XGBoost - 친밀도(Affinity), 콘텐츠 가중치(Weight), 최신성(Decay) 기반 정렬.

## Ⅲ. 소셜네트워크서비스(SNS)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 팬아웃 온 라이트 (Push Model) | 팬아웃 온 리드 (Pull Model) |
|---|---|---|
| **데이터 처리 시점** | 사용자가 게시물을 작성(Write)하는 시점 | 사용자가 타임라인을 조회(Read)하는 시점 |
| **읽기 성능 (Read Latency)** | 최고 (자신의 Redis Inbox만 단순 조회, <10ms) | 느림 (모든 팔로잉 대상의 글을 동적 쿼리 및 병합) |
| **쓰기 부하 (Write Load)** | 극단적으로 높음 (팔로워 N명에게 N번 복제 쓰기) | 매우 낮음 (작성자 테이블에 1회 쓰기만 수행) |
| **스토리지 낭비** | 심각 (휴면 사용자 Inbox에도 데이터 복제 누적) | 최소화 (게시물 원본 1벌만 저장) |
| **유명인 계정 취약성** | 치명적 병목 (팔로워가 매우 많을 때 쓰기 폭증) | 완벽 대응 (작성 시 부하 없음) |
| **최적 적용 대상** | 팔로워 수가 적은 일반 사용자 간의 피드 전파 | 팔로워 수만~수천만 이상의 슈퍼 인플루언서 계정 |

- 소셜네트워크서비스는 상기 비교 지표를 바탕으로 비즈니스 요구사항과 운영 인프라 환경을 고려한 최적의 아키텍처를 선정하고, 확장성과 안정성을 균형 있게 확보해야 함.

## Ⅳ. 소셜네트워크서비스(SNS)의 주요 한계점 및 해결 방안

- 유명인(Celebrity) 게시물 발행 시 팬아웃 스톰(Storm) 발생 :
  - 한계점 : 수천만 팔로워를 가진 계정의 글 작성 시 메시지 큐 포화 및 타임라인 캐시 쓰기 지연.
  - 해결 방안 : 동적 하이브리드 분기 및 지연 평가(Lazy Evaluation) - 팔로워 임계치를 기준으로 일반 사용자는 Push, 인플루언서는 Pull 모델 적용. - 활성 사용자(최근 접속)에게만 선별적 Push를 수행하여 캐시 낭비 제거.
- 필터 버블(Filter Bubble) 및 확증 편향에 따른 유해 정보 증폭 :
  - 한계점 : 클릭률(CTR(Click-Through Rate)) 극대화 중심 알고리즘이 극단적 콘텐츠 및 가짜 뉴스를 상위 노출.
  - 해결 방안 : 탐색-활용(Exploration-Exploitation) 균형 및 다양성 페널티 - 멀티암드 밴딧(MAB) 알고리즘을 도입하여 일부 피드 슬롯에 새로운 주제 탐색 강제. - 출처 신뢰도 점수 및 사실 검증(Fact-Check) 메타데이터를 랭킹 가중치에 차감 반영.
- 서비스 사일로화 및 플랫폼 독점 종속(Lock-in) :
  - 한계점 : 플랫폼 폐쇄성으로 인해 계정 이동 및 외부 플랫폼과의 데이터 연동 불가.
  - 해결 방안 : 탈중앙화 연합 소셜 프로토콜(ActivityPub, AT Proto) 도입 - W3C(World Wide Web Consortium) 표준 ActivityPub을 적용하여 이종 서버 간 프로필 및 게시물 상호운용성 보장. - 데이터 이동권(Data Portability) API(Application Programming Interface)를 제공하여 소셜 그래프 내보내기 지원.

## Ⅴ. 소셜네트워크서비스(SNS) 적용 및 발전을 위한 기술사적 제언

- 피드 로딩 지연(P99) 절감 및 최적화 체계 구축 : 낮은 지연 목표의 한계를 탈피하고, Redis Cluster 샤딩 및 클라이언트 사이드 프리페칭(Pre-fetching)를 체계적으로 추진하여 실무 운영 효율성과 엔지니어링 신뢰성을 극대화해야 함.
- 팬아웃 지연 시간 절감 및 최적화 체계 구축 (Celery) : 일반 계정의 낮은 지연 목표의 한계를 탈피하고, 비동기 셀러리(Celery)/카프카 파티션 분산 병렬화를 체계적으로 추진하여 실무 운영 효율성과 엔지니어링 신뢰성을 극대화해야 함.
- 어뷰징 봇 탐지율 고도화 및 그래프 이상 탐지 추진 : 악성 자동화 계정 차단의 한계를 탈피하고, 그래프 이상 탐지(Graph Anomaly Detection) 및 행동 패턴 분석을 체계적으로 추진하여 실무 운영 효율성과 엔지니어링 신뢰성을 극대화해야 함.
