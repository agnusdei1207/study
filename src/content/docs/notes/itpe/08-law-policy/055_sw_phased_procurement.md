## 연관 키워드

- 단계별 발주제도(Phased Procurement), 설계 동결(Design Freeze), 요구사항 추적 매트릭스(RTM)
- 제안요청서(RFP), 기능점수(FP), 분석·설계 사업, 구현·시험 사업
- 턴키(Turnkey) 발주, 상용SW 분리발주, 감리, 과업 변경, 대가 산정

## Ⅰ. 소프트웨어 단계별 발주제도(Phased Procurement)의 개요

- 핵심 요약 : 공공 SW 사업을 분석·설계와 구현으로 나눠 순차 발주하여 요구사항 불확실성과 설계 책임 공방을 줄이는 계약 방식.
- 개념 : 공공 SW 사업을 하나의 일괄 계약으로 묶지 않고, 1단계(요구사항 분석·설계)와 2단계(구현·시험)로 나누어 순차 발주하는 **단계별 발주제도** (Phased Procurement).
- 배경 및 필요성 : 요구사항이 덜 정리된 채 일괄 계약을 맺으면 착수 뒤 설계 변경과 추가 과업이 반복되어 무상 과업과 납기 지연이 쌓인다. 따라서 설계를 먼저 확정하고, 확정된 설계 산출물을 기준으로 2단계를 발주해야 한다.
- 주요 목적 : 과업 범위의 불확실성 해소, 잦은 설계 변경에 따른 납기 지연 방지, 소프트웨어 대가의 근거 있는 산정.

## Ⅱ. 소프트웨어 단계별 발주제도(Phased Procurement)의 특징 및 장점

- 핵심 요약 : 단계 분리와 설계 동결 게이트로 과업 범위를 고정하고, 설계 책임을 2단계까지 잇는 발주 방식.

1. 단계 분리 발주 : 분석·설계와 구현을 각각 계약 → 착수 전에 요구사항이 확정되어 과업 변경 감소.
2. 설계 동결 게이트 : 1단계 산출물 검수 후 설계를 고정 → 2단계 진행 중 범위 확대를 통제.
3. **요구사항 추적 매트릭스** (RTM, Requirements Traceability Matrix) 인계 : 요구사항부터 기능 설계, 구현, 인수시험까지 추적 가능 → 산출물 간 누락을 확인.
4. 기능점수 기반 대가 산정 : 1단계 결과로 **기능점수** (FP, Function Point)를 산정하여 2단계 규모를 측정 → 투입 인월 추정보다 근거 있는 대가 책정.

## Ⅲ. 소프트웨어 단계별 발주제도(Phased Procurement)의 구조 (흐름)

- 핵심 요약 : 1단계 설계가 동결 게이트를 거쳐 2단계 구현으로 넘어가고, 요구사항 추적 매트릭스가 전 과정을 잇는 구조.

```text
[ 1단계 분석·설계 발주 ]
  업무 재설계, 상세 요구사항 정의
  아키텍처 설계, 2단계 RFP 확정
      ↓
[ 산출물 검수 · 설계 동결 게이트 ]
      ↓
[ 2단계 구현·시험 발주 ]
  설계서 인계, 개발, 통합 시험
      ↓
[ 종합 감리 · 최종 인수 ]
```

```text
[ 요구사항 추적 흐름 ]
1단계 사용자 요구사항
      ↓
1단계 기능 설계서
      ↓
2단계 제안요청서 (RFP)
      ↓
2단계 구현 소스코드
      ↓
인수 시험 시나리오
```

## Ⅳ. 일괄 발주, 단계별 발주, 상용SW 분리발주의 비교

- 핵심 요약 : 일괄 발주는 행정이 간소하지만 요구사항 불확실성을 떠안고, 단계별 발주는 범위를 고정하는 대신 계약 행정이 늘어나는 구조.

| 비교 항목 | 전통적 일괄 발주 (Turnkey) | 단계별 발주 (Phased Procurement) | 상용SW 분리발주 |
| --- | --- | --- | --- |
| 발주 개념 | 분석부터 구현까지 단일 계약 | 개발 시점에 따라 분석·설계와 구현을 분리 | 구축 용역과 상용 패키지 SW를 분리 |
| 분리 기준 | 분리 없음 | 개발 라이프사이클(시점) | 조달 대상(용역 대 상용 SW) |
| 요구사항 확정 | 불명확한 상태로 착수 후 변경 | 1단계에서 확정 후 2단계 착수 | 상용 SW의 기능 범위를 별도로 규격화 |
| 과업 변경 리스크 | 재작업과 납기 지연 빈번 | 2단계 착수 전 범위 고정으로 감소 | 조달 대상별 대가 구분이 명확 |
| 계약 행정 부담 | 입찰 1회로 간소 | 단계마다 공고와 계약이 반복 | 복수 계약으로 행정 소요 증가 |

- 선택 기준 : 요구사항이 명확하고 규모가 작은 사업은 일괄 발주, 대규모·복합 사업은 단계별 발주를 택하는 것이 합리적임.

## Ⅴ. 소프트웨어 단계별 발주제도(Phased Procurement)의 한계와 방안

- 핵심 요약 : 설계와 구현 사업자 간 책임 공방, 단계 간 행정 지연, 법령 변경에 따른 과업 변경 갈등을 계약 조건과 조달 절차로 관리해야 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 설계·구현 사업자 분리에 따른 책임 공방 | 사업자가 다르면 설계 결함의 귀책이 불분명해 분쟁 발생 | 1단계 사업자의 2단계 기술지원 의무를 계약 특수조건으로 명시하고, 2단계 초기에 설계 인계 워크숍 운영 | 설계 질의 처리 기간, 귀책 분쟁 건수 |
| 단계 간 입찰·계약 행정에 따른 공기 지연 | 단계마다 공고, 평가, 계약 절차가 붙어 전체 리드타임 증가 | 1단계 종료 전 2단계 규격을 미리 공개하고 사전 발주 준비를 병행하는 조달 패스트트랙 적용 | 단계 전환 소요 일수 |
| 설계 이후 법령·정책 변경에 따른 과업 변경 갈등 | 설계 확정 뒤 법 개정으로 수정이 필요하나 대가 보상 기준이 불명확 | 과업심의를 거친 변경 절차를 두고, 기능점수 재산정으로 계약금액과 공기를 조정 | 변경 요청 건수, 재산정 소요 기간 |

## Ⅵ. 소프트웨어 단계별 발주제도에 대한 기술사적 제언

- 핵심 요약 : 1단계 수행자의 2단계 참여를 제도화하고, 설계 동결과 변경 통제를 하나의 엔지니어링 거버넌스로 묶어 운영.

1. 설계 책임의 연속성 : 1단계 수행 기업이 2단계 품질 감리와 설계 검증 자문에 참여하도록 제도화하여, 설계 의도가 구현 단계에서 끊기지 않게 하는 방향이 필요하다.
2. 변경 통제의 체계화 : 현업의 구두 추가 요구를 차단하고, 요구사항 추적 매트릭스 기반의 변경영향 분석을 거친 경우에만 설계를 바꾸는 절차를 두어야 한다.
3. 대가 산정의 근거화 : 1단계 산출물에서 도출한 기능점수로 2단계 대가를 산정하여, 대략적인 투입 인월 기준에서 벗어나도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 단계별 발주는 설계를 먼저 확정해 범위와 대가, 책임을 명확히 하는 계약 장치임.
- 시사점 : 설계 동결의 실효성은 1단계 산출물의 품질과 2단계 인계 절차에 달려 있으므로, 발주 행정이 아니라 설계 책임의 연속성으로 평가해야 한다.
