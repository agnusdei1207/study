## Ⅰ. 카피레프트 라이선스(Copyleft License)의 개요

- **개념** : 소프트웨어의 사용·수정·배포의 자유를 보장하는 동시에, 이를 기반으로 제작된 모든 파생 저작물에도 동일한 조건과 소스코드 공개를 강제하는 상호주의적 저작권 이용허락 규약.
- **제정 배경 및 필요성** : 상용 상용화 제품에 정적/동적 링크 시 독점적 영업비밀(IP) 소스코드의 강제 공개 위험이 상존하므로 CI/CD 파이프라인 내 SBOM 기반 의존성 스캔과 프로세스 간 IPC/REST 격리 아키텍처 수립 필수.
- **핵심 목적** : 오픈소스 생태계의 사유화 방지, 지식 공유의 지속성 보장 및 자유 소프트웨어의 지속적인 생태계 선순환 유지.

## Ⅱ. 카피레프트 라이선스(Copyleft License)의 법제도 체계 및 핵심 메커니즘

**카피레프트 라이선스**(Copyleft License)는 전염성의 강도에 따라 강력한 카피레프트(Strong Copyleft: GPL, AGPL)와 약한 카피레프트(Weak Copyleft: LGPL, MPL)로 구분되며, 바이너리 배포 또는 네트워크 서비스(SaaS) 제공 시 전체 소스코드 제공 의무 발동 과정을 거쳐 체계적인 법제도적 통제와 기술적 신뢰성을 확보함.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ [ 오픈소스 소프트웨어(OSS) 라이선스 전염성 판정 및 격리 파이프라인 ]         │
└─────────────────────────────────────────────────────────────────────────────┘
  [ 외부 오픈소스 라이브러리 반입 ] ── SBOM(소프트웨어 자재명세서) 등록
                 │
                 ▼
  [ 라이선스 유형 판별 (ScanCode / FOSSID) ]
        ├── 허용적 (Permissive: MIT, Apache) ──> 저작권 및 면책 고지만 유지
        └── 카피레프트 (Copyleft 계열)
                 │
                 ▼
  [ 소프트웨어 배포 형태 및 결합 방식 분석 ]
        ├── (1) 내부망 전용 사용 (비배포) ──> 소스코드 외부 공개 의무 면제
        ├── (2) 외부 바이너리 배포 (온프레미스/임베디드/앱)
        │      ├── GPL: 전체 프로젝트 소스코드 공개 의무 발생
        │      └── LGPL: 동적 링크(Dynamic Link) 적용 시 독점 소스 보호
        └── (3) 클라우드 SaaS 원격 서비스 제공
               ├── AGPL: 네트워크 접속 이용자 대상 백엔드 소스코드 공개 강제
               └── 일반 GPL: 네트워크 서비스 시 배포로 보지 않아 소스 비공개 가능
                 │
                 ▼ (독점 코드 보호를 위한 아키텍처 격리)
  [ 프로세스 분리: REST API / IPC 소켓 통신을 통한 파생 저작물성 배제 ]

[ 결합 방식에 따른 GPL 전염성 파급 구조 ]
┌─────────────────────────┬─────────────────────────┬─────────────────────────┐
│ 정적 링크 (Static Link) │ 동적 링크 (Dynamic Link)│ IPC / REST API 통신     │
├─────────────────────────┼─────────────────────────┼─────────────────────────┤
│ 동일 단일 바이너리 생성 │ 런타임 메모리 주소 공유 │ 독립된 프로세스 간 통신 │
│ ──> GPL 전염 (공개)│ ──> GPL 전염 논란(공개) │ ──> 파생물 아님 (비공개)│
└─────────────────────────┴─────────────────────────┴─────────────────────────┘
```

- **강력한 카피레프트 (Strong)** : GPLv2, GPLv3 - 정적/동적 링크 불문하고 결합된 전체 파생 소프트웨어의 소스코드 공개 의무화.
- **네트워크 카피레프트 (Network)** : AGPLv3 - 바이너리 배포 없이 웹/클라우드 네트워크를 통해 원격 서비스(SaaS) 제공 시에도 소스 공개.
- **약한 카피레프트 (Weak)** : LGPLv2.1, LGPLv3 - 라이브러리 단순 동적 링크 시 독점 코드 보호 허용 (라이브러리 자체 수정 시만 공개).
- **코드 분석** : 패키지 의존성 트리(Dependency Tree) 전수 스캔 - SBOM 명세서 (SPDX / CycloneDX 포맷).
- **결합 검토** : 헤더 인클루드, 함수 직접 호출, 빌드 링크 방식 - 아키텍처 의존성 다이어그램, 링커 스크립트.

## Ⅲ. 카피레프트 라이선스(Copyleft License)의 세부 규정 및 국내외 제도 비교 분석

| 비교 항목 | 강력한 카피레프트 (GPL/AGPL) | 약한 카피레프트 (LGPL/MPL) | 허용적 라이선스 (MIT/Apache) |
|---|---|---|---|
| **철학적 목표** | 소프트웨어 자유 보장 (반독점) | 자유 보장과 상용화의 타협 | 제약 없는 자유로운 이용 및 확산 |
| **전염성 범위** | 결합된 전체 파생 소프트웨어 | 동적 링크 시 라이브러리/파일 한정 | 전염성 전무 (독점 라이선스 허용) |
| **SaaS 소스 공개**| AGPL: 공개 의무 / GPL: 면제 | 면제 | 면제 |
| **특허 조항** | GPLv3/AGPL: 특허 보복 조항 명시 | LGPLv3: 특허 조항 포함 | Apache 2.0: 명시 / MIT: 묵시적 |
| **기업 수용성** | 엄격한 관리 필요 (도입 기피) | 아키텍처 분리 시 제한적 수용 | 가장 선호됨 (자유로운 상용화) |

- **제도적 시사점** : 카피레프트 라이선스(Copyleft License)는 상기 비교 지표를 바탕으로 법적 의무 준수와 비즈니스 연속성 간의 균형을 확보하고, 규제 환경 변화에 선제적으로 대응할 수 있는 아키텍처 및 거버넌스 체계를 확립해야 함.

## Ⅳ. 카피레프트 라이선스(Copyleft License)의 주요 한계점 및 해결 방안

- **개발자의 무단 카피레프트 임포트로 인한 기업 독점 코드 오염(GPL 감염)** :
  - **한계점** : 개발자의 무단 카피레프트 라이브러리 임포트로 인해 기업의 핵심 독점 코드가 GPL에 오염(Contamination)되어 기업 가치 훼손.
  - **해결 방안** : CI/CD 파이프라인 상에 블랙덕(Black Duck) 등 오픈소스 라이선스 검사기를 연동하여 PR(Pull Request) 시 GPL/AGPL 자동 빌드 실패 처리.
- **SaaS 클라우드 환경에서 AGPL 컴포넌트 사용 시 백엔드 코드 공개 요구** :
  - **한계점** : SaaS 클라우드 환경에서 AGPL 라이브러리 사용 시 원격 API 이용자에게도 백엔드 비즈니스 로직 소스코드 공개 요구 발생.
  - **해결 방안** : AGPL 소프트웨어의 코드 레벨 직접 수정을 전면 금지하고, 표준 퍼블릭 API를 경유하는 완전 독립된 마이크로서비스(Sidecar 패턴)로 망 격리.
- **LGPL 동적 링크 시 라이브러리 교체 수단(Relink) 미제공 규약 위반** :
  - **한계점** : LGPL 라이브러리를 동적 링크하더라도 이용자가 해당 라이브러리를 교체하여 리링크(Relink)할 수 있는 수단 미제공 시 규약 위반.
  - **해결 방안** : 최종 배포 시 오브젝트 파일(.o) 또는 동적 링크 라이브러리(.so/.dll) 분리 배포를 보장하고 Docker 컨테이너 레벨 교체 가이드라인 문서화.

## Ⅴ. 카피레프트 라이선스(Copyleft License) 정착 및 실효성 확보를 위한 기술사적 제언

독점 지적재산권을 보호하고 오픈소스의 혜택을 극대화하기 위하여 SBOM 기반 거버넌스를 구축하고, 카피레프트 모듈을 REST/IPC로 격리하는 클린 아키텍처 수립.

- **도입 통제 관점의 고도화 및 실무 전환** : 개발자 임의 npm/Maven 다운로드의 한계와 비효율을 탈피하고, 전사 승인된 OSS 레포지토리(Nexus) 한정을 체계적으로 도입·적용하여 실무적 신뢰성과 거버넌스 실효성을 극대화해야 함.
- **결합 구조 관점의 고도화 및 실무 전환** : 정적 링크로 단일 바이너리 결합의 한계와 비효율을 탈피하고, 네트워크 API 및 IPC 기반 완전 프로세스 격리를 체계적으로 도입·적용하여 실무적 신뢰성과 거버넌스 실효성을 극대화해야 함.
- **컴플라이언스 관점의 고도화 및 실무 전환** : 출시 전 수작업 라이선스 조사의 한계와 비효율을 탈피하고, CI/CD 자동화 SBOM 린팅 및 PR 차단을 체계적으로 도입·적용하여 실무적 신뢰성과 거버넌스 실효성을 극대화해야 함.
