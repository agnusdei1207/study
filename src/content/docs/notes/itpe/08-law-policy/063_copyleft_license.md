## 30초 인출

- 본질: **카피레프트 라이선스** 는 저작권(Copyright)의 독점성에 반대하여 소프트웨어의 자유로운 사용, 복제, 수정 및 재배포를 보장하되, 이를 활용한 2차적 저작물에도 동일한 라이선스와 소스코드 공개 조건을 강제하는 상호주의 오픈소스 라이선스
- 메커니즘: 전염성의 강도에 따라 강력한 카피레프트(Strong Copyleft: GPL, AGPL)와 약한 카피레프트(Weak Copyleft: LGPL, MPL)로 구분되며, 바이너리 배포 또는 네트워크 서비스(SaaS) 제공 시 전체 소스코드 제공 의무 발동
- 통찰: 상용 상용화 제품에 정적/동적 링크 시 독점적 영업비밀(IP) 소스코드의 강제 공개 위험이 상존하므로 CI/CD 파이프라인 내 SBOM 기반 의존성 스캔과 프로세스 간 IPC/REST 격리 아키텍처 수립 필수

<details><summary>핵심 용어</summary>

- **카피레프트 (Copyleft)** : 자유 소프트웨어 재단(FSF)의 리처드 스톨먼이 제창한 개념으로, 저작물의 자유로운 공유와 파생물의 동일 라이선스 적용을 의무화한 조항.
- **GPL (General Public License)** : FSF가 만든 대표적 강력한 카피레프트 라이선스로, 수정 배포 시 전체 소스코드 공개 및 동일 라이선스 적용 강제.
- **AGPL (Affero GPL)** : 전통적 배포(Distribution) 외에 네트워크를 통한 서비스(SaaS/Cloud) 제공 시에도 백엔드 소스코드 공개 의무를 부과하는 라이선스.
- **LGPL (Lesser GPL)** : 라이브러리 동적 링크(Dynamic Link) 시 독점 소프트웨어의 소스코드 공개 의무를 면제하여 상용 소프트웨어 결합을 유연하게 허용한 라이선스.
- **MPL (Mozilla Public License)** : 파일 단위 카피레프트 라이선스로, 수정한 해당 파일만 소스를 공개하고 결합된 다른 파일은 독점 라이선스 유지가 가능.
- **파생 저작물 (Derivative Works)** : 원저작물을 번역, 편곡, 변형, 각색 또는 결합하여 작성한 새로운 창작물.

</details>

## 2~4교시 예상문제 (25점)

> 오픈소스 소프트웨어(OSS) 거버넌스에서 핵심적인 '카피레프트(Copyleft) 라이선스'의 개념과 철학을 설명하고, 강력한 카피레프트(GPL/AGPL)와 약한 카피레프트(LGPL/MPL)의 전염성 범위 및 의무 요건을 비교한 후, 기업의 독점 지적재산권(IP) 보호를 위한 엔지니어링 컴플라이언스 통제 방안을 논하시오. (기출·제122회 1교시 4번 변형·25점)

## 2~4교시 25점 답안

## Ⅰ. 카피레프트 라이선스의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **카피레프트 라이선스** 는 소프트웨어의 사용·수정·배포의 자유를 보장하는 동시에, 이를 기반으로 제작된 모든 파생 저작물에도 동일한 조건과 소스코드 공개를 강제하는 상호주의적 저작권 이용허락 규약 |
| 목적 | 오픈소스 생태계의 사유화 방지, 지식 공유의 지속성 보장 및 자유 소프트웨어의 지속적인 생태계 선순환 유지 |

## Ⅱ. 카피레프트 라이선스의 분류 체계 및 전염성 특징

| 구분 | 주요 라이선스 | 전염성 강도 및 소스코드 공개 트리거 |
|---|---|---|
| **강력한 카피레프트 (Strong)** | GPLv2, GPLv3 | 정적/동적 링크 불문하고 결합된 전체 파생 소프트웨어의 소스코드 공개 의무화 |
| **네트워크 카피레프트 (Network)**| AGPLv3 | 바이너리 배포 없이 웹/클라우드 네트워크를 통해 원격 서비스(SaaS) 제공 시에도 소스 공개 |
| **약한 카피레프트 (Weak)** | LGPLv2.1, LGPLv3 | 라이브러리 단순 동적 링크 시 독점 코드 보호 허용 (라이브러리 자체 수정 시만 공개) |
| **파일 단위 카피레프트 (File)** | MPL 2.0, CDDL | 수정한 특정 파일 단위만 소스 공개, 별도 신규 파일로 작성된 결합 코드는 독점 유지 가능 |

## Ⅲ. 오픈소스 라이선스 컴플라이언스 및 소스코드 공개 의무 판정 프로세스

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ [ 오픈소스 소프트웨어(OSS) 라이선스 전염성 판정 및 격리 파이프라인 ]         │
└─────────────────────────────────────────────────────────────────────────────┘
  [ 외부 오픈소스 라이브러리 반입 ] ── SBOM(소프트웨어 자재명세서) 등록
                 │
                 ▼
  [ 라이선스 유형 판별 (ScanCode / FOSSID) ]
        ├── 허용적 (Permissive: MIT, Apache) ──> 저작권 및 면책 고지만 유지
        └── 카피레프트 (Copyleft 계열)
                 │
                 ▼
  [ 소프트웨어 배포 형태 및 결합 방식 분석 ]
        ├── (1) 내부망 전용 사용 (비배포) ──> 소스코드 외부 공개 의무 면제
        ├── (2) 외부 바이너리 배포 (온프레미스/임베디드/앱)
        │      ├── GPL: 전체 프로젝트 소스코드 공개 의무 발생
        │      └── LGPL: 동적 링크(Dynamic Link) 적용 시 독점 소스 보호
        └── (3) 클라우드 SaaS 원격 서비스 제공
               ├── AGPL: 네트워크 접속 이용자 대상 백엔드 소스코드 공개 강제
               └── 일반 GPL: 네트워크 서비스 시 배포로 보지 않아 소스 비공개 가능
                 │
                 ▼ (독점 코드 보호를 위한 아키텍처 격리)
  [ 프로세스 분리: REST API / IPC 소켓 통신을 통한 파생 저작물성 배제 ]
```

```text
[ 결합 방식에 따른 GPL 전염성 파급 구조 ]
┌─────────────────────────┬─────────────────────────┬─────────────────────────┐
│ 정적 링크 (Static Link) │ 동적 링크 (Dynamic Link)│ IPC / REST API 통신     │
├─────────────────────────┼─────────────────────────┼─────────────────────────┤
│ 동일 단일 바이너리 생성 │ 런타임 메모리 주소 공유 │ 독립된 프로세스 간 통신 │
│ ──> GPL 전염 (100% 공개)│ ──> GPL 전염 논란(공개) │ ──> 파생물 아님 (비공개)│
└─────────────────────────┴─────────────────────────┴─────────────────────────┘
```

| 검증 단계 | 주요 점검 항목 | 공학적 준수 산출물 |
|---|---|---|
| **코드 분석** | 패키지 의존성 트리(Dependency Tree) 전수 스캔 | SBOM 명세서 (SPDX / CycloneDX 포맷) |
| **결합 검토** | 헤더 인클루드, 함수 직접 호출, 빌드 링크 방식 | 아키텍처 의존성 다이어그램, 링커 스크립트 |
| **배포 검증** | 바이너리 패키징 내 소스코드 다운로드 링크 확인 | 오픈소스 고지문(Notice.txt), 라이선스 사본 |
| **격리 조치** | AGPL/GPL 모듈의 마이크로서비스(MSA) 분리 | 독립 컨테이너 이미지, gRPC/REST API 명세서 |

## Ⅳ. 강력/약한 카피레프트와 허용적 라이선스 비교

| 비교 항목 | 강력한 카피레프트 (GPL/AGPL) | 약한 카피레프트 (LGPL/MPL) | 허용적 라이선스 (MIT/Apache) |
|---|---|---|---|
| **철학적 목표** | 소프트웨어 자유 보장 (반독점) | 자유 보장과 상용화의 타협 | 제약 없는 자유로운 이용 및 확산 |
| **전염성 범위** | 결합된 전체 파생 소프트웨어 | 동적 링크 시 라이브러리/파일 한정 | 전염성 전무 (독점 라이선스 허용) |
| **SaaS 소스 공개**| AGPL: 공개 의무 / GPL: 면제 | 면제 | 면제 |
| **특허 조항** | GPLv3/AGPL: 특허 보복 조항 명시 | LGPLv3: 특허 조항 포함 | Apache 2.0: 명시 / MIT: 묵시적 |
| **기업 수용성** | 엄격한 관리 필요 (도입 기피) | 아키텍처 분리 시 제한적 수용 | 가장 선호됨 (자유로운 상용화) |
| **대표 소프트웨어**| Linux 커널, Git, MongoDB(SSPL) | FFmpeg, 7-Zip, Mozilla Firefox | React, Kubernetes, Nginx |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 개발자의 무단 카피레프트 라이브러리 임포트로 인해 기업의 핵심 독점 코드가 GPL에 오염(Contamination)되어 기업 가치 훼손 | CI/CD 파이프라인 상에 블랙덕(Black Duck) 등 오픈소스 라이선스 검사기를 연동하여 PR(Pull Request) 시 GPL/AGPL 자동 빌드 실패 처리 |
| SaaS 클라우드 환경에서 AGPL 라이브러리 사용 시 원격 API 이용자에게도 백엔드 비즈니스 로직 소스코드 공개 요구 발생 | AGPL 소프트웨어의 코드 레벨 직접 수정을 전면 금지하고, 표준 퍼블릭 API를 경유하는 완전 독립된 마이크로서비스(Sidecar 패턴)로 망 격리 |
| LGPL 라이브러리를 동적 링크하더라도 이용자가 해당 라이브러리를 교체하여 리링크(Relink)할 수 있는 수단 미제공 시 규약 위반 | 최종 배포 시 오브젝트 파일(.o) 또는 동적 링크 라이브러리(.so/.dll) 분리 배포를 보장하고 Docker 컨테이너 레벨 교체 가이드라인 문서화 |

## Ⅵ. 제언

독점 지적재산권을 보호하고 오픈소스의 혜택을 극대화하기 위하여 SBOM 기반 거버넌스를 구축하고, 카피레프트 모듈을 REST/IPC로 격리하는 클린 아키텍처 수립.

```text
[ 기업 독점 비즈니스 로직 (Proprietary IP: 비공개) ]
                 │
                 ▼ (gRPC / REST API 통신) ── IPC 프로세스 완전 분리
[ 오픈소스 카피레프트 모듈 (GPL/AGPL 컨테이너: 오픈소스 공개) ]
                 │
                 ▼
[ CI/CD 오픈소스 컴플라이언스 게이트웨이 ]
    ├── 1단계: SBOM 자동 추출 및 라이선스 위험 등급 분류
    ├── 2단계: 카피레프트 직접 링크 탐지 시 빌드 중단
    └── 3단계: 고지문(Open Source Notice) 자동 생성 및 패키징
```

| 구분 | 무통제 오픈소스 도입 관행 | 제언: SBOM & 프로세스 격리 거버넌스 |
|---|---|---|
| **도입 통제** | 개발자 임의 npm/Maven 다운로드 | 전사 승인된 OSS 레포지토리(Nexus) 한정 |
| **결합 구조** | 정적 링크로 단일 바이너리 결합 | 네트워크 API 및 IPC 기반 완전 프로세스 격리 |
| **컴플라이언스**| 출시 전 수작업 라이선스 조사 | CI/CD 자동화 SBOM 린팅 및 PR 차단 |
| **의무 이행** | 소스 미공개로 저작권 소송 피소 | 투명한 고지문 부착 및 분리된 OSS 소스 공개 |
