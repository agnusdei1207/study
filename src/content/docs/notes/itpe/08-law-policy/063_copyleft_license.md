## 연관 키워드

- 카피레프트 라이선스(Copyleft License), GPL, AGPL, LGPL, MPL
- 전염성, 파생 저작물, 정적 링크, 동적 링크, 프로세스 격리
- SBOM(Software Bill of Materials), SPDX, 허용적 라이선스, 라이선스 스캔, 네트워크 카피레프트

## Ⅰ. 카피레프트 라이선스(Copyleft License)의 개요

- 핵심 요약 : 소프트웨어의 자유를 보장하는 대가로 파생 저작물에도 같은 조건의 소스코드 공개를 요구하는 상호주의 라이선스.
- 개념 : 소프트웨어의 사용·수정·배포 자유를 보장하면서, 이를 기반으로 만든 파생 저작물에도 같은 조건을 이어 주도록 강제하는 **카피레프트 라이선스**(Copyleft License).
- 배경 및 필요성 : 오픈소스를 상용 제품에 결합하거나 SaaS(Software as a Service)로 제공할 때 **전염성**으로 인해 독점 소스코드가 공개될 위험이 있음. 따라서 **소프트웨어 자재명세서**(SBOM, Software Bill of Materials)로 의존성을 파악하고, 독점 모듈을 IPC(Inter-Process Communication)나 REST API로 분리하는 설계를 개발 초기에 해야 함.
- 주요 목적 : 오픈소스 생태계가 사유화되지 않도록 막고, 공유된 지식이 지속적으로 순환하도록 보장.

## Ⅱ. 카피레프트 라이선스(Copyleft License)의 특징 및 장점

- 핵심 요약 : 전염성의 강도와 발동 조건에 따라 세 유형으로 나뉘며, 공개 범위를 통제할 수 있다는 점이 특징.

1. **강한 카피레프트** (GPL, GNU General Public License) : 결합된 전체 파생 소프트웨어의 소스코드 공개 의무 → 자유 전파를 가장 강하게 보장.
2. **네트워크 카피레프트** (AGPL, GNU Affero General Public License) : 바이너리 배포가 없어도 네트워크 사용자에게 서비스하면 소스 공개 의무 발생 → 클라우드 환경의 무임승차 방지.
3. **약한 카피레프트** (LGPL, GNU Lesser General Public License 및 MPL, Mozilla Public License) : 라이브러리나 파일 단위로만 공개 범위가 한정 → 독점 코드와의 분리 설계를 전제로 상용화와 공존.

## Ⅲ. 카피레프트 라이선스(Copyleft License)의 구조 (흐름)

- 핵심 요약 : 의존성 등록에서 배포 형태 분석을 거쳐 결합 방식을 판정하는 순차 구조로, 결합 방식이 의무의 범위를 결정함.

```text
[ 라이선스 판정 파이프라인 ]

외부 오픈소스 반입
   ↓
SBOM 등록 및 라이선스 판별
   ↓
배포 형태 분석
   ↓
(1) 내부 전용: 공개 의무 없음
(2) 바이너리 배포: GPL 전체 공개 위험
(3) SaaS 제공: AGPL 공개 위험
```

```text
[ 결합 방식별 전염 범위 ]

정적 링크
  → 단일 바이너리 생성, 전염 가능성 큼
동적 링크
  → 런타임 결합, 해석 논란 존재
IPC / REST API
  → 독립 프로세스, 파생물 아님으로 보는 경향
```

## Ⅳ. 카피레프트 라이선스와 허용적 라이선스의 비교

- 핵심 요약 : 카피레프트는 자유의 전파를, 허용적 라이선스는 상용 결합의 자유를 우선하며, 두 방식의 차이는 공개 범위에서 갈림.

| 비교 축 | 강한 카피레프트 (GPL, AGPL) | 약한 카피레프트 (LGPL, MPL) | 허용적 라이선스 (MIT, Apache) |
| --- | --- | --- | --- |
| 철학 | 파생물 전체의 자유 보장 | 라이브러리 단위의 자유와 상용화 조화 | 제약 없는 이용과 확산 |
| 공개 범위 | 결합된 전체 프로젝트 | 해당 라이브러리 또는 파일 | 공개 의무 없음 |
| SaaS 제공 | AGPL은 공개 의무, GPL은 배포로 보지 않음 | 공개 의무 없음 (수정 파일 제외) | 공개 의무 없음 |
| 기업 수용성 | 엄격한 관리 필요 | 분리 설계 시 수용 가능 | 가장 선호됨 |

- 선택 기준 : 자사 코드를 공개할 의사가 없으면 강한 카피레프트를 피하고, 라이브러리 교체 가능성이 필요하면 약한 카피레프트를 우선 검토함.

## Ⅴ. 카피레프트 라이선스의 한계와 방안

- 핵심 요약 : 무단 도입에 따른 독점 코드 오염, AGPL의 네트워크 공개 의무, LGPL의 교체 수단 미제공이 주요 한계이며, 자동 검사와 아키텍처 격리로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 무단 카피레프트 도입 | 개발자가 승인 없이 GPL 라이브러리를 가져와 독점 코드가 오염 | CI/CD(Continuous Integration/Continuous Delivery)에 라이선스 스캐너를 연동해 GPL, AGPL 검출 시 빌드 실패 처리 | 승인 외 라이선스 검출 건수 |
| SaaS에서 AGPL 사용 | 원격 서비스 이용자에게 백엔드 소스 공개 요구 발생 | AGPL 코드 직접 수정 금지, 표준 API로 분리한 독립 서비스 구성 | AGPL 컴포넌트 격리율 |
| LGPL 교체 수단 미제공 | 이용자가 라이브러리를 교체해 재링크할 수 없으면 규약 위반 | 오브젝트 파일 또는 공유 라이브러리를 분리 배포 | 교체 가능 배포 여부 점검 |

## Ⅵ. 카피레프트 라이선스의 실효성 확보를 위한 기술사적 제언

- 핵심 요약 : 승인된 저장소와 자동 점검으로 도입 경로를 한정하고, 카피레프트 모듈은 프로세스 경계로 격리하는 거버넌스.

개발자가 임의로 패키지를 내려받지 못하도록 사내 승인 저장소를 도입 통로로 두고, 그 저장소에서 들어오는 모든 의존성은 SBOM에 기록되어야 한다. 카피레프트 모듈은 REST API나 IPC로만 호출하도록 아키텍처 경계를 정하고, 그 경계를 넘는 호출은 설계 검토에서 차단한다. 라이선스 해석은 개별 사안마다 법무 검토가 필요하므로, 기술 점검과 법무 판단의 역할을 문서로 나누어 두는 것이 안전하다.

## Ⅶ. 결론

- 핵심 요약 : 카피레프트 라이선스는 자유를 지키는 장치이면서 동시에 결합 설계를 강제하는 규율임.
- 시사점 : 라이선스 관리는 출시 직전의 점검이 아니라 의존성 도입 시점부터 이어지는 설계 문제로 다뤄야 함.
