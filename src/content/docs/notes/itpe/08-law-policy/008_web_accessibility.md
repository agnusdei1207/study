## 30초 인출

- 본질: **웹 접근성 (Web Accessibility)** 은 장애인과 고령자를 포함한 모든 사용자가 신체적·환경적 조건에 구애받지 않고 웹 콘텐츠와 기능을 동등하게 인식하고 활용할 수 있도록 보장하는 소프트웨어 설계 표준
- 메커니즘: POUR 4대 원칙(인식의 용이성·운용의 용이성·이해의 용이성·견고성)을 준수하여 시맨틱 HTML5 및 WAI-ARIA 태그를 적용하고 스크린리더 및 키보드 단독 조작 지원
- 통찰: 단순 자동화 진단 도구 통과만으로는 동적 비동기 웹(SPA)의 포커스 소실과 스크린리더 맥락 단절을 방지할 수 없으므로 컴포넌트 주도 개발(CDD) 단계의 접근성 테스트와 장애 당사자 실사용 평가 체계 구축 필수

<details><summary>핵심 용어</summary>

- **웹 접근성 (Web Accessibility)** : 어떠한 사용자도 웹 사이트에서 제공하는 정보에 접근하고 상호작용하는 데 차별을 받지 않도록 보장하는 상태.
- **POUR 원칙** : W3C WCAG의 핵심 프레임워크인 인식(Perceivable)·운용(Operable)·이해(Understandable)·견고성(Robust).
- **KWCAG 2.2** : 한국산업표준(KS X 3261)으로 제정된 한국형 웹 콘텐츠 접근성 국가 지침.
- **WAI-ARIA** : HTML의 시맨틱 한계를 보완하여 동적 웹 애플리케이션의 역할(Role), 상태(State), 속성(Property)을 보조기술에 전달하는 웹 표준.
- **정보통신접근성 품질인증** : 지능정보화 기본법 제47조 및 장애인차별금지법에 따라 접근성 표준을 충족한 사이트에 인증마크를 부여하는 제도.

</details>

## 2~4교시 예상문제 (25점)

> 장애인차별금지법 및 지능정보화 기본법에 따른 웹 접근성(Web Accessibility)의 개념과 POUR 4대 원칙을 설명하고, 최신 SPA(Single Page Application) 환경에서의 기술적 접근성 확보 방안과 품질인증 심사 프로세스를 논하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 웹 접근성의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **웹 접근성** 은 장애인, 고령자 등 정보 취약계층이 웹 사이트 이용 시 비장애인과 동등하게 정보를 인식하고 제어할 수 있도록 보장하는 기술적·법적 설계 지침 |
| 목적 | 디지털 정보 격차 해소, 보편적 사용자 경험(UX) 제공 및 법적 컴플라이언스 준수 |

## Ⅱ. 웹 접근성 POUR 4대 원칙 및 기술적 특징

| 4대 원칙 | 핵심 의미 및 지침 항목 | 프런트엔드 엔지니어링 구현 특징 |
|---|---|---|
| **1. 인식의 용이성 (Perceivable)** | 정보와 사용자 인터페이스 요소를 인지할 수 있도록 제공 | **대체 텍스트** : 비텍스트 콘텐츠 `alt` 속성 제공<br />**자막 제공** : 멀티미디어 동영상에 동기화된 자막/수어<br />**색상 독립성** : 명도 대비 4.5:1 이상 확보 (대형 3:1) |
| **2. 운용의 용이성 (Operable)** | 인터페이스 구성 요소를 원활하게 조작 가능하도록 보장 | **키보드 접근성** : 모든 기능을 마우스 없이 탭 키로 접근<br />**초점 이동** : 논리적 초점 순서 및 가시적 초점 링 표시<br />**조작 시간** : 시간제한 연장 기능, 광과민성 발작 예방 |
| **3. 이해의 용이성 (Understandable)** | 콘텐츠와 인터페이스 작동 방식을 쉽게 이해하도록 설계 | **기본 언어 표기** : `html lang="ko"` 속성 명시<br />**예측 가능성** : 초점 획득 시 맥락 자동 변경(팝업) 금지<br />**입력 오류 방지** : 오류 위치 텍스트 안내 및 수정 기회 |
| **4. 견고성 (Robust)** | 보조기술(Screen Reader)을 포함한 다양한 브라우저 호환 | **마크업 유효성** : 태그 열고 닫음, 중복 속성 배제<br />**WAI-ARIA 적용** : 커스텀 UI의 `role`, `aria-live` 속성 부여 |

## Ⅲ. 웹 접근성 진단 및 품질 인증 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 웹 접근성 진단 및 엔드투엔드 품질인증 심사 파이프라인 ]             │
└────────────────────────────────────────────────────────────────────────┘

 [ 웹 서비스 기획/디자인 ] ── 명도 대비 검증, 건너뛰기 링크(Skip Navigation) 설계
           │
           ▼
 [ 프런트엔드 개발 단계 ] ── 시맨틱 마크업, WAI-ARIA 속성 및 키보드 이벤트 핸들러
           │
           ▼
 [ 1단계: 전문가 자동 평가 ] ── K-WAH, axe-core, Lighthouse 자동 진단 (신택스 오류 검출)
           │
           ▼
 [ 2단계: 전문가 수동 평가 ] ── 키보드 단독 조작, 화면 낭독기(NVDA/센스리더) 음성 검증
           │
           ▼
 [ 3단계: 사용자 체감 평가 ] ── 전맹·저시력·지체·뇌병변 장애 당사자 과업 수행(Task Test)
           │
           ▼
 [ 접근성 품질인증 심사 ] ──(합격 기준: 95점 이상)──> [ 품질인증 마크(WA) 획득 및 갱신 ]
```

| 심사 단계 | 주요 진단 내용 | 핵심 검증 도구 및 산출물 |
|---|---|---|
| **전문가 자동 심사** | HTML 문법 유효성, 대체 텍스트 누락, 명도 대비 자동 검사 | axe DevTools, Lighthouse, 자동 검사 리포트 |
| **전문가 수동 심사** | 키보드 트랩 탈출 여부, 포커스 순서, 프레임 제목 제공 | NVDA, 센스리더, VoiceOver, 수동 진단표 |
| **사용자 체감 심사** | 시각·지체 장애인 당사자의 실제 로그인, 결제 등 과업 완수 | 장애 당사자 실사용 테스트 결과 보고서 |
| **사후 유지 관리** | 정기 배포 후 회귀 결함 모니터링 및 인증 연장 심사 | 연례 사후 심사 보고서, 결함 조치 확인서 |

## Ⅳ. KWCAG 2.2와 W3C WCAG 2.2 비교

| 비교 항목 | 한국형 KWCAG 2.2 (KS X 3261) | 국제 표준 W3C WCAG 2.2 |
|---|---|---|
| **제정 주체** | 과학기술정보통신부, 국립전파연구원 | W3C WAI (Web Accessibility Initiative) |
| **체계 구성** | 4대 원칙 24개 검사 항목 | 4대 원칙 13개 지침 86개 성공 기준 (Level A/AA/AAA) |
| **타깃 플랫폼** | 국내 행정·공공기관 및 민간 웹사이트 | 글로벌 웹, 모바일, 디지털 기기 전반 |
| **모바일 대응** | 모바일 터치 타깃 크기(9mm) 규정 준용 | 최소 타깃 크기 24x24 CSS 픽셀 등 구체적 명시 |
| **인증 연계** | 국내 공인 정보통신접근성 품질인증 심사 기준 | 글로벌 웹 접근성 소송 대응 및 적합성 평가 기준 |
| **포커스 통제** | 초점 이동 및 가시적 표시 요구 | 가시적 초점(Focus Appearance) 최소 영역 및 명도 공식화 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 리액트/뷰 기반 SPA 환경에서 라우팅 변경 시 스크린리더가 페이지 갱신을 인지하지 못하는 한계 | 라우터 이동 시 `aria-live="polite"` 알림 영역을 활용해 페이지 타이틀을 음성 출력하고 포커스를 메인 콘텐츠로 자동 이동 |
| 자동화 검사 통과 위주의 형식적 인증 획득으로 인해 실제 장애인의 과업 완수율 저하 | CI/CD 파이프라인 내 Cypress 기반 키보드 E2E 테스트 자동화 및 장애인 사용자 패널 상시 검증 체계 구축 |

## Ⅵ. 제언

디자인 시스템 단계부터 접근성 토큰을 내재화(Design-System-in-Accessibility)하고, 빌드 파이프라인에 접근성 정적 분석 및 키보드 자동 테스트를 결합하는 Shift-Left 전략 필요.

```text
[ Figma 디자인 컴포넌트 ]
    ├── 명도 대비 토큰 자동 검증 (Contrast Checker Plugin)
    └── 초점 이동 순서(Focus Order) 주석 정의
          │
          ▼
[ Git 커밋 및 CI 파이프라인 ]
    ├── Step 1: ESLint-plugin-jsx-a11y 정적 린팅
    ├── Step 2: Storybook Axe 자동 접근성 스캔
    └── Step 3: Playwright/Cypress 키보드 탐색 E2E 검증
          │
          ▼
[ 배포 후 무결점 웹 접근성 유지 ] ──> [ 모니터링 대시보드 경보 ]
```

| 구분 | 기존 사후 인증 심사 방식 | 제언: 디자인 시스템 연계 Shift-Left |
|---|---|---|
| **검증 시점** | 개발 완료 후 출시 직전 수동 진단 | 디자인 및 코드 커밋 시 실시간 자동 검증 |
| **비용 및 공수** | 결함 발견 시 전체 DOM 재구조화로 고비용 | 컴포넌트 단위 사전 차단으로 유지보수 최소화 |
| **동적 SPA 지원** | 렌더링 후 상태 변화 추적 곤란 | Storybook 상태별 ARIA 실시간 유효성 평가 |
| **접근성 연속성** | 주기적 인증 시점에만 반짝 개선 | 배포 파이프라인 결합으로 품질 상시 유지 |
