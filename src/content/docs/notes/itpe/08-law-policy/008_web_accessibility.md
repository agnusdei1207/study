## 연관 키워드

- 웹 접근성, KWCAG 2.2, WCAG 2.2, POUR
- 대체 텍스트, 키보드 접근성, 명도 대비, 스크린리더
- 자동 검사, 수동 검사, 장애 당사자 과업 평가

## Ⅰ. 웹 접근성의 개요

- 핵심 요약 : 장애 여부나 사용 환경에 관계없이 **웹 접근성**(Web Accessibility)을 확보해 웹의 정보와 기능을 인식·조작·이해할 수 있도록 설계하는 품질 특성.
- 개념 : 시각·청각·운동·인지적 제약을 고려해 콘텐츠와 인터페이스의 이용 장벽을 제거하는 설계·개발·평가 활동.
- 배경 및 필요성 : 웹 서비스가 생활 필수 수단이 되면서 장애인과 고령자 등의 정보 접근권을 보장할 필요가 커짐. 국내에서는 지능정보화 기본법이 웹 접근성 보장을 규정하고 있음.
- 주요 목적 : 동등한 과업 수행, 정보 격차 완화, 이용성과 법·표준 대응 수준 향상.

## Ⅱ. 웹 접근성의 특징 및 장점

- 핵심 요약 : **POUR**(Perceivable, Operable, Understandable, Robust) 4대 원칙을 구현 요소에 연결해 장애인뿐 아니라 다양한 기기·환경 이용자의 경험을 개선.

1. 인식 가능(Perceivable) : 이미지 **대체 텍스트**와 자막을 제공 → 감각 수단이 달라도 정보 획득 가능.
2. 운용 가능(Operable) : **키보드 접근성**과 명확한 초점 표시 제공 → 마우스 사용이 어려운 이용자의 기능 수행 지원.
3. 이해 가능(Understandable) : 예측 가능한 동작과 입력 오류 안내 제공 → 입력 실수와 인지 부담 감소.
4. 견고성(Robust) : 의미 있는 마크업과 보조기술 호환성 확보 → 브라우저와 스크린리더 간 이용 가능성 향상.
5. 다중 평가 : **자동 검사**에 수동 탐색과 당사자 과업 평가를 더함 → 도구가 놓치는 실제 사용 장애 발견.

## Ⅲ. 웹 접근성의 구조와 평가 흐름

- 핵심 요약 : POUR 원칙을 구현 요소로 바꾸고, 자동·수동 검사와 당사자 과업 검증을 거쳐 개선을 반복하는 과정.

```text
[ POUR 원칙과 구현 요소 ]

인식 가능 → 대체 텍스트·자막·명도 대비
운용 가능 → 키보드·초점·시간 조절
이해 가능 → 일관된 탐색·입력 오류 안내
견고성   → 의미 있는 마크업·보조기술 호환
```

```text
[ 평가 반복 흐름 ]

설계 기준 선정
      ↓
컴포넌트 구현
      ↓
자동 검사 → 수동 탐색·보조기술 시험
      ↓
장애 당사자 과업 평가
      ↓
결함 수정 (설계 기준 선정으로 복귀)
```

- 시맨틱 HTML을 먼저 사용하고, 기본 요소만으로 의미가 전달되지 않을 때 WAI-ARIA(Web Accessibility Initiative – Accessible Rich Internet Applications)를 보완적으로 적용.
- 색상 대비와 타깃 크기 등 수치 기준은 적용하는 표준, 성공 기준, 적합 수준을 함께 확인.
- 자동 도구 통과만으로 모든 이용자의 과업 완수를 입증할 수 없으므로 키보드, 스크린리더, 실사용 평가를 병행.

## Ⅳ. KWCAG 2.2와 WCAG 2.2의 비교

- 핵심 요약 : 국가표준 **KWCAG 2.2**(한국형 웹 콘텐츠 접근성 지침, Korean Web Content Accessibility Guidelines)와 WCAG 2.2(Web Content Accessibility Guidelines)는 같은 접근성 원칙을 공유하지만 제정 주체와 적용 문맥이 달라 기준을 구분해야 함.

| 비교 항목 | KWCAG 2.2 | WCAG 2.2 |
| --- | --- | --- |
| 제정·관리 | 국가표준(KS X OT0003:2022), 2022년 12월 제정 | W3C 권고(Recommendation), 2023년 10월 발행 |
| 기반 | 국내 웹 환경과 검사 항목 체계 | POUR 4대 원칙과 검증 가능한 성공 기준 |
| 활용 | 국내 평가·개발·품질 기준 | 국제적 설계·적합성 평가 기준 |
| 실무 유의 | 대상 기관과 적용 근거를 국내 법령에서 확인 | 목표 적합 수준(A/AA/AAA)과 해당 성공 기준 확인 |

- 법적 의무, 기술 표준, 품질인증은 서로 다른 개념이므로 서비스별 적용 근거를 구분해 기록.

## Ⅴ. 웹 접근성의 한계와 방안

- 핵심 요약 : 동적 UI의 초점 소실, 자동 검사의 사각지대, 일회성 인증의 노후화를 컴포넌트 규칙과 실사용 평가로 보완.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 동적 화면의 초점 소실 | 경로·모달 변경 시 보조기술이 맥락을 잃음 | 제목·초점·상태 알림을 사용자 흐름에 맞게 관리 | 키보드 과업 성공률 |
| 자동 검사의 한계 | 대체 텍스트의 적절성과 논리적 초점은 자동 판정이 어려움 | 수동 검사와 스크린리더 시험 병행 | 수동 검사에서 발견된 결함 수 |
| 색상 의존 표현 | 색상만으로 상태를 나타내면 구분이 어려움 | 텍스트·아이콘을 함께 쓰고 명도 대비 점검 | 대비 실패 건수 |
| 일회성 평가 | 기능 변경 후 기존 인증 결과가 노후화 | 배포 전 회귀 검사와 정기 당사자 평가 | 재발 결함률 |

## Ⅵ. 웹 접근성에 대한 기술사적 제언

- 핵심 요약 : 접근성은 출시 직전 검사가 아니라 디자인 시스템과 개발 및 운영 전 단계의 품질 기준으로 내재화해야 함.

1. 공통 컴포넌트에 키보드, 초점, 이름, 역할, 상태 규칙을 정의하여 개별 화면마다 같은 결함이 반복되지 않도록 하는 것이 바람직하다.
2. 빌드 과정에서 자동 검사로 반복 결함을 차단하고, 주요 사용자 여정은 수동 검증으로 보완하는 것이 필요하다.
3. 장애 당사자와 핵심 과업을 함께 수행하여 실제 이용 가능성을 측정하고 그 결과를 개선 우선순위에 반영해야 한다.
4. 법적 요구, 국가표준, 국제 지침, 품질인증의 적용 범위를 서비스별로 기록해 두어 준수 근거를 추적할 수 있어야 한다.

## Ⅶ. 결론

- 핵심 요약 : 웹 접근성은 POUR 원칙을 실제 과업 수행으로 검증할 때 의미가 있으며, 자동 도구만으로는 완결되지 않음.
- 시사점 : 보조기술 호환성과 장애 당사자 경험을 제품 품질의 지속적 지표로 관리해야 함.

근거 : KS X OT0003:2022(KWCAG 2.2, 국가표준), W3C WCAG 2.2 권고 문서.
