## 답안 골격
```text
[보안 품질(Security Quality)] ◀━━ 머리: Ⅶ 내 의견 (사후 취약점 패치 패러다임 탈피 → 요구사항부터 배포까지 Shift-Left 보안 품질 게이트웨이 내재화)
 ┃
 ┣━ Ⅰ 개요 ───── 소프트웨어 시스템이 비인가된 접근·수정·손상으로부터 데이터와 프로그램을 보호하고, 공격에 직면했을 때 의도된 보안 요구조건을 충족하는 소프트웨어 제품 품질(ISO/IEC 25010)의 핵심 속성
 ┣━ Ⅱ 특징 ───── 비기능 요구사항의 핵심 축 · 비용 지수적 증가(개발 후반 수정 시 수십 배) · 정량적 측정이 어려움(취약점 수, CVSS 점수 등으로 간접 측정) · 기능 품질과의 트레이드오프
 ┣━ Ⅲ 구조 ───── ISO/IEC 25010 보안성 5대 부특성: 기밀성(Confidentiality) + 무결성(Integrity) + 부인방지(Non-repudiation) + 책임성(Accountability) + 진정성(Authenticity)
 ┣━ Ⅳ 흐름 ───── 보안 품질 요구정의(위협 모델링) → 보안 아키텍처 설계 → 시큐어 코딩 및 정적 분석(SAST) → 동적 보안 테스트(DAST) → 침투 테스트 및 릴리스 품질 판정
 ┣━ Ⅴ 비교 ───── 신뢰성(장애 없이 작동, 내부 결함 중심) vs 보안 품질(적대적 공격자의 의도적 침해로부터 시스템 및 데이터 보호)
 ┗━ Ⅵ 실무 ───── 보안 요구사항의 정량적 명세 결여 / 개발 마감 압박에 따른 보안 테스트 생략 / 서드파티 라이브러리 품질 통제 부재
```
- 필수 키워드: ISO/IEC 25010 · 보안성 5대 부특성 · 기밀성 · 무결성 · 부인방지 · 책임성 · 진정성 · 시큐어 코딩 · 위협 모델링 · Shift-Left
- 기출: 제136회 4교시 6번: "소프트웨어 품질 속성 중 보안 품질에 대하여 다음을 설명하시오."

## 한 줄 본질
- 기능 구현에 치중하여 보안 결함이 운영 단계에서야 발견되는 품질 병목 → ISO/IEC 25010 5대 보안 부특성을 정의하고 소프트웨어 생애주기 전반에 보안 테스트를 전진 배치(Shift-Left) → 침해 사고 사전 예방 / 초기 분석 및 테스트 공수 증가

## 핵심 용어
- 기밀성(Confidentiality): 권한이 없는 개인이나 엔티티, 프로세스가 데이터를 열람하거나 접근할 수 없도록 보장하는 품질 속성
- 부인방지(Non-repudiation): 특정 사건이나 행위가 실제로 일어났음을 증명하여 나중에 이를 부인할 수 없도록 증거를 제공하는 품질 속성
- 책임성(Accountability): 시스템 내에서 일어난 모든 동작과 변경 사항을 고유한 사용자 또는 프로세스의 책임으로 명확히 귀속시킬 수 있는 감사 추적 속성

## 핵심 통찰
- 보안 품질은 다른 품질 속성과 끊임없이 충돌함 → 보안을 강화하면(다중 인증, 실시간 트래픽 복호화 검사) 사용성(Usability)과 성능(Performance)이 필연적으로 저하됨
- 배포 직전의 침투 테스트만으로는 보안 품질을 담보할 수 없음 → 아키텍처 단계의 결함은 코드를 아무리 잘 짜도 해결되지 않으므로, 설계 단계의 '위협 모델링(Threat Modeling)'이 필수적임
- 테스트 자동화가 없는 보안은 지속될 수 없음 → 개발자가 Git에 코드를 푸시할 때마다 SAST와 SCA가 자동 실행되는 CI/CD 통합 품질 게이트(Quality Gate)를 통과해야 함

## 이웃 토픽과 구분
- 소프트웨어 안전성(Safety) vs 보안성(Security): 안전성 = 시스템 오류나 우발적 결함으로 인해 인명 피해나 물리적 재난이 발생하는 것을 방지 / 보안성 = 외부 공격자의 고의적·악의적 침해 행위로부터 시스템을 보호

## 문제·원인·대책
- 사례: 상용 웹 애플리케이션 출시 직후 SQL Injection 및 권한 우회 취약점이 노출되어 긴급 패치한 사례
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 배포 후 심각한 입력값 검증 취약점 다수 발견 | 구현 단계에서 개발자 자율에만 의존하고 시큐어 코딩 규칙 미강제 | SonarQube 등 SAST 도구를 CI 파이프라인에 연동하고 심각 결함 시 빌드 차단 | 배포 전 소스코드 취약점 90% 이상 사전 제거 |
| 침해 발생 시 어떤 사용자가 침투했는지 추적 불가 | 인증 로그만 남기고 권한 변경 및 데이터 삭제 행위 감사로그 누락 | 책임성(Accountability) 충족을 위한 중앙 불변 SIEM 감사 로그 구축 | 모든 행위자의 세션 및 변경 이력 완전 입증 가능 |

## 이렇게 출제된다
- 제136회 4교시 6번: "소프트웨어 품질 속성 중 보안 품질에 대하여 다음을 설명하시오." → 요구 포인트: Ⅰ 보안 품질 개념 + Ⅲ ISO/IEC 25010 5대 부특성(기밀성, 무결성, 부인방지, 책임성, 진정성) + Ⅵ SDLC 단계별 품질 검증 기법

## 내 의견
- [보안 품질 속성을 SLA 및 완료 조건(DoD)에 명시] 많은 소프트웨어 사업에서 기능 개발 완료만 축하하고 보안 테스트는 오픈 전 형식적 스캔으로 때우는 관행 만연 → 나라면: 애자일 스프린트의 '완료의 정의(Definition of Done)'에 'CVSS 7.0 이상 취약점 Zero'와 'OWASP Top 10 점검 통과'를 강제하고, 외주 감리 검수 시 기능 완성도와 동일한 비중으로 보안 품질 지표를 감리 평가 항목에 반영
