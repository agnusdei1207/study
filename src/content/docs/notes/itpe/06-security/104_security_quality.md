## 지식 로드맵 내 현재 위치

소프트웨어 품질 → ISO/IEC 25010 보안성 → SDLC 보안 품질 엔지니어링

## 30초 인출

- **본질:** 소프트웨어가 악의적 침입, 비인가 접근, 데이터 변조에 저항하고 시스템의 기밀성, 무결성, 부인방지, 책임성, 진정성, 저항성(2023 추가)을 보장하는 품질 속성.
- **메커니즘:** 요구사항 단계 위협 모델링 → 개발/빌드 시 SAST/SCA/시크릿 스캔 → 테스트 시 DAST/IAST/퍼징 → 보안 품질 게이트(Quality Gate) 통과 후 안전 배포.
- 통찰: 배포 후 취약점 수정 비용은 기획/설계 단계 대비 최대 100배(보엠의 법칙)에 달하므로, DevSecOps 기반의 쉬프트 레프트(Shift-Left) 자동화 검증 체계 구축 필수.

<details><summary>핵심 용어</summary>

- **소프트웨어 보안 품질(Security Quality)**: 시스템이 비인가된 접근이나 데이터 유출, 서비스 마비 공격을 견디고 의도된 보안 요구를 완벽히 충족하는 능력.
- **ISO/IEC 25010:2023**: 소프트웨어 제품 품질의 8대 주특성 중 '보안성(Security)'의 부특성을 기밀성, 무결성, 부인방지, 책임성, 진정성, 저항성(Resistance)으로 정의한 최신 국제표준.
- **쉬프트 레프트(Shift-Left)**: 배포 직전이나 운영 단계에 수행하던 보안 검증을 요구사항, 설계, 개발 초기 단계로 전진 배치하는 접근법.
- **보안 품질 게이트(Security Quality Gate)**: CI/CD 빌드 파이프라인에서 정적/동적 취약점 기준(예: 치명적 취약점 0건)을 충족하지 못하면 배포를 자동 차단하는 통제점.
- **IAST(대화형 애플리케이션 보안 테스팅)**: 런타임 에이전트 형태로 애플리케이션 내부에 상주하며 SAST의 코드 가시성과 DAST의 실행 맥락을 결합해 실시간 취약점을 판별하는 도구.
</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 보안 품질의 정의와 중요성을 설명하고, ISO/IEC 25010 표준에 따른 품질 특성, SDLC 전주기 자동화 검증 기술(SAST/DAST/IAST/SCA) 및 보안 품질 게이트 구축 시의 엔지니어링 한계와 극복 방안을 제시하시오. (기출·제136회 4교시 6번)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어가 외부의 악의적 사이버 공격과 비인가 데이터 변경에 저항하고, 기밀성·무결성·가용성을 보장하도록 SDLC 전주기에서 내재화하는 제품 비기능 품질 속성 |
| 목적 | 운영 단계 보안 사고로 인한 대규모 금융 피해 및 법적 제재를 방지하고, 결함 수정 비용(보엠의 법칙)을 최소화하며 신뢰성 높은 시스템 배포 달성 |

## Ⅱ. ISO/IEC 25010 기반 소프트웨어 보안 품질의 핵심 특성

| 품질 부특성 | 세부 정의 | 엔지니어링 검증 메커니즘 |
|---|---|---|
| 기밀성 (Confidentiality) | 인가된 사용자나 프로세스만 데이터에 접근할 수 있도록 보장 | AES-256 저장 암호화, TLS 1.3 전송 암호화, 컬럼 마스킹 |
| 무결성 (Integrity) | 데이터나 프로그램이 비인가자에 의해 변조되지 않음을 보장 | SHA-256 디지털 서명, HMAC 무결성 검증, DB 제약조건 |
| 부인방지 (Non-repudiation) | 행위나 사건이 발생했음을 제3자에게 증명하여 사후 부인을 차단 | 공인 전자서명(PKI), RFC 3161 공인 시점확인(TSA) |
| 책임성 (Accountability) | 시스템 내 모든 동작을 특정 주체(사용자/프로세스)로 유일하게 추적 | WORM 감사 로깅, SIEM 기반 사용자 행위 추적(UEBA) |
| 진정성 (Authenticity) | 주체나 자원의 신원이 주장하는 바와 일치함을 엄격히 증명 | FIDO2 다중요소인증(MFA), mTLS 상호 인증 |
| 저항성 (Resistance, 2023 신설) | 능동적 공격(DoS, 익스플로잇, 퍼징)을 받더라도 스스로 견디는 능력 | 서킷 브레이커, 메모리 보호(ASLR/DEP), 샌드박스 격리 |

## Ⅲ. 소프트웨어 보안 품질 자동화 테스팅 도구 및 SDLC 전주기 아키텍처

```text
[ 요구사항 / 설계 단계 ] ──▶ 위협 모델링 (STRIDE / ATLAS) & 보안 비기능 요구 도출
                                    │
                                    ▼
[ 개발 단계 (Coding) ]  ──▶ IDE 보안 린터 + 커밋 시 시크릿 스캐닝 (TruffleHog)
                                    │
                                    ▼
[ CI 빌드 단계 (Build) ] ──▶ SAST (정적 코드 분석: SonarQube)
                        ──▶ SCA (오픈소스 의존성 분석: Snyk, Dependency-Check)
                                    │
                                    ▼
+---------------------------------------------------------------------------------+
| 보안 품질 게이트 (Security Quality Gate) 판정                                   |
| - 조건: CVSS 9.0 이상 Critical 취약점 0건, 오픈소스 라이선스 위반 0건          |
| - 미충족 시: 빌드 즉시 실패(Build Break) 및 개발자 피드백 자동 발송             |
+---------------------------------------------------------------------------------+
                                    │ (통과 시)
                                    ▼
[ CD 테스트 단계 (Test) ]──▶ DAST (동적 웹 스캔: OWASP ZAP)
                        ──▶ IAST (런타임 대화형 검증: Contrast Security)
                        ──▶ Fuzzing (예상 밖 비정상 입력 충돌 테스트)
                                    │
                                    ▼
[ 운영 및 모니터링 (Run) ]──▶ RASP (자가 방어) + 실시간 취약점 수집 및 피드백
```

| 자동화 기술 | 분석 시점 및 대상 | 주요 장점 | 한계 및 극복 과제 |
|---|---|---|---|
| SAST (정적 분석) | 컴파일 전 소스코드 패턴 및 데이터 흐름 분석 | 100% 코드 커버리지, 조기 발견 | 높은 오탐률(False Positive), 비즈니스 로직 미탐 |
| SCA (의존성 분석) | package.json 등 오픈소스 라이브러리 및 SBOM | 알려진 취약점(CVE) 고속 적발 | 코드 도달 가능성(Reachability) 미고려로 취약점 과다 도출 |
| DAST (동적 분석) | 실행 중인 웹 애플리케이션의 HTTP 요청/응답 | 소스코드 없이 실제 공격 시뮬레이션 | 복잡한 인증 세션 및 API 심층 탐색 한계, 느린 검사 속도 |
| IAST (대화형 분석) | 런타임 테스트 중 JVM/CLR 내부 에이전트 분석 | 매우 낮은 오탐률, 정확한 취약 라인 특정 | 특정 언어/프레임워크 종속성, 런타임 오버헤드 유발 |

## Ⅳ. 전통적 기능 품질(QA) vs 소프트웨어 보안 품질(DevSecOps) 비교

| 비교 항목 | 전통적 소프트웨어 품질 (Functional QA) | 소프트웨어 보안 품질 (Security Quality) |
|---|---|---|
| 주요 목표 | 시스템이 '명시된 기능'을 올바르게 수행하는가 | 시스템이 '의도되지 않은 동작'을 하지 않도록 방어하는가 |
| 테스트 시나리오 | 정상 케이스(Happy Path) 및 예외 처리 검증 | 적대적 비정상 입력(Adversarial Inputs) 및 악의적 우회 |
| 결함 발견 비용 | 릴리스 직전 테스트 단계 집중 | 쉬프트 레프트(Shift-Left)로 개발 초기 단계 집중 제거 |
| 통제 메커니즘 | 단위 테스트, 통합 테스트, E2E 시나리오 | SAST, DAST, SCA, IAST, 위협 모델링, 퍼징 |
| 책임 주체 | QA 테스터 및 개발 조직 | 개발팀, 보안팀, 운영팀 공동 책임 (DevSecOps) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| SAST 도구의 과도한 오탐(False Positive)으로 인해 빌드가 빈번히 중단되어 개발 생산성 저하 및 경보 피로 유발 | AI 기반 오탐 필터링 엔진을 연동하고, 심각도와 악용 가능성(EPSS 점수)을 결합한 지능형 품질 게이트(Quality Gate) 정책 커스터마이징 |
| 마이크로서비스 및 SPA 환경에서 DAST 스캐너가 인증 토큰(JWT) 만료 및 비동기 API 엔드포인트를 탐색하지 못하는 한계 | OpenAPI(Swagger) 명세서를 DAST 도구에 직접 주입하여 엔드포인트를 100% 매핑하고, 런타임 IAST 에이전트와 하이브리드 결합 |
| SCA 도구가 수천 개의 취약점을 경보하지만 실제 실행 경로에서 호출되지 않는 사장 코드(Dead Code) 취약점 과다 보고 | 정적 호출 그래프(Call Graph) 기반의 도달 가능성 분석(Reachability Analysis) 도구를 적용하여 실제 호출되는 의존성만 선별 조치 |
| 할인 쿠폰 중복 적용, 권한 상승 등 비즈니스 로직 결함(Business Logic Flaws)은 자동화 도구(SAST/DAST)로 검출 불가 | 설계 단계 위협 모델링(STRIDE)을 의무화하고, 도메인 지식을 갖춘 보안 전문가의 피어 코드 리뷰(Peer Review) 필수 결합 |

## Ⅵ. 제언

```text
[ 소프트웨어 보안 품질 고도화 3대 프레임워크 ]

+-------------------------+      +-------------------------+      +-------------------------+
|     1. 쉬프트 레프트    | ---> |     2. 품질 게이트 자동화| ---> |     3. 피드백 루프 완성 |
| (IDE 린터 / 위협모델링) |      | (SAST/SCA/IAST 파이프라인|      | (RASP 운영 데이터 회귀) |
+-------------------------+      +-------------------------+      +-------------------------+
```

| 이행 영역 | 엔지니어링 실무 구현 과제 | 비즈니스 가치 |
|---|---|---|
| 개발 문화 혁신 | 개발자 IDE에 보안 린터(Security Linter) 기본 탑재 및 시큐어 코딩 교육 정례화 | 코드 작성 시점에 보안 결함 70% 사전 제거 |
| 파이프라인 자동화 | CI/CD 단계별 보안 품질 게이트 구축 및 Critical 취약점 발견 시 배포 자동 거부 | 취약 코드의 프로덕션 환경 유입 원천 차단 |
| 지속적 품질 거버넌스 | 운영 환경 RASP/SIEM 탐지 이벤트를 다음 개발 스프린트의 보안 요구사항으로 자동 연동 | 제품 릴리스 주기 단축 및 결함 수정 비용 90% 절감 |
