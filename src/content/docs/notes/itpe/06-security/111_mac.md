## 답안 골격
```text
[MAC(Message Authentication Code)] ◀━━ 머리: Ⅶ 내 의견 (단순 해시의 위변조 취약성 극복 → 공유 비밀키 기반 HMAC/GMAC을 통한 무결성·송신처 인증 동시 보장)
 ┃
 ┣━ Ⅰ 개요 ───── 송신자와 수신자가 사전에 공유한 비밀키(Symmetric Key)와 임의 길이의 메시지를 입력으로 하여 고정 길이의 검증 태그(Tag)를 생성함으로써, 전송 도중 메시지 위·변조 방지(무결성)와 송신자 신원 입증(인증)을 동시에 제공하는 암호학적 기법
 ┣━ Ⅱ 특징 ───── 대칭키 공유 기반 동작 · 고속 연산 처리(전자서명 대비 수십~수백 배) · 무결성 및 인증 제공 · 대칭키 공유 특성으로 인한 제3자 부인방지(Non-repudiation) 불가
 ┣━ Ⅲ 구조 ───── 송수신자 공유 비밀키(K) + 메시지(M) + MAC 생성 알고리즘 $C_K(M)$ + 검증 태그(Tag)
 ┣━ Ⅳ 흐름 ───── 송신자가 메시지 M과 비밀키 K로 태그 T 생성 → (M, T) 전송 → 수신자가 수신된 M과 동일 비밀키 K로 로컬 태그 T' 계산 → T == T' 비교 및 일치 시 수락
 ┣━ Ⅴ 비교 ───── 단순 해시(MDC, 무결성만 제공, 키 없음) vs MAC(무결성+인증, 대칭키, 부인방지 불가) vs 전자서명(무결성+인증+부인방지, 비대칭키)
 ┗━ Ⅵ 실무 ───── 안전하지 않은 해시 함수(MD5, SHA-1) 사용 금지 / 타이밍 공격(Timing Attack) 방지를 위한 상수 시간(Constant-time) 비교 강제 / 키 관리 취약점
```
- 필수 키워드: MAC(메시지 인증 코드) · HMAC · CMAC · GMAC · 무결성(Integrity) · 출처 인증(Authentication) · 부인방지 불가 · 공유 비밀키
- 기출: 제127회 1교시 5번: "메시지 인증 코드(Message Authentication Code)"

## 한 줄 본질
- 공격자가 메시지와 단순 해시값을 동시에 조작해 가로채는 전송 변조 병목 → 오직 정당한 당사자만 아는 대칭키를 섞어 태그를 생성(MAC)함으로써 도중 변조와 송신처 위조를 차단 → 고속 무결성 및 인증 확보 / 송수신자 간 분쟁 시 제3자에 대한 부인방지 불가

## 핵심 그림
```text
[MAC(Message Authentication Code)의 생성 및 검증 절차]

[송신자 (Sender)]                                       [수신자 (Receiver)]
  [메시지 M] ──┬─────────────────(네트워크 전송)─────────────────> [메시지 M] ──┬──> [MAC 생성]
               │                                                              │    - 알고리즘: C
               ▼                                                              │    - 공유키: K
        [MAC 생성 $C_K(M)$]                                                   │         │
        - 비밀키: K                                                           │         ▼
               │                                                              │   [수신자 계산 태그 T']
               ▼                                                              │         │
          [태그 T] ────────────────(네트워크 전송)────────────────> [태그 T] ──┴──> [일치 여부 비교: T == T' ?]
                                                                                     ├─ 일치: 무결성/인증 성공!
                                                                                     └─ 불일치: 변조 패킷 폐기!
```

## 핵심 용어
- HMAC (Hash-based MAC): SHA-256 등 단방향 암호학적 해시 함수를 기반으로 내부 패딩(ipad)과 외부 패딩(opad)의 2중 해싱 구조를 적용해 길이 확장 공격(Length Extension Attack)을 완벽히 방어한 표준 MAC
- GMAC (Galois MAC): 블록 암호(AES)의 CTR 운용 모드와 결합하여 갈루아 체($GF(2^{128})$) 상에서 고속 병렬 연산을 수행하는 태그 생성 방식으로, 현대 최고 표준인 AES-GCM의 인증 엔진으로 사용됨

## 핵심 통찰
- 단순 해시 함수(SHA-256)는 보안 키가 없으므로 공격자가 평문을 고치고 해시를 다시 계산해서 보내면 수신자는 변조를 알 수 없음 → 따라서 반드시 비밀키가 개입된 MAC을 써야 함
- MAC은 "너와 나" 둘만의 통신에서는 완벽한 인증을 제공하지만, "법정에서 판사 앞"에서는 증거 효력이 없음 → 둘 다 동일한 대칭키를 쥐고 있으므로 수신자가 스스로 메시지를 위조해 놓고 송신자가 보냈다고 거짓 주장할 수 있기 때문(부인방지 불가)
- MAC 검증 코드 작성 시 단순 문자열 비교(`tag == received_tag`)를 쓰면 공격자가 바이트 단위 시간차를 측정하는 타이밍 공격(Timing Attack)으로 태그를 알아낼 수 있음 → 반드시 바이트 수와 무관하게 일정한 시간이 걸리는 `HMAC.equal()` 함수를 사용해야 함

## 이웃 토픽과 구분
- MAC vs 전자서명: MAC = 대칭키 사용, 초고속 연산, 부인방지 불가 / 전자서명 = 비대칭키(개인키/공개키) 사용, 연산 오버헤드 큼, 법적 부인방지 보장

## 문제·원인·대책
- 사례: 웹 API 통신에서 단순 해시값을 토큰으로 검증하다가 공격자의 중간자 변조 공격에 당한 사례
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 중간자(MITM)가 API 파라미터 변조 후 해시 재계산 주입 | 키 없는 단순 해시 함수(SHA-256)를 무결성 검증용으로 오용 | 비밀키 기반의 HMAC-SHA256 또는 AES-GCM 적용 | 비밀키 없는 공격자의 임의 태그 위조 원천 차단 |
| 바이트 단위 비교 시간차를 이용한 MAC 값 원격 복원 (타이밍 공격) | 일반 `strcmp()` 함수 사용으로 첫 번째 불일치 바이트에서 조기 리턴 | 상수 시간 비교(Constant-Time Comparison) 알고리즘 적용 | 문자열 일치 여부에 따른 응답 시간차 제거로 타이밍 분석 무력화 |

## 이렇게 출제된다
- 제127회 1교시 5번: "메시지 인증 코드(Message Authentication Code)" → 요구 포인트: Ⅰ MAC 정의 + Ⅲ 생성 및 검증 메커니즘 도식 + Ⅴ MDC, MAC, 전자서명 비교

## 내 의견
- [암호화(Encryption)와 인증(MAC)의 결합 순서 표준화: Encrypt-then-MAC] 과거 많은 시스템이 평문을 MAC한 후 암호화(MAC-then-Encrypt)하여 패딩 오라클 공격에 무너짐 → 나라면: 평문을 먼저 암호화하고 암호문에 대해 MAC을 생성하는 'Encrypt-then-MAC' 방식을 강제하거나, 이를 내부적으로 일체화하여 하드웨어 가속(AES-NI)까지 지원하는 AES-GCM(AEAD)을 전사 표준으로 단일화
