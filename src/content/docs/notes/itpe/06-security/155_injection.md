## Ⅰ. 인젝션(Injection) 공격의 개요

- 핵심 요약 : 신뢰할 수 없는 입력이 명령이나 쿼리의 일부로 해석되어 실행되는 취약점 공격군.
- 개념 : 외부 입력값이 애플리케이션의 **인터프리터** (Interpreter)나 **파서** (Parser)에 의해 문법적 명령의 일부로 오해되어 그대로 실행됨으로써, 데이터베이스를 탈취하거나 OS 쉘 명령을 실행하게 되는 취약점 공격군이며 OWASP(Open Worldwide Application Security Project) Top 10에 꼽히는 대표 위협.
- 배경 및 필요성 : 사용자 입력을 순수한 데이터로 다루지 않고 명령 문자열에 그대로 결합하는 구현 관행 때문에 제어 흐름이 공격자의 의도대로 바뀌는 결함이 반복해서 발생한다.
- 주요 목적 : 공격자가 인증을 우회하고, 데이터베이스를 빼내고, 서버 파일을 조작하며, 궁극적으로 **임의 코드 실행** (RCE, Remote Code Execution)으로 서버 전체를 장악하는 것.

## Ⅱ. 인젝션(Injection) 공격의 특징 및 장점

- 핵심 요약 : 데이터와 명령이 한 문자열에 섞이는 구조, 인터프리터별 다양한 문법, 단계적 피해 확장이 결합된 특징.

1. 데이터와 명령의 혼재 : 입력값이 문자열 결합으로 명령 구문에 삽입 → 파서가 입력을 명령의 일부로 해석해 실행.
2. 인터프리터별 분화 : 대상 해석기의 문법에 맞춘 페이로드 작성 → SQL, OS 명령, LDAP, 템플릿 등 여러 영역으로 공격 확장.
3. 연쇄 피해 : 인증 우회 후 데이터 유출, 쉘 획득으로 이어짐 → 단일 입력 지점의 결함이 서버 전체 장악으로 확대.

분류는 대상 인터프리터에 따라 **SQL 인젝션** (SQL Injection), **OS 명령 인젝션** (OS Command Injection), **LDAP 인젝션** (LDAP Injection), XPath/XQuery 인젝션, **SSTI** (Server-Side Template Injection, 서버 측 템플릿 인젝션) 등으로 나뉜다.

## Ⅲ. 인젝션(Injection) 공격의 구조 (흐름)

- 핵심 요약 : 서로 다른 인터프리터의 입력 왜곡이 하나의 취약한 결합 지점에서 만나 실행되고, 근본 방어는 데이터와 명령의 분리로 이루어지는 구조.

```text
[ 인터프리터별 인젝션 경로 ]

공격자의 조작된 입력값
          ↓
SQL 인젝션 : ' OR 1=1 -- 입력
  → WHERE 조건이 항상 참
OS 명령 인젝션 : ; 추가 명령
  → 쉘이 다중 명령 실행
SSTI : {{7*7}} 입력
  → 템플릿 엔진 내부에서 코드 실행
          ↓
데이터가 명령으로 승격되어 실행
          ↓
기밀 유출, 랜섬웨어 설치, 원격 쉘 획득
```

```text
[ 근본 방어 원칙: 데이터와 명령의 분리 ]

1. 매개변수화 질의
   (PreparedStatement 바인딩)
2. 쉘 경유 금지
   (인자를 배열로 직접 전달, execve)
3. 화이트리스트 입력 검증
```

- OS 명령 인젝션 : ping, mail 같은 시스템 명령을 호출할 때 입력값을 검증 없이 쉘 문자열에 결합해, 세미콜론(;)이나 파이프(|)로 임의 명령을 추가 실행하는 취약점.
- LDAP 인젝션 : 입력값을 검증 없이 LDAP 검색 필터에 결합해 디렉터리 서비스의 인증을 우회하거나 계정 정보를 탈취하는 취약점.
- SSTI : 템플릿 엔진(Jinja2, FreeMarker 등)에 악의적인 템플릿 구문이 전달되어, 객체 리플렉션을 통해 서버 측에서 코드가 실행되는 취약점.
- 공통 메커니즘 : 모든 인젝션의 본질은 파서가 데이터 영역과 제어 코드 영역을 구분하지 못해 데이터가 명령으로 승격되는 현상.

## Ⅳ. 인젝션(Injection) 공격 유형의 비교

- 핵심 요약 : 유형마다 대상 인터프리터와 특수 문자는 다르지만, 원천 해결책은 모두 바인딩이나 API 분리라는 같은 원칙으로 수렴.

| 비교 항목 | OS 명령 인젝션 | SQL 인젝션 | LDAP 인젝션 | SSTI |
| --- | --- | --- | --- | --- |
| 대상 인터프리터 | OS 시스템 쉘 (/bin/sh, cmd.exe) | 데이터베이스 엔진 (Oracle, MySQL) | 디렉터리 서비스 (OpenLDAP, AD) | 웹 템플릿 엔진 (Jinja2, Velocity) |
| 공격 영향 | 서버 OS 장악 (RCE) | 데이터 유출, 원장 변조, 관리자 우회 | 계정 도용, 디렉터리 정보 유출 | 서버 메모리 접근, 원격 쉘 획득 |
| 주요 특수 문자 | ;, &, \|, `, $(), > | ', ", --, ;, UNION | *, (, ), &, \|, !, = | {{, }}, ${, }, <%, %> |
| 위험도 | 매우 높음 (서버 장악 즉시 완료) | 매우 높음 (대규모 데이터 침해) | 높음 (계정 인프라 붕괴) | 매우 높음 (프레임워크 샌드박스 탈출) |
| 원천 해결책 | 쉘 호출 금지, 인자 배열 전달 | PreparedStatement 바인딩 | 매개변수화된 검색 필터 | 템플릿에 사용자 입력 직접 렌더링 금지 |

- 선택 기준 : 공격 대상 해석기가 쉘인지, 쿼리 엔진인지, 디렉터리 서비스인지, 템플릿 엔진인지에 따라 점검 항목을 나눔.

## Ⅴ. 인젝션(Injection) 공격의 한계와 방안

- 핵심 요약 : 레거시 쉘 호출, 블랙리스트 우회, ORM 환경의 Raw Query를 구조적 API, 화이트리스트, 정적 분석 차단으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 레거시 쉘 호출 관행 | system(), exec() 등에 문자열 인자를 결합하는 코드가 남아 명령 주입 경로가 잔존 | 쉘을 거치지 않는 ProcessBuilder에 인자를 배열로 개별 전달 | 쉘 호출 API 사용 건수 |
| 블랙리스트 필터의 우회 | 공백·세미콜론을 차단해도 ${IFS}, 인코딩, 줄바꿈으로 필터 우회 | 블랙리스트 폐기, 허용된 문자만 통과시키는 화이트리스트 검증 | 필터 우회 탐지 건수 |
| ORM(Object-Relational Mapping) 환경의 Raw Query 남용 | JPA나 MyBatis를 쓰면서도 성능과 동적 조건을 이유로 Native Query와 문자열 결합 사용 | SAST(Static Application Security Testing) 룰셋에서 문자열 결합을 검출하면 빌드 차단 | 빌드 차단 건수 |

## Ⅵ. 인젝션(Injection) 공격에 대한 기술사적 제언

- 핵심 요약 : 개발 파이프라인의 자동 검사, 최소 권한 실행 환경, 다층 방어를 결합해 인젝션을 설계 단계부터 차단하는 체계로 정착.

1. 개발 조직은 CI(Continuous Integration)/CD(Continuous Delivery) 파이프라인에 SAST와 DAST(Dynamic Application Security Testing)를 연결해, 인젝션 취약점이 배포 전에 걸러지도록 해야 한다.
2. 운영 조직은 웹 프로세스를 일반 권한으로 구동하고 셸 바이너리가 없는 경량 컨테이너 이미지를 사용해, 명령 주입이 성공해도 시스템 영향이 제한되도록 하는 것이 바람직하다.
3. 보안 조직은 웹 애플리케이션 방화벽(WAF, Web Application Firewall)과 RASP(Runtime Application Self-Protection)를 함께 두어, 네트워크 경계와 애플리케이션 실행 시점이라는 두 지점에서 인젝션을 막는 다층 방어를 구성해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 인젝션은 데이터와 명령의 경계가 무너져 생기는 고전적 취약점이며, 문법 분리 원칙으로 원천 차단이 가능한 결함.
- 시사점 : 탐지 도구보다 바인딩과 API 설계 같은 구현 원칙이 방어의 핵심이므로, 이를 개발 표준으로 고정하는 것이 전제다.
