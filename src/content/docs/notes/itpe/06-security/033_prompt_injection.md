## 지식 로드맵 내 현재 위치

AI 보안 → 생성형 AI 애플리케이션 보안 → 프롬프트 인젝션

## 30초 인출

- **본질:** **프롬프트 인젝션**은 입력된 지시가 LLM의 동작·출력을 의도와 다르게 바꾸는 공격
- **경로:** 직접 입력 또는 문서·웹 등 외부 콘텐츠를 모델이 읽는 간접 경로
- **영향:** 정보 노출·잘못된 응답·권한 있는 도구의 오용 가능성

<details>
<summary>핵심 용어</summary>

- **프롬프트 인젝션(Prompt Injection):** 입력 지시가 LLM 동작·출력을 의도와 다르게 유도하는 취약점·공격
- **LLM (Large Language Model):** 프롬프트와 문맥을 처리해 언어 출력을 생성하는 대규모 언어모델
- **직접 인젝션:** 사용자가 제공한 프롬프트가 모델 동작을 예상과 다르게 유도하는 유형
- **간접 인젝션:** 웹·파일·검색 결과 등 외부 콘텐츠의 지시가 모델 동작에 영향을 주는 유형
- **RAG (Retrieval-Augmented Generation):** 외부 자료를 검색해 생성 모델의 입력 문맥에 제공하는 방식
- **도구 호출(tool call):** 모델의 출력을 애플리케이션이 함수·서비스 실행 요청으로 처리하는 기능
- **최소 권한:** 모델 연동 서비스에 업무 수행에 필요한 최소 권한만 부여하는 원칙
- **OWASP (Open Worldwide Application Security Project):** 웹·애플리케이션 보안 지침과 프로젝트를 제공하는 비영리 재단
</details>

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **프롬프트 인젝션**은 입력 지시가 LLM의 동작·출력을 의도와 다르게 유도하는 공격 |
| 목적 | 시스템의 의도된 지시·권한 경계를 벗어난 응답이나 행위 유도 |

### Ⅱ. 입력 경로와 영향

```text
직접: 사용자 프롬프트 ──────┐
                             ├──> LLM ──> 응답·도구 요청
간접: 웹·문서·검색 자료 ─────┘                 ↓
                                  정보 노출·오응답·비인가 행위 위험
```

| 유형 | 입력 위치 | 핵심 차이 |
|---|---|---|
| 직접 인젝션 | 사용자가 넣은 프롬프트 | 대화 입력에서 지시를 삽입 |
| 간접 인젝션 | 모델이 읽는 외부 자료 | 비신뢰 콘텐츠를 처리하는 과정에서 지시를 삽입 |

**제언:** 외부 콘텐츠를 비신뢰 입력으로 취급하고 민감 작업의 모델 권한을 제한

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **프롬프트 인젝션**은 입력 지시가 LLM의 동작·출력을 의도와 다르게 유도하는 공격 |
| 목적 | 시스템의 의도된 지시·권한 경계를 벗어난 응답이나 행위 유도 |

```text
비신뢰 지시 (사용자 입력·외부 문맥)
                  ↓ 모델 문맥에 유입
           의도하지 않은 출력·계획
                  ↓ 애플리케이션 검증 없이 실행될 때
          데이터 노출·비인가 행위 가능성
```

## Ⅱ. 공격 유형과 보안 영향

| 유형 | 입력 경로 | 가능한 영향 |
|---|---|---|
| 직접 인젝션 | 사용자 프롬프트 | 안전 지시 우회 시도, 의도하지 않은 출력 |
| 간접 인젝션 | 웹페이지·파일·검색 결과·이메일 등 모델이 읽는 자료 | 검색·요약 문맥을 통한 응답 조작·정보 노출 |
| 도구 연동 악용 | 모델이 호출하도록 허용된 함수·서비스 | 권한이 있는 데이터 조회·변경·전송의 오용 |

RAG (Retrieval-Augmented Generation)나 미세조정만으로 입력 지시와 신뢰 경계를 완전히 구분하지 못하므로 애플리케이션 통제 병행 필요.

## Ⅲ. 다층 방어

| 통제 지점 | 방어 설계 |
|---|---|
| 입력·검색 자료 | 외부 문맥의 출처 표시·격리, 검색 범위·민감자료 최소화 |
| 모델 출력 | 예상 형식·업무 범위 검증, 민감 응답의 정책 검사 |
| 도구·데이터 | 최소 권한 토큰, 허용 함수 제한, 객체별 인가 검사 |
| 고위험 행위 | 전송·삭제·승인 등 외부 효과 발생 전 별도 검증·사람 승인 |
| 운영 | 공격 시나리오 시험, 로그·사고 대응, 통제 재평가 |

```text
비신뢰 입력·검색 자료 → 모델 추론 → 출력·도구 요청 검증
                                       ↓ 검증 통과만
                           최소권한 도구 → 외부 실행
                                       ↑
                          고위험 행위는 사람 승인
```

## Ⅳ. 설계 판단

| 설계 선택 | 보안상 의미 |
|---|---|
| 프롬프트 지시만으로 방어 | 우회 가능성을 배제할 수 없는 보조 통제 |
| 코드·정책 계층에서 권한 제한 | 모델이 지시를 오해해도 접근 가능한 데이터·행위의 범위 축소 |
| 실행 결과를 독립 검증 | 모델 출력과 실제 시스템 변경 사이의 검증 지점 확보 |
| 사람 승인 추가 | 영향이 크거나 되돌리기 어려운 행위의 최종 결정권 분리 |

## Ⅴ. 한계와 기술사적 제언

| 한계 | 해결 방안 |
|---|---|
| 자연어 입력과 외부 문맥을 완전히 신뢰·불신으로 나누기 어렵고 프롬프트 규칙만으로 공격을 모두 차단할 수 없음 | 입력 경계를 표시하되 실행 권한은 애플리케이션 코드에서 제한하고, 외부 효과가 있는 요청은 별도 검증 |
| 초기 적용부터 모델에 변경·전송 권한을 주면 프롬프트 오류가 곧바로 외부 시스템 영향으로 이어질 수 있음 | 도입 초기에는 읽기 전용 검색으로 시작하고, 쓰기 기능은 데이터 범위·승인 조건·복구 방안을 검증한 업무부터 별도 도구로 확대하는 적용 순서 제안 |
