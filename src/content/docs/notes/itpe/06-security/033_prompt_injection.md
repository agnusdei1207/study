## 연관 키워드

- 프롬프트 인젝션(Prompt Injection), 직접 인젝션(Direct Injection), 간접 인젝션(Indirect Injection), 탈옥(Jailbreak)
- 시스템 프롬프트 유출(System Prompt Leakage), 도구 오용(Tool Misuse), 가드레일(Guardrails), 데이터 래핑
- 이중 LLM(Dual LLM), Human-in-the-Loop, SQL 인젝션(SQLi), 레드팀(Red Teaming)

## Ⅰ. 프롬프트 인젝션(Prompt Injection)의 개요

- 핵심 요약 : 자연어 명령을 조작해 LLM 애플리케이션의 안전 규칙과 시스템 프롬프트를 우회하는 적대적 공격.
- 개념 : 대규모 언어 모델(LLM, Large Language Model) 애플리케이션에 악의적 지시문을 주입하여, 개발자가 설정한 **시스템 프롬프트** (System Prompt)과 안전 규칙을 우회하고 공격자 의도대로 출력이나 도구 실행을 유도하는 공격인 **프롬프트 인젝션** (Prompt Injection).
- 배경 및 필요성 : 챗봇, 검색 증강 생성(RAG, Retrieval-Augmented Generation) 서비스, 자율 에이전트가 확산되면서 OWASP(Open Worldwide Application Security Project)의 LLM 애플리케이션 위험 목록에서 최상위로 꼽힐 만큼 빈번한 공격 표면이 됨.
- 주요 목적 : 자연어 입력의 신뢰 경계를 규명하고, 입력 경로별 공격을 차단하는 **가드레일** (Guardrails) 체계를 구축하여 AI 애플리케이션을 보호.

## Ⅱ. 프롬프트 인젝션(Prompt Injection)의 특징 및 장점

- 핵심 요약 : 명령과 데이터가 같은 자연어 채널로 섞이는 특성 때문에, 공격 경로에 따라 직접형과 간접형으로 나뉘며 방어가 어려움.

1. **직접 인젝션** (Direct Injection) : 사용자가 입력창에 역할 부여나 지시 무시 문구를 넣어 안전 규칙을 우회 → 악성 텍스트 생성.
2. **간접 인젝션** (Indirect Injection) : 웹페이지, 이메일, 문서에 숨긴 명령이 RAG 검색 결과로 유입 → 사용자 모르게 에이전트가 조종됨.
3. 명령과 데이터의 경계 모호성 : 시스템 명령과 사용자 데이터가 하나의 문자열로 합쳐져 모델이 둘을 구분하기 어려움 → 코드 수준의 완전한 차단이 곤란함.
4. 시스템 프롬프트 유출 (System Prompt Leakage) : 개발자의 초기 지시와 비즈니스 로직을 그대로 출력하도록 유도 → 기밀 노출.
5. **도구 오용** (Tool Misuse) : 이메일 발송, 파일 삭제, DB 수정 API를 대리 호출하도록 유도 → 실제 시스템 피해.

## Ⅲ. 프롬프트 인젝션(Prompt Injection)의 구조 (흐름)

- 핵심 요약 : 직접 공격은 사용자 입력으로, 간접 공격은 검색된 외부 데이터로 LLM 컨텍스트에 들어와 도구 실행으로 이어지는 흐름.

```text
[ 직접 인젝션 흐름 ]

공격자의 채팅 입력
("이전 지침을 무시하라")
          ↓
LLM이 안전 지침을 우회
          ↓
악성 출력 또는 시스템 프롬프트 노출
```

```text
[ 간접 인젝션 흐름 ]

공격자: 웹페이지, 이메일에 악성 명령 은닉
          ↓
사용자: "이 이메일 요약해줘" 요청
          ↓
RAG 검색기: 악성 문서를 컨텍스트에 결합
          ↓
LLM: 은닉 명령을 정상 지시로 오인
          ↓
도구 호출: 메일 전송 등 무단 실행
```

## Ⅳ. 프롬프트 인젝션(Prompt Injection)의 비교

- 핵심 요약 : SQL 인젝션은 코딩 기법으로 원천 차단이 가능하지만, 프롬프트 인젝션은 자연어의 모호성과 확률적 추론 구조 때문에 완전 방어가 어려움.

| 비교 항목 | SQL 인젝션(SQLi, SQL Injection) | 직접 프롬프트 인젝션 | 간접 프롬프트 인젝션 |
| --- | --- | --- | --- |
| 공격 입력 | SQL(Structured Query Language) 구문과 특수문자 | 자연어 지시문, 역할 부여 | 웹페이지, PDF(Portable Document Format), 이메일 속 숨김 텍스트 |
| 실행 엔진 | 결정론적 DBMS(Database Management System) 파서 | 확률론적 LLM 추론 | 확률론적 LLM 추론 |
| 공격 벡터 | 클라이언트 파라미터 조작 | 사용자 채팅 입력 | RAG 검색 문서, 외부 API 응답 |
| 핵심 원인 | 코드와 데이터의 결합 | 명령과 데이터의 경계 모호성 | 비신뢰 외부 데이터의 무검증 결합 |
| 근본 대책 | 매개변수화 쿼리(Prepared Statement) | 완전 차단이 어려워 완화 중심 | 데이터 래핑, 격리 실행 |

## Ⅴ. 프롬프트 인젝션(Prompt Injection)의 한계와 방안

- 핵심 요약 : 명령과 데이터의 분리 불가, 필터 우회, 에이전트의 위험 호출이 주요 한계이며 각각 완화책을 겹쳐 적용해야 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 명령과 데이터의 본질적 분리 불가 | 단일 문자열로 입력되어 모델이 명령을 식별하기 어려움 | 외부 데이터를 XML, JSON 태그로 감싸고 태그 내부를 명령으로 해석하지 않도록 지시. 완전한 해결이 아니므로 위험을 낮추는 완화책으로 취급 | 래핑 적용 비율 |
| 인코딩, 다국어, 난독화를 통한 필터 우회 | 키워드 블랙리스트는 번역이나 Base64 인코딩으로 쉽게 우회됨 | 입력을 디코딩과 정규화한 뒤 Llama Guard, NeMo Guardrails 같은 의미 기반 분류 모델로 사전 검사 | 우회 성공 사례 수 |
| 에이전트의 위험한 도구 호출 | 간접 인젝션에 걸린 에이전트가 삭제나 이체 API를 자동 실행 | 고위험 도구 호출에 Human-in-the-Loop 승인 적용, 도구 권한 최소화 | 승인 없이 실행된 고위험 호출 건수 |

## Ⅵ. 프롬프트 인젝션(Prompt Injection)에 대한 기술사적 제언

- 핵심 요약 : 인젝션을 완전히 막을 수 없다는 전제에서, 권한 격리와 다층 검사를 설계 기본값으로 삼아야 함.
- 신뢰할 수 없는 외부 데이터를 처리하는 모델과 최종 응답을 만드는 모델을 분리하는 **이중 LLM** (Dual LLM) 구조를 아키텍처의 기본값으로 채택하는 것이 바람직하다.
- 배포 파이프라인에 Garak, PyRIT 같은 **레드팀** (Red Teaming) 도구를 편입해 매 배포마다 탈옥 저항성을 점검하는 절차를 정례화할 필요가 있다.
- 시스템 프롬프트는 언제든 노출될 수 있다는 전제로 설계하고, API 키 같은 시크릿은 프롬프트 밖의 권한 계층에서 관리하는 원칙을 세워야 한다.

## Ⅶ. 결론

- 핵심 요약 : 프롬프트 인젝션은 모델 교정만으로 해결되지 않는 신뢰 경계 문제이므로, 권한 최소화와 다층 방어로 피해 범위를 관리해야 함.
- 명령과 데이터를 구분할 수 없다는 전제를 설계에 반영할 때 AI 애플리케이션의 실질적 안전이 확보됨.
