## 연관 키워드

- SQL 인젝션(SQL Injection), 문자열 결합, 인밴드(In-band), 블라인드(Blind), 아웃오브밴드(Out-of-band)
- 2차 SQL 인젝션(Second-Order), 매개변수화 쿼리(Parameterized Query), 화이트리스트, WAF, RASP, OWASP Top 10

## Ⅰ. SQL 인젝션의 개요

- 핵심 요약 : 입력값 검증이 부실한 웹 애플리케이션을 통해 악성 SQL(Structured Query Language) 구문을 주입해 데이터베이스를 조작하는 대표적 인젝션 공격.
- 개념 : 웹 애플리케이션의 입력값 검증 부실을 악용해 악의적인 **SQL 인젝션** (SQL Injection) 구문을 삽입·실행하여, 데이터 무단 열람, 원장 변조, 관리자 권한 획득, 나아가 운영체제 명령 실행까지 가능하게 하는 공격.
- 배경 및 필요성 : 동적 웹 애플리케이션이 확산되면서 사용자 입력을 **문자열 결합** (String Concatenation) 방식으로 쿼리에 그대로 넣는 개발 관행이 지속되었고, 이 때문에 OWASP(Open Worldwide Application Security Project) Top 10에서 오랫동안 주요 취약점으로 꼽힘.
- 공격 목적 : 개인정보와 금융 데이터를 대량 유출하고, 인증 절차를 우회하며, DB 서버의 확장 저장 프로시저를 호출해 서버 제어권을 장악하는 것.

## Ⅱ. SQL 인젝션의 특징 및 장점

- 핵심 요약 : 입력값이 쿼리의 구문으로 해석되는 원리 때문에 작은 입력 한 줄로 전체 데이터에 접근할 수 있는 공격.

1. 쿼리 구조 변조 : 입력값이 쿼리의 구문으로 해석됨 → 조건절을 항상 참으로 만들어 전 테이블 조회.
2. 작은 입력으로 큰 피해 : 입력 필드 하나로 DB 전체에 접근 → 개인정보 대량 유출 가능.
3. 방화벽 우회 : 정상 HTTP(Hypertext Transfer Protocol) 요청 형태로 전달되어 포트 차단만으로는 막을 수 없음 → 웹 계층 방어 필요.
4. 권한 확장 : DB 계정 권한이 크면 저장 프로시저를 통해 운영체제 명령까지 실행 → 서버 장악으로 이어짐.

```text
[ SQL 인젝션 공격 흐름 ]

공격자 입력 : ' OR '1'='1' --
    ↓ (문자열 결합)
실행 쿼리 : WHERE id='' OR '1'='1' --
    ↓ (조건식이 항상 참)
전체 행 반환 → 데이터 유출
```

## Ⅲ. SQL 인젝션의 구조 (흐름)

- 핵심 요약 : 결과를 확인하는 채널에 따라 인밴드, 블라인드, 아웃오브밴드로 나뉘고, 2차 인젝션은 실행 시점이 지연되는 공격.
- **인밴드 SQL 인젝션** (In-band) : 요청과 같은 채널로 결과를 확인하며, UNION 연산자로 타 테이블을 결합하는 Union-based와 에러 메시지로 정보를 노출시키는 Error-based로 나뉨.
- **블라인드 SQL 인젝션** (Blind) : 결과가 화면에 나오지 않을 때 참·거짓에 따른 응답 차이(Boolean-based)나 지연 시간(Time-based)을 측정해 값을 한 글자씩 추론.
- **아웃오브밴드 SQL 인젝션** (Out-of-band, OOB) : DB의 DNS(Domain Name System) 질의나 HTTP 요청 기능을 이용해 외부 서버로 데이터를 송신.
- **2차 SQL 인젝션** (Second-Order) : 입력 시점에는 악성 값이 안전하게 저장되었다가, 이후 다른 쿼리에서 호출될 때 실행되는 지연형 공격.

```text
[ 2차 인젝션의 시점 분리 ]

1차 요청 : 악성 입력을 DB에 저장
    ↓ (시간 경과)
2차 처리 : 저장된 값을 쿼리에 결합
    ↓
관리자 배치 실행 시 페이로드 동작
```

## Ⅳ. SQL 인젝션의 비교 분석

- 핵심 요약 : 결과 확인이 빠른 인밴드, 느리지만 탐지가 어려운 블라인드, 방화벽 제약을 넘는 아웃오브밴드가 공격 환경에 따라 선택되는 구조.

비교 대상은 인밴드, 블라인드(추론형), 아웃오브밴드 세 유형이다.

| 비교 축 | 인밴드 (Union·Error) | 추론형 (Blind) | 아웃오브밴드 (OOB) |
| --- | --- | --- | --- |
| 결과 확인 채널 | 응답 본문에 직접 출력 | HTTP 응답 코드·크기·지연 시간 | 공격자가 구축한 외부 DNS·웹 서버 |
| 공격 속도 | 매우 빠름 (짧은 시간에 대량 유출) | 느림 (비트 단위 질의 반복) | 빠름 (비동기 전송) |
| 탐지 난이도 | 낮음 (WAF(Web Application Firewall) 시그니처, 에러 모니터링) | 높음 (정상 파라미터와 유사) | 높음 (아웃바운드 DNS 질의에 은닉) |
| 필요 전제 | 쿼리 결과나 에러가 화면에 출력 | 참·거짓에 따른 미세한 응답 차이 | DB의 외부 네트워크 통신 허용 |
| 대표 기법 | UNION 결합, 에러 유도 | SLEEP 지연으로 참·거짓 판별 | DBMS 함수로 외부 경로 질의 (예: xp_dirtree) |

- 선택 기준 : 공격자는 응답 채널이 열려 있으면 인밴드를, 응답이 막혀 있으면 블라인드를, 아웃바운드가 열려 있으면 OOB를 택하므로 방어는 세 경로를 모두 막아야 함.

## Ⅴ. SQL 인젝션의 한계와 방안

- 핵심 요약 : 블랙리스트 필터의 우회, 동적 식별자 바인딩의 한계, 레거시 코드의 수정 부담을 매개변수화 쿼리, 화이트리스트, 가상 패치로 보완.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **블랙리스트 필터** 우회 | 주석 치환, 인코딩 변형, 대소문자 혼합 등으로 정규식 필터가 무력화 | 블랙리스트를 폐기하고 SQL 구문과 데이터를 분리하는 **매개변수화 쿼리** (Parameterized Query) 및 ORM(Object-Relational Mapping) 도입 | 필터 우회 시도 탐지 건수 |
| 동적 식별자와 정렬 구문의 바인딩 불가 | Prepared Statement는 값만 바인딩할 수 있어 컬럼명이나 ORDER BY 구문에서 문자열 결합 유혹 발생 | 허용 목록(화이트리스트)에 든 필드명만 매핑하고, 불일치 시 기본 정렬로 치환 | 비허용 입력 차단 건수 |
| 대규모 레거시 코드의 수정 부담 | 수백만 라인에 흩어진 문자열 결합 DAO(Data Access Object) 코드를 전수 점검하기 어려움 | **SAST** (Static Application Security Testing)로 취약 지점을 찾고, 수정 전까지 WAF 가상 패치(Virtual Patching)와 **RASP** (Runtime Application Self-Protection)을 과도기적으로 적용 | 취약 지점 잔존 건수 |

## Ⅵ. SQL 인젝션의 기술사적 제언

- 핵심 요약 : 개발 표준과 빌드 검사, 최소 권한 DB 계정, 공통 예외 처리를 함께 갖춰 인젝션이 구조적으로 발생하지 않는 개발 체계를 만드는 방향.

1. 전사 개발 표준에 문자열 치환 방식의 쿼리 작성을 금지하는 규칙을 두고, 빌드 파이프라인에서 이를 자동 검사하여 위반 코드가 배포되지 않도록 관리하는 것이 바람직하다.
2. 웹 애플리케이션이 쓰는 DB 계정은 업무 조회와 갱신에 필요한 권한만 가지도록 설계하고, 테이블 구조 변경 권한과 시스템 프로시저 실행 권한은 애초에 부여하지 않아야 한다.
3. DBMS의 오류 상세 정보가 사용자 화면에 노출되지 않도록 공통 예외 처리 계층을 두어, 공격자가 DB 구조를 추측할 단서를 주지 않도록 할 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : SQL 인젝션은 입력과 구문을 섞는 설계 실수에서 비롯되며, 쿼리와 데이터를 분리하는 것이 근본 해법임.
- 시사점 : 필터링은 우회되기 쉬우므로 방어의 중심을 쿼리 구조에 두고, 탐지·차단 장비는 보조 계층으로 운용해야 함.
