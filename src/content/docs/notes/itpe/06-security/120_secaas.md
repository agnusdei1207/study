## 지식 로드맵 내 현재 위치

지식 위치: 클라우드 보안 → 서비스형 보안 기능 → **SECaaS**

## 30초 인출

- 본질: 신원 관리·웹/메일 보호·탐지·키 관리 등 보안 기능을 클라우드 서비스로 제공받는 방식
- 메커니즘: 인라인 트래픽 검사·API 연계·로그 분석 등 기능별 경로로 보안 정책과 탐지·대응을 제공
- 통찰: 한계: 공급자 운영만으로 고객의 보안 책임이 사라지지 않음 → 방안: 서비스별 데이터 경로·정책 설정·로그·사고 대응의 분계를 확인

<details>
<summary>핵심 용어</summary>

- **SECaaS** : 보안 기능을 클라우드 서비스로 제공·이용하는 모델.
- **인라인형** : 사용자와 목적지 사이의 트래픽을 서비스가 경유하며 검사하는 방식.
- **API 연동형** : 서비스 간 API로 설정·이벤트·데이터를 교환해 보안 기능을 제공하는 방식.
- **책임 분계** : 공급자와 고객이 맡는 설정·운영·사고 대응 범위의 구분.

</details>

## 2~4교시 예상문제 (25점)

> SECaaS의 기능·제공 구조·도입 효과를 설명하고, 서비스 장애·데이터 보호·책임 분계의 대응을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

### Ⅰ. 개요

| 항목 | 개요 |
|---|---|
| 정의 | SECaaS는 신원 관리·트래픽 보호·탐지 등 보안 기능을 클라우드 서비스로 제공받는 운영 모델 |
| 목적 | 필요 범위의 보안 기능 적용과 서비스별 운영 부담·대응 책임 관리 |

보안 솔루션의 기능을 서비스 사업자의 클라우드에서 제공받는 운영 방식. 자체 장비의 구매·운영 부담을 줄일 수 있으나, 구성·책임·가용성은 서비스별 평가가 필요.

### Ⅱ. 제공 구조

```text
사용자·응용·워크로드
       ├─ 인라인형: 웹/메일 트래픽 → 보안 서비스 → 목적지
       ├─ API형: 클라우드 자원 설정·활동 정보 ↔ 보안 서비스
       └─ 로그형: 이벤트 → 분석/관제 서비스 → 경보·대응 연계
```

모든 기능이 동일한 인라인 경로를 거친다는 그림은 부정확.

### Ⅲ. 기능별 선택

| 목적 | 기능 예 | 검증 관점 |
|---|---|---|
| 사용자 통제 | IAM·CASB | 권한·SSO 연계·세션 정책 |
| 트래픽 보호 | 보안 웹 게이트웨이·메일 보안 | 지연·검사 범위·우회 경로 |
| 탐지·대응 | IDS/IPS·SIEM·관리형 탐지 | 로그 품질·처리 책임·복구 절차 |
| 데이터 보호 | DLP·키 관리 | 데이터 위치·키 소유·접근 기록 |

CSA의 2011년 분류는 당시 범주이며, 현재 SECaaS를 고정된 '12개 항목'으로 정의하는 근거가 아님. CSA Security Guidance v5에서는 독립적인 SECaaS 도메인을 제거.

#### 효과와 한계

| 효과 | 한계·대응 |
|---|---|
| 기능의 신속한 도입 | 기존 정책·예외와의 통합 시험 |
| 공급자의 업데이트 활용 | 변경 고지·롤백·검증 체계 |
| 여러 사이트의 중앙 운영 | 장애 시 우회·차단 정책과 SLA |
| 전문 인력 보완 | 내부 소유자의 결정·감사 책임 유지 |

#### 규제·계약

인증 요건은 산업·업무·서비스 범위별로 확인. 특정 SECaaS 제품 전체에 CSAP 등 단일 인증이 무조건 필요한 것으로 일반화하지 않음. 로그·개인정보 국외 이전, 위탁, 사고 통지와 종료 시 데이터 반환 조건을 계약에 반영.

### Ⅳ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 공급자 운영만으로 고객의 설정·데이터 보호 책임이 사라지지 않음 | 서비스별 데이터 경로·권한·로그·사고 대응 분계를 확인 |

### Ⅴ. 제언

기능 목록보다 데이터 흐름·장애 모드·책임 분계를 먼저 설계하고, 실제 트래픽과 위협을 이용해 서비스 효과를 검증.
