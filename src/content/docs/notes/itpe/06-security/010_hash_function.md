## 큰 그림과 30초 인출

```text
임의 길이 메시지 M ── Hash ──▶ 고정 길이 다이제스트 h
       │                            │
       ├─ 무결성 검증: H(M) 비교    ├─ 전자서명: 다이제스트에 서명
       ├─ 인증: HMAC                └─ 비밀번호: Salt+KDF
       └─ 데이터 식별·체인 연결

보안성: 역상 저항성 / 제2역상 저항성 / 충돌 저항성
```

- 본질: **복호화하는 암호화가 아니라, 입력을 고정 길이 지문으로 압축해 변조 여부와 결합 관계를 검증하는 단방향 함수**
- 현행 중심: SHA-2·SHA-3 계열; MD5·SHA-1은 충돌 저항이 필요한 신규 보안 설계에서 제외
- 비밀번호: 단순 해시가 아니라 Salt와 반복·메모리 비용을 갖는 전용 KDF 사용

## 예상문제

> 암호학적 해시 함수의 개념과 보안 요구사항, 구조와 활용을 설명하고 충돌공격·레인보우테이블 대응 및 알고리즘 전환방안을 제시하시오. (25점)

## Ⅰ. 데이터 무결성과 결합을 검증하는 해시 함수 개요

- 정의: **암호학적 해시 함수**는 임의 길이 입력을 고정 길이 다이제스트로 변환하며, 입력 복원과 동일·연관 입력 탐색이 계산상 어렵도록 설계된 함수
- 목적: 메시지 무결성, 전자서명의 효율적 서명 대상 생성, 메시지 인증, 비밀번호 검증, 콘텐츠 식별 지원
- 한계: 해시만으로 송신자 인증과 기밀성을 보장하지 않으며, 공격자가 메시지와 해시를 함께 바꿀 수 있는 구간에는 키 기반 인증 또는 전자서명 필요

## Ⅱ. 결정성·눈사태 효과와 세 가지 보안 요구사항

| 요구사항 | 공격자 목표 | 보안 의미 |
|---|---|---|
| **역상 저항성** | 주어진 `h`에서 `H(M)=h`인 M 탐색 | 다이제스트로 원문 복원 곤란 |
| **제2역상 저항성** | 주어진 M과 같은 해시의 다른 M' 탐색 | 특정 원문 대체 곤란 |
| **충돌 저항성** | 같은 해시를 갖는 임의 M, M' 탐색 | 서로 다른 문서의 동일 지문 조작 방지 |
| **결정성** | 같은 입력의 결과 일관성 | 저장·전송 전후 검증 가능 |
| **눈사태 효과** | 입력의 작은 변화가 출력 전반 변화 | 입력 간 통계적 관계 은닉 |

## Ⅲ. 전처리·압축·다이제스트 생성 구조

```text
[Message]
   │ Padding·Length Encoding
   ▼
[Block 1] → Compression → Chaining Value 1
                                  │
[Block 2] ────────────────────────┘ → ... → [Digest]

SHA-2: 반복 압축 구조 중심
SHA-3: Keccak Sponge = Absorb → Permutation → Squeeze
```

| 구성 | 책임 |
|---|---|
| **전처리** | 메시지를 알고리즘 블록 규격에 맞게 패딩·분할 |
| **압축·순열** | 입력 블록과 내부 상태를 반복 혼합 |
| **연쇄 상태** | 이전 블록 결과를 다음 처리에 반영 |
| **다이제스트 출력** | 규격 길이의 최종 해시값 생성 |

## Ⅳ. 목적별 안전한 적용 절차

```text
무결성: 원본 H(M) 저장 → 수신 M' 해시 → 안전하게 보관된 값과 비교
인증  : 송신 HMAC(K,M) → 수신자가 K로 재계산·상수시간 비교
서명  : H(M) → 개인키 서명 → 공개키 검증 + 수신 메시지 해시 비교
암호저장: Password + Unique Salt → Password KDF → 검증값 저장
```

- 일반 파일 해시를 비밀번호 저장에 그대로 사용하면 대량 추측에 취약하므로 전용 비밀번호 KDF를 적용
- 무결성 기준값이 공격자와 같은 변경 권한에 있으면 검증 의미가 없으므로 서명·HMAC·신뢰 저장소로 기준값을 보호

## Ⅴ. 해시·암호화·MAC·전자서명 비교

| 기준 | 해시 | 대칭키 암호화 | HMAC | 전자서명 |
|---|---|---|---|---|
| 주목적 | 무결성 지문 | 기밀성 | 무결성+공유키 인증 | 무결성+서명자 인증·부인방지 |
| 키 | 없음 | 공유 비밀키 | 공유 비밀키 | 개인키 서명·공개키 검증 |
| 원문 복원 | 불가 | 복호화 가능 | 불가 | 서명 대상 원문은 별도 |
| 제3자 검증 | 기준값 보호 필요 | 공유키 보유자 | 공유키 보유자 | 공개키로 가능 |
| 대표 적용 | 파일 식별 | 데이터 암호화 | API 메시지 인증 | 전자문서·코드서명 |

## Ⅵ. 충돌·사전계산 공격과 전환대책

| 문제 | 원인 | 대책 | 검증 |
|---|---|---|---|
| **충돌 가능 알고리즘** | MD5·SHA-1 등 낡은 선택 | SHA-2·SHA-3 계열로 전환, 알고리즘 식별자 저장 | 신규·기존 데이터 검증 호환성 |
| **레인보우테이블** | 무염·동일 해시 반복 저장 | 사용자별 고유 Salt와 비밀번호 KDF | Salt 중복률, 파라미터 준수율 |
| **고속 무차별 대입** | 범용 고속 해시의 낮은 비용 | 반복·메모리 비용 조정, 재해시 정책 | 검증 지연·공격비용·서비스 부하 |
| **해시 길이 확장 오용** | 단순 `H(K||M)` 방식의 취약 설계 | 표준 HMAC 사용 | 테스트 벡터·라이브러리 검증 |
| **전환 불가 구조** | 알고리즘·파라미터를 데이터와 미기록 | 버전·알고리즘·Salt·비용 파라미터 저장 | 점진적 재해시 성공률 |

- 암호 민첩성: 알고리즘을 코드에 고정하지 않고 승인 목록·버전·전환 기간·재처리 절차를 관리
- 비교 구현: 비밀값 검증은 조기 종료 비교 대신 상수시간 비교 함수를 사용해 시간 부채널을 줄임

## Ⅶ. 해시 선택보다 목적과 키·Salt 관리가 중요한 결론

- 해시는 단독 보안 기능이 아니라 **무결성, 인증, 전자서명, 비밀번호 저장**의 목적에 맞는 구성요소로 배치해야 함
- 신규 설계에서는 승인된 SHA-2·SHA-3 및 표준 HMAC·비밀번호 KDF를 사용하고, 알고리즘 식별자와 파라미터를 보존해 향후 전환 가능성을 확보해야 함

## 1교시 10점 답안 발췌

### 1. 정의와 보안성

- 임의 길이 입력을 고정 길이 다이제스트로 변환하는 단방향 함수
- 역상·제2역상·충돌 저항성과 눈사태 효과 필요

### 2. 구조와 활용

```text
Message → Padding/Block → Compression·Permutation → Digest
                 ├─ HMAC
                 ├─ Digital Signature
                 └─ Salt + Password KDF
```

### 3. 적용 원칙

- MD5·SHA-1은 신규 보안 설계에서 제외하고 SHA-2·SHA-3, HMAC, Salt 기반 전용 KDF를 목적별로 적용
