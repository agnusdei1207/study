## 연관 키워드

- 해시 함수(Hash Function), 다이제스트(Digest), 단방향성, 충돌 저항성(Collision Resistance)
- 눈사태 효과(Avalanche Effect), 생일 공격(Birthday Attack), SHA-3, HMAC
- 솔트(Salt), Argon2, 레인보우 테이블(Rainbow Table), 그로버 알고리즘(Grover Algorithm)

## Ⅰ. 해시 함수의 개요

- 핵심 요약 : 임의 길이의 입력을 고정 길이 값으로 바꾸는 단방향 함수로, 무결성 검증과 안전한 비밀번호 저장의 기반이 되는 기술.
- 개념 : 임의 길이의 입력 데이터를 고정 길이의 **다이제스트** (Digest, 해시 값)로 변환하는 알고리즘을 **해시 함수** (Hash Function)라 하며, 암호학적 해시 함수는 역산이 어렵도록 설계되며, 대표 표준으로 **SHA** (Secure Hash Algorithm) 계열이 있음.
- 배경 및 필요성 : 데이터를 전송하거나 보관할 때 위변조 여부를 확인해야 하고, 비밀번호는 원문 대신 해시 값으로 저장해야 하며, 전자서명과 블록체인 작업증명(PoW, Proof of Work)도 해시에 의존함.
- 주요 목적 : 데이터 **무결성** (Integrity) 확인, 원본 역산이 어려운 단방향성 제공, 데이터의 고유 식별자 생성.

## Ⅱ. 해시 함수의 특징 및 장점

- 핵심 요약 : 고정 길이 출력과 세 가지 안전성 요건, 눈사태 효과가 위변조 탐지와 역산 방지의 근거가 되는 구조.

1. 고정 길이 출력 : 입력 크기와 관계없이 정해진 길이의 다이제스트를 생성 → 대용량 데이터도 짧은 값으로 비교 가능.
2. **눈사태 효과** (Avalanche Effect, 입력이 조금 바뀌면 출력이 크게 바뀌는 성질) : 입력 1비트 변경이 출력 비트의 절반가량을 바꿈 → 미세한 변조도 값 비교로 드러남.
3. 단방향성과 충돌 저항성 : 출력으로 입력을 구하기 어렵고 같은 출력을 내는 두 입력을 찾기 어려움 → 원본 노출 없이 무결성을 확인할 수 있음.
4. 키 기반 확장 : **HMAC** (Hash-based Message Authentication Code, 비밀키를 결합한 메시지 인증 코드)과 키 스트레칭으로 확장 → 메시지 인증과 비밀번호 보호로 응용 범위 확대.

## Ⅲ. 해시 함수의 구조 (흐름)

- 핵심 요약 : 송신 측과 수신 측이 같은 함수로 다이제스트를 각각 계산해 비교하는 무결성 검증 흐름과, 블록을 순차 압축하는 내부 구조.
- 암호학적 해시 함수는 **제1 역상 저항성** (Preimage Resistance, 출력으로 입력을 찾기 어려움), **제2 역상 저항성** (Second Preimage Resistance, 같은 출력을 내는 다른 입력을 찾기 어려움), **충돌 저항성** (Collision Resistance, 같은 출력을 내는 두 입력을 찾기 어려움)의 세 요건을 충족해야 함.

```text
[ 무결성 검증 흐름 ]

원본 데이터
      ↓ 해시 함수 적용
다이제스트 A (송신 측 보관·전송)
      ↓ 수신 측에서 동일 함수로 재계산
다이제스트 B
      ↓ A와 B 비교
일치: 무결성 확인 / 불일치: 위변조 의심
```

```text
[ Merkle-Damgård 구조 (SHA-2) ]

메시지 블록 1
      ↓ 압축 함수 (상태 h0 → h1)
메시지 블록 2
      ↓ 압축 함수 (상태 h1 → h2)
      ↓
최종 다이제스트
```

## Ⅳ. 해시 함수의 비교

- 핵심 요약 : 세대가 올라갈수록 출력 길이가 길어지고 내부 구조가 개선되었으며, MD5와 SHA-1은 보안 용도로 사용하지 않는 것이 원칙.

| 비교 항목 | MD5 (Message Digest 5) | SHA-1 | SHA-2 (SHA-256, SHA-512) | SHA-3 (Keccak) |
| --- | --- | --- | --- | --- |
| 출력 길이 | 128비트 | 160비트 | 224·256·384·512비트 | 224·256·384·512비트 |
| 내부 구조 | Merkle-Damgård | Merkle-Damgård | Merkle-Damgård | 스펀지(Sponge) 구조 |
| 충돌 공격 현황 | 실용적 충돌 사례 공개 | 실용적 충돌 시연(SHAttered) | 알려진 실용적 충돌 공격 없음 | 알려진 실용적 충돌 공격 없음 |
| 길이 확장 공격 | 취약 | 취약 | 구성 방식에 따라 취약 (HMAC 사용 권장) | 구조적으로 면역 |
| 권장 용도 | 체크섬 용도로 한정 | 신규 사용 중단 | 일반 보안 표준 | 차세대 표준으로 병행 사용 |

- 선택 기준 : 신규 시스템은 최소 256비트 이상의 SHA-2나 SHA-3를 사용하고, 메시지 인증은 단순 해시 대신 HMAC 구성을 사용.

## Ⅴ. 해시 함수의 한계와 방안

- 핵심 요약 : 사전 계산 공격, 생일 공격, 양자 컴퓨터의 탐색 가속이라는 세 가지 위협을 솔트, 출력 길이 확대, 메모리 하드 알고리즘으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **레인보우 테이블** (Rainbow Table) 및 GPU 대입 공격 | 솔트 없이 단순 해시로 비밀번호를 저장하면 사전 계산 표와 고성능 GPU로 원문이 역산됨 | 사용자별 **솔트** (Salt) 적용, 반복 연산과 메모리 하드 알고리즘인 Argon2id, bcrypt 사용 | 단순 해시 저장 건수 |
| **생일 공격** (Birthday Attack) | n비트 해시는 약 2^(n/2)번의 시도로 충돌이 발생할 수 있어, 128비트 이하는 충돌 위험이 큼 | 256비트 이상 해시 함수로 전환, 레거시 해시 사용 금지 | 128비트 이하 해시 사용 건수 |
| **그로버 알고리즘** (Grover Algorithm) 기반 탐색 가속 | 양자 컴퓨터에서 역상 탐색 비용이 제곱근 수준으로 줄어듦 | 장기 보관 서명과 중요 인프라에 384·512비트 출력 선적용 | 장기 보관 서명의 해시 길이 |

## Ⅵ. 해시 함수에 대한 기술사적 제언

- 핵심 요약 : 비밀번호 저장, API 메시지 인증, 배포 파이프라인의 세 영역에서 취약 해시를 걷어내는 전환 계획.

비밀번호 저장 체계는 레거시 단순 해시를 Argon2id 같은 메모리 하드 키 유도 함수로 이관하는 계획을 세우고, 인증 서버 담당 조직이 전환 일정을 주도하는 것이 바람직하다.

서비스 간 API 호출은 타임스탬프와 논스(Nonce)를 포함한 HMAC-SHA-256 서명을 전사 공통 규약으로 두어, 재전송과 변조를 함께 막는 것이 현실적이다.

배포 파이프라인에는 MD5나 SHA-1 사용을 자동으로 차단하는 정적 검사를 넣고, 공급망 소프트웨어의 해시와 서명 알고리즘을 주기적으로 목록화해 점검해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 해시 함수는 원본을 드러내지 않고 무결성을 확인하는 암호학의 기본 도구.
- 시사점 : 알고리즘 자체의 안전성보다 용도에 맞는 구성(솔트, HMAC, 메모리 하드 함수)을 고르는 것이 실제 보안 수준을 좌우함.
