## 연관 키워드

- XZ Utils, liblzma, CVE-2024-3094, 공급망 백도어, OpenSSH
- IFUNC, GOT, 재현 가능한 빌드, SLSA, 사회공학, 전체 RELRO, 최소 권한 원칙

## Ⅰ. XZ Utils 백도어(CVE-2024-3094)의 개요

- 핵심 요약 : 리눅스 압축 라이브러리의 배포 아카이브 안에 숨겨져 SSH 인증을 우회하려 한 공급망 백도어.
- 개념 : 리눅스 배포판에 널리 쓰이는 압축 라이브러리 liblzma(XZ Utils)의 공식 배포 tarball에 은닉된 **공급망 백도어** (Supply Chain Backdoor, 빌드와 배포 과정에 심어진 악성 코드)로, OpenSSH 서버(sshd)를 하이재킹해 인증 없이 원격 코드 실행(RCE, Remote Code Execution)을 가능하게 하려 한 사건. 취약점 식별 번호는 CVE(Common Vulnerabilities and Exposures) CVE-2024-3094임.
- 배경 및 필요성 : 2024년 3월 말 SSH 접속 지연을 추적하던 개발자가 이상을 발견해 정식 배포판으로 확산되기 전에 차단됨. 리눅스 핵심 라이브러리의 빌드 과정에 수년간 정교하게 침투한 사례로, 오픈소스 기여 거버넌스와 배포물 무결성 검증의 중요성을 드러냄.
- 주요 목적 : 원격 접속의 관문인 SSH 데몬에 은밀한 통로를 만들어 임의 시스템의 제어권을 확보하는 것.

## Ⅱ. XZ Utils 백도어(CVE-2024-3094)의 특징 및 장점

- 핵심 요약 : 정상 기여로 쌓은 신뢰, 배포물 안의 은닉, 특정 환경에서만 활성화되는 조건부 실행이 결합된 다단계 공격.

1. 사회공학적 신뢰 축적 : 수년간 정상 기여를 쌓아 메인테이너 권한을 얻음 → 코드 검토의 경계를 자연스럽게 통과.
2. 배포물 은닉 : 페이로드를 소스 저장소가 아닌 tarball의 빌드 스크립트와 테스트 파일에 분산 → 저장소 중심 검토로는 발견이 어려움.
3. 조건부 활성화 : x86-64 리눅스와 GCC 빌드 환경에서만 동작 → 분석 환경을 피해 탐지를 늦춤.

## Ⅲ. XZ Utils 백도어(CVE-2024-3094)의 구조 (흐름)

- 핵심 요약 : 빌드 단계에서 페이로드가 복원되고, 실행 단계에서 sshd의 인증 함수가 가로채지는 두 단계 흐름.

```text
[ 1. 빌드 단계 ]

정상 소스 + 위장된 테스트 파일
              ↓
배포 tarball에 악성 m4 스크립트 주입
              ↓
배포판 빌드 시 조건 확인 후 페이로드 복원
```

```text
[ 2. 실행 단계 ]

sshd 실행 → libsystemd 로드 → liblzma 로드
              ↓
IFUNC 해석 단계에서 함수 주소 변조
              ↓
RSA_public_decrypt를 공격자 루틴으로 교체
              ↓
서명된 인증 요청에만 명령 셸 제공
```

1. **IFUNC** (GNU Indirect Functions, 동적 링커가 심볼 해석 시점에 구현 함수를 선택하는 기능) 후킹 : 실행 초기에 함수 주소 결정 과정을 가로채 임의 코드를 실행.
2. **GOT** (Global Offset Table, 동적 링크된 함수 주소를 담는 전역 테이블) 변조 : sshd의 인증 확인 함수인 RSA_public_decrypt의 주소를 백도어 루틴으로 교체.
3. 페이로드 은닉 : 테스트 디렉터리의 정상처럼 보이는 파일에서 `sed`와 `tr` 명령으로 바이너리를 복원.
4. 서명 기반 실행 : 공격자의 Ed448 개인키로 서명된 인증 패킷에만 명령 셸을 제공하는 비대칭 서명 방식.

- 핵심 요약 : 일반 취약점은 실수로 생긴 결함인 반면, 이 백도어는 배포 과정의 신뢰를 노린 의도적 설계였음.

| 코드 위치 | 저장소의 소스 파일 | 배포 tarball의 빌드 스크립트와 테스트 파일 |
| 탐지 방법 | 정적 분석 도구(SAST, Static Application Security Testing), 퍼징 | 저장소와 배포물의 차이 검증, 재현 빌드 비교 |

## Ⅴ. XZ Utils 백도어(CVE-2024-3094)의 한계와 방안

- 핵심 요약 : 배포물 검증 부재, 단일 관리자 의존, 과도한 의존성, 링커 단계 후킹을 재현 빌드, 다자 유지보수, 최소 의존성, 보안 링크 옵션으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 저장소와 배포물의 불일치 미검증 | tarball 내용을 소스 저장소와 대조하지 않는 관행 | 저장소에서 직접 컴파일하는 재현 가능한 빌드(Reproducible Builds) 의무화, 배포물과 저장소 간 SHA(Secure Hash Algorithm)-256 해시와 차이 검증 자동화 | 재현 빌드 일치율 |
| 단일 관리자 의존 | 소수 인력과 고립된 상황을 노린 사회공학적 기여 | 다자 유지보수 체계 구축과 서명 키의 다중 통제 | 서명 키 접근 권한자 수 |
| 과도한 의존성 | sshd가 알림 기능을 위해 libsystemd를 거쳐 liblzma를 로드 | 최소 권한 원칙에 따라 sshd에서 불필요한 의존성을 분리하고 프로세스 간 통신으로 대체 | 데몬이 로드하는 라이브러리 수 |
| 링커 단계 후킹 허용 | IFUNC 해석 시점에 검증 없이 임의 코드가 실행될 수 있음 | 전체 RELRO(Full RELRO, Relocation Read-Only)와 즉시 바인딩(-z now) 적용으로 GOT를 읽기 전용화 | 보안 링크 옵션 적용 비율 |

## Ⅵ. XZ Utils 백도어(CVE-2024-3094)에 대한 기술사적 제언

- 핵심 요약 : 빌드 출처의 증명, 오픈소스 유지보수 체계, 배포판 기본 하드닝을 세 축으로 묶어 내재화해야 함.

1. 빌드 무결성 : 배포 산출물을 소스 저장소의 태그에서 자동으로 재생성하고, 빌드 출처를 증명하는 SLSA(Supply-chain Levels for Software Artifacts) 수준을 목표로 관리하는 체계 필요.
2. 오픈소스 거버넌스 : 핵심 라이브러리에 재정 지원과 복수 유지보수자 체계를 제도화하여 권한이 한 개인에게 쏠리는 구조를 줄이는 방향 필요.
3. 시스템 하드닝 : 배포판의 기본 링크 옵션과 보안 기준선에 하드닝 설정을 포함시켜, 개별 운영자가 설정하지 않아도 보호되는 환경 필요.

## Ⅶ. 결론

- 핵심 요약 : XZ Utils 백도어는 코드 결함이 아니라 신뢰 관계와 배포 과정의 틈을 노린 공급망 공격이었음.
- 시사점 : 소스와 배포물의 일치를 검증하고 빌드 과정을 감시하는 조직이어야 같은 유형의 침투를 조기에 가려낼 수 있음.
