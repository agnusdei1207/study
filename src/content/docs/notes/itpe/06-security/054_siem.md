## 연관 키워드

- SIEM, 로그 정규화, 상관분석, 이벤트 수집, 경보 피로
- UEBA, SOAR, 위협 인텔리전스(CTI), IoC, 위협 헌팅, OCSF
- Cyber Kill Chain, APT, EDR, TLS, JA3/JA4, 보안 데이터 레이크

## Ⅰ. SIEM의 개요

- 핵심 요약 : 여러 시스템의 로그를 한곳에 모아 상관분석으로 위협을 찾아내는 중앙 집중형 보안 관제 플랫폼.
- 개념 : 이기종 IT 인프라(서버, 네트워크, 보안 장비, 클라우드, 데이터베이스 등)의 로그와 보안 이벤트를 실시간으로 수집·정규화하고, 상관분석 룰과 기계학습으로 위협을 탐지해 경보하는 **SIEM**(Security Information and Event Management)의 중앙 플랫폼.
- 배경 및 필요성 : 방화벽, IPS(Intrusion Prevention System), WAF(Web Application Firewall) 등 개별 장비가 만드는 파편화된 로그로는 **침해 공격 경로**(Cyber Kill Chain, 공격의 단계별 흐름 모델)를 한눈에 보기 어려워, 전사 관점의 관제 사각지대를 줄이기 위해 등장.
- 핵심 목적 : 전사 보안 가시성 일원화, **지능형 지속 위협**(APT, Advanced Persistent Threat)의 상관분석 탐지, 로그 보관 등 법적 요구 준수와 침해 조사 효율화.

## Ⅱ. SIEM의 특징 및 장점

- 핵심 요약 : 로그를 공통 형식으로 맞추고 여러 장비의 이벤트를 엮어 보는 능력이, 단일 장비로는 놓치는 공격 흐름을 찾아내는 장점으로 이어지는 구조.

1. 대용량 수집 : 여러 원천의 로그를 실시간으로 받아 저장 → 한 시스템에서 보이지 않는 이상 징후를 전사 단위로 조회.
2. **로그 정규화**(Normalization) : 제조사별로 다른 형식을 **OCSF**(Open Cybersecurity Schema Framework) 같은 공통 스키마로 변환 → 통합 검색과 룰 재사용이 가능.
3. **상관분석**(Correlation Analysis) : 시간, IP, 사용자 계정 축으로 이벤트를 결합 → 단일 로그로는 알 수 없는 공격 시나리오 추적.
4. **UEBA**(User and Entity Behavior Analytics, 사용자·장비 행위 분석) : 사용자와 장비의 평소 행위를 기준선으로 삼아 이상 행위를 탐지 → 알려지지 않은 내부 위협에도 대응.

## Ⅲ. SIEM의 구조 (흐름)

- 핵심 요약 : 수집, 정규화, 상관분석, 경보의 순서로 흐르고, 경보는 분석가 판단과 **SOAR**(Security Orchestration, Automation and Response) 자동 대응으로 이어지는 구조.

```text
[ SIEM 데이터 파이프라인 ]

분산 로그 소스
(방화벽, AD, EDR, 클라우드 감사로그)
      ↓ 1. 실시간 수집 (Syslog, API)
수집·정규화 계층
      ↓ 2. 공통 스키마 매핑
상관분석·탐지 엔진
      ↓ 3. 고신뢰 인시던트 경보
SOC 분석가 → SOAR 연동 자동 대응
```

```text
[ 상관분석 시나리오 예 ]

외부 스캔 탐지
      ↓
로그인 실패 반복
      ↓
관리자 권한 상승
      ↓
대량 파일 전송 → 고신뢰 경보
```

- **위협 인텔리전스**(CTI, Cyber Threat Intelligence) 연동 : 수집된 IP나 파일 해시를 **IoC**(Indicator of Compromise, 침해 지표)와 대조해 경보 우선순위를 조정.
- 상관분석은 개별 이벤트가 아니라 여러 장비의 이벤트가 이어지는 시퀀스를 룰로 정의하는 것이 핵심.

## Ⅳ. SIEM의 비교

- 핵심 요약 : 온프레미스 SIEM은 고정 장비의 용량 한계에, 클라우드 SIEM은 데이터 송출 비용에, 차세대 SIEM은 행위 분석의 기준선 확보에 각각 제약이 있음.

| 비교 항목 | 전통적 온프레미스 SIEM | 클라우드 네이티브 SIEM | 차세대 SIEM + UEBA |
| --- | --- | --- | --- |
| 인프라 | 전용 장비와 물리 스토리지 | 클라우드 서비스형 제공 | 분산 빅데이터 플랫폼 |
| 확장성 | 스토리지 증설 시 장비 추가 필요 | 클라우드 자원에 따라 탄력 확장 | 분산 스트리밍으로 대용량 처리 |
| 분석 방식 | 정적 룰 기반 | 클라우드 질의와 위협 헌팅 | 정적 룰 + 비지도 학습 행위 분석 |
| 과금 기준 | 초당 이벤트 수 기반 라이선스 | 수집 데이터량 기반 과금 | 사용자 또는 노드 수 기반 |
| 주요 한계 | 경보 피로, 수집 병목 | 데이터 송출 비용 | 학습을 위한 초기 기준선 필요 |

- 선택 기준 : 로그 발생량, 클라우드 전환 정도, 분석 인력의 역량을 기준으로 수집 범위와 분석 방식을 정함.

## Ⅴ. SIEM의 한계와 방안

- 핵심 요약 : 경보 과잉, 클라우드 로그 전송 비용, 암호화 트래픽의 가시성 상실을 위험 점수화, 엣지 필터링, 메타데이터 결합으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 오탐 경보 과잉과 **경보 피로** | 대량의 무의미한 경보가 실제 침해 신호를 묻음 | **위험 점수화**(Risk-based Alerting)로 경보를 중복 제거하고, 단순 경보는 SOAR로 자동 처리 | 경보 대비 실제 인시던트 비율 |
| 클라우드 전환에 따른 로그 전송 비용 | 모든 로그를 중앙으로 보내면 네트워크 송출 비용이 크게 증가 | **엣지 전처리 필터**(Logstash, Cribl)로 불필요한 디버그 로그를 원천에서 제거 | 로그 전송량 대비 탐지 기여도 |
| **TLS**(Transport Layer Security) 암호화 확산 | 페이로드 검사가 불가능해 IP·포트 같은 메타데이터 분석에 머무름 | EDR 텔레메트리와 DNS 쿼리 로그를 결합하고, **JA3/JA4**(TLS 지문) 기반 행위 프로파일링 적용 | 암호화 트래픽 중 식별 가능 비율 |

## Ⅵ. SIEM에 대한 기술사적 제언

- 핵심 요약 : 로그 형식과 저장 계층을 표준화하고, 탐지를 분석가의 능동적 활동과 결합하는 운영 체계로 전환하는 것이 핵심.

1. 벤더 종속 로그 형식을 줄이기 위해 OCSF 같은 개방형 스키마를 전사 기준으로 채택하고, 신규 장비 도입 시 이 기준에 맞는 수집 규격을 요구해야 한다.
2. 자주 조회되는 최근 데이터는 SIEM에 두고, 장기 보존 로그는 저비용 저장소로 넘기는 보안 데이터 레이크 구조로 나누어 운영하면 비용과 조회 성능을 함께 관리할 수 있다.
3. 경보를 기다리기만 하지 않고, MITRE ATT&CK 기법을 기준으로 로그를 능동적으로 탐색하는 **위협 헌팅**(Threat Hunting) 인력을 두어 잠복한 공격을 찾아야 한다.

## Ⅶ. 결론

- 핵심 요약 : SIEM은 흩어진 로그를 하나의 관제 시야로 묶어 공격의 흐름을 보게 하는 플랫폼임.
- 시사점 : 도구의 성능보다 수집 범위, 룰 품질, 분석 인력의 대응 절차가 관제 효과를 좌우하므로, 세 요소를 함께 설계하는 조직이 실효성 있는 관제를 얻음.
