## 지식 로드맵 내 현재 위치

지식 위치: 네트워크 보안 → IoT 악성코드 → **미라이 봇넷**

## 30초 인출

- **본질:** 공장 초기 기본 자격증명(Default Credentials)이 노출된 IP 카메라, 홈 라우터 등 IoT 기기를 대량 감염시켜 테라비트급 분산 서비스 거부(DDoS) 공격을 수행하는 악성코드 및 좀비 네트워크
- **메커니즘:** 무작위 IPv4 Telnet(23/2323) 스캔 → 사전 정의된 자격증명 대입 → 타깃 CPU 아키텍처별 맞춤 로더 다운로드 및 실행 → C2 지시 기반 L3~L7 DDoS 트래픽 투사
- **통찰:** 단순 재부팅은 수분 내 재감염되므로 기기별 고유 비밀번호 강제 및 MUD 프로파일 기반 네트워크 격리와 Anycast 스크러빙 다층 방어 체계 필수

<details>
<summary>핵심 용어</summary>

- **Mirai** : 기본 계정을 악용해 리눅스 임베디드 기기를 감염시키고 대규모 DDoS를 감행한 대표적 IoT 악성코드.
- **Botnet** : 공격자(Botmaster)의 C2 서버 명령에 따라 일사불란하게 분산 공격을 수행하는 감염 단말 군집.
- **Loader Server** : 기기의 CPU 아키텍처(ARM, MIPS 등)를 판별하여 최적화된 악성 바이너리를 주입하는 서버.
- **MUD (RFC 8520)** : 제조사가 기기의 허용 통신 경로를 선언하여 비인가 외부 접속을 차단하는 사물인터넷 프로파일 규격.

</details>

## 2~4교시 예상문제 (25점)

> 미라이 봇넷(Mirai Botnet)의 아키텍처 구성 요소, 4단계 감염·제어·공격 메커니즘을 설명하고, 임베디드 기기 및 대규모 네트워크 관점에서의 엔지니어링 한계와 다층 방어 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 공장 출하 시 설정된 기본 계정/비밀번호가 변경되지 않은 채 인터넷에 노출된 리눅스 기반 IoT 장비를 침투·장악하여 초대형 분산 서비스 거부(DDoS) 공격을 감행하는 봇넷 악성코드 |
| 목적 | 수십만 대의 임베디드 단말을 단일 명령제어(C2) 체계로 통합하여 테라비트(Tbps) 단위의 L3~L7 볼륨 공격을 발생시켜 표적 인터넷 인프라 및 DNS 서비스 마비 |

- 2016년 KrebsOnSecurity, OVH 및 Dyn DNS를 연쇄 마비시키며 인터넷 전역의 가용성을 붕괴시킨 사건을 계기로 IoT 공급망 및 기기 보안의 패러다임 전환 촉발

## Ⅱ. 미라이 봇넷의 기술적 특성

| 특성 항목 | 세부 내용 및 기술적 의미 | 구현 메커니즘 |
|---|---|---|
| 크로스 아키텍처 지원 | ARM, MIPS, x86, PPC, SPARC 등 다양한 임베디드 CPU 바이너리 사전 컴파일 보유 | 타깃 핑거프린팅 후 아키텍처에 부합하는 ELF 바이너리 전송 |
| 고속 비동기 스캐닝 | SYN 스캐너를 통해 무작위 공인 IPv4 공간의 23, 2323 포트를 초당 수만 회 이상 탐색 | 메모리 효율적인 비동기 RAW 소켓 기반 스캔 스레드 |
| 메모리 상주 및 타 악성코드 제거 | 디스크 저장을 최소화하고 RAM 상주 실행하며, 기존 경쟁 악성코드 프로세스 및 경쟁 포트 선제 사살 | Killer 모듈을 통한 프로세스/포트 점유 및 재감염 방지 |
| 단순하면서도 치명적인 확산 | 제로데이 취약점 없이 순수 60여 개 기본 계정/비밀번호(admin/admin 등) 사전 대입만으로 폭발적 전파 | 하드코딩된 사전 대입(Dictionary Attack) 자동화 엔진 |

- 감염된 기기가 즉시 또 다른 스캐너로 동작하여 기하급수적 자기 증식(Self-propagating) 능력을 발휘하는 웜(Worm) 형태 특성 보유

## Ⅲ. 미라이 봇넷 아키텍처 및 4단계 동작 메커니즘

```text
[미라이 봇넷의 4단계 감염, C2 연계 및 DDoS 공격 메커니즘]

   [ 1. 스캔 및 취약 기기 탐색 ]
   공인 IPv4 무작위 탐색 (Port 23/2323)
   기본 자격증명(60여 개 사전) 브루트포스
                  │
                  ▼ (로그인 성공 IP:Port 보고)
   [ 2. 로더(Loader) 서버 바이너리 배포 ]
   - 대상 시스템 아키텍처 판별 (ARM/MIPS/x86)
   - Wget/TFTP 명령어로 악성 바이너리 전송 및 실행
                  │
                  ▼ (메모리 상주 및 프로세스 은닉)
   [ 3. C2(명령제어) 서버 등록 및 대기 ]
   - 감염 봇 등록 (Keep-alive 신호 교환)
   - 킬러 모듈 가동 (경쟁 프로세스 종료, Telnet 차단)
                  │
                  ▼ (공격 명령 하달: 대상 IP, 포트, 기간)
   [ 4. 표적 대상 분산 공격(DDoS) 개시 ]
   - SYN Flood / ACK Flood / UDP Plain Flood
   - DNS Water Torture (의사 무작위 서브도메인 질의)
   - HTTP GET/POST Flood ───> [ 표적 인터넷/DNS 인프라 마비 ]
```

| 동작 단계 | 세부 프로세스 | 공격 양상 및 프로토콜 |
|---|---|---|
| 1. 스캐닝 (Scan) | 봇이 무작위 IP의 23/2323 포트에 TCP SYN 패킷 전송 후 응답 시 딕셔너리 공격 | 텔넷 로그인 성공 시 보고 서버(Report Server)에 기기 정보 전송 |
| 2. 로딩 (Load) | 로더 서버가 취약 기기에 원격 접속하여 쉘 명령어 실행 (`echo`, `tftp`, `wget`) | 기기 CPU 아키텍처에 맞는 전용 ELF 바이너리 다운로드 및 메모리 로드 |
| 3. 장악 및 제어 | 바이너리 실행 즉시 프로세스 이름을 변경하고, 경쟁 봇 사살 및 C2 서버와 TCP 연결 | 메모리 상주(Watchdog 비활성화), 단말 재부팅 시까지 생존 유지 |
| 4. 공격 실행 (Attack) | C2 서버로부터 공격 명령(공격 유형, 대상 IP, 포트, 시간) 수신 시 일제히 패킷 투사 | SYN Flood, GRE Flood, DNS Water Torture 등 초당 수백 Gbps 패킷 발생 |

## Ⅳ. 미라이(Mirai) vs 전통적 PC 봇넷 vs 차세대 P2P IoT 봇넷(Mozi) 비교

| 비교 항목 | 미라이 봇넷 (Mirai) | 전통적 PC 봇넷 (Zeus/Conficker) | 차세대 IoT 봇넷 (Mozi) |
|---|---|---|---|
| 주요 감염 대상 | IP 카메라, 공유기, DVR (IoT/임베디드) | 윈도우 기반 데스크톱 PC, 워크스테이션 | IoT 기기 및 네트워크 게이트웨이 |
| 감염 경로 | 텔넷 기본 계정/비밀번호 무차별 대입 | 피싱 메일, 악성 첨부파일, 드라이브 바이 다운로드 | N-day/0-day 익스플로잇 취약점 복합 악용 |
| 제어 토폴로지 | 중앙 집중형 C2 서버 (IRC/TCP) | 중앙 C2 또는 도메인 생성 알고리즘(DGA) | DHT(Distributed Hash Table) 기반 순수 P2P |
| C2 차단 난이도 | 보통 (C2 서버 IP/도메인 블랙리스트 차단 가능) | 높음 (수천 개 DGA 도메인 동적 생성) | 극도로 높음 (단일 실패점 부재, DHT 노드 분산) |
| 주요 공격 목적 | 대규모 인프라 대상 네트워크 대역폭 고갈(DDoS) | 금융 정보 탈취, 랜섬웨어 유포, 스팸 발송 | DDoS 공격, 데이터 탈취 및 봇넷 임대(BaaS) |

## Ⅴ. IoT 봇넷 대응 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| 기기 재부팅 시 RAM 상주 악성코드는 소멸하나, 기본 자격증명이 유지되어 수분 내 재스캔에 의해 무한 재감염 루프 발생 | 공장 출하 시 기기별 고유 난수 비밀번호(Unique-per-device Password) 부여를 의무화하고, 최초 웹 콘솔 접속 시 강제 변경 플로우 및 Telnet 서비스 기본 비활성화 적용 |
| 저사양 임베디드 기기의 리소스(CPU/RAM) 제약으로 인해 단말 내부 백신/EDR 보안 에이전트 설치 및 실시간 감시 불가 | 네트워크 단에서 RFC 8520 MUD(Manufacturer Usage Description) 표준을 적용하여 해당 IoT 기기가 사전에 허가된 제조사 도메인 외 외부 통신을 전면 차단하도록 SDN 격리 |
| C2 서버의 IP를 차단해도 클라우드 CDN 뒤로 은닉하거나 빠른 주소 변경(Fast-Flux)을 적용하여 제어 채널 무력화 곤란 | 통신사(ISP) 및 클라우드 망 연동 기반 BGP Flowspec 기술을 적용하여 C2 제어 트래픽 및 감염 봇 발신 비정상 트래픽을 네트워크 에지에서 선제 드롭(Blackholing) |
| 정상적인 DNS 질의와 구별하기 어려운 DNS Water Torture(무작위 프리픽스 쿼리) 공격 시 Authoritative DNS 서버 과부하 | Authoritative DNS 앞단에 Anycast 기반 대규모 스크러빙 센터를 구축하고, 유효하지 않은 NXDOMAIN 응답률 임계치 기반 동적 레이트 리미팅(Rate Limiting) 적용 |

## Ⅵ. 사물인터넷(IoT) 생명주기 보안 및 다층 방어 체계 제언

```text
[IoT 기기 및 네트워크 전 주기 3대 방어 아키텍처]

 ┌─────────────────────────────────────────────────────────────┐
 │                1. 기기 제조 단계 (Secure by Design)         │
 │   - 기기별 고유 비밀번호 부착   - 불필요한 포트/서비스(Telnet) 영구 제거 │
 │   - 하드웨어 신뢰 루트(RoT) 기반 서명된 펌웨어 Secure Boot 적용   │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              2. 네트워크 인프라 단계 (Zero Trust Isolation)  │
 │   - RFC 8520 MUD 프로파일 적용 (인가된 목적지 외 통신 차단) │
 │   - 통신사 에지 라우터 BCP 38 적용 (IP 스푸핑 원천 차단)    │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              3. 서비스 수용 단계 (DDoS Mitigation)          │
 │   - Anycast BGP 기반 트래픽 스크러빙 센터 및 CDN 캐싱 분산  │
 │   - 비정상 트래픽 패턴 실시간 차단 (BGP Flowspec 자동화)    │
 └─────────────────────────────────────────────────────────────┘
```

| 영역 | 엔지니어링 실행 과제 | 달성 성과 지표 |
|---|---|---|
| 디바이스 보안 | IoT 보안인증(KISA) 기준 준수 및 텔넷 비활성화 펌웨어 배포 | 출하 기기 디폴트 계정 존재율 0%, 보안 펌웨어 적용률 100% |
| 네트워크 관제 | 이상 발신 트래픽(대량 23번 포트 스캔) 모니터링 및 가입자 회선 차단 | 좀비 PC/단말 감염 탐지 및 망 분리 시간 < 10분 |
| 인프라 방어 | 초대형 볼륨(Tbps급) DDoS 공격 대비 Anycast 트래픽 흡수 인프라 확보 | 1Tbps 이상 DDoS 공격 유입 시 정상 서비스 가용성 99.99% 유지 |
