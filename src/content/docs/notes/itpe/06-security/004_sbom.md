## 1교시 예상문제 (10점)

> SBOM의 정의와 주요 구성요소, 공급망 보안에서의 활용을 설명하시오. (예상)

---

## 1교시 10점 답안

### 1. 정의·목적

정의: SBOM은 소프트웨어에 포함된 구성요소와 의존관계를 기록한 기계 판독형 명세다.
목적: 구성요소의 취약점과 라이선스 영향을 식별하고 공급망 위험을 관리한다.

### 2. 핵심 구성과 활용

| 구성·단계 | 역할 |
|---|---|
| 공급자·컴포넌트명·버전·식별자 | 포함된 소프트웨어 부품을 식별 |
| 의존관계·작성자·타임스탬프 | 부품 간 관계와 작성 정보를 기록 |
| CVE 대조·VEX | 취약점을 찾고 실제 영향 여부를 구분 |

빌드 시 SBOM 생성·서명 → 취약점 DB 대조 → VEX로 실제 조치 대상을 가린다.

제안: SBOM을 빌드 때 생성하고 취약점 정보와 지속적으로 대조한다.

## 2~4교시 25점 답안
```text
[SBOM] ◀━━ 머리: Ⅶ 내 의견 (정적 명세서 보관 탈피 → VEX 연계 자동 분석 및 공급망 통제 의무화)
 ┃
 ┣━ Ⅰ 개요 ───── 오픈소스 전이 의존성 급증 및 Log4j 사태 → 기계 판독 가능한 SW 부품 명세서 표준화
 ┣━ Ⅱ 특징 ───── 구성요소 계층화 · 고유 식별자 부여 · 라이선스/취약점 추적성 · 포맷 표준화(SPDX/CycloneDX)
 ┣━ Ⅲ 구조 ───── NTIA 7대 최소요소(공급자·컴포넌트명·버전·식별자·의존관계·작성자·타임스탬프)
 ┣━ Ⅳ 흐름 ───── ① CI/CD 빌드 시 SBOM 추출 → ② 전자서명(Cosign) 첨부 → ③ CVE DB 대조 → ④ VEX 발행 및 배포
 ┣━ Ⅴ 비교 ───── SPDX(ISO/IEC 5962, 컴플라이언스) vs CycloneDX(OWASP, 보안 분석)
 ┗━ Ⅵ 실무 ───── 취약점 오탐 피로(Alert Fatigue) 해소 / 동적 패키지 식별 한계 / 공급업체 납품 강제 규제
```
- 필수 키워드: NTIA 최소요소 · SPDX · CycloneDX · VEX · 전이 의존성(Transitive Dependency) · Cosign
- 기출: 134회 3교시 3번 `SBOM 개념과 구성요소` → Ⅰ·Ⅲ / 136회 4교시 4번 `공급망 보안과 SBOM 아키텍처` → Ⅳ·Ⅵ

## 한 줄 본질
- 오픈소스 패키지 중첩으로 소프트웨어 내부 부품 파악 불가 → 빌드 시 모든 컴포넌트·버전·해시·의존성을 표준 형식으로 기계 추출 → 신속한 CVE 영향도 파악 / 단순 명세 시 대량 오탐 알림 발생

## 핵심 그림
```text
[CI/CD 파이프라인 내 SBOM 생성, 서명 및 VEX 취약점 교차 검증]

 [소스코드/컨테이너] ──> [ 빌드/생성 (Syft) ] ──> [ 무결성 서명 (Cosign) ]
                               │                              │
                               ▼                              ▼
                       [ CycloneDX JSON ]             [ OCI 레지스트리 ]
                               │
               ┌───────────────┴───────────────┐
               ▼                               ▼
       [ CVE 취약점 스캔 (Grype) ]      [ VEX 실행가능성 판정 ]
       (수백 개 잠재 취약점 도출)        (실제 미사용 코드 필터링)
                               │
                               ▼
                   [ 실질적 위협만 선별 조치 ]
```

## 핵심 용어
- 전이 의존성(Transitive Dependency): 직접 호출한 라이브러리가 내부적으로 다시 참조하는 하위 라이브러리의 연쇄 종속 관계
- VEX(Vulnerability Exploitability eXchange): SBOM에 기재된 취약점 컴포넌트가 해당 시스템 환경에서 실제로 악용 가능한지 상태를 명시하는 보완 규격

## 핵심 통찰
- SBOM은 생성 자체보다 실시간 취약점 인텔리전스 DB와의 지속적 대조(Continuous Monitoring)가 핵심 가치임
- SBOM 단독 배포 시 실제 런타임에서 호출되지 않는 데드 코드의 취약점까지 경보가 울려 개발팀의 패치 피로(Patch Fatigue)를 유발함 → VEX 결합 필수
- 소스코드 레벨 SBOM 외에 베이스 이미지 OS 패키지까지 포함하는 컨테이너 레벨 SBOM이 누락되면 인프라 계층 취약점을 놓침

## 이웃 토픽과 구분
- SBOM vs VEX: SBOM = 시스템에 어떤 부품이 들어있는지 명세(Who is there) / VEX = 그 부품의 취약점이 실제 실행되어 피해를 주는지 판정(Can it hurt me)

## 문제·원인·대책
- 사례: 134회 기출 오픈소스 의존성 증가에 따른 Log4j 제로데이 취약점 영향도 분석 지연
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 신규 CVE 발표 시 사내 영향 시스템 파악에 수주 소요 | 중앙화된 소프트웨어 부품 명세 부재 | 빌드 파이프라인(CI/CD)에 Syft 기반 CycloneDX 자동 생성 강제 | 취약점 발표 시 단 1회의 쿼리로 전사 영향 자산 식별 |
| 수백 개 CVE 경보로 개발팀 패치 업무 마비 | 미사용 취약 함수가 포함된 라이브러리 일괄 탐지 | OpenVEX/CSAF 기반으로 실행 불가(not_affected) 선언문 자동 발행 | 실질적 조치 대상 취약점 80% 이상 압축 |

## 이렇게 출제된다
- 제134회 3교시 3번: "SBOM(Software Bill of Materials)의 개념과 구성요소, 공급망 보안을 위한 활용 방안을 설명하시오." → 요구 포인트: Ⅰ 정의와 배경 + Ⅲ NTIA 7대 요소 + Ⅳ 공급망 관리 프로세스
- 제136회 4교시 4번: "공급망 보안(Supply Chain Security)을 설명하고, 제로트러스트(Zero Trust) 기반 공급망 보안 아키텍처 및 SBOM의 역할을 설명하시오." → 요구 포인트: Ⅳ CI/CD 서명 검증 + Ⅵ VEX 연동

## 내 의견
- [단순 서류 제출용 SBOM 납품 관행] 공공·금융 SI 사업에서 납품 시점에 텍스트 파일 하나 제출하고 서랍에 방치하여 운영 중 발생하는 공급망 공격에 무방비 → 나라면: 공공 발주 가이드라인에 SBOM 표준 포맷(CycloneDX) 준수를 강제하고, Dependency-Track과 연동된 상시 점검 체계를 운영 검수 조건으로 규정
