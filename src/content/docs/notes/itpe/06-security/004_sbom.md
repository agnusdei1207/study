## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **SBOM (Software Bill of Materials)**은 소프트웨어 구성요소와 공급망 관계를 기록한 기계 판독 가능 명세 |
| 목적 | 구성요소 식별과 취약점 영향 분석을 통한 소프트웨어 공급망 위험관리 |

SBOM은 구성요소의 존재·관계를 투명하게 기록하는 자료이며, 단독으로 취약점의 실제 악용 가능성이나 제품 안전성을 판정하지 않음.

## Ⅱ. 구성 정보와 표준 형식

| 구성 정보 | 보안상 쓰임 |
|---|---|
| 구성요소·공급자·버전·식별자 | 구성요소 식별과 출처 확인 |
| 의존 관계 | 직접·전이 구성요소 추적 |
| 생성시점·작성자·도구 정보 | 명세의 생성 경위와 최신성 확인 |
| SPDX·CycloneDX 형식 | 도구 간 교환과 자동 처리 |

```text
소프트웨어 제품
  ├─ 직접 구성요소
  │    └─ 전이 구성요소
  └─ 빌드·공급 출처 정보
```

## Ⅲ. 생성·분석·대응 과정

```text
소스·빌드 산출물
        ↓ 구성요소 분석
형식화된 SBOM 생성·검증
        ↓ 취약점 정보와 대조
영향 제품·버전 식별
        ↓ 제품 맥락 확인
수정·완화·영향없음 상태 기록
```

| 단계 | 확인 사항 |
|---|---|
| 생성 | 빌드 결과와 구성요소 인벤토리의 일치, 생성도구·시점 기록 |
| 분석 | 식별자·버전·의존 관계와 취약점 정보의 대조 |
| 영향 검토 | 취약 코드 포함·실행 경로·제품 설정 등 제품 맥락 확인 |
| 조치·갱신 | 수정·완화·영향없음 상태의 근거 기록과 SBOM 갱신 |

## Ⅳ. VEX를 이용한 영향 정보 보완

| 구분 | SBOM | VEX |
|---|---|---|
| 핵심 질문 | 어떤 구성요소가 포함되는가 | 특정 취약점이 제품에 어떤 상태인가 |
| 정보 | 구성요소·버전·관계 | 영향 상태와 판단 근거 |
| 운영 역할 | 영향 제품 탐색 | 조치 우선순위와 상태 공유 |

VEX의 영향 상태는 제품별 주장과 근거이므로 공급자·운영자의 확인 및 검증 절차 필요.

## Ⅴ. 공급망 통제와 한계

| 한계 | 대응 |
|---|---|
| 생성 시점 이후 구성요소 변경으로 명세와 배포물이 달라짐 | 빌드 산출물과 SBOM을 함께 식별·보관하고 변경 시 재생성 |
| 식별자·버전 정보가 누락되거나 형식이 달라 자동 대조에 실패 | 표준 형식과 식별자 검증, 생성 결과의 품질 점검 |
| SBOM만으로 실제 영향 여부를 확정하기 어려움 | 실행 경로·설정·제품 버전을 확인하고 VEX 상태와 근거 기록 |

## Ⅵ. 기술사적 제언

| 한계 | 해결 방안 |
|---|---|
| SBOM이 납품 문서로만 보관되어 운영 취약점 대응에 연결되지 않음 | 제품·버전·빌드 식별자를 취약점 관리와 묶고, 영향 분석부터 조치 완료까지 추적하는 운영 연계 |
