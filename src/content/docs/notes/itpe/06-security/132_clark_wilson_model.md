## 지식 로드맵 내 현재 위치

지식 위치: 접근통제·무결성 모델 → 정형 거래와 직무 분리 → **Clark-Wilson 모델**

## 30초 인출

- **본질:** 군사용 기밀성 모델을 탈피하여 금융·상업 환경의 데이터 무결성을 보장하기 위해 정형 거래(Well-formed Transaction)와 직무 분리(Separation of Duty)를 수학적으로 정립한 접근통제 모델
- **메커니즘:** 비인가 직접 수정 차단 → 승인된 사용자·TP·CDI 삼원소 인가 → TP를 통한 UDI 검증 및 CDI 상태 전이 → IVP를 통한 데이터 일관성 주기적 감사
- **통찰:** DBA의 직접 쿼리 우회 조작은 DB 접근제어와 원장형 WORM 스토리지로 통제하고 분산 환경 트랜잭션 지연은 사가 패턴 보상 트랜잭션으로 해결 필수

<details>
<summary>핵심 용어</summary>

- **CDI (Constrained Data Item)** : 무결성 상태가 엄격히 유지되어야 하는 시스템 내부의 통제 데이터 (예: 회계 원장).
- **UDI (Unconstrained Data Item)** : 외부에서 입력되어 무결성이 검증되지 않은 임의의 데이터 (예: 사용자 입력 전표).
- **TP (Transformation Procedure)** : CDI를 항상 올바른 유효 상태로만 전이시키는 사전에 검증된 정형 트랜잭션 절차.
- **IVP (Integrity Verification Procedure)** : CDI가 시스템 내부 제약조건 및 외부 현실과 일치하는지 검증하는 무결성 확인 절차.

</details>

## 2~4교시 예상문제 (25점)

> 상업적 무결성 보장을 위한 Clark-Wilson 모델의 핵심 4대 요소(CDI, UDI, TP, IVP)와 2대 원칙(정형 거래, 직무 분리)을 설명하고, Biba 모델과의 비교 및 분산 트랜잭션 시스템 구현 시 엔지니어링 한계와 해결 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 상업 및 금융 환경에서 발생할 수 있는 내부자의 부정 행위, 데이터 입력 오류, 불완전한 상태 전이를 방지하기 위해 정형 거래와 직무 분리를 기반으로 설계된 데이터 무결성 보장 모델 |
| 목적 | 주체의 데이터 직접 조작을 원천 금지하고, 검증된 변환 절차(TP)만을 통해 통제 데이터를 수정하도록 강제하여 시스템 내부 및 외부 일관성 유지 |

- 군사적 다단계 보안(MLS) 기반의 Bell-LaPadula(기밀성) 및 Biba(단순 무결성 등급) 모델이 충족하지 못하는 상업 시스템의 업무 프로세스 무결성 요구사항을 완벽히 해결

## Ⅱ. Clark-Wilson 모델의 핵심 기술적 특성

| 특성 항목 | 세부 내용 및 기술적 의미 | 엔지니어링 구현 가치 |
|---|---|---|
| 정형 거래 (Well-Formed Transaction) | 사용자는 통제 데이터(CDI)를 직접 수정할 수 없으며 오직 검증된 절차(TP)를 경유 | 원본 테이블에 대한 임의의 SQL Injection 및 수동 조작 차단 |
| 직무 분리 (Separation of Duty) | 고위험 업무 프로세스를 분할하여 단독 주체가 모든 단계를 완결하지 못하도록 통제 | 2인 승인 시스템(Dual Control), 기안자와 결재자 계정 분리 |
| 삼원소 접근 인가 (Access Triple) | 단순 주체-객체(`Sub-Obj`) 관계가 아닌 주체-절차-객체(`User, TP, {CDIs}`) 바인딩 강제 | 최소 권한 원칙의 정밀한 세분화(Granular RBAC) 구현 |
| 내부 및 외부 일관성 검증 | 내부 장부의 대차대조 일치(내부) 및 실물 현금과의 실사 일치(외부)를 동시 만족 | IVP(무결성 검증 절차)를 통한 실시간 및 배치 무결성 감사 |

- 시스템 관리자나 인증자라도 거래 실행 코드를 직접 임의로 생성하거나 실행할 수 없도록 설계된 상호 견제 특성 보유

## Ⅲ. Clark-Wilson 핵심 4대 요소 및 무결성 제어 프로세스

```text
[Clark-Wilson 모델의 4대 요소 상호작용 및 통제 아키텍처]

                 ┌─────────────────────────────┐
                 │       IVP (무결성 검증)      │
                 │   - CDI의 유효 상태 검사     │
                 │   - 내부/외부 일관성 대조    │
                 └──────────────┬──────────────┘
                                │ (상태 검증)
                                ▼
  [외부 입력]              [통제 데이터]               [감사 로그]
  ┌────────┐  UDI 검증   ┌────────┐  TP 변환 전이   ┌────────┐
  │  UDI   │ ─────────>  │  CDI   │ ─────────────>  │ Audit  │
  └────────┘             └────────┘                 └────────┘
       ▲                      ▲
       │                      │ (오직 TP를 통해서만 수정 가능)
       └──────────┬───────────┘
                  │
        ┌─────────┴─────────┐
        │   TP (정형 거래)  │ <─── [인가된 주체(User)]
        │ - 사전 검증된 변환│      Access Triple: (User, TP, {CDIs})
        └───────────────────┘
```

| 구성 요소 | 기술적 정의 | 실제 엔터프라이즈 예시 | 통제 규칙 매핑 |
|---|---|---|---|
| CDI (통제 데이터) | 무결성 유지가 필수적인 핵심 데이터 객체 | 은행 계좌 잔고, 고객 크레딧, 거래 원장 DB | 인증 규칙 C1, C2, 강제 규칙 E1 |
| UDI (비통제 데이터) | 무결성이 검증되지 않은 외부 유입 입력값 | 사용자 입력 HTTP 요청 파라미터, 외부 파일 | 인증 규칙 C5 (UDI 유효성 검증) |
| TP (변환 절차) | CDI를 항상 유효한 상태에서 유효한 상태로 전이 | 계좌 이체 트랜잭션, 분개 승인 프로그램 | 인증 규칙 C2, 강제 규칙 E2 |
| IVP (무결성 검증) | CDI가 시스템 유효 제약조건을 만족하는지 점검 | 차변/대변 합계 대사 배치 프로그램 | 인증 규칙 C1 (초기/정기 무결성 검증) |

## Ⅳ. 보안 모델 비교: Clark-Wilson vs Biba vs Bell-LaPadula

| 비교 항목 | Clark-Wilson 모델 | Biba 모델 | Bell-LaPadula (BLP) 모델 |
|---|---|---|---|
| 최우선 보안 목표 | 상업 데이터 무결성 (Integrity) | 무결성 등급 보호 (Integrity) | 정보 기밀성 보장 (Confidentiality) |
| 핵심 통제 규칙 | Well-Formed Transaction, 직무 분리 | Simple Integrity, Star Integrity | Simple Security, Star Property |
| 데이터 접근 제어 방식 | Access Triple `(User, TP, CDI)` | 주체-객체 간 무결성 레이블 비교 | 주체-객체 간 보안 등급 레이블 비교 |
| 접근 원칙 | 직접 수정 불가 (오직 TP 경유) | No Read Down, No Write Up | No Read Up, No Write Down |
| 주요 적용 분야 | 금융 거래, 회계 시스템, ERP, 전자상거래 | OS 커널 메모리 격리, 무결성 제어 | 군사, 정부 정보 시스템, 국방 기밀망 |
| 직무 분리 지원 여부 | 모델 차원에서 완전 지원 | 미지원 (등급 비교만 수행) | 미지원 (등급 비교만 수행) |

## Ⅴ. 분산 시스템 구축 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| 클라우드 마이크로서비스(MSA) 환경에서 여러 마이크로서비스에 걸친 TP 실행 시 2PC(2-Phase Commit)의 극심한 지연 및 블로킹 장애 | 사가 패턴(Saga Pattern)을 도입하여 오케스트레이터 기반으로 로컬 트랜잭션을 순차 실행하고, 실패 시 역순 보상 트랜잭션(Compensating Transaction)을 가동하여 최종 일관성(Eventual Consistency) 달성 |
| 데이터베이스 관리자(DBA)나 특권 계정이 콘솔 직접 접속을 통해 TP 프로그램을 우회하여 CDI 테이블 데이터를 무단 수정(Direct Query) | 데이터베이스 접근 제어(DAC/DBSAC) 솔루션을 통해 애플리케이션 서비스 계정 외 직접 UPDATE/DELETE 쿼리를 전면 차단하고, 불변 원장 데이터베이스(AWS QLDB 등) 적용 |
| 외부 사용자로부터 유입되는 UDI의 입력 검증(인증 규칙 C5) 미흡 시 SQL Injection, 버퍼 오버플로우 등으로 TP 로직 왜곡 | API 게이트웨이 및 웹 프론트엔드 단에 엄격한 화이트리스트 스키마 검증을 적용하고, 런타임 애플리케이션 자가 보호(RASP) 모듈을 연동하여 비정상 입력 실시간 살균(Sanitization) |
| 개발자가 임의로 TP 프로그램 코드를 악의적으로 수정하여 배포하는 내부자 위협(Insider Threat) 발생 위험 | GitOps 파이프라인 상에 다중 서명 코드 리뷰(2-Peer Review)를 강제하고, CI/CD 배포 시 Cosign 기반 디지털 서명이 검증된 불변 컨테이너 이미지만 프로덕션 쿠버네티스에 배포 |

## Ⅵ. 금융 및 엔터프라이즈 환경에서의 Clark-Wilson 구현 제언

```text
[Clark-Wilson 아키텍처 기반 엔터프라이즈 시스템 구축 프레임워크]

  ┌─────────────────────────────────────────────────────────────┐
  │                 1. 입력 계층 (UDI Validation)               │
  │   - API Gateway 화이트리스트 검증   - 입력 데이터 스키마 강제│
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────┴──────────────────────────────┐
  │              2. 비즈니스 로직 계층 (TP & 직무 분리)          │
  │   - Access Triple RBAC (기안자 != 승인자 강제)              │
  │   - 마이크로서비스 사가 오케스트레이터 기반 트랜잭션 전이    │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────┴──────────────────────────────┐
  │                 3. 데이터 계층 (CDI & IVP)                  │
  │   - 직접 DB 접근 차단 (Zero Direct Query Policy)            │
  │   - 매일 자정 배치 IVP 실행 (차변/대변 대사 및 머클 무결성)  │
  └─────────────────────────────────────────────────────────────┘
```

| 영역 | 엔지니어링 세부 과제 | 통제 목표치 |
|---|---|---|
| 정형 거래 강제 | 애플리케이션 외 DBA 직접 DML(INSERT/UPDATE/DELETE) 차단 | 직접 쿼리 수행 건수 0건 |
| 직무 분리 구현 | 고위험 금융 이체 및 시스템 설정 변경 시 2인 다중 승인 적용 | 단독 고위험 트랜잭션 승인율 0% |
| 무결성 검증 | 배치 IVP 및 실시간 불변 감사 로깅(WORM) 파이프라인 가동 | 무결성 불일치 탐지 시 통보 시간 < 1분 |
