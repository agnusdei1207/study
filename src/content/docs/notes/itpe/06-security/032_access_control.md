## 30초 인출

- **본질:** 신원이 확인된 주체가 정보자산 및 객체에 접근할 때 사전에 정의된 보안 정책에 따라 허용 또는 차단 여부를 중재하는 정보보안의 기본 통제
- **메커니즘:** 식별(Identification) → 인증(Authentication) → 인가(Authorization) → 책임추적성(Accountability/Audit)의 4A 파이프라인 집행
- 통찰: API 환경의 객체 수준 인가 결함(BOLA)과 탈취된 JWT 토큰의 권한 남용을 방지하기 위해 컨텍스트 소유권 검증 및 Redis 분산 블랙리스트 필수

<details>
<summary>핵심 용어</summary>

- **접근통제 (Access Control):** 정당한 권한을 가진 주체에게만 객체에 대한 허용된 행위를 인가하고 비인가자의 접근을 원천 차단하는 종합 보안 메커니즘
- **4A 프레임워크:** 식별(Identification), 인증(Authentication), 인가(Authorization), 책임추적성(Accountability/Auditing)으로 구성된 접근통제 4단계
- **BOLA (Broken Object Level Authorization):** 사용자가 유효한 토큰을 보유했으나 타인의 객체 ID(`GET /account/1002`)를 직접 호출할 때 소유권 검증 누락으로 데이터가 노출되는 취약점
- **XACML (eXtensible Access Control Markup Language):** OASIS 표준으로, 정책결정점(PDP)과 정책집행점(PEP) 간의 XML 기반 세분화된 접근제어 정책 규격
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **접근통제(Access Control)** 는 시스템의 기밀성, 무결성, 가용성을 수호하기 위해 주체(Subject)의 자원(Object)에 대한 접근 요청을 보안 정책에 따라 평가하여 허가하거나 거부하는 보안 프로세스 |
| 목적 | 비인가 자원 접근 및 악성 수정 차단, 사용자별 최소 권한 보장, 침해 사고 발생 시 행위자 책임추적성(Non-repudiation) 확보 |

초기 호스트 OS 파일 권한 관리에서 시작하여, 현대에는 API 게이트웨이 및 클라우드 서비스 메시 상의 동적 인가 체계로 진화.

## Ⅱ. 접근통제의 특징 및 4A 보안 체계

```text
[접근통제 4A 파이프라인 처리 흐름]

 1. 식별 (Identification)    2. 인증 (Authentication)   3. 인가 (Authorization)     4. 책임추적성 (Accountability)
+-------------------------+   +-------------------------+   +-------------------------+   +-------------------------+
| "나는 누구인가?"        |   | "너의 주장을 증명하라!" |   | "무엇을 할 수 있는가?"  |   | "무엇을 하였는가?"      |
| 사용자 ID, 이메일, IP   |-->| 패스워드, FIDO2, MFA    |-->| RBAC, ABAC, OPA 정책     |-->| 감사 로그, SIEM 이벤트  |
| 신원 주장 (Claim)       |   | 신원 검증 (Verify)      |   | 권한 부여 (Permission)  |   | 사후 추적 (Audit Trail) |
+-------------------------+   +-------------------------+   +-------------------------+   +-------------------------+
```

| 4A 요소 | 정의 및 역할 | 엔지니어링 구현 기술 |
|---|---|---|
| **1. 식별 (Identification)** | 주체가 시스템에 자신의 신원(Identity)을 고유하게 식별 가능하도록 알리는 단계 | 사용자 계정 ID, 공인 사번, 머신 식별자(UUID) |
| **2. 인증 (Authentication)** | 주체가 주장한 신원이 진짜 본인임을 자격증명(Credentials)을 통해 검증하는 단계 | 패스워드, FIDO2 WebAuthn, TOTP, 생체인증 |
| **3. 인가 (Authorization)** | 인증된 주체가 특정 객체에 대해 어떤 작업(Read/Write/Exec)을 할 수 있는지 결정 | ACL, RBAC, ABAC, OAuth 2.0 Scope, OPA |
| **4. 책임추적성 (Accountability)** | 주체가 수행한 모든 행위를 시스템에 변조 불가능하게 기록하여 감사를 지원하는 단계 | Syslog, 감사 로그(Auditd), 블록체인/WORM 로그 |

## Ⅲ. XACML 기반 접근통제 아키텍처 및 메커니즘

```text
[XACML 표준 접근통제 참조 모델 (Reference Architecture)]

 +---------------------------------------------------------------+
 |               [정책 관리점: PAP (Policy Admin Point)]          |
 |                     정책 작성, 승인, 배포                     |
 +-------------------------------+-------------------------------+
                                 | (정책 배포)
 +-------------------------------v-------------------------------+
 |               [정책 결정점: PDP (Policy Decision Point)]       |
 |                     XACML / Rego 기반 정책 평가               |
 +---------------+-------------------------------+---------------+
                 |                               ^ (속성 조회)
                 | (인가 결정: 허용/거부)        |
                 |               +---------------+---------------+
                 |               | [정책 정보점: PIP]            |
                 |               | 주체/객체/환경 속성 DB        |
                 |               +-------------------------------+
                 v
 +---------------+---------------+
 | [정책 집행점: PEP]            |
 | API Gateway / Envoy Proxy     |
 +---------------+---------------+
                 ^ (접근 요청: Subject -> Object)
```

### 1. 주요 XACML 컴포넌트 동작

| 컴포넌트 | 기능 및 처리 프로세스 |
|---|---|
| **PEP (Policy Enforcement Point)** | 주체의 자원 접근 요청을 가로채어 PDP에 인가 결정을 요청하고, PDP의 판정에 따라 트래픽을 전달하거나 차단 |
| **PDP (Policy Decision Point)** | PEP로부터 전달받은 요청을 PAP의 정책과 PIP의 실시간 속성(시간, 위치, 단말 상태)을 참조하여 허용/거부 최종 판정 |
| **PIP (Policy Information Point)** | 주체의 부서 정보, 리소스의 보안 등급, 외부 위험 인텔리전스 등 정책 평가에 필요한 추가 메타데이터 제공 |
| **PAP (Policy Administration Point)** | 보안 관리자가 전사 접근통제 룰셋 및 XACML/Rego 정책을 생성, 테스트, 배포하는 중앙 저장소 |

## Ⅳ. 시스템 레벨 vs 데이터 레벨 vs API 레벨 접근통제 비교

| 비교 항목 | 시스템 레벨 접근통제 | 데이터베이스 레벨 접근통제 | API / 마이크로서비스 레벨 접근통제 |
|---|---|---|---|
| **통제 위치** | OS 커널, 하이퍼바이저 | DBMS 엔진, RDBMS 세션 | API 게이트웨이, 서비스 메시 프록시 |
| **통제 단위** | 파일, 디렉터리, 프로세스, 소켓 | 테이블, 뷰, 컬럼, 로우(RLS) | REST 엔드포인트, HTTP 메서드, JSON 객체 |
| **적용 모델** | POSIX 퍼미션, SELinux(MAC) | SQL GRANT/REVOKE, DB 암호화 솔루션 | OAuth 2.0 Scope, ABAC, OPA Rego |
| **주요 위협** | 로컬 권한 상승(LPE), 루트 탈취 | SQL Injection, 대량 데이터 덤프 | **BOLA/IDOR, 토큰 탈취, 대량 할당** |
| **오버헤드** | 극히 낮음 (커널 인라인) | 쿼리 파싱 오버헤드 (낮음~보통) | 네트워크 홉 지연 (보통~높음) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| **API 환경의 BOLA(Broken Object Level Authorization) 인가 누락**<br>사용자가 인증된 정상 JWT 토큰을 가지고 URL 파라미터(`GET /api/v1/users/1002/orders`)의 ID만 변경하여 타인의 민감 주문 내역을 무단 열람하는 취약성 | **컨텍스트 기반 데이터 소유권(Data Ownership) 검증 미들웨어**<br>컨트롤러 진입 전 AOP(관점지향 프로그래밍) 미들웨어를 구축하여, JWT 내의 주체 식별자(`sub`)와 요청 대상 객체의 데이터베이스 상 소유자 ID(`owner_id`)가 일치하는지 DB 쿼리 레벨에서 강제 검증 |
| **JWT(JSON Web Token) 탈취 시 즉각적인 세션 무효화 불가**<br>무상태(Stateless) JWT 특성상 서버에 세션 상태가 없어, 사용자 계정이 탈취되거나 퇴직 시 토큰 만료시간(Exp)까지 해커의 접근을 차단할 수 없음 | **단기 Access Token(5~15분) 및 Redis 기반 분산 블랙리스트 동기화**<br>Access Token 수명을 10분 이내로 극단적으로 단축하고 Refresh Token을 통해서만 갱신하게 하며, 긴급 로그아웃이나 권한 변경 시 Redis 클러스터에 토큰 JTI를 블랙리스트로 등재하여 API 게이트웨이에서 즉각 차단 |

## Ⅵ. 제언

```text
[연속적 적응형 접근통제(CARTA) 아키텍처]

 +--------------------+     +---------------------+     +--------------------+
 | 1. 정적 인가       | --> | 2. 런타임 행동 감시 | --> | 3. 이상 탐지 차단  |
 | 최초 접근 시       |     | 세션 중 트래픽 감시 |     | 대량 다운로드 감지 |
 | OAuth / OPA 허용   |     | (UEBA 인공지능)     |     | 세션 즉시 강제 종료|
 +--------------------+     +---------------------+     +--------------------+
```

| 접근통제 진화 단계 | 특징 및 메커니즘 | 지향 가치 |
|---|---|---|
| **경계형 접근통제 (과거)** | 네트워크 방화벽 및 VPN 접속 성공 시 무제한 인가 | 외부 차단, 내부 무한 신뢰 |
| **역할형 접근통제 (현재)** | RBAC 기반 포털 로그인 및 정적 권한 부여 | 관리 편의성 중심 |
| **연속형 접근통제 (권장)** | 세션 도중에도 위험도 점수를 실시간 재평가하는 CARTA 모델 | 제로 트러스트 실현, 세션 하이재킹 원천 방어 |

최초 1회 인증으로 세션 전체를 신뢰하는 정적 접근통제를 지양하고, API 요청 단위의 소유권 검증 및 실시간 행동 이상 탐지를 결합한 연속적 적응형 접근통제 체계 구축 권장.
