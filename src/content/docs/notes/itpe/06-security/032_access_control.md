## 답안 골격
```text
[접근통제] ◀━━ 머리: Ⅶ 내 의견 (단순 ID/PW 기반 경계 인증 탈피 → 실시간 위험 평가 기반 동적 지속 인증(CARTA) 체계 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 정보자산 보호의 제1관문 → 정당한 권한을 가진 주체만이 인가된 방식으로 객체에 접근하도록 제한하는 기제
 ┣━ Ⅱ 특징 ───── 3A 체계(인증·인가·책임추적성) · 정책(Policy)과 메커니즘(Mechanism)의 분리 · 최소 권한 부여
 ┣━ Ⅲ 구조 ───── 식별(Identification) ➔ 인증(Authentication) ➔ 인가(Authorization) ➔ 감사(Accounting/Auditing)
 ┣━ Ⅳ 흐름 ───── ① 사용자 식별정보 제출 → ② 인증요소 검증 → ③ 권한 목록(ACL) 대조 → ④ 리소스 접근 허용 및 로그 기록
 ┣━ Ⅴ 비교 ───── 신분 기반(DAC) vs 규칙 기반(MAC) vs 역할 기반(RBAC) vs 속성 기반(ABAC)
 ┗━ Ⅵ 실무 ───── 수평적/수직적 권한 상승 취약점(BOLA/IDOR) 방어 / IAM 거버넌스 수립 / 멀티클라우드 권한 관리(CIEM)
```
- 필수 키워드: 3A 체계(Authentication, Authorization, Accounting) · 참조 모니터 · 최소 권한 · 식별/인증/인가 · 감사 추적성
- 기출: 133회 4교시 3번 `접근제어의 개념과 정책, 절차, 구현 메커니즘` → Ⅰ·Ⅲ·Ⅳ·Ⅵ / 129회 2교시 `접근제어 통제정책` → Ⅱ·Ⅴ

## 한 줄 본질
- 시스템 주체가 객체에 접근할 때 신원을 확인하고 허가된 권한 범위 내에서만 행위를 허용하며 모든 내역을 감사 로그로 남기는 보안 원칙 → 비인가 접근 및 권한 오남용 차단 / 정책 설계 복잡성 및 사용자 편의성 저하

## 핵심 그림
```text
[접근통제 기본 4단계 프레임워크 (Identification ➔ 3A 체계)]

 1. 식별 (Identification)    2. 인증 (Authentication)
 ┌──────────────────────┐   ┌──────────────────────┐
 │ "내가 누구인가?"     │──>│ "신원을 증명하라"    │
 │ (ID, 사번, 이메일)   │   │ (PW, 생체, OTP, 토큰)│
 └──────────────────────┘   └──────────┬───────────┘
                                       │ 인증 성공
                                       ▼
 4. 감사 (Accounting)       3. 인가 (Authorization)
 ┌──────────────────────┐   ┌──────────────────────┐
 │ "무슨 행위를 했는가?"│<──│ "어떤 권한이 있는가?"│
 │ (접속 일시, 파일변경,│   │ (읽기/쓰기/실행 권한,│
 │  SIEM 감사 로그 기록)│   │  RBAC/ABAC 정책 검증)│
 └──────────────────────┘   └──────────────────────┘
```

## 핵심 용어
- 3A 체계: 인증(Authentication: 신원 증명), 인가(Authorization: 권한 부여), 계정관리/감사(Accounting: 행위 기록 및 추적)로 구성된 접근통제의 3대 핵심 기둥
- BOLA(Broken Object Level Authorization): 객체 식별자(ID)를 URL 파라미터에서 임의로 변경하여 타인의 데이터에 비인가 접근하는 현대 API의 대표 취약점

## 핵심 통찰
- '인증'과 '인가'를 혼동해서는 안 됨: 인증은 시스템에 들어올 자격이 있는지 확인하는 것이고, 인가는 들어온 사람이 특정 문서를 열어볼 자격이 있는지 통제하는 것임
- 완벽한 인증을 거쳤더라도 인가 검증 로직이 코드 레벨에서 누락되면(IDOR 취약점) 일반 사용자가 URL 수정만으로 관리자 DB를 다운로드할 수 있음
- 감사가 없는 인가는 보안이 아님: 사고 발생 시 원인 규명과 법적 증거 확보를 위해 '누가, 언제, 어디서, 무엇을 했는지'를 남기는 부인방지 감사 로그가 필수적임

## 이웃 토픽과 구분
- 접근통제 vs 암호화: 접근통제 = 리소스에 도달하는 문(Gate)을 지키는 문지기 / 암호화 = 문이 뚫려 리소스가 도난당하더라도 내용을 읽지 못하게 잠그는 금고

## 문제·원인·대책
- 사례: 133회 기출 웹 애플리케이션에서 로그인한 일반 사용자가 URL의 주문번호 파라미터를 변경하여 타인의 결제 정보를 전수 열람한 BOLA 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 사용자 ID 변경만으로 타인 계좌 내역 열람 | 세션 토큰의 주체와 요청된 객체 소유권 간의 인가 검증 누락 | API 게이트웨이 및 서비스 로직에 객체 레벨 인가(RBAC/ABAC) 강제 | 타인 자산 비인가 조회 원천 차단 |
| 장기 미사용 퇴직자 계정 방치로 인한 침해 | 퇴사 시 계정 라이프사이클 관리 미흡 | HR 인사 시스템과 IAM 디렉토리 간 실시간 자동 프로비저닝 연동 | 퇴사 즉시 전 시스템 로그인 및 권한 자동 회수 |

## 이렇게 출제된다
- 제133회 4교시 3번: "정보보호 방법을 암호화와 접근제어로 크게 분류할 때, 접근제어에 대하여, 그 개념과 정책, 절차, 그리고 이를 구현하는 메커니즘을 설명하시오." → 요구 포인트: Ⅰ 개념 + Ⅱ 3A 체계 + Ⅲ 절차 및 메커니즘
- 제129회 2교시 2번: "접근 제어(Access Control)의 통제정책을 설명하시오." → 요구 포인트: Ⅴ DAC/MAC/RBAC/ABAC 비교

## 내 의견
- [단일 로그인 시점 인증에 안주하는 정적 보안의 위험] 로그인 성공 후 세션이 유지되는 수시간 동안 단말이 감염되거나 사용자가 자리를 비웠을 때 발생하는 세션 하이재킹에 완전 무방비 → 나라면: 평소와 다른 IP 접속, 심야 시간대 대량 다운로드 등 이상 징후 발생 시 즉시 추가 MFA를 요구하는 '위험 기반 적응형 인증(Adaptive Authentication)'을 표준으로 확립
