<details>
<summary>핵심 용어</summary>

- **접근통제(Access Control):** 주체의 시스템 자원 접근 요청을 정책에 따라 허용·거부하는 통제
- **주체(subject):** 자원에 접근을 요청하는 사용자·프로세스·시스템
- **객체(object):** 접근 대상인 데이터·서비스·장치 등 자원
- **3A:** 식별(Identification)·인증(Authentication)·인가(Authorization)의 접근결정 흐름
- **감사(audit):** 접근 결정과 행위를 기록해 책임 추적·검토에 활용하는 활동
- **API (Application Programming Interface):** 소프트웨어 구성요소가 기능·데이터를 요청하는 인터페이스
- **NIST (National Institute of Standards and Technology):** 미국 국립표준기술연구소
- **OWASP (Open Worldwide Application Security Project):** 웹·애플리케이션 보안 지침과 프로젝트를 제공하는 비영리 재단
- **DAC (Discretionary Access Control):** 자원 소유자에게 권한 부여 재량을 두는 정책 모델
- **MAC (Mandatory Access Control):** 보안 등급과 인가 규칙으로 중앙 통제하는 정책 모델
- **RBAC (Role-Based Access Control):** 직무 역할에 권한을 연결해 관리하는 정책 모델
- **ABAC (Attribute-Based Access Control):** 주체·객체·요청·환경 속성을 정책에 대조해 권한을 결정하는 방식
- **BOLA (Broken Object Level Authorization):** 요청 객체의 권한 검증 누락으로 다른 사용자의 객체에 접근할 수 있는 취약점

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **접근통제**는 주체의 자원 접근을 정책에 따라 허용하거나 거부하는 보안 통제 |
| 목적 | 권한 없는 정보·서비스 이용의 방지와 접근 책임의 추적 |

### Ⅱ. 접근결정 흐름

```text
요청: 주체·객체·행위
          ↓
식별 → 인증 → 정책에 따른 인가 판단
                    ├─ 허용 → 요청한 행위 수행
                    └─ 거부 → 자원 접근 차단

접근 결정·행위 ── 기록 ──> 감사·검토
```

| 단계 | 확인 내용 |
|---|---|
| 식별 | 요청 주체가 누구인지 확인할 식별자 제시 |
| 인증 | 자격증명으로 주장된 신원 확인 |
| 인가 | 주체·객체·행위를 정책에 대조해 허용 여부 결정 |

**제언:** 요청마다 객체·행위 단위의 권한을 확인하고 결정기록을 검토

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **접근통제**는 주체의 자원 접근을 정책에 따라 허용하거나 거부하는 보안 통제 |
| 목적 | 권한 없는 정보·서비스 이용의 방지와 접근 책임의 추적 |

```text
요청 속성(주체·객체·행위·맥락) + 정책
                    │
                 인가 평가
          ┌──────┴──────┐
        허용            거부
          └──────┬──────┘
                 ↓
         접근결정 기록 → 감사·검토
```

## Ⅱ. 주체·객체·정책에 따른 결정

접근결정의 입력은 요청 주체, 대상 객체, 요청 행위이며, 인증은 주체의 신원을 확인하고 인가는 정책에 따라 요청을 허용·거부하는 결정

| 요소 | 확인 질문 | 예 |
|---|---|---|
| 주체 | 누가 요청하는가 | 사용자·프로세스·서비스 계정 |
| 객체 | 무엇에 접근하는가 | 파일·데이터·API·장치 |
| 행위 | 무엇을 하려는가 | 조회·수정·삭제·실행 |
| 정책 | 어떤 조건에서 허용하는가 | 소유권·등급·역할·속성 |

## Ⅲ. 정책 모델

| 모델 | 권한 결정 기준 | 적용 특징 |
|---|---|---|
| DAC (Discretionary Access Control) | 자원 소유자의 권한 부여 | 공유·위임의 유연성, 권한 전파 관리 필요 |
| MAC (Mandatory Access Control) | 보안 등급·인가 규칙 | 중앙 정책과 등급 일치에 따른 엄격한 통제 |
| RBAC (Role-Based Access Control) | 직무 역할에 연결한 권한 | 역할 설계·직무 변경에 따른 권한관리 |
| ABAC (Attribute-Based Access Control) | 주체·객체·행위·환경 속성 | 속성 정책에 따른 세밀한 조건부 결정 |

모델은 업무·위험에 따라 선택·조합하는 정책 설계 기준이며 서로 배타적인 제품 유형이 아님.

## Ⅳ. 권한 생명주기와 검증

```text
업무 역할·필요 확인
        ↓ 승인
최소 권한 부여 → 요청별 인가 검사 → 접근·결정 기록
        ↓                         ↓
직무 변경·퇴직 시 회수       정기 권한 검토·이상 조사
```

| 통제 지점 | 적용 내용 |
|---|---|
| 권한 부여 | 업무 필요성·직무분리 원칙에 따른 최소권한 승인 |
| 실행 전 검사 | 서버 측에서 요청 객체와 행위마다 권한 확인 |
| 계정 변경 | 직무 이동·퇴직·계약 종료 시 권한 조정·회수 |
| 검토·감사 | 권한 예외와 접근 기록의 정기 확인·이상 행위 조사 |

## Ⅴ. 한계와 기술사적 제언

| 한계 | 해결 방안 |
|---|---|
| 여러 서비스가 각자 인가 규칙을 구현하면 동일한 주체·객체 요청에 서로 다른 결정이 생길 수 있음 | 공통 인가 계약에 주체·객체·행위·요청 맥락을 명시하고, 서비스 경계에서 같은 정책결정 결과를 집행하는 구조 제안 |
| 속성 정책이 복잡하거나 역할이 누적되면 결정 근거를 설명·검토하기 어려움 | 핵심 업무의 역할부터 정리하고 예외 속성·권한을 기록·승인하는 정책 변경 절차 운영 |
