## 한 줄 본질
- 가변 길이 데이터를 한 번에 암호화하기 어려운 계산적 제약 병목 → 데이터를 고정 크기 블록(64/128비트)으로 나누고 혼돈(치환)과 확산(순열)을 다중 라운드로 반복 적용 → 고속 대칭키 기밀성 보장 / 블록 경계 패딩 및 운용 모드 선택 복잡도 발생

## 핵심 그림
```text
[블록 암호 양대 설계 아키텍처: Feistel 구조 vs SPN 구조]

  [ Feistel 구조 (DES, SEED) ]           [ SPN 구조 (AES, ARIA) ]
       평문 (L0 | R0)                        평문 블록 (128비트)
      ┌───────┴───────┐                               │
      │               │                               ▼
      │    ┌─────┐    │                     ┌───────────────────┐
      │    │  F  │<───┼── 라운드키 (Ki)     │ 1. AddRoundKey    │
      │    └──┬──┘    │                     └─────────┬─────────┘
      ▼       │       │                               ▼
     (XOR)<───┘       │                     ┌───────────────────┐
      │               │                     │ 2. SubBytes (S-Box) - 혼돈
      └───────┬───────┘                     └─────────┬─────────┘
          Swap (L1=R0, R1=L0^F)                       ▼
              │                             ┌───────────────────┐
     * 복호화 시 F의 역함수 불필요          │ 3. Shift/Mix (P-Box) - 확산
       (단순히 라운드키 역순 적용)          └─────────┬─────────┘
                                                      ▼
                                            * 복호화 시 각 단계의 역연산 필요
                                              (하드웨어 구현 시 병렬성 우수)
```

## 핵심 용어
- 혼돈(Confusion): 암호문과 암호키 사이의 상관관계를 숨겨 키를 유추할 수 없게 만드는 성질 (주로 S-Box 치환으로 구현)
- 확산(Diffusion): 평문의 1비트 변화가 암호문 전체에 광범위하게 퍼지게 하여 통계적 특징을 없애는 성질 (주로 P-Box 순열/행렬 곱으로 구현, 눈사태 효과)

## 핵심 통찰
- 블록 암호 설계의 양대 축인 Feistel과 SPN의 차이는 '하드웨어/소프트웨어 트레이드오프'임 → Feistel은 역함수가 필요 없어 칩 면적이 작고 구현이 쉽지만, SPN은 모든 비트를 동시에 치환하므로 최신 CPU(AES-NI)에서 병렬 가속 성능이 압도적임
- 블록 크기가 64비트(DES, 3DES, 초기 Blowfish)인 암호는 생일 역설에 의해 약 $2^{32}$개(약 32GB) 블록을 암호화하면 블록 충돌이 발생(Sweet32 공격)하므로 폐기되고, 128비트 이상(AES, ARIA, LEA)만 표준으로 사용됨
- 블록 암호 자체는 단지 '한 블록(16바이트)'을 바꿀 뿐임 → 실제 긴 문서를 암호화하려면 블록 암호 운용 모드(CBC, CTR, GCM)와 반드시 결합되어야 함

## 이웃 토픽과 구분
- 블록 암호 vs 스트림 암호: 블록 암호 = 데이터를 덩어리(128비트) 단위로 묶어 복잡한 다중 라운드 치환 / 스트림 암호 = 의사난수 키 스트림을 비트 단위로 평문과 XOR 연산

## 문제·원인·대책
- 사례: 64비트 블록 암호인 3DES를 장시간 유지되는 TLS 세션에 사용하다가 32GB 트래픽 발생 시점에 블록 충돌로 인증 쿠키가 복호화된 사건(Sweet32)
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 짧은 블록 크기(64비트)로 인한 충돌 취약점(Sweet32) | 블록 크기 64비트 암호의 생일 한계($2^{32}$ 블록) 도달 | 128비트 이상 현대 블록 암호(AES-128/256, ARIA)로 전면 교체 | 블록 충돌 가능성을 우주적 한계($2^{64}$)로 지연 |
| 암호문 조작으로 인한 평문 비트 반전 공격 | 단순 기밀성 암호화만 수행하고 메시지 인증 부재 | 인증 결합 모드(AEAD: AES-GCM, ChaCha20-Poly1305) 적용 | 암호문 위변조 시 복호화 거부로 무결성 보장 |
