## 30초 인출
- **본질:** DevSecOps는 개발·보안·운영이 책임을 나누고 소프트웨어 생애주기와 CI/CD에 보안 활동을 통합하는 방식이다.
- **메커니즘:** 변경 시점에 자동 점검 → 위험에 따른 승인·차단 → 빠른 수정 피드백 → 배포 후 감시
- **핵심:** 도구를 많이 넣기보다 위험기반 기준, 실행 가능한 피드백, 지속적인 개선을 갖춘다.

<details>
<summary>핵심 용어</summary>

- **CI/CD**: 코드 변경을 통합하고 빌드·시험·배포하는 자동화 흐름이다.
- **SAST**: 소스코드를 실행하지 않고 분석해 잠재 취약점을 찾는 시험이다.
- **SCA**: 소프트웨어 구성요소와 의존성을 확인하고 취약점·라이선스 정보를 점검하는 활동이다.
- **DAST**: 실행 중인 애플리케이션에 시험 요청을 보내 외부에서 관찰되는 보안 문제를 찾는 시험이다.
- **IaC 보안**: 코드로 정의한 인프라의 설정을 배포 전에 점검하는 활동이다.
</details>

## 1교시 10점 답안

### 1. 정의·목적

정의: DevSecOps는 개발·보안·운영의 협업과 자동화를 통해 보안을 소프트웨어 생애주기에 통합하는 개발·운영 방식이다.

목적: 취약점을 조기에 발견하고 수정 가능한 피드백을 제공해 안전한 변경의 지속적인 배포를 지원한다.

### 2. 파이프라인 흐름

```mermaid
flowchart LR
  A[코드 변경] --> B[빌드·정적분석 SAST]
  B --> C[의존성 점검 SCA]
  C --> D[동적시험 DAST]
  D --> E[배포 승인·보안정책 확인]
  E --> F[운영 모니터링]
  F -->|운영 결과를 개발에 반영| A
```

| 성공 조건 | 적용 방향 |
|---|---|
| 자동화 | 반복 가능한 보안 점검을 파이프라인에 연결 |
| 위험기반 게이트 | 업무 중요도와 위험에 따라 차단·예외·추적 기준 설정 |
| 협업 | 발견사항을 담당자와 수정 방법에 연결하고 재시험 |

## 2~4교시 25점 답안

### Ⅰ. 도입 배경과 원칙

DevSecOps는 출시 직전의 일회성 보안검사에 의존하지 않고, 보안을 설계·개발·시험·배포·운영 과정에 통합한다. NIST SSDF는 보안 개발 활동을 조직의 개발 방식에 통합할 공통 실천 항목을 제시하며, 특정 도구를 일괄 강제하지 않는다.

| 기존 병목 | DevSecOps 원칙 |
|---|---|
| 출시 직전 취약점 발견으로 수정 지연 | 변경 초기에 위험을 발견하고 피드백 |
| 보안 부서가 최종 승인만 담당 | 개발·보안·운영이 공동 책임 |
| 점검 기준이 사람과 팀마다 다름 | 보안정책과 점검을 반복 가능하게 코드화 |

### Ⅱ. CI/CD 단계별 보안 흐름

```mermaid
flowchart LR
  A[계획·위협모델링] --> B[코드·시크릿 점검]
  B --> C[빌드·SAST·SCA]
  C --> D[시험환경·DAST]
  D --> E[IaC·이미지·배포정책 확인]
  E --> F[승인된 배포]
  F --> G[운영 모니터링·취약점 대응]
  G -->|개선사항 반영| A
```

### Ⅲ. 점검 통제와 증거

| 단계 | 점검·통제 | 남길 근거 |
|---|---|---|
| 계획 | 위협모델링, 보안요구사항과 위험 기준 설정 | 요구사항·위협모델·예외 승인 |
| 코드·빌드 | 시크릿 검사, SAST, SCA, SBOM 생성 | 커밋·빌드 ID와 검사 결과 |
| 시험 | DAST·통합 시험, 취약점 재현·수정 확인 | 시험 결과와 결함 추적 링크 |
| 배포 | IaC·컨테이너 이미지·서명·설정 점검 | 승인자·산출물 버전·배포 이력 |
| 운영 | 취약점·로그·런타임 징후 모니터링 | 탐지·대응 기록과 개선 작업 |

도구는 위험과 기술환경에 맞춰 선택한다. SAST는 실행 중 경로를 모두 검증하지 못하고, DAST는 시험환경과 인증된 경로 범위에 제한될 수 있으므로 여러 통제와 수동 검토를 함께 적용한다.

### Ⅳ. 품질 게이트와 조직 운영

| 운영 요소 | 적용 원칙 |
|---|---|
| 위험 등급 | 심각도뿐 아니라 자산 중요도·노출도·악용 가능성을 고려 |
| 차단 기준 | 배포에 직접 영향을 줄 기준을 합의하고 테스트·수정 경로 제공 |
| 예외 관리 | 사유·책임자·만료일·보완통제를 기록하고 재검토 |
| 피드백 | 개발자가 수정할 위치·재현 근거를 이해할 수 있게 전달 |
| 지표 | 취약점 처리시간, 재발률, 오탐률, 예외 만료 여부 등으로 개선 |

### Ⅴ. 기술사적 제언

| 문제 | 해결 방안 |
|---|---|
| 기본 규칙을 무차별 차단으로 설정하면 오탐과 지연이 쌓여 개발팀이 점검을 우회할 수 있음 | 초기에 위험기반 게이트를 시범 적용하고 오탐을 검토해 규칙·예외·수정 경로를 조정 |
| 보안팀이 도구만 배포하고 개발팀에 결함 수정 책임을 전가하면 협업이 정착하지 않음 | 개발팀별 보안 챔피언과 보안팀 자문 경로를 두고 공동으로 위험을 분류·조치 |
| 구성요소와 빌드 결과의 출처를 추적하지 못하면 공급망 사고 때 영향 범위를 확인하기 어려움 | 의존성·빌드·배포 산출물의 버전과 출처 증거를 보존하고 취약점 공지와 연계해 추적 |
