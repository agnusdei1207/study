## 연관 키워드

- 롯데카드 해킹, 웹셸(WebShell), 원격 코드 실행(RCE, Remote Code Execution), 결제 데이터 유출
- 파일 무결성 감시(FIM, File Integrity Monitoring), EDR, WAF, RASP
- 결제 토큰화, 이상금융거래탐지시스템(FDS), 데이터 유출 방지(DLP), 2차 부정 결제

## Ⅰ. 롯데카드 해킹의 개요

- 핵심 요약 : 2025년 온라인 결제 웹서버 침해로 대규모 고객 정보가 유출되고, 카드 부정 사용 위험이 생긴 금융 침해사고.
- 개념 : 2025년 8월 롯데카드 온라인 결제 서버가 외부 공격으로 침해되어 **웹셸** (WebShell, 웹 서버에 심어 원격 명령을 실행하게 하는 악성 스크립트) 등 악성코드가 설치되고, 고객 신용정보와 결제 관련 정보가 유출된 사고로, 2025년 9월 회사 발표 기준 피해 고객은 약 297만 명이며 이 중 약 28만 명은 카드 보안코드 등 부정 사용 위험이 큰 정보까지 노출된 것으로 파악됨.
- 배경 및 필요성 : 고객 결제 정보를 다루는 인터넷 노출 서버의 취약점이 대규모 유출로 이어진 대표 사례로, 외부 공격 차단, 결제 정보 최소 보관, 이상거래 탐지 강화의 필요성을 다시 보여 줌.
- 핵심 목적 : 대고객 웹서버의 취약점과 결제 데이터 처리의 맹점을 규명하고, 결제 정보 토큰화와 웹셸 차단 구조를 설계.

## Ⅱ. 롯데카드 해킹의 특징 및 장점

- 핵심 요약 : 해킹 사고 대응의 핵심은 침입 차단, 실행 격리, 데이터 최소화, 이상거래 탐지를 겹쳐 두는 다계층 방어.

1. 웹 진입 방어 : 웹셸 업로드를 탐지·차단 → 초기 침투 경로 봉쇄.
2. 실행 격리 : 업로드 디렉터리의 스크립트 실행 권한을 제거 → 악성 파일이 있어도 실행되지 않음.
3. 데이터 최소화 : 카드 보안 코드와 비밀번호를 저장하지 않고 **결제 토큰화** (Tokenization, 실제 카드번호를 대체값으로 바꾸는 기법)를 적용 → 서버가 뚫려도 실제 결제 정보 노출을 줄임.
4. 이상거래 탐지 : 유출 가능성이 있는 카드의 해외·심야·고액 결제를 실시간 점수로 판정 → 2차 피해 차단.

## Ⅲ. 롯데카드 해킹의 구조 (흐름)

- 핵심 요약 : 웹 진입, 웹셸 설치, 정보 수집, 외부 반출로 이어진 공격 체인과, 각 단계에 대응하는 방어 계층.

```text
[ 공격 체인 ]
외부 인터넷 → 결제 웹서버 침투
          ↓
웹셸 설치 · 시스템 명령 획득
          ↓
메모리와 로그에서 결제 정보 수집
          ↓
외부 서버로 분할 반출
```

```text
[ 단계별 방어 계층 ]
진입 : 웹방화벽 · 웹셸 업로드 차단
실행 : 업로드 경로 실행 권한 제거
호스트 : 파일 무결성 감시 · EDR 탐지
데이터 : 토큰화 · 메모리 즉시 소거
반출 : 송신 트래픽 탐지 · 이상거래 탐지
```

- 핵심 흐름은 웹서버에서 시작해 내부 데이터를 거쳐 외부 반출로 끝나므로, 한 계층에서 놓친 공격을 다음 계층이 잡도록 설계하는 것이 중요.

## Ⅳ. 롯데카드 해킹의 비교

- 핵심 요약 : 2014년 카드사 유출은 내부 인력의 물리적 반출이었던 반면, 2025년 사고는 인터넷 노출 웹서버를 통한 외부 침투로 공격 표면이 옮겨 감.

| 비교 항목 | 2014년 카드사 정보 유출 | 2025년 롯데카드 침해 |
| --- | --- | --- |
| 공격 주체 | 외주 개발 인력 등 내부자 | 외부 해킹 조직 |
| 유출 경로 | 저장매체를 통한 물리적 반출 | 결제 서버 웹셸과 외부 통신 |
| 공격 표면 | 개발·테스트 PC 관리 | 인터넷에 노출된 결제 웹서버 |
| 유출 항목 | 개인 식별 정보와 카드 정보 | 신용정보와 일부 고객의 카드 보안 정보 |
| 2차 피해 위험 | 보안 정보 부재로 직접 결제 어려움 | 보안 정보까지 노출된 경우 온라인 부정 결제 위험 |

## Ⅴ. 롯데카드 해킹의 한계와 방안

- 핵심 요약 : 결제 승인 과정의 평문 노출, 정상 포트를 이용한 웹셸 통신, 장기간 유출 미탐지, 2차 부정 결제가 주요 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 결제 정보 평문 노출 | 승인 과정에서 보안 코드와 비밀번호가 서버 메모리나 로그에 남음 | 보안 코드의 저장을 금지하고, 클라이언트에서 결제 코어까지 **HSM**(Hardware Security Module) 기반 암호화 경로로 직결 | 평문 로그 검출 건수 |
| 정상 포트 위장 통신 | 80, 443 포트로 웹셸 통신을 해 경계 방화벽이 식별하지 못함 | EDR(Endpoint Detection and Response)로 웹 서버 프로세스가 셸을 실행하는 행위를 탐지해 즉시 차단 | 비정상 셸 실행 탐지 건수 |
| 장기간 대량 반출 미탐지 | 데이터가 분할 전송되어 트래픽 이상 탐지가 실패 | 송신 게이트웨이에 **데이터 유출 방지**(NDLP, Network DLP) 솔루션을 두고 카드번호 형식과 대용량 송신을 탐지 | 대용량 송신 탐지율 |
| 2차 부정 결제 | 유출된 보안 정보로 해외와 취약 가맹점에서 결제 시도 | 유출 의심 계좌의 위험 점수를 상향하고, 승인 시 추가 인증을 의무화 | 부정 승인 차단률 |

## Ⅵ. 롯데카드 해킹에 대한 기술사적 제언

- 핵심 요약 : 결제 데이터 설계, 서버 보안, 사후 피해 차단의 세 영역을 함께 강화해야 같은 유형의 침해를 줄일 수 있음.

1. 결제 데이터 : 실제 카드번호 대신 일회용 토큰으로 결제하는 체계를 넓히고, 보안 코드는 메모리에서 즉시 소거되도록 설계하는 것이 바람직하다.
2. 서버 보안 : 파일 업로드 경로를 실행 경로와 분리하고 웹 루트의 무결성 감시를 상시 가동해, 웹셸 기반 백도어가 자리 잡지 못하게 해야 한다.
3. 사후 피해 : 금융사는 기계학습 기반 이상거래 탐지를 도입해 유출 카드의 부정 승인을 실시간으로 막는 체계를 갖춰야 한다.

## Ⅶ. 결론

- 핵심 요약 : 롯데카드 해킹은 인터넷에 노출된 결제 서버와 결제 데이터의 평문 처리가 결합될 때 피해가 얼마나 커지는지 보여 준 사례.
- 시사점 : 결제 정보는 저장과 처리를 최소화하고, 침해를 전제로 한 탐지와 차단을 함께 설계해야 한다.
