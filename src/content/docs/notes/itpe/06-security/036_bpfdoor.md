## 연관 키워드

- BPFdoor, BPF(Berkeley Packet Filter), 원시 소켓(Raw Socket), 매직 패킷(Magic Packet), 리버스 셸(Reverse Shell)
- 리스닝 포트, 프로세스 위장(Masquerading), 고도 표적 공격(APT), eBPF, C2(Command and Control)
- auditd, YARA, 아웃바운드 통제(Egress Filtering), 메모리 파일 실행

## Ⅰ. BPFdoor의 개요

- 핵심 요약 : 열린 포트 없이 커널 패킷 필터를 엿보다가 특정 패킷을 받으면 원격 셸을 여는 스텔스 백도어.
- 개념 : 리눅스 커널의 패킷 필터인 **BPF** (Berkeley Packet Filter)와 **원시 소켓** (Raw Socket)을 악용하여, 평소 리스닝 포트를 열지 않고 잠복하다가 사전에 정의된 **매직 패킷** (Magic Packet)을 수신하면 **리버스 셸** (Reverse Shell)을 여는 리눅스 백도어 (BPFdoor).
- 배경 및 필요성 : 통신, 금융, 공공 인프라를 노린 **고도 표적 공격** (APT, Advanced Persistent Threat)에 쓰인 것으로 보고되었고, 포트 스캔과 방화벽 점검을 우회해 장기간 잠복하는 사례가 있어 탐지 역량이 필요해짐.
- 주요 목적 : 방화벽 우회 메커니즘을 이해하고, 커널 수준의 감시 체계와 eBPF(extended Berkeley Packet Filter) 기반 탐지 역량을 확보.

## Ⅱ. BPFdoor의 특징 및 장점

- 핵심 요약 : 포트를 열지 않고 커널 단에서 패킷을 관찰하는 구조가 탐지 회피와 잠복성을 함께 만드는 특징.

1. 리스닝 포트 없음 : bind와 listen 호출 없이 원시 소켓으로 패킷을 관찰 → 포트 스캔으로 발견하기 어려움.
2. 방화벽 체인 이전의 패킷 수신 : 커널에서 방화벽 규칙보다 앞서 패킷을 복사 → 호스트 방화벽의 차단 정책 무력화.
3. 매직 패킷 기반 활성화 : 평소에는 통신하지 않고 사전 정의된 패턴을 받을 때만 동작 → 네트워크 흔적 최소화.
4. 동적 방화벽 조작 : 세션 중에만 허용 규칙을 임시로 삽입하고 종료 후 삭제 → 안티포렌식 효과.
5. **프로세스 위장** (Masquerading) : 정상 시스템 데몬과 비슷한 이름을 쓰고 타임스탬프를 조작 → 프로세스 목록 점검 우회.

## Ⅲ. BPFdoor의 구조 (흐름)

- 핵심 요약 : 외부의 매직 패킷이 커널 필터에 포착되어 방화벽 허용과 역방향 셸 연결로 이어지는 흐름.

```text
[ BPFdoor 침해 흐름 ]

외부 공격자 C2(Command and Control) 서버
          ↓ 1. 매직 패킷 전송
희생 서버 (리스닝 포트 없음)
          ↓ 2. 커널 패킷 복사
BPF 필터 (매직 값 일치 검증)
          ↓ 3. 일치 시 백도어 활성화
백도어 프로세스 (정상 데몬 위장)
          ↓ 4. 방화벽 허용 규칙 임시 추가
          ↓ 5. 역방향 셸 연결
공격자 C2 서버로 아웃바운드 연결
```

```text
[ 단계별 탐지 지점 ]

매직 패킷 수신 → 네트워크 시그니처 탐지
          ↓
원시 소켓 생성 → 커널 시스템 콜 감사
          ↓
방화벽 규칙 변경 → 규칙 변경 로그 감시
          ↓
셸 연결 → 아웃바운드 트래픽 감시
```

| 구성 요소 | 기능 | 악용 방식 |
| --- | --- | --- |
| 원시 소켓 (AF_PACKET) | 커널 수준에서 패킷 수신 | 포트 바인딩 없이 패킷 관찰 |
| BPF 필터 | 매직 값 시그니처 검증 | 특정 패킷만 선별 |
| 셸 연결 모듈 | 역방향 세션 수립 | 아웃바운드 허용 경로 이용 |
| 흔적 제거 모듈 | 규칙 삭제, 프로세스명 변경 | 사후 분석 방해 |

## Ⅳ. BPFdoor의 비교

- 핵심 요약 : 전통적 백도어는 포트와 세션으로 드러나지만, BPFdoor는 포트와 통신 흔적이 없어 탐지 관점이 커널과 아웃바운드 계층으로 옮겨가야 함.

| 비교 항목 | 전통적 백도어 (Netcat, Meterpreter 등) | BPFdoor | 탐지 관점 |
| --- | --- | --- | --- |
| 포트 개방 | LISTEN 상태의 포트 유지 | 포트 미개방, 소켓으로 패킷만 관찰 | 리스닝 포트 점검만으로는 부족 |
| 외부 노출 | 포트 스캔으로 발견 가능 | 포트 스캔으로 발견 어려움 | 패킷 시그니처와 커널 이벤트 감시 |
| 방화벽 대응 | 인바운드 방화벽에 차단될 수 있음 | 방화벽 규칙 이전에 패킷 수신 | 방화벽 외부의 커널 계층 감시 |
| 명령 제어 | C2와 지속 세션 유지 (비콘) | 평시 무통신, 신호를 받을 때만 동작 | 비정상 아웃바운드 셸 연결 감시 |

- BPFdoor는 커널 이벤트 추적 없이는 탐지가 어려워, 기존 호스트 진단 체계의 사각지대를 드러냄.

## Ⅴ. BPFdoor의 한계와 방안

- 핵심 요약 : 표준 진단 도구의 무력화, 메모리 파일 실행, 정상 데몬 위장이 주요 한계이며 커널 감시와 실행 통제로 대응해야 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 표준 진단 도구의 무력화 | 열린 포트가 없어 netstat, ss, lsof로 침해를 인지하기 어려움 | 네트워크 인터페이스의 프로미스큐어스 모드 상태와 원시 소켓 목록을 정기 점검 | 비정상 원시 소켓 탐지 건수 |
| 메모리 파일 실행을 통한 증적 인멸 | /dev/shm 등 임시 파일시스템에 바이너리를 두고 삭제해 디스크 포렌식 곤란 | 임시 영역의 마운트 옵션을 noexec, nosuid, nodev로 설정 | 임시 영역 실행 차단 적용률 |
| 정상 데몬 위장 | 프로세스명과 부모 프로세스가 정상처럼 보여 목록 점검 우회 | 실행 파일 링크(/proc/PID/exe)가 가리키는 바이너리의 해시 검증과 YARA 룰 기반 메모리 스캔 | 해시 불일치 프로세스 수 |

## Ⅵ. BPFdoor에 대한 기술사적 제언

- 핵심 요약 : 커널 수준의 런타임 관측과 아웃바운드 기본 차단을 결합하여, 포트 기반 점검에 의존하지 않는 탐지 체계로 전환.
- 서버에는 eBPF 기반 런타임 보안 도구를 도입하여 원시 소켓 생성과 관련 시스템 콜을 실시간으로 관찰하고, 비인가 생성을 즉시 차단하는 정책을 검토할 필요가 있다.
- 내부 서버에서 외부로 나가는 연결은 허용 목록에 근거하여 기본 차단하는 것이 바람직하며, 이는 C2 통신 경로를 끊는 효과가 있다.
- Linux 감사 데몬(auditd)에 방화벽 명령 호출, 네트워크 네임스페이스 변경, 프로세스 명칭 변경 이벤트를 규칙으로 등록해 사후 분석 증적을 확보해야 한다.

## Ⅶ. 결론

- 핵심 요약 : BPFdoor는 커널 네트워크 구조를 악용한 스텔스 백도어로서, 포트와 방화벽 점검만으로는 탐지가 어렵다는 점을 보여 줌.
- 커널 이벤트 관측과 아웃바운드 통제를 결합하는 체계가 갖춰질 때 이런 유형의 탐지 공백이 메워짐.
