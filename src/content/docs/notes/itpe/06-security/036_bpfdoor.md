## 지식 로드맵 내 현재 위치

악성코드·침해분석 → Linux 스텔스 백도어 → BPFdoor 및 eBPF 악용 위협

## 30초 인출

- **본질:** 리눅스 커널의 BPF(Berkeley Packet Filter)와 원시 패킷 소켓(AF_PACKET)을 악용하여 개방 포트 없이 대기하다가 특정 매직 패킷을 수신하면 원격 리버스 셸을 활성화하는 스텔스 백도어
- **메커니즘:** BPF 필터 등록 → 수신 패킷 스니핑 → 매직 바이트 검증 → iptables 조작 후 C2 리버스 셸 연결 → 프로세스명 위장
- 통찰: 포트 리스닝이 없어 netstat으로 탐지 불가능한 한계를 극복하기 위해 `setsockopt` 커널 시스템 콜 감사와 프로미스큐어스 모드 감시 결합 필수

<details>
<summary>핵심 용어</summary>

- **BPFdoor:** 리눅스/유닉스 통신사 및 금융망을 표적으로 삼은 고도화된 스텔스 백도어로, BPF 기술을 이용해 로컬 방화벽을 우회
- **BPF (Berkeley Packet Filter):** 네트워크 드라이버 계층에서 사용자 공간으로 복사되기 전 패킷을 커널 레벨에서 고속 필터링하는 메커니즘
- **AF_PACKET / SOCK_RAW:** 전송 계층(L4) 포트 바인딩 없이 네트워크 드라이버로부터 직접 이더넷 프레임을 수신할 수 있는 저수준 리눅스 소켓
- **매직 패킷 (Magic Packet):** 공격자가 BPFdoor 백도어를 깨우기 위해 전송하는 암호화된 인증 바이트열이 포함된 ICMP, UDP 또는 TCP 패킷
- **iptables 동적 조작:** 통신 개시 직전 로컬 방화벽에 임시 허용 룰을 삽입하고, 세션 종료 즉시 룰을 삭제하여 탐지를 회피하는 안티포렌식 기법
</details>

## 2~4교시 예상문제 (25점)

> 리눅스 환경의 스텔스 백도어인 BPFdoor의 동작 메커니즘(BPF 필터링, 매직 패킷, 방화벽 우회)을 설명하고, 전통적 포트 바인딩 백도어와의 차이점 및 네트워크·호스트 레벨의 엔지니어링 탐지·대응 방안을 제시하시오. (기출·137회 4교시 1번 변형·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **BPFdoor** 는 리눅스 운영체제의 커널 패킷 필터링 기능인 BPF(Berkeley Packet Filter)와 원시 패킷 소켓(`AF_PACKET`)을 악용하여, 시스템에 리스닝 포트를 열지 않고 대기하다가 사전에 정의된 특정 매직 패킷(Magic Packet)을 감지하면 원격 명령 제어 셸을 실행하는 고도화된 스텔스 백도어 |
| 목적 | 전통적인 포트 스캐닝 및 호스트 침입탐지시스템(HIDS)의 감시망을 완벽히 우회하여 기간통신망, 금융망, 정부 백본망에 수년간 은닉 잠복 |

전통적인 악성코드와 달리 일반 포트(`LISTEN`)를 일절 개방하지 않으므로 `netstat`, `ss`, `lsof` 등의 표준 진단 명령어로 탐지 불가능.

## Ⅱ. BPFdoor의 은닉 특징

| 스텔스 특징 | 공격자의 구현 메커니즘 | 방어자 관점의 시사점 |
|---|---|---|
| **리스닝 포트 부재** | `bind()` 및 `listen()` 시스템 콜을 호출하지 않고 `SOCK_RAW`로 패킷 스니핑 | Nmap 등 외부 포트 스캐너로 감염 여부 확인 불가 |
| **로컬 방화벽 자동 우회** | 패킷 수신 시 `iptables` 규칙을 동적으로 일시 변경하여 C2 포트 개방 | 호스트 방화벽 차단 정책 무력화 |
| **정상 데몬 위장** | 프로세스명을 `/sbin/udevd`, `auditd`, `dbus-daemon` 등으로 변조 (`prctl`) | `ps -ef` 명령 시 정상 OS 서비스로 오인 |
| **안티포렌식 기법** | `/dev/shm` 인메모리 공간에서 실행 후 원본 파일 즉시 삭제 (`unlink`) | 디스크 포렌식 시 악성 실행 파일 증거 인멸 |

## Ⅲ. BPFdoor 동작 아키텍처 및 메커니즘

```text
[BPFdoor의 패킷 수신 감시 및 리버스 셸 동작 프로세스]

 [공격자 (C2)]                  [네트워크 드라이버]               [BPFdoor 백도어 프로세스]
       |                                |                                   |
       |                                | 1. AF_PACKET 소켓 생성            |
       |                                |    BPF 필터(SO_ATTACH_FILTER) 부착|
       |                                | <---------------------------------+
       |                                |   (커널 계층에서 특정 패킷 감시)  |
       |                                |                                   |
       | 2. 매직 패킷 발송 (ICMP/UDP/TCP) |                                   |
       |    (암호화된 시크릿 키 포함)   |                                   |
       | -----------------------------> | 3. 패킷 인터셉트 및 BPF 필터링    |
       |                                | --------------------------------> |
       |                                |                                   | 4. 매직 바이트 검증 성공
       |                                |                                   | 5. iptables 임시 룰 추가
       |                                |                                   |
       | 6. 역방향 C2 리버스 셸 연결    |                                   |
       | <==================================================================+
       |    (원격 root 쉘 획득 및 명령 실행)
```

### 1. 세부 동작 단계별 엔지니어링 분석

| 단계 | 수행 작업 내용 | 시스템 콜 및 기술 요소 |
|---|---|---|
| **1. 소켓 및 필터 초기화** | 네트워크 인터페이스에 원시 소켓 생성 후 컴파일된 BPF 필터 주입 | `socket(AF_PACKET, SOCK_RAW, ...)`<br>`setsockopt(..., SO_ATTACH_FILTER, ...)` |
| **2. 잠복 대기 (Sniffing)** | CPU 자원을 거의 소모하지 않고 커널 드라이버를 통과하는 모든 패킷 감시 | 커널 공간 내 BPF 가상머신에서 바이트 패턴 매칭 |
| **3. 매직 패킷 트리거** | 공격자가 보낸 패킷 페이로드에서 비밀 패스워드와 C2 IP/Port 파싱 | RC4 또는 XOR 기반 대칭 암호화 해독 |
| **4. 방화벽 해제 및 셸 실행**| `iptables -I INPUT ... -j ACCEPT` 실행 후 C2로 리버스 셸 연결 | `fork()`, `dup2()`, `/bin/sh` 프로세스 스폰 |

## Ⅳ. 전통적 백도어 vs BPFdoor 심층 비교

| 비교 항목 | 전통적 백도어 (Legacy Backdoor) | BPFdoor 스텔스 백도어 |
|---|---|---|
| **네트워크 대기 방식** | 특정 포트(예: 4444)에 `LISTEN` 소켓 개방 | **리스닝 포트 없음 (`AF_PACKET` BPF 필터링)** |
| **로컬 방화벽 관계** | 인바운드 방화벽에 막혀 연결 실패 가능 | **패킷 트리거 시 `iptables` 동적 조작으로 우회** |
| **포트 스캔 탐지** | Nmap 스캔 시 오픈 포트로 즉시 노출 | **스캔 시 포트가 닫혀 있어 완전 스텔스** |
| **프로세스 식별** | 비인가 프로세스명 노출 | **`argv[0]` 변조로 정상 시스템 데몬 위장** |
| **탐지 난이도** | 낮음 (네트워크 스캐너 및 EDR 감지) | **극도로 높음 (커널 시스템 콜 레벨 감사 필수)** |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| **netstat 및 포트 기반 보안 도구의 무력화로 인한 미탐 지속**<br>리스닝 포트가 열리지 않고 정상 패킷 흐름 속에 매직 패킷이 은닉되어 있어 전통적 NIDS/방화벽과 호스트 점검 스크립트가 침해 사실을 인지 불가 | **`setsockopt(SO_ATTACH_FILTER)` 커널 감사 및 Auditd 룰 강제**<br>리눅스 커널 감사 프레임워크(Auditd)에 `-a always,exit -F arch=b64 -S setsockopt -F a2=26` 룰을 등록하여 비인가 프로세스가 BPF 필터를 부착하는 행위를 실시간 탐지하고, `ip link`의 무차별 모드(PROMISC) 플래그를 상시 모니터링 |
| **iptables 일시 조작 후 즉시 삭제에 따른 네트워크 증적 인멸**<br>원격 셸 연결 시점에만 방화벽을 열고 종료 즉시 룰을 삭제하므로 사후 침해사고 조사 시 방화벽 설정 파일 상에 침해 흔적이 남지 않음 | **Netfilter 커널 이벤트 실시간 스트리밍 및 메모리 프로세스 맵 검증**<br>호스트 내 eBPF 모니터링 도구(Cilium Tetragon)를 배치하여 방화벽 규칙 변경 이벤트를 실시간 불변 WORM 로그로 전송하고, `/proc/[PID]/exe` 심볼릭 링크가 가리키는 실제 바이너리와 `/proc/[PID]/cmdline`의 불일치(위장 데몬)를 주기적으로 자동 스캔 |

## Ⅵ. 제언

```text
[리눅스 인프라 BPFdoor 방어 및 헌팅 파이프라인]

 +--------------------+     +---------------------+     +--------------------+
 | 1. 커널 감사       | --> | 2. 런타임 eBPF 감시 | --> | 3. 무결성 정밀 검증|
 | Auditd 시스템 콜   |     | Tetragon 커널 추적  |     | /proc 파일시스템   |
 | setsockopt 감시    |     | iptables 변조 감시  |     | 삭제된 바이너리탐지|
 +--------------------+     +---------------------+     +--------------------+
```

| 점검 영역 | 점검 명령어 및 엔지니어링 기법 | 확인 대상 이상 징후 |
|---|---|---|
| **원시 소켓 점검** | `ss -0` 또는 `cat /proc/net/packet` | 비인가 프로세스가 생성한 `PACKET` 소켓 목록 |
| **프로세스 위장 점검** | `ls -l /proc/*/exe | grep '(deleted)'` | 메모리 상에서만 실행 중인 삭제된 악성 바이너리 |
| **방화벽 훅 감시** | `auditctl -w /sbin/iptables -p x` | `iptables` 바이너리를 비정상 실행하는 스크립트 |

BPFdoor는 전통적인 포트 및 시그니처 기반 보안의 종말을 고한 사례이며, 호스트 커널 시스템 콜과 프로세스 실행 계보를 연속 추적하는 eBPF 기반 런타임 가시성 확보 권장.
