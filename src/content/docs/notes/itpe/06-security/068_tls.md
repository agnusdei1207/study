## 연관 키워드

- TLS, 핸드셰이크, ECDHE, 전방 비밀성, AEAD, 1-RTT, 0-RTT
- 재전송 공격, PSK, SNI, ECH, 상호 TLS(mTLS), 서비스 메시, SPIFFE
- 복호화 장비, IDS, IPS, WAF, DLP

## Ⅰ. TLS(Transport Layer Security)의 개요

- 핵심 요약 : 전송 계층 아래에서 상호 인증, 기밀성, 무결성을 제공하는 IETF(Internet Engineering Task Force) 표준 암호 통신 프로토콜.
- 개념 : TCP/IP 상에서 응용 계층과 전송 계층 사이에 놓여, 종단 간 상호 인증과 데이터 기밀성, 메시지 무결성을 제공하는 **TLS** (Transport Layer Security).
- 배경 및 필요성 : 공용 인터넷 구간에서 웹 트래픽이 도청, 위변조, **재전송 공격**(Replay Attack)에 노출되므로, 이를 막는 표준 보안 프로토콜이 필요해짐.
- 주요 목적 : 도청(Sniffing), 변조(Tampering), 서버 사칭(Spoofing) 방어와 짧은 지연의 연결 수립.

## Ⅱ. TLS(Transport Layer Security)의 특징 및 장점

- 핵심 요약 : 연결마다 키를 새로 합의하고 AEAD(Authenticated Encryption with Associated Data)로 데이터를 보호해, 기밀성과 무결성을 함께 얻는 구조.

1. 임시 키 교환 : ECDHE(Elliptic Curve Diffie-Hellman Ephemeral) 키를 연결마다 새로 생성 → 장기 키가 유출되어도 과거 세션 복호화가 어려워짐, 즉 **전방 비밀성** (PFS, Perfect Forward Secrecy) 확보.
2. 인증서 기반 서버 인증 : 서버 인증서와 전자서명을 검증 → 서버 사칭 차단.
3. AEAD 레코드 보호 : 암호화와 인증 태그 생성을 한 번에 처리 → 위변조 탐지와 고속 처리를 동시에 확보.
4. 핸드셰이크 무결성 : Finished 메시지로 핸드셰이크 전체를 검증 → 중간자의 협상 변조 탐지.
5. 짧은 연결 수립 : 1-RTT(Round-Trip Time) 핸드셰이크 → 첫 데이터 전송까지의 지연 축소.

## Ⅲ. TLS(Transport Layer Security)의 구조 (흐름)

- 핵심 요약 : 키 교환과 서버 인증을 마친 뒤 AEAD로 데이터를 보호하는 핸드셰이크 구조.
- ClientHello : 지원 암호 스위트와 ECDHE 공개키(Key Share)를 함께 전송하며, 서버 이름 표시(SNI, Server Name Indication)도 포함.
- ServerHello : 하나의 AEAD 스위트를 고르고 서버의 ECDHE 공개키를 회신 → 양측이 공유 비밀을 계산.
- 암호화된 핸드셰이크 : 인증서, 서명, Finished를 협상된 키로 보호 → 인증서 노출과 스니핑 차단.
- 상호 Finished : 핸드셰이크 전체의 해시를 양측이 검증 → 협상 과정의 변조 탐지.

```text
[ TLS 1.3 핸드셰이크 ]

클라이언트 → 서버
  ClientHello (암호 스위트, 키 공유)
   ↓
서버 → 클라이언트
  ServerHello (선택 스위트, 서버 키)
  인증서, 서명, Finished (암호화)
   ↓
클라이언트 → 서버
  Finished
   ↓
암호화된 애플리케이션 데이터 (AEAD)
```

## Ⅳ. TLS(Transport Layer Security)의 비교

- 핵심 요약 : TLS 1.3은 1.2에서 허용되던 약한 키 교환과 암호 방식을 제거해 왕복 횟수와 설정 복잡도를 함께 줄임.

| 비교 항목 | TLS 1.2 (RFC 5246) | TLS 1.3 (RFC 8446) |
| --- | --- | --- |
| 일반 핸드셰이크 | 보통 2-RTT | 보통 1-RTT, 재개 시 0-RTT 지원 |
| 키 교환 | 정적 RSA(Rivest-Shamir-Adleman), DH(Diffie-Hellman), ECDHE 혼재 | (EC)DHE 전용, PSK(Pre-Shared Key) 결합 가능 |
| 레코드 암호화 | CBC(Cipher Block Chaining), RC4, 3DES, AEAD 혼재 | AEAD 전용 (AES-GCM, ChaCha20-Poly1305) |
| 핸드셰이크 노출 | 인증서 등 일부 정보가 평문으로 노출 | ServerHello 이후 전 구간 암호화 |
| 암호 스위트 | 조합 수가 많아 설정 오류 빈번 | 소수의 AEAD 스위트로 축소 |

- 선택 기준 : 호환성 요구가 없는 신규 서비스는 TLS 1.3 전용으로 구성하고, 레거시 연동이 있을 때만 1.2를 제한적으로 허용.

## Ⅴ. TLS(Transport Layer Security)의 한계와 방안

- 핵심 요약 : 0-RTT 재전송, 대규모 인증서 관리, 복호화 가시성 상실이라는 세 한계를 요청 제한, 자동 순환, 정책형 복호화로 통제하는 구조.

```text
[ 0-RTT 재전송 위험 ]

클라이언트 → 0-RTT 데이터 (PSK 티켓)
   ↓ 공격자가 같은 요청을 재전송
서버 → 같은 요청을 다시 처리
   ↓
비멱등 요청(결제 등)은 중복 실행
```

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 0-RTT 재전송 | 조기 데이터와 PSK 티켓이 재전송되면 결제처럼 중복 처리되면 안 되는 요청이 다시 실행됨 | 멱등(Idempotent) 조회 요청에만 0-RTT를 허용하고, 서버에 일회용 티켓 캐시 구축 | 0-RTT 허용 요청 비율 |
| 마이크로서비스 상호 TLS 인증서 관리 | 마이크로서비스(MSA, Microservice Architecture)마다 상호 TLS(mTLS, mutual TLS)를 적용하면 인증서 발급과 갱신이 대량 발생 | 서비스 메시(Istio, Linkerd)와 SPIFFE(Secure Production Identity Framework For Everyone) 기반 단기 인증서 자동 순환 | 만료 임박 인증서 건수 |
| 복호화 가시성 상실 | 암호화 범위가 넓어져 IDS(Intrusion Detection System), IPS(Intrusion Prevention System), WAF(Web Application Firewall), DLP(Data Loss Prevention)가 내용을 검사하지 못함 | 정당한 목적에 한해 SSL(Secure Sockets Layer) 복호화 장비를 프록시에 배치하거나 엔드포인트 에이전트로 모니터링 | 복호화 검사 대상 트래픽 비율 |

## Ⅵ. TLS(Transport Layer Security)에 대한 기술사적 제언

- 핵심 요약 : TLS를 개별 서버 설정이 아닌 전사 버전 정책과 인증서 수명 주기 체계로 운영.

1. 조직은 대외 서비스와 내부 통신 전반에 TLS 1.3을 기준으로 정하고, 구형 버전을 쓰는 시스템은 예외 승인과 종료 일정을 함께 관리한다.
2. 인증서와 키의 수명 주기를 전사 자산 관리 체계에 포함해 발급, 갱신, 폐기를 한곳에서 추적하며, 만료 사고를 막는 자동화 기준을 둔다.
3. 복호화 검사의 범위는 법무 조직과 함께 정해, 보안 가시성과 개인정보 보호의 균형을 정책으로 명문화하고, 사생활 노출을 줄이는 ECH(Encrypted Client Hello) 도입 여부도 주기적으로 검토한다.

## Ⅶ. 결론

- 핵심 요약 : TLS는 임시 키 교환과 AEAD를 기본으로 하는 전송 구간 보안의 표준 프로토콜.
- 시사점 : 버전 정책, 인증서 자동화, 복호화 가시성 정책을 함께 운영하는 것이 보안 효과의 전제.
