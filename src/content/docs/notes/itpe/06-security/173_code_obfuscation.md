## 연관 키워드

- 코드 난독화(Code Obfuscation), 역공학(Reverse Engineering), 디컴파일러, 탬퍼링(Tampering), 지적재산권(IP, Intellectual Property)
- 제어 흐름 평탄화(Control Flow Flattening), 불투명 술어(Opaque Predicate), 문자열 암호화, 바이너리 패킹(Packing)
- 안티 디버깅, 안티 탬퍼링(Anti-Tampering), RASP(Runtime Application Self-Protection), 매핑 파일(Mapping.txt)

## Ⅰ. 코드 난독화의 개요

- 핵심 요약 : 프로그램의 동작은 그대로 두고 코드의 구조를 복잡하게 바꿔 역공학 분석 비용을 높이는 소프트웨어 보호 기술.
- 개념 : 소스코드나 바이너리를 사람이나 역공학 도구가 이해하기 어렵도록 문법, 제어 흐름, 데이터 측면에서 변환하는 기법 (**코드 난독화** (Code Obfuscation)).
- 배경 및 필요성 : Java 바이트코드, .NET CIL, 안드로이드 DEX, 웹 자바스크립트는 메타데이터가 풍부해 디컴파일러로 원본에 가깝게 복원되므로, 핵심 알고리즘 유출과 변조가 쉬워짐.
- 주요 목적 : **리버스 엔지니어링** (Reverse Engineering, 완성된 프로그램을 분석해 구조를 파악하는 작업)의 비용과 시간을 늘려 영업비밀을 보호하고, 변조와 크랙을 어렵게 만드는 것.

## Ⅱ. 코드 난독화의 특징 및 장점

- 핵심 요약 : 이름과 흐름, 데이터를 동시에 변환하여 분석 단계마다 시간을 지연시키는 것이 핵심 원리.

1. **레이아웃 난독화** (Layout, 식별자 축소와 디버그 정보 제거) : 클래스·변수 이름을 의미 없는 문자열로 바꾸고 주석을 삭제 → 코드의 의미 파악 시간 증가.
2. **제어 흐름 난독화** (Control Flow, 분기와 반복 구조를 변환) : 제어 흐름 평탄화와 불투명 술어로 실행 경로 추적을 어렵게 함 → 디컴파일 결과의 해독 비용 증가.
3. **데이터 난독화** (Data, 상수와 문자열을 감춤) : URL, 라이선스 키, SQL 구문을 암호화해 런타임에만 복호화 → 정적 분석으로 민감 값을 찾기 어려워짐.
4. **예방 난독화** (Preventive, 분석 도구 자체를 방해) : 안티 디버깅과 디컴파일러 충돌 유도 코드 삽입 → 분석 도구 사용 자체를 지연.

## Ⅲ. 코드 난독화의 구조 (흐름)

- 핵심 요약 : 원본 분기 구조가 하나의 상태 기계 루프로 바뀌어 실행 흐름을 읽기 어렵게 되는 구조.
- **제어 흐름 평탄화** (Control Flow Flattening, 중첩된 분기를 단일 반복문과 switch 구조로 납작하게 만드는 기법) : 원래의 분기 순서가 상태 값 변화 뒤로 숨겨짐.

```text
[ 원본 코드 ]
  if (a) Block_1 else Block_2
        ↓
[ 평탄화된 코드 ]
  state = INIT
  while (state != EXIT)
    switch (state)
      라우터: a 값에 따라 상태 전환
      Block_1, Block_2: 실행 후 다음 상태
```

```text
[ 불투명 술어 (Opaque Predicate) ]
  항상 참인 조건 (예: x² ≥ 0)
        ↓
  분석 도구는 참 여부를 계산하기 어려움
        ↓
  거짓 분기의 죽은 코드를 함께 생성
```

## Ⅳ. 코드 난독화와 다른 보호 기법의 비교

- 핵심 요약 : 난독화는 코드 구조를 바꾸어 분석을 지연시키고, 패킹은 실행 파일을 포장하며, DRM은 실행 권한 자체를 통제함.

| 비교 항목 | 코드 난독화 | 바이너리 패킹 | DRM·암호화 |
| --- | --- | --- | --- |
| 동작 원리 | 코드 구조와 제어 흐름을 변환 | 실행 파일을 압축·암호화하여 포장 | 인증 서버와 연동해 실행 권한 통제 |
| 실행 방식 | 네이티브 코드로 직접 실행 | 실행 시 메모리에서 풀어서 실행 | 전용 복호화 모듈을 거쳐 실행 |
| 성능 영향 | 연산 지연, 파일 크기 증가 | 초기 로딩 지연 | 지속적인 라이선스 확인 부하 |
| 대응 한계 | 분석 시간만 늘릴 뿐 완전 차단 불가 | 메모리 덤프로 원본 복원 가능 | 키가 탈취되면 콘텐츠 노출 |
| 대표 도구 | ProGuard, DexGuard, OLLVM | UPX, Themida, VMProtect | Widevine, PlayReady |

- 선택 기준 : 보호 대상이 알고리즘인지 콘텐츠인지, 성능 저하를 감수할 수 있는지에 따라 난독화, 패킹, DRM을 조합함.

## Ⅴ. 코드 난독화의 한계와 방안

- 핵심 요약 : 성능 저하, 자동 복원 도구의 발전, 장애 분석의 어려움을 선별 적용, 다계층 런타임 보호, 매핑 파일 관리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 실행 성능 저하와 크기 증가 | 불투명 술어와 더미 코드로 실행 사이클과 바이너리 크기가 늘어남 | 전체가 아니라 핵심 로직과 보안 모듈만 선별 난독화 | 기동 시간, 바이너리 크기 |
| 자동 복원 도구의 발전 | 기호 실행과 SMT(Satisfiability Modulo Theories) 솔버로 불투명 술어를 제거하고 흐름을 복원 | 정적 방어에 그치지 않고 안티 디버깅, 후킹 탐지, 무결성 검증을 결합한 RASP(Runtime Application Self-Protection) 적용 | 변조 탐지 건수 |
| 장애 분석의 어려움 | 운영 중 스택 트레이스의 함수명이 난독화되어 원인 추적이 지연 | 빌드마다 생성되는 매핑 파일을 보안 저장소에 보관하고 크래시 분석과 연동 | 장애 원인 분석 소요 시간 |

## Ⅵ. 코드 난독화에 대한 기술사적 제언

- 핵심 요약 : 난독화를 단독 방패로 두지 않고, 네이티브 컴파일 단계 보호, 무결성 검증, 핵심 로직의 서버 이전을 묶은 설계로 전환.
- 바이트코드보다 분석이 어려운 C/C++ 네이티브 빌드 단계에서 **OLLVM** (LLVM 기반 난독화 컴파일러)을 적용하면 명령어 치환과 레지스터 난독화를 함께 얻을 수 있다.
- 앱 바이너리가 재서명되거나 변조되면 실행을 중단하는 **안티 탬퍼링** (Anti-Tampering, 변조 감지와 실행 차단 기법)을 기본 탑재해야 한다.
- 결제 로직이나 핵심 암호 알고리즘은 클라이언트에 두지 않고 서버 API 뒤로 옮기는 설계가 근본적인 해결책이다.

## Ⅶ. 결론

- 핵심 요약 : 코드 난독화는 역공학을 영구히 막는 기술이 아니라 분석 비용을 높이는 시간 지연 수단임.
- 시사점 : 난독화는 무결성 검증과 서버 측 로직 이전을 보완하는 한 계층으로 쓸 때 실효성이 있음.
