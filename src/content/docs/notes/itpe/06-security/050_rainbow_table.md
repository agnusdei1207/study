## 연관 키워드

- 레인보우 테이블, 시간-메모리 트레이드오프, 해시 체인, 축약 함수
- 무차별 대입, 솔트, 키 스트레칭, PBKDF2, bcrypt, Argon2id

## Ⅰ. 레인보우 테이블의 개요

- 핵심 요약 : 해시 체인을 압축 저장해 사전 계산 비용과 저장 공간을 절충한 비밀번호 역산용 룩업 테이블.
- 개념 : 단방향 해시의 출력값을 미리 계산해 두고 **해시 체인**(Hash Chain)의 시작점과 끝점만 저장하여, 해시 역산을 **시간-메모리 트레이드오프**(TMTO, Time-Memory Trade-off) 방식으로 수행하는 공격용 테이블.
- 배경 및 필요성 : 단순 **무차별 대입**(Brute-Force)은 연산 시간이 과도하고, 모든 해시를 저장하는 전수 테이블은 저장 공간이 현실적이지 않아, 두 방식의 절충안으로 2003년 Philippe Oechslin이 제안.
- 주요 목적 : 솔트 없이 저장된 비밀번호 해시의 역산 속도를 높이는 공격 기법을 이해하고, 이를 무력화하는 **솔트**(Salt)와 **키 스트레칭**(Key Stretching) 방어의 필요성을 확인하는 것.

## Ⅱ. 레인보우 테이블의 특징 및 장점

- 핵심 요약 : 사전 계산과 체인 압축이 온라인 역산 속도를 끌어올리며, 이 효율은 솔트가 없는 저장 방식에서만 유효함.

1. 사전 계산 분리 : 오프라인에서 체인을 생성하고 온라인에서는 조회만 수행 → 실시간 역산 시간 단축.
2. 체인 압축 : 중간 값을 버리고 시작점과 끝점만 저장 → 전수 테이블 대비 저장 공간 절감.
3. 축약 함수 교체 : 체인의 단계마다 서로 다른 축약 함수를 적용 → 같은 함수에서 생기는 체인 병합을 줄여 탐색 범위 확대.

## Ⅲ. 레인보우 테이블의 구조 (흐름)

- 핵심 요약 : 체인 생성은 사전에 한 번 수행하고, 역산은 대상 해시를 체인의 끝점과 대조하는 두 단계 구조.
- **축약 함수**(Reduction Function) : 해시값을 다시 유효한 비밀번호 후보 문자열로 바꾸는 함수로, 체인 단계마다 R1, R2, ..., Rk로 달리 적용.

```text
[ 1. 체인 생성 (사전 계산) ]

시작 평문 P0
      ↓ H (해시)
해시값 H0
      ↓ R1 (축약 함수)
평문 P1
      ↓ H, R2 ... 반복
최종값 EP

※ 테이블에는 P0과 EP 두 값만 저장
```

```text
[ 2. 역산 (온라인 검색) ]

대상 해시 H_target
      ↓ Rk 적용
값 X
      ↓ 테이블의 EP 열과 대조
      ↓ 불일치 시 한 단계 앞으로 되돌려 반복
일치 행의 P0에서 체인 재연산
      ↓
H_target 직전의 평문 복원
```

- **체인 병합**(Chain Collision) : 서로 다른 체인이 중간에서 같은 값을 만나 합쳐지면 일부 평문이 테이블에서 누락되어 탐색이 실패할 수 있는 현상.

## Ⅳ. 레인보우 테이블의 비교

- 핵심 요약 : 전수 공격은 시간을, 전수 룩업 테이블은 저장 공간을 과다하게 요구하므로 레인보우 테이블이 그 중간 지점을 택한 구조.

| 비교 항목 | 전수 공격 (Brute-Force) | 전수 룩업 테이블 | 레인보우 테이블 |
| --- | --- | --- | --- |
| 사전 계산 | 없음 | 모든 조합을 미리 계산 | 체인 생성에 시간 소요 |
| 저장 공간 | 불필요 | 현실적으로 과다 | 체인 압축으로 절감 |
| 온라인 역산 속도 | 가장 느림 | 가장 빠름 | 빠름 |
| 시간-메모리 균형 | 시간 많음, 메모리 없음 | 시간 없음, 메모리 많음 | 두 자원의 절충점 |
| 솔트 적용 시 | 영향이 작음 | 사전 계산 무용지물 | 테이블 전체가 무력화 |

- 선택 기준 : 공격자 입장에서는 대상 해시 체계에 솔트가 없는지가 레인보우 테이블 적용 가능 여부를 가르는 기준임.

## Ⅴ. 레인보우 테이블의 한계와 방안

- 핵심 요약 : 솔트 미적용, 고속 해시 사용, 약한 비밀번호 저장이 공격 조건을 만들므로 각각에 대응하는 방어를 함께 적용.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 솔트 미적용 저장 | 공통 사전 계산 테이블을 여러 계정에 재사용 가능 | 사용자별 **CSPRNG**(Cryptographically Secure Pseudorandom Number Generator, 암호학적으로 안전한 의사난수 생성기) 기반의 충분히 긴 무작위 Salt 적용 | 솔트 미적용 계정 수 |
| 고속 해시의 병렬 연산 취약성 | SHA-256 같은 범용 해시는 하드웨어 병렬 연산에 최적화되어 대량 시도가 가능 | 키 스트레칭 기능을 가진 Argon2id, bcrypt, PBKDF2 적용 | 해싱 연산 지연 시간 |
| 약한 비밀번호의 저장 | 짧고 단순한 비밀번호가 사전 계산 대상에 그대로 포함 | 최소 길이·복잡도 정책과 유출 비밀번호 대조 | 정책 위반 가입 차단 수 |

## Ⅵ. 레인보우 테이블에 대한 기술사적 제언

- 핵심 요약 : 해시 저장 방식을 조직 차원에서 점검하고, 레거시 저장 방식을 무중단으로 바꾸는 전환 체계를 갖추는 것이 핵심.

1. 기존 데이터베이스에 MD5나 솔트 없이 저장된 비밀번호 해시가 남아 있는지 전수 점검하고, Argon2id 기반 저장 방식으로 전환해야 한다. 전환은 사용자가 로그인하는 시점에 새 방식으로 재해싱하는 방식으로 서비스 중단 없이 진행할 수 있다.
2. 키 스트레칭 파라미터는 서버 성능과 로그인 응답 시간을 함께 고려해 정기적으로 상향 검토해야 한다.
3. 회원 가입과 비밀번호 변경 시점에 유출 비밀번호 목록과 대조하는 정책을 두어, 사전 계산 대상이 되는 약한 비밀번호가 저장되지 않게 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 레인보우 테이블은 해시 함수 자체보다 솔트 없는 저장과 고속 해시의 조합이 만든 공격 기법임.
- 시사점 : 솔트와 키 스트레칭을 기본값으로 삼으면 사전 계산 공격은 실효성을 잃으므로, 저장 방식이 비밀번호 보호의 첫 번째 방어선이 됨.
