## Ⅰ. 레인보우 테이블(Rainbow Table)의 개요

- **개념** : 해시 함수의 단방향 암호화 특성을 역이용하여, 가능한 모든 평문과 그에 대응하는 해시값을 미리 대량으로 계산해 둔 후 해시 체인(Hash Chain)과 축약 함수(Reduction Function)를 통해 메모리 용량을 획기적으로 압축하여 저장한 시간-메모리 트레이드오프(Time-Memory Trade-off) 기반의 암호 해독 룩업 테이블.
- **배경 및 필요성** : 단순 무차별 대입(Brute-Force)은 연산 시간이 너무 오래 걸리고, 전수 룩업 테이블(Full Precomputed Table)은 수 페타바이트의 스토리지 용량이 필요한 한계를 극복하기 위해 Philippe Oechslin이 제안.
- **핵심 목적** : 단방향 해시로 저장된 사용자 비밀번호의 고속 역산 크랙, 해시 함수의 충돌 저항성 평가, 솔트(Salt) 및 키 스트레칭 방어 기법의 필요성 입증.

## Ⅱ. 레인보우 테이블(Rainbow Table)의 핵심 아키텍처 및 동작 메커니즘

레인보우 테이블은 해시 함수(H)와 해시값을 다시 평문 도메인으로 매핑하는 축약 함수(R)를 번갈아 적용하여 긴 해시 체인을 형성하고, 시작점(Start Point)과 끝점(End Point)만을 저장하여 저장 공간을 절약함.

```text
[ 레인보우 체인의 생성 및 비밀번호 역산 메커니즘 ]

  [ 1. 체인 생성 단계 (Precomputation) ]
  평문(P0) ──H──> H0 ──R1──> P1 ──H──> H1 ──R2──> P2 ... ──H──> Hk ──Rk──> 최종값(EP)
  * 저장 테이블: 오직 [ 시작 평문 P0 ] 과 [ 최종값 EP ] 만 테이블에 2개 열로 저장!
    (중간에 생성된 수만 개의 해시값은 모두 버림 -> 스토리지 용량 대폭 절약)

  ========================================================================

  [ 2. 크랙/역산 단계 (Online Search) ]
  공격 대상 암호화 해시: H_target
  1. H_target 에 축약 함수 Rk 적용 -> 값 X 도출
  2. 테이블의 [ 최종값 EP ] 열에서 X를 검색
     - 없으면: H_target 에 R_(k-1) 적용 후 다시 H, Rk 적용하여 검색 (반복)
     - 일치 발견 시: 해당 행의 [ 시작 평문 P0 ] 부터 체인을 재연산하여
                     H_target 바로 직전의 평문 P_(target) 도출 -> 암호 해독 성공!
```

- **시간-메모리 트레이드오프(TMTO)** : 모든 해시를 저장하지 않고 체인의 시작점과 끝점만 저장함으로써, 약간의 재계산 시간(Time)을 대가로 엄청난 스토리지 공간(Memory)을 절약.
- **축약 함수(Reduction Function)** : 해시값(예: 32바이트 16진수)을 다시 유효한 비밀번호 문자열(예: 8자리 영숫자)로 변환하는 함수.
- **다양한 축약 함수(R1, R2, ..., Rk)의 레인보우 색상 적용** : 동일한 축약 함수 사용 시 발생하는 체인 충돌(Merge/Collision)을 방지하기 위해 체인의 각 스텝마다 서로 다른 축약 함수를 적용(마치 무지개 색상처럼 배열).
- **체인 충돌 및 누락(False Alarm)** : 서로 다른 체인이 중간에 동일한 값을 만나 합쳐질 경우 탐색 실패가 발생할 수 있어 여러 개의 독립된 테이블 생성 필요.

## Ⅲ. 레인보우 테이블(Rainbow Table)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 전수 공격 (Brute-Force) | 사전 계산 룩업 테이블 (Lookup Table) | 레인보우 테이블 (Rainbow Table) |
| --- | --- | --- | --- |
| 사전 계산 시간 | 없음 (즉시 공격 시작) | 극도로 김 (모든 조합 사전 계산) | 김 (체인 생성에 시간 소요) |
| 스토리지 용량 | 0 (저장 불필요) | 천문학적 (현실적 불가) | 적절함 (체인 압축으로 절감) |
| 실시간 해독 속도 | 극도로 느림 (수일~수년 소요) | 즉시 (O(1) 해시 테이블 검색) | 매우 빠름 (수초~수분 이내 탐색) |
| 시간-메모리 효율 | 시간 최대, 메모리 최소 | 시간 최소, 메모리 최대 | 시간과 메모리의 최적 절충점 달성 |
| 솔트(Salt) 방어력 | 무차별 대입에 약간의 지연 | 솔트 적용 시 사전 계산 무용지물 | 솔트 적용 시 테이블 전량 무력화 |

- 레인보우 테이블은 오프라인 사전 계산을 통해 실시간 온라인 크랙 속도를 비약적으로 단축시킨 기법이나, 사용자별 고유한 솔트(Salt)가 추가되면 사전 계산 테이블 전체가 무력화됨.

## Ⅳ. 레인보우 테이블(Rainbow Table)의 주요 한계점 및 해결 방안

- **암호학적 솔트(Cryptographic Salt) 적용 시 테이블 완전 무력화** :
  - **한계점** : 비밀번호마다 128비트 이상의 무작위 난수(Salt)를 결합하여 해시하면, 공격자가 각 솔트값마다 별도의 레인보우 테이블을 새로 생성해야 하므로 사전 계산 불가능.
  - **해결 방안** : 모든 패스워드 해싱 시 사용자별 고유한 CSPRNG(암호학적으로 안전한 의사난수) 기반 128비트 이상 Salt를 반드시 적용.
- **단순 고속 해시(MD5, SHA-256)의 GPU 클러스터 병렬 연산 취약성** :
  - **한계점** : SHA-256 등 범용 해시는 하드웨어 연산에 최적화되어 있어, 고성능 GPU 클러스터로 초당 대량의 해시를 연산하여 실시간 전수 공격 가능.
  - **해결 방안** : 메모리 집약적(Memory-Hard)이고 연산 비용이 높은 표준 KDF인 Argon2id, bcrypt, PBKDF2를 적용하여 GPU 가속 무력화.
- **체인 병합(Chain Collision / Merge)으로 인한 탐색 실패율 존재** :
  - **한계점** : 축약 함수 연산 중 서로 다른 평문이 우연히 동일한 값을 생성하여 체인이 겹칠 경우 탐색 대상 평문이 테이블에서 누락되는 현상.
  - **해결 방안** : 다양한 색상의 축약 함수 셋(R1~Rk)을 적용하고 체인 길이를 적정 수준(1,000~10,000)으로 제한하며 복수 테이블 중첩 생성.

## Ⅴ. 레인보우 테이블(Rainbow Table) 적용 및 발전을 위한 기술사적 제언

- **레거시 단방향 해시 알고리즘 전면 교체** : DB 내에 MD5, SHA-1, 솔트 없는 SHA-256으로 저장된 비밀번호 컬럼을 탐지하여 Argon2id로 강제 마이그레이션.
- **키 스트레칭(Key Stretching) 반복 횟수(Work Factor) 최적화** : PBKDF2 적용 시 충분히 높은 반복 횟수, bcrypt cost 파라미터도 충분히 높게 설정하여 연산 지연 유도.
- **비밀번호 복잡도 정책 및 유출 크리덴셜 차단** : 8자리 단순 비밀번호를 금지하고, Have I Been Pwned API와 연계하여 이미 다크웹에 유출된 비밀번호 사용을 등록 시점에 차단.
