## 30초 인출

- **본질**: 레인보우 테이블은 해시·환원함수 연쇄를 미리 계산해 해시에서 비밀번호 후보를 찾는 시간·메모리 절충 공격 기법.
- **메커니즘**: 후보 → 해시 → 위치별 환원함수 반복 → 체인 양 끝만 저장 → 탈취 해시와 끝점 대조 후 체인 재계산.
- **방어**: 계정별 salt와 비용 인자가 있는 비밀번호 해싱으로 사전 계산 결과의 재사용과 오프라인 추측 속도를 낮춤.

<details><summary>핵심 용어</summary>

- **레인보우 테이블(Rainbow Table)**: 해시·환원함수 체인의 시작점과 끝점을 저장해 해시 후보를 찾는 사전 계산 자료구조.
- **환원함수(Reduction Function)**: 해시 출력을 비밀번호 후보 공간으로 옮기는 함수로, 해시의 역함수는 아님.
- **Salt**: 비밀번호별 해시 입력에 더하는 임의 값으로, 같은 비밀번호의 해시를 다르게 만들고 사전 계산표의 재사용을 방해.
- **비밀번호 해싱(Password Hashing)**: 비밀번호·salt·비용 인자로 저장용 검증값을 만드는 처리.
- **NIST(National Institute of Standards and Technology)**: 미국 연방 기술표준 기관으로, 디지털 신원 지침을 발간.

### Ⅰ. 개요

| 구분 | 핵심 |

| 목적 | 해시 저장소 탈취 뒤 후보 대조에 필요한 반복 계산과 저장 공간의 절충. |

### Ⅱ. 사전 계산과 검색

```text
사전 계산                         탈취 해시 검색
후보 → 해시 → 환원함수 ──┐        목표 해시 → 체인 위치별 계산
       ↑                 │                         ↓ 끝점 대조
       └─ 위치별 환원 ───┘                 일치 시 시작점부터 재계산
                                                   ↓
                                            후보 비밀번호 확인
```

환원함수는 체인 위치마다 달라지며, 끝점이 맞으면 시작점부터 다시 계산해 목표 해시와 후보를 확인.

### Ⅲ. 한 줄 제언

제언: 계정별 고유 salt와 충분한 비용의 비밀번호 해싱을 함께 적용해 오프라인 추측 부담을 높이는 방안.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **레인보우 테이블**은 해시·환원함수 체인을 사전 계산해 해시에서 비밀번호 후보를 찾는 자료구조. |
| 목적 | 해시 저장소 탈취 뒤 후보 대조에 필요한 반복 계산과 저장 공간의 절충. |

## Ⅱ. 생성과 검색 메커니즘

```text
생성: 시작 후보 → 해시 → 위치별 환원함수 → 다음 후보 → … → 끝점 저장
                                           (중간값은 저장하지 않음)

검색: 목표 해시 → 가능한 체인 위치부터 끝점 계산 → 저장된 끝점 대조
                                                    │ 일치
                                                    ↓
                                   해당 체인의 시작점부터 재계산
                                                    ↓
                                      목표 해시와 후보를 직접 확인
```

일치한 끝점만으로 비밀번호가 확정되지는 않으며 후보 체인을 재계산해야 함. 서로 다른 시작점의 체인이 합쳐지거나 준비한 후보 공간 밖이면 복구에 실패할 수 있음.

## Ⅲ. 시간·메모리 절충과 한계

| 방식 | 저장 공간 | 검색 비용 | 한계 |
|---|---|---|---|
| 후보별 해시 사전 | 큼 | 낮음 | 넓은 후보 공간을 저장하기 어려움 |
| 레인보우 체인 | 시작점·끝점 중심 | 체인 재계산 필요 | 체인 병합·후보 범위에 따라 복구 누락 |
| 즉석 추측 | 사전 저장 없음 | 후보마다 계산 | 빠른 해시라면 대량 오프라인 추측에 취약 |

같은 해시·환원 체계의 표는 재사용 가능하지만, salt가 다르면 salt별로 별도 사전 계산이 필요해 대량 재사용의 이점이 줄어듦.

## Ⅳ. 안전한 비밀번호 저장

```text
비밀번호 ─┐
고유 salt ─┼→ 비용 인자 적용 해싱 → 검증값 + salt + 방식·비용 버전 저장
          │
비밀키(선택) → 별도 보호영역에서 keyed hash 추가
```

NIST SP 800-63B-4는 중앙 검증 비밀번호를 salt와 비용 인자를 쓰는 적절한 방식으로 해싱하고, 비용은 성능을 해치지 않는 범위에서 높이며 시간이 지나면 조정하도록 권고. salt와 해시, 방식·비용 정보는 계정별 검증값과 함께 보관하고 추가 비밀키는 해시 저장소와 분리.

## Ⅴ. 기술사적 제언

| 한계 | 해결 방안 |
|---|---|
| 하드웨어 성능이 높아지면 과거의 고정 해싱 비용이 약해질 수 있음. | 로그인 검증 경로에 방식·비용 버전을 기록하고, 성능·위협 재평가 때 비용을 높이며 성공 로그인 시 구형 검증값을 단계적으로 갱신하는 방안. |

## 출제 이력과 검증 출처

- 공식 기출 확인 불가. 레인보우 테이블의 생성·검색과 방어 원칙을 묻는 예상문항.
- [NIST SP 800-63B-4, Authenticators](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/) — salt·비용 인자·비밀키 분리와 비밀번호 검증값 저장 원칙.
- [NIST SP 800-115, Technical Guide to Information Security Testing and Assessment](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-115.pdf) — 사전 계산 해시 공격과 salt의 방어 효과.
