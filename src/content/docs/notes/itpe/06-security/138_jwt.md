## 지식 로드맵 내 현재 위치

지식 위치: 정보보안 → 토큰 기반 인증 → **JWT**

## 30초 인출

- **본질:** 사용자 신원과 권한 정보를 담은 JSON 클레임(Claim) 세트를 Base64URL로 인코딩하고 디지털 서명(JWS) 또는 암호화(JWE)하여 무상태(Stateless)로 전달하는 웹 표준 토큰
- **메커니즘:** 클라이언트 로그인 → IdP의 개인키 서명 토큰 발급 → 리소스 서버 공개키 기반 서명·만료(exp)·발급자(iss) 무상태 검증 → 인가 승인
- **통찰:** 무상태 토큰의 즉각적 권한 철회 불가 한계는 RTR(Refresh Token Rotation)과 분산 캐시 블랙리스트로 해결하고 토큰 탈취는 DPoP 결속으로 방어 필수

<details>
<summary>핵심 용어</summary>

- **JWT (JSON Web Token)** : RFC 7519에 정의된 자가수용적(Self-contained) 클레임 기반 토큰 규격.
- **JWS (JSON Web Signature)** : 전자서명 또는 MAC을 통해 페이로드의 무결성과 진정성을 보장하는 형식.
- **JWE (JSON Web Encryption)** : 페이로드를 암호화하여 기밀성을 보장하는 형식.
- **DPoP (RFC 9449)** : 클라이언트 개인키 증명을 토큰에 결합하여 도난된 토큰의 재사용을 차단하는 기술.

</details>

## 2~4교시 예상문제 (25점)

> JWT(JSON Web Token)의 3단 구조(Header, Payload, Signature), 발급 및 무상태 검증 프로세스를 설명하고, 알고리즘 혼동(Algorithm Confusion) 및 즉각적 철회 불가 등 엔지니어링 한계와 RFC 8725 BCP 기반 해결 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 클라이언트와 서버 간에 인증 정보 및 사용자 속성을 JSON 객체 포맷으로 안전하게 전송하기 위해 RFC 7519로 표준화된 자가수용적(Self-contained) 컴팩트 토큰 |
| 목적 | 중앙 세션 저장소(Redis, DB)에 대한 상태 동기화 부하 없이, 분산 마이크로서비스 환경에서 수평적 확장성(Stateless Scalability)을 확보하고 안전한 단일 로그인(SSO) 구현 |

- HTTP 헤더의 Authorization 필드에 Bearer 스키마로 전달되며, OAuth 2.0 및 OpenID Connect(OIDC) ID 토큰의 실질적 표준 인코딩 포맷으로 활용

## Ⅱ. JWT의 핵심 기술적 특성

| 특성 항목 | 세부 내용 및 기술적 의미 | 엔지니어링 구현 가치 |
|---|---|---|
| 자가수용성 (Self-contained) | 토큰 자체에 사용자 식별자, 권한 목록, 만료 시각이 모두 포함되어 추가 DB 조회 불필요 | 마이크로서비스 간 인증 처리 레이턴시 극소화 (수 ms 이내) |
| 무상태 아키텍처 (Stateless) | 서버가 활성 세션 상태를 메모리나 DB에 유지하지 않고 암호학적 서명만 검증 | 서버 수평 증설(Scale-Out) 시 세션 클러스터링 구성 불필요 |
| 크로스 도메인 및 모바일 친화 | 쿠키(Cookie)의 동일 출처 정책(SOP) 제약을 넘어 모바일 앱, REST API, 이종 도메인 간 자유로운 전송 | 모바일 네이티브 앱 및 다중 클라우드 연동 최적화 |
| 암호학적 무결성 보장 | 비밀키(HMAC) 또는 공개키(RSA/ECDSA/EdDSA) 서명을 통해 클레임 위변조 원천 방지 | 중간 게이트웨이 및 공격자의 권한 상승(Privilege Escalation) 차단 |

- Base64URL 인코딩을 적용하여 URL 파라미터나 HTTP 헤더에 안전하게 포함될 수 있는 컴팩트 텍스트 포맷 특성 보유

## Ⅲ. JWT 3단 내부 구조 및 무상태 인증 프로세스

```text
[JWT 3단 구조 및 분산 마이크로서비스 무상태 검증 프로세스]

 JWT 포맷: [ Base64URL(Header) ] . [ Base64URL(Payload) ] . [ Signature ]

  [사용자 클라이언트]           [인증 서버 (IdP)]            [API Gateway / Microservice]
          │                           │                                    │
          │ 1. 로그인 요청 (ID/PW)     │                                    │
          ├──────────────────────────>│                                    │
          │                           │ 2. 토큰 생성:                       │
          │                           │    - RS256 비대칭 개인키 서명      │
          │                           │    - 짧은 exp(15분), jti 부여      │
          │ 3. Access/Refresh 토큰 반환│                                    │
          │<──────────────────────────┤                                    │
          │                                                                │
          │ 4. API 요청 (Header: Bearer <JWT>)                             │
          ├───────────────────────────────────────────────────────────────>│
          │                                                                │ 5. 자체 무상태 검증:
          │                                                                │    - Header alg(RS256) 검증
          │                                                                │    - IdP 공개키(JWKS)로 서명 검증
          │                                                                │    - exp 만료 및 aud 확인
          │                                                                │    - DB 조회 없이 즉시 인가
          │ 6. 정상 비즈니스 응답 반환                                     │
          │<───────────────────────────────────────────────────────────────┤
```

| 구성 영역 | 필드 및 주요 클레임 | 상세 설명 |
|---|---|---|
| Header (헤더) | `typ`: 토큰 유형 ("JWT")<br>`alg`: 서명 알고리즘 ("RS256", "ES256") | 서명 검증 방식과 키 식별자(`kid`) 명시 |
| Payload (페이로드) | `iss`: 발급자 (Issuer)<br>`sub`: 사용자 식별자 (Subject)<br>`aud`: 대상 수신자 (Audience)<br>`exp`: 만료 시간 (Unix Timestamp)<br>`jti`: 토큰 고유 식별자 | 실제 전송할 클레임(Claim) 세트 (기본 비암호화 노출) |
| Signature (서명) | `RSASHA256( Base64URL(H) + "." + Base64URL(P), PrivateKey )` | 헤더와 페이로드의 무결성을 보증하는 디지털 서명값 |

## Ⅳ. 세션 기반 인증 vs JWT 기반 인증 vs 불투명 토큰(Opaque Token) 비교

| 비교 항목 | 전통적 세션 기반 인증 | JWT (JSON Web Token) | 불투명 토큰 (Opaque / Reference) |
|---|---|---|---|
| 상태 저장 위치 | 서버 측 (Redis, RDBMS 세션 테이블) | 클라이언트 측 (자가수용적 토큰 보관) | 서버 측 (난수 문자열 $\rightarrow$ DB 매핑) |
| 서버 부하 | 요청마다 세션 DB 조회 I/O 발생 | CPU 기반 암호 서명 검증만 수행 (DB 부하 제로) | 요청마다 권한 확인 DB 조회 I/O 발생 |
| 즉각적 권한 철회 | 즉시 가능 (세션 레코드 즉시 삭제) | 기본적으로 불가능 (만료 시까지 유효) | 즉시 가능 (토큰 상태 무효화 업데이트) |
| 페이로드 노출 | 서버에만 존재 (완전 은닉) | 클라이언트 및 네트워크 노출 (기밀정보 금지) | 의미 없는 난수 문자열 (정보 노출 없음) |
| 네트워크 오버헤드 | 쿠키 헤더의 짧은 세션 ID (수십 바이트) | 클레임 포함으로 비교적 큰 크기 (수 KB) | 짧은 UUID/해시 토큰 (수십 바이트) |
| 마이크로서비스 적합성 | 낮음 (중앙 세션 동기화 병목) | 극도로 높음 (서비스 간 독립 검증 가능) | 보통 (토큰 인트로스펙션 서버 병목) |

## Ⅴ. JWT 운용 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| 공격자가 헤더를 `{"alg": "none"}`으로 조작하거나 RS256 비대칭 검증 서버에 HS256을 주입하여 공개키로 서명하는 알고리즘 혼동(Key Confusion) 공격 | 검증 라이브러리 설정 시 `none` 알고리즘을 강제 비활성화하고, 서버 코드 레벨에서 사전에 허용된 단일 서명 알고리즘(예: RS256 전용)만 명시적으로 화이트리스트 고정 |
| JWT는 완전 무상태 특성으로 인해 사용자가 로그아웃하거나 관리자가 권한을 박탈해도 토큰 만료(`exp`) 시점까지 유효하여 악의적 오용 방치 | Access Token의 수명을 극단적으로 단축(5~15분)하고, Redis 분산 인메모리 저장소에 탈취된 `jti`를 등록하는 블랙리스트 캐시 또는 블룸 필터(Bloom Filter) 결합 |
| Bearer 토큰 특성상 XSS 취약점이나 패킷 스니핑으로 토큰이 한 번 탈취되면 공격자가 어디서든 정상 사용자로 위장하여 API 호출 가능 | RFC 9449 DPoP(Demonstrating Proof-of-Possession) 표준을 적용하여 클라이언트가 생성한 비대칭 개인키 증명을 매 API 요청마다 헤더에 첨부하도록 강제 결속 |
| Base64URL 인코딩은 단순 텍스트 변환일 뿐 암호화가 아니므로 페이로드에 주민번호, 비밀번호, 내부 IP 등 민감정보 노출 위험 | 페이로드에는 최소한의 불투명 식별자(UUID)만 포함하고, 민감 데이터 전달이 필수적인 경우 JWS 대신 JWE(JSON Web Encryption, A256GCM)를 적용하여 페이로드 자체를 완전 암호화 |

## Ⅵ. 안전한 엔터프라이즈 JWT 수명주기 거버넌스 제언

```text
[엔터프라이즈 JWT 수명주기 및 다계층 방어 아키텍처]

 ┌─────────────────────────────────────────────────────────────┐
 │                 1. 클라이언트 계층: 안전한 보관             │
 │   - 웹: HttpOnly + Secure + SameSite=Strict 쿠키 보관       │
 │   - 모바일: iOS Keychain / Android KeyStore 개인키 격리      │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              2. 게이트웨이 계층: DPoP 및 검증 하드닝        │
 │   - DPoP 서명 증명 검증 (토큰 도난 후 재사용 원천 차단)    │
 │   - RFC 8725 준수 alg 화이트리스트 및 exp/iss/aud 엄격 검증 │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              3. 토큰 수명 및 철회 계층 (RTR & Redis)         │
 │   - Access Token: 초단기 수명 (10분)                        │
 │   - Refresh Token: 일회용 회전 (RTR: 사용 즉시 파기 및 재발급)│
 │   - 비상 철회: Redis Cluster 기반 탈취 jti 분산 블랙리스트  │
 └─────────────────────────────────────────────────────────────┘
```

| 관리 영역 | 핵심 엔지니어링 세부 과제 | 통제 목표치 |
|---|---|---|
| 토큰 하드닝 | RFC 8725 BCP 준수 `alg: none` 차단 및 서명 검증 강화 | 알고리즘 조작 공격 성공률 0% |
| 세션 수명 관리 | Access Token 10분, Refresh Token Rotation 적용 | 미인가 장기 세션 잔존율 0% |
| 토큰 도난 방어 | API 게이트웨이 DPoP 프로토콜 전면 도입 및 쿠키 보안 강제 | 토큰 재사용 침해 사고 0건 |
