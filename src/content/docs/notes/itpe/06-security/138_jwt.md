## Ⅰ. JWT(JSON Web Token)의 개요

- **개념** : 당사자 간에 정보를 안전하고 간결하게 전송하기 위해 정보를 JSON 객체로 정의하고, 암호학적 디지털 서명(HMAC 또는 RSA/ECDSA)을 적용하여 위변조를 방지하는 자가 수용적(Self-contained) 개방형 웹 표준(RFC 7519) 토큰.
- **배경 및 필요성** : 전통적인 세션 기반 인증은 서버의 메모리나 공유 저장소(Redis)에 세션 상태를 유지해야 하므로, 대규모 트래픽이 발생하는 마이크로서비스 아키텍처(MSA) 및 모바일 환경에서 수평적 확장(Scale-out) 시 동기화 병목이 발생함.
- **핵심 목적** : 토큰 자체에 사용자의 신원 및 권한 정보(Claims)를 내장하여 서버의 세션 DB 조회 없이도 무상태(Stateless) 분산 인증을 초고속으로 처리.

## Ⅱ. JWT(JSON Web Token)의 핵심 아키텍처 및 동작 메커니즘

JWT는 마침표(.)를 구분자로 하여 헤더(Header), 내용(Payload), 서명(Signature)의 3개 영역으로 구성되며, Base64URL로 인코딩되어 HTTP 헤더에 실려 전송됨.

```text
[ JWT(JSON Web Token) 구조 및 무상태 검증 아키텍처 ]

 JWT 문자열 구조:
 [ Header (Base64URL) ] . [ Payload (Base64URL) ] . [ Signature (암호학적 서명) ]
         |                         |                           |
         v                         v                           v
 +-------------------+     +---------------------+     +-------------------------+
 | {                 |     | {                   |     | HMACSHA256(             |
 |   "alg": "HS256", |     |   "sub": "user123", |     |   base64UrlEncode(head) |
 |   "typ": "JWT"    |     |   "role": "admin",  |     |   + "." +               |
 | }                 |     |   "exp": 1700000000 |     |   base64UrlEncode(pay), |
 +-------------------+     | }                   |     |   SecretKey             |
                           +---------------------+     | )                       |
                                                       +-------------------------+

 [ 마이크로서비스 환경에서의 무상태(Stateless) 인증 흐름 ]
  [클라이언트] ---- (1) 로그인 요청 (ID/PW) ----> [ 인증 서비스 (Auth Server) ]
                                                   * 서명 키로 JWT 발급
  [클라이언트] <--- (2) JWT 토큰 발급 (Header) <----+
       |
       | (3) API 요청 (Authorization: Bearer <JWT>)
       +------------------------------------+
       |                                    |
       v                                    v
 [ 마이크로서비스 A ]                 [ 마이크로서비스 B ]
  * 세션 DB 조회 없음!                 * 세션 DB 조회 없음!
  * 자체 보관 공개키로 서명 검증       * 페이로드 Claim(role) 즉각 판독
  * 즉시 인가 처리                     * 고속 처리 완료
```

- **헤더(Header)** : 토큰의 타입(typ: 'JWT')과 서명에 사용된 암호화 알고리즘(alg: 'HS256', 'RS256', 'ES256')을 명시.
- **내용(Payload)과 클레임(Claims)** : 토큰에 담길 정보의 조각들로 등록된 클레임(iss: 발급자, sub: 주제, exp: 만료시간, nbf: 활성시간), 공개 클레임, 사용자 정의 비공개 클레임으로 구성.
- **서명(Signature)** : 헤더와 페이로드를 Base64URL 인코딩한 후 서버의 비밀키(대칭키)나 개인키(비대칭키)로 암호화 해시 서명하여 위변조를 완벽히 차단.
- **자가 수용성(Self-contained)** : 인증 및 인가 처리에 필요한 모든 정보가 토큰 자체에 포함되어 있어, 수평적으로 확장된 수백 대의 분산 API 서버가 중앙 DB에 의존하지 않고 독자 검증 가능.

## Ⅲ. JWT(JSON Web Token)의 세부 구성 요소 및 비교 분석

| 비교 항목 | JWT (JSON Web Token) | 서버 세션 (Session-Cookie) | 불투명 토큰 (Opaque Token) |
| --- | --- | --- | --- |
| 상태 저장 | 무상태 (Stateless, 서버 저장소 없음) | 상태 유지 (Stateful, 서버 메모리/Redis) | 상태 유지 (서버 DB에 매핑 저장) |
| 확장성 | 극도로 우수 (MSA 및 멀티 리전 최적) | 서버 간 세션 클러스터링 동기화 부담 | 토큰 검증 시마다 중앙 서버 DB 조회 |
| 페이로드 노출 | 평문 노출 (Base64 디코딩 누구나 가능) | 클라이언트는 난수 세션 ID만 보유 | 클라이언트는 무의미한 난수 문자열 보유 |
| 즉각 폐기 | 원칙적 불가능 (토큰 만료까지 유효) | 서버에서 세션 삭제 시 즉시 만료 | 서버 DB에서 레코드 삭제 시 즉시 만료 |
| 네트워크 부하 | 토큰 크기가 커서 대역폭 오버헤드 있음 | 쿠키 크기가 작아 네트워크 부하 낮음 | 토큰 크기 작음, DB I/O 부하 높음 |

- JWT는 MSA 환경의 분산 무상태 아키텍처에 가장 이상적인 토큰 규격이나, 페이로드 기밀성 미보장과 실시간 토큰 폐기 불가라는 트레이드오프 관리가 필수적임.

## Ⅳ. JWT(JSON Web Token)의 주요 한계점 및 해결 방안

- **발급 후 즉각적인 강제 폐기(Revocation) 불가능** :
  - **한계점** : 사용자가 로그아웃하거나 권한이 박탈되어도, 토큰 자체의 유효기간(exp)이 만료되기 전까지는 발급된 JWT로 시스템 접근이 가능.
  - **해결 방안** : Access Token 유효기간을 짧게 극단적으로 단축하고, Refresh Token을 이용한 재발급(Rotation) 및 Redis 기반 블랙리스트(Denylist) 보완.
- **Base64URL 단순 인코딩에 따른 데이터 기밀성(Confidentiality) 부재** :
  - **한계점** : 서명은 위변조만 방지할 뿐 암호화가 아니므로, 페이로드에 비밀번호, 주민번호 등 민감정보를 담을 경우 누구나 디코딩하여 탈취 가능.
  - **해결 방안** : 민감정보의 페이로드 적재를 엄격히 금지하고, 필요 시 JWE(JSON Web Encryption) 표준을 적용하여 페이로드 자체를 암호화.
- **'alg: none' 취약점 및 서명 검증 우회 공격** :
  - **한계점** : 일부 미흡한 검증 라이브러리가 헤더의 alg 필드를 'none'으로 조작한 토큰을 서명 검증 없이 정상 수락하여 관리자 권한 탈취 발생.
  - **해결 방안** : 서버 검증 로직에서 허용 알고리즘을 화이트리스트(예: RS256만 강제)로 명시하고 'none' 알고리즘을 코드 레벨에서 원천 거부.

## Ⅴ. JWT(JSON Web Token) 적용 및 발전을 위한 기술사적 제언

- **비대칭키 서명(RS256 / ES256) 기반 마이크로서비스 설계** : 대칭키(HS256) 공유에 따른 키 유출 리스크를 제거하기 위해 인증 서버만 개인키로 서명하고 모든 마이크로서비스는 JWKS(공개키 엔드포인트)로 검증.
- **Refresh Token Rotation(RTR)을 통한 자격증명 도난 방어** : Refresh Token을 사용하여 새 Access Token을 발급할 때마다 기존 Refresh Token을 즉시 파기하고 새로운 Refresh Token을 재발급하여 재사용 시도 탐지.
- **OAuth 2.0 DPoP(Demonstrating Proof-of-Possession) 표준 도입** : 탈취된 JWT의 악용을 막기 위해 클라이언트의 개인키 서명을 토큰 요청에 바인딩하여 토큰을 훔쳐도 타 기기에서 사용하지 못하도록 하드닝.
