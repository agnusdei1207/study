## 지식 로드맵 내 현재 위치

정보보안 → 토큰 기반 인증 → JWT(JSON Web Token)

## 30초 인출

- 본질: JWT는 JSON 클레임을 JWS 서명 또는 JWE 암호화 형태로 전달하는 형식이며, 토큰 검증만으로 인가가 완료되지는 않음
- 메커니즘: 서명·알고리즘·발급자·대상·만료 검증 → 현재 권한·철회 정책 확인 → 접근 허용

<details><summary>핵심 용어</summary>

- **JWS:** 서명 또는 MAC으로 무결성을 보호하는 표현.
- **JWE:** ** 내용을 암호화해 기밀성을 제공하는 표현.

</details>

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | JSON 클레임을 JWS 서명 또는 JWE 암호화 형태로 전달하는 토큰 형식 |
| 목적 | 주체·발급자·대상 등 검증 가능한 클레임의 전달 |

- **정의:** ** RFC 7519의 JSON 클레임 전달 형식으로 서명형 JWS 또는 암호화형 JWE로 표현.
- **구조:** ** 일반적인 Compact JWS는 Base64url(Header).Base64url(Payload).Signature의 세 부분.
- **검증:** ** 허용 알고리즘·키와 서명, 발급자(iss)·대상(aud)·만료(exp)를 서비스 정책에 맞게 검사. Base64url 인코딩은 암호화가 아님.

## 2~4교시 25점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | JSON 클레임을 JWS 서명 또는 JWE 암호화 형태로 전달하는 토큰 형식 |
| 목적 | 주체·발급자·대상 등 검증 가능한 클레임의 전달 |

### Ⅱ. 토큰 역할
- 발급자가 주체·대상·시각 등의 클레임을 담아 전달. 토큰 검증과 실제 권한 인가는 별개 결정.
### Ⅲ. 처리 흐름
- 발급 → 보호된 채널로 전송 → 서명/암호 및 알고리즘·키 확인 → 필수 클레임 검증 → 권한·철회 정책 적용.
### Ⅳ. 주요 위험
- `alg` 혼동·무서명 토큰 수용, 토큰 탈취·재사용, 노출 가능한 JWS 페이로드, 장기 유효 토큰의 철회 지연.
### Ⅴ. 통제
- 알고리즘과 키의 고정·검증, 짧은 유효기간의 정책별 설정, 민감 클레임 최소화, 재발급 토큰 보호·회전과 철회 수단 설계.

### 기술사적 제언

- 토큰 검증과 인가를 분리하고 허용 알고리즘·대상·만료·철회 정책을 서비스 경계마다 검증한다.
