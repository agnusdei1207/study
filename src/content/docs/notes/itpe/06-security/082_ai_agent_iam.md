## 연관 키워드

- AI 에이전트 IAM, 머신 신원(NHI, Non-Human Identity), 단기 위임 권한, Confused Deputy
- RFC 8693 Token Exchange, Actor Claim, 정책 집행점(PEP), Just-In-Time 접근
- 과도한 권한 행사(Excessive Agency), SPIFFE, mTLS, 최소 권한

## Ⅰ. AI 에이전트 IAM의 개요

- 핵심 요약 : 사용자를 대리하는 AI 에이전트에 머신 신원과 단기 위임 권한을 부여해 통제하고 감사하는 신원 관리 체계.
- 개념 : 사용자를 대리해 복합 작업을 수행하는 AI 에이전트에 고유 **머신 신원** (NHI, Non-Human Identity)을 주고, 작업 단위의 **단기 위임 권한**을 동적으로 제어·감사하는 신원 및 접근 통제 체계 (**AI 에이전트 IAM**).
- 배경 및 필요성 : 도구 호출과 외부 API 실행 권한을 가진 자율 에이전트가 늘어나면서, 비인가 대리 실행과 권한 남용을 막고 작업 전 과정을 추적할 체계가 필요해짐.
- 주요 목적 : **과도한 권한 행사** (Excessive Agency)와 **Confused Deputy** (대리인 공격) 방지, 비인가 리소스 조작 차단, 종단 간 책임 추적성 확보.

## Ⅱ. AI 에이전트 IAM의 특징 및 장점

- 핵심 요약 : 사용자 권한을 작업 단위로 좁혀 위임하고 호출마다 검사하는 방식이, 권한 남용 위험과 사고 시 책임 범위를 함께 줄임.

1. 위임 토큰 교환 : 사용자 토큰을 **RFC 8693** Token Exchange로 교환해 최소 범위의 대리 토큰 발급 → 에이전트가 맡은 작업 이상의 권한을 갖지 않음.
2. 단기 수명 : 작업 한 건에 맞춘 임시 토큰 사용 → 자격증명이 탈취되어도 노출 시간이 짧음.
3. 호출 단위 검사 : 정책 집행점(PEP)에서 도구 파라미터를 검증 → 프롬프트 인젝션이 있어도 파괴적 실행을 차단.
4. 이중 추적 : 사용자 식별자와 에이전트 인스턴스 ID를 함께 기록 → 사고 시 누가 위임했고 무엇을 실행했는지 추적 가능.

## Ⅲ. AI 에이전트 IAM의 구조 (흐름)

- 핵심 요약 : 사용자 위임, 토큰 교환, 정책 검사, 자원 접근, 감사 기록이 순서대로 이어지는 구조.
- 토큰 교환 : 사용자 원본 토큰과 에이전트의 머신 자격증명을 검증하고, 범위를 줄인 대리 토큰을 발행.
- 정책 집행 : 도구 호출 파라미터의 금액 한도, 대상 자산, 비정상 질의 여부를 검사.
- 토큰 구조 : JWT(JSON Web Token) 안에 위임자(`sub`)와 대리 실행자(`act`)를 중첩해 명시.

```text
[ 사용자 ]
    ↓ 1. 인증 및 작업 위임
[ AI 에이전트 ]
    ↓ 2. RFC 8693 토큰 교환 요청
[ 인가 서버 ]
    ↓ 3. 신원 검증·범위 축소 토큰 발급
[ AI 에이전트 ]
    ↓ 4. 도구 호출 요청
[ 정책 집행점 (PEP) ]
    ↓ 5. 파라미터 검증
[ 대상 리소스 서버 ]
    ↓ 6. 실행 및 감사 기록
```

## Ⅳ. 전통적 사용자 IAM과 AI 에이전트 IAM의 비교

- 핵심 요약 : 사람의 세션 단위 인증에서 기계의 작업 단위 위임으로 권한 모델이 바뀌는 구조.

| 비교 축 | 전통적 사용자 IAM | AI 에이전트 IAM |
| --- | --- | --- |
| 인증 주체 | 임직원, 고객 | LLM 런타임, 마이크로서비스 에이전트 |
| 인증 수단 | 패스워드, FIDO2, OTP 기반 MFA | mTLS, 워크로드 자격증명, SPIFFE |
| 인가 모델 | RBAC 기반 정적 권한 그룹 | ABAC 기반 작업별 JIT 동적 위임 |
| 권한 수명 | 수 시간에서 수 주 세션 | 작업 한 건 단위의 단기 토큰 |
| 주요 위협 | 피싱, 자격증명 스터핑, 세션 탈취 | 프롬프트 인젝션, Confused Deputy, 권한 과다 |

- 선택 기준 : 사람이 개입하는 세션은 기존 사용자 IAM으로, 에이전트가 자율적으로 연속 호출하는 경로는 에이전트 IAM으로 분리해 관리.

## Ⅴ. AI 에이전트 IAM의 한계와 방안

- 핵심 요약 : 위임 체인 단절, 데이터 유출형 권한 악용, 고정 자격증명, 정책 검사 지연을 체인 보존, 목적지 통제, 동적 시크릿, 캐시 설계로 해결.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 다단계 에이전트 체인의 신원 누락 | 중간 에이전트에서 원 사용자 식별자가 빠져 책임 추적 불가 | 중첩된 Actor Claim 체인을 강제해 종단 리소스까지 원 사용자 식별자 보존 | 체인 내 신원 보존율 |
| **Confused Deputy** (대리인 공격) | 간접 프롬프트 인젝션으로 정상 권한을 악용해 민감 데이터를 외부로 전송 | 에이전트의 외부 전송 목적지를 허용 목록으로 제한하고 중요 데이터 접근 시 재인증 요구 | 비허용 목적지 전송 차단 건수 |
| 고정 API 비밀키 노출 | 에이전트 환경에 장기 시크릿이 하드코딩되어 컨테이너 탈취 시 확산 | 1회용 동적 시크릿 주입과 클라우드 인스턴스 역할 기반 무키 인증 | 장기 시크릿 보유 건수 |
| 정책 검사 지연 | 잦은 토큰 교환과 정책 검증이 API 응답을 지연 | PEP에 로컬 정책 캐시를 두고 서명 검증을 분산 처리 | 정책 검사 지연 시간 |

```text
[ 에이전트 요청의 권한 검증 흐름 ]

에이전트 작업 요청
   ↓ 원 사용자 식별자 체인 보존
종단 리소스까지 Actor Claim 유지
   ↓ 외부 전송 목적지 허용 목록 검사
중요 데이터 접근 시 재인증 요구
   ↓ 정책 판정은 로컬 캐시 활용
작업 단위 단기 토큰과 동적 시크릿
```

## Ⅵ. AI 에이전트 IAM의 기술사적 제언

- 핵심 요약 : 신원 인프라, 인가 통제, 감사 증적을 함께 설계해 에이전트 권한을 사람 계정과 같은 수준의 거버넌스 대상으로 편입.

1. 플랫폼 조직은 에이전트마다 워크로드 신원을 자동 발급하고 고정 자격증명을 폐기하는 절차를 표준화해, 자격증명 유출의 원천을 줄여야 한다.
2. 보안 조직은 도구 호출 단위의 정책 검사를 기본값으로 삼고, 파괴적 작업에는 사람의 재확인을 붙이는 인가 기준을 마련해야 한다.
3. 규제 대응 조직은 자율 판단으로 발생한 거래와 처리에 대해 사용자와 에이전트의 이중 감사 증적을 보존하는 방식을 법무 기준과 함께 정해야 한다.

## Ⅶ. 결론

- 핵심 요약 : AI 에이전트 IAM은 자율 실행하는 기계에 사람과 다른 방식의 신원과 위임 통제를 부여하는 체계.
- 시사점 : 에이전트가 늘어날수록 권한을 작업 단위로 좁히고 추적하는 능력이 보안의 기본 조건이 됨.
