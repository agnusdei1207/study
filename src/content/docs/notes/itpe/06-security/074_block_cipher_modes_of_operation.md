## 답안 골격
```text
[블록 암호 운용 모드] ◀━━ 머리: Ⅶ 내 의견 (단순 기밀성 운용 모드 탈피 → 무결성 인증 결합 및 병렬 처리가 가능한 AES-GCM(AEAD) 의무화)
 ┃
 ┣━ Ⅰ 개요 ───── 고정 크기(128비트)의 블록 암호 알고리즘을 반복 사용하여 가변 길이의 긴 평문을 안전하게 암호화하기 위한 표준 절차(NIST SP 800-38A)
 ┣━ Ⅱ 특징 ───── 모드별 오류 전파 특성 · 초기화 벡터(IV) 활용 · 병렬 처리 가능 여부 · 스트림 암호화 변환 지원
 ┣━ Ⅲ 구조 ───── 전통 5대 모드(ECB, CBC, CFB, OFB, CTR) + 현대 인증 결합 모드(AEAD: GCM, CCM)
 ┣━ Ⅳ 흐름 ───── ① 평문 패딩(PKCS#7) 및 IV 생성 → ② 모드별 피드백/카운터 연산 수행 → ③ 블록 암호화 엔진 통과 → ④ 암호문 블록 연쇄 결합
 ┣━ Ⅴ 비교 ───── ECB(패턴 노출, 절대 금지) vs CBC(IV 필요, 직렬 처리, 패딩 오라클 취약) vs CTR(난수 카운터, 병렬 처리) vs GCM(CTR + GMAC, 고속 인증 암호화)
 ┗━ Ⅵ 실무 ───── IV 재사용 시 기밀성 붕괴 / 패딩 오라클 공격(POODLE) / 대용량 데이터 전송 시 CTR/GCM의 멀티코어 병렬 성능 가속
```
- 필수 키워드: 블록 암호 운용 모드 · ECB · CBC · CFB · OFB · CTR · GCM(AEAD) · 초기화 벡터(IV) · 오류 전파
- 기출: KPC 127회 `블록 암호 운용 모드(ECB, CBC, CFB, OFB, CTR)의 특징과 장단점 비교 및 최신 동향` → Ⅰ~Ⅴ 전반

## 한 줄 본질
- 1블록(16바이트)만 처리하는 블록 암호 알고리즘의 길이적 한계 병목 → 블록들을 이전 결과와 체이닝(CBC)하거나 카운터(CTR)로 키스트림화하여 가변 데이터를 처리 → 임의 길이 암호화 달성 / 잘못된 모드(ECB) 선택 시 평문 패턴 노출 및 무결성 검증 부재 위험 발생

## 핵심 그림
```text
[블록 암호 대표 운용 모드 아키텍처 비교]

 1. ECB (Electronic Codebook) - 패턴 노출! (사용 금지)
    평문1 ──[AES]──> 암호문1  (동일한 평문 블록은 항상 동일한 암호문 생성!)

 2. CBC (Cipher Block Chaining) - 직렬 암호화 (IV 필수)
    평문1 ──(XOR)──[AES]──> 암호문1 ──┐ (암호문1이 다음 블록의 입력으로 전파)
              ▲                        │
             IV                        ▼
    평문2 ──────────────────(XOR)──[AES]──> 암호문2

 3. CTR (Counter) - 병렬 처리 고속 모드 (스트림 암호화)
    Nonce | 1 ──[AES]──> KeyStream1 ──(XOR)── 평문1 ──> 암호문1 (병렬 연산 가능!)
    Nonce | 2 ──[AES]──> KeyStream2 ──(XOR)── 평문2 ──> 암호문2

 4. GCM (Galois/Counter Mode) - CTR 암호화 + 갈루아 필드 MAC (AEAD 표준)
```

## 핵심 용어
- 초기화 벡터(IV, Initialization Vector): 첫 번째 블록을 암호화할 때 동일한 평문이라도 매번 다른 암호문이 생성되도록 주입하는 무작위 난수 블록
- AEAD(Authenticated Encryption with Associated Data): 암호화(기밀성)와 메시지 인증 코드(무결성/인증)를 하나의 알고리즘 모드에서 동시에 산출하는 운용 모드 (GCM)

## 핵심 통찰
- ECB 모드는 암호학의 재앙임 → 리눅스 펭귄(Tux) 이미지를 ECB로 암호화하면 픽셀 색상은 바뀌지만 펭귄의 윤곽선 형태가 그대로 드러남(패턴 보존)
- CBC 모드는 20년간 인터넷의 표준이었으나 '패딩 오라클(Padding Oracle)' 취약점 때문에 퇴출됨 → 수신자가 패딩 에러를 반환하는 시간차를 이용해 공격자가 평문을 한 바이트씩 알아낼 수 있음
- 오늘날의 정답은 단 하나, 'AES-GCM'임 → CTR 모드의 고속 병렬 연산 장점과 GHASH 기반 무결성 인증 태그를 결합하여 기밀성과 변조 방지를 완벽히 보장함

## 이웃 토픽과 구분
- 블록 암호 알고리즘 vs 운용 모드: 블록 암호 알고리즘(AES, ARIA) = 1개 블록을 뒤섞는 엔진 / 운용 모드(CBC, GCM) = 그 엔진을 이용해 긴 책 한 권을 암호화하는 도로 규칙

## 문제·원인·대책
- 사례: 웹 애플리케이션에서 CBC 모드를 사용하다가 패딩 에러 메시지를 노출하여 암호화된 세션 토큰이 복호화된 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 패딩 검증 실패 응답을 악용한 패딩 오라클 공격 | PKCS#7 패딩 처리 오류 메시지를 클라이언트에 그대로 노출 | 패딩이 필요 없는 CTR 기반 AEAD(AES-GCM) 모드로 전면 교체 | 패딩 연산 자체를 제거하여 오라클 공격 원천 차단 |
| 대용량 파일 암호화 시 극심한 CPU 병목 | CBC 모드의 직렬 체이닝 구조로 멀티코어 병렬 처리 불가 | CTR 또는 GCM 모드 적용(블록 간 독립 연산 지원) | 멀티코어 CPU 및 GPU 병렬 가속으로 처리 속도 수배 향상 |

## 이렇게 출제된다
- 제127회 기출: "블록 암호 운용 모드 5가지(ECB, CBC, CFB, OFB, CTR)의 특징과 장단점을 비교하고, 최근 널리 활용되는 AEAD 모드에 대하여 설명하시오." → 요구 포인트: Ⅰ 운용 모드 필요성 + Ⅲ 5대 모드 동작 도식 및 비교표 + Ⅵ GCM(AEAD) 최신 트렌드

## 내 의견
- [단순 AES 사용 표시의 함정] 보안 규정에 "AES 암호화 적용"이라고만 적어두고 실제 소스코드를 보면 기본값인 `AES/ECB/PKCS5Padding`을 그대로 사용하여 심각한 패턴 노출을 방치하는 프로젝트 다수 → 나라면: 사내 시큐어 코딩 정적 분석 룰에 ECB 모드 선언을 치명적 오류(Blocker)로 지정하고, 암호화 유틸리티 라이브러리를 `AES-256-GCM` 단일 표준으로 래핑하여 강제 배포
