## 연관 키워드

- 블록 암호 운용 모드(Block Cipher Mode of Operation), 블록 암호(Block Cipher), AES(Advanced Encryption Standard)
- ECB, CBC, CFB, OFB, CTR, GCM, AEAD(Authenticated Encryption with Associated Data)
- 초기화 벡터(IV, Initialization Vector), Nonce, GHASH, 패딩 오라클(Padding Oracle), 키 갱신(Rekeying)

## Ⅰ. 블록 암호 운용 모드의 개요

- 핵심 요약 : 고정 길이 블록 암호를 임의 길이 데이터에 적용하는 표준 절차로, 패턴 은닉·병렬성·무결성 요구에 따라 모드를 고르는 규격.
- 개념 : 고정 크기 블록(AES는 128비트)만 처리하는 **블록 암호** (Block Cipher)를 연속 적용해 임의 길이 데이터를 암호화하는 절차 규격을 **블록 암호 운용 모드** (Block Cipher Mode of Operation)라 함.
- 배경 및 필요성 : 블록 암호는 한 블록의 입력이 같으면 출력도 같으므로, 블록을 어떻게 연결할지 정하지 않으면 평문의 반복 패턴이 암호문에 그대로 드러남.
- 주요 목적 : 평문 패턴 은닉, 오류 전파 범위 통제, 병렬 처리 성능 확보, 기밀성과 무결성의 동시 달성 (**AEAD** (Authenticated Encryption with Associated Data), 인증 암호화).

## Ⅱ. 블록 암호 운용 모드의 특징 및 장점

- 핵심 요약 : 블록을 체인으로 묶을지, 카운터로 독립 처리할지, 인증 태그를 붙일지에 따라 모드별 장단점이 갈리는 설계 공간.

1. **CBC** (Cipher Block Chaining) : 이전 암호문을 다음 평문 블록과 XOR한 뒤 암호화 → 같은 평문도 매번 다른 암호문이 되어 패턴 은닉.
2. **CTR** (Counter Mode) : Nonce와 카운터를 암호화한 키스트림을 평문과 XOR → 블록이 서로 독립이라 병렬 처리와 임의 접근이 가능.
3. **GCM** (Galois/Counter Mode) : CTR 암호화에 **GHASH** 기반 인증 태그를 결합 → 기밀성과 변조 탐지를 한 번에 제공.

## Ⅲ. 블록 암호 운용 모드의 구조 (흐름)

- 핵심 요약 : 블록 연결이 직렬 체인이냐 독립 키스트림이냐에 따라 병렬성과 오류 전파가 갈리는 두 흐름.
- 표기 : `E_K`는 키 K를 이용한 블록 암호 연산, `⊕`는 배타적 논리합(XOR), `IV`는 초기화 벡터.

```text
[ CBC 직렬 체인 ]

P1 ⊕ IV → E_K → C1
               ↓
P2 ⊕ C1 → E_K → C2
               ↓
P3 ⊕ C2 → E_K → C3
```

```text
[ GCM 병렬 처리 ]

Nonce+카운터 1 → E_K → ⊕ P1 → C1
Nonce+카운터 2 → E_K → ⊕ P2 → C2
                            ↓
C1·C2·AAD → GHASH → 인증 태그
```

## Ⅳ. 블록 암호 운용 모드의 비교

- 핵심 요약 : 기밀성만 필요한 환경과 무결성까지 필요한 환경에서 권장 모드가 달라지며, 현재 표준은 AEAD인 GCM.

| 모드 | 기밀성 원리 | 암호화 병렬화 | 복호화 병렬화 | 패딩 | 무결성 | 실무 판단 |
| --- | --- | --- | --- | --- | --- | --- |
| ECB (Electronic Codebook) | 블록별 독립 암호화 | 가능 | 가능 | 필요 | 없음 | 사용 금지 (패턴 노출) |
| CBC | 이전 암호문 피드백 XOR | 불가 (직렬) | 가능 | 필요 | 없음 | 레거시 연동 한정 |
| CFB (Cipher Feedback) | 암호문 피드백 스트림화 | 불가 | 가능 | 불필요 | 없음 | 스트림 성격 환경 |
| OFB (Output Feedback) | 키스트림 피드백 | 불가 | 불가 | 불필요 | 없음 | 오류 전파 방지 환경 |
| CTR | 카운터 키스트림 XOR | 가능 | 가능 | 불필요 | 없음 | 고속 처리, 인증 별도 결합 |
| GCM | CTR 암호화 + GHASH 태그 | 가능 | 가능 | 불필요 | 제공 (AEAD) | 현행 표준 우선 권장 |

- 선택 흐름 : 무결성 인증이 필요한지 먼저 판단 → 필요하면 GCM 같은 AEAD를 선택하고, 레거시 연동으로 불가피하면 CBC나 CTR에 별도 MAC을 결합하는 순서로 정함.
- 참고 : TLS(Transport Layer Security) 1.3은 AEAD 암호만 허용하므로 GCM이 사실상 기본 선택지가 됨.

## Ⅴ. 블록 암호 운용 모드의 한계와 방안

- 핵심 요약 : 패턴 노출, 패딩 오라클, Nonce 재사용을 모드 금지, AEAD 교체, Nonce 관리와 키 교체로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| ECB 패턴 노출 | 같은 평문 블록이 같은 암호문을 만들어 원본 윤곽이 드러남 | ECB 사용 금지 정책 적용, 난수 IV를 쓰는 CBC나 GCM으로 전환 | ECB 사용 탐지 건수 |
| **패딩 오라클** (Padding Oracle) | CBC 복호화 시 패딩 오류 응답의 차이로 평문 일부가 복원됨 | GCM 같은 AEAD로 교체하고, 태그 검증 실패 시 복호화 결과를 폐기 | 레거시 CBC 잔존 건수 |
| Nonce 재사용 | CTR·GCM에서 같은 키와 Nonce가 반복되면 키스트림이 노출되고 GCM의 GHASH 키가 탈취될 수 있음 | 카운터 기반 Nonce 관리, 사용량 임계치 도달 시 **키 갱신** (Rekeying) | Nonce 중복 발생 건수, 키 교체 주기 |

## Ⅵ. 블록 암호 운용 모드에 대한 기술사적 제언

- 핵심 요약 : 암호 표준 체계가 AEAD만 허용하는 프로파일로 정리되고, 키와 Nonce 관리가 시스템 설계에 내장될 때 모드 선택 문제가 실효성을 가짐.

1. 정책 : 암호 정책 기구가 AEAD 전용 프로파일을 조직 표준으로 채택하고, 레거시 모드의 사용 기한과 전환 계획을 정함.
2. 키 관리 : 정보보호 조직이 Nonce 생성과 키 교체를 키 관리 시스템(KMS)의 기능으로 내장해, 개발자가 Nonce를 직접 관리하지 않도록 함.
3. 구현 : 개발 조직이 검증된 암호 라이브러리만 사용하고 모드 로직을 직접 구현하지 않는 개발 기준을 두어 구현상의 오류를 예방함.

## Ⅶ. 결론

- 핵심 요약 : 블록 암호 운용 모드는 블록 연결 방식이 기밀성·병렬성·무결성의 조합을 결정하는 설계 규격.
- 시사점 : 현행 권장 모드인 GCM은 무결성까지 제공하지만 Nonce 관리 책임이 따르므로, 모드 선택과 키 운영을 함께 설계해야 실효성이 확보됨.
