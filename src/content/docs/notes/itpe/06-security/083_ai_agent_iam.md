## 답안 골격
```text
[AI 에이전트 IAM] ◀━━ 머리: Ⅶ 내 의견 (비인간 신원 통제 완성 → 세분화된 단기 토큰 위임(OAuth Scope) 및 동적 행위 기반 권한 박탈 체계 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 자율적으로 도구(Tool)를 호출하고 외부 시스템과 통신하는 AI 에이전트에게 고유 신원을 부여하고, 최소 권한 원칙으로 접근을 통제하는 식별·인증·인가 관리 체계
 ┣━ Ⅱ 특징 ───── 비인간 신원(NHI) 특화 · 대리인 권한 위임(User Delegation) · 동적 상황 기반 인가(ABAC/PBAC) · 일회용 단기 자격증명(Ephemeral Credential)
 ┣━ Ⅲ 구조 ───── 신원 제공자(IdP) + 권한 위임 브로커(OAuth 2.0 Token Broker) + 정책 결정 포인트(PDP) + 정책 집행 포인트(PEP) + 활동 감사 로그
 ┣━ Ⅳ 흐름 ───── 사용자 요청 → AI 에이전트 신원 인증 → 최소 권한 범위(Scope) 산정 → 단기 토큰 발급 → 도구/API 호출 시 토큰 검증 → 세션 종료 시 즉시 폐기
 ┣━ Ⅴ 비교 ───── AI 에이전트 IAM(동적 컨텍스트 인가, 세밀한 도구 단위 제어, 프롬프트 오염 대비) vs 전통적 인간 IAM(정적 RBAC, 패스워드/MFA, 인간 세션 관리)
 ┗━ Ⅵ 실무 ───── 고정된 API Key 하드코딩 금지 / 권한 상승(Privilege Escalation) 공격 방지 / 에이전트 간 연쇄 호출(Chaining) 시 신뢰 사슬 단절 방어
```
- 필수 키워드: AI 에이전트 IAM · 비인간 신원(NHI) · 대리인 위임(User Delegation) · 단기 자격증명(Ephemeral Token) · 세분화된 스코프(Fine-grained Scope) · 제로트러스트
- 배점 전략: 10점 = Ⅰ AI 에이전트 자격증명의 위험성 및 IAM 필요성 → Ⅲ 아키텍처 및 권한 위임 흐름 도식 → Ⅴ 인간 IAM 대비 차이점 / 25점 = Ⅰ~Ⅶ 전개, OAuth 2.0 Token Exchange(RFC 8693) 기반 위임 구조 및 컨지(Confused Deputy) 문제 방어 메커니즘 집중
- 기출: 미출제. 에이전틱 AI 보안 및 비인간 신원 관리 핵심 트렌드로 유력 예상

## 한 줄 본질
- AI 에이전트에게 광범위한 마스터 관리자 키를 부여하여 프롬프트 인젝션 시 백엔드 시스템 전체가 장악되는 권한 과잉 병목 → 에이전트마다 고유 신원을 부여하고 실행 단위별로 극소 범위의 단기 토큰을 동적으로 위임 → 시스템 오남용 및 권한 탈취 차단 / 복잡한 토큰 교환 오버헤드 발생

## 핵심 그림
```text
[AI 에이전트 IAM의 동적 권한 위임 및 접근 통제 아키텍처]

   [사용자 (User)]
          │ (작업 요청: "DB에서 지난달 매출 통계 조회해줘")
          ▼
   ┌────────────────────────────────────────────────────────┐
   │                  AI 에이전트 (신원: Agent-A)             │
   │  - 정적 마스터 키 없음 (No Static Secrets)              │
   └──────────────────────────┬─────────────────────────────┘
                              │ 1. 권한 요청 (작업에 필요한 최소 범위만)
                              ▼
   ┌────────────────────────────────────────────────────────┐
   │             AI IAM 브로커 (IdP & PDP: OAuth 2.0)         │
   │  - 사용자 권한 검증 + 정책(Policy) 평가                 │
   │  - 5분 유효 단기 토큰(Token Exchange) 발급              │
   └──────────────────────────┬─────────────────────────────┘
                              │ 2. 임시 토큰 전달 (Scope: `db:sales:read`)
                              ▼
   ┌────────────────────────────────────────────────────────┐
   │              백엔드 자원 (PEP / 데이터베이스)            │
   │  - 토큰 내 권한(`db:sales:read`)만 허용                 │
   │  - 쓰기(`db:sales:write`)나 삭제 요청 인입 시 즉각 거부! │
   └────────────────────────────────────────────────────────┘
```

## 핵심 용어
- 컨퓨즈드 데퓨티(Confused Deputy): 높은 권한을 가진 에이전트가 악의적인 저권한 사용자의 간접 프롬프트 명령에 속아, 자신이 가진 권한을 남용하여 피해 시스템의 기밀 데이터를 대신 빼돌리는 보안 취약점
- 임시 자격증명(Ephemeral Credential): 디스크나 설정 파일에 저장되지 않고, 메모리상에서 1회성 또는 수 분 이내로만 유효하게 동작하고 자동 만료되는 단기 보안 토큰

## 핵심 통찰
- 실무에서 가장 흔한 치명적 실수는 "AI 에이전트에게 회사 AWS 관리자 키나 슈퍼유저 DB 접속 정보를 통째로 주는 것"임 → 공격자가 프롬프트 인젝션 한 번으로 회사 인프라 전체를 삭제할 수 있음
- AI 에이전트는 사용자를 대신해 행동하므로 '사용자가 가진 권한보다 더 많은 권한'을 가져서는 절대 안 됨 → 사용자 권한과 에이전트 권한의 교집합(Intersection)만을 허용하는 토큰 스코프 다운스코핑(Downscoping)이 필수임
- 에이전트가 다른 하위 에이전트를 호출하는 다단계 체인(Multi-Agent System)에서는 호출 단계마다 신원과 의도가 기록되어야 감사(Audit)가 성립함

## 이웃 토픽과 구분
- AI 에이전트 IAM vs 서비스 계정 관리: 서비스 계정 = 특정 서버 간 정형화된 배치를 위한 정적 계정 / AI 에이전트 IAM = 사용자의 예측 불가능한 자연어 요청에 따라 동적으로 권한 범위를 조절하는 적응형 신원 관리

## 문제·원인·대책
- 사례: 사내 지식검색 AI 챗봇이 악성 이메일을 읽은 뒤 간접 프롬프트 인젝션에 감염되어, 챗봇에 부여된 전사 이메일 발송 API 권한을 악용해 피싱 메일을 전 직원에게 발송한 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| AI 에이전트의 권한 남용을 통한 전사 피싱 메일 무단 발송 | 에이전트에 불필요하게 넓은 쓰기/발송 권한을 상시 부여(과잉 권한) | AI IAM 기반 실행 시점 도구별 승인 및 읽기 전용 Scope 제한 | 비인가 메일 발송 API 호출 차단 및 악용 영향도 최소화 |
| 소스코드 및 GitHub 저장소에 AI 에이전트 연동용 API Key 유출 | 개발 편의를 위해 소스코드 내 장기 유효 API Key 하드코딩 | OIDC(OpenID Connect) 기반 임시 토큰 교환 및 Vault 연동 | 키 하드코딩 제거 및 탈취된 토큰의 즉시 자동 만료 |

## 이렇게 출제된다
- 미출제. 예상: "에이전틱 AI(Agentic AI) 확산에 따른 비인간 신원(NHI)의 보안 위험과 AI 에이전트 전용 IAM(Identity and Access Management)의 권한 위임 및 최소 권한 통제 아키텍처를 설명하시오." → 요구 포인트: Ⅰ 비인간 신원 위협 + Ⅲ OAuth Token Exchange 기반 IAM 아키텍처 + Ⅵ 최소 권한 및 Confused Deputy 방어

## 내 의견
- [도구(Tool) 단위의 마이크로 인가 정책 필수화] AI 에이전트에게 포괄적인 '데이터베이스 접근 권한'을 부여하는 관행을 금지해야 함 → 나라면: MCP(Model Context Protocol) 및 API 게이트웨이 전면에 AI IAM 프록시를 배치하여, AI가 호출하려는 개별 함수(Function/Tool)마다 호출 파라미터가 안전한지 검사하고 사용자 본인 확인(Step-up Auth)을 거친 후에만 실행을 허가하는 Zero Trust Tool Gateway 체계를 구축

## 찾아볼 것
- RFC 8693(OAuth 2.0 Token Exchange)을 활용한 AI 에이전트 신원 위임 표준 구현 방식
