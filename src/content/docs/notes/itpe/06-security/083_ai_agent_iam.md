신원·접근 관리 → 비인간 신원 → AI 에이전트 권한 위임

## 30초 인출

- 본질: AI 에이전트 IAM은 사용자·에이전트·도구의 신원과 위임 범위를 구분해 접근을 통제하는 체계
- 메커니즘: 원 사용자 요청 확인 → 작업별 토큰 발급 → 도구의 대상·범위 검증 → 고영향 호출 승인·감사
- 통찰: 한계: 장기 마스터 키나 원 사용자 정보가 빠진 위임은 권한 오용을 키움 → 방안: 작업별 짧은 권한을 발급하고 도구 호출마다 사용자·에이전트를 추적

> AI 에이전트가 사용자를 대신해 도구를 호출할 때의 신원·권한 위임 구조와 위험을 설명하시오. (예상·25점)

---

## 2~4교시 25점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | AI 에이전트 IAM은 사용자·에이전트·도구 신원과 위임된 권한을 구분해 인증·인가·감사하는 체계 |
| 목적 | 대리 실행의 권한 남용 감소와 호출 책임 추적 |

- 사용자, 에이전트 실행 인스턴스, 도구 서버의 신원을 분리하고 작업 목적·승인 범위 기록.
### Ⅱ. 권한 흐름

```text
사용자 ─요청·승인 범위─> 에이전트
                           │ 신원·정책 평가
                           ↓
                  자원·시간 제한 토큰
                           │
                           ↓
                    도구의 권한 검증·감사
```
- 사용자 요청 → 에이전트 인증 → 정책 평가 → 자원·범위가 제한된 토큰 발급 → 도구 측 검증·감사.
### Ⅲ. 위험

| 권한 경로 | 위험 | 확인 대상 |
|---|---|---|
| 사용자→에이전트 | 원 사용자 정보 누락 | 위임 대상·만료·동의 |
| 에이전트→도구 | 프롬프트에 의한 권한 승격 | 도구별 인가·인수 검증 |
| 다단계 위임 | 장기 토큰 재사용 | 호출 주체·범위·철회 기록 |
- 장기 마스터 키 노출, 간접 프롬프트 인젝션의 권한 악용, 다단계 위임 과정의 원 사용자 정보 손실.
#### 통제
- RFC 8693 기반 토큰 교환은 가능한 설계 수단이며 자동 표준 구현은 아님. 승인·만료·대상 제한·철회와 도구 파라미터 검증을 구현별 시험.

### Ⅳ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 장기 권한 위임은 원 사용자와 실행 주체의 책임 추적을 흐림 | 작업별 짧은 권한을 발급하고 호출마다 사용자·에이전트를 기록 |

### Ⅴ. 제언

도구 호출마다 원 사용자와 에이전트 신원을 추적하고 자원·동작·시간이 제한된 권한만 발급한다.

## 출제 이력과 검증 출처

- 위 10·25점 문항은 예상문제다. 이 절의 자료는 개념·사건 사실의 근거이며 해당 문항의 기출 이력을 뜻하지 않는다.

- [RFC 8693, OAuth 2.0 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693): 대리 수행과 토큰 교환의 구분
- [OWASP LLM06 과도한 대행](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/): 에이전트 도구 권한 남용 사례와 완화
