## 지식 로드맵 내 현재 위치

AI 보안 → 기업 및 개발 업무의 LLM 도입 → 데이터·지시·코드 전주기 보안 위험

## 30초 인출

- **본질:** 기업 업무 및 소프트웨어 개발 수명주기(SDLC)에 LLM을 적용할 때 발생하는 프롬프트 데이터 유출, 간접 프롬프트 인젝션, AI 생성 취약 코드 삽입, 패키지 환각(Package Hallucination) 위협에 대응하는 보안 거버넌스.
- **메커니즘:** 입력 데이터 분류 및 엔터프라이즈 DLP 차단 → 인라인 가드레일 프록시 기반 지시어 검증 → 생성 코드 대상 SAST/SCA 정밀 분석 및 샌드박스 격리 테스트.
- 통찰: 임직원의 무분별한 섀도 AI(Shadow AI) 사용을 차단하고 데이터 재학습 방지(Zero Data Retention) 계약 및 DevSecOps 파이프라인 내 AI 코드 검증 내재화 필수.

<details><summary>핵심 용어</summary>

- **섀도 AI(Shadow AI)**: 사내 보안 승인을 받지 않은 외부 퍼블릭 생성형 AI 서비스에 임직원이 업무 데이터나 소스코드를 무단 입력하여 사용하는 행위.
- **패키지 환각(Package Hallucination / Slopsquatting)**: LLM이 존재하지 않는 오픈소스 라이브러리 이름을 추천하고, 공격자가 이를 선점하여 악성코드를 배포하는 공격 기법.
- **간접 프롬프트 인젝션(Indirect Prompt Injection)**: RAG 검색 문서나 웹페이지 등에 악의적 명령어를 은닉하여 LLM이 사용자 명령 대신 공격자 지시를 실행하도록 유도하는 기법.
- **ZDR(Zero Data Retention)**: 기업이 전송한 프롬프트 및 완성 데이터가 AI 벤더의 모델 재학습이나 로그 저장에 활용되지 않도록 보장하는 엔터프라이즈 계약 조건.
- **AI-SAST/SCA**: LLM이 생성한 소스코드의 CWE 취약점과 라이선스 위반, 악성 의존성을 검증하기 위한 정적 보안 분석 도구.
</details>

## 2~4교시 예상문제 (25점)

> 기업 및 소프트웨어 개발 환경에서 거대언어모델(LLM)을 도입할 때 발생하는 주요 보안 위험(데이터 유출, 프롬프트 인젝션, AI 생성 코드 취약성, 패키지 환각)을 분석하고, 안전한 활용을 위한 엔지니어링 아키텍처 및 DevSecOps 대응 방안을 제시하시오. (기출·제136회 2교시 3번)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 기업 비즈니스 및 SW 개발 수명주기 전반에 LLM을 도입할 때 발생하는 데이터 유출, 적대적 프롬프트, 취약 코드 주입 위험을 식별하고 전주기 통제를 적용하는 보안 활동 |
| 목적 | 생성형 AI 기반 개발 생산성 및 비즈니스 혁신을 극대화하면서도 사내 핵심 지적재산권(IP) 보호, 안전한 코드 품질 확보, 시스템 무결성 유지 |

## Ⅱ. LLM 도입 시 발생하는 핵심 보안 위험의 특징

| 특징 | 세부 위험 양상 | 기술적 및 비즈니스 피해 |
|---|---|---|
| 데이터 외부 전송 | 임직원의 소스코드, 고객 개인정보, 핵심 전략 프롬프트 입력 | 외부 AI 벤더 서버 저장 및 차세대 모델 학습 데이터로 누출 |
| 비신뢰 지시 실행 | RAG 검색 대상 외부 웹/문서에 은닉된 악성 프롬프트 실행 | 내부 DB 무단 조회, 악성 URL 호출, 민감 데이터 외부 반출 |
| 취약 코드의 자동 전파 | 최신 보안 패치가 미반영된 레거시 코드를 학습한 LLM의 취약점 추천 | SQL Injection, 메모리 오버플로우 등 CWE 상위 취약점 유입 |
| 가상 패키지 신뢰 | 존재하지 않는 의존성 패키지를 LLM이 환각하여 개발자에게 안내 | 공격자가 선점한 동명 악성 패키지(Slopsquatting) 자동 설치 |
| 에이전트 과도한 권한 | CI/CD 배포 및 인프라 수정 권한을 가진 에이전트의 오작동 | 운영 인프라 설정 파괴, 비인가 컨테이너 배포 사고 발생 |

## Ⅲ. 기업 LLM 도입 보안 아키텍처 및 라이프사이클 통제

```text
[ 사내 사용자 / 개발자 ]
       │ 1. 프롬프트 질의 및 소스코드 입력
       ▼
+---------------------------------------------------------------------------------+
| 엔터프라이즈 AI 보안 게이트웨이 (AI Gateway / In-line Guardrails)                 |
|  ├── [DLP 엔진]: 개인정보(주민번호/이메일), 소스코드, API 시크릿 탐지 및 마스킹|
|  ├── [프롬프트 가드]: 탈옥(Jailbreak), 시스템 프롬프트 유출 시도 차단          |
|  └── [접근 통제]: 임직원 직무별 모델 접근 권한 인가 (ABAC/RBAC)                 |
+---------------------------------------------------------------------------------+
       │ 2. 정제된 프롬프트 전송 (ZDR 계약 적용 채널)
       ▼
[ 프라이빗 LLM / 전용 클라우드 인스턴스 ]
       │ 3. 추론 결과 생성 (코드, 텍스트 답변)
       ▼
+---------------------------------------------------------------------------------+
| 출력 필터링 및 DevSecOps 파이프라인 (Output Validation & CI/CD Pipeline)         |
|  ├── [출력 검증]: 기밀 데이터 재유출 탐지 및 유해 콘텐츠 필터링                 |
|  ├── [AI-SAST/DAST]: 생성된 코드의 CWE 취약점 및 시큐어 코딩 규칙 정적 검사     |
|  └── [SCA 의존성 검사]: 생성된 라이브러리 실존 여부 및 악성 패키지 해시 대조    |
+---------------------------------------------------------------------------------+
       │ 4. 검증 통과한 안전 코드만 병합
       ▼
[ 전사 프로덕션 코드베이스 / 저장소 ]
```

| 도입 단계 | 통제 대상 | 핵심 엔지니어링 구현 솔루션 |
|---|---|---|
| 입력 (Ingress) | 프롬프트 텍스트, 첨부 파일 | 데이터 마스킹(Presidio), 시크릿 스캐너, Regex DLP, 프롬프트 인젝션 필터 |
| 처리 (Processing) | LLM 모델 및 연동 인프라 | 프라이빗 VPC 호스팅, ZDR(학습 배제) 계약, TLS 1.3 암호화 통신 |
| 연계 (RAG/Tool) | 검색 문서, 외부 API 호출 | 문서 출처 격리(Sandboxed Context), 최소 권한 API 토큰, 파라미터 유효성 검사 |
| 출력 (Egress) | 생성 텍스트, 추천 소스코드 | SonarQube(SAST), Snyk(SCA), Bandit, 패키지 레지스트리 화이트리스팅 |

## Ⅳ. LLM 도입 4대 핵심 위협 유형 비교

| 위협 유형 | 발생 메커니즘 | 공격 매개체 | 주요 엔지니어링 방어 대책 |
|---|---|---|---|
| 민감정보 유출 | 프롬프트 입력창을 통한 사내 기밀 및 소스코드 전송 | 웹 브라우저, IDE 플러그인 | CASB, 엔터프라이즈 AI 게이트웨이, 데이터 토큰화 |
| 간접 프롬프트 인젝션 | 비신뢰 외부 웹페이지/이메일 내용이 RAG 지식으로 유입 | 검색된 컨텍스트 데이터 | 입력 데이터와 시스템 프롬프트 엄격 분리, XML 태그 격리 |
| 취약 코드 생성 | 오래된 오픈소스 취약 코드를 학습한 모델의 결함 코드 제안 | 코드 자동완성(Copilot 등) | CI/CD 파이프라인 내 정적 분석(SAST) 및 자동 단위 테스트 강제 |
| 패키지 환각 (Slopsquatting) | LLM의 통계적 단어 예측 오류로 가상 라이브러리 명칭 생성 | 생성된 requirements.txt/package.json | 사내 프라이빗 패키지 미러(Nexus/Artifactory) 강제 프록시 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 자연어 기반 프롬프트 인젝션은 공격 구문이 무한 변형되어 정규식 기반 탐지 룰로 완전 차단 불가 | 시스템 지시문과 외부 데이터 영역을 구조화된 구분자(`<user_data>...</user_data>`)로 완전 격리하고 이중 판별용 경량 가드레일 LLM을 병렬 배치 |
| LLM이 생성한 코드가 정적 분석기(SAST)를 우회하는 논리적 결함(Logic Bug)이나 레이스 컨디션을 유발 | 자동화된 동적 분석(DAST) 및 퍼징(Fuzzing) 테스트를 CI 단계에 통합하고, 개발자 최종 코드 리뷰(Peer Review) 통과 의무화 정책 강제 |
| LLM이 추천한 가상 패키지 이름을 공격자가 실제 npm/PyPI에 등록하여 침투하는 공급망 공격 발생 | 내부 패키지 관리자 설정에서 퍼블릭 레지스트리 직접 다운로드를 금지하고, 사전 검증된 사내 아티팩토리(Artifactory) 프록시만 접근 허용 |
| 엔터프라이즈 계약(ZDR)을 체결했음에도 불구하고 외부 클라우드 SaaS AI 사용에 따른 컴플라이언스 감사 불투명성 | 사내 프라이빗 클라우드(VPC) 내에 오픈소스 가중치 모델(Llama, Mistral 등)을 자체 서빙하는 온프레미스 AI 인프라 구축 |

## Ⅵ. 제언

```text
[ 기업형 LLM 도입 안전 거버넌스 3단계 체계 ]

  [ 1단계: 섀도 AI 양성화 ]           [ 2단계: 시큐어 AI 게이트웨이 ]       [ 3단계: 전주기 DevSecOps 연동 ]
+----------------------------+     +-------------------------------+     +-------------------------------+
| • 사내 AI 사용 가이드라인  | ──> | • DLP 및 인라인 가드레일 프록시| ──> | • AI 코드 전용 SAST/SCA 검증 |
| • 엔터프라이즈 ZDR 라이선스 |     | • 직무별 접근 통제 및 감사로그|     | • 프라이빗 패키지 레지스트리  |
+----------------------------+     +-------------------------------+     +-------------------------------+
```

| 거버넌스 축 | 세부 실행 과제 | 기대 효과 |
|---|---|---|
| 정책 및 제도 | 생성형 AI 사용 가이드라인 배포 및 데이터 입력 허용 등급(공개/대외비/극비) 규정 | 법적 데이터 침해 위험 및 개인정보보호법 위반 사전 예방 |
| 인프라 보안 | 전사 공통 AI Gateway 단일 창구화 및 중앙 집중 로깅/모니터링 구축 | 무단 섀도 AI 사용 100% 억제 및 프롬프트 감사 추적성 확보 |
| 개발 프로세스 | 개발자 IDE 및 CI/CD 빌드 파이프라인에 AI 생성 코드 자동 검증 툴킷 연동 | 안전한 고품질 소프트웨어 신속 출시 및 공급망 무결성 보장 |
