## 연관 키워드

- LLM 도입 보안, 섀도 AI(Shadow AI), 간접 프롬프트 인젝션, 패키지 환각(Slopsquatting)
- AI 게이트웨이, DLP(Data Loss Prevention), SAST, DAST, SCA(Software Composition Analysis)
- 환각(Hallucination), 프라이빗 LLM, 데이터 보존 배제 계약(ZDR), 최소 권한

## Ⅰ. LLM 도입 보안 위험·대응의 개요

- 핵심 요약 : 기업이 LLM을 업무와 개발 전반에 들일 때 생기는 데이터 유출, 적대적 입력, 취약 코드 위험을 전 주기에서 통제하는 활동.
- 개념 : 기업 업무와 소프트웨어 개발 수명주기에 **LLM**(Large Language Model)을 도입할 때 발생하는 데이터 유출, 적대적 프롬프트, 취약 코드 주입 위험을 식별하고 통제하는 보안 활동.
- 배경 및 필요성 : 생성형 AI 도입이 빨라지면서 사내 기밀과 소스코드가 외부로 나가거나, 승인되지 않은 **섀도 AI** (Shadow AI) 사용이 늘고, 환각에 따른 업무 오류가 생겨 엔터프라이즈 통제 기준이 시급해짐.
- 주요 목적 : 생산성과 혁신 효과를 유지하면서 지적재산권 보호, 코드 품질 확보, 시스템 무결성 유지.

## Ⅱ. LLM 도입 보안 위험·대응의 특징 및 장점

- 핵심 요약 : 입력, 처리, 출력의 세 지점에 통제를 두어 사용 편의를 해치지 않고 위험을 걸러내는 방식.

1. 입력 통제 : 프롬프트와 첨부 파일을 DLP와 시크릿 스캐너로 검사 → 개인정보와 소스코드의 외부 유출 차단.
2. 처리 통제 : 학습 배제 계약과 암호화 통신을 쓰는 전용 인스턴스 사용 → 외부 학습 재사용 위험 감소.
3. 출력 통제 : 생성 코드를 SAST, DAST, SCA로 검사 → 취약 코드와 존재하지 않는 패키지의 병합 방지.

## Ⅲ. LLM 도입 보안 위험·대응의 구조 (흐름)

- 핵심 요약 : 사용자 입력이 AI 게이트웨이에서 정제되고, 전용 모델의 결과가 출력 검증과 개발 파이프라인을 거쳐서만 코드베이스에 들어가는 흐름.
- **AI 게이트웨이** : 개인정보 탐지와 마스킹, 프롬프트 가드, 직무별 모델 접근 통제를 한곳에서 수행.
- 출력 검증 : 기밀 재유출과 유해 콘텐츠를 걸러내고 생성 코드를 정적·동적 분석.
- 연계 : RAG 문서와 외부 API 호출은 격리된 컨텍스트와 최소 권한 토큰으로 제한.

```text
[ 사내 사용자 · 개발자 ]
        ↓ 1. 프롬프트·소스코드 입력
[ AI 게이트웨이 ]
  DLP 마스킹 · 프롬프트 가드 · 접근 통제
        ↓ 2. 정제된 프롬프트 전송
[ 전용 LLM 인스턴스 ]
        ↓ 3. 결과 생성
[ 출력 검증 · 개발 파이프라인 ]
  기밀 재검사 · SAST · DAST · SCA
        ↓ 4. 검증 통과 코드만 병합
[ 프로덕션 코드베이스 ]
```

## Ⅳ. 외부 SaaS LLM과 프라이빗 LLM의 비교

- 핵심 요약 : 외부 서비스는 도입이 빠르지만 데이터 통제와 감사가 어렵고, 프라이빗 LLM은 통제가 쉬운 대신 운영 부담이 큼.

| 비교 축 | 외부 SaaS LLM | 프라이빗 LLM (전용 인스턴스) |
| --- | --- | --- |
| 데이터 경로 | 외부 서비스로 전송 | 사내 네트워크나 전용 VPC 내부에서 처리 |
| 통제 수단 | 계약 조항과 서비스 설정 | 네트워크 격리와 자체 로깅 |
| 감사 가능성 | 제공자 보고서에 의존 | 자체 감사 로그 확보 |
| 도입 속도 | 빠름 | 인프라 구축 기간 필요 |
| 운영 부담 | 낮음 | 모델 서빙과 보안 패치 부담 |

- 선택 기준 : 공개 가능한 업무는 SaaS를 쓰고, 기밀과 소스코드를 다루는 업무는 프라이빗 LLM으로 분리해 적용.

## Ⅴ. LLM 도입 보안 위험·대응의 한계와 방안

- 핵심 요약 : 정규식 탐지의 한계, 생성 코드의 논리 결함, 존재하지 않는 패키지 악용, 외부 SaaS의 감사 불투명성을 구조적 분리, 동적 분석, 사내 미러, 자체 서빙으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **간접 프롬프트 인젝션** (Indirect Prompt Injection) | 외부 웹·메일 내용이 RAG로 유입되어 지시문으로 작동 | 시스템 지시문과 외부 데이터를 구조적 구분자로 격리하고 이중 판별용 가드레일 모델 병행 | 인젝션 탐지 건수 |
| 생성 코드의 논리 결함 | 정적 분석을 우회하는 논리 오류와 레이스 컨디션 발생 | CI 단계에 DAST와 퍼징을 넣고 동료 리뷰를 필수화 | 동적 분석 결함 검출률 |
| **패키지 환각** (Slopsquatting) | 모델이 만든 없는 패키지명을 공격자가 공개 저장소에 등록 | 공개 저장소 직접 다운로드를 막고 검증된 사내 패키지 미러만 허용 | 미검증 패키지 설치 시도 수 |
| 외부 SaaS의 감사 불투명성 | 계약을 맺어도 실제 데이터 처리 경로를 검증하기 어려움 | 사내 VPC에 오픈 가중치 모델을 직접 서빙 | 감사 증적 충족률 |

## Ⅵ. LLM 도입 보안 위험·대응의 기술사적 제언

- 핵심 요약 : 정책, 인프라, 개발 프로세스를 함께 세워 섀도 AI를 줄이고 생성 코드의 안전성을 제도로 보장.

1. 경영진과 보안 조직은 데이터의 공개, 대외비, 극비 등급별 입력 허용 기준을 사용 지침으로 정하고, 이를 개인정보 보호 법령과 맞추어 교육해야 한다.
2. 정보시스템 부서는 모든 AI 사용을 하나의 게이트웨이로 모아 로깅과 모니터링을 중앙화하고, 승인되지 않은 도구 사용을 탐지하는 체계를 운영해야 한다.
3. 개발 조직은 IDE와 빌드 파이프라인에 AI 생성 코드 검증 도구를 기본 포함해, 생성 속도가 보안 검증을 건너뛰지 않도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : LLM 도입 보안은 입력, 처리, 출력 전 구간에 통제를 두어 생산성과 보호를 함께 지키는 활동.
- 시사점 : 생성 AI는 이미 업무에 들어와 있으므로, 금지보다 통제된 경로를 제공하는 조직이 섀도 AI 위험을 줄일 수 있음.
