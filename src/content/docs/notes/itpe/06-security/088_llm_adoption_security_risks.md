## 답안 골격
```text
[LLM 도입 보안 위험·대응] ◀━━ 머리: Ⅶ 내 의견 (AI 혁신과 안전의 공존 완성 → 전사 프롬프트 데이터 유출 차단 DLP 및 AI Guardrails 다계층 방어선 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 기업 및 SW 개발 환경에 대형언어모델(LLM)을 도입할 때 발생하는 기밀 유출, 적대적 공격, 취약한 코드 생성 등 신종 보안 위험과 종합 통제 대책
 ┣━ Ⅱ 특징 ───── 비결정론적 출력 통제 난해 · 프롬프트 입력단 통한 직접 침투 · 데이터 유출(Data Leakage) 위험 · 생성된 소스코드의 잠재 취약점 상속
 ┣━ Ⅲ 구조 ───── 3대 핵심 위험: ① 기밀/개인정보 유출 ② 프롬프트 인젝션(Prompt Injection) ③ 취약한 코드 생성 및 공급망 오염
 ┣━ Ⅳ 흐름 ───── 사용자·외부 자료 입력 → 데이터 분류와 신뢰 경계 검사 → LLM 추론·도구 호출 권한 검토 → 출력 검증·코드 리뷰 → 승인된 결과 활용
 ┣━ Ⅴ 비교 ───── LLM 도입 보안(프롬프트 조작, 환각, 학습 데이터 오염, 비정형 텍스트 위협) vs 전통적 SW 보안(SQL 인젝션, 메모리 버퍼 오버플로우, 정형 트래픽 위협)
 ┗━ Ⅵ 실무 ───── 사내 프라이빗 LLM 구축을 통한 데이터 주권 확보 / 개발자 코딩 어시스턴트 사용 가이드라인 및 DevSecOps 연동
```
- 필수 키워드: LLM 보안 위험 · 프롬프트 인젝션 · 민감정보 유출 · 취약한 코드 생성 · AI 가드레일(Guardrails) · RAG 중독 · 전사 AI 정책
- 기출: 136회 2교시 3번 `AI 기반 소프트웨어 개발에서 LLM(Large Language Model)을 도입할 때 고려해야 할 보안 위험을 3가지 이상 쓰고 각 대응 방안을 설명하시오.` → Ⅲ 3대 보안 위험 + Ⅵ 각 위험별 구체적 대응 방안

## 한 줄 본질
- 업무 효율화를 위해 LLM을 무분별하게 도입할 때 사내 소스코드와 기밀이 외부로 유출되고 조작된 프롬프트로 시스템이 장악되는 위협 → 입력-추론-출력 전 단계에 가드레일(Guardrails) 필터를 배치하고 데이터 비식별화 및 코드 정적 분석을 강제 → 안전한 AI 생산성 달성 / 개발 편의성과의 조화 필요

              ▼
   ┌────────────────────────────────────────────────────────┐

   │  - 위험 ②: 프롬프트 인젝션 ➔ 적대적 프롬프트 시그니처 차단 │
   └──────────────────────────┬─────────────────────────────┘

   ┌────────────────────────────────────────────────────────┐
   │ 2. [추론단 보호: Isolated LLM & RAG]                    │

   │  - RAG 지식베이스 무결성 검증 (데이터 중독 차단)        │

## 핵심 용어
- 간접 프롬프트 인젝션(Indirect Prompt Injection): 사용자가 직접 악성 질문을 하지 않아도, LLM이 읽어들인 웹페이지나 외부 문서 내에 숨겨진 악의적 지시어에 속아 비인가 동작을 수행하는 공격
- AI 가드레일(Guardrails): LLM의 입력 프롬프트와 출력 결과물을 실시간으로 감시하여 개인정보, 악성코드, 비속어, 편향적 문장을 걸러내는 전·후처리 보안 필터 레이어

## 핵심 통찰
- 개발자가 외부 LLM 서비스에 소스코드나 비밀번호를 입력하면 해당 서비스로 기밀이 전송된다. 학습 이용 여부·보존 기간·제3자 제공 범위는 서비스와 계약·설정에 따라 다르므로 확인해야 한다. 입력 즉시 재학습되어 전 세계에 공개된다고 단정할 수 없다.
- LLM이 짜준 코드는 겉보기엔 그럴듯하지만 SQL 인젝션, XSS, 하드코딩된 시크릿 등 보안 취약점을 심각하게 내포하고 있음 → LLM이 생성한 코드는 '출처를 알 수 없는 인터넷 오픈소스'와 동일한 위험 등급으로 다루어야 함
- 자연어 입력 자체가 곧 실행 코드가 되는 것은 아니다. LLM이 신뢰되지 않은 문서의 지시를 따라 도구를 호출하거나 생성 코드를 배포할 때 권한 경계가 무너질 수 있다. 도구 권한 제한·승인 절차와 코드 리뷰·테스트·SAST를 함께 적용한다.

## 이웃 토픽과 구분
- LLM 도입 보안 vs 전통 소프트웨어 보안: LLM 도입 보안 = 자연어 프롬프트 해석의 비결정론적 취약점 및 데이터 유출 통제 / 전통 SW 보안 = 정형화된 코드 결함과 네트워크 패킷 수준의 통제

## 문제·원인·대책
- 적용 상황: 사내 개발 부서에서 코딩 생산성 향상을 위해 외부 퍼블릭 LLM API를 도입한 상황
| 문제 (3대 위험) | 원인 | 대책 (대응 방안) | 효과 |
|---|---|---|---|
| 1. 핵심 기밀 및 API Key의 외부 유출 | 승인되지 않은 외부 서비스로 소스코드·고객 데이터 전송 | 데이터 분류·입력 제한, DLP, 서비스 보존·학습 설정 및 계약 확인 | 전송 범위와 재사용 위험 축소 |
| 2. 프롬프트 인젝션을 통한 AI 조종 | 외부 텍스트의 지시를 상위 명령으로 취급 | 신뢰 경계 분리, 도구 최소 권한, 고위험 작업 승인 및 결과 검증 | 악성 입력이 실행 행위로 이어질 위험 축소 |
| 3. 보안 취약점을 내포한 소스코드 배포 | 생성 결과를 검증 없이 병합·배포 | 코드 리뷰, 테스트, SAST·DAST 및 라이선스 검토 | 배포 전 결함 발견 가능성 향상 |

## 1교시 예상문제 (10점)
- LLM을 소프트웨어 개발에 도입할 때의 주요 보안 위험 세 가지와 대응을 설명하시오.

## 1교시 10점 답안
- **기밀 유출:** 소스코드·키·개인정보의 외부 전송 → 데이터 분류·입력 제한·서비스 계약·보존 정책 검토.
- **프롬프트 인젝션:** 신뢰되지 않은 문서의 지시가 도구 실행을 유도 → 입력 신뢰 경계 분리·도구 최소 권한·고영향 작업 승인.
- **취약 코드:** 생성 코드를 검증 없이 반영 → 코드 리뷰·테스트·SAST/DAST·의존성·라이선스 검사.

## 2~4교시 예상문제 (25점)
- AI 기반 SW 개발에서 LLM 도입 시 보안 위험을 세 가지 이상 쓰고 각 대응 방안을 설명하시오.

## 2~4교시 25점 답안
### Ⅰ. 적용 범위
- 코드 작성·문서 검색·자동화 도구 연결의 입력·출력·실행 경계를 정의.
### Ⅱ. 위험과 대응
| 위험 | 발생 경로 | 대응 |
|---|---|---|
| 기밀·개인정보 유출 | 프롬프트·로그·검색 자료의 외부 전송 | 데이터 분류·최소 전송·DLP·계약 확인 |
| 프롬프트 인젝션 | 외부 문서가 상위 지시처럼 해석 | 문서·지시 분리, 도구 권한 제한·승인 |
| 취약 코드·공급망 | 생성 코드·의존성의 검증 없는 병합 | 리뷰·테스트·SAST/DAST·구성요소 점검 |
### Ⅲ. 운영
- 모델 제공자의 저장·학습 정책, 접근 로그, 보존 기간과 사고 대응 책임을 확인.
### Ⅳ. 검증
- 실제 개발 흐름에서 입력 유출·주입·취약 코드 사례를 재현해 통제 효과를 반복 시험.

## 이렇게 출제된다
- 제136회 2교시 3번: "AI 기반 소프트웨어 개발에서 LLM(Large Language Model)을 도입할 때 고려해야 할 보안 위험을 3가지 이상 쓰고 각 대응 방안을 설명하시오." → 요구 포인트: Ⅲ 3가지 핵심 보안 위험(기밀 유출, 프롬프트 인젝션, 취약한 코드 생성) + Ⅵ 각 위험별 대응 방안(DLP/프라이빗 구축, Guardrails 적용, DevSecOps SAST 검증)

## 내 의견
- [금지가 아닌 통제된 환경(Paved Path) 제공] "보안이 위험하니 AI를 일체 쓰지 말라"는 지침은 개발자들의 '섀도우 AI(Shadow AI)' 사용을 부추겨 사각지대를 키움 → 나라면: 사내 인증과 연동된 '엔터프라이즈 AI 게이트웨이'를 공식 제공하고, 이 게이트웨이를 통과할 때 개인정보와 소스코드 시크릿이 자동으로 마스킹되도록 인프라를 구축하여 개발자의 생산성과 보안성을 동시에 확보
