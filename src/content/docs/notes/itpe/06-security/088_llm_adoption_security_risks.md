```text
[LLM 도입 보안 위험·대응] ◀━━ 머리: Ⅶ 내 의견 (AI 혁신과 안전의 공존 완성 → 전사 프롬프트 데이터 유출 차단 DLP 및 AI Guardrails 다계층 방어선 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 기업 및 SW 개발 환경에 대형언어모델(LLM)을 도입할 때 발생하는 기밀 유출, 적대적 공격, 취약한 코드 생성 등 신종 보안 위험과 종합 통제 대책
 ┣━ Ⅱ 특징 ───── 비결정론적 출력 통제 난해 · 프롬프트 입력단 통한 직접 침투 · 데이터 유출(Data Leakage) 위험 · 생성된 소스코드의 잠재 취약점 상속
 ┣━ Ⅲ 구조 ───── 3대 핵심 위험: ① 기밀/개인정보 유출 ② 프롬프트 인젝션(Prompt Injection) ③ 취약한 코드 생성 및 공급망 오염
 ┣━ Ⅳ 흐름 ───── 사용자 프롬프트 입력 → 입력단 Guardrails(민감정보 마스킹, 인젝션 검사) → LLM 추론 → 출력단 Guardrails(코드 정적분석, 독성 필터링) → 안전한 결과 반환
 ┣━ Ⅴ 비교 ───── LLM 도입 보안(프롬프트 조작, 환각, 학습 데이터 오염, 비정형 텍스트 위협) vs 전통적 SW 보안(SQL 인젝션, 메모리 버퍼 오버플로우, 정형 트래픽 위협)
 ┗━ Ⅵ 실무 ───── 사내 프라이빗 LLM 구축을 통한 데이터 주권 확보 / 개발자 코딩 어시스턴트 사용 가이드라인 및 DevSecOps 연동
```

## 한 줄 본질
- 업무 효율화를 위해 LLM을 무분별하게 도입할 때 사내 소스코드와 기밀이 외부로 유출되고 조작된 프롬프트로 시스템이 장악되는 위협 → 입력-추론-출력 전 단계에 가드레일(Guardrails) 필터를 배치하고 데이터 비식별화 및 코드 정적 분석을 강제 → 안전한 AI 생산성 달성 / 개발 편의성과의 조화 필요

## 핵심 용어
- 간접 프롬프트 인젝션(Indirect Prompt Injection): 사용자가 직접 악성 질문을 하지 않아도, LLM이 읽어들인 웹페이지나 외부 문서 내에 숨겨진 악의적 지시어에 속아 비인가 동작을 수행하는 공격
- AI 가드레일(Guardrails): LLM의 입력 프롬프트와 출력 결과물을 실시간으로 감시하여 개인정보, 악성코드, 비속어, 편향적 문장을 걸러내는 전·후처리 보안 필터 레이어

## 핵심 통찰
- 개발자가 LLM에게 "이 버그 좀 고쳐줘"라며 사내 핵심 알고리즘이나 DB 접속 패스워드를 복사해 붙여넣는 순간, 해당 데이터는 퍼블릭 LLM의 재학습 데이터로 들어가 전 세계에 공개될 수 있음
- LLM이 짜준 코드는 겉보기엔 그럴듯하지만 SQL 인젝션, XSS, 하드코딩된 시크릿 등 보안 취약점을 심각하게 내포하고 있음 → LLM이 생성한 코드는 '출처를 알 수 없는 인터넷 오픈소스'와 동일한 위험 등급으로 다루어야 함
- LLM 보안의 본질은 "자연어(텍스트)가 곧 코드(실행 명령어)가 되었다"는 점임 → 자연어 입력을 완벽히 제어할 수 없으므로 출력 단계의 엄격한 결정론적 유효성 검사(SAST)가 필수적임

## 이웃 토픽과 구분
- LLM 도입 보안 vs 전통 소프트웨어 보안: LLM 도입 보안 = 자연어 프롬프트 해석의 비결정론적 취약점 및 데이터 유출 통제 / 전통 SW 보안 = 정형화된 코드 결함과 네트워크 패킷 수준의 통제

## 문제·원인·대책
- 적용 상황: 사내 개발 부서에서 코딩 생산성 향상을 위해 외부 퍼블릭 LLM API를 도입한 상황
| 문제 (3대 위험) | 원인 | 대책 (대응 방안) | 효과 |
|---|---|---|---|
| 1. 핵심 기밀 및 API Key의 외부 유출 | 퍼블릭 LLM에 사내 소스코드 원본 및 고객 데이터 무단 전송 | 엔드포인트 AI DLP 도입, 사내 프라이빗 LLM 구축 및 학습 배제(Opt-out) 계약 | 기밀 정보의 외부 전송 및 재학습 활용 원천 차단 |
| 2. 프롬프트 인젝션을 통한 AI 조종 | 신뢰되지 않은 외부 텍스트 입력 시 시스템 프롬프트 덮어쓰기 허용 | NeMo Guardrails 등 AI 방화벽 적용 및 입력 프롬프트 살균(Sanitization) | 공격자의 비인가 악성 프롬프트 실행 무력화 |
| 3. 보안 취약점을 내포한 소스코드 배포 | LLM의 통계적 코드 생성 특성(보안성보다 코드 완성도 우선) | CI/CD 파이프라인 내 SAST 정적 분석 및 라이선스 스캐너 연동 | 생성된 코드의 취약점 및 오픈소스 라이선스 위반 사전 차단 |

## 이렇게 출제된다
- 제136회 2교시 3번: "AI 기반 소프트웨어 개발에서 LLM(Large Language Model)을 도입할 때 고려해야 할 보안 위험을 3가지 이상 쓰고 각 대응 방안을 설명하시오." → 요구 포인트: Ⅲ 3가지 핵심 보안 위험(기밀 유출, 프롬프트 인젝션, 취약한 코드 생성) + Ⅵ 각 위험별 대응 방안(DLP/프라이빗 구축, Guardrails 적용, DevSecOps SAST 검증)

## 내 의견
- [금지가 아닌 통제된 환경(Paved Path) 제공] "보안이 위험하니 AI를 일체 쓰지 말라"는 지침은 개발자들의 '섀도우 AI(Shadow AI)' 사용을 부추겨 사각지대를 키움 → 나라면: 사내 인증과 연동된 '엔터프라이즈 AI 게이트웨이'를 공식 제공하고, 이 게이트웨이를 통과할 때 개인정보와 소스코드 시크릿이 자동으로 마스킹되도록 인프라를 구축하여 개발자의 생산성과 보안성을 동시에 확보
