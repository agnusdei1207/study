## Ⅰ. LLM 도입 보안 위험·대응의 개요

- 개념 : 기업 비즈니스 및 SW 개발 수명주기 전반에 **LLM**을 도입할 때 발생하는 데이터 유출, 적대적 프롬프트, 취약 코드 주입 위험을 식별하고 전주기 통제를 적용하는 보안 활동.
- 배경 및 필요성 : 기업의 생성형 AI 도입 가속화에 따라 사내 기밀 및 소스코드 누출, 비인가 **섀도우 AI** 사용, **환각** (Hallucination) 기반 업무 왜곡 등 새로운 보안 위협 표면이 급증하여 엔터프라이즈 통제 방안 수립이 시급해짐.
- 핵심 목적 : 생성형 AI 기반 개발 생산성 및 비즈니스 혁신을 극대화하면서도 사내 핵심 지적재산권(IP) 보호, 안전한 코드 품질 확보, 시스템 무결성 유지.

## Ⅱ. LLM 도입 보안 위험·대응의 핵심 아키텍처 및 동작 메커니즘

LLM 도입 보안 위험·대응은(는) 신뢰할 수 있는 보안 구조와 표준화된 절차를 기반으로 동작하며, 세부적인 아키텍처와 구성요소 간의 상호작용 메커니즘은 다음과 같음.

```text
[ 사내 사용자 / 개발자 ]
       │ 1. 프롬프트 질의 및 소스코드 입력
       ▼
+---------------------------------------------------------------------------------+
| 엔터프라이즈 AI 보안 게이트웨이 (AI Gateway / In-line Guardrails)                 |
|  ├── [DLP 엔진]: 개인정보(주민번호/이메일), 소스코드, API 시크릿 탐지 및 마스킹|
|  ├── [프롬프트 가드]: 탈옥(Jailbreak), 시스템 프롬프트 유출 시도 차단          |
|  └── [접근 통제]: 임직원 직무별 모델 접근 권한 인가 (ABAC/RBAC)                 |
+---------------------------------------------------------------------------------+
       │ 2. 정제된 프롬프트 전송 (ZDR 계약 적용 채널)
       ▼
[ 프라이빗 LLM / 전용 클라우드 인스턴스 ]
       │ 3. 추론 결과 생성 (코드, 텍스트 답변)
       ▼
+---------------------------------------------------------------------------------+
| 출력 필터링 및 DevSecOps 파이프라인 (Output Validation & CI/CD Pipeline)         |
|  ├── [출력 검증]: 기밀 데이터 재유출 탐지 및 유해 콘텐츠 필터링                 |
|  ├── [AI-SAST/DAST]: 생성된 코드의 CWE 취약점 및 시큐어 코딩 규칙 정적 검사     |
|  └── [SCA 의존성 검사]: 생성된 라이브러리 실존 여부 및 악성 패키지 해시 대조    |
+---------------------------------------------------------------------------------+
       │ 4. 검증 통과한 안전 코드만 병합
       ▼
[ 전사 프로덕션 코드베이스 / 저장소 ]
```

- **입력 (Ingress)** : 프롬프트 텍스트, 첨부 파일 (데이터 마스킹(Presidio), 시크릿 스캐너, Regex DLP, **프롬프트 인젝션** 필터).
- **처리 (Processing)** : LLM 모델 및 연동 인프라 (프라이빗 VPC 호스팅, ZDR(학습 배제) 계약, TLS 1.3 암호화 통신).
- **연계 (RAG/Tool)** : 검색 문서, 외부 API 호출 (문서 출처 격리(Sandboxed Context), 최소 권한 API 토큰, 파라미터 유효성 검사).
- **출력 (Egress)** : 생성 텍스트, 추천 소스코드 (SonarQube(SAST), Snyk(SCA), Bandit, 패키지 레지스트리 화이트리스팅).

## Ⅲ. LLM 도입 보안 위험·대응의 세부 구성 요소 및 비교 분석

| 위협 유형 | 발생 메커니즘 | 공격 매개체 | 주요 엔지니어링 방어 대책 |
|---|---|---|---|
| 민감정보 유출 | 프롬프트 입력창을 통한 사내 기밀 및 소스코드 전송 | 웹 브라우저, IDE 플러그인 | CASB, 엔터프라이즈 AI 게이트웨이, 데이터 토큰화 |
| **간접 프롬프트 인젝션** | 비신뢰 외부 웹페이지/이메일 내용이 RAG 지식으로 유입 | 검색된 컨텍스트 데이터 | 입력 데이터와 시스템 프롬프트 엄격 분리, XML 태그 격리 |
| 취약 코드 생성 | 오래된 오픈소스 취약 코드를 학습한 모델의 결함 코드 제안 | 코드 자동완성(Copilot 등) | CI/CD 파이프라인 내 정적 분석(SAST) 및 자동 단위 테스트 강제 |
| **패키지 환각** (Slopsquatting) | LLM의 통계적 단어 예측 오류로 가상 라이브러리 명칭 생성 | 생성된 requirements.txt/package.json | 사내 프라이빗 패키지 미러(Nexus/Artifactory) 강제 프록시 |

- LLM 도입 보안 위험·대응은(는) 상기 핵심 비교 지표와 아키텍처 구성을 바탕으로 보안 위협에 대한 방어 효과성을 극대화하며, 기존 레거시 통제 기법 대비 우수한 신뢰성과 운영 효율성을 제공함.

## Ⅳ. LLM 도입 보안 위험·대응의 주요 한계점 및 해결 방안

- 한계점 : 자연어 기반 프롬프트 인젝션은 공격 구문이 무한 변형되어 정규식 기반 탐지 룰로 완전 차단 불가.
  - 해결 방안 : 시스템 지시문과 외부 데이터 영역을 **구조화된 구분자** (`<user_data>...</user_data>`)로 완전 격리하고 이중 판별용 경량 가드레일 LLM을 병렬 배치.
- 한계점 : LLM이 생성한 코드가 정적 분석기(SAST)를 우회하는 논리적 결함(Logic Bug)이나 레이스 컨디션을 유발.
  - 해결 방안 : 자동화된 **동적 분석** (DAST) 및 **퍼징** (Fuzzing) 테스트를 CI 단계에 통합하고, 개발자 최종 코드 리뷰(Peer Review) 통과 의무화 정책 강제.
- 한계점 : LLM이 추천한 가상 패키지 이름을 공격자가 실제 npm/PyPI에 등록하여 침투하는 공급망 공격 발생.
  - 해결 방안 : 내부 패키지 관리자 설정에서 퍼블릭 레지스트리 직접 다운로드를 금지하고, 사전 검증된 사내 아티팩토리(Artifactory) 프록시만 접근 허용.
- 한계점 : **엔터프라이즈 계약** (ZDR)을 체결했음에도 불구하고 외부 클라우드 SaaS AI 사용에 따른 컴플라이언스 감사 불투명성.
  - 해결 방안 : 사내 프라이빗 클라우드(VPC) 내에 오픈소스 가중치 모델(Llama, Mistral 등)을 자체 서빙하는 온프레미스 AI 인프라 구축.

## Ⅴ. LLM 도입 보안 위험·대응 적용 및 발전을 위한 기술사적 제언

- 정책 및 제도 중심의 거버넌스 및 실행 체계 구축 : 생성형 AI 사용 가이드라인 배포 및 데이터 입력 허용 등급(공개/대외비/극비) 규정을(를) 적극 추진하여, 법적 데이터 침해 위험 및 개인정보보호법 위반 사전 예방 효과를 극대화해야 함.
- 인프라 보안 중심의 거버넌스 및 실행 체계 구축 : 전사 공통 AI Gateway 단일 창구화 및 중앙 집중 로깅/모니터링 구축을(를) 적극 추진하여, 무단 섀도 AI 사용 억제 및 프롬프트 감사 추적성 확보 효과를 극대화해야 함.
- 개발 프로세스 중심의 거버넌스 및 실행 체계 구축 : 개발자 IDE 및 CI/CD 빌드 파이프라인에 AI 생성 코드 자동 검증 툴킷 연동을(를) 적극 추진하여, 안전한 고품질 소프트웨어 신속 출시 및 공급망 무결성 보장 효과를 극대화해야 함.
