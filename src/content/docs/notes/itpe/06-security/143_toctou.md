## 연관 키워드

- TOCTOU(Time Of Check To Time Of Use), 경쟁 상태(Race Condition), 경쟁 구간(Race Window)
- 심볼릭 링크(Symbolic Link), 원자성(Atomicity), 파일 디스크립터(File Descriptor), 이중 인출(Double Spending), 권한 상승(Privilege Escalation)

## Ⅰ. TOCTOU의 개요

- 핵심 요약 : 자원의 상태를 검사하는 시점과 사용하는 시점 사이의 틈을 이용해 검사 결과를 뒤집는 경쟁 상태 취약점.
- 개념 : 프로그램이 파일, 메모리, 권한 같은 자원의 상태를 확인(Check)한 뒤 실제로 사용(Use)하기까지의 시간 차를 악용해 자원을 바꿔치는 **경쟁 상태** (Race Condition) 취약점으로, TOCTOU(Time Of Check To Time Of Use)라고 부름.
- 배경 및 필요성 : 멀티태스킹 운영체제는 시분할(Time-sharing) 방식으로 프로세스를 번갈아 실행하므로, 검사 직후 사용 직전에 다른 프로세스로 문맥 전환(Context Switching)이 일어날 수 있는 구조적 맹점이 존재함.
- 공격 목적 : 검사 결과를 무력화하여 비인가자가 특권(SetUID root) 프로그램을 통해 /etc/shadow 같은 핵심 파일을 덮어쓰거나 열람하는 것.

## Ⅱ. TOCTOU의 특징 및 장점

- 핵심 요약 : 검사와 사용이 원자적으로 묶이지 않는 구조가 권한 상승과 임의 파일 변조로 이어지는 방식.

1. **경쟁 구간** (Race Window) : 검사 시스템 콜과 사용 시스템 콜 사이에 존재하는 짧은 시간 간극 → 공격자가 자원을 교체할 기회를 얻음.
2. **심볼릭 링크 레이스** (Symlink Race) : 검사 통과 직후 일반 파일을 지우고 시스템 파일을 가리키는 심볼릭 링크를 만듦 → 특권 프로그램이 핵심 파일에 쓰기를 수행.
3. **원자성 결여** (Lack of Atomicity) : 검사와 사용이 하나의 불가분 연산이 아니라 두 개의 시스템 콜로 나뉨 → 구조적 결함이 상시 존재.
4. 동시성 전반의 취약성 : 파일뿐 아니라 DB 잔액 조회 후 인출, 메모리 플래그 검사 후 포인터 사용에서도 발생 → **이중 인출** (Double Spending) 같은 금융 사고로 이어짐.

```text
[ TOCTOU 공격 흐름 ]

특권 프로그램 : access() 권한 확인 통과
    ↓
[ 경쟁 구간 ] 공격자 : 파일을 심볼릭 링크로 교체
    ↓
특권 프로그램 : open()·write() 실행
    ↓
핵심 시스템 파일이 특권으로 변조됨
```

## Ⅲ. TOCTOU의 구조 (흐름)

- 핵심 요약 : 특권 프로그램의 검사 단계와 사용 단계 사이에서 자원이 바뀌는 흐름이 성립하는 구조.
- **검사 단계** (Check) : access()나 stat()으로 경로의 권한과 상태를 확인.
- **사용 단계** (Use) : open()과 write()로 같은 경로를 다시 열어 쓰기 수행. 이때 경로가 가리키는 대상이 검사 때와 같다는 보장이 없음.

```text
[ 경로명 방식과 디스크립터 방식 ]

경로명 방식 : 검사 → 같은 경로로 다시 열기
    ↓ (틈 발생, 대상 교체 가능)

디스크립터 방식 : 열기 → fd로 검사·사용
    ↓ (대상 고정, 교체 불가)
```

## Ⅳ. TOCTOU의 비교 분석

- 핵심 요약 : 검사 시점의 원자성 결여로 생기는 TOCTOU는 확률적으로 발생하며 권한 상승으로 이어져, 메모리 경계 결함이나 자원 대기 결함과 원인이 구분되는 구조.

비교 대상은 **버퍼 오버플로** (BOF, Buffer Overflow)와 **교착 상태** (Deadlock)다.

| 비교 축 | TOCTOU | 버퍼 오버플로 | 교착 상태 |
| --- | --- | --- | --- |
| 발생 원인 | 검사와 사용 사이의 시간 차와 원자성 결여 | 경계 검사 부실로 버퍼 초과 쓰기 | 프로세스 간 상호 배제 자원의 순환 대기 |
| 악용 기법 | 심볼릭 링크 교체, 스레드 경쟁 | 스택 덮어쓰기, ROP(Return-Oriented Programming) | 서비스 지연·중단 유발 (DoS, Denial of Service) |
| 보안 영향 | 권한 상승, 임의 파일 변조 | 원격 임의 코드 실행(RCE, Remote Code Execution), 쉘 획득 | 시스템 교착과 서비스 정지 |
| 해결 원리 | 원자적 시스템 콜, 파일 디스크립터 기반 조작 | ASLR(Address Space Layout Randomization), DEP(Data Execution Prevention), 스택 카나리 | 자원 할당 순서 고정, 타임아웃, 점유 대기 방지 |
| 재현성 | 확률적 (경쟁에서 이겨야 함) | 결정론적 (페이로드 주입 시 재현) | 타이밍에 따른 간헐적 발생 |

- 선택 기준 : TOCTOU는 경로명 기반 파일 조작에서 주로 나타나므로, 파일 조작 API를 설계하는 단계에서 원자성을 확보하는 것이 가장 근본적인 대응임.

## Ⅴ. TOCTOU의 한계와 방안

- 핵심 요약 : 확률적 재현 특성, 공용 임시 디렉터리 노출, 분산 환경의 동시성 충돌을 정적 분석, 보호 설정, 잠금과 원자적 갱신으로 보완.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 동적 탐지와 재현의 어려움 | 공격 성공이 경쟁에서 이기는 데 의존하여 일반 단위 테스트나 동적 스캐너로는 감지가 어려움 | **SAST** (Static Application Security Testing)로 access()와 open()이 짝을 이루는 안티 패턴을 정적 규칙으로 전수 검사 | 안티 패턴 검출 건수 |
| 공용 임시 디렉터리 노출 | /tmp처럼 모든 로컬 사용자가 쓰기 가능한 공간에서 심볼릭 링크 공격 표면이 상시 열림 | Linux 커널의 fs.protected_symlinks, fs.protected_hardlinks 설정을 활성화하여 타인 소유 디렉터리의 링크 추적 차단 | 보호 설정 적용률 |
| 분산 환경의 동시성 충돌 | 잔액을 검사하고 차감하는 병렬 API 요청이 동시에 실행되어 이중 인출 발생 | SQL(Structured Query Language)의 SELECT FOR UPDATE 비관적 잠금, 분산 락(Redis Redlock), 원자적 조건부 갱신(CAS, Compare-And-Swap) 적용 | 잠금 대기 시간, 충돌 재시도 건수 |

## Ⅵ. TOCTOU의 기술사적 제언

- 핵심 요약 : 원자적 파일 생성과 디스크립터 기반 API를 기본 원칙으로 삼아, 경로명 재사용으로 생기는 틈을 설계 단계에서 없애는 방향.

1. 임시 파일이나 잠금 파일을 만들 때는 존재 여부를 따로 검사하지 않고 `O_CREAT | O_EXCL` 플래그로 생성과 확인을 한 번에 처리하도록 개발 표준에 명시하는 것이 바람직하다.
2. 파일 조작 로직은 최초 open()으로 얻은 파일 디스크립터를 중심으로 재구성하고, 경로명을 반복 사용하는 호출을 점진적으로 대체하도록 보안 코딩 지침을 제정할 필요가 있다.
3. 임시 파일은 O_TMPFILE과 O_NOFOLLOW 플래그를 채택하고, 공용 디렉터리 대신 사용자별로 격리된 경로를 쓰도록 운영 기준을 세우는 것이 실효적이다.

## Ⅶ. 결론

- 핵심 요약 : TOCTOU는 검사와 사용을 분리한 설계에서 비롯된 경쟁 상태이며, 검사한 대상을 디스크립터로 고정하는 것이 근본 해법임.
- 시사점 : 확률적으로만 드러나는 취약점이므로 원자적 연산을 설계 기본값으로 두고, 정적 분석으로 상시 점검하는 체계가 필요함.
