## 지식 로드맵 내 현재 위치

지식 위치: 정보보안 → 경쟁 상태·시스템 보안 → **TOCTOU**

## 30초 인출

- **본질:** 자원의 보안 상태나 권한을 검사하는 시점(TOC)과 해당 자원을 실제로 사용하는 시점(TOU) 사이의 시간 간극(Race Window)에 자원이 변조되어 검증이 무력화되는 경쟁 상태(Race Condition) 취약점
- **메커니즘:** 권한 검사(TOC) $\rightarrow$ 컨텍스트 스위칭 간극에 공격자가 심볼릭 링크 생성 $\rightarrow$ 특권 프로세스가 변조된 대상을 조작(TOU) $\rightarrow$ 시스템 파일 변조 및 권한 상승
- **통찰:** 단순 시간 단축은 경쟁을 없앨 수 없으므로 `openat()`과 `fstat` 기반 파일 디스크립터 고정 및 분산 펜싱 토큰 기반 원자적 연산 필수

<details>
<summary>핵심 용어</summary>

- **TOCTOU (Time-of-Check to Time-of-Use)** : 검사 시점과 사용 시점 사이의 비동기 상태 변화를 악용하는 CWE-367 취약점.
- **Race Window (경쟁 구간)** : 검사 완료 후 실제 자원 사용 직전까지 공격자가 개입할 수 있는 미세한 시간 간극.
- **File Descriptor (파일 디스크립터)** : 커널이 열린 파일 객체를 직접 가리키는 정수형 인덱스로 경로 변경 공격에 불변.
- **Fencing Token** : 분산 락 만료 시 오래된 요청의 스토리지 쓰기를 차단하는 단조 증가 번호 메커니즘.

</details>

## 2~4교시 예상문제 (25점)

> 경쟁 상태(Race Condition) 취약점인 TOCTOU(Time-of-Check to Time-of-Use)의 발생 원리, 파일 시스템 심볼릭 링크 및 비즈니스 로직 침투 시나리오를 설명하고, 원자적 연산(Atomic Operation)과 파일 디스크립터 기반 하드닝 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 자원의 유효성이나 접근 권한을 확인하는 시점(TOC)과 해당 자원을 실제로 읽거나 수정하는 시점(TOU) 사이의 시간 차(Race Window)를 악용하여 자원의 상태를 바꿔치기하는 소프트웨어 보안 결함 |
| 목적 | 시스템 검증 로직을 우회하여 비인가 파일(예: `/etc/shadow`)을 변조하거나, 포인트/잔액 중복 인출(Double Spending) 및 권한 상승(Privilege Escalation) 유발 |

- 멀티태스킹 OS의 시분할(Context Switching) 및 분산 환경의 비동기 처리 특성으로 인해 '검사 대상과 사용 대상이 동일하다'는 개발자의 가정이 깨지면서 발생

## Ⅱ. TOCTOU의 핵심 기술적 특성

| 특성 항목 | 세부 내용 및 기술적 의미 | 엔지니어링 위험성 |
|---|---|---|
| 비원자적 상태 전이 | 검사(Check) 연산과 사용(Use) 연산이 분리된 시스템 콜로 실행 | 두 연산 사이에 공격자 프로세스가 스케줄링될 기회 제공 |
| 파일 경로 이름 기반 조작 | 커널 내부 객체가 아닌 문자열 경로(`char *path`)를 기반으로 재접근 | 중간 디렉터리나 파일의 심볼릭 링크 교체 공격에 취약 |
| 비결정론적 취약성 재현 | CPU 부하, 스레드 스케줄링에 따라 공격 성공 확률이 달라짐 | 디버깅 및 정적 분석 도구로 탐지하기 극히 난해 |
| 광범위한 도메인 적용성 | 파일 시스템뿐 아니라 전자상거래 쿠폰 중복 사용, 은행 계좌 잔액 동시 인출에 발생 | 비즈니스 로직 계층의 심각한 금전적 손실 유발 |

- 시큐어 코딩에서 검사와 사용을 하나의 트랜잭션 또는 단일 시스템 콜로 결합하는 '원자성(Atomicity)' 보장이 핵심 특성

## Ⅲ. 파일 시스템 TOCTOU 공격 메커니즘 및 방어 프로세스

```text
[심볼릭 링크 교체 기반 파일 시스템 TOCTOU 공격 흐름]

  [특권 프로세스 (Root Daemon)]                 [공격자 프로세스 (Unprivileged)]
               │                                                │
  [1. TOC]     │ access("/tmp/tempfile", W_OK)                  │
               ├───────────────────────────────────────────────>│ (권한 확인 성공: 정상 파일)
               │                                                │
               │ [ Race Window: 컨텍스트 스위칭 발생 ]         │
               │                                                │ [2. 자원 변조]
               │                                                │ unlink("/tmp/tempfile");
               │                                                │ symlink("/etc/shadow", "/tmp/tempfile");
               │                                                │
  [3. TOU]     │ fd = open("/tmp/tempfile", O_WRONLY);          │
               │ write(fd, "악의적 계정 데이터", ...);           │
               ├───────────────────────────────────────────────>│ [4. 피해 발생]
               │                                                │ /etc/shadow 파일이 변조되어
               │                                                │ 루트 권한 완전 탈취!
```

| 프로세스 단계 | 공격 동작 및 취약 코드 | 안전한 시큐어 코딩 방어 메커니즘 |
|---|---|---|
| 1. 검사 시점 (TOC) | `access(path, W_OK)`로 쓰기 권한 확인 | 경로 기반 사전 검사 함수(`access()`) 전면 배제 |
| 2. 경쟁 구간 (Race) | 공격자가 파일을 삭제하고 대상 시스템 파일 심볼릭 링크 생성 | 예측 불가능한 임시 파일 생성 (`mkstemp()`) |
| 3. 사용 시점 (TOU) | `open(path, O_WRONLY)`으로 파일 열기 | `open(path, O_CREAT | O_EXCL)` 원자적 플래그 사용 |
| 4. 사후 검증 | 검사 없이 오픈된 파일에 대해 무조건 쓰기 | 열린 파일 디스크립터(`fd`) 기반 `fstat(fd, &st)` 무결성 검증 |

## Ⅳ. 동시성 제어 및 경쟁 상태 취약점 유형 비교

| 비교 항목 | TOCTOU (CWE-367) | 교착 상태 (Deadlock) | 라이브락 (Livelock) | 임계 구역 (Critical Section) |
|---|---|---|---|---|
| 핵심 현상 | 검사와 사용 간격 사이 자원 변조 | 둘 이상의 프로세스가 자원을 무한 대기 | 상태를 계속 바꾸며 무한 진행 불가 | 동시 접근 시 정합성이 깨지는 코드 블록 |
| 발생 원인 | 연산의 비원자성 및 시간차 간극 | 상호배제, 점유대기, 비선점, 환형대기 | 상호 양보 알고리즘의 대칭적 충돌 | 동기화 락(Lock) 메커니즘 누락 |
| 보안 영향 | 권한 상승, 파일 변조, 이중 인출 | 서비스 거부(DoS), 시스템 행(Hang) | CPU 100% 점유, 성능 급격 저하 | 데이터 오염, 비즈니스 무결성 붕괴 |
| 해결 기법 | 원자적 API, 파일 디스크립터 고정 | 자원 할당 순서 고정, 타임아웃 | 무작위 백오프(Random Backoff) | 뮤텍스(Mutex), 세마포어, 모니터 |

## Ⅴ. TOCTOU 방어 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| `access()` 검사 후 `open()` 분리를 제거하더라도, 디렉터리 경로 트래버스 중간에 공격자가 상위 디렉터리를 심볼릭 링크로 교체하는 Path Traversal TOCTOU 발생 | `openat()` 계열 시스템 콜을 사용하여 사전에 신뢰 검증된 디렉터리 파일 디스크립터(dirfd) 기준으로 상대 경로를 열고, `O_NOFOLLOW` 플래그로 심볼릭 링크 추적을 원천 차단 |
| 마이크로서비스 분산 환경에서 Redis 분산 락(Redlock)을 사용하더라도, 네트워크 지연이나 GC Stop-the-world로 인해 락 TTL이 만료된 후 늦은 쓰기(Late Write)가 발생하는 정합성 붕괴 | 분산 락 획득 시 단조 증가하는 펜싱 토큰(Fencing Token)을 발급받아 스토리지 쓰기 트랜잭션에 포함하고, 데이터베이스에서 현재 버전보다 낮은 토큰의 쓰기는 무조건 거절(Drop) |
| 파일 오픈과 상태 검사를 단일 프로세스에서 수행하더라도, 정적 임시 파일명(`/tmp/app.tmp`)을 사용할 경우 예측 공격(Predictable Filename)에 노출 | 정적 파일명을 금지하고 OS 수준에서 암호학적 난수를 생성해 파일 생성과 배타적 오픈을 단일 원자 연산으로 완결하는 `mkstemp()` 또는 `O_TMPFILE` 플래그 강제 |
| 비즈니스 금융 로직(계좌 잔액 확인 후 송금)에서 다중 스레드 동시 요청 시 발생하는 이중 출금(Double Spending) 취약점 | 애플리케이션 레벨의 단순 IF문 검사를 배제하고, DB 레벨의 원자적 조건부 업데이트(`UPDATE ... SET bal = bal - ? WHERE id = ? AND bal >= ?`) 또는 비관적 락(`SELECT ... FOR UPDATE`) 적용 |

## Ⅵ. 안전한 동시성 제어 및 시스템 프로그래밍 하드닝 제언

```text
[TOCTOU 원천 봉쇄를 위한 3대 계층 엔지니어링 아키텍처]

 ┌─────────────────────────────────────────────────────────────┐
 │                 1. 시스템 프로그래밍 계층 (OS Core)          │
 │   - 경로 기반 검사(access) 금지 -> 디스크립터(fstat) 검증  │
 │   - openat() + O_NOFOLLOW + O_CREAT|O_EXCL 원자 연산 결합  │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              2. 애플리케이션 동시성 계층 (Concurrency)       │
 │   - 임계 구역 뮤텍스(Mutex) 및 원자적 CAS(Compare-and-Swap) │
 │   - 비즈니스 로직 불변 객체(Immutable Object) 패턴 적용    │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │                 3. 분산 데이터 계층 (Distributed Storage)    │
 │   - DB 조건부 원자적 쿼리 및 비관적 락(SELECT FOR UPDATE)   │
 │   - 분산 락 연계 단조 증가 펜싱 토큰(Fencing Token) 검증    │
 └─────────────────────────────────────────────────────────────┘
```

| 관리 영역 | 핵심 엔지니어링 세부 과제 | 통제 목표치 |
|---|---|---|
| 파일 시스템 | 임시 파일 생성 시 `mkstemp()` 및 `O_EXCL` 원자적 플래그 적용 | 파일 교체 경쟁 상태 취약점 0건 |
| 비즈니스 트랜잭션 | 계좌/재고 차감 로직에 DB 레벨 조건부 원자적 연산 관철 | 이중 출금(Double Spending) 사고 0건 |
| 분산 정합성 | 분산 락 사용 시 펜싱 토큰 유효성 검증 로직 배포 | 락 만료로 인한 데이터 덮어쓰기 0건 |
