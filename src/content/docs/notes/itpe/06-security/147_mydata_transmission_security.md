## 지식 로드맵 내 현재 위치

지식 위치: 정보보안 → 개인정보 보호 → **전송 보안**

## 30초 인출

- **본질:** 정보주체의 개인정보 전송요구권 행사에 따라 정보보유자로부터 인가된 정보수신자에게 개인신용정보를 안전하고 최소화된 범위로 전송하기 위한 API 보안 거버넌스 체계
- **메커니즘:** 본인 인증 및 전송 동의 $\rightarrow$ FAPI 기반 인가 토큰 발급 $\rightarrow$ mTLS/DPoP 송신자 결속 API 요청 $\rightarrow$ 동의 스코프 일치 검증 및 전송 이력 암호화 기록
- **통찰:** API 응답의 과다 전송은 데이터 사전 기반 실시간 필드 필터링으로 차단하고 금융 레거시 시스템 과부하는 토큰 버킷 레이트 리미팅과 비동기 배치로 해결 필수

<details>
<summary>핵심 용어</summary>

- **마이데이터 (MyData)** : 정보주체가 본인 데이터에 대한 실질적 통제권을 갖고 제3자에게 전송을 요구할 수 있는 제도.
- **FAPI (Financial-grade API)** : 금융권 고신뢰 API 통신을 위해 강화된 OpenID Foundation의 OAuth 2.0 보안 프로파일.
- **mTLS (Mutual TLS)** : 클라이언트와 서버가 상호 X.509 인증서를 검증하고 세션 토큰을 인증서에 바인딩하는 전송 보안.
- **Sender-Constrained Token** : 특정 클라이언트의 암호학적 키(인증서/개인키)에 종속되어 토큰 탈취 시 재사용이 불가능한 토큰.

</details>

## 2~4교시 예상문제 (25점)

> 개인정보 전송요구권 기반의 마이데이터 전송 보안 프레임워크(FAPI, mTLS, DPoP)의 아키텍처 및 전송 절차를 설명하고, 과다 전송(Over-fetching) 및 대량 API 트래픽 과부하에 대응하기 위한 엔지니어링 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 정보주체의 법적 전송요구권에 따라 정보보유자(금융사, 공공기관, 통신사)가 보유한 개인정보를 표준 API를 통해 공인된 정보수신자(마이데이터 사업자)에게 전송할 때 적용되는 신원·인가·암호화·감사 보안 통제 체계 |
| 목적 | 비인가 스크래핑(Screen Scraping) 관행을 전면 철폐하고, 정보주체의 동의 범위 내에서만 최소한의 데이터를 안전하게 이동시켜 데이터 주권 보장 및 유출 방지 |

- 개인정보보호법 제35조의2 및 신용정보법에 근거하며, 전송 프로토콜로서 글로벌 표준인 OpenID Foundation의 FAPI(Financial-grade API) 보안 규격을 채택

## Ⅱ. 마이데이터 전송 보안의 핵심 기술적 특성

| 특성 항목 | 세부 내용 및 기술적 의미 | 엔지니어링 구현 가치 |
|---|---|---|
| 송신자 구속 토큰 (Sender-Constrained) | 발급된 접근 토큰(Access Token)을 클라이언트의 mTLS 인증서 지문이나 DPoP 공개키에 암호학적 결속 | 토큰 탈취 공격자의 중간 재사용(Replay Attack) 원천 무력화 |
| 푸시 인가 요청 (PAR: RFC 9126) | 브라우저 전면 채널(Front-channel) URL 대신 백엔드 직접 통신으로 인가 요청 파라미터 전송 | 인가 요청 파라미터의 URL 노출, 변조 및 브라우저 히스토리 유출 차단 |
| 상호 인증 및 전송 암호화 (mTLS) | 게이트웨이 간 통신 시 서버뿐 아니라 클라이언트(마이데이터 사업자)의 X.509 인증서 상호 검증 | 비인가 비등록 사업자의 사칭 API 호출 원천 차단 |
| 세분화된 전송 동의 스코프 | 사용자가 선택한 금융 계좌 및 상세 항목에 대해서만 개별 권한 범위(Scope)를 정밀 발행 | 과다한 개인정보가 일괄 전송되는 프라이버시 침해 방지 |

- 금융보안원 및 중계기관(마이데이터 중계센터)을 신뢰 앵커로 하여 실시간 사업자 적격성과 인증서 유효성을 상시 검증하는 특성 보유

## Ⅲ. 마이데이터 전송 보안 아키텍처 및 4단계 전송 프로세스

```text
[마이데이터 FAPI 기반 전송요구 및 데이터 수신 프로세스]

 [정보주체 (사용자)]      [정보수신자 (마이데이터사)]      [공인 인증기관]      [정보보유자 (금융사/공공)]
         │                         │                       │                         │
         │ 1. 전송요구 및 동의     │                       │                         │
         ├────────────────────────>│                       │                         │
         │                         │ 2. 본인확인 및 전자서명 요청                    │
         │                         ├──────────────────────>│                         │
         │ 3. 통합인증 전자서명    │                       │                         │
         │<────────────────────────────────────────────────┤                         │
         │                         │ 4. FAPI PAR 인가 요청 (백채널)                  │
         │                         ├────────────────────────────────────────────────>│
         │                         │ 5. mTLS 상호 인증 및 DPoP 토큰 발급             │
         │                         │<────────────────────────────────────────────────┤
         │                         │                                                 │
         │                         │ 6. 마이데이터 API 전송 요청 (mTLS + Token)       │
         │                         ├────────────────────────────────────────────────>│
         │                         │                                                 │ 7. 동의 Scope 대조
         │                         │                                                 │    과다 전송 필터링
         │                         │ 8. 암호화된 JSON 데이터 응답 (TLS 1.3)           │
         │                         │<────────────────────────────────────────────────┤
         │ 9. 통합 자산 분석 화면  │                                                 │ 10. 전송 이력 보존
         │<────────────────────────┤                                                 │     (WORM 감사 로깅)
```

| 프로세스 단계 | 핵심 엔지니어링 세부 동작 | 보안 통제 규격 |
|---|---|---|
| 1. 전송 동의 및 인증 | 정보주체가 모바일 전자서명(공동인증서/금융인증서)으로 전송 대상 기관 및 항목 지정 | 본인확인기관 연동 전자서명 |
| 2. 인가 토큰 획득 | FAPI 2.0 프로파일 준수, PAR 엔드포인트 호출 후 mTLS 기반 접근 토큰(JWT) 발급 | RFC 9126 PAR, RFC 8705 mTLS |
| 3. 표준 API 데이터 요청 | 마이데이터 사업자 API 게이트웨이가 클라이언트 인증서와 DPoP 서명을 헤더에 포함해 요청 | FAPI Sender-Constrained Token |
| 4. 데이터 전송 및 로깅 | 정보보유자 API 서버가 동의 스코프 검증 후 허용된 JSON 필드만 반환 및 전송 이력 기록 | TLS 1.3 암호화, 개인정보보호법 감사 로깅 |

## Ⅳ. 마이데이터 보안 프로토콜 규격 비교

| 비교 항목 | 일반 웹 OAuth 2.0 (RFC 6749) | FAPI 1.0 Advanced Profile | FAPI 2.0 Security Profile |
|---|---|---|---|
| 주 적용 분야 | 일반 상용 웹/모바일 서비스 | 초기 금융 마이데이터 및 오픈뱅킹 | 차세대 글로벌 마이데이터 및 헬스케어 |
| 클라이언트 인증 | 클라이언트 시크릿(Shared Secret) | 비대칭 개인키(Private Key JWT) | mTLS 또는 DPoP 기반 비대칭 서명 |
| 토큰 보안 방식 | Bearer 토큰 (탈취 시 재사용 가능) | MTLS 또는 OIDC 하이브리드 바인딩 | 완전한 송신자 구속 토큰 (Sender-Constrained) |
| 인가 요청 전송 | 프런트채널 브라우저 쿼리스트링 | Request Object (JWS 서명 객체) | Pushed Authorization Requests (PAR 필수) |
| 응답 데이터 무결성 | 서명 없음 (HTTPS 전송 의존) | JARM (JWS 응답 메시지 서명) | TLS 1.3 기본 전송 암호화 최적화 |
| 암호 스위트 통제 | CSP/서버 자유 설정 (취약 스위트 위험) | 엄격한 화이트리스트 암호 스위트 지정 | TLS 1.3 표준 최신 AEAD 알고리즘 강제 |

## Ⅴ. 마이데이터 전송 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| 정보주체의 동의 스코프보다 백엔드 DB에서 조회된 레거시 DTO 객체의 필드가 과도하여 API 응답에 비인가 데이터가 누출되는 과다 전송(Over-fetching) | API 게이트웨이 계층에 '동의-응답 데이터 사전 매핑 검증 인터셉터'를 구축하여, 토큰에 명시된 Claim Scope에 승인되지 않은 JSON 필드는 정규화 단계에서 자동 삭제(Drop) |
| 수십 개 마이데이터 사업자가 매일 자정 또는 특정 시간대에 대량 정기 전송(Batch Scraping)을 동시 호출하여 정보보유자 코어 시스템 장애 유발 | 분산 토큰 버킷(Token Bucket) 기반의 실시간 트래픽 쓰로틀링(Throttling) 및 기관별 Quota 제도를 운영하고, 대량 데이터는 Kafka 기반 비동기 대기열 배치 엔드포인트로 분리 |
| mTLS 통신을 위한 사업자 클라이언트 인증서가 만료되거나 침해 사고로 유출되었을 때 실시간 폐기 검증 지연 | 금융보안원 중계 센터의 CRL/OCSP Stapling 캐시를 API 게이트웨이에 1분 주기로 동기화하고, FAPI DPoP(RFC 9449)를 이중 적용하여 인증서 유출 피해 원천 차단 |
| 전송이 완료된 후 정보수신자(마이데이터 사업자)의 자체 DB 보안 취약점으로 인해 수집된 타사 고객 데이터가 대량 유출되는 공급망 위험 | 마이데이터 사업자 인프라에 대한 연례 ISMS-P 인증 의무화, 수집 데이터 저장 시 KMS 기반 필드 레벨 암호화 강제, 전송 이력 WORM 스토리지 5년 보존 |

## Ⅵ. 안전하고 지속 가능한 마이데이터 전송 아키텍처 제언

```text
[엔드투엔드 마이데이터 전송 보안 및 거버넌스 아키텍처]

 ┌─────────────────────────────────────────────────────────────┐
 │                 1. API 게이트웨이 보안 계층                   │
 │   - FAPI 2.0 PAR + mTLS 상호 인증 (X.509 검증)              │
 │   - DPoP 기반 송신자 구속 토큰 (Sender-Constrained) 강제    │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              2. 데이터 프라이버시 통제 계층 (Zero Over-fetch) │
 │   - 실시간 동의 스코프(Scope) 대조 필드 마스킹              │
 │   - 불필요 민감 필드 자동 드롭 (Data Minimization Filter)    │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │                 3. 인프라 탄력성 및 감사 계층                │
 │   - 분산 토큰 버킷 기반 기관별 Rate Limiting 및 Quota 제어  │
 │   - 블록체인/WORM 원장 기반 전송 이력 불변 로깅             │
 └─────────────────────────────────────────────────────────────┘
```

| 관리 영역 | 핵심 엔지니어링 세부 과제 | 통제 목표치 |
|---|---|---|
| 데이터 최소화 | 전송 동의 범위와 실제 반환 API JSON 필드의 100% 일치성 보장 | 동의 범위 초과 과다 전송 건수 0건 |
| 전송 가용성 | 대규모 마이데이터 호출 집중 시 코어 뱅킹 트래픽 보호 및 분산 | API 요청 성공률 > 99.99%, 지연 < 200ms |
| 토큰 무결성 | FAPI 준수 mTLS / DPoP 적용을 통한 토큰 탈취 재사용 차단 | 비인가 토큰 재생 공격 차단율 100% |

## 출제 이력과 검증 출처

- 제125회 정보관리기술사 예상 연계 주제: 개인정보 전송요구권 및 마이데이터 보안 표준
- OpenID Foundation: Financial-grade API (FAPI) 2.0 Security Profile
- IETF RFC 8705: OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens
- IETF RFC 9126: OAuth 2.0 Pushed Authorization Requests (PAR)
- 개인정보보호위원회: 본인정보 전송요구권 가이드라인 및 공공 마이데이터 보안 규격
- 금융보안원: 금융분야 마이데이터 서비스 보안 가이드라인
