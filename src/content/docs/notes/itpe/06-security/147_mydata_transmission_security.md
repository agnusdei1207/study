## 연관 키워드

- 마이데이터, 전송요구권, 개인신용정보, 스크래핑, 표준 API
- 상호 TLS(mTLS), OAuth 2.0, FAPI, 접근 토큰, 스코프
- 필드 단위 암호화, 이상전송거래 탐지, 전송 데이터 최소화

## Ⅰ. 마이데이터 전송 보안의 개요

- 핵심 요약 : 정보주체의 전송요구에 따라 데이터가 이동하는 과정에서 기밀성, 무결성, 인증·인가를 보장하는 전송 보안 체계.
- 개념 : 금융 등 분야에서 정보주체의 **전송요구권** (정보주체가 자신의 데이터를 제3자에게 전송하도록 요구할 수 있는 권리)에 따라 정보제공자와 **마이데이터 사업자** (수신자) 사이에 개인신용정보를 전송할 때, 그 구간과 인가 절차를 보호하는 보안 아키텍처.
- 배경 및 필요성 : 2020년 개정 신용정보법은 이용자의 인증 정보를 사업자가 보관하는 **스크래핑** (Screen Scraping) 방식 대신 **표준 API** (Application Programming Interface)로 데이터를 받도록 방향을 정하였다. 스크래핑은 이용자 인증 정보가 사업자에게 남고 수집 범위가 과도해지는 문제가 있었기 때문이다.
- 주요 목적 : 스크래핑을 대체하는 표준 API 전송 체계를 정착시키고, 정보주체가 동의한 최소 범위의 데이터만 위변조와 유출 없이 전달.

## Ⅱ. 마이데이터 전송 보안의 특징 및 장점

- 핵심 요약 : 인증 정보를 사업자가 갖지 않는 토큰 기반 구조와 채널 상호 인증이 결합되어, 데이터 이동성과 프라이버시를 함께 얻는 방식.

1. 토큰 기반 인가 : **OAuth 2.0** (Open Authorization 2.0)의 인가 코드와 접근 토큰을 쓰면 사업자가 이용자 비밀번호를 보관하지 않음 → 인증 정보 유출면이 줄어듦.
2. 범위와 기간 지정 : 정보주체가 조회 항목(스코프)과 기간을 정하면 그 범위의 짧은 수명 토큰만 발급 → 과도한 데이터 수집 방지.
3. 상호 인증 채널 : **상호 TLS** (mTLS, Mutual Transport Layer Security)는 양측이 인증서를 서로 제시해 검증하므로 서버만 확인하는 일반 TLS보다 비인가 접속을 막기 쉬움 → 중간자 도청 위험 감소.
4. 필드 단위 암호화 : 주민등록번호 같은 고유식별정보는 페이로드 안에서 별도로 암호화 → 채널이 뚫려도 핵심 항목 노출 최소화.

## Ⅲ. 마이데이터 전송 보안의 구조 (흐름)

- 핵심 요약 : 본인 확인과 인가를 거친 뒤 상호 인증된 채널에서 토큰으로 API를 호출하는 3단계 흐름.

```text
[ 마이데이터 전송 흐름 ]

(1) 정보주체: 전송요구 및 본인 확인
   ↓
(2) 수신자 → 정보제공자: 인가 후 접근 토큰 발급
   ↓
(3) 상호 TLS 채널 형성 후 API 호출
   ↓
정보제공자: 최소 항목만 암호화하여 응답
```

- 설계 원칙 : 전송 구간 암호화, 토큰 인가, 필드 단위 보호를 각각 독립된 통제로 두어 한 층이 뚫려도 다른 층이 데이터를 지키도록 구성한다.

## Ⅳ. 마이데이터 전송 방식의 비교

- 핵심 요약 : 표준 API 전송은 인증 정보 보관과 수집 범위에서 스크래핑과 구조적으로 다르다.

| 비교 항목 | 마이데이터 표준 API | 전통적 스크래핑 | 일반 웹 API 연동 |
| --- | --- | --- | --- |
| 인증 정보 보관 | 사업자는 토큰만 보관 | 사업자가 이용자 인증 정보를 보관 | 사업자별 API 키 관리 |
| 수집 범위 | 정보주체가 고른 최소 항목 | 화면 전체 데이터 수집 | 제공자 API 범위에 종속 |
| 접근 통제 | 토큰과 스코프 기반 인가 | 이용자 계정 권한을 대행 | IP 제한이나 토큰 |
| 채널 인증 | 상호 TLS 등 양측 인증 설계 | 서버 인증 중심 | 서버 인증 중심 |

- 선택 기준 : 데이터 이동권을 보장해야 하는 금융 분야에서는 표준 API를, 제공자 내부 연동에서는 일반 웹 API를 쓰되 인가 범위를 명확히 한다.

## Ⅴ. 마이데이터 전송 보안의 한계와 방안

- 핵심 요약 : 수신 사업자 보안, 토큰 탈취, 트래픽 집중을 인증 요건, 토큰 바인딩, 호출 제한으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 수신 사업자 내부 보안 취약 | 전송 구간이 안전해도 수신 측 내부망이 뚫리면 대량 개인정보가 유출됨 | 사업자 보안 인증 요건 강화와 정기 취약점 점검 | 점검 지적 사항 조치율 |
| 토큰 탈취와 재전송 | 접근 토큰이 로그나 메모리에서 노출되면 유효기간 동안 무단 조회 가능 | 인증서 바인딩 토큰 등 FAPI(Financial-grade API) 계열 프로파일 적용 | 토큰 재사용 탐지 건수 |
| 표준 API 트래픽 집중 | 다수 사업자의 일괄 조회가 제공자 백엔드 데이터베이스 부하를 높임 | 게이트웨이 단계의 호출 제한과 비동기 배치 분산 | API 응답 지연 시간 |

## Ⅵ. 마이데이터 전송 보안에 대한 기술사적 제언

- 핵심 요약 : 금융 중심으로 정착한 표준 API 체계를 다른 분야로 넓히되, 분야별 규격 차이를 줄이는 상호운용 기준을 먼저 세우는 방향.

1. 토큰 바인딩 기반의 고보증 프로파일 확대 : 장기적으로는 FAPI 계열의 메시지 서명과 토큰 바인딩을 전 API에 확대하여, 토큰이 다른 기기에서 쓰이지 못하도록 설계하는 것이 바람직하다.
2. 분야 간 상호운용 기준 마련 : 의료, 통신, 에너지 등으로 확장할 때 분야마다 다른 전송 규격이 생기지 않도록, 공통 인가 모델과 데이터 용어 사전을 정부가 주도해 정하는 것이 필요하다.
3. 이상 전송 감시 체계 도입 : 평소 패턴과 다른 대량 조회나 스코프를 벗어난 요청을 실시간으로 탐지하는 이상거래 탐지 기능을 전송 게이트웨이에 두어, 사업자 단위의 오남용을 조기에 차단한다.

## Ⅶ. 결론

- 핵심 요약 : 마이데이터 전송 보안은 데이터 이동권과 프라이버시를 토큰, 상호 인증, 최소 수집이라는 기술 규칙으로 함께 보장하는 모델.
- 시사점 : 스크래핑 퇴출 이후의 과제는 전송 구간보다 수신 측 관리와 분야 간 상호운용에 있으므로, 그 영역의 관리 체계가 함께 성숙해야 한다.
