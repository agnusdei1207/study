## Ⅰ. 마이데이터 전송 보안의 개요

- 개념 : 금융, 공공, 의료 등 전 분야 마이데이터 생태계에서 정보주체의 개인정보 **자기결정권** 행사에 따라 정보제공자, 중계기관, **마이데이터 사업자** (수신자) 간에 개인신용정보 및 본인 데이터를 전송할 때 데이터의 기밀성, 무결성, 안전한 인증·인가를 보장하는 **엔드-투-엔드 전송 보안** 아키텍처.
- 배경 및 필요성 : 과거 금융 핀테크 서비스에서 관행적으로 사용하던 **스크래핑** (Screen Scraping) 방식은 이용자의 공인인증서 비밀번호를 사업자가 직접 저장해야 하는 보안 맹점과 과도한 데이터 수집 문제를 초래하여 법적으로 전면 금지됨.
- 핵심 목적 : 스크래핑을 퇴출하고 표준화된 OpenAPI와 강력한 전송 계층 보안을 도입하여, 정보주체가 동의한 범위 내의 최소 데이터만을 위변조 및 유출 없이 안전하게 전송.

## Ⅱ. 마이데이터 전송 보안의 핵심 아키텍처 및 동작 메커니즘

마이데이터 전송 보안은 상호 TLS(mTLS), OAuth 2.0 기반 인가 프레임워크, **금융보안원 종합포털** 연계, 본인확인 및 전자서명 체계로 구축됨.

```text
[ 마이데이터 표준 API 전송 보안 아키텍처 및 통신 메커니즘 ]

 [정보주체 (사용자 앱)]
   | (1) 전송요구권 행사 및 본인인증 (사설인증서 전자서명)
   v
 [마이데이터 사업자 (수신자)] <===================> [금융보안원 종합포털]
   |                                                   * 기관별 등록/인가 관리
   | (2) 접근 토큰(Access Token) 발급 요청              * 서비스 적합성 심사
   v     (OAuth 2.0 Authorization Code Flow)
 [정보제공자 (은행/카드/보험사)]
   * 종합포털 검증: 인가된 사업자 여부 실시간 확인
   * 인가 코드 및 토큰 발급
   |
   | (3) 데이터 전송 요청 (RESTful OpenAPI)
   |  ==============================================================
   |  * 상호 TLS (Mutual TLS: mTLS 1.3) 전송 채널 형성
   |    - 양 당사자 금융 전용 X.509 보안 인증서 상호 검증
   |    - MITM 도청 원천 차단
   |  * HTTP Authorization 헤더에 OAuth 2.0 Bearer 토큰 탑재
   |  * 전송 데이터: 민감정보 필드 단위 암호화 (ARIA / AES-256)
   |  ==============================================================
   v
 [정보제공자 Core DB] ---> 안전한 JSON 응답 ---> [마이데이터 사업자 저장소]
                            * 암호화 보관 / 개인정보 분리 보관 원칙 준수
```

- **스크래핑 금지 및 표준 API 의무화** : 취약한 ID/PW 저장 기반 웹 스크래핑을 전면 배제하고, 표준화된 JSON RESTful API만을 통해 정형화된 데이터 전송을 강제.
- **상호 전송 계층 보안(mTLS: Mutual TLS)** : 클라이언트만 서버를 검증하는 일반 TLS와 달리, 정보제공자와 마이데이터 사업자 양측 모두 금융보안원이 발급한 전용 상호인증서를 제시하고 검증하여 비인가 접근을 원천 차단.
- **OAuth 2.0 인가 프레임워크** : 정보주체가 특정 범위(Scope)와 기간(Expiration)을 지정하여 데이터 조회를 인가하면, 시스템은 암호화된 짧은 수명의 일회용 접근 토큰(Access Token)을 발급하여 API 호출.
- **전송 데이터의 이중 암호화** : 전송 구간 mTLS 암호화 외에도 주민등록번호, 계좌번호 등 고유식별정보 및 금융 민감 데이터는 페이로드 내부에서 필드 단위(Field-level)로 대칭키 암호화(AES/ARIA) 수행.

## Ⅲ. 마이데이터 전송 보안의 세부 구성 요소 및 비교 분석

| 비교 항목 | **마이데이터 표준 API 전송** | **전통적 스크래핑** (Screen Scraping) | **단순 웹 API 전송** |
| --- | --- | --- | --- |
| 자격증명 보관 | 사업자가 비밀번호 일절 보관 안 함 (토큰) | 사업자가 이용자 공인인증서/비밀번호 저장 | API 키(Secret Key) 하드코딩 저장 |
| 통신 채널 보안 | 상호 TLS (mTLS 1.2/1.3) 의무화 | 단방향 SSL/TLS (서버만 인증) | 일반 HTTPS (단방향 인증) |
| 데이터 수집 범위 | 정보주체가 선택한 최소 항목만 전송 | 화면 전체 텍스트 무차별 긁어오기 (과다) | 제공자 API 구현 범위에 종속 |
| 보안성 심사 | 금융보안원 서비스 취약점 점검 필수 | 보안성 검증 체계 전무 (음성적 활용) | 자체 테스트 위주 (공인 검증 부재) |
| 접근 통제 | OAuth 2.0 인가 코드 및 스코프 제어 | 사용자 계정 권한 전체를 대행 | 단순 IP 화이트리스트 또는 토큰 |

- 마이데이터 전송 보안은 데이터 이동권 보장과 프라이버시 보호라는 상반된 가치를 mTLS와 OAuth 2.0이라는 기술적 표준으로 조화시킨 현대 데이터 경제의 보안 표준 모델임.

## Ⅳ. 마이데이터 전송 보안의 주요 한계점 및 해결 방안

- 중계기관 및 마이데이터 사업자의 영세성에 따른 단말/내부 보안 취약 :
  - 한계점 : 전송 구간은 mTLS로 완벽히 암호화되나, 데이터를 수신한 중소 마이데이터 사업자의 내부망 침해 시 대규모 개인정보 일괄 유출 위험.
  - 해결 방안 : 마이데이터 사업자 진입 시 ISMS-P 인증 취득 의무화 및 금융보안원 연 1회 보안 취약점 점검 및 상시 보안성 평가제 도입.
- OAuth 2.0 토큰 탈취 및 재전송(Replay) 리스크 :
  - 한계점 : 발급된 Access Token이 네트워크 장비 로그나 메모리에서 탈취될 경우 유효기간 동안 비인가 데이터 대량 조회가 가능한 한계.
  - 해결 방안 : OAuth 2.0 FAPI(Financial-grade API) 보안 프로파일을 적용하여 클라이언트 인증서 바인딩 토큰(MTLS-bound Access Tokens) 의무화.
- 표준 API 트래픽 폭증에 따른 금융사 기간계 시스템 과부하 :
  - 한계점 : 수백 개의 마이데이터 사업자가 정기적으로 일괄 데이터 조회를 호출함에 따라 금융사 백엔드 DB의 가용성 저하 발생.
  - 해결 방안 : API 게이트웨이 레벨의 지능형 트래픽 쓰로틀링(Throttling), 속도 제한(Rate Limiting), 비동기 배치 전송 분산 설계.

## Ⅴ. 마이데이터 전송 보안 적용 및 발전을 위한 기술사적 제언

- 금융보안 FAPI 2.0(Financial-grade API) 표준으로의 선제 전환 : 기존 OAuth 2.0 수준을 넘어 암호학적 비부인성과 종단간 메시지 서명을 보장하는 FAPI 2.0 보안 프로파일을 전사 API 아키텍처에 구현.
- 전 분야 마이데이터 확산에 따른 이종 산업 간 상호운용성 표준 정립 : 금융을 넘어 통신, 의료, 에너지 마이데이터로 확장 시 각 부처별 상이한 전송 규격을 단일한 개인정보보호위원회 표준 전송 체계로 통합 일원화.
- 이상전송거래탐지시스템(FDS) 및 AI 기반 전송 데이터 모니터링 : 특정 마이데이터 사업자가 비정상적인 심야 시간에 대량의 데이터 전송을 요구하거나 스코프를 초과하는 조회를 시도할 때 즉시 자동 차단하는 AI 이상징후 관제 체계 가동.
