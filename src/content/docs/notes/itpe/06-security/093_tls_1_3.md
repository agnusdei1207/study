## 연관 키워드

- TLS 1.3, 핸드셰이크, 1-RTT, 0-RTT, PFS, AEAD, PSK, RFC 8446
- ECH, SNI, 재생 공격, 하이브리드 키 교환, ML-KEM, 양자 내성 암호(PQC)

## Ⅰ. TLS 1.3의 개요

- 핵심 요약 : 취약한 암호 선택지를 없애고 핸드셰이크를 단축한 전송 계층 보안(TLS, Transport Layer Security)의 최신 표준 규격.
- 개념 : 전송 계층 위에서 데이터의 기밀성, 무결성, 서버 인증을 보장하는 암호화 통신 프로토콜인 TLS(Transport Layer Security)의 최신 버전으로, IETF(Internet Engineering Task Force)가 RFC 8446(2018)으로 표준화함.
- 배경 및 필요성 : 이전 버전에는 CBC(Cipher Block Chaining) 모드와 정적 RSA(Rivest-Shamir-Adleman) 키 교환 같은 취약 요소가 남아 있었고, 2회 왕복(2-RTT, Round-Trip Time)이 필요한 핸드셰이크는 연결 지연의 원인이었음. 이를 해결하기 위해 설계됨.
- 주요 목적 : 레거시 취약 암호 제거로 구조적 안전성을 확보하고, 핸드셰이크를 단축해 지연을 줄이며, 핸드셰이크 메시지 자체도 암호화하는 것.

## Ⅱ. TLS 1.3의 특징 및 장점

- 핵심 요약 : 선택지를 줄이고 핸드셰이크를 단축해, 안전성과 지연 시간을 함께 개선한 설계.

1. 1-RTT 핸드셰이크 : 키 합의를 한 번의 왕복에 끝내 → 연결 설정 지연이 줄어듦.
2. **PFS** (Perfect Forward Secrecy, 완전 순방향 비밀성으로 장기 키가 유출되어도 과거 세션을 복호화할 수 없는 성질) : 임시 키 교환만 허용 → 과거 통신 기록 보호.
3. **AEAD** (Authenticated Encryption with Associated Data, 인증된 암호화) 전용 : 암호화와 변조 탐지를 한 번에 제공하는 방식만 허용 → 암호 조합 실수에 따른 취약점이 줄어듦.
4. 핸드셰이크 암호화 : 서버 인증서를 암호화해 전송 → 인증서 정보에 대한 도청이 어려워짐.

## Ⅲ. TLS 1.3의 구조 (흐름)

- 핵심 요약 : 첫 왕복에서 키를 합의하고 이후 메시지를 모두 암호화하는 1-RTT 흐름이 기본이며, 재개 연결은 0-RTT로 단축됨.

```text
[ TLS 1.3 핸드셰이크 (1-RTT) ]

클라이언트 → 서버
ClientHello (키 공유 값 포함)
              ↓
서버 → 클라이언트
ServerHello (키 공유 값 포함)
[ 이후 메시지는 핸드셰이크 키로 암호화 ]
인증서, 인증서 검증, Finished
              ↓
클라이언트 → 서버
Finished
              ↓
애플리케이션 데이터 (AEAD 암호화)
```

```text
[ 세션 재개 (0-RTT) ]

클라이언트 → 서버
ClientHello + 조기 데이터 (PSK 기반)
              ↓
서버: 재전송 여부 검사
              ↓
정상 요청이면 처리, 아니면 거부
```

1. ClientHello : 지원 암호 목록과 키 공유 값(key_share)을 전송.
2. ServerHello : 암호 방식을 선택하고 서버의 키 공유 값을 응답해 세션 키를 합의.
3. Finished : 주고받은 메시지 전체의 해시에 대해 메시지 인증 코드(MAC, Message Authentication Code)를 계산해 위변조 여부 검증.
4. **0-RTT** (Zero Round-Trip Time, 재개 연결에서 첫 메시지에 데이터를 실어 보내는 방식) : 사전 공유 키(PSK, Pre-Shared Key)를 이용하며, 재생 공격에 노출되는 구조적 한계를 가짐.

## Ⅳ. TLS 1.3과 TLS 1.2의 비교

- 핵심 요약 : TLS 1.2의 선택 가능한 조합을 대폭 줄여, 허용되는 암호 구성 자체를 안전한 것으로 한정.

| 비교 항목 | TLS 1.2 (RFC 5246) | TLS 1.3 (RFC 8446) |
| --- | --- | --- |
| 기본 핸드셰이크 | 2-RTT 후 데이터 전송 | 1-RTT 후 데이터 전송 |
| 세션 재개 | Session ID, Session Ticket | PSK 기반 0-RTT 조기 데이터 |
| 키 교환 | 정적 RSA, 정적 DH, DHE, ECDHE 혼용 | 임시 키 교환(DHE, ECDHE)만 허용 |
| 암호 방식 | CBC, RC4, 3DES 등 다양한 조합 | AEAD 전용 (AES-GCM, ChaCha20-Poly1305 등) |
| 인증서 노출 | 서버 인증서가 평문으로 전송 | 핸드셰이크 이후 암호화 전송 |
| 알려진 공격 | POODLE, BEAST, CRIME, ROBOT 등 취약점 존재 | 취약 기능 제거로 해당 공격 벡터 차단 |

## Ⅴ. TLS 1.3의 한계와 방안

- 핵심 요약 : 재생 공격, 보안장비 가시성 상실, 접속 도메인 노출, 양자 컴퓨터 위협을 재생 방지, 정책 기반 복호화, 암호화 클라이언트 헬로, 하이브리드 키 교환으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 0-RTT 재생 공격 | 공격자가 조기 데이터를 가로채 서버에 반복 전송 | 멱등성이 보장되는 GET 요청만 0-RTT 허용, 서버 측 재생 방지(Anti-Replay) 캐시 적용 | 재생 요청 탐지 건수 |
| 보안장비 가시성 상실 | 암호화 구간 증가로 차세대 방화벽(NGFW, Next-Generation Firewall), 침입방지시스템(IPS), 데이터 유출 방지(DLP) 장비의 내용 검사 불가 | 엔드포인트 EDR 로깅 강화와 개인정보 기준에 따른 승인을 거친 정방향 TLS 프록시 기반 검사 | 복호화 검사 대상 비율 |
| SNI 노출 | ClientHello의 SNI(Server Name Indication) 필드가 평문이라 접속 도메인이 도청자에게 노출 | DNS 조회로 얻은 공개 설정을 이용해 ClientHello 전체를 암호화하는 ECH(Encrypted Client Hello) 적용 | ECH 지원 연결 비율 |
| 양자 컴퓨터 위협 | 쇼어 알고리즘(Shor's algorithm)에 의해 ECDHE와 RSA, ECDSA 기반 키 교환과 서명이 무력화될 가능성 | X25519와 ML-KEM(Module-Lattice-Based Key-Encapsulation Mechanism)을 결합한 **하이브리드 키 교환** (X25519MLKEM768) 적용 | 하이브리드 키 교환 지원 비율 |

## Ⅵ. TLS 1.3에 대한 기술사적 제언

- 핵심 요약 : 프로토콜 기본값, 프라이버시, 양자 대비를 운영 정책으로 묶어 전환 계획을 세워야 함.

1. 프로토콜 정책 : 웹 서버와 API 게이트웨이에서 TLS 1.2 이하를 비활성화하고, 0-RTT는 안전한 요청으로 한정하는 설정 기준 필요.
2. 접속 프라이버시 : ECH와 DNS 암호화를 함께 도입해 이용자의 접속 도메인 정보를 보호하는 네트워크 설계 필요.
3. 양자 대비 : 하이브리드 키 교환을 지원하는 TLS 구현체를 도입하고, 지금 수집해 나중에 해독하는 공격(HNDL, Harvest Now, Decrypt Later)에 대비하는 암호 전환 계획을 수립 필요.

## Ⅶ. 결론

- 핵심 요약 : TLS 1.3은 취약한 선택지를 없애고 1-RTT 핸드셰이크를 기본값으로 만든 표준 전송 암호화 체계임.
- 시사점 : 프로토콜 자체보다 운영 정책과 양자 대비 전환 계획이 실제 보안 수준을 결정함.
