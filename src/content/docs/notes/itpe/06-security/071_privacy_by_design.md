## 답안 골격
```text
[개인정보보호 중심 설계(PbD)] ◀━━ 머리: Ⅶ 내 의견 (사후 동의 체크박스 탈피 → 기획·설계 단계부터 기본값 프라이버시(Privacy by Default) 및 최소 수집 내재화)
 ┃
 ┣━ Ⅰ 개요 ───── 사후적 규제 준수나 침해사고 후 땜질식 대응의 한계 극복 → IT 시스템 기획·설계·개발 생애주기 전반에 프라이버시 보호를 기본 탑재(Ann Cavoukian 제안)
 ┣━ Ⅱ 특징 ───── 7대 기본 원칙(사전예방, 기본값 프라이버시, 라이프사이클 전반 보호, 투명성 등) · 제로섬 탈피(포지티브섬) · GDPR 법제화(제25조)
 ┣━ Ⅲ 구조 ───── 7대 기본 원칙(사전예방, 기본설정, 설계내재, 포지티브섬, 생애주기 보호, 가시성/투명성, 사용자 존중) · 기술적 구현 기법(PET, 비식별화, 암호화)
 ┣━ Ⅳ 흐름 ───── ① 서비스 기획 및 프라이버시 영향평가(PIA) → ② 최소 수집 및 기본값 비공개 설계 → ③ 가명화/암호화 구현 → ④ 데이터 수명주기 만료 시 파기 검증
 ┣━ Ⅴ 비교 ───── 사후 보안 조치(Reactive: 시스템 완성 후 체크박스 추가, 유출 사고 후 패치) vs PbD(Proactive: 데이터 수집 자체를 최소화하고 기본 설정을 비공개로 구현)
 ┗━ Ⅵ 실무 ───── 마케팅 부서의 과도한 데이터 수집 요구와의 갈등 / 디폴트 설정(Opt-in vs Opt-out) 충돌 / AI 학습 데이터 파이프라인 PbD 적용
```
- 필수 키워드: Privacy by Design(PbD) · Ann Cavoukian · 7대 원칙 · Privacy by Default · 사전예방(Proactive) · 포지티브섬(Positive-Sum) · 개인정보 영향평가(PIA)
- 기출: 133회 2교시 5번 `PbD(Privacy by Design)의 개념과 7대 기본 원칙, ICT 분야 적용 방안` → Ⅰ~Ⅶ 전반 완벽 대응

## 한 줄 본질
- 시스템 구축 완료 후 개인정보 보호를 덧붙이려다 발생하는 설계 변경 비용과 유출 위험 병목 → IT 시스템의 초기 기획·아키텍처 설계 단계부터 프라이버시 보호 메커니즘을 기본값(Default)으로 내재화 → 사전 침해 예방 및 규제 면책 / 초기 개발 기획 기간 및 설계 검토 공수 발생

```text
[Ann Cavoukian의 Privacy by Design(PbD) 7대 기본 원칙]

 ├────────────────────────────────────────────────────────┤
 │ 2. 기본값으로서의 프라이버시 (Privacy as the Default)  │
 ├────────────────────────────────────────────────────────┤
 │ 3. 설계에 내재화된 프라이버시 (Privacy Embedded)       │
 ├────────────────────────────────────────────────────────┤
 │ 4. 완전한 기능성: 포지티브 섬 (Positive-Sum, Win-Win)  │
 ├────────────────────────────────────────────────────────┤
 │ 5. 전 생애주기 종단간 보안 (End-to-End Security)       │
 ├────────────────────────────────────────────────────────┤
 │ 6. 가시성과 투명성 유지 (Visibility and Transparency) │

 └────────────────────────────────────────────────────────┘
```

## 핵심 용어
- 기본값으로서의 프라이버시(Privacy as the Default): 사용자가 별도의 보안 설정을 변경하지 않아도 시스템 기본 세팅 자체가 가장 높은 수준의 개인정보 보호(예: 마케팅 수신 거부, 프로필 비공개) 상태로 동작하는 원칙
- 포지티브 섬(Positive-Sum): "개인정보를 보호하면 서비스 기능이나 사용자 편의성이 떨어진다"는 제로섬(Zero-Sum) 편견을 거부하고, 혁신적 설계로 보안과 비즈니스 목표를 둘 다 달성하는 접근법

## 핵심 통찰
- PbD의 가장 위대한 원칙은 '최소 수집(Data Minimization)'임 → "수집하지 않은 데이터는 유출될 수도 없다"는 공학적 진리
- 사후에 법적 동의서에 체크박스 10개를 빽빽하게 넣는 것은 면피용 행정일 뿐 PbD가 아님 → 진짜 PbD는 회원가입 시 생년월일이나 성별 입력 필드 자체를 UI에서 없애는 것임
- EU GDPR은 제25조에 '설계 및 기본 설정에 의한 개인정보보호'를 법적 의무로 명문화하여, PbD를 지키지 않은 제품은 유럽 시장 출시 자체가 불가능해짐

## 이웃 토픽과 구분
- 시큐어 코딩 vs PbD: 시큐어 코딩 = 소스코드 버그 및 취약점 방지 / PbD = 데이터 흐름, 비즈니스 수집 목적, 사용자 권리 관점의 아키텍처적 설계 철학

## 문제·원인·대책
- 사례: 모바일 앱 설치 시 사용자의 사전 인지 없이 주소록과 위치 정보 권한을 기본 '허용' 상태로 요구하여 규제 기관의 철퇴를 맞은 사례
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 불필요한 스마트폰 권한 기본 수집 및 동의 강제 | 마케팅 활용 목적의 과도한 데이터 수집 기획 | 기능 수행에 필수적인 권한만 런타임에 동적으로 요청(JIT Consent) | 규제 위반 과징금 차단 및 사용자 신뢰도 제고 |
| 회원 탈퇴 후 백업 DB에 개인정보 영구 방치 | 데이터 수명주기(Lifecycle) 폐기 설계 누락 | 회원 탈퇴 이벤트 트리거 기반 백업/로그 데이터 파기 자동화 설계 | 데이터 보존 기한 위반 컴플라이언스 위험 해소 |

## 이렇게 출제된다
- 제133회 2교시 5번: "PbD(Privacy by Design)는 광범위한 네트워크 환경에서 발생할 수 있는 데이터 처리의 폐해를 방지하기 위해 창안된 개념이다. ICT 분야에 적용하기 위한 7대 기본원칙과 실무 적용 방안을 설명하시오." → 요구 포인트: Ⅰ 개념 및 배경 + Ⅲ 7대 기본원칙 상세 + Ⅵ ICT(클라우드, 모바일, AI) 적용 대책

## 내 의견
- [다크 패턴(Dark Pattern)을 통한 동의 유도 관행] 가입 시 '모두 동의' 버튼을 강조하고 마케팅 정보 제공 동의를 교묘하게 묶어 사용자를 속이는 기만적 UI 디자인 만연 → 나라면: 신규 서비스 기획 단계에서 프라이버시 전담 아키텍트(PIA 전문가)의 서명이 없으면 스프린트 개발에 착수할 수 없도록 사내 거버넌스를 확립하고, 동의 UI는 명시적 선택(Opt-in)만 허용하는 PbD 디자인 시스템 표준화

## 찾아볼 것
- ISO/IEC 27701(개인정보보호 경영시스템) 내 PbD 구현 요구사항 및 개인정보보호위원회의 개인정보 중심 설계(PbD) 인증 가이드라인
