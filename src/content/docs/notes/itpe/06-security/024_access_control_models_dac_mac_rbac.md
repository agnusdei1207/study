## 지식 로드맵 내 현재 위치

보안 원칙 → 식별·인증·인가 → 접근통제 정책 모델(DAC, MAC, RBAC, ABAC)

## 30초 인출

- **본질:** 인증된 주체(Subject)가 정보시스템의 객체(Object)에 접근하여 특정 연산(Operation)을 수행할 권한을 보안 정책에 따라 판정하고 통제하는 체계
- **메커니즘:** 참조 모니터(Reference Monitor)가 보안 정책(소유자 재량, 보안 라벨, 역할, 속성)에 따라 접근 요청을 중재하고 감사 로그 기록
- 통찰: RBAC의 역할 폭발 및 권한 누적과 ABAC의 인가 지연 병목을 해결하기 위해 역할 마이닝 기반 정제와 OPA 엣지 인메모리 컴파일 결합 필수

<details>
<summary>핵심 용어</summary>

- **참조 모니터 (Reference Monitor):** 주체와 객체 사이의 모든 접근 요청을 중재하는 추상적 보안 기계 (완전중재, 격리보호, 검증가능성 3대 속성 충족)
- **DAC (Discretionary Access Control):** 객체의 소유자가 자신의 판단에 따라 다른 주체에게 접근 권한을 자유롭게 부여하고 회수하는 임의적 접근통제
- **MAC (Mandatory Access Control):** 시스템 관리자가 설정한 강제 보안 레이블(비밀등급)과 주체의 인가등급을 비교하여 커널이 강제하는 접근통제
- **RBAC (Role-Based Access Control):** 권한을 역할(Role)에 할당하고, 사용자에게 해당 역할을 부여함으로써 대규모 조직의 권한 관리를 단순화하는 통제
- **ABAC (Attribute-Based Access Control):** 주체, 객체, 행위뿐만 아니라 시간, 위치, 디바이스 등 환경 속성(Attribute)을 정책 규칙과 대조하는 차세대 동적 통제
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **접근통제 정책·모델(Access Control Policy/Model)** 은 식별 및 인증된 주체(사용자, 프로세스)가 시스템의 객체(파일, DB, 네트워크)에 대해 읽기·쓰기·실행 등의 작업을 수행할 수 있는 권한을 정의하고 집행하는 논리적 프레임워크 |
| 목적 | 정보자산의 기밀성·무결성·가용성 보장, 비인가 접근 차단, 최소 권한 보장 및 컴플라이언스 준수 |

주체 중심의 권한 부여에서 시작하여 대규모 조직의 역할 중심(RBAC), 최근 제로트러스트 환경의 실시간 속성 중심(ABAC)으로 진화.

## Ⅱ. 접근통제의 특징 및 3대 기본 원칙

### 1. 접근통제 3대 보안 원칙

| 보안 원칙 | 핵심 개념 | 적용 목적 |
|---|---|---|
| **최소 권한의 원칙**<br>(Principle of Least Privilege) | 업무를 수행하는 데 필요한 최소한의 권한만을 부여 | 계정 침해 시 피해 범위 최소화 |
| **직무 분리의 원칙**<br>(Separation of Duties) | 한 사람에게 단독으로 모든 권한을 부여하지 않고 다단계 승인 분리 | 내부 부정 및 고의적 시스템 파괴 예방 |
| **알 필요성의 원칙**<br>(Need-to-Know) | 직무 수행상 반드시 확인해야 할 정당한 이유가 있는 정보만 인가 | 불필요한 사내 민감 데이터 열람 차단 |

### 2. 참조 모니터(Reference Monitor) 3대 구현 요건

- **완전한 중재 (Complete Mediation):** 모든 접근 요청은 예외 없이 반드시 참조 모니터를 경유하는 원칙 준수.
- **격리 보호 (Tamperproof / Isolation):** 공격자나 비인가 프로세스가 참조 모니터의 코드나 정책 DB를 변조할 수 없도록 OS 커널 레벨에서 격리.
- **검증 가능성 (Verifiability):** 코드베이스가 작고 단순하여 수학적 정형 검증 및 보안 감사 가능성 보장.

## Ⅲ. 접근통제 4대 핵심 모델 아키텍처 및 메커니즘

```text
[접근통제 모델별 권한 결정 아키텍처 비교]

 1. DAC (임의적)      2. MAC (강제적)       3. RBAC (역할 기반)     4. ABAC (속성 기반)
+-------------+     +---------------+     +---------------+     +---------------+
| 소유자 재량 |     | 중앙 보안라벨 |     | 사용자(User)  |     | 주체/객체/환경|
| ACL / 행렬  |     | Bell-LaPadula |     |      ↓        |     | 속성(Attribute|
| chmod / NTFS|     | Biba 모델     |     | 역할(Role)    |     |      ↓        |
+------+------+     +-------+-------+     |      ↓        |     | XACML / Rego  |
       |                    |             | 권한(Perm)    |     | 동적 정책 규칙|
       v                    v             +-------+-------+     +-------+-------+
  [객체 접근]          [객체 접근]                v                     v
                                             [객체 접근]           [객체 접근]
```

### 1. 주요 모델별 엔지니어링 메커니즘

| 모델 | 권한 결정 기준 | 핵심 구현 기술 | 장단점 및 특징 |
|---|---|---|---|
| **DAC** | 객체 소유자가 생성한 ACL(Access Control List) | 파일시스템 퍼미션 (Linux `chmod`, Windows ACL) | 구현이 단순하고 유연하나, 트로이목마 및 권한 전파 통제 불가 |
| **MAC** | 주체의 클리어런스(Clearance)와 객체의 레이블(Label) 비교 | SELinux, AppArmor, 다중 등급 보안(MLS) | 보안성이 극도로 높으나 유연성이 결여되고 정책 관리 부담 극심 |
| **RBAC** | 조직 내 부여된 직무 역할(Role) | Active Directory 그룹, AWS IAM Role, K8s RBAC | 관리가 직관적이고 직무분리 적용 용이하나, 역할 폭발 위험 |
| **ABAC** | 주체/객체/환경 속성을 조합한 불리언 규칙 | XACML 3.0, OPA(Open Policy Agent) Rego | 초정밀 동적 제어 가능하나 정책 복잡도 및 연산 부하 증가 |

## Ⅳ. 접근통제 모델 4자 심층 비교

| 비교 항목 | DAC (임의적) | MAC (강제적) | RBAC (역할 기반) | ABAC (속성 기반) |
|---|---|---|---|---|
| **통제 주체** | 데이터 소유자 (User) | 보안 관리자 (System) | 조직 관리자 (Role) | 정책 관리자 (Policy) |
| **권한 결정 시점** | 정적 (ACL 조회) | 정적 (라벨 비교) | 정적 (역할 매핑) | **동적 (런타임 속성 평가)** |
| **상황 인지 능력** | 없음 (고정 권한) | 없음 (고정 라벨) | 없음 (역할 기반) | **우수 (시간, IP, 기기 상태 반영)** |
| **확장성** | 낮음 (사용자 증가 시 복잡) | 보통 (군사/정부 특화) | 우수 (엔터프라이즈 표준) | **최상 (클라우드/API 분산 환경)** |
| **보안 강도** | 낮음 | 매우 높음 | 보통~높음 | 높음 (제로트러스트 부합) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| **RBAC의 역할 폭발(Role Explosion) 및 권한 누적(Privilege Creep)**<br>조직 규모 확장 및 세분화된 업무 예외 처리로 인해 사용자 수보다 역할 수가 많아지고, 부서 이동 시 기존 역할이 회수되지 않고 누적되는 보안 구멍 발생 | **역할 마이닝(Role Mining) ML 정제 및 권한 재인증(Access Certification)**<br>실제 사용자 접근 로그를 클러스터링하여 중복·유휴 역할을 통폐합하는 역할 마이닝을 분기별 수행하고, 분기마다 부서장에게 소속원의 역할 유지 필요성을 강제 결재받는 자동화 워크플로우 운영 |
| **ABAC의 복잡한 XACML 정책 평가로 인한 분산 인가 레이턴시 병목**<br>대규모 마이크로서비스(MSA) 환경에서 수십 개의 속성을 외부 IdP에서 실시간 조회하여 XACML PDP에서 평가할 경우 수십 ms의 지연이 발생해 API 통신 마비 | **OPA(Open Policy Agent) 인메모리 컴파일 및 엣지 캐싱(Sidecar)**<br>선언형 언어인 Rego 기반의 OPA를 서비스 메시(Envoy)의 사이드카 프록시로 임베딩하여 로컬 메모리에서 서브 밀리초(sub-ms) 단위로 정책을 직접 평가하고, 만료시간(TTL) 기반 속성 캐싱 적용 |

## Ⅵ. 제언

```text
[현대 엔터프라이즈를 위한 RBAC + ABAC 하이브리드 거버넌스]

 +--------------------+     +---------------------+     +--------------------+
 | 기본 권한: RBAC    | --> | 동적 제한: ABAC     | --> | 실시간 컨텍스트 인가|
 | 직무별 거시적 권한 |     | IP, 단말상태, 시간대|     | 제로트러스트 달성  |
 | (HR 시스템 연동)   |     | (EDR/위치 연동)     |     | (미인가 환경 차단) |
 +--------------------+     +---------------------+     +--------------------+
```

| 접근통제 계층 | 구현 기술 및 모델 | 적용 정책 예시 |
|---|---|---|
| **거시적 접근통제 (Coarse-grained)** | RBAC (IAM 그룹 및 역할) | "재무팀 직원은 결제 API에 접근할 수 있다." |
| **미시적 접근통제 (Fine-grained)** | ABAC (OPA / 조건부 액세스) | "단, 사내 VPN 경유 및 보안 승인된 단말에서 업무시간에만 가능하다." |

거버넌스 관리가 용이한 RBAC으로 기본 직무 역할을 배정하고, 실행 시점에는 상황적 위험을 평가하는 ABAC 조건을 오버레이하는 하이브리드 인가 아키텍처 구축 권장.
