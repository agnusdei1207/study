## Ⅰ. 접근통제 모델(DAC·MAC·RBAC)의 개요

- 핵심 요약 : 주체의 객체 접근을 권한 결정 방식에 따라 DAC·MAC·RBAC·ABAC로 나누어 통제하는 정보보안 기법.
- 개념 : 정보 자산(객체, Object)에 대해 식별된 사용자(주체, Subject)가 허가된 작업(읽기, 쓰기, 실행)만 수행하도록 규칙을 정하고 강제하는 **접근통제** (Access Control).
- 배경 및 필요성 : 다중 사용자 운영체제와 대규모 기업 정보시스템에서 비인가자의 정보 유출, 무단 변조, 권한 오남용 위험이 커져, 주체와 객체 사이의 권한 관계를 모델로 체계화할 필요가 생김.
- 주요 목적 : 기밀성과 무결성 보장, **최소 권한 원칙** (Least Privilege, 업무 수행에 필요한 최소한의 권한만 부여) 실현, 권한 관리 효율과 **감사 추적성** (Auditability, 누가 어떤 접근을 했는지 추적할 수 있는 성질) 확보.

## Ⅱ. 접근통제 모델(DAC·MAC·RBAC)의 특징 및 장점

- 핵심 요약 : 권한 결정 주도권에 따라 모델이 나뉘고, 모델별 통제 기준이 보안 강도와 관리 편의성의 차이로 이어지는 구조.

1. **DAC** (Discretionary Access Control, 임의적 접근통제) : 소유자가 ACL (Access Control List, 접근제어목록)로 권한을 재량 설정 → 설정이 유연하고 도입 비용이 낮음.
2. **MAC** (Mandatory Access Control, 강제적 접근통제) : 시스템이 주체와 객체에 보안 레이블 (Label)을 부여하고 중앙 정책으로 강제 → 임의 권한 전파가 차단되어 기밀성 보장 강도가 높음.
3. **RBAC** (Role-Based Access Control, 역할기반 접근통제) : 권한을 직무 역할에 매핑하고 사용자를 역할에 배속 → 대규모 조직의 권한 관리가 단순해지고 **SoD** (Separation of Duties, 상충 업무를 한 주체에게 겹치지 않게 나누는 직무 분리) 구현이 쉬워짐.
4. **ABAC** (Attribute-Based Access Control, 속성기반 접근통제) : 주체·객체·환경 속성을 정책으로 동적 평가 → 시간, 위치, 디바이스 같은 상황을 반영한 정밀 통제.

## Ⅲ. 접근통제 모델(DAC·MAC·RBAC)의 구조 (흐름)

- 핵심 요약 : 권한 결정 주도권이 소유자에서 중앙 정책, 역할, 속성 순으로 이동하며, 모델마다 판정 경로가 다른 구조.

```text
[ 권한 결정 주도권의 이동 ]

DAC (소유자 재량)
   ↓
MAC (중앙 보안 정책)
   ↓
RBAC (직무 역할 매핑)
   ↓
ABAC (속성 동적 평가)
```

- **BLP** (Bell-LaPadula, 기밀성 모델) : 주체 등급이 객체 등급보다 낮으면 읽기를 막는 No Read Up 규칙과, 높은 등급 정보가 낮은 등급 객체로 흐르지 않게 하는 No Write Down 규칙으로 기밀성 보장.
- **Biba** (무결성 모델) : 낮은 등급 데이터를 읽지 않고 높은 등급 객체에 쓰지 않게 하는 No Read Down, No Write Up 규칙으로 무결성 보장.

```text
[ BLP 읽기 판정 ]

주체 등급 : 비밀
   ↓ 객체 등급과 비교
객체 등급 : 극비
   ↓ 주체 등급이 낮아 거부
읽기 차단 (No Read Up)
```

```text
[ RBAC 권한 할당 흐름 ]

사용자 (홍길동)
   ↓ 역할 할당
역할 (회계팀장)
   ↓ 권한 할당
권한 (전표 승인, 급여 조회)
```

```text
[ ABAC 동적 판정 ]

주체 속성 : 보안팀
   ↓
환경 속성 : 근무시간, 사내 IP
   ↓
객체 속성 : 민감도 중
   ↓
정책 엔진 판정 → 허용 또는 거부
```

## Ⅳ. 접근통제 모델(DAC·MAC·RBAC)의 비교

- 핵심 요약 : 권한 결정 주체와 통제 기준이 달라 보안 강도와 관리 복잡도가 상충하므로, 단독 선택보다 조직 요구에 맞춘 조합이 필요.

| 비교 축 | DAC | MAC | RBAC | ABAC |
| --- | --- | --- | --- | --- |
| 권한 결정 주체 | 데이터 소유자 | 중앙 보안 관리자 | 직무 설계자 | 중앙 정책 엔진 |
| 통제 기준 | 신원과 ACL | 보안 레이블 | 사용자의 역할 | 주체·객체·환경 속성 |
| 보안 강도 | 낮음 (권한 전파 위험) | 매우 높음 (엄격한 강제) | 높음 (최소 권한, 직무 분리) | 매우 정밀한 동적 통제 |
| 관리 복잡도 | 사용자·파일 증가 시 급증 | 라벨링과 정책 수립 비용 높음 | 대규모 조직에서 단순화 | 정책 규칙 복잡도 증가 |
| 대표 적용처 | Windows·Linux 파일 권한 | SELinux, 군사 보안체계 | 기업 ERP (Enterprise Resource Planning), 포털 | 클라우드 IAM (Identity and Access Management) |

- 선택 기준 : 단일 모델보다 RBAC으로 대분류 역할을 두고 ABAC으로 세부 조건을 더하는 융합 방식이 클라우드와 제로트러스트 환경에서 널리 쓰임.

## Ⅴ. 접근통제 모델(DAC·MAC·RBAC)의 한계와 방안

- 핵심 요약 : 모델별 고유 한계를 권한 전파 차단, 역할 축소, 등급 해제 절차로 보완하여 통제 강도와 업무 유연성을 함께 확보.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| DAC의 **트로이 목마** (Trojan Horse) 권한 탈취 | 소유자가 권한을 임의로 부여하므로 악성 프로그램이 소유자 권한을 대리 실행, 비밀 파일 읽기 권한이 외부로 전파 | 중요 자산에 커널 수준 강제 통제(SELinux, AppArmor)를 적용해 프로세스 행위 격리 | 권한 변경 감사 이상 건수 |
| **역할 폭증** (Role Explosion) | 예외 권한 요구가 늘어 역할 수가 사용자 수보다 빠르게 증가하고 관리가 어려워짐 | 정적 역할을 최소화하고 시간·위치·프로젝트 상태를 평가하는 ABAC 속성 정책과 결합 | 사용자 대비 역할 수 비율 |
| MAC의 경직성 | 지정된 보안 등급을 임의로 바꿀 수 없어 긴급 협업과 데이터 개방에 장애 발생 | 신뢰된 주체에 한해 등급을 낮추는 **등급 해제** (Declassification) 절차를 두고, **CDS** (Cross Domain Solution, 망 간 안전한 데이터 전달 장치)와 연계 | 등급 조정 요청 처리 시간 |

## Ⅵ. 접근통제 모델(DAC·MAC·RBAC)에 대한 기술사적 제언

- 핵심 요약 : 역할 기반 통제를 상황 인식형 정책으로 확장하고 권한 감사를 상시 체계로 운영해, 접근통제를 일회성 설정이 아닌 지속 관리 대상으로 전환.

1. 제로트러스트 전환 : 정보보안 부서가 접근통제 모델을 제로트러스트 원칙에 맞춰 단계적으로 재설계하고, 단말 위험도와 접속 위치를 정책 결정점(PDP, Policy Decision Point)에서 함께 판단하는 **PBAC** (Policy-Based Access Control, 정책 기반 접근통제) 도입 범위를 정하는 것이 필요.
2. 권한 상시 감사 : 인사·감사 부서가 직무 분리 기준을 정하고 권한 매트릭스를 정기 검증하여, 결제 기안과 승인, 개발과 배포가 한 사람에게 겹치지 않도록 감사 추적성을 확보하는 체계 운영이 필요.
3. 클라우드 권한 정리 : 클라우드 운영 조직이 **CIEM** (Cloud Infrastructure Entitlement Management, 클라우드 인프라 권한 관리) 도구로 과다 권한 계정을 탐지하고 미사용 권한을 자동 회수하는 체계 구축이 필요.

## Ⅶ. 결론

- 핵심 요약 : 접근통제 모델은 단일 방식이 아니라 권한 구조와 위험 수준에 맞춘 조합 설계 문제임.
- 시사점 : 역할 기반의 관리 효율과 속성 기반의 동적 정밀도를 결합하는 방향이 현재 접근통제 설계의 기본 틀로 자리 잡는 흐름.
