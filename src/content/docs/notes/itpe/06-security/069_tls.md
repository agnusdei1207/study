## 지식 로드맵 내 현재 위치

정보보안 → 통신 보안 → 전송 계층 보안(TLS 1.2 및 TLS 1.3)

## 30초 인출

- **본질:** TCP 전송 계층 상단에서 통신 개체 간의 상호 인증, 기밀성, 무결성을 보장하며, 정적 RSA와 비-AEAD 암호를 제거하고 1-RTT 핸드셰이크로 최적화된 최신 통신 보안 프로토콜
- **메커니즘:** ClientHello(키 공유 제안) → ServerHello(키 합의) → 암호화된 확장/인증서/Finished → 1-RTT 완료 후 AEAD 레코드 암호 통신 개시
- 통찰: TLS 1.3 전환을 통한 1-RTT 고속화와 완전 순방향 비밀성(PFS) 달성에도 불구하고 0-RTT 재전송(Replay) 공격 및 마이크로서비스 간 mTLS 인증서 라이프사이클 관리 복잡성을 극복하기 위해 멱등성 검증과 SPIFFE/SPIRE 기반 자동화 키 발급 체계 결합 필수

<details><summary>핵심 용어</summary>

- **TLS(Transport Layer Security):** 전송 계층 보안 표준(RFC 8446 / RFC 9846)으로, 인터넷 웹(HTTPS), 메일, API 통신의 암호화 기저 규격.
- **순방향 비밀성(PFS, Perfect Forward Secrecy):** 서버의 장기 개인키가 사후에 유출되더라도 과거에 기록된 암호화 세션 트래픽을 복호화할 수 없는 특성(ECDHE로 구현).
- **1-RTT 핸드셰이크:** 클라이언트와 서버 간의 단 1회 왕복 통신만으로 키 합의와 서버 인증을 완료하는 고속 연결 메커니즘.
- **0-RTT (Early Data):** 이전에 연결했던 서버와 재연결 시 첫 번째 요청 패킷부터 애플리케이션 데이터를 전송하여 지연 시간을 극소화하는 기법.
- **AEAD(Authenticated Encryption with Associated Data):** 암호화와 무결성 인증 태그 생성을 단일 알고리즘으로 수행(AES-GCM, ChaCha20-Poly1305).

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | TCP/IP 네트워크 상에서 애플리케이션 계층과 전송 계층 사이에 위치하여 종단 간 상호 인증, 데이터 기밀성, 메시지 무결성을 제공하는 IETF 표준 암호화 통신 프로토콜 |
| 목적 | 중간자 도청(Sniffing), 패킷 변조(Tampering), 서버 사칭(Spoofing) 방어 및 고속 연결 수립을 통한 안전한 디지털 트랜잭션 보장 |

## Ⅱ. TLS의 주요 특징 및 프로토콜 계층 구조

| 프로토콜 | 핵심 역할 | TLS 1.3 변화 사항 |
|---|---|---|
| Handshake Protocol | 보안 매개변수 협상, 암호 알고리즘 선정, 서버/클라이언트 인증 및 세션 키 합의 | 기존 2-RTT에서 1-RTT로 단축, Hello 이후 전 메시지 암호화 |
| Record Protocol | 상위 애플리케이션 데이터를 블록/스트림 단위로 분할, 압축(폐지), AEAD 암호화 및 전송 | CBC/RC4 모드 전면 제거, AEAD 암호화만 강제 적용 |
| Alert Protocol | 통신 도중 발생하는 오류, 경고, 세션 종료(Close Notify) 통지 | 암호화 오류 세분화, 평문 Alert 제거 |
| Change Cipher Spec | 암호화 파라미터 전환을 통보하던 레거시 프로토콜 | **TLS 1.3에서 전면 삭제** (호환성 더미 패킷만 지원) |

## Ⅲ. TLS 1.3 1-RTT 핸드셰이크 프로세스 및 키 교환 체계

```text
[ 클라이언트 (Client) ]                               [ 서버 (Server) ]
ClientHello ─────────────────────────────────────────▶
  ├─ 지원 암호 스위트 목록 (AEAD 전용)
  └─ Key Share (ECDHE 공개키 파라미터 사전 전송)
                                                      ServerHello ◀────────────────────────
                                                        ├─ 선택된 암호 스위트
                                                        └─ Key Share (서버 ECDHE 공개키)
                                                      [ 양측 공유 세션키 유도 완료! ]
                                                      {EncryptedExtensions} (암호화 전송)
                                                      {Certificate} (서버 인증서)
                                                      {CertificateVerify} (인증서 전자서명)
                                                      {Finished} (무결성 검증 HMAC)
                                                      ◀────────────────────────────────────
[ 1-RTT 만에 핸드셰이크 완료 ]
{Finished} ──────────────────────────────────────────▶
[Application Data (AEAD 양방향 암호 통신)] ◀═════════▶ [Application Data]
```

| 단계 | 수행 작업 | 핵심 보안 메커니즘 |
|---|---|---|
| 1. ClientHello | 클라이언트가 지원 알고리즘 목록과 자신의 ECDHE 공개키(Key Share)를 동시 발송 | 1-RTT 단축의 핵심 (사전 키 전송) |
| 2. ServerHello | 서버가 하나의 AEAD 알고리즘을 선택하고 자신의 ECDHE 공개키를 반환 | Diffie-Hellman 공유 비밀(Master Secret) 즉시 계산 |
| 3. 암호화 핸드셰이크 | 서버의 인증서 및 서명, Finished 메시지가 유도된 트래픽 키로 암호화되어 전송 | 인증서 스니핑 차단 (SNI 암호화 ECH 연계) |
| 4. 상호 Finished | 양측이 핸드셰이크 전체 해시값을 검증하여 중간자 변조가 없음을 최종 확인 | 핸드셰이크 무결성 보증 |
| 5. 레코드 통신 | 협상된 대칭키와 AEAD(AES-GCM)를 사용하여 애플리케이션 데이터 암호 통신 수행 | 고속 병렬 암·복호화 |

## Ⅳ. TLS 1.2 vs TLS 1.3 아키텍처 및 보안 특성 상세 비교

| 비교 항목 | TLS 1.2 (RFC 5246) | TLS 1.3 (RFC 8446 / RFC 9846) | 개선 효과 및 사유 |
|---|---|---|---|
| 일반 핸드셰이크 왕복 | 보통 **2-RTT** 소요 | 보통 **1-RTT** (재개 시 0-RTT 지원) | 연결 수립 지연 시간 50% 단축 |
| 키 교환 알고리즘 | 정적 RSA, DH, ECDH, DHE, ECDHE | **(EC)DHE 전용** (PSK 결합 가능) | **정적 RSA 전면 퇴출로 순방향 비밀성(PFS) 강제** |
| 레코드 암호화 모드 | CBC, RC4, 3DES, AEAD 혼재 | **AEAD 전용** (AES-GCM, ChaCha20) | 패딩 오라클(POODLE, Lucky13) 원천 차단 |
| 핸드셰이크 암호화 | 인증서 및 파라미터가 평문 노출 | ServerHello 직후 전 구간 암호화 | 중간자의 통신 대상 식별 및 도청 방어 |
| 암호 스위트 개수 | 수백 개 조합 (설정 오류 빈번) | 핵심 5개로 정예화 | 복잡도 감소 및 구현 취약점 최소화 |

## Ⅴ. TLS 1.3 도입 및 운영의 한계와 방안

| 한계 | 방안 |
|---|---|
| 0-RTT 조기 데이터(Early Data) 사용 시 사전 공유 키(PSK) 티켓 재전송 공격(Replay Attack)으로 비멱등적 금융 결제 중복 처리 위험 | HTTP GET 등 조회성 멱등(Idempotent) 요청에만 0-RTT를 엄격히 제한하고, 서버 측에 단일 티켓 일회용 폐기(Single-use Ticket) 캐시 구축 |
| 마이크로서비스(MSA) 전 구간 mTLS 적용 시 수만 개 서비스 인증서 발급·갱신 주기 관리 실패로 인한 대규모 장애 위험 | 클라우드 네이티브 서비스 메시(Istio, Linkerd) 및 SPIFFE/SPIRE 기반 단기 인증서 자동 발급·순환(Auto-Rotation) 파이프라인 수립 |
| TLS 1.3의 인증서 및 핸드셰이크 전면 암호화로 인해 사내망 경계선 보안 장비(IDS/IPS, WAF, DLP)의 패킷 가시성 상실(Blind Spot) | 엔터프라이즈 프록시 전면에 정당한 SSL 복호화 장비(SSL Visibility Appliance)를 배치하거나 엔드포인트 eBPF 기반 에이전트 모니터링 연동 |

## Ⅵ. 제언

```text
[ 취약한 TLS 1.2 환경 ]               [ 고속·강인한 TLS 1.3 표준 체계 ]
정적 RSA (PFS 미보장) ─┐               ┌── 임시 ECDHE 기반 완전 순방향 비밀성(PFS)
취약한 CBC 패딩 오라클 ┼─→ [ 침해 노출 ] ─┼── AEAD 단일 강제 및 1-RTT 연결 최적화
2-RTT 지연 발생 ───────┘               └── ECH(Encrypted Client Hello) 및 mTLS 연계
```

| 평가 영역 | TLS 1.2 레거시 체계 | TLS 1.3 최신 체계 | 향후 발전 방향 |
|---|---|---|---|
| 키 보안성 | 정적 RSA 설정 시 과거 해독 노출 | 완벽한 순방향 비밀성 보장 | 양자 내성 암호(PQC) 하이브리드 KEM 연동 |
| 통신 속도 | 2-RTT 지연으로 성능 저하 | 1-RTT / 0-RTT 고속 통신 | QUIC 기반 HTTP/3 네이티브 통합 |
| 프라이버시 | 서버 인증서 평문 노출 | 인증서 암호화 및 ECH 지원 | DNS-over-HTTPS(DoH) 결합 완벽한 메타 은닉 |

TLS 1.3은 인터넷 암호 통신의 성능과 보안성을 동시에 비약적으로 격상시킨 현대 웹 보안의 절대적 표준이며, 양자 컴퓨팅 위협에 대비한 하이브리드 PQC 암호 스위트 도입과 0-RTT 보안 가이드라인 준수가 필수적 과제.
