```text

 ┃
 ┣━ Ⅰ 개요 ───── 전송계층(TCP) 상단에서 엔드투엔드 데이터 기밀성·무결성·서버/클라이언트 상호인증을 제공하는 표준 보안 통신 프로토콜(RFC 5246, 8446)
 ┣━ Ⅱ 특징 ───── 하이브리드 암호화(비대칭키 키교환 + 대칭키 데이터 암호화) · 완전순방향비밀성(PFS) · 인증서 기반 신원 검증 · 변조 방지(HMAC)
 ┣━ Ⅲ 구조 ───── 하위 레코드 프로토콜(Record Protocol) + 상위 4대 프로토콜(Handshake, Alert, Change Cipher Spec, Application Data)
 ┣━ Ⅳ 흐름 ───── ① ClientHello(지원 암호스위트, 난수) → ② ServerHello(인증서, 키교환 파라미터) → ③ 세션키 유도 → ④ Finished(암호 통신 개시)
 ┣━ Ⅴ 비교 ───── TLS 1.2(2-RTT 핸드셰이크, 정적 RSA 키교환 허용, 레거시 암호 취약점) vs TLS 1.3(1-RTT/0-RTT 단축, DHE만 강제(PFS 보장), AEAD 전용)
 ┗━ Ⅵ 실무 ───── Heartbleed, POODLE, ROBOT 등 레거시 취약점 / mTLS(상호인증) 기반 제로트러스트 구축 / SSL 복호화 장비와의 충돌
```

## 한 줄 본질
- 평문 전송(TCP)의 도청·위변조 위험과 TLS 1.2의 긴 핸드셰이크 지연 및 취약 암호 지원 병목 → 타원곡선 디피헬만(ECDHE)과 인증 결합 암호화(AEAD)로 통신 절차를 1-RTT로 단축하고 과거 세션 도청을 방지(PFS) → 안전하고 빠른 보안 통신 / 구형 클라이언트 호환성 제약 발생

## 핵심 용어
- 완전순방향비밀성(PFS, Perfect Forward Secrecy): 향후 서버의 개인키(Private Key)가 유출되더라도 과거에 도청하여 녹음해 둔 통신 트래픽 세션키를 역산해 복호화할 수 없도록 보장하는 성질 (임시 디피헬만 Ephemeral DH 사용)
- AEAD(Authenticated Encryption with Associated Data): 기밀성과 무결성(인증)을 별도 연산하지 않고 단일 암호화 과정에서 동시에 생성하는 블록 암호 모드 (AES-GCM, ChaCha20-Poly1305)

## 핵심 통찰
- TLS 1.2 시절에는 서버의 RSA 개인키 하나만 훔치면 지난 1년간 도청한 회사 전 직원의 HTTPS 트래픽을 모두 평문으로 복호화할 수 있었음 → TLS 1.3에서 정적 RSA 키교환을 완전 폐지하고 오직 ECDHE만 허용하여 PFS를 강제함
- TLS 1.3의 본질은 "더 많은 기능의 추가"가 아니라 "위험하고 낡은 쓰레기 암호의 대대적 숙청(Removal)"임 → 취약한 CBC 모드, RC4, MD5, SHA-1을 완전히 삭제함
- 마이크로서비스(MSA)와 제로트러스트 환경에서는 클라이언트만 서버를 검증하는 단방향 TLS를 넘어, 서버도 클라이언트 인증서를 검증하는 mTLS(Mutual TLS)가 표준으로 자리잡음

## 이웃 토픽과 구분
- SSL vs TLS: SSL = 넷스케이프가 개발한 초기 규격(SSL 2.0/3.0은 치명적 결함으로 폐기) / TLS = IETF가 표준화한 정식 후속 프로토콜(TLS 1.0~1.3)

## 문제·원인·대책
- 사례: TLS 1.2에서 CBC 모드 패딩 처리 오류를 악용해 세션 쿠키를 바이트 단위로 복호화한 POODLE 공격 사례
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| CBC 운용 모드 취약점을 악용한 패딩 오라클 공격 | 복호화 에러 메시지의 시간차 및 패딩 검증 구조적 결함 | 취약한 CBC 암호스위트 비활성화 및 AEAD(AES-GCM) 전용 모드 전환 | 패딩 조작을 통한 복호화 공격 원천 무력화 |
| 최초 접속 시 2-RTT 지연으로 인한 웹 성능 저하 | 핸드셰이크 단계가 4단계 왕복으로 길어 응답 지연 초래 | TLS 1.3 적용(1-RTT) 및 재방문 시 0-RTT 조기 데이터(Early Data) 활용 | 연결 수립 지연 50% 단축 및 모바일 체감 성능 개선 |

## 이렇게 출제된다
- 제136회 2교시 6번: "인터넷 통신에서 보안성 강화를 위해 활용되는 TLS 1.2에 대한 취약점이 발견되어 TLS 1.3 사용을 권고하고 있다. 이와 관련하여 다음을 설명하시오. 가. TLS 개념 및 계층 구조 나. TLS 1.2 취약점 다. TLS 1.3의 주요 개선사항" → 요구 포인트: Ⅰ~Ⅶ 완벽 대응

## 내 의견
- [사내 레거시 호환성을 이유로 TLS 1.0/1.1을 방치하는 보안 부실] 구형 POS 단말이나 사내 노후 인트라넷 호환을 위해 서버 암호스위트에 TLS 1.0/1.1을 '하위 호환'으로 열어두어 다운그레이드 공격(POODLE/DROWN)에 노출되는 문제 상존 → 나라면: 웹서버(Nginx, Apache) 설정에서 TLS 1.0 및 1.1 프로토콜을 강제 차단하고, TLS 1.2도 CBC 스위트를 제거한 뒤 장기적으로 TLS 1.3 단일화를 추진

## 찾아볼 것
