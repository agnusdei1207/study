## 연관 키워드

- JWT(JSON Web Token), 무상태(Stateless), 클레임(Claims), 서명(Signature), 자가 수용성
- 토큰 폐기(Revocation), Refresh Token Rotation, alg none 취약점, JWE, JWKS, DPoP

## Ⅰ. JWT의 개요

- 핵심 요약 : 정보를 서명된 JSON(JavaScript Object Notation) 객체로 담아 위변조를 막고, 세션 저장소 없이 신원을 전달하는 자가 수용적 토큰.
- 개념 : 당사자 간에 정보를 간결하고 안전하게 전달하기 위해 JSON 객체에 담고 HMAC(Hash-based Message Authentication Code)이나 RSA(Rivest-Shamir-Adleman) 같은 서명을 적용한 개방형 웹 표준 토큰인 **JSON 웹 토큰** (JWT, JSON Web Token)으로, RFC(Request for Comments) 7519에 규정됨.
- 배경 및 필요성 : 전통적인 세션 기반 인증은 서버 메모리나 공유 저장소(Redis)에 세션 상태를 유지해야 하므로, 마이크로서비스 아키텍처(MSA, Microservice Architecture)와 모바일 환경에서 수평 확장 시 동기화 부담이 커짐.
- 주요 목적 : 토큰에 신원과 권한 정보(Claims)를 담아 세션 DB 조회 없이 무상태 인증을 처리하는 것.

## Ⅱ. JWT의 특징 및 장점

- 핵심 요약 : 자가 수용적 토큰과 서명 검증이 세션 조회 없는 분산 인증으로 이어지는 방식.

1. **자가 수용성** (Self-contained) : 인증·인가에 필요한 정보가 토큰 안에 있음 → 각 API 서버가 중앙 DB 없이 독자 검증 → 수평 확장 시 조회 병목 제거.
2. 위변조 방지 : 헤더와 페이로드에 서명을 적용 → 서명 키를 가진 발급자만 유효한 토큰 생성 가능 → 클레임 조작 탐지.
3. **무상태** (Stateless) : 서버에 세션 저장소가 없음 → 여러 서비스와 리전에서 동일한 토큰을 재사용.
4. 표준 기반 상호운용 : 공개 규격을 따름 → 언어와 플랫폼이 달라도 같은 방식으로 검증.

```text
[ JWT 문자열 구조 ]

Header . Payload . Signature

Header    : 서명 알고리즘(alg), 타입(typ)
Payload   : 클레임(sub, exp, role 등)
Signature : 헤더·페이로드에 대한 서명값
```

## Ⅲ. JWT의 구조 (흐름)

- 핵심 요약 : 헤더, 페이로드, 서명 세 부분이 Base64URL로 이어져 위변조를 검증할 수 있는 토큰을 이루는 구조.
- **헤더** (Header) : 토큰 타입과 서명 알고리즘(HS256, RS256, ES256 등)을 명시.
- **클레임** (Claims) : iss(발급자), sub(주체), exp(만료 시각), nbf(활성 시각)와 사용자 정의 클레임으로 구성.
- **서명** (Signature) : 헤더와 페이로드를 Base64URL로 인코딩한 값을 비밀키(대칭키)나 개인키(비대칭키)로 서명.

```text
[ 무상태 인증 흐름 ]

클라이언트 → 인증 서버
    ↓ (ID·PW 검증 후 JWT 발급)
클라이언트 (토큰 보관)
    ↓ (Authorization: Bearer 헤더)
마이크로서비스 A·B
    ↓ (서명 검증, 클레임 판독)
인가 처리 완료 (세션 DB 조회 없음)
```

## Ⅳ. JWT의 비교 분석

- 핵심 요약 : 무상태 토큰인 JWT는 확장성에서 유리하고, 즉시 폐기가 필요하면 상태를 유지하는 방식이 적합한 구조.

인증 토큰 방식을 **서버 세션** (Session-Cookie), **불투명 토큰** (Opaque Token)과 비교하면 다음과 같다.

| 비교 축 | JWT | 서버 세션 | 불투명 토큰 |
| --- | --- | --- | --- |
| 상태 저장 | 무상태 (서버 저장소 없음) | 상태 유지 (서버 메모리·Redis) | 상태 유지 (서버 DB 매핑) |
| 확장성 | MSA·멀티 리전 환경에 유리 | 세션 클러스터 동기화 부담 | 검증 때마다 중앙 조회 |
| 페이로드 노출 | Base64URL 디코딩으로 누구나 열람 가능 | 클라이언트는 난수 세션 ID만 보유 | 의미 없는 난수 문자열만 보유 |
| 즉각 폐기 | 원칙적으로 불가 (만료까지 유효) | 서버에서 세션 삭제 시 즉시 만료 | DB 레코드 삭제 시 즉시 만료 |
| 전송 부담 | 토큰 크기만큼 대역폭 부담 | 쿠키 크기가 작음 | 토큰은 작으나 DB 조회 부담 |

- 선택 기준 : 분산 서비스 간 인증 전파가 많으면 JWT, 세션을 즉시 끊어야 하는 환경이면 서버 세션이나 불투명 토큰이 적합함.

## Ⅴ. JWT의 한계와 방안

- 핵심 요약 : 즉각 폐기 불가, 페이로드 기밀성 부재, 알고리즘 검증 우회라는 세 취약점을 수명 단축, 민감정보 배제, 알고리즘 화이트리스트로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 발급 후 **토큰 폐기** (Revocation) 불가 | 서명 검증만으로 유효성을 판단하여, 로그아웃이나 권한 박탈 후에도 만료 전까지 접근 가능 | Access Token 만료를 짧게 두고 Refresh Token으로 재발급, Redis 기반 블랙리스트(Denylist) 보완 | 블랙리스트 적중 건수, 토큰 평균 수명 |
| 페이로드 기밀성 부재 | 서명은 위변조만 막고 암호화하지 않아 민감정보를 누구나 디코딩 가능 | 비밀번호·주민번호 등의 페이로드 적재 금지, 필요 시 **JWE** (JSON Web Encryption)로 페이로드 자체를 암호화 | 페이로드 내 민감 클레임 탐지 건수 |
| **alg none** 취약점 | 검증 라이브러리가 헤더의 alg 값을 신뢰하여 서명 없는 토큰을 수락 → 권한 상승 | 허용 알고리즘을 화이트리스트(예: RS256만 허용)로 고정하고 none 값을 코드 수준에서 거부 | 서명 검증 실패 로그 건수 |

## Ⅵ. JWT의 기술사적 제언

- 핵심 요약 : 키 관리, 토큰 수명, 재사용 탐지를 함께 설계하여 확장성을 유지하면서 도난 위험을 낮추는 방향.

1. 인증 서버만 개인키로 서명하고 모든 마이크로서비스는 **JWKS** (JSON Web Key Set) 공개키 엔드포인트로 검증하도록 설계하면, 대칭키 공유에 따른 키 유출 위험을 구조적으로 없앨 수 있다.
2. 재발급 체계에는 **Refresh Token Rotation** (RTR)을 적용하여, 재발급할 때마다 이전 Refresh Token을 파기하고 재사용 시도를 탐지하는 절차를 두는 것이 바람직하다.
3. 탈취된 토큰의 악용을 막기 위해 OAuth 2.0 기반의 **DPoP** (Demonstrating Proof-of-Possession, RFC 9449)를 도입하여 토큰을 클라이언트 키에 묶는 표준 전환을 검토할 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : JWT는 세션 저장소 없이 신원을 검증하는 분산 인증 토큰이며, 확장성과 폐기 통제의 균형이 설계의 핵심임.
- 시사점 : 클레임에 민감정보를 담지 않고 수명과 키 관리를 엄격히 할 때에만 무상태 인증의 이점이 안정적으로 유지됨.
