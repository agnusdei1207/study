## 답안 골격
```text
[대칭키 암호화] ◀━━ 머리: Ⅶ 내 의견 (키 배송 문제 해결 → 하이브리드 암호화(전자봉투) 및 중앙화된 KMS 기반 키 수명주기 통제)
 ┃
 ┣━ Ⅰ 개요 ───── 암호화(Encryption)와 복호화(Decryption)에 동일한 비밀키(Secret Key)를 사용하는 암호화 방식으로 고속 대용량 데이터 보호의 근간
 ┣━ Ⅱ 특징 ───── 고속 연산(비대칭키 대비 1,000배 이상 빠름) · 키 배송 문제(Key Distribution Problem) · $N(N-1)/2$ 키 관리 복잡도 · 부인방지 불가
 ┣━ Ⅲ 구조 ───── 블록 암호(AES, ARIA, SEED: Feistel/SPN 구조) · 스트림 암호(RC4, ChaCha20: 키스트림 XOR)
 ┣━ Ⅳ 흐름 ───── ① 송수신자 간 비밀키 사외/사전 공유 → ② 평문 데이터를 블록/비트 단위로 분할 → ③ 비밀키 기반 라운드 연산(암호화) → ④ 수신자가 동일 키로 역연산(복호화)
 ┣━ Ⅴ 비교 ───── 대칭키 암호(키 1개, 고속 연산, 키 배송 취약, 부인방지 불가) vs 비대칭키 암호(키쌍 2개, 저속 연산, 키 분배 용이, 전자서명/부인방지 가능)
 ┗━ Ⅵ 실무 ───── 키 탈취 시 과거 모든 암호문 해독 위험 / 클라우드 KMS(Key Management Service) 연계 / 하드웨어 가속(AES-NI) 최적화
```
- 필수 키워드: 대칭키 암호화 · 비밀키(Secret Key) · 키 배송 문제 · 블록 암호 · 스트림 암호 · AES · $N(N-1)/2$ · KMS
- 배점 전략: 10점 = Ⅰ 정의 및 동작 원리 → Ⅲ 블록/스트림 암호 분류 도식 → Ⅴ 비대칭키 대비 비교 / 25점 = Ⅰ~Ⅶ 전개, 키 분배 문제 해결 기법(디피헬만, KDC)과 Ⅵ 엔터프라이즈 KMS 키 관리 체계 집중
- 기출: 132회 1교시 4번 `대칭 암호화와 비대칭 암호화` → Ⅰ 대칭키 개념 + Ⅲ 원리 + Ⅴ 비대칭키와의 비교

## 한 줄 본질
- 동일한 비밀키를 사용하여 초고속 암·복호화를 달성하지만, 그 비밀키를 통신 상대방에게 안전하게 전달해야 하는 '키 배송의 딜레마' 병목 → 비대칭키로 대칭키만 암호화해 전달하는 하이브리드 방식(전자봉투)으로 해결 → 대용량 고속 기밀성 확보 / 참여자 증가 시 관리해야 할 키 개수가 $O(N^2)$으로 폭증하는 비용 발생

## 핵심 그림
```text
[대칭키 암호화 기본 동작 원리 및 키 배송의 딜레마]

           [ 동일한 비밀키 (Secret Key, K) 공유 ]
                      │                       │
                      ▼                       ▼
  [송신자] ──> [암호화 엔진] ──(암호문 전송)──> [복호화 엔진] ──> [수신자]
   (평문 M)         (E_K)     인터넷 도청 위험       (D_K)          (평문 M)

 * 대칭키 암호화의 3대 한계:
   1. 키 배송 문제: 송수신자가 키 K를 안전하게 전달할 채널이 없음
   2. 키 관리 복잡도: N명이 통신할 때 필요한 총 키의 수 = N(N-1)/2
   3. 부인 방지 불가: 동일한 키를 둘 다 가지고 있으므로 누가 작성했는지 입증 불가
```

## 핵심 용어
- 키 배송 문제(Key Distribution Problem): 사전에 만나지 않은 원격지의 두 주체가 도청이 가능한 공공 통신망에서 비밀키를 상대방에게 안전하게 전달할 수 없는 근본적 모순
- 하이브리드 암호화(Hybrid Encryption): 실제 대용량 데이터는 빠른 대칭키(AES)로 암호화하고, 그 대칭키는 안전한 비대칭키(RSA/ECC)로 암호화하여 함께 전송하는 현실적 절충 방식

## 핵심 통찰
- 현대 디지털 세상의 거의 모든 암호화(디스크 암호화, DB 암호화, HTTPS 트래픽)는 실제로 대칭키로 수행됨 → 비대칭키는 너무 느려서 수 메가바이트의 파일조차 암호화하기 벅차기 때문
- 양자컴퓨터가 등장해도 대칭키 암호는 안전함 → 그로버(Grover) 알고리즘이 대칭키 탐색을 가속하지만 키 길이를 2배(AES-128 → AES-256)로 늘리면 양자컴퓨터로도 해독이 불가능함
- 대칭키 보안의 성패는 알고리즘이 아니라 '키의 보관(Key Management)'임 → 소스코드나 설정 파일에 하드코딩된 대칭키는 암호화하지 않은 것과 다름없음

## 이웃 토픽과 구분
- 대칭키 vs 공개키: 대칭키 = 자물쇠를 잠근 열쇠로만 열 수 있음(1개) / 공개키 = 누구나 자물쇠를 잠글 수 있지만(공개키), 오직 주인만이 자신의 열쇠로 열 수 있음(개인키)

- 사례: 사내 DB 암호화 키를 웹 애플리케이션의 `application.yml` 설정 파일에 평문으로 저장했다가 GitHub 유출로 전사 DB가 복호화된 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 소스코드 및 형상관리 리포지토리에 대칭키 노출 | 키 수명주기 관리 체계 부재 및 개발 편의주의적 하드코딩 | 클라우드 KMS(AWS KMS, HashiCorp Vault) 및 엔벨로프 암호화 적용 | 키의 메모리 비노출 및 중앙 감사 로그 확보 |

## 내 의견
- [KMS 도입 후 키 회전(Rotation)을 방치하는 운영 관행] 클라우드 KMS를 도입했으나 수년 동안 마스터 키를 한 번도 회전하지 않아 과거 유출 사고 시 피해 복구가 불가능한 문제 상존 → 나라면: KMS 정책에서 '연 1회 자동 키 회전(Automatic Key Rotation)'을 강제하고, 이전 키로 암호화된 데이터를 점진적으로 재암호화하는 백그라운드 배치 파이프라인 구축
