## 지식 로드맵 내 현재 위치

지식 위치: 암호 운용 모드 → 암호문 피드백 → **CFB**

## 30초 인출

- **본질:** 직전 단계의 암호문을 암호화 엔진의 입력으로 피드백하여 키스트림을 생성하고 평문과 XOR하여 블록 암호를 스트림 암호처럼 구동시키는 운용 모드
- **메커니즘:** IV(또는 직전 암호문)를 암호화($E_K$) → 출력 상위 $s$비트와 평문 $P_i$ XOR 연산 → 암호문 $C_i$ 생성 및 시프트 레지스터 피드백
- **통찰:** 암호화의 직렬 의존성으로 병렬 처리가 불가하고 비트 플리핑에 취약하므로 무결성 검증을 위한 HMAC 결합 또는 AEAD(GCM) 모드로의 전환 필수

<details>
<summary>핵심 용어</summary>

- **CFB (Cipher Feedback)** : 이전 블록의 암호문을 암호화 입력으로 재사용하는 블록 암호 운용 모드.
- **Self-synchronizing (자기 동기)** : 비트 누락이나 오류 발생 시 일정 블록 수신 후 자동으로 복호화 동기가 회복되는 특성.
- **Segment Size (s-bit)** : 한 번에 XOR 연산하여 처리하는 비트 단위 (보통 8비트 또는 128비트).
- **Bit Flipping Attack** : 암호문의 특정 비트를 반전시켜 복호화 평문의 해당 비트를 조작하는 능동적 공격.

</details>

## 2~4교시 예상문제 (25점)

> 블록 암호 운용 모드 중 CFB(Cipher Feedback)의 동작 원리, 암·복호화 메커니즘 및 오류 전파(Error Propagation) 특성을 설명하고, 다른 운용 모드와의 비교 및 실무 엔지니어링 한계와 해결 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 블록 암호 알고리즘을 스트림 암호처럼 동작시키기 위해, 이전 단계에서 생성된 암호문 블록을 암호화 함수의 입력으로 피드백하는 블록 암호 운용 방식 |
| 목적 | 데이터 길이가 블록 크기(128비트)의 배수가 아니어도 패딩(Padding) 없이 문자(Byte) 단위의 실시간 데이터 스트림을 지연 없이 암호화 |

- NIST SP 800-38A에 정의된 블록 암호 운용 모드 중 하나로, 복호화 시에도 암호화 함수($E_K$)만을 사용하는 하드웨어 친화적 구조 보유

## Ⅱ. CFB 모드의 핵심 기술적 특징

| 특징 항목 | 세부 내용 및 기술적 의미 | 엔지니어링 이점 및 한계 |
|---|---|---|
| 패딩 불필요 (No Padding) | 임의의 크기($s$-bit) 단위로 평문을 즉시 처리하므로 블록 패딩 오버헤드 완전 제거 | 통신 세션의 문자 단위 즉시 전송 가능, 패딩 오라클 공격 면역 |
| 복호화 시 암호화 함수 사용 | 복호화 과정에서도 복호화 엔진($D_K$)이 아닌 암호화 엔진($E_K$)을 그대로 사용 | 하드웨어(FPGA/ASIC) 면적 절감 및 펌웨어 코드 경량화 |
| 제한적 오류 전파 및 자기 동기 | 전송 중 암호문 비트 에러 발생 시 해당 비트 및 레지스터 크기만큼 전파된 후 자동 동기화 | 비트 동기 누락(Slip) 발생 시에도 일정 수신 후 세션 복구 가능 |
| 암호화 직렬 의존성 | 다음 암호문 생성을 위해 반드시 직전 암호문 $C_{i-1}$이 필요하므로 암호화 병렬화 불가 | 고속 네트워크 대역폭(10Gbps 이상) 처리 시 CPU 병목 발생 |

- 복호화의 경우 수신된 암호문 블록들을 이미 알고 있으므로 병렬 처리가 가능한 비대칭적 처리 특성 보유

## Ⅲ. CFB 암·복호화 메커니즘 및 오류 전파 프로세스

```text
[CFB 128-bit 모드 암호화 및 복호화 메커니즘]

 [암호화 프로세스]
       IV (Initial Vector)
              │
              ▼
        ┌───────────┐
        │  E_K (암호)│ <── 대칭키 K
        └─────┬─────┘
              │
              ▼ (키스트림)
 평문 P1 ───> ⊕ ───────────────> 암호문 C1
                                   │
              ┌────────────────────┘ (피드백)
              ▼
        ┌───────────┐
        │  E_K (암호)│ <── 대칭키 K
        └─────┬─────┘
              │
              ▼ (키스트림)
 평문 P2 ───> ⊕ ───────────────> 암호문 C2

 [복호화 프로세스]
 암호문 C1 ───> E_K(IV) 출력과 ⊕ ───> 평문 P1 (복호화 시에도 E_K 사용)
```

| 프로세스 단계 | 핵심 수식 및 동작 | 상세 설명 |
|---|---|---|
| 초기 블록 암호화 | $I_1 = IV$, $O_1 = E_K(I_1)$, $C_1 = P_1 \oplus O_1$ | 최초 고유한 IV를 암호화하여 키스트림 생성 후 $P_1$과 XOR |
| 연속 피드백 암호화 | $I_j = C_{j-1}$, $O_j = E_K(I_j)$, $C_j = P_j \oplus O_j$ | 직전 암호문을 암호화 함수의 입력으로 피드백하여 순차 처리 |
| 복호화 처리 | $P_j = C_j \oplus E_K(C_{j-1})$ ($j=1$인 경우 $I_1 = IV$) | 수신된 암호문을 $E_K$에 입력하고 $C_j$와 XOR하여 평문 복원 |
| 오류 전파 특성 | 암호문 $C_1$의 1비트 변조 시 발생 영향 | 복호화 시 $P_1$의 해당 1비트 에러 + $P_2$ 전체 블록 왜곡 후 $P_3$부터 정상 복구 |

## Ⅳ. 블록 암호 5대 운용 모드(NIST SP 800-38A) 비교

| 비교 항목 | ECB | CBC | CFB | OFB | CTR |
|---|---|---|---|---|---|
| 피드백 대상 | 없음 | 암호문 $\rightarrow$ 평문 결합 | 암호문 $\rightarrow$ 암호 입력 | 함수 출력 $\rightarrow$ 암호 입력 | 카운터 값 증가 |
| 스트림 모드 지원 | 불가능 (블록) | 불가능 (블록) | 지원 (스트림) | 지원 (스트림) | 지원 (스트림) |
| 패딩(Padding) 필요 | 필수 (PKCS#7) | 필수 (PKCS#7) | 불필요 | 불필요 | 불필요 |
| 병렬 암호화 | 가능 | 불가 (직렬) | 불가 (직렬) | 불가 (직렬) | 가능 (고속) |
| 병렬 복호화 | 가능 | 가능 | 가능 | 불가 (직렬) | 가능 (고속) |
| 전송 오류 전파 | 해당 블록만 | 해당 및 다음 블록 | 해당 비트 + 다음 블록 | 해당 비트만 왜곡 | 해당 비트만 왜곡 |
| 대표적 취약점 | 패턴 노출 | 패딩 오라클 공격 | 비트 플리핑 변조 | 키스트림 재사용 누출 | IV/Nonce 재사용 시 완전 붕괴 |

## Ⅴ. CFB 모드 적용 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| 암호화 연산이 이전 암호문 생성 완료에 종속되어 멀티코어 CPU 및 GPU 기반 병렬 파이프라인 가속 불가 | 병렬 암복호화가 완전 지원되는 카운터 모드(CTR) 또는 하드웨어 AES-NI 가속을 지원하는 Galois/Counter Mode(GCM)로 운용 모드 전면 전환 |
| CFB는 순수 기밀성 운용 모드로 무결성 인증이 부재하여, 공격자가 암호문 비트를 반전시키는 비트 플리핑(Bit-flipping) 공격 탐지 불가 | HMAC-SHA256을 암호문 뒤에 결합하는 Encrypt-then-MAC(EtM) 아키텍처를 적용하거나 인증과 암호화가 결합된 표준 AEAD(AES-GCM/ChaCha20-Poly1305) 채택 |
| 동일 대칭키 환경에서 IV(Initial Vector)가 재사용될 경우 최초 블록의 키스트림이 동일하여 공격자에게 평문 XOR 관계 노출 | 암호학적으로 안전한 의사난수 생성기(CSPRNG)를 통해 매 세션마다 128비트 유니크 IV 생성을 강제하고 세션당 최대 전송 블록 수 제한 |
| 전송 채널에서 비트 누락(Bit Drop) 발생 시 프레임 재동기화 이전까지 1블록(128비트) 전체 데이터가 손실되는 버스트 에러 발생 | 하위 전송 계층에 TCP 등 신뢰성 있는 전송 프로토콜을 사용하거나 상위 프레임워크에 FEC(순방향 오류 정정) 코드 결합 |

## Ⅵ. 안전한 데이터 전송 모드 설계 및 마이그레이션 제언

```text
[레거시 CFB에서 모던 AEAD로의 마이그레이션 아키텍처]

  +---------------------------------------------------------------+
  |        레거시 레벨: CFB 모드 (기밀성 전용, 패딩 불필요)         |
  |        [ P_i ] ──> ⊕ <── [ E_K(C_{i-1}) ] ──> [ C_i ]         |
  +---------------------------------------------------------------+
                                  │
                                  ▼ (보안 결함: 비트 조작 위협)
  +---------------------------------------------------------------+
  |        과도기 레벨: CFB + HMAC (Encrypt-then-MAC 구조)         |
  |        [ C_i ] 전송 + [ HMAC(K_auth, C_1 || ... || C_n) ]     |
  +---------------------------------------------------------------+
                                  │
                                  ▼ (성능 및 표준화 최적화)
  +---------------------------------------------------------------+
  |        최신 표준: AES-GCM (AEAD 단일 통합 파이프라인)          |
  |   - CTR 모드 병렬 암호화 + GMAC 무결성 인증 태그 원스텝 생성  |
  +---------------------------------------------------------------+
```

| 검토 영역 | 엔지니어링 핵심 과제 | 통과 기준 지표 |
|---|---|---|
| 암호 강도 | 레거시 DES/3DES 기반 CFB를 최소 AES-128/256-CFB로 업그레이드 | 취약 암호 알고리즘 제거율 100% |
| 무결성 검증 | 전송 프로토콜 상에 변조 탐지용 인증 태그(Auth Tag) 검증 필수화 | 비인가 변조 패킷 즉시 폐기율 100% |
| 현대화 전환 | 신규 설계 시스템 전반에 NIST SP 800-38D 준수 AES-GCM 적용 | 병렬 처리를 통한 처리 속도 향상 >= 300% |
