## 연관 키워드

- 소프트웨어 보안 품질, S-SDLC(Secure SDLC), 쉬프트 레프트(Shift-Left), DevSecOps
- SAST, DAST, IAST, SCA, 퍼징(Fuzzing), 위협 모델링(STRIDE)
- 품질 게이트(Quality Gate), RASP, 도달 가능성 분석, 비즈니스 로직 결함, 오탐(False Positive)

## Ⅰ. 소프트웨어 보안 품질의 개요

- 핵심 요약 : 소프트웨어가 악의적 공격과 비인가 변경에 저항하도록 개발 전 생애주기에 보안을 내재화하는 비기능 품질 속성.
- 개념 : 외부 공격과 비인가 데이터 변경에 저항하여 **기밀성·무결성·가용성**을 보장하도록, **SDLC**(Software Development Life Cycle, 소프트웨어 개발 생애주기) 전 단계에서 보안을 내재화하는 품질 속성.
- 배경 및 필요성 : 개발 완료 후 취약점을 고치는 비용이 설계 단계 대비 크게 늘어나므로, 요구사항 정의부터 유지보수까지 보안을 정량적으로 관리해야 한다는 요구가 커짐.
- 핵심 목적 : 운영 중 보안 사고와 법적 제재를 줄이고, 결함을 초기에 발견해 수정 비용을 낮추며, 신뢰할 수 있는 시스템을 배포.

## Ⅱ. 소프트웨어 보안 품질의 특징 및 장점

- 핵심 요약 : 정적·동적 분석과 위협 모델링을 파이프라인 각 단계에 배치해, 결함을 발견 비용이 가장 낮은 시점에 잡는 것이 장점.

1. 조기 발견 : 설계 단계에서 **위협 모델링**(STRIDE, 위협을 6개 범주로 분류하는 기법) 수행 → 구조적 위험을 코드 작성 전에 제거.
2. 자동화 검사 : **SAST**(Static Application Security Testing, 소스 정적 분석)와 **SCA**(Software Composition Analysis, 오픈소스 구성 분석)를 빌드에 연결 → 알려진 취약 패턴과 취약 라이브러리를 반복 검출.
3. 실행 기반 검증 : **DAST**(Dynamic Application Security Testing, 실행 중인 애플리케이션의 동적 분석)와 **IAST**(Interactive Application Security Testing, 런타임 내부 에이전트 분석)를 테스트 단계에 적용 → 실제 공격 경로와 정확한 취약 위치를 확인.
4. 품질 게이트 : 심각도 기준을 빌드 조건으로 삼아 미충족 산출물의 배포를 차단 → 취약 코드의 운영 유입 방지.

## Ⅲ. 소프트웨어 보안 품질의 구조 (흐름)

- 핵심 요약 : 요구사항과 설계에서 위협을 모델링하고, 개발과 빌드에서 자동 분석하며, 테스트와 운영에서 실행 기반 검증과 방어를 이어 가는 단계별 구조.

```text
[ 요구사항 · 설계 ]
위협 모델링 · 보안 비기능 요구
          ↓
[ 개발 · 빌드 ]
린터 · 시크릿 스캐닝 · SAST · SCA
          ↓
[ 품질 게이트 ]
Critical 취약점 0건일 때만 통과
          ↓
[ 테스트 ]
DAST · IAST · 퍼징
          ↓
[ 운영 ]
RASP · 취약점 수집과 피드백
```

- 품질 게이트 판정 기준은 치명도 높은 취약점(CVSS 9.0 이상)과 라이선스 위반 여부를 예로 들 수 있으며, 미충족 시 빌드를 실패시키고 개발자에게 결과를 알리는 방식으로 운영.

## Ⅳ. 소프트웨어 보안 품질의 비교

- 핵심 요약 : 기존 품질 보증이 명세된 기능이 맞게 동작하는지를 본다면, 보안 품질은 의도되지 않은 동작을 막는지를 본다는 점에서 관점이 다름.

| 비교 항목 | 전통적 기능 품질 (Functional QA) | 소프트웨어 보안 품질 (Security Quality) |
| --- | --- | --- |
| 주요 목표 | 명시된 기능을 올바르게 수행하는가 | 의도되지 않은 동작을 하지 않도록 방어하는가 |
| 테스트 시나리오 | 정상 입력과 예외 처리 검증 | 적대적 비정상 입력과 우회 시도 |
| 결함 발견 시점 | 릴리스 직전 테스트 단계에 집중 | **쉬프트 레프트**(Shift-Left)로 개발 초기에 집중 |
| 통제 수단 | 단위·통합·E2E 테스트 | SAST, DAST, SCA, IAST, 위협 모델링, 퍼징 |
| 책임 주체 | QA 및 개발 조직 | 개발, 보안, 운영이 함께 맡는 **DevSecOps** 체계 |

## Ⅴ. 소프트웨어 보안 품질의 한계와 방안

- 핵심 요약 : 오탐 과다, 동적 분석의 인증 한계, 사용되지 않는 의존성 경보, 비즈니스 로직 결함이 자동화 도구의 주요 약점.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 정적 분석 **오탐** (False Positive) 과다 | 실제가 아닌 경보로 빌드가 자주 중단되어 개발 생산성 저하와 경보 피로 발생 | 심각도와 악용 가능성 점수(EPSS)를 결합한 품질 게이트 정책을 조직에 맞게 조정 | 오탐 비율, 빌드 중단 횟수 |
| 동적 분석의 인증·API 탐색 한계 | 토큰 만료와 비동기 API 때문에 스캐너가 엔드포인트를 충분히 찾지 못함 | API 명세를 DAST 도구에 주입하고 런타임 IAST와 결합 | 엔드포인트 탐색 커버리지 |
| 사용되지 않는 의존성 경보 과다 | 실행 경로에서 호출되지 않는 취약 라이브러리까지 보고됨 | 호출 그래프 기반의 **도달 가능성 분석**(Reachability Analysis)으로 실제 호출되는 의존성만 조치 | 실호출 취약점 비율 |
| 비즈니스 로직 결함 | 쿠폰 중복 적용, 권한 상승은 도구가 패턴으로 탐지하기 어려움 | 설계 단계 위협 모델링을 의무화하고, 도메인을 아는 보안 담당자의 동료 검토 결합 | 로직 결함 발견 건수 |

```text
[ 보안 품질 경보 감소 흐름 ]

정적 분석 오탐 과다
   ↓ 심각도와 악용 가능성 점수 결합
품질 게이트 정책 조정
   ↓ 실제 호출되는 의존성만 선별
도달 가능성 분석으로 경보 축소
   ↓ 로직 결함은 설계 단계에서 차단
위협 모델링과 도메인 동료 검토
```

## Ⅵ. 소프트웨어 보안 품질에 대한 기술사적 제언

- 핵심 요약 : 개발 문화, 파이프라인 자동화, 운영 피드백을 하나의 순환으로 묶어야 보안 품질이 릴리스마다 유지됨.

1. 개발 문화 : 조직은 개발자 IDE에 보안 린터를 기본 탑재하고 시큐어 코딩 교육을 정기화해, 코드 작성 단계에서 결함이 줄어들게 해야 한다.
2. 파이프라인 자동화 : CI(Continuous Integration)와 CD(Continuous Delivery) 각 단계에 품질 게이트를 두고, 심각한 취약점이 발견되면 배포가 자동으로 멈추도록 하는 것이 바람직하다.
3. 운영 피드백 : 운영 환경의 RASP와 SIEM(Security Information and Event Management) 탐지 결과를 다음 스프린트의 보안 요구사항으로 연결해, 같은 유형의 결함이 반복되지 않도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 소프트웨어 보안 품질은 기능 검증의 연장이 아니라, 개발 전 과정에 보안 검증을 내장하는 품질 속성.
- 시사점 : 결함은 늦게 발견될수록 비싸므로, 자동화 도구와 사람의 판단을 단계별로 나누어 배치하는 것이 효율적이다.
