## 답안 골격
```text
[클라우드 서비스 보안(Cloud Service Security)] ◀━━ 머리: Ⅶ 내 의견 (CSP 맹신 탈피 → 공동 책임 모델의 명확한 인지와 CNAPP 기반의 전주기 설정·워크로드 통합 통제)
 ┃
 ┣━ Ⅰ 개요 ───── IaaS, PaaS, SaaS 등 클라우드 컴퓨팅 환경에서 데이터, 애플리케이션, 가상 인프라의 기밀성·무결성·가용성을 보장하기 위해 클라우드 서비스 제공자(CSP)와 고객사가 책임을 분담하는 종합 정보보호 체계
 ┣━ Ⅱ 특징 ───── 공동 책임 모델(Shared Responsibility Model) 적용 · 클라우드 설정 오류(Misconfiguration)가 최대 위협 · 멀티 테넌시(Multi-tenancy) 환경의 데이터 격리 요구 · API 기반 동적 자원 제어
 ┣━ Ⅲ 구조 ───── 클라우드 보안 4대 핵심 축(CNAPP): CSPM(설정 관리) + CWPP(워크로드 보호) + CIEM(과다 권한 제어) + CASB(클라우드 접근 중계)
 ┣━ Ⅳ 흐름 ───── 클라우드 자산 식별 및 태깅 → CSPM 설정 감사 및 취약점 스캔 → CIEM 최소 권한 회수 → CWPP 런타임 위협 차단 → 통합 보안 대시보드 모니터링
 ┣━ Ⅴ 비교 ───── IaaS 보안(OS, 미들웨어, 네트워크 고객 통제) vs PaaS 보안(런타임/플랫폼 제공자 관리) vs SaaS 보안(데이터/계정만 고객 책임)
 ┗━ Ⅵ 실무 ───── 퍼블릭 S3 버킷 공개 등 설정 실수로 인한 대규모 정보 유출 / 하이퍼바이저 탈출(VM Escape) / 섀도우 클라우드 가시성 부족
```
- 필수 키워드: 클라우드 서비스 보안 · 공동 책임 모델 · CSPM · CWPP · CIEM · CNAPP · 설정 오류(Misconfiguration) · CSAP · ISO/IEC 27017
- 기출: 제130회 4교시 3번: "최근 다수의 기업들이 클라우드 서비스를 도입하면서 다양한 보안 문제가 대두되고 있다. IT 담당자 입장에서 클라우드 서비스 도입 시 고려해야 할 보안 요소..."

## 한 줄 본질
- 클라우드로 전환하면 보안도 CSP가 다 알아서 해줄 것이라는 안일한 착각 병목 → 서비스 모델별(IaaS/PaaS/SaaS) 책임 분계선을 명확히 정의하고 설정 관리(CSPM)와 권한 최소화(CIEM)를 자동화 → 클라우드 확장성과 보안 동시 확보 / 멀티클라우드 환경의 통제 복잡성 증가

## 핵심 용어
- 공동 책임 모델 (Shared Responsibility Model): 클라우드 인프라 자체의 물리적·가상화 보안은 CSP(AWS, MS 등)가 책임지고, 클라우드 내부의 데이터, OS 설정, 애플리케이션 및 계정 권한 관리는 이용자(고객)가 전적으로 책임지는 보안 분계선 원칙
- CSPM (Cloud Security Posture Management): 멀티클라우드 환경의 수천 개 리소스 설정을 지속적으로 감사하여 퍼블릭 오픈 스토리지, 기본 방화벽 규칙 등 컴플라이언스 위반 및 보안 설정 오류를 자동 탐지하고 교정하는 기술

## 핵심 통찰
- 가트너(Gartner)에 따르면 "2025년까지 발생하는 클라우드 보안 실패의 99%는 클라우드 제공업체의 결함이 아니라 고객의 설정 실수(Misconfiguration)에서 기인"함 → CSP 인프라가 뚫리는 것이 아니라 직원이 S3 버킷을 Public으로 열어두어 털림
- 클라우드는 콘솔 클릭 한 번으로 수천 대의 서버가 열리는 '소프트웨어 정의 인프라'임 → 과거처럼 방화벽 신청서를 내고 일주일 기다리는 수동 방식은 동작하지 않으므로, 코드로 인프라를 배포할 때 보안 룰을 검사하는 'IaC 보안(Policy as Code)'이 필수적임
- 클라우드 내 권한의 90% 이상은 인간이 아닌 '기계(Service Principal, Lambda 역할)'가 가짐 → 이 비인간 신원(NHI)의 과다 권한을 통제하는 CIEM이 최우선 과제임

## 이웃 토픽과 구분
- CSPM vs CWPP: CSPM = 외부 시점의 클라우드 설정 상태 및 API 구성 감사(인프라 자세 평가) / CWPP = 내부 시점의 실행 중인 가상머신 및 컨테이너 런타임 프로세스 감시(워크로드 방어)

## 문제·원인·대책
- 사례: 글로벌 금융사 Capital One에서 오픈소스 WAF의 잘못된 IAM 권한 설정(SSRF 취약점)으로 1억 명 이상의 고객 금융 데이터가 탈취된 사건
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 클라우드 인스턴스 과다 권한 악용을 통한 자산 탈취 (SSRF 공격) | EC2 인스턴스 프로파일에 S3 전체 접근 권한(`*`) 무분별 부여 | 최소 권한 원칙 기반의 CIEM 도입 및 IMDSv2(메타데이터 토큰) 강제 | 인스턴스 침해 시에도 타 리소스 접근 및 메타데이터 탈취 원천 차단 |
| 개발자의 실수로 민감 데이터가 담긴 클라우드 스토리지가 외부에 전체 공개 | 테넌트 단위 기본 보안 통제 미비 및 엑셀 수동 점검 | CSPM 솔루션을 통한 실시간 위험 설정 탐지 및 자동 차단(Remediation) | 공개된 스토리지 버킷 발생 즉시 5초 이내에 자동 비공개 격리 |

## 내 의견
- [클라우드 프로덕션 배포 파이프라인의 IaC 보안 게이트웨이 강제화] 개발자가 AWS 콘솔에서 직접 클릭하여 서버를 생성하도록 허용하면 설정 오류 통제가 불가능함 → 나라면: 콘솔을 통한 리소스 생성을 원천 차단하고 모든 인프라 생성을 테라폼(Terraform) 코드로 일원화한 후, Git 커밋 단계에서 Checkov나 Trivy 같은 정적 IaC 분석기를 연동하여 암호화나 보안 그룹 룰이 누락된 인프라 코드는 배포 파이프라인 자체를 실패 처리하는 'Secure by Design'을 확립
