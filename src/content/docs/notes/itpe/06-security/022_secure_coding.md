## 지식 로드맵 내 현재 위치

소프트웨어 보안 → 안전한 개발 생애주기(SDLC) → 시큐어 코딩 및 소스코드 취약점 진단

## 30초 인출

- **본질:** 소프트웨어 개발 생애주기 전반에 걸쳐 보안 약점을 사전에 제거하여 사이버 침해사고의 원인을 원천 차단하는 개발 기법
- **메커니즘:** 행안부 7대 보안약점 기준 적용 → SAST/SCA 정적 검증 → IAST/DAST 동적 검증 → CI/CD 보안 게이트웨이 차단
- 통찰: 정적 분석(SAST)의 대량 오탐과 런타임 비즈니스 로직 미탐을 해결하기 위해 테인트 분석 기반 오염 경로 필터링과 IAST 에이전트 결합 필수

<details>
<summary>핵심 용어</summary>

- **보안 약점 (CWE, Weakness):** 소프트웨어의 결함, 버그, 설계 오류로 인해 향후 보안 취약점으로 발전할 수 있는 잠재적 원인
- **보안 취약점 (CVE, Vulnerability):** 공격자가 실제로 시스템을 침해하거나 악용할 수 있는 구체적인 보안 결함
- **테인트 분석 (Taint Analysis):** 외부 비신뢰 입력(Source)이 검증 없이 위험한 실행 함수(Sink)로 흘러가는 데이터 흐름을 정밀 추적하는 기법
- **SAST (Static Application Security Testing):** 소스코드를 실행하지 않고 구문 트리(AST)와 제어 흐름 그래프를 분석하여 약점을 찾는 정적 도구
- **IAST (Interactive Application Security Testing):** 애플리케이션 런타임 메모리에 에이전트를 삽입하여 테스트 트래픽 실행 중 취약점을 실시간 검출하는 기술
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **시큐어 코딩(Secure Coding)** 은 기획·설계·구현·테스트 등 소프트웨어 개발 전 과정에 보안 요구사항을 반영하여 소스코드 레벨의 잠재적 보안 약점(Weakness)을 사전에 제거하는 개발 기법 |
| 목적 | 운영 단계 보안 패치 비용의 획기적 절감(Shift-Left), 제로데이 공격 및 데이터 유출 사고 예방, 전자정부 SW 개발보안 컴플라이언스 준수 |

사후 침투 테스트나 방화벽에 의존하던 전통적 보안에서 벗어나 소스코드 자체의 내재적 면역성(Immunity) 확보 지향.

## Ⅱ. 행정안전부 7대 보안약점 기준 및 특징

전자정부 소프트웨어 개발보안 가이드에서 규정한 49개 세부 보안약점 기준.

| 보안약점 분야 | 주요 결함 내용 | 대표적 취약점 예시 |
|---|---|---|
| **1. 입력데이터 검증 및 표현** | 사용자 입력값에 대한 검증 누락으로 시스템 명령이나 쿼리가 임의 실행 | SQL Injection, XSS, Path Traversal, 자원 삽입 |
| **2. 보안 기능** | 인증, 접근통제, 권한관리, 암호화 등 보안 메커니즘의 부적절한 구현 | 하드코딩된 패스워드, 취약한 암호 알고리즘(DES, MD5) |
| **3. 시간 및 상태** | 동시 실행 스레드 간 동기화 부재로 인한 자원 상태 불일치 | 경쟁 조건(Race Condition), 검사시점-사용시점(TOCTOU) |
| **4. 에러 처리** | 예외 처리 미흡으로 시스템 내부 정보 및 스택 트레이스 노출 | 오류 메시지를 통한 정보 노출, 오류 상황 미처리 |
| **5. 코드 오류** | 프로그래밍 언어의 문법적·자원적 오용으로 비정상 종료 유발 | 널 포인터 역참조(Null Pointer Dereference), 메모리 누수 |
| **6. 캡슐화** | 민감 데이터나 내부 디버깅 코드가 외부에 무단 노출 | Private 배열의 Public 반환, 디버그 코드 잔존 |
| **7. API 오용** | 보안상 위험하거나 취약한 라이브러리 및 API의 무분별한 사용 | 취약한 난수 생성기 사용, DNS lookup 기반 보안 결정 |

## Ⅲ. 시큐어 코딩 프로세스 및 AST 메커니즘

```text
[Shift-Left DevSecOps 파이프라인 내 시큐어 코딩 구현 체계]

   [개발자 환경: IDE]              [CI 서버: GitHub Actions]              [CD 및 런타임]
 +--------------------+          +--------------------------+          +-------------------+
 | SonarLint 실시간   |          | SAST (Checkmarx/SonarQube|          | DAST (OWASP ZAP)  |
 | 시큐어코딩 피드백  | -------> | SCA (의존성 오픈소스 분석)| -------> | IAST (컨테이너    |
 | Git Pre-commit Hook|          | Quality Gate (빌드 차단) |          | 에이전트 인메모리)|
 +--------------------+          +--------------------------+          +-------------------+
```

### 1. 소스코드 정적 분석(SAST)의 핵심 테인트(Taint) 분석 메커니즘

```text
[Source] 외부 입력 수신 (request.getParameter("id"))
   | (오염된 데이터 유입: Tainted Data)
   v
[Propagation] 변수 할당 및 문자열 결합 (query = "SELECT * FROM user WHERE id=" + id)
   | (검증/정제 함수 Sanitizer 누락)
   v
[Sink] 데이터베이스 쿼리 실행 (statement.executeQuery(query))  ==> [SQL Injection 결함 탐지]
```

## Ⅳ. 보안 테스팅 기법 3자 심층 비교

| 비교 항목 | 정적 분석 (SAST) | 동적 분석 (DAST) | 대화형 분석 (IAST) |
|---|---|---|---|
| **분석 대상** | 원본 소스코드, 바이트코드 | 실행 중인 웹 애플리케이션 (HTTP) | 런타임 바이트코드 + 실행 트래픽 |
| **수행 시점** | 코딩 중 (IDE) 및 빌드 단계 | 테스트 및 스테이징 배포 후 | 통합 테스트 및 QA 단계 |
| **코드 가시성** | 화이트박스 (코드 라인 지정) | 블랙박스 (URL/파라미터 중심) | **그레이박스 (코드 라인 + 런타임)** |
| **오탐률 (FP)** | 높음 (데이터 흐름 과대추정) | 낮음 (실제 발생 결함만 탐지) | **극도로 낮음 (실제 실행 증명)** |
| **비즈니스 로직**| 로직 흐름 파악 곤란 | 탐지 제한적 | **우수 (실제 권한 흐름 추적)** |
| **대표 도구** | SonarQube, Fortify, Checkmarx | OWASP ZAP, Burp Suite | Contrast Security, Synopsys Seeker |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| **SAST 대량 오탐(False Positive)으로 인한 개발자 피로 및 파이프라인 지연**<br>수만 줄 코드 분석 시 수천 건의 경보가 발생하여 개발자가 실제 취약점을 간과하고 보안 품질 게이트(Quality Gate)를 무력화하는 현상 | **테인트 경로 역추적 정밀화 및 IDE 레벨 사전 차단(Shift-Left)**<br>입력(Source)부터 실행(Sink)까지의 오염 경로에 정제 함수(Sanitizer)가 존재하는지 수학적으로 판별하는 고정밀 테인트 엔진을 적용하고, Git Commit 전 SonarLint 기반 로컬 검사를 통해 빌드 서버 부하 최소화 |
| **런타임 복합 권한 인가 우회(IDOR) 및 비즈니스 로직 취약점 미탐**<br>타인의 계좌 조회나 가격 변조 같은 업무 흐름 결함은 소스코드 문법 검사(SAST)로는 검출이 불가능하여 운영 배포 후 침해 사고 발생 | **IAST 런타임 계측(Instrumentation) 및 보안 단위 테스트(Security BDD)**<br>애플리케이션 JVM에 IAST 센서를 부착하여 QA 테스트 중 발생하는 데이터 흐름과 세션 상태를 실시간 감시하고, 취약점 패턴을 자동화된 단위 테스트(JUnit) 코드로 작성하여 CI 회귀 테스트 강제 |

## Ⅵ. 제언

```text
[현대적 DevSecOps 파이프라인의 보안 게이트웨이 운영 모델]

 +--------------------+     +---------------------+     +--------------------+
 | Commit 단계 (IDE)  | --> | Build 단계 (CI)     | --> | Release 단계 (CD)  |
 | Lint 규칙 위반 차단|     | High/Critical 0개   |     | SBOM / 컨테이너 서명|
 | (소요 시간 < 5초)  |     | 조건 미충족 시 차단 |     | 검증 후 무중단 배포 |
 +--------------------+     +---------------------+     +--------------------+
```

| 파이프라인 단계 | 적용 보안 통제 | 통제 기준 및 액션 |
|---|---|---|
| **1. IDE / Commit** | SonarLint, Git Secrets | 하드코딩된 API Key 커밋 즉각 거부 |
| **2. CI Build** | SAST, SCA(의존성 스캔) | Critical 등급 취약점 발견 시 빌드 FAILED 차단 |
| **3. QA / Stage** | IAST, DAST 자동 스캔 | 런타임 취약점 발견 시 Jira 티켓 자동 발행 |
| **4. Production** | RASP(런타임 자가보호) | 제로데이 공격 시도 시 실시간 세션 차단 |

시큐어 코딩은 개발 완료 후의 일회성 감사가 아니라, CI/CD 파이프라인에 품질 게이트(Quality Gate)로 내재화되어 보안 미달 코드가 배포 단계로 넘어가지 못하도록 강제하는 엔지니어링 거버넌스 확립 권장.
