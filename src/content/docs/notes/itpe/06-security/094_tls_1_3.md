## Ⅰ. TLS 1.3의 개요

- 개념 : 인터넷 통신에서 종단 간(End-to-End) 데이터 기밀성, 무결성, 주체 인증을 보장하기 위해 전송 계층 상위에 동작하는 **암호화 통신 프로토콜**의 최신 표준 규격.
- 배경 및 필요성 : 이전 버전(TLS 1.2 이하)의 취약한 **암호 스위트** (CBC, 정적 RSA)와 2-RTT 연결 지연 문제를 해결하고, 핸드셰이크를 **1-RTT** (또는 0-RTT)로 단축하면서 **완전 순방향 비밀성** (PFS)을 강제하기 위해 **IETF**에서 표준화됨.
- 핵심 목적 : 레거시 취약 암호 알고리즘 제거를 통한 구조적 안전성 확보, 핸드셰이크 RTT 단축을 통한 통신 레이턴시 혁신 및 핸드셰이크 자체의 암호화 달성.

## Ⅱ. TLS 1.3의 핵심 아키텍처 및 동작 메커니즘

TLS 1.3은(는) 신뢰할 수 있는 보안 구조와 표준화된 절차를 기반으로 동작하며, 세부적인 아키텍처와 구성요소 간의 상호작용 메커니즘은 다음과 같음.

```text
[ 클라이언트 (Client) ]                                       [ 서버 (Server) ]
         │                                                            │
         │ 1. ClientHello + Supported Groups + Key Share (ECDHE)      │ (0.5 RTT)
         ├───────────────────────────────────────────────────────────>│
         │                                                            │
         │ 2. ServerHello + Key Share (ECDHE)                         │ (1.0 RTT)
         │    [이 시점 이후 모든 전송 패킷 핸드셰이크 키로 암호화!]   │
         │    {EncryptedExtensions}                                   │
         │    {Certificate (서버 인증서)}                             │
         │    {CertificateVerify (인증서 서명 검증)}                  │
         │    {Finished (서버 핸드셰이크 완료)}                       │
         │<───────────────────────────────────────────────────────────┤
         │                                                            │
         │ 3. {Finished (클라이언트 핸드셰이크 완료)}                 │
         ├───────────────────────────────────────────────────────────>│
         │                                                            │
         │ 4. [양측 마스터 트래픽 키 도출 완료 -> AEAD 응용 데이터 전송] │
         │<==========================================================>│
```

- **1. ClientHello** : 지원 암호군 목록과 함께 자신이 추측한 키 교환 그룹(예: X25519)의 공개 파라미터 전송 (`key_share`, `supported_versions`).
- **2. ServerHello** : 클라이언트가 제시한 그룹 중 하나를 선택하고 자신의 Key Share를 응답하여 공유키 생성 (선택된 `CipherSuite`, Server `key_share`).
- **3. 핸드셰이크 암호화** : 생성된 임시 핸드셰이크 키(Handshake Key)를 사용하여 서버 인증서와 확장 필드 암호화 전송 (AES-GCM / ChaCha20-Poly1305).
- **4. 상호 Finished 검증** : 이전까지 교환된 전체 메시지의 해시값에 대해 HMAC을 계산하여 Finished 교환 및 위변조 검증 (HKDF 기반 finished_key 유도).
- **5. 애플리케이션 데이터** : 트래픽 암호키(Application Traffic Key)로 암호화된 레코드 계층 데이터 송수신 시작 (RFC 8446 AEAD 레코드 페이로드).

## Ⅲ. TLS 1.3의 세부 구성 요소 및 비교 분석

| 비교 항목 | TLS 1.2 (RFC 5246) | TLS 1.3 (RFC 8446) |
|---|---|---|
| 기본 핸드셰이크 지연 | 2-RTT (2회 왕복 후 데이터 전송) | 1-RTT (1회 왕복 후 즉시 데이터 전송) |
| 세션 재개 메커니즘 | Session ID / Session Ticket (1-RTT) | PSK(Pre-Shared Key) 기반 0-RTT 조기 데이터 전송 |
| 키 교환 방식 | 정적 RSA, 정적 DH, DHE, ECDHE 혼용 | **임시 디피-헬만** (DHE, ECDHE)만 허용 (PFS 강제) |
| 암호화 알고리즘 | CBC 모드, RC4, 3DES, AES-GCM 등 복잡 | **AEAD 전용** (AES-GCM, AES-CCM, ChaCha20-Poly1305) |
| 인증서 암호화 | 서버 인증서가 평문(Plaintext)으로 노출 | ServerHello 이후 인증서 전송 구간 암호화 |
| 취약점 노출 위험 | POODLE, BEAST, CRIME, DROWN, ROBOT 취약 | 취약 기능 제거로 기존 알려진 공격 벡터 원천 차단 |

- TLS 1.3은(는) 상기 핵심 비교 지표와 아키텍처 구성을 바탕으로 보안 위협에 대한 방어 효과성을 극대화하며, 기존 레거시 통제 기법 대비 우수한 신뢰성과 운영 효율성을 제공함.

## Ⅳ. TLS 1.3의 주요 한계점 및 해결 방안

- 한계점 : 0-RTT 세션 재개 모드 사용 시 공격자가 조기 데이터 패킷을 가로채 서버에 반복 전송하는 **재생 공격** (Replay Attack) 노출.
  - 해결 방안 : 0-RTT 조기 데이터에는 **멱등성** (Idempotent)이 보장되는 안전한 HTTP GET 요청만 허용하고, Single-Use Ticket 및 서버 측 **Anti-Replay 캐시** (Bloom Filter) 강제.
- 한계점 : 핸드셰이크 및 인증서 구간이 전면 암호화됨에 따라 기업 내부 보안 장비(NGFW, IPS, DLP)의 트래픽 가시성 상실.
  - 해결 방안 : 엔드포인트 EDR 에이전트 기반 로깅을 강화하고, 게이트웨이 구간에서 정당한 기업용 **TLS 프록시** (Forward Proxy)를 통한 복호화 인스펙션 아키텍처 수립.
- 한계점 : ClientHello의 **SNI** (Server Name Indication) 필드가 평문으로 전송되어 도청자에게 접속 도메인이 노출되는 프라이버시 침해.
  - 해결 방안 : DoH(DNS over HTTPS)를 통해 서버의 공개키를 획득하고 SNI를 암호화하여 전송하는 **ECH** (Encrypted Client Hello) 표준 의무화.
- 한계점 : Shor 알고리즘 기반 양자컴퓨터 등장 시 TLS 1.3의 ECDHE 키 교환 및 RSA/ECDSA 서명 체계 일괄 붕괴 위험.
  - 해결 방안 : X25519와 NIST PQC 표준인 **ML-KEM** (Kyber)을 결합한 **하이브리드 키 교환** (X25519Kyber768) 및 하이브리드 서명 체계 사전 도입.

## Ⅴ. TLS 1.3 적용 및 발전을 위한 기술사적 제언

- 프로토콜 현대화 중심의 거버넌스 및 실행 체계 구축 : 웹 서버 및 API 게이트웨이의 TLS 1.2 이전 버전 비활성화 및 0-RTT GET 한정 설정을(를) 적극 추진하여, 통신 레이턴시 혁신 및 레거시 패딩 공격 원천 차단 효과를 극대화해야 함.
- 네트워크 프라이버시 중심의 거버넌스 및 실행 체계 구축 : ECH(Encrypted Client Hello) 및 DNSSEC/DoH 인프라 통합 구축을(를) 적극 추진하여, ISP 및 통신 감청자로부터 대고객 접속 메타데이터 완벽 보호 효과를 극대화해야 함.
- 양자 내성 준비 중심의 거버넌스 및 실행 체계 구축 : OpenSSL 3.x/BoringSSL의 양자 내성 암호(ML-KEM) 하이브리드 키 교환 모듈 활성화을(를) 적극 추진하여, '지금 도청하고 나중에 해독(Harvest Now, Decrypt Later)' 위협 무력화 효과를 극대화해야 함.
