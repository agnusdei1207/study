## 지식 로드맵 내 현재 위치

통신 보안 → 전송 계층 보안(TLS) → TLS 1.3 프로토콜

## 30초 인출

- **본질:** 취약한 암호군과 정적 RSA 키 교환을 전면 제거하고, 1-RTT 기본 핸드셰이크와 AEAD 전용 암호화를 통해 성능 향상과 완전한 전방향 비밀성(PFS)을 강제한 차세대 전송 계층 보안 표준.
- **메커니즘:** ClientHello 단계에서 키 교환 파라미터(Key Share)를 사전 전달하여 1-RTT 만에 공유 대칭키 도출 → 인증서 및 핸드셰이크 패킷 암호화 전송 → AEAD 기반 레코드 계층 데이터 전송.
- 통찰: 지연 시간을 극소화하는 0-RTT 조기 데이터(Early Data)는 재생 공격(Replay Attack)에 본질적으로 취약하므로 멱등(Idempotent) 요청 제한 및 Anti-Replay 캐시 메커니즘 결합 필수.

<details><summary>핵심 용어</summary>

- **TLS 1.3 (RFC 8446 / RFC 9846)**: 전송 계층 보안의 보안성과 성능을 획기적으로 개선한 최신 인터넷 표준 프로토콜.
- **1-RTT 핸드셰이크**: 최초 연결 시 기존 2-RTT였던 암호 협상 과정을 단 1회의 왕복(Round Trip)으로 완료하는 기법.
- **0-RTT (Early Data)**: 이전 연결 경험이 있는 클라이언트가 최초 핸드셰이크 패킷에 암호화된 애플리케이션 데이터를 즉시 실어 보내는 초저지연 모드.
- **완전한 전방향 비밀성(PFS, Perfect Forward Secrecy)**: 서버의 장기 개인키가 사후에 유출되더라도 과거에 기록된 암호화 세션 트래픽을 복호화할 수 없도록 보장하는 암호학적 성질.
- **AEAD(Authenticated Encryption with Associated Data)**: 기밀성(암호화)과 무결성/인증을 단일 연산으로 동시에 제공하는 현대적 암호 모드(AES-GCM, ChaCha20-Poly1305 등).
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 인터넷 통신에서 종단 간(End-to-End) 데이터 기밀성, 무결성, 주체 인증을 보장하기 위해 전송 계층 상위에 동작하는 암호화 통신 프로토콜의 최신 표준 규격 |
| 목적 | 레거시 취약 암호 알고리즘 제거를 통한 구조적 안전성 확보, 핸드셰이크 RTT 단축을 통한 통신 레이턴시 혁신 및 핸드셰이크 자체의 암호화 달성 |

## Ⅱ. TLS 1.3의 핵심 특징 및 보안 설계 원칙

| 특징 항목 | 세부 설계 내용 | 보안 및 성능 가치 |
|---|---|---|
| 1-RTT 핸드셰이크 | 키 교환 파라미터를 최초 ClientHello에 통합하여 1왕복 만에 세션키 생성 완료 | 초기 연결 지연 50% 단축 및 모바일/HTTP/3 최적화 |
| 완전 전방향 비밀성(PFS) | 정적 RSA 및 정적 DH 키 교환 전면 퇴출, 오직 임시 디피-헬만(DHE/ECDHE)만 허용 | 서버 개인키가 탈취되어도 과거 트래픽 복호화 원천 차단 |
| AEAD 암호군 단일화 | 취약한 CBC 모드, 스트림 암호(RC4), 정적 MAC 제거, 오직 AEAD 알고리즘만 채택 | 패딩 오라클(POODLE, Lucky 13) 공격 근본적 차단 |
| 핸드셰이크 자체 암호화 | ServerHello 직후 서버 인증서(Certificate)를 포함한 모든 핸드셰이크 메시지 암호화 | 네트워크 스니핑을 통한 중간자의 서버 인증서 도청 방지 |
| 단순화된 암호군(Cipher Suite) | 알고리즘 조합을 5대 AEAD 암호군으로 축소하여 설정 오류 위험 원천 제거 | TLS_AES_128_GCM_SHA256, TLS_CHACHA20_POLY1305 등 |

## Ⅲ. TLS 1.3 핸드셰이크 및 레코드 암호화 아키텍처

```text
[ 클라이언트 (Client) ]                                       [ 서버 (Server) ]
         │                                                            │
         │ 1. ClientHello + Supported Groups + Key Share (ECDHE)      │ (0.5 RTT)
         ├───────────────────────────────────────────────────────────>│
         │                                                            │
         │ 2. ServerHello + Key Share (ECDHE)                         │ (1.0 RTT)
         │    [이 시점 이후 모든 전송 패킷 핸드셰이크 키로 암호화!]   │
         │    {EncryptedExtensions}                                   │
         │    {Certificate (서버 인증서)}                             │
         │    {CertificateVerify (인증서 서명 검증)}                  │
         │    {Finished (서버 핸드셰이크 완료)}                       │
         │<───────────────────────────────────────────────────────────┤
         │                                                            │
         │ 3. {Finished (클라이언트 핸드셰이크 완료)}                 │
         ├───────────────────────────────────────────────────────────>│
         │                                                            │
         │ 4. [양측 마스터 트래픽 키 도출 완료 -> AEAD 응용 데이터 전송] │
         │<==========================================================>│
```

| 핸드셰이크 단계 | 세부 프로토콜 동작 | 핵심 암호 매개변수 |
|---|---|---|
| 1. ClientHello | 지원 암호군 목록과 함께 자신이 추측한 키 교환 그룹(예: X25519)의 공개 파라미터 전송 | `key_share`, `supported_versions` |
| 2. ServerHello | 클라이언트가 제시한 그룹 중 하나를 선택하고 자신의 Key Share를 응답하여 공유키 생성 | 선택된 `CipherSuite`, Server `key_share` |
| 3. 핸드셰이크 암호화 | 생성된 임시 핸드셰이크 키(Handshake Key)를 사용하여 서버 인증서와 확장 필드 암호화 전송 | AES-GCM / ChaCha20-Poly1305 |
| 4. 상호 Finished 검증 | 이전까지 교환된 전체 메시지의 해시값에 대해 HMAC을 계산하여 Finished 교환 및 위변조 검증 | HKDF 기반 finished_key 유도 |
| 5. 애플리케이션 데이터 | 트래픽 암호키(Application Traffic Key)로 암호화된 레코드 계층 데이터 송수신 시작 | RFC 8446 AEAD 레코드 페이로드 |

## Ⅳ. TLS 1.2 vs TLS 1.3 기술적 차이점 비교

| 비교 항목 | TLS 1.2 (RFC 5246) | TLS 1.3 (RFC 8446 / RFC 9846) |
|---|---|---|
| 기본 핸드셰이크 지연 | 2-RTT (2회 왕복 후 데이터 전송) | 1-RTT (1회 왕복 후 즉시 데이터 전송) |
| 세션 재개 메커니즘 | Session ID / Session Ticket (1-RTT) | PSK(Pre-Shared Key) 기반 0-RTT 조기 데이터 전송 |
| 키 교환 방식 | 정적 RSA, 정적 DH, DHE, ECDHE 혼용 | 임시 디피-헬만(DHE, ECDHE)만 허용 (PFS 강제) |
| 암호화 알고리즘 | CBC 모드, RC4, 3DES, AES-GCM 등 복잡 | AEAD 전용 (AES-GCM, AES-CCM, ChaCha20-Poly1305) |
| 인증서 암호화 | 서버 인증서가 평문(Plaintext)으로 노출 | ServerHello 이후 인증서 전송 구간 암호화 |
| 취약점 노출 위험 | POODLE, BEAST, CRIME, DROWN, ROBOT 취약 | 취약 기능 제거로 기존 알려진 공격 벡터 원천 차단 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 0-RTT 세션 재개 모드 사용 시 공격자가 조기 데이터 패킷을 가로채 서버에 반복 전송하는 재생 공격(Replay Attack) 노출 | 0-RTT 조기 데이터에는 멱등성(Idempotent)이 보장되는 안전한 HTTP GET 요청만 허용하고, Single-Use Ticket 및 서버 측 Anti-Replay 캐시(Bloom Filter) 강제 |
| 핸드셰이크 및 인증서 구간이 전면 암호화됨에 따라 기업 내부 보안 장비(NGFW, IPS, DLP)의 트래픽 가시성 상실 | 엔드포인트 EDR 에이전트 기반 로깅을 강화하고, 게이트웨이 구간에서 정당한 기업용 TLS 프록시(Forward Proxy)를 통한 복호화 인스펙션 아키텍처 수립 |
| ClientHello의 SNI(Server Name Indication) 필드가 평문으로 전송되어 도청자에게 접속 도메인이 노출되는 프라이버시 침해 | DoH(DNS over HTTPS)를 통해 서버의 공개키를 획득하고 SNI를 암호화하여 전송하는 ECH(Encrypted Client Hello) 표준 의무화 |
| Shor 알고리즘 기반 양자컴퓨터 등장 시 TLS 1.3의 ECDHE 키 교환 및 RSA/ECDSA 서명 체계 일괄 붕괴 위험 | X25519와 NIST PQC 표준인 ML-KEM(Kyber)을 결합한 하이브리드 키 교환(X25519Kyber768) 및 하이브리드 서명 체계 사전 도입 |

|---|---|---|
| 프로토콜 현대화 | 웹 서버 및 API 게이트웨이의 TLS 1.2 이전 버전 비활성화 및 0-RTT GET 한정 설정 | 통신 레이턴시 혁신 및 레거시 패딩 공격 원천 차단 |
| 네트워크 프라이버시 | ECH(Encrypted Client Hello) 및 DNSSEC/DoH 인프라 통합 구축 | ISP 및 통신 감청자로부터 대고객 접속 메타데이터 완벽 보호 |
