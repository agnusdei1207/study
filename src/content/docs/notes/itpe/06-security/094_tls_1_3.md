## 답안 골격
```text
[TLS 1.3] ◀━━ 머리: Ⅶ 내 의견 (통신 지연과 보안의 동시 혁신 완성 → TLS 1.2 레거시 완전 비활성화 및 0-RTT 재전송 공격 방지 정책 수립)
 ┃
 ┣━ Ⅰ 개요 ───── TLS 1.2의 취약한 고전 암호 알고리즘을 전면 퇴출하고, 핸드셰이크 지연을 1-RTT(재접속 시 0-RTT)로 획기적으로 단축한 인터넷 전송계층 암호화 표준(RFC 8446)
 ┣━ Ⅱ 특징 ───── 보안성 극대화(취약 알고리즘 삭제, 완전 순방향 비밀성 의무화) · 고속화(1-RTT 핸드셰이크, 0-RTT 조기 데이터) · 핸드셰이크 암호화 범위 확대
 ┣━ Ⅲ 구조 ───── ClientHello(키 공유 파라미터 포함) + ServerHello(인증서/서명 암호화) + 단 5개 AEAD 암호군(AES-GCM, ChaCha20-Poly1305 등)
 ┣━ Ⅳ 흐름 ───── 1-RTT: ClientHello(지원 그룹/Key Share 전송) → ServerHello(Key Share + 암호화된 인증서 전송) → 암호화 통신 즉시 개시 / 0-RTT: 과거 세션키로 즉시 첫 패킷 전송
 ┣━ Ⅴ 비교 ───── TLS 1.3(1-RTT, 0-RTT, 취약 암호 전면 제거, 핸드셰이크 본문 암호화, PFS 강제) vs TLS 1.2(2-RTT, RSA 정적 키 교환 허용, 취약 CBC 모드 허용)
 ┗━ Ⅵ 실무 ───── 0-RTT Replay Attack 방어 / 구형 브라우저 및 방화벽과의 미들박스 비호환성(Middlebox Compatibility Mode) 해결
```
- 필수 키워드: TLS 1.3 · RFC 8446 · 1-RTT 핸드셰이크 · 0-RTT Early Data · 완전 순방향 비밀성(PFS) · AEAD 전용 · 재전송 공격(Replay Attack)
- 기출: 136회 2교시 6번 `인터넷 통신에서 보안성 강화를 위해 활용되는 TLS(Transport Layer Security) 1.2에 대한 취약점이 발견되어 TLS 1.3 사용을 권고하고 있다. 이와 관련하여 다음을 설명하시오.` → Ⅰ TLS 1.2 취약점 + Ⅲ/Ⅳ TLS 1.3의 개선 구조 및 동작 흐름 + Ⅵ 실무 적용 이슈

## 한 줄 본질
- TLS 1.2의 정적 RSA 키 교환 및 CBC 모드로 인한 패딩 오라클 취약점과 2-RTT 연결 지연 병목 → 안전하지 않은 암호군을 전면 폐기하고 키 교환을 첫 패킷에 통합하여 1-RTT로 단축 → 도청 차단(완전 순방향 비밀성) 및 지연 시간 50% 감축 / 0-RTT 사용 시 재생 공격 방어 필요

## 핵심 그림
```text
[TLS 1.2 (2-RTT) vs TLS 1.3 (1-RTT) 핸드셰이크 비교]

  [TLS 1.2 : 2-RTT 지연]                    [TLS 1.3 : 1-RTT 지연]
  Client               Server              Client               Server
    │── ClientHello ────>│                   │── ClientHello ────>│
    │                    │                   │   (+ Key Share)    │ (첫 패킷에 키 교환)
    │<── ServerHello ────│                   │                    │
    │<── Certificate ────│ (평문 노출!)       │<── ServerHello ────│
    │<── KeyExchange ────│                   │   (+ Key Share)    │
    │<── ServerDone ─────│                   │<── Encrypted Cert ─│ (인증서부터 암호화!)
    │── KeyExchange ────>│                   │<── Finished ───────│
    │── Finished ───────>│                   │                    │
    │<── Finished ───────│                   │── Finished ───────>│
    │                    │                   │                    │
    │==== 암호화 통신 ===│ (2-RTT 후)        │==== 암호화 통신 ===│ (1-RTT 만에 완료!)
```

## 핵심 용어
- 완전 순방향 비밀성(Perfect Forward Secrecy, PFS): 서버의 비밀키(개인키)가 훗날 해킹되어 유출되더라도, 과거에 가로채서 보관해 둔 TLS 암호 통신 세션을 복호화할 수 없도록 매 세션마다 임시 키(Ephemeral Diffie-Hellman)를 사용하는 성질
- 0-RTT (Early Data): 과거에 접속했던 서버에 다시 연결할 때, 핸드셰이크가 완료되기도 전인 '첫 번째 요청 패킷'에 이전 세션 티켓으로 암호화한 HTTP GET 데이터를 함께 전송하는 초고속 기법

## 핵심 통찰
- TLS 1.2에서는 서버의 인증서와 도메인 이름(SNI)이 평문으로 날아다녀 중간 통신사나 도청자가 "누가 어느 사이트에 접속하는지" 감청할 수 있었으나, TLS 1.3은 ServerHello 직후부터 인증서를 즉시 암호화하여 사용자 프라이버시를 완벽히 보호함
- 정적 RSA 키 교환을 완전히 삭제하여 '모든 TLS 1.3 세션은 예외 없이 완전 순방향 비밀성(PFS)'을 만족하도록 강제함 → "지금 도청해 두고 10년 뒤 키가 털리면 해독하겠다"는 공격을 원천 무력화함
- 0-RTT는 지연을 극단적으로 줄여주지만, 공격자가 해당 0-RTT 패킷을 가로채 서버에 똑같이 다시 보내는 '재생 공격(Replay Attack)'에 취약함 → 결제나 송금 같은 변경 요청(POST)에는 0-RTT를 금지하고 읽기(GET)에만 허용해야 함

## 이웃 토픽과 구분
- TLS 1.3 vs TLS 1.2: TLS 1.3 = 1-RTT 속도, 임시 디피-헬만(PFS) 강제, AEAD 암호군 5종만 허용 / TLS 1.2 = 2-RTT 지연, 정적 RSA 허용(PFS 미보장), 취약한 CBC/RC4 암호 허용

## 문제·원인·대책
- 사례: TLS 1.2의 CBC 모드 패딩 오류를 이용한 골든두들(GoldenDoodle) 및 패딩 오라클 공격으로 웹 서버 세션 쿠키가 복호화된 침해 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 정적 RSA 키 유출 시 과거 도청된 모든 암호 통신 복호화 | TLS 1.2에서 정적 RSA 키 교환 허용(Forward Secrecy 부재) | TLS 1.3 전면 강제 적용(ECDHE 일시적 키 교환만 허용) | 미래 서버 키 유출 시에도 과거 통신 데이터 기밀성 완벽 유지 |
| 0-RTT 기능 악용을 통한 금융 거래 중복 요청(Replay) 공격 | 0-RTT Early Data의 단방향 전송 특성(상호 챌린지 검증 부재) | 단일 세션 티켓 1회 사용 강제 및 멱등성(GET) 요청에만 0-RTT 허용 | 재생 공격 차단 및 안전한 지연 시간 단축 달성 |

## 이렇게 출제된다
- 제136회 2교시 6번: "인터넷 통신에서 보안성 강화를 위해 활용되는 TLS(Transport Layer Security) 1.2에 대한 취약점이 발견되어 TLS 1.3 사용을 권고하고 있다. 이와 관련하여 다음을 설명하시오." → 요구 포인트: Ⅰ TLS 1.2의 대표적 보안 취약점(정적 RSA, CBC 패딩 오라클, 취약 해시 SHA-1) + Ⅲ TLS 1.3의 핵심 개선점(1-RTT 구조, PFS 의무화, AEAD 전용) + Ⅵ 0-RTT 도입 시 재전송 공격 대응책

## 내 의견
- [TLS 1.2 완전 비활성화(Deprecation) 일정 수립] 여전히 많은 레거시 클라이언트 지원을 핑계로 서버에 TLS 1.0/1.1/1.2를 모두 열어두어 다운그레이드 공격(Downgrade Attack)의 빌미를 제공함 → 나라면: 공공 및 금융 서비스 전산망에서 TLS 1.2 이하의 모든 레거시 버전을 서버 설정(`ssl_protocols TLSv1.3;`)에서 전면 차단하고, ECH(Encrypted Client Hello) 표준을 추가 도입하여 클라이언트가 접속하는 SNI 도메인 주소까지 완벽히 암호화하는 차세대 통신 암호화 체계를 구축
