## 2~4교시 25점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | TLS 1.3은 핸드셰이크로 인증·키 설정을 수행하고 레코드 계층으로 통신을 보호하는 프로토콜 |
| 목적 | 통신 주체 사이의 기밀성·무결성을 갖춘 보안 채널 형성 |
핸드셰이크는 인증·키 설정, 레코드 계층은 데이터 기밀성·무결성 제공. 기본 ClientHello의 SNI는 별도 ECH가 성공적으로 적용되지 않으면 평문 노출 가능.

### Ⅱ. TLS 1.3 핸드셰이크와 레코드 보호

```text
클라이언트 ─ ClientHello·key_share ─→ 서버
            ← ServerHello·key_share ──
            ← 인증서·Finished ────────
            ─ Finished ───────────────→
       양측 키 도출 → AEAD 레코드로 응용 데이터 보호
```

### Ⅲ. TLS 1.2와 개선점·운영 고려

| 항목 | TLS 1.2의 위험 설정 | TLS 1.3의 변화 |
|---|---|---|
| 키 설정 | 정적 RSA 키 교환 허용 | 정적 RSA 키 교환 제거, 공개키 기반 키 설정의 순방향 비밀성 |
| 레코드 보호 | CBC 등 레거시 암호군 허용 | AEAD 중심 |
| 핸드셰이크 | 보통 더 많은 왕복 | 일반 연결 1-RTT |

TLS 1.2의 모든 설정이 취약하다는 뜻은 아니며 안전한 설정의 TLS 1.2와 비교해야 함.

| 운용 항목 | 기대 효과 | 남는 조건 |
|---|---|---|
| TLS 1.3 핸드셰이크 | 협상·키 설정 보호 | 인증서·키 검증 |
| 세션 재개 | 재연결 지연 감소 | 재개 비밀과 정책 관리 |
| 0-RTT | 조기 요청 전송 | 재전송에 안전한 작업만 허용 |
0-RTT 조기 데이터는 재전송 가능성 때문에 중복 실행 위험이 있는 작업에 적용하지 않음. 재개 방식, 암호군·버전 정책, 인증서 검증, 중간 장비와 클라이언트 호환성을 함께 점검. RFC 9846은 RFC 8446을 대체한 TLS 1.3 개정 규격.

### Ⅳ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 0-RTT 조기 데이터는 재전송으로 중복 실행을 일으킬 수 있음 | 재전송에 안전한 요청만 허용하고 인증서·키 설정을 점검 |

### Ⅴ. 제언

0-RTT를 쓰는 서비스는 중복 요청의 업무 영향을 시험하고 PSK 재개 방식의 보안 조건을 따로 확인한다.
