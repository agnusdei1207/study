## 1교시 10점 답안

### 1. 정의·목적

정의: 인젝션은 신뢰할 수 없는 입력이 명령·질의의 일부로 해석되어 의도하지 않은 실행을 일으키는 취약점이다.
목적: 입력을 명령과 분리해 정보 유출·변조·비인가 명령 실행을 막는다.

### 2. 발생 과정과 방어

| 단계 | 동작·통제 |
|---|---|
| 악성 입력 | 신뢰되지 않는 값을 입력받음 |
| 문맥 오염 | 문자열 결합으로 입력이 실행 구문이 됨; 파라미터화로 분리 |
| 실행·피해 | DB·OS 명령 실행; 최소권한·검증·출력처리 적용 |

제안: 입력을 명령문과 분리하는 파라미터화 질의를 기본으로 사용한다.

## 2~4교시 25점 답안

# 인젝션(Injection)

## 핵심 개념
- 신뢰할 수 없는 외부 입력 데이터가 명령문(Command)이나 질의어(Query)의 일부로 인터프리터에 전달되어 의도하지 않은 명령이 실행되거나 데이터가 변조·유출되는 보안 취약점.
- OWASP Top 10의 전통적 핵심 취약점으로, SQL, OS Command, LDAP, XPath, 프롬프트(Prompt) 등 다양한 인터프리터 환경에서 발생.

```
+-------------------------------------------------------------+
|                      인젝션 공격 동작 메커니즘                 |
+-------------------------------------------------------------+
| 1. 악의적 입력 주입 | 특수문자(' ; & | 등)와 함께 악성 구문 삽입     |
| 2. 문맥 오염        | 데이터 필드가 인터프리터의 실행 코드로 해석    |
| 3. 비인가 명령 실행 | DB 덤프, OS 루트 셸 획득, 파일 삭제 등 피해 발생|
+-------------------------------------------------------------+
```

---

## 인젝션 공격 주요 유형 비교

| 인젝션 유형 | 대상 인터프리터 | 공격 입력 예시 | 피해 및 위험도 |
|---|---|---|---|
| **SQL Injection** | DBMS SQL 파서 | `' OR '1'='1` | 인증 우회, 데이터베이스 전량 탈취, 테이블 삭제 |
| **Command Injection** | OS 시스템 셸 (sh, bash, cmd) | `127.0.0.1; cat /etc/passwd` | 서버 운영체제 명령 임의 실행, 백도어 설치 |
| **LDAP Injection** | 디렉터리 서비스(LDAP) | `*)(&)` | 디렉터리 인증 우회, 임직원 조직도 및 정보 노출 |
| **XPath/XQuery Injection** | XML 파서 | `' or '1'='1` | XML 문서 전체 노출, 비인가 XML 노드 조회 |
| **NoSQL Injection** | NoSQL 엔진 (MongoDB 등) | `{"$gt": ""}` | BSON 연산자를 악용한 인증 우회 및 도큐먼트 유출 |
| **Prompt Injection** | LLM 프롬프트 파서 | `"Ignore previous instructions"` | 시스템 지침 무력화, 내부 가드레일 우회 |

## 인젝션 공격 발생 원리 및 방어 메커니즘

```
[취약한 동적 구문 생성 방식]
사용자 입력: admin' --
서버 처리: "SELECT * FROM users WHERE id = '" + userInput + "' AND pw = '" + userPw + "'"
실제 실행: SELECT * FROM users WHERE id = 'admin' --' AND pw = '...'
결과: 주석 처리(--)로 비밀번호 검증이 생략되어 인증 우회 성공

[안전한 구조화 바인딩 방식 (Parameterized Query)]
사용자 입력: admin' --
서버 처리: PreparedStatement 생성 -> "SELECT * FROM users WHERE id = ? AND pw = ?"
바인딩: id 파라미터에 "admin' --" 문자열 리터럴 전체를 단순 데이터로 할당
실제 실행: ID 컬럼 값이 정확히 "admin' --"인 레코드 탐색
결과: 인터프리터 구조 해석 변경 불가 -> 인젝션 원천 무력화
```

---

## 취약점 대응 및 시큐어 코딩 규칙

### 1. 파라미터화된 쿼리(Parameterized Query) 사용
- **PreparedStatement 및 ORM 바인딩**: 동적 문자열 연결(String Concatenation)을 전면 배제하고, 컴파일된 SQL 템플릿에 파라미터 플레이스홀더(`?`)를 사용하는 구조화된 바인딩 강제.

### 2. 정규식 기반 엄격한 화이트리스트 입력 검증
- 입력값의 타입, 길이, 허용 문자셋(예: 알파벳, 숫자만 허용)을 서버 측에서 검증.
- 블랙리스트 필터링(예: `'`, `--` 차단)은 인코딩 우회(URL 인코딩, Hex 등)에 취약하므로 화이트리스트 방식을 원칙으로 함.

### 3. 최소 권한 계정 운용
- 웹 애플리케이션의 DB 연결 계정에서 `DROP`, `ALTER`, `GRANT` 등 DDL 및 관리자 권한을 박탈하고 `SELECT`, `INSERT`, `UPDATE` 권한만 부여.
- OS 시스템 명령 호출 함수(`system()`, `exec()`, `Runtime.getRuntime().exec()`)의 사용을 원천 금지하거나 비특권 계정으로 실행 격리.

### 4. 에러 메시지 은닉 및 WAF 연동
- DBMS 내부 오류나 SQL 구문 오류 메시지가 클라이언트 응답 화면에 출력되지 않도록 차단(Error-based Injection 방어).
- ModSecurity 등 WAF(웹 방화벽)를 전방에 배치하여 알려진 인젝션 시그니처 트래픽 1차 차단.

## 결론 및 실무 시사점
- 인젝션 취약점은 코딩 실수 하나로 시스템 전체 제어권이 공격자에게 넘어가는 치명적인 결함임.
- 입력값 검증과 더불어 매개변수화된 인터페이스 사용을 표준 라이브러리 및 프레임워크 수준에서 강제하고, 정적 분석(SAST) 및 동적 분석(DAST)을 CI/CD 파이프라인에 필수 연동해야 함.
