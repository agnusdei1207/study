## 지식 로드맵 내 현재 위치

사용자 인증 → 공개키 기반 피싱 저항 인증 → 패스워드리스(Passwordless) 패스키

## 30초 인출

- **본질:** 비밀번호 없이 W3C WebAuthn 및 FIDO2 표준 비대칭 공개키 암호화를 활용하여 클라우드 키체인으로 동기화되거나 보안 칩에 격리 저장되는 차세대 피싱 저항성(Phishing-resistant) 인증 자격증명
- **메커니즘:** 등록(RP 챌린지 → 로컬 생체인증 → 키 쌍 생성 후 공개키 등록) → 인증(로그인 챌린지 → RP ID 도메인 일치 확인 → 개인키 전자서명 → RP 공개키 검증)
- 통찰: 도메인 결합을 통한 피싱 사이트 원천 차단 효과에도 불구하고 클라우드 동기화 계정 탈취 및 디바이스 분실 시 대체 복구 채널의 보안 취약성을 극복하기 위해 다중 패스키 등록과 조건부 접근 제어 결합 필수

<details><summary>핵심 용어</summary>

- **패스키(Passkey):** FIDO 얼라이언스와 W3C가 표준화한 다중 기기 지원 발견형(Discoverable) FIDO2 자격증명의 범용 상용 브랜드명.
- **WebAuthn(Web Authentication):** 웹 브라우저와 웹 서비스(RP) 간 공개키 자격증명을 생성하고 검증하기 위한 W3C 표준 JavaScript API.
- **CTAP2(Client to Authenticator Protocol 2):** PC/스마트폰과 외부 하드웨어 보안키(FIDO 토큰) 간 근거리 통신 프로토콜.
- **RP ID(Relying Party ID):** 패스키가 발급된 웹사이트 도메인(예: login.example.com)으로, 피싱 사이트의 도메인 위조를 원천 차단하는 핵심 요소.
- **피싱 저항성(Phishing Resistance):** 사용자가 악의적 피싱 사이트에 속아 접속하더라도 브라우저가 RP ID 불일치를 감지하여 개인키 서명을 거부하는 특성.
- **동기화형 패스키(Synced Passkey):** 애플 키체인, 구글 비밀번호 관리자 등을 통해 종단간 암호화(E2EE)로 다중 기기에 자동 동기화되는 패스키.

</details>

## 2~4교시 예상문제 (25점)

> 패스워드리스 인증 기술인 패스키(Passkey)의 동작 메커니즘(등록 및 인증 절차)과 핵심 구성요소를 설명하고, 기존 패스워드 및 SMS/OTP 대비 우수성과 기기 분실 및 크로스 플랫폼 전환 시 한계 극복 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 웹 브라우저 및 운영체제에 내장된 FIDO2/WebAuthn 표준 기반의 비대칭 공개키 암호화 기술로, 서버에는 공개키만 저장하고 단말에는 개인키를 안전하게 보관하여 비밀번호 없이 로그인하는 차세대 인증 기술 |
| 목적 | 비밀번호 유출, 크리덴셜 스터핑, 피싱 사이트 사칭 공격의 원천 차단 및 사용자 로그인 경험(UX) 극대화 |

## Ⅱ. 패스키의 주요 특징

| 특징 | 세부 내용 | 구현 요소 |
|---|---|---|
| 피싱 저항성 (Phishing Resistance) | 브라우저가 접속 중인 실제 URL의 Origin과 RP ID를 강제 대조하므로 피싱 사이트에서 인증 불가 | WebAuthn origin 바인딩 |
| 서버 측 비밀 비저장 | 서버에는 공개키만 등록되므로 데이터베이스 해킹으로 인한 대규모 비밀번호 유출 사고 원천 차단 | 공개키 암호학(ECC secp256r1) |
| 발견형 자격증명 (Discoverable) | 아이디(ID) 입력 없이도 사용자의 패스키를 브라우저가 자동 식별하여 원터치 생체인증 로그인 지원 | Resident Key (자격증명 검색) |
| 클라우드 키체인 동기화 | 단말 교체 시에도 암호화된 클라우드 백업(Apple, Google)을 통해 새 기기로 안전하게 자동 복원 | 종단간 암호화(E2EE) 키체인 |

## Ⅲ. 패스키 등록 및 인증 아키텍처와 프로세스

```text
[ 패스키 등록 단계 (Registration) ]
사용자 ── 1. 등록 요청 ──▶ 웹 서버 (Relying Party)
                           │ 2. 챌린지(Challenge) + RP ID 생성
브라우저/OS ◀── 챌린지 전송 ──┘
   │
   ├─ 3. 사용자 검증 (지문/Face ID / PIN)
   ├─ 4. TEE 내부에서 비대칭 키 쌍(비밀키/공개키) 생성
   ▼ 5. 공개키 + 서명된 증명(Attestation) 반환
웹 서버 ── 6. 챌린지 및 서명 검증 후 [ 사용자 ID : 공개키 ] DB 저장 완료!

[ 패스키 인증 단계 (Authentication) ]
사용자 ── 1. 로그인 시도 ──▶ 웹 서버 (RP)
                             │ 2. 일회성 챌린지(Challenge) 발급
브라우저/OS ◀── 챌린지 전송 ────┘
   │
   ├─ 3. 브라우저가 현재 도메인과 RP ID 일치 여부 엄격 검증 (피싱 차단)
   ├─ 4. 생체인증 확인 후 저장된 개인키로 챌린지 전자서명 (Assertion)
   ▼ 5. 서명값 + 클라이언트 데이터 서버로 전송
웹 서버 ── 6. 서버에 보관된 공개키로 서명 유효성 검증 성공 시 세션 발급 완료!
```

| 단계 | 수행 주체 | 상세 활동 내용 |
|---|---|---|
| 1. 등록 요청 | 사용자 / 클라이언트 | 패스키 등록 선택, navigator.credentials.create() 호출 |
| 2. 챌린지 발급 | RP (서비스 서버) | 재전송 공격 방지를 위한 무작위 암호학적 난수 챌린지 생성 |
| 3. 로컬 사용자 확인 | 인증기 (Authenticator) | 기기 내 생체인식(Touch ID/Windows Hello)으로 로컬 잠금 해제 |
| 4. 키 쌍 생성 | 인증기 TEE/SE | ECC P-256 비대칭 키 쌍 생성, 개인키는 보안 칩에 영구 격리 |
| 5. 인증 수행 | 브라우저 / RP | navigator.credentials.get() 호출, RP ID 검증 후 서명 생성 및 검증 |

## Ⅳ. 패스키 vs 패스워드 vs 2차 인증(SMS/OTP) 비교

| 구분 | 전통적 패스워드 | 2차 인증 (SMS / TOTP) | 패스키 (Passkey) |
|---|---|---|---|
| 인증 요소 | 지식 기반 (Something you know) | 소유 기반 결합 (MFA) | 소유(기기 보안칩) + 생체(고유특징) |
| 피싱 공격 내성 | 취약 (가짜 사이트에 입력 시 유출) | 취약 (실시간 피싱 프록시 AitM 우회) | **완전 면역 (Origin 바인딩으로 원천 차단)** |
| 서버 침해 위험 | 해시 덤프 탈취 시 크래킹 위험 | SMS 인터셉트 및 SIM 스와핑 위험 | 공개키만 보관하므로 탈취 위험 전무 |
| 사용자 편의성 | 복잡한 규칙 암기 및 변경 스트레스 | 코드 복사 및 입력 번거로움 | 생체인증 1회로 즉시 로그인 완료 |
| 분실 복구 방식 | 이메일/문자 본인확인 재설정 | 백업 코드, 관리자 수동 초기화 | 클라우드 계정 E2EE 백업 동기화 |

## Ⅴ. 패스키 도입 및 운영의 한계와 방안

| 한계 | 방안 |
|---|---|
| 애플(Apple), 구글(Google), MS 등 플랫폼 생태계 간 패스키 교차 전송 불가(Platform Lock-in)로 기기 변경 시 마이그레이션 장애 | FIDO 얼라이언스의 자격증명 교환 프로토콜(CXP, Credential Exchange Protocol) 표준 채택 및 서드파티 비밀번호 관리자(1Password, Bitwarden) 연동 |
| 스마트폰 분실 및 동기화 클라우드 계정(Apple ID/Google 계정) 탈취 시 모든 패스키가 일괄 노출되는 단일 장애점(SPOF) 리스크 | 단일 기기 종속형 하드웨어 보안키(YubiKey)를 보조 패스키로 등록 권장 및 클라우드 복구 시 하드웨어 2단계 인증 강제 |
| 레거시 엔터프라이즈 사내 인트라넷 및 WebAuthn API를 지원하지 않는 노후 시스템에서의 도입 불가 | 현대적 OIDC/SAML 기반 중앙 IdP(Identity Provider)를 전면에 배치하고 레거시 시스템은 페더레이션 SSO로 간접 수용 |

## Ⅵ. 제언

```text
[ 취약한 레거시 인증 ]                 [ 피싱 저항성 패스워드리스 체계 ]
비밀번호 암기/재사용 ─┐               ┌── FIDO2 / WebAuthn 비대칭 암호키 체계
피싱 사이트 탈취 노출 ┼─→ [ 계정 탈취 ] ─┼── 도메인(RP ID) 기반 피싱 원천 차단
SMS 인증 가로채기 ───┘               └── 클라우드 E2EE 백업 및 하드웨어 토큰 연계
```

| 평가 영역 | 비밀번호 + OTP 체계 | 패스키 단독 체계 | 향후 발전 방향 |
|---|---|---|---|
| 인증 보안성 | AitM 프록시 피싱에 취약 | 피싱 공격 수학적 차단 | 지속적 상황 인지 적응형 인증 결합 |
| 관리 비용 | 패스워드 재설정 지원 비용 발생 | 헬프데스크 리셋 요청 80% 절감 | 무자격증명(Zero-Knowledge) 신원 증명 |
| 글로벌 표준 | 각 사이트별 상이한 규칙 | W3C / FIDO 글로벌 표준 통일 | 탈중앙 신원증명(DID)과 패스키 연동 |

패스키(Passkey)는 수십 년간 지속된 패스워드의 구조적 취약점을 종식시키는 가장 진보된 패스워드리스 인증 규격이며, 피싱 저항성과 사용자 편의성을 동시에 보장하는 현대 IAM 인프라의 필수 표준.

## 출제 이력과 검증 출처

- 정보관리기술사 제131회 1교시 (FIDO2 및 WebAuthn 인증 기술)
- 정보관리기술사 제124회 2교시 (패스워드리스 인증 체계 구현 방안)
- W3C Recommendation: Web Authentication (WebAuthn Level 3)
- FIDO Alliance: Passkey Implementation Guidance and Security Whitepaper
- NIST SP 800-63B: Digital Identity Guidelines (AAL3 피싱 저항 인증 요건)
