## 연관 키워드

- 패스키, Passkey, FIDO2, WebAuthn, 비대칭 공개키 암호, RP ID, 챌린지
- 인증기, 피싱 내성, 크리덴셜 스터핑, 중간자 공격, AitM, SIM 스와핑
- 플랫폼 종속, 단일 장애점, 하드웨어 보안키, IdP, OIDC, SAML, SSO

## Ⅰ. 패스키의 개요

- 핵심 요약 : 기기에 개인키를 두고 서버에는 공개키만 등록하여 비밀번호 없이 로그인하는 차세대 인증 기술.
- 개념 : 웹 브라우저와 운영체제에 내장된 **FIDO2** 표준 기반의 **비대칭 공개키 암호** (Asymmetric Public-Key Cryptography) 방식으로, 서버는 공개키만 저장하고 단말은 개인키를 보안 영역에 보관하여 로그인하는 인증 기술 (**패스키**, Passkey).
- 배경 및 필요성 : 비밀번호 체계는 **크리덴셜 스터핑** (Credential Stuffing), 피싱 사이트를 통한 자격증명 탈취, 비밀번호 재사용 위험에 노출되고, SMS와 OTP(One-Time Password) 기반 2차 인증도 중간자 공격 (AitM, Adversary-in-the-Middle)으로 우회될 수 있어 새로운 인증 구조가 필요해짐.
- 주요 목적 : 비밀번호 유출, 크리덴셜 스터핑, 피싱 사칭 공격을 구조적으로 차단하면서 로그인 경험을 단순화.

## Ⅱ. 패스키의 특징 및 장점

- 핵심 요약 : 비대칭 키, 도메인 바인딩, 로컬 사용자 확인이 결합되어 서버 유출과 피싱의 영향을 줄이는 방식.

1. 비대칭 키 기반 인증 : 개인키는 기기에 두고 서버에는 공개키만 보관 → 서버 유출 시에도 재사용 가능한 비밀 값이 남지 않음.
2. 도메인 바인딩 (**RP ID**, Relying Party Identifier) : 브라우저가 등록된 도메인과 일치할 때만 서명을 허용 → 가짜 사이트에서는 서명 자체가 불가능해 피싱 차단.
3. 로컬 사용자 확인 : 생체 인식이나 PIN으로 기기 잠금을 해제한 뒤 서명 → 기기를 훔쳐도 무단 사용이 어려움.
4. **챌린지-응답** 방식 : 매 인증마다 새로 발급된 챌린지에 서명 → 이전 인증 값의 재전송 공격 차단.
5. 플랫폼 동기화 : 사용자 계정의 암호화 백업으로 패스키를 기기 간 동기화 → 기기 분실 시 복구 부담 감소.

## Ⅲ. 패스키의 구조 (흐름)

- 핵심 요약 : 등록 단계에서 기기가 키 쌍을 만들고 공개키를 서버에 넘기며, 인증 단계에서 서버가 챌린지에 대한 서명을 검증하는 2단계 구조.

1. 등록 요청 : 사용자가 패스키 등록을 선택하고 브라우저가 등록 절차를 시작.
2. 챌린지 발급 : 웹 서버 (**RP**, Relying Party)가 재전송 방지용 무작위 챌린지와 RP ID를 생성.
3. 사용자 검증 : **인증기** (Authenticator)가 생체 인식이나 PIN으로 사용자 본인을 확인.
4. 키 쌍 생성 : 인증기가 보안 영역 (TEE(Trusted Execution Environment) 또는 SE(Secure Element))에서 비대칭 키 쌍을 만들고 개인키는 기기 밖으로 내보내지 않음.
5. 인증 수행 : 서버가 발급한 챌린지에 개인키로 서명하고, 서버가 보관한 공개키로 검증.

```text
[ 패스키 등록 흐름 ]

사용자 → 웹 서버(RP): 등록 요청
      ↓
웹 서버: 챌린지와 RP ID 발급
      ↓
인증기: 사용자 검증 (생체·PIN)
      ↓
인증기: 키 쌍 생성, 개인키는 기기 내 보관
      ↓
웹 서버: 공개키를 사용자 ID와 함께 저장
```

```text
[ 패스키 인증 흐름 ]

웹 서버(RP): 일회성 챌린지 발급
      ↓
브라우저: RP ID와 현재 도메인 일치 검증
      ↓
인증기: 생체 확인 후 개인키로 서명
      ↓
웹 서버: 저장된 공개키로 서명 검증
```

## Ⅳ. 패스키와 기존 인증 방식의 비교

- 핵심 요약 : 패스키는 피싱 내성과 서버 침해 영향 측면에서 기존 방식보다 구조적으로 우수하지만, 플랫폼 종속과 복구 체계라는 새 과제를 동반.

| 비교 항목 | 전통적 패스워드 | 2차 인증 (SMS, TOTP(Time-based One-Time Password)) | 패스키 |
| --- | --- | --- | --- |
| 인증 요소 | 지식 기반 | 지식과 소유의 결합 (MFA, Multi-Factor Authentication) | 기기 보안 영역의 소유 요소와 생체 확인 |
| 피싱 내성 | 취약 (가짜 사이트에 입력 시 유출) | 취약 (실시간 중간자 공격으로 우회 가능) | 도메인 바인딩으로 구조적 차단 |
| 서버 침해 영향 | 해시 탈취 시 오프라인 크래킹 위험 | SMS 가로채기와 SIM 스와핑 위험 | 공개키만 보관하여 탈취 가치가 낮음 |
| 사용자 편의성 | 복잡한 규칙 암기와 주기적 변경 | 코드 확인과 입력의 번거로움 | 생체 확인만으로 즉시 로그인 |
| 분실 복구 | 본인 확인 후 재설정 | 백업 코드, 관리자 수동 초기화 | 플랫폼 계정 동기화 백업으로 복구 |

- 선택 기준 : 피싱 위험이 큰 고위험 계정과 신규 서비스에는 패스키를, 기존 시스템 연동이 필요한 구간에는 2차 인증을 병행하는 방식을 검토.

## Ⅴ. 패스키의 한계와 방안

- 핵심 요약 : 플랫폼 종속, 동기화 계정 단일 장애점, 레거시 시스템 미지원을 표준 교환 규격, 보조 키, 중앙 IdP로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 플랫폼 종속 (Platform Lock-in) | 생태계 간 패스키 교차 전송이 제한되어 기기 변경 시 이전 장애 | FIDO 얼라이언스가 추진하는 자격증명 교환 규격의 도입과 서드파티 비밀번호 관리자 연동 | 자격증명 이전 성공률 |
| **단일 장애점** (SPOF, Single Point of Failure) | 동기화 클라우드 계정이 탈취되면 패스키가 일괄 노출 | 하드웨어 보안키(예: YubiKey)를 보조 인증 수단으로 등록하고, 복구 시 추가 인증 강제 | 보조 키 등록률 |
| 레거시 시스템 미지원 | WebAuthn을 지원하지 않는 사내 시스템에서 도입 불가 | **중앙 IdP** (Identity Provider)를 두고 OIDC(OpenID Connect)와 SAML(Security Assertion Markup Language)로 연계, 레거시는 페더레이션 SSO(Single Sign-On)로 수용 | IdP 연계 시스템 비율 |

## Ⅵ. 패스키에 대한 기술사적 제언

- 핵심 요약 : 패스워드 중심 인증을 단계적으로 줄여 패스키를 기본 수단으로 두고, 고위험 권한과 복구 체계를 함께 설계하는 방향.

1. 조직은 패스워드 중심 인증을 단계적으로 줄이고 패스키를 기본 인증 수단으로 제공하되, 기존 시스템과의 연계는 중앙 IdP를 통해 관리하는 체계를 마련할 필요가 있음.
2. 관리자 계정 같은 고위험 권한에는 패스키와 하드웨어 보안키를 함께 요구하여, 동기화 계정 하나의 장애가 전체 권한 탈취로 이어지지 않도록 정책을 설계하는 것이 바람직함.
3. 서비스 제공자는 도메인 바인딩을 전제로 한 인증 설계와 분실 시 복구 절차를 함께 정의하여, 편의성과 보안을 동시에 확보하는 운영 기준을 세울 필요가 있음.

## Ⅶ. 결론

- 핵심 요약 : 패스키는 공개키 서명과 도메인 바인딩으로 피싱과 서버 유출의 영향을 줄이는 차세대 인증 방식.
- 시사점 : 인증 수단의 전환 성패는 인증 자체보다 복구와 플랫폼 이동 체계의 설계에 달려 있으므로, 전환 계획에 복구 정책을 함께 포함해야 함.
