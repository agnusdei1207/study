## 지식 로드맵 내 현재 위치

지식 위치: 정보보안 → 암호 기법 비교 → **대칭키 vs 비대칭키 암호**

## 30초 인출

- **본질:** 암·복호화에 동일한 비밀키를 사용하여 대용량 데이터 처리에 최적화된 대칭키와, 수학적 난제를 기반으로 공개키·개인키 쌍을 분리하여 키 교환과 전자서명을 제공하는 비대칭키 암호 방식
- **메커니즘:** 비대칭키(ECDHE/KEM)로 일회용 세션키 안전 교환(키 설정) $\rightarrow$ 대칭키 AEAD(AES-GCM)로 대용량 데이터 고속 암복호화(하이브리드 암호 체계)
- **통찰:** 공개키 바꿔치기 위협은 PKI 인증서 체인으로 방어하고 쇼어 알고리즘 양자 해독 위험은 격자 기반 양자내성암호(PQC: ML-KEM) 하이브리드 전환 필수

<details>
<summary>핵심 용어</summary>

- **대칭키 암호** : 암호화 키와 복호화 키가 동일한 암호 방식 (AES, ARIA, ChaCha20).
- **비대칭키 암호** : 수학적 트랩도어 함수 기반의 공개키와 개인키 쌍을 사용하는 공개키 암호 방식 (RSA, ECC, ML-KEM).
- **하이브리드 암호 (Hybrid Cryptosystem)** : 비대칭키의 키 교환 편의성과 대칭키의 고속 연산 장점을 결합한 구조 (TLS 1.3).
- **PFS (Perfect Forward Secrecy)** : 장기 개인키가 사후 유출되어도 과거의 세션 암호문이 복호화되지 않는 순방향 비밀성.

</details>

## 2~4교시 예상문제 (25점)

> 대칭키 암호와 비대칭키(공개키) 암호의 수학적 기반, 키 관리, 연산 성능 및 보안 특성을 비교하고, 현대 통신(TLS 1.3)의 하이브리드 암호화 아키텍처와 양자 컴퓨터 위협에 대응하는 엔지니어링 방안을 제시하시오. (제132회 1교시 기출 연계·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 동일한 단일 비밀키를 공유하여 데이터를 암·복호화하는 대칭키(Symmetric Key) 암호와, 수학적 일방향 함수를 기반으로 공개키와 개인키를 분리 사용하는 비대칭키(Asymmetric Key) 암호의 기술 체계 |
| 목적 | 데이터 기밀성(대칭키)과 키 분배·전자서명·부인방지(비대칭키)의 장점을 상호 보완하여 안전하고 효율적인 종단간 암호 통신 환경 확립 |

- 대칭키의 치명적 약점인 '키 사전 분배 문제'를 비대칭키가 해결하고, 비대칭키의 약점인 '느린 연산 속도'를 대칭키가 보완하는 상호 공생적 현대 암호학의 양대 축

## Ⅱ. 대칭키 vs 비대칭키 암호의 핵심 기술적 특성

| 특성 항목 | 대칭키 암호 (Symmetric) | 비대칭키 암호 (Asymmetric) |
|---|---|---|
| 키의 구조 | 단일 비밀키 (Secret Key) | 수학적으로 결속된 공개키(Public) + 개인키(Private) 쌍 |
| 수학적 기반 | 치환-순열 네트워크(SPN), 페이스텔(Feistel) 구조 | 소인수분해(RSA), 이산대수(DH), 타원곡선(ECC), 격자(LWE) |
| 연산 속도 및 자원 | 극도로 빠름 (비대칭키 대비 100~1,000배 이상 빠름) | 복잡한 거듭제곱·스칼라 곱셈으로 느림 (CPU 집약적) |
| 키 개수 ($n$명 기준) | $n(n-1)/2$ 개 (참여자 증가 시 $O(n^2)$ 키 폭증) | $2n$ 개 (사용자당 공개키 1개, 개인키 1개 관리) |
| 핵심 제공 기능 | 대용량 데이터 기밀성, 고속 블록 암호화, HMAC | 키 교환/합의, 전자서명(부인 방지), 공개 신원 인증 |
| 대표 알고리즘 | AES-256, ARIA, LEA, ChaCha20 | RSA-3072, ECDSA, Ed25519, ML-KEM (Kyber) |

- 현대 정보보안 시스템은 두 암호를 단독으로 쓰지 않고 세션 수립 단계(비대칭)와 데이터 전송 단계(대칭)를 분리하는 하이브리드 결합 특성 보유

## Ⅲ. 현대 하이브리드 암호화 아키텍처 및 세션 수립 프로세스

```text
[TLS 1.3 기반 하이브리드 암호 세션 수립 및 데이터 보호 메커니즘]

  [클라이언트 (Browser)]                                [서버 (Web Server)]
            │                                                    │
            │ 1. ClientHello                                     │
            │    - 지원 암호 스위트 (TLS_AES_256_GCM_SHA384)      │
            │    - ECDHE 임시 공개키 (KeyShare_Client)            │
            ├───────────────────────────────────────────────────>│
            │                                                    │ 2. ECDHE 키쌍 생성 및 세션키 계산
            │ 3. ServerHello                                     │    Server Secret = (Priv_S * Pub_C)
            │    - 선택 암호 스위트, KeyShare_Server             │    HKDF(Server Secret) -> Session Key
            │ 4. {EncryptedExtensions, Certificate, CertVerify}  │
            │    - 서버 X.509 인증서 (디지털 서명 검증용)        │
            │<───────────────────────────────────────────────────┤
            │                                                    │
            │ 5. 서버 인증서 체인 검증 (PKI)                     │
            │ 6. 세션키 계산: Client Secret = (Priv_C * Pub_S)   │
            │    HKDF(Client Secret) -> Session Key 확정         │
            │                                                    │
            │<============ 대칭키(AES-256-GCM) 암호화 통신 =====>│
            │ 7. 고속 대용량 HTTP 페이로드 기밀성/무결성 전송    │
```

| 처리 단계 | 적용 암호 방식 | 핵심 엔지니어링 세부 동작 |
|---|---|---|
| 1. 키 교환 파라미터 전달 | 비대칭키 (ECDHE) | 클라이언트와 서버가 임시 타원곡선 키쌍(Ephemeral Key) 교환 |
| 2. 서버 신원 인증 | 비대칭키 (전자서명 / PKI) | 서버 인증서의 공개키 서명을 공인 CA 루트 인증서로 검증 (사칭 방어) |
| 3. 대칭 세션키 도출 | 키 유도 함수 (HKDF) | 공유된 비대칭 공통 비밀(Shared Secret)로부터 대칭키 $K_{session}$ 파생 |
| 4. 페이로드 암복호화 | 대칭키 (AES-GCM AEAD) | 기밀성 암호화 및 128비트 인증 태그를 동시 생성하여 고속 스트리밍 |

## Ⅳ. 대칭키 암호 vs 비대칭키 암호 심층 비교

| 비교 항목 | 대칭키 암호 (Symmetric) | 비대칭키 암호 (Asymmetric) |
|---|---|---|
| 보안 강도 기준 | 128비트, 256비트 (키 길이 = 보안 강도) | RSA 2048/3072비트, ECC 256/384비트 |
| 키 분배 메커니즘 | 사전에 안전한 채널 필요 (Key Distribution Problem) | 공개 채널을 통해 자유롭게 배포 가능 |
| 부인 방지(Non-repudiation) | 불가 (양측이 동일한 키를 소유하므로 송신 부인 가능) | 가능 (오직 송신자 본인만 아는 개인키로 서명) |
| 전송 오버헤드 | 데이터 길이와 거의 동일 (스트림 또는 1블록 패딩) | 키 크기가 크고 암호문 패딩 오버헤드 발생 |
| 하드웨어 가속 | AES-NI 명령어 셋 지원으로 초당 수십 Gbps 가속 | 큰 정수 곱셈 및 모듈러 연산으로 가속기 부하 큼 |
| 양자 컴퓨팅 내성 | 그로버(Grover) 알고리즘으로 키 강도 절반 (AES-256 안전) | 쇼어(Shor) 알고리즘으로 RSA/ECC 완전 붕괴 (치명적) |

## Ⅴ. 암호 시스템 구축 시 엔지니어링 한계와 해결 방안

| 한계 | 방안 |
|---|---|
| 비대칭키 공개 채널 배포 시 공격자가 중간에서 자신의 가짜 공개키로 바꿔치기하는 중간자 사칭 공격(MitM) 취약 | 신뢰할 수 있는 공인 인증기관(CA)의 X.509 디지털 인증서 체인 검증을 필수화하고, 브라우저/클라이언트 단에 인증서 투명성(Certificate Transparency: CT) 및 OCSP Stapling 강제 |
| 통신 세션의 장기 개인키가 사후 유출될 경우 공격자가 과거에 캡처해 둔 모든 대칭 세션 통신을 소급 복호화하는 취약점 | 정적 RSA 키 교환을 전면 폐지하고, 세션마다 일회용 임시 키쌍을 생성·폐기하여 완전 순방향 비밀성(PFS: Perfect Forward Secrecy)을 보장하는 ECDHE 키 교환 프로토콜 강제 |
| 대칭키를 다수의 시스템에 분배할 때 통신 노드 수($n$) 증가에 따라 키 관리 개수가 $n(n-1)/2$로 기하급수적 폭증 | 중앙 집중형 키 관리 시스템(KMS: HashiCorp Vault, AWS KMS)을 구축하고 엔벨로프 암호화(Envelope Encryption: DEK + KEK 2계층) 구조 적용 |
| 미래 고성능 양자 컴퓨터 출현 시 쇼어(Shor) 알고리즘에 의해 기존 비대칭 암호(RSA, ECC)가 다항 시간 내 완전 무력화 | 격자 기반 양자내성암호(PQC) 표준인 ML-KEM(Kyber) 및 ML-DSA(Dilithium)를 도입하고, 고전 암호와 PQC를 결합하는 하이브리드 키 교환(X25519 + Kyber768) 사전 배포 |

## Ⅵ. 양자 내성 및 암호 민첩성(Crypto Agility) 아키텍처 제언

```text
[포스트 퀀텀 대비 하이브리드 차세대 암호 아키텍처]

 ┌─────────────────────────────────────────────────────────────┐
 │                 1. 암호 민첩성 계층 (Crypto Agility)         │
 │   - 하드코딩된 암호 알고리즘 제거 -> 설정 기반 동적 스위칭  │
 │   - OpenSSL 3.0+ / Bouncy Castle PQC 프로바이더 연동        │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │              2. 하이브리드 키 교환 계층 (Hybrid KEM)        │
 │   - 고전 타원곡선(X25519) + NIST 표준 PQC(ML-KEM-768) 결합 │
 │   - 두 알고리즘 중 하나가 해독되어도 세션 보안 완전 유지    │
 └──────────────────────────────┬──────────────────────────────┘
                                │
 ┌──────────────────────────────┴──────────────────────────────┐
 │                 3. 양자 안전 대칭 암호 계층 (Quantum-Safe)   │
 │   - Grover 알고리즘 대비 AES-256 / ARIA-256 표준 강제      │
 │   - Envelope Encryption 기반 대칭키 주기적 자동 로테이션   │
 └─────────────────────────────────────────────────────────────┘
```

| 관리 영역 | 핵심 엔지니어링 세부 과제 | 통제 목표치 |
|---|---|---|
| 세션 기밀성 | 전사 TLS 통신에서 PFS(완전 순방향 비밀성) 지원 암호 스위트 적용 | PFS 적용률 100% (정적 RSA 교환 0건) |
| 대칭키 암호 강도 | 데이터 저장 및 전송 구간 대칭키를 최소 256비트(AES-256)로 상향 | 128비트 이하 취약 암호화 0건 |
| PQC 전환 준비 | 사내 핵심 인증·KMS 인프라의 PQC 알고리즘 호환성 테스트베드 구축 | 양자내성암호 마이그레이션 적합성 100% |
