## 한 줄 본질
- 대칭키는 키를 나눠주기 어렵고 비대칭키는 연산이 너무 느린 상충 병목 → 비대칭키(ECDH/RSA)로 일회용 세션키만 안전하게 교환하고 본문 데이터는 대칭키(AES)로 고속 암호화(하이브리드 암호) → 안전성과 속도의 완벽한 결합 달성 / 암호 프로토콜 핸드셰이크 오버헤드 발생

## 핵심 용어
- 키 배송 문제 (Key Distribution Problem): 대칭키 암호에서 송신자와 수신자가 도청 위험이 있는 공인 인터넷망을 통해 암호화에 사용할 비밀키를 상대방에게 안전하게 전달할 수 없는 고전적 한계
- 하이브리드 암호 시스템 (Hybrid Cryptosystem): 속도가 빠른 대칭키 암호의 장점과 키 관리가 편리한 공개키 암호의 장점만을 결합하여, 세션키 교환에는 공개키 암호를 쓰고 실제 데이터 전송에는 대칭키 암호를 사용하는 복합 기법

## 핵심 통찰
- 대칭키와 비대칭키는 "경쟁 관계"가 아니라 "상호보완적인 부부 관계"임 → 어느 하나만 단독으로 쓰면 인터넷 뱅킹이나 HTTPS는 성립할 수 없음
- 사용자 수가 1,000명일 때 대칭키는 무려 499,500개($1000 \times 999 / 2$)의 서로 다른 비밀키를 쌍마다 만들어 보관해야 하므로 키 관리가 불가능에 이름 → 비대칭키는 각자 키 쌍 1개씩 총 2,000개($2n$)의 키만 있으면 됨
- 양자 컴퓨터가 등장했을 때의 파급력도 다름 → 쇼어 알고리즘에 의해 비대칭키(RSA, ECC)는 즉시 영구 파괴되지만, 대칭키(AES-256)는 그로버(Grover) 알고리즘으로도 키 길이가 절반(128비트 강도)으로 줄어들 뿐 여전히 안전함

## 이웃 토픽과 구분
- 블록 암호 vs 스트림 암호: 대칭키 내부에서의 분류축(고정 블록 단위 뒤섞기 vs 비트/바이트 단위 연속 XOR) / 대칭키 vs 비대칭키 = 암호화 키와 복호화 키의 일치 여부를 가르는 근본 분류축

## 문제·원인·대책
- 사례: 모바일 클라이언트가 대용량 파일(1GB)을 전송하면서 RSA 알고리즘으로 직접 암호화를 시도하여 스마트폰 CPU가 100% 포화되고 배터리가 방전된 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 비대칭키를 이용한 대용량 데이터 직접 암호화로 인한 극심한 성능 저하 | 비대칭키 알고리즘의 거듭제곱 및 소인수분해 연산 복잡도 | 하이브리드 암호(AES-256 대칭키로 데이터 암호화 + RSA로 대칭키만 암호화) 전환 | 처리 속도 수백 배 향상 및 단말 CPU 부하 최소화 |
| 사내 시스템 간 통신에서 하드코딩된 단일 대칭키 노출 | 대칭키 배송의 어려움으로 인해 소스코드 내 비밀키 고정 | ECDH(타원곡선 디피헬만) 기반 동적 키 교환 및 완전순방향비밀성(PFS) 보장 | 키 탈취 시에도 과거 통신 복호화 원천 차단 |

## 이렇게 출제된다
- 제132회 1교시 4번: "대칭 암호화와 비대칭 암호화" → 요구 포인트: Ⅰ 대칭키/비대칭키 개념 + Ⅲ 하이브리드 암호 아키텍처 + Ⅴ 8대 비교축 종합 비교표

## 내 의견
- [공개키 암호의 PQC(양자내성암호) 전환 및 대칭키 256비트 표준화] '지금 도청하고 나중에 해독한다(Store Now, Decrypt Later)'는 국가 배후 조직의 도청 위협에 대비해야 함 → 나라면: 모든 신규 암호화 시스템의 대칭키를 AES-128에서 AES-256으로 상향하고, 키 교환에 사용되는 비대칭키 알고리즘을 기존 X25519와 격자 기반 PQC(ML-KEM/Kyber)를 결합한 '하이브리드 양자내성 키 교환'으로 즉시 전환
