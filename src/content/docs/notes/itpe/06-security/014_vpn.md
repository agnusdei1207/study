## Ⅰ. VPN(Virtual Private Network)의 개요

- 개념 : 공중 인터넷망(Public Network) 상에 암호화 터널링(Tunneling) 기술을 적용하여 마치 전용 사설망(Private Network)을 구축한 것처럼 안전한 통신 환경을 제공하는 가상사설망 기술.
- 배경 및 필요성 : 원격지 지사 간의 물리적 전용선(Leased Line) 구축에 따르는 막대한 비용 부담을 해소하고, 원격/재택근무자의 본사 사내망 안전 접속을 실현하기 위해 광범위하게 도입됨.
- 핵심 목적 : 데이터 전송 구간의 기밀성(암호화), 완전성(해시/MAC), 발신처 인증(전자서명/사전공유키) 보장 및 전용선 대비 획기적인 인프라 비용 절감.

## Ⅱ. VPN(Virtual Private Network)의 핵심 아키텍처 및 동작 메커니즘

VPN은 OSI 3계층에서 동작하는 IPsec VPN과 4~7계층에서 동작하는 SSL/TLS VPN으로 대별되며, 패킷 캡슐화(Encapsulation)와 암호화를 통해 보안 터널을 형성함.

```text
[ IPsec VPN 터널 모드 동작 메커니즘 ]

  [ 원본 IP 패킷 (Host A -> Host B) ]
  +------------------+------------------+-----------------------+
  | 원본 IP 헤더     | TCP 헤더         | 전송 페이로드 (Data)  |
  +------------------+------------------+-----------------------+
                             │
                             ▼ IPsec Gateway 암호화 및 캡슐화
  +-------------------------------------------------------------------------+
  | 신규 IP 헤더 | ESP 헤더 | 원본 IP 헤더 | TCP 헤더 | 페이로드 | ESP 트레일러 | ESP 인증|
  | (Gateway A->B) | (SPI/Seq) | <──────────── 암호화 영역 ────────────> | (HMAC 인증 영역) |
  +-------------------------------------------------------------------------+
       신규 패킷       공중 인터넷망 전송 (중간 라우터는 내부 원본 IP 식별 불가)
```

- **IPsec 프로토콜 제품군** : 인증 및 무결성을 제공하는 AH(Authentication Header)와 기밀성까지 함께 제공하는 ESP(Encapsulating Security Payload)로 구성.
- **IKE(Internet Key Exchange) 키 교환** : Diffie-Hellman 및 ISAKMP 프레임워크를 기반으로 1단계(보안 채널 수립) 및 2단계(IPsec SA 협상) 키 교환 수행.
- **터널 모드 vs 전송 모드** : 전송 모드는 페이로드만 암호화(호스트-대-호스트), 터널 모드는 원본 IP 헤더 전체를 암호화하고 신규 외부 IP 헤더를 추가(게이트웨이-대-게이트웨이).
- **SSL/TLS VPN** : 전용 클라이언트 설치 없이 웹 브라우저를 통해 사내 웹 애플리케이션 및 포털에 암호화 접속(포트 포워딩 방식 지원).

## Ⅲ. VPN(Virtual Private Network)의 세부 구성 요소 및 비교 분석

| 비교 항목 | IPsec VPN | SSL/TLS VPN | WireGuard VPN | ZTNA (Zero Trust 대체재) |
| --- | --- | --- | --- | --- |
| 동작 계층 | OSI 3계층 (네트워크 계층) | OSI 4~7계층 (전송/응용 계층) | OSI 3계층 (커널 내장 모듈) | 소프트웨어 정의 응용 계층 |
| 클라이언트 요구 | 전용 클라이언트/하드웨어 필수 | 클라이언트리스 (웹 브라우저 가능) | 경량 커널/클라이언트 드라이버 | 경량 제로트러스트 에이전트 |
| 접근 허용 범위 | 네트워크 서브넷 전체 IP 접근 | 특정 웹 포털 및 허용된 포트 | 네트워크 터널 IP 접근 | 특정 애플리케이션 단위만 접근 |
| 코드 복잡도/성능 | 매우 복잡, 핸드셰이크 지연 큼 | TLS 암복호화 오버헤드 존재 | 극도로 단순 (4천 라인), 초고속 | 중앙 컨트롤러 연동 동적 최적화 |
| 권장 환경 | 본사-지사 간 사이트 투 사이트 | 재택근무자 사내 업무 시스템 접속 | 클라우드 컨테이너 간 메시 네트워킹 | 차세대 전사 원격 근무 보안 인프라 |

- VPN은 외부에서 사내 서브넷으로 진입하는 유용한 통로였으나, 접속 후 내부망 전체를 무제한 신뢰하는 구조적 결함으로 인해 최근 애플리케이션 단위 최소 권한만 부여하는 ZTNA로의 전환이 가속화됨.

## Ⅳ. VPN(Virtual Private Network)의 주요 한계점 및 해결 방안

- VPN 게이트웨이 침해 시 내부망 무제한 **횡적 이동** (Lateral Movement) 허용 :
  - 한계점 : 공격자가 도난된 계정이나 취약점(Pulse Secure, Fortinet 등 CVE)으로 VPN 인증을 통과하면 내부 서브넷 전체의 다른 서버로 자유롭게 침투 가능.
  - 해결 방안 : ZTNA(Zero Trust Network Access)를 도입하여 네트워크 계층 접속을 폐지하고, 신원 및 단말 검증 통과 후 특정 애플리케이션 세션만 허용.
- **스플릿 터널링** (Split Tunneling) 활성화에 따른 엔드포인트 우회 감염 :
  - 한계점 : 대역폭 절감을 위해 사내망 트래픽만 VPN으로 보내고 일반 인터넷은 직접 접속하도록 설정할 경우, 단말이 외부 악성코드에 감염된 후 VPN 터널을 타고 본사 침투.
  - 해결 방안 : 전체 터널링(Full Tunneling) 강제 및 SASE(Secure Access Service Edge) 기반 클라우드 보안 웹 게이트웨이(SWG)를 연계하여 모든 아웃바운드 트래픽 일괄 검사.
- 레거시 VPN 하드웨어의 암복호화 병목 및 원격 동시접속 폭증 시 다운 :
  - 한계점 : 팬데믹 또는 비상 상황 시 다수의 동시 접속 암복호화 트래픽이 집중되어 온프레미스 VPN 장비의 CPU 고갈 및 네트워크 단절 발생.
  - 해결 방안 : 커널 레벨 초경량 비동기 암호화 프로토콜인 WireGuard 도입 및 클라우드 네이티브 탄력적 오토스케일링 VPN 게이트웨이로 전환.

## Ⅴ. VPN(Virtual Private Network) 적용 및 발전을 위한 기술사적 제언

- VPN 계정에 대한 피싱 저항성 **MFA** (FIDO2) 필수 적용 : 단순 ID/비밀번호 기반 접속을 전면 금지하고, OTP를 넘어 스마트폰 생체인증 또는 FIDO2 하드웨어 토큰 강제.
- VPN 게이트웨이 펌웨어 취약점 긴급 패치 체계 자동화 : CISA KEV(알려진 악용 취약점)에 등록되는 엣지 VPN 장비 취약점에 대해 24시간 이내 가상 패치 및 펌웨어 업데이트 수행.
- **SASE/SSE** 프레임워크로의 장기적 전환 전략 수립 : 온프레미스 VPN 허브앤스포크 아키텍처를 폐기하고, 전 세계 PoP을 보유한 클라우드 보안 서비스(ZTNA, CASB, FWaaS)로 전면 통합.
