## 지식 로드맵 내 현재 위치

네트워크 보안 → 안전한 원격 연결 → 가상사설망(VPN) 및 ZTNA 전환

## 30초 인출

- **본질:** 인터넷 등 공중망 상에 전용 암호화 터널을 형성하여 마치 독립된 사설 전용망처럼 안전하게 통신할 수 있게 지원하는 네트워크 가상화 보안 기술
- **메커니즘:** IKEv2 키 교환 및 SA 협상 후 IPsec(ESP/AH), SSL/TLS, WireGuard 캡슐화를 통해 기밀성·무결성·인증 보장
- 통찰: VPN 터널 연결 시 단말의 서브넷 전면 노출과 기기 경유 우회 침투를 원천 방어하기 위해 SDP 기반 ZTNA 및 단일 패킷 인가(SPA) 체계 전환 필수

<details>
<summary>핵심 용어</summary>

- **IPsec (Internet Protocol Security):** 네트워크 계층(L3)에서 IP 패킷을 직접 캡슐화하고 암호화하는 표준 보안 프로토콜 슈트
- **ESP (Encapsulating Security Payload):** IPsec에서 데이터 기밀성(암호화), 무결성, 발신지 인증, 재전송 방지를 제공하는 코어 프로토콜
- **IKEv2 (Internet Key Exchange v2):** IPsec 피어 간 상호 인증 및 Diffie-Hellman 키 교환을 통해 보안 연계(SA)를 동적 협상하는 프로토콜
- **분할 터널링 (Split Tunneling):** 사내망 트래픽만 VPN으로 전달하고 일반 인터넷 트래픽은 로컬 ISP로 직접 라우팅하여 대역폭을 절감하는 구성
- **WireGuard:** 초경량 커널 모듈 기반으로 ChaCha20-Poly1305와 Curve25519 암호 프리미티브를 고정 적용한 고성능 차세대 VPN 프로토콜
</details>

## 2~4교시 예상문제 (25점)

> 가상사설망(VPN)의 핵심 기능과 계층별 구현 프로토콜(IPsec, SSL/TLS, WireGuard)을 비교하고, IPsec의 터널 모드와 전송 모드의 패킷 캡슐화 구조를 설명하며, 최근 VPN 어플라이언스 취약점 악용에 대응하기 위한 제로트러스트(ZTNA) 전환 방안을 제시하시오. (예상·25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **VPN(Virtual Private Network)** 은 인터넷 등 공중망(Public Network) 환경에서 터널링(Tunneling), 암호화(Encryption), 인증(Authentication) 기술을 적용하여 사설 전용선과 동일한 보안성을 제공하는 가상 통신망 |
| 목적 | 고비용의 물리적 전용선(Leased Line) 구축 비용 절감, 원격 근무자 및 본·지사 간 안전한 데이터 기밀성·무결성 보장 |

재택근무 확산과 클라우드 확장에 따라 레거시 게이트웨이 집중 모델에서 분산 ZTNA 연동 모델로 진화.

## Ⅱ. VPN의 특징 및 3대 핵심 보안 기능

| 핵심 기능 | 세부 기술 메커니즘 | 보장하는 보안 속성 |
|---|---|---|
| **터널링 (Tunneling)** | 원래의 데이터 패킷을 공중망 라우팅이 가능한 새로운 패킷 헤더로 감싸는 캡슐화(Encapsulation) 수행 | 논리적 사설 통신 채널 형성, 내부 네트워크 토폴로지 은닉 |
| **데이터 암호화** | 대칭키 암호(AES-GCM, ChaCha20)를 사용하여 전송 페이로드 전체를 암호화 | 공중망 도청(Sniffing)에 대한 완벽한 기밀성 보장 |
| **인증 및 무결성** | HMAC-SHA256, 디지털 서명, PKI 기반 인증서 및 사전 공유키(PSK)로 피어 검증 | 비인가자의 중간자 공격(MITM) 및 패킷 변조 원천 차단 |

## Ⅲ. VPN 아키텍처 및 IPsec 캡슐화 메커니즘

```text
[IPsec 패킷 캡슐화 구조 비교: 전송 모드 vs 터널 모드]

1. 전송 모드 (Transport Mode: 호스트-호스트 통신)
   +---------------+---------------+---------------+-----------+---------------+
   | 원본 IP 헤더  |   ESP 헤더    | TCP/UDP 헤더  |  데이터   |  ESP 트레일러| ESP 인증 테일 |
   +---------------+---------------+---------------+-----------+---------------+
                   |<----------------- 암호화 영역 ----------->|
                   |<----------------------- 무결성 인증 영역 ---------------->|

2. 터널 모드 (Tunnel Mode: 사이트-사이트 / 게이트웨이-게이트웨이 통신)
   +---------------+---------------+---------------+-----------+-----------+---------------+---------------+
   | 새로운 IP 헤더|   ESP 헤더    | 원본 IP 헤더  | TCP/UDP   |  데이터   |  ESP 트레일러| ESP 인증 테일 |
   +---------------+---------------+---------------+-----------+-----------+---------------+---------------+
                   |<------------------------- 암호화 영역 --------------->|
                   |<------------------------------- 무결성 인증 영역 ------------------------>|
```

### 1. 주요 모드 및 IKEv2 협상 프로세스

| 구분 | 전송 모드 (Transport Mode) | 터널 모드 (Tunnel Mode) |
|---|---|---|
| **적용 시나리오** | 종단 호스트 간 직접 종단 통신 (Host-to-Host) | 본·지사 라우터 간 통신 (Gateway-to-Gateway) |
| **원본 IP 헤더** | 유지 (암호화되지 않고 라우팅에 그대로 노출) | **완전 캡슐화되어 암호화 (내부 IP 주소 완벽 은닉)** |
| **신규 IP 헤더** | 생성되지 않음 | 게이트웨이 간 공중망 라우팅을 위한 신규 IP 헤더 추가 |
| **IKEv2 2단계 협상** | Phase 1 (IKE SA): 디피-헬만(DH)으로 보안 채널 확립<br>Phase 2 (Child SA): 실제 데이터 암호화를 위한 ESP SA 파라미터 협상 |

## Ⅳ. 주요 VPN 프로토콜 비교

| 비교 항목 | IPsec VPN | SSL/TLS VPN | WireGuard |
|---|---|---|---|
| **동작 계층** | 3계층 (네트워크 계층) | 4~7계층 (전송 및 응용 계층) | 3계층 (리눅스 커널 내부 구현) |
| **클라이언트 설치** | 전용 전용 에이전트/OS 지원 필수 | 웹 브라우저 기반 (Clientless 지원) | 경량 에이전트 설치 |
| **NAT/방화벽 통과** | NAT-Traversal(UDP 4500) 필요 | 표준 HTTPS(443 포트)로 원활한 통과 | 고정 UDP 포트 사용 |
| **암호화 알고리즘** | 모듈식 협상 (AES, 3DES, SHA 등) | TLS 암호 스위트 협상 | 고정 스택 (ChaCha20, Curve25519) |
| **코드베이스 크기** | 수십만 라인 (복잡하고 취약점 노출) | 수십만 라인 (OpenSSL 의존) | 약 4,000 라인 (검증 용이, 고속) |
| **주요 적용처** | 본·지사 사이트 간 전용망 연계 | 재택근무자 애플리케이션 원격 접속 | 클라우드 노드 간 메시 네트워크 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| **VPN 터널 통과 후 평면(Flat) 네트워크 내 횡적 이동(Lateral Movement)**<br>VPN 인증 1회 성공 시 내부 사내망 전체 서브넷에 접근할 수 있어, 감염된 재택 단말이 랜섬웨어를 전사 서버로 전파하는 숙주로 악용 | **SDP(Software Defined Perimeter) 기반 ZTNA 전환**<br>단일 패킷 인가(SPA: Single Packet Authorization)를 적용하여 인가받지 않은 모든 인프라를 외부에서 은닉(Dark Cloud)하고, 네트워크 세그먼트가 아닌 개별 애플리케이션 단위 1:1 마이크로 터널만 동적 개설 |
| **SSL-VPN 장비 엣지 취약점(RCE) 및 분할 터널링 우회 위험**<br>공개 인터넷에 상시 노출된 VPN 어플라이언스의 미패치 무인증 RCE 취약점(CVE) 익스플로잇 및 분할 터널링 단말을 경유한 역침투 발생 | **클라우드 네이티브 SASE/ZTNA 브로커 및 EDR 기기 검증(Posture Check)**<br>인터넷 인바운드 리스닝 포트를 전면 제거하고 아웃바운드 기반 클라우드 SASE 브로커로 연결하며, 엔드포인트 EDR과 연동하여 보안 패치와 백신이 최신 상태인 검증된 단말만 세션 연결 허용 |

## Ⅵ. 제언

```text
[VPN에서 ZTNA/SASE 중심의 원격 접속 패러다임 전환]

 +--------------------+     +---------------------+     +--------------------+
 | 레거시 VPN 인바운드| --> | 클라우드 SASE 브로커| --> | 개별 애플리케이션  |
 | (공격 표면 노출)   |     | (인바운드 포트 제거)|     | (마이크로세그멘트) |
 +--------------------+     +---------------------+     +--------------------+
```

| 접근 방식 | 기존 레거시 VPN 모델 | 현대적 ZTNA/SASE 모델 (권장) |
|---|---|---|
| **신뢰 경계** | IP 대역 및 네트워크 위치 기반 신뢰 | 신원(Identity) 및 기기 상태 기반 동적 검증 |
| **인가 범위** | 네트워크 서브넷 전체 접근 권한 허용 | 특정 승인된 단일 애플리케이션 및 포트만 허용 |
| **공격 표면** | 게이트웨이 공인 IP 상시 노출 (DDoS/스캔 노출) | 인바운드 리스닝 포트 없음 (외부 스캔 불가) |

공개 인터넷에 인바운드 포트를 열어두는 레거시 하드웨어 VPN을 단계적으로 퇴역시키고, 신원 제공자(IdP)와 결합된 클라우드 서비스형 ZTNA 솔루션 도입 권장.
