## 연관 키워드

- VPN(Virtual Private Network), 터널링(Tunneling), IPsec, SSL/TLS VPN
- AH, ESP, IKE, 스플릿 터널링(Split Tunneling), 전체 터널링(Full Tunneling)
- ZTNA(Zero Trust Network Access), SASE(Secure Access Service Edge), WireGuard, 횡적 이동(Lateral Movement), FIDO2

## Ⅰ. VPN의 개요

- 핵심 요약 : 공중 인터넷 위에 암호화 터널을 만들어 사설망에 준하는 통신 경로를 제공하는 기술.
- 개념 : 공중망(Public Network) 위에 **터널링** (Tunneling, 원본 패킷을 암호화해 다른 패킷 안에 담아 전송하는 방식)을 적용해 사설망처럼 쓸 수 있게 한 가상 사설망(VPN, Virtual Private Network).
- 배경 및 필요성 : 지사 간을 전용선으로 잇는 비용이 크고, 원격·재택근무자가 사내 시스템에 안전하게 접속해야 하므로, 인터넷 회선을 활용한 저비용 연결 수단이 필요해짐.
- 주요 목적 : 전송 구간의 기밀성(암호화), 무결성(해시·MAC, Message Authentication Code), 발신처 인증 보장과 전용선 대비 인프라 비용 절감.

## Ⅱ. VPN의 특징 및 장점

- 핵심 요약 : 캡슐화 기반 암호화 터널이 공중망 도청을 막고, 계층별 프로토콜 선택이 환경에 맞는 적용을 가능하게 하는 구조.

1. 암호화 캡슐화 : 원본 IP 패킷을 암호화해 새 헤더로 감싸 전송 → 중간 라우터가 내부 원본 주소와 내용을 식별하기 어려움.
2. 계층별 프로토콜 선택 : IPsec(Internet Protocol Security, 3계층)은 네트워크 단위 연결, SSL/TLS(Secure Sockets Layer, Transport Layer Security, 4~7계층)는 웹 기반 접속에 적합 → 사이트 간 연결과 원격 접속을 각각 최적화.
3. 전용선 대체 : 인터넷 회선으로 사이트 간 연결을 구성 → 회선 비용과 구축 기간이 줄어듦.

## Ⅲ. VPN의 구조 (흐름)

- 핵심 요약 : IPsec은 IKE로 키를 협상한 뒤 ESP 또는 AH로 패킷을 보호하며, 터널 모드에서는 원본 IP 헤더 전체를 감싸는 구조.
- **IPsec** (Internet Protocol Security) : 네트워크 계층에서 인증과 암호화를 제공하는 프로토콜 제품군.
- **ESP** (Encapsulating Security Payload) : 기밀성과 무결성을 함께 제공. **AH** (Authentication Header)는 인증과 무결성만 제공.
- **IKE** (Internet Key Exchange) : ISAKMP(Internet Security Association and Key Management Protocol)의 보안 채널을 세운 뒤 IPsec 보안 연계(SA, Security Association)를 협상하는 키 교환 절차.
- 전송 모드는 페이로드만 암호화하고, 터널 모드는 원본 IP 헤더까지 감싸 게이트웨이 간 연결에 쓰임.

```text
[ IPsec 터널 모드 패킷 ]

[ 원본 IP 패킷 ]
원본 IP 헤더 | TCP 헤더 | 데이터
      ↓ 게이트웨이에서 암호화·캡슐화
[ 터널 모드 패킷 ]
신규 IP 헤더 | ESP 헤더
  - 암호화 영역: 원본 IP·TCP·데이터
  - ESP 트레일러와 인증값
```

```text
[ IKE 키 협상 절차 ]

1단계: 보안 채널(ISAKMP SA) 수립
      ↓ Diffie-Hellman 키 교환
2단계: IPsec SA 협상
      ↓
ESP 또는 AH로 패킷 보호
```

## Ⅳ. VPN의 비교

- 핵심 요약 : IPsec은 네트워크 단위 접근, SSL/TLS VPN은 웹 중심 접근을 제공하며, 최근에는 애플리케이션 단위 접근을 제공하는 ZTNA(Zero Trust Network Access)로 이동하는 추세.
- 최근에는 구현이 단순한 **WireGuard** 같은 프로토콜도 쓰이며, ZTNA는 VPN의 대체 개념으로 함께 비교됨.

| 비교 항목 | IPsec VPN | SSL/TLS VPN | WireGuard | ZTNA |
| --- | --- | --- | --- | --- |
| 동작 계층 | 3계층(네트워크) | 4~7계층(전송·응용) | 3계층 | 응용 계층 |
| 클라이언트 요구 | 전용 클라이언트 또는 장비 필요 | 웹 브라우저로 접속 가능 | 경량 클라이언트 | 경량 에이전트 |
| 접근 범위 | 서브넷 전체 | 허용된 웹 포털과 포트 | 터널 내 IP 대역 | 애플리케이션 단위 |
| 구현 복잡도 | 설정 항목이 많고 복잡 | TLS 처리 부담 존재 | 코드 규모가 작고 단순 | 중앙 정책과 연동 |
| 권장 환경 | 본사와 지사 간 연결 | 재택근무자의 사내 시스템 접속 | 클라우드 환경의 장비 간 연결 | 전사 원격 접근 체계 |

- 선택 기준 : 사이트 간 연결은 IPsec, 원격 사용자의 웹 업무는 SSL/TLS VPN, 접근 범위를 최소화해야 하는 환경은 ZTNA를 우선 검토.

## Ⅴ. VPN의 한계와 방안

- 핵심 요약 : 게이트웨이 침해 후의 무제한 횡적 이동, 우회 트래픽을 통한 감염, 장비 병목을 접근 통제 전환과 전체 터널링, 탄력적 게이트웨이로 보완.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| VPN 게이트웨이 침해 시 내부망 **횡적 이동** (Lateral Movement) | 도난된 계정이나 장비 취약점으로 인증을 통과하면 서브넷 전체 접근이 가능해짐 | 네트워크 단위 접속을 폐지하고 **ZTNA** (Zero Trust Network Access)로 특정 애플리케이션 세션만 허용 | 비정상 내부 접근 시도 건수 |
| **스플릿 터널링** (Split Tunneling)에 따른 우회 감염 | 인터넷 트래픽이 VPN을 우회해 단말 감염이 터널을 통해 사내로 전파됨 | 전체 터널링 강제, **SASE** (Secure Access Service Edge) 기반 보안 웹 게이트웨이 연계로 아웃바운드 검사 | 우회 트래픽 비율 |
| 레거시 장비의 암복호화 병목과 동시 접속 폭증 | 비상 상황에 접속이 몰리면 온프레미스 장비의 CPU(Central Processing Unit)가 고갈되어 단절이 발생함 | 탄력적으로 확장되는 클라우드 게이트웨이 전환, 경량 프로토콜 검토 | 게이트웨이 CPU 사용률 |

## Ⅵ. VPN에 대한 기술사적 제언

- 핵심 요약 : 피싱에 강한 인증, 엣지 장비 패치 자동화, 클라우드 보안 서비스로의 단계적 전환을 통해 VPN의 구조적 약점을 줄이는 방향.

VPN 계정은 ID와 비밀번호만으로 접속하는 방식을 금지하고, 피싱에 강한 **FIDO2** (Fast IDentity Online 2) 기반 인증을 기본으로 적용하는 것이 바람직하다.

인터넷에 노출된 VPN 장비는 취약점 공개 후 신속히 조치해야 하므로, 펌웨어 점검과 긴급 패치 절차를 자동화해 대응 공백을 줄여야 한다.

장기적으로는 온프레미스 VPN 허브 구조를 줄이고 클라우드 기반 보안 서비스로 옮기는 전환 계획을 세워, 접근 통제를 애플리케이션 단위로 재편하는 것이 현실적이다.

## Ⅶ. 결론

- 핵심 요약 : VPN은 공중망에 사설 통신 경로를 여는 기술이지만, 접속 후 내부 신뢰를 전제하는 구조라 최소 권한 접근으로 보완되어야 함.
- 시사점 : 터널 자체의 암호화보다, 누가 어떤 애플리케이션에 접근하는지를 통제하는 방향으로 원격 접속 설계가 옮겨 가는 추세임.
