## Ⅰ. 가상머신(Virtual Machine)의 개요

- 개념 : 물리적인 단일 컴퓨터 하드웨어 시스템 상에서 **하이퍼바이저(Hypervisor, 가상머신 모니터: VMM)** 라는 가상화 소프트웨어 계층을 통해 CPU, 메모리, 스토리지, 네트워크 등 하드웨어 자원을 완전히 추상화하여, 독립된 **게스트 운영체제** (Guest OS)와 애플리케이션을 구동할 수 있도록 생성된 소프트웨어 기반의 컴퓨터 실행 환경.
- 배경 및 필요성 : 단일 물리 서버에 단일 OS와 애플리케이션만 구동하던 전통적 방식의 극히 낮은 하드웨어 자원 이용률(매우 낮은 수준), 데이터센터 상면 및 전력 낭비, 서버 증설 리드타임 한계를 극복하기 위해 등장.
- 핵심 목적 : **하드웨어 자원 통합** (Server Consolidation)을 통한 **TCO** 절감, 완전한 OS 수준의 보안 격리(Isolation), 신속한 프로비저닝 및 **실시간 무중단 이전** (Live Migration)을 통한 가용성 극대화.

## Ⅱ. 가상머신의 핵심 아키텍처 및 하이퍼바이저 유형

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 하이퍼바이저 2대 유형 아키텍처 비교 ]                                │
│                                                                        │
│   [ Type 1: 베어메탈 하이퍼바이저 ]      [ Type 2: 호스트형 하이퍼바이저 ]│
│   ┌─────────────────────────────┐        ┌─────────────────────────────┐   │
│   │ App A        │ App B        │        │ App A        │ App B        │   │
│   ├──────────────┼──────────────┤        ├──────────────┼──────────────┤   │
│   │ Guest OS 1   │ Guest OS 2   │        │ Guest OS 1   │ Guest OS 2   │   │
│   ├──────────────┴──────────────┤        ├──────────────┴──────────────┤   │
│   │ Type 1 하이퍼바이저 (VMM)   │        │ Type 2 하이퍼바이저 (VMM)   │   │
│   │ (ESXi, KVM, Xen, Hyper-V)   │        │ (VMware Workstation, VBox)  │   │
│   ├─────────────────────────────┤        ├─────────────────────────────┤   │
│   │ 베어메탈 물리 하드웨어      │        │ 호스트 운영체제 (Host OS)   │   │
│   │ (Bare-Metal Hardware)       │        ├─────────────────────────────┤   │
│   │ (CPU VT-x, RAM, NIC)        │        │ 물리 하드웨어 (Hardware)    │   │
│   └─────────────────────────────┘        └─────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────┘
```

- **CPU 가상화 (하드웨어 지원 가상화)** : Intel VT-x, AMD-V 기술을 통해 루트/비루트 모드(VMX Root/Non-Root Mode)를 제공하여 게스트 OS의 특권 명령(Ring 0) 실행 시 발생하는 트랩(VM-Exit)을 하드웨어 레벨에서 고속 가로채기 처리.
- **메모리 가상화 (중첩 페이지 테이블: SLAT)** : 게스트 가상 주소(GVA)를 호스트 물리 주소(HPA)로 변환하기 위해 Intel EPT(Extended Page Tables) 하드웨어 회로를 통해 이중 주소 변환 성능 오버헤드 최소화.

## Ⅲ. 가상머신(VM)과 컨테이너(Container) 비교 분석

| 비교 항목 | 가상머신 (Virtual Machine) | 컨테이너 (Container) |
| :--- | :--- | :--- |
| **가상화 수준** | 하드웨어 수준 가상화 (Hardware Abstraction)| 운영체제 커널 수준 가상화 (OS Virtualization) |
| **게스트 OS 유무** | 독립 게스트 OS 필수 탑재 (수 GB 용량) | 게스트 OS 없음 (호스트 커널 공유, 수십 MB) |
| **격리 수준 및 보안**| 하드웨어 레벨의 완벽한 격리, 보안성 최상 | cgroups, namespaces 기반 논리적 격리, 침해 위험 상대적 높음|
| **부팅 속도** | 수십 초 ~ 수 분 소요 | 수 밀리초 ~ 수 초 이내 즉각 기동 |
| **자원 오버헤드** | 게스트 OS 메모리 점유로 오버헤드 큼 | 최소한의 프로세스 자원만 소모 (고집적도) |
| **실행 엔진** | VMware ESXi, KVM, Hyper-V | Docker, containerd, Podman |
| **주요 적합 영역** | 레거시 모놀리식 시스템, 이종 OS 환경, 높은 보안| 마이크로서비스(MSA), CI/CD 파이프라인, 웹 스케일 서비스 |

## Ⅳ. 가상머신의 주요 한계점 및 해결 방안

- 이중 OS 계층 구조에 따른 자원 낭비 및 성능 오버헤드 :
  - 한계점 : 각 VM마다 개별 OS 커널, 시스템 데몬이 중복 구동되어 메모리와 스토리지 공간이 심각하게 낭비됨.
  - 해결 방안 : 메모리 중복 제거(KSM, Kernel Samepage Merging), 씬 프로비저닝 적용, 애플리케이션 계층은 컨테이너로 점진적 전환.
- 가상화 드라이버 거침에 따른 **I/O** 레이턴시 증가 :
  - 한계점 : 가상 디스크 및 가상 NIC 접근 시 에뮬레이션 오버헤드로 인해 고성능 네트워크 및 스토리지 I/O 처리율 저하.
  - 해결 방안 : 반가상화 I/O 드라이버(Virtio) 도입, 하드웨어 레벨 가상화 패스스루인 SR-IOV(Single Root I/O Virtualization) 적용.
- **VM 스프롤(VM Sprawl)** 현상으로 인한 관리 통제 상실 :
  - 한계점 : VM 생성이 용이하여 테스트 후 방치된 좀비 VM들이 기하급수적으로 늘어나 컴퓨팅 자원과 라이선스 비용 잠식.
  - 해결 방안 : 클라우드 관리 플랫폼(CMP) 도입, VM 자동 수명주기 만료 정책(TTL) 설정 및 승인 기반 워크플로 정립.

## Ⅴ. 클라우드 인프라 진화를 위한 기술사적 제언

- 컨테이너와 VM의 **융합(경량 마이크로VM)** 도입 : 서버리스(FaaS) 및 멀티테넌트 쿠버네티스 환경에서는 VM의 강력한 하드웨어 격리 보안성과 컨테이너의 초경량·고속 기동성을 결합한 AWS Firecracker, Kata Containers 같은 마이크로VM 아키텍처를 도입해야 함.
- 소프트웨어 정의 **인프라(SDI)** 로의 통합 관리 고도화 : 단순 VM 관리에 머무르지 않고, 테라폼(Terraform) 등 IaC(Infrastructure as Code) 도구를 통해 VM, 네트워크(SDN), 스토리지(SDS) 전체 수명주기를 코드 기반으로 선언하고 자동화하는 데브옵스 거버넌스를 구축할 것을 제언함.
