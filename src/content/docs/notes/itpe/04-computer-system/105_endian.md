## 연관 키워드

- 엔디언(Endianness), 빅 엔디언(Big Endian), 리틀 엔디언(Little Endian), 바이 엔디언(Bi-Endian), 미들 엔디언(Middle Endian)
- 네트워크 바이트 순서(Network Byte Order), 호스트 바이트 순서(Host Byte Order), htons, htonl, ntohs, ntohl
- 직렬화(Serialization), Protocol Buffers, 비트필드(Bit-field), 비트 마스킹(Bit Masking)
- 바이트 스왑(BSWAP), 제로 카피(Zero-Copy), __BYTE_ORDER__

## Ⅰ. 엔디언의 개요

- 핵심 요약 : **엔디언** (Endianness)은 2바이트 이상의 멀티바이트 데이터를 메모리와 네트워크에 배열하는 바이트 순서 규칙이며, 빅·리틀·바이 방식이 존재함.
- 개념 : 16·32·64비트 등 멀티바이트 워드를 1차원 바이트 주소 공간에 저장하거나 전송할 때 바이트를 배열하는 순서를 정한 컴퓨터 아키텍처 규칙.
- 배경 및 필요성 : 조너선 스위프트의 소설 『걸리버 여행기』에서 달걀을 깨는 쪽을 두고 벌어진 대립에서 명칭이 유래했으며, CPU 제조사마다 설계 방식이 달라 시스템 간 데이터 교환 시 호환성 문제가 생김.
- 주요 목적 : CPU(Central Processing Unit) 연산 설계 효율과 사람의 가독성·네트워크 일관성 사이의 트레이드오프를 조정하고, 이기종 시스템 간 통신의 무결성을 보장하는 것.

## Ⅱ. 엔디언의 특징 및 장점

- 핵심 요약 : 세 방식은 각각 네트워크 표준, 범용 프로세서, 유연한 아키텍처에 대응하며 시스템 계층별로 채택됨.

1. **빅 엔디언** (Big Endian) : **최상위 유효 바이트** (MSB, Most Significant Byte)를 최하위 주소에 저장 → 사람이 숫자를 읽는 순서와 같아 덤프 해석이 쉽고, TCP(Transmission Control Protocol)/IP(Internet Protocol)의 네트워크 바이트 순서로 사용됨.
2. **리틀 엔디언** (Little Endian) : **최하위 유효 바이트** (LSB, Least Significant Byte)를 최하위 주소에 저장 → 낮은 바이트부터 접근해 가변 길이 정수 변환이 쉬워져 x86, ARM 등 범용 프로세서가 채택.
3. **바이 엔디언** (Bi-Endian) : 설정 레지스터로 빅과 리틀 모드를 전환할 수 있는 구조 → 하나의 프로세서 아키텍처로 여러 환경에 대응하는 유연성 확보.

## Ⅲ. 엔디언의 구조 (흐름)

- 핵심 요약 : 같은 32비트 값도 엔디언에 따라 바이트 배열이 달라지며, 변환이 빠지면 수신 측에서 값이 왜곡됨.

```text
[ 0x0A0B0C0D 의 바이트 배열 ]

빅 엔디언   : 0A → 0B → 0C → 0D
리틀 엔디언 : 0D → 0C → 0B → 0A
미들 엔디언 : 0B → 0A → 0D → 0C
(낮은 주소부터 순서대로 기록)
```

```text
[ 변환 없이 전송할 때의 왜곡 ]

리틀 엔디언 호스트: 포트 80 (0x0050)
      ↓ 바이트 그대로 전송 (50 00)
빅 엔디언 수신자: 0x5000 (포트 20480)
      ↓
htons()로 변환해 전송해야 정상 전달
```

- 미들 엔디언 : 과거 PDP-11 등 일부 아키텍처가 쓴 16비트 워드 단위 혼합 배열로, 현재 범용 시스템에서는 사용되지 않음.

## Ⅳ. 엔디언의 비교

- 핵심 요약 : 시스템 계층마다 채택된 엔디언이 달라, 계층 경계에서 변환 지점을 두는 설계가 필요함.

| 시스템 계층 / 영역 | 채택 엔디언 | 채택 이유 및 특징 |
| --- | --- | --- |
| 범용 프로세서 | 리틀 엔디언 (x86-64, ARM 기본 설정) | 하위 바이트부터 접근해 정수 형변환과 주소 계산이 효율적 |
| 네트워크 프로토콜 | 빅 엔디언 (TCP, UDP, IPv4, IPv6) | RFC(Request for Comments) 1700이 네트워크 바이트 순서로 규정해 헤더 해석 기준 통일 |
| 메인프레임과 일부 서버 | 빅 엔디언 (IBM Z, 과거 SPARC) | 레거시 엔터프라이즈 시스템과의 호환성 유지 |
| 이미지·오디오 파일 | BMP, WAV는 리틀 / JPEG, PNG, AIFF는 빅 | 포맷을 정의할 당시 플랫폼의 관행을 따름 |
| JVM(Java Virtual Machine) 클래스 파일 | 빅 엔디언 | 하부 운영체제와 무관하게 바이트 해석을 통일 |

## Ⅴ. 엔디언의 한계와 방안

- 핵심 요약 : 네트워크 헤더 왜곡, 이기종 데이터 교환 파손, 비트필드의 비이식성을 표준 변환 함수, 직렬화, 비트 연산으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 네트워크 헤더 해석 왜곡 | 리틀 엔디언 호스트 바이트 순서(Host Byte Order)를 쓰는 기기가 포트 80을 그대로 보내면 빅 엔디언 수신자가 20480으로 해석해 연결 실패 | 버클리 소켓의 htons, htonl, ntohs, ntohl을 모든 헤더 송수신부에 일관되게 적용 | 헤더 파싱 오류율 |
| IPC(Inter-Process Communication)와 파일 공유 시 데이터 파손 | 이종 시스템 간 구조체 덤프를 파일이나 공유 메모리로 옮기면 값의 바이트 순서가 뒤집힘 | Protocol Buffers, FlatBuffers, XDR 같은 플랫폼 독립 **직렬화** (Serialization) 방식이나 JSON(JavaScript Object Notation) 텍스트 포맷 사용 | 역직렬화 실패 건수 |
| 비트필드의 비이식성 | C 표준이 비트필드 내 비트 배치 순서를 정하지 않아 컴파일러와 엔디언에 따라 배치가 달라짐 | 하드웨어 레지스터와 패킷 처리에서 비트필드 대신 **비트 마스킹** (Bit Masking)과 시프트 연산을 명시적으로 사용 | 비트필드 사용 코드 수 |

## Ⅵ. 엔디언의 적용 제언

- 핵심 요약 : 컴파일 시점에 엔디언을 식별하고, 플랫폼 독립 직렬화를 기본으로 삼는 것이 바람직함.
- 빌드 시점 감지 : 컴파일러가 제공하는 `__BYTE_ORDER__` 매크로로 엔디언을 판별하고 필요한 경우에만 바이트 스왑 코드를 포함하도록 공통 매크로를 표준화하면, 플랫폼별 분기 오류를 줄일 수 있음.
- 직렬화 기반 설계 : 마이크로서비스 간 통신에서는 FlatBuffers처럼 버퍼를 그대로 읽는 **제로 카피** (Zero-Copy) 직렬화를 도입해 인코딩과 디코딩 부하를 줄이는 방향이 바람직함.

## Ⅶ. 결론

- 핵심 요약 : 엔디언은 멀티바이트 데이터의 바이트 배열 순서 규칙으로, 현대 범용 시스템은 리틀 엔디언이 주류임.
- 시사점 : 네트워크 헤더, 파일 공유, 비트필드 문제는 변환 지점을 명확히 두고 직렬화 표준을 쓸 때에만 통제되어 상호운용성이 확보됨.
