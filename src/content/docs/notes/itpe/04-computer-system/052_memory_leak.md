## 한 줄 본질
- 힙 영역에 동적으로 할당된 메모리 블록을 다 쓴 뒤 `free()`로 반납하지 않거나 루트 참조를 끊지 않아 OS/런타임이 이를 회수하지 못함 → 시간 경과에 따라 가용 메모리가 고갈되어 OOM 패닉 또는 시스템 정지 발생 / RAII 패턴 도입 및 스마트 포인터 사용으로 해결

## 핵심 그림
```text
[ C/C++ 포인터 참조 상실 vs Java/Go 의도치 않은 참조 유지 누수 메커니즘 ]

(1) C/C++: 포인터 덮어쓰기로 인한 고립
   스택(Stack)                    힙(Heap)
  [ ptr: 0x1000 ] ───(할당)───> [ 10MB 할당 블록 (0x1000) ]
        │
  (ptr = NULL 변경!)
        v
  [ ptr: 0x0000 ]               [ 10MB 블록: 참조 포인터 상실! ] 
                                  ==> 영구적으로 free() 호출 불가 (누수 확정)

(2) Java/Go: 장기 생존 객체의 불필요한 참조 유지 (GC 수거 불가)
   [ Static Cache (Root) ] ───(강한 참조)───> [ 미사용 임시 객체들... ]
                                                 ==> GC Reachable 상태로 판단되어
                                                     힙에 영구 잔존 (GC 누수)
```

## 핵심 용어
- RAII(Resource Acquisition Is Initialization): 자원의 획득은 객체의 생성자에서, 자원의 해제는 소멸자에서 자동으로 수행하여 생명주기를 스코프와 일치시키는 설계 패턴
- OOM Killer(Out of Memory Killer): 리눅스 커널이 물리 메모리와 스왑 공간이 모두 고갈되었을 때 시스템 완전 마비를 막기 위해 특정 프로세스를 강제 종료(SIGKILL)시키는 커널 서브시스템
- AddressSanitizer(ASan): 컴파일러(GCC/Clang) 플래그를 통해 메모리 할당 주변에 Redzone을 두고 접근 오류 및 누수를 런타임에 즉시 잡아내는 계측 도구

## 핵심 통찰
- GC(Garbage Collector)가 있어도 메모리 누수는 발생함 → 사용하지 않는 객체가 static 컬렉션이나 싱글톤 캐시에 여전히 참조(Strong Reference)되어 있으면 GC는 이를 살아있는 객체로 판단해 결코 수거하지 않음
- 누수는 속도의 문제가 아니라 '수명의 문제'임 → 작은 단위의 누수는 짧게 끝나는 배치 작업에서는 OS가 프로세스 종료 시 한꺼번에 회수하므로 문제가 없지만, 24시간 365일 도는 서버 데몬에서는 결국 OOM을 터뜨림
- 메모리 누수는 디스크 스왑 폭증과 스래싱을 동반함 → 가용 물리 RAM이 줄어들면 OS가 적극적으로 페이징을 시도하면서 디스크 I/O가 100%를 찍고 서비스 응답 속도가 급격히 지연됨

## 이웃 토픽과 구분
- 메모리 누수 vs 메모리 단편화: 메모리 누수 = 사용하지 않는데 반납되지 않아 총 가용 공간 자체가 줄어드는 현상 / 메모리 단편화 = 총 가용 공간은 충분하지만 쪼개져 있어 연속된 큰 블록 할당이 실패하는 현상

## 문제·원인·대책
- 적용 상황: 장기 운영 서버에서 해제되지 않은 객체가 누적되어 OOM 종료로 이어지는 상황
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| C/C++ 데몬 프로세스가 3주 운영 후 커널 OOM Killer에 의해 피살 | 예외 발생 및 에러 리턴 경로에서 `free()` 호출 누락 | C++ 스마트 포인터(`std::unique_ptr`, `std::shared_ptr`) 및 RAII 전면 적용 | 스코프 탈출 시 소멸자에서 메모리 자동 반납 |
| Java 스프링 웹 서버에서 Full GC가 지속 발생하며 Stop-the-World 지연 | `ThreadLocal` 변수 사용 후 웹 스레드 풀 반환 시 `.remove()` 누락 | 프레임워크 필터/인터셉터의 `finally` 블록에서 `ThreadLocal.remove()` 강제 | 스레드 재사용 시 이전 요청 데이터 영구 잔존 원천 차단 |
