## Ⅰ. 메모리 누수(Memory Leak)의 개요

- 핵심 요약 : 할당한 메모리를 해제하지 않아 사용할 수 없는 메모리가 누적되는 소프트웨어 결함.
- 개념 : 프로그램이 동적으로 할당받은 메모리(힙 등)를 사용을 마친 뒤에도 해제하거나 회수 대상에서 빼지 못해, 점유된 채 재사용할 수 없는 메모리가 점진적으로 쌓이는 **메모리 누수** (Memory Leak) 결함. 명시적 해제 언어와 **가비지 컬렉터** (GC, Garbage Collection)를 쓰는 관리 언어 모두에서 발생함.
- 배경 및 필요성 : 포인터 관리 실수나 객체 참조 해제 누락이 장기 가동 서버에 누적되면 가용 메모리가 고갈되어 **메모리 부족** (OOM, Out of Memory) 종료로 이어지므로, 누수를 사전에 탐지하고 생명주기를 관리하는 체계가 필요함.
- 핵심 목적 : 메모리 생명주기 관리의 무결성 확보, 메모리 팽창의 조기 탐지, 분석 도구를 통한 누수 지점의 규명과 예방.

## Ⅱ. 메모리 누수(Memory Leak)의 특징 및 장점

- 핵심 요약 : 명시적 해제 누락과 참조 유지라는 두 메커니즘이 누적과 종료로 이어지는 구조.

1. **포인터 유실 누수** (Unreachable Memory) : 할당 블록의 주소를 담은 마지막 포인터가 덮어쓰이거나 스코프를 벗어나 해제 호출이 불가능해짐 → 힙 공간이 영구 점유.
2. **GC 참조 누수** (Reachable Leak) : 관리 언어에서 더 이상 쓰이지 않는 객체가 정적 컬렉션, 스레드 로컬, 이벤트 리스너에 강하게 묶여 GC가 살아 있는 객체로 판단 → 수거되지 않고 누적.
3. **메모리 팽창** (Memory Bloat) : 누수는 아니지만 불필요하게 큰 캐시를 장기간 보관 → 시스템 자원 고갈.
4. **OOM 종료** : 힙이 상한에 도달해 추가 할당이 실패하면 운영체제가 프로세스를 강제 종료(OOM Killer) → 서비스 중단.

## Ⅲ. 메모리 누수(Memory Leak)의 구조 및 동작 메커니즘

- 핵심 요약 : C/C++은 해제 호출이 사라져서, Managed 언어는 GC 루트에서 죽은 객체로 가는 참조가 남아서 누수가 발생함.
- C/C++에서는 명시적 해제 누락으로 인한 도달 불가능 메모리가, Java나 C# 같은 관리 언어에서는 의도치 않은 참조 유지로 인해 수거되지 않는 객체가 생김.

```text
[ C/C++ : 포인터 유실 ]

포인터 ptr → 힙 블록 할당
   ↓ ptr을 덮어쓰거나 스코프 이탈
블록 주소 소실
   ↓
free() 호출 불가 → 영구 점유
```

```text
[ Managed : 참조 유지 누수 ]

GC 루트 (static 필드, 싱글톤, 스레드 로컬)
   ↓ 강한 참조 유지
장수명 캐시·이벤트 리스너 목록
   ↓ remove·unregister 누락
사용 종료된 객체 (수거 불가)
   ↓
Old 세대 포화 → Full GC 빈발
```

## Ⅳ. 메모리 누수(Memory Leak)의 비교

- 핵심 요약 : 명시적 해제 환경은 개발자의 해제 책임이, 관리 환경은 참조 관리 책임이 누수 방지의 핵심이 됨.

| 비교 축 | Unmanaged (C/C++) | Managed (Java, C#) |
| --- | --- | --- |
| 메모리 관리 주체 | 개발자가 malloc/free, new/delete 직접 수행 | 런타임 GC가 도달 불가능 객체를 자동 회수 |
| 누수 원인 | 해제 코드 누락, 예외 경로에서의 해제 누락 | 정적 컬렉션 미정리, 리스너 미해제, ThreadLocal 미제거 |
| 탐지 도구 | Valgrind, ASan(AddressSanitizer) | 힙 덤프 분석기(MAT, Memory Analyzer Tool), APM(Application Performance Monitoring) 힙 모니터링 |
| 해결 기법 | RAII(Resource Acquisition Is Initialization), 스마트 포인터 | 약한 참조(Weak Reference), try-with-resources |
| 장애 징후 | 물리 메모리 사용량 지속 증가 후 종료 | Old 세대 사용량 증가와 Full GC 빈발 |

- 선택 기준 : 자원 해제를 개발자가 통제해야 하는 환경인지, 관리 언어의 GC에 맡기되 참조 관리를 엄격히 해야 하는 환경인지에 따라 점검 항목을 정함.
- 가비지 컬렉터가 있어도 참조가 살아 있는 객체는 회수되지 않으므로, 생명주기 관리는 엔지니어의 책무로 남음.

## Ⅴ. 메모리 누수(Memory Leak)의 한계와 방안

- 핵심 요약 : 장기 운영 누수의 사전 미발견, 힙 덤프 시 일시 정지, 스레드 풀 오염을 장시간 테스트, 격리 분석, 정리 코드 강제로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 장기 운영에서만 드러나는 누수 | 단위·짧은 기능 테스트에서는 미발견, 운영 중 수일에서 수주 후 OOM 발생 | CI/CD 파이프라인에 **장시간 부하 테스트** (Soak Test) 포함 | 시간 경과별 힙 사용량 기울기 |
| **힙 덤프** (Heap Dump) 생성 중 일시 정지 | 대용량 덤프 기록 동안 **STW** (Stop-the-World) 발생 → 실운영 트래픽 장애 | 운영 트래픽을 차단한 격리 인스턴스에서 덤프 추출, eBPF(extended Berkeley Packet Filter) 기반 할당 추적 활용 | 덤프 소요 시간, 격리 인스턴스 가동률 |
| **ThreadLocal** 미제거 | WAS 스레드 풀에서 요청 종료 후 remove() 미호출 → 재사용 스레드에 이전 데이터 잔존 | 필터·인터셉터의 finally 블록에서 remove() 호출을 코딩 표준으로 강제 | 요청 간 잔존 데이터 탐지 건수 |

## Ⅵ. 메모리 누수(Memory Leak)의 기술사적 제언

- 핵심 요약 : 해제 구조의 설계화, 힙 추세의 상시 감시, 소유권 기반 언어 검토를 묶어 누수를 사후 발견이 아닌 설계와 운영 단계에서 통제.

1. RAII 패턴의 전면 적용 : 자원의 획득과 해제를 객체의 생성과 소멸 범위에 묶는 RAII 패턴을 C++ 코딩 표준으로 두어 해제 누락을 구조적으로 차단하는 것이 바람직함.
2. APM 기반 힙 추세 감시 : APM이 힙 사용량의 우상향 추세를 감지하면 경보를 발생시키는 체계를 운영 기준에 포함하여 누수 징후를 조기에 파악함.
3. 소유권 모델 검토 : 해제 시점을 컴파일 단계에서 결정하는 Rust의 소유권(Ownership) 모델을 신규 시스템 개발에서 벤치마킹하여 도입 범위를 정함.

## Ⅶ. 결론

- 핵심 요약 : 메모리 누수는 해제 누락과 참조 유지로 생기는 소프트웨어 결함이며, 생명주기 관리가 핵심 통제 수단임.
- 시사점 : 관리 언어를 쓰더라도 참조 관리가 누수를 좌우하므로, 자동 회수에 기대지 않는 점검 체계가 필요함.
