## Ⅰ. 스래싱(Thrashing)의 개요

- **개념** : 가상 메모리 페이징(Paging) 시스템에서 시스템의 다중 프로그래밍 정도(Degree of Multiprogramming)가 과도하게 증가하여, 운영체제가 실제 유용한 CPU 연산 명령어를 실행하는 시간보다 프로세스 간 페이지 부재(Page Fault)를 해결하기 위해 페이지를 디스크 스왑 영역과 메모리 간에 교체(Page Swap In/Out)하는 입출력 시간이 훨씬 더 많아지는 비정상적 시스템 성능 고갈 상태.
- **배경 및 필요성** : 한정된 물리 메모리 크기를 극복하고 시스템 처리량을 높이기 위해 동시에 여러 프로세스를 실행하지만, 활성 프로세스들의 작업 집합(Working Set) 총합이 물리 메모리 가용량을 초과할 때 급격한 붕괴가 발생함.
- **핵심 목적** : 스래싱 발생 임계점 사전 감지, CPU 이용률 급락 방지, 적정 다중 프로그래밍 정도(DOM) 통제를 통한 시스템 수율 회복.

## Ⅱ. 스래싱의 발생 메커니즘 및 악순환 궤적

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 다중 프로그래밍 정도 (DOM) 증가에 따른 스래싱 발생 곡선 및 악순환 ] │
│                                                                        │
│   CPU 이용률 (%)                                                       │
│     ▲                                                                  │
│     │              임계점 (Thrashing Threshold)                        │
│     │                 ┌───┐                                            │
│     │                /     \                                           │
│     │               /       \ ──> 급격한 성능 붕괴 (Thrashing 발생!)    │
│     │              /         \                                         │
│     │             /           \                                        │
│     │            /             \                                       │
│     └───────────┴───────────────┴─────────────────────────────> DOM     │
│             [정상 가동 영역]   [스래싱 영역: I/O 100%, CPU 5% 미만]   │
│                                                                        │
│   ─── [ 스래싱의 자기 증폭 악순환 루프 (Vicious Cycle) ] ───────────   │
│                                                                        │
│   (1) 프로세스 증가 -> 각 프로세스당 할당 프레임 수 부족               │
│         │                                                              │
│         ▼                                                              │
│   (2) 빈번한 페이지 폴트(Page Fault) 발생 -> 스왑 디바이스 대기 큐 폭증 │
│         │                                                              │
│         ▼                                                              │
│   (3) 모든 프로세스가 I/O 대기 상태 진입 -> CPU 이용률(Utilization) 급락│
│         │                                                              │
│         ▼                                                              │
│   (4) OS 스케줄러가 CPU가 논다고 오판! -> 다중 프로그래밍 정도(DOM) 증가│
│         │                                                              │
│         └────── 더 많은 프로세스 적재! ──────> (1)로 회귀 (시스템 마비)│
└────────────────────────────────────────────────────────────────────────┘
```

- **OS의 잘못된 판단 메커니즘** : 전통적 CPU 스케줄러는 CPU 이용률이 낮아지면 시스템 자원이 유휴 상태인 것으로 판단하여, 처리량을 올리기 위해 메모리에 새로운 프로세스를 추가 투입함으로써 페이지 부재를 더욱 가속화하는 치명적 피드백 루프 형성.
- **임계 프레임 미달** : 프로세스가 원활히 실행되기 위한 최소한의 지역성 페이지 수(지역 세트)를 보장받지 못해 명령어를 단 한 줄 실행할 때마다 페이지 부재 발생.

## Ⅲ. 스래싱 방지 핵심 기법 비교 분석 (워킹셋 모델 vs PFF)

| 비교 항목 | 워킹셋 모델 (Working Set Model) | 페이지 부재 빈도 기법 (PFF: Page Fault Frequency) |
| :--- | :--- | :--- |
| **제안자 및 개념** | 피터 데닝(Peter Denning) 제안,<br>최근 $\Delta$ 시간 동안 참조된 페이지 집합 | 프로세스의 실제 발생 페이지 부재율을 측정하여 동적 조절 |
| **동작 메커니즘** | $WSS_i(t, \Delta)$의 합 $\sum WSS_i > 	ext{총 메모리}$ 일 때 프로세스 스왑아웃 | 부재율이 상한(Upper Bound) 초과 시 프레임 추가 할당,<br>하한(Lower Bound) 미만 시 잉여 프레임 회수 |
| **통제 방식** | **사전 예방적 (Proactive)** 통제 | **사후 반응적 (Reactive)** 피드백 제어 |
| **장점** | 지역성 이론에 충실하며 이상적인 메모리 할당 보장 | 알고리즘 구현이 단순하며 오버헤드가 적음 |
| **단점 및 한계** | 윈도우 크기($\Delta$) 최적값 선정이 어렵고 추적 부하 큼 | 페이지 폴트 발생 시점에만 반응하므로 순간 스래싱 발생 가능|

## Ⅳ. 스래싱 현상의 주요 진단 한계점 및 해결 방안

- **단순 고부하 CPU 사용과 스래싱 간의 식별 혼선** :
  - **한계점** : 시스템 응답 지연 시 top/vmstat 모니터링에서 원인이 CPU 바운드 연산인지 메모리 스래싱인지 즉각 식별 난항.
  - **해결 방안** : 리눅스 PSI(Pressure Stall Information) 지표 도입, `some` 및 `full` 메모리 스톨 지연율이 60%를 초과하는지 실시간 감시.
- **전역 페이지 교체(Global Replacement) 정책의 연쇄 희생양 문제** :
  - **한계점** : 한 프로세스가 페이지 폴트를 일으켜 다른 정상 프로세스의 핵심 워킹셋 프레임을 빼앗아 전체 프로세스로 스래싱 전이.
  - **해결 방안** : 자기 프로세스에 할당된 프레임 풀 내에서만 교체하는 지역 페이지 교체(Local Replacement) 정책 적용.
- **스왑 디스크(HDD/SATA SSD)의 I/O 병목에 따른 시스템 완전 정지** :
  - **한계점** : 느린 디스크로 스왑 I/O가 폭주할 때 커널 I/O 락이 걸려 SSH 접속 및 관리자 로그인조차 불가능.
  - **해결 방안** : RAM의 일부를 압축하여 빠른 스왑으로 사용하는 zRAM/zswap 기술 필수 활성화, 초고속 NVMe 전용 스왑 파티션 분리.

## Ⅴ. 고가용성 시스템 설계를 위한 기술사적 제언

- **Linux OOM Killer 및 cgroups v2 메모리 보호 정책 최적화** : 스래싱이 시스템 전체를 중단시키기 전에, systemd 및 cgroups v2의 `memory.high` 스로틀링과 `memory.max` 설정을 통해 개별 컨테이너/프로세스 단위로 메모리 상한을 강제하고, 임계치 초과 시 우선순위가 낮은 배치 작업을 OOM Killer로 즉시 희생시키는 격리 아키텍처를 구축해야 함.
- **쿠버네티스 노드 Eviction 및 HPA 연동 거버넌스 수립** : 클라우드 환경에서는 노드 메모리 사용률이 85%에 도달할 경우 Pod Eviction 정책을 발동하여 부하를 다른 노드로 자동 드레인(Drain)하고, 스왑 사용을 원천 비활성화(`swapoff`)하여 스래싱으로 인한 지연 스파이크를 방지할 것을 제언함.
