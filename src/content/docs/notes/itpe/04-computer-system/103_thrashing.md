## 연관 키워드

- 스래싱(Thrashing), 성능 운영(Performance Operations), PSI(Pressure Stall Information), 스와핑(Swapping)
- 페이지 부재(Page Fault), 백분위(Percentile), OOM(Out of Memory) Killer, 축출(Eviction)
- 용량 계획(Capacity Planning), 워크로드 격리(Workload Isolation), 표준 운영 절차(SOP, Standard Operating Procedure)

## Ⅰ. 스래싱의 개요

- 핵심 요약 : 스래싱 운영 관리는 **스래싱** (Thrashing)으로 인한 처리량 붕괴를 지표로 조기 탐지하고 절차적으로 해소하는 성능 운영 체계.
- 개념 : 메모리 부족으로 페이지 교체·**스와핑** (Swapping) 활동이 연산을 잠식해 시스템 처리량이 급락하는 상태를, 관측·진단·완화의 운영 흐름으로 다루는 관리 활동.
- 배경 및 필요성 : 스래싱은 서버 전체의 응답을 동시에 느려지게 해 관리자 접속조차 어렵게 만들므로, 사후 대응이 아닌 지표 기반의 사전 탐지 체계가 필요함.
- 주요 목적 : 탐지 지표의 선정, 붕괴 진행의 모니터링, 단계별 해소 절차의 표준화로 장애 시간 최소화.

## Ⅱ. 스래싱 운영 관리의 특징 및 장점

- 핵심 요약 : 이용률 역전 패턴, 스톨 지표, 스와핑 추적, 백분위 관측으로 붕괴 조짐을 식별하고 운영 개입으로 회복 시간을 단축하는 구조.

1. 이용률 역전 패턴(Inversion Pattern) : CPU 이용률은 낮은데 시스템 시간·입출력 대기 비율이 높은 조합 → 연산 부하가 아닌 스래싱 조짐의 판별 효과.
2. 스톨 직접 측정(Stall Measurement) : **PSI** (Pressure Stall Information, 리눅스 커널의 자원 대기 시간 비율 지표)의 메모리 항목 감시 → 자원 대기가 실제 발생한 시간을 직접 확인하는 효과.
3. 스와핑 활동 추적(Swap Activity Tracking) : 스왑 입출력량과 주요 **페이지 부재** (Page Fault) 카운터의 추이 관찰 → 페이지 교체 폭증의 조기 신호 효과.
4. 백분위 기반 관측(Percentile) : 평균 대신 상위 백분위 응답 시간 추적 → 순간 붕괴를 평균이 가리는 문제를 우회하는 정밀 관측 효과.

## Ⅲ. 스래싱 운영 관리의 구조 (흐름)

- 핵심 요약 : 탐지·진단·완화·복귀·재발 방지의 5단계 운영 흐름과 지표·이벤트·추세의 3층 관측 체계로 구성됨.

```text
[ 스래싱 대응 운영 흐름 ]

탐지 (지표 임계 알림)
      ↓
진단 (스와핑·스톨 지표 교차 확인)
      ↓
완화 (작업 연기·축출 등 개입)
      ↓
복귀 확인 (처리량·응답 시간 회복)
      ↓
재발 방지 (원인 분석 반영)
```

```text
[ 3층 관측 체계 ]

추세층 : 응답 시간 백분위·자원 사용 추이
      ↓
지표층 : PSI 메모리 스톨·스와핑량
      ↓
이벤트층 : OOM·축출 이벤트 기록
```

- 구성요소 : 수집 에이전트, 임계값 정책, 알림 체계, 완화 조치 목록, 사후 분석 절차의 다섯 요소로 운영 체계 구성.
- 이벤트 근거 : **OOM** (Out of Memory) Killer의 강제 종료와 컨테이너 **축출** (Eviction) 기록은 붕괴 확정의 사고 판정 근거로 사용함.

## Ⅳ. 스래싱 탐지 지표의 비교

- 핵심 요약 : 지표마다 관측 위치와 탐지 시점이 달라, 조기 탐지용과 사고 판정용을 조합해 사용함.

| 지표 | 관측 위치 | 탐지 신호 | 강점 | 한계 |
| --- | --- | --- | --- | --- |
| PSI 메모리 스톨 | 커널 | 메모리 대기 비율 상승 | 대기 시간의 직접 측정 | 커널 버전 의존 |
| 스와핑량 (스왑 입출력) | 커널 카운터 | 스와핑 활동 급증 | 범용 도구로 관측 가능 | 압축 스왑 환경의 해석 주의 |
| 주요 페이지 부재 카운터 | 커널 카운터 | 디스크 뒷받침 부재 급증 | 부재 원인과 직결 | 워크로드별 편차 |
| 입출력 대기·시스템 시간 비율 | CPU 통계 | 연산 대비 대기의 역전 | 취득이 용이 | 단독 판단에는 부족 |
| OOM·축출 이벤트 | 오케스트레이터 | 메모리 한계 도달 기록 | 사고 판정이 명확 | 사후 지표 성격 |

- 선택 기준 : 조기 탐지는 PSI와 부재 카운터, 사고 확정은 OOM·축출 이벤트, 추세 관리는 백분위 응답 시간을 담당 지표로 지정.

## Ⅴ. 스래싱 운영의 한계와 방안

- 핵심 요약 : 탐지 지연, 부하 유형 오판, 완화 후 재발을 백분위 관측, 교차 판정, 근본 원인 관리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 탐지 지연 | 평균값 집계가 순간 붕괴를 평활 → 알림이 사고 이후에 도착 | 상위 백분위 지표와 짧은 수집 주기의 병행 | 붕괴 시작 대비 알림 시점 격차 |
| 부하 유형 오판 | 응답 지연을 연산 부하로 해석 → 무의미한 서버 증설 | 스톨·스와핑·이용률 지표의 교차 판정 기준 운영 | 오판 조치 건수 |
| 완화 후 재발 | 임시 완화만으로 과다 투입·메모리 누수 등 원인이 남음 → 반복 장애 | 근본 원인 분석의 용량 계획 반영과 워크로드 격리 | 재발 주기, 재발률 |

## Ⅵ. 스래싱 운영에 대한 기술사적 제언

- 핵심 요약 : 대응 절차 표준화, 알림 정책 체계, 승인 심사 연계의 세 축으로 스래싱 대응을 상시 운영 역량으로 내재화할 필요.
- 절차 표준화 : 서비스 운영 조직이 탐지부터 복귀까지의 조치와 담당 권한을 **표준 운영 절차** (SOP, Standard Operating Procedure)로 제정.
- 알림 정책 체계 : 인프라 관리 조직이 PSI·스와핑·축출 이벤트를 통합 대시보드로 수집하고 단계별 알림 임계값을 정책화.
- 승인 심사 연계 : 아키텍처 검토 조직이 신규 서비스 승인 시 메모리 상한과 예상 자원 요구량을 심사하는 사전 검토 절차를 제도화.

## Ⅶ. 결론

- 핵심 요약 : 스래싱 운영 관리는 붕괴 조짐을 지표로 먼저 듣고 절차로 끝내는 사전 대응 체계임.
- 시사점 : 탐지 지표와 해소 절차가 표준으로 정착할 때 처리량 붕괴 장애의 시간과 범위가 함께 줄어듦.
