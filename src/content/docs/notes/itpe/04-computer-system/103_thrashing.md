## 답안 골격
```text
[스래싱] ◀━━ 머리: Ⅶ 내 의견 (워킹셋 모델과 PFF 임계값 기반 다중 프로그래밍 정도(MPD) 동적 조절 체계 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 가상 메모리 환경에서 다중 프로그래밍 정도(MPD) 과도 증가 → 페이지 교체 빈도 폭증으로 CPU 활용률이 0에 수렴하는 현상
 ┣━ Ⅱ 특징 ───── 페이지 부재율(Page Fault Rate) 급증 · 디스크 I/O 큐 포화 · CPU 활용률 급락 · 시스템 마비 악순환(Vicious Cycle)
 ┣━ Ⅲ 구조 ───── 물리 메모리(프레임 부족) + 스왑 영역(디스크 I/O) + 페이지 교체기 + MPD 제어 모듈
 ┣━ Ⅳ 흐름 ───── ① MPD 증가 → ② 프로세스당 프레임 감소 → ③ 페이지 부재 폭증 → ④ 디스크 I/O 대기로 CPU 유휴 → ⑤ OS의 오판(MPD 추가 증가)
 ┣━ Ⅴ 비교 ───── 워킹셋(Working Set) 모델 vs 페이지 부재 빈도(PFF: Page Fault Frequency) 알고리즘
 ┗━ Ⅵ 실무 ───── 스왑 메모리 점유율 100% 도달로 인한 서비스 무응답 / OOM Killer 비정상 프로세스 강제 종료 / 디스크 트래픽 급증
```
- 필수 키워드: 스래싱 · 다중 프로그래밍 정도(MPD) · 페이지 부재(Page Fault) · 워킹셋 · PFF · 지역성(Locality)
- 기출: 126회 1교시 10번 `스레싱(Thrashing)` 단답형 출제

## 한 줄 본질
- 프로세스가 실행에 필요한 최소한의 메모리 프레임을 확보하지 못함 → 실제 프로그램 연산 시간보다 디스크에서 페이지를 스왑인/아웃하는 I/O 시간이 압도적으로 많아져 CPU가 멈춤 → 워킹셋과 PFF로 MPD를 강제 조절하여 방지 / 제어 실패 시 시스템 전체 멈춤 현상 초래

## 핵심 그림
```text
[ 다중 프로그래밍 정도(MPD)와 CPU 활용률 곡선 및 스래싱 임계점 ]

CPU 활용률 (%)
100 │                 스래싱 임계점 (Thrashing Point)
    │                       ▲
    │                     /   \  [ 스래싱 발생 구간! ]
    │                   /       \  - 페이지 부재 급증
    │                 /           \  - 디스크 I/O 병목
    │               /               \  - CPU는 I/O 대기 상태로 유휴
    │             /                   \
    │           /                       \
  0 └─────────┴───────────────────────────┴───────────> 다중 프로그래밍 정도 (MPD)
              [ 정상 가동 구간 ]          [ 스래싱 붕괴 구간 ]
```

## 핵심 용어
- 다중 프로그래밍 정도(MPD: Multiprogramming Degree): 주기억장치에 동시에 적재되어 실행 대기 중인 활성 프로세스의 총 수
- 워킹셋(Working Set): 프로세스가 일정 시간(윈도우 $\Delta$) 동안 자주 참조하는 페이지들의 집합으로, 이 집합 전체가 메모리에 상주해야 스래싱이 발생하지 않음
- PFF(Page Fault Frequency): 페이지 부재 발생 주기를 측정하여 상한선 초과 시 프레임을 추가 할당하고 하한선 미만 시 프레임을 회수하는 적응형 메모리 관리 기법

## 핵심 통찰
- 운영체제의 치명적인 오판이 스래싱을 부름 → CPU 사용률이 떨어지면 OS 스케줄러는 "할 일이 없구나"라고 착각하여 큐에서 새 프로세스를 메모리에 더 집어넣음(MPD 증가) → 이로 인해 기존 프로세스의 프레임이 더 뺏기며 시스템이 완전히 마비되는 악순환에 빠짐
- 국소성(Locality)의 붕괴 → 프로그램의 시간/공간 지역성이 깨지거나 배열을 행/열 반대로 잘못 순회하는 루프가 돌면 한 번 접근할 때마다 페이지 부재가 터져 스래싱을 유발함
- 현대 클라우드에서는 OOM Killer가 조기 차단함 → 스래싱으로 시스템 전체가 좀비 상태에 빠지는 것을 막기 위해 최신 리눅스 커널은 스왑 한도에 도달하면 메모리를 가장 많이 먹는 프로세스를 즉각 강제 종료(SIGKILL)시키는 극약 처방을 씀

## 이웃 토픽과 구분
- 스래싱 vs 단편화: 스래싱 = 프로세스들의 메모리 요구량 총합이 물리 메모리를 초과하여 발생하는 I/O 병목 현상 / 단편화 = 빈 메모리 공간이 자잘하게 쪼개져 있어 할당이 불가능한 배치 공간 비효율

## 문제·원인·대책
- 사례: 126회 기출 및 야간 배치 작업 동시 실행으로 인한 데이터베이스 서버 무응답 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 야간 배치 프로그램 수십 개 동시 기동 후 서버 명령 입력 불가(무응답) | 과도한 프로세스 동시 실행으로 스왑 공간 포화 및 스래싱 발생 | 스케줄러 동시 실행 수(MPD) 제한 및 우선순위 큐 분리 | 프로세스별 최소 워킹셋 보장 및 스래싱 원천 방지 |
| 컨테이너 호스트에서 특정 파드가 메모리를 과점하여 이웃 파드까지 정체 | 메모리 상한선(Limit) 미설정으로 인한 커널 스왑 경합 | 쿠버네티스 자원 Limit 설정 및 `vm.swappiness` 0 또는 낮은 값 조정 | 메모리 초과 컨테이너만 격리 차단하여 노드 전체 스래싱 방지 |

## 이렇게 출제된다
- 제126회 1교시 10번: "스레싱(Thrashing)" → 요구 포인트: Ⅰ 스래싱의 정의 및 원인 + Ⅲ MPD-CPU 곡선도 및 발생 악순환 메커니즘 + Ⅵ 해결 방안(워킹셋, PFF, 메모리 증설)

## 내 의견
- [프로세스 워킹셋 프로파일링 기반의 컨테이너 자원 상한선 자동 튜닝] 개발자가 임의로 지정하는 메모리 Request/Limit은 스래싱이나 자원 낭비를 유발함 → 나라면: Prometheus와 VPA(Vertical Pod Autoscaler)를 연동하여 실제 운영 중 프로세스의 Working Set 크기(container_memory_working_set_bytes)를 연속 추적하고, 물리 메모리 부족 징후 감지 시 지연 배치 작업을 일시 정지(Suspend)시키는 자동 부하 제어 아키텍처 구축
