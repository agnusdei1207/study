## 답안 골격
```text
[i-node] ◀━━ 머리: Ⅶ 내 의견 (디렉터리 엔트리와 메타데이터의 물리적 분리를 통한 고속 파일 시스템 인덱싱 및 공간 효율화)
 ┃
 ┣━ Ⅰ 개요 ───── 파일명 중심 순차 검색의 비효율 극복 → 파일 메타데이터와 디스크 블록 포인터를 고정 크기 블록에 보관하는 인덱스 노드
 ┣━ Ⅱ 특징 ───── 고정 크기 자료구조(128/256B) · 파일명 제외 메타데이터 전부 저장 · 다단계 간접 포인터(대용량 지원) · 하드 링크 지원
 ┣━ Ⅲ 구조 ───── 파일 속성(크기/소유자/권한/타임스탬프) + 직접 블록 포인터(12개) + 단일/이중/삼중 간접 포인터
 ┣━ Ⅳ 흐름 ───── ① 디렉터리에서 파일명-i-node 매핑 조회 → ② i-node 테이블 접근 → ③ 블록 포인터 역참조 → ④ 실제 데이터 블록 읽기
 ┣━ Ⅴ 비교 ───── i-node(유닉스/리눅스) vs FAT(윈도우 파일 할당 테이블) vs NTFS MFT(마스터 파일 테이블)
 ┗━ Ⅵ 실무 ───── i-node 고갈(No space left on device) / 하드 링크 참조 카운트 불일치 / 디스크 단편화
```
- 필수 키워드: i-node · 메타데이터 · 직접 블록 포인터 · 간접 블록 포인터 · 하드 링크 · i-node 고갈

## 한 줄 본질
- 디렉터리에 파일 메타데이터를 직접 넣으면 검색 속도가 느려지고 파일명 변경 시 구조가 깨짐 → 파일 메타데이터와 데이터 블록 주소를 고유 번호 기반의 고정 크기 i-node로 분리 인덱싱 → 빠른 무작위 접근과 링크 관리 실현 / 디스크 용량이 남아도 i-node 개수가 소진되면 파일 생성 불가

## 핵심 그림
```text
[ i-node 내부 구조 및 다단계 블록 포인터 체계 ]

i-node (고정 크기 128B 또는 256B)
+─────────────────────────────────────────+
| 파일 타입, 접근 권한 (Permissions)       |
| 소유자 UID / GID, 파일 크기 (File Size) |
| 타임스탬프 (atime, mtime, ctime)         |
| 링크 카운트 (Hard Link Count)           |
+─────────────────────────────────────────+
| 직접 포인터 0 ~ 11 (Direct Pointers)    |───> [ 데이터 블록 0 ~ 11 ]
+─────────────────────────────────────────+
| 단일 간접 포인터 (Single Indirect)      |───> [ 인덱스 블록 ] ───> [ 데이터 블록 ]
+─────────────────────────────────────────+
| 이중 간접 포인터 (Double Indirect)      |───> [ 인덱스 블록 ] ───> [ 인덱스 블록 ] ───> [ 데이터 블록 ]
+─────────────────────────────────────────+
| 삼중 간접 포인터 (Triple Indirect)      |───> [ 인덱스 블록 ] ───> [ 인덱스 ] ───> [ 인덱스 ] ───> [ 데이터 ]
+─────────────────────────────────────────+
```

## 핵심 용어
- 하드 링크(Hard Link): 동일한 i-node 번호를 가리키는 서로 다른 디렉터리 엔트리(파일명)로, 링크 카운트가 0이 될 때만 실제 데이터가 삭제됨
- 간접 포인터(Indirect Pointer): i-node 자체의 포인터 슬롯 한계를 넘어 수 기가~테라바이트 파일 크기를 지원하기 위해 인덱스 블록 주소를 1단계 이상 중첩 참조하는 구조
- 디렉터리 엔트리(dentry): 디렉터리 파일 내부에 `파일명 : i-node 번호` 쌍으로만 구성된 초경량 매핑 테이블

## 핵심 통찰
- i-node에는 '파일명'이 존재하지 않음 → 파일명은 상위 디렉터리 파일의 데이터 영역에만 기록되며, 덕분에 파일 이름을 바꾸거나 다른 디렉터리로 이동(mv)해도 i-node 본체와 데이터 블록 복사 없이 즉각 처리됨
- 다단계 간접 블록 설계는 공간 효율성과 접근 속도의 완벽한 절충임 → 전체 파일의 80% 이상을 차지하는 수 KB 미만 소형 파일은 12개의 직접 포인터로 1회 디스크 I/O 만에 읽고, 거대 파일만 추가 인덱스 블록을 거치게 설계됨
- 디스크 용량과 i-node 용량은 완전히 독립적인 제약임 → 파일 시스템 포맷(mkfs) 시 i-node 개수가 고정되므로, 바이트 용량이 90% 비어 있어도 0바이트 파일 수백만 개를 만들면 시스템이 정지함

## 이웃 토픽과 구분
- 하드 링크 vs 심볼릭 링크: 하드 링크 = 원본과 동일한 i-node 번호 공유, 파일 시스템 경계 통과 불가 / 심볼릭 링크 = 원본 경로 문자열을 데이터로 갖는 완전히 독립된 새 i-node 생성

## 문제·원인·대책
- 적용 상황: 웹 서버 세션 파일 및 이메일 큐 폭증으로 인한 시스템 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 디스크 공간(df -h)이 충분함에도 신규 파일 생성 시 `No space left on device` 오류 | 수백만 개의 소형 임시 파일 방치로 할당된 i-node 번호 전량 소진(df -i 100%) | find 명령 기반 0바이트 세션 파일 일괄 삭제 및 cron 주기적 청소 | i-node 즉시 반환으로 파일 생성 기능 정상 복구 |
| 대용량 데이터베이스 파일 접근 시 과도한 간접 포인터 순회로 인한 I/O 지연 | 전통적 포인터 블록 방식의 연속 블록 관리 비효율 | 익스텐트(Extent) 기반 파일 시스템(ext4, XFS) 전환 | 블록별 주소 대신 `시작 블록 + 길이`로 메타데이터 대폭 축소 |
