## 연관 키워드

- NAS, Network-Attached Storage, 파일 수준 접근, NFS, SMB, DAS, SAN
- 파일 잠금, RAID, 스케일아웃, SPOF, RDMA, Kerberos, 정보 생애주기 관리

## Ⅰ. NAS의 개요

- 핵심 요약 : TCP/IP 이더넷 기반의 파일 수준 공유 스토리지로, 이기종 OS 사이의 파일 공유와 중앙 관리를 제공하는 전용 파일 서버.
- 개념 : TCP/IP(Transmission Control Protocol/Internet Protocol) 이더넷 네트워크에 연결되어 여러 이기종 클라이언트에 **파일 수준** (File-Level) 입출력과 공유 공간을 제공하는 **네트워크 연결 스토리지** (NAS, Network-Attached Storage).
- 배경 및 필요성 : 서버 내장 디스크나 직접 연결된 저장 장치에 데이터가 묶이면 다른 서버와 공유할 수 없어 데이터가 서버별로 고립되는 문제가 생김. 부서 간 문서와 미디어 협업 수요가 커지면서 **직접 연결 스토리지** (DAS, Direct-Attached Storage)의 고립 문제를 파일 공유 기능을 갖춘 독립 장비로 중앙화하는 방식이 필요해짐.
- 주요 목적 : 표준 파일 공유 프로토콜인 **NFS** (Network File System)와 **SMB** (Server Message Block)로 이기종 OS 간 공유를 제공하고, 파일 단위 권한 제어와 스토리지 관리를 일원화해 운영 비용을 낮추는 것.

## Ⅱ. NAS의 특징 및 장점

- 핵심 요약 : 파일 수준 I/O 추상화와 파일 잠금이 결합되어, 클라이언트가 디스크 구조를 몰라도 안전하게 공유하는 구조.

1. **파일 수준 I/O** (File-Level I/O) : 클라이언트가 경로, 파일명, 바이트 오프셋 단위의 원격 호출로 데이터를 요청 → 블록 위치와 파일 시스템 관리를 컨트롤러가 전담해 클라이언트 구현이 단순해짐.
2. **파일 잠금** (File Locking) : NFS 잠금 관리(NLM, Network Lock Manager)와 SMB의 **기회적 잠금** (Oplock, Opportunistic Lock)으로 다중 클라이언트의 동시 쓰기 충돌을 막고 캐시 일관성을 유지 → 공동 편집 데이터의 훼손 방지.

## Ⅲ. NAS의 구조 (흐름)

- 핵심 요약 : 클라이언트의 파일 요청이 NAS 컨트롤러의 프로토콜 계층과 파일 시스템을 거쳐 물리 디스크의 블록 입출력으로 바뀌는 구조.
- 구성 요소 : NFS와 SMB 요청을 받는 프로토콜 데몬, 파일 시스템과 파일 잠금을 관리하는 계층, 여러 디스크를 묶어 중복 저장하는 **RAID** (Redundant Array of Independent Disks)와 스냅샷 같은 볼륨 관리 계층.

```text
[ 파일 요청 처리 경로 ]

클라이언트 (Linux: NFS / Windows: SMB)
   ↓ IP 네트워크 (이더넷)
NAS 컨트롤러: 프로토콜 데몬
   ↓
파일 시스템 (메타데이터·파일 잠금)
   ↓
볼륨 관리 (RAID·스냅샷)
   ↓ 블록 입출력
물리 디스크 (하드디스크, 플래시 저장 장치)
```

```text
[ 파일 해석 위치 ]

NAS  : 클라이언트 → 파일 경로 → 컨트롤러
SAN  : 호스트 → 블록 번호 → 호스트 파일 시스템
DAS  : 서버 → 블록 번호 → 내장 디스크
```

## Ⅳ. NAS의 비교

- 핵심 요약 : 파일 시스템을 어디서 해석하느냐에 따라 NAS, SAN, DAS의 성능 특성과 적합 업무가 갈리는 구조.
- 비교 대상 : NAS와 **SAN** (Storage Area Network), DAS를 액세스 레벨, 전송 프로토콜, 파일 시스템 위치 기준으로 비교한다.
- 선택 기준 : 공유가 필요한지 여부와 지연 민감도, 업무가 파일 단위인지 블록 단위인지에 따라 고른다.

| 비교 항목 | NAS | SAN | DAS |
| :--- | :--- | :--- | :--- |
| 액세스 레벨 | 파일 수준 (NFS, SMB) | 블록 수준 | 블록 수준 |
| 네트워크 매체 | 범용 이더넷 (TCP/IP) | 파이버 채널(FC, Fibre Channel) 또는 IP 기반 블록 네트워크 | 호스트 직접 연결 버스 |
| 전송 프로토콜 | NFS, SMB | FC, iSCSI(Internet Small Computer Systems Interface), NVMe(Non-Volatile Memory Express) over Fabrics | 호스트 내부 버스 프로토콜 |
| 파일 시스템 위치 | NAS 컨트롤러 내부 | 각 호스트 서버 내부 | 각 호스트 서버 내부 |
| 성능 특성 | 네트워크 프로토콜 스택에 따른 지연 존재 | 저지연과 대규모 고성능 입출력에 최적화 | 단일 서버 기준 가장 빠른 직접 접근 |
| 적합 업무 | 문서 공유, 미디어 협업, 콘텐츠 관리 | 대규모 데이터베이스, 가상화 데이터스토어 | 단일 고성능 데이터베이스, 로컬 캐시 |

## Ⅴ. NAS의 한계와 방안

- 핵심 요약 : 중앙 컨트롤러 병목, TCP/IP 오버헤드, 레거시 NFS의 보안 약점을 스케일아웃, RDMA, 최신 NFS와 통합 인증으로 대응하는 구조.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 컨트롤러 병목과 **단일 장애점** (SPOF, Single Point of Failure) | 단일 또는 이중 컨트롤러 구조에서 파일 수가 많아지면 메타데이터 잠금 경합으로 처리량 급감, 컨트롤러 장애 시 전체 서비스 중단 | 분산 메타데이터 구조의 스케일아웃 NAS 도입, 노드 추가에 따라 성능이 늘어나는 구성(예: Dell PowerScale(구 Isilon), CephFS, GlusterFS 계열) | 메타데이터 응답 지연, 노드별 처리량 |
| TCP/IP 스택 오버헤드 | 대용량 학습 데이터를 커널 경유 패킷 처리로 옮기며 CPU 부담과 지연이 커져 그래픽 처리 장치(GPU, Graphics Processing Unit)가 입력을 기다리는 현상 발생 | RDMA(Remote Direct Memory Access) 기반 NFS(NFSoRDMA) 적용, 병렬 NFS(pNFS, Parallel NFS)와 Lustre, GPFS 같은 병렬 파일 시스템 도입 | GPU 입력 대기 시간, 처리량 |
| NFSv3 보안과 권한 불일치 | 레거시 인증은 클라이언트 신뢰에 의존해 UID(User Identifier)·GID(Group Identifier) 위조가 가능하고, Windows 접근 제어 목록(ACL, Access Control List)과 Linux POSIX(Portable Operating System Interface) 권한이 어긋남 | Kerberos 암호화 인증을 지원하는 NFSv4.1 이상으로 전환, LDAP(Lightweight Directory Access Protocol)과 Active Directory 신원 체계 연계 | 인증 방식 전환율, 권한 오류 건수 |

## Ⅵ. NAS에 대한 기술사적 제언

- 핵심 요약 : 고성능 스케일아웃 NAS를 인공지능(AI, Artificial Intelligence) 데이터 진입점으로 두고, 접근 빈도에 따라 저장 계층을 나누는 운영 체계.

1. 대규모 데이터 분석과 AI 학습 환경에서는 올플래시 NVMe 기반 스케일아웃 NAS를 데이터 레이크의 진입 저장소로 두고, **GPUDirect Storage** (NVIDIA의 GPU 직접 스토리지 접근 기술)를 연계해 학습 서버의 입력 경로를 짧게 만드는 것이 바람직하다.
2. 협업 문서와 트랜잭션 파일은 NAS에 두고, 오래 보관하는 데이터는 **정보 생애주기 관리** (ILM, Information Lifecycle Management) 정책에 따라 오브젝트 스토리지로 옮기는 계층화 운영이 필요하다.
3. 파일 공유 장비를 교체할 때는 프로토콜 전환과 권한 이관을 한 번에 묶지 않고, 파일럿 구간에서 권한 매핑을 먼저 검증한 뒤 단계적으로 옮기는 절차를 두는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : NAS는 TCP/IP 기반의 파일 수준 공유 스토리지로, 이기종 OS 사이의 협업과 중앙 관리를 실현하는 방식.
- 컨트롤러 병목과 네트워크 오버헤드가 성능의 상한이므로, 워크로드 특성에 맞춰 스케일아웃 구조와 고속 프로토콜을 고르는 것이 관건.
