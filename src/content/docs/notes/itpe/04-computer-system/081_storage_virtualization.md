## 연관 키워드

- 스토리지 가상화, Storage Virtualization, 가상 스토리지 풀, 씬 프로비저닝, 자동 계층화
- 인밴드 가상화, 아웃오브밴드 가상화, LVM, SPOF, MPIO, CDP
- SDS, CSI, NVMe over Fabrics

## Ⅰ. 스토리지 가상화의 개요

- 핵심 요약 : 이기종 물리 스토리지를 하나의 논리 풀로 추상화하여 중앙에서 할당과 관리를 단순화하는 인프라 기술.
- 개념 : 벤더가 다른 디스크 어레이와 **직접 연결 스토리지** (DAS, Direct-Attached Storage), **스토리지 영역 네트워크** (SAN, Storage Area Network), **네트워크 연결 스토리지** (NAS, Network-Attached Storage)의 물리 공간을 논리 계층으로 추상화하여, 단일 **가상 스토리지 풀** (Logical Storage Pool)로 묶고 중앙에서 동적으로 할당하는 기술.
- 배경 및 필요성 : 벤더별로 나뉜 스토리지는 자원이 장비 단위로 고립되어 어떤 장비는 포화되고 다른 장비는 유휴 상태로 남음. 장비를 교체하거나 데이터를 옮길 때 서비스를 멈춰야 해서 **총소유비용** (TCO, Total Cost of Ownership)이 커짐 → 물리 장비의 경계를 논리 풀로 가려 활용률과 이전 용이성을 확보하는 방향.
- 주요 목적 : 이기종 스토리지의 용량 통합으로 활용률을 높이고, **씬 프로비저닝** (Thin Provisioning)과 **자동 계층화** (Auto-Tiering)를 적용하며, 무중단 증설과 데이터 이전을 보장하는 것.

## Ⅱ. 스토리지 가상화의 특징 및 장점

- 핵심 요약 : 가상화 엔진을 데이터 경로에 두는지 제어 경로에만 두는지에 따라 캐싱과 보안의 효율, 병목의 위치가 달라지는 구조.

1. **인밴드 가상화** (In-Band Virtualization) : 데이터와 제어 정보가 모두 가상화 엔진을 통과 → 캐시와 보안 기능을 한곳에서 일관되게 적용하나, 엔진이 병목이 되거나 **단일 장애점** (SPOF, Single Point of Failure)이 될 수 있음.
2. **아웃오브밴드 가상화** (Out-of-Band Virtualization) : 메타데이터만 별도 서버가 처리하고 실제 데이터는 호스트와 스토리지가 직접 주고받음 → 데이터 경로 병목이 줄어 고성능을 유지하나, 호스트에 전용 에이전트를 설치해야 함.

## Ⅲ. 스토리지 가상화의 구조 (흐름)

- 핵심 요약 : 가상화 기능을 호스트, 네트워크, 스토리지 어레이 중 어디에 두느냐에 따라 구현 계층이 나뉘는 구조.
- 구현 계층 : **호스트 기반 가상화** (Host-Based Virtualization), **네트워크 기반 가상화** (Network-Based Virtualization), **어레이 기반 가상화** (Array-Based Virtualization). 논리 장치는 **논리 유닛 번호** (LUN, Logical Unit Number)로 호스트에 노출됨.

```text
[ 구현 3계층 ]

호스트 기반 (볼륨 관리자·에이전트)
   ↓ 블록 입출력 요청
네트워크 기반 (SAN 스위치·가상화 장치)
   ↓ 물리 입출력
어레이 기반 (컨트롤러가 타사 LUN 관리)
```

```text
[ 인밴드 방식 ]

호스트
   ↓ 데이터와 제어 모두
가상화 엔진
   ↓
스토리지
```

```text
[ 아웃오브밴드 방식 ]

호스트
   ↓ 제어 정보 ↔ 메타데이터 서버
   ↓ 데이터는 스토리지와 직접 전송
스토리지
```

## Ⅳ. 스토리지 가상화의 비교

- 핵심 요약 : 구현 위치에 따라 서버 부하, 이기종 지원 범위, 기능 활용 방식이 달라지는 구조.
- 선택 기준 : 이기종 장비의 범위, 서버 자원 여유, 하부 장비의 고유 기능을 살려야 하는지에 따라 계층을 고른다.

| 비교 항목 | 호스트 기반 | 네트워크 기반 | 어레이 기반 |
| :--- | :--- | :--- | :--- |
| 구현 위치 | 각 서버의 OS 볼륨 관리자 | SAN 스위치 또는 독립 가상화 장치 | 메인 스토리지 컨트롤러 펌웨어 |
| 대표 기술 | Linux LVM(Logical Volume Manager), Veritas Volume Manager | IBM SAN Volume Controller(SVC) | Hitachi VSP 가상화, NetApp FlexArray |
| 이기종 지원 | 호스트 OS가 지원하는 범위 내 | 대부분의 SAN 스토리지 | 인증된 타사 어레이에 한정 |
| 호스트 영향 | 서버 CPU와 메모리 자원 점유 | 호스트에는 영향 없음 | 호스트에는 영향 없음 |
| 주요 장점 | 추가 하드웨어 구매 부담 없음 | 중앙 집중식 단일 뷰 관리 | 컨트롤러 캐시 기능을 최대한 활용 |

## Ⅴ. 스토리지 가상화의 한계와 방안

- 핵심 요약 : 중앙 가상화 장치의 병목, 하부 장비 기능의 비호환, 매핑 메타데이터 손상을 다중 노드 구성, 벤더 독립 기능, 메타데이터 다중화로 대응하는 구조.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 중앙 가상화 장치의 I/O 병목과 단일 장애점 | 전사 트래픽이 인밴드 엔진 하나에 몰리면 지연이 늘고, 엔진 장애 시 연결된 서비스 전체 중단 | 액티브-액티브 구성의 다중 노드 스케일아웃 엔진, 다중 경로 I/O(MPIO, Multipath I/O)를 통한 페일오버 구성 | 경로별 지연, 페일오버 전환 시간 |
| 하부 장비 고유 기능의 비호환 | 하드웨어 가속 기능(스냅샷, 원격 복제)이 상위 가상화 계층의 공통 관리로 묶이며 고유 기능 사용이 제한됨 | 가상화 계층의 벤더 독립 스냅샷과 **지속적 데이터 보호** (CDP, Continuous Data Protection) 엔진 사용, 표준 API 연계 | 기능 사용률, 복구 시점 충족률 |
| 매핑 메타데이터 손상 | 논리-물리 주소 매핑 테이블(Mapping Table)이 훼손되면 연결된 물리 블록을 식별할 수 없어 전사 볼륨이 붕괴할 위험 | 메타데이터 3중 미러링, 주기적 메타데이터 백업과 트랜잭션 저널링 | 메타데이터 무결성 점검 결과, 복원 성공률 |

## Ⅵ. 스토리지 가상화에 대한 기술사적 제언

- 핵심 요약 : 소프트웨어 정의 방식의 풀과 컨테이너 연동, 고속 패브릭을 묶어 스토리지 가상화를 하드웨어 교체 주기와 분리된 운영 체계로 정착.

1. 신규 인프라에서는 기존 장비마다 가상화를 따로 붙이기보다 **소프트웨어 정의 스토리지** (SDS, Software-Defined Storage) 기반으로 풀을 구성해, 하드웨어 교체 주기와 무관하게 용량을 확장하는 방향이 바람직하다.
2. 쿠버네티스 환경에서는 **컨테이너 스토리지 인터페이스** (CSI, Container Storage Interface)로 볼륨을 자동 생성하고 연결하도록 하며, 플랫폼 조직과 스토리지 조직이 용량과 성능 정책을 함께 정의하는 것이 필요하다.
3. 고성능 구간은 **NVMe over Fabrics** (NVMe-oF)로 연결하고 원격 직접 메모리 접근(RDMA, Remote Direct Memory Access) 기반의 RoCE v2(RDMA over Converged Ethernet v2) 같은 고속 전송 방식을 검토하되, 패브릭 장애에 대비한 다중 경로 설계를 함께 두는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : 스토리지 가상화는 이기종 물리 스토리지를 논리 풀로 추상화해 활용률과 무중단 이전을 실현하는 인프라 기술.
- 중앙 병목과 메타데이터 무결성이 가용성을 좌우하므로, 가상화 계층의 이중화와 메타데이터 보호를 도입 전에 확정해야 함.
