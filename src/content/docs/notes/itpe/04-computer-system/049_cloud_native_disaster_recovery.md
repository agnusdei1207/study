## Ⅰ. 클라우드 네이티브 재해복구의 개요

- 핵심 요약 : **클라우드 네이티브 재해복구**는 코드형 인프라와 크로스 리전 복제를 결합해 원격지 인프라를 필요할 때 재현하는 차세대 재해복구 방식.
- 개념 : 데이터센터 재난이나 클라우드 **리전** (Region) 전면 장애가 발생하면, 컨테이너, 마이크로서비스, **코드형 인프라** (IaC, Infrastructure as Code), **GitOps** (Git 저장소를 기준으로 배포 상태를 맞추는 운영 방식)를 이용해 원격 리전에 인프라를 온디맨드로 재현하고 업무를 이어 가는 **재해복구** (DR, Disaster Recovery) 아키텍처.
- 배경 및 필요성 : 온프레미스 DR 센터는 평상시에도 유휴 장비 비용이 들고, 수동 복구에 시간이 오래 걸리며, 본 센터와 환경이 어긋나는 **구성 드리프트** (Configuration Drift) 문제가 생긴다. 클라우드의 탄력성과 코드형 인프라를 결합해 이 문제를 풀려는 요구가 커졌다.
- 주요 목적 : **목표 복구 시간** (RTO, Recovery Time Objective)을 크게 줄이고, **목표 복구 시점** (RPO, Recovery Point Objective)을 0에 가깝게 하며, 상시 대기 비용을 최소화하는 것.

## Ⅱ. 클라우드 네이티브 재해복구의 특징 및 장점

- 핵심 요약 : 선언적 재현, 글로벌 데이터 복제, 오토스케일링, 자동 트래픽 전환이 맞물려 복구 시간을 줄이는 구조.

1. **GitOps 기반 선언적 재현** : 인프라 정의(Terraform)와 쿠버네티스(Kubernetes) 매니페스트를 Git 저장소에 두고, 동기화 도구(ArgoCD)가 원격 리전을 같은 상태로 맞춤 → 수작업 없이 환경 동일성 확보.
2. **크로스 리전 복제** : 리전 사이에 데이터 스토리지를 비동기로 복제해 원격 리전을 상시 동기화 → 복구 시점 목표에 맞춘 데이터 보존.
3. **파일럿 라이트** (Pilot Light) 확장 : 평상시에는 최소한의 파드와 노드만 두었다가, 장애 감지 시 **오토스케일링** (Autoscaling)으로 전체 용량까지 확장. 노드는 Karpenter, 파드는 수평형 파드 오토스케일러(HPA, Horizontal Pod Autoscaler)가 맡음 → 대기 비용과 복구 시간의 균형.
4. **GSLB 자동 전환** : 주 리전의 헬스 체크가 실패하면 **글로벌 서버 부하 분산** (GSLB, Global Server Load Balancing)이 **DNS** (Domain Name System) 응답을 DR 리전으로 바꿔 트래픽을 재라우팅 → 수동 절체 시간 제거.

## Ⅲ. 클라우드 네이티브 재해복구의 구조 및 동작 메커니즘

- 핵심 요약 : GitOps 기반 인프라 동기화, 데이터 복제, GSLB 트래픽 전환이 주 리전과 DR 리전을 잇는 구조이며, 장애 시에는 전환 순서가 정해져 있다.

```text
[ 크로스 리전 DR 구조 ]

사용자 트래픽
      ↓
GSLB (헬스 체크 기반 DNS 라우팅)
      ↓
주 리전 ◀─ GitOps 동기화 ─▶ DR 리전
      ↓                       ▲
주 DB (쓰기) ─ 크로스 리전 복제 ─▶ 보조 DB (읽기)
```

```text
[ 장애 시 전환 순서 ]

주 리전 헬스 체크 실패
      ↓
GSLB가 DNS 응답을 DR 리전으로 변경
      ↓
DR 리전 DB 승격 (쿼럼 확인 후)
      ↓
오토스케일링으로 용량 확장
```

- DB 승격 단계에서 쿼럼 확인을 거치는 이유는, 네트워크 단절을 재난으로 오판한 승격이 두 리전에서 동시에 쓰기를 일으키는 사고를 막기 위해서다.

## Ⅳ. 클라우드 네이티브 재해복구의 비교

- 핵심 요약 : Backup & Restore, Pilot Light, Warm Standby, Active-Active는 복구 시간, 데이터 손실, 평상시 비용에서 단계적으로 대비되는 전략.

| 클라우드 DR 전략 | 아키텍처 구성 및 특징 | 복구 시간 (RTO) | 데이터 손실 (RPO) | 평상시 인프라 비용 |
| --- | --- | --- | --- | --- |
| Backup & Restore | 정기 스냅샷을 원격 스토리지에 보관하고, 재난 시 새로 프로비저닝 | 길다 (수 시간 이상 가능) | 백업 주기만큼 손실 | 가장 낮음 (저장 비용 중심) |
| Pilot Light | 핵심 DB만 원격에 복제 유지, 컴퓨팅은 장애 시 생성 | 비교적 짧음 | 짧음 | 낮음 (DB 인스턴스 중심) |
| Warm Standby | 축소된 규모의 컴퓨팅과 앱이 상시 대기 | 짧음 | 매우 짧음 | 중간 (상시 축소 클러스터) |
| Active-Active | 두 리전 모두 트래픽을 처리하고 양방향으로 동기화 | 거의 없음 (무중단) | 거의 없음 | 가장 높음 (완전 이중화) |

- 과거 온프레미스의 전부 아니면 전무(All-or-Nothing) 방식과 달리, 워크로드의 중요도에 따라 Pilot Light와 Warm Standby를 조합해 비용 대비 가용성을 맞추는 것이 일반적이다.

## Ⅴ. 클라우드 네이티브 재해복구의 한계와 방안

- 핵심 요약 : 리전 용량 부족, DB 스플릿 브레인, DNS 캐싱 지연을 예약 용량, 쿼럼 기반 승격, 짧은 TTL과 Anycast로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 리전 **용량 부족** (Capacity Stockout) | 주 리전 대규모 장애 때 고객이 보조 리전으로 한꺼번에 몰려 특정 GPU나 인스턴스 유형이 품절됨 | 온디맨드 **예약 용량** (ODCR, On-Demand Capacity Reservation)을 DR 리전에 사전 확보하고, 여러 인스턴스 계열을 허용하는 유연 배포 설정 | 예약 용량 충족률, 전환 실패율 |
| **스플릿 브레인** (Split-Brain) 데이터 분기 | 일시적 네트워크 단절을 재난으로 오판해 보조 DB를 승격하면 양쪽에서 쓰기가 발생함 | 스토리지 수준의 쿼럼 기반 승격 검증, **사가** (Saga) 패턴과 보상 트랜잭션으로 정합성 복구 | 잘못된 승격 건수, 분기 데이터 건수 |
| DNS 캐싱에 따른 **전환 지연** | 인터넷 서비스 제공자(ISP)와 클라이언트가 DNS 응답을 오래 캐싱해, 레코드를 바꿔도 이전 리전으로 접속이 계속 들어옴 | DNS 캐시 시간(TTL, Time to Live)을 짧게 낮추고, 고정 IP 기반의 **애니캐스트** (Anycast) 가속 서비스 활용 | TTL 설정값, 구 리전 잔류 트래픽 비율 |

## Ⅵ. 클라우드 네이티브 재해복구의 적용 제언

- 핵심 요약 : 정기 훈련, 등급별 목표 설정, 무상태 설계를 기본 체계로 두어야 전환 절차와 비용이 함께 통제된다.

1. 주 리전을 격리한 상황을 가정하는 **카오스 게임데이** (Chaos GameDay)를 정기 훈련으로 편성해, 전환 절차와 권한 체계를 실전처럼 검증해야 한다.
2. 서비스 중요도에 따라 등급(Tier)을 나누고 등급별로 RTO, RPO 목표와 비용 한도를 함께 정하는 DR 티어링 거버넌스를 세워, 클라우드 비용 관리 관점에서 과잉 대기 자원을 줄여야 한다.
3. 애플리케이션은 세션과 상태를 외부 저장소로 분리하는 **무상태 설계** (Stateless Design)를 지켜, 리전이 바뀌어도 사용자 세션이 끊기지 않도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 클라우드 네이티브 DR은 코드형 인프라, 크로스 리전 복제, GSLB 전환으로 복구 시간을 줄이지만, 용량 부족과 데이터 분기 리스크를 함께 관리해야 하는 방식.
- 시사점 : 복구 시간은 원격지 장비의 존재보다 재현 절차와 전환 권한이 얼마나 자동화되어 있는지에 따라 정해지므로, 목표별 DR 등급을 사전에 설계하는 것이 중요하다.
