## 답안 골격
```text
[다중지역 동시 가동방식 재해복구시스템] ◀━━ 머리: Ⅶ 내 의견 (비즈니스 도메인별 데이터 샤딩과 글로벌 애니캐스트 기반의 단계적 Active-Active 전환)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 지역 광역 재해(지진·화재·전쟁) 시 서비스 전면 마비 → 2개 이상의 원격 리전에서 실서비스를 동시 분산 처리
 ┣━ Ⅱ 특징 ───── RTO=0(즉시 우회) · RPO=0(동기 시) · 대기 자원 유휴 해소 · 분산 데이터 정합성 관리 난이도
 ┣━ Ⅲ 구조 ───── 글로벌 트래픽 분배기(GSLB) + 원격 리전 A/B(K8s) + 분산 스토리지/DB + 감시 쿼럼(Quorum) 노드
 ┣━ Ⅳ 흐름 ───── ① 사용자 접속 → ② GSLB 위치/지연 기반 라우팅 → ③ 리전별 트랜잭션 수용 → ④ 리전 간 비동기/동기 복제
 ┣━ Ⅴ 비교 ───── Active-Active vs Active-Standby vs Multi-AZ Active-Active
 ┗━ Ⅵ 실무 ───── 데이터 쓰기 충돌(Write Conflict) / 광케이블 물리 지연(Latency) / 스플릿 브레인(Split-Brain)
```
- 필수 키워드: 다중지역 동시 가동 · Active-Active · GSLB · RTO=0 · 데이터 동기화 · 분산 합의(Raft) · 스플릿 브레인
- 기출: 137회 3교시 3번 `다중지역 동시 가동방식(Multi-Region Active-Active) 재해복구시스템` 논술형 출제

## 한 줄 본질
- 주 센터와 대기 센터로 나누는 전통적 DR은 재해 시 수동 전환 시간(RTO 수십 분~수 시간)이 걸리고 대기 자원이 낭비됨 → 지리적으로 격리된 복수의 센터에 동일한 액티브 인프라를 올리고 실시간 트래픽을 상시 양방향 분산 처리 → 장애 시 전환 과정 없이 무중단 연속성 보장 / 리전 간 WAN 지연(RTT) 극복 및 데이터 동시 갱신 충돌 해결 과제 수반

## 핵심 그림
```text
[ 다중지역 동시 가동방식 재해복구 시스템 3계층 아키텍처 ]

[ 클라이언트 (전국/글로벌 사용자) ]
                │
                v
[ 1계층: 글로벌 GSLB / Anycast DNS ] ─── (실시간 상태 감시 / 50:50 부하 분산)
       │                              │
       ├──────────────────────────────┼──────────────────────────────┐
       │ (정상 트래픽 분기)           │                              │
       v                              v                              │ (상태 쿼럼)
+──────────────────────────────+ +──────────────────────────────+   │
| 2계층: 제1지역 (수도권 센터) | | 2계층: 제2지역 (영남권 센터) |   │
| - Web/WAS (K8s 클러스터)     | | - Web/WAS (K8s 클러스터)     |   │
| - Ingress Controller         | | - Ingress Controller         |   │
+──────────────┬───────────────+ +──────────────┬───────────────+   │
               │                                │                   │
               v                                v                   v
+───────────────────────────────────────────────────────────────────────+
| 3계층: 분산 데이터 정합성 계층                                         |
| [ 분산 DB 인스턴스 A ] <──────(초고속 전용회선 DCI)─────> [ 분산 DB B ]   |
|                          양방향 복제 / Raft 합의                      |
+───────────────────────────────────────────────────────────────────────+
```

## 핵심 용어
- GSLB(Global Server Load Balancing): 전 세계 또는 전국 단위의 데이터센터 헬스체크 결과를 바탕으로 사용자 DNS 질의에 최적의 가용 IP를 응답하는 글로벌 트래픽 분배 기술
- DCI(Data Center Interconnect): 지리적으로 멀리 떨어진 데이터센터 간에 고대역폭, 초저지연 광 전송망(DWDM)을 직결하여 단일 LAN처럼 연결하는 통신 기술
- 2단계 커밋(2PC, Two-Phase Commit): 분산 노드 간 원자적 트랜잭션을 보장하기 위해 준비(Prepare)와 반영(Commit)의 2단계를 거치는 프로토콜

## 핵심 통찰
- 완벽한 RTO=0은 공짜가 아님 → 두 센터 모두 100% 트래픽을 감당할 수 있도록 평소에 각각 50%의 용량만 사용(오버프로비저닝)해야 한쪽이 죽었을 때 장애 없이 살아남으므로 인프라 비용이 2배로 뜀
- 동기식 복제는 '물리적 거리의 덫'에 걸림 → 서울-부산 간 광케이블 왕복 시간(RTT 약 5~8ms) 때문에 모든 DB 쓰기를 동기식으로 묶으면 트랜잭션 처리량(TPS)이 급감함
- 무상태(Stateless) 계층과 유상태(Stateful) 계층의 분리 설계가 필수임 → 웹/WAS 애플리케이션은 즉시 Active-Active가 가능하지만, DB는 결제 계좌 잔액처럼 단일 진실이 필요한 영역과 장바구니/조회처럼 최종 일관성이 허용되는 영역으로 나누어야 함

## 이웃 토픽과 구분
- Multi-Region Active-Active vs Active-Standby: Active-Active = 양쪽 리전 상시 트래픽 처리, 제로 RTO, 유휴 자원 0% / Active-Standby = 대기 센터 평시 유휴, 재해 시 페일오버 절차(수분~수십분 RTO 소요)

## 문제·원인·대책
- 사례: 137회 기출 및 데이터센터 정전 발생 시 페일오버 지연으로 금융 대고객 서비스가 8시간 동안 중단된 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 양쪽 리전에서 동일 고객의 주문을 동시 수용하여 재고 마이너스 차감 | 리전 간 비동기 복제 지연 시간(Replication Lag) 동안의 동시 쓰기 허용 | 사용자/계정 해시 기반 리전 소유권 할당(Data Pinning) | 특정 사용자의 쓰기를 지정 리전으로 강제하여 충돌 원천 차단 |
| 리전 간 통신 두절 시 양 센터가 독립 운영되며 데이터 찢김(Split-Brain) | 네트워크 파티션 발생 시 상호 상태 확인 불가 | 제3 지역(클라우드 등) 중립 쿼럼(Tie-Breaker) 노드 배치 | 과반수를 확보한 단일 센터만 쓰기 승격 허용 |

## 이렇게 출제된다
- 제137회 3교시 3번: "다중지역 동시 가동방식(Multi-Region Active-Active) 재해복구시스템에 대하여 다음을 설명하시오." → 요구 포인트: Ⅰ 다중지역 동시 가동의 개념 및 필요성 + Ⅲ 3계층(트래픽-앱-데이터) 아키텍처 + Ⅵ 데이터 동기화 지연 및 정합성 보장 방안

## 내 의견
- [비즈니스 크리티컬 도메인 단위의 단계적 Active-Active 전환 전략] 모든 시스템을 일괄 Active-Active로 전환하려는 시도는 천문학적인 비용과 데이터 정합성 실패를 부름 → 나라면: 사용자 조회성 서비스와 세션 클러스터링을 1단계로 분산하고, 핵심 원장 데이터는 리전 간 데이터 Pinning 아키텍처를 적용하여 2단계로 전환하며, 연 2회 무통보 실전 리전 단절 모의훈련을 의무화하여 실질적 무중단 연속성 달성
