## Ⅰ. 백필(Backfill)의 개요

- **개념** : (1) 데이터 엔지니어링 환경에서 파이프라인 로직 수정, 소스 데이터 오류 보정, 누락 데이터 인입 등으로 인해 과거 시점의 데이터를 소급하여 재처리(Reprocessing)하는 작업, 또는 (2) HPC/배치 스케줄링 환경에서 우선순위가 높은 대형 작업의 실행 예정 시간을 지연시키지 않는 범위 내에서 유휴 자원에 소형 작업을 끼워 넣어 실행하는 자원 스케줄링 기법.
- **배경 및 필요성** : 실시간/배치 데이터 파이프라인에서 지연 도착 데이터(Late Data) 및 비즈니스 룰 변경에 따른 소급 적재 요구와, 대규모 컴퓨팅 클러스터의 자원 단편화(Fragmentation)로 인한 노드 유휴 문제를 해결하기 위해 필수적임.
- **핵심 목적** : 과거 데이터의 무결성 및 정합성 회복(데이터 엔지니어링), 클러스터 시스템 자원 활용률 극대화 및 대기 시간 최소화(잡 스케줄링).

## Ⅱ. 백필의 양대 도메인별 핵심 아키텍처 및 동작 메커니즘

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 1. 데이터 엔지니어링 백필 메커니즘 (파티션 멱등 덮어쓰기) ]          │
│                                                                        │
│   과거 날짜 파티션 범위: [2026-01-01 ~ 2026-01-31] 소급 요청 인입     │
│                     │                                                  │
│                     ▼                                                  │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │ [ 데이터 오케스트레이터 (Apache Airflow / Dagster) ]           │   │
│   │  - execution_date 기준 과거 DAG Run 인스턴스 동적 생성         │   │
│   │  - 동시 실행 제한(max_active_runs) 적용으로 소스 DB 부하 제어  │   │
│   └───────────────────────────────┬────────────────────────────────┘   │
│                                   │ 원자적 파티션 교체 (Atomic Overwrite)│
│                                   ▼                                    │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │ [ 데이터 레이크/웨어하우스 (Iceberg / Delta Lake / BigQuery) ] │   │
│   │  - 파티션별 타깃 디렉터리 임시 적재 -> 무중단 포인터 스왑      │   │
│   └────────────────────────────────────────────────────────────────┘   │
│                                                                        │
│   [ 2. HPC/클러스터 EASY 백필 스케줄링 메커니즘 ]                      │
│                                                                        │
│   현재 클러스터 가용 노드: 2대                                         │
│   대기 큐:                                                             │
│    - Job 1 (우선순위 최고, 8개 노드 필요, 1시간 뒤 실행 예약됨)        │
│    - Job 2 (우선순위 낮음, 2개 노드 필요, 30분 실행) -> 백필 승인!     │
│    - Job 3 (우선순위 낮음, 2개 노드 필요, 2시간 실행) -> 백필 거부!    │
│    * 메커니즘: Job 2는 Job 1의 시작 시간(1시간 뒤) 전에 끝나므로 즉시 실행│
└────────────────────────────────────────────────────────────────────────┘
```

- **데이터 멱등성(Idempotency)** : 동일한 파라미터와 시간 범위로 백필을 수십 번 재실행하더라도 항상 동일한 결과가 도출되도록 `INSERT OVERWRITE` 또는 업서트(Upsert/Merge) 패턴을 강제.
- **EASY(Extensible Argonne Scheduling System) 백필** : 최우선순위 작업의 시작 예정 시각(Shadow Time)을 계산하여 자원을 예약해 두고, 그보다 일찍 종료될 수 있는 작은 후속 작업만 유휴 슬롯에 끼워 실행.

## Ⅲ. 백필 구현 방식 및 관련 스케줄링 전략 비교 분석

| 도메인 | 구현 기법 | 핵심 메커니즘 | 주요 장점 | 고려사항 및 리스크 |
| :--- | :--- | :--- | :--- | :--- |
| **데이터 파이프라인** | **전체 재적재 (Full Refresh)** | 기존 테이블 전체를 DROP/TRUNCATE 후 전체 재계산 | 로직이 단순하고 정합성 완벽 보장 | 막대한 컴퓨팅 비용 및 장시간 소요 |
| | **파티션 단위 백필 (Partitioned Backfill)**| 일자/시간 파티션 단위로 필터링하여 특정 구간만 덮어쓰기 | 비용 효율적이며 실시간 서빙 영향 최소화 | 파티션 간 집계 데이터 정합성 유지 주의 |
| **잡 스케줄링** | **보수적 백필 (Conservative Backfill)**| 큐에 있는 모든 대기 작업의 예약 시간을 엄격히 보장 | 모든 대기 작업의 기아(Starvation) 방지 | 예약 조건이 엄격하여 백필 기회 감소 |
| | **EASY 백필 (EASY Backfill)** | **오직 최우선 1등 작업의 예약 시간만 보장** | **클러스터 활용률 극대화, 구현 단순** | 2등 이하 작업의 기아 현상 가능성 |

## Ⅳ. 백필 수행 시 주요 한계점 및 해결 방안

- **원천 DB(OLTP) 및 운영 파이프라인 리소스 고갈** :
  - **한계점** : 과거 대용량 데이터를 한꺼번에 조회 및 적재하면서 프로덕션 DB 커넥션 풀 고갈 및 CPU 100% 장애 유발.
  - **해결 방안** : 배치 처리 청크 크기(Chunk Size) 제한, 읽기 전용 복제본(Read Replica) 지정, 야간 유휴 시간대 분할 백필 스케줄링.
- **다운스트림 데이터 의존성(Cascade Dependency) 전파 오류** :
  - **한계점** : 상위 원천 테이블을 백필했으나 이를 참조하는 파생 마트 테이블들이 연쇄 갱신되지 않아 데이터 간 불일치 발생.
  - **해결 방안** : dbt(data build tool) 등 데이터 리니지 기반의 다운스트림 자동 전파 실행(`dbt run --select source+`).
- **HPC 스케줄링에서 작업 실행 시간(Walltime) 과소 추정 오류** :
  - **한계점** : 사용자가 백필로 끼워 넣기 위해 예상 실행 시간을 실제보다 짧게 선언하여 최우선 대형 작업의 시작이 지연되는 현상.
  - **해결 방안** : 선언된 Walltime 초과 시 즉각 작업을 강제 종료(SIGKILL)하는 엄격한 타임아웃 정책 적용.

## Ⅴ. 성공적인 엔지니어링 운영을 위한 기술사적 제언

- **파이프라인 설계 초기 단계부터 멱등성(Idempotency) 내재화** : 백필은 예외적인 상황이 아니라 운영 중 상시 발생하는 일상 작업으로 간주해야 하므로, 모든 데이터 파이프라인 DAG를 설계할 때 현재 시각(`now()`) 참조를 금지하고 실행 기준 시점(Logical Execution Date) 기반의 파티션 덮어쓰기를 표준 아키텍처로 강제해야 함.
- **모던 데이터 레이크하우스(ACID) 도입** : Apache Iceberg, Delta Lake 등 트랜잭션을 지원하는 테이블 포맷을 도입하여 백필 중 쿼리 실패 시 자동 롤백 및 읽기 일관성(Snapshot Isolation)을 보장함으로써 백필 중에도 대시보드 조회가 중단되지 않도록 조치할 것을 제언함.
