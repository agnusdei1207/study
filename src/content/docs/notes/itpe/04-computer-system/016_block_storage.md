## 답안 골격
```text
[블록 스토리지] ◀━━ 머리: Ⅶ 내 의견 (NVMe-oF 기반 RoCE v2 패브릭 구성을 통한 DB·AI 체크포인트 I/O 극대화)
 ┃
 ┣━ Ⅰ 개요 ───── 파일/오브젝트 스토리지의 메타데이터 오버헤드 → 로우(Raw) 블록 단위 초저지연 I/O 제공
 ┣━ Ⅱ 특징 ───── 고정 블록 분할 · 논리 블록 주소(LBA) · 마이크로초 저지연 · 단일 호스트 전용 마운트
 ┣━ Ⅲ 구조 ───── LUN(Logical Unit Number) + SAN 스위치(FC/iSCSI) + HBA + NVMe-oF 컨트롤러
 ┣━ Ⅳ 흐름 ───── ① OS I/O 요청 → ② 블록 디바이스 드라이버 변환 → ③ SAN/NVMe 패브릭 전송 → ④ 컨트롤러 블록 쓰기
 ┣━ Ⅴ 비교 ───── 블록 vs 파일 vs 오브젝트 스토리지
 ┗━ Ⅵ 실무 ───── 다중 호스트 동시 쓰기 불가 / 고비용(GB당 단가) / 스토리지 프로비저닝(Thin vs Thick)
```
- 필수 키워드: LBA(Logical Block Addressing) · SAN(Storage Area Network) · NVMe-oF · IOPS · LUN · 로우 디바이스(Raw Device)
- 기출: 132회 1교시 `3대 스토리지 비교`, 140회 3교시 `대규모 AI 인프라 구축을 위한 3대 스토리지 비교 및 최적 활용방안`

## 한 줄 본질
- 파일 시스템이나 객체 스토리지의 무거운 메타데이터 조회와 전체 파일 갱신 오버헤드 → 데이터를 고정 크기 블록(512B/4KB)으로 쪼개어 고유 논리 주소(LBA)로 직접 제어하는 원시(Raw) 볼륨 제공 → 데이터베이스 및 VM 부팅용 초고속 IOPS 및 마이크로초 저지연 달성 / 네트워크 경유 다중 노드 파일 공유 불가 및 높은 인프라 비용

## 핵심 그림
```text
[ 서버 OS (호스트) ]
  │
  ├─ [ 파일 시스템 계층 (ext4 / XFS / NTFS) ]
  │           │
  └─ [ RDBMS 엔진 (Oracle / MySQL) ] ──(Raw Device 직접 접근)
              │
              v
[ 블록 I/O 드라이버 (LBA 주소 변환: Sector #1024 ~ #2048) ]
              │
  (초고속 SAN 패브릭: Fibre Channel 32G / NVMe-oF RDMA)
              │
              v
[ 블록 스토리지 컨트롤러 (Array Controller) ]
  +--------------------------------------------------------+
  |  LUN 0 (고성능 SSD 풀)  |  LUN 1 (고용량 HDD 풀)       |
  |  [Block 0][Block 1]...  |  [Block 0][Block 1]...       |
  +--------------------------------------------------------+
```

## 핵심 용어
- LBA(Logical Block Addressing): 스토리지의 물리적 실린더/헤더 구조와 무관하게, 블록마다 0번부터 순차적으로 부여된 고유 번호를 통해 선형적으로 데이터 위치를 지정하는 주소 체계
- NVMe-oF(NVMe over Fabrics): 고속 NVMe 명령어 세트를 이더넷(RDMA)이나 파이버 채널 패브릭 위로 확장하여, 원격 네트워크 스토리지를 로컬 PCIe SSD 수준의 지연시간(수 마이크로초)으로 접근하는 기술

## 핵심 통찰
- 블록 스토리지는 스스로 파일이나 폴더의 개념을 알지 못함 → 데이터의 물리적 배치 주소만 관리하며, 파일 이름이나 계층 구조는 호스트 OS의 파일 시스템이 책임짐
- RDBMS(Oracle, PostgreSQL)가 최고 성능을 낼 수 있는 유일한 저장소임 → 파일 시스템의 이중 버퍼링을 건너뛰고 OS 캐시 없이 직접 블록을 읽고 쓰는 Direct I/O가 가능하기 때문
- 여러 대의 서버가 동일한 블록 볼륨(LUN)을 동시에 마운트하여 일반 파일시스템으로 쓰면, 파일시스템 메타데이터 동기화 부재로 즉각적인 파일시스템 깨짐(Corruption) 발생 → GFS2나 OCFS2 같은 클러스터 파일시스템이 필수적으로 개입해야 함

## 이웃 토픽과 구분
- 블록 스토리지 vs 파일 스토리지: 블록 스토리지 = LBA 주소 기반의 전용 원시 볼륨(DB/OS용, 공유 불가) / 파일 스토리지 = NFS/SMB 프로토콜 기반의 계층형 디렉터리 공유 볼륨(다중 사용자 협업용)

## 문제·원인·대책
- 사례: 140회 기출 고빈도 트랜잭션 금융 DB 및 대규모 AI 학습 체크포인트 I/O 지연 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 대규모 언어 모델 학습 중 체크포인트 저장 시 GPU 연산 수십 분 중단 | 기존 레거시 iSCSI 블록 스토리지의 네트워크 대역폭 및 TCP 스택 병목 | RoCE v2 기반 NVMe-oF(RDMA) 블록 스토리지 어레이 도입 | 테라바이트급 가중치 덤프 시간을 80% 이상 단축 |
| 프로비저닝된 블록 볼륨의 실제 사용률 저조로 비용 낭비 | 볼륨 생성 시 물리 디스크 전체를 선할당하는 Thick Provisioning | 씬 프로비저닝(Thin Provisioning) 및 자동 볼륨 확장(Auto-grow) 정책 | 스토리지 실질 가용 용량 2배 이상 개선 |
