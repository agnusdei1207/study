## Ⅰ. 프로세스 간 통신(IPC)의 개요

- 개념 : 운영체제에서 **독립된 가상 주소 공간**을 가지며 상호 격리되어 실행되는 프로세스들이 협업을 위해 데이터와 상태 정보를 교환하고 작업을 동기화할 수 있도록 지원하는 커널 매개 통신 메커니즘.
- 배경 및 필요성 : 현대 멀티태스킹 OS는 프로세스 간 **메모리 보호** (Memory Protection)를 기본 원칙으로 하므로 한 프로세스가 다른 프로세스의 메모리를 직접 참조할 수 없어, 프로세스 간 안전한 상호작용 채널이 요구됨.
- 핵심 목적 : 프로세스 간 데이터 공유 및 메시지 교환, **동기화(Synchronization)** 보장, 네트워크를 넘어선 분산 프로세스 협업 인프라 제공.

## Ⅱ. 프로세스 간 통신(IPC)의 핵심 아키텍처 및 동작 메커니즘

IPC는 커널을 거치지 않고 직접 메모리를 읽고 쓰는 '공유 메모리(Shared Memory)' 모델과 커널 큐를 통해 데이터를 복사 전달하는 '메시지 전달(Message Passing)' 모델로 대별됨.

```text
[ IPC 2대 아키텍처: 공유 메모리 vs 메시지 전달 ]

1. 공유 메모리 모델 (Shared Memory Model - 초고속)
+-------------------+                       +-------------------+
| Process A 주소공간|                       | Process B 주소공간|
| +---------------+ |                       | +---------------+ |
| | 로컬 메모리   | |                       | | 로컬 메모리   | |
| +---------------+ |                       | +---------------+ |
| | 공유 매핑 영역 | | ───┐               ┌─── | | 공유 매핑 영역 | |
| +---------------+ |   │               │   | +---------------+ |
+-------------------+   ▼               ▼   +-------------------+
             [물리 메모리 내 공유 세그먼트 (DRAM)]
             * 데이터 직접 참조: 커널 개입 없음 (Zero-Copy)
             * 동기화(세마포어/뮤텍스) 필수!

2. 메시지 전달 모델 (Message Passing: 파이프, 소켓, 메시지 큐)
+-------------------+                       +-------------------+
| Process A (Sender)|                       | Process B (Recv)  |
| send(msg) 호출    |                       | recv(buf) 호출    |
+-------------------+                       +-------------------+
          │ (시스템 콜: 복사 1)                      ▲ (복사 2)
          ▼                                         │
+---------------------------------------------------------------+
| OS 커널 (Kernel Space: Message Queue / Pipe Buffer / Socket)   |
+---------------------------------------------------------------+
```

- **공유 메모리 (Shared Memory)** : 두 프로세스가 동일한 물리 메모리 페이지를 가상 주소에 매핑하여 커널 시스템 콜 복사 없이 최고 속도로 통신(POSIX `shm_open`, `mmap`).
- **파이프 (Pipe / FIFO)** : 단방향 바이트 스트림 통신으로 익명 파이프(부모-자식 간)와 명명된 파이프(FIFO: 무관한 프로세스 간)로 구분.
- **메시지 큐 (Message Queue)** : 커널이 관리하는 큐에 메시지 단위로 데이터를 저장하고 우선순위에 따라 비동기 수신(POSIX `mq_open`).
- **유닉스 도메인 소켓 (UDS)** : 네트워크 소켓 API를 사용하되 IP 패킷화 없이 커널 메모리 버퍼를 통해 초고속 로컬 프로세스 간 통신 수행.
- **동기화 프리미티브 (Semaphore / Mutex)** : 공유 메모리 동시 접근 시 경쟁 상태를 방지하기 위해 원자적 카운터 및 락 제어 연동.

## Ⅲ. 프로세스 간 통신(IPC)의 세부 구성 요소 및 비교 분석

| IPC 기법 | 통신 모델 | 통신 방향 및 범위 | 전송 속도 / 성능 | 동기화 필요 여부 |
|---|---|---|---|---|
| **익명 파이프 (Pipe)** | 스트림 | 단방향 (부모-자식 간) | 빠름 (커널 버퍼 1회 복사) | 파이프 내부 자동 블로킹 |
| **명명된 파이프 (FIFO)** | 스트림 | 단방향/양방향 (임의 프로세스) | 빠름 | 자동 블로킹 동기화 |
| **메시지 큐 (Message Queue)** | 패킷/메시지 | 양방향 (큐 식별자 공유) | 보통 (구조체 복사 오버헤드) | 큐 상태에 따른 블로킹 |
| **공유 메모리 (Shared Memory)**| 메모리 직접 | 양방향 (최고 속도) | 극대화 (Zero-Copy) | 개발자가 세마포어로 직접 구현 |
| **유닉스 소켓 (UDS)** | 소켓 스트림 | 양방향 (로컬 프로세스) | 매우 빠름 (TCP 스택 바이패스)| 소켓 내부 동기화 내장 |
| **네트워크 소켓 (TCP/IP)** | 패킷 스트림 | 양방향 (이기종 원격 호스트) | 지연시간 큼 (NIC 및 네트워크) | 프로토콜 레벨 핸드셰이크 |

- 동일 노드 내 대용량 데이터는 공유 메모리가 압도적이나 동기화 버그 위험이 크며, 구조화된 제어 메시지는 유닉스 도메인 소켓이나 gRPC가 널리 쓰임.

## Ⅳ. 프로세스 간 통신(IPC)의 주요 한계점 및 해결 방안

- 공유 메모리 동기화 실패에 따른 데이터 레이스 및 교착상태 :
  - 한계점 : 세마포어/뮤텍스 획득 순서 오류나 프로세스 비정상 종료 시 락 미해제로 인해 시스템 전체 데드락 유발.
  - 해결 방안 : Robust Mutex(소유자 프로세스 사망 시 자동 복구) 적용 및 Lock-Free 링버퍼(Ring Buffer) 아키텍처 채택.
- 메시지 전달 방식의 잦은 문맥 교환 및 메모리 복사 부하 :
  - 한계점 : 데이터가 송신자 메모리 -> 커널 버퍼 -> 수신자 메모리로 2회 복사(Double Copy)되며 대용량 전송 시 CPU 점유율 폭증.
  - 해결 방안 : vmsplice 시스템 콜 및 제로 카피(Zero-Copy) 전송 API 활용, 대용량 데이터는 공유 메모리 참조 전달.
- **마이크로서비스(MSA)** 환경에서 네트워크 IPC의 직렬화 오버헤드 :
  - 한계점 : JSON over HTTP/1.1 사용 시 텍스트 파싱 및 무거운 TCP 연결 맺기로 인한 서비스 간 레이턴시 급증.
  - 해결 방안 : Protocol Buffers 기반 고속 바이너리 직렬화와 HTTP/2 다중화를 지원하는 gRPC 프레임워크 표준화.

## Ⅴ. 프로세스 간 통신(IPC) 적용 및 발전을 위한 기술사적 제언

- 쿠버네티스 파드 내 로컬 통신 최적화 : 동일 파드 내 컨테이너 간 통신 시 느린 로컬호스트 TCP 대신 볼륨 마운트 기반의 Unix Domain Socket 또는 IPC 네임스페이스 공유(`shareProcessNamespace`) 적용 권장.
- 차세대 비동기 **I/O io** _uring 연동 : 고성능 IPC 파이프라인에서 시스템 콜 진입 비용을 제거하기 위해 커널과 유저 공간이 링버퍼를 공유하는 `io_uring` 적극 도입 필요.
- **eBPF** 소켓 리다이렉션을 통한 IPC 가속 : 서비스 메시(Istio/Envoy) 도입 시 발생하는 프록시 IPC 지연을 해소하기 위해 eBPF 기반 sockops 우회 라우팅 구축 권장.
