## 연관 키워드

- 프로세스 간 통신(IPC), 공유 메모리(Shared Memory), 메시지 전달(Message Passing)
- 파이프(Pipe), 명명된 파이프(FIFO), 메시지 큐(Message Queue), 유닉스 도메인 소켓(UDS)
- 세마포어(Semaphore), 뮤텍스(Mutex), 로버스트 뮤텍스(Robust Mutex), 제로 카피(Zero-Copy)
- 데이터 레이스, 메모리 보호, gRPC, Protocol Buffers, 마이크로서비스(MSA)

## Ⅰ. 프로세스 간 통신의 개요

- 핵심 요약 : **프로세스 간 통신** (IPC, Inter-Process Communication)은 격리된 프로세스들이 데이터와 상태를 교환하고 동기화하도록 커널이 중개하는 통신 메커니즘.
- 개념 : 운영체제에서 독립된 가상 주소 공간을 가지고 서로 격리되어 실행되는 프로세스들이 협업을 위해 데이터와 상태 정보를 주고받고 작업 순서를 맞출 수 있도록 지원하는 메커니즘.
- 배경 및 필요성 : 멀티태스킹 운영체제(OS, Operating System)는 **메모리 보호** (Memory Protection)를 기본 원칙으로 하여 한 프로세스가 다른 프로세스의 메모리를 직접 참조하지 못하므로, 안전한 상호작용 채널 필요.
- 주요 목적 : 데이터 공유와 메시지 교환, **동기화** (Synchronization) 보장, 같은 노드와 네트워크 경계를 넘는 분산 프로세스 협업 기반 제공.

## Ⅱ. 프로세스 간 통신의 특징 및 장점

- 핵심 요약 : 공유 메모리와 메시지 전달이라는 두 모델이 속도와 안전성을 각각 다른 방식으로 확보.

1. **공유 메모리** (Shared Memory) : 두 프로세스가 같은 물리 메모리 영역을 자기 주소 공간에 매핑해 커널을 거치지 않고 직접 읽고 씀 → 복사 비용이 없어 대용량 데이터 전달에 유리.
2. **파이프** (Pipe) : 단방향 바이트 스트림으로, 부모와 자식 프로세스 사이의 익명 파이프와 무관한 프로세스 사이의 명명된 파이프(FIFO, First In, First Out)로 나뉨 → 간단한 명령 연결에 적합.
3. **메시지 큐** (Message Queue) : 커널이 관리하는 큐에 메시지 단위로 저장하여 비동기로 주고받음 → 송수신 시점을 분리해 결합도 감소.
4. **유닉스 도메인 소켓** (UDS, Unix Domain Socket) : 네트워크 소켓 API (Application Programming Interface)를 쓰되 같은 호스트 안에서만 동작하여 IP (Internet Protocol) 패킷 처리 없이 빠르게 통신 → 소켓 기반 프로그램을 그대로 로컬 통신에 활용.
5. 동기화 프리미티브 : 세마포어와 뮤텍스로 공유 자원의 동시 접근을 제어 → 경쟁 상태(Race Condition)를 막아 데이터 무결성 확보.

## Ⅲ. 프로세스 간 통신의 구조 및 동작 메커니즘

- 핵심 요약 : 커널을 우회하는 공유 메모리와 커널 버퍼를 거치는 메시지 전달이 IPC의 두 가지 기본 구조.

```text
[ 공유 메모리 모델 ]

Process A
   ↓ 직접 읽기·쓰기
공유 메모리 영역 (물리 메모리)
   ↑ 직접 읽기·쓰기
Process B
   ↓
세마포어·뮤텍스로 동시 접근 조정
```

```text
[ 메시지 전달 모델 ]

Process A (send)
   ↓ 시스템 콜 : 1차 복사
커널 버퍼 (파이프·큐·소켓)
   ↓ 시스템 콜 : 2차 복사
Process B (recv)
```

- **공유 메모리 모델** : 커널 개입 없이 데이터를 직접 참조하여 **제로 카피** (Zero-Copy)에 가까운 속도를 얻으나, 동기화를 개발자가 직접 책임짐.
- **메시지 전달 모델** : 파이프, 메시지 큐, 소켓이 해당하며 커널 버퍼로 데이터를 복사하므로 동기화와 격리를 커널이 보장하는 대신 복사 비용이 발생.

## Ⅳ. 프로세스 간 통신의 비교

- 핵심 요약 : 같은 노드 안에서는 속도와 동기화 부담의 교환 관계로, 이기종 원격 통신은 네트워크 소켓으로 구분.

| 비교 항목 | 익명·명명 파이프 | 메시지 큐 | 공유 메모리 | UDS | 네트워크 소켓 (TCP/IP, Transmission Control Protocol/Internet Protocol) |
| --- | --- | --- | --- | --- | --- |
| 통신 모델 | 바이트 스트림 | 메시지 단위 | 메모리 직접 참조 | 소켓 스트림 | 패킷 스트림 |
| 방향 및 범위 | 단방향(익명) / 양방향(명명) | 양방향, 큐 식별자 공유 | 양방향, 같은 노드 | 같은 호스트 | 원격 호스트 포함 |
| 전송 성능 | 커널 버퍼 1회 복사 | 구조체 복사 부담 | 복사 없이 최고 속도 | 네트워크 스택 생략으로 빠름 | 네트워크 지연의 영향 큼 |
| 동기화 | 자동 블로킹 | 큐 상태에 따른 블로킹 | 세마포어로 직접 구현 | 소켓 내부 처리 | 프로토콜 수준 확인 |

- 선택 기준 : 같은 노드에서 대용량을 주고받으면 공유 메모리, 구조화된 제어 메시지는 UDS나 gRPC처럼 구현이 단순한 방식을 우선 검토.

## Ⅴ. 프로세스 간 통신의 한계와 방안

- 핵심 요약 : 동기화 실패, 복사 부하, 서비스 간 직렬화 비용을 락 설계, 제로 카피, 바이너리 RPC로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 공유 메모리의 데이터 레이스와 교착 | 획득 순서 오류나 프로세스 비정상 종료로 락이 풀리지 않아 전체 교착 | 소유 프로세스가 죽어도 복구되는 로버스트 뮤텍스(Robust Mutex) 적용, 락 없는 링버퍼 설계 검토 | 락 대기 시간, 교착 발생 건수 |
| 메시지 전달의 복사 부하 | 송신자 메모리에서 커널 버퍼, 수신자 메모리로 2회 복사되어 대용량 전송 시 CPU (Central Processing Unit) 점유 증가 | 제로 카피 전송 API 사용, 대용량은 공유 메모리 참조 전달로 전환 | CPU 사용률, 복사 바이트 수 |
| 마이크로서비스 아키텍처(MSA, Microservice Architecture) 환경의 직렬화 오버헤드 | JSON (JavaScript Object Notation) 텍스트 파싱과 HTTP (Hypertext Transfer Protocol)/1.1 연결 비용으로 서비스 간 지연 증가 | Protocol Buffers 기반 바이너리 직렬화와 HTTP/2 다중화를 쓰는 gRPC 표준화 | 호출 지연 시간, 직렬화 비용 |

## Ⅵ. 프로세스 간 통신에 대한 기술사적 제언

- 핵심 요약 : 노드 내 통신은 로컬 IPC 경로로, 노드 간 통신은 표준 바이너리 RPC로 나누어 설계하는 원칙을 조직 차원에서 정착.

1. 플랫폼 팀이 같은 파드 내 컨테이너 사이의 통신을 UDS 경로를 공유 볼륨에 두는 방식으로 표준화하여 네트워크 경유 비용을 제거.
2. 시스템 아키텍트가 공유 메모리를 쓰는 모듈에 대해 동기화 규칙과 락 획득 순서를 설계 문서로 정하고, 코드 리뷰 체크리스트에 반영.
3. 서비스 메시 운영 조직이 사이드카 간 로컬 소켓 경로에 eBPF 기반 소켓 리다이렉션 적용 여부를 성능 시험으로 판단.

## Ⅶ. 결론

- 핵심 요약 : IPC는 공유 메모리와 메시지 전달 두 모델로 격리된 프로세스의 협업을 지원하며, 속도와 동기화 부담의 교환으로 설계.
- 시사점 : 복사 비용과 동기화 위험을 노드 안팎의 경계에 맞춰 나누어 관리할 때 IPC의 장점을 안정적으로 얻을 수 있음.
