## 답안 골격
```text
[뮤텍스] ◀━━ 머리: Ⅶ 내 의견 (스핀락과 블로킹의 임계구역 시간 기반 선택 및 RAII 패턴 기반 락 자동 해제 강제)
 ┃
 ┣━ Ⅰ 개요 ───── 멀티스레드 공유 자원 동시 접근 시 경쟁 상태(Race Condition) → 단일 스레드 상호배제(Mutex)
 ┣━ Ⅱ 특징 ───── 상호배제(Mutual Exclusion) · 소유권(Ownership) 존재 · 락(Lock) 획득 및 해제 · 1개 자원 보호
 ┣━ Ⅲ 구조 ───── 불리언 락 플래그(locked/unlocked) + 소유 스레드 ID + 대기 큐(Wait Queue) + 원자적 TAS 명령어
 ┣━ Ⅳ 흐름 ───── ① lock() 호출 → ② 원자적 락 획득(성공 시 임계구역 진입) → ③ 실패 시 대기 큐 수면(Sleep) → ④ unlock() 시 대기 스레드 기상
 ┣━ Ⅴ 비교 ───── 뮤텍스 vs 이진 세마포어 vs 스핀락(Spinlock)
 ┗━ Ⅵ 실무 ───── 락 획득 후 미해제에 따른 데드락 / 우선순위 역전(Priority Inversion) / 빈번한 문맥 교환 오버헤드
```
- 필수 키워드: 상호배제(Mutual Exclusion) · 소유권(Ownership) · lock()/unlock() · 원자적 명령어(TAS) · 피터슨 알고리즘 · 우선순위 역전
- 기출: 139회 4교시 2번 `운영체제의 프로세스 동기화 기법 중 뮤텍스(Mutex), 세마포어(Semaphore), 모니터(Monitor)에 대하여 설명하시오.`

## 한 줄 본질
- 공유 메모리에 여러 스레드가 동시에 쓰기를 시도할 때 발생하는 데이터 불일치(Race Condition) → 락(Lock)을 쥔 단 하나의 스레드만 임계 구역에 진입하도록 보장하고 락을 쥔 자만 해제할 수 있는 엄격한 소유권(Ownership) 메커니즘 → 완벽한 데이터 무결성 보장 / 락 경합 시 스레드 수면 및 문맥 교환 오버헤드 발생

## 핵심 그림
```text
[ 뮤텍스(Mutex) 락 획득 및 상호배제 흐름 ]

Thread A (실행 중)                         Thread B (동시 접근)
      │                                            │
      ├─> mutex.lock() (성공! Lock 획득)            │
      │   - locked = true                          │
      │   - owner = Thread A                       │
      v                                            v
+───────────────────────────+               mutex.lock() 호출
|   임계 구역 (Critical)    |                      │
|   - 공유 변수 안전하게 수정|               (Lock 이미 점유됨!)
+─────────────┬─────────────+                      │
              │                                    v
              │                            +───────────────────────────+
              v                            |    뮤텍스 대기 큐 (Sleep) |
      mutex.unlock() (해제!)               |    - CPU 반납 및 문맥 교환|
      - locked = false                     +─────────────┬─────────────+
      - Wakeup(Thread B) ────────────────────────────────┘
```

## 핵심 용어
- 상호배제(Mutual Exclusion): 하나의 프로세스나 스레드가 임계 구역(Critical Section)에서 작업 중일 때, 다른 어떤 스레드도 동일 임계 구역에 진입할 수 없도록 강제하는 원칙
- 소유권(Ownership): 뮤텍스 락을 획득(lock)한 바로 그 스레드만이 해당 락을 해제(unlock)할 수 있는 고유 속성(세마포어와의 가장 결정적인 기술적 차이점)
- TAS(Test-And-Set): "메모리 특정 위치의 이전 값을 읽어오고 새 값을 쓰는 동작"을 CPU 하드웨어 차원에서 단 1클록 안에 원자적(Atomic)으로 분할 없이 수행하는 동기화 명령어

## 핵심 통찰
- 이진 세마포어(0 또는 1)와 뮤텍스는 겉보기에 같아 보이지만 '소유권(Ownership)' 유무로 완전히 갈림 → 세마포어는 A 스레드가 wait하고 B 스레드가 signal 할 수 있는 '신호 기제'이지만, 뮤텍스는 A가 lock했으면 반드시 A만 unlock해야 하는 '자원 잠금 장치'임
- 임계 구역의 실행 시간이 수 나노초 단위로 매우 짧을 때는 스레드를 잠재우고 깨우는 문맥 교환 비용(수 마이크로초)이 더 크므로, 루프를 돌며 바쁘게 대기하는 스핀락(Spinlock)이 뮤텍스보다 훨씬 빠름
- 뮤텍스를 쥐고 있는 저순위 스레드가 고순위 스레드의 작업을 방해하는 '우선순위 역전(Priority Inversion)'이 발생하므로, 실시간 OS(RTOS)에서는 우선순위 상속(Priority Inheritance) 메커니즘이 필수 탑재됨

## 이웃 토픽과 구분
- 뮤텍스 vs 스핀락: 뮤텍스 = 락 획득 실패 시 CPU를 양보하고 대기 큐에서 수면(Sleep, 긴 작업용) / 스핀락 = CPU를 반납하지 않고 루프를 돌며 락 해제를 대기(Busy-wait, 멀티코어의 극히 짧은 작업용)

## 문제·원인·대책
- 사례: 139회 기출 멀티스레드 주문 처리 시스템에서 예외 발생 후 락 미해제로 인한 전체 스레드 멈춤
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 비즈니스 로직 예외 발생 시 `unlock()`을 호출하지 못하고 함수를 탈출하여 영구 교착 | 수동 lock/unlock 배치 시 예외 경로 누락 | RAII 패턴 기반 스코프 락(`std::lock_guard`, `try-with-resources`) 적용 | 스택 언와인딩 시 소멸자에서 락 자동 반납 100% 보장 |
| 저우선순위 스레드가 락을 쥔 채 중간 순위 스레드에 밀려 고우선순위 스레드 타임아웃 | 중간 스레드의 CPU 선점으로 인한 우선순위 역전(Priority Inversion) | 우선순위 상속 프로토콜(PIP) 활성화된 뮤텍스 사용 | 락을 쥔 스레드의 우선순위를 임시 승격시켜 락 조기 반납 유도 |

## 내 의견
- [락 경합(Lock Contention) 최소화를 위한 락 분할 및 RCU(Read-Copy-Update) 전환] 단일 거대 뮤텍스로 맵 전체를 잠그는 코드는 멀티코어 환경에서 1개 코어만 일하게 만드는 병목의 근원임 → 나라면: 락의 단위를 버킷 단위로 쪼개는 락 스트라이핑(Lock Striping, `ConcurrentHashMap` 방식)을 적용하고, 읽기 비중이 90% 이상인 데이터 구조는 리눅스 커널 표준인 RCU 기법을 도입하여 읽기 작업 시 락을 아예 잡지 않도록 최적화
