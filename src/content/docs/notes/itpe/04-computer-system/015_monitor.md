## 답안 골격
```text
[모니터] ◀━━ 머리: Ⅶ 내 의견 (Mesa 시그널링 규격에 맞춘 while 루프 재검증 기반 모니터 구현 강제)
 ┃
 ┣━ Ⅰ 개요 ───── 세마포어 P/V 수동 연산의 프로그래밍 오류 극복 → 언어 수준의 자동 상호배제 캡슐화
 ┣━ Ⅱ 특징 ───── 자동 상호배제 · 조건 변수(Condition Variable) · 캡슐화(ADT) · 정보 은닉
 ┣━ Ⅲ 구조 ───── 공유 데이터 + 내부 프로시저 + 진입 큐(Entry Queue) + 조건 변수 대기 큐(Condition Queue)
 ┣━ Ⅳ 흐름 ───── ① 프로시저 호출 진입 → ② 조건 불충족 시 wait()(조건 큐 수면) → ③ 타 스레드 signal() → ④ 준비 큐 이동 후 재실행
 ┣━ Ⅴ 비교 ───── 모니터 vs 뮤텍스 vs 세마포어 / Hoare 방식 vs Mesa 방식
 ┗━ Ⅵ 실무 ───── 허위 깨어남(Spurious Wakeup) / signal 호출 순서 오류 / 데드락 위험
```
- 필수 키워드: 공유 데이터 캡슐화 · 조건 변수(Condition Variable) · wait/signal · Hoare 방식 · Mesa 방식 · Spurious Wakeup
- 기출: 139회 4교시 `뮤텍스, 세마포어, 모니터` → Ⅲ 메커니즘 및 Ⅴ 비교표

## 한 줄 본질
- 세마포어의 P/V 연산 수동 배치 실수로 인한 상호배제 실패 및 영구 교착상태 위험 → 공유 데이터와 조작 프로시저를 단일 모듈로 묶고 컴파일러가 진입 스레드를 오직 1개로 제한하는 고수준 동기화 구조체 → 안전하고 직관적인 동시성 제어 달성 / 언어 및 런타임 종속성과 조건 변수 시그널링(Mesa) 처리 주의 필요

## 핵심 그림
```text
                       [ 외부 스레드 호출 ]
                                │
                                v
               +----------------------------------+
               |     진입 큐 (Entry Queue)        |
               +----------------┬-----------------+
                                │ (상호배제: 오직 1개 스레드만 진입 허용)
                                v
+─────────────────────────────────────────────────────────────────+
|                           모니터 (Monitor)                      |
|                                                                 |
|   +---------------------------------------------------------+   |
|   |  공유 데이터 (Shared Data): 캡슐화되어 외부 접근 불가   |   |
|   +---------------------------------------------------------+   |
|                                                                 |
|   +---------------------------------------------------------+   |
|   |  작업 프로시저 (Operations): 오직 하나의 스레드만 실행  |   |
|   +---------------------------------------------------------+   |
|            │ (조건 불만족: cond.wait)       ▲ (깨어남: cond.signal)
|            v                                │                   |
|   +-----------------------------------------┴---------------+   |
|   |            조건 변수 큐 (Condition Queue)               |   |
|   |   - x.wait(): 락 반납 후 x 조건 큐에 대기               |   |
|   |   - x.signal(): x 조건 큐에서 대기 중인 스레드 호출     |   |
|   +---------------------------------------------------------+   |
+─────────────────────────────────────────────────────────────────+
```

## 핵심 용어
- 조건 변수(Condition Variable): 모니터 내에서 특정 동기화 조건이 만족될 때까지 스레드를 일시 중단(`wait()`)시키거나, 조건이 충족되었음을 알리는(`signal()`) 특수 변수
- Hoare 방식(Signal-and-Wait): signal을 호출한 스레드가 즉시 대기 상태로 물러나고, 깨어난 스레드가 모니터를 즉각 선점하여 실행하는 방식
- Mesa 방식(Signal-and-Continue): signal을 호출한 스레드가 모니터를 계속 유지하며 작업을 끝내고, 깨어난 스레드는 다시 경쟁하여 진입하는 방식(현대 Java의 `synchronized`가 채택)

## 핵심 통찰
- 모니터는 개발자가 락을 획득(`acquire`)하고 반납(`release`)하는 코드를 작성할 필요가 없음 → Java의 `synchronized` 키워드나 C#의 `Monitor` 클래스처럼 런타임이 진입과 퇴출 시 암묵적 상호배제를 강제
- Mesa 방식을 채택한 현대 런타임에서는 대기 큐에서 깨어난 시점에 다른 스레드가 먼저 진입해 조건을 변경할 수 있음 → 따라서 조건 검사는 반드시 `if`가 아닌 `while (condition) { wait(); }` 루프로 재확인해야 함
- 모니터 내부에서 또 다른 외부 모니터를 호출하는 중첩 모니터 호출(Nested Monitor Call)은 내부 락을 쥔 채 외부 락을 대기하는 상태를 유발하여 치명적인 교착상태의 주원인이 됨

## 이웃 토픽과 구분
- 모니터 vs 세마포어: 모니터 = 언어가 지원하는 객체 지향적 고수준 캡슐화(자동 상호배제) / 세마포어 = 정수 변수 기반의 수동 저수준 카운팅(소유권 없음)

## 문제·원인·대책
- 사례: 139회 기출 프로세스 동기화 및 Java 생산자-소비자 큐 구현 시 조건 경쟁 버그
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 버퍼가 비어 있는데 소비자가 데이터를 꺼내려다 NullPointerException 발생 | `if (!empty) wait()` 사용으로 깨어난 후 조건 변경 미감지 (Mesa 방식 특성) | 조건 검사 블록을 `while (!empty) wait()` 루프로 변경 | 스레드가 다시 진입할 때마다 상태 무결성 재검증 |
| 다수 스레드 대기 중 특정 스레드만 깨워 영구 기아 발생 | `notify()` 호출 시 임의의 단일 스레드만 선택되어 신호 누락 | `notifyAll()` 또는 명시적 Condition 변수 분리(`notFull`, `notEmpty`) | 의도한 조건 대기 스레드 전체 갱신 및 기아 차단 |

## 내 의견
- [모니터 기반 저수준 wait/notify 직접 구현 폐기 및 블로킹 큐 채택] 현대 엔터프라이즈 환경에서 개발자가 직접 `wait()`와 `notifyAll()`을 조합해 스레드 안전 큐를 짜는 것은 버그 양산 행위임 → 나라면: 언어 표준 프레임워크가 제공하는 검증된 동시성 컬렉션(예: `ArrayBlockingQueue`, `ConcurrentHashMap`)을 기본 채택하고, 복잡한 상태 머신 제어가 필요할 때만 명시적 `ReentrantLock`과 복수 `Condition` 객체를 사용하여 락과 대기 큐의 책임을 엄격히 분리
