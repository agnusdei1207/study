## 연관 키워드

- 서버리스 컴퓨팅(Serverless Computing), FaaS(Function as a Service), BaaS(Backend as a Service)
- 콜드 스타트(Cold Start), Scale-to-Zero, 상태 비저장(Stateless), 사용량 기반 과금
- 이벤트 기반 아키텍처(EDA, Event-Driven Architecture), 벤더 종속(Vendor Lock-in), 관측성(Observability), 최소 권한 원칙(PoLP)

## Ⅰ. 서버리스 컴퓨팅의 개요

- 핵심 요약 : 이벤트가 함수를 호출하고 실행된 만큼만 과금되는, 서버 운영 책임이 제공업체에 있는 실행 모델.
- 개념 : **서버리스 컴퓨팅** (Serverless Computing)은 서버의 프로비저닝, 확장, 런타임 패치를 제공업체가 담당하고, 개발자는 이벤트에 반응하는 **FaaS** (Function as a Service) 함수와 관리형 백엔드인 **BaaS** (Backend as a Service)를 조합해 애플리케이션을 구성하는 실행 모델. 서버의 부재가 아니라 서버 관리 책임의 이전을 의미함.
- 배경 및 필요성 : 상시 가동 서버는 부하가 낮은 시간에도 유휴 비용과 용량 계획 부담을 수반하므로, 간헐적·이벤트성 워크로드의 낭비 제거 요구가 커짐.
- 주요 목적 : 유휴 실행 환경을 완전히 회수하는 **Scale-to-Zero**, 사용량 기반 과금, 함수 단위의 신속한 배포로 비용 효율과 개발 생산성을 동시에 확보하는 것.

## Ⅱ. 서버리스 컴퓨팅의 특징 및 장점

- 핵심 요약 : 이벤트 기반 실행, 상태 비저장 구조, 사용량 과금이 유휴 비용 제거와 탄력적 확장이라는 장점으로 연결되는 구조.

1. 이벤트 기반 실행 : HTTP(Hypertext Transfer Protocol) 요청, 큐 메시지, 스토리지 변경 같은 이벤트가 함수 호출의 트리거 → 기능 단위 배포로 변경 주기 단축.
2. 상태 비저장 실행 : 함수 인스턴스가 호출 간 내부 상태를 유지하지 않고 상태 저장을 외부 서비스에 위임하는 **상태 비저장** (Stateless) 구조 → 인스턴스의 자유로운 생성·회수로 수평 확장 용이.
3. 사용량 기반 과금 : 실행 시간과 할당 메모리를 과금 단위로 삼음 → 간헐적 워크로드의 유휴 비용 제거.
4. 운영 책임 이관 : 런타임 격리와 인프라 패치를 제공업체가 담당 → 용량 계획 부담의 해소와 비즈니스 로직 집중.

## Ⅲ. 서버리스 컴퓨팅의 구조 (흐름)

- 핵심 요약 : 이벤트 소스, 라우팅, 함수 실행, 외부 상태 계층의 분리 구조와 실행 인스턴스의 생명주기가 핵심.

1. 이벤트 소스와 라우팅 : API 게이트웨이와 이벤트 라우터가 다양한 이벤트를 표준 형식으로 변환해 함수에 전달.
2. 함수 실행 환경 : 요청 유입 시 실행 환경을 생성하거나 재사용하고, 동시 실행 수를 플랫폼이 제어.
3. BaaS 계층 : 데이터베이스, 객체 스토리지, 인증 같은 관리형 서비스가 상태 저장과 공통 기능을 담당.
4. 실행 인스턴스 생명주기 : 유휴 후 첫 호출에서 런타임을 초기화하는 **콜드 스타트** (Cold Start)가 발생하고, 유휴 시간이 길어지면 인스턴스가 회수되는 구조.

```text
[ 이벤트 처리 흐름 ]

이벤트 소스 (HTTP · 큐 · 스토리지 변경)
   ↓
게이트웨이 · 이벤트 라우터
   ↓
FaaS 런타임 (필요 시 인스턴스 생성)
   ↓
함수 실행 (상태 비저장 로직)
   ↓
BaaS 계층 (상태 저장)
```

```text
[ 인스턴스 생명주기 ]

유휴 상태 (실행 인스턴스 없음)
   ↓ 이벤트 유입
콜드 스타트 (런타임 초기화)
   ↓
웜 상태 (인스턴스 재사용)
   ↓ 유휴 시간 경과
인스턴스 회수 (Scale-to-Zero)
```

## Ⅳ. 서버리스 컴퓨팅과 상시 실행 모델의 비교

- 핵심 요약 : 운영 자동화와 유휴 비용 절감을 얻는 대신 지연 변동성과 실행 제약을 감수하는 선택이며, 부하 패턴이 기준이 됨.

| 비교 축 | 상시 실행 (가상머신 · 컨테이너) | 서버리스 (FaaS) |
| --- | --- | --- |
| 배포 단위 | 애플리케이션 · 컨테이너 이미지 | 단일 함수 코드 |
| 확장 방식 | 사전 정의한 인스턴스 수의 조정 | 요청에 따른 자동 확장 · 회수 |
| 과금 기준 | 프로비저닝한 자원의 사용 시간 | 실행 시간과 할당 메모리 |
| 응답 지연 | 웜 상태 유지로 일정 수준 유지 | 첫 요청에서 초기화 지연 가능 |
| 상태 관리 | 인스턴스 내 상태 유지 가능 | 외부 저장소 위임이 전제 |
| 실행 제한 | 실행 시간의 사실상 무제한 | 실행 시간과 자원의 상한 존재 |
| 적합 워크로드 | 상시 트래픽, 장기 실행 처리 | 간헐적 · 이벤트성 트래픽 |

- 선택 기준 : 부하의 간헐성이 크고 지연 요건이 완만하면 서버리스를, 상시 트래픽이 유지되거나 장기 실행·저지연이 요구되면 컨테이너 기반 상시 실행을 우선 검토하는 방식으로 판단.

## Ⅴ. 서버리스 컴퓨팅의 한계와 방안

- 핵심 요약 : 콜드 스타트, 벤더 종속, 관측성의 제약을 실행 환경 최적화, 계약 분리, 분산 추적으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 콜드 스타트 지연 | 유휴 후 첫 요청에서 초기화 비용 발생 → 응답 시간 불안정 | 경량 런타임 채택, 의존성 최소화, 예약 동시성 설정 | 최초 요청 응답 시간 |
| **벤더 종속** (Vendor Lock-in) | 플랫폼별 이벤트 규격과 배포 도구의 차이 → 이전 비용 증가 | 함수 코드와 플랫폼 바인딩의 분리, 이벤트 형식의 표준 준수 | 이식 가능한 함수 비율 |
| **관측성** (Observability) 확보의 어려움 | 인스턴스가 단명하고 내부 접근이 차단 → 장애 추적이 어려움 | 분산 추적과 구조화 로그의 중앙 수집 체계 구축 | 장애 원인 식별 소요 시간 |

## Ⅵ. 서버리스 컴퓨팅에 대한 기술사적 제언

- 핵심 요약 : 함수별 권한, 비동기 이벤트 설계, 실행 모델 전환 기준을 조직 표준으로 정착시키는 방향.

- 개발 조직은 함수마다 전용 권한을 부여하는 **최소 권한 원칙** (PoLP, Principle of Least Privilege)을 배포 파이프라인의 검증 항목으로 내재화하는 방안을 권고.
- 아키텍처 조직은 함수 간 직접 호출 연쇄를 지양하고 이벤트 중개 계층을 경유하는 **이벤트 기반 아키텍처** (EDA, Event-Driven Architecture)를 표준 설계로 지정.
- 비용 관리 조직은 호출 빈도와 지속 부하를 실측해 서버리스와 상시 실행 중 유리한 쪽으로 전환하는 판단 기준을 문서화하여 운영.

## Ⅶ. 결론

- 핵심 요약 : 서버리스 컴퓨팅은 이벤트성 워크로드의 유휴 비용과 운영 부담을 제거하는 실행 모델.
- 지연 요건, 총비용, 플랫폼 종속성의 검증을 전제로 할 때 그 가치가 실현됨.
