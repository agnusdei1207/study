## 연관 키워드

- 서버리스 컴퓨팅(Serverless Computing), FaaS(Function as a Service), BaaS(Backend as a Service)
- 콜드 스타트(Cold Start), Scale-to-Zero, 사용량 기반 과금, 벤더 종속(Vendor Lock-in)
- 이벤트 기반 아키텍처(EDA, Event-Driven Architecture), 최소 권한 원칙(PoLP), 관측성(Observability)

## Ⅰ. 서버리스 컴퓨팅의 개요

- 핵심 요약 : 인프라 운영을 제공업체에 맡기고 이벤트에 반응한 실행 시간만큼 과금받는 클라우드 실행 모델.
- 개념 : 서버 프로비저닝, 운영체제(OS, Operating System) 패치, 오토스케일링 같은 하부 인프라 운영을 클라우드 제공업체가 담당하고, 사용자는 이벤트에 반응하는 **FaaS** (Function as a Service)와 관리형 백엔드인 **BaaS** (Backend as a Service)만 구성하여 실행 시간에 따라 과금받는 모델 (**서버리스 컴퓨팅**, Serverless Computing).
- 배경 및 필요성 : **서비스형 인프라** (IaaS, Infrastructure as a Service)나 컨테이너(CaaS, Container as a Service)를 상시 가동하면 부하가 낮은 시간에도 유휴 비용과 클러스터 운영 부담이 발생하므로, 마이크로서비스 아키텍처(MSA, Microservice Architecture) 환경에서 운영 부담을 줄이고 비즈니스 로직에 집중하려는 요구가 등장함.
- 주요 목적 : 유휴 시 실행 인스턴스를 0으로 줄이는 **Scale-to-Zero**로 총소유비용(TCO, Total Cost of Ownership)을 낮추고, 수요에 따라 자동으로 확장하며, 개발 주기를 단축하는 것.

## Ⅱ. 서버리스 컴퓨팅의 특징 및 장점

- 핵심 요약 : 이벤트 기반 실행, 자동 확장, 사용량 기반 과금이 결합되어 운영 부담을 낮추고 가변 부하에 빠르게 대응하는 방식.

1. 이벤트 기반 실행 : HTTP 요청, 큐 메시지, 스토리지 변경 같은 이벤트가 함수를 호출 → 이벤트 처리 코드를 독립적으로 배포하여 기능 단위의 변경 주기 단축.
2. 자동 확장 : 플랫폼이 동시 실행 인스턴스를 조절 → 사용자가 서버 용량을 직접 산정하지 않아도 급격한 트래픽 증가에 대응.
3. 사용량 기반 과금 : 실행 시간과 할당 자원에 따라 비용 산정 → 간헐적 부하에서 유휴 자원 비용 절감. 다만 최소 인스턴스 설정과 연계 서비스 비용은 별도로 확인해야 함.
4. 관리형 운영 : 인프라 패치와 런타임 격리를 제공업체가 담당 → 배포 주기 단축과 운영 인력 부담 축소. 애플리케이션 보안 설정과 접근 권한의 책임은 사용자에게 남음.

## Ⅲ. 서버리스 컴퓨팅의 구조 및 동작 원리

- 핵심 요약 : 이벤트 소스, 라우팅, 함수 실행, 외부 상태 저장의 계층이 분리되어 요청을 처리하는 흐름.
- **이벤트 트리거링** : HTTP(Hypertext Transfer Protocol) 요청, 메시지 큐 적재, 객체 스토리지 변경 등 다양한 이벤트를 표준화된 이벤트 형식으로 받아 함수를 호출.
- **상태 비저장 실행** (Stateless Execution) : 함수 인스턴스는 영속 상태를 내부에 두지 않고, 모든 상태 데이터를 외부 데이터베이스(DB, Database)나 캐시에 위임.

```text
[ 서버리스 이벤트 처리 흐름 ]

이벤트 소스 (HTTP, 큐, 스토리지 변경)
   ↓
게이트웨이 / 이벤트 라우터
   ↓
함수 실행 환경 (필요 시 생성)
   ↓
함수 실행 (상태 비저장 로직)
   ↓
BaaS 계층 (DB, 캐시, 객체 스토리지)
```

```text
[ 인스턴스 생명주기 ]

유휴 상태
   ↓ 이벤트 유입
콜드 스타트 (런타임 초기화)
   ↓
웜 상태 (실행 환경 재사용)
   ↓ 유휴 시간 경과
자원 회수 (Scale-to-Zero)
```

## Ⅳ. 서버리스 컴퓨팅과 다른 컴퓨팅 모델의 비교

- 핵심 요약 : 인프라 제어권을 줄이는 대신 운영 자동화를 얻는 선택이며, 부하 패턴과 지연 요구에 따라 적합성이 갈림.

| 비교 축 | IaaS (가상머신) | CaaS (Container as a Service) / PaaS (Platform as a Service) | FaaS (서버리스) |
| --- | --- | --- | --- |
| 배포 단위 | 가상머신 이미지 | 컨테이너 이미지 | 단일 함수 단위 코드 |
| 확장 방식 | 가상머신 오토스케일링 | 파드 단위 수평 확장 | 플랫폼 관리형 동시 실행 확장, 콜드 스타트 발생 가능 |
| 과금 기준 | 프로비저닝한 자원의 사용 시간 | 클러스터에 예약한 자원 | 실제 실행 시간과 메모리 사용량 |
| 운영 책임 | OS, 미들웨어, 런타임, 애플리케이션 | 컨테이너 오케스트레이션, 노드 관리 | 비즈니스 로직과 접근 권한 정책 |
| 상태 관리 | 로컬 디스크와 메모리 상태 유지 가능 | 볼륨 마운트로 상태 유지 가능 | 호출 간 상태 보장이 제한적, 외부 저장소 연계 필요 |

- 서버리스는 운영 자동화와 비용 효율에서 강점이 있으나, 장기 실행 배치나 저지연이 지속적으로 요구되는 워크로드에는 부적합하므로 하이브리드 배포 전략이 필요함.

## Ⅴ. 서버리스 컴퓨팅의 한계와 방안

- 핵심 요약 : 콜드 스타트, 제공업체 종속, 가시성의 제약을 실행 환경 최적화, 표준 이벤트 규격, 분산 추적으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 콜드 스타트 지연 | 유휴 후 첫 요청에서 런타임 부팅과 의존성 적재가 일어나 응답 지연 발생 | 사전 워밍 설정, 경량 런타임 채택, 의존성 패키지 축소 | 콜드 스타트 발생률, 최초 요청 응답 시간 |
| 제공업체 종속 (Vendor Lock-in) | 플랫폼별 이벤트 규격과 바인딩 API(Application Programming Interface)가 달라 타 플랫폼 이전이 어려움 | 오픈소스 서버리스 프레임워크 도입, CloudEvents 표준 준수 | 이식 가능한 함수 비율 |
| 분산 환경의 관측성(Observability) 한계 | 로컬 디스크와 SSH(Secure Shell) 접근이 막히고 인스턴스가 파편화되어 장애 원인 추적이 어려움 | OpenTelemetry 기반 분산 추적, 로그의 중앙 수집 파이프라인 구축 | 장애 원인 식별 소요 시간 |

## Ⅵ. 서버리스 컴퓨팅의 적용 제언

- 핵심 요약 : 이벤트 기반 비동기 구조와 비용 기준, 함수별 최소 권한을 함께 세우는 방향.

- 함수 간 동기 호출 연쇄를 설계 규칙에서 제외하고, 이벤트 브로커를 통한 비동기 연결을 기본값으로 정하는 것이 바람직함. 비동기 **이벤트 기반 아키텍처** (EDA, Event-Driven Architecture)의 효과는 이 분리에서 나옴.
- 워크로드별로 호출 빈도와 지속 부하를 측정해 서버리스와 상시 컨테이너 운영 중 어느 쪽이 비용상 유리한지 판단하는 전환 기준을 마련하는 것이 필요함.
- 함수마다 전용 권한 역할을 부여하는 **최소 권한 원칙** (PoLP, Principle of Least Privilege)을 적용하고, 비밀 값 관리와 정적 분석을 배포 파이프라인의 필수 단계로 포함시키는 것이 바람직함.

## Ⅶ. 결론

- 핵심 요약 : 서버리스는 변동성이 큰 이벤트 처리에 유리한 실행 모델이며, 지연 시간, 총비용, 플랫폼 종속성을 함께 검증해야 함.
- 지속적인 고부하나 엄격한 응답 시간 보장이 필요한 서비스는 사전 워밍 또는 컨테이너 등 대안과 비교한 뒤 배치하는 것이 적절함.
