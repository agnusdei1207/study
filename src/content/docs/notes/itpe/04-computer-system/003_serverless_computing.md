## 답안 골격
```text
[서버리스 컴퓨팅] ◀━━ 머리: Ⅶ 내 의견 (콜드스타트 완화 및 런타임 제로트러스트 권한 격리 체계 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 유휴 서버 유지 비용 및 인프라 관리 부담 → 이벤트 기반 무서버 실행 및 종량제
 ┣━ Ⅱ 특징 ───── NoOps 지향 · 밀리초 종량 과금 · 0부터 무한대 자동 스케일 · 무상태(Stateless)
 ┣━ Ⅲ 구조 ───── FaaS(함수 실행 엔진) + BaaS(관리형 서비스) + 이벤트 소스 + API 게이트웨이
 ┣━ Ⅳ 흐름 ───── ① 이벤트 발생(HTTP/큐) → ② 컨테이너 콜드/웜 기동 → ③ 함수 실행 → ④ 자원 반납
 ┣━ Ⅴ 비교 ───── FaaS vs BaaS vs IaaS / 가상머신 vs 컨테이너 vs 서버리스
 ┗━ Ⅵ 실무 ───── 콜드 스타트 지연 / 함수 실행 시간 제약(15분) / 분산 추적(디버깅) 및 보안
```
- 필수 키워드: FaaS · BaaS · 이벤트 드리븐 · 콜드 스타트(Cold Start) · 밀리초 종량 과금 · 무상태
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ FaaS/BaaS 결합 도식 → Ⅵ 콜드스타트 대책 / 25점 = Ⅰ~Ⅶ 전개, Ⅳ 수명주기 흐름과 Ⅵ 보안 위협(권한 과다, 이벤트 주입) 집중
- 기출: 140회 2교시 `가. 개념/특징 나. 유형 및 장단점 다. 보안위협 및 대응` → Ⅰ~Ⅵ 전체 정합

## 한 줄 본질
- 24시간 상시 가동되는 가상 서버의 유휴 비용과 OS/인프라 패치 오버헤드 → 이벤트 발생 시에만 마이크로 컨테이너를 띄워 함수를 실행하고 밀리초 단위로 과금 → 인프라 관리 제로화 및 비용 최적화 / 첫 호출 시 콜드 스타트 지연 및 장기 실행 작업 제한

## 핵심 그림
```text
[ 이벤트 소스 ]              [ 서버리스 실행 환경 ]             [ 백엔드 연계 ]
- HTTP 요청 (API Gateway) ──> [ 이벤트 라우터 ] 
- 메시지 큐 (SQS/Kafka)        │ (스케줄링)
- 객체 업로드 (S3 Storage) ───> v
- DB CDC (DynamoDB Stream)    +-----------------------+ 
                              |  FaaS 인스턴스        | ──> [ BaaS (DB/인증) ]
                              |  - 컨테이너 초기화    |
                              |  - 핸들러 코드 실행   | ──> [ 분산 로깅/추적 ]
                              |  - 유휴 시 회수(0)    |     (X-Ray/OTel)
                              +-----------------------+
```

## 핵심 용어
- 콜드 스타트(Cold Start): 유휴 상태에서 새 요청이 들어올 때 컨테이너 이미지 다운로드, 런타임 초기화, 코드 로딩으로 수백 ms 지연이 발생하는 현상
- FaaS(Function as a Service): 개발자가 작성한 개별 함수 단위를 독립적으로 실행·확장·관리해 주는 컴퓨팅 서비스

## 핵심 통찰
- 서버리스는 물리적 서버가 없는 것이 아니라, 서버 라이프사이클 관리와 확장 실패 책임을 클라우드 제공업체로 완전히 외주화한 아키텍처임
- 트래픽 편차가 극심하고 간헐적인 배치·이벤트 처리에 비용 효율이 극대화되나, 24시간 일정한 고부하 트래픽에서는 상시 가동 인스턴스(EKS/ECS) 대비 누적 비용이 2~3배 이상 비싸질 수 있음
- 서버리스 보안의 핵심은 경계 방어가 아닌 '함수 단위 최소 권한(Least Privilege)'임 → 수백 개로 쪼개진 함수가 광범위한 IAM 권한을 가지면 단일 함수 탈취로 인프라 전체 장악 위험

## 이웃 토픽과 구분
- 서버리스 vs 컨테이너(CaaS): CaaS = 컨테이너 기동 및 스케일링 임계치를 직접 튜닝하고 클러스터를 유지 / 서버리스 = 요청이 0이면 리소스가 0이며 클러스터 개념 자체가 사용자에게 은폐됨

## 내 의견
- [서버리스 아키텍처의 관측가능성(Observability) 위기] 함수가 수백 개로 파편화되면서 장애 발생 시 단일 트랜잭션의 병목 지점을 추적하기가 기존 모놀리스 대비 극도로 어려움 → 나라면: OpenTelemetry 기반 W3C Trace Context를 이벤트 헤더에 주입하여 API Gateway-FaaS-BaaS를 관통하는 분산 트레이싱 파이프라인을 필수 연동하고, 함수 콜드스타트 비율 및 에러율을 SLO 지표로 상시 모니터링
