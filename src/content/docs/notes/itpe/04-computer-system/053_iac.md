## 연관 키워드

- 코드형 인프라, IaC, 선언적 접근법, 명령적 접근법, 멱등성, 상태 파일, 상태 관리
- 드리프트, Blast Radius, Policy as Code, GitOps, 상태 잠금, Terraform, Ansible, CDK, Pulumi

## Ⅰ. 코드형 인프라(IaC)의 개요

- 핵심 요약 : 인프라를 기계 판독형 코드로 정의해 자동화, 재현성, 변경 이력 관리를 확보하는 클라우드 엔지니어링 방식.
- 개념 : 서버, 네트워크, 스토리지, 데이터베이스 같은 인프라 자원을 수동 콘솔 조작 대신 버전 관리가 가능한 **기계 판독형 코드**로 정의하고, 자동화 도구로 배포와 관리를 수행하는 **코드형 인프라** (IaC, Infrastructure as Code) 방법론.
- 배경 및 필요성 : 수작업 구축은 설정 오류와 긴 프로비저닝 기간을 낳고, 개발 환경과 운영 환경의 설정이 어긋나는 **구성 드리프트** (Configuration Drift, 코드와 실제 인프라가 달라지는 현상)를 방치하게 되어 장애 조사 비용이 커지므로, 인프라를 코드로 관리하는 방식이 필요해짐.
- 핵심 목적 : 프로비저닝의 자동화와 신속화, 멱등성 기반 환경 재현, **GitOps** (Git 저장소를 인프라 변경의 기준으로 삼는 운영 방식)에 따른 변경 감사와 거버넌스 확립.

## Ⅱ. 코드형 인프라(IaC)의 특징 및 장점

- 핵심 요약 : 선언과 절차라는 두 작성 방식, 멱등성, 상태 관리가 자동화와 재현성, 거버넌스로 이어지는 구조.

1. **선언적 접근법** (Declarative) : 최종 목표 상태만 기술하면 도구가 현재 상태와의 차이를 계산해 수렴 → 작성자의 절차 부담 감소와 변경 계산의 자동화 (예: Terraform, CloudFormation).
2. **명령적 접근법** (Imperative) : 원하는 상태에 도달하는 단계별 명령을 스크립트로 기술 → 세부 절차에 대한 통제력 확보와 OS 내부 설정에 적합 (예: Ansible, 셸 스크립트).
3. **멱등성** (Idempotency) : 같은 코드를 한 번 실행하든 여러 번 실행하든 최종 인프라 상태가 동일하게 유지 → 재실행 안전성과 환경 재현성 확보.
4. **상태 관리** (State Management) : 도구가 프로비저닝한 리소스와 코드의 대응 정보를 보관 → 변경이 미칠 영향 범위를 정확히 추적.

## Ⅲ. 코드형 인프라(IaC)의 구조 및 동작 메커니즘

- 핵심 요약 : Git 커밋에서 시작해 계획 산출, 정책 검증, 적용, 상태 갱신으로 이어지는 수렴 파이프라인.
- **상태 파일** (State File) : 실제 리소스와의 매핑 정보를 담는 파일로, 도구는 이를 기준으로 코드가 선언한 상태와 실제 상태의 차이를 계산함.
- **Policy as Code** (코드로 작성한 보안·규정 정책을 배포 전에 자동으로 검증하는 방식) : 계획 단계와 적용 단계 사이에 위치하여 위반 설정이 실제 인프라에 반영되는 것을 막음.

```text
[ 선언적 IaC 실행 파이프라인 ]

Git 저장소 (코드 커밋)
   ↓ CI/CD 웹훅 트리거
plan (코드와 상태 파일 비교)
   ↓
정책 검증 (Policy as Code)
   ↓
apply (클라우드 API 호출)
   ↓
상태 파일 갱신 (잠금 적용)
```

```text
[ 드리프트 발생과 감지 ]

콘솔에서 수동 변경
   ↓
코드와 실제 인프라 불일치
   ↓
정기 plan 실행으로 차이 탐지
   ↓
코드 반영 또는 실제 인프라 원복
```

## Ⅳ. 코드형 인프라(IaC)의 비교

- 핵심 요약 : 선언적 도구는 상태 중심의 인프라 프로비저닝에, 명령적 도구는 OS 내부 구성에, 모던 코드형은 복잡한 조건을 가진 추상화에 강점이 있음.

| 비교 축 | 선언적 (Terraform 등) | 명령적 (Ansible 등) | 모던 코드형 (AWS CDK(Cloud Development Kit), Pulumi) |
| --- | --- | --- | --- |
| 작성 언어 | HCL(HashiCorp Configuration Language), YAML(YAML Ain't Markup Language) | YAML, 셸 스크립트 | 범용 프로그래밍 언어 (TypeScript, Python 등) |
| 상태 관리 | 상태 파일을 명시적으로 유지 | 별도 상태 파일 없이 대상 호스트를 조회 | 백엔드에 상태 유지 |
| 주 적용 영역 | 클라우드 기반 인프라 (네트워크, 데이터베이스, 클러스터) | OS 내부 설정, 패키지 설치 | 조건과 반복이 많은 인프라 추상화 |
| 드리프트 감지 | plan 단계에서 감지 | 플레이북 재실행 시 감지 | 배포 엔진의 비교 결과로 감지 |
| 재사용 단위 | 모듈(Module) | 역할(Role)과 플레이북 | 라이브러리 패키지 |

- 선택 기준 : 인프라 프로비저닝과 VM 내부 구성을 분리하여, 선언적 도구로 자원을 만들고 명령적 도구로 소프트웨어를 구성하는 분업 결합이 흔히 쓰임.

## Ⅴ. 코드형 인프라(IaC)의 한계와 방안

- 핵심 요약 : 상태 파일 충돌과 노출, 드리프트, 영향 범위 확대를 잠금, 비밀 관리, 감지 주기, 상태 분리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 상태 파일 충돌과 민감 정보 노출 | 동시 배포로 상태 손상, 평문 상태 파일에 비밀번호와 키 노출 | 원격 백엔드의 암호화 저장, **상태 잠금** (State Locking, 동시 변경 차단), HashiCorp Vault 연동으로 동적 비밀 주입 | 잠금 충돌 건수, 평문 비밀 검출 건수 |
| 드리프트 | 장애 대응 중 콘솔 수동 변경으로 코드와 운영 상태 불일치 | 주기적 plan 기반 감지 파이프라인 운영, 콘솔 쓰기 권한을 IAM 정책으로 제한 | 드리프트 탐지 건수, 콘솔 변경 건수 |
| **Blast Radius** (변경 한 번이 영향을 주는 범위) | 모든 리소스를 한 상태에 두어 실행 지연과 의도치 않은 삭제 위험 발생 | 네트워크·데이터·컴퓨팅 계층 분리, 상태 파일 격리, 중요 리소스에 삭제 방지 설정 | 상태당 리소스 수, 삭제 계획 건수 |

## Ⅵ. 코드형 인프라(IaC)의 기술사적 제언

- 핵심 요약 : 정책 검증의 자동화, 승인 기반 배포 거버넌스, 범용 언어 기반 도구 역량을 묶어 인프라 변경을 통제 가능한 개발 흐름으로 편입.

1. 정책 코드 게이트웨이 : OPA(Open Policy Agent)로 보안 기준을 코드화하고, 배포 계획 단계에서 위반 설정을 자동으로 차단하도록 전사 파이프라인에 연결하는 것이 바람직함.
2. GitOps 배포 거버넌스 : 풀 리퀘스트에 plan 결과를 남기고 승인을 거친 뒤에만 apply가 실행되도록 Atlantis 같은 도구를 운영 기준으로 두는 방식이 효과적임.
3. 모던 코드형 도구 역량 : AWS CDK나 Pulumi처럼 범용 언어로 인프라를 표현하는 도구의 타입 안정성과 추상화 역량을 내재화하여 복잡한 구성을 관리하는 방향이 유효함.

## Ⅶ. 결론

- 핵심 요약 : 코드형 인프라는 선언과 자동화로 재현성과 거버넌스를 확보하는 인프라 운영 방식이며, 상태와 변경 범위의 관리가 전제 조건임.
- 시사점 : 코드화 자체보다 상태 파일 보호, 드리프트 감지, 변경 승인 체계가 함께 갖춰질 때 자동화의 효과가 지속됨.
