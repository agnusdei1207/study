```text

 ┃
 ┣━ Ⅰ 개요 ───── 수동 GUI 인프라 설정의 설정 표류(Drift) 및 휴먼 에러 → 코드로 인프라 정의 및 자동 프로비저닝
 ┣━ Ⅱ 특징 ───── 버전 관리 가능 · 선언적 명세 · 멱등성(Idempotency) 보장 · 재사용 및 자동화
 ┣━ Ⅲ 구조 ───── 형상 저장소(Git) + 선언적 코드(Terraform/Ansible) + 상태 파일(State) + 공급자 API
 ┣━ Ⅳ 흐름 ───── ① 코드 작성(HCL/YAML) → ② 변경사항 계획(`plan`) → ③ 실제 인프라 반영(`apply`) → ④ 상태 저장
 ┣━ Ⅴ 비교 ───── 선언적(Declarative: Terraform) vs 절차적(Imperative: Ansible/Shell)

```

## 한 줄 본질
- 웹 콘솔이나 CLI로 수동 구성하던 서버·네트워크 인프라는 이력 추적이 불가능하고 환경 간 설정 차이를 유발함 → 인프라의 최종 상태를 선언적 코드로 작성하여 형상관리하고 자동 배포 → 일관된 인프라 복제 및 멱등성 확보 / 실제 인프라와 코드 간의 형상 불일치(Drift) 및 상태 파일 유출 위험 수반

## 핵심 용어
- 멱등성(Idempotency): 연산을 여러 번 적용하더라도 결과가 달라지지 않는 성질로, IaC 코드를 10번 실행해도 최초 의도한 최종 상태가 동일하게 유지됨
- 구성 표류(Configuration Drift): 운영자가 콘솔에서 긴급하게 수동 변경하거나 보안 패치를 적용하여 코드베이스와 실제 클라우드 인프라 상태가 달라지는 현상
- 상태 파일(tfstate): 테라폼 등의 도구가 관리 대상 인프라의 실제 리소스 매핑 정보를 기록하는 메타데이터 파일

## 핵심 통찰
- IaC의 최대 가치는 '배포 속도'가 아니라 '감사 추적성(Auditability)'임 → 누가 언제 어떤 보안 그룹의 0.0.0.0/0 포트를 열었는지 Git 커밋과 PR 리뷰 이력으로 투명하게 역추적할 수 있음
- 상태 파일(State)은 양날의 검임 → 테라폼의 `terraform.tfstate`에는 데이터베이스 암호, API 키 등 민감 정보가 평문으로 들어갈 수 있으므로, 원격 백엔드(S3+KMS) 암호화와 엄격한 IAM 권한 분리가 필수적임
- 불변 인프라(Immutable Infrastructure)와 결합할 때 진가를 발휘함 → 운영 중인 인프라를 수정 패치하지 않고 코드를 고쳐 새 인프라를 프로비저닝한 뒤 트래픽을 전환하는 Blue-Green 배포의 기반이 됨

## 이웃 토픽과 구분
- 프로비저닝 도구 vs 구성 관리 도구: 프로비저닝(Terraform, CloudFormation) = 서버, 네트워크, 스토리지 등 뼈대 자원 생성에 특화(선언적) / 구성 관리(Ansible, Puppet) = 생성된 OS 내부에 패키지 설치 및 설정 파일 주입에 특화(절차적/혼합)

| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 배포 파이프라인 실행 시 정상 운영 중인 프로덕션 DB가 파괴 및 재생성 | 수동으로 콘솔에서 설정을 변경하여 코드와 실제 리소스 간 Drift 발생 | `prevent_destroy = true` 수명주기 락 및 정기 Drift 감지 배치 실행 | 위험한 리소스 삭제 차단 및 설정 불일치 사전 알림 |
| 팀원 동시 실행으로 상태 파일 경합 및 손상 발생 | 로컬 머신에서 각자 테라폼 명령어를 실행하여 상태 파일 덮어쓰기 | 중앙 원격 백엔드(S3) 및 분산 락(DynamoDB Table) 적용 | 동시 실행 차단 및 상태 무결성 영구 유지 |
