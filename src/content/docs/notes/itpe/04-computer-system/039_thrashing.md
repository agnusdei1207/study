```text
 ┃
 ┣━ Ⅰ 개요 ───── 과도한 다중 프로그래밍으로 인한 페이지 부재 빈발 → CPU 연산 대신 I/O만 수행하는 성능 급락
 ┣━ Ⅱ 특징 ───── CPU 이용률 급락 · 디스크 I/O 100% 포화 · 시스템 멈춤(Hang) · 악순환 루프
 ┣━ Ⅲ 구조 ───── 다중 프로그래밍 정도(MPD) vs CPU 이용률 곡선 + 워킹셋(Working Set) + 페이지 부재 빈도(PFF)
 ┣━ Ⅳ 흐름 ───── ① MPD 과다 증가 → ② 프로세스별 가용 프레임 부족 → ③ 페이지 부재 폭증 → ④ CPU 유휴 및 스케줄러 착각 → ⑤ 스래싱 심화
 ┣━ Ⅴ 비교 ───── 워킹셋(Working Set) 모델 vs 페이지 부재 빈도(PFF) 방식
 ┗━ Ⅵ 실무 ───── MPD 조절(스왑 아웃) / 물리 메모리 증설 / zRAM(인메모리 압축 스왑) 도입
```

- 기출: 126회 `가상 메모리 환경에서 발생하는 스래싱(Thrashing)의 원인, 현상 및 해결방안(워킹셋, PFF)`

## 한 줄 본질
- 시스템에 프로세스를 너무 많이 띄워 각 프로세스가 최소한으로 필요로 하는 페이지 프레임조차 확보하지 못할 때 발생하는 병목 → CPU가 실제 프로그램 명령어를 실행하는 시간보다 페이지를 디스크에서 읽고 쓰는 I/O 교체 작업에 대부분의 시간을 낭비하여 시스템이 마비되는 현상 → 워킹셋(Working Set) 크기 합산 제어 및 PFF 기반 프레임 동적 재할당으로 해결 / 메모리 제어 오버헤드

## 핵심 그림
```text
[ 스래싱(Thrashing) 발생 곡선 및 악순환 메커니즘 ]

  CPU 이용률 (CPU Utilization)
      ^
      │            임계점 (Threshold)
      │                 ▲
      │               /   \  <── 급격한 성능 붕괴 (스래싱 구간!)
      │              /     \
      │             /       \     * 악순환 사이클:
      │            /         \      페이지 부재 증가 ──> 디스크 I/O 대기 (CPU 유휴)
      │           /           \     ──> OS가 CPU 놀고 있다고 착각 ──> MPD 추가 증가!
      │          /             \    ──> 메모리 더 부족 ──> 시스템 완전 멈춤
      +─────────┴───────────────┴───> 다중 프로그래밍 정도 (MPD / 프로세스 수)

[ 해결 모델 1: 워킹셋 (Working Set) ]
  - 최근 Δ 시간 동안 참조된 페이지 집합(WS)을 파악
  - 전체 프로세스의 워킹셋 크기 합 > 가용 프레임 수 이면, 특정 프로세스를 디스크로 스왑 아웃!

[ 해결 모델 2: 페이지 부재 빈도 (PFF: Page Fault Frequency) ]
  - PFF가 상한선(Upper Bound) 초과 ──> 프레임 추가 할당
  - PFF가 하한선(Lower Bound) 미달 ──> 잉여 프레임 회수
```

## 핵심 용어
- 다중 프로그래밍 정도(MPD: Multiprogramming Degree): 주기억장치(RAM)에 동시에 적재되어 실행 중인 프로세스의 총 개수
- 워킹셋(Working Set): 프로그램의 시간적·공간적 지역성(Locality)에 기반하여, 특정 윈도우 시간($\Delta$) 동안 프로세스가 자주 집중적으로 참조한 페이지들의 집합
- 페이지 부재 빈도(PFF: Page Fault Frequency): 프로세스의 페이지 부재 발생 비율을 측정하여 상한선(Upper)과 하한선(Lower)을 두고 프레임 할당량을 적응적으로 증감시키는 제어 기법

## 핵심 통찰
- 스래싱의 가장 역설적인 원인은 'OS의 잘못된 판단'임 → 페이지 부재로 모든 프로세스가 디스크 I/O를 기다리며 Blocked 상태가 되면 CPU 이용률이 0%로 떨어지는데, 단순한 OS는 "CPU가 노니까 프로세스를 더 실행해야지"라며 새로운 프로세스를 메모리에 더 집어넣어 파멸적 붕괴를 가속화함
- 따라서 해결의 핵심은 '프로세스 수를 줄이는 것(MPD 하향 조정)'임 → 일부 프로세스를 희생시켜 통째로 디스크로 쫓아내고(Swap-out), 남은 프로세스들에게 충분한 프레임을 몰아주어 워킹셋을 온전히 보장해야 함
- 현대 시스템에서는 느린 기계식 디스크로 스왑하는 대신, RAM의 일부를 압축 메모리로 쓰는 zRAM(Android/Linux 표준)을 적용하여 I/O 지연 자체를 수십만 배 단축

## 이웃 토픽과 구분
- 워킹셋 모델 vs PFF 모델: 워킹셋 = 참조 이력(과거)을 모니터링하여 필요한 페이지 집합을 사전 예측 / PFF = 실제 발생하는 페이지 부재율(결과)을 실시간 피드백 루프로 측정하여 프레임 수를 동적 가감

| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 메모리 점유율 98%에서 CPU 이용률 5% 미만으로 급락하며 서버 응답 불능 | 메모리 부족 상태에서 웹 워커 프로세스 과다 기동(스래싱 발생) | 워커 프로세스 최대 생성 한도(MaxClients/MaxWorkers) 축소 및 프로세스 스왑아웃 | 프로세스별 최소 워킹셋 보장으로 스래싱 즉시 탈출 |
