## 연관 키워드

- 스래싱(Thrashing), 다중 프로그래밍 정도(DoM, Degree of Multiprogramming), 페이지 부재(Page Fault)
- 워킹셋(Working Set), 지역성(Locality), PFF(Page Fault Frequency)
- zRAM, zswap, OOM Killer, 클록 알고리즘(Clock Algorithm), Swap
- PSI, Cgroups v2, Requests/Limits, 임계점

## Ⅰ. 스래싱의 개요

- 핵심 요약 : **스래싱** (Thrashing)은 다중 프로그래밍 정도가 지나치게 커져 프로세스당 프레임이 부족해지고, 페이지 교체만 반복하여 CPU (Central Processing Unit) 이용률이 급락하는 시스템 마비 현상.
- 개념 : 가상 메모리 시스템에서 **다중 프로그래밍 정도** (DoM, Degree of Multiprogramming)가 과도해지면, 프로세스마다 물리 프레임이 모자라 **페이지 부재** (Page Fault)를 처리하는 디스크 스와핑 시간이 유효 연산 시간을 넘어서고, 그 결과 CPU 이용률이 0에 가깝게 떨어지는 상태.
- 배경 및 필요성 : CPU 이용률이 낮으면 운영체제가 준비 큐에 프로세스를 더 투입하는데, 이 탐욕적 방식이 메모리 부족을 키워 악순환을 만들므로 원인을 분석하고 제어할 필요가 있음.
- 주요 목적 : 스래싱 임계점 이전의 적정 다중 프로그래밍 정도 유지, 프로세스별 최소 동작 집합(워킹셋) 보장으로 처리량 보호.

## Ⅱ. 스래싱의 특징 및 장점

- 핵심 요약 : 임계점 초과, 스와핑 병목, 워킹셋과 PFF라는 두 가지 제어 기준으로 스래싱을 예측하고 억제.

1. DoM 임계점 초과 : 물리 메모리가 실행 중인 프로세스들의 워킹셋 합을 감당하지 못하는 순간 스래싱이 시작 → 임계점 이하로 투입 수준을 관리.
2. 스와핑 병목 : 느린 디스크 I/O에 페이지 인과 아웃 요청이 몰려 큐 대기 시간이 길어짐 → 스와프 장치 성능이 복구 속도를 좌우.
3. **워킹셋** (Working Set) 모델 : 프로세스가 일정 시간 동안 참조하는 페이지 집합을 메모리에 유지하는 모델이며, **지역성** (Locality)에 근거함 → 필요한 페이지만 남겨 부재를 줄임.
4. **PFF** (Page Fault Frequency) 알고리즘 : 프로세스의 부재 빈도를 측정하여 상한을 넘으면 프레임을 더 주고, 하한 아래로 떨어지면 회수 → 프레임 분배를 부재 상황에 맞춰 조정.

## Ⅲ. 스래싱의 구조 및 동작 메커니즘

- 핵심 요약 : DoM 증가가 프레임 부족과 페이지 부재 폭증을 불러오고, 그 결과 CPU가 놀게 되어 운영체제가 프로세스를 더 넣는 피드백 루프가 스래싱의 본질.

```text
[ 스래싱 악순환 ]

DoM 과도 증가
   ↓
프로세스당 프레임 부족
   ↓
페이지 부재 폭증 → 디스크 스왑 포화
   ↓
CPU 이용률 급락
   ↓
"CPU가 논다"고 판단해 프로세스 추가
   ↓ (악순환 반복)
```

```text
[ CPU 이용률과 DoM의 관계 ]

CPU 이용률
   ↑
   |      *****
   |    *       *
   |  *           *  ← 임계점 이후 급락
   | *              *
   ------------------------→ DoM
      정상 영역    스래싱 영역
```

- 워킹셋 W(t, Δ) : 시점 t 직전 Δ 시간 동안 참조된 고유 페이지의 집합.
- PFF : 부재 간격이 짧으면 프레임을 추가하고, 길면 프레임을 회수하는 피드백 제어.

## Ⅳ. 스래싱 제어 기법의 비교

- 핵심 요약 : 워킹셋은 지역성에 기반한 사전 예측, PFF는 부재 관측에 기반한 사후 교정, zRAM은 디스크 스왑 자체를 압축 메모리로 대체.

| 비교 항목 | 워킹셋 (Working Set) | PFF (Page Fault Frequency) | zRAM 압축 스왑 |
| --- | --- | --- | --- |
| 제어 방식 | 참조 윈도우 Δ 안의 고유 페이지 추적 | 페이지 부재 발생 간격 측정 | 스왑 데이터를 RAM에 압축 저장 |
| 프레임 할당 | 워킹셋 크기만큼 가변 보장 | 상한과 하한 임계치로 증감 | 압축률만큼 가용 메모리 확장 |
| 장점 | 지역성 이론에 충실해 스래싱 예방에 유리 | 부재가 날 때만 계산하므로 오버헤드가 적음 | 디스크 I/O를 줄여 스왑 속도 향상 |
| 단점 | 참조마다 윈도우를 추적하는 비용 | 부재 후에야 대응하는 사후 제어 | 압축과 해제에 CPU 사이클 소모 |
| 실제 적용 | 이론 모델, 클록 알고리즘 등으로 근사 | 가변 프레임 할당 정책에 활용 | 안드로이드, 리눅스 커널에서 사용 |

- 선택 기준 : 예측형 보장이 필요한지, 관측 기반 교정으로 충분한지, 메모리 압축으로 스왑 부담을 낮출 수 있는지에 따라 기법을 고름.

## Ⅴ. 스래싱의 한계와 방안

- 핵심 요약 : 워킹셋 윈도우 크기 결정, 메모리 완전 고갈, 디스크(HDD, Hard Disk Drive) 스왑 병목을 근사 알고리즘, OOM 처리, 고속 스왑으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 워킹셋 윈도우 크기 결정의 어려움 | 윈도우가 크면 불필요한 페이지가 메모리를 점유, 작으면 워킹셋이 잘려 스래싱 유발 | 참조 비트 기반 클록 알고리즘으로 워킹셋을 근사하고 윈도우를 주기적으로 조정 | 프레임 회수 빈도, 부재율 |
| 메모리 완전 고갈에 따른 서버 마비 | 스래싱이 계속되어 스왑까지 포화되면 커널 처리가 지연되어 서버 전체가 멈춤 | 리눅스 OOM Killer (Out-of-Memory Killer)로 oom_score가 높은 비핵심 프로세스를 종료하여 메모리 확보 | OOM 종료 횟수, 가용 메모리 |
| 디스크 스왑(HDD)의 I/O 병목 | 초당 많은 페이지 교체가 기계식 탐색 시간에 막혀 지연이 크게 늘어남 | NVMe (Non-Volatile Memory Express) 기반 고속 스왑 공간 구성, zRAM이나 zswap으로 압축 메모리 활용 | 스왑 I/O 대기 시간, 스왑 사용률 |

## Ⅵ. 스래싱에 대한 기술사적 제언

- 핵심 요약 : 쿠버네티스 자원 정책, 압력 지표 기반 선제 대응, 인메모리 시스템의 스왑 제한으로 스래싱을 진입 전에 차단.

1. 플랫폼 운영 조직이 쿠버네티스 메모리 Requests와 Limits를 워크로드 등급별로 설정하고 오버커밋 비율을 제한하여 노드가 임계점을 넘지 않도록 설계.
2. 운영 조직이 Cgroups v2의 **PSI** (Pressure Stall Information) 지표를 수집해 메모리 압력이 올라갈 때 스케줄러가 워크로드를 다른 노드로 옮기도록 연동.
3. 데이터 플랫폼 조직이 Redis, Elasticsearch, Kafka처럼 메모리 상주가 핵심인 노드에 스왑 사용을 제한하는 표준을 적용하여 지연 시간이 스왑으로 흡수되지 않게 관리.

## Ⅶ. 결론

- 핵심 요약 : 스래싱은 다중 프로그래밍 정도가 과도해져 페이지 부재가 폭증하고 CPU 이용률이 떨어지는 현상이며, 워킹셋과 PFF로 예방.
- 시사점 : 개별 프로세스의 프레임 보장보다 노드 전체의 메모리 압력을 상시 관측하고 투입 수준을 제한하는 체계가 스래싱 억제의 핵심.
