## Ⅰ. 스래싱(Thrashing)의 개요

- 개념 : 가상 메모리 시스템에서 다중 프로그래밍의 정도(DoM: Degree of Multiprogramming)가 과도하게 증가하여, 각 프로세스에 할당된 물리 메모리 프레임이 부족해짐에 따라 CPU가 유효한 프로그램 연산을 수행하는 시간보다 **페이지 부재(Page Fault)** 를 처리하기 위한 디스크 I/O 스와핑 시간이 더 많아져 시스템의 CPU 이용률이 급격히 0으로 곤두박질치는 시스템 마비 현상.
- 배경 및 필요성 : OS가 CPU 이용률이 낮을 때 시스템 성능을 높이기 위해 준비 큐에 프로세스를 더 많이 투입하는 탐욕적 스케줄링 메커니즘의 오류로 인해 발생하는 악순환을 분석하고 제어하기 위해 대두됨.
- 핵심 목적 : 스래싱 임계점(DoM Threshold) 이전의 최적 다중 프로그래밍 정도 유지, 프로세스별 최소 동작 세트(Working Set) 보장을 통한 시스템 처리량 보호.

## Ⅱ. 스래싱(Thrashing)의 핵심 아키텍처 및 동작 메커니즘

스래싱은 'DoM 증가 -> 프로세스당 프레임 감소 -> 페이지 부재 폭증 -> 디스크 큐 포화 및 CPU 대기 -> OS가 프로세스 추가 투입'이라는 치명적 피드백 루프로 전개됨.

```text
[ 스래싱 발생 메커니즘 및 CPU 이용률 곡선 ]

1. 스래싱 악순환 (Vicious Cycle)
   [DoM 과도 증가] ──> [프로세스당 프레임 부족] ──> [Page Fault 빈발]
          ▲                                               │
          │                                               ▼
   [OS: "CPU 놀고 있네?"] <── [CPU 이용률 급락] <── [디스크 I/O 스왑 포화]
   (프로세스 추가 적재!)

2. CPU 이용률 vs 다중 프로그래밍 정도(DoM) 곡선
   CPU 이용률 (%)
   100 ┤              /＼
       │             /   ＼  <-- 스래싱 임계점 (Thrashing Threshold)
       │            /      ＼
       │           /         ＼
       │          /            ＼
     0 ┼─────────/───────────────＼─────> 다중 프로그래밍 정도 (DoM)
                 [정상 동작 영역]  [스래싱 마비 영역]

3. 해결 기법: 워킹셋(Working Set) 및 PFF(Page Fault Frequency)
   - Working Set W(t, delta) : 최근 delta 시간 동안 참조된 고유 페이지 집합
   - PFF : 상한선 초과 시 프레임 추가 할당, 하한선 미달 시 프레임 회수
```

- **DoM 임계점 초과** : 물리 메모리의 총량이 프로세스들의 워킹셋 합계를 감당하지 못하는 순간 스래싱 발생.
- **스와핑 병목 (Swapping Bottleneck)** : 느린 디스크 I/O 서브시스템에 페이지 인/아웃 요청이 폭주하여 큐 대기시간이 무한정 증가.
- **워킹셋(Working Set) 모델** : 프로세스가 특정 시점에 원활히 수행되기 위해 반드시 메모리에 유지되어야 하는 페이지들의 집합으로, 지역성(Locality)에 기반함.
- **페이지 부재 빈도(PFF) 알고리즘** : 프로세스의 페이지 부재 비율을 지속 측정하여 상한선(Upper Bound)을 넘으면 프레임을 더 주고, 하한선(Lower Bound) 밑으로 떨어지면 프레임을 회수.

## Ⅲ. 스래싱(Thrashing)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 워킹셋(Working Set) 알고리즘 | PFF(Page Fault Frequency) 알고리즘 | zRAM 압축 스왑 기법 |
|---|---|---|---|
| **제어 메커니즘** | 참조 윈도우(delta) 내 고유 페이지 추적 | 페이지 부재 발생 주기(주기 간격) 측정 | 스왑 데이터를 디스크 대신 RAM에 압축 저장 |
| **프레임 할당 방식** | 워킹셋 크기만큼 가변적 프레임 보장 | 상한/하한 임계치에 따른 동적 증감 | 압축률 기반 가용 RAM 공간 확장 |
| **장점** | 지역성 이론에 충실, 스래싱 완벽 방어 | 페이지 부재 시에만 계산하므로 오버헤드 적음 | 디스크 I/O 자체를 차단하여 초고속 스왑 |
| **단점** | 매 메모리 참조마다 윈도우 추적 오버헤드 | 부재가 발생한 후에야 사후 대응 | 압축/해제에 따른 CPU 사이클 소모 |
| **OS 적용** | 개념적 이론 모델 (근사 기법 활용) | 리눅스 등 가변 프레임 할당에 활용 | 안드로이드, 최신 리눅스 커널 표준 |

- 워킹셋은 프로세스의 미래 요구를 지역성으로 예측하는 사전적 모델이고, PFF는 부재 빈도를 관측하여 사후에 교정하는 피드백 제어 모델임.

## Ⅳ. 스래싱(Thrashing)의 주요 한계점 및 해결 방안

- 워킹셋 **윈도우(delta)** 크기 결정의 딜레마 :
  - 한계점 : 윈도우가 너무 크면 불필요한 페이지까지 메모리에 묶여 자원이 낭비되고, 너무 작으면 워킹셋이 파편화되어 스래싱 유발.
  - 해결 방안 : 하드웨어 참조 비트(Reference Bit) 기반의 클록(Clock) 알고리즘과 결합하여 동적으로 윈도우 크기를 미세 조정.
- 시스템 메모리 완전 고갈 시 동반 다운 :
  - 한계점 : 스래싱 상태가 지속되어 스왑 공간마저 포화되면 커널 인터럽트 처리마저 중단되어 서버 전면 셧다운.
  - 해결 방안 : 리눅스 OOM Killer(Out-of-Memory Killer) 메커니즘을 작동시켜 `oom_score`가 높은 비핵심 프로세스를 강제 종료하고 메모리 즉시 확보.
- 기계식 **HDD** 스왑 공간의 극심한 I/O 병목 :
  - 한계점 : 초당 수십 회 이상의 페이지 교체 시 기계식 디스크의 탐색 시간 한계로 지연시간이 수 초대로 폭증.
  - 해결 방안 : 초고속 NVMe 기반 ZNS 스왑 파티션 구성 및 커널 메모리 압축(zRAM / zswap) 필수 활성화.

## Ⅴ. 스래싱(Thrashing) 적용 및 발전을 위한 기술사적 제언

- 쿠버네티스 메모리 **Requests/Limits** 기반 스래싱 원천 방지 : 노드의 총 메모리 용량을 초과하는 무분별한 파드 스케줄링을 차단하기 위해 리소스 쿼터와 오버커밋 비율을 엄격 제어.
- Cgroups v2 메모리 압력 **감지(PSI: Pressure Stall Information)** 연동 : 메모리 부족으로 CPU가 대기하는 시간 비율(some/full)을 모니터링하여 스래싱 진입 전 선제적으로 컨테이너를 수평 확장하거나 워크로드 드레인.
- 인메모리 데이터베이스의 **스왑 비활성화(Swap-off)** 표준화 : Redis, ElasticSearch, Kafka 등 대용량 캐시/DB 노드는 스래싱 발생 시 클러스터 전체 분산 합의 붕괴를 초래하므로 OS 스왑을 원천 비활성화(`swapoff -a`) 권장.
