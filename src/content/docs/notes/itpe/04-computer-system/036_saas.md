## 연관 키워드

- SaaS(Software as a Service), 멀티테넌시(Multi-Tenancy), 테넌트(Tenant)
- 데이터 격리 모델(사일로·브리지·풀), 논리적 격리, RLS(Row-Level Security)
- 구독(Subscription), 미터링(Metering), 사용량 기반 과금
- 노이지 네이버(Noisy Neighbor), Rate Limiting, 무중단 업데이트, SLA(Service Level Agreement)

## Ⅰ. SaaS의 개요

- 핵심 요약 : **SaaS** (Software as a Service)는 완성된 소프트웨어를 제공업체가 클라우드에서 운영하고 구독 방식으로 이용하게 하는 소프트웨어 전달 모델.
- 개념 : 소프트웨어를 단말에 설치하지 않고 네트워크로 접속해 사용하며, 사용 기간과 사용량에 따라 요금을 지불하는 애플리케이션 제공 방식.
- 배경 및 필요성 : 패키지 라이선스 방식의 높은 초기 도입 비용, 버전별 파편화, 설치·패치의 고객 부담이 문제가 되어 중앙 운영형 모델 필요.
- 주요 목적 : 소프트웨어 운영 부담의 제공업체 집중, 구독 과금 기반의 비용 구조 전환, 항상 최신 버전 이용 환경 제공.

## Ⅱ. SaaS의 특징 및 장점

- 핵심 요약 : 하나의 애플리케이션을 여러 고객이 공유하면서도 사용량과 데이터를 분리하는 구조가 운영 효율과 과금 투명성으로 이어짐.

1. **멀티테넌시** (Multi-Tenancy) : 단일 애플리케이션 인스턴스에서 다수 고객사인 **테넌트** (Tenant)를 논리적 격리로 분리해 서비스하는 구조 → 자원 공유로 고객당 운영 비용 절감 효과.
2. **구독** (Subscription) 과금 : 사용 기간과 **미터링** (Metering)으로 계량한 사용량에 따라 요금을 부과하는 사용량 기반 과금 방식 → 초기 투자 없이 수요에 맞춘 비용 구조 확보.
3. 무중단 업데이트 : 제공업체가 단일 코드베이스를 중앙에서 패치해 전체 고객에게 동시 적용하는 방식 → 버전 파편화 제거와 최신 기능 즉시 이용 효과.
4. 접속 단말의 범용성 : 웹 브라우저와 API (Application Programming Interface)로 이용하는 접근 방식 → 기기 제약 없는 업무 환경과 연계 확장성 확보.
5. 운영 책임의 이전 : 인프라·애플리케이션 계층의 유지 책임이 제공업체에 집중 → 고객의 이용과 설정 집중 효과.

## Ⅲ. SaaS의 구조 (흐름)

- 핵심 요약 : 요청이 테넌트 식별을 거쳐 공유 애플리케이션 계층에 진입하고, 데이터 접근 시점에 테넌트 격리 모델이 적용됨.

```text
[ SaaS 요청 처리 흐름 ]

테넌트 사용자의 접속 요청
   ↓
테넌트 식별 (서브도메인·인증 토큰)
   ↓
공유 애플리케이션 계층
   ↓
테넌트 범위가 적용된 데이터 접근
   ↓
사용량 계량과 구독 과금 반영
```

```text
[ 데이터 격리 3대 모델 ]

사일로 : 테넌트별 독립 저장소
   ↓ 격리 수준 완화 방향
브리지 : 공용 저장소의 스키마 분리
   ↓
풀 : 공용 테이블과 식별 컬럼
```

- 구성요소 : 테넌트 식별·인증 계층, 공유 비즈니스 로직 계층, 테넌트별 데이터 분리 계층, 사용량 계량·과금 모듈로 구성.
- **데이터 격리 모델** (Data Isolation Model) : 사일로는 물리적 완전 분리로 보안성이 높고, 브리지는 스키마 단위 분리, 풀은 행 단위 분리로 비용 효율이 높은 구조.

## Ⅳ. SaaS 전달 모델의 비교

- 핵심 요약 : 실행 위치와 격리 방식, 과금 구조에 따라 온프레미스 패키지, 싱글테넌트 호스팅, 멀티테넌트 SaaS의 성격이 구분됨.

| 비교 항목 | 온프레미스 패키지 | 싱글테넌트 호스팅 | 멀티테넌트 SaaS |
| --- | --- | --- | --- |
| 실행 위치 | 고객사 자체 서버 | 제공사 인프라의 고객 전용 구역 | 제공사의 공유 인스턴스 |
| 격리 방식 | 물리적 완전 분리 | 인프라 단위 분리 | 논리적 테넌트 분리 |
| 과금 구조 | 라이선스 구매와 유지보수 계약 | 전용 자원 기반 월 단위 비용 | 구독료와 사용량 기반 과금 |
| 업데이트 | 고객 주도의 버전 이행 | 고객 일정에 맞춘 적용 | 제공사 주도의 무중단 업데이트 |
| 단위 비용 효율 | 낮음 | 중간 | 자원 풀링으로 높음 |

- 선택 기준 : 데이터 통제 요구 수준, 맞춤 개발 범위, 비용 구조 선호에 따라 전달 모델을 선택.

## Ⅴ. SaaS의 한계와 방안

- 핵심 요약 : 테넌트 간 데이터 침범, 테넌트 간 성능 간섭, 가용성 의존을 격리 강제, 처리율 제어, 서비스 수준 관리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 테넌트 간 데이터 침범 | 질의에서 테넌트 조건 누락 → 타 고객 데이터 노출 | 행 수준 보안 **RLS** (Row-Level Security) 강제, 격리 모델별 접근 통제 적용 | 격리 위반 탐지 건수 |
| **노이지 네이버** (Noisy Neighbor) 성능 간섭 | 특정 테넌트의 대량 사용 → 같은 인스턴스의 타 테넌트 지연 | 테넌트별 **처리율 제한** (Rate Limiting) 적용, 사용량 급증 테넌트의 전용 구역 전환 | 테넌트별 응답 지연, 제한 발동 횟수 |
| 서비스 가용성 의존 | 중앙 운영 구조 특성상 제공사 장애가 전 고객으로 확산 | SLA (Service Level Agreement) 기반 가용성 관리, 장애 통지·보상 절차 명문화 | SLA 달성률, 장애 전파 시간 |

## Ⅵ. SaaS에 대한 기술사적 제언

- 핵심 요약 : 격리 검증의 표준화, 과금 체계의 유연 설계, 서비스 수준 관리를 조직 역량으로 정착하는 방향.

1. 제품 개발 조직이 테넌트 격리 검증을 출시 전 필수 시험 항목으로 지정해 격리 계층의 안전성을 표준 절차로 확보.
2. 플랫폼 운영 조직이 미터링 지표 수집과 요금 정책 적용을 분리한 과금 아키텍처로 설계해 정책 변경의 유연성 확보.
3. 서비스 관리 조직이 테넌트별 서비스 등급과 SLA 조항을 계약·기술 양쪽에서 일치시키는 관리 체계를 운영해 신뢰 기반 확보.

## Ⅶ. 결론

- 핵심 요약 : SaaS는 멀티테넌시와 구독 과금으로 소프트웨어 공급 방식을 전환한 전달 모델.
- 시사점 : 공유 구조의 격리 신뢰가 확보될 때 운영 효율과 고객 신뢰가 함께 성립하는 구조.
