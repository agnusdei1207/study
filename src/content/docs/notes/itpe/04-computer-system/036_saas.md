## 연관 키워드

- SaaS(Software as a Service), 멀티테넌시(Multi-Tenancy), 테넌트(Tenant), 테넌트 컨텍스트
- 데이터 격리 모델(사일로·브리지·풀), RLS(Row-Level Security), 미터링(Metering), 구독(Subscription)
- 노이지 네이버(Noisy Neighbor), Rate Limiting, Headless SaaS, iPaaS
- PLG(Product-Led Growth), AI-Native SaaS, 데이터 레지던시(Data Residency)

## Ⅰ. SaaS의 개요

- 핵심 요약 : **SaaS** (Software as a Service)는 소프트웨어를 클라우드에서 중앙 호스팅하고 구독 방식으로 제공하는 클라우드 서비스 모델.
- 개념 : 고객이 소프트웨어를 자신의 PC나 서버에 설치하지 않고, 제공업체가 운영하는 완성된 애플리케이션을 웹 브라우저, 모바일 앱, API (Application Programming Interface)로 이용하고 사용 기간에 따라 **구독** (Subscription) 요금을 내는 서비스 모델.
- 배경 및 필요성 : 기존 라이선스 구매 방식은 초기 구축비가 크고, 설치와 패치 부담 및 버전 파편화가 심하여, 최신 기능을 어디서나 바로 쓰게 하는 모델의 필요.
- 주요 목적 : 인프라와 소프트웨어 운영 부담 감소, 구독형 과금을 통한 초기 비용 절감, 무중단 기능 업데이트와 협업 환경 제공.

## Ⅱ. SaaS의 특징 및 장점

- 핵심 요약 : 하나의 애플리케이션을 여러 고객이 공유하면서도 데이터와 사용량을 분리하는 구조가 운영 효율과 과금 투명성으로 이어짐.

1. **멀티테넌시** (Multi-Tenancy) : 단일 소프트웨어 인스턴스와 공용 인프라에서 다수 고객사를 **테넌트** (Tenant)로 논리적으로 격리하여 서비스 → 인프라 공유로 단위 고객당 운영 비용 감소.
2. 테넌트 컨텍스트 주입 : 요청마다 JWT (JSON Web Token) 클레임이나 서브도메인에서 테넌트 식별자를 꺼내 모든 서비스 호출과 데이터 질의에 범위를 자동 적용 → 누락에 의한 데이터 혼선 억제.
3. **데이터 격리 모델** : 사일로(Silo, 테넌트별 독립 데이터베이스), 브리지(Bridge, 한 데이터베이스 안의 테넌트별 스키마), 풀(Pool, 공용 테이블과 테넌트 식별 컬럼) 중에서 보안 요구와 비용에 맞춰 선택 → 고객 등급별 격리 수준 차별화.
4. **미터링** (Metering) : API 호출 수, 저장 용량, 활성 사용자 수 같은 사용량을 실시간으로 계량하여 단계별 구독 요금에 반영 → 사용량 기반의 공정한 과금.

## Ⅲ. SaaS의 구조 및 동작 메커니즘

- 핵심 요약 : 요청은 테넌트 식별을 거쳐 공유 비즈니스 계층으로 들어가고, 데이터 접근 단계에서 격리 모델 적용.

```text
[ SaaS 요청 처리 흐름 ]

테넌트 사용자 요청
   ↓
테넌트 식별 (서브도메인·JWT 클레임)
   ↓
공유 애플리케이션 계층 (단일 인스턴스)
   ↓
테넌트 범위가 적용된 데이터 접근
   ↓
사용량 계량 후 구독 요금 반영
```

```text
[ 데이터 격리 3대 모델 ]

사일로 (Silo) : 테넌트별 전용 저장소
   ↓ 비용 절감, 격리 완화
브리지 (Bridge) : 저장소 내 스키마 분리
   ↓ 비용 절감, 격리 완화
풀 (Pool) : 공용 테이블 + 테넌트 ID
```

- 구성 : 테넌트 식별과 인증을 담당하는 게이트웨이, 모든 테넌트가 공유하는 비즈니스 로직 계층, 테넌트별 데이터 분리 계층, 사용량 측정 및 과금 모듈로 이루어짐.

## Ⅳ. SaaS의 비교

- 핵심 요약 : 온프레미스, IaaS 기반 호스팅, 클라우드 네이티브 SaaS는 소유 주체와 업그레이드 방식이 달라 운영 책임의 위치가 바뀜.

| 비교 항목 | 온프레미스 패키지 소프트웨어 | IaaS (Infrastructure as a Service) 기반 호스팅 | 클라우드 네이티브 SaaS |
| --- | --- | --- | --- |
| 소유 및 배포 | 고객사 서버에 직접 설치 | 클라우드 VM (Virtual Machine)에 단독 설치 | 제공사가 운영하는 멀티테넌트 공유 구조 |
| 과금 방식 | 영구 라이선스와 유지보수료 | 인프라 비용과 소프트웨어 라이선스 | 구독료 (SaaS Subscription) |
| 업그레이드 | 수동 패치와 마이그레이션 프로젝트 | 고객이 OS와 앱 버전을 직접 관리 | 제공사 주도의 무중단 업데이트 |
| 커스터마이징 | 소스 수정까지 가능 | 일정 수준 가능 | 표준 설정과 API, 웹훅 연계 중심 |
| 자원 효율성 | 피크 대비 유휴 자원 낭비 | 오토스케일링 가능 | 풀링으로 높은 집적도 |

- 선택 기준 : 소스 수준의 맞춤이 필수인지, 운영 인력을 둘 수 있는지, 업데이트 주기를 제공사에 맡길 수 있는지에 따라 모델을 고름.

## Ⅴ. SaaS의 한계와 방안

- 핵심 요약 : 테넌트 간 데이터 침범, 성능 간섭, 표준화에 따른 맞춤 한계를 격리 강제와 자원 제한, 헤드리스 구조로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 테넌트 간 데이터 침범 | 질의에서 테넌트 조건이 빠지면 다른 고객사 데이터가 노출 | 데이터베이스 행 수준 보안 RLS (Row-Level Security)를 데이터베이스 엔진에서 강제, ORM (Object-Relational Mapping) 계층에서 테넌트 조건 자동 주입 | 테넌트 조건 누락 탐지 건수 |
| 노이지 네이버 (Noisy Neighbor) 성능 간섭 | 특정 테넌트의 대량 배치나 트래픽 폭증이 같은 클러스터의 다른 테넌트 응답을 지연 | 테넌트별 Rate Limiting (처리율 제한), 메시지 큐 우선순위 분리, 대형 고객의 전용 격리 티어 제공 | 테넌트별 지연 시간, 제한 발동 횟수 |
| 고객사 맞춤 요구와 레거시 연계 | 표준 UI와 워크플로우로 복잡한 결재선이나 특수 규칙 수용 불가 | 헤드리스 (Headless) SaaS 구조, iPaaS (Integration Platform as a Service) 연계, 사용자 정의 필드 제공 | 맞춤 요청 처리 기간, 연계 실패율 |

## Ⅵ. SaaS에 대한 기술사적 제언

- 핵심 요약 : 제품 성장 측정, 데이터 주권 요구, AI 기능 결합을 플랫폼 공통 역량으로 설계하는 방향이 적절.

1. 제품 조직이 **PLG** (Product-Led Growth) 텔레메트리를 수집하여 사용자 행동과 이탈 경로를 분석하고, 이를 가입 이후 온보딩 설계에 환류.
2. 아키텍처 조직이 리전별 저장소와 **데이터 레지던시** (Data Residency) 정책을 플랫폼 공통 기능으로 두어 국가별 데이터 보관 요구에 대응.
3. 개발 조직이 AI (Artificial Intelligence) 기능을 워크플로우 단계에 결합하는 **AI-Native SaaS** 방향을 택하되, 테넌트별 권한 범위와 감사 로그를 같은 인증 계층에서 관리하도록 설계.

## Ⅶ. 결론

- 핵심 요약 : SaaS는 멀티테넌시와 테넌트 격리, 미터링으로 구독형 서비스를 효율화하는 클라우드 소프트웨어 모델.
- 시사점 : 공유에 따른 격리와 성능 간섭 위험을 기술적으로 통제하는 것이 신뢰의 전제이며, 이 전제가 충족되어야 운영 이점을 온전히 얻는 구조.
