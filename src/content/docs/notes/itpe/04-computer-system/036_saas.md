## 답안 골격
```text
[SaaS] ◀━━ 머리: Ⅶ 내 의견 (멀티 테넌트 데이터 격리 보안 아키텍처와 CASB/CSPM 연계 통합 거버넌스 수립)
 ┃
 ┣━ Ⅰ 개요 ───── 온프레미스 소프트웨어 설치·패치·라이선스 부담 → 웹 브라우저 경유 구독형 완전관리형 소프트웨어
 ┣━ Ⅱ 특징 ───── 멀티 테넌시(Multi-Tenancy) · 구독형 과금(Subscription) · 중앙 집중식 자동 업데이트 · 확장성
 ┣━ Ⅲ 구조 ───── 테넌트 관리 계층 + 미터링/빌링 + 애플리케이션 계층 + 테넌트 데이터 격리 모델(Pool vs Silo)
 ┣━ Ⅳ 흐름 ───── ① 사용자 웹/모바일 로그인 → ② 테넌트 식별 및 인증(SAML/OIDC) → ③ 공용 애플리케이션 라우팅 → ④ 격리된 테넌트 데이터 조회
 ┣━ Ⅴ 비교 ───── SaaS vs PaaS vs IaaS / 싱글 테넌트(Silo) vs 멀티 테넌트(Pool)
 ┗━ Ⅵ 실무 ───── 테넌트 간 데이터 침범(Data Leakage) / 커스터마이징 제약 / 클라우드 섀도우 IT(Shadow IT)
```
- 필수 키워드: 멀티 테넌시(Multi-Tenancy) · 구독 모델 · 테넌트 격리(Silo vs Pool) · CASB · API 경제 · 완전관리형
- 기출: 122회 `클라우드 컴퓨팅 서비스 모델(SaaS, PaaS, IaaS)의 특징 및 차이점`

## 한 줄 본질
- 개별 PC나 자체 서버마다 패키지 소프트웨어를 설치하고 업그레이드하던 막대한 유지보수 공수와 라이선스 관리 비용 → 클라우드 인프라 위에서 공급자가 애플리케이션을 단일 인스턴스로 호스팅하고 고객은 웹/API를 통해 서비스 형태로 구독(Subscribe) → 설치 제로 및 최신 기능 즉시 활용 / 고객 맞춤 커스터마이징 제약 및 기업 데이터 외부 위탁에 따른 보안 리스크

## 핵심 그림
```text
[ 멀티 테넌트 데이터 격리 3대 모델 (Multi-Tenant Data Isolation) ]

1. 사일로 모델 (Silo: 완벽 격리)      2. 브릿지 모델 (Bridge: 스키마 분리)   3. 풀 모델 (Pool: 완전 공유)
+──────────────────────────+         +──────────────────────────+        +──────────────────────────+
|  [Tenant A]  [Tenant B]  |         |  [Tenant A]  [Tenant B]  |        |  [Tenant A]  [Tenant B]  |
+──────┬────────────┬──────+         +──────┬────────────┬──────+        +──────┬────────────┬──────+
       │            │                       │            │                      └─────┬──────┘
       v            v                       v            v                            v
+------------+ +------------+        +--------------------------+        +--------------------------+
| 전용 DB A  | | 전용 DB B  |        | 단일 DB 내 개별 Schema   |        | 단일 DB 단일 Table       |
| (물리 분리)| | (물리 분리)|        | (Schema A) │ (Schema B)  |        | (Tenant_ID 컬럼으로 식별)|
+------------+ +------------+        +--------------------------+        +--------------------------+
* 비용: 최고가, 격리: 완벽           * 비용: 중간, 격리: 우수           * 비용: 최저, 격리: 로직 의존
```

## 핵심 용어
- 멀티 테넌시(Multi-Tenancy): 단일 소프트웨어 인스턴스와 데이터베이스 인프라를 여러 고객(테넌트)이 공유하면서도, 논리적으로 각자의 데이터가 완벽히 분리되어 안전하게 실행되는 아키텍처
- CASB(Cloud Access Security Broker): 사용자와 SaaS 클라우드 애플리케이션 사이에 위치하여 데이터 보안, 규제 준수, 위협 탐지 및 인가 정책을 단일하게 적용하는 보안 솔루션
- 테넌트 격리(Tenant Isolation): 특정 테넌트의 악의적 쿼리나 과도한 부하(Noisy Neighbor)가 다른 고객의 서비스 성능이나 데이터 무결성을 침범하지 못하도록 보장하는 경계선

## 핵심 통찰
- SaaS의 성공 방정식은 '규모의 경제(Economies of Scale)'에 있음 → 고객마다 서버를 따로 띄우는 호스팅 방식은 SaaS가 아니며, 단일 코드베이스 위에서 수만 고객을 동시에 서비스해야 운영 비용이 0에 수렴
- SaaS 아키텍처에서 가장 까다로운 결정은 '데이터 격리 모델(Silo vs Pool)'임 → 규제가 엄격한 금융/헬스케어는 비용을 감수하고 물리적 전용 DB(Silo)를 요구하며, 스타트업/B2C는 테넌트 ID 컬럼 기반의 단일 테이블 풀(Pool) 모델로 원가 절감
- 기업 내부에서 부서별로 IT 부서 승인 없이 무분별하게 도입하는 '섀도우 IT(Shadow IT)' SaaS로 인해 기업 비밀 데이터가 외부로 유출되는 사고가 급증하고 있음

## 이웃 토픽과 구분
- SaaS vs PaaS: SaaS = 최종 사용자가 완성된 업무 소프트웨어(Slack, Salesforce, M365)를 웹으로 소비 / PaaS = 개발자가 애플리케이션을 직접 개발·배포하기 위한 실행 플랫폼(Heroku, App Engine)을 소비

## 문제·원인·대책
- 사례: 122회 기출 B2B 멀티테넌트 SaaS 서비스에서 타사 데이터 노출 사고 및 부하 전파 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| A사 사용자가 B사의 고객 개인정보 데이터를 조회하는 치명적 정보 유출 | 애플리케이션 ORM 계층에서 테넌트 식별자(`tenant_id`) WHERE 절 누락 | DB 수준의 행 단위 보안(RLS: Row Level Security) 강제 활성화 | 코드 버그가 있어도 데이터베이스 엔진이 타 테넌트 데이터 차단 |
| 특정 대형 테넌트의 대규모 배치 작업으로 다른 테넌트의 웹 응답 시간 10배 폭증 | 공유 자원 풀 모델에서의 리소스 경합(Noisy Neighbor) | 테넌트별 API 호출 속도 제한(Rate Limiting) 및 비동기 워커 큐 분리 | 테넌트 간 성능 간섭 차단 및 공평한 서비스 품질 유지 |
