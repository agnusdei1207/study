## 큰 그림과 30초 인출

```text
애플리케이션
 ├─ [Volume/LUN] → [Block ID : Raw Block]       : 블록
 ├─ [/dir/file]  → [File System : File]         : 파일
 └─ [Bucket/Key] → [Object + Metadata + ID]     : 오브젝트

선택축 = 접근 단위 × 네임스페이스 × 갱신 방식 × 지연 × 확장 × 공유
```

```text
블록 = 저수준 블록 접근, DB·VM 디스크
파일 = 계층 경로와 공유 파일, 협업·홈 디렉터리
오브젝트 = Key 기반 객체+메타데이터, 대규모 비정형·데이터 레이크
주의 = 일관성·내구성·성능은 제품과 구성별 검증
```

## 예상문제

> 블록·파일·오브젝트 스토리지를 접근방식과 구조 관점에서 비교하고, 대규모 AI 데이터 인프라의 최적 활용 방안을 설명하시오.

## Ⅰ. 개요 ───── 정의·선정 관점

스토리지는 데이터를 **블록, 파일, 오브젝트 중 어떤 논리 단위와 인터페이스로 표현·접근하는가**에 따라 구분하며, 워크로드의 지연·공유·확장·갱신 특성에 맞춰 선택해야 한다.

## Ⅱ. 특징 ───── 세 유형의 본질

| 유형 | 본질 | 접근 | 대표 용도 |
|---|---|---|---|
| 블록 | 주소 가능한 고정 크기 블록 | 볼륨·블록 프로토콜 | DB, VM 부트·데이터 디스크 |
| 파일 | 파일시스템이 관리하는 파일·디렉터리 | 경로·파일 프로토콜 | 공유 문서, 홈, 콘텐츠 제작 |
| 오브젝트 | 데이터·메타데이터·식별자의 객체 | Key·객체 API | 백업, 미디어, 데이터 레이크 |

## Ⅲ. 구조 ───── 주소·메타데이터·접근 경로

```text
[Block Client]─Volume─>[Block Controller]─>[Block][Block][Block]
[File Client] ─Path───>[File System]───────>/dir/file + inode/metadata
[Object App]──Key/API─>[Object Service]────>Bucket/{Data+Metadata+ID}
```

| 관점 | 블록 | 파일 | 오브젝트 |
|---|---|---|---|
| 주소 | 블록 번호 | 디렉터리 경로 | Bucket·Key/ID |
| 메타데이터 | 상위 파일시스템 담당 | 파일시스템 속성 | 객체와 함께 풍부하게 관리 가능 |
| 갱신 | 블록 단위 | 파일·바이트 범위 | 통상 객체 교체 중심 |
| 공유 모델 | 호스트·클러스터 SW 필요 | 다중 클라이언트 파일 공유 | API 기반 분산 접근 |

## Ⅳ. 동작 ───── 쓰기·읽기와 AI 데이터 흐름

```text
수집 → Object Raw Zone → 정제·특징 생성 → 학습
          │                                │
          └─ 대규모 원본·체크포인트         ├─ Block: DB·고성능 작업영역
                                           └─ File: 공유 코드·도구·POSIX 작업
```

| 단계 | 블록 | 파일 | 오브젝트 |
|---|---|---|---|
| 쓰기 | 블록 주소에 기록 | 경로 열기 후 기록 | Key로 객체 PUT |
| 조회 | 파일시스템/DB가 해석 | 경로·권한 확인 | Key로 객체 GET |
| 보호 | 복제·스냅샷·RAID 등 | 스냅샷·ACL 등 | 복제·삭제코딩·버전 등 |

보호 방식은 구현별 선택 사항이며 특정 방식을 세 유형의 절대 속성으로 단정하지 않는다.

## Ⅴ. 비교 ───── 선택 기준과 최적 활용

| 기준 | 블록 | 파일 | 오브젝트 |
|---|---|---|---|
| 저지연 임의 갱신 | 강점 | 중간 | 비권장 영역 |
| 계층 탐색·공유 | 파일시스템 필요 | 강점 | 논리 Prefix는 가능하나 의미가 다름 |
| 수평 확장·대량 객체 | 구현 의존 | 구현 의존 | 강점 |
| 애플리케이션 인터페이스 | Device/Volume | POSIX·파일 프로토콜 | HTTP 기반 객체 API |
| 최적 업무 | DB·VM | 공동 파일 작업 | 비정형·보관·분석 원천 |

## Ⅵ. 고려 ───── 워크로드 기반 배치·검증

| 문제 | 원인 | 대응 | 검증 |
|---|---|---|---|
| 작은 객체 비효율 | 호출·메타데이터 비용 | 묶음·포맷·파티션 설계 | 객체 크기별 처리량 |
| 오브젝트 갱신 부적합 | 객체 교체 중심 모델 | 변경 데이터는 DB/Block 분리 | 갱신 지연·비용 |
| 데이터 중력 | 대용량 이동 | 계산을 데이터 근처 배치 | 이동 시간·전송비 |
| 일관성 오해 | 제품·연산별 의미 차이 | 요구 수준과 API 보장 대조 | 동시 읽기/쓰기 시험 |
| 계층 간 복제 | Hot/Warm/Cold 이동 | 수명주기·카탈로그·계보 | 복구시간·추적성 |

## Ⅶ. 결론 ───── 계층형 결합과 데이터 거버넌스

세 유형은 우열 관계가 아니라 접근 의미가 다르다. 대규모 AI 인프라는 **오브젝트의 확장성, 파일의 공유성, 블록의 저지연 갱신성**을 데이터 생명주기에 맞춰 결합하고, 카탈로그·권한·암호화·복구 시험으로 통제해야 한다.

## 1교시 10점 발췌

```text
블록: Volume/Block ID, 저지연 임의 갱신, DB·VM
파일: Path/File System, 계층·공유, 협업 데이터
오브젝트: Bucket/Key, Data+Metadata+ID, 비정형·데이터 레이크

선정축: 접근 단위·지연·공유·확장·갱신·일관성·비용
```
