## 한 줄 본질
- IT 시스템을 구성하는 인프라, 플랫폼, 애플리케이션 스택의 관리 책임을 표준 단위로 분할하여 온디맨드로 임대 → 인프라 구축 기간 단축 및 핵심 로직 집중 / 상위 모델일수록 공급자 플랫폼 종속 및 아키텍처 제어권 축소

## 핵심 용어
- IaaS(Infrastructure as a Service): 가상머신, 스토리지, 가상 네트워크 등 원시 컴퓨팅 자원을 제공하며 OS 이상의 스택을 사용자가 직접 제어하는 모델
- PaaS(Platform as a Service): OS, 프로그래밍 언어 런타임, DBMS, 미들웨어를 CSP가 관리하고 개발자는 애플리케이션 코드와 데이터만 배포하는 모델
- SaaS(Software as a Service): CSP가 전체 소프트웨어 스택과 인프라를 일괄 운영하며 최종 사용자는 웹 브라우저나 API를 통해 완성된 기능을 구독하는 모델

## 핵심 통찰
- 서비스 모델의 본질은 기술의 차이가 아니라 '운영 위험의 외주화 범위'임 → 상위 모델로 올라갈수록 서버 관리, 패치, 물리 장애 대응의 책임이 CSP로 넘어가지만, 내부 아키텍처를 튜닝할 권한은 박탈됨
- 추상화 수준과 벤더 종속(Lock-in) 비용은 정비례함 → IaaS는 VM 이미지나 테라폼으로 타 CSP 이전이 수월하지만, 특정 CSP 고유 PaaS/FaaS에 종속된 코드는 타 환경 마이그레이션 시 전면 재개발 비용을 유발함
- 책임 공유 모델에서 보안 실패의 90% 이상은 사용자 영역에서 발생함 → IaaS 환경에서 게스트 OS 보안 패치 미적용, 방화벽 포트 전면 개방, IAM 키 탈취 등은 CSP의 책임 범위를 벗어난 사용자 과실임

## 이웃 토픽과 구분
- 배포 모델(Deployment Model) vs 서비스 모델(Service Model): 배포 모델 = 인프라의 위치와 소유/공유 형태(Public, Private, Hybrid) / 서비스 모델 = 제공되는 IT 스택의 추상화 계층과 책임 범위(IaaS, PaaS, SaaS)

## 문제·원인·대책
- 적용 상황: 클라우드 도입 기업의 서비스 모델 선정 및 운영 거버넌스
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 CSP PaaS 전용 데이터베이스 및 API 종속으로 타 CSP 이전 불가 | 독점적 기능 활용에 치중한 애플리케이션 설계 | 컨테이너(K8s) 기반 표준 런타임 및 오픈소스 호환 PaaS 채택 | 아키텍처 이식성 확보 및 이전 비용 억제 |
| IaaS 인스턴스의 랜섬웨어 감염 및 데이터 유출 | CSP가 모든 보안을 책임진다는 사용자의 착각 및 OS 패치 태만 | 책임 공유 모델 기반 IAM, OS 하드닝, EDR 솔루션 직접 적용 | 사용자 영역 공격 표면 제거 및 침해 차단 |
| SaaS 도입 후 기존 사내 ERP 시스템과의 데이터 연동 실패 | 표준 API 부재 및 커스터마이징 불가 구조 | iPaaS(통합 플랫폼) 및 웹훅(Webhook) 기반 비동기 연계 설계 | 사내 시스템과 SaaS 간 데이터 무결성 유지 |

## 이렇게 출제된다
