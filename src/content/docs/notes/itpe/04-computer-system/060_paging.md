## 답안 골격
```text
[페이징] ◀━━ 머리: Ⅶ 내 의견 (TLB 미스 완화와 대규모 메모리 접근 효율을 위한 HugePage(2MB/1GB) 선별 적용)
 ┃
 ┣━ Ⅰ 개요 ───── 외부 단편화와 메모리 연속 할당의 한계 극복 → 가상 메모리와 물리 메모리를 고정 크기 블록으로 분할
 ┣━ Ⅱ 특징 ───── 고정 크기 분할(4KB) · 외부 단편화 완전 제거 · 비연속 물리 배치 · 내부 단편화 발생
 ┣━ Ⅲ 구조 ───── 논리 주소 <p, d> + 페이지 테이블(Page Table) + TLB(변환 색인 버퍼) + 물리 프레임(Frame)
 ┣━ Ⅳ 흐름 ───── ① 논리 주소(p, d) 분할 → ② TLB 조회(Hit 시 즉시 변환) → ③ Miss 시 다단계 페이지 테이블 탐색 → ④ 프레임 주소 f + d 결합
 ┣━ Ⅴ 비교 ───── 페이징(Paging) vs 세그먼테이션(Segmentation)
 ┗━ Ⅵ 실무 ───── 다단계 페이징으로 인한 메모리 접근 오버헤드 / TLB 미스 폭증 / 페이지 폴트(Page Fault)
```
- 필수 키워드: 페이징 · 페이지(Page) · 프레임(Frame) · 페이지 테이블 · TLB · 내부 단편화 · 다단계 페이징 · HugePage
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ 페이징 주소 변환 및 TLB 구조도 → Ⅴ 페이징 vs 세그먼테이션 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅳ 다단계 페이지 테이블(4-Level Paging) 탐색 과정 및 Ⅵ TLB 적중률 최적화(HugePage)
- 기출: 131회 3교시 5번 `운영체제 메모리 관리 기법 중 페이징 기법과 세그먼테이션 기법 비교` 서술형 출제

## 한 줄 본질
- 가변 크기로 프로세스를 적재하면 외부 단편화로 메모리가 낭비됨 → 가상 메모리를 고정 크기 '페이지', 물리 메모리를 동일 크기 '프레임'으로 쪼개어 물리 메모리의 빈자리에 비연속적으로 분산 적재 → 외부 단편화 완전 해결 / 마지막 페이지의 내부 단편화 및 주소 변환을 위한 2회 메모리 접근 오버헤드 수반

## 핵심 그림
```text
[ 하드웨어 페이징 주소 변환 및 TLB 캐시 구조 ]

CPU 발생 논리 주소: [ 가상 페이지 번호 (p) | 오프셋 (d) ]
                             │                 │
                             ├───────+         │
                             │       │         │
                             v       v         │
              [ TLB 고속 캐시 조회 ]           │
             +---------+---------+             │
             | Page(p) |Frame(f) |             │
             +---------+---------+             │
             |   0x01  |  0x5A   |             │
             +---------+---------+             │
                             │                 │
              +──────────────┴──────────────+  │
          TLB Hit!                      TLB Miss!
              │                             │
              │                             v
              │              [ 다단계 페이지 테이블 탐색 (DRAM 접근) ]
              │              (CR3 -> PGD -> PUD -> PMD -> PTE)
              │                             │
              v                             v
       [ 프레임 번호 f ] <───────────────────┘
              │
              v (주소 결합: f || d)
       [ 실제 물리 메모리 주소 (DRAM) ] <──────┘
```

## 핵심 용어
- 페이지(Page) / 프레임(Frame): 가상 주소 공간을 나눈 고정 크기 블록을 '페이지', 실제 물리 RAM을 동일 크기로 나눈 블록을 '프레임'(기본 4KB)이라 칭함
- TLB(Translation Lookaside Buffer): 가상 주소(VPN)에서 물리 주소(PFN)로의 변환 결과를 최근 참조 이력 기반으로 보관하는 MMU 내부의 초고속 하드웨어 캐시
- 내부 단편화(Internal Fragmentation): 페이지 크기(예: 4KB)보다 작은 데이터(예: 100바이트)를 할당하여 남은 3996바이트가 낭비되는 현상

## 핵심 통찰
- 페이징의 본질은 '주소 공간의 비연속화'임 → 프로세스 관점에서는 0번지부터 4GB까지 완벽하게 연속된 메모리를 보는 것처럼 속이고, 실제 물리 RAM에서는 조각조각 빈 프레임마다 던져 넣어 외부 단편화를 0으로 만듦
- 페이징은 메모리 접근 속도를 반토막 낼 뻔했음 → 데이터 1개를 읽으려면 페이지 테이블을 읽기 위해 1번, 실제 데이터를 읽기 위해 1번, 총 2번의 DRAM 접근이 필요함 → 이를 1사이클로 되돌려 놓은 구원투수가 바로 'TLB' 캐시임
- 64비트 환경에서는 4단계(4-Level) 페이징이 기본임 → 64비트 전체를 단일 페이지 테이블로 만들면 테이블 크기만 수백만 GB에 달하므로, 트리 구조로 쪼개어 실제로 사용하는 영역의 페이지만 계층적으로 생성함

## 이웃 토픽과 구분
- 페이징 vs 세그먼테이션: 페이징 = 하드웨어 관점, 고정 크기(4KB), 내부 단편화 존재, 물리적 주소 분할 / 세그먼테이션 = 사용자/프로그래머 관점, 가변 크기, 외부 단편화 존재, 논리적 의미 분할

## 문제·원인·대책
- 사례: 131회 기출 및 1TB 메모리를 탑재한 Redis 인메모리 DB에서 메모리 접근 속도 저하 및 CPU 지연
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 수백 GB 대규모 메모리 DB 순회 시 TLB 미스율 급증으로 CPU Stall 발생 | 4KB 기본 페이지 사용 시 페이지 테이블 엔트리(PTE) 수가 수천만 개로 폭증 | 리눅스 HugePage(2MB 또는 1GB 페이지) 설정 활성화 | TLB 엔트리 1개가 커버하는 메모리 범위 500배 확장 |
| Fork 기반 스냅샷 저장 시 순간적인 메모리 사용량 2배 폭증 | 부모와 자식 프로세스가 전체 메모리 페이지를 통째로 복제 시도 | 지연 할당 및 Copy-on-Write(CoW) 기법 적용 | 쓰기 발생 전까지 물리 페이지를 읽기 전용으로 공유 |

## 이렇게 출제된다

## 내 의견
- [워크로드 특성에 맞춘 HugePage 선별 적용 전략] 무조건적인 HugePage(특히 Transparent Huge Pages: THP) 활성화는 단편화와 메모리 낭비를 부르고 백그라운드 압축(khugepaged) 락을 유발함 → 나라면: 범용 웹 서버는 4KB 표준 페이지를 유지하고, 오라클/Redis/PostgreSQL 등 대규모 공유 메모리를 사용하는 DBMS 프로세스에 한해 정적 HugePage(Static HugePage)를 사전 예약 할당하여 TLB 미스 없는 극강의 I/O 성능을 확보
