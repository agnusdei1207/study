## 답안 골격
```text
[좀비 프로세스] ◀━━ 머리: Ⅶ 내 의견 (SIGCHLD 시그널 핸들러 등록과 부모 프로세스 종료를 통한 init(PID 1) 자원 회수)
 ┃
 ┣━ Ⅰ 개요 ───── 자식 프로세스 종료 후 부모의 종료 상태 미회수로 PCB가 잔존하는 디펀트(Defunct) 상태
 ┣━ Ⅱ 특징 ───── 메모리/CPU 자원은 반납 · PID와 프로세스 테이블(PCB) 점유 유지 · kill -9로 강제 종료 불가
 ┣━ Ⅲ 구조 ───── 프로세스 생명주기 + PCB(Process Control Block) 엔트리 + 종료 코드(Exit Status)
 ┣━ Ⅳ 흐름 ───── ① 자식 exit() 호출 → ② 커널 자원 반납 및 PCB 유지(Zombie) → ③ 부모 wait() 호출 누락 → ④ PID 테이블 누적
 ┣━ Ⅴ 비교 ───── 좀비 프로세스(Zombie) vs 고아 프로세스(Orphan) vs 데몬 프로세스(Daemon)
 ┗━ Ⅵ 실무 ───── PID 고갈(PID Exhaustion)로 신규 프로세스 생성 불가 / 컨테이너 환경 PID 1 바인딩 문제
```

## 한 줄 본질
- 실행을 완료하고 `exit()`을 호출한 자식 프로세스의 종료 상태(Exit Code)를 부모 프로세스가 `wait()` 시스템 콜로 수거하지 않아, 메모리는 해제되었으나 프로세스 번호(PID)와 커널 관리 테이블(PCB) 엔트리가 영구 잔존하는 상태 → 다량 누적 시 시스템 PID 번호 고갈로 신규 프로세스 포크 불가 / 부모 프로세스 재설계 및 init 프로세스 입양으로 해결

## 핵심 용어
- PCB(Process Control Block): 프로세스의 상태, PID, 레지스터 값, 열린 파일 디스크립터 등을 보관하는 OS 커널 내부의 핵심 자료구조
- 고아 프로세스(Orphan Process): 부모 프로세스가 자식보다 먼저 종료되어 부모를 잃은 프로세스로, 커널에 의해 즉시 최상위 프로세스(PID 1: systemd/init)에게 입양되어 정상 회수됨
- `wait()` / `waitpid()`: 부모 프로세스가 자식 프로세스의 종료를 대기하고, 자식이 남긴 종료 상태 코드(Exit Status)를 읽어와 PCB를 완전히 소멸시키는 시스템 콜

## 핵심 통찰
- 좀비 프로세스는 CPU나 RAM을 1바이트도 먹지 않음 → 이미 메모리 할당이 해제된 유령 상태이므로 `kill -9 <PID>` 명령어를 날려도 죽일 수 없음(이미 죽어있는 프로세스이기 때문)
- 좀비 프로세스가 초래하는 진정한 재앙은 'PID 고갈(PID Exhaustion)'임 → 리눅스의 최대 PID 개수(기본 32,768개)가 좀비로 가득 차면 시스템 메모리가 아무리 널널해도 `fork(): Cannot allocate memory` 에러가 뜨며 서버 전체가 마비됨
- 도커(Docker) 컨테이너에서 단일 애플리케이션을 PID 1로 띄웠을 때, 해당 앱이 좀비 회수 로직이 없으면 컨테이너 내부가 좀비 프로세스로 가득 차게 됨 → 이를 막기 위해 경량 init 프로세스(Tini)를 PID 1로 두어야 함

## 이웃 토픽과 구분
- 좀비 프로세스 vs 고아 프로세스: 좀비 = 자식은 죽었는데 부모가 살아있어 회수를 안 한 상태(PID 점유, 문제 발생) / 고아 = 부모가 먼저 죽어 자식만 살아있는 상태(PID 1이 자동 입양하여 정상 종료 회수, 문제 없음)

## 문제·원인·대책
- 사례: 140회 기출 노드JS 기반 웹 서버 운영 중 백그라운드 프로세스 누적으로 신규 프로세스 생성 불가 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| `ps -ef` 조회 시 `<defunct>` 프로세스가 수만 개 누적되어 `fork()` 실패 | 부모 프로세스 코드 내 `SIGCHLD` 시그널 핸들러 및 `wait()` 호출 누락 | `SIGCHLD` 시그널 핸들러에 `waitpid(-1, &status, WNOHANG)` 등록 | 자식 종료 즉시 논블로킹으로 PCB 자동 회수 |
| 쿠버네티스 컨테이너 내부에서 좀비 프로세스 누적으로 파드 재기동 빈발 | 일반 Node/Python 앱이 PID 1번을 점유하여 자식 좀비 입양/수거 불가 | 컨테이너 엔트리포인트에 `tini` 또는 `dumb-init`을 PID 1로 배치 | 서브프로세스 종료 시 표준 init 로직으로 좀비 완벽 수거 |

## 내 의견
- [컨테이너 환경의 init 프로세스 플래그 활성화 표준화] 개발자들이 Dockerfile 작성 시 `CMD ["node", "app.js"]` 형태로 앱을 PID 1로 직결하여 좀비 프로세스 누적 및 시그널(SIGTERM) 무시 장애를 빈번히 유발함 → 나라면: 도커 실행 시 `--init` 플래그를 기본 활성화하고, 쿠버네티스 Pod Spec의 `shareProcessNamespace: true` 설정을 활용하여 파드 내 사이드카 컨테이너와 PID 공간을 안전하게 공유하고 좀비를 중앙 수거하도록 인프라 매니페스트 표준화
