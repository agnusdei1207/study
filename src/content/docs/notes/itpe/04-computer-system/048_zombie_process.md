## Ⅰ. 좀비 프로세스(Zombie Process)의 개요

- **개념** : 실행을 정상 또는 비정상적으로 종료하여 자신에게 할당되었던 모든 메모리와 디스크, 파일 디스크립터 등 물리 자원을 운영체제에 반환했음에도 불구하고, 부모 프로세스가 `wait()` 또는 `waitpid()` 시스템 콜을 호출하여 종료 상태 코드(Exit Status)를 회수하지 않아 프로세스 테이블(Process Table)에 엔트리가 여전히 남아 있는 프로세스(상태 코드 'Z' 또는 'defunct').
- **배경 및 필요성** : 유닉스/리눅스 계열 OS는 부모 프로세스가 자식 프로세스의 종료 원인과 반환 코드를 확인할 수 있도록 최소한의 종료 메타데이터를 커널 프로세스 테이블에 유지하는 설계 원칙을 채택하고 있어 발생함.
- **핵심 목적** : 자식 프로세스의 종료 상태 보존 메커니즘 이해, 좀비 누적으로 인한 커널 PID 고갈 방지, init/systemd 기반의 고아 프로세스 회수 파이프라인 수립.

## Ⅱ. 좀비 프로세스(Zombie Process)의 핵심 아키텍처 및 동작 메커니즘

좀비 프로세스는 자식의 `exit()` 호출 후 부모가 `SIGCHLD` 시그널을 처리하여 `wait()`로 수거하기 전까지의 과도기적 상태이며, 부모가 먼저 죽으면 고아(Orphan) 프로세스가 되어 PID 1(init/systemd)에 입양되어 자동 수거됨.

```text
[ 좀비 프로세스 발생 및 수거(Reaping) 메커니즘 ]

[부모 프로세스 (Parent)]                 [자식 프로세스 (Child)]
         │                                       │
         ├────── fork() / exec() ───────────────>│ (정상 실행)
         │                                       │
         │                                       │ 작업 완료
         │                                       ▼ exit(status) 호출
         │                              +-------------------------------+
         │                              | 메모리, 힙, 스택, FD 즉시 반환|
         │ <──── SIGCHLD 시그널 송출 ────| PCB 엔트리만 커널에 잔존      |
         │                              +-------------------------------+
         │                                       │
         │ (부모가 wait() 호출 지연 시)          ▼
         │                              [좀비 상태 (Zombie / defunct)]
         │                              * CPU/메모리 소비 = 0
         │                              * 커널 PID 슬롯 1개 지속 점유!
         │                                       │
         ├────── wait() / waitpid() 호출 ────────┤ (정상 수거: Reaping)
         │                                       ▼
         │                              [프로세스 테이블 엔트리 완전 소멸]
         │
  [부모가 wait 없이 비정상 종료 시]
         │
         ▼
  [고아(Orphan) 프로세스로 전환] ──> [PID 1 (systemd / tini) 입양 후 즉시 wait() 수거]
```

- **자원 반환과 PCB 잔존** : 실행 코드와 데이터 세그먼트는 즉시 해제되지만, 종료 상태(exit code)와 CPU 사용 통계를 담은 태스크 구조체(PCB)는 커널 메모리에 유지.
- **SIGCHLD 시그널** : 자식 프로세스가 종료될 때 커널이 부모 프로세스에게 비동기 시그널(`SIGCHLD`)을 전달하여 자식 수거 기회 부여.
- **wait() / waitpid() 수거** : 부모가 시스템 콜을 호출하여 자식의 종료 코드를 읽어가는 순간 커널이 PID 엔트리를 최종 삭제.
- **고아(Orphan) 프로세스 입양** : 부모가 자식을 수거하지 않고 먼저 종료되면, 커널이 자식의 부모를 루트 프로세스(PID 1)로 변경하고 PID 1이 주기적으로 `wait()`를 실행하여 좀비 제거.

## Ⅲ. 좀비 프로세스(Zombie Process)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 정상 프로세스 (Running/Sleeping) | 좀비 프로세스 (Zombie / defunct) | 고아 프로세스 (Orphan Process) |
|---|---|---|---|
| **프로세스 상태** | 'R' (실행 중) 또는 'S' (대기) | **'Z' (종료되었으나 미수거 상태)** | 'R' 또는 'S' (정상 실행 중) |
| **메모리/CPU 점유**| 텍스트, 힙, 스택, CPU 스케줄링 점유 | **0 (CPU/RAM 전혀 사용 안 함)** | 정상적인 CPU 및 메모리 점유 |
| **프로세스 테이블** | PID 및 모든 자원 엔트리 유지 | **PID 및 최소 PCB 메타데이터만 점유** | 정상 PID 및 PCB 유지 |
| **부모 프로세스** | 정상 부모 존재 | 부모가 살아있으나 wait() 미호출 | **부모가 사망하여 PID 1로 입양됨** |
| **Kill 명령 통제** | `kill -9`로 강제 종료 가능 | **이미 죽었으므로 kill 불가 (무반응)**| `kill -9`로 정상 종료 가능 |

- 좀비 프로세스는 이미 죽은 상태이므로 `kill -9` 명령어가 듣지 않으며, 부모 프로세스를 종료시키거나 부모에게 시그널 핸들러를 수정 배포해야만 제거됨.

## Ⅳ. 좀비 프로세스(Zombie Process)의 주요 한계점 및 해결 방안

- **대량의 좀비 누적으로 인한 커널 PID 공간 고갈** :
  - **한계점** : 좀비가 수만 개 누적되면 리눅스 커널의 최대 프로세스 수 상한(`pid_max: 32768 또는 4194304`)에 도달하여 신규 프로세스 생성(`fork()`) 전면 실패.
  - **해결 방안** : 부모 프로세스를 재기동하거나 `kill`하여 init 프로세스가 입양 수거하도록 유도, `sysctl kernel.pid_max` 모니터링.
- **비동기 SIGCHLD 시그널 유실 및 블로킹 대기 부작용** :
  - **한계점** : 단순 `wait()` 호출 시 자식이 끝날 때까지 부모가 블로킹되거나, 다수의 자식이 동시 종료될 때 시그널 큐 포화로 일부 좀비 방치.
  - **해결 방안** : 논블로킹 루프 `while(waitpid(-1, &status, WNOHANG) > 0)`를 `SIGCHLD` 핸들러 내에 구현하여 모든 종료 자식 일괄 수거.
- **도커/쿠버네티스 컨테이너 환경의 좀비 누적 현상** :
  - **한계점** : 컨테이너 내 메인 앱이 PID 1로 실행될 때 표준 init 역할을 하지 못해 하위 자식 프로세스가 고아 및 좀비로 영구 잔존.
  - **해결 방안** : 컨테이너 엔트리포인트에 경량 init 시스템(tini, dumb-init)을 PID 1로 채택하거나 Docker의 `--init` 플래그 활성화.

## Ⅴ. 좀비 프로세스(Zombie Process) 적용 및 발전을 위한 기술사적 제언

- **컨테이너 이미지 빌드 시 tini 엔트리포인트 표준화** : 자바나 노드 애플리케이션을 단독 PID 1로 띄우지 않고 고아 수거를 전담하는 init 바이너리를 래핑하는 보안 베이스 이미지 구축.
- **APM 및 인프라 모니터링에 좀비 프로세스 카운트 임계치 등록** : 서버별 좀비 프로세스 수가 10개 이상 지속 감지될 경우 데드락 및 애플리케이션 버그 경보 발령 파이프라인 수립.
- **현대 언어의 프로세스 라이프사이클 관리 패턴 정착** : Python `subprocess`, Node.js `child_process` 사용 시 반드시 명시적 `wait()` 또는 비동기 리스너를 결합하는 코딩 표준 수립 권장.
