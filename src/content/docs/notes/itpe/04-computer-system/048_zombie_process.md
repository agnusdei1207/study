## Ⅰ. 좀비 프로세스의 개요

- 핵심 요약 : **좀비 프로세스** (Zombie Process)는 실행을 끝냈지만 부모가 종료 상태를 수거하지 않아 프로세스 테이블 항목이 남아 있는 프로세스.
- 개념 : 정상 또는 비정상으로 종료하면서 메모리, 디스크, 파일 디스크립터 같은 자원은 운영체제에 모두 반환했으나, 부모 프로세스가 `wait()` 또는 `waitpid()` 시스템 콜로 **종료 상태** (Exit Status)를 회수하지 않아 **프로세스 테이블** (Process Table)에 항목이 남은 상태. 상태 표시는 'Z' 또는 'defunct'로 나타난다.
- 배경 및 필요성 : 유닉스와 리눅스 계열 운영체제는 부모가 자식의 종료 원인과 반환 코드를 확인할 수 있도록 최소한의 종료 정보를 커널에 남기는 설계를 택했고, 이 설계 때문에 수거되지 않은 항목이 생긴다.
- 주요 목적 : 자식 프로세스의 종료 상태 보존 메커니즘을 이해하고, 좀비 누적으로 커널의 **프로세스 식별자** (PID, Process Identifier) 고갈을 막으며, init 또는 systemd가 고아 프로세스를 수거하는 흐름을 확인하는 것.

## Ⅱ. 좀비 프로세스의 특징 및 장점

- 핵심 요약 : 자원은 즉시 반환하고 종료 정보만 남기며, 부모의 수거, SIGCHLD 통지, 고아 입양이 정리 경로를 이루는 구조.

1. **자원 반환과 PCB 잔존** : 코드와 데이터 세그먼트, 파일 디스크립터는 즉시 해제되고, 종료 코드와 CPU 사용 통계를 담은 **프로세스 제어 블록** (PCB, Process Control Block)만 커널 메모리에 남음 → 자원 소비는 사실상 0.
2. **SIGCHLD 시그널** : 자식이 종료되면 커널이 부모에게 `SIGCHLD` 시그널을 보내 수거 기회를 줌 → 비동기 통지 방식.
3. **wait()·waitpid() 수거** : 부모가 시스템 콜로 종료 코드를 읽어 가는 순간 커널이 PID 항목을 삭제 → 정리 완료.
4. **고아 프로세스** (Orphan Process) 입양 : 부모가 수거하기 전에 먼저 종료하면 커널이 자식의 부모를 PID 1로 바꾸고, PID 1이 주기적으로 `wait()`를 호출해 좀비를 제거 → 정리 책임의 이전.

## Ⅲ. 좀비 프로세스의 구조 및 동작 메커니즘

- 핵심 요약 : 자식의 exit 호출부터 부모의 wait 호출까지의 과도기가 좀비 상태이며, 부모가 먼저 사라지면 고아가 되어 PID 1이 수거하는 구조.

```text
[ 좀비 발생과 수거 흐름 ]

자식 프로세스가 exit() 호출
      ↓
메모리·파일 디스크립터 반환, PCB만 잔존
      ↓
커널이 부모에게 SIGCHLD 전달
      ↓
부모가 wait() 호출 전 → 좀비 상태 유지
      ↓
부모가 wait() 호출 → 항목 삭제 (수거)
```

```text
[ 부모가 먼저 종료한 경우 ]

부모 프로세스 종료 (wait 없음)
      ↓
자식은 고아 프로세스로 전환
      ↓
PID 1 (init/systemd)에 입양
      ↓
PID 1이 wait()로 수거 → 좀비 제거
```

- 좀비는 이미 끝난 프로세스이므로, 정리는 자식이 아니라 부모의 수거 동작이나 PID 1의 입양 경로에서 이루어진다.

## Ⅳ. 좀비 프로세스의 비교

- 핵심 요약 : 정상, 좀비, 고아 프로세스는 상태 표시, 자원 점유, 부모 관계, 종료 명령 가능 여부에서 뚜렷이 구분된다.

| 비교 항목 | 정상 프로세스 (Running/Sleeping) | 좀비 프로세스 (Zombie/defunct) | 고아 프로세스 (Orphan Process) |
| --- | --- | --- | --- |
| 프로세스 상태 | 'R'(실행) 또는 'S'(대기) | 'Z'(종료 후 미수거) | 'R' 또는 'S'(정상 실행) |
| 메모리·CPU 점유 | 텍스트, 힙, 스택을 사용하고 스케줄링 대상 | 없음 | 정상적으로 사용 |
| 프로세스 테이블 | PID와 모든 자원 항목 유지 | PID와 최소한의 PCB 정보만 점유 | 정상 항목 유지 |
| 부모 프로세스 | 정상 부모 존재 | 부모가 살아 있으나 wait()를 호출하지 않음 | 부모가 종료되어 PID 1에 입양됨 |
| kill 명령 | `kill -9`로 강제 종료 가능 | 이미 끝난 상태라 kill에 반응하지 않음 | `kill -9`로 종료 가능 |

- 좀비에는 `kill -9`가 듣지 않으므로, 제거하려면 부모 프로세스를 종료시키거나 부모 코드의 수거 로직을 고쳐야 한다.

## Ⅴ. 좀비 프로세스의 한계와 방안

- 핵심 요약 : 프로세스 식별자 고갈, 시그널 유실과 블로킹, 컨테이너 환경의 PID 1 부재를 부모 재기동, 논블로킹 수거, 경량 init으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 대량 좀비에 따른 **PID 고갈** | 좀비가 많이 쌓이면 커널의 최대 프로세스 수 상한(pid_max)에 닿아 `fork()`가 실패함 | 부모 프로세스를 재기동해 init이 입양·수거하도록 유도, pid_max 설정과 좀비 수 모니터링 | 좀비 개수, PID 사용률 |
| **SIGCHLD** 유실과 블로킹 | 단순 `wait()`는 자식이 끝날 때까지 부모를 막고, 다수 자식이 동시에 끝나면 시그널이 누락되어 일부가 방치됨 | SIGCHLD 핸들러 안에서 `WNOHANG` 옵션의 `waitpid`를 반복 호출해 종료된 자식을 일괄 수거 | 미수거 항목 수, 수거 지연 시간 |
| 컨테이너 환경의 **PID 1 부재** | 애플리케이션이 PID 1로 뜨면 init 역할을 하지 못해 자식 프로세스가 고아와 좀비로 남음 | tini나 dumb-init을 PID 1로 두는 엔트리포인트 구성, Docker의 `--init` 옵션 사용 | 컨테이너별 좀비 수 |

## Ⅵ. 좀비 프로세스의 적용 제언

- 핵심 요약 : 플랫폼 기본값으로 PID 1 정책을 고정하고, 좀비 수를 경보 지표로 삼으며, 언어 런타임의 하위 프로세스 관리 규약을 세우는 것이 재발을 막는다.

1. 컨테이너 플랫폼의 기본 정책으로 PID 1 역할을 init 프로세스가 맡도록 고정해, 개별 팀이 빠뜨리는 일이 없도록 해야 한다.
2. **응용 성능 관리** (APM, Application Performance Management)과 인프라 모니터링에 좀비 프로세스 수를 등록하고, 지속적으로 증가하는 추세를 경보 기준으로 삼는 것이 현실적이다.
3. Python `subprocess`, Node.js `child_process`처럼 하위 프로세스를 띄우는 라이브러리를 쓸 때는 종료 대기 호출을 명시적으로 짝지어 쓰는 코딩 규약을 팀 표준으로 정착시켜야 한다.

## Ⅶ. 결론

- 핵심 요약 : 좀비 프로세스는 CPU와 메모리를 쓰지 않아도 PID 슬롯을 점유하므로, 부모의 wait 수거나 PID 1 입양으로 정리해야 하는 상태.
- 시사점 : 좀비는 코드 한 줄의 누락에서 생기는 문제이므로, 프로세스 정리 책임을 플랫폼 기본값과 모니터링으로 묶어 두는 것이 재발을 막는 가장 확실한 방법이다.
