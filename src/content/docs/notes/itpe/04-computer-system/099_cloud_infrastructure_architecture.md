## 연관 키워드

- 클라우드 인프라 아키텍처, SDDC(Software-Defined Data Center), 가용 영역(Availability Zone)
- 리전(Region), 오토스케일링(Auto Scaling), 로드밸런싱(Load Balancing), Multi-AZ
- Well-Architected Framework, IaC(Infrastructure as Code), GitOps, 구성 드리프트
- 하이브리드 클라우드, 멀티 클라우드, 재해복구(DR, Disaster Recovery), FinOps

## Ⅰ. 클라우드 인프라 아키텍처의 개요

- 핵심 요약 : 물리 자원을 소프트웨어로 추상화한 데이터센터 위에서 가용성, 탄력성, 비용 효율을 동시에 달성하도록 자원을 배치하고 운영하는 설계 체계.
- 개념 : 컴퓨팅, 스토리지, 네트워크를 소프트웨어 정의 기술로 추상화·자동화하는 **SDDC** (Software-Defined Data Center, 소프트웨어 정의 데이터센터)를 기반으로 리전과 가용 영역 단위로 자원을 배치하는 설계 방법론.
- 배경 및 필요성 : 온프레미스는 조달 리드타임과 선투자 부담, 급증 트래픽 대응의 한계를 안고 있어 자원을 코드로 다루고 필요 만큼만 쓰는 구조로의 전환이 필요.
- 주요 목적 : 서비스 가용성 확보, 수요 변동에 따른 탄력적 확장, 사용량 기반 비용 최적화, 재해복구 대응력 확보.

## Ⅱ. 클라우드 인프라 아키텍처의 특징 및 장점

- 핵심 요약 : 추상화, 분산 배치, 자동 확장, 코드 기반 운영의 결합이 민첩한 변경과 장애 격리, 비용 절감으로 이어지는 구조.

1. 소프트웨어 정의 추상화 : 하드웨어를 API(Application Programming Interface)로 제어 → 조달 대기 없이 분 단위 프로비저닝 효과.
2. **가용 영역** (Availability Zone) 분산 배치 : 독립된 전력과 네트워크를 가진 시설에 자원을 분산 → 단일 시설 장애가 서비스 전면 중단으로 번지지 않는 효과.
3. **오토스케일링** (Auto Scaling) : 지표 임계치에 따라 인스턴스 수를 자동 조정 → 수요 급증 대응과 유휴 자원 축소의 비용 효과.
4. 코드 기반 프로비저닝 : 인프라 정의를 코드로 관리하는 **IaC** (Infrastructure as Code) → 환경 재현과 변경 이력 추적이 가능해지는 효과.
5. 설계 품질 기준 프레임 : **Well-Architected Framework**의 운영 우수성, 보안, 안정성, 성능 효율성, 비용 최적화, 지속 가능성 여섯 기둥 → 품질을 항목별로 점검하는 효과.

## Ⅲ. 클라우드 인프라 아키텍처의 구조 (흐름)

- 핵심 요약 : 리전-가용 영역-데이터센터의 물리 계층 위에 가상화 계층이 놓이고 요청은 로드밸런서를 거쳐 여러 가용 영역으로 분산되는 이중 구조.

```text
[ 물리 인프라 계층 ]

리전 (Region) : 지리적 배치 단위
   ↓
가용 영역 (AZ) : 독립 전력·네트워크
   ↓
데이터센터 : 물리 서버와 랙
   ↓
가상화 계층 : 자원 풀(Pool)화
```

```text
[ 요청 처리와 장애 격리 흐름 ]

사용자 요청 도착
   ↓
로드밸런서가 여러 AZ에 분배
   ↓
오토스케일링으로 용량 조정
   ↓
장애 AZ 이탈 시 잔여 AZ 유지
```

- 리전(Region)은 데이터 주권과 지연 시간 요건을 결정하는 배치 단위이고, Multi-AZ 구성은 가용성 요건의 기본 패턴이 됨.
- 재해복구 전략은 백업·복원, 파일럿 라이트, 웜 스탠바이, 액티브-액티브의 단계 가운데 복구 목표와 비용의 균형으로 선택함.

## Ⅳ. 클라우드 배치 모델의 비교

- 핵심 요약 : 퍼블릭, 프라이빗, 하이브리드, 멀티 클라우드는 확장성과 통제력, 운영 복잡도의 균형점이 서로 다름.

| 비교 축 | 퍼블릭 | 프라이빗 | 하이브리드 | 멀티 클라우드 |
| :--- | :--- | :--- | :--- | :--- |
| 인프라 소유 | CSP 제공 | 기업 자체 구축 | 내부와 퍼블릭 결합 | 복수 CSP 병용 |
| 확장성 | 탄력적 확장 용이 | 물리 도입 속도 제약 | 초과 수요를 퍼블릭으로 | CSP별 강점 활용 |
| 데이터 통제 | 공동 책임 모델 | 직접 통제 | 핵심 데이터 내부 보관 | 지역 요건별 배치 |
| 운영 복잡도 | 낮음에서 중간 | 높음 | 높음 (연계 관리) | 매우 높음 (도구 분산) |
| 적합 용도 | 웹 서비스·변동 수요 | 규제·핵심 데이터 | 절충 배치 | 종속성 분산 |

- 선택 기준 :
  1. 변동 수요와 빠른 출시가 우선이면 퍼블릭.
  2. 규제 대상 데이터면 프라이빗 또는 하이브리드.
  3. CSP 장애와 종속 위험을 낮추려면 멀티 클라우드.

## Ⅴ. 클라우드 인프라 아키텍처의 한계와 방안

- 핵심 요약 : 비용 폭증, 단일 리전 장애, 온프레미스 연계 지연을 비용 거버넌스, 다중 리전 구성, 전용 회선 이중화로 일대일 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 비용 폭증 | 유휴 자원 방치, 송신(Egress) 요금 누적 → 예산 초과 | FinOps 체계 도입, 예산 알람과 미사용 자원 정리 자동화 | 예산 대비 실사용 비율 |
| 단일 리전 장애 | 리전 전체 중단이나 CSP 백본 장애 → 서비스 정지 | 다중 리전 DR 구성과 글로벌 로드밸런싱 절체 | 복구 목표 시간 준수율 |
| 온프레 연계 지연 | 인터넷 VPN(Virtual Private Network) 구간의 지연·변동 → 하이브리드 트랜잭션 실패 | 전용 사설 회선 이중화와 SD-WAN(Software-Defined Wide Area Network) 최적화 | 구간 왕복 지연 시간 |

## Ⅵ. 클라우드 인프라 아키텍처에 대한 기술사적 제언

- 핵심 요약 : 인프라 변경을 코드와 자동화 파이프라인으로 일원화하고 데이터 성격별 배치 기준을 문서화하는 방향.
- 조직 : 클라우드 거버넌스 조직이 IaC 코드 리뷰와 변경 승인 절차를 표준으로 운영.
- 수단 : 플랫폼 운영 조직이 GitOps 방식 배포 자동화로 수작업 설정에 따른 구성 드리프트(configuration drift)를 억제.
- 정책 : 데이터 관리 조직이 규제 대상 데이터와 일반 서비스 데이터의 배치 기준을 문서로 정해 리전 선택을 표준화.

## Ⅶ. 결론

- 핵심 요약 : 클라우드 인프라 아키텍처는 소프트웨어 정의 추상화와 다층 분산 배치로 가용성, 탄력성, 비용 효율을 함께 추구하는 설계 체계.
- 시사점 : 설계의 완성도는 장애와 비용을 측정 가능한 지표로 관리하는 운영 체계에서 결정됨.
