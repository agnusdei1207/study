## 연관 키워드

- 서비스형 플랫폼, PaaS, 빌드팩, 서비스 브로커, 블루-그린 배포, 플랫폼 오토스케일링, FaaS
- 벤더 종속, 12-Factor App, IDP, OCI, CVE, CI/CD

## Ⅰ. 서비스형 플랫폼(PaaS)의 개요

- 핵심 요약 : **서비스형 플랫폼** (PaaS, Platform as a Service)은 런타임, 데이터베이스, 미들웨어, 배포 파이프라인을 제공하여 개발자가 애플리케이션과 데이터에만 집중하게 하는 클라우드 서비스 모델.
- 개념 : 개발자가 서버 하드웨어, 네트워크, 운영체제(OS, Operating System), 런타임 환경의 관리 없이 소스 코드 작성과 데이터 설계에 집중하도록, 실행 런타임, 데이터베이스, 미들웨어, 지속적 통합과 지속적 배포(CI/CD, Continuous Integration/Continuous Delivery) 파이프라인을 클라우드 플랫폼 형태로 제공하는 모델.
- 배경 및 필요성 : 서비스형 인프라(IaaS, Infrastructure as a Service) 환경에서는 가상 머신의 OS 패치, 웹 서버 튜닝, 오토스케일링 스크립트 작성 같은 작업이 비즈니스 로직 개발 시간을 잠식하는 비용으로 쌓이므로, 개발자 경험(DX, Developer Experience)과 출시 기간 단축을 위한 플랫폼 계층이 필요해짐.
- 핵심 목적 : 인프라 프로비저닝 부담의 제거, 빌드팩 기반의 자동 컨테이너화와 배포, 플랫폼 수준의 무중단 배포와 확장 제공.

## Ⅱ. 서비스형 플랫폼(PaaS)의 특징 및 장점

- 핵심 요약 : 빌드, 바인딩, 배포, 확장을 플랫폼이 맡아 개발자의 인프라 작업을 줄이는 구조.

1. **클라우드 네이티브 빌드팩** (Cloud Native Buildpacks) : 소스 코드를 분석해 언어 런타임과 의존 라이브러리를 결합한 컨테이너 이미지를 자동 생성 → Dockerfile 작성 부담 감소와 보안 패치 반영의 자동화.
2. **서비스 브로커** (Service Broker) : 데이터베이스, 캐시, 메시지 큐 인스턴스를 플랫폼에서 생성하고 접속 정보를 환경 변수로 자동 바인딩 → 연결 설정 작업 감소.
3. **블루-그린 배포** (Blue-Green Deployment) : 라우팅 계층이 트래픽 전환과 롤링 배포를 제어 → 무중단 배포와 원터치 롤백.
4. **플랫폼 오토스케일링** (Autoscaling) : 요청량과 응답 지연을 측정해 애플리케이션 인스턴스를 자동으로 늘리고 줄임 → 개발자 개입 없는 수평 확장.

## Ⅲ. 서비스형 플랫폼(PaaS)의 구조 및 동작 메커니즘

- 핵심 요약 : 소스 푸시 이후 빌드팩, 서비스 브로커, 라우팅과 오토스케일러가 순서대로 작동하고, 데이터 계층은 관리형 백킹 서비스가 담당하는 구조.
- 플랫폼 컨트롤러(Cloud Foundry, OpenShift, Heroku 등)가 빌드와 바인딩, 라우팅을 맡고, 실제 데이터 계층은 플랫폼이 관리하는 백킹 서비스로 분리됨.

```text
[ PaaS 배포 라이프사이클 ]

소스 코드 푸시 (git push)
   ↓
빌드팩 (언어 감지·의존성 설치·이미지 생성)
   ↓
서비스 브로커 (DB·캐시 바인딩)
   ↓
라우팅·오토스케일러 (트래픽 전환)
   ↓
애플리케이션 인스턴스 (수평 확장)
```

```text
[ 플랫폼 구성 계층 ]

개발자 (소스·설정 관리)
   ↓
플랫폼 컨트롤러 (빌드·라우팅·확장)
   ↓
애플리케이션 인스턴스 (관리형 런타임)
   ↓
관리형 백킹 서비스 (DB·메시지 큐·검색)
```

## Ⅳ. 서비스형 플랫폼(PaaS)의 비교

- 핵심 요약 : IaaS에서 PaaS, FaaS(Function as a Service)로 갈수록 개발자의 관리 범위는 줄고 생산성은 높아지지만, 제어 유연성과 이식성은 낮아짐.

| 비교 축 | IaaS(Infrastructure as a Service) | PaaS | FaaS(Function as a Service, 서버리스) |
| --- | --- | --- | --- |
| 개발자 관리 범위 | OS, 미들웨어, 런타임, 앱 코드 | 애플리케이션 코드와 데이터 | 단일 함수 코드 |
| 배포 단위 | 가상 머신 이미지 | 소스 푸시 또는 컨테이너 | 이벤트 기반 함수 단위 |
| 개발 생산성 | 서버 구축과 패치 부담으로 낮음 | 개발 집중 구조로 높음 | 이벤트 처리 중심으로 높음 |
| 시스템 제어 유연성 | 커널과 네트워크까지 자유 | 플랫폼 규약 내에서 제한 | 상태 없는 실행으로 매우 제한 |
| 벤더 종속성 | 표준 가상 머신으로 이전 용이 | 플랫폼 고유 설정으로 중간에서 높음 | 이벤트 트리거가 클라우드 서비스 제공자(CSP, Cloud Service Provider)에 묶여 높음 |

- 선택 기준 : 개발 속도가 우선이고 플랫폼 규약을 수용할 수 있으면 PaaS, 커널과 네트워크 수준의 제어가 필요하면 IaaS를 택함.
- 쿠버네티스(Kubernetes) 기반의 개방형 PaaS는 특정 플랫폼 종속을 낮추는 대안으로 검토됨.

## Ⅴ. 서비스형 플랫폼(PaaS)의 한계와 방안

- 핵심 요약 : 플랫폼 종속, 커널 수준 제어 제약, 관리 프리미엄 비용을 표준 컨테이너, 하이브리드 구성, 내부 플랫폼으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **벤더 종속** (Lock-in) | 플랫폼 고유 환경 변수와 배포 규격에 앱이 결합되어 타 클라우드 이전 시 리팩토링 비용 발생 | 12-Factor App 원칙 준수, OCI(Open Container Initiative) 표준 컨테이너 이미지 기반 배포 | 플랫폼 고유 설정 의존도 |
| 커널 수준 제어 제약 | C/C++ 네이티브 확장 모듈, 특수 드라이버 설치가 막혀 특수 워크로드 구동 불가 | 커스텀 컨테이너 이미지를 지정할 수 있는 하이브리드 PaaS 모드 활용 | 커스텀 이미지 사용 비율 |
| 관리 프리미엄 비용 | 대규모 장기 운영 시 서비스 마진이 붙어 IaaS 대비 비용 증가 | 기저 부하는 사내 쿠버네티스 기반 **내부 개발자 플랫폼** (IDP, Internal Developer Platform)으로 내재화하고, 변동성 부하만 상용 PaaS 사용 | 요청당 단위 비용, 기저 부하 비율 |

## Ⅵ. 서비스형 플랫폼(PaaS)의 기술사적 제언

- 핵심 요약 : 플랫폼 조직, 설계 심사, 보안 자동화를 묶어 PaaS를 개발자가 자율적으로 쓰되 통제가 유지되는 운영 모델로 정착.

1. 플랫폼 엔지니어링 조직 : 인프라 전문 인력을 플랫폼 팀으로 편성하여 개발팀이 셀프 서비스로 자원을 쓰되 표준 안에서 움직이도록 운영 모델을 세우는 것이 바람직함.
2. 설계 심사 기준 : 신규 서비스의 설계 심사에 12-Factor 원칙 충족 여부를 포함하여, 플랫폼 교체 가능성을 설계 단계에서 확보함.
3. 보안 거버넌스 자동화 : 빌드팩 단계에서 라이선스와 공통 취약점 식별자(CVE, Common Vulnerabilities and Exposures) 검증을 수행하고 기준을 넘는 이미지의 배포를 차단하는 체계가 필요함.

## Ⅶ. 결론

- 핵심 요약 : PaaS는 런타임, 데이터베이스, 배포 파이프라인을 플랫폼으로 제공하여 개발 생산성을 높이는 모델이며, 종속과 제어 한계의 관리가 전제임.
- 시사점 : 생산성의 이득은 플랫폼 규약의 범위 안에서 발생하므로, 이식성과 비용을 측정하는 기준을 함께 운영하는 것이 PaaS 선택의 조건임.
