## 30초 인출

- 본질: 서버 인프라 프로비저닝과 웹/WAS 미들웨어 셋업에 소요되는 시간과 운영 비용
- 메커니즘: OS·런타임·데이터베이스 등 실행 환경 일체를 관리형 플랫폼으로 추상화하여 제공

## 핵심 용어

- 빌드팩(Buildpacks): 도커파일(Dockerfile) 없이도 소스 코드를 분석하여 언어 런타임과 의존성을 자동으로 감지하고 프로덕션용 컨테이너 이미지를 빌드하는 표준 도구
- K-PaaS(구 파스-타, PaaS-TA): 공공 클라우드 전환 시 특정 해외 CSP에 대한 기술 종속을 방지하기 위해 과기정통부와 NIA가 개발한 오픈소스 기반 공공 PaaS 플랫폼
- 벤더 락인(Vendor Lock-in): 특정 클라우드 서비스 제공자의 독점적 API나 런타임 기능에 강하게 결합되어 다른 플랫폼으로 이전할 때 막대한 전환 비용이 발생하는 현상

## 1교시 10점 답안

### Ⅰ. 정의·목적

- 정의: PaaS은/는 OS·런타임·데이터베이스 등 실행 환경 일체를 관리형 플랫폼으로 추상화하여 제공 방식이다.

                         +────────────┬────────────+
                                      │
             +────────────────────────┴────────────────────────+

             │   - Service Mesh (mTLS / Ingress 라우팅)        │
             │   - Managed DB / Message Queue 연결             │

### Ⅱ. 핵심 특성

- PaaS의 본질은 '개발자의 인프라 망각'임 → 개발자가 CPU 코어 수, 서브넷 대역, Nginx 프록시 설정을 고민하지 않고 오직 비즈니스 로직 코드 작성에만 집중할 수 있게 하여 출시 시간(Time-to-Market)을 수개월에서 수일로 단축함
- 유연성과 편리성은 완전한 반비례 관계임 → 플랫폼이 알아서 관리해 주는 만큼, 특수한 OS 커널 모듈을 올리거나 비표준 C 라이브러리를 직접 링크해야 하는 고성능/레거시 시스템은 PaaS에 올라가지 못함
- 오픈 표준(Open Container Initiative)을 타지 않는 PaaS는 독이 됨 → 클라우드 초기의 독점적 PaaS는 이전이 불가능한 족쇄가 되었으나, 현대 PaaS는 쿠버네티스와 OCI 컨테이너를 기반으로 표준화되어 이식성이 대폭 개선됨

### Ⅲ. 관련 개념과 구분

- PaaS vs FaaS(서버리스): PaaS = 항상 기동되는 상시 프로세스/컨테이너를 기반으로 지속적 웹/WAS 트래픽을 처리(월정액/사용량) / FaaS = 이벤트 발생 시에만 컨테이너를 밀리초 단위로 띄워 단발 함수를 실행하고 즉시 종료(호출 횟수당 과금)

### Ⅳ. 적용 문제와 대응

- 사례: 122회 기출 및 해외 특정 퍼블릭 PaaS를 사용하던 스타트업이 트래픽 증가 후 비용 폭증과 플랫폼 기능 제약으로 마이그레이션을 시도했으나 6개월간 이전 실패
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 상용 PaaS 런타임 전용 SDK 의존으로 타 클라우드 이전 불가 | 독점적 PaaS의 데이터베이스 바인딩 및 파일 API 직접 호출 | 표준 OCI 컨테이너 및 12-Factor App 원칙 기반 설계 | 인프라 독립적인 멀티 클라우드 이식성 확보 |
| 피크 트래픽 유입 시 PaaS 인스턴스 기동 지연으로 서비스 장애 | 무거운 모놀리식 애플리케이션의 콜드 스타트(Cold Start) 지연 | 스프링 네이티브(GraalVM AOT) 컴파일 및 파드 사전 워밍(Pre-warming) | 기동 시간을 초 단위에서 수십 밀리초 단위로 단축 |
