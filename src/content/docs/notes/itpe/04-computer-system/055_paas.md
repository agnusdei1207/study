## 연관 키워드

- 서비스형 플랫폼, PaaS, 빌드팩, 서비스 브로커, 관리형 런타임, 블루-그린 배포, 오토스케일링
- 벤더 종속, 12-Factor App, OCI, 내부 개발자 플랫폼, IDP

## Ⅰ. 서비스형 플랫폼(PaaS)의 개요

- 핵심 요약 : 런타임·데이터베이스·배포 파이프라인을 플랫폼으로 제공하여 개발자가 애플리케이션과 데이터에만 집중하게 하는 클라우드 서비스 모델.
- 개념 : 서버와 네트워크, 운영체제, 실행 환경의 구축·운영을 클라우드가 대신 맡고, 소스 코드 배포만으로 서비스가 실행되도록 런타임과 미들웨어, 배포 체계를 제공하는 **서비스형 플랫폼** (PaaS, Platform as a Service) 모델.
- 배경 및 필요성 : 서비스형 인프라(IaaS, Infrastructure as a Service) 환경의 운영체제 패치와 웹 서버 튜닝, 확장 스크립트 작성 같은 운영 작업이 개발 시간을 잠식 → 개발자 경험과 출시 기간 단축을 위한 플랫폼 계층의 필요.
- 주요 목적 : 인프라 운영 부담의 제거, 코드 푸시 기반의 자동 배포, 플랫폼 수준의 무중단 배포와 자동 확장 제공.

## Ⅱ. 서비스형 플랫폼(PaaS)의 특징 및 장점

- 핵심 요약 : 빌드 자동화, 서비스 바인딩, 무중단 배포, 자동 확장이 개발자의 인프라 작업을 줄이는 구조.

1. **빌드팩** (Buildpack) : 소스 코드를 분석해 언어 런타임과 의존 라이브러리를 결합한 컨테이너 이미지를 자동 생성 → Dockerfile 작성 부담 제거와 보안 패치 반영의 자동화.
2. **서비스 브로커** (Service Broker) : 데이터베이스·캐시·메시지 큐 인스턴스를 생성하고 접속 정보를 환경 변수로 자동 바인딩 → 연결 설정 작업의 감소.
3. **블루-그린 배포** (Blue-Green Deployment) : 동일 구성의 두 환경 사이에서 라우팅 전환으로 배포 → 무중단 배포와 즉시 롤백.
4. **오토스케일링** (Autoscaling) : 요청량과 응답 지연 측정에 따라 인스턴스 수를 자동 조정 → 개발자 개입 없는 수평 확장.
5. **관리형 런타임** (Managed Runtime) : 런타임 패치와 로그 수집, 장애 감시를 플랫폼이 담당 → 운영 인력 투입의 최소화.

## Ⅲ. 서비스형 플랫폼(PaaS)의 구조 (흐름)

- 핵심 요약 : 소스 푸시 이후 빌드, 바인딩, 배포, 확장의 단계가 플랫폼 컨트롤러에 의해 순서대로 자동 수행되는 구조.
- 플랫폼 컨트롤러 : 빌드와 라우팅, 확장을 조율하는 제어 구성요소이며, 데이터 계층은 관리형 백킹 서비스가 담당함.

```text
[ PaaS 배포 라이프사이클 ]

소스 코드 푸시 (git push)
   ↓
빌드팩 (언어 감지·이미지 생성)
   ↓
서비스 브로커 (DB·캐시 바인딩)
   ↓
라우팅 전환 (블루-그린 배포)
   ↓
오토스케일링 (인스턴스 수 조정)
```

```text
[ 플랫폼 구성 계층 ]

개발자 (소스와 설정)
   ↓
플랫폼 컨트롤러 (빌드·라우팅·확장)
   ↓
관리형 런타임 (애플리케이션 실행)
   ↓
백킹 서비스 (DB·메시지 큐·검색)
```

## Ⅳ. IaaS·PaaS·FaaS의 비교

- 핵심 요약 : IaaS에서 PaaS, FaaS(Function as a Service)로 갈수록 관리 범위는 줄고 생산성은 높아지지만, 제어 유연성과 이식성은 낮아짐.

| 비교 축 | IaaS | PaaS | FaaS |
| --- | --- | --- | --- |
| 관리 범위 | OS·미들웨어·런타임·코드 | 애플리케이션 코드와 데이터 | 단일 함수 코드 |
| 배포 단위 | 가상 머신 이미지 | 소스 푸시, 컨테이너 | 이벤트 기반 함수 |
| 개발 생산성 | 운영 부담으로 낮음 | 개발 집중 구조로 높음 | 이벤트 처리 중심으로 높음 |
| 제어 유연성 | 커널 수준까지 자유 | 플랫폼 규약 내 제한 | 상태 없는 실행으로 제한 |
| 이식성 | 표준 이미지로 높음 | 플랫폼 설정 의존으로 중간 | 트리거·서비스 의존으로 낮음 |

- 선택 기준 : 출시 속도가 우선하고 플랫폼 규약 수용이 가능하면 PaaS, 커널·네트워크 제어가 필요하면 IaaS, 비정기 이벤트 처리 중심이면 FaaS를 기준으로 삼음.

## Ⅴ. 서비스형 플랫폼(PaaS)의 한계와 방안

- 핵심 요약 : 벤더 종속, 커널 수준 제약, 관리 프리미엄 비용을 표준 컨테이너, 하이브리드 구성, 내부 플랫폼으로 일대일 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **벤더 종속** (Vendor Lock-in) | 플랫폼 고유 설정에 앱 결합 → 이식 시 리팩토링 비용 발생 | **12-Factor App** (환경 변수 설정, 프로세스 무상태 등 클라우드 앱 설계 12원칙) 준수, **OCI** (Open Container Initiative) 표준 이미지 배포 | 플랫폼 고유 설정 의존도 |
| 커널 수준 제어 제약 | 네이티브 모듈·특수 드라이버 설치 불가 → 특수 워크로드 구동 차단 | 커스텀 컨테이너 이미지를 허용하는 하이브리드 모드 활용 | 커스텀 이미지 사용 비율 |
| 관리 프리미엄 비용 | 서비스 마진으로 대규모 장기 운영 시 IaaS 대비 비용 증가 | 기저 부하는 사내 플랫폼으로 내재화, 변동 부하만 상용 PaaS 사용 | 요청당 단위 비용 |

## Ⅵ. 서비스형 플랫폼(PaaS)에 대한 기술사적 제언

- 핵심 요약 : 플랫폼 조직, 설계 심사, 보안 자동화의 세 축으로 PaaS를 자율성과 통제가 공존하는 운영 모델로 정착시키는 방향.

1. 플랫폼 엔지니어링 조직 : 인프라 인력으로 **내부 개발자 플랫폼** (IDP, Internal Developer Platform)을 구축하여 개발팀이 셀프 서비스로 자원을 쓰게 하는 운영 모델이 바람직함.
2. 설계 심사 제도 : 아키텍처 심사에 12-Factor 원칙 충족 여부를 포함하여 플랫폼 교체 가능성을 설계 단계에서 확보하는 절차가 필요함.
3. 보안 자동화 체계 : 빌드 단계에서 라이선스와 취약점 검증을 수행하고 기준 초과 이미지의 배포를 차단하는 파이프라인이 유효함.

## Ⅶ. 결론

- 핵심 요약 : PaaS는 런타임과 배포 체계를 플랫폼으로 제공해 개발 생산성을 높이는 서비스 모델.
- 생산성 이득은 플랫폼 규약의 범위 안에서 발생하므로 이식성과 비용 기준의 병행 운영이 선택의 조건임.
