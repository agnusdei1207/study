## Ⅰ. PaaS(Platform as a Service)의 개요

- **개념** : 애플리케이션 개발자가 하부의 서버 하드웨어, 네트워크, 운영체제(OS), 런타임 환경 관리에 신경 쓰지 않고, 소스코드 작성과 데이터 설계에만 집중할 수 있도록 실행 런타임, 데이터베이스, 미들웨어, CI/CD 배포 파이프라인을 클라우드 플랫폼 형태로 제공하는 서비스 모델.
- **배경 및 필요성** : IaaS 환경에서 가상머신 OS 패치, 웹 서버 미들웨어 튜닝, 오토스케일링 스크립트 작성 등 비즈니스 로직 외적인 인프라 운영 작업이 개발 생산성을 저해함에 따라 개발자 경험(DX)과 타임투마켓 단축을 위해 탄생함.
- **핵심 목적** : 인프라 프로비저닝 부담 배제, 빌드팩(Buildpack) 기반 소스코드 자동 컨테이너화 및 배포, 플랫폼 차원의 무중단 오토스케일링 및 백엔드 서비스 바인딩.

## Ⅱ. PaaS(Platform as a Service)의 핵심 아키텍처 및 동작 메커니즘

PaaS는 클라우드 네이티브 빌드팩, 서비스 브로커(Service Broker), 그리고 플랫폼 컨트롤 플레인(Cloud Foundry, OpenShift, Heroku, AWS Elastic Beanstalk) 기반으로 동작함.

```text
[ PaaS 애플리케이션 라이프사이클 및 플랫폼 스택 ]

[개발자 소스코드: git push]
             │
             ▼
+---------------------------------------------------------------+
| PaaS Platform Controller (Cloud Foundry / OpenShift / Heroku) |
|                                                               |
|  1. Cloud Native Buildpack (언어 감지: Java, Node, Go, Python)|
|     - 소스코드 컴파일 + 최적 런타임 결합 -> OCI 컨테이너 생성 |
|                                                               |
|  2. Service Broker API (DB, Redis, MQ 등 외부 서비스 바인딩)  |
|     - 환경 변수(VCAP_SERVICES / ConfigMap) 자동 주입          |
|                                                               |
|  3. Routing & Autoscaler (L7 인그레스 라우팅 및 무중단 배포)   |
+---------------------------------------------------------------+
             │                                   │
             ▼                                   ▼
+---------------------------+       +---------------------------+
| App Instance (Worker Pod) |       | App Instance (Worker Pod) |
| (완전 관리형 격리 런타임) |       | (트래픽 급증 시 자동 증설)|
+---------------------------+       +---------------------------+
             │                                   │
             └─────────────────┬─────────────────┘
                               ▼
+---------------------------------------------------------------+
| Managed Backing Services (플랫폼 관리형 RDS, Kafka, Elastic)  |
+---------------------------------------------------------------+
```

- **Cloud-Native Buildpack** : Dockerfile 없이도 소스코드를 분석하여 JVM, Node 런타임 및 의존성 라이브러리를 최신 보안 패치와 결합하여 컨테이너 이미지 자동 빌드.
- **서비스 브로커 (Service Broker)** : 데이터베이스나 캐시 인스턴스를 클릭 한 번으로 생성하고 접속 자격 증명을 앱 환경 변수로 자동 바인딩.
- **블루-그린 및 롤링 배포 내장** : 플랫폼이 라우팅 계층(Router)을 제어하여 무중단 배포 및 실패 시 원터치 롤백 제공.
- **플랫폼 레벨 오토스케일링** : HTTP 처리량 및 응답 지연을 측정하여 개발자의 개입 없이 애플리케이션 인스턴스를 수평 확장.

## Ⅲ. PaaS(Platform as a Service)의 세부 구성 요소 및 비교 분석

| 비교 항목 | IaaS (인프라 서비스) | PaaS (플랫폼 서비스) | FaaS / Serverless |
|---|---|---|---|
| **개발자 관리 범위** | OS, 미들웨어, 런타임, 앱 코드 | **애플리케이션 코드 및 데이터만** | **단일 함수(Function) 코드만** |
| **배포 단위** | 가상머신 이미지 (AMI) | 소스코드 Git 푸시 / 컨테이너 | 이벤트 기반 함수 아티팩트 |
| **개발 생산성 (DX)** | 낮음 (서버 구축 및 패치 부담) | **매우 높음 (개발 집중 최적화)** | 매우 높음 (이벤트 처리 특화) |
| **시스템 제어 유연성**| 완전한 자유도 (커널/네트워크) | **제한적 (플랫폼 제약 준수)** | 극도로 제한적 (Stateless) |
| **벤더 종속성** | 낮음 (표준 가상머신 이전 용이) | **중간~높음 (플랫폼 특화 설정)** | 높음 (CSP 이벤트 트리거 종속) |

- PaaS는 높은 생산성을 보장하나 특정 플랫폼 규격에 종속될 수 있으므로, 최근에는 쿠버네티스 표준을 내장한 개방형 PaaS(Red Hat OpenShift 등)가 주류임.

## Ⅳ. PaaS(Platform as a Service)의 주요 한계점 및 해결 방안

- **특정 PaaS 런타임 및 프레임워크 종속(Lock-in)** :
  - **한계점** : 플랫폼 고유의 환경 변수 및 배포 규격에 앱이 결합되어 타 클라우드로의 이전 시 리팩토링 비용 발생.
  - **해결 방안** : 12-Factor App 원칙 준수, OCI 표준 컨테이너 이미지 기반의 클라우드 중립적 오픈 PaaS(OpenShift, Cloud Run) 채택.
- **시스템 커널 레벨 튜닝 및 특수 OS 라이브러리 사용 불가** :
  - **한계점** : C/C++ 네이티브 확장 모듈이나 특정 소켓 옵션, GPU 드라이버 커스텀 설치가 차단되어 특수 워크로드 구동 불가.
  - **해결 방안** : 커스텀 컨테이너 이미지를 직접 지정할 수 있는 하이브리드 PaaS 모드 활용.
- **플랫폼 관리 프리미엄으로 인한 대규모 확장 시 비용 증가** :
  - **한계점** : 동일 하드웨어 대비 관리 소프트웨어 라이선스 및 서비스 마진이 부과되어 대규모 장기 운영 시 IaaS 대비 비용 상승.
  - **해결 방안** : 베이스라인 워크로드는 사내 K8s 기반 자체 플랫폼(IDP)으로 내재화하고 변동성 워크로드에 상용 PaaS 활용.

## Ⅴ. PaaS(Platform as a Service) 적용 및 발전을 위한 기술사적 제언

- **플랫폼 엔지니어링(Internal Developer Platform: IDP) 구축** : 개발팀의 인프라 티켓 요청을 없애고 Backstage와 쿠버네티스를 결합한 엔터프라이즈 맞춤형 셀프서비스 PaaS 정착.
- **클라우드 네이티브 12-Factor 원칙 준수** : 코드베이스 일원화, 명시적 의존성 선언, 설정의 환경 변수 분리, 무상태 프로세스 설계를 전사 아키텍처 원칙으로 확립.
- **보안 거버넌스 자동화 파이프라인 연계** : 빌드팩 단계에서 오픈소스 라이선스 검증 및 CVE 취약점 차단이 자동으로 수행되는 DevSecOps 통합 체계 수립 권장.
