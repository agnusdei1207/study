## 연관 키워드

- 멀티클라우드(Multi-Cloud), CSP(Cloud Service Provider), 벤더 종속(Vendor Lock-in), 데이터 주권(Data Sovereignty)
- GSLB(Global Server Load Balancing), CMP(Cloud Management Platform), IaC(Infrastructure as Code), CSPM(Cloud Security Posture Management)
- 송출 비용(Egress), 데이터 그래비티(Data Gravity), RTO(Recovery Time Objective), RPO(Recovery Point Objective), 워크로드 티어링(Workload Tiering)

## Ⅰ. 멀티클라우드의 개요

- 핵심 요약 : 둘 이상의 클라우드 제공업체를 목적별로 조합해 운영함으로써 장애 대응력과 통제력을 높이는 전략.
- 개념 : **멀티클라우드** (Multi-Cloud)는 가용성 확보, 워크로드 적합성, 규제 대응을 위해 둘 이상의 **CSP** (Cloud Service Provider)의 서비스를 함께 운영하는 전략. 온프레미스와 퍼블릭의 결합인 하이브리드 클라우드와는 배치 환경의 결합 여부라는 축에서 구분됨.
- 배경 및 필요성 : 단일 제공업체의 특정 리전 장애가 전 서비스 중단으로 확산할 수 있고, **벤더 종속** (Vendor Lock-in)은 계약 협상력을 약화시키며, 국가별 데이터 현지화 규제의 강화로 **데이터 주권** (Data Sovereignty) 요건 충족이 과제화됨.
- 주요 목적 : 장애 시의 선택지 확보, 워크로드별 최적 배치, 데이터 위치에 대한 통제력 향상.

## Ⅱ. 멀티클라우드의 특징 및 장점

- 핵심 요약 : 장애 도메인의 분리와 워크로드별 선택권이 복원력과 협상력이라는 장점으로 연결되는 운영 전략.

1. 장애 도메인 분리 : 도메인 이름 체계, 인증, 데이터 복제, 배포 경로를 제공업체별로 분리 구성 → 단일 제공업체 장애의 파급 범위 축소. 제어 경로가 공유되면 분리 효과가 제한됨.
2. 최적 서비스 배치 : 제공업체별 강점 서비스를 워크로드 요구에 맞춰 선택 → 성능과 비용의 워크로드 단위 최적화.
3. 계약·규제 대응 : 제공업체 선택지의 확보 → 계약 협상력 강화와 지역별 규제 대응 용이.

## Ⅲ. 멀티클라우드의 구조 (흐름)

- 핵심 요약 : 트래픽 라우팅, 통합 관제, 코드형 배포, 복구 목표 관리가 제공업체 경계를 넘어 결합되는 운영 구조.

1. **GSLB** (Global Server Load Balancing) : 지리적 위치, 헬스체크 결과, 지연 시간을 기준으로 사용자 요청을 최적 엔드포인트로 라우팅하는 글로벌 트래픽 관리.
2. **CMP** (Cloud Management Platform) : 복수 제공업체의 프로비저닝, 자원 현황, 비용, 정책 준수를 통합 관제하는 플랫폼.
3. **IaC** (Infrastructure as Code) : 이종 환경의 인프라를 코드로 정의해 동일 절차로 배포하는 방식.
4. **CSPM** (Cloud Security Posture Management) : 제공업체별 보안 설정의 점검과 정책 위반 탐지를 수행하는 도구.
5. 복구 목표 : 장애 후 서비스 복구 목표 시간인 **RTO** (Recovery Time Objective)와 허용 데이터 손실 범위인 **RPO** (Recovery Point Objective)의 사전 정의와 검증.

```text
[ 멀티클라우드 운영 구조 ]

글로벌 사용자 요청
   ↓
GSLB (글로벌 트래픽 관리)
   ↓
CSP A (주 서비스) ⇄ CSP B (복제 · 대기)
   ↑                    ↑
통합 관제 (CMP · IaC · CSPM)
```

```text
[ 장애 전환 흐름 ]

헬스체크 실패 감지
   ↓
전환 정책 판정 (자동 · 수동)
   ↓
트래픽을 대기 CSP로 변경
   ↓
RPO · RTO 충족 여부 검증
```

## Ⅳ. 싱글·하이브리드·멀티클라우드의 비교

- 핵심 요약 : 싱글은 단순성, 하이브리드는 배치 유연성, 멀티클라우드는 제공업체 선택권에서 각각 강점을 가짐.

| 비교 항목 | 싱글 클라우드 | 하이브리드 클라우드 | 멀티클라우드 |
| --- | --- | --- | --- |
| 구성 | 단일 제공업체 | 온프레미스·프라이빗과 퍼블릭의 결합 | 둘 이상의 제공업체 |
| 운영 복잡도 | 낮음, 단일 도구 체계 | 중간, 환경 간 연동 필요 | 높음, 관리 도구와 절차의 분화 |
| 벤더 종속 위험 | 관리형 서비스 의존에 좌우 | 연계 구조의 수준에 좌우 | 공통 계층으로 완화, 데이터 종속 잔존 |
| 재해 복구 | 다중 리전 구성으로 대응 | 환경 간 복제·전환 설계 필요 | 제공업체 간 복제·전환의 구현·검증 필요 |
| 비용 구조 | 단일 계약 할인에 유리 | 인프라 이중 투자 발생 | 제공업체 간 **송출 비용** (Egress) 관리 필요 |

- 선택 기준 : 규제와 장애 요건이 완만하면 싱글로 시작하고, 레거시 통합·데이터 통제 목적은 하이브리드로, 장애 복원력과 협상력이 사업상 필수일 때 멀티클라우드를 채택하는 방식으로 판단.

## Ⅴ. 멀티클라우드의 한계와 방안

- 핵심 요약 : 송출 비용, 운영 파편화, 보안 정책 불일치를 데이터 배치 설계, 공통 자동화, 통합 관제로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 송출 비용 증가 | 제공업체 간 잦은 데이터 동기화로 예상 밖의 요금 발생 | **데이터 그래비티** (Data Gravity)를 고려한 데이터 배치, 쓰기 리전의 지정 | 제공업체 간 송출량 |
| 운영 파편화 | 네트워크 모델, 권한 체계, 지표 체계의 차이 → 관리 복잡도 급증 | IaC 표준 모듈화, 통합 관제 플랫폼의 채택 | 표준 모듈 적용률 |
| 보안 정책 불일치 | 제공업체별 설정 체계의 차이 → 구성 오류와 사각지대 발생 | CSPM의 전사 일원화, 통합 권한 관리 체계 연동 | 설정 오류 건수 |

## Ⅵ. 멀티클라우드에 대한 기술사적 제언

- 핵심 요약 : 전면 복제가 아닌 중요도 기반의 단계 적용, 비용 거버넌스, 개방형 표준 중심 설계가 확산의 전제.

- 전사 아키텍처 조직은 서비스 중요도와 복구 목표에 따라 워크로드를 계층화하고 핵심 거래 체계에만 다중 제공업체 구성을 적용하는 **워크로드 티어링** (Workload Tiering)을 도입 기준으로 채택.
- 비용 관리 조직은 제공업체별 약정 할인과 사용량을 통합 조회하는 비용 거버넌스를 운영하여 분산 운영으로 인한 할인 누락을 방지.
- 개발 조직은 컨테이너·오픈소스 데이터베이스 같은 개방형 표준을 설계 기본값으로 삼아 이식성을 확보하고 특정 제공업체 전용 서비스의 의존을 최소화.

## Ⅶ. 결론

- 핵심 요약 : 멀티클라우드는 제공업체 선택권을 통한 복원력과 통제력의 확보 전략.
- 장애 전환 절차의 검증과 관리 가능한 복잡도가 갖춰질 때 그 가치가 실현됨.
