## 연관 키워드

- 프로세스 메모리 구조, 가상 주소 공간, 세그먼트, Text, Data, BSS, 힙(Heap), 스택(Stack)
- 버퍼 오버플로우, 스택 카나리, ASLR, DEP/NX, KPTI, Meltdown/Spectre, 메모리 누수

## Ⅰ. 프로세스 메모리 구조의 개요

- 핵심 요약 : 가상 주소 공간을 역할별 세그먼트로 나누어 권한 분리, 동적 확장, 공격 방어를 함께 구현하는 메모리 배치 체계.
- 개념 : 프로세스가 사용하는 **가상 주소 공간** (Virtual Address Space, 프로세스마다 독립적으로 주어지는 주소 범위)을 코드·데이터·동적 영역·스택 등 역할과 수명이 다른 구간으로 나눈 배치 구조(**프로세스 메모리 구조**, Process Memory Layout). 실행 파일 ELF(Executable and Linkable Format)를 읽어 적재할 때 이 배치가 만들어짐.
- 배경 및 필요성 : 명령어와 데이터가 한 공간에 뒤섞여 실행되면 코드 변조와 메모리 침범이 쉬워져 보안 사고 대응과 장애 복구 비용이 커지므로, 구간별 접근 권한과 주소 분리를 OS가 강제하는 구조가 필요해짐.
- 주요 목적 : 구간별 권한 분리로 코드 변조 차단, 힙과 스택의 런타임 확장 보장, **버퍼 오버플로우** (Buffer Overflow, 입력이 할당 경계를 넘어 인접 메모리를 덮어쓰는 취약점)를 비롯한 악성 코드 실행 방어.

## Ⅱ. 프로세스 메모리 구조의 특징 및 장점

- 핵심 요약 : 세그먼트별 역할과 권한을 나눈 설계가 보호, 확장, 공격 방어의 효과로 이어지는 구조.

1. **텍스트 세그먼트** (Text Segment) : 컴파일된 기계어 명령어를 적재하고 쓰기 권한을 주지 않음 → 코드 변조 차단.
2. **데이터 세그먼트** (Data Segment) : 초기값이 명시된 전역 변수와 static 변수를 저장 → 초기 상태가 프로그램 시작 시 보장.
3. **BSS 세그먼트** (Block Started by Symbol) : 초기값이 없는 전역·static 변수를 배치하고, 적재 시 OS가 0으로 초기화 → 실행 파일 크기를 줄임.
4. **힙 세그먼트** (Heap) : `malloc()`, `new` 등 런타임 동적 할당 영역으로 낮은 주소에서 높은 주소 방향으로 성장 → 실행 중 가변 크기 데이터를 수용.
5. **스택 세그먼트** (Stack) : 함수 호출 시 생기는 활성화 레코드(지역 변수, 복귀 주소)를 저장하고 높은 주소에서 낮은 주소로 성장 → 함수 호출 흐름을 후입선출로 관리.

## Ⅲ. 프로세스 메모리 구조의 구조 및 동작 메커니즘

- 핵심 요약 : 낮은 주소에서 높은 주소로 Text, Data, BSS, Heap, 빈 영역, Stack, Kernel 순으로 배치되는 레이아웃.
- 세그먼트는 고정 크기 영역(Text, Data, BSS)과 가변 크기 영역(Heap, Stack)으로 나뉘며, 가변 영역은 서로 마주 보고 자라는 구조로 배치됨.

```text
[ 가상 주소 공간 배치 (낮은 주소 → 높은 주소) ]

Text   : 기계어 명령어, 읽기·실행만 허용
   ↓
Data   : 초기화된 전역·static 변수
   ↓
BSS    : 초기화되지 않은 전역·static 변수
   ↓
Heap   : 동적 할당 영역 (주소 증가 방향)
   ↓
(빈 영역)
   ↓
Stack  : 지역 변수·복귀 주소 (주소 감소 방향)
   ↓
Kernel : 커널 공간, 사용자 모드 접근 불가
```

```text
[ 힙과 스택의 성장 방향 ]

낮은 주소  Heap   ──→ 증가 방향 성장
                      (빈 영역 소진 시 충돌)
높은 주소  Stack  ←── 감소 방향 성장

충돌 감지 → 가드 페이지(Guard Page) 배치
```

## Ⅳ. 프로세스 메모리 구조의 비교

- 핵심 요약 : 세그먼트마다 할당 시점, 해제 시점, 성장 방향, 저장 데이터가 달라 관리 방식도 달라짐.

| 세그먼트 | 할당 시점 | 해제 시점 | 성장 방향 | 주요 저장 데이터 |
| --- | --- | --- | --- | --- |
| Text | 프로세스 적재 시 | 프로세스 종료 시 | 고정 크기 | 기계어 명령어, 리터럴 상수 |
| Data | 프로세스 적재 시 | 프로세스 종료 시 | 고정 크기 | 초기화된 전역·static 변수 |
| BSS | 프로세스 적재 시 | 프로세스 종료 시 | 고정 크기 (0 초기화) | 초기값 없는 전역·static 변수 |
| Heap | 런타임 동적 할당 | 명시적 해제 또는 GC(Garbage Collection) | 낮은 주소에서 높은 주소 | 동적 생성 객체, 런타임 버퍼 |
| Stack | 함수 호출 시 | 함수 반환 시 | 높은 주소에서 낮은 주소 | 지역 변수, 파라미터, 복귀 주소 |

- 선택 기준 : 수명이 프로세스 전체와 같은 데이터는 Data·BSS에, 실행 중 크기가 정해지는 데이터는 Heap에, 함수 단위로 수명이 끝나는 데이터는 Stack에 두는 기준으로 구분함.

## Ⅴ. 프로세스 메모리 구조의 한계와 방안

- 핵심 요약 : 버퍼 오버플로우, 메모리 누수, 하드웨어 투기적 실행 취약점을 세그먼트 보호와 커널 격리 기법으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 스택 버퍼 오버플로우 | 배열 경계 검사 미흡 → 복귀 주소 변조로 임의 코드 실행 | **스택 카나리** (Stack Canary, 복귀 주소 앞의 무작위 값 검증), **DEP** (Data Execution Prevention) 및 NX(No-eXecute) 비트로 스택 실행 권한 제거, **ASLR** (Address Space Layout Randomization) 활성화 | 보호 기능 적용률, 메모리 침범 탐지 건수 |
| 힙 메모리 누수 | 할당 후 해제 누락 → 힙 고갈과 장기 운영 프로세스 비정상 종료 | 스마트 포인터 사용, ASan(AddressSanitizer)과 Valgrind로 빌드 단계 검증 | 힙 사용량 추이, 누수 탐지 건수 |
| 커널 공간 침범 취약점 (Meltdown/Spectre) | 비순차 실행과 투기적 실행을 악용해 캐시에 남은 커널 데이터 탈취 | **KPTI** (Kernel Page Table Isolation) 적용, 최신 마이크로코드 패치 | 패치 적용률, 커널 격리 설정 여부 |

- 메모리 누수의 세부 메커니즘과 대응은 별도 토픽에서 다루며, 본 표는 프로세스 메모리 영역 관점의 대응만 정리함.

## Ⅵ. 프로세스 메모리 구조의 기술사적 제언

- 핵심 요약 : 빌드 보안 기본값, 주소 공간 무작위화 점검, 메모리 안전 언어 도입을 묶어 메모리 보호를 설계 단계에서 내재화.

1. 빌드 보안 기본값 : 스택 보호와 재배치 정보 보호 링크 옵션(`-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, `-Wl,-z,relro,-z,now`)을 전사 빌드 파이프라인의 기본 설정으로 두는 방향이 적절함.
2. 주소 공간 무작위화 점검 : 서버 기준선 점검 항목에 `kernel.randomize_va_space=2` 설정 여부를 포함하여 ASLR 상태를 자동으로 확인하는 체계가 필요함.
3. 메모리 안전 언어 도입 : 보안 민감 모듈은 Rust 같은 메모리 안전(Memory-safe) 언어의 도입을 검토하여 버퍼 오류를 언어 수준에서 줄이는 방향이 유효함.

## Ⅶ. 결론

- 핵심 요약 : 프로세스 메모리 구조는 세그먼트 분리로 보호, 확장, 공격 방어를 실현하는 기반 설계.
- 시사점 : 세그먼트 분리만으로 방어가 완성되지 않으므로, 빌드 보안 옵션과 커널 격리를 함께 운영하는 것이 전제 조건임.
