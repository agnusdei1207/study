## Ⅰ. FaaS(Function as a Service)의 개요

- 개념 : 개발자가 서버의 프로비저닝, 관리, 패치, 스케일링 등 인프라 전반을 전혀 고려하지 않고 오직 비즈니스 로직이 담긴 **개별 함수(Function)** 코드만을 작성하여 배포하면, 이벤트 발생 시 런타임이 마이크로초~밀리초 단위로 컨테이너를 구동하여 실행하고 자원을 반환하는 **이벤트 주도(Event-Driven)** 서버리스 컴퓨팅 핵심 모델.
- 배경 및 필요성 : 가상머신(IaaS)과 상시 가동 컨테이너(PaaS)의 **유휴 자원 낭비(Idle Cost)** 와 오토스케일링 지연 한계를 극복하고, **마이크로서비스(MSA)** 및 클라우드 네이티브 환경에서 개발 생산성과 운영 민첩성을 극대화하기 위해 등장.
- 핵심 목적 : 제로 인프라 관리(NoOps), 진정한 제로 스케일링(Scale-to-Zero), 코드 실행 밀리초(ms) 단위의 정밀 종량제 과금을 통한 **TCO** 절감.

## Ⅱ. FaaS의 핵심 수명주기 및 마이크로VM 아키텍처

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ FaaS (Function as a Service) 런타임 아키텍처 및 실행 수명주기 ]      │
│                                                                        │
│   [ 이벤트 소스 (API Gateway, S3 Object, Kafka Message, Webhook) ]    │
│                     │ Event Trigger                                    │
│                     ▼                                                  │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │ [ 서버리스 컨트롤 플레인 (Serverless Control Plane) ]          │   │
│   │  - 라우팅 및 큐잉 (Workload Dispatcher)                        │   │
│   │  - 웜 풀(Warm Pool) 여부 확인                                  │   │
│   └───────────────┬────────────────────────────────┬───────────────┘   │
│                   │ Cold Start (신규 생성)         │ Warm Start (재사용)│
│                   ▼                                ▼                   │
│   ┌───────────────────────────────┐  ┌─────────────────────────────┐   │
│   │ [ Cold Start 격리 런타임 ]    │  │ [ Warm Container 인스턴스 ] │   │
│   │  - MicroVM 생성 (Firecracker) │  │  - 런타임 이미 상주         │   │
│   │  - 언어 런타임(Node/Java) 초기화│  │  - 핸들러 코드 즉시 호출   │   │
│   │  - 핸들러 로딩 및 정적 초기화 │  │                            │   │
│   └───────────────┬───────────────┘  └─────────────┬───────────────┘   │
│                   │                                │                   │
│                   └────────────────┬───────────────┘                   │
│                                    ▼                                   │
│   [ 함수 실행 (handler(event, context)) ] ──> 응답 반환 및 유휴 대기   │
│                                    │ (일정 시간 미호출 시 Scale-to-Zero)│
│                                    ▼                                   │
│   [ 인스턴스 파기 (Destroy) ] ──> 메모리 및 컴퓨팅 자원 완전 반환       │
└────────────────────────────────────────────────────────────────────────┘
```

- **마이크로VM 기반 경량 격리** : 전통적인 무거운 도커 컨테이너 대신 Firecracker, gVisor 등 초경량 마이크로VM 기술을 활용하여 밀리초 단위 부팅 속도와 커널 레벨 멀티테넌트 보안 격리를 동시 달성.
- **무상태(Stateless) 실행 원칙** : 각 함수 인스턴스는 영속적 상태를 보존하지 않으며, 모든 영속 상태는 외부 분산 DB(DynamoDB)나 공유 캐시(Redis), 오브젝트 스토리지(S3)에 위임하여 완벽한 수평 확장성 확보.

## Ⅲ. 클라우드 컴퓨팅 실행 모델 간 비교 분석

| 비교 항목 | IaaS (가상머신) | CaaS/PaaS (컨테이너/쿠버네티스) | FaaS (서버리스 함수) |
| :--- | :--- | :--- | :--- |
| **추상화 단위** | 하드웨어/가상머신 (OS 레벨) | 애플리케이션 패키징 (컨테이너) | 비즈니스 로직 단위 (함수/Code) |
| **스케일링 특성** | 오토스케일링 시 수 분 소요 | HPA/KEDA 기반 수 초~수십 초 | 이벤트 유입 즉시 밀리초 단위 자동 확장 |
| **스케일-투-제로** | 불가능 (VM 상시 가동 비용) | 제한적 (최소 1개 파드 유지 필요) | 완벽 지원 (트래픽 없으면 0원) |
| **과금 방식** | 할당된 가상머신 사양별 시간/월 과금 | 노드 클러스터 또는 파드 요청 자원 과금 | 함수 실행 시간(ms) × 할당 메모리(MB) |
| **실행 시간 제한** | 무제한 | 무제한 | 제한적 (일반적으로 최대 15분) |
| **상태 관리** | 로컬 디스크 및 세션 자유 유지 | 볼륨 마운트(PVC) 기반 상태 유지 | 완전한 무상태(Stateless) 강제 |

## Ⅳ. FaaS 도입 및 운영 시 주요 한계점 및 해결 방안

- **콜드 스타트(Cold Start)** 지연으로 인한 사용자 응답 지연 :
  - 한계점 : 유휴 상태에서 첫 요청 인입 시 마이크로VM 기동, 언어 런타임(특히 JVM, .NET) 적재로 인해 수백 ms~수 초 지연 발생.
  - 해결 방안 : 프로비저닝된 동시성(Provisioned Concurrency) 사전 할당, 스냅샷 복원 기술(AWS Lambda SnapStart) 적용, Go/Rust/Node.js 등 경량 런타임 채택.
- 분산 환경에서의 디버깅, 모니터링 및 추적 복잡성 증대 :
  - 한계점 : 수십 개의 마이크로 함수가 비동기 큐와 이벤트로 얽혀 있어 장애 발생 시 에러의 원인 추적 및 엔드투엔드 프로파일링 불가.
  - 해결 방안 : OpenTelemetry 표준 분산 트레이싱 적용, W3C Trace Context 기반 상관관계 ID(Correlation ID) 전파, 통합 로깅 파이프라인 구축.
- 함수 지속 **실행 시간(Execution Timeout)** 제한과 벤더 락인 :
  - 한계점 : 15분 이상의 대규모 데이터 배치 작업 실행 불가 및 CSP(AWS, Azure, GCP)별 이벤트 시그니처 상이로 이식성 저하.
  - 해결 방안 : 장기 배치는 컨테이너 기반 작업(AWS ECS/Fargate)으로 핸드오버, 워크플로 오케스트레이션(Step Functions) 분할, Serverless Framework/Knative 표준 채택.

## Ⅴ. 성공적인 FaaS 아키텍처 구축을 위한 기술사적 제언

- **FaaS** 만능주의 탈피 및 워크로드 적합성 선별 : 불규칙한 트래픽 스파이크가 발생하는 API 백엔드, 비동기 이미지/동영상 트랜스코딩, IoT 센서 데이터 수집 파이프라인에는 FaaS가 최적이나, 24시간 균일한 고부하 웹 트래픽이나 장기 세션 유지가 필수적인 서비스는 컨테이너(EKS/ECS)를 혼용하는 하이브리드 아키텍처를 수립해야 함.
- 비용 **모니터링(FinOps)** 과 분산 트랜잭션 패턴 설계 : 함수 호출 빈도가 수억 건 이상 폭증할 경우 FaaS 비용이 전용 VM 비용을 초과할 수 있으므로 임계치 알람을 필수 설정하고, 데이터 일관성을 위해 2PC 대신 사가(Saga) 패턴(Choreography/Orchestration)을 체계적으로 구현할 것을 제언함.
