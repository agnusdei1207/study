## 연관 키워드

- FaaS, Function as a Service, 서버리스, 이벤트 주도, 무상태, Scale-to-Zero
- 콜드 스타트, 웜 스타트, 프로비저닝드 동시성, 마이크로VM, 사가 패턴
- OpenTelemetry, 벤더 락인, FinOps, NoOps

## Ⅰ. FaaS의 개요

- 핵심 요약 : 인프라 운영을 제공자에게 맡기고 이벤트에 반응하는 함수 단위로 실행과 과금을 나누는 서버리스 실행 모델.
- 개념 : 개발자가 비즈니스 로직을 담은 함수(Function) 코드만 배포하면, 이벤트가 발생할 때 관리형 런타임이 함수를 실행하고 자원을 관리하는 **서비스형 함수** (FaaS, Function as a Service). 이 실행 모델은 **서버리스** (Serverless) 컴퓨팅의 대표 형태.
- 배경 및 필요성 : **서비스형 인프라** (IaaS, Infrastructure as a Service)나 **서비스형 플랫폼** (PaaS, Platform as a Service)처럼 서버나 컨테이너를 상시 띄워 두면 호출이 적은 시간에도 자원 비용이 발생하고, 트래픽 변화에 맞춘 확장도 늦음. 기능을 잘게 나누는 **마이크로서비스 아키텍처** (MSA, Microservice Architecture)가 확산되면서 유휴 비용을 없애고 기능 단위로 배포하는 방식이 요구됨.
- 주요 목적 : 서버 운영 부담을 줄이고 호출 단위로 과금하여 유휴 비용과 운영 복잡성을 낮추며, 인프라 운영을 최소화하는 **NoOps** (No Operations) 방향을 지향하는 것.

## Ⅱ. FaaS의 특징 및 장점

- 핵심 요약 : 이벤트 주도 호출, 무상태 실행, 마이크로VM 격리, 호출 단위 과금이 맞물려 자동 확장과 유휴 비용 절감으로 이어지는 구조.

1. **이벤트 주도** (Event-Driven) : 웹 요청, 객체 저장, 메시지 큐 같은 이벤트가 함수를 직접 호출 → 항상 떠 있는 프로세스가 없어 유휴 자원 감소.
2. **무상태** (Stateless) 실행 : 함수 인스턴스가 상태를 보존하지 않고 영속 데이터는 외부 저장소에 위임 → 인스턴스를 자유롭게 늘리고 줄여 수평 확장이 쉬움.
3. 마이크로VM 기반 격리 : Firecracker 같은 경량 마이크로 가상 머신(MicroVM, Micro Virtual Machine)으로 함수를 격리 → 빠른 기동과 멀티테넌트 보안을 함께 확보.
4. **Scale-to-Zero** (호출이 없으면 실행 인스턴스를 0개로 줄이는 확장 방식) : 실행 시간과 할당 메모리 기준으로 과금 → 호출이 없는 구간의 비용이 발생하지 않음.

## Ⅲ. FaaS의 구조 (흐름)

- 핵심 요약 : 이벤트 트리거를 받은 컨트롤 플레인이 인스턴스 기동 방식을 고른 뒤 실행하고, 유휴 시 회수하는 수명주기 구조.
- 구성 요소 : 이벤트를 받아 라우팅하고 웜 풀을 확인하는 컨트롤 플레인, 새 인스턴스를 띄우는 **콜드 스타트** (Cold Start), 기존 인스턴스를 재사용하는 **웜 스타트** (Warm Start), 핸들러 함수를 실행하고 유휴 인스턴스를 회수하는 실행 계층.

```text
[ 호출 경로 ]

이벤트 발생 (웹 요청·스토리지·메시지 큐)
   ↓
컨트롤 플레인 (라우팅, 웜 풀 확인)
   ↓
웜 인스턴스 있음 ──> 핸들러 실행
   ↓ 없음
콜드 스타트 (마이크로VM 생성, 런타임 로딩)
   ↓
핸들러 실행 ──> 응답 반환
```

```text
[ 인스턴스 생애 주기 ]

생성 (콜드 스타트)
   ↓
요청 처리 (상태 비보존)
   ↓
유휴 대기 (웜 상태 유지)
   ↓ 일정 시간 미호출
회수 (Scale-to-Zero)
```

## Ⅳ. FaaS의 비교

- 핵심 요약 : 가상 머신, 컨테이너, 함수는 추상화 단위가 다르고, 그에 따라 확장 속도와 과금 방식, 상태 관리 방식이 달라지는 구조.
- 선택 기준 : 요청 빈도의 변동성, 작업 한 번의 실행 시간, 상태 유지 필요성에 따라 추상화 수준을 고른다.

| 비교 항목 | IaaS (가상 머신) | 컨테이너 기반 (PaaS, 쿠버네티스 등) | FaaS (함수) |
| :--- | :--- | :--- | :--- |
| 추상화 단위 | 가상 머신, OS 수준 | 애플리케이션 패키지(컨테이너) | 비즈니스 로직 단위(함수) |
| 확장 속도 | 기동 지연이 커서 자동 확장이 느림 | 수평 파드 자동 확장(HPA, Horizontal Pod Autoscaler), 이벤트 기반 확장(KEDA, Kubernetes Event-driven Autoscaling) | 이벤트 유입에 맞춰 빠르게 확장 |
| 유휴 시 비용 | 인스턴스가 떠 있는 동안 과금 | 최소 파드 수만큼 과금 | 호출이 없으면 과금 없음 |
| 과금 단위 | 가상 머신 사양과 사용 시간 | 노드 또는 파드가 요청한 자원 | 실행 시간과 할당 메모리 |
| 실행 시간 제한 | 운영 정책에 따름 | 운영 정책에 따름 | 플랫폼별 상한 있음(예: AWS Lambda 15분) |
| 상태 관리 | 로컬 디스크와 세션 유지 가능 | 볼륨 마운트 기반 상태 유지 | 무상태 원칙 |

## Ⅴ. FaaS의 한계와 방안

- 핵심 요약 : 콜드 스타트, 분산 추적의 어려움, 실행 시간 상한과 벤더 종속을 사전 기동 설정, 표준 관측 체계, 작업 분할로 대응하는 구조.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 콜드 스타트 지연 | 유휴 후 첫 요청에서 마이크로VM 기동과 런타임 적재가 일어나 응답 지연 발생, 특히 무거운 런타임에서 두드러짐 | 프로비저닝드 동시성(Provisioned Concurrency)으로 인스턴스 사전 확보, 스냅샷 복원(예: AWS Lambda SnapStart), 경량 런타임 채택 | 콜드 스타트 비율, 지연 백분위 |
| 분산 추적과 디버깅 복잡성 | 많은 함수가 큐와 이벤트로 얽혀 장애 원인과 전체 흐름 추적이 어려움 | **OpenTelemetry** (분산 추적 표준)으로 계측, W3C(World Wide Web Consortium) Trace Context 기반 상관관계 ID 전파, 통합 로그 수집 | 추적 완결률, 장애 원인 식별 시간 |
| 실행 시간 상한과 벤더 락인 | 장시간 배치 작업이 상한을 넘고, 클라우드마다 이벤트 규격이 달라 이식성 저하 | 장기 작업은 컨테이너 기반 작업으로 분리, 워크플로 오케스트레이션 서비스로 작업 분할, Knative 같은 공개 표준 채택 | 상한 초과 실패율, 이식 작업 비용 |

## Ⅵ. FaaS에 대한 기술사적 제언

- 핵심 요약 : 워크로드 적합성 선별, 호출 비용의 상시 관리, 여러 함수에 걸친 트랜잭션 설계를 묶어 FaaS를 운영 체계로 정착.

1. 모든 워크로드를 함수로 옮기기보다, 요청과 응답이 짧은 백엔드, 비동기 변환, 이벤트 수집처럼 호출이 간헐적이고 실행이 짧은 작업에 먼저 적용하고, 장시간 세션이나 고부하 상시 처리는 컨테이너와 혼용하는 편이 바람직하다.
2. 비용은 호출 빈도와 실행 시간에 경보 임계치를 두어 관리하고, 재무 조직과 개발 조직이 함께 보는 **FinOps** (Cloud Financial Operations) 체계로 운영하는 것이 필요하다.
3. 여러 함수에 걸친 업무 트랜잭션은 **사가 패턴** (Saga Pattern)으로 보상 트랜잭션을 설계해 중간 실패를 복구하도록 하고, 이를 워크플로 도구로 구현하는 방식을 표준으로 두는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : FaaS는 이벤트 주도의 무상태 함수 실행으로 인프라 운영을 줄이고 유휴 비용을 없애는 서버리스 모델.
- 채택 성패는 콜드 스타트와 추적, 실행 시간 상한을 감당할 수 있는 워크로드인지에 달려 있음.
