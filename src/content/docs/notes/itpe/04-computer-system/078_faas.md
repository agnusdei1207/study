```text
 ┃
 ┣━ Ⅰ 개요 ───── 상시 가동 서버의 유휴 비용 및 용량 산정 난제 → 이벤트 발생 시에만 함수 단위로 컨테이너를 기동하는 서버리스 핵심 모델
 ┣━ Ⅱ 특징 ───── 이벤트 주도(Event-driven) · 0부터 무한대 자동 확장 · 100ms/1ms 단위 종량제 · 무상태(Stateless)

 ┣━ Ⅴ 비교 ───── FaaS vs BaaS vs PaaS
 ┗━ Ⅵ 실무 ───── 초기 기동 지연(Cold Start) / 최대 실행 시간(15분) 제한 / 분산 트랜잭션 및 디버깅 복잡성
```

## 한 줄 본질
- 트래픽이 없을 때도 24시간 켜두는 웹 서버는 클라우드 비용을 낭비하고 트래픽 폭증 시 스케일아웃이 느림 → 애플리케이션을 단일 함수(Function) 단위로 쪼개어 이벤트가 올 때만 밀리초 단위로 띄우고 즉시 소멸 → 서버 관리 제로 및 완벽한 비용 최적화 / 첫 호출 시 런타임 초기화 지연(Cold Start) 발생

## 핵심 용어
- 콜드 스타트(Cold Start): 유휴 상태에서 새로운 요청이 들어왔을 때, FaaS 플랫폼이 가상 격리 환경(MicroVM)을 생성하고 코드와 언어 런타임을 메모리에 적재하느라 첫 응답이 수백 밀리초 이상 지연되는 현상
- 웜 스타트(Warm Start): 이전에 실행되었던 컨테이너가 파괴되지 않고 메모리에 남아있어, 추가적인 부팅 절차 없이 비즈니스 로직만 즉각 실행되는 고속 상태
- 프로비저닝된 동시성(Provisioned Concurrency): 콜드 스타트를 원천 방지하기 위해 사용자가 지정한 개수만큼의 함수 실행 환경을 항상 웜 상태로 사전 예약 유지하는 기능

## 핵심 통찰
- FaaS는 '서버가 없는 게 아니라, 서버를 CSP가 관리하는 것'임 → 개발자가 OS 패치, 용량 증설, 로드밸런서를 신경 쓸 필요가 전혀 없으며, 코드만 올리면 1초에 1건이 오든 1만 건이 오든 알아서 확장됨
- 상태(State)를 가지는 순간 FaaS는 지옥이 됨 → 함수 컨테이너는 언제든지 생성되고 파괴되므로 로컬 디스크나 메모리에 세션을 보관할 수 없으며, 모든 상태는 외부 Redis나 DynamoDB로 밀어내야 하는 순수 무상태(Stateless) 구조를 강제함
- 15분 이상 도는 긴 배치는 FaaS에 올리면 안 됨 → 주요 FaaS 플랫폼은 단일 함수 최대 실행 시간을 15분으로 강제 차단하므로, 장시간 연산이나 지속적인 웹소켓 연결은 컨테이너(ECS/K8s)로 돌리는 것이 맞음

## 이웃 토픽과 구분
- FaaS vs BaaS: FaaS = 비즈니스 로직을 개발자가 코드로 작성해 올리는 컴퓨트 서비스 / BaaS = 인증(Auth), 데이터베이스, 푸시 등 이미 만들어진 기성 백엔드 API를 클라이언트가 소비하는 서비스

## 문제·원인·대책
- 사례: 121회 기출 및 전자상거래 결제 승인 API를 FaaS로 구축 후 간헐적 3초 이상 응답 지연 발생
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| Java 기반 람다 함수의 초기 콜드 스타트 지연(2~4초)으로 사용자 타임아웃 | 무거운 JVM 클래스 로딩 및 의존성 주입(Spring) 프레임워크 오버헤드 | GraalVM 네이티브 이미지(Native Image) AOT 컴파일 적용 | 콜드 스타트 시간을 100ms 이하로 단축 |
| FaaS 파드가 수천 개로 급증하면서 백엔드 RDBMS 커넥션 풀 고갈 | 무상태 함수 인스턴스마다 DB 커넥션을 1:1로 생성하여 한도 초과 | 클라우드 매니지드 프록시(AWS RDS Proxy) 도입 | 커넥션 풀 공유 및 멀티플렉싱으로 DB 과부하 방지 |
