## 연관 키워드

- 클라우드 배포 모델, 퍼블릭 클라우드, 프라이빗 클라우드, 하이브리드 클라우드, 커뮤니티 클라우드, 멀티클라우드
- 클라우드 버스팅, CSP, 멀티테넌시, 벤더 종속, 단일 제어면, 제로 트러스트, 마이그레이션 전략, 컨테이너 이식성

## Ⅰ. 클라우드 배포 모델의 개요

- 핵심 요약 : **클라우드 배포 모델** (Cloud Deployment Model)은 인프라의 소유, 위치, 관리 주체, 공유 범위에 따라 나뉘는 인프라 구축 형태로, 보안 요건과 변동성에 맞춰 조합하는 것이 핵심.
- 개념 : 클라우드 인프라 자원의 소유권, 물리적 위치, 관리 주체, 테넌트 간 공유 범위에 따라 퍼블릭, 프라이빗, 하이브리드, 커뮤니티, 멀티클라우드로 구분되는 배포 패러다임.
- 배경 및 필요성 : 조직마다 데이터 보안 규제, 초기 투자 여력, 업무 부하의 변동성이 다르고, 특정 사업자에 묶이는 **벤더 종속** (Vendor Lock-in) 우려도 크다. 이를 하나의 모델로 모두 해결할 수 없어 배포 모델을 나누어 쓰게 되었다.
- 주요 목적 : 보안과 민첩성의 균형 확보, **규제 준수** (컴플라이언스) 충족, **총소유비용** (TCO, Total Cost of Ownership) 최적화.

## Ⅱ. 클라우드 배포 모델의 특징 및 장점

- 핵심 요약 : 다섯 모델은 소유 주체와 공유 범위를 달리해 비용, 확장성, 통제권 사이의 교환 관계를 나눈다.

1. **퍼블릭 클라우드** (Public Cloud) : 제3자 **클라우드 서비스 제공자** (CSP, Cloud Service Provider)가 하드웨어를 소유·운영하고, 불특정 다수가 **멀티테넌시** (Multi-tenancy) 기반으로 자원을 공유 → 초기 투자 없이 탄력적으로 확장.
2. **프라이빗 클라우드** (Private Cloud) : 단일 기관이 독점 사용하는 전용 인프라 → 보안과 통제권이 높지만 구축 초기 비용이 큼.
3. **하이브리드 클라우드** (Hybrid Cloud) : 핵심 데이터는 프라이빗에 두고, 변동이 큰 웹 계층은 퍼블릭에 두어 전용 회선으로 연결 → 보안과 탄력성을 함께 확보. 트래픽이 몰릴 때 퍼블릭으로 확장하는 **클라우드 버스팅** (Cloud Bursting)이 대표 활용이다.
4. **커뮤니티 클라우드** (Community Cloud) : 금융, 공공, 의료처럼 공통의 규제 요건을 가진 기관들이 공동으로 구축해 공유 → 규제 대응 비용을 나눠 부담.
5. **멀티클라우드** (Multi-Cloud) : 복수의 이종 퍼블릭 CSP를 함께 사용 → **벤더 종속**을 피하고 서비스별로 최적의 사업자를 고를 수 있음.

## Ⅲ. 클라우드 배포 모델의 구조 및 동작 메커니즘

- 핵심 요약 : 인프라의 배타적 전용 여부와 네트워크 연결 방식으로 모델을 구분하며, 현실에서는 프라이빗과 다중 퍼블릭을 잇는 하이브리드·멀티클라우드로 통합되는 흐름.

```text
[ 배포 모델의 기본 구분 ]

공유 인프라 : 퍼블릭 클라우드
  (CSP 소유, 멀티테넌시)

전용 인프라 : 프라이빗 클라우드
  (단일 조직 전용)
```

```text
[ 하이브리드·멀티클라우드 연결 ]

프라이빗 클라우드 (핵심 데이터)
      ↓ 전용 회선
퍼블릭 클라우드 (웹·버스팅 계층)
      ↓ 단일 제어면
멀티클라우드 (이종 CSP 통합 관리)
```

- 연결 구간은 대역폭과 보안 정책이 함께 설계되어야 하며, 이 구간이 약하면 하이브리드 구조 전체의 신뢰도가 떨어진다.

## Ⅳ. 클라우드 배포 모델의 비교

- 핵심 요약 : 퍼블릭, 프라이빗, 하이브리드는 소유권, 테넌트 구조, 초기 투자, 확장성, 통제권, 운영 복잡도에서 뚜렷이 다르다.

| 비교 항목 | 퍼블릭 클라우드 | 프라이빗 클라우드 | 하이브리드 클라우드 |
| --- | --- | --- | --- |
| 인프라 소유권 | 클라우드 서비스 제공자 | 기업 자체 소유 또는 전용 임차 | 온프레미스 자산과 CSP 자원의 혼합 |
| 테넌트 구조 | 멀티테넌트 (논리적 격리) | 싱글테넌트 (물리적 격리) | 핵심 업무는 싱글, 확장 구간은 멀티 |
| 초기 투자비 (CAPEX, Capital Expenditure) | 낮음, 종량 과금 | 높음, 하드웨어와 솔루션 구매 | 기존 투자 보호와 일부 구독 |
| 확장성 | 탄력성이 높음 | 보유 하드웨어 용량에 제한 | 버스팅으로 동적 확장 |
| 보안 및 통제권 | 공동 책임 모델, CSP 의존 | 전반적인 통제권 | 데이터 등급별 차등 보안 |
| 운영 복잡도 | 낮음, 관리형 서비스 활용 | 높음, 사내 인력이 직접 운영 | 매우 높음, 이기종 환경 연동 |

- 어느 한 모델이 절대적으로 우월하지 않다. 워크로드의 보안 등급과 변동성에 따라 차등 배치하는 하이브리드 전략이 표준처럼 자리 잡았다.

## Ⅴ. 클라우드 배포 모델의 한계와 방안

- 핵심 요약 : 연결 구간의 병목과 보안 사각지대, 운영 도구의 파편화, 버스팅 시의 데이터 지연을 전용 회선, 단일 제어면, 무상태 확장으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 하이브리드 **연결 구간의 병목**과 보안 경계 모호화 | 사내망과 퍼블릭을 잇는 VPN(Virtual Private Network) 대역폭 병목, 양쪽 보안 정책 불일치로 사각지대 발생 | AWS Direct Connect, Azure ExpressRoute 같은 전용 회선 구축, 전사 **제로 트러스트** (Zero Trust) 접근 통제 적용 | 연결 지연 시간, 정책 불일치 건수 |
| 이기종 관리 도구의 파편화 | 온프레미스, AWS, Azure를 각각 다른 콘솔로 관리해 운영 부담 급증 | **단일 제어면** (Single Control Plane)을 제공하는 하이브리드 플랫폼(Anthos, Azure Arc, Red Hat OpenShift) 검토 | 관리 도구 수, 정책 일관성 점검 건수 |
| **클라우드 버스팅** 시의 데이터 동기화 지연 | 트래픽 폭증 때 대용량 데이터 전송이 늦어 실시간 처리가 실패함 | 상태가 없는 웹·앱 계층만 퍼블릭으로 확장하고, 분산 캐시로 읽기 데이터를 미리 동기화 | 동기화 지연 시간, 버스팅 전환 시간 |

## Ⅵ. 클라우드 배포 모델의 적용 제언

- 핵심 요약 : 워크로드별 전환 전략, 데이터 등급 기준, 컨테이너 이식성을 기본 설계로 삼아야 배포 모델 간 이동과 규제 대응이 함께 가능하다.

1. 워크로드마다 보안 등급과 변동성을 기준으로 재호스팅(Rehost), 재플랫폼(Replatform), 리팩터링(Refactor) 같은 **마이그레이션 전략**을 정하는 평가 절차를 마련해야 한다.
2. 원천 거래 장부처럼 규제 대상 자료는 프라이빗에 두고, 비식별 처리를 거친 분석 자료만 퍼블릭으로 옮기도록 데이터 분류 기준을 금융·공공 가이드라인에 맞춰 정해야 한다.
3. 워크로드를 **컨테이너** (Container)로 패키징해 OCI(Open Container Initiative) 표준 이미지를 쓰면, 특정 CSP에 묶이지 않고 배포 모델 사이를 옮겨 다닐 수 있다.

## Ⅶ. 결론

- 핵심 요약 : 클라우드 배포 모델은 소유, 위치, 관리, 공유 범위에 따라 나뉘며, 어느 한 모델의 우월성보다 워크로드 특성에 맞춘 조합이 표준이 됨.
- 시사점 : 배포 모델 선택은 기술 비교보다 데이터 등급과 변동성에 대한 판단이므로, 이동성과 통제 체계를 함께 설계해야 장기 비용과 종속 위험을 함께 관리할 수 있다.
