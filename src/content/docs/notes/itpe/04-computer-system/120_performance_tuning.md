## 연관 키워드

- 성능 튜닝(Performance Tuning), 병목(Bottleneck), 응답 시간, 처리량
- 암달의 법칙(Amdahl's Law), APM(Application Performance Monitoring), 측정 우선
- 실행 계획(Explain Plan), 커넥션 풀, 스레드 풀, GC(Garbage Collection)
- 성능 회귀 테스트, AIOps, 엔드투엔드 모니터링

## Ⅰ. 성능 튜닝의 개요

- 핵심 요약 : 측정으로 병목 계층을 찾아 제거하는 전 계층 최적화 활동이며, 증설 이전에 시도하는 구조적 개선 방법.
- 개념 : 응답 시간, 처리량, 자원 이용률 목표 달성을 위해 운영체제·미들웨어·데이터베이스·애플리케이션 전 계층에서 **병목** (Bottleneck, 전체 처리를 지연시키는 최대 제약 구간)을 측정하고 제거하는 **성능 튜닝** (Performance Tuning) 활동.
- 배경 및 필요성 : 락 경합·직렬 구간이 남아 있으면 **암달의 법칙** (Amdahl's Law, 직렬 처리 비율만큼 자원 증설 효과가 제한된다는 법칙)에 따라 무조건적 증설의 효과가 제한.
- 주요 목적 : 최소 자원으로 트랜잭션 처리량 극대화, 병목 근원 제거, 사용자 체감 응답 개선.

## Ⅱ. 성능 튜닝의 특징 및 장점

- 핵심 요약 : 측정 우선 원칙과 병목 중심 개선이 적은 작업으로 큰 효과를 얻는 구조.

1. 측정 우선 원칙 : **APM** (Application Performance Monitoring) 프로파일러로 지연 기여도를 수치화 → 추측에 의한 수정 차단과 튜닝 효과 검증.
2. 병목 중심 개선 : 지연 기여도가 가장 큰 계층부터 개선 → 적은 작업으로 전체 응답 시간 대폭 단축.
3. 계층 간 연계 점검 : 상위 계층부터 하위 계층으로 순차 점검 → 한 계층 개선 뒤 드러나는 다음 병목의 대응.

## Ⅲ. 성능 튜닝의 구조 (흐름)

- 핵심 요약 : 측정·식별·개선·검증의 반복 사이클과 계층별 튜닝 대상으로 이루어진 구조.

```text
[ 측정 기반 튜닝 사이클 ]

부하 측정 (APM·프로파일러)
     ↓
병목 계층 식별 (지연 기여도)
     ↓
개선 적용 (기여도 큰 계층 우선)
     ↓
재측정과 회귀 검증
     ↓ 목표 미달 시 반복
```

```text
[ 계층별 튜닝 대상 ]

애플리케이션 : 알고리즘, 캐시, 락 범위
     ↓
런타임 : GC, 스레드 풀
     ↓
데이터베이스 : 실행 계획, 인덱스, 버퍼
     ↓
OS·네트워크 : 커널 파라미터, 대역폭
```

- 애플리케이션 계층 : 비효율 알고리즘 개선, 캐싱·비동기 입출력 도입, **커넥션 풀** (Connection Pool, 데이터베이스 연결을 미리 만들어 재사용하는 자원 풀) 크기 조정.
- 런타임 계층 : **GC** (Garbage Collection, 사용 종료 객체의 메모리 회수 절차) 일시정지 축소와 **스레드 풀** (Thread Pool) 크기 조정.
- 데이터베이스 계층 : **실행 계획** (Explain Plan, 쿼리 처리 절차의 표시)으로 풀스캔 쿼리를 분석하고 복합 인덱스를 재설계.

## Ⅳ. 계층별 튜닝 대상과 기법의 비교

- 핵심 요약 : 계층마다 병목 증상과 측정 지표가 다르므로 같은 증상이라도 원인 계층을 먼저 가려내야 튜닝 방향이 맞음.

| 계층 | 주요 병목 지점 | 핵심 지표 | 대표 기법 |
| :--- | :--- | :--- | :--- |
| 애플리케이션 | N+1 조회, 락 경합 | 동기화 대기 시간 | 배치 페치, 로컬 캐시 |
| 런타임 (자바 가상머신·웹 애플리케이션 서버) | 잦은 Full GC, 스레드 풀 고갈 | GC 일시정지 시간 | 힙·스레드 풀 조정 |
| 데이터베이스 | 풀스캔, 부적절한 인덱스, 락 대기 | 버퍼 캐시 적중률 | 실행 계획 분석, 커버링 인덱스 |
| OS·네트워크 | 컨텍스트 스위칭 과다, 대역폭 포화 | 컨텍스트 스위치, IOPS(Input/Output Operations Per Second) | 커널 파라미터 조정, 전용망 분리 |

- 선택 기준 : 측정된 지연 기여도가 가장 큰 계층을 튜닝 대상으로 정하고, 기여도가 작은 계층은 후순위로 미루는 기준.

## Ⅴ. 성능 튜닝의 한계와 방안

- 핵심 요약 : 국소 최적화에 따른 병목 전이, 테스트·운영 환경의 데이터 편차, 과도한 인덱스가 주요 한계이며 엔드투엔드 측정, 운영 규모 검증, 인덱스 정리로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 국소 최적화에 따른 병목 전이 | 애플리케이션 처리 속도만 높이면 하위 계층에 부하 집중 → 새 병목 발생 | 엔드투엔드(End-to-End) 모니터링 아래의 단계적 부하 테스트 | 계층별 자원 사용률 |
| 테스트·운영 환경의 데이터 편차 | 개발 데이터가 적어 운영 전용 문제 미발견 | 운영 규모 데이터 복제 검증 환경 구축 | 검증·운영 환경의 응답 차이 |
| 과도한 인덱스 | 조회 인덱스 과다 → 삽입·갱신 부하 | 미사용 인덱스 정기 식별·삭제, 복합 인덱스 재설계 | 쓰기 지연, 미사용 인덱스 수 |

## Ⅵ. 성능 튜닝에 대한 기술사적 제언

- 핵심 요약 : 성능 관리를 배포 파이프라인과 운영 관제에 상시로 내장하는 체계를 만들어야 함.

1. 개발 조직은 CI/CD(Continuous Integration/Continuous Delivery) 파이프라인에 **성능 회귀 테스트** (Performance Regression Test, 코드 병합마다 성능 기준선을 다시 검증하는 테스트)를 자동화하고, 기준선 대비 응답 악화 시 배포를 차단해야 한다.
2. 운영 조직은 AIOps(Artificial Intelligence for IT Operations) 기반 관제로 시계열 이상 감지를 도입해, 고정 임계치 알람 이전에 지연 징후를 선제 식별해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 성능 튜닝은 측정과 제거의 반복 공학 활동이며, 자동화된 회귀 검증이 그 효과를 지속시킴.
- 시사점 : 증설보다 측정과 구조 개선이 선행되는 원칙이 비용 대비 성능을 좌우.
