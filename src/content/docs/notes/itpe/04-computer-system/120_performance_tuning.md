## 핵심 용어

- 병목(Bottleneck): 시스템 전체의 흐름을 제한하여 최대 처리량과 응답 속도를 저하시키는 가장 취약한 단일 구성요소 또는 구간
- 베이스라인(Baseline): 튜닝 작업 전 정상 운영 상태에서 시스템이 나타내는 기준 성능 측정값으로, 튜닝 효과의 성공 여부를 입증하는 비교 기준
- 병목 전이(Bottleneck Shifting): 한 계층(예: WAS 스레드 풀)을 튜닝하여 처리량을 늘렸을 때, 그 하위 계층(예: DB 커넥션 풀 또는 디스크 I/O)으로 병목이 이동하여 시스템이 더 크게 마비되는 현상

### Ⅱ. 핵심 특성

- 80/20 파레토 법칙의 지배 → 전체 시스템 성능 저하의 80%는 단 20%의 악성 SQL과 부적절한 인덱스 설계, 그리고 불필요한 반복 네트워크 호출에서 발생하므로, 인프라 파라미터를 건드리기 전에 데이터베이스 쿼리와 애플리케이션 코드를 먼저 정밀 분석해야 함
- 하드웨어 증설(Scale-up)은 근본 해법이 아님 → 락(Lock) 경합이나 소프트웨어 병목이 존재하는 상태에서 CPU를 2배로 늘려도 처리량은 10%도 증가하지 않으며, 오히려 코어 간 캐시 동기화 오버헤드로 인해 응답 지연이 악화될 수 있음
- 튜닝은 한 번에 '오직 하나의 변수'만 변경해야 함 → 여러 파라미터(힙 크기, 스레드 수, 커널 값)를 동시에 수정하면 어떤 변경이 성능 개선을 가져왔고 어떤 변경이 부작용을 일으켰는지 공학적으로 인과관계를 입증할 수 없음

### Ⅲ. 관련 개념과 구분

- 부하 테스트(Load Testing) vs 성능 튜닝(Performance Tuning): 부하 테스트 = 임계치까지 가상 트래픽을 인가하여 시스템의 한계 용량과 취약점을 측정하는 진단 행위 / 성능 튜닝 = 측정된 취약점과 병목의 근본 원인을 찾아 설정을 수정하고 코드를 고치는 치료 행위

### Ⅳ. 적용 문제와 대응

- 적용 상황: 대규모 금융 거래 시스템 개통 전 성능 검증 및 튜닝
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| WAS 스레드 풀을 200에서 1,000으로 늘린 후 오히려 시스템 전체 응답 불가 | 하위 DB 커넥션 풀 고갈 및 CPU의 과도한 문맥 교환(Context Switching) | 리틀의 법칙(Little's Law) 기반 스레드 풀 최적화 및 DB 커넥션 풀 1:1 정합 | 스레드 경합 제거 및 CPU 안정화 |
| 특정 대량 조회 화면 호출 시 JVM의 장시간 정지(Stop-The-World) 발생 | 수십만 건 객체 일괄 메모리 로드로 인한 Major GC 빈발 | 저지연 가비지 컬렉터(ZGC) 전환 및 페이지네이션(Limit/Offset) 강제 | GC 일시 정지 시간을 1ms 미만으로 단축 |
| 특정 테이블 UPDATE 시 동시 접속 트랜잭션 수백 개가 대기열에 걸려 타임아웃 | 인덱스 부재로 인한 테이블 전체 락(Table Lock) 유발 | 복합 인덱스 추가를 통한 로우 레벨 락(Row Lock) 전환 및 트랜잭션 범위 축소 | 락 대기 시간 제거 및 동시 처리량 증대 |
