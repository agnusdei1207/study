## 연관 키워드

- 도커 스웜(Docker Swarm), 컨테이너 오케스트레이션(Container Orchestration), 스웜 모드(Swarm Mode)
- Raft, 라우팅 메시(Routing Mesh), 오버레이 네트워크(Overlay Network), 인그레스(Ingress), IPVS
- 쿠버네티스(Kubernetes), RBAC(Role-Based Access Control), 카나리 배포, 블루-그린 배포, 서비스 메시, Kompose

## Ⅰ. 도커 스웜의 개요

- 핵심 요약 : 도커 엔진에 내장된 경량 컨테이너 오케스트레이션으로, 별도 설치 없이 여러 호스트를 하나의 클러스터로 묶는 도구.
- 개념 : 도커 엔진에 내장된 **도커 스웜** (Docker Swarm, Swarm Mode)은 여러 도커 호스트를 하나의 클러스터로 묶어 컨테이너의 배포, 스케줄링, 스케일링, 로드밸런싱을 수행하는 **컨테이너 오케스트레이션** (Container Orchestration) 도구.
- 배경 및 필요성 : 단일 호스트 도커는 호스트가 장애를 일으키면 서비스가 멈추고 자원 증설에도 한계가 있음. **쿠버네티스** (Kubernetes)는 이를 해결하지만 학습과 운영 부담이 커서, 중소 규모 서비스가 고가용성 클러스터를 손쉽게 구성할 수단이 필요해짐.
- 주요 목적 : 간단한 절차의 클러스터 구축, 선언형 서비스 배포, **오버레이 네트워크** (Overlay Network)와 **인그레스** (Ingress) 기반 부하 분산 지원.

## Ⅱ. 도커 스웜의 특징 및 장점

- 핵심 요약 : 내장 합의 기능으로 외부 저장소 없이 매니저를 이중화하고, 라우팅 메시로 어느 노드에 접속해도 서비스에 닿는 구조.

1. **Raft 합의 알고리즘** 기반 매니저 : 매니저 노드들이 외부 저장소 없이 Raft로 클러스터 상태를 복제 → 리더 장애 시 과반수 투표로 새 리더를 선출해 제어 계층의 고가용성 확보.
2. **라우팅 메시** (Routing Mesh) : 모든 노드가 서비스 게시 포트를 열어 두고 IPVS(IP Virtual Server) 기반으로 요청을 실행 중인 컨테이너에 전달 → 접속한 노드와 무관하게 서비스 연결 유지.

## Ⅲ. 도커 스웜의 구조 및 동작 메커니즘

- 핵심 요약 : 매니저 노드가 상태를 합의하고 워커 노드가 태스크를 실행하며, 외부 진입은 인그레스 라우팅 메시가 맡는 3요소 구조.
- 매니저 노드는 서비스 스펙을 태스크 단위로 나누어 워커에 할당하고, 매니저와 워커 사이의 제어 통신은 TLS(Transport Layer Security) 상호 인증으로 보호됨. 컨테이너 간 통신은 VXLAN(Virtual eXtensible LAN) 기반 오버레이 네트워크를 사용.

```text
[ 도커 스웜 클러스터 구조 ]

매니저 노드 (Raft 합의, 홀수 개 권장)
      ↓ TLS 상호 인증 제어 채널
워커 노드 A (태스크 실행)
워커 노드 B (태스크 실행)
      ↓ VXLAN 오버레이 네트워크
컨테이너 간 통신
```

```text
[ 인그레스 라우팅 메시 흐름 ]

외부 요청 (임의 노드 IP)
      ↓
노드의 게시 포트에서 수신 (IPVS)
      ↓
서비스 태스크가 떠 있는 노드로 전달
```

## Ⅳ. 도커 스웜과 쿠버네티스의 비교

- 핵심 요약 : 설치와 운영의 단순성은 스웜이, 자동화 기능과 생태계의 폭은 쿠버네티스가 우위에 있음.
- 비교 축은 설치, 학습 곡선, 상태 저장소, 오토스케일링, 생태계, 적합 규모이며, 선택 기준은 팀 역량과 워크로드 규모다.

| 비교 축 | 도커 스웜 | 쿠버네티스 |
| :--- | :--- | :--- |
| 설치 | `docker swarm init` 명령으로 즉시 구성 | kubeadm 또는 관리형 서비스 등 절차가 많음 |
| 학습 곡선 | 기존 docker-compose 문법과 거의 같아 낮음 | Pod, Deployment 등 개념이 많아 높음 |
| 상태 저장소 | 매니저에 내장된 Raft 저장소 사용 | 별도의 etcd 분산 키-값 저장소 필요 |
| 오토스케일링 | 기본 기능이 제한적이며 외부 스크립트 결합 필요 | HPA(Horizontal Pod Autoscaler), VPA(Vertical Pod Autoscaler) 등 내장 |
| 생태계 | 유지보수 중심으로 운영되는 추세 | CNCF(Cloud Native Computing Foundation) 중심의 사실상 표준 |
| 적합 규모 | 단일 팀, 소규모 노드, 단순한 웹 서비스 | 다수 마이크로서비스, 하이브리드 환경 등 대규모 운영 |

## Ⅴ. 도커 스웜의 한계와 방안

- 핵심 요약 : 스토리지, 권한 제어, 고급 트래픽 제어의 공백을 외부 구성요소로 보완하는 방식으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 스토리지 오케스트레이션 부족 | 쿠버네티스의 동적 스토리지 프로비저닝에 해당하는 기능이 없어 상태 저장 애플리케이션 운영이 어려움 | 공유 스토리지(NFS, Ceph) 볼륨을 노드에 사전 마운트하거나, 상태 저장 DB를 관리형 서비스로 분리 | 볼륨 마운트 오류 건수 |
| **RBAC** (Role-Based Access Control)와 멀티테넌시 제한 | 하나의 클러스터에서 네임스페이스 격리와 사용자별 API 권한 세분화가 제한되어 전사 공용 운영이 곤란 | 외부 관리 콘솔(예: Portainer)을 연계해 팀별 접근 권한과 정책 보완 | 권한 정책 위반 건수 |
| **카나리 배포** (Canary)와 **블루-그린 배포** (Blue-Green) 미지원 | 롤링 업데이트 외에 가중치 기반 트래픽 전환과 **서비스 메시** (Service Mesh) 연동이 어려움 | 클러스터 앞단에 Traefik이나 Nginx 프록시를 두어 레이블 기반 가중치 라우팅 구현 | 배포 실패 후 롤백 소요 시간 |

## Ⅵ. 도커 스웜 적용에 대한 기술사적 제언

- 핵심 요약 : 조직 역량에 맞는 도구 선정과 단계적 전환 경로 확보로 운영 복잡도와 확장 가능성을 함께 관리.
- SRE 인력이 부족한 조직이라면 쿠버네티스의 복잡도 대신 스웜으로 클러스터를 운영해 장애 대응 부담을 낮추는 선택이 합리적이다.
- 서비스 규모가 커질 때를 대비해 compose 정의를 표준 형식으로 관리하고, Kompose 같은 변환 도구로 쿠버네티스 전환 경로를 미리 검증해 두는 것이 바람직하다.
- 도구 선택 기준을 팀 역량과 워크로드 규모로 명문화하고 전환 시점을 주기적으로 재검토해, 기술 부채가 쌓이지 않도록 관리할 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : 도커 스웜은 내장 합의와 라우팅 메시로 제로 구성 클러스터를 제공하는 경량 컨테이너 오케스트레이션.
- 스토리지, 권한, 트래픽 제어의 공백은 외부 구성요소로 메우되, 규모가 커지면 쿠버네티스 전환을 준비해야 한다.
