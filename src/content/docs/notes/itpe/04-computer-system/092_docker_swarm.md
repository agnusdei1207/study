## Ⅰ. 도커 스웜(Docker Swarm)의 개요

- 개념 : 도커(Docker) 엔진에 기본 내장(Swarm Mode)되어 별도의 외부 에이전트나 복잡한 컨트롤 플레인 설치 없이, 다수의 물리적/가상 도커 호스트들을 단일한 가상 호스트 클러스터로 묶어 컨테이너의 배포, 스케줄링, 스케일링, 로드밸런싱을 수행하는 경량 **컨테이너 오케스트레이션** 도구.
- 배경 및 필요성 : 단일 호스트 도커의 한계(호스트 다운 시 서비스 중단, 자원 증설 한계)를 극복하고, **쿠버네티스** (Kubernetes)의 극심한 학습 곡선과 무거운 운영 인프라 부담을 감당하기 어려운 중소규모 서비스에서 손쉽게 고가용성 클러스터를 구축하기 위해 발전.
- 핵심 목적 : 제로 구성(Zero-Configuration)에 가까운 신속한 클러스터 구축, 선언적 서비스 배포, 내장된 **오버레이 네트워크** 및 **인그레스** 부하 분산 지원.

## Ⅱ. 도커 스웜의 핵심 아키텍처 및 내부 클러스터링 메커니즘

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 도커 스웜 (Docker Swarm Mode) 클러스터 아키텍처 ]                    │
│                                                                        │
│   [ 스웜 매니저 노드 클러스터 (Manager Nodes: 홀수 3/5대 권장) ]       │
│    - Raft 분산 합의 알고리즘 기반 클러스터 상태(State) 완전 동기화     │
│    - 내부 분산 데이터스토어 및 내장 CA(Certificate Authority) 관리    │
│    - 스케줄러: 서비스 스펙(Replicas=N)을 작업(Task)으로 분할 할당      │
│   └───────────────┬────────────────────────────────┬───────────────────┘│
│                   │ gRPC (TLS 상호 인증 2377/TCP)   │                   │
│                   ▼                                ▼                   │
│   [ 워커 노드 1 (Worker Node 1) ]    [ 워커 노드 2 (Worker Node 2) ]   │
│    - containerd / Docker Engine       - containerd / Docker Engine     │
│    - Task (Container Instance)        - Task (Container Instance)      │
│   └───────────────┬────────────────────────────────┬───────────────────┘│
│                   │ VXLAN 오버레이 네트워크 (Overlay Network: 4789/UDP) │
│                   ▼                                                     │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │ [ 인그레스 라우팅 메시 (Ingress Routing Mesh: IPVS 기반) ]     │   │
│   │  - 어느 노드로 들어와도 서비스가 떠 있는 노드로 자동 라우팅    │   │
│   └────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────┘
```

- **Raft 합의 기반 매니저 클러스터** : 매니저 노드들은 외부 DB(etcd 등) 없이 자체 Raft 구현체를 통해 클러스터 상태를 공유하며, 리더 장애 시 과반수 투표로 새로운 리더를 밀리초 단위로 자동 선출.
- **라우팅 메시** (Routing Mesh) : 클러스터 내 모든 노드가 공통 포트를 열어두고, 사용자가 서비스 컨테이너가 없는 노드의 IP(Internet Protocol)로 접속하더라도 리눅스 **IPVS** 기반 오버레이 네트워크를 통해 실제 실행 중인 컨테이너로 투명하게 로드밸런싱.

## Ⅲ. 도커 스웜과 쿠버네티스(Kubernetes) 상세 비교 분석

| 비교 항목 | 도커 스웜 (Docker Swarm) | 쿠버네티스 (Kubernetes) |
| :--- | :--- | :--- |
| **설치 및 셋업** | `docker swarm init` 명령 한 줄로 즉시 완료 | kubeadm, 클라우드 관리형(EKS/GKE) 등 복잡한 절차 |
| **학습 곡선** | 매우 낮음 (기존 docker-compose 문법 거의 동일) | 매우 높음 (Pod, Deployment, CRD 등 방대한 개념) |
| **클러스터 상태 저장소**| 매니저 내부 내장 Raft 엔진 (외부 DB 불필요)| 외부 분산 키-값 저장소인 etcd 클러스터 필수 |
| **오토스케일링** | 수동 스케일링 기본 (외부 스크립트 결합 필요)| HPA(Horizontal Pod Autoscaler; CPU(Central Processing Unit)/메모리/커스텀 메트릭), VPA(Vertical Pod Autoscaler), KEDA(Kubernetes Event-Driven Autoscaling) 내장 |
| **생태계 및 확장성** | 정체 상태 (Mirantis 인수 후 유지보수 위주)| 사실상 클라우드 네이티브 글로벌 표준 (CNCF) |
| **적합한 규모** | 단일 팀, 수십 대 이내 노드, 단순 웹 서비스 | 대규모 엔터프라이즈, 복잡한 MSA(Microservice Architecture), 하이브리드 클라우드|

## Ⅳ. 도커 스웜의 주요 한계점 및 해결 방안

- 복잡한 스토리지 오케스트레이션 및 볼륨 바인딩 한계 :
  - 한계점 : 쿠버네티스의 PVC/PV/StorageClass 같은 동적 스토리지 프로비저닝 기능이 없어 상태 저장(Stateful) 애플리케이션 클러스터링 극히 난해.
  - 해결 방안 : 공유 스토리지(NFS/Ceph) 볼륨 플러그인 사전 마운트 후 전역 마운트하거나 상태 저장 DB는 클라우드 관리형 DB(RDS)로 분리.
- 세분화된 역할 기반 접근 제어(RBAC, Role-Based Access Control) 및 멀티테넌시 부재 :
  - 한계점 : 단일 클러스터 내에서 네임스페이스 격리나 세분화된 유저별 API(Application Programming Interface) 권한 제어가 불가능하여 전사 공용 인프라 운영 불가.
  - 해결 방안 : 포테이너(Portainer Business) 등 외부 상용 관리 콘솔을 연계하여 팀별 접근 권한 및 RBAC 정책 보완.
- 고급 트래픽 제어(카나리, 블루-그린, 서비스 메시) 미지원 :
  - 한계점 : 롤링 업데이트 외에 정밀한 가중치 기반 트래픽 라우팅이나 mTLS 서비스 메시 연동 불가.
  - 해결 방안 : 클러스터 전면에 Traefik 또는 Nginx 인그레스 프록시를 배치하여 서비스 레이블 기반의 가중치 라우팅 구현.

## Ⅴ. 컨테이너 오케스트레이션 실무 적용을 위한 기술사적 제언

- 조직 역량과 워크로드 규모에 기반한 실용적 도구 선정 : 쿠버네티스가 산업계 표준이라 하더라도 전담 SRE(Site Reliability Engineering) 팀이 없는 스타트업이나 소규모 엔터프라이즈 사내 시스템에서는 도커 스웜을 채택하여 운영 복잡도를 획기적으로 낮추고 비즈니스 개발에 집중하는 것이 실용적임.
- 쿠버네티스로의 단계적 마이그레이션 전략 수립 : 서비스 규모가 수백 개 마이크로서비스로 성장할 경우를 대비하여 `docker-compose.yml` 매니페스트를 Kompose 도구를 활용해 쿠버네티스 리소스로 쉽게 변환할 수 있도록 컨테이너 환경 변수와 시크릿 설정을 클라우드 네이티브 표준에 맞추어 모듈화할 것을 제언함.
