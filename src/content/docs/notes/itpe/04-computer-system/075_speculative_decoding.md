## 답안 골격
```text
[추측 디코딩] ◀━━ 머리: Ⅶ 내 의견 (초경량 드래프트 모델과 타깃 LLM 결합을 통한 추론 레이턴시 2.5배 가속 및 서빙 비용 절감)
 ┃
 ┣━ Ⅰ 개요 ───── LLM 자동회귀(Autoregressive) 생성의 토큰당 순차 연산 병목 → 소형 모델 추측과 대형 모델 일괄 검증 결합
 ┣━ Ⅱ 특징 ───── 수학적 무손실(Lossless) 동일 품질 · 메모리 대역폭 병목 극복 · 2~3배 생성 가속 · 병렬 검증
 ┣━ Ⅲ 구조 ───── 드래프트 모델(Small/Draft Model) + 타깃 모델(Large/Target Model) + 검증기(Rejection Sampler)
 ┣━ Ⅳ 흐름 ───── ① 드래프트 모델 K개 토큰 초고속 선제 생성 → ② 타깃 모델 단일 순전파(Forward)로 K개 토큰 동시 검증 → ③ 채택/기각 판정
 ┣━ Ⅴ 비교 ───── 일반 자동회귀 디코딩 vs 추측 디코딩 vs 메두사(Medusa/다중 헤드)
 ┗━ Ⅵ 실무 ───── 수락률(Acceptance Rate) 저하 시 오버헤드 / 드래프트 모델 추가 메모리 점유 / 도메인 편향
```
- 필수 키워드: 추측 디코딩 · 자동회귀 병목 · 드래프트 모델 · 타깃 모델 · 거부 샘플링(Rejection Sampling) · 무손실(Lossless) 가속
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ 드래프트-타깃 2단계 디코딩 아키텍처 도식 → Ⅴ 일반 디코딩 vs 추측 디코딩 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅳ 거부 샘플링 수학적 일치 증명 흐름 및 Ⅵ 엔터프라이즈 vLLM 서빙 엔진 적용 방안

## 한 줄 본질
- 초거대 LLM은 토큰을 1개 뽑을 때마다 수백 GB 가중치 전체를 HBM에서 읽어와야 해 메모리 대역폭 병목(Memory Bound)으로 추론이 느림 → 가벼운 소형 모델이 K개의 토큰을 빠르게 미리 추측해 두고 대형 모델이 1번의 순전파로 이를 한꺼번에 병렬 검증 → 원본 모델과 100% 동일한 품질로 생성 속도 2~3배 향상 / 수락률이 낮으면 추가 검증 연산 낭비 발생

## 핵심 그림
```text
[ 추측 디코딩(Speculative Decoding) 생성 및 병렬 검증 파이프라인 ]

1단계: 초경량 드래프트 모델 (Small Draft Model, 예: Llama-3-1B)
  - 연산량 극소, 초고속으로 K=4개 토큰 연속 자동회귀 추측
  입력: "대한민국의" ──> 추측 생성: [ "수도는", "서울이며", "인구는", "약" ] (매우 빠름!)
                                      │
                                      v
2단계: 초거대 타깃 모델 (Large Target Model, 예: Llama-3-70B)
  - 4개 토큰을 배치(Batch)로 묶어 '단 1번의 병렬 포워드 패스'로 동시 확률 검증!
  - 거부 샘플링(Rejection Sampling) 판정:
    * "수도는"   ──> [ 일치! 수락 (Accept) ]
    * "서울이며" ──> [ 일치! 수락 (Accept) ]
    * "인구는"   ──> [ 일치! 수락 (Accept) ]
    * "약"       ──> [ 불일치! 기각 (Reject) ] ──> 타깃 모델이 직접 새 토큰 "천만" 생성
                                      │
                                      v
  [ 최종 결과: 1번의 대형 모델 순전파로 4개 토큰 동시 확정! (기존 대비 3배 가속) ]
```

## 핵심 용어
- 메모리 대역폭 제약(Memory-Bound): LLM 추론 시 연산 코어(ALU)는 노는데 HBM 메모리에서 가중치를 읽어오는 속도가 느려 전체 성능이 메모리 속도에 묶이는 현상
- 거부 샘플링(Rejection Sampling): 드래프트 모델의 확률 분포 $q(x)$와 타깃 모델의 확률 분포 $p(x)$를 수학적으로 보정하여, 최종 채택된 토큰 분포가 타깃 모델이 단독으로 뽑았을 때와 완벽히 일치하도록 보장하는 알고리즘
- 수락률(Acceptance Rate, $\alpha$): 드래프트 모델이 추측한 토큰이 타깃 모델에 의해 채택되는 비율로, 수락률이 70~80% 이상이어야 실질적인 2배 이상의 속도 가속이 발생함

## 핵심 통찰
- 추측 디코딩은 '수학적으로 공짜 점심'임 → 근사치 모델을 쓰는데도 결과물은 타깃 거대 모델이 처음부터 끝까지 혼자 생성한 것과 수학적 확률 분포가 100% 동일함(Lossless)
- 대형 GPU는 병렬 연산이 남아돎 → 토큰 1개를 처리하나 5개를 한꺼번에 처리하나 HBM에서 가중치 140GB를 읽어오는 시간은 똑같으므로, 남는 연산 텐서 코어를 활용해 5개 토큰을 동시에 검증하는 것이 이득임
- 드래프트 모델이 너무 똑똑할 필요는 없음 → "is", "the", "입니다" 같은 뻔한 접속사와 문법적 어휘만 드래프트 모델이 맞혀줘도, 대형 모델은 복잡한 추론 단어에만 집중할 수 있어 전체 레이턴시가 급감함

## 이웃 토픽과 구분
- 추측 디코딩 vs 모델 양자화(Quantization): 양자화 = 가중치 비트 수를 줄여(INT4/FP8) 모델 자체를 가볍게 만듦(미세한 정확도 손실 가능) / 추측 디코딩 = 가중치를 전혀 손대지 않고 디코딩 순서만 병렬화함(정확도 손실 0%)

## 문제·원인·대책
- 적용 상황: 수만 명의 동시 사용자를 수용하는 상용 LLM 챗봇의 초당 토큰 생성(TPS) 가속화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 코딩이나 수학 문제 등 고난도 추론 시 수락률 급락으로 가속 효과 미미 | 드래프트 소형 모델의 추론 능력이 떨어져 추측 토큰이 연속 기각됨 | 도메인 특화 드래프트 파인튜닝 또는 다중 예측 헤드(Medusa) 기법 채택 | 수락률 75% 이상 회복 및 2배 속도 보장 |
| GPU VRAM이 부족한 환경에서 2개 모델을 동시 적재하지 못함 | 타깃 모델만으로도 80GB VRAM이 가득 차 드래프트 모델 적재 불가 | 모델 비공유 드래프트 대신 타깃 모델 상단에 경량 MLP 헤드만 부착(Medusa) | 추가 메모리 1% 미만 점유로 추측 디코딩 달성 |
