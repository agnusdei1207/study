## 연관 키워드

- 워크플로 스케줄링(Workflow Scheduling), DAG(Directed Acyclic Graph), 백필(Backfill)
- 멱등성(Idempotency), 데이터 구간(data_interval), 논리적 실행 시점(Logical Date)
- 파티션 원자적 교체, Upsert, 동시성 제어(Pool), 지연 도착 데이터(Late Data)
- 오케스트레이션(Orchestration), 데이터 계보(Lineage), Apache Airflow

## Ⅰ. 워크플로 스케줄링·백필의 개요

- 핵심 요약 : 작업 의존성을 방향성 비순환 그래프로 선언해 자동 실행하고, 과거 구간을 소급 재처리하는 백필을 안전하게 결합하는 데이터 파이프라인 운영 기술.
- 개념 : 추출·변환·적재 작업의 선후 관계를 **DAG** (Directed Acyclic Graph, 방향성 비순환 그래프)로 선언해 스케줄러가 자동 실행하는 **워크플로 스케줄링**과, 결함 수정이나 **지연 도착 데이터** (Late Data) 처리를 위해 과거 구간을 다시 실행하는 **백필** (Backfill)의 결합 체계.
- 배경 및 필요성 : cron 수준의 시각 기반 스케줄링은 작업 간 의존성을 표현하지 못해 과거 구간 재처리가 수작업으로 이어지고, 이때 중복 적재와 누락이 잦아 의존성 인식형 오케스트레이션 엔진이 필요.
- 주요 목적 : 의존성의 자동 해소, 과거 구간의 재현 가능한 재처리, 재실행에도 결과가 변하지 않는 **멱등성** (Idempotency) 보장.

## Ⅱ. 워크플로 스케줄링·백필의 특징 및 장점

- 핵심 요약 : 실행 대상을 시각이 아닌 데이터 구간으로 고정하고 파티션 단위 원자적 교체를 결합해 백필의 안전성을 만드는 구조.

1. **논리적 실행 시점** (Logical Date) 기반 실행 : 실제 실행 시각 대신 처리 대상 **데이터 구간** (data_interval)을 파라미터로 전달 → 같은 구간은 언제 실행해도 같은 대상을 처리하므로 백필 결과가 재현되는 효과.
2. 파티션 원자적 교체 : 결과를 임시 위치에 완성한 뒤 메타스토어 포인터를 한 번에 교체 → 백필 도중에도 조회자가 불완전한 데이터를 읽지 않는 효과.
3. 의존성 자동 해소 : 스케줄러가 DAG 위상에 따라 선행 태스크 완료 후 후속 태스크를 기동 → 수작업 의존 관리를 제거하고 병렬 실행으로 처리 시간을 단축하는 효과.
4. 부분 재실행 : 실패 태스크 이후만 재기동하고 선행 결과는 재사용 → 전체 파이프라인 재실행 비용을 절감하는 효과.
5. 동시성 제어 : 풀(Pool)과 병렬 한도로 구간별 실행 개수를 제한 → 백필 폭주로 인한 원천 시스템 과부하를 막는 효과.

## Ⅲ. 워크플로 스케줄링·백필의 구조 (흐름)

- 핵심 요약 : DAG 정의가 스케줄러의 실행 인스턴스 생성과 워커 분배로 이어지고, 백필은 구간 지정부터 원자적 교체까지 같은 경로를 반복하는 구조.

```text
[ DAG 실행 구조 ]

DAG 정의 : 작업·의존성·주기 선언
   ↓
스케줄러 : 실행 인스턴스 생성
   ↓
실행기(Executor) : 워커에 태스크 분배
   ↓
결과를 파티션 단위로 저장
```

```text
[ 백필 실행 흐름 ]

백필 요청 : 대상 구간 지정
   ↓
구간별 DAG Run 순차 생성
   ↓
동시성 한도 내 워커 실행
   ↓
파티션 원자적 교체로 반영
```

- Apache Airflow는 스케줄러, 실행기, 워커로 구성되며 태스크 인스턴스 상태를 메타데이터 데이터베이스에 기록해 재실행 지점을 판단함.
- 데이터 계보(Lineage) 관점에서 상위 태스크의 재실행은 하위 자산 전체로 전파될 수 있으므로 영향 범위 산정이 백필 계획의 선행 요건이 됨.

## Ⅳ. DAG 오케스트레이션과 cron 스케줄링의 비교

- 핵심 요약 : 의존성 표현과 소급 재처리 능력이 cron 방식과 DAG 오케스트레이션을 가르는 핵심 차이.

| 비교 축 | cron 시각 기반 스케줄링 | DAG 오케스트레이션 | 스트림 처리 |
| :--- | :--- | :--- | :--- |
| 의존성 표현 | 없음 (각 작업 독립) | 그래프로 선언적 정의 | 이벤트 시간 기반 |
| 과거 구간 재처리 | 수작업 재실행 | 백필 명령으로 자동화 | 오프셋 조정으로 수행 |
| 부분 재실행 | 스크립트 수정 필요 | 실패 지점부터 재개 | 체크포인트 기반 |
| 지연 도착 대응 | 별도 로직 필요 | 구간 재실행으로 흡수 | 워터마크로 지연 처리 |
| 적합 용도 | 단순 주기 스크립트 | 배치 데이터 파이프라인 | 실시간 집계 |

- 선택 기준 :
  1. 의존성과 백필 요구가 있으면 DAG 오케스트레이션.
  2. 단순 주기 작업이면 cron으로 충분.
  3. 초 단위 실시간성이 필요하면 스트림 처리와의 병행 설계.

## Ⅴ. 워크플로 스케줄링·백필의 한계와 방안

- 핵심 요약 : 백필 폭주, 비멱등 설계, 의존성 오류를 동시성 제어, Upsert 원자적 교체, 데이터 계보 기반 영향 분석으로 일대일 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 백필 폭주 | 수개월 구간 동시 실행 → 원천 데이터베이스 커넥션 고갈 | 풀(Pool) 동시성 제한과 유휴 시간대 실행 | 원천 커넥션 사용률 |
| 비멱등 태스크 | 단순 INSERT 재실행 → 같은 구간 중복 적재로 집계 왜곡 | Upsert 또는 파티션 원자적 교체 강제, 코드 리뷰에 멱등성 점검 반영 | 중복 레코드 수 |
| 의존성 오류 | 잘못된 상위 결과가 하위 전체로 전파 → 오염 범위 확대 | 데이터 계보로 영향 자산을 역추적해 재처리 범위 확정 | 오염 파악 소요 시간 |

## Ⅵ. 워크플로 스케줄링·백필에 대한 기술사적 제언

- 핵심 요약 : 백필을 운영 중 수작업이 아니라 배포 전 검증 대상으로 전환하는 방향.
- 조직 : 데이터 플랫폼 조직이 백필 요청, 승인, 결과 확인의 표준 프로세스를 제정.
- 수단 : 개발 조직이 CI/CD(Continuous Integration/Continuous Delivery) 파이프라인에 스테이징 환경의 가상 백필 검증 단계를 포함.
- 설계 : 파이프라인 설계자가 태스크 중심 선언을 데이터 자산 중심 선언으로 전환해 변경 시 재처리 대상을 자동 식별.

## Ⅶ. 결론

- 핵심 요약 : DAG 의존성 관리와 백필의 결합은 데이터 파이프라인의 재현성과 회복력을 동시에 확보하는 기반 기술.
- 시사점 : 백필의 안전성은 멱등성과 구간 정의가 설계 단계에서 검증될 때 확보됨.
