## 연관 키워드

- 프로세스 동기화(Process Synchronization), 경쟁 상태(Race Condition), 임계 영역(Critical Section)
- 상호 배제(Mutual Exclusion), 뮤텍스(Mutex), 세마포어(Semaphore), 모니터(Monitor)
- 조건 변수(Condition Variable), 우선순위 역전(Priority Inversion), 교착상태(Deadlock), 기아 상태(Starvation)

## Ⅰ. 프로세스 동기화 기법의 개요

- 핵심 요약 : 공유 자원에 대한 동시 접근을 순서대로 통제하여 데이터 일관성을 지키는 운영체제 동시성 제어 기법.
- 개념 : 둘 이상의 실행 흐름이 공유 자원(메모리 변수, 파일, I/O 장치 등)에 동시에 접근할 때, 실행 순서를 조정하여 **경쟁 상태** (Race Condition, 실행 순서에 따라 결과가 달라지는 현상)를 막고 **임계 영역** (Critical Section, 공유 자원에 접근하는 코드 구간)의 진입을 직렬화하는 기법.
- 배경 및 필요성 : 병렬 실행에서 여러 명령어로 이루어진 구간이 **원자성** (Atomicity, 중간에 끊기지 않고 한 번에 수행되는 성질)을 보장받지 못하면 데이터가 왜곡되고, **교착상태** (Deadlock)와 **기아 상태** (Starvation) 같은 결함이 생김.
- 주요 목적 : 임계 영역의 세 가지 요구조건을 충족시켜 공유 자원 접근의 정합성과 시스템 신뢰성을 확보.

임계 영역 구현이 충족해야 할 요구조건은 다음과 같다.

1. **상호 배제** (Mutual Exclusion) : 한 실행 흐름이 임계 영역에 있으면 다른 흐름은 진입할 수 없음.
2. **진행** (Progress) : 임계 영역이 비어 있으면 진입 희망자만 경쟁하며, 그 선택이 무한히 미뤄지지 않음.
3. **한정 대기** (Bounded Waiting) : 진입을 요청한 뒤 허용될 때까지 다른 흐름이 먼저 진입하는 횟수에 상한이 있음.

## Ⅱ. 뮤텍스·세마포어·모니터의 특징 및 장점

- 핵심 요약 : 소유권, 카운터, 캡슐화라는 설계 차이가 각각 단일 구간 보호, 자원 풀 제어, 실수 방지의 장점으로 이어지는 세 기법.

1. **뮤텍스** (Mutex, Mutual Exclusion Object) : 잠금을 획득한 스레드만 해제할 수 있는 이진 잠금 → 단일 임계 영역 보호에 적합하고 잘못된 해제를 막음.
2. **세마포어** (Semaphore, Dijkstra 고안) : 정수 카운터로 가용 자원 수를 관리하고 P·V 연산으로 신호를 주고받음 → 다중 자원 풀과 순서 동기화에 적합.
3. **모니터** (Monitor) : 공유 변수와 프로시저를 하나의 단위로 묶어 한 번에 한 스레드만 진입하게 함 → 언어가 상호 배제를 보장하여 수동 실수가 줄어듦.
4. **조건 변수** (Condition Variable) : 모니터 안에서 조건이 맞을 때까지 대기하고, 조건이 바뀌면 신호로 깨우는 장치 → 생산자·소비자 같은 조건부 대기를 구조적으로 표현.

## Ⅲ. 뮤텍스·세마포어·모니터의 구조 (흐름)

- 핵심 요약 : 세 기법 모두 진입 전 획득과 진출 후 해제의 쌍으로 임계 영역을 감싸되, 해제 주체와 대기 방식이 다름.

```text
[ 뮤텍스: 획득 → 해제 쌍 ]

스레드 A : lock()
   ↓
임계 영역 실행
   ↓
unlock() (획득한 스레드만 가능)
```

```text
[ 세마포어: P·V 연산 ]

P (wait) : S = S - 1
   ↓ S < 0이면 대기 큐 진입
임계 영역 또는 자원 사용
   ↓
V (signal) : S = S + 1
   ↓ 대기 중인 프로세스 1개 깨움
```

```text
[ 모니터: 조건 변수 대기·신호 ]

스레드 진입 (한 번에 1개만)
   ↓
조건 불충족 → x.wait()
   ↓ 락 반납, 조건 큐에서 대기
다른 스레드가 x.signal() 호출
   ↓ 대기 스레드 재개 시도
```

## Ⅳ. 뮤텍스·세마포어·모니터의 비교

- 핵심 요약 : 뮤텍스는 단일 자원의 잠금, 세마포어는 자원 개수의 신호, 모니터는 객체 단위 캡슐화로 구분됨.

| 비교 축 | 뮤텍스 (Mutex) | 세마포어 (Semaphore) | 모니터 (Monitor) |
| --- | --- | --- | --- |
| 추상화 수준 | 운영체제 동기화 객체 | 운영체제 정수형 동기화 변수 | 프로그래밍 언어 수준 구조 |
| 자원 개수 | 1개 (이진 잠금) | 이진 또는 계수형 (N개) | 객체 단위로 캡슐화 |
| 소유권 | 잠근 스레드만 해제 | 소유권 없음 (다른 스레드가 신호 가능) | 모니터 진입 스레드가 반납 |
| 주요 용도 | 단일 임계 영역 상호 배제 | 자원 풀 제어, 순서 동기화 | 객체 상태의 안전한 동기화 |
| 주요 연산 | acquire, release | P(wait), V(signal) | 진입, wait, signal (Java에서는 synchronized, wait, notify) |
| 실수 위험 | 상대적으로 적음 | P·V 순서가 어긋나면 교착상태 유발 | 컴파일러와 런타임이 상호 배제를 보장 |

- 선택 기준 : 보호 대상이 하나의 구간인지, 여러 자원의 개수인지, 객체 상태의 일관성인지에 따라 기법을 고름.

## Ⅴ. 동기화 기법 적용 시 한계와 방안

- 핵심 요약 : 우선순위 역전, 락 순서 꼬임, 신호 의미론 차이가 주요 한계이며, 상속·순서 규칙·재검사 루프로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **우선순위 역전** (Priority Inversion) | 낮은 우선순위 작업이 락을 쥔 채 중간 우선순위 작업에 선점되어 높은 우선순위 작업이 무한정 지연 (1997년 화성 탐사선 패스파인더 사고) | **우선순위 상속** (Priority Inheritance)으로 락 보유자를 대기자 수준으로 일시 승격하거나 우선순위 상한(Priority Ceiling) 프로토콜 적용 | 락 대기 시간, 응답 지연 |
| 교착상태 | 스레드마다 락 획득 순서가 달라 순환 대기(Circular Wait) 발생 | 전역 락 순서(Lock Ordering)를 정해 오름차순으로만 획득, 락 획득 시간 제한(tryLock) 적용 | 락 대기 그래프, 타임아웃 횟수 |
| **Mesa** · **Hoare** 신호 의미론 차이 | 깨어난 스레드가 실행되기 전에 조건이 다시 거짓이 될 수 있음 (Mesa 방식) | 조건 검사를 if 대신 while 루프로 작성하여 깨운 뒤에도 재검증 | 조건 재확인 횟수 |

## Ⅵ. 안전한 동시성 프로그래밍을 위한 기술사적 제언

- 핵심 요약 : 저수준 동기화 직접 조작을 줄이고 언어 수준 추상화와 자동 검출 도구로 실수를 구조적으로 막는 개발 체계.

1. 개발 조직은 세마포어를 직접 조작하는 코드를 줄이고, 언어가 제공하는 모니터 구조(Java의 ReentrantLock, ConcurrentHashMap 등)와 **CAS**(Compare and Swap) 기반 원자적 변수를 기본 선택지로 정해야 한다.
2. 품질 조직은 락 점유 범위를 최소로 유지하는지를 코드 리뷰의 정식 항목으로 두고, **ThreadSanitizer**(TSan) 같은 런타임 레이스 검출기를 빌드 파이프라인에 연동하여 배포 전에 동기화 누락을 걸러내야 한다.

## Ⅶ. 결론

- 핵심 요약 : 뮤텍스, 세마포어, 모니터는 임계 영역의 상호 배제를 서로 다른 추상화 수준에서 구현하는 기법임.
- 시사점 : 자원 수와 소유권 요구에 맞춰 기법을 고르고, 추상화 수준이 높을수록 사람의 실수가 끼어들 여지가 줄어든다는 점이 설계의 기준이 됨.
