## 지식 로드맵 내 현재 위치

지식 위치: 컴퓨터 시스템 → 서비스 가용성 → **HA**

## 30초 인출

- 본질: **HA** 는 한 구성요소가 고장 나도 예비 자원과 절체로 서비스 중단을 줄이는 설계다.
- 메커니즘: 장애를 감지하고 기존 노드를 격리한 뒤 정상 노드로 서비스를 넘긴다. 복구 시간과 데이터 손실 범위는 목표와 실제 시험으로 확인한다.

<details>
<summary>핵심 용어</summary>

- **가용성** : 정해진 기간에 서비스가 정상 제공된 시간의 비율
- **Failover** : 장애가 난 구성요소에서 정상 구성요소로 서비스를 넘기는 동작
- **Quorum** : 클러스터가 어느 노드 집합에서 서비스를 계속 운영할지 결정하는 합의 조건
- **Fencing** : 장애·분할 상황의 노드가 공유 자원을 계속 쓰지 못하도록 격리하는 조치
- **Split-Brain** : 통신이 끊긴 노드들이 각각 자신을 활성 노드로 판단하는 상태
- **RTO** : 장애 후 서비스를 다시 제공할 때까지 허용하는 최대 시간
- **RPO** : 장애가 났을 때 허용하는 최대 데이터 손실 시점 차이

</details>

## 1교시 10점 답안

### 1. 정의·목적

- 정의: **HA** 는 구성요소 장애 시 예비 자원으로 서비스를 넘겨 중단을 줄이는 설계다.
- 목적: 장애로 인한 서비스 중단 시간을 허용 범위 안으로 줄인다.

### 2. 장애 대응 흐름

```mermaid
flowchart TD
    DETECT["활성 노드 장애 감지"] --> CHECK["Quorum 확인·기존 노드 격리"]
    CHECK --> SWITCH["정상 노드로 서비스 절체"]
    SWITCH --> VERIFY["서비스·데이터 상태 확인"]
```

### 3. 목표의 구분

| 지표 | 묻는 것 |
|---|---|
| 가용성 | 측정 기간 중 얼마나 정상 제공했는가 |
| RTO | 장애 후 언제까지 복구해야 하는가 |
| RPO | 어느 시점까지의 데이터 손실을 허용하는가 |

제언: 절체 시험으로 실제 복구 시간과 복구 데이터 시점을 측정해 목표와 비교한다.

## 2~4교시 25점 답안

## Ⅰ. HA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 구성요소 장애 시 예비 자원으로 서비스를 넘겨 중단을 줄이는 설계 |
| 목적 | 서비스 중단 시간을 허용 범위 안으로 줄임 |

## Ⅱ. 장애 감지와 절체

```mermaid
flowchart TD
    DETECT["활성 노드 장애 감지"] --> CHECK["Quorum 확인·기존 노드 격리"]
    CHECK --> SWITCH["정상 노드로 서비스 절체"]
    SWITCH --> VERIFY["서비스·데이터 상태 확인"]
```

장애 감지만으로 대기 노드를 활성화하면 통신 분할 때 두 노드가 동시에 쓰기 작업을 할 수 있다. 공유 자원에 접근하기 전에 운영 권한과 격리 상태를 확인해야 한다.

## Ⅲ. 이중화 구성 선택

| 구분 | Active-Standby | Active-Active |
|---|---|---|
| 정상 시 | 활성 노드가 요청 처리, 대기 노드 준비 | 두 노드 이상이 요청 처리 |
| 장애 시 | 대기 노드로 절체 | 남은 노드로 트래픽 재분배 |
| 설계 초점 | 절체 시간·대기 자원의 준비 상태 | 부하 여유·데이터 일관성·장애 영역 |

어느 구성도 단독으로 가용률이나 무손실 복구를 보장하지 않는다. 데이터 복제와 애플리케이션 재접속까지 함께 설계한다.

## Ⅳ. 장애 유형과 확인할 통제

| 위험 | 통제 | 확인할 결과 |
|---|---|---|
| 노드 간 통신 분할 | Quorum·Fencing | 한쪽만 공유 자원에 쓰는지 |
| 절체 중 연결 끊김 | 재접속·재시도 정책 | 이용자가 다시 처리할 수 있는지 |
| 복제 지연 | 복제 방식·데이터 검증 | 실제 복구 시점이 RPO 이내인지 |
| 절체 지연 | 장애 감지·승격·서비스 확인 시험 | 실제 복구 시간이 RTO 이내인지 |

## Ⅴ. 절체 검증에 대한 제언

| 문제 | 해결 방안 |
|---|---|
| 감지 후 양쪽 노드가 동시에 활성화될 수 있음 | 통신 분할 시험에서 Quorum·Fencing 작동과 단일 쓰기 권한을 확인 |
| 목표 가용률만 제시하고 실제 복구 능력을 모름 | 노드 장애와 데이터 복구를 정기적으로 시험해 RTO·RPO 달성 여부를 기록 |
