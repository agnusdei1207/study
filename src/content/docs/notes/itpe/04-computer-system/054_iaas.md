## 답안 골격
```text
[IaaS] ◀━━ 머리: Ⅶ 내 의견 (공동 책임 모델 기반 인프라 보안 자동화 및 예약 인스턴스/스팟 혼합을 통한 FinOps 최적화)
 ┃
 ┣━ Ⅰ 개요 ───── 물리 하드웨어 도입 리드타임과 CAPEX 부담 → 가상화 기반 컴퓨트·네트워크·스토리지 자원 임대 모델
 ┣━ Ⅱ 특징 ───── 온디맨드 셀프서비스 · 탄력적 확장(Elasticity) · 종량제 과금 · 높은 제어권
 ┣━ Ⅲ 구조 ───── 하이퍼바이저/물리 서버 계층 + 가상 머신(EC2/GCE) + 가상 네트워크(VPC) + 블록 스토리지(EBS)
 ┣━ Ⅳ 흐름 ───── ① 사용자 API/콘솔 요청 → ② 클라우드 오케스트레이터(Nova) 스케줄링 → ③ 하이퍼바이저 VM 프로비저닝 → ④ IP/볼륨 바인딩
 ┣━ Ⅴ 비교 ───── IaaS vs PaaS vs SaaS (관리 책임 영역 비교)
 ┗━ Ⅵ 실무 ───── 공동 책임 모델(Shared Responsibility) 오해로 인한 보안 홀 / 유휴 자원 비용 누수
```
- 필수 키워드: IaaS · 공동 책임 모델 · 가상화(Hypervisor) · 멀티테넌시 · VPC · 탄력성(Elasticity) · FinOps
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ IaaS 핵심 구성요소 도식 → Ⅴ IaaS/PaaS/SaaS 책임 모델 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅳ VM 프로비저닝 내부 흐름 및 Ⅵ 엔터프라이즈 마이그레이션(Lift-and-Shift) 시 비용·보안 최적화
- 기출: 122회 4교시 1번 `IaaS, PaaS, SaaS의 특징 및 구축방법` 논술형 출제

## 한 줄 본질
- 자체 전산실 서버 구매는 초기 구축 비용(CAPEX)이 크고 용량 확장에 수주~수개월이 소요됨 → 하이퍼바이저 기반의 가상화된 하드웨어 자원을 클라우드 API를 통해 실시간 임대 제공 → 인프라 민첩성 및 OPEX 전환 / OS 패치 및 미들웨어 보안 관리 책임이 고객에게 남음

## 핵심 그림
```text

+──────────────────+ +────────────+  +────────────+   +────────────+   +────────────+
| 애플리케이션      | |    고객    |  |    고객    |   |    고객    |   |    CSP     |
| 데이터           | |    고객    |  |    고객    |   |    고객    |   |    CSP     |
| 런타임           | |    고객    |  |    고객    |   |    CSP     |   |    CSP     |
| 미들웨어         | |    고객    |  |    고객    |   |    CSP     |   |    CSP     |
| OS               | |    고객    |  |    고객    |   |    CSP     |   |    CSP     |
+~~~~~~~~~~~~~~~~~~+ +~~~~~~~~~~~~+  +~~~~~~~~~~~~+   +~~~~~~~~~~~~+   +~~~~~~~~~~~~+
| 가상화           | |    고객    |  |    CSP     |   |    CSP     |   |    CSP     |
| 서버 하드웨어    | |    고객    |  |    CSP     |   |    CSP     |   |    CSP     |
| 스토리지         | |    고객    |  |    CSP     |   |    CSP     |   |    CSP     |
| 네트워크 (물리)  | |    고객    |  |    CSP     |   |    CSP     |   |    CSP     |
+──────────────────+ +────────────+  +────────────+   +────────────+   +────────────+
```

## 핵심 용어
- 공동 책임 모델(Shared Responsibility Model): CSP는 클라우드 자체의 보안(하드웨어, 물리 시설)을 책임지고, 고객은 클라우드 내부 자원의 보안(OS, 데이터, 방화벽 규칙)을 책임지는 역할 분담 원칙
- Lift-and-Shift: 온프레미스의 가상머신이나 물리 서버 구성을 변경 없이 그대로 IaaS의 VM으로 1:1 이전하는 마이그레이션 전략
- 멀티테넌시(Multi-tenancy): 하나의 물리적 하드웨어 인프라를 여러 고객이 논리적으로 격리되어 안전하게 공유하는 아키텍처

## 핵심 통찰
- IaaS는 가장 자유롭지만 가장 비효율적인 클라우드임 → 레거시 시스템을 손쉽게 옮길 수 있는 장점이 있지만, OS 관리, 커널 튜닝, 백업 패치를 직접 해야 하므로 클라우드 네이티브의 진정한 운영 절감 효과를 보기 어려움
- 보안 사고의 95% 이상은 CSP가 아니라 고객 과실에서 발생함 → IaaS 환경에서 보안 그룹(Security Group)을 0.0.0.0/0으로 개방하거나 기본 계정 비밀번호를 방치하여 발생하는 침해가 대다수임
- FinOps가 결합되지 않은 IaaS는 온프레미스보다 비쌈 → 24시간 켜져 있는 온디맨드 인스턴스는 3년 TCO 관점에서 온프레미스 하드웨어 구매 비용을 초과하므로 예약 인스턴스(RI)나 절약 플랜(Savings Plans) 전환이 필수적임

## 이웃 토픽과 구분
- IaaS vs PaaS: IaaS = OS와 미들웨어의 완전한 통제권을 고객이 보유(높은 제어권, 무거운 관리 부담) / PaaS = OS와 런타임 환경까지 CSP가 관리하고 고객은 애플리케이션 코드만 배포(낮은 제어권, 가벼운 관리 부담)

| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 클라우드 전환 후 월간 인프라 비용 폭증 | 온프레미스 피크 기준 사이징을 그대로 적용하여 가상머신 오버프로비저닝 | 리소스 사용률 메트릭 분석 후 라이트사이징(Rightsizing) 및 RI 구매 | 불필요한 유휴 VM 스펙 축소로 월 비용 30% 이상 절감 |

## 내 의견
- [IaaS는 클라우드 전환의 종착점이 아닌 과도기 단계로 한정] 온프레미스 레거시를 IaaS로 단순 이전하는 Lift-and-Shift는 인프라 관리 부담을 그대로 유지한 채 비용만 증가시킴 → 나라면: 초기 이전은 IaaS로 빠르게 완료하되, 이후 1년 내 컨테이너 기반(CaaS/PaaS) 또는 서버리스로 단계적 애플리케이션 리팩토링(Re-architecting)을 수행하도록 클라우드 현대화 로드맵을 의무 수립
