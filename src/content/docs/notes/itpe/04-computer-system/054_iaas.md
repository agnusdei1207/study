## 연관 키워드

- 서비스형 인프라, IaaS, CSP, 하이퍼바이저, 소프트웨어 정의 네트워킹, VPC, 블록 스토리지, 오브젝트 스토리지
- 책임 공유 모델, CSPM, CWPP, 라이트사이징, 베어메탈, Lift-and-Shift, 예약 인스턴스, Savings Plans, IaC

## Ⅰ. 서비스형 인프라(IaaS)의 개요

- 핵심 요약 : **서비스형 인프라** (IaaS, Infrastructure as a Service)는 서버, 스토리지, 네트워크 같은 기본 자원을 API(Application Programming Interface)로 임대받아 운영체제 이상을 직접 제어하는 클라우드 서비스 모델.
- 개념 : 기업이 서버를 직접 구매하지 않고 **클라우드 서비스 제공자** (CSP, Cloud Service Provider)가 가상화하여 제공하는 컴퓨팅, 스토리지, 네트워크 자원을 임대받아, 그 위에 운영체제(OS, Operating System), 미들웨어, 애플리케이션을 직접 설치하고 운영하는 클라우드 서비스 모델.
- 배경 및 필요성 : 온프레미스 구축은 자본적 지출(CAPEX, Capital Expenditure)과 긴 하드웨어 납기, 설비 유지 부담이 크므로, 필요한 만큼 빌려 쓰는 방식으로 비용 구조를 운영 비용 중심으로 옮기려는 요구가 생김.
- 핵심 목적 : 프로비저닝의 즉시성에 따른 민첩성 확보, 사용량 기반 운영 비용(OPEX, Operating Expenditure) 전환, 리전 단위의 확장성 확보.

## Ⅱ. 서비스형 인프라(IaaS)의 특징 및 장점

- 핵심 요약 : 가상화, 소프트웨어 정의 네트워크, 분산 스토리지, 루트 제어권이 맞물려 자유도와 민첩성을 함께 제공하는 구조.

1. **컴퓨팅 가상화** : 하이퍼바이저가 물리 서버를 분할해 가상 머신(VM, Virtual Machine)을 API 요청으로 즉시 생성 → 자원 확보 시간 단축.
2. **소프트웨어 정의 네트워킹** (SDN, Software-Defined Networking) : 물리 장비를 건드리지 않고 가상 사설 클라우드(VPC, Virtual Private Cloud), 서브넷, 라우팅 테이블을 API로 구성 → 네트워크 변경의 신속화와 논리적 격리 확보.
3. **분산 스토리지** : 디스크 단위의 **블록 스토리지**와 무제한에 가까운 확장을 목표로 하는 **오브젝트 스토리지**를 풀 형태로 제공 → 용량 증설을 자원 추가로 해결.
4. **루트 제어권** (Root Access) : 고객이 OS 커널 파라미터, 미들웨어, 보안 그룹 규칙을 직접 설정 → 레거시 요구사항을 그대로 반영하는 자유도 확보.

## Ⅲ. 서비스형 인프라(IaaS)의 구조 및 동작 메커니즘

- 핵심 요약 : API로 자원을 요청하면 CSP 관리 영역이 가상 자원을 할당하고, 고객 관리 영역의 OS 이상은 고객이 책임지는 계층 구조.
- 가상화 계층(하이퍼바이저), 물리 자원(서버, 네트워크, 스토리지), 데이터센터 설비는 CSP가 전담하고, 운영체제와 그 위의 미들웨어, 애플리케이션은 고객이 관리함.

```text
[ IaaS 책임 계층 ]

고객 관리 영역
  애플리케이션·미들웨어·데이터베이스
  운영체제 (패치·커널·보안 설정)
   ↓
CSP 관리 영역
  가상화 계층 (하이퍼바이저)
  물리 서버·네트워크·스토리지
  데이터센터 설비
```

```text
[ 자원 프로비저닝 흐름 ]

관리자 또는 자동화 도구
   ↓ API 호출
CSP 제어 평면 (Control Plane)
   ↓ 가상 자원 할당
가상 머신·가상 네트워크·볼륨
   ↓
고객이 OS 이상 구성
```

## Ⅳ. 서비스형 인프라(IaaS)의 비교

- 핵심 요약 : 온프레미스에서 IaaS, PaaS(Platform as a Service)로 갈수록 관리 책임은 CSP로 이동하고 고객의 제어 자유도는 줄어듦.

| 비교 축 | 온프레미스 | IaaS | PaaS(Platform as a Service) |
| --- | --- | --- | --- |
| 자원 조달 | 긴 납기 필요 | API로 즉시 프로비저닝 | 플랫폼 단위로 즉시 사용 |
| OS 및 패치 관리 | 정보기술(IT, Information Technology) 운영팀 전담 | 고객 책임 | CSP 중심 관리 |
| 커스터마이징 | 하드웨어까지 자유 | OS 수준까지 제어 가능 | 플랫폼 제약 내에서 제한 |
| 책임 범위 | 기업이 전부 책임 | OS 이상은 고객, 하부는 CSP | 애플리케이션과 데이터 중심 |
| 비용 구조 | 자본적 지출 중심 | 사용량 기반 운영 비용 | 사용량 기반 운영 비용 (관리 비용 포함) |

- 선택 기준 : 자유도가 가장 높아 기존 레거시 시스템을 수정 없이 옮기는 **Lift-and-Shift** 방식의 이전에 가장 적합함.

## Ⅴ. 서비스형 인프라(IaaS)의 한계와 방안

- 핵심 요약 : 책임 공유 오판, 과다 사이징, 입출력 지연을 보안 점검 자동화, 규격 조정, 하드웨어 격리 선택으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **책임 공유 모델** (Shared Responsibility Model) 오판 | 고객이 OS 패치, 포트 개방, 방화벽 설정을 소홀히 하여 악성코드 감염과 데이터 유출 위험 증가 | 골든 이미지 파이프라인으로 기준 이미지 관리, 취약점 정기 스캔, CSPM(Cloud Security Posture Management)과 CWPP(Cloud Workload Protection Platform) 도입 | 패치 적용률, 설정 위반 건수 |
| 과다 사이징 (Over-provisioning) | 온프레미스 기준 스펙을 그대로 옮겨 중앙 처리 장치(CPU, Central Processing Unit) 이용률이 낮아도 비용이 계속 발생 | **라이트사이징** (Rightsizing, 실사용량에 맞춘 규격 조정) 분석, 유휴 인스턴스 자동 중지 스케줄 운영 | 평균 CPU 이용률, 유휴 인스턴스 비율 |
| 가상화 계층에 따른 입출력 지연 | 하이퍼바이저를 거치면서 고성능 데이터베이스 워크로드의 입출력 성능이 물리 서버 대비 저하될 수 있음 | 하드웨어 오프로드 기능을 갖춘 인스턴스 선택, **베어메탈** (Bare-Metal) 인스턴스 활용 | 입출력 지연 시간, 입출력 연산 수 (IOPS, Input/Output Operations Per Second) |

## Ⅵ. 서비스형 인프라(IaaS)의 기술사적 제언

- 핵심 요약 : 클라우드 네이티브 전환, 구매 약정 포트폴리오, 코드 기반 배포를 묶어 IaaS를 비용과 보안이 통제되는 운영 체계로 전환.

1. 클라우드 네이티브 현대화 : Lift-and-Shift 이후 컨테이너와 서버리스 구조로 점진적 리팩토링하는 로드맵을 두어 장기 운영 비용과 확장성을 함께 개선하는 방향이 바람직함.
2. 구매 약정 포트폴리오 : 상시 가동 자원은 예약 인스턴스(RI, Reserved Instance)와 Savings Plans로, 중단을 허용하는 배치 작업은 스팟 인스턴스로 나누어 구매 전략을 세우는 것이 효과적임.
3. 코드 기반 배포 : 콘솔 수동 프로비저닝을 금지하고 코드형 인프라(IaC, Infrastructure as Code)로 배포하여 형상 관리와 변경 감사가 가능한 상태를 확보하는 것이 전제가 됨.

## Ⅶ. 결론

- 핵심 요약 : IaaS는 기본 자원을 API로 임대하여 가장 높은 자유도를 주지만, 책임 공유와 자원 규격 관리가 운영의 핵심 과제임.
- 시사점 : 자유도는 곧 고객 책임이므로, 빌려 쓰는 자원의 보안 상태와 사용량을 지속 측정하는 체계가 IaaS 도입 효과를 좌우함.
