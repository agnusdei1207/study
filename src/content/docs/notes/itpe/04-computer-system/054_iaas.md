## 연관 키워드

- 서비스형 인프라, IaaS, CSP, 하이퍼바이저, VPC, 블록 스토리지, 오브젝트 스토리지
- 책임 공유 모델, CAPEX, OPEX, 라이트사이징, 베어메탈

## Ⅰ. 서비스형 인프라(IaaS)의 개요

- 핵심 요약 : 서버·스토리지·네트워크 같은 기본 인프라 자원을 API로 임대받아 운영체제 이상을 직접 제어하는 클라우드 서비스 모델.
- 개념 : **클라우드 서비스 제공자** (CSP, Cloud Service Provider)가 가상화하여 제공하는 컴퓨팅·스토리지·네트워크 자원을 필요한 만큼 임대받고, 그 위에 운영체제와 미들웨어, 애플리케이션을 직접 구성하는 **서비스형 인프라** (IaaS, Infrastructure as a Service) 모델.
- 배경 및 필요성 : 온프레미스 구축은 하드웨어 구매에 따른 자본적 지출(**CAPEX**, Capital Expenditure)과 긴 납기, 설비 유지 부담이 커서, 필요한 만큼 빌려 쓰는 운영 비용(**OPEX**, Operating Expenditure) 중심의 조달 구조로 전환이 요구됨.
- 주요 목적 : 자원 프로비저닝의 즉시성에 따른 민첩성 확보, 사용량 기반 비용 구조로의 전환, 자원 규격의 탄력적 조정.

## Ⅱ. 서비스형 인프라(IaaS)의 특징 및 장점

- 핵심 요약 : 가상화, 소프트웨어 정의 네트워크, 풀 형태의 스토리지, 루트 제어권이 자유도와 민첩성을 함께 제공하는 구조.

1. **컴퓨팅 가상화** : **하이퍼바이저** (Hypervisor, 물리 서버를 분할해 여러 가상 머신을 구동하는 소프트웨어)가 물리 자원을 나눔 → API 요청 기반의 즉시 서버 확보.
2. **소프트웨어 정의 네트워킹** (SDN, Software-Defined Networking) : 가상 사설 클라우드인 **VPC** (Virtual Private Cloud)와 서브넷, 라우팅을 API로 구성 → 물리 장비 변경 없는 네트워크 구성과 논리 격리.
3. **분산 스토리지** : 디스크 볼륨 형태의 **블록 스토리지** (Block Storage)와 대규모 확장에 적합한 **오브젝트 스토리지** (Object Storage)를 풀 형태로 제공 → 증설을 자원 추가로 해결.
4. **루트 제어권** (Root Access) : 운영체제 커널 파라미터와 미들웨어, 방화벽 규칙을 고객이 직접 설정 → 레거시 요구사항을 반영하는 자유도 확보.

## Ⅲ. 서비스형 인프라(IaaS)의 구조 (흐름)

- 핵심 요약 : 하부 인프라 계층은 CSP가, 운영체제 이상은 고객이 담당하는 책임 분담 계층 구조.
- **책임 공유 모델** (Shared Responsibility Model) : CSP는 물리 설비와 가상화 계층의 안정성·보호를, 고객은 운영체제 이상의 구성과 데이터를 각자 책임지는 원칙.

```text
[ IaaS 책임 분담 계층 ]

애플리케이션·데이터 (고객 책임)
   ↓
운영체제 (고객 책임 : 패치·설정)
   ↓
가상화 계층 (CSP 책임)
   ↓
물리 서버·네트워크·스토리지 (CSP 책임)
   ↓
데이터센터 설비 (CSP 책임)
```

```text
[ 자원 프로비저닝 흐름 ]

관리자·자동화 도구의 요청
   ↓ API 호출
CSP 제어 평면 (Control Plane)
   ↓ 가상 자원 할당
가상 머신·가상 네트워크·볼륨 생성
   ↓
고객의 운영체제 이상 구성
```

## Ⅳ. 온프레미스와 클라우드 서비스 모델의 비교

- 핵심 요약 : 온프레미스에서 IaaS, PaaS(Platform as a Service)로 갈수록 관리 책임은 CSP로 이동하고 고객의 제어 자유도는 줄어듦.

| 비교 축 | 온프레미스 | IaaS | PaaS |
| --- | --- | --- | --- |
| 자원 조달 | 하드웨어 구매와 납기 필요 | API 기반 즉시 프로비저닝 | 플랫폼 단위 즉시 사용 |
| OS 관리 | 운영 조직 전담 | 고객 책임 | CSP 중심 |
| 제어 범위 | 하드웨어까지 자유 | OS 수준까지 제어 | 플랫폼 규약 내 제한 |
| 고객 책임 범위 | 전 계층 | OS 이상 | 애플리케이션과 데이터 |
| 비용 구조 | 자본적 지출 중심 | 사용량 기반 운영 비용 | 사용량 기반 (관리비 포함) |

- 선택 기준 : 기존 시스템의 수정 없는 이전과 커널 수준 제어가 필요하면 IaaS, 애플리케이션 개발 집중이 우선이면 PaaS를 기준으로 삼음.
- SaaS(Software as a Service)는 애플리케이션까지 제공자가 운영하는 모델로 별도 토픽에서 다룸.

## Ⅴ. 서비스형 인프라(IaaS)의 한계와 방안

- 핵심 요약 : 책임 공유 오판, 과다 프로비저닝, 가상화 지연을 자동 점검, 규격 조정, 격리형 인스턴스로 일대일 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 책임 공유 오판 | 고객 영역의 OS 패치·포트 관리 소홀 → 침해 사고 위험 증가 | 골든 이미지 기반 패치 자동화, 설정 점검 도구의 정기 스캔 | 패치 적용률, 설정 위반 건수 |
| 과다 프로비저닝 | 온프레미스 기준 스펙의 이식 → 낮은 이용률과 불필요 비용 | **라이트사이징** (Rightsizing, 실사용량에 맞춘 규격 조정), 유휴 자원의 자동 중지 | 평균 이용률, 유휴 인스턴스 비율 |
| 가상화 계층의 지연 | 하이퍼바이저 경유로 고성능 워크로드의 입출력 성능 저하 | 하드웨어 오프로드 지원 인스턴스, **베어메탈** (Bare-Metal, 가상화 없는 물리 서버 임대) 선택 | 입출력 지연 시간, 초당 입출력 수 |

## Ⅵ. 서비스형 인프라(IaaS)에 대한 기술사적 제언

- 핵심 요약 : 클라우드 거버넌스 체계, 비용 관리 조직, 전환 로드맵의 세 축으로 IaaS를 통제된 운영 체계로 정착시키는 방향.

1. 거버넌스 조직 : 클라우드 정책 위원회가 자원 명명 규칙과 접근 권한 기준, 배포 절차를 정하고 예외 승인을 통제하는 체계가 바람직함.
2. 비용 관리 조직 : 재무·인프라 부서가 태그 기반 비용 배분과 예산 경보를 운영하여 사용 주체별 책임을 명확히 하는 제도가 필요함.
3. 전환 로드맵 : 이전 이후 컨테이너·서버리스 구조로의 점진적 현대화를 로드맵에 두어 장기 비용과 확장성을 함께 관리하는 방안이 유효함.

## Ⅶ. 결론

- 핵심 요약 : IaaS는 기본 자원의 임대로 최고 수준의 자유도를 제공하는 동시에 고객 책임을 넓히는 서비스 모델.
- 자유도가 곧 고객 책임이라는 원칙의 인식이 IaaS 운영 효과를 좌우함.
