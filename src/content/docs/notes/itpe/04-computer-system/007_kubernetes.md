## 연관 키워드
- Kubernetes, 컨테이너 오케스트레이션, Pod, Service, Deployment, control plane

## Ⅰ. 쿠버네티스의 개요
- 핵심 요약 : 쿠버네티스는 컨테이너화된 애플리케이션의 배포·확장·복구를 선언형으로 자동화하는 오케스트레이션 플랫폼.
- 개념 : **Kubernetes**는 원하는 클러스터 상태를 API 객체로 선언하면 컨트롤러가 실제 상태를 조정하는 컨테이너 플랫폼.
- 배경 및 필요성 : 컨테이너 수가 늘며 배치, 장애 복구, 서비스 탐색, 롤링 배포를 수작업으로 관리하기 어려움.
- 목적 : 분산 애플리케이션의 배포와 운영을 일관된 제어 루프로 관리.

## Ⅱ. 핵심 객체 및 장점
- 핵심 요약 : 선언형 API와 조정 루프가 노드 장애와 수요 변화에 대응.
- Pod는 함께 배치되는 최소 실행 단위 → 컨테이너 간 네트워크·스토리지 공유.
- Deployment는 복제 수와 롤아웃을 관리 → 선언된 버전으로 점진 배포.
- Service는 안정적 네트워크 주소와 로드분산 제공 → 일시적 Pod IP 변화 추상화.
- Scheduler, Controller Manager, API Server, etcd가 제어 평면 구성.

## Ⅲ. 조정 흐름
- 핵심 요약 : 사용자가 원하는 상태를 API에 선언하고 컨트롤러와 노드 에이전트가 실제 상태를 맞춤.
```text
manifest 적용
  ↓ API Server·etcd 저장
Controller가 차이 감지
  ↓ Scheduler가 노드 선택
kubelet이 Pod 실행
  ↓ 상태 보고·재조정
Service로 트래픽 전달
```
```text
원하는 복제 수: 3
실제 실행 수: 2
  ↓ 조정
새 Pod 생성 → 3개로 수렴
```
## Ⅳ. 컨테이너 운영 방식 비교
- 핵심 요약 : 쿠버네티스는 컨테이너 실행 자체보다 여러 노드의 상태 조정과 서비스 운영을 제공.
| 비교 축 | 단일 컨테이너 런타임 | Kubernetes |
| --- | --- | --- |
| 범위 | 호스트의 컨테이너 | 다중 노드 워크로드 |
| 복구 | 외부 자동화 필요 | 선언 상태 기반 재생성 |
| 운영 부담 | 단순하나 수작업 확장 | 기능 풍부·제어 평면 운영 필요 |

## Ⅴ. 한계와 방안
- 핵심 요약 : 복잡한 네트워크·스토리지·권한 구성은 플랫폼 표준과 관측성으로 줄임.
| 한계 | 원인·영향 | 대응 |
| --- | --- | --- |
| 운영 복잡성 | 객체·컨트롤러 다수 | 골든 패스·정책 템플릿 |
| 과잉 권한 | RBAC·서비스 계정 설정 오류 | 최소권한·정기 권한 검토 |
| 자원 경합 | requests·limits 부정확 | 용량 관측·부하 시험 |
| 상태 저장 어려움 | Pod 교체·볼륨 수명 | StatefulSet·백업·복구 점검 |

## Ⅵ. 도입 제언
- 핵심 요약 : 플랫폼팀은 애플리케이션 팀이 안전하게 배포할 공통 경로와 운영 가드레일을 제공.
- 클러스터 버전·접근권한·네트워크 정책·이미지 출처·백업 책임을 문서화.

## Ⅶ. 결론
- 핵심 요약 : Kubernetes는 선언된 상태를 지속 조정해 컨테이너 워크로드의 운영을 자동화.
- 자동 복구와 확장 이점은 플랫폼 역량과 정책 관리가 갖춰질 때 실현.
