## Ⅰ. 시스템 장애 예방·운영 전환(Cutover)의 개요

- 개념 : 차세대 정보시스템 구축, 대규모 클라우드 마이그레이션, 코어 데이터베이스 교체 시, 기존 레거시 시스템에서 신규 목표 시스템으로 비즈니스 다운타임을 최소화하고 데이터 무결성을 보장하며 성공적으로 전환하기 위한 사전 장애 예방 검증 및 **종합 운영 전환(Cutover)** 실행 전략.
- 배경 및 필요성 : 대형 금융권 및 공공기관 차세대 시스템 오픈 당일 데이터 불일치, 성능 저하, 롤백 불가로 인한 서비스 마비 대형 금융사고를 방지하기 위해 정밀한 리허설과 이행 거버넌스가 필수로 요구됨.
- 핵심 목적 : 오픈 당일 무중단 또는 최소 다운타임 달성, **데이터 마이그레이션** 정합성 철저 검증, 비상 상황 시 제한 시간 내 완전 **롤백(Rollback)** 능력 확보.

## Ⅱ. 시스템 장애 예방·운영 전환(Cutover)의 핵심 아키텍처 및 동작 메커니즘

운영 전환은 '전환 계획 수립 -> 모의 전환(Rehearsal) -> 본 컷오버 실행 -> 모니터링 및 안정화'의 4단계 라이프사이클로 수행되며, Go/No-Go 판정 게이트와 **데이터 역이관 파이프라인** 으로 리스크를 통제함.

```text
[ 차세대 시스템 운영 전환(Cutover) 실행 절차 및 판정 게이트 ]

[Phase 1: 사전 준비]
  - 이행 시나리오 작성 (분 단위 타임테이블, R&R 매핑)
  - 1차~3차 모의 전환 리허설 (실제 데이터 기반 반복 검증)
  │
  ▼
[Phase 2: 본 컷오버 개시 (D-Day 연휴/야간)]
  - 기존 레거시 시스템 거래 차단 및 최종 배치 마감
  - 초기 데이터 이관 (Initial Load) + CDC 실시간 차분 데이터 동기화
  │
  ▼
+---------------------------------------------------------------+
| 정합성 검증 (Data Verification: 건수, 금액, 해시 대사 100% 일치) |
+---------------------------------------------------------------+
                                │
                                ▼ 판정 회의
+---------------------------------------------------------------+
| Go / No-Go 의사결정 게이트 (오픈 데드라인 기준)                 |
+---------------------------------------------------------------+
         │                                              │
  [Go 결정: 신규 오픈]                           [No-Go 결정: 롤백]
         │                                              │
         ▼                                              ▼
+-------------------------------+              +----------------+
| 트래픽 신규 시스템으로 절체  |              | 즉각 롤백 실행 |
| (DNS / 로드밸런서 경로 변경)  |              | (기존 시스템   |
| 역방향 CDC 가동 (비상 롤백용) |              |  원상 복구)    |
+-------------------------------+              +----------------+
```

- **분 단위 이행 시나리오 (Runbook)** : 모든 이행 작업을 분(Minute) 단위로 세분화하고 작업자, 검증자, 소요시간, 선행 작업을 정의한 타임테이블 수립.
- **다회차 모의 전환 (Rehearsal)** : 운영 환경과 동일한 인프라에서 여러 차례 실제 운영 데이터를 사용하여 모의 컷오버를 수행하고 작업 시간 단축.
- **CDC(Change Data Capture) 기반 무중단 이관** : 기준 시점 대용량 데이터는 사전 일괄 적재하고, 전환 시점까지 발생하는 변경분은 CDC로 실시간 복제하여 서비스 중단 시간을 극소화.
- **Go/No-Go 의사결정 게이트** : 예정된 마지노선 시간(예: 오픈 당일 새벽 4시)까지 필수 검증 항목이 통과되지 않으면 즉시 오픈을 포기하고 기존 시스템으로 복귀하는 원칙 준수.

## Ⅲ. 시스템 장애 예방·운영 전환(Cutover)의 세부 구성 요소 및 비교 분석

| 전환 전략 (Strategy) | 이행 메커니즘 | 다운타임 및 비용 | 장점 | 리스크 및 단점 |
|---|---|---|---|---|
| **빅뱅 전환 (Big-Bang)** | D-Day 특정 시점에 구 시스템을 전면 내리고 신 시스템 일괄 오픈 | 보통 (수 시간~수일 다운타임) | 시스템 구조 단순, 인터페이스 이중화 불필요 | 장애 발생 시 전면 마비, 롤백 극도로 어려움 |
| **단계적 전환 (Phased)** | 업무 모듈별 또는 사용자 그룹별로 순차적 오픈 | 적음 (업무별 단시간) | 리스크 분산, 문제 조기 발견 | 구-신 시스템 간 장기간 양방향 동기화 부담 |
| **병행 운영 (Parallel)** | 구 시스템과 신 시스템에 트랜잭션을 동시 입력하고 결과 대조 | 높음 (인프라 이중 운영) | 최고 수준의 안전성, 완벽한 무결성 검증 | 이중 입력 비용 발생, 데이터 정합성 충돌 |
| **블루-그린 배포 (Blue-Green)**| 신규 인프라에 미리 배포 후 로드밸런서 트래픽 100% 즉시 전환 | 다운타임 제로 (Zero Downtime)| 즉각적인 롤백 가능, 무중단 전환 | 동일 규모의 이중 인프라 비용 소요 |

- 금융권 차세대에서는 빅뱅 전환을 채택하되 CDC 기반의 준병행 검증을 결합하며, 클라우드 네이티브 MSA 환경에서는 블루-그린 또는 카나리 배포가 표준임.

## Ⅳ. 시스템 장애 예방·운영 전환(Cutover)의 주요 한계점 및 해결 방안

- 전환 작업 **시간 초과(Time Overrun)** 로 인한 영업 개시 불가 :
  - 한계점 : 데이터 이관 및 인덱스 재생성 시간이 예상보다 길어져 은행 영업 시작 시간(오전 9시)까지 전환 미완료.
  - 해결 방안 : 사전 병렬 인덱스 빌드, CDC 기반 사전 동기화, 엄격한 Go/No-Go 마감 시점(Deadline) 설정 및 준수.
- 오픈 후 장애 발생 시 기존 시스템으로의 **역이관(Rollback)** 불가 :
  - 한계점 : 오픈 직후 신규 시스템에서 처리된 신규 거래 데이터가 레거시 시스템에 반영되지 않아 기존 시스템으로 롤백 불가능.
  - 해결 방안 : 신규 시스템에서 레거시 시스템으로 역방향 실시간 복제를 수행하는 '역CDC(Reverse CDC)' 파이프라인 상시 가동.
- 오픈 당일 예상치 못한 성능 병목 및 DB 커넥션 풀 고갈 :
  - 한계점 : 실제 대고객 트래픽 유입 시 쿼리 플랜 변경, 락 경합으로 신규 시스템 응답 지연 및 다운.
  - 해결 방안 : 실운영 트래픽 미러링(Traffic Shadowing) 부하 테스트 수행, 사전 DB 쿼리 플랜 고정(Plan Baseline Freeze).

## Ⅴ. 시스템 장애 예방·운영 전환(Cutover) 적용 및 발전을 위한 기술사적 제언

- 종합 **관제 워룸(War Room)** 및 긴급 상황실 거버넌스 수립 : 비즈니스 현업, 인프라, 애플리케이션, 데이터베이스 전문가가 한자리에 모여 실시간 지표를 공유하는 비상 체계 가동 필수.
- 오픈 후 2주간의 특별 안정화 **기간(Hypercare)** 운영 : 전환 성공 판정 후에도 전담 안정화 TF를 운영하여 미세 튜닝, 미결 데이터 보정 및 모니터링 임계치 상향 관리.
- 클라우드 **카나리(Canary)** 전환 아키텍처 도입 : 전체 트래픽을 한 번에 전환하지 않고 소량부터 단계적으로 가중치 기반 동적 트래픽 절체를 수행하여 리스크 극소화 권장.
