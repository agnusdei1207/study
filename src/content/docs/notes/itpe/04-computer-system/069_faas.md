## 연관 키워드

- FaaS, Function as a Service, 이벤트 트리거, 호출 유형, 콜드 스타트
- 웜 스타트, 프로비저닝드 동시성, 스냅샷 복원, 무상태, Scale-to-Zero, 실행 시간 상한

## Ⅰ. FaaS의 개요

- 핵심 요약 : 이벤트가 발생하면 함수를 기동하고 실행량만큼 과금하는 플랫폼 실행 서비스.
- 개념 : 개발자가 함수 코드만 배포하면 플랫폼이 이벤트에 반응해 실행 환경을 준비하고 회수하는 **서비스형 함수** (FaaS, Function as a Service).
- 배경 및 필요성 : 상시 구동형 서버는 호출이 없는 구간에도 자원 비용이 발생하고, 트래픽 급변에 맞춘 수동 확장은 대응이 늦음. 이벤트 발생 시점에만 자원을 점유하는 실행 모델이 필요.
- 주요 목적 : 인프라 기동·회수를 플랫폼에 위임하고 호출 단위 과금으로 유휴 비용을 제거하는 것.

## Ⅱ. FaaS의 특징 및 장점

- 핵심 요약 : 이벤트 트리거, 무상태 실행, Scale-to-Zero, 실행량 기반 과금이 플랫폼 동작의 축.

1. **이벤트 트리거** (Event Trigger) : HTTP 요청, 메시지 큐, 객체 저장 변경, 스케줄 같은 이벤트가 함수 호출을 직접 유발 → 상시 프로세스 없이 이벤트 시점에만 자원 점유.
2. **무상태** (Stateless, 호출 사이의 상태를 보존하지 않는 실행 방식) : 영속 데이터를 외부 저장소에 위임 → 인스턴스의 자유로운 증감과 수평 확장 용이.
3. **Scale-to-Zero** (호출이 없을 때 실행 인스턴스를 0개로 줄이는 확장 방식) : 미호출 구간의 인스턴스 완전 회수 → 유휴 비용 제거.
4. 실행량 기반 과금 : 호출 횟수와 실행 시간에 할당 메모리를 곱한 단위 청구 → 사용량과 비용이 직결되는 투명한 비용 구조.

## Ⅲ. FaaS의 구조 (흐름)

- 핵심 요약 : 이벤트 라우팅, 웜 풀 판단, 실행 환경 준비, 핸들러 실행, 회수로 이어지는 인스턴스 수명주기.
- 구성 요소 : 이벤트를 함수로 연결하는 컨트롤 플레인, 재사용 가능한 인스턴스의 웜 풀, 마이크로 가상 머신(MicroVM, Micro Virtual Machine) 기반의 격리 실행 환경, 유휴 후 첫 호출에 실행 환경을 새로 만드는 **콜드 스타트** (Cold Start)와 기존 인스턴스를 재사용하는 **웜 스타트** (Warm Start).

```text
[ 호출 처리 경로 ]

이벤트 발생 (HTTP·큐·스토리지·스케줄)
        ↓
컨트롤 플레인 (함수 매핑·라우팅)
        ↓
웜 풀 확인 ──(인스턴스 있음)──> 웜 스타트
        ↓ (없음)
콜드 스타트 (실행 환경 신규 생성)
        ↓
핸들러 실행 → 응답 반환
```

```text
[ 콜드 스타트 지연의 발생 단계 ]

자원 할당 (메모리·네트워크)
        ↓
마이크로VM 기동 (격리 환경 생성)
        ↓
런타임 초기화 (언어 실행기 적재)
        ↓
핸들러 초기화 (초기화 코드·연결 생성)
        ↓
첫 요청 처리 (지연 누적 구간)
```

## Ⅳ. 호출 유형의 비교

- 핵심 요약 : 동기, 비동기, 폴링 소비의 호출 유형에 따라 응답 대기 방식과 재시도 책임이 달라지는 구조.
- 선택 기준 : 호출자의 응답 필요 여부, 이벤트 유실 허용 한도, 처리 순서 요구를 기준으로 호출 유형을 고른다.

| 비교 항목 | 동기 호출 | 비동기 호출 | 폴링·스트림 소비 |
| :--- | :--- | :--- | :--- |
| 호출 계기 | HTTP 요청 등의 직접 호출 | 이벤트 제출 후 즉시 반환 | 큐·로그 스트림의 적재 이벤트 |
| 응답 방식 | 실행 완료까지 호출자 대기 | 결과는 후속 이벤트로 전달 | 함수가 적극적으로 읽어 처리 |
| 재시도 책임 | 호출자 또는 플랫폼 | 플랫폼의 재시도·DLQ(Dead Letter Queue) 전송 | 소비 위치(오프셋) 관리에 따름 |
| 적합 사례 | API 백엔드, 웹훅 처리 | 이미지 변환, 알림 발송 | 데이터 파이프라인, 로그 수집 |

## Ⅴ. FaaS의 한계와 방안

- 핵심 요약 : 콜드 스타트 지연, 실행 시간 상한, 무상태 제약을 사전 기동, 작업 분할, 상태 외부화 설계로 일대일 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 콜드 스타트 지연 | 유휴 후 첫 요청에서 실행 환경 생성 비용이 응답 지연으로 나타남 | **프로비저닝드 동시성** (Provisioned Concurrency, 인스턴스 사전 확보), 스냅샷 복원 방식(예: AWS Lambda SnapStart)의 메모리 상태 재사용, 경량 런타임 채택 | 콜드 호출 비율, 지연 백분위 |
| **실행 시간 상한** | 플랫폼별 최대 실행 시간 제한으로 장기 작업이 중단됨 | 장기 작업을 단계로 분할해 워크플로 오케스트레이션으로 연결, 컨테이너 작업으로 분리 | 상한 초과 실패율 |
| 무상태 제약 | 세션·트랜잭션 상태를 함수 내부에 둘 수 없어 외부 저장소 지연·비용 추가 | 상태를 관리형 데이터베이스·캐시로 위임, 다중 함수 흐름은 보상 트랜잭션 기반의 사가 패턴 적용 | 상태 조회 지연, 트랜잭션 실패율 |

## Ⅵ. FaaS에 대한 기술사적 제언

- 핵심 요약 : 워크로드 적합성 선별, 이벤트 계약 관리, 비용 거버넌스로 FaaS 운영을 조직 체계로 정착.

1. 적합성 선별 : 플랫폼 조직은 짧은 요청-응답과 간헐적 호출의 백엔드·비동기 변환에 우선 적용하고, 상시 연결·고부하 처리는 컨테이너와 혼용하는 배치 기준 수립.
2. 이벤트 계약 관리 : 개발 조직은 함수 간 이벤트 스키마의 버전 관리용 이벤트 레지스트리 운영으로 소비자 함수 파손 사고 예방.
3. 비용 거버넌스 : 재무 조직과 개발 조직은 호출 수·실행 시간 지표에 비용 경보를 연동한 FinOps 체계의 상시 운영.

## Ⅶ. 결론

- 핵심 요약 : FaaS는 이벤트 시점에만 자원을 점유하는 무상태 함수 실행 플랫폼.
- 기동 지연, 실행 시간 상한, 상태 외부화라는 플랫폼 메커니즘의 제약을 감당할 수 있는 워크로드 판별이 도입의 출발점.
