## 연관 키워드

- 쿠버네티스(Kubernetes), 컨테이너 오케스트레이션(Container Orchestration), 컨트롤 플레인(Control Plane), 워커 노드(Worker Node)
- 선언적 구성(Declarative Configuration), 조정 루프(Reconcile Loop), 자가 치유(Self-healing), etcd
- 파드(Pod), 디플로이먼트(Deployment), 스테이트풀셋(StatefulSet), 데몬셋(DaemonSet), 서비스(Service), CNI(Container Network Interface)

## Ⅰ. 쿠버네티스의 개요

- 핵심 요약 : 컨테이너의 배포·확장·복구를 선언된 상태 기준으로 자동화하는 오케스트레이션 플랫폼.
- 개념 : **쿠버네티스** (Kubernetes)는 컨테이너화된 애플리케이션의 배포, 스케일링, 서비스 연결, 장애 복구를 원하는 상태의 선언으로 자동화하는 **컨테이너 오케스트레이션** (Container Orchestration) 플랫폼. 구글의 클러스터 관리 경험(보그, Borg)을 바탕으로 공개되어 CNCF(Cloud Native Computing Foundation)가 관리.
- 배경 및 필요성 : 마이크로서비스의 확산으로 운영 대상 컨테이너 수가 급증하면서 수동 배포와 장애 복구의 한계가 드러남.
- 주요 목적 : 선언적 운영으로 가용성 확보, 인프라 추상화를 통한 이식성 확보, 자원 활용률의 향상.

## Ⅱ. 쿠버네티스의 특징 및 장점

- 핵심 요약 : 선언적 구성과 자가 치유, 자동 확장이 수동 개입 최소화라는 장점으로 연결되는 운영 체계.

1. 선언적 운영 : 원하는 상태(Desired State)를 명세로 제출하면 시스템이 그 상태에 수렴하는 **선언적 구성** (Declarative Configuration) 방식 → 배포 절차의 표준화와 수동 개입 감소.
2. 자가 치유 : 장애가 발생한 파드를 감지해 재시작하거나 다른 노드에 재배치하는 **자가 치유** (Self-healing) → 장애 복구 시간의 단축.
3. 서비스 디스커버리 : 변동하는 파드 주소를 고정 가상 주소로 추상화하는 **서비스** (Service) 객체 → 클라이언트 설정 변경 없는 연결 유지.
4. 수평 확장 : 메트릭 기준으로 파드 수를 자동 조정하는 HPA(Horizontal Pod Autoscaler) → 부하 변화의 선제 대응.
5. 무중단 배포 : 롤링 업데이트와 롤백의 내장 → 배포 실패 리스크의 축소.

## Ⅲ. 쿠버네티스의 구조 (흐름)

- 핵심 요약 : 컨트롤 플레인이 상태를 저장·판단하고 워커 노드가 실행을 담당하며 조정 루프가 양자를 일치시킴.

1. **컨트롤 플레인** (Control Plane) : kube-apiserver(모든 접근의 관문), etcd(분산 키-값 저장소), kube-scheduler(파드 배치 판단), kube-controller-manager(상태 수렴 담당)의 집합.
2. **워커 노드** (Worker Node) : 실제 워크로드가 실행되는 노드로 kubelet(컨테이너 생명주기 관리)과 kube-proxy(트래픽 규칙 적용)가 동작.
3. **파드** (Pod) : 하나 이상의 컨테이너가 네트워크와 스토리지를 공유하는 최소 실행 단위.
4. **조정 루프** (Reconcile Loop) : 원하는 상태와 현재 상태를 지속 비교해 차이를 해소하는 핵심 메커니즘.

```text
[ 선언 요청의 처리 흐름 ]

kubectl (매니페스트 제출)
   ↓
kube-apiserver (인증 · 검증)
   ↓
etcd (원하는 상태 기록)
   ↓
컨트롤러 · 스케줄러 (차이 감지 · 배치)
   ↓
kubelet (컨테이너 런타임 실행)
```

```text
[ 조정 루프 ]

원하는 상태 ↔ 현재 상태 비교
   ↓ 차이 존재
조정 동작 (생성 · 갱신 · 재배치)
   ↓
상태 수렴 확인 후 대기
```

## Ⅳ. 쿠버네티스의 워크로드 리소스 비교

- 핵심 요약 : 상태 유지 여부, 실행 범위, 실행 주기에 따라 파드를 감싸는 상위 리소스의 선택이 갈림.

| 리소스 | 역할 및 메커니즘 | 적합 용도 |
| --- | --- | --- |
| **디플로이먼트** (Deployment) | 파드 수 유지, 롤링 업데이트·롤백 제어 | 무상태 웹 서비스, API 서버 |
| **스테이트풀셋** (StatefulSet) | 순차 배치, 영속 볼륨, 안정적 네트워크 식별자 제공 | 데이터베이스, 메시지 브로커 |
| **데몬셋** (DaemonSet) | 모든(또는 지정) 노드마다 파드를 하나씩 실행 | 로그 수집, 모니터링 에이전트 |
| 잡 · 크론잡 (Job · CronJob) | 일회성 또는 주기적 실행의 완료 보장 | 배치 처리, 정기 점검 작업 |

- 선택 기준 : 상태 유지와 식별자의 필요 여부, 노드 전체 실행의 필요성, 실행 주기의 유무를 기준으로 리소스를 선택하고 배포 흐름은 디플로이먼트 계열로 통일하는 방식이 일반적.

## Ⅴ. 쿠버네티스의 한계와 방안

- 핵심 요약 : 상태 저장소 병목, 설정 복잡성, 보안 설정 오류를 저장소 분리, 표준화, 정책 자동 검증으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| etcd 병목 | 노드·이벤트 증가로 쓰기 지연 발생 → API 응답 저하와 장애 확산 | etcd 전용 고속 저장소 배정, 이벤트 데이터의 저장소 분리 | etcd 쓰기 지연 시간 |
| 설정 복잡성 | 방대한 개념과 매니페스트 → 학습 곡선과 설정 오류 증가 | 조직 표준 템플릿 제공, 검증 도구의 파이프라인 내장 | 배포 실패율 |
| 보안 설정 오류 | RBAC(Role-Based Access Control) 과권한과 비밀 값 노출 → 침해 위험 | 정책 엔진으로 매니페스트 자동 검증, 외부 비밀 값 관리 연계 | 정책 위반 건수 |
| 네트워크 오버헤드 | 오버레이 캡슐화로 처리량 저하와 추적의 어려움 | **CNI** (Container Network Interface) 플러그인 교체와 네트워크 가시성 도구 | 패킷 처리량 |

## Ⅵ. 쿠버네티스에 대한 기술사적 제언

- 핵심 요약 : 개발자 셀프서비스 플랫폼, 버전 운영 절차화, 가속기 자원 관리로 플랫폼 성숙도를 높이는 방향.

- 플랫폼 엔지니어링 조직은 표준 템플릿과 자동화를 묶은 **IDP** (Internal Developer Platform)를 제공하여 개발 팀이 환경을 직접 구성하는 셀프서비스 체계를 마련.
- 클러스터 운영 조직은 버전 업그레이드 주기와 지원 버전 범위 정책을 운영 절차로 고정하여 구성 요소 간 버전 불일치를 예방.
- 인공지능(AI, Artificial Intelligence) 워크로드 운영 조직은 그래픽 처리 장치(GPU, Graphics Processing Unit)를 파티셔닝해 다수 작업에 분배하는 방식으로 가속기 가동률을 관리.

## Ⅶ. 결론

- 핵심 요약 : 쿠버네티스는 선언적 조정 루프로 컨테이너 운영을 자동화하는 사실상의 표준 오케스트레이션 체계.
- 제어 평면의 안정성과 정책의 자동 검증 수준이 플랫폼 신뢰도를 좌우함.
