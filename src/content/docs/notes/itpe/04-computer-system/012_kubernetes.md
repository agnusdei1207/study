## 지식 로드맵 내 현재 위치

컴퓨터 시스템 및 네트워크 → 핵심 개념 → 쿠버네티스

## 30초 인출

- 본질: 수백~수천 개 컨테이너의 수작업 배포, 네트워크 라우팅, 장애 복구의 운영 한계
- 메커니즘: 선언적 상태(Desired State) 정의와 연속적인 조정 루프(Reconciliation Loop)를 통해 컨테이너 수명주기를 자동 제어

## 핵심 용어

- 파드(Pod): 쿠버네티스에서 생성하고 관리할 수 있는 배포의 가장 작은 단위로, 네트워크 네임스페이스와 스토리지를 공유하는 1개 이상의 컨테이너 집합
- etcd: 클러스터의 모든 상태 정보(설정, 오브젝트 명세, 현재 상태)를 키-값 형태로 안전하게 보관하는 고가용성 분산 일관성(Raft 기반) 저장소
- 조정 루프(Reconciliation Loop): 컨트롤러가 현재 상태(Current State)를 감시(Watch)하다가 사용자가 선언한 목표 상태(Desired State)와 달라지면 둘을 일치시키도록 동작하는 핵심 메커니즘

### Ⅱ. 핵심 특성

- 쿠버네티스는 '명령형(Imperative)'이 아닌 '선언형(Declarative)' 엔진임 → "컨테이너를 지금 띄워라"가 아니라 "항상 파드 3개가 유지되게 하라"고 선언하면 노드가 죽어도 다른 노드에 스스로 파드를 복구
- 쿠버네티스 생태계의 폭발적 성장은 표준 인터페이스(CRI: 런타임, CNI: 네트워크, CSI: 스토리지)의 분리 덕분임 → 클라우드 벤더나 특정 스토리지 제품에 종속되지 않고 자유로운 플러그인 교체 가능
- etcd의 쿼럼(Quorum) 상실은 곧 클러스터 마비를 의미하므로, 프로덕션 환경에서는 3대 이상의 홀수 노드 구성과 주기적인 스냅샷 백업이 클러스터 생존의 절대 조건임

### Ⅲ. 관련 개념과 구분

- 쿠버네티스 vs 도커 스웜: 도커 스웜 = 설치와 학습이 단순하나 대규모 엔터프라이즈 기능 부족 / 쿠버네티스 = 복잡하지만 오토스케일링, 서비스 메시, 확장성(CRD/Operator) 측면에서 글로벌 사실상 표준(De-facto Standard)

### Ⅳ. 적용 문제와 대응

- 사례: 137회 기출 쿠버네티스 대규모 배포 시 노드 장애로 인한 서비스 중단 및 etcd 응답 지연
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 워커 노드 하드웨어 결함 시 파드 스케줄링 지연으로 서비스 장애 | 기본 노드 축출(Eviction) 대기 시간(5분) 설정 과다 | 파드 중단 예산(PDB) 및 토폴로지 분산 제약(TopologySpreadConstraints) 적용 | 노드 장애 시에도 최소 가용 파드 유지 및 다중 존 분산 |
| 클러스터 규모 확대 시 API Server 및 스케줄러 먹통 | etcd 디스크 I/O 병목 및 대량의 이벤트(Event) 객체 누적 | etcd 전용 초고속 NVMe 분리 및 비핵심 이벤트 자동 TTL 만료 설정 | API Server 응답 속도 및 클러스터 안정성 확보 |
