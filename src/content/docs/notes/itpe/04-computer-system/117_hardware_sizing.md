## 연관 키워드

- 하드웨어 규모산정(Hardware Sizing), 용량 계획(Capacity Planning), 여유율(Headroom)
- TPS(Transactions Per Second), tpmC, TPC-C, 피크 계수
- 과소 산정, 과대 산정, IOPS(Input/Output Operations Per Second)
- OLTP(Online Transaction Processing), OLAP(Online Analytical Processing), 오토스케일링

## Ⅰ. 하드웨어 규모산정의 개요

- 핵심 요약 : 업무 요건을 서버·스토리지·네트워크의 필요 용량으로 환산해 구축 근거를 만드는 공학적 용량 계획 활동.
- 개념 : 동시 사용자 수, 일일 트랜잭션, 데이터 볼륨, 응답 시간 목표를 중앙처리장치(CPU, Central Processing Unit)·메모리·디스크·네트워크 자원량으로 산출하는 **하드웨어 규모산정** (Hardware Sizing) 활동으로, **용량 계획** (Capacity Planning)과 같은 의미로 통용.
- 배경 및 필요성 : **과소 산정** (Under-sizing)은 오픈 직후 성능 장애로, **과대 산정** (Over-sizing)은 예산 낭비와 라이선스 비용 증가로 직결되므로 객관적 산정 근거가 필요.
- 주요 목적 : 적정 인프라 용량 도출, **총소유비용** (TCO, Total Cost of Ownership) 최적화, 피크 트래픽 수용과 향후 증설 여지 확보.

## Ⅱ. 하드웨어 규모산정의 특징 및 장점

- 핵심 요약 : 요건의 수치화와 피크 기준, 공인 벤치마크, 여유율 반영이 과소·과대 산정을 함께 줄이는 구조.

1. 요건의 수치화 : 동시 접속·일일 트랜잭션을 **TPS** (Transactions Per Second, 초당 트랜잭션 수)로 환산 → 자원 산정 입력의 표준화.
2. 피크 기준 산정 : 평균 부하에 **피크 계수** (Peak Factor, 최대 부하와 평균 부하의 비율)를 곱해 최대 부하 기준으로 환산 → 피크 시간대 장애 예방.
3. 공인 벤치마크 환산 : **TPC-C** (Transaction Processing Performance Council-C) 벤치마크의 **tpmC** (Transactions Per Minute C) 지표로 코어 수 산출 → 예산 심사의 객관적 근거 확보.
4. 여유율 반영 : **여유율** (Headroom, 향후 데이터 증가와 운영 비효율을 흡수하는 예비 용량)을 최종 산정치에 가산 → 계획 수명 기간 내 용량 보장.

## Ⅲ. 하드웨어 규모산정의 구조 (흐름)

- 핵심 요약 : 요건 정의, 부하 분석, 자원별 산정, 여유율 반영의 순차 절차와 자원별 계산 구성.

```text
[ 규모산정 4단계 절차 ]

1. 업무 요건 정의
   동시 접속, 일일 트랜잭션, 응답 시간
      ↓
2. 부하 분석
   평균 트랜잭션 × 피크 계수
      ↓
3. 자원별 용량 산정
   CPU, 메모리, 디스크, 네트워크
      ↓
4. 여유율 반영과 검증
   증가율 가산, 부하 테스트 확인
```

```text
[ 자원별 산정 구성 ]

CPU
  필요 tpmC ÷ 코어당 성능치 = 코어 수
Memory
  운영체제 + 런타임 힙 + 캐시
Disk
  데이터 볼륨 × 증가율 × 이중화 배수
Network
  피크 TPS × 평균 처리 크기
```

- CPU 산정 : 필요 tpmC에 시스템·업무 보정 계수를 곱한 뒤 코어당 공인 성능치로 나누어 코어 수를 구하는 절차.
- 스토리지 산정 : 용량과 함께 **IOPS** (Input/Output Operations Per Second, 초당 입출력 동작 수)와 큐 깊이를 함께 산정해야 병목 예측이 가능.

## Ⅳ. 워크로드 유형별 규모산정 기준의 비교

- 핵심 요약 : 워크로드마다 부하의 성격이 달라 산정 지표와 초점이 달라지는 구조.

| 워크로드 유형 | 대표 업무 | 핵심 산정 지표 | 산정 초점 |
| :--- | :--- | :--- | :--- |
| **OLTP** (Online Transaction Processing) | 업무 시스템, 예약·조회 | TPS, 응답 시간 | CPU 코어 수, 커넥션 수 |
| 배치 (Batch) | 정산, 대량 집계 | 배치 윈도 처리 시간 | CPU, 디스크 처리량 |
| **OLAP** (Online Analytical Processing) | 리포팅, 통계 분석 | 쿼리 처리량, 스캔량 | 메모리, 스토리지 대역폭 |
| 웹·파일 서비스 | 포털, 문서 저장 | 동시 접속 수, 저장 증가율 | 메모리, 디스크 용량 |

- 선택 기준 : 복합 워크로드는 유형별로 나누어 산정한 뒤 합산하되, 부하가 겹치는 피크 시간대를 기준으로 삼는 기준.

## Ⅴ. 하드웨어 규모산정의 한계와 방안

- 핵심 요약 : 공식 산정의 현실 괴리, 중앙처리장치 중심 산정의 맹점, 정적 산정의 경직화가 주요 한계이며 복합 지표, 풀스택 산정, 재산정 체계로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 공식 산정의 현실 괴리 | 마이크로서비스·가상화 구조가 공식에 충분히 반영되지 않음 → 산정 오차 | TPS·메모리·네트워크 I/O를 함께 보는 복합 지표 산정 | 산정치 대비 실측 오차율 |
| CPU 중심 산정의 맹점 | 코어는 충분해도 IOPS·대역폭 부족 → 응답 지연 | 용량과 함께 IOPS·큐 깊이를 포함한 풀스택 산정 | 디스크 큐 대기 시간 |
| 정적 산정의 경직화 | 오픈 후 부하 변화 미반영 → 과잉·과소 고정 | 주기적 재산정과 오토스케일링 정책 연계 | 자원 사용률 |

## Ⅵ. 하드웨어 규모산정에 대한 기술사적 제언

- 핵심 요약 : 산정은 계산으로 끝낼 작업이 아니라 실측 검증과 운영 계측으로 갱신되는 순환 활동으로 정착시켜야 함.

1. 발주 기관은 제안요청서와 계약에 산정 근거 제출과 부하 테스트 기반 검증 조건을 명시해, 수식 계산만으로 끝나는 산정을 막아야 한다.
2. 운영 조직은 APM(Application Performance Monitoring) 계측 데이터로 분기 단위 재산정을 수행하는 FinOps 기반 용량 관리 체계를 정착시켜야 한다.

## Ⅶ. 결론

- 핵심 요약 : 하드웨어 규모산정은 자원 발주 전에 근거를 만드는 용량 계획 활동.
- 시사점 : 산정 공식과 운영 계측을 하나의 순환으로 연결할 때 과소·과대 산정 비용이 함께 줄어듦.
