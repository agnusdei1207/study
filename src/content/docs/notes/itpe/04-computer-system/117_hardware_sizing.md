## Ⅰ. 하드웨어 규모산정(Hardware Sizing)의 개요

- **개념** : 정보시스템 구축 및 고도화 사업에서 목표 비즈니스 요구사항(동시 사용자 수, 일평균 트랜잭션, 데이터 볼륨, 응답 시간 SLA)을 안정적으로 수용하기 위해 필요한 서버(CPU, Memory), 스토리지(Disk, IOPS), 네트워크 대역폭 등 하드웨어 자원의 용량을 공학적·수학적으로 산출하는 용량 계획(Capacity Planning) 방법론.
- **배경 및 필요성** : 하드웨어를 과소 산정(Under-sizing)할 경우 오픈 당일 시스템 다운과 비즈니스 장애가 발생하고, 과대 산정(Over-sizing)할 경우 막대한 공공/기업 예산 낭비 및 라이선스 비용 폭증을 초래하므로 객관적인 산정 기준이 필수적임.
- **핵심 목적** : 적정 인프라 용량 도출, TCO(총소유비용) 최적화, 피크 타임(Peak-time) 트래픽 수용 및 향후 데이터 증가율을 반영한 확장성(Scalability) 확보.

## Ⅱ. 하드웨어 규모산정 3대 방식 및 표준 산정 절차

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ 하드웨어 규모산정 표준 4단계 절차 및 핵심 산정 수식 ]                │
│                                                                        │
│   [ 1단계: 업무 요건 및 기초 데이터 조사 ]                             │
│    - 목표 응답시간, 동시 접속자 수, 일/초당 트랜잭션 수(TPS) 도출     │
│                     │                                                  │
│                     ▼                                                  │
│   [ 2단계: 피크 계수 및 시스템 부하 분석 ]                             │
│    - 기본 트랜잭션 = (일일 트랜잭션 수 / 업무 시간)                    │
│    - 피크 트랜잭션 = 기본 트랜잭션 × 피크율 (Peak Factor: 1.5 ~ 3.0)   │
│                     │                                                  │
│                     ▼                                                  │
│   [ 3단계: 공학적 하드웨어 용량 산정 계산 ]                            │
│    - CPU 산정 (TPC-C 기반 tpmC):                                       │
│      보정 tpmC = 피크 tpmC × 시스템 계수 × 업무 계수                   │
│      소요 CPU Core = 보정 tpmC / (코어당 공인 tpmC 성능치)              │
│    - Memory 산정: OS 기본 + WAS 인스턴스 힙 + DB 버퍼풀 + 캐시 + 마진   │
│    - Disk 산정: 데이터베이스 순수 볼륨 × 여유율 × 인덱스/로그 배수 × RAID│
│                     │                                                  │
│                     ▼                                                  │
│   [ 4단계: 여유율(Headroom) 및 미래 증가율 적용 최종 확정 ]            │
│    - 연간 데이터 증가율(Compound Growth), 안전 마진 반영       │
└────────────────────────────────────────────────────────────────────────┘
```

- **TPC-C 벤치마크 기반 tpmC 산정** : 데이터베이스 서버의 트랜잭션 처리 성능을 분당 트랜잭션 처리 건수(tpmC: Transactions Per Minute C)로 표준화하여 공인 벤치마크 점수에 따라 필요 코어 수를 산출.
- **보정 계수(Correction Factors) 적용** : 실제 운영 환경의 비효율성을 반영하기 위해 클러스터 다중화 계수, 피크 부하 계수, 통신 프로토콜 암호화(TLS) 부하 계수를 곱하여 안전 마진 확보.

## Ⅲ. 하드웨어 규모산정 3대 방법론 비교 분석

| 비교 항목 | 분석적 기법 (Mathematical / TPC) | 참조 모델 기법 (Reference / Analogy)| 시뮬레이션 및 부하 테스트 (PoC/Benchmark)|
| :--- | :--- | :--- | :--- |
| **산정 원리** | 표준 산정 공식 및 벤치마크(tpmC) 수식 대입| 유사 규모의 기존 운영 시스템 실측치 차용| 가상 부하 생성기를 통한 실제 한계 측정 |
| **적용 시점** | 사업 기획, 예산 수립, 발주 RFP 단계 | 차세대 전환, 동종 업계 레퍼런스 존재 시| 시스템 오픈 직전 검증, 성능 튜닝 단계 |
| **정확도** | 중간 (이론적 계산으로 실제 병목 미반영)| 중간 ~ 높음 (유사 업무 특성 반영) | **최고 (실제 애플리케이션 병목 직접 검증)**|
| **소요 비용/시간**| 낮음 (공식 기반 신속한 문서 산정) | 낮음 ~ 중간 | 높음 (테스트베드 구축 및 부하 도구 필요) |
| **주요 장점** | 공공 발주 시 객관적 예산 승인 근거 제공| 실제 운영 경험치가 녹아 있어 실용적 | 숨겨진 아키텍처/DB 락 결함 사전 발견 |

## Ⅳ. 하드웨어 규모산정의 주요 한계점 및 해결 방안

- **공공 소프트웨어 사업 대가기준 공식의 현실 괴리** :
  - **한계점** : 한국정보사회진흥원(NIA)의 전통적 tpmC 기반 규모산정 공식이 최신 멀티스레드 CPU 아키텍처나 클라우드 마이크로서비스(MSA) 환경을 반영하지 못함.
  - **해결 방안** : 단순 tpmC 일변도에서 탈피하여 서비스별 동시 트랜잭션(TPS), 메모리 풋프린트, 네트워크 I/O 기반의 복합 사이징 가이드라인 적용.
- **CPU 코어 중심 산정으로 인한 I/O 및 메모리 병목 간과** :
  - **한계점** : CPU 코어 수는 충분히 산정했으나 스토리지 IOPS나 네트워크 대역폭 부족으로 시스템 응답 지연 발생.
  - **해결 방안** : Full-Stack 규모산정 수행, 스토리지 산정 시 단순 용량(GB) 외에 반드시 요구 IOPS 및 큐 깊이(Queue Depth) 산정식 병행.
- **클라우드 환경에서의 오버 프로비저닝(Over-Provisioning) 관행** :
  - **한계점** : 온프레미스 관행대로 5년 치 피크 용량을 첫날부터 클라우드에 프로비저닝하여 불필요한 클라우드 요금 폭증.
  - **해결 방안** : 클라우드 특성을 살린 '최소 단위 시작(Right-Sizing)' 및 실시간 오토스케일링(HPA/KEDA) 정책 기반의 동적 사이징 체계 수립.

## Ⅴ. 모던 인프라 용량 계획을 위한 기술사적 제언

- **사전 정적 사이징에서 지속적 자원 최적화(Continuous Sizing)로 전환** : 시스템 오픈 전 1회의 정적 하드웨어 규모산정에 머무르지 않고, 오픈 후 APM(핀포인트, 제니퍼)과 클라우드 모니터링 도구를 통해 실제 CPU/메모리 병목을 실시간 계측하고 인스턴스 사양을 동적으로 재조정하는 FinOps 사이징 문화를 정착시켜야 함.
- **부하 테스트(JMeter/Locust)를 통한 실측 기반 베이스라인 검증 의무화** : 신규 시스템 발주 시 계산 수식에만 의존하지 말고, 통합 테스트 완료 단계에서 실전 피크 트래픽을 크게 초과하는 부하를 가하는 임계치 스트레스 테스트를 의무화하여 비기능 요구사항(SLA) 충족 여부를 최종 검증할 것을 제언함.
