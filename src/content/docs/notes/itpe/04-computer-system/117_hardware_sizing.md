## 연관 키워드

- 하드웨어 규모산정(Hardware Sizing), 용량 계획(Capacity Planning), 여유율(Headroom)
- TPS(Transactions Per Second), tpmC, TPC-C, IOPS(Input/Output Operations Per Second)
- 피크 부하, 과소 산정, 과대 산정, 부하 테스트
- 오토스케일링, Right-Sizing, FinOps, 지속적 자원 최적화

## Ⅰ. 하드웨어 규모산정의 개요

- 핵심 요약 : 목표 업무 요건을 서버, 스토리지, 네트워크의 필요 용량으로 환산하는 공학적 용량 계획 활동.
- 개념 : 동시 사용자 수, 일일 트랜잭션, 데이터 볼륨, 응답 시간 목표(SLA)를 CPU, 메모리, 디스크, 네트워크 자원량으로 산출하는 **하드웨어 규모산정** (Hardware Sizing) 방법론으로, 같은 말로 **용량 계획** (Capacity Planning)이라고도 함.
- 배경 및 필요성 : **과소 산정** (Under-sizing)은 오픈 직후 장애로 이어지고 **과대 산정** (Over-sizing)은 예산 낭비와 라이선스 비용 증가를 부르므로, 객관적 산정 근거가 필요함.
- 주요 목적 : 적정 인프라 용량 도출, **총소유비용** (TCO, Total Cost of Ownership) 최적화, 피크 시간 트래픽 수용과 향후 증설 여지 확보.

## Ⅱ. 하드웨어 규모산정의 특징 및 장점

- 핵심 요약 : 업무 요건을 측정 가능한 처리량으로 바꾸고 여유율을 더해 용량을 확정하므로, 과소와 과대 산정을 함께 줄이는 구조.

1. 요건의 수치화 : 응답 시간, 동시 접속, 일일 트랜잭션을 초당 처리량(TPS, Transactions Per Second)으로 환산 → 자원 산정의 입력값 확보.
2. 피크 반영 : 평균 부하에 피크 계수를 곱해 최대 부하 기준으로 산정 → 피크 시간 장애 예방.
3. 벤치마크 환산 : **TPC-C** (Transaction Processing Performance Council-C) 기반 tpmC (Transactions Per Minute C) 같은 공인 성능치로 코어 수를 계산 → 예산 승인의 객관적 근거 확보.
4. 보정과 여유율 : 이중화 구성, 암호화(TLS, Transport Layer Security) 부하 같은 보정 계수와 증가율을 반영 → 운영 환경의 비효율을 흡수하고 확장 계획과 충돌 방지.

## Ⅲ. 하드웨어 규모산정의 구조 (흐름)

- 핵심 요약 : 요건 조사, 피크 분석, 자원별 계산, 여유율 확정의 4단계 순차 절차.

```text
[ 규모산정 4단계 절차 ]

1. 업무 요건 조사
   응답 시간, 동시 접속, 일일 트랜잭션
     ↓
2. 피크 부하 분석
   평균 트랜잭션 × 피크 계수
     ↓
3. 자원 용량 산정
   CPU, 메모리, 디스크, 네트워크
     ↓
4. 여유율·증가율 확정
```

```text
[ 자원별 산정 구성 ]

CPU
  tpmC → 보정 tpmC → 코어 수
Memory
  OS + WAS 힙 + DB 버퍼 + 캐시
Disk
  DB 볼륨 × 여유율 × 인덱스·로그 배수
  → RAID 구성 반영
```

- 자원별 산정 : CPU는 피크 tpmC에 시스템 계수와 업무 계수를 곱한 뒤 코어당 공인 성능치로 나누어 코어 수를 구하고, 메모리와 디스크는 구성 요소별 합산과 배수 적용으로 계산함.
- 스토리지 산정 : 용량(GB)과 함께 요구 IOPS(Input/Output Operations Per Second)와 큐 깊이를 함께 산정해야 함.

## Ⅳ. 하드웨어 규모산정 방법론의 비교 분석

- 핵심 요약 : 분석적 기법은 사업 초기의 예산 근거에, 참조 모델은 유사 시스템 경험에, 부하 테스트는 오픈 직전의 실제 병목 검증에 강점이 있음.

| 비교 항목 | 분석적 기법 (공식·벤치마크) | 참조 모델 기법 (유사 시스템 실측) | 부하 테스트 (PoC·벤치마크) |
| :--- | :--- | :--- | :--- |
| 산정 원리 | 표준 산정 공식과 벤치마크 수식 대입 | 유사 규모 운영 시스템의 실측치 차용 | 부하 생성기로 실제 한계 측정 |
| 적용 시점 | 사업 기획, 예산 수립, 제안 요청 단계 | 차세대 전환, 동종 레퍼런스 존재 시 | 오픈 직전 검증, 성능 튜닝 단계 |
| 정확도 | 중간 (실제 병목 미반영) | 중간 ~ 높음 (유사 업무 특성 반영) | 높음 (실제 애플리케이션 병목 검증) |
| 소요 비용·시간 | 낮음 | 낮음 ~ 중간 | 높음 (테스트 환경과 도구 필요) |
| 주요 장점 | 객관적 예산 승인 근거 제공 | 운영 경험치가 녹아 있어 실용적 | 숨은 구조·DB 락 결함을 사전 발견 |

- 선택 기준 : 사업 단계에 따라 세 기법을 병행하되, 최종 확정은 실측 검증 결과를 우선함.

## Ⅴ. 하드웨어 규모산정의 주요 한계와 방안

- 핵심 요약 : 단일 벤치마크 공식의 현실 괴리, CPU 중심 산정의 I/O 간과, 클라우드 과잉 프로비저닝이 주요 한계이며 복합 산정, 풀스택 산정, 동적 사이징으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| tpmC 중심 공식의 현실 괴리 | 공식이 멀티코어 구조와 마이크로서비스 환경을 충분히 반영하지 못해 산정 오차 발생 | 서비스별 TPS, 메모리 점유량, 네트워크 I/O를 함께 쓰는 복합 산정 기준 적용 | 산정치 대비 실측 오차율 |
| CPU 중심 산정의 I/O·메모리 병목 간과 | 코어는 충분해도 IOPS나 대역폭이 부족해 응답 지연 발생 | 풀스택 산정, 스토리지는 용량과 함께 IOPS·큐 깊이 산정 병행 | 디스크 큐 대기 시간, 응답 지연 |
| 클라우드 과잉 프로비저닝 | 온프레미스 관행대로 장기 피크 용량을 처음부터 할당 → 불필요한 요금 | 최소 단위로 시작하는 Right-Sizing, HPA(Horizontal Pod Autoscaler)·KEDA(Kubernetes Event-Driven Autoscaling) 기반 오토스케일링 | 자원 사용률, 유휴 비용 비율 |

## Ⅵ. 모던 인프라 용량 계획을 위한 기술사적 제언

- 핵심 요약 : 용량 계획은 오픈 전 한 번의 정적 산정이 아니라 운영 중 계측으로 갱신되는 지속적 자원 최적화 활동이어야 하며, 검증 기준도 실측으로 고정해야 함.

1. 오픈 후 APM(Application Performance Monitoring)과 클라우드 모니터링 데이터로 CPU와 메모리 병목을 실시간 계측하고, 인스턴스 사양을 주기적으로 조정하는 FinOps 기반 사이징 문화를 정착시키는 것이 바람직하다.
2. 발주 단계에서는 계산 수식만 근거로 삼지 않고, 통합 테스트 단계에 JMeter나 Locust 같은 도구로 실전 피크를 넘는 부하를 가해 비기능 요구사항(SLA) 충족을 확인하도록 계약 조건에 명시해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 하드웨어 규모산정은 자원 발주 전에 근거를 만드는 작업이며, 실측 검증과 지속적 조정을 거쳐 완성됨.
- 시사점 : 과소와 과대 산정의 비용을 모두 피하려면 산정 공식과 운영 계측을 하나의 순환으로 연결해야 함.
