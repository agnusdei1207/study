## 연관 키워드

- 경쟁 상태(Race Condition), 데이터 레이스(Data Race), 임계 영역(Critical Section), 상호 배제(Mutual Exclusion)
- 원자성(Atomicity), 뮤텍스(Mutex), 세마포어(Semaphore), 스핀락(Spinlock), 모니터(Monitor)
- CAS(Compare-And-Swap), 문맥 교환(Context Switch), 갱신 유실(Lost Update), TOCTOU(Time-of-Check to Time-of-Use)

## Ⅰ. 경쟁 상태의 개요

- 핵심 요약 : 둘 이상의 실행 흐름이 공유 자원에 동시 접근할 때 타이밍에 따라 결과가 달라지는 동시성 결함.
- 개념 : 멀티스레드·멀티프로세스 환경에서 실행 흐름들이 공유 자원을 동시에 읽고 쓰는 과정에서 명령 실행 순서가 겹치는 인터리빙에 따라 결과가 달라지는 **경쟁 상태** (Race Condition).
- 배경 및 필요성 : 멀티코어 보편화로 병렬 실행이 기본 구조가 되었으나 동기화가 없으면 잔액 오류·데이터 손상 같은 간헐적 결함이 발생함. 병렬화 이득을 지키려면 공유 구간 통제가 필요함.
- 주요 목적 : **임계 영역** (Critical Section, 공유 자원에 접근하는 코드 구간)의 직렬화, **데이터 레이스** (Data Race, 같은 메모리에 대한 무동기 동시 접근) 차단, 간헐 결함의 조기 검출.

## Ⅱ. 경쟁 상태의 특징 및 장점

- 핵심 요약 : 고수준 한 줄 연산도 기계어 수준에서 여러 단계로 나뉘어 경쟁이 생기며, 임계 영역 3대 조건이 동기화 설계의 판정 기준이 됨.

1. **원자성** (Atomicity, 연산이 중간 상태 노출 없이 온전히 수행되는 성질) 결여 : `count++` 같은 연산이 **읽기-수정-쓰기** (Read-Modify-Write)의 여러 명령으로 실행 → 중간 개입 시 **갱신 유실** (Lost Update)이 확인되는 결함 구조.
2. 실행 타이밍 의존성 : 스레드 실행 순서가 실행마다 달라져 재현이 어려운 간헐 결함 형태 → 탐지 도구와 코드 규준의 필요 근거.
3. 임계 영역 3대 조건 : **상호 배제** (Mutual Exclusion), 진행(Progress), 한정 대기(Bounded Waiting)의 보장 요구 → 동기화 기법의 정확성을 검증하는 기준으로 활용.

## Ⅲ. 경쟁 상태의 구조 (흐름)

- 핵심 요약 : 읽기·계산·쓰기 단계 사이에 **문맥 교환** (Context Switch)이 끼어드는 인터리빙이 결함을 만들고, 락으로 임계 영역을 직렬화해 제거함.
- 두 스레드가 같은 값을 읽고 각자 갱신하면 나중 쓰기가 앞선 쓰기를 덮어써 한 번의 증가가 사라짐.

```text
[ 갱신 유실 발생 흐름 ]

A: 값 10 읽기
      ↓ 문맥 교환
B: 값 10 읽기
      ↓
B: 11 계산 후 저장
      ↓
A: 11 계산 후 저장
      ↓
최종 11 (기대값 12 불일치)
```

```text
[ 상호 배제 적용 흐름 ]

A: 락 획득
      ↓
A: 임계 영역 수행 후 락 해제
      ↓
B: 락 획득 대기 후 진입
      ↓
갱신 순서 보장
```

## Ⅳ. 동기화 기법의 비교

- 핵심 요약 : 대기 방식과 제어 범위, 충돌 빈도에 따라 블로킹 기법과 락 프리 기법의 선택이 갈림.
- 비교 대상은 **뮤텍스** (Mutex), **세마포어** (Semaphore), **스핀락** (Spinlock), **모니터** (Monitor), **CAS** (Compare-And-Swap, 기존값과 비교해 일치할 때만 교체하는 하드웨어 원자적 명령)임.

| 기법 | 동작 방식 | 장점 | 트레이드오프 |
| :--- | :--- | :--- | :--- |
| 뮤텍스 | 소유 스레드만 임계 영역 진입 | 단일 자원 보호가 명확 | 문맥 교환 비용 |
| 세마포어 | 카운터로 N개 자원의 동시 접근 제어 | 자원 풀 관리에 적합 | 연산 오용 시 교착 가능 |
| 스핀락 | 해제까지 대기 루프로 점유 | 짧은 구간에서 빠름 | 긴 구간에서 CPU 낭비 |
| 모니터 | 락과 조건 변수를 언어 차원 캡슐화 | 동기화 실수 가능성 감소 | 언어·런타임 지원 필요 |
| CAS | 락 없이 원자적 교체 반복 | 락 프리 구현 가능 | 충돌이 잦으면 재시도 급증 |

- 선택 기준 : 임계 영역이 짧고 코어가 많으면 스핀락, 자원 풀 제어는 세마포어, 언어 지원 환경은 모니터, 충돌이 드문 카운터·포인터 갱신은 CAS를 기준으로 삼음.

## Ⅴ. 경쟁 상태의 한계와 방안

- 핵심 요약 : 재현 곤란, 락 병목, 검사-사용 공백 공격을 탐지 자동화, 락 세분화, 원자적 처리로 일대일 대응함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 디버거 부착 시 증상이 사라지는 간헐 결함 | 타이밍 변화로 운영 부하에서만 재현 → 원인 규명 지연 | **ThreadSanitizer** (실행 중 메모리 접근 패턴으로 레이스를 탐지하는 도구)를 빌드·통합 테스트에 상시 적용 | 탐지된 레이스 건수 |
| 전역 락에 따른 확장성 저하 | 직렬화 구간이 커져 코어를 늘려도 처리량이 비례하지 않음 | 락 세분화, 읽기-쓰기 락, **RCU** (Read-Copy-Update, 읽기를 잠금 없이 허용하는 갱신 기법) 적용 | 락 대기 시간 |
| **TOCTOU** (Time-of-Check to Time-of-Use, 검사와 사용 사이의 상태 변경 공백) | 권한 검사 후 파일 경로가 바뀌어 권한 상승 발생 | 파일 디스크립터 기반 처리, 생성 플래그를 조합한 원자적 생성 | 경로 변경 탐지 건수 |

## Ⅵ. 경쟁 상태에 대한 기술사적 제언

- 핵심 요약 : 공유 상태를 줄이는 설계 표준과 동시성 검증 자동화를 개발 조직의 기본 절차로 내재화하는 방향.
- 개발 조직은 불변 객체와 메시지 전달 모델을 설계 표준으로 채택해 잠금이 필요한 지점 자체를 줄이는 구조적 접근을 확산해야 함.
- 플랫폼 운영 조직은 레이스 탐지 도구를 지속적 통합 파이프라인의 필수 단계로 등록해 결함이 배포 전에 걸러지는 품질 관문을 두어야 함.
- 기술 총괄 부서는 동시성 코드 리뷰 체크리스트와 락 사용 규칙을 사내 표준 문서로 정해 담당자 교체 이후에도 기준이 유지되는 거버넌스를 마련해야 함.

## Ⅶ. 결론

- 핵심 요약 : 경쟁 상태는 공유 자원의 비원자적 접근이 만드는 타이밍 의존 결함.
- 임계 영역의 직렬화와 공유 최소화 설계, 자동화된 탐지가 결합될 때 동시성 품질이 확보됨.
