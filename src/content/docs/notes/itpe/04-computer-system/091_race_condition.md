## 지식 로드맵 내 현재 위치

컴퓨터 시스템 및 네트워크 → 핵심 개념 → 경쟁 상태

## 30초 인출

- 본질: 공유 메모리에 대해 원자적이지 않은 '읽기-수정-쓰기' 연산이 비순차적으로 끼어듦(Interleaving)
- 메커니즘: 실행 순서에 따라 최종 결과가 달라지는 비결정적 데이터 손상 발생

## 핵심 용어

- 임계 영역(Critical Section): 둘 이상의 스레드가 공유 자원에 접근하여 데이터를 변경할 수 있는 코드 블록으로, 한 번에 오직 하나의 스레드만 진입해야 함
- 상호 배제(Mutual Exclusion): 한 스레드가 임계 영역에서 작업 중일 때 다른 어떤 스레드도 해당 영역에 들어오지 못하도록 강제하는 원칙
- 하이젠버그(Heisenbug): 디버거나 로깅을 붙여 관찰하려고 하면 실행 타이밍이 바뀌어 버그가 사라지고, 실제 운영 환경에서만 간헐적으로 터지는 동시성 결함

## 1교시 10점 답안

### Ⅰ. 정의·목적

- 정의: 경쟁 상태은/는 실행 순서에 따라 최종 결과가 달라지는 비결정적 데이터 손상 발생 방식이다.
- 목적: 락(Lock) 또는 원자적 하드웨어 인스트럭션으로 임계 영역을 상호 배제하여 해결에 기여한다.

### Ⅱ. 핵심 구조와 작동

```text
[ 두 스레드의 동시 접근(Interleaving)으로 인한 경쟁 상태 발생 메커니즘 ]

시간축 (Time)        스레드 1 (Thread 1)             스레드 2 (Thread 2)           공유 변수 (Count = 10)
    │
    ▼        [1] Count 읽기 (값: 10)
             [2] 1 증가 연산 (10 + 1 = 11)
                       │ (컨텍스트 스위칭!)
                       └────────────────────────> [3] Count 읽기 (값: 10)
                                                  [4] 1 증가 연산 (10 + 1 = 11)
                                                  [5] Count 쓰기 (값: 11) ────> Count = 11
                       ┌───────────────────────────────────┘
                       │ (스위칭 복귀)
             [6] Count 쓰기 (값: 11) ─────────────────────────────────────────> Count = 11 (버그!)
    │
    ▼        [ 정상 기대치: 12 / 실제 결과: 11 (스레드 2의 증가 연산이 완전히 유실됨: Lost Update) ]
```

## 2~4교시 25점 답안

### Ⅰ. 핵심 구조와 작동

```text
[ 두 스레드의 동시 접근(Interleaving)으로 인한 경쟁 상태 발생 메커니즘 ]

시간축 (Time)        스레드 1 (Thread 1)             스레드 2 (Thread 2)           공유 변수 (Count = 10)
    │
    ▼        [1] Count 읽기 (값: 10)
             [2] 1 증가 연산 (10 + 1 = 11)
                       │ (컨텍스트 스위칭!)
                       └────────────────────────> [3] Count 읽기 (값: 10)
                                                  [4] 1 증가 연산 (10 + 1 = 11)
                                                  [5] Count 쓰기 (값: 11) ────> Count = 11
                       ┌───────────────────────────────────┘
                       │ (스위칭 복귀)
             [6] Count 쓰기 (값: 11) ─────────────────────────────────────────> Count = 11 (버그!)
    │
    ▼        [ 정상 기대치: 12 / 실제 결과: 11 (스레드 2의 증가 연산이 완전히 유실됨: Lost Update) ]
```

### Ⅱ. 핵심 특성

- `count++`는 단일 명령어가 아니라 3개의 기계어임 → 메모리 로드(Load), 레지스터 연산(Add), 메모리 저장(Store)의 3단계 사이에 인터럽트나 스레드 전환이 끼어들 수 있는 틈이 존재함
- 락(Lock)은 안전하지만 비쌈 → 경쟁 상태를 막겠다고 모든 공유 함수에 뮤텍스를 걸면 멀티코어 CPU가 단일 코어처럼 직렬화되어 처리량이 폭락하고 교착 상태(Deadlock) 위험이 발생함
- 최신 고성능 시스템은 락 프리(Lock-Free)로 진화함 → 하드웨어 CPU가 단일 사이클로 제공하는 `CMPXCHG`(x86의 Compare-And-Swap) 명령어를 통해 락 대기 없이 충돌 시에만 재시도하는 방식으로 오버헤드를 극소화함

### Ⅲ. 관련 개념과 구분

- 경쟁 상태 vs 데이터 레이스: 경쟁 상태 = 타이밍에 따라 비즈니스 로직 결과가 틀어지는 시스템적 결함 / 데이터 레이스 = 동기화 없이 최소 하나가 쓰기 연산인 두 메모리 접근이 발생하는 저수준 메모리 모델 결함

### Ⅳ. 적용 문제와 대응

- 사례: 126회 기출 및 선착순 100명 쿠폰 발급 이벤트 시 동시 요청 1만 건으로 인한 쿠폰 300장 초과 지급 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 선착순 한정 수량 상품이 정원보다 수십 개 초과 결제되는 오버셀 발생 | 수량 체크(SELECT)와 차감(UPDATE) 사이의 원자성 결여 | Redis 원자적 분기문(DECR) 또는 DB 낙관적 락(Version 조건) 적용 | 밀리초 단위 동시성 충돌 100% 방지 및 정확한 정원 통제 |
| 멀티스레드 네트워크 서버에서 간헐적 메모리 크래시(SIGSEGV) 발생 | 객체 참조 해제와 읽기 스레드 간의 경쟁(Use-After-Free) | 스마트 포인터(std::shared_ptr)의 원자적 카운팅 및 RCU 기법 적용 | 메모리 안정성 확보 및 읽기 작업의 락 프리 무지연 보장 |

### Ⅴ. 기술사적 제언

| 문제 | 해결 방안 |
|---|---|
