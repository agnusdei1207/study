## 연관 키워드

- 경쟁 상태(Race Condition), 데이터 레이스(Data Race), 임계 영역(Critical Section), 상호 배제(Mutual Exclusion)
- 원자성(Atomicity), 뮤텍스(Mutex), 세마포어(Semaphore), 스핀락(Spinlock), 원자적 연산(CAS, Compare-And-Swap), 모니터(Monitor)
- Heisenbug, ThreadSanitizer(TSan), 암달의 법칙(Amdahl's Law), RCU(Read-Copy-Update), TOCTOU(Time-of-Check to Time-of-Use)

## Ⅰ. 경쟁 상태의 개요

- 핵심 요약 : 공유 자원에 대한 동시 접근으로 실행 순서에 따라 결과가 달라지는 동시성 결함.
- 개념 : 멀티스레드, 멀티프로세스, 분산 환경에서 둘 이상의 실행 흐름이 **공유 자원** (Shared Resource)을 동시에 읽고 쓸 때, 실행 타이밍에 따라 결과가 달라지는 **경쟁 상태** (Race Condition).
- 배경 및 필요성 : 멀티코어 보편화로 병렬 실행이 기본 구조가 되었지만, 동기화가 없으면 결제 오류나 데이터 손상 같은 결함이 발생. 병렬화로 얻는 성능 이득을 지키려면 공유 구간을 통제하는 동기화 체계가 필요해짐.
- 주요 목적 : **임계 영역** (Critical Section)의 직렬화 보장, **데이터 레이스** (Data Race) 원천 차단, 재현이 어려운 간헐적 결함의 조기 검출.

## Ⅱ. 경쟁 상태의 특징 및 장점

- 핵심 요약 : 고수준의 한 줄 연산도 기계어 수준에서 여러 단계로 나뉘어 경쟁이 생기며, 임계 영역 3대 조건이 해결의 판정 기준이 됨.

1. **원자성** (Atomicity) 결여 : `count++`는 기계어 수준에서 **읽기-수정-쓰기** (Read-Modify-Write) 단계로 나뉘어 실행 → 중간에 문맥이 바뀌면 갱신이 유실됨.
2. 임계 영역 3대 조건 : **상호 배제** (Mutual Exclusion), 진행(Progress), 한정 대기(Bounded Waiting)가 모두 보장되어야 함 → 동기화 기법을 평가하는 기준이 되어 설계 검증이 가능해짐.

## Ⅲ. 경쟁 상태의 구조 및 동작 메커니즘

- 핵심 요약 : 공유 변수 갱신이 읽기·계산·쓰기로 쪼개진 사이에 **문맥 교환** (Context Switch)이 끼어드는 인터리빙이 원인.
- 두 스레드가 같은 값을 읽고 각자 갱신하면, 나중의 쓰기가 앞선 쓰기를 덮어써 한 번의 증가가 사라짐.

```text
[ count++ 경쟁 상태 흐름 ]

A: LOAD (10 읽음)
      ↓
A: ADD (11 계산, 저장 전)
      ↓ 문맥 교환
B: LOAD (10 읽음)
      ↓
B: ADD 후 STORE (11 저장)
      ↓
A: STORE (11 덮어씀)
      ↓
기대 12, 실제 11 (갱신 유실)
```

```text
[ 상호 배제 적용 흐름 ]

스레드 A: 락 획득
      ↓
임계 영역 수행 (count++)
      ↓
스레드 A: 락 해제
      ↓
스레드 B: 락 획득 후 수행
```

## Ⅳ. 경쟁 상태 해결 기법의 비교

- 핵심 요약 : 블로킹 기법은 대기 방식과 자원 제어 범위에 따라, 락 프리 기법은 충돌 빈도에 따라 선택이 달라짐.
- 비교 대상은 **뮤텍스** (Mutex), **세마포어** (Semaphore), **스핀락** (Spinlock), **원자적 연산** (CAS, Compare-And-Swap), **모니터** (Monitor)이다.

| 기법 | 동작 메커니즘 | 장점 | 트레이드오프·한계 |
| :--- | :--- | :--- | :--- |
| 뮤텍스 | 락 소유 스레드만 임계 영역 진입 | 단일 자원 상호 배제가 명확 | 문맥 교환 비용, 우선순위 역전 위험 |
| 세마포어 | 카운터로 N개 자원의 동시 접근 허용 | 자원 풀 제어에 적합 | P/V 연산 오용 시 데드락 가능 |
| 스핀락 | 락 해제까지 대기 루프로 점유 | 임계 영역이 매우 짧으면 문맥 교환 없이 빠름 | 임계 영역이 길면 CPU 자원 낭비 |
| 원자적 연산 | 하드웨어 비교 교환 명령으로 락 없이 갱신 | 블로킹 없는 락 프리 구현 가능 | 충돌이 잦으면 재시도 반복 |
| 모니터 | 상호 배제와 조건 변수를 언어 차원에서 캡슐화 | 동기화 실수 가능성 최소화 | 언어·런타임의 지원 필요 |

## Ⅴ. 경쟁 상태의 한계와 방안

- 핵심 요약 : 재현 난제, 락 병목, 권한 검사 시점 공격을 탐지 도구·세분화 락·원자적 처리로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 간헐적 재현 불가 결함 (**Heisenbug**) | 디버거 연결 시 타이밍이 달라져 운영 부하에서만 크래시 발생 | **ThreadSanitizer** (TSan)를 지속적 통합 (CI, Continuous Integration) 파이프라인에 적용 | 탐지된 레이스 건수 |
| 과도한 전역 락으로 인한 확장성 저하, **암달의 법칙** (Amdahl's Law) | 직렬화 구간이 커져 코어를 늘려도 처리량이 비례하지 않음 | 락 세분화, 읽기-쓰기 분리 락, **RCU** (Read-Copy-Update) 적용 | 락 대기 시간 |
| **TOCTOU** (Time-of-Check to Time-of-Use) | 권한 검사와 사용 사이에 공격자가 심볼릭 링크를 바꿔 권한 상승 | 파일 디스크립터 기반 처리, O_CREAT와 O_EXCL 플래그로 생성을 원자적으로 수행 | 검사-사용 사이 경로 변경 탐지 건수 |

## Ⅵ. 경쟁 상태 적용에 대한 기술사적 제언

- 핵심 요약 : 공유 상태를 줄이는 설계와 동시성 검증 기준을 개발 표준으로 묶어 관리.
- 불변 객체와 이벤트 소싱을 중심으로 설계하면 잠금이 필요한 지점 자체가 줄어들어, 레이스가 생길 경로를 구조적으로 제거할 수 있다.
- 액터 모델이나 채널 기반 메시지 전달은 공유 메모리를 상태 단위로 격리하므로, 대규모 병렬 서비스에서 동기화 부담을 낮추는 데 유리하다.
- 동시성 코드 리뷰 기준과 레이스 탐지 도구를 개발 표준에 포함해, 결함이 운영 단계에서 드러나기 전에 걸러지도록 관리할 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : 경쟁 상태는 공유 자원의 비원자적 접근이 만드는 결함으로, 상호 배제와 공유 최소화 설계로 통제하는 과제.
- 동기화 기법 선택과 탐지 도구, 설계 원칙을 함께 적용해야 동시성 결함을 실효성 있게 줄일 수 있다.
