## 답안 골격
```text
[경쟁 상태] ◀━━ 머리: Ⅶ 내 의견 (락 없는 원자적 연산(CAS)과 정적 동시성 분석 도구를 결합한 비결정적 동시성 결함 원천 차단)
 ┃
 ┣━ Ⅰ 개요 ───── 동시성 프로그래밍 환경에서 실행 타이밍의 비결정성 발생 → 두 개 이상의 프로세스/스레드가 공유 자원에 동시 접근하여 결과 왜곡
 ┣━ Ⅱ 특징 ───── 비결정적(Non-deterministic) 버그 · 재현 난이도 극상(Heisenbug) · 임계 영역 보호 실패 · 데이터 무결성 파괴
 ┣━ Ⅲ 구조 ───── 스레드 A/B + 공유 메모리(자원) + 임계 영역(Critical Section) + 동기화 프리미티브(Mutex/Semaphore/CAS)
 ┣━ Ⅳ 흐름 ───── ① 스레드 A 읽기 → ② 컨텍스트 스위칭 발생 → ③ 스레드 B 읽기 및 수정 → ④ 스레드 A 옛 값 기반 덮어쓰기(Lost Update)
 ┣━ Ⅴ 비교 ───── 경쟁 상태(Race Condition) vs 교착 상태(Deadlock) vs 라이브락(Livelock)
 ┗━ Ⅵ 실무 ───── 금융 계좌 잔액 차감 이상 / 재고 수량 초과 판매(오버셀) / 멀티스레드 포인터 해제 경쟁(Use-After-Free)
```
- 필수 키워드: 경쟁 상태 · 임계 영역 · 상호 배제 · 원자성(Atomicity) · CAS(Compare-And-Swap) · 뮤텍스
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ 인터리빙 실행 타이밍도 → Ⅴ 경쟁 상태 vs 교착 상태 비교표 / 25점 = Ⅰ~Ⅶ 전개, Ⅳ 동시성 제어 3대 조건(상호배제/진행/유한대기) 충족 메커니즘과 Ⅵ 하드웨어 CAS 및 락 프리 알고리즘
- 기출: 126회 1교시 3번 `Race Condition` 단답형 출제

## 한 줄 본질
- 공유 메모리에 대해 원자적이지 않은 '읽기-수정-쓰기' 연산이 비순차적으로 끼어듦(Interleaving) → 실행 순서에 따라 최종 결과가 달라지는 비결정적 데이터 손상 발생 → 락(Lock) 또는 원자적 하드웨어 인스트럭션으로 임계 영역을 상호 배제하여 해결 / 과도한 락 적용 시 처리량 급감 및 병목 유발

## 핵심 그림
```text
[ 두 스레드의 동시 접근(Interleaving)으로 인한 경쟁 상태 발생 메커니즘 ]

시간축 (Time)        스레드 1 (Thread 1)             스레드 2 (Thread 2)           공유 변수 (Count = 10)
    │
    ▼        [1] Count 읽기 (값: 10)
             [2] 1 증가 연산 (10 + 1 = 11)
                       │ (컨텍스트 스위칭!)
                       └────────────────────────> [3] Count 읽기 (값: 10)
                                                  [4] 1 증가 연산 (10 + 1 = 11)
                                                  [5] Count 쓰기 (값: 11) ────> Count = 11
                       ┌───────────────────────────────────┘
                       │ (스위칭 복귀)
             [6] Count 쓰기 (값: 11) ─────────────────────────────────────────> Count = 11 (버그!)
    │
    ▼        [ 정상 기대치: 12 / 실제 결과: 11 (스레드 2의 증가 연산이 완전히 유실됨: Lost Update) ]
```

## 핵심 용어
- 임계 영역(Critical Section): 둘 이상의 스레드가 공유 자원에 접근하여 데이터를 변경할 수 있는 코드 블록으로, 한 번에 오직 하나의 스레드만 진입해야 함
- 상호 배제(Mutual Exclusion): 한 스레드가 임계 영역에서 작업 중일 때 다른 어떤 스레드도 해당 영역에 들어오지 못하도록 강제하는 원칙
- 하이젠버그(Heisenbug): 디버거나 로깅을 붙여 관찰하려고 하면 실행 타이밍이 바뀌어 버그가 사라지고, 실제 운영 환경에서만 간헐적으로 터지는 동시성 결함

## 핵심 통찰
- `count++`는 단일 명령어가 아니라 3개의 기계어임 → 메모리 로드(Load), 레지스터 연산(Add), 메모리 저장(Store)의 3단계 사이에 인터럽트나 스레드 전환이 끼어들 수 있는 틈이 존재함
- 락(Lock)은 안전하지만 비쌈 → 경쟁 상태를 막겠다고 모든 공유 함수에 뮤텍스를 걸면 멀티코어 CPU가 단일 코어처럼 직렬화되어 처리량이 폭락하고 교착 상태(Deadlock) 위험이 발생함
- 최신 고성능 시스템은 락 프리(Lock-Free)로 진화함 → 하드웨어 CPU가 단일 사이클로 제공하는 `CMPXCHG`(x86의 Compare-And-Swap) 명령어를 통해 락 대기 없이 충돌 시에만 재시도하는 방식으로 오버헤드를 극소화함

## 이웃 토픽과 구분
- 경쟁 상태 vs 데이터 레이스: 경쟁 상태 = 타이밍에 따라 비즈니스 로직 결과가 틀어지는 시스템적 결함 / 데이터 레이스 = 동기화 없이 최소 하나가 쓰기 연산인 두 메모리 접근이 발생하는 저수준 메모리 모델 결함
