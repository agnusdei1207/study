## 연관 키워드

- 결함허용시스템(FTS, Fault-Tolerant System), 결함(Fault), 오류(Error), 장애(Failure)
- TMR(Triple Modular Redundancy), 투표기(Voter), 락스텝(Lockstep), 결함 마스킹(Fault Masking)
- 공통 원인 결함(Common-Cause Failure), NVP(N-Version Programming), SPOF(Single Point of Failure)
- HA(High Availability), DR(Disaster Recovery), RPO(Recovery Point Objective), ASIL, DO-178C, 카오스 엔지니어링

## Ⅰ. 결함허용시스템(FTS)의 개요

- 핵심 요약 : **결함허용시스템** (FTS, Fault-Tolerant System)은 결함을 감지·마스킹·복구하여 중단 없이 정상 기능을 수행하는 고신뢰 시스템.
- 개념 : 하드웨어나 소프트웨어 구성요소에 **결함** (Fault)이 생겨도 시스템 전체가 멈추거나 잘못 동작하지 않도록, 결함 감지, 격리, 마스킹, 복구 메커니즘을 내장한 시스템.
- 배경 및 필요성 : 항공우주, 원자력 발전, 철도 신호, 금융 코어 뱅킹처럼 짧은 중단이나 오작동도 인명과 재난으로 이어지는 미션 크리티컬 환경에서 완전한 무결성이 요구됨.
- 주요 목적 : 결함이 **장애** (Failure)로 번지는 것을 차단하고, 다수결 상쇄로 무중단 가용성을 확보하며, 신뢰도(Reliability)와 안전성(Safety)을 극대화.

## Ⅱ. 결함허용시스템(FTS)의 특징 및 장점

- 핵심 요약 : 다수결 상쇄, 동기 실행 비교, 격리, 복구가 결합되어 결함이 발생한 순간에도 서비스 연속성을 유지하는 구조.

1. **결함 마스킹** (Fault Masking) : 3중 모듈과 다수결 투표로 틀린 출력을 상쇄 → 외부로 오류가 전달되지 않아 서비스가 계속됨.
2. **하드웨어 락스텝** (Lockstep) : 복수의 CPU(Central Processing Unit) 코어가 같은 클록에 같은 명령을 실행하고, 비교기가 매 사이클 결과를 대조 → 불일치를 즉시 감지.
3. **결함 격리** (Fault Confinement) : 결함이 확인된 노드나 보드를 전기적·논리적으로 차단 → 건전한 부품으로 오염이 번지는 것을 방지.
4. **전진·후진 복구** (Forward/Backward Recovery) : 체크포인트로 과거 정상 상태에 되돌아가는 후진 복구와, 보상 트랜잭션 등으로 현재 상태에서 이어가는 전진 복구를 상황에 맞게 적용 → 중단 시간 최소화.

## Ⅲ. 결함허용시스템(FTS)의 구조 및 동작 메커니즘

- 핵심 요약 : 결함, 오류, 장애로 이어지는 연쇄를 다중화 모듈의 다수결 구조로 끊는 방식.
- **TMR** (Triple Modular Redundancy, 3중 모듈 중복) : 동일 기능 모듈 세 개를 두고 다수결로 출력을 결정하는 구조.
- **투표기** (Voter, 다수결 회로) : 모듈 출력 중 두 개 이상이 일치하는 값을 채택하는 판정 회로.

```text
[ 결함 연쇄와 차단 지점 ]

결함 (Fault, 잠재적 원인)
        ↓ 결함 마스킹과 감지로 차단
오류 (Error, 비정상 상태)
        ↓ 격리와 복구로 차단
장애 (Failure, 서비스 중단)
```

```text
[ TMR 다수결 마스킹 ]

모듈 A, 모듈 B, 모듈 C 출력
        ↓
투표기 (2-out-of-3 다수결 판정)
        ↓
모듈 C에 오류가 있어도 A와 B 값 채택
        ↓
최종 출력 (정상 유지)
```

## Ⅳ. 결함허용시스템(FTS)의 비교

- 핵심 요약 : HA, FTS, DR은 목적과 다운타임, 구현 방식, 데이터 손실 한도가 달라 서로 대체 관계가 아닌 보완 관계.

| 비교 항목 | 고가용성 시스템 (HA, High Availability) | 결함허용시스템 (FTS) | 재해복구 시스템 (DR, Disaster Recovery) |
| --- | --- | --- | --- |
| 설계 목적 | 연간 다운타임 최소화 | 단 한 순간의 중단이나 오작동도 허용하지 않음 | 지진, 화재 등 광역 재난 복구 |
| 장애 시 서비스 | 페일오버(Failover) 동안 짧은 중단 | 중단 없이 연속 수행 | 복구 목표 시간(RTO, Recovery Time Objective) 기준으로 복구 |
| 구현 방식 | Active-Standby, Active-Active 클러스터링 | TMR, 락스텝 하드웨어 다중화 | 원격지 백업 센터와 데이터 복제 |
| 비용과 복잡도 | 중간 (상용 장비와 소프트웨어 활용) | 매우 높음 (특수 제작 하드웨어) | 인프라 이중 구축으로 높음 |
| 데이터 손실 한도 (RPO, Recovery Point Objective) | 비동기 복제 시 일부 유실 가능 | 무손실 목표 | 복제 주기에 따라 유실 가능 |

- HA는 장애 발생 후 대기 시스템으로 넘기는 인계 방식이지만, FTS는 장애 순간에도 결함을 실시간으로 마스킹하여 연산이 끊기지 않는 동시 존속 방식임.

## Ⅴ. 결함허용시스템(FTS)의 한계와 방안

- 핵심 요약 : 동시 결함, 판정 회로의 취약점, 중복 비용을 다양화 설계, 판정 회로 이중화, 선별 적용으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **공통 원인 결함** (Common-Cause Failure) | 같은 소프트웨어 버그나 펌웨어 설계 결함이 있으면 하드웨어를 3중화해도 모든 모듈이 같은 오류를 내 투표가 무력화 | **NVP** (N-Version Programming): 독립 팀이 서로 다른 언어와 알고리즘으로 개발, 이종 OS와 하드웨어 조합 적용 | 공통 결함 발견 건수, 버전 간 출력 불일치율 |
| 투표기 자체의 SPOF (Single Point of Failure) | 투표 회로에 결함이 생기면 전체 출력이 정지되거나 오염 | 투표기 자체를 3중화하는 트라이플리케이트 투표기 구조, 자가 검사형 논리 설계 | 투표기 자가 진단 결과 |
| 중복 하드웨어의 비용과 전력 | 같은 연산을 여러 장비에서 수행해 민간 일반 업무에는 경제성이 낮음 | 미션 크리티컬 핵심 프로세스에만 선별 적용, 나머지 영역은 HA 방식 병행 | 단위 서비스당 장비 비용, 전력 사용량 |

## Ⅵ. 결함허용시스템(FTS)에 대한 기술사적 제언

- 핵심 요약 : 안전 규격 연계, 실제 장애 주입 검증, 소프트웨어 계층의 대안을 함께 추진하여 FTS를 실효성 있는 안전 체계로 정착.

1. 자율주행과 UAM(도심 항공 모빌리티) 개발사는 **ASIL** (Automotive Safety Integrity Level) 수준의 ISO 26262 요구와 **DO-178C** 인증 기준을 설계 초기에 반영하여, 락스텝 구조를 안전 필수 기능으로 포함시킨다.
2. 운영 조직은 **카오스 엔지니어링** (Chaos Engineering)으로 SEU(Single Event Upset, 단일 사건 비트 반전)나 전원 차단을 주입해 결함 마스킹이 실제로 동작하는지 주기적으로 검증한다.
3. 소프트웨어 계층 연구팀은 Raft, Paxos 같은 분산 합의 알고리즘을 활용한 소프트웨어 기반 FTS를 검토하여, 하드웨어 중복 없이 노드 장애를 흡수하는 방향을 탐색한다.

## Ⅶ. 결론

- 핵심 요약 : FTS는 TMR, 락스텝, 투표기로 결함을 실시간 마스킹하여 무중단 고신뢰성을 확보하는 시스템.
- 시사점 : 공통 원인 결함과 비용이 한계를 정하므로, 전 시스템이 아닌 미션 크리티컬 영역에 선별 적용하는 설계 판단이 핵심.
