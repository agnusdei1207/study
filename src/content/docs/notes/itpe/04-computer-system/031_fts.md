## 답안 골격
```text
[FTS] ◀━━ 머리: Ⅶ 내 의견 (초고비용 하드웨어 록스텝 대신 클라우드 네이티브 소프트웨어 합의 알고리즘(Raft) 기반 FTS 구현)
 ┃
 ┣━ Ⅰ 개요 ───── 부품 장애 시 수 초의 페일오버 중단도 불허하는 미션 크리티컬 환경 → 무정지 결함 감내 시스템
 ┣━ Ⅱ 특징 ───── 제로 다운타임(0초 절체) · 결함 마스킹(Masking) · 록스텝(Lockstep) 동기화 · 다중 모듈 중복(TMR)
 ┣━ Ⅲ 구조 ───── 하드웨어 중복(TMR 3중화) + 보팅 로직(Voter) + 동기화 클록 + 핫스왑 전원/팬
 ┣━ Ⅳ 흐름 ───── ① 3개 CPU에 동일 클록 동일 명령 투입 → ② 록스텝 병렬 연산 → ③ 다수결 보팅(2:1 판정) → ④ 무중단 결과 출력
 ┣━ Ⅴ 비교 ───── FTS(무정지) vs HA(고가용성) vs DR(재해복구)
 ┗━ Ⅵ 실무 ───── 막대한 하드웨어 비용(3~4배) / 공통 모드 결함(Common Mode Failure) / 소프트웨어 버그 취약성
```
- 필수 키워드: 결함 감내(Fault Tolerance) · 록스텝(Lockstep) · TMR(Triple Modular Redundancy) · 보팅(Voter) · 제로 다운타임 · 결함 마스킹
- 기출: 138회 3교시 `가용성 보장에 대하여 다음 내용을 설명하시오 (HA와 FTS 비교)`

## 한 줄 본질
- 일반 HA 시스템의 장애 감지 및 페일오버 전환 중 발생하는 수 초~수 분의 서비스 일시 중단과 인메모리 세션 단절 불허 → 하드웨어 부품(CPU, 메모리, 버스)을 3중화(TMR)하여 동일 클록으로 동시 실행하고 다수결 투표로 오류를 즉각 마스킹(Masking) → 단 1초의 중단도 없는 완벽한 무정지(Zero-downtime) 실현 / 극심한 하드웨어 도입 비용 및 소프트웨어 논리 오류 방어 한계

## 핵심 용어
- TMR(Triple Modular Redundancy): 동일한 기능의 하드웨어 모듈을 3개 병렬로 배치하고 출력을 다수결 투표기(Voter)에 연결하여, 1개 모듈이 고장 나더라도 정상 출력을 유지하는 대표적 하드웨어 중복 기법
- 록스텝(Lockstep): 2개 이상의 프로세서가 완벽히 동일한 마이크로초 클록에 맞춰 동일한 명령어를 나란히 실행하고, 매 사이클마다 레지스터 상태와 버스 출력을 상호 검증하는 기법
- 결함 마스킹(Fault Masking): 시스템 내부에서 결함이 발생했음에도 불구하고 시스템 외부(사용자/상위 앱)로는 결함의 징후나 성능 저하가 일절 노출되지 않도록 하드웨어적으로 오류를 은폐·차단하는 것

## 핵심 통찰
- FTS는 '초고신뢰성'을 사기 위해 '비용 효율성'을 완전히 희생한 아키텍처임 → 3개 CPU와 3중 메모리를 돌려 1대의 연산 결과만 취하므로 하드웨어 비용과 전력 소모가 일반 서버의 3배 이상 발생
- 하드웨어 FTS는 물리적 부품 고장(알파 입자 플립, 전원 불량)은 완벽히 막아내지만, 운영체제나 애플리케이션의 소프트웨어 버그는 3개 모듈이 동일하게 실행하므로 동시에 다운되는 '공통 모드 결함(Common Mode Failure)'에 무력함
- 이에 따라 원자력, 철도 신호, 항공 우주, 증권 거래소 등 '1초의 멈춤이 인명 피해나 수백억 금융 손실로 직결되는 영역'에서만 제한적으로 사용됨

## 이웃 토픽과 구분
- FTS vs HA: FTS = 하드웨어 3중화와 록스텝으로 장애 순간에도 서비스 단절 시간 0초(Zero-downtime) / HA = 평소 1대만 서비스하고 장애 감지 시 수 초 내 대기 서버로 절체(페일오버 지연 존재)

## 문제·원인·대책
- 사례: 138회 기출 미션 크리티컬 관제 시스템 운영 시 단일 소프트웨어 결함으로 인한 FTS 전체 정지
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 메모리 누수 버그로 인해 3중화된 FTS 서버 3대가 동일 시점에 동시 다운 | 하드웨어는 독립적이나 동일한 소스코드 바이너리를 공유(공통 모드 결함) | N-버전 프로그래밍(NVP: 독립 팀이 서로 다른 언어/로직으로 개발) 적용 | 단일 코드 결함의 동시 전파 차단 |
| 주기적인 하드웨어 부품 고장 시 시스템 정지 없는 유지보수 난항 | 섀시 전원 및 백플레인의 단일 설계 결함 | 핫 스왑(Hot-swap) 지원 이중화 전원 공급 장치(PSU) 및 온라인 보드 교체 설계 | 전원 인가 상태에서 불량 CPU 모듈 무중단 교체 |

## 이렇게 출제된다
- 제138회 3교시 4번: "가용성 보장에 대하여 다음 내용을 설명하시오." → 요구 포인트: Ⅰ 가용성 정의 + Ⅲ FTS 록스텝/TMR 아키텍처 + Ⅴ HA와 FTS의 비교표 (절체시간, 비용, 데이터 유실 여부)

## 내 의견
- [소프트웨어 정의 분산 합의 기반 FTS로의 진화] 전용 스트라투스(Stratus) 같은 고가의 특수 FTS 하드웨어는 장비 노후화 시 부품 수급 단절과 벤더 락인 문제 초래 → 나라면: x86 범용 서버 클러스터 위에서 Raft 또는 Paxos 분산 합의 알고리즘과 메모리 복제(State Machine Replication)를 적용하여, 소프트웨어적으로 단일 노드 장애를 무중단 마스킹하는 분산 클라우드 네이티브 FTS 구조로 현대화
