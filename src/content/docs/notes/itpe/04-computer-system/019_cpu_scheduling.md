## 30초 인출

- 본질: **CPU 스케줄링** 은 실행 가능한 작업 중 다음에 CPU를 사용할 작업을 고르는 일이다.
- 메커니즘: 준비 큐의 작업을 정책에 따라 선택하고, 디스패처가 문맥을 바꿔 CPU를 넘긴다. I/O 대기와 선점이 생기면 작업은 다시 준비 상태로 돌아올 수 있다.

<details>
<summary>핵심 용어</summary>

- **준비 큐** : 실행 가능하지만 CPU 할당을 기다리는 작업의 집합
- **디스패처** : 스케줄러가 고른 작업으로 CPU 실행을 전환하는 운영체제 구성요소
- **선점** : 실행 중인 작업의 CPU 사용을 중단시키고 다른 작업에 CPU를 주는 방식
- **기아** : 우선순위 등 정책 때문에 어떤 작업이 계속 CPU를 받지 못하는 상태
- **타임 퀀텀** : 라운드 로빈에서 한 작업이 한 번에 사용할 수 있는 CPU 시간
- **EEVDF** : 실행 자격과 가상 마감시각을 함께 고려해 다음 작업을 고르는 Linux 공정 스케줄링 방식

</details>

## 1교시 10점 답안

### 1. 정의·목적

- 정의: **CPU 스케줄링** 은 실행 가능한 작업 중 다음에 CPU를 사용할 작업을 선택하는 운영체제 기능이다.
- 목적: 처리량과 응답성을 높이고 작업의 대기 시간을 관리한다.

### 2. 상태 전환과 스케줄링

```mermaid
flowchart TD
    READY["준비 큐"] -->|"스케줄러 선택·디스패치"| RUN["실행"]
    RUN -->|"선점·시간 할당 종료"| READY
    RUN -->|"I/O 요청"| WAIT["대기"]
    WAIT -->|"I/O 완료"| READY
    RUN -->|"작업 완료"| END["종료"]
```

### 3. 평가 기준

| 기준 | 무엇을 보는가 |
|---|---|
| 응답 시간 | 요청 후 첫 실행까지 걸린 시간 |
| 대기 시간 | 준비 큐에서 기다린 시간 |
| 처리량 | 일정 시간 동안 완료한 작업 수 |

제언: 대화형·배치 작업의 요구가 다르면 응답 시간과 처리량 중 우선할 목표를 정해 정책을 선택한다.

## 2~4교시 25점 답안

## Ⅰ. CPU 스케줄링의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 실행 가능한 작업 중 다음에 CPU를 사용할 작업을 선택 |
| 목적 | 처리량·응답성·대기 시간의 균형 |

## Ⅱ. 준비·실행·대기의 전환

```mermaid
flowchart TD
    READY["준비 큐"] -->|"스케줄러 선택·디스패치"| RUN["실행"]
    RUN -->|"선점·시간 할당 종료"| READY
    RUN -->|"I/O 요청"| WAIT["대기"]
    WAIT -->|"I/O 완료"| READY
    RUN -->|"작업 완료"| END["종료"]
```

I/O가 끝난 작업은 실행 상태로 바로 가는 것이 아니라 준비 큐로 돌아와 다시 CPU 배정을 기다린다.

## Ⅲ. 대표 스케줄링 방식의 선택 기준

| 방식 | 선택 원리 | 유의점 |
|---|---|---|
| FCFS | 준비된 순서대로 실행 | 긴 작업이 뒤 작업을 지연할 수 있음 |
| SJF | 예상 CPU 사용 시간이 짧은 작업 우선 | 사용 시간을 미리 정확히 알기 어려움 |
| RR | 시간 할당량마다 작업 교체 | 할당량이 작으면 전환 비용 증가 |
| 우선순위 | 중요도가 높은 작업 우선 | 낮은 우선순위 작업의 기아 가능 |

선점형 정책은 실행 중인 작업을 교체할 수 있어 응답성을 높일 수 있지만, 문맥 전환 비용도 고려해야 한다.

## Ⅳ. 목표에 따른 평가와 구현 예

| 목표 | 확인할 지표·기법 |
|---|---|
| 대화형 응답 | 응답 시간, 선점 지점, 타임 퀀텀 |
| 배치 처리 | 처리량, 평균 대기·반환 시간 |
| 공정성 | 작업별 CPU 사용 비율, 장시간 대기 여부 |

Linux의 과거 CFS는 가상 실행시간을 중심으로 공정성을 다뤘고, 최근 커널은 **EEVDF** 로 전환 중이다. 특정 Linux 버전의 실제 정책은 해당 커널 문서와 설정으로 확인한다.

## Ⅴ. 응답 지연과 기아에 대한 제언

| 문제 | 해결 방안 |
|---|---|
| 낮은 우선순위 작업이 계속 밀림 | 대기 시간이 길어질 때 우선순위를 조정하는 에이징 등 기아 방지 정책 적용 |
| RR의 할당량이 너무 작아 전환이 잦음 | 실제 작업의 응답 시간과 문맥 전환 비용을 측정해 할당량 조정 |
