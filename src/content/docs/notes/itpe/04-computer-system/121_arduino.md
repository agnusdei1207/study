## 핵심 용어
- 부트로더(Bootloader): MCU의 플래시 메모리 시작 영역에 상주하며, 리셋 시 PC와 USB 시리얼 통신을 열어 컴파일된 헥사(HEX) 코드를 수신하여 플래시 메모리에 직접 기록하는 소형 프로그램
- GPIO(General Purpose Input/Output): 디지털 0(0V)과 1(5V) 신호를 소프트웨어 명령을 통해 입력 또는 출력으로 자유롭게 전환하여 사용할 수 있는 범용 핀
- PWM(Pulse Width Modulation): 디지털 펄스의 듀티 사이클(Duty Cycle: High 상태의 시간 비율)을 고속으로 조절하여 모터 속도나 LED 밝기를 아날로그처럼 제어하는 변조 기술

## 핵심 통찰
- 아두이노의 본질은 '임베디드 레지스터의 완전한 추상화'임 → 기존 임베디드 개발은 데이터시트 수백 페이지를 보며 `DDRB`, `PORTB` 같은 비트 레지스터를 직접 건드려야 했으나, 아두이노는 `pinMode()`, `digitalWrite()` 함수 하나로 이를 은닉하여 개발 진입 장벽을 파괴함
- 컴퓨터(SBC)가 아니라 '컨트롤러(MCU)'임 → 라즈베리 파이는 OS(리눅스)가 돌아가는 범용 컴퓨터로서 지연이 불규칙한 반면, 아두이노는 단일 마이크로컨트롤러 위에서 루프가 직접 돌기 때문에 나노초/마이크로초 단위의 엄격한 타이밍 제어가 가능함
- 메모리의 절대적 한계(SRAM 2KB)가 소프트웨어 설계를 지배함 → 문자열(String) 객체를 동적 생성하거나 재귀 호출을 남발하면 2KB 램이 순식간에 고갈되어 스택-힙 충돌로 MCU가 무한 리셋되므로, 정적 버퍼 할당과 `PROGMEM`(플래시 메모리에 상수 저장) 기법이 필수적임

## 이웃 토픽과 구분
- 아두이노(Arduino) vs 라즈베리 파이(Raspberry Pi): 아두이노 = OS 없이 단일 제어 루프를 도는 저전력 마이크로컨트롤러(센서/모터 직접 제어 특화) / 라즈베리 파이 = 리눅스 OS 위에서 다중 프로세스를 구동하는 고성능 단일 기판 컴퓨터(영상 처리/서버 특화)

## 문제·원인·대책
- 적용 상황: 스마트 팩토리 온습도 수집 및 공압 밸브 제어 단말 프로토타이핑
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 문자열 연결 및 센서 로그 출력 중 기기가 멈추거나 주기적으로 리셋 발생 | 힙 메모리 파편화 및 SRAM 2KB 한도 초과(Stack Overflow) | `String` 클래스 사용을 금지하고 `char` 배열 및 `F()` 매크로 적용 | SRAM 점유율 70% 이하 유지 및 메모리 크래시 방지 |
| 모터 회전 감지 인터럽트 처리 중 센서 값 읽기가 지연되어 펄스 누락 | `loop()` 내에 블로킹 지연 함수(`delay()`) 남발 | 타이머 카운터(`millis()`) 기반 논블로킹 스케줄링 전환 | 비동기 상태 머신 동작으로 인터럽트 응답성 확보 |
| 공장 내 대형 인버터 모터 기동 시 아두이노 핀이 오작동하고 다운 | 외부 유도 기전력 및 산업용 전원 서지 노이즈 유입 | 포토커플러(Optocoupler) 기반 입출력 광절연 쉴드 및 TVS 다이오드 부착 | 외부 노이즈 차단 및 하드웨어 회로 소손 방지 |

## 내 의견
- [FreeRTOS 포팅 기반 태스크 분리와 상용 단계에서의 산업용 PLC/ESP32 전환 체계 구축] 아두이노의 단순 `loop()` 구조는 단일 기능 테스트에는 이상적이나 실무에서 여러 센서와 통신을 동시에 다루기에는 구조적 한계가 뚜렷함 → 나라면: 프로토타입 단계에서는 아두이노 환경에 FreeRTOS를 올려 센서 수집 태스크와 네트워크 전송 태스크를 선점형 우선순위로 분리하여 신뢰성을 확보하고, 양산 검증 단계에서는 노이즈 내성이 검증된 산업용 아두이노(Portenta Machine Control)나 Wi-Fi/BLE가 기본 내장된 듀얼코어 ESP32로 단계적 전환하는 하드웨어 라이프사이클 전략 수립
