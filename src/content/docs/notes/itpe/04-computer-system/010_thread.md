## Ⅰ. 스레드(Thread)의 개요

- 개념 : **프로세스(Process)** 내에서 실행되는 흐름의 최소 단위이자 CPU 스케줄러에 의해 독립적으로 할당되는 실행 단위로서, 프로세스의 코드, 데이터, 힙 및 시스템 자원을 공유하며 고유한 레지스터 집합과 스택 영역을 유지하는 경량 프로세스(LWP).
- 배경 및 필요성 : 전통적인 멀티프로세스 모델은 독립된 가상 주소 공간으로 인해 프로세스 생성 비용이 크고, 문맥 교환(Context Switching) 오버헤드 및 **IPC** 통신 복잡도가 높아 멀티코어 환경의 병렬성을 고속으로 활용하기 위해 고안됨.
- 핵심 목적 : 자원 생성 및 스케줄링 오버헤드 최소화, 메모리 공유를 통한 프로세스 내 초고속 통신 실현, 멀티코어 하드웨어의 병렬 처리량 극대화.

## Ⅱ. 스레드(Thread)의 핵심 아키텍처 및 동작 메커니즘

스레드는 프로세스의 자원을 공유하는 영역과 개별 스레드가 독립적으로 유지하는 영역으로 구분되며, **커널 스레드** 와 **사용자 스레드** 간 매핑 모델에 따라 다르게 동작함.

```text
[ 프로세스 내 멀티스레드 메모리 공유 구조 ]

+---------------------------------------------------------------+
| Process 가상 주소 공간                                        |
|                                                               |
|  [공유 영역]                                                  |
|  +--------------------+ +-------------------+ +-------------+ |
|  | Code (Text) Segment| | Data / BSS Segment| | Heap Segment| |
|  +--------------------+ +-------------------+ +-------------+ |
|  | 오픈 파일 디스크립터 (File Descriptors), 프로세스 ID 등 자원  |
|                                                               |
|  [스레드별 독립 영역]                                         |
|  +------------------+  +------------------+  +--------------+ |
|  | Thread 1         |  | Thread 2         |  | Thread 3     | |
|  | - Program Counter|  | - Program Counter|  | - PC         | |
|  | - Register Set   |  | - Register Set   |  | - Registers  | |
|  | - Stack Segment  |  | - Stack Segment  |  | - Stack      | |
|  | - TCB (상태정보) |  | - TCB            |  | - TCB        | |
|  +------------------+  +------------------+  +--------------+ |
+---------------------------------------------------------------+
         │                       │                    │
         ▼                       ▼                    ▼
+───────────────────────────────────────────────────────────────+
| CPU Core 0            | CPU Core 1         | CPU Core 2       |
+───────────────────────────────────────────────────────────────+
```

- **자원 공유성** : 동일 프로세스 내 스레드들은 Code, Data, Heap 및 OS 자원을 공유하여 메모리 낭비 방지.
- **독립 실행성** : 각 스레드는 고유의 TCB(Thread Control Block), 프로그램 카운터(PC), 범용 레지스터 및 스택 메모리를 보유하여 독립적인 함수 호출 추적.
- **경량 문맥 교환** : 동일 프로세스 내 스레드 간 스위칭 시 가상 주소 공간(CR3 레지스터)과 MMU 페이지 테이블을 교체하지 않으므로 캐시 플러시 오버헤드 최소화.
- **매핑 아키텍처** : **1:1 모델** (리눅스 pthread, 커널이 직접 스케줄링) vs **M:1 모델** (그린 스레드) vs **M:N 모델** (Go goroutine, 가상 스레드).

## Ⅲ. 스레드(Thread)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 프로세스 (Process) | 스레드 (Thread) | 코루틴 / 가상 스레드 (Coroutine) |
|---|---|---|---|
| **정의** | OS 자원 할당의 독립된 기본 단위 | CPU 스케줄링 및 실행의 최소 단위 | 유저 공간에서 협조적으로 스케줄링되는 경량 루틴 |
| **메모리 공간** | 독립된 주소 공간 (완전 격리) | 프로세스의 주소 공간 공유 (스택만 독립) | 유저 힙에 스택 프레임 동적 할당 |
| **문맥 교환 오버헤드** | 큼 (TLB 플러시, 페이지 테이블 변경) | 작음 (레지스터 세트 및 스택 포인터만 교체) | 극소 (시스템 콜 없음, 유저 레벨 레지스터 저장) |
| **통신 메커니즘** | 고비용 IPC (파이프, 소켓, 공유메모리) | 초고속 메모리 직접 참조 (전역/힙 변수) | 채널(Channel) 또는 메모리 직접 참조 |
| **장애 파급성** | 한 프로세스 크래시 시 타 프로세스 안전 | 한 스레드의 메모리 오염 시 전체 프로세스 중단 | 애플리케이션 레벨 예외 전파 제어 가능 |

- 스레드는 효율성이 뛰어나나 공유 메모리로 인한 동기화 문제와 데이터 레이스가 발생하므로 세심한 락 제어가 수반되어야 함.

## Ⅳ. 스레드(Thread)의 주요 한계점 및 해결 방안

- 동시성 제어 실패에 따른 **경쟁 상태(Race Condition)** :
  - 한계점 : 다중 스레드가 임계 구역(Critical Section)에 동시 접근하여 동기화 없이 값을 갱신할 때 데이터 불일치 및 영구 손상 발생.
  - 해결 방안 : 뮤텍스(Mutex), 세마포어(Semaphore), CAS(Compare-And-Swap) 기반 원자적 연산(Atomic Operations) 및 Lock-Free 자료구조 도입.
- 스레드 폭증으로 인한 커널 메모리 고갈 및 스케줄링 부하 :
  - 한계점 : 요청당 스레드(Thread-per-request) 모델에서 동시 접속자 수천 명 초과 시 OS 스택 메모리(기본 1~8MB) 고갈 및 OOM 발생.
  - 해결 방안 : 스레드 풀(Thread Pool) 적용, Reactor/Event-Driven 비동기 논블로킹 I/O 채택, Java 21 Virtual Threads 도입.
- **교착상태(Deadlock)** 및 우선순위 역전 리스크 :
  - 한계점 : 복수의 락을 상호 교차 획득하거나 실시간 우선순위 스케줄링 시 하위 스레드로 인해 상위 스레드가 영구 대기하는 현상 발생.
  - 해결 방안 : 락 획득 순서 체계화(Lock Ordering), 타임아웃 락 적용, 우선순위 상속(Priority Inheritance) 프로토콜 적용.

## Ⅴ. 스레드(Thread) 적용 및 발전을 위한 기술사적 제언

- 모던 언어의 **가상 스레드(Virtual Thread)** 전환 : 자바 Project Loom, Go Goroutine 등 커널 스레드와 분리된 유저 레벨 경량 동시성 모델을 도입하여 I/O 집약적 워크로드의 처리량을 극대화해야 함.
- 불변 **객체(Immutability)** 패턴 중심 설계 : 멀티스레드 동기화 오버헤드를 근원적으로 제거하기 위해 함수형 프로그래밍의 불변 데이터 구조와 RCU(Read-Copy-Update) 패턴 적용 권장.
- 스레드 풀 사이징 엔지니어링 : CPU Bound 작업(코어 수 N+1)과 I/O Bound 작업(N * (1 + Wait/Compute))의 스레드 풀을 물리적으로 분리 격리하여 상호 간섭 차단 필수.
