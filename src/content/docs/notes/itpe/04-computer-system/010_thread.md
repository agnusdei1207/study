## Ⅰ. 스레드(Thread)의 개요

- 핵심 요약 : **스레드**는 프로세스 내 실행 흐름의 최소 단위로 자원을 공유하며 병렬 처리량을 극대화하는 경량 실행 단위.
- 개념 : **프로세스(Process)** 내에서 실행되는 흐름의 최소 단위이자 CPU(Central Processing Unit) 스케줄러에 의해 독립적으로 할당되는 실행 단위로서, 프로세스의 코드, 데이터, 힙 및 시스템 자원을 공유하며 고유한 레지스터 집합과 스택 영역을 유지하는 경량 프로세스(LWP, Lightweight Process).
- 배경 및 필요성 : 전통적인 멀티프로세스 모델은 독립된 가상 주소 공간으로 인해 프로세스 생성 비용이 크고, 문맥 교환(Context Switching) 오버헤드 및 **IPC**(Inter-Process Communication) 통신 복잡도가 높아 멀티코어 환경의 병렬성을 고속으로 활용하기 위해 고안됨.
- 핵심 목적 : 자원 생성 및 스케줄링 오버헤드 최소화, 메모리 공유를 통한 프로세스 내 초고속 통신 실현, 멀티코어 하드웨어의 병렬 처리량 극대화.

## Ⅱ. 스레드(Thread)의 특징 및 장점

- 핵심 요약 : **자원 공유·독립 실행·경량 문맥 교환**으로 고속 병렬 처리 실현.
1. **자원 공유성** : 동일 프로세스 내 스레드들은 Code, Data, Heap 및 OS(Operating System) 자원을 공유하여 메모리 낭비 방지.
2. **독립 실행성** : 각 스레드는 고유의 TCB(Thread Control Block), 프로그램 카운터(PC, Program Counter), 범용 레지스터 및 스택 메모리를 보유하여 독립적인 함수 호출 추적.
3. **경량 문맥 교환** : 동일 프로세스 내 스레드 간 스위칭 시 가상 주소 공간(CR3 레지스터)과 MMU(Memory Management Unit) 페이지 테이블을 교체하지 않으므로 캐시 플러시 오버헤드 최소화.
4. **매핑 아키텍처** : **1:1 모델** (리눅스 pthread, 커널이 직접 스케줄링) vs **M:1 모델** (그린 스레드) vs **M:N 모델** (Go goroutine, 가상 스레드).

## Ⅲ. 스레드(Thread)의 구조 및 동작 메커니즘

- 핵심 요약 : **공유 영역(Code/Data/Heap)과 독립 영역(PC/Register/Stack)** 구분 및 매핑 모델.
- 스레드는 프로세스의 자원을 공유하는 영역과 개별 스레드가 독립적으로 유지하는 영역으로 구분되며, **커널 스레드**와 **사용자 스레드** 간 매핑 모델에 따라 다르게 동작함.

## Ⅳ. 스레드(Thread)의 비교

- 핵심 요약 : **프로세스·스레드·코루틴**의 메모리·오버헤드·통신·장애 비교.

| 비교 항목 | 프로세스 (Process) | 스레드 (Thread) | 코루틴 / 가상 스레드 (Coroutine) |
|---|---|---|---|
| 정의 | OS 자원 할당의 독립된 기본 단위 | CPU 스케줄링 및 실행의 최소 단위 | 유저 공간에서 협조적으로 스케줄링되는 경량 루틴 |
| 메모리 공간 | 독립된 주소 공간 (완전 격리) | 프로세스의 주소 공간 공유 (스택만 독립) | 유저 힙에 스택 프레임 동적 할당 |
| 문맥 교환 오버헤드 | 큼 (TLB(Translation Lookaside Buffer) 플러시, 페이지 테이블 변경) | 작음 (레지스터 세트 및 스택 포인터만 교체) | 극소 (시스템 콜 없음, 유저 레벨 레지스터 저장) |
| 통신 메커니즘 | 고비용 IPC (파이프, 소켓, 공유메모리) | 초고속 메모리 직접 참조 (전역/힙 변수) | 채널(Channel) 또는 메모리 직접 참조 |
| 장애 파급성 | 한 프로세스 크래시 시 타 프로세스 안전 | 한 스레드의 메모리 오염 시 전체 프로세스 중단 | 애플리케이션 레벨 예외 전파 제어 가능 |

## Ⅴ. 스레드(Thread)의 한계와 방안

- 핵심 요약 : **경쟁 상태·스레드 폭증·교착상태**를 동기화·풀·타임아웃으로 대응.

- 동시성 제어 실패에 따른 **경쟁 상태(Race Condition)** :
  - 한계점 : 다중 스레드가 임계 구역(Critical Section)에 동시 접근하여 동기화 없이 값을 갱신할 때 데이터 불일치 및 영구 손상 발생.
  - 해결 방안 : 뮤텍스(Mutex), 세마포어(Semaphore), CAS(Compare-And-Swap) 기반 원자적 연산(Atomic Operations) 및 Lock-Free 자료구조 도입.
- 스레드 폭증으로 인한 커널 메모리 고갈 및 스케줄링 부하 :
  - 한계점 : 요청당 스레드(Thread-per-request) 모델에서 동시 접속자 수천 명 초과 시 OS 스택 메모리(기본 1~8MB) 고갈 및 OOM(Out of Memory) 발생.
  - 해결 방안 : 스레드 풀(Thread Pool) 적용, Reactor/Event-Driven 비동기 논블로킹 I/O 채택, Java 21 Virtual Threads 도입.
- **교착상태(Deadlock)** 및 우선순위 역전 리스크 :
  - 한계점 : 복수의 락을 상호 교차 획득하거나 실시간 우선순위 스케줄링 시 하위 스레드로 인해 상위 스레드가 영구 대기하는 현상 발생.
  - 해결 방안 : 락 획득 순서 체계화(Lock Ordering), 타임아웃 락 적용, 우선순위 상속(Priority Inheritance) 프로토콜 적용.

## Ⅵ. 스레드(Thread) 적용 제언

- 핵심 요약 : **가상 스레드·불변 객체·풀 사이징**으로 동시성 효율화.
- 가상 스레드(Virtual Thread) 전환 : Java Project Loom, Go Goroutine 등 유저 레벨 경량 동시성 모델 도입.
- 불변 객체(Immutability) 패턴 : 동기화 오버헤드 근원 제거, RCU 패턴.
- 스레드 풀 사이징 : CPU Bound (N+1) / I/O Bound (N*(1+Wait/Compute)) 분리.

## Ⅶ. 결론

- 핵심 요약 : 스레드는 **프로세스 내 경량 실행 단위**로 자원 공유·문맥 교환 효율이 강점이나 동기화 제어가 필수.
- 스레드는 프로세스 자원을 공유하는 경량 실행 단위로 멀티코어 병렬성과 통신 효율을 높이지만, 공유 메모리로 인한 경쟁 상태·교착상태·스레드 폭증 리스크를 동기화·풀·가상 스레드로 관리해야 함.
- 답안에는 메모리 공유 구조, 프로세스/스레드/코루틴 비교, 한계·대응, 가상 스레드 제언을 연결.
