## 연관 키워드

- 오토스케일링(Auto Scaling), 클라우드 탄력성(Elasticity), 수평 확장(Scale-Out), 수직 확장(Scale-Up)
- 반응형 스케일링(Reactive Scaling), 예측형 스케일링(Predictive Scaling), 쿨다운(Cooldown), 플래핑(Flapping)
- 커넥션 드레이닝(Connection Draining), 그레이스풀 셧다운(Graceful Shutdown), KEDA, SLA

## Ⅰ. 오토스케일링(Auto Scaling)의 개요

- 핵심 요약 : **오토스케일링** (Auto Scaling)은 워크로드 변동에 맞춰 컴퓨팅 자원을 자동으로 늘리고 줄이는 클라우드 탄력성 제어 기술.
- 개념 : 트래픽 증가와 CPU(Central Processing Unit), 메모리 부하를 실시간으로 관측하여 자원 용량을 사람의 개입 없이 확장(Scale-Out, Scale-Up)하거나 축소하는 **클라우드 탄력성** (Elasticity) 제어 방식.
- 배경 및 필요성 : 온프레미스에서는 피크 트래픽에 맞춰 설비를 미리 늘려 두면 평시 유휴 자원 비용이 누적되고, 용량이 모자라면 돌발 트래픽에 장애가 발생하므로 사용량에 맞춰 용량을 조절하는 체계가 필요함.
- 주요 목적 : SLA(Service Level Agreement)에서 약속한 가용성을 지키고, 피크 외 시간의 자원을 회수하여 TCO(Total Cost of Ownership)를 낮춤.

## Ⅱ. 오토스케일링(Auto Scaling)의 특징 및 장점

- 핵심 요약 : 측정값을 근거로 용량을 자동 조정하며, 반응형·예측형·스케줄형 정책을 조합하는 방식.

1. **반응형 스케일링** (Reactive Scaling) : CPU 이용률이나 요청 수가 임계치를 넘으면 증설 → 실제 부하를 근거로 판단하여 구현이 단순함.
2. **예측형 스케일링** (Predictive Scaling) : 과거 트래픽 주기를 시계열 모델로 학습해 부하가 오기 전에 미리 증설 → 인스턴스 기동 지연을 가리는 선제 대응.
3. **스케줄형 스케일링** (Scheduled Scaling) : 출근 시간대나 행사처럼 시점이 정해진 피크에 용량을 미리 설정 → 예측 가능한 부하를 낭비 없이 처리.
4. 비대칭 정책 : 증설(Scale-Out)은 빠르게, 축소(Scale-In)는 점진적으로 수행 → 급증에 신속히 대응하면서 **플래핑** (Flapping)을 막음.
5. **쿨다운** (Cooldown) : 신규 인스턴스의 기동과 안정화 시간 동안 연속 트리거를 차단 → 같은 부하를 두고 과잉 증설되는 현상 억제.

## Ⅲ. 오토스케일링(Auto Scaling)의 구조 및 동작 메커니즘

- 핵심 요약 : 지표 수집, 정책 판정, 프로비저닝, 쿨다운으로 이어지는 순환 구조.
- **폐루프 제어** (Closed-loop Control) : 자원 용량의 변화가 다시 측정 지표에 반영되어 다음 판단의 입력이 되는 피드백 구조.
- 판정 컨트롤러는 클라우드 오토스케일링 그룹이나 쿠버네티스 HPA(Horizontal Pod Autoscaler)처럼 구현 환경에 따라 달라지지만, 입력과 출력의 흐름은 같음.

```text
[ 오토스케일링 폐루프 ]

트래픽 유입
      ↓
지표 수집 (CPU, 요청 수, 큐 길이)
      ↓
정책 판정 (임계치, 예측, 스케줄)
      ↓
프로비저닝 (Scale-Out / Scale-In)
      ↓
쿨다운 후 지표 재수집 (폐루프 복귀)
```

```text
[ 목표 추적 판정 공식 ]

현재 지표 값 (Current Metric)
      ↓
목표 값 (Target) 대비 비율 계산
      ↓
목표 수 = 현재 수 × (현재 지표 ÷ 목표 값)
      ↓
Scale-Out 또는 Scale-In 실행
```

## Ⅳ. 오토스케일링(Auto Scaling)의 비교

- 핵심 요약 : 노드·파드를 늘리는 수평 확장, 단일 인스턴스 사양을 올리는 수직 확장, 외부 이벤트 기반의 KEDA(Kubernetes Event-Driven Autoscaling)를 비교하여 워크로드 성격에 맞춰 선택.

| 비교 항목 | 수평 확장 (Scale-Out) | 수직 확장 (Scale-Up) | KEDA (Kubernetes Event-Driven Autoscaling) |
| --- | --- | --- | --- |
| 확장 방식 | 인스턴스·파드 개수 증가 | 단일 인스턴스의 vCPU·메모리 사양 증설 | 메시지 큐 등 외부 이벤트 양에 따라 파드 증감 |
| 무중단성 | 로드 밸런서 편입으로 무중단 가능 | 재기동이 필요해 다운타임 수반 가능 | 무중단이며 0 파드까지 축소 가능 |
| 확장 한계 | 분산 구조가 갖춰지면 사실상 확장 여지 큼 | 단일 하드웨어 최대 사양에 제한 | 이벤트 소스의 처리량에 비례 |
| 상태 관리 | 무상태(Stateless) 워크로드에 적합 | 상태 저장 시스템(DB)에 적합 | 배치 작업, 비동기 파이프라인에 적합 |
| 비용 특성 | 스팟 인스턴스 등과 결합해 탄력적 운영 | 고사양 인스턴스 단가가 비선형으로 증가 | 유휴 시 0까지 줄여 비용 최소화 |

- 선택 기준 : 상태 없는 웨이브형 트래픽은 수평 확장, 상태 저장 계층은 수직 확장과 별도 설계, 큐 기반 비동기 작업은 KEDA로 구분하는 것이 일반적임.

## Ⅴ. 오토스케일링(Auto Scaling)의 한계와 방안

- 핵심 요약 : 지연, 잦은 증감, 종료 시 요청 유실을 예측형 결합, 임계치 간격 조정, 드레이닝 절차로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 반응형 지연에 따른 스파이크 장애 | 메트릭 감지와 인스턴스 기동 시간 동안 용량 부족 → 급증 구간 서비스 저하 | 예측형 스케일링 결합, 여유 용량(예비 파드) 상시 유지 | 기동 소요 시간, 급증 구간 오류율 |
| 플래핑 (Flapping) | 임계치 경계에서 증설과 축소가 반복 → 라우팅 변경과 시스템 불안정 | **히스테리시스** (Hysteresis, 증설·축소 임계치 간격 확대), 축소 안정화 윈도우 적용 | 스케일 이벤트 빈도 |
| 스케일인 시 트랜잭션 유실 | 인스턴스 강제 종료로 연결과 처리 중 요청이 끊겨 502·504 등 게이트웨이 오류 발생 | **커넥션 드레이닝** (Connection Draining), preStop 훅과 SIGTERM 처리로 **그레이스풀 셧다운** (Graceful Shutdown) 구현 | 종료 중 실패 요청 수, 드레이닝 완료 시간 |

- 쿠버네티스 HPA는 축소 안정화 윈도우의 기본값을 300초로 두고 있어, 이 값을 워크로드 특성에 맞게 조정하는 절차가 필요함.

## Ⅵ. 오토스케일링(Auto Scaling)에 대한 기술사적 제언

- 핵심 요약 : 비용 구조, 이벤트 지표, 검증 절차를 함께 설계하여 오토스케일링을 상시 운영 가능한 탄력성 체계로 정착.

1. 운영팀은 기본 용량을 온디맨드 인스턴스로 고정하고, 급증 구간만 스팟 인스턴스로 채우는 혼합 운영을 우선 적용하며, 월별 비용 지표로 효과를 검증한다.
2. 아키텍처팀은 주문 대기열이나 결제 요청 수 같은 비즈니스 지표를 KEDA의 이벤트 소스로 연결하여, CPU 지표보다 앞서 증설하는 구조를 마련한다.
3. 품질팀은 부하 테스트와 카오스 엔지니어링을 릴리스 주기에 포함시켜, 임계치와 쿨다운 값이 실제 장애 상황에서도 유효한지 주기적으로 확인한다.

## Ⅶ. 결론

- 핵심 요약 : 오토스케일링은 폐루프 제어로 SLA 보장과 TCO 절감을 함께 노리는 탄력성 기술이며, 지연과 플래핑, 종료 시 유실 관리가 성패를 가름.
- 시사점 : 자동화의 효과는 임계치와 정책 값, 종료 절차가 함께 설계될 때 나타나므로 세 요소를 하나의 운영 기준으로 묶어야 함.
