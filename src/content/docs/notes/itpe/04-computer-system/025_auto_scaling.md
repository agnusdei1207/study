## 연관 키워드

- 오토스케일링(Auto Scaling), 클라우드 탄력성(Elasticity), 수평 확장(Scale-Out), 수직 확장(Scale-Up)
- 반응형 스케일링(Reactive Scaling), 예측형 스케일링(Predictive Scaling), 스케줄형 스케일링(Scheduled Scaling)
- 폐루프 제어(Closed-loop Control), 쿨다운(Cooldown), 플래핑(Flapping), 히스테리시스(Hysteresis)
- 커넥션 드레이닝(Connection Draining), 그레이스풀 셧다운(Graceful Shutdown), HPA, KEDA

## Ⅰ. 오토스케일링의 개요

- 핵심 요약 : 워크로드 변화에 맞춰 컴퓨팅 자원 용량을 자동으로 늘리고 줄여 가용성과 비용 효율을 함께 확보하는 클라우드 탄력성 제어 기술.
- 개념 : **오토스케일링** (Auto Scaling)은 CPU(Central Processing Unit) 이용률, 요청 수, 큐 길이 같은 운영 지표를 관측해 서버나 파드의 수를 사람의 개입 없이 늘리고 줄이는 자동 용량 제어 방식.
- 배경 및 필요성 : 피크 트래픽 기준으로 설비를 고정하면 평시 유휴 자원 비용이 남고, 용량이 모자라면 돌발 트래픽에서 장애가 발생하므로 사용량에 맞춘 **클라우드 탄력성** (Elasticity) 확보가 필요함.
- 주요 목적 : SLA(Service Level Agreement)의 가용성 목표 준수, 피크 외 시간의 자원 회수를 통한 TCO(Total Cost of Ownership) 절감.

## Ⅱ. 오토스케일링의 특징 및 장점

- 핵심 요약 : 측정 지표 기반의 정책과 시점 제어 장치가 결합되어 부하에 신속히 대응하면서 과잉 증설을 억제하는 구조.

1. **반응형 스케일링** (Reactive Scaling) : 지표가 임계치를 넘으면 즉시 증설 → 실측 부하를 근거로 판단해 구현이 단순하고 오판 위험이 낮음.
2. **예측형 스케일링** (Predictive Scaling) : 과거 트래픽 주기를 시계열 학습으로 예측해 부하 발생 전에 용량 확보 → 인스턴스 기동 지연을 흡수하는 선제 대응.
3. **스케줄형 스케일링** (Scheduled Scaling) : 시점이 정해진 피크에 용량을 미리 지정 → 예측 가능한 부하를 낭비 없이 처리.
4. **쿨다운** (Cooldown) : 신규 인스턴스의 기동과 안정화 동안 추가 트리거를 차단 → 같은 부하에 대한 중복 증설 억제.
5. 비대칭 정책 : 증설은 즉시, 축소는 안정화 창을 두고 점진 수행 → 임계치 경계의 **플래핑** (Flapping, 증설과 축소의 반복) 방지.

## Ⅲ. 오토스케일링의 구조 (흐름)

- 핵심 요약 : 지표 수집, 정책 판정, 프로비저닝, 안정화로 이어지는 피드백 순환 구조.
- **폐루프 제어** (Closed-loop Control) : 용량 변경 결과가 다시 지표에 반영되어 다음 판정의 입력이 되는 피드백 구조. 구현체로 퍼블릭 클라우드의 오토스케일링 그룹과 쿠버네티스 **HPA** (Horizontal Pod Autoscaler)가 대표적.

```text
[ 오토스케일링 폐루프 ]

트래픽 유입
   ↓
지표 수집 (CPU, 요청 수, 큐 길이)
   ↓
정책 판정 (임계치, 예측, 스케줄)
   ↓
프로비저닝 (Scale-Out, Scale-In)
   ↓
쿨다운 후 지표 재수집 (순환)
```

```text
[ 목표 추적 판정 ]

현재 지표 값 측정
   ↓
목표 값 대비 비율 계산
   ↓
목표 수 = 현재 수 × (지표 ÷ 목표 값)
   ↓
증설 또는 축소 실행
```

## Ⅳ. 수평 확장과 수직 확장의 비교

- 핵심 요약 : 개수를 늘리는 수평 확장, 사양을 올리는 수직 확장, 외부 이벤트 기반의 **KEDA** (Kubernetes Event-Driven Autoscaling)가 확장 축과 상태 관리, 비용 특성에서 달라 워크로드 성격에 따라 선택.

| 비교 항목 | 수평 확장 (Scale-Out) | 수직 확장 (Scale-Up) | KEDA |
| --- | --- | --- | --- |
| 확장 축 | 인스턴스·파드 개수 증가 | 단일 인스턴스 사양 증설 | 큐 길이 등 이벤트 양 |
| 무중단성 | 로드 밸런서 편입으로 가능 | 재기동 수반 가능 | 가능, 0 파드까지 축소 |
| 확장 한계 | 분산 구조 안에서 여지가 큼 | 하드웨어 최대 사양 제한 | 이벤트 소스 처리량에 비례 |
| 적합 워크로드 | 무상태(Stateless) 웹·API | 상태 저장 DB 계층 | 큐 기반 배치·비동기 처리 |
| 비용 특성 | 스팟 인스턴스 결합으로 탄력적 | 고사양 단가 비선형 증가 | 유휴 구간 비용 최소화 |

- 선택 기준 : 상태 없는 변동 트래픽은 수평 확장, 상태 저장 계층은 수직 확장, 메시지 큐 기반 비동기 작업은 KEDA로 구분하는 구성이 일반적.

## Ⅴ. 오토스케일링의 한계와 방안

- 핵심 요약 : 반응 지연, 플래핑, 스케일인 시 요청 유실을 예측 결합, 임계치 간격, 종료 절차로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 반응형 지연에 따른 스파이크 장애 | 지표 감지와 기동 사이 용량 부족 → 급증 구간 서비스 저하 | 예측형 스케일링 결합, 여유 용량 상시 유지 | 기동 소요 시간, 급증 구간 오류율 |
| 플래핑 (Flapping) | 임계치 경계에서 증설과 축소 반복 → 라우팅 변경과 시스템 불안정 | **히스테리시스** (Hysteresis, 증설·축소 임계치 간격 확대), 축소 안정화 창 조정 | 스케일 이벤트 빈도 |
| 스케일인 시 트랜잭션 유실 | 인스턴스 강제 종료로 처리 중 요청 단절 → 게이트웨이 오류 | **커넥션 드레이닝** (Connection Draining, 종료 전 연결 처리 대기) 후 **그레이스풀 셧다운** (Graceful Shutdown) 적용 | 종료 중 실패 요청 수 |

- 쿠버네티스 HPA는 축소 안정화 창의 기본값을 300초로 두므로 워크로드 특성에 맞춘 조정 절차가 필요함.

## Ⅵ. 오토스케일링에 대한 기술사적 제언

- 핵심 요약 : 비용 구조 설계, 비즈니스 지표 연계, 정책 검증 절차를 함께 갖추어 오토스케일링을 상시 운영 체계로 정착.

1. 운영팀은 기본 용량을 온디맨드 인스턴스로 고정하고 급증 구간만 스팟 인스턴스로 채우는 혼합 운영을 적용해 비용 효과를 월별 지표로 검증한다.
2. 아키텍처팀은 주문 대기열 깊이 같은 비즈니스 지표를 KEDA 이벤트 소스로 연결해 CPU 지표보다 앞선 증설 구조를 마련한다.
3. 품질팀은 부하 테스트와 카오스 엔지니어링을 릴리스 주기에 포함시켜 임계치와 쿨다운 값의 유효성을 주기적으로 확인한다.

## Ⅶ. 결론

- 핵심 요약 : 오토스케일링은 폐루프 제어로 가용성과 비용 효율을 함께 얻는 탄력성 기술.
- 자동화의 효과는 지표 선정과 정책 값, 종료 절차가 하나의 운영 기준으로 묶일 때 실현됨.
