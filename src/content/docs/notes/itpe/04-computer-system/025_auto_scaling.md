## Ⅰ. 오토스케일링(Auto Scaling)의 개요

- 핵심 요약 : **오토스케일링**은 워크로드 변동에 따라 컴퓨팅 리소스를 자동 확장/축소하는 클라우드 탄력성 제어 기술.
- 개념 : 애플리케이션의 워크로드 변동, 사용자 트래픽 급증, CPU(Central Processing Unit)/메모리 부하 상태를 실시간 모니터링하여, 컴퓨팅 리소스의 용량을 인적 개입 없이 자동으로 확장(Scale-out/Scale-up)하거나 축소(Scale-in/Scale-down)하는 **클라우드 탄력성(Elasticity)** 제어 기술.
- 배경 및 필요성 : 전통적인 온프레미스의 피크 트래픽 대비 **과다 프로비저닝** (Over-provisioning)에 따른 비용 낭비와, 돌발 트래픽 폭증 시 인프라 용량 부족으로 발생하는 서비스 장애를 근원적으로 해결하기 위해 개발됨.
- 핵심 목적 : **SLA**(Service Level Agreement) 서비스 가용성 보장, 트래픽 급증 시 무중단 자동 확장, 유휴 시간대 자원 회수를 통한 클라우드 인프라 TCO(Total Cost of Ownership) 극적 절감.

## Ⅱ. 오토스케일링(Auto Scaling)의 특징 및 장점

- 핵심 요약 : **폐루프 제어·반응형/예측형/스케줄형**으로 자동 탄력성 확보.
1. **반응형 스케일링 (Reactive)** : CPU 이용률, 메모리, HTTP(Hypertext Transfer Protocol) 요청 수가 지정된 임계치(Threshold)를 초과하거나 미달할 때 사후 확장/축소.
2. **예측형 스케일링 (Predictive)** : 머신러닝 시계열 예측 모델을 적용하여 과거 트래픽 주기 패턴을 학습하고 급증 15~30분 전에 사전 선제 증설.
3. **스케일링 정책 (Scale-Out vs Scale-In)** : 급증 시 신속한 증설(Scale-Out)을 위해 공격적 스텝 정책을 적용하고, 축소(Scale-In) 시 플래핑 방지를 위해 점진적 축소.
4. **쿨다운 기간 (Cooldown Period)** : 신규 인스턴스 기동 및 서비스 안정화 시간을 고려하여 연속적인 스케일링 트리거를 일정 시간 차단.

## Ⅲ. 오토스케일링(Auto Scaling)의 구조 및 동작 메커니즘

- 핵심 요약 : **모니터링 → 정책 평가 → 프로비저닝 → 쿨다운** 폐루프 제어.
- 오토스케일링은 지표 수집(Metrics Collection), 정책 평가(Evaluation), 프로비저닝 실행(Execution), 안정화 대기(Cooldown)의 **폐루프 제어(Closed-loop Control)** 아키텍처로 동작함.

```text
[ 오토스케일링 폐루프 제어(Feedback Loop) 아키텍처 ]

[사용자 트래픽 유입]
        │
        ▼
+---------------------------------------------------------------+
| 로드 밸런서 & 애플리케이션 인스턴스 풀 (EC2 / K8s Pods)         |
+---------------------------------------------------------------+
        │
        ▼ 실시간 메트릭 추출
+---------------------------------------------------------------+
| 모니터링 엔진 (CloudWatch / Prometheus / Metrics Server)       |
|   - CPU / 메모리 이용률, 요청 수(RPS), 큐 대기열(Kafka Lag)    |
+---------------------------------------------------------------+
        │
        ▼ 임계치 비교 및 정책 판정
+---------------------------------------------------------------+
| 오토스케일링 컨트롤러 (Auto Scaling Group / HPA / Karpenter)   |
|                                                               |
|   * 판정 공식 : Desired = Current × (CurrentMetric / Target)  |
|                                                               |
|   - 반응형 (Threshold): CPU > 70% -> +2대 확장                |
|   - 예측형 (Predictive): AI 시계열 예측 기반 사전 증설         |
|   - 스케줄형 (Scheduled): 출근 시간대 사전 확장               |
+---------------------------------------------------------------+
        │
        ▼ 스케일링 액션 트리거
+---------------------------------------------------------------+
| 인프라 프로비저닝 (Scale-Out) / 자원 회수 (Scale-In)          |
|   - 쿨다운 기간 (Cooldown / Stabilization Window) 적용        |
|   - 그레이스풀 셧다운 (Graceful Termination) 및 드레이닝       |
+---------------------------------------------------------------+
```

## Ⅳ. 오토스케일링(Auto Scaling)의 비교

- 핵심 요약 : **Scale-Out/Scale-Up/KEDA** 비교.

| 비교 항목 | 수평적 확장 (Scale-Out) | 수직적 확장 (Scale-Up) | K8s 이벤트 기반 (KEDA, Kubernetes Event-Driven Autoscaling) |
|---|---|---|---|
| 확장 방식 | 노드/파드 인스턴스 개수 증가 | 단일 인스턴스의 vCPU/RAM(Random-Access Memory) 스펙 증설 | 메시지 큐 등 외부 이벤트 큐 기반 증설 |
| 서비스 무중단성 | 완전 무중단 (로드밸런서 자동 편입) | 재기동 필요 (다운타임 수반 가능) | 완전 무중단 (0부터 수천 개까지 확장) |
| 확장 한계 | 분산 소프트웨어 구조 시 사실상 무한 | 단일 하드웨어 최대 물리 스펙 한계 | 이벤트 소스 처리량에 비례하여 무한 |
| 상태 관리 | 무상태(Stateless) 워크로드 필수 | 상태 유지(Stateful: DB) 시스템 적합 | 배치 작업, 비동기 파이프라인 적합 |
| 비용 효율 | 유연한 탄력성, 스팟 인스턴스 활용 | 대형 인스턴스 단가 비선형적 증가 | Scale-to-Zero 지원으로 비용 극소화 |

- 현대 클라우드에서는 단일 서버 스펙을 키우는 Scale-Up보다 MSA(Microservice Architecture) 무상태 컨테이너 기반의 Scale-Out이 오토스케일링의 핵심 주류를 형성함.

## Ⅴ. 오토스케일링(Auto Scaling)의 한계와 방안

- 핵심 요약 : **스파이크 지연·플래핑·트랜잭션 유실**을 예측형·Hysteresis·Graceful Shutdown으로 대응.

- 반응형 스케일링의 **지연** (Lag)으로 인한 스파이크 장애 :
  - 한계점 : 트래픽이 수 초 내에 급증할 때 메트릭 감지 및 VM(Virtual Machine)/파드 기동 시간(수 분 소요) 동안 서버 다운 발생.
  - 해결 방안 : 예측형 스케일링(Predictive Scaling) 결합, 최소 예비 버퍼(Over-provisioning) 파드 상시 유지, Karpenter 기반 초고속 노드 프로비저닝.
- 잦은 확장과 축소 반복에 따른 **플래핑(Flapping)** 현상 :
  - 한계점 : 임계치 경계에서 인스턴스가 지속적으로 켜지고 꺼지며 네트워크 라우팅 변경 및 시스템 불안정성 유발.
  - 해결 방안 : 확장과 축소의 임계치 간격을 넓게 설정(Hysteresis), Scale-In 안정화 윈도우(기본 300초) 엄격 적용.
- **스케일인(Scale-In)** 시 처리 중인 트랜잭션 유실 :
  - 한계점 : 인스턴스 강제 종료 시 클라이언트 연결 및 인플라이트(In-flight) 요청이 중단되어 HTTP 502/504 에러 발생.
  - 해결 방안 : 커넥션 드레이닝(Connection Draining / Deregistration Delay), K8s PreStop Hook 및 Graceful Shutdown(SIGTERM) 구현.

## Ⅵ. 오토스케일링(Auto Scaling) 적용 제언

- 핵심 요약 : **스팟 하이브리드·KEDA·카오스 엔지니어링**.
- 스팟(Spot) 인스턴스 하이브리드 오토스케일링 : 온디맨드 베이스라인 + 스팟 확장 영역으로 비용 최적화.
- KEDA 비즈니스 메트릭 기반 : 주문 대기열·결제 요청 수 기반 선제 스케일링.
- 카오스 엔지니어링 기반 탄력성 검증 : 부하 테스트 및 모의 훈련.

## Ⅶ. 결론

- 핵심 요약 : 오토스케일링은 **폐루프 자동 탄력성**으로 SLA 보장·TCO 절감을 실현하나 스파이크 지연·플래핑 관리가 필수.
- 오토스케일링은 실시간 메트릭 기반 폐루프 제어로 자원을 자동 확장/축소하여 SLA와 TCO를 최적화하지만, 스파이크 지연·플래핑·트랜잭션 유실 리스크를 예측형·Hysteresis·Graceful Shutdown으로 관리해야 함.
- 답안에는 폐루프 아키텍처, Scale-Out/Up/KEDA 비교, 한계·대응, 스팟·KEDA·카오스 제언을 연결.
