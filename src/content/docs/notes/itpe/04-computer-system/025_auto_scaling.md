## 지식 로드맵 내 현재 위치

컴퓨터 시스템 및 네트워크 → 핵심 개념 → 오토스케일링

## 30초 인출

- 본질: 시간대별 트래픽 편차에 따른 유휴 자원 비용 낭비와 순간 트래픽 폭주 시의 서버 다운 위험
- 메커니즘: 시스템 부하 메트릭(CPU, 메모리, 요청 수)을 실시간 모니터링하여 서버 인스턴스나 컨테이너를 자동으로 동적 확장(Scale-out) 및 축소(Scale-in)

## 핵심 용어

- HPA(Horizontal Pod Autoscaler): 파드의 개수를 늘리거나 줄여(수평 확장) 부하를 분산하는 쿠버네티스의 표준 오토스케일러
- 쿨다운(Cooldown / Stabilization Window): 스케일링 동작 후 새로운 인스턴스가 완전히 부팅되어 메트릭이 안정화될 때까지 추가 스케일링을 일시 제한하는 대기 시간
- 플래핑(Flapping): 부하가 임계치 주변에서 진동할 때 인스턴스 증설과 삭제가 끊임없이 반복되며 시스템을 불안정하게 만드는 현상

## 1교시 10점 답안

### 정의·목적

- 정의: 오토스케일링은/는 시스템 부하 메트릭(CPU, 메모리, 요청 수)을 실시간 모니터링하여 서버 인스턴스나 컨테이너를 자동으로 동적 확장(Scale-out) 및 축소(Scale-in) 방식이다.
- 목적: 서비스 무중단 보장 및 인프라 비용 절감에 기여한다.

### 핵심 구조와 작동

```text
[ 모니터링 에이전트 (Metrics Server / Prometheus) ]
                 │ (CPU/메모리/큐 적재량 수집: 15초 주기)
                 v
+─────────────────────────────────────────────────────────────+
|               오토스케일링 컨트롤러 (HPA / ASG)              |
|   - 계산식: 목표 레플리카 수 = ceil[ 현재 레플리카 x (현재 부하 / 목표 부하) ]
|   - 판정: CPU 사용률 80% 초과 시 스케일 아웃 트리거         |
+─────────────────────────────────────────────────────────────+
                 │
  (증설 명령: Scale-out) ──> [ 쿨다운 타이머 가동 (Cooldown: 300초) ]
                 │
                 v
+─────────────────────────────────────────────────────────────+
|     서버 / 컨테이너 인프라 풀                                |
|  [ Pod 1 ] [ Pod 2 ] ───(동적 신규 투입)───> [ Pod 3 ] [ Pod 4 ] |
+─────────────────────────────────────────────────────────────+
                 ▲
                 │ (새 인스턴스 헬스체크 통과 후 트래픽 유입)
[ 로드밸런서 (ALB / Ingress Controller) ] <── [ 사용자 트래픽 폭주 ]
```

## 2~4교시 25점 답안

### Ⅰ. 핵심 구조와 작동

```text
[ 모니터링 에이전트 (Metrics Server / Prometheus) ]
                 │ (CPU/메모리/큐 적재량 수집: 15초 주기)
                 v
+─────────────────────────────────────────────────────────────+
|               오토스케일링 컨트롤러 (HPA / ASG)              |
|   - 계산식: 목표 레플리카 수 = ceil[ 현재 레플리카 x (현재 부하 / 목표 부하) ]
|   - 판정: CPU 사용률 80% 초과 시 스케일 아웃 트리거         |
+─────────────────────────────────────────────────────────────+
                 │
  (증설 명령: Scale-out) ──> [ 쿨다운 타이머 가동 (Cooldown: 300초) ]
                 │
                 v
+─────────────────────────────────────────────────────────────+
|     서버 / 컨테이너 인프라 풀                                |
|  [ Pod 1 ] [ Pod 2 ] ───(동적 신규 투입)───> [ Pod 3 ] [ Pod 4 ] |
+─────────────────────────────────────────────────────────────+
                 ▲
                 │ (새 인스턴스 헬스체크 통과 후 트래픽 유입)
[ 로드밸런서 (ALB / Ingress Controller) ] <── [ 사용자 트래픽 폭주 ]
```

### Ⅱ. 핵심 특성

- CPU/메모리 기반의 전통적 오토스케일링은 '사후 반응형(Reactive)'임 → 트래픽이 몰려 CPU가 튀었을 때는 이미 늦었으며, 새 컨테이너가 뜨는 수십 초 동안 타임아웃 장애 발생
- 따라서 큐 대기 패킷 수(Kafka Lag, SQS Queue Depth)나 초당 요청 수(RPS) 같은 '선행 비즈니스 지표'를 기준으로 스케일링하는 KEDA(Kubernetes Event-driven Autoscaling) 도입이 필수적임
- 웹/앱 서버는 무한히 스케일 아웃될 수 있으나 백엔드 RDBMS의 커넥션 풀(DB Connection Pool)은 물리적 한계가 존재 → 프론트엔드가 100대로 확장될 때 DB가 커넥션 폭주로 동반 붕괴하므로 데이터베이스 프록시(PgBouncer, RDS Proxy)가 반드시 동반되어야 함

### Ⅲ. 관련 개념과 구분

- HPA vs VPA: HPA = 인스턴스 개수를 늘려 수평 분산(무중단, 무상태 앱용) / VPA = 단일 인스턴스의 CPU/메모리 스펙을 격상(재기동 수반, 상태 보유 DB용)

### Ⅳ. 적용 문제와 대응

- 사례: 131회 기출 선착순 티켓팅 이벤트 시 오토스케일링 지연으로 인한 서비스 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 이벤트 시작 1분 만에 접속자 100배 폭증 시 인스턴스 생성 지연으로 타임아웃 | 이미지 다운로드 및 초기화 시간(수 분) 소요로 인한 반응형 스케일링 지체 | 사전 스케줄링(Scheduled Scaling) 및 인스턴스 사전 예열(Pre-warming) | 트래픽 유입 즉시 100% 가용 용량 확보 |
| 트래픽 경계선에서 파드가 생성과 삭제를 수 분 주기로 반복하여 자원 낭비 | 스케일인(Scale-in) 안정화 윈도우(쿨다운) 부재 | HPA 축소 지연 윈도우(기본 300초) 설정 및 점진적 축소율(Rate Limit) 적용 | 플래핑 억제 및 클러스터 안정화 |

### Ⅴ. 기술사적 제언

| 문제 | 해결 방안 |
|---|---|
| 적용 환경에서 발생하는 핵심 제약 | 기존 대책을 적용하고 핵심 운영 지표를 확인해 개선한다. |
