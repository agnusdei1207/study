## 30초 인출

- 본질: 가속기(GPU/FPGA)가 호스트 메모리를 접근할 때 PCIe 버스를 타면 복사와 DMA 오버헤드로 지연이 크고 캐시 동기화가 불가능함
- 메커니즘: PCIe 물리 계층 위에 하드웨어 레벨의 캐시 일관성(Cache Coherence)과 메모리 직접 접근 프로토콜을 구현

## 핵심 용어

- CXL.io: PCIe 프로토콜과 호환되는 I/O 프로토콜로, 장치 검색, 등록, 인터럽트 및 가상화 I/O를 담당
- CXL.cache: 가속기(디바이스)가 호스트 CPU의 메인 메모리를 극도로 낮은 지연시간으로 직접 캐싱할 수 있도록 지원하는 프로토콜
- CXL.mem: 호스트 CPU가 CXL로 연결된 외부 메모리 장치를 마치 로컬 DDR 메모리처럼 읽고 쓸 수 있게 해주는 메모리 확장 프로토콜

### Ⅱ. 핵심 특성

- CXL의 최대 킬러 앱은 '메모리 풀링(Memory Pooling)'임 → 기존 서버들은 CPU 소켓당 메모리 장착 한계 때문에 일부 서버는 메모리가 부족해 터지고 다른 서버는 메모리가 남아도는 '메모리 고립(Stranded Memory)'이 심각했음 → CXL 스위치로 메모리를 풀로 묶어 필요한 서버에 동적 할당함
- Type 3 메모리는 '느린 DRAM이 아니라 빠른 스토리지'로 봐야 함 → 로컬 CPU 직결 DDR보다는 수십 ns 느리지만, NVMe SSD보다는 수천 배 빠르므로 대규모 인메모리 DB나 LLM KV-Cache의 계층형 메모리(Tier 2)로 최적임
- 소프트웨어 수정 없이 하드웨어가 일관성을 보장함 → 프로그래머가 복잡한 DMA 복사 API나 소켓 통신을 짤 필요 없이 일반 포인터 역참조(`*ptr`)로 원격 가속기 메모리를 읽고 쓸 수 있음

### Ⅲ. 관련 개념과 구분

- CXL vs PCIe: PCIe = 블록 I/O 전송 중심, OS 드라이버 경유, 캐시 비일관성, 수 마이크로초 지연 / CXL = 바이트 단위 메모리 주소 지정, 하드웨어 캐시 일관성, 수십~수백 나노초 초저지연

### Ⅳ. 적용 문제와 대응

- 적용 상황: 서버별 메모리 수요 편차가 커서 일부 장비의 유휴 메모리를 다른 장비가 활용하지 못하는 상황
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 VM의 메모리 스파이크 시 전체 서버 OOM 발생 및 메모리 파편화 | 서버 간 물리 메모리가 격리되어 유휴 메모리를 공유하지 못함(Stranded Memory) | CXL Type 3 기반 메모리 풀링(CXL Switch Fabric) 도입 | 서버 간 동적 메모리 대여 및 유휴율 15% 이하 절감 |
| CXL 확장 메모리 접근 시 L1/L2 캐시 미스로 인한 애플리케이션 지연 | 로컬 NUMA 노드 대비 CXL 링크 경유 레이턴시(약 100ns 추가) 발생 | 리눅스 티어드 메모리(Tiered Memory / AutoNUMA) 커널 적용 | 핫 데이터는 로컬 DRAM, 콜드 데이터는 CXL에 자동 계층화 |
