## Ⅰ. 우선순위 역전(Priority Inversion)의 개요

- **개념** : 실시간 운영체제(RTOS) 또는 선점형 우선순위 스케줄링 환경에서, 높은 우선순위를 가진 프로세스가 낮은 우선순위 프로세스가 점유한 공유 자원(뮤텍스/세마포어)을 대기하는 동안, 자원과 무관한 중간 우선순위 프로세스가 낮은 우선순위 프로세스를 선점하여 실행됨으로써 결과적으로 높은 우선순위 프로세스의 실행이 지연되는 비정상적 스케줄링 역전 현상.
- **배경 및 필요성** : 1997년 화성 패스파인더(Mars Pathfinder) 탐사선의 잦은 시스템 리셋 장애 원인으로 전 세계에 널리 알려졌으며, 엄격한 마감시간(Deadline) 준수가 필수적인 하드 리얼타임 임베디드 및 미션 크리티컬 제어 시스템에서 시스템 붕괴를 초래할 수 있어 연구됨.
- **핵심 목적** : 실시간 태스크의 데드라인 준수 보장, 우선순위 상속(PIP) 및 우선순위 올림(PCP) 프로토콜을 통한 블로킹 지연 상한 통제.

## Ⅱ. 우선순위 역전(Priority Inversion)의 핵심 아키텍처 및 동작 메커니즘

우선순위 역전은 고/중/저 3개 태스크 간의 락 경합과 선점으로 발생하며, 락을 보유한 저순위 태스크의 우선순위를 일시 승격시키는 상속(PIP) 또는 자원 자체에 최고 우선순위를 부여하는 올림(PCP)으로 해결함.

```text
[ 우선순위 역전 발생 과정 vs 우선순위 상속(PIP) 해결 ]

1. 우선순위 역전 발생 (Task H: 고순위, Task M: 중순위, Task L: 저순위)
Task H ─── (대기) ───────────────X [Task L이 Lock 반환 못해 블로킹 지속!]
Task M ────────────────────────> [Task L 선점하여 CPU 독점 실행!]
Task L ──> [Lock 획득] ──X(선점됨)
  * 결과: 우선순위가 낮은 Task M이 가장 높은 Task H보다 먼저 실행 완료되는 모순!

2. 우선순위 상속 프로토콜 (PIP: Priority Inheritance Protocol) 해결
Task H ─── (Lock 요청) ──────────┐ (Task H 수준으로 우선순위 상속!)
                                 ▼
Task L ──> [Lock 획득] ─────────> [Task L 실행 가속] ──> [Lock 해제]
Task M ─── (Task L보다 순위 낮아져 선점 불가!) ──────────────────┐
                                                                 ▼
Task H ──────────────────────────────────────────────> [Lock 획득 및 정상 완료]
Task M ────────────────────────────────────────────────────────> [후순위 실행]
```

- **발생 시나리오** : 저순위 태스크 L이 공유 자원 락을 획득 -> 고순위 태스크 H가 동일 자원 요청 후 블록 -> 무관한 중순위 태스크 M이 태스크 L을 선점 -> 태스크 L이 락을 풀지 못해 태스크 H가 무한 대기.
- **무한 블로킹 위험** : 태스크 M과 유사한 중간 우선순위 태스크들이 지속적으로 유입될 경우 고순위 태스크 H의 지연시간이 비결정적(Unbounded)으로 팽창.
- **우선순위 상속 (PIP)** : 공유 자원을 점유한 저순위 태스크에게 해당 자원을 대기하는 가장 높은 태스크의 우선순위를 일시적으로 상속 부여하여 중순위 태스크의 선점을 방지.
- **우선순위 올림 (PCP)** : 각 공유 자원마다 해당 자원을 접근할 수 있는 태스크들 중 가장 높은 우선순위(Ceiling)를 사전에 부여하고, 락 획득 시 즉시 Ceiling으로 승격시켜 교착상태까지 동시 예방.

## Ⅲ. 우선순위 역전(Priority Inversion)의 세부 구성 요소 및 비교 분석

| 비교 항목 | 기본 우선순위 스케줄링 | 우선순위 상속 프로토콜 (PIP) | 우선순위 올림 프로토콜 (PCP) |
|---|---|---|---|
| **역전 방지 여부** | **역전 발생 (무방비)** | **역전 방지 (동적 승격)** | **역전 완벽 방지 (사전 상한)** |
| **우선순위 승격 시점**| 없음 | 고순위 태스크가 락 대기 시 | **자원(Lock) 획득 즉시** |
| **승격 우선순위 값** | 없음 | 대기 중인 최고 태스크 우선순위 | **자원에 사전 정의된 Ceiling 값** |
| **교착상태(Deadlock)**| 발생 가능 | 연쇄 상속 시 데드락 발생 가능 | **교착상태 원천 방지 (Deadlock-Free)**|
| **블로킹 횟수 상한** | 무제한 (비결정적) | 다중 락 대기 시 복수 블로킹 | **최대 1개 임계 영역 시간으로 제한** |

- PIP는 구현이 직관적이나 연쇄 블로킹과 교착상태 위험이 있고, PCP는 교착상태까지 완벽 차단하나 시스템 전체의 우선순위 사전 분석이 요구됨.

## Ⅳ. 우선순위 역전(Priority Inversion)의 주요 한계점 및 해결 방안

- **우선순위 상속(PIP) 환경에서의 교착상태(Deadlock) 및 연쇄 블로킹** :
  - **한계점** : 복수의 공유 자원을 교차 점유하는 환경에서 PIP 적용 시 상속 체인이 꼬이며 환형 대기 데드락 발생 가능.
  - **해결 방안** : 우선순위 올림 프로토콜(PCP) 또는 즉시 올림(Immediate Priority Ceiling)을 적용하여 단일 임계영역 블로킹 보장.
- **세마포어(Semaphore) 사용 시 소유자 추적 불가** :
  - **한계점** : 카운팅 세마포어는 신호 전달(Signaling) 메커니즘으로 사용되어 락을 '소유한' 태스크를 특정할 수 없어 우선순위 승격 불가.
  - **해결 방안** : 상호 배제 목적의 동기화에는 소유자 스레드 ID가 명확한 뮤텍스(Mutex with Priority Inheritance)만 사용.
- **임계 구역(Critical Section) 장기 점유로 인한 스케줄링 지연** :
  - **한계점** : 저순위 태스크가 락을 잡은 상태에서 I/O를 수행하거나 긴 연산을 실행하여 상속을 적용해도 고순위 태스크 지연.
  - **해결 방안** : 임계 구역 내 I/O 및 블로킹 시스템 콜 호출 엄격 금지, 락 프리(Lock-Free) 큐 및 RCU 도입.

## Ⅴ. 우선순위 역전(Priority Inversion) 적용 및 발전을 위한 기술사적 제언

- **차량용 전장 SW(AUTOSAR) OS 스케줄링 표준 준수** : 자동차 기능안전성(ISO 26262) 충족을 위해 실시간 브레이크 및 조향 태스크의 리소스 락에 PCP(Priority Ceiling) 프로토콜 필수 적용.
- **자바 및 POSIX 멀티스레드 PTHREAD_PRIO_INHERIT 활성화** : 고성능 C/C++ 미션 크리티컬 애플리케이션 개발 시 `pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT)` 설정 점검.
- **주기적 태스크 스케줄링 분석(RMA: Rate Monotonic Analysis) 수행** : 태스크 주기와 실행 시간을 수리 모델링하여 최악의 블로킹 시간(Worst-case Blocking Time)을 수학적으로 증명하는 엔지니어링 실증 권장.
