## 연관 키워드

- 메모리 누수, Memory Leak, 포인터 유실, 참조 유지, 가비지 컬렉션, GC 루트, OOM
- RAII, 약한 참조, ThreadLocal, 힙 덤프, Soak Test, APM

## Ⅰ. 메모리 누수의 개요

- 핵심 요약 : 사용을 마친 메모리가 해제 또는 회수되지 못해 가용 자원이 점진적으로 줄어드는 소프트웨어 결함.
- 개념 : 프로그램이 동적으로 할당한 메모리를 사용 종료 후에도 해제하지 않거나 회수 대상에서 벗어나, 점유된 채 재사용할 수 없는 영역이 누적되는 **메모리 누수** (Memory Leak) 결함. 명시적 해제 언어와 관리(Managed) 언어 모두에서 발생함.
- 배경 및 필요성 : 장기 가동 서버에서 누적 누수가 가용 힙을 고갈시키면 **메모리 부족** (OOM, Out of Memory)에 따른 강제 종료로 서비스 중단이 발생하여, 사전 탐지와 생명주기 통제 체계의 필요가 커짐.
- 주요 목적 : 메모리 생명주기 관리의 무결성 확보, 누수 징후의 조기 탐지, 분석 도구 기반 원인 지점의 규명과 예방.

## Ⅱ. 메모리 누수의 특징 및 장점

- 핵심 요약 : 해제 경로의 상실과 참조 경로의 잔존이라는 두 원리가 자원 고갈과 서비스 장애로 이어지는 구조.

1. **포인터 유실** (Unreachable Memory) : 할당 블록의 주소를 담은 마지막 참조가 덮어쓰기나 스코프 이탈로 소실 → 해제 호출이 불가능해진 상태의 영구 점유.
2. **참조 유지 누수** (Reachable Leak) : 사용 종료 객체가 정적 컬렉션·이벤트 리스너의 강한 참조에 묶여 **가비지 컬렉션** (GC, Garbage Collection)의 회수 대상에서 제외 → 누적의 지속.
3. 자원 핸들 누수 : 파일·소켓·데이터베이스 커넥션의 close 누락 → 힙 이외의 커널 자원 고갈로 확대.
4. 장애 징후 : 힙 사용량의 우상향 추세, Full GC의 빈발, 재시작 후의 일시적 정상화 → 조기 감지의 근거로 활용 가능.

## Ⅲ. 메모리 누수의 구조 (흐름)

- 핵심 요약 : 비관리 언어는 해제 경로의 단절로, 관리 언어는 GC 루트로부터의 참조 잔존으로 누수가 발생하는 이중 구조.
- **GC 루트** (GC Root, static 필드와 스레드 스택 등 회수 판단의 기준점) : GC는 루트에서 도달 가능한 객체만 살아 있는 것으로 판단하므로, 루트로의 참조가 남으면 회수되지 않음.

```text
[ C/C++ 포인터 유실 경로 ]

힙 블록 할당 (포인터가 주소 보관)
   ↓ 주소 덮어쓰기·스코프 이탈
해제 함수 호출 불가
   ↓
영구 점유 (가용 힙 감소)
```

```text
[ 관리 언어 참조 유지 경로 ]

GC 루트 (static·싱글톤·스레드 로컬)
   ↓ 강한 참조 잔존
장수명 캐시·이벤트 리스너
   ↓ 등록 해지 누락
사용 종료 객체 (도달 가능 판정)
   ↓
Old 세대 포화 → Full GC 빈발
```

## Ⅳ. 비관리 환경과 관리 환경의 비교

- 핵심 요약 : 비관리 환경은 해제 책임이, 관리 환경은 참조 관리 책임이 개발자에게 남는 구조의 차이.

| 비교 축 | 비관리 환경 (C/C++) | 관리 환경 (Java, C#) |
| --- | --- | --- |
| 회수 주체 | 개발자의 명시적 해제 호출 | 런타임 GC의 자동 회수 |
| 대표 원인 | 해제 누락, 예외 경로의 해제 이탈 | 컬렉션·리스너 미정리, 스레드 로컬 미제거 |
| 탐지 도구 | Valgrind, ASan(AddressSanitizer) | 힙 덤프 분석기, APM(Application Performance Monitoring) |
| 예방 기법 | **RAII** (Resource Acquisition Is Initialization, 자원 획득과 해제를 객체 수명에 묶는 기법), 스마트 포인터 | 약한 참조(Weak Reference), try-with-resources |
| 장애 징후 | 프로세스 메모리의 지속 증가 | Old 세대 증가와 Full GC 빈발 |

- 선택 기준 : 환경별 회수 주체에 맞춰 점검 항목을 정하고, 관리 언어라도 참조 관리를 개발자의 책무로 유지하는 기준으로 운영함.

## Ⅴ. 메모리 누수의 한계와 방안

- 핵심 요약 : 단기 테스트의 미발견, 덤프 분석 부담, 스레드 풀 오염을 장시간 테스트, 격리 분석, 정리 강제화로 일대일 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 단기 테스트 미발견 | 소량 누수는 반복 실행 후 가시화 → 운영 수일 후 OOM | 배포 전 검증에 **Soak Test** (장시간 부하 테스트) 포함 | 시간 경과별 힙 사용량 기울기 |
| **힙 덤프** (Heap Dump, 힙 상태의 전체 스냅샷) 분석 부담 | 대용량 덤프 캡처 동안 서비스 지연 위험 | 격리 인스턴스에서 덤프 추출, 운영 중에는 추세 감시만 수행 | 덤프 추출 소요 시간 |
| 스레드 풀 오염 | 스레드 로컬(ThreadLocal) 미정리 → 재사용 스레드에 데이터 잔존 | 요청 종료 경로의 정리 코드 실행을 코딩 표준으로 강제 | 잔존 데이터 탐지 건수 |

## Ⅵ. 메모리 누수에 대한 기술사적 제언

- 핵심 요약 : 코딩 표준, 운영 감시, 언어 전략의 세 주체가 누수를 사후 발견이 아닌 설계·운영 단계에서 통제하는 방향.

1. 개발 조직 : 자원의 획득·해제를 객체 수명에 묶는 RAII 패턴과 try-with-resources 사용을 코딩 표준으로 채택하는 제도가 바람직함.
2. 운영 조직 : APM의 힙 사용량 추세 경보를 장애 관리 절차에 연동하여 누수 징후를 상시 감시하는 체계가 필요함.
3. 기술 전략 조직 : 해제 시점을 컴파일 단계에서 강제하는 소유권(Ownership) 모델 언어의 도입 범위를 신규 시스템 기준으로 검토하는 방안이 유효함.

## Ⅶ. 결론

- 핵심 요약 : 메모리 누수는 해제와 회수 경로의 상실로 생기는 결함이며, 생명주기 통제가 근본 대책.
- 자동 회수 기능의 유무와 무관하게 참조 관리의 책임은 개발 조직에 남는다는 인식이 예방의 출발점임.
