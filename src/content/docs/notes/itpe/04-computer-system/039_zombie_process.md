## 연관 키워드

- 좀비 프로세스(Zombie Process), 종료 상태(Exit Status), 프로세스 테이블, PCB(Process Control Block)
- PID, wait()·waitpid(), SIGCHLD, WNOHANG, 고아 프로세스(Orphan Process)
- init·systemd, 컨테이너 PID 1, tini, pid_max

## Ⅰ. 좀비 프로세스의 개요

- 핵심 요약 : 실행을 마친 뒤 자원은 반환했지만 부모가 종료 상태를 수거하지 않아 프로세스 테이블 항목만 남은 프로세스 상태.
- 개념 : 유닉스·리눅스에서 자식 프로세스가 종료한 후 부모가 wait() 계열 시스템 콜로 **종료 상태** (Exit Status)를 회수하지 않아 **프로세스 테이블** (Process Table)에 항목이 남은 **좀비 프로세스** (Zombie Process) 상태. 목록 표시는 Z 또는 defunct.
- 배경 및 필요성 : 커널은 부모가 자식의 종료 원인을 확인할 수 있도록 최소한의 종료 정보를 남기는 설계를 택함. 이 설계상 부모가 수거하지 않으면 항목이 누적되어 시스템 자원 관리의 장애 요인이 됨.
- 주요 목적 : 좀비 발생 원리의 이해, **프로세스 식별자** (PID, Process Identifier) 고갈의 예방, 컨테이너 환경에서 정리 책임의 설계.

## Ⅱ. 좀비 프로세스의 특징 및 장점

- 핵심 요약 : 자원 즉시 반환, 부모의 수거, 시그널 통지, 입양 정리가 정리 경로를 이루는 구조.

1. 자원 즉시 반환 : 메모리와 파일 디스크립터는 해제되고 종료 코드와 통계를 담은 **프로세스 제어 블록** (PCB, Process Control Block)만 잔존 → CPU·메모리 소비는 사실상 없음.
2. 수거 메커니즘 : 부모가 wait()·waitpid()로 종료 상태를 읽는 순간 커널이 항목을 제거 → 정상 정리 경로.
3. 비동기 통지 : 자식 종료 시 커널이 부모에 **SIGCHLD** 시그널을 전달 → 부모가 수거 시점을 인지하는 기반.
4. 입양 정리 : 부모가 먼저 종료하면 자식은 **고아 프로세스** (Orphan Process)가 되어 init 또는 systemd에 입양되고, PID 1이 주기 수거 → 정리 책임의 자동 이전.
5. 설계상 의미 : 종료 상태의 보존은 부모의 후속 판단(재시작 여부 등)을 가능하게 하는 정보 전달 수단 → 프로세스 계층 관리의 기반.

## Ⅲ. 좀비 프로세스의 구조 (흐름)

- 핵심 요약 : 자식의 종료부터 부모의 수거까지의 과도기가 좀비 상태이며, 부모 선종료 시 입양 경로로 전환되는 구조.

```text
[ 좀비 발생과 수거 ]

자식 exit() 호출
   ↓
자원 반환 · PCB 잔존
   ↓
커널의 부모 SIGCHLD 통지
   ↓
부모의 wait() 수거 전 → Z 상태 유지
   ↓
wait() 수거 → 항목 제거
```

```text
[ 부모 선종료 시 입양 ]

부모 프로세스 종료 (수거 없음)
   ↓
자식의 고아 프로세스 전환
   ↓
PID 1(init·systemd) 입양
   ↓
PID 1의 주기 wait() 수거
```

- 좀비는 이미 실행이 끝난 프로세스이므로 정리의 주체는 자식이 아니라 부모의 수거 동작 또는 PID 1의 입양 경로.

## Ⅳ. 정상·좀비·고아 프로세스의 비교

- 핵심 요약 : 상태 표시, 자원 점유, 부모 관계, 종료 처리에서 세 유형이 뚜렷이 구분됨.

| 비교 항목 | 정상 프로세스 | 좀비 프로세스 | 고아 프로세스 |
| --- | --- | --- | --- |
| 상태 표시 | R(실행)·S(대기) | Z·defunct | R·S |
| 자원 점유 | 메모리·CPU 사용 | PCB만 점유 | 정상 사용 |
| 부모 관계 | 생존 부모 | 생존하나 미수거 | 종료로 PID 1 입양 |
| 종료 처리 | 신호로 종료 가능 | 이미 종료, 신호 무효 | 신호로 종료 가능 |
| 발생 원인 | 일반 실행 | 부모의 수거 누락 | 부모의 선종료 |

- 좀비는 신호로 제거되지 않으므로 부모의 수거 로직 수정이나 부모 종료에 의한 입양 유도가 제거 수단이 됨.

## Ⅴ. 좀비 프로세스의 한계와 방안

- 핵심 요약 : PID 고갈, 수거 누락, 컨테이너 PID 1 공백을 입양 유도, 반복 수거, init 구성으로 일대일 해소.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| PID 고갈 | 좀비 누적으로 pid_max 상한 도달, 프로세스 생성 실패 | 부모 재기동으로 입양 유도, 상한·좀비 수 감시 | 좀비 수·PID 사용률 |
| 수거 누락 | 다수 자식 동시 종료 시 시그널 유실로 일부 방치 | SIGCHLD 핸들러에서 WNOHANG 옵션의 waitpid 반복 수거 | 미수거 항목 수 |
| 컨테이너 PID 1 공백 | 응용이 PID 1로 기동하면 수거 역할 부재 | tini·dumb-init 설치 또는 --init 옵션으로 init 구성 | 컨테이너별 좀비 수 |

## Ⅵ. 좀비 프로세스에 대한 기술사적 제언

- 핵심 요약 : 플랫폼 기본값의 정책화, 경보 지표화, 코딩 규약의 정착으로 누적 사고를 예방하는 방향.

1. 플랫폼 조직은 컨테이너 기본 정책으로 init 프로세스의 PID 1 역할을 고정해 팀별 구성 편차를 제거.
2. 운영 조직은 모니터링 체계에 좀비 프로세스 수를 경보 지표로 등록하고 증가 추세를 상시 추적.
3. 개발 조직은 하위 프로세스 생성 라이브러리 사용 시 종료 대기 호출의 짝 사용을 코딩 규약으로 정착.

## Ⅶ. 결론

- 핵심 요약 : 좀비 프로세스는 자원이 아닌 식별자 슬롯을 점유하는 종료 후 미수거 상태.
- 수거 책임을 부모 코드와 플랫폼 기본값에 이중으로 부여할 때 누적 사고가 예방됨.
