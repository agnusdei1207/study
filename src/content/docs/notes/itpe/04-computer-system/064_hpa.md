## 30초 인출

- 본질: 정적으로 고정된 파드 개수는 돌발 트래픽 시 OOM 다운을 부르고 유휴 시간대에는 클라우드 비용을 낭비함
- 메커니즘: 쿠버네티스 컨트롤러가 메트릭 서버로부터 실시간 부하를 폴링하여 목표 사용률에 맞게 파드 레플리카(Replicas) 수를 동적으로 조절

## 핵심 용어

- KEDA(Kubernetes Event-driven Autoscaling): CPU/메모리 외에 Kafka 큐 길이, AWS SQS 메시지 수 등 외부 이벤트 기반으로 파드를 0부터 N까지 오토스케일링하는 쿠버네티스 확장 컴포넌트
- 플래핑(Flapping / Churn): 트래픽이 경계선에서 출렁일 때 파드가 생성되었다가 즉시 삭제되기를 반복하며 클러스터 전체가 불안정해지는 현상
- 안정화 윈도우(Stabilization Window): 스케일 다운 시 일시적 트래픽 감소로 인한 성급한 파드 축소를 막기 위해 일정 시간(기본 5분) 동안의 최고 메트릭을 평가 기준으로 유지하는 지연 버퍼

### Ⅱ. 핵심 특성

- HPA의 기본 CPU 메트릭은 '가장 멍청한 메트릭'임 → 웹 애플리케이션의 응답 지연이나 장애는 DB 커넥션 고갈, 쓰레드 블로킹으로 터지는데, 이때 CPU 사용률은 오히려 0%로 떨어져 HPA가 파드를 줄여버리는 참사가 발생함
- 스케일링 수식은 올림(`ceil`)으로 동작함 → 부하가 1%만 넘어도 파드를 하나 더 띄워 여유를 확보하도록 설계되어 있어 보수적인 가용성을 지향함
- HPA와 VPA를 동일 메트릭(CPU/Mem)으로 동시 적용하면 자멸함 → HPA는 파드를 늘리려 하고 VPA는 파드 리소스를 키우려 하면서 서로 무한 충돌하므로, 동시 사용 시 HPA는 비즈니스 메트릭, VPA는 오프라인 모드(`Off`)로 분리해야 함

### Ⅲ. 관련 개념과 구분

- HPA vs CA(Cluster Autoscaler): HPA = 쿠버네티스 파드(Pod)의 개수를 동적으로 조절 / CA = 파드들이 노드에 스케줄링되지 못하고 `Pending`에 걸릴 때 클라우드 VM 노드 자체를 동적으로 증설

### Ⅳ. 적용 문제와 대응

- 사례: 137회 기출 및 대규모 쇼핑몰 타임세일 오픈 직후 파드 증설 지연으로 504 Gateway Timeout 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 트래픽 급증 시 HPA 반응이 늦어 초기 유입 사용자 접속 불가 | 메트릭 집계 지연(수십 초) 및 신규 스프링 부트 파드 기동 시간(1분 이상) 소요 | KEDA 기반 초당 요청 수(RPS) 선제 스케일링 및 스케줄 기반(CronHPA) 사전 증설 | 이벤트 시작 전 파드 선제 확보로 무중단 수용 |
| 트래픽 일시 진정 시 파드가 대량 삭제되어 곧이어 다시 재부팅 반복(Flapping) | 트래픽 출렁임에 즉각 스케일 다운 실행 | HPA `behavior.scaleDown.stabilizationWindowSeconds: 300` 설정 | 5분간 피크 메트릭 관찰 후 점진적 스케일 다운 |
