## 연관 키워드

- HPA(Horizontal Pod Autoscaler), 쿠버네티스(Kubernetes), 파드(Pod), 복제본(Replica), Metrics Server, 컨트롤 루프(Control Loop)
- 안정화 윈도우(Stabilization Window), 플래핑(Flapping), KEDA(Kubernetes Event-driven Autoscaling), VPA(Vertical Pod Autoscaler), CA(Cluster Autoscaler), Karpenter
- Requests, Pending, OPA Gatekeeper(Open Policy Agent Gatekeeper), 그레이스풀 셧다운(Graceful Termination)

## Ⅰ. HPA (Horizontal Pod Autoscaler)의 개요

- 핵심 요약 : **HPA**(Horizontal Pod Autoscaler)는 쿠버네티스(Kubernetes)에서 측정된 부하 지표에 따라 파드 복제본 수를 자동으로 늘리고 줄이는 컨트롤러.
- 개념 : 쿠버네티스 클러스터에서 Deployment, ReplicaSet 같은 워크로드의 CPU(Central Processing Unit) 이용률, 메모리 사용량, 또는 HTTP(Hypertext Transfer Protocol) 처리량과 큐 대기열 같은 커스텀·외부 메트릭을 주기적으로 관찰하여 **파드**(Pod)의 복제본(Replicas) 수를 조정하는 수평 확장 컨트롤러.
- 배경 및 필요성 : 마이크로서비스에서 트래픽 급증을 사람이 알아채 파드를 수동으로 늘리면 대응이 늦어 장애로 번지고, 반대로 트래픽이 줄어도 유휴 파드가 남아 인프라 비용이 새는 구조적 비용이 생김. 이 비용을 줄이려고 메트릭에 따라 복제본 수를 자동 조정하는 계층이 필요해져 도입됨.
- 주요 목적 : 트래픽 급증 시 무중단 가용성 보장, 목표 사용률 유지를 통한 성능 일관성 확보, 유휴 시 자원 회수를 통한 비용 최적화.

## Ⅱ. HPA (Horizontal Pod Autoscaler)의 특징 및 장점

- 핵심 요약 : 목표 파드 수 산정 공식, 주기적 컨트롤 루프, 안정화 윈도우, 이벤트 기반 확장이 결합되어 확장은 빠르게, 축소는 신중하게 이루어지는 구조.

1. 목표 파드 수 산정 : `desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]` → 현재 부하 비율을 복제본 수에 곱하고 올림하여 용량 부족을 남기지 않음.
2. 컨트롤 루프(Control Loop) 주기 : 기본 15초마다 메트릭을 조회하고 상태를 평가 → 부하 변화에 반응하는 최소 간격이 정해짐.
3. **안정화 윈도우** (Stabilization Window) : 축소 결정은 기본 300초 동안의 권고값 중 가장 큰 값을 적용 → 트래픽이 잠깐 줄었다가 다시 튀는 상황에서 파드가 반복 종료되고 생성되는 **플래핑**(Flapping)을 방지.
4. **KEDA**(Kubernetes Event-driven Autoscaling) 연동 : 메시지 큐 길이나 스트림 지연 같은 외부 이벤트를 기준으로 파드를 늘리고, 이벤트가 없을 때 0개까지 줄이는 확장 지원 → 유휴 비용 절감.

## Ⅲ. HPA (Horizontal Pod Autoscaler)의 구조 및 동작 메커니즘

- 핵심 요약 : 메트릭 수집 계층이 제공한 값을 HPA 컨트롤러가 주기적으로 평가하고, 결과 복제본 수를 Deployment의 spec.replicas에 반영하는 흐름.

```text
[ HPA 컨트롤 루프 ]

메트릭 수집
(Metrics Server, Prometheus Adapter)
      ↓ 기본 15초 주기 조회
HPA 컨트롤러
(목표 파드 수 계산, 스케일 정책 검증)
      ↓ 스케일 서브리소스 호출
Deployment / ReplicaSet
(spec.replicas 갱신)
      ↓
파드 생성 또는 종료
```

```text
[ 목표 파드 수 계산 예시 ]

현재 파드 2대, 현재 CPU 80%, 목표 CPU 50%

Desired = ceil[ 2 × (80 / 50) ]
        = ceil[ 3.2 ] = 4대
```

- 스케일 업은 평가 결과를 즉시 반영하고, 스케일 다운은 안정화 윈도우가 지난 뒤 반영되는 비대칭 구조임.

## Ⅳ. HPA (Horizontal Pod Autoscaler)의 비교

- 핵심 요약 : HPA는 파드 수를, VPA는 파드 하나의 크기를, CA는 노드 수를 조정하므로 확장 대상과 한계가 서로 다름.

| 비교 항목 | HPA (수평 파드 확장) | VPA (Vertical Pod Autoscaler, 수직 파드 확장) | CA (Cluster Autoscaler, 노드 확장) |
| --- | --- | --- | --- |
| 확장 대상 | 파드 복제본 수 | 파드 하나의 CPU·메모리 요청량 | 워커 노드 수 |
| 적용 워크로드 | 무상태(Stateless) 웹·API(Application Programming Interface) 서비스 | 재기동을 감수할 수 있는 단일 인스턴스 성격의 워크로드 | 클러스터 전체 자원이 부족할 때 |
| 무중단성 | 신규 파드 투입으로 무중단 | 파드 재기동이 따라와 일시 중단 가능 | 신규 노드 합류로 무중단 |
| 확장 한계 | 가용 노드 자원까지 | 단일 노드의 최대 스펙까지 | 클라우드 쿼터와 예산까지 |
| 운용 시 주의 | 같은 지표로 VPA와 함께 쓰면 충돌 위험 | 파드 크기만 키우면 노드가 막히므로 노드 확장과 결합 필요 | 파드 확장 없이 노드만 늘면 자원이 놀게 됨 |

- 선택 기준 : 무상태 워크로드는 HPA로 파드를 늘리고, 노드가 모자라면 CA나 Karpenter가 노드를 추가하는 식으로 두 계층을 결합하는 것이 일반적임.

## Ⅴ. HPA (Horizontal Pod Autoscaler)의 한계와 방안

- 핵심 요약 : 지표 지연, **Requests** 미설정, 노드 자원 고갈로 생기는 한계를 KEDA의 선행 지표, 정책 강제, 노드 자동 증설로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| CPU·메모리 지표의 지연 | 트래픽 급증 후 메트릭 집계와 파드 기동까지 시차가 생겨 초기 요청이 밀림 | KEDA로 메시지 큐 대기열 같은 선행 지표 기반 선제 확장 | 스케일 지연 시간, 초기 요청 실패율 |
| 리소스 Requests 미설정 | 파드 스펙에 `resources.requests`가 없으면 사용률 비율을 계산할 수 없어 HPA가 동작하지 않음 | 모든 배포 매니페스트에 requests를 필수로 두는 OPA Gatekeeper(Open Policy Agent 기반 정책 엔진) 정책 적용 | requests 미설정 워크로드 수 |
| 노드 자원 고갈로 인한 Pending 파드 | 파드 수는 늘었지만 노드 용량이 없어 신규 파드가 Pending 상태에 머묾 | Karpenter 또는 CA로 Pending 감지 시 노드를 자동 증설 | Pending 파드 체류 시간 |

## Ⅵ. HPA (Horizontal Pod Autoscaler)의 적용 제언

- 핵심 요약 : 축소 정책을 워크로드별로 튜닝하고, 비즈니스 지표를 함께 판정에 쓰며, 종료 시 요청 손실을 막는 그레이스풀 셧다운을 기본으로 삼는 방향.

1. 플랫폼 운영 조직은 HPA의 behavior 필드에서 확장 정책의 상한과 축소 안정화 윈도우를 워크로드별로 나누어 설정하여, 급증에는 빠르게 대응하고 일시적 감소에는 파드를 유지하게 한다.
2. 서비스 개발 조직은 CPU 사용률만으로 판단하지 않고 초당 요청 수(RPS, Requests Per Second)와 P99 응답 지연 같은 비즈니스 메트릭을 결합한 다차원 HPA 지표를 구성한다.
3. 서비스 개발 팀은 파드 종료 때 preStop 훅과 SIGTERM 신호 처리를 구현하여 진행 중인 요청을 마친 뒤 종료하는 **그레이스풀 셧다운**(Graceful Termination)을 표준 패턴으로 적용한다.

## Ⅶ. 결론

- 핵심 요약 : HPA는 메트릭 기반으로 파드 복제본 수를 자동 조정하여 무중단 가용성과 비용 최적화를 달성하는 쿠버네티스 확장의 기본 장치.
- 지표 지연, Requests 누락, 노드 고갈은 이벤트 기반 확장과 정책 강제, 노드 자동 증설이 함께 있어야 해소되므로, HPA는 단독 기능이 아니라 클러스터 자원 계층과 묶어 설계해야 한다.
