## Ⅰ. HPA (Horizontal Pod Autoscaler)의 개요

- **개념** : 쿠버네티스(Kubernetes) 클러스터에서 애플리케이션 워크로드(Deployment, ReplicaSet)의 실시간 CPU 이용률, 메모리 사용량 또는 커스텀/외부 메트릭(HTTP 처리량, 큐 대기열 등) 부하 변동에 따라 파드(Pod)의 복제본 수(Replicas)를 자동으로 수평 확장하거나 축소하는 클라우드 네이티브 오토스케일링 컨트롤러.
- **배경 및 필요성** : 마이크로서비스 환경에서 예측하기 어려운 트래픽 스파이크 발생 시 수동으로 파드 개수를 증설하는 운영 지연을 극복하고, 트래픽 감소 시 유휴 컨테이너를 신속히 회수하여 인프라 비용을 절감하기 위해 필수적으로 도입됨.
- **핵심 목적** : 사용자 급증 시 애플리케이션 무중단 가용성 보장, 리소스 목표 사용률 유지를 통한 성능 일관성 확보, 트래픽 유휴 시 클러스터 자원 회수를 통한 비용 최적화.

## Ⅱ. HPA (Horizontal Pod Autoscaler)의 핵심 아키텍처 및 동작 메커니즘

HPA는 메트릭 수집기(Metrics Server / Prometheus Adapter), 컨트롤 루프 평가 엔진, 그리고 목표 파드 수 계산 공식에 따라 15초(기본값) 주기로 동적 스케일링을 수행함.

```text
[ HPA 컨트롤 루프 및 목표 파드 수 판정 아키텍처 ]

[메트릭 수집 계층]
+---------------------------------------------------------------+
| K8s Metrics Server (리소스 메트릭: CPU / Memory)              |
| Prometheus / Datadog (커스텀 메트릭: RPS, Kafka Consumer Lag)  |
+---------------------------------------------------------------+
                                │
                                ▼ (15초 주기 컨트롤 루프 폴링)
+---------------------------------------------------------------+
| HPA Controller (HorizontalPodAutoscaler)                      |
|                                                               |
|   [목표 파드 수 계산 공식]                                    |
|   Desired = ceil[ CurrentReplicas × (CurrentMetric / Target) ]|
|                                                               |
|   - 예시: 현재 파드 2대, 현재 CPU 80%, 목표 CPU 50%           |
|     -> Desired = ceil[ 2 × (80 / 50) ] = ceil[ 3.2 ] = 4대    |
|                                                               |
|   [스케일링 정책 (Scaling Rules) 검증]                        |
|   - Scale-Up : 즉각 확장 (기본 0초 대기)                       |
|   - Scale-Down: 플래핑 방지 안정화 윈도우 (기본 300초 대기)   |
+---------------------------------------------------------------+
                                │
                                ▼ 스케일 서브리소스(Scale API) 호출
+---------------------------------------------------------------+
| Deployment / ReplicaSet (파드 복제본 수 갱신: spec.replicas)  |
|   - Worker Pod 1 ──> Worker Pod 2 ──> Worker Pod 3 ──> Pod 4  |
+---------------------------------------------------------------+
```

- **목표 파드 수 판정 공식** : `desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]`에 따라 올림 연산으로 안전한 용량 산출.
- **컨트롤 루프 주기 (Horizontal-pod-autoscaler-sync-period)** : 기본 15초마다 메트릭을 질의하고 상태를 평가하여 즉각적인 스케일링 이벤트 트리거.
- **스케일다운 안정화 윈도우 (Stabilization Window)** : 트래픽이 일시적으로 줄었다가 다시 튀는 상황에서 파드가 섣불리 종료되는 플래핑(Flapping)을 방지하기 위해 기본 5분(300초) 동안 대기.
- **KEDA (Kubernetes Event-driven Autoscaling) 연동** : 표준 리소스 메트릭 외에 카프카 랙, AWS SQS 큐 길이, Redis 스트림 등 외부 이벤트 기반 0개(Scale-to-Zero)까지 확장.

## Ⅲ. HPA (Horizontal Pod Autoscaler)의 세부 구성 요소 및 비교 분석

| 비교 항목 | HPA (수평 파드 확장) | VPA (수직 파드 확장) | CA (클러스터 노드 확장) |
|---|---|---|---|
| **확장 대상** | **파드 복제본 개수 (Replicas)**| **파드 하나의 CPU/RAM 크기** | **물리/가상 워커 노드 개수** |
| **적용 워크로드** | **무상태(Stateless) 웹/API 앱** | 상태 유지(Stateful), 단일 프로세스| 클러스터 전체 물리 자원 부족 시|
| **무중단성** | **완전 무중단 (신규 파드 투입)** | 파드 재기동 수반 (일시 중단 가능) | 완전 무중단 (신규 노드 조인) |
| **스케일링 한계** | 노드의 가용 자원 한계까지 | 단일 물리 노드의 최대 스펙 한계 | CSP 쿼터 및 클라우드 예산 한계 |
| **상호 운용성** | 동일 메트릭(CPU/RAM)으로 HPA와 VPA 동시 사용 시 충돌 위험 | **HPA(파드 증설) + CA(노드 증설) 결합 표준** |

- HPA는 마이크로서비스 확장의 기본 표준이며, 클러스터의 물리 노드가 부족할 때 노드를 추가하는 Cluster Autoscaler(또는 Karpenter)와 필수적으로 결합되어야 함.

## Ⅳ. HPA (Horizontal Pod Autoscaler)의 주요 한계점 및 해결 방안

- **CPU/메모리 지표의 지연(Lag)으로 인한 스파이크 대응 실패** :
  - **한계점** : 트래픽이 폭증한 후 CPU 사용률이 올라가고 메트릭 서버가 집계하여 파드가 뜨기까지 수 분이 걸려 콜드 스타트 장애 유발.
  - **해결 방안** : KEDA를 도입하여 애플리케이션 진입 전 메시지 큐 대기열(Kafka Lag) 기반으로 선제적 스케일아웃 실행.
- **리소스 Requests 미설정 시 HPA 동작 불능** :
  - **한계점** : 파드 스펙에 `resources.requests.cpu`가 선언되지 않은 경우 백분율(Percentage) 계산이 불가능하여 HPA 컨트롤러 비활성화.
  - **해결 방안** : 모든 배포 매니페스트에 리소스 Requests를 필수로 강제하는 OPA Gatekeeper 정책 수립.
- **노드 자원 고갈 시 파드 Pending 상태 방치** :
  - **한계점** : HPA가 파드 개수를 100대로 늘렸으나 워커 노드 메모리가 꽉 차서 신규 파드들이 스케줄링되지 못하고 대기.
  - **해결 방안** : Karpenter 초고속 노드 오토스케일러를 결합하여 파드 Pending 감지 즉시 수 초 내에 최적의 노드 자동 증설.

## Ⅴ. HPA (Horizontal Pod Autoscaler) 적용 및 발전을 위한 기술사적 제언

- **HPA behavior 스케일링 정책 미세 튜닝** : 급격한 트래픽 증가에는 초당 파드 증가율 상한을 높이고(`scaleUp.policies`), 스케일다운은 분당 10% 이내로 서서히 줄이도록 안전 정책 구성.
- **비즈니스 메트릭 기반의 다차원 HPA 정착** : CPU에만 의존하지 않고 초당 HTTP 요청 수(RPS)와 응답 레이턴시 P99 지표를 결합한 복합 스케일링 규칙 적용 권장.
- **그레이스풀 셧다운(Graceful Termination) 구현** : HPA에 의해 파드가 축소될 때 진행 중인 고객 요청이 유실되지 않도록 `preStop` 훅(sleep 10s)과 SIGTERM 신호 처리 필수 반영.
