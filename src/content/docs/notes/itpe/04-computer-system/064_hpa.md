## 연관 키워드

- HPA(Horizontal Pod Autoscaler), 쿠버네티스(Kubernetes), 파드(Pod), 복제본(Replica)
- Metrics Server, 컨트롤 루프(Control Loop), 안정화 윈도우(Stabilization Window), 플래핑(Flapping)
- KEDA(Kubernetes Event-driven Autoscaling), VPA(Vertical Pod Autoscaler), CA(Cluster Autoscaler), Karpenter
- Requests, OPA Gatekeeper, 그레이스풀 셧다운(Graceful Termination)

## Ⅰ. HPA의 개요

- 핵심 요약 : 쿠버네티스(Kubernetes)에서 측정된 부하 지표에 따라 애플리케이션 인스턴스 수를 자동 조정하는 **HPA** (Horizontal Pod Autoscaler) 컨트롤러.
- 개념 : 클러스터에서 워크로드의 CPU(Central Processing Unit) 이용률·메모리 사용량과 커스텀·외부 메트릭을 주기적으로 관찰하여 **파드** (Pod)의 **복제본** (Replica) 수를 늘리고 줄이는 수평 확장 컨트롤러.
- 배경 및 필요성 : 트래픽 급증을 사람이 감지해 수동 확장하면 대응 지연으로 장애로 번지고, 트래픽 감소 후에도 유휴 파드가 남아 비용이 새는 구조적 비용 발생. 부하 지표 기반 자동 조정 계층이 이 비용의 해법.
- 주요 목적 : 트래픽 급증 시의 무중단 가용성 확보, 목표 사용률 유지를 통한 성능 일관성, 유휴 자원 회수를 통한 비용 최적화.

## Ⅱ. HPA의 특징 및 장점

- 핵심 요약 : 목표 복제본 수 산정 공식과 주기적 컨트롤 루프, 안정화 윈도우, 이벤트 기반 확장이 결합되어 확장은 빠르게·축소는 신중하게 작동하는 구조.

1. 목표 파드 수 산정 공식 : `desiredReplicas = ceil[현재 복제본 수 × (현재 지표값 / 목표 지표값)]` → 현재 부하 비율을 복제본 수에 반영하고 올림 처리로 용량 부족 방지.
2. **컨트롤 루프** (Control Loop) : 기본 15초 주기로 메트릭을 조회·평가 → 부하 변화에 대한 반응 간격의 기준 확립.
3. **안정화 윈도우** (Stabilization Window) : 축소 권고에 기본 300초 창을 두고 창 내 최댓값을 적용 → 일시적 부하 감소에 따른 **플래핑** (Flapping, 생성·종료 반복) 방지.
4. **KEDA** (Kubernetes Event-driven Autoscaling) 연동 : 큐 길이·스트림 지연 같은 외부 이벤트를 확장 기준으로 사용 → 지표 집계 지연에 앞선 선제 확장.

## Ⅲ. HPA의 구조 (흐름)

- 핵심 요약 : 메트릭 수집 계층의 값을 컨트롤 루프가 평가하여 워크로드 리소스의 복제본 수에 반영하는 흐름.

```text
[ HPA 컨트롤 루프 ]

Metrics Server 등 메트릭 수집
      ↓ 기본 15초 주기
HPA 컨트롤러
(목표 파드 수 계산·정책 검증)
      ↓ 스케일 서브리소스 갱신
Deployment / ReplicaSet
      ↓
파드 생성 또는 종료
```

```text
[ 목표 파드 수 계산 예시 ]

현재 파드 2, 현재 CPU 80%, 목표 50%
      ↓
ceil[ 2 × (80 / 50) ] = ceil[ 3.2 ]
      ↓
목표 복제본 수 = 4
```

- 구성요소 : Metrics Server가 노드·cAdvisor의 자원 지표를 모아 API(Application Programming Interface)로 제공하고, HPA 컨트롤러가 평가 결과를 Deployment의 spec.replicas에 기록.
- 지표 기준 : CPU 이용률은 파드가 선언한 **Requests**(자원 요청량) 대비 실제 사용량의 비율로 계산되므로, Requests의 사전 정의가 HPA 동작의 전제 조건.
- 비대칭 동작 : 확장 권고는 즉시 반영되고 축소 권고는 안정화 윈도우 경과 후 반영되는 구조.

## Ⅳ. HPA와 VPA·CA의 비교

- 핵심 요약 : HPA는 파드 수를, **VPA** (Vertical Pod Autoscaler)는 파드 크기를, **CA** (Cluster Autoscaler)는 노드 수를 조정하는 상호 보완적 확장 계층.

| 비교 항목 | HPA (파드 수평 확장) | VPA (파드 수직 확장) | CA (노드 확장) |
| --- | --- | --- | --- |
| 확장 대상 | 파드 복제본 수 | 파드의 자원 요청량 | 워커 노드 수 |
| 적용 워크로드 | 무상태(Stateless) 웹·API 서비스 | 재기동 가능한 단일 인스턴스형 | 클러스터 자원 부족 시 |
| 무중단성 | 신규 파드 투입으로 무중단 | 파드 재기동 수반 가능 | 신규 노드 합류로 무중단 |
| 확장 한계 | 노드 가용 자원까지 | 단일 노드 최대 스펙까지 | 클라우드 쿼터까지 |
| 결합 시 유의점 | 같은 지표로 VPA와 병용 시 충돌 | 노드 용량과 정합 필요 | 파드 확장 없이는 자원 유휴 |

- 선택 기준 : 무상태 서비스의 부하 대응은 HPA, 자원 요청량의 자동 튜닝은 VPA, 노드 용량 보충은 CA나 Karpenter를 결합하는 판단 기준.

## Ⅴ. HPA의 한계와 방안

- 핵심 요약 : 지표 집계의 시차, 자원 요청량 누락, 노드 용량 고갈을 이벤트 기반 확장·정책 강제·노드 자동 증설로 대응하는 원칙.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 지표 집계의 시차 | 급증 후 집계·기동까지의 지연으로 초기 요청 처리 밀림 | KEDA의 큐 길이 같은 선행 지표 기반 선제 확장 | 확장 소요 시간, 초기 요청 실패율 |
| Requests 미설정 | `resources.requests` 부재 시 사용률 비율 계산 불가로 HPA 정지 | OPA Gatekeeper(Open Policy Agent 기반 정책 엔진)로 requests 필수 강제 | 미설정 워크로드 수 |
| 노드 용량 고갈 | 복제본은 늘었으나 신규 파드가 Pending 상태로 체류 | Karpenter·CA가 Pending 감지 시 노드 자동 증설 | Pending 체류 시간 |

## Ⅵ. HPA에 대한 기술사적 제언

- 핵심 요약 : 확장 정책의 워크로드별 튜닝, 다차원 지표 판정, 무손실 종료 패턴의 표준화로 HPA 운영 성숙도를 높이는 방향.

1. 플랫폼 운영 조직은 behavior 필드에서 확장 정책의 상한과 축소 안정화 윈도우를 워크로드별로 구성하여, 급증 대응 속도와 일시 감소 시 파드 유지를 동시에 확보한다.
2. 서비스 개발 조직은 CPU 이용률 외에 초당 요청 수(RPS, Requests Per Second)·P99 지연 같은 서비스 지표를 결합한 다차원 판정 체계를 구축한다.
3. 서비스 개발 조직은 preStop 훅과 SIGTERM 처리로 진행 중 요청을 마친 뒤 종료하는 **그레이스풀 셧다운** (Graceful Termination)을 배포 표준 패턴으로 채택한다.

## Ⅶ. 결론

- 핵심 요약 : HPA는 메트릭 기반으로 파드 복제본 수를 자동 조정하여 가용성과 비용 효율을 동시에 추구하는 쿠버네티스 확장의 기본 장치.
- 지표·정책·노드 용량이 한 세트로 설계될 때 비로소 의도한 대로 작동하는 여러 계층의 협업형 자동화 장치.
