## 연관 키워드

- 도커 스웜(Docker Swarm), 스웜 모드(Swarm Mode), 컨테이너 오케스트레이션(Container Orchestration)
- 서비스(Service), 태스크(Task), 매니저 노드(Manager Node), 워커 노드(Worker Node), Raft 합의 알고리즘(Raft Consensus)
- 라우팅 메시(Routing Mesh), 오버레이 네트워크(Overlay Network), IPVS(IP Virtual Server), 쿠버네티스(Kubernetes)

## Ⅰ. 도커 스웜의 개요

- 핵심 요약 : 도커 엔진에 내장되어 여러 호스트를 하나의 클러스터로 묶는 경량 컨테이너 오케스트레이션.
- 개념 : 도커 엔진에 내장된 클러스터 기능인 **스웜 모드** (Swarm Mode)를 활성화해 여러 도커 호스트를 하나의 클러스터로 묶는 경량 **컨테이너 오케스트레이션** (Container Orchestration) 도구가 **도커 스웜** (Docker Swarm)임.
- 배경 및 필요성 : 단일 호스트 도커는 호스트 장애 시 서비스가 중단되고 자원 증설에 한계가 있음. 별도 관리 플랫폼 설치 없이 고가용성 클러스터를 구성할 수단이 필요함.
- 주요 목적 : 선언형 서비스 배포와 자동 복구, 매니저 이중화에 따른 제어 계층 고가용성, 어느 노드로 접속해도 서비스에 닿는 부하 분산.

## Ⅱ. 도커 스웜의 특징 및 장점

- 핵심 요약 : 서비스·태스크 선언형 모델, 내장 Raft 합의, 라우팅 메시가 클러스터 구축 부담을 낮추면서 가용성을 높이는 구조.

1. 서비스·태스크 모델 : **서비스** (Service, 클러스터에서 유지할 컨테이너 집합의 이상 상태 선언)를 정의하면 **태스크** (Task, 스케줄링 단위로 컨테이너에 1:1 대응)가 배치됨 → 상태 불일치 탐지 시 자동 재배치로 장애 복구.
2. **Raft 합의 알고리즘** (과반수 매니저의 동의로 클러스터 상태를 일치시키는 분산 합의 방식) 내장 : 클러스터 상태를 관리하는 **매니저 노드** (Manager Node, 합의·스케줄링 담당 노드)가 상태를 서로 복제하고 리더 장애 시 과반수 투표로 새 리더 선출 → 외부 저장소 없는 제어 계층 이중화.
3. **라우팅 메시** (Routing Mesh, 모든 노드가 서비스 게시 포트를 열어 요청을 실행 노드로 전달하는 구조) : 노드의 **IPVS** (IP Virtual Server, 커널 계층 부하 분산 기능)가 임의 노드로 들어온 요청을 태스크 실행 노드로 전달 → 접속 노드와 무관한 연속 서비스.

## Ⅲ. 도커 스웜의 구조 (흐름)

- 핵심 요약 : 매니저 노드가 합의와 스케줄링을 담당하고 워커 노드가 태스크를 실행하며, 외부 진입은 라우팅 메시가 처리하는 구조.
- 매니저와 워커 사이 제어 통신은 TLS(Transport Layer Security) 상호 인증으로 보호되고, 컨테이너 간 통신은 VXLAN(Virtual eXtensible LAN) 기반 **오버레이 네트워크** (Overlay Network, 물리 네트워크 위에 구성한 가상 네트워크)를 사용함.

```text
[ 서비스-태스크 배치 흐름 ]

서비스 정의 (이미지·복제 수 선언)
      ↓ desired state 선언
매니저 노드 (Raft 합의·스케줄링)
      ↓ TLS 제어 채널
워커 노드 (태스크를 컨테이너로 구동)
      ↓
상태 불일치 탐지 시 태스크 재조정
```

```text
[ 인그레스 라우팅 메시 흐름 ]

외부 요청 (임의 노드의 게시 포트)
      ↓ IPVS 부하 분산
태스크가 실행 중인 노드로 전달
      ↓
서비스 컨테이너가 응답
```

## Ⅳ. 도커 스웜과 쿠버네티스의 비교

- 핵심 요약 : 설치와 운영의 단순성은 스웜이, 자동화 기능과 생태계의 폭은 쿠버네티스가 우위에 있음.
- 비교 대상인 **쿠버네티스** (Kubernetes)는 CNCF(Cloud Native Computing Foundation)가 주관하는 사실상 표준 컨테이너 오케스트레이션 플랫폼임.

| 비교 축 | 도커 스웜 | 쿠버네티스 |
| :--- | :--- | :--- |
| 설치·구성 | `docker swarm init` 한 번으로 클러스터화 | 설치 절차가 많거나 관리형 서비스 이용 |
| 학습 곡선 | 기존 도커·compose 문법과 유사해 낮음 | 오브젝트 개념이 많아 높음 |
| 상태 저장소 | 매니저 내장 Raft 저장소 | 별도 분산 키-값 저장소 운영 필요 |
| 오토스케일링 | 기본 제공이 제한적 | 리소스 기반 자동 확장 내장 |
| 생태계 | 유지보수 중심 운영 | 확장 생태계가 가장 넓음 |
| 적합 규모 | 소규모·단일 팀 워크로드 | 다수 팀·대규모 마이크로서비스 |

- 선택 기준 : 팀 규모와 운영 역량이 제한적이고 워크로드가 단순하면 도커 스웜, 다수 팀 공용·복잡한 스케줄링 요구는 쿠버네티스를 기준으로 삼음.

## Ⅴ. 도커 스웜의 한계와 방안

- 핵심 요약 : 스토리지, 권한 세분화, 고급 트래픽 제어의 공백을 외부 구성요소 결합으로 일대일 보완함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 상태 저장 워크로드 운영 곤란 | 동적 스토리지 프로비저닝 기능이 없어 데이터 보존 배치가 어려움 | 공유 스토리지 볼륨 사전 마운트, 데이터베이스의 관리형 서비스 분리 | 볼륨 마운트 오류 건수 |
| 클러스터 내 권한 세분화 제한 | 팀별 격리와 사용자별 권한 관리가 단순해 전사 공용 운영이 곤란 | 외부 관리 콘솔 연계로 팀별 접근 통제 보완 | 권한 정책 위반 건수 |
| 가중치 기반 트래픽 전환 부재 | 롤링 업데이트 외에 **카나리 배포** (Canary, 일부 트래픽에 신버전을 먼저 노출하는 배포)·블루-그린 배포 기능이 없음 | 클러스터 앞단 프록시에서 레이블 기반 가중치 라우팅 구성 | 배포 장애 복구 시간 |

## Ⅵ. 도커 스웜에 대한 기술사적 제언

- 핵심 요약 : 조직 역량에 맞춘 도구 선택 기준의 명문화와 정의 자산의 이식 경로 확보 방향.
- 인프라 운영 조직은 서비스 규모와 운영 인력 역량을 도구 선택 기준으로 문서화해 운영 복잡도가 조직 능력을 넘지 않게 관리해야 함.
- 개발 조직은 compose 파일을 표준 형식으로 관리해 오케스트레이터 교체 시에도 서비스 정의 자산이 재사용되는 이식 경로를 확보해야 함.
- 기획·총괄 부서는 클러스터 도구의 유지보수 상태를 기술 로드맵 점검 항목에 넣어 표준 변화에 대응하는 전환 판단 체계를 두어야 함.

## Ⅶ. 결론

- 핵심 요약 : 도커 스웜은 서비스·태스크 모델과 라우팅 메시로 경량 클러스터를 제공하는 내장형 오케스트레이션.
- 설치 부담과 가용성 요구의 균형점에서 채택 가치가 평가되는 기술.
