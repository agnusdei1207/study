## 연관 키워드

MongoDB, BSON, 복제셋, 샤딩, 임베딩, 참조, WiredTiger, NoSQL, mongos, Config Server

## Ⅰ. MongoDB의 개요

- 핵심 요약 : 문서 지향 데이터 모델을 쓰고 수평 확장과 고가용성을 기능으로 갖춘 데이터베이스 제품.
- 개념 : **MongoDB**는 **BSON** (Binary JSON) 형식의 문서를 저장하는 **NoSQL** (Not Only SQL) 데이터베이스의 한 종류임.
- 배경 및 필요성 : 관계형 데이터베이스 관리 시스템(RDBMS, Relational Database Management System)은 정해진 스키마에 맞춰야 해서, 구조가 자주 바뀌는 서비스와 대규모 트래픽을 감당하기 어려운 제약이 있음. 이를 줄이려면 필드를 유연하게 바꾸고 수평으로 늘릴 수 있는 저장소가 필요함.
- 주요 목적 : 동적 스키마 환경에서 대규모 데이터를 유연하게 저장하고 조회.
- 특징 : 문서 지향 모델과 내장된 확장·가용성 기능.

## Ⅱ. MongoDB의 특징 및 장점

- 핵심 요약 : 문서 지향 모델, 수평 확장, 고가용성이 맞물려 변화가 잦은 웹과 앱 데이터에 적합한 구조.

1. 동적 스키마 : 컬렉션 정의를 바꾸지 않고 필드를 추가할 수 있음 → 서비스 변경에 따른 스키마 마이그레이션 부담 감소.
2. **샤딩** (Sharding) : 샤드 키 기준으로 데이터를 여러 샤드에 나눠 저장 → 데이터량과 쓰기 부하의 수평 확장.
3. **복제셋** (Replica Set) : Primary 한 대와 Secondary 여러 대로 구성하고 장애 시 선출로 Primary를 전환 → 고가용성 확보.
4. **임베딩** (Embedding)과 **참조** (Referencing) : 관련 데이터를 한 문서 안에 넣거나 별도 문서로 연결하는 두 방식 → 원자적 갱신과 조회 효율 사이에서 선택 가능.
5. **집계 파이프라인** (Aggregation Pipeline) : 여러 단계 연산을 문서 흐름으로 조합 → 서버 쪽에서 집계해 응답 데이터 축소.

## Ⅲ. 복제셋과 샤딩 흐름

- 핵심 요약 : Replica Set은 P-S-S 구성으로 가용성을 맡고, Sharded Cluster는 mongos 라우팅으로 확장을 맡는 두 흐름.
- 구성 요소 : **mongos** (쿼리 라우터), **Config Server** (샤드 메타데이터 저장소), **Shard** (실제 데이터를 나눠 저장하는 단위이며 각 샤드는 복제셋으로 구성).

```text
[ 복제셋 P-S-S 구성 ]

Primary (쓰기 처리)
      ↓ 변경 내역 복제
Secondary 1 / Secondary 2
      ↓ Primary 장애 시
선출로 Secondary 중 하나를 승격
```

```text
[ 샤딩 클러스터 요청 흐름 ]

애플리케이션
      ↓
mongos (쿼리 라우터)
      ↓ 샤드 키 확인
Shard A          Shard B
(복제셋)         (복제셋)
```

## Ⅳ. 임베딩과 참조 비교

- 핵심 요약 : 조회 성능, 원자성, 문서 크기가 서로 맞바꾸는 관계이므로 관계의 성격에 따라 방식을 고름.

| 비교 축 | 임베딩 (Embedded) | 참조 (Referenced) |
| --- | --- | --- |
| 데이터 구조 | 부모 문서 안에 하위 배열로 포함 | 별도 컬렉션에 두고 _id로 연결 |
| 조회 성능 | 한 번의 읽기로 끝나 빠름 | $lookup 또는 여러 번의 쿼리 필요 |
| 원자성 | 단일 문서 단위로 원자적 갱신 | 여러 문서에 걸치면 다중 문서 트랜잭션 필요 |
| 문서 크기 | 16MB BSON 한계에 닿을 위험 | 문서 크기 제약에서 상대적으로 자유로움 |
| 적합 관계 | 1:1, 상한이 있는 1:N | 1:다수, M:N |

- 선택 기준 : 함께 읽히고 함께 바뀌는 데이터는 임베딩, 개수가 무한히 늘거나 여러 곳에서 공유되는 데이터는 참조로 나눔.

## Ⅴ. 한계와 방안

- 핵심 요약 : 문서 크기 상한, 샤드 키 핫스팟, 쓰기 정체를 모델링 패턴, 샤드 키 설계, 캐시 튜닝으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 16MB 한계 초과 | 제한 없이 늘어나는 하위 배열을 임베딩해 문서 크기 상한 초과 | 서브셋 패턴이나 버킷 패턴으로 나누고, 증가가 큰 관계는 참조로 분리 | 문서 크기 |
| 샤드 키 핫스팟 | 단조 증가하는 키로 최신 샤드에만 쓰기가 몰림 | 복합 샤드 키 또는 해시 샤드 키 사용, 점보 청크 모니터링 | 샤드별 부하 |
| 쓰기 정체 | **WiredTiger** 저장 엔진의 더티 캐시 비율이 임계치(기본 약 20%)를 넘으면 쓰기가 지연됨 | 캐시 크기 최적화, 쓰기 관심(Write Concern) 설정 분리, NVMe 저장소 사용 | 쓰기 지연 시간 |

## Ⅵ. 기술사적 제언

- 핵심 요약 : 저장 엔진 캐시, 샤드 키, 모델링 패턴을 초기에 설계해야 운영이 안정됨.

1. 캐시 고정 : WiredTiger 캐시 크기를 명시적으로 고정해 두면 메모리 경합에 따른 메모리 부족(OOM, Out of Memory)과 쓰기 정체를 함께 줄일 수 있다.
2. 샤드 키 설계 : 카디널리티가 높고 값이 고르게 퍼지는 키를 고르며, 단조 증가하는 값을 키의 앞쪽에 두지 않는다.
3. 모델링 원칙 : 관계의 증가율과 조회 패턴을 먼저 파악해 임베딩과 참조를 고르고, 커지는 배열은 서브셋이나 버킷 패턴으로 나눈다.

## Ⅶ. 결론

- 핵심 요약 : MongoDB는 문서 지향 모델과 수평 확장, 고가용성을 갖춘 NoSQL 데이터베이스로, 샤드 키와 모델링 설계가 운영 품질을 좌우함.
- 시사점 : 스키마 유연성은 데이터 설계 책임을 애플리케이션 쪽으로 넘기는 것이므로, 데이터 증가율을 전제로 한 모델링과 샤드 키 설계를 도입 초기에 검토해야 함.
