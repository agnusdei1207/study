## 한 줄 본질
- 데이터 레이크에 일단 모아두고 보자는 안이한 수집 정책 → 데이터 사전·카탈로그·품질 검증이 결여되어 쓰레기 데이터만 누적 → 가치 있는 데이터를 찾을 수 없고 비용만 소모하는 폐기물 처리장으로 전락

## 핵심 그림
```text
[데이터 레이크가 데이터 늪으로 변질되는 구조와 탈출 경로]

 [데이터 레이크] ──(메타데이터 부재/방치)──> [데이터 늪 (Data Swamp)]
 - 정돈된 메타데이터                         - 어떤 데이터인지 모름
 - 검색 및 활용 용이                        - 품질 오류 및 중복 파일
 - 접근 제어 및 계보 관리                   - 스토리지 비용만 낭비
        ▲                                          │
        └─────── [정화 파이프라인 가동] ────────────┘
                 - 데이터 카탈로그 자동 등록
                 - 데이터 프로파일링 & 클렌징
                 - Raw -> Curated Zone 엄격 통제
```

## 핵심 용어
- 데이터 카탈로그(Data Catalog): 데이터 자산의 위치, 스키마, 소유자, 태그, 계보 정보를 색인화하여 검색 가능하게 제공하는 중앙 레지스트리
- 다크 데이터(Dark Data): 수집·저장되었으나 비즈니스 분석이나 의사결정에 전혀 사용되지 않고 방치된 비정형 데이터

## 핵심 통찰
- 데이터 늪의 원인은 기술이 아니라 '조직 거버넌스'의 부재임 → 스토리지(S3)가 너무 싸서 버리지 않고 다 쌓아둔 결과, 탐색 비용이 저장 비용을 초과하게 됨
- 데이터는 가공 단계별로 공간(Zone)을 엄격히 격리해야 함 → 검증되지 않은 원시 데이터(Raw)와 정제된 비즈니스 데이터(Curated)를 섞어두면 전체 저장소가 오염
- 메타데이터 수집을 수동 입력에 맡기면 늪화를 막을 수 없음 → 데이터 파이프라인(Airflow, Spark) 실행 시 스키마와 메타데이터가 카탈로그로 자동 푸시되어야 함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| Zone 아키텍처 | 데이터 레이크 정화 기법 | Raw(원시), Cleansed(정제), Curated(분석) 단계별로 접근 권한과 품질 기준을 분리 |
| 데이터 수명주기 정책(ILM) | 스토리지 비용 최적화 | 90일 이상 미조회 원시 데이터는 Glacier/Archive 계층으로 자동 전환하거나 폐기 |

## 이웃 토픽과 구분
- 데이터 레이크 vs 데이터 늪: 레이크 = 메타데이터와 카탈로그가 있어 분석가가 5분 내에 데이터를 찾아 쿼리할 수 있는 상태 / 늪 = 수십 PB가 쌓여 있어도 데이터의 의미와 신뢰성을 보장할 수 없어 아무도 쓰지 못하는 상태

## 문제·원인·대책
- 적용 상황: 클라우드 S3 기반 전사 데이터 레이크 운영 3년 차 기업
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 분석가가 필요한 테이블을 찾지 못해 동일 원천 데이터를 각자 재수집 | 데이터 카탈로그 부재 및 부서별 데이터 사일로 심화 | 전사 데이터 카탈로그(DataHub) 구축 및 검색 엔진 연동 | 중복 수집 제거 및 검색 시간 90% 단축 |
| 레이크 내 개인정보(주민번호, 카드번호) 비인가 파일 대량 방치 | 적재 시 개인정보 필터링 및 접근 제어 정책 미비 | 자동 민감정보 스캐닝 도구 도입 및 비식별화 파이프라인 필수화 | 개인정보 유출 리스크 차단 및 법규 준수 |
