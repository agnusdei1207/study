## 연관 키워드

- B-Tree와 B+Tree

## Ⅰ. B-Tree와 B+Tree의 개요

- 핵심 요약 : 디스크 기반 대용량 데이터의 효율적 탐색·삽입·삭제를 위한 자가 균형 다중 경로 트리 자료구조.
- 개념 : 이진 트리의 높이를 낮추기 위해 노드당 다수의 키(자식 포인터)를 허용하는 다중 경로 트리(Multiway Tree)로, 모든 리프 노드가 같은 깊이에 위치하는 높이 균형(Height-Balanced) 특성을 유지하여 디스크 I/O 횟수를 최소화하는 인덱스 자료구조. B+Tree는 B-Tree의 변형으로 내부 노드는 키만, 리프 노드에 데이터 레코드(또는 포인터)를 저장하고 리프 노드 간 연결 리스트로 순차 접근 최적화.
- 배경 및 필요성 : BST(Binary Search Tree) 등 메모리 기반 트리는 디스크 블록 단위 I/O 특성 미고려로 높이가 깊어져 I/O 비용 폭증. 데이터베이스 인덱스, 파일 시스템에서 블록 단위 읽기/쓰기 최적화 필요.
- 주요 목적 : 로그 시간 O(log_m N) 탐색 보장, 디스크 블록 단위 노드 배치로 I/O 최소화, 순차·범위 질의 고속 지원.

## Ⅱ. B-Tree와 B+Tree의 특징

- 핵심 요약 : 차수(Order) 기반 노드 용량, 높이 균형 유지, B+Tree의 리프 연결 리스트가 결합된 디스크 친화적 구조.

1. 차수(Order, m) : 내부 노드 최대 m개 자식, 최소 ⌈m/2⌉개 자식(루트 제외). 키 개수는 자식 수 - 1.
2. 높이 균형 : 모든 리프 노드 동일 깊이, 트리 높이 h = O(log_m N).
3. B-Tree : 내부 노드와 리프 노드 모두 키와 데이터(또는 포인터) 저장.
4. B+Tree : 내부 노드는 키만(라우팅용), 리프 노드에 모든 데이터 저장, 리프 노드 간 양방향 연결 리스트로 순차 스캔 최적화.
5. 노드 분할/병합 : 삽입 시 오버플로(Overflow) → 분할(Split), 삭제 시 언더플로(Underflow) → 병합(Merge) 또는 재분배(Redistribution).

## Ⅲ. B-Tree와 B+Tree의 구조 (흐름)

- 핵심 요약 : B-Tree와 B+Tree의 노드 구조 비교와 삽입·삭제 시 분할/병합 메커니즘.
- B-Tree 노드 구조 vs B+Tree 노드 구조.

```text
[ B-Tree 노드 (차수 m=3 예시) ]
내부 노드: [ 키1 | 데이터1 | 키2 | 데이터2 ]  → 자식 포인터 3개
리프 노드: [ 키1 | 데이터1 | 키2 | 데이터2 ]  → 자식 없음

[ B+Tree 노드 (차수 m=3 예시) ]
내부 노드: [ 키1 | 키2 ]          → 자식 포인터 3개 (라우팅 전용)
리프 노드: [ 키1 | 데이터1 | 키2 | 데이터2 | 다음 리프 포인터 ] → 데이터 저장 + 순차 연결
```

- B+Tree 삽입 분할 메커니즘.

```text
[ B+Tree 삽입 분할 (차수 3, 리프 용량 2) ]
초기:   리프1: [10 | 20]  →  리프2: [30 | 40]
                ↓
삽입 25 → 리프1 오버플로
                ↓
분할:   리프1: [10 | 20]     리프2: [25 | 30]     리프3: [40]
                ↓              ↓              ↓
부모 노드 갱신: [20 | 40] (라우팅 키, 오른쪽 자식의 첫 키)
                ↓
리프 연결: 리프1 → 리프2 → 리프3 (양방향 연결 리스트 유지)
```

## Ⅳ. B-Tree와 B+Tree의 비교

- 핵심 요약 : 데이터 저장 위치와 순차 접근 성능에서 B+Tree가 데이터베이스 인덱스 표준으로 채택.

| 비교 항목 | B-Tree | B+Tree |
|---|---|---|
| 데이터 저장 위치 | 내부 노드 + 리프 노드 모두 저장 | 리프 노드에만 저장 (내부 노드는 라우팅 키만) |
| 리프 노드 연결 | 연결 없음 | 양방향 연결 리스트 (Doubly Linked List) |
| 순차/범위 질의 | 트리 재탐색 필요, 비효율 | 리프 연결 리스트로 O(1) 순차 이동, 매우 효율 |
| 내부 노드 팬아웃 | 데이터 저장으로 팬아웃 낮음 | 키만 저장으로 팬아웃 높음 → 트리 높이 낮아짐 |
| 공간 효율성 | 키·데이터 중복 저장 가능 | 키 중복(내부+리프)이나 데이터는 리프에만 |
| 주 용도 | 파일 시스템(NTFS, HFS+), 일부 임베디드 DB | 관계형 DB 인덱스(MySQL InnoDB, PostgreSQL, Oracle), NoSQL(Cassandra SSTable) |

## Ⅴ. B-Tree와 B+Tree의 장점과 한계

- 핵심 요약 : 디스크 I/O 최소화와 범위 질의 강점, 쓰기 증폭(Write Amplification)과 메모리 오버헤드 한계.
- 장점
  1. 디스크 블록 단위 노드 배치로 탐색 I/O를 트리 높이 O(log_m N)로 최소화 (m 대략 100~1000).
  2. B+Tree 리프 연결 리스트로 범위 질의(Range Query), 전체 스캔(Full Scan), ORDER BY 최적화.
  3. 자가 균형으로 최악 탐색 시간 보장, 동시성 제어(래치 래치 크래빙, B-link Tree) 성숙.
- 한계점 1 : 쓰기 증폭(Write Amplification)과 래치 경합
  - 한계점 : 삽입·삭제 시 노드 분할/병합으로 다중 블록 갱신 발생, 고동시성 환경에서 래치(Latch) 경합으로 처리량 저하.
  - 해결 방안 : B-link Tree(링크 기반 래치 크래빙), Bw-Tree(락 프리, 델타 업데이트), LSM-Tree(Log-Structured Merge Tree) 기반 쓰기 최적화 스토리지 엔진(RocksDB, LevelDB) 채택.
- 한계점 2 : 메모리 오버헤드와 캐시 비친화성
  - 한계점 : 내부 노드가 메모리에 상주해야 효율적이나 대용량 인덱스 시 메모리 압박, 포인터 기반 노드 구조로 CPU 캐시 미스 빈발.
  - 해결 방안 : 압축된 B-Tree(Prefix Compression), 페이지 단위 캐시(Buffer Pool) 관리, 메모리 내 인덱스(ART, Adaptive Radix Tree) 하이브리드 활용.
- 한계점 3 : 고정 차수 기반 분할로 인한 공간 파편화
  - 한계점 : 순차 삽입 시 우측 노드만 분할되어 좌측 노드 공간 낭비(50% 채움), 삭제 후 병합 지연으로 파편화 누적.
  - 해결 방안 : 지연 병합(Deferred Merge), 페이지 병합 임계치 조정, 주기적 리빌드(Rebuild/Reorganize) 스케줄링.

## Ⅵ. B-Tree와 B+Tree에 대한 기술사적 제언

- 핵심 요약 : 워크로드별 인덱스 선택(OLTP vs OLAP)과 LSM-Tree 하이브리드 아키텍처 검토 필요.
- OLTP vs OLAP 워크로드별 인덱스 전략 차별화 : 고빈도 포인트 룩업(Point Lookup) 위주 OLTP는 B+Tree(클러스터형 인덱스) 표준 유지, 대용량 순차 스캔·집계 위주 OLAP는 컬럼 기반 스토리지(Parquet, ORC) + 존맵(Zone Map) + LSM-Tree 기반 쓰기 최적화 엔진 병행 검토 필요.
- 쓰기 집중 워크로드에서 LSM-Tree 하이브리드 전환 : 시계열, 로그, IoT 센서 데이터 등 쓰기 비중 90% 이상 워크로드는 B+Tree 대신 LSM-Tree(RocksDB, Cassandra, HBase) 기반 스토리지 엔진 채택으로 쓰기 증폭 최소화, 읽기 성능은 블룸 필터(Bloom Filter)와 블록 캐시로 보완.
- 클라우드 네이티브 환경에서의 인덱스 분리 아키텍처 : 컴퓨트-스토리지 분리(Disaggregated Architecture) 환경에서 인덱스를 별도 서비스(예: AWS Aurora의 분산 스토리지 레이어, TiKV의 Raft 기반 리전)로 분리하여 컴퓨트 노드 무상태화와 독립적 스케일아웃 지원 필요.

## Ⅶ. 결론

- 핵심 요약 : B+Tree는 디스크 기반 데이터베이스 인덱스의 사실상 표준이나 쓰기 집중 워크로드에서 LSM-Tree 대안 검토 필요.
- 요약 : 차수 m 기반 자가 균형 다중 경로 트리로 디스크 I/O 최소화, B+Tree는 리프 연결 리스트로 범위 질의까지 최적화한 인덱스 자료구조.
- 시사점 : 워크로드 특성(읽기/쓰기 비율, 포인트/범위 질의)에 따른 B+Tree vs LSM-Tree 선택, 클라우드 네이티브 분리 아키텍처로의 진화가 차세대 인덱스 전략의 핵심.
