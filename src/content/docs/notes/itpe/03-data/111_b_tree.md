## 연관 키워드

- B-Tree, B+Tree, 다중 경로 트리(Multiway Tree), 차수(Order), 높이 균형(Height-Balanced)
- 리프 노드, 노드 분할(Split), 노드 병합(Merge), 범위 질의(Range Query)
- 쓰기 증폭(Write Amplification), 래치 크래빙(Latch Crabbing), LSM-Tree, 블룸 필터(Bloom Filter), 존맵(Zone Map)

## Ⅰ. B-Tree와 B+Tree의 개요

- 핵심 요약 : 디스크 기반 대용량 데이터의 탐색·삽입·삭제를 효율화하기 위한 자가 균형 다중 경로 트리 자료구조.
- 개념 : 노드당 여러 개의 키를 담는 **B-Tree**(균형 다중 경로 탐색 트리)는 모든 리프 노드가 같은 깊이에 있도록 유지해 디스크 I/O 횟수를 줄이는 인덱스 자료구조다. **B+Tree**는 이를 변형한 구조로, 내부 노드에는 키만 두고 데이터는 리프 노드에 저장하며 리프끼리 연결 리스트로 묶어 순차 접근을 최적화한다.
- 배경 및 필요성 : 이진 탐색 트리(BST, Binary Search Tree)처럼 노드마다 자식이 둘뿐인 구조는 트리 높이가 깊어져 디스크 접근 횟수가 많아진다. 데이터베이스 인덱스와 파일 시스템은 디스크 블록 단위로 읽고 쓰므로, 블록 크기에 맞춰 노드를 구성하는 구조가 필요하다.
- 주요 목적 : 로그 시간 탐색 보장, 디스크 블록 단위 노드 배치로 I/O 최소화, 범위 질의의 고속 처리.

## Ⅱ. B-Tree와 B+Tree의 특징 및 장점

- 핵심 요약 : 차수 기반 노드 용량과 높이 균형이 디스크 I/O를 줄이고, B+Tree의 리프 연결 리스트가 범위 질의를 빠르게 처리하는 구조.

1. **차수**(Order, m) : 내부 노드의 자식 수 최대값을 m으로 정함 → 한 노드에 많은 키를 담아 트리 높이 축소. 루트를 제외한 내부 노드는 최소 ⌈m/2⌉개의 자식을 가짐.
2. **높이 균형** (Height-Balanced) : 모든 리프 노드가 같은 깊이에 위치 → 탐색 시간이 데이터 위치와 무관하게 일정한 범위로 유지.
3. B-Tree 저장 방식 : 내부 노드와 리프 노드 모두 키와 데이터를 저장 → 자주 쓰는 데이터를 상위 노드에서 바로 찾을 수 있음.
4. B+Tree 저장 방식 : 내부 노드는 라우팅용 키만 저장하고 **리프 노드**(Leaf Node)에 모든 데이터를 저장 → 노드당 팬아웃이 커져 트리가 낮아지고, 리프끼리 연결되어 범위 탐색이 쉬워짐.
5. **노드 분할**(Split)과 **노드 병합**(Merge) : 삽입으로 노드가 넘치면 분할하고, 삭제로 노드가 부족해지면 병합 또는 재분배 → 균형을 유지하며 구조를 자동 조정.

## Ⅲ. B-Tree와 B+Tree의 구조 (흐름)

- 핵심 요약 : 내부 노드가 라우팅을 맡고 리프 노드가 데이터를 맡는 계층 구조, 그리고 리프를 잇는 순차 경로의 이중 구조.

```text
[ B+Tree 노드 구조 (차수 m=3 예시) ]

내부 노드: [ 키1 | 키2 ]
              ↓ 자식 포인터 3개
리프 노드: [ 키1 | 데이터1 | 키2 | 데이터2 | 다음 리프 ]
```

범위 질의는 탐색 경로로 시작 리프를 찾은 뒤 리프 연결 리스트를 따라 이동하는 방식으로 처리된다.

```text
[ B+Tree 범위 질의 경로 ]

루트 → 내부 노드
   (키 비교로 시작 리프 탐색)
         ↓
리프1 ⇄ 리프2 ⇄ 리프3
   (연결 리스트로 순차 이동)
```

## Ⅳ. B-Tree와 B+Tree의 비교

- 핵심 요약 : 데이터의 저장 위치와 순차 접근 성능에서 B+Tree가 관계형 데이터베이스 인덱스의 표준으로 채택됨.

| 비교 기준 | B-Tree | B+Tree |
| --- | --- | --- |
| 데이터 저장 위치 | 내부 노드와 리프 노드 모두 | 리프 노드에만 (내부 노드는 라우팅 키) |
| 리프 노드 연결 | 연결 없음 | 양방향 연결 리스트(Doubly Linked List) |
| 순차·범위 질의 | 트리를 다시 탐색해야 해 비효율 | 리프 연결 리스트로 순차 이동, 효율적 |
| 내부 노드 팬아웃 | 데이터 저장으로 낮음 | 키만 저장해 높음, 트리 높이 낮음 |
| 주요 사용 예 | 일부 파일 시스템, 임베디드 저장소 | MySQL InnoDB, PostgreSQL, Oracle 인덱스 |

## Ⅴ. B-Tree와 B+Tree의 한계와 방안

- 핵심 요약 : 노드 갱신에 따른 쓰기 증폭과 래치 경합, 메모리·캐시 비효율, 공간 파편화의 한계를 워크로드별 기법으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **쓰기 증폭**(Write Amplification)과 래치 경합 | 삽입·삭제 때 여러 블록을 갱신하고, 고동시성에서 래치 대기가 늘어 처리량 저하 | **래치 크래빙**(Latch Crabbing) 기반 B-link Tree, 락 프리 구조인 Bw-Tree, **LSM-Tree**(Log-Structured Merge Tree) 기반 저장 엔진(RocksDB, LevelDB) 채택 | 쓰기 처리량, 블록 갱신 횟수 |
| 메모리 오버헤드와 캐시 비효율 | 대용량 인덱스의 내부 노드를 메모리에 상주시키기 어렵고, 포인터 기반 구조는 CPU 캐시 미스를 유발 | 접두어 압축(Prefix Compression), 버퍼 풀(Buffer Pool) 관리, 메모리 내 적응형 기수 트리(ART, Adaptive Radix Tree) 병행 | 버퍼 적중률 |
| 공간 파편화 | 순차 삽입 시 한쪽 노드만 갈라져 노드 채움률이 낮아지고, 삭제 후 병합이 지연되어 빈 공간이 누적 | 지연 병합, 병합 임계치 조정, 주기적 재구성(Rebuild) | 노드 평균 채움률 |

## Ⅵ. B-Tree와 B+Tree에 대한 기술사적 제언

- 핵심 요약 : 워크로드 특성에 따라 B+Tree와 LSM-Tree를 구분해 쓰고, 저장과 연산을 분리하는 클라우드 구조를 검토하는 것이 필요.

조회가 주로 특정 키를 찾는 OLTP 워크로드에서는 B+Tree 기반 인덱스를 표준으로 유지하는 것이 바람직하다. 반면 대용량 순차 스캔과 집계가 중심인 OLAP 워크로드에서는 컬럼 기반 저장 형식(Parquet, ORC)과 **존맵**(Zone Map, 블록별 최솟값과 최댓값을 기록해 읽을 블록을 건너뛰는 기법)을 함께 쓰는 방식을 검토한다. 쓰기 비중이 큰 시계열과 로그 데이터는 LSM-Tree 기반 엔진을 채택하고, 읽기 성능은 **블룸 필터**(Bloom Filter, 키의 존재 여부를 확률적으로 판정하는 자료구조)와 블록 캐시로 보완하는 것이 합리적이다. 클라우드 환경에서는 컴퓨트와 스토리지를 분리한 구조에서 인덱스를 별도 계층으로 두면 컴퓨트 노드를 상태 없이 운영하며 독립적으로 확장할 수 있다.

## Ⅶ. 결론

- 핵심 요약 : B+Tree는 디스크 기반 인덱스의 표준이지만, 쓰기 집중 워크로드에서는 LSM-Tree와의 선택적 적용이 필요.
- 시사점 : 읽기와 쓰기 비율, 포인트와 범위 질의 비중에 따라 인덱스 구조를 고르는 것이 차세대 인덱스 설계의 기본이다.
