## 큰 그림과 30초 인출



- 본질: **B-Tree는 한 노드에 여러 키와 자식 포인터를 두는 균형 탐색 트리이며, B+Tree는 레코드 탐색 키를 리프에 모으고 리프 페이지를 연결해 범위 검색을 지원하는 인덱스 구조**
- 암기: `균-다-블-분` (균형트리, 다원탐색, 디스크블록 매핑, 분할/병합) / `비플-리-연-팬` (B+Tree는 리프집중, 양방향연결, 팬아웃극대화)
- 판단축:
  - **B-Tree**: 키와 레코드 참조가 내부 노드에도 놓일 수 있는 다원 탐색 트리
  - **B+Tree**: 리프를 순차 탐색하기 쉬운 구조이나 실제 저장 방식과 리프 연결은 DBMS별 구현 차이가 있음
- 주의: 무작위 키 삽입은 페이지 분할과 캐시 효율에 영향을 줄 수 있으므로 실제 부하·엔진의 인덱스 구현을 측정한 뒤 키 전략을 결정
<details><summary>핵심 용어</summary>

- **B-Tree** : 여러 키와 자식 포인터를 한 노드에 두고 모든 리프를 같은 깊이로 유지하는 균형 탐색 트리.
- **B+Tree** : 내부 노드에는 분기 키를 두고 레코드 탐색 키를 리프에 모아 범위 순회를 지원하는 트리 구조.
- **팬아웃 (Fan-out)** : 한 내부 노드가 가리키는 자식 노드의 수.
- **RID (Record Identifier)** : 인덱스 키가 실제 레코드를 찾도록 가리키는 식별자 또는 위치 정보.
- **페이지 분할 (Page Split)** : 삽입으로 노드 용량이 넘을 때 노드를 나누고 상위 분기 정보를 갱신하는 과정.

### Ⅰ. 개요

### Ⅱ. 핵심 개념

### Ⅲ. B-Tree와 B+Tree의 정의
- **B-Tree**: 디스크 I/O를 최소화하기 위해 노드당 다수의 키를 배치하는 자가 균형 다원 탐색 트리
- **B+Tree**: 내부 노드에는 탐색용 키를 두고 데이터 항목은 리프에 두는 다원 탐색 트리. 리프 간 연결 방식과 저장 내용은 구현에 따라 다름

### Ⅳ. B-Tree vs B+Tree 핵심 구조 비교

| 비교 항목 | B-Tree | B+Tree |
|:---|:---|:---|
| **데이터 저장 위치** | 내부 노드와 리프에 탐색 키의 연관 데이터를 둘 수 있음 | 데이터 항목은 리프에 둠 |
| **팬아웃 (Fan-out)** | 노드 크기와 키·포인터 표현에 따라 결정 | 레코드 참조를 내부 노드에 두지 않는 구현에서는 더 큰 팬아웃 가능 |
| **범위 검색 (Range)** | 구현에 따라 다음 키 탐색 | 리프 페이지 연결을 활용하는 구현에서 범위 순회에 유리 |
| **키 중복성** | 중복 키 허용·표현 방식은 구현에 좌우 | 내부 분기 키가 리프 키를 복사해 나타날 수 있음 |

### Ⅴ. DBMS 적용 이유 및 실무 제언
- 높은 Fan-out은 트리 높이를 낮추고, 리프 순회는 범위 검색(`BETWEEN`, `ORDER BY`)에 유리할 수 있음
- 키 분포와 삽입 패턴을 부하 시험해 페이지 분할·쓰기 비용을 평가하고, 필요하면 순차성 키를 검토

## 2~4교시 25점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|:---|:---|
| 정의 | B-Tree는 여러 키를 한 노드에 두는 균형 탐색 트리이며, B+Tree는 레코드 탐색 키를 리프에 모아 범위 순회를 지원하는 인덱스 구조 |
| 목적 | 페이지 단위 탐색과 범위 검색을 효율화하고, 갱신 시 균형을 유지 |

### Ⅰ. 디스크 I/O 병목을 해결하는 다원 균형 트리 개요

#### 한줄 요약: 디스크 페이지에 다수의 키를 저장해 트리 높이와 디스크 탐색 비용을 줄이는 다원 균형 인덱스

- **배경**: 노드당 분기 수가 작은 탐색 트리를 디스크 페이지에 그대로 대응시키면 탐색 경로가 길어질 수 있어, 페이지에 여러 키를 담는 다원 트리를 활용
- **정의**:
  - **B-Tree**: 차수 $M$을 기준으로 모든 노드가 최대 $M-1$개의 키와 $M$개의 자식 포인터를 가지며, 모든 리프 노드가 동일한 깊이를 유지하는 자가 균형 다원 탐색 트리
  - **B+Tree**: 내부 노드는 분기 키를, 리프는 데이터 항목을 보관하는 구조. 리프 연결과 레코드 저장 방식은 구현에 따라 다름

| 층 | 역할 |
|:---|:---|
| 루트·내부 페이지 | 키 구간에 따라 다음 자식 페이지 선택 |
| 리프 페이지 | 정렬된 키와 레코드 참조 보관, 범위 순회 출발점 |

### Ⅱ. B-Tree의 구조적 규칙과 수학적 제약조건

#### 한줄 요약: 차수 $M$에 따라 루트, 내부 노드, 리프 노드가 만족해야 하는 최소·최대 키 개수 제약

- **차수 $M$인 B-Tree 노드의 불변식 (Invariants)**:
  1. 루트 노드: 최소 2개 이상의 자식 노드 보유 (자식이 있는 경우)
  2. 루트 외 내부 노드: 최소 $\lceil M/2 \rceil$개 자식, 최소 $\lceil M/2 \rceil - 1$개 키 보유. 루트 외 리프는 자식이 없고 최소 $\lceil M/2 \rceil - 1$개 키 보유
  3. 내부 노드: 최대 $M$개 자식. 모든 노드: 최대 $M - 1$개 키 보유
  4. 모든 리프 노드는 반드시 동일한 깊이(Level)에 위치하여 완벽한 균형(Self-balancing) 유지

| 노드 구성요소 | B-Tree 구조 | B+Tree 구조 |
|:---|:---|:---|
| **내부 노드 (Non-Leaf)** | 자식 포인터($P$) + 키($Key$) + **데이터 레코드 포인터($RID$)** | 자식 포인터($P$) + **인덱스 분기 키($Key$)만 저장** |
| **리프 노드 (Leaf Node)** | 자식 포인터 없음 + 키($Key$) + 연관 데이터 | 키($Key$) + 연관 데이터; 리프 연결은 구현에 따라 다름 |
| **키의 중복성** | 중복 키 허용·표현 방식은 구현에 좌우 | 내부 분기 키가 리프 키를 복사해 나타날 수 있음 |

### Ⅲ. B-Tree vs B+Tree 핵심 특성 비교

#### 한줄 요약: 내부 데이터 배치와 리프 순회 방식에 따른 탐색·범위 검색의 차이

| 비교 항목 | B-Tree | B+Tree |
|:---|:---|:---|
| **데이터 항목 저장 위치** | 내부 노드·리프에 둘 수 있음 | 리프에 두며 저장 형태는 DBMS 구현에 따름 |
| **팬아웃 (Fan-out)** | 페이지 크기·키·연관 데이터 표현에 좌우 | 내부 노드에 데이터 항목을 두지 않아 팬아웃이 커질 수 있음 |
| **트리 높이 (Depth)** | 키·포인터 크기와 페이지 크기에 좌우 | 팬아웃과 데이터 규모에 따라 달라짐 |
| **단건 검색 성능 ($=$)** | 키 위치에 따라 탐색 경로 길이가 다를 수 있음 | 일반적으로 리프까지 탐색하며 비용은 트리 높이에 좌우 |
| **범위 검색 성능 (BETWEEN)** | 트리 구조와 구현에 따라 순회 비용 발생 | 리프 순차 연결을 활용하는 구현에서 효율적 |
| **인덱스 풀스캔** | 키 배치에 따라 내부·리프 방문 | 구현의 리프 순회 구조를 활용 가능 |
| **DBMS 적용** | 용어와 구현이 제품마다 다름 | 다수 DBMS에서 내부 분기 키·리프 데이터 구조 활용 |

### Ⅳ. B+Tree 인덱스의 동적 갱신: 노드 분할(Split)과 병합(Merge)

#### 한줄 요약: 노드 포화 시 상향 분할하는 Split과, 언더플로우 시 인접 노드와 결합하는 Merge

### 1. 삽입 연산: 노드 분할 (Page Split)
1. 탐색을 통해 신규 키가 삽입될 적절한 리프 노드 위치 결정
2. 리프 노드에 빈 공간이 있으면 키를 정렬 순서에 맞게 삽입
3. 노드 용량을 초과하면 구현의 분할 정책에 따라 노드를 둘로 나눔
4. 중간 키(Median Key)를 복사하여 부모 노드로 승격 (B+Tree는 리프에도 키 유지)
5. 부모 노드도 가득 차면 루트까지 분할이 상향 전파 $\rightarrow$ 루트 분할 시 트리 높이 1 증가

### 2. 삭제 연산: 노드 재분배 및 병합 (Merge)
1. 리프 노드에서 대상 키 삭제
2. 노드의 키 개수가 최소 기준($\lceil M/2 \rceil - 1$) 미만으로 떨어지면 언더플로우 발생
3. 형제(Sibling) 노드에 여유 키가 있으면 키를 하나 빌려옴 (Borrow / Redistribution)
4. 형제 노드도 여유가 없으면 두 노드를 하나로 합침 (Merge)
5. 부모 노드의 분기 키를 제거하고, 언더플로우가 상향 전파되어 루트 노드 병합 시 높이 감소

| 갱신 상황 | 조정 |
|:---|:---|
| 삽입으로 페이지 초과 | 페이지를 나누고 분기 정보를 상위 페이지에 반영 |
| 삭제로 점유 부족 | 형제 페이지에서 재분배하거나 병합하고 상위 분기 갱신 |

### Ⅴ. DBMS 인덱스에 B+Tree 계열을 활용하는 이유

#### 한줄 요약: 내부 분기 수와 정렬된 리프 순회를 활용하는 인덱스 구조

1. **페이지 단위 탐색 비용 완화**:
   - 한 페이지에 여러 키와 자식 포인터를 저장해 이진 트리보다 높은 분기 수를 제공
   - 실제 팬아웃과 높이는 페이지 크기, 키·포인터 표현, 엔진 구현과 데이터 분포에 따라 산정
2. **범위 검색(Index Range Scan)**:
   - `BETWEEN 20 AND 50` 쿼리에서는 시작 키의 리프를 찾고 정렬된 리프 항목을 순회할 수 있음. 실제 페이지 접근은 연결 방식·캐시·저장 배치에 좌우
3. **일정한 탐색 깊이**:
   - 리프에서 데이터 항목을 찾는 경로의 길이가 트리 높이로 정해지지만, 실제 응답 시간은 캐시·입출력·동시성에 따라 변동

| 특성 | 질의에 주는 이점 |
|:---|:---|
| 내부 노드에 레코드 주소 없음 | 동일 페이지 크기에서 더 많은 분기 키를 둘 수 있음 |
| 리프 수준 순회 | 인덱스 키 순서의 범위 조회에 활용 |

### Ⅵ. 실무 운영 이슈 및 인덱스 튜닝 (Troubleshooting)

#### 한줄 요약: 무작위 UUID 삽입으로 인한 페이지 분할 폭증과 인덱스 단편화 해소

| 장애 요인 | 근본 원인 | 실무 엔지니어링 극복 방안 |
|:---|:---|:---|
| **불규칙 키 삽입에 따른 페이지 분할** | 삽입 위치와 페이지 여유 공간에 따라 분할·쓰기 증폭이 발생할 수 있음 | 인덱스 통계와 부하 시험으로 영향 확인 후 식별자·인덱스 전략 조정 |
| **인덱스 공간·접근 비효율** | 삭제·갱신·삽입 패턴에 따라 페이지 점유율과 접근 지역성이 변함 | DBMS별 통계와 실제 성능을 확인한 뒤 필요한 경우에만 해당 제품의 재구성 방법 적용 |
| **과도한 인덱스 생성** | 쓰기마다 유지 대상 인덱스가 갱신되어 저장·쓰기 비용 증가 | 질의 계획과 워크로드를 근거로 중복·저효용 인덱스 정리 |

### Ⅶ. 기술사적 제언
