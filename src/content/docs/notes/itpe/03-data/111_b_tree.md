## 30초 인출



- 본질: **B-Tree는 한 노드에 여러 키와 자식 포인터를 두는 균형 탐색 트리이며, B+Tree는 레코드 탐색 키를 리프에 모으고 리프 페이지를 연결해 범위 검색을 지원하는 인덱스 구조**
- 메커니즘: 내부 분기 키를 따라 리프까지 탐색하고, 삽입·삭제 시 분할·재분배·병합으로 균형을 유지
- 통찰: 한계: 트리 이름만으로 읽기·쓰기 성능을 단정하면 DBMS 구현과 키 분포를 놓침 → 방안: 실행계획·인덱스 통계·대표 부하로 구조를 비교
<details><summary>핵심 용어</summary>

- **B-Tree** : 여러 키와 자식 포인터를 한 노드에 두고 모든 리프를 같은 깊이로 유지하는 균형 탐색 트리.
- **B+Tree** : 내부 노드에는 분기 키를 두고 레코드 탐색 키를 리프에 모아 범위 순회를 지원하는 트리 구조.
- **팬아웃 (Fan-out)** : 한 내부 노드가 가리키는 자식 노드의 수.
- **RID (Record Identifier)** : 인덱스 키가 실제 레코드를 찾도록 가리키는 식별자 또는 위치 정보.
- **페이지 분할 (Page Split)** : 삽입으로 노드 용량이 넘을 때 노드를 나누고 상위 분기 정보를 갱신하는 과정.

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|:---|:---|
| 정의 | B-Tree는 여러 키를 한 노드에 두는 균형 탐색 트리이며, B+Tree는 레코드 탐색 키를 리프에 모아 범위 순회를 지원하는 인덱스 구조 |
| 목적 | 페이지 단위 탐색과 범위 검색을 효율화하고, 갱신 시 균형을 유지 |

## Ⅱ. 다진 분기·균형 리프의 특징

| 특징 | 탐색·갱신상 의미 |
|---|---|
| 다진 분기 | 페이지 하나에 여러 키와 자식 포인터를 두어 높이를 낮춤 |
| 같은 리프 깊이 | 키가 늘거나 줄어도 분할·재분배·병합으로 균형 유지 |
| B+Tree 리프 집중 | 내부 분기 키를 따라 리프를 찾고 정렬된 리프에서 범위를 순회 |


#### 한줄 요약: 차수 $M$에 따라 루트, 내부 노드, 리프 노드가 만족해야 하는 최소·최대 키 개수 제약

- **차수 $M$인 B-Tree 노드의 불변식 (Invariants)** :
  1. 루트 노드: 최소 2개 이상의 자식 노드 보유 (자식이 있는 경우)
  2. 루트 외 내부 노드: 최소 $\lceil M/2 \rceil$개 자식, 최소 $\lceil M/2 \rceil - 1$개 키 보유. 루트 외 리프는 자식이 없고 최소 $\lceil M/2 \rceil - 1$개 키 보유
  3. 내부 노드: 최대 $M$개 자식. 모든 노드: 최대 $M - 1$개 키 보유
  4. 모든 리프 노드는 반드시 동일한 깊이(Level)에 위치하여 완벽한 균형(Self-balancing) 유지

## Ⅲ. 리프 탐색·분할·병합 메커니즘

```text
검색 키 → 루트의 키 구간 비교 → 내부 페이지 분기 → 리프 도달
                                                 ↓
                   B+Tree 범위 검색: 시작 리프 → 다음 리프 순회
삽입: 대상 리프에 키 추가
  ├─ 공간 있음 → 종료
  └─ 포화 → 리프 분할·분기 키 상위 반영 → 부모 포화 시 상향 분할
삭제: 대상 키 제거
  ├─ 점유 기준 유지 → 종료
  └─ 부족 → 형제에서 재분배 / 병합 → 상위 분기 갱신
```

## Ⅳ. B-Tree와 B+Tree의 키 배치·범위 검색 비교

#### 한줄 요약: 내부 데이터 배치와 리프 순회 방식에 따른 탐색·범위 검색의 차이

| 비교 항목 | B-Tree | B+Tree |
|:---|:---|:---|
| **데이터 항목 저장 위치** | 내부 노드·리프에 둘 수 있음 | 리프에 두며 저장 형태는 DBMS 구현에 따름 |
| **팬아웃 (Fan-out)** | 페이지 크기·키·연관 데이터 표현에 좌우 | 내부 노드에 데이터 항목을 두지 않아 팬아웃이 커질 수 있음 |
| **트리 높이 (Depth)** | 키·포인터 크기와 페이지 크기에 좌우 | 팬아웃과 데이터 규모에 따라 달라짐 |
| **단건 검색 성능 ($=$)** | 키 위치에 따라 탐색 경로 길이가 다를 수 있음 | 일반적으로 리프까지 탐색하며 비용은 트리 높이에 좌우 |
| **범위 검색 성능 (BETWEEN)** | 트리 구조와 구현에 따라 순회 비용 발생 | 리프 순차 연결을 활용하는 구현에서 효율적 |
| **인덱스 풀스캔** | 키 배치에 따라 내부·리프 방문 | 구현의 리프 순회 구조를 활용 가능 |
| **DBMS 적용** | 용어와 구현이 제품마다 다름 | 다수 DBMS에서 내부 분기 키·리프 데이터 구조 활용 |

실제 팬아웃·높이·범위 순회 성능은 페이지 크기, 키 길이, 캐시와 DBMS 구현에 따라 달라진다.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 트리 이름만으로 읽기·쓰기 성능을 단정하면 DBMS 구현과 키 분포를 놓침 | 실행계획·인덱스 통계·대표 부하로 구조를 비교 |
| 무작위 삽입 위치와 페이지 여유에 따라 분할·쓰기 비용 증가 | 실제 삽입 분포와 페이지 통계를 측정한 뒤 키·인덱스 전략 조정 |
| 저효용 인덱스를 많이 만들어 쓰기·저장 비용 증가 | 대표 질의 계획과 갱신 비용을 비교해 중복 인덱스 정리 |

## Ⅵ. 제언

쓰기 부하가 높은 인덱스의 페이지 분할과 저장 비용을 줄이기 위해 대표 조회·갱신을 함께 재현하고 키·인덱스 전략을 선택한다.
