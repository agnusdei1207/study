## 지식 로드맵 내 현재 위치

자료처리·데이터 → SQL·응용 연계 → **정적 SQL vs 동적 SQL**

## 30초 인출

- 본질: 정적 SQL은 질의 구조를 코드 작성 시 고정하는 방식이고, 동적 SQL은 실행 중 조건에 맞춰 SQL을 구성하는 방식
- 메커니즘: 구조가 고정이면 정적 SQL 템플릿을, 구조가 바뀌면 허용 목록의 열·정렬·조건 조각만 조립하며, 두 방식 모두 값은 SQL 문장과 분리해 바인딩하고 준비·권한 확인 후 실행
- 통찰: 값은 바인드 변수로 넘기면 SQL 구문이 바뀌지 않지만 테이블·열·정렬 같은 구조 요소는 바인딩할 수 없으므로 코드의 허용 목록에서만 고르고 최소 권한 계정으로 실행

<details>
<summary>핵심 용어</summary>

- **정적 SQL(Static SQL)** : 질의 구조가 코드에 고정된 SQL
- **동적 SQL(Dynamic SQL)** : 실행 시점에 구성되는 SQL
- **바인드 변수(플레이스홀더)** : 값을 SQL 문장과 분리해 전달하는 매개변수
- **SQL 인젝션** : 입력이 SQL 구문으로 해석되어 질의가 변조되는 공격
- **허용 목록(Allow List)** : 코드에서 정한 허용 값만 선택하는 방식
- **하드 파싱** : 캐시에 없는 SQL을 새로 파싱·최적화하는 처리

</details>

## 2~4교시 25점 답안

## Ⅰ. 정적·동적 SQL의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **정적 SQL** 은 구조를 코드 작성 시 고정하고, **동적 SQL** 은 실행 중 구성하는 방식 |
| 목적 | 질의 구조의 고정성과 조건 변화 요구에 맞는 작성 방식 선택 |

## Ⅱ. 특징

| 특징 | 정적 SQL | 동적 SQL |
|---|---|---|
| 질의 구조 | 코드에 고정 | 조건에 맞춰 허용된 구조 조합 |
| 값 전달 | 바인드 변수 사용 | 바인드 변수 사용 |
| 주요 부담 | 구조 변경 시 코드 수정·배포 | 문자열 조립·권한·계획 변동 통제 |

## Ⅲ. 선택과 실행 절차

```text
업무 조건 확인
 ├ 구조 고정 → 정적 SQL 템플릿
 └ 구조 변경 → 허용 목록의 열·정렬·조건 조각만 조립
        ↓ 공통
값은 SQL 문장과 분리해 바인딩 → 준비·권한 확인 → 실행계획 선택·실행·관측
```

```text
"정렬 열" 입력 → 허용 목록과 대조 → 코드가 정한 열 이름만 삽입
"검색 값" 입력 → 플레이스홀더에 바인딩 → SQL 구문으로 해석되지 않음
```

## Ⅳ. 입력 종류별 통제

| 입력 종류 | 처리 원칙 |
|---|---|
| 값·검색어 | 준비된 문장과 바인드 변수 사용 |
| 테이블·열·정렬 방향 | 바인딩 불가, 코드의 허용 목록에서 선택 |
| 사용자 권한 | 필요한 테이블·행·열만 허용하는 최소 권한 계정 |
| 실행 결과 | 입력 변형 시험, 오류·권한 로그와 비정상 질의 감시 |

동적 SQL이라는 이유만으로 매번 하드 파싱이 발생하는 것은 아니며, 캐시와 재사용은 DBMS·드라이버·문장 텍스트·바인드 사용에 따라 다름.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 값을 SQL에 직접 붙여 구문이 바뀜 | 값은 매개변수로 바인딩 |
| 식별자·정렬 방향을 자유 입력으로 받아 비허용 객체 조회 | 허용 목록에서만 선택, 최소 권한 |
| 조건 조합 증가로 계획 성능 예측 곤란 | 대표 조합별 실행계획·응답시간 시험, 문장 수 관리 |

## Ⅵ. 제언

구조가 고정이면 정적 SQL을 쓰고, 동적 구성이 필요하면 값은 바인딩하고 구조는 허용 목록으로 제한

```text
구조 고정 → 정적 / 구조 가변 → 동적(값 바인딩 + 구조 허용 목록 + 최소 권한)
```

| 구분 | 문자열 이어 붙이기 | 제언: 바인딩 + 허용 목록 |
|---|---|---|
| 인젝션 | 취약 | 차단 |
| 계획 재사용 | 문장 다양화 | 문장 수 관리 |
