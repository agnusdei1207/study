## 연관 키워드

- 동적 SQL, 정적 SQL, 하드 파싱, 소프트 파싱, 바인드 변수, SQL Injection, MyBatis, Querydsl

## Ⅰ. 동적 SQL의 개요

- 핵심 요약 : 실행 시점에 조건에 따라 질의문의 구조를 조립해 실행하는 기법.
- 개념 : 실행 시점에 조건에 따라 SQL(Structured Query Language) 구문을 조립해 실행하는 기법(**동적 SQL**, Dynamic SQL). 구문이 미리 고정된 방식은 **정적 SQL** (Static SQL)이라 부름.
- 배경 및 필요성 : 정적 방식은 조건 조합마다 질의문이 중복되어 관리가 어려우므로, 질의문을 동적으로 생성할 필요가 생김.
- 주요 목적 : 가변 검색 조건과 다차원 필터링에 유연하게 대응하는 것.
- 특징 : 정적 방식과 대비되며, 파싱 방식과 입력 값 처리에 따라 성능과 보안 특성이 달라짐.

## Ⅱ. 동적 SQL의 특징 및 장점

- 핵심 요약 : 런타임 유연성과 가변 조건 처리가 핵심 장점인 기법.

1. 유연성 : 사용자 입력과 분기 로직에 따라 질의문을 조립 → 가변 조건에 대응.
2. 재사용성 : 하나의 템플릿으로 다중 조건을 처리 → 질의문 중복 감소.
3. **바인드 변수** (Bind Variable, 실행 시점에 값만 끼워 넣는 자리표시자) : 값과 구문을 분리 → 재사용과 주입 방지.
4. 프레임워크 지원 : **MyBatis** (SQL 매퍼 프레임워크)와 **Querydsl** (타입 안전 쿼리 작성 라이브러리)로 조건별 쿼리를 작성 → 코드 검증 용이.
5. 파싱 비용 절감 : 같은 구문을 반복 사용하면 파싱 비용이 줄어듦 → 응답 성능 향상.

## Ⅲ. 동적 SQL의 파싱 흐름

- 핵심 요약 : 라이브러리 캐시를 검색한 뒤 캐시 존재 여부에 따라 소프트 파싱과 하드 파싱으로 갈라지는 흐름.
- 라이브러리 캐시 : SGA(System Global Area, 인스턴스의 공유 메모리 영역) 안에서 파싱된 SQL과 실행 계획을 보관함.
- **소프트 파싱** (Soft Parsing, 캐시에 있는 실행 계획을 재사용하는 파싱) : CPU 사용이 적음.
- **하드 파싱** (Hard Parsing, 신규 구문에 대해 문법·권한·비용을 새로 계산하는 파싱) : CPU 사용이 급증하고 래치 경합을 유발함.

```text
[ SQL 파싱 흐름 ]

[SQL 입력]
     ↓
[라이브러리 캐시 검색]
     ↓
캐시 있음 → 소프트 파싱
  실행 계획 재사용, CPU 적음
     ↓
캐시 없음 → 하드 파싱
  문법·권한·비용 계산
```

```text
[ 정적 vs 동적 SQL ]

정적 : 컴파일 시점 확정
       소프트 파싱 유리, 입력값 바인딩 시 주입 방지
동적 : 런타임 조립
       하드 파싱 위험, 유연성 최상
```

## Ⅳ. 정적 SQL과 동적 SQL의 비교

- 핵심 요약 : 유연성과 성능·보안 사이의 트레이드오프로 이해해야 함.

| 항목 | 정적 SQL | 동적 SQL |
| --- | --- | --- |
| 구문 확정 시점 | 컴파일·빌드 시 | 런타임 |
| 파싱 비용 | 소프트 파싱 유리 | 하드 파싱 발생 가능 |
| 보안성 | 바인드 변수 사용 시 주입 방지 | 문자열 결합 시 취약 |
| 개발 유연성 | 조건이 복잡하면 질의문 중복 | 가변 조건에 최적 |

## Ⅴ. 동적 SQL의 한계와 방안

- 핵심 요약 : 하드 파싱 고갈, 주입 공격, 실행 계획 불안정을 바인드 변수, 화이트리스트, 모듈화로 대응.
- **SQL Injection** (SQL 인젝션, 사용자 입력 문자열이 질의문의 구조를 바꾸는 공격) : 문자열 결합이 있는 동적 질의에서 발생함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 하드 파싱 고갈 | 문자열 결합으로 매번 신규 구문이 생성됨 | 바인드 변수(#{param}) 사용, 파라미터 바인딩 | 하드 파싱 비율 |
| SQL Injection | 사용자 입력을 검증 없이 삽입 | 입력값 화이트리스트 검증, SAST(Static Application Security Testing, 정적 보안 분석) 점검 | 취약점 발견 건수 |
| 실행 계획 불안정 | 조건 조합 분기로 옵티마이저 판단이 흔들림 | 정적 쿼리 모듈화, 힌트 활용, Querydsl 같은 타입 안전 도구 사용 | 실행 계획 안정성 |

## Ⅵ. 동적 SQL에 대한 기술사적 제언

- 핵심 요약 : 바인드 변수와 화이트리스트, 바인드 피킹 대응을 원칙으로 삼아 안전과 성능을 함께 확보.

1. 값은 바인드 변수로만 전달하고, 테이블명이나 정렬 기준처럼 구조를 바꾸는 부분은 미리 정한 목록에서만 고르게 해야 한다. MyBatis 기준으로 값은 `#{}`, 식별자는 `${}`를 쓰되 `${}`는 화이트리스트 검증을 거친 값에만 쓴다.
2. 편향이 심한 조건은 정적 분기 쿼리로 분리해, 최초 바인드 값으로 실행 계획이 고정되는 바인드 피킹(Bind Peeking) 문제를 피하는 것이 바람직하다.
3. MyBatis나 Querydsl처럼 타입 안전성을 제공하는 도구를 도입해 동적 조건을 코드 수준에서 검증할 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : 동적 SQL은 런타임 유연성이 강점이지만, 바인드 변수와 보안 통제가 필수임.
- 시사점 : 정적과 동적의 비교, 파싱 흐름, 한계와 대응을 함께 적용해야 유연성과 안전성을 동시에 확보할 수 있음.
