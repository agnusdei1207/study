## 답안 골격
```text
[동적 SQL (Dynamic SQL)] ◀━━ 머리: Ⅶ 내 의견 (QueryDSL/MyBatis 바인드 변수 강제와 하드 파싱 방지형 템플릿 설계)
 ┃
 ┣━ Ⅰ 개요 ───── 애플리케이션 실행 시점(Runtime)에 사용자의 다양한 검색 조건이나 비즈니스 분기에 따라 문자열을 조합하여 완성하는 가변형 SQL
 ┣━ Ⅱ 특징 ───── 런타임 쿼리 생성 · 조건절 유연성 극대화 · 하드 파싱 부하 위험 · SQL 인젝션 취약점 노출 · 바인드 변수 필수 결합
 ┣━ Ⅲ 구조 ───── 조건 평가기 / 쿼리 빌더(MyBatis, QueryDSL) / 바인드 파라미터 매핑 / DBMS 파서 및 라이브러리 캐시
 ┣━ Ⅳ 흐름 ───── ① 사용자 입력값 수집 → ② 애플리케이션 조건절 동적 조합(WHERE 1=1) → ③ 바인드 변수 매핑 → ④ DBMS 런타임 파싱 → ⑤ 실행 및 결과 반환
 ┣━ Ⅴ 비교 ───── 정적 SQL vs 동적 SQL (컴파일 시점 검증/높은 성능·보안 vs 런타임 조립/극대화된 검색 유연성·인젝션 위험)
 ┗━ Ⅵ 실무 ───── 문자열 단순 연결로 인한 SQL Injection 침투 / 매번 다른 쿼리문으로 인한 하드 파싱 폭증 및 CPU 고갈
```

## 한 줄 본질
- 수십 가지 검색 필터 조건에 대응하기 위해 정적 SQL을 수백 개 작성해야 하는 유지보수 폭증 → 런타임에 필요한 조건절만 동적으로 조립하여 단일 쿼리 파이프라인으로 처리 → 개발 생산성 및 유연성 확보 / 하드 파싱과 SQL 인젝션 위험

## 핵심 그림
```text
[동적 SQL 조합 파이프라인 및 바인드 변수 처리 구조]

 [사용자 입력]: 카테고리='IT', 가격 50000 이하 선택 (작성자 미선택)
       │
       ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 애플리케이션 동적 쿼리 엔진 (QueryDSL / MyBatis)            │
 │   SELECT * FROM 도서 WHERE 1=1                              │
 │   <if test="category != null"> AND category = #{category}  │
 │   <if test="maxPrice != null"> AND price <= #{maxPrice}    │
 └──────────────────────────────┬──────────────────────────────┘
                                ▼
 [ 올바른 바인드 변수 동적 SQL ] : "SELECT * FROM 도서 WHERE category = ? AND price <= ?"
  - 라이브러리 캐시 공유 (소프트 파싱 달성)
  - SQL 인젝션 원천 차단

 [ 위험한 리터럴 동적 SQL ] : "SELECT * FROM 도서 WHERE category = '" + cat + "'..."
  - 매번 다른 쿼리로 인식되어 하드 파싱 폭증 (CPU 마비)
  - 악의적 SQL 인젝션 공격에 100% 무방비 노출
```

## 핵심 용어
- 하드 파싱(Hard Parsing): DBMS가 이전에 실행된 적 없는 새로운 SQL로 인식하여 문법 검사, 권한 검증, 옵티마이저 최적화, 실행 계획 생성을 처음부터 끝까지 새로 수행하는 고비용 연산
- 바인드 변수(Bind Variable): 쿼리의 문법적 구조는 고정하고 값만 런타임에 파라미터(`?` 또는 `:val`)로 넘겨, DBMS가 동일한 실행 계획을 재사용(소프트 파싱)하도록 유도하는 기술

## 핵심 통찰
- 동적 SQL의 유연성은 공짜가 아님 → 조건 조합에 따라 생성되는 쿼리 모양이 달라지면 DBMS의 라이브러리 캐시에 서로 다른 쿼리로 등록되어 메모리를 고갈시키고 하드 파싱 부하로 CPU가 폭발함
- 실무에서 동적 SQL을 안전하게 쓰는 유일한 방법은 '문자열 결합(`${}`)을 금지하고 반드시 파라미터 바인딩(`#{}`)을 강제'하는 것임
- 복잡한 다이나믹 검색 화면(필터 10개)에서는 동적 SQL을 쓰더라도, 파티션 키(예: 생성일자)만큼은 반드시 필수로 입력받도록 설계해야 전체 파티션 풀스캔 장애를 막을 수 있음

## 이웃 토픽과 구분
- 정적 SQL vs 동적 SQL: 정적 SQL = 개발 시점에 쿼리 구조가 완전히 확정되어 컴파일/빌드 시 검증 가능한 쿼리 / 동적 SQL = 프로그램 실행 중 사용자 입력에 따라 동적으로 조건문이 붙었다 떨어지는 가변 쿼리

## 문제·원인·대책
- 적용 상황: 쇼핑몰 통합 상품 검색 API의 런타임 성능 저하 및 보안 감사 지적
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 검색창에 `' OR '1'='1` 입력 시 전체 비공개 상품이 노출되는 취약점 발생 | 사용자 입력값을 동적 SQL 문자열로 직접 결합(`+`) | PreparedStatement 및 MyBatis `#{}` 바인드 변수 문법 전면 전환 | SQL Injection 취약점 100% 차단 |
| 이벤트 당일 다중 필터 검색 요청 폭증 시 DB CPU 100% 도달 및 서비스 정체 | 조건마다 다른 리터럴 SQL 생성으로 인한 하드 파싱 래치(Latch) 경합 | 바인드 변수 기반 쿼리 표준화 및 대표 검색 패턴 5종 정적 인덱스 캐싱 | CPU 점유율 30%로 안정화 및 소프트 파싱율 98% 달성 |

## 내 의견
- [원시 문자열 동적 SQL 폐지] 개발자가 자바 코드에서 `StringBuilder`로 공백과 쉼표를 이어 붙이며 동적 쿼리를 짜다가 괄호 누락이나 인젝션 구멍을 만드는 사고 빈발 → 나라면: QueryDSL이나 jOOQ 같은 타입 세이프(Type-Safe) 쿼리 빌더를 전사 표준으로 지정하여 컴파일 타임에 문법 오류를 잡고, 런타임에는 100% 바인드 파라미터로만 쿼리가 생성되도록 통제

## 찾아볼 것
- 동적 SQL 실행 시 바인드 변수 값에 따라 최적 플랜이 달라지는 문제를 해결하기 위한 오라클의 Adaptive Cursor Sharing(ACS) 동작 기제
