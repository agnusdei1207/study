```text
[키 (Key)] ◀━━ 머리: Ⅶ 내 의견 (유일성·최소성 기반 키 계층 설계와 자연키 종속성 탈피를 위한 불변 대리키 채택)
 ┃
 ┣━ Ⅰ 개요 ───── 관계형 데이터 모델에서 릴레이션 내의 개별 튜플을 고유하게 식별하거나 테이블 간의 참조 관계를 정의하기 위해 사용하는 하나 이상의 속성 집합

 ┣━ Ⅴ 비교 ───── 5대 키(슈퍼키, 후보키, 기본키, 대체키, 외래키) 특성 비교
 ┗━ Ⅵ 실무 ───── 변경 가능한 비즈니스 속성(이메일, 전화번호)을 PK로 선정하여 값 수정 시 전사 연쇄 락 및 무결성 붕괴
```

## 한 줄 본질
- 튜플들이 중복되거나 테이블 간의 관계가 연결되지 못하면 데이터 모순과 검색 불가 발생 → 유일성과 최소성을 만족하는 속성을 선별하여 튜플 식별자 및 외래 참조로 지정 → 데이터 무결성 보장 / 복합키 과다 시 인덱스 비대화

## 핵심 그림
```text
[관계형 데이터베이스 5대 키의 계층적 포함 관계 및 속성 매핑]

  ┌─────────────────────────────────────────────────────────────┐
  │ 1. 슈퍼키 (Super Key): [유일성 O, 최소성 X]                 │
  │    튜플을 고유하게 식별할 수 있는 모든 속성 집합            │

  │  │ 2. 후보키 (Candidate Key): [유일성 O, 최소성 O]       │  │
  │  │    유일성과 최소성을 모두 만족하는 최소 식별자        │  │
  │  │    예: (학번), (주민번호)                             │  │

  │  │  │  - 후보키 중 대표 선정│ │  - 탈락한 나머지 후보키│ │  │
  │  │  │  - NOT NULL & UNIQUE  │ │  - Unique 인덱스 활용 │  │  │
  │  │  │  예: (학번)           │ │  예: (주민번호)       │  │  │
  │  │  └───────────────────────┘ └───────────────────────┘  │  │
  │  └───────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────┘
   * 5. 외래키 (Foreign Key): 타 릴레이션의 기본키를 참조하는 속성 (참조 무결성)
```

## 핵심 용어
- 유일성(Uniqueness): 하나의 릴레이션 안에서 키로 지정된 속성값의 조합으로 서로 다른 튜플들을 중복 없이 유일하게 구별해낼 수 있는 성질
- 최소성(Minimality): 유일성을 만족하는 키 속성들 중에서 어느 하나의 속성이라도 제거하면 유일성이 깨져버리는, 꼭 필요한 최소한의 속성만으로 구성된 성질

## 핵심 통찰
- 기본키 선정의 4대 황금률은 '유일성, 최소성, 불변성(Immutability), 존재성(NOT NULL)'임 → 특히 실무에서 가장 많이 위반하는 것이 '불변성'인데, 이메일이나 사원번호처럼 비즈니스 상황에 따라 바뀔 수 있는 값을 PK로 쓰면 변경 시 모든 자식 테이블의 FK까지 수정해야 하는 대참사 유발
- 외래키(FK)는 반드시 부모의 '기본키'만 참조해야 하는 것은 아니며, 부모의 '후보키(UNIQUE)'이기만 하면 문법적으로 참조 가능함
- 최근 대규모 분산/MSA 환경에서는 비즈니스 의미가 담긴 복합 자연키(Natural Key)를 완전히 배제하고, 단일 정수 시퀀스나 UUID v7 같은 불변의 인조 '대리키(Surrogate Key)'를 기본키로 채택하는 것이 글로벌 표준

## 이웃 토픽과 구분
- 슈퍼키 vs 후보키: 슈퍼키 = 유일성만 만족하면 불필요한 속성이 더덕더덕 붙어있어도 인정(예: 학번+이름+전화번호) / 후보키 = 슈퍼키 중에서 군더더기를 완전히 뺀 가장 간결한 키(예: 학번)

## 문제·원인·대책
- 적용 상황: 회원 가입 및 주문 통합 시스템의 기본키 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 회원이 이메일 주소를 변경할 때 주문, 결제, 배송 테이블의 모든 외래키 갱신 락 발생 | 변경 가능한 자연키(이메일)를 PK로 설계하여 불변성 원칙 위배 | 시스템 내부용 단일 대리키(UUID v7)를 PK로 도입하고 이메일은 대체키(UNIQUE)로 격리 | PK 변경 없는 영구 불변성 확보 및 연쇄 갱신 제거 |
| 5개 복합키로 이루어진 식별 관계 테이블로 인해 인덱스 크기가 테이블 본체보다 커짐 | 최소성 원칙을 무시한 과도한 복합키 상속 | 단일 컬럼 대리키를 기본키로 대체하고 복합키는 유니크 인덱스로 분리 | 인덱스 스토리지 70% 절감 및 조인 단순화 |

## 이렇게 출제된다
- 제105회: "관계형 데이터베이스의 키(Key)의 개념과 2가지 핵심 특성(유일성, 최소성)을 설명하고, 5가지 키(슈퍼키, 후보키, 기본키, 대체키, 외래키)의 정의 및 상호 관계를 비교 기술하시오." → 요구 포인트: 키의 정의 + 유일성/최소성 개념 + 5대 키 계층 구조도 + 자연키 vs 대리키 실무 가이드

## 내 의견
- [개인정보 식별자의 기본키 사용 원천 금지] 과거 주민등록번호나 전화번호를 테이블의 기본키로 설계하여 개인정보보호법 개정 시 암호화 및 테이블 재구축에 수억 원의 비용을 치른 뼈아픈 과거 존재 → 나라면: 어떠한 경우에도 개인식별정보(PII)나 비즈니스 속성을 PK로 쓰지 못하도록 아키텍처 원칙을 못 박고, 100% 무의미한 대리키(Surrogate Key)만을 기본키로 강제하여 비즈니스 변경에 영향받지 않는 견고한 데이터 모델링 구축
