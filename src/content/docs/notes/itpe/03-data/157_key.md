## Ⅰ. 튜플의 유일성과 관계 무결성의 초석, 데이터베이스 키(Key) 개요

### 가. 키(Key)의 정의
- **키**는 관계형 데이터베이스에서 릴레이션(Relation)을 구성하는 튜플(Tuple, 행)들을 서로 고유하게 식별(Identify)하거나, 서로 다른 릴레이션 간의 참조적 연관 관계를 맺기 위해 사용되는 단일 속성 또는 속성들의 집합.

### 나. 키의 2대 기본 성립 요건
1. **유일성 (Uniqueness)** : 하나의 릴레이션 안에서 키로 지정된 속성값의 조합은 모든 튜플에 걸쳐 고유해야 함 (중복 행 불가).
2. **최소성 (Minimality)** : 유일성을 만족하는 데 꼭 필요한 최소한의 속성들로만 구성되어야 함 (속성 하나라도 제거하면 유일성 상실).

## Ⅱ. 관계형 데이터베이스의 5대 핵심 키 분류 체계

```text
[ 키의 계층적 포함 관계도 ]
   +-------------------------------------------------------+
   | 슈퍼키 (Super Key) - [유일성 만족, 최소성 미만족]       |
   |   +-----------------------------------------------+   |
   |   | 후보키 (Candidate Key) - [유일성 + 최소성 만족] |   |
   |   |   +--------------------+  +----------------+  |   |
   |   |   | 기본키 (Primary)   |  | 대체키 (Alt)   |  |   |
   |   |   +--------------------+  +----------------+  |   |
   |   +-----------------------------------------------+   |
   +-------------------------------------------------------+
     * 외래키 (Foreign Key) : 다른 릴레이션의 기본키를 참조하는 참조 무결성 키
```

### 가. 5대 키 상세 비교 매트릭스

| 키 종류 | 유일성 | 최소성 | NULL 허용 | 정의 및 핵심 특성 |
| :--- | :--- | :--- | :--- | :--- |
| **슈퍼키 (Super Key)** | **만족** | 미만족 | 허용 가능 | 튜플을 유일하게 식별할 수 있는 모든 속성 집합 (예: `주민번호 + 성명 + 전화번호`) |
| **후보키 (Candidate Key)** | **만족** | **만족** | 불허 | 유일성과 최소성을 모두 만족하여 기본키가 될 수 있는 자격을 갖춘 속성 집합 |
| **기본키 (Primary Key)** | **만족** | **만족** | **절대 불허 (NOT NULL)** | 후보키 중에서 설계자가 대표로 선택한 주식별자 (개체 무결성 보장, 인덱스 자동 생성) |
| **대체키 (Alternate Key)** | **만족** | **만족** | 불허 | 후보키 중 기본키로 선택되지 않고 남은 보조 키 (Unique Index 생성) |
| **외래키 (Foreign Key)** | 미만족 | 미만족 | **허용 (NULL 가능)** | 다른 릴레이션의 기본키(또는 대체키)를 참조하여 참조 무결성을 강제하는 키 |

## Ⅲ. 자연키(Natural Key) vs 인조키(Surrogate Key) 설계 트레이드오프

| 비교 항목 | 자연키 (Natural Key / 본질 식별자) | 인조키 (Surrogate Key / 대리 식별자) |
| :--- | :--- | :--- |
| **식별자 기원** | 비즈니스 업무 도메인에 실제 존재하는 고유 속성 (예: 주민번호, 사업자등록번호) | 시스템이 임의로 순차 채번한 인위적 일련번호 (예: `AUTO_INCREMENT`, `UUID`) |
| **저장 공간 및 조인** | 복합키(Composite)가 되기 쉬워 인덱스 크기가 커지고 조인 복잡 | 단일 정수형(BIGINT)으로 인덱스 크기 극소화 및 조인 속도 극상 |
| **비즈니스 변경 영향** | 비즈니스 규칙 변경 시(예: 주민번호 수집 금지 법제화) 전사 스키마 수정 | 업무 변경에 전혀 영향받지 않는 완벽한 독립성 보장 |
| **데이터 중복 검증** | 자연키 자체로 중복 입력 원천 차단 | 인조키만 있으면 동일 고객이 중복 생성될 수 있어 별도 Unique 제약 필수 |

## Ⅳ. 관계형 데이터베이스 키(Key) 설계의 주요 한계점 및 해결 방안

- **자연키(Natural Key) 채택에 따른 비즈니스 요건 변경 시 파급도 폭증** :
  - **한계점** : 주민등록번호, 사업자번호 등 자연키를 기본키(PK)로 사용할 경우 법령 변경이나 번호 체계 개편 시 외래키 참조 테이블 전반의 DDL 수정 및 데이터 마이그레이션 참사 발생.
  - **해결 방안** : 대리키(Surrogate Key: Auto Increment, 시퀀스, TSID)를 기본키로 채택하여 물리적 식별자와 비즈니스 속성을 철저히 분리, 자연키는 유니크 인덱스로 통제.
- **분산 환경에서 무작위 인조키(UUID v4) 사용 시 B+Tree 인덱스 단편화 및 쓰기 성능 저하** :
  - **한계점** : 분산 DB에서 고유성을 위해 완전 무작위 UUID를 기본키로 지정할 경우 인덱스 삽입 시 랜덤 I/O 및 페이지 분할(Page Split)이 폭증하여 처리량 급감.
  - **해결 방안** : 시간 순서 정렬이 가능한 순차적 UUID(UUID v7, ULID, Snowflake ID) 도입으로 B+Tree 인덱스 리프 노드 순차 적재 유도.
- **과도한 복합키(Composite Key) 설계에 따른 보조 인덱스 비대화** :
  - **한계점** : 4~5개 이상의 속성으로 구성된 복합키를 PK로 설정 시 모든 보조 인덱스(Secondary Index)가 PK를 리프 노드에 포함하므로 인덱스 크기가 기하급수적으로 팽창.
  - **해결 방안** : 복합키를 단일 대리키로 대체하고, 업무적 복합 조건은 결합 유니크 인덱스로 분리 설계하여 인덱스 스토리지 오버헤드 최소화.

## Ⅴ. 고성능 데이터 모델링을 위한 실무 제언

- **자연키 유일성 제약(Unique)과 인조키 PK의 하이브리드 조합** : 조인 성능과 유연성을 위해 모든 테이블의 PK를 단일 정수형 대리키(`id BIGINT`)로 설계하더라도, 업무적 중복 데이터가 삽입되는 것을 방지하기 위해 원래의 자연키 컬럼들에 대해 반드시 **복합 대체키(Unique Index)** 를 함께 선언해야 함.
- **분산 환경에서의 UUID v7 / TSID 채택** : 샤딩 및 분산 DBMS 환경에서 단일 시퀀스는 병목이 되므로, 무작위 UUID v4 대신 시간 순으로 정렬되어 B+Tree 인덱스 페이지 분할을 유발하지 않는 **UUID v7** 또는 **TSID(Time-Sorted Unique Identifier)** 를 기본키로 채택할 것을 제언함.
