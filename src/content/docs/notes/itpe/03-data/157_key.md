## 연관 키워드

- 키, 슈퍼키, 후보키, 기본키, 대체키, 외래키
- 유일성, 최소성, 개체 무결성, 참조 무결성
- 자연키, 인조키, 대리키(Surrogate Key), UUID v7

## Ⅰ. 관계형 데이터베이스 키의 개요

- 핵심 요약 : 키는 릴레이션의 튜플을 고유하게 식별하고 테이블 간 참조를 보증하는 속성 집합.
- 개념 : 릴레이션에서 튜플 하나를 유일하게 가리키는 속성 또는 속성 집합인 **키**(Key).
- 배경 및 필요성 : 같은 테이블 안에서 행을 구분하지 못하면 갱신과 삭제가 특정 행을 지목할 수 없고, 테이블 사이의 관계를 맺을 근거도 사라짐.
- 주요 목적 : **개체 무결성**(행마다 기본키 값이 유일하고 비어 있지 않음을 보장)과 **참조 무결성**(외래키 값이 참조 대상에 실제로 존재함을 보장)을 확보.

## Ⅱ. 관계형 데이터베이스 키의 특징 및 장점

- 핵심 요약 : 유일성과 최소성 두 조건으로 식별 기능을 정의하고, 이를 충족하는 키 유형별로 무결성 제약을 구현.

1. **유일성**(Uniqueness) : 같은 키 값을 가진 튜플이 둘 이상 존재하지 않는 성질 → 행 중복을 DBMS 수준에서 차단.
2. **최소성**(Minimality) : 식별에 꼭 필요한 속성만 남긴 성질 → 불필요한 속성 조합을 줄여 인덱스를 작게 유지.
3. **슈퍼키**(Super Key) : 유일성만 만족하는 속성 집합(최소성은 요구하지 않음) → 식별 가능한 모든 조합의 출발점.
4. **후보키**(Candidate Key) : 유일성과 최소성을 모두 만족하는 키 → 기본키로 선정될 자격을 가짐.
5. **기본키**(Primary Key) : 후보키 중 대표로 고른 키 → 개체 무결성의 기준이 되고 NULL을 허용하지 않음.
6. **대체키**(Alternate Key) : 기본키로 선택되지 않은 나머지 후보키 → UNIQUE 제약으로 중복을 막아 기본키를 보조.
7. **외래키**(Foreign Key) : 다른 릴레이션의 기본키를 참조하는 속성 → 참조 무결성을 DBMS가 강제.

## Ⅲ. 키 계층과 참조 구조

- 핵심 요약 : 슈퍼키가 최소성 조건으로 후보키까지 좁혀지고, 그중 하나가 기본키가 되며, 외래키는 다른 테이블의 기본키를 참조하는 구조.

```text
[ 키 계층 ]

슈퍼키 : 유일성만 만족
   ↓ 최소성 만족
후보키 : 유일성 + 최소성
   ↓ 대표 1개 선정
기본키 (나머지 후보키는 대체키)
```

```text
[ 외래키 참조 ]

사원 릴레이션
  외래키 : 부서코드
        ↓ 참조
부서 릴레이션
  기본키 : 부서코드
```

- **자연키**(Natural Key) : 주민등록번호처럼 업무 의미를 가진 속성 → 값이 바뀌면 참조하는 모든 테이블을 함께 고쳐야 함.
- **인조키**(Surrogate Key, 대리키) : 시스템이 부여하는 의미 없는 값(일련번호, UUID(Universally Unique Identifier) 등) → 업무 변경의 영향을 차단하고 조인을 단순하게 함.

## Ⅳ. 5대 키 비교

- 핵심 요약 : 5대 키의 차이는 유일성과 최소성 충족 여부에서 나오며, 기본키와 대체키만 두 조건을 모두 만족함.

| 키 | 유일성 | 최소성 | 정의 |
| --- | --- | --- | --- |
| 슈퍼키 | 만족 | 미만족 | 유일 식별이 가능한 모든 속성 집합 |
| 후보키 | 만족 | 만족 | 기본키 자격을 갖춘 최소 속성 집합 |
| 기본키 | 만족 | 만족 | 후보키 중 대표로 선택한 식별자 |
| 대체키 | 만족 | 만족 | 기본키로 선택되지 않은 후보키 |
| 외래키 | 미만족 | 적용 대상 아님 | 다른 릴레이션의 기본키 값을 참조 |

- 선택 기준 : 업무 의미가 안정적이고 변경 가능성이 낮은 속성은 자연키 후보로, 변경이 잦거나 분산 환경에서 채번이 필요하면 인조키를 기본키로 선택함.

## Ⅴ. 키 설계의 한계와 방안

- 핵심 요약 : 자연키 변경 파급, 무작위 UUID에 따른 인덱스 단편화, 복합키 비대화를 대리키와 시간 순 UUID, 대체키로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 자연키 변경 파급 | 업무 속성 변경 시 참조 테이블 전체 수정 | 대리키 PK와 자연키 Unique 제약 병행 | 마이그레이션 비용 |
| UUID v4의 인덱스 단편화 | 무작위 삽입으로 B-Tree 페이지 분할 증가 | 시간 순으로 정렬되는 UUID v7 채택 | 인덱스 단편화율 |
| 복합키 비대화 | 속성 4~5개 이상의 PK가 보조 인덱스 크기를 키움 | 단일 대리키와 결합 Unique 제약 | 인덱스 크기 |

## Ⅵ. 키 설계에 대한 기술사적 제언

- 핵심 요약 : 대리키를 기본키로 통일하고 자연키는 Unique 제약으로 관리하는 설계 기준을 데이터 표준으로 정착.
1. 모든 테이블의 기본키를 단일 정수형 대리키로 통일하고, 업무상 고유한 속성은 Unique 제약으로 중복을 막을 필요가 있다.
2. 분산 환경에서 키를 생성할 때는 시간 순으로 정렬되는 UUID v7을 채택해 인덱스 삽입 비용을 낮출 필요가 있다.
3. 키 설계 기준을 데이터 표준으로 문서화하고 설계 검토 단계에서 반드시 확인하는 거버넌스를 둘 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : 키 설계는 유일성과 최소성 위에 대리키와 시간 순 UUID를 더한 방식으로 정착된 상태.
- 시사점 : 5대 키의 정의, 자연키와 인조키의 선택 기준, 한계별 대응을 하나의 흐름으로 연결한 답안이 설계 근거를 명확히 보여줌.
