## 연관 키워드

- 분산 데이터베이스 투명성(Transparency), 위치 투명성, 분할 투명성, 복제 투명성, 중복 투명성, 병행 투명성, 장애 투명성
- CAP(Consistency, Availability, Partition Tolerance) 정리, PACELC 이론, NewSQL, 분산 트랜잭션, 데이터 로컬리티(Data Locality)

## Ⅰ. 분산 데이터베이스 투명성의 개요

- 핵심 요약 : 분산 환경의 복잡성을 숨겨 단일 데이터베이스처럼 보이게 하는 추상화 계층.
- 개념 : 여러 네트워크 노드에 나뉘어 저장된 데이터베이스를 쓸 때, 저장 위치·분할·복제·장애 같은 복잡성을 사용자가 인식하지 않고 단일 중앙 집중형 데이터베이스처럼 다루게 해 주는 특성인 **분산 데이터베이스 투명성**(Transparency).
- 배경 및 필요성 : 노드 분산과 복제, 장애 대응이 애플리케이션에 노출되면 개발 부담과 유지보수 비용이 함께 커진다.
- 주요 목적 : 복잡성을 애플리케이션에서 완전히 은닉해 개발 생산성과 유지보수성을 높이고, 고가용성(High Availability), 지역 자율성(Local Autonomy), 수평적 확장성(Horizontal Scalability)을 확보하며, 일관된 SQL(Structured Query Language) 인터페이스를 제공하는 것.

## Ⅱ. 분산 데이터베이스 투명성의 특징

- 핵심 요약 : 위치·분할·복제·중복·병행·장애의 6대 투명성이 계층처럼 쌓여 분산 복잡성을 단계적으로 은닉.

1. 위치 투명성 : 물리적 서버 위치 없이 논리적 이름만으로 접근 → 서버 이전 시 애플리케이션 수정 불필요.
2. 분할 투명성 : 수평·수직 분할과 분산 저장 방식을 숨김 → 단일 테이블처럼 조회 가능.
3. 복제 투명성 : 여러 복제본의 존재를 숨김 → 갱신이 모든 복제본에 자동 반영.
4. 중복 투명성 : 중복 저장 여부와 무관하게 정합성 보장 → 사본 간 불일치 노출 감소.
5. 병행 투명성 : 다수 트랜잭션의 동시 분산 실행 간섭을 숨김 → 앱 로직의 갱신 손실 방어 부담 감소.
6. 장애 투명성 : 노드나 네트워크 장애에도 서비스 지속 → 수동 페일오버 개입 없이 가용성 유지.

## Ⅲ. 분산 데이터베이스 투명성의 구조 (흐름)

- 핵심 요약 : 애플리케이션과 분산 노드 사이에 투명성 추상화 계층이 놓이는 구조와, NewSQL의 계층별 구현 방식.

```text
[ 투명성 추상화 계층 ]
사용자 / 애플리케이션
        ↓  단일 데이터베이스처럼 보임
투명성 추상화 계층
  위치 → 분할 → 복제 → 중복 → 병행 → 장애
        ↓
분산 노드 1 / 분산 노드 2 / 분산 노드 3
```

```text
[ NewSQL 계층 구조 (예시) ]
SQL 계층       : SQL 파서, 위치·분할 투명성
        ↓
분산 실행 계층 : 분산 쿼리 플래너, 분할·병행 투명성
        ↓
트랜잭션·합의  : 분산 직렬성, Raft 합의, 복제·장애 투명성
        ↓
저장 엔진      : 분산 Key-Value 저장소
```

- NewSQL의 구현 방식 : SQL 계층에서 위치와 분할을 감추고, 합의 프로토콜(Raft 등)과 직렬성 기법을 조합해 복제와 장애를 감춘다.

## Ⅳ. 6대 투명성 종류의 비교

- 핵심 요약 : 투명성 종류마다 숨기는 대상과 구현 기술이 달라, 미보장 시 애플리케이션에 미치는 영향도 다르다.

| 투명성 종류 | 은닉하는 대상 | 미보장 시 영향 | 구현 핵심 기술 |
| --- | --- | --- | --- |
| 위치 투명성 | 물리적 노드 위치 | 서버 이전·IP 변경 시 앱 코드 수정 | 분산 데이터 사전(DD/D), 글로벌 네이밍 서비스 |
| 분할 투명성 | 수평·수직 분할 방식 | 분할 조건을 알고 파티션별 쿼리 작성 | 글로벌 뷰, 분산 쿼리 옵티마이저 |
| 복제 투명성 | 복제본의 존재 | 모든 복제본에 UPDATE를 직접 전송 | 자동 복제 프로토콜(Raft, Paxos, Quorum) |
| 중복 투명성 | 사본 간 시점 차이 | 읽기 데이터 불일치 | 분산 캐시 무효화, 2단계 커밋 |
| 병행 투명성 | 동시 실행 간 충돌 | 분산 교착상태와 갱신 손실을 앱이 직접 방어 | 분산 2단계 로킹, 분산 타임스탬프 |
| 장애 투명성 | 노드·디스크·네트워크 장애 | 노드 장애 시 서비스 전체 중단 | 하트비트 감시, 쿼럼 기반 페일오버, 로그 복구 |

## Ⅴ. 분산 데이터베이스 투명성의 장점과 한계

- 핵심 요약 : 생산성과 가용성 확보가 장점이며, 지연 오버헤드, CAP 트레이드오프, 분산 교착과 조인 병목이 한계.

- 장점
  1. 애플리케이션 코드에서 위치·복제·장애 의존성 제거.
  2. 장애와 노드 변경 시 수동 개입이 줄어 유지보수성 향상.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 네트워크 왕복 지연 (RTT, Round-Trip Time) | 완전한 은닉을 위한 글로벌 라우팅과 분산 코디네이터 경유로 응답 지연 | 클라이언트 측 스마트 라우팅으로 데이터 로컬리티 우선 질의, 핫 파티션 로컬 캐싱 | 질의 지연 시간, 교차 노드 홉 수 |
| CAP 트레이드오프 | 네트워크 분할 시 강한 일관성과 무중단 가용성을 동시에 만족할 수 없음 | PACELC 관점에서 평시(지연과 일관성)와 장애 시(가용성과 일관성) 설정을 나누어 조정 | 장애 시 응답 정책 준수율 |
| 분산 교착과 조인 병목 | 다중 노드 락의 대기 그래프 관리 비용, 셔플 조인의 네트워크 포화 | 타임아웃 기반 락 해제, 브로드캐스트 조인, 연관 테이블을 같은 샤드 키로 배치(Colocation) | 교착 발생 빈도, 셔플 데이터량 |

## Ⅵ. 분산 데이터베이스 투명성에 대한 기술사적 제언

- 핵심 요약 : CAP 한계를 전제로 업무별로 투명성의 엄격도를 달리 설계하고, 분산 질의 비용을 상시 관찰.

네트워크가 끊어지는 상황에서는 가용성과 일관성 중 하나를 양보할 수밖에 없다. 그러므로 금융 핵심 원장처럼 틀린 값이 치명적인 영역은 일관성을 우선하고, 글로벌 콘텐츠 서비스처럼 잠시 오래된 값을 보여줘도 되는 영역은 가용성을 우선하여 투명성의 엄격도를 업무별로 나누는 것이 현실적이다.

분산 셔플과 네트워크 홉이 많은 쿼리는 평소에도 지연을 키우므로, 실행 계획을 주기적으로 점검하고 로컬리티를 살리는 샤드 키 설계를 유지해야 한다. 투명성은 편의를 주지만 비용을 감추기도 하므로, 감춰진 비용을 드러내 보는 관찰 체계가 함께 필요하다.

## Ⅶ. 결론

- 핵심 요약 : 투명성은 분산 복잡성을 줄이는 수단이지만 CAP 트레이드오프 아래에서 업무별로 조정해야 하는 설계 대상.
- 시사점 : 완전한 투명성보다 일관성, 가용성, 지연 시간의 균형을 설계하는 것이 기술사적 관점의 핵심.
