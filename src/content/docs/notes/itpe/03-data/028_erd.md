## 연관 키워드

- ERD(Entity-Relationship Diagram), 개체(Entity), 속성(Attribute), 관계(Relationship)
- 카디널리티(Cardinality), 선택성(Mandatory·Optional), Crow's Foot 표기법
- 식별 관계(Identifying)·비식별 관계(Non-identifying), 교차 엔티티(Associative Entity)

## Ⅰ. 개체-관계 다이어그램의 개요

- 핵심 요약 : 엔티티·속성·관계를 시각 기호로 모델링하는 개념적 데이터 모델링 표준 도구.
- 개념 : ERD(Entity-Relationship Diagram)는 피터 첸(Peter Chen)에 의해 제안된 것으로, 현실 세계의 비즈니스 업무 프로세스에 존재하는 데이터의 실체(Entity), 속성(Attribute), 관계(Relationship)를 시각적 그래픽 기호로 모델링한 다이어그램.
- 배경 및 필요성 : 업무 요구사항의 구조화와 개념적·논리적 데이터베이스 설계로의 구체화 수단 필요.
- 주요 목적 : 이해관계자 간 커뮤니케이션 도구로서 데이터 구조의 표준화된 표현.
- 표기법 발전 :
  1. 피터 첸 표기법(Chen Notation) : 사각형(개체), 타원(속성), 마름모(관계)를 선으로 연결하는 학술적 초기 표준.
  2. 정보공학 표기법(IE, Information Engineering / Crow's Foot) : 까마귀 발 모양으로 카디널리티(1:1, 1:N, M:N)와 선택성(필수·선택)을 직관적 표현하는 엔터프라이즈 실무 표준.
  3. Barker 표기법 : 오라클 CASE 도구에서 널리 활용된 소프트박스 기반 표기법.

## Ⅱ. 개체-관계 다이어그램의 특징

- 핵심 요약 : 3대 구성요소와 선택성·카디널리티 기호 체계가 핵심.

1. 엔티티(Entity) : 업무에서 영속적으로 관리하는 사람, 장소, 사물, 사건(명사형).
2. 속성(Attribute) : 엔티티의 고유한 성질·세부 항목(최소 데이터 단위).
3. 관계(Relationship) : 두 개 이상 엔티티 간 비즈니스적 연관성(동사형).
4. 외측 기호의 선택성 표현 : 세로 실선(`|`)은 Mandatory(필수), 원(`O`)은 Optional(선택).
5. 내측 기호의 카디널리티 표현 : 세로 실선(`|`)은 One(단일), 까마귀 발(`<`)은 Many(다수).
6. 개념·논리·물리 수준의 계층적 모델링 지원.

## Ⅲ. 개체-관계 다이어그램의 구조 (흐름)

- 핵심 요약 : 업무 분석부터 물리 설계 전환까지의 작성 흐름과 기호 체계.

```text
[ ERD 작성 흐름 ]
업무 분석 및 요구사항 정의
        ↓
엔티티 도출(명사) → 속성 정의 → 식별자 지정
        ↓
관계 도출(동사) → 카디널리티·선택성 표기
        ↓
정규화 검증 → 논리·물리 설계 전환
```

```text
[ Crow's Foot 관계 표기법 ]
  기호       의미                              비즈니스 규칙 예시
  --||---    1 and Mandatory (필수 1)          고객 1명은 반드시 회원 등급 1개 보유
  --|o---    1 and Optional (선택 1)           사원은 부서 0개 또는 1개 소속
  --|<---    Many and Mandatory (필수 다수)    주문은 반드시 1개 이상의 주문상세 보유
  --|o<--    Many and Optional (선택 다수)     고객은 0개 이상의 주문 보유 가능
```

- 기호 체계의 구조적 의미 : 외측 기호는 대상 인스턴스의 존재 여부(선택성), 내측 기호는 대응 인스턴스의 최대 수(카디널리티) 표현.

## Ⅳ. 식별 관계와 비식별 관계의 비교

- 핵심 요약 : 식별자 상속 위치(PK 포함 여부)에 따른 설계 차이.

```text
[ 식별 관계 vs 비식별 관계 구조 ]
(A) 식별 관계 (Identifying) : 실선 표기
    [부모: 부서] ===(실선)===> [자식: 프로젝트] (부서번호가 자식의 PK에 포함)
(B) 비식별 관계 (Non-identifying) : 점선 표기
    [부모: 부서] ---(점선)---> [자식: 사원]     (부서번호가 자식의 일반 FK 속성으로 포함)
```

| 비교 항목 | 식별 관계(Identifying Relationship) | 비식별 관계(Non-identifying Relationship) |
| :--- | :--- | :--- |
| ERD 선 표기 | 실선(Solid Line) | 점선(Dashed Line) |
| PK(Primary Key)·FK(Foreign Key) 배치 | 부모의 주식별자가 자식의 주식별자(PK) 일부로 상속 | 부모의 주식별자가 자식의 일반 속성(FK)으로 상속 |
| 존재 종속성 | 강한 의존성(부모 없이 자식 인스턴스 단독 존재 불가) | 약한 의존성(부모 NULL 허용, 자식 단독 존재 가능) |
| 설계 영향 | 자식의 PK 복합키 컬럼의 지속 증가로 조인 조건 복잡화 | 테이블 간 결합도 감소로 유연성 확보, 조인 시 외래키 인덱스 필요 |

## Ⅴ. 개체-관계 다이어그램의 장점과 한계

- 핵심 요약 : 데이터 구조 표준화의 장점과 형상 불일치·복잡도·표현 범위 한계.
- 장점
  1. 이해관계자 간 데이터 구조 커뮤니케이션 표준 확보.
  2. 식별·비식별 관계 표기 기반 존재 종속성·무결성 설계 명확화.
- 한계점 1 : 모델-실제 DB(Database) 간 형상 불일치(Drift)
  - 한계점 : 긴급 운영 패치 등의 DDL(Data Definition Language) 직접 수정 시 ERD 미현행화, 모델의 서류상 박제(Shelfware) 및 시스템 분석 불가 상태 초래.
  - 해결 방안 : DB 형상 관리 도구(Flyway, Liquibase) 도입, Git 기반 스키마 CI(Continuous Integration)/CD(Continuous Delivery) 파이프라인에서 DDL 변경 시 자동 리버스 엔지니어링 동기화.
- 한계점 2 : 대규모 시스템의 다이어그램 복잡도(Spaghetti ERD)
  - 한계점 : 수백~수천 개 엔티티의 관계선 얽힘으로 가독성 상실, 도메인 간 결합도 과대.
  - 해결 방안 : 주제영역(Subject Area)별 서브모델 분할, 개념·논리·물리 수준 계층화, DDD(Domain-Driven Design)의 Bounded Context 기반 모듈형 ERD 분리.
- 한계점 3 : 비정형·반정형 및 NoSQL(Not Only SQL) 모델링 표현 한계
  - 한계점 : 전통적 Crow's Foot 표기법의 1:1, 1:N 관계형 스키마 중심 지원, JSON(JavaScript Object Notation) 계층 구조·벡터 임베딩·그래프 관계 표현 불가.
  - 해결 방안 : 복합 데이터 타입용 확장 표기법 정의, 데이터 흐름 다이어그램(DFD, Data Flow Diagram) 및 시스템 아키텍처 다이어그램과의 상호 참조 연계.

## Ⅵ. 개체-관계 다이어그램에 대한 기술사적 제언

- 핵심 요약 : M:N 관계의 논리 모델 단계 해소, 인위적 서로게이트 키 남발 지양.
- M:N(다대다) 관계의 논리 모델 단계 해소 : 개념 모델의 M:N 관계는 물리적 RDBMS(Relational Database Management System) 테이블로 직접 구현 불가, 논리 모델링 단계에서 교차 엔티티(Associative Entity, 매핑 테이블) 추가를 통한 1:N - M:1 관계 해소.
- 인위적 서베이키(Surrogate Key) 남발 지양 : 모든 테이블의 무조건 단일 ID(Auto Increment/UUID, Universally Unique Identifier) PK 부여 시 비즈니스 식별성·데이터 무결성 검증 약화, 자연키(Natural Key)의 비즈니스 안정성 검토 후 복합 식별 관계와의 균형 유지.

## Ⅶ. 결론

- 핵심 요약 : ERD는 데이터 아키텍처 커뮤니케이션 표준이자 무결성 설계의 출발점.
- 요약 : 3대 구성요소와 카디널리티 기호 체계로 업무 규칙을 시각화하고, 형상 관리 연계로 현행화 유지.
- 시사점 : 표기법 표준화와 도메인 단위 분할이 대규모 데이터 모델 품질 확보의 핵심.
