## Ⅰ. 개념적 데이터 모델링의 표준 도구, ERD의 개요

### 가. ERD(Entity-Relationship Diagram)의 정의
- **ERD** : 피터 첸(Peter Chen)에 의해 제안된 것으로, 현실 세계의 비즈니스 업무 프로세스에 존재하는 데이터의 **실체** (Entity), **속성** (Attribute), 그리고 이들 간의 **관계** (Relationship)를 시각적인 그래픽 기호로 모델링한 다이어그램.
- 업무 요구사항을 구조화하여 개념적·논리적 데이터베이스 설계로 구체화하는 핵심 커뮤니케이션 도구.

### 나. ERD 표기법의 발전
- **피터 첸 표기법 (Chen Notation)** : 사각형(개체), 타원(속성), 마름모(관계)를 선으로 연결하는 학술적 초기 표준.
- **정보공학 표기법 (IE / Crow's Foot)** : 까마귀 발(Crow's foot) 모양으로 카디널리티(1:1, 1:N, M:N)와 선택성(필수/선택)을 직관적으로 표현하는 엔터프라이즈 실무 표준.
- **Barker 표기법** : 오라클 CASE 도구에서 널리 활용된 소프트박스 기반 표기법.

## Ⅱ. ERD 핵심 3대 구성 요소 및 Crow's Foot 표기법 분석

### 가. ERD 3대 핵심 구성 요소

```text
[ ERD 3대 요소 ]
1. 엔티티 (Entity)       : 업무에서 영속적으로 관리해야 하는 사람, 장소, 사물, 사건 (명사형)
2. 속성 (Attribute)      : 엔티티가 가지는 고유한 성질이나 세부 항목 (최소 데이터 단위)
3. 관계 (Relationship)   : 두 개 이상의 엔티티 간에 존재하는 비즈니스적 연관성 (동사형)
```

### 나. IE / Crow's Foot(까마귀 발) 카디널리티 및 선택성 기호 체계

```text
[ Crow's Foot 관계 표기법 ]
  기호       의미                  비즈니스 규칙 예시
  --||---    1 and Mandatory (필수 1) : 고객 1명은 반드시 회원 등급 1개를 가짐
  --|o---    1 and Optional (선택 1)  : 사원은 부서 0개 또는 1개에 소속
  --|<---    Many and Mandatory (필수 다수) : 주문은 반드시 1개 이상의 주문상세를 가짐
  --|o<--    Many and Optional (선택 다수)  : 고객은 0개 이상의 주문을 가질 수 있음
```

| 표기 요소 | 시각적 기호 | 기호의 구조적 의미 |
| :--- | :--- | :--- |
| **외측 기호 (선택성)** | 세로 실선(`\|`) | **Mandatory (필수)** : 관계를 맺는 대상 인스턴스가 반드시 1개 이상 존재해야 함 |
| **외측 기호 (선택성)** | 원(`O`) | **Optional (선택)** : 관계를 맺는 대상 인스턴스가 존재하지 않을 수도 있음 (0개 허용) |
| **내측 기호 (카디널리티)** | 세로 실선(`\|`) | **One (단일)** : 대응되는 인스턴스 최대 수가 1개임 |
| **내측 기호 (카디널리티)** | 까마귀 발(`<`) | **Many (다수)** : 대응되는 인스턴스 최대 수가 여러 개임 |

## Ⅲ. 식별 관계(Identifying) vs 비식별 관계(Non-identifying)의 비교

### 가. 식별자 상속 관계에 따른 설계 비교

```text
[ 식별 관계 vs 비식별 관계 구조 ]
(A) 식별 관계 (Identifying) : 실선 표기
    [부모: 부서] ===(실선)===> [자식: 프로젝트] (부서번호가 자식의 PK에 포함)
(B) 비식별 관계 (Non-identifying) : 점선 표기
    [부모: 부서] ---(점선)---> [자식: 사원]     (부서번호가 자식의 일반 FK 속성으로 포함)
```

| 비교 항목 | 식별 관계 (Identifying Relationship) | 비식별 관계 (Non-identifying Relationship) |
| :--- | :--- | :--- |
| **ERD 선 표기** | **실선 (Solid Line)** | **점선 (Dashed Line)** |
| **PK/FK 배치** | 부모의 주식별자가 자식의 **주식별자(PK)의 일부**로 상속됨 | 부모의 주식별자가 자식의 **일반 속성** (FK)으로 상속됨 |
| **존재 종속성** | 강한 의존성 (부모 없이는 자식 인스턴스 단독 존재 불가) | 약한 의존성 (부모가 없거나 NULL이어도 자식 단독 존재 가능) |
| 설계 영향 | 자식의 PK 복합키 컬럼이 계속 증가하여 조인 조건 복잡화 | 테이블 간 결합도가 낮아져 유연성 확보, 조인 시 외래키 인덱스 필요 |

## Ⅳ. ERD 설계 및 유지관리의 주요 한계점 및 해결 방안

- 비즈니스 요구사항 변경에 따른 모델-실제 DB 간 형상 불일치(Drift) :
  - 한계점 : 긴급 운영 패치 등으로 DDL이 직접 수정될 경우 ERD가 현행화되지 않아 모델이 서류상 박제(Shelfware)되고 시스템 분석 불가 상태 초래.
  - 해결 방안 : DB 형상 관리 도구(Flyway, Liquibase) 도입, Git 기반 스키마 CI/CD 파이프라인에서 DDL 변경 시 ERD를 자동 리버스 엔지니어링하여 동기화.
- 대규모 엔터프라이즈 시스템에서의 다이어그램 복잡도(Spaghetti ERD) :
  - 한계점 : 엔티티 수가 수백~수천 개에 달할 경우 관계선이 거미줄처럼 얽혀 가독성이 상실되고 도메인 간 결합도가 지나치게 높아짐.
  - 해결 방안 : 주제영역(Subject Area)별 서브모델 분할, 개념/논리/물리 수준의 계층화 및 DDD의 Bounded Context 기반 모듈형 ERD 분리.
- 비정형/반정형 데이터 및 NoSQL/빅데이터 모델링 표현의 한계 :
  - 한계점 : 전통적 Crow's Foot 표기법은 1:1, 1:N의 엄격한 관계형 스키마만 지원하여 JSON 계층 구조, 벡터 임베딩, 그래프 관계 표현 불가.
  - 해결 방안 : 복합 데이터 타입을 위한 확장 표기법 정의, 폴리그랏(Polyglot) 데이터 파이프라인을 위한 데이터 흐름 다이어그램(DFD) 및 시스템 아키텍처 다이어그램과의 상호 참조 연계.

## Ⅴ. 품질 높은 ERD 작성을 위한 실무 제언

- M:N(다대다) 관계의 논리 모델 단계 해소 : 개념 모델에서 도출된 M:N 관계는 물리적 RDBMS 테이블로 직접 구현할 수 없으므로, 논리 모델링 단계에서 반드시 교차 엔티티(Associative Entity, 매핑 테이블)를 추가하여 1:N - M:1 관계로 해소해야 함.
- 인위적 서베이키(Surrogate Key) 남발 지양 : 모든 테이블에 무조건 단일 `ID`(Auto Increment/UUID)를 PK로 부여하면 테이블 간 비즈니스 식별성과 데이터 무결성 검증이 약화되므로, 자연키(Natural Key)의 비즈니스 안정성을 검토한 후 복합 식별 관계와 적절한 균형을 유지할 것을 제언함.
