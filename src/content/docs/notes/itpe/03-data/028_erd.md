## 지식 로드맵 내 현재 위치

<div class="itpe-topic-path" aria-label="지식 경로"><span>데이터 설계</span><span>개념적·논리적 데이터 모델링</span><strong>ERD</strong></div>

## 큰 그림과 30초 인출

```text
[현실 세계 업무 요구사항]
        │ 추상화 (엔티티, 속성, 관계 도출)
        ▼
[개념적 ERD] ────── 엔티티 도출, 핵심 관계 및 주식별자 정의 (1:1, 1:N, M:N)
        │
        ▼ 구체화 (정규화, 식별/비식별 관계, M:N 해소)
[논리적 ERD] ────── 엔티티별 모든 속성, 도메인, 참조 무결성, 교차 엔티티 확정
        │
        ▼ 물리적 변환 (반정규화, 인덱스, 테이블스페이스, 파티셔닝)
[물리적 DDL]  ────── Table, Column, PK/FK 제약조건, Storage 파라미터 구현
```

- 본질: **현실 세계의 비즈니스 규칙과 업무 데이터를 개체(Entity), 속성(Attribute), 관계(Relationship)의 3대 요소로 정형화하여 시각적으로 표현한 데이터베이스 논리적 설계 청사진**
- 암기: `엔-속-관` = 엔티티 · 속성 · 관계 / 표기법: `피터 첸(개념) vs IE(까마귀발) vs 바커(오라클)`
- M:N 해소: 논리 모델의 다대다 관계는 물리적으로 구현 불가 → 교차 엔티티(Associative Entity)를 도출하여 두 개의 1:N 관계로 분해
- 주의: 식별 관계(실선) 남용 시 복합 PK 비대화로 조인 성능 저하, 비식별 관계(점선) 남용 시 부모 엔티티 조인 횟수 증가

## 예상문제

> 데이터베이스 설계 시 사용되는 개체-관계 다이어그램(ERD, Entity Relationship Diagram)의 개념 및 구성요소를 설명하고, 주요 표기법(IE vs Barker) 비교 및 논리 모델에서 M:N 관계의 해소 방안을 기술하시오. (25점)

## Ⅰ. 비즈니스 규칙을 시각화하는 데이터 모델링의 표준 언어, ERD 개요

- 정의: **ERD(Entity Relationship Diagram)**는 피터 첸(Peter Chen)에 의해 제안된 개념 모델링 도구로, 업무 도메인 내 데이터의 실체(Entity), 성질(Attribute), 상호작용(Relationship)을 표준화된 기호로 도식화한 다이어그램
- 목적: 현업 비즈니스 분석가, 데이터 아키텍트(DA), 개발자 간에 데이터 구조와 업무 제약조건을 오차 없이 소통할 수 있는 단일 진실 공급원(SSOT) 제공
- 필요성: 텍스트 형태의 요구사항 명세서만으로는 복잡한 비즈니스 엔티티 간의 참조 무결성, 카디널리티, 부모-자식 의존성을 명확히 파악할 수 없어 데이터 중복과 불일치가 발생함

#### 한줄 요약

- ERD는 비즈니스 도메인의 데이터 실체와 불변 규칙을 시각적 기호 체계로 정의하는 데이터베이스 설계의 근본 설계도임

## Ⅱ. ERD의 3대 핵심 구성요소와 무결성 속성

| 구성요소 | 정의 및 의미 | 논리 모델 요소 | 물리 DB 변환 |
|---|---|---|---|
| **개체 (Entity)** | 업무상 지속적으로 관리해야 하는 유의미한 정보 집합 (인스턴스의 집합) | 엔티티 (예: 고객, 주문, 계좌) | 테이블 (Table) |
| **속성 (Attribute)** | 엔티티가 가질 수 있는 최소 단위의 성질 또는 데이터 항목 | 속성, 도메인, 식별자(UID) | 컬럼 (Column), 데이터 타입 |
| **관계 (Relationship)**| 두 개 이상의 엔티티 간에 맺어지는 업무적 연관성 및 상호작용 | 카디널리티(1:1, 1:N, M:N), 참여도 | 외래키 (FK 제약조건) |

```text
[속성의 3대 분류]
1. 기본 속성 (Basic)    : 업무로부터 자연스럽게 도출되는 본래의 속성 (예: 고객명, 생년월일)
2. 설계 속성 (Designed) : 업무에 없으나 데이터 모델링을 위해 인위적으로 부여한 속성 (예: 상태코드, 일련번호)
3. 파생 속성 (Derived)  : 타 속성으로부터 계산·가공되어 생성된 속성 (예: 총결제금액, 평균점수 - 성능 고려)
```

#### 한줄 요약

- 엔티티는 행들의 모임, 속성은 열의 정의, 관계는 테이블 간 외래키 연결과 제약조건으로 실체화됨

## Ⅲ. ERD 표기법 심층 비교: IE 표기법 vs 바커(Barker) 표기법

```text
[IE 표기법: Information Engineering (James Martin, 까마귀발)]
 [고객] ───┼───────O──< [주문]
         필수 1    선택 N (고객은 주문을 0개 또는 여러 개 가질 수 있음)

[Barker 표기법: Oracle Case Method]
 [고객] ───+───────#─── [주문]  (실선=필수, 점선=선택, 까마귀발=N, #=식별자, *=필수속성, o=선택속성)
```

| 비교 항목 | IE 표기법 (Crow's Foot) | 바커(Barker) 표기법 (CASE Method) |
|---|---|---|
| **제안자** | James Martin, Clive Finkelstein | Richard Barker (Oracle사 채택) |
| **관계선 형태** | 실선(식별 관계) 및 점선(비식별 관계) 구분 | 실선(필수 관계) 및 점선(선택 관계) 구분 |
| **다수(N) 표기** | 까마귀발(Crow's Foot, 세 갈래 선) | 까마귀발 형태의 끝단 기호 사용 |
| **선택도 표기** | 관계선에 O(선택, 0) 또는 짝대기(필수, 1) 원형 결합 | 엔티티와 맞닿은 선이 실선(반드시 참여) / 점선(선택 참여) |
| **속성 표시 위치**| 엔티티 사각형 내부 구역 분할하여 기재 | 엔티티 사각형 내부에 기호와 함께 기재 (`#` PK, `*` 필수, `o` 선택) |
| **실무 채택 도구**| ERwin, DA# 등 다수 범용 CASE 도구 표준 | Oracle SQL Developer Data Modeler 표준 |

#### 한줄 요약

- IE 표기법은 식별/비식별 관계를 선의 종류로, 선택성을 기호(O/|)로 표현하고, 바커 표기법은 필수/선택을 선의 실선/점선으로 표현함

## Ⅳ. ERD 모델링 4단계 수행 절차

```text
① 주제 영역 정의 및 핵심 엔티티(Core Entity) 도출
               ↓
② 식별자(UID/PK) 확정 및 엔티티 상세 속성 정의
               ↓
③ 엔티티 간 업무 관계(Relationship) 연결 및 카디널리티/선택도 설정
               ↓
④ M:N 관계 해소(교차 엔티티 생성) 및 정규화(1NF~3NF)·무결성 검증
```

| 단계 | 주요 활동 | 핵심 산출물 및 기법 |
|---|---|---|
| **1. 엔티티 도출** | 업무 명세서 내 명사형 단어 추출, 관리 대상 여부 판정 (2개 이상의 인스턴스 존재 여부 확인) | 엔티티 정의서, 주제영역 분류도 |
| **2. 속성 및 식별자** | 엔티티의 성질을 나타내는 속성 분류, 본질 식별자 및 인조 식별자(대체키) 결정 | 속성 목록, 도메인 정의서 |
| **3. 관계 및 차수** | 업무 동사 분석, 카디널리티(1:1, 1:N, M:N)와 선택도(Mandatory/Optional) 결정 | 초기 ERD (개념 모델) |
| **4. 관계 정교화** | M:N 다대다 관계를 교차 엔티티로 분해, 함수적 종속성 기반 정규화 수행 | 완성된 논리 ERD |

#### 한줄 요약

- ERD 작성은 업무에서 명사를 뽑아 엔티티를 세우고, 동사를 분석해 관계를 잇고, 다대다 관계를 풀어 정규화하는 과정임

## Ⅴ. 논리 모델에서 M:N (다대다) 관계의 문제점 및 해소 방안

```text
[M:N 관계의 직접 표현 불가]
 [학생] >───────────────< [과목]   ──▶ 한 학생은 여러 과목 수강, 한 과목은 여러 학생 수강
 (RDBMS는 외래키 컬럼 하나에 복수의 값을 담을 수 없으므로(1NF 위배) 물리 테이블 구현 불가)
               │
               ▼ 교차 엔티티(Associative Entity) 도입을 통한 1:N 분해
 [학생] ───┼──< [수강신청] >──┼─── [과목]
 (1)             (M:N 해소)         (1)
 - 교차 엔티티: [수강신청]
 - 주식별자: (학생번호 + 과목번호) 복합키 또는 수강신청번호(인조키)
 - 관계 속성 흡수: 수강신청일자, 중간성적, 기말성적
```

| 해소 단계 | 수행 작업 | 실무 주의사항 |
|---|---|---|
| **1. 교차 엔티티 도출** | M:N 관계 사이에 두 엔티티를 매핑할 새로운 엔티티 생성 | 명확한 행위 업무 명칭 부여 (예: 주문내역, 수강신청) |
| **2. 식별자 구조 결정** | 복합 식별자(PK1 + PK2) 사용 vs 단일 인조 식별자(ID) 부여 | 자식 테이블이 많을 경우 복합키 누적으로 인한 조인 부하 검토 |
| **3. 관계 속성 배치** | 관계가 발생할 때 생성되는 고유 속성을 교차 엔티티로 이전 | 예: 수강신청의 신청일자, 주문내역의 주문수량/단가 |
| **4. 카디널리티 재정의** | 양 부모 엔티티와 교차 엔티티 간 관계를 각각 1:N 관계로 확정 | 부모 엔티티의 참조 무결성(Cascade/Restricted) 규칙 설정 |

#### 한줄 요약

- M:N 관계는 1NF를 위반하여 RDBMS에 직접 매핑될 수 없으므로, 교차 엔티티를 생성하고 관계 속성을 이전하여 두 개의 1:N 관계로 해소해야 함

## Ⅵ. ERD 모델링 실무 문제 상황 및 해결 대책

| 문제 상황 | 근본 원인 | 실무 대책 | 기대 효과 |
|---|---|---|---|
| **과도한 식별 관계로 인한 복합키 비대화** | 5~6계층 이상 부모의 PK가 자식에게 실선(식별)으로 계속 전속 상속 | 최하위 트랜잭션 테이블은 비식별 관계(점선)로 전환하고 인조 식별자(Sequence/UUID) 적용 | SQL 조인 조건 간소화 및 인덱스 저장 공간 절감 |
| **ERD와 운영 RDBMS 스키마 불일치** | 배포 후 DB 콘솔 직수정 및 형상관리 도구와의 동기화 단절 | Liquibase/Flyway 스키마 마이그레이션 도구 도입 및 Git 기반 ERD 역공학 자동 검증 | 문서와 물리 DB 형상의 100% 일치 |
| **M:N 미해소 상태로 물리 DDL 생성** | 모델링 검증 단계 누락으로 비정규화된 쉼표(,) 구분 데이터 저장 | 모델링 툴의 정적 검증 룰셋 활성화 (M:N 검출 시 DDL 생성 차단) | 제1정규형 준수 및 정합성 보장 |
| **필수/선택 관계의 오정의로 인한 데이터 누락** | 비즈니스 예외 조건을 간과하고 무조건 필수(Mandatory)로 관계 설정 | 현업 인터뷰 및 데이터 프로파일링을 통해 NULL 허용 여부(Optionality) 재검증 | 런타임 외래키 위반 에러 방지 |

#### 한줄 요약

- 식별/비식별 관계의 신중한 선택, 교차 엔티티 정규화, CI/CD와 연계된 스키마 형상관리가 ERD 품질을 결정함

## Ⅶ. '박제된 문서'를 넘어 '살아있는 아키텍처'로의 발전 제언

- **[Living ERD 파이프라인 구축]**: 프로젝트 초기 산출물로 작성된 후 캐비닛에 보관되는 ERD는 기술 부채의 원흉이며, 변경되는 코드가 곧 데이터 모델이 되는 체계가 필요함
- 나라면:
  1. 도메인 주도 설계(DDD)를 적용하여 전사 거대 ERD를 각 마이크로서비스의 Bounded Context 단위로 분할된 독립 ERD 모델로 재편
  2. 스키마 DDL 변경을 애플리케이션 코드(Git)로 관리하는 Code-as-Schema 체계를 수립하고, PR(Pull Request) 시 Mermaid 또는 SchemaSpy를 통해 웹 기반 살아있는 ERD 다이어그램이 자동 빌드·배포되는 아키텍처를 구현

#### 한줄 요약

- ERD는 개발 단계의 일회성 그림이 아니라, 비즈니스 도메인의 변경을 지속적으로 반영하고 형상관리되는 살아있는 거버넌스 자산이어야 함

## 1교시 10점 답안 발췌

### 1. ERD(Entity Relationship Diagram) 정의

- 비즈니스 도메인의 현실 세계 데이터를 **엔티티(Entity), 속성(Attribute), 관계(Relationship)**의 표준 기호로 추상화한 데이터베이스 논리적 설계 다이어그램

### 2. IE 표기법 기호 및 M:N 관계 해소 메커니즘

```text
[IE 표기법 관계선 기호]
──┼──  : 필수 1 (Mandatory One)      ──O──  : 선택 1 (Optional One)
──┼──< : 필수 N (Mandatory Many)     ──O──< : 선택 N (Optional Many)
```

```text
[M:N 관계 해소: 교차 엔티티 도입]
[고객] >────────< [상품]   ──▶   [고객] ───┼──< [주문내역] >──┼─── [상품]
(물리 RDBMS 구현 불가)                  (1:N)  (교차 엔티티) (N:1)
```

| 구분 | 논리 모델 M:N 상태 | 교차 엔티티 해소 후 |
|---|---|---|
| 물리 구현 가능 여부 | 불가능 (1차 정규형 위반) | 가능 (단일 값 외래키 매핑) |
| 관계 속성 보관 | 둘 곳이 없어 엔티티 오염 | 교차 엔티티 내 배치 (주문수량, 단가 등) |
| 주식별자 구조 | 정의 불가 | 복합 식별자(PK1+PK2) 또는 단일 인조키 |

### 3. 차별화 제언

- 과도한 식별 관계(실선) 상속으로 인한 복합키 비대화를 방지하기 위해 3단계 이상 자식 테이블은 **비식별 관계(점선)**로 전환하고, Git 형상관리와 연동된 **Living ERD 파이프라인**을 구축함

## 출제 이력과 검증 출처

- 제121회 공식 문제지: 논리 데이터 모델링 단계별 수행 절차 및 산출물

## 학습 체크

- [ ] IE 표기법(까마귀발)의 카디널리티 및 선택도 기호 4가지를 정확히 작도할 수 있는가
