## 연관 키워드

- ERD(Entity-Relationship Diagram), 개체(Entity), 속성(Attribute), 관계(Relationship)
- 카디널리티(Cardinality), 선택성(Mandatory·Optional), Crow's Foot 표기법
- 식별 관계(Identifying Relationship), 비식별 관계(Non-identifying Relationship), 교차 엔티티(Associative Entity)

## Ⅰ. 개체-관계 다이어그램의 개요

- 핵심 요약 : 엔티티, 속성, 관계를 기호로 그려 업무 데이터 구조를 표준화하는 개념적 데이터 모델링 도구.
- 개념 : 업무 대상이 되는 데이터의 실체(Entity), 속성(Attribute), 관계(Relationship)를 그래픽 기호로 표현한 **개체-관계 다이어그램**(ERD, Entity-Relationship Diagram). 1976년 피터 첸(Peter Chen)이 제안한 방식이 출발점이다.
- 배경 및 필요성 : 업무 요구사항이 문서로만 전달되면 이해관계자마다 데이터 구조를 다르게 해석해 설계 오류가 늘어난다. 그림으로 합의된 구조는 개념 모델에서 논리·물리 설계로 이어지는 기준이 된다.
- 주요 목적 : 이해관계자 사이의 공통 언어로서 데이터 구조를 표준 기호로 표현하는 것.
- 표기법 : 피터 첸 표기법(사각형·타원·마름모), 정보공학(IE, Information Engineering) 표기법인 Crow's Foot, Barker 표기법이 쓰인다. 실무에서는 카디널리티를 직관적으로 보여주는 **Crow's Foot** 표기가 널리 쓰인다.

## Ⅱ. 개체-관계 다이어그램의 특징

- 핵심 요약 : 세 가지 구성요소와 선택성·카디널리티 기호 체계가 ERD 읽기의 핵심.

1. 개체 : 업무에서 영속적으로 관리하는 사람, 장소, 사물, 사건으로 명사형으로 표현 → 테이블 후보의 출발점.
2. 속성 : 개체가 가진 고유한 성질로 더 나눌 수 없는 최소 데이터 단위 → 컬럼 후보.
3. 관계 : 두 개체 사이의 업무적 연관으로 동사형으로 표현 → 외래키 설계의 근거.
4. 선택성 기호 : 세로 실선은 필수(Mandatory), 원은 선택(Optional)을 뜻함 → 존재 여부 표현.
5. 카디널리티 기호 : 세로 실선은 하나(One), 까마귀 발은 여럿(Many)을 뜻함 → 1:1, 1:N, M:N 구분.
6. 계층적 모델링 : 개념, 논리, 물리 수준으로 나누어 표현 → 단계별 상세화 지원.

## Ⅲ. 개체-관계 다이어그램의 구조 (흐름)

- 핵심 요약 : 업무 분석에서 물리 설계로 이어지는 작성 흐름과 Crow's Foot 기호의 의미 구조.

```text
[ ERD 작성 흐름 ]
업무 분석 및 요구사항 정의
        ↓
엔티티 도출 (명사) → 속성 정의 → 식별자 지정
        ↓
관계 도출 (동사) → 카디널리티·선택성 표기
        ↓
정규화 검증 → 논리·물리 설계 전환
```

| 기호 조합 | 의미 | 업무 규칙 예시 |
| --- | --- | --- |
| 1 and Mandatory | 필수 하나 | 고객은 반드시 회원 등급 하나를 가짐 |
| 1 and Optional | 선택 하나 | 사원은 부서가 없거나 하나에 소속 |
| Many and Mandatory | 필수 여럿 | 주문은 주문 상세를 하나 이상 가짐 |
| Many and Optional | 선택 여럿 | 고객은 주문이 없거나 여러 개 보유 |

- 기호의 구조적 의미 : 바깥쪽 기호는 상대 인스턴스의 존재 여부(선택성), 안쪽 기호는 최대 개수(카디널리티)를 나타낸다.

## Ⅳ. 식별 관계와 비식별 관계의 비교

- 핵심 요약 : 부모의 식별자가 자식의 기본키에 들어가느냐 일반 속성으로 들어가느냐에 따라 설계 차이가 생긴다.

```text
[ 식별 관계 (실선) ]
부모 : 부서 ==== 자식 : 프로젝트
자식 기본키 = 부서번호 + 프로젝트번호

[ 비식별 관계 (점선) ]
부모 : 부서 ---- 자식 : 사원
자식 기본키 = 사원번호, 부서번호는 외래키
```

| 비교 항목 | 식별 관계 | 비식별 관계 |
| --- | --- | --- |
| ERD 선 표기 | 실선 | 점선 |
| 키 배치 | 부모의 식별자가 자식 기본키의 일부로 상속 | 부모의 식별자가 자식의 일반 외래키로 상속 |
| 존재 종속성 | 부모 없이 자식이 단독으로 존재하기 어려움 | 부모 없이도 자식이 존재할 수 있음 |
| 설계 영향 | 자식 기본키 컬럼이 늘어 조인 조건이 복잡해짐 | 결합도가 낮아 유연하나 외래키 인덱스 관리 필요 |

## Ⅴ. 개체-관계 다이어그램의 장점과 한계

- 핵심 요약 : 데이터 구조 소통의 표준화가 장점이며, 실제 DB와의 불일치, 복잡도, 표현 범위가 한계.

- 장점
  1. 이해관계자 사이에 데이터 구조를 같은 기호로 소통.
  2. 식별·비식별 표기로 존재 종속성과 무결성 설계를 명확히 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 모델과 실제 DB의 불일치 | 긴급 패치의 DDL 직접 수정으로 ERD가 현행화되지 않아 문서가 무용해짐 | Flyway, Liquibase 같은 형상 관리 도구 도입, DDL 변경 시 자동 역공학 동기화 | 모델-DB 차이 건수 |
| 대규모 ERD의 복잡도 | 수백에서 수천 개의 개체 관계선이 얽혀 가독성 상실 | 주제영역(Subject Area)별 분할, 개념·논리·물리 계층화, DDD의 Bounded Context 단위 분리 | 주제영역당 개체 수 |
| 비정형 데이터 표현 한계 | Crow's Foot은 관계형 스키마 중심이라 JSON 계층이나 그래프 관계를 표현하기 어려움 | 복합 데이터 타입용 확장 표기 정의, DFD와 아키텍처 다이어그램과 상호 참조 | 표현 누락 항목 수 |

## Ⅵ. 개체-관계 다이어그램에 대한 기술사적 제언

- 핵심 요약 : 개념 모델의 M:N 관계는 교차 엔티티로 해소하고, 인위적 대리키를 무분별하게 붙이지 않는 모델링 원칙.

개념 모델의 M:N 관계는 물리 RDBMS(Relational Database Management System) 테이블로 바로 구현할 수 없으므로, 논리 모델링 단계에서 교차 엔티티를 넣어 1:N과 M:1 관계로 바꾸는 것이 원칙이다. 이 과정을 생략하면 물리 설계에서 구조가 임의로 바뀌어 모델과 실제 DB가 어긋나기 시작한다.

모든 테이블에 자동 증가 ID나 UUID(Universally Unique Identifier) 기반 대리키를 기계적으로 붙이면 비즈니스 식별성이 약해지고 중복 검증도 어려워진다. 자연키의 안정성을 먼저 검토하고, 식별 관계와 대리키를 상황에 맞게 섞어 쓰는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : ERD는 데이터 구조를 함께 이해하는 소통 표준이자 무결성 설계의 출발점.
- 시사점 : 표기법의 통일과 도메인 단위 분할, 형상 관리와의 연계가 대규모 데이터 모델의 품질을 지키는 핵심 조건.
