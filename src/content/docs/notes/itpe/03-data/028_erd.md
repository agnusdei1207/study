 ┃
 ┣━ Ⅰ 개요 ───── 복잡한 현실 세계 비즈니스 요구사항 → 엔티티·관계·속성으로 추상화하여 시각적으로 모델링
 ┣━ Ⅱ 특징 ───── 직관적 시각화 · 개념/논리/물리 3단계 모델링 매핑 · 개발자-현업 간 의사소통 표준 도구

## 한 줄 본질
- 복잡하게 얽힌 업무 규칙과 데이터 구조 → 개체, 속성, 관계의 정형화된 기호 다이어그램으로 가시화 → 데이터베이스 설계의 청사진 및 의사소통 단일 진실 공급원(SSOT) 역할 / 물리 DB와의 동기화 부재 시 문서 박제화 위험

## 핵심 그림
```text
[IE 표기법 (Crow's Foot, 까마귀발) 관계 표현 기호]

  기호 모양       카디널리티 (차수)          의미
  ────┼───       1 (Mandatory One)         반드시 1개 (필수 1)
  ────O───       0 (Optional One)          0개 또는 1개 (선택 1)
  ────┼──<       N (Mandatory Many)        1개 이상 (필수 다수)
  ────O──<       0..N (Optional Many)      0개 이상 (선택 다수)

[M:N 관계 해소 (교차 엔티티 도입)]
  [고객] >────O──< [상품]   ===>   [고객] ───┼──< [주문내역] >──┼─── [상품]
   (다대다 물리 구현 불가)                     (1:N)  (교차 엔티티) (N:1)
```

## 핵심 용어
- 카디널리티(Cardinality): 관계를 맺는 두 엔티티 간에 대응되는 인스턴스의 수(1:1, 1:N, M:N)
- 교차 엔티티(Associative Entity): RDBMS에서 물리적으로 직접 구현할 수 없는 M:N 다대다 관계를 1:N 두 개로 분해하기 위해 생성하는 매핑 테이블

## 핵심 통찰
- ERD는 '그림 그리기'가 아니라 '업무 규칙(Business Rule)의 정의'임 → 선 하나(실선 vs 점선, 동그라미 유무)가 "주문 없이 고객이 존재할 수 있는가?", "탈퇴 시 주문이 지워지는가?"라는 핵심 비즈니스 로직을 규정
- M:N 관계는 논리 모델의 중간 산물일 뿐 물리 DB에는 존재할 수 없음 → 반드시 주문상세, 수강신청 같은 교차 엔티티를 도출해 1:N으로 해소해야 PK/FK 설정 가능
- 식별 관계(실선)와 비식별 관계(점선)의 구분이 아키텍처를 좌우함 → 식별 관계가 깊어질수록 자식 테이블의 PK 컬럼 수가 누적 증가해 쿼리 조인 복잡도 폭증

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 식별 관계 vs 비식별 관계 | 관계의 속성 전이 방식 | 부모의 PK가 자식의 PK에 포함되면 식별(실선), 단순 일반 FK면 비식별(점선) |
| 선택도 (Optionality) | 관계의 참여 제약 | 관계에 반드시 참여해야 하면 필수(Mandatory), 참여하지 않아도 되면 선택(Optional) |

## 이웃 토픽과 구분
- ERD vs 클래스 다이어그램: ERD = 데이터 상태와 영속적 저장 관계 중심 / 클래스 다이어그램 = 데이터뿐만 아니라 객체의 행위(메서드, 책임)까지 모델링

## 문제·원인·대책
- 적용 상황: 대규모 공공 차세대 차세대 데이터베이스 재구축
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| M:N 관계를 그대로 물리 테이블에 생성하려다 복합키 충돌 및 조인 실패 | 논리 ERD의 M:N 관계 미해소 상태로 물리 모델링 이행 | 관계 속성을 분석해 새로운 업무 엔티티(교차 테이블) 도출 및 1:N 분해 | 정규화된 물리 테이블 완성 |
| 운영 DB 컬럼은 계속 바뀌는데 ERD 문서는 2년 전 상태로 방치 | 모델링 도구와 실제 RDBMS 간 리버스/포워드 엔지니어링 단절 | DDL 형상관리(Git)와 ERD 도구(ERwin, DBeaver) CI 연동 | 문서와 실제 DB 100% 동기화 |
