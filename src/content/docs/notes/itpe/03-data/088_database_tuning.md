## 연관 키워드

- 데이터베이스 튜닝, 병목 분석, 실행계획, 인덱스, 조인, 대기 이벤트, 성능 기준선, 옵티마이저, 회귀 검증

## Ⅰ. 데이터베이스 튜닝의 개요

- 핵심 요약 : 관측된 병목을 근거로 SQL·설계·자원 설정을 조정해 서비스 성능을 개선하는 반복 활동.
- 개념 : 응답시간과 처리량을 측정해 원인을 찾고, SQL(Structured Query Language) 쿼리·스키마·DBMS(Database Management System) 설정을 개선하는 활동(**데이터베이스 튜닝**, Database Tuning).
- 배경 및 필요성 : 데이터량과 동시 접속이 늘면 같은 자원에서도 지연이 생기므로, 증설에 앞서 원인을 찾아 비용을 줄일 필요가 있음.
- 주요 목적 : 응답시간·처리량·자원 사용과 안정성 사이의 균형 확보.
- 원칙 : **병목 분석**(관측 지표로 병목의 위치를 찾는 단계)에 근거해 변경하고, 변경 전후를 같은 조건으로 비교.

## Ⅱ. 데이터베이스 튜닝의 특징 및 장점

- 핵심 요약 : 계층별 점검과 기준선 관리로 병목 원인을 근거 있게 좁히는 접근.

1. 근거 기반 개선 : **실행계획** (DBMS가 선택한 데이터 접근·조인 경로)을 근거로 가설을 세움 → 추측성 변경 감소.
2. 다계층 원인 분리 : 쿼리, 스키마와 **인덱스**, 설정·인프라 순서로 원인을 좁힘 → 불필요한 증설 방지.
3. 지속 관리 : 워크로드와 데이터량 변화에 따라 **성능 기준선** (평시 응답시간·처리량의 기준값)을 갱신 → 성능 회귀를 조기 발견.

- 효과 한계 : 튜닝 효과는 워크로드·DBMS·데이터 분포에 따라 다르며, 특정 계층이 항상 큰 효과를 내지는 않음.

## Ⅲ. 데이터베이스 튜닝의 구조 (흐름)

- 핵심 요약 : 기준선 측정에서 시작해 병목 확인, 변경, 검증을 거쳐 기록으로 닫히는 반복 루프.
- **대기 이벤트** (DBMS가 세션의 작업 대기 원인을 기록한 항목) : 병목이 CPU·I/O·잠금 중 어디에 있는지 가리키는 증거.
- **회귀 검증** (변경 후 기존 성능과 정합성이 유지되는지 재확인) : 변경 뒤 핵심 SQL 성능과 데이터 정합성을 다시 확인하는 단계.

```text
[서비스 목표·성능 기준선]
          ↓
[상위 SQL·대기 이벤트·자원 측정]
          ↓
[실행계획·데이터 분포 분석]
          ↓
[SQL·인덱스·설정 변경]
          ↓
[부하·정합성 회귀 검증]
          ↓
[성과 기록·지속 모니터링]
```

- 실행계획과 실제 실행 통계의 차이를 확인하고, 대표 데이터와 파라미터 조건으로 재현한다.
- 변경은 한 번에 한 요인씩 적용해 원인과 효과를 구분한다.

## Ⅳ. 주요 튜닝 대상 비교

- 핵심 요약 : **옵티마이저**가 데이터 분포에 따라 고르는 접근·조인·정렬 방식을 워크로드에 맞게 평가.
- **조인** (두 테이블을 조건으로 결합하는 연산) : Nested Loop, Hash Join, Sort Merge 중 입력 크기와 정렬 상태에 맞는 방식을 고름.

```text
[튜닝 계층: 위에서 아래로 좁힘]
    ① 쿼리
   (SQL 재작성·호출 빈도)
          ↓
    ② 스키마·인덱스
   (데이터 모델·접근 경로)
          ↓
    ③ 설정·인프라
   (메모리·I/O·DBMS 파라미터)
```

| 대상 | 확인 항목 | 선택·개선 기준 |
| --- | --- | --- |
| SQL | 불필요한 조회·반복 연산 | 결과 동일성·호출 빈도 |
| 인덱스 | 선택도·컬럼 순서·유지 비용 | 읽기 개선과 쓰기 비용의 균형 |
| Nested Loop | 외부 행 수·내부 인덱스 접근 | 작은 입력과 효율적 인덱스 |
| Hash Join | 메모리·해시 디스크 전환 | 대량 동등 조인 |
| Sort Merge | 정렬 비용·입력 정렬 상태 | 정렬·범위 조건 적합성 |
| DBMS 자원 | CPU·메모리·I/O·대기 | 병목 증거가 있을 때 조정 |

- 조인 방식과 인덱스 사용은 옵티마이저, 데이터 분포, 제품 구현에 따라 달라진다.

## Ⅴ. 데이터베이스 튜닝의 한계와 방안

- 핵심 요약 : 측정 오류, 인덱스 부작용, 실행계획 변화, 증설 의존을 기준선과 회귀 검증으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 불완전한 진단 | 피크 시간·실제 파라미터 미반영 → 잘못된 병목 판단 | 피크 시간을 포함한 기준선 수집 | 기준선의 대표성 |
| 인덱스 과다 | 삽입·갱신 비용과 저장 공간 증가 | 읽기·쓰기를 함께 측정하고 불필요 인덱스 정리 | 쓰기 지연, 저장 공간 |
| 통계정보 변화 | 실행계획 변동 → 핵심 SQL 성능 저하 | 통계 갱신 후 핵심 SQL 재검증 | 실행계획 변경 건수 |
| 증설 반복 | 근본 원인 미해결, 비용만 증가 | SQL·데이터 모델·잠금·자원 병목을 구분 | 병목 유형별 해소율 |

## Ⅵ. 데이터베이스 튜닝에 대한 기술사적 제언

- 핵심 요약 : 튜닝을 서비스 수준 목표와 변경관리에 연결해 성능 개선을 안전하게 운영하는 체계로 정착.

1. 서비스 수준 목표(SLO, Service Level Objective)의 응답시간 백분위와 처리량을 튜닝 목표로 삼고, 변경 전후 값을 같은 지표로 기록할 필요가 있다.
2. 부하 시험, 카나리 적용, 롤백 기준을 변경 절차에 넣어 성능과 데이터 정합성을 함께 확인해야 한다.
3. DBMS별 진단 도구와 로그의 해석 범위를 문서화하고, 수집된 SQL 값에 포함된 개인정보를 마스킹하여 보호할 필요가 있다.

## Ⅶ. 결론

- 핵심 요약 : 데이터베이스 튜닝은 증설보다 측정·실행계획·검증을 바탕으로 병목을 개선하는 과정임.
- 시사점 : 튜닝 계층, 진단 흐름, 인덱스·조인 선택과 회귀 검증을 한 흐름으로 연결해야 개선 효과가 유지됨.
