## 지식 로드맵 내 현재 위치

데이터베이스 → 물리적 설계·운영 → 성능 관리와 튜닝

## 30초 인출

- 본질: **데이터베이스 튜닝은** 측정된 성능 병목을 찾아 데이터 구조·DBMS 자원·질의 접근을 개선하는 작업
- 메커니즘: 기준 부하와 지표 측정 → 원인 분석 → 변경 → 동일 조건의 전후 검증
- 통찰: 병목 구간의 과학적 식별을 위해 비즈니스 모델링부터 SQL, 인덱스, 인스턴스, OS/하드웨어 계층까지 하향식(Top-Down) 체계적 튜닝 파이프라인 정립 필수

<details>
<summary>핵심 용어</summary>

| 용어 | 설명 |
|---|---|
| **데이터베이스 튜닝(Database Tuning)** | 데이터베이스의 응답·처리 성능을 측정하고 병목을 개선하는 작업 |
| **실행계획(execution plan)** | 질의를 수행하기 위해 옵티마이저가 선택한 접근·조인 연산의 계획 |
| **인덱스(index)** | 조건 검색과 정렬 등을 지원하도록 키와 행 위치를 관리하는 자료구조 |
| **대기 이벤트(wait event)** | 세션이 CPU 외의 자원이나 작업 완료를 기다리는 상태를 나타내는 관측 정보 |
| **서비스 수준 목표(Service Level Objective, SLO)** | 서비스 성능·신뢰성에 대해 합의한 측정 가능한 목표 |

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 데이터베이스의 응답·처리 성능을 측정하고 병목을 개선하는 작업 |
| 목적 | 업무 부하에 맞는 자원 사용과 예측 가능한 질의 성능 확보 |

## Ⅱ. 데이터베이스 튜닝의 특징

| 특징 | 관찰 대상 | 적용 의미 |
|---|---|---|
| 업무 부하 의존 | 대표 SQL·동시성·데이터 분포 | 같은 설정도 업무마다 효과가 다름 |
| 계층 간 영향 | SQL·인덱스·DBMS·저장장치 | 한 계층의 개선이 다른 계층의 비용을 바꿀 수 있음 |
| 실측 검증 | 지연 분포·처리량·자원·오류 | 계획의 예상 비용보다 실제 전후 결과 우선 |

## Ⅲ. 부하 측정·병목 분리·전후 검증 프로세스

```text
대표 읽기·쓰기 부하와 p95·처리량 기준선 측정
                 ↓ 느린 질의·대기 구간 분리
  ├─ 계획 행 수·실제 행 수 차이 → 통계·접근/조인 경로 검토
  └─ CPU·I/O·잠금 대기 집중 → 자원·경합 검토
                 ↓ 원인에 맞는 변경 한 가지 적용
동일 부하 재측정: 읽기·쓰기·자원·오류
  ├─ 목표 달성·부작용 허용 → 변경 확정
  └─ 효과 없음·회귀 발생 → 롤백·다른 원인 분석
```

측정 조건·목표를 고정하고 주요 질의와 대기 구간을 찾은 뒤, 원인에 맞는 변경을 한 번에 점진 적용. 동일 부하로 성능·기능 회귀를 검증하고 효과 미흡 시 롤백 수행.

## Ⅳ. 튜닝 영역과 조정 항목

| 영역 | 주요 점검 | 대표 조정 |
|---|---|---|
| 데이터 모델 | 중복·관계·데이터 증가·접근 빈도 | 정규화·반정규화 검토, 파티션·저장 구조 설계 |
| DBMS·인프라 | CPU·메모리·디스크·동시 세션·대기 | 용량·설정·배치 시간 조정, 자원 경합 완화 |
| SQL·인덱스 | 실행계획·조건절·조인·정렬·논리 읽기 | SQL 수정, 통계 갱신, 인덱스 추가·변경·제거 |

인덱스는 조회 경로를 줄일 수 있지만 저장 공간과 DML 비용 수반. 인덱스 컬럼 가공도 표현식 인덱스 등 DBMS 기능과 질의 형태에 따라 유연하게 대응.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 평균 응답만 보면 느린 요청이 가려짐 | 대표 질의의 p95 등 지연 분포와 처리량을 함께 측정 |
| 조회용 인덱스가 쓰기·저장 비용을 높임 | 읽기·쓰기 부하를 같은 조건에서 전후 비교하고 롤백 기준 설정 |
| 계획상 비용 감소를 실제 성능 개선으로 오인 | 실행계획과 실제 행 수·대기 시간을 대조하고 부하 시험으로 검증 |

## Ⅵ. 제언

비용 대비 효과가 가장 높은 SQL 및 인덱스 튜닝을 우선 실행하고 대량 I/O 병목은 파티셔닝과 버퍼 풀 최적화를 통해 밀리초 단위 쿼리 응답 보장.

### 데이터베이스 튜닝 4계층 접근법

```text
[1계층: 비즈니스/데이터 모델 튜닝] (효과 극대, 비용 극소)
  - 정규화/반정규화 최적화, 파티셔닝 설계, 아카이빙
       │
       ▼
[2계층: SQL 및 인덱스 튜닝] (실무 핵심, 80% 성능 개선 달성)
  - 실행계획 분석, 커버링 인덱스, 힌트(Hint), 조인 순서 최적화
       │
       ▼
[3계층: DBMS 인스턴스 튜닝]
  - 버퍼 풀(Buffer Pool) 확대, 동시성 락 파라미터, 체크포인트 튜닝
       │
       ▼
[4계층: OS 및 하드웨어 튜닝]
  - NVMe SSD 도입, 커널 I/O 스케줄러, 파일시스템 마운트 옵션 최적화
```

### 선택 근거: 제언: 소프트웨어 계층 튜닝

| 구분 | 하드웨어 증설 중심 (Scale-Up) | 제언: 소프트웨어 계층 튜닝 |
|---|---|---|
| 개선 비용 | 클라우드 인스턴스 비용 지속 증가 | 비용 발생 없이 SQL/인덱스 최적화로 성능 극대화 |
| 근본 해결 | 비효율 쿼리 존속으로 재차 병목 도달 | Full Table Scan 제거 등 근본 원인 해결 |
| 확장 한계 | 서버 단일 스케일업 한계 도달 | 아키텍처 최적화로 처리량 수배 이상 확장 |
