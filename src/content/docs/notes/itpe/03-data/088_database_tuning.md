## 답안 골격
```text
[데이터베이스 튜닝 (Database Tuning)] ◀━━ 머리: Ⅶ 내 의견 (APM 슬로우 쿼리 모니터링 기반 SQL/인덱스 튜닝 우선 및 바인드 변수 체계화)
 ┃
 ┣━ Ⅰ 개요 ───── 한정된 시스템 자원 환경에서 DB의 처리량(Throughput)을 극대화하고 응답 시간(Response Time)을 최소화하기 위해 전 계층을 개선하는 최적화 활동
 ┣━ Ⅱ 특징 ───── 3계층 튜닝 접근(설계-환경-SQL) · 병목(Bottleneck) 해소 · 최소 I/O 원칙 · 비용 효율성 · 지속적 사이클 활동
 ┣━ Ⅲ 구조 ───── 모델 튜닝(정규화/반정규화/파티셔닝) / 환경 튜닝(메모리/디스크 I/O/체크포인트) / SQL·인덱스 튜닝(실행계획/인덱스/힌트)
 ┣━ Ⅳ 흐름 ───── ① 성능 모니터링(AWR, 슬로우쿼리) → ② 병목 지점 분석 → ③ 튜닝 목표치 설정 → ④ 3단계 튜닝 수행 → ⑤ 성능 검증 및 기준선(Baseline) 갱신
 ┣━ Ⅴ 비교 ───── 모델 튜닝 vs 환경 튜닝 vs SQL 튜닝 (효과 최상·비용 고 vs 인프라 스케일업 vs 빈도 최다·즉각적 개선)
 ┗━ Ⅵ 실무 ───── 바인드 변수 미사용으로 인한 하드 파싱 폭증 / 인덱스 과다로 인한 DML 지연 / 잘못된 풀스캔
```
- 필수 키워드: DB 튜닝 · 모델 튜닝 · 환경 튜닝 · SQL 튜닝 · 최소 I/O · 실행 계획(Execution Plan) · 바인드 변수 · 인덱스 설계
- 기출: 127회 `데이터베이스 튜닝의 필요성, 3대 영역(설계, 환경, SQL)별 주요 접근 방법 및 최적화 절차를 설명하시오.` → Ⅰ 필요성 + Ⅲ 3대 영역 + Ⅳ 절차

## 한 줄 본질
- 자원 한계와 비효율적 데이터 접근으로 인한 트랜잭션 지연 및 서버 장애 → 모델 설계 개선, DBMS 메모리/스토리지 파라미터 조정, SQL 및 인덱스 접근 경로 최적화 → 최소 블록 I/O 달성 / 인덱스 남발 시 쓰기 성능 저하

## 핵심 그림
```text
[DB 튜닝 3계층 피라미드 및 비용-효과 관계]

                    ▲ [1. 모델 튜닝 (설계)]
                   / \  - 정규화/반정규화, 파티셔닝
                  /   \ - 효과: 극대 (근본적 해결)
                 /     \ - 수정 비용: 매우 높음 (초기 단계 필수)
                /───────\
               / 2. 환경 \ [2. 환경 튜닝 (인스턴스/인프라)]
              /   튜닝    \ - 버퍼 캐시, 체크포인트 주기, 커넥션 풀
             /             \ - 효과: 중간, 비용: 하드웨어 증설 비용
            /───────────────\
           /   3. SQL 및     \ [3. SQL 및 인덱스 튜닝]
          /    인덱스 튜닝    \ - 인덱스 생성, 조인 방식, 실행계획 변경
         /─────────────────────\ - 효과: 즉각적, 빈도: 전체 튜닝의 80% 차지
```

## 핵심 용어
- 블록 I/O 최소화 원칙: DB 튜닝의 가장 근본적인 대원칙으로, 디스크 I/O뿐만 아니라 메모리 버퍼 캐시에서 읽는 논리적 블록 수(Logical Reads) 자체를 줄이는 것
- 소프트 파싱(Soft Parsing): 이미 메모리(라이브러리 캐시)에 캐싱된 실행 계획을 재사용하여 구문 분석과 최적화 단계를 건너뛰는 것으로, 바인드 변수 사용이 필수 전제

## 핵심 통찰
- 튜닝 효과는 모델 튜닝이 가장 크지만, 이미 운영 중인 시스템에서 테이블 구조를 바꾸는 것은 비용상 거의 불가능함 → 따라서 실무 튜닝의 80% 이상은 'SQL 및 인덱스 튜닝'에 집중됨
- 느린 쿼리를 잡겠다고 인덱스를 무제한 추가하면, `SELECT`는 빨라지지만 `INSERT/UPDATE/DELETE` 시 인덱스 리프 노드 분할(Split)로 쓰기 성능이 급락함
- 하드웨어 스케일업(CPU, RAM 증설)은 일시적인 진통제일 뿐임 → 비효율적 조인으로 1억 건을 풀스캔하는 악성 SQL 하나가 투입되면 아무리 큰 서버도 순식간에 CPU 100%로 마비됨

## 이웃 토픽과 구분
- SQL 튜닝 vs 환경 튜닝: SQL 튜닝 = 쿼리가 읽는 데이터 블록 수를 줄이는 소프트웨어적 알고리즘 개선 / 환경 튜닝 = 버퍼 캐시 크기, I/O 스레드 수 등 DBMS 인스턴스 파라미터 최적화

## 문제·원인·대책
- 적용 상황: 대규모 공공 포털 서비스 오픈 직후 동시 접속 폭증 시 DB 마비
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 동시 사용자 증가 시 DB CPU 100% 점유 및 래치(Latch) 경합 발생 | 리터럴 SQL 사용(`WHERE id = 123`)으로 하드 파싱 폭증 | 바인드 변수(`WHERE id = ?`) 전면 적용 및 쿼리 캐싱 유도 | CPU 파싱 부하 제거 및 라이브러리 캐시 적중률 99% 달성 |
| 상품 검색 쿼리 응답이 10초 이상 소요되며 풀스캔 발생 | 검색 조건 컬럼에 복합 인덱스 부재 및 인덱스 컬럼 가공(`TO_CHAR(date)`) | 조건절 컬럼 원본 유지 및 카디널리티 높은 컬럼 선행 복합 인덱스 구성 | 인덱스 레인지 스캔 유도로 응답 시간 10초에서 0.05초로 단축 |

## 이렇게 출제된다
- 제127회: "데이터베이스 시스템의 성능 개선을 위한 데이터베이스 튜닝(Database Tuning)의 단계별 접근 방법(데이터 모델 튜닝, 환경 튜닝, SQL 튜닝)과 주요 튜닝 절차를 설명하시오." → 요구 포인트: 3대 튜닝 영역별 상세 기법(정규화, 파라미터, 인덱스) + 튜닝 5단계 라이프사이클 + 바인드 변수/실행계획

## 내 의견
- [사후 약방문식 튜닝 문화 지양] 개발 단계에서는 데이터가 몇백 건뿐이라 대충 짜고, 운영 배포 후 실데이터가 수천만 건 쌓여 장애가 터진 후에야 DBA를 불러 튜닝하는 악순환 반복 → 나라면: CI 단계에서 정적 SQL 분석 도구를 돌려 Full Table Scan 여부와 인덱스 미사용 쿼리를 배포 전에 자동 검출하고, 스테이징 환경에 실데이터 규모의 통계를 주입해 부하 테스트 통과를 배포 승인 조건으로 의무화
