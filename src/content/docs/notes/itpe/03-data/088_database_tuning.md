## Ⅰ. 엔터프라이즈 시스템 성능 최적화, 데이터베이스 튜닝의 개요

### 가. 데이터베이스 튜닝(Database Tuning)의 정의
- **데이터베이스 튜닝** : 최소한의 하드웨어 리소스(CPU, Memory, Disk I/O, Network)를 소모하면서 최단 응답 시간(Response Time)과 최대 트랜잭션 처리량(Throughput)을 달성할 수 있도록 데이터 모델, 데이터베이스 환경, 인덱스 및 SQL 쿼리를 분석하고 개선하는 체계적인 엔지니어링 활동.

### 나. 튜닝의 3대 핵심 목표
- 디스크 블록 I/O 횟수 최소화 (메모리 버퍼 캐시 적중률 극대화).
- 불필요한 락(Lock) 경합 및 대기 시간 해소.
- CPU 집약적인 무거운 연산(정렬, 해시 조인) 최소화.

## Ⅱ. 데이터베이스 튜닝의 3단계 계층 구조 및 접근법

### 가. 튜닝 3대 계층과 투자 대비 효과(ROI)

```text
[ 데이터베이스 튜닝 3단계 피라미드 ]
       /\
      /  \     [3단계: 환경 및 인스턴스 튜닝] (투자 대비 효과 낮음) : OS, 커널, 메모리 풀, SGA/PGA 파라미터
     /    \
    /------\   [2단계: 설계 및 인덱스 튜닝]   (투자 대비 효과 중간) : 정규화/반정규화, 파티셔닝, 복합 인덱스
   /        \
  /----------\ [1단계: SQL 문장 튜닝]         (투자 대비 효과 가장 큼) : 실행계획 분석, 조인방식 개선, 힌트 최적화
```

| 튜닝 계층 | 주요 튜닝 대상 및 활동 | 성능 개선 잠재력 | 주요 수행 주체 |
| :--- | :--- | :--- | :--- |
| **SQL 튜닝 (Application)** | 실행 계획(Explain Plan) 분석, 비효율적인 Full Table Scan 제거, 인덱스 스캔 유도, 조인 순서 및 기법 변경, 서브쿼리 언네스팅(Unnesting) | 가장 높음 (큰 폭 개선) | 애플리케이션 개발자, SQL 튜너 |
| **설계 튜닝 (Design/Index)** | 인덱스 컬럼 순서 재조정, 커버링 인덱스 설계, 파티셔닝(Range/Hash), 대용량 집계 테이블 반정규화 | 높음 (아키텍처 레벨 개선) | 데이터 모델러, 수석 DBA |
| **인스턴스 튜닝 (Environment)** | Buffer Cache, Shared Pool 크기 조정, Redo Log 버퍼 크기 최적화, 비동기 I/O 활성화, OS 커널 세마포어 조정 | 보통 (시스템 전반 개선) | 인프라 엔지니어, 시스템 DBA |

## Ⅲ. 실행 계획(Execution Plan) 분석 및 3대 테이블 조인 기법 튜닝

### 가. 실행 계획의 3대 핵심 확인 요소
1. **액세스 경로 (Access Path)** : Full Table Scan vs Index Unique/Range Scan.
2. **조인 순서 (Join Order)** : 드라이빙 테이블(Driving/Outer)과 드리븐 테이블(Driven/Inner)의 적절성.
3. **조인 기법 (Join Method)** : NL Join, Hash Join, Sort Merge Join.

### 나. 3대 핵심 조인 기법의 동작 메커니즘 및 튜닝 가이드

| 조인 기법 | 동작 원리 | 최적 적용 환경 | 튜닝 주의사항 |
| :--- | :--- | :--- | :--- |
| **Nested Loop (NL Join)** | 드라이빙 테이블의 각 행마다 드리븐 테이블의 인덱스를 반복 탐색 ($O(M \times \log N)$) | OLTP 소량 데이터 조회, 드라이빙 테이블 건수가 적고 **드리븐 테이블에 PK/인덱스 존재 시** | 대량 데이터 조인 시 디스크 Random I/O 폭발로 성능 급락 |
| **Hash Join** | 작은 테이블(Build Input)을 메모리에 해시 테이블로 구축 후, 큰 테이블(Probe Input)을 스캔하며 매칭 | OLAP 대용량 배치 처리, 동등 조인(`=`), 적절한 인덱스가 없는 대량 조인 | 해시 테이블이 PGA 메모리를 초과하면 디스크 임시 공간(Temp Tablespace) 사용으로 지연 발생 |
| **Sort Merge Join** | 양쪽 테이블을 조인 키 기준으로 먼저 정렬한 후 병합 스캔 ($O(M \log M + N \log N)$) | 비동등 조인(`>`, `<`, `BETWEEN`), 이미 인덱스로 정렬되어 있는 경우 | 정렬에 따른 대규모 CPU 및 임시 메모리 부하 발생 |

## Ⅳ. 데이터베이스 튜닝의 주요 한계점 및 해결 방안

- 무분별한 보조 인덱스(Secondary Index) 생성에 따른 DML 성능 급감 :
  - 한계점 : 쿼리 조회 성능 개선만을 목적으로 인덱스를 과도하게 생성하여 Insert/Update/Delete 시 인덱스 트리 재구성 및 블록 I/O, 락 경합 폭증.
  - 해결 방안 : 인덱스 모니터링을 통한 미사용(Unused) 인덱스 식별 및 제거, 결합 인덱스(Composite Index) 컬럼 순서 최적화(카디널리티 기반), 커버링 인덱스 활용.
- CBO 옵티마이저 통계정보 왜곡 및 바인드 피킹(Bind Peeking) 부작용 :
  - 한계점 : 대량 데이터 변경 후 통계정보 미갱신으로 비효율적 실행 계획 선택, 바인드 피킹으로 인해 초기 매개변수에 편향된 플랜이 캐시되어 이후 쿼리 성능 악화.
  - 해결 방안 : 통계정보 수집 주기 자동화(Auto Gathering), 데이터 편향 컬럼에 대한 히스토그램 생성, 플랜 안정화를 위한 SQL 플랜 베이스라인(SPM) 또는 힌트(Hint) 통제.
- 인프라/하드웨어 증설에 의존하는 임시방편식(Band-Aid) 튜닝의 한계 :
  - 한계점 : 비효율적인 SQL 아키텍처나 잘못된 정규화/비정규화 설계를 방치한 채 CPU/RAM 증설로만 대응하여 비용 폭증 및 근본 병목 미해결.
  - 해결 방안 : APM 기반 상위 비효율 SQL(Top-N Query) 사전 식별, 블록 I/O 감소를 위한 세미조인/파티셔닝 튜닝, 애플리케이션 캐싱(Redis) 도입 등 다계층 튜닝 수행.

## Ⅴ. 고성능 데이터베이스 유지를 위한 실무 제언

- 주기적 AWR / ASH 성능 진단 보고서 분석 : Oracle AWR, MySQL Performance Schema를 통해 시스템 대기 이벤트(Wait Event - `db file sequential read`, `latch: cache buffers chains`)를 주 단위로 모니터링하여 병목 Top-10 SQL을 지속적으로 격리 튜닝해야 함.
- 옵티마이저 통계정보(Statistics) 최신성 보장 : 옵티마이저가 최적의 실행 계획을 수립하지 못하는 가장 흔한 원인은 오래되거나 누락된 통계정보 때문이므로, 야간 배치 시간대에 `DBMS_STATS.GATHER_TABLE_STATS`를 자동화하고 데이터 변경율이 높은 테이블을 상시 식별할 것을 제언함.
