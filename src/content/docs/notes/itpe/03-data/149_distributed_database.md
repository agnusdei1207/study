## 연관 키워드

- 분산 데이터베이스, Distributed Database
- 분할, 할당, 복제, 투명성
- 2단계 커밋(2PC), CAP 정리, 수평 확장, 단일 장애점

## Ⅰ. 분산 데이터베이스의 개요

- 핵심 요약 : 물리적으로 분산된 노드를 논리적으로 단일 데이터베이스처럼 운영하는 분산 데이터 관리 체계.
- 개념 : 지리적으로 떨어진 네트워크 노드에 배치된 여러 **분산 데이터베이스**(Distributed Database)가 통신 네트워크로 연결되어, 사용자에게는 하나의 데이터베이스처럼 통합된 서비스를 제공하는 시스템.
- 배경 및 필요성 : 단일 대형 서버의 수직 확장(Scale-Up) 한계와 **단일 장애점**(SPOF, Single Point of Failure) 리스크를 극복하고, 글로벌 서비스에서 지리적 접근성을 확보할 필요.
- 주요 목적 : 데이터 분할·복제·투명성 설계를 통한 수평 확장(Scale-Out) 체계 구축과 분산 트랜잭션의 원자성 보장.

## Ⅱ. 분산 데이터베이스의 특징 및 장점

- 핵심 요약 : 분할, 할당, 복제, 투명성의 4대 설계 영역과 분산 트랜잭션 프로토콜이 결합된 운영 체계.

1. **분할** (Fragmentation) : 릴레이션을 수평·수직·혼합 방식으로 조각(Fragment)에 나눔 → 데이터를 노드별로 나누어 처리.
2. **할당** (Allocation) : 조각을 어느 노드에 배치할지 정하는 정책 → 접근이 많은 곳에 데이터를 가깝게 배치.
3. **복제** (Replication) : 동일 조각의 사본을 여러 노드에 보관 → 노드 장애 시에도 서비스 지속.
4. **투명성** (Transparency) : 분할, 위치, 복제 사실을 애플리케이션에서 숨김 → 단일 시스템처럼 사용.
5. **2단계 커밋** (2PC, Two-Phase Commit) : 준비 단계와 커밋 단계로 여러 노드의 원자성 보장 → 부분 반영 방지.

## Ⅲ. 분산 데이터베이스의 구조 (흐름)

- 핵심 요약 : 4대 설계 영역의 구조와, 2PC 기반 분산 트랜잭션이 준비 단계를 거쳐 전 노드에 커밋되는 흐름.

```text
[ 분산 설계 4대 영역 ]

분할 : 릴레이션을 조각(Fragment)으로 나눔
   ↓
할당 : 조각을 노드 서버에 배치
   ↓
복제 : 조각 사본을 여러 노드에 보관
   ↓
투명성 : 분할·위치·복제를 애플리케이션에서 은닉
```

```text
[ 2단계 커밋(2PC) 동작 흐름 ]

조정자 : Prepare 메시지 전송
   ↓
참여자 : 준비 완료(Vote-Commit) 응답
   ↓
조정자 : 모든 참여자 준비 완료 확인
   ↓
조정자 : Global-Commit 브로드캐스트
   ↓
참여자 : ACK 응답 후 트랜잭션 종료
```

- 릴레이션 분할 유형의 비교는 다음 표와 같다.

| 분할 유형 | 분할 기준 | 재구성 연산 | 장점과 고려 사항 |
| --- | --- | --- | --- |
| 수평 분할(Horizontal) | 조건절로 행(Tuple)을 나눔 | 합집합(Union) | 지역별·기간별 독립 처리에 적합, 전체 집계 시 네트워크 비용 발생 |
| 수직 분할(Vertical) | 속성(Column)을 나눔, PK는 모든 조각에 포함 | 자연 조인(Natural Join) | 자주 쓰는 컬럼 집중, 조인 비용 발생 |
| 혼합 분할(Hybrid) | 수평과 수직 분할을 다단계로 적용 | 합집합 후 조인 | 정밀한 데이터 지역성 확보, 트랜잭션 관리 복잡도 증가 |

## Ⅳ. 분산 데이터베이스와 중앙 집중식 데이터베이스의 비교

- 핵심 요약 : 단일 노드 중심의 중앙 집중식 구조와 다중 노드 분산 구조의 확장성, 장애, 일관성 차이.

| 비교 항목 | 중앙 집중식 DB | 분산 데이터베이스 |
| --- | --- | --- |
| 데이터 배치 | 단일 서버에 집중 저장 | 다수 노드에 분산 저장과 복제 |
| 확장 방식 | 수직 확장(Scale-Up) | 수평 확장(Scale-Out) |
| 장애 영향 | 단일 장애점으로 전체 중단 | 부분 장애 시에도 서비스 지속 가능 |
| 트랜잭션 관리 | 로컬 트랜잭션으로 단순 처리 | 2PC 등 분산 트랜잭션 프로토콜 필요 |
| 데이터 일관성 | 강한 일관성 보장이 용이 | **CAP**(Consistency, Availability, Partition Tolerance) 정리에 따른 트레이드오프 |
| 네트워크 의존성 | 낮음 | 높음, 지연과 파티션 리스크 존재 |

## Ⅴ. 분산 데이터베이스의 한계와 방안

- 핵심 요약 : 2PC의 블로킹, 노드 간 시계 불일치, 네트워크 파티션 시 일관성과 가용성의 트레이드오프를 한계로 보고, 각각 대체 패턴과 합의·시계 기법으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 2PC의 블로킹 | 코디네이터 장애 시 참여 노드가 락을 쥔 채 대기 | Raft·Paxos 기반 복제, 마이크로서비스에서는 **사가**(Saga) 패턴과 TCC(Try-Confirm-Cancel) 패턴 적용 | 트랜잭션 대기 시간 |
| 노드 간 시계 불일치 | NTP(Network Time Protocol) 시계 드리프트로 커밋 순서 판별 왜곡 | 원자시계와 GPS를 결합한 **트루타임**(TrueTime) 방식, **HLC**(Hybrid Logical Clock) 또는 벡터 클록(Vector Clock) 도입 | 시계 오차 범위 |
| 파티션 시 CP와 AP의 선택 | 쓰기를 거부하면 중단, 허용하면 데이터 불일치와 **스플릿 브레인**(Split Brain) 발생 | 정족수(Quorum) 설정(W + R > N), CRDT(Conflict-Free Replicated Data Type) 적용, 도메인별 CP·AP 분리 | 충돌 해소 건수 |

## Ⅵ. 분산 데이터베이스에 대한 기술사적 제언

- 핵심 요약 : 하이브리드 논리 시계 기반의 순서 보장, 분산 조인 최소화, 도메인별 일관성 등급 분리를 함께 설계하는 방향이 바람직함.
- 다중 데이터센터 환경에서 트랜잭션의 순서를 일관되게 보장하려면, 물리 시계 대신 HLC를 기준 시계로 채택하는 것을 검토할 필요가 있다. 원자시계 기반 트루타임은 전용 인프라가 필요하므로, 범용 환경에서는 HLC가 현실적인 대안이다.
- 서로 다른 노드에 놓인 테이블 간 조인은 네트워크 셔플 비용이 크므로, 외래키로 연결된 자식 테이블을 부모 테이블과 같은 파티션에 함께 두는 **인터리브드 테이블**(Interleaved Table, 공동 배치) 설계를 우선 검토하는 것이 바람직하다.
- 금융 원장처럼 강한 일관성이 필요한 도메인과 추천·로그처럼 가용성이 중요한 도메인을 나누어 각각 CP와 AP 계열로 운영하면, 전사 단일 정책에 따른 과잉 설계를 피할 수 있다.

## Ⅶ. 결론

- 핵심 요약 : 분산 데이터베이스는 수평 확장과 고가용성을 얻는 대신, 일관성 제어의 복잡도를 감수하는 아키텍처.
- 분할·복제·투명성 설계와 분산 트랜잭션 프로토콜을 함께 설계할 때 그 장점이 실현되므로, 도메인별 일관성 등급을 먼저 정의하는 것이 출발점이 된다.
