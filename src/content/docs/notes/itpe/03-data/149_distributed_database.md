## Ⅰ. 대규모 클라우드 환경을 위한 분산 데이터베이스의 개요

### 가. 분산 데이터베이스(Distributed Database)의 정의
- 물리적으로 서로 다른 지리적 위치나 네트워크 노드에 분산 배치된 여러 개의 데이터베이스 시스템들이 통신 네트워크로 상호 연결되어 있으면서도, 논리적으로는 단일한 하나의 데이터베이스 시스템처럼 사용자에게 통합된 데이터 서비스를 제공하는 시스템.

### 나. 전통적 중앙 집중식 DB 대비 분산 DB의 등장 배경
- 단일 대형 서버의 수직 확장(Scale-Up) 한계 및 단일 장애점(SPOF) 리스크 극복.
- 글로벌 서비스 환경에서 지리적 접근성을 통한 데이터 전송 지연 시간(Latency) 단축.

## Ⅱ. 분산 데이터베이스의 4대 핵심 분산 설계 전략

```text
[ 분산 설계 4대 영역 ]
1. 분할 (Fragmentation) : 단일 릴레이션을 여러 작은 조각(Fragment)으로 나눔 (수평, 수직, 혼합)
2. 할당 (Allocation)     : 쪼개진 조각들을 어느 물리적 노드 서버에 배치할 것인가 결정
3. 복제 (Replication)    : 데이터 가용성을 위해 동일 조각 사본을 여러 노드에 동시 보관
4. 투명성 (Transparency) : 분할, 위치, 복제 사실을 애플리케이션으로부터 완벽 은닉
```

### 가. 릴레이션 분할의 3대 유형 비교

| 분할 유형 | 분할 기준 및 메커니즘 | 재구성 복원 연산 | 장점 및 고려사항 |
| :--- | :--- | :--- | :--- |
| **수평 분할 (Horizontal)** | 특정 조건절(`WHERE`)을 기준으로 행(Tuple)들을 분할 | **합집합 (Union: $\cup$)** | 지역별/기간별 독립 처리에 최적, 전수 조사 시 네트워크 집계 필요 |
| **수직 분할 (Vertical)** | 속성(Column)들을 기준으로 분할 (단, PK는 모든 조각에 필수 포함) | **자연 조인 (Natural Join: $\bowtie$)** | 자주 접근하는 핵심 컬럼의 메모리 캐시 적중률 극대화, 조인 비용 발생 |
| **혼합 분할 (Hybrid)** | 수평 분할과 수직 분할을 다단계로 교차 적용 | 합집합 후 조인 | 정밀한 데이터 로컬리티 달성, 분산 트랜잭션 관리 복잡도 극상 |

## Ⅲ. 분산 트랜잭션 원자성 보장: 2단계 커밋(2PC) 프로토콜

```text
[ 2단계 커밋 (2PC, Two-Phase Commit) 동작 흐름 ]
[조정자 (Coordinator)]                [참여자 1 (Participant)]   [참여자 2 (Participant)]
------------------------------------------------------------------------------------------
(Phase 1: 준비 단계)
   --- Prepare(준비) 메시지 전송 --->
                                      --- Vote-Commit(준비 완료) 응답 --->
                                      --- Vote-Commit(준비 완료) 응답 --->
(Phase 2: 커밋 단계)
   [모든 참여자 성공 확인!]
   --- Global-Commit 메시지 브로드캐스트 --->
                                      --- ACK (적용 완료) 응답 --->
                                      --- ACK (적용 완료) 응답 --->
   [트랜잭션 완전 종료]
```

### 나. 2PC의 치명적 한계: 블로킹(Blocking) 문제
- 준비 단계(Phase 1) 완료 후 조정자가 장애로 다운되면, 참여자들은 자원에 락(Lock)을 건 채 무한정 대기(Blocking) 상태에 빠져 시스템 전체가 정지됨 $\rightarrow$ Raft/Paxos 기반의 3PC 또는 합의 분산 DB로 진화.

## Ⅳ. 분산 데이터베이스의 주요 한계점 및 해결 방안

- **2단계 커밋(2PC)의 블로킹 메커니즘과 가용성 저하** :
  - **한계점** : 분산 트랜잭션 수행 중 코디네이터 노드가 장애를 일으키면 모든 참여 노드가 락을 보유한 채 대기 상태에 빠져 시스템 전체 중단(Hang) 발생.
  - **해결 방안** : Raft/Paxos 합의 알고리즘 기반 복제 적용, 마이크로서비스 간에는 2PC 대신 사가(Saga) 패턴(보상 트랜잭션) 및 TCC(Try-Confirm-Cancel) 패턴 적용.
- **분산 노드 간 물리적 시계 불일치로 인한 이벤트 순서화(Ordering) 오류** :
  - **한계점** : 개별 서버의 NTP 시계 드리프트(Clock Drift)로 인해 분산 트랜잭션의 커밋 순서 판별이 왜곡되어 스냅샷 격리성 파괴 및 데이터 덮어쓰기 발생.
  - **해결 방안** : 구글 트루타임(TrueTime: GPS + 원자시계 결합) API 활용, 또는 논리적 인과관계를 보장하는 HLC(Hybrid Logical Clock) 및 벡터 클록(Vector Clock) 도입.
- **네트워크 파티션 발생 시 일관성(CP)과 가용성(AP)의 불가피한 트레이드오프** :
  - **한계점** : 노드 간 네트워크 단절 시 쓰기를 거부하여 비즈니스 중단이 발생하거나, 쓰기를 허용하여 데이터 불일치 및 스플릿 브레인 초래.
  - **해결 방안** : 정족수(Quorum) 기반 쓰기/읽기 설정(W + R > N), 충돌 없는 복제 데이터 타입(CRDT) 적용, 도메인 중요도별 CP/AP 이원화 아키텍처 수립.

## Ⅴ. 차세대 분산 데이터베이스(NewSQL) 구축을 위한 실무 제언

- **글로벌 정렬을 위한 하이브리드 논리 시계(HLC) 채택** : 지리적으로 분산된 다중 데이터센터 간 트랜잭션의 엄격한 직렬성(Strict Serializability)을 보장하기 위해, 원자시계가 필요한 Google TrueTime의 대안으로 NTP 오차를 논리 시계로 보정하는 **HLC(Hybrid Logical Clock - CockroachDB 방식)** 를 표준으로 검토해야 함.
- **분산 조인의 네트워크 셔플(Shuffle) 최소화** : 분산 DB에서 서로 다른 노드에 위치한 테이블 간 조인은 막대한 네트워크 대역폭을 고갈시키므로, 외래키 관계의 자식 테이블을 부모 테이블과 동일한 물리 노드 파티션에 함께 묶어 저장하는 **인터리브드 테이블(Interleaved Table / Colocation)** 설계를 적용할 것을 제언함.
