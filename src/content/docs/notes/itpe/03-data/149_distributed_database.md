## 핵심 그림
```text
[분산 데이터베이스 5대 투명성 및 분산 트랜잭션 처리(2PC) 구조]

  [사용자/응용 프로그램] (단일 DB로 인식: 5대 투명성)
           │
  ┌────────▼────────────────────────────────────────────────────────┐
  │ 분산 트랜잭션 코디네이터 (Coordinator)                          │
  │  - 위치 투명성 (Location)  : 데이터의 물리적 저장 위치 은닉      │
  │  - 분할 투명성 (Division)  : 수평/수직 분할 사실 은닉           │
  │  - 복제 투명성 (Replication): 여러 노드에 사본 존재 은닉        │
  │  - 병행 투명성 (Concurrency): 다중 분산 트랜잭션 간섭 배제       │
  │  - 장애 투명성 (Failure)    : 특정 사이트 고장 시에도 동작 유지 │
  └────────┬──────────────────────┬──────────────────────┬──────────┘
           │ 2PC: Prepare / Commit │                      │
  ┌────────▼─────────┐   ┌────────▼─────────┐   ┌────────▼─────────┐
  │  로컬 노드 A     │   │  로컬 노드 B     │   │  로컬 노드 C     │
  │  (서울 데이터)   │   │  (도쿄 데이터)   │   │  (싱가포르)      │
  └──────────────────┘   └──────────────────┘   └──────────────────┘
```

## 핵심 용어
- 5대 투명성(Transparency): 위치(Location), 분할(Division/Fragmentation), 복제(Replication), 병행(Concurrency), 장애(Failure) 투명성으로 구성된 분산 시스템의 사용자 편의성 보장 원칙
- 2단계 커밋(2PC, Two-Phase Commit): 분산 트랜잭션에 참여하는 모든 노드가 변경 사항을 영구 반영하기 위해 준비(Prepare) 단계와 실행(Commit) 단계를 거쳐 원자성을 보장하는 프로토콜

## 핵심 통찰
- 분산 DB의 가장 큰 적은 '네트워크 지연과 부분 실패(Partial Failure)'임 → 3개 노드 중 2개는 성공하고 1개만 타임아웃이 났을 때 전체 시스템을 어떻게 롤백할 것인가가 분산 트랜잭션의 본질
- 2PC는 '코디네이터가 1단계 준비를 마치고 2단계 커밋을 지시하기 직전에 사망하면, 모든 로컬 노드가 락을 쥔 채 무한정 멈춰버리는(Blocking)' 치명적 결함이 있음
- 현대 마이크로서비스(MSA)와 글로벌 분산 DB(Google Spanner, CockroachDB)에서는 2PC 대신 Raft/Paxos 같은 분산 합의 알고리즘을 도입하거나, 최종 일관성 기반의 사가(Saga) 패턴으로 격리 수준을 완화하는 것이 대세

## 이웃 토픽과 구분
- 분산 DB vs 분산 파일 시스템(HDFS): 분산 DB = 테이블 스키마, 인덱스, 5대 투명성, 2PC 기반 ACID 트랜잭션을 엄격히 보장 / 분산 파일 시스템 = 트랜잭션 없이 단순히 대용량 파일 블록을 여러 머신에 쪼개어 복제 보관(배치 분석 최적화)

## 문제·원인·대책
- 적용 상황: 글로벌 핀테크 서비스의 해외 거점 간 분산 트랜잭션 정합성 보장
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 트랜잭션 중 네트워크 일시 순단 시 2PC 코디네이터의 응답 대기로 모든 참여 노드 DB 커넥션 풀 고갈 | 2PC의 동기식 블로킹(Blocking) 메커니즘 특성 | 코디네이터 타임아웃 자동 판정과 비동기 보상 트랜잭션(Saga Orchestration) 도입 | 시스템 데드락 방지 및 가용성 99.99% 복원 |
| 지역별 노드 간 시계(Clock) 불일치로 분산 트랜잭션의 선후 관계(Serialization) 왜곡 | 각 서버의 NTP(Network Time Protocol) 동기화 오차(수십 ms) | GPS와 원자시계를 결합한 구글의 TrueTime API 또는 논리적 HLC(Hybrid Logical Clock) 도입 | 전 세계 분산 트랜잭션의 엄밀한 외부 일관성(External Consistency) 보장 |

## 내 의견
- [단일 글로벌 분산 트랜잭션의 오버헤드 경계] 마이크로서비스 아키텍처에서 모든 서비스 간 통신을 2PC 분산 트랜잭션으로 묶으려다 전체 시스템 처리량이 1/100로 급락하는 설계 실패 빈발 → 나라면: 금융 계좌 등 필수 구간에만 분산 합의(Raft) 기반 NewSQL을 국소 적용하고, 일반 주문-배송-알림 업무는 Kafka 이벤트 기반의 최종 일관성(Eventual Consistency) 및 사가(Saga) 패턴을 전사 표준으로 채택
