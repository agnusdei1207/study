## 답안 골격
```text
[데이터베이스 (Database)] ◀━━ 머리: Ⅶ 내 의견 (단일 모놀리식 DB 탈피 및 도메인 요구에 맞춘 폴리글랏 지속성(Polyglot) 설계)
 ┃
 ┣━ Ⅰ 개요 ───── 특정 조직의 업무를 수행하기 위해 여러 사용자와 응용 프로그램이 공동으로 소유하고 유지하는 통합·저장·운영·공용 데이터의 집합
 ┣━ Ⅱ 특징 ───── 4대 특성(실시간 접근성, 계속적인 변화, 동시 공유, 내용에 의한 참조) · 데이터 독립성(논리적/물리적) · 무결성 및 일관성
 ┣━ Ⅲ 구조 ───── ANSI/SPARC 3단계 계층: 외부 스키마(사용자 관점) / 개념 스키마(전체 논리 구조) / 내부 스키마(물리 저장 구조)
 ┣━ Ⅳ 흐름 ───── ① 응용 프로그램 질의 요청 → ② 외부/개념 사상(매핑) → ③ 개념/내부 사상 → ④ DBMS 엔진 버퍼 캐시 및 디스크 I/O → ⑤ 결과 반환
 ┣━ Ⅴ 비교 ───── 파일 시스템 vs RDBMS vs NoSQL vs NewSQL
 ┗━ Ⅵ 실무 ───── 데이터 종속성과 중복성으로 인한 이상현상 / 단일 중앙 DB에 모든 부하가 집중되는 확장성 한계
```
- 필수 키워드: 데이터베이스 · 통합 데이터 · 저장 데이터 · 운영 데이터 · 공용 데이터 · ANSI/SPARC 3단계 · 데이터 독립성 · DBMS · 폴리글랏 지속성
- 기출: 130회 `데이터베이스(Database)의 정의, 4대 기본 특성 및 ANSI/SPARC 3단계 데이터베이스 구조와 데이터 독립성을 설명하시오.` → Ⅰ 정의 + Ⅱ 4대 특성 + Ⅲ ANSI/SPARC 구조 + Ⅳ 논리적/물리적 독립성

## 한 줄 본질
- 파일 시스템의 극심한 데이터 중복과 응용 프로그램 종속성 문제 해결 필요 → 데이터를 중앙 집중식으로 통합하고 3단계 스키마(외부-개념-내부)로 추상화하여 관리 → 데이터 독립성과 무결성 보장 / DBMS 도입 비용 및 시스템 복잡도 증가

## 핵심 그림
```text
[ANSI/SPARC 3단계 데이터베이스 스키마 구조 및 데이터 독립성]

  [사용자 계층]      응용 1 (화면 A)       응용 2 (화면 B)       응용 3 (보고서)
                           │                    │                    │
  [외부 스키마]       외부 스키마 1        외부 스키마 2        외부 스키마 3
                           └────────────────────┼────────────────────┘
                                                │ ◄── 논리적 데이터 독립성
  [개념 스키마]                           개념 스키마 (전사 논리 모델)
                                                │ (전체 테이블, 제약조건, 관계)
                                                │ ◄── 물리적 데이터 독립성
  [내부 스키마]                           내부 스키마 (물리 저장 구조)
                                                │ (인덱스, 블록, 테이블스페이스)
                                                ▼
  [물리 계층]                         물리적 데이터베이스 (디스크)
```

## 핵심 용어
- 논리적 데이터 독립성: 개념 스키마(테이블 컬럼 추가 등)가 변경되더라도 외부 스키마(응용 프로그램 뷰)는 영향을 받지 않고 그대로 유지되는 성질
- 물리적 데이터 독립성: 내부 스키마(디스크 구조, 인덱스 추가, 파일 경로 변경 등)가 변경되더라도 개념 스키마 및 응용 프로그램이 영향을 받지 않는 성질

## 핵심 통찰
- 데이터베이스의 본질은 '데이터를 저장하는 소프트웨어'가 아니라 '데이터와 응용 프로그램을 논리적·물리적으로 완전히 떼어놓는(Decoupling) 추상화 계층'임
- 파일 시스템으로 데이터를 관리하면, 고객 테이블에 '이메일' 컬럼 하나 추가할 때 그 파일을 읽는 수백 개의 C/자바 소스코드를 모조리 다시 컴파일하고 배포해야 하는 재앙 발생
- 현대의 데이터베이스 아키텍처는 하나의 거대한 RDBMS로 모든 것을 해결하려던 시대에서 벗어나, 관계형(RDB), 문서형(Doc), 캐시(In-memory), 벡터(Vector)를 용도별로 조합하는 폴리글랏 지속성(Polyglot Persistence)으로 진화

## 이웃 토픽과 구분
- 데이터베이스 vs DBMS: 데이터베이스 = 구조화되어 저장된 '데이터 자체의 집합(내용물)' / DBMS = 데이터베이스를 생성, 관리, 조작, 보안 통제하는 '소프트웨어 엔진(컨테이너 및 도구)'

## 문제·원인·대책
- 적용 상황: 수십 년간 누적된 레거시 파일 기반 고객 시스템의 DBMS 전면 전환
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 영업부 파일과 배송부 파일 간 고객 주소가 서로 달라 오배송 및 클레임 속출 | 동일 데이터가 부서별 파일에 중복 저장되어 동기화 불일치 | ANSI/SPARC 3단계 구조의 RDBMS로 통합하고 개념 스키마 단일화 | 데이터 중복 제거 및 무결성 100% 확보 |
| 디스크 성능 향상을 위해 SSD로 스토리지를 교체하자 기존 애플리케이션 I/O 에러 | 물리적 스토리지 의존적인 하드코딩 파일 I/O 로직 | DBMS의 내부 스키마(테이블스페이스) 추상화 계층 적용 | 물리 하드웨어 변경에도 응용 프로그램 소스코드 무수정 보존 |

## 이렇게 출제된다
- 제130회: "데이터베이스(Database)의 4대 특성과 ANSI/SPARC 3단계 구조를 기술하고, 논리적 데이터 독립성과 물리적 데이터 독립성을 비교 설명하시오." → 요구 포인트: 데이터베이스 정의(통합, 저장, 운영, 공용) + 4대 특성 + 3단계 스키마 구조도 + 2단계 데이터 독립성 매핑

## 내 의견
- [RDBMS 만능주의 맹신 지양] 데이터베이스를 도입할 때 모든 시스템 요구사항을 Oracle이나 MySQL 하나에만 몰아넣어 초당 수십만 트랜잭션 환경에서 병목을 일으키는 아키텍처 결함 빈발 → 나라면: 도메인 주도 설계(DDD)를 기반으로 트랜잭션 ACID가 필수인 결제는 RDBMS, 고속 세션 및 캐시는 Redis, 비정형 로그는 Document DB로 분리 배치하는 폴리글랏 지속성(Polyglot Persistence) 원칙을 전사 아키텍처로 수립

## 찾아볼 것
- 클라우드 네이티브 환경에서 컴퓨팅 엔진과 스토리지를 완전히 분리하여 무한 확장을 지원하는 NewSQL(Google Spanner, CockroachDB) 아키텍처
