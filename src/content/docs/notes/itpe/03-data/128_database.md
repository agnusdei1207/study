## 연관 키워드

- 데이터베이스

## Ⅰ. 데이터베이스(Database)의 개요

- 핵심 요약 : 특정 조직의 고유 업무 수행에 필요한 상호 관련된 데이터를 통합·저장·운영·공유되도록 구조화한 영속적 데이터 저장소
- 개념 : 데이터베이스(Database)는 복수의 응용 시스템과 다수의 사용자가 상호 공유하여 사용할 수 있도록 구조화하여 통합(Integrated), 저장(Stored), 운영(Operational), 공유(Shared)되는 상호 관련된 데이터 집합체
- 배경 : 파일 시스템 기반 데이터 관리는 데이터 중복, 종속성, 불일치 등의 문제를 야기하여 데이터 관리 비용과 오류 가능성 증가
- 필요성 : 조직 전체 데이터의 일관성, 무결성, 보안성, 동시성 제어를 체계적으로 보장하는 통합 관리 체계 필요
- 주요 목적 : 데이터 중복 최소화, 데이터 독립성 보장, 동시 공유 접근 제공, 데이터 무결성 및 보안성 유지

```text
[ 데이터베이스 4대 본질 특성 (ISOS) ]
1. 통합된 데이터 (Integrated Data)   : 동일 데이터의 불필요한 중복(Redundancy)을 원천 배제
2. 저장된 데이터 (Stored Data)       : 컴퓨터가 접근 가능한 디지털 저장 매체에 영속 저장
3. 운영 데이터 (Operational Data)    : 조직의 고유 업무를 정상 수행하기 위해 반드시 필요한 데이터
4. 공용 데이터 (Shared Data)         : 여러 사용자와 다양한 응용 프로그램이 동시 공유 접근
```

## Ⅱ. 데이터베이스(Database)의 특징

- 핵심 요약 : 데이터 독립성 보장, 동시성 제어, 장애 회복, 보안성 등 파일 시스템과 구별되는 체계적 관리 특성 보유
- 특징 1 : 데이터 독립성 — 물리적 데이터 독립성(디스크 구조 변경 시 논리 구조 무영향)과 논리적 데이터 독립성(개념 스키마 변경 시 외부 스키마 무영향)을 모두 보장하는 3단계 추상화 아키텍처(ANSI/SPARC) 제공
- 특징 2 : 동시성 제어 — 다수 사용자 트랜잭션이 동시에 실행되더라도 데이터 일관성을 유지하도록 락(Lock), MVCC(Multi-Version Concurrency Control) 등의 메커니즘 제공
- 특징 3 : 장애 회복 — ACID(Atomicity, Consistency, Isolation, Durability) 속성 보장을 통해 트랜잭션 원자성, 일관성, 고립성, 영속성 확보
- 특징 4 : 보안성 — 사용자 인증, 권한 기반 접근 제어(RBAC, Role-Based Access Control), 암호화 등의 다층적 보안 체계 제공

```text
[ ANSI/SPARC 3단계 계층 구조 ]
[사용자 1 뷰]        [사용자 2 뷰]        [사용자 3 뷰]  <--- [외부 스키마 (External Schema)]
      \                   |                   /
       +------------------+------------------+
                          | (논리적 데이터 독립성: 개념 스키마 변경 시 외부 스키마 무영향)
                          v
                [개념 스키마 (Conceptual Schema)]      <--- 전사 통합 논리 뷰 (ERD, 테이블 구조)
                          |
                          | (물리적 데이터 독립성: 디스크 구조 변경 시 개념 스키마 무영향)
                          v
                [내부 스키마 (Internal Schema)]        <--- 물리적 저장 뷰 (인덱스, 파티션, 블록)
```

## Ⅲ. 데이터베이스의 구조 (흐름)

- 핵심 요약 : 외부-개념-내부 3단계 스키마 계층 구조를 기반으로 사용자 뷰부터 물리적 저장 구조까지 단계적 추상화 제공

```text
[ 데이터베이스 시스템 처리 흐름 ]
[응용 프로그램] --> [외부 스키마: 사용자별 뷰]
                          |
                          v
                   [개념 스키마: 전체 논리 구조]
                          |
                          v
                   [내부 스키마: 물리적 저장 구조]
                          |
                          v
                   [디스크 저장 매체: 파일, 블록, 페이지]
```

```text
[ DBMS 내부 모듈 구조 ]
[쿼리 프로세서] --> [옵티마이저] --> [실행 엔진]
                                       |
[버퍼 매니저] <----> [스토리지 매니저] <----> [디스크]
       |                    |
       v                    v
[�시 메모리]          [파일 & 인덱스]
```

- 개념 스키마는 전사 데이터의 논리적 구조를 정의하는 단계로, ERD(Entity-Relation Diagram)와 테이블 구조로 표현
- 내부 스키마는 물리적 저장 구조를 정의하는 단계로, 인덱스, 파티션, 블록 단위 관리

## Ⅳ. 파일 시스템과의 비교

- 핵심 요약 : 파일 시스템 대비 DBMS는 데이터 중복 제거, 독립성 보장, 동시성 제어, 장애 회복 등 체계적 관리 능력 우위

| 비교 항목 | 파일 시스템 | 데이터베이스 관리 시스템(DBMS) |
| :--- | :--- | :--- |
| **데이터 중복** | 부서별 중복 저장으로 일관성 훼손 | 단일 저장 지점으로 중복 배제 및 일관성 유지 |
| **데이터 독립성** | 파일 구조 변경 시 응용 프로그램 수정 필요 | 3단계 스키마로 독립성 보장 |
| **동시성 제어** | 파일 단위 락으로 동시 접근 제어 제한적 | 트랜잭션 단위 세밀한 동시성 제어 |
| **장애 회복** | 백업/복원에 의존, 시점 복구 어려움 | 로그 기반 회복, 시점 복구(Point-in-time Recovery) 가능 |
| **보안** | OS 수준 파일 권한만 제공 | 테이블/컬럼 단위 세분화된 접근 제어 제공 |
| **질의 언어** | 없음(응용 프로그램 코드로 처리) | SQL(Structured Query Language) 선언적 질의 제공 |

## Ⅴ. 데이터베이스(Database)의 장점과 한계

- 핵심 요약 : 데이터 일관성과 보안성이 우수하지만 단일 노드 확장성 한계와 객체-관계 임피던스 불일치 존재
- 장점 :
  1. 데이터 일관성 및 무결성 보장 — 중복 최소화와 제약 조건을 통한 정합성 유지
  2. 데이터 독립성 — 응용 프로그램과 저장 구조의 결합도 완화
  3. 동시 공유 접근 — 다수 사용자 및 응용 프로그램의 동시 접근 지원
  4. 장애 회복 및 보안 — 트랜잭션 로그 기반 회복과 세분화된 접근 제어
- 한계점 :
  1. 단일 노드 수직 확장(Scale-up) 한계 — 초대규모 데이터 환경에서 하드웨어 스펙 한계 도달
     - 해결 방안 : 샤딩(Sharding), 분산 SQL 데이터베이스(NewSQL: Spanner, TiDB)로의 전환, CQRS(Command Query Responsibility Segregation) 기반 읽기/쓰기 분리
  2. 임피던스 불일치(Object-Relational Impedance Mismatch) — 객체지향 모델과 관계형 모델 간 불일치
     - 해결 방안 : 도메인 주도 설계(DDD, Domain-Driven Design) 기반 바운디드 컨텍스트 수립, 폴리그랏 퍼시스턴스(Polyglot Persistence) 적용
  3. 스키마 침식 및 기술 부채 누적 — 빠른 서비스 출시로 비정규화, 미사용 레거시 테이블 방치
     - 해결 방안 : 전사 메타데이터 관리 시스템(MDR, Metadata Repository) 및 데이터 카탈로그 정례화, 데이터 계보(Lineage) 추적 도구 도입

## Ⅵ. 데이터베이스에 대한 기술사적 제언

- 핵심 요약 : 다중 저장소 전략 기본화와 클라우드 네이티브 전환을 통한 현대 데이터 아키텍처 구축 필요
- 제언 1 : 다중 저장소(Polyglot Persistence) 전략의 기본화 — 모든 워크로드를 단일 RDBMS(Relational Database Management System)에 우겨넣는 아키텍처는 성능 병목을 유발하므로, 트랜잭션은 PostgreSQL, 고속 세션 캐싱은 Redis, 전문 검색은 Elasticsearch, AI(Artificial Intelligence) 벡터는 Milvus로 용도에 맞게 분리 필요
- 제언 2 : 클라우드 완전관리형(PaaS, Platform as a Service) DB로의 전환 가속화 — 온프레미스 인스턴스 설치·운영에 소모되는 엔지니어링 리소스를 절감하고, 자동 백업, Multi-AZ 페일오버, 자동 스케일링을 제공하는 클라우드 네이티브 데이터베이스 우선 검토 필요

```text
[ 현대 다중 저장소 아키텍처 ]
[트랜잭션 처리] --> [PostgreSQL / MySQL]
[고속 캐싱]     --> [Redis / Memcached]
[전문 검색]     --> [Elasticsearch]
[AI 벡터 검색] --> [Milvus / Qdrant]
[문서 저장]     --> [MongoDB]
```

## Ⅶ. 결론

- 핵심 요약 : 데이터베이스는 조직 데이터의 통합적 관리와 일관성 보장의 핵심 인프라이며, 다중 저장소 전략과 클라우드 전환으로 진화 중
- 요약 : 데이터베이스는 파일 시스템의 한계를 극복하기 위해 데이터 독립성, 동시성 제어, 장애 회복, 보안성을 체계적으로 제공하는 영속적 데이터 저장소이며, 3단계 추상화 아키텍처를 통해 논리적·물리적 독립성을 동시에 달성
- 시사점 : 현대 엔터프라이즈 환경에서는 단일 DBMS로 모든 워크로드를 커버하기 어렵므로, 워크로드 특성에 맞는 다중 저장소 전략과 클라우드 네이티브 데이터베이스 도입이 필요하며, 메타데이터 관리와 데이터 거버넌체 체계 구축이 데이터 자산화의 핵심 과제
