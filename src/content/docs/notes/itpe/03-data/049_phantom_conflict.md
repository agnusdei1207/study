## 30초 인출

- 본질: 팬텀 충돌(팬텀 읽기)은 같은 검색 조건의 반복 조회에서 다른 트랜잭션이 커밋한 삽입·삭제 때문에 결과 집합이 달라지는 현상
- 메커니즘: T1이 조건으로 범위를 조회한 뒤 T2가 조건에 맞는 행을 삽입·커밋하면 T1의 재조회에 새 행이 나타나며, DBMS는 간격 잠금·직렬화 충돌 감지·스냅샷 등으로 이를 막음
- 통찰: 기존 행의 값은 그대로여도 집합이 바뀌므로 행 단위 잠금만으로는 막지 못하고, 보호 방식이 DBMS와 격리 수준마다 달라 동시 삽입 시나리오로 직접 검증해야 함

<details>
<summary>핵심 용어</summary>

- **팬텀 읽기(Phantom Read)** : 같은 조건의 재조회에서 행 집합이 달라지는 현상
- **술어(Predicate)** : 조회 조건(예: id > 100)
- **넥스트키 잠금(Next-Key Lock)** : 인덱스 레코드와 앞 간격을 함께 잠그는 방식(MySQL InnoDB)
- **직렬화 충돌 감지** : 읽은 조건과 충돌하는 쓰기를 추적해 위험한 실행을 취소하는 방식(PostgreSQL SSI)
- **스냅샷 격리** : 트랜잭션이 같은 시점의 데이터 버전을 읽게 하는 방식
- **직렬화 이상** : 동시 실행 결과가 어떤 직렬 실행과도 같지 않은 현상

</details>

## 2~4교시 25점 답안

## Ⅰ. 팬텀 충돌의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **팬텀 충돌** 은 같은 조건의 반복 조회에서 다른 트랜잭션의 커밋으로 결과 집합이 달라지는 현상 |
| 목적 | 범위 조회와 동시 쓰기 사이의 일관성 요구를 식별하고 적절한 격리·충돌 처리 선택 |

## Ⅱ. 특징

| 특징 | 확인 조건 |
|---|---|
| 집합 변화 | 기존 행 값이 그대로여도 조건에 맞는 행이 삽입·삭제 |
| 반복 술어 조회 | 같은 트랜잭션에서 같은 조건의 결과를 비교 |
| 구현 의존 | 격리 수준·스냅샷·인덱스 접근에 따라 관찰·방지 방식 변화 |

## Ⅲ. 발생 흐름

```text
T1: 조건 id > 100 조회 → 결과 집합 기록
              ↓ T1 종료 전
T2: id = 101 행 삽입·커밋
              ↓
T1: 같은 조건 재조회 → 새 행 포함 = 팬텀
```

## Ⅳ. DBMS별 방지 기법

| 기법 | 예시 구현 | 동작과 제한 |
|---|---|---|
| 넥스트키 잠금 | MySQL InnoDB | 인덱스 레코드와 앞 간격을 잠가 삽입 제한, 인덱스·격리·질의 형태에 좌우 |
| 직렬화 충돌 감지 | PostgreSQL Serializable | 읽은 조건과 충돌하는 쓰기를 추적해 이상 시 취소·재시도 |
| 스냅샷 기반 반복 읽기 | MVCC DBMS | 재조회 결과를 안정화하나 직렬화 가능성과는 별도 |

| 접근 | 운영 고려사항 |
|---|---|
| 범위·간격 잠금 | 대기·교착 가능성, 인덱스·실행계획 영향 |
| 직렬화 충돌 감지 | 재시도 로직·반복 실패 모니터링 |
| 스냅샷 격리 | 팬텀·직렬화 이상 보장 여부가 DBMS별로 다름 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 범위 잠금이 질의계획과 무관하게 팬텀을 막는다고 오해 | 인덱스·질의계획별 동시 삽입 시나리오로 검증 |
| 직렬화 실패를 애플리케이션이 처리하지 못함 | 재시도와 반복 실패 모니터링 시험 |

## Ⅵ. 제언

허용할 수 없는 팬텀이 있는 업무만 강한 격리를 적용하고, 사용 DBMS에서 동시 삽입 시나리오를 시험

```text
범위 조회·동시 삽입 업무 식별 → 격리·잠금 선택 → 시나리오 시험 → 재시도 설계
```

| 구분 | 모든 트랜잭션 강한 격리 | 제언: 필요한 업무에만 적용 |
|---|---|---|
| 처리량 | 대기 증가 | 유지 |
| 정합성 | 과잉 보호 | 필요한 범위 보호 |
