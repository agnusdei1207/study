## 답안 골격
```text
[고가용성(HA) 아키텍처] ◀━━ 머리: Ⅶ 내 의견 (스플릿 브레인 방지 쿼럼(Quorum) 합의체 구축 + 자동 페일오버 카오스 엔지니어링 검증)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 장애점(SPOF) 제거 및 이중화·복제를 통해 시스템 중단 없이 지속적인 서비스 제공을 보장하는 구조
 ┣━ Ⅱ 특징 ───── 99.999%(Five-Nines) 지향 · 무중단 페일오버 · 실시간 동기/비동기 데이터 복제 · 헬스체크 기반 장애 감지
 ┣━ Ⅲ 구조 ───── 로드밸런서(VIP) / 클러스터 관리자(Heartbeat) / 액티브-스탠바이 노드군 / 공유/복제 스토리지 / 스플릿 브레인 방지(Fencing)
 ┣━ Ⅳ 흐름 ───── ① 주 노드 장애 발생 → ② 하트비트 두절 감지 → ③ 펜싱(STONITH)으로 구 노드 차단 → ④ 대기 노드 승격 → ⑤ VIP 인계 및 서비스 재개
 ┣━ Ⅴ 비교 ───── Active-Active vs Active-Standby (Hot/Warm/Cold) (동시 부하분산/복잡성 vs 대기 자원/단순 전환)
 ┗━ Ⅵ 실무 ───── 네트워크 단절 시 스플릿 브레인(Split-Brain) 데이터 오염 / 페일오버 지연에 따른 트랜잭션 유실
```
- 필수 키워드: 단일 장애점(SPOF) · Active-Active · Active-Standby · 하트비트(Heartbeat) · 페일오버(Failover) · 스플릿 브레인 · 쿼럼(Quorum)
- 기출: 138회 3교시 4번 `가용성 보장에 대하여 다음 내용을 설명하시오` → Ⅰ 개념 + Ⅲ HA 아키텍처 + Ⅳ 페일오버 및 정합성 보장

## 한 줄 본질
- 단일 서버 장애로 인한 서비스 전면 중단(SPOF) 위험 → 모든 핵심 계층(L4, App, DB, Storage)의 다중화 및 자동 감시·절체(Failover) 메커니즘 구축 → 연간 다운타임 최소화(99.999%) / 복제 지연 및 정합성 비용 발생

## 핵심 그림
```text
[고가용성(HA) 클러스터 아키텍처 및 페일오버]

                 [ 가상 IP (VIP) / 로드밸런서 ]
                               │
                 ┌─────────────┴─────────────┐
                 ▼ (정상 라우팅)             │ (장애 시 절체)
          ┌─────────────┐             ┌─────────────┐
          │ Active 노드 │<─Heartbeat─>│Standby 노드 │
          │  (서비스 중)│  (상태감시) │   (대기 중) │
          └──────┬──────┘             └──────┬──────┘
                 │                           │
                 │      [ 데이터 복제 ]     │
                 └──────(Sync / Async)───────┘
                               │
                               ▼
                   [ 공유 스토리지 / 분산 DB ]
                    * 장애 감지 시 Fencing(STONITH)
                      -> Standby가 Active로 승격 & VIP 인계!
```

## 핵심 용어
- SPOF(Single Point of Failure): 시스템 내에서 장애 발생 시 전체 시스템의 작동을 완전히 멈추게 만드는 단일 구성요소
- 스플릿 브레인(Split-Brain): 노드 간 하트비트 통신망 장애로 양 노드가 서로 상대방이 죽었다고 판단해 동시에 Active로 승격되어 데이터 충돌 및 오염을 일으키는 현상

## 핵심 통찰
- 99.9%와 99.999%의 비용 차이는 수 배에 달함 → 가용성을 한 9(Nine) 올릴 때마다 인프라 이중화뿐 아니라 데이터 동기 복제에 따른 쿼리 레이턴시 증가를 감수해야 함
- 자동 페일오버는 양날의 검 → 네트워크 순시 지연으로 인한 조급한 페일오버는 스플릿 브레인을 유발하므로 3노드 이상의 쿼럼(Quorum) 합의나 STONITH(Shoot The Other Node In The Head) 격리가 필수
- 백업은 재해복구(DR)용이고 고가용성(HA)이 아님 → HA는 '수 초 내 자동 복구(RTO)'를 목표로 하므로 인메모리 및 블록 레벨의 실시간 복제가 동반되어야 함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| STONITH / Fencing | 스플릿 브레인 방지 메커니즘 | 오동작 의심 노드의 전원(IPMI)을 강제 차단하여 스토리지 동시 쓰기를 물리적으로 봉쇄 |
| 쿼럼(Quorum) 합의 | 분산 노드 상태 결정 | 과반수($N/2 + 1$) 노드의 동의를 얻은 파티션만 마스터 역할을 수행하도록 통제 |

## 이웃 토픽과 구분
- HA vs DR: HA = 동일 데이터센터/로컬 영역 내 단일 장비 장애 즉시 자동 절체(RTO 초~분) / DR = 데이터센터 전소 등 광역 재난 대비 원격지 복구(RTO 분~시간)

## 문제·원인·대책
- 적용 상황: 금융 결제 시스템 코어 DB의 Active-Standby 클러스터
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 인터커넥트 케이블 불량 시 양쪽 노드가 모두 Active로 동작해 DB 데이터 분기(Split-Brain) 발생 | 2-Node 구성으로 과반수 판별 불가 | 3번째 노드로 쿼럼 감시자(Witness) 추가 및 IPMI 펜싱 연동 | 데이터 오염 원천 방지 |
| 마스터 장애 후 슬레이브 승격 시 마지막 1초간의 결제 트랜잭션 유실 | 네트워크 성능 확보를 위해 비동기(Async) 복제 적용 | 반동기(Semi-Sync) 복제 전환 및 쓰기 트랜잭션 시 최소 1개 슬레이브 ACK 대기 | 데이터 유실 없는 무손실 페일오버(RPO=0) 달성 |

## 이렇게 출제된다
- 제138회 3교시 4번: "가용성 보장에 대하여 다음 내용을 설명하시오." → 요구 포인트: HA 개념 및 평가 지표(가용률 공식) + 이중화 구조(Active-Active/Standby) + 페일오버 및 데이터 정합성 통제

## 내 의견
- [테스트되지 않은 페일오버는 장애다] 평소에 스탠바이 서버 전환 훈련을 하지 않다가 실제 장애 상황에서 설정 오류나 DNS 캐싱 지연으로 RTO 수 시간 초과 사례 속출 → 나라면: 프로덕션과 동일한 스테이징 환경에서 카오스 엔지니어링(Chaos Mesh) 툴을 이용해 주 노드 전원을 무작위 차단하고 자동 절체 및 정합성을 주기적으로 강제 검증

## 찾아볼 것
- 클라우드 환경에서 멀티 가용영역(Multi-AZ) 간 데이터베이스 동기 복제 지연 시간과 커밋 처리량 상관관계
