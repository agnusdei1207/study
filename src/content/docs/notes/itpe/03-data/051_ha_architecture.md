## 지식 로드맵 내 현재 위치

<div class="itpe-topic-path" aria-label="지식 경로"><span>데이터베이스</span><span>분산 데이터베이스·고가용성</span><strong>고가용성(HA) 아키텍처</strong></div>

## 큰 그림과 30초 인출

```text
[고가용성(HA) 클러스터 아키텍처 및 페일오버 절체 흐름]

                   [ 가상 IP (VIP) / L4 로드밸런서 ]
                                  │
                 ┌────────────────┴────────────────┐
                 ▼ (정상 라우팅: VIP 보유)          │ (장애 감지 시 절체)
          ┌─────────────┐                  ┌─────────────┐
          │ Active 노드 │<───Heartbeat────>│Standby 노드 │
          │  (Master)   │    (상태 감시)   │   (Slave)   │
          └──────┬──────┘                  └──────┬──────┘
                 │                                │
                 │        [ 데이터 실시간 복제 ]  │
                 └────────(Sync / Semi-Sync)──────┘
                                  │
                                  ▼
                      [ 분산 / 공유 스토리지 ]
          * 장애 발생 시: 쿼럼(Quorum) 합의 ──▶ STONITH 펜싱 ──▶ Standby 승격 & VIP 인계
```

- 본질: **단일 장애점(SPOF, Single Point of Failure)을 제거하기 위해 하드웨어·네트워크·데이터베이스 전 계층을 다중화하고, 하트비트 감시와 자동 페일오버(Failover)를 통해 연간 가용률 99.999%(Five-Nines) 수준의 무중단 서비스를 제공하는 인프라 및 데이터 아키텍처**
- 암기: `단-다-감-절` (단일장애점 제거, 다중화/복제, 상태 감시, 자동 절체) / `스-쿼-스-펜` (스플릿 브레인, 쿼럼 합의, STONITH, 펜싱)
- 판단축:
  - **Active-Active**: 모든 노드가 동시에 트랜잭션을 처리하여 자원 효율과 부하분산이 극대화되나, 분산 락 및 데이터 동기화 복잡성 증가
  - **Active-Standby (Hot Standby)**: 주 노드만 쓰기를 수행하고 대기 노드는 복제 상태를 유지하여 구조가 단순하고 안정적이나, 유휴 자원 비용 발생
- 주의: 자동 페일오버 설계 시 하트비트 네트워크 일시 단절로 양 노드가 동시에 Active로 승격되는 **스플릿 브레인(Split-Brain)** 발생 위험을 차단하기 위해 3노드 이상 쿼럼(Quorum) 또는 물리적 펜싱(STONITH)이 필수적임

## 예상문제

> 데이터베이스 및 엔터프라이즈 시스템의 서비스 연속성을 보장하기 위한 고가용성(HA) 아키텍처의 개념과 가용도 평가 지표를 제시하고, Active-Active 및 Active-Standby 구성 모델의 메커니즘을 비교한 후, 페일오버 시 발생하는 스플릿 브레인(Split-Brain) 현상의 방지 방안을 설명하시오. (25점)

## Ⅰ. 단일 장애점(SPOF)을 극복하는 고가용성(HA) 개요

#### 한줄 요약: 시스템 구성요소의 이중화와 자동 장애 감지 및 절체를 통해 다운타임을 최소화하고 99.999% 이상의 서비스 지속성을 보장하는 아키텍처

- **추진 배경**:
  - 금융, 전자상거래, 미션 크리티컬 인프라에서 수 분간의 시스템 정지는 천문학적인 금전적 손실과 대외 신뢰도 추락을 초래함
  - 특정 단일 부품이나 서버 1대의 결함이 전체 서비스 중단으로 번지는 단일 장애점(SPOF)의 원천 배제가 필수적임
- **고가용성(HA, High Availability)의 정의**:
  - 정보시스템이 장애 발생 시에도 사람의 개입 없이(또는 최소 개입으로) 정상적인 운영 상태를 유지하거나, 허용된 목표 복구 시간(RTO) 내에 자동으로 복구되어 지속적인 서비스를 제공하는 능력
- **시스템 가용도(Availability) 공식**:
  $$\text{Availability} (A) = \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}} \times 100\%$$
  - **MTBF (Mean Time Between Failures)**: 평균 무고장 시간 (시스템의 신뢰성 지표)
  - **MTTR (Mean Time To Repair)**: 평균 수리·복구 시간 (시스템의 유지보수성 및 HA 절체 속도 지표)

```text
[가용도 등급(Nines)과 연간 허용 다운타임]
 ┌──────────────┬───────────────┬───────────────────────────────┐
 │ 가용도 등급  │ 백분율 (%)   │ 연간 허용 다운타임 (Downtime)  │
 ├──────────────┼───────────────┼───────────────────────────────┤
 │ Two-Nines    │ 99.0%         │ 약 3.65일 (87.6시간)           │
 │ Three-Nines  │ 99.9%         │ 약 8.76시간                    │
 │ Four-Nines   │ 99.99%        │ 약 52.6분                      │
 │ Five-Nines   │ 99.999%       │ 약 5.26분 (HA 아키텍처의 목표) │
 │ Six-Nines    │ 99.9999%      │ 약 31.5초                      │
 └──────────────┴───────────────┴───────────────────────────────┘
```

## Ⅱ. HA 아키텍처의 핵심 구성요소 및 시스템 토폴로지

#### 한줄 요약: 가상 IP, 클러스터 매니저의 하트비트 감시, 실시간 데이터 복제 및 스토리지 펜싱으로 구성된 다계층 이중화 체계

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    고가용성(HA) 클러스터의 논리적 계층 구조                   │
└─────────────────────────────────────────────────────────────────────────────┘
  [네트워크 계층]  - VIP (Virtual IP) / L4/L7 스위치 / Anycast BGP 라우팅
        │
  [서버 노드군]   - Active 노드 (Master) ─── Heartbeat ─── Standby 노드 (Slave)
        │           (Pacemaker, Corosync, Keepalived 클러스터 매니저)
  [데이터 복제]   - 동기(Sync) / 반동기(Semi-Sync) / 비동기(Async) 트랜잭션 로그 복제
        │
  [스토리지/펜싱] - SAN/NAS 공유 스토리지 또는 분산 블록 스토리지 (Ceph, DRBD)
                  - IPMI / ILO 기반 하드웨어 전원 차단 장치 (STONITH)
```

### 1. 핵심 구성요소 상세

| 구성 요소 | 역할 및 핵심 기능 | 대표 기술 / 솔루션 |
|:---|:---|:---|
| **가상 IP (VIP)** | 클라이언트가 특정 물리 노드에 종속되지 않고 접속할 수 있도록 동적으로 이동하는 대표 IP 주소 | Keepalived, VRRP |
| **클러스터 매니저** | 노드 간 상호 헬스체크(Heartbeat)를 수행하고 상태 전이 및 리소스 제어를 총괄 | Pacemaker, Corosync |
| **하트비트 (Heartbeat)** | 노드 간의 생존 여부와 네트워크 무결성을 확인하기 위해 주기적으로 주고받는 제어 패킷 | 전용 인터커넥트 LAN, 링 토폴로지 |
| **복제 엔진 (Replication)** | Active의 트랜잭션 로그(WAL, Binlog)를 Standby로 실시간 전송하여 데이터 일치 유지 | MySQL Group Replication, PostgreSQL Streaming Replication |
| **펜싱 (Fencing)** | 장애가 의심되는 구 노드가 공유 스토리지나 네트워크에 쓰기 작업을 수행하지 못하도록 물리적으로 강제 차단 | STONITH (IPMI, iLO), SAN Switch 바인딩 해제 |

## Ⅲ. 페일오버(Failover) 동작 절차 및 스플릿 브레인 방지 메커니즘

#### 한줄 요약: 하트비트 두절 감지부터 노드 펜싱, 대기 노드 승격, VIP 인계로 이어지는 무중단 절체 흐름과 쿼럼 기반 스플릿 브레인 원천 차단

### 1. 자동 페일오버 5단계 프로세스

```text
 [1단계: 장애 발생] ──▶ 주 노드(Active) 하드웨어 결함 또는 커널 패닉 발생
          │
 [2단계: 장애 감지] ──▶ Standby 노드가 Heartbeat 신호 타임아웃 감지 (예: 3초 무응답)
          │
 [3단계: 노드 펜싱] ──▶ 쿼럼 합의 후 STONITH 명령으로 Active 노드 IPMI 전원 강제 OFF (격리)
          │
 [4단계: 노드 승격] ──▶ Standby 노드가 Master 역할로 전환 (Read-Write 모드 활성화)
          │
 [5단계: VIP 인계]   ──▶ ARP 브로드캐스트(GARP)를 통해 VIP를 신규 Master로 재할당 후 서비스 재개
```

### 2. 스플릿 브레인(Split-Brain) 현상 및 방지 방안

- **스플릿 브레인의 본질**:
  - 노드 간의 하트비트 전용 네트워크가 단절되었으나 각 노드 자체는 정상 동작 중일 때 발생
  - 양쪽 노드가 서로 "상대방이 죽었다"고 오판하여 **둘 다 Active로 승격**
  - 클라이언트 요청이 양쪽으로 분산 쓰기되어 **데이터베이스 정합성이 영구적으로 파괴(데이터 분기)**되는 치명적 재난
- **스플릿 브레인 3대 방지 대책**:
  1. **쿼럼(Quorum) 다수결 합의체**:
     - 클러스터 노드 수를 홀수(최소 3노드 이상)로 구성
     - 네트워크 파티션 분할 시 전체의 과반수($N/2 + 1$) 이상을 확보한 파티션만 Active 권한을 획득하고, 나머지는 스스로 격리
     - 2노드 구성 시 외부 3번째 감시자(Witness / Arbiter 노드)를 반드시 배치
  2. **STONITH (Shoot The Other Node In The Head)**:
     - 쿼럼을 확보한 노드가 베이스보드 관리 컨트롤러(IPMI, iLO)를 통해 상대방 노드의 전원을 물리적으로 즉시 셧다운(Power Off)
  3. **하트비트 통신망 다중화**:
     - 하트비트 케이블을 단일 LAN에 의존하지 않고, 듀얼 NIC 본딩 및 디스크 공유 하트비트(Disk Heartbeat)를 동시 운용

## Ⅳ. HA 구성 패턴 비교: Active-Active vs Active-Standby

#### 한줄 요약: 동시 부하분산과 분산 락 복잡성을 갖는 Active-Active와, 단방향 복제와 유휴 자원을 갖는 Active-Standby의 구조적 비교

```text
┌───────────────────────────────────┬───────────────────────────────────┐
│     Active - Active 구성 모델     │     Active - Standby 구성 모델    │
├───────────────────────────────────┼───────────────────────────────────┤
│    [L4/L7 로드밸런서 (부하분산)]    │     [VIP / Keepalived (전환)]     │
│        ┌──────────────┐           │           ┌──────────────┐        │
│        ▼              ▼           │           ▼              │        │
│  ┌──────────┐   ┌──────────┐      │     ┌──────────┐   ┌──────────┐   │
│  │ Node A   │   │ Node B   │      │     │ Node A   │   │ Node B   │   │
│  │ (Active) │   │ (Active) │      │     │ (Active) │   │ (Standby)│   │
│  └────┬─────┘   └─────┬────┘      │     └────┬─────┘   └─────┬────┘   │
│       └───────┬───────┘           │          └───────┬───────┘        │
│               ▼                   │                  ▼                │
│    [분산 락 / 멀티 마스터 스토리지] │       [단방향 동기/반동기 복제]       │
└───────────────────────────────────┴───────────────────────────────────┘
```

### 1. 구성 모델 간 상세 비교

| 비교 항목 | Active - Active (멀티 마스터) | Active - Standby (Hot Standby) |
|:---|:---|:---|
| **트랜잭션 처리** | 모든 노드가 쓰기(Write)/읽기(Read) 동시 수행 | Active 노드만 Write 수행, Standby는 대기(또는 Read-Only) |
| **자원 활용률** | **100%** (모든 하드웨어 자원을 상시 활용) | **50% 수준** (대기 노드의 컴퓨팅 자원이 유휴 상태) |
| **장애 시 절체 시간** | **RTO $\approx$ 0** (트래픽을 정상 노드로 즉시 리디렉션) | **RTO 수 초~수 분** (헬스체크 판정 + 승격 + VIP 이동 소요) |
| **데이터 동기화** | 멀티 마스터 양방향 복제 및 분산 락(Distributed Lock) 필수 | 마스터 $\rightarrow$ 슬레이브 단방향 트랜잭션 로그 스트리밍 |
| **아키텍처 복잡도** | **극도로 높음** (동시 쓰기 충돌 해결, 네트워크 분할 대응) | **상대적으로 낮음** (검증된 상용/오픈소스 솔루션 풍부) |
| **대표 사례** | Oracle RAC, MySQL Group Replication, Cassandra | PostgreSQL Patroni, MySQL MHA/Orchestrator, Redis Sentinel |

### 2. Active-Standby의 3가지 세부 형태
- **Hot Standby**: 대기 노드가 항상 부팅되어 있고 DB 엔진이 구동되어 있으며, 최신 로그를 실시간 반영하여 즉각 승격 가능 ($RTO \le 10$초 이내)
- **Warm Standby**: 시스템과 DB 엔진은 켜져 있으나 복제 데이터가 주기적(배치)으로 갱신되어 최신 동기화 절차가 일부 필요 ($RTO \le$ 수 분)
- **Cold Standby**: 하드웨어 전원이 꺼져 있거나 백업 데이터만 보관되어 장애 시 서버 기동 및 데이터 복원이 수반됨 ($RTO \ge$ 수 시간)

## Ⅴ. 고가용성(HA) vs 재해복구(DR) 비교 및 RTO/RPO 지표 분석

#### 한줄 요약: 동일 센터 내 장비 장애에 대응하는 단거리 자동 절체(HA)와 광역 재난에 대비한 원격지 복구 체계(DR)의 비교

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       HA와 DR의 보호 영역 및 핵심 목표                      │
└─────────────────────────────────────────────────────────────────────────────┘
  [고가용성 (HA)] : 동일 전산실 / 가용영역(AZ) 내 하드웨어·네트워크 장애 방어
                   - RTO: 수 초 ~ 수 분 (자동 절체)
                   - RPO: 0 (동기 복제 기반 데이터 무손실)
  
  [재해복구 (DR)] : 지진, 화재, 전쟁 등 데이터센터 전소 및 광역 재난 방어
                   - 원격지(수십~수백 km) 센터로 데이터 소산
                   - RTO: 수십 분 ~ 수 시간 (재해 선언 후 전환)
                   - RPO: 0 또는 수 초~수 분 (비동기 복제 시 지연분 손실 감수)
```

| 구분 | 고가용성 (HA, High Availability) | 재해복구 (DR, Disaster Recovery) |
|:---|:---|:---|
| **대상 장애 수준** | 부품 고장, 단일 서버 장애, 프로세스 다운, 로컬 스위치 불량 | IDC 정전, 화재, 지진, 사이버 테러 등 센터 전체 마비 |
| **물리적 거리** | 동일 랙(Rack), 동일 센터, 또는 인접 가용영역(AZ, 수십 ms 이내) | 원격지 데이터센터 (물리적 거리 30km~수백 km 이상 격리) |
| **복제 메커니즘** | **동기(Sync) / 반동기(Semi-Sync)** 네트워크 복제 | 지연 시간(Latency) 극복을 위한 **비동기(Async)** 스토리지 복제 |
| **복구 목표 시간 (RTO)** | **수 초 ~ 수 분** 이내 (시스템 기반 자동 페일오버) | **수 분 ~ 수 시간** (경영진 재해 선언 및 비상 운영 매뉴얼 수행) |
| **복구 목표 시점 (RPO)** | **$RPO = 0$** (트랜잭션 유실 절대 불가 원칙) | $RPO \approx 0$ 또는 허용된 복제 지연 분량 유실 가능 |

## Ⅵ. 실무 데이터베이스 HA 구축 시 장애 패턴 및 튜닝 전략

#### 한줄 요약: 반동기 복제 튜닝을 통한 RPO=0 달성과 플래핑(Flapping) 방지, 카오스 검증 체계 확립

### 1. 비동기 복제 환경의 마스터 페일오버 시 트랜잭션 유실 (Split Data)
- **문제점**: 마스터 장애 시 슬레이브로 아직 전송되지 못한 트랜잭션 로그가 존재하여, 슬레이브 승격 후 구 마스터가 복구되었을 때 데이터가 서로 분기(Divergence)됨
- **대응 전략**:
  - **반동기 복제(Semi-Synchronous Replication)** 적용: 트랜잭션 커밋 시 최소 1개 이상의 슬레이브 릴레이 로그에 기록되었다는 ACK를 수신해야 최종 커밋 완료
  - **Raft / Paxos 기반 합의 분산 DB** 채택 (CockroachDB, TiDB)

### 2. 일시적 네트워크 지연으로 인한 잦은 절체(Flapping) 방지
- **문제점**: 네트워크 스파이크로 인해 1~2초간 핑이 튀었을 때 페일오버가 조급하게 트리거되어 VIP가 노드 간을 요동치며 대규모 커넥션 단절 유발
- **대응 전략**:
  - 하트비트 타임아웃 윈도우 적정화 (기본 3~5회 연속 실패 시 장애 판정)
  - 페일백(Failback) 자동화 금지: 원본 마스터가 살아나더라도 자동으로 마스터 권한을 탈환하지 못하도록 수동 페일백 정책 설정

## Ⅶ. 데이터 아키텍트 관점의 HA 신뢰성 및 카오스 엔지니어링 제언

#### 한줄 요약: 정기적인 무작위 장애 주입(Chaos Engineering)을 통해 페일오버의 실효성을 검증하고 무손실 무중단 운영을 실현

- **"검증되지 않은 페일오버는 재앙의 전주곡"**:
  - 실무에서 HA 구성을 완료했음에도 실제 장애 발생 시 페일오버 스크립트 오작동, DNS 캐시 고정, 방화벽 미개방 등으로 수 시간 이상 서비스가 정지되는 사례가 빈번함
  - 카오스 엔지니어링 툴(Chaos Mesh, LitmusChaos)을 스테이징 및 프로덕션 비수기 구간에 도입하여, 주기적으로 임의의 DB 노드 전원을 차단(Kill)하고 RTO/RPO 지표를 실측 검증해야 함
- **전 계층 엔드투엔드(End-to-End) HA 설계**:
  - DB 계층만의 HA는 무의미하며, DNS(Anycast) $\rightarrow$ L4/L7 $\rightarrow$ Web/WAS $\rightarrow$ DB $\rightarrow$ 공유 스토리지 전 계층에 걸쳐 SPOF가 완전히 제거되었는지 토폴로지 아키텍처 매핑을 정례화해야 함

```text
[문제 4] 서비스 연속성 보장을 위한 고가용성(HA) 아키텍처 및 페일오버

Ⅰ. 서비스 연속성을 위한 고가용성(HA) 개요
 1. 개념: 단일 장애점(SPOF) 제거 및 자동 절체로 연간 가용률 99.999%(Five-Nines)를 달성하는 아키텍처
 2. 가용도 공식: Availability = MTBF / (MTBF + MTTR) * 100% (MTTR 최소화가 핵심)

Ⅱ. HA 아키텍처 핵심 모델 비교: Active-Active vs Active-Standby
 ┌────────────────┬──────────────────────────┬──────────────────────────┐
 │    비교 항목   │       Active-Active      │  Active-Standby (Hot)    │
 ├────────────────┼──────────────────────────┼──────────────────────────┤
 │ 트랜잭션 처리  │ 모든 노드 Write/Read 수행│ Active만 Write, Standby대기│
 │ 자원 활용률    │ 100% (상시 부하분산)     │ 약 50% (대기 노드 유휴)  │
 │ 절체 시간(RTO) │ RTO ≈ 0 (즉각 리디렉션)  │ RTO 수 초 ~ 수십 초      │
 │ 분산 락/복잡도 │ 극도로 높음 (데이터 충돌)│ 상대적 단순, 신뢰성 높음 │
 └────────────────┴──────────────────────────┴──────────────────────────┘

Ⅲ. 페일오버 절차 및 스플릿 브레인(Split-Brain) 방지 방안
 1. 페일오버 5단계: 장애발생 -> 하트비트 두절 감지 -> STONITH 펜싱 -> Standby 승격 -> VIP 인계
 2. 스플릿 브레인 방지 3대 메커니즘
  가. 쿼럼(Quorum) 합의체: 홀수 노드(3노드 이상) 구성으로 과반수(N/2+1) 파티션만 마스터 승격
  나. STONITH (Fencing): 과반수 획득 노드가 의심 노드의 IPMI 전원을 강제 OFF하여 쓰기 봉쇄
  다. 하트비트 다중화: 전용 인터커넥트 LAN 및 공유 디스크 하트비트 듀얼 구성

Ⅳ. 실무 아키텍처 제언: 카오스 엔지니어링을 통한 실효성 검증
 1. Semi-Sync 복제 적용으로 RPO=0 무손실 페일오버 보장
 2. 비수기 정기 전원 차단 테스트(Chaos Mesh)를 통해 실측 RTO 검증 및 DNS 캐시 단절 예방
```
