## 지식 로드맵 내 현재 위치

자료처리·데이터 → 데이터베이스 운영 → **고가용성(HA) 아키텍처**

## 30초 인출

- 본질: 고가용성 아키텍처는 구성요소 장애 시 서비스 중단을 줄이도록 중복 자원·장애 감지·전환 경로를 갖춘 시스템 구조
- 메커니즘: 활성 노드의 데이터를 대기 노드에 복제하고 상태 감시로 장애를 판단해, 운영권 확인과 이전 노드 격리 후 대기 노드를 승격하고 요청 경로를 전환
- 통찰: 통신 단절을 장애로 오판하면 두 노드가 동시에 활성화되어(스플릿 브레인) 데이터가 손상되므로 쿼럼·펜싱을 두고, 복제 방식에 따른 RPO와 전환 시간 RTO를 업무별로 정해 정기 훈련으로 검증

<details>
<summary>핵심 용어</summary>

- **고가용성(HA, High Availability)** : 장애가 있어도 서비스를 계속 제공하도록 하는 구성
- **장애 조치(Failover)** : 활성 노드 장애 시 대기 노드가 서비스를 인계하는 절차
- **스플릿 브레인** : 통신이 끊긴 양쪽 노드가 각자 활성 상태라고 판단하는 상황
- **쿼럼(Quorum)** : 운영권을 가질 파티션을 정하는 기준
- **펜싱(Fencing)** : 이전 노드의 공유 자원 접근을 차단하는 조치
- **RTO** : 장애 후 서비스를 복구하기까지 허용하는 목표 시간
- **RPO** : 복구 데이터의 허용 손실 시점 차이

</details>

## 2~4교시 25점 답안

## Ⅰ. 고가용성 아키텍처의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **고가용성 아키텍처** 는 구성요소 장애 시 서비스 중단을 줄이도록 중복 자원·장애 감지·전환 경로를 배치한 구조 |
| 목적 | 단일 장애에 따른 서비스 중단과 데이터 손실 최소화 |

## Ⅱ. 특징

| 특징 | 설계 의미 |
|---|---|
| 중복 자원 | 활성 노드 장애 시 인계할 대기 자원 확보 |
| 상태·권한 판단 | 감시·쿼럼·펜싱으로 잘못된 중복 활성화 방지 |
| 복구 목표 | 전환 시간(RTO)과 데이터 손실(RPO)을 별도 평가 |

## Ⅲ. 구성과 장애 조치

```text
요청 → 활성 노드 ── 데이터 복제 ──→ 대기 노드
          └ 상태 감시 → 장애 판단 → 운영권 확인·기존 노드 격리
                                   → 대기 노드 승격 → 요청 경로 전환
```

| 구성 | 역할 | 설계 고려 |
|---|---|---|
| 서비스 진입점 | 요청을 활성 노드로 전달 | 전환 시 연결·이름 해석·경로 갱신 |
| 상태 감시 | 노드·서비스 상태 확인 | 네트워크 지연과 실제 장애 구분 |
| 데이터 복제 | 변경 내용을 대기 노드에 전달 | 동기화 방식에 따른 지연·손실 가능성 |
| 자원 격리 | 이전 노드의 자원 접근 방지 | 환경에 맞는 펜싱 |

```text
노드 A ←─ 통신 단절 ─→ 노드 B
    └── 쿼럼·외부 증인으로 운영권 결정 ──┘
운영권 없는 노드의 공유 자원 접근 차단 → 허가된 노드만 쓰기 지속
```

스플릿 브레인에서 양쪽이 같은 데이터에 쓰면 충돌·손상이 생기므로 쿼럼으로 운영권을 정하고 펜싱으로 차단하며, 구성은 클러스터 환경에 따라 선택.

## Ⅳ. 구성 방식과 복구 지표

| 구분 | 활성-대기 | 활성-활성 |
|---|---|---|
| 정상 운영 | 한 노드가 서비스, 다른 노드는 대기 | 여러 노드가 동시에 처리 |
| 장애 대응 | 대기 노드 승격·경로 전환 | 남은 노드로 부하 재분산 |
| 고려 | 대기 자원 비용·복제 지연·승격 절차 | 쓰기 충돌·일관성 |
| 적합 | 단순한 쓰기 경로가 필요할 때 | 애플리케이션이 분산 쓰기·충돌을 처리할 때 |

| 지표 | 의미 |
|---|---|
| 가용도 | 관측 기간 중 서비스 이용 가능 시간의 비율 |
| RTO | 복구까지 허용 시간 |
| RPO | 허용 데이터 손실 시점 차이 |

가용도는 측정 기간, 서비스 범위, 계획 중단 포함 여부를 먼저 정해야 산정 가능.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 감시망 단절을 서버 장애로 오판 | 복수 신호와 쿼럼 기준 사용, 전환 조건 시험 |
| 비동기 복제 지연으로 최근 데이터 손실 | 업무별 RPO를 정하고 복제 방식·복구 절차 정합 |
| 자동 전환 설정 오류·미검증 | 실제 장애 시나리오로 정기 훈련·정합성 확인 |

## Ⅵ. 제언

업무별 RTO·RPO를 정해 구성 방식과 복제 방식을 선택하고, 전환을 정기적으로 훈련

```text
RTO·RPO 목표 → 활성-대기·활성-활성 선택 → 복제·쿼럼·펜싱 구성 → 정기 전환 훈련
```

| 구분 | 단일 노드 | 제언: 중복 구성 + 훈련 |
|---|---|---|
| 장애 영향 | 서비스 중단 | 목표 시간 내 복구 |
| 검증 | 없음 | 정기 훈련 |
