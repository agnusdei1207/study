## 연관 키워드

- 고가용성, 이중화, 페일오버, 하트비트, 스플릿 브레인, 쿼럼, 펜싱, MTBF, MTTR, RPO, RTO, 로드밸런서, 다중 가용영역(Multi-AZ), 재해복구(DR)

## Ⅰ. 고가용성 아키텍처의 개요

- 핵심 요약 : 하드웨어·소프트웨어 장애에도 무중단 서비스를 지속하도록 장애 감지와 자동 복구 체계를 갖춘 아키텍처.
- 개념 : **고가용성** (HA, High Availability)은 시스템·네트워크·애플리케이션·데이터베이스에 결함이나 장애가 생겨도 정상 서비스를 지속하도록 **이중화**와 장애 복구 체계를 갖춘 아키텍처.
- 배경 및 필요성 :
  1. 무중단 비즈니스 요구 : 서비스 중단이 매출과 신뢰도 손실로 직결되는 환경의 확대.
  2. 단일 장애점(SPOF, Single Point of Failure) 제거와 자동 장애 조치 체계의 필요.
  3. 'Five Nines'(99.999%, 연간 장애 시간 약 5.26분 이내) 수준의 가용성 목표 대두.
- 주요 목적 : 장애 감지부터 **페일오버** (Failover)까지 자동화해 가용성과 데이터 정합성을 확보하고, 대규모 재해는 **재해복구** (DR, Disaster Recovery) 체계로 연계.

## Ⅱ. 고가용성 아키텍처의 특징 및 장점

- 핵심 요약 : 이중화 토폴로지와 자동 장애 감지, 합의 기반 방어, 복구 목표 관리가 맞물려 장애 중에도 서비스 연속성을 유지하는 방식.

1. 이중화 구성 : Active-Standby 또는 Active-Active 토폴로지로 결함 내성 확보 → 단일 노드 장애에서도 서비스 유지.
2. 정량 평가 지표 : **MTBF** (Mean Time Between Failures)와 **MTTR** (Mean Time To Repair) 기반의 가용도 공식 적용 → 가용도를 수치로 관리.
3. **하트비트** (Heartbeat) 기반 자동 장애 감지 : 노드 간 전용 링크로 신호를 주기적으로 교환 → 신호 단절 시 즉시 장애 판정.
4. **스플릿 브레인** (Split-Brain) 방어 : **쿼럼** (Quorum, 과반수 합의 투표)과 **펜싱** (Fencing) 적용 → 양측이 동시에 활성화되는 상황 차단.
5. 복구 목표 관리 : **RPO** (Recovery Point Objective)와 **RTO** (Recovery Time Objective)를 사전 정의하고 검증 → 데이터 유실과 중단 시간을 목표치 안에 통제.

```text
[HA 핵심 평가 공식]
  가용도(A) = MTBF / (MTBF + MTTR)
  * MTBF : 평균 무고장 시간 (극대화 필요)
  * MTTR : 평균 수리 복구 시간 (극소화 필요)
```

## Ⅲ. 고가용성 아키텍처의 구조 (흐름)

- 핵심 요약 : 두 가지 클러스터 구성 모델과, 장애 감지에서 트래픽 전환까지의 페일오버 흐름.
- 정상 시 트래픽은 **로드밸런서** (Load Balancer)가 나누어 처리하며, 장애 노드는 헬스체크에서 제외된다.

```text
[Active-Standby]
[Active 노드]
      ↓ 하트비트·데이터 동기화
[Standby 노드] (장애 시 승격)
```

```text
[Active-Active]
  ↓ 트래픽 분산
[Active 노드 1] ↔ [Active 노드 2]
  (서로 예비 노드 역할)
```

장애 감지 및 페일오버 흐름은 다음과 같다.

1. 하트비트 단절 또는 헬스체크 임계치 초과에 따른 장애 판정.
2. 쿼럼 투표 기반의 신규 Active 노드 승격.
3. 펜싱(STONITH, Shoot The Other Node In The Head)으로 구 노드 격리.
4. DNS(Domain Name System)와 VIP(Virtual IP) 스위칭으로 트래픽 전환.

```text
[마지막 복제 시점]
          ↓ RPO (데이터 유실 허용 구간)
[재해 발생]
          ↓ RTO (서비스 중단 허용 시간)
[서비스 정상화]
```

## Ⅳ. HA 구성 모델 및 RPO·RTO의 비교

- 핵심 요약 : RTO, 비용, 자원 효율의 트레이드오프에 따라 구성 모델을 고르고, RPO와 RTO의 역할을 구분.

| 구성 모델 | 동작 메커니즘 | 장점 | 트레이드오프 및 한계 |
| --- | --- | --- | --- |
| Active-Hot Standby | Standby 노드가 가동 상태로 데이터를 실시간 동기화하며 대기 | 페일오버 시간(RTO) 수초 이내 | Standby 노드 자원이 유휴 상태로 방치되어 비용 비효율 |
| Active-Active | 복수 노드가 트래픽을 분산 처리하며 서로의 예비 노드 역할 수행 | 자원 활용률 극대화, 전체 처리량 증대 | 노드 간 동기화 오버헤드, 한 노드 장애 시 잔여 노드 부하 급증 |
| Active-Warm Standby | Standby 노드는 가동하되 애플리케이션은 비활성 상태 | Hot 대비 인프라 비용 절감 | 앱 기동과 캐시 적재에 따른 수분 수준의 RTO 소요 |

| 구분 | RPO (Recovery Point Objective) | RTO (Recovery Time Objective) |
| --- | --- | --- |
| 정의 | 장애 시 감내 가능한 최대 데이터 손실 시점 | 서비스 중단부터 정상 복구까지의 최대 허용 중단 시간 |
| 측정 대상 | 데이터 유실 허용치 | 서비스 중단 시간 |
| 관리 수단 | 동기식 복제, 로그 전송 주기 단축 | 자동 페일오버, 헬스체크 임계치 튜닝 |

- 선택 기준 : RTO가 수초 수준으로 요구되면 Active-Hot Standby, 자원 효율과 처리량이 우선이면 Active-Active, 비용을 최소화하고 수분 수준의 중단을 허용하면 Active-Warm Standby.

## Ⅴ. 고가용성 아키텍처의 한계와 방안

- 핵심 요약 : 스플릿 브레인, 페일오버 시점의 데이터 유실과 지연, 스탠바이 자원 유휴화라는 한계를 합의 메커니즘과 복제 방식, 구성 전략으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 스플릿 브레인에 따른 정합성 파괴 | 하트비트 네트워크 단절 시 양측이 활성 마스터로 승격되어 상이한 쓰기로 데이터 분기 | 홀수 노드 구성의 쿼럼 메커니즘 필수 적용, 펜싱(STONITH) 하드웨어 차단 장치 연동 | 데이터 분기 발생 건수 |
| 페일오버 시 RPO·RTO 지연 | 비동기 복제는 미복제 트랜잭션 유실(RPO > 0), 판정과 승격 시간 동안 서비스 중단 | 동기식 복제 또는 Raft 기반 합의 엔진 적용, 자동 DNS·VIP 전환과 클라이언트 자동 재연결 | 복제 지연, 페일오버 소요 시간 |
| Active-Standby 자원 유휴화 | 정상 운영 시 대기 서버가 트래픽을 처리하지 않아 인프라 비용 효율 저하 | Active-Active 멀티 리전 전환, 읽기 전용 쿼리 분산용 읽기 복제본(Read Replica) 활용 | 자원 활용률 |

## Ⅵ. 고가용성 아키텍처에 대한 기술사적 제언

- 핵심 요약 : 여러 가용영역에 걸친 액티브-액티브 배포와 카오스 엔지니어링으로 장애 대응을 상시 검증하는 체계 필요.
- 상태 비저장(Stateless) 웹·앱 컨테이너를 3개 이상의 **다중 가용영역** (Multi-AZ, Multiple Availability Zones)에 분산 배치하고, DB는 Multi-AZ 자동 동기식 복제를 적용하는 것이 바람직하다.
- 카오스 엔지니어링(Chaos Engineering)을 상시화해 Chaos Mesh 같은 도구로 운영 환경의 인스턴스를 무작위 종료하는 테스트를 정례화한다.
- MTBF 극대화와 MTTR 극소화 지표를 대시보드로 상시 관찰하고, 재해복구 훈련을 같은 주기로 연계한다.

## Ⅶ. 결론

- 핵심 요약 : 고가용성은 가용도 공식 기반의 정량 관리와 이중화·합의 메커니즘을 결합해야 완성되는 체계.
- 시사점 : 클라우드 네이티브 환경에서는 다중 가용영역 설계와 카오스 테스트를 상시 검증 수단으로 삼아야 함.
