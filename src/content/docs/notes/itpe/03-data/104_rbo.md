## 답안 골격
```text
[RBO (Rule Based Optimizer)] ◀━━ 머리: Ⅶ 내 의견 (레거시 RBO 탈피 및 CBO 전환 시 통계 수집과 힌트 정제)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터의 실제 분포나 비용을 고려하지 않고 사전 정의된 15개 고정 규칙 우선순위에 따라 실행 계획을 생성하는 초기 옵티마이저
 ┣━ Ⅱ 특징 ───── 고정된 15계층 순위(ROWID 최우선, FTS 최하위) · 데이터 통계 불필요 · 개발자 코딩 방식(WHERE절 순서)에 종속 · 직관적 예측 가능
 ┣━ Ⅲ 구조 ───── 1순위: Single row by ROWID / 4순위: Unique Index / 8순위: Composite Index / 15순위: Full Table Scan
 ┣━ Ⅳ 흐름 ───── ① SQL 문법 분석 → ② 접근 경로(Access Path) 후보 식별 → ③ 고정 15개 규칙 순위 비교 → ④ 가장 높은 순위(낮은 번호)의 경로를 실행 계획으로 확정
 ┣━ Ⅴ 비교 ───── RBO vs CBO (규칙 우선순위 vs I/O·CPU 예상 비용 계산 / 통계 불필요 vs 최신 데이터 딕셔너리 통계 필수)
 ┗━ Ⅵ 실무 ───── 데이터 99%가 특정 값에 몰려도 인덱스 스캔 강제 / 조인 시 FROM절의 뒤쪽 테이블을 무조건 드라이빙 테이블로 선택
```
- 필수 키워드: RBO · 15개 우선순위 규칙 · ROWID 스캔 · CBO · 인덱스 랭킹 · 실행 계획 · 드라이빙 테이블
- 기출: 127회 `옵티마이저의 유형인 RBO와 CBO를 비교하고, RBO의 한계점을 설명하시오.` → Ⅰ 정의 + Ⅲ 15개 규칙 + Ⅴ RBO vs CBO + Ⅵ 한계 및 마이그레이션

## 한 줄 본질
- 실제 데이터의 볼륨이나 분포와 무관하게 하드코딩된 규칙 순위표만 보고 기계적으로 경로를 결정 → 통계 정보가 없어도 일관된 플랜을 얻음 / 데이터 왜곡 시 치명적 비효율 경로 선택

## 핵심 그림
```text
[RBO 핵심 15개 규칙 우선순위 계층 (상위일수록 우선 채택)]

  Rank 1  : Single row by ROWID (가장 빠름)
  Rank 2  : Single row by Cluster Join
  Rank 3  : Single row by Hash Cluster Key with Unique/Primary Key
  Rank 4  : Single row by Unique / Primary Key
  Rank 8  : Composite Index Scan
  Rank 9  : Single Column Index Scan
  Rank 10 : Bounded Range Search on Indexed Columns (BETWEEN, LIKE)
  Rank 11 : Unbounded Range Search on Indexed Columns (> , >=)
  ...
  Rank 15 : Full Table Scan (가장 느림, 최후 순위)
```

## 핵심 용어
- ROWID: 데이터 파일 번호, 블록 번호, 행 번호로 구성된 디스크 상의 물리적 행 주소로 RBO에서 가장 높은 1순위 접근 경로
- 드라이빙 테이블(Driving Table): 조인 연산 수행 시 먼저 읽혀서 조인 기준 데이터를 공급하는 테이블 (RBO는 FROM절 우측 테이블을 드라이빙으로 선택)

## 핵심 통찰
- RBO 환경에서는 SQL 작성자가 공백 하나, WHERE절 조건 순서 하나, FROM절 테이블 배치 순서 하나까지 조율해야 최적 성능이 나옴 → 쿼리 작성자가 옵티마이저 노릇을 대신함
- 전체 데이터의 99.9%가 동일한 상태(예: 주문상태 = '완료')여도 RBO는 인덱스가 존재하면 무조건 인덱스 레인지 스캔(Rank 9)을 채택하여 수천만 건의 무작위 디스크 I/O를 일으킴
- 현대 RDBMS(Oracle 10g 이후 등)에서는 RBO 지원이 공식 중단되었으므로, 구형 코드를 유지보수할 때만 분석 대상이 됨

## 이웃 토픽과 구분
- RBO vs CBO: RBO = 고정된 규칙 순위(Rule)만 따름(데이터 무시) / CBO = 테이블 크기, 인덱스 높이, 데이터 분포 등 통계 정보 기반으로 실제 소요 비용(Cost)을 계산하여 최저 비용 선택

## 문제·원인·대책
- 적용 상황: 수억 건의 결제 데이터가 적재된 금융권 레거시 배치 시스템
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 대용량 배치 실행 시 Full Table Scan으로 수시간 동안 디스크 I/O 병목 | RBO 엔진에서 두 테이블 크기를 고려하지 않고 FROM절 테이블 순서대로 조인 | 대형 테이블을 드라이빙으로 지정하거나 CBO 모드로 전환 | 최적 조인 순서(해시 조인) 적용으로 배치 수행 시간 80% 단축 |
| 인덱스 컬럼에 `BETWEEN`을 걸었으나 극소수 유효 행임에도 비효율적 인덱스 스캔 발생 | RBO의 고정 랭킹(Rank 10) 기계적 적용 | CBO 힌트(`/*+ ALL_ROWS */`) 주입 및 히스토그램 통계 갱신 | 데이터 분포에 맞는 최적 실행 계획 유도 |

## 이렇게 출제된다
- 제127회: "관계형 데이터베이스 관리시스템(RDBMS)의 쿼리 옵티마이저 유형인 규칙 기반 옵티마이저(RBO)와 비용 기반 옵티마이저(CBO)를 비교하고, RBO의 동작 규칙 및 한계점에 대하여 설명하시오." → 요구 포인트: RBO 정의 + 15개 랭킹 구조 + CBO와의 비교표 + RBO의 데이터 분포 무시 한계

## 내 의견
- [RBO 힌트 잔재로 인한 장애] 과거 시스템에서 억지로 튜닝해 둔 `/*+ RULE */` 힌트나 특정 드라이빙 순서 코딩이 CBO 환경으로 업그레이드된 뒤에도 남아 옵티마이저의 지능적 판단을 가로막는 사고 빈발 → 나라면: SQL 분석 스크립트를 통해 코드베이스 내의 하드코딩된 `RULE` 힌트를 전수 추출하여 제거하고, 최신 통계 수집 배치(`DBMS_STATS`)를 정착시켜 CBO가 완전히 주도하도록 마이그레이션 추진

## 찾아볼 것
- 오라클 옵티마이저 모드 파라미터(`OPTIMIZER_MODE`)의 변천사(`RULE`, `CHOOSE`, `ALL_ROWS`, `FIRST_ROWS`)
