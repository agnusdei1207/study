- 본질: **기업 내 여러 부서와 이기종 시스템(ERP, CRM, SCM 등)에 중복·파편화되어 존재하는 핵심 비즈니스 엔티티(고객, 상품, 공급업체, 계정 등)를 수집, 정제, 매칭, 머징하여 전사적으로 유일한 단일 진실 공급원(SSOT, Single Source of Truth)인 골든 레코드(Golden Record)를 구축하고 동기화하는 전사 데이터 관리 체계**
- 암기: `수-정-매-머-배` (원천 수집, 표준화/정제, 매칭, 머징, 배포) / `레-통-공-트` (레지스트리형, 통합형, 공존형, 트랜잭션형)
- 판단축:
  - **레지스트리/통합형**: 원천 시스템의 프로세스 수정을 최소화하여 빠르고 안전하게 전사 가시성을 확보하되, 원천 데이터의 실시간 동기화 한계
  - **공존/트랜잭션형**: 전사 데이터의 완벽한 일관성과 중앙 통제를 달성하되, 시스템 연계 복잡도 및 현업 업무 프로세스 개편 부담 수반
- 주의: MDM 프로젝트의 주요 실패 원인은 기술적 알고리즘 부재가 아니라, 부서 간 데이터 오너십(Ownership) 갈등과 속성별 신뢰도(Trust Score) 정의 부재에 있으므로, 데이터 스튜어드십(Data Stewardship) 거버넌스 조직 정립이 선행되어야 함

## Ⅰ. 데이터 사일로와 중복을 극복하는 MDM 개요

#### 한줄 요약: 시스템별로 파편화된 핵심 기준 데이터의 단일 진실 공급원(SSOT)을 수립하여 전사적 정합성을 달성하는 거버넌스

- **추진 배경**:
  - 기업의 성장과 M&A로 인해 ERP, CRM, 쇼핑몰, 물류 시스템이 독자적인 고객 코드와 상품 코드를 발번하여 운영되는 **'데이터 사일로(Data Silo)'** 발생
  - 동일 고객에게 마케팅 메시지가 중복 발송되거나, 동일 공급업체에 대한 법인별 구매 단가가 달라 전사적 협상력이 약화되는 등 막대한 비효율 초래
- **마스터 데이터(Master Data)의 정의**:
  - 비즈니스 트랜잭션(거래, 결제 등)의 핵심 주체이자 명사형 객체로서, 시스템 전반에 걸쳐 공유되는 고객(Customer), 제품(Product), 자산(Asset), 공급업체(Vendor) 등의 **핵심 기준 정보**
- **MDM의 정의**:
  - 전사적인 관점에서 마스터 데이터를 정의, 통합, 정제, 동기화하고 이를 유지하기 위한 정책, 프로세스, 조직 및 기술 솔루션의 종합적 체계

### 1. 매칭 알고리즘 (Matching Algorithm)
- **결정론적 매칭 (Deterministic Matching)**: 주민등록번호, 사업자등록번호, 이메일 등 유일 식별자가 정확히 일치하는 경우 동일인으로 판정
- **확률론적 매칭 (Probabilistic Matching)**: 이름의 오타나 주소 표기 차이를 극복하기 위해 **Jaro-Winkler 거리, Levenshtein 거리, Soundex 음성 알고리즘**을 결합하여 가중 유사도 점수(Similarity Score)가 임계값(예: 85점) 이상이면 동일 개체로 판정

### 2. 머징 및 신뢰도 점수 (Trust Score Merging)
- 두 시스템의 데이터가 매칭되었을 때, 어떤 시스템의 속성을 골든 레코드에 채택할지 결정:
  - 예: 고객 주소는 배송 시스템(SCM)의 신뢰도를 90점, 전화번호는 고객센터(CRM)의 신뢰도를 95점으로 지정하여 **속성 단위(Attribute-level) 최적 결합** 수행

## Ⅲ. MDM 4대 구축 아키텍처 유형 심층 분석

#### 한줄 요약: 원천 시스템에 미치는 영향도와 마스터 데이터 통제 수준에 따라 4가지 아키텍처로 진화

| 비교 항목 | Registry (참조형) | Consolidated (통합형) | Co-existence (공존형) | Transactional (트랜잭션형) |
|:---|:---|:---|:---|:---|
| **골든 레코드 저장**| **미저장** (매핑 색인만) | **허브에 저장** (단방향) | **허브 및 원천에 저장** | **허브가 유일 원천** |
| **데이터 흐름** | 가상화 조회 (Federation)| 원천 $\rightarrow$ 허브 (단방향) | 원천 $\leftrightarrow$ 허브 (양방향) | 허브 $\rightarrow$ 원천 (단방향 배포) |
| **원천 시스템 수정**| **전혀 없음 (Zero)** | 거의 없음 (읽기 권한만) | 보통 (배포 수신 로직 추가) | **매우 큼 (생성 로직 제거)** |
| **데이터 정합성** | 낮음 (조회 시점에만 매핑)| 보통 (분석용으로만 일치) | **높음 (운영계 정합성 달성)**| **완벽 (원천 오염 원천 배제)** |
| **구축 난이도/비용**| 가장 낮음 / 소규모 | 낮음 / 분석 부서 주도 | 중간~높음 / 단계적 추진 | **가장 높음 / 전사 빅뱅** |
| **적합한 구축 시기**| 도입 1단계 (현황 파악) | 도입 2단계 (분석 통합) | **실무 엔터프라이즈 최적** | 신규 차세대 ERP 구축 시 |

## Ⅳ. MDM vs 데이터 웨어하우스(DW) vs 메타데이터 관리 비교

#### 한줄 요약: 현재 시점의 기준 엔티티(MDM), 과거 이력 트랜잭션 집계(DW), 데이터의 구조와 사전(메타)의 역할 분담

| 비교 항목 | 마스터 데이터 관리 (MDM) | 데이터 웨어하우스 (DW) | 메타데이터 관리 (Metadata) |
|:---|:---|:---|:---|
| **관리 대상** | **마스터 데이터 (고객, 상품, 계정)** | **트랜잭션 팩트(Fact) 및 과거 이력** | **데이터의 구조, 속성명, 스키마 정의** |
| **데이터 성격** | 현재 시점의 유효한 **단일 진실(SSOT)** | 시계열 분석을 위한 **스냅샷 이력 누적** | 데이터에 대한 데이터 (사전, 도메인) |
| **주요 사용자** | 운영계 시스템, 현업 비즈니스 담당자 | 경영진, 데이터 분석가, 기획 부서 | DBA, 데이터 모델러, 시스템 개발자 |
| **처리 방식** | 실시간 트랜잭션 동기화 및 API | 대용량 야간 배치 ETL / ELT | DDL 파싱, 표준화 관리 도구 |

### 1. 실무 도입 시의 주요 실패 요인
- **부서 간 이기주의 및 오너십 갈등**: 영업부는 간이 고객정보 입력을 선호하고, 재무부는 엄격한 사업자번호 인증을 요구할 때 합의점 부재
- **예외 처리 인력 부재**: 확률적 매칭 점수가 애매한 데이터(회색 지대, 예: 70~84점)를 수작업으로 검증할 전문 인력(Data Steward) 부재

## Ⅵ. 데이터 아키텍트 관점의 차세대 MDM 제언

### 학습자 통찰 메모 — 답안 밖

> **[핵심 통찰]**
> MDM 프로젝트가 실패하는 이유는 "데이터 매칭 기술이 부족해서"가 아니라 **"부서 간 오너십 정치 싸움과 중앙집중식 허브의 병목"** 때문이다. 영업부와 재무부가 고객의 마스터 속성 정의를 합의하지 못하면 어떤 비싼 솔루션도 무용지물이 된다. 따라서 데이터 거버넌스 위원회와 **데이터 스튜어드십(Data Stewardship)** 조직이 반드시 선행되어야 하며, 최신 아키텍처에서는 모놀리식 단일 허브 대신 **도메인 주도 설계(DDD)와 실시간 CDC(Kafka) 기반의 탈중앙화된 공존형(Co-existence)**으로 구축해야 한다.

> **[나라면 이렇게 쓴다]**
> 10점형 답안이라면 4대 구축 유형(Registry, Consolidated, Co-existence, Transactional)의 데이터 흐름도와 원천 영향도 비교표를 명쾌하게 작성하겠다. 25점형이라면 골든 레코드 매칭/머징 알고리즘(Jaro-Winkler, Trust Score)을 상세히 제시하고, 실무 장애 방지를 위한 3단계 진화 로드맵과 데이터 스튜어드 거버넌스를 4단 제언으로 제시하겠다.

### 실전 답안용 기술사적 제언

- **판정 (현행 한계)**: 부서별 독자 코드 발번으로 전사 데이터 사일로 심화 및 단일 중앙집중식 MDM 추진 시 업무 마비 리스크
- **대응 (개선 방안)**: 분석용 통합형에서 시작하여 실시간 CDC 기반 공존형(Co-existence)으로 단계적 진화 및 데이터 스튜어드십 조직 신설
- **검증 (검증 기준)**: 전사 고객/상품 중복률 1% 미만 감축, 원천-허브 간 동기화 지연시간(Lag) 3초 이내 검증, 골든 레코드 정합성 99.9%
- **효과 (실행 효과)**: 마케팅 중복 발송 비용 40% 절감, 전사 구매 협상력 단일화로 공급망 단가 12% 절감 및 데이터 신뢰성 확보

> MDM (Master Data Management, 마스터 데이터 관리) 및 4대 구축 아키텍처의 정의, 목적, 핵심 메커니즘을 설명하시오. (예상)

## 1교시 10점 답안

### 1. 정의·목적

- 정의: 전사 핵심 엔티티(고객, 상품 등)의 단일 진실 공급원(SSOT)인 골든 레코드를 구축·배포하는 체계
- 목적: 조직 전반의 핵심 엔터티를 정합화해 신뢰할 수 있는 골든 레코드를 제공한다.

### 2. 핵심 관계

| 구축 유형 | 동작 메커니즘 | 핵심 특징 |
|:---|:---|:---|
| **1. Registry (참조형)** | 허브는 원천 ID 매핑 색인만 유지하고 데이터 미보관 | 원천 시스템 무수정, 가장 빠르고 경량 구축 가능 |
| **2. Consolidated (통합형)** | 원천 데이터를 허브로 단방향 수집하여 골든 레코드 구축 | 전사 BI/DW 분석에 최적, 운영계 불일치는 잔존 |
| **3. Co-existence (공존형)** | 원천 생성 $\to$ 허브 정제머징 $\to$ 원천으로 양방향 동기화 | 운영계 데이터 정합성 보장, 엔터프라이즈 실무 표준 |
| **4. Transactional (트랜잭션형)** | 마스터는 오직 허브에서 생성 후 원천 시스템으로 강제배포 | 완벽한 거버넌스 통제, 원천 시스템 프로세스 개편 |

## 2~4교시 25점 답안

### Ⅰ. 데이터 사일로를 극복하는 MDM의 개념 및 필요성

1. **배경**: 시스템별 독자적 코드 발번으로 인한 데이터 중복 및 전사 정합성 왜곡 극복
2. **정의**: 전사 핵심 엔티티(고객, 상품 등)의 단일 진실 공급원(SSOT)인 골든 레코드를 구축·배포하는 체계

### Ⅱ. 골든 레코드(Golden Record) 생성 핵심 프로세스

1. **프로세스**: 프로파일링/클렌징 $\to$ 중복 매칭(결정론+확률론) $\to$ 신뢰도 머징(Trust Score) $\to$ 전사 배포
2. **매칭 기술**: Jaro-Winkler, Levenshtein 거리 알고리즘을 활용한 복수 시스템 레코드 유사도 판정

### Ⅲ. MDM 4대 구축 아키텍처 유형 심층 비교

| 구축 유형 | 동작 메커니즘 | 핵심 특징 |
|:---|:---|:---|
| **1. Registry (참조형)** | 허브는 원천 ID 매핑 색인만 유지하고 데이터 미보관 | 원천 시스템 무수정, 가장 빠르고 경량 구축 가능 |
| **2. Consolidated (통합형)** | 원천 데이터를 허브로 단방향 수집하여 골든 레코드 구축 | 전사 BI/DW 분석에 최적, 운영계 불일치는 잔존 |
| **3. Co-existence (공존형)** | 원천 생성 $\to$ 허브 정제머징 $\to$ 원천으로 양방향 동기화 | 운영계 데이터 정합성 보장, 엔터프라이즈 실무 표준 |
| **4. Transactional (트랜잭션형)** | 마스터는 오직 허브에서 생성 후 원천 시스템으로 강제배포 | 완벽한 거버넌스 통제, 원천 시스템 프로세스 개편 |

### Ⅳ. 실무 성공 전략 및 아키텍처 제언

1. **단계적 접근**: 통합형(가시화) $\to$ 공존형(실시간 동기화)으로 점진적 진화
2. **조직 거버넌스**: 데이터 스튜어드십(Data Stewardship) 조직을 신설하여 부서 간 오너십 갈등 중재
