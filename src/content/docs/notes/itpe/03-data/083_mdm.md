## Ⅰ. 단일 진실 공급원(SSOT) 구축을 위한 마스터 데이터 관리(MDM) 개요

### 가. 마스터 데이터 관리(Master Data Management)의 정의
- 기업의 비즈니스 프로세스 전반에 걸쳐 공유되는 핵심 비즈니스 엔티티(고객, 상품, 공급업체, 계정, 조직 등)의 기준 데이터를 전사적으로 단일화하고, 데이터의 생성·변경·폐기 전 생명주기를 일관되게 통제하여 **단일 진실 공급원(SSOT, Single Source of Truth)** 을 보장하는 프로세스, 정책 및 통합 기술 아키텍처.

### 나. 마스터 데이터 vs 트랜잭션 데이터 비교

| 비교 항목 | 마스터 데이터 (Master Data) | 트랜잭션 데이터 (Transactional Data) |
| :--- | :--- | :--- |
| **데이터 성격** | 비즈니스의 핵심 명사 (Who, What, Where) | 비즈니스에서 발생하는 사건의 동사 (Did What, When) |
| **구체적 예시** | 고객(Customer), 상품(Product), 거래처, 사원, 계정 | 주문(Order), 입출금(Payment), 배송로그, 통화내역 |
| **변경 빈도** | 상대적으로 낮음 (안정적, 수명주기가 김) | 극도로 높음 (초당 수천 건 지속 생성) |
| **데이터 볼륨** | 수만~수백만 건 (관리 가능한 크기) | 수천만~수억 건 (대규모 스트리밍/로그) |
| **관리의 핵심** | **정확성, 일관성, 유일성 (중복 제거가 최우선)** | 처리 속도(Throughput), 확장성, 트랜잭션 정합성 |

## Ⅱ. MDM의 핵심 아키텍처 구현 모델 4가지

### 가. 4대 MDM 아키텍처 비교

```text
[ MDM 4대 아키텍처 토폴로지 ]
1. Registry (참조형)   : 원천 시스템 유지, 중앙에는 식별자 매핑 키(Cross-reference)만 보관
2. Consolidation (통합형): 원천 시스템에서 배치 수집하여 중앙에 골든 레코드(Golden Record) 구축 (분석용)
3. Coexistence (공존형) : 중앙에서 골든 레코드 관리 및 원천 시스템으로 변경 전파 (운영/분석 혼합)
4. Transaction (트랜잭션): 모든 마스터 데이터 CUD가 오직 중앙 MDM 허브에서만 직접 발생 (완전 중앙집중)
```

| 구현 모델 | 동작 방식 및 메커니즘 | 장점 | 트레이드오프 및 한계 |
| :--- | :--- | :--- | :--- |
| **Registry (등록 모델)** | 원천 시스템의 데이터는 그대로 두고, 중앙 허브에는 글로벌 식별자 매핑 인덱스만 유지 | 레거시 시스템 변경 불필요, 가장 빠르고 저비용 구축 | 원천 데이터의 실시간 불일치 정제 불가, 조회 시 분산 쿼리 필요 |
| **Consolidation (통합 모델)** | 원천 시스템에서 데이터를 일괄 수집하여 중앙 허브에서 중복 제거 및 단일 뷰 생성 | 분석 및 BI 대시보드 관점에서 완벽한 전사 단일 뷰 제공 | 운영 시스템으로 역방향 동기화가 되지 않아 운영 단 불일치 잔존 |
| **Coexistence (공존 모델)** | 중앙 허브에서 골든 레코드를 생성·관리하고, 변경 사항을 원천 시스템들로 실시간 비동기 동기화 | 운영과 분석 데이터가 모두 최신 정합성 유지 | 분산 시스템 간 양방향 동기화 및 충돌 해결 복잡도 극상 |
| **Transaction (중앙 트랜잭션)** | 모든 마스터 데이터의 등록/수정/삭제를 오직 중앙 MDM 시스템에서만 수행하고 원천으로 단방향 배포 | 완벽한 전사 데이터 무결성 및 엄격한 거버넌스 보장 | 레거시 시스템 전면 개편 필요, 초기 도입 비용 및 기간 막대 |

## Ⅲ. MDM의 핵심 엔진 기능: 매칭 및 머징(Matching & Merging)

### 가. 골든 레코드(Golden Record) 생성 프로세스

```text
[ 매칭 및 머징 4단계 흐름 ]
[이종 시스템 고객 데이터 인입] ---> [1. 데이터 표준화 & 주소 정제]
                                             |
                                             v
[3. 중복 판정 (Match Rule)]   <--- [2. 후보군 차단 (Blocking / Indexing)]
(결정론적 룰 + 확률적 유사도)
       |
       +---> [자동 병합 (Auto-Merge)]: 신뢰도 95% 이상 -> 단일 골든 레코드 생성
       +---> [수동 검토 (Steward)]: 신뢰도 70~95% 애매함 -> 데이터 스튜어드 승인
```

- **Blocking** : 수백만 건 전체를 $O(n^2)$ 비교할 수 없으므로, 유사한 우편번호나 성씨 등으로 블록을 묶어 비교 대상 축소.
- **확률적 매칭 (Probabilistic Matching)** : 자로-윙클러(Jaro-Winkler), 레벤슈타인 거리를 적용하여 오타나 축약어("LG전자" vs "(주)엘지전자")를 동일 개체로 인식.
- **생존 규칙(Survivorship Rule)** : 서로 다른 시스템의 컬럼 값이 충돌할 때 어떤 시스템의 값을 최종 채택할 것인가(예: 전화번호는 CRM 우선, 주소는 배송 시스템 우선).

## Ⅳ. 성공적인 전사 MDM 구축을 위한 실무 제언

- **기술 도입 전 조직 거버넌스(Data Governance) 선행** : MDM의 실패 원인 90%는 기술이 아니라 부서 간의 이기주의와 표준 불일치 때문임. 어떤 부서의 고객 코드를 마스터로 삼을지 조정할 수 있는 전사 데이터 거버넌스 위원회의 강력한 권한 부여가 최우선 전제 조건임.
- **점진적(Phased) 영역 확장 전략** : 전사 모든 엔티티를 한 번에 MDM으로 통합하려는 빅뱅 방식은 100% 실패하므로, 비즈니스 파급 효과가 가장 크고 중복이 극심한 **'고객 마스터(Customer MDM)'** 영역을 1단계로 선구축하여 성과를 입증한 후 상품, 계정 등으로 단계적 확대할 것을 제언함.
