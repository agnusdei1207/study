## 지식 로드맵 내 현재 위치

<div class="itpe-topic-path" aria-label="지식 경로"><span>데이터베이스</span><span>데이터 거버넌스·품질관리</span><strong>MDM (Master Data Management)</strong></div>

## 큰 그림과 30초 인출

```text
[MDM 아키텍처 및 4대 구축 유형]

  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │  ERP 시스템  │   │  CRM 시스템  │   │  SCM 시스템  │ (원천 업무 시스템)
  └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
         │ 원천 데이터 수집 │                  │
         ▼                  ▼                  ▼
  ┌─────────────────────────────────────────────────────────────┐
  │                      MDM 허브 엔진                          │
  │  ┌────────────────┐ ┌────────────────┐ ┌─────────────────┐  │
  │  │ 프로파일/클렌징│ │ 유사도 매칭    │ │ 머징 (속성 결합)│  │
  │  └────────────────┘ └────────────────┘ └─────────────────┘  │
  └──────────────────────────────┬──────────────────────────────┘
                                 ▼
                     ┌───────────────────────┐
                     │ 골든 레코드 (SSOT)    │ (유일한 단일 진실 공급원)
                     └───────────┬───────────┘
                                 ▼ 전사 배포 (API / Kafka CDC / 배치)
 ─────────────────────────────────────────────────────────────────────────────
 [MDM 4대 구축 유형]
  1. Registry (참조형)     : 허브는 원천 ID 매핑 색인만 보관 (원천 DB 무수정)
  2. Consolidated (통합형) : 원천 ──▶ 허브 단방향 통합 (BI 및 전사 분석용)
  3. Co-existence (공존형) : 원천 ◀──▶ 허브 양방향 동기화 (원천 분산 생성 + 허브 조율)
  4. Transaction (트랜잭션형): 허브에서 직접 마스터 데이터 생성/통제 후 원천으로 단방향 배포
```

- 본질: **기업 내 여러 부서와 이기종 시스템(ERP, CRM, SCM 등)에 중복·파편화되어 존재하는 핵심 비즈니스 엔티티(고객, 상품, 공급업체, 계정 등)를 수집, 정제, 매칭, 머징하여 전사적으로 유일한 단일 진실 공급원(SSOT, Single Source of Truth)인 골든 레코드(Golden Record)를 구축하고 동기화하는 전사 데이터 관리 체계**
- 암기: `수-정-매-머-배` (원천 수집, 표준화/정제, 매칭, 머징, 배포) / `레-통-공-트` (레지스트리형, 통합형, 공존형, 트랜잭션형)
- 판단축:
  - **레지스트리/통합형**: 원천 시스템의 프로세스 수정을 최소화하여 빠르고 안전하게 전사 가시성을 확보하되, 원천 데이터의 실시간 동기화 한계
  - **공존/트랜잭션형**: 전사 데이터의 완벽한 일관성과 중앙 통제를 달성하되, 시스템 연계 복잡도 및 현업 업무 프로세스 개편 부담 수반
- 주의: MDM 프로젝트의 주요 실패 원인은 기술적 알고리즘 부재가 아니라, 부서 간 데이터 오너십(Ownership) 갈등과 속성별 신뢰도(Trust Score) 정의 부재에 있으므로, 데이터 스튜어드십(Data Stewardship) 거버넌스 조직 정립이 선행되어야 함

## 예상문제

> 기업의 디지털 전환과 데이터 품질 보장을 위한 마스터 데이터 관리(Master Data Management, MDM)의 개념 및 필요성을 제시하고, 골든 레코드(Golden Record) 생성을 위한 핵심 프로세스와 MDM의 4대 구축 아키텍처(Registry, Consolidated, Co-existence, Transaction)를 비교 설명하시오. (25점)

## Ⅰ. 데이터 사일로와 중복을 극복하는 MDM 개요

#### 한줄 요약: 시스템별로 파편화된 핵심 기준 데이터의 단일 진실 공급원(SSOT)을 수립하여 전사적 정합성을 달성하는 거버넌스

- **추진 배경**:
  - 기업의 성장과 M&A로 인해 ERP, CRM, 쇼핑몰, 물류 시스템이 독자적인 고객 코드와 상품 코드를 발번하여 운영되는 **'데이터 사일로(Data Silo)'** 발생
  - 동일 고객에게 마케팅 메시지가 중복 발송되거나, 동일 공급업체에 대한 법인별 구매 단가가 달라 전사적 협상력이 약화되는 등 막대한 비효율 초래
- **마스터 데이터(Master Data)의 정의**:
  - 비즈니스 트랜잭션(거래, 결제 등)의 핵심 주체이자 명사형 객체로서, 시스템 전반에 걸쳐 공유되는 고객(Customer), 제품(Product), 자산(Asset), 공급업체(Vendor) 등의 **핵심 기준 정보**
- **MDM의 정의**:
  - 전사적인 관점에서 마스터 데이터를 정의, 통합, 정제, 동기화하고 이를 유지하기 위한 정책, 프로세스, 조직 및 기술 솔루션의 종합적 체계

## Ⅱ. MDM 핵심 프로세스: 골든 레코드(Golden Record) 생성 메커니즘

#### 한줄 요약: 데이터 프로파일링부터 유사도 매칭, 신뢰도 기반 속성 머징을 거쳐 단 하나의 완벽한 레코드를 도출하는 과정

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                      골든 레코드 생성 4단계 파이프라인                       │
└─────────────────────────────────────────────────────────────────────────────┘
  [1단계: 표준화 및 정제 (Cleansing)] ──▶ 주소 정규화, 전화번호 포맷 통일, 결측치 보정
  [2단계: 중복 식별 및 매칭 (Matching)]──▶ 결정론적(주민/사업자번호) + 확률론적 유사도(Jaro-Winkler)
  [3단계: 신뢰도 기반 머징 (Merging)]   ──▶ 속성별 Trust Score 우선순위에 따라 최적 필드 결합
  [4단계: 골든 레코드 생성 (SSOT)]     ──▶ 유일한 글로벌 마스터 ID 부여 및 배포 큐 적재
```

### 1. 매칭 알고리즘 (Matching Algorithm)
- **결정론적 매칭 (Deterministic Matching)**: 주민등록번호, 사업자등록번호, 이메일 등 유일 식별자가 정확히 일치하는 경우 동일인으로 판정
- **확률론적 매칭 (Probabilistic Matching)**: 이름의 오타나 주소 표기 차이를 극복하기 위해 **Jaro-Winkler 거리, Levenshtein 거리, Soundex 음성 알고리즘**을 결합하여 가중 유사도 점수(Similarity Score)가 임계값(예: 85점) 이상이면 동일 개체로 판정

### 2. 머징 및 신뢰도 점수 (Trust Score Merging)
- 두 시스템의 데이터가 매칭되었을 때, 어떤 시스템의 속성을 골든 레코드에 채택할지 결정:
  - 예: 고객 주소는 배송 시스템(SCM)의 신뢰도를 90점, 전화번호는 고객센터(CRM)의 신뢰도를 95점으로 지정하여 **속성 단위(Attribute-level) 최적 결합** 수행

## Ⅲ. MDM 4대 구축 아키텍처 유형 심층 분석

#### 한줄 요약: 원천 시스템에 미치는 영향도와 마스터 데이터 통제 수준에 따라 4가지 아키텍처로 진화

```text
┌───────────────────────────────────┬───────────────────────────────────┐
│     1. Registry (참조형)          │    2. Consolidated (통합형)       │
├───────────────────────────────────┼───────────────────────────────────┤
│ - 원천 시스템의 데이터 변경 없음  │ - 원천 데이터를 허브로 단방향 복제│
│ - 허브는 글로벌 ID와 매핑 포인터  │ - 허브에 골든 레코드를 물리 저장  │
│   인덱스만 유지 (경량, 비침투적)  │ - 주로 전사 DW/BI 분석용으로 활용 │
├───────────────────────────────────┼───────────────────────────────────┤
│     3. Co-existence (공존형)      │    4. Transactional (트랜잭션형)  │
├───────────────────────────────────┼───────────────────────────────────┤
│ - 원천 시스템에서 데이터 생성     │ - 마스터 데이터는 오직 허브에서만 │
│ - 허브로 전송되어 정제/머징 후,   │   직접 생성, 수정, 승인 통제      │
│   다시 모든 원천으로 양방향 동기화│ - 허브가 원천 DB로 단방향 강제배포│
└───────────────────────────────────┴───────────────────────────────────┘
```

### 1. 레지스트리형 (Registry Model)
- **개념**: 마스터 데이터를 물리적으로 한곳에 통합하지 않고, 각 원천 시스템의 식별자(PK)들을 연결해 주는 **글로벌 ID 교차 참조 테이블(Cross-reference Index)**만 허브에 보관
- **장단점**: 기존 시스템을 전혀 수정하지 않아 구축이 가장 빠르지만, 실시간 통합 속성 조회를 위해서는 매번 원천 DB들을 페더레이션 쿼리로 실시간 조인해야 하는 성능 한계

### 2. 통합형 (Consolidated Model)
- **개념**: 원천 시스템에서 데이터를 주기적으로 수집(ETL/배치)하여 MDM 허브에 물리적으로 골든 레코드를 생성·저장하지만, 원천 시스템으로 다시 역배포하지는 않는 단방향 구조
- **장단점**: 전사 보고서, BI 분석, 규제 준수(Compliance)에 최적이나, 운영계 원천 시스템 간의 데이터 불일치는 그대로 잔존

### 3. 공존형 (Co-existence Model)
- **개념**: 원천 시스템에서 기존처럼 마스터 데이터를 생성할 수 있으나, 생성 즉시 MDM 허브로 전송되어 정제 및 골든 레코드로 병합된 후, 변경된 최신 마스터 데이터가 **모든 원천 시스템으로 다시 동기화 배포**되는 양방향 순환 구조
- **장단점**: 운영계 시스템의 데이터 품질과 일관성을 보장하며 현업의 업무 프로세스를 크게 바꾸지 않아도 되나, 양방향 동기화에 따른 트랜잭션 정합성 제어 및 충돌 해결 복잡도 증가

### 4. 트랜잭션형 / 중앙집중형 (Transactional / Centralized Model)
- **개념**: 원천 시스템에서는 마스터 데이터의 직접 생성이 원천 차단되며, 오직 **MDM 전용 관리 포털에서만 데이터가 입력, 검증, 승인**된 후 승인 완료된 마스터 데이터가 전사 원천 시스템으로 배포되는 중앙 통제 구조
- **장단점**: 데이터 무결성과 거버넌스가 가장 완벽(100%)하지만, 레거시 시스템의 프로세스 전면 수정이 불가피하며 허브 장애 시 전사 업무가 중단되는 리스크 수반

## Ⅳ. 4대 아키텍처 유형 간 기술적·운영적 상세 비교

#### 한줄 요약: 구현 난이도, 시스템 수정 범위, 거버넌스 통제 수준, 투자 비용 관점의 종합 트레이드오프

| 비교 항목 | Registry (참조형) | Consolidated (통합형) | Co-existence (공존형) | Transactional (트랜잭션형) |
|:---|:---|:---|:---|:---|
| **골든 레코드 저장**| **미저장** (매핑 색인만) | **허브에 저장** (단방향) | **허브 및 원천에 저장** | **허브가 유일 원천** |
| **데이터 흐름** | 가상화 조회 (Federation)| 원천 $\rightarrow$ 허브 (단방향) | 원천 $\leftrightarrow$ 허브 (양방향) | 허브 $\rightarrow$ 원천 (단방향 배포) |
| **원천 시스템 수정**| **전혀 없음 (Zero)** | 거의 없음 (읽기 권한만) | 보통 (배포 수신 로직 추가) | **매우 큼 (생성 로직 제거)** |
| **데이터 정합성** | 낮음 (조회 시점에만 매핑)| 보통 (분석용으로만 일치) | **높음 (운영계 정합성 달성)**| **완벽 (원천 오염 원천 배제)** |
| **구축 난이도/비용**| 가장 낮음 / 소규모 | 낮음 / 분석 부서 주도 | 중간~높음 / 단계적 추진 | **가장 높음 / 전사 빅뱅** |
| **적합한 구축 시기**| 도입 1단계 (현황 파악) | 도입 2단계 (분석 통합) | **실무 엔터프라이즈 최적** | 신규 차세대 ERP 구축 시 |

## Ⅴ. MDM vs 데이터 웨어하우스(DW) vs 메타데이터 관리 비교

#### 한줄 요약: 현재 시점의 기준 엔티티(MDM), 과거 이력 트랜잭션 집계(DW), 데이터의 구조와 사전(메타)의 역할 분담

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    엔터프라이즈 데이터 관리 3대 축의 역할                   │
└─────────────────────────────────────────────────────────────────────────────┘
  - 메타데이터 관리 ──▶ "데이터의 정의와 구조": 표준 단어, 도메인, 테이블 정의서
  - MDM             ──▶ "데이터의 실체(Who/What)": 고객 마스터, 상품 마스터 (SSOT)
  - 데이터 웨어하우스──▶ "비즈니스 사건(Event/Fact)": 5년간의 일별 매출, 주문 이력 Fact
```

| 비교 항목 | 마스터 데이터 관리 (MDM) | 데이터 웨어하우스 (DW) | 메타데이터 관리 (Metadata) |
|:---|:---|:---|:---|
| **관리 대상** | **마스터 데이터 (고객, 상품, 계정)** | **트랜잭션 팩트(Fact) 및 과거 이력** | **데이터의 구조, 속성명, 스키마 정의** |
| **데이터 성격** | 현재 시점의 유효한 **단일 진실(SSOT)** | 시계열 분석을 위한 **스냅샷 이력 누적** | 데이터에 대한 데이터 (사전, 도메인) |
| **주요 사용자** | 운영계 시스템, 현업 비즈니스 담당자 | 경영진, 데이터 분석가, 기획 부서 | DBA, 데이터 모델러, 시스템 개발자 |
| **처리 방식** | 실시간 트랜잭션 동기화 및 API | 대용량 야간 배치 ETL / ELT | DDL 파싱, 표준화 관리 도구 |

## Ⅵ. 기업 실무 도입 시의 갈등 요소 및 단계적 로드맵 전략

#### 한줄 요약: 부서 간 데이터 오너십 분쟁을 해결하기 위한 데이터 스튜어드십 조직 구성과 3단계 점진적 도입 로드맵

### 1. 실무 도입 시의 주요 실패 요인
- **부서 간 이기주의 및 오너십 갈등**: 영업부는 간이 고객정보 입력을 선호하고, 재무부는 엄격한 사업자번호 인증을 요구할 때 합의점 부재
- **예외 처리 인력 부재**: 확률적 매칭 점수가 애매한 데이터(회색 지대, 예: 70~84점)를 수작업으로 검증할 전문 인력(Data Steward) 부재

### 2. MDM 3단계 진화 로드맵
```text
 [1단계: 가시화 단계 (통합형)]
  - ERP, CRM 데이터를 허브로 수집하여 전사 고객/상품 중복 현황을 시각화하고 거버넌스 룰 확립
           │
           ▼
 [2단계: 연계 동기화 단계 (공존형)]
  - Kafka CDC를 구축하여 원천 시스템의 변경을 실시간 동기화하고, 골든 레코드를 원천으로 피드백
           │
           ▼
 [3단계: 거버넌스 고도화 단계 (부분 트랜잭션형)]
  - 신규 상품 등 핵심 도메인에 한하여 MDM 포털에서 사전 결재 후 배포하는 승인 체계 적용
```

## Ⅶ. 데이터 아키텍트 관점의 차세대 MDM 제언

#### 한줄 요약: 모놀리식 MDM 허브의 한계를 극복하고 도메인 주도 데이터 메시(Data Mesh)와 실시간 CDC 결합

- **"중앙집중식 MDM 허브의 거대한 병목을 경계하라"**:
  - 전사 수백 개 시스템의 모든 기준정보를 거대한 단일 MDM 소프트웨어에 밀어넣으면, 스키마 변경 시마다 전사 배포가 지연되는 단일 장애점(SPOF)으로 전락함
  - 최근 아키텍처는 **도메인 주도 설계(DDD)**를 기반으로 고객 마스터, 상품 마스터, 물류 마스터를 각각의 독립된 도메인 서비스로 분리하고, **이벤트 브로커(Kafka)와 CDC(Debezium)**를 통해 탈중앙화된 페더레이션 MDM(Federated MDM)을 구축하는 추세임
- **데이터 품질 대시보드와 SLA 연계**:
  - MDM 시스템 내에 머징 성공률, 중복률, 수기 보정 대기 건수를 실시간 모니터링하는 지표를 수립하고, 데이터 스튜어드의 검수 완료 시간을 SLA로 관리하여 골든 레코드의 최신성을 보장해야 함

## 2교시 25점 답안 발췌

```text
[문제 2] 마스터 데이터 관리(MDM)의 필요성 및 4대 구축 아키텍처

Ⅰ. 데이터 사일로를 극복하는 MDM의 개념 및 필요성
 1. 배경: 시스템별 독자적 코드 발번으로 인한 데이터 중복 및 전사 정합성 왜곡 극복
 2. 정의: 전사 핵심 엔티티(고객, 상품 등)의 단일 진실 공급원(SSOT)인 골든 레코드를 구축·배포하는 체계

Ⅱ. 골든 레코드(Golden Record) 생성 핵심 프로세스
 1. 프로세스: 프로파일링/클렌징 -> 중복 매칭(결정론+확률론) -> 신뢰도 머징(Trust Score) -> 전사 배포
 2. 매칭 기술: Jaro-Winkler, Levenshtein 거리 알고리즘을 활용한 복수 시스템 레코드 유사도 판정

Ⅲ. MDM 4대 구축 아키텍처 유형 심층 비교
 ┌──────────────┬────────────────────────────┬────────────────────────────┐
 │  구축 유형   │          동작 메커니즘     │          핵심 특징         │
 ├──────────────┼────────────────────────────┼────────────────────────────┤
 │ 1. Registry  │ 허브는 원천 ID 매핑 색인만 │ 원천 시스템 무수정, 가장   │
 │    (참조형)  │ 유지하고 데이터 미보관     │ 빠르고 경량 구축 가능      │
 ├──────────────┼────────────────────────────┼────────────────────────────┤
 │ 2. Consolid. │ 원천 데이터를 허브로 단방향│ 전사 BI/DW 분석에 최적,    │
 │    (통합형)  │ 수집하여 골든 레코드 구축  │ 운영계 불일치는 잔존       │
 ├──────────────┼────────────────────────────┼────────────────────────────┤
 │ 3. Co-exist. │ 원천 생성 -> 허브 정제머징 │ 운영계 데이터 정합성 보장, │
 │    (공존형)  │ -> 원천으로 양방향 동기화  │ 엔터프라이즈 실무 표준     │
 ├──────────────┼────────────────────────────┼────────────────────────────┤
 │ 4. Transact. │ 마스터는 오직 허브에서 생성│ 완벽한 거버넌스 통제,      │
 │    (트랜잭션)│ 후 원천 시스템으로 강제배포│ 원천 시스템 프로세스 개편  │
 └──────────────┴────────────────────────────┴────────────────────────────┘

Ⅳ. 실무 성공 전략 및 아키텍처 제언
 1. 단계적 접근: 통합형(가시화) -> 공존형(실시간 동기화)으로 점진적 진화
 2. 조직 거버넌스: 데이터 스튜어드십(Data Stewardship) 조직을 신설하여 부서 간 오너십 갈등 중재
```
