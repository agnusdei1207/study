## 연관 키워드

- 데이터 복제(Replication), 동기식·비동기식·반동기식 복제, 단일 리더·다중 리더·리더리스 복제
- stale read, CRDT, GTID, RPO, RTO, Read-Your-Writes

## Ⅰ. 데이터 복제의 개요

- 핵심 요약 : 데이터 사본을 분리된 노드에 지속 동기화해 가용성과 재해 복구 수준을 확보하는 기법.
- 개념 : 한 데이터베이스의 변경 내용을 다른 노드(복제본)에 전달·반영해 같은 데이터의 사본을 여러 위치에 유지하는 기술 (**데이터 복제**, Replication).
- 배경 및 필요성 : 단일 데이터베이스의 장애나 부하가 서비스 전체 중단으로 이어지므로, 사본을 두어 장애 시에도 서비스를 이어갈 필요가 있음.
- 주요 목적 : 데이터 손실 범위를 줄이고(**복구 시점 목표**, RPO, Recovery Point Objective), 서비스 복구 시간을 단축하며(**복구 시간 목표**, RTO, Recovery Time Objective), 읽기 부하를 분산.

## Ⅱ. 데이터 복제의 특징 및 장점

- 핵심 요약 : 복제 토폴로지와 동기화 방식의 조합으로 가용성, 확장성, 정합성 수준을 설계하는 구조.

1. **단일 리더 복제** (Single-Leader Replication, 쓰기를 하나의 리더 노드가 맡고 나머지 노드는 복제본으로 동작) : 충돌이 발생하지 않아 구조가 단순함 → 쓰기 확장에는 한계.
2. **다중 리더 복제** (Multi-Leader Replication, 여러 노드가 쓰기를 받아 서로 전파) : 쓰기 분산과 지역 분산이 가능함 → 쓰기 충돌 해결 규칙이 필요.
3. **리더리스 복제** (Leaderless Replication, 클라이언트가 여러 노드에 읽기와 쓰기를 보내는 방식) : 일부 노드 장애에 강건함 → 정합성 관리 부담이 큼.
4. **동기식 복제** (Synchronous Replication, 복제본의 확인 응답을 받은 뒤 커밋) : 무손실(RPO=0) 보장 → 쓰기 지연 증가.
5. **비동기식 복제** (Asynchronous Replication, 복제본 응답을 기다리지 않고 커밋) : 빠른 응답 → 장애 시 전달되지 않은 데이터 유실 위험.
6. **반동기식 복제** (Semi-Synchronous Replication, 최소 한 개 복제본의 확인 응답 후 커밋) : 무손실에 가까운 보장과 지연의 절충.

## Ⅲ. 데이터 복제의 메커니즘 흐름

- 핵심 요약 : 커밋 확인 시점이 복제 방식을 나누고, 복제 지연이 과거 값 조회라는 정합성 문제를 만드는 흐름.
- **stale read** : 복제 지연 동안 방금 쓴 데이터가 복제본에 반영되지 않아 과거 값이 조회되는 현상.
- **Read-Your-Writes** (읽기 자신의 쓰기 보장) : 클라이언트가 쓴 값은 이후 자신의 읽기에 반드시 보이도록 보장하는 정합성 모델.

```text
[ 커밋 시점에 따른 복제 흐름 ]

(A) 동기식
  Primary → Standby 확인 → Commit

(B) 비동기식
  Primary → Commit → Standby 반영

(C) 반동기식
  Primary → 1개 이상 확인 응답 → Commit
```

```text
[ stale read 발생 흐름 ]

Client 쓰기 → Primary 커밋
                  ↓
Client 읽기 → Replica (미반영 상태)
                  ↓
        이전 값 반환 (stale read)
```

## Ⅳ. 토폴로지와 동기화 방식의 비교

- 핵심 요약 : 동기화 방식은 무손실과 지연이 맞바꿈 관계이고, 토폴로지는 충돌과 쓰기 확장이 맞바꿈 관계.

| 비교 축 | 동기식 | 비동기식 | 반동기식 |
| :--- | :--- | :--- | :--- |
| RPO | 0 (무손실) | 0 초과 (유실 가능) | 0에 가까움 |
| 쓰기 지연 | 높음 | 낮음 | 중간 |
| 처리량 | 낮음 | 높음 | 중간 |

| 비교 축 | 단일 리더 | 다중 리더 | 리더리스 |
| :--- | :--- | :--- | :--- |
| 쓰기 확장 | 제한적 | 가능 | 가능 |
| 충돌 | 발생하지 않음 | 충돌 해결 규칙 필요 | 버전 판단 필요 |
| 장애 대응 | 리더 장애 시 전환(failover) 필요 | 지역별 독립 쓰기 가능 | 일부 노드 장애에도 동작 |

## Ⅴ. 데이터 복제의 한계와 방안

- 핵심 요약 : stale read, 광역 전송 지연, 대규모 DDL 복제 지연을 GTID 기반 읽기, CRDT, 다중 스레드 복제로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| stale read | 복제 지연 동안 방금 쓴 값이 복제본에 없어 과거 값 반환 | **GTID** (Global Transaction Identifier, 트랜잭션 고유 식별자) 위치 확인 후 읽기, 쓰기 직후 읽기는 리더로 라우팅 | 복제 지연 시간 |
| 광역 전송 지연 | 광역 네트워크(WAN, Wide Area Network) 지연으로 동기 복제 응답이 느려짐 | 리전별 다중 리더 구성과 **CRDT** (Conflict-free Replicated Data Type, 충돌 없이 병합되는 복제 데이터 타입) 기반 충돌 해소 | 리전 간 복제 지연 |
| 대규모 DDL(Data Definition Language) 복제 지연 | 스키마 변경이 복제 스레드를 막아 복제본 지연 발생 | 다중 스레드 복제(MTS, Multi-Threaded Slave) 활성화와 온라인 스키마 변경 도구(pt-online-schema-change, gh-ost) 사용 | DDL 소요 시간, 복제 지연 |

## Ⅵ. 데이터 복제에 대한 기술사적 제언

- 핵심 요약 : 지리적 복제의 절충 설계, 손실 없는 충돌 해결, GTID 기반 읽기 제어로 고신뢰 복제를 구현.

1. 지리적 복제 : 리전 간에는 비동기 복제를 기본으로 두고, 결제처럼 유실이 허용되지 않는 트랜잭션만 동기 또는 반동기로 보호하는 절충 설계 필요.
2. 충돌 해결 : 최종 쓰기 우선(LWW, Last Write Wins) 대신 버전 벡터나 CRDT처럼 데이터 손실 없이 병합 가능한 구조를 우선 검토할 필요.
3. 읽기 일관성 : 업무별로 허용 가능한 stale read 범위를 정하고, GTID 기반 대기 읽기 기준을 서비스 표준에 명시할 필요.

## Ⅶ. 결론

- 핵심 요약 : 데이터 복제는 토폴로지와 동기화 방식의 조합으로 가용성과 확장성을 설계하는 핵심 기법.
- 시사점 : 업무별 허용 정합성 수준을 먼저 정한 뒤 복제 방식을 고르는 순서가 실무 설계의 출발점.
