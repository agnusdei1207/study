## 답안 골격
```text
[B+Tree] ◀━━ 머리: Ⅶ 내 의견 (리프 노드 양방향 연결 리스트를 통한 범위 스캔 최적화와 인덱스 페이지 단편화 관리)
 ┃
 ┣━ Ⅰ 개요 ───── 모든 실제 데이터 레코드를 오직 최하위 리프 노드에만 저장하고, 리프 노드들을 양방향 연결 리스트로 연결하여 범위 검색 성능을 극대화한 인덱스 표준 자료구조
 ┣━ Ⅱ 특징 ───── 내부 노드는 라우팅 키만 보관(팬아웃 극대화 $\rightarrow$ 트리 높이 축소) · 리프 노드 간 순차 연결로 수평 순차 I/O · 모든 탐색 경로 동일($O(\log N)$)
 ┣━ Ⅲ 구조 ───── 내부 노드(Index Block: 키 + 자식 노드 포인터) ┃ 리프 노드(Data Block: 키 + 데이터 RID + Prev/Next 포인터)
 ┣━ Ⅳ 흐름 ───── ① 범위 검색(`WHERE age BETWEEN 20 AND 30`) → ② 루트 노드에서 시작값(20)까지 하향 탐색 → ③ 리프 노드 도착 → ④ 리프 연결 링크를 타고 수평 순차 스캔 → ⑤ 30 초과 시 즉시 종료
 ┣━ Ⅴ 비교 ───── B-Tree vs B+Tree vs B*Tree
 ┗━ Ⅵ 실무 ───── 무작위 키 삽입으로 인한 빈번한 페이지 분할(Page Split) 및 인덱스 단편화 발생
```
- 필수 키워드: B+Tree · 내부 노드 · 리프 노드 · 양방향 연결 리스트 · 범위 스캔(Range Scan) · 팬아웃(Fan-out) · B-Tree · 클러스터드 인덱스 · 페이지 분할
- 기출: 101회 `데이터베이스 인덱스 구조로 가장 널리 사용되는 B+Tree의 구조적 특징과 B-Tree와의 차이점을 설명하시오.` → Ⅰ 정의 + Ⅲ 구조도 + Ⅴ 상세 비교표 + Ⅵ 범위 검색 우수성

## 한 줄 본질
- B-Tree는 내부 노드에도 데이터를 담아 블록당 키 수가 적고 범위 검색 시 트리를 오르내려야 함 → 내부 노드는 길잡이 키만 두고 모든 데이터는 리프에 모아 연결 리스트로 직결 → 트리 높이 최소화 및 초고속 범위 스캔 달성 / 중복 키 저장 발생


## 핵심 용어
- 팬아웃(Fan-out): 하나의 인덱스 블록이 가질 수 있는 자식 노드 포인터의 개수로, B+Tree는 내부 노드에 데이터를 넣지 않으므로 팬아웃이 수백 개로 증가하여 트리의 높이를 3~4 레벨로 극단적 압축
- 페이지 분할(Page Split): 리프 블록(16KB)이 꽉 찬 상태에서 새로운 키가 삽입될 때, 블록을 50:50으로 나누어 새 블록을 할당하는 I/O 고비용 연산

## 핵심 통찰
- 현대 거의 모든 RDBMS(MySQL InnoDB, Oracle, PostgreSQL)의 기본 인덱스는 B-Tree가 아니라 실제로는 'B+Tree'임 → 실무 쿼리의 80% 이상이 날짜나 ID 범위 검색(`BETWEEN`, `<`, `>`)인데 B-Tree는 이 범위 검색에 매우 취약하기 때문
- 내부 노드에 데이터 레코드 포인터가 없다는 것은 '블록 하나에 인덱스 키를 5배 이상 많이 채울 수 있다'는 뜻임 → 결과적으로 수억 건의 데이터도 트리의 깊이(Height)가 3~4에 불과하여, 단 3~4회의 디스크 블록 읽기만으로 원하는 행에 도달
- 리프 노드의 양방향 링크 덕분에 `ORDER BY col ASC`뿐만 아니라 `ORDER BY col DESC` 역순 스캔도 추가 정렬 비용 없이 순수 포인터 이동만으로 처리

## 이웃 토픽과 구분
- B-Tree vs B+Tree: B-Tree = 모든 노드에 데이터 포인터 분산, 임의 검색 운 좋으면 루트에서 조기 종료 / B+Tree = 오직 리프 노드에만 데이터 포인터 집중, 모든 검색이 리프까지 가야 하지만 팬아웃이 크고 범위 검색이 압도적으로 빠름

## 문제·원인·대책
- 적용 상황: 대규모 이커머스 주문 테이블의 일자별 매출 집계 쿼리 최적화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 최근 30일 주문 내역 조회 시 수백 번의 랜덤 디스크 I/O로 쿼리 타임아웃 | 인덱스 컬럼 가공으로 B+Tree 인덱스를 타지 못하고 테이블 풀스캔 발생 | 인덱스 컬럼 원본 유지 및 B+Tree 리프 노드 순차 레인지 스캔(Range Scan) 유도 | 쿼리 응답 시간 15초에서 0.03초로 500배 단축 |
| UUID v4 무작위 키를 PK로 사용하자 B+Tree 리프 노드 분할(Page Split) 빈발 | 비순차적 무작위 삽입으로 리프 블록 중간이 계속 쪼개지며 단편화율 60% 도달 | 시간순 정렬이 보장되는 UUID v7 또는 순차 시퀀스 키로 PK 전환 | 페이지 분할 90% 감소 및 버퍼 캐시 효율 극대화 |

## 이렇게 출제된다
- 제101회: "데이터베이스 인덱스 구조로 가장 널리 사용되는 B+Tree의 구조적 특징과 B-Tree와의 차이점을 설명하고, B+Tree가 대용량 데이터의 범위 검색(Range Search)에서 뛰어난 성능을 발휘하는 이유를 기술하시오." → 요구 포인트: B+Tree 구조도(내부 노드 vs 리프 노드) + B-Tree와의 5대 비교표 + 팬아웃과 트리 높이 수식 + 리프 연결 리스트 스캔 원리

## 내 의견
- [인덱스 리빌드(Rebuild) 맹신 탈피] 대량의 DELETE와 INSERT가 반복되어 B+Tree 인덱스가 비대해졌을 때 무조건 서비스 중단을 수반하는 테이블 락 리빌드를 수행하는 구태 반복 → 나라면: 온라인 인덱스 재구성(Online Index Rebuild) 명령이나 `pt-online-schema-change` 도구를 활용하여 무중단으로 페이지 단편화를 해소하고, B+Tree 리프 노드 채움 비율(Fillfactor)을 80%로 사전 설정하여 페이지 분할 빈도를 선제 억제

## 찾아볼 것
- MySQL InnoDB의 클러스터드 인덱스(Clustered Index)에서 세컨더리 인덱스의 리프 노드가 물리 행 주소(RID) 대신 PK 값을 가리키는 2단계 B+Tree 탐색 구조
