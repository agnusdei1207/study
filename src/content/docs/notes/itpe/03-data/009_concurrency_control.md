## 연관 키워드

- 동시성 제어(Concurrency Control), 트랜잭션, 직렬 가능성(Serializability), 로킹(Locking), 2PL
- 타임스탬프 순서화, 낙관적 병행 제어, MVCC, 교착상태(Deadlock), 격리 수준(Isolation Level)

## Ⅰ. 동시성 제어의 개요

- 핵심 요약 : 다중 트랜잭션의 병행 실행에서 무결성과 일관성을 지키며 직렬 가능성을 보장하는 기술.
- 개념 : 다중 사용자 환경에서 여러 트랜잭션이 데이터베이스를 동시에 공유 접근할 때, 무결성(Integrity)과 일관성(Consistency)을 해치지 않으면서 병행 실행을 제어하는 기술인 **동시성 제어** (Concurrency Control). 대상은 데이터베이스 관리 시스템(DBMS, Database Management System)의 **트랜잭션** (Transaction)이다.
- 배경 및 필요성 :
  1. 갱신 분실(Lost Update) : T1의 갱신을 T2가 덮어써서 T1의 변경이 사라짐.
  2. 모순성(Inconsistency) : T1 수행 중 T2의 일부 갱신이 반영되어 불일치 상태를 조회함.
  3. 연쇄 복귀(Cascading Rollback) : T1이 롤백되면 미커밋 데이터를 읽은 T2도 연쇄적으로 롤백해야 함.
  4. 비재현성(Unrepeatable Read) : 한 트랜잭션 안에서 같은 데이터를 다시 읽었을 때 값이 달라짐.
- 주요 목적 : **직렬 가능성** (Serializability) 보장, 즉 병행 실행 결과가 트랜잭션을 순차 실행한 결과와 같도록 하는 것.

## Ⅱ. 동시성 제어의 특징 및 장점

- 핵심 요약 : 직렬 가능성 목표 아래 로킹, 타임스탬프 순서화, 낙관적 제어, MVCC의 4대 기법이 상호 보완하는 구성.

1. 직렬 가능성 목표 : 병행 실행 결과를 순차 실행 결과와 일치시킴 → 무결성 보장. 로킹에서는 2단계 로킹 규약(2PL, Two-Phase Locking)으로 구현.
2. 4대 이상 현상 방지 : 갱신 분실, 모순성, 연쇄 복귀, 비재현성을 막는 것이 목표.
3. 4대 기법 : 로킹, 타임스탬프 순서화, 낙관적 병행 제어, 다중 버전 동시성 제어(MVCC, Multi-Version Concurrency Control) 중에서 워크로드에 맞게 선택 → 기법별 장단점을 조합.
4. 격리 수준 연계 : **격리 수준** (Isolation Level)을 조정해 정합성과 성능의 균형을 맞춤 → 워크로드별 튜닝 가능.

```text
[ 4대 동시성 이상 현상 ]

 1. 갱신 분실 (Lost Update)
    T1의 갱신을 T2가 덮어씀
 2. 모순성 (Inconsistency)
    T1이 T2의 부분 갱신을 조회
 3. 연쇄 복귀 (Cascading Rollback)
    미커밋 데이터를 읽은 T2도 롤백
 4. 비재현성 (Unrepeatable Read)
    같은 조회의 결과가 달라짐
```

## Ⅲ. 동시성 제어의 구조 (흐름)

- 핵심 요약 : 2단계 로킹 규약의 단계 구조, MVCC의 무차단 읽기 원리, 교착상태의 예방·회피·탐지 전략으로 이루어진 흐름.

```text
[ 2PL과 Strict 2PL 단계 ]

 Basic 2PL
   확장 단계 (락 획득)
          ↓ 최대 락 도달
   축소 단계 (락 해제)

 Strict 2PL
   확장 단계 (락 획득)
          ↓
   배타 락을 커밋·롤백까지 유지 후 일괄 해제
```

```text
[ MVCC 무차단 읽기 ]

 T1 (쓰기): Row A의 새 버전 V2 생성
            (커밋 대기)
 T2 (읽기): Row A 요청
          ↓ T1의 락과 무관하게
 이전 버전 V1 즉시 반환 (대기 없음)
```

- 교착상태(Deadlock) 해결 전략 :
  1. 예방(Prevention) : 타임스탬프 기반의 **Wait-Die** (오래된 트랜잭션은 대기, 젊은 트랜잭션은 중단)와 **Wound-Wait** (오래된 트랜잭션이 젊은 트랜잭션을 선점 취소).
  2. 회피(Avoidance) : 은행가 알고리즘(Banker's Algorithm)처럼 자원 할당 전에 안전 상태 여부를 검사하여 교착 가능성을 차단.
  3. 탐지·복구(Detection & Recovery) : **대기 그래프** (WFG, Wait-For Graph)를 주기적으로 검사해 사이클이 있으면 희생자(Victim)를 골라 롤백.

## Ⅳ. 동시성 제어 4대 기법의 비교

- 핵심 요약 : 확실한 차단의 로킹, 순서 고정의 타임스탬프, 읽기 최적화의 낙관적 제어, 무차단 읽기의 MVCC로 구분.

| 제어 기법 | 동작 원리 및 메커니즘 | 직렬성 보장 방식 | 주요 장단점 |
|---|---|---|---|
| 로킹(Locking) | 접근 전 Lock 획득, 완료 후 해제. 공유 락(S-Lock)과 배타 락(X-Lock) 사용 | 2PL 준수(확장 단계에서 획득, 축소 단계에서 해제) | 충돌 차단이 확실함 / 교착상태 발생 가능, 동시성 저하 |
| 타임스탬프 순서화 | 트랜잭션 시작 시 고유 타임스탬프 TS(T)를 부여하고 읽기·쓰기 타임스탬프와 비교 | 진입 순서(TS)를 직렬 순서로 고정, 위반 시 중단 후 재시작 | 교착상태 배제 / 연쇄 복귀 위험, 잦은 중단으로 처리량 저하 |
| 낙관적 병행 제어 | 수행 중에는 락 없이 작업하고 커밋 시점에 충돌을 검증(읽기→확인→기록) | 검증 단계에서 읽기 집합과 쓰기 집합의 겹침 확인 | 읽기 위주 환경에서 처리량이 높음 / 쓰기 충돌이 많으면 롤백 비용 급증 |
| MVCC | 갱신 시 원본을 덮어쓰지 않고 새 버전을 만들어 타임스탬프와 함께 보관 | 읽기는 트랜잭션 시작 시점의 스냅샷 버전을 참조 | 읽기와 쓰기가 서로 막지 않음(Oracle, PostgreSQL 등) / 버전 저장 공간 관리 부담 |

## Ⅴ. 동시성 제어의 한계와 방안

- 핵심 요약 : 교착상태와 락 경합, 낙관적 제어의 중단 폭주, MVCC의 버전 누적을 예방 정책, 재시도 전략, 정리 정책으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 비관적 락 기반 교착상태와 병목 | 2PL 환경에서 자원 점유 순서가 엇갈리면 교착상태가 잦고, 락 에스컬레이션으로 처리량이 급락 | 자원 획득 순서의 전사 표준화, 락 타임아웃 설정, Wait-Die·Wound-Wait 기반 선제 예방 | 교착상태 발생 건수, 락 대기 시간 |
| **낙관적 동시성 제어** (OCC, Optimistic Concurrency Control)의 중단 폭주 | 핫스팟 데이터에서 검증 실패가 반복되어 재시도 루프가 자원을 낭비 | 분산 카운터와 파티셔닝으로 경합 분산, 지수 백오프와 지터(Jitter)를 적용한 재시도 | 재시도 횟수, 중단률 |
| MVCC 환경의 버전 누적 | 장기 실행 트랜잭션이 이전 버전을 붙잡아 테이블 팽창(Table Bloat)이나 스냅샷 만료 오류(ORA-01555)가 발생 | 트랜잭션 실행 시간 임계치 모니터링과 자동 종료, VACUUM 튜닝, Undo 세그먼트의 동적 확장 | 장기 트랜잭션 수, 테이블 팽창률 |

## Ⅵ. 고성능 동시성 제어 설계에 대한 기술사적 제언

- 핵심 요약 : 격리 수준의 전략적 조정, 트랜잭션 범위의 최소화, 분산 환경에서의 분산 락 선별 도입.
- 격리 수준을 기본값(Repeatable Read 또는 Read Committed)에 맹목적으로 두지 말고, 단순 집계나 통계 쿼리에는 낮은 격리 수준이나 스냅샷 읽기를 적용해 락 경합을 줄이는 것이 바람직함.
- 트랜잭션 블록 안에서 외부 API 호출, 파일 입출력, 무거운 연산을 빼서 락 유지 시간을 밀리초 단위로 줄이는 설계가 필요함.
- 마이크로서비스 아키텍처(MSA, Microservice Architecture)처럼 단일 DB 로킹이 불가능한 환경에서는 Redis Redlock이나 Zookeeper 기반 분산 락을 임계 영역에만 선별적으로 도입하는 것이 현실적임.

## Ⅶ. 결론

- 핵심 요약 : 동시성 제어는 직렬 가능성 보장과 처리량 확보의 균형을 설계하는 일이 핵심인 기술.
- 시사점 : 워크로드별 기법과 격리 수준을 고르고, 트랜잭션 범위를 작게 유지하는 것이 실효성을 결정함.
