## 답안 골격
```text
[데이터 무결성 (Data Integrity)] ◀━━ 머리: Ⅶ 내 의견 (DB 물리 제약조건과 애플리케이션 검증 계층의 역할 분담 및 사후 정합성 배치 감사)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터의 생성, 저장, 갱신, 전송 등 라이프사이클 전반에서 데이터의 정확성(Accuracy), 일관성(Consistency), 유효성(Validity)을 보장하는 특성
 ┣━ Ⅱ 특징 ───── 4대 무결성 제약 · ACID 트랜잭션 연계 · 비즈니스 규칙 강제 · 동시성 오염 방지 · 데이터 품질의 핵심 척도
 ┣━ Ⅲ 구조 ───── 개체 무결성(PK) / 참조 무결성(FK) / 도메인 무결성(CHECK, Type) / 사용자 정의 무결성(Trigger, Rule)
 ┣━ Ⅳ 흐름 ───── ① 사용자 입력 검증 → ② 애플리케이션 비즈니스 룰 검사 → ③ DBMS 트랜잭션 격리/락 → ④ DDL 제약조건 평가 → ⑤ 커밋 및 디스크 기록
 ┣━ Ⅴ 비교 ───── 데이터 무결성 vs 데이터 보안성 (정확성·일관성·오염방지 vs 기밀성·비인가접근차단)
 ┗━ Ⅵ 실무 ───── 성능을 이유로 FK 제거 시 고아 레코드 발생 / 분산 환경(MSA) 무결성 붕괴 / 캐시-DB 불일치
```
- 필수 키워드: 데이터 무결성 · 개체 무결성 · 참조 무결성 · 도메인 무결성 · 사용자 정의 무결성 · PK/FK · CHECK 제약 · 트랜잭션 ACID
- 배점 전략: 10점 = Ⅰ → Ⅲ 4대 무결성 매핑 구조도 → Ⅵ 실무 FK 제거 부작용 / 25점 = Ⅰ~Ⅶ, Ⅳ 다층 검증 파이프라인 및 Ⅵ MSA 환경 최종 무결성 보장
- 기출: 128회 `관계형 데이터베이스에서 데이터 무결성(Data Integrity)의 개념과 4대 무결성 제약조건의 유형 및 보장 방안을 설명하시오.` → Ⅰ 개념 + Ⅲ 4대 제약조건 + Ⅳ 보장 메커니즘

## 한 줄 본질
- 동시 다발적 갱신과 비즈니스 로직 오류로 인한 데이터 오염 및 쓰레기값 적재 → RDBMS 제약조건(PK/FK/CHECK)과 ACID 트랜잭션 제어를 통해 데이터 정확성 강제 → 비즈니스 신뢰 확보 / 과도한 물리 제약 시 쓰기 성능 저하

## 핵심 그림
```text
[데이터 무결성 4대 제약조건 및 다층 방어 체계]

 ┌─────────────────────────────────────────────────────────────┐
 │  1. 개체 무결성 (Entity Integrity)                           │
 │     - 기본키(PK)는 중복될 수 없고, NULL을 허용하지 않음     │
 ├─────────────────────────────────────────────────────────────┤
 │  2. 참조 무결성 (Referential Integrity)                      │
 │     - 외래키(FK)는 참조하는 부모 PK와 일치하거나 NULL이어야 함│
 │     - 부모 행 삭제/수정 시 RESTRICT, CASCADE, SET NULL 제어 │
 ├─────────────────────────────────────────────────────────────┤
 │  3. 도메인 무결성 (Domain Integrity)                         │
 │     - 컬럼 값은 정의된 타입, 길이, 허용 범위(CHECK, ENUM) 준수│
 ├─────────────────────────────────────────────────────────────┤
 │  4. 사용자 정의 무결성 (User-Defined Integrity)               │
 │     - 비즈니스 업무 규칙(트리거, Stored Procedure, 앱 로직) │
 └─────────────────────────────────────────────────────────────┘
                               ▲
                               │ 계층적 보장 메커니즘
 ┌───────────────┐     ┌───────────────┐     ┌───────────────┐
 │ 애플리케이션  │ ──► │  DBMS DDL     │ ──► │ DBMS 엔진     │
 │ 유효성 검증   │     │ 제약조건 선언 │     │ 트랜잭션 ACID │
 └───────────────┘     └───────────────┘     └───────────────┘
```

## 핵심 용어
- 참조 무결성 옵션: 부모 테이블의 행 변경 시 자식 테이블의 동기화 방식(`ON DELETE CASCADE`, `ON DELETE RESTRICT`, `ON DELETE SET NULL`)
- 고아 레코드(Orphan Record): 부모 테이블의 데이터가 삭제되었으나 자식 테이블의 FK 제약이 없어 부모 ID를 참조한 채 방치된 무결성 파괴 데이터

## 핵심 통찰
- 실무 대규모 트래픽 환경에서 성능과 데드락 회피를 이유로 '물리적 FK 제약조건'을 삭제하는 경우가 흔함 → 이 순간 무결성 책임이 100% 애플리케이션으로 넘어가며, 개발자의 사소한 버그 하나로 수백만 건의 고아 데이터가 누적됨
- 마이크로서비스 아키텍처(MSA)에서는 DB가 물리적으로 쪼개지므로 RDBMS 고유의 참조 무결성이 원천 붕괴함 → 사가(Saga) 패턴의 보상 트랜잭션과 아웃박스 패턴을 통한 '최종 일관성(Eventual Consistency)'으로 무결성의 패러다임을 전환해야 함
- 데이터 무결성은 DB 내부만의 문제가 아니라 '입력-전송-저장'의 엔드투엔드(E2E) 무결성으로 확장되어야 함

## 이웃 토픽과 구분
- 무결성(Integrity) vs 보안성(Security): 무결성 = 데이터가 훼손되거나 논리적으로 모순되지 않고 올바른 상태 유지 / 보안성 = 비인가자에게 노출되지 않고(기밀성), 필요할 때 접근 가능한(가용성) 권한 통제

## 문제·원인·대책
- 적용 상황: 대용량 쇼핑몰의 물리 FK 제약조건 제거 후 운영 데이터 오염
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 탈퇴한 회원 ID를 참조하는 미배송 주문 레코드가 남아 결제 정산 불일치 | 쓰기 성능 확보를 위해 물리 FK 제약을 삭제하고 코드 레벨 처리 누락 | 심야 배치로 고아 레코드 검증 SQL 자동 실행 및 보정 프로세스 구축 | 정산 불일치 건수 0건 유지 및 이상 데이터 준실시간 적발 |
| 동시 주문 처리 시 상품 재고 수량이 음수(-3)로 갱신되는 정합성 훼손 | 트랜잭션 격리 수준 미흡 및 CHECK 제약 부재 | 컬럼에 `CHECK (stock_qty >= 0)` 제약 부여 및 비관적 락(`FOR UPDATE`) 적용 | 재고 초과 차감 원천 차단 및 도메인 무결성 보장 |

## 이렇게 출제된다
- 제128회: "데이터베이스에서 데이터 무결성(Data Integrity)의 중요성을 서술하고, 4대 무결성 제약조건의 개념 및 DBMS에서 이를 구현하기 위한 기법을 설명하시오." → 요구 포인트: 무결성 정의 + 4대 제약조건(개체, 참조, 도메인, 사용자정의) + DDL 제약(PK/FK/CHECK) 및 트랜잭션 보장 방안

## 내 의견
- [DB 제약조건 전면 삭제 유행의 경계] "MSA나 성능 최적화를 하려면 DB의 FK, CHECK를 다 빼야 한다"는 속설을 맹신하여 단일 DB 모놀리스 시스템에서도 제약조건을 전부 날려버리는 안티패턴 만연 → 나라면: 단일 DB 도메인 내에서는 DDL 수준의 제약조건(PK, FK, NOT NULL, CHECK)을 100% 선언하여 DB 엔진의 물리적 최종 방어선을 유지하고, MSA 서비스 간 경계에서만 논리적 이벤트 정합성 모델을 적용

## 찾아볼 것
- 블록체인 및 불변 원장(Ledger Database)에서 암호학적 해시 체인을 이용한 위변조 방지 데이터 무결성 검증 구조
