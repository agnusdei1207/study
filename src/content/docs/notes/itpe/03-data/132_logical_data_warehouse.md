## 연관 키워드

- 논리적 DW 아키텍처 (DW: Data Warehouse), 데이터 패브릭(Data Fabric), 연합 쿼리 엔진(Federated Query Engine)
- 의미 계층(Semantic Layer), 통합 보안 게이트웨이, 쿼리 푸시다운, 데이터 메시(Data Mesh), CDC, 워크로드 관리(WLM)

## Ⅰ. 논리적 DW 아키텍처의 개요

- 핵심 요약 : 이종 분산 저장소를 연결 계층으로 묶어 단일 논리적 접근 지점을 제공하는 전사 데이터 플랫폼 구조.
- 개념 : 정형 EDW(Enterprise Data Warehouse), 데이터 레이크, 실시간 스트림, SaaS(Software as a Service) 데이터처럼 분산된 저장소를 **데이터 패브릭** (Data Fabric, 이종 데이터를 공통 메타데이터와 접근 계층으로 엮는 설계 개념)으로 묶어 사용자에게 단일 접근 지점을 주는 **논리적 DW 아키텍처** (Logical DW Architecture).
- 배경 : 모놀리식 단일 저장소는 데이터 볼륨 증가, 소스 다양화, 실시간 분석 요구에 대응하기 어려움.
- 필요성 : 민첩성과 비용 효율성을 함께 달성하는 유연한 데이터 플랫폼 구조가 필요함.
- 주요 목적 : 데이터 이동 최소화, 단일 논리 접근 제공, 전사 거버넌스 일관성 확보.

## Ⅱ. 논리적 DW 아키텍처의 특징 및 장점

- 핵심 요약 : 분산 질의 실행, 지표 정의 계층, 통합 보안, 고속 캐시의 4대 구성 블록이 이종 저장소를 하나의 접근 경험으로 묶는 구조.

1. **연합 쿼리 엔진** (Federated Query Engine, 이종 DBMS(Database Management System)의 SQL(Structured Query Language) 문법 차이를 추상화하고 분산 실행 계획을 세우는 엔진) : 여러 저장소를 한 번의 질의로 다룸 → 사용자가 저장소 위치를 의식하지 않음.
2. **의미 계층** (Semantic Layer, 비즈니스 용어와 물리 스키마의 매핑을 관리하는 계층) : 매출, 활성 사용자 같은 지표의 계산식을 한곳에서 관리 → 지표 불일치 감소.
3. **통합 보안 게이트웨이** : 저장소 위치와 무관하게 역할에 따른 동적 컬럼 마스킹과 **행 수준 보안** (RLS, Row-Level Security) 강제 → 보안 정책 일관성 확보.
4. **고속 버퍼·캐시 계층** : 원격 스토리지의 읽기 지연을 분산 인메모리 티어링으로 완화 → 반복 질의의 응답 속도 향상.

```text
[ 논리적 DW 4대 구성 블록 ]

1. 서비스·분석 소비 계층
   셀프서비스 분석, 대화형 질의, 머신러닝 서빙
            ↓
2. 연합 쿼리·가상화 계층
   분산 옵티마이저, 연산 위임, 캐싱
            ↓
3. 거버넌스·보안 계층
   단일 보안 정책, 카탈로그, 개인정보 마스킹
            ↓
4. 이종 분산 스토리지 계층
   DW, 객체 스토리지, 비관계형 DB, 스트림
```

## Ⅲ. 논리적 DW 아키텍처의 구조 (흐름)

- 핵심 요약 : 소비 계층에서 연합 쿼리 계층을 거쳐 이종 스토리지 계층으로 질의가 분산 실행되는 4단계 구조.
- 의미 계층은 비즈니스 용어와 물리 스키마의 매핑을 관리해 사용자가 지표 기반으로 질의하게 함.
- 연합 쿼리 엔진은 질의를 분해해 각 저장소의 네이티브 엔진에 **쿼리 푸시다운** (Query Pushdown, 필터와 집계를 원천 엔진에 위임하는 기법)으로 실행한 뒤 결과를 메모리에서 병합.
- **비용 기반 옵티마이저** (CBO, Cost-Based Optimizer) : 실행 비용을 추정해 최적의 분산 계획을 고르는 구성 요소.

```text
[ 질의 처리 흐름 ]

사용자·분석 도구
      ↓
의미 계층 (지표 정의 해석)
      ↓
연합 쿼리 엔진 (분해·계획)
      ↓
원천별 푸시다운 실행
      ↓
결과 병합 후 반환
```

```text
[ 연합 쿼리 엔진 내부 처리 ]

SQL 파싱
      ↓
논리적 계획 수립
      ↓
CBO 기반 실행 계획 선택
      ↓
푸시다운 실행 / 캐시 조회 / 분산 병렬 실행
```

## Ⅳ. 물리적 DW 아키텍처와의 비교

- 핵심 요약 : 물리적 DW는 단일 저장소 중심의 배치 적재, 논리적 DW는 분산 가상화 중심의 실시간 질의라는 패러다임 차이.
- 선택 기준 : 고성능 집계와 강한 일관성이 우선이면 물리적 DW, 실시간성과 저장소 독립 확장이 우선이면 논리적 DW 아키텍처를 검토.

| 비교 항목 | 물리적 DW 아키텍처 | 논리적 DW 아키텍처 |
| :--- | :--- | :--- |
| 데이터 저장 | 중앙 저장소에 ETL(Extract, Transform, Load)로 복사 적재 | 원천 저장소를 유지하고 가상화 계층에서 통합 질의 |
| 실시간성 | 배치 주기에 제한 | 원천 시스템의 실시간 데이터 접근 |
| 스토리지 비용 | 중복 저장으로 증가 | 중복 저장을 줄여 비용 절감 |
| 쿼리 성능 | 사전 처리된 저장소로 고성능 | 분산 조인으로 지연 가능성 |
| 확장성 | 중앙 저장소의 스케일업 한계 | 저장소별 독립 확장 가능 |
| 데이터 일관성 | 단일 저장소로 관리 용이 | 원천 간 정합성 관리 필요 |

## Ⅴ. 논리적 DW 아키텍처의 장점과 한계

- 핵심 요약 : 유연성과 실시간성이 우수하지만 분산 쿼리 최적화 복잡성과 통합 보안 정책의 일관성 관리가 과제.

1. 아키텍처 민첩성 : 이종 저장소를 물리적으로 통합하지 않고도 단일 접근 지점 제공.
2. 실시간 분석 체계 : 원천 시스템의 실시간 데이터를 직접 접근.
3. 비용 효율성 : 데이터 중복 저장을 줄여 스토리지 비용 절감.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 분산 쿼리 최적화 한계 | 이종 엔진의 연산 특성 차이로 최적 계획 수립이 어려움 | 커넥터별 통계 수집 고도화, 동적 파티션 프루닝(Dynamic Partition Pruning)과 런타임 필터링 활성화 | 질의 응답 시간 |
| 글로벌 보안·거버넌스 정책 일관성 | 저장소마다 권한 모델이 달라 정책 누락 발생 | 전사 거버넌스 솔루션(Apache Ranger, Immuta) 연계로 컬럼 마스킹과 행 필터링을 중앙 통제 | 정책 위반 건수 |
| 가상화 서버 메모리 고갈 (OOM, Out of Memory) | 복잡한 비즈니스 로직과 대용량 집계가 가상화 서버 메모리를 초과 | **워크로드 관리** (WLM, Workload Management)로 쿼리 쿼터 적용, 무거운 집계는 dbt 기반 물리 ELT(Extract, Load, Transform) 테이블로 분리 | 메모리 사용률, OOM 발생 건수 |

```text
[ 쿼리 푸시다운 전후 비교 ]

[기존] 원천 전체 데이터 전송
  원천 DW → (대량 전송) → 가상화 엔진
  → 엔진 메모리 부담과 네트워크 포화

[개선] 조건과 집계를 원천으로 밀어냄
  가상화 엔진 → (필터·집계 질의) → 원천 DW
  원천 DW → (결과만 전송) → 가상화 엔진
```

## Ⅵ. 논리적 DW 아키텍처에 대한 기술사적 제언

- 핵심 요약 : 캐시 무효화 체계, 데이터 메시 거버넌스 연계, 커넥터 품질 관리가 성공적 구축의 핵심 조건.

1. 캐시 무효화 : 가상화 캐시가 원천 갱신을 제때 반영하지 못하면 분석 데이터가 어긋나므로, **변경 데이터 캡처** (CDC, Change Data Capture)로 원천 변경을 수신해 해당 논리 뷰의 캐시를 즉시 무효화하는 구조 구현 필요.
2. 데이터 메시 연계 : 논리적 DW 아키텍처는 기술적 가상화에 그치지 않고, 도메인 팀이 데이터를 제품으로 등록해 전사가 공유하도록 하는 **데이터 메시** (Data Mesh, 도메인별로 데이터 소유와 책임을 나누는 거버넌스 모델)의 실행 플랫폼으로 위치시킬 필요.
3. 커넥터 품질 : 이종 엔진 간 쿼리 품질은 커넥터 구현에 좌우되므로, 통계 수집 주기 관리와 정기 성능 벤치마크를 운영 체계로 둘 필요.

## Ⅶ. 결론

- 핵심 요약 : 논리적 DW 아키텍처는 데이터 패브릭 기반의 유연한 플랫폼이며, 최적화와 거버넌스 관리가 성패를 좌우.
- 시사점 : 아키텍처의 가치는 연결 기술보다 측정과 정책 관리에서 드러나므로, 도입 전에 성능과 보안 기준을 먼저 정하는 것이 바람직.
