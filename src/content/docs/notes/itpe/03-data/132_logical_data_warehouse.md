## 연관 키워드

- 논리적 DW 아키텍처 (DW: Data Warehouse)

## Ⅰ. 논리적 DW(Data Warehouse) 아키텍처의 개요

- 핵심 요약 : 이종 분산 저장소를 데이터 패브릭으로 결합하여 단일 논리적 액세스 지점을 제공하는 전사 데이터 플랫폼 아키텍처
- 개념 : 논리적 DW(Data Warehouse) 아키텍처는 정형 비즈니스 데이터(EDW, Enterprise Data Warehouse), 빅데이터 레이크(Hadoop/S3), 실시간 이벤트 스트림(Kafka), 클라우드 SaaS(Software as a Service) 데이터 등 분산·이질적인 저장소를 하나의 논리적 데이터 패브릭(Data Fabric)으로 결합하여 사용자에게 단일한 논리적 액세스 지점을 제공하는 전사 데이터 플랫폼 아키텍처
- 배경 : 모놀리식 단일 저장소 아키텍처는 데이터 볼륨 증가, 이종 소스 다양화, 실시간 분석 요구 증가에 대응하기 어려운 한계 존재
- 필요성 : 아키텍처의 민첩성(Agility)과 비용 효율성을 동시에 달성할 수 있는 유연한 데이터 플랫폼 구조 필요
- 주요 목적 : 데이터 이동 최소화, 단일 논리적 액세스 제공, 전사 데이터 거버넌스 일관성 확보

## Ⅱ. 논리적 DW(Data Warehouse) 아키텍처의 특징

- 핵심 요약 : 연합 쿼리, 의미 계층, 통합 보안 게이트웨이, 이종 스토리지를 4대 핵심 빌딩 블록으로 구성
- 특징 1 : 연합 쿼리 엔진(Federated Query Engine) — 이종 DBMS(Database Management System) 간 SQL(Structured Query Language) 문법 차이를 추상화하고 최적의 분산 실행 계획 수립
- 특징 2 : 의미 계층(Semantic Layer) — 비즈니스 메트릭(매출, 활성 유저 등)의 계산 공식을 중앙 단일화하여 지표 일관성 확보
- 특징 3 : 통합 보안 게이트웨이 — 저장소 위치와 무관하게 사용자 역할에 따른 전사 동적 컬럼 마스킹 및 RLS(Row-Level Security, 행 수준 보안) 강제
- 특징 4 : 고속 버퍼/캐시 — 원격 스토리지(S3(Simple Storage Service) 등)의 읽기 지연을 극복하기 위한 분산 인메모리 티어링(Tiering) 제공

```text
[ 논리적 DW 아키텍처 4대 구성 블록 ]
+-------------------------------------------------------------------------+
| [1. 서비스 및 분석 소비 계층]                                            |
| - 셀프서비스 BI, Ad-hoc 대화형 SQL, 머신러닝 피처 서빙                  |
+-------------------------------------------------------------------------+
| [2. 연합 쿼리 및 가상화 계층 (Federated Execution & Semantic Layer)]    |
| - 분산 옵티마이저, 푸시다운(Pushdown), 데이터 계보(Lineage), 캐싱       |
+-------------------------------------------------------------------------+
| [3. 데이터 거버넌스 및 보안 계층]                                        |
| - RBAC/ABAC 단일 보안 정책 강제, 데이터 카탈로그, PII(Personally Identifiable Information) 마스킹 |
+-------------------------------------------------------------------------+
| [4. 이종 분산 스토리지 계층]                                             |
| - 엔터프라이즈 DW | 클라우드 객체 스토리지 | NoSQL(Not Only SQL)/시계열 | 실시간 스트림 |
+-------------------------------------------------------------------------+
```

## Ⅲ. 논리적 DW(Data Warehouse) 아키텍처의 구조 (흐름)

- 핵심 요약 : 소비 계층에서 연합 쿼리 계층을 거쳐 이종 분산 스토리지 계층으로 쿼리가 분산 실행되는 4단계 계층 구조

```text
[ 논리적 DW 아키텍처 데이터 흐름 ]
[사용자/BI 도구]
       |
       v
[의미 계층: 메트릭 정의 해석]
       |
       v
[연합 쿼리 엔진: 쿼리 분해 및 실행 계획 수립]
       |
       +-------+-------+-------+
       |       |       |       |
       v       v       v       v
   [EDW]   [레이크]  [NoSQL]  [스트림]
       |       |       |       |
       +-------+-------+-------+
               |
               v
       [결과 병합 및 반환]
```

```text
[ 연합 쿼리 엔진 내부 처리 과정 ]
[SQL 파싱] --> [논리적 계획] --> [비용 기반 최적화(CBO)]
                                       |
                    +------------------+------------------+
                    |                  |                  |
                    v                  v                  v
             [푸시다운 실행]   [캐시 조회]      [분산 병렬 실행]
```

- 의미 계층은 비즈니스 용어와 물리적 스키마 간 매핑을 관리하여 사용자가 메트릭 기반으로 쿼리 작성 가능
- 연합 쿼리 엔진은 쿼리를 분해하여 각 저장소의 네이티브 엔진으로 푸시다운 실행 후 결과를 인메모리에서 병합

## Ⅳ. 물리적 DW(Data Warehouse) 아키텍처와의 비교

- 핵심 요약 : 물리적 DW는 단일 저장소 중심의 배치 적재, 논리적 DW는 분산 가상화 중심의 실시간 질의라는 패러다임 차이

| 비교 항목 | 물리적 DW 아키텍처 | 논리적 DW 아키텍처 |
| :--- | :--- | :--- |
| 데이터 저장 방식 | 중앙 단일 저장소에 ETL(Extract, Transform, Load)로 복사 적재 | 원천 저장소 유지, 가상화 계층에서 통합 질의 |
| 실시간성 | 배치 주기 제한적 | 원천 시스템 실시간 데이터 접근 |
| 스토리지 비용 | 중복 저장으로 비용 증가 | 중복 없음, 비용 절감 |
| 쿼리 성능 | 사전 처리된 단일 저장소로 고성능 | 분산 조인으로 인한 잠재적 지연 |
| 확장성 | 중앙 저장소 스케일업 한계 | 저장소 독립 확장 가능 |
| 데이터 일관성 | 단일 저장소로 일관성 보장 용이 | 원천 간 정합성 관리 필요 |

## Ⅴ. 논리적 DW(Data Warehouse) 아키텍처의 장점과 한계

- 핵심 요약 : 유연성과 실시간성이 우수하지만 분산 쿼리 최적화 복잡성과 통합 보안 정책 일관성 관리가 과제
- 장점 :
  1. 아키텍처 민첩성 — 이종 저장소 통합 없이 단일 액세스 지점 제공
  2. 실시간 분석 체계 — 원천 시스템 실시간 데이터 직접 접근
  3. 비용 효율성 — 데이터 중복 저장 제거로 스토리지 비용 절감
- 한계점 :
  1. 이종 엔진 간 연산 특성 차이로 인한 분산 쿼리 최적화기(Optimizer)의 한계
     - 해결 방안 : 커넥터별 통계정보 수집기(Catalog Stats Collector) 고도화, 동적 파티션 프루닝(Dynamic Partition Pruning) 및 런타임 필터링(Runtime Filtering) 엔진 활성화
  2. 글로벌 데이터 보안 및 거버넌스 정책 일관성 보장 난제
     - 해결 방안 : 전사 통합 거버넌스 솔루션(Apache Ranger, Immuta) 연계를 통한 컬럼 레벨 마스킹 및 행 레벨 필터링(Row-Level Security) 중앙 통제
  3. 복잡한 비즈니스 로직 연산 시 가상화 서버 메모리 고갈(OOM, Out of Memory)
     - 해결 방안 : 워크로드 관리(WLM: Workload Management) 기반 쿼리 리소스 쿼터제 시행, 무거운 집계 워크로드는 dbt 기반 물리적 ELT(Extract, Load, Transform) 테이블 생성으로 유연한 하이브리드 운영

```text
[ 쿼리 푸시다운 전후 비교 ]
[ 비효율적 가상화 (전체 데이터 네트워크 전송) ]
[LDW Engine] <=== (1억 건 전체 테이블 전송) === [Oracle DW: 1억 건]
- LDW 엔진 메모리 폭발, 네트워크 포화

[ 쿼리 푸시다운 적용 (스마트 최적화) ]
[LDW Engine] ---> [WHERE date >= '2026-01-01' 집계 푸시다운] ---> [Oracle DW]
             <=== (집계 결과 1,000건만 전송) <==================+
```

## Ⅵ. 논리적 DW(Data Warehouse) 아키텍처에 대한 기술사적 제언

- 핵심 요약 : 캐시 무효화 체계, Data Mesh 거버넌스 연계, 워크로드 관리 도입이 성공적 구축의 핵심 조건
- 제언 1 : 데이터 캐싱 계층의 정교한 무효화(Invalidation) 전략 — 가상화 캐시가 원천 시스템 갱신 사항을 제때 반영하지 못하면 분석 데이터 불일치가 발생하므로, CDC(Change Data Capture)(Debezium) 이벤트를 수신하여 원천 데이터 변경 시 해당 논리 뷰 캐시 즉시 무효화하는 이벤트 기반 캐시 제어 체계 구현 필요
- 제언 2 : Data Mesh 거버넌스와의 연계 — 논리적 DW 아키텍처는 기술적 가상화에 그치지 않고, 각 도메인 팀이 자체 데이터를 데이터 제품(Data as a Product)으로 등록하고 가상화 계층을 통해 전사 공유하는 페더레이션 거버넌스(Data Mesh)의 기술적 실행 플랫폼으로 포지셔닝 필요
- 제언 3 : 커넥터 품질 관리 체계 — 이종 엔진 간 쿼리 최적화 품질이 커넥터 구현에 좌우되므로, 커넥터 통계정보 수집 주기 관리와 정기적 성능 벤치마크 체계 수립 필요

## Ⅶ. 결론

- 핵심 요약 : 논리적 DW 아키텍처는 가상화 기반의 유연한 데이터 플랫폼이지만 최적화와 거버넌스 관리가 성패를 좌우
- 요약 : 논리적 DW 아키텍처는 서비스/연합 쿼리/거버넌스/이종 스토리지 4대 블록으로 구성되며, 연합 쿼리 엔진과 의미 계층을 통해 이종 저장소를 단일 논리적 액세스 지점으로 통합하는 데이터 패브릭 기반 아키텍처
- 시사점 : 물리적 DW와 논리적 DW는 상보적 관계로, 사전 처리된 고속 집계가 필요한 워크로드는 물리적 적재, 실시간·이종 소스 통합 분석이 필요한 워크로드는 논리적 가상화로 분리 운영하는 하이브리드 접근이 효과적이며, 전사 통합 보안 정책 관리와 커넥터 품질 관리가 지속적 과제
