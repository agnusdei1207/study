## 핵심 용어
- 스키마 링킹(Schema Linking): 자연어 질문에 등장한 표현(예: "구매액")을 실제 데이터베이스의 특정 테이블과 컬럼(예: `orders.total_amount`)에 정확히 결속시키는 사전 매핑 기술
- 실행 정확도(Execution Accuracy, EX): 생성된 SQL이 문법적으로 맞는지를 넘어, 실제 데이터베이스에서 실행했을 때 골든 정답 SQL과 동일한 결과 테이블을 반환하는지를 측정하는 벤치마크 척도

## 핵심 통찰
- LLM에 수백 개의 전체 DB DDL을 통째로 프롬프트에 넣으면 컨텍스트 윈도우 한계와 어텐션 희석으로 100% 환각이 발생함 → 질문과 연관된 3~5개 핵심 테이블만 RAG로 골라내는 '스키마 프루닝'이 선행되어야 함
- 완벽한 SQL을 한 번에 뽑는 것은 불가능함 → 생성된 SQL을 테스트 DB에 `EXPLAIN`으로 Dry-run 돌려보고, 에러 발생 시 에러 로그를 LLM에 다시 먹여 스스로 고치게 하는 '셀프 디버깅(Self-Correction) 루프'가 정확도를 20% 이상 끌어올림
- TEXT2SQL의 최우선 순위는 '보안'임 → 생성된 SQL에 `UPDATE`, `DELETE`, `DROP`이 섞이거나 악의적 프롬프트 인젝션으로 권한 밖의 인사/급여 테이블을 조회하지 못하도록 DB 사용자 계정을 철저히 'Read-Only'로 제한하고 뷰(View)로 격리해야 함

## 이웃 토픽과 구분
- TEXT2SQL vs NL2Code: NL2Code = Python, Java 등 범용 프로그래밍 언어를 생성하는 상위 포괄 기술 / TEXT2SQL = RDBMS의 테이블 스키마, 무결성 제약, SQL Dialect에 특화되어 정형 데이터를 질의하는 도메인 특화 기술

## 문제·원인·대책
- 적용 상황: 기업 내부 경영정보시스템(MIS)의 자연어 질의 챗봇 서비스 구축
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 생성된 SQL이 실제 존재하지 않는 가상의 컬럼명(`sales_amt`)을 참조하여 실행 에러 | DB 메타데이터 미주입으로 인한 LLM의 스키마 환각 | 카탈로그 DDL 정보와 실제 컬럼 코멘트 사전 벡터화 RAG 파이프라인 구축 | 스키마 링킹 오류 80% 감소 및 정상 실행율 개선 |
| 프롬프트 인젝션("테이블 지워줘")을 통해 `DROP TABLE` SQL 생성 위험 | LLM 생성 코드의 무비판적 DB 직접 실행 | SQL 파서로 AST 트리를 분석하여 SELECT 외 DDL/DML 전면 차단 및 DB 계정 Read-Only 강제 | 악성 쿼리 침투 위험 100% 원천 차단 |

## 내 의견
- [DB 원본 테이블 직접 노출 지양] 운영 DB의 복잡하게 정규화된 수십 개 테이블을 LLM에 그대로 던져주면 조인 조건이 엉켜 엉뚱한 수치를 계산해냄 → 나라면: 현업 질의가 잦은 비즈니스 핵심 지표에 대해 사전 집계된 반정규화 마트 뷰(Semantic Layer / Metric Layer)를 별도로 구축하고, LLM은 이 정제된 시맨틱 뷰 5~10개만을 대상으로 간단한 쿼리를 만들도록 통제
