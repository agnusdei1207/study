## 연관 키워드
- Text2SQL, 스키마 링킹, Few-Shot, 자가 교정, 시맨틱 레이어, 데이터 민주화, LLM, RAG

### Ⅰ. Text2SQL의 개요

- 핵심 요약 : 자연어 질문을 SQL 쿼리로 자동 변환하는 대규모 언어 모델 기반 데이터 접근 기술.
- 개념 : 자연어 질문을 실행 가능한 SQL로 바꾸는 기술(**Text2SQL**), 이를 구현하는 데 **LLM** (Large Language Model, 대규모 언어 모델)이 쓰임.
- 배경 및 필요성 : SQL과 스키마에 대한 지식이 장벽이 되어 데이터 접근이 제한됨.
- 주요 목적 : 비전문가도 데이터에 직접 질의해 분석할 수 있도록 하는 **데이터 민주화** (비전문가도 데이터를 직접 활용하게 하는 흐름).

### Ⅱ. Text2SQL의 특징 및 장점

- 핵심 요약 : 스키마 링킹, 예시 학습, 오류 교정을 결합해 정확한 SQL을 생성하는 구조.

1. 자연어 인터페이스 : SQL 지식 없이 데이터를 질의할 수 있음 → 질의 진입 장벽 감소.
2. 스키마 링킹(**Schema Linking**, 자연어 단어를 테이블·컬럼·외래키에 매핑하는 과정) : 질문이 가리키는 대상을 정확히 식별 → 엉뚱한 테이블 조회 감소.
3. Few-Shot (소수의 예시를 프롬프트에 넣어 출력 형식과 패턴을 따르게 하는 방식) : RAG (Retrieval-Augmented Generation, 검색으로 찾은 자료를 프롬프트에 넣어 생성하는 방식)로 유사한 과거 (질문, SQL) 쌍을 주입 → 복합 조인과 비즈니스 로직의 정확도 향상.
4. **자가 교정**(Self-Correction, 실행 오류 메시지를 LLM에 다시 넣어 SQL을 고치는 과정) : 실패 시 자동으로 재생성 → 최종 성공률 향상.

### Ⅲ. Text2SQL의 파이프라인 흐름

- 핵심 요약 : 질문에서 스키마 링킹, 프롬프트 구성, LLM 추론, 검증을 거쳐 DBMS 실행으로 이어지는 흐름.
- 프롬프트 구성 : DDL(Data Definition Language, 테이블 구조를 정의하는 SQL 명령)와 Few-Shot 예시, 도메인 규칙을 함께 넣음.
- SQL 검증 : 구문 검사와 Dry-Run(실행하지 않고 계획만 확인하는 점검)으로 실행 전에 오류를 차단함.

```text
[ Text2SQL 파이프라인 ]

[자연어 질문]
     ↓
[스키마 링킹] 관련 테이블·컬럼·외래키 추출
     ↓
[프롬프트 구성] DDL + Few-Shot + 도메인 규칙
     ↓
[LLM 추론] SQL 생성
     ↓
[SQL 검증] 구문 검사 + Dry-Run
     ↓
[DBMS 실행 및 결과 시각화]
```

```text
[ 자가 교정 루프 ]

SQL 생성 (LLM)
     ↓
구문 검사와 실행
     ↓ 오류 발생 시
오류 메시지를 프롬프트에 재주입
     ↓
SQL 재생성 (재시도 상한까지)
```

### Ⅳ. Text2SQL 구성 요소의 비교

- 핵심 요약 : 스키마 링킹, Few-Shot, 구문 검증, 자가 교정은 맡는 역할이 서로 다름.

| 구성 요소 | 메커니즘 | 해결 과제 |
|---|---|---|
| 스키마 링킹 | 자연어 단어를 DB 컬럼에 의미론적으로 매핑 | 가상 예시: "고객 주문 금액" → 주문 테이블의 금액 컬럼 |
| Few-Shot RAG | 유사한 과거 (질문, SQL) 쌍을 벡터 검색으로 찾아 주입 | 복합 조인과 비즈니스 로직 가이드 |
| 구문 검증 | SQL 파서(sqlglot, ANTLR 등)로 문법 오류를 사전 차단 | 컴파일 오류 없는 SQL 확보 |
| 자가 교정 | 실행 오류 메시지를 LLM에 재주입 | 1회 실패 시 자동 수정 |

### Ⅴ. Text2SQL의 한계와 방안

- 핵심 요약 : 스키마 규모, 보안 위험, 자원 폭주를 스키마 프루닝, 권한 분리, 가드레일로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 스키마 규모 | 테이블이 많아 전체 스키마를 프롬프트에 담기 어려움 | 스키마 프루닝으로 질문과 관련된 테이블만 추출 | 실행 정확도 (Execution Accuracy) |
| 보안·쿼리 파괴 | DDL 및 DML 실행, SQL 인젝션 위험 | 읽기 전용 계정 사용, AST(Abstract Syntax Tree, 추상 구문 트리) 검사로 변경 구문 차단 | 보안 사고 건수 |
| 자원 폭주 | 잘못된 SQL의 대량 조회로 DB 자원 고갈 | 실행 시간·스캔량 상한(가드레일), 실행 계획 검증 | 쿼리 실행 시간 |

### Ⅵ. Text2SQL에 대한 기술사적 제언

- 핵심 요약 : 시맨틱 레이어, 가드레일, 권한 분리를 결합해 안전한 데이터 민주화 체계를 구축하는 방향.
- SQL·API 담당자는 비즈니스 용어와 API 계약 및 승인 조건을 표준화하는 방향으로 접근해야 함.

1. 컬럼의 업무 명칭과 계산 공식, 동의어를 **시맨틱 레이어** (Semantic Layer, 물리 스키마를 업무 용어로 바꿔 제공하는 중간 계층)에서 표준화해야 함. dbt나 Cube.js 같은 도구로 구현할 수 있음.
2. 행 수, 실행 시간, 스캔량의 상한을 가드레일로 두고 실행 계획을 검증한 뒤에 쿼리를 허용해야 자원 폭주를 막을 수 있음.
3. Text2SQL 전용 읽기 전용 계정을 분리해 쓰기 권한을 원천 차단하고, 생성된 질의 로그를 감사할 수 있는 체계를 함께 두는 것이 바람직하다.

### Ⅶ. 결론

- 핵심 요약 : Text2SQL은 자연어 기반 데이터 접근 기술로, 스키마 링킹과 자가 교정, 시맨틱 레이어가 정확도를 좌우함.
- 시사점 : 파이프라인 설계와 보안 가드레일을 함께 갖춰야 데이터 민주화가 안전하게 확산될 수 있음.
