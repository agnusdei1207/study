## 답안 골격
```text
[DB 튜닝 (Database Tuning)] ◀━━ 머리: Ⅶ 내 의견 (대기 이벤트 기반 병목 진단과 CI/CD 쿼리 정적 분석 게이트 구축)
 ┃
 ┣━ Ⅰ 개요 ───── DB 시스템의 처리량(Throughput)을 극대화하고 응답 시간을 단축하기 위해 설계, SQL, 메모리, I/O 전 영역의 병목을 진단·개선하는 공학적 최적화
 ┣━ Ⅱ 특징 ───── 최소 비용 최대 효과(SQL 튜닝 중심) · 파레토 법칙(20% 악성 SQL이 80% 부하 유발) · 트레이드오프(저장공간/CUD 속도 vs 조회 속도)
 ┣━ Ⅲ 구조 ───── 4대 계층: 비즈니스/데이터 모델 튜닝 / SQL 및 인덱스 튜닝 / DBMS 인스턴스 및 메모리 튜닝 / OS 및 스토리지 튜닝
 ┣━ Ⅳ 흐름 ───── ① 성능 모니터링(AWR, APM) → ② 병목 대기 이벤트(Wait Event) 식별 → ③ 실행 계획 분석 → ④ 인덱스/쿼리/파라미터 개선 → ⑤ 사후 검증
 ┣━ Ⅴ 비교 ───── SQL 튜닝 vs 환경(인스턴스) 튜닝 vs 하드웨어 증설(Scale-up)
 ┗━ Ⅵ 실무 ───── 특정 쿼리 최적화를 위해 생성한 인덱스가 다른 배치 DML 성능을 급격히 저하시키는 부작용
```
- 필수 키워드: DB 튜닝 · 대기 이벤트(Wait Event) · AWR · 실행 계획(Execution Plan) · 파레토 법칙 · 바인드 변수 · 인덱스 튜닝 · 버퍼 캐시
- 기출: 127회 `데이터베이스 튜닝의 목표 및 단계별(모델, 환경, SQL) 튜닝 접근 방법` → Ⅰ 목표 + Ⅲ 단계별 기법 + Ⅳ 절차 + Ⅵ 실무 고려사항

## 한 줄 본질
- 무분별한 하드웨어 증설(Scale-up)은 고비용 대비 성능 개선 한계 봉착 → 대기 이벤트 분석으로 병목 원인을 규명하고 상위 계층(SQL/인덱스/모델)부터 최소 비용으로 최적화 → 최소 자원으로 최대 처리량 달성 / 인덱스 과다 시 쓰기 부하 유발

## 핵심 용어
- 대기 이벤트(Wait Event): 세션이 작업을 진행하지 못하고 자원(I/O, 락, 래치)을 획득하기 위해 대기하는 상태를 나타내는 성능 진단의 나침반
- 라이브러리 캐시(Library Cache): 파싱된 SQL 문장과 컴파일된 실행 계획을 저장해 두어 동일한 쿼리의 재파싱(소프트 파싱)을 유도하는 메모리 영역

## 핵심 통찰
- DB 튜닝의 황금률은 '항상 높은 계층부터 손대는 것'임 → 하드웨어를 2배 비싼 것으로 바꾸면 성능이 최대 2배 오르지만, 잘못된 풀스캔 SQL 하나를 인덱스 스캔으로 바꾸면 성능이 1,000배 향상됨
- 튜닝 대상 SQL을 찾을 때는 실행 시간(Elapsed Time)이 오래 걸리는 쿼리만 보면 안 됨 → 0.01초 걸리지만 초당 1만 번 호출되며 CPU를 태우는 '빈발 마이크로 쿼리'가 전체 시스템 마비의 진짜 주범임
- 인덱스는 조회를 빠르게 만들지만 INSERT, UPDATE, DELETE 시에는 매번 인덱스 블록을 수정해야 하므로, 테이블당 인덱스가 5개를 넘어가면 심각한 쓰기 지연 발생

## 이웃 토픽과 구분
- SQL 튜닝 vs 인스턴스 튜닝: SQL 튜닝 = 개별 쿼리의 실행 계획과 접근 경로를 바로잡는 작업(소프트웨어/로직 관점) / 인스턴스 튜닝 = 버퍼 캐시 크기, 체크포인트 주기, 정렬 영역 등 DBMS 엔진 전체의 환경 변수를 조율하는 작업(인프라 관점)

## 문제·원인·대책
- 적용 상황: 대규모 공공 취업 포털 서비스의 채용 마감일 동시 접속 폭증 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| DB CPU가 100%에 달하며 로그인 및 채용공고 조회가 타임아웃 발생 | 사용자 ID 조회 쿼리가 리터럴 SQL로 작성되어 대규모 하드 파싱 래치 경합 | 바인드 변수(`?`) 전면 적용 및 커서 공유(Cursor Sharing) 파라미터 강제 | 하드 파싱 99% 제거 및 CPU 점유율 35%로 안정화 |
| 특정 회원의 지원 이력 조회 시 30초 이상 디스크 I/O 발생 | 지원서 테이블(5천만 건) 풀스캔 발생 및 복합 인덱스 컬럼 순서 역전 | (회원번호, 지원일자) 순서로 결합 인덱스 재생성 및 인덱스 패스트 풀스캔 유도 | 응답 시간 30초에서 0.02초로 1,500배 단축 |

## 이렇게 출제된다
- 제127회: "데이터베이스 시스템의 성능 개선을 위한 데이터베이스 튜닝(Database Tuning)의 단계별 접근 방법(데이터 모델 튜닝, 환경 튜닝, SQL 튜닝)과 주요 튜닝 절차를 설명하시오." → 요구 포인트: 튜닝 4계층 피라미드 + 5단계 수행 절차 + 대기 이벤트 분석 + 튜닝 시 부작용 방지 대책

## 내 의견
- [장애 후 소방수식 튜닝 문화 척결] 서비스 오픈 후 시스템이 다운되면 외부 튜너를 불러 수천만 원을 들여 땜질식 힌트를 떡칠하는 구태 반복 → 나라면: 개발 파이프라인(CI)에 쿼리 분석 플러그인을 연동해, 인덱스를 타지 않는 Full Table Scan 쿼리나 바인드 변수를 쓰지 않은 동적 문자열 쿼리는 빌드 단계에서 머지(Merge)를 자동 차단하는 예방적 튜닝 게이트 구축

## 찾아볼 것
