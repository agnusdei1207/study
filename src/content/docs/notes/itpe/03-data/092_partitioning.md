 ┃
 ┣━ Ⅰ 개요 ───── 대용량 테이블이나 인덱스를 논리적으로는 하나의 객체로 유지하면서, 물리적으로는 여러 개의 작은 세그먼트로 분할 저장하는 최적화 기법
 ┣━ Ⅱ 특징 ───── 파티션 프루닝(Pruning) · 관리 독립성(백업/삭제 고속화) · 가용성 격리 · I/O 병목 분산 · 로컬/글로벌 인덱스
 ┣━ Ⅲ 구조 ───── 파티션 키(Partition Key) / 범위(Range) / 목록(List) / 해시(Hash) / 복합(Composite) / 로컬·글로벌 파티션 인덱스
 ┣━ Ⅳ 흐름 ───── ① 데이터 접근 패턴 및 주기 분석 → ② 최적 파티션 키 및 분할 방식 선정 → ③ DDL 파티션 테이블 생성 → ④ 파티션 프루닝 쿼리 검증 → ⑤ 보관주기 만료 파티션 Drop/Truncate
 ┣━ Ⅴ 비교 ───── 파티셔닝 vs 샤딩 (단일 DBMS 내부 물리 분할 vs 복수 물리 서버 간 분산 네트워크 분할)
 ┗━ Ⅵ 실무 ───── 쿼리 조건절 파티션 키 누락으로 전 파티션 풀스캔 / 글로벌 인덱스 존재 시 파티션 Drop 에러(Index Unusable)

## 한 줄 본질
- 수억 건 대용량 단일 테이블의 전체 스캔 비용과 백업/삭제 시 DB 락 병목 → 파티션 키 기준으로 세그먼트를 물리 분할하고 불필요한 파티션을 배제(Pruning) → 대규모 I/O 절감 및 초고속 이력 삭제 / 파티션 키 미사용 시 오버헤드

## 핵심 그림
```text
[파티션 4대 분할 방식 및 파티션 프루닝(Pruning)]

 [4대 분할 방식]
 1. Range (범위)  : 날짜, 연속값 기준 (예: 202601, 202602, 202603)
 2. List (목록)   : 불연속 코드 기준 (예: 서울, 경기, 부산)
 3. Hash (해시)   : 해시 함수로 균등 분산 (예: 고객ID Hash P1~P4)
 4. Composite(복합): Range + Hash (예: 일자별 Range 후 고객ID Hash)

 [파티션 프루닝(Pruning) 동작]
  SQL: SELECT * FROM 주문 WHERE 주문일자 BETWEEN '2026-03-01' AND '2026-03-31'
  ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
  │  Part 1 (1월)   │ │  Part 2 (2월)   │ │  Part 3 (3월)   │
  │   [ 스캔 제외 ] │ │   [ 스캔 제외 ] │ │ [ 물리 I/O 수행 ]│
  └─────────────────┘ └─────────────────┘ └─────────────────┘
  * 옵티마이저가 조건절을 해석하여 Part 1, 2를 원천 배제(Pruning)
```

## 핵심 용어
- 파티션 프루닝(Partition Pruning): 옵티마이저가 SQL 조건절을 분석하여 질의와 관련 없는 파티션은 아예 디스크 I/O 대상에서 제외하여 성능을 비약적으로 끌어올리는 메커니즘
- 로컬 파티션 인덱스(Local Partitioned Index): 테이블 파티션과 1:1로 매핑되는 독립적인 인덱스 구조로, 특정 파티션이 삭제(Drop)되어도 다른 파티션 인덱스에 영향을 주지 않음

## 핵심 통찰
- 파티셔닝의 진짜 가치는 '조회 속도'보다 '유지보수 관리(Operation)'에 있음 → 1억 건 로그 테이블에서 3년 지난 데이터를 `DELETE`로 지우면 Undo/Redo 폭증으로 DB가 멈추지만, Range 파티션 테이블은 `ALTER TABLE DROP PARTITION` 명령 0.1초 만에 메타데이터만 지워 무중단 삭제 완료
- 파티션을 쪼갰다고 무조건 빨라지지 않음 → 쿼리의 `WHERE` 절에 파티션 키가 없으면 옵티마이저는 모든 파티션을 다 뒤져야 하므로 단일 테이블보다 오히려 세그먼트 오버헤드로 인해 느려짐
- 글로벌 인덱스(Global Index)를 걸어둔 상태에서 파티션을 드롭하면 글로벌 인덱스 전체가 무효화(`UNUSABLE`)되어 서비스 전면 장애 발생 → 파티션 테이블에는 반드시 로컬 인덱스를 기본으로 채택

## 이웃 토픽과 구분
- 파티셔닝 vs 샤딩: 파티셔닝 = 단일 DB 인스턴스/스토리지 내부에서 테이블을 물리 세그먼트로 분할 / 샤딩 = 네트워크로 분리된 서로 다른 물리 DB 서버 노드들로 데이터를 분산 저장

## 문제·원인·대책
- 적용 상황: 대용량 결제 이력 테이블(월 3,000만 건)의 이력 보관 및 삭제
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 오래된 데이터 정기 삭제 시 `DELETE FROM ...` 실행으로 DB 락 발생 및 정체 | 단일 테이블 대량 DML 수행으로 인한 Undo 로그 폭증 및 행 락 | 월별 Range 파티셔닝 구축 후 `ALTER TABLE ... DROP PARTITION` 수행 | 삭제 작업 소요 시간 3시간에서 0.1초로 단축 및 무중단 운영 |
| 파티션 테이블 조회 쿼리가 인덱스를 타지 않고 극심한 디스크 병목 발생 | 쿼리 WHERE 조건절에서 파티션 키(`주문일자`) 누락 | 애플리케이션 쿼리에 파티션 키 필수 입력 강제 및 프루닝 실행계획 확인 | 불필요 파티션 I/O 90% 제거 및 쿼리 지연 해소 |

## 이렇게 출제된다
- 제127회: "대용량 관계형 데이터베이스에서 성능과 가용성을 향상시키기 위한 테이블 파티셔닝(Partitioning)의 개념, 분할 기법 4가지(Range, List, Hash, Composite) 및 로컬 인덱스와 글로벌 인덱스를 비교 설명하시오." → 요구 포인트: 파티셔닝 정의 + 4대 분할 방식 + 파티션 프루닝 원리 + 로컬/글로벌 인덱스 장단점

## 내 의견
- [글로벌 유니크 인덱스 강박의 위험] 비즈니스 요구로 "전체 파티션을 통틀어 주문번호가 유일해야 한다"며 글로벌 유니크 인덱스를 생성했다가, 매월 파티션 정리 작업마다 인덱스가 깨져 새벽 장애를 겪는 운영팀 다수 → 나라면: 파티션 키(예: 주문일자)를 복합키로 포함시켜 `(주문일자, 주문번호)` 형태의 로컬 유니크 인덱스로 설계하여 완벽한 파티션 독립성과 운영 안정성을 동시 확보
