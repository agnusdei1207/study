## 한 줄 본질
- 단일 데이터 저장소 장애 시 데이터 유실 및 서비스 전면 중단 불가피 → 스토리지, DBMS, CDC 등 계층별 로그 복제를 통해 원격지에 실시간 사본을 유지 → 무중단 회복탄력성 달성 / 복제 지연 및 동시 수정 충돌 발생

## 핵심 용어
- 스플릿 브레인(Split-Brain): 네트워크 단절로 인해 복제 노드들이 서로 상대방이 죽었다고 판단하여 각자 독립적으로 Primary 역할을 수행하면서 데이터가 영구적으로 갈라지는 현상
- LWW(Last Write Wins): Active-Active 분산 복제 환경에서 동일한 레코드에 동시 쓰기 충돌이 발생했을 때, 타임스탬프가 가장 늦은 트랜잭션을 승자로 채택하는 충돌 해결 정책

## 핵심 통찰
- 완벽한 Active-Active 양방향 복제는 '환상'에 가까움 → 두 리전에서 동시에 동일한 좌석을 예약하면 네트워크 지연 때문에 무조건 충돌이 나므로, LWW나 CRDT(Conflict-free Replicated Data Types) 같은 엄밀한 충돌 해결 수학 모델이 선행되어야 함
- 이기종 DB 간(Oracle $\rightarrow$ PostgreSQL) 복제 시 스토리지 복제나 DB 내장 복제는 원천 불가하므로, SQL 레벨에서 이벤트를 가로채는 CDC(Change Data Capture) 솔루션 도입이 유일한 해법
- 재해복구(DR) 관점에서 복제는 '백업'을 대체할 수 없음 → 개발자가 운영 DB에서 잘못 `DROP TABLE`을 실행하면, 그 즉시 밀리초 단위로 DR 센터의 복제본까지 함께 날아가기 때문

## 이웃 토픽과 구분
- 데이터 복제 vs 데이터 샤딩: 복제 = 동일한 데이터를 여러 노드에 '중복 복사'하여 가용성과 읽기 분산을 도모 / 샤딩 = 데이터를 서로 다른 노드에 '조각내어 분산'하여 쓰기 용량과 저장 공간을 확장

## 문제·원인·대책
- 적용 상황: 글로벌 핀테크 서비스의 서울-도쿄 간 액티브-액티브 다중 리전 복제
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 동일 고객 계좌에 대해 양쪽 리전에서 동시 인출 시 잔고 마이너스 충돌 발생 | 비동기 양방향 복제 환경에서의 쓰기 경합(Race Condition) | 고객 ID 해시 기반으로 특정 고객의 쓰기는 단일 리전으로만 라우팅(리전 고정) | 데이터 충돌 원천 차단 |
| 장거리 복제 시 회선 불안정으로 복제 지연이 1시간 이상 누적 | WAN 대역폭 부족 및 단일 스레드 복제 적용 병목 | 변경 로그 압축 전송 및 병렬 복제(Multi-threaded Replication) 엔진 활성화 | 복제 지연 5초 이내로 단축 |

## 이렇게 출제된다
- 제120회: "데이터베이스 및 스토리지 레벨에서의 데이터 복제(Data Replication) 기술 유형을 비교하고, 재해복구(DR) 센터 구축 시 RPO와 RTO 관점에서의 복제 방식 선정 기준을 제시하시오." → 요구 포인트: 3대 복제 계층 비교 + 동기/비동기 트레이드오프 + RPO/RTO 지표 매핑 + 충돌 해결 방안

## 내 의견
- [단일 복제 기술 맹신 탈피] 모든 업무에 무조건 값비싼 스토리지 실시간 동기 미러링을 적용하려다 프로젝트 예산을 탕진하는 안티패턴 존재 → 나라면: 계좌·원장 등 핵심 금융 데이터는 DBMS 반동기 복제로 RPO 0을 지키고, 대용량 로그나 분석용 데이터는 Kafka 기반의 비동기 CDC 파이프라인으로 분리하는 계층화된 다중 복제 아키텍처 수립
