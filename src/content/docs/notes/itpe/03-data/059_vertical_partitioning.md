## 답안 골격
```text
[수직분할] ◀━━ 머리: Ⅶ 내 의견 (접근 빈도와 보안 등급에 따른 컬럼 분리 및 LOB 대용량 데이터의 외부 분리 저장)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 테이블의 컬럼(속성)들을 접근 빈도, 보안 등급, 데이터 크기(LOB)에 따라 분리하여 복수의 테이블로 분할
 ┣━ Ⅱ 특징 ───── 컬럼 단위 분할 · 기본키(PK) 공유(1:1 관계) · I/O 블록당 레코드 밀도 증가 · 조인 비용 트레이드오프
 ┣━ Ⅲ 구조 ───── 빈번 조회 컬럼 테이블 / 간헐 조회 컬럼 테이블 / 대용량 LOB 테이블 / 공통 기본키(PK)
 ┣━ Ⅳ 흐름 ───── ① 컬럼별 트랜잭션 접근 패턴 및 빈도 분석 → ② 1:1 관계의 하위 테이블 분리 DDL 정의 → ③ PK 기반 외래키 연결 → ④ 쿼리 시 필요한 테이블만 조회
 ┣━ Ⅴ 비교 ───── 수직분할 vs 수평분할 (열 단위 분리/블록당 행 수 증가 vs 행 단위 분리/전체 스키마 유지)
 ┗━ Ⅵ 실무 ───── 전체 속성 조회 시 1:1 조인 오버헤드 / 분할 테이블 간 트랜잭션 정합성 관리 비용
```
- 필수 키워드: 컬럼 분할 · 기본키(PK) 복제 · 1:1 관계 · 블록 집적도 · LOB(Large Object) · 접근 빈도 · 조인 오버헤드
- 기출: 138회 2교시 3번 `분산 데이터베이스 구축을 위한 데이터베이스 분할(수평/수직 분할)` → Ⅰ 개념 + Ⅲ 수직분할 구조 + Ⅴ 비교

## 한 줄 본질
- 수십 개 컬럼과 대용량 텍스트/바이너리로 인한 블록 I/O 낭비 → 자주 쓰이는 컬럼과 그렇지 않은 컬럼을 기본키(PK) 기준으로 1:1 분리 → 버퍼 캐시 효율 및 디스크 I/O 최적화 / 통합 조회 시 조인 비용 발생

## 핵심 그림
```text
[수직분할(Vertical Partitioning) 구조 및 I/O 절감 원리]

 [분할 전: 단일 거대 테이블] (1개 블록에 5개 행만 적재 -> I/O 낭비)
 ┌────────────────────────────────────────────────────────┐
 │ 사원ID(PK) | 이름 | 직급 | 급여(보안) | 이력서(CLOB) │ 사진(BLOB) │
 └────────────────────────────────────────────────────────┘
                           │
             [ 접근 빈도 및 데이터 크기별 수직분할 ]
                           ▼
 [자주 조회: 사원 기본 테이블]          [간헐 조회: 사원 상세/LOB 테이블]
 (1개 블록에 100개 행 적재 가능!)      (필요할 때만 읽음)
 ┌───────────────────────────┐         ┌───────────────────────────┐
 │ 사원ID(PK) | 이름 | 직급 │ <─ 1:1 ─>│ 사원ID(PK) | 이력서 | 사진│
 └───────────────────────────┘         └───────────────────────────┘
```

## 핵심 용어
- 블록 집적도(Block Density): 데이터베이스 단일 I/O 블록(8KB 등) 내에 저장될 수 있는 유효 레코드(Row)의 수
- 컬럼 친밀도(Column Affinity): 동일한 트랜잭션이나 쿼리에서 두 개 이상의 컬럼이 함께 참조되는 빈도를 나타내는 척도

## 핵심 통찰
- 사용자는 `SELECT name, rank`만 원해도 DB 엔진은 행 전체(이력서 텍스트, 이미지 포함)를 디스크에서 메모리로 퍼올림 → 수직분할은 블록당 행 집적도를 극대화하여 불필요한 바이트 I/O를 원천 차단
- 보안 등급 격리의 최적 수단 → 주민등록번호, 계좌번호, 급여 같은 민감 컬럼만 별도 수직 분할 테이블로 떼어내 암호화 및 엄격한 테이블 단위 접근 통제(GRANT) 적용 가능
- 무분별한 분할은 재앙 → 평소에 함께 조회되는 컬럼들을 쪼개 놓으면 매번 1:1 조인이 발생해 오히려 성능이 심각하게 악화됨

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| LOB(Large Object) 외부화 | 대용량 데이터의 수직 분할 특례 | 수 메가바이트의 이미지·문서 컬럼을 별도 세그먼트나 파일 스토리지(S3)로 격리 저장 |
| 컬럼형 스토리지(Columnar DB) | 수직분할의 극단적 아키텍처화 | Parquet, ClickHouse처럼 모든 단일 컬럼을 개별 파일로 수직 저장해 대규모 집계 가속 |

## 이웃 토픽과 구분
- 수직분할 vs 반정규화(테이블 분할): 반정규화의 테이블 수직분할 = 성능 최적화를 위한 물리 모델링 기법 / 분산 DB의 수직분할 = 노드별 데이터 분산 배치를 위한 아키텍처 기법

## 문제·원인·대책
- 적용 상황: 포털 게시판 목록 조회 시 심각한 DB I/O 병목
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 제목과 작성자만 표시하는 목록 조회인데 디스크 I/O 포화 | 수십 KB의 게시글 본문(content) 컬럼이 동일 테이블에 위치 | 게시글 마스터(제목, 작성자, 조회수)와 본문 테이블로 수직분할 | 블록 집적도 10배 증가, 목록 쿼리 속도 80% 향상 |
| 수직분할 후 화면 렌더링 시 잦은 조인으로 CPU 부하 증가 | 함께 쓰이는 컬럼 분석 없이 임의로 컬럼 분리 | 트랜잭션 프로파일링 후 상호 참조율 90% 이상인 컬럼 재결합 | 불필요한 조인 횟수 제거 |

## 이렇게 출제된다
- 제138회 2교시 3번: "분산 데이터베이스 시스템 구축을 위한 데이터베이스분할에 대하여 다음 내용을 설명 하시오." → 요구 포인트: 수직분할의 개념, 분할 기준(접근 빈도, 보안, 크기), 수평분할과의 차이점 및 물리적 I/O 효과

## 내 의견
- [LOB 데이터의 RDBMS 보관 지양] 이미지, PDF, JSON 바이너리를 RDBMS 컬럼에 그대로 적재하여 백업 시간을 지연시키고 버퍼 캐시를 오염시키는 안티패턴 만연 → 나라면: 수직분할을 통해 LOB 속성을 분리하되, 대용량 파일은 클라우드 오브젝트 스토리지(S3)에 저장하고 DB에는 URL 메타데이터만 남기는 아키텍처 원칙 준수

## 찾아볼 것
- RDBMS의 인라인(In-line) LOB과 아웃오브라인(Out-of-line) LOB 저장 메커니즘의 임계 크기(Threshold)
