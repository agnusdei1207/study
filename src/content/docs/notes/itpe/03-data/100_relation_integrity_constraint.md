 ┃
 ┣━ Ⅰ 개요 ───── 관계형 데이터 모델에서 릴레이션(테이블)에 저장되는 튜플과 속성값들이 정확성, 일관성, 유효성을 항상 만족하도록 강제하는 데이터베이스 상태 규칙
 ┣━ Ⅱ 특징 ───── 선언적 무결성(DDL) · 동적 상태 전이 검증 · DBMS 엔진 레벨 강제 · 도메인/개체/참조/키 4대 제약 · 데이터 품질 보증의 근간
 ┣━ Ⅲ 구조 ───── 개체 무결성(PK Not Null) / 참조 무결성(FK-부모 PK 일치) / 도메인 무결성(타입, CHECK) / 키 무결성(Unique, 최소 1개 키 존재)
 ┣━ Ⅳ 흐름 ───── ① 사용자 DML 요청(Insert/Update/Delete) → ② 릴레이션 제약조건 평가(PK 중복, FK 참조, CHECK) → ③ 위반 시 에러 및 자동 롤백 → ④ 통과 시 트랜잭션 커밋
 ┣━ Ⅴ 비교 ───── 선언적 제약(DDL) vs 절차적 제약(Trigger) vs 애플리케이션 제약 (DBMS 엔진 레벨 보장/고성능 vs 복합 비즈니스 룰/유지보수 난해 vs 프론트 검증/데이터 직접 접근 시 무력화)
 ┗━ Ⅵ 실무 ───── 참조 무결성 cascade 삭제로 인한 연쇄 삭제 사고 / 대량 데이터 적재(Bulk Load) 시 제약조건 검사 병목

## 핵심 그림
```text
[릴레이션 4대 무결성 제약조건 및 구현 DDL 매핑]

 ┌─────────────────────────────────────────────────────────────┐
 │ 1. 개체 무결성 (Entity)   : PK는 NOT NULL & UNIQUE           │
 │    예: 고객 릴레이션의 [고객번호]는 NULL이거나 중복 불가    │
 ├─────────────────────────────────────────────────────────────┤
 │ 2. 참조 무결성 (Referential): FK는 부모 릴레이션 PK와 일치  │
 │    예: 주문 릴레이션의 [고객번호]는 고객 테이블에 실존해야 함│
 ├─────────────────────────────────────────────────────────────┤
 │ 3. 도메인 무결성 (Domain) : 속성값은 정의된 허용 범위 준수 │
 │    예: [나이] 속성은 0 이상 150 이하의 정수 (CHECK 제약)    │
 ├─────────────────────────────────────────────────────────────┤
 │ 4. 키 무결성 (Key)       : 릴레이션에 최소 하나의 키 존재   │
 │    예: [이메일] 속성은 중복될 수 없음 (UNIQUE 제약)         │
 └─────────────────────────────────────────────────────────────┘
                               │
                               ▼ DBMS 구현 DDL
 ┌─────────────────────────────────────────────────────────────┐
 │ CREATE TABLE 주문 (                                         │
 │   주문번호 INT PRIMARY KEY,                 -- 개체 무결성  │
 │   고객번호 INT REFERENCES 고객(고객번호)     -- 참조 무결성  │
 │                ON DELETE RESTRICT,                          │
 │   주문수량 INT CHECK (주문수량 > 0),         -- 도메인 무결성│
 │   결제번호 VARCHAR(50) UNIQUE               -- 키/고유 무결성│
 │ );                                                          │
 └─────────────────────────────────────────────────────────────┘
```

## 핵심 용어
- 개체 무결성(Entity Integrity): 기본키(PK)를 구성하는 어떠한 속성도 NULL 값을 가질 수 없으며 릴레이션 내에서 유일해야 한다는 제약
- 참조 무결성(Referential Integrity): 외래키(FK) 값은 참조하는 부모 릴레이션의 기본키 값과 정확히 일치하거나 NULL이어야 하며, `ON DELETE CASCADE / RESTRICT`로 참조 규칙 통제

## 핵심 통찰
- 무결성 검증을 애플리케이션 코드에만 맡겨두면, 개발자가 작성한 배치가 DB에 직접 쿼리를 날릴 때 제약조건이 모조리 뚫려 쓰레기 데이터가 적재됨 → DBMS의 DDL 수준 선언적 무결성이 최종 방어선
- 참조 무결성의 `ON DELETE CASCADE`는 실무에서 가장 위험한 양날의 검임 → 고객 테이블에서 탈퇴 회원 1명을 지웠다가 수년간 누적된 수만 건의 결제/주문 이력이 연쇄 삭제되는 참사 발생
- 대량 배치 적재(Bulk Insert) 시에는 제약조건 검사 때문에 속도가 수십 배 느려짐 → 적재 전 제약조건을 `DISABLE`하고, 적재 완료 후 `ENABLE NOVALIDATE`로 전환하는 운영 기교 필요

## 이웃 토픽과 구분
- 릴레이션 무결성 vs 트랜잭션 일관성(Consistency): 릴레이션 무결성 = 데이터 구조와 값 자체의 규칙(PK, FK, 도메인) / 트랜잭션 일관성 = 트랜잭션 실행 전후로 무결성 제약조건을 포함한 시스템 전체 상태가 모순되지 않음을 보장하는 ACID 성질

## 문제·원인·대책
- 적용 상황: 대규모 공공 행정 데이터베이스 통합 이관 프로젝트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 부모 기관 코드 삭제 시 자식 테이블의 수억 건 민원 데이터가 함께 삭제 | 외래키에 `ON DELETE CASCADE` 옵션 무비판적 적용 | 참조 무결성 규칙을 `ON DELETE RESTRICT`로 변경 | 데이터 무단 연쇄 삭제 사고 원천 방지 |
| 1억 건 데이터 마이그레이션 중 PK 및 FK 제약 검사로 24시간 초과 지연 | 건건이 발생하는 인덱스 트리 탐색 및 참조 무결성 유효성 검사 | `ALTER TABLE ... DISABLE CONSTRAINT` 후 적재하고 사후 `ENABLE NOVALIDATE` 복원 | 마이그레이션 작업 시간 24시간에서 1.5시간으로 단축 |

## 내 의견
- [무결성 제약과 성능의 조화로운 분리] "무결성을 지키려면 무조건 DB 제약조건을 걸어야 한다"와 "성능을 위해 제약조건을 다 빼야 한다"는 극단론의 대립 → 나라면: 온라인 실시간 트랜잭션(OLTP) 테이블에는 PK, NOT NULL, CHECK 등 단일 테이블 제약을 100% 강제하고, 분산 서비스 간 경계나 초대형 로그 테이블의 참조 무결성은 비동기 사후 검증 배치로 분리하는 절충안 실행
