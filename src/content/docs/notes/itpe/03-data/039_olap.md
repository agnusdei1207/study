## 답안 골격
```text
[OLAP] ◀━━ 머리: Ⅶ 내 의견 (전통적 큐브 구축 지양 → 클릭하우스/DuckDB 등 초고속 컬럼형 엔진 기반 실시간 OLAP 전환)
 ┃
 ┣━ Ⅰ 개요 ───── 트랜잭션 중심 OLTP 한계 → 최종 사용자가 다차원(Multi-dimensional) 관점에서 대화식으로 분석
 ┣━ Ⅱ 특징 ───── 다차원 데이터 큐브(Cube) 모델 · 복잡한 집계 쿼리 최적화 · 실시간 슬라이싱/다이싱 지원
 ┣━ Ⅲ 구조 ───── 다차원 큐브(차원 테이블, 팩트 테이블) / 4대 기본 연산 (Roll-up, Drill-down, Slicing/Dicing, Pivoting)
 ┣━ Ⅳ 흐름 ───── ① 스타/스노우플레이크 스키마 모델링 → ② 큐브 사전 집계 → ③ 다차원 질의(MDX) 실행 → ④ 동적 드릴다운 분석
 ┣━ Ⅴ 비교 ───── 3대 아키텍처 비교 (ROLAP vs MOLAP vs HOLAP)
 ┗━ Ⅵ 실무 ───── 차원 수 증가 시 큐브 데이터 폭증(Data Explosion) / 원천 데이터 갱신 지연 / 스토리지 비용
```
- 필수 키워드: 다차원 큐브 · ROLAP · MOLAP · HOLAP · Roll-up · Drill-down · Slicing · Dicing · 스타 스키마
- 기출: 122회 `다차원 분석 및 ROLAP, MOLAP, HOLAP 비교` → Ⅲ 큐브 연산 + Ⅴ 3대 아키텍처 비교 완결

## 한 줄 본질
- 수억 건의 트랜잭션 로그를 매번 RDBMS로 조인 집계하는 연산 병목 → 시간·지역·상품 등 다차원 큐브에 사전 집계(Pre-aggregation)하여 저장 → 밀리초 단위의 대화식 분석 제공 / 차원 증가에 따른 큐브 폭증 문제 수반

## 핵심 그림
```text
[OLAP 4대 핵심 다차원 연산]

           [롤업 (Roll-up)] : 일별 -> 월별 -> 연도별 (상위 집계)
                 ▲
                 │
 [슬라이싱 (Slicing)] ── [ 다차원 큐브 ] ── [다이싱 (Dicing)]
 - 한 차원을 고정하여     (제품 × 지역 × 시간)   - 작은 하위 큐브를
   2차원 평면 자르기                             선택해 떼어내기
                 │
                 ▼
          [드릴다운 (Drill-down)] : 연도별 -> 분기별 -> 월별 (세부 분석)

 * 피보팅 (Pivoting): 행과 열의 축을 맞바꾸어 다른 관점으로 회전 보기
```

## 핵심 용어
- 팩트 테이블(Fact Table): 매출액, 판매량, 접속 횟수처럼 비즈니스에서 측정 가능한 수치 데이터(Measure)와 외래키들의 집합
- 차원 테이블(Dimension Table): 날짜, 고객, 매장, 상품처럼 팩트 테이블의 측정값을 필터링하고 그룹화하는 기준 속성들의 집합

## 핵심 통찰
- OLAP의 속도는 '사전 계산(Pre-computation)'에서 나옴 → 사용자가 쿼리를 날릴 때 계산하는 것이 아니라, 밤새 모든 차원의 조합(Cube)을 미리 더해두기 때문에 즉답이 가능함
- 그러나 차원이 늘어나면 '차원의 폭증(Cube Explosion)' 발생 → 10개 차원에 각각 100개 카테고리만 있어도 $100^{10}$개의 셀이 생겨 디스크 용량 파탄
- 현대 데이터 웨어하우스(Snowflake, ClickHouse, BigQuery)는 MOLAP 큐브를 미리 깎지 않고, 컬럼 지향 스토리지와 벡터화 엔진(SIMD)을 이용해 즉석에서 수억 행을 스캔 집계하는 방향으로 진화

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 스타 스키마 (Star Schema) | DW 논리 모델링 | 중앙의 팩트 테이블을 단일 계층의 차원 테이블들이 둘러싼 조인 최적화 구조 |
| 스노우플레이크 스키마 | 정규화된 DW 모델링 | 스타 스키마의 차원 테이블들을 3NF로 부분 정규화하여 중복을 줄인 눈송이 형태 |

## 이웃 토픽과 구분
- OLTP vs OLAP: OLTP = 실시간 단건 쓰기/수정 트랜잭션(ACID, 정규화) / OLAP = 대량의 과거 데이터 다차원 읽기 분석(집계, 비정규화)

## 문제·원인·대책
- 적용 상황: 유통 대기업 전사 글로벌 일일 매출 분석 대시보드
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 차원을 5개 추가했더니 큐브 빌드 배치 작업이 24시간 동안 안 끝남 | 차원 조합 수 폭증으로 인한 MOLAP 큐브 물리적 용량 한계 | 하이브리드 OLAP(HOLAP) 또는 분산 컬럼형 DB(ClickHouse)로 전환 | 실시간 스캔 집계로 큐브 빌드 시간 제거 |
| 경영진이 분기 실적 조회 시 로딩 20초 지연 | 스타 스키마의 대용량 팩트 테이블 풀스캔 | 사전 집계된 구체화 뷰(Materialized View) 및 프로젝션 인덱스 적용 | 1초 이내 즉시 응답성 회복 |

## 내 의견
- [무거운 레거시 OLAP 큐브 툴체인의 퇴출] Cognos나 SSAS 같은 전통적 MOLAP 솔루션은 유연성이 떨어져 비즈니스 변경 시 큐브 스키마 수정에만 수주 소요 → 나라면: dbt를 이용해 원천 레이크하우스(Iceberg) 위에서 스타 스키마 뷰를 코드로 관리하고, 초고속 인메모리 엔진(DuckDB)을 연동해 브라우저 위에서 즉각 다차원 피벗팅을 수행하는 모던 데이터 스택(MDS) 구축
