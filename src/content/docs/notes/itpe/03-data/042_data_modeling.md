## 연관 키워드

- 데이터 모델링(Data Modeling), ERD(Entity-Relationship Diagram), 개념적·논리적·물리적 모델링, 정규화(Normalization), 반정규화(Denormalization)
- 엔티티(Entity), 식별자(Identifier), 주식별자(Primary Identifier), 카디널리티(Cardinality), 단일 진실 공급원(SSOT, Single Source of Truth)

## Ⅰ. 데이터 모델링(Data Modeling)의 개요

- 핵심 요약 : 현실 세계의 업무와 데이터를 추상화하여 데이터베이스 구조로 형상화하는 체계적 과정.
- 개념 : 복잡한 업무 프로세스와 데이터를 약속된 표기법인 **ERD** (Entity-Relationship Diagram) 등으로 추상화(Abstraction), 단순화(Simplification), 명확화(Clarity)하여 데이터베이스 구축에 쓰이는 논리적·물리적 구조로 만드는 과정.
- 배경 및 필요성 : 업무 요구사항을 누락 없이 반영하고, 시스템의 확장과 유지보수를 쉽게 할 수 있는 구조가 요구됨.
- 주요 목적 : 데이터 아키텍처의 근간을 세우고 업무 규칙을 데이터 계층에 반영.

## Ⅱ. 데이터 모델링의 특징

- 핵심 요약 : 중복 최소화, 업무 규칙 반영, 성능과 유연성의 균형을 갖추고 3단계로 순차 전개하는 체계.

1. **단일 진실 공급원** (SSOT, Single Source of Truth) : 같은 데이터를 한 곳에서만 관리 → 데이터 중복이 줄어 시스템 전반의 정합성 유지.
2. 업무 규칙의 반영 : **카디널리티** (Cardinality)와 엔티티 간 관계로 도메인 규칙을 데이터 구조에 명시 → 규칙 위반 데이터의 입력을 구조적으로 억제.
3. 성능과 유연성의 균형 : 미래의 업무 변화를 수용할 구조와 질의 처리 성능을 함께 확보 → 변경 비용과 응답 속도를 동시에 관리.
4. 개념적 → 논리적 → 물리적 모델링의 3단계 순차 전개 → 현업 합의부터 하드웨어 종속 설계까지 단계별 검증 가능.
5. 엔티티의 키(Key), 메인(Main), 액션(Action) 3분류 체계 → 기준 정보와 거래 정보를 구분하여 설계 목적을 명확히 함.

## Ⅲ. 데이터 모델링의 구조 (흐름)

- 핵심 요약 : 업무 요구사항에서 물리 데이터베이스까지 3단계로 발전하는 구조.
- 엔티티(Entity)는 업무에서 관리할 대상을, 식별자(Identifier)는 엔티티의 각 인스턴스를 구분하는 속성을 뜻함.

```text
[ 데이터 모델링 3단계 ]
현실 세계 업무 요구사항
   ↓
개념적 모델링 (Conceptual)
   핵심 엔티티 도출, 주요 관계 정의
   ↓
논리적 모델링 (Logical)
   속성 정의, 식별자 확정, 정규화
   ↓
물리적 모델링 (Physical)
   데이터베이스 제품 선정, 테이블·컬럼, 인덱스
   ↓
물리 데이터베이스 구축·운영
```

- 논리적 모델링에서 **정규화**(Normalization)로 중복을 줄이고, 물리적 모델링에서 조회 성능을 위해 **반정규화**(Denormalization)를 선택적으로 적용한다.
- 물리적 모델링 단계에서는 특정 DBMS(Database Management System)를 선정하고 테이블과 컬럼을 명명하며, 데이터 타입, 인덱스, 반정규화를 설계한다.

```text
[ 엔티티 분류 체계 ]
키 엔티티 (Key)
   예: 고객, 상품, 사원
   ↓ 독립 생성 후 참조
메인 엔티티 (Main)
   예: 주문, 청구, 계약
   ↓ 상세·이력 기록
액션 엔티티 (Action)
   예: 주문상세, 입출금이력
```

- 식별자 설계 기준은 다음과 같다.
  1. 대표성에 따라 주식별자(Primary Identifier)와 보조식별자(Alternate Identifier)로 구분.
  2. 생성 방식에 따라 업무 속성 조합인 본질식별자와 일련번호, **UUID**(Universally Unique Identifier) 같은 인조식별자로 구분.

## Ⅳ. 3단계 모델링의 비교

- 핵심 요약 : 추상화 수준과 핵심 고려사항이 단계별로 달라 각 단계의 산출물과 검토 대상을 구분해야 함.

| 모델링 단계 | 주요 활동과 산출물 | 추상화 수준 | 핵심 고려사항 |
| :--- | :--- | :--- | :--- |
| 개념적 모델링 (Conceptual) | 핵심 엔티티 선정, 엔티티 간 관계 정의, 주제 영역 분류 | 가장 높음 (전사 관점) | 현업·경영진과의 의사소통, 업무 범위 확정 |
| 논리적 모델링 (Logical) | 전체 속성 정의, 주식별자와 외래키 지정, 카디널리티 구체화, 정규화 수행 | 중간 (업무 완전성) | DBMS에 독립적인 업무 규칙의 무결성 구현 |
| 물리적 모델링 (Physical) | 테이블과 컬럼 명명, 데이터 타입과 길이, 인덱스, 파티셔닝, 반정규화 검토 | 가장 낮음 (DBMS와 하드웨어 종속) | 저장 공간 효율, 트랜잭션 처리량, 디스크 입출력 최적화 |

## Ⅴ. 데이터 모델링의 한계와 방안

- 핵심 요약 : 요구사항 정확 반영과 유연성 확보의 장점에 대해, 현업과의 이해 격차, 확장성 부족, 서비스 분할에 따른 파편화라는 한계가 공존.
- 장점 : 업무 요구사항을 누락 없이 반영하고 의사소통의 표준을 제공하며, 중복을 줄여 시스템의 확장과 유지보수를 쉽게 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| :--- | :--- | :--- | :--- |
| 분석가와 현업 간 도메인 이해 격차 | 현업의 암묵지가 모델 변환 과정에서 누락되거나 왜곡되어 구축 후 모델 재수정 빈발 | 이벤트 스토밍(Event Storming) 워크숍으로 유비쿼터스 언어(Ubiquitous Language) 확립, 도메인 전문가와 모델러의 페어 모델링 제도화 | 요구사항 재작업 건수 |
| 확장성을 고려하지 않은 물리 모델 | 정규화 이론에 치우친 설계로 트래픽 급증 시 인덱스 비대화와 테이블 락 발생 | 워크로드 기반 용량 산정과 쿼리 패턴 분석, 샤딩과 파티셔닝을 고려한 설계, 수평 확장(Scale-out)에 적합한 키 설계 | 질의 응답 시간, 락 대기 시간 |
| MSA(Microservice Architecture) 확산에 따른 모델 파편화 | 서비스별 분할로 고객·상품 같은 마스터 데이터의 일관성이 흔들리고 서비스 간 중복과 동기화 문제 발생 | MDM(Master Data Management) 체계 유지, Kafka 기반 도메인 이벤트의 발행·구독(Pub/Sub) 구조 | 마스터 데이터 불일치 건수 |

## Ⅵ. 데이터 모델링에 대한 기술사적 제언

- 핵심 요약 : 논리 모델의 원칙을 지키고 물리 모델은 측정 근거에 따라 최적화하며, 이를 모델 거버넌스로 관리하는 방향.

1. 데이터 설계 조직은 논리 모델을 3NF(Third Normal Form)까지 정규화한 상태로 유지하고, 성능 목적의 반정규화나 샤딩은 실행 계획과 트래픽 추정치를 근거로 물리 모델링 단계에서만 적용해야 한다.
2. 애자일로 운영하는 개발 조직은 스프린트마다 바뀌는 모델을 Git 기반 버전 관리와 마이그레이션 도구(Flyway, Liquibase 등)로 관리하고, 전사 데이터 아키텍트(DA, Data Architect)가 변경을 검토하는 절차를 두어야 한다.

## Ⅶ. 결론

- 핵심 요약 : 데이터 모델링은 업무 본질을 데이터 구조에 옮기는 설계 활동이며, 업무 모델과 물리 최적화를 분리하는 것이 핵심임.
- 시사점 : 도메인 협업 체계와 모델 거버넌스가 갖춰져야 파편화를 막고 확장성을 확보할 수 있음.
