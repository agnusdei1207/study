## Ⅰ. 정보시스템 구축의 설계도, 데이터 모델링의 개요

### 가. 데이터 모델링의 정의
- 복잡한 현실 세계의 비즈니스 프로세스와 데이터를 약속된 표기법(ERD 등)을 사용하여 추상화(Abstraction), 단순화(Simplification), 명확화(Clarity)함으로써 컴퓨터 데이터베이스로 구축하기에 최적화된 논리적·물리적 구조로 형상화하는 체계적 과정.
- 업무 요구사항을 누락 없이 반영하고 향후 시스템 확장 및 유지보수의 유연성을 결정짓는 데이터 아키텍처의 근간.

### 나. 좋은 데이터 모델의 3대 핵심 특성
- **단일 진실 공급원(SSOT)** : 데이터 중복을 최소화하여 시스템 전반의 정합성 유지.
- **비즈니스 규칙의 정확한 반영** : 카디널리티와 관계를 통해 도메인 규칙을 데이터 계층에서 강제.
- **성능과 유연성의 균형** : 미래 비즈니스 변화 수용성 및 쿼리 처리 성능 동시 확보.

## Ⅱ. 데이터 모델링의 3단계 전개 프로세스

### 가. 3단계 모델링 계층도

```text
[ 데이터 모델링 3단계 발전 과정 ]
[현실 세계 업무 요구사항]
           |
           v
  [1. 개념적 모델링 (Conceptual)] : 핵심 엔티티 도출, 주요 관계 정의 (업무 중심, 고수준 ERD)
           |
           v
  [2. 논리적 모델링 (Logical)]    : 모든 속성 정의, 식별자 확정, 정규화(3NF), M:N 해소 (기술 독립)
           |
           v
  [3. 물리적 모델링 (Physical)]   : 특정 DBMS 선정, 테이블/컬럼명, 데이터타입, 인덱스, 반정규화
           |
           v
[물리 데이터베이스 (DDL 생성 및 운영)]
```

### 나. 3단계 모델링 세부 비교

| 모델링 단계 | 주요 활동 및 산출물 | 추상화 수준 | 핵심 고려사항 |
| :--- | :--- | :--- | :--- |
| **개념적 모델링 (Conceptual)** | 핵심 엔티티(Entity) 선정, 엔티티 간 관계(Relationship) 정의, 주제영역(Subject Area) 분류 | 가장 높음 (전사 관점) | 현업 및 경영진과의 의사소통, 업무 범위의 명확한 획정 |
| **논리적 모델링 (Logical)** | 전체 속성 정의, 주식별자/외래키 지정, 관계 카디널리티 구체화, 1~3차 정규화 수행 | 중간 (업무 완전성) | 특정 DBMS에 독립적인 비즈니스 규칙의 완전 무결한 구현 |
| **물리적 모델링 (Physical)** | 물리적 테이블/컬럼 명명, 데이터 타입/길이 지정, 인덱스 설계, 파티셔닝, 역정규화 검토 | 가장 낮음 (하드웨어/DBMS 종속) | 저장 공간 효율성, 트랜잭션 처리량, 디스크 I/O 최적화 |

## Ⅲ. 엔터프라이즈 데이터 모델링의 핵심 구성 요소

### 가. 엔티티 분류 체계
- **키 엔티티 (Key / Fundamental)** : 자신의 부모 없이 독립적으로 생성되는 기본 엔티티 (예: 고객, 상품, 사원).
- **메인 엔티티 (Main)** : 업무의 중심을 이루며 키 엔티티로부터 생성되는 엔티티 (예: 주문, 청구, 계약).
- **액션 엔티티 (Action / Transactional)** : 메인 엔티티의 상세 내역이나 상태 변경 이력 (예: 주문상세, 입출금이력).

### 나. 식별자(Identifier)의 체계적 설계
- **대표성** : 주식별자(Primary) vs 보조식별자(Alternate).
- **생성 여부** : 본질식별자(업무적 속성 조합) vs 인조식별자(일련번호, UUID 등 시퀀스 부여).

## Ⅳ. 데이터 모델링 수행 시 주요 한계점 및 해결 방안

- **분석가-현업 간 도메인 이해 격차로 인한 요구사항 불일치** :
  - **한계점** : 비즈니스 규칙이 개념/논리 모델로 변환되는 과정에서 현업의 암묵지가 누락되거나 왜곡되어 시스템 구축 후 모델 전면 재수정 사태 빈발.
  - **해결 방안** : 이벤트 스토밍(Event Storming) 워크숍을 통한 유비쿼터스 언어(Ubiquitous Language) 확립, 도메인 전문가와 데이터 모델러의 페어 모델링 제도화.
- **확장성을 고려하지 않은 물리 모델 설계로 인한 성능 병목** :
  - **한계점** : 정규화 이론에만 치중하여 실제 인덱스 크기, I/O 블록 단위, 트래픽 급증을 예측하지 못해 대량 트래픽 환경에서 병목 및 테이블 락 발생.
  - **해결 방안** : 워크로드 기반 용량 산정 및 쿼리 패턴 프로파일링, 샤딩/파티셔닝 고려 설계 및 수평 확장(Scale-out) 친화적 키 설계.
- **MSA 확산에 따른 데이터 모델 파편화 및 정합성 관리 난제** :
  - **한계점** : 서비스 단위 분할로 인해 전사 마스터 데이터(고객, 상품 등)의 일관성이 상실되고 서비스 간 데이터 중복 및 동기화 난제 야기.
  - **해결 방안** : 마스터 데이터 관리(MDM) 체계 유지, 분산 이벤트 브로커(Kafka) 기반의 도메인 이벤트 발행/구독(Pub/Sub) 아키텍처 구축.

## Ⅴ. 현대적 데이터 아키텍처 환경에서의 실무 제언

- **논리 모델의 불변성과 물리 모델의 최적화 분리** : 논리 데이터 모델은 비즈니스의 본질을 투영하므로 정규화(3NF)를 완벽히 준수해야 하며, 성능을 위한 반정규화나 샤딩 설계는 물리 모델링 단계에서 명문화된 근거(Explain Plan, 트래픽 추정치)를 바탕으로 분리 설계해야 함.
- **애자일 개발 환경에서의 데이터 모델 거버넌스** : 스프린트 단위의 빠른 기능 배포로 인해 데이터 모델이 파편화되는 현상을 방지하기 위해, Git 기반 모델 버전 관리(Schemachange, Flyway, Liquibase)와 전사 데이터 아키텍트(DA)의 변경 검토 체계를 확립할 것을 제언함.
