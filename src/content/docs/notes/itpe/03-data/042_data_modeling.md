## 연관 키워드

- 데이터 모델링(Data Modeling), ERD(Entity-Relationship Diagram), 개념적·논리적·물리적 모델링, 정규화(Normalization), 반정규화(Denormalization)
- 엔티티(Entity), 식별자(Identifier), 주식별자(Primary Identifier), 카디널리티(Cardinality), 단일 진실 공급원(SSOT, Single Source of Truth)

## Ⅰ. 데이터 모델링(Data Modeling)의 개요

- 핵심 요약 : 현실 세계의 업무와 데이터를 추상화·단순화·명확화하여 데이터베이스 구조로 형상화하는 체계적 과정.
- 개념 : 복잡한 현실 세계의 비즈니스 프로세스와 데이터를 약속된 표기법(ERD(Entity-Relationship Diagram) 등)으로 추상화(Abstraction), 단순화(Simplification), 명확화(Clarity)하여 컴퓨터 데이터베이스 구축에 최적화된 논리적·물리적 구조로 형상화하는 체계적 과정.
- 배경 및 필요성 : 업무 요구사항의 누락 없는 반영과 시스템 확장·유지보수 유연성 확보 요구.
- 주요 목적 : 데이터 아키텍처의 근간 확립과 비즈니스 규칙의 데이터 계층 반영.

## Ⅱ. 데이터 모델링의 특징

- 핵심 요약 : 중복 최소화·규칙 반영·성능과 유연성의 균형을 갖춘 3단계 순차 전개 체계.

1. 단일 진실 공급원(SSOT, Single Source of Truth) : 데이터 중복 최소화를 통한 시스템 전반 정합성 유지.
2. 비즈니스 규칙의 정확한 반영 : 카디널리티(Cardinality)와 관계를 통한 도메인 규칙의 데이터 계층 강제.
3. 성능과 유연성의 균형 : 미래 비즈니스 변화 수용성과 쿼리 처리 성능의 동시 확보.
4. 개념적 → 논리적 → 물리적 모델링의 3단계 순차 전개.
5. 엔티티의 키(Key)·메인(Main)·액션(Action) 3분류 체계.

## Ⅲ. 데이터 모델링의 구조 (흐름)

- 핵심 요약 : 현실 요구사항에서 물리 데이터베이스까지의 3단계 전개와 엔티티·식별자 체계.
- 3단계 모델링 전개 과정.

```text
[ 데이터 모델링 3단계 발전 과정 ]
[현실 세계 업무 요구사항]
           |
           v
  [1. 개념적 모델링 (Conceptual)] : 핵심 엔티티 도출, 주요 관계 정의 (업무 중심, 고수준 ERD)
           |
           v
  [2. 논리적 모델링 (Logical)]    : 모든 속성 정의, 식별자 확정, 정규화(3NF, Third Normal Form), M:N 해소 (기술 독립)
           |
           v
  [3. 물리적 모델링 (Physical)]   : 특정 DBMS 선정, 테이블/컬럼명, 데이터타입, 인덱스, 반정규화
           |
           v
[물리 데이터베이스 (DDL(Data Definition Language) 생성 및 운영)]
```

- 물리적 모델링 단계 : 특정 DBMS(Database Management System) 선정 및 테이블·컬럼 명명, 데이터 타입, 인덱스 설계, 반정규화 적용.
- 엔티티 분류 체계.

```text
[ 엔티티 분류 체계 ]
[키 엔티티(Key/Fundamental)] --독립 생성--> [메인 엔티티(Main)] --상세·이력--> [액션 엔티티(Action/Transactional)]
   예 : 고객, 상품, 사원                    예 : 주문, 청구, 계약             예 : 주문상세, 입출금이력
```

- 식별자(Identifier) 설계 기준.
  1. 대표성 : 주식별자(Primary)와 보조식별자(Alternate)의 구분.
  2. 생성 여부 : 본질식별자(업무적 속성 조합)와 인조식별자(일련번호, UUID(Universally Unique Identifier) 등 시퀀스 부여)의 구분.

## Ⅳ. 3단계 모델링의 비교

- 핵심 요약 : 추상화 수준과 고려사항이 단계별로 상이한 개념·논리·물리 모델링의 구분.

| 모델링 단계 | 주요 활동 및 산출물 | 추상화 수준 | 핵심 고려사항 |
| :--- | :--- | :--- | :--- |
| 개념적 모델링 (Conceptual) | 핵심 엔티티(Entity) 선정, 엔티티 간 관계(Relationship) 정의, 주제영역(Subject Area) 분류 | 가장 높음 (전사 관점) | 현업 및 경영진과의 의사소통, 업무 범위의 명확한 획정 |
| 논리적 모델링 (Logical) | 전체 속성 정의, 주식별자/외래키 지정, 관계 카디널리티 구체화, 1~3차 정규화 수행 | 중간 (업무 완전성) | 특정 DBMS 독립적인 비즈니스 규칙의 완전 무결한 구현 |
| 물리적 모델링 (Physical) | 물리적 테이블/컬럼 명명, 데이터 타입/길이 지정, 인덱스 설계, 파티셔닝, 역정규화 검토 | 가장 낮음 (하드웨어/DBMS 종속) | 저장 공간 효율성, 트랜잭션 처리량, 디스크 I/O 최적화 |

## Ⅴ. 데이터 모델링의 장점과 한계

- 핵심 요약 : 요구사항 정확 반영·유연성 확보의 장점과 이해 격차·확장성·파편화 이슈의 한계 공존.
- 장점
  1. 업무 요구사항의 누락 없는 반영과 의사소통 표준 제공.
  2. 데이터 중복 최소화를 통한 시스템 확장·유지보수 유연성 확보.
- 한계점 1 : 분석가-현업 간 도메인 이해 격차에 따른 요구사항 불일치
  - 한계점 : 비즈니스 규칙의 개념/논리 모델 변환 과정에서 현업 암묵지의 누락·왜곡, 시스템 구축 후 모델 전면 재수정 사태 빈발.
  - 해결 방안 : 이벤트 스토밍(Event Storming) 워크숍을 통한 유비쿼터스 언어(Ubiquitous Language) 확립, 도메인 전문가와 데이터 모델러의 페어 모델링 제도화.
- 한계점 2 : 확장성 미고려 물리 모델 설계에 따른 성능 병목
  - 한계점 : 정규화 이론 편중으로 인한 인덱스 크기·I/O 블록 단위·트래픽 급증의 미예측, 대량 트래픽 환경의 병목 및 테이블 락 발생.
  - 해결 방안 : 워크로드 기반 용량 산정 및 쿼리 패턴 프로파일링, 샤딩/파티셔닝 고려 설계 및 수평 확장(Scale-out) 친화적 키 설계.
- 한계점 3 : MSA(Microservice Architecture) 확산에 따른 데이터 모델 파편화·정합성 관리 난제
  - 한계점 : 서비스 단위 분할에 따른 전사 마스터 데이터(고객, 상품 등) 일관성 상실, 서비스 간 데이터 중복·동기화 난제 야기.
  - 해결 방안 : 마스터 데이터 관리(MDM, Master Data Management) 체계 유지, 분산 이벤트 브로커(Kafka) 기반의 도메인 이벤트 발행/구독(Pub/Sub, Publish/Subscribe) 아키텍처 구축.

## Ⅵ. 데이터 모델링에 대한 기술사적 제언

- 핵심 요약 : 논리 모델의 불변성 유지와 물리 모델의 근거 기반 최적화 분리, 모델 거버넌스 확립.
- 논리 모델의 불변성과 물리 모델의 최적화 분리 : 논리 데이터 모델의 정규화(3NF) 완전 준수, 성능 목적의 반정규화·샤딩 설계의 물리 모델링 단계 근거(Explain Plan, 트래픽 추정치) 명문화 기반 분리 설계.
- 애자일 개발 환경에서의 데이터 모델 거버넌스 : 스프린트 단위 배포에 따른 데이터 모델 파편화 방지, Git 기반 모델 버전 관리(Schemachange, Flyway, Liquibase)와 전사 데이터 아키텍트(DA, Data Architect)의 변경 검토 체계 확립.

## Ⅶ. 결론

- 핵심 요약 : 데이터 모델링은 비즈니스 본질의 투영과 물리 최적화의 분리가 핵심인 설계 활동.
- 요약 : 개념·논리·물리 3단계 전개를 통한 업무 요구사항의 데이터 구조 형상화.
- 시사점 : 도메인 협업 체계와 모델 거버넌스를 통한 파편화 방지 및 확장성 확보 필요.
