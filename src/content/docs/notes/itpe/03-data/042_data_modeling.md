## 지식 로드맵 내 현재 위치

자료처리·데이터 → 데이터 모델링 → **데이터 모델링(식별·비식별 관계)**

## 30초 인출

- 본질: 데이터 모델링은 업무 정보와 규칙을 데이터 구조와 관계로 표현하는 설계 활동
- 메커니즘: 개념(엔터티·관계) → 논리(속성·키·제약·정규화) → 물리(테이블·자료형·인덱스·DDL) 순으로 구체화하며, 부모 키가 자식 기본키의 일부가 되는지에 따라 식별·비식별 관계를 선택
- 통찰: 논리 모델과 실제 DB 제약이 어긋나면 중복·오류가 쌓이므로 대표 거래 사례와 CRUD 매트릭스로 업무 규칙을 검증하고 요구사항·모델·DDL을 추적

<details>
<summary>핵심 용어</summary>

- **데이터 모델링(Data Modeling)** : 업무 정보와 규칙을 데이터 구조와 관계로 표현하는 설계
- **개념·논리·물리 모델** : 업무 대상 / DBMS 독립적 구조 / 특정 DBMS 구현 구조
- **식별 관계(Identifying)** : 부모 키가 자식 기본키의 일부가 되는 관계
- **비식별 관계(Non-Identifying)** : 부모 키가 자식의 외래키로만 참조되는 관계
- **CRUD 매트릭스** : 프로세스가 엔터티를 생성·조회·수정·삭제하는 관계를 표로 나타낸 것
- **기본키·외래키** : 행을 식별하는 키 / 다른 엔터티의 키를 참조하는 속성

</details>

## 2~4교시 25점 답안

## Ⅰ. 데이터 모델링의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **데이터 모델링** 은 업무 정보와 규칙을 데이터 구조와 관계로 표현하는 설계 활동 |
| 목적 | 업무 규칙의 명확화와 일관된 데이터베이스 구현 기준 제공 |

## Ⅱ. 특징

| 특징 | 설계 의미 |
|---|---|
| 단계적 구체화 | 업무 개체에서 속성·키·DDL까지 상세화 |
| 논리·물리 분리 | 업무 규칙을 DBMS와 독립적으로 정의한 뒤 제품 기능 반영 |
| 관계 중심 검증 | 식별자·참조·필수성 규칙을 대표 거래 사례로 확인 |

## Ⅲ. 모델링 단계별 수행내용

```text
개념: 엔터티·관계 ─ 업무 용어와 대상 합의
        ↓ 구체화
논리: 속성·키·제약·정규화 ─ DBMS 독립적 구조
        ↓ 구현 결정
물리: 테이블·자료형·인덱스·DDL ─ 실제 DBMS 반영
```

| 수준 | 대상 | 주요 내용 |
|---|---|---|
| 개념 | 업무 관리 대상 | 주요 개체와 업무 관계 |
| 논리 | 개체 식별·연결 규칙 | 속성·기본키·외래키·제약·정규화 |
| 물리 | 선택한 DBMS의 구현 구조 | 테이블·자료형·인덱스·파티션 |

## Ⅳ. 식별·비식별 관계 비교와 고려사항

| 기준 | 식별 관계 | 비식별 관계 |
|---|---|---|
| 키 구조 | 부모 키가 자식 기본키의 일부 | 부모 키는 외래키이며 자식 기본키와 분리 |
| 식별 방식 | 부모 키와 자식 속성의 조합으로 식별 | 자식 자체 기본키로 식별 |
| 선택 기준 | 자식의 식별이 부모에 의존하는 업무 규칙 | 자식이 독립 식별자를 갖는 업무 규칙 |
| 제약 주의 | 기본키에 포함된 FK는 NULL 불가 | FK의 NULL 허용은 업무 규칙에 따름 |

```text
부모 PK = P_ID
 ├ 자식 식별이 부모에 종속 → 자식 PK(P_ID, C_NO), FK(P_ID)   [식별]
 └ 자식 고유 식별자 존재  → 자식 PK(C_ID),      FK(P_ID)   [비식별]
```

| 고려사항 | 확인 내용 |
|---|---|
| 업무 적합성 | 엔터티·속성·관계가 요구사항을 반영하는지 |
| 식별성 | 기본키가 행을 유일하게 식별하는지 |
| 무결성 | 필수값·도메인·참조 제약이 업무 규칙과 맞는지 |
| 구현 가능성 | DBMS 기능·예상 부하·운영 제약 |
| CRUD 매트릭스 | 프로세스별 엔터티 생성·조회·수정·삭제를 표로 만들어 누락·중복 검증 |

표기 관례는 모델링 도구에 따라 다르며, 관계 유형만으로 참조 무결성이나 성능을 단정하지 않음.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 논리 모델과 실제 DB 제약 불일치 | 요구사항·논리 모델·DDL의 추적표 유지 |
| 식별 관계를 업무 규칙과 다르게 설계 | 실제 거래 사례로 식별 방식과 FK 제약 검증 |

## Ⅵ. 제언

개념→논리→물리 순으로 업무 의미를 확정하고, 요구사항·모델·DDL을 추적해 변경을 함께 검토

```text
요구사항 → 개념 → 논리(정규화·CRUD 검증) → 물리(성능 반영) → DDL 동기화
```

| 구분 | 물리 중심 설계 | 제언: 단계적 설계 |
|---|---|---|
| 업무 반영 | 맥락 유실 | 업무 의미 보존 |
| 변경 대응 | 불일치 누적 | 추적으로 동기화 |
