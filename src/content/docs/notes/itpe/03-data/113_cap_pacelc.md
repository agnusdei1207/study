## 지식 로드맵 내 현재 위치

자료처리·데이터 → 분산 데이터베이스 → **CAP·PACELC 정리**

## 30초 인출

- 본질: CAP은 네트워크 분할 중에 일관성과 가용성을 함께 보장할 수 없다는 한계이고, PACELC는 정상 상태에서도 지연과 일관성 사이의 선택이 있음을 더한 분산 시스템 모형
- 메커니즘: 분할이 생기면 최신 상태를 확인할 때까지 응답을 보류(일관성)하거나 정상 노드가 계속 응답(가용성)하고, 분할이 없어도 복제본 확인 범위를 넓히면 일관성이 강해지는 대신 지연이 늘어남
- 통찰: 제품의 CP/AP 별칭은 배포·설정·API별 동작 차이를 숨기므로 업무별로 성공 응답의 의미와 허용할 오래된 값의 범위를 정하고 정상·분할 상태 모두에서 시험

<details>
<summary>핵심 용어</summary>

- **CAP 정리** : 분할 발생 시 일관성(C)과 가용성(A) 중 하나를 선택해야 한다는 한계
- **일관성(Consistency)** : 성공한 쓰기가 이후 읽기에 반영되는 선형화 가능성
- **가용성(Availability)** : 장애가 없는 노드에 접수된 요청이 응답을 받는 성질
- **분할 허용(Partition tolerance)** : 노드 사이 통신이 끊겨도 시스템이 동작
- **PACELC** : 분할(P) 시 A와 C, 그 밖에는(Else) 지연(L)과 C를 절충
- **쿼럼(R + W > N)** : 읽기·쓰기 집합이 겹치도록 하는 조건
- **최종 일관성** : 갱신이 없으면 복제본이 결국 같은 값으로 수렴

</details>

## 2~4교시 25점 답안

## Ⅰ. CAP·PACELC의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **CAP·PACELC** 는 분할 중 일관성·가용성의 한계와 정상 상태의 지연·일관성 선택을 설명하는 분산 시스템 모형 |
| 목적 | 읽기·쓰기 요구에 맞는 복제·장애 처리 방식 선택 |

## Ⅱ. 특징

| 개념 | 정확한 의미 | 설계상 확인 |
|---|---|---|
| C | 선형화 가능한 읽기·쓰기 | 성공한 쓰기 뒤 다른 노드의 읽기 결과 |
| A | 장애 없는 노드에 접수된 요청의 응답 | 분할된 노드가 응답을 계속하는지 |
| P | 노드 간 통신 단절 | 분할 중 읽기·쓰기 동작 |

CAP은 세 가지 중 둘을 고르는 제품 분류표가 아니라 분할 상황의 보장 한계이며, 단일 노드의 `CA` 분류나 제품의 고정된 `CP/AP` 표기는 설정·API별 차이를 숨김.

## Ⅲ. 분할·정상 상태별 선택

```text
분할 발생 → 최신 상태 확인 불가
   ├ 응답 보류: 일관성 우선
   └ 응답 계속: 최신 값 보장 약화(가용성 우선)
정상 상태 → 복제본 확인 범위 선택
   ├ 확인 확대: 일관성 강화, 지연 증가
   └ 확인 축소: 지연 감소, 최신 값 보장 약화
```

## Ⅳ. CAP과 PACELC 비교, 업무별 판단

| 비교 | CAP | PACELC |
|---|---|---|
| 다루는 조건 | 분할 중 | 분할 중 + 정상 상태 |
| 절충 | C와 A | P일 때 A와 C, 그 외 L과 C |
| 쓰임 | 분할 동작의 한계 설명 | 읽기·쓰기 정책 비교 |

| 검증 | 관계 |
|---|---|
| 쿼럼 중첩 | R + W > N이면 읽기·쓰기 집합이 겹침 |
| 버전·순서 | 겹친 복제본에서 최신 성공 쓰기 식별 |
| API 차이 | 강한 읽기와 최종 일관 읽기 구분(예: DynamoDB는 기본 최종 일관 읽기와 선택적 강한 일관 읽기를 함께 제공) |

R + W > N은 집합이 겹친다는 조건일 뿐 선형화를 보장하지 않으며 쓰기 승인 순서·버전 판정·장애 모델까지 확인.

| 업무 요구 | 우선 확인 | 시험 |
|---|---|---|
| 잔액·재고 등 동시 갱신 | 성공 쓰기의 읽기 관찰과 충돌 처리 | 분할·중복 쓰기 시험 |
| 검색·추천 등 지연 민감 조회 | 허용 가능한 오래된 데이터 범위 | 복제 지연·응답시간 측정 |
| 로그·이벤트 수집 | 유실 허용·복구 절차 | 장애 중 적재와 복구 후 대사 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| CP/AP 별칭만으로 업무별 결과를 알 수 없음 | 핵심 API의 분할 중 결과를 정의하고 장애 실험 |
| 쿼럼 교집합만으로 선형화 가능성 단정 | 쓰기 순서·버전 판정·복구 모델 검증 |
| 정상 시 지연 요구를 분할 시험에서만 판단 | 정상·분할 모두에서 지연·허용 오래된 값 측정 |

## Ⅵ. 제언

업무 데이터별로 일관성 수준을 다르게 정하고 정상·분할 상태 모두에서 시험

```text
업무별 허용 오래된 값·지연 정의 → 복제·쿼럼 설정 → 정상·분할 상태 시험
```

| 구분 | 제품 전체를 CP/AP로 분류 | 제언: 업무·API별 선택 |
|---|---|---|
| 잔액·재고 | 오해 위험 | 강한 일관성 적용 |
| 로그·추천 | 과잉 보장 | 완화한 일관성 |
