## 지식 로드맵 내 현재 위치

지식 위치: 자료처리·데이터 → 분산 데이터베이스 → **CAP·PACELC**

## 30초 인출

- 본질: **CAP** 은 네트워크 분할 시 선형화 가능한 일관성과 모든 정상 노드의 응답 가용성을 동시에 보장할 수 없다는 한계
- 메커니즘: 분할 중 일관성·가용성 선택 → 정상 상태의 일관성·지연 선택 → API·복제 설정별 장애 실험
- 통찰: 네트워크 분할(P) 시 일관성(C)과 가용성(A)의 양자택일을 규정한 CAP의 한계를 극복하고 정상 상태의 지연시간(Latency)과 일관성(Consistency)을 함께 고려하는 PACELC 관점의 아키텍처 설계 필수

<details>
<summary>핵심 용어</summary>

- **CAP** : 분산 시스템의 네트워크 분할 상황에서 일관성과 가용성의 동시 보장 한계
- **일관성(Consistency)** : 성공한 쓰기를 뒤이은 읽기가 최신 값으로 관찰하는 선형화 가능성
- **가용성(Availability)** : 장애가 없는 노드가 받은 요청에 결국 응답하는 성질; 응답이 최신 값임을 뜻하지는 않음
- **네트워크 분할(Partition)** : 노드 집합 사이의 메시지 전달이 끊기거나 지연되는 상황
- **PACELC** : 분할 시 가용성·일관성, 정상 시 지연·일관성 사이의 선택을 구분하는 분산 시스템 설명 틀
- **쿼럼(Quorum)** : 읽기·쓰기 작업에 참여시킬 복제본 수의 기준; 중첩만으로 선형화 가능성이 자동 보장되지는 않음

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **CAP·PACELC** 는 분할 중 일관성·가용성의 한계와 정상 상태의 지연·일관성 선택을 설명하는 분산 시스템 모형 |
| 목적 | 업무의 읽기·쓰기 요구에 맞는 복제·장애 처리 방식의 선택 |

## Ⅱ. 분할 조건과 API별 보장의 특징

```text
네트워크 분할로 복제본 간 통신 불가
   ├ 최신 상태를 확인할 때까지 응답 보류 → 일관성 선택
   └ 정상 노드가 계속 응답 ───────────→ 가용성 선택
분할 시 선택은 읽기·쓰기 API와 복제 설정에 따라 관찰
```

| 개념 | 정확한 의미 | 설계상 확인 |
|---|---|---|
| C | 선형화 가능한 읽기·쓰기 | 성공한 쓰기 뒤 다른 노드의 읽기 결과 |
| A | 장애가 없는 노드에 접수된 요청의 응답 | 분할된 노드가 응답을 계속하는지 |
| P | 노드 사이의 통신 단절 | 분할 중 읽기·쓰기 동작 |

- CAP은 세 가지 중 두 가지를 임의로 고르는 제품 분류표가 아니라 **분할 상황** 의 보장 한계
- 단일 노드 DBMS의 `CA` 분류나 특정 제품의 영구적 `CP/AP` 표기는 배포·설정·API별 동작 차이를 숨기는 한계

## Ⅲ. 분할·정상 상태별 읽기·쓰기 선택 체계

```text
분할 발생 → 최신 상태 확인 불가
          ├─ 응답 제한: 강한 일관성 요구 유지
          └─ 응답 계속: 최신 값 보장은 약화 가능
정상 상태 → 복제본 확인 범위 선택
          ├─ 확인 확대: 일관성 강화, 지연 증가 가능
          └─ 확인 축소: 지연 감소, 최신 값 보장 약화 가능
```

## Ⅳ. CAP·PACELC와 업무별 일관성 요구 비교

| 비교 | CAP | PACELC |
|---|---|---|
| 다루는 조건 | 네트워크 분할 중 | 분할 중 + 정상 상태 |
| 중심 절충 | C와 A | P일 때 A와 C, 그 외 L과 C |
| 쓰임 | 분할 동작의 한계 설명 | 정상·장애 상태의 읽기·쓰기 정책 비교 |

PACELC는 설계 선택을 설명하는 모형이며 모든 시스템의 고정된 네 칸 분류나 특정 성능 수치를 보장하는 규칙이 아님.

### 쿼럼과 제품별 설정 검증

| 항목 | 검증할 관계 |
|---|---|
| 쿼럼 중첩 | $R+W>N$일 때 참여 복제본의 교집합 |
| 버전·순서 | 겹친 복제본의 최신 성공 쓰기 식별 |
| 장애 복구 | 분할 후 충돌과 재동기화 처리 |
| API 차이 | 제품 내 강한 읽기와 최종 일관 읽기의 구분 |

$R+W>N$은 읽기·쓰기 집합이 중첩된다는 조건. 강한 일관성은 쓰기 승인 순서, 버전 판정, 장애 모델까지 확인해야 판단 가능. 예를 들어 DynamoDB도 테이블 읽기에는 기본 최종 일관 읽기와 선택적 강한 일관 읽기가 공존하므로 제품 전체를 단일 CAP 유형으로 고정할 수 없음.

### 업무 요구에 따른 판단

| 업무 요구 | 우선 확인할 동작 | 시험 방법 |
|---|---|---|
| 잔액·재고 등 동시 갱신 | 성공한 쓰기의 읽기 관찰과 충돌 처리 | 분할·중복 쓰기 시험 |
| 검색·추천 등 지연 민감 조회 | 허용 가능한 오래된 데이터의 범위 | 복제 지연과 응답시간 측정 |
| 로그·이벤트 수집 | 유실 허용 여부와 복구 절차 | 장애 중 적재와 복구 후 대사 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 제품의 CP/AP 별칭만으로 업무별 읽기·쓰기 결과를 알 수 없음 | 핵심 API의 성공 응답·분할 중 결과를 정의하고 복제 설정별 장애 실험 |
| 쿼럼 교집합만으로 선형화 가능성을 단정 | 성공 쓰기 순서·버전 판정·복구 모델까지 검증 |
| 정상 시 지연 요구를 분할 시험에서만 판단 | 정상·분할 상태 모두에서 읽기·쓰기 지연과 허용 오래된 값 측정 |

## Ⅵ. 제언

분할 시(PC vs PA)와 정상 시(EL vs EC)의 비즈니스 트레이드오프를 평가하여 결제는 PC/EC(RDBMS, Spanner), 소셜 피드는 PA/EL(DynamoDB, Cassandra)로 차등 구현.

### PACELC 정리 의사결정 모델

```text
[분산 데이터베이스 상태]
       │
       ├─ [네트워크 분할 발생 시 (Partition P)]
       │        ├─ [A: 가용성 우선] ──► PA (최종 일관성, DynamoDB)
       │        └─ [C: 일관성 우선] ──► PC (트랜잭션 중단, HBase)
       │
       └─ [정상 운영 상태 시 (Else E)]
                ├─ [L: 지연시간 최소] ──► EL (비동기 복제, Cassandra)
                └─ [C: 일관성 우선]   ──► EC (동기 복제, Google Spanner)
```

### 선택 근거: 제언: PACELC 정리

| 구분 | CAP 정리 | 제언: PACELC 정리 |
|---|---|---|
| 평가 관점 | 네트워크 장애(Partition) 상황만 평가 | 장애 상황(P/A/C)과 정상 운영 상황(E/L/C) 동시 평가 |
| 정상 시 트레이드오프 | 정상 상태의 성능 특성 설명 불가 | 지연시간(Latency)과 일관성(Consistency) 절충 모델링 |
| 실무 아키텍처 | 단순 CP vs AP 이분법 매핑 | PA/EL, PC/EC 등 업무별 정밀 데이터 저장소 선정 |
