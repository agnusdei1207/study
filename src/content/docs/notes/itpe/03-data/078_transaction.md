## 연관 키워드

트랜잭션, ACID, COMMIT·ROLLBACK, 격리 수준, WAL, 동시성 제어, 사가

## Ⅰ. 트랜잭션의 개요

- 핵심 요약 : 하나의 논리적 작업을 데이터베이스가 전부 반영하거나 전부 취소하도록 묶은 연산 단위.
- 개념 : **트랜잭션** (Transaction)은 여러 읽기·쓰기 연산을 하나의 경계로 묶어, 성공하면 **COMMIT** (반영), 실패하면 **ROLLBACK** (취소)으로 처리하는 작업 단위.
- 배경 및 필요성 : 송금처럼 여러 변경이 함께 성공하거나 함께 실패해야 하는 업무에서, 중간 장애나 동시 실행이 있으면 데이터가 어긋날 수 있음.
- 주요 목적 : 실패와 동시 실행이 있어도 데이터 변경의 원자성과 정합성을 유지.

## Ⅱ. 트랜잭션의 특징 및 장점

- 핵심 요약 : 네 가지 속성이 원자성·일관성·격리성·영속성을 보장해 트랜잭션의 신뢰성을 설명하는 구조.

1. **원자성** (Atomicity) : 전체 작업을 모두 반영하거나 모두 취소 → 부분 반영과 중간 상태 노출 방지.
2. **일관성** (Consistency) : 정의된 제약과 업무 규칙을 지키는 상태로만 전이 → 무결한 데이터 유지.
3. **격리성** (Isolation) : 동시 실행이 서로에게 미치는 영향을 격리 수준으로 조절 → 동시 작업의 결과를 예측 가능하게 관리.
4. **영속성** (Durability) : 커밋된 변경을 장애 후에도 남도록 로그와 저장장치를 활용 → 장애 시 복구 가능.

- 위 네 속성을 묶어 **ACID** (Atomicity, Consistency, Isolation, Durability)라 부른다.
- DBMS가 모든 응용 업무 규칙을 자동으로 보장하지는 않으므로, 일관성은 제약조건과 설계가 함께 뒷받침해야 한다.

## Ⅲ. 트랜잭션 처리와 복구 흐름

- 핵심 요약 : 시작, 연산과 검증, 커밋 또는 롤백, 장애 복구의 단계로 데이터 상태를 관리.
- **WAL** (Write-Ahead Logging) : 데이터 페이지를 기록하기 전에 변경 로그를 안정 저장소에 먼저 남기는 원칙. 구체적인 로그 구조와 보장 범위는 DBMS에 따라 다름.
- **동시성 제어** (Concurrency Control) : 여러 트랜잭션이 같은 데이터에 접근할 때 충돌을 조정하는 장치로, 락(Lock)이나 MVCC(Multi-Version Concurrency Control) 등으로 구현.

```text
[트랜잭션 시작]
          ↓
[읽기·쓰기 연산]
          ↓
[제약·업무 규칙 검증]
          ↓
  성공 → COMMIT (반영)
  실패 → ROLLBACK (취소)
          ↓
[장애 발생 시 로그로 복구]
```

```text
[동시 트랜잭션의 데이터 접근]
          ↓
[동시성 제어: 락·MVCC]
          ↓
[격리 수준에 따른 변경 가시성 결정]
```

- 격리성의 구현 방식은 제품마다 다르므로 실제 동작을 DBMS 문서로 확인해야 한다.

## Ⅳ. ACID와 격리 수준 비교

- 핵심 요약 : 격리 수준이 높을수록 이상현상은 줄지만 동시성 비용이 커지므로, 두 요소의 균형으로 수준을 고른다.
- **격리 수준** (Isolation Level) : 동시에 실행되는 트랜잭션 사이에서 어떤 변경을 볼 수 있는지 정하는 단계.

| 격리 수준 | 일반적 특징 | 고려할 점 |
| --- | --- | --- |
| Read Uncommitted | 커밋되지 않은 데이터 읽기를 허용할 수 있음 | 오염 읽기(Dirty Read) 위험 |
| Read Committed | 커밋된 데이터만 읽음 | 반복 읽기 결과가 달라질 수 있음 |
| Repeatable Read | 트랜잭션 안에서 반복 읽기 일관성 강화 | 팬텀 읽기 등 동작은 제품별 차이 |
| Serializable | 직렬 실행과 동등한 결과를 지향 | 충돌·재시도·대기 비용 고려 |

- 실제 격리 보장은 DBMS 구현과 동시성 제어 방식에 따라 확인해야 한다.

## Ⅴ. 트랜잭션의 한계와 방안

- 핵심 요약 : 긴 트랜잭션, 격리 충돌, 분산 경계를 줄이고 재시도와 복구 절차를 함께 설계.
- **사가** (Saga) : 분산 환경에서 각 단계의 보상 트랜잭션으로 전체 일관성을 맞추는 패턴.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 긴 락 점유 | 트랜잭션이 길어져 다른 작업이 대기 → 처리량 저하 | 트랜잭션 범위 축소, 네트워크 호출을 트랜잭션 밖으로 분리 | 락 대기 시간 |
| 데드락·충돌 | 접근 순서가 엇갈려 교착 발생 → 재시도 증가 | 접근 순서 일관화, 오류 분류 후 제한적 재시도 | 데드락 건수, 롤백률 |
| 높은 격리 비용 | 높은 격리 수준은 대기와 재시도 비용 증가 | 업무상 허용되는 격리 수준 선정, 이상현상 시험 | 재시도율, 응답 시간 |
| 서비스 간 원자성 | 서로 다른 데이터베이스에 걸친 작업은 단일 커밋으로 묶을 수 없음 → 부분 실패 | 사가와 아웃박스 패턴으로 보상 절차 관리 | 보상 실행 건수 |

## Ⅵ. 트랜잭션에 대한 기술사적 제언

- 핵심 요약 : 업무 불변조건과 실패 시나리오를 먼저 정의한 뒤 격리와 복구 방식을 고르는 설계 순서를 따르는 것이 바람직.
- 커밋 지연, 락 대기 시간, 롤백률을 운영 지표로 상시 모니터링해 병목 위치를 찾아내는 체계가 필요하다.
- 여러 서비스가 얽힌 결제나 주문 업무는 멱등성 키와 운영 대사 체계를 설계에 포함해야 한다.
- 백업과 복구 훈련을 주기적으로 실시해, 로그와 저장장치 설정이 요구 복구 목표를 만족하는지 검증하는 것이 안전하다.

## Ⅶ. 결론

- 핵심 요약 : 트랜잭션은 데이터 신뢰성의 기본 단위이며, ACID·격리·복구·분산 실패 대응을 함께 설계해야 하는 기술.
- ACID 속성과 WAL, 격리 수준의 선택, 분산 환경의 사가 처리가 하나의 설계로 이어질 때 정합성이 유지된다.
