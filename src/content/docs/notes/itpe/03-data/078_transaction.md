## 답안 골격
```text
[트랜잭션] ◀━━ 머리: Ⅶ 내 의견 (ACID 원자성 보장과 MSA 분산 환경의 Saga 패턴 결과적 일관성 조화)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터베이스의 상태를 변환시키는 하나의 논리적 기능을 수행하기 위한 작업의 분할 불가능한 최소 단위
 ┣━ Ⅱ 특징 ───── ACID 4대 특성(원자성·일관성·격리성·영속성) · 올 오어 고씽(All or Nothing) · 커밋/롤백 제어
 ┣━ Ⅲ 구조 ───── 원자성(Atomicity: Undo 로그) / 일관성(Consistency: 무결성 제약) / 격리성(Isolation: 락, MVCC) / 영속성(Durability: Redo 로그, WAL)
 ┣━ Ⅳ 흐름 ───── 활동(Active) → 부분 완료(Partially Committed) → 완료(Committed) 또는 실패(Failed) → 철회(Aborted)
 ┣━ Ⅴ 비교 ───── 로컬 트랜잭션 vs 분산 트랜잭션 (단일 DBMS ACID/2PL vs 네트워크 분산/2PC 및 Saga 패턴)
 ┗━ Ⅵ 실무 ───── 긴 트랜잭션(Long-running)으로 인한 락 경합 및 커넥션 풀 고갈 / 분산 환경 2PC 블로킹
```
- 필수 키워드: ACID · 원자성(Undo) · 영속성(Redo, WAL) · 격리성(MVCC) · 5대 상태 전이 · 커밋(Commit) · 롤백(Rollback) · 분산 트랜잭션
- 기출: 129회 `데이터베이스 트랜잭션의 ACID 특성과 상태 전이도` → Ⅰ 개념 + Ⅲ ACID 4대 특성 + Ⅳ 상태 전이 5단계

## 한 줄 본질
- 동시 실행 및 시스템 장애 상황에서의 데이터 파손 위험 → 논리적 연산군을 하나의 묶음으로 정의하고 복구 로그(WAL)와 동시성 제어로 원자성·일관성 통제 → 완벽한 데이터 무결성 보장 / 잠금 대기 지연 발생

## 핵심 용어
- WAL(Write-Ahead Logging): 데이터베이스 메모리 버퍼의 변경 내용을 실제 디스크 데이터 파일에 쓰기 전에, 반드시 Redo 로그 파일에 먼저 기록하는 영속성 보장 메커니즘
- ARIES 복구 알고리즘: 장애 발생 시 Redo로 실패 직전 상태를 복원(Analysis $\rightarrow$ Redo)하고, 미완료 트랜잭션을 Undo로 취소하는 현대 DBMS 복구의 표준 알고리즘

## 핵심 통찰
- ACID는 단순한 단어가 아니라 '구체적 하드웨어/소프트웨어 장치'에 의해 구현됨:
  - 원자성(A) $\rightarrow$ Undo 로그 (실패 시 되돌림)
  - 일관성(C) $\rightarrow$ 무결성 제약조건, 트리거, DDL
  - 격리성(I) $\rightarrow$ 락(Lock), 격리 수준, MVCC 스냅샷
  - 영속성(D) $\rightarrow$ Redo 로그, 트랜잭션 저널링(WAL)
- 트랜잭션의 범위를 넓게 잡으면 시스템 전체가 멈춤 → 결제 API 호출이나 이메일 발송 같은 외부 네트워크 I/O를 DB 트랜잭션 블록 내부에 포함시키면 커넥션이 고갈되는 전형적 장애 발생
- 마이크로서비스(MSA)에서는 ACID를 버려야 함 → 분산 2단계 커밋(2PC)은 코디네이터 단일 장애와 긴 락 대기 때문에 실무 적용이 불가능하며, 최종 일관성(Saga 패턴)으로 우회해야 함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 체크포인트(Checkpoint) | 트랜잭션 복구 시간 단축 | 메모리의 더티 페이지를 디스크에 강제 플러시하여 장애 시 분석해야 할 Redo 로그 범위를 좁힘 |
| 보상 트랜잭션(Compensating Tx) | 분산 트랜잭션의 롤백 대체 | 이미 커밋된 이전 단계 작업을 논리적으로 반대되는 새 작업(예: 결제 완료 후 결제 취소)을 실행해 상쇄 |

## 이웃 토픽과 구분
- ACID vs BASE: ACID = 전통 RDBMS의 즉각적이고 엄격한 일관성 / BASE(Basically Available, Soft-state, Eventual consistency) = NoSQL 및 분산 시스템의 가용성 중심 결과적 일관성

## 문제·원인·대책
- 적용 상황: 이커머스 주문 결제 시 외부 PG사 결제 연동
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 외부 PG사 응답 지연(5초) 시 DB 커넥션 풀(DBCP) 100% 소진 및 전면 장애 | 외부 HTTP 통신을 DB `@Transactional` 범위 내에 포함시킴 | 외부 결제 통신을 트랜잭션 밖으로 분리하고 DB 작업만 최소 시간 트랜잭션으로 격리 | DB 커넥션 점유 시간 5초에서 5ms로 단축 |
| 전원 차단 장애 후 재부팅 시 커밋된 트랜잭션 데이터 유실 | 성능을 위해 `innodb_flush_log_at_trx_commit = 0` 설정 | WAL 매 커밋 시 디스크 동기 플러시(fsync, 설정값 1) 복원 | 정전 시에도 영속성(Durability) 100% 보장 |

## 이렇게 출제된다
- 제129회: "데이터베이스 트랜잭션(Transaction)의 ACID 특성을 각각 구현하기 위한 DBMS의 기술 요소를 매핑하고, 5가지 상태 전이도를 설명하시오." → 요구 포인트: ACID 4대 특성 정의 + Undo/Redo/Lock 매핑표 + 5대 상태(Active, Partially Committed, Committed, Failed, Aborted) 전이도

## 내 의견
- [트랜잭션 최소화 원칙과 트랜잭션 아웃박스 패턴] 분산 시스템에서 트랜잭션 내에 카프카 메시지 발행을 섞었다가 DB 롤백 시 이벤트만 날아가는 유령 이벤트 사고 빈번 → 나라면: 로컬 DB 트랜잭션에는 비즈니스 데이터와 아웃박스(Outbox) 테이블 적재만 묶고, 별도 Debezium CDC 프로세스가 카프카로 비동기 안전 발행하는 트랜잭셔널 아웃박스 패턴 도입
