## 지식 로드맵 내 현재 위치

데이터 관리 → 아키텍처·운영 역할 → DA와 DBA

## 30초 인출

- 본질: **DA와 DBA는** 조직의 데이터 구조·표준 설계와 데이터베이스 구현·운영을 나누어 수행하는 역할
- 메커니즘: DA는 업무 요구와 논리 구조를 정리하고, DBA는 이를 DBMS 물리 설계·운영 조건에 맞춰 구현하며 피드백
- 통찰: 클라우드 매니지드 DB 환경에서 단순 설치·패치 중심 운영을 벗어나 데이터 아키텍처, 성능 튜닝, 보안 거버넌스 중심의 데이터 신뢰성 엔지니어(DRE)로 전환 필수

<details>
<summary>핵심 용어</summary>

| 용어 | 설명 |
|---|---|
| **데이터 아키텍트(Data Architect, DA)** | 데이터 정의·구조·표준을 업무 요구에 맞게 설계하는 역할 |
| **데이터베이스 관리자(Database Administrator, DBA)** | 데이터베이스의 물리 구현·접근·성능·복구를 관리하는 역할 |
| **논리 데이터 모델(logical data model)** | 업무 엔티티·속성·관계를 DBMS 구현 세부와 분리해 표현한 모델 |
| **물리 데이터 모델(physical data model)** | 특정 DBMS의 저장·인덱스·파티션 등 구현 구조를 표현한 모델 |
| **데이터베이스 신뢰성 엔지니어(Database Reliability Engineer, DBRE)** | 자동화·신뢰성 공학을 데이터베이스 운영에 적용하는 직무 명칭 |

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 데이터 구조·표준 설계 역할과 데이터베이스 구현·운영 역할의 구분 |
| 목적 | 업무 데이터의 의미·품질을 유지하면서 안전하고 효율적인 저장·이용 지원 |

## Ⅱ. DA·DBA 역할의 특징

| 특징 | DA | DBA |
|---|---|---|
| 주된 관점 | 업무 데이터의 의미·표준 | DBMS 구현·운영 |
| 변경 시점 | 논리 모델과 업무 규칙 검토 | 물리 구조·성능·복구 영향 검토 |
| 공동 책임 | 정의가 실제 저장 구조에 반영되는지 확인 | 운영 변경이 데이터 의미를 깨지 않는지 확인 |

## Ⅲ. 논리 모델·DDL·운영 변경의 협업 체계

```text
업무 요구·용어·품질 규칙
       ↓ DA: 개념·논리 모델과 표준 정의
논리 모델 ─── 대응 확인 ─── DBA: 물리 모델·DDL·권한
       ↓ 공동 변경 검토             ↓ 배포·복구 시험
모델 기준선 ← 차이·영향 환류 ← 운영 성능·보안·장애 증거
```

## Ⅳ. DBA와 DA의 책임·관점 비교

| 관점 | DA | DBA |
|---|---|---|
| 데이터 의미 | 업무 용어·정의·관계·표준 정리 | 구현이 의미·제약을 유지하는지 확인 |
| 구조 | 개념·논리 구조와 데이터 규칙 | DBMS별 저장·접근 구조와 제약 구현 |
| 운영 요구 | 데이터 품질·계보·변경 요구 전달 | 성능·용량·접근통제·백업복구 관리 |
| 의사결정 | 업무 모델·표준 변경 협의 | 물리 구조·운영 변경의 위험과 결과 공유 |

### 클라우드·자동화 환경의 역할 조정

| 변화 | 역할 조정 |
|---|---|
| 관리형 데이터베이스가 인프라 작업 일부를 제공 | DBA 업무는 서비스 책임분계·설정·접근통제·비용·복구 검증을 포함 |
| 스키마 변경이 코드 배포와 연결 | DA 표준과 DBA 운영 조건을 버전관리·자동 검사 절차에 반영 |
| 데이터 플랫폼·제품별 기능이 다양 | 역할을 고정 직급으로 가정하지 않고 조직·서비스 계약의 책임 경계를 문서화 |

직무 명칭과 권한은 조직 성숙도에 따라 유연하게 운영. DA와 DBA 간의 협업 체계를 구축하고 클라우드 전환에 따른 데이터 플랫폼 엔지니어링 역량 내재화 추진.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 논리 모델과 실제 스키마의 변경 경로가 분리돼 정의·제약 불일치 | 모델·DDL·승인·배포 결과를 같은 변경 건으로 형상관리하고 차이 검토 |
| 물리 최적화가 데이터 의미·품질 규칙을 깨뜨림 | DA의 업무 제약과 DBA의 실행 성능·복구 결과를 함께 승인 |
| 관리형 DB 사용 후 접근·복구 책임이 불명확 | 공급자 책임분계를 확인하고 권한·백업 복원 시험 책임자 지정 |

## Ⅵ. 제언

백업/복구 RTO/RPO 검증을 자동화하고 IaC(Terraform) 기반 선언적 인프라 관리 및 FinOps 관점의 클라우드 스토리지 비용 최적화 주도.

### 현대적 DBA의 4대 핵심 직무 영역

```text
[현대적 DBA (Data Reliability Engineer)]
       │
       ├─ [아키텍처 및 설계] : 논리/물리 데이터 모델링, 파티셔닝, 샤딩 설계
       ├─ [성능 및 튜닝]     : SQL 실행계획 분석, 인덱스 최적화, 커넥션 풀 통제
       ├─ [가용성 및 복구]   : 백업 자동화, 정기 DR 모의훈련, 쿼럼 HA 클러스터링
       └─ [보안 및 거버넌스] : 접근 통제, TDE 암호화, 메타데이터 표준화 통제
```

### 선택 근거: 제언: 클라우드 시대의 Modern DBA

| 구분 | 전통적 온프레미스 DBA | 제언: 클라우드 시대의 Modern DBA |
|---|---|---|
| 단순 인프라 작업 | OS 패치, DBMS 설치, 수동 백업 | 클라우드 자동화 위임 및 IaC 파이프라인 관리 |
| 주요 가치 창출 | 단순 시스템 장애 복구 | 데이터 아키텍처 고도화 및 SQL 성능 튜닝 집중 |
| 비용 관리 | 초기 서버 구매(CAPEX) 중심 | FinOps 기반 클라우드 자원 사용량 최적화 |
