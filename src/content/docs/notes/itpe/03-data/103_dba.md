```text
  │  - 전사 데이터 표준화 (단어, 용어, 도메인, 코드 사전 제정)  │
  │  - 데이터 거버넌스 총괄 및 메타데이터 단일진실공급원(SSOT)  │
  └──────────────────────────────┬──────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │              데이터베이스 관리자 (DBA)                      │
  │  - 물리 데이터 모델링 (테이블스페이스, 파티셔닝, 반정규화)  │
  │  - DBMS 인스턴스 구축 및 메모리(SGA/PGA)·파라미터 튜닝      │
  │  - 24x7 고가용성(HA), 백업/복구(DR, RTO/RPO), 보안 권한(DCL)│

                                 ▲
                                 │ 성능 피드백 & 물리 모델 변경 요청
```

- 본질: **비즈니스 요구사항을 개념적·논리적 관점에서 구조화하고 전사 데이터 표준과 거버넌스를 설계하는 데이터 아키텍트(DA)와, 이를 특정 DBMS 엔진의 물리적 저장 구조로 구현하여 성능 최적화, 24x7 고가용성(HA), 백업/재해복구(DR)를 전담하는 데이터베이스 관리자(DBA)의 역할 분담과 유기적 협력 체계**
- 암기: `디에이-논-표-거` (DA: 논리모델, 표준화, 거버넌스) / `디비에이-물-성-복` (DBA: 물리모델, 성능튜닝, 백업복구) / `디비알이` (DBRE: SRE 기반 자동화)
- 판단축:
  - **DA 중심 거버넌스**: 데이터 중복 최소화 및 전사 단일진실공급원(SSOT) 확보가 최우선인 신규 차세대 시스템 구축 및 엔터프라이즈 통합 영역
  - **DBA/DBRE 중심 운영**: 밀리초 단위 쿼리 지연시간 단축, 인덱스 튜닝, 무중단 장애 절체(Failover)가 최우선인 대규모 실시간 서비스 운영 영역
- 주의: 클라우드 완전관리형 DB(DBaaS) 확산으로 인프라 설치·OS 패치 업무는 자동화되었으나, 논리-물리 모델 정합성 관리, SQL 튜닝, FinOps 비용 최적화 등 DA-DBA 협업의 공학적 중요성은 더욱 증대됨

## 예상문제

> 전사 정보시스템의 안정적 구축 및 운영을 위한 데이터 아키텍트(DA)와 데이터베이스 관리자(DBA)의 개념 및 핵심 직무를 비교하고, 데이터 생애주기 전반에서 양자 간의 유기적 협업 체계 및 클라우드(DBaaS) 환경에서의 직무 진화 방향을 설명하시오. (25점)

## Ⅰ. 데이터 경쟁력을 결정하는 전문 조직: DA와 DBA 개요

#### 한줄 요약: 비즈니스 언어를 논리 모델로 설계하는 DA와 물리 엔진에서 성능과 영속성을 수호하는 DBA의 공학적 분업

- **배경**: 시스템 규모가 방대해지고 데이터 파편화(Silo)가 심화되면서, 업무 중심의 데이터 모델링과 시스템 중심의 인프라 운영을 단일 인력이 전담할 수 없는 한계 도래
- **정의**:
  - **DA (Data Architect)**: 기업의 비즈니스 규칙을 수용하여 전사 데이터 구조, 개념/논리 데이터 모델, 표준 메타데이터 체계를 설계·감수하는 전문가
  - **DBA (Database Administrator)**: 특정 DBMS의 물리 스키마를 구현하고, 튜닝, 보안, 백업/복구, 고가용성을 통해 무중단 운영을 책임지는 전문가

## Ⅱ. DA와 DBA의 5대 핵심 직무 비교 분석

#### 한줄 요약: 논리적 무결성을 지향하는 DA와 물리적 성능 및 가용성을 지향하는 DBA의 R&R 매트릭스

| 비교 항목 | 데이터 아키텍트 (DA) | 데이터베이스 관리자 (DBA) |
|:---|:---|:---|
| **핵심 관점** | **비즈니스 및 논리적 관점 (Logical View)** | **시스템 및 물리적 엔지니어링 관점 (Physical View)** |
| **모델링 영역** | 개념 데이터 모델링, 논리 데이터 모델링 (정규화) | 물리 데이터 모델링 (반정규화, 인덱스, 파티셔닝) |
| **주요 산출물** | 엔티티-관계 다이어그램(ERD), 전사 표준 용어 사전, 도메인 정의서 | 테이블정의서, DDL 스크립트, 파라미터 구성도, 백업/복구 절차서 |
| **품질 평가 척도** | 데이터 중복률 최소화, 표준 준수율, 비즈니스 반영도 | 쿼리 응답 시간, TPS, 가용성(99.999%), RTO/RPO 준수율 |
| **주요 통제 권한** | 데이터 모델 승인권, 표준 사전 등록 및 변경 심의권 | DDL/DCL 실행 권한, 프로덕션 DB 접근 제어권 |
| **협업 인터페이스** | 비즈니스 현업, BA(Business Analyst), AA(App Architect) | 시스템 엔지니어(SE), 인프라팀, 백엔드 개발자 |

## Ⅲ. 데이터 생애주기 전반의 DA-DBA 협업 프로세스

#### 한줄 요약: 분석 $\rightarrow$ 설계 $\rightarrow$ 구축 $\rightarrow$ 운영에 걸친 단계별 핸드오프(Handoff) 및 피드백 루프

```text
 [1. 분석·설계 단계] ──► [2. 물리 변환 단계] ──► [3. 구축·이행 단계] ──► [4. 운영·모니터링 단계]
  - DA: 비즈니스 분석      - DBA: 물리 모델 변환     - DA: 표준 준수 검수      - DBA: 성능 모니터링
  - DA: 3차 정규화 논리ERD - DBA: 파티셔닝/인덱스   - DBA: DDL 배포/초기적재   - DA-DBA: 반정규화 협의
```

1. **분석 및 논리 설계 단계**: DA가 현업의 요구사항을 수렴하여 엔티티와 관계를 정의하고 3차 정규화(3NF) 기반의 순수 논리 데이터 모델 도출
2. **물리 모델 변환 단계**: DBA가 논리 모델을 전달받아 트랜잭션 빈도와 데이터 볼륨을 분석하고, 성능을 위해 제한적 반정규화(테이블 병합, 중복 컬럼 추가), 파티션 키 선정, 인덱스 전략 수립
3. **구축 및 이행 단계**: DBA가 DDL을 작성하여 DB 인스턴스에 반영하고, DA는 생성된 물리 테이블이 전사 명명 규칙 및 표준 용어를 준수했는지 교차 감사
4. **운영 및 튜닝 단계**: 프로덕션 운영 중 특정 SQL에서 I/O 병목이 발생하면 DBA가 인덱스 튜닝을 수행하고, 구조 변경이 필요할 경우 DA와 협의하여 논리 ERD의 정합성을 동기화

## Ⅳ. 현대적 직무 확장: DBRE(Database Reliability Engineer)의 부상

#### 한줄 요약: 수작업 반복 운영 업무를 IaC와 CI/CD 파이프라인으로 자동화하는 SRE 사상의 데이터베이스 접목

```text
 [전통적 DBA: 수작업 티켓 중심]
  개발자 ──(티켓 신청)──► DBA ──(수작업 DDL 실행)──► 운영 DB (병목 발생, 실수 위험)

 [현대적 DBRE: 플랫폼 자동화 중심]
  개발자 ──(Git Commit)──► [CI/CD 파이프라인] ──► [자동화 검증기] ──► [무중단 DDL 배포]
                             (Flyway / Liquibase)    (DA 표준 린트)     (gh-ost / pt-osc)
```

- **DBRE의 핵심 원칙**:
  - **Everything as Code**: 데이터베이스 스키마 마이그레이션을 Git 리포지토리에서 형상 관리(Flyway, Liquibase)
  - **Toil Reduction**: 백업, 복구 검증, 슬로우 쿼리 수집 작업을 Python/Terraform 코드로 100% 자동화
  - **무중단 DDL(Online Schema Change)**: `gh-ost`나 `pt-online-schema-change`를 활용해 대용량 테이블 변경 시 락 없는 온라인 배포 보장

## Ⅴ. 클라우드 완전관리형 DB(DBaaS) 환경에서의 역할 진화

#### 한줄 요약: 하드웨어 인프라 유지보수에서 데이터 아키텍처 및 비용 최적화(FinOps)로의 무게중심 이동

| 구분 | 온프레미스(On-Premise) 환경 | 클라우드(DBaaS: AWS RDS/Aurora) 환경 |
|:---|:---|:---|
| **인프라 프로비저닝** | 하드웨어 발주, OS 설치, DBMS 엔진 설치 | Terraform 클릭 몇 번으로 즉시 프로비저닝 |
| **백업 및 패치** | 쉘 스크립트 작성, 백업 스토리지 관리, 수동 패치 | 스냅샷 기반 자동 백업, 유지보수 윈도우 자동 패치 |
| **고가용성(HA)** | 공유 스토리지, VIP 클러스터웨어(Pacemaker) 구축 | Multi-AZ 자동 페일오버 스위칭 (수십 초 내 완결) |
| **핵심 집중 업무** | 인프라 유지보수, 장애 대응, 물리 락 해소 | **데이터 거버넌스(DA), 쿼리 튜닝, FinOps 비용 통제** |

## Ⅵ. 실무 현장 분쟁 사례 및 갈등 해결 프로토콜

#### 한줄 요약: 표준과 성능 간의 상충, 비인가 DDL 배포 사고를 통제하는 거버넌스 룰

| 갈등 및 장애 상황 | 근본 원인 | 실무 해결 및 거버넌스 프로토콜 |
|:---|:---|:---|
| **정규화 vs 반정규화 갈등** | DA는 데이터 무결성을 위해 3NF 고수, DBA/개발자는 조인 부하 회피 위해 컬럼 중복 요구 | 1차적으로 쿼리 튜닝 및 커버링 인덱스로 해결 시도, 불가피할 경우 DA의 승인 하에 논리 ERD에 반정규화 사유 명시 |
| **비표준 컬럼 배포 사고** | 바쁜 일정으로 개발자가 DA 사전 검토 없이 임의로 DDL을 배포하여 용어 파편화 | CI/CD 파이프라인에 '데이터 표준 사전 Linter'를 탑재하여 비표준 단어 포함 시 빌드 실패 처리 |
| **운영 DB DDL 락(Lock) 장애** | DBA 검토 없이 수천만 건 테이블에 `ALTER TABLE ADD COLUMN` 수행으로 전사 타임아웃 | 온라인 DDL 도구 의무화 및 점검 시간대(Maintenance Window) 배포 통제 |

## Ⅶ. 기술사적 제언: 단일 진실 공급원(SSOT)과 데이터 카탈로그 거버넌스

#### 한줄 요약: DA와 DBA의 협업 산출물을 최신 상태로 유지하는 자동화된 엔터프라이즈 데이터 카탈로그 구축

- **과거 한계**: 프로젝트 초기에만 ERD를 예쁘게 그리고, 운영 단계에서는 DBA와 개발자가 임의로 DDL을 수정하여 모델과 실 DB가 따로 노는 'ERD 화석화' 발생
- **현대적 해법**:
  - 데이터 딕셔너리로부터 DDL 변경 사항을 매일 역공학(Reverse Engineering)하여 모델과 실 DB 간의 불일치를 자동 탐지
  - Alation, DataHub 등 현대적 **데이터 카탈로그**를 도입하여 비즈니스 용어(DA 영역), 물리적 테이블/인덱스(DBA 영역), 데이터 리니지(Data Lineage)를 전사 단일 뷰로 통합 제공해야 함

## 1교시 10점 답안 발췌

```text
1. DA(Data Architect)와 DBA(Database Administrator)의 개념
  - DA: 비즈니스 요구사항을 수용하여 전사 개념/논리 데이터 모델, 표준화, 거버넌스를 설계하는 전문가.
  - DBA: 특정 DBMS의 물리 스키마를 구축하고 성능 튜닝, 24x7 고가용성(HA), 백업/복구를 운영하는 엔지니어.

2. 핵심 직무 비교 및 협업 프로세스
  가. R&R 비교:
    - DA: 논리적 관점, 3NF 정규화, 표준 용어사전, SSOT 구축, 모델 승인권.
    - DBA: 물리적 관점, 반정규화/인덱스, SGA/PGA 튜닝, RTO/RPO 백업복구, DDL 실행권.
  나. 협업:
    - [DA 논리모델] -> [DBA 물리변환] -> [DA 표준감수] -> [DBA 배포/튜닝 피드백].

3. 클라우드 시대 직무 진화 (DBRE)
  - 단순 설치/패치는 DBaaS로 자동화, Git 기반 스키마 버전 관리 및 무중단 온라인 DDL을 수행하는 DBRE로 고도화.
```
