## 지식 로드맵 내 현재 위치

자료처리·데이터 → 데이터베이스 성능 → **인덱스(클러스터드·논클러스터드)**

## 30초 인출

- 본질: 데이터베이스 인덱스는 검색 조건에 맞는 행을 적은 탐색으로 찾도록 돕는 보조 자료구조
- 메커니즘: 검색 키로 인덱스의 루트·내부 노드를 거쳐 리프의 키와 행 참조에 도달해 행에 접근하며, 클러스터드는 키가 행의 저장 순서를 정하고 논클러스터드는 행과 별도 구조로 행 위치를 참조
- 통찰: 인덱스는 조회를 빠르게 하는 대신 저장 공간과 삽입·수정·삭제 비용을 늘리므로 대표 질의의 실행 계획과 선택도로 필요한 인덱스만 두고 쓰기 부하와 함께 측정

<details>
<summary>핵심 용어</summary>

- **인덱스(Index)** : 검색 키로 행을 빠르게 찾게 하는 보조 자료구조
- **클러스터드 인덱스** : 인덱스 키가 테이블 행의 저장 순서를 결정하는 인덱스(DBMS별 구현 차이)
- **논클러스터드 인덱스** : 테이블 행과 별도 구조로 행 위치·키를 참조하는 인덱스
- **선택도(Selectivity)** : 조건이 전체 행 중 걸러내는 정도
- **복합 인덱스** : 여러 열을 묶어 만든 인덱스
- **커버링 인덱스** : 질의에 필요한 열을 모두 포함해 테이블 접근 없이 응답하는 구성
- **실행 계획** : 최적화기가 선택한 질의 처리 경로

</details>

> 데이터베이스 인덱스를 설명하고, 클러스터드 인덱스와 논클러스터드 인덱스를 비교하여 설명하시오. (예상)

---

## 2~4교시 25점 답안

## Ⅰ. 인덱스의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **인덱스** 는 검색 조건에 맞는 행을 더 적은 탐색으로 찾도록 돕는 보조 자료구조 |
| 목적 | 접근 비용을 줄여 질의 응답 지원 |

## Ⅱ. 특징

| 특징 | 설계 영향 |
|---|---|
| 별도 접근 경로 | 키로 후보 행을 먼저 탐색 |
| 읽기·쓰기 절충 | 조회 이득과 저장·갱신 비용 동시 발생 |
| 계획 의존 | 선택도·통계·조건에 따라 최적화기의 사용 여부 변화 |

## Ⅲ. 기본 구조와 접근

```text
검색 키 → 루트 → 내부 노드 → 리프(키·행 참조) → 행 위치·기본키로 자료 접근
범위 조건은 정렬된 키 구간을 따라 후보 행을 좁힘
```

## Ⅳ. 클러스터드·논클러스터드 비교

| 항목 | 클러스터드 | 논클러스터드 |
|---|---|---|
| 저장 관계 | 인덱스 키가 행의 저장 순서를 결정(DBMS별) | 행과 별도의 인덱스 구조 |
| 행 참조 | 행이 인덱스 리프에 저장되는 구현 가능 | 행 위치 또는 클러스터링 키를 참조 |
| 고려사항 | 테이블당 개수·갱신 방식은 DBMS별 상이 | 보조 인덱스가 많으면 공간·쓰기 비용 증가 |

| 질의 특성 | 검토할 구성 | 확인 방법 |
|---|---|---|
| 동등·범위 검색 | B-tree 계열 인덱스 | 선택도·정렬·실행 계획 |
| 여러 열 조건 | 선두 열을 고려한 복합 인덱스 | 필터·정렬 조합의 계획 비교 |
| 인덱스만으로 응답 | 커버링 구성 | 테이블 접근 감소와 저장 비용 비교 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 인덱스 증가로 저장·백업 비용 확대 | 실행 계획으로 사용하지 않는 인덱스 제거 |
| 삽입·수정·삭제마다 갱신 비용 | 읽기 개선과 쓰기 부하를 함께 측정 |
| 낮은 선택도·불필요한 복합 인덱스 | 실제 조건·정렬 패턴과 선택도로 검증 |

인덱스 종류·클러스터드의 의미·최적화기 선택은 DBMS와 데이터 분포에 따라 달라지므로 실행 계획과 부하 측정으로 판단.

## Ⅵ. 제언

대표 질의의 실행 계획과 선택도를 근거로 인덱스를 설계하고 쓰기 부하까지 측정해 조정

```text
느린 질의 식별 → 실행 계획 확인 → 인덱스 설계 → 조회·쓰기 부하 측정 → 불필요 인덱스 정리
```

| 구분 | 컬럼마다 인덱스 생성 | 제언: 계획 기반 설계 |
|---|---|---|
| 조회 | 일부 개선 | 대표 질의 개선 |
| 쓰기·공간 | 부담 큼 | 필요한 만큼 |
