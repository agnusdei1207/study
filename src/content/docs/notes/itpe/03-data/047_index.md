## 연관 키워드

- 인덱스(Index), B+Tree, 클러스터드 인덱스, 넌클러스터드 인덱스, 결합 인덱스, 커버링 인덱스, 페이지 분할(Page Split)
- 풀 테이블 스캔(Full Table Scan), 카디널리티(Cardinality), ROWID, 비트맵 인덱스(Bitmap Index), 함수 기반 인덱스(Function-Based Index), 인덱스 재구성(REBUILD)
- 인덱스

## Ⅰ. 인덱스의 개요

- 핵심 요약 : 대규모 테이블의 검색 속도를 로그 수준으로 향상시키는 물리적 보조 자료구조 설계 체계.
- 개념 : DB(Database) 테이블의 특정 컬럼 값과 해당 레코드의 물리적 위치(ROWID 또는 기본키)를 키-값 쌍으로 매핑하여 정렬 상태로 유지하는 보조 자료구조.
- 배경 및 필요성 :
  1. 풀 테이블 스캔(Full Table Scan)의 디스크 I/O 비용 $O(n)$ 에 비한 트리 탐색 비용 $O(\log n)$ 으로의 절감 필요.
  2. 범위 검색, 다중 조건 검색, 정렬 연산의 고속화 요구.
  3. 데이터 규모 팽창에 따른 응답 지연 최소화 필요.
- 주요 목적 : 조회(SELECT) 성능 극대화와 디스크 I/O 감소, 데이터 변경(CUD) 오버헤드와의 균형 관리.

## Ⅱ. 인덱스의 특징

- 핵심 요약 : 정렬된 키-포인터 구조, 클러스터드·넌클러스터드 분류, 목적별 특수 인덱스 체계.

1. 정렬 보조 자료구조 : 키 순서로 정렬된 키-포인터 쌍의 유지와 범위 탐색 최적화.
2. 클러스터드·넌클러스터드 분류 : 물리적 데이터 정렬 여부에 따른 리프 노드 내용과 생성 개수의 차이.
3. 목적별 특수 인덱스 : 결합, 커버링, 비트맵, 함수 기반 인덱스의 용도별 특화.
4. 쓰기 오버헤드 발생 : 데이터 변경 시 트리 재정렬, 페이지 분할, 추가 공간 점유.
5. 옵티마이저 의존 : 통계 정보와 카디널리티에 따른 인덱스 선택 가능성.

## Ⅲ. 인덱스의 구조 (흐름)

- 핵심 요약 : B+Tree의 루트-브랜치-리프 3단 계층과 리프 양방향 연결, 페이지 분할의 부하 메커니즘.

```text
[ B+Tree 인덱스 구조 ]
          [루트 노드 (Root)]
                 |
          [브랜치 노드 (Branch)]
                 |
   [리프 노드] <--> [리프 노드] <--> [리프 노드]
   (키 + 데이터 포인터)   (양방향 연결 리스트, 범위 스캔 최적화)
```

```text
[ 페이지 분할 (Page Split) 흐름 ]
리프 페이지 포화 → 중간 키 삽입 → 새 페이지 할당
     → 기존 데이터의 일부 이동 → 랜덤 I/O 및 Redo 로그 다량 발생
```

## Ⅳ. 클러스터드 인덱스와 넌클러스터드 인덱스의 비교

- 핵심 요약 : 물리적 데이터 정렬 여부와 리프 노드 내용, 생성 개수와 범위 검색 성능의 차이.

| 비교 항목 | 클러스터드 인덱스 | 넌클러스터드 인덱스 |
| :--- | :--- | :--- |
| 물리적 정렬 여부 | 실제 데이터 행이 키 순서로 디스크에 정렬 | 인덱스만 정렬, 데이터 행 위치는 무작위 |
| 리프 노드 내용 | 실제 데이터 페이지 | 인덱스 키 + 클러스터드 키 또는 ROWID |
| 생성 가능 개수 | 테이블당 1개 | 테이블당 다수 |
| 범위 검색 성능 | 연속 블록 I/O로 순차 스캔 가능 | 인덱스 스캔 후 랜덤 I/O 접근 필요 |
| 쓰기 비용 | 물리적 행 재배치·페이지 분할로 높음 | 인덱스 페이지만 수정해 상대적으로 낮음 |

## Ⅴ. 인덱스의 장점과 한계

- 핵심 요약 : 조회 가속·I/O 절감의 장점과 과도한 인덱스의 쓰기 저하, 스큐, 단편화의 한계.

- 장점
  1. 풀 테이블 스캔 대비 로그 수준의 조회 성능 향상.
  2. 범위 검색과 정렬 연산의 고속화.
  3. 조인·집계 쿼리의 실행 계획 안정화.

- 한계점 1 : 과도한 인덱스 생성에 따른 쓰기 성능 저하
  - 한계점 : 조회 쿼리마다 개별 인덱스를 무분별하게 추가하면 데이터 변경 시 페이지 분할과 WAL(Write-Ahead Logging) 쓰기 오버헤드로 쓰기 처리량 급락.
  - 해결 방안 : 인덱스 머지와 결합 인덱스 통합, 카디널리티가 높은 컬럼의 선두 배치, 미사용 인덱스의 정기 삭제.
- 한계점 2 : 카디널리티 저하와 NULL 편중 시 효율 급락
  - 한계점 : 값의 종류가 적은 컬럼이나 NULL이 대량 포함된 경우 인덱스 풀 스캔 유발 및 옵티마이저의 풀 스캔 오판.
  - 해결 방안 : 부분 인덱스(Partial/Filtered Index) 생성, 함수 기반 인덱스(FBI, Function-Based Index) 활용, 통계 정보(히스토그램) 상시 수집.
- 한계점 3 : 단편화와 블로트 누적
  - 한계점 : 빈번한 삭제·수정으로 리프 노드에 빈 공간이 누적되어 디스크 낭비와 버퍼 캐시 적중률 저하.
  - 해결 방안 : 온라인 인덱스 재구성(REBUILD) 스케줄링, Fill Factor 튜닝을 통한 여유 공간 선제 확보.

## Ⅵ. 인덱스에 대한 기술사적 제언

- 핵심 요약 : 선두 컬럼 선정, 컬럼 가공 금지, 미사용 인덱스 정례 정리.
- 선두 컬럼 선정의 절대 원칙 : 결합 인덱스 설계 시 WHERE 절에서 동치 조건으로 가장 빈번히 조회되는 컬럼을 첫 선두 컬럼으로 지정하고, 범위 검색 컬럼은 후순위로 배치.
- 인덱스 컬럼 가공 금지 : 조건절에서 인덱스 컬럼을 함수·연산으로 가공하면 풀 스캔이 발생하므로 함수 기반 인덱스 생성 또는 쿼리 형태의 변경.
- 미사용 인덱스 정리 정례화 : DBMS의 동적 성능 뷰를 주기적으로 모니터링하여 조회 빈도가 0인 인덱스를 제거.
