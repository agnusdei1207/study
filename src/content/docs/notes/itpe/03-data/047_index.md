## 연관 키워드

- 인덱스, B+Tree, 클러스터드 인덱스, 넌클러스터드 인덱스, 결합 인덱스, 커버링 인덱스, 페이지 분할, 풀 테이블 스캔, 카디널리티, ROWID, 비트맵 인덱스, 함수 기반 인덱스, 인덱스 재구성

## Ⅰ. 인덱스의 개요

- 핵심 요약 : **인덱스**는 대규모 테이블의 검색 속도를 로그 수준으로 높이는 물리적 보조 자료구조.
- 개념 : 테이블 특정 컬럼의 값과 해당 레코드의 물리적 위치(**ROWID** 또는 기본키)를 키-값 쌍으로 묶어 정렬 상태로 유지하는 보조 자료구조.
- 배경 및 필요성 :
  1. **풀 테이블 스캔** (Full Table Scan)의 디스크 입출력(I/O, Input/Output) 비용 $O(n)$을 트리 탐색 비용 $O(\log n)$ 수준으로 줄일 필요.
  2. 범위 검색, 다중 조건 검색, 정렬 연산의 고속화 요구.
  3. 데이터 규모 팽창에 따른 응답 지연 최소화 필요.
- 주요 목적 : 조회 성능을 극대화하고 디스크 I/O를 줄이되, 데이터 변경(CUD, Create·Update·Delete) 오버헤드와의 균형 관리.

## Ⅱ. 인덱스의 특징 및 장점

- 핵심 요약 : 정렬된 키-포인터 구조 위에 클러스터드·넌클러스터드 분류와 목적별 특수 인덱스가 얹힌 체계.

1. 정렬 보조 자료구조 : 키 순서로 정렬된 키-포인터 쌍을 유지 → 범위 탐색 최적화.
2. **클러스터드 인덱스**와 **넌클러스터드 인덱스** : 데이터 행의 물리적 정렬 여부에 따라 리프 노드 내용과 생성 개수가 달라짐 → 용도에 맞춘 선택 가능.
3. 목적별 특수 인덱스 : **결합 인덱스**, **커버링 인덱스**, **비트맵 인덱스**, **함수 기반 인덱스**가 용도별로 특화 → 쿼리 형태에 맞춘 조회 최적화.
4. 쓰기 오버헤드 발생 : 데이터 변경 시 트리 재정렬, **페이지 분할** (Page Split), 추가 공간 점유 → 쓰기 성능 저하 요인.
5. 옵티마이저 의존 : 통계 정보와 **카디널리티** (Cardinality, 컬럼 값의 서로 다른 개수)에 따라 인덱스 선택 여부가 달라짐.

## Ⅲ. 인덱스의 구조 (흐름)

- 핵심 요약 : 루트·브랜치·리프 3단 계층과 리프 양방향 연결로 범위 탐색을 돕는 **B+Tree** 구조와 페이지 분할의 부하 메커니즘.
- 리프 노드는 키와 데이터 포인터를 담고 양방향으로 연결되어 범위 스캔을 최적화한다.

```text
[B+Tree 인덱스 구조]
[루트 노드]
     ↓
[브랜치 노드]
     ↓
[리프 노드] ↔ [리프 노드] ↔ [리프 노드]
```

```text
[페이지 분할 흐름]
리프 페이지 포화
     ↓
중간 키 삽입 → 새 페이지 할당
     ↓
기존 데이터 일부 이동
     ↓
랜덤 I/O와 Redo 로그 다량 발생
```

## Ⅳ. 클러스터드 인덱스와 넌클러스터드 인덱스의 비교

- 핵심 요약 : 물리적 데이터 정렬 여부에 따라 리프 노드 내용, 생성 개수, 범위 검색 성능이 달라짐.

| 비교 항목 | 클러스터드 인덱스 | 넌클러스터드 인덱스 |
| --- | --- | --- |
| 물리적 정렬 여부 | 실제 데이터 행이 키 순서로 디스크에 정렬 | 인덱스만 정렬, 데이터 행 위치는 무작위 |
| 리프 노드 내용 | 실제 데이터 페이지 | 인덱스 키 + 클러스터드 키 또는 ROWID |
| 생성 가능 개수 | 테이블당 1개 | 테이블당 다수 |
| 범위 검색 성능 | 연속 블록 I/O로 순차 스캔 가능 | 인덱스 스캔 후 랜덤 I/O 접근 필요 |
| 쓰기 비용 | 물리적 행 재배치·페이지 분할로 높음 | 인덱스 페이지만 수정해 상대적으로 낮음 |

## Ⅴ. 인덱스의 한계와 방안

- 핵심 요약 : 조회 가속과 I/O 절감의 장점 이면에 과도한 인덱스의 쓰기 저하, 카디널리티 저하, 단편화라는 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 쓰기 성능 저하 | 조회마다 인덱스를 무분별히 추가 → 변경 시 페이지 분할과 WAL (Write-Ahead Logging) 부담 | 인덱스 머지와 결합 인덱스 통합, 카디널리티가 높은 컬럼 선두 배치, 미사용 인덱스 삭제 | 쓰기 처리량, 미사용 인덱스 수 |
| 카디널리티 저하·NULL 편중 | 값 종류가 적거나 NULL이 많으면 풀 스캔 유발과 옵티마이저 오판 | 부분 인덱스(Partial Index) 생성, 함수 기반 인덱스 활용, 히스토그램 상시 수집 | 실행 계획 변화 |
| 단편화·블로트 누적 | 삭제·수정이 누적되어 리프에 빈 공간 축적 → 디스크 낭비, 버퍼 캐시 적중률 저하 | **인덱스 재구성** (REBUILD) 스케줄링, Fill Factor 튜닝으로 여유 공간 확보 | 단편화율, 버퍼 캐시 적중률 |

## Ⅵ. 인덱스에 대한 기술사적 제언

- 핵심 요약 : 선두 컬럼 선정, 인덱스 컬럼 가공 금지, 미사용 인덱스 정례 정리의 세 원칙으로 인덱스를 설계하고 관리.
- 결합 인덱스를 설계할 때는 WHERE 절에서 동치 조건으로 가장 자주 쓰이는 컬럼을 선두에 두고, 범위 검색 컬럼은 뒤에 배치하는 것이 바람직하다.
- 조건절에서 인덱스 컬럼을 함수나 연산으로 가공하면 풀 스캔이 발생하므로, 함수 기반 인덱스를 만들거나 쿼리 형태를 바꾼다.
- DBMS의 사용 통계 뷰를 주기적으로 점검해 조회 빈도가 0인 인덱스를 제거하는 절차를 정례화한다.

## Ⅶ. 결론

- 핵심 요약 : 인덱스는 조회 성능과 쓰기 비용의 균형을 지키는 물리적 설계 요소.
- 시사점 : 질의 패턴과 데이터 분포를 반영한 선별적 인덱스 설계와 주기적 정리가 필요.
