- 메커니즘: 데이터·처리특성·서비스 수준·운영역량을 요구사항과 대조하고 검증
- 통찰: 한계: 기능표·벤치마크 숫자만 보면 실제 데이터·동시성·운영 인력비가 빠짐 → 방안: 업무 시나리오 PoC와 성능·비용·보안·운영성의 사전 합의 기준으로 비교

<details>
<summary>핵심 용어</summary>

- **서비스 수준 목표(Service Level Objective, SLO)** : 서비스가 충족해야 할 측정 가능한 신뢰성·성능 목표
- **총소유비용(Total Cost of Ownership, TCO)** : 도입·운영·인력·이관 등 수명주기 비용의 합
- **개념검증(Proof of Concept, PoC)** : 핵심 기술 위험과 요구 적합성을 제한된 범위에서 검증하는 활동

</details>

## 2~4교시 25점 답안

## Ⅰ. 빅데이터 분석도구 선정의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **빅데이터 분석도구 선정** 은 업무 요구와 데이터·운영 조건에 맞는 분석 도구를 평가·선정하는 의사결정 |
| 목적 | 요구 성능과 분석 활용을 달성하면서 비용·운영 위험을 관리 |

## Ⅱ. 분석도구 선정의 특징

| 특징 | 선택상 의미 |
|---|---|
| 워크로드 우선 | 제품 이름보다 배치·스트림·대화형 질의의 실제 부하와 지연 요구를 먼저 정의 |
| 동일 조건 비교 | 대표 데이터·동시성·장애 시나리오를 같은 조건으로 후보에 적용 |
| 수명주기 비용 | 도입가뿐 아니라 운영 인력·저장·컴퓨팅·이관 비용을 함께 평가 |

## Ⅲ. 요구 정의·후보 평가 체계와 PoC 검증 프로세스

```text
업무·데이터·SLO·보안 요구 → 평가축·가중치 합의
                                 ↓
처리 유형별 후보 선정 → 대표 워크로드 PoC
                                 ↓
성능·정확성·운영·TCO 비교 → 선정·예외 기록
                                 ↓
운영 지표와 초기 가정 비교·재평가
```

### 대표 워크로드 PoC의 하위 검증

```text
실제 형식·규모의 입력 데이터 + 대표 질의·동시 사용자
                        ↓
                같은 환경에서 후보별 실행
                        ↓
정확성·지연·처리량·장애 복구·자원 사용 기록
                        ↓
      운영 인력·인프라 비용과 SLO 충족 여부 비교
```

PoC에서 실패·재처리와 운영자 개입까지 기록해야 벤치마크 숫자와 실제 유지 비용의 차이가 드러난다.

## Ⅳ. 워크로드별 도구 유형과 평가축 비교

| 워크로드 요구 | 우선 검토할 도구 유형 | 주요 검증점 |
|---|---|---|
| 지속 유입 이벤트 처리 | 스트림 처리 엔진 | 상태·체크포인트·지연·재처리 |
| 대용량 변환·모델 학습 | 분산 배치 처리 엔진 | 셔플·메모리·확장·작업 재시작 |
| 여러 저장소의 탐색 질의 | 분산 SQL·연합 질의 엔진 | 커넥터 기능·푸시다운·원천 부하 |
| 제한된 규모의 대화형 분석 | 단일 노드 분석 엔진·노트북 도구 | 메모리 한계·동시 사용자·재현성 |

도구 유형은 초기 후보군이며 실제 처리량·지연 성능을 고정값으로 보장하지 않으므로, 데이터와 구성에 맞춘 검증 필요.

### 공통 평가축

| 평가축 | 확인 항목 | 근거 자료 |
|---|---|---|
| 워크로드·데이터 | 배치·스트림·SQL·학습, 규모·형식·유입률 | 대표 업무·데이터 |
| 서비스 품질 | 지연·처리량·가용성·복구 | SLO·부하 패턴 |
| 운영·보안 | 권한·감사·연계·기술지원·운영역량 | 운영 요구사항 |
| 비용·종속성 | 라이선스·컴퓨팅·저장·인력·이관비 | 수명주기 TCO |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 기능표·벤치마크 숫자만 보면 실제 데이터·동시성·운영 인력비가 빠짐 | 업무 시나리오 PoC와 성능·비용·보안·운영성의 사전 합의 기준으로 비교 |
| 처리량만 평가해 장애 복구·재처리 실패를 놓침 | 오류·재시작 시나리오를 PoC에 포함하고 복구시간·누락 확인 |
| 도입 뒤 데이터·워크로드 변화를 반영하지 못함 | 운영 SLO·비용 추이를 기준선과 비교해 도구 구성 재평가 |

## Ⅵ. 제언

기능표·벤치마크 숫자만으로는 실제 부하와 운영비를 알 수 없다. 먼저 대표 데이터·질의·동시성·장애 시나리오를 고정하고 후보별 정확성·지연·복구·TCO를 같은 기준으로 비교해 선정한다.

## 출제 이력과 검증 출처

- [Apache Spark Structured Streaming](https://spark.apache.org/streaming/): 배치·스트림 API 통합과 체크포인트 등 처리 특성. 도구 선택 시 워크로드별 검증 근거

- 분석도구의 성능은 제품 버전, 구성, 데이터, 워크로드에 따라 달라지므로 고정 지연시간·데이터 용량 기준은 제시하지 않음.
