## 핵심 용어
- TCO(Total Cost of Ownership): 초기 소프트웨어 라이선스 비용뿐만 아니라 클러스터 인프라 비용, 네트워크 전송료, 엔지니어 채용 및 학습 비용, 장애 대응 유지보수 비용을 총합한 총소유비용
- PoC(Proof of Concept): 본격 도입 전 실제 운영 데이터를 모사한 테스트베드에서 도구의 처리량, 지연시간, 장애 복구력을 실측 검증하는 사전 기술 검증

## 핵심 통찰
- "가장 유명한 도구가 가장 좋은 도구"라는 생각은 빅데이터에서 가장 위험한 착각임 → 데이터가 10GB 미만인데 하둡이나 스파크 클러스터를 띄우면 JVM 오버헤드 때문에 파이썬 Pandas나 단일 PostgreSQL보다 10배 더 느림
- 분석 도구 선택의 제1 분기점은 '지연시간 요구사항'임 → 결과가 1초 안에 나와야 하는 부정거래탐지(FDS)는 Flink를 써야 하고, 내일 아침 9시까지 나오면 되는 일간 리포트는 Spark 배치를 쓰는 것이 정답
- 클라우드 서버리스 도구(BigQuery, Athena)는 서버 관리가 필요 없어 편하지만, 파티셔닝 없이 풀스캔 쿼리를 반복 날리면 하룻밤 사이에 수천만 원의 과금 폭탄을 맞을 수 있음

## 이웃 토픽과 구분
- 분산 연산 엔진(Spark) vs 분산 쿼리 엔진(Trino): Spark = 복잡한 다단계 데이터 변환(ETL)과 머신러닝 등 긴 배치 작업(Long-running)에 최적화 / Trino = 저장소 없이 오직 메모리 위에서 빠른 SQL 조회(Interactive Query)에 최적화

## 문제·원인·대책
- 적용 상황: 신규 이커머스 스타트업의 전사 로그 분석 플랫폼 도구 선정
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 야간 배치 집계용으로 구축한 Spark 클러스터의 유휴 자원 낭비로 월 인프라 비용 폭증 | 상시 24시간 가동형 EMR 클러스터 프로비저닝 | 사용 시점에만 컨테이너가 뜨는 서버리스(Serverless EMR/BigQuery) 전환 | 인프라 비용 75% 절감 |
| 실시간 이상 징후 탐지 시스템에 Spark Micro-batch 적용 시 10초 지연 발생 | 마이크로 배치 방식의 근본적인 주기성 윈도우 한계 | 진정한 이벤트 단위 스트리밍 처리를 지원하는 Apache Flink로 교체 | 탐지 지연시간 10초에서 200ms로 단축 |
