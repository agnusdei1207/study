## 30초 인출

- 본질: NoSQL은 관계형 테이블 대신 키-값·문서·컬럼 패밀리·그래프 같은 모델로 대규모 데이터를 분산 저장하는 데이터베이스 계열
- 메커니즘: 조회 방식(접근 패턴)에 맞춰 데이터를 함께 읽는 단위로 묶어 저장하고 샤딩과 복제로 노드를 늘려 확장
- 통찰: NoSQL은 조인을 쓰지 않고 저장 구조가 조회에 맞춰져 있어 나중에 조회 방식이 바뀌면 재설계 비용이 크므로 데이터가 아닌 조회 패턴에서 출발해 모델링

<details>
<summary>핵심 용어</summary>

- **NoSQL(Not Only SQL)** : 관계형 테이블 이외의 모델로 데이터를 저장하는 데이터베이스 계열
- **키-값(Key-Value)** : 고유한 키로 값을 바로 조회하는 모델
- **문서(Document)** : JSON 같은 문서 단위로 속성을 묶어 저장하는 모델
- **컬럼 패밀리(Column Family)** : 행 키와 컬럼 묶음 단위로 저장하는 모델
- **그래프(Graph)** : 노드와 간선으로 개체와 관계를 저장하는 모델
- **BASE** : 기본적 가용성, 소프트 상태, 최종 일관성을 지향하는 성질
- **샤딩(Sharding)** : 데이터를 키 기준으로 여러 노드에 나누어 저장하는 방식
- **복제(Replication)** : 같은 데이터의 사본을 여러 노드에 두는 방식

</details>

## 2~4교시 25점 답안

## Ⅰ. NoSQL의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **NoSQL** 은 키·문서·컬럼 패밀리·그래프 등 관계형 테이블 이외의 모델로 데이터를 저장하는 데이터베이스 계열 |
| 목적 | 대규모 데이터의 분산 저장과 유연한 스키마 운영 |

## Ⅱ. 관계형 데이터베이스와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 유연한 스키마 | 문서·행마다 구조가 달라도 저장 |
| 접근 패턴 중심 | 함께 읽는 데이터를 한 단위로 저장 |
| 수평 확장 | 샤딩·복제로 노드 추가 |
| 일관성 선택 | 강한 일관성부터 최종 일관성까지 설정 |

## Ⅲ. 유형과 모델링 절차

### NoSQL의 네 가지 유형

```text
[키-값]        [문서]          [컬럼 패밀리]     [그래프]
 key → value   {id, 속성...}   행키 │ 컬럼묶음    ●──●
 세션·캐시     주문·상품       로그·시계열        │╲ │  관계 순회
                                                  ●──●
```

### 모델링 절차

```text
조회·갱신 패턴 정리
      ↓
유형 선택
      ↓
키·문서 구조 설계 (함께 읽는 데이터는 한 단위로)
      ↓
샤드 키 설계 → 조회 성능 검증
```

## Ⅳ. 유형별 비교

| 유형 | 조회 방식 | 적합 대상 | 대표 예 |
|---|---|---|---|
| 키-값 | 키로 직접 조회 | 세션·캐시 | Redis |
| 문서 | 문서 내부 속성으로 조회 | 주문·상품 카탈로그 | MongoDB |
| 컬럼 패밀리 | 행 키와 컬럼 묶음 조회 | 대용량 로그·시계열 | Cassandra, HBase |
| 그래프 | 관계를 따라 순회 | 추천·사기 탐지 | Neo4j |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 조회 방식이 바뀌면 저장 구조 재설계 | 접근 패턴을 먼저 정리하고 변경 가능성이 큰 조회는 별도 사본으로 대응 |
| 조인·다중 문서 트랜잭션의 제약 | 함께 갱신하는 데이터를 한 문서에 묶고 필요 시 보상 처리 |
| 샤드 키 편중으로 특정 노드에 부하 집중 | 값이 고르게 분포하는 샤드 키 선택 |

## Ⅵ. 제언

데이터 구조가 아니라 조회·갱신 패턴을 먼저 정리한 뒤 그에 맞는 유형과 키를 정해 모델링

```text
질의 목록 작성 → 질의별 필요한 필드·키 도출 → 유형·문서 구조 결정
```

| 구분 | 데이터 구조 중심 | 제언: 접근 패턴 중심 |
|---|---|---|
| 설계 출발점 | 엔티티와 관계 | 질의 목록 |
| 조회 성능 | 조인·재구성 필요 | 질의에 맞춰 저장 |
| 변경 대응 | 스키마 변경 | 질의 변경 시 재설계 필요 |
