## 30초 인출



- 본질: **빅데이터는 규모·생성 속도·형태가 기존 처리 방식의 한계를 넘는 데이터를 분산 기술과 적절한 분석 방법으로 다루는 접근**
- 메커니즘: 데이터의 규모·속도·형식 요구를 확인해 수집·저장·처리·분석 구조를 구성하고 품질·접근을 관리
- 통찰: Volume·Velocity·Variety의 3V를 넘어 Veracity(정확성)와 Value(가치)를 창출하기 위해 분산 병렬 스토리지와 실시간 스트리밍 결합 아키텍처 구축 필수
<details><summary>핵심 용어</summary>

- **빅데이터 (Big Data)** : 기존 처리 방식으로 비용·시간·품질 요구를 충족하기 어려운 규모·속도·다양성의 데이터를 다루는 접근.
- **5V** : Volume·Velocity·Variety·Veracity·Value로 데이터의 규모·속도·다양성·신뢰성·가치를 살피는 특성 묶음.
- **Schema-on-Write** : 데이터를 저장하기 전에 스키마를 적용해 구조를 맞추는 방식.
- **Schema-on-Read** : 저장 시 원천 형식을 유지하고 읽을 때 해석할 스키마를 적용하는 방식.
- **Lambda Architecture** : 배치 처리와 스트림 처리를 분리해 결과를 결합하는 데이터 처리 아키텍처.
- **Kappa Architecture** : 스트림 처리 경로를 중심으로 데이터를 처리하고 재생해 과거 자료를 재계산하는 아키텍처.

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|:---|:---|
| 정의 | 빅데이터는 기존 처리 방식으로 비용·시간·품질 요구를 충족하기 어려운 규모·속도·다양성의 데이터를 다루는 접근 |
| 목적 | 업무 요구에 맞는 수집·저장·처리·분석으로 데이터 활용 가치와 품질 관리 지원 |

## Ⅱ. 규모·속도·다양성·신뢰성·가치의 특징

| 특성 | 설계에 미치는 영향 |
|---|---|
| Volume·Velocity | 저장·처리 용량과 유입 지연 목표를 함께 정함 |
| Variety | 정형·반정형·비정형의 형식과 해석 시점을 구분 |
| Veracity | 출처·품질·편향을 확인해 분석 결과의 신뢰성 관리 |
| Value | 처리량보다 실제 업무 의사결정·서비스 효과로 성과 판단 |

## Ⅲ. 수집·저장·처리·서빙과 거버넌스 체계

```text
업무 목적·보존 기준
   ↓
원천 DB·로그·센서 → 배치/스트림 수집 → 원천 저장
                                         ↓ 품질·형식 변환
                              분산 배치/스트림 처리
                                         ↓
                               분석·모델·서비스 제공
출처·계보·접근권한·품질 관측 ─── 전 단계에 적용
```

| 단계 | 역할 |
|:---|:---|
| 수집·저장 | 다양한 원천 데이터를 배치·스트림으로 적재하고 보존 |
| 처리·활용 | 품질·변환·분석을 수행해 서비스와 사용자에게 제공 |

## Ⅳ. 람다·카파와 DW·레이크 구조 비교

### 실시간 빅데이터 스트리밍 아키텍처: 람다 vs 카파

#### 한줄 요약: 배치와 스트림을 분리하는 람다(Lambda)와 단일 스트림 파이프라인으로 통합한 카파(Kappa)의 비교

| 비교 항목 | 람다 아키텍처 (Lambda) | 카파 아키텍처 (Kappa) |
|:---|:---|:---|
| **설계 철학** | 실시간 레이어와 배치 레이어를 분리 | 이벤트 재생이 가능한 스트림 처리 경로 중심 |
| **코드베이스** | 두 경로의 비즈니스 로직을 일치시켜야 함 | 같은 처리 경로에서 재처리를 지원하도록 설계 |
| **과거 데이터 재처리** | 보존한 원천을 배치로 다시 처리 | 보존·재생 가능한 이벤트를 같은 처리 경로로 다시 읽음 |
| **시스템 복잡도** | 두 경로의 결과 병합·정합성 관리 필요 | 이벤트 보존·재생과 상태 관리 필요 |
| **적용 제약** | 배치와 저지연 처리 요구가 함께 있는 경우 | 재생 가능한 이벤트 보존 기간과 순서·중복 처리 설계 필요 |

### 전통적 데이터 웨어하우스(DW) vs 빅데이터 플랫폼

#### 한줄 요약: 스키마 온 라이트의 정형 DW와 스키마 온 리드의 비정형 빅데이터 레이크의 대조

| 비교 항목 | 전통적 데이터 웨어하우스 (DW) | 빅데이터 플랫폼 (Data Lake / Lakehouse) |
|:---|:---|:---|
| **데이터 형태** | 정형 분석·보고에 최적화된 관리 모델이 일반적 | 정형·반정형·비정형 원천의 보존·탐색을 폭넓게 지원 |
| **스키마 시점** | 적재 전 스키마를 적용하는 설계가 일반적 | 원천 보존 후 읽을 때 해석 가능; 레이크하우스는 쓰기 시 제약도 적용 가능 |
| **스토리지 비용** | 제품·구성·보존 기간에 따라 달라지는 저장 비용 | 저장과 계산 분리 여부, 데이터 이동·질의 비용을 함께 고려 |
| **확장성** | 병렬 DW와 클라우드 DW도 수평 확장 가능 | 분산 처리 가능하나 데이터 편향·네트워크·메타데이터가 확장 효율을 제한 |
| **주요 사용자** | 정형 분석·보고 중심 사용자 | 원천 데이터 탐색·분석·학습 중심 사용자; 실제 사용자 범위는 겹칠 수 있음 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 출처·품질·접근 책임이 없으면 데이터가 쌓여도 재현·활용이 어려움 | 업무 목적·보유기간·품질 규칙·접근 통제를 파이프라인에 포함 |
| 배치·스트림 이중 경로의 집계 기준이 달라 결과 불일치 | 공통 이벤트 정의·검증 기준을 두고 병합 결과를 대조 |
| 원천을 무제한 적재해 저장·질의 비용 증가 | 활용 목적·보존 기간·접근 빈도에 따라 계층화·폐기 |

## Ⅵ. 제언

원천 데이터의 계보와 신뢰성을 보장하는 데이터 레이크하우스를 구축하고 도메인별 데이터 메시(Data Mesh) 거버넌스를 통해 분석 ROI 극대화.

### 빅데이터 5V 기반 수집-저장-처리-분석 파이프라인

```text
[원천 데이터 (다양성 Variety)] ──► [실시간/배치 수집 (속도 Velocity)]
                                       │
                                       ▼
[분산 스토리지 (규모 Volume)] : 오브젝트 스토리지 + 오픈 테이블 포맷
                                       │
                                       ▼
[데이터 품질 검증 (정확성 Veracity)] ──► 비즈니스 모델링 (가치 Value 창출)
```

### 선택 근거: 제언: 현대적 빅데이터 플랫폼 (5V)

| 구분 | 전통적 DW (3V 이전) | 제언: 현대적 빅데이터 플랫폼 (5V) |
|---|---|---|
| 데이터 형태 | 정형 관계형 데이터 한정 | 정형, 반정형(JSON), 비정형(텍스트/영상) 전 수용 |
| 처리 구조 | 수직 스케일업 및 정기 야간 배치 | 수평 스케일아웃 및 실시간 스트림/배치 하이브리드 |
| 가치 창출 | 사후 실적 보고 중심 | 실시간 이상 탐지, 추천, AI 예측 모델 서빙 |
