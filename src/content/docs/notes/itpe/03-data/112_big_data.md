## 연관 키워드

- 빅데이터(Big Data), 5V, 람다 아키텍처(Lambda Architecture), 카파 아키텍처(Kappa Architecture)
- 데이터 레이크(Data Lake), 데이터 늪(Data Swamp), 레이크하우스(Lakehouse), 오픈 테이블 포맷
- ACID, 데이터 카탈로그, FinOps, TCO

## Ⅰ. 빅데이터의 개요

- 핵심 요약 : 전통적 처리 용량을 넘는 대규모·고속·다양한 데이터를 수집·저장·분석해 가치를 창출하는 기술 체계.
- 개념 : 관계형 데이터베이스 관리 시스템(RDBMS, Relational Database Management System)이나 단일 서버의 처리 용량을 넘는 규모와 속도로 생성되며, 정형·반정형·비정형 형태가 섞인 데이터 집합을 **빅데이터**(Big Data)라 하고, 이를 수집·저장·관리·분석하는 제반 정보기술을 포함한다.
- 배경 및 필요성 : 센서, 로그, 클릭스트림 같은 데이터 유입이 폭증하면서 단일 서버를 키우는 수직 확장(Scale-Up) 방식은 비용이 빠르게 커진다. 이에 따라 여러 서버에 나누어 저장하고 병렬로 처리하는 수평 확장 구조가 필요해졌고, 비정형 데이터의 활용 가치와 예측 분석 수요도 함께 커졌다.
- 주요 목적 : 분산 저장, 병렬 처리, 실시간 분석을 통해 비즈니스 가치를 창출.

## Ⅱ. 빅데이터의 특징

- 핵심 요약 : 규모, 속도, 다양성, 정확성, 가치의 5V 특성이 분산 처리 기반 위에서 함께 다뤄지는 데이터 체계.

1. **규모**(Volume) : 테라바이트(TB)에서 페타바이트(PB), 제타바이트(ZB)로 커지는 데이터 양 → 분산 저장 구조 필요.
2. **속도**(Velocity) : 센서, 금융 거래, 클릭스트림처럼 실시간으로 쏟아지는 데이터 → 스트림 처리 필요.
3. **다양성**(Variety) : JSON(JavaScript Object Notation), XML(Extensible Markup Language), 로그, 음성, 영상 등 비정형 데이터 확산 → 스키마에 덜 의존하는 저장 방식 필요.
4. **정확성**(Veracity) : 노이즈, 결측치, 편향이 섞인 데이터에서 신뢰할 수 있는 품질 확보 → 정제와 품질 검증 절차 필요.
5. **가치**(Value) : 방대한 데이터를 처리해 투자 대비 수익을 만드는 것이 목표 → ROI(Return on Investment, 투자 대비 수익) 관점의 관리 필요.

## Ⅲ. 빅데이터의 구조 (흐름)

- 핵심 요약 : 배치 계층과 속도 계층을 둘로 나누는 **람다 아키텍처**(Lambda Architecture)와, 모든 처리를 단일 스트림으로 통합하는 **카파 아키텍처**(Kappa Architecture)의 두 구조.

```text
[ 람다 아키텍처 ]

      [모든 데이터 유입]
        ↓             ↓
[배치 계층]        [속도 계층]
 정확한 집계        실시간 근사 집계
        ↓             ↓
      [서빙 계층]
  두 결과를 통합 조회
```

```text
[ 카파 아키텍처 ]

[모든 데이터 유입]
         ↓
[분산 로그 스트림 (Apache Kafka)]
         ↓
[단일 스트림 엔진 (Apache Flink)]
         ↓
[서빙 DB]
```

카파 아키텍처에서 과거 데이터를 다시 처리해야 하면 스트림의 읽기 위치를 과거로 되돌려 같은 코드로 결과를 다시 만든다.

## Ⅳ. 람다 아키텍처와 카파 아키텍처의 비교

- 핵심 요약 : 정확성과 실시간성을 이원으로 나누는 람다 아키텍처와 단일 스트림으로 통합하는 카파 아키텍처의 설계 철학과 복잡도 차이.

| 비교 기준 | 람다 아키텍처 (Lambda Architecture) | 카파 아키텍처 (Kappa Architecture) |
| --- | --- | --- |
| 설계 철학 | 정확성은 배치로, 실시간성은 스트림으로 이원 분리 | 모든 데이터를 스트림으로 보는 단일화 |
| 코드 구성 | 배치용 코드와 스트림용 코드를 각각 작성하고 유지 | 단일 처리 코드로 실시간과 재처리를 수행 |
| 시스템 복잡도 | 두 계층의 결과를 병합하므로 높음 | 구조가 단순해 운영 관리가 쉬움 |
| 과거 재처리 | 배치 계층을 다시 수행해 정확하게 재계산 | 스트림 위치를 되돌려 같은 코드로 재생산 |
| 적합 환경 | 정확한 배치 집계와 실시간 근사가 함께 필요한 환경 | 처리 로직 단일화와 단순 운영이 우선인 환경 |

## Ⅴ. 빅데이터의 한계와 방안

- 핵심 요약 : 데이터 늪, 코드 이중화, 플랫폼 비용 증가의 한계를 테이블 포맷과 아키텍처 단일화, 비용 관제로 대응.
- 장점 : 분산 저장과 병렬 처리로 확장성을 확보하고, 스트림 분석으로 즉각적인 의사결정을 지원하며, 비정형 데이터에서 새로운 인사이트를 얻을 수 있다.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **데이터 늪**(Data Swamp) 전락 | 메타데이터 없이 정제되지 않은 원천 데이터가 쌓여 유효성, 계보(Lineage), 소유권 파악이 불가능 | Apache Iceberg, Delta Lake 같은 오픈 테이블 포맷의 ACID(Atomicity, Consistency, Isolation, Durability) 트랜잭션과 스키마 강제, 데이터 카탈로그 자동 등록 | 카탈로그 등록률 |
| 람다 아키텍처의 코드 이중화 | 같은 비즈니스 로직을 두 계층에 구현해 결과가 어긋나고 디버깅이 어려움 | Kafka와 Flink 기반 카파 아키텍처로 단일화, 또는 Spark Structured Streaming 같은 단일 엔진 사용 | 로직 불일치 건수 |
| 클라우드 자원 비효율 | 유휴 클러스터 방치와 셔플, 파티셔닝 전략 부재로 **총소유비용**(TCO, Total Cost of Ownership)이 통제되지 않음 | 컴퓨팅과 스토리지 분리, 스팟 인스턴스 기반 오토스케일링, FinOps 도구로 쿼리별 비용 추적 | 쿼리당 비용, 유휴 자원 비율 |

## Ⅵ. 빅데이터에 대한 기술사적 제언

- 핵심 요약 : 레이크하우스 구조를 기본으로 채택하고, 데이터 거버넌스와 비용 관리를 설계 단계부터 함께 내재화하는 것이 필요.

저장 계층은 클라우드 객체 스토리지 위에 **레이크하우스**(Lakehouse, **데이터 레이크**(Data Lake)의 저장 유연성과 데이터 웨어하우스의 트랜잭션 기능을 결합한 구조)를 두고, 오픈 테이블 포맷으로 ACID 트랜잭션과 분석 성능을 함께 확보하는 방향이 바람직하다. 접근 통제는 Apache Ranger나 AWS Lake Formation처럼 테이블, 행, 열 단위로 정책을 거는 도구를 초기 아키텍처에 반영해야 개인정보와 기밀 데이터가 뒤늦게 노출되는 일을 막을 수 있다. 비용은 쿼리별 추적과 컴퓨팅·스토리지 분리 구조를 상시 운영하며 관리하는 것이 필요하다.

## Ⅶ. 결론

- 핵심 요약 : 5V 특성에 맞춘 분산 처리와 레이크하우스 구조의 결합이 빅데이터 가치 창출의 기반.
- 시사점 : 오픈 테이블 포맷과 거버넌스, 비용 관리를 플랫폼에 내재화하는 수준이 빅데이터 플랫폼의 신뢰성과 효율을 좌우한다.
