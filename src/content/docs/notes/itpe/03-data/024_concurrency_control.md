## 답안 골격
```text
[병행제어] ◀━━ 머리: Ⅶ 내 의견 (락 기반 대기 병목 탈피 → MVCC 기반 스냅샷 격리 및 낙관적 충돌 감지 결합)
 ┃
 ┣━ Ⅰ 개요 ───── 다중 사용자 트랜잭션 동시 실행 환경 → 데이터베이스 일관성을 유지하기 위한 상호 배제 통제
 ┣━ Ⅱ 특징 ───── 직렬 가능성(Serializability) 보장 · 격리성 유지 · 동시 처리량(TPS) 향상
 ┣━ Ⅲ 구조 ───── 병행 미통제 이상현상 4가지 / 제어 기법 4가지 (로킹·타임스탬프·낙관적·다중버전)
 ┣━ Ⅳ 흐름 ───── ① 트랜잭션 판독/기록 요청 → ② 직렬성 검증 메커니즘 통과 → ③ 데이터 접근 → ④ 원자적 반영
 ┣━ Ⅴ 비교 ───── 병행 미제어 시 4대 이상현상 (갱신손실 vs 모순성 vs 연쇄복귀 vs 비완료의존성)
 ┗━ Ⅵ 실무 ───── 교착상태(Deadlock) 발생 / 락 세분도(Granularity) 설정 오류 / 장기 트랜잭션 블로킹
```
- 필수 키워드: 병행제어 · 직렬 스케줄 · 갱신 손실(Lost Update) · 모순성(Inconsistency) · 연쇄 복귀(Cascading Rollback) · 2PL · 락 세분도
- 기출: 130회 1교시 2번 `데이터베이스 병행 제어 기법 및 필요성` → Ⅰ 필요성 + Ⅲ 기법 / 128회 4교시 5번 `데이터베이스의 병행제어` → 직렬성 검증 및 2PL

## 한 줄 본질
- 여러 트랜잭션이 동시에 동일 데이터에 접근할 때 생기는 덮어쓰기·불일치 왜곡 → 직렬 스케줄과 동일한 실행 순서를 강제하여 일관성을 보존 → 시스템 동시성과 무결성 양립 / 락 대기 지연과 교착상태 오버헤드 수반

## 핵심 그림
```text
[병행 미제어 시 발생하는 4대 문제점]

 1. 갱신 손실 (Lost Update)       2. 현상 분석 (Inconsistency, 모순성)
    T1: X=100 읽음                   T1: X, Y 읽어 합계 계산 중
    T2: X=100 읽음                   T2: X에서 Y로 50 이체 후 커밋
    T1: X=150 기록 (커밋)            T1: 변경 전 X와 변경 후 Y를 읽어
    T2: X=120 기록 (T1 갱신 덮어씀)       불일치된 합계 도출 (모순 발생)

 3. 연쇄 복귀 (Cascading Rollback) 4. 비완료 의존성 (Dirty Read)
    T1이 갱신한 미커밋 데이터를        T1이 갱신 후 롤백했는데,
    T2가 읽고 작업하던 중            T2가 그 취소된 값을 그대로
    T1 롤백 시 T2도 연쇄 취소 불가피   읽어버려 잘못된 결과 도출
```

## 핵심 용어
- 직렬 가능성(Serializability): 비직렬 스케줄(동시 실행)의 결과가 어떤 직렬 스케줄(하나씩 순차 실행)의 결과와 항상 같음을 보장하는 성질
- 락 세분도(Lock Granularity): 락을 거는 대상 단위의 크기(데이터베이스 > 테이블 > 블록 > 행 > 컬럼)로, 클수록 관리는 쉬우나 동시성은 저하

## 핵심 통찰
- 병행제어의 출발점은 '이상현상 차단'임 → 갱신 손실, 모순성, 연쇄 복구, 비완료 의존성 4가지를 막기 위해 DBMS가 트랜잭션 간 실행 순서를 개입
- 락의 크기(세분도)는 동시성과 트레이드오프 관계임 → 테이블 락은 락 관리는 간단하지만 동시 실행 트랜잭션 수가 급감하고, 행(Row) 락은 동시성은 극대화되나 락 테이블 메모리 오버헤드와 락 에스컬레이션(Escalation) 유발
- 현대 웹 서비스에서는 락에 의한 블로킹을 피하기 위해 읽기 작업에는 락을 걸지 않는 MVCC 스냅샷 읽기를 기본으로 하고, 갱신 시점에만 행 레벨 충돌을 검사

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 직렬화 그래프 (Precedence Graph) | 직렬 가능성 판정 도구 | 트랜잭션 간 선행 관계를 유향 그래프로 그려 사이클(Cycle)이 없으면 직렬 가능 판정 |
| 락 에스컬레이션 | 락 관리 메커니즘 | 다수의 행(Row) 락이 메모리 한도를 넘으면 DBMS가 상위 테이블 락으로 강제 승격 |

## 이웃 토픽과 구분
- 병행제어 vs 회복(Recovery): 병행제어 = 트랜잭션들이 '동시에' 돌 때 상호 간섭을 막는 기술 / 회복 = 시스템 장애(Crash) 시 '원자성·영속성'을 되살리는 기술

## 문제·원인·대책
- 적용 상황: 은행 계좌 이체 및 금융 원장 트랜잭션 처리
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| A계좌 잔액 100만 원에서 B와 C가 동시 100만 원 출금 성공 (마이너스 통장화) | 락 제어 없는 단순 조회 후 인출로 갱신 손실 발생 | 비관적 배타 락(`SELECT FOR UPDATE`) 또는 엄격 2PL 적용 | 이중 출금 차단 및 잔액 정합성 보장 |
| 두 트랜잭션이 서로 상대방의 계좌 락을 요구하며 무한 대기 | 자원 접근 순서 불일치로 교착상태(Deadlock) 발생 | 계좌 번호 오름차순 접근 규칙 강제 및 DBMS 락 타임아웃(3초) 설정 | 교착상태 원천 방지 및 즉시 예외 복구 |

## 이렇게 출제된다
- 제130회 1교시 2번: "데이터베이스 병행 제어 기법 및 필요성" → 요구 포인트: 병행 미제어 시 4대 문제점 + 4대 제어 기법
- 제128회 4교시 5번: "데이터베이스의 병행제어(Concurrency Control )" → 요구 포인트: 충돌 직렬성 개념 + 2PL 규칙 및 한계 극복

## 내 의견
- [분산 트랜잭션 환경의 병행제어 한계] MSA 분할 후 여러 마이크로서비스 간에 단일 RDBMS 2PL 병행제어를 적용할 수 없어 데이터 정합성 파괴 → 나라면: 계좌 이체 등 핵심 정합성 구간은 Saga 오케스트레이터를 통해 보상 트랜잭션(Compensating Transaction)을 정의하고, 멱등성(Idempotency) 키를 적용해 최종 일관성을 달성하는 분산 병행 통제 체계 구축

## 찾아볼 것
- 토마스 기록 규칙(Thomas Write Rule): 타임스탬프 기반 병행제어에서 늦게 도착한 오래된 쓰기 연산을 무시함으로써 불필요한 롤백을 줄이는 최적화 규칙
