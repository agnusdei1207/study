## 핵심 용어
- WAL(Write-Ahead Logging): 데이터 파일의 실제 블록을 디스크에 쓰기 전에, 반드시 트랜잭션 로그(Redo)를 디스크에 먼저 기록하는 영속성(Durability)의 핵심 원리
- Undo Log: 트랜잭션 실패 시 변경 사항을 되돌리기(Rollback) 위한 변경 전 데이터의 사본으로, 원자성(Atomicity)과 MVCC 읽기 일관성의 핵심

## 핵심 통찰
- ACID는 추상적 철학이 아니라 'DBMS 엔진의 4개 서브시스템 코드'로 완벽히 1:1 대응됨 → 원자성은 회복 관리자, 일관성은 제약조건 검사기, 격리성은 동시성 제어기, 영속성은 로그 관리자가 책임짐
- 이 중 가장 큰 성능 비용을 유발하는 것은 '격리성(Isolation)'임 → 완벽한 격리(Serializable)를 걸면 모든 트랜잭션이 줄을 서서 기다리므로, 현실에서는 Read Committed 수준으로 타협하고 동시성을 확보
- 분산 시스템(MSA)으로 넘어가면 물리적 단절 때문에 단일 DB 수준의 ACID는 불가능해짐 → 이때는 ACID를 포기하고 최종 일관성을 수용하는 BASE(Basically Available, Soft-state, Eventual consistency) 모델로 전환

## 이웃 토픽과 구분
- ACID vs BASE: ACID = 데이터의 '엄격한 즉각 일관성(Pessimistic)'을 최우선으로 하여 금융 결제에 적용 / BASE = 시스템의 '고가용성과 빠른 응답(Optimistic)'을 최우선으로 하고 사후에 일관성을 맞춤

## 문제·원인·대책
- 적용 상황: 대규모 트래픽 은행 계좌 이체 트랜잭션 처리
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 출금 후 입금 처리 도중 서버 전원 차단으로 출금만 되고 입금은 누락 | 원자성 보장 실패 및 회복 관리 미흡 | ARES 회복 알고리즘(Redo 후 Undo) 및 Undo Log 기반 자동 롤백 | All or Nothing 원자성 100% 보장 |
| 동시 트랜잭션 폭증 시 디스크 I/O 100% 포화로 응답 불가 | 영속성 보장을 위해 매 커밋마다 데이터 파일 블록을 디스크에 동기 기록 | WAL 적용으로 가벼운 Redo 로그만 순차 디스크 기록하고 데이터 파일 쓰기는 지연 | 디스크 무작위 I/O 90% 절감 및 처리량 10배 향상 |

## 내 의견
- [마이크로서비스 환경에서의 ACID 집착 탈피] 서비스가 10개로 쪼개진 MSA 환경에서 서비스 간 호출을 무리하게 2PC 분산 트랜잭션으로 엮어 ACID를 맞추려다 잦은 타임아웃과 서비스 연쇄 장애를 유발하는 실패 빈발 → 나라면: 서비스 경계 내부(Local DB)에서만 엄격한 ACID를 강제하고, 서비스 간 연계는 Apache Kafka 기반의 비동기 이벤트 발행과 보상 트랜잭션(Saga Pattern)으로 분리하여 고가용성과 비즈니스 일관성을 절충

## 찾아볼 것
- DBMS 장애 후 재기동 시 Redo 로그로 시스템 상태를 재현(Roll-forward)한 뒤 Undo 로그로 미완료 트랜잭션을 되돌리는 ARIES(Algorithm for Recovery and Isolation Exploiting Semantics) 회복 알고리즘
