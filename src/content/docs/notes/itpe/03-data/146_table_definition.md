## 한 줄 본질
- 개발자가 임의로 테이블을 만들어 컬럼명과 타입이 제각각 파편화되는 혼란 방지 → 물리 스키마의 모든 규격(PK, FK, 도메인, 인덱스)을 단일 표준 서식으로 명세화 → 정확한 DDL 생성 및 유지보수 보장 / 문서와 실제 DB 간 동기화 비용 발생

## 핵심 그림
```text
[테이블 정의서 표준 명세 구조 및 DDL 파이프라인]

  [테이블 기본 메타정보]
  - 테이블 논리명 : 고객주문               - 테이블 물리명 : TB_CUST_ORD
  - 테이블스페이스: TS_ORD_DATA            - 파티션 키     : ORD_DT (월별 Range)
  ─────────────────────────────────────────────────────────────────────────────
  [컬럼 세부 명세표]
  순번 | 컬럼논리명 | 컬럼물리명 | 데이터타입   | PK | FK | Null? | Default | 비고/제약
  ─────┼────────────┼────────────┼──────────────┼────┼────┼───────┼─────────┼───────────
   1   | 주문번호   | ORD_NO     | VARCHAR(20)  | Y  |    | N     |         | 시퀀스 채번
   2   | 고객식별자 | CUST_ID    | VARCHAR(20)  |    | Y  | N     |         | TB_CUST 참조
   3   | 주문일시   | ORD_DT     | TIMESTAMP    |    |    | N     | SYSDATE |
   4   | 결제금액   | PAY_AMT    | NUMBER(15,2) |    |    | N     | 0       | CHECK > 0
  ─────────────────────────────────────────────────────────────────────────────
          │ 자동 스크립트 추출 (Forward Engineering)
          ▼
  CREATE TABLE TB_CUST_ORD ( ... );  --> Git 형상관리 및 DB 배포
```

## 핵심 용어
- 포워드 엔지니어링(Forward Engineering): 모델링 도구의 논리/물리 설계 정보 또는 테이블 정의서 명세로부터 실제 DBMS에 실행 가능한 DDL 스크립트를 자동 생성하는 과정
- 형상 불일치(Schema Drift): 운영 배포 후 긴급 패치 등의 이유로 실제 DBMS 스키마는 수정되었으나 테이블 정의서 문서는 갱신되지 않아 둘 사이의 내용이 어긋나는 현상

## 핵심 통찰
- 실무에서 엑셀 파일로 작성된 테이블 정의서는 '만들어진 순간부터 썩기 시작함' → 오픈 후 3개월만 지나면 DB에는 컬럼이 5개 더 있고 타입도 바뀌어 있는데 엑셀 문서는 그대로 방치됨
- 따라서 현대적인 소프트웨어 공학에서는 엑셀 테이블 정의서를 완전히 폐지하고, ERwin/DbSchema 같은 도구의 모델 파일 자체를 Git으로 관리하거나 DDL 코드에서 문서를 자동 역생성(Reverse)하는 방식을 취함
- 테이블 정의서의 '비고/설명(Comment)'란을 비워두는 것은 미래의 유지보수 개발자에게 재앙을 떠넘기는 행위이므로, 컬럼의 업무적 의미와 코드값 목록을 명확히 명시해야 함

## 이웃 토픽과 구분
- 테이블 정의서 vs 시스템 카탈로그(데이터 딕셔너리): 테이블 정의서 = 사람이 읽고 감수하기 위해 작성된 '설계 문서(문서 파일)' / 시스템 카탈로그 = DBMS 엔진이 스키마를 실행하기 위해 메모리/디스크에 보관하는 '메타데이터 시스템 테이블(실체)'

## 문제·원인·대책
- 적용 상황: 대규모 공공 SI 차세대 시스템 감리 및 인수 단계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 감리 점검 결과 실제 운영 DB의 컬럼 타입과 테이블 정의서 내용의 40%가 불일치 | 개발자들이 엑셀 정의서 수정 없이 DB에 직접 DDL을 날리는 무단 패치 관행 | Liquibase/Flyway 기반 DDL 배포 파이프라인 구축 및 DDL 커밋 시 문서 자동 렌더링 | 문서-DB 정합성 100% 일치 달성 |
| 코드 테이블의 공통 코드값 명세가 테이블 정의서에 없어 비즈니스 로직 분석 난항 | 컬럼 설명란 작성 표준 미준수 및 검수 누락 | 표준 템플릿에 도메인 코드 매핑 테이블 링크를 의무화하고 감수 게이트 통과 강제 | 유지보수 인수인계 시간 70% 단축 |

## 내 의견
- [문서 중심 개발에서 코드 기반 단일 진실원(SSOT)으로의 전환] 프로젝트 관리자가 엑셀 테이블 정의서 수작업 작성에 수백 시간을 낭비하고 사후 불일치로 감리 지적을 받는 비효율 반복 → 나라면: 스키마 형상을 코드로 관리하는 DB 마이그레이션 도구(Flyway/Prisma)를 도입하고, DDL 스크립트 내의 `COMMENT ON COLUMN` 구문으로부터 마크다운 웹 문서가 CI/CD로 자동 빌드되어 사내 포털에 배포되는 문서 자동화 체계 정착
