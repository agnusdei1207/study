## 답안 골격
```text
[샤딩] ◀━━ 머리: Ⅶ 내 의견 (일관된 해싱(Consistent Hashing) 적용으로 노드 증설 시 데이터 재분배 최소화)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 DB 노드의 스케일업 한계 극복 → 대규모 데이터를 샤드 키 기준으로 물리적 독립 노드에 수평 분산
 ┣━ Ⅱ 특징 ───── 물리적 데이터 분할 · 무공유(Shared Nothing) 아키텍처 · 선형적 용량/처리량 확장 · 복잡성 증가
 ┣━ Ⅲ 구조 ───── 애플리케이션 / 샤드 라우터(프록시) / 컨피그 서버(메타데이터) / 데이터 샤드 노드군
 ┣━ Ⅳ 흐름 ───── ① 쿼리 유입 → ② 샤드 라우터가 쿼리의 샤드 키 추출 → ③ 라우팅 맵 조회 → ④ 타깃 샤드 노드로 쿼리 전송 및 취합
 ┣━ Ⅴ 비교 ───── 레인지 샤딩 vs 해시 샤딩 vs 디렉터리 샤딩 (범위 쿼리 유리/핫스팟 위험 vs 균등 분산/범위 쿼리 취약 vs 유연성/룩업 오버헤드)
 ┗━ Ⅵ 실무 ───── 크로스 샤드 조인(Cross-Shard Join) 성능 저하 / 샤드 불균형(Hotspot) / 2단계 커밋(2PC) 오버헤드
```
- 필수 키워드: 수평 분할 · 샤드 키(Shard Key) · 라우터(Router) · Shared Nothing · 일관된 해싱 · 크로스 샤드 조인 · 핫스팟(Hotspot)
- 기출: 127회 `데이터베이스 샤딩의 개념과 분할 전략` → Ⅰ 개념 + Ⅲ 아키텍처 + Ⅴ 분할 전략

## 한 줄 본질
- 단일 서버의 I/O 및 스토리지 물리 한계 → 행(Row) 단위 데이터를 샤드 키 기준으로 분리하여 다수의 독립 DB 인스턴스에 분산 적재 → 수평적 무한 확장성 확보 / 분산 조인 및 트랜잭션 관리 비용 폭증

## 핵심 그림
```text
[샤딩 아키텍처 및 라우팅 구조]

      애플리케이션 요청 (Query: Shard Key = User_ID)
                     │
                     ▼
             ┌──────────────┐      ┌────────────────┐
             │ 샤드 라우터  │<────>│  컨피그 서버   │
             │ (Router)     │      │(샤드 메타데이터│
             └───────┬──────┘      └────────────────┘
                     │ 샤드 키 해싱/범위 분기
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
 ┌───────────┐ ┌───────────┐ ┌───────────┐
 │ 샤드 노드1│ │ 샤드 노드2│ │ 샤드 노드3│
 │ (ID 1~1M) │ │(ID 1M~2M) │ │ (ID 2M~)  │
 └───────────┘ └───────────┘ └───────────┘
```

## 핵심 용어
- 샤드 키(Shard Key): 데이터를 어느 샤드로 라우팅할지 결정하는 기준 컬럼으로, 분산 균등성과 쿼리 패턴을 좌우하는 핵심 속성
- 크로스 샤드 조인(Cross-Shard Join): 서로 다른 물리 노드에 위치한 샤드 간 조인 연산으로, 네트워크 I/O 및 데이터 전송 병목 유발

## 핵심 통찰
- 잘못된 샤드 키 선정은 샤딩을 하지 않는 것보다 못함 → 특정 값에 데이터나 트래픽이 몰리면 핫스팟 샤드가 발생해 전체 시스템 장애 유발
- 샤딩 도입 순간 RDBMS 고유의 강점인 강력한 트랜잭션(ACID)과 조인이 포기됨 → 크로스 샤드 트랜잭션은 2PC나 사가(Saga) 패턴으로 처리해야 하므로 애플리케이션 복잡도 급증
- 따라서 스케일업, 읽기 복제본(Read Replica), 테이블 파티셔닝을 끝까지 시도한 후 최종 수단으로 샤딩을 채택해야 함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 일관된 해싱(Consistent Hashing) | 해시 샤딩의 노드 재분배 최적화 | 해시 링(Ring) 구조를 활용해 노드 추가·제거 시 재배치되는 데이터 비율을 $1/N$로 억제 |
| 사가 패턴(Saga Pattern) | 분산 샤드 간 트랜잭션 보상 | 2PC의 락 지연을 회피하기 위해 각 샤드별 로컬 트랜잭션과 실패 시 보상 트랜잭션으로 결과적 일관성 달성 |

## 이웃 토픽과 구분
- 샤딩 vs 파티셔닝: 샤딩 = 물리적으로 분리된 여러 대의 DB 서버에 분산 저장 / 파티셔닝 = 단일 DB 인스턴스 내부에서 물리적 파일(디스크)만 분리

## 문제·원인·대책
- 적용 상황: 글로벌 대형 이커머스 결제 트랜잭션 분산 DB
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 연말 세일 기간 특정 판매자 샤드로 주문 트래픽 집중(Hotspot) | 단순 판매자 ID 기준 레인지 샤딩 적용 | 판매자 ID + 주문 시간 복합 해시 샤딩 적용 | 노드 간 CPU/트래픽 편차 10% 이내 분산 |
| 여러 샤드에 걸친 결제 및 재고 차감 시 성능 급락 | 2단계 커밋(2PC) 글로벌 분산 락에 따른 블로킹 | 사가(Saga) 패턴 기반 비동기 보상 트랜잭션 전환 | 결제 처리 지연 90% 감소 및 처리량 5배 증대 |

## 이렇게 출제된다
- 제127회: "데이터베이스 샤딩(Sharding)의 개념, 샤드 분할 방식 3가지 및 구축 시 고려사항을 설명하시오." → 요구 포인트: Ⅰ 개념 + Ⅴ 레인지/해시/디렉터리 3대 방식 + Ⅵ 샤드 키 선정 및 크로스 샤드 문제

## 내 의견
- [성급한 샤딩 도입으로 인한 운영 복잡성] 단순 트래픽 증가에 놀라 캐시(Redis)나 읽기 복제본 확장 없이 샤딩을 먼저 도입해 데이터 정합성 유지비용으로 개발 조직 소진 → 나라면: 쓰기 트래픽의 병목 지점을 정량 계측하고, 복제본 증설과 수평 파티셔닝으로 한계 도달 시에만 핵심 도메인 단위로 단계적 샤딩을 격리 적용
