## Ⅰ. 수평적 무한 확장을 위한 샤딩(Sharding)의 개요

### 가. 샤딩의 정의
- **샤딩**은 단일 데이터베이스 인스턴스의 CPU, 메모리, I/O 대역폭 한계를 극복하기 위해, 대규모 데이터셋을 샤드(Shard)라는 물리적으로 독립된 여러 개의 데이터베이스 서버(Shared-Nothing 노드)에 수평으로 분할하여 저장하고 처리하는 아키텍처임.
- 하드웨어 성능을 증설하는 수직 확장(Scale-Up)의 물리적·비용적 한계에 도달했을 때 채택하는 궁극의 수평 확장(Scale-Out) 해법.

### 나. 샤딩이 반드시 필요한 임계 상황
- 단일 테이블의 레코드 수가 수억 건을 초과하여 B-Tree 인덱스 깊이 증가로 인한 I/O 지연 발생.
- 초당 쓰기 트랜잭션(TPS)이 단일 마스터 노드의 디스크 WAL 기록 한계를 초과했을 때.

## Ⅱ. 샤딩의 핵심 아키텍처 및 샤드 키(Shard Key) 결정 전략

### 가. 샤딩 시스템 3대 구조

```text
[ 샤딩 시스템 구조도 ]
[App Client] ---> [Shard Router / Proxy] ---> Shard Key 해시 계산
                           |
      +--------------------+--------------------+
      |                    |                    |
      v                    v                    v
 [Shard Node 1]       [Shard Node 2]       [Shard Node 3]
 (Data: 0 ~ 33%)      (Data: 34 ~ 66%)     (Data: 67 ~ 100%)
```

### 나. 샤드 키 분할 알고리즘 비교

| 샤딩 방식 | 분할 원리 | 장점 | 단점 및 위험 요인 |
| :--- | :--- | :--- | :--- |
| **해시 기반 샤딩 (Hash-Based)** | Shard ID = $Hash(Key) \pmod N$ | 데이터가 모든 노드에 가장 균등하게 분산됨 | 범위 검색 시 모든 샤드를 스캔해야 함, 노드 추가 시 대규모 데이터 재배치 발생 |
| **안정 해시 샤딩 (Consistent Hashing)** | 가상의 원형 해시 링(Hash Ring) 상에 노드와 키를 배치 | 노드 증설 시 $1/N$의 데이터만 이동하여 리밸런싱 최소화 | 링 상에서 노드 간 불균형 발생 가능(가상 노드 기법으로 완화) |
| **범위 기반 샤딩 (Range-Based)** | 키의 특정 값 범위별로 샤드 지정 (예: 1~100만, 100만~200만) | 범위 검색 성능 우수, 특정 기간 데이터 관리 용이 | 최신 데이터가 특정 샤드로만 쏠리는 핫스팟(Hotspot) 발생 |
| **디렉토리 기반 샤딩 (Directory-Based)** | 룩업 서비스(Lookup Table)를 두어 키와 샤드의 매핑 정보를 중앙 관리 | 동적 샤드 이동 및 데이터 재배치가 극도로 유연함 | 룩업 테이블 자체가 단일 실패점(SPOF) 및 병목 지점이 됨 |

## Ⅲ. 샤딩 환경의 트랜잭션·쿼리 한계점·문제점 및 해결 방안

### 가. Cross-Shard 트랜잭션과 2단계 커밋(2PC)
- 서로 다른 샤드 노드에 걸친 데이터 갱신 시 원자성을 보장하기 위해 분산 2PC(Prepare $\rightarrow$ Commit)를 적용해야 하지만, 네트워크 지연과 블로킹 락으로 인해 시스템 처리량이 1/10 이하로 급감함.
- **해법** : 동일 트랜잭션에서 함께 처리되는 데이터는 반드시 **동일한 샤드 키를 공유** 하도록 엔티티 그룹화 설계(예: 주문과 주문상세는 `User_ID`를 샤드 키로 공유).

### 나. 분산 집계 및 글로벌 정렬 (Scatter-Gather)
- `ORDER BY`나 `GROUP BY` 수행 시 라우터가 모든 샤드에 쿼리를 브로드캐스트(Scatter)한 후 결과를 메모리에서 병합 정렬(Gather)해야 하므로 메모리 부하 급증.

## Ⅳ. 무중단 샤딩 운영을 위한 실무 제언

- **샤드 분할(Resharding) 자동화 체계 구축** : 서비스 성장에 따라 단일 샤드가 포화 상태에 이를 경우를 대비하여, Debezium 등 CDC(Change Data Capture) 기반으로 무중단 상태에서 데이터를 새 샤드로 복제하고 컷오버(Cut-over)할 수 있는 자동화 툴링을 사전에 준비해야 함.
- **복합 샤드 키(Composite Shard Key) 설계** : 특정 대형 엔터프라이즈 고객(파레토 법칙의 상위 소수)으로 인해 단일 샤드가 터지는 현상을 막기 위해, `Tenant_ID + Hash(Entity_ID)` 형태의 복합 키를 적용하여 대형 고객 데이터를 여러 노드로 안전하게 분산시킬 것을 제언함.
