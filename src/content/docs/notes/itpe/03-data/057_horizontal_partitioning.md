## 답안 골격
```text
[데이터베이스 수평분할] ◀━━ 머리: Ⅶ 내 의견 (파티션 프루닝(Pruning) 최적화와 파티션 키 기반 주기적 아카이빙 자동화)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 테이블의 스키마 구조는 유지한 채 행(Row, 튜플) 단위로 데이터를 분리하여 독립된 물리 저장소에 분산
 ┣━ Ⅱ 특징 ───── 행 단위 분할 · 릴레이션 스키마 불변 · 파티션 프루닝으로 I/O 절감 · 대용량 테이블 관리성 향상
 ┣━ Ⅲ 구조 ───── 범위 분할(Range) / 해시 분할(Hash) / 리스트 분할(List) / 컴포지트 분할(Composite) / 파티션 키
 ┣━ Ⅳ 흐름 ───── ① 파티션 키 및 분할 기준 선정 → ② DDL 파티션 테이블 생성 → ③ 데이터 유입 시 파티션 엔진이 분기 저장 → ④ 쿼리 시 프루닝 실행
 ┣━ Ⅴ 비교 ───── 수평분할 vs 수직분할 (행 단위 분리/전체 컬럼 유지 vs 컬럼 단위 분리/기본키 공유)
 ┗━ Ⅵ 실무 ───── 파티션 키 조건 누락으로 인한 전 파티션 풀스캔 / 글로벌 인덱스 재구성 오버헤드
```
- 필수 키워드: 수평 파티셔닝 · 파티션 키(Partition Key) · 레인지(Range) · 해시(Hash) · 리스트(List) · 파티션 프루닝(Partition Pruning) · 로컬 인덱스
- 기출: 138회 2교시 3번 `분산 데이터베이스 시스템 구축을 위한 데이터베이스 분할(수평/수직 분할)` → Ⅰ 개념 + Ⅲ 수평분할 유형 + Ⅴ 비교

## 한 줄 본질
- 수억 건 대용량 테이블에서 인덱스 트리 비대화 및 I/O 병목 발생 → 행(Row) 집합을 기준 키에 따라 독립 물리 세그먼트로 분할 저장 → 쿼리 대상 파티션만 좁혀 읽는 프루닝(Pruning) 달성 / 분할 키 변경 시 이동 비용 발생

## 핵심 그림
```text
[수평분할(Horizontal Partitioning) 구조 및 파티션 프루닝]

  [논리적 단일 테이블: 주문 (Orders)]
  주문번호(PK) | 주문일자     | 고객ID | 금액
  ────────────┼──────────────┼────────┼───────
  1001        │ 2024-01-15   │ U01    │ 50000
  1002        │ 2025-05-20   │ U02    │ 30000
  1003        │ 2026-03-10   │ U03    │ 70000
                     │
       [ 파티션 키: 주문일자 (Range 분할) ]
                     │
     ┌───────────────┼───────────────┐
     ▼               ▼               ▼
 ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
 │ 파티션 2024 │ │ 파티션 2025 │ │ 파티션 2026 │
 │ (물리 파일1)│ │ (물리 파일2)│ │ (물리 파일3)│
 └─────────────┘ └─────────────┘ └──────┬──────┘
                                        ▲
  SELECT * FROM 주문                     │ (파티션 프루닝:
  WHERE 주문일자 >= '2026-01-01'  ───────┘  파티션 2024, 2025는 I/O 완전 배제!)
```

## 핵심 용어
- 파티션 프루닝(Partition Pruning): 옵티마이저가 SQL의 WHERE 절 조건을 분석하여 불필요한 파티션을 쿼리 실행 대상에서 완전히 배제하는 I/O 최적화 기술
- 로컬 파티션 인덱스(Local Partitioned Index): 각 파티션 테이블마다 1:1로 매핑되어 독립적으로 생성되는 인덱스로, 파티션 삭제(DROP) 시 타 파티션 인덱스 영향 없음

## 핵심 통찰
- 수평분할의 생명은 '파티션 키'가 WHERE 절에 반드시 포함되도록 설계하는 것 → 파티션 키가 빠진 쿼리는 모든 분할 파일을 다 뒤져야 하므로 분할하지 않은 것보다 훨씬 느림
- 글로벌 인덱스(Global Index)는 분할된 모든 파티션을 하나의 인덱스로 묶으므로, 특정 파티션을 DROP하거나 TRUNCATE할 때 전체 인덱스가 Unusable 상태에 빠져 장애 유발
- 따라서 파티션 삭제를 통한 이력 데이터 정리가 목적이라면 반드시 '로컬 파티션 인덱스'를 채택해야 함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 컴포지트 분할(Composite) | 2차 결합 수평분할 방식 | 1차로 범위(Range) 분할 후 2차로 해시(Hash) 분할을 결합해 파티션 내 편중을 해소 |
| 파티션 익스체인지(Partition Exchange) | 초고속 데이터 적재 및 이관 | 대량의 신규 데이터를 일반 테이블에 적재 후 메타데이터 교환만으로 1초 만에 파티션으로 편입 |

## 이웃 토픽과 구분
- 수평분할 vs 샤딩: 수평분할 = 단일 DBMS 인스턴스 내에서 스토리지 파일(세그먼트)만 쪼개어 관리 / 샤딩 = 물리적으로 분리된 여러 대의 DB 서버 인스턴스로 분산

## 문제·원인·대책
- 적용 상황: 전자상거래 1억 건 로그 테이블 조회 및 아카이빙
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 3년 지난 로그 삭제 시 DELETE 문 수행으로 DB 락 발생 및 10시간 소요 | 트랜잭션 롤백 로그(Undo) 및 인덱스 갱신을 수반하는 DML 삭제 | 월별 Range 수평분할 후 `ALTER TABLE DROP PARTITION` DDL 적용 | 삭제 시간 1초로 단축 및 Undo 부하 제로 |
| 특정 파티션에만 80%의 데이터가 몰려 I/O 병목 발생 | 편향된 고객 지역 코드를 파티션 키로 단독 사용 | 주문일자(Range) + 고객ID(Hash) 컴포지트 분할 전환 | 파티션 간 데이터 균등 분산 달성 |

## 이렇게 출제된다
- 제138회 2교시 3번: "분산 데이터베이스 시스템 구축을 위한 데이터베이스분할에 대하여 다음 내용을 설명 하시오." → 요구 포인트: 수평분할과 수직분할의 개념, 수평분할의 4대 방식(Range, Hash, List, Composite) 및 프루닝 원리

## 내 의견
- [무분별한 파티셔닝으로 인한 성능 역효과] 테이블 용량이 수 기가바이트에 불과한 소규모 테이블까지 파티션을 쪼개어 메타데이터 락과 메모리만 낭비하는 안티패턴 만연 → 나라면: 단일 테이블 용량이 최소 수 천만 건 또는 100GB를 초과하고, 명확한 일자별 아카이빙 요건이나 병렬 쿼리 이득이 확인될 때만 수평분할 적용 가이드라인 수립

## 찾아볼 것
- RDBMS(Oracle, PostgreSQL)의 인터벌 파티셔닝(Interval Partitioning)을 통한 신규 일자 파티션 자동 생성 메커니즘
