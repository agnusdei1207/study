## 한 줄 본질
- 분할이 발생하지 않는 대부분의 정상 운영 시간에 발생하는 지연시간과 일관성의 트레이드오프를 CAP이 설명하지 못함 → 정상(Else) 시 L vs C의 절충축을 추가 → 분산 DBMS의 실제 성능 및 일관성 동작을 정확히 모델링

## 핵심 용어
- Latency vs Consistency (L vs C): 분할이 없는 정상 상태에서도, 모든 복제본에 데이터를 동기식으로 쓰고 확인할 것인가(High C, High Latency) 아니면 마스터에만 쓰고 바로 응답할 것인가(Low Latency, Eventual Consistency)의 절충
- 쿼럼(Quorum, $R + W > N$): 전체 노드 $N$개 중 읽기 노드 수 $R$과 쓰기 노드 수 $W$의 합이 $N$보다 크도록 설정하여 PACELC의 동작 강도를 동적으로 튜닝하는 기법

## 핵심 통찰
- 네트워크 분할(Partition)은 현실 시스템에서 1년에 몇 번 안 일어나는 예외적 재난임 → CAP만 보면 평상시 시스템이 어떻게 작동하는지 전혀 알 수 없음
- 시스템의 일상 운영 비용을 결정하는 것은 결국 '정상 상태의 지연시간(Latency)과 일관성(Consistency)의 교환'임
- PACELC는 고정된 라벨이 아니라 런타임 설정임 → Cassandra나 DynamoDB도 일관성 수준을 `QUORUM`이나 `ALL`로 올리면 PA/EL에서 PC/EC 성격으로 즉시 전환됨

## 이웃 토픽과 구분
- CAP vs PACELC: CAP = "분할이 발생했을 때 가용성과 일관성 중 무엇을 포기할 것인가"만 설명 / PACELC = "분할 시 A vs C뿐만 아니라, 정상 시 지연시간(L)과 일관성(C) 중 무엇을 우선할 것인가"까지 완결

## 문제·원인·대책
- 적용 상황: 글로벌 이커머스 주문 및 재고 처리 분산 저장소 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 글로벌 다중 리전 배포 후 주문 처리 API 지연시간이 300ms로 급증 | 정상 상태에서 모든 글로벌 리전으로 완전 동기 복제(EC) 강제 | 주문/결제는 PC/EC(로컬 쿼럼), 장바구니/조회는 PA/EL로 분리 | 평균 응답 지연 300ms에서 25ms로 90% 이상 단축 |
| 네트워크 순간 단절 시 상품 재고가 음수로 떨어지는 데이터 오염 | 분할 상황에서 PA(가용성 우선 로컬 쓰기) 정책 채택 | 재고 차감 트랜잭션 영역에 한해 조건부 쓰기(Conditional Put, PC) 강제 | 분할 시에도 오버셀링(초과 판매) 원천 차단 |

## 이렇게 출제된다
- 제126회: "분산 데이터베이스 시스템에서 CAP 이론의 한계점을 분석하고, 이를 해결하기 위해 제안된 PACELC 이론의 개념, 분류 기준 및 주요 NoSQL 데이터베이스별 매핑을 설명하시오." → 요구 포인트: CAP 한계(정상상태 L/C 부재) + PACELC 수식 정의 + 4분면 분류 매핑표(Cassandra, Spanner, MongoDB 등)

## 내 의견
- [모든 도메인에 단일 분산 DB 강제 지양] 개발 편의를 위해 전사 표준 DB로 Cassandra(PA/EL)만 지정했다가 정산 업무에서 데이터 불일치 사태를 겪거나, 반대로 Spanner(PC/EC)만 지정해 단순 로그 수집 지연이 폭증하는 오류 발생 → 나라면: 도메인의 비즈니스 손실 비용을 기준으로 정산·결제는 PC/EC, 사용자 피드·추천·로그는 PA/EL로 이원화하는 폴리글랏 퍼시스턴스(Polyglot Persistence) 원칙 수립
