## 연관 키워드

- 스타 스키마(Star Schema), 팩트 테이블(Fact Table), 차원 테이블(Dimension Table), Kimball
- SCD(Slowly Changing Dimension), 대리 키(Surrogate Key), 스노우플레이크 스키마(Snowflake Schema)

## Ⅰ. 스타 스키마의 개요

- 핵심 요약 : 측정값 중심 테이블 주변에 분석 관점 테이블을 방사형으로 연결한 DW(Data Warehouse)의 차원 모델링 구조.
- 개념 : 비즈니스 프로세스의 측정값을 중앙 테이블에 두고, 분석 관점을 담은 테이블을 주변에 배치한 데이터 모델 (**스타 스키마**, Star Schema).
- 배경 및 필요성 : 운영 DB를 정규화한 구조는 분석 질의에서 조인이 많아 느리고 복잡하므로, 분석 목적에 맞게 구조를 단순화할 필요가 생김.
- 주요 목적 : 다차원 집계 질의를 단순한 조인으로 빠르고 이해하기 쉽게 수행.
- 설계 근거 : Ralph Kimball이 체계화한 **차원 모델링** (Dimensional Modeling, 분석 관점 중심의 DW 설계 방법론)을 기반으로 함.

## Ⅱ. 스타 스키마의 특징 및 장점

- 핵심 요약 : 팩트와 차원의 역할을 분리하고 역정규화를 적용해, 단순한 1단계 조인과 빠른 집계로 이어지는 구조.

1. **팩트 테이블** (Fact Table, 측정값과 차원 키를 담은 중심 테이블) : 측정값과 외래 키(FK, Foreign Key) 위주의 좁고 깊은 구조 → 집계 대상 데이터를 한곳에 모음.
2. **차원 테이블** (Dimension Table, 분석 관점의 속성을 담은 테이블) : 고객, 날짜, 제품 같은 속성을 넓게 펼친 구조 → 필터와 그룹 기준 제공.
3. **역정규화** (Denormalization, 조인을 줄이려고 중복을 허용하는 설계) : 차원 속성을 한 테이블에 모음 → 조인 단계를 줄여 쿼리 속도 향상.
4. 단순 조인 : 팩트와 각 차원이 1단계로만 연결됨 → 질의 구문이 단순해 유지보수가 쉬움.
5. 비즈니스 친화성 : "기간별, 지역별 매출"처럼 사용자의 분석 관점이 모델에 그대로 드러남.

## Ⅲ. 스타 스키마의 구조 (흐름)

- 핵심 요약 : 팩트 테이블을 중심으로 차원이 방사형으로 붙는 구조이며, 차원을 다시 정규화하면 스노우플레이크 구조가 됨.
- **스노우플레이크 스키마** (Snowflake Schema, 차원 테이블을 다시 정규화해 하위 차원으로 분해한 구조) : 스토리지는 절약하지만 조인 단계가 늘어남.

```text
[ 스타 스키마 방사형 구조 ]

[Dim_Customer]      [Dim_Date]
       \             /
        v           v
      [Fact_Sales]
        ^           ^
       /             \
[Dim_Product]      [Dim_Store]
```

```text
[ Fact_Sales 구성 ]

Date_Key (FK)      -> Dim_Date
Customer_Key (FK)  -> Dim_Customer
Product_Key (FK)   -> Dim_Product
Store_Key (FK)     -> Dim_Store
Quantity, Amount   -> 측정값
```

```text
[ 스노우플레이크 확장 ]

Fact_Sales
      ↓
Dim_Product
      ↓
Dim_Category (추가 정규화)
```

## Ⅳ. 팩트 테이블과 차원 테이블의 비교

- 핵심 요약 : 저장하는 내용과 볼륨, 정규화 정도, 형태가 두 테이블 유형에서 반대로 설계됨.

| 항목 | 팩트 테이블 | 차원 테이블 |
| --- | --- | --- |
| 저장 내용 | 측정값과 외래 키 | 분석 기준이 되는 속성 |
| 예시 | 매출액, 수량 | 고객명, 제품 분류, 지역 |
| 행 수 | 누적에 따라 가장 크게 증가 | 상대적으로 작게 유지 |
| 정규화 | 측정값과 키만 보유 | 의도적 역정규화 |
| 형태 | 좁고 깊은(Narrow & Deep) | 넓고 평평한(Wide & Flat) |

| 항목 | 스타 스키마 | 스노우플레이크 스키마 |
| --- | --- | --- |
| 차원 구조 | 역정규화 | 부분 정규화 |
| 조인 단계 | 1단계 | 다단계 |
| 스토리지 | 중복으로 증가 | 중복 감소 |
| 쿼리 성능 | 단순 조인에 유리 | 조인 증가로 불리 |

## Ⅴ. 스타 스키마의 한계와 방안

- 핵심 요약 : 역정규화에 따른 갱신 이상, 팩트 테이블 비대화, M:N 관계를 SCD, 구체화 뷰, 브릿지 테이블로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 역정규화 갱신 이상 | 차원 값이 바뀌면 중복 행을 모두 갱신해야 해 불일치 위험 발생 | **SCD** (Slowly Changing Dimension, 점진적으로 변하는 차원)의 이력 관리, MERGE 문 기반 차원 갱신 | 정합성 검사 결과 |
| 팩트 테이블 비대화 | 대용량 팩트의 풀 스캔이 병목이 되어 응답 지연 | 파티셔닝, 구체화 뷰(Materialized View), 컬럼형 저장 | 질의 응답 시간 |
| M:N 관계 | 단순 스타로 표현할 수 없어 이중 집계 발생 | 브릿지 테이블(Bridge Table), 가중치 팩터 적용 | 집계 정확도 |

## Ⅵ. 스타 스키마에 대한 기술사적 제언

- 핵심 요약 : 대리 키와 SCD 타입 2로 조인 성능과 이력 보존을 함께 확보하고, 대용량에는 파티셔닝과 구체화 뷰를 조합하는 것이 바람직함.

1. 원천 시스템의 자연 키 대신 정수형 **대리 키** (Surrogate Key, 웨어하우스에서 부여하는 일련번호 키)를 쓰면 조인 비용이 줄고, 원천 키가 바뀌어도 웨어하우스 구조가 흔들리지 않는다.
2. 고객 등급이나 소속 부서처럼 이력 분석이 필요한 속성은 SCD 타입 2를 적용해 시작일과 종료일을 가진 새 행을 추가하고, 과거 시점의 값을 보존하는 것이 좋다.
3. 대용량 팩트 테이블은 날짜 기준 파티셔닝과 구체화 뷰를 함께 적용해 자주 쓰는 집계를 미리 계산해 두는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : 스타 스키마는 팩트와 차원의 분리, 역정규화, 대리 키와 SCD를 결합한 차원 모델링 표준임.
- 시사점 : 분석 질의가 빠르고 단순해지는 대신 갱신 관리 비용이 생기므로, 설계 단계에서 이력 관리와 갱신 파이프라인을 함께 설계해야 함.
