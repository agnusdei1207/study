## Ⅰ. 데이터 웨어하우스 차원 모델링의 표준, 스타 스키마 개요

### 가. 스타 스키마(Star Schema)의 정의
- 랄프 킴볼(Ralph Kimball)의 차원 모델링(Dimensional Modeling) 이론에 기반한 것으로, 비즈니스 프로세스에서 발생하는 계량적 수치 데이터를 저장하는 단 하나의 중앙 **팩트 테이블(Fact Table)** 을 중심으로, 이를 다양한 비즈니스 관점에서 분석하기 위한 복수의 **차원 테이블(Dimension Table)** 들이 별(Star) 모양의 방사형으로 직접 연결된 데이터베이스 스키마 구조.

---

## Ⅱ. 팩트 테이블(Fact) vs 차원 테이블(Dimension) 구조 분석

### 가. 스타 스키마 물리적 구조도

```text
[ 스타 스키마 방사형 구조도 ]
      [고객 차원 (Dim_Customer)]        [날짜 차원 (Dim_Date)]
                   \                       /
                    \                     /
                     v                   v
              +---------------------------------+
              |    판매 팩트 (Fact_Sales)       |
              |---------------------------------|
              | - Date_Key (FK)                 |
              | - Customer_Key (FK)             |
              | - Product_Key (FK)              |
              | - Store_Key (FK)                |
              |---------------------------------|
              | * 판매수량 (Quantity) - 측정값  |
              | * 판매금액 (Sales_Amount)       |
              +---------------------------------+
                     ^                   ^
                    /                     \
                   /                       \
       [상품 차원 (Dim_Product)]        [매장 차원 (Dim_Store)]
```

### 나. 팩트 테이블 vs 차원 테이블 비교 매트릭스

| 비교 항목 | 팩트 테이블 (Fact Table) | 차원 테이블 (Dimension Table) |
| :--- | :--- | :--- |
| **저장 내용** | 비즈니스 사건의 **정량적 측정값(Measures)** 및 차원 FK | 분석의 관점이 되는 **정성적 컨텍스트(문맥/속성)** |
| **구체적 예시** | 매출액, 판매량, 주문 건수, 접속 시간, 할인율 | 고객명, 성별, 상품 카테고리, 매장 지역, 요일 |
| **데이터 볼륨** | 수천만~수십억 건 (극도로 거대함) | 수백~수십만 건 (상대적으로 작음) |
| **정규화 수준** | 차원 조인을 위한 FK와 측정값만 포함 | **의도적인 완전 역정규화(Denormalized)** 적용 |
| **테이블 형태** | 세로로 긴 형태 (Narrow & Deep) | 가로로 넓은 형태 (Wide & Flat) |

## Ⅲ. 스타 스키마 vs 스노우플레이크 스키마(Snowflake Schema) 비교

```text
[ 스타 스키마 vs 스노우플레이크 스키마 ]
(A) 스타 스키마 : [Fact] ---> [Dim_Product (카테고리명 컬럼 포함 - 역정규화)]
(B) 스노우플레이크: [Fact] ---> [Dim_Product] ---> [Dim_SubCategory] ---> [Dim_Category (정규화)]
```

| 비교 항목 | 스타 스키마 (Star Schema) | 스노우플레이크 스키마 (Snowflake Schema) |
| :--- | :--- | :--- |
| **차원 정규화** | **역정규화 유지 (중복 허용)** | **차원 테이블을 3NF로 부분 정규화** |
| **조인(JOIN) 복잡도** | **단 1단계 조인** (Fact와 Dim 간 단순 조인) | 차원 간 다단계 계층 조인(Multi-level JOIN) 필요 |
| **쿼리 성능** | **극도로 빠름 (조인 최소화)** | 복잡한 조인으로 인해 쿼리 응답 시간 지연 |
| **스토리지 사용량** | 역정규화로 인한 중복 데이터로 약간 큼 | 정규화로 중복이 제거되어 스토리지 절감 |
| **유지보수성** | 차원 데이터 수정 시 중복 컬럼 동시 갱신 필요 | 정규화된 차원 마스터 단일 수정으로 정합성 우수 |

## Ⅳ. 스타 스키마(Star Schema)의 주요 한계점 및 해결 방안

- **차원 테이블의 비정규화(Denormalization)에 따른 데이터 중복 및 갱신 이상** :
  - **한계점** : 조인 성능을 극대화하기 위해 차원을 비정규화하므로 차원 데이터 갱신 시 다량의 레코드를 일괄 수정해야 하며 정합성 불일치 위험 상존.
  - **해결 방안** : 서서히 변하는 차원(SCD: Slowly Changing Dimension Type 2) 모델링 표준화, 배치 적재 시 멱등성을 보장하는 머지(MERGE) 파이프라인 적용.
- **팩트 테이블(Fact Table)의 기하급수적 비대화에 따른 쿼리 스캔 병목** :
  - **한계점** : 거래 데이터가 수십억 건 이상 누적될 경우 스타 조인(Star Join) 시 팩트 테이블 풀 스캔으로 인해 DW/OLAP 시스템의 메모리 및 I/O 고갈.
  - **해결 방안** : 일자/월 단위 파티셔닝 적용, 빈번한 다차원 집계를 사전에 계산하는 구체화 뷰(Materialized View) 및 칼럼나 스토리지(Parquet, ClickHouse) 적용.
- **다대다(M:N) 관계 및 다중 그레인(Granularity) 모델링의 복잡성** :
  - **한계점** : 계좌와 고객, 주문과 프로모션처럼 M:N 관계가 발생할 경우 단순 스타 스키마로 표현 불가하며 중복 집계(Double Counting) 오류 발생.
  - **해결 방안** : 브릿지 테이블(Bridge Table) 도입, 가중치 팩터(Weighting Factor) 부여를 통한 집계 왜곡 방지.

## Ⅴ. 스타 스키마 최적화 및 모델링 실무 제언

- **대리키(Surrogate Key)의 전면 적용** : 차원 테이블의 기본키(PK)로 원천 시스템의 자연키(Natural Key, 주민번호나 상품코드)를 직접 쓰지 말고, 정수형 일련번호인 **대리키(Surrogate Key - Integer)** 를 생성하여 팩트 테이블에 저장해야 함 $\rightarrow$ 조인 연산 속도 수십 배 향상 및 원천 시스템의 키 변경에 따른 DW 영향 격리.
- **느리게 변화하는 차원(SCD) 관리 기법 적용** : 고객의 주소나 부서가 변경될 때 과거 시점의 매출 분석 왜곡을 방지하기 위해, 기존 행을 덮어쓰지 않고 시작일/종료일 컬럼과 함께 새 행을 추가하는 **SCD Type 2(이력 보존)** 기법을 표준으로 구현할 것을 제언함.
