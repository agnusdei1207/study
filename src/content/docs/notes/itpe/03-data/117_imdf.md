## 연관 키워드
- 실내 매핑 데이터 포맷, OGC, GeoJSON, 실내 공간정보, IPS, 디지털 트윈, 객체 계층, 피처 유형

### Ⅰ. 실내 매핑 데이터 포맷의 개요

- 핵심 요약 : 실내 공간을 **GeoJSON** (지리 데이터를 JSON으로 표현하는 형식) 기반으로 모델링하는 표준 포맷.
- 개념 : 공항, 쇼핑몰, 병원 등 건물 내부의 공간과 시설을 피처 단위로 표현하는 실내 공간정보 포맷(**IMDF**, Indoor Mapping Data Format).
- 배경 및 필요성 : 실외에서는 위성 측위(GPS, Global Positioning System)로 위치를 알 수 있지만 실내에서는 신호가 약해 쓸 수 없으므로, 건물마다 다른 도면을 공통 포맷으로 맞춰 실내 공간정보를 여러 서비스가 함께 쓸 수 있음.
- 주요 목적 : 실내 지도의 상호 운용성 확보와 실내 위치 기반 서비스의 기준 데이터 마련.
- 특징 : 계층형 피처 모델과 GeoJSON 기반 표준 구조.

### Ⅱ. 실내 매핑 데이터 포맷의 특징 및 장점

- 핵심 요약 : 계층 모델과 표준 기반 상호 운용이 실내 측위와 디지털 트윈 연계의 바탕이 되는 구조.

1. 구조 모델(Vertex → Face → Cell) : 건물 내부의 공간과 시설을 계층적으로 표현 → 실내 공간의 정교한 표현과 분석.
2. OGC(OGC, Open Geospatial Consortium) 표준 : GeoJSON 기반 구조를 공통 규약으로 따름 → 서로 다른 시스템 간 데이터 교환 호환성 확보.
3. IPS(Indoor Positioning System, 실내 측위 시스템) 연동 : BLE나 Wi-Fi 비콘의 신호로 위치를 추정하고 그 결과를 IMDF 도면 위에 표시 → 실내 위치 서비스의 기준 지도 역할.
4. 디지털 트윈 (Digital Twin) 연계 : BIM(Building Information Modeling) 모델을 경량화해 IoT(Internet of Things) 센서 값을 겹쳐 보여줌 → 건물 상태를 공간 단위로 모니터링.
5. 경량 렌더링 : 설계 원본 대신 GeoJSON 기반 경량 데이터를 쓰므로 웹과 모바일에서 빠르게 그릴 수 있음.

### Ⅲ. 객체 계층의 흐름

- 핵심 요약 : Venue에서 Level로 내려가며 Unit, Opening, Amenity, Anchor가 층 안에 배치되는 포함 관계 구조.
- 피처 유형 : Venue, Building, Footprint, Level, Unit, Opening, Amenity, Anchor, Relationship 등으로 역할을 분리.

```text
[ 상태 다이어그램 ]

액터 ─── (주문 생성)
          ├─ «include» 결제 승인(항상 포함되는 공통 하위 기능)
          └─ «extend» 쿠폰 적용(조건이 충족될 때 선택적으로 확장)
```

```text
[ 실내 매핑 데이터 포맷의 구조 ]

클래스 다이어그램
 ├ 이름·속성·연산
 └ 관계 → 다중성
```

### Ⅳ. 주요 UML 행위 다이어그램과의 비교

- 핵심 요약 : 단일 객체의 상태 변화, 전체 업무 흐름, 객체 간 메시지 순서라는 서로 다른 모델링 초점.

| 비교 항목 | 상태 다이어그램 | 활동 다이어그램 | 시퀀스 다이어그램 |
|---|---|---|---|
| 모델링 초점 | 단일 객체의 생명주기와 상태 변화 | 전체 시스템의 업무 프로세스 흐름 | 여러 객체 간 시간 순서의 메시지 교환 |
| 제어 주체 | 외부에서 들어오는 이벤트 | 선행 작업 완료에 따른 내부 흐름 | 호출자와 피호출자의 호출 순서 |
| 주 활용 대상 | 주문 상태, 결제 트랜잭션, 임베디드 제어기 | 업무 절차, 알고리즘 흐름 | 서비스 간 호출 순서, 연동 흐름 |

- 선택 기준 : 객체 생명주기가 핵심이면 상태, 업무 절차가 핵심이면 활동, 객체 간 메시지 순서가 핵심이면 시퀀스 다이어그램을 택함.

### Ⅴ. 상태 다이어그램의 한계와 방안

- 핵심 요약 : 불법 전이 차단과 테스트 도출의 강점, 상태 폭발과 모델-코드 불일치의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 상태 폭발(State Explosion) | 변수와 동시성 요건 증가 → 상태와 전이 수 급증, 가독성 저하 | 하렐 상태차트 개념으로 슈퍼상태와 직교 영역 구조화 | 상태 수, 전이 수 |
| 분산 환경의 상태 불일치 | 네트워크 분할과 비동기 지연 → 서비스 간 전역 상태 불일치 | 사가 패턴 오케스트레이터 연계, 이벤트 소싱 기반 상태 재구성, 전이 멱등성 보장 | 보상 트랜잭션 발생률 |
| 모델과 코드의 불일치 (Architectural Drift) | 설계 문서 미갱신 → 상태 다이어그램이 레거시 문서로 전락 | XState, Spring Statemachine 등 상태 머신 프레임워크로 정의 기반 코드 생성 | 모델과 코드 차이 건수 |

### Ⅵ. 상태 머신 구현과 검증에 대한 기술사적 제언

- 핵심 요약 : 상태 패턴으로 구현 구조를 세우고 전이 커버리지 테스트를 자동화해 설계와 검증을 함께 유지하는 방향.
- 클래스 안에 if-else나 switch-case로 상태를 하드코딩하면 새 상태가 추가될 때마다 기존 코드를 고쳐야 하므로, 개방-폐쇄 원칙(OCP, Open-Closed Principle)을 지키도록 **상태 패턴** (State Pattern)을 적용해 상태별 행위를 독립 클래스로 캡슐화하는 것을 기본 설계로 삼는 것이 좋다.
- 테스트 조직은 상태 전이 표를 바탕으로 모든 유효 전이를 한 번씩 방문하는 0-스위치와 연속된 두 전이 쌍을 방문하는 1-스위치 커버리지를 목표로 **상태 전이 테스팅** (State Transition Testing) 케이스를 생성하고 자동화하면, 사람이 놓치기 쉬운 전이를 줄일 수 있다.

### Ⅶ. 결론

- 핵심 요약 : 상태 다이어그램은 이벤트 기반 객체 생명주기를 검증 가능한 기준 모델로 만드는 설계 도구.
- 시사점 : 복잡도는 계층화로 억제하고 모델과 코드의 일치는 도구로 유지할 때 상태 다이어그램이 설계와 검증의 공통 기준이 된다.
