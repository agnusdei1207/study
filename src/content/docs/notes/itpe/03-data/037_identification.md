## 답안 골격
```text
[식별] ◀━━ 머리: Ⅶ 내 의견 (DB 모델링의 식별 관계 남용 지양 + 보안상 단일 식별자 탈피 분산 신원(DID) 연계)
 ┃
 ┣━ Ⅰ 개요 ───── 정보시스템에서 주체나 개체를 유일하게 구분 → 데이터 모델링의 키(Key) 및 보안의 신원 확인 기본 개념
 ┣━ Ⅱ 특징 ───── 유일성(Uniqueness) · 최소성(Minimality) · 존재 종속성 결정(데이터 모델링) · 신원 주장(보안)
 ┣━ Ⅲ 구조 ───── 데이터 모델링 관점(후보키/기본키, 식별/비식별 관계) vs 보안 관점(식별, 인증, 인가, 책임추적성)
 ┣━ Ⅳ 흐름 ───── ① 신원 주장(ID 제시 / 엔티티 식별자 부여) → ② 검증(인증 / 무결성 제약 검사) → ③ 식별 확정 및 접근/참조 허용
 ┣━ Ⅴ 비교 ───── 식별(Identification) vs 인증(Authentication) vs 인가(Authorization)
 ┗━ Ⅵ 실무 ───── 복합 식별자로 인한 자식 테이블 PK 비대화 / 개인 식별자(주민번호) 직접 사용 컴플라이언스 위반
```
- 필수 키워드: 유일 식별자(UID) · 기본키(PK) · 식별 관계(실선) · 비식별 관계(점선) · 신원 주장(Identification) · 인증(Authentication) · DID
- 기출: 128회 4교시 6번 `식별(Identification)과 인증(Authentication)` → 보안 4단계 체계 / 133회 `데이터 모델링` → 식별자 및 식별 관계

## 한 줄 본질
- 수많은 데이터 인스턴스와 시스템 사용자 중 "누구인가/어떤 개체인가"를 유일하게 지목하는 성질 → 데이터 무결성의 기준점 및 정보보안 접근 통제의 출발점 / 과도한 식별자 전이 시 테이블 결합도와 개인정보 침해 위험 증가

## 핵심 그림
```text
[데이터 모델링의 식별 관계 vs 보안의 식별 체계]

 [데이터 모델링 관점: 식별 관계]         [정보보안 4대 통제 관점]
      [부모 엔티티] (PK: 고객번호)             1. 식별 (Identification)
           │                                      - "나는 홍길동이다" (ID 입력)
           │ (실선: 식별 관계)                            │
           ▼                                              ▼
      [자식 엔티티]                            2. 인증 (Authentication)
      - PK: 고객번호 + 주문순번                       - "증거(비밀번호/생체) 제시"
      - 부모의 PK가 자식의 PK로 전이됨                   │
                                                          ▼
 [비식별 관계 (점선)]: 부모 PK -> 자식 일반 속성    3. 인가 (Authorization) -> 4. 책임추적
```

## 핵심 용어
- 식별 관계(Identifying Relationship): 부모 엔티티의 기본키(PK)가 자식 엔티티의 기본키(PK)의 일부로 상속되는 관계로, 자식은 부모 없이는 독립적으로 존재할 수 없는 종속 엔티티
- 대체 식별자(Surrogate Key): 자연 식별자(주민번호, 이메일 등) 대신 시스템에서 일련번호(Auto-Increment, UUID)로 인위적으로 생성한 인조 식별자

## 핵심 통찰
- 보안에서 '식별'은 단지 주장에 불과함 → ID를 입력하는 행위는 식별(Claim)이고, 그 주장이 맞는지 비밀번호나 OTP로 증명하는 행위가 인증(Verification)임
- 데이터 모델링에서 식별 관계(실선)를 남용하면 '상속의 족쇄'에 갇힘 → 4~5단계 계층을 내려가면 자식 테이블의 PK가 5개 컬럼으로 불어나 인덱스 크기가 커지고 조인 쿼리가 극도로 난해해짐
- 개인식별번호(주민번호, 여권번호)를 DB의 물리 PK로 잡으면 안 됨 → 개인정보보호법상 암호화 저장 의무가 있어 인덱스 탐색 성능이 파괴되므로, 대체 키(UUID)를 식별자로 삼고 주민번호는 비식별 속성으로 격리해야 함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 비식별 관계 (Non-identifying) | 느슨한 엔티티 결합 | 부모 PK가 자식의 일반 속성(FK)으로만 내려가 자식의 독립적 생존 보장 |
| 분산 식별자 (DID) | 차세대 탈중앙 신원 식별 | 중앙 서버 없이 블록체인 기반으로 정보주체가 자신의 신원 식별 권한을 통제 |

## 이웃 토픽과 구분
- 식별 vs 인증: 식별 = 시스템에 자신의 계정 ID를 알리는 행위(주장) / 인증 = 패스워드나 생체인증을 통해 그 사람이 본인임을 증명하는 행위(검증)

## 문제·원인·대책
- 적용 상황: 대규모 공공 포털 데이터 모델링 및 사용자 인증 시스템
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 하위 5번째 자식 테이블의 PK 컬럼이 6개로 늘어나 쿼리 작성 불가능 | 모든 부모-자식 관계를 무분별하게 식별 관계(실선)로 모델링 | 부모-자식 관계를 비식별 관계(점선)로 전환하고 단일 시퀀스 PK 채택 | 테이블 간 결합도 완화 및 쿼리 단순화 |
| 주민등록번호를 회원 테이블 PK로 설계해 법적 컴플라이언스 위반 | 자연 식별자 직접 사용으로 인한 법적 규제 위배 | 비즈니스와 무관한 인조 식별자(UUID v7)를 PK로 도입하고 주민번호 격리 | 법적 리스크 해소 및 보안 강화 |

## 이렇게 출제된다
- 제128회 4교시 6번: "식별(Identification)과 인증(Authentication)" → 요구 포인트: 식별과 인증의 개념적 차이 + 사용자 인증 기술 3요소(지식/소유/생체) + 최신 인증 트렌드
- 제133회: "데이터 모델링에서 식별자와 관계 도출" → 요구 포인트: 주식별자의 특징(유일성, 최소성, 불변성, 존재성) 및 식별/비식별 관계의 장단점 비교

## 내 의견
- [식별 관계 일변도의 레거시 DB 부채] 과거 설계 관행대로 모든 관계를 식별 관계로 묶어두어 테이블 간 종속성이 너무 높아 테이블 하나를 수정할 수 없는 레거시 시스템 빈발 → 나라면: 부모와 라이프사이클이 100% 일치하는 강한 복합 엔티티(주문-주문상세)에만 식별 관계를 제한 적용하고, 그 외에는 전면 비식별 관계로 설계하여 마이크로서비스 분할이 용이한 구조 지향
