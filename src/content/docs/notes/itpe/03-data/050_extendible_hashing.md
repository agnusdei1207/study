## 큰 그림과 30초 인출

```text
[확장성 해싱(Extendible Hashing)의 구조 및 오버플로우 분할 메커니즘]

   글로벌 깊이 (d = 2)
   ┌─────────────┐
   │ 디렉터리(4) │
   ├─────────────┤             로컬 깊이 (d')
   │  00 ────────┼───────────> ┌───────────┐ (d' = 2)
   ├─────────────┤             │  버킷 A   │ [0010, 0011]
   │  01 ────────┼──┐          └───────────┘
   ├─────────────┤  │
   │  10 ────────┼──┼────────> ┌───────────┐ (d' = 1)  <-- 01과 11이 공유
   ├─────────────┤  └─────────>│  버킷 B   │ [0101, 1100]
   │  11 ────────┼────────────>└───────────┘
   └─────────────┘
  ──────────────────────────────────────────────────────────────────────
  [시나리오 1: d' < d 인 버킷 B 넘침]
   - 디렉터리 확장 없이 버킷 B만 2개로 분할하고 로컬 깊이를 2로 증가 (d' = 2)
   - 디렉터리 01은 버킷 B1, 11은 버킷 B2로 포인터 재지정
  ──────────────────────────────────────────────────────────────────────
  [시나리오 2: d' = d 인 버킷 A 넘침]
   - 디렉터리를 2배(2^3 = 8개)로 확장하고 글로벌 깊이 증가 (d = 3)
   - 버킷 A를 분할하고 로컬 깊이 3으로 증가 (d' = 3), 신규 디렉터리 포인터 갱신
```

- 본질: **데이터 증가 시 전체 파일의 재해싱(Rehashing) 없이, 해시값의 비트 접두사를 가리키는 디렉터리(Directory)를 두고 오버플로우가 발생한 특정 버킷(Bucket)만 국소적으로 분할하는 동적 해싱(Dynamic Hashing) 기법**
- 암기: `디-버-글-로` (디렉터리, 버킷, 글로벌 깊이, 로컬 깊이) / `국-이-모-균` (국소 분할, 최대 2회 디스크 I/O, 모조키 비트열, 균일한 $O(1)$ 탐색)
- 판단축:
  - **$d' < d$ (로컬 깊이 < 글로벌 깊이)**: 디렉터리는 가만히 두고 넘친 버킷만 분할, 포인터만 재연결 (비용 극소)
  - **$d' = d$ (로컬 깊이 = 글로벌 깊이)**: 디렉터리 엔트리를 2배($2^{d+1}$)로 확장한 후 넘친 버킷 분할 (디렉터리 팽창 비용 발생)
- 주의: 디렉터리 크기가 $2^d$로 지수적으로 증가하므로, 특정 버킷에만 동일 비트 해시가 몰릴 경우 디렉터리 폭증(Directory Explosion) 및 메모리 고갈 위험이 존재함

## 예상문제

> 대용량 데이터베이스의 인덱싱 기법 중 정적 해싱의 한계와 이를 극복하기 위한 확장성 해싱(Extendible Hashing)의 개념, 구성요소, 동작 메커니즘을 설명하고, 버킷 오버플로우 발생 시의 2가지 분할 시나리오 및 선형 해싱(Linear Hashing)과의 차이점을 비교하시오. (25점)

## Ⅰ. 정적 해싱의 한계를 극복하는 확장성 해싱(Extendible Hashing) 개요

#### 한줄 요약: 고정 버킷 정적 해싱의 재해싱 병목을 해결하고 모조키 비트열과 디렉터리를 통해 버킷을 국소 분할하는 동적 해싱 기법

- **정적 해싱(Static Hashing)의 구조적 한계**:
  - 고정된 수의 버킷을 사용하므로 데이터가 증가하면 오버플로우 체인(Overflow Chain)이 길어져 탐색 성능이 $O(N)$으로 급격히 퇴화함
  - 이를 해결하기 위해 버킷 수를 늘리려면 전체 테이블을 다시 해싱(Full Rehashing)해야 하므로 대규모 서비스 중단 및 막대한 디스크 I/O 부하가 발생함
- **확장성 해싱의 정의**:
  - 검색 키를 해시 함수에 통과시켜 얻은 이진 비트열(모조키)의 접두사(Prefix)를 인덱스로 사용하는 **디렉터리(Directory)**와 실제 데이터가 저장되는 **버킷(Bucket)**을 분리 운용하는 동적 해싱 기법
  - 버킷이 가득 찼을 때 전체가 아닌 **해당 버킷만 독립적으로 분할(Local Split)**하고, 필요 시에만 디렉터리를 2배로 확장하여 항상 고른 $O(1)$의 탐색 성능을 보장함

## Ⅱ. 확장성 해싱의 핵심 구조 및 구성 요소

#### 한줄 요약: 글로벌 깊이를 갖는 디렉터리 테이블과 로컬 깊이를 갖는 데이터 버킷 간의 계층적 포인터 매핑 체계

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    확장성 해싱의 논리-물리 구성 구조                         │
└─────────────────────────────────────────────────────────────────────────────┘
  [검색 키 K] ──▶ [해시 함수 h(K)] ──▶ [모조키 이진 비트열: 1011001...]
                                                    │ (상위 d 비트 추출)
                                                    ▼
                                     ┌─────────────────────────────┐
                                     │   글로벌 깊이 (Global Depth d)│
                                     ├─────────────────────────────┤
                                     │ 디렉터리 (크기: 2^d 엔트리)  │
                                     └──────────────┬──────────────┘
                                                    │ 포인터 참조
                                                    ▼
                                     ┌─────────────────────────────┐
                                     │ 데이터 버킷 (Data Buckets)   │
                                     │ - 로컬 깊이 (Local Depth d') │
                                     │ - 고정 레코드 슬롯 수 (B)    │
                                     └─────────────────────────────┘
```

### 1. 주요 구성 요소 상세

| 구성 요소 | 역할 및 핵심 특징 | 비고 / 수식 |
|:---|:---|:---|
| **모조키 (Pseudo Key)** | 원본 키를 해시 함수에 입력하여 생성한 고정 길이 이진 비트열 | $h(K) \in \{0, 1\}^*$ |
| **디렉터리 (Directory)** | 모조키의 접두사 비트 패턴을 인덱스로 하여 각 버킷의 물리 주소를 가리키는 포인터 배열 | 주기억장치(RAM)에 상주 권장 |
| **글로벌 깊이 (Global Depth, $d$)** | 디렉터리에서 버킷을 구분하기 위해 현재 사용 중인 유효 접두사 비트 수 | 디렉터리 엔트리 수 = $2^d$ |
| **버킷 (Bucket)** | 실제 데이터 레코드가 저장되는 고정 크기의 디스크 블록 (또는 메모리 페이지) | 용량 $B$ (레코드 수) |
| **로컬 깊이 (Local Depth, $d'$)** | 해당 버킷에 속한 모든 레코드의 모조키가 공통으로 공유하는 접두사 비트 수 | 항상 $d' \le d$ 성립 |

### 2. 깊이(Depth) 간의 수학적 상관관계
- **버킷을 가리키는 디렉터리 포인터 수**: $2^{d - d'}$개
  - 예: $d = 3$이고 특정 버킷의 $d' = 1$이면, 디렉터리 내 $2^{3-1} = 4$개의 엔트리가 해당 버킷 하나를 동시에 가리킴
- **동일 깊이($d' = d$)**: 디렉터리의 정확히 1개 엔트리가 해당 버킷을 일대일로 가리킴

## Ⅲ. 확장성 해싱 동작 메커니즘 및 2대 분할 시나리오

#### 한줄 요약: 비트 접두사 기반의 최대 2회 디스크 I/O 탐색과 버킷 오버플로우 발생 시 깊이 비교에 따른 조건부 디렉터리 확장

### 1. 데이터 탐색(Search) 및 삽입(Insert) 기본 절차
1. **해시 비트 추출**: 검색 키 $K$에 대해 $h(K)$를 계산하고 상위 $d$개 비트를 추출함
2. **디렉터리 조회**: 해당 $d$개 비트를 정수로 환산하여 디렉터리의 인덱스로 접근, 연결된 버킷 포인터 획득
3. **버킷 읽기**: 버킷 포인터를 통해 실제 데이터 블록을 읽고 레코드 인출 (**디렉터리가 RAM에 있으면 단 1회의 디스크 I/O**)
4. **삽입 시 여유 공간 검사**: 버킷에 빈 슬롯이 있으면 삽입 완료. 슬롯이 꽉 찼다면 **오버플로우 분할 프로토콜** 진입

```text
[버킷 오버플로우 발생 시 2대 분할 경로]

                     [버킷 오버플로우 발생!]
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
        [시나리오 1: d' < d]        [시나리오 2: d' = d]
         디렉터리 확장 불필요        디렉터리 2배 확장 필수
                 │                           │
          - 신규 버킷 생성             - 글로벌 깊이 d <- d + 1
          - 넘친 버킷 d' <- d'+1       - 디렉터리 2^d -> 2^(d+1) 팽창
          - 기존/신규 버킷에 레코드 분배 - 신규 버킷 생성 및 d' <- d'+1
          - 디렉터리 포인터 재배정     - 기존/신규 버킷 레코드 분배 및 포인터 재배정
```

### 2. 분할 시나리오 상세 분석

#### 가. 시나리오 1: 로컬 깊이가 글로벌 깊이보다 작은 경우 ($d' < d$)
- **상황**: 디렉터리의 복수 엔트리가 해당 버킷을 가리키고 있는 상태
- **처리 절차**:
  1. 신규 버킷을 1개 할당함
  2. 넘친 버킷과 신규 버킷의 로컬 깊이를 모두 $d' + 1$로 증가시킴
  3. $(d'+1)$번째 비트 값이 0인 레코드는 기존 버킷에, 1인 레코드는 신규 버킷에 재분배함
  4. 디렉터리에서 해당 버킷들을 가리키던 포인터들 중 절반은 신규 버킷을 가리키도록 갱신함
- **비용**: 디스크 블록 1개 할당 및 2개 블록 재기록만 수반 (매우 경량)

#### 나. 시나리오 2: 로컬 깊이가 글로벌 깊이와 같은 경우 ($d' = d$)
- **상황**: 디렉터리의 단 1개 엔트리만이 해당 버킷을 가리키고 있어, 분할 결과를 수용할 디렉터리 슬롯이 부족함
- **처리 절차**:
  1. **디렉터리 2배 확장**: 글로벌 깊이를 $d \leftarrow d + 1$로 증가시키고, 디렉터리 크기를 $2^d$에서 $2^{d+1}$로 2배 복제 확장
  2. 기존 디렉터리 엔트리 $i$의 내용을 새로운 위치 $i$와 $i + 2^d$에 각각 복사하여 초기화
  3. 이제 넘친 버킷의 로컬 깊이는 $d' < d_{new}$ 상태가 되었으므로, **시나리오 1의 절차를 그대로 수행**하여 버킷 분할 및 포인터 재연결
- **비용**: 디렉터리 테이블 2배 복제 메모리 비용 + 버킷 분할 I/O

## Ⅳ. 확장성 해싱 vs 선형 해싱 (Linear Hashing) 상세 비교

#### 한줄 요약: 디렉터리를 사용하는 비트 접두사 기반 국소 분할과 디렉터리 없이 포인터를 전진시키며 순차 분할하는 선형 해싱의 비교

```text
┌───────────────────────────────────┬───────────────────────────────────┐
│     확장성 해싱 (Extendible Hashing)│       선형 해싱 (Linear Hashing)    │
├───────────────────────────────────┼───────────────────────────────────┤
│ - 디렉터리: 필수 (메모리 포인터 배열)│ - 디렉터리: 없음 (무디렉터리 방식)  │
│ - 분할 방식: 오버플로우 발생 버킷만 │ - 분할 방식: 포인터(Split Pointer)가│
│   국소적으로 즉시 분할             │   지정한 버킷을 순서대로 순차 분할  │
│ - 임시 오버플로우 체인: 거의 불필요 │ - 임시 오버플로우 체인: 일시적 필요 │
│ - 디렉터리 확장: 2배 지수 팽창     │ - 공간 확장: 1버킷씩 선형(Linear) 확장│
└───────────────────────────────────┴───────────────────────────────────┘
```

| 비교 항목 | 확장성 해싱 (Extendible Hashing) | 선형 해싱 (Linear Hashing) |
|:---|:---|:---|
| **디렉터리 존재 유무** | **필수** (글로벌 깊이 기반 포인터 배열 필요) | **불필요** (디렉터리 없이 수식으로 버킷 번호 산출) |
| **버킷 분할 대상** | **오버플로우가 발생한 해당 버킷만 분할** | 오버플로우 발생 위치와 무관하게 **분할 포인터($P$)가 가리키는 버킷 분할** |
| **공간 확장 형태** | 디렉터리가 $2^d$로 **지수적(Exponential) 2배 도약** | 버킷이 라운드 로빈 방식으로 **1개씩 선형(Linear) 증가** |
| **임시 체인 발생** | 동일 해시값 과밀 시 외에는 오버플로우 체인 없음 | 분할 포인터가 도달할 때까지 임시 오버플로우 체인 연결 불가피 |
| **탐색 디스크 I/O** | 디렉터리 RAM 상주 시 **최대 1~2회 디스크 I/O** 보장 | 오버플로우 체인이 길어질 경우 일시적으로 I/O 횟수 증가 |
| **저장 효율성** | 디렉터리 메모리 오버헤드 존재, 버킷 사용률 약 69% | 디렉터리가 없어 메모리 효율 우수, 버킷 사용률 약 60~70% |

## Ⅴ. B+Tree 인덱스 vs 확장성 해싱 아키텍처 비교

#### 한줄 요약: 점 검색 최적화($O(1)$)와 범위 검색 지원($O(\log N)$) 간의 질의 패턴별 스토리지 인덱스 선정 기준

| 비교 항목 | 확장성 해싱 (Extendible Hashing) | B+Tree 인덱스 (B+Tree Index) |
|:---|:---|:---|
| **기본 시간 복잡도** | **$O(1)$ (상수 시간)** | **$O(\log N)$ (트리 높이 비례)** |
| **점 검색 (Point Query)** | 극도로 빠름 (단 1~2회 블록 접근) | 우수하나 루트-브랜치-리프 수직 탐색 필요 |
| **범위 검색 (Range Scan)** | **불가능** (해시 순서는 키 순서와 완전 무관) | **최적** (리프 블록 간 양방향 링크드 리스트 순회) |
| **정렬 결과 반환** | 불가 (별도 정렬 연산 필요) | 기 정렬 상태이므로 ORDER BY 비용 제로 |
| **동적 확장 메커니즘** | 디렉터리 2배 확장 및 버킷 국소 분할 | 노드 분할(Node Split) 및 트리 높이 증가 |
| **주요 활용 분야** | 세션 스토어, 키-값 저장소(NoSQL), 심볼 테이블 | RDBMS 기본 인덱스, 파일 시스템 색인 |

## Ⅵ. 실무 적용 시 문제점, 장애 패턴 및 대응 전략

#### 한줄 요약: 해시 비트 편향에 따른 디렉터리 폭증(Directory Explosion) 및 메모리 고갈 방지 엔지니어링

```text
[해시 충돌 편향으로 인한 디렉터리 폭증 장애 메커니즘]

 키 유입: k1, k2, k3, k4... 모두 해시 상위 비트가 "0000000..."으로 동일!
 버킷 오버플로우 계속 발생 -> d' = d 상태에서 연속 분할 트리거
 글로벌 깊이 d가 4 -> 8 -> 16 -> 24로 급상승!
 디렉터리 크기: 2^24 = 16,777,216 엔트리 (수백 MB의 메모리가 단 몇 개 키 때문에 낭비됨)
 ──▶ [장애 결과: Out Of Memory 발생 및 디렉터리 스캔 지연]
```

### 1. 주요 장애 패턴 및 원인
- **디렉터리 폭증 (Directory Explosion)**: 해시 함수의 균등 분포 특성이 나쁘거나 동일 키가 대량 인입될 때, 버킷 내 레코드들이 분할되어도 계속 같은 버킷으로 쏠려 글로벌 깊이가 끝없이 올라가는 현상
- **동시성 락 병목**: 디렉터리 2배 확장 시 디렉터리 전체에 대한 배타적 락(Exclusive Lock)이 걸려 모든 읽기/쓰기 작업이 일시 중단되는 병목 발생

### 2. 엔지니어링 대응 전략
1. **고성능 균등 해시 함수 채택**: MD5, SHA 계열 대신 CPU 연산이 빠르고 비트 분포가 극도로 균일한 **MurmurHash3**, **CityHash**, **xxHash** 적용
2. **버킷 용량(Bucket Capacity) 적정화**: 버킷 크기를 너무 작게 설정(예: 2~4개)하면 조기 분할이 빈발하므로, OS 페이지 크기(4KB~8KB)에 맞추어 수십~수백 개 슬롯으로 설계
3. **최대 글로벌 깊이 상한($d_{max}$) 지정**: 무제한 디렉터리 확장을 차단하기 위해 $d_{max}$를 설정하고, 상한 도달 시 임시 오버플로우 체인 블록을 연결한 뒤 비동기 재해싱 트리거

## Ⅶ. 데이터 아키텍트 관점의 동적 해싱 아키텍처 제언

#### 한줄 요약: 디렉터리 인메모리 상주 구조 확보와 점 검색 중심의 NoSQL/캐시 계층에 특화된 물리 설계 수립

- **디렉터리 인메모리 상주(In-Memory Caching) 전제**:
  - 확장성 해싱의 $O(1)$ 탐색 성능은 디렉터리가 주기억장치에 상주할 때만 디스크 I/O 1회로 유효함
  - 디렉터리가 디스크로 스왑 아웃(Swap-out)되면 디렉터리 읽기 1회 + 버킷 읽기 1회로 총 2회 이상의 I/O가 발생하여 B+Tree 대비 이점이 급감함
- **워크로드 특성에 따른 하이브리드 배치**:
  - 범위 질의가 많은 업무 테이블은 전통적 B+Tree 인덱스를 유지
  - 사용자 세션 검증, 인증 토큰 매핑, URL 단축기 등 순수 단건 Point Query가 95% 이상인 서비스 구간에 확장성 해싱 기반 키-값 엔진을 집중 배치하여 DB 전체 Throughput을 극대화해야 함

## 2교시 25점 답안 발췌

```text
[문제 1] 대용량 데이터베이스의 정적 해싱 한계와 확장성 해싱(Extendible Hashing) 기법

Ⅰ. 정적 해싱의 한계와 확장성 해싱의 등장 배경
 1. 정적 해싱의 한계: 버킷 수 고정으로 오버플로우 체인 증가(O(N) 퇴화), 재해싱 시 전체 I/O 병목
 2. 확장성 해싱의 정의: 모조키 비트 접두사와 디렉터리를 두어 넘친 버킷만 국소 분할하는 동적 해싱

Ⅱ. 확장성 해싱의 구조 및 2대 오버플로우 분할 메커니즘
 1. 핵심 구성 요소
  가. 글로벌 깊이(d): 디렉터리 식별 비트 수 (디렉터리 엔트리 수 = 2^d)
  나. 로컬 깊이(d'): 해당 버킷 레코드들이 공유하는 공통 비트 수 (d' <= d)
  다. 디렉터리 & 버킷: RAM 상주 포인터 배열 및 실제 레코드 디스크 블록

 2. 오버플로우 분할 2대 시나리오 메커니즘
  가. 시나리오 1: 로컬 깊이 < 글로벌 깊이 (d' < d)
   - 디렉터리 확장 없이 신규 버킷 생성 후 d' <- d'+1 증가
   - (d'+1)번째 비트(0, 1)에 따라 레코드 분배 및 디렉터리 포인터 재연결
  나. 시나리오 2: 로컬 깊이 = 글로벌 깊이 (d' = d)
   - 글로벌 깊이 증가(d <- d+1) 및 디렉터리 엔트리 2배(2^(d+1)) 복제 확장
   - 이후 시나리오 1과 동일하게 버킷 분할 및 d' 증가 수행

Ⅲ. 확장성 해싱 vs 선형 해싱(Linear Hashing) 비교
 ┌────────────────┬──────────────────────────┬──────────────────────────┐
 │   비교 항목    │    확장성 해싱           │        선형 해싱         │
 ├────────────────┼──────────────────────────┼──────────────────────────┤
 │ 디렉터리 유무  │ 필수 (2^d 엔트리 배열)   │ 불필요 (무디렉터리 방식) │
 │ 분할 대상 버킷 │ 오버플로우 발생 버킷     │ 포인터(P)가 가리키는 버킷│
 │ 공간 확장 형태 │ 디렉터리 지수 2배 팽창   │ 버킷 1개씩 선형 순차 확장│
 │ 점 검색 성능   │ O(1) 극대화 (1~2회 I/O)  │ 임시 체인 발생 시 I/O 증가│
 └────────────────┴──────────────────────────┴──────────────────────────┘

Ⅳ. 실무 디렉터리 폭증(Directory Explosion) 방지 및 아키텍처 제언
 1. 장애 예방: MurmurHash3 등 균등 해시 적용, OS 페이지 크기(4~8KB) 맞춤 버킷 용량 튜닝
 2. 아키텍처 제언: 세션/토큰/인증 등 순수 Point Query 워크로드에 한정하여 선별 적용
```
