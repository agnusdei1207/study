## Ⅰ. 동적 해싱 기법으로서의 확장성 해싱(Extendible Hashing) 개요

### 가. 확장성 해싱의 정의
- **확장성 해싱** : 대용량 데이터베이스 파일에서 데이터의 삽입과 삭제에 따라 **디렉토리** (Directory) 구조와 **버킷** (Bucket)의 수를 동적으로 분할·병합함으로써, 해시 테이블의 크기를 유연하게 확장하는 **동적 해싱** (Dynamic Hashing) 기법.
- 정적 해싱(Static Hashing)의 치명적 한계인 버킷 오버플로우(Overflow) 시의 긴 체이닝 탐색 비용 및 성능 저하를 해결하기 위해 고안됨.

### 나. 정적 해싱 vs 확장성 해싱
- **정적 해싱** : 고정된 버킷 수로 시작하여 데이터 증가 시 충돌(Collision)로 인한 선형 탐색 및 오버플로우 버킷 체인 증가 $\rightarrow$ 조회 성능 급락.
- **확장성 해싱** : 디렉토리 포인터와 버킷의 분할을 통해 데이터가 아무리 증가해도 최대 2번의 디스크 접근($O(1)$) 으로 레코드 검색 보장.

## Ⅱ. 확장성 해싱의 핵심 구조 및 깊이(Depth) 메커니즘

### 가. 핵심 3대 구성 요소

```text
[ 확장성 해싱 구조도 (전역 깊이 d=2) ]
디렉토리(접두사)   버킷
  00  ----------> [Bucket A] 지역 깊이 d'=2 : 해시값 00... 레코드
  01  ----------> [Bucket B] 지역 깊이 d'=2 : 해시값 01... 레코드
  10  ----+
          +-----> [Bucket C] 지역 깊이 d'=1 : 해시값 1... 레코드
  11  ----+       (10, 11 두 엔트리가 Bucket C를 공동 참조)
```

| 구성 요소 | 정의 및 역할 | 동작 특성 |
| :--- | :--- | :--- |
| **해시 함수 $h(K)$** | 키 값을 충분히 긴 이진수(예: 32비트)로 변환하는 의사 난수 함수 | 균등한 비트 분포 생성 |
| **전역 깊이 (Global Depth, $d$)** | 디렉토리에서 버킷을 식별하기 위해 사용하는 해시값의 접두사(Prefix) 비트 수 | 디렉토리 크기는 항상 $2^d$ 개 |
| **지역 깊이 (Local Depth, $d'$)** | 특정 버킷이 현재 데이터를 구분하기 위해 사용하는 해시값 비트 수 | 항상 $d' \le d$ 성립 |
| **버킷 (Bucket)** | 실제 데이터 레코드가 고정 크기로 저장되는 블록 단위 | 가득 차면(Overflow) 분할 |

### 나. 버킷 오버플로우 발생 시의 분할 알고리즘

```text
[ 버킷 분할 의사결정 ]
버킷 오버플로우 발생!
       |
       +---> [지역 깊이 d' < 전역 깊이 d 인 경우] :
       |       - 디렉토리 확장은 불필요
       |       - 해당 버킷만 2개로 분할하고 d'를 1 증가시킴 (d' = d' + 1)
       |       - 디렉토리 포인터를 분할된 새 버킷으로 재조정
       |
       +---> [지역 깊이 d' == 전역 깊이 d 인 경우] :
               - 디렉토리 크기를 2배로 확장! (전역 깊이 d = d + 1)
               - 디렉토리 엔트리가 2^d에서 2^(d+1)로 증가
               - 해당 버킷 분할 후 d' 1 증가 및 포인터 재설정
```

## Ⅲ. 확장성 해싱과 선형 해싱(Linear Hashing)의 비교

| 비교 항목 | 확장성 해싱 (Extendible Hashing) | 선형 해싱 (Linear Hashing) |
| :--- | :--- | :--- |
| **디렉토리 필요 여부** | 필수 (Directory 존재) | 불필요 (Directory-less) |
| 확장 방식 | 전역 깊이 증가 시 디렉토리 크기가 2배로 급격히 도약($2^d$) | 버킷을 순차적으로 1개씩 점진적 확장 |
| 오버플로우 처리 | 버킷 분할로 해결 (오버플로우 체인 최소화) | 임시 오버플로우 페이지 연결 후 포인터($P$)가 도달할 때 분할 |
| 메모리 오버헤드 | 디렉토리가 커지면 메모리 적재 부담 발생 가능 | 메모리 오버헤드가 극히 적음 |

## Ⅳ. 확장성 해싱 구현 및 운용의 주요 한계점 및 해결 방안

- 전역 깊이(Global Depth) 증가 시 디렉터리 크기 지수적 폭증 :
  - 한계점 : 특정 버킷으로 해시 충돌이 집중될 경우 로컬 깊이가 증가하면서 전역 깊이도 증가하여 디렉터리 엔트리 수가 $2^d$로 2배씩 폭증, 메인 메모리 한계 초과.
  - 해결 방안 : 균일한 분산을 보장하는 고품질 해시 함수(MurmurHash3 등) 채택, 또는 디렉터리가 필요 없는 선형 해싱(Linear Hashing)으로의 전환 검토.
- 디렉터리 접근을 위한 이중 디스크 I/O(Double I/O) 오버헤드 :
  - 한계점 : 디렉터리가 메모리 용량을 초과하여 디스크에 저장될 경우 레코드 1건 조회를 위해 디렉터리 참조와 실제 버킷 접근의 최소 2회 디스크 I/O 필수 발생.
  - 해결 방안 : 디렉터리 계층을 압축하여 인메모리 버퍼 풀에 100% 핀(Pin) 고정, 다단계 페이징 디렉터리 구조 설계.
- 동시성 환경에서의 디렉터리 분할 시 글로벌 락(Lock) 경합 :
  - 한계점 : 버킷 분할로 인해 디렉터리 배열을 재할당하고 포인터를 갱신하는 동안 전체 디렉터리에 대한 배타적 쓰기 락이 필요하여 동시 처리량 급감.
  - 해결 방안 : 락 프리(Lock-Free) 원자적 포인터 교체(Compare-And-Swap, CAS) 기법 도입 및 세분화된 버킷 레벨 래치(Bucket-level Latch) 분리.

## Ⅴ. 스토리지 엔진 구현 관점의 실무 제언

- 디렉토리 메모리 상주화 : 확장성 해싱의 최고 장점인 2번의 디스크 I/O(디렉토리 1회 + 버킷 1회)를 유지하려면, 디렉토리가 항상 메인 메모리(RAM, Random-Access Memory)에 상주하도록 크기를 관리해야 함.
- 해시 키 스큐(Skew) 방지 : 해시 함수의 비트 분포가 불균일하여 특정 접두사에 데이터가 편향될 경우 디렉토리 크기만 기하급수적으로 폭발하는 병리적 현상이 발생하므로, 균등 분포 특성이 우수한 해시 함수(MurmurHash3 등)를 적용할 것을 제언함.
