## 연관 키워드

- 데이터 표준화, 표준 단어·용어·도메인·코드, 동음이의어·이음동의어, 메타데이터 관리 시스템(MDR)
- 변경 관리(RFC), 영향도 분석, 표준 검증 린터(Linter), 바운디드 컨텍스트, Strangler Fig 패턴

## Ⅰ. 데이터 표준화의 개요

- 핵심 요약 : 분산 시스템 간 데이터의 명칭·정의·형식·규칙을 전사 표준으로 통일하는 프로세스.
- 개념 : 조직 내 분산된 정보시스템 간 데이터의 명칭, 정의, 형식, 규칙을 일관된 표준에 맞춰 통일하고 전사적으로 공유·관리하는 **데이터 표준화** (Data Standardization).
- 배경 및 필요성 :
  1. 데이터 중복과 불일치 : 같은 고객을 CUST_NO, USER_ID, CUSTOMER_NUM 등으로 혼용해 전사 통합 분석이 어려움.
  2. 인터페이스 변환 비용 증가 : 시스템 연계 때마다 데이터 타입 변환(VARCHAR와 CHAR)과 코드 매핑 로직이 추가됨.
  3. 유지보수 생산성 저하 : 개발자가 바뀌면 컬럼의 실제 의미를 파악하는 데 많은 시간이 듦.
- 주요 목적 : 모델링과 DB 구축, 인터페이스 연계에서 같은 의미 데이터가 다른 명칭과 타입으로 갈라지는 것을 막고 상호운용성을 확보.

## Ⅱ. 데이터 표준화의 특징 및 장점

- 핵심 요약 : 4대 표준 요소의 계층 구조와 5단계 추진 절차, 거버넌스 기반 변경 관리가 결합된 체계.

1. 4대 표준 요소 : 표준 단어, 표준 용어, 표준 도메인, 표준 코드를 계층으로 구성 → 최소 단위에서 유효값까지 일관된 정의 확보.
2. 상호운용성 확보 : 시스템 간 명칭·정의·형식·규칙을 통일 → 인터페이스 변환 비용 절감.
3. 5단계 추진 절차 : 대상 수집, 현황 분석, 표준안 확정, 메타데이터 등록, 적용·사후 관리 순으로 진행.
4. 거버넌스 기반 변경 관리 : **변경 관리** (RFC, Request for Change) 요청서로 영향도 분석과 위원회 심의를 거쳐 변경 → 기존 시스템의 예기치 못한 중단 방지.
5. 자동 검증 연계 : **표준 검증 린터** (Linter)를 모델링 도구와 CI(Continuous Integration)/CD(Continuous Delivery) 파이프라인에 연결 → 표준 준수를 사람이 아닌 도구가 검사.

```text
[ 데이터 표준 정의 흐름 ]

 1. 표준 단어 (최소 의미 단위: 고객, 번호)
          ↓ 단어 조합
 2. 표준 용어 (업무 명칭: 고객번호)
          ↓ 도메인 매핑
 3. 표준 도메인 (물리 속성 그룹: 금액)
          ↓ 값 집합 제한
 4. 표준 코드 (유효값 집합: 성별코드)
```

## Ⅲ. 데이터 표준화의 구조 (흐름)

- 핵심 요약 : 표준 단어에서 표준 코드까지 정의 흐름을 세우고, 개발 라이프사이클 안에서 MDR 중심으로 표준을 통제하는 구조.

```text
[ 개발 라이프사이클 내 표준 통제 ]

 데이터 모델러
          ↓
 MDR 검색 → 표준 용어 자동 완성
          ↓ 미등록 시
 표준 신청 및 워크플로우 심의
          ↓ 승인 후 모델 반영
 CI/CD DDL 표준 준수 검증 (Linter)
```

- 표준화 5단계 절차 :
  1. 표준화 대상 수집 : 기존 시스템의 DDL(Data Definition Language), 데이터 사전, 테이블 정의서, 인터페이스 명세서를 추출.
  2. 현황 분석 및 정비 : **동음이의어** (같은 단어에 다른 의미)와 **이음동의어** (다른 단어에 같은 의미)를 식별해 정리.
  3. 표준안 확정 : 표준 단어·용어·도메인·코드 정의서를 작성하고 데이터 관리 위원회의 심의와 승인을 받음.
  4. 전사 메타데이터 등록 : 메타데이터 관리 시스템(MDR, Metadata Repository)에 등록하고 배포.
  5. 적용 및 사후 관리 : 신규 프로젝트 모델링에서 표준 준수율을 점검하고 변경 관리 워크플로우를 운영.
- 변경 통제 절차 : 변경 요청서(RFC) 제출 → 영향도 분석(기 구축 테이블과 인터페이스 영향 파악) → 거버넌스 위원회 심의 → 시스템 동기화 공지와 일괄 적용.

## Ⅳ. 데이터 표준 4대 요소의 비교

- 핵심 요약 : 최소 단위인 표준 단어에서 유효값 집합인 표준 코드까지, 각 요소의 역할과 관리 기준이 계층적으로 다름.

| 표준 구성 요소 | 정의 및 작성 원칙 | 구체적 예시 | 관리 기준 |
|---|---|---|---|
| 표준 단어 | 더 이상 분해되지 않는 최소 의미 단위, 동의어·유의어 정비와 금칙어 지정 | 고객(Customer), 번호(Number), 일자(Date) | 표준 영문 약어 부여(CUST, NO, DT) |
| 표준 용어 | 표준 단어를 조합해 업무적 의미를 표현 | 고객번호(CUST_NO), 가입일자(JOIN_DT) | 영문 컬럼명은 표준 단어 약어를 언더스코어로 연결 |
| 표준 도메인 | 속성의 물리 타입, 길이, 허용 범위를 묶은 틀 | 금액 도메인 NUMBER(15,2), 여부 도메인 CHAR(1) | DB별 데이터 타입 매핑 규칙 명시 |
| 표준 코드 | 속성이 가질 수 있는 값 목록의 통일된 부호 집합 | 성별코드 M/F, 주문상태코드 10/20/30 | 코드 체계 일련번호 부여, 유효 기간 관리 |

- 선택 기준 : 새로 만드는 데이터 요소는 4대 요소의 계층 규칙을 따르고, 기존 요소는 매핑 테이블로 연결해 점진적으로 편입.

## Ⅴ. 데이터 표준화의 한계와 방안

- 핵심 요약 : 레거시 강제 적용의 비용, 도메인 간 합의 지연, 수작업 검증의 한계를 점진적 적용, 도메인 계층화, 자동 검증으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 레거시 시스템과의 강제 충돌 | 수십 년간 축적된 약어·도메인·코드 체계가 달라 신규 표준을 일괄 적용하면 연계 애플리케이션 재개발과 결함이 발생 | 표준 매핑 테이블과 변환 어댑터 기반의 점진적 표준화, 신규 프로젝트에 엄격 적용하는 **Strangler Fig 패턴** | 표준 준수율, 매핑 테이블 잔존 건수 |
| 다의어·동음이의어에 따른 합의 난항 | 고객, 계좌 같은 핵심 엔티티를 부서마다 다르게 정의해 전사 단일 정의 합의가 지연 | 도메인 주도 설계(DDD, Domain-Driven Design)의 **바운디드 컨텍스트** (Bounded Context) 도입, 전사 표준과 도메인 표준의 계층화 | 용어 합의 소요 기간, 중복 정의 건수 |
| 자동 검증 부재 | 설계자의 수작업 대조에 의존해 미준수 컬럼명과 임의 약어가 빈발 | ERD(Entity-Relationship Diagram) 도구와 Git CI/CD 파이프라인의 표준 린터 연동으로 미준수 DDL 배포 차단 | 미준수 DDL 차단 건수 |

## Ⅵ. 전사 데이터 표준화 정착에 대한 기술사적 제언

- 핵심 요약 : 표준 준수의 자동 강제, 레거시 이행의 과도기 전략, 신속한 표준 승인 체계의 운영.
- 모델러의 자발적 준수에 기대지 말고, ERD 도구와 Git 훅을 연동해 미준수 DDL 커밋이 저장소에 들어오지 못하도록 CI 파이프라인에서 원천 차단하는 것이 바람직함.
- 레거시 물리 컬럼명을 한꺼번에 바꾸면 위험이 크므로, 차세대 시스템에 먼저 표준을 적용하고 뷰(View)나 CDC(Change Data Capture) 계층에서 표준 컬럼명을 노출하는 과도기 전략이 현실적임.
- 신조어와 신규 기술 용어가 계속 생기므로, 표준 신청과 승인의 처리 기한(SLA, Service Level Agreement)을 정하고 짧은 주기로 갱신하는 애자일 거버넌스를 운영하는 것이 필요함.

## Ⅶ. 결론

- 핵심 요약 : 데이터 표준화는 4대 표준 요소의 정립과 자동 검증·점진적 적용의 결합이 성공 조건인 체계.
- 시사점 : 레거시 과도기 전략과 CI 기반 표준 검증 자동화가 함께 갖춰져야 표준이 실효성을 가짐.
