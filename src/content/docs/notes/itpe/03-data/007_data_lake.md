## 지식 로드맵 내 현재 위치

자료처리·데이터 → 데이터 플랫폼 → **데이터 레이크(데이터 늪 포함)**

## 30초 인출

- 본질: 데이터 레이크는 정형·반정형·비정형 데이터를 원본에 가까운 형태로 대규모 저장하고 필요할 때 구조를 적용해 분석하는 저장소
- 메커니즘: 원천 데이터를 원본 영역에 적재하고 정제·가공 영역으로 단계적으로 옮기며 메타데이터 카탈로그가 데이터의 의미·위치·소유자를 관리
- 통찰: 메타데이터와 품질·권한 관리 없이 데이터를 쌓기만 하면 찾고 믿을 수 없는 데이터 늪이 되므로 적재 시점에 카탈로그 등록과 책임자를 필수로 지정

<details>
<summary>핵심 용어</summary>

- **데이터 레이크(Data Lake)** : 다양한 형태의 데이터를 원본에 가깝게 대규모로 저장하는 저장소
- **읽기 시점 스키마(Schema-on-Read)** : 저장할 때가 아니라 읽을 때 구조를 적용하는 방식
- **원본 영역(Raw Zone)** : 수집한 데이터를 원본에 가깝게 보관하는 영역
- **메타데이터 카탈로그** : 데이터의 의미·위치·소유자·형식·이용 조건을 관리하는 목록
- **데이터 계보(Lineage)** : 데이터가 가공·제공되기까지의 흐름과 이력
- **데이터 늪(Data Swamp)** : 관리 부족으로 데이터를 찾거나 믿을 수 없게 된 레이크
- **레이크하우스(Lakehouse)** : 레이크의 저장 유연성에 웨어하우스의 관리·트랜잭션 기능을 결합한 구조

</details>

## 2~4교시 25점 답안

## Ⅰ. 데이터 레이크의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **데이터 레이크** 는 다양한 형태의 데이터를 원본에 가깝게 대규모로 저장하는 저장소 |
| 목적 | 데이터의 통합 저장과 분석·AI 활용 유연성 확보 |

## Ⅱ. 데이터 웨어하우스와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 원본 보존 | 가공 전 형태로 저장 |
| 읽기 시점 스키마 | 사용 시 구조 적용 |
| 다양한 형태 | 정형·반정형·비정형 수용 |
| 낮은 저장 비용 | 확장성 있는 저장소 활용 |

## Ⅲ. 아키텍처

```text
원천(DB·로그·파일·IoT)
        ↓ 수집
   ┌────────── 데이터 레이크 ──────────┐
   │ 원본 영역 → 정제 영역 → 활용 영역   │  ← 메타데이터 카탈로그
   └────────────────────────────────────┘     · 계보 · 접근 통제
        ↓
분석·BI·AI 활용
```

## Ⅳ. 데이터 늪의 원인과 웨어하우스와의 비교

### 데이터 늪의 발생 원인

| 원인 | 내용 |
|---|---|
| 메타데이터 부재 | 어떤 데이터인지 알 수 없음 |
| 품질 관리 부재 | 중복·오류 데이터 축적 |
| 책임자 부재 | 갱신·폐기 주체 없음 |
| 접근 통제 부재 | 보안·개인정보 위험 |

### 데이터 웨어하우스와의 비교

| 구분 | 데이터 웨어하우스 | 데이터 레이크 |
|---|---|---|
| 데이터 형태 | 정형 중심 | 정형·반정형·비정형 |
| 스키마 | 저장 시 적용 | 읽기 시점 |
| 목적 | 정형 분석·보고 | 탐색·AI·다양한 분석 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 메타데이터 없이 적재해 데이터를 찾지 못함 | 적재 시 카탈로그 등록을 필수화 |
| 품질·중복 데이터 축적 | 영역별 품질 검사와 폐기 정책 |
| 접근 통제 미흡 | 영역·데이터 등급별 권한 관리 |

## Ⅵ. 제언

데이터 적재 시 카탈로그 등록·책임자 지정·품질 등급 부여를 필수 절차로 두어 데이터 늪 방지

```text
적재 요청 → 카탈로그 등록 · 책임자 지정 · 등급 부여 → 통과 시 적재, 미통과 시 반려
```

| 구분 | 자유 적재 | 제언: 등록 필수 |
|---|---|---|
| 검색성 | 낮음 | 카탈로그로 검색 |
| 품질 | 방치 | 책임자가 관리 |
