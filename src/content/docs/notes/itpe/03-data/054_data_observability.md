## 연관 키워드

- 데이터 옵저버빌리티(Data Observability), 데이터 다운타임(Data Downtime), DataOps, 데이터 계약(Data Contract)
- 최신성(Freshness), 분포(Distribution), 볼륨(Volume), 스키마(Schema), 리니지(Lineage), 회로 차단기(Circuit Breaker)

## Ⅰ. 데이터 옵저버빌리티의 개요

- 핵심 요약 : 데이터 파이프라인의 상태를 지속 관찰해 데이터 결함을 조기에 격리하는 운영 체계.
- 개념 : 데이터 파이프라인 전반의 최신성·품질·신뢰성을 지속 모니터링·추적·진단하여 데이터 결함을 사전에 감지하고 원인을 신속히 찾는 활동 및 기술 체계 (**데이터 옵저버빌리티** (Data Observability)).
- 배경 및 필요성 : 배치 성공 여부만 확인하는 모니터링은 데이터 내용의 오류를 놓쳐 오염 데이터가 하류 보고서와 의사결정으로 확산되는 비용을 키우므로, 데이터의 내용과 맥락을 감시하는 계층이 필요.
- 주요 목적 : DataOps 체계 안에서 **데이터 다운타임** (Data Downtime)을 줄이고 데이터 신뢰성을 확보.

## Ⅱ. 데이터 옵저버빌리티의 특징 및 장점

- 핵심 요약 : 실행 여부 감시를 넘어 데이터 내용·맥락·계보를 함께 감시하여 결함의 확산을 줄이는 방식.

1. 내용 중심 감시 : 적재 데이터의 행 수·스키마·값 분포를 점검 → 배치가 성공해도 잘못된 데이터를 걸러냄.
2. 사전 감지 : 결함이 하류로 확산되기 전에 이상을 경보 → 피해 범위 축소.
3. 근본 원인 분석 : **데이터 리니지** (Data Lineage, 원천부터 소비까지 데이터의 이동·변환 경로)를 따라 오염원을 추적 → 복구 시간 단축.
4. 다면 감시 : 최신성·분포·볼륨·스키마·리니지의 다섯 항목을 함께 점검 → 결함 유형별 탐지 누락 감소.
5. 자동화 지향 : 메타데이터를 활용한 수집과 이상탐지를 자동 운영 → 사람의 상시 점검 부담 감소.

## Ⅲ. 데이터 옵저버빌리티의 구조 (흐름)

- 핵심 요약 : 메타데이터 수집부터 이상 점수 산출, 경보, 원인 격리까지 이어지는 자동화 흐름.

```text
[데이터 파이프라인 실행]
          ↓
[메타데이터 수집 (OpenLineage 등)]
          ↓
[기둥별 이상 점수 산출]
          ↓
[경보 발송 (Slack, PagerDuty 등)]
          ↓
[리니지 따라 원인 격리·복구]
```

| 감시 항목 | 점검 내용 | 결함 시 위험 시나리오 |
| --- | --- | --- |
| 최신성(Freshness) | 마지막 적재 시점과 SLA(Service Level Agreement) 간 지연 | 실시간 대시보드에 전일 데이터 노출 |
| 분포(Distribution) | 컬럼별 결측률·평균·백분위수·유효값 범위 | 가격 컬럼에 음수 유입 |
| 볼륨(Volume) | 적재 레코드 수의 급증·급감 | 원천 시스템 장애로 결제 건 누락 적재 |
| 스키마(Schema) | 컬럼 추가·삭제·타입 변경 감지 | 다운스트림 BI(Business Intelligence) 쿼리 오류 |
| 리니지(Lineage) | 원천부터 최종 마트까지의 흐름 추적 | 오염된 보고서의 영향 범위 파악 불가 |

## Ⅳ. 기존 데이터 모니터링과의 비교

- 핵심 요약 : 시스템 실행 여부 중심의 감시에서 데이터 내용·맥락·계보 중심의 감시로 전환.

| 비교 항목 | 기존 데이터 모니터링 | 데이터 옵저버빌리티 |
| --- | --- | --- |
| 감시 초점 | 배치 잡의 실행 성공·실패 | 데이터 내용과 맥락의 정상성 |
| 감지 시점 | 장애 발생 후 사후 확인 | 결함 확산 이전 사전 감지 |
| 원인 분석 | 로그 수동 조회 | 리니지 기반 원인 추적 |
| 대표 도구 | 워크플로 스케줄러 알림 | Monte Carlo, Databand, Bigeye 등 |

- 솔루션 구분 : 상용 플랫폼은 Monte Carlo, Databand(IBM 제품), Bigeye가 있고, 오픈소스는 Elementary(dbt 기반), Great Expectations, Soda Core, OpenLineage(리니지 오픈 규격)가 있다.

## Ⅴ. 데이터 옵저버빌리티의 한계와 방안

- 핵심 요약 : 조기 감지의 장점은 연산 부담, 오경보, 리니지 단절의 한계와 함께 관리해야 함.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 연산 오버헤드 | 전 데이터셋의 5대 기둥 전수 검증 → DW(Data Warehouse) 쿼리 자원 고갈과 비용 증가 | 통계적 샘플링 기반 프로파일링, 정보 스키마 등 메타데이터의 무부하 추출 | 파이프라인 지연, 검증 비용 |
| 오경보 피로(Alert Fatigue) | 고정 임계치가 요일·이벤트성 변동을 반영하지 못함 → 온콜 피로 누적과 실제 장애 간과 | 시계열 이상탐지(Prophet, Isolation Forest 등)에 기반한 동적 임계치 운영 | 오경보율, 경보당 조치 시간 |
| 리니지 파편화 | dbt, Airflow, Spark, 프로시저가 섞인 파이프라인에서 컬럼 레벨 리니지 단절 | 오픈 규격(OpenLineage) 채택, SQL(Structured Query Language) 파서 기반 AST(Abstract Syntax Tree) 분석으로 컬럼 리니지 통합 | 리니지 커버리지율 |

```text
[고정 임계치 경보]
          ↓ 요일·이벤트 변동 미반영
[오경보 누적·온콜 피로]
          ↓
[동적 임계치와 지속 조건 적용]
```

## Ⅵ. 데이터 옵저버빌리티에 대한 기술사적 제언

- 핵심 요약 : 데이터 계약으로 결함을 원천에서 막고, 회로 차단기식 자동 격리를 병행하는 것이 바람직함.
- 원천 시스템과 데이터 팀이 **데이터 계약** (Data Contract)을 체결하고, 스키마 변경을 CI(Continuous Integration)/CD(Continuous Delivery) 단계의 린터 검증으로 걸러 무통보 변경을 막는다.
- 품질 게이트에서 볼륨·최신성 이상이 확인되면 오염 데이터의 Gold 마트 유입을 **회로 차단기** (Circuit Breaker) 로직으로 차단하고 파이프라인을 자동 일시 중지한다.
- 리니지와 계약 규격은 OpenLineage처럼 공개 표준을 우선 채택해 특정 벤더에 종속되지 않도록 한다.

## Ⅶ. 결론

- 핵심 요약 : 데이터 옵저버빌리티는 내용과 계보를 감시해 데이터 다운타임을 줄이는 데이터 운영 체계.
- 시사점 : 품질은 사후 탐지보다 계약과 감시를 함께 설계할 때 확보되므로, 두 축을 나란히 두는 것이 핵심이다.
