## Ⅰ. 운영체제와 스토리지의 기본 추상화, 파일 시스템 데이터 관리 개요

### 가. 파일 시스템(File System)의 정의
- 운영체제(OS)가 보조기억장치(HDD, SSD, 플래시 메모리) 상에 파일(File)이라는 논리적 단위로 데이터를 구조화하여 저장, 색인, 검색, 접근 제어, 무결성을 유지할 수 있도록 지원하는 시스템 소프트웨어 계층.
- 데이터베이스 관리 시스템(DBMS)이 물리적 디스크에 테이블스페이스와 데이터 파일을 영속화하는 하부 기반 인프라.

---

## Ⅱ. 파일 시스템 디스크 할당(Allocation) 방식 3가지

```text
[ 3대 디스크 블록 할당 기법 ]
(A) 연속 할당 (Contiguous) : 연속된 블록에 순차 저장 -> 순차 탐색 극상 / 외부 단편화 심각
(B) 연결 할당 (Linked)     : 각 블록 끝에 다음 블록 포인터 저장 -> 단편화 해결 / 직접 접근 불가
(C) 색인 할당 (Indexed)    : 전용 색인 블록(i-node)에 모든 데이터 블록 주소를 모아 관리 -> 현대 표준!
```

| 할당 방식 | 동작 메커니즘 | 장점 | 치명적 단점 |
| :--- | :--- | :--- | :--- |
| **연속 할당 (Contiguous)** | 디스크의 물리적으로 연속된 블록들에 파일을 통째로 할당 | 순차 I/O 속도 극상, 디스크 헤드 이동 최소화 | 파일 생성 시 크기 예측 불가, 디스크 빈 공간 조각화(외부 단편화) 발생 |
| **연결 할당 (Linked)** | 블록들을 포인터로 연결 리스트처럼 연결 (FAT 파일시스템) | 외부 단편화 완전 해결, 파일 크기 동적 확장 | 특정 위치 직접 접근(Random Access) 불가 ($O(N)$ 탐색), 포인터 파손 시 파일 유실 |
| **색인 할당 (Indexed)** | 각 파일마다 **색인 블록(Index Block / i-node)** 을 두어 모든 포인터 집중 관리 | 직접 접근과 순차 접근 모두 고속 지원 (현대 Linux Ext4, XFS 표준) | 작은 파일도 색인 블록을 추가 소모하여 공간 오버헤드 발생 |

## Ⅲ. 유닉스/리눅스 i-node 다계층 색인 구조

```text
[ 리눅스 i-node 구조도 ]
[i-node 메타데이터: 소유자, 권한, 크기, 시간]
  |
  +---> 직접 블록 (Direct Blocks 0~11)       ---> 실제 데이터 블록 (수십 KB 고속 접근)
  +---> 단일 간접 (Single Indirect Block)     ---> 포인터 블록 1개 거쳐 데이터 블록 접근
  +---> 이중 간접 (Double Indirect Block)     ---> 포인터 블록 2단계 계층 접근
  +---> 삼중 간접 (Triple Indirect Block)     ---> 테라~페타바이트급 거대 파일 지원!
```

## Ⅳ. 파일 시스템 데이터 관리의 주요 한계점 및 해결 방안

- **할당 방식(연속/연결/색인)에 따른 단편화 및 I/O 성능 트레이드오프** :
  - **한계점** : 연속 할당은 외부 단편화가 심각하고 파일 크기 확장이 불가능하며, 연결/색인 할당은 포인터 추적에 따른 다단계 디스크 탐색(Seek) 오버헤드 발생.
  - **해결 방안** : 익스텐트(Extent) 기반 할당(ext4, XFS) 채택으로 연속 공간과 유연성 동시 확보, 파일 시스템 디프래그먼테이션(Defrag) 정기 스케줄링.
- **갑작스러운 정전 및 시스템 크래시 시 메타데이터 불일치** :
  - **한계점** : 디렉터리 수정 및 i-node 갱신 도중 비정상 종료 시 고아 블록(Orphan Block) 및 파일 손상이 발생하여 부팅 시 긴 fsck 복구 시간 소요.
  - **해결 방안** : 저널링(Journaling: JBD2) 파일 시스템 적용(Ordered/Journal 모드), CoW(Copy-on-Write) 기반 차세대 파일 시스템(ZFS, Btrfs) 도입.
- **수백만 개의 소용량 파일(Small Files) 집중에 따른 i-node 고갈 및 룩업 병목** :
  - **한계점** : 디스크 용량이 남아있어도 i-node가 100% 소진되어 신규 파일 생성이 중단되거나, 단일 디렉터리 내 수십만 파일 존재 시 선형 검색으로 인한 심각한 지연.
  - **해결 방안** : 디렉터리 인덱싱(dir_index: HTree 기반 B-Tree) 활성화, 소용량 파일을 단일 아카이브로 병합 보관, 객체 스토리지(S3)로의 아카이빙.

## Ⅴ. 고성능 DBMS 스토리지를 위한 실무 제언

- **DBMS 데이터 파일에 최적화된 파일시스템 선정** : 고성능 RDBMS(Oracle, PostgreSQL) 적재용 스토리지로는 Ext4보다 대용량 병렬 I/O 처리와 확장성(Scalability)이 탁월하고 저널링 지연이 적은 **XFS** 파일시스템을 채택하는 것이 표준임.
- **Direct I/O(O_DIRECT) 활성화** : OS 파일시스템이 자체적으로 수행하는 페이지 캐시(Page Cache)와 DBMS의 자체 버퍼 풀(Buffer Pool)이 동일 데이터를 이중으로 메모리에 복사하는 '이중 버퍼링(Double Buffering)' 오버헤드를 배제하기 위해, DBMS 파라미터에서 OS 캐시를 우회하여 디스크에 직접 읽고 쓰는 Direct I/O를 필수 활성화할 것을 제언함.
