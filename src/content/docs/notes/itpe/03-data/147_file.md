## 한 줄 본질
- 데이터를 운영체제의 디스크 블록에 바이트/레코드 단위로 직접 저장하는 원시적 방식 → 구조가 단순하고 가벼워 순차 I/O가 빠름 / 다중 사용자 동시성 제어 불가 및 애플리케이션 종속성 발생

## 핵심 그림
```text
[파일의 3대 구조적 조직 방식(순차, 직접, ISAM) 비교]

  [1. 순차 파일 (Sequential)]       [2. 직접 파일 (Direct/Random)]
   - 물리적 연속 공간에 차례대로 적재 - 키 값을 해시 함수에 넣어 주소 계산
   ┌────┬────┬────┬────┐              ┌───────────────────────────┐
   │Rec1│Rec2│Rec3│Rec4│              │ Key ──► Hash() ──► 주소 #7│
   └────┴────┴────┴────┘              └───────────────────────────┘
   (일괄 배치 처리에 최적)            (랜덤 직접 접근 $O(1)$)

  [3. 색인 순차 파일 (ISAM: Indexed Sequential Access Method)]
   - 인덱스 블록을 거쳐 순차 데이터 블록으로 접근 (B-Tree의 원형)
   ┌──────────────┐     ┌─────────────────────────────────────────┐
   │ 인덱스 영역  │────►│ 기본 데이터 영역 (정렬된 순차 레코드)   │
   └──────────────┘     ├─────────────────────────────────────────┤
                        │ 오버플로우 영역 (추가 레코드 체인 연결) │
                        └─────────────────────────────────────────┘
```

## 핵심 용어
- ISAM(Indexed Sequential Access Method): 레코드를 키 순서대로 물리 디스크에 정렬하여 순차 접근을 지원하는 동시에, 별도의 인덱스 영역을 두어 랜덤 접근까지 지원하는 고전적 파일 조직 방식
- 데이터 종속성(Data Dependency): 데이터의 물리적 저장 구조나 포맷이 변경되면, 이를 읽고 쓰는 응용 프로그램의 소스코드까지 함께 수정되어야 하는 강한 결합 현상

## 핵심 통찰
- 파일 시스템의 가장 치명적인 문제는 '동시성(Concurrency)과 무결성(Integrity)'임 → 두 프로세스가 동일한 텍스트 파일의 서로 다른 줄을 동시에 수정하면 파일 전체가 깨져버리거나 마지막 쓰기가 이전 쓰기를 덮어버림
- 하지만 파일이 완전히 사라진 것은 아님 → 현대 빅데이터의 데이터 레이크(HDFS, S3)는 여전히 Parquet, ORC, CSV 같은 '파일' 단위로 페타바이트급 데이터를 저장하며, 하부의 단순한 파일 위에 고도화된 쿼리 엔진(Spark, Trino)을 얹는 구조로 회귀
- 고성능 로그 수집(Kafka)의 밑바닥 역시 DBMS가 아닌 OS 파일 시스템의 '순차 쓰기(Sequential Append-only)와 페이지 캐시'를 직접 활용하여 극적인 I/O 성능을 달성함

## 이웃 토픽과 구분
- 파일 시스템 vs DBMS: 파일 시스템 = 데이터의 내용이나 의미를 모른 채 단순히 바이트 블록으로 저장(OS 레벨) / DBMS = 데이터의 논리적 스키마, 제약조건, 관계, ACID 트랜잭션을 엔진이 보장(미들웨어 계층)

- 적용 상황: 결제 로그를 로컬 서버의 텍스트 파일로 직접 기록하던 레거시 시스템의 결손 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 멀티 스레드 결제 환경에서 로그 파일 쓰기 경합으로 로그 라인이 깨지고 유실 | 파일 I/O 레벨의 원자적 동시성 제어 부재 및 버퍼 플러시 충돌 | 파일 직접 쓰기를 폐지하고 카프카(Kafka) 기반 로그 큐로 전환 | 로그 유실 0% 달성 및 비동기 처리 분리 |

## 이렇게 출제된다
- 제130회: "데이터 관리 방식인 파일 시스템(File System)의 구조적 유형(순차 파일, 직접 파일, 색인 순차 파일)의 특징과 장단점을 비교하고, 파일 시스템이 가진 한계점과 이를 극복하기 위한 DBMS의 등장 배경을 설명하시오." → 요구 포인트: 3대 파일 조직 방식 도식 및 비교 + 데이터 종속성/중복성 문제점 + DBMS의 4대 해결책

## 내 의견
- [적재적소의 파일-DB 하이브리드 아키텍처 수립] 대용량 첨부파일이나 비정형 이미지를 무리하게 RDBMS의 BLOB 컬럼에 넣어 DB 용량과 백업 시간을 폭증시키는 설계 오류 빈발 → 나라면: 정형 트랜잭션 메타데이터만 RDBMS에 보관하고, 대용량 파일 실체는 S3/Ceph 같은 클라우드 객체 스토리지(Object Storage)에 저장한 뒤 파일의 URI만 DB에 매핑하는 관심사 분리 아키텍처 표준화
