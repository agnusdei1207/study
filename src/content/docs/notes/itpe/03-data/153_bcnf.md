## Ⅰ. 제3정규형을 뛰어넘는 엄격한 정규형, BCNF의 개요

### 가. BCNF(Boyce-Codd Normal Form)의 정의
- 제3정규형(3NF, Third Normal Form)을 만족하면서도 복수의 **후보키** (Candidate Key)가 존재하고 이들이 서로 중첩될 때 발생하는 잔여 이상 현상을 해결하기 위해, 릴레이션에 존재하는 모든 **결정자** (Determinant)가 반드시 후보키(Candidate Key)가 되도록 강제 하는 정규화 이론.
- 레이먼드 보이스(Raymond Boyce)와 에드가 커드(E.F. Codd)에 의해 제안된 **강한 제3정규형** (Strong 3NF).

---

## Ⅱ. 3NF 만족 상태에서 BCNF 위반 사례 및 이상 현상

### 가. BCNF 위반 릴레이션의 전형적 조건
1. 릴레이션이 복수의 후보키를 가짐.
2. 후보키들이 2개 이상의 속성으로 구성된 **복합키** (Composite Key)임.
3. 후보키의 속성들이 서로 일부 겹쳐 있음(Overlapping).
4. 후보키가 아닌 일반 속성이 후보키의 일부 속성을 결정하는 비사소한 함수 종속성 존재.

### 나. 클래식 위반 사례: 수강지도 (학번, 과목, 담당교수)

```text
[ 수강지도 릴레이션의 함수적 종속성 (FD) ]
- 조건 1: 한 학생(학번)은 여러 과목을 수강할 수 있다.
- 조건 2: 한 과목은 여러 교수가 강의할 수 있으나, 한 교수는 오직 한 과목만 담당한다!
  FD 1: (학번, 과목) -> 담당교수  <--- 기본키 (후보키 1)
  FD 2: (학번, 담당교수) -> 과목  <--- 대체키 (후보키 2)
  FD 3: 담당교수 -> 과목          <--- 결정자(교수)가 후보키가 아님! (BCNF 위반)
```

```text
[ 수강지도 릴레이션 인스턴스 ]
  학번  |  과목  | 담당교수
  ------+--------+----------
  1001  | 데이터 | 김교수
  1002  | 데이터 | 김교수
  1003  | 보안   | 박교수
```

### 다. 3대 이상 현상 발생 분석
- **삽입 이상** : 최교수가 신규 부임하여 '인공지능' 과목을 담당하게 되었으나, 아직 수강 신청한 학생(학번)이 없어 학번이 NULL이 되므로 개체 무결성에 의해 등록 불가.
- **삭제 이상** : 1003번 학생이 '보안' 과목을 수강 취소하여 해당 레코드를 삭제하면, 박교수가 보안 과목을 담당한다는 정보까지 연쇄 유실됨.
- **수정 이상** : 김교수의 담당 과목이 변경될 때, 김교수를 듣는 수많은 학생 레코드 중 일부만 변경하면 데이터 모순 발생.

## Ⅲ. BCNF 무손실 분해 및 종속성 보존(Dependency Preservation)의 트레이드오프

### 가. BCNF 분해 결과

```text
[ BCNF 무손실 분해 ]
원본: 수강지도(학번, 과목, 담당교수)
       |
       +---> R1 (담당교수, 과목) : 담당교수가 PK (결정자=후보키 만족!)
       +---> R2 (학번, 담당교수) : (학번, 담당교수)가 PK (만족!)
```

### 나. BCNF의 딜레마: 함수 종속성 미보존
- 분해 결과 모든 이상 현상은 완벽히 해결되고 무손실 조인($R_1 \bowtie R_2$)도 성립하지만, 원래 존재하던 `(학번, 과목) -> 담당교수`라는 함수 종속성을 단일 테이블 내에서 검증할 수 없게 됨 (종속성 상실).
- 새로운 수강 신청 시 학생이 이미 해당 과목을 신청했는지 확인하려면 반드시 두 테이블을 조인해야 하는 부하 발생.

## Ⅳ. BCNF(보이스-코드 정규형)의 주요 한계점 및 해결 방안

- BCNF(Boyce-Codd Normal Form) 무손실 분해 시 함수적 **종속성 보존** (Dependency Preservation)의 실패 :
  - 한계점 : 3NF를 BCNF로 분해하는 과정에서 모든 결정자가 후보키가 되도록 쪼개면, 기존의 유효한 함수적 종속성($X \to Y$)이 보존되지 못하는 구조적 딜레마 발생.
  - 해결 방안 : 종속성 보존이 필수적인 비즈니스 규칙인 경우 3NF 상태를 유지하고 무결성은 데이터베이스 트리거나 애플리케이션 트랜잭션 로직에서 강제 보완.
- 테이블 분할 증가에 따른 조인(Join) 오버헤드 및 쿼리 복잡성 증가 :
  - 한계점 : 결정자가 후보키가 아니라는 이유로 세부 테이블로 분해할수록 일상적인 SELECT 질의에서 다단계 조인이 불가피하여 응답 지연 발생.
  - 해결 방안 : 조회 빈도가 압도적으로 높은 읽기 집약적(Read-intensive) 시스템에서는 성능을 위해 3NF 유지 또는 의도적 **반정규화** (Denormalization) 허용.
- 후보키 판별의 모호성과 복합 키 설계 복잡성 :
  - 한계점 : 실무 데이터 모델링에서 복합 속성 간의 상호 종속 관계를 정확히 식별하지 못해 BCNF 위반 상태를 간과하거나 잘못된 키 분해로 데이터 이상 현상 유발.
  - 해결 방안 : **암스트롱 공리** 기반의 **종속성 폐포** (Closure) 자동 계산 알고리즘 활용, 전문 모델러 중심의 도메인 업무 규칙 교차 검증.

## Ⅴ. 데이터 모델링 실무 제언

- 3NF vs BCNF 선택의 실무 가이드라인 : 함수 종속성을 보존하는 것이 무결성 유지에 필수적인 도메인에서는 무리하게 BCNF로 쪼개지 말고 3NF 상태를 유지한 채 애플리케이션이나 복합 인덱스 제약으로 방어 하는 것이 정석임.
- BCNF 분해 시 **외래키 인덱스** 필수화 : BCNF로 분해하여 정규화를 완성한 경우, 조인 성능 저하를 방지하기 위해 분해된 테이블의 연결 고리 속성(`담당교수`)에 반드시 B-Tree 인덱스를 생성해 둘 것을 제언함.
