## 답안 골격
```text
[정규화] ◀━━ 머리: Ⅶ 내 의견 (논리 설계 시 3NF/BCNF 완벽 달성 → 성능 검증 후 통제된 반정규화 절차 이행)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터 중복으로 인한 이상현상(삽입·삭제·갱신) 제거 → 무손실 분해를 통해 릴레이션을 분리하는 과정
 ┣━ Ⅱ 특징 ───── 데이터 중복 최소화 · 무손실 조인 보장 · 종속성 보존 · 함수적 종속성(FD) 기반
 ┣━ Ⅲ 구조 ───── 1NF(원자값) → 2NF(부분함수종속 제거) → 3NF(이행함수종속 제거) → BCNF(결정자 후보키) → 4NF(다치종속) → 5NF(조인종속)
 ┣━ Ⅳ 흐름 ───── ① 비정규 릴레이션 → ② 도메인 원자화(1NF) → ③ 완전 함수종속화(2NF) → ④ 이행종속 분리(3NF) → ⑤ 모든 결정자 후보키화(BCNF)
 ┣━ Ⅴ 비교 ───── 이상현상 3가지 (삽입 이상 vs 삭제 이상 vs 갱신 이상)
 ┗━ Ⅵ 실무 ───── 과도한 분해로 인한 조인 성능 저하 / 테이블 개수 급증에 따른 쿼리 복잡도 증가
```
- 필수 키워드: 함수적 종속성(FD) · 무손실 분해 · 삽입/삭제/갱신 이상 · 1NF~BCNF · 완전 함수적 종속 · 이행적 함수 종속
- 배점 전략: 10점 = Ⅰ → Ⅲ 1NF~BCNF 단계별 분해 기준 표 → Ⅵ 한 행 / 25점 = Ⅰ~Ⅶ, 앞 1/3에 Ⅲ 정규화 단계별 도식 및 수강테이블 변환 사례
- 기출: 129회 `이상현상과 정규화(수강테이블)` → 이상현상 원인 + 단계별 정규화 수행 과정 / 125회 `정규화와 역정규화` → Ⅴ 두 개념 비교

## 한 줄 본질
- 잘못 설계된 테이블 내의 함수적 종속성 혼재로 발생하는 삽입·삭제·갱신 이상 → 관계를 무손실 분해하여 하나의 테이블에 하나의 사실(One Fact in One Place)만 저장 → 데이터 무결성 보장 / 다중 조인에 따른 조회 성능 저하

## 핵심 그림
```text
[정규화 단계별 핵심 종속성 제거 기준]

 [비정규 릴레이션]
       │
       ▼ (원자값이 아닌 다중값/반복그룹 제거)
    [ 1NF ] : 모든 속성의 도메인이 원자값(Atomic Value)
       │
       ▼ (기본키의 진부분집합에 종속되는 부분 함수 종속 제거)
    [ 2NF ] : 기본키에 대한 완전 함수적 종속(Full FD)
       │
       ▼ (A -> B, B -> C 형태의 이행적 함수 종속 제거)
    [ 3NF ] : 기본키가 아닌 일반 속성 간의 이행 종속 배제
       │
       ▼ (모든 결정자가 후보키(Candidate Key)가 되도록 분해)
   [ BCNF ] : 강한 제3정규형
```

## 핵심 용어
- 함수적 종속성(Functional Dependency, $X \rightarrow Y$): 속성 $X$의 값이 속성 $Y$의 값을 유일하게 결정하는 관계
- 이행적 함수 종속($X \rightarrow Y$ 이고 $Y \rightarrow Z$ 일 때 $X \rightarrow Z$): 기본키 $X$를 통해 $Y$를 알고, $Y$를 통해 $Z$를 알게 되는 꼬리물기 종속 관계

## 핵심 통찰
- 정규화의 핵심은 '테이블을 쪼개는 기술'이 아니라 '종속성을 제자리에 찾아주는 기술'임 → 관련 없는 속성들을 한 테이블에 억지로 모아두면 한 데이터를 지울 때 다른 중요 데이터까지 함께 날아가는 삭제 이상 발생
- 3NF와 BCNF의 차이는 '결정자가 후보키가 아닌 경우'에 발생 → 복합키 중 일부가 다른 일반 속성에 종속될 때 BCNF 위배가 생김
- 정규화는 '무손실 분해(Lossless Decomposition)'여야 함 → 분해된 테이블들을 자연 조인(Natural Join)했을 때 원래 테이블과 완전히 같아야 하며, 가짜 데이터(Spurious Tuple)가 생겨서는 안 됨

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 암스트롱의 공리(Armstrong's Axioms) | 함수적 종속성 유도 규칙 | 반사의 법칙, 증강의 법칙, 이행의 법칙을 통해 모든 종속성 집합 도출 |
| 다치 종속(MVD)과 4NF | 고급 정규화 | $A \rightarrow\rightarrow B$ 형태의 다치 종속이 존재할 때 독립적인 두 속성을 별도 분해 |

## 이웃 토픽과 구분
- 3NF vs BCNF: 3NF = $X \rightarrow Y$에서 $X$가 슈퍼키이거나 $Y$가 주속성(Primary Attribute)이면 허용 / BCNF = $Y$가 주속성이더라도 $X$가 반드시 슈퍼키여야만 허용하는 엄격한 기준

## 문제·원인·대책
- 적용 상황: 학생-과목-교수 수강신청 테이블 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 학생이 수강을 취소했을 뿐인데 담당 교수의 학과 정보까지 DB에서 영구 삭제 (삭제 이상) | 학생번호(PK)에 교수이름이 종속되고, 교수이름에 교과목/학과가 종속 (이행 종속) | 3NF 적용: 수강(학번, 과목코드)과 과목-교수(과목코드, 교수ID, 학과)로 분리 | 수강 취소해도 과목 정보 보존 |
| 신설 과목을 개설하려 하나 수강 신청한 학생이 없어 과목 등록 불가 (삽입 이상) | 학생번호가 복합 기본키의 일부여서 PK NOT NULL 제약 위배 | 2NF/3NF 분해로 과목 자체를 단독 엔티티 테이블로 독립 | 수강생 없이도 신규 과목 개설 가능 |

## 이렇게 출제된다
- 제129회 4교시 2번: "데이터베이스에서 정규화는 이상현상(Anomaly)이 있는 릴레이션(Relation)을 해결하기 위한 방법이다. 다음의 <수강테이블>을 활용하여" → 요구 포인트: 이상현상 3가지 개념 + 1NF부터 3NF까지 실제 테이블 스키마 분해 과정 제시
- 제125회 1교시 6번: "관계형 데이터베이스의 정규화와 역정규화" → 요구 포인트: 정규화의 목적과 단계 + 역정규화와의 트레이드오프

## 내 의견
- [조인 걱정으로 인한 조기 반정규화의 폐해] 초보 설계자가 "나중에 조인하면 느려진다"는 막연한 불안감으로 2NF 상태에서 설계를 끝내 갱신 이상으로 데이터 오염 발생 → 나라면: 논리 데이터 모델링 단계에서는 예외 없이 BCNF까지 완전히 정규화하여 개념적 무결성을 완성하고, 이후 부하 테스트와 슬로우 쿼리 분석을 거쳐 명확한 병목이 확인된 지점만 반정규화 수행

## 찾아볼 것
- 무손실 조인 분해와 종속성 보존(Dependency Preservation)을 동시에 만족하는 정규화 상한선(3NF는 항상 보장, BCNF는 종속성 보존이 안 될 수 있음)
