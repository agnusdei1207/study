## Ⅰ. 관계형 데이터베이스 설계의 근간인 정규화(Normalization) 개요

### 가. 정규화의 정의
- **정규화** : 관계형 데이터베이스 설계에서 중복 데이터(Data Redundancy)를 최소화하고, 함수적 종속성(Functional Dependency)을 기반으로 테이블을 논리적으로 분해하여 데이터 이상 현상(Anomaly)을 원천 방지하는 프로세스.
- 에드가 F. 커드(E.F. Codd)에 의해 제안된 무손실 분해(Lossless Decomposition)와 종속성 보존(Dependency Preservation)을 지향하는 이론적 체계.

### 나. 정규화를 수행하지 않을 때 발생하는 3대 이상 현상(Anomaly)

```text
[ 비정규화 테이블의 3대 이상 현상 ]
1. 삽입 이상 (Insertion) : 새 데이터를 등록하려 할 때 불필요한 속성값(NULL 불가)까지 강제로 입력해야 함
2. 삭제 이상 (Deletion)  : 특정 레코드를 삭제할 때 의도하지 않은 유용한 다른 정보까지 연쇄 삭제됨
3. 수정 이상 (Update)    : 중복된 데이터 중 일부만 수정되어 릴레이션 내 데이터 간 불일치(모순) 발생
```

## Ⅱ. 단계별 정규화 과정 및 함수적 종속성(FD) 전개

### 가. 기본 정규형(1NF ~ BCNF) 단계별 규칙

```text
[ 정규화 단계 요약 ]
[비정규 릴레이션]
       |
       v  (원자값이 아닌 도메인 분해)
    [ 제1정규형 (1NF) ] : 모든 속성은 원자값(Atomic Value)이어야 함
       |
       v  (부분 함수 종속성 제거)
    [ 제2정규형 (2NF) ] : 기본키의 진부분집합에 종속되는 속성 분리 (완전 함수 종속)
       |
       v  (이행적 함수 종속성 제거: X -> Y, Y -> Z)
    [ 제3정규형 (3NF) ] : 기본키가 아닌 일반 속성에 종속되는 속성 분리
       |
       v  (결정자이면서 후보키가 아닌 것 제거)
    [ BCNF (보이스-코드) ] : 모든 결정자가 후보키(Candidate Key)여야 함
```

| 정규형 | 위반 조건 및 문제 구조 | 변환 규칙 및 조치 | 해결되는 이상 현상 |
| :--- | :--- | :--- | :--- |
| **제1정규형 (1NF)** | 컬럼이 다중값(Repeating Group) 또는 복합값을 가짐 | 반복 그룹 분리, 모든 도메인을 단일 원자값으로 재구성 | 다중값으로 인한 검색 및 조작 불가 해결 |
| **제2정규형 (2NF)** | 복합 기본키(PK)의 일부분에 종속되는 속성 존재 (부분 함수 종속) | 부분 종속 컬럼들을 별도 릴레이션으로 분리 (완전 함수 종속화) | 복합키 중 일부만 알 때 발생하는 삽입/삭제 이상 |
| **제3정규형 (3NF)** | 기본키가 아닌 일반 속성에 다른 일반 속성이 종속 ($X \rightarrow Y, Y \rightarrow Z$) | 이행 종속 속성($Y \rightarrow Z$)을 별도 릴레이션으로 분리 | 일반 속성 갱신 시 발생하는 수정 이상 |
| **BCNF** | 후보키가 아닌 속성이 결정자(Determinant)로 작용 | 후보키가 아닌 결정자를 포함하는 종속 관계를 분해 | 다수의 후보키가 중첩될 때 발생하는 잔여 이상 |

### 나. 고차 정규형 (4NF, 5NF)
- **제4정규형 (4NF)** : 비사소한 다치 종속성(MVD, Multivalued Dependency $X \twoheadrightarrow Y$) 제거.
- **제5정규형 (5NF, PJNF)** : 무손실 조인 종속성(JD, Join Dependency) 제거 (프로젝션-조인 정규형).

## Ⅲ. 무손실 분해(Lossless Decomposition)와 종속성 보존 원칙

### 가. 무손실 조인 분해 조건
- 릴레이션 $R$을 $R_1, R_2$로 분해했을 때, $R_1 \bowtie R_2 = R$을 만족해야 함.
- 수학적 판정 조건 : $(R_1 \cap R_2 \rightarrow R_1)$ 또는 $(R_1 \cap R_2 \rightarrow R_2)$ 중 적어도 하나가 성립해야 함 (공통 속성이 어느 한쪽의 슈퍼키여야 함).

### 나. 종속성 보존(Dependency Preservation)의 중요성
- 분해된 릴레이션들 각각의 함수 종속성 집합의 합집합이 원래 릴레이션의 함수 종속성 집합을 모두 커버해야 함. BCNF는 종속성을 보존하지 못할 수 있어 실무에서는 3NF를 절충점으로 선택하는 경우가 많음.

## Ⅳ. 정규화 수행 시 주요 한계점 및 해결 방안

- 과도한 테이블 분해로 인한 다중 JOIN 부하 및 조회 성능 저하 :
  - 한계점 : 3NF 또는 BCNF까지 엄격히 정규화할 경우 단순 업무 조회에도 5~10개 이상의 다중 JOIN이 유발되어 인덱스 스캔 및 메모리 소트 오버헤드로 TPS 급락.
  - 해결 방안 : 워크로드 분석을 통해 조회 빈도가 극도로 높은 핵심 트랜잭션에 한해 부분적 반정규화(중복 컬럼, 집계 테이블) 적용 및 읽기 캐시(Redis) 계층화.
- 고차 정규화(BCNF, 4NF) 과정에서의 함수적 종속성(FD) 보존 실패 :
  - 한계점 : 특정 릴레이션을 BCNF로 분해할 때 기존의 모든 함수 종속성을 보존하지 못하여 INSERT/UPDATE 시 관계 간 무결성 검증을 위해 무거운 외래키 JOIN 필요.
  - 해결 방안 : 종속성 보존이 필수적인 도메인에서는 무리한 BCNF 분해 대신 3NF 수준에서 정규화를 절충(Trade-off)하고 애플리케이션 트랜잭션 로직으로 보완.
- 동적 스키마 변경 및 애자일 개발 환경에서의 모델 경직성 :
  - 한계점 : 정규화된 모델은 엄격한 참조 관계와 제약조건으로 인해 비즈니스 요구사항 변경 시 다수 테이블의 DDL 수정과 마이그레이션 다운타임 유발.
  - 해결 방안 : 반정형 속성에 대해 JSON/JSONB 하이브리드 컬럼 타입을 선별 적용하거나 유연한 NoSQL/도큐먼트 저장소를 혼용하는 Polyglot Persistence 구축.

## Ⅴ. 엔터프라이즈 데이터 모델링 실무 제언

- OLTP vs OLAP 모델링 전략의 차별화 : 트랜잭션의 정합성이 핵심인 OLTP 시스템은 원칙적으로 BCNF/3NF까지 엄격히 정규화하여 데이터 이상 현상을 방지해야 하며, 대규모 읽기 및 다차원 분석이 목적인 OLAP/DW 환경에서는 스타 스키마 형태의 의도적 역정규화를 설계해야 함.
- 과도한 정규화에 따른 성능 저하 예방 : 정규화 레벨이 높아질수록 조인(JOIN) 횟수가 증가하여 I/O 오버헤드가 발생하므로, 실무에서는 3NF를 기본 표준으로 삼고 병목 쿼리가 입증된 테이블에 한해 선별적 반정규화를 적용할 것을 제언함.
