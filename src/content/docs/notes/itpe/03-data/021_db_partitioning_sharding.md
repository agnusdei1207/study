## 연관 키워드

- 데이터베이스 분할(Partitioning), 샤딩(Sharding), 수평적 확장(Scale-Out), 파티션(Partition)
- 범위·해시·목록·복합 분할, 샤드 키(Shard Key), 안정 해싱(Consistent Hashing)
- 2단계 커밋(2PC, Two-Phase Commit), 핫스팟(Hotspot), 리밸런싱(Rebalancing)

## Ⅰ. 데이터베이스 분할·샤딩의 개요

- 핵심 요약 : 대용량 테이블을 작은 단위로 나누어 성능과 관리 효율, 확장성을 확보하는 분산 저장 기술 체계.
- 개념 : 대용량 테이블이나 인덱스를 관리·성능 목적으로 나누어 단일 DBMS(Database Management System) 인스턴스 안에서 관리하는 **데이터베이스 분할**(Partitioning).
- 개념 : 분할 개념을 네트워크 경계 너머로 넓혀, 공유 자원이 없는 여러 물리 노드에 데이터를 나누어 저장하고 처리하는 **샤딩**(Sharding). 노드를 늘려 확장하는 **수평적 확장**(Scale-Out) 아키텍처의 한 형태다.
- 배경 및 필요성 : 단일 인스턴스의 저장 용량이 한계에 닿으면 락 경합으로 처리량이 포화되고, 대형 테이블의 백업과 인덱스 재구축 비용이 커진다.
- 주요 목적 : 저장 용량과 트랜잭션 처리량을 함께 확장하고, 파티션 단위 관리 효율을 높이며, 장애 영향 범위를 줄이는 것.

## Ⅱ. 데이터베이스 분할·샤딩의 특징

- 핵심 요약 : 분할은 단일 인스턴스 안에서의 물리적 분리이고, 샤딩은 노드 사이에 데이터를 분포시키는 방식이라는 차이.

1. 분할의 범위 : 단일 OS와 인스턴스 안에서 수행 → 락 경합이 일부 남지만 운영이 단순.
2. 샤딩의 범위 : 노드 간 네트워크 분산 → 노드별 트랜잭션 격리와 확장 여지 확보, 대신 분산 운영 복잡도 증가.
3. 분할 기준 : 범위(Range), 해시(Hash), 목록(List), 복합(Composite) 4대 방식 → 데이터 특성에 맞춰 고름.
4. 샤드 라우팅 : 애플리케이션 기반, 프록시 기반, 안정 해싱 기반으로 구현 → 라우팅 책임의 위치가 달라짐.
5. 안정 해싱 : 노드를 추가하거나 제거해도 전체 키를 다시 배치하지 않고 대략 K/N(K는 키 수, N은 노드 수) 수준의 키만 옮김 → 리밸런싱 비용 최소화.

## Ⅲ. 데이터베이스 분할·샤딩의 구조 (흐름)

- 핵심 요약 : 단일 노드 안의 파티셔닝과 여러 노드에 걸친 샤딩 라우팅의 이중 구조.

```text
[ 분할과 샤딩의 범위 ]
단일 DBMS 인스턴스 → 파티셔닝
  ORDERS 테이블을 파티션 1, 2, 3으로 분할
  (단일 OS 공유, 락 경합 일부 잔존)

여러 물리 노드 → 샤딩
  노드 A(샤드 1) / 노드 B(샤드 2) / 노드 C(샤드 3)
  (네트워크 분산, 노드별 독립 저장)
```

```text
[ 샤드 라우팅 구조 ]
애플리케이션 / 클라이언트
        ↓  SQL 요청
라우터 (프록시 미들웨어)
        ↓  샤드 키 기준 분기
샤드 1 (A~M)     샤드 2 (N~Z)
```

- 애플리케이션 기반 샤딩 : 애플리케이션이 샤드 키로 연결 대상을 직접 고른다. 구조는 단순하지만 애플리케이션 복잡도가 커진다.
- 프록시 기반 샤딩 : Vitess, Apache ShardingSphere 같은 미들웨어가 SQL을 해석해 샤드로 보내고 결과를 모은다.
- 안정 해싱 기반 샤딩 : 노드 구성이 바뀌어도 키 재배치를 최소화하는 해시 링 방식으로 라우팅한다.

## Ⅳ. 4대 분할 방식의 비교

- 핵심 요약 : 데이터의 접근 패턴에 따라 범위·해시·목록·복합 분할을 고르는 전략 차이.

| 분할 방식 | 분할 기준 | 적합한 데이터 | 장점과 주의사항 |
| --- | --- | --- | --- |
| 범위 분할(Range) | 일자나 연속 수치의 값 범위 | 시계열 로그, 월별 매출, 회계 장부 | 과거 파티션 일괄 삭제(DROP PARTITION)가 쉬움 / 최신 파티션에 쓰기가 몰리는 쏠림 주의 |
| 해시 분할(Hash) | 분할 키에 해시 함수를 적용한 값 | 고객 ID, 주문 번호 같은 고유 식별자 | 노드 간 균등 분산이 쉬움 / 범위 검색(BETWEEN) 시 전체 파티션 조회 필요 |
| 목록 분할(List) | 미리 정한 이산 값(지역 코드 등) | 지역 코드, 사업부 코드 | 업무 도메인별 물리 분리가 명확 / 정의되지 않은 값의 예외 처리 필요 |
| 복합 분할(Composite) | 주 분할과 보조 분할의 결합(Range-Hash 등) | 대규모 결제·거래 데이터 | 세밀한 관리와 고른 분산을 함께 달성 / 관리 오버헤드 증가 |

## Ⅴ. 데이터베이스 분할·샤딩의 장점과 한계

- 핵심 요약 : 파티션 단위 관리와 수평 확장이 장점이며, 교차 샤드 조인, 분산 트랜잭션, 리밸런싱, 핫스팟이 한계.

- 장점
  1. 과거 이력 데이터의 일괄 삭제와 파티션 단위 백업이 용이.
  2. 데이터의 노드 간 균등 분산과 도메인별 물리 분리.
  3. 노드 증설로 저장 용량과 처리량을 함께 확장.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 교차 샤드 조인 불가 | 다른 샤드에 있는 테이블끼리 직접 조인할 수 없음 | 공통 기준 정보를 전 샤드에 복제(Global Table)하거나 애플리케이션 계층에서 결합 | 교차 샤드 질의 비율 |
| 분산 트랜잭션 오버헤드 | 2단계 커밋 적용 시 네트워크 지연과 락 유지 시간 증가 | 비동기 이벤트 기반의 최종 일관성, 즉 Saga 패턴으로 전환 | 트랜잭션 지연 시간, 보상 처리 건수 |
| 샤드 리밸런싱 부담 | 트래픽 급증 시 노드를 나누며 무중단 데이터 이동 필요 | CDC(Change Data Capture) 기반 무중단 마이그레이션 도구 사용 | 이동 중 지연, 불일치 건수 |
| 핫스팟(Hotspot) 집중 | 특정 인기 키로 트래픽이 몰려 한 샤드가 포화 | 샤드 키에 솔트(Salt)를 더해 분산, 복합 샤드 키 적용 | 샤드별 요청 편차 |

## Ⅵ. 데이터베이스 분할·샤딩에 대한 기술사적 제언

- 핵심 요약 : 파티셔닝으로 충분한 구간을 먼저 해결하고 샤딩은 임계점에서 도입하며, 샤드 키는 초기 설계에서 신중히 확정.

샤딩은 운영 복잡도와 트랜잭션 관리 비용을 크게 높인다. 그러므로 수직 확장(Scale-Up), 테이블 파티셔닝, 읽기 전용 복제본(Read Replica) 분리로 해결이 어려워진 시점에 비로소 도입하는 것이 바람직하다. 임계점은 조직이 측정한 처리량과 응답 시간 지표로 판단해야 하며, 추측에 기대지 않는다.

샤드 키는 사후 변경 비용이 커서 사실상 되돌리기 어려운 결정이다. 데이터 분포의 균등성과 주요 업무 쿼리의 조건절 패턴을 분석한 뒤 초기 설계 단계에서 확정해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 분할은 관리와 성능의 1차 수단이고, 샤딩은 확장 임계점 이후에 택하는 전략적 선택.
- 시사점 : 샤드 키의 초기 검증이 대용량 데이터 플랫폼의 확장성과 운영 안정성을 좌우함.
