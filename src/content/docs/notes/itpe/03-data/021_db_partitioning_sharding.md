## Ⅰ. 대용량 데이터 분산 처리를 위한 분할·샤딩의 개요

### 가. 데이터베이스 분할(Partitioning) 및 샤딩(Sharding)의 정의
- **데이터베이스 분할(Partitioning)** : 대용량 테이블이나 인덱스를 관리적·성능적 목적을 위해 물리적으로 작은 단위의 파티션(Partition)으로 쪼개어 단일 DBMS 인스턴스 내에서 관리하는 기술.
- **데이터베이스 샤딩(Sharding)** : 데이터 분할 개념을 네트워크 경계를 넘어 복수의 독립된 물리적 데이터베이스 서버(Shared-Nothing 노드)로 확장하여 데이터를 분산 저장·처리하는 수평적 확장(Scale-Out) 아키텍처.

### 나. 분할과 샤딩의 핵심 차이점

```text
[ 단일 노드 파티셔닝 vs 분산 노드 샤딩 ]
  단일 DBMS 노드 (Partitioning)           다중 물리 노드 클러스터 (Sharding)
  +-------------------------------+      +----------+  +----------+  +----------+
  | Table: ORDERS                 |      | Shard #1 |  | Shard #2 |  | Shard #3 |
  |  Part 1 | Part 2 | Part 3    |      | (Node A) |  | (Node B) |  | (Node C) |
  +-------------------------------+      +----------+  +----------+  +----------+
    - 단일 OS/인스턴스, 락 경합 잔존        - 네트워크 분산, 트랜잭션 격리, 무제한 확장
```

## Ⅱ. 분할(Partitioning) 및 샤딩(Sharding)의 핵심 분할 전략

### 가. 4대 분할 방식 비교

| 분할 방식 | 분할 기준 및 메커니즘 | 적용에 적합한 데이터 특성 | 장점 및 주의사항 |
| :--- | :--- | :--- | :--- |
| **범위 분할 (Range)** | 특정 컬럼(일자, 연속 수치)의 연속된 값 범위를 기준으로 분할 | 시계열 로그, 월별 매출 데이터, 회계 장부 | 과거 이력 데이터의 일괄 삭제(`DROP PARTITION`) 용이 / 특정 파티션 쏠림 현상 주의 |
| **해시 분할 (Hash)** | 분할 키에 해시 함수를 적용한 해시값 모듈로 연산으로 분할 | 고객 ID, 주문 번호 등 고유 식별자 | 데이터를 노드 간 균등하게 분산 / 범위 검색(`BETWEEN`) 시 전체 파티션 스캔 필요 |
| **목록 분할 (List)** | 사전에 명시된 불연속적인 이산값(코드, 지역 등) 목록으로 분할 | 지역코드(서울, 경기, 부산), 사업부 코드 | 비즈니스 도메인별 물리 분리 명확 / 정의되지 않은 값 입력 시 예외 처리 필요 |
| **복합 분할 (Composite)** | 주 분할과 보조 분할을 결합 (예: Range-Hash, Range-List) | 대용량 글로벌 전자상거래 결제 데이터 | 세밀한 데이터 관리와 고른 성능 분산 동시 달성 / 관리 오버헤드 증가 |

### 나. 샤딩 아키텍처 및 라우팅 메커니즘

```text
[ 샤딩 라우팅 아키텍처 ]
[Client / App] ---> [Router / Shard Proxy (Vitess, Citus)]
                            |
           +----------------+----------------+
           | (Consistent Hashing or Lookup)  |
           v                                 v
     [Shard 1 (A-M)]                   [Shard 2 (N-Z)]
```

- **애플리케이션 기반 샤딩** : 애플리케이션 코드 내에서 샤드 키 기반으로 직접 커넥션 풀을 분기(단순하나 앱 복잡도 증가).
- **프록시 기반 샤딩** : 중간 미들웨어(Vitess, Apache ShardingSphere)가 SQL을 파싱하여 적절한 샤드로 라우팅하고 분산 집계를 수행.
- **안정 해싱(Consistent Hashing)** : 노드 증설/삭제 시 전체 재배치가 아닌 $K/N$ 개의 키만 재배치하여 데이터 리밸런싱 비용 최소화.

## Ⅲ. 샤딩 적용 시의 한계점·문제점 및 해결 방안

### 가. 샤딩 4대 엔지니어링 난제
1. Cross-Shard Join 불가 : 서로 다른 샤드 서버에 존재하는 테이블 간의 직접 조인이 불가능함 $\rightarrow$ 공통 기준 정보는 모든 샤드에 브로드캐스트 복제(Global Table)하거나 애플리케이션 계층에서 조인.
2. 분산 트랜잭션 오버헤드 : 2단계 커밋(2PC) 적용 시 네트워크 지연 및 락 유지 시간 증가 $\rightarrow$ 비동기 이벤트 기반 최종 일관성(Saga 패턴)으로 전환.
3. 샤드 리밸런싱(Rebalancing) : 트래픽 급증 노드 분할 시 무중단 데이터 마이그레이션 도구(CDC 기반) 필요.
4. 핫스팟(Hotspot) 문제 : 특정 유명인이나 프로모션 대상 키에 트래픽이 집중되는 경우 복합 샤드 키(Hash + Salt) 적용.

## Ⅳ. 고가용 분산 데이터베이스 구축을 위한 실무 제언

- 파티셔닝 선행 후 샤딩 검토 : 샤딩은 시스템 운영 복잡도와 트랜잭션 관리 비용을 급격히 증가시키므로, 단일 인스턴스 수직 확장(Scale-Up) 및 테이블 파티셔닝, 읽기 전용 복제본(Read Replica) 분리로 해결 불가능한 임계점(테이블 수억 건, 초당 수만 TPS)에 도달했을 때 도입해야 함.
- 샤드 키(Shard Key) 선정의 불가역성 : 한 번 지정된 샤드 키는 사후 변경 시 서비스 전체를 중단하고 데이터를 재적재해야 할 만큼 치명적이므로, 데이터 분포의 균등성과 주요 비즈니스 쿼리의 조건절 패턴을 심층 분석하여 초기 설계에 만전을 기할 것을 제언함.
