## 답안 골격
```text
[DB 분할·샤딩] ◀━━ 머리: Ⅶ 내 의견 (단일 DB 파티셔닝 우선 소진 → 쓰기 한계 시 샤드 라우터 기반 수평 샤딩 단계적 이행)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 서버 자원 한계 및 락 경합 → 물리적/논리적 분할로 디스크 I/O 분산 및 확장성 확보
 ┣━ Ⅱ 특징 ───── 스케일아웃(Scale-Out) 지향 · 샤드 키(Shard Key) 기반 라우팅 · 분산 트랜잭션 복잡도 증가
 ┣━ Ⅲ 구조 ───── 파티셔닝(단일 DB 내 수직/수평 분할) vs 샤딩(물리적으로 독립된 복수 DB 노드 분산)
 ┣━ Ⅳ 흐름 ───── ① 쿼리 패턴 및 데이터 용량 분석 → ② 분할 기준(범위/해시/리스트) 결정 → ③ 샤드 키 선정 → ④ 라우팅 구현
 ┣━ Ⅴ 비교 ───── 파티셔닝 vs 샤딩 (단일 인스턴스/OS 파일 분할 vs 분산 인스턴스/네트워크 분할)
 ┗━ Ⅵ 실무 ───── 샤드 간 조인 불가 / 핫스팟(Hotspot) 불균형 / 글로벌 2PC 트랜잭션 성능 급락
```
- 필수 키워드: 파티셔닝(수직/수평) · 샤딩(Sharding) · 샤드 키 · 레인지/해시 샤딩 · 2PC(Two-Phase Commit) · 핫스팟
- 기출: 138회 `데이터베이스 분할(수평/수직)` → Ⅲ 파티셔닝 유형 / 127회 `데이터베이스 샤딩` → Ⅲ 샤딩 아키텍처 및 Ⅵ 실무 고려사항

## 한 줄 본질
- 수억 건의 대용량 테이블로 인한 단일 인스턴스 I/O 포화 → 단일 DB 내 파티션 분할이나 물리적 독립 노드로 데이터를 샤딩 분산 → 선형적 읽기/쓰기 용량 증설 / 샤드 간 조인 불가 및 분산 트랜잭션 오버헤드 발생

## 핵심 그림
```text
[파티셔닝 vs 샤딩 아키텍처]

       [파티셔닝 (단일 RDBMS)]                [샤딩 (수평 분산 RDBMS)]
      +------------------------+                     +---------------+
      |    단일 DBMS 엔진      |                     | 샤드 라우터   |
      +------------------------+                     +-------+-------+
       /          |           \                             / \
  [파티션1]   [파티션2]   [파티션3]                        /   \
  (파일 A)    (파일 B)    (파일 C)             [샤드 DB 1]      [샤드 DB 2]
  - OS 파일 단위 분할                         - 물리적 분리된   - 물리적 분리된
  - 단일 CPU/메모리 공유                        독립 서버 노드    독립 서버 노드
```

## 핵심 용어
- 샤드 키(Shard Key): 데이터를 어떤 물리적 샤드 노드에 저장하고 조회할지 결정하는 기준 컬럼(예: 사용자 ID, 주문 번호)
- 일관된 해싱(Consistent Hashing): 노드가 추가되거나 삭제될 때 전체 데이터를 재배치하지 않고 최소한의 데이터만 이동시키는 분산 해싱 알고리즘

## 핵심 통찰
- 샤딩은 복잡성이 매우 큼 → 애플리케이션 레벨에서 샤드 간 조인이 불가능하고, 트랜잭션이 여러 샤드에 걸치면 분산 2PC로 인해 TPS가 1/10로 급락
- 따라서 샤딩 전에 단일 DB 파티셔닝(Partitioning)과 Read Replica 분리를 먼저 끝까지 소진해야 함
- 샤드 키 선택이 시스템 생사를 결정 → 순차 증가 ID나 날짜를 샤드 키로 잡으면 오늘 데이터가 특정 샤드 하나로 몰려 핫스팟(Hotspot) 발생

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 수평 파티셔닝(Range/List/Hash) | 단일 DB 파티셔닝 방식 | 날짜 범위, 코드 목록, 해시 함수 기준으로 행(Row)을 여러 세그먼트 파일로 분할 |
| 2단계 커밋(2PC) | 샤드 간 분산 트랜잭션 | 준비(Prepare)와 커밋(Commit) 2단계로 원자성을 보장하나 네트워크 블로킹 유발 |

## 이웃 토픽과 구분
- 파티셔닝 vs 샤딩: 파티셔닝 = 단일 DB 서버 안에서 테이블을 물리 파일 단위로 쪼갬 / 샤딩 = 서로 다른 서버에 데이터를 분산 저장하는 아키텍처

## 문제·원인·대책
- 적용 상황: 글로벌 핀테크 결제 플랫폼의 트랜잭션 폭증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 샤드 노드의 CPU/디스크 사용률이 99% 도달 | 날짜(Timestamp) 단일 키 샤딩으로 당일 트랜잭션 집중 | 복합 샤드 키(사용자ID 해시 + 주문일자)로 라우팅 규칙 재설계 | 전 샤드 노드 균등 부하 분산 |
| 여러 샤드에 걸친 통계 쿼리 실행 시 타임아웃 | 샤드 간 물리 네트워크 분리로 인한 RDBMS JOIN 불가 | 분석 전용 데이터 레이크/DW로 CDC(Change Data Capture) 비동기 복제 | 실시간 운영계 영향 없는 OLAP 분석 보장 |

## 이렇게 출제된다
- 제127회 4교시 3번: "데이터베이스 샤딩(Sharding)에 대한" → 요구 포인트: Ⅰ 개념 + 샤딩 방식(수평/수직, 해시/레인지) + Ⅵ 샤드 간 조인·트랜잭션 대책
- 제138회: "데이터베이스 분할(수평분할, 수직분할)" → 요구 포인트: 파티셔닝 기준과 I/O 절감 원리

## 내 의견
- [섣부른 샤딩 도입으로 인한 운영 복잡도 폭증] 데이터 500만 건 수준에서 샤딩을 도입했다가 cross-shard 쿼리 때문에 개발 생산성 급감 → 나라면: 1차로 인덱스 튜닝 및 수평 파티셔닝, 2차로 CQRS 패턴(읽기/쓰기 분리)을 적용하고, 단일 테이블 쓰기 초당 1만 건 초과 시에만 분산 샤딩 미들웨어(ShardingSphere 등)를 점진적으로 도입
