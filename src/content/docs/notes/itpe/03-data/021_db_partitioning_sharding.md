## 연관 키워드

- 데이터베이스 분할(Partitioning), 샤딩(Sharding), 수평적 확장(Scale-Out)
- 범위·해시·목록·복합 분할, 샤드 키(Shard Key), 안정 해싱(Consistent Hashing)
- 2단계 커밋(2PC, Two-Phase Commit), 핫스팟(Hotspot), 리밸런싱(Rebalancing)

## Ⅰ. 데이터베이스 분할·샤딩의 개요

- 핵심 요약 : 대용량 테이블을 작은 단위로 쪼개어 성능·관리·확장성을 확보하는 분산 저장 기술 체계.
- 개념 : 데이터베이스 분할(Partitioning)은 대용량 테이블이나 인덱스를 관리적·성능적 목적으로 물리적으로 작은 단위의 파티션(Partition)으로 쪼개어 단일 DBMS(Database Management System) 인스턴스 내에서 관리하는 기술.
- 개념 : 데이터베이스 샤딩(Sharding)은 데이터 분할 개념을 네트워크 경계를 넘어 복수의 독립된 물리적 데이터베이스 서버(Shared-Nothing 노드)로 확장하여 데이터를 분산 저장·처리하는 수평적 확장(Scale-Out) 아키텍처.
- 배경 및 필요성 : 단일 인스턴스의 저장 용량 한계, 락 경합에 따른 처리량 포화, 대형 테이블의 백업·인덱스 재구축 부담.
- 주요 목적 : 저장 용량과 트랜잭션 처리량의 확장성 확보, 파티션 단위 관리 효율화, 장애 영향 범위 최소화.

## Ⅱ. 데이터베이스 분할·샤딩의 특징

- 핵심 요약 : 분할은 단일 인스턴스 내 물리 분리, 샤딩은 노드 간 데이터 분포라는 차별점 보유.

1. 분할은 단일 OS·인스턴스 내에서 수행되어 락 경합이 잔존.
2. 샤딩은 네트워크 분산 기반으로 트랜잭션 격리 및 사실상 무제한 확장 확보.
3. 분할 기준은 범위(Range), 해시(Hash), 목록(List), 복합(Composite)의 4대 방식.
4. 샤딩 라우팅은 애플리케이션 기반, 프록시 기반, 안정 해싱 기반으로 구현.
5. 안정 해싱(Consistent Hashing)은 노드 증설·삭제 시 전체 재배치가 아닌 $K/N$개 키만 재배치하여 리밸런싱 비용 최소화.

## Ⅲ. 데이터베이스 분할·샤딩의 구조 (흐름)

- 핵심 요약 : 단일 노드 파티셔닝과 라우터 기반 다중 샤드 라우팅의 이중 구조.

```text
[ 단일 노드 파티셔닝 vs 분산 노드 샤딩 ]
  단일 DBMS 노드 (Partitioning)           다중 물리 노드 클러스터 (Sharding)
  +-------------------------------+      +----------+  +----------+  +----------+
  | Table: ORDERS                 |      | Shard #1 |  | Shard #2 |  | Shard #3 |
  |  Part 1 | Part 2 | Part 3     |      | (Node A) |  | (Node B) |  | (Node C) |
  +-------------------------------+      +----------+  +----------+  +----------+
    단일 OS/인스턴스, 락 경합 잔존          네트워크 분산, 트랜잭션 격리, 무제한 확장
```

```text
[ 샤딩 라우팅 아키텍처 ]
[Client / App] ---> [Router / Shard Proxy (Vitess, Citus)]
                            |
           +----------------+----------------+
           | (Consistent Hashing or Lookup)  |
           v                                 v
     [Shard 1 (A-M)]                   [Shard 2 (N-Z)]
```

- 애플리케이션 기반 샤딩 : 애플리케이션 코드 내에서 샤드 키 기반으로 커넥션 풀을 직접 분기(단순하나 앱 복잡도 증가).
- 프록시 기반 샤딩 : 중간 미들웨어(Vitess, Apache ShardingSphere)가 SQL(Structured Query Language)을 파싱하여 적절한 샤드로 라우팅하고 분산 집계 수행.
- 안정 해싱 기반 샤딩 : 노드 토폴로지 변화에도 최소 키 재배치로 안정적 라우팅 유지.

## Ⅳ. 4대 분할 방식의 비교

- 핵심 요약 : 데이터 특성에 따라 범위·해시·목록·복합 분할을 선택하는 전략 차별화.

| 분할 방식 | 분할 기준 및 메커니즘 | 적합한 데이터 특성 | 장점 및 주의사항 |
| :--- | :--- | :--- | :--- |
| 범위 분할(Range) | 특정 컬럼(일자, 연속 수치)의 연속된 값 범위 기준 분할 | 시계열 로그, 월별 매출 데이터, 회계 장부 | 과거 이력 데이터의 일괄 삭제(`DROP PARTITION`) 용이 / 특정 파티션 쏠림 현상 주의 |
| 해시 분할(Hash) | 분할 키의 해시 함수 적용값 모듈로 연산 기준 분할 | 고객 ID(Identifier), 주문 번호 등 고유 식별자 | 데이터의 노드 간 균등 분산 / 범위 검색(`BETWEEN`) 시 전체 파티션 스캔 필요 |
| 목록 분할(List) | 사전 정의된 불연속 이산값(코드, 지역) 목록 기준 분할 | 지역코드(서울, 경기, 부산), 사업부 코드 | 비즈니스 도메인별 물리 분리 명확 / 정의되지 않은 값 입력 시 예외 처리 필요 |
| 복합 분할(Composite) | 주 분할과 보조 분할의 결합(Range-Hash, Range-List) | 대용량 글로벌 전자상거래 결제 데이터 | 세밀한 데이터 관리와 고른 성능 분산의 동시 달성 / 관리 오버헤드 증가 |

## Ⅴ. 데이터베이스 분할·샤딩의 장점과 한계

- 핵심 요약 : 파티션 단위 관리·확장성의 장점과 샤딩 4대 엔지니어링 난제의 한계.
- 장점
  1. 과거 이력 데이터의 일괄 삭제(`DROP PARTITION`) 용이.
  2. 데이터의 노드 간 균등 분산과 도메인별 물리 분리.
  3. 세밀한 데이터 관리와 고른 성능 분산의 동시 달성.
- 한계점 1 : Cross-Shard Join 불가
  - 한계점 : 서로 다른 샤드 서버에 존재하는 테이블 간 직접 조인 불가능.
  - 해결 방안 : 공통 기준 정보의 전 샤드 브로드캐스트 복제(Global Table) 또는 애플리케이션 계층 조인.
- 한계점 2 : 분산 트랜잭션 오버헤드
  - 한계점 : 2단계 커밋(2PC, Two-Phase Commit) 적용 시 네트워크 지연 및 락 유지 시간 증가.
  - 해결 방안 : 비동기 이벤트 기반 최종 일관성(Saga 패턴) 전환.
- 한계점 3 : 샤드 리밸런싱(Rebalancing)
  - 한계점 : 트래픽 급증 노드 분할 시 무중단 데이터 마이그레이션 부담.
  - 해결 방안 : CDC(Change Data Capture) 기반 무중단 마이그레이션 도구 도입.
- 한계점 4 : 핫스팟(Hotspot) 문제
  - 한계점 : 특정 유명인·프로모션 대상 키로의 트래픽 집중.
  - 해결 방안 : 복합 샤드 키(Hash + Salt) 적용.

## Ⅵ. 데이터베이스 분할·샤딩에 대한 기술사적 제언

- 핵심 요약 : 파티셔닝 선행 후 샤딩 검토, 샤드 키 선정의 초기 설계 완성도 확보.
- 파티셔닝 선행 후 샤딩 검토 : 샤딩은 시스템 운영 복잡도와 트랜잭션 관리 비용을 급격히 증가시키므로, 단일 인스턴스 수직 확장(Scale-Up), 테이블 파티셔닝, 읽기 전용 복제본(Read Replica) 분리로 해결 불가능한 임계점(테이블 수억 건, 초당 수만 TPS(Transactions Per Second)) 도달 시 도입.
- 샤드 키(Shard Key) 선정의 불가역성 인지 : 사후 변경 시 서비스 전체 중단 및 데이터 재적재 수준의 비용 발생, 데이터 분포의 균등성과 주요 비즈니스 쿼리 조건절 패턴의 심층 분석 후 초기 설계 확정.

## Ⅶ. 결론

- 핵심 요약 : 분할은 관리·성능 최적화의 1차 수단, 샤딩은 확장 임계점 이후의 전략적 선택.
- 요약 : 파티셔닝으로 단일 인스턴스 한계를 완화하고, 임계점 도달 시 샤딩 기반 확장 체계로 전환.
- 시사점 : 샤드 키 설계와 분할 전략의 초기 검증이 대용량 데이터 플랫폼 구축의 성패를 결정.
