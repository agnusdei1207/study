## 연관 키워드

참조 무결성, 기본키, 외래키, 고아 레코드, ON DELETE, 제약조건, 트랜잭션

## Ⅰ. 참조 무결성의 개요

- 핵심 요약 : 외래키가 실제로 존재하는 부모 키만 가리키도록 막아 관계 데이터의 일관성을 지키는 제약.
- 개념 : 자식 테이블의 **외래키** (FK, Foreign Key)가 부모 테이블의 **기본키** (PK, Primary Key) 또는 후보키를 참조할 때, 참조 값이 항상 실제 부모 행을 가리키도록 보장하는 데이터베이스 제약 (**참조 무결성**, Referential Integrity).
- 배경 및 필요성 : 응용 프로그램마다 관계 검사를 따로 구현하면 누락이 생겨 존재하지 않는 부모를 가리키는 **고아 레코드** (Orphan Record)가 쌓이므로, 검사를 DBMS(Database Management System) 제약으로 한곳에 모을 필요가 있음.
- 주요 목적 : 존재하지 않는 부모를 참조하는 고아 레코드와 잘못된 관계 데이터의 유입 차단.

## Ⅱ. 참조 무결성의 특징 및 장점

- 핵심 요약 : DBMS가 관계 규칙을 선언적으로 검증해 응용 프로그램 간 데이터 불일치를 줄이는 구조.

1. 선언적 검증 : 관계 규칙을 스키마에 선언 → 모든 입력 경로에 같은 검사가 적용되어 응용 프로그램별 검사 누락 감소.
2. 연산 보호 : 자식의 삽입·갱신과 부모의 삭제·키 변경 시 지정된 규칙을 DBMS가 수행 → 관계가 깨지는 쓰기 차단.
3. 삭제·갱신 정책 명시 : **참조 동작** (RESTRICT, CASCADE, SET NULL 등)을 설계 단계에서 고정 → 관계 변경 결과를 예측 가능하게 관리.

- 제약 검증은 쓰기 부하를 만들 수 있으나, 이를 이유로 무조건 비활성화하면 무결성이 응용 코드에 의존하게 되어 위험하다.

## Ⅲ. 참조 무결성 검증 흐름

- 핵심 요약 : 자식의 외래키 쓰기와 부모 키 변경이라는 두 경로에서 DBMS가 관계 조건을 확인.
- 자식 쓰기 경로 : 외래키 값이 부모 키에 존재하는지 확인해 있으면 반영, 없으면 거부.
- 부모 변경 경로 : 참조 중인 자식 행을 찾은 뒤 참조 동작 규칙을 적용하며, 규칙은 ON DELETE·ON UPDATE 절로 지정.

```text
[자식 행 INSERT·UPDATE]
          ↓
[외래키 값이 부모 키에 존재하는가]
          ↓
   예 → 반영   /   아니오 → 거부
```

```text
[부모 행 DELETE·키 UPDATE]
          ↓
[참조 중인 자식 행 확인]
          ↓
[참조 동작 적용]
  RESTRICT·CASCADE·SET NULL 등
```

- 검증 시점과 지연 검증 방식은 DBMS 제품과 스키마 정의에 따라 다르므로 실제 설정을 확인해야 한다.
- 부모 키를 바꿀 때 참조 중인 자식이 어떻게 처리되는지는 설계 단계에서 명시해야 한다.

## Ⅳ. 참조 동작 비교

- 핵심 요약 : 업무상 관계의 의미와 삭제·갱신 정책을 기준으로 참조 동작을 선택.

| 참조 동작 | 부모 삭제·키 변경 시 자식 처리 | 적합한 경우 |
| --- | --- | --- |
| RESTRICT / NO ACTION | 참조하는 자식이 남아 있으면 작업 거부 | 자식 데이터 보존이 중요한 경우 |
| CASCADE | 자식 외래키를 함께 바꾸거나 연쇄 삭제 | 생명주기를 부모와 공유하는 데이터 |
| SET NULL | 자식 외래키를 NULL로 변경 | 관계를 해제해도 자식을 보존해야 하는 경우 |
| SET DEFAULT | 자식 외래키를 기본값으로 변경 | 유효한 기본 부모 행이 존재하는 경우 |

- 선택 기준 : 자식 데이터의 생명주기가 부모에 종속되는지, 관계 해제 후에도 자식이 의미를 갖는지에 따라 동작을 고른다.
- RESTRICT와 NO ACTION의 검증 시점은 제품별로 다르므로 확인이 필요하며, SET NULL은 컬럼의 NULL 허용 여부와 함께 설계한다.

## Ⅴ. 참조 무결성의 한계와 방안

- 핵심 요약 : 검증 비용, 대량 연쇄 작업, 분산 경계를 DBMS 제품과 업무 구조에 맞춰 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 부모 변경 시 검증 부하 | 외래키 컬럼에 인덱스가 없으면 자식 탐색 비용 증가 → 쓰기 지연 | 참조 키 인덱스와 실행 계획 점검, 트랜잭션 크기 관리 | 쓰기 지연 시간 |
| CASCADE 오용 | 연쇄 삭제가 예상보다 넓게 번져 데이터 대량 손실 | 삭제 영향 범위 분석, 소프트 삭제 검토 | 연쇄 삭제 건수 |
| 분산 환경의 샤드 간 참조 | 단일 DBMS의 외래키 검사가 노드 경계를 넘지 못함 → 불일치 가능 | 데이터 배치와 서비스 경계 설계, 정기 보정 절차 | 불일치 탐지 건수 |
| 제약조건 없는 서비스 | 응용 코드에서만 검사해 고아 데이터 누적 | 쓰기 경로 검증, 고아 데이터 탐지 쿼리 운영 | 고아 레코드 수 |

## Ⅵ. 참조 무결성에 대한 기술사적 제언

- 핵심 요약 : 무결성 규칙을 DB와 서비스 경계에 맞게 배치하고 예외 경로를 감시하는 운영 원칙을 세운다.
- 단일 데이터베이스 안에서는 선언적 제약조건을 우선 적용하고, 성능 문제가 실제로 확인될 때에만 검사 위치를 응용 계층으로 옮기는 것이 바람직하다.
- 서비스 간 비동기 연계에서는 이벤트 재처리와 멱등성 설계를 함께 두고, 관계의 책임 주체를 서비스별로 명확히 나누어 두어야 한다.
- 외래키 비활성화는 부하를 실제로 측정하고 복구 절차를 검증한 뒤에만 제한적으로 결정하는 것이 안전하다.

## Ⅶ. 결론

- 핵심 요약 : 참조 무결성은 부모·자식 관계를 보호하는 기본 제약이며, 정책 선택과 운영 영향 검토가 함께 필요한 설계 요소.
- 검증 시점과 참조 동작의 선택이 인덱스 설계와 분산 환경의 보정 체계까지 이어질 때 관계 데이터의 일관성이 유지된다.
- 참고 : [PostgreSQL 공식 제약조건 문서](https://www.postgresql.org/docs/current/ddl-constraints.html).
