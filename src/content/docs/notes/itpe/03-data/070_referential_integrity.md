## Ⅰ. 관계형 모델의 핵심 정합성 규칙, 참조 무결성 개요

### 가. 참조 무결성(Referential Integrity)의 정의
- **참조 무결성** : 관계형 데이터베이스에서 두 릴레이션 간의 관계를 맺을 때, 참조하는 자식 테이블의 외래키(Foreign Key) 값은 반드시 참조되는 부모 테이블의 기본키(Primary Key) 값으로 존재하거나, 널(NULL)이어야 한다는 규칙.
- 데이터베이스 내에 참조할 수 없는 고아 레코드(Orphan Record)가 발생하는 것을 원천적으로 차단하여 릴레이션 간의 관계적 일관성을 유지함.

### 나. 참조 무결성 위반 시의 비즈니스 재앙
- 고객 테이블에서 특정 고객이 삭제되었으나 주문 테이블에 해당 고객의 주문 데이터가 잔존하여, 배송이나 정산 시 시스템 널 포인터 예외(NPE) 또는 회계 불일치 발생.

## Ⅱ. 참조 무결성 제약조건의 위반 조건 및 DBMS 대응 옵션

### 가. CUD 연산에 따른 무결성 검증 시점

```text
[ 부모 테이블과 자식 테이블 간 연산 흐름 ]
  [부모 테이블: 부서 (DEPT)]              [자식 테이블: 사원 (EMP)]
  DEPT_NO (PK) <------------------------- DEPT_NO (FK)
  - DELETE / UPDATE 시 위험               - INSERT / UPDATE 시 위험
    (자식이 참조 중인데 부모 삭제?)           (부모에 없는 부서번호 등록?)
```

### 나. 부모 레코드 삭제/수정 시 4대 참조 무결성 규칙 매트릭스

| 참조 무결성 규칙 | 부모 레코드 삭제/수정 시 DBMS 동작 | 적용 시 장점 | 위험 및 주의사항 |
| :--- | :--- | :--- | :--- |
| **RESTRICT / NO ACTION** | 자식 테이블에서 해당 부모 키를 참조하고 있는 레코드가 1건이라도 존재하면, **부모 삭제/수정 명령 자체를 거절하고 에러 롤백** | 데이터 오염을 가장 엄격하게 방지 | 연관 데이터를 수동으로 일일이 먼저 삭제해야 하는 운영 번거로움 |
| **CASCADE** | 부모 레코드가 삭제/수정되면, 이를 참조하고 있던 **모든 자식 레코드도 연쇄적으로 동반 삭제/수정** | 편리한 일괄 정리 가능 | 수억 건의 자식 데이터가 단 한 번의 부모 삭제로 영구 소실될 수 있는 극단적 위험 |
| **SET NULL** | 부모 레코드가 삭제/수정되면, 자식 테이블의 해당 **외래키 컬럼 값을 NULL로 자동 변경** | 자식 레코드 보존 가능 | 자식의 외래키 컬럼이 `NOT NULL` 제약조건인 경우 충돌 에러 발생 |
| **SET DEFAULT** | 부모 레코드가 삭제/수정되면, 자식 테이블의 외래키 값을 **사전에 정의된 기본값(Default)으로 변경** | '미지정 부서' 등으로 유연하게 재배치 가능 | 기본값에 해당하는 레코드가 부모 테이블에 사전에 등록되어 있어야 함 |

## Ⅲ. 외래키(FK) 인덱스와 데이터베이스 락(Lock) 경합

### 가. 자식 테이블 외래키 컬럼 인덱스의 중요성
- 부모 테이블에서 레코드를 삭제하거나 PK를 변경할 때, DBMS는 자식 테이블을 스캔하여 참조 중인 레코드가 있는지 검증해야 함.
- 자식 테이블 외래키에 인덱스가 없는 경우 : 오라클 등 DBMS는 자식 테이블 전체에 테이블 수준 공유 락(Table-level Share Lock)을 걸어버려, 자식 테이블에 대한 모든 INSERT/UPDATE 트랜잭션이 블로킹되는 심각한 병목 발생.

### 나. 연쇄 삭제(CASCADE) 시의 성능 폭탄
- 부모 레코드 1건 삭제 시 자식, 손자 테이블까지 수십만 건의 `DELETE` 쿼리가 내부적으로 트리거되어 Undo/Redo 로그 폭증 및 CPU 점유율 100% 초래.

## Ⅳ. 참조 무결성 적용·운영 시 주요 한계점 및 해결 방안

- 대량 트랜잭션 환경에서 외래키 검증에 따른 쓰기 성능 저하 및 락 경합 :
  - 한계점 : 부모-자식 테이블 간 참조 무결성 제약(FK Constraint) 검증 시 부모 테이블 공유락(Shared Lock) 획득으로 인해 동시성(Throughput) 급감 및 데드락(Deadlock) 빈발.
  - 해결 방안 : 대량 배치 및 OLTP 분리, 외래키 컬럼에 대한 B-Tree 인덱스 필수 생성, 실시간 DB 레벨 FK 비활성화 및 애플리케이션 계층(도메인 엔티티 검증/Saga 패턴) 이관.
- 샤딩(Sharding) 및 분산 DB 환경에서의 크로스 노드 참조 무결성 검증 불가 :
  - 한계점 : 데이터가 물리적으로 분할된 샤드 간에는 RDBMS 내장 FK 제약조건을 통한 외래키 검증이 불가능하여 고아 레코드(Orphan Record) 발생 리스크 상존.
  - 해결 방안 : 비정규화(Denormalization)를 통한 샤드 키(Shard Key) 일치화(Co-location), CDC 기반 비동기 무결성 검증 파이프라인 및 배치 정합성 보정(Reconciliation) 잡 운영.
- 연쇄 삭제/수정(CASCADE)에 따른 의도치 않은 대량 I/O 및 데이터 유실 :
  - 한계점 : ON DELETE CASCADE 설정 시 루트 레코드 삭제가 수백만 건의 하위 레코드 연쇄 삭제로 이어져 세그먼트 블록 I/O 폭증 및 서비스 행(Hang) 초래.
  - 해결 방안 : 물리적 삭제(Hard Delete)를 지양하고 논리 삭제(Soft Delete: deleted_at 플래그) 표준화, 대량 삭제 필요 시 청크 단위(Chunk-based) 분할 삭제 스크립트 적용.

## Ⅴ. 대규모 트랜잭션 시스템에서의 참조 무결성 실무 제언

- 물리적 외래키(Physical FK)의 선별적 제거 : 초당 수천 TPS가 발생하는 대규모 MSA 및 전자상거래 시스템에서는 쓰기 지연과 테이블 락 경합을 방지하기 위해 물리적 DDL 상의 `FOREIGN KEY` 제약조건을 의도적으로 생략하되,
  1. 외래키 컬럼에 대한 B-Tree 인덱스는 반드시 생성 하여 조인 성능을 확보하고,
  2. 무결성 검증은 애플리케이션 서비스 계층의 트랜잭션 로직에서 방어해야 함.
- 데이터 정합성 사후 검증 배치 운영 : 물리적 FK가 없는 시스템에서는 일 1회 새벽 배치로 `EMP.DEPT_NO NOT IN (SELECT DEPT_NO FROM DEPT)`와 같은 고아 레코드 탐지 쿼리를 수행하여 불일치 데이터를 자동 감시하고 알림을 발생시킬 것을 제언함.
