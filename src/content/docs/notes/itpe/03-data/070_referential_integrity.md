## 답안 골격
```text
[참조 무결성] ◀━━ 머리: Ⅶ 내 의견 (DB 레벨 외래키 제약과 애플리케이션 트랜잭션 검증의 이중 안전망 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 관계형 데이터베이스에서 자식 릴레이션의 외래키(FK) 값은 반드시 부모 릴레이션의 기본키(PK) 값과 일치하거나 NULL이어야 한다는 제약
 ┣━ Ⅱ 특징 ───── 고아 레코드(Orphan Record) 방지 · 릴레이션 간 관계 일관성 · DML 연쇄 제어 규칙 수반 · 성능 vs 정합성 상충
 ┣━ Ⅲ 구조 ───── 부모 릴레이션(기본키, PK) / 자식 릴레이션(외래키, FK) / 참조 무결성 제약조건 / 연쇄 제어 옵션
 ┣━ Ⅳ 흐름 ───── ① 부모 행 삭제/수정 요청 → ② 참조 제약 검사 → ③ 연쇄 동작(Restrict / Cascade / Set Null / Set Default) 분기 수행
 ┣━ Ⅴ 비교 ───── 개체 무결성 vs 참조 무결성 vs 도메인 무결성 (PK Not Null 및 유일성 vs 부모-자식 FK 일치 vs 속성 허용값 범위)
 ┗━ Ⅵ 실무 ───── 대량 INSERT 시 FK 검사 디스크 I/O 병목 / 부모 행 무분별한 CASCADE DELETE로 인한 연쇄 데이터 참사
```
- 필수 키워드: 외래키(FK) · 기본키(PK) · 고아 레코드(Orphan Record) · 제한(Restrict) · 연쇄(Cascade) · Null 설정(Set Null) · 무결성 제약
- 기출: 138회 1교시 9번 `정보모델링의 참조 무결성` → Ⅰ 개념 + Ⅲ 구성요소 + Ⅳ 연쇄 제어 옵션(Cascade 등)

## 한 줄 본질
- 자식 테이블이 존재하지 않는 부모 데이터를 가리키는 고아(Orphan) 상태 방지 → 외래키(FK) 값이 부모 기본키(PK)에 반드시 존재하도록 DBMS 레벨 강제 통제 → 관계 데이터 정합성 보장 / DML 쓰기 지연 수반

## 핵심 그림
```text
[참조 무결성 위반 및 4대 제어 옵션 메커니즘]

    [ 부모: 부서 테이블 ]                   [ 자식: 사원 테이블 ]
    부서코드(PK) | 부서명                  사원ID | 이름 | 부서코드(FK)
    ─────────────┼───────                  ───────┼──────┼─────────────
    D01          │ 개발팀                  101    │ 김철수│ D01
    D02          │ 기획팀                  102    │ 이영희│ D01
    D03          │ 인사팀                  103    │ 박민수│ D99 (위반! D99 없음)
         │                                          ▲
         │ (D01 삭제 시도 시)                       │
         ▼                                          │
    ┌───────────────────────────────────────────────┴────────┐
    │ 1. RESTRICT / NO ACTION : D01을 참조하는 사원이 있으므로 삭제 거부│
    │ 2. CASCADE              : 사원 101, 102번도 연쇄적으로 함께 삭제 │
    │ 3. SET NULL             : 사원 101, 102번의 부서코드를 NULL로 변경│
    │ 4. SET DEFAULT          : 사원 101, 102번의 부서코드를 기본부서로 변경│
    └────────────────────────────────────────────────────────┘
```

## 핵심 용어
- 고아 레코드(Orphan Record): 부모 테이블에서 원천 키가 삭제되었음에도 불구하고 자식 테이블에 여전히 남아 유령처럼 부모를 참조하고 있는 유효하지 않은 데이터
- CASCADE: 부모 테이블의 행이 삭제되거나 기본키가 변경될 때, 그 값을 참조하던 자식 테이블의 모든 행을 DBMS가 자동으로 연쇄 삭제/수정하는 동작 규칙

## 핵심 통찰
- 완벽한 데이터 무결성의 대가는 '성능(Performance)'임 → 자식 테이블에 한 건 INSERT할 때마다 부모 테이블에 해당 키가 있는지 매번 락(S-Lock)을 걸고 조회하므로 쓰기 동시성 저하
- 이 때문에 대규모 초고속 트래픽 시스템(MSA, 샤딩 환경)에서는 DB 레벨의 물리적 FK(외래키) 생성을 의도적으로 금지하고, 비즈니스 로직(Application) 계층에서 무결성을 통제하는 전략 채택
- CASCADE DELETE는 운영의 시한폭탄 → 관리자가 실수로 테스트 부서 하나 지웠다가 연관된 수천 명의 사원과 결제 내역이 DB 엔진에 의해 순식간에 영구 삭제되는 재앙 초래 가능

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 개체 무결성(Entity Integrity) | RDBMS 3대 기본 무결성 | 릴레이션의 기본키는 절대 NULL 값을 가질 수 없으며 유일해야 한다는 제약 |
| 논리적 삭제(Soft Delete) | 실무 참조 무결성 보존 기법 | 물리적 DELETE를 금지하고 `is_deleted` 플래그를 두어 부모 삭제 시에도 자식의 참조 무결성을 안전하게 보존 |

## 이웃 토픽과 구분
- 물리적 FK 제약 vs 논리적 FK 관계: 물리적 FK = DBMS 엔진이 DDL로 강제하여 위반 시 SQL 에러 발생 / 논리적 FK = ERD 상에만 존재하고 실제 DB에는 제약조건을 걸지 않아 애플리케이션 코드가 정합성 책임

## 문제·원인·대책
- 적용 상황: 대규모 주문 결제 시스템의 고객 탈퇴 처리
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 고객 탈퇴 시 고객 행을 삭제하자 기존 수년 치 주문 내역이 함께 삭제(CASCADE 참사) | 고객-주문 테이블 간 ON DELETE CASCADE 물리 외래키 설정 | 물리적 DELETE 금지(소프트 딜리트 적용) 및 주문 테이블 고객FK를 RESTRICT로 전환 | 회계 및 감사용 거래 이력 데이터 무손실 보존 |
| 배치 데이터 1,000만 건 INSERT 시 FK 제약 검사로 10시간 이상 소요 | 행 단위 FK 유효성 검사로 인한 부모 테이블 버퍼 경합 | 배치 작업 전 FK 비활성화(`DISABLE NOVALIDATE`) 후 적재 완료 시 재활용 | 배치 적재 시간 80% 단축 |

## 이렇게 출제된다
- 제138회 1교시 9번: "정보모델링의 참조 무결성" → 요구 포인트: 참조 무결성 개념 및 정의 + 부모/자식 관계 도식 + 4대 연쇄 옵션(Restrict, Cascade, Set Null, Set Default) + 실무 고려사항

## 내 의견
- [단일 DB의 물리적 FK 환상 탈피] 마이크로서비스(MSA) 환경에서는 서비스마다 DB가 분리되므로 DB 엔진 레벨의 참조 무결성이 원천적으로 불가능함 → 나라면: 도메인 내부 핵심 정합성은 RDBMS 트랜잭션으로 묶되, 서비스 간 참조 무결성은 카프카(Kafka) 이벤트 기반의 결과적 일관성(Eventual Consistency) 및 정기 배치 정합성 대사(Reconciliation)로 달성
