## 연관 키워드

- 무결성 제약(Integrity Constraint), 개체 무결성(Entity Integrity), 참조 무결성(Referential Integrity), 도메인 무결성(Domain Integrity), 사용자 정의 무결성(User-Defined Integrity)
- 기본키(PK, Primary Key), 외래키(FK, Foreign Key), 고아 레코드(Orphan Record), RESTRICT, CASCADE, SET NULL, SET DEFAULT, Saga 패턴

## Ⅰ. 무결성 제약의 개요

- 핵심 요약 : 데이터의 정확성·일관성·유효성을 지키기 위해 데이터 변경 시 강제되는 규칙과 조건의 총체.
- 개념 : 데이터베이스에 저장된 데이터의 정확성(Accuracy), 일관성(Consistency), 유효성(Validity)을 보장하도록 삽입·수정·삭제 시 지켜야 하는 규칙과 조건의 총체 (**무결성 제약** (Integrity Constraint)).
- 배경 및 필요성 : 권한 없는 변경이나 비정상 트랜잭션으로 데이터가 모순 상태로 바뀌는 것을 막아야 하며, 외래키 단절로 **고아 레코드** (Orphan Record)가 생기는 것도 억제해야 함.
- 주요 목적 : 비즈니스 규칙을 데이터 모델 계층에서 강제해 애플리케이션 버그에 대한 방어선을 구축하고 데이터 신뢰성을 확보.

## Ⅱ. 무결성 제약의 특징

- 핵심 요약 : 개체·참조·도메인·사용자 정의의 네 가지 무결성과 참조 옵션으로 이루어진 데이터 품질 방어 체계.

1. **개체 무결성** (Entity Integrity) : 기본키(PK, Primary Key) 구성 속성은 NULL 불가, 중복 불가 → 행의 유일한 식별 보장.
2. **참조 무결성** (Referential Integrity) : 외래키(FK, Foreign Key) 값은 참조 릴레이션의 기본키 값이거나 NULL → 존재하지 않는 부모를 가리키는 데이터 차단.
3. **도메인 무결성** (Domain Integrity) : 속성값이 정의된 데이터 타입, 길이, 허용 범위(CHECK)를 따름 → 잘못된 형식의 값 입력 차단.
4. **사용자 정의 무결성** (User-Defined Integrity) : 업무 특성상 필요한 복합 규칙(TRIGGER, ASSERTION 등)을 강제 → 업무 규칙 위반 차단.
5. 참조 옵션 : 부모 레코드를 삭제하거나 수정할 때 자식 레코드를 처리하는 방식을 정한다.
   1. RESTRICT (또는 NO ACTION) : 참조하는 자식이 있으면 부모의 삭제·수정을 거부.
   2. CASCADE : 부모의 삭제·수정을 자식에도 연쇄 반영.
   3. SET NULL : 부모 삭제 시 자식의 외래키 값을 NULL로 변경.
   4. SET DEFAULT : 부모 삭제 시 자식의 외래키 값을 기본값으로 변경.

## Ⅲ. 무결성 제약의 구조 (흐름)

- 핵심 요약 : DML(Data Manipulation Language) 처리 경로에서 제약을 검증해 통과 시 확정하고 위반 시 롤백하는 흐름.

```text
[ 무결성 검증 흐름 ]
DML 요청 (INSERT/UPDATE/DELETE)
        ↓
제약조건 검사 (PK·FK·CHECK)
        ↓               ↓
      통과             위반
        ↓               ↓
     COMMIT      에러 반환, ROLLBACK
```

- 제약을 어느 계층에서 강제하는지에 따라 구조가 둘로 나뉜다. 데이터베이스(DB, Database) 계층은 선언적 제약을 강제하고, 애플리케이션 계층은 ORM(Object-Relational Mapping)과 서비스 로직으로 유효성을 검증한다.

```text
[ 무결성 구현 계층 ]
(A) DB 계층 강제
    FK·CHECK·TRIGGER 선언
    쓰기 비용 증가, 샤딩 곤란
(B) 애플리케이션 계층 강제
    ORM·서비스 로직 검증
    부하 분산, 수평 확장 유리
    앱 버그 시 데이터 오염 위험
```

## Ⅳ. 무결성 유형 및 구현 계층의 비교

- 핵심 요약 : 네 가지 무결성의 규칙과 구현 기법 차이, 그리고 DB 계층과 애플리케이션 계층의 정합성-성능 트레이드오프.

| 무결성 종류 | 핵심 규칙 | 구현 기법 | 위반 시 동작 |
| --- | --- | --- | --- |
| 개체 무결성 | 기본키 구성 속성의 NULL 불가, 중복 불가 | PRIMARY KEY 제약 선언 (대부분 DBMS가 고유 인덱스를 함께 생성) | 유일성 위반(예: Oracle ORA-00001) 또는 NOT NULL 위반 에러 후 롤백 |
| 참조 무결성 | 외래키 값은 부모 기본키 값 또는 NULL | FOREIGN KEY 제약 선언 (REFERENCES 부모(PK)) | 부모에 없는 값의 삽입 차단, 참조 중인 부모의 삭제 차단 |
| 도메인 무결성 | 값이 정의된 타입·길이·범위를 만족 | 데이터 타입, NOT NULL, CHECK 제약 | 타입 불일치 또는 CHECK 위반 에러 |
| 사용자 정의 무결성 | 업무 특성상 요구되는 복합 규칙 준수 | TRIGGER, 트랜잭션 로직, 애플리케이션 검증 | 업무 예외 발생 후 트랜잭션 중단 |

DBMS(Database Management System)에 제약을 두는 방식과 애플리케이션에 두는 방식은 다음처럼 다르다.

| 비교 항목 | DB 계층 (FK, PK, CHECK) | 애플리케이션 계층 (ORM, 서비스 로직) |
| --- | --- | --- |
| 정합성 보장 | 어떤 경로로 SQL(Structured Query Language)을 실행해도 DB가 강제 | 직접 쿼리나 다른 애플리케이션이 우회하면 깨질 수 있음 |
| 쓰기 성능 | 외래키 검사를 위한 부모 테이블 추가 조회 발생 | 잠금과 I/O를 줄여 고성능 쓰기에 유리 |
| 분산 환경 | 샤딩·분산 DB에서 테이블 간 외래키 설정이 일반적으로 어려움 | 서비스 경계를 넘는 정합성을 **사가 패턴** (Saga Pattern)으로 제어 |

## Ⅴ. 무결성 제약의 장점과 한계

- 핵심 요약 : 애플리케이션 우회와 무관한 품질 방어선이라는 장점과 달리, 쓰기 성능·분산 환경·복합 규칙 표현에서 한계를 가짐.

장점은 세 가지다.
1. 애플리케이션 버그나 우회 경로와 무관하게 데이터 품질을 지키는 방어선 확보.
2. 외래키 단절을 막아 데이터의 신뢰성과 일관성 유지.
3. 업무 규칙을 데이터 모델 계층에 두어 품질 관리를 일관되게 유지.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 대용량 쓰기 성능 저하 | 매 건마다 부모 인덱스 탐색과 잠금이 발생해 I/O 병목과 초당 트랜잭션 수(TPS, Transactions Per Second) 저하 | 대량 적재 시 제약을 일시 비활성화한 뒤 검증 복원, 애플리케이션 계층 검증 분담 | TPS, 적재 소요 시간 |
| 마이크로서비스(MSA, Microservice Architecture) 환경의 참조 무결성 단절 | 서비스별 DB 분리(Database per Service)로 물리적 외래키 설정 불가 | 사가 패턴 기반 보상 처리, **변경 데이터 캡처** (CDC, Change Data Capture)와 아웃박스(Outbox) 패턴으로 최종 일관성 보장 | 불일치 건수, 보상 처리 지연 |
| 복합 규칙의 트리거 남용 | 기본 제약(PK, FK, CHECK)으로 표현하기 어려운 규칙을 트리거에 몰아 넣으면 연쇄 동작 추적이 어려움 | **도메인 주도 설계** (DDD, Domain-Driven Design)의 **애그리게이트** (Aggregate) 루트에 규칙을 캡슐화하고 DB 제약은 핵심 불변식에 집중 | 트리거 개수, 장애 추적 시간 |

## Ⅵ. 무결성 제약에 대한 기술사적 제언

- 핵심 요약 : 무결성을 데이터 중요도에 따라 등급화하고, 제약을 완화한 영역일수록 정합성 점검을 상시 운영하는 정책.
- 모든 규칙을 같은 방식으로 강제하기보다, 금전·재고처럼 훼손 시 피해가 큰 불변식은 DB 제약으로 강하게 묶고, 쓰기 부하가 큰 로그성 데이터는 애플리케이션 검증과 사후 점검으로 다루는 등급 정책이 현실적이다.
- 제약을 완화하는 영역에는 불일치 건수를 세는 정합성 점검 배치를 상시 두어, 완화에 따른 위험을 수치로 확인할 수 있어야 한다. 점검 결과는 설계 변경의 근거로 환류되어야 한다.

## Ⅶ. 결론

- 핵심 요약 : 무결성 제약은 데이터 품질의 마지막 방어선이지만, 성능과 분산 환경 조건에 따라 강제 위치를 고르는 개념.
- 시사점 : 데이터 중요도별 등급화와 정합성 점검 체계가 뒷받침될 때 품질과 확장성의 균형이 확보됨.
