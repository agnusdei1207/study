## Ⅰ. 관계형 데이터 모델의 무결성 제약(Integrity Constraint) 개요

### 가. 무결성 제약의 정의
- **무결성 제약**은 데이터베이스에 저장된 데이터의 정확성(Accuracy), 일관성(Consistency), 유효성(Validity)을 보장하기 위해 데이터의 삽입(Insert), 수정(Update), 삭제(Delete) 시 준수되어야 하는 규칙과 조건의 총체.
- 권한이 없는 사용자나 비정상적인 트랜잭션 오류로 인해 데이터베이스가 왜곡되거나 모순된 상태로 빠지는 것을 방지하는 핵심 방어선.

### 나. 무결성 보장의 필요성
- 비즈니스 룰을 데이터 모델 계층에 강제하여 애플리케이션 버그로 인한 데이터 오염 방지.
- 외래키 단절로 인한 고아 레코드(Orphan Record) 생성 억제 및 데이터 신뢰성 확보.

## Ⅱ. 관계형 데이터베이스의 4대 무결성 제약조건

### 가. 4대 무결성 제약 메커니즘

```text
[ RDBMS 4대 핵심 무결성 ]
1. 개체 무결성 (Entity)     : 기본키(PK) != NULL, 유일성(Unique) 만족
2. 참조 무결성 (Referential) : 외래키(FK) 값은 참조 테이블의 PK 값이거나 NULL
3. 도메인 무결성 (Domain)    : 속성값은 사전에 정의된 데이터 타입, 길이, 허용 범위(Check) 준수
4. 사용자 정의 무결성 (User) : 업무 규칙에 따른 비즈니스 제약 (Trigger, Assertion 등)
```

| 무결성 종류 | 핵심 규칙 및 정의 | 데이터베이스 구현 기법 | 위반 시 DBMS 동작 |
| :--- | :--- | :--- | :--- |
| **개체 무결성 (Entity Integrity)** | 릴레이션의 기본키(Primary Key)를 구성하는 어떤 속성도 널(NULL) 값을 가질 수 없으며, 중복될 수 없음 | `PRIMARY KEY` 제약조건 선언 (내부적으로 Unique B-Tree 인덱스 생성) | ORA-00001 (Unique constraint violated), Not Null 위반 에러 발생 후 롤백 |
| **참조 무결성 (Referential Integrity)** | 외래키(Foreign Key) 값은 참조하는 다른 릴레이션의 기본키 값과 일치하거나 널(NULL)이어야 함 | `FOREIGN KEY` 제약조건 선언 (`REFERENCES parent(pk)`) | 자식에 없는 부모값 삽입 차단, 자식이 참조 중인 부모 삭제 차단 |
| **도메인 무결성 (Domain Integrity)** | 특정 속성에 입력되는 모든 값은 해당 속성에 정의된 원자값(도메인) 범위를 만족해야 함 | 데이터 타입(VARCHAR, INT), `NOT NULL`, `CHECK` 제약조건 | 범위를 벗어난 값 입력 시 타입 불일치 또는 Check 제약조건 위반 에러 |
| **사용자 정의 무결성 (User-Defined)** | 개체, 참조, 도메인 제약 외에 업무 특성상 요구되는 복합 비즈니스 규칙 준수 | 데이터베이스 트리거(`TRIGGER`), 트랜잭션 로직, 애플리케이션 검증 | 비즈니스 예외 발생 후 트랜잭션 강제 Abort |

### 나. 참조 무결성 유지 옵션 (부모 레코드 삭제/수정 시)
- **RESTRICT / NO ACTION** : 자식 테이블에서 참조 중인 경우 부모 레코드 삭제/수정 거부.
- **CASCADE** : 부모 레코드 삭제/수정 시 이를 참조하는 모든 자식 레코드도 연쇄 삭제/수정.
- **SET NULL** : 부모 레코드 삭제 시 자식의 외래키 컬럼 값을 NULL로 자동 변경.
- **SET DEFAULT** : 부모 레코드 삭제 시 자식의 외래키 컬럼 값을 사전 정의된 기본값으로 변경.

## Ⅲ. 무결성 강제 방식의 비교: DBMS 제약 vs 애플리케이션 계층

### 가. 구현 계층별 트레이드오프

```text
[ 무결성 구현 계층 비교 ]
(A) DB 계층 강제 (FK, Check, Trigger) : 완벽한 데이터 정합성 보장, 성능 저하(오버헤드), 샤딩 곤란
(B) 앱 계층 강제 (ORM, 서비스 로직)     : DB 부하 분산, 유연한 수평 확장, 앱 버그 시 데이터 오염 위험
```

| 비교 항목 | 데이터베이스 계층 (FK, PK, Check) | 애플리케이션 계층 (Spring, Django, ORM) |
| :--- | :--- | :--- |
| **정합성 보장성** | 100% 보장 (어떤 경로로 직접 SQL을 실행해도 무결성 유지) | 다중 애플리케이션이나 직접 쿼리 수행 시 정합성 파괴 가능 |
| **성능 및 쓰기 지연** | 외래키 검증을 위한 부모 테이블 추가 읽기 I/O 발생 | DB 락킹 및 I/O 최소화로 대규모 고성능 쓰기 지원 |
| **분산 환경 지원** | 분산 DB 및 샤딩 환경에서 테이블 간 FK 제약 불가 | 서비스 경계를 넘는 데이터 정합성을 Saga 패턴 등으로 유연 제어 |

## Ⅳ. 무결성 제약조건 적용 시 주요 한계점 및 해결 방안

- **DBMS 제약조건(FK, Check) 적용에 따른 대용량 쓰기 성능 저하** :
  - **한계점** : 대규모 INSERT/UPDATE 배치 시 매 건마다 부모 테이블 B+Tree 인덱스 탐색 및 락 획득으로 인해 I/O 병목 및 초당 트랜잭션 수(TPS) 급감.
  - **해결 방안** : 대량 데이터 로더(Bulk Loader) 작업 시 제약조건을 일시 비활성화(Disable Novalidate) 후 작업 완료 후 병렬 활성화, 또는 애플리케이션 계층 유효성 검증 분담.
- **마이크로서비스(MSA) 및 분산 DB 환경에서의 외래키(FK) 무결성 붕괴** :
  - **한계점** : 서비스별 DB 분리(Database per Service) 아키텍처에서는 물리적 외래키 제약 설정이 불가능하여 서비스 간 참조 무결성 단절 발생.
  - **해결 방안** : 사가(Saga) 패턴 기반의 오케스트레이션 적용, 비동기 CDC(Debezium)와 Outbox 패턴을 활용한 최종적 참조 무결성(Eventual Referential Integrity) 보장.
- **복잡한 업무 규칙 표현의 한계 및 트리거 남용 시 디버깅 난제** :
  - **한계점** : 기본 SQL 무결성 제약(PK, FK, Check)만으로는 다중 행/테이블 간 복합 검증이 어려워 DB 트리거(Trigger)를 남용하게 되고 연쇄 동작으로 사이드 이펙트 추적 불가.
  - **해결 방안** : 복합 도메인 무결성은 도메인 주도 설계(DDD)의 애그리게잇(Aggregate) 루트 내부 비즈니스 로직으로 캡슐화하고 데이터베이스는 기본 제약에 집중.

## Ⅴ. 대규모 시스템에서의 무결성 제약 실무 제언

- **대용량 트랜잭션 시스템의 외래키(FK) 완화 전략** : 초당 수만 건의 쓰기가 발생하는 커머스 주문/로그 시스템에서는 물리적 외래키 제약조건을 의도적으로 제거하고 인덱스만 생성한 뒤, 애플리케이션 트랜잭션 및 비동기 정합성 배치 검증 체계로 이원화할 것.
- **데이터 마이그레이션 시 제약조건 일시 비활성화** : 수천만 건의 데이터를 초기 적재할 때는 `DISABLE NOVALIDATE` 옵션으로 제약조건을 끄고 고속 로드(Direct Path Insert)한 후, 적재 완료 시점에 병렬 검증(`ENABLE NOVALIDATE`)으로 복원하여 작업 시간을 단축할 것을 제언함.
