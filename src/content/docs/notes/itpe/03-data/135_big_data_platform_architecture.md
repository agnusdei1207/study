## 핵심 용어
- 람다 아키텍처(Lambda Architecture): 실시간 처리를 담당하는 스피드 레이어(Speed Layer)와 전체 데이터의 정확한 배치를 담당하는 배치 레이어(Batch Layer)를 병렬로 두고 서빙 레이어에서 둘을 결합하는 아키텍처
- 카파 아키텍처(Kappa Architecture): 람다의 코드 중복 문제를 해결하기 위해 배치 레이어를 완전히 없애고, 카프카(Kafka) 같은 로그 브로커에 데이터를 영구 보관하며 단일 스트림 처리 엔진(Flink)으로 모든 데이터를 재처리(Replay)하는 아키텍처

## 핵심 통찰
- 람다 아키텍처의 치명적 결함은 '개발자가 동일한 집계 비즈니스 로직을 자바(Spark 배치)와 스칼라/파이썬(실시간 스트림)으로 두 번 코딩해야 한다는 점'임 → 요구사항이 바뀔 때 한쪽만 수정하면 배치 뷰와 실시간 뷰의 숫자가 틀어짐
- 카파 아키텍처는 이를 극복했으나 과거 데이터 수년 치를 스트림 엔진으로 재처리할 때 막대한 메모리와 리소스가 소모되는 한계 봉착
- 현대 빅데이터 플랫폼의 최종 종착지는 '데이터 레이크하우스(Data Lakehouse)'임 → S3 스토리지 위에 Apache Iceberg 테이블 포맷을 올려, 단일 스토리지에서 배치와 스트리밍 쓰기 모두에 ACID 트랜잭션을 보장

## 이웃 토픽과 구분
- 람다 아키텍처 vs 카파 아키텍처: 람다 = 배치 레이어와 스트림 레이어를 이원화하여 병렬 운영 / 카파 = 배치 레이어를 폐지하고 단일 스트림 처리 엔진으로 과거 재처리와 실시간 처리를 일원화

## 문제·원인·대책
- 적용 상황: 글로벌 핀테크 이상금융거래탐지(FDS) 및 일간 정산 플랫폼 구축
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 배치 정산 결과와 실시간 FDS 대시보드의 당일 매출 수치가 5% 불일치 | 람다 아키텍처 환경에서 배치 집계 룰과 실시간 스트림 집계 룰의 구현 차이 | Kafka 기반 단일 이벤트 소싱 및 단일 Flink 스트림 파이프라인(카파) 일원화 | 실시간-배치 간 데이터 100% 일치 보장 |
| 데이터 레이크에 수백만 개의 1KB 미만 초소형 파일이 생성되어 쿼리 지연 극심 | 실시간 스트리밍 적재 시 잦은 플러시로 인한 작은 파일 문제(Small File Problem) | Apache Iceberg의 비동기 파일 압축(Compaction) 배치 자동화 | 파일 수 99% 축소 및 쿼리 속도 10배 향상 |

## 이렇게 출제된다
- 제126회: "빅데이터 플랫폼 아키텍처의 5대 계층 구조를 설명하고, 대용량 실시간 처리를 위한 람다(Lambda) 아키텍처와 카파(Kappa) 아키텍처의 동작 원리 및 장단점을 비교 설명하시오." → 요구 포인트: 5계층 아키텍처 도식 + 람다 vs 카파 비교 다이어그램 + 람다의 이중 코드 문제 + 현대 레이크하우스 대안

## 내 의견
- [단일 만능 도구 환상 탈피] 모든 것을 단 하나의 오픈소스 엔진으로 해결하려다 시스템 전체가 다운되는 아키텍처 실패 사례 빈발 → 나라면: 스토리지 계층은 Apache Iceberg 오픈 포맷으로 표준화하여 벤더 종속을 없애고, 실시간 이벤트 처리는 Flink, 야간 무거운 ETL은 Spark, 현업의 대화형 SQL 조회는 Trino를 배치하는 관심사 분리(Separation of Concerns) 아키텍처 확립
