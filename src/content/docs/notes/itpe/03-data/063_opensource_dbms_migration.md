## Ⅰ. 상용 소프트웨어 종속성 탈피를 위한 오픈소스 DBMS 마이그레이션 개요

### 가. 오픈소스 DBMS 마이그레이션의 정의
- 기존 고가의 상용 RDBMS(Oracle, MS-SQL 등)의 막대한 라이선스 비용 및 벤더 종속성(Vendor Lock-in)을 탈피하고, 클라우드 환경에 최적화된 오픈소스 데이터베이스(PostgreSQL, MySQL, MariaDB)로 스키마, 데이터, 애플리케이션 로직을 전환하는 엔지니어링 프로세스.

### 나. 마이그레이션 추진의 3대 핵심 동기
- **비용 절감 (TCO 절감)** : CPU 코어당 수천만 원에 달하는 상용 라이선스 및 연간 22%의 유지보수료 절감.
- **클라우드 네이티브 전환** : AWS Aurora, GCP Cloud SQL 등 완전관리형(PaaS) DB로의 전환 가속화.
- **아키텍처 현대화** : 모놀리식 단일 DB에서 마이크로서비스(MSA)별 독립 DB 구조로의 재편.

## Ⅱ. 마이그레이션 4대 대상 영역 및 호환성 난제

### 가. 마이그레이션 4대 계층별 변환 과제

```text
[ 오픈소스 DBMS 마이그레이션 4대 전환 영역 ]
+-------------------------------------------------------------------------+
| 1. 데이터 스키마 (Schema) : 테이블, 컬럼 타입(VARCHAR2->TEXT, NUMBER)    |
+-------------------------------------------------------------------------+
| 2. 데이터 이관 (Data)    : 대용량 데이터 추출, 정제, 초고속 병렬 적재    |
+-------------------------------------------------------------------------+
| 3. SQL 및 힌트 (Query)    : 오라클 독자 쿼리(+, DECODE, ROWNUM) 표준화    |
+-------------------------------------------------------------------------+
| 4. 저장 프로시저 (Logic) : PL/SQL (패키지, 커서, 예외처리) -> PL/pgSQL   |
+-------------------------------------------------------------------------+
```

### 나. 주요 비호환 항목 및 전환 매핑 가이드 (Oracle $\rightarrow$ PostgreSQL 기준)

| 구분 | 상용 DBMS (Oracle) | 오픈소스 DBMS (PostgreSQL) | 변환 가이드라인 |
| :--- | :--- | :--- | :--- |
| **데이터 타입** | `VARCHAR2(n)`, `NUMBER(p, s)` | `VARCHAR(n)`, `NUMERIC(p, s)` | 문자열 길이는 바이트가 아닌 문자 수 기준이므로 인코딩(UTF-8) 확인 |
| **NULL과 빈 문자열** | 빈 문자열(`''`)을 **NULL로 자동 처리** | 빈 문자열(`''`)과 **NULL을 엄격히 구분** | 애플리케이션 조건절(`WHERE col IS NULL` vs `WHERE col = ''`) 전수 수정 |
| **아우터 조인** | 오라클 전용 `(+)` 연산자 | ANSI 표준 `LEFT/RIGHT OUTER JOIN` | ANSI SQL 표준 구문으로 전면 리팩토링 |
| **계층형 쿼리** | `START WITH ... CONNECT BY` | `WITH RECURSIVE` 재귀 공통 테이블 식 | 재귀 CTE 구문으로 전환 |
| **페이징 처리** | `ROWNUM` 가상 컬럼 조건문 | `LIMIT n OFFSET m` 구문 | 정렬 기준(`ORDER BY`)과 함께 명시적 페이징 전환 |
| **옵티마이저 힌트** | `/*+ INDEX(a idx_1) */` 강제 힌트 | 힌트 미지원 (비용 기반 파라미터 튜닝) | 통계정보(`ANALYZE`) 최신화 또는 `pg_hint_plan` 확장 모듈 검토 |

## Ⅲ. 무중단 데이터 이관 전략 및 CDC 파이프라인

### 가. CDC 기반 무중단 컷오버(Cut-over) 3단계 프로세스

```text
[ CDC 기반 무중단 마이그레이션 아키텍처 ]
[Oracle DB (운영)] ===(1. 초기 벌크 적재)===> [PostgreSQL DB (타깃)]
        |                                           ^
        | (2. 트랜잭션 실시간 복제)                 |
        +---> [Debezium / GoldenGate] ---> [Kafka] -+
```

1. **초기 데이터 복제 (Initial Load)** : 운영 중인 상용 DB의 특정 SCN(시점) 스냅샷을 덤프하여 타깃 오픈소스 DB에 병렬 적재.
2. **증분 데이터 동기화 (CDC)** : 초기 적재 중 발생한 트랜잭션 Redo 로그를 실시간 캡처하여 타깃 DB에 지속 적용(복제 지연 시간 0에 수렴).
3. **최종 컷오버 (Cut-over)** : 애플리케이션 점검 모드 전환 $\rightarrow$ 최종 잔여 트랜잭션 반영 확인 $\rightarrow$ 애플리케이션 DB 엔드포인트를 오픈소스 DB로 스위칭 (다운타임 수분 이내).

## Ⅳ. 성공적인 마이그레이션을 위한 실무 제언

- **자동화 변환 도구의 적극 활용 및 수동 검증** : AWS SCT(Schema Conversion Tool), Ora2Pg 등 자동 변환 도구를 활용하여 스키마와 쿼리의 80% 이상을 자동 변환하되, 성능을 좌우하는 복합 인덱스와 PL/SQL 프로시저는 DBA가 수동으로 최적화해야 함.
- **롤백 계획(Fallback Plan) 수립의 의무화** : 신규 오픈소스 DB 오픈 후 예기치 못한 성능 저하나 버그 발생 시 구 시스템으로 즉시 복귀할 수 있도록, 반대 방향(오픈소스 $\rightarrow$ 상용 DB) 역방향 CDC 복제 파이프라인을 전환 당일 최소 48시간 이상 가동 유지할 것을 제언함.
