## Ⅰ. 차세대 시스템 전환의 성패를 가르는 데이터 이관 개요

### 가. 데이터 이관(Data Migration)의 정의
- **데이터 이관** : 기존 레거시 시스템(As-Is)에 저장된 대용량 데이터를 신규 구축 시스템(To-Be)의 목표 데이터베이스 구조로 **추출** (Extraction), **변환** (Transformation), **적재** (Loading)하고, 정합성을 철저히 검증하여 안정적으로 서비스를 개통하는 일련의 엔지니어링 프로세스.

### 나. 데이터 이관 프로젝트의 3대 핵심 난제
- **다운타임(Downtime) 한계** : 주말 또는 야간의 수 시간 이내에 수십 테라바이트(TB) 적재 완료 필요.
- **데이터 정합성(Consistency) 불일치** : 단 한 건의 금액이나 계좌 불일치도 차세대 오픈 취소로 직결.
- **스키마 구조 불일치** : 20년간 누적된 레거시 시스템의 비표준 암묵적 데이터 정제 필요.

## Ⅱ. 엔드투엔드 데이터 이관 5단계 추진 절차

```text
[ 데이터 이관 5단계 로드맵 ]
[1. 분석 및 계획] ---> [2. 이관 설계 및 매핑] ---> [3. 이관 개발 및 테스트]
- 범위 획정, 용량 산정     - 원천-목표 컬럼 매핑         - ETL 스크립트 작성
- 이관 전략 및 절차서       - 코드 매핑, 정제 룰 확정      - 모의 이관 반복 수행 (1~4차)
                                                                 |
                                                                 v
[5. 사후 안정화] <--- [4. 본 이관 및 무중단 전환 (Cut-over)] <---+
- 정합성 최종 서명         - 초기 벌크 적재 + CDC 증분 반영
- 오류 데이터 사후 정제   - 100% 전수 정합성 검증 후 서비스 오픈
```

## Ⅲ. 초고속 데이터 적재 및 실시간 CDC 무중단 전환 전략

### 가. 대용량 벌크 적재 최적화 기술
- 다이렉트 **패스 인서트 (Direct Path Insert)** : 버퍼 캐시를 우회하고 HWM(High Water Mark) 뒤에 직접 블록 쓰기 수행 (`/*+ APPEND */`).
- **NOLOGGING** / UNLOGGED 모드 : 대량 적재 시 Redo/WAL(Write-Ahead Logging) 로그 기록을 일시 중단하여 디스크 I/O 절감 (적재 완료 직후 즉시 백업 수행 필수).
- 제약조건 및 인덱스 비활성화 : 적재 전 PK(Primary Key), FK(Foreign Key), Index를 비활성화(`UNUSABLE`)하고, 적재 완료 후 병렬(`PARALLEL`)로 일괄 재빌드.

### 나. CDC 기반 무중단 컷오버(Cut-over) 타임라인

```text
[ 무중단 CDC 컷오버 시나리오 ]
t0: 원천 DB 기준 SCN(스냅샷) 생성 및 CDC 캡처 시작
    |
t1: SCN 시점의 초기 대용량 데이터 덤프 및 To-Be DB 벌크 적재 수행 (수 시간 소요)
    |
t2: 벌크 적재 완료 후, t0~t2 사이에 발생한 증분 트랜잭션을 CDC로 초고속 Replay (지연시간 0초 수렴)
    |
t3: [다운타임 진입] As-Is 서비스 접속 차단 -> 잔여 최종 트랜잭션 동기화 확인
    |
t4: [정합성 검증] 자동화 검증 도구 수행 (수 분 소요) -> 성공 판정
    |
t5: To-Be 시스템 DNS 스위칭 및 서비스 정식 개통!
```

## Ⅳ. 대용량 데이터 이관(Data Migration)의 주요 한계점 및 해결 방안

- **다운타임 윈도우** (Cutover Window) 제약과 대량 데이터 전송 병목 :
  - 한계점 : 차세대 시스템 전환 시 허용된 다운타임(예: 주말 24시간) 내에 수십 테라바이트 데이터를 물리적으로 이관·인덱싱하기 어려운 한계.
  - 해결 방안 : 사전 **초기 적재** (Initial Load) 후 실시간 **변경 데이터 캡처** (CDC, Change Data Capture: Debezium, GoldenGate) 기반 변경분 동기화, 전환 당일 최소 다운타임(Near-Zero Downtime) 컷오버 수행.
- 소스-타깃 시스템 간 데이터 타입 및 스키마 불일치로 인한 데이터 왜곡 :
  - 한계점 : Oracle에서 오픈소스 PostgreSQL/MySQL로 이관 시 문자열 인코딩, 날짜 포맷, LOB 데이터 처리 차이로 인한 데이터 잘림 및 정합성 결함 발생.
  - 해결 방안 : **스키마 자동 변환 도구** (AWS(Amazon Web Services) SCT 등) 활용, 이관 전 사전 매핑 룰 정의 및 모의 이관(Mock Migration) 3회 이상 의무화.
- 사후 데이터 정합성 전수 검증의 기술적 난제 :
  - 한계점 : 수억 건에 달하는 테이블의 건수 비교만으로는 속성 레벨의 미세한 값 왜곡을 검출하지 못하며, 전체 해시 비교 시 막대한 시간 소요.
  - 해결 방안 : 청크(Chunk) 단위 병렬 **체크섬** (Checksum/MD5) 비교 스크립트 운영, 비즈니스 핵심 지표(원장 잔액, 합계) 대사 자동화 파이프라인 가동.

## Ⅴ. 무결성 및 정합성 검증 체계와 실무 제언

### 가. 3단계 전수 정합성 검증 프레임워크

| 검증 단계 | 검증 대상 및 기법 | 검증 메커니즘 | 허용 오차 |
| :--- | :--- | :--- | :--- |
| **1단계: 건수 검증 (Count)** | 전체 테이블별 총 레코드 수 | 원천 건수 - 예외 건수 = 목표 건수 대조 | 오차 0건 (100% 일치) |
| **2단계: 합계 검증 (Sum)** | 금액, 수량 등 핵심 계량 수치 | `SUM(SALES_AMOUNT)`, 잔액 총합 대조 | 오차 0원 (100% 일치) |
| **3단계: 내용 검증 (Hash / Diff)** | 개별 컬럼 값의 정확성 | 행 단위 SHA(Secure Hash Algorithm)-256 해시값 생성 후 비교 (`MINUS` 쿼리) | 오차 0건 (완전 일치) |

### 나. 데이터 이관 프로젝트 성공을 위한 실무 제언
- **모의 이관** (Dry-Run) 복수 회 의무화 : 본 이관 당일에는 온갖 예기치 못한 스토리지 공간 고갈, 인덱스 락, 네트워크 대역폭 병목이 발생하므로, 본 이관과 동일한 인프라 스펙에서 사전 리허설(모의 이관)을 반복하여 소요 시간을 분 단위로 예측해야 함.
- **비상 롤백** (Rollback) 시나리오 사전 승인 : 본 이관 수행 중 정합성 검증이 실패하거나 목표 시간(RTO, Recovery Time Objective)을 초과할 경우를 대비하여, 미련 없이 구 시스템으로 복귀하는 롤백 의사결정 시점(Point of No Return)을 정하고 경영진의 사전 서명을 받아둘 것을 제언함.
