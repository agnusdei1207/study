## 연관 키워드

데이터베이스 복제, 동기식·비동기식·반동기식 복제, 단일 리더·다중 리더·리더리스, SBR·RBR, Quorum, RPO·RTO, CRDT, Raft·Paxos, 스플릿 브레인

## Ⅰ. 데이터베이스 복제의 개요

- 핵심 요약 : 주 데이터베이스의 변경을 복제본에 지속 전달해 가용성과 확장성을 확보하는 기술.
- 개념 : 데이터베이스(DB, Database)의 변경 내용을 하나 이상의 복제본에 전달해 같은 상태를 유지하는 기술 (**데이터베이스 복제**, Database Replication).
- 배경 및 필요성 : 단일 DB는 장애 한 번에 서비스 전체가 멈추고 읽기 부하가 한곳에 몰리는 구조이므로, 이 비용을 줄이려면 복제본 계층을 따로 두어 가용성과 부하 분산을 맡겨야 함.
- 주요 목적 : 무중단 가용성 확보, 읽기 부하 분산, 지리적으로 가까운 복제본을 통한 응답 지연 단축.

## Ⅱ. 데이터베이스 복제의 특징 및 장점

- 핵심 요약 : 동기화 시점, 토폴로지, 전송 계층의 세 축을 조합해 정합성과 응답 속도의 균형을 고르는 설계.

1. **동기식 복제** : 커밋 전에 복제본의 응답 확인(ACK, Acknowledgement)을 기다림 → 데이터 무손실에 가깝지만 쓰기 지연 증가.
2. **비동기식 복제** : 커밋 후 백그라운드로 복제본에 전송 → 응답이 빠르지만 장애 시 미전송 데이터 유실 위험.
3. **반동기식 복제** : 최소 한 개 노드의 ACK를 받은 뒤 커밋 → 무손실 수준을 높이면서 동기식보다 지연을 줄임.
4. **단일 리더** : 쓰기를 리더 한 곳에서만 처리 → 충돌이 없지만 쓰기 확장은 불가능.
5. **다중 리더**와 **리더리스** : 여러 노드가 쓰기를 받음 → 쓰기 분산과 강건성 확보, 대신 충돌 해결 로직 필요.

## Ⅲ. 복제 구조와 동기화 흐름

- 핵심 요약 : 커밋이 복제본 응답을 기다리는 시점에 따라 데이터 흐름이 갈리고, 전달 단위는 문장 단위와 행 단위로 나뉨.

```text
[ 동기식 복제 ]

Client 쓰기 요청
      ↓
Primary 기록
      ↓
Standby 반영 후 ACK
      ↓
Client에 커밋 응답
```

```text
[ 비동기식 복제 ]

Client 쓰기 요청
      ↓
Primary 기록 후 즉시 커밋 응답
      ↓
(백그라운드) Standby로 전송
```

- 토폴로지 : 단일 리더는 쓰기 노드가 하나, 다중 리더는 여러 노드가 쓰기를 받고, 리더리스는 클라이언트가 **Quorum** (정족수, 읽기·쓰기에 필요한 최소 응답 수)으로 판정.
- 전송 계층 : **SBR** (Statement-Based Replication, 문장 단위 복제)은 SQL 문장을 그대로 전달하고, **RBR** (Row-Based Replication, 행 단위 복제)은 바뀐 행의 값을 전달하며, 두 방식을 상황에 따라 섞는 Mixed 방식도 있음.

```text
[ 토폴로지 3형태 ]

단일 리더 : 쓰기 노드 1곳 → 충돌 없음
다중 리더 : 쓰기 노드 여러 곳 → 충돌 해결 필요
리더리스  : Quorum으로 읽기·쓰기 판정
```

## Ⅳ. 토폴로지 비교

- 핵심 요약 : 쓰기를 받는 위치에 따라 충돌, 확장성, 강건성이 서로 맞바꾸는 관계에 있음.

| 비교 축 | 단일 리더 | 다중 리더 | 리더리스 |
| --- | --- | --- | --- |
| 쓰기 경로 | 리더 한 곳 | 복수 리더 | 클라이언트가 여러 노드에 기록 |
| 충돌 | 발생하지 않음 | 발생 가능, 해결 규칙 필요 | 버전 비교로 관리 |
| 강건성 | 리더 장애 시 페일오버 필요 | 한 리더가 죽어도 쓰기 지속 | 단일 장애점 없음 |
| 정합성 | 강함 | 충돌 해결 규칙에 의존 | W + R > N 조건으로 관리 |

- 선택 기준 : 쓰기 충돌을 허용할 수 없으면 단일 리더, 지역별 쓰기가 필요하면 다중 리더, 가용성이 정합성보다 우선이면 리더리스를 검토함.

## Ⅴ. 한계와 방안

- 핵심 요약 : 지연, 유실, 충돌, 비결정성 같은 한계를 반동기 복제, 합의 프로토콜, 충돌 없는 데이터 타입으로 통제.
- 관리 지표 : **RPO** (Recovery Point Objective, 목표 복구 시점)는 유실 허용 범위를, **RTO** (Recovery Time Objective, 목표 복구 시간)는 복구 소요 한도를 나타냄.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 동기 지연 | 모든 복제본의 ACK를 기다려 처리량 저하 | 반동기 복제로 ACK 대상을 최소화 | 쓰기 지연 시간 |
| 비동기 유실 | 리더 장애 시 미전송 데이터 소실 | 무손실이 필요한 구간에 동기·반동기 적용 | RPO |
| 다중 리더 충돌 | 동시 갱신과 네트워크 분단으로 값이 갈라짐 | **CRDT** (Conflict-free Replicated Data Type) 적용 | 충돌 발생률 |
| **스플릿 브레인** | 분단된 노드가 각자 리더를 주장 | 합의 기반 리더 선출, 구 리더 펜싱 | 리더 전환 횟수 |
| SBR 비결정성 | NOW(), UUID() 같은 함수가 노드마다 다른 값 생성 | RBR 또는 Mixed 방식으로 전환 | 복제 불일치 건수 |

- 합의 프로토콜 : **Raft**와 **Paxos**는 과반수 투표로 리더를 하나만 인정하게 만들어 스플릿 브레인을 막는 알고리즘임.

## Ⅵ. 기술사적 제언

- 핵심 요약 : 복제 지연을 상시 감시하고, 장애 전환은 합의 기반 도구에 맡기며, 다중 쓰기 데이터는 충돌 없는 타입으로 설계해야 고신뢰 복제가 됨.

1. 읽기 일관성 확보 : 쓰기 직후 최신 값이 필요한 경로는 Primary에서 읽도록 라우팅해, 복제 지연으로 오래된 값을 읽는 문제를 막는다.
2. 장애 전환 자동화 : 분산 설정 저장소를 쓰는 Patroni 같은 오케스트레이터에 리더 선출을 맡겨 사람의 판단 지연과 분할 장애 위험을 함께 줄인다.
3. 다중 쓰기 데이터 설계 : 여러 지역에서 동시에 갱신되는 데이터는 병합 규칙이 정해진 CRDT 계열 타입을 고르고, 충돌 처리 로직을 애플리케이션에 떠넘기지 않는다.

## Ⅶ. 결론

- 핵심 요약 : 데이터베이스 복제는 동기화 시점, 토폴로지, 전송 계층의 조합으로 가용성과 정합성의 균형을 정하는 설계 문제임.
- 시사점 : 복제 방식은 RPO와 RTO 목표에서 역산해 고르는 것이 기본이며, 복제 지연을 측정하는 체계가 있어야 선택한 방식이 실제 보장으로 이어짐.
