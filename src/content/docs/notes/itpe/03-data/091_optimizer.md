```text
[옵티마이저 (Optimizer)] ◀━━ 머리: Ⅶ 내 의견 (통계정보 수집 자동화와 힌트 격리를 통한 CBO 적응형 최적화 신뢰 확보)
 ┃
 ┣━ Ⅰ 개요 ───── 사용자가 입력한 선언적 SQL을 해석하여 최소의 시스템 자원(I/O, CPU)으로 최단 시간에 결과를 반환하도록 최적의 실행 계획을 수립하는 DBMS 핵심 엔진
 ┣━ Ⅱ 특징 ───── 선언적 언어의 절차적 변환 · 실행 경로 탐색 · 비용 산정(선택도, 카디널리티) · RBO에서 CBO로 진화 · 힌트 기반 오버라이드
 ┣━ Ⅲ 구조 ───── 파서(Parser) ➔ 질의 변환기(Query Transformer) ➔ 대안 생성기(Plan Generator) ➔ 비용 산정기(Cost Estimator) ➔ 코드 생성기
 ┣━ Ⅳ 흐름 ───── ① SQL 문법/의미 파싱 → ② 서브쿼리 언네스팅/뷰 머징 등 논리 변환 → ③ 접근 경로/조인 방식 후보 생성 → ④ 통계 기반 비용 계산 → ⑤ 최적 플랜 확정
 ┣━ Ⅴ 비교 ───── RBO vs CBO vs 적응형 옵티마이저(Adaptive) (정적 우선순위 15개 vs 통계 기반 동적 비용 계산 vs 런타임 피드백 실시간 플랜 보정)
 ┗━ Ⅵ 실무 ───── 통계 정보 부재로 인한 풀스캔 / 바인드 피킹(Bind Peeking) 왜곡 / 악성 힌트 남발로 인한 플랜 고착화
```

## 한 줄 본질
- 비절차적 SQL만으로는 물리적 저장 구조에 최적화된 데이터 접근 경로 결정 불가 → 구문 분석, 논리적 질의 재작성, 통계 기반 비용 계산을 거쳐 최소 비용 실행 계획 확정 → 쿼리 처리 속도 극대화 / 통계 오염 시 최악의 플랜 채택 위험

## 핵심 그림
```text

 │ 1. 파서     │ : 문법(Syntax) 검사, 의미(Semantic) 검사, 파스 트리 생성
 └──────┬──────┘

 ┌─────────────┐
 │2. 질의변환기│ : 서브쿼리 언네스팅(Unnesting), 뷰 머징, 조건절 전이
 └──────┬──────┘
        ▼
 ┌─────────────┐      ┌──────────────────────────────┐
 │3. 대안생성기│ ───► │ 4. 비용 산정기 (Estimator)   │
 │ (후보 플랜) │      │   - 선택도 (Selectivity)     │
 └──────┬──────┘      │   - 카디널리티 (Cardinality) │

```

## 핵심 용어
- 질의 변환기(Query Transformer): 원본 SQL을 성능상 유리한 동등한 형태의 내부 SQL(예: Subquery $\rightarrow$ Semi-Join, View Merging)로 자동 재작성하는 핵심 모듈
- 선택도(Selectivity): 전체 레코드 중 특정 조건에 의해 필터링되어 반환될 것으로 예상되는 행의 비율($1 / \text{Distinct Values}$)

## 핵심 통찰
- 옵티마이저는 모든 가능한 실행 계획을 다 계산해보지 않음 → 테이블이 10개만 넘어가도 가능한 조인 순서의 조합($10!$)이 수백만 개에 달하므로 시간 제한 내에 휴리스틱 탐색(동적 프로그래밍, 유전 알고리즘)으로 조기 종료
- 옵티마이저 판단 실패의 99%는 '비용 산정 공식의 오류'가 아니라 '입력 통계의 부정확함' 때문임 → 테이블 통계가 어제 날짜로 고정되어 있으면 아무리 뛰어난 옵티마이저도 쓰레기 플랜을 생성
- 바인드 변수를 사용할 때 옵티마이저가 최초 실행 시점의 변수값만 엿보고 플랜을 영구 고정하는 '바인드 피킹(Bind Peeking)'은 운영 시스템의 대표적 플랜 급변(Plan Flapping) 원인

## 이웃 토픽과 구분
- 옵티마이저 vs 실행 계획: 옵티마이저 = 최적의 경로를 찾아내는 판단 알고리즘 엔진(주체) / 실행 계획 = 옵티마이저가 최종 확정한 절차적 작업 명세서(산출물)

## 문제·원인·대책
- 적용 상황: 대용량 트랜잭션 시스템에서 특정 시간대 동일 쿼리의 극심한 속도 편차
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 동일 쿼리가 어떤 날은 0.01초, 어떤 날은 20초 걸리며 시스템 마비 | 바인드 피킹으로 편향된 특정 파라미터 값에 맞춘 플랜이 라이브러리 캐시에 고착화 | Adaptive Cursor Sharing(ACS) 활성화 또는 편향 컬럼 리터럴 분리 | 변수 분포에 따른 동적 실행계획 분기 보장 |
| 인덱스가 존재함에도 옵티마이저가 풀 테이블 스캔(FTS) 강제 선택 | 컬럼 가공(`WHERE SUBSTR(code,1,3) = 'ABC'`)으로 인한 인덱스 무력화 | FBI(함수 기반 인덱스) 생성 또는 조건절 원본 복원(`WHERE code LIKE 'ABC%'`) | 인덱스 레인지 스캔 정상 복원 및 I/O 99% 절감 |

## 이렇게 출제된다
- 제127회: "관계형 데이터베이스 관리시스템(RDBMS)의 옵티마이저(Optimizer)의 역할과 주요 구성 요소(파서, 질의 변환기, 대안 생성기, 비용 산정기)의 동작 방식을 설명하시오." → 요구 포인트: 옵티마이저 정의 + 4대 구성요소의 역할과 상호작용 + 선택도/카디널리티 기반 비용 계산 개념

## 내 의견
- [옵티마이저 힌트 만능주의 청산] 개발자가 쿼리가 조금만 느려도 CBO를 불신하고 `/*+ LEADING(...) USE_NL(...) */` 같은 힌트를 덕지덕지 붙여 놓으면, 데이터 볼륨이 10배 커졌을 때 Hash Join으로 전환되어야 할 쿼리가 끝까지 NL Join으로 버티다 대형 장애 발생 → 나라면: 힌트는 P1급 긴급 장애 복구용 임시 패치로만 제한하고, 근본적으로는 테이블/인덱스 통계 수집과 히스토그램 최적화로 CBO 스스로 올바른 결정을 내리도록 체계 정비
