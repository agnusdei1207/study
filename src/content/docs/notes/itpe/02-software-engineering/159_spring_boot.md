소프트웨어 공학 → 프레임워크 → **스프링 부트(Spring Boot)**

## 30초 인출

- 본질: 스프링 부트는 스프링 프레임워크의 복잡한 설정을 자동화해 독립 실행형 애플리케이션을 빠르게 만들게 하는 프레임워크
- 메커니즘: 스타터 의존성이 필요한 라이브러리를 묶어 가져오고 자동 설정이 클래스패스의 라이브러리를 보고 기본 설정을 구성하며 내장 서버로 바로 실행
- 통찰: 자동 설정은 기본값을 가정하므로 운영에서 의도와 다르게 동작할 수 있어 실제 적용된 설정을 확인하고 필요한 값만 명시적으로 재정의

<details>
<summary>핵심 용어</summary>

- **스프링 부트(Spring Boot)** : 설정 자동화와 내장 서버로 스프링 애플리케이션을 간편하게 만드는 프레임워크
- **스타터(Starter)** : 특정 기능에 필요한 의존성을 묶어 둔 의존성 묶음
- **자동 설정(Auto-Configuration)** : 클래스패스의 라이브러리를 보고 기본 설정을 자동으로 구성하는 기능
- **내장 서버(Embedded Server)** : 애플리케이션에 포함되어 별도 서버 설치 없이 실행되는 웹 서버
- **액추에이터(Actuator)** : 상태 확인·지표 등 운영용 엔드포인트를 제공하는 기능

</details>

## 2~4교시 25점 답안

## Ⅰ. 스프링 부트의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **스프링 부트** 는 설정을 자동화하고 내장 서버를 포함해 스프링 애플리케이션을 간편하게 만드는 프레임워크 |
| 목적 | 초기 설정 부담 감소와 빠른 개발·배포 |

## Ⅱ. 스프링 프레임워크와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 스타터 | 의존성 묶음으로 버전 조합 부담 감소 |
| 자동 설정 | 라이브러리에 맞춘 기본 설정 자동 구성 |
| 내장 서버 | 별도 WAS 설치 없이 실행 |
| 운영 기능 | 액추에이터로 상태·지표 제공 |

## Ⅲ. 구성과 시작 흐름

```text
스타터 의존성 추가
      ↓
클래스패스 라이브러리 확인 → 자동 설정
      ↓
내장 서버 기동 → 애플리케이션 실행
```

## Ⅳ. 스프링과 스프링 부트의 비교

| 구분 | 스프링 프레임워크 | 스프링 부트 |
|---|---|---|
| 설정 | 직접 구성 | 자동 설정 |
| 의존성 | 개별 선택·버전 조율 | 스타터 |
| 서버 | 외부 WAS에 배포 | 내장 서버로 실행 |
| 운영 지표 | 별도 구성 | 액추에이터 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 자동 설정이 어떤 값을 적용하는지 알기 어려움 | 적용된 설정 확인 기능으로 점검 |
| 기본값이 운영 요구와 어긋남 | 필요한 값만 명시적으로 재정의 |
| 불필요한 스타터로 실행 파일 비대 | 필요한 스타터만 사용 |

## Ⅵ. 제언

운영 배포 전에 실제 적용된 자동 설정을 확인하고, 운영 요구와 다른 값만 명시적으로 재정의

```text
자동 설정 적용 결과 확인
      ├─ 운영 요구와 일치 → 유지
      └─ 불일치 → 해당 값만 명시적 재정의
```

| 구분 | 기본값 그대로 사용 | 제언: 확인 후 재정의 |
|---|---|---|
| 운영 적합성 | 사후 발견 | 배포 전 확인 |
| 설정 관리 | 암묵적 | 변경분 명시 |
