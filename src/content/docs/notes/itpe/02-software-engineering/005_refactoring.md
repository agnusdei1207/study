## 연관 키워드

- 리팩토링(Refactoring), 동작 보존, 코드 스멜(Code Smell), 자동화 시험, 중복 제거
- 메서드 추출(Extract Method), 특성화 시험(Characterization Test), 재작성(Rewrite)

## Ⅰ. 리팩토링의 개요

- 핵심 요약 : 겉으로 드러나는 동작을 바꾸지 않으면서 내부 구조를 개선해 변경 비용을 낮추는 통제된 코드 변환 기법.
- 개념 : 소프트웨어의 관찰 가능한 동작을 유지하며 내부 구조를 개선하는 변경 기법이 **리팩토링** (Refactoring).
- 배경 및 필요성 : 기능 추가·수정의 반복으로 중복·긴 메서드·엉킨 의존 관계가 누적되어 작은 변경에도 수정 범위가 커지는 구조 저하 발생.
- 주요 목적 : 유지보수성·가독성·확장성 향상과 결함 수정·기능 추가 비용의 지속적 절감.

## Ⅱ. 리팩토링의 특징 및 장점

- 핵심 요약 : 동작 보존 전제 아래 코드 스멜을 신호로 삼아 시험 보호망에서 작은 변환을 반복.

1. 동작 보존 : **동작 보존** (Behavior Preservation, 외부에서 관찰되는 입력·출력 관계의 유지)을 전제 → 기능 변경과 구조 개선의 책임 분리.
2. 작은 단계 변환 : **메서드 추출** (Extract Method)·이름 변경 같은 단일 변환을 한 번에 적용 후 즉시 시험 → 회귀 원인의 신속한 특정.
3. 코드 스멜 기반 판단 : **코드 스멜** (Code Smell, 구조 문제를 알리는 표면 신호)을 개선 대상 선정 근거로 활용 → 주관 아닌 공통 기준 확보.
4. 시험 보호망 : 자동화 시험이 변경 전후 동작 일치를 검증 → 구조 개선의 안전성 확보.

## Ⅲ. 리팩토링의 구조 (흐름)

- 핵심 요약 : 스멜 탐지→기준선 확인→단일 변환→시험→기록의 주기를 반복하는 점진적 개선 절차.

```text
코드 스멜 탐지
   ↓
기존 자동화 시험 실행 (기준선 확인)
   ↓
단일 변환 적용 (예: 메서드 추출)
   ↓
전체 시험 재실행
   ↓
버전관리에 커밋
```

```text
중복 코드     → 메서드·클래스 추출로 통합
긴 메서드     → 메서드 추출로 책임 분할
기능 편애     → 메서드 이동으로 소속 재조정
거대 클래스   → 클래스 추출로 관심사 분리
```

- 대표 변환 : 메서드 추출, 이름 변경, 메서드 이동, 중복 제거 등이 작은 단계의 표준 변환 목록.
- 적용 범위 : 공개 인터페이스·저장 데이터 구조는 외부 계약이므로 하위 호환 조건에서 다룸.

## Ⅳ. 리팩토링과 재작성(Rewrite)의 비교

- 핵심 요약 : 리팩토링이 기존 동작 위의 점진적 구조 개선인 반면 **재작성** (Rewrite, 기존 코드를 버리고 새로 구현하는 방식)은 전환 위험을 함께 안음.

| 비교 축 | 리팩토링 | 재작성 (Rewrite) |
| --- | --- | --- |
| 대상 범위 | 기존 코드의 내부 구조 | 시스템 전체·주요 모듈의 재구현 |
| 동작 연속성 | 관찰 가능한 동작 유지 | 신규 구현의 동작 재정의 수반 |
| 위험 성격 | 작은 단계의 즉시 검증 가능 | 요구 누락·전환 시점의 일괄 위험 |
| 투입 방식 | 지속적 소규모 투입 | 장기 집중 투입 후 일괄 전환 |
| 적합 상황 | 동작 유지하며 구조만 개선할 때 | 기반 기술·요구가 근본적으로 변경될 때 |

## Ⅴ. 리팩토링의 한계와 방안

- 핵심 요약 : 시험 부족·변경 혼재·범위 상실·계약 파괴가 동작 보존을 흔드는 요인으로 기준선과 경계 관리 필요.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 자동화 시험 부족 | 동작 보존의 입증 수단 부재 → 숨은 동작 손상 | **특성화 시험** (Characterization Test, 현 동작을 기록해 기준선으로 삼는 시험)으로 기준선 확보 | 회귀 결함 수 |
| 기능 변경과의 혼재 | 동작 변화와 구조 변화가 한 커밋에 섞여 원인 추적 곤란 | 변경 유형별 커밋 분리·리뷰 기준 적용 | 유형 혼재 커밋 비율 |
| 과도한 개선 | 개선 범위의 경계 상실 → 일정 지연 | 개선 목표·범위의 백로그 사전 합의 | 리팩토링 소요 공수 비율 |
| 외부 계약 파괴 | 공개 인터페이스·데이터 구조 변경이 연동 시스템 장애로 확산 | 하위 호환 유지·전환 어댑터 적용 | 호환성 위반 건수 |

## Ⅵ. 리팩토링 정착에 대한 제언

- 핵심 요약 : 백로그·도구·품질 계획에 구조 개선을 상시 과제로 편성해 일회성 정리가 아닌 운영 체계로 확립.

1. 개발 조직은 기능 변경 전후 구조 개선 과제를 백로그에 상시 등록하고 정적 분석 도구의 스멜 지표를 점검 항목으로 통합.
2. 품질 조직은 리팩토링 대상 모듈의 시험 커버리지 기준을 품질 계획에 명시하고 미달 모듈의 개선 우선순위를 지정.
3. 아키텍처 검토 회의에서 구조 개선 성과를 변경 소요 시간·결함 밀도 추세로 정기 보고해 경영진 승인 과제로 관리.

## Ⅶ. 결론

- 핵심 요약 : 리팩토링은 동작 보존을 전제로 변경 비용 상승을 억제하는 지속적 구조 관리 활동.
- 시사점 : 코드 스멜은 즉시 수정 명령이 아니라 구조 위험을 조사할 단서로 해석 필요.
