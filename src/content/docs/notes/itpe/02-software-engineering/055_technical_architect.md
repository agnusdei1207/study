## 한 줄 본질
- 애플리케이션 개발자만으로는 서버, 클라우드, 네트워크, 미들웨어의 복잡한 비기능 요구사항(TPS, 가용성 99.99%)을 충족할 수 없는 아키텍처 공백 병목 → 시스템의 하부 인프라 구조를 설계하고 하드웨어 용량 산정, 미들웨어 튜닝, 재해복구(DR) 기술을 전담 총괄 → 시스템 안정성과 고성능 보장 / 클라우드 기술 급변에 따른 학습 및 관리 복잡도 대가

## 핵심 용어
- 용량 산정(Capacity Sizing): 시스템의 예상 동시 접속자 수, 트랜잭션 빈도, 데이터 증가량을 바탕으로 필요한 CPU, 메모리, 스토리지, 네트워크 대역폭을 과학적으로 계산하는 작업
- 클라우드 네이티브 TA: 온프레미스 장비 발주 중심에서 벗어나 쿠버네티스 오케스트레이션, 테라폼(IaC), 마이크로서비스 네트워크(Service Mesh), 클라우드 비용(FinOps)을 설계하는 현대적 TA

## 핵심 통찰
- AA가 "비즈니스 기능(What)을 어떻게 프로그램으로 구조화할 것인가"를 고민한다면, TA는 "그 프로그램이 무너지지 않고 빠르게 돌 수 있는 기술 기반(How Platform Runs)"을 구축함
- 클라우드 환경에서 TA의 역할은 서버 조립과 OS 설치 같은 물리적 관리에서, IaC 코드를 통한 인프라 자동화와 관측성(Observability) 아키텍처 설계로 완전히 재정의됨
- TA가 설계한 인프라가 아무리 강력해도 AA가 작성한 애플리케이션에 락 경합이나 메모리 누수가 있으면 시스템이 다운되므로, TA와 AA의 밀접한 성능 튜닝 협업이 필수적임

## 이웃 토픽과 구분
- TA vs AA: TA = 비기능 요구(성능, 인프라, 가용성, 배포) / AA = 기능 요구(비즈니스 모델, 컴포넌트 설계, 도메인 아키텍처)

## 내 의견
- [인프라만 만지고 코드는 모르는 전통적 TA의 한계] 클라우드 시대에 인프라 엔지니어가 애플리케이션 코드나 CI/CD 파이프라인을 전혀 이해하지 못해, 개발팀과 인프라팀이 여전히 서로 남 탓만 하는 구시대적 사일로 잔존 → 나라면: 테라폼(Terraform)과 쿠버네티스 선언적 코드를 다룰 수 있는 '소프트웨어 엔지니어링 역량을 갖춘 TA'를 육성하고, 애플리케이션 프로파일링(APM) 결과를 바탕으로 코드 레벨 최적화를 함께 수행하는 Dev-Infra 융합 체계 수립
