## 한 줄 본질
- 하나의 거대한 소프트웨어를 단일 책임과 명확한 인터페이스를 갖춘 독립적 블록들로 쪼개어 변경의 파급을 막고 재사용성을 높이는 소프트웨어 공학의 대원칙 / 높은 응집도와 낮은 결합도

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  버트란드 마이어(Meyer)의 모듈성 5대 평가 기준          |
+-------------------------------------------------------------------------+
| 1. 분해성(Decomposability) : 복잡한 문제를 작은 독립적 서브 모듈로 분할 |
| 2. 조합성(Composability)   : 기존 모듈들을 조립하여 새로운 시스템 구축  |
| 3. 이해성(Understandability): 다른 모듈을 몰라도 해당 모듈 단독 이해 가능|
| 4. 연속성(Continuity)      : 사소한 요구 변경이 소수의 모듈에만 국한 전파|
| 5. 보호성(Protection)      : 모듈 내 오류 발생 시 타 모듈로 장애 전파 방지|
+-------------------------------------------------------------------------+

```

## 핵심 용어
- 모듈성(Modularity): 소프트웨어 시스템이 모듈이라 불리는 개별적이고 자율적인 구성 요소들로 얼마나 잘 분해되어 있는지를 나타내는 척도
- 정보 은닉(Information Hiding): 모듈 내부의 복잡한 구현 세부사항이나 데이터 구조를 외부로부터 숨기고, 오직 정의된 공개 인터페이스(Public Interface)를 통해서만 접근하도록 제한하는 기법
- 분해성(Decomposability): 시스템 설계를 하향식으로 체계적인 서브 문제로 분해하여 각 서브 문제를 독립적으로 해결할 수 있는 정도
- 연속성(Continuity): 시스템의 요구사항에 작은 변화가 생겼을 때, 코드 변경의 영향이 전체로 번지지 않고 오직 한두 개의 국소 모듈에만 영향을 미치는 특성
- 보호성(Protection): 런타임에 특정 모듈 내부에서 비정상 예외(Exception)나 장애가 발생했을 때 그 영향이 다른 모듈로 파급되지 않고 해당 모듈 내에 국한되는 특성

## 핵심 통찰
- 소프트웨어 공학의 역사는 본질적으로 '어떻게 모듈성을 극대화할 것인가'의 역사임 (함수 → 객체 → 컴포넌트 → 서비스)
- 모듈성이 낮은 시스템은 하나의 기능을 수정했을 때 예상치 못한 다른 기능이 연쇄적으로 고장 나는 '소프트웨어 부패(Software Rot)'를 겪게 됨
- 모듈성의 정량적 건전성은 '응집도(Cohesion: 높을수록 좋음)'와 '결합도(Coupling: 낮을수록 좋음)'라는 두 축으로 판정됨
- 그러나 시스템을 너무 잘게 쪼개면 모듈 간의 호출 빈도와 통신 오버헤드, 통합 복잡도가 증가하므로, 비즈니스 맥락(Bounded Context)에 부합하는 적정 입도(Granularity) 설정이 중요함

## 이웃 토픽과 구분
| 비교 항목 | 모듈 (Module) | 컴포넌트 (Component) | 객체 (Object) | 마이크로서비스 (Service) |
| :--- | :--- | :--- | :--- | :--- |
| **개념적 위상** | 논리적 기능 분할 단위 (파일/패키지) | 독립 배포 가능한 바이너리 단위 (JAR/DLL) | 상태와 행위가 캡슐화된 런타임 인스턴스 | 독립 배포 및 실행되는 네트워크 서비스 |
| **결합 형태** | 컴파일 타임 의존성 | 런타임 링크 및 바인딩 | 메모리 주소 직접 참조 | 네트워크 API (HTTP/gRPC) 통신 |
| **독립 배포성** | 불가능 (전체 빌드 필요) | 가능 (단독 교체 가능) | 불가능 (프로세스 내 상주) | 완전 독립 배포 (컨테이너 단위) |
| **추상화 수준** | 프로그래밍 언어 수준 | 시스템 아키텍처 수준 | 객체지향 설계 수준 | 분산 엔터프라이즈 시스템 수준 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **단일 모듈 수정 시 전사적 사이드 이펙트 발생** | 모듈 간 전역 변수 공유 및 구현 세부사항에 직접 의존(내용/공통 결합도) | 데이터 직접 참조를 차단하고 인터페이스 기반 의존성 역전(DIP) 및 Getter/Setter 캡슐화 |
| **모듈 분할 과다로 인한 성능 저하 및 트레이싱 난항** | 기능 단위로 지나치게 잘게 쪼개어 모듈 간 함수 호출 및 컨텍스트 스위칭 급증 | 도메인 주도 설계(DDD)의 Bounded Context와 응집도(기능적 응집도) 기준으로 모듈 재통합 |
| **모듈 인터페이스의 잦은 변경으로 협업 장애** | 모듈 경계가 명확하지 않고 요구사항 정의가 불충분한 상태에서 조기 인터페이스 확정 | 계약에 의한 설계(Design by Contract) 및 인터페이스 분리 원칙(ISP)을 통한 인터페이스 최소화 |

## 이렇게 출제된다
- **10점형**: 소프트웨어 모듈성(Modularity)의 개념 및 버트란드 마이어(Meyer)가 제시한 모듈성 5대 기준을 설명하시오.
- **25점형**: 
  - 1) 소프트웨어 아키텍처에서 모듈성의 필요성과 설계 5대 원칙(직접/적은/작은/명시적 인터페이스, 정보 은닉)을 도식으로 제시하시오.
  - 2) 모듈성을 평가하는 핵심 척도인 응집도(Cohesion 7단계)와 결합도(Coupling 6단계)를 각각 높은 순서/낮은 순서대로 비교 설명하시오.
  - 3) 모놀리식 아키텍처를 마이크로서비스(MSA)로 전환할 때 모듈성 원칙을 적용하여 서비스 경계를 도출하는 실무 전략을 논하시오.

## 내 의견
- 많은 개발팀이 모듈성을 단순히 '파일을 여러 개로 쪼개는 것'으로 오해하지만, 인터페이스가 오염되어 있다면 수백 개의 파일로 쪼개도 모듈성은 제로(0)에 수렴함
- 진정한 모듈성은 다른 모듈의 내부를 전혀 알지 못해도(정보 은닉), 공개된 인터페이스 스펙만 보고 모듈을 레고 블록처럼 갈아 끼울 수 있을 때 완성됨
- 실무에서는 모듈 간의 순환 참조(Circular Dependency)를 정적 분석 도구(ArchUnit, SonarQube)로 상시 모니터링하고, 도메인 주도 설계(DDD)의 애그리거트(Aggregate) 단위로 강한 일관성을 묶어내는 아키텍처 거버넌스를 정립해야 함
