## 연관 키워드
- 모듈화, 응집도, 결합도, 모듈 경계, 정보 은닉, 인터페이스

### Ⅰ. 모듈화의 개요

- 핵심 요약 : 모듈화는 소프트웨어를 명확한 책임과 인터페이스를 가진 구성 단위로 나눠 변경과 이해를 관리하는 설계 원칙.
- 개념 : 기능·데이터·책임을 응집된 단위로 묶고 모듈 간 의존을 통제 하는 구조화 기법(**모듈화**, Modularity).
- 배경 및 필요성 : 규모가 커질수록 전체 코드의 이해와 변경 영향 분석이 어려워져 분해와 경계 설정 필요.
- 주요 목적 : 변경 범위와 복잡성을 줄이고 병렬 개발·시험·재사용 가능성을 높임.

### Ⅱ. 좋은 모듈의 특성

- 핵심 요약 : 모듈 내부 책임은 응집시키고 외부 의존은 안정된 인터페이스로 제한.

1. 높은 응집도 : 관련 데이터와 기능을 함께 배치 → 모듈 변경 이유 단순화.
2. 낮은 결합도 : 구현 세부가 아닌 계약에 의존 → 변경 전파 감소.
3. 정보 은닉 : 내부 표현과 알고리즘을 숨김 → 인터페이스를 유지 한 내부 개선 가능.
4. 단일 책임 경계 : 함께 변경되는 기능을 모음 → 테스트와 소유권 분리 용이.

### Ⅲ. 분해·호출 구조 (구조)

- 핵심 요약 : 상위 기능을 책임 단위로 분해 하고 의존 방향과 인터페이스를 명시.

```text
업무 기능
   ↓ 책임 기준 분해
모듈 A ──계약──> 모듈 B
   │                │
   └── 공통 규약 ───┘
```

```text
외부 호출
   ↓ 공개 인터페이스
모듈 내부 구현·데이터
   ↓ 결과·오류 계약
호출자
```

- 의존성 그래프의 순환은 테스트·배포 순서를 복잡하게 하므로 방향성 규칙과 계층을 통해 관리.

### Ⅳ. 결합도 비교

- 핵심 요약 : 결합은 구현 세부를 직접 공유할수록 강하고, 명시적 데이터·메시지 계약을 사용할수록 약함.

| 비교 축 | 내용 결합 | 공통 결합 | 제어 결합 | 스탬프 결합 | 데이터·메시지 결합 |
|---|---|---|---|---|---|
| 의존 내용 | 다른 모듈 내부를 직접 변경·참조 | 전역 데이터 공유 | 제어 플래그로 상대 동작 지시 | 큰 자료 구조 전체 전달 | 필요한 값 또는 계약으로 통신 |
| 일반적 위험 | 구현 변경이 즉시 파급 | 변경 영향·동시성 통제 곤란 | 호출자가 상대 내부 흐름을 알아야 함 | 불필요한 데이터 의존 | 계약 관리가 필요하나 의존 범위 명확 |

### Ⅴ. 모듈성의 한계와 방안

- 핵심 요약 : 과도한 세분화와 공유 상태, 순환 의존은 모듈성의 이점을 약화 하므로 변경 이유와 경계를 검증.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 지나친 세분화 | 호출·조립 복잡성과 추상화 비용 | 변경 응집도와 배포 단위에 맞춰 재통합 | 재통합 비율 |
| 숨은 공통 상태 | 전역 데이터·부수 효과 | 명시적 의존성 주입·불변 데이터 활용 | 공통 상태 건수 |
| 순환 의존 | 책임 경계 불일치 | 의존성 역전·계층 재설계 | 순환 의존 모듈 수 |
| 불안정한 인터페이스 | 구현 변경 때마다 소비자 수정 | 계약 버전 관리·호환성 시험 | 인터페이스 변경 건수 |

### Ⅵ. 설계·조직 제언

- 핵심 요약 : 아키텍트와 팀은 조직도 보다 업무 책임과 변경 패턴을 근거로 모듈 경계를 정함.

1. 코드 리뷰에서 모듈 공개 API, 데이터 소유자, 의존 방향을 확인 하고 내부 구현의 외부 노출을 최소화.
2. 측정 가능한 변경 이력과 결함 전파를 바탕으로 경계를 조정 하며, 모듈 수 자체를 성과 지표로 쓰지 않음.

### Ⅶ. 결론

- 핵심 요약 : 모듈화는 높은 응집도와 낮은 결합도를 통해 변경 가능한 소프트웨어 구조를 만드는 설계 원칙.
- 시사점 : 효과는 분해 자체가 아니라 책임 경계와 계약의 안정성에서 비롯.
