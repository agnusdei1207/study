## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 설계·품질 → 모듈성(결합도·응집도)

## 지식 위치

소프트웨어공학 > 소프트웨어 설계 > 모듈성

## 30초 인출

- 본질: 소프트웨어 시스템을 독립적인 기능과 책임을 수행하는 모듈 단위로 분할하여 복잡도를 낮추고 유지보수성을 극대화하는 설계 척도로, 높은 응집도(High Cohesion)와 낮은 결합도(Loose Coupling)를 지향
- 메커니즘: 단일 책임 원칙(SRP) 기반 모듈 분할 → 변경 가능한 내부 자료구조 및 알고리즘 은닉(Information Hiding) → 표준 인터페이스를 통한 통신 → 결합도 6단계 및 응집도 7단계 정량 평가/리팩토링
- 통찰: 과도한 미세 모듈 분할은 네트워크 레이턴시 및 분산 트랜잭션 관리 오버헤드를 유발하므로 도메인 주도 설계(DDD)의 Bounded Context에 입각한 최적 모듈 경계 설정 필수

<details>
<summary>핵심 용어</summary>

- **모듈성 (Modularity)** : 소프트웨어가 독립적으로 개발, 테스트, 유지보수될 수 있는 모듈 단위로 잘 나누어져 있는 공학적 특성
- **결합도 (Coupling)** : 모듈과 모듈 간의 상호 의존성(상호 연관성)의 세기를 나타내는 척도로, 약할수록(낮을수록) 독립성이 높음
- **응집도 (Cohesion)** : 모듈 내부를 구성하는 요소(명령문, 데이터, 함수)들이 단일 목적이나 책임을 달성하기 위해 얼마나 밀접하게 관련되어 있는지를 나타내는 척도로, 강할수록(높을수록) 바람직함
- **정보 은닉 (Information Hiding)** : 데이비드 파나스(David Parnas)가 제안한 원칙으로 변경 가능성이 높은 내부 구현 상세는 모듈 내부에 감추고 최소한의 안정적인 인터페이스만 외부에 공개하는 기법
- **Fan-in / Fan-out** : Fan-in은 특정 모듈을 호출하는 상위 모듈의 수, Fan-out은 특정 모듈이 호출하는 하위 모듈의 수
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 복잡하고 거대한 소프트웨어 시스템을 이해, 수정, 테스트가 용이하도록 독립된 역할과 명확한 인터페이스를 갖춘 서브시스템 또는 모듈 단위로 분해하고 조직화하는 설계 원리 |
| 목적 | 시스템 복잡도 완화, 변경의 파급 효과(Ripple Effect) 국소화, 재사용성 극대화 및 병렬 개발 생산성 향상 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 高응집·低결합 원칙 | 모듈 내부는 단일 목적을 위해 긴밀히 협력(High Cohesion)하고, 모듈 간 상호 의존성은 최소화(Loose Coupling) |
| 정보 은닉 (Information Hiding) | 모듈의 내부 구현 로직이나 자료구조를 캡슐화하여 외부의 무단 접근 및 변경 전파를 원천 차단 |
| 인터페이스 기반 상호작용 | 구체적인 구현체에 의존하지 않고 추상화된 공개 인터페이스(Contract)를 통해서만 느슨하게 결합 |
| 정량적 계측 가능성 | LCOM(Lack of Cohesion in Methods), CBO(Coupling Between Objects), Fan-in/Fan-out 등 정량 메트릭으로 측정 가능 |

전통적 함수 모듈화부터 현대적 객체지향 클래스 설계 및 마이크로서비스(MSA) 경계 획정에 이르는 모든 소프트웨어 아키텍처의 절대적 황금률.

## Ⅲ. 체계·프로세스

```text
[모듈성 최적화 아키텍처 및 정보 은닉 메커니즘]

[모듈 A (호출자)]                         [모듈 B (피호출자)]
  ┌───────────────────────┐                 ┌───────────────────────────────────┐
  │ 비즈니스 로직 실행    │                 │ [공개 인터페이스: Contract]       │
  │                       │                 │  + calculateTax(orderData): Money │
  │ publicInterface 호출 ──┼── 파라미터 전달 ──►│                                   │
  └───────────────────────┘ (자료 결합도)   ├───────────────────────────────────┤
                                            │ [내부 은닉 영역: Private Encapsulated]│
                                            │  - 국가별 세법 계산 복잡 로직     │
                                            │  - 내부 캐시 테이블 및 DB 접근     │
                                            │  - 변경 시 외부에 무영향 유지      │
                                            └───────────────────────────────────┘
```

```text
[Fan-in / Fan-out 기반 모듈 구조 최적화 흐름]
       [모듈 1]   [모듈 2]   [모듈 3]
          │          │          │
          └──────────┼──────────┘
                     ▼
             [공통 모듈: High Fan-in] ──► 재사용성이 매우 높음 (철저한 단위 테스트 필요)
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       [하위 모듈 A]         [하위 모듈 B]  ──► Low Fan-out 지향 (복잡도 최소화)
```

인터페이스를 통한 정보 은닉 실현과 High Fan-in / Low Fan-out 구조를 통한 아키텍처 복잡도 통제 프로세스.

## Ⅳ. 종류·비교

### 1. 결합도(Coupling) 6단계 (약함/우수 ──► 강함/불량)

| 결합도 단계 | 수준 | 설명 및 특징 | 실무 사례 |
|---|---|---|---|
| **자료 결합도 (Data)** | 가장 약함 (최선) | 모듈 간에 오직 단순 값(파라미터)만 전달되는 가장 이상적인 결합 | `add(int a, int b)` 호출 |
| **스탬프 결합도 (Stamp)** | 약함 | 레코드나 구조체 배열 등 복합 데이터 구조를 전달하나 일부 필드만 사용 | 객체 전체를 인자로 넘겨 특정 필드 1개만 참조 |
| **제어 결합도 (Control)** | 중간 | 한 모듈이 다른 모듈의 내부 처리 흐름을 제어하는 플래그를 전달 | 제어 플래그(true/false)에 따른 `if-else` 분기 실행 |
| **외부 결합도 (External)** | 강함 | 외부 통신 프로토콜, OS API, 외부 장치 인터페이스를 공유 | 외부 파일 포맷이나 OS 시그널에 직접 종속 |
| **공통 결합도 (Common)** | 매우 강함 | 여러 모듈이 전역 변수(Global Variable)나 공유 메모리를 직접 참조/수정 | 전역 설정 변수를 여러 모듈이 동시 변경 |
| **내용 결합도 (Content)** | 가장 강함 (최악) | 한 모듈이 다른 모듈의 내부 코드나 비공개 데이터에 직접 접근 | 타 모듈의 private 변수를 메모리 포인터로 조작 |

### 2. 응집도(Cohesion) 7단계 (강함/우수 ──► 약함/불량)

| 응집도 단계 | 수준 | 설명 및 특징 | 실무 사례 |
|---|---|---|---|
| **기능적 응집도 (Functional)** | 가장 강함 (최선) | 모듈 내부의 모든 요소가 단 하나의 고유 목적과 기능을 위해 협력 | 단일 수학 연산 함수 `Math.sqrt()` |
| **순차적 응집도 (Sequential)** | 강함 | 한 요소의 출력 결과가 다음 요소의 입력값으로 파이프라인처럼 연결 | 입력 데이터 수신 ──► 유효성 검증 ──► 암호화 |
| **교환적 응집도 (Communicational)** | 보통 | 동일한 입력 데이터를 사용하여 서로 다른 여러 기능을 수행 | 주문 객체를 받아 화면 출력도 하고 DB 저장도 수행 |
| **절차적 응집도 (Procedural)** | 보통 이하 | 다수의 기능이 특정 순서(절차)대로 실행되어야 하므로 한데 묶음 | 파일 열기 ──► 권한 확인 ──► 로그 기록 |
| **시간적 응집도 (Temporal)** | 약함 | 특정 시점(프로그램 기동, 종료 등)에 함께 실행된다는 이유로 묶음 | 시스템 초기화 함수(`initAll()`) |
| **논리적 응집도 (Logical)** | 매우 약함 | 논리적으로 유사한 작업(출력 작업, 입출력 등)을 하나의 모듈에 모음 | 모든 입출력 처리를 담당하는 거대 모듈 |
| **우연적 응집도 (Coincidental)** | 가장 약함 (최악) | 아무런 관련성 없는 함수나 코드들이 임의로 한 파일에 모여 있음 | 공통 유틸리티 잡동사니 파일(`Util.java`) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 모듈성을 극대화하기 위해 클래스나 서비스를 지나치게 잘게 쪼개어 파일 수 급증 및 전체 시스템 파악 곤란 | 도메인 주도 설계(DDD)의 Bounded Context와 단일 책임 원칙(SRP)을 기준으로 응집력 있는 패키지 구성 |
| 성능 최적화를 위해 전역 메모리나 공유 DB를 사용하여 공통/내용 결합도로 회귀하는 문제 | 캐싱 계층(Redis)을 도입하고 이벤트 기반 아키텍처(EDA)를 통한 비동기 메시지 교환으로 느슨한 결합 유지 |
| 복잡한 시스템에서 특정 모듈의 Fan-out(호출 수)이 과도하게 증가하여 의존성 오염 발생 | 파사드(Facade) 또는 중재자(Mediator) 디자인 패턴을 적용하여 하위 의존성을 단일 지점으로 집약 |

## Ⅵ. 제언

정적 코드 분석 도구(SonarQube)를 CI 파이프라인에 통합하여 결합도 및 순환 참조(Cyclic Dependency)를 상시 모니터링하고, High Fan-in 공통 모듈에 대한 100% 테스트 커버리지 거버넌스 확립 권장.

```text
[모듈 품질 엔지니어링 파이프라인]
  소스 코드 커밋 → 정적 분석(SonarQube: LCOM/CBO 측정) → 순환 의존성(JDepend) 검출 → Quality Gate 통과
```

| 관리 영역 | 전통적 모듈 관리 | 현대적 모듈성 거버넌스 |
|---|---|---|
| 설계 평가 | 개발자의 주관적 코드 리뷰 | 도구 기반 정량적 메트릭(Fan-in/Fan-out, CBO) 측정 |
| 의존성 통제 | 컴파일 타임 단순 결합 | 의존성 역전 원칙(DIP) 및 마이크로서비스 API 경계 격리 |
