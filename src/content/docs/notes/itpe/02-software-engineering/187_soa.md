## 연관 키워드

- SOA(Service-Oriented Architecture), ESB(Enterprise Service Bus), WSDL(Web Services Description Language), SOAP(Simple Object Access Protocol)
- UDDI(Universal Description, Discovery and Integration), 오케스트레이션(BPEL, Business Process Execution Language), 느슨한 결합(Loose Coupling), MSA(Microservice Architecture), DDD(Domain-Driven Design)

## Ⅰ. SOA의 개요

- 핵심 요약 : 비즈니스 기능을 재사용 가능한 서비스 단위로 구축하고 표준 인터페이스와 ESB로 통합하는 아키텍처 스타일.
- 개념 : 대규모 엔터프라이즈 환경에서 비즈니스 기능을 독립적이고 재사용 가능한 서비스(Service) 단위로 구축하고, 표준화된 인터페이스(WSDL(Web Services Description Language), SOAP(Simple Object Access Protocol) 등)와 엔터프라이즈 서비스 버스 ESB(Enterprise Service Bus)를 매개체로 유연하게 통합(연계)하는 아키텍처 스타일.
- 배경 및 필요성 : 기업 내 부서별로 분절된 이기종 레거시 시스템의 중복 투자 방지, 비즈니스 프로세스 변화에 맞춘 기존 서비스의 오케스트레이션(BPEL, Business Process Execution Language)을 통한 신속한 프로세스 재구성 필요.
- 핵심 구성요소 : 서비스 제공자(Provider), 서비스 요청자(Consumer), 서비스 레지스트리(Registry/UDDI, Universal Description, Discovery and Integration), 엔터프라이즈 서비스 버스(ESB).

## Ⅱ. SOA의 특징

- 핵심 요약 : 표준 계약과 느슨한 결합을 기반으로 재사용·자율·검색 가능한 서비스 단위 구조.

1. 표준화된 서비스 계약(Service Contract).
2. 느슨한 결합(Loose Coupling).
3. 서비스 추상화(Service Abstraction).
4. 재사용성(Reusability).
5. 자율성(Autonomy).
6. 무상태성(Statelessness).
7. 검색 가능성(Discoverability).

- ESB(Enterprise Service Bus) : 다양한 이기종 프로토콜과 데이터 포맷의 버스 상 상호 변환과 지능형 라우팅을 제공하는 통합 미들웨어 백본.

## Ⅲ. SOA의 구조 (흐름)

- 핵심 요약 : 요청자의 표준 메시지가 ESB의 변환·라우팅을 거쳐 개별 서비스로 전달되는 연계 구조.
- ESB 기반 연계 구조.

```text
[ 서비스 요청자 (Client / Portal) ]
    │
    ▼ (표준 메시지: SOAP / XML / HTTP)
[ 엔터프라이즈 서비스 버스 (ESB) ]
 - 프로토콜 변환 (HTTP <-> JMS <-> TCP 소켓)
 - 메시지 라우팅 및 데이터 변환
   (XML <-> JSON)
 - 트랜잭션 관리 및 보안 정책
   (WS-Security) 적용
    │
    ├─▶ [ 계정 서비스 (EJB) ]
    │
    └─▶ [ 여신 서비스 (C) ]
```

- 연계 절차 : 요청자의 표준 메시지 발행, ESB의 프로토콜 변환·라우팅·보안 정책 적용, 개별 서비스의 처리 및 응답.

## Ⅳ. 마이크로서비스 아키텍처(MSA)와의 비교

- 핵심 요약 : 전사 재사용·중앙 ESB의 SOA와 독립 배포·경량 파이프의 MSA의 철학 차이.
- 미들웨어 지능 배치의 대조.

```text
[ SOA ]  엔드포인트(단순) ──▶ [ ESB : 스마트 파이프 ] ──▶ 엔드포인트(단순)
[ MSA ]  엔드포인트(스마트) ──▶ [ 경량 파이프(Dumb Pipes) ] ──▶ 엔드포인트(스마트)
```

| 비교 항목 | 서비스 지향 아키텍처(SOA) | 마이크로서비스 아키텍처(MSA, Microservice Architecture) |
|---|---|---|
| 설계 철학 | 전사적 재사용 및 비즈니스 프로세스 통합 | 서비스의 독립적 배포 및 빠른 시장 출시 |
| 통신 미들웨어 | 무거운 중앙 집중형 ESB(Smart Pipes, Dumb Endpoints) | 가벼운 메시지 큐 또는 REST(Dumb Pipes, Smart Endpoints) |
| 데이터베이스 | 전사적 공유 단일 통합 DB(Database) 지향 | 서비스별 독립 DB(Database per Service) 지향 |
| 서비스 크기 | 상대적으로 큰 엔터프라이즈 서비스 단위(Coarse-Grained) | 도메인 바운디드 컨텍스트 중심의 작은 단위(Fine-Grained) |
| 거버넌스 형태 | 중앙 집중식 표준화 거버넌스 | 팀별 자율적 분산 거버넌스(폴리글랏) |

## Ⅴ. SOA의 장점과 한계

- 핵심 요약 : 레거시 통합·프로세스 유연성의 장점, ESB 병목·프로토콜 오버헤드·과잉 거버넌스의 한계.
- 장점
  1. 이기종 레거시 시스템의 통합과 중복 투자 방지.
  2. 표준 인터페이스 기반의 상호운용성 확보.
  3. 오케스트레이션을 통한 비즈니스 프로세스 신속 재구성.
  4. 서비스 재사용을 통한 개발 효율 향상.
- 한계점 1 : 중앙집중형 ESB의 비대화 및 성능 병목
  - 한계점 : ESB 내부의 데이터 변환, 라우팅, 오케스트레이션 로직 집중으로 인한 단일 장애점(SPOF, Single Point of Failure)화 및 확장성 병목 전락.
  - 해결 방안 : 무거운 ESB 로직의 서비스 내부 이관(Smart Endpoints, Dumb Pipes 원칙), 경량 메시지 브로커(Kafka, RabbitMQ) 기반 비동기 통신 전환.
- 한계점 2 : 무거운 SOAP/XML(Extensible Markup Language) 프로토콜의 통신 오버헤드
  - 한계점 : WSDL, WS-Security 등 엄격한 엔터프라이즈 표준 규약 준수로 인한 메시지 페이로드 비대화 및 파싱 CPU(Central Processing Unit) 부하 급증.
  - 해결 방안 : 경량 RESTful JSON(JavaScript Object Notation) 또는 gRPC/Protobuf 기반 초고속 직렬화 프로토콜로의 점진적 API(Application Programming Interface) 인터페이스 마이그레이션.
- 한계점 3 : 서비스 재사용 강박에 따른 과도한 거버넌스 및 결합도 증가
  - 한계점 : 전사 범용 재사용 서비스 구축 과정에서의 서비스 간 결합도 과잉 상승, 사소한 변경의 전사 서비스 전파로 인한 마비 상태 초래.
  - 해결 방안 : 도메인 주도 설계 DDD(Domain-Driven Design)의 바운디드 컨텍스트 개념 도입, 독립적 배포와 진화가 가능한 마이크로서비스 아키텍처(MSA)로의 단계적 진화.

## Ⅵ. 엔터프라이즈 시스템 진화를 위한 기술사적 제언

- 핵심 요약 : 중앙 ESB 병목의 경량 API Gateway 전환과 SOA 자산의 DDD 기반 재구조화.
- 중앙 ESB 병목 해소 및 경량 API Gateway로의 전환 : 전사 ESB의 과도한 비즈니스 변환 로직 집중 시 단일 장애점(SPOF)이자 개발 병목으로 변질, ESB 지능의 걷어내기와 경량 API Gateway·이벤트 브로커(Kafka)로의 분산 이전 필요.
- 기존 SOA 자산의 DDD 기반 마이크로서비스 재구조화 : 기 구축 SOA 서비스의 잘 정의된 비즈니스 기능 활용, 전면 폐기 대신 도메인 주도 설계(DDD) 기반 서비스 경계 재조정과 클라우드 네이티브 MSA로의 점진적 현대화 추진 권장.

## Ⅶ. 결론

- 핵심 요약 : 표준화·재사용의 가치와 중앙집중 한계의 인식, 경량화·분산화 진화 필요.
- 요약 : 표준 인터페이스와 ESB 기반으로 엔터프라이즈 서비스를 통합하는 아키텍처 스타일.
- 시사점 : ESB 지능의 분산 이전과 DDD 기반 서비스 경계 재조정을 통한 점진적 MSA 진화 권장.
