## 30초 인출

- 본질: 대규모 기업 비즈니스 기능을 독립적인 소프트웨어 서비스 단위로 모듈화하고 표준화된 서비스 계약(WSDL/XML)을 통해 네트워크 상에서 느슨하게 결합(Loose Coupling)하여 재사용하는 엔터프라이즈 아키텍처
- 메커니즘: 서비스 제공자(Provider)의 서비스 구현 및 등록소(UDDI/Registry) 등록(Publish) → 서비스 요청자(Consumer)의 검색(Find) 및 동적 바인딩(Bind) → ESB(Enterprise Service Bus) 기반 라우팅 및 프로토콜 변환 실행
- 통찰: 무거운 SOAP 프로토콜과 중앙집중형 ESB의 단일 장애점(SPOF) 병목을 해소하기 위해 경량 RESTful API 및 독립 배포/자율성을 강조하는 마이크로서비스 아키텍처(MSA)로의 진화적 전환 필요

<details>
<summary>핵심 용어</summary>

- **SOA (Service-Oriented Architecture)** : 비즈니스 기능을 독립적이고 자율적인 서비스로 모델링하여 표준 인터페이스 기반으로 조합·재사용하는 분산 아키텍처
- **서비스 계약 (Service Contract)** : 서비스가 제공하는 기능, 입출력 메시지 형식, 프로토콜, 오류 명세를 정의한 기계 판독 가능한 규격 (예: WSDL)
- **ESB (Enterprise Service Bus)** : 이기종 시스템 및 서비스 간의 메시지 라우팅, 데이터 변환, 보안, 트랜잭션 중재를 담당하는 중앙 미들웨어 백본
- **SOAP (Simple Object Access Protocol)** : XML 기반으로 HTTP, SMTP 등을 통해 구조화된 메시지를 교환하기 위한 W3C 표준 통신 프로토콜
- **WSDL (Web Services Description Language)** : 웹 서비스의 위치(포트), 제공 메서드, 입출력 매개변수 구조를 XML로 기술한 인터페이스 명세 언어
- **UDDI (Universal Description, Discovery, and Integration)** : 웹 서비스의 등록, 검색 및 동적 바인딩을 지원하는 범용 디렉터리 서비스 표준 규격
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 업무적 의미를 갖는 비즈니스 기능들을 상호 독립적인 표준 서비스(Service) 단위로 분할하고, 표준 인터페이스 계약에 의해 플랫폼 독립적으로 연계·조합(Orchestration)하는 아키텍처 패러다임 |
| 목적 | 전사적 IT 자산의 재사용성(Reusability) 극대화, 비즈니스 환경 변화에 대한 기민한 대응(Agility), 이기종 레거시 시스템 간의 원활한 상호운용성 확보 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 표준화된 서비스 계약 | WSDL/XSD 등을 통해 서비스 내부 구현 로직을 은닉하고 외부 인터페이스 규격만 엄격히 정의 |
| 느슨한 결합도 (Loose Coupling) | 호출자(Consumer)는 제공자(Provider)의 내부 플랫폼(Java, .NET, 메인프레임)에 종속되지 않고 통신 |
| 서비스 자율성 및 무상태성 | 서비스는 독립적으로 관리되며, 상태 정보를 유지하지 않는 무상태(Stateless) 설계를 지향하여 확장성 보장 |
| 서비스 조합 (Composability) | 원자적 서비스(Atomic Service)들을 비즈니스 프로세스(BPEL) 엔진을 통해 복합 서비스로 자유롭게 조립 가능 |

기업의 사일로화된 시스템을 전사적 관점의 비즈니스 서비스 풀(Pool)로 재구성한 엔터프라이즈 통합 표준.

## Ⅲ. 체계·프로세스

```text
[SOA 3각 상호작용 및 ESB 연계 아키텍처]

               [서비스 등록소 (Service Registry / UDDI)]
                 ▲                                  │
                 │ 1) 등록 (Publish: WSDL 배포)      │ 2) 검색 (Find)
                 │                                  ▼
      [서비스 제공자 (Provider)]             [서비스 요청자 (Consumer)]
                 │                                  │
                 ▼                                  ▼
  ┌────────────────────────────────────────────────────────┐
  │         엔터프라이즈 서비스 버스 (ESB: Service Bus)     │
  │  - 메시지 라우팅 (Content-Based Routing)               │
  │  - 프로토콜 및 데이터 변환 (Transformation: XML/JSON)   │
  │  - 서비스 오케스트레이션 (WS-BPEL 프로세스 조립)        │
  │  - 보안 및 QoS 정책 적용 (WS-Security, WS-Reliability) │
  └────────────────────────────────────────────────────────┘
                 ▲                                  │
                 └─────────── 3) 실행 (Bind) ───────┘
```

서비스 발행, 검색, 바인딩의 3대 주체와 중앙 ESB를 통한 라우팅, 변환, 정책 통제가 결합된 통합 프로세스.

## Ⅳ. 종류·비교

| 비교 항목 | SOA (Service-Oriented Architecture) | MSA (Microservices Architecture) |
|---|---|---|
| **설계 범위** | 전사 엔터프라이즈 차원의 비즈니스 통합 | 단일 도메인/애플리케이션 차원의 기능 분할 |
| **핵심 철학** | 서비스 재사용성(Reuse) 및 전사 거버넌스 극대화 | 서비스 자율성(Autonomy) 및 빠른 독립 배포(Time-to-Market) |
| **통합 미들웨어** | 스마트 파이프: 중앙 집중형 **ESB** 필수 채택 | 덤 파이프: 경량 메시지 브로커(Kafka, RabbitMQ) 또는 REST |
| **데이터베이스 아키텍처** | 대다수 전사 통합 RDBMS 공유 모델 (Shared DB) | 폴리글랏 영속성: 서비스별 독립 DB (Database per Service) |
| **프로토콜 및 통신** | 무거운 SOAP, XML, WSDL, WS-* 표준 스택 | 경량 HTTP/REST, JSON, gRPC, Protobuf |
| **거버넌스 체계** | 중앙 집중식 엄격한 표준화 및 위원회 통제 | 분산 자율 거버넌스 (팀별 기술 스택 자율 선택) |

### SOA 핵심 표준 기술 스택 비교

| 기술 표준 | 프로토콜 계층 | 역할 및 정의 |
|---|---|---|
| **SOAP** | 메시징 프로토콜 | XML 포맷 기반의 분산 환경 메시지 인벨로프(Envelope) 교환 규격 |
| **WSDL** | 인터페이스 기술 | 서비스의 엔드포인트 URL, 오퍼레이션, 파라미터를 기술하는 XML 문서 |
| **UDDI** | 디렉터리 서비스 | 전사 서비스 카탈로그를 등록하고 조회하는 글로벌 레지스트리 규약 |
| **WS-BPEL** | 비즈니스 프로세스 | 여러 웹 서비스를 순차/병렬로 엮어 엔드투엔드 워크플로우를 구성하는 언어 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 중앙 집중형 ESB에 모든 트래픽과 변환 로직이 집중되어 단일 실패점(SPOF) 및 성능 병목 발생 | ESB 내 비즈니스 로직을 배제하고 경량 API Gateway 및 분산 서비스 메시(Service Mesh) 구조로 전환 |
| SOAP/XML 기반의 방대한 패킷 헤더와 암복호화(WS-Security) 처리로 인한 극심한 CPU/네트워크 오버헤드 | 서비스 간 통신 규격을 경량 JSON/RESTful 또는 고성능 바이너리 gRPC 프로토콜로 현대화 |
| 전사적 서비스 재사용성을 지나치게 강조하여 서비스 간 결합도가 증가하고 배포 유연성 저하 | 도메인 주도 설계(DDD)의 바운디드 컨텍스트(Bounded Context) 원칙을 적용하여 서비스 경계 재획정 |

## Ⅵ. 제언

기존 레거시 통합 환경의 SOA 자산과 ESB 인프라를 전면 폐기하기보다는, 코어 뱅킹 등 후방 레거시는 유지한 채 대고객 전방 채널을 MSA 및 이벤트 기반 아키텍처(EDA)로 점진적 이원화하는 투트랙(Two-Track) 현대화 전략 추진 필요.

```text
[엔터프라이즈 하이브리드 아키텍처]
  채널 영역 (Cloud Native MSA) ──► EIP/ESB 연계 계층 ──► 코어 영역 (전통 SOA)
```

| 검증 단계 | SOA 기반 엔터프라이즈 계층 | 클라우드 네이티브 MSA 계층 |
|---|---|---|
| 핵심 역할 | 전사 데이터 무결성 및 핵심 기간계 트랜잭션 보장 | 빠른 고객 인터페이스 제공 및 빈번한 지속적 배포 |
| 통제 방식 | 중앙 통제형 거버넌스 및 엄격한 계약 버전 관리 | CI/CD 파이프라인 및 데브옵스 기반 팀별 자율 배포 |
