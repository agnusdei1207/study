## 큰 그림과 30초 인출

- 본질: 대규모 엔터프라이즈의 업무 기능을 독립적이고 재사용 가능한 표준 '서비스' 단위로 분할하고, 플랫폼에 독립적인 표준 인터페이스(WSDL)와 엔터프라이즈 서비스 버스(ESB)를 통해 느슨하게 결합(Loose Coupling)하여 비즈니스 민첩성을 극대화하는 아키텍처 스타일
- 메커니즘: 서비스 제공자가 기능 구현 후 WSDL 명세 $\rightarrow$ UDDI 등록소에 게시(Publish) $\rightarrow$ 서비스 요청자가 등록소에서 검색(Find) $\rightarrow$ SOAP/HTTP 프로토콜로 직접 바인딩(Bind) 및 호출 $\rightarrow$ ESB 메시지 중재
- 산출물: 서비스 명세서(WSDL) · 서비스 비즈니스 프로세스(BPEL) 모델 · ESB 연계 정의서 · 전사 서비스 포트폴리오 맵

<details>
<summary>핵심 용어</summary>

- **WSDL(Web Services Description Language)**: 서비스가 제공하는 메서드, 입력 파라미터, 반환값, 전송 프로토콜 규격을 XML 형식으로 엄격히 기술한 서비스 명세서
- **SOAP(Simple Object Access Protocol)**: HTTP/HTTPS 및 SMTP 등을 전송 계층 삼아 XML 형식의 봉투(Envelope) 메시지를 교환하는 원격 프로토콜
- **UDDI(Universal Description, Discovery, and Integration)**: 네트워크상에 공개된 웹 서비스들의 메타데이터와 WSDL 주소를 등록하고 동적으로 검색할 수 있는 디렉터리 저장소
- **ESB(Enterprise Service Bus)**: 서비스 간의 상호작용에 필요한 프로토콜 변환, 내용 기반 라우팅, 메시지 변환, 트랜잭션 관리를 중앙에서 일괄 중개하는 백본 미들웨어
</details>

## 1. 개요 및 필요성

### 엔터프라이즈 시스템 사일로(Silo)와 서비스 재사용의 필요성

전통적 대기업 시스템은 부서마다 독자적인 모놀리식 소프트웨어와 데이터베이스를 구축하여 전사적으로 동일한 업무 로직(예: 고객 인증, 결제)이 중복 개발되고 시스템 간 연동이 극도로 난해했다.

SOA는 "코드 수준의 재사용"을 넘어 **"비즈니스 프로세스 수준의 서비스 재사용"**을 지향하여, 표준 인터페이스로 포장된 서비스를 레고 블록처럼 조합함으로써 급변하는 시장 요구에 전사 IT가 즉각 적응할 수 있도록 설계된 통합 아키텍처 패러다임이다.

### SOA vs MSA vs EAI 비교

| 구분 | SOA (Service Oriented) | MSA (Microservices Architecture) | EAI (Enterprise App Integration) |
|---|---|---|---|
| **서비스 단위** | 비즈니스 도메인 단위 (중·대형 크기) | **단일 책임 원칙에 입각한 극소 단위 (Fine-grained)** | 거대 패키지 애플리케이션 단위 (ERP, CRM) |
| **통합 백본** | **중앙 집중형 무거운 ESB (Smart Pipes)** | **경량 분산 이벤트 버스 (Dumb Pipes & Smart Endpoints)** | 허브 앤 스포크 (Hub-and-Spoke) 전용 어댑터 |
| **통신 프로토콜** | SOAP, XML, WS-*, WSDL | **RESTful API, gRPC, JSON** | 벤더 독점 프로토콜, 바이너리 RPC |
| **데이터베이스** | **전사 중앙 데이터베이스 공유 지향** | **서비스별 독립 데이터베이스 (Polyglot Persistence)** | 각 레거시 시스템 DB 직접 연동 |
| **거버넌스** | 중앙 전사 아키텍처 거버넌스 조직 통제 | 각 서비스 팀 단위의 자율적 분산 거버넌스 | 시스템별 중앙 관리자 통제 |

## 3. 실무 적용 및 고려사항

### 위험 대응 매트릭스

| 위험 | 대책 | 효과 |
|---|---|---|
| 전사 모든 트래픽과 변환 로직이 중앙 ESB로 집중되어 단일 장애점(SPOF) 및 시스템 마비 초래 | 분산 API Gateway 및 Kafka/RabbitMQ 경량 이벤트 브로커 기반 탈중앙 분산 아키텍처 전환 | 단일 장애점 원천 제거 및 처리 성능 5배 향상 |
| 무겁고 장황한 XML/SOAP 봉투 파싱으로 인한 극심한 CPU 소모와 네트워크 응답 지연 | 경량 JSON 기반 RESTful API 및 Protobuf/gRPC 고성능 바이너리 프로토콜로 마이그레이션 | 페이로드 크기 70% 감소 및 지연시간 대폭 단축 |
| 엄격한 WSDL 인터페이스 변경 시 연계된 수십 개 클라이언트의 스텁 코드 컴파일 에러 속출 | 시맨틱 버저닝(SemVer) 및 하위 호환성을 보장하는 OpenAPI 규격(Swagger) 적용 | 인터페이스 변경에 따른 연쇄 장애 100% 방지 |

## 4. 기술사 답안 차별화 포인트

### SOA의 이상과 실패 원인: "Smart Pipes"의 한계

SOA는 개념적으로 완벽했으나, 2000년대 기술적 한계로 좌초되었다. 중앙의 ESB에 너무 많은 비즈니스 로직, 데이터 변환, 라우팅 책임을 부여한 **"똑똑한 파이프(Smart Pipes)"** 구조는 결국 ESB 자체가 거대한 모놀리스가 되는 병목을 초래했다. 또한 WS-Security 등 복잡한 WS-* 표준군의 오버헤드가 발목을 잡았다. 이 실패의 교훈을 짚어주는 것이 고득점 포인트이다.

### 마틴 파울러의 "Dumb Pipes and Smart Endpoints"로의 패러다임 전환

현대 마이크로서비스 아키텍처(MSA)는 SOA의 핵심 사상(서비스 분할과 느슨한 결합)을 계승하되, 무거운 ESB를 걷어내고 **"멍청한 파이프(경량 메시지 큐)와 똑똑한 엔드포인트(각 서비스 자체 로직)"** 원칙을 채택하였다. SOA에서 MSA로 진화한 기술사적 계보를 명확히 대비하여 결론으로 정리한다.
