## 연관 키워드

- SOA(Service-Oriented Architecture), ESB(Enterprise Service Bus), WSDL(Web Services Description Language), SOAP(Simple Object Access Protocol)
- UDDI(Universal Description, Discovery and Integration), 오케스트레이션(BPEL, Business Process Execution Language), 느슨한 결합(Loose Coupling), MSA(Microservice Architecture), DDD(Domain-Driven Design)

## Ⅰ. SOA의 개요

- 핵심 요약 : 비즈니스 기능을 재사용 가능한 서비스 단위로 구축하고 표준 인터페이스와 ESB로 통합하는 아키텍처 스타일.
- 개념 : **서비스 지향 아키텍처** (SOA, Service-Oriented Architecture)는 비즈니스 기능을 독립적이고 재사용 가능한 서비스 단위로 구축하고, 표준 인터페이스와 중앙 연계 계층으로 통합하는 아키텍처 스타일.
- 배경 및 필요성 : 부서별로 분절된 이기종 레거시 시스템의 중복 투자를 줄이고, **오케스트레이션** (BPEL, Business Process Execution Language)으로 기존 서비스를 엮어 변화하는 업무 프로세스를 빠르게 재구성할 필요가 생김.
- 핵심 구성요소 : 서비스 제공자(Provider), 서비스 요청자(Consumer), 서비스 레지스트리(**UDDI** (Universal Description, Discovery and Integration)), **엔터프라이즈 서비스 버스** (ESB, Enterprise Service Bus).

## Ⅱ. SOA의 특징 및 장점

- 핵심 요약 : 표준 계약과 느슨한 결합을 기반으로 재사용·자율·검색이 가능한 서비스 단위 구조.

1. 표준화된 서비스 계약 : **WSDL** (Web Services Description Language)로 인터페이스를 공개하고 **SOAP** (Simple Object Access Protocol) 메시지로 호출 → 상대 구현을 몰라도 상호운용성 확보.
2. **느슨한 결합** (Loose Coupling) : 요청자와 제공자가 인터페이스만 공유 → 한쪽 변경이 다른 쪽에 미치는 파급 축소.
3. 서비스 추상화 : 내부 구현을 감추고 비즈니스 기능 단위로 노출 → 기술 변경 시에도 호출 측 수정 최소화.
4. 재사용성 : 한 번 만든 서비스를 여러 업무 프로세스에서 호출 → 개발 중복 감소와 투자 효율 향상.
5. 자율성 : 서비스가 자신의 로직과 자원을 스스로 관리 → 독립적 운영 주기 확보.
6. 무상태성 : 요청 간 상태를 서비스가 들고 있지 않음 → 확장과 부하 분산이 쉬워짐.
7. 검색 가능성 : 레지스트리에 기능 메타데이터를 등록 → 필요한 서비스를 찾아 재사용.

- 장점 요약 : 이기종 시스템 통합, 프로세스 유연성, 재사용을 통한 개발 효율이 핵심 효익.

## Ⅲ. SOA의 구조 (흐름)

- 핵심 요약 : 요청자의 표준 메시지가 ESB의 변환·라우팅을 거쳐 개별 서비스로 전달되는 연계 구조.

```text
[ 서비스 제공자 (Provider) ]
          ↓ 기능 등록
[ 서비스 레지스트리 (UDDI) ]
          ↑ 기능 검색
[ 서비스 요청자 (Consumer) ]
```

```text
[ 서비스 요청자 ]
          ↓ 표준 메시지 (SOAP 기반)
[ ESB : 프로토콜 변환·라우팅 ]
          ↓ 보안 정책 적용 후 전달
[ 개별 서비스 (계정, 여신 등) ]
```

1. 요청자가 표준 메시지를 발행한다.
2. ESB가 프로토콜 변환, 데이터 변환, 라우팅과 보안 정책을 적용한다.
3. 개별 서비스가 처리하고 응답을 같은 경로로 돌려준다.

## Ⅳ. 마이크로서비스 아키텍처(MSA)와의 비교

- 핵심 요약 : 전사 재사용과 중앙 ESB를 중시하는 SOA와, 독립 배포와 경량 연결을 중시하는 **마이크로서비스 아키텍처** (MSA, Microservice Architecture)의 설계 철학 차이.

```text
[ SOA ]
 단순 엔드포인트 → [ ESB ] → 단순 엔드포인트
 지능은 중앙 미들웨어에 집중

[ MSA ]
 지능형 엔드포인트 → [ 경량 파이프 ] → 지능형 엔드포인트
 지능은 서비스 내부에 분산
```

| 비교 항목 | 서비스 지향 아키텍처 (SOA) | 마이크로서비스 아키텍처 (MSA) |
| --- | --- | --- |
| 설계 철학 | 전사적 재사용과 비즈니스 프로세스 통합 | 서비스 독립 배포와 빠른 출시 |
| 통신 미들웨어 | 중앙 집중형 ESB (Smart Pipes) | 메시지 브로커 또는 REST(Representational State Transfer) (Dumb Pipes) |
| 데이터베이스 | 전사 공유 통합 DB 지향 | 서비스별 독립 DB 지향 |
| 서비스 크기 | 큰 엔터프라이즈 단위 (Coarse-Grained) | 도메인 중심의 작은 단위 (Fine-Grained) |
| 거버넌스 | 중앙 집중식 표준 거버넌스 | 팀 단위 분산 거버넌스 |

- 선택 기준 : 레거시 통합과 프로세스 표준화가 우선인지, 변경 속도와 독립 배포가 우선인지에 따라 두 방식을 고른다.

## Ⅴ. SOA의 한계와 방안

- 핵심 요약 : ESB 병목, 무거운 프로토콜, 과도한 거버넌스가 한계이며, 지능의 분산과 경계 재설계로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 중앙 ESB 병목 | 변환·라우팅·오케스트레이션 로직 집중 → 단일 장애점(SPOF, Single Point of Failure)과 확장성 제약 | 로직을 서비스 내부로 이관하고 경량 메시지 브로커 기반 비동기 통신으로 전환 | 중앙 경유 지연 시간, 장애 영향 범위 |
| 무거운 SOAP·XML(Extensible Markup Language) 오버헤드 | 엄격한 표준 준수로 메시지가 비대해지고 파싱 CPU(Central Processing Unit) 부하 증가 | RESTful JSON(JavaScript Object Notation) 또는 gRPC 기반 API로 점진 전환 | 페이로드 크기, 응답 시간 |
| 과도한 재사용 거버넌스 | 전사 범용 서비스로 결합도가 높아져 사소한 변경이 전사로 파급 | **도메인 주도 설계** (DDD, Domain-Driven Design)의 바운디드 컨텍스트 적용 후 MSA로 단계 진화 | 변경 영향 범위, 배포 빈도 |

## Ⅵ. 엔터프라이즈 시스템 진화를 위한 기술사적 제언

- 핵심 요약 : 중앙 ESB의 지능을 경량 게이트웨이로 옮기고, 기존 SOA 자산을 DDD 기준으로 재구조화하는 방향.

1. 중앙 ESB 병목 해소 : 정보전략 조직은 ESB에 쌓인 업무 변환 로직을 API(Application Programming Interface) 게이트웨이와 이벤트 브로커로 나누어 옮기는 계획을 세워야 한다.
2. 기존 자산의 재구조화 : 전면 폐기 대신, 정보시스템 부서가 잘 정의된 SOA 서비스를 DDD 기반으로 경계 재조정하고 클라우드 환경의 MSA로 점진 이전하는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : 표준화와 재사용의 가치를 살리되 중앙 집중의 한계를 인식하는 경량화·분산화 진화가 필요함.
- 시사점 : SOA는 레거시 통합의 출발점으로 가치가 있으며, 지능의 분산 이전과 경계 재설계를 거쳐 MSA로 이어지는 진화 경로로 이해해야 함.
