## Ⅰ. SOA(서비스 지향 아키텍처)의 개요

- 개념 : **서비스 지향 아키텍처** (SOA, Service-Oriented Architecture) 란 대규모 엔터프라이즈 환경에서 비즈니스 기능을 독립적이고 재사용 가능한 '서비스(Service)' 단위로 구축하고, 표준화된 인터페이스(WSDL, Web Services Description Language; SOAP, Simple Object Access Protocol 등)와 엔터프라이즈 서비스 버스(ESB, Enterprise Service Bus)를 매개체로 이들을 유연하게 통합(연계)하는 아키텍처 스타일.
- 배경 및 필요성 : 기업 내 부서별로 분절된 이기종 레거시 시스템들의 중복 투자를 방지하고, 새로운 비즈니스 프로세스 변화에 맞추어 기존 서비스들을 **오케스트레이션** (BPEL, Business Process Execution Language)하여 신속하게 비즈니스 프로세스를 재구성하기 위해 고안.
- 핵심 구성요소 : **서비스 제공자** (Provider), **서비스 요청자** (Consumer), **서비스 레지스트리** (Registry/UDDI, Universal Description, Discovery and Integration), 엔터프라이즈 서비스 버스(ESB).

## Ⅱ. SOA 아키텍처 및 ESB 기반 연계 구조

```text
   [ 서비스 요청자 (Client / Portal) ]
                   │
                   ▼ (표준 메시지: SOAP / XML / HTTP)
   ┌────────────────────────────────────────────────────────┐
   │ [ 엔터프라이즈 서비스 버스 (ESB) ]                     │
   │  - 프로토콜 변환 (HTTP <-> JMS <-> TCP 소켓)           │
   │  - 메시지 라우팅 및 데이터 변환 (XML <-> JSON)         │
   │  - 트랜잭션 관리 및 보안 정책 (WS-Security) 적용       │
   └──────────┬───────────────────────────────┬─────────────┘
              │                               │
              ▼                               ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │ [ 계정 서비스 (EJB) ]│        │ [ 여신 서비스 (C) ]  │
   └──────────────────────┘        └──────────────────────┘
```

- 서비스의 기본 원칙 : 표준화된 서비스 계약, **느슨한 결합** (Loose Coupling), 서비스 추상화, 재사용성, 자율성, 무상태성, 검색 가능성.
- **ESB** (Enterprise Service Bus) : 다양한 이기종 프로토콜과 데이터 포맷을 버스 상에서 상호 변환하고 지능형 라우팅을 제공하는 통합 미들웨어 백본.

## Ⅲ. SOA와 마이크로서비스 아키텍처(MSA)의 비교

| 비교 항목 | 서비스 지향 아키텍처 (SOA) | 마이크로서비스 아키텍처 (MSA, Microservice Architecture) |
|---|---|---|
| 설계 철학 | '전사적 재사용' 및 비즈니스 프로세스 통합 | 서비스의 '독립적 배포' 및 빠른 시장 출시 |
| 통신 미들웨어 | 무거운 중앙 집중형 ESB (Smart Pipes, Dumb Endpoints) | 가벼운 메시지 큐 또는 REST (Dumb Pipes, Smart Endpoints) |
| 데이터베이스 | 전사적 공유 단일 통합 DB(Database) 지향 | 서비스별 독립 DB (Database per Service) 지향 |
| 서비스 크기 | 상대적으로 큰 엔터프라이즈 서비스 단위 (Coarse-Grained) | 도메인 바운디드 컨텍스트 중심의 작은 단위 (Fine-Grained) |
| 거버넌스 형태 | 중앙 집중식 표준화 거버넌스 | 팀별 자율적 분산 거버넌스 (폴리글랏) |

## Ⅳ. SOA(서비스 지향 아키텍처)의 주요 한계점 및 해결 방안

- 중앙집중형 ESB(Enterprise Service Bus)의 비대화 및 성능 병목 :
  - 한계점 : ESB 내부에 데이터 변환, 라우팅, 오케스트레이션 등 복잡한 비즈니스 로직이 집중되어 ESB 자체가 **단일 장애점** (SPOF, Single Point of Failure)이자 확장성 병목으로 전락.
  - 해결 방안 : 무거운 ESB 로직을 서비스 내부로 이관(Smart Endpoints, Dumb Pipes 원칙), 경량 메시지 브로커(Kafka, RabbitMQ) 기반 비동기 통신 전환.
- 무거운 SOAP/XML(Extensible Markup Language) 프로토콜로 인한 통신 오버헤드 :
  - 한계점 : WSDL, WS-Security 등 엄격한 엔터프라이즈 표준 규약 준수로 인해 메시지 페이로드가 비대해지고 파싱 CPU(Central Processing Unit) 부하 급증.
  - 해결 방안 : 경량 RESTful JSON(JavaScript Object Notation) 또는 gRPC/Protobuf 기반 초고속 직렬화 프로토콜로의 점진적 API(Application Programming Interface) 인터페이스 마이그레이션.
- 서비스 재사용 강박으로 인한 과도한 거버넌스 및 결합도 증가 :
  - 한계점 : 전사 범용 재사용 서비스를 구축하려다 서비스 간 결합도가 지나치게 높아져 사소한 변경에도 전사 서비스가 영향을 받는 마비 상태 초래.
  - 해결 방안 : 도메인 주도 설계(DDD, Domain-Driven Design)의 바운디드 컨텍스트 개념을 도입하여 독립적 배포와 진화가 가능한 마이크로서비스 아키텍처(MSA)로 단계적 진화.

## Ⅴ. 엔터프라이즈 시스템 진화를 위한 기술사적 제언

- 중앙 ESB 병목 해소 및 경량 API Gateway로의 전환 : 전사 ESB에 과도한 비즈니스 변환 로직이 집중되면 ESB 자체가 거대한 단일 장애점(SPOF)이자 개발 병목으로 변질되므로, ESB의 지능을 걷어내고 경량 API Gateway와 이벤트 브로커(Kafka)로 분산 이전해야 함.
- 기존 SOA 자산의 DDD 기반 마이크로서비스 재구조화 : 엔터프라이즈에 기 구축된 SOA 서비스들은 비즈니스 기능이 잘 정의되어 있으므로, 이를 무리하게 전면 폐기하지 말고 도메인 주도 설계(DDD)를 통해 서비스 경계를 재조정하여 클라우드 네이티브 MSA로 점진적 현대화 추진 권장.
