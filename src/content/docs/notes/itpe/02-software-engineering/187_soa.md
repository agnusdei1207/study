## 연관 키워드
- 서비스 지향 아키텍처, 서비스 계약, 느슨한 결합, ESB, 오케스트레이션

### Ⅰ. SOA의 개요

- 핵심 요약 : SOA는 업무 기능을 명시적 계약을 가진 상호 운용 서비스로 구성하는 아키텍처 접근.
- 개념 : 독립된 업무 서비스를 표준화 된 계약과 메시지 교환으로 연결 하는 설계 원칙(**SOA**, Service-Oriented Architecture).
- 배경 및 필요성 : 부서·플랫폼 별 로 분리 된 업무 시스템의 기능과 데이터를 재사용 하고 연계를 단순화 할 필요.
- 주요 목적 : 업무 기능의 재사용성과 상호 운용성을 높이고 변화 영향을 서비스 경계로 제한.

### Ⅱ. SOA의 핵심 원칙 및 장점

- 핵심 요약 : 표준 계약·자율성·느슨한 결합이 서비스 재사용과 이기종 연계를 지원.

1. 명시적 서비스 계약 : 입력·출력·오류·보안 규약 정의 → 소비자와 제공자의 결합 감소.
2. 자율성 : 서비스가 자신의 로직과 데이터 경계를 통제 → 독립적 변경 여지 확대.
3. 상호 운용성 : 플랫폼 중립적 메시지·프로토콜 사용 → 이기종 시스템 연계.
4. 발견·조합 : 서비스 목록과 오케스트레이션 → 업무 프로세스 재구성 가능.

### Ⅲ. SOA의 참조 구성과 요청 흐름 (구조)

- 핵심 요약 : 소비자는 계약에 따라 서비스를 호출 하고 통합 계층 또는 프로세스가 복합 업무를 조정.

```text
서비스 소비자
   ↓ 계약 기반 요청
통신·보안·중재 계층
   ↓ 라우팅·변환
서비스 제공자 → 업무 기능·데이터
```

```text
업무 요청
   ↓ 오케스트레이터
서비스 A → 서비스 B → 서비스 C
   ↓ 결과 조합
소비자 응답
```

- ESB는 일부 SOA 구현에서 라우팅·변환·프로토콜 중재를 제공하는 통합 인프라로 사용 되며 SOA의 필수 조건은 아님.

### Ⅳ. SOA와 마이크로서비스 아키텍처 비교

- 핵심 요약 : SOA와 MSA는 서비스 경계를 지향하지만 배포 단위·조직 운영·통합 방식에서 일반적 경향이 다름.

| 비교 축 | SOA | 마이크로서비스 아키텍처 |
|---|---|---|
| 서비스 범위 | 업무 기능·기업 서비스 단위 | 독립 배포 가능한 작은 업무 역량 |
| 통합 경향 | ESB·공유 표준 계약을 활용할 수 있음 | 경량 통신·분산 소유를 선호 |
| 데이터 소유 | 기업 공통 데이터 서비스 가능 | 서비스 별 데이터 소유를 강조 |
| 운영 초점 | 전사 상호 운용·재사용 | 독립 배포·팀 자율성과 관측성 |

### Ⅴ. SOA의 한계와 방안

- 핵심 요약 : 중앙 통합 계층의 과도한 의존과 서비스 계약의 불일치는 자율성·가용성 저하로 이어질 수 있음.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| ESB 병목·단일 장애 | 모든 연계가 중앙 집중 | 중복화·용량 관리·필요 시 직접 경량 연계 | ESB 가용성 |
| 서비스 경계 불명확 | 조직 기능을 그대로 분리 | 업무 도메인·변경 이유 기준으로 경계 설계 | 경계 변경 건수 |
| 계약 불일치 | 스키마·오류 의미의 비호환 | 버전 정책·계약 시험·소비자 영향 분석 | 계약 불일치 건수 |
| 분산 호출 장애 | 지연·타임아웃·부분 실패 | 타임아웃·멱등성·보상 흐름·추적 적용 | 분산 호출 실패율 |

### Ⅵ. 전사 아키텍처 제언

- 핵심 요약 : 기업 아키텍트는 서비스 계약과 데이터 책임을 표준화 하면서 과도한 중앙 통제를 피함.

1. 서비스 카탈로그에 소유자, 계약 버전, 보안 분류, 가용성 책임, 폐기 일정을 기록.
2. 프로세스 담당 자는 분산 트랜잭션을 기본 가정 하지 말고 보상·재시도·중복 처리 정책을 업무 흐름에 설계.

### Ⅶ. 결론

- 핵심 요약 : SOA는 업무 서비스를 계약으로 정의하고 조합 해 기업 시스템의 상호 운용성과 재사용을 높이는 접근.
- 시사점 : 서비스 경계와 운영 책임이 명확 할 때 통합 복잡성을 관리 가능한 수준으로 낮출 수 있음.
