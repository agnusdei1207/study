 ┃
 ┣━ Ⅰ 개요 ───── 대규모 엔터프라이즈의 업무 기능을 독립적인 '서비스' 단위로 분할하고 표준 인터페이스를 통해 느슨하게 결합하는 아키텍처
 ┣━ Ⅱ 특징 ───── 서비스 재사용성(Reusability) 극대화 · 플랫폼 독립적 표준 인터페이스 · ESB 기반의 서비스 오케스트레이션(Orchestration)

```text

|                                                                         |
| === 전사 연계 미들웨어: ESB (Enterprise Service Bus : 라우팅, 프로토콜 변환) ===|

```

## 핵심 용어
- WSDL(Web Services Description Language): 웹 서비스가 제공하는 기능, 파라미터, 데이터 형식, 통신 프로토콜을 기술한 XML 기반 서비스 명세서
- SOAP(Simple Object Access Protocol): HTTP, HTTPS, SMTP 등을 기반으로 XML 메시지를 네트워크상에서 안전하게 교환하기 위한 원격 프로토콜
- UDDI(Universal Description, Discovery and Integration): 네트워크상에서 사용 가능한 웹 서비스들의 정보를 등록하고 동적으로 검색할 수 있는 글로벌 디렉터리 서비스
- ESB(Enterprise Service Bus): 서비스 간의 연동에 필요한 메시지 변환, 내용 기반 라우팅, 보안, 트랜잭션을 중앙에서 일괄 중개하는 백본 미들웨어
- 오케스트레이션(Orchestration): 중앙의 프로세스 엔진(BPEL 등)이 각 서비스를 정해진 비즈니스 워크플로우에 따라 순차/병렬로 지휘하는 서비스 조합 방식

## 핵심 통찰
- SOA의 핵심 철학은 '코드의 재사용'을 넘어선 '비즈니스 서비스 단위의 재사용'을 통해 IT가 비즈니스 민첩성(Agility)을 뒷받침하는 데 있었음
- 그러나 구현 기술로 채택된 WS-* 표준군(WS-Security, WS-Reliability)과 SOAP/XML이 지나치게 복잡하고 무거워 성능 저하를 초래함
- 또한 전사 시스템의 모든 트래픽이 중앙 집중형 ESB로 몰리면서 ESB 자체가 거대한 병목 구간이자 단일 장애점(SPOF)으로 작용하여 많은 엔터프라이즈 프로젝트가 좌초됨
- 이러한 SOA의 서비스 분할 사상은 계승하고, 무거운 ESB를 걷어낸 채 경량 REST/JSON과 서비스별 독립 DB를 채택한 모델이 오늘날의 마이크로서비스 아키텍처(MSA)임

## 이웃 토픽과 구분
| 비교 항목 | SOA (Service Oriented) | MSA (Microservices) | EAI (Enterprise App Integration) |
| :--- | :--- | :--- | :--- |
| **서비스 크기** | 엔터프라이즈 규모의 큰 서비스 단위 | 단일 기능(도메인) 중심의 작은 서비스 | 애플리케이션 단위 (ERP, CRM 등) |
| **통합 미들웨어** | 중앙 집중형 무거운 ESB | 스마트 엔드포인트 & 덤 파이프 (경량 MQ) | 전용 어댑터 허브 앤 스포크 (Hub-and-Spoke) |
| **데이터 저장소** | 전사 공통 데이터베이스 공유 | 각 서비스별 독립적 데이터베이스(Polyglot) | 기존 레거시 데이터베이스 직접 연동 |
| **통신 프로토콜** | SOAP, XML, WS-*, WSDL | RESTful API, gRPC, JSON | 독점 바이너리 어댑터, RPC |
| **거버넌스** | 중앙 전사 거버넌스 조직 통제 | 자율적 팀 단위 분산 거버넌스 | 시스템별 중앙 관리자 통제 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **중앙 ESB 병목으로 전사 시스템 장애 전이** | 모든 서비스 호출과 변환 로직이 중앙 단일 ESB 미들웨어에 집중 | 분산 게이트웨이(API Gateway) 및 경량 메시지 브로커(Kafka, RabbitMQ)로 분산 전환 |
| **XML 직렬화/역직렬화 오버헤드로 지연 증가** | 장황한 XML 태그와 무거운 SOAP 봉투(Envelope) 구조로 인한 CPU 소모 | 페이로드를 경량 JSON 또는 바이너리 프로토콜(Protobuf, gRPC)로 전면 마이그레이션 |
| **서비스 인터페이스 변경 시 연계 시스템 장애** | 엄격한 WSDL 계약 변경 시 클라이언트 측 스텁 코드의 컴파일 오류 유발 | 시맨틱 버저닝(Semantic Versioning) 및 하위 호환성을 보장하는 유연한 JSON 스키마 적용 |

## 이렇게 출제된다

- **25점형**:

  - 2) 서비스 조합 방식인 오케스트레이션(Orchestration)과 코레오그래피(Choreography)의 개념과 차이점을 비교하시오.
  - 3) 과거 SOA가 겪었던 실패 요인을 아키텍처 및 거버넌스 관점에서 분석하고, 이를 극복한 마이크로서비스 아키텍처(MSA)로의 진화 과정을 논하시오.

## 내 의견
- SOA는 개념적으로 흠잡을 데 없는 완벽한 아키텍처였으나, 2000년대 당시 하드웨어 성능과 너무 무겁고 복잡했던 WS-* 기술 스펙이 시대적 제약으로 작용했음
- 현대 엔지니어링에서 SOA의 '서비스 계약'과 '느슨한 결합' 철학은 MSA, OpenAPI, 이벤트 기반 아키텍처(EDA)의 형태로 완전히 녹아들어 있음
- 실무적으로 기존 SOA 환경을 MSA로 전환할 때는, 한 번에 시스템을 재구축하는 빅뱅 방식 대신 스트랭글러 피그(Strangler Fig) 패턴을 적용하여 ESB에 물려있는 서비스를 경량 API Gateway 뒤로 점진 이관하는 전략이 필수적임
