## 30초 인출

- 본질: SOA는 업무 기능을 표준 인터페이스를 가진 서비스로 만들어 서비스를 조합해 업무 프로세스를 구성하는 아키텍처
- 메커니즘: 서비스 제공자가 서비스를 등록하면 요청자가 검색해 표준 메시지(SOAP·WSDL)로 호출하며 ESB가 라우팅과 변환을 중계
- 통찰: 중앙의 ESB에 통합 로직이 몰리면 병목과 변경 부담이 되므로 ESB는 라우팅·변환 같은 중계에 두고 업무 로직은 서비스에 두어 서비스 계약으로 결합

<details>
<summary>핵심 용어</summary>

- **SOA(Service-Oriented Architecture)** : 서비스 단위로 업무 기능을 제공하고 조합하는 아키텍처
- **서비스 계약(Service Contract)** : 서비스의 기능·입출력 형식·조건을 정한 규약
- **ESB(Enterprise Service Bus)** : 서비스 사이의 라우팅·변환·중계를 맡는 통합 버스
- **SOAP·WSDL·UDDI** : 메시지 교환, 서비스 기술, 서비스 등록·검색의 웹 서비스 표준
- **서비스 조합(Composition)** : 여러 서비스를 엮어 업무 프로세스를 만드는 것

</details>

## 2~4교시 25점 답안

## Ⅰ. SOA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **SOA** 는 업무 기능을 표준 인터페이스의 서비스로 만들어 조합하는 아키텍처 |
| 목적 | 서비스 재사용과 업무 변화에 대한 유연한 대응 |

## Ⅱ. 특징

| 특징 | 의미 |
|---|---|
| 서비스 단위 | 업무 기능을 독립 서비스로 제공 |
| 표준 인터페이스 | 플랫폼 독립적인 호출 |
| 느슨한 결합 | 서비스 계약으로만 연결 |
| 조합 | 서비스를 엮어 프로세스 구성 |

## Ⅲ. 구성

```text
서비스 요청자 ─(검색)─▶ 서비스 레지스트리(UDDI)
      │                        ▲(등록)
      ▼(SOAP 호출)              │
   [ESB]  ─────────────▶ 서비스 제공자(WSDL로 기술)
```

## Ⅳ. SOA와 MSA의 비교

| 구분 | SOA | MSA |
|---|---|---|
| 서비스 크기 | 업무 단위로 큰 편 | 작은 단위 |
| 통합 | ESB 중심 | 경량 API·메시징 |
| 데이터 | 공유 가능 | 서비스별 소유 |
| 배포 | 상대적으로 통합 | 서비스별 독립 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| ESB에 통합 로직이 몰려 병목·변경 부담 | ESB는 중계에 한정하고 업무 로직은 서비스로 |
| 표준(SOAP·XML) 처리 비용 | 경량 API 병행 |
| 서비스 경계·계약의 불명확 | 서비스 계약을 먼저 정의 |

## Ⅵ. 제언

ESB는 라우팅·변환 같은 중계에 두고 업무 로직은 서비스에 두어 서비스 계약으로 결합

```text
서비스 ⇄ (계약) ⇄ ESB(중계만) ⇄ 서비스
```

| 구분 | ESB에 로직 집중 | 제언: 중계·서비스 분리 |
|---|---|---|
| 병목 | 위험 | 완화 |
| 변경 | ESB 수정 | 해당 서비스 수정 |
