```text
 ┣━ Ⅱ 특징 ───── 점근적 상한(Asymptotic Upper Bound) · 최고차항만 표기(상수·저차항 무시) · 최악의 경우(Worst-case) 성능 보장
 ┣━ Ⅲ 구조 ───── 복잡도 3대 점근 표기법: 빅오($O$, 상한) / 빅오메가($\Omega$, 하한) / 빅세타($\Theta$, 정확한 차수)

```

## 한 줄 본질
- 알고리즘 실행 시간을 초(sec) 단위로 측정하면 CPU나 메모리 사양에 따라 결과가 왜곡되는 병목 → 입력 데이터 크기 $n$이 무한히 커질 때 연산 횟수가 증가하는 수학적 상한 기울기를 표기하는 점근적 분석 기법 / 작은 $n$에서 상수 계수 무시로 인한 오차

## 핵심 용어
- 빅오 표기법($O$): $n \ge n_0$인 모든 $n$에 대해 $f(n) \le c \cdot g(n)$을 만족하는 양의 상수 $c$와 $n_0$가 존재할 때 $f(n) = O(g(n))$으로 정의되는 점근적 상한선
- 빅세타 표기법($\Theta$): 알고리즘의 상한($O$)과 하한($\Omega$)이 일치할 때 사용하는 표기법으로, 알고리즘의 정확한 증가 차수를 의미함

## 핵심 통찰
- 빅오 표기법은 상수 계수($c$)를 생략하므로, 이론상 $O(n)$ 알고리즘이더라도 내부 루프가 10,000번 돌면 작은 데이터셋에서는 $O(n^2)$ 알고리즘보다 실제 실행 시간이 훨씬 느릴 수 있음
- 공간 복잡도(Space Complexity)와 시간 복잡도는 대부분 트레이드오프 관계에 있으며, 대표적으로 메모이제이션(DP)이나 인덱스(B-Tree)는 공간을 더 써서 시간 복잡도를 $O(2^n)$에서 $O(n)$ 또는 $O(\log n)$으로 단축시킴
- 현대 CPU 아키텍처에서는 캐시 라인(L1/L2 Cache) 적중률이 성능에 결정적이므로, 복잡도가 동일한 $O(n)$이더라도 메모리 불연속 접근(Linked List)보다 연속 배열 순회가 수십 배 빠름

## 이웃 토픽과 구분
- 빅오($O$) vs 빅오메가($\Omega$) vs 빅세타($\Theta$): 빅오 = 아무리 나빠도 이보다는 빠르다(상한) / 빅오메가 = 아무리 좋아도 이보다는 느리다(하한) / 빅세타 = 이 상한과 하한 사이에서 정확히 일치한다(동등)

## 문제·원인·대책
- 적용 상황: 수십만 건의 회원 결제 내역과 주문 데이터를 매핑하는 배치 로직
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 데이터 건수가 10만 건으로 늘어나자 배치 작업이 3분에서 8시간으로 급증하여 타임아웃 | 중첩 for 루프로 결제 건마다 주문 리스트를 전수 검색하는 $O(n \times m) \approx O(n^2)$ 설계 | 주문 목록을 사전 해시맵(HashMap)으로 인덱싱하여 $O(1)$ 조회로 변경 ($O(n+m)$) | 배치 처리 시간 8시간에서 15초로 대폭 단축 |
| 검색어 추천 API 호출 시 응답 지연 발생으로 사용자 이탈 | 단순 배열 순차 탐색($O(n)$)으로 전체 단어 목록을 매번 스캔 | 트라이(Trie) 자료구조를 적용하여 문자열 길이에 비례하는 $O(L)$ 탐색으로 전환 | 데이터 규모 증가와 무관한 일관된 검색 성능 확보 |

## 내 의견
- [알고리즘 빅오 복잡도에만 매몰된 과도한 엔지니어링 경계] 데이터 건수가 수십 건에 불과한 소규모 설정값 조회를 위해 복잡한 B-Tree나 트라이 자료구조를 도입하여 코드 가독성만 해치는 현상 발생 → 나라면: 도메인의 실질적 데이터 규모($n$)와 증가율을 먼저 분석하고, $n \le 1,000$ 이하에서는 단순 배열과 표준 라이브러리를 활용하되 대규모 트랜잭션 구간에만 선택적으로 복잡도 최적화 자료구조를 적용
