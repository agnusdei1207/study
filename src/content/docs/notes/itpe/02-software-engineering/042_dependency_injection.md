## 연관 키워드

- 의존성 주입(DI, Dependency Injection), 제어의 역전(IoC, Inversion of Control), DI 컨테이너
- SOLID, DIP(Dependency Inversion Principle), 생성자 주입(Constructor Injection), 순환 참조(Circular Dependency), Mock 테스트

## Ⅰ. 의존성 주입(DI)의 개요

- 핵심 요약 : 의존 객체를 외부 컨테이너로부터 주입받아 결합도를 낮추는 객체지향 설계 기법.
- 개념 : 객체가 사용할 의존 객체(Dependency)를 내부에서 직접 생성하지 않고 외부 조립기(컨테이너)로부터 주입받게 하는 설계 기법 (**의존성 주입**, DI, Dependency Injection). 제어의 역전(IoC, Inversion of Control)을 구현하는 대표적 방식.
- 배경 및 필요성 : 클래스 내부에서 구현체를 직접 생성하면 특정 구현에 강하게 묶여 모듈 교체와 단위 테스트(Mock 테스트)가 어려워지므로 이를 해소할 구조가 필요함.
- 설계 원칙 연계 : SOLID 원칙 가운데 **DIP**(Dependency Inversion Principle, 의존성 역전 원칙)를 실천하는 기법. SOLID는 SRP(단일 책임), OCP(개방·폐쇄), LSP(리스코프 치환), ISP(인터페이스 분리), DIP로 구성됨.
- 주요 목적 : 객체 간 결합도를 낮추고 구현체 교체와 테스트를 쉽게 하는 것.

## Ⅱ. 의존성 주입의 특징 및 장점

- 핵심 요약 : IoC 구현이라는 구조적 특성이 결합도 최소화와 테스트 용이성이라는 효익으로 이어지는 설계 기법.

1. 제어의 역전 구현 : 객체가 의존 대상을 고르는 권한을 외부 컨테이너에 넘김 → 구현 교체 시 클라이언트 코드 수정이 불필요.
2. 인터페이스 기반 주입 : 클라이언트가 구현체가 아닌 인터페이스에만 의존 → 결합도 감소와 확장 용이성.
3. 테스트 대역 주입 : 인터페이스 자리에 Mock 객체를 넣을 수 있음 → 외부 시스템 없이 단위 테스트 가능.
4. 3가지 주입 방식 : 생성자, 수정자(Setter), 필드 주입을 지원 → 의존의 성격에 맞춰 방식을 선택.
5. 빈(Bean) 생명주기 관리 : 컨테이너가 객체의 생성과 소멸을 맡음 → 객체 관리 책임을 애플리케이션 코드에서 분리.

## Ⅲ. 의존성 주입의 구조 (흐름)

- 핵심 요약 : DI 컨테이너가 인터페이스 타입의 구현체를 만들어 클라이언트에 넘기는 구조.

```text
[ DI 컨테이너 ]
MariaDbRepository 빈 생성
      ↓ 인터페이스 타입으로 주입
[ 클라이언트 클래스 ]
Repository 인터페이스에만 의존
```

```text
[ 적용 전: 강한 결합 ]
클라이언트
      ↓ new 직접 생성
MariaDbRepository

[ 적용 후: 느슨한 결합 ]
클라이언트 → Repository (인터페이스)
MariaDbRepository → Repository 구현
```

- 생성자 주입(Constructor Injection) : 필수 의존성을 생성자 매개변수로 전달받는 방식. 불변성 확보와 누락 시 컴파일 오류 발생이 장점이며 가장 권장됨.
- 수정자 주입(Setter Injection) : 선택적 의존성을 Setter 메서드로 교체하는 방식. 런타임 교체가 가능하지만 객체가 불완전한 상태로 남을 위험이 있음.
- 필드 주입(Field Injection) : @Autowired 등으로 필드에 직접 주입하는 방식. 코드가 간결하나 순수 자바 단위 테스트가 어렵고 프레임워크 결합이 커 지양함.

## Ⅳ. 3가지 주입 방식의 비교

- 핵심 요약 : 불변성, 테스트 용이성, 순환 참조 감지 측면에서 생성자 주입이 우위.

| 주입 방식 | 불변성 (Immutability) | 테스트 용이성 | 순환 참조 감지 | 권장 여부 |
| --- | --- | --- | --- | --- |
| 생성자 주입 | final 필드로 보장 가능 | 프레임워크 없이 POJO(Plain Old Java Object)에 Mock 주입 가능 | 애플리케이션 구동 시점에 예외로 드러남 | 기본 권장 |
| 수정자 주입 | 재설정이 가능해 보장 불가 | Mock 주입은 가능하나 Setter 호출 필요 | 실제 호출 시점까지 드러나지 않을 수 있음 | 선택적 의존성에 한정 |
| 필드 주입 | 리플렉션에 의존해 보장 불가 | DI 프레임워크 없이는 Mock 주입 어려움 | 구동 시점 감지가 어려움 | 사용 지양 |

## Ⅴ. 의존성 주입의 한계와 방안

- 핵심 요약 : 기동 비용, 순환 의존, 추적 난이도의 한계를 컴파일 타임 주입, 생성자 주입 강제, 정적 규칙 검증으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 런타임 리플렉션과 기동 지연 | 빈이 많은 대규모 애플리케이션에서 런타임 스캔과 리플렉션으로 기동 시간과 메모리 사용이 증가 | 컴파일 타임 DI 도구(Dagger 2, Micronaut, Quarkus) 검토, Spring의 AOT(Ahead-of-Time) 컴파일 적용 | 기동 시간, 메모리 사용량 |
| 순환 의존성 (Circular Dependency) | A가 B를, B가 A를 참조하는 구조에서 컨테이너 초기화가 실패하고 결합이 강해짐 | 필드 주입을 금지하고 생성자 주입을 강제해 구동 시점에 탐지, 이벤트 발행·구독 모델로 의존 분리 | 순환 참조 탐지 건수 |
| 객체 생명주기 추적 난이도 | 생성과 소멸이 컨테이너에 숨겨져 실제 주입 구현체를 소스만으로 파악하기 어려움 | @Profile, @Conditional 남용 제한, ArchUnit으로 계층 의존 규칙을 CI에서 자동 검증 | 의존 규칙 위반 건수 |

## Ⅵ. 대규모 애플리케이션 아키텍처에 대한 기술사적 제언

- 핵심 요약 : 생성자 주입을 코딩 표준으로 정하고, 도메인 계층을 프레임워크로부터 독립시키는 두 가지 원칙.
- 생성자 주입을 기본 표준으로 정하고 Lombok의 @RequiredArgsConstructor와 final 필드를 함께 쓰면, 보일러플레이트를 줄이면서도 의존 객체를 빠뜨리는 실수를 컴파일 단계에서 막을 수 있다. 이 규칙을 개발 표준 문서와 코드 리뷰 체크리스트에 명시하는 것이 실효성이 높다.
- 핵심 도메인 엔티티와 유스케이스는 클린 아키텍처나 헥사고날 아키텍처의 경계에 따라 특정 DI 컨테이너의 어노테이션 없이 순수 자바 또는 코틀린으로 유지하는 편이 좋다. 그래야 컨테이너를 교체하거나 기동 최적화 도구를 바꿀 때 도메인 로직을 건드리지 않는다.

## Ⅶ. 결론

- 핵심 요약 : DI는 결합도를 낮추고 테스트를 쉽게 하는 IoC의 핵심 실천 기법.
- 시사점 : 생성자 주입 표준화와 도메인 계층의 프레임워크 독립성을 함께 지켜야 장기적으로 변경에 강한 구조가 됨.
