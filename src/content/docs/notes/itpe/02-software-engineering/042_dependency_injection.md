## Ⅰ. 의존성 주입(DI)의 개요

- **개념** : 객체가 자신이 사용할 의존 객체(Dependency)를 내부에서 직접 생성(new)하지 않고, 외부의 조립기(컨테이너)로부터 주입(Injection)받도록 하여 객체 간의 결합도를 낮추는 객체지향 설계 패턴이자 제어의 역전(IoC, Inversion of Control)의 대표적 구현체.
- **배경 및 필요성** : 클래스 내부에서 구현체를 직접 생성하면 구현 클래스에 강하게 결합되어 모듈의 교체, 확장, 단위 테스트(Mocking)가 불가능해지는 문제를 해결.
- **설계 원칙 연계** : 객체지향 5대 원칙(SOLID) 중 의존성 역전 원칙(DIP, Dependency Inversion Principle)의 실천적 기법.

## Ⅱ. 의존성 주입의 메커니즘 및 3가지 주입 방식

```text
   [ 클라이언트 클래스 ] ──(의존)──> [ <<interface>> Repository ]
           ▲                                  ▲
           │                                  │ (구현)
           │ (인터페이스를 통한 주입)          │
   ┌───────┴──────────────────────────────────┴──────┐
   │         [ DI 컨테이너 (Spring IoC / Guice) ]      │
   │  - 객체의 생명주기 관리 및 빈(Bean) 생성         │
   │  - new MariaDbRepository() 생성 후 클라이언트에 주입│
   └─────────────────────────────────────────────────┘
```

- **생성자 주입 (Constructor Injection)** : 필수적인 의존성을 생성자의 매개변수로 전달받는 방식. 불변성(Immutable) 확보, 누락 시 컴파일 에러 발생, 순환 참조 감지 가능 (가장 권장됨).
- **수정자 주입 (Setter Injection)** : 선택적인 의존성을 변경할 수 있도록 Setter 메서드를 제공하는 방식. 런타임에 의존성 교체가 가능하나 객체 상태가 불완전해질 위험 존재.
- **필드 주입 (Field Injection)** : @Autowired 어노테이션으로 필드에 직접 주입. 코드가 간결하나 순수 자바 단위 테스트 작성이 어렵고 DI 프레임워크에 강하게 결합되는 안티패턴.

## Ⅲ. 3가지 주입 방식 비교

| 주입 방식 | 불변성 (Immutability) | 테스트 용이성 | 순환 참조 감지 | 권장 여부 |
|---|---|---|---|---|
| 생성자 주입 | 완벽 보장 (final 필드 선언 가능) | 프레임워크 없이 순수 POJO Mock 주입 가능 | 애플리케이션 구동 시점에 즉시 예외 발생 | 최우선 권장 (Best Practice) |
| 수정자 주입 | 보장 불가 (이후 재설정 가능) | Mock 주입 가능하나 메서드 호출 필요 | 런타임 호출 시점까지 지연될 수 있음 | 선택적 의존성에 한해 사용 |
| 필드 주입 | 보장 불가 (리플렉션 의존) | DI 프레임워크 없이는 Mock 주입 불가 | 구동 시점 감지 어려움 | 사용 지양 (Anti-pattern) |

## Ⅳ. 대규모 애플리케이션 아키텍처에서의 기술사적 제언

- **생성자 주입과 Lombok @RequiredArgsConstructor 표준화** : final 필드 선언과 롬복을 결합하여 보일러플레이트 코드를 제거하면서도 객체의 불변성을 확립하고, NullPointerException을 원천 차단하는 코딩 표준 수립.
- **도메인 계층의 프레임워크 독립성 유지** : 클린 아키텍처나 헥사고날 아키텍처 관점에서, 핵심 도메인 엔티티와 유스케이스는 특정 DI 컨테이너(Spring 등)의 어노테이션에 오염되지 않도록 순수 Java/코틀린 표준으로 유지하는 아키텍처 경계 통제 필요.
