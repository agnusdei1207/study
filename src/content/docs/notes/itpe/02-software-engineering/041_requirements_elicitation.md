## 연관 키워드

- 요구사항 도출(Requirements Elicitation), JAD(Joint Application Development), 프로토타이핑(Prototyping)
- 인터뷰, 설문지(Questionnaire), 관찰법(Observation), 브레인스토밍, MoSCoW, 카노(Kano) 모델

## Ⅰ. 요구사항 도출 기법의 개요

- 핵심 요약 : 이해관계자의 잠재 니즈와 제약조건을 구조화된 기법으로 이끌어내는 도출 활동.
- 개념 : 프로젝트 초기에 사용자, 고객, 운영자 등 이해관계자의 잠재 니즈, 비즈니스 목표, 시스템 제약조건을 체계적으로 발굴하는 공학적 활동 (**요구사항 도출**, Requirements Elicitation).
- 배경 및 필요성 : 사용자는 자신이 원하는 바를 말로 정리하지 못하는 암묵지(Tacit Knowledge) 상태에 있는 경우가 많고, 부서 간 이해관계가 엇갈려 요구가 누락되거나 왜곡되므로 구조화된 도출 기법이 필요함.
- 주요 목적 : 숨은 요구 발굴, 이해관계자 간 공감대 형성, 프로젝트 범위의 조기 명확화.

## Ⅱ. 요구사항 도출 기법의 특징 및 장점

- 핵심 요약 : 전통, 협업, 시각화, 관찰 계열 기법을 목적에 따라 나누어 쓰면 암묵지와 상충 요구를 함께 다룰 수 있는 구조.

1. 전통적 기법 : 인터뷰와 설문조사로 개별 의견과 현황을 수집 → 광범위한 의견을 짧은 시간에 확보.
2. 협업·합의 기법 : **JAD**(Joint Application Development, 공동 응용 개발) 워크숍과 브레인스토밍으로 이해관계자를 한자리에 모음 → 상충 요구를 조기에 조율.
3. 시각화·검증 기법 : **프로토타이핑**(Prototyping, 핵심 화면과 흐름을 시험 가능한 모형으로 구현) → 말로 정하기 어려운 요구를 화면으로 확인.
4. 관찰·인류학 기법 : 작업 관찰, 섀도잉(Shadowing), 에스노그래피(Ethnography)로 실제 업무 절차를 현장에서 확인 → 말로 드러나지 않는 불편 사항 발굴.

## Ⅲ. 요구사항 도출 기법의 구조 (흐름)

- 핵심 요약 : 기법을 네 계열로 분류하고, 단계마다 다른 계열을 이어 붙이는 하이브리드 파이프라인 구조.

```text
[ 요구사항 도출 기법 4계열 ]
전통적 기법
  (인터뷰, 설문조사)
협업·합의 기법
  (JAD, 브레인스토밍)
시각화·검증 기법
  (프로토타이핑)
관찰·인류학 기법
  (작업 관찰, 섀도잉)
```

```text
[ 하이브리드 도출 파이프라인 ]
1. 설문조사 (거시적 니즈 파악)
      ↓
2. 핵심 실무자 인터뷰 (심층 요구 확인)
      ↓
3. 프로토타이핑 (화면 기반 피드백)
      ↓
4. JAD 워크숍 (최종 합의와 조율)
```

- JAD 운영 방식 : 사용자, 개발자, 관리자가 중재자(Facilitator)의 진행으로 집중 워크숍을 열어 요구를 신속하게 합의.
- 작업 관찰과 섀도잉 : 사용자가 설명하지 못하는 실제 수행 절차와 불편 사항(Pain Point)을 현장에서 직접 확인.

## Ⅳ. 요구사항 도출 기법의 비교

- 핵심 요약 : 기법마다 적합한 상황과 장단점이 달라, 대상 규모와 합의 필요도로 기법을 고르는 기준.

| 기법 | 적합한 상황 | 주요 장점 | 주요 단점 |
| --- | --- | --- | --- |
| 인터뷰 (Interview) | 소수의 핵심 의사결정자, 도메인 전문가 | 깊이 있는 정성 요구와 배경 맥락 파악 | 다수 적용 불가, 인터뷰어 역량 편차 |
| 설문지 (Questionnaire) | 다수의 최종 사용자 의견 수렴 | 대량 데이터를 비교적 빠르게 수집 | 질문의 모호성, 세부 요구 파악 한계 |
| JAD 워크숍 | 부서 간 이해 상충이 크고 빠른 합의가 필요한 경우 | 의사결정 기간 단축, 갈등의 조기 조율 | 참석자 일정 조율 어려움, 진행자 역량 의존 |
| 프로토타이핑 | 사용자가 요구를 구체화하지 못한 경우 | 시각적 피드백으로 오해를 줄임 | 제작 공수 발생, 과도한 기대감 유발 가능 |
| 현장 관찰 (Observation) | 복잡한 수작업 공정이나 전문 조작 업무 | 암묵적 지식과 숨은 절차 발굴 | 관찰 대상자의 심리적 부담(호손 효과), 시간 소요 |

- 선택 기준 : 대상 인원이 많으면 설문, 합의가 급하면 JAD, 화면 요구가 불확실하면 프로토타이핑, 업무 지식이 암묵적이면 관찰을 우선 고려.

## Ⅴ. 요구사항 도출 기법의 한계와 방안

- 핵심 요약 : 소극적 참여, 우선순위 교착, 범위 확장의 한계를 관찰 기반 발굴, 정량 우선순위, 스코프 필터링으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 현업의 소극적 참여와 숨은 니즈 미발굴 | 본업 부담으로 단답형 응답에 그치고 현행 수작업을 그대로 전산화 | 업무 밀착 관찰(Job Shadowing), 에스노그래피 도입, 디자인 씽킹 워크숍으로 통증점 가시화 | 관찰 기반 신규 요구 건수 |
| 상충 요구의 조율 병목 | 부서별 목표가 충돌해(예: 편의성과 보안) 우선순위 합의가 교착 | MoSCoW 분류, 카노 모델, AHP(Analytic Hierarchy Process, 계층화 분석법)로 가치와 난이도를 정량 비교 | 우선순위 합의 소요 기간 |
| 범위의 무한 확장 (Gold Plating) | 비즈니스 목표와 무관한 희망 사항이 브레인스토밍에서 무분별하게 유입 | 프로젝트 헌장의 목표(OKR, KPI)와 연결된 항목만 남기는 스코프 필터링 | 목표 연계 요구 비율 |

## Ⅵ. 요구사항 도출에 대한 기술사적 제언

- 핵심 요약 : 단일 기법에 기대지 않는 하이브리드 조합을 표준 절차로 삼고, 생성형 AI는 도출 결과의 정리 도구로 활용.

도출 절차는 기법 하나를 고르는 방식이 아니라 설문으로 큰 방향을 잡고, 핵심 실무자 인터뷰와 프로토타이핑으로 세부를 확인한 뒤, JAD 워크숍에서 최종 합의하는 순서로 짜는 것이 좋다. 프로젝트 관리 조직이 이 순서를 표준 도출 절차로 정해 두면 단계마다 누락되는 요구를 줄일 수 있다.

인터뷰 녹취나 현장 기록이 방대할 때는 생성형 AI로 요약하고 페르소나와 사용자 스토리 초안을 만드는 방법을 쓸 수 있다. 다만 AI가 만든 초안은 이해관계자가 검증하기 전까지 요구로 확정하지 않는 원칙을 정보시스템 부서가 지침으로 명시해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 요구사항 도출은 기법의 조합과 우선순위의 정량화로 완성도를 높이는 상류 공학 활동.
- 시사점 : 암묵지를 드러내는 관찰과 프로토타이핑, 상충을 정리하는 JAD와 MoSCoW를 함께 써야 도출 누락과 왜곡을 줄일 수 있음.
