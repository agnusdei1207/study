## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 요구공학·설계 → **요구사항 도출 기법(Requirements Elicitation)**

## 30초 인출

- 본질: 다양한 이해관계자(사용자, 고객, 운영자, 도메인 전문가)로부터 명시적 요구뿐만 아니라 언어화되지 않은 암묵적 요구와 시스템 제약사항을 체계적으로 발굴하는 요구공학 초기 활동
- 메커니즘: 이해관계자 식별 및 분류 → 정성적/정량적 도출 기법(인터뷰, JAD, 관찰, 설문, 프로토타이핑) 적용 → 암묵지(Tacit)의 형식지(Explicit) 변환 → 요구사항 후보 목록화 및 출처 매핑
- 통찰: 특정 이해관계자의 목소리만 편향 청취할 경우 부서 간 충돌과 핵심 예외 프로세스 누락이 발생하므로 JAD 워크숍과 현장 관찰(Observation) 기반의 교차 검증 파이프라인 필수 구축

<details>
<summary>핵심 용어</summary>

- **Requirements Elicitation(요구사항 도출)** : 고객 및 사용자의 잠재적 니즈와 해결 과제를 다양한 공학 기법을 통해 끄집어내는 활동
- **Stakeholder(이해관계자)** : 시스템 개발에 직접적·간접적 영향을 주거나 시스템 결과로부터 영향을 받는 모든 개인 또는 조직
- **JAD(Joint Application Development)** : 사용자, 개발자, 관리자가 중립적 촉진자(Facilitator)의 주도하에 집중 워크숍을 통해 요구사항을 신속히 합의하는 협업 기법
- **Observation(현장 관찰/에스노그라피)** : 사용자가 실제 작업 환경에서 업무를 수행하는 모습을 직접 관찰하여 말로 표현하지 못하는 암묵적 지식과 예외를 발견하는 기법
- **Prototyping(프로토타이핑)** : 요구사항의 불확실성을 해소하기 위해 UI/UX나 핵심 기능 모형을 신속히 구현하여 피드백을 수렴하는 기법
- **Tacit Knowledge(암묵지)** : 사용자가 오랜 경험으로 체득하여 문서나 말로 명시하지 못하는 숨겨진 업무 지식

</details>

## 2~4교시 25점 답안

## Ⅰ. 요구사항 도출의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 개발 프로젝트의 착수 단계에서 시스템의 목적을 달성하기 위해 이해관계자의 내재된 비즈니스 요구, 사용자 요구, 시스템 제약사항을 체계적으로 수집하고 발굴하는 공학적 활동 |
| 목적 | 고객과 개발팀 간 요구사항 인식 격차 해소, 숨은 요구(암묵지)의 조기 발견, 과업 범위 정의를 위한 요구사항 베이스라인 토대 구축 |

## Ⅱ. 요구사항 도출의 핵심 특징

| 특징 | 의미 |
|---|---|
| 암묵지의 형식지 변환 | SECI 모델과 같이 사용자가 당연하게 여겨 말하지 않는 관행과 예외 절차를 가시화된 요구사항으로 도출 |
| 다각적 기법의 융합 | 단일 인터뷰에 의존하지 않고 관찰, 설문, 워크숍(JAD), 프로토타이핑을 상호 보완적으로 결합 |
| 이해관계자 다변화 | 최종 사용자, 발주자, 시스템 관리자, 규제 기관 등 다양한 계층의 요구와 상충 관계를 입체적 수렴 |
| 출처 및 근거 추적성 | 모든 도출된 요구사항에 대해 제안자, 인터뷰 일자, 원본 녹취록 등 발원 근거(Rationale) 부여 |

## Ⅲ. 요구사항 도출 체계 및 4단계 실행 프로세스

### 도출 전주기 프로세스 및 기법 간 교차 검증 구조

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1단계: 도출 준비 (Elicitation Preparation)                             │
│   - 이해관계자 맵핑(RACI 매트릭스), 비즈니스 목표 분석, 도출 기법 선정 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2단계: 다각적 도출 실행 (Elicitation Execution)                       │
│                                                                        │
│   [정성적 심층 탐색]           [집중 협업 및 합의]      [암묵지 및 가시화]│
│   - 개별 인터뷰(Interview)     - JAD 집중 워크숍       - 현장 관찰(Observation)│
│   - 전문가 델파이 기법         - 브레인스토밍          - 목업 프로토타이핑 │
│         │                             │                      │         │
│         └─────────────────────────────┼──────────────────────┘         │
│                                       ▼                                │
│                   [정량적 설문조사 및 기존 레거시 문서 분석]           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3단계: 도출 결과 정제 및 분류 (Consolidation & Conflict Resolution)    │
│   - 중복 요구 병합, 기능/비기능 분류, 요구사항 충돌(Trade-off) 식별    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4단계: 이해관계자 확인 및 확정 (Confirmation & Baseline)               │
│   - 사용자 확인 서명, 요구사항 등록부(Requirements Register) 작성      │
└────────────────────────────────────────────────────────────────────────┘
```

### 도출 프로세스 4대 단계 세부 활동

| 단계 | 수행 명칭 | 핵심 산출물 및 주요 활동 |
|---|---|---|
| **1단계** | **도출 준비** | 이해관계자 식별 매트릭스 작성, 프로젝트 배경 도메인 학습, 인터뷰 질문지 및 시나리오 준비 |
| **2단계** | **도출 실행** | 인터뷰, 관찰, 설문, JAD 워크숍 수행, 요구사항 원시 데이터(Raw Data) 및 회의록 기록 |
| **3단계** | **정제 및 분류** | 모호한 표현 정제, 상호 모순되는 요구사항 식별 및 우선순위 협의, 유스케이스 후보 도출 |
| **4단계** | **도출 결과 확인** | 도출된 요구사항을 이해관계자에게 재확인(Walkthrough)받고 초기 요구사항 목록 확정 |

## Ⅳ. 5대 요구사항 도출 기법 비교 및 상황별 선정

### 주요 도출 기법 간 특성 비교

| 비교 항목 | 인터뷰 (Interview) | JAD (집중 워크숍) | 현장 관찰 (Observation) | 설문조사 (Survey) | 프로토타이핑 (Prototyping) |
|---|---|---|---|---|---|
| **접근 방식** | 1:1 또는 소그룹 질의응답 | 다자간 집중 토론 및 합의 | 업무 현장 직접 밀착 관찰 | 표준 설문지 기반 원격 수집 | 시각적 모형 개발 및 시연 |
| **적합한 상황** | 개별 업무 심층 파악 및 예외 | 부서 간 이해관계 대립 시 | 사용자가 업무를 설명 못할 때 | 대규모 사용자 의견 수렴 | 화면/동선 요구가 모호할 때 |
| **주요 장점** | 심층적이고 구체적 정보 획득 | 신속한 합의 도출, 오버헤드 축소 | 실제 프로세스 및 편법 발굴 | 통계적 분석 가능, 비용 저렴 | 요구사항 직관적 검증 가능 |
| **주요 단점** | 면담자 스킬 의존, 많은 시간 소모 | 일정 조율 곤란, 주관적 발언 | 관찰자 효과(호손 효과) 발생 | 심층 의도 파악 불가, 회신율 저하 | 개발 비용 발생, 과도한 기대 |

### 이해관계자 유형별 최적 도출 기법 매핑

| 이해관계자 그룹 | 주요 관심사 및 특징 | 추천 도출 기법 및 접근 전략 |
|---|---|---|
| **최고 의사결정권자 (C-Level)** | 비즈니스 ROI, 시스템 구축 목표, 납기 및 예산 | **구조화된 1:1 심층 인터뷰**, 비즈니스 케이스 분석 |
| **현업 부서장 및 관리자** | 부서 간 업무 경계, 데이터 권한, 승인 결재선 | **JAD 워크숍**, 포커스 그룹 인터뷰(FGI) |
| **실무 현장 작업자** | 일상적 작업 효율성, 화면 입력 편의성, 예외 처리 | **현장 관찰(Job Shadowing)**, 사용성 프로토타이핑 |
| **일반 최종 소비자** | 직관적 UI, 빠른 응답 속도, 모바일 사용성 | **설문조사**, A/B 테스트, 사용자 여정 맵(User Journey) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 사용자가 자신이 진정으로 원하는 바를 알지 못하거나(Yes, but 증후군) 모호하게 진술 | 빠른 목업 프로토타이핑(Figma, 와이어프레임)을 선제시하여 구체적 피드백 유도 |
| 특정 직급자나 목소리 큰 이해관계자의 의견으로 요구사항이 왜곡되는 집단사고 현상 | 중립적 전문 퍼실리테이터를 투입하고 무기명 투표 및 델파이(Delphi) 기법 병행 |
| 부서 간 이기주의로 인한 상충되는 요구사항(예: 보안 강화 vs 업무 간소화)의 장기 표류 | 비즈니스 목표 기여도를 기준으로 MoSCoW 가중치 모델을 적용하고 스폰서 최종 중재 |

## Ⅵ. 제언

도메인 스토리텔링(Domain Storytelling)과 생성형 AI 인터뷰 봇을 활용한 지능형 요구사항 도출 파이프라인

### AI 기반 요구사항 도출 및 가시화 파이프라인

```text
[이해관계자 음성 인터뷰 / JAD 회의 녹음]
       ↓
[Whisper STT 음성 텍스트 변환 파이프라인]
       ↓
[LLM 기반 요구사항 분석 에이전트]
  ├─ 1. 비즈니스 액터, 액션, 업무 엔티티 자동 추출
  ├─ 2. 모호한 표현(형용사/부사) 탐지 및 추가 질의 리스트 생성
  ├─ 3. 사용자 스토리(User Story) 및 인수 조건(Given-When-Then) 자동 변환
  └─ 4. PlantUML 기반 도메인 스토리텔링 다이어그램 자동 렌더링
       ↓
[이해관계자 검토 및 클릭 기반 피드백 즉시 수렴]
```

### 요구사항 도출 기법 선정 의사결정 체계

```text
도출 대상 업무 및 이해관계자 특성 분석
       ↓
[사용자가 일상 업무 절차를 명확한 언어로 설명할 수 있는가?]
       ├─ 아니오 ─→ 현장 관찰(Observation) 및 에스노그라피 수행
       └─ 예 ───→ [부서 간 요구 충돌이나 인터페이스 대립이 존재하는가?]
                      ├─ 예 ──→ JAD (Joint Application Development) 워크숍 소집
                      └─ 아니오 ─→ [대상 사용자 집단이 수백 명 이상으로 방대한가?]
                                        ├─ 예 ──→ 설문조사(Survey) + 표본 인터뷰
                                        └─ 아니오 ─→ 1:1 심층 인터뷰 및 프로토타이핑
```

### 선택 근거: 전통적 인터뷰 방식과 제언 AI 결합 협업 도출 비교

| 구분 | 전통적 수기 인터뷰 중심 도출 | 제언: AI 결합 도메인 스토리텔링 도출 |
|---|---|---|
| 암묵지 발굴력 | 기록자의 주관적 필터링으로 숨은 요구 누락 | 발화 원문 전체 텍스트 분석 및 모호성 자동 질의 |
| 합의 도출 속도 | 회의록 정리 및 피드백에 수일 소요 | 회의 종료 즉시 다이어그램과 유스케이스 초안 가시화 |
| 요구사항 품질 | 기능 나열 위주로 작성되어 비즈니스 맥락 결여 | 액터-행동-가치 중심의 스토리텔링으로 맥락 보존 |
