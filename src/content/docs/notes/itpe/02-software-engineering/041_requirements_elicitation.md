## 답안 골격
```text
[요구사항 도출] ◀━━ 머리: Ⅶ 내 의견 (암묵지 발굴을 위한 인터뷰와 프로토타이핑 및 디자인 씽킹의 융합)
 ┃
 ┣━ Ⅰ 개요 ───── 이해관계자의 숨겨진 니즈 미식별로 인한 실패 극복 → 체계적 요구 수집 활동
 ┣━ Ⅱ 특징 ───── 인간 중심 접근 · 암묵지(Tacit Knowledge)의 형식지화 · 이해관계자 전원 참여
 ┣━ Ⅲ 구조 ───── 전통적 기법(인터뷰, 설문) + 그룹 기법(브레인스토밍, JAD, 워크숍) + 관찰/프로토타입
 ┣━ Ⅳ 흐름 ───── ① 이해관계자 식별 → ② 도출 기법 선정 → ③ 요구 수집 실행 → ④ 정제 및 합의
 ┣━ Ⅴ 비교 ───── 인터뷰(심층 개별 니즈) vs 설문조사(대규모 통계) vs JAD(집중 공동 합의)
 ┗━ Ⅵ 실무 ───── 이해관계자 간 상충 요구와 언어 장벽 / 사용자 스토리(User Story) 및 공감 맵(Empathy Map)
```
- 필수 키워드: 암묵지 · 인터뷰 · 설문조사 · 브레인스토밍 · JAD(Joint Application Design) · 프로토타이핑 · 디자인 씽킹
- 배점 전략: 10점 = Ⅲ 도출 기법 4대 분류 체계 표 → Ⅴ 주요 기법 비교 / 25점 = Ⅰ~Ⅶ 전개, 124회 기출 디자인 씽킹의 공감(Empathize) 기법과 JAD 융합
- 기출: 124회 2교시 `사용자 요구사항 도출 기법 4가지 및 요구사항 도출 시 유의사항` → Ⅰ·Ⅲ·Ⅵ / 130회 4교시 `요구사항 체계적 관리와 문서화` → Ⅲ·Ⅳ

## 한 줄 본질
- 고객이 자신의 업무를 너무 당연하게 여겨 말로 설명하지 못하는 암묵적 지식(Tacit Knowledge)의 전달 병목 → 인터뷰, 관찰, 워크숍(JAD), 프로토타이핑을 통해 고객의 숨은 고통과 잠재 요구를 시각적·공식적으로 추출 → 요구사항 누락 방지 및 프로젝트 목표 정렬 / 일정 및 다자간 합의 도출 시간 소모 대가

## 핵심 그림
```text
                  [ 요구사항 도출 기법 4대 스펙트럼 ]
+----------------------+----------------------+----------------------+----------------------+
| 1. 개별적 기법       | 2. 집단적 기법       | 3. 관찰/분석 기법    | 4. 실험/체험 기법    |
+----------------------+----------------------+----------------------+----------------------+
| - 심층 인터뷰        | - 브레인스토밍       | - 현장 직무 관찰     | - UI/UX 프로토타입   |
| - 설문지 조사        | - JAD (집중 워크숍)  | - 기존 문서/양식 역분석| - 디자인 씽킹(공감)  |
| - 1:1 Q&A 세션       | - 워크플로 워크숍    | - 타사 벤치마킹      | - 유스케이스 롤플레잉|
+----------------------+----------------------+----------------------+----------------------+
```

## 핵심 용어
- JAD(Joint Application Design): 사용자와 개발자, 중재자(Facilitator)가 집중 워크숍을 통해 요구사항을 단기간에 집중 합의·도출하는 공동 애플리케이션 설계 기법
- 암묵지(Tacit Knowledge): 현업 사용자의 몸에 체화되어 있으나 문서나 언어로 명확히 표현되지 않아 면밀한 관찰과 질문 없이는 드러나지 않는 지식

## 핵심 통찰
- 사용자가 "이런 기능이 필요하다"고 말하는 솔루션(Wants)을 그대로 적는 것은 하수이며, "왜 그 작업이 필요한가?"를 파고들어 근본 문제(Needs)를 캐내는 것이 요구 도출의 본질임
- 인터뷰만으로는 사용자가 거짓말을 하거나 왜곡된 기억을 전달할 수 있으므로, 실제 업무 현장을 지켜보는 에스노그래피(Ethnography, 현장 관찰)가 병행되어야 함
- 프로토타입은 "백문이 불여일견"의 원칙을 실현하여 말로 소통할 때 발생하는 80% 이상의 오해를 첫 화면 시연만으로 단숨에 해소함

## 이웃 토픽과 구분
- 요구사항 도출 vs 요구사항 분석: 도출 = 요구사항을 수집하고 끌어내는 활동(Gathering) / 분석 = 도출된 요구사항의 충돌을 해결하고 모델링하는 활동(Refining)

## 문제·원인·대책
- 사례: 124회 기출 대형 차세대 프로젝트 요구 도출 부실로 인한 오픈 후 대규모 재작업
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 개발 완료 후 현업이 "기존 레거시 화면의 필수 기능이 빠졌다"며 배포 거부 | 인터뷰 대상자를 관리자급으로만 한정하여 실무자 예외 업무 파악 누락 | 실무자 대상 직무 관찰 및 기존 화면/출력물 전수 리버스 엔지니어링 병행 | 실무 암묵적 예외 요구사항 100% 발굴 |
| 인터뷰 회의에서 부서 간 이견 대립으로 1개월간 요구사항 도출 공전 | 중재자 없는 자유 토론으로 인한 부서 이기주의 충돌 | 독립된 퍼실리테이터가 진행하는 타임박스 JAD 워크숍 강제 | 3일 집중 세션으로 전사 단일 요구사항 합의 완료 |

## 이렇게 출제된다
- 제124회 2교시 3번: "사용자 요구사항 도출 기법 4가지 및 요구사항 도출 시 유의사항" → 요구 포인트: 인터뷰, 설문, JAD, 관찰의 개념 및 장단점 + 도출 시 이해관계자 편향 방지 유의사항
- 제124회 2교시 2번: "디자인 싱킹(Design Thinking)에서 요구분석을 위한 공감(Empathize)방법의 중요성" → 요구 포인트: 사용자 인터뷰와 관찰을 통한 잠재 니즈 도출

## 내 의견
- [요구사항 도출을 단순 설문지 배포로 때우는 게으름] 수백 개 문항의 엑셀 설문지를 배포하고 객관식 응답만 취합했다가, 실제 현업 업무 프로세스의 병목을 단 하나도 짚어내지 못하는 실패 목격 → 나라면: 사용자 여정 지도(Customer Journey Map)를 벽에 붙이고 현업 실무자와 함께 페인 포인트(Pain Point)를 포스트잇으로 붙이는 이벤트 스토밍(Event Storming) 워크숍을 도입하여 요구사항 도출을 촉진
