## 연관 키워드
- 캡슐화, 정보 은닉, 불변조건, 결합도
- Tell, Don't Ask, 도메인 모델

## Ⅰ. 캡슐화의 개요

- 핵심 요약 : 캡슐화는 상태와 연산을 묶고 내부 구현을 숨겨 공개된 연산으로만 상호작용하게 하는 객체지향 설계 원칙.
- 개념 : 객체의 상태(데이터)와 그 상태를 다루는 연산을 하나로 묶고, 내부 구현을 외부에 숨겨 공개된 연산을 통해서만 접근하게 하는 객체지향 설계 원칙이 **캡슐화** (Encapsulation)임.
- 배경 및 필요성 : 외부 코드가 내부 상태를 직접 수정하면 객체의 **불변조건** (유효한 상태를 항상 유지해야 하는 조건)이 깨지고, 구현 변경이 광범위하게 파급됨.
- 주요 목적 : 낮은 **결합도** (모듈·객체 간 상호 의존 정도)와 변경 파급 최소화를 통한 유지보수성·재사용성 확보.

## Ⅱ. 캡슐화의 특징 및 장점

- 핵심 요약 : 상태 은닉·구현 세부 은닉·책임 응집·명령 중심 협력이 유지보수성과 재사용성으로 연결됨.

1. 상태 은닉 : 접근제한자(private)로 내부 필드를 보호하고 상태 변경을 공개 연산으로 제한 → 불변조건 보호와 오류 원인의 국소화 효과.
2. 구현 세부 은닉 : 자료구조·알고리즘 같은 구현 세부를 숨기는 **정보 은닉** (Information Hiding) → 내부 교체가 외부 호출부에 영향을 주지 않는 변경 용이성 확보.
3. 책임 응집 : 상태와 그 상태를 다루는 행위를 한 객체에 배치 → 자신의 데이터와 규칙을 스스로 다루는 응집도 향상.
4. 명령 중심 협력 : 상태를 꺼내 외부에서 판단하지 않고 객체에 명령을 전달하는 **Tell, Don't Ask** (묻지 말고 명령하라) 원칙 적용 → 판단 로직 분산 방지와 결합도 축소 효과.

## Ⅲ. 캡슐화의 구조 (흐름)

- 핵심 요약 : 불변조건 정의부터 상태 은닉·연산 공개·접근 통제까지 설계 절차로 적용하고, 접근은 공개 연산 경로로만 허용.

```text
불변조건 정의
   ↓
상태 필드 은닉 (private)
   ↓
업무 연산 설계 (public)
   ↓
입력 검증·상태 전이 통제
   ↓
단위 시험으로 경계 확인
```

```text
외부 코드 → 공개 연산 → 검증 → 내부 상태

외부 코드 → 내부 필드 직접 접근 : 차단
```

## Ⅳ. 캡슐화와 상속 중심 재사용의 비교

- 핵심 요약 : 부모 구현을 물려받는 상속 중심 재사용과 달리, 캡슐화는 공개 계약 중심의 재사용으로 변경 파급을 최소화.

| 비교 축 | 상속 중심 재사용 | 캡슐화 중심 설계 |
| --- | --- | --- |
| 재사용 수단 | 부모 클래스 구현의 물려받기 | 합성·공개 인터페이스 호출 |
| 내부 노출 | protected 등 일부 내부 노출 | 구현 전체 은닉·계약만 공개 |
| 결합 대상 | 자식이 부모 구현 세부에 결합 | 호출부가 공개 계약에만 결합 |
| 변경 파급 | 부모 변경이 자식 전체에 파급 | 내부 교체 시 호출부 영향 최소 |
| 대표 위험 | **취약 기반 클래스** (fragile base class, 부모 변경에 무너지는 자식) 문제 | 게터·세터 남발의 형식적 캡슐화 |

## Ⅴ. 캡슐화의 한계와 방안

- 핵심 요약 : 형식적 접근자·규칙 분산·기술 제약·과잉 은닉을 업무 연산·경계 분리·최소 노출 원칙으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 게터·세터 남발 | 모든 필드에 접근자 자동 생성 → 상태가 사실상 공개 | 업무 의미 연산 위주 설계·코드 리뷰 기준 적용 | 외부 상태 변경 지점 수 |
| **빈약한 도메인 모델** (Anemic Domain Model, 데이터만 담는 객체 설계) | 규칙이 서비스 계층으로 분산 → 규칙 중복·불일치 | 규칙과 행위를 도메인 객체에 응집 배치 | 계층 간 규칙 중복 수 |
| 기술 제약 | 직렬화·객체 관계 매핑(ORM, Object-Relational Mapping)의 필드 접근 요구 | 도메인 객체와 데이터 전송 객체(DTO, Data Transfer Object) 경계 분리 | 도메인 외부 노출 인터페이스 수 |
| 과잉 은닉 | 필요한 협력까지 차단 → 우회 코드·복잡도 증가 | 협력에 필요한 최소 연산만 공개·정기 재검토 | 우회·중복 코드 비율 |

## Ⅵ. 캡슐화에 대한 제언

- 핵심 요약 : 개발 조직은 설계 표준·검증 도구·교육으로 캡슐화를 개인 관습이 아닌 팀의 기본 역량으로 내재화해야 함.

1. 설계 표준 : 아키텍트가 접근제한자 기준·연산 공개 원칙을 코딩 표준으로 규정하고 도메인 설계 가이드를 배포.
2. 검증 체계 : 코드 리뷰·정적 분석 규칙에 캡슐화 위반 점검 항목을 포함해 설계 품질을 상시 확인.
3. 역량 확산 : 도메인 주도 설계(DDD, Domain-Driven Design) 교육과 설계 사례 공유로 책임 중심 모델링 문화 확산.

## Ⅶ. 결론

- 핵심 요약 : 캡슐화는 접근제한자 선언이 아니라 객체가 자신의 상태와 규칙을 책임지는 설계 원칙.
- 시사점 : 내부 구현을 숨긴 계약 중심 협력만이 규모 확장에도 유지보수성을 유지하는 기반이 됨.
