## 연관 키워드

- SW 비용 산정, 공수(M/M, Man-Month), LOC(Lines of Code), COCOMO(Constructive Cost Model)
- 기능점수(FP, Function Point), 하향식/상향식 산정, 델파이(Delphi) 기법, 간이 기능점수법, DET/RET/FTR

## Ⅰ. SW 규모·비용 산정의 개요

- 핵심 요약 : 요구사항을 분석해 소프트웨어 규모를 정량 측정하고, 공수와 예산을 예측하는 계획 단계의 공학적 프로세스.
- 개념 : 개발 계획 단계에서 요구사항을 분석해 소프트웨어 크기를 정량 측정하고, 이를 바탕으로 필요한 **공수** (M/M, Man-Month)와 예산을 예측하는 공학적 프로세스(**SW 비용 산정**, Software Cost Estimation).
- 배경 및 필요성 : 근거 없는 예산 책정으로 인한 부실 개발을 막고, 공공 SW(Software) 사업 발주 시 객관적 계약 기준을 세울 필요가 있음.
- 주요 목적 : 예측 가능한 일정과 예산 수립을 통한 프로젝트 성공률 제고.
- 3대 기법 :
  1. 소스코드 라인 수를 기준으로 하는 **LOC** (Lines of Code, 코드 라인 수) 기법.
  2. 정량 수식으로 노력을 산출하는 **COCOMO** (Constructive Cost Model, 구축 비용 모델) 기법.
  3. 사용자 관점의 논리 기능을 세는 **기능점수** (FP, Function Point) 기법.

## Ⅱ. SW 규모·비용 산정의 특징 및 장점

- 핵심 요약 : 하향식, 상향식, 수학적 모델, 기능 기반의 네 갈래 기법이 상호 보완하며 단계별 견적을 가능하게 하는 체계.

1. 하향식 산정 (Top-Down) : 전문가 판단과 **델파이 기법** (Delphi, 전문가 의견을 반복 수렴하는 방식)으로 전체 규모를 추정 → 초기 단계의 빠른 개략 견적.
2. 상향식 산정 (Bottom-Up) : 작업 단위별 노력을 합산하고 LOC 기반으로 단계별 노력을 계산 → 세부 근거가 명확한 견적.
3. 수학적 모델 : COCOMO 계열(Basic, Intermediate, Detailed, COCOMO II)의 정량 수식으로 노력을 산출 → 규모 변수에 따른 재현 가능한 계산.
4. 기능 기반 규모 측정 : 사용자 관점의 논리 기능을 세는 기능점수 모델로, ISO(International Organization for Standardization)/IEC(International Electrotechnical Commission) 20926에 규정된 측정 방법을 따름 → 언어와 기술 스택에 독립적인 규모 측정.
5. 산정 단위 : 공수(M/M, Man-Month)를 노력 단위로 쓰고 이를 인건비 등 예산으로 환산 → 일정과 예산의 직접 연결.

## Ⅲ. SW 규모·비용 산정의 구조 (흐름)

- 핵심 요약 : 하향식에서 수학적 모델과 기능 기반 측정으로 발전하는 기법 체계와, 기능점수의 단계별 적용 절차.

```text
[ 비용 산정 기법 체계 ]

하향식 산정 : 전문가 판단, 델파이 기법
   ↓
상향식 산정 : LOC 기반 단계별 노력 합산
   ↓
수학적 모델 : COCOMO 정량 수식
   ↓
기능 기반 측정 : 기능점수 (ISO/IEC 20926)
```

- COCOMO 노력 식 : 노력 = A × KLOC(Kilo Lines of Code)^B × EAF(Effort Adjustment Factor, 노력 조정 계수).
- 프로젝트 유형별 계수 : 조직형(Organic)은 50 KLOC 이하의 소규모 업무용 SW에, 반분리형(Semi-detached)은 중간 규모의 트랜잭션·컴파일러 시스템에, 임베디드형(Embedded)은 엄격한 하드웨어 제약을 받는 시스템에 적용.

```text
[ COCOMO 프로젝트 유형별 계수 ]

조직형 (Organic) : 소규모 업무용
   A=2.4, B=1.05
        ↓
반분리형 (Semi-detached) : 중간 규모
   A=3.0, B=1.12
        ↓
임베디드형 (Embedded) : 제약 조건 큼
   A=3.6, B=1.20
```

- 기능점수 측정 요소 :
  1. 데이터 요소수(DET, Data Element Type) : 사용자가 인식하는 고유 데이터 항목 수.
  2. 레코드 요소수(RET, Record Element Type) : 데이터 그룹 내부의 하위 구분 수.
  3. 참조 파일수(FTR, File Type Referenced) : 트랜잭션이 참조하는 논리 파일 수.
- 단계별 적용 : 기획·예산 단계에서는 평균 복잡도를 쓰는 **간이 기능점수법**을 적용하고, 분석·설계가 끝나면 DET·RET·FTR을 정밀 측정하는 정규법으로 전환하며, 최종적으로 사후 정산(True-up)으로 차이를 맞춤.

## Ⅳ. 주요 SW 규모·비용 산정 기법의 비교

- 핵심 요약 : LOC는 단순하지만 언어에 의존하고, COCOMO는 정량적이지만 현대 개발 환경 반영에 한계가 있으며, 기능점수는 기술 독립적이고 객관적인 기준.

| 비교 항목 | LOC (코드 라인 수) | COCOMO 모델 | 기능점수 (FP, Function Point) |
| --- | --- | --- | --- |
| 산정 기준 | 소스코드의 물리적 라인 수 | 코드 라인 수와 노력 조정 계수(EAF) | 사용자 관점의 논리적 기능 수 |
| 측정 시점 | 코딩 이후 또는 상세 설계 후반 | 구현 단계에 근접한 시점 | 기획 및 요구사항 분석 초기 단계 |
| 언어 의존성 | 프로그래밍 언어에 강하게 의존 | 언어에 의존 (KLOC 기준) | 언어·개발 도구·기술 스택과 무관 |
| 장단점 | 단순하고 직관적이나 초기 예측이 불가능 | 정량적이나 현대 고수준 언어 반영에 한계 | 객관적이고 표준화되었으나 분석가 역량에 의존 |
| 활용 맥락 | 과거 생산성 데이터 축적과 사후 분석 | 구현 단계의 노력 추정 | 공공 SW 사업 대가 산정의 기준 척도 |

## Ⅴ. SW 규모·비용 산정의 장점과 한계

- 핵심 요약 : 데이터 기반의 객관적 예산 수립이라는 장점과, 초기 불확실성·신기술 미반영·산정자 주관성이라는 한계.

1. 데이터 기반의 객관적 예산 및 일정 수립.
2. 적정 대가 산정을 통한 개발자 권익 보호.
3. 공공 SW 사업의 표준화된 계약 기준 제공.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 초기 요구사항 불확실성에 따른 기능점수 왜곡 | 기획 단계에서 데이터 모델과 트랜잭션이 구체화되지 않아 간이법에 의존 → 실제 투입 공수와 견적 오차 발생 | 유사 프로젝트 기반 모수 추정(Parametric Estimation)을 병행하고, 분석·설계 완료 후 정규법으로 재산정(True-up)하는 단계별 정산 제도화 | 단계별 견적 오차율 |
| 신기술 생산성 미반영 | 레거시 Java·C 환경 기준의 FP·LOC 모델이 클라우드 SaaS, 노코드 도구, 생성형 AI 코딩 도입에 따른 생산성 변화를 담지 못함 | 대가 산정 가이드에 신기술 보정 계수를 반영하고, 애자일 팀의 벨로시티 기반 스토리 포인트 추정을 상호 보완으로 활용 | 보정 계수 적용 건수 |
| 산정자 주관성과 복잡도 판정 불일치 | DET·RET·FTR 식별 기준을 산정자마다 다르게 적용 → 같은 요구사항에서도 발주자와 수주자의 견적 분쟁 발생 | 공인 기능점수 전문가(CFPS, Certified Function Point Specialist) 참여, 요구사항 명세와 DB(Database) 스키마 기반 측정 도구 도입, 내부 산정 매뉴얼 확립 | 견적 분쟁 건수 |

## Ⅵ. 공공 SW 및 현대 클라우드 환경에서의 기술사적 제언

- 핵심 요약 : 간이법과 정규법의 단계별 적용을 제도화하고, 클라우드와 AI의 생산성 변화를 반영하도록 산정 체계를 현대화하는 것이 필요.

1. 단계별 기능점수 적용 : 발주 절차에 기획 단계의 간이법, 설계 완료 후의 정규법, 사후 정산을 명시하도록 발주 기관이 가이드를 개정해야 한다. 초기 예산 범위와 최종 계약 금액 사이의 간격을 줄이는 것이 목표다.
2. 클라우드·AI 생산성 반영 : 레거시 코딩 생산성을 전제로 한 대가 체계는 SaaS(Software as a Service) 도입, 로우코드·노코드(LCNC, Low-Code/No-Code) 도구, 생성형 AI 활용에 따른 공수 변화를 담지 못하므로, 보정 계수와 구독형 비용 항목을 산정 기준에 포함해야 한다.
3. 산정 품질 관리 : 공인 전문가 검증과 자동화 측정 도구를 병행 운영하여 산정자 간 편차를 줄이는 체계를 갖춰야 한다.

## Ⅶ. 결론

- 핵심 요약 : 공공 표준인 기능점수법의 단계별 정밀화와 신기술 보정이 SW 비용 산정의 신뢰도를 좌우함.
- 시사점 : 사업 초기 견적과 최종 정산 사이의 오차가 줄어드는 것이 산정 체계 현대화의 대표적 성과 지표가 됨.
