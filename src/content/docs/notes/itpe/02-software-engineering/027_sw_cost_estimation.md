## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어 공학 → 공공 SW·거버넌스 → **SW 규모·비용 산정**

## 30초 인출

- 본질: **SW 규모·비용 산정**은 소프트웨어 개발 프로젝트의 공수, 일정, 소요 예산을 합리적으로 예측하여 예산 왜곡과 사업 부실을 방지하는 정량적 측정 체계
- 메커니즘: 규모 측정(**LOC, FP, 스토리 포인트**) → 노력(Man-Month) 추정(**COCOMO II, Putnam, 기능점수 단가법**) → 개발 원가 산출
- 효과: 합리적 발주 예산 확정 · 과업 변경 대가 산정 기준선(Baseline) 마련 · 개발 생산성 평가

<details>
<summary>핵심 용어</summary>

- **Function Point (기능점수, FP)**: 사용자가 요구한 기능의 논리적 크기를 데이터 기능(ILF, EIF)과 트랜잭션 기능(EI, EO, EQ)으로 측정하는 표준 기법
- **LOC(Lines of Code)**: 원시 소스코드의 총 라인 수를 기준으로 소프트웨어 규모를 측정하는 전통적 기법
- **COCOMO (Constructive Cost Model)**: Boehm이 제안한 모델로, 규모(KLOC)와 프로젝트 복잡도(비용동인)를 수학 공식에 대입해 공수(M/M)를 산출하는 기법
- **COCOMO II**: 현대 소프트웨어 공학(객체지향, 재사용, RAD)을 반영하여 Application Composition, Early Design, Post-Architecture 3단계로 발전된 모델
- **SW사업 대가산정 가이드**: 한국소프트웨어산업협회의 사업 대가 추정 참고 기준. 적용 연도와 사업 유형에 맞는 산정 조건의 확인 필요.

</details>

## 1교시 10점 답안

### Ⅰ. SW 규모·비용 산정의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **SW 규모·비용 산정** 은 소프트웨어 규모를 추정해 개발 노력·일정·비용으로 연결하는 활동 |
| 목적 | 예산·일정 계획과 과업 변경 영향 비교 |

### Ⅱ. 산정 기준 비교

| 기법 | 주요 입력 | 유의점 |
|---|---|---|
| LOC | 코드 라인 수 | 언어·구현 방식에 영향 |
| COCOMO | 코드 규모·비용 동인 | 보정 계수와 경험 데이터 필요 |
| FP | 사용자 기능 5종 | 비기능 작업은 별도 확인 |

**핵심 통제**

- **COCOMO 모델**: KLOC 기반 수학적 공수 산정 및 비용동인(Cost Driver) 반영
- **FP 구성**: 데이터 기능 ILF·EIF, 트랜잭션 기능 EI·EO·EQ의 분류

- 한 줄 제언: 초기 추정 가정을 기록하고 기능 범위가 구체화될 때 산정 근거 갱신

## 2~4교시 25점 답안

## Ⅰ. SW 규모·비용 산정의 개요

> **SW 비용 산정**은 구현 범위를 규모로 추정하고 노력·기간·비용으로 연결하는 작업.

| 구분 | 핵심 |
|---|---|
| 정의 | **SW 규모·비용 산정** 은 소프트웨어 규모를 추정해 개발 노력·일정·비용으로 연결하는 활동 |
| 목적 | 예산·일정 계획과 과업 변경 영향 비교 |

## Ⅱ. 3대 주요 비용 산정 기법: LOC, COCOMO, 기능점수(FP)

> LOC·COCOMO·FP는 서로 다른 기준으로 추정하며, 요구사항의 구체화 정도와 사업 특성에 맞게 고른다.

| 비교 항목 | LOC 기법 | COCOMO 기법 | 기능점수 (Function Point) |
|---|---|---|---|
| **측정 기준** | 소스코드 라인 수 | 코드 규모와 비용 동인 | 사용자 관점 논리적 기능 수 |
| **적용 시점** | 언어·구현 방식이 구체화된 뒤 정확도 향상 | 입력 규모·보정 근거가 있을 때 | 기능 요구와 경계가 정의되면 산정 가능 |
| **주의점** | 언어와 코딩 방식에 영향 | 계수·경험 데이터 보정 필요 | 비기능·연구개발 작업량은 별도 고려 |
| **특성·근거** | 구현 후 측정 용이 | 경험 데이터 보정 필요 | 국제 표준·공공 대가산정 가이드에서 활용 |

## Ⅲ. 기능점수(FP)의 5대 기능 구성요소와 산정 체계

> **기능점수**의 데이터 기능 2종과 트랜잭션 기능 3종 구분.

### 기능점수(FP) 5대 기능 분류 및 개발비 산정 메커니즘

| 구분 | 기능 | 확인할 경계 |
|---|---|---|
| 데이터 | ILF | 대상 시스템이 유지하는 논리적 데이터 |
| 데이터 | EIF | 다른 시스템이 유지하고 대상 시스템이 참조하는 데이터 |
| 트랜잭션 | EI | 외부 입력으로 데이터·동작을 변경 |
| 트랜잭션 | EO | 계산·파생을 포함한 외부 출력 |
| 트랜잭션 | EQ | 파생 계산 없이 조회하는 외부 질의 |

### 공공 SW 사업 산정 시 확인할 요소

| 요소 | 확인 사항 |
|---|---|
| 기능 규모 | ILF·EIF·EI·EO·EQ의 경계와 중복 여부 |
| 대가 산정 | 적용 가이드의 기준 연도·단가·보정 항목·직접경비 |
| 변경 | 승인된 과업 범위와 산정 근거가 함께 바뀌었는지 |

## Ⅳ. 소프트웨어 비용 산정 한계·대응책

> 추정 근거가 부족하거나 과업 변경이 반영되지 않으면 비용과 실제 작업 범위가 어긋난다.

| 위험 | 대책 | 효과 |
|---|---|---|
| 초기 요구가 불명확함 | 산정 가정을 명시하고 기능이 구체화될 때 재산정 | 추정 오차의 원인 확인 |
| 성능·보안 등 비기능 작업이 FP에 드러나지 않음 | 해당 가이드의 보정·별도 산정 기준과 실제 작업량 검토 | 누락된 비용 항목 식별 |
| 과업 범위가 변경됨 | 변경 내용·규모·일정 영향을 기록하고 계약상 절차에 따라 검토 | 승인된 범위와 추정액의 차이 추적 |

## Ⅴ. 산정 근거와 과업 변경에 대한 제언

> 기능 규모와 비기능 작업의 분리 추정, 과업 변경 시 범위·일정·비용 근거의 동시 갱신.

| 한계 | 해결 방안 |
|---|---|
| 요구사항 성숙도와 무관하게 한 가지 산정 기법만 적용함 | 초기 단계의 유사 과업·전문가 판단 기반 범위 추정, 요구 구체화 뒤 규모 기준·생산성 자료에 따른 상세 산정 |
