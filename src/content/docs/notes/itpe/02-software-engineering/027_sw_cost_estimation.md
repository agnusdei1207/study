## 답안 골격
```text
[SW 규모·비용 산정] ◀━━ 머리: Ⅶ 내 의견 (요구사항 조기 고정 및 기획 단계 간이법과 개발 단계 정규법의 단계별 정밀화)
 ┃
 ┣━ Ⅰ 개요 ───── 주관적 라인 수(LOC) 산정의 왜곡 극복 → 사용자 관점의 논리적 기능 규모 측정
 ┣━ Ⅱ 특징 ───── 프로그래밍 언어 독립적 · 데이터 기능(ILF, EIF)과 트랜잭션 기능(EI, EO, EQ) 분류
 ┣━ Ⅲ 구조 ───── 데이터 기능 2종 + 트랜잭션 기능 3종 = 총 미조정 기능점수(UFP) × 보정계수 = 보정 FP
 ┣━ Ⅳ 흐름 ───── 기능 식별 → RET/DET 또는 FTR/DET 기반 복잡도 판정(간이법은 평균 복잡도) → FP 산출 → 단가 곱셈
 ┣━ Ⅴ 비교 ───── 정규 기능점수법(상세 복잡도 매트릭스) vs 간이 기능점수법(평균 복잡도 적용) vs LOC 기반
 ┗━ Ⅵ 실무 ───── 공공 SW 사업 과소 산정 및 과업 변경 분쟁 / 사업대가 산정 가이드 2025 기준 준수
```
- 필수 키워드: 기능점수(FP) · ILF · EIF · EI · EO · EQ · DET/RET/FTR · 간이법 · 보정계수 · SW사업 대가산정 가이드
- 배점 전략: 10점 = Ⅲ 5대 기능 구성요소 표 및 산식 → Ⅴ 정규법과 간이법 비교 / 25점 = Ⅰ~Ⅶ 전개, 공공 SW 대가산정 현실적 개선 방안(과업심의위 연계)
- 기출: 132회 4교시 `소프트웨어 규모 산정 방식 종류·특징 및 공공 사업 현실적 개선 방안` → Ⅰ·Ⅲ·Ⅵ / 126회 2교시 `SW 비용 산정방법 비교` → Ⅴ

## 한 줄 본질
- 코드 라인 수(LOC)나 투입 인력(M/M)에 의존한 비용 산정의 왜곡과 저가 수주 병목 → 사용자가 요구하는 데이터 저장 및 입출력 기능을 5대 표준 기능(ILF, EIF, EI, EO, EQ)으로 정량화하고 단가를 곱해 예산 도출 → 객관적·표준적 사업 대가 산정 / 분석·설계 초기 상세 기능 도출의 불확실성 대가

## 핵심 그림
```text
                  [ 기능점수(FP) 5대 기능 분류 ]
             +--------------------+--------------------+
             | 데이터 기능 (Data) | 트랜잭션 기능 (Tx) |
+------------+--------------------+--------------------+
| 내부 관점  | 내부논리파일 (ILF) | 외부입력 (EI)      |
+------------+--------------------+--------------------+
| 외부 관점  | 외부연계파일 (EIF) | 외부출력 (EO)      |
|            |                    | 외부조회 (EQ)      |
+------------+--------------------+--------------------+
  * UFP (미조정 FP) = (ILF*7.5 + EIF*5.4 + EI*4.6 + EO*5.2 + EQ*3.9) - (간이법 가중치 예시)
  * 최종 보정 FP = UFP * 규모보정 * 연계복잡도 * 성능보정 * 다국어보정
```

## 핵심 용어
- ILF(Internal Logical File): 대상 시스템 내부에서 등록·수정·삭제 등 유지관리되는 사용자 식별 가능한 논리적 데이터 그룹
- 간이 기능점수법: 개발 초기 상세 DET, RET를 알 수 없을 때 기능의 개수에 평균 가중치를 곱하여 빠르게 규모를 산출하는 실무 기법
- EO vs EQ: EO(외부출력)는 계산 로직이나 파생 데이터 생성이 포함된 출력이고, EQ(외부조회)는 단순 검색 및 직접 출력만을 수행함

## 핵심 통찰
- 기능점수는 코딩 방식이나 언어(C, Java, Python)와 무관하게 사용자가 체감하는 비즈니스 기능의 양만을 측정하므로 계약 표준으로 가장 적합함
- 예산 수립 단계(기획)에서는 화면과 테이블이 확정되지 않아 정규법 적용이 불가능하므로 공공 대가산정 가이드에서는 '간이법'을 표준으로 채택함
- EO와 EQ를 가르는 핵심 기준은 '수학적 계산이나 파생 데이터 생성 유무'이며, 단순 조회를 EO로 둔갑시켜 예산을 부풀리는 산정 왜곡이 자주 발생함

## 이웃 토픽과 구분
- 정규법 vs 간이법: 정규법 = DET/RET 매트릭스로 상/중/하 복잡도 개별 계산 / 간이법 = 기능 유형별 사전 고정된 평균 복잡도 가중치 일괄 적용

## 문제·원인·대책
- 사례: 132회 기출 공공 차세대 소프트웨어 사업 규모 산정 부실 및 과업 변경 분쟁
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 사업 기획 단계 산정 예산 대비 실제 구축 단계 기능 40% 증가 | 요구사항 불명확 상태에서 보수적 간이법 적용 및 요구사항 누락 | 과업심의위원회 의무화 및 요구사항 상세화에 따른 단계별 FP 재산정 계약 | 추가 과업에 대한 정당한 대가 보장 |
| 단순 그리드 조회를 통계 연산 외부출력(EO)으로 오분류해 감사 적발 | 기능점수 산정 원칙 이해 부족 및 수기 엑셀 계산 오류 | 한국소프트웨어산업협회(KOSA) 공인 FP 검증 도구 도입 및 기능정의서 교차 검증 | 기능점수 산정 객관성 및 적법성 확보 |

## 이렇게 출제된다
- 제132회 4교시 5번: "소프트웨어개발에 필요한 규모 산정 방식종류와 특징을 비교 설명하고, 공공 소프트웨어 사업 규모 산정 방식의 현실적 개선 방안에 대하여 설명하시오." → 요구 포인트: 기능점수·COCOMO·LOC 비교 + 공공 SW 사업 대가산정 가이드의 문제점 및 현실적 개선책(과업심의위, 적기발주)
- 제126회 2교시 1번: "소프트웨어 비용 산정방법에 대하여 설명하고, 각각의 장단점을 비교하시오" → 요구 포인트: 하향식(전문가, 델파이) vs 상향식(LOC, COCOMO, FP) 비교표

## 내 의견
- [요구사항 모호성을 개발사에게 전가하는 공공 발주 관행] 기획 단계에서 부정확하게 책정한 간이 FP 예산을 불변의 계약 금액으로 묶어두고, 개발 단계에서 쏟아지는 현업 추가 요구를 "공공 사업이니까 그냥 해달라"고 압박하는 구조적 모순 심각 → 나라면: 소프트웨어진흥법 제50조에 따른 과업심의위원회를 정례화하고, 분석·설계 종료 시점에 확정된 정규 FP를 기준으로 계약 금액을 사후 정산(True-up)하는 유연 계약제 도입
