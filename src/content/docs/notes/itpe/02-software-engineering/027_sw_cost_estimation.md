## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 공공 SW·거버넌스 → **SW 규모·비용 산정**

## 30초 인출

- 본질: 소프트웨어 개발 프로젝트의 공수, 개발 기간, 투입 예산을 합리적으로 예측하여 예산 왜곡과 사업 부실을 방지하는 정량적 엔지니어링 측정 체계
- 메커니즘: 요구사항 및 기능 범위 확정 → 정량적 규모 측정(LOC, FP) 및 생산성·비용동인 결합(COCOMO) → 직접인건비·제경비·기술료 합산 개발비 도출
- 통찰: 사업 초기 불명확한 요구사항으로 인한 단일값 추정 오류를 방지하기 위해 단계별 재산정(Re-estimation) 절차와 공식 과업심의위원회 변경 관리 연계 필수

<details>
<summary>핵심 용어</summary>

- **Function Point (기능점수, FP)** : 사용자 관점의 논리적 기능을 데이터 기능(ILF, EIF)과 트랜잭션 기능(EI, EO, EQ)으로 정량화하는 ISO 표준 규모 측정 기법
- **LOC(Lines of Code)** : 원시 소스코드 라인 수를 기준으로 작업량을 측정하는 직관적이고 전통적인 비용 산정 기법
- **COCOMO (Constructive Cost Model)** : Boehm이 제안한 모델로 KLOC 규모와 개발 유형(Organic, Semi-detached, Embedded) 및 비용동인(Cost Drivers)을 결합한 수학적 추정 모델
- **COCOMO II** : 현대의 객체지향, 컴포넌트 재사용(RAD) 환경을 반영하여 Application Composition, Early Design, Post-Architecture 3단계 모델로 확장한 체계
- **SW사업 대가산정 가이드** : 공공 및 민간 SW 사업의 기획, 구현, 운영 단계별 표준 대가 산정 기준을 규정한 한국소프트웨어산업협회(KOSA) 가이드라인

</details>

## 2~4교시 25점 답안

## Ⅰ. SW 규모·비용 산정의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 개발에 소요되는 기능 규모, 투입 노력(Man-Month), 일정, 소요 예산을 정량적 공학 모델과 경험 데이터를 바탕으로 합리적으로 예측하는 활동 |
| 목적 | 적정 사업 예산 확보, 공정 일정 계획 수립, 과업 변경 시 객관적 대가 조정 근거 확보 및 부실 개발 방지 |

## Ⅱ. SW 규모·비용 산정의 핵심 특징

| 특징 | 의미 |
|---|---|
| 불확실성의 점진적 축소 | 프로젝트 초기 '불확실성의 원추(Cone of Uncertainty)' 현상을 감안하여 단계별 재산정 수행 |
| 객관적 측정 지표 활용 | 구현 기술에 독립적인 기능점수(FP) 또는 통계적 이력 데이터 기반의 알고리즘 모델 적용 |
| 복합 보정 계수 반영 | 시스템 복잡도, 연계 인터페이스, 성능 요구수준 등 사업 환경 특성을 보정치로 가산 |
| 법제도적 준거성 유지 | 공공 SW 사업의 경우 소프트웨어 진흥법 및 SW사업 대가산정 가이드 규격 준수 필수 |

## Ⅲ. SW 규모 및 비용 산정 체계·프로세스

### 비용 산정 생명주기 및 대가 도출 메커니즘

```text
[요구사항 정의 (RFP/SRS)]
       │
       ▼
[규모 산정 기법 선정] ──────────┬────────────────────────┐
       │ (사용자 관점 논리 기능)  │ (소스코드 라인 예측)    │ (알고리즘 기반)
       ▼                          ▼                        ▼
[기능점수(FP) 분석]          [LOC 산정]               [COCOMO / COCOMO II]
 ├─ 데이터 기능 (ILF, EIF)    ├─ 낙관치, 비관치, 기대치 ├─ 규모(KLOC) 산정
 └─ 트랜잭션 (EI, EO, EQ)     └─ M/M = LOC / 월평균생산성 ├─ 17개 비용동인 보정
       │                          │                        │
       ▼                          ▼                        ▼
[소프트웨어 기능 규모 (FP/LOC)] ──┴────────────────────────┘
       │
       ▼
[공공 SW 대가기준 적용 산식]
  ┌────────────────────────────────────────────────────────┐
  │ 개발원가 = 기능점수(FP) × 기능당 단가 × 보정계수      │
  │           (규모·연계·성능·품질·다국어 지원 보정)       │
  │ 사업대가 = 개발원가 + 이윤(최대 25%) + 직접경비        │
  └────────────────────────────────────────────────────────┘
       │
       ▼
[예산 편성 / 과업 계약 체결 / 변경 시 과업심의위원회 재산정]
```

### 기능점수(FP) 5대 기능 구성요소 분석

| 기능 분류 | 구성요소 | 판정 기준 및 데이터 경계 | 산정 가이드 |
|---|---|---|---|
| **데이터 기능 (Data Functions)** | **내부논리파일 (ILF)** | 대상 애플리케이션 경계 내에서 유지·관리되는 영속적 데이터 그룹 | 엔티티 종류, 관계형 DB 테이블군, RET/DET 기준 복잡도 산정 |
| 데이터 기능 (Data Functions) | **외부연계파일 (EIF)** | 타 시스템에서 유지되며 대상 시스템이 순수 참조만 하는 데이터 그룹 | 외부 기관 연계 테이블, 공통 마스터 참조군, RET/DET 산정 |
| **트랜잭션 기능 (Transaction Functions)** | **외부입력 (EI)** | 경계 외부에서 인입되어 ILF 데이터를 등록, 수정, 삭제하는 트랜잭션 | 화면 입력 폼, 파일 업로드, 배치 수신 등, FTR/DET 산정 |
| 트랜잭션 기능 (Transaction Functions) | **외부출력 (EO)** | 데이터를 가공, 계산, 파생하여 시스템 외부로 전달하는 트랜잭션 | 통계 리포트, 요약 조회, 차트 생성 등, FTR/DET 산정 |
| 트랜잭션 기능 (Transaction Functions) | **외부조회 (EQ)** | 단순 데이터 검색 및 검색 결과를 즉시 표출하는 트랜잭션 (무가공) | 단순 목록 조회, 상세 화면 조회 등, FTR/DET 산정 |

## Ⅳ. 주요 비용 산정 기법 간 비교

### LOC vs COCOMO vs 기능점수(FP) 비교

| 비교 항목 | 원시 코드 라인 수 (LOC) | 구조적 비용 모델 (COCOMO) | 기능점수 (Function Point) |
|---|---|---|---|
| **측정 관점** | 개발자 구현 코드 라인 수 | 소스코드 규모 + 환경 비용동인 | **사용자 관점의 논리적 기능 수** |
| **적용 시점** | 설계 후반부 및 구현 단계 | 시스템 아키텍처 수립 이후 | **기획, 제안, 요구분석 초기 단계부터 가능** |
| **언어 종속성** | 언어 및 개발 스타일 의존도 극심 | 언어별 LOC 변환 계수 필요 | **구현 언어 및 플랫폼과 완전 독립적** |
| **장점** | 계산이 직관적이고 측정이 용이 | 공수 공식에 의한 정량적 일정 산출 | 국제 표준(ISO/IEC 20926), 높은 객관성 |
| **단점** | 프로젝트 초기 산정 불가능 | 과거 통계 데이터 없이는 오차 발생 | 산정자의 주관 개입 가능, 숙련도 요구 |
| **주 활용 분야** | 소규모 프로젝트 및 레거시 측정 | 항공, 방산, 미션 크리티컬 시스템 | **공공 SW 사업, 엔터프라이즈 발주 예산** |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 사업 기획 초기 요구사항 불명확성으로 인한 FP 산정 오차 및 예산 왜곡 | 초기 단계는 간이법(평균 복잡도)을 적용하고 설계 완료 후 정규법으로 사후 정산 |
| 비기능 요구사항(성능, 보안성, 가용성)이 기능점수 측정 대상에서 배제되는 한계 | 공공 대가산정 가이드의 규모·품질 보정계수(최대 1.3배) 및 직접경비 항목 적극 반영 |
| 개발 진행 중 잦은 과업 변경 및 추가 요구로 인한 사업 부실화 위험 | 과업심의위원회를 통한 공식 계약 변경 절차를 거치고 추가 FP에 대한 추가 대가 청구 |

## Ⅵ. 제언

불확실성의 원추(Cone of Uncertainty) 극복을 위한 단계별 점진적 재산정 체계 및 데이터 기반 산정 자동화

### 소프트웨어 생명주기 단계별 점진적 재산정 체계

```text
[사업 기획 단계] ──→ 간이 기능점수법 / 유사 사업 실적 기반 추정 (오차범위 ±50%)
       ↓
[요구분석 완료] ──→ 유스케이스 기반 정밀 기능점수(FP) 도출 (오차범위 ±25%)
       ↓
[아키텍처 설계] ──→ 컴포넌트/테이블 확정 및 정규 FP 재산정 (오차범위 ±10%)
       ↓
[과업 범위 변동 시] ─→ 과업심의위원회 개최 및 증감 FP 확정 → 계약 변경 완료
```

### AI 기반 코드 및 요구사항 자동 규모 산정 파이프라인

```text
[요구사항 명세서 (SRS)]
       ↓
[NLP 기반 요구사항 분석 파이프라인]
  ├─ 사용자 스토리 및 인수 조건 자동 파싱
  ├─ ILF / EIF / EI / EO / EQ 후보군 자동 분류
  └─ 과거 유사 프로젝트 실적 데이터 매핑
       ↓
[초기 자동 기능점수(FP) 산출 보고서 생성]
       ↓
[전문 산정인(CFPS) 교차 검증 및 최종 보정]
```

### 선택 근거: 전통적 1회성 계약 산정과 점진적 재산정 거버넌스 비교

| 구분 | 전통적 고정비 1회성 산정 | 제언: 점진적 재산정 거버넌스 |
|---|---|---|
| 산정 횟수 | 발주 시점 1회 고정 산정 | 기획, 분석 완료, 설계 완료 시점 3회 점진 산정 |
| 리스크 귀속 | 요구사항 변동 시 개발사 독박 부담 | 정량적 증감 데이터 기반 발주처-수행사 분담 |
| 과업 통제 | 구두 요구에 의한 과업 스코프 크립 빈발 | 과업심의위원회 연계를 통한 투명한 계약 변경 |
