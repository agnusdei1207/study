## Ⅰ. 소프트웨어 규모 및 비용 산정의 개요

- 개념 : 소프트웨어 개발 프로젝트의 계획 단계에서 요구사항을 분석하여 개발할 소프트웨어의 크기(규모)를 정량적으로 측정하고, 이를 바탕으로 필요한 **공수** (M/M, Man-Month)와 사업 예산을 과학적으로 예측하는 공학적 프로세스.
- 배경 및 필요성 : 불합리한 예산 책정으로 인한 부실 개발 방지, 적정 대가 산정을 통한 개발자 권익 보호, 국가 공공 SW(Software) 사업 발주의 객관적 계약 기준 마련.
- 주요 3대 기법 : **소스코드 라인 수 기반** (LOC, Lines of Code), **수학적 산정 모델** (COCOMO, Constructive Cost Model), **사용자 관점 기능 기반** (기능점수, FP(Function Point)).

## Ⅱ. 비용 산정 기법 발전 체계 및 COCOMO 모델

```text
   [ 하향식 기법 ] ──── 전문가 판단, 델파이(Delphi) 기법
          │
   [ 상향식 기법 ] ──── LOC(Lines of Code) 기반 단계별 노력 계산
          │
   [ 수학적 모델 ] ──── COCOMO (Basic -> Intermediate -> Detailed -> COCOMO II)
          │
   [ 기능 기반 규격 ] ── 기능점수(FP) 모델 (ISO/IEC 20926) -> 공공 SW 대가 기준
```

- **COCOMO (Constructive Cost Model)** : **보엠** (Boehm)이 제안한 모델로 규모(KLOC)에 기반하여 수식 $Effort = A \times (KLOC)^B \times EAF$ 로 공수 산정.
  - **조직형 (Organic)** : 5만 라인(50 KDSI) 이하의 소규모 일상 업무용 SW ($A=2.4, B=1.05$).
  - **반분리형 (Semi-detached)** : 30만 라인 이하의 중간 규모 트랜잭션/컴파일러 시스템 ($A=3.0, B=1.12$).
  - **임베디드형 (Embedded)** : 엄격한 하드웨어 제약과 신뢰성이 요구되는 초대형 복합 시스템 ($A=3.6, B=1.20$).

## Ⅲ. 주요 SW 규모·비용 산정 기법 비교

| 비교 항목 | LOC (코드 라인 수) | COCOMO 모델 | 기능점수 (FP, Function Point) |
|---|---|---|---|
| 산정 기준 | 소스코드의 물리적 라인 수 | 소스코드 라인 수 + **노력 승수** (EAF) | 사용자 관점의 논리적 기능 수 |
| 측정 시점 | 코딩 이후 또는 상세 설계 후반 | 구현 단계 근접 시점 | 기획 및 요구사항 분석 초기 단계 |
| 언어 의존성 | 프로그래밍 언어에 극도로 의존 | 언어에 의존적 (**KLOC** 기준) | 언어, 개발 도구, 기술 스택과 무관 |
| 장단점 | 단순하고 직관적이나 초기 예측 불가 | 정량적이나 현대 고수준 언어 반영 한계 | 객관적이고 표준화됨, 분석가 역량 의존 |
| 국내 표준 | 사장 추세 | 학술적/참고용 활용 | **공공 소프트웨어 사업 대가산정 가이드** 공식 표준 |

## Ⅳ. SW 규모 및 비용 산정의 주요 한계점 및 해결 방안

- 사업 초기 요구사항 불확실성에 따른 기능점수(FP) 왜곡 :
  - 한계점 : 기획 및 제안 단계에서는 데이터 모델(테이블)과 트랜잭션 기능(화면/배치)이 구체화되지 않아 간이법에 의존하므로 실제 투입 공수와 심각한 견적 오차 발생.
  - 해결 방안 : 사업 초기에는 간이 기능점수법과 유사 프로젝트 모수 추정(Parametric Estimation)을 병행하고, 분석·설계 완료 후 상세 기능점수법으로 재산정(True-up)하는 단계별 정산 체계 제도화.
- 클라우드 네이티브 및 AI(Artificial Intelligence) 기반 개발 생산성 미반영 :
  - 한계점 : 전통적 기능점수(FP) 및 LOC 모델은 레거시 온프레미스 Java/C 개발 환경에 맞춰져 있어 클라우드 PaaS/SaaS 활용, 노코드 도구, 생성형 AI 코딩 도입에 따른 생산성 격차 미반영.
  - 해결 방안 : SW 대가산정 가이드라인 내 신기술 보정 계수를 적극 신설·반영하고, 애자일 프로젝트의 경우 팀 벨로시티 기반 스토리 포인트 원가 추정 모델을 상호 보완적으로 활용.
- 산정자의 주관성 개입 및 복잡도 판정의 비일관성 :
  - 한계점 : 데이터 요소수(DET, Data Element Type), 레코드 요소수(RET, Record Element Type), 참조 파일수(FTR, File Type Referenced) 식별 기준에 대한 산정자의 숙련도 차이로 인해 동일한 요구사항에서도 발주자와 수주자 간 견적 불일치 분쟁 빈발.
  - 해결 방안 : 공인 기능점수 전문가(CFPS) 참여 의무화, 요구사항 명세서 및 DB(Database) 스키마 기반의 자동화된 기능점수 측정 도구 도입, 내부 산정 기준 표준 매뉴얼 확립.

## Ⅴ. 공공 SW 및 현대 클라우드 환경에서의 기술사적 제언

- 간이 기능점수법과 정규 기능점수법의 단계별 적용 : 사업 기획 및 예산 수립 단계에서는 평균 복잡도를 활용하는 간이법을 적용하고, 상세 분석/설계 완료 후에는 데이터/트랜잭션 요소(RET, DET, FTR)를 정밀 측정하는 정규법으로 사후 정산 체계 구축.
- 클라우드 네이티브 및 AI 기반 개발 환경의 생산성 반영 : 기존 FP 대가 체계는 레거시 코딩 생산성을 전제하므로, 클라우드 SaaS 도입, 로우코드(LCNC), 생성형 AI 도구 활용에 따른 공수 절감 효과와 구독형 라이선스 비용을 반영할 수 있도록 원가 산정 체계의 현대화 필요.
