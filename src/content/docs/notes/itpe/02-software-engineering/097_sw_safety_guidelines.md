## 연관 키워드

- SW(Software)안전 확보 지침, 소프트웨어진흥법, 위험원(Hazard) 분석, SW안전 등급
- FTA(Fault Tree Analysis), FMEA(Failure Mode and Effects Analysis), STPA(System-Theoretic Process Analysis), 페일 세이프(Fail-Safe), 기능안전

## Ⅰ. SW안전 및 SW안전 확보 지침의 개요

- 핵심 요약 : 소프트웨어 결함·오작동으로부터 생명·신체·공공 재산을 보호하기 위한 법정 공학 관리 지침.
- 개념 : SW(Software)의 오작동, 결함 또는 사이버 공격으로 인해 발생할 수 있는 사고로부터 사람의 생명, 신체 또는 공공의 안전과 재산을 보호하기 위해 과학기술정보통신부가 소프트웨어진흥법에 근거하여 제정한 법정 공학적 관리 지침.
- 법적 근거 : 소프트웨어진흥법(소프트웨어 안전 확보 관련 조항), 과학기술정보통신부 고시 소프트웨어안전 확보 지침.
- 적용 대상 : 국민의 생명·신체·재산과 직결되는 공공 인프라, 교통, 에너지, 의료, 정보시스템 등 국가 중요 소프트웨어 시스템.

## Ⅱ. SW안전 확보 지침의 특징

- 핵심 요약 : 생명주기 전 단계 관리와 등급별 차등 규제, 위험원 분석 기반 안전 요구사항 도출.

1. SW안전 등급 체계 : 사고 발생 시 인명 피해 규모, 경제적 손실, 사회적 파급도의 종합 평가에 따른 등급(예: 1~4등급) 부여와 등급별 차등 안전 관리 활동 강제.
2. 위험원 분석 : FTA(Fault Tree Analysis), FMEA(Failure Mode and Effects Analysis), STPA(System-Theoretic Process Analysis) 적용을 통한 시스템 오작동 유발 잠재 위험원의 사전 도출과 안전 조치 요구사항 수립.
3. 안전 아키텍처 원칙 : 페일 세이프(Fail-Safe), 결함 허용(Fault-Tolerant), 비상 정지 메커니즘의 소프트웨어 아키텍처 구현.
4. 요구분석 단계 SRS(Software Requirements Specification)의 안전항목 반영.
5. 운영 단계 안전 상태 모니터링과 사고 보고·조치 체계 운영.

## Ⅲ. SW안전 생명주기 관리의 구조 (흐름)

- 핵심 요약 : 기획부터 운영·유지보수까지 안전 활동이 이어지는 생명주기 관리 흐름.
- SW안전 생명주기 관리 및 위험원 분석 흐름.

```text
[ 1. 기획 단계 ]
 - SW안전 등급 분류, 안전관리 계획 수립
   │
   ▼
[ 2. 요구분석 단계 ]
 - 위험원(Hazard) 분석, 안전 요구사항 명세
 - SRS에 안전항목 반영
   │
   ▼
[ 3. 설계 단계 ]
 - 안전 아키텍처, Fail-Safe/다중화 설계
   │
   ▼
[ 4. 구현/시험 단계 ]
 - 안전성 시험, 결함 주입 시험, 정적/동적 검증
   │
   ▼
[ 5. 운영/유지보수 단계 ]
 - 안전 상태 모니터링, 변경 영향도 분석
 - 사고 보고 및 조치
```

- 기획·요구분석 단계 : SW안전 등급 분류와 안전관리 계획 수립, 위험원 분석 기반 안전 요구사항 명세화.
- 설계·구현 시험 단계 : 안전 아키텍처와 페일 세이프·다중화 설계, 안전성 시험과 결함 주입 시험, 정적·동적 검증 수행.
- 운영·유지보수 단계 : 안전 상태 모니터링과 변경 영향도 분석, 사고 보고 및 조치 체계 운영.

## Ⅳ. 일반 소프트웨어 품질과 SW안전의 비교

- 핵심 요약 : 기능 정확성 추구와 인명·재산 피해 방지의 관심사 차이.
- 두 관점의 실패 개념 대조.

```text
[ 일반 품질(Quality) ]              [ SW 안전(Safety) ]
 기능 오류·화면 오류·계산 착오        오작동·사이버 공격
        ↓                                  ↓
 업무 불편·비즈니스 손실             인명 상해·시설 파괴·인프라 마비
 (ISO/IEC 25010 품질 모델)          (SW안전 지침, IEC 61508, ISO 26262)
```

| 비교 항목 | 일반 소프트웨어 품질(Quality) | 소프트웨어 안전(Safety) |
|---|---|---|
| 핵심 관심사 | 시스템이 요구된 비즈니스 기능을 올바르고 빠르게 수행하는가 | 소프트웨어 오작동으로 인해 인명 피해나 대형 사고가 발생하는가 |
| 실패의 정의 | 기능 미동작, 화면 오류, 비즈니스 계산 착오 | 인명 상해, 사망, 물리적 시설 파괴, 국가적 인프라 마비 |
| 표준 규격 | ISO(International Organization for Standardization)/IEC(International Electrotechnical Commission) 25010(품질 모델), ISO/IEC 12207 | 과기정통부 SW안전 확보 지침, IEC 61508, ISO 26262 |
| 주요 분석 기법 | 유스케이스 분석, 경계값/동등분할 블랙박스 테스팅 | 결함수 분석(FTA), 고장모드 분석(FMEA), STPA 위험원 분석 |
| 설계 접근법 | 사용성 최적화, 성능 최적화, 기능 확장성 중심 | 방어적 프로그래밍, 다중화(Redundancy), 페일 세이프 중심 |

## Ⅴ. SW안전 확보 지침의 장점과 한계

- 핵심 요약 : 법적 안전 관리 표준화의 장점, 형식적 점검·도메인 괴리·레거시 소급의 한계.
- 장점
  1. 국가 중요 소프트웨어의 법정 안전 관리 기준 통일.
  2. 등급 기반 차등 관리를 통한 합리적 안전 자원 배분.
  3. 생명주기 전 단계 안전 활동의 추적성 확보.
- 한계점 1 : 체크리스트 위주의 형식적 점검으로 인한 실질적 위험원 식별 한계
  - 한계점 : 규정 준수(Compliance) 증빙 서류 작성 편중, 소프트웨어 내부 복잡 상호작용과 런타임 타이밍 결함 누락.
  - 해결 방안 : 시스템 이론 프로세스 분석(STPA), 결함수 분석(FTA) 기반 위험원 추적성 모델 수립과 실질적 동적 장애 주입 시험 의무화.
- 한계점 2 : 도메인 특수성과 범용 공공 지침 간의 규격 괴리
  - 한계점 : 철도, 의료, 원자력 등 특수 산업 표준(IEC(International Electrotechnical Commission) 62304, IEC 62278 등)과 범용 공공 SW 안전 지침 간 용어·요구사항 불일치, 현장 혼선.
  - 해결 방안 : 공공 가이드라인의 산업별 특화 매핑 프로파일(Profile) 제공, 프로젝트 위험도(Criticality) 등급별 맞춤형 테일러링 기준 명시.
- 한계점 3 : 레거시 시스템 소급 적용 시 막대한 수정 비용 및 리스크
  - 한계점 : 기 구축 레거시 시스템의 안전 설계(이중화, 모니터링 등) 사후 적용 시 아키텍처 재설계 수준의 예산과 리스크 수반.
  - 해결 방안 : 외부 안전 래퍼(Safety Wrapper) 패턴과 독립적 하드웨어 안전 감시 장치(Watchdog, Safety PLC(Programmable Logic Controller))의 결합, 비침습적 보호 계층 우선 구축.

## Ⅵ. 공공 및 주요 인프라 안전 확보를 위한 기술사적 제언

- 핵심 요약 : 발주 단계 안전 요구사항 명시와 전문 감리·SIL 검증 체계 강화.
- 발주 전 위험원 분석 및 제안요청서 RFP(Request for Proposal) 안전 요구사항 명시 : 사업 기획 단계 SW안전 등급의 공식 평가, 제안요청서의 안전 아키텍처 구현 요건과 독립적 제3자 V&V(Verification and Validation) 의무화, 적정 사업 예산 반영.
- SW안전 전문 감리 체계 및 안전 무결성 SIL(Safety Integrity Level) 검증 강화 : 정보시스템 감리 시 소프트웨어 안전 전담 감리원 배정, MISRA-C/C++ 안전 코딩 표준 준수, MC/DC(Modified Condition/Decision Coverage) 커버리지 달성률과 비상 정지 로직 유효성의 실증적 검증 제도 정착.

## Ⅶ. 결론

- 핵심 요약 : SW안전 확보 지침은 인명·공공 안전 보호를 위한 국가 차원의 공학 관리 기준.
- 요약 : 등급 분류, 위험원 분석, 안전 아키텍처, 생명주기 관리가 지침의 핵심 골격.
- 시사점 : 형식적 컴플라이언스에서 실질적 위험원 검증으로의 전환과 도메인 맞춤 적용이 지침 실효성 확보의 과제.
