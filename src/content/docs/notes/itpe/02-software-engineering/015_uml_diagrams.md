## 연관 키워드

- UML, 구조(정적) 다이어그램, 행위(동적) 다이어그램
- 클래스·시퀀스·상태 머신·활동·유스케이스 다이어그램

## Ⅰ. UML의 개요

- 핵심 요약 : UML은 객체지향 시스템의 구조와 행위를 표준 표기법으로 명세·의사소통하는 모델링 언어.
- 개념 : 시스템의 구조 요소와 동작을 표준화된 다이어그램 체계로 표현하는 시각적 모델링 언어(**UML**, Unified Modeling Language), OMG(Object Management Group) 표준.
- 배경 및 필요성 : 방법론마다 상이한 표기로 인한 설계 공유 비용 → 단일 표기 표준의 필요.
- 주요 목적 : 분석·설계·검증·문서화 전 과정의 일관된 소통 기반 확보.

## Ⅱ. UML 다이어그램의 특징 및 장점

- 핵심 요약 : 정적 구조와 동적 행위의 관점 분리가 이해관계자별 소통과 설계 검증의 효율 제공.

1. 관점 분리 : **구조 다이어그램**은 정적 구성과 관계, **행위 다이어그램**은 흐름·상태·상호작용 담당 → 목적에 맞는 모델 선택 가능.
2. 표준 표기 : 공식 명세로 기호·의미 고정 → 도구·조직 간 모델 호환성 확보.
3. 다중 관점 모델링 : 동일 시스템을 여러 관점의 모델로 분할 → 이해관계자별 질문에 대응하는 소통 수단.
4. 도구 자동화 연계 : 모델 기반 코드 생성·문서화 → 설계와 구현 산출물의 정합성 유지 보조.

## Ⅲ. UML 다이어그램의 구조 (흐름)

- 핵심 요약 : 구조 7종·행위 7종으로 분류되며 해결하려는 질문에 따라 관점과 다이어그램 선택.
- **클래스 다이어그램** : 클래스와 관계로 정적 구조 표현.
- **시퀀스 다이어그램** : 객체 간 메시지의 시간 순서 표현.
- **상태 머신 다이어그램** : 객체의 상태와 전이 표현.
- **활동 다이어그램** : 업무 흐름과 병렬·분기 표현.
- **유스케이스 다이어그램** : 액터와 시스템 기능의 관계 표현.

```text
[ UML 다이어그램 분류 ]

구조(정적) 다이어그램
   1. 클래스·객체
   2. 컴포넌트·패키지
   3. 배치·복합구조·프로파일

행위(동적) 다이어그램
   1. 유스케이스·활동
   2. 상태 머신
   3. 시퀀스·통신·타이밍·상호작용 개요
```

```text
[ 관점 선택 흐름 ]

무엇으로 구성되는가?
   → 구조 다이어그램
어떻게 동작하는가?
   → 행위 다이어그램
순서·상태 변화가 중요한가?
   → 시퀀스·상태 머신
```

- 분류 기준 : UML 2.5 명세 기준 14종의 다이어그램을 구조 7종·행위 7종으로 구분.

## Ⅳ. 구조(정적) 다이어그램과 행위(동적) 다이어그램의 비교

- 핵심 요약 : 구조 다이어그램이 한 시점의 구성과 관계를, 행위 다이어그램이 시간 흐름의 동작을 담당.

| 비교 축 | 구조(정적) 다이어그램 | 행위(동적) 다이어그램 |
| --- | --- | --- |
| 표현 대상 | 구성 요소·관계·배치 | 시나리오·상태 전이·메시지 흐름 |
| 시간 축 | 없음(한 시점 구성) | 있음(시간에 따른 변화) |
| 대표 종류 | 클래스·컴포넌트·배치 | 유스케이스·활동·상태 머신·시퀀스 |
| 주요 활용 | 모듈 경계·인터페이스·배포 설계 | 업무 흐름·예외·수명주기 검토 |

## Ⅴ. UML 활용의 한계와 방안

- 핵심 요약 : 표기 부담·모델 노후화·과잉 상세화를 목적별 최소 모델링과 동기화 체계로 완화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 표기 학습 부담 | 다양한 표기의 진입장벽 | 목적·독자별 최소 표기 사용 | 모델링 소요 시간 |
| 모델·코드 불일치 | 갱신 소홀 → 문서 신뢰 하락 | 코드 생성·주기적 동기화 | 불일치 발견 건수 |
| 과잉 상세화 | 가독성 저하·유지 비용 | 추상화 수준·독자 사전 정의 | 다이어그램당 요소 수 |

## Ⅵ. UML 적용에 대한 제언

- 핵심 요약 : 모델을 관리 대상 산출물로 편성하고 갱신 책임과 검토 절차의 제도화 필요.

1. 아키텍처 조직은 다이어그램별 독자·목적·갱신 책임자를 표준으로 지정.
2. 개발 조직은 Diagrams as Code 방식으로 모델을 저장소에서 코드와 함께 버전 관리.
3. 품질 조직은 설계 리뷰 항목에 모델 최신성·정합성 검토 포함.

## Ⅶ. 결론

- 핵심 요약 : UML은 시스템 전체를 그리는 목적이 아니라 구조·행위의 명료한 공유 언어.
- 설계 질문에 답하는 최소 범위의 모델 유지가 활용 효과의 전제 조건.
