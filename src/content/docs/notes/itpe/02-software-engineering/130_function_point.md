## 답안 골격
```text
[기능점수(Function Point)] ◀━━ 머리: Ⅶ 내 의견 (정규법 기반 기능점수 산정 자동화 도구 도입과 과업 변경에 따른 가변 계약 정착)
 ┃
 ┣━ Ⅰ 개요 ───── 언어와 플랫폼에 종속된 LOC 산정 왜곡 한계 → 사용자 관점에서 제공되는 비즈니스 기능의 양적 크기 정량화
 ┣━ Ⅱ 특징 ───── 기술 독립적(Language Independent) · 사용자 관점 논리적 기능 측정 · 공공 SW 사업 대가산정 공식 기준
 ┣━ Ⅲ 구조 ───── 데이터 기능(ILF, EIF) + 트랜잭션 기능(EI, EO, EQ) + 14대 일반 시스템 특성(GSC, 보정계수)
 ┣━ Ⅳ 흐름 ───── 측정 범위 식별 → 데이터/트랜잭션 기능 식별 → RET/DET/FTR 복잡도 매트릭스 적용 → 미조정 FP 산출 → 보정계수 적용 → 최종 FP
 ┣━ Ⅴ 비교 ───── 정규법(Detailed FP, 상세 산정) vs 간이법(Average Weight FP, 평균 가중치 산정)
 ┗━ Ⅵ 실무 ───── 기획 단계 요구사항 불명확성 / 복잡도 주관성 개입 / 과업 추가에 따른 변경 계약 반영
```
- 필수 키워드: 기능점수 · IFPUG · 데이터 기능(ILF, EIF) · 트랜잭션 기능(EI, EO, EQ) · RET/DET/FTR · 간이법 · 정규법 · 보정계수
- 기출: 119회 1교시 `기능점수(FP)의 5가지 기능 유형` → Ⅲ, 105회 2교시 `기능점수 산정 절차 및 정규법과 간이법의 비교` → Ⅳ·Ⅴ

## 한 줄 본질
- 작성된 소스코드 라인 수(LOC)에 의존하여 언어 간 생산성 격차와 프로그래밍 스타일에 따라 크기가 왜곡되는 병목 → 소프트웨어가 사용자에게 제공하는 논리적 데이터 저장 기능과 트랜잭션 처리 기능을 식별하여 표준 가중치로 환산하는 기능적 규모 측정 표준 / 세부 명세 부재 시 산정 불가

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  기능점수(Function Point) 5대 기능 유형 분류            |
+-------------------------------------------------------------------------+
|                                                                         |
|                          [ 사용자 요구사항 ]                            |
|                                   │                                     |
|         ┌─────────────────────────┴─────────────────────────┐           |
|         v                                                   v           |
|  [ 데이터 기능 (Data Functions) ]             [ 트랜잭션 기능 (Transactions) ]|
|  데이터 저장 및 참조 관점                     데이터 입력, 출력, 조회 관점     |
|                                                                         |
|  - ILF (내부논리파일) :                       - EI (외부입력) :                 |
|    애플리케이션 경계 내부에서 유지되는 파일     DB 데이터 등록, 수정, 삭제      |
|    (복잡도: RET 레코드 유형, DET 데이터 요소)   (복잡도: FTR 참조 파일, DET 요소)|
|                                                                         |
|  - EIF (외부연계파일) :                       - EO (외부출력) :                 |
|    타 시스템에서 관리되나 단순 참조하는 파일    수학적 계산/파생 데이터를 포함한 출력|
|    (복잡도: RET 레코드 유형, DET 데이터 요소) - EQ (외부조회) :                 |
|                                                 단순 검색 및 데이터 디스플레이   |
|                                                                         |

```

## 핵심 용어
- ILF(Internal Logical File): 측정 대상 애플리케이션 경계 내부에서 비즈니스 로직에 의해 지속적으로 등록·수정·삭제되는 논리적 데이터 그룹
- DET(Data Element Type): 사용자가 인식할 수 있는 고유하고 반복되지 않는 필드(컬럼) 단위의 데이터 항목

## 핵심 통찰
- 기능점수는 화면 수나 테이블 수가 아니라 "사용자가 인식 가능한 논리적 비즈니스 트랜잭션"을 세는 것이므로, 개발자가 만든 내부 임시 테이블이나 캐시 테이블은 ILF에서 철저히 제외되어야 함
- 간이법은 기획 및 예산 수립 단계에서 각 기능의 평균 복잡도 가중치(ILF=7.5, EIF=5.4, EI=4.6, EO=5.2, EQ=3.9)를 일괄 적용하므로 빠르게 산정할 수 있으나, 시스템의 실질적 알고리즘 난이도를 반영하지 못함
- EO(외부출력)와 EQ(외부조회)의 핵심 차이는 "파생 데이터 계산 로직(통계 집계, 세금 계산 등)이 포함되는가"에 있으며, 단순 검색 조회를 EO로 잘못 산정하면 기능점수가 부풀려져 감사 대상이 됨

## 이웃 토픽과 구분
- 정규법 vs 간이법: 정규법 = 분석/설계 완료 후 RET/DET/FTR을 전수 계수하여 복잡도 매트릭스 적용(정밀함) / 간이법 = 사업 기획/발주 시 기능 개수에 평균 가중치를 곱해 신속 추정(예산 편성용)

## 문제·원인·대책
- 적용 상황: 차세대 공공 행정망 정보시스템 감리 및 정산
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 정기 감사 시 기능점수가 20% 과다 산정되었다는 지적을 받고 대가 삭감 처분 | 코드성 테이블 및 임시 백업 테이블을 독립된 ILF로 중복 계수한 오류 | 데이터 모델 정규화 기준 검증 및 공통 코드 테이블은 단일 ILF로 통합 산정 | 산정 기준 정합성 확보 및 감사 리스크 제거 |
| 프로젝트 진행 중 발주자의 비기능 요구사항(보안, 가용성)이 폭증했으나 대가 미인정 | 기능점수는 비기능적 품질 속성을 규모에 직접 반영하기 어려운 구조적 한계 | 소프트웨어 사업 대가산정 가이드의 보정계수(다중 사이트, 성능 요구 수준 등) 정량 반영 | 비기능 요구사항에 대한 정당한 개발 원가 보상 |

## 이렇게 출제된다
- 제119회 1교시: "소프트웨어 기능점수(Function Point)의 5가지 기능 유형과 복잡도 결정 요인을 설명하시오." → 요구 포인트: 데이터 기능(ILF, EIF) + 트랜잭션 기능(EI, EO, EQ) + 복잡도 인자(DET, RET, FTR)
- 제105회 2교시: "기능점수 산정 방식 중 정규법과 간이법의 절차와 특징을 비교하고, 공공사업 적용 시 유의사항을 설명하시오." → 요구 포인트: 산정 절차 7단계 + 정규법 vs 간이법 비교표 + 단계별 적용 방안

## 내 의견
- [기획 단계 간이법 예산과 구축 단계 요구사항 간의 구조적 충돌] 기획 단계의 엉성한 제안요청서로 간이법 산정한 예산이 고정된 상태에서 구축 단계의 실제 기능 요구사항이 폭증하여 수주사가 결함을 떠안는 구조 만연 → 나라면: 공공 SW 사업에 "설계·구축 분할 발주" 제도를 정착시키고, 기본설계 완료 시점에 산출된 정규 기능점수 결과에 따라 총사업비를 $\pm 10\%$ 범위 내에서 유연하게 증액·정산하는 변경 계약 거버넌스 확립
