## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 개발·운영 → 기능점수(Function Point)

## 지식 위치

소프트웨어공학 > 프로젝트 관리·비용 산정 > 기능 규모 측정

## 30초 인출

- 본질: 사용자의 관점에서 소프트웨어가 제공하는 논리적 기능의 크기를 측정하여 비용 산정 및 생산성 평가의 기준으로 삼는 국제 표준 소프트웨어 규모 측정 기법
- 메커니즘: 측정 범위 및 애플리케이션 경계 설정 → 데이터 기능(ILF, EIF) 및 트랜잭션 기능(EI, EO, EQ) 식별 → 복잡도(DET/RET/FTR) 평가 및 미조정 기능점수(UFP) 산출 → 보정계수 반영을 통한 최종 기능점수 산출
- 통찰: 시스템 개발 초기 불명확한 요구사항으로 인한 물리적 테이블-논리 파일 간 괴리를 방지하기 위해 기획 단계의 간이법과 설계 이후의 정규법을 분리 적용하는 단계별 규모 산정 거버넌스 확립 필요

<details>
<summary>핵심 용어</summary>

- **ILF (Internal Logical File)** : 대상 애플리케이션 내부에서 유지·관리되는 사용자 식별 가능 논리적 데이터 그룹
- **EIF (External Interface File)** : 타 시스템에 의해 유지되나 대상 애플리케이션 내부에서 참조 목적으로만 사용하는 논리적 데이터 그룹
- **EI (External Input)** : 애플리케이션 경계 외부에서 인입되어 내부 논리 파일(ILF)을 등록, 수정, 삭제하는 트랜잭션 기능
- **EO (External Output)** : 데이터 또는 제어 정보를 경계 외부로 보내는 트랜잭션으로, 계산 로직이나 파생 데이터 생성을 포함하는 기능
- **EQ (External Inquiry)** : 데이터 또는 제어 정보를 경계 외부로 보내는 단순 검색 및 조회 트랜잭션 (계산 로직 배제)
- **DET (Data Element Type)** : 사용자가 식별할 수 있는 고유하고 반복되지 않는 데이터 필드 항목
- **RET / FTR** : RET는 논리 파일 내의 서브 레코드 그룹, FTR은 트랜잭션 기능이 참조하거나 갱신하는 ILF/EIF 파일 수
</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 규모 산정 기법인 기능점수(Function Point)의 개념과 구성요소(데이터 기능, 트랜잭션 기능)를 설명하고, 정규법과 간이법의 절차적 차이 및 공공 SW 대가산정 시의 고려사항을 기술하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어의 물리적 코드 라인 수(LOC)가 아닌 사용자에게 제공되는 논리적 기능(데이터 관리 및 처리)을 정량적으로 계량화하는 국제 표준(ISO/IEC 14143) 기반 규모 산정 방식 |
| 목적 | 구현 기술/언어 독립적인 객관적 규모 측정, 합리적인 소프트웨어 개발 대가 산정, 프로젝트 예산 수립 및 공정별 생산성 분석 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 사용자 관점의 측정 | 하드웨어 환경이나 사용 언어와 무관하게 사용자가 요구하고 체감하는 비즈니스 기능 중심 계량 |
| 체계적인 기능 분류 | 시스템 내부/외부 데이터를 저장하는 데이터 기능과 데이터 처리 흐름을 다루는 트랜잭션 기능으로 이원화 |
| 객관적 복잡도 매트릭스 | 식별된 각 기능의 데이터 요소 수(DET), 레코드 유형 수(RET), 참조 파일 수(FTR)에 따라 복잡도(낮음/보통/높음) 차등 적용 |
| 생명주기 전반의 적용성 | 상세 설계 이전 기획/분석 단계(간이법)부터 설계/구현 완료 후 검증 단계(정규법)까지 유연하게 측정 가능 |

프로젝트 초기 비용 산정부터 종료 후 생산성 측정까지 일관된 척도를 제공하는 SW 대가산정의 핵심 표준으로 기능.

## Ⅲ. 체계·프로세스

```text
[1. 측정 범위 및 경계 설정]
  - 측정 대상 애플리케이션 및 타 시스템 간의 물리적/논리적 인터페이스 경계 확정
       │
       ▼
[2. 기능 식별 및 분류]
  ┌───────────────────────────────┬───────────────────────────────┐
  │         데이터 기능           │        트랜잭션 기능          │
  │  - 내부논리파일 (ILF)         │  - 외부입력 (EI)              │
  │  - 외부연계인터페이스 (EIF)   │  - 외부출력 (EO) / 외부조회(EQ)│
  └───────────────────────────────┴───────────────────────────────┘
       │
       ▼
[3. 복잡도 평가 및 미조정 FP(UFP) 산출]
  - 데이터 기능 복잡도 매트릭스 (RET × DET)
  - 트랜잭션 기능 복잡도 매트릭스 (FTR × DET)
  - UFP = Σ (기능 유형별 수량 × 복잡도 가중치)
       │
       ▼
[4. 보정계수 적용 및 최종 FP 산출]
  - 규모 보정, 애플리케이션 복잡도, 연계 복잡도 등 보정계수(VAF) 적용
  - 최종 FP = UFP × 보정계수 ──► 사업비(SW 개발 대가) 산출
```

경계 설정에서 출발하여 데이터/트랜잭션 기능 식별, 가중치 매트릭스 기반 UFP 도출 및 보정계수 반영을 통해 최종 대가를 확정하는 프로세스.

## Ⅳ. 종류·비교

| 기능 유형 | 분류 | 정의 | 복잡도 판정 기준 |
|---|---|---|---|
| **ILF (Internal Logical File)** | 데이터 기능 | 애플리케이션 내부에서 유지·관리되는 논리적 데이터 그룹 | RET(하위 레코드 수) × DET(데이터 필드 수) |
| **EIF (External Interface File)** | 데이터 기능 | 타 시스템에 의해 유지되며 해당 시스템은 오직 참조만 수행 | RET(하위 레코드 수) × DET(데이터 필드 수) |
| **EI (External Input)** | 트랜잭션 기능 | 외부 데이터를 입력받아 ILF를 등록, 수정, 삭제하는 기능 | FTR(참조 파일 수) × DET(입력 필드 수) |
| **EO (External Output)** | 트랜잭션 기능 | 계산식/파생 데이터를 생성하거나 외부 상태를 변경하여 출력 | FTR(참조 파일 수) × DET(출력 필드 수) |
| **EQ (External Inquiry)** | 트랜잭션 기능 | 계산 로직 없이 내부/외부 데이터를 단순 검색하여 표출 | FTR(참조 파일 수) × DET(조회 조건/결과 필드 수) |

### 기능점수 산정 방식 비교 (정규법 vs 간이법)

| 비교 항목 | 정규법 (Detailed Function Point) | 간이법 (Average Complexity) |
|---|---|---|
| **적용 시점** | 분석/설계 완료 이후 상세 스펙 가용 시점 | 사업 기획, 발주, 예산 수립 초기 단계 |
| **복잡도 산정** | 개별 기능마다 DET, RET, FTR을 실측하여 가중치 결정 | 기능 유형별 평균 가중치(ILF 7.5, EIF 5.4 등) 일괄 적용 |
| **정확도 및 공수** | 정확도 높음 / 많은 시간과 분석 노력 소요 | 신속한 규모 추정 가능 / 상세 분석 대비 편차 발생 가능 |
| **주요 용도** | 최종 검수, 사후 정산, 외주 개발 검증 | 예산 편성, 발주 금액 산정, 제안 견적서 작성 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 물리적 DB 테이블 수와 사용자 관점의 논리 파일(ILF) 간의 혼동으로 인한 왜곡 | 정규화된 물리 테이블이 아닌 업무 엔티티 및 비즈니스 데이터 단위를 기준으로 ILF 통합 식별 |
| 단순 조회(EQ)와 통계/집계 로직을 포함한 출력(EO)의 자의적 판별 및 분쟁 발생 | 계산식 유무, 파생 필드 존재 여부, 외부 시스템 제어 플래그 변경 여부를 명문화한 판별 가이드 적용 |
| 기획 단계 간이법으로 산정한 예산과 실제 상세 설계 후 정규법 간의 기능 규모 차이 발생 | 요구사항 변경 관리 프로세스를 수립하고 기준 범위를 초과하는 증감 발생 시 계약 변경 절차 제도화 |

## Ⅵ. 제언

공공 SW 발주 시 제안요청서(RFP) 단계의 기능 요구사항 명확화를 선행하고, 사업 추진 단계별 간이법-정규법 재산정 및 정산 체계 정립 권장.

```text
[SW 수명주기별 기능점수 거버넌스]
  사업 기획/발주 (간이법 예산 산정) → 설계 완료 (정규법 1차 검증) → 개발/검수 (최종 FP 정산 및 생산성 평가)
```

| 검증 단계 | 발주/계획 단계 (간이법) | 검수/정산 단계 (정규법) |
|---|---|---|
| 핵심 활동 | 업무 기능 목록 기반 평균 가중치 산출 | 화면/DB 명세서 기반 DET/RET/FTR 전수 실측 |
| 관리 지표 | 사업 예산 한도 및 투입 M/M 적정성 | 요구사항 추적 매트릭스(RTM) 대비 기능 구현율 및 정산 대가 |
