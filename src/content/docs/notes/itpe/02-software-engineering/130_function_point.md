## Ⅰ. 기능점수(FP)의 개요

- 개념 : 앨런 알브레히트(Allan Albrecht)가 창안하고 IFPUG(국제기능점수사용자그룹)에서 표준화한 소프트웨어 규모 측정 기법으로, 구현에 사용된 프로그래밍 언어나 기술 스택에 관계없이 최종 사용자의 관점에서 소프트웨어가 제공하는 논리적 업무 기능을 정량적으로 측정하는 국제 표준 소프트웨어 규모 및 대가 산정 척도.
- 배경 및 필요성 : 소스코드 라인 수(LOC) 방식의 언어별 편차와 사전 예측 불가능성을 극복하고, 프로젝트 기획 단계부터 객관적이고 일관된 사업 규모와 예산을 산정하기 위해 도입.
- 국제 표준 및 국내 지침 : ISO/IEC 20926, 한국소프트웨어산업협회(KOSA) '소프트웨어사업 대가산정 가이드'.

## Ⅱ. 기능점수 5대 기능 구성요소 및 계산 체계

```text
                               [ 전체 기능점수 (FP) ]
                                         │
           ┌─────────────────────────────┴─────────────────────────────┐
           ▼                                                           ▼
   [ 데이터 기능 (Data Functions) ]                     [ 트랜잭션 기능 (Transaction Functions) ]
   - 내부논리파일 (ILF, Internal Logical File)          - 외부입력 (EI, External Input)
   - 외부연계파일 (EIF, External Interface File)        - 외부출력 (EO, External Output)
                                                        - 외부조회 (EQ, External Inquiry)
```

- **데이터 기능 측정** (Data Functions) :
  - **ILF** (내부논리파일) : 시스템 내부에서 생성, 갱신, 관리되는 논리적 데이터 그룹 (RDB의 관리 테이블). RET(레코드요소타입)와 DET(데이터요소타입) 수에 따라 낮음/보통/높음 복잡도 결정.
  - **EIF** (외부연계파일) : 타 시스템에서 유지관리되지만 해당 시스템에서 참조하여 읽어오는 데이터 그룹.
- **트랜잭션 기능 측정** (Transaction Functions) :
  - **EI** (외부입력) : 시스템 내부로 데이터를 들여와 ILF를 등록/수정/삭제하는 기능 (회원가입, 주문등록).
  - **EO** (외부출력) : 데이터를 가공, 계산, 변환하여 외부로 내보내는 기능 (통계 리포트, 집계 화면).
  - **EQ** (외부조회) : 단순 검색 및 데이터 조회 기능 (단순 목록 조회, 상세 조회).

## Ⅲ. 간이 기능점수법과 정규 기능점수법의 비교

| 비교 항목 | 간이 기능점수법 (평균 복잡도 적용) | 정규 기능점수법 (상세 복잡도 매트릭스) |
|---|---|---|
| 적용 시점 | 기획, 예산 수립, 발주 공고 단계 | 상세 분석 및 설계 완료 후 개발 단계 |
| 데이터 수집 수준 | 기능 식별만 수행 (RET/DET/FTR 미측정) | RET, DET, FTR의 개수를 전수 카운팅 |
| 기능별 가중치 | 고정된 평균 가중치 적용 (ILF: 7.5, EIF: 5.4, EI: 4.6, EO: 5.2, EQ: 3.9) | 복잡도(Low, Average, High) 매트릭스에 따른 차등 가중치 적용 |
| 산정 소요 공수 | 매우 적음 (신속한 예산 견적 가능) | 많은 시간과 전문 인력 필요 (정밀 정산) |
| 오차율 | $\pm 10\sim 15\%$ 수준 오차 존재 가능 | 오차 최소화 (가장 정확한 규모 확정) |

## Ⅳ. 기능점수(Function Point)의 주요 한계점 및 해결 방안

- 측정자의 주관성에 따른 산정 결과의 변동성(편차) :
  - 한계점 : 데이터 기능(ILF/EIF) 및 트랜잭션 기능(EI/EO/EQ) 식별 시 분석가의 도메인 이해도와 해석 기준에 따라 상당한 오차 발생.
  - 해결 방안 : 공인 기능점수 전문가(CFPS) 참여 의무화, 내부 산정 표준 가이드라인 구체화 및 다자간 교차 검증(Cross-check) 프로세스 제도화.
- 현대 클라우드 네이티브 및 비기능 아키텍처 복잡도 반영 한계 :
  - 한계점 : 사용자 인터페이스 중심의 논리적 기능 측정 방식으로 인해 MSA, 데이터 파이프라인, AI 모델 학습, 고가용성 인프라 엔지니어링 공수 과소 계상.
  - 해결 방안 : 공공 SW 대가산정 가이드라인 내 비기능/아키텍처 보정계수 현실화, 인프라 및 신기술 요소에 대한 별도 실비정액가산 방식 복합 적용.
- 사업 초기 요구사항 불명확 시 간이법의 오차 리스크 :
  - 한계점 : 제안/기획 단계에서 평균 복잡도를 적용하는 간이 기능점수법은 실제 상세 분석/설계 후 도출되는 정규 기능점수와 심각한 예산 괴리 유발.
  - 해결 방안 : 사업 단계별 점진적 상세화(Rolling Wave) 예산 조정 제도 도입, 과업 변경 시 객관적 정규 FP 기반 계약금액 증액 거버넌스 확립.

## Ⅴ. 공공 SW 사업 대가산정 관점의 기술사적 제언

- 설계 완료 후 정규 기능점수 기반의 사후 정산제 정착 : 공공 발주 시 기획 단계의 간이법으로 확정된 예산과 실제 상세 설계 후 도출된 정규 FP 간에 차이가 발생할 경우, 과업심의위원회를 거쳐 계약금액을 공식적으로 증감 정산하는 사후 정산 거버넌스 제도화 필수.
- 클라우드 및 마이크로서비스 환경에 부합하는 FP 측정 기준 고도화 : 기존 모놀리식 단일 DB 중심의 ILF/EIF 산정 기준은 서비스별로 DB가 분리된 MSA 환경에서 EIF가 폭증하거나 복잡한 이벤트 브로커 연계가 누락되는 왜곡이 발생하므로, 분산 아키텍처 특성을 반영한 현대적 FP 가이드라인 개정 필요.
