## Ⅰ. 클래스 다이어그램의 개요

- 개념 : 객체지향 소프트웨어 시스템의 **정적 구조** (Static Structure)를 모델링하기 위해 클래스의 내부 속성(Attribute), 연산(Operation), **접근 제한자** 및 클래스 간의 다양한 관계를 시각적으로 표현하는 대표적인 UML 구조 다이어그램.
- 배경 및 필요성 : 시스템의 논리적 설계 청사진을 제공하여 개발자 간의 의사소통을 명확히 하고, **코드 자동 생성** (Forward Engineering) 및 **역공학** (Reverse Engineering)의 핵심 기반으로 활용.
- 클래스 표현 3영역 : 클래스 이름(Top), 속성(Middle), 연산/메서드(Bottom).

## Ⅱ. 클래스 간의 6대 관계 표기법 및 의미

```text
   [ 일반화 (Generalization) ] ───────▷ [ 부모 클래스 ] (상속: is-a)
   [ 실체화 (Realization) ]   - - - - ▷ [ <<interface>> ] (구현)
   [ 의존 (Dependency) ]      - - - - > [ 파라미터/로컬 객체 ] (일시적 참조: uses-a)
   [ 연관 (Association) ]     ────────> [ 참조 객체 ] (멤버 변수: has-a)
   [ 집약 (Aggregation) ]     ◇───────> [ 부분 객체 ] (약한 포함: 독립 생명주기)
   [ 합성 (Composition) ]     ◆───────> [ 부분 객체 ] (강한 포함: 종속 생명주기)
```

- **일반화 (Generalization)** : 하위 클래스가 상위 클래스를 상속받는 관계 (실선 빈 삼각 화살표).
- **실체화 (Realization)** : 인터페이스의 추상 명세를 클래스가 구체적으로 구현하는 관계 (점선 빈 삼각 화살표).
- **연관 (Association)** : 한 클래스가 다른 클래스의 인스턴스를 멤버 변수로서 지속적으로 참조하는 관계 (실선 화살표).
- **의존 (Dependency)** : 메서드의 매개변수나 로컬 변수로서 일시적으로 다른 객체를 사용하는 관계 (점선 화살표).
- **집약 (Aggregation)** : 전체-부분(Whole-Part) 관계이나 전체 객체가 소멸되어도 부분 객체는 독립적으로 생존 가능한 관계 (빈 다이아몬드).
- **합성 (Composition)** : 전체 객체와 부분 객체의 생명주기가 완전히 일치하여, 전체 객체가 소멸되면 부분 객체도 함께 소멸하는 강한 포함 관계 (채워진 다이아몬드).

## Ⅲ. 접근 제한자 표기법 및 다중성(Multiplicity) 규격

| 표기 기호 | 접근 제한자 | 의미 및 접근 허용 범위 |
|---|---|---|
| + | **public** | 모든 외부 클래스에서 자유롭게 접근 가능 |
| - | **private** | 해당 클래스 내부의 메서드에서만 접근 가능 (정보은닉) |
| # | **protected** | 해당 클래스 및 이를 상속받은 하위 클래스에서만 접근 가능 |
| ~ | **package-private** | 동일한 패키지/네임스페이스 내의 클래스들에만 접근 허용 |

- **다중성** (Multiplicity) 표기 : `1` (정확히 1개), `0..1` (없거나 1개), `*` 또는 `0..*` (0개 이상), `1..*` (최소 1개 이상), `m..n` (m개 이상 n개 이하).

## Ⅳ. 클래스 다이어그램의 주요 한계점 및 해결 방안

- 다이어그램의 과도한 복잡도로 인한 가독성 및 소통 기능 상실 :
  - 한계점 : 수십~수백 개의 도메인 클래스와 모든 프라이빗 필드, 세부 게터/세터 메서드를 하나의 다이어그램에 표현하려다 선이 복잡하게 얽혀 설계 의도 전달 실패.
  - 해결 방안 : 도메인 주도 설계(DDD)의 바운디드 컨텍스트(Bounded Context) 단위로 다이어그램을 분할하고, 세부 속성은 생략한 채 핵심 비즈니스 메서드와 고수준 연관 관계 중심으로 모델링.
- 상속(Generalization)의 남용으로 인한 취약한 기반 클래스(Fragile Base Class) 문제 :
  - 한계점 : 코드 재사용만을 목적으로 다단계 상속 계층을 무리하게 설계하여, 상위 부모 클래스의 사소한 변경이 하위 모든 자식 클래스들의 오작동을 유발하는 구조적 결함 발생.
  - 해결 방안 : '상속보다는 합성(Composition over Inheritance)' 원칙을 설계 표준에 명시하고, 클래스 간 직접 상속 대신 인터페이스(Interface)를 통한 다형적 역할 계약 모델링.
- 런타임 동적 협력 및 메시징 흐름 표현의 근본적 한계 :
  - 한계점 : 클래스 다이어그램은 컴파일 타임 정적 구조만을 나타내므로, 런타임에 다형적으로 어떤 객체가 선택되어 메시지를 주고받는지 실제 실행 순서를 표현 불가.
  - 해결 방안 : 정적 클래스 다이어그램과 함께 런타임 객체 간 동적 상호작용을 나타내는 시퀀스 다이어그램(Sequence Diagram) 및 상태 머신 다이어그램을 병행 설계.

## Ⅴ. 실무 객체지향 설계 시 기술사적 제언

- 상속(Generalization)보다 합성(Composition)을 우선(Favor Composition over Inheritance) : 클래스 상속은 부모와 자식 간의 결합도를 극도로 높여 변경에 취약해지므로, GoF 설계 원칙에 따라 필요한 기능을 멤버 변수로 합성하고 위임(Delegation)하는 설계를 적극 권장.
- 도메인 주도 설계(DDD)와의 연계 모델링 : 클래스 다이어그램 작성 시 기술적 엔티티에만 치중하지 않고, 도메인 경계 내의 애그리게잇(Aggregate), 루트 엔티티, 값 객체(Value Object)를 명확히 구분하여 비즈니스 불변식을 보장하도록 모델링 체계화.
