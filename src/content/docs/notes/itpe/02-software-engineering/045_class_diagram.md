## 연관 키워드

- 클래스 다이어그램(Class Diagram), UML(Unified Modeling Language), 정적 구조(Static Structure), 구조 다이어그램
- 일반화(Generalization), 실체화(Realization), 연관(Association), 의존(Dependency), 집약(Aggregation), 합성(Composition), 접근 제한자, 다중성(Multiplicity)

## Ⅰ. 클래스 다이어그램의 개요

- 핵심 요약 : 시스템의 정적 구조를 클래스의 속성, 연산, 관계로 나타내는 대표적인 UML 구조 다이어그램.
- 개념 : 객체지향 시스템의 정적 구조를 모델링하기 위해 클래스의 속성, 연산, 접근 제한자와 클래스 간 관계를 표현하는 **UML**(Unified Modeling Language, 통합 모델링 언어)의 구조 다이어그램 (**클래스 다이어그램**, Class Diagram).
- 배경 및 필요성 : 논리적 설계 청사진을 제공해 개발자 간 의사소통을 명확하게 하고, 코드 자동 생성(Forward Engineering)과 역공학(Reverse Engineering)의 기반이 됨.
- 주요 목적 : 설계 의도를 명확히 전달하고, 정적 모델과 코드 사이의 동기화 기반을 확보하는 것.

## Ⅱ. 클래스 다이어그램의 특징 및 장점

- 핵심 요약 : 3영역 클래스 표기와 여섯 가지 관계 표기가 정적 구조를 정확히 전달하는 핵심 수단.

1. 클래스 3영역 표기 : 이름(Top), 속성(Middle), 연산(Bottom)을 세 칸으로 나눠 표기 → 한눈에 클래스 책임을 파악.
2. **일반화**(Generalization, 하위 클래스가 상위 클래스를 상속하는 관계) : 실선에 빈 삼각형 화살표로 표기 → is-a 관계를 드러냄.
3. **실체화**(Realization, 인터페이스의 명세를 클래스가 구현하는 관계) : 점선에 빈 삼각형 화살표로 표기 → 역할 계약을 명시.
4. **연관**(Association, 멤버 변수로 다른 클래스를 지속적으로 참조하는 관계) : 실선 화살표 → has-a 관계를 드러냄.
5. **의존**(Dependency, 매개변수나 지역 변수로 잠시 사용하는 관계) : 점선 화살표 → 변경 영향 범위를 좁게 표현.
6. **집약**(Aggregation, 부분 객체가 전체와 독립적으로 생존 가능한 관계) : 빈 다이아몬드 표기.
7. **합성**(Composition, 전체와 부분의 생명주기가 일치하는 관계) : 채운 다이아몬드 표기 → 전체 소멸 시 부분도 함께 소멸함을 드러냄.

## Ⅲ. 클래스 다이어그램의 구조 (흐름)

- 핵심 요약 : 3영역 클래스 박스로 구조를 적고, 여섯 가지 관계와 다중성으로 클래스 사이의 연결을 기술.

```text
[ 클래스 표현 3영역 ]
    ClassName            ← Top : 이름
-------------------
- attribute          ← Middle : 속성
-------------------
+ operation()        ← Bottom : 연산
```

```text
[ 6대 관계 표기법 ]
일반화  ──────▷  부모 클래스 (is-a)
실체화  - - - ▷  인터페이스 (구현)
연관    ──────>  참조 객체 (has-a)
의존    - - - >  매개변수·지역 변수 (uses-a)
집약    ◇──────  부분 객체 (독립 생명주기)
합성    ◆──────  부분 객체 (종속 생명주기)
```

- 다중성(Multiplicity) 표기 : `1`은 정확히 1개, `0..1`은 없거나 1개, `*` 또는 `0..*`는 0개 이상, `1..*`는 1개 이상, `m..n`은 m개 이상 n개 이하를 뜻함.

## Ⅳ. 접근 제한자 표기법의 비교

- 핵심 요약 : 기호마다 접근 허용 범위가 달라, 기호만 보고도 정보은닉 수준을 읽을 수 있게 하는 표기.

| 표기 기호 | 접근 제한자 | 접근 허용 범위 |
| --- | --- | --- |
| + | public | 모든 외부 클래스에서 접근 가능 |
| - | private | 해당 클래스 내부에서만 접근 가능 (정보은닉) |
| # | protected | 해당 클래스와 하위 클래스에서만 접근 가능 |
| ~ | package | 같은 패키지 안의 클래스에서만 접근 가능 |

- 선택 기준 : 외부에 공개할 연산은 +, 내부 상태는 -, 상속 확장을 허용할 항목은 #으로 표기하여 설계 의도를 드러냄.

## Ⅴ. 클래스 다이어그램의 한계와 방안

- 핵심 요약 : 과도한 복잡도, 상속 남용, 동적 흐름 미표현의 한계를 영역 분할, 합성 우선, 동적 다이어그램 병행으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 과도한 복잡도 | 모든 클래스와 세부 필드를 한 장에 그려 선이 얽히고 설계 의도 전달이 실패 | DDD(Domain-Driven Design)의 바운디드 컨텍스트 단위로 분할하고, 핵심 메서드와 고수준 연관 중심으로 모델링 | 다이어그램당 클래스 수 |
| 상속 남용과 취약한 기반 클래스 (Fragile Base Class) | 재사용만을 위해 다단계 상속을 만들면 상위 클래스의 사소한 변경이 하위 클래스 전체의 오작동으로 이어짐 | 상속보다 합성을 우선하고, 역할 계약은 인터페이스로 모델링 | 상속 깊이, 상위 변경 시 영향 클래스 수 |
| 동적 협력 표현의 한계 | 클래스 다이어그램은 컴파일 시점의 정적 구조만 나타내 런타임 메시지 흐름을 보여 주지 못함 | 시퀀스 다이어그램과 상태 머신 다이어그램을 병행 작성 | 정적·동적 모델 간 추적 링크 수 |

## Ⅵ. 객체지향 설계에 대한 기술사적 제언

- 핵심 요약 : 상속보다 합성을 기본 설계 원칙으로 삼고, DDD의 도메인 경계에 맞춰 클래스를 모델링하는 방향.
- 클래스 재사용을 위해 상속 계층부터 만들지 말고, 필요한 기능을 멤버로 합성하고 위임하는 구조를 기본으로 두는 것이 좋다. 이 원칙을 설계 표준에 명시해 두면 상위 클래스 변경이 하위 전체로 번지는 문제를 줄일 수 있다. GoF(Gang of Four)의 설계 원칙이 이 방향을 뒷받침한다.
- 클래스 다이어그램은 기술적 엔티티 위주로 그리기보다 도메인 경계 안의 애그리게이트(Aggregate), 루트 엔티티, 값 객체(Value Object)를 구분해 그리는 편이 좋다. 이렇게 해야 비즈니스 불변식을 어느 객체가 지키는지 드러난다.

## Ⅶ. 결론

- 핵심 요약 : 클래스 다이어그램은 정적 구조 설계의 표준 표기이며, 동적 뷰 보완과 합성 우선 원칙이 함께 필요.
- 시사점 : 여섯 가지 관계와 접근 제한자를 정확히 쓰고, 시퀀스 다이어그램과 DDD 경계를 함께 써야 설계 품질이 높아짐.
