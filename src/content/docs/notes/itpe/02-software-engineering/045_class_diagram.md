## 30초 인출

- 본질: 클래스 다이어그램은 시스템을 구성하는 클래스의 속성·오퍼레이션과 클래스 사이의 관계를 나타내는 UML 구조 다이어그램
- 메커니즘: 클래스를 이름·속성·오퍼레이션 칸으로 그리고 연관·집약·합성·일반화·실체화·의존 관계와 다중성으로 연결
- 통찰: 관계 종류를 잘못 표기하면 객체의 소유와 수명 관계가 오해되므로 전체가 사라질 때 부분도 사라지면 합성, 독립적이면 집약이나 연관으로 구분해 표기

<details>
<summary>핵심 용어</summary>

- **클래스 다이어그램(Class Diagram)** : 클래스와 클래스 사이의 정적 관계를 나타내는 다이어그램
- **다중성(Multiplicity)** : 관계에 참여하는 객체의 수(1, 0..*, 1..* 등)
- **일반화(Generalization)** : 하위 클래스가 상위 클래스의 속성과 오퍼레이션을 상속하는 관계
- **실체화(Realization)** : 클래스가 인터페이스에 정의된 오퍼레이션을 구현하는 관계
- **집약(Aggregation)** : 부분이 전체와 독립적으로 존재할 수 있는 전체-부분 관계
- **합성(Composition)** : 부분이 전체의 생명주기에 종속되어 전체가 사라지면 함께 사라지는 관계
- **의존(Dependency)** : 한 클래스가 다른 클래스를 일시적으로 사용하는 관계

</details>

## 2~4교시 25점 답안

## Ⅰ. 클래스 다이어그램의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **클래스 다이어그램** 은 클래스와 클래스 사이의 관계로 시스템의 정적 구조를 나타내는 UML 구조 다이어그램 |
| 목적 | 객체지향 설계의 구조 표현과 구현 기준 제공 |

## Ⅱ. 클래스 다이어그램의 특징

| 특징 | 의미 |
|---|---|
| 정적 구조 | 시간 흐름이 아닌 구성과 관계 표현 |
| 설계·구현 연결 | 클래스 코드와 직접 대응 |
| 단계별 상세도 | 분석 단계는 개념, 설계 단계는 속성·오퍼레이션까지 |

## Ⅲ. 클래스 표기와 관계

### 클래스 표기

```text
┌──────────────┐
│    Order     │  클래스 이름
├──────────────┤
│ - orderId    │  속성 (- private, + public)
│ - total      │
├──────────────┤
│ + addItem()  │  오퍼레이션
│ + cancel()   │
└──────────────┘
```

### 확대: 관계 표기

```text
연관      A ─────── B          (참조·협력)
의존      A - - - → B          (일시 사용)
일반화    A ────▷ B            (A가 B를 상속)
실체화    A - - -▷ B           (A가 인터페이스 B를 구현)
집약      A ◇───── B           (부분이 독립 존재)
합성      A ◆───── B           (부분이 A와 함께 소멸)
```

## Ⅳ. 관계의 비교

| 관계 | 의미 | 수명 관계 | 예 |
|---|---|---|---|
| 연관 | 객체 간 참조·협력 | 독립 | 고객-주문 |
| 집약 | 전체-부분, 부분 독립 | 독립 | 부서-직원 |
| 합성 | 전체-부분, 부분 종속 | 함께 소멸 | 주문-주문항목 |
| 일반화 | 상속 | 해당 없음 | 결제-카드결제 |
| 실체화 | 인터페이스 구현 | 해당 없음 | 카드결제-결제 인터페이스 |
| 의존 | 일시적 사용 | 독립 | 서비스-유틸리티 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 집약·합성 구분 오류로 수명 관계 오해 | 부분의 독립 존재 여부로 구분 |
| 과도한 상세 표기로 가독성 저하 | 핵심 클래스와 관계 위주로 표기 |
| 코드와 다이어그램의 불일치 | 설계 변경 시 함께 갱신하고 코드에서 역생성 검토 |

## Ⅵ. 제언

전체가 소멸할 때 부분도 소멸하는지를 기준으로 합성과 집약을 구분해 표기하고, 관계마다 다중성을 함께 표기

### 관계 표기 판단 순서

```text
두 클래스의 관계 확인
    ├─ 상속 → 일반화 / 인터페이스 구현 → 실체화
    ├─ 전체-부분 → 부분이 전체와 함께 소멸? → 예: 합성 / 아니오: 집약
    └─ 일시 사용 → 의존, 그 외 → 연관
```

### 선택 근거: 모든 관계를 연관으로 표기하는 경우와의 비교

| 구분 | 모두 연관 | 제언: 관계 구분 표기 |
|---|---|---|
| 수명 관계 | 불명확 | 명확 |
| 구현 대응 | 모호 | 코드 구조와 대응 |
| 표기 부담 | 낮음 | 판단 필요 |
