## 답안 골격 (10점 / 25점)

```text
[클래스 다이어그램] ◀━━ 머리: Ⅶ 공학적 제언 (집약·합성의 엄격한 생명주기 모델링과 DDD 애그리게잇 루트 설계 연계)
 ┃
 ┣━ Ⅰ 개요 ───── 객체지향 시스템의 정적 구조(속성, 행위)와 클래스 간의 관계를 시각화하는 핵심 구조 모델
 ┣━ Ⅱ 3단 구획 ─ 클래스명(이름/스테레오타입) · 속성(Attributes: 가시성/타입) · 오퍼레이션(Operations: 파라미터/반환타입)
 ┣━ Ⅲ 4대 가시성 ─ Public(`+`) · Private(`-`) · Protected(`#`) · Package/Default(`~`)
 ┣━ Ⅳ 5대 관계 심볼 ─ 일반화(상속: 실선+빈삼각형) · 실체화(인터페이스: 점선+빈삼각형) · 연관(실선) · 의존(점선)
 ┃                    · 집약(Aggregation: 빈마름모) vs 합성(Composition: 채운마름모)
 ┣━ Ⅴ 비교 ───── 집약(독립 생명주기, 약한 결합) vs 합성(생명주기 종속, 강한 결합, JPA Cascade 연계)
 ┣━ Ⅵ 실무 문제 ─ 상속 남용으로 인한 깨지기 쉬운 기반 클래스 / 엔티티 삭제 시 고아 객체(Orphan) 잔존
 ┗━ Ⅶ 결론 ───── 상속보다 합성(Favor Composition) 원칙 및 DDD 애그리게잇 경계 확립 수단화
```

- **필수 키워드**: 정적 구조 다이어그램, 3단 구획(이름·속성·오퍼레이션), 가시성(`+`, `-`, `#`, `~`), 다중성(Multiplicity: `0..1`, `1..*`), 일반화(Generalization), 실체화(Realization), 의존(Dependency), 집약(Aggregation, `◇`), 합성(Composition, `◆`), DDD 애그리게잇 루트
  - **10점형**: 클래스 다이어그램 3단 구조 및 가시성 기호 표 → 5대 관계 심볼 및 집약 vs 합성 비교도.
  - **25점형**: Ⅰ~Ⅶ 전체 구조 전개 + 실무 시나리오(예: 주문-주문항목, 주사위 게임) 클래스 다이어그램 작성 + 상속 vs 합성 설계 원칙 및 JPA ORM 매핑 연계 심층 제시.

## 30초 인출용 핵심 다이어그램

```text
+-------------------------------------------------------------------------+
|                  UML 클래스 다이어그램 표기법 및 5대 관계               |
+-------------------------------------------------------------------------+
|  [ 1. 클래스 3단 구획 및 가시성 ]      [ 2. 실체화 및 일반화(상속) ]    |
|  +-----------------------------+       <<interface>> Printable          |
|  |       <<Entity>> Order      |                 ▲                      |
|  +-----------------------------+                 ┆ (점선+빈삼각형: 실체화)|
|  | - orderId: String           |                 |                      |
|  | # totalAmount: BigDecimal   |        +-----------------+             |
|  | + orderStatus: Status       |        |     Invoice     |             |
|  +-----------------------------+        +-----------------+             |
|  | + calculateTotal(): void    |                 ▲                      |
|  | - validateOrder(): boolean  |                 │ (실선+빈삼각형: 일반화)|
|  +-----------------------------+        +-----------------+             |
|                                         |   TaxInvoice    |             |
|  [ 3. 집약 vs 합성 (생명주기 결합도) ]  +-----------------+             |
|                                                                         |
|    Car ◇──────── 4 Tire       (집약: 타이어는 차가 폐차되어도 재사용)  |
|   (전체) (빈마름모: 독립 생존)                                          |
|                                                                         |
|    Order ◆─────── 1..* OrderItem (합성: 주문이 삭제되면 항목도 삭제)   |
|   (전체) (채운마름모: 생명주기 종속, DDD Aggregate Root, JPA Cascade)   |
+-------------------------------------------------------------------------+
```

## 본론: 개념 및 핵심 메커니즘

### 1. 클래스 다이어그램의 구성 요소

1. **3단 구획 구조**:
   - **상단 (Name Compartment)**: 클래스명, 추상 클래스(이탤릭체), 스테레오타입(`<<interface>>`, `<<entity>>`).
   - **중단 (Attributes Compartment)**: `[가시성] 속성명: 타입 [다중성] [= 기본값]`
   - **하단 (Operations Compartment)**: `[가시성] 메서드명(파라미터: 타입): 반환타입`
2. **가시성(Visibility) 표기법**:
   - `+` (Public): 모든 외부 클래스에서 접근 허용.
   - `-` (Private): 선언된 클래스 내부에서만 접근 허용 (정보은닉의 기본).
   - `#` (Protected): 동일 패키지 및 상속받은 자식 클래스에서 접근 허용.
   - `~` (Package/Default): 동일 패키지 내부 클래스에서만 접근 허용.

### 2. UML 클래스 간 5대 핵심 관계 심볼

| 관계 유형 | 심볼 및 선 형태 | 관계의 본질 및 코드 매핑 | 예시 |
|---|---|---|---|
| **연관<br>(Association)** | 실선 (`───` 또는 `───>`) | 클래스가 다른 클래스를 인스턴스 멤버 변수로 영구적 참조. | `class Order { Member member; }` |
| **의존<br>(Dependency)** | 점선 화살표 (`- - ->`) | 메서드 인자(Parameter), 로컬 변수, 반환값으로 일시적 참조. | `class Car { void run(Gas gas) }` |
| **일반화<br>(Generalization)** | 실선 + 닫힌 빈 삼각형 (`───▷`) | 객체지향 상속(Inheritance), "is-a" 관계, 다형성 지원. | `class Dog extends Animal` |
| **실체화<br>(Realization)** | 점선 + 닫힌 빈 삼각형 (`- - -▷`) | 인터페이스 명세를 클래스가 실제 구현(Implementation). | `class FileRepo implements Repo` |
| **집약<br>(Aggregation)** | 실선 + 빈 마름모 (`◇───`) | "has-a" 공유 관계. 전체와 부분이 독립적 생명주기 유지. | 자동차(`Whole`)와 타이어(`Part`) |
| **합성<br>(Composition)** | 실선 + 채운 마름모 (`◆───`) | "contains-a" 복합 관계. 전체가 부분의 생명주기를 배타적 소유. | 주문(`Whole`)과 주문상세(`Part`) |

### 3. 집약(Aggregation) vs 합성(Composition) 상세 비교

- **생명주기 종속성**:
  - **집약 (◇)**: 전체 객체가 메모리에서 해제(GC/소멸자)되어도 부분 객체는 다른 곳에서 계속 참조되어 살아남음.
  - **합성 (◆)**: 전체 객체가 소멸하면 부분 객체도 강제로 함께 소멸됨 (배타적 소유).
- **엔터프라이즈 아키텍처 연계**:
  - **도메인 주도 설계 (DDD)**: 합성 관계의 전체 객체가 바로 **애그리게잇 루트(Aggregate Root)**가 되며, 외부에서는 애그리게잇 루트만을 통해서만 부분 엔티티를 조작해야 함.
  - **JPA / 하이버네이트**: 합성 관계는 `@OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)`로 매핑되어 데이터 정합성을 물리적으로 강제함.

## 실무 장애 시나리오 및 공학적 대안

### 1. 현장 장애 사례

1. **단순 연관 매핑으로 인한 고아 객체(Orphan) 및 DB 무결성 훼손**:
   - 주문 삭제 시 주문 상세(OrderItem) 테이블의 레코드가 지워지지 않고 외래키 오류 또는 쓰레기 데이터로 남아 통계 왜곡.
2. **무분별한 상속 계층 확장으로 인한 부모 클래스 수정 파장**:
   - 기능 재사용을 위해 상속을 6단계까지 확장했다가, 부모 클래스의 메서드 하나를 변경하자 수십 개 하위 서비스가 런타임 에러 발생.

### 2. 문제 원인 및 공학적 해결책

| 장애 상황 | 근본 원인 | 공학적 대책 (대안 기술) | 개선 효과 |
|---|---|---|---|
| **고아 객체 쓰레기 데이터** | 집약/합성 생명주기 구분 부재 | 클래스 다이어그램에서 **합성(◆)** 관계 정의 및 JPA `orphanRemoval=true` 적용 | 부모 객체 삭제 시 자식 자동 연쇄 삭제 보장 |
| **상속 기반 클래스 취약성** | "상속보다는 합성" 원칙 위반 | 상속 관계를 **합성 위임(Composition & Delegation)** 및 전략 패턴으로 전환 | 결합도 완화 및 독립적 알고리즘 교체 달성 |
| **다이어그램 가독성 상실** | 롬복 Getter/Setter 무차별 표기 | 비즈니스 핵심 도메인 메서드만 선별하는 **의사소통 중심 모델링 표준화** | 모델링 가독성 및 아키텍처 이해도 80% 향상 |

## 결론: 기술사 답안 차별화 포인트

1. **도식 작성의 정확성**: 시험 답안 작성 시 화살표와 마름모의 모양(점선 vs 실선, 빈 마름모 vs 채운 마름모, 빈 삼각형)을 혼동 없이 정확하게 작도할 것.
2. **DDD(도메인 주도 설계) 애그리게잇 루트와의 접목**: 클래스 다이어그램의 **합성(Composition) 관계가 현대 도메인 주도 설계의 애그리게잇(Aggregate) 경계를 긋는 결정적 도구**이며, 데이터 무결성과 트랜잭션 일관성 단위의 청사진이 됨을 3단락 제언으로 명문화할 것.
