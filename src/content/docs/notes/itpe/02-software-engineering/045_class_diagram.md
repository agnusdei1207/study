## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 아키텍처·객체지향 설계 → **클래스 다이어그램(Class Diagram)**

## 30초 인출

- 본질: 객체지향 시스템을 구성하는 클래스들의 내부 구조(속성·연산)와 클래스 간의 정적 관계(연관, 일반화, 의존, 집약, 합성)를 시각적으로 명세하는 UML 표준 정적 구조 다이어그램
- 메커니즘: 3단 구획(클래스명, 속성, 연산 및 가시성 기호) 정의 + 관계선 및 다중성(Multiplicity) 매핑 + 인터페이스 실체화(Realization)
- 통찰: 클래스 다이어그램의 집약(Aggregation)과 합성(Composition)을 혼동하여 구현할 경우 메모리 누수와 생명주기 고아 객체가 발생하므로 소유권과 생명주기 종속성에 따른 명확한 표기 규약 준수 필수

<details>
<summary>핵심 용어</summary>

- **Class Diagram(클래스 다이어그램)** : 시스템의 정적 구조를 구성하는 클래스, 인터페이스, 그리고 그들 간의 관계를 시각화한 UML 구조 모델
- **Multiplicity(다중성)** : 두 클래스 간의 연관 관계에서 참여할 수 있는 인스턴스의 개수 제약(`1`, `0..1`, `1..*`, `*`)
- **Generalization(일반화, 상속)** : 하위 클래스가 상위 클래스의 속성과 메서드를 상속받아 확장하는 Is-a 관계 (실선 + 닫힌 빈 삼각형)
- **Realization(실체화, 구현)** : 클래스가 추상 인터페이스에 정의된 오퍼레이션 계약을 구체적으로 구현하는 관계 (점선 + 닫힌 빈 삼각형)
- **Aggregation(집약)** : 부분이 전체와 독립적으로 존재 가능하며 복수의 전체에 공유될 수 있는 약한 Has-a 관계 (실선 + 빈 마름모)
- **Composition(합성)** : 부분이 전체의 생명주기에 종속되어 전체 객체 소멸 시 부분 객체도 함께 소멸되는 강한 Has-a 관계 (실선 + 채운 마름모)
- **Dependency(의존)** : 한 클래스가 다른 클래스를 메서드 파라미터나 로컬 변수 형태로 일시적으로 사용하는 짧은 관계 (점선 화살표)

</details>

## 2~4교시 25점 답안

## Ⅰ. 클래스 다이어그램의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 객체지향 소프트웨어의 정적 구조를 모델링하기 위해 클래스의 내부 구조(이름, 속성, 메서드)와 클래스 간의 구조적 관계(상속, 연관, 집약, 합성, 의존)를 OMG 표준 표기법으로 명세한 다이어그램 |
| 목적 | 시스템의 도메인 모델 가시화, 객체 간 책임 분할 및 결합도 검증, 상세 설계와 소스코드 간의 1:1 구조적 정합성 보장 |

## Ⅱ. 클래스 다이어그램의 핵심 특징

| 특징 | 의미 |
|---|---|
| 정적 뷰(Static View) | 런타임의 시간적 제어 흐름이 아닌 컴파일 타임의 구조적 연결성과 데이터 타입을 정적으로 기술 |
| 추상화 수준 조절 | 분석 단계의 개념적 도메인 모델부터 구현 단계의 상세 설계 클래스 모델까지 단계적 상세화 지원 |
| 엄격한 캡슐화 표기 | 접근 제어자(`+`, `-`, `#`, `~`)를 통해 정보은닉 경계와 외부 공개 인터페이스를 명확히 구분 |
| 양방향 코드 생성성 | CASE 도구를 통해 다이어그램에서 소스코드 스켈레톤을 자동 생성하거나 역공학(Reverse Engineering) 가능 |

## Ⅲ. 클래스 다이어그램 체계 및 관계 구조

### 클래스 3단 구획 및 6대 관계 메커니즘

```text
┌────────────────────────────────────────────────────────┐
│                   <<interface>>                        │
│                   PaymentService                       │
├────────────────────────────────────────────────────────┤
│ + processPayment(amount: double): boolean              │
└───────────────────────────▲────────────────────────────┘
                            │ ..▷ 실체화 (Realization, 점선+빈삼각형)
┌───────────────────────────┴────────────────────────────┐
│                    CreditCardPayment                   │
├────────────────────────────────────────────────────────┤
│ - cardNumber: String                                   │
├────────────────────────────────────────────────────────┤
│ + processPayment(amount: double): boolean              │
└───────────────────────────▲────────────────────────────┘
                            │ 
┌───────────────────────────┴────────────────────────────┐
│                         Order                          │
├────────────────────────────────────────────────────────┤
│ - orderId: String                                      │
│ - orderDate: Date                                      │
├────────────────────────────────────────────────────────┤
│ + calculateTotal(): double                             │
│ + cancelOrder(): void                                  │
└────────────┬─────────────────────────────◆─────────────┘
             │                             │ 1 (전체)
             │                             │
             │                             ▼ 1..* (부분: 합성)
             │                  ┌────────────────────────┐
             │                  │       OrderItem        │
             │                  ├────────────────────────┤
             │                  │ - quantity: int        │
             │                  │ - unitPrice: double    │
             │                  └───────────┬────────────┘
             │ 1 (전체)                     │
             │                              │
             ▼ 0..1 (부분: 집약)            ▼ 1 (단방향 연관)
┌────────────────────────┐      ┌────────────────────────┐
│      CouponDiscount    │      │        Product         │
│ (빈 마름모, 공유 가능) │      │  - name: String        │
└────────────────────────┘      └────────────────────────┘
```

### 클래스 3단 구획(Compartment) 구조 및 표기 규칙

| 구획 구분 | 표기 문법 및 형식 | 세부 의미 및 모델링 규칙 |
|---|---|---|
| **1단: 클래스 이름** | `<<스테레오타입>> ClassName` | 파스칼 케이스(PascalCase) 명명, 추상 클래스는 *이탤릭체*, 인터페이스는 `<<interface>>` 표기 |
| **2단: 속성 (Attributes)** | `가시성 속성명: 타입 [다중성] = 기본값` | 상태(State)를 나타내며 정보은닉을 위해 주로 Private(`-`) 가시성 부여 |
| **3단: 연산 (Operations)** | `가시성 연산명(파라미터: 타입): 반환타입` | 행위(Behavior) 및 책임을 나타내며 공개 인터페이스는 Public(`+`) 가시성 부여 |

### UML 가시성(Visibility) 4대 기호
- **Public (`+`)** : 모든 외부 클래스에서 자유롭게 접근 가능
- **Private (`-`)** : 해당 클래스 내부의 메서드에서만 접근 가능 (정보은닉의 기본)
- **Protected (`#`)** : 해당 클래스 및 이를 상속받은 하위 자식 클래스에서 접근 가능
- **Package (`~`)** : 동일한 네임스페이스(패키지) 내에 위치한 클래스들만 접근 가능

## Ⅳ. 클래스 간 6대 관계 비교 및 집약 vs 합성 분석

### UML 클래스 간 6대 관계 분류 및 코드 매핑

| 관계 유형 | UML 화살표 표기법 | 관계의 본질 및 결합 강도 | 코드 구현 매핑 형태 |
|---|---|---|---|
| **일반화 (Generalization)** | 실선 + 닫힌 빈 삼각형 (`──▷`) | Is-a 상속 관계, 가장 강한 결합도 | `class Dog extends Animal` |
| **실체화 (Realization)** | 점선 + 닫힌 빈 삼각형 (`··▷`) | 인터페이스 규격 계약 구현 | `class OrderServiceImpl implements OrderService` |
| **의존 (Dependency)** | 점선 + 열린 화살표 (`··>`) | 일시적 메서드 호출, 가장 약한 관계 | 메서드 파라미터나 로컬 변수: `void pay(Card card)` |
| **연관 (Association)** | 실선 + 열린 화살표 (`──>`) | 객체 간 영속적 참조 관계 (다중성 수반) | 클래스의 멤버 필드로 참조: `private User customer;` |
| **집약 (Aggregation)** | 실선 + 빈 마름모 (`◇──`) | 약한 전체-부분, 부분 객체 독립 생존 | 멤버 필드 참조하되 외부에서 주입: `Department(List<Emp>)` |
| **합성 (Composition)** | 실선 + 채운 마름모 (`◆──`) | 강한 전체-부분, 전체 소멸 시 부분 소멸 | 내부에서 직접 생성: `Order() { this.items = new ArrayList(); }` |

### 집약(Aggregation) vs 합성(Composition) 상세 비교

| 비교 항목 | 집약 (Aggregation, 약한 결합) | 합성 (Composition, 강한 결합) |
|---|---|---|
| **소유권 및 배타성** | **공유 가능 (Shared Ownership)** | **배타적 단일 소유 (Exclusive Ownership)** |
| **생명주기 종속성** | **독립적 (부분은 전체가 삭제되어도 생존)** | **완전 종속 (전체 객체 소멸 시 부분 객체도 연쇄 소멸)** |
| **UML 표기 기호** | 전체 쪽에 **빈 마름모 (`◇`)** 표기 | 전체 쪽에 **채워진 검은 마름모 (`◆`)** 표기 |
| **실세계 비유** | 동아리(전체)와 동아리 회원(부분) | 사람(전체)과 심장(부분), 주문(전체)과 주문항목(부분) |
| **객체 생성 주체** | 외부에서 생성되어 파라미터로 전달받음 | 전체 객체의 생성자 내부에서 부분 객체를 직접 인스턴스화 |
| **외래키(FK) 설계** | Nullable 외래키 허용 | Not Null 외래키 및 복합 키(Composite Key) 구성 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 집약과 합성을 구분 없이 단순 연관으로 작성하여 객체 생명주기 및 메모리 해제 누락 | 생성/소멸 책임을 분석하여 배타적 소유 시 반드시 합성(Composition)으로 엄격 표기 |
| 모든 세부 Getter/Setter와 프라이빗 필드를 기계적으로 다이어그램에 기재하여 모델 가독성 상실 | 도메인 핵심 비즈니스 로직과 공개 오퍼레이션 중심의 모델링 테일러링 수행 |
| 객체지향 상속(Generalization)의 남발로 인한 상위 클래스 변경 시 하위 클래스 연쇄 파괴 현상 | 상속보다는 조합(Composition over Inheritance) 원칙을 적용하여 위임 구조로 모델링 |

## Ⅵ. 제언

PlantUML/Mermaid 기반 Docs-as-Code 모델링 및 ArchUnit을 통한 클래스 다이어그램-소스코드 정합성 검증

### Docs-as-Code 기반 클래스 모델링 파이프라인

```text
[개발자 Markdown 내 PlantUML 클래스 텍스트 작성]
       ↓
[Git 커밋 및 Pull Request 생성]
       ↓
[CI 파이프라인 자동 검증 실행]
  ├─ 1. PlantUML 문법 검사 및 SVG 다이어그램 자동 렌더링
  ├─ 2. ArchUnit 정적 분석: 클래스 간 상속 깊이(Depth of Inheritance) 검사
  ├─ 3. 무분별한 순환 참조(Cyclic Dependency) 자동 차단
  └─ 4. 다이어그램과 실제 Java/Kotlin 클래스 구조의 일치율 검사
       ↓
[정합성 검증 완료 시 개발자 포털 및 아키텍처 문서 사이트 자동 배포]
```

### 클래스 간 관계 설계 의사결정 체계

```text
두 클래스 A, B 간의 구조적 관계 모델링
       ↓
[A가 B의 속성과 메서드를 그대로 물려받는 진정한 Is-a 관계인가?]
       ├─ 예 ──→ 일반화(Generalization) 적용 (LSP 원칙 준수 확인)
       └─ 아니오 ─→ [A가 B를 멤버 변수로 영구히 참조하는 Has-a 관계인가?]
                         ├─ 아니오 ─→ 일시적 메서드 호출인 의존(Dependency) 적용
                         └─ 예 ───→ [A가 소멸할 때 B도 반드시 함께 소멸해야 하는가?]
                                        ├─ 예 ──→ 합성 (Composition, 채운 마름모)
                                        └─ 아니오 ─→ 집약 (Aggregation, 빈 마름모)
```

### 선택 근거: 전통적 무거운 CASE 도구와 제언 텍스트 기반 클래스 모델링 비교

| 구분 | 상용 비주얼 CASE 도구 | 제언: 텍스트 기반 모델링 (PlantUML) |
|---|---|---|
| 버전 관리 | 바이너리 파일(.vsdx, .mdl)로 Git Diff 불가능 | 일반 텍스트 코드로 Git 브랜치, PR, Diff 완벽 지원 |
| 코드 동기화 | 구현 코드 변경 시 수동 수정으로 다이어그램 노후화 | CI 파이프라인에서 코드 변경과 다이어그램 동시 검증 |
| 접근성 | 고가의 라이선스 및 무거운 전용 프로그램 필요 | VS Code 및 브라우저에서 누구나 즉시 열람 및 수정 |
