소프트웨어 공학 → 인터페이스·아키텍처 → **Open API(API 일반)**

## 30초 인출

- 본질: 외부 개발자 및 제3자 기관이 플랫폼의 핵심 데이터와 비즈니스 기능에 프로그래밍 방식으로 접근할 수 있도록 공개된 표준 인터페이스
- 메커니즘: 표준 웹 프로토콜(HTTP/REST)과 명세(OAS) 기반으로 인증·인가(OAuth 2.0/OIDC), 트래픽 제어(Rate Limit), 객체 수준 접근 통제 거쳐 백엔드 연동
- 통찰: 단순 게이트웨이 인증만으로는 객체 수준 인가 취약점(BOLA)과 과도한 데이터 노출 위험이 상존하므로 백엔드 세부 인가 검증과 스키마 필터링 체계 필수 구축

<details>
<summary>핵심 용어</summary>

- **Open API** : 외부 개발자에게 플랫폼의 핵심 데이터와 기능을 프로그래밍 방식으로 개방하는 공개 인터페이스
- **API Gateway** : 인증, 인가, 라우팅, 속도 제한, 로깅, 분석을 중앙에서 일괄 처리하는 관문 컴포넌트
- **OAuth 2.0** : 제3자 클라이언트에 제한된 자원 접근 권한을 위임하는 업계 표준 인가 프레임워크
- **Rate Limiting / Throttling** : 서비스 가용성 보장을 위해 클라이언트별 단위 시간당 호출 횟수를 제한하는 트래픽 제어 기법
- **OAS(OpenAPI Specification)** : RESTful API의 엔드포인트, 파라미터, 요청/응답 형식을 기술하는 기계 판독형 표준 명세 규격
- **BOLA(Broken Object Level Authorization)** : 사용자 권한 검증 누락으로 타인의 데이터 객체에 무단 접근 가능한 API 보안 취약점

</details>

## 2~4교시 25점 답안

## Ⅰ. Open API의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 기업 및 기관이 보유한 데이터와 비즈니스 서비스를 외부 개발자 및 제3자에게 프로그래밍 방식으로 안전하게 개방하는 표준 연계 인터페이스 |
| 목적 | 플랫폼 생태계 확장, 비즈니스 파트너십 강화 및 디지털 서비스 간 민첩한 융합 촉진 |

## Ⅱ. Open API의 핵심 특징

| 특징 | 의미 |
|---|---|
| 표준화된 명세 | OAS(Swagger) 기반의 기계 판독형 명세를 제공하여 클라이언트 코드 자동 생성 및 빠른 통합 지원 |
| 엄격한 접근 통제 | API Key, OAuth 2.0, mTLS 등을 결합하여 호출 주체와 데이터 접근 권한을 다계층으로 검증 |
| 트래픽 보호 | Rate Limiting, Throttling, Quota 정책을 적용하여 백엔드 과부하 방지 및 서비스 가용성 보장 |
| 라이프사이클 관리 | 버전 관리(Semantic Versioning), 사용 중단(Deprecation) 통보를 통해 외부 호환성 유지 |

## Ⅲ. Open API 아키텍처 및 요청 처리 체계

### 외부 연계 3계층 아키텍처 및 요청 제어 흐름

```text
[외부 클라이언트]             [API Gateway 관문 계층]              [내부 백엔드 마이크로서비스]
       │                                 │                                    │
       │ 1. API 호출 (Token, Key)        │                                    │
       ├────────────────────────────────→│                                    │
       │                                 ├─ [인증·인가 검증 (JWT/OAuth)]      │
       │                                 ├─ [Rate Limit / 할당량 체크]        │
       │                                 ├─ [WAF / 악성 페이로드 필터링]      │
       │                                 │                                    │
       │                                 │ 2. 검증된 요청 라우팅              │
       │                                 ├───────────────────────────────────→│
       │                                 │                                    ├─ [객체 수준 인가(BOLA 검사)]
       │                                 │                                    ├─ [비즈니스 로직 처리]
       │                                 │                                    └─ [민감 데이터 마스킹]
       │                                 │ 3. 정제된 응답 반환                │
       │                                 │←───────────────────────────────────┤
       │ 4. 최종 응답 (JSON)             │                                    │
       │←────────────────────────────────┤                                    │
```

| 핵심 구성요소 | 주요 기술 및 메커니즘 | 실무 역할 |
|---|---|---|
| **개발자 포털 (Developer Portal)** | API 카탈로그, Sandbox, 대화형 문서(Swagger UI) | 외부 개발자의 API 학습, 테스트 및 키 발급 신청 지원 |
| **API Gateway** | 인라인 프록시, 라우팅, 로드밸런싱 | 트래픽 집중 관리, 인증 캐싱, 유량 제어 및 횡단 관심사 처리 |
| **보안 및 인증 모듈** | OAuth 2.0 Authorization Server, OIDC | 클라이언트 식별, 토큰 발급, 범위(Scope) 기반 인가 판정 |
| **정책 엔진 (Policy Engine)** | 토큰 버킷(Token Bucket), 누출 버킷(Leaky Bucket) | 클라이언트 등급별 호출 빈도 및 총 호출량 제한 집행 |
| **관측성 및 과금 시스템** | 분산 트레이싱(OpenTelemetry), 메트릭 집계 | API 사용 통계 수집, SLA 모니터링, 호출량 기반 과금 정산 |

## Ⅳ. Open API 개방 범위별 비교 및 보안 위협 분석

### 개방 범위에 따른 3대 API 유형 비교

| 구분 | 프라이빗 API (Private) | 파트너 API (Partner) | 퍼블릭 Open API (Public) |
|---|---|---|---|
| **개방 대상** | 사내 내부 개발팀 및 내부 시스템 | 제휴 협약이 체결된 특정 파트너사 | **불특정 다수 외부 개발자 및 일반 대중** |
| **비즈니스 목적** | 시스템 간 결합도 완화 및 재사용성 증대 | B2B 데이터 연계 및 공동 비즈니스 창출 | **플랫폼 생태계 확장 및 오픈 이노베이션** |
| **인증 및 통제** | 내부 SSO, mTLS, 내부 IAM 기반 | 파트너 전용 API Key, 상호 인증, 전용선/VPN | **공개 OAuth 2.0, API Key 발급, WAF 보호** |
| **운영 및 거버넌스** | 조직 내부 릴리스 일정에 맞춘 통합 관리 | 파트너 계약 기반 SLA 및 접근 권한 통제 | **엄격한 시맨틱 버저닝 및 Deprecation 정책 공표** |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 객체 수준 인가 취약점(BOLA)으로 인한 타인 데이터 무단 열람 | API Gateway 단일 인증을 탈피하여 백엔드 비즈니스 로직 내 리소스 소유권 검증 로직 강제 |
| 대량 악의적 트래픽 집중 및 DDoS 공격으로 인한 백엔드 자원 고갈 | IP 및 클라이언트 ID 기반의 동적 Rate Limiting과 적응형 트래픽 차단 알고리즘 적용 |
| 응답 페이로드 내 불필요한 개인정보 및 민감 데이터 과도 노출 | 응답 DTO 필터링 규격 적용 및 게이트웨이 레벨 데이터 마스킹 파이프라인 구축 |

## Ⅵ. 제언

API-First 설계와 자동화된 계약 검증(Consumer-Driven Contract Testing) 체계를 통한 무중단 생태계 진화

### API-First 라이프사이클 거버넌스 체계

```text
[비즈니스 요구] → [OAS 명세 작성] → [Mock 서버 배포] → [클라이언트 병행 개발]
                          │
                          ├─→ [Contract 자동 검증] (Pact)
                          │
                          └─→ [API Gateway 자동 배포] → [실시간 텔레메트리 관측]
```

### API 보안 및 트래픽 통제 파이프라인

```text
[외부 요청 인입]
       ↓
[L7 WAF 검사] ── (악성 공격 탐지 시) ──→ [즉시 차단 및 감사 로그 기록]
       ↓ 정상 요청
[Rate Limiting 판정] ── (한도 초과 시) ──→ [HTTP 429 Too Many Requests 반환]
       ↓ 허용 범위
[OAuth 토큰 유효성 검증]
       ↓
[백엔드 포워딩 및 BOLA 검증]
```

### 선택 근거: 전통적 API 관리와 현대적 API 거버넌스 비교

| 구분 | 전통적 포인트 투 포인트 연계 | 제언: 현대적 API-First 거버넌스 |
|---|---|---|
| 인터페이스 설계 | 코드 작성 후 수동 문서화 진행 | OAS 기반 명세 선행 설계 및 코드 자동 생성 |
| 보안 통제 방식 | 애플리케이션 개별 코드에서 분산 처리 | API Gateway를 통한 정책 중앙화 및 심층 방어 |
| 변경 영향도 검증 | 배포 후 통합 테스트 시점에 오류 발견 | Contract Test 기반 CI/CD 파이프라인에서 자동 사전 차단 |
