## 답안 골격
```text
[유지보수 및 3R] ◀━━ 머리: Ⅶ 내 의견 (역공학 기반 문서화와 점진적 재공학을 통한 레거시 유지보수 비용 통제)
 ┃
 ┣━ Ⅰ 개요 ───── 전체 TCO의 70~80%를 차지하는 유지보수 비용 위기 → 소프트웨어 수명 연장과 생산성 향상을 위한 공학적 3R 체계
 ┣━ Ⅱ 특징 ───── 소프트웨어 생명주기 최장 단계 · 레이먼 법칙(지속적 변화/복잡도 증가) · 3R(역공학, 재공학, 재사용) 기반 비용 절감
 ┣━ Ⅲ 구조 ───── 유지보수 4대 유형(수정, 적응, 완전, 예방) + 3R 체계(역공학 Reverse, 재공학 Re-engineering, 재사용 Reuse)
 ┣━ Ⅳ 흐름 ───── 레거시 소스코드 분석(역공학) → 아키텍처/설계 복원 → 리팩토링 및 코드 재구조화(재공학) → 표준 컴포넌트화(재사용)
 ┣━ Ⅴ 비교 ───── 3R 상호 비교: 역공학(코드→설계 추출) vs 재공학(설계 개선 및 신규 구현) vs 재사용(부품 자산 활용)
 ┗━ Ⅵ 실무 ───── 문서 없는 레거시 시스템의 유지보수 한계 / 리팩토링(기능 불변) vs 재공학(기능/구조 확장) / 레이먼(Lehman)의 법칙
```
- 필수 키워드: 소프트웨어 유지보수 · 3R · 역공학(Reverse Engineering) · 재공학(Re-engineering) · 재사용(Reuse) · 수정/적응/완전/예방 유지보수 · 리팩토링
- 기출: 133회 1교시 11번: "소프트웨어 유지보수 향상 및 비용절감을 위한 3R을 설명하시오." → Ⅰ~Ⅵ

## 한 줄 본질
- 소프트웨어 배포 후 설계 문서 유실과 스파게티 코드 누적으로 인해 전체 IT 예산의 80%가 단순 유지보수에 잠식되는 레거시 병목 → 기존 시스템 자산으로부터 지식을 추출(역공학)하고, 구조를 현대화(재공학)하여, 재활용(재사용)함으로써 유지보수 생산성을 극대화하는 공학 체계 / 분석 오차 위험

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  소프트웨어 유지보수 4대 유형 및 3R 유기적 관계         |

|  [ 유지보수 4대 분류 (수 - 적 - 완 - 예) ]                              |

|  3. 완전 유지보수 (Perfective, 50%) : 사용자 요구 반영 기능 개선 (최다) |
|  4. 예방 유지보수 (Preventive, 5%)  : 미래 오류 방지를 위한 선제적 개선|
|                                                                         |
|  [ 유지보수 비용 절감을 위한 3R 프레임워크 ]                            |
|                                                                         |
|         [ 상위 설계 / 아키텍처 모델 ] <──────재공학──────┐              |
|                     ▲                                    │              |
|                     │ 역공학 (Reverse)                   v              |
|         [ 레거시 소스코드 / 바이너리 ] ──재사용(Reuse)──> [ 신규 시스템 ]|
|                                                                         |
|    * 역공학: 구현물로부터 설계/요구사항 정보 추출 (코드 -> 설계)         |
|    * 재공학: 역공학 산출물을 바탕으로 현대적 구조로 재구축 (설계 -> 구현) |
|    * 재사용: 검증된 기존 모듈/컴포넌트를 신규 시스템에 조립 활용        |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 역공학(Reverse Engineering): 기존 소스코드나 실행 바이너리를 분석하여 유실된 데이터 모델, 비즈니스 규칙, 아키텍처 설계를 거꾸로 추출·복원하는 공학 활동
- 재공학(Re-engineering): 역공학을 통해 복원된 설계를 기반으로, 비즈니스 가치를 높이고 유지보수성을 극대화하기 위해 시스템을 새로운 기술 스택이나 구조로 재구축하는 활동

## 핵심 통찰
- 일반적인 통념과 달리 유지보수 업무에서 "버그 수정(수정 유지보수)"이 차지하는 비중은 20%에 불과하며, 실제 공수의 절반 이상(50%)은 비즈니스 환경 변화에 맞춘 기능 추가 및 성능 개선인 "완전 유지보수(Perfective Maintenance)"에 투입됨
- 레거시 시스템을 버리고 무조건 처음부터 다시 짜는(Scratch) 빅뱅 재개발은 70% 이상 실패하므로, 기존 코드의 검증된 비즈니스 규칙을 역공학으로 추출한 뒤 단계적으로 재공학하는 3R 접근법이 훨씬 안전하고 경제적임
- 리먼(Lehman)의 소프트웨어 진화 법칙에 따르면, "지속적으로 변화하지 않는 프로그램은 도태되고(제1법칙), 진화할수록 복잡도가 증가하여 구조 개선(재공학)을 하지 않으면 붕괴된다(제2법칙)"는 공학적 필연이 존재함

## 딸려 나오는 하위 토픽

| 하위 토픽 | 상위 구조 속 위치 | 한 줄 (정의 → 메커니즘 → 구분축) |
|---|---|---|
| 역공학(Reverse Engineering) | Ⅲ 3R 체계 / 설계 복원 | 이미 구현되어 운영 중인 소스코드나 바이너리로부터 데이터 모델, 제어 흐름, 비즈니스 규칙 등 상위 설계를 거꾸로 추출·문서화하는 활동 (코드 기반 상위 설계 및 아키텍처 복원) |
| 재공학(Re-engineering) | Ⅲ 3R 체계 / 현대화 재구축 | 역공학으로 추출된 설계 자산을 기반으로 유지보수성, 성능, 확장성을 극대화하기 위해 시스템을 새로운 아키텍처나 현대적 플랫폼으로 재구성·재구현하는 활동 (단순 기능 불변 리팩토링 vs 아키텍처 및 플랫폼 현대화) |

## 이웃 토픽과 구분
- 리팩토링(Refactoring) vs 재공학(Re-engineering): 리팩토링 = 외부 동작(기능)은 전혀 바꾸지 않고 내부 소스코드 구조만 개선하는 미시적 활동 / 재공학 = 플랫폼 변경, 아키텍처 전환, 기능 확장까지 포함하는 거시적 시스템 갱신 활동

## 문제·원인·대책
- 적용 상황: 20년 된 금융 계정계 COBOL 레거시 코어 시스템 현대화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 원개발자 전원 퇴사 및 설계 문서 부재로 사소한 금리 정책 변경에도 시스템 전체 마비 | 문서화 결여 및 주먹구구식 패치 누적으로 시스템 가시성(Visibility) 상실 | 정적 역공학 도구를 활용한 COBOL 코드 분석 및 비즈니스 룰/ERD 자동 복원 | 업무 로직 100% 자산화 및 파악 기간 80% 단축 |
| 레거시 재구축 시 신규 언어로 바닥부터 다시 짜다가 100억 예산 초과 및 일정 파탄 | 기존 레거시 시스템에 내재된 수만 가지 엣지 예외 케이스를 간과한 빅뱅 재개발 | 3R 기법에 기반하여 핵심 모듈을 자바 컴포넌트로 재사용/재공학하는 단계적 전환 | 재개발 리스크 최소화 및 기존 비즈니스 자산 보존 |

## 이렇게 출제된다
- 제133회 1교시 11번: "소프트웨어 유지보수 향상 및 비용절감을 위한 3R을 설명하시오." → 요구 포인트: 소프트웨어 유지보수 문제점 + 3R(역공학, 재공학, 재사용)의 개념, 필요성 및 상호 관계

## 내 의견
- [빅뱅 재구축 유혹을 이겨내는 스트랭글러(Strangler) 재공학 전략] 운영 중인 대규모 시스템을 멈추고 전면 재개발하려다 납기 지연으로 실패하는 사례 빈발 → 나라면: 3R 철학에 따라 레거시 핵심 인터페이스를 역공학으로 명세화하고, 신규 비즈니스 기능부터 클라우드 네이티브 마이크로서비스로 하나씩 떼어내어 교체해 나가는 점진적 스트랭글러 패턴 기반 재공학 거버넌스 추진
