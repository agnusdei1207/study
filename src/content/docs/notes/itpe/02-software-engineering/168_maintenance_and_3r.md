## 연관 키워드

- 유지보수(Maintenance), 역공학(Reverse Engineering), 재공학(Re-engineering), 재사용(Reuse)
- ISO/IEC 14764 유지보수 4대 유형, 스트랭글러 피그 패턴(Strangler Fig Pattern), 레거시 시스템 현대화

## Ⅰ. SW 유지보수 및 3R의 개요

- 핵심 요약 : 인도 후 소프트웨어(SW, Software)의 생명주기를 연장하는 유지보수와, 이를 실천하는 역공학·재공학·재사용의 3R 체계.
- 개념 : **유지보수** (Maintenance)는 인도된 소프트웨어의 결함 수정, 운영 환경 적응, 기능 추가를 수행하는 활동이며, 이를 공학적으로 실천하는 핵심 기술이 **역공학** (Reverse Engineering), **재공학** (Re-engineering), **재사용** (Reuse)의 3R 체계.
- 배경 및 필요성 : 소프트웨어 생명주기 비용 중 유지보수 단계의 비중이 크고, 레만(Lehman)의 소프트웨어 진화 법칙이 설명하듯 시간이 지나면 시스템이 노후화하고 구조가 흐트러지므로 체계적 대응이 필요.
- 주요 목적 : **ISO/IEC 14764** 기준의 유지보수 4대 유형을 관리해 레거시 자산의 가치를 지속적으로 확보.

## Ⅱ. 유지보수 3R의 특징

- 핵심 요약 : 코드로부터 설계를 복원하고, 기능을 유지한 채 구조를 개선하며, 검증된 자산을 재활용하는 순환적 공학 체계.

1. 역공학 : 소스코드에서 상위 설계와 아키텍처를 복원 → 문서가 없는 시스템의 이해도 향상.
2. 재공학 : 기능을 유지하면서 내부 구조를 리팩토링하거나 마이그레이션 → 변경 위험을 줄인 구조 개선.
3. 재사용 : 검증된 컴포넌트와 테스트 자산을 신규 개발에 활용 → 생산성과 품질의 동시 확보.
4. 4대 유형 관리 : 수정, 적응, 완전, 예방 유지보수를 구분해 공수와 목표를 나누어 관리.
5. 점진적 현대화 : 시스템 전체를 한 번에 바꾸지 않고 단계적으로 전환 → 운영 중단 위험 감소.

## Ⅲ. 유지보수 3R의 구조 (흐름)

- 핵심 요약 : 레거시 코드에서 출발해 역공학, 재공학, 재사용으로 이어지며 자산이 축적되는 순환 흐름.
- 역공학 단계에서는 소스코드로부터 DFD(Data Flow Diagram), ERD(Entity-Relationship Diagram), 클래스 구조를 복원해 설계 문서를 확보.

```text
[ 레거시 소스 코드 ]
          ↓ 1. 역공학
[ 설계 복원: 흐름도·ERD·클래스 ]
          ↓ 2. 재공학
[ 구조 개선·리팩토링·현대화 ]
          ↓ 3. 재사용
[ 검증된 컴포넌트 자산 ]
```

- 역공학(Reverse Engineering) : 구현된 소스코드, 실행 파일, DB(Database) 스키마에서 상위 수준의 분석·설계 명세와 아키텍처를 복원하는 기법.
- 재공학(Re-engineering) : 기능은 유지하면서 시스템 내부 구조를 변경·개선하는 작업으로, 리팩토링과 마이그레이션을 포함.
- 재사용(Reuse) : 검증된 지식, 아키텍처, 컴포넌트, 테스트 스위트를 신규 소프트웨어 구축에 다시 쓰는 기법.

## Ⅳ. ISO/IEC 14764 소프트웨어 유지보수 4대 유형 비교

- 핵심 요약 : 발생 원인과 목적이 다른 네 가지 유지보수 유형을 구분해야 공수 계획과 품질 목표를 맞출 수 있음.

```text
[ ISO/IEC 14764 유지보수 4대 유형 ]
  1. 완전 (Perfective) : 신규 요구 반영
  2. 적응 (Adaptive) : 환경 변화 대응
  3. 수정 (Corrective) : 운영 중 결함 수정
  4. 예방 (Preventive) : 잠재 결함 사전 제거
```

| 유형 | 발생 원인과 목적 | 대표 예시 |
| --- | --- | --- |
| 완전 유지보수 (Perfective) | 사용자 요구 반영과 성능·기능 개선 | 보고서 기능 추가, 처리 속도 개선 |
| 적응 유지보수 (Adaptive) | OS, 하드웨어, DB 등 외부 환경 변화 대응 | 운영체제 업그레이드 대응, 클라우드 이전 |
| 수정 유지보수 (Corrective) | 운영 중 발견된 결함의 수정 | 계산 오류 긴급 패치, 크래시 디버깅 |
| 예방 유지보수 (Preventive) | 잠재 결함의 사전 예방과 유지보수성 향상 | 기술 부채 상환 리팩토링, 코드 정리 |

## Ⅴ. SW 유지보수 3R의 장점과 한계

- 핵심 요약 : 레거시 자산 가치 연장과 비용 절감의 장점, 암묵지 소실과 빅뱅 전환 실패, 재사용 결합도의 한계.

1. 장점 : 문서가 유실된 레거시 시스템의 이해도를 높임.
2. 장점 : 전면 재개발보다 낮은 비용으로 구조 개선과 품질 향상을 얻음.
3. 장점 : 검증된 자산 재활용으로 개발 생산성과 품질을 함께 확보.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 역공학 시 암묵지 소실 | 비즈니스 규칙의 설계 배경과 예외 처리 맥락은 코드만으로 복원하기 어려움 | LLM(Large Language Model) 기반 코드 분석 보조, 도메인 전문가(SME, Subject Matter Expert) 인터뷰, 운영 로그 분석 | 문서화된 규칙 비율 |
| 빅뱅 재공학의 실패 위험 | 일거에 재개발하면 일정과 예산이 초과되고 숨은 버그가 누락 | 모듈 단위의 점진적 분리와 병렬 운영 검증 | 병렬 운영 불일치 건수 |
| 재사용 컴포넌트의 결합도 심화 | 무분별한 복사 재사용은 의존성 충돌과 패치 누락을 낳음 | DDD(Domain-Driven Design) 기반 경계 설정, 공유 라이브러리 배포, API 계약 체결 | 공유 컴포넌트 변경 영향 범위 |

## Ⅵ. 레거시 현대화 및 지속 가능한 진화를 위한 기술사적 제언

- 핵심 요약 : 스트랭글러 피그 기반 점진적 재공학과 역공학 도구를 통한 자산 가시화의 선행.

- 레거시 시스템을 맡은 개발 조직은 **스트랭글러 피그 패턴** (Strangler Fig Pattern)을 적용해, 외곽의 독립 도메인부터 마이크로서비스나 모듈로 하나씩 떼어 옮기는 방식으로 재공학을 진행해야 한다. 기존 시스템을 유지한 채 새 기능이 자리를 잡아 가므로 전환 실패의 피해가 작다.
- 문서가 유실된 시스템을 맡은 경우에는 정적 분석과 아키텍처 검사 도구로 실제 의존성 맵과 사용되지 않는 코드를 먼저 파악한 뒤 재공학 범위를 정하는 것이 바람직하다. 설계 문서가 없는 상태에서 무리하게 구조를 바꾸는 일을 막는 절차다.

## Ⅶ. 결론

- 핵심 요약 : 3R 체계는 레거시 자산의 생명주기를 연장하면서 현대화를 이루는 유지보수 공학의 핵심.
- 시사점 : 빅뱅 전환을 피하고, 점진적 패턴과 도구 기반 가시화, 도메인 지식의 보전을 병행해야 유지보수 성숙도가 높아짐.
