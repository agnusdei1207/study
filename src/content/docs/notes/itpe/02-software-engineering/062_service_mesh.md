## 연관 키워드

- 서비스 메시(Service Mesh), 데이터 플레인, 컨트롤 플레인, 사이드카 프록시
- 트래픽 관리, mTLS, 관측성

## Ⅰ. 서비스 메시의 개요

- 핵심 요약 : 서비스 메시는 서비스 간 통신의 제어·보안·관측을 애플리케이션 코드에서 분리한 인프라 계층.
- 개념 : 마이크로서비스 간 호출의 라우팅·보안·계측을 애플리케이션 코드에서 분리해 전용 프록시 계층에서 수행하는 구조가 **서비스 메시**(Service Mesh)임.
- 배경 및 필요성 : 서비스 수·네트워크 경로가 늘어나면 재시도·인증·추적 로직이 서비스마다 중복 구현되고 언어·팀별 정책 편차가 커지는 문제.
- 주요 목적 : 서비스 간 통신의 신뢰성·보안·운영 일관성 확보를 통한 분산 시스템의 확장성·관리성 향상.

## Ⅱ. 서비스 메시의 특징 및 장점

- 핵심 요약 : 프록시 두 계층의 역할 분담이 코드 독립성·중앙 정책·암호화·계측의 이득으로 연결되는 구조.

1. 데이터 플레인 : 실제 호출을 중계하는 **데이터 플레인**(data plane)이 **트래픽 관리**(traffic management, 라우팅·재시도·타임아웃 제어)와 암호화 정책을 실행 → 애플리케이션 코드의 통신 부담 제거.
2. 사이드카 프록시 : 각 서비스 옆에 별도 프로세스로 배치되는 **사이드카 프록시**(sidecar proxy) → 언어·프레임워크와 무관한 동일 정책 적용.
3. 컨트롤 플레인 : 정책·구성을 프록시에 일괄 배포하는 **컨트롤 플레인**(control plane) → 통신 정책의 중앙 집중 관리.
4. mTLS 보안 : 서비스 신원 인증과 전송 암호화를 **mTLS**(mutual TLS, 양방향 인증 기반 전송 암호화)로 수행 → 서비스 간 제로 트러스트 통신.
5. 관측성 : 호출 지연·오류율·트래픽을 프록시에서 일관 계측하는 **관측성**(observability) → 병목·장애 원인 추적.

## Ⅲ. 서비스 메시의 구조 (흐름)

- 핵심 요약 : 정책을 배포하는 관리 계층과 호출을 중계하는 실행 계층의 분리, 그리고 프록시를 통과하는 호출 흐름.

```text
[ 서비스 메시 두 계층 ]

컨트롤 플레인
   정책·인증서·라우팅 구성 관리
        ↓ 구성 배포
데이터 플레인
   각 서비스의 사이드카 프록시 집합
        ↓ 정책 실행
재시도·타임아웃·mTLS·지표 수집
```

```text
[ 서비스 간 호출 흐름 ]

서비스 A가 서비스 B 호출 요청
   ↓ 자신의 사이드카 프록시로 전달
프록시 A : 라우팅·재시도·암호화 적용
   ↓ mTLS로 암호화된 전송
프록시 B : 신원 검증·정책 확인 후 전달
   ↓
서비스 B가 요청 처리
   ↓
양쪽 프록시가 지표·추적 정보 기록
```

## Ⅳ. 서비스 메시와 애플리케이션 내장 통신 방식의 비교

- 핵심 요약 : 재시도·인증 로직을 각 서비스 코드에 두는 내장 방식과 달리, 서비스 메시는 통신 제어를 프록시 인프라 계층으로 옮김.

| 비교 축 | 서비스 메시 | 애플리케이션 내장 통신 방식 |
| --- | --- | --- |
| 구현 위치 | 프록시 인프라 계층 | 각 서비스의 코드·라이브러리 |
| 정책 일관성 | 중앙 정책의 전 서비스 적용 | 언어·팀별 구현 편차 |
| 언어 종속성 | 언어와 무관 | 프레임워크별 대응 필요 |
| 자원 비용 | 프록시 추가 홉·자원 오버헤드 | 추가 인프라 없음 |
| 도입 부담 | 플랫폼 운영 역량 필요 | 초기 구현이 단순 |

## Ⅴ. 서비스 메시의 한계와 방안

- 핵심 요약 : 프록시 오버헤드·정책 오구성·자체 장애 영역·조기 도입을 성능 시험, 단계별 배포, 도입 심사로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 프록시 오버헤드 | 모든 호출에 추가 홉·자원 → 지연·비용 증가 | 핵심 경로 성능 시험, 선택적 적용, 자원 한도 설정 | p95 지연, 프록시 자원 사용률 |
| 정책·인증서 오구성 | 과도한 차단·만료 미갱신 → 서비스 장애 | 단계별 정책 배포, 만료·회전 자동화 | 정책 오류 건수, 인증서 잔여 기간 |
| 메시 자체 장애 영역 | 통신 계층이 새 장애 지점·운영 부담이 되는 상태 | 장애 격리·우회 구성, 운영자 훈련 | 프록시 오류율, 변경 실패율 |
| 조기 전면 도입 | 서비스 수가 적을 때 이득 미미 | 통신 정책 공통화 가치가 비용을 넘는 시점 판단 | 적용 서비스 비율 |

## Ⅵ. 서비스 메시 적용에 대한 제언

- 핵심 요약 : 플랫폼 조직은 도입 기준·정책 소유 체계를 정의해 애플리케이션 책임과 인프라 정책 책임을 분리하는 거버넌스로 확산.
- 도입 기준 : 플랫폼 조직이 서비스 수·정책 공통화 가치·운영 역량을 판단 요소로 하는 도입 심사 절차 운영.
- 책임 분리 : 애플리케이션 팀은 업무 로직에, 플랫폼 조직은 메시 정책·인증서·버전 관리에 대한 소관을 명문화.
- 표준 확산 : 트래픽 정책·보안 기준을 조직 표준 템플릿으로 배포하고 신규 서비스의 기본 구성으로 채택.

## Ⅶ. 결론

- 핵심 요약 : 서비스 메시는 분산 통신을 코드에서 인프라 계층으로 옮겨 표준화하는 수단.
- 프록시·정책의 복잡성 통제가 전제될 때 신뢰성·보안·관측의 이득이 실현.
