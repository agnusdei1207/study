## 핵심 용어
- 정방향 추적성(Forward Traceability): 요구사항으로부터 출발하여 설계, 소스코드, 테스트 케이스로 내려가며, 발주자의 모든 요구가 최종 구현물에 100% 반영되었는지(완전성)를 검증하는 방향
- 역방향 추적성(Backward Traceability): 테스트 케이스나 소스코드로부터 상위 요구사항으로 거슬러 올라가며, 요구사항에 없는 불필요한 기능이나 근거 없는 코드가 임의로 삽입되지 않았는지(순수성)를 검증하는 방향

## 핵심 통찰
- RTM은 단순한 감리 제출용 문서가 아니라, "요구사항 변경 요청(CR)이 들어왔을 때 소스코드 어디를 고치고 어떤 테스트 케이스를 다시 돌려야 하는가"를 알려주는 가장 강력한 영향도 분석(Impact Analysis) 나침반임
- 설계나 테스트와 연결되지 않은 요구사항은 "구현 누락 결함"이며, 상위 요구사항이 없는 코드나 테스트는 "고아 산출물(Orphan Artifact)"이자 불필요한 비용 낭비임
- 사람이 수천 행의 엑셀 RTM을 수작업으로 업데이트하는 것은 100% 최신화 실패로 이어지므로, Git 커밋 메시지나 Jira 티켓에 요구사항 ID를 명시하여 자동 렌더링되게 해야 함

## 이웃 토픽과 구분
- 요구사항 추적표(RTM) vs 요구사항 명세서(SRS): SRS = 요구사항 자체의 내용, 속성, 제약조건을 상세히 기술한 문서 / RTM = SRS에 명시된 요구사항이 하위 산출물들과 어떻게 연결되어 있는지 관계를 나타낸 매핑 표

## 문제·원인·대책
- 적용 상황: 수만 개 요구사항이 존재하는 금융 차세대 시스템 구축 프로젝트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 인수 테스트 단계에서 핵심 결제 취소 기능이 전혀 구현되지 않은 사실 뒤늦게 발견 | 요구사항 분석 후 설계 단계에서 누락되었으나 추적 체계 부재로 인지 못함 | 단계별 RTM 정방향 추적성 전수 점검 및 미매핑 항목 품질 게이트 차단 | 요구사항 구현 누락률 0% 달성 |
| 고객의 요구사항 1건 변경 시 시스템 전체에서 수정해야 할 모듈 파악에 2주 소요 | 요구사항과 코드 모듈 간 매핑 데이터가 없어 담당자 기억에 의존 | ALM 도구(Jira-Confluence-Bitbucket) 기반 역방향 RTM 자동화 연동 | 변경 영향도 분석 시간 2주에서 1시간 이내로 단축 |
