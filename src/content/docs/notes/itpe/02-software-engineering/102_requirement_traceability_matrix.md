## 30초 인출

- 본질: **요구사항 추적표(RTM: Requirement Traceability Matrix)** 는 소프트웨어 개발 생애주기 전반에 걸쳐 요구사항 정의서와 시스템 아키텍처 설계서, 소스코드 컴포넌트, 테스트 케이스(TC), 인수 검사 기준 간의 유기적 매핑 관계를 격자(Matrix) 형태로 시각화하여 관리하는 핵심 형상 통제 문서
- 메커니즘: 요구사항 식별자(Req-ID) 부여 → 정방향 추적(Forward: 요구 $\rightarrow$ 설계 $\rightarrow$ 코드 $\rightarrow$ 테스트)으로 구현 누락 검출 → 역방향 추적(Backward: 코드/테스트 $\rightarrow$ 요구)으로 골드 플레이팅(Gold Plating) 배제 → 요구 변경 시 영향도 분석(Impact Analysis) 수행
- 통찰: 수작업 엑셀 기반 RTM은 프로젝트 후반부로 갈수록 소스코드 변경과의 동기화가 깨져 문서 파편화가 발생하므로 Jira, Git, ALM 도구와 연계하여 커밋 해시 및 자동화 테스트 케이스와 실시간 양방향 링크되는 동적 RTM 체계 구축이 필수적임

<details>
<summary>핵심 용어</summary>

- **정방향 추적성 (Forward Traceability)** : 사용자 요구사항에서 출발하여 하위 산출물(설계서, 코드, 테스트)로의 진행 관계를 추적하여 구현 누락(Missing Feature)을 방지하는 방향
- **역방향 추적성 (Backward Traceability)** : 구현된 코드나 테스트 케이스에서 상위 요구사항으로 거슬러 올라가 요구사항에 없는 불필요한 과잉 기능(Gold Plating)을 식별하는 방향
- **영향도 분석 (Impact Analysis)** : 특정 요구사항이 변경되거나 삭제될 때 영향을 받는 설계 클래스, DB 테이블, 테스트 케이스의 범위를 사전에 산출하는 활동
- **골드 플레이팅 (Gold Plating)** : 고객이 공식적으로 요청하지 않은 기능을 개발자가 임의로 추가하여 일정 지연과 결함 위험을 초래하는 현상
- **수평적 추적성 (Horizontal Traceability)** : 동일 라이프사이클 단계 내에서 서브시스템 간, 혹은 모듈 간의 인터페이스 및 데이터 연동 추적성

</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 프로젝트 품질 및 형상 관리를 위한 요구사항 추적표(RTM)의 개념과 구성요소를 설명하고, 정방향(Forward) 및 역방향(Backward) 추적 메커니즘, 요구사항 변경 시 영향도 분석(Impact Analysis) 절차 및 ALM 연계 자동화 방안을 제시하시오.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 요구사항의 도출부터 설계, 소스코드 구현, 테스트 실행 및 릴리스에 이르는 전 생애주기 산출물 간의 연결 고리를 매핑하여 관리하는 표 |
| 목적 | 요구사항 구현 누락 방지, 스코프 크립(Scope Creep) 및 골드 플레이팅 차단, 요구 변경 시 수정 영향 범위의 신속·정확한 파악 |

## Ⅱ. 핵심 특징

단순한 문서 목록이 아닌 시스템의 완전성(Completeness)과 일관성(Consistency)을 보증하는 공학적 기준선.

| 핵심 속성 | 관리 메커니즘 | 실무 기대 효과 |
|---|---|---|
| **양방향 추적성 (Bi-directional)** | 정방향(Forward) 추적과 역방향(Backward) 추적을 동시에 지원 | 구현 누락 제로화 및 근거 없는 과잉 개발 원천 차단 |
| **고유 식별성 (Uniqueness)** | 모든 요구사항과 단위 산출물에 계층적 고유 ID(REQ-001 등) 부여 | 이해관계자 간 모호성 배제 및 형상 항목과의 1:1 바인딩 |
| **영향도 정량화 (Impact Analysis)** | 요구 변경 발생 시 수정 대상이 되는 설계, 코드, 테스트 케이스 즉시 도출 | 변경 비용 및 프로젝트 일정 재산정의 객관적 근거 제공 |
| **감리 및 검수 기준 (Auditability)** | 공공 감리 및 CMMI/SPICE 심사 시 요구사항 충족 증빙 자료로 활용 | 공식 발주처 인수 시험(UAT) 합격 기준선 확립 |

## Ⅲ. 체계·프로세스

RTM의 양방향 추적 메커니즘 및 변경 영향도 분석 아키텍처.

```text
[요구사항 추적표(RTM) 양방향 추적 체계]
[요구사항 정의]            [아키텍처 설계]            [소스코드 구현]            [테스트 케이스]
   (Requirements)              (Architecture)             (Source Code)              (Test Cases)
  +─────────────────+        +─────────────────+        +─────────────────+        +─────────────────+
  | REQ-001         | ────>  | ARCH-MOD-101    | ────>  | OrderService.java| ────> | TC-INT-501      |
  | (장바구니 결제) |        | (주문 결제 모듈)|        | (결제 로직 구현)|        | (결제 정상 흐름)|
  +─────────────────+        +─────────────────+        +─────────────────+        +─────────────────+
           │                          │                          │                          │
           ▼                          ▼                          ▼                          ▼
  ═══════════════════════════════════════════════════════════════════════════════════════════════════════
  [ 정방향 추적 (Forward Traceability) : 요구사항 누락 방지 (설계 및 구현 여부 100% 검증) ] ──────────>
  <────────── [ 역방향 추적 (Backward Traceability) : 골드 플레이팅 방지 (구현의 요구사항 근거 확인) ]
  ═══════════════════════════════════════════════════════════════════════════════════════════════════════
           ▲
           │ 요구사항 변경 발생! (Change Request)
           ▼
  [영향도 분석 (Impact Analysis)] ──> [ARCH-MOD-101 수정] ──> [OrderService.java 수정] ──> [TC-501 재시험]
```

- **RTM 변경 관리 4단계 프로세스**:
  1. **변경 요청 접수(Change Request)** : 고객의 요구 변경 요청서가 인입되면 대상 요구사항 식별자(REQ-001) 특정.
  2. **영향도 범위 분석(Impact Analysis)** : RTM 매트릭스를 탐색하여 연결된 설계서, API 명세, 소스코드 파일, 테스트 케이스 리스트 추출.
  3. **공수 산정 및 CCB 승인** : 추출된 영향 범위를 바탕으로 공수와 일정을 재산정하고 형상통제위원회(CCB)의 공식 승인 획득.
  4. **산출물 동기화 및 재시험** : 코드 수정 완료 후 RTM에 매핑된 회귀 테스트 케이스를 자동 재실행하고 RTM 버전 업데이트.

## Ⅳ. 종류·비교

#### 정방향 추적 vs 역방향 추적 상세 비교

| 비교 항목 | 정방향 추적 (Forward Traceability) | 역방향 추적 (Backward Traceability) |
|---|---|---|
| **추적 방향** | **요구사항 $\rightarrow$ 설계 $\rightarrow$ 소스코드 $\rightarrow$ 테스트** | **테스트 $\rightarrow$ 소스코드 $\rightarrow$ 설계 $\rightarrow$ 요구사항** |
| **핵심 목적** | 모든 요구사항이 누락 없이 실제 구현되었는가? | 현재 작성된 코드가 승인된 요구에 근거하는가? |
| **방지 결함** | **기능 누락 (Missing Requirements)** | **골드 플레이팅 (Gold Plating), 무단 스코프 확장** |
| **수행 시점** | 개발 진행 단계, 중간 점검, 개발 완료 시점 | 코드 리뷰, 인수 시험, 소프트웨어 감리 시점 |
| **미달 시 조치** | 미구현 기능에 대한 긴급 구현 및 일정 보정 | 불필요한 코드 및 테스트 제거, 요구사항 역반영 |

#### 수작업 엑셀 RTM vs ALM 도구 연동 동적 RTM 비교

| 구분 | 스프레드시트 RTM (Excel 기반) | ALM 연동 동적 RTM (Jira/GitLab 기반) |
|---|---|---|
| **작성 및 유지 방식** | PM/PL이 수작업으로 셀 매핑 및 갱신 | Git Commit 태그(`fixes #REQ-101`)로 자동 링크 |
| **동기화 신뢰도** | 코드 변경 시 문서 업데이트 누락 빈발 (낡은 문서화) | PR 머지 및 CI 파이프라인과 실시간 100% 동기화 |
| **영향도 분석 속도** | 수동 검색으로 수 시간~수일 소요 | 종속성 그래프 클릭 한 번으로 즉시 시각화 |
| **적합한 프로젝트** | 소규모 단기 프로젝트, 문서 중심 폭포수 사업 | 대규모 엔터프라이즈, 애자일/DevOps 프로젝트 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 프로젝트 후반부 촉박한 일정 속에서 소스코드는 수정되었으나 엑셀 RTM이 방치되는 문서 파편화 | GitLab/Jira 등의 ALM 도구를 도입하여 커밋 메시지에 Req-ID 기재를 강제(Pre-commit Hook)하는 자동화 구축 |
| 비기능 요구사항(성능, 보안, 가용성 등)은 특정 단일 클래스로 매핑되지 않아 추적성 단절 | 비기능 요구는 아키텍처 전술(Tactic) 및 부하 테스트 스크립트와 1:N으로 다대다 매핑하여 관리 |
| 요구사항 세분화 수준(Granularity)이 불균일하여 추적 매트릭스가 지나치게 비대해지는 현상 | 에픽(Epic)-기능(Feature)-유스케이스(Use-Case)의 계층적 ID 체계를 수립하여 일관된 단위로 표준화 |

## Ⅵ. 제언

RTM은 단순 검수용 보고서가 아닌 소프트웨어 아키텍처 거버넌스의 척도이므로, 요구사항 식별자부터 Git 커밋, SonarQube 정적 분석, 테스트 케이스까지 완전히 자동 연결되는 ALM 기반 End-to-End 추적 파이프라인을 구축할 필요가 있음.

```text
[요구사항 (Jira Issue)] ──> [설계 (Figma/Enterprise Architect)] ──> [Git 커밋 (#REQ-ID)] ──> [CI/CD 자동 테스트]
      (REQ-101 정의)                 (인터페이스 매핑)                 (소스코드 연동)             (추적성 100% 검증)
```

| 관리 영역 | 핵심 엔지니어링 실천법 | 통제 지표 |
|---|---|---|
| **추적성 커버리지** | 모든 요구사항 ID에 1개 이상의 테스트 케이스 매핑 | 요구사항 추적성 커버리지(Requirements Coverage) 100% |
| **변경 통제 연계** | CCB 승인 없이 PR 머지 불가 정책 수립 | 무단 코드 변경(Unapproved Changes) 0건 달성 |
| **검수 인수 증빙** | 공공 발주처 UAT 시험 시 RTM 매트릭스 기반 합격 증빙 | 최종 납품 감리 적합 판정 및 인수 지연 제로 |
