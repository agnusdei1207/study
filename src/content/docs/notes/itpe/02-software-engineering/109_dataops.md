---

## 30초 인출

- 본질: **데이터옵스(DataOps)** 는 애자일(Agile) 개발 방식의 신속한 반복, 데브옵스(DevOps)의 지속적 CI/CD 파이프라인 자동화, 린(Lean) 제조의 통계적 공정 제어(SPC) 원리를 데이터 분석 엔지니어링에 결합하여 데이터 사일로를 제거하고 엔드투엔드 데이터 품질과 딜리버리 속도를 극대화하는 협업 프레임워크
- 메커니즘: 데이터 계약(Data Contract) 체결 → 소스코드 및 데이터 파이프라인 CI/CD 자동화 → 실시간 데이터 품질 테스트(Great Expectations) → 데이터 계보(Lineage) 추적 → 메타데이터 기반 자동 관측성(Data Observability) 확보
- 통찰: 단순 데이터 엔지니어링 코드의 배포 자동화만으로는 입력 원천 데이터의 불시 스키마 변형이나 결측치 유입을 막을 수 없으므로 데이터 생산자-소비자 간 데이터 계약과 실시간 품질 게이트(Quality Gate) 및 계보 기반 영향 분석 체계를 필수적으로 구축할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **데이터 계약 (Data Contract)** : 데이터 생산자(애플리케이션 개발팀)와 데이터 소비자(분석가/엔지니어) 간에 합의된 스키마, SLA, 의미론, 품질 기준 명세
- **데이터 계보 (Data Lineage)** : 데이터가 생성된 원천 소스부터 가공, 변환(ETL), 최종 BI 대시보드 및 AI 모델에 이르기까지의 전체 흐름 경로와 종속성 지도
- **데이터 관측성 (Data Observability)** : 신선도(Freshness), 분포(Distribution), 볼륨(Volume), 스키마(Schema), 계보(Lineage)의 5대 기둥 기반 데이터 상태 추적
- **통계적 공정 제어 (SPC: Statistical Process Control)** : 데이터 파이프라인 각 단계에서 데이터의 이상 징후를 통계적 임계치로 실시간 탐지하는 린 품질 기법
- **OpenLineage** : 데이터 파이프라인 실행 중 발생하는 계보 메타데이터를 수집·표준화하기 위한 리눅스 재단 오픈소스 표준 규격

</details>

## 2~4교시 예상문제 (25점)

> 엔터프라이즈 데이터 파이프라인의 신뢰성 확보를 위한 데이터옵스(DataOps)의 개념과 등장 배경을 설명하고, DevOps와의 비교, 데이터옵스 3대 핵심 기둥(데이터 계약, 품질 검증, 데이터 계보) 및 데이터 관측성(Data Observability) 확보 전략을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 데이터 관리자, 데이터 엔지니어, 데이터 과학자가 협업하여 데이터 파이프라인의 개발, 배포, 운영을 자동화하고 데이터 품질을 지속 보증하는 문화 및 기술 실천법 |
| 목적 | 데이터 사일로 해소, 데이터 분석 사이클 타임 단축, 데이터 다운타임(Data Downtime) 극소화, 비즈니스 의사결정의 신뢰도 제고 |

## Ⅱ. 핵심 특징

순수 소프트웨어 코드뿐만 아니라 파이프라인을 통과하는 '데이터 자체의 상태와 품질'을 제어.

| 핵심 영역 | 메커니즘 | 실무 적용 방안 |
|---|---|---|
| **코드와 데이터의 이중 검증** | 파이프라인 로직(SQL, Python) 검증과 인입 데이터(값, 스키마) 검증 병행 | dbt 테스트 및 Great Expectations 품질 단언문 가동 |
| **데이터 계약 (Data Contract)** | API 스펙처럼 데이터 생산자-소비자 간 명시적 스키마/SLA 합의 | JSON Schema, Protobuf 기반 스키마 레지스트리 강제 |
| **엔드투엔드 계보 추적** | 컬럼(Column) 단위까지 데이터의 변환 및 전파 경로 실시간 시각화 | OpenLineage 및 Marquez 연동을 통한 파이프라인 추적 |
| **통계적 공정 제어 (SPC)** | 데이터 건수 급감이나 이상치 발생 시 파이프라인을 자동 정지하고 알람 | 데이터 볼륨/신선도 모니터링 기반 슬랙(Slack) 즉시 경보 |

## Ⅲ. 체계·프로세스

DataOps의 이중 피드백 파이프라인 및 데이터 품질 통제 체계.

```text
+---------------------------------------------------------------------------------------------------------+
|                                    DataOps 아키텍처 및 데이터 품질 통제 체계                             |
+---------------------------------------------------------------------------------------------------------+
                                                                                                           
  [1] 데이터 계약 (Data Contract) ──> 스키마 정의 및 SLA 합의                                              
           │                                                                                               
           ▼                                                                                               
  [2] 데이터 파이프라인 실행 (CI/CD)                                                                        
  +─────────────────────────────────────────────────────────────────────────────────────────────────────+  
  |  원천 데이터 인입 ──> [사전 품질 검사] ──> [데이터 변환 & 적재] ──> [사후 품질 검사] ──> 데이터 마트  |  
  |  (RDB / Kafka / S3)    (Schema/Null 검증)  (Airflow / dbt / Spark)   (비즈니스 룰 검증)   (Snowflake)   |  
  +───────────────────────────────┬────────────────────────────────────────────┬────────────────────────+  
                                  │                                            │                           
                                  ▼ (검증 실패 시)                             ▼ (정상 통과)               
                     +──────────────────────────+                 +──────────────────────────+             
                     | 데이터 격리 (Quarantine) |                 | OpenLineage 계보 메타 등록|             
                     | 파이프라인 중단 & 슬랙 알람|                | BI 대시보드 / AI 모델 서빙|             
                     +──────────────────────────+                 +──────────────────────────+             
                                  │                                            │                           
                                  └─────────────────────┬──────────────────────┘                           
                                                        ▼                                                  
  [3] 데이터 관측성 (Data Observability) 모니터링 (신선도, 볼륨, 스키마 드리프트 추적)                     
```

- **DataOps 핵심 운영 4단계 프로세스**:
  1. **데이터 계약 체결 및 버전화** : 생산자와 소비자가 데이터 스키마와 허용 오차 범위를 Git 기반 계약 파일로 명문화.
  2. **지속적 통합(CI) 파이프라인** : 변환 로직 변경 시 스테이징 환경에서 샘플 데이터를 기반으로 회귀 단위 테스트 수행.
  3. **실시간 런타임 품질 게이트** : ETL 구동 중 원천 데이터의 결측치, 중복, 타입 불일치 감지 시 즉시 격리(Quarantine) 레인으로 우회.
  4. **데이터 계보 기반 사후 분석** : 장애 발생 시 OpenLineage 메타데이터를 역추적하여 영향을 받는 하류(Downstream) 보고서 파악.

## Ⅳ. 종류·비교

#### DevOps vs DataOps 상세 비교

| 비교 항목 | DevOps (데브옵스) | DataOps (데이터옵스) |
|---|---|---|
| **핵심 통제 대상** | 소프트웨어 소스코드 및 인프라 환경 | **소스코드 + 지속적으로 변화하는 원시 데이터(Data)** |
| **결함 발생 원인** | 코드 버그, 환경 불일치, 컴파일 오류 | **원천 데이터 스키마 변경, 누락값, 이상치 유입** |
| **파이프라인 결과물**| 불변 컨테이너 이미지, 실행 바이너리 | 비즈니스 인사이트, BI 대시보드, ML 모델 데이터셋 |
| **품질 테스트 기법** | 단위 테스트, 통합 테스트, 시스템 테스트 | **스키마 테스트, 데이터 신선도, 분포 이상 탐지(SPC)** |
| **대표 도구** | Git, Jenkins, Docker, Kubernetes | Airflow, dbt, Great Expectations, OpenLineage |

#### 데이터 관측성(Data Observability) 5대 기둥

| 관측성 기둥 | 핵심 모니터링 내용 | 장애 발생 예시 |
|---|---|---|
| **신선도 (Freshness)** | 데이터가 예상된 주기에 맞춰 적시에 갱신되는가? | 일일 정산 배치가 새벽 4시에 완료되지 않고 지연됨 |
| **분포 (Distribution)** | 데이터 값의 통계적 분포(평균, 백분위수)가 정상인가? | 사용자 나이 컬럼에 음수나 999 등 이상치 급증 |
| **볼륨 (Volume)** | 인입되는 레코드 건수가 예상된 범위 내에 있는가? | 평소 하루 100만 건 유입되던 로그가 1만 건으로 급감 |
| **스키마 (Schema)** | 테이블 필드 구조와 데이터 타입이 변경되지 않았는가? | 생산자 측에서 사전 공지 없이 컬럼명을 임의 변경 |
| **계보 (Lineage)** | 데이터의 업스트림 원천과 다운스트림 종속성은 무엇인가? | 원천 DB 장애 시 어떤 경영진 대시보드가 영향받는지 추적 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 파이프라인 상류(Upstream) 개발팀의 일방적 DB 스키마 수정으로 인한 다운스트림 데이터 파이프라인 연쇄 붕괴 | 데이터 계약(Data Contract) 검증을 원천 앱 배포 CI 파이프라인에 통합하여 호환성 깨짐 시 배포 차단 |
| 수천 개의 데이터 테이블에 일일이 품질 검사 규칙을 수작업 작성하는 데 따르는 관리 공수 과다 | 기계학습 기반의 데이터 프로파일링 도구를 도입하여 비정상 수치(Outlier)를 통계적으로 자동 탐지 |
| 대규모 빅데이터 파이프라인에서 매 단계 전수 검사 수행 시 발생하는 ETL 런타임 지연 | 핵심 결제/정산 지표는 전수 검사하고 비정형 로그는 통계적 샘플링(Sampling) 검증으로 분원화 |

## Ⅵ. 제언

데이터옵스는 단순 기술 스택이 아닌 조직적 협업 문화이므로, 도메인 중심의 데이터 메시(Data Mesh) 아키텍처와 연계하여 데이터 제품(Data Product) 단위의 계약 기반 자율 운영 체계를 확립할 필요가 있음.

```text
[데이터 생산자 (도메인팀)] ──> [데이터 계약 및 자동 테스트] ──> [중앙 DataOps 플랫폼] ──> [신뢰도 100% 데이터 소비]
  (Data as a Product 책임)        (dbt + Great Expectations)     (OpenLineage 관측성)        (BI 대시보드 & MLOps)
```

| 관리 영역 | 권장 실천 지침 | 핵심 관리 지표 |
|---|---|---|
| **계약 거버넌스** | Git 기반 스키마 레지스트리 연계 및 버전 태깅 의무화 | 스키마 드리프트로 인한 장애 발생률 0건 |
| **품질 자동화** | dbt 파이프라인 내 유일성(Unique), Not Null 단언문 기본 적용 | 데이터 다운타임(Data Downtime) 월 1시간 이내 단축 |
| **계보 가시성** | 전사 데이터 파이프라인의 OpenLineage 메타데이터 100% 수집 | 원천 장애 발생 시 영향 범위 파악 시간 10분 이내 달성 |
