## 연관 키워드

- 소프트웨어 제품라인(SPL, Software Product Line), 도메인 공학(Domain Engineering), 응용 공학(Application Engineering)
- 핵심 자산(Core Asset), 공통성(Commonality), 가변성(Variability), 피처 모델링(Feature Modeling), 바인딩 시점(Binding Time)

## Ⅰ. 소프트웨어 제품라인(SPL)의 개요

- 핵심 요약 : 공통성과 가변성을 분석해 핵심 자산을 미리 구축하고, 이를 조합해 파생 제품을 빠르게 만드는 제품군 개발 체계.
- 개념 : 같은 도메인에서 공유되는 **공통성** (Commonality)과 제품마다 다른 **가변성** (Variability)을 분석하여, 재사용 가능한 **핵심 자산** (Core Asset)을 사전에 만들고 이를 조합해 파생 제품군을 생산하는 **소프트웨어 제품라인** (SPL, Software Product Line) 공학 체계.
- 배경 및 필요성 : 제품마다 코드를 처음부터 새로 작성하는 개별 개발은 생산성이 낮고, 코드를 복사해 붙여 넣는 재사용은 유지보수를 무너뜨린다. 비용과 출시 기간(Time-to-Market)을 함께 줄일 방법이 필요하다.
- 주요 목적 : 핵심 자산의 체계적 재사용으로 제품군의 개발 비용을 줄이고, 납기를 단축하며, 품질을 일관되게 유지하는 것.

## Ⅱ. 소프트웨어 제품라인(SPL)의 특징 및 장점

- 핵심 요약 : 두 갈래의 공학 프로세스, 핵심 자산 중심의 재사용, 피처 모델링 기반의 가변성 관리가 결합된 구조.

1. **도메인 공학** (Domain Engineering)과 **응용 공학** (Application Engineering)의 2중 프로세스 : 공통 자산을 만드는 쪽과 자산을 조립해 제품을 만드는 쪽을 나누어 순환 운영 → 역할 분리로 재사용 효율 확보.
2. 핵심 자산 중심 : 아키텍처, 프레임워크, 컴포넌트 라이브러리를 사전에 구축 → 제품마다 같은 기능을 새로 만드는 중복 제거.
3. **피처 모델링** (Feature Modeling, 제품군의 공통 기능과 선택 기능을 특징(feature) 단위로 형식화하는 방법) : 필수, 선택, 대안, 다중 선택 관계를 모델로 관리 → 제품 구성 규칙의 명확화.
4. **바인딩 시점** (Binding Time) 다양화 : 가변 요소를 컴파일, 빌드, 실행 중 어느 시점에 결정할지 고름 → 성능과 유연성의 균형 조정.

## Ⅲ. 소프트웨어 제품라인(SPL)의 구조 (흐름)

- 핵심 요약 : 도메인 공학에서 핵심 자산을 구축하고 응용 공학에서 이를 조립해 파생 제품을 생산하는 순환 구조.

```text
[ 1. 도메인 공학 ]
 도메인 분석: 공통성·가변성 식별
 핵심 자산 개발: 아키텍처, 컴포넌트
       ↓ 핵심 자산 저장소 제공
[ 2. 응용 공학 ]
 요구사항 수집, 피처 모델 바인딩
 핵심 자산 조립 + 차별화 컴포넌트
       ↓
[ 파생 제품 A / B / C ]
       ↓ 피드백
  (도메인 공학으로 회귀)
```

- 피처 모델의 가변성 유형 : 제품군의 특징을 나무 구조로 나누어 제품마다 포함 여부를 정한다.

```text
[ 피처 모델 ]
  - 필수 피처: 모든 제품에 포함
  - 선택 피처: 제품에 따라 포함 여부 결정
  - 대안 피처: 하나만 선택
  - 다중 선택 피처: 여럿을 선택 가능
```

## Ⅳ. 개별 개발과 소프트웨어 제품라인(SPL)의 비교

- 핵심 요약 : 일회성 개발 대신 핵심 자산 재사용 기반의 제품군 대량 생산 체계로 전환하는 것이 핵심 차이다.

| 비교 항목 | 개별 개발(One-off Development) | 소프트웨어 제품라인(SPL) |
| --- | --- | --- |
| 개발 방식 | 제품마다 처음부터 독립 개발 | 핵심 자산 재사용과 가변성 조립 |
| 개발 비용 | 반복 개발로 비용이 누적 | 초기 투자 후 파생 제품 비용 절감 |
| 납기 | 제품마다 전체 개발 기간 소요 | 핵심 자산 조립으로 납기 단축 |
| 품질 일관성 | 제품별 품질 편차 발생 | 공통 아키텍처와 컴포넌트로 일관성 확보 |
| 유지보수 | 복사-붙여넣기로 유지보수 파탄 | 핵심 자산 집중 관리로 효율적 유지보수 |
| 적용 도메인 | 단일 제품, 특수 목적 | 스마트폰 펌웨어, 차량 인포테인먼트, 스마트 TV 등 제품군 |

## Ⅴ. 소프트웨어 제품라인(SPL)의 한계와 방안

- 핵심 요약 : 비용 절감과 납기 단축의 장점에 비해, 초기 투자 부담, 가변성 관리 실패, 조직 사일로가 한계로 따른다.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 초기 투자 부담 | 공통성을 추출하고 재사용 프레임워크를 설계하는 데 높은 비용과 긴 기간이 필요 | 2~3개 제품을 대상으로 한 파일럿 기반 경량 SPL을 먼저 도입하고 자산을 단계적으로 확대 | 자산 재사용률, 투자 회수 기간 |
| 가변성 관리 실패 | 가변성 포인트가 통제 없이 늘어 조건문이 남발되고 스파게티 코드화 | 피처 모델링 전용 도구 도입, 전략 패턴과 플러그인 아키텍처로 바인딩 방식 표준화 | 가변성 포인트 수, 조건 분기 밀도 |
| 조직 사일로 | 핵심 자산팀과 제품팀의 우선순위가 달라 자산을 포크(Fork)해 독자 수정하는 안티패턴 발생 | 두 조직 간 순환 근무, 핵심 자산 변경 관리 위원회(CAB, Change Advisory Board) 운영, 공통 자산 기여 보상 | 자산 포크 건수, 자산 기여 건수 |

## Ⅵ. 소프트웨어 제품라인(SPL)에 대한 기술사적 제언

- 핵심 요약 : 핵심 자산 거버넌스를 강화하고 같은 원리를 클라우드 웹 환경으로 넓혀 제도의 실효성을 높이는 방향.
- 핵심 자산은 제품 개발 팀이 아니라 전담 플랫폼 조직이 관리하도록 분리하고, 응용 팀은 자산을 직접 고치지 않고 정해진 확장 지점을 통해서만 쓰도록 버전 관리 규칙을 세워야 한다.
- 과거 임베디드 중심이던 제품라인 개념을 클라우드와 SaaS 환경으로 넓혀, 고객사별 차이를 코드 분기 대신 기능 플래그(Feature Flag)와 공용 UI 컴포넌트로 실행 중에 제공하는 구조를 검토할 만하다.

## Ⅶ. 결론

- 핵심 요약 : SPL은 핵심 자산 재사용 기반의 제품군 개발 체계로, 거버넌스와 단계적 도입이 성공의 관건.
- 시사점 : 도메인 공학과 응용 공학의 2중 프로세스, 피처 모델링을 통한 가변성 관리, 자산 거버넌스를 병행해야 제품라인의 효과가 지속된다.
