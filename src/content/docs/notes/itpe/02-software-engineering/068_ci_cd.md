## 연관 키워드

- CI/CD, 지속적 통합(CI), 지속적 전달(Continuous Delivery)
- 지속적 배포(Continuous Deployment), 빌드 파이프라인, 아티팩트, 롤백, 기능 플래그

## Ⅰ. CI/CD의 개요

- 핵심 요약 : CI/CD는 변경 통합부터 배포까지 자동 파이프라인으로 검증·전달해 릴리스 속도와 안전성을 동시에 확보하는 실천 체계.
- 개념 : 코드 변경을 자주 통합하고 빌드 파이프라인으로 시험·배포를 자동 수행하는 소프트웨어 공급 실천 (**CI/CD**, Continuous Integration / Continuous Delivery / Continuous Deployment).
- 배경 및 필요성 : 장기 브랜치·수동 릴리스는 통합 충돌과 배포 위험을 릴리스 직전에 집중시켜 결함 발견 지연·출시 부담 확대.
- 주요 목적 : 작은 변경의 빠르고 안전한 사용자 전달로 피드백 주기 단축·제품 가치 실현 앞당김.

## Ⅱ. CI/CD의 특징 및 장점

- 핵심 요약 : 통합·전달·배포의 단계적 자동화와 단일 산출물 승격이 빠른 피드백과 재현 가능한 릴리스로 연결.

1. **지속적 통합** (CI, Continuous Integration) : 개발자 변경을 공유 브랜치에 자주 병합하고 빌드·시험을 자동 실행 → 통합 충돌·결함의 조기 발견.
2. **지속적 전달** (Continuous Delivery) : 검증된 **아티팩트** (Artifact, 빌드 결과물)를 상시 배포 가능 상태로 유지 → 운영 반영 시점을 승인으로 자유롭게 결정.
3. **지속적 배포** (Continuous Deployment) : 모든 게이트 통과 변경을 자동 운영 반영 → 승인 지연 없는 가치 전달.
4. 단일 아티팩트 승격 : 동일 산출물을 환경별로 승격 → 환경 간 차이로 인한 오류 제거·재현성 확보.
5. 빠른 피드백·복구 : 모니터링·**기능 플래그** (Feature Flag)·**롤백** (Rollback) 체계 → 장애 영향 시간 최소화.

## Ⅲ. CI/CD의 구조 (흐름)

- 핵심 요약 : 커밋부터 운영 감시까지 게이트를 거치는 파이프라인과, 승인 게이트 유무로 구분되는 통합·전달·배포의 단계 구조.

```text
CI/CD 파이프라인 흐름

코드 커밋 (공유 브랜치)
   ↓
빌드·정적 분석
   ↓
단위·통합 시험
   ↓
보안·품질 게이트
   ↓
아티팩트 저장·버전화
   ↓
스테이징 배포·검증
   ↓
승인 또는 자동 운영 배포
   ↓
모니터링·롤백
```

```text
CI와 CD 단계 구분

지속적 통합 : 변경 통합·빌드·시험
      ↓
지속적 전달 : 배포 가능 상태 유지
      ↓  [승인 게이트 존재]
지속적 배포 : 운영 자동 반영
      (승인 게이트 없음)
```

## Ⅳ. CI/CD 파이프라인과 수동 빌드·배포의 비교

- 핵심 요약 : 수동 절차가 위험과 작업을 릴리스 직전에 집중시키는 반면, 파이프라인은 통합 직후부터 검증·기록을 분산 수행.

| 비교 축 | CI/CD 파이프라인 | 수동 빌드·배포 |
| --- | --- | --- |
| 통합 주기 | 커밋 단위 상시 통합 | 릴리스 단위 집중 통합 |
| 빌드·시험 | 자동 실행·표준 절차 | 담당자 수작업·편차 발생 |
| 배포 판정 | 게이트 기준 자동 판정 | 경험·승인 문서 의존 |
| 오류 발견 시점 | 통합 직후 | 릴리스 직전·운영 중 |
| 기록·감사 | 로그·아티팩트 자동 축적 | 수작업 기록·누락 위험 |

- 선택 기준 : 자동 검증·관측·복구 역량이 뒷받침될 때 자동 배포, 규제·변경 관리 요구가 큰 서비스는 지속적 전달 수준 유지.

## Ⅴ. CI/CD의 한계와 방안

- 핵심 요약 : 검증 축소·파이프라인 장애·공급망 오염·복구 미준비를 게이트·코드화·서명 검증·단계적 노출로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 검증 축소로 인한 결함 유출 | 속도 우선으로 시험 생략 → 장애의 빠른 확산 | 위험 기반 시험·보안 게이트·점진 배포 | 변경 실패율 |
| 파이프라인 자체 장애 | 파이프라인 오류가 전 개발 흐름 지연 | 파이프라인 코드화·버전 관리·자체 모니터링 | 파이프라인 가동률 |
| 공급망 오염 | 의존성·빌드 도구 오염이 배포로 확산 | 의존성 검사·SBOM(Software Bill of Materials)·서명 검증 | 취약 의존성 수 |
| 복구 준비 미흡 | 오류 배포의 장시간 고객 영향 | 자동 롤백·기능 플래그·단계적 노출 | 평균 복구 시간(MTTR, Mean Time To Recovery) |

## Ⅵ. CI/CD 적용에 대한 기술사적 제언

- 핵심 요약 : 개발·보안·운영 조직은 CI/CD를 공유 플랫폼과 위험 기준으로 운영하는 플랫폼 엔지니어링 체계로 확산.
- 플랫폼화 : 플랫폼 팀이 표준 파이프라인 템플릿·게이트 정책을 제공해 팀별 편차 제거.
- 보안 통합 : 보안 검사를 개발 초기 단계로 이동(Shift-Left)해 게이트의 형식화 방지.
- 위험 기준 : 서비스 중요도에 따라 지속적 전달과 지속적 배포의 적용 수준을 구분한 정책 운영.

## Ⅶ. 결론

- 핵심 요약 : CI/CD는 작고 검증된 변경의 지속 통합·전달로 소프트웨어 공급 체계를 자동화하는 실천.
- 파이프라인 속도가 아니라 검증·복구 역량이 CI/CD 성숙도의 판단 기준.
