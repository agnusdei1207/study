## 연관 키워드

- Monkey Test, 몽키 테스트, 무작위 테스트, Random Testing
- Dumb Monkey, Smart Monkey, Fuzzing, Grammar-based Fuzzing
- ANR, Crash, 메모리 릭, 레이스 컨디션
- Chaos Engineering, 시드(Seed), 테스트 오라클(Test Oracle), 불변식(Invariant)

## Ⅰ. 몽키 테스트(Monkey Test)의 개요

- 핵심 요약 : 무작위 이벤트를 대량 주입하여 크래시·메모리 릭·예외 처리 누락을 검출하는 확률적 동적 테스트 기법.
- 개념 : 사전에 정의된 테스트 케이스나 시나리오 없이 무작위 데이터와 예측 불가능한 사용자 입력 이벤트를 대량으로 주입해 크래시, 메모리 릭, 무한 루프, 예외 처리 누락을 찾아내는 **몽키 테스트** (Monkey Test, 무작위 이벤트 주입 테스트).
- 배경 및 필요성 : 개발자와 QA(Quality Assurance, 품질 보증) 엔지니어는 예상 가능한 정상·비정상 시나리오에 치우치기 쉬우나, 실제 사용자는 기기를 떨어뜨리거나 버튼을 연타하는 등 돌발 행동을 하므로 이에 대한 회복탄력성 검증이 필요.
- 주요 목적 : 예외 처리 누락 탐지, 크래시와 **ANR** (Application Not Responding, 응답 없음) 검출, 회복탄력성(Resilience) 검증.
- 대표 도구 : **Android UI/Application Exerciser Monkey** (안드로이드 UI 무작위 이벤트 도구)와 넷플릭스의 **Chaos Monkey** (무작위 서버 인스턴스 종료 도구).

## Ⅱ. 몽키 테스트(Monkey Test)의 특징 및 장점

- 핵심 요약 : 무작위성에 따른 비결정론적 실행과 덤·스마트 몽키의 분류가 탐색 범위와 결함 검출력으로 이어지는 방식.

1. **덤 몽키** (Dumb Monkey, 도메인 지식 없이 무작위 이벤트만 주입하는 방식) : 화면과 내부 상태를 알지 못하므로 구현이 간단 → 예상치 못한 크래시 탐지에 유리.
2. **스마트 몽키** (Smart Monkey, 화면 구조를 인지하는 방식) : DOM(Document Object Model, 문서 객체 모델)이나 뷰 계층을 읽어 유효한 입력 범위 내에서 이벤트를 조합 → 깊은 화면 전이와 복합 결함 탐지.
3. 비결정론적 실행 : 난수에 따라 매 실행마다 다른 이벤트 순서가 생성 → 사람이 설계하지 못한 조합 탐색.
4. 장시간 무인 실행 : 도구만 가동하면 야간에도 테스트가 진행 → 인력 투입 없이 탐색 시간 확보.
5. 오라클 한계 : 크래시와 ANR은 감지하나 비즈니스 논리 오류는 감지하지 못함 → 별도의 **테스트 오라클** (Test Oracle, 실행 결과의 정상 여부를 판정하는 기준) 필요.

## Ⅲ. 몽키 테스트(Monkey Test)의 구조 (흐름)

- 핵심 요약 : 무작위 이벤트 발생기에서 덤·스마트 몽키로 분기하고, 런타임 이상을 감지·기록하는 구조.

```text
[ 몽키 테스트 구성 구조 ]

무작위 이벤트 발생기 (Random Event Generator)
              ↓
  덤 몽키 : 화면과 상태를 모름
  스마트 몽키 : UI 상태를 인지
              ↓
런타임 이상 감지 (크래시·ANR·메모리 릭)
```

```text
[ 몽키 테스트 수행 흐름 ]

테스트 대상 실행
        ↓
무작위 이벤트 대량 주입
        ↓
크래시·ANR·메모리 릭 감지
        ↓
시드와 이벤트 로그 보관
        ↓
결함 재현 및 수정
```

## Ⅳ. 전통적 테스트와 몽키 테스트의 비교

- 핵심 요약 : 명세 기반의 결정론적 테스트와 무작위 기반의 비결정론적 테스트가 재현성과 검출 결함에서 상호 보완적인 관계.

| 비교 항목 | 전통적 명세 기반 테스트 | 몽키 테스트 (Monkey Testing) |
| --- | --- | --- |
| 테스트 케이스 설계 | SRS(Software Requirements Specification, 소프트웨어 요구사항 명세서) 기반으로 입력과 기대 결과를 작성 | 사전에 작성된 테스트 케이스 없이 무작위 생성 |
| 수행 방식 | 정해진 순서대로 결정론적 실행 | 난수 기반의 비결정론적 실행 |
| 결함 재현성 | 동일 절차로 재현이 용이 | 시드(Seed) 값이 없으면 재현이 매우 어려움 |
| 주요 검출 결함 | 비즈니스 로직 오류, 인터페이스 규격 불일치 | 메모리 누수, 레이스 컨디션, 크래시, ANR |
| 수행 비용 | 케이스 작성과 유지보수 비용이 높음 | 도구 가동만으로 장시간 무인 테스트 가능 |

## Ⅴ. 몽키 테스트(Monkey Test)의 한계와 방안

- 핵심 요약 : 저비용 장시간 탐색과 회복탄력성 검증이라는 장점 이면에 재현성, 얕은 탐색, 오라클 부재의 한계가 존재.
- 장점 : 케이스 작성 없이 장시간 무인 실행이 가능하고, 인지적 편향을 넘어 예상치 못한 크래시를 찾으며, 극단적 사용 행동에 대한 회복탄력성을 검증.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 크래시 재현 난제 | 수많은 무작위 이벤트 중 결함 유발 시퀀스를 특정하기 어려움 | 난수 시드 고정과 이벤트 타임스탬프 로깅, 크래시 직전 이벤트를 재생하는 기록 도구 연동 | 크래시 재현 성공률 |
| **얕은 탐색** (Shallow Testing) | 덤 몽키는 로그인 창과 폼 유효성 검사에서 막혀 핵심 로직에 도달하지 못함 | 스마트 몽키 도입, 입력 문법을 따르는 **문법 기반 퍼징** (Grammar-based Fuzzing) 결합 | 화면 도달률, 코드 커버리지 |
| 테스트 오라클 부재 | 크래시나 먹통은 감지되지만 잘못된 계산이나 데이터 정합성 붕괴는 감지되지 않음 | **불변식** (Invariant) 검사기 연동, 메모리 누수 탐지기와 DB 트랜잭션 모니터링을 결합한 통합 오라클 구성 | 불변식 위반 건수 |

## Ⅵ. 몽키 테스트(Monkey Test)에 대한 기술사적 제언

- 핵심 요약 : 시드 로깅으로 재현성을 확보하고, 카오스 엔지니어링으로 확장해 운영 수준의 복원력을 검증할 것.
- 재현 가능한 몽키 테스트 체계 : 크래시가 발생하면 원인을 수정할 수 있도록 실행에 쓰인 난수 시드와 이벤트 타임라인을 반드시 보관하고, 같은 시드로 동일한 이벤트 시퀀스를 다시 실행할 수 있도록 테스트 환경을 설계하는 것이 우선이다.
- 카오스 엔지니어링으로의 확장 : 단말 UI 수준의 무작위 주입 개념을 백엔드 인프라로 넓혀, 운영에 가까운 환경에서 컨테이너 인스턴스를 무작위로 중단시키는 **카오스 엔지니어링** (Chaos Engineering, 장애를 의도적으로 주입해 복원력을 검증하는 방법론)을 CI(Continuous Integration, 지속적 통합) 파이프라인과 연계하면 분산 시스템의 자가 복구 능력을 상시 점검할 수 있다.

## Ⅶ. 결론

- 핵심 요약 : 몽키 테스트는 무작위 이벤트 주입으로 크래시와 회복탄력성을 검증하는 확률적 테스트 기법.
- 사전 시나리오 없이 대량의 무작위 이벤트로 예외 처리 누락을 찾아내는 경험 기반 기법이며, 재현성과 오라클 보강이 함께 갖춰질 때 실질적인 품질 보증 효과를 얻는다.
