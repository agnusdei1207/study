## 한 줄 본질
- 테스터가 미리 계획한 시나리오 경로만 검증하여 예측하지 못한 사용자 난타나 극단적 입력 오류를 놓치는 병목 → 사전 테스트 케이스 없이 원숭이가 키보드를 두드리듯 무작위 이벤트를 무차별 주입하여 비정상 종료를 유발하는 테스팅 기법 / 결함 발생 시 재현 경로 추적의 어려움

## 핵심 용어
- 덤 몽키(Dumb Monkey): 시스템에 대한 아무런 지식이나 사전 정보 없이 완전히 무작위로 화면을 클릭하거나 키를 입력하는 초보적 테스팅 방식
- 스마트 몽키(Smart Monkey): 시스템의 상태 전이 모델이나 화면 구조(DOM)를 인식하여, 각 화면의 컴포넌트에 맞는 이벤트를 지능적으로 주입하는 테스팅 방식

## 핵심 통찰
- 몽키 테스트의 가장 치명적인 약점은 "버그를 찾아서 앱이 죽었는데, 어떤 순서로 눌러서 죽었는지 재현할 수 없다"는 점이므로, 반드시 의사 난수 생성기의 "시드(Seed) 값"과 이벤트 히스토리를 로그로 보존해야 함
- 모바일 환경에서는 사용자의 주머니 속 오작동, 연타, 화면 회전 중 백그라운드 전환 등 비정형 조작이 일상적이므로 구글 안드로이드의 `Monkey` 도구 테스트가 필수 릴리스 관문으로 쓰임
- 넷플릭스의 카오스 몽키(Chaos Monkey)는 이 개념을 UI 입력에서 인프라 레벨로 확장하여, 운영 환경의 서버 인스턴스를 무작위로 강제 종료시킴으로써 시스템 자가 치유 능력을 검증함

## 이웃 토픽과 구분
- 몽키 테스트 vs 고릴라 테스트(Gorilla Test): 몽키 = 전체 시스템을 대상으로 무작위 입력 주입 / 고릴라 = 시스템의 특정 단일 모듈을 지정하여 파괴될 때까지 집중적인 부하와 입력을 가하는 테스팅

## 문제·원인·대책
- 적용 상황: 모바일 배달 앱 신규 결제 화면 릴리스 전 안정성 검증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 팝업창에서 뒤로가기 버튼과 결제 승인을 동시에 난타할 때 앱 비정상 종료 | 일반 기능 테스트 케이스에는 복수 버튼 동시 클릭 등 비정상 사용자 입력 패턴 미반영 | 모바일 스마트 몽키 테스트를 CI 야간 빌드에 편성하여 수십만 회 무작위 터치 수행 | 레이스 컨디션 및 멀티스레드 크래시 사전 식별 |
| 몽키 테스트 중 NullPointerException 크래시가 발생했으나 재현 절차를 몰라 미해결 방치 | 무작위 이벤트 주입 시 실행 시드(Seed)와 타임스탬프 로그가 저장되지 않음 | 실행 시드 고정 및 이벤트 캡처 리플레이 도구(Replay Framework) 도입 | 버그 100% 결정론적 재현 및 디버깅 지원 |
