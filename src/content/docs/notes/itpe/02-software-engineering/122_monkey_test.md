## Ⅰ. 몽키 테스트의 개요

- 개념 : **몽키 테스트** (Monkey Test) 란 원숭이가 키보드를 무작위로 두드리는 것처럼, 시스템에 대해 사전 정의된 테스트 케이스나 시나리오 없이 무작위(Random) 데이터, 예측 불가능한 사용자 제스처, 무작위 이벤트를 대량으로 무차별 주입하여 시스템의 크래시(Crash), 메모리 릭, 무한 루프, 예외 처리 누락을 검출하는 경험 기반·확률적 동적 테스팅 기법.
- 배경 및 필요성 : 개발자나 QA 엔지니어는 자신의 인지적 편향으로 인해 '예상 가능한 정상/비정상 시나리오'만을 테스트하기 쉬우나, 실제 최종 사용자는 기기를 떨어뜨리거나 버튼을 광속 연타하는 등 극단적인 돌발 행동을 하므로 이에 대한 회복탄력성 검증 필수.
- 대표 솔루션 : **Android UI/Application Exerciser Monkey**와 **Chaos Monkey** (넷플릭스)

## Ⅱ. 몽키 테스트의 유형 분류 및 동작 아키텍처

```text
                 [ 무작위 이벤트 발생기 (Random Event Generator) ]
                  - 화면 터치, 드래그, 핀치, 텍스트 무작위 입력, 볼륨 키 조작
                                      │
         ┌────────────────────────────┴────────────────────────────┐
         ▼                                                         ▼
   [ 덤 몽키 (Dumb Monkey) ]                                [ 스마트 몽키 (Smart Monkey) ]
   - 시스템 내부 상태 및 화면 전혀 모름                    - 현재 UI 상태와 데이터 모델 인지
   - 순수 무작위 좌표 난타 ($100\%$ Random)                - 유효 상태 내에서 무작위성 부여
   - 크래시 및 시스템 다운 검출 탁월                       - 깊은 화면 전이 및 복합 결함 탐지
                                      │
                                      ▼
                      [ 시스템 런타임 이상 감지 및 로깅 ]
                       - ANR (Application Not Responding)
                       - NullPointerException 및 OutOfMemoryError
```

- **덤 몽키** (Dumb Monkey) : 시스템에 대한 아무런 도메인 지식 없이 순수 무작위 이벤트를 초당 수십 회 이상 난사. 구현이 매우 간단하고 예상치 못한 크래시 탐지에 탁월.
- **스마트 몽키** (Smart Monkey) : 현재 애플리케이션의 화면 구조(DOM/View 계층)와 데이터 흐름을 인지하여, 클릭 가능한 버튼에 우선순위를 부여하고 유효한 입력 범위 내에서 무작위 데이터를 조합 주입.

## Ⅲ. 전통적 테스트와 몽키 테스트의 비교

| 비교 항목 | 전통적 명세 기반 테스트 | 몽키 테스트 (Monkey Testing) |
|---|---|---|
| 테스트 케이스 설계 | SRS 기반으로 입력값과 기대 출력값을 정밀 작성 | 사전에 작성된 테스트 케이스 없음 (순수 무작위 생성) |
| 수행 방식 | 정해진 순서와 절차대로 결정론적 실행 | 무작위 난수 기반의 비결정론적(Random) 실행 |
| 결함 재현성 (Reproducibility) | 동일 절차 수행 시 $100\%$ 결함 재현 가능 | 난수 시드(Seed) 값이 없으면 결함 재현이 극도로 난해 |
| 주요 검출 결함 | 비즈니스 로직 오류, 인터페이스 규격 불일치 | 메모리 누수, 동시성 레이스 컨디션, 크래시, ANR |
| 테스트 수행 비용 | 테스트 케이스 작성 및 유지보수 비용 높음 | 도구 실행만으로 장시간 무인 야간 테스트 가능 |

## Ⅳ. 몽키 테스트(Monkey Test)의 주요 한계점 및 해결 방안

- 무작위 입력 특성으로 인한 크래시 결함의 재현(Reproducibility) 난제 :
  - 한계점 : 수만 번의 무작위 이벤트 중 시스템이 비정상 종료되었을 때, 결함을 유발한 정확한 사용자 액션 시퀀스를 재현하기 극도로 어려움.
  - 해결 방안 : 의사 난수 생성기의 시드(Seed) 값 고정 및 이벤트 타임스탬프 기반 로깅, 크래시 발생 시 직전 N개 이벤트를 재생하는 블랙박스 레코더 연동.
- 입력 유효성 검증 계층을 통과하지 못하는 **얕은 탐색** (Shallow Testing) :
  - 한계점 : 순수 무작위 클릭/키보드 입력(Dumb Monkey)은 로그인 창, 폼 유효성 검사에서 막혀 시스템 내부의 핵심 비즈니스 로직에 도달하지 못함.
  - 해결 방안 : UI 위젯 계층 구조를 인지하는 스마트 몽키(Smart Monkey) 도입, 도메인 입력 문법을 준수하는 **문법 기반 퍼징** (Grammar-based Fuzzing) 결합.
- 테스트 오라클 부재로 인한 논리적 비기능 결함 감지 불가 :
  - 한계점 : 시스템 크래시나 먹통(ANR)은 쉽게 감지하지만, 화면에 잘못된 금액이 계산되거나 데이터베이스 정합성이 깨지는 비즈니스 논리 오류는 감지 불가.
  - 해결 방안 : **시스템 불변식** (Invariant) 검사기 연동, 몽키 테스트 수행 중 메모리 누수(LeakCanary), CPU 점유율, 비정상 DB 트랜잭션 모니터링을 결합한 통합 오라클 구성.

## Ⅴ. 모바일 및 고신뢰성 시스템 구축 시 기술사적 제언

- **의사 난수 시드** (Pseudo-Random Seed) 로깅을 통한 재현성 확보 : 몽키 테스트에서 치명적인 크래시가 발생했을 때 개발자가 원인을 수정할 수 있도록, 테스트 실행 시 사용된 난수 시드 번호(`--seed 12345`)와 이벤트 타임라인 로그를 반드시 보관하여 동일한 무작위 시퀀스를 $100\%$ 재현할 수 있는 체계 구축 필수.
- **카오스 엔지니어링** (Chaos Engineering)으로의 진화 확장 : 단말기 UI 레벨의 몽키 테스트 개념을 클라우드 백엔드 인프라로 확장하여, 운영 환경에서 컨테이너 파드를 무작위로 강제 종료시키는 Chaos Mesh, Chaos Kong을 CI 파이프라인과 연계하여 분산 시스템의 자가 치유(Self-Healing) 능력 검증.
