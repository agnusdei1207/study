지식 위치: 소프트웨어공학 → 분산 시스템 및 아키텍처 → 마이크로서비스 및 통신 → **서비스 메시(Service Mesh)**

---

## 30초 인출

- 본질: **서비스 메시(Service Mesh)** 는 마이크로서비스 간의 동적 서비스 디스커버리, 로드밸런싱, mTLS 암호화, 장애 복원력(Circuit Breaker), 분산 추적 등 네트워크 통신 기능을 애플리케이션 소스코드에서 완전히 분리하여 전담 처리하는 전용 인프라 소프트웨어 계층
- 메커니즘: 컨트롤 플레인(Control Plane)이 중앙 정책 및 TLS 인증서 관리 → xDS API로 데이터 플레인(Data Plane) 프록시에 동적 주입 → 사이드카(Envoy Proxy)가 iptables로 트래픽을 가로채 투명하게 mTLS 암호화 및 라우팅 수행
- 통찰: 파드(Pod)마다 사이드카 프록시를 배치하는 전통적 방식은 컨테이너 수백 대 확장 시 심각한 메모리 오버헤드와 홉(Hop) 지연을 유발하므로 L4 mTLS 전송 계층과 L7 애플리케이션 계층을 분리하는 앰비언트 메시(Ambient Mesh)나 eBPF 기반 무사이드카 아키텍처로의 전환이 요구됨

<details>
<summary>핵심 용어</summary>

- **데이터 플레인(Data Plane)** : 실제 서비스 간 네트워크 패킷을 가로채고, 라우팅, mTLS 암호화, 메트릭 수집을 수행하는 고성능 프록시 영역(Envoy)
- **컨트롤 플레인(Control Plane)** : 라우팅 규칙, 보안 정책, 인증서 발급 설정을 중앙에서 관리하고 데이터 플레인에 동적으로 배포하는 제어 영역(Istiod)
- **사이드카 패턴(Sidecar Pattern)** : 애플리케이션 컨테이너 변경 없이 동일 파드(Pod) 내에 별도 프록시 컨테이너를 배치하여 네트워크 통신을 위임하는 구조
- **mTLS(Mutual TLS)** : 클라이언트와 서버가 서로의 인증서를 양방향 검증하고 통신 패킷을 암호화하는 제로 트러스트 보안 프로토콜
- **앰비언트 메시(Ambient Mesh)** : 파드 내 사이드카 주입 없이 노드 단위 공유 프록시(ztunnel)와 L7 웨이포인트(Waypoint)로 계층화한 차세대 서비스 메시 모델

</details>

## 2~4교시 예상문제 (25점)

> 대규모 마이크로서비스 아키텍처(MSA)에서 서비스 메시(Service Mesh)의 도입 배경과 핵심 아키텍처(컨트롤 플레인 vs 데이터 플레인)를 설명하고, API Gateway와의 역할 분담, 사이드카 방식의 성능 한계 극복을 위한 앰비언트 메시(Ambient Mesh) 및 eBPF 적용 방안을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 마이크로서비스 간의 통신(East-West Traffic)을 안전하고 신뢰성 있게 관리하기 위해 프록시 네트워크를 통해 트래픽 제어, 보안, 관측성을 비침투적으로 제공하는 전용 인프라 계층 |
| 목적 | 비즈니스 로직과 통신 인프라 로직의 완전한 관심사 분리, 다국어(Polyglot) 환경의 일관된 보안/통신 거버넌스 확립, 제로 트러스트 보안 실현 |

## Ⅱ. 핵심 특징

애플리케이션 코드를 한 줄도 수정하지 않고 인프라 레벨에서 L4/L7 네트워크 정책을 중앙 통제.

| 핵심 기능 영역 | 세부 메커니즘 | 기술 구현체 및 프로토콜 |
|---|---|---|
| **트래픽 관리 (Traffic Management)** | 카나리 배포(동적 가중치 분할), 서비스 디스커버리, 로드밸런싱, A/B 테스팅 | Envoy Proxy, Kubernetes Service CRD |
| **제로 트러스트 보안 (Zero Trust)** | 서비스 간 mTLS 상호 인증, SPIFFE ID 기반 신원 발급, 세부 인가 정책 | Istiod (Citadel), SPIRE, X.509 인증서 |
| **장애 복원력 (Resilience)** | 타임아웃, 지수 백오프 재시도, 서킷 브레이커, 이상치 탐지(Outlier Detection) | Envoy Connection Pool, Circuit Breaker |
| **통합 관측성 (Observability)** | 분산 추적 컨텍스트 전파, L7 골든 시그널(요청수, 에러율, 지연시간) 계측 | OpenTelemetry, Jaeger, Prometheus, Kiali |

## Ⅲ. 체계·프로세스

서비스 메시의 제어 평면(Control Plane)과 데이터 평면(Data Plane) 간 상호작용 체계.

```text
[서비스 메시(Service Mesh) 아키텍처 체계]
+─────────────────────────────────────────────────────────────────────────────────────────────────────+
  |                                   컨트롤 플레인 (Control Plane : Istiod)                             |
  |                                                                                                     |
  |      [Pilot] (트래픽 라우팅 규칙)      [Citadel] (인증서 발급 & mTLS)      [Galley] (설정 유효성)     |
  +───────────────────────────────────────────────────┬─────────────────────────────────────────────────+
                                                      │ xDS gRPC API (동적 설정 동기화 & SPIFFE 발급)
                                                      ▼
  ─────────────────────────────────────────────────────────────────────────────────────────────────────────
  [ 데이터 플레인 (Data Plane) : Kubernetes Pod 내부 ]

  +─────────────────────────+                              +─────────────────────────+
  |       주문 파드 (Pod)   |                              |       결제 파드 (Pod)   |
  |                         |                              |                         |
  |  +───────────────────+  |                              |  +───────────────────+  |
  |  |  주문 서비스 컨테이너 |  |                              |  |  결제 서비스 컨테이너 |  |
  |  +─────────┬─────────+  |                              |  +─────────▲─────────+  |
  |            │ 로컬 호출  |                              |            │ 로컬 호출  |
  |            ▼ (localhost)|                              |            │ (localhost)|
  |  +───────────────────+  |   양방향 암호화 mTLS 통신     |  +───────────────────+  |
  |  |   Envoy 사이드카  |  | ═══════════════════════════> |  |   Envoy 사이드카  |  |
  |  |      (Proxy)      |  |   (East-West 내부 트래픽)    |  |      (Proxy)      |  |
  |  +───────────────────+  |                              |  +───────────────────+  |
  +────────────┬────────────+                              +────────────┬────────────+
               │                                                        │
               └───────────────────────────┬────────────────────────────┘
                                           ▼ 골든 시그널 & 추적 스팬 전송
                             +───────────────────────────+
                             |   Prometheus / Jaeger     |
                             +───────────────────────────+
```

- **서비스 메시 트래픽 처리 4단계 프로세스**:
  1. **정책 및 신원 배포** : Istiod가 쿠버네티스 CRD를 감시하여 라우팅 규칙을 생성하고, Envoy 프록시에 xDS 프로토콜로 실시간 전송하며 SPIFFE ID 인증서 주입.
  2. **트래픽 투명 가로채기** : 애플리케이션의 아웃바운드 호출을 `iptables` 규칙을 통해 로컬 Envoy 사이드카 프록시로 자동 리다이렉션.
  3. **보안 핸드셰이크 및 라우팅** : 발신 Envoy와 수신 Envoy 간 mTLS 세션을 수립하여 패킷을 암호화하고 카나리 가중치에 맞춰 최적 파드로 전송.
  4. **인바운드 복호화 및 전달** : 수신 Envoy가 트래픽을 복호화하고 인가 정책을 검증한 후, `localhost` 포트를 통해 실제 결제 컨테이너로 전달.

## Ⅳ. 종류·비교

#### API Gateway vs 서비스 메시(Service Mesh) 아키텍처 비교

| 비교 항목 | API Gateway | 서비스 메시 (Service Mesh) |
|---|---|---|
| **트래픽 관점** | **North-South (외부 클라이언트 $\rightarrow$ 내부)** | **East-West (내부 마이크로서비스 간 통신)** |
| **배치 위치** | 전체 시스템의 최외곽 경계(Ingress Edge) | 각 파드(Pod) 내부 사이드카 또는 노드 프록시 |
| **핵심 목적** | 외부 단일 진입점, 통합 인증/인가, API 과금/할당량 | 제로 트러스트 내부 암호화, 동적 라우팅, 관측성 |
| **주요 기능** | API 변환, Rate Limiting, SSL 종단, WAF | mTLS 상호인증, L7 서킷브레이커, 카나리 트래픽 분할 |
| **대표 기술** | Spring Cloud Gateway, Kong, Apigee | Istio, Linkerd, Consul Connect |

#### 사이드카(Sidecar) 방식 vs 앰비언트 메시(Ambient Mesh) 비교

| 비교 항목 | 사이드카 메시 (Sidecar Mesh) | 앰비언트 메시 (Ambient Mesh) |
|---|---|---|
| **프록시 배치** | 모든 애플리케이션 파드마다 1개씩 주입 | L4 노드 공유 데몬셋(ztunnel) + L7 웨이포인트(Waypoint) |
| **리소스 오버헤드** | 높음 (파드 수 비례 메모리 사용량 급증) | 매우 낮음 (노드당 ztunnel 1개로 mTLS 전담) |
| **업그레이드 영향** | 프록시 패치 시 모든 애플리케이션 파드 재기동 필요 | 무중단 투명 업그레이드 가능 (애플리케이션 영향 제로) |
| **프로토콜 분리** | L4 암호화와 L7 정책 처리가 단일 프록시에 결합 | L4 보안 전송(ztunnel)과 복잡한 L7 정책(Waypoint) 분리 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 파드마다 사이드카가 추가됨에 따라 메모리/CPU 낭비 및 홉(Hop) 수 증가로 지연 시간(Latency) 가중 | L4 보안 통신만 우선 적용 시 앰비언트 메시(ztunnel)를 도입하거나 Cilium eBPF로 커널 레벨 패킷 바이패스 |
| 수백 개의 마이크로서비스 확장에 따른 Istiod 컨트롤 플레인의 xDS 설정 배포 부하 및 동기화 지연 | 사이드카(Sidecar) 리소스를 정의하여 각 서비스가 필요로 하는 대상 서비스의 엔드포인트만 선별 구독(Egress 격리) |
| 복잡한 YAML 설정과 디버깅 난이도로 인한 운영 엔지니어링 학습 곡선 극대화 | Kiali 및 서비스 토폴로지 대시보드를 표준 도입하고 GitOps 기반의 배포 자동화 파이프라인 수립 |

## Ⅵ. 제언

서비스 메시는 운영 복잡도가 매우 높은 기술이므로, 초기에는 API Gateway 기반의 경계 통제에 집중하고 서비스 규모가 50개 이상으로 확장되거나 엄격한 제로 트러스트 보안 규제가 요구되는 시점에 앰비언트 메시 방식으로 단계적 도입할 필요가 있음.

```text
[소규모 MSA (1~20개)] ──> [중규모 확장 (20~50개)] ──> [대규모 엔터프라이즈 (50개 이상)]
  (API Gateway + Spring Cloud)  (선별적 사이드카 mTLS 도입)   (Ambient Mesh / eBPF 통합 인프라)
```

| 도입 단계 | 중점 관리 항목 | 성공 판단 기준 |
|---|---|---|
| **1단계: 인그레스 정립** | API Gateway를 통한 외부 보안 및 라우팅 표준화 | 외부 접근 단일 진입점 확보 및 TLS 종단 완결 |
| **2단계: L4 보안 확장** | ztunnel / eBPF 기반 노드 공유형 mTLS 전면 구축 | 서비스 간 통신 100% 암호화 및 메모리 오버헤드 5% 미만 |
| **3단계: L7 거버넌스** | 카나리 배포 및 OpenTelemetry 분산 추적 연계 | 전사 트랜잭션 추적 완성 및 카나리 롤아웃 자동화 |
