## 답안 골격
```text
[서비스 메시] ◀━━ 머리: Ⅶ 내 의견 (사이드카 프록시 리소스 오버헤드 최적화를 위한 eBPF/앰비언트 메시 도입)
 ┃
 ┣━ Ⅰ 개요 ───── MSA 서비스 간 통신(East-West)의 복잡성과 보안 위험 극복 → 전용 인프라 통신 계층
 ┣━ Ⅱ 특징 ───── 비침투적(Non-invasive) · 사이드카(Sidecar) 패턴 · mTLS 암호화 · 관측성(Observability)
 ┣━ Ⅲ 구조 ───── 데이터 플레인(Envoy Proxy, 패킷 포워딩) / 컨트롤 플레인(Istiod, 정책/인증서 주입)
 ┣━ Ⅳ 흐름 ───── 마이크로서비스 요청 발송 → 로컬 사이드카 가로채기 → mTLS 터널링 및 정책 검사 → 대상 사이드카 수신 → 앱 전달
 ┣━ Ⅴ 비교 ───── 서비스 메시(내부 서비스 간 East-West) vs API Gateway(외부 진입 North-South) vs 인앱 라이브러리(Spring Cloud)
 ┗━ Ⅵ 실무 ───── 사이드카 프록시 누적으로 인한 메모리 낭비와 네트워크 홉 지연 / eBPF 커널 기반 통신 최적화
```

## 한 줄 본질
- 수백 개 마이크로서비스 간에 타임아웃, 재시도, mTLS 암호화 로직을 애플리케이션 코드에 일일이 라이브러리로 심어 언어별 파편화가 발생하는 병목 → 모든 통신을 사이드카 프록시로 가로채 인프라 계층에서 투명하게 제어 → 소스코드 수정 없는 제로 트러스트 보안 및 관측성 달성 / 프록시 경유에 따른 CPU 소모와 레이턴시 추가

## 핵심 용어
- 사이드카 패턴(Sidecar Pattern): 오토바이 옆에 보조 탑승석(사이드카)을 붙이듯, 애플리케이션 컨테이너 변경 없이 같은 파드(Pod) 내에 별도 프록시 컨테이너를 실행하여 부가 기능을 처리하는 패턴
- 상호 TLS(mTLS, Mutual TLS): 클라이언트와 서버가 서로의 디지털 인증서를 양방향으로 상호 검증하고 전송 데이터를 엔드투엔드로 암호화하는 통신 보안 규약

## 핵심 통찰
- 서비스 메시는 Netflix Zuul이나 Spring Cloud Eureka처럼 '자바 코드 안에 라이브러리를 임베딩하던 방식'에서 벗어나, 언어(Polyglot)에 구애받지 않고 인프라 레벨로 통신 관심사를 완전히 외주화한 기술임
- 서비스 메시를 도입하면 코드 수정 단 한 줄 없이도 99:1 카나리(Canary) 카오스 배포, 트래픽 미러링, 서킷 브레이커, 분산 추적(Distributed Tracing)을 일괄 적용할 수 있음
- 그러나 1,000개 파드가 뜨면 사이드카 프록시도 1,000개 떠서 기가바이트 단위 메모리를 먹고 홉당 1~2ms 지연이 발생하므로, 최근에는 노드 레벨 프록시(Istio Ambient Mesh)나 eBPF로 진화하고 있음

## 이웃 토픽과 구분
- 서비스 메시 vs API Gateway: API Gateway = 시스템 외부의 클라이언트가 시스템 내부로 진입하는 'North-South' 트래픽 제어 / 서비스 메시 = 시스템 내부의 마이크로서비스 간에 일어나는 'East-West' 트래픽 제어

## 내 의견
- [서비스 10개도 안 되는데 유행 따라 Istio부터 띄우는 인프라 과시욕] 복잡한 분산 통신 문제가 발생하지도 않는 소규모 MSA에 서비스 메시를 얹어 엔지니어링 리소스를 인프라 디버깅에 낭비하는 주객전도 경계 → 나라면: 초기에는 쿠버네티스 표준 Service와 가벼운 API Gateway로 시작하고, 마이크로서비스 수가 50개를 넘어가며 폴리글랏 통신 보안과 분산 추적이 감당 불가능해지는 시점에 서비스 메시를 도입하는 '규모 기반 단계적 도입 전략' 수립
