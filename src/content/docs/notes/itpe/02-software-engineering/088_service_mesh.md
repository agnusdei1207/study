## Ⅰ. 서비스 메시의 개요

- **개념** : 마이크로서비스 아키텍처(MSA)에서 마이크로서비스 간의 통신(East-West 트래픽)을 안전하고 신뢰성 있게 중계하기 위해, 비즈니스 애플리케이션 코드의 수정 없이 인프라 계층에서 서비스 디스커버리, 로드밸런싱, 암호화(mTLS), 트래픽 라우팅, 관측성을 제공하는 전용 인프라 통신 계층.
- **배경 및 필요성** : 수백 개의 마이크로서비스 환경에서 각 서비스마다 통신 라이브러리(Netflix Eureka, Ribbon, Hystrix)를 애플리케이션 코드에 직접 내장할 때 발생하는 언어 종속성(Polyglot 제약) 및 프레임워크 유지보수 한계 극복.
- **핵심 패턴** : 사이드카 패턴(Sidecar Pattern), 데이터 플레인과 컨트롤 플레인의 분리.

## Ⅱ. 서비스 메시 아키텍처: 데이터 플레인과 컨트롤 플레인

```text
   ┌────────────────────────────────────────────────────────────────────────┐
   │ [ 컨트롤 플레인 (Control Plane: Istiod) ]                              │
   │  - 트래픽 라우팅 정책 배포, 인증서(CA) 발급 및 관리, 원격 측정 수집   │
   └──────────────────┬──────────────────────────────────┬──────────────────┘
                      │ (xDS 설정 동기화)                │ (xDS 설정 동기화)
                      ▼                                  ▼
   ┌──────────────────────────────────┐┌──────────────────────────────────┐
   │ [ 서비스 파드 A ]                ││ [ 서비스 파드 B ]                │
   │  ┌────────────────────────────┐  ││  ┌────────────────────────────┐  │
   │  │ 비즈니스 앱 (Service A)    │  ││  │ 비즈니스 앱 (Service B)    │  │
   │  └─────────────┬──────────────┘  ││  └─────────────▲──────────────┘  │
   │                │ (로컬 루프백)   ││                │ (로컬 루프백)   │
   │  ┌─────────────▼──────────────┐  ││  ┌─────────────┴──────────────┐  │
   │  │ 사이드카 프록시 (Envoy)    │  ││  │ 사이드카 프록시 (Envoy)    │  │
   │  └─────────────┬──────────────┘  ││  └────────────────────────────┘  │
   └────────────────┼─────────────────┘└──────────────────────────────────┘
                    │ (데이터 플레인: mTLS 암호화 통신)  ▲
                    └───────────────────────────────────┘
```

- **데이터 플레인 (Data Plane)** : 각 서비스 컨테이너 옆에 사이드카로 주입된 Envoy 프록시들이 서비스 간 오가는 모든 인/아웃바운드 네트워크 패킷을 가로채어 mTLS 암호화, 서킷 브레이킹, 메트릭 수집 수행.
- **컨트롤 플레인 (Control Plane)** : Istiod가 중앙에서 전체 네트워크 토폴로지와 라우팅 룰을 관리하고 xDS API를 통해 사이드카 프록시들에 실시간 동기화.

## Ⅲ. API Gateway와 Service Mesh의 비교

| 비교 항목 | API Gateway | Service Mesh |
|---|---|---|
| 주요 트래픽 방향 | North-South (외부 클라이언트 -> 내부 백엔드) | East-West (내부 마이크로서비스 간 통신) |
| 핵심 책임 | 인증/인가(OAuth 2.0/JWT), Rate Limiting, API 수익화 | 서비스 간 보안(mTLS), 트래픽 셰이핑, 카나리 라우팅, 관측성 |
| 배포 위치 | 시스템 외곽 경계선 (Edge Boundary) | 각 애플리케이션 파드 내부 (사이드카) |
| 대상 클라이언트 | 웹 브라우저, 모바일 앱, 외부 제휴사 시스템 | 동일 클러스터 내의 다른 마이크로서비스 인스턴스 |
| 대표 솔루션 | Kong, Spring Cloud Gateway, Apigee | Istio, Linkerd, Consul Connect, Cilium |

## Ⅳ. 엔터프라이즈 도입을 위한 기술사적 제언

- **사이드카 프록시로 인한 리소스 및 지연 오버헤드 통제** : 모든 파드에 Envoy 프록시가 배치되면서 발생하는 메모리 소비와 마이크로초 단위의 네트워크 레이턴시를 감안하여, 트래픽이 적거나 단순한 서비스는 선별 적용하고 eBPF 기반의 사이드카리스(Sidecar-less) 메시(Cilium) 도입 검토.
- **제로 트러스트(Zero Trust) 보안 아키텍처 실현** : 내부 사설망이라도 결코 신뢰하지 않는 원칙에 따라, 서비스 메시의 mTLS 자동 인증서 교환 및 인가 정책(AuthorizationPolicy)을 전면 강제하여 내부 횡적 이동(Lateral Movement) 공격 원천 방어.
