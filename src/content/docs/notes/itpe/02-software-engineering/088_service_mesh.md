## 연관 키워드
- 서비스 메시, 데이터 플레인, 컨트롤 플레인, 사이드카 프록시, 트래픽 관리, mTLS, 정책·관측성

### Ⅰ. 서비스 메시의 개요

- 핵심 요약 : 서비스 메시는 분산 서비스 간 통신을 애플리케이션 코드와 분리해 트래픽 제어·보안·관측을 공통 인프라 계층에서 제공하는 구조.
- 개념 : 분산 서비스 간 통신을 애플리케이션 코드와 분리해 트래픽 제어·보안·관측을 공통 인프라 계층에서 제공하는 구조(**서비스 메시**, Service Mesh).
- 배경 및 필요성 : 서비스 수와 네트워크 경로가 늘면 호출 재시도·인증·장애 추적 구현이 서비스마다 중복되므로 공통 통신 계층 필요.
- 주요 목적 : 마이크로서비스 간 통신의 신뢰성·보안·운영 일관성을 높여 분산 시스템의 확장성과 관리성을 확보.

### Ⅱ. 서비스 메시의 특징 및 장점

- 핵심 요약 : 데이터 플레인·컨트롤 플레인·워크로드 신원·mTLS·텔레메트리 수집.

1. 데이터 플레인 : 프록시가 서비스 호출을 중계 → 라우팅·재시도·타임아웃·암호화 정책 실행.
2. 컨트롤 플레인 : 정책과 구성 정보를 프록시에 배포 → 여러 서비스의 통신 정책을 중앙 관리.
3. 워크로드 신원·mTLS : 서비스 정체를 인증하고 전송을 암호화 → 제로 트러스트 서비스 간 통신 구현.
4. 텔레메트리 수집 : 호출 지연·오류·트래픽을 계측 → 병목·장애 원인 추적과 운영 개선.

### Ⅲ. 서비스 메시의 구조 (흐름)

- 핵심 요약 : 서비스 배포·프록시 연결 → 워크로드 신원 발급 → 컨트롤 플레인 정책 배포 → 프록시가 호출 중계·보호 → 텔레메트리 수집·정책 조정.

```text
서비스 배포·프록시 연결
   ↓
워크로드 신원 발급
   ↓
컨트롤 플레인 정책 배포
   ↓
프록시가 호출 중계·보호
   ↓
텔레메트리 수집·정책 조정
```

```text
컨트롤 플레인
정책·인증서·라우팅 구성
        ↓ 구성 배포
프록시 A ⇄ mTLS 호출 ⇄ 프록시 B
        ↓                     ↓
서비스 A                 서비스 B
        └──── 텔레메트리 ────┘
```

### Ⅳ. 서비스 메시와 다른 통신 방식 비교

- 핵심 요약 : 애플리케이션 라이브러리 방식은 통신 기능을 각 서비스 코드·SDK(Software Development Kit, 소프트웨어 개발 키트)에 구현, 사이드카 메시는 서비스 옆 프록시가 통신 정책 실행.

| 비교 대상 | 핵심 특성 | 적용·판단 기준 |
|---|---|---|
| 애플리케이션 라이브러리 방식 | 통신 기능을 각 서비스 코드·SDK에 구현 | 단순 규모·낮은 복잡도, 코드 통제가 가능한 경우 |
| 사이드카 메시 | 서비스 옆 프록시가 통신 정책 실행 | 언어와 무관한 일관 정책·세밀한 트래픽 제어 |
| 노드 프록시·eBPF 방식 | 호스트·커널 계층에서 트래픽 처리 | 프록시 자원·홉을 줄이는 것이 중요한 경우 |

### Ⅴ. 서비스 메시의 한계와 방안

- 핵심 요약 : 프록시 추가 지연·자원·정책·인증서 오구성·메시 자체 장애·복잡성을 성능 시험·단계별 배포·장애 격리로 관리.

| 위험 | 원인·영향 | 대응 통제 | 지표 예시 |
|---|---|---|---|
| 프록시 추가 지연·자원 | 각 호출 경로에 프록시·제어 계층 비용 증가 | 핵심 경로 성능 시험, 선택적 적용·리소스 한도 | p95 지연, CPU·메모리 |
| 정책·인증서 오구성 | 광범위 차단 또는 서비스 간 권한 과다 | 단계별 정책 배포, 기본 거부와 만료·회전 검증 | 정책 실패, 인증서 만료 |
| 메시 자체 장애·복잡성 | 통신 계층이 추가 장애 영역과 운영 부담이 됨 | 장애 격리·우회 전략·운영자 훈련과 구성 검증 | 프록시 오류, 변경 실패율 |

### Ⅵ. 서비스 메시 적용에 대한 기술사적 제언

- 핵심 요약 : 마이크로서비스 간 통신의 신뢰성·보안·운영 일관성을 높여 분산 시스템의 확장성과 관리성을 확보.

- 실행 제언 : 플랫폼팀은 서비스 메시를 모든 문제의 기본 해법으로 간주하지 말고 통신 정책의 공통화 가치가 비용을 넘는 서비스부터 적용하며, 애플리케이션 책임과 메시 정책 소유자를 분리.

### Ⅶ. 결론

- 핵심 요약 : 서비스 메시는 분산 서비스 간 통신을 애플리케이션 코드와 분리해 트래픽 제어·보안·관측을 공통 인프라 계층에서 제공하는 구조.
- 시사점 : 서비스 메시는 분산 통신을 운영 인프라로 표준화하는 수단이며, 신뢰성 이득은 프록시·정책의 추가 복잡성을 통제할 때 실현.
