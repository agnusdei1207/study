## 연관 키워드

- 기술 부채(Technical Debt), Ward Cunningham, 부채 이자(Interest), 기술 부채 4분면(Technical Debt Quadrant)
- 리팩토링, 코드 스멜(Code Smell), SQALE, 품질 게이트(Quality Gate), 부채 등록부(Debt Register)

## Ⅰ. 기술 부채의 개요

- 핵심 요약 : 설계와 품질 활동을 생략한 대가가 미래의 수정 비용과 복잡성(이자)으로 되돌아오는 소프트웨어 공학적 부채.
- 개념 : 출시 일정을 맞추려고 아키텍처 설계, 리팩토링, 테스트를 생략하며 타협한 결과가 추가 수정 비용과 복잡성으로 쌓이는 현상 (**기술 부채**, Technical Debt).
- 배경 및 필요성 : 워드 커닝햄(Ward Cunningham)이 금융 대출에 빗대어 제안한 개념으로, 불명확한 요구사항과 촉박한 일정에서 무계획적으로 개발하면 시스템이 노후화하고 유지보수 비용이 누적되므로 부채를 관리할 필요가 있음.
- 주요 목적 : 부채를 가시화하고 체계적으로 상환해 개발 속도와 품질을 함께 유지.

## Ⅱ. 기술 부채의 특징 및 장점

- 핵심 요약 : 원금과 이자의 구조, 복리적 증식, 비가시성, 의도성과 신중성의 2축 분류가 기술 부채의 특징.

1. 원금과 이자 구조 : 설계 타협 시점의 원금과 상환을 미룰 때 누적되는 이자(복잡성)로 나뉨 → 부채 규모를 원금과 이자로 나누어 설명 가능.
2. 이자의 발생 형태 : 신규 기능 개발 지연, 버그 증가, 신규 인력 온보딩 비용 상승, 잦은 운영 장애로 나타남 → 개발 속도 저하가 측정 가능한 형태로 드러남.
3. 복리적 증식 : 임시방편 코드를 방치하면 수정 비용이 누적되며 가속 증가 → 상환 시점을 앞당길수록 비용이 작아짐.
4. 비가시성 : 기능으로 드러나지 않고 코드와 아키텍처 내부에 잠재 → 관리 대상으로 인식하기 어려움.
5. **기술 부채 4분면** (Technical Debt Quadrant) : 의도적 여부와 신중함 여부를 교차해 부채를 네 유형으로 분류 → 수용 가능한 부채와 무모한 부채를 구분.

## Ⅲ. 기술 부채의 구조 (흐름)

- 핵심 요약 : 4분면으로 부채의 성격을 나누고, 발생에서 예방까지 생명주기로 관리하는 구조.

```text
[ 기술 부채 4분면 (Martin Fowler) ]

의도적 + 신중 : 지금 출시하고 결과는 감당
의도적 + 무모 : 설계할 시간이 없음
비의도적 + 신중 : 더 나은 방법을 나중에 앎
비의도적 + 무모 : 기초 지식 부재
```

```text
[ 기술 부채 생명주기 ]

발생 (일정 압박 속 설계 타협)
          ↓
식별·등록 (부채 등록부, Debt Register)
          ↓
정량화 (SQALE 지표로 상환 비용 환산)
          ↓
상환 (스프린트 백로그 할당, 리팩토링)
          ↓
예방 (품질 게이트, 임계치 초과 시 머지 차단)
```

## Ⅳ. 기술 부채 유형의 비교

- 핵심 요약 : 코드, 아키텍처, 테스트, 문서 부채는 원인과 징후, 해결 수단이 서로 다름.

| 부채 유형 | 주요 원인 및 징후 | 해결 방안 |
| --- | --- | --- |
| 코드 부채 (Code Debt) | 코드 스멜, 중복 코드, 매직 넘버, 복잡한 제어 흐름 | 정적 분석 도구 기반 리팩토링 |
| 아키텍처 부채 (Architecture Debt) | 순환 의존성, 모듈 간 강결합 | 계층 구조 재정립, 의존성 역전 원칙(DIP) 적용 |
| 테스트 부채 (Test Debt) | 단위 테스트 부재, 불안정한 테스트, 낮은 커버리지 | 테스트 주도 개발(TDD) 도입, 자동화 테스트 파이프라인 구축 |
| 문서 부채 (Documentation Debt) | 최신화되지 않은 설계 명세, 사라진 도메인 이력 | 코드와 함께 관리하는 문서화(Doc-as-Code) |

## Ⅴ. 기술 부채의 장점과 한계

- 핵심 요약 : 출시 적시성을 확보하는 전략적 활용 여지가 있으나, 비가시성과 복리 증식, 구분 체계 부재가 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 비가시성으로 인한 설득 한계 | 내부 구조 부채가 기능 출시보다 후순위로 밀림 | SQALE 지표로 상환 비용 환산, 배포 리드타임·장애율과 연계한 대시보드 제시 | 상환 비용 추이, 장애율 |
| 이자의 복리 증식 | 임시 코드 방치 → 사소한 변경에도 장애가 번지는 개발 마비 | 스프린트 용량의 일정 비율을 상환 전용으로 할당, 부채 임계치 초과 시 머지 차단 | 신규 코드 부채 비율, 변경 실패율 |
| 전략적 부채와 무모한 부채의 혼재 | 의도적 부채와 역량 부족에서 비롯된 부채를 구분하지 않아 상환 계획 실패 | 4분면 기반 분류, 아키텍처 결정 기록(ADR)에 수용 사유와 상환 목표일 명시 | 부채 등록 건수, 목표일 초과 건수 |

## Ⅵ. 기술 부채 관리에 대한 기술사적 제언

- 핵심 요약 : 부채를 제품 백로그에 올려 정례적으로 상환하고, 정량 지표와 등록부로 관리 근거를 세우는 방향.

1. 부채 백로그의 정례화 : 기술 부채 개선 작업을 비즈니스 기능과 같은 백로그에 등록하고, 매 스프린트 개발 공수의 일정 비율을 상환에 의무 배정한다.
2. 정량 지표 기반의 보고 : 정적 분석 도구로 상환 소요 시간을 측정하고, 그 값을 경영진 보고 체계에 편입해 우선순위 협상의 근거로 삼는다.
3. 등록부와 결정 기록의 운영 : 부채를 수용한 이유와 상환 목표일을 기록해 무분별한 부채 축적을 막고, 정기 검토에서 상환 여부를 결정한다.

## Ⅶ. 결론

- 핵심 요약 : 기술 부채 관리는 상환을 피하는 것이 아니라 부채를 가시화하고 계획적으로 상환하는 체계를 세우는 일.
- 시사점 : 상환 공수를 스프린트마다 확보해 이자의 복리 증식을 차단할 때 지속 가능한 개발 속도가 유지됨.
