## Ⅰ. 기술 부채의 개요

- 개념 : 단기적인 비즈니스 출시 일정을 맞추기 위해 정석적인 아키텍처 설계와 리팩토링, 테스트를 생략하고 타협함으로써 미래에 추가적인 수정 비용과 **복잡성** (이자)으로 되돌아오는 소프트웨어 공학적 부채.
- 배경 및 필요성 : **워드 커닝햄** (Ward Cunningham)이 금융 대출에 비유하여 제안한 개념으로, 불명확한 요구사항과 촉박한 일정 속에서 무계획적으로 개발될 경우 시스템 노후화와 유지보수 비용 폭증(소프트웨어 위기) 유발.
- **부채의 이자(Interest)** : 신규 기능 개발 지연, 버그 발생률 증가, 온보딩 비용 상승, 잦은 운영 장애.

## Ⅱ. 기술 부채 4분면(Technical Debt Quadrant) 및 발생 메커니즘

```text
                  [ 신중함 (Prudent) ]
             ┌─────────────────────────┐
             │ 우리는 위험을 알고      │
             │ 빠른 출시 후 즉시       │
             │ 리팩토링할 것이다.      │
 [ 의도적 ]  ├─────────────────────────┤  [ 비의도적 ]
 (Deliberate)│ 설계할 시간 따윈 없다.   │  (Inadvertent)
             │ 일단 돌아가게만 짜라!   │  "계층형 아키텍처가 뭐죠?"
             └─────────────────────────┘
                  [ 무모함 (Reckless) ]
```

- **의도적-신중함 (Deliberate & Prudent)** : 시장 선점을 위해 의도적으로 부채를 지고, 릴리스 직후 리팩토링 스프린트를 계획 (가장 바람직한 관리 형태).
- **의도적-무모함 (Deliberate & Reckless)** : 품질 엔지니어링을 무시하고 무조건적인 납기만을 강요하는 개발.
- **비의도적-무모함 (Inadvertent & Reckless)** : 개발팀의 역량 부족, 디자인 패턴 및 클린 코드 지식 부재로 발생.
- **비의도적-신중함 (Inadvertent & Prudent)** : 최선을 다해 설계했으나 비즈니스 도메인의 변화와 기술 진화로 사후에 발생함을 인지.

## Ⅲ. 기술 부채의 유형 및 측정 관리 프레임워크

| 부채 유형 | 주요 원인 및 징후 | 해결 방안 |
|---|---|---|
| **코드 부채** (Code Debt) | 코드 스멜, 중복 코드, 매직 넘버, 복잡한 제어 흐름 | SonarQube 정적 분석 기반 리팩토링 |
| **아키텍처 부채** (Arch Debt) | 순환 의존성, 모듈 간 강결합, 스파게티 아키텍처 | 계층화 아키텍처 재정립, MSA 분리, **의존성 역전** (DIP) |
| **테스트 부채** (Test Debt) | 단위 테스트 부재, 불안정한(Flaky) 테스트, 낮은 커버리지 | **테스트 주도 개발** (TDD), 자동화 테스트 파이프라인 구축 |
| **문서 부채** (Doc Debt) | 최신화되지 않은 아키텍처 명세서, 사라진 도메인 히스토리 | **코드 기반 문서화** (Doc-as-Code), Swagger 연동 |

## Ⅳ. 기술 부채 관리의 주요 한계점 및 해결 방안

- 부채의 비가시성(Invisibility)으로 인한 경영진 설득 한계 :
  - 한계점 : 기술 부채는 코드 및 아키텍처 내부에 잠재되어 눈에 보이는 기능으로 드러나지 않으므로, 신규 비즈니스 기능 출시를 우선시하는 비즈니스 조직과의 우선순위 협상에서 항상 후순위로 밀림.
  - 해결 방안 : SonarQube 등 정적 분석 도구를 도입하여 기술 부채를 시간 및 화폐 단위(Remediation Cost)로 수치화(SQALE 지표)하고, 배포 리드타임 저하 및 장애 발생률과의 인과관계를 경영진 대시보드로 시각화.
- 부채 이자(Interest)의 복리 증식과 시스템 엔트로피 급증 :
  - 한계점 : 초기 빠른 출시를 위해 임시방편으로 작성된 코드가 방치되면 수정 비용이 복리처럼 지수함수적으로 증가하여, 사소한 변경에도 전사 시스템 장애가 유발되는 개발 마비 상태 도달.
  - 해결 방안 : 매 스프린트마다 전체 가용 용량의 일정 비율을 기술 부채 상환 전용 백로그로 강제 할당하고, 신규 코드에 대해 기술 부채가 임계치를 초과하면 머지를 차단하는 품질 게이트(Quality Gate) 의무화.
- 전략적 부채와 무분별한 부채의 구분 관리 체계 부재 :
  - 한계점 : 시장 적시성을 위해 의도적으로 수용한 신중한 부채(Prudent Debt)와 역량 부족이나 태만으로 유발된 무모한 부채(Reckless Debt)를 구분하지 못해 체계적 상환 계획 수립 실패.
  - 해결 방안 : 마틴 파울러의 기술 부채 사분면(Technical Debt Quadrant) 기반 분류 프레임워크를 수립하고, 아키텍처 결정 레코드(ADR)에 부채 수용 사유와 상환 목표일을 명시하는 '기술 부채 등록부(Debt Register)' 운영.

## Ⅴ. 기술 부채 관리를 위한 기술사적 제언

- 기술 부채 백로그(Tech Debt Backlog) 정례화 : 비즈니스 피처 백로그와 동일한 우선순위 체계에서 기술 부채 개선 작업을 제품 백로그에 등록하고, 매 스프린트마다 개발 공수의 일정 비율을 부채 상환에 의무 할당.
- 정량적 SQALE 방법론 기반 메트릭 관리 : SonarQube의 SQALE(Software Quality Assessment based on Lifecycle Expectations) 지표를 도입하여 부채 상환에 소요되는 일수(Man-Day)를 수치화하고 경영진 대상 보고 체계 수립.
