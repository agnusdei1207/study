## 30초 인출

- 본질: 기술 부채(Technical Debt)는 단기적 납기 단축을 위해 선택한 임시적 설계와 코드로 인해 향후 유지보수와 기능 변경 비용이 눈덩이처럼 누적되는 상태
- 메커니즘: 마틴 파울러의 4분면(신중함/무모함, 의도적/우발적) 분류 기반 식별 → SQALE 정량화 모델 측정 → 기술 부채 백로그 등록 → 상환 관리
- 통찰: 모호한 요구사항에 기반한 임시방편 구현은 부채 이자를 가속하므로 Acceptance Criteria 명세화와 정적분석 기반 핫스팟 우선 상환 적용

<details>
<summary>핵심 용어</summary>

- **기술 부채(Technical Debt)** : Ward Cunningham이 제안한 개념으로, 현재의 미봉책 설계가 향후 시스템 변경 시 이자(Interest) 형태의 추가 공수를 발생시키는 상태
- **부채 원금(Principal)** : 결함 코드를 리팩토링하여 이상적인 클린 아키텍처 상태로 바로잡는 데 소요되는 일회성 공수
- **부채 이자(Interest)** : 부채 원금을 상환하지 않고 방치함으로써 매 변경 시마다 추가로 소모되는 개발 지연 시간과 결함 수정 비용
- **기술 부채 사분면(Technical Debt Quadrant)** : Martin Fowler가 기술 부채를 의도성(Deliberate/Inadvertent)과 태도(Prudent/Reckless) 축으로 분류한 모델
- **SQALE(Software Quality Assessment based on Lifecycle Expectations)** : 소스코드 품질 결함을 수정하는 데 소요되는 시간을 금전적·시간적 기술 부채로 정량 환산하는 표준 모델
- **TDR(Technical Debt Ratio)** : 시스템 전체 재개발 비용 대비 현재 식별된 기술 부채를 상환하는 데 필요한 시정 비용의 비율

## 2~4교시 25점 답안

## Ⅰ. 기술 부채의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **기술 부채(Technical Debt)** 는 신속한 출시를 위해 타협한 설계와 구현으로 인해 향후 유지보수 시 지속적인 추가 비용을 유발하는 상태 |
| 목적 | 단기 비즈니스 가치와 장기 코드 품질 간의 트레이드오프 통제, 부채의 정량적 가시화 및 계획적 상환 |

## Ⅱ. 기술 부채의 핵심 특징

| 특징 | 의미 |
|---|---|
| 비용 누적성 | 방치된 부채는 매 스프린트마다 기능 수정 지연과 결함 발생이라는 '이자'를 지속 청구 |
| 가시성 결여 | 외부 기능 동작은 정상으로 보여 비즈니스 의사결정자에게 은닉되기 쉬운 내부적 품질 문제 |
| 계획적 관리 | 모든 부채의 즉시 제거가 아닌, 시스템 변경 빈도(Churn)에 따른 우선순위별 점진적 상환 필요 |

## Ⅲ. 기술 부채의 측정과 거버넌스 메커니즘

### 기술 부채 생명주기 관리 체계

```text
[코드스멜·아키텍처 부채 식별]
        ↓ (SonarQube SQALE 모델 분석)
[기술 부채 정량화: TDR, 시정 시간 산출]
        ↓
[기술 부채 백로그(Debt Backlog) 등록 및 우선순위화]
        ↓
[스프린트 백로그 반영 및 점진적 리팩토링 상환]
        ↓
[품질 게이트웨이 검증 및 기술 부채 재측정]
```

### 불명확한 요구사항에서 기술 부채로 이어지는 악순환 고리

```text
모호한 요구사항 접수
    ↓
개발자의 추정에 기반한 하드코딩 및 임시 예외 처리 (부채 원금 발생)
    ↓
운영 배포 후 요구사항 불일치 및 사이드 이펙트 결함 빈발 (부채 이자 지급)
    ↓
일정 압박 속 핫픽스 덧칠 누적 및 코드스멜 가속
    ↓
시스템 아키텍처 경화 및 신규 기능 납기 지연 (기술 부채 파산)
```

| 정량 측정 지표 | 측정 방식 및 산식 | 의미 및 해석 |
|---|---|---|
| 기술 부채 시간 (Remediation Effort) | SQALE 규칙 위반 사항 수 × 규칙별 표준 시정 시간 | 코드베이스를 이상적 상태로 정제하는 데 필요한 절대 공수 |
| 기술 부채 비율 (TDR) | (추정 시정 비용 ÷ 추정 재개발 비용) × 100% | 전체 시스템 대비 기술 부채의 상대적 심각도 (5% 이하 우수) |
| 코드 복잡도 (Cyclomatic Complexity) | 제어 흐름 그래프의 선형 독립 경로 수 계산 | 높을수록 테스트 케이스 설계 난이도 및 결함 유입 가능성 증가 |
| 코드 중복률 (Duplication Rate) | 전체 라인 중 중복 블록 라인 비율 | 로직 변경 시 동시 수정 누락에 따른 결함 위험도 지표 |

## Ⅳ. 마틴 파울러의 기술 부채 사분면(Technical Debt Quadrant)

```text
                    [ 신중함 (Prudent) ]
                             │
     (A) 신중하고 의도적인 부채   │   (B) 신중하고 우발적인 부채
     "빠른 출시 후 즉시 리팩토링"│   "이제야 올바른 설계를 깨달았음"
                             │
───────────────[ 의도적 ]─────┼─────[ 우발적 ]───────────────
               (Deliberate)  │    (Inadvertent)
                             │
     (C) 무모하고 의도적인 부채   │   (D) 무모하고 우발적인 부채
     "설계할 시간 없으니 대충 구현"│   "계층 아키텍처가 뭔지도 모름"
                             │
                    [ 무모함 (Reckless) ]
```

| 사분면 분류 | 발생 원인 및 특징 | 조직적 대응 방안 |
|---|---|---|
| 신중함 / 의도적 (A) | 비즈니스 선점을 위한 의식적 타협, 부채 규모 인지 | 릴리스 직후 스프린트에 상환 작업 필수 배정 |
| 신중함 / 우발적 (B) | 구현 완료 후 비즈니스 도메인 및 기술 학습 심화 | 배운 도메인 지식을 반영하여 아키텍처 점진 리팩토링 |
| 무모함 / 의도적 (C) | 출시 압박을 핑계로 아키텍처 원칙과 테스트 의도적 포기 | 기술 부채 상환 비용 가시화 및 경영진 인식 제고 |
| 무모함 / 우발적 (D) | 개발팀의 역량 부족, 기본적 설계 원칙 부재로 스파게티 코드 양산 | 엔지니어링 교육 강화, 페어 프로그래밍, 시니어 코드 리뷰 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 신규 비즈니스 기능 개발 우선순위에 밀려 기술 부채 상환 작업의 지속적 연기 | 매 스프린트 개발 용량(Capacity)의 15~20%를 기술 부채 전담 공수로 사전 할당 |
| 분석 도구가 측정한 기술 부채 수치(시간)와 실제 비즈니스 위험 간의 괴리 발생 | 수정 빈도(Churn)와 결함 발생률을 결합한 핫스팟(Hotspot) 분석으로 상환 우선순위 조정 |
| 불명확한 요구사항으로 인한 임시방편성 코드 누적 및 재작업 공수 폭증 | BDD(Given-When-Then) 기반의 인수 조건(Acceptance Criteria) 합의 후 개발 착수 |

## Ⅵ. 제언

CI/CD 품질 게이트 연동과 핫스팟 기반 기술 부채 백로그 거버넌스 체계 구축

### 기술 부채 거버넌스 및 상환 파이프라인

```text
Git PR 생성 시 정적 분석(SonarQube) 자동 실행
    ↓
품질 게이트 검증: 신규 코드(New Code) 대상
    ├─ TDR > 5% 또는 치명적 코드스멜 발생 → 머지 자동 차단 (부채 유입 방지)
    └─ 품질 기준 충족 → 코드 머지 승인
    ↓
레거시 부채는 Churn-Complexity 매트릭스 기반 핫스팟 우선 상환
```

### Churn-Complexity 기반 상환 우선순위 매트릭스

```text
수정 빈도 (Churn)
   High │  [최우선 상환 대상]     │  [모니터링 대상]
        │  (자주 바뀌며 복잡한 코드)│  (자주 바뀌나 단순한 코드)
        ├────────────────────────┼────────────────────────
    Low │  [상환 보류 / 관찰]     │  [상환 불필요]
        │  (복잡하나 수정 없는 레거시)│  (단순하며 안정된 코드)
        └────────────────────────┴────────────────────────
                   High                     Low
                        순환 복잡도 (Complexity)
```

### 선택 근거: 전수 상환과 핫스팟 기반 선택적 상환 비교

| 구분 | 전체 코드베이스 전수 상환 | 제언: 핫스팟 기반 선택적 상환 |
|---|---|---|
| 엔지니어링 비용 | 막대한 공수 투입으로 비즈니스 마비 | 핵심 수정 영역 집중으로 최소 비용 상환 |
| 투자 대비 효익 | 변경 없는 레거시 수정으로 효익 미미 | 빈번한 변경 영역 품질 개선으로 생산성 극대화 |
| 부채 유입 억제 | 사후적 일괄 청소에 의존 | 품질 게이트로 신규 부채 유입 원천 봉쇄 |
