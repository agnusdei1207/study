## 답안 골격
```text
[SW 규모 산정 방식] ◀━━ 머리: Ⅶ 내 의견 (요구사항 상세화 단계별 산정 기법 전환 및 설계·구축 분할 발주 기반의 정산 체계 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 주관적 직관에 의존한 원가 산정 실패 → 사업 대가 산정과 개발 공기 추정을 위한 공학적·정량적 크기 측정
 ┣━ Ⅱ 특징 ───── 프로젝트 계획 수립의 입력값 · 기술 독립적 기능 측정(FP) vs 구현 중심 물리 측정(LOC) · 다차원 접근
 ┣━ Ⅲ 구조 ───── 기능적 크기 측정(기능점수 정규법/간이법, COSMIC) / 물리적 크기(LOC) / 객체지향 크기(UCP, 클래스 수) / 애자일(스토리 포인트)
 ┣━ Ⅳ 흐름 ───── 사업 기획(간이법 추정) → 분석/기본설계(정규법 확정) → 구현(LOC 모니터링) → 배포/종료(실제 투입 공수 대조)
 ┣━ Ⅴ 비교 ───── 기능점수(FP) vs 유스케이스 점수(UCP) vs LOC vs 스토리 포인트(Story Point)
 ┗━ Ⅵ 실무 ───── 공공 SW 사업 RFP 요구사항 모호성 / 과업 추가(Scope Creep) 정산 분쟁 / 현실적 개선 방안(과심위, 분할발주)
```

## 한 줄 본질
- 소프트웨어 개발 시작 전 개발 대상의 실질적 크기를 객관적으로 측정하지 못해 예산 부족과 납기 지연이 반복되는 병목 → 소프트웨어의 기능적 요구량과 기술적 복잡도를 표준화된 측정 단위로 정량화하여 공수를 산출하는 공학적 프로세스 / 요구사항 변경에 따른 재산정 오버헤드

```text
+-------------------------------------------------------------------------+
|                                                                         |
|  [ 프로젝트 단계 ]   [ 기획 / 예산 수립 ] ──> [ 분석 / 설계 ] ──> [ 구현 / 운영 ] |
|                             │                      │               │    |

|    2. 객체/시나리오 크기 (Object/Scenario) : 액터와 유스케이스 복잡도 기반 (UCP)|

```

## 핵심 용어
- COSMIC 기능점수(COSMIC FP): ISO/IEC 19761 표준으로, 전통적 비즈니스 IT가 아닌 실시간/임베디드 소프트웨어의 데이터 이동(Entry, Exit, Read, Write) 관점에서 규모를 측정하는 기법
- 유스케이스 포인트(UCP, Use Case Point): 요구사항 분석 단계의 액터 분류(가중치)와 유스케이스 트랜잭션 단계 수에 기술/환경 복잡도 팩터를 곱해 소프트웨어 크기를 산정하는 객체지향 규모 산정 기법

## 핵심 통찰
- 공공 소프트웨어 사업에서 발생하는 분쟁의 90%는 "기획 단계의 개략적인 RFP를 보고 간이법으로 확정한 예산"과 "실제 상세설계 완료 후 도출된 정규 기능점수 규모" 간의 30~50% 괴리에서 비롯됨
- 하드웨어 구매와 달리 소프트웨어는 무형의 자산이므로 초기 요구사항이 계속 진화하며, 완벽한 사전 규모 산정은 불가능하다는 공학적 현실을 인정해야 함
- 따라서 규모 산정 방식을 고도화하는 것만큼이나, 기본설계 완료 시점에 규모를 재산정하여 총사업비를 정산할 수 있도록 뒷받침하는 제도적 장치(과업심의위원회, 설계·구축 분할 발주)가 필수적임

## 이웃 토픽과 구분
- 기능점수(FP) vs 유스케이스 포인트(UCP): FP = 데이터베이스 파일(ILF/EIF)과 입력/출력 트랜잭션 중심 측정 / UCP = 유스케이스 시나리오의 상호작용 단계 수와 액터 유형 중심 측정

## 문제·원인·대책
- 적용 상황: 중앙행정기관 대국민 포털 재구축 사업 발주 및 예산 수립
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 사업 진행 중 발주처의 추가 기능 요구로 개발 공수가 40% 증가했으나 예산 추가 미인정 | 기획 단계 간이법으로 총사업비를 고정 계약하고 과업 변경 절차를 거치지 않음 | 소프트웨어 진흥법 상 과업심의위원회 심의를 통해 변경 기능점수 산정 및 계약 변경 | 수주사의 적자 예방 및 정당한 과업 대가 보상 |
| 산정 기관마다 기능점수 결과가 최대 30% 차이 나며 감사원 지적 및 입찰 잡음 발생 | 산정자마다 DET(데이터요소)와 FTR(참조파일)에 대한 주관적 판단 기준 불일치 | 소스코드/DB 스키마 기반 자동화 기능점수 측정 도구 활용 및 산정 근거 표준화 | 산정 객관성 확보 및 감사 리스크 완전 제거 |

## 이렇게 출제된다
- 제132회 4교시 5번: "소프트웨어개발에 필요한 규모 산정 방식종류와 특징을 비교 설명하고, 공공 소프트웨어 사업 규모 산정 방식의 현실적 개선 방안에 대하여 설명하시오." → 요구 포인트: 규모 산정 방식 4가지(FP, LOC, UCP, COCOMO 등) 비교 + 공공 SW 사업의 현실적 한계 3가지 + 개선 방안(분할발주, 단가 현실화, 과심위 활성화)
