## Ⅰ. 폭포수 개발 방법론의 개요

- 개념 : **폭포수 개발 방법론** 이란 윈스턴 로이스(Winston Royce)가 1970년에 소개한 전통적인 소프트웨어 공학 라이프사이클 모델로, 소프트웨어 개발의 각 단계(타당성 검토, 요구분석, 설계, 구현, 시험, 유지보수)를 폭포에서 물이 떨어지듯 순차적으로 진행하며, 이전 단계의 검토와 승인이 완료되어야만 다음 단계로 진입하는 엄격한 순차적(Sequential) 개발 방법론.
- 배경 및 필요성 : 소프트웨어 개발을 주먹구구식 코딩에서 벗어나 예측 가능하고 통제 가능한 공학적 제조 공정으로 체계화.
- 핵심 원칙 : 엄격한 단계별 마일스톤 관리, 상세한 표준 산출물 작성, **변경 통제** (CCB) 중심의 거버넌스

## Ⅱ. 폭포수 모델의 단계별 공정 및 V-모델 연계

```text
   [ 1. 요구사항 분석 ] ─────────────────────────> [ 인수 테스트 (Acceptance) ]
           │                                                ▲
           ▼ (SRS 승인)                                     │
   [ 2. 시스템 설계 ] ─────────────────────────> [ 시스템 테스트 (System) ]
           │                                                ▲
           ▼ (SAD 승인)                                     │
   [ 3. 상세 설계 ] ───────────────────────────> [ 통합 테스트 (Integration) ]
           │                                                ▲
           ▼ (설계서 확정)                                  │
   [ 4. 코딩 및 구현 ] ────────────────────────> [ 단위 테스트 (Unit) ]
```

- V-모델과의 관계 : 폭포수 모델의 각 개발 단계(요구-설계-상세설계-코딩)에 대응하는 **검증 및 확인** (V&V) 테스트 계층(단위-통합-시스템-인수)을 1:1로 매핑하여 품질 보증 구조화.
- **단계별 종료 기준** (Exit Criteria) : 각 공정이 끝날 때마다 **공식 검토** (Formal Review)를 거치고 **베이스라인** (Baseline)을 수립해야 다음 단계로 전이 가능.

## Ⅲ. 폭포수 모델의 장단점 비교

| 장점 (Strengths) | 단점 및 위험 요소 (Weaknesses & Risks) |
|---|---|
| 전체 프로젝트 범위와 일정이 초기에 명확히 가시화됨 | 개발 후반부(테스트 단계)까지 동작하는 소프트웨어를 볼 수 없음 |
| 단계별 산출물이 풍부하여 인력 교체 시 인수인계 용이 | 고객의 요구사항 변경을 수용하기가 극도로 어렵고 비용이 큼 |
| 대규모 공공 및 국방 사업의 계약 및 예산 관리에 최적 | 통합 단계에서 대규모 결함이 일시에 폭발하는 위험(Big-Bang) 존재 |
| 초보 개발자도 정해진 프로세스와 설계서대로 작업 가능 | 분석/설계 지연 시 코딩 및 테스트 일정이 압축되어 품질 붕괴 |

## Ⅳ. 폭포수 개발 방법론의 주요 한계점 및 해결 방안

- 후반부 **빅뱅 통합** (Big Bang Integration) 단계의 결함 폭발 위험 :
  - 한계점 : 분석·설계·구현이 순차 완료된 후 프로젝트 말기 테스트 단계에서 서브시스템 간 통합 오류가 집중 분출되어 납기 지연 및 사업 파행.
  - 해결 방안 : V-모델 변형을 적용하여 각 개발 단계마다 대응되는 테스트 레벨(단위-통합-시스템-인수) 사전 설계 및 CI(Continuous Integration) 자동화 파이프라인 조기 구축.
- 요구사항 변경에 대한 극심한 경직성 및 고객 피드백 단절 :
  - 한계점 : 초기 요구사항 동결 후 비즈니스 환경이 급변하더라도 스코프 변경 절차가 까다로워 최종 인도물에 대한 고객 만족도 급락.
  - 해결 방안 : 공식 변경통제위원회(CCB)의 신속한 영향도 평가 체계 확립, 초기 단계 핵심 기능 프로토타이핑(Prototyping)을 통한 고객 조기 검증 병행.
- 방대한 문서 산출물 작성으로 인한 엔지니어링 리소스 낭비 :
  - 한계점 : 프로젝트 일정의 상당 부분이 검수용 형식 문서 작성에 소모되어 정작 핵심 소스코드의 설계 품질과 테스트가 부실해지는 현상.
  - 해결 방안 : 프로젝트 규모와 특성에 맞춘 산출물 테일러링 가이드라인 적용, 자동 문서화 도구(Swagger, Javadoc)를 활용한 산출물 작성 공수 절감.

## Ⅴ. 현대 엔지니어링 환경에서의 기술사적 제언

- 요구사항 명확성에 따른 방법론 선정(Stacey 매트릭스) : 기술과 요구사항이 모두 확실한 도메인(공공 행정 시스템 재구축 등)에는 폭포수 모델이 계약 및 일정 통제에 가장 유리하므로, 무조건적인 애자일 추종을 지양하고 프로젝트 복잡도에 따라 폭포수 방식을 합리적으로 채택.
- **단계별 게이트웨이 검증** (Phase-Gate)을 통한 품질 조기 통제 : 분석 단계 종료 시점에 실제 사용자가 참여하는 UI(User Interface) 프로토타이핑을 결합하고, 설계 단계 종료 시점에 **ATAM**(Architecture Tradeoff Analysis Method) 아키텍처 평가를 의무화하여 폭포수 모델의 최대 약점인 '후반부 요구 불일치 리스크'를 선제 차단.
