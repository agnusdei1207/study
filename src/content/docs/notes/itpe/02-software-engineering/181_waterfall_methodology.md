## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 개발 프로세스·생명주기 → 폭포수 개발 방법론(Waterfall)

## 지식 위치

소프트웨어공학 > 개발 생명주기 모델 > 폭포수 모델

## 30초 인출

- 본질: 소프트웨어 개발 생명주기(SDLC)를 요구분석, 설계, 구현, 시험, 유지보수의 순차적 단계로 분할하고 선행 단계의 공식 승인(Sign-off) 후 후행 단계로 이행하는 전통적 선형 순차 모델
- 메커니즘: 단계별 작업 정의 → 단계별 산출물 작성 → 동료 검토 및 공식 승인(Baseline 설정) → 다음 단계 착수 → 변경 요청 시 공식 변경통제위원회(CCB) 심의 수행
- 통찰: 후반부 테스트 단계까지 작동하는 소프트웨어를 확인할 수 없는 빅뱅 검증의 위험을 방지하기 위해 핵심 요구사항에 대한 프로토타이핑 병행 및 요구사항 추적 매트릭스(RTM)의 엄격한 관리 필수

<details>
<summary>핵심 용어</summary>

- **폭포수 모델 (Waterfall Model)** : 1970년 윈스턴 로이스(Winston Royce)가 제시한 체계적이고 문서 중심적인 고전적 선형 순차 소프트웨어 수명주기 모델
- **기준선 (Baseline)** : 공식적인 검토와 승인을 거쳐 합의된 산출물의 상태로, 이후의 모든 변경은 공식 절차를 통해서만 통제되는 기준
- **소프트웨어 요구사항 명세서 (SRS)** : 개발할 시스템의 기능적/비기능적 요구사항을 완벽하고 모호함 없이 기술한 최상위 기준 문서
- **요구사항 추적성 (Requirements Traceability)** : 요구사항 정의부터 설계서, 소스코드, 테스트 케이스까지 양방향으로 연결성을 추적할 수 있는 역량
- **변경통제위원회 (CCB: Change Control Board)** : 요구사항 변경 요청(CR)에 대해 일정, 비용, 품질 영향을 심의하여 승인/기각을 결정하는 의사결정 기구
</details>

## 2~4교시 예상문제 (25점)

> 전통적 소프트웨어 개발 수명주기인 폭포수(Waterfall) 모델의 개념과 단계별 활동 및 기준선(Baseline) 관리 체계를 설명하고, 애자일(Agile) 모델과의 비교 및 대규모 공공/국방 프로젝트에서의 성공적 적용 방안을 제시하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 개발의 전 과정을 요구분석, 설계, 구현, 테스트, 배포/운영의 논리적 단계로 명확히 구분하고, 선행 단계의 산출물이 완벽히 검증·승인된 후 다음 단계로 진입하는 선형 순차적 개발 수명주기 모델 |
| 목적 | 프로젝트 관리의 가시성(Visibility) 확보, 단계별 산출물의 품질 통제, 일정 및 예산의 예측 가능성 극대화 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 선형 순차적 흐름 | 물이 위에서 아래로 떨어지듯 원칙적으로 이전 단계로의 역행을 지양하고 순차적으로 이행 |
| 문서 중심의 산출물 관리 | 각 단계의 완료 여부를 코드 동작이 아닌 엄격한 산출물 문서(SRS, 아키텍처 설계서 등)의 공식 승인으로 판정 |
| 엄격한 기준선(Baseline) 설정 | 각 단계 종료 시점에 산출물을 공식 동결하고, 변경 발생 시 CCB를 통한 엄격한 변경 통제 수행 |
| 명확한 책임과 역할 분담 | 기획자(분석), 아키텍트(설계), 프로그래머(구현), QA(테스트) 등 공정별 전문 인력의 순차 투입 가능 |

요구사항이 명확하고 변경 가능성이 극히 낮은 대규모 시스템 구축의 표준 공정으로 확립.

## Ⅲ. 체계·프로세스

```text
[요구사항 분석 (Requirements)] ──► 요구사항 정의서 / SRS 확정 ──► [기능 기준선: Functional Baseline]
         │ (공식 승인 후 진입)
         ▼
[시스템 설계 (Design)]         ──► 아키텍처/상세설계서 확정   ──► [설계 기준선: Allocated Baseline]
         │ (공식 승인 후 진입)
         ▼
[구현/코딩 (Implementation)]   ──► 소스코드 / 단위테스트 완료  ──► [개발 기준선: Development Baseline]
         │ (빌드 검증 후 진입)
         ▼
[통합/시험 (Verification)]     ──► 통합/시스템/인수테스트 통과 ──► [제품 기준선: Product Baseline]
         │ (최종 인수 승인)
         ▼
[운영 및 유지보수 (Maintenance)] ──► 변경 요청(CR) 발생 시 CCB 심의 후 역방향 수정 통제
```

단계별 산출물 완성, 공식 리뷰를 통한 기준선 수립, 승인 후 다음 공정 이행 및 CCB 기반 변경 통제 체계.

## Ⅳ. 종류·비교

| 비교 항목 | 폭포수 모델 (Waterfall) | 애자일 모델 (Agile / Scrum) |
|---|---|---|
| **개발 패러다임** | 계획 중심, 선형 순차적, 문서 주도 | 변화 적응 중심, 반복 점진적, 가치 주도 |
| **요구사항 관리** | 프로젝트 초기에 100% 확정 지향, 변경 억제 | 주기적인 백로그 정제, 스프린트 단위 변경 수용 |
| **산출물 및 검증** | 방대한 정형 산출물(명세서) 기반 승인 | 작동하는 소프트웨어(Working Software) 중심 시연 |
| **고객 참여 시점** | 프로젝트 초기(요구분석) 및 말기(인수시험) | 매 스프린트 데모마다 지속적인 피드백 참여 |
| **위험 식별 시점** | 통합/시험 단계인 프로젝트 후반부에 집중 노출 | 매 반복 주기마다 조기에 위험 노출 및 해결 |
| **최적 적용 분야** | 국방, 항공, 금융 차세대, 공공 SI (요구 확정형) | 모바일 앱, 스타트업 서비스, AI 솔루션 (요구 가변형) |

### 폭포수 모델의 변형 및 발전 형태 비교

| 변형 모델 | 핵심 개념 | 폭포수 한계 극복 방식 |
|---|---|---|
| **V-모델 (V-Model)** | 개발 단계와 테스트 레벨(단위, 통합, 시스템, 인수)을 1:1 매핑 | 설계 단계에서 테스트 계획을 선행 수립하여 검증력 강화 |
| **반복적 폭포수** | 대형 시스템을 서브시스템별로 나누어 폭포수를 반복 수행 | 대규모 위험을 서브시스템 단위로 분산 |
| **프로토타이핑 결합 폭포수** | 요구분석 단계에서 Mockup/프로토타입을 먼저 제작하여 검증 | 사용자 요구사항 불일치로 인한 후반부 재작업 방지 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 프로젝트 후반부 통합 테스트 단계에서야 결함이 발견되어 수정 비용이 기하급수적으로 폭증(Boehm의 법칙) | V-모델을 채택하여 분석/설계 단계에서 테스트 케이스를 조기 도출하고 정적 분석/동료 검토 강화 |
| 사용자 요구사항의 초기 동결 불가능성으로 인한 지속적 변경과 프로젝트 납기/예산 초과 | 요구사항 추적 매트릭스(RTM)를 확립하고 공식 CCB(변경통제위원회)를 통한 변경 영향 평가 의무화 |
| 고객이 프로젝트 말기까지 동작하는 결과물을 보지 못해 완성도에 대한 불신과 불안감 가중 | 요구분석 및 초기 설계 시점에 핵심 화면과 워크플로우에 대한 UI/UX 프로토타입 제작 시연 |

## Ⅵ. 제언

공공 및 엔터프라이즈 SI 프로젝트에서는 폭포수의 '계획·일정·예산 통제성'과 애자일의 '기민한 변화 적응력'을 결합한 하이브리드(Water-Scrum-Fall) 거버넌스 정착 권장.

```text
[현대적 하이브리드 (Water-Scrum-Fall) 아키텍처]
  [Upfront Waterfall]           [Agile Sprint Iterations]          [Downstream Waterfall]
  기획/예산/아키텍처 정의 ──► 2주 단위 스프린트 (구현/단위검증) ──► 통합 테스트/보안 감사/공식 인수
```

| 관리 영역 | 전통적 순수 폭포수 | 하이브리드 거버넌스 (Water-Scrum-Fall) |
|---|---|---|
| 개발 공정 | 6개월 이상의 일괄 코딩 후 일괄 테스트 | 2주 단위의 동작하는 모듈 단위 점진 빌드 |
| 고객 피드백 | 최종 납품 시점에 첫 검수 | 스프린트 종료 시점마다 정기 데모를 통한 고객 조기 검증 |
