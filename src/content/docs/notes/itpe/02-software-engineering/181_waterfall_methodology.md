## 연관 키워드

- 폭포수 모델(Waterfall Model), 순차적 개발, V-모델(V-Model), 단계별 게이트(Phase-Gate)
- 변경통제위원회(CCB, Change Control Board), 베이스라인(Baseline), 마일스톤(Milestone), 공식 검토(Formal Review), 빅뱅 통합(Big Bang Integration), Stacey 매트릭스

## Ⅰ. 폭포수 개발 방법론의 개요

- 핵심 요약 : 단계마다 검토와 승인을 거쳐 다음 단계로 넘어가는 순차형 소프트웨어 개발 라이프사이클 모델.
- 개념 : 요구분석, 설계, 구현, 시험, 유지보수를 앞 단계의 완료 승인 후에만 순서대로 진행하는 순차형 개발 모델(**폭포수 모델** (Waterfall Model)).
- 배경 및 필요성 : 대규모 시스템에서 설계 결함이 후반 시험 단계에 드러나면 수정 비용이 커지므로, 개발 과정을 계획·문서·검토로 통제할 필요가 제기됨. 1970년 Winston Royce의 논문에서 이러한 순차 모델이 제시되어 이후 전통적 개발 방법론의 기준 틀이 됨.
- 주요 목적 : 단계 종료 시점의 **마일스톤** (Milestone)을 기준으로 일정과 산출물을 관리하고, **변경통제위원회** (CCB, Change Control Board)를 통해 요구사항 변경을 공식 절차로 통제하여 대규모 프로젝트의 예측 가능성을 확보.

## Ⅱ. 폭포수 모델의 특징 및 장점

- 핵심 요약 : 단계 순차성, 공식 검토, 문서 중심 관리가 예측 가능성과 계약 통제력으로 이어지는 계약형 개발 공정.

1. 단계 순차성 : 이전 단계 승인 후에만 다음 단계로 진입 → 단계별 완료 상태가 명확해 진척 파악이 쉬움.
2. 공식 검토와 기준선 : 단계 산출물을 **공식 검토** (Formal Review)로 확인한 뒤 **베이스라인** (Baseline)으로 고정 → 승인된 기준 이후의 무단 변경 방지.
3. 표준 산출물 중심 문서화 : SRS(Software Requirements Specification), SAD(Software Architecture Document) 등을 작성 → 인력 교체 시 인수인계와 검수 근거 확보.
4. 변경 통제 : 요구사항을 초기에 동결하고 변경은 CCB 절차를 거치게 함 → 범위 확산 억제와 예산 통제.
5. **V-모델** (V-Model) 연계 : 개발 단계마다 대응하는 테스트 계층을 미리 정의 → 검증·확인 (V&V, Verification and Validation) 체계화.
6. 마일스톤 기반 관리 : 단계 종료 시점을 기준점으로 삼아 일정·예산·인력을 계획 → 진척 보고와 자원 배분의 근거 확보.

## Ⅲ. 폭포수 모델의 구조 (흐름)

- 핵심 요약 : 승인 게이트를 통과하는 순차 공정과 V-모델 테스트 레벨의 1:1 대응 구조.
- 각 단계는 **단계별 게이트** (Phase-Gate)를 통과해야 다음 단계로 전이하며, 종료 조건은 공식 검토 통과와 베이스라인 수립이다.

```text
[ 폭포수 모델의 순차 공정 ]

요구사항 분석
      ↓ (SRS 승인)
시스템 설계
      ↓ (SAD 승인)
상세 설계
      ↓ (설계서 확정)
구현 (코딩)
      ↓
시험 및 배포
      ↓
유지보수
```

```text
[ V-모델의 1:1 대응 ]

개발 단계        테스트 레벨
요구사항 분석 →  인수 테스트
시스템 설계   →  시스템 테스트
상세 설계     →  통합 테스트
구현          →  단위 테스트
```

- 대응 구조의 의미 : 설계 단계에서 정한 검증 기준이 테스트 단계에서 그대로 쓰이므로, 후반 테스트가 설계 의도와 어긋나는 것을 구조적으로 줄임.

## Ⅳ. 폭포수 모델과 애자일 방법론의 비교

- 핵심 요약 : 계약·문서·순차 통제 중심의 폭포수 모델과 협업·반복·변경 수용 중심의 애자일 방법론의 대비.

| 비교 항목 | 폭포수 모델 (Waterfall) | 애자일 방법론 (Agile) |
| --- | --- | --- |
| 개발 방식 | 단계별 순차 진행, 이전 단계 복귀 곤란 | 반복·점증 (Iterative & Incremental) 스프린트 개발 |
| 요구사항 변경 | 초기 동결 후 CCB 절차로 엄격 관리 | 스프린트 단위로 지속 수용 |
| 동작 소프트웨어 확인 | 개발 후반 테스트 단계 이후 | 매 반복 주기마다 결과 확인 |
| 문서 및 산출물 | 표준 산출물 중심의 방대한 문서화 | 동작 소프트웨어 중심의 경량 문서화 |
| 적합 프로젝트 | 요구가 명확한 공공·국방·대규모 계약 사업 | 요구 불확실성이 큰 신규·혁신 서비스 |

- 선택 기준 : 요구사항의 명확성과 계약 형태에 따라 두 방식의 적용 범위를 정함.

## Ⅴ. 폭포수 모델의 한계와 방안

- 핵심 요약 : 후반 통합 결함 집중, 변경 경직성, 문서 과잉의 세 한계를 단계별 검증, 변경 절차 정비, 산출물 테일러링으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **빅뱅 통합** (Big Bang Integration) | 설계·구현 완료 후 통합에서 결함 집중 발견 → 납기 지연 | V-모델 기반 테스트 계획의 사전 수립, 지속적 통합 (CI, Continuous Integration) 조기 도입 | 통합 결함 발견 시점 |
| 요구사항 변경 경직성 | 초기 동결 후 환경 변화 반영이 어려움 → 고객 만족도 저하 | CCB의 영향도 평가 신속화, 핵심 기능의 **프로토타이핑** (Prototyping) 병행 | 변경 요청 처리 기간 |
| 문서 과잉 | 형식 문서 작성에 공수 집중 → 설계 품질과 테스트 부실 | 프로젝트 규모에 맞춘 산출물 **테일러링** (Tailoring), 문서 자동화 도구(Swagger, Javadoc) 활용 | 문서 작성 공수 비율 |

## Ⅵ. 폭포수 모델에 대한 기술사적 제언

- 핵심 요약 : 요구사항 불확실성에 따라 방법론을 고르고, 단계 게이트에서 품질을 점검하는 운영 체계를 갖출 것.
- 방법론 선정 기준을 조직 표준으로 정해 두고, 폭포수 모델을 무조건 배제하거나 맹목적으로 따르지 않도록 하는 것이 바람직하다. **Stacey 매트릭스**는 요구사항 합의 수준과 기술 확실성의 두 축으로 프로젝트를 나눠 이러한 선택을 돕는 도구로 쓸 수 있다.
- 단계 게이트의 통과 기준을 문서로 정하고, 설계 단계 종료 시 ATAM(Architecture Tradeoff Analysis Method) 기반 아키텍처 평가를 게이트 조건으로 넣으면 후반부 구조 결함을 앞당겨 찾을 수 있다.
- 폭포수 방식과 점증적 개발을 혼용할 경우 게이트는 유지하되 개발 주기는 나누는 하이브리드 운영을 검토하는 것이 현실적이다.

## Ⅶ. 결론

- 핵심 요약 : 폭포수 모델은 요구가 명확한 도메인에서 통제력을 확보하는 여전히 유효한 개발 모델.
- 순차 공정, 문서 산출물, 변경 통제의 체계성은 강점이자 경직성의 원천이므로, 프로젝트 특성에 맞는 게이트 설계와 테일러링이 활용의 관건이다.
