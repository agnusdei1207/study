## 연관 키워드

- 폭포수 모델(Waterfall Model), 순차적 개발(Sequential), V-모델(V-Model)
- 변경통제위원회(CCB, Change Control Board), 베이스라인(Baseline), 마일스톤(Milestone), Stacey 매트릭스

## Ⅰ. 폭포수 개발 방법론의 개요

- 핵심 요약 : 단계별 검토·승인 게이트를 통과하며 순차 진행하는 전통적 소프트웨어 개발 라이프사이클 모델.
- 개념 : 폭포수 개발 방법론(Waterfall)이란 윈스턴 로이스(Winston Royce)가 1970년에 소개한 전통적인 소프트웨어 공학 라이프사이클 모델로, 소프트웨어 개발의 각 단계(타당성 검토, 요구분석, 설계, 구현, 시험, 유지보수)를 폭포에서 물이 떨어지듯 순차적으로 진행하며, 이전 단계의 검토와 승인이 완료되어야만 다음 단계로 진입하는 엄격한 순차적(Sequential) 개발 방법론.
- 배경 및 필요성 : 주먹구구식 코딩 관행에서 예측 가능하고 통제 가능한 공학적 제조 공정으로의 개발 체계화 필요.
- 주요 목적 : 엄격한 단계별 마일스톤 관리, 상세한 표준 산출물 작성, 변경 통제(CCB, Change Control Board) 중심 거버넌스를 통한 대규모 프로젝트 통제력 확보.

## Ⅱ. 폭포수 모델의 특징

- 핵심 요약 : 단계 순차성·문서 중심·변경 경직성을 특징으로 하는 계약형 개발 공정.

1. 이전 단계 승인 없이 진입이 불가능한 엄격한 단계 순차성(Sequential).
2. 단계 종료 시점의 공식 검토(Formal Review)와 베이스라인(Baseline) 수립.
3. SRS(Software Requirements Specification), SAD(Software Architecture Document) 등 풍부한 표준 산출물.
4. 요구사항 초기 동결을 전제로 한 변경통제위원회(CCB) 기반 변경 관리.
5. V-모델(V-Model)과의 연계를 통한 단계별 검증·확인(V&V, Verification and Validation) 구조화.
6. 명확한 마일스톤 기반의 일정·예산·인력 관리.

## Ⅲ. 폭포수 모델의 구조 (흐름)

- 핵심 요약 : 승인 게이트를 통과하는 순차 공정과 V-모델 테스트 레벨의 1:1 대응 구조.
- 폭포수 모델의 단계별 순차 공정.

```text
[ 1. 요구사항 분석 ]
    │ ▼ (SRS 승인)
[ 2. 시스템 설계 ]
    │ ▼ (SAD 승인)
[ 3. 상세 설계 ]
    │ ▼ (설계서 확정)
[ 4. 코딩 및 구현 ]
    │ ▼
[ 5. 시험 → 유지보수 ]
```

- V-모델과의 연계 구조.

```text
[ 개발 단계 ]                [ 테스트 레벨 ]
 요구사항 분석  ◀──1:1 대응──▶  인수 테스트(Acceptance)
 시스템 설계    ◀──1:1 대응──▶  시스템 테스트(System)
 상세 설계      ◀──1:1 대응──▶  통합 테스트(Integration)
 코딩·구현      ◀──1:1 대응──▶  단위 테스트(Unit)
```

- V-모델과의 관계 : 폭포수 모델의 각 개발 단계(요구-설계-상세설계-코딩)에 대응하는 검증·확인(V&V) 테스트 계층(단위-통합-시스템-인수)의 1:1 매핑을 통한 품질 보증 구조화.
- 단계별 종료 기준(Exit Criteria) : 각 공정 종료 시마다 공식 검토(Formal Review)와 베이스라인(Baseline) 수립 후의 다음 단계 전이.

## Ⅳ. 폭포수 모델과 애자일 방법론의 비교

- 핵심 요약 : 계약·문서·순차 통제 중심 체계와 협업·반복·변경 수용 중심 체계의 대비.
- 두 방법론의 다축 비교.

| 비교 항목 | 폭포수 모델 (Waterfall) | 애자일 방법론 (Agile) |
|---|---|---|
| 개발 방식 | 단계별 순차 진행, 이전 단계 복귀 곤란 | 반복·점증(Iterative & Incremental) 스프린트 개발 |
| 요구사항 변경 | 초기 동결 후 변경통제위원회(CCB) 절차의 엄격 관리 | 스프린트 단위의 지속적 변경 수용 |
| 동작 소프트웨어 가시화 | 개발 후반부(테스트 단계) 이후 | 매 반복 주기마다 동작 결과 제공 |
| 문서 및 산출물 | 표준 산출물 중심의 방대한 문서화 | 동작 소프트웨어 중심의 경량 문서화 |
| 적합 프로젝트 | 요구사항이 명확한 공공·국방·대규모 계약 사업 | 요구 불확실성이 큰 신규·혁신 서비스 |

## Ⅴ. 폭포수 모델의 장점과 한계

- 핵심 요약 : 예측 가능성·문서 자산의 장점, 후반부 결함 폭발·변경 경직성·문서 부담의 한계.
- 장점
  1. 전체 프로젝트 범위와 일정의 초기 명확 가시화.
  2. 단계별 산출물 풍부에 따른 인력 교체 시 인수인계 용이성.
  3. 대규모 공공·국방 사업의 계약·예산 관리 적합성.
  4. 정해진 프로세스와 설계서 기반 작업이 가능한 초보 개발자 친화성.
- 한계점 1 : 후반부 빅뱅 통합(Big Bang Integration) 단계의 결함 폭발 위험
  - 한계점 : 분석·설계·구현의 순차 완료 후 프로젝트 말기 테스트 단계에서 서브시스템 간 통합 오류의 집중 분출로 납기 지연·사업 파행 초래.
  - 해결 방안 : V-모델 변형 적용을 통한 각 개발 단계별 대응 테스트 레벨(단위-통합-시스템-인수)의 사전 설계, CI(Continuous Integration) 자동화 파이프라인의 조기 구축.
- 한계점 2 : 요구사항 변경에 대한 극심한 경직성 및 고객 피드백 단절
  - 한계점 : 초기 요구사항 동결 후 비즈니스 환경 급변 시에도 까다로운 스코프 변경 절차로 인한 최종 인도물 고객 만족도 급락.
  - 해결 방안 : 공식 변경통제위원회(CCB)의 신속한 영향도 평가 체계 확립, 초기 단계 핵심 기능 프로토타이핑(Prototyping) 병행을 통한 고객 조기 검증.
- 한계점 3 : 방대한 문서 산출물 작성으로 인한 엔지니어링 리소스 낭비
  - 한계점 : 프로젝트 일정의 상당 부분이 검수용 형식 문서 작성에 소모되는 정작 핵심 소스코드 설계 품질·테스트의 부실화.
  - 해결 방안 : 프로젝트 규모·특성에 맞춘 산출물 테일러링 가이드라인 적용, 자동 문서화 도구(Swagger, Javadoc) 활용을 통한 산출물 작성 공수 절감.

## Ⅵ. 현대 엔지니어링 환경에서의 기술사적 제언

- 핵심 요약 : 요구사항 명확성 기반 방법론 선정과 단계별 게이트웨이 검증의 결합.
- 요구사항 명확성에 따른 방법론 선정(Stacey 매트릭스) : 기술·요구사항이 모두 확실한 도메인(공공 행정 시스템 재구축 등)에서 폭포수 모델의 계약·일정 통제 우위를 감안한 무조건적 애자일 추종 지양과 프로젝트 복잡도 기반의 합리적 채택.
- 단계별 게이트웨이 검증(Phase-Gate)을 통한 품질 조기 통제 : 분석 단계 종료 시점의 실사용자 참여 UI(User Interface) 프로토타이핑 결합, 설계 단계 종료 시점의 ATAM(Architecture Tradeoff Analysis Method) 아키텍처 평가 의무화를 통한 후반부 요구 불일치 리스크의 선제 차단.

## Ⅶ. 결론

- 핵심 요약 : 폭포수 모델은 명확한 요구 도메인에서 여전히 유효한 통제 중심 개발 방법론.
- 요약 : 순차 공정·문서 산출물·변경 통제의 체계성이 강점이자 한계의 원천.
- 시사점 : V-모델 검증 통합, 게이트웨이 평가, 방법론 테일러링을 통한 경직성 보완 필요.
