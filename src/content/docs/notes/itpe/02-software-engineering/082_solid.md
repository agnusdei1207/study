소프트웨어 공학 → 객체지향·설계 → **객체지향 설계원칙 SOLID(DIP 포함)**

## 30초 인출

- 본질: SOLID는 변경에 유연하고 이해하기 쉬운 객체지향 설계를 위한 다섯 원칙(SRP·OCP·LSP·ISP·DIP)
- 메커니즘: 클래스의 책임을 하나로 나누고(SRP), 확장에는 열고 수정에는 닫으며(OCP), 하위 타입이 상위 타입을 대체하고(LSP), 인터페이스를 쪼개고(ISP), 추상화에 의존(DIP)
- 통찰: 원칙을 모든 클래스에 기계적으로 적용하면 과설계가 되므로 요구가 반복해서 바뀌는 지점에 우선 적용해 변경 비용을 줄임

<details>
<summary>핵심 용어</summary>

- **SRP(Single Responsibility Principle, 단일 책임 원칙)** : 클래스는 변경 이유가 하나여야 한다는 원칙
- **OCP(Open-Closed Principle, 개방-폐쇄 원칙)** : 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙
- **LSP(Liskov Substitution Principle, 리스코프 치환 원칙)** : 하위 타입은 상위 타입을 대체해도 동작이 깨지지 않아야 한다는 원칙
- **ISP(Interface Segregation Principle, 인터페이스 분리 원칙)** : 클라이언트는 쓰지 않는 메서드에 의존하지 않아야 한다는 원칙
- **DIP(Dependency Inversion Principle, 의존관계 역전 원칙)** : 상위 모듈이 하위 모듈의 구체 구현이 아닌 추상화에 의존해야 한다는 원칙

</details>

## 2~4교시 25점 답안

## Ⅰ. SOLID의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **SOLID** 는 변경에 유연한 객체지향 설계를 위한 다섯 원칙 |
| 목적 | 변경 영향의 국소화와 재사용성·유지보수성 향상 |

## Ⅱ. SOLID의 특징

| 특징 | 의미 |
|---|---|
| 변경 대응 | 변경 이유별 책임 분리 |
| 추상화 지향 | 구체 구현이 아닌 인터페이스에 의존 |
| 상호 보완 | 다섯 원칙이 함께 결합도를 낮춤 |

## Ⅲ. 다섯 원칙의 구조

### 다섯 원칙의 관계

```text
SRP ── 클래스의 책임을 하나로
OCP ── 확장은 추가로, 수정은 최소로 ── (LSP·DIP로 뒷받침)
LSP ── 하위 타입의 상위 타입 대체
ISP ── 작고 역할별 인터페이스
DIP ── 추상화에 의존
```

### 확대: DIP 적용 전후

```text
전: OrderService → MySqlOrderRepository (구체 클래스)
후: OrderService → OrderRepository(인터페이스) ← MySqlOrderRepository
```

## Ⅳ. 원칙별 위반 사례와 해결

| 원칙 | 위반 사례 | 해결 |
|---|---|---|
| SRP | 한 클래스가 주문 처리와 이메일 발송을 모두 담당 | 책임별 클래스 분리 |
| OCP | 결제 수단 추가 때마다 조건문 수정 | 결제 인터페이스와 구현체 추가 |
| LSP | 하위 클래스가 상위 메서드 계약을 깨뜨림 | 상속 대신 구성 또는 계약 준수 |
| ISP | 큰 인터페이스의 불필요한 메서드 구현 | 역할별 인터페이스 분리 |
| DIP | 구체 클래스 직접 생성 | 인터페이스 의존과 주입 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 기계적 적용으로 클래스·인터페이스 과다 | 변경이 반복되는 지점에 우선 적용 |
| 원칙 간 충돌 시 판단 곤란 | 변경 비용 기준으로 우선순위 결정 |
| 원칙을 이해하고도 코드 리뷰 누락 | 리뷰 체크리스트에 반영 |

## Ⅵ. 제언

요구가 자주 바뀌는 지점(결제 수단·외부 연동 등)에 OCP·DIP를 우선 적용하고, 변경이 드문 부분은 단순하게 유지

### 적용 우선순위

```text
변경 이력 분석
    ├─ 자주 바뀌는 지점 → OCP·DIP 적용
    └─ 거의 안 바뀜 → 단순 구현 유지
```

### 확대: 적용 판단

```text
새 요구 발생 시 같은 위치를 반복 수정?
    ├─ 예 → 추상화 도입
    └─ 아니오 → 현행 유지
```

### 선택 근거: 전면 적용과의 비교

| 구분 | 모든 곳에 적용 | 제언: 변경 지점 우선 |
|---|---|---|
| 클래스 수 | 과다 | 필요한 만큼 |
| 변경 비용 | 낮으나 복잡도 증가 | 변경 지점에서 감소 |
| 이해 난이도 | 높음 | 적정 |
