## 1. 객체지향 설계원칙 SOLID의 개요 및 필요성

### (1) SOLID 원칙의 정의
- 로버트 C. 마틴(Uncle Bob)이 정립한 **유지보수성(Maintainability), 확장성(Extensibility), 테스트 용이성(Testability)이 뛰어난 고품질 객체지향 소프트웨어를 설계하기 위한 5대 핵심 기본 원칙**.

### (2) SOLID의 궁극적 지향점
- **높은 응집도(High Cohesion)**와 **낮은 결합도(Low Coupling)**를 구조적으로 달성.
- 새로운 요구사항 추가 시 기존의 검증된 코드를 수정하지 않고(폐쇄), 다형성을 통해 새로운 코드를 안전하게 덧붙이는(개방) 소프트웨어 무결성 유지.

## 2. SOLID 5대 핵심 원칙 및 메커니즘

### (1) SOLID 5원칙 상호작용 구조도
```text
+-------------------------------------------------------------------------+
|                  객체지향 설계 5대 원칙 (SOLID) 구조 및 매핑            |
+-------------------------------------------------------------------------+
|  [ 목표 : 변경에 유연한 고품질 아키텍처 (OCP : 개방-폐쇄 원칙 달성) ]    |
|                                    │                                    |
|         ┌──────────────────────────┴──────────────────────────┐         |
|         v (응집도 극대화 관점)                                v (결합도 최소화 관점) |
|  [ SRP : 단일 책임 원칙 ]                             [ DIP : 의존관계 역전 원칙 ]
|  - 클래스는 단 하나의 변경 이유만 가짐                - 구체가 아닌 추상화에 의존
|  - 액터(Actor)별 책임 격리                            - 인터페이스 소유권 역전
|         │                                                     │         |
|         v                                                     v         |
|  [ ISP : 인터페이스 분리 원칙 ]                       [ LSP : 리스코프 치환 원칙 ]
|  - 클라이언트별 특화 인터페이스 분할                  - 하위 타입은 상위 타입 대체
|  - 불필요한 메서드 의존 강제 배제                     - 계약에 의한 설계 준수   |
+-------------------------------------------------------------------------+
```

### (2) SOLID 5대 원칙 상세 비교
| 원칙 | 영문명 | 핵심 개념 및 규칙 | 위반 시 발생하는 코드 스멜(Smell) |
|---|---|---|---|
| **SRP** | Single Responsibility | 한 클래스는 단 하나의 책임(단 하나의 변경 사유)만 가져야 함 | 클래스 비대화(God Object), 엉뚱한 수정에 의한 연쇄 결함 |
| **OCP** | Open-Closed | 확장에 대해서는 열려 있고(Open), 수정에 대해서는 닫혀 있어야 함(Closed) | 신규 기능 추가 시 기존 `if-else` / `switch` 조건문 대량 수정 |
| **LSP** | Liskov Substitution | 하위 클래스는 언제나 자신의 상위 클래스를 대체할 수 있어야 함 | `instanceof` 타입 검사 분기 남발, 상위 계약 파괴 |
| **ISP** | Interface Segregation | 클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 함 | 껍데기만 남은 빈 구현 메서드(throw UnsupportedException) |
| **DIP** | Dependency Inversion | 고수준 모듈은 저수준 모듈에 의존해서는 안 되며, 둘 다 추상화에 의존해야 함 | 상위 비즈니스 로직 내 `new 구체클래스()` 직접 생성 강결합 |

## 3. DIP(의존관계 역전 원칙) 심층 분석

### (1) 전통적 절차적 의존 vs DIP 역전 의존 구조도
```text
+-------------------------------------------------------------------------+
|                  전통적 의존 구조 vs DIP 적용 의존 구조 비교            |
+-------------------------------------------------------------------------+
| [ 전통적 구조 : 상위가 하위에 종속 ]                                    |
|   +-----------------------+              +-----------------------+      |
|   | OrderService (비즈니스)| ───────────▶ | MySQLRepository (DB)  |      |
|   +-----------------------+    (의존)    +-----------------------+      |
|   (DB 기술이나 SQL 벤더 변경 시 핵심 비즈니스 로직까지 오염 및 수정 불가피) |
+─────────────────────────────────────────────────────────────────────────+
| [ DIP 적용 구조 : 둘 다 추상화에 의존 (의존 방향 역전) ]                 |
|   +-----------------------+              +───────────────────────+      |
|   | OrderService (고수준)  | ───────────▶ │ <<interface>>         │      |
|   +-----------------------+    (의존)    │ OrderRepository       │      |
|                                          +───────────────────────+      |
|                                                      ▲                  |
|                                                      │ (구현/실체화)    |
|                                          +───────────────────────+      |
|                                          | MySQLRepository (저수준)│     |
|                                          +───────────────────────+      |
+-------------------------------------------------------------------------+
```

### (2) DIP의 핵심 실천 메커니즘
- **인터페이스 소유권의 역전**: `OrderRepository` 인터페이스는 데이터베이스 패키지에 속하는 것이 아니라, 고수준 비즈니스 로직 패키지(`OrderService`와 같은 계층)에 속함.
- **제어의 역전(IoC) 및 의존성 주입(DI)**: 애플리케이션 실행 시점에 스프링 IoC 컨테이너가 생성자 주입(Constructor Injection)을 통해 구현체를 외부에서 주입해 줌으로써, 비즈니스 코드는 순수 POJO 상태를 유지함.

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **간편 결제 수단 추가 시 기존 30개 파일 수정**<br>(네이버페이 추가 시 소스 전역 수정) | 결제 분기마다 구체 클래스를 직접 호출하여 OCP/DIP 위반 | `PaymentGateway` 인터페이스 정의 및 전략(Strategy) 패턴 기반 DI 주입 | 신규 결제사 추가 시 기존 소스 수정 0줄, 무중단 확장 |
| **직사각형 상속한 정사각형의 면적 계산 왜곡**<br>(가로 세로 변경 시 기대값 파탄 사고) | 상위 직사각형의 불변식(가로/세로 독립성)을 깨뜨린 부모 상속 남용(LSP 위반) | 상속 관계 폐기, 상위 `Shape` 인터페이스 분리 및 합성(Composition) 채택 | 기하 알고리즘 다형성 계산 정확도 100% 보장 |
| **MySQL에서 DynamoDB 전환 시 서비스 전면 재구축**<br>(엔터프라이즈 저장소 교체 마비) | 서비스 계층이 MySQL DAO 구체 클래스를 직접 `new`하여 강결합(DIP 위반) | 도메인 전용 리포지토리 인터페이스 정의 및 헥사고날 아키텍처 포트/어댑터 분리 | 서비스 계층 코드 보존율 100%, 저장소 격리 전환 완결 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 기계적 상속과 구체 클래스 결합]        [현대: 클린/헥사고날 아키텍처 기반의 DIP 실천]
- 무분별한 class 상속 (LSP 위반)      ──▶   - 인터페이스 합성(Composition over Inheritance)
- 비즈니스와 인프라의 뒤엉킴 (SRP 위반) ──▶   - 헥사고날 포트-어댑터 분리 (DIP의 아키텍처화)
- 교조주의적 원칙 남용 (클래스 폭증)   ──▶   - 도메인 복잡도에 기반한 실용적 SOLID 거버넌스
```

- **DIP의 현대적 아키텍처 확장 (클린·헥사고날 아키텍처)**: DIP는 클래스 간의 설계 원칙에 그치지 않고, 시스템 전체의 아키텍처를 결정하는 핵심 원리임. **"도메인 중심의 비즈니스 코어가 중심에 서고, DB·웹·메시지 큐 같은 인프라는 외곽 어댑터로 밀려나 인터페이스(포트)에 의존하게 만드는 헥사고날(Ports and Adapters) 아키텍처"**가 곧 DIP의 거시적 완성형임을 부각해야 함.
- **실용적 SOLID 엔지니어링 (Pragmatic Engineering)**: 원칙에 매몰되어 1줄짜리 인터페이스를 무한정 양산하는 교조주의를 경계해야 함. 변하지 않는 단순 데이터 전송 객체(DTO)나 단순 조회 모듈에는 YAGNI(You Aren't Gonna Need It)를 적용하고, **비즈니스 규칙이 빈번히 변경되거나 외부 연계가 잦은 핵심 도메인 영역에 선별적으로 SOLID를 집중 투입**하는 트레이드오프 균형 감각을 피력해야 함.
