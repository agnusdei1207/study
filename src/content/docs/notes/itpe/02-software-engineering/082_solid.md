## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어공학 → 객체지향 및 아키텍처 설계 → **객체지향 설계원칙 SOLID**

---

## 30초 인출

- 본질: **SOLID** 는 로버트 C. 마틴(Robert C. Martin)이 정립한 객체지향 소프트웨어 설계의 5대 핵심 원칙으로, 모듈 간 결합도를 낮추고 응집도를 극대화하여 요구사항 변경에 유연하게 대응할 수 있도록 하는 아키텍처 품질 가이드라인
- 메커니즘: 단일 액터 중심 책임 분리(SRP) → 인터페이스 기반 다형성 확장(OCP) → 계약에 의한 상속 치환(LSP) → 클라이언트 맞춤형 인터페이스 분할(ISP) → 고수준 정책과 저수준 세부사항의 추상화 의존 역전(DIP)
- 통찰: 무분별하고 기계적인 추상화는 인터페이스 폭증과 과도한 간접 참조로 시스템 복잡성을 가중시키므로 비즈니스 변경 가능성과 결합 위험도를 분석하여 적정 수준의 추상화 경계를 수립할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **SRP (Single Responsibility Principle)** : 클래스는 단 하나의 변경 이유(단일 액터의 요구)만을 가져야 한다는 원칙
- **OCP (Open-Closed Principle)** : 소프트웨어 개체는 확장에 열려 있고, 기존 코드 수정에는 닫혀 있어야 한다는 원칙
- **LSP (Liskov Substitution Principle)** : 서브타입은 슈퍼타입의 행위 규약을 위배하지 않고 언제나 대체 가능해야 한다는 원칙
- **ISP (Interface Segregation Principle)** : 클라이언트는 자신이 사용하지 않는 인터페이스 메서드에 강제 의존하지 않아야 한다는 원칙
- **DIP (Dependency Inversion Principle)** : 고수준 모듈이 저수준 모듈에 직접 의존하지 않고, 둘 모두 추상화(Interface)에 의존해야 한다는 원칙

</details>

## 2~4교시 예상문제 (25점)

> 객체지향 설계의 핵심인 SOLID 5대 원칙의 개념과 상호 연계 구조를 설명하고, 의존성 역전 원칙(DIP)과 제어의 역전(IoC)/의존성 주입(DI)의 관계 및 SOLID 위반 시 발생하는 코드 스멜과 리팩토링 방안을 제시하시오.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 유지보수성과 확장성이 뛰어난 객체지향 시스템을 구축하기 위해 준수해야 하는 5대 설계 원칙(SRP, OCP, LSP, ISP, DIP)의 집합 |
| 목적 | 모듈 간 결합도(Coupling) 완화, 응집도(Cohesion) 극대화, 코드 중복 제거 및 요구사항 변경 시 파급 효과(Ripple Effect) 최소화 |

## Ⅱ. 핵심 특징

SOLID는 개별 독립 원칙이 아니며, 응집도 향상(SRP, ISP)과 추상화 결합(OCP, LSP, DIP)이 유기적으로 맞물려 동작.

| 설계 관점 | 해당 원칙 | 핵심 가치 및 적용 메커니즘 |
|---|---|---|
| **책임과 응집도 (Cohesion)** | **SRP** (단일 책임) | 단일 변경 이유(액터)를 기준으로 모듈 분리, 만능 클래스(God Class) 방지 |
| **확장과 다형성 (Extension)** | **OCP** (개방-폐쇄) | 추상 인터페이스를 통해 새로운 기능 추가 시 기존 클라이언트 코드 수정 차단 |
| **상속과 계약 (Contract)** | **LSP** (리스코프 치환) | 계약에 의한 설계(DbC) 준수, 서브클래싱 시 사전조건 약화 및 사후조건 강화 금지 |
| **인터페이스 격리 (Segregation)**| **ISP** (인터페이스 분리)| 호출자 맞춤형 역할 인터페이스(Role Interface) 도출, 비대한 인터페이스 분할 |
| **의존성 거버넌스 (Inversion)** | **DIP** (의존관계 역전)| 비즈니스 도메인(고수준)이 DB/인프라(저수준)에 종속되는 방향성을 추상화로 역전 |

## Ⅲ. 체계·프로세스

SOLID 5대 원칙 간의 상호작용 체계 및 DIP 기반 아키텍처 의존 흐름.

```text
+---------------------------------------------------------------------------------------------------------+
|                                    SOLID 5대 원칙 간 연계 체계 및 DIP 구조                               |
+---------------------------------------------------------------------------------------------------------+
                                                                                                           
  [요구사항 변경 발생]                                                                                     
           │                                                                                               
           ▼                                                                                               
  +─────────────────+         단일 액터 분리                                                               
  |     SRP 적용    | ───────────────────────────────┐                                                     
  +─────────────────+                                │                                                     
           │                                         ▼                                                     
           │                          +─────────────────────────────+                                      
           │                          |       ISP 역할 인터페이스    |                                      
           │                          +─────────────────────────────+                                      
           ▼                                         ▲                                                     
  +─────────────────+                                │                                                     
  |     DIP 적용    | ─── 고수준 정책이 인터페이스 소유──┤                                                     
  +─────────────────+                                │                                                     
           │                                         ▼                                                     
           ▼                          +─────────────────────────────+                                      
  +─────────────────+                 |   <<interface>> Repository  |                                      
  |  OCP / LSP 실현 | ───────────────> +─────────────────────────────+                                      
  +─────────────────+                                ▲                                                     
                                      ┌──────────────┴──────────────┐                                      
                                      │ 상속/구현 (LSP 대체 가능)   │                                      
                         +──────────────────────────+  +──────────────────────────+                        
                         |    RDB 구현체 (MySQL)    |  |   NoSQL 구현체 (MongoDB) |                        
                         +──────────────────────────+  +──────────────────────────+                        
                                      ▲                                                                    
                                      │ 외부 IoC 컨테이너가 런타임에 주입 (DI)                             
```

- **DIP 기반 설계 리팩토링 3단계 프로세스**:
  1. **고수준 정책과 저수준 구현 분리** : 주문 비즈니스 로직(OrderService)과 데이터베이스 접근 코드(MySQLDao) 간의 직접적인 `new` 결합 식별.
  2. **추상화 인터페이스 추출 및 소유권 역전** : 고수준 도메인 관점에서 필요한 행위를 규정한 `OrderRepository` 인터페이스를 도메인 패키지 내에 선언.
  3. **의존성 주입(DI) 결합** : 스프링 컨테이너 등 외부 조립기가 런타임에 구체 구현체(MySQLOrderRepository)를 OrderService 생성자로 전달하도록 제어 역전(IoC) 적용.

## Ⅳ. 종류·비교

#### SOLID 원칙별 위반 징후(Code Smell) 및 해결 패턴 비교

| 원칙 | 위반 시 발생하는 코드 스멜 | 공학적 해결 방안 및 디자인 패턴 |
|---|---|---|
| **SRP** (단일 책임) | 수천 라인의 거대 클래스(God Object), 잦은 머지 충돌 | 책임 단위 클래스 분리, 파사드(Facade) 패턴 적용 |
| **OCP** (개방-폐쇄) | 기능 확장 시 기존 코드에 `if-else` / `switch` 분기문 급증 | 전략(Strategy) 패턴, 팩토리 메서드(Factory Method) 패턴 |
| **LSP** (리스코프 치환) | 호출 측에서 `instanceof` 타입 다운캐스팅 남발, 빈 메서드 오버라이딩 | 상속 대신 합성(Composition over Inheritance) 사용 |
| **ISP** (인터페이스 분리) | 사용하지 않는 인터페이스 메서드에 빈 바디 구현(`throw UnsupportedException`) | 어댑터(Adapter) 패턴을 통한 역할별 다중 인터페이스 구현 |
| **DIP** (의존관계 역전) | 상위 서비스 클래스 내부에서 하위 세부 클래스를 직접 인스턴스화 | 생성자 기반 의존성 주입(Constructor Injection), 헥사고날 포트-어댑터 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 지나친 인터페이스 세분화로 인해 파일 수 폭증 및 네비게이션 복잡도 증가 | YAGNI(You Aren't Gonna Need It) 원칙을 준수하여 실제 확장이 예견되는 지점에 한해 단계적 추상화 도입 |
| 상속 계층의 깊이가 깊어짐에 따라 LSP를 위배하는 암묵적 규약 파괴 발생 | 계약에 의한 설계(Design by Contract) 도구 도입 및 기반 클래스 대신 인터페이스와 객체 합성 활용 |
| 스프링 등 프레임워크의 과도한 DI 설정으로 인한 런타임 빈 순환 참조(Circular Dependency) 유발 | 도메인 이벤트(Domain Event) 발행을 통한 비동기 결합 전환 및 서비스 간 의존성 방향 단방향 강제 |

## Ⅵ. 제언

SOLID 원칙은 단순 코딩 규칙이 아닌 도메인 주도 설계(DDD) 및 클린/헥사고날 아키텍처의 근간이므로, 정적 코드 분석 도구를 CI/CD 파이프라인에 통합하여 지속적으로 아키텍처 무결성을 점검할 필요가 있음.

```text
[요구사항 분석] ──> [도메인 모델링 (DDD)] ──> [SOLID 원칙 코딩] ──> [정적 아키텍처 검증] ──> [CI/CD 자동 배포]
                     (경계 설정 & 포트 도출)    (인터페이스 분리 & DI)   (ArchUnit / SonarQube)     (클린 코드 유지)
```

| 거버넌스 단계 | 적용 기술 및 방법 | 핵심 통제 지표 |
|---|---|---|
| **설계 표준화** | 인터페이스 소유권을 도메인 코어에 배치(Ports & Adapters) | 외부 인프라 변경 시 도메인 계층 코드 수정률 0% 달성 |
| **정적 검증 자동화** | ArchUnit 기반 아키텍처 단위 테스트 및 SonarQube 정적 분석 | 결합도 지수(Afferent/Efferent Coupling) 및 순환 의존 제로 |
| **품질 메트릭 관리** | C&K 메트릭(WMC, CBO, LCOM) 지속적 모니터링 | 모듈 응집도(LCOM) 낮음 유지 및 클래스당 메서드 수 제한 |
