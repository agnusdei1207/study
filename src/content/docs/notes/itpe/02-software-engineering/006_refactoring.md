## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 유지보수·형상관리 → **리팩토링(코드스멜)**

## 30초 인출

- 본질: 리팩토링(Refactoring)은 소프트웨어의 외부 관찰 동작을 보존하면서 내부 구조를 개선하여 가독성, 유지보수성, 확장성을 높이는 엔지니어링 기법
- 메커니즘: 정적분석 기반 코드스멜(Code Smell) 식별 → 단위 테스트 세이프티넷 확보 → 마이크로 단위 구조 변환 → 자동화 회귀테스트 통과 검증
- 통찰: 테스트 커버리지 없는 대규모 구조 변경은 회귀 결함을 유발하므로 특성화 테스트 확보 후 변경 빈도가 높은 핫스팟 모듈부터 점진적 개선

<details>
<summary>핵심 용어</summary>

- **리팩토링(Refactoring)** : 소프트웨어의 외부 동작은 그대로 유지한 채, 코드를 이해하고 수정하기 쉽도록 내부 구조를 개선하는 기법
- **Code Smell(코드스멜)** : 시스템의 잠재적 설계 결함이나 기술 부채를 암시하는 코드 내부의 나쁜 징후
- **Regression Test(회귀 테스트)** : 코드 변경 이후 기존 기능이 파괴되지 않고 정상 동작함을 보장하는 반복 테스트
- **Extract Method(메서드 추출)** : 하나의 메서드가 과도한 책임을 지닐 때 독립적인 기능을 별도 메서드로 분리하는 핵심 기법
- **Characterization Test(특성화 테스트)** : 레거시 코드의 현재 실제 동작을 기준선으로 고정하여 변경 시 의도치 않은 파괴를 방지하는 테스트
- **Technical Debt(기술 부채)** : 빠른 납기를 위해 선택한 조잡한 설계와 코드로 인해 향후 유지보수 비용이 누적되는 현상

## 2~4교시 25점 답안

## Ⅰ. 리팩토링의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **리팩토링(Refactoring)** 은 소프트웨어의 외부 관찰 동작을 보존하면서 내부 구조를 개선하여 품질을 높이는 정제 활동 |
| 목적 | 코드 가독성 향상, 기술 부채 해소, 유지보수 비용 절감 및 신규 기능 추가의 용이성 확보 |

## Ⅱ. 리팩토링의 핵심 특징

| 특징 | 의미 |
|---|---|
| 외부 동작 불변 | 코드 구조 변경 전후의 시스템 입력 대비 출력 및 부수 효과의 완전한 동일성 유지 |
| 마이크로 스텝 | 컴파일 및 테스트가 가능한 최소 단위(Small Steps)로 코드를 점진적 변환 |
| 테스트 주도 보호 | 기존 동작을 입증하는 자동화 단위·회귀 테스트 세이프티넷을 전제 조건으로 수행 |

## Ⅲ. 코드스멜 식별과 리팩토링 수행 메커니즘

### 안전한 리팩토링 실행 루프

```text
[코드스멜 식별] ──→ [단위·특성화 테스트 확보]
                           │
                           ▼
[회귀 테스트 검증] ←── [마이크로 리팩토링 수행]
       │
       ├─ 실패 → 즉시 롤백 및 원인 분석
       └─ 통과 → 변경 커밋 및 다음 코드스멜 정제
```

### 마이크로 단계별 코드 변환 및 검증 절차

```text
메서드 추출(Extract Method) 대상 코드 블록 식별
    ↓
새로운 독립 메서드로 분리 및 파라미터 전달
    ↓
즉시 단위 테스트 실행
    ├─ 테스트 통과 → 원래 위치를 새 메서드 호출로 치환
    └─ 테스트 실패 → 변경 취소 및 종속성 재분석
    ↓
전체 회귀 테스트 스위트 일괄 수행 후 소형 단위 Git 커밋
```

| 주요 코드스멜 | 구조적 문제점 | 핵심 해결 리팩토링 기법 |
|---|---|---|
| Duplicated Code (중복 코드) | 로직 수정 시 다중 위치 동시 수정 누락 위험 | **Extract Method** , Pull Up Method |
| Long Method (장대 함수) | 단일 책임 원칙 위반 및 가독성 급감 | **Extract Method** , Replace Temp with Query |
| Large Class (거대 클래스) | 클래스의 역할 과다로 응집도 저하 및 결합도 증가 | Extract Class, Extract Subclass |
| Feature Envy (기능 편애) | 다른 클래스의 데이터나 메서드를 과도하게 참조 | Move Method, Move Field |
| Switch Statements (복잡한 분기문) | 신규 조건 추가 시 분기문 전체 전수 수정 유발 | Replace Conditional with Polymorphism (다형성 전환) |

## Ⅳ. 신규 기능 개발, 리팩토링, 재공학(Re-engineering) 비교

| 비교 항목 | 신규 기능 개발 | 리팩토링 (Refactoring) | 재공학 (Re-engineering) |
|---|---|---|---|
| 주 목적 | 비즈니스 신규 가치 추가 | 내부 구조 개선 및 가독성 확보 | 레거시 아키텍처 전면 현대화 |
| 외부 동작 변화 | **동작 추가 및 변경** | **동작 불변 (완전 동일)** | 일부 변경 또는 전면 재설계 |
| 수행 주기 | 스프린트 내 기능 구현 시 | 기능 추가 전후 상시 점진적 수행 | 시스템 수명 한계 도달 시 프로젝트 단위 |
| 테스트 의존성 | 신규 기능 검증 테스트 작성 | **기존 자동화 회귀 테스트 필수** | 통합 및 시스템 인수 테스트 중심 |
| 투입 위험도 | 신규 결함 유입 가능성 | 안전장치 확보 시 위험 극소화 | 고비용, 고위험 대규모 마이그레이션 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 테스트 커버리지가 부재한 레거시 코드 수정 시 의도치 않은 회귀 결함 발생 | 수정 전 기존 동작을 고정하는 **Characterization Test(특성화 테스트)** 선행 구축 |
| 리팩토링과 신규 기능 추가를 동시에 진행하여 결함 원인 추적 불가 | 기능 추가 모드(두 모자 기법)와 리팩토링 모드를 엄격히 분리하고 개별 커밋 |
| 상용 릴리스 일정 압박으로 인한 리팩토링 작업의 지속적 연기 및 부채 심화 | 기술 부채 백로그를 정량화(SonarQube)하고 스프린트 용량의 10~20% 고정 할당 |

## Ⅵ. 제언

정적분석 기반 기술 부채 핫스팟 식별과 특성화 테스트를 결합한 점진적 리팩토링 파이프라인 정착

### 핫스팟 중심 점진적 리팩토링 파이프라인

```text
정적 코드 분석 도구(SonarQube) 실행
    ↓
수정 빈도(Churn)와 복잡도(Complexity) 결합 분석
    ↓
고위험 핫스팟 모듈 선정
    ↓
특성화 테스트 작성 및 안전망 확보
    ↓
점진적 마이크로 리팩토링 및 CI 파이프라인 자동 검증
```

### 기능 추가와 리팩토링 분리 운영 절차 (두 개의 모자)

```text
작업 착수
    ├─ 모자 A: 기능 추가 (기존 코드 수정 금지, 신규 테스트 작성 및 통과)
    └─ 모자 B: 리팩토링 (기능 추가 금지, 구조 개선 및 기존 테스트 통과 유지)
    ↓
단계별 분리 커밋 및 리뷰
```

### 선택 근거: 빅뱅 재작성과 점진적 리팩토링 비교

| 구분 | 빅뱅 전면 재작성 (Big Bang) | 제언: 핫스팟 기반 점진적 리팩토링 |
|---|---|---|
| 전환 위험 | 서비스 중단 및 예산 초과 위험 높음 | 운영 중 무중단 점진적 정제 가능 |
| 소요 기간 | 장기간 대규모 프로젝트 소요 | 일일 스프린트 단위 상시 수행 |
| 검증 가능성 | 프로젝트 말기 통합 시 결함 폭증 | 매 마이크로 스텝마다 회귀 검증 완료 |
