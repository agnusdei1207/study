## 연관 키워드

- 리팩토링(Refactoring), 코드 스멜(Code Smell), 기술 부채(Technical Debt)
- 메서드 추출(Extract Method), 테스트 안전망(Safety Net), 보이스카우트 규칙(Boy Scout Rule), 정적 분석

## Ⅰ. 리팩토링과 코드 스멜의 개요

- 핵심 요약 : 외부 동작을 바꾸지 않고 내부 구조를 고치는 개선 활동과, 설계 결함의 징후를 찾아 해소하는 체계.
- 개념 : 소프트웨어의 외부 동작(기능 요구사항)을 바꾸지 않고 내부 구조를 개선해 가독성, 유지보수성, 확장성을 높이는 엔지니어링 기법인 **리팩토링** (Refactoring).
- **코드 스멜** (Code Smell) : 설계 결함, 복잡도 증가, 변경 취약성을 암시하는 코드 수준의 징후나 나쁜 패턴.
- 배경 및 필요성 : 기능이 쌓일수록 구조가 무너져 **기술 부채** (Technical Debt)가 누적되고, 그에 따라 결함 수정과 변경 비용이 커지는 문제.
- 주요 목적 : 소프트웨어 엔트로피 증가 억제, 결함 발생률 감소, 기능 추가 생산성 유지.

## Ⅱ. 리팩토링의 특징

- 핵심 요약 : 기능 보존, 안전망 전제, 소규모 반복을 골자로 하는 구조 개선 활동.

1. 외부 동작(기능 요구사항)의 불변성 유지 → 변경 범위가 내부 구조로 한정되어 안심하고 개선 가능.
2. **테스트 안전망** (Safety Net, 리팩토링 전에 확보하는 회귀 테스트 세트) → 구조를 바꾸는 중에도 기능 파손을 즉시 판별.
3. 소규모 단위 변경 후 즉시 검증하는 점진적 수행 → 문제 발생 시 되돌릴 범위와 충돌 위험 최소화.
4. **정적 분석** (Static Analysis, 코드를 실행하지 않고 규칙 위반과 복잡도를 검사하는 기법) 도구와 코드 리뷰 병행 → 코드 스멜의 조기 탐지.
5. **TDD** (Test-Driven Development, 테스트 주도 개발)의 Red-Green-Refactor 사이클과 연계 → 설계를 테스트로 먼저 고정한 뒤 구조를 개선.

## Ⅲ. 리팩토링의 구조 (흐름)

- 핵심 요약 : 테스트 준비, 스멜 식별, 단위 리팩토링, 테스트 검증이 All Green을 기준으로 순환하는 절차.

```text
[ 테스트 안전망 확보 ]
        ↓
[ 코드 스멜 식별 ]
        ↓
[ 단위 리팩토링 ]
        ↓
[ 단위 테스트 검증 ]
        ↓
  All Green이면 다음 사이클
```

- 테스트 안전망 확보 : 리팩토링 전에 단위·통합 테스트 커버리지를 높여 기능 파손을 즉시 판별할 수 있게 함.
- 코드 스멜 탐지 : SonarQube, Checkstyle 같은 정적 분석 도구와 코드 리뷰로 비정상 복잡도를 찾아냄.
- 소규모 변경과 즉시 검증 : 큰 수정을 피하고 작은 단위로 바꾼 뒤 바로 테스트를 실행해 All Green 상태를 유지.

## Ⅳ. 대표 코드 스멜 유형과 해결 기법 비교

- 핵심 요약 : 코드 스멜 유형마다 문제점과 대응 리팩토링 기법을 1:1로 대응시키는 방식.
- **메서드 추출** (Extract Method) : 긴 메서드에 섞인 여러 책임을 별도 메서드로 떼어내는 대표 리팩토링 기법.

| 코드 스멜 | 문제점 | 해결 리팩토링 기법 |
| --- | --- | --- |
| 긴 메서드(Long Method) | 여러 책임이 섞여 파악이 어렵고 재사용이 불가능 | 메서드 추출 |
| 거대한 클래스(Large Class) | 단일 책임 원칙 위반, 필드와 결합도 과다 | 클래스 추출, 서브클래스 분리 |
| 기능 편애(Feature Envy) | 다른 클래스의 메서드·데이터를 과도하게 참조 | 메서드 이동 |
| 긴 매개변수 목록(Long Parameter List) | 매개변수 순서 혼동, 변경 시 영향 범위 확산 | 객체 보존, 매개변수 객체화 |
| 중복된 스위치 문(Repeated Switch) | 조건 추가 시 여러 파일을 동시에 수정 | 조건문을 다형성으로 대체 |
| 기본형 집착(Primitive Obsession) | 도메인 검증 로직 분산, 타입 안전성 부족 | 기본형 데이터를 객체로 전환 |

## Ⅴ. 리팩토링의 장점과 한계

- 핵심 요약 : 유지보수성과 생산성 개선이라는 장점과, 기능 파손 위험·대규모 일괄 변경·효과 입증의 한계.

1. 가독성, 유지보수성, 확장성 향상.
2. 기술 부채 경감을 통한 결함 발생률 감소.
3. 기능 추가 생산성과 아키텍처 수명 연장.

리팩토링 안전망을 TDD 사이클로 만드는 방식은 다음과 같다.

```text
[ TDD Red-Green-Refactor ]
Red : 실패하는 테스트 작성
  ↓
Green : 최소 구현으로 통과
  ↓
Refactor : 구조 개선 (All Green 유지)
  ↓
다음 기능에서 Red로 반복
```

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **회귀 결함** (Regression Bug) | 자동화된 회귀 테스트가 없는 상태에서 구조를 바꾸면 기존 로직이 깨짐 | **특성화 테스트** (Characterization Test, 현재 동작을 그대로 고정하는 테스트)와 골든 마스터(Golden Master) 테스트를 선행 작성하고, TDD의 Red-Green-Refactor 준수 | 회귀 결함 건수, 테스트 커버리지 |
| **빅뱅 리팩토링** (Big-Bang Refactoring) | 장기 브랜치의 대규모 구조 변경이 신규 기능 브랜치와 대량 충돌하고 일정 지연 | 상시 소규모 개선, 기능 플래그(Feature Toggle)와 트렁크 기반 개발로 주 브랜치 병합 빈도 증가 | 브랜치 수명, 병합 충돌 건수 |
| 정량 효과 입증의 어려움과 과잉 설계 | 취향에 따른 과도한 추상화로 복잡도가 오르고 공수 승인이 어려움 | **SQALE** (Software Quality Assessment based on Lifecycle Expectations) 방법론으로 기술 부채를 측정하고, 순환 복잡도·중복률 지표를 정기 관리 | 기술 부채 비율, 순환 복잡도 |

## Ⅵ. 엔터프라이즈 환경에서의 기술사적 제언

- 핵심 요약 : 정기 소규모 개선을 파이프라인에 내재화하고, 정적 분석 지표로 기술 부채를 경영진이 볼 수 있게 가시화하는 운영 체계.

1. **보이스카우트 규칙** (Boy Scout Rule, 코드를 손댈 때마다 조금 더 깨끗하게 남긴다는 원칙) : 대규모 리팩토링의 일정 위험을 피하기 위해 코드 변경 시마다 품질 기준을 확인하고, CI/CD(Continuous Integration/Continuous Delivery) 파이프라인의 품질 게이트와 연계해 상시 적용하는 것이 필요함.
2. 정량 지표 기반 가시화 : 결함 수정 시간이 늘어나는 기술 부채의 이자를 설득하려면 McCabe 순환 복잡도와 중복률을 대시보드로 시각화하고, SQALE 방법론으로 부채 규모를 환산해 정기 보고 체계에 올려야 함.

## Ⅶ. 결론

- 핵심 요약 : 리팩토링은 안전망 테스트와 소규모 반복을 전제로 하는 지속적 구조 개선 활동.
- 시사점 : 코드 스멜의 상시 탐지와 정량 지표 기반 기술 부채 관리가 지속 가능한 품질 확보의 핵심.
