## 연관 키워드
- 리팩토링, 코드 스멜, 테스트, 중복 제거, 캡슐화

## Ⅰ. 리팩토링의 개요
- 핵심 요약 : 리팩토링은 외부 동작을 보존하면서 내부 구조를 개선해 변경 비용을 낮추는 통제된 코드 변환.
- 개념 : 테스트로 동작을 확인하며 작은 단계로 코드 구조를 정리하는 기법.
- 배경 : 중복·긴 메서드·과도한 결합이 기능 변경과 결함 수정 비용을 높임.
- 목적 : 변경 전후 이해도·시험 가능성·확장성 개선.

## Ⅱ. 리팩토링의 특징 및 장점
- 핵심 요약 : 코드 스멜을 신호로 삼되 테스트 보호망 아래 작은 변환을 반복.
1. 동작 보존 : 외부 관찰 결과 유지 → 기능 변경과 구조 변경 분리.
2. 단계성 : Extract Method, Rename, Move Method 등 작은 변환 → 회귀 원인 축소.
3. 테스트 의존 : 자동시험이 안전망 역할 → 구조 개선 신뢰성 확보.

## Ⅲ. 리팩토링 절차와 코드 스멜
- 핵심 요약 : 냄새 탐지 → 동작 기준선 확보 → 작은 변환 → 시험 → 반복.
```text
코드 스멜 식별 → 테스트 실행 → 한 가지 변환 → 전체 테스트 → 커밋
```
```text
Long Method → Extract Method
Duplicated Code → Extract Method/Class
Feature Envy → Move Method
Large Class → Extract Class
```
- 주요 냄새 : 중복 코드, 긴 메서드, 산탄식 변경, 데이터 덩어리, 임시 필드.

## Ⅳ. 리팩토링과 재작성 비교
- 핵심 요약 : 리팩토링은 기존 시스템에서 점진 개선, 재작성은 구현을 새로 만들어 전환 위험이 큼.
| 기준 | 리팩토링 | 재작성 |
|---|---|---|
| 동작 연속성 | 기존 흐름에서 단계 적용 | 신·구현 병행 또는 일괄 전환 |
| 위험 | 작고 추적 가능한 변경 | 요구 누락·전환·호환 위험 |
| 적합 상황 | 동작을 유지하며 구조 개선 가능 | 기반 기술·요구가 근본적으로 바뀜 |

## Ⅴ. 리팩토링 한계와 대응
- 핵심 요약 : 테스트 부족과 동시 기능변경은 동작 보존을 흔드므로 변경 범위·기준선을 통제.
| 한계 | 영향 | 대응 |
|---|---|---|
| 회귀시험 부족 | 숨은 동작 손상 | 특성화 테스트로 기준선 확보 |
| 대규모 일괄 변경 | 검토·롤백 어려움 | 작은 커밋과 점진 적용 |
| 외부 계약 변화 | API·DB 호환성 파괴 | 호환 계약·전환 어댑터 활용 |

## Ⅵ. 리팩토링 실행 제언
- 핵심 요약 : 팀은 신규 기능의 변경 지점에서 스멜을 정리하고 구조 부채를 가시화.
1. 개발팀은 기능 변경과 구조 변경을 분리한 커밋·리뷰 기준 적용.
2. QA는 테스트 공백이 큰 핵심 모듈부터 특성화 테스트 마련.
3. 아키텍트는 리팩토링을 백로그·품질지표에 반영하고 회고.

## Ⅶ. 결론
- 핵심 요약 : 리팩토링은 동작 보존을 시험으로 확인하며 내부 설계를 지속 개선하는 활동.
- 시사점 : 코드 스멜은 자동 수정 명령이 아니라 변경 비용을 조사할 단서.
