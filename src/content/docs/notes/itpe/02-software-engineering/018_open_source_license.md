## 연관 키워드

- 오픈소스 라이선스, 허용적(Permissive), 카피레프트(Copyleft), Source-Available
- GPL(GNU General Public License), AGPL, LGPL, SBOM(Software Bill of Materials), SCA(Software Composition Analysis), OSPO(Open Source Program Office)

## Ⅰ. 오픈소스 라이선스 체계의 개요

- 핵심 요약 : 소스코드의 복제·수정·배포를 허용하면서 준수 조건을 명시하는 저작권 계약 체계.
- 개념 : 오픈소스 소프트웨어(OSS, Open Source Software)의 저작권자가 사용자에게 복제·수정·배포 권한을 주고, 저작권 고지나 소스 공개 같은 준수 조건을 정한 법적 계약 (**오픈소스 라이선스**, Open Source License).
- 배경 및 필요성 : 현대 소프트웨어는 오픈소스 컴포넌트를 상당 부분 포함하는데, 라이선스 조건을 어기면 저작권 침해 분쟁이나 독점 소스코드의 강제 공개 위험이 생기므로 사전 검증과 준수 체계가 필요함.
- 주요 목적 : 라이선스 조건을 사전에 검증하고 체계적으로 준수해 법적 리스크를 차단.
- 3대 분류 : **허용적** (Permissive), **카피레프트** (Copyleft), 소스 공개형 비오픈소스 (Source-Available).

## Ⅱ. 오픈소스 라이선스의 특징 및 장점

- 핵심 요약 : 조건 강도가 점진적으로 달라지는 스펙트럼 구조와, 카피레프트 계열의 전염성이 핵심 특징.

1. 허용적 : MIT, Apache 2.0은 소스 공개 의무 없이 저작권 고지만 유지하면 재사용 가능 → 상용 제품에 넣기 쉬움.
2. 약한 카피레프트 : LGPL(GNU Lesser General Public License), MPL(Mozilla Public License)은 수정한 라이브러리 범위의 소스만 공개 → 라이브러리 단위의 공개 의무.
3. 강한 카피레프트 : GPL(GNU General Public License) v2·v3은 결합된 파생 저작물 전체의 소스 공개를 요구 → 전염성이 가장 강함.
4. 네트워크 카피레프트 : AGPL(GNU Affero General Public License) v3은 네트워크 서비스로 제공해도 소스 공개 의무가 적용 → SaaS 환경에서 주의 필요.
5. 특허 조항 차등 : Apache 2.0은 명시적 특허 라이선스와 분쟁 방지 조항을 두고, MIT에는 명시 조항이 없음 → 특허 리스크 대응력 차이.
6. Source-Available : BSL(Business Source License), SSPL(Server Side Public License)은 소스는 공개하지만 OSI 인증 오픈소스가 아니며, 경쟁 클라우드 서비스 제공을 제한 → 공개와 사업 보호를 함께 노린 방식.

## Ⅲ. 오픈소스 라이선스의 구조 (흐름)

- 핵심 요약 : 조건 강도 순으로 배열된 라이선스 스펙트럼과, 도입 심의에서 감사까지 이어지는 관리 흐름의 이중 구조.

```text
[ 라이선스 스펙트럼 ]

허용적 : MIT, Apache 2.0
   ↓ 조건 강화
약한 카피레프트 : LGPL, MPL
   ↓ 조건 강화
강한 카피레프트 : GPL v2, v3
   ↓ 조건 강화
네트워크 카피레프트 : AGPL v3
```

```text
[ 오픈소스 관리 프로세스 ]

도입 심의 (라이선스 조건 검토)
      ↓
SBOM 자동 생성 (SPDX, CycloneDX)
      ↓
SCA 검사 (고위험 라이선스 탐지)
      ↓
빌드 차단 (허용되지 않은 라이선스)
      ↓
정기 감사 (라이선스 변경 모니터링)
```

## Ⅳ. 주요 오픈소스 라이선스의 의무 비교

- 핵심 요약 : 소스 공개 의무의 범위와 특허 조항의 유무가 라이선스 선택의 핵심 기준.

| 라이선스 | 구분 | 소스코드 공개 의무 범위 | 특허 조항 | 대표 프로젝트 |
| --- | --- | --- | --- | --- |
| MIT | 허용적 | 없음 (저작권·허가 고지만 표시) | 명시 조항 없음 | React, Node.js |
| Apache 2.0 | 허용적 | 없음 (고지와 변경사항 표시) | 특허 라이선스 부여와 분쟁 방지 | Kubernetes, Kafka |
| LGPL | 약한 카피레프트 | 수정한 라이브러리 자체만 공개, 동적 링킹 시 본체는 비공개 가능 | 특허 라이선스 포함 | glibc |
| GPL v2, v3 | 강한 카피레프트 | 링킹된 전체 애플리케이션 소스 공개 (전염성) | 특허 라이선스 포함 | Linux 커널(v2), GCC(v3) |
| AGPL v3 | 네트워크 카피레프트 | 네트워크 서비스 제공 시에도 전체 소스 공개 | 특허 라이선스 포함 | Grafana, Mastodon |
| SSPL, BSL | Source-Available | 경쟁 클라우드 서비스 제공 제한 (OSI 인증 아님) | 사업자별 상이 | MongoDB(SSPL), Terraform(BSL) |

## Ⅴ. 오픈소스 라이선스 관리의 한계와 방안

- 핵심 요약 : 재사용과 생태계 활용의 장점, 전염성과 전이적 의존성, 라이선스 전환의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 카피레프트 전염성 | GPL·AGPL 컴포넌트와 독점 로직의 결합 → 핵심 소스 공개 위험 | Permissive 우선 채택 원칙, 부득이한 경우 별도 프로세스로 분리해 API로 연동 | 카피레프트 컴포넌트 수 |
| 전이적 의존성 속 라이선스 오염 | 3~4차 하위 의존성의 고위험 라이선스가 감지되지 않음 | SBOM 자동 생성과 SCA 도구 연동, 허용되지 않은 라이선스 유입 시 빌드 차단 | 미승인 라이선스 탐지 건수 |
| Source-Available 전환 | 주요 프로젝트의 라이선스 변경 → 기존 사용 시스템의 준수 리스크 발생 | 의존성 라이선스 변경 모니터링, 완전 오픈소스 포크로의 이전 계획 수립 | 라이선스 변경 의존성 수 |

## Ⅵ. 기업 오픈소스 거버넌스에 대한 기술사적 제언

- 핵심 요약 : 빌드 파이프라인에 SBOM과 SCA를 넣어 자동 통제하고, 전담 조직이 정책과 심의를 맡는 체계.
- 빌드 단계의 자동 통제 : SPDX 또는 CycloneDX 형식의 SBOM을 빌드마다 생성하고 SCA 도구를 CI 파이프라인에 넣어, 카피레프트 유입을 배포 전에 걸러낸다.
- 전담 조직의 정책 운영 : 오픈소스 전담 조직(OSPO)이 도입 심의와 링킹 방식 가이드라인을 만들고, 법무와 협업해 정기 감사를 수행한다.
- 라이선스 변경의 조기 감지 : 주요 의존성의 라이선스 전환 신호를 모니터링하고, 포크 프로젝트로의 전환 경로를 미리 점검해 둔다.

## Ⅶ. 결론

- 핵심 요약 : 오픈소스 라이선스 관리는 조건의 이해에서 그치지 않고, 자동 검사와 조직 거버넌스로 법적 리스크를 통제하는 일.
- 시사점 : 허용적 라이선스 우선, 전염성 격리, SBOM과 SCA의 자동 검사를 함께 운영할 때 오픈소스 활용의 이익을 안전하게 누릴 수 있음.
