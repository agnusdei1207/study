## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어 공학 → 공공 SW·거버넌스 → **오픈소스 라이선스**

## 30초 인출

- 본질: **오픈소스 소프트웨어(Open Source Software, OSS) 라이선스**는 저작권자가 소프트웨어의 사용·수정·재배포 권리와 조건을 정하는 허락
- 메커니즘: **Permissive**(최소 조건) · **Copyleft**(동일 조건 제공) · **Source-Available**(용도 제한 가능)을 구분
- 효과: 라이선스 조건 준수 · 기업 지식재산 보호 · **SBOM(Software Bill of Materials)** 기반 구성요소 관리

<details>
<summary>핵심 용어</summary>

- **Open Source License**: 오픈소스 정의에 맞는 권리를 부여하고 재배포 조건을 정하는 저작권자의 법적 허락
- **Permissive License(허용적 라이선스)**: 저작권·라이선스 고지 등 개별 조건을 지키면서 비교적 폭넓은 재사용·수정·배포를 허용하는 계열 (MIT, Apache 2.0)
- **Copyleft(카피레프트)**: 적용되는 라이선스 조건에 따라 수정·결합 저작물의 배포에 동일 계열의 조건을 요구하는 원칙 (GPL)
- **AGPLv3(Affero General Public License version 3)**: 수정한 프로그램과 원격으로 상호작용하는 이용자에게 해당 라이선스 조건에 따른 소스 제공 기회를 요구하는 라이선스
- **SBOM(Software Bill of Materials)**: 제품에 포함된 소프트웨어 구성요소와 관련 정보를 기록한 자재명세서
- **SCA(Software Composition Analysis)**: 소프트웨어 구성요소와 그 출처·버전·라이선스·취약점을 식별하는 분석
- **Source-Available**: 소스코드 열람을 허용하되 별도의 이용 제한을 둘 수 있는 배포 조건; 오픈소스 여부는 해당 정의와 라이선스 조건으로 구별
- **SPDX(Software Package Data Exchange)**: 소프트웨어 구성요소와 라이선스 정보를 교환하기 위한 표준 형식

</details>

## 1교시 10점 답안

### Ⅰ. 오픈소스 라이선스의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **오픈소스 라이선스** 는 저작권자가 소프트웨어의 사용·수정·재배포를 허용하며 이용 조건을 정하는 법적 허락 |
| 목적 | 권리·의무 확인을 통한 적법한 재사용과 재배포 |

### Ⅱ. 라이선스 조건 확인

```text
도입 구성요소·사용 방식 확인
    ↓
적용 라이선스 원문 대조
    ↓ 배포·수정 조건 판단
고지·저작권 표시·소스 제공 의무 정리
```

### Ⅲ. 준수 통제

- **SBOM 관리**: SPDX(Software Package Data Exchange)·CycloneDX 기반 오픈소스 자재명세서 작성
- **SCA 자동화**: 구성요소와 라이선스를 식별하고, 조직의 검토 정책에 따라 담당자 확인을 요청
- 한 줄 제언: 배포 전 구성요소별 라이선스 원문과 사용·수정·배포 형태를 대조해 이행 조건 기록

## 2~4교시 25점 답안

## Ⅰ. 권리와 이용 조건을 정하는 오픈소스 라이선스의 개요

> 오픈소스는 단순한 소스 열람이 아니라 사용·수정·재배포 권리를 부여하는 라이선스 조건의 준수 대상

| 구분 | 핵심 |
|---|---|
| 정의 | **오픈소스 라이선스** 는 저작권자가 소프트웨어의 사용·수정·재배포를 허용하며 이용 조건을 정하는 법적 허락 |
| 목적 | 권리·의무 확인을 통한 적법한 재사용과 재배포 |

## Ⅱ. 오픈소스 라이선스 유형별 의무 범위 비교

> 의무 범위는 라이선스 원문·결합 방식·배포 형태에 따라 달라지므로 개별 조건을 판정해야 한다.

### 오픈소스 라이선스 스펙트럼 및 의무 강도 비교

| 라이선스 계열 | 대표 라이선스 | 소스코드 공개 의무 범위 | 특허 조항 | 상용 소프트웨어 결합 위험도 |
|---|---|---|---|---|
| **Permissive** | MIT, BSD, Apache 2.0 | 일반적으로 결합 저작물의 소스 공개 의무가 없으며 라이선스·저작권 고지 등 개별 조건 확인 | Apache 2.0 특허 조항 등 라이선스별 확인 | 사용·수정·배포 방식에 따라 원문 검토 |
| **Weak Copyleft** | LGPL 2.1/3.0, MPL | 적용 대상 구성요소·수정·결합 방식에 따라 조건 확인 | 버전별 조항 확인 | 결합 방식과 배포 계획에 따라 검토 |
| **Strong Copyleft** | GPL 2.0/3.0 | 배포하는 적용 대상 저작물에 대한 해당 버전의 라이선스·대응 소스 조건 확인 | GPL 3.0(특허 조항 포함) | 결합 방식과 배포 계획에 따라 검토 |
| **Network Copyleft**| AGPL 3.0 | 수정 프로그램과 원격 상호작용하는 이용자에 대한 제13조 조건 확인 | AGPL 3.0(특허 조항 포함) | 서비스·수정 범위와 라이선스 원문 검토 |

## Ⅲ. 사용·수정·배포 형태별 준수 조건

> 라이선스 의무는 이름만으로 결정되지 않으며 구성요소의 수정·결합·배포 방식과 원문 조건을 함께 확인

| 사용 형태 | 확인 항목 |
|---|---|
| 내부 사용 | 라이선스 고지와 내부 이용 조건 |
| 수정·결합 | 수정물·결합물에 적용되는 조건과 고지 의무 |
| 바이너리 배포 | 저작권 고지, 라이선스 문서, 해당 시 소스 제공 조건 |
| 네트워크 서비스 | AGPL 등 해당 라이선스의 네트워크 이용 조항 |

## Ⅳ. 오픈소스 컴플라이언스 한계·대응책

> 구성요소가 늘어나는 환경에서는 SBOM과 라이선스 검토 절차가 구성요소·조건을 추적하는 데 도움이 된다.

### 1. 오픈소스 컴플라이언스 절차

```text
오픈소스 도입·구성요소 식별
    ↓
SCA로 라이선스·버전 점검
    ↓
SBOM으로 구성·의존성 기록
    ↓
고지·소스 제공 의무 검수
```

### 2. 오픈소스 라이선스 실무 위험 및 대응 통제

| 위험 | 대책 | 효과 |
|---|---|---|
| 구성요소의 라이선스 조건을 확인하지 않고 배포 | SCA 결과를 구성요소·버전·사용 방식과 연결해 공개 전 검토 | 해당 배포에서 이행할 조건과 고지 항목 확인 |
| 오픈소스 고지 의무 누락 | SPDX·CycloneDX 등으로 구성요소를 기록하고, 도구가 생성한 고지문을 라이선스 원문과 대조·검토 | 해당 배포에 필요한 고지 조건 확인 |
| AI 코딩 도구가 제안한 코드의 출처·조건이 불명확함 | 도구의 출처 표시 기능과 코드 검토 절차를 적용하고, 확인이 필요한 제안은 공개 전 검토 | 코드 출처와 사용 조건을 추적 가능하게 관리 |

## Ⅴ. 라이선스 조건 적용을 위한 제언

> 오픈소스 관리는 개발팀의 자율에만 맡길 수 없는 전사적 법무·보안·엔지니어링 통합 거버넌스 영역이다.

### 기술사적 제언

| 한계 | 해결 방안 |
|---|---|
| 라이선스 이름만으로 배포 의무를 일괄 판정하면 결합 방식·수정 여부·배포 형태를 놓칠 수 있음 | 공개 전 구성요소별 라이선스 원문과 사용·수정·배포 방식을 함께 검토하고, 적용 의무·고지·소스 제공 조건을 SBOM 및 릴리스 자료에 연결 |
