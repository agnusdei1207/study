## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 오픈소스·라이선스 → **오픈소스 라이선스(Permissive·Copyleft)와 Source-Available 라이선스**

## 30초 인출

- 본질: 오픈소스 라이선스는 소스 코드의 사용·수정·배포 조건을 정한 계약이며, 의무 강도에 따라 허용적(Permissive)·카피레프트(Copyleft)로 나뉘고 상업 사용을 제한하는 Source-Available이 별도로 존재
- 메커니즘: 사용 방식(내부 사용·배포·네트워크 서비스 제공)과 수정 여부에 따라 고지·소스 공개·동일 조건 배포 의무가 결정
- 통찰: 배포나 서비스 제공 방식에 따라 소스 공개 의무가 달라져 위반이 뒤늦게 드러나면 교체 비용이 크므로 도입 전 SBOM과 라이선스 스캔으로 의무를 확인

<details>
<summary>핵심 용어</summary>

- **오픈소스 라이선스** : 소스 코드의 사용·수정·배포 조건을 정한 라이선스
- **허용적 라이선스(Permissive License)** : 저작권·라이선스 고지만 유지하면 수정본을 비공개로도 배포할 수 있는 라이선스. MIT·BSD·Apache 2.0
- **카피레프트(Copyleft)** : 수정·결합한 결과물을 배포할 때 같은 라이선스로 소스를 공개하도록 요구하는 조건. GPL
- **AGPL** : 네트워크 서비스로 제공하는 경우에도 소스 공개를 요구하는 카피레프트 라이선스
- **Source-Available** : 소스는 공개하지만 상업적 서비스 제공 등을 제한해 오픈소스 정의를 충족하지 않는 라이선스. SSPL·BSL
- **SBOM(Software Bill of Materials)** : 제품을 구성하는 소프트웨어 구성요소와 라이선스 목록

</details>

## 2~4교시 25점 답안

## Ⅰ. 오픈소스 라이선스의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **오픈소스 라이선스** 는 소스 코드의 사용·수정·배포 조건을 정한 라이선스 |
| 목적 | 저작권을 유지하면서 소프트웨어의 공유·재사용 조건 명확화 |

## Ⅱ. 상용 라이선스와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 소스 공개 | 사용·수정·재배포 허용 |
| 조건부 허용 | 고지·소스 공개 등 의무 준수 조건 |
| 의무 차등 | 라이선스별로 의무 강도가 다름 |

## Ⅲ. 라이선스 유형과 의무 판단

### 의무 강도에 따른 라이선스 체계

```text
오픈소스 라이선스
    ├─ 허용적(Permissive) ── MIT·BSD·Apache 2.0
    ├─ 약한 카피레프트 ── LGPL·MPL
    ├─ 강한 카피레프트 ── GPL
    └─ 네트워크 카피레프트 ── AGPL
Source-Available ── SSPL·BSL (오픈소스 정의 미충족)
```

### 확대: 사용 방식별 소스 공개 의무 판단

```text
사용 방식 확인
    ├─ 내부 사용만 → 대체로 공개 의무 없음
    ├─ 수정·결합해 배포 → GPL 계열은 결합물 소스 공개
    └─ 네트워크 서비스 제공 → AGPL은 소스 공개, SSPL은 서비스 전체 공개
```

## Ⅳ. 라이선스 비교와 개방형에서 폐쇄형으로의 변화

### 라이선스 유형 비교

| 구분 | 허용적 | 카피레프트 | Source-Available |
|---|---|---|---|
| 의무 | 고지 유지 | 동일 조건 소스 공개 | 상업적 서비스 제한 |
| 상용 제품 결합 | 자유 | 배포 시 공개 의무 | 조건에 따라 제한 |
| 오픈소스 정의 | 충족 | 충족 | 미충족 |

### 개방형에서 폐쇄형으로의 변화

| 구분 | 내용 |
|---|---|
| 배경 | 클라우드 사업자가 오픈소스를 서비스로 제공해 수익을 얻는 반면 프로젝트 기업은 개발 비용 회수 곤란 |
| 사례 | MongoDB의 SSPL 전환, HashiCorp의 BSL 전환 |
| 산업 영향 | 커뮤니티의 포크(OpenTofu·Valkey 등) 등장, 기업의 사용 조건 재검토 부담 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 사용 방식별 의무를 몰라 배포·서비스 뒤 위반 발생 | 도입 전 사용 방식별 의무 판단표 작성 |
| 의존 패키지의 하위 라이선스 미파악 | SBOM과 라이선스 스캔(SCA) 도구로 전이 의존성 확인 |
| 라이선스 변경으로 사용 조건 급변 | 핵심 의존성의 라이선스 변경 모니터링과 대체 후보 확보 |
| AI 생성 코드·오픈웨이트 모델의 라이선스 불명확 | 생성 코드 출처 점검, 모델 라이선스 조건 확인 |

## Ⅵ. 제언

도입 전에 SBOM과 라이선스 스캔으로 사용 방식별 의무를 확인하고, 위험 라이선스는 승인 절차를 거치도록 통제

### 도입 전 라이선스 점검 절차

```text
구성요소 도입 요청
    ↓
SBOM 작성·라이선스 스캔
    ↓
사용 방식별 의무 판정
    ├─ 허용 가능 → 도입
    └─ 위험 라이선스 → 승인 절차 또는 대체
```

### 선택 근거: 사후 점검과의 비교

| 구분 | 배포 후 점검 | 제언: 도입 전 점검 |
|---|---|---|
| 위반 발견 시점 | 배포·서비스 이후 | 도입 전 |
| 교체 비용 | 큼 | 작음 |
| 근거 | 개별 확인 | SBOM 기록 |
