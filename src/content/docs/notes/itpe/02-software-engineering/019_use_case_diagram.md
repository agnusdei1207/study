## 연관 키워드

- 유스케이스, 액터, 시스템 경계, 유스케이스 명세서
- include, extend, 일반화, 기본 흐름, 대안 흐름

## Ⅰ. 유스케이스 다이어그램의 개요

- 핵심 요약 : 유스케이스 다이어그램은 액터와 시스템의 목표 지향적 상호작용을 시스템 경계 안에 시각화하는 요구 분석 모델.
- 개념 : 시스템 외부의 액터가 시스템을 통해 달성하려는 목표인 **유스케이스**(Use Case)와 그 상호작용 범위를 UML(Unified Modeling Language) 다이어그램으로 표현한 모델(**유스케이스 다이어그램**, Use Case Diagram).
- 배경 및 필요성 : 기능 목록 방식의 텍스트 나열은 사용자 목표·범위·예외 상황의 문맥이 드러나지 않아 기능 누락·중복·범위 분쟁 발생.
- 주요 목적 : 이해관계자 간 기능 범위 합의와 요구·시험의 추적 기준 확보.

## Ⅱ. 유스케이스 다이어그램의 특징 및 장점

- 핵심 요약 : 액터의 목표를 단위로 기능을 재구성하고 명세서와 연계해 구현·시험 가능한 요구로 전환.

1. 액터 중심 모델링 : 사람·외부 시스템처럼 시스템과 상호작용하는 역할을 **액터**(Actor)로 식별 → 이해관계자·연계 시스템 도출.
2. 목표 단위 기능 정의 : 사용자 가치 단위로 기능을 묶어 유스케이스화 → 기능 누락·중복 방지와 우선순위·인수 기준 도출.
3. 시스템 경계 명확화 : 경계 내부(시스템 책임)와 외부(액터 책임)의 구분인 **시스템 경계**(system boundary) 표현 → 개발 범위·연계 책임 합의.
4. 명세서 연계 : 다이어그램은 업무 규칙·예외를 생략하므로 **유스케이스 명세서**(use case specification, 흐름별 상세 문서)가 사전·사후 조건과 **기본 흐름**(정상 시나리오)·**대안 흐름**(변형·예외 시나리오)을 기술 → 구현·시험 가능한 요구로 전환.

## Ⅲ. 유스케이스 다이어그램의 구조 (흐름)

- 핵심 요약 : 액터-유스케이스의 연관을 기본으로 하고, include·extend·일반화는 관계 의미에 맞을 때만 사용.

```text
[ 관계 구조 ]
액터(고객) ── 연관 ── (상품 주문)

(상품 주문) ─ «include» → (결제 처리)
: 항상 수행되는 공통 하위 기능

(상품 주문) ─ «extend» → (쿠폰 적용)
: 조건 충족 시 선택적 확장

(회원 주문) ─ 일반화 → (상품 주문)
: 상위 유스케이스의 특수화
```

```text
[ 작성 절차 ]
액터 식별 → 시스템 경계 확정
   ↓
유스케이스 도출(액터 목표 단위)
   ↓
관계 정의 : include·extend·일반화
   ↓
명세서 작성 : 사전·사후 조건,
기본 흐름, 대안·예외 흐름
   ↓
요구사항·시험사례와 추적
```

- 관계의 의미 :

  1. **include**(포함) : 기본 흐름에서 항상 수행되는 공통 기능의 재사용.
  2. **extend**(확장) : 조건 충족 시에만 추가되는 선택적 확장.
  3. **일반화**(Generalization) : 상위 유스케이스를 하위가 특수화.

## Ⅳ. 유스케이스 모델과 기능 목록 방식의 비교

- 핵심 요약 : 유스케이스 모델은 목표·관계·흐름의 문맥을 담는 반면, 기능 목록 방식은 항목 나열에 머묾.

| 비교 축 | 유스케이스 모델 | 기능 목록 방식 |
| --- | --- | --- |
| 표현 형식 | 액터·목표·관계의 시각적 모델과 흐름 명세 | 텍스트 중심의 기능 항목 나열 |
| 요구 문맥 | 사용자 목표·상호작용 흐름 포함 | 기능 항목만 제공 |
| 예외 처리 | 대안·예외 흐름 명세화 | 예외 조건 누락 용이 |
| 범위 합의 | 시스템 경계로 책임 구분 | 범위·연계 경계 모호 |
| 시험 연계 | 시나리오 기반 인수시험 연결 | 항목별 개별 검증에 그침 |

## Ⅴ. 유스케이스 모델의 한계와 방안

- 핵심 요약 : 관계 남용·비기능 요구 누락·명세 불일치를 관계 기준 리뷰와 추적 체계로 보완.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 관계 남용 | include·extend 과다 사용 → 기능 과잉 분해·흐름 혼란 | 액터 목표 수준 유지·관계 의미 기준 리뷰 | 유스케이스 수·관계 수 |
| 비기능 요구 표현 불가 | 성능·보안·가용성이 다이어그램 밖에 남음 | 품질 요구를 별도 명세로 병행·연결 | 품질 요구 추적률 |
| 명세-다이어그램 불일치 | 변경 반영 지연 → 상충 요구 발생 | 변경 통제 절차로 동시 갱신 | 불일치 발견 건수 |
| 대안 흐름 미비 | 예외 상황의 구현·시험 누락 | 기본 흐름당 대안·예외 최소 정의 | 예외 흐름 정의율 |

## Ⅵ. 유스케이스 모델에 대한 제언

- 핵심 요약 : 명세 표준 정착과 시험 추적, 변경 통제를 요구 관리 체계로 연결.
- 요구 분석가 : 액터별 업무 목표를 현업과 검증하고 명세서 표준(흐름·조건·예외)을 조직에 정착.
- 품질팀 : 유스케이스별 정상·예외 시나리오를 인수시험·회귀시험 사례로 추적 관리.
- 변경 통제 조직 : 다이어그램·명세서·시험사례의 동시 갱신을 변경 절차에 포함.

## Ⅶ. 결론

- 핵심 요약 : 유스케이스 모델은 기능을 사용자 목표·관계·흐름으로 재구성해 범위 합의부터 수용시험까지 이어주는 요구 분석 기준.
- 다이어그램의 간결성과 명세의 검증 가능성을 함께 유지하는 것이 활용 조건.
