## 연관 키워드
- UML, 클래스 다이어그램, 정적 구조, 속성·연산
- 연관·집합·합성·일반화·의존·실현, 다중성, 접근 제한자

## Ⅰ. 클래스 다이어그램의 개요

- 핵심 요약 : 클래스 다이어그램은 UML에서 클래스와 그 관계로 시스템의 정적 구조를 표현하는 구조 다이어그램.
- 개념 : **클래스 다이어그램**(Class Diagram)은 **UML**(Unified Modeling Language)에서 클래스의 속성·연산과 클래스 간 관계로 시스템의 **정적 구조**(Static Structure)를 표현하는 구조 다이어그램.
- 배경 및 필요성 : 객체지향 설계에서 클래스 간 책임·의존·제약을 팀이 공유·검토할 공통 표기의 필요.
- 주요 목적 : 설계 구조의 명확화로 의사소통·변경 영향 분석·코드 구현의 기준 확보.

## Ⅱ. 클래스 다이어그램의 특징 및 장점

- 핵심 요약 : 3구획 표기·관계 유형·다중성·정적 관점이 설계 합의의 공통 언어로 작동.

1. 3구획 표기 : 클래스 상자를 이름·**속성**(Attribute)·**연산**(Operation) 구획으로 표기 → 책임의 명시적 합의.
2. 캡슐화 표현 : **접근 제한자**(+ 공개, - 비공개, # 보호) 표기 → 정보 은닉 수준의 설계 합의.
3. 관계 유형 구분 : 결합 형태를 여섯 관계로 구분 → 구현 전략·생명주기 책임 구체화.
   - **연관**(Association) : 구조적 연결 관계
   - **집합**(Aggregation) : 전체-부분의 약한 소유
   - **합성**(Composition) : 생명주기를 공유하는 강한 소유
   - **일반화**(Generalization) : 상속 계층 관계
   - **실현**(Realization) : 인터페이스 구현 계약
   - **의존**(Dependency) : 일시적 사용 관계
4. 다중성 제약 : 관계 양단에 1, 0..1, 1..* 등의 개수 제약을 **다중성**(Multiplicity)으로 표기 → 업무 규칙의 구조 반영.
5. 정적 관점 : 실행 순서를 배제한 구조·제약 전달 → 시간 조건 없는 설계 기준 제공.

## Ⅲ. 클래스 다이어그램의 구조 (흐름)

- 핵심 요약 : 도메인 개념에서 출발해 관계·제약을 덧대는 절차와 표기 구조의 결합.

```text
작성 절차

도메인 개념·용어 정리
   ↓
클래스 식별 (이름·속성·연산)
   ↓
관계·다중성 설정
   ↓
접근 제한자·제약 표기
   ↓
설계 검토 → 코드 반영
```

```text
클래스 상자의 3구획 표기

주문 (클래스명)
   - 주문번호 : String (속성)
   + 주문 접수 (연산)
```

## Ⅳ. 클래스 다이어그램과 객체 다이어그램의 비교

- 핵심 요약 : 클래스 다이어그램은 설계 시점의 일반 형판, 객체 다이어그램은 특정 시점의 인스턴스 스냅샷.
- 비교 개요 : **객체 다이어그램**(Object Diagram)은 특정 시점의 객체 인스턴스와 링크를 표현하는 UML 구조 다이어그램.

| 비교 축 | 클래스 다이어그램 | 객체 다이어그램 |
|---|---|---|
| 표현 대상 | 클래스(설계 시점의 형판) | 객체 인스턴스(실행 시점 실체) |
| 시점 | 시스템 전역의 일반 구조 | 특정 시점의 스냅샷 |
| 속성값 | 선언만 표기 | 실제 값 보유 |
| 관계 | 다중성의 일반 제약 | 개별 링크의 구체 사례 |
| 활용 | 설계 합의·코드 구조 기준 | 예제 검증·시험 데이터 설계 |

## Ⅴ. 클래스 다이어그램의 한계와 방안

- 핵심 요약 : 과도한 상속·제약 오류·모델-코드 불일치·동적 행동 미표현을 설계 원칙과 모델 관리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 과도한 상속 | 구현 재사용 목적 상속 → 취약한 기반 클래스·강한 결합 | 합성 우선 원칙·역할 인터페이스 검토 | 상속 깊이 |
| 다중성·제약 오류 | 업무 규칙 미반영 → 불가능한 구조 허용 | 도메인 규칙·키 제약과 대조 검토 | 제약 위반 건수 |
| 모델-코드 불일치 | 유지 책임 부재 → 문서 신뢰 상실 | 핵심 구조만 모델링·코드 리뷰 연계 | 모델 최신성 |
| 동적 행동 미표현 | 정적 구조만으로 흐름·상태 확인 불가 | 시퀀스·상태 다이어그램과 역할 분담 | 시나리오 커버리지 |

## Ⅵ. 클래스 다이어그램에 대한 제언

- 핵심 요약 : 표기 표준·동기화 절차·모델 자산화의 조직 체계로 다이어그램 신뢰성 제고.

1. 설계 표준 조직은 표기 규칙과 모델링 범위(핵심 도메인 중심)를 설계 표준에 명문화.
2. 프로젝트 팀은 모델-코드 동기화 지점을 코드 리뷰·변경 관리 절차에 편성해 모델 신뢰성 유지.
3. 조직은 검증된 도메인 모델을 아키텍처 자산으로 등록해 신규 프로젝트 재사용 체계 구축.

## Ⅶ. 결론

- 핵심 요약 : 클래스 다이어그램은 시스템의 정적 구조와 제약을 공통 언어로 고정하는 설계 기준.
- 정적 구조의 합의를 동적 행동 모델과 조합할 때 설계 품질 관리 효과 완성.
