## 한 줄 본질
- 테스트를 무한정 돌려도 버그가 0개임을 입증할 수 없다는 비현실적 기대의 병목 → ISTQB 7대 공학적 원리를 바탕으로 위험도 높은 모듈에 조기·지속적으로 자원을 집중 배분 → 한정된 비용 내 결함 검출 극대화 / 케이스 미갱신 시 신규 결함 탐지력 상실

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               소프트웨어 테스팅의 7대 기본 원리 (ISTQB)           |
+-------------------------------------------------------------------+
| 1. 결함 존재 증명 : 결함이 있음을 보일 뿐, 결함이 없음을 입증 못함|
| 2. 완벽 테스팅 불가: 모든 입력·경로의 전수 테스팅은 현실적으로 불가|
| 3. 조기 테스팅    : 요구사항 단계부터 일찍 시작할수록 결함비용 절감|
| 4. 결함 집중      : 20%의 핵심 모듈에서 전체 결함의 80% 발생(파레토)|
| 5. 살충제 패러독스: 동일한 테스트를 반복하면 더 이상 버그를 못 잡음|
| 6. 맥락 의존성    : 전자상거래와 의료기기 소프트웨어의 테스트는 다름|
| 7. 오류부재의 궤변: 요구를 만족 못하면 결함을 다 고쳐도 무용지물  |
+-------------------------------------------------------------------+
```

## 핵심 용어
- 살충제 패러독스(Pesticide Paradox): 동일한 살충제를 계속 쓰면 해충이 내성을 갖듯, 동일한 테스트 케이스만 반복 실행하면 새로운 결함을 발견하지 못하는 현상
- 오류-부재의 궤변(Absence-of-Errors Fallacy): 시스템의 모든 버그를 수정하여 결함이 0건이라 할지라도, 사용자의 실제 비즈니스 요구를 만족하지 못하면 실패한 시스템이라는 원리

## 핵심 통찰
- 테스팅의 목표는 "버그가 없음을 증명"하는 것이 아니라, "치명적인 결함을 출시 전에 최대한 빠르게 노출시키는 것"임
- 결함 집중(Defect Clustering) 원리에 따라, 결함이 한 번 터진 복잡한 레거시 모듈에 테스트 자원을 우선 집중하는 위험 기반 테스팅(Risk-based Testing)이 가장 경제적임
- 살충제 패러독스를 깨뜨리기 위해서는 정형화된 자동화 회귀 테스트 외에도, 테스터의 직관과 경험을 활용하는 '탐색적 테스팅(Exploratory Testing)'을 주기적으로 병행해야 함

## 이웃 토픽과 구분
- 살충제 패러독스 vs 회귀 테스팅: 회귀 테스팅 = 기존 기능의 안정성 보존을 위해 '같은' 테스트를 자동 반복 / 살충제 패러독스 = 새 버그를 잡으려면 '새로운' 테스트 케이스를 끊임없이 추가·수정해야 함

## 내 의견
- [테스트 통과율 100%라는 숫자에 현혹되는 경영진의 착각] "테스트 1,000개가 모두 초록색이니 버그가 없다"는 보고서만 믿고 출시했다가 운영 환경에서 대형 사고가 터지는 사례 다수 → 나라면: 살충제 패러독스를 방지하기 위해 코드에 가짜 결함을 주입하여 테스트가 이를 잡아내는지 측정하는 '뮤테이션 점수(Mutation Score)'를 품질 지표로 도입하고, 릴리스 전 탐색적 테스팅 세션을 의무화
