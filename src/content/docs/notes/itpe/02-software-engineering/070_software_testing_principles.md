## 본론: 개념 및 핵심 메커니즘

### 1. 소프트웨어 테스트 7대 원리의 공학적 본질

- **ISTQB 정의**: 무한한 소프트웨어 상태 공간에서 유한한 비용과 시간으로 최적의 품질을 확보하기 위해 테스터와 엔지니어가 반드시 견지해야 하는 7가지 기본 공리.

### 2. 7대 원리 상세 분석

| 번호 | 원리 명칭 | 공학적 의미 및 메커니즘 | 실무 적용 방안 |
|---|---|---|---|
| **1** | **결함 존재 증명<br>(Testing shows defect)** | 테스트는 결함이 잠재되어 있음을 증명할 뿐, 결함이 전혀 없음을 입증할 수 없음. | "버그 0건"을 출시 기준으로 삼지 않고 잔존 위험률(Residual Risk) 관리. |
| **2** | **완벽한 테스팅 불가<br>(Exhaustive testing impossible)** | 모든 입력과 사전 조건 조합의 전수 검사는 시간·비용상 불가능. | 동등 분할, 경계값 분석, 리스크 기반 테스팅(RBT)으로 표본 추출. |
| **3** | **조기 테스팅<br>(Early testing / Shift-Left)** | 개발 생명주기 초기(요구분석, 아키텍처)에 테스트를 시작할수록 결함 수정 비용 지수적 절감 (Boehm 곡선). | 정적 분석, 동료 검토(Walkthrough/Inspection), BDD 인수 조건 명세. |
| **4** | **결함 집중<br>(Defect clustering)** | 파레토 원칙(80:20) 적용. 소수의 복잡하고 결합도 높은 모듈에 대부분의 결함이 편중됨. | 복잡도(McCabe)가 높은 모듈 및 과거 결함 다발 모듈에 테스트 자원 80% 집중. |
| **5** | **살충제 패러독스<br>(Pesticide paradox)** | 동일한 테스트 스위트만 반복 실행하면 시스템이 내성을 가져 새로운 결함을 탐지하지 못함. | 정기적인 테스트 케이스 리팩토링, 탐색적 테스팅 및 뮤테이션 테스팅 병행. |
| **6** | **정황 의존성<br>(Testing is context dependent)** | 소프트웨어 도메인과 비즈니스 맥락에 따라 테스트 접근법과 강도가 완전히 달라짐. | 일반 전자상거래(가용성, UX) vs 차량 기능안전 ISO 26262(MC/DC 커버리지). |
| **7** | **오류-부재의 궤변<br>(Absence-of-errors fallacy)** | 사양서대로 구현되어 결함이 0건이라 하더라도, 실제 사용자의 요구와 목적을 충족하지 못하면 무용지물. | Verification(사양 일치 검증)을 넘어 Validation(고객 가치 확인) 수행. |

## 3대 핵심 역설과 극복 전략

### 1. 살충제 패러독스 (Pesticide Paradox)

- **원인**: 자동화된 회귀 테스트가 매일 100% Pass하더라도, 이는 이미 검증된 코드 경로만 지나가므로 신규 기능이나 엣지 케이스를 검증하지 못함.
- **극복책**:
  - **테스트 케이스 지속적 개정**: 분기별 테스트 케이스 결함 검출 기여도 평가 및 쇄신.
  - **탐색적 테스팅 (Exploratory Testing)**: 테스터의 직관을 바탕으로 사전 스크립트 없이 수행.
  - **뮤테이션 테스트 (Mutation Testing)**: 코드에 의도적 돌연변이를 주입하여 테스트 스위트의 결함 검출력 검증.

### 2. 오류-부재의 궤변 (Absence-of-errors Fallacy)

- **원인**: "개발 요구사항 정의서"대로 완벽히 개발하여 버그를 모두 잡았으나, 현업 비즈니스 프로세스와 어긋나 시스템이 사장됨.
- **극복책**: 개발 초기부터 사용자가 참여하는 행위 주도 개발(BDD) 및 사용자 인수 테스팅(UAT) 조기 수행.

## 실무 장애 시나리오 및 공학적 대안

### 1. 현장 장애 사례

1. **테스트 패스율 100% 보고 후 운영 배포 당일 전산 마비**:
   - 기존 자동화 리그레션 스위트만 맹신(살충제 패러독스)하여, 신규 프로모션 동시성 트래픽 경로를 전혀 검증하지 못함.
2. **모든 단위 테스트 통과 후 사용자 전면 거부**:
   - 복잡한 입력 화면의 유효성 검사 버그는 완벽히 잡았으나, 현장 결제 동선이 5단계나 늘어나 고객 이탈 폭증(오류-부재의 궤변).

### 2. 문제 원인 및 공학적 해결책

| 장애 상황 | 근본 원인 | 공학적 대책 (대안 기술) | 개선 효과 |
|---|---|---|---|
| **신규 결함 탐지 실패** | 고정 테스트 케이스 반복 (살충제 패러독스) | **자동화 회귀(60%) + 탐색적 테스팅(40%)** 하이브리드 편성 | 운영 장애 조기 적출률 35% 향상 |
| **고객 요구 불일치** | Verification 중심 테스팅 (오류 부재의 궤변) | 현업 주도 **BDD(Cucumber/Gherkin)** 인수 테스트 조기 도입 | 요구사항 불일치 결함 90% 예방 |
| **일정 부족으로 테스트 생략** | 균등 분배 테스트로 인한 자원 낭비 | 비즈니스 영향도와 실패 가능성 기반 **RBT(리스크 기반 테스팅)** | 핵심 비즈니스 모듈 테스트 커버리지 100% 달성 |

## 결론: 기술사 답안 차별화 포인트

1. **원리의 단순 나열을 탈피한 공학적 상관관계 제시**: 7대 원리를 개별 항목으로만 쓰지 않고, "완벽한 테스팅 불가(한계)" $\rightarrow$ "조기 테스팅 & 결함 집중(선택과 집중 전략)" $\rightarrow$ "살충제 패러독스 & 오류 부재 궤변(실행 시 주의점)"으로 유기적으로 엮어 논리적 완결성을 확보할 것.
2. **Shift-Left와 RBT(리스크 기반 테스팅)의 구체적 방법론 연계**: 결론부에서 현대 애자일/데브옵스 환경의 **Shift-Left 테스팅**과 시스템 위험도(Risk Matrix)에 따라 테스트 강도를 차등 적용하는 **RBT**를 7대 원리의 실천적 결론으로 제시할 것.
