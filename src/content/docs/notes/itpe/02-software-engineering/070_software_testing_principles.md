## 30초 인출

- 본질: 소프트웨어 테스팅의 본질적 한계, 결함 분포 특성, 효율적인 테스트 설계 및 운영 방향을 제시하는 국제 표준(ISTQB) 기반의 핵심 공학 원리 집합
- 메커니즘: 결함 존재 증명, 완벽 테스팅 불가, 조기 테스팅(Shift-Left), 결함 집중(파레토 법칙), 살충제 패러독스 극복, 맥락 의존성, 오류 부재의 궤변 방어
- 통찰: 테스트 통과 건수만으로 소프트웨어의 무결성을 입증할 수 없으므로 위험 기반 테스팅(RBT)과 사용자 가치 검증(Validation)을 결합한 지속적 테스트 스위트 갱신 필수

<details>
<summary>핵심 용어</summary>

- **Testing Principles(테스팅 원리)** : 소프트웨어 테스트의 현실적 한계와 경제성을 고려하여 효과적인 테스트 전략을 수립하기 위한 7대 공리
- **ISTQB (International Software Testing Qualifications Board)** : 전 세계 소프트웨어 테스팅 표준 가이드라인과 인증 체계를 운영하는 국제 비영리 단체
- **Defect Clustering (결함 집중)** : 소프트웨어의 결함 대부분(약 80%)은 소수의 특정 복잡한 모듈(약 20%)에 편중되어 발견된다는 파레토 법칙 기반 원리
- **Pesticide Paradox (살충제 패러독스)** : 동일한 테스트 케이스를 반복 실행하면 내성이 생겨 새로운 결함을 검출하지 못하므로 주기적 갱신이 필요하다는 원리
- **Absence-of-Errors Fallacy (오류 부재의 궤변)** : 시스템 결함을 모두 수정하더라도 사용자의 실질적 비즈니스 요구와 목적을 충족하지 못하면 쓸모없다는 원리
- **Risk-Based Testing (RBT, 위험 기반 테스팅)** : 전수 테스트가 불가능하므로 비즈니스 실패 영향도와 발생 가능성을 바탕으로 우선순위를 정하는 접근법

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 테스팅 7대 원리의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 테스팅 활동의 본질적 한계와 결함 발생 메커니즘을 규명하고, 제한된 프로젝트 자원 내에서 최적의 테스트 전략을 수립하도록 돕는 ISTQB 공인 7대 지침 |
| 목적 | 무의미한 전수 테스트 시도 방지, 테스트 설계의 조기 착수를 통한 결함 수정 비용 절감, 비즈니스 가치에 부합하는 위험 기반 품질 보증 달성 |

## Ⅱ. 테스팅 7대 원리의 핵심 특징 및 실무 적용

| 7대 원리 명칭 | 공학적 본질 및 의미 | 실무 테스트 전략 적용 방안 |
|---|---|---|
| **1. 결함의 존재 증명** | 테스팅은 결함이 '있음'을 증명할 뿐 결함이 '없음'을 증명하지 못함 | 테스트 100% 통과를 결함 무결성으로 오판하지 않고 모니터링 체계 유지 |
| **2. 완벽한 테스팅은 불가** | 모든 입력값과 경로의 조합을 전수 테스트(Exhaustive)하는 것은 불가능 | 위험 분석(RBT)과 동등 분할, 경계값 분석을 통해 대표 케이스 선별 |
| **3. 조기 테스팅 (Shift-Left)** | 개발 초기 요구사항 단계부터 테스팅을 시작해야 수정 비용 절감 | 요구사항 명세 인스펙션 및 정적 분석 도구를 개발 초기에 전면 배치 |
| **4. 결함 집중 (Defect Cluster)** | 대부분의 결함은 소수의 복잡하고 변경이 잦은 모듈에 집중됨 | 파레토 80:20 법칙에 따라 과거 결함 다발 영역에 테스트 자원 집중 투입 |
| **5. 살충제 패러독스** | 동일한 테스트 케이스를 계속 반복하면 새로운 결함을 탐지하지 못함 | 정기적인 테스트 케이스 리뷰, 뮤테이션 테스트 및 탐색적 테스팅 병행 |
| **6. 맥락 의존성 (Context)** | 시스템의 비즈니스 도메인과 환경에 따라 적합한 테스팅 방식이 상이 | 안전 필수 자동차 소프트웨어(ISO 26262)와 모바일 앱의 테스트 접근 차별화 |
| **7. 오류 부재의 궤변** | 모든 버그를 잡았더라도 사용자 요구와 목적에 맞지 않으면 실패한 시스템 | 단순 스펙 검증(Verification)을 넘어 사용자 인수 검증(Validation) 필수화 |

## Ⅲ. 테스팅 7대 원리 유기적 연계 체계 및 프로세스

### 7대 원리의 상호작용 및 위험 기반 테스팅(RBT) 흐름

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [원리 1: 결함 존재 증명] + [원리 2: 완벽 테스팅 불가]                   │
│   - 전수 테스트 불가능성 및 잔존 결함의 불가피성 인정                 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (현실적 제약 극복 전략)
┌────────────────────────────────────────────────────────────────────────┐
│ [원리 3: 조기 테스팅 (Shift-Left)] ──→ [원리 6: 맥락 의존적 접근]      │
│   - 요구사항/설계 정적 분석 조기 시작    - 도메인 특성별 테스트 강도 조절│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (테스트 자원 최적 분배)
┌────────────────────────────────────────────────────────────────────────┐
│ [원리 4: 결함 집중 (Defect Clustering)] ── (80:20 파레토 법칙)          │
│   - 고위험/고복잡도 코어 모듈 식별 및 집중 테스트 케이스 설계         │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (테스트 효용성 유지)
┌────────────────────────────────────────────────────────────────────────┐
│ [원리 5: 살충제 패러독스 극복] ──→ [테스트 케이스 지속 갱신 & 변이]    │
│   - 자동화 회귀 스위트 리팩토링 및 탐색적 테스팅(Exploratory) 결합    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (최종 목표 달성)
┌────────────────────────────────────────────────────────────────────────┐
│ [원리 7: 오류 부재의 궤변 방어] ──→ [비즈니스 가치 검증 (Validation)] │
│   - 사용자의 실제 작업 시나리오 부합성 확인 및 사용자 인수 테스트(UAT)  │
└────────────────────────────────────────────────────────────────────────┘
```

## Ⅳ. 핵심 3대 난제(결함 집중, 살충제 패러독스, 오류 부재) 상세 대응

### 3대 핵심 테스팅 딜레마 및 극복 전략 비교

| 구분 | 결함 집중 (Defect Clustering) | 살충제 패러독스 (Pesticide Paradox) | 오류 부재의 궤변 (Absence-of-Errors) |
|---|---|---|---|
| **발생 원인** | 시스템의 복잡도 불균형 및 개발자 역량 편차 | 기존 통과 테스트 스위트의 정체 및 매너리즘 | 사용자의 본질적 요구를 외면한 기술 중심 명세 |
| **위험 현상** | 핵심 취약 모듈을 놓치고 엉뚱한 곳에 테스트 낭비 | 매일 회귀 테스트가 PASS되나 운영 장애 빈발 | 버그 0건 출시 후 고객으로부터 외면받는 제품 |
| **극복 기법** | **소프트웨어 메트릭(McCabe) 및 결함 히스토리 분석** | **뮤테이션 테스트, 테스트 데이터 가변화, 카오스** | **BDD, 사용자 스토리 인수 기준(AC), 페르소나** |
| **품질 관리 척도**| 모듈별 결함 밀도(Defect Density) 추적 | 신규 결함 검출률(Defect Detection Rate) | 사용자 만족도(NPS), 비즈니스 목표 달성률 |

### 검증(Verification)과 확인(Validation)의 비교 (원리 7 대응)

| 비교 항목 | 검증 (Verification) | 확인 (Validation) |
|---|---|---|
| **핵심 질문** | "우리가 소프트웨어를 **올바르게 만들고 있는가?** " | "우리가 **올바른 소프트웨어를 만들고 있는가?** " |
| **평가 기준** | 사전에 정의된 소프트웨어 요구사항 명세서(SRS) 규격 | 최종 사용자 및 고객의 실제 운영 목적과 비즈니스 니즈 |
| **수행 주체** | 내부 개발팀, 동료 리뷰어, SQA 감사자 | 실제 최종 사용자, 고객 대리인, 제품 책임자(PO) |
| **위험 회피** | 스펙 불일치 및 소프트웨어 구현 결함 방지 | **오류 부재의 궤변 방지 (쓸모없는 완벽한 제품 방지)** |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 테스트 통과율 100%만을 맹신하여 프로젝트 후반 릴리스 승인을 서두르다 대형 장애 발생 | 미시험 영역의 잔존 위험(Residual Risk)을 정량 평가하여 릴리스 위험 평가서 발행 |
| 기존 자동화 테스트 스크립트만 고집하여 유지보수 비용은 증가하고 신규 버그 검출력 저하 | 주기적인 테스트 스위트 가지치기(Pruning) 및 테스트 케이스 뮤테이션(Mutation) 적용 |
| 도메인 맥락을 무시하고 금융권 시스템에 단순 웹 수준의 경량 테스트 프로세스를 적용 | 산업별 규제 표준(도메인 컴플라이언스)을 고려한 테스트 프로세스 테일러링 수행 |

## Ⅵ. 제언

위험 기반 테스팅(RBT) 매트릭스 수립 및 AI 기반 자율 탐색적 테스팅(Autonomous Exploratory Testing)

### 위험 기반 테스팅(RBT) 우선순위화 파이프라인

```text
[요구사항 및 아키텍처 모듈 식별]
       ↓
[위험 분석 매트릭스 도출: 발생 가능성(L) × 비즈니스 영향도(I)]
  ├─ 치명 위험 (Catastrophic): 결제 트랜잭션, 개인정보 암호화 모듈
  ├─ 고위험 (High): 주문 생성, 장바구니 연계 모듈
  └─ 저위험 (Low): 정적 안내 페이지, 푸터 링크
       ↓
[테스트 자원 차등 배분 및 테스팅 전략 수립]
  ├─ 치명 위험: 정형 인스펙션 + 페어 테스팅 + 100% MCDC 커버리지 강제
  ├─ 고위험: 경계값 분석 + 상태 전이 테스팅 + 100% 분기 커버리지
  └─ 저위험: 스모크 테스트 및 탐색적 테스팅 위임
       ↓
[최적화된 테스트 스위트 완성]
```

### 테스트 전략 선정 의사결정 체계

```text
테스트 계획 수립 단계
       ↓
[기존 테스트 케이스의 신규 결함 검출률이 0%에 수렴하는가?]
       ├─ 예 ──→ [살충제 패러독스 발생] → 탐색적 테스팅 도입 및 입력 데이터 다변화
       └─ 아니오 ─→ [특정 모듈에서 결함이 80% 이상 집중되는가?]
                         ├─ 예 ──→ [결함 집중 대응] → 해당 모듈 전면 코드 리팩토링 및 집중 테스트
                         └─ 아니오 ─→ 사용자 인수 시나리오 기반 목적 적합성(Validation) 집중 검증
```

### 선택 근거: 전통적 무차별 테스팅과 제언 위험 기반 테스팅(RBT) 비교

| 구분 | 전통적 동일 비중 무차별 테스팅 | 제언: 위험 기반 테스팅 (Risk-Based) |
|---|---|---|
| 자원 투입 | 모든 모듈에 균등한 테스트 공수 배분 | 비즈니스 위험도가 높은 20% 핵심 모듈에 자원 80% 집중 |
| 일정 지연 시 | 후반부 테스트가 통째로 생략되어 미검증 위험 | 저위험 영역만 선별 생략되므로 핵심 비즈니스 리스크 방어 |
| ROI (투자대비효과)| 단순 반복 작업으로 ROI 급감 | 최소의 비용으로 치명적 비즈니스 장애 95% 사전 차단 |
