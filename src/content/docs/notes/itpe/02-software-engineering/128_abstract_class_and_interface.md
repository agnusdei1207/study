## 연관 키워드

- 추상 클래스, 인터페이스, 상속, 다중 구현
- 템플릿 메서드, 디폴트 메서드, ISP

## Ⅰ. 추상 클래스와 인터페이스의 개요

- 핵심 요약 : **추상 클래스**(Abstract Class)는 공통 상태·구현을 하위에 물려주는 기반이고 **인터페이스**(Interface)는 구현체가 제공할 역할 계약.
- 개념 : Java에서 인스턴스화할 수 없고 공통 필드·구현 메서드를 하위 클래스에 제공하는 추상 클래스와, 구현체가 제공할 연산 계약을 정의하는 인터페이스로 구성되는 객체지향 설계의 두 추상화 수단.
- 배경 및 필요성 : 공통 코드 재사용과 다형성·느슨한 결합이 동시에 요구되며, 두 수단의 구분 없는 사용은 클래스 간 결합·계약 비대화 유발.
- 주요 목적 : 재사용과 교체 가능성의 적절한 추상화 경계 확보를 통한 변경 비용 최소화.

## Ⅱ. 추상 클래스와 인터페이스의 특징 및 장점

- 핵심 요약 : 상태·구현 공유는 추상 클래스, 역할 계약·복수 수용은 인터페이스가 담당하는 상호 보완 구조.

1. 추상 클래스의 상태·생성자 공유 : **상속**(Inheritance, 기반 클래스의 멤버를 하위 클래스가 물려받는 구조)으로 인스턴스 필드·생성자·구현 메서드 제공 → 하위 클래스 중복 제거·불변식 통일.
2. 인터페이스의 **다중 구현**(한 클래스가 여러 인터페이스 계약을 동시에 수용하는 구조) : 단일 상속 제약 보완·역할 조합 → 교체 가능성 향상.
3. 템플릿 메서드 구조 : **템플릿 메서드**(Template Method, 상위 클래스가 절차를 고정하고 세부 단계를 하위에 위임하는 구조)의 공통 절차 재사용 → 변형 지점 명확화.
4. 디폴트 메서드 : **디폴트 메서드**(Default Method, 인터페이스가 기본 구현을 제공하는 메서드)의 계약 확장 시 호환성 유지 → 상태 공유 없는 제한적 구현 제공.

## Ⅲ. 추상 클래스와 인터페이스의 구조 (흐름)

- 핵심 요약 : 상태·생성자 공유 필요 여부와 역할 조합 가능성의 판단으로 수단을 선택하고 계약에 의존하는 구조로 구현.

```text
[ 추상화 수단 선택 절차 ]

공통 요구 분석
   ↓
상태·생성자·기본 구현 공유 필요?
   예 → 추상 클래스 상속
   아니오 → 인터페이스 역할 계약
   ↓
구현체 작성·계약 준수 검증
```

- 설계 원칙 : 호출부의 인터페이스 계약 의존과 상속의 is-a 관계(하위 타입이 상위 타입의 한 종류인 관계) 한정 → 대체 가능성 확보.

```text
[ 계약 기반의 다형 구조 ]

호출부 → 인터페이스 (역할 계약)
            ↓
  구현체 A · 구현체 B (교체 가능)
```

## Ⅳ. 추상 클래스와 인터페이스의 비교

- 핵심 요약 : 상속 계층의 공통 기반이 필요하면 추상 클래스, 역할 계약·복수 조합이 필요하면 인터페이스가 적합.

| 비교 축 | 추상 클래스 | 인터페이스 |
| --- | --- | --- |
| 설계 의미 | is-a 관계의 공통 기반 클래스 | can-do 역할의 계약 |
| 상태·생성자 | 인스턴스 필드·생성자 보유 가능 | 인스턴스 상태·생성자 없음 |
| 상속·구현 수 | 클래스의 단일 상속 | 클래스당 다중 구현 가능 |
| 구현 제공 | 필드·구현 메서드의 자유로운 제공 | 디폴트 메서드의 제한적 제공 |
| 적합 용도 | 밀접한 하위 타입의 공통 구현 재사용 | 서로 다른 타입에 공통 적용되는 역할 분리 |

## Ⅴ. 추상 클래스와 인터페이스의 한계와 방안

- 핵심 요약 : 상속 결합·계약 비대화·과도한 추상화를 조합 우선·계약 분리·선별 추상화로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 상속 결합 | 기반 클래스 변경의 하위 전체 파급 | 상속 최소화·구성(Composition) 우선·대체 가능성 검증 | 하위 클래스 영향 범위 |
| 계약 비대화 | 무관한 연산 혼재의 불필요 구현 강제 | **ISP**(Interface Segregation Principle, 클라이언트가 불필요한 연산에 의존하지 않게 계약을 작게 분리하는 원칙) 적용·역할별 분리 | 빈 구현·미사용 메서드 수 |
| 과도한 추상화 | 변형 가능성 없는 계층·래퍼 추가의 탐색 복잡도 증가 | 실제 변경 지점·복수 구현 필요성 확인 후 추상화 | 미사용 추상 타입 수 |

## Ⅵ. 추상 클래스와 인터페이스의 제언

- 핵심 요약 : 설계 조직은 소비자 관점의 계약 우선 원칙과 상속 허용 기준을 정하고 리뷰 체계로 대체 가능성 검증.

1. API 설계 조직은 작은 계약 원칙·하위 호환 정책·디폴트 메서드 충돌 규칙의 표준화.
2. 도메인 설계 조직은 상속의 업무적 is-a 관계 한정과 공유 구현의 변동성 검토 후 최소화.
3. 품질 조직은 인터페이스 계약 시험 운영을 통한 구현체 간 대체 가능성 확인.

## Ⅶ. 추상 클래스와 인터페이스의 결론

- 핵심 요약 : 추상 클래스는 공통 구현의 상속 수단, 인터페이스는 역할 계약의 수단.
- 시사점 : 재사용과 교체라는 설계 의도의 구분이 두 수단 선택의 기준.
