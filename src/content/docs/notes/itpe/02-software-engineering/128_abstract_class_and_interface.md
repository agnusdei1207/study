## 연관 키워드
- 추상 클래스, 인터페이스, 상속, 다중 구현, 템플릿 메서드, ISP

### Ⅰ. 추상 클래스와 인터페이스의 개요

- 핵심 요약 : 추상 클래스는 공통 상태·구현을 공유하는 상속 기반이고 인터페이스는 구현체가 제공할 역할 계약을 정의.
- 개념 : Java에서 **추상 클래스**는 인스턴스화할 수 없고 필드·생성자·구현 메서드를 가질 수 있으며, **인터페이스**는 타입 계약과 다중 구현 가능한 역할을 표현.
- 배경 및 필요성 : 여러 구현체 간 공통 코드 재사용과 느슨한 결합·대체 가능성의 균형 필요.
- 주요 목적 : 공통 구현 재사용과 다형적 계약을 적절한 추상화 경계로 제공.

### Ⅱ. 추상 클래스와 인터페이스의 특징 및 장점

- 핵심 요약 : 구현·상태 공유가 핵심이면 추상 클래스, 독립 역할·다중 타입 계약이 핵심이면 인터페이스가 적합.

1. 추상 클래스의 생성자·상태 : 공통 불변식과 기본 구현 제공 → 하위 클래스 간 중복 감소.
2. 인터페이스의 다중 구현 : 서로 다른 클래스에 같은 능력 계약 적용 → 결합 감소와 대체성 향상.
3. 디폴트 메서드 : 인터페이스에 기본 동작을 추가할 수 있으나 상태·생성자 기반 공유는 불가 → 진화 편의와 제한된 구현 재사용.

### Ⅲ. 추상 클래스와 인터페이스의 구조 (흐름)

- 핵심 요약 : 공통 상태·생성 초기화가 필요한지와 역할의 조합 가능성을 따져 계약 또는 기반 클래스를 정의.

```text
공통 요구 분석
   ↓
공유 상태·생성자·기본 구현 필요?
   ├ 예 → 추상 클래스 상속 구조
   └ 아니오 → 인터페이스 역할 계약
               ↓
        구현체가 계약 구현
               ↓
        다형적 호출·교체 검증
```

- 설계 원칙 : 구현은 인터페이스에 의존하고 구현체의 상속은 is-a 관계와 대체 가능성이 성립할 때 사용.

```text
인터페이스 역할 A ─┐
인터페이스 역할 B ─┼→ 구체 클래스 (다중 구현 가능)
추상 기반 클래스 ───┘  (클래스 상속은 단일)
```

### Ⅳ. 추상 클래스와 인터페이스 비교

- 핵심 요약 : 상속 계층의 공통 기반 구현은 추상 클래스, 독립 역할 계약과 복수 조합은 인터페이스가 유리.

| 비교 기준 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 상태·생성자 | 인스턴스 필드·생성자 보유 가능 | 인스턴스 상태·생성자 없음 |
| 상속·구현 수 | 클래스 단일 상속 | 여러 인터페이스 구현 가능 |
| 적합 목적 | 밀접한 하위 타입의 상태·기본 구현 공유 | 서로 다른 타입에 적용할 역할·계약 정의 |

### Ⅴ. 추상 클래스와 인터페이스의 한계와 방안

- 핵심 요약 : 잘못된 상속 계층·비대해진 계약·불필요한 추상화는 결합과 변경 비용을 높이므로 작고 안정적인 역할 중심으로 설계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 상속 결합 | 기반 클래스 변경이 모든 하위 클래스에 파급 | 조합 우선, 대체 가능성 검증, 보호된 확장 점 최소화 | 하위 클래스 변경 영향 |
| 비대 인터페이스 | 한 계약에 무관한 기능이 혼재해 구현체가 불필요 메서드 구현 | ISP에 따라 역할 별 작은 인터페이스 분리 | 빈 구현·예외 메서드 수 |
| 과도한 추상화 | 변형 가능성 없는 계층·래퍼가 탐색 복잡도 증가 | 실제 변경 이유·소비자가 확인된 지점 만 추상화 | 간접 호출 깊이·미사용 추상 타입 |

### Ⅵ. 추상 클래스와 인터페이스의 제언

- 핵심 요약 : 아키텍트는 소비자 관점에서 계약을 먼저 정의 하고 공통 구현은 변동성과 대체성 검토 후 최소화.

1. API 설계 자는 인터페이스를 작게 구성 하고 하위 호환 정책과 디폴트 메서드 충돌을 명시.
2. 도메인 팀 은 상속을 업무적 is-a 관계에 한정 하고 상태 공유 보다 조합을 우선 검토.
3. 리뷰 자 는 구체 구현 시험과 계약 시험을 병행 해 구현체 간 대체 가능성을 확인.

### Ⅶ. 추상 클래스와 인터페이스의 결론

- 핵심 요약 : 추상 클래스는 상태·기본 구현의 상속 수단이고 인터페이스는 구현 독립적 역할 계약의 수단.
- 시사점 : 둘 중 하나를 일률적으로 선택 하기 보다 공유 구현과 다형적 확장 이라는 설계 의도를 분명히 할 필요.
