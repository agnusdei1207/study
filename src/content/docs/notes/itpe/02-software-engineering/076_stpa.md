## 연관 키워드

- STPA(System-Theoretic Process Analysis), STAMP, 제어 구조, 안전 제약
- 손실, 위험, 안전하지 않은 제어 행위(UCA), 손실 시나리오, 프로세스 모델

## Ⅰ. STPA의 개요

- 핵심 요약 : 사고 원인을 부품 고장이 아닌 제어와 피드백의 부적절함에서 찾아내는 시스템 이론 기반 안전 분석 기법.
- 개념 : **손실**(인명·임무·정보·환경 등 가치의 상실)과 그로 이어질 수 있는 **위험**(손실을 일으킬 수 있는 시스템 상태)을 제어 루프의 부적절함에서 찾아내는 기법, **시스템 이론적 프로세스 분석**(STPA, System-Theoretic Process Analysis).
- 배경 및 필요성 : 소프트웨어·사람·조직이 얽힌 복잡 시스템에서는 각 구성 요소가 정상 작동해도 상호 작용 설계의 결함으로 사고가 발생하므로, 고장 중심 분석만으로 부족.
- 주요 목적 : 위험 상태를 설계 단계에서 찾아내 **안전 제약**(위험을 차단·완화하도록 부과하는 조건)과 시험 요건으로 전환해 시스템 수준의 안전성 확보.

## Ⅱ. STPA의 특징 및 장점

- 핵심 요약 : 제어 관점의 사고 모형·시스템 전체 대상·제어 행위 점검·설계 초기 적용이 분석의 깊이를 높이는 구조.

1. 제어 관점의 사고 모형 : **STAMP**(System-Theoretic Accident Model and Processes, 시스템 이론 기반 사고 모형) 관점에서 사고를 제어 실패의 결과로 해석 → 고장 확률 데이터 없이도 분석 가능.
2. 시스템 전체 분석 대상 : 소프트웨어·운영자·조직 절차·외부 환경을 **제어 구조**(제어자와 제어 대상 사이의 위계적 연결)에 포함 → 구성 요소 간 상호 작용 위험까지 포괄.
3. 제어 행위 점검 : 모든 제어 행위를 **안전하지 않은 제어 행위**(UCA, Unsafe Control Action) 관점에서 제공·미제공·시기·지속 4가지로 점검 → 위험 조건의 체계적 발견.
4. 설계 초기 적용 : 요구 정의 단계부터 수행해 위험을 사후 조사가 아닌 사전 제거 대상으로 전환 → 설계 변경 비용 절감.
5. 시나리오 기반 결과물 : 도출 결과를 **손실 시나리오**와 안전 제약 형태로 정리해 요구 사항·시험 케이스로 전환 → 검증 가능한 안전 요건 확보.

## Ⅲ. STPA의 구조 (흐름)

- 핵심 요약 : 손실·위험 정의에서 손실 시나리오 분석까지 이어지는 4단계 절차와, 제어자·피드백의 루프 모델이 분석 기준.
- 4단계 절차 : 손실·위험·안전 제약 정의 → 제어 구조 모델링 → UCA 식별 → 손실 시나리오 분석 순서로 진행하고, 결과를 요건과 모델에 환류.
- 제어 루프 : 제어자는 제어 행위로 프로세스에 작용하고 피드백으로 상태를 파악하며, 그 판단 기준을 **프로세스 모델**(제어자가 유지하는 대상 상태 정보)이라 함.

```text
1단계  손실·위험·안전 제약 정의
   ↓
2단계  제어 구조 모델링
   ↓
3단계  UCA 식별
   ↓
4단계  손실 시나리오 분석
   ↓
안전 요건 반영·모델 갱신
```

```text
제어자 (프로세스 모델 보유)
   ↓ 제어 행위
제어 대상 프로세스
   ↑ 피드백 (센서·상태 보고)
```

```text
[ UCA 4가지 유형 ]

제공 : 위험한 제공 · 필요한 미제공
시기 : 너무 이른 · 너무 늦은 제공
지속 : 너무 긴 · 너무 짧은 적용
```

## Ⅳ. STPA와 FTA·FMEA의 비교

- 핵심 요약 : FTA·FMEA가 구성 요소의 고장을 분석 단위로 삼는 데 비해, STPA는 제어와 상호 작용을 단위로 삼음.
- FTA : **FTA**(Fault Tree Analysis, 결함 트리 분석)는 사고(최상위 사건)를 하위 원인의 논리 결합으로 역추적하는 기법.
- FMEA : **FMEA**(Failure Mode and Effects Analysis, 고장 모드 및 영향 분석)는 구성 요소별 고장 모드와 영향을 나열해 심각도를 평가하는 기법.

| 비교 축 | STPA | FTA | FMEA |
| --- | --- | --- | --- |
| 분석 방향 | 제어 구조 전체에서 출발 | 최상위 사건에서 원인으로 역추적 | 구성 요소 고장에서 영향으로 전개 |
| 사고 원인 관점 | 제어·피드백의 부적절함 | 사건의 논리적 결합 | 부품 고장과 그 영향 |
| 소프트웨어·인간 처리 | 제어 행위로 자연스럽게 포함 | 고장 사건화가 곤란 | 고장 모드 정의가 곤란 |
| 데이터 요구 | 정성 분석 중심 | 고장 확률 데이터 필요 | 심각도·발생도 평가 필요 |
| 결과물 | 안전 제약·손실 시나리오 | 최소 절단 집합 | 고장 모드별 조치 목록 |

## Ⅴ. STPA의 한계와 방안

- 핵심 요약 : 분석 경계 누락·UCA 폭증·결과의 설계 미반영·역량 편차를 경계 정의·우선 순위·추적·검토로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 분석 경계 누락 | 시스템 경계를 좁게 설정 → 외부 운영자·공급자 제어 누락 | 경계·이해관계자 정의를 별도 단계로 수행·검토 | 미검토 인터페이스 수 |
| UCA 폭증 | 제어 행위와 맥락의 조합 급증 → 분석 지연·품질 저하 | 위험도 높은 제어 행위 우선 분석, 맥락 정의 표준화 | 미분석 제어 행위 비율 |
| 결과의 설계 미반영 | 시나리오가 문서에 머묾 → 요구·시험 누락 | 안전 제약의 요구·시험 항목 추적 관리 | 미추적 안전 제약 수 |
| 수행 역량 편차 | 분석자별 판단 기준 상이 → 결과 편차 | 교육·사례 템플릿·동료 검토 절차 | 검토 지적 사항 수 |

## Ⅵ. STPA 적용에 대한 기술사적 제언

- 핵심 요약 : 개발 생명 주기 전반에 STPA를 내재화하고 안전·보안·운영 분석과 통합하는 조직 체계 필요.
- 시스템 안전 조직 : 개발 초기부터 STPA 수행을 의무 절차로 규정하고, 안전 담당자·설계자·운영자가 참여하는 공동 분석 체계 운영.
- 안전·보안 통합 : 침해 시나리오를 제어 관점에서 같은 절차로 분석해 안전 요건과 보안 요건의 중복·공백 제거.
- 인증·규제 연계 : 손실 시나리오·안전 제약을 인증 심사와 규제 대응의 근거 자료로 활용.

## Ⅶ. 결론

- 핵심 요약 : STPA는 고장 목록이 아닌 제어 구조의 안전 제약을 산출하는 설계 단계 분석 기법임.
- 복잡 시스템의 안전은 구성 요소 신뢰도의 합이 아니라 제어·피드백 구조의 적절성에서 확보됨.
