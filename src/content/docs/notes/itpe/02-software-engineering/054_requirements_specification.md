## 본론: 개념 및 핵심 메커니즘

### 1. 요구사항 명세(SRS)의 본질과 표준 규격

- **개념**: 시스템이 수행해야 할 기능과 준수해야 할 제약조건 및 비기능 품질 속성을 체계적으로 정의한 **발주자-개발자 간의 공식적인 기술 계약 기준선(Baseline)**.
- **표준 규격의 진화**:
  - **IEEE 830-1998**: 전통적인 소프트웨어 요구사항 명세서(SRS) 권고 실천 지침.
  - **ISO/IEC/IEEE 29148:2018**: 시스템 및 소프트웨어 공학의 요구공학 생명주기를 포괄하는 최신 국제 통합 표준으로 IEEE 830을 공식 대체(Superseded).

### 2. 우수한 요구사항 명세서의 8대 품질 특성 (IEEE 830)

| 품질 특성 | 공학적 의미 및 검증 기준 | 안티패턴 및 위반 사례 |
|---|---|---|
| **1. 정확성 (Correct)** | 실제 시스템이 충족해야 하는 진정한 요구와 정확히 일치함. | 잘못된 세법 산식을 기술하여 오작동 유발 |
| **2. 명확성 (Unambiguous)** | 모든 문장이 단 하나의 의미로만 해석되어 다의적 해석이 배제됨. | "적절한 속도로 처리한다" (사람마다 해석 상이) |
| **3. 완전성 (Complete)** | 모든 필수 기능, 성능, 제약조건, 예외 처리, 입출력이 누락 없이 포함됨. | 정상 흐름만 명세하고 네트워크 타임아웃 예외 누락 |
| **4. 일관성 (Consistent)** | 명세서 내부의 요구사항 간에 충돌이나 모순이 존재하지 않음. | 앞쪽엔 화면당 50건 페이징, 뒤쪽엔 무한 스크롤 명세 |
| **5. 순위화 (Ranked)** | 각 요구사항의 비즈니스 중요도와 안정성(우선순위)이 명시됨. | 모든 요구사항이 1순위로 지정되어 범위 조정 불가 |
| **6. 검증가능성 (Verifiable)**| 유한하고 비용 효율적인 시험/검사를 통해 충족 여부를 판정할 수 있음. | "사용하기 편리해야 한다" (정량 수치 부재) |
| **7. 수정가능성 (Modifiable)**| 중복 서술이 없고 목차와 색인이 잘 정리되어 수정이 용이함. | 동일 요구사항이 10군데 산재하여 수정 시 누락 |
| **8. 추적가능성 (Traceable)** | 요구사항의 출처(비즈니스 니즈) 및 후속 산출물(설계/테스트)과 매핑됨. | 요구사항 ID 부재로 테스트 케이스 누락 |

### 3. ISO/IEC 25010 제품 품질속성과 요구사항 상충(Trade-off)

- **제품 품질속성 8대 특성**:
  1. 기능 적합성 (완전성, 정확성, 적절성)
  2. 성능 효율성 (시간 반응성, 자원 활용성, 용량)
  3. 사용성 (적절성 인식, 학습성, 운영성, 오류방지)
  4. 신뢰성 (성숙성, 가용성, 결함허용, 복구성)
  5. 보안성 (기밀성, 무결성, 부인방지, 책임추적성, 인증)
  6. 유지보수성 (모듈성, 재사용성, 분석성, 수정성, 시험성)
  7. 이식성 (적응성, 설치성, 대체성)
  8. 호환성 (공존성, 상호운용성)
- **품질 상충 해결 전략**:
  - 보안성(다중 암호화/인증) 강화 시 성능 및 사용성 저하 발생 $\rightarrow$ **유틸리티 트리(Utility Tree) 기반 ATAM 워크숍**을 통해 비즈니스 우선순위에 따라 허용 가능한 임계선 확정.

## 명세 작성 기법 3종 비교

| 비교 항목 | 비정형 명세 (자연어) | 정형 명세 (Formal Spec) | 실행 가능한 명세 (BDD) |
|---|---|---|---|
| **작성 도구** | 한글, MS-Word, Confluence | 수학적 기호, Z, VDM, Petri-Net | Gherkin 문법 (Given-When-Then), Cucumber |
| **이해도/가독성** | 누구나 쉽게 읽음 (최상) | 수학/공학 전문가만 판독 (최악) | 비즈니스 담당자와 개발자 모두 공유 (우수) |
| **모호성** | **해석 차이 발생 위험 큼** | 모호성 제로 (완벽한 엄밀성) | 구체적 예시 기반으로 모호성 극소화 |
| **자동 검증** | 불가능 (수기 인스펙션만 가능) | 수학적 정리 증명기(Theorem Prover) | **테스트 코드로 즉시 자동 실행 (CI 연동)** |
| **주 적용처** | 일반 엔터프라이즈 SI 사업 | 원자력, 항공, 의료기기 기능안전 | 현대 애자일/클라우드 네이티브 서비스 |

## 실무 장애 시나리오 및 공학적 대안

### 1. 현장 장애 사례

1. **"빠르게 응답해야 한다"는 모호한 명세로 인한 준공 검수 파행**:
   - SRS에 정량 지표 없이 서술했다가, 발주자는 0.5초를 요구하고 개발사는 3초를 주장하며 소송전 비화.
2. **요구사항 변경 시 영향받는 소스코드 추적 불가**:
   - 법 개정으로 할인율 정책이 바뀌었으나, 해당 요구사항이 어느 클래스와 테스트 케이스에 구현되어 있는지 알 수 없어 수작업 전수 검사로 납기 지연.

### 2. 문제 원인 및 공학적 해결책

| 장애 상황 | 근본 원인 | 공학적 대책 (대안 기술) | 개선 효과 |
|---|---|---|---|
| **모호한 성능 검수** | 정량적 검증 가능성(Verifiable) 부재 | **SEI 품질속성 시나리오 (자극-환경-반응-측정)** 템플릿 강제 ("피크 타임 1,000 TPS 유입 시 95% 응답시간 1.5초 이내") | 주관적 해석 차단 및 객관적 검수 합격 |
| **변경 영향도 미파악** | 요구사항 추적성(Traceability) 결여 | 요구사항 고유 식별자(REQ-01) 기반 **요구사항 추적 매트릭스(RTM)** 전산화 | 변경 영향 분석 시간 80% 단축 및 결함 예방 |
| **사문화된 워드 문서** | 코드와 분리된 무거운 명세 관리 | **Cucumber BDD를 연계한 살아있는 문서(Living Documentation)** 체계 도입 | 명세서와 실제 구현 코드의 100% 동기화 |

## 결론: 기술사 답안 차별화 포인트

1. **검증 가능성(Verifiability)의 절대적 기준 제시**: 기술사 답안에서 "검증할 수 없는 문장은 요구사항이 아니다"라는 공학적 명제를 선언하고, 모든 정성적 형용사를 **정량적 측정 지표(SLA, MTTR, TPS, 커버리지)**로 전환하는 구체적 시나리오를 제시할 것.
2. **Living Documentation(살아있는 명세) 패러다임 제언**: 책장에 꽂혀 사문화되는 수백 쪽의 종이 명세서 관행을 비판하고, **Git 기반 마크다운과 BDD(Given-When-Then) 테스트 코드를 결합하여 빌드 시마다 자동 검증되는 '실행 가능한 명세'**로 진화해야 함을 결론으로 강조할 것.
