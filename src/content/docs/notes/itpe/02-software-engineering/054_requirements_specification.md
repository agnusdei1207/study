## 30초 인출

- 본질: **소프트웨어 요구사항 명세서(SRS)**는 소프트웨어와 외부 인터페이스에 필요한 요구사항을 구조화한 정보
- 메커니즘: 이해관계자 요구 → 분석·정제 → 검증 가능한 요구사항 기록 → 추적·변경 관리
- 핵심: 개별 요구의 품질과 요구사항 집합의 완전성·일관성 확인

<details>
<summary>핵심 용어</summary>

- **소프트웨어 요구사항 명세서(SRS, Software Requirements Specification)**: 소프트웨어의 기능·성능·제약·속성과 외부 인터페이스에 관한 필수 요구사항의 구조화된 집합
- **ISO/IEC/IEEE 29148**: 시스템·소프트웨어 생애주기의 요구공학 프로세스와 요구사항 정보 항목을 다루는 국제표준
- **IEEE 830-1998**: 소프트웨어 요구사항 명세서 작성 지침으로, ISO/IEC/IEEE 29148에 의해 대체된 표준
- **요구사항 추적성**: 요구사항과 상위 요구·구현·검증 항목 사이의 연결 관계
- **요구사항 검증(Verification)**: 요구사항이 명확하고 잘 구성됐는지 확인하는 활동
- **요구사항 확인(Validation)**: 정의된 요구사항이 이해관계자의 의도에 맞는 시스템을 표현하는지 확인하는 활동

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 요구사항 명세서(SRS)**는 소프트웨어의 기능·성능·제약·속성과 외부 인터페이스에 관한 필수 요구사항의 구조화된 집합 |
| 목적 | 이해관계자의 필요를 구현·검증 가능한 기준으로 정리하고 요구사항 합의·추적을 지원 |

### Ⅱ. 주요 정보 항목

| 정보 항목 | 핵심 내용 |
|---|---|
| 맥락·범위 | 시스템 목적·범위·사용자·운영 환경 |
| 인터페이스 | 외부 시스템·사용자·통신 접점과 제약 |
| 기능 | 시스템이 제공해야 할 행위와 응답 |
| 품질·제약 | 성능·보안 등 품질 요구와 설계·운영 제약 |

### Ⅲ. 요구사항 품질 관리

```text
이해관계자 필요·제약
    ↓ 도출·분석
명확하고 단일한 요구
    ↓ 검토·시험 가능성 확인
승인된 SRS
    ↓ 추적·변경통제
설계·구현·시험 기준
```

개별 요구사항은 필요성·명확성·단일성·실현 가능성·검증 가능성을 확인하고, 요구사항 집합은 완전성·일관성 검토.

제언: 이해관계자 합의와 검증 방법이 함께 확인된 요구사항만 기준선에 반영.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 요구사항 명세서(SRS)**는 소프트웨어의 기능·성능·제약·속성과 외부 인터페이스에 관한 필수 요구사항의 구조화된 집합 |
| 목적 | 이해관계자의 필요를 구현·검증 가능한 기준으로 정리하고 요구사항 합의·추적을 지원 |

현행 요구공학 표준인 ISO/IEC/IEEE 29148은 생애주기 요구공학 프로세스와 정보 항목의 내용을 다루며, 과거 IEEE 830-1998을 대체한 표준.

## Ⅱ. 요구사항의 도출과 명세

```text
이해관계자 필요·제약
    ↓
이해관계자 요구
    ↓ 기능·품질 요구 구체화
시스템·소프트웨어 요구
    ↓ 합의·명세
SRS 항목·수락 기준
```

## Ⅲ. SRS의 주요 정보 항목

| 정보 항목 | 확인할 내용 | 예시 |
|---|---|---|
| 목적·범위·맥락 | 문제·사용자·운영 환경과 대상 경계 | 적용 대상과 제외 범위 |
| 인터페이스 | 외부 사용자·시스템·통신 접점 | 요청·응답 형식과 오류 처리 |
| 기능 요구 | 주어진 조건에서 시스템이 수행할 동작 | 권한별 조회·변경 행위 |
| 품질 요구 | 성능·보안·가용성 등 요구 품질 | 부하·측정 조건·목표값 |
| 제약·가정 | 법적·기술적 제약과 전제 | 사용 가능한 플랫폼·연계 조건 |

위 항목은 문서 구성의 실무 예시이며, 특정 목차가 모든 프로젝트에 동일하게 강제되는 의미는 아님.

## Ⅳ. 요구사항 품질 특성

| 관점 | 특성 | 검토 질문 |
|---|---|---|
| 개별 요구 | 필요성·적절성 | 실제 필요에 대응하고 해당 추상화 수준에 맞는가 |
| 개별 요구 | 명확성·단일성 | 하나의 의미와 요구만 담고 있는가 |
| 개별 요구 | 완전성·정확성 | 조건·응답이 빠짐없고 원래 필요를 바르게 표현하는가 |
| 개별 요구 | 실현 가능성·검증 가능성 | 제약 안에서 실현 가능하며 시험·분석으로 확인할 수 있는가 |
| 요구사항 집합 | 완전성·일관성 | 집합 전체가 필요한 기능을 포괄하며 서로 충돌하지 않는가 |
| 요구사항 집합 | 추적성·관리성 | 상위 필요와 구현·시험을 연결하고 변경 영향을 찾을 수 있는가 |

요구사항 특성은 개별 문장과 요구사항 집합을 구분해 평가하며, IEEE 830의 과거 8개 특성을 현행 국제표준의 고정 목록처럼 취급하지 않음.

## Ⅴ. 검증·확인과 추적 관리

| 활동 | 목적 | 대표 방법 |
|---|---|---|
| 검증(Verification) | 요구사항이 잘 구성되고 품질 특성을 갖췄는지 확인 | 동료 검토·모호성 검사·검증 가능성 점검 |
| 확인(Validation) | 요구사항이 이해관계자의 실제 필요를 표현하는지 확인 | 시나리오 검토·프로토타입·이해관계자 합의 |
| 추적·변경 관리 | 요구사항의 출처와 후속 구현·시험 연결 유지 | 식별자·추적표·변경 영향 분석 |

## Ⅵ. 명세 결함과 실무 대응

| 한계 | 대응 |
|---|---|
| “빠르게”, “편리하게” 같은 모호한 표현 | 조건·대상·측정 방법을 합의해 시험 가능한 문장으로 구체화 |
| 서로 충돌하거나 중복된 요구 | 요구사항 집합 단위 검토와 이해관계자 간 우선순위 합의 |
| 요구 변경의 구현·시험 누락 | 상위 필요부터 요구·설계·시험까지 연결하고 영향 항목 갱신 |
| 요구가 문서에만 남아 실제 동작과 불일치 | 승인된 변경을 명세와 검증 자산에 함께 반영 |

## Ⅶ. 기술사적 제언 — 인수 기준까지 이어지는 요구 추적

| 한계 | 해결 방안 |
|---|---|
| 승인된 요구사항이 설계·구현·시험 및 인수 기준과 분리되어 변경 영향과 검증 책임이 흐려질 가능성 | 요구사항 식별자를 상위 필요·설계 요소·시험 사례·인수 기준에 연결하고, 변경 승인 때 관련 항목의 동시 갱신 책임 지정 |
