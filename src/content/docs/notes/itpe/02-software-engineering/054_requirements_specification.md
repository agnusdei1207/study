## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 요구공학 → **요구사항 명세(SRS)**

## 30초 인출

- 본질: 이해관계자로부터 도출·분석된 기능적·비기능적 요구와 시스템 인터페이스, 설계 제약조건을 공학적 표준(ISO/IEC/IEEE 29148)에 따라 정형화하여 문서화하는 공식 기준선 산출물
- 메커니즘: 자연어 및 정형 표기법 결합 명세 → 개별 요구사항 품질(원자성, 명확성, 검증가능성) 점검 → 요구사항 집합 품질(완전성, 일관성, 추적성) 검증 → 기준선(Baseline) 동결
- 통찰: 모호한 정성적 표현은 인수 테스트 판정 분쟁과 재작업을 유발하므로 정량적 측정 메트릭 기반의 수락 기준(Acceptance Criteria) 명시 및 BDD 문법 결합 필수

<details>
<summary>핵심 용어</summary>

- **SRS(Software Requirements Specification)** : 소프트웨어가 제공해야 할 기능, 품질속성, 외부 인터페이스를 정형화하여 기술한 공식 소프트웨어 요구사항 명세서
- **ISO/IEC/IEEE 29148** : 시스템 및 소프트웨어 생명주기 요구공학 프로세스와 SRS 표준 작성 지침을 규정한 최신 국제 표준
- **IEEE 830-1998** : 과거 널리 사용되었던 SRS 권고 표준으로 현재는 ISO/IEC/IEEE 29148로 통합 대체
- **Verification vs Validation (V&V)** : 요구사항 명세서가 표준 양식에 맞게 잘 작성되었는지(검증)와 실제 고객의 진정한 의도에 부합하는지(확인)를 점검하는 활동
- **Acceptance Criteria(수락/인수 기준)** : 시스템이 요구사항을 성공적으로 만족했는지를 객관적으로 판정하기 위한 구체적인 테스트 조건 및 기대 결과치

</details>

## 2~4교시 25점 답안

## Ⅰ. 요구사항 명세의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 개발의 대상이 되는 시스템의 기능, 비기능, 성능, 인터페이스 제약사항을 분석하여 고객과 개발자 간의 공식 계약 기준으로 삼기 위해 정형화된 형식으로 기록한 소프트웨어 요구사항 명세서(SRS) 작성 활동 |
| 목적 | 시스템 개발 범위 확정, 아키텍처 설계 및 구현의 기준점 제공, 종단간 인수 테스트(Acceptance Test) 판정 기준선 수립 |

## Ⅱ. 요구사항 명세의 핵심 특징

| 특징 | 의미 |
|---|---|
| 계약적 구속력 | 발주자와 수탁 사업자 간의 공식 산출물로서 과업 범위 및 계약 변경의 법적 기준선(Baseline) 역할 |
| 검증 가능성 (Verifiable) | 모든 명세 항목은 시스템 테스트 단계에서 객관적 수치나 시나리오를 통해 합격/불합격 판정이 가능해야 함 |
| 다관점 구조화 | 기능적 동작뿐만 아니라 외부 하드웨어/소프트웨어 인터페이스, 보안, 성능, 규제 제약조건을 망라 |
| 추적의 시발점 | 각 요구사항마다 고유 식별자(ID)를 부여하여 설계(UML), 코드(Git), 테스트 케이스(TC)와의 1:1 매핑 지원 |

## Ⅲ. ISO/IEC/IEEE 29148 기반 SRS 작성 체계

### 요구사항 정제 및 명세서 구체화 아키텍처

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. 상위 비즈니스 니즈 및 이해관계자 요구 (Stakeholder Requirements)    │
│    - "사용자가 모바일로 빠르게 결제하고 영수증을 즉시 확인하고 싶다"    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (엔지니어링 정제 및 분해)
┌────────────────────────────────────────────────────────────────────────┐
│ 2. 시스템 및 소프트웨어 요구사항 명세 (SRS 요구항목 작성)              │
│                                                                        │
│   [기능 요구사항 (Functional)]        [품질/비기능 요구사항 (Non-Functional)]│
│   - REQ-F-01: 원클릭 간편결제 지원      - REQ-NF-01: 동시접속 1만TPS 처리     │
│   - REQ-F-02: 결제 승인 즉시 푸시 알림 - REQ-NF-02: 95% 응답속도 1.5초 이하 │
│                                                                        │
│   [외부 인터페이스 (Interface)]        [설계 및 법적 제약사항 (Constraints)] │
│   - REQ-IF-01: PG사 REST API 연동     - REQ-C-01: PCI-DSS 카드 보안 규정   │
│   - REQ-IF-02: 국세청 현금영수증 연계  - REQ-C-02: 개인정보 암호화 저장     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (정형화된 문법 및 인수 조건 결합)
┌────────────────────────────────────────────────────────────────────────┐
│ 3. Given-When-Then BDD 인수 기준 (Acceptance Criteria) 명세           │
│    - Given: 잔액이 충분한 등록 카드가 존재할 때                        │
│    - When: 사용자가 결제 버튼을 클릭하면                               │
│    - Then: 2초 이내에 승인 토큰이 발행되고 주문 상태가 COMPLETED로 변경│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. V&V 품질 검증 및 공식 기준선(Baseline) 동결                         │
└────────────────────────────────────────────────────────────────────────┘
```

### SRS 표준 문서 핵심 목차 구성 (ISO/IEC/IEEE 29148)

| 장/절 | 핵심 기술 내용 | 작성 시 고려사항 |
|---|---|---|
| **1. 개요 (Introduction)** | 시스템 목적, 개발 범위, 용어 정의, 참조 문서 표준 | 대상 시스템의 경계를 명확히 설정 |
| **2. 전반적 설명 (Overall)** | 시스템 관점(Context), 사용자 특성, 운영 환경, 일반 제약 | 시스템 외부 환경과의 상호작용 개요 |
| **3. 특정 요구사항 (Specific)** | 기능 요구, 데이터베이스 요구, 성능/가용성/보안 품질속성 | 기능별 고유 ID 부여 및 정량 수치 명시 |
| **4. 외부 인터페이스 명세** | 사용자 인터페이스(UI), H/W 인터페이스, S/W API 연계 | 프로토콜, 입출력 데이터 포맷(JSON/XML) 명시 |
| **5. 검증 기준 (Verification)** | 요구사항별 검증 방법 (시험, 분석, 인스펙션, 시연) | 인수 테스트 통과 기준 사전 정의 |

## Ⅳ. 기능 요구 vs 비기능 요구 및 명세 품질 속성

### 기능 요구사항과 비기능 요구사항의 비교

| 비교 항목 | 기능적 요구사항 (Functional Requirements) | 비기능적 요구사항 (Non-Functional Requirements) |
|---|---|---|
| **본질적 성격** | 시스템이 **무엇을(What) 수행해야 하는가** | 시스템이 **어떻게(How well) 작동해야 하는가** |
| **명세 대상** | 비즈니스 로직, 데이터 입출력, 연산, CRUD 기능 | 성능(Throughput, Latency), 신뢰성, 보안성, 가용성 |
| **측정 기준** | 기능의 성공적 실행 여부 (참/거짓 판단) | 정량적 수치 메트릭 (초당 트랜잭션, 가용률 99.99%) |
| **아키텍처 영향** | 도메인 모델, 컴포넌트 분할, 서비스 API 설계 | 시스템 인프라 아키텍처, 이중화, 캐싱, 보안 솔루션 |

### 우수한 요구사항의 2대 품질 특성 체계 (ISO/IEC/IEEE 29148)

| 분류 | 품질 속성 | 정의 및 세부 점검 기준 |
|---|---|---|
| **개별 요구사항 특성 (Individual)** | **명확성 (Clear)** | 전문 용어가 일관되고 하나의 의미로만 해석되는가 |
| 개별 요구사항 특성 (Individual) | **원자성 (Singular)** | 하나의 요구 문장에 복수의 요구가 얽혀 있지 않은가 |
| 개별 요구사항 특성 (Individual) | **검증 가능성 (Verifiable)** | 테스트나 계측을 통해 요구 충족 여부를 객관적 입증 가능한가 |
| 개별 요구사항 특성 (Individual) | **실현 가능성 (Feasible)** | 주어진 예산, 기간, 기술 제약 내에서 구현 가능한가 |
| **요구사항 집합 특성 (Set)** | **완전성 (Complete)** | 시스템에 필요한 모든 조건과 예외가 누락 없이 기술되었는가 |
| 요구사항 집합 특성 (Set) | **일관성 (Consistent)** | 요구사항 간에 논리적 충돌이나 모순이 없는가 |
| 요구사항 집합 특성 (Set) | **추적성 (Traceable)** | 요구사항의 출처와 후속 설계·시험 산출물이 연결되는가 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 자연어로 작성되어 "빠르게", "직관적으로" 등 주관적이고 모호한 형용사 다수 포함 | 응답 시간(ms), 가용성(%), 학습 시간 등 정량적 수치 메트릭으로 전환 기술 |
| 기능 요구사항에만 집중하고 보안, 장애 복구 등 품질속성을 누락하여 아키텍처 실패 | ISO/IEC 25010 소프트웨어 품질 모델 체크리스트를 기반으로 비기능 요구 전수 검토 |
| 개발 중 요구사항 변경이 빈번하게 발생하여 SRS 문서가 최신 코드와 불일치 | Docs-as-Code(Markdown + Git) 기반의 명세서 버전 관리 및 PR 머지 시 동시 갱신 |

## Ⅵ. 제언

BDD(행위 주도 개발) Gherkin 문법을 결합한 실행 가능한 명세(Executable Specification) 및 AI 기반 명세서 린팅

### 실행 가능한 명세서(Executable SRS) 파이프라인

```text
[요구사항 명세서 작성 (Markdown)]
  ├─ 비즈니스 목표 기술
  └─ Gherkin 문법 기반 피처(Feature) 시나리오 작성
       ↓
[Cucumber / Playwright 테스트 코드 자동 파싱]
  ├─ Given: 테스트 데이터 사전 세팅
  ├─ When: 실제 시스템 API/UI 호출
  └─ Then: 기대 응답값 단정문(Assert) 자동 매핑
       ↓
[CI 파이프라인에서 명세서가 곧바로 자동화 테스트로 실행]
       ↓
[명세 통과 시 '살아있는 문서(Living Documentation)' 포털에 자동 발행]
```

### 요구사항 명세 작성 의사결정 체계

```text
요구사항 문장 작성
       ↓
[문장에 '빠르게', '편리하게', '적절히' 등 주관적 형용사가 포함되었는가?]
       ├─ 예 ──→ [정량적 측정 지표로 재작성] (예: 피크타임 2초 이내)
       └─ 아니오 ─→ [하나의 문장에 '그리고', '또한'으로 복수 기능이 묶였는가?]
                         ├─ 예 ──→ 단일 원자적 요구사항으로 분할
                         └─ 아니오 ─→ Given-When-Then 인수 기준 도출 및 SRS 반영
```

### 선택 근거: 전통적 문서 SRS와 제언 실행 가능한 명세(BDD) 비교

| 구분 | 전통적 자연어 워드(Word) SRS | 제언: 실행 가능한 명세 (Executable SRS) |
|---|---|---|
| 해석의 명확성 | 자연어 문장으로 개발자/테스터 간 해석 왜곡 빈발 | 정형 Gherkin 문법으로 누구나 동일하게 이해 |
| 문서 최신성 | 개발 완료 후 방치되어 코드와 문서 괴리 발생 | 빌드 시 테스트로 실행되므로 코드와 100% 동기화 |
| 테스트 연계 | 테스트 팀이 별도로 테스트 케이스를 수기 작성 | 명세서 자체가 즉시 자동화 테스트 스크립트로 동작 |
