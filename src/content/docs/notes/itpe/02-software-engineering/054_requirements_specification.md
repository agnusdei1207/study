## 30초 인출

- 본질: 요구사항 명세서(SRS)는 소프트웨어가 제공할 기능·품질·제약을 개발자와 사용자가 같은 뜻으로 이해하도록 문서화한 합의 문서
- 메커니즘: 요구를 기능·비기능·제약으로 구분해 요구 ID별로 기술하고 명확성·완전성·일관성·검증 가능성을 점검
- 통찰: "빠르게"·"사용자 친화적" 같은 모호한 표현은 시험할 수 없으므로 비기능 요구도 측정 가능한 수치와 조건으로 명시

<details>
<summary>핵심 용어</summary>

- **요구사항 명세서(SRS, Software Requirements Specification)** : 소프트웨어의 기능·품질·제약을 기술한 문서
- **ISO/IEC/IEEE 29148** : 요구공학 프로세스와 요구사항 명세서 작성을 다루는 표준
- **검증(Verification)과 확인(Validation)** : 명세서가 규칙에 맞게 작성됐는지 확인하는 활동과 사용자 요구를 반영하는지 확인하는 활동
- **인수 기준(Acceptance Criteria)** : 요구가 충족됐다고 인정하는 판정 조건

</details>

## 2~4교시 25점 답안

## Ⅰ. 요구사항 명세서의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **요구사항 명세서** 는 소프트웨어가 제공할 기능·품질·제약을 문서화한 합의 문서 |
| 목적 | 개발자·사용자 간 동일한 이해와 개발·시험의 기준 제공 |

## Ⅱ. 명세서의 특징

| 특징 | 의미 |
|---|---|
| 합의 문서 | 이해관계자가 확인·승인 |
| 개발·시험 기준 | 설계·구현·시험의 출발점 |
| 변경 통제 | 승인 후 변경은 절차에 따라 관리 |

## Ⅲ. 명세서의 구성과 작성 절차

### 명세서의 구성

```text
요구사항 명세서
    ├─ 개요 ── 목적·범위·용어
    ├─ 기능 요구사항 ── 요구 ID별 기능
    ├─ 비기능 요구사항 ── 성능·보안·신뢰성 (측정 기준 포함)
    └─ 제약사항 ── 법규·기술·운영 환경
```

### 확대: 명세 작성과 검토 절차

```text
요구사항 분류·ID 부여
    ↓
요구별 서술 (측정 기준·인수 기준 포함)
    ↓
품질 특성 점검 (명확성·완전성·일관성·검증 가능성)
    ↓
이해관계자 검토·승인
```

## Ⅳ. 명세 품질 특성

| 특성 | 의미 | 나쁜 예 → 좋은 예 |
|---|---|---|
| 명확성 | 하나의 해석만 가능 | "빠르게" → "응답 2초 이내" |
| 완전성 | 필요한 요구가 모두 포함 | 정상 흐름만 → 예외 흐름 포함 |
| 일관성 | 요구 사이에 충돌 없음 | 서로 상반된 요구 → 조정 |
| 검증 가능성 | 시험으로 확인 가능 | "사용하기 쉽다" → "신규 사용자 5분 내 주문 완료" |
| 추적 가능성 | 고유 ID로 설계·시험 연결 | ID 없음 → 요구 ID 부여 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 모호한 표현으로 해석 차이 발생 | 비기능 요구에 수치·조건 명시 |
| 요구 간 충돌·중복 | 검토 회의와 일관성 점검표 |
| 명세서가 최신이 아니게 되는 문제 | 변경 통제 절차와 추적표 연계 |

## Ⅵ. 제언

모든 요구사항에 측정 가능한 기준과 인수 기준을 함께 기술하고, 검토 시 검증 가능성을 필수 점검 항목으로 적용

### 검증 가능 요구 작성

```text
요구 서술
    ↓
측정 기준(수치·조건) 포함 여부 점검
    ├─ 있음 → 인수 기준 연결
    └─ 없음 → 기준 보완 후 재검토
```

### 선택 근거: 서술형 요구만 기술하는 방식과의 비교

| 구분 | 서술형만 | 제언: 측정·인수 기준 포함 |
|---|---|---|
| 해석 | 사람마다 상이 | 기준으로 통일 |
| 시험 | 기준 부재 | 인수 기준으로 시험 |
| 분쟁 | 발생 가능 | 기준으로 판정 |
