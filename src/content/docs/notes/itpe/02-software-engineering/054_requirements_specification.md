## 연관 키워드

- 요구사항 명세서(SRS, Software Requirements Specification), IEEE 830, ISO/IEC/IEEE 29148, 기능 요구사항, 비기능 요구사항
- 정확성, 명확성, 완전성, 일관성, 검증 가능성, 추적 가능성, 인수 기준(Acceptance Criteria), Living Documentation

## Ⅰ. 요구사항 명세서(SRS)의 개요

- 핵심 요약 : 확정된 요구사항을 문서화해 계약 기준선과 단일한 구현·검증 기준을 제공하는 공식 기술 문서.
- 개념 : 이해관계자 합의를 거쳐 확정된 기능 요구사항, 품질속성, 인터페이스, 설계 제약조건을 명확하고 완전하게 기술한 **요구사항 명세서**(SRS, Software Requirements Specification)다.
- 배경 및 필요성 : 발주자와 수주자 사이에 계약 기준선(Baseline)을 세우고, 설계자·개발자·테스터가 같은 문서를 보고 일하도록 해 요구 해석 분쟁을 줄일 필요가 있다.
- 주요 목적 : 구현과 검증이 따라야 할 단일 기준을 제공하고, 인수 시점의 합격 여부를 판단할 근거를 마련하는 것.
- 표준 규격 : IEEE(Institute of Electrical and Electronics Engineers) 830은 SRS 작성 가이드로 널리 쓰였고, 현행 표준은 ISO/IEC/IEEE 29148이 이를 대체한다.

## Ⅱ. SRS의 특징 및 장점

- 핵심 요약 : 정확성·명확성·완전성·일관성 등 품질 특성을 갖춘 명세가 검증 가능한 기준으로 작동하는 구조.

1. 정확성(Correctness) : 실제로 충족해야 할 요구를 빠짐없이 반영 → 재작업 감소.
2. 명확성(Unambiguous) : 모든 문장이 하나의 의미로만 읽힘 → 발주자와 개발자의 해석 차이 방지.
3. 완전성(Completeness) : 기능, 예외, 제약조건이 누락 없이 기술됨 → 구현 중 미정의 요구 발생 억제.
4. 일관성(Consistency) : 요구 간 충돌과 모순이 없음 → 모듈 간 데이터 규격과 업무 규칙의 충돌 방지.
5. 중요도 순위화(Ranked) : 요구별 우선순위와 안정성을 명시 → 일정 압박 시 핵심 기능 우선 확보.
6. 검증 가능성(Verifiable) : 테스트로 합격 여부를 판정할 수 있음 → 인수 테스트 설계 가능.
7. 수정 용이성(Modifiable) : 구조와 표현을 유지하며 변경을 반영할 수 있음 → 변경 시 문서 누락 감소.
8. 추적 가능성(Traceable) : 요구의 출처(RFP, Request for Proposal)와 설계·코드·테스트를 양방향으로 연결 → 과업 누락 확인과 변경 영향도 분석.

## Ⅲ. SRS의 구조 (흐름)

- 핵심 요약 : IEEE 830 기준으로 소개, 전체 설명, 구체적 요구사항의 3단 구성을 따르며, 요구사항은 추적 흐름으로 후속 산출물과 연결.

```text
[ 1. 소개 (Introduction) ]
  목적, 범위, 용어 정의, 참조 문서
        ↓
[ 2. 전체 설명 (Overall Description) ]
  제품 조망, 사용자 특성, 제약 조건
        ↓
[ 3. 구체적 요구사항 (Specific Req.) ]
  인터페이스, 기능, 비기능, 품질속성
```

```text
[ 요구사항 추적 흐름 (Traceability) ]

RFP (제안요청서)
        ↓
SRS (요구사항 명세서)
        ↓
설계 명세 / 소스코드 / 테스트 케이스
        ↓
양방향 매핑으로 누락과 변경 영향 검증
```

## Ⅳ. 기능 요구사항과 비기능 요구사항의 비교

- 핵심 요약 : 기능 요구사항은 시스템이 무엇을 하는지, 비기능 요구사항은 얼마나 잘 하는지를 정의하며 검증 방식도 다름.

| 비교 항목 | 기능 요구사항(Functional Requirement) | 비기능 요구사항(Non-functional Requirement) |
| --- | --- | --- |
| 정의 | 수행해야 할 기능, 입력, 처리 로직, 출력 | 품질속성과 설계 제약조건 |
| SRS상 예시 | 사용자·하드웨어·소프트웨어·통신 인터페이스 명세 | 응답 시간, 처리량, 동시 접속자 수 |
| 관련 품질속성 | 기능 충족 여부로 판별 | 신뢰성, 가용성, 보안성, 유지보수성 |
| 검증 방법 | 기능 테스트로 합격 여부 판정 | SLA(Service Level Agreement) 등 정량 지표로 측정 |

## Ⅴ. SRS의 한계와 방안

- 핵심 요약 : 문서 박제화, 과잉 명세, 모호한 표현의 한계를 실행 명세, 기술 타당성 검증, 정량 인수 기준으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 명세와 구현의 동기화 단절 | 초기에 작성한 방대한 SRS가 잦은 변경을 반영하지 못해 실제 코드와 괴리되는 문서 박제화 | 살아있는 문서(Living Documentation) 체계, Cucumber·SpecFlow 같은 실행 가능한 명세, CI(Continuous Integration) 파이프라인 연동 | 명세와 코드 불일치 건수 |
| 기술 타당성 검증 없는 과잉 명세 | 아키텍처 제약과 인프라 비용, 레거시 연동을 고려하지 않아 개발 중 전면 재설계 위험 | 기술 아키텍트 참여 아래 스파이크(Spike)와 PoC(Proof of Concept) 선행 검증, 비기능 요구에 측정 가능한 SLA 수치 명시 | 변경 요청 건수, 재설계 건수 |
| 자연어의 모호성 | TBD(To Be Determined)나 '신속한 응답' 같은 주관 표현이 남아 납품 검수 때 분쟁 발생 | 요구마다 정량적 인수 기준(Acceptance Criteria)과 검증 방법(테스트, 검사, 시연)을 1:1로 정의 | 모호 표현 검출 건수 |

## Ⅵ. 현대 애자일 및 클라우드 환경에서의 기술사적 제언

- 핵심 요약 : 무거운 전통 문서 대신 사용자 스토리와 실행 가능한 명세를 쓰고, 요구 기준선은 ALM 도구에서 관리.

1. 사용자 스토리와 인수 기준의 결합 : 수백 쪽짜리 SRS 대신 'As a [사용자], I want to [행위], So that [가치]' 형식의 사용자 스토리에 Gherkin(Given-When-Then) 인수 기준을 붙여, 명세가 곧 테스트가 되는 살아있는 문서로 관리한다. 이 방식은 BDD(Behavior-Driven Development)와 맞물린다.
2. ALM 도구 기반의 요구 기준선 관리 : 요구사항 변경 이력, 변경통제위원회(CCB, Change Control Board)의 승인 기록, 테스트 케이스 연결을 Jira, Confluence, Polarion 같은 ALM(Application Lifecycle Management) 도구에 모아 두어 감리와 형상 관리 때 추적 근거를 바로 제시할 수 있게 한다.

## Ⅶ. 결론

- 핵심 요약 : SRS는 계약과 검증의 기준이 되는 문서이며, 실행 가능한 살아있는 명세로 진화해야 실효성을 유지.
- 시사점 : 품질 특성을 갖춘 명세를 단일 기준으로 삼되, 변경 추적과 자동 검증을 함께 갖춰야 문서가 현장과 어긋나지 않는다.
