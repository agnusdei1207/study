## 연관 키워드
- REST, 자원, 표현, 무상태, 캐시, 균일 인터페이스, HATEOAS

### Ⅰ. REST의 개요

- 핵심 요약 : REST는 자원과 표현을 중심으로 분산 하이퍼미디어 시스템을 구성하는 아키텍처 스타일.
- 개념 : 클라이언트·서버, 무상태성, 캐시, 균일 인터페이스, 계층화, 선택적 코드 제약을 조합(**REST**, Representational State Transfer).
- 배경 및 필요성 : 웹 규모의 확장성과 독립적인 구성요소 진화가 요구됨.
- 주요 목적 : 느슨한 결합·확장성·재사용 가능한 웹 상호작용 제공.

### Ⅱ. REST 제약조건과 장점

- 핵심 요약 : 제약을 지킬수록 가시성·확장성·캐시성이 높아지나 구현 자유도와 상태 관리 편의는 낮아질 수 있음.

1. Client-Server : 관심사 분리 → 독립 진화.
2. Stateless : 요청마다 필요한 맥락 포함 → 서버 수평 확장 용이.
3. Cache : 응답 캐시 가능성 명시 → 지연·서버 부하 감소.
4. Uniform Interface : 자원 식별·표현·메시지 자기서술·하이퍼미디어 → 결합 완화.
5. Layered System : 중간 계층 허용 → 보안·로드밸런싱 삽입.
6. Code-on-Demand(선택) : 실행 코드 전달 → 클라이언트 기능 확장.

### Ⅲ. REST 요청 흐름과 성숙도 (구조)

- 핵심 요약 : 클라이언트가 자원을 식별하고 표현을 교환하며 HTTP 의미와 링크로 상태 전이를 수행.

```text
클라이언트 → 자원 URI·HTTP 메서드 → 서버
           ← 상태코드·표현·캐시 정책 ←
```

```text
Richardson 성숙도:
Level 0 단일 엔드포인트/RPC → Level 1 자원 → Level 2 HTTP 동사·상태코드
→ Level 3 하이퍼미디어 제어(HATEOAS)
```

### Ⅳ. REST와 RPC 비교

- 핵심 요약 : REST는 자원 표현과 HTTP 의미 활용, RPC는 작업 호출과 명령 의미에 적합.

| 비교 축 | REST | RPC(Remote Procedure Call) |
|---|---|---|
| 모델 | 자원·표현 | 원격 작업·메서드 |
| 인터페이스 | URI·HTTP 동사·상태코드 | 메서드명·인자·결과 |
| 장점 | 캐시·웹 인프라 활용 | 동작 의미 명확, 내부 호출 간결 |
| 주의 | 복합 업무의 자원 모델링 | 결합도·버전·캐시 제약 |

### Ⅴ. REST 적용 한계와 방안

- 핵심 요약 : 부분적 REST는 용어 혼란을 부르고 무상태성은 대화형 작업의 상태 설계를 요구.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 자원·동작 모델 혼합 | API 일관성 저하 | 리소스 명명·메서드 의미 기준 수립 | API 통일성 검토 |
| 장기 작업·다단계 상태 | 단일 요청 응답으로 표현 곤란 | 작업 자원과 상태조회·콜백 설계 | 상태 추적 누락 |
| 민감한 데이터 캐시 | 정보 노출·오래된 응답 | Cache-Control·권한별 캐시 분리 | 캐시 관련 사고 |

### Ⅵ. REST API 설계 제언

- 핵심 요약 : API 담당자는 자원 모델·HTTP 의미·버전 호환·오류 표현을 계약으로 관리.

1. 설계자는 상태코드·멱등성·페이지네이션·오류 스키마를 명세.
2. 보안 담당자는 인증·인가·속도 제한·민감정보 노출을 검토.
3. 운영팀은 계약 테스트와 사용량·오류율 관측을 릴리스 게이트에 연결.

### Ⅶ. 결론

- 핵심 요약 : REST는 HTTP를 단순 전송으로 쓰는 방식이 아니라 제약 기반 자원 지향 아키텍처 스타일.
- 시사점 : 실용 API는 필요한 제약을 명시하고 일관된 계약·캐시·보안 정책을 유지해야 함.
