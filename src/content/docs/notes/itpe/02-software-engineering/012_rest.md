## 연관 키워드

- REST, 자원(리소스), 표현, 무상태성, 캐시 가능성
- 균일 인터페이스, HATEOAS, Richardson 성숙도 모델, SOAP

## Ⅰ. REST의 개요

- 핵심 요약 : REST는 자원과 표현을 중심으로 분산 하이퍼미디어 시스템을 구성하는 아키텍처 스타일.
- 개념 : **자원**을 URI로 식별하고 그 **표현**을 균일한 인터페이스로 교환하도록 정의한 제약의 집합(**REST**, Representational State Transfer), 로이 필딩(Roy Fielding)의 박사 학위 논문(2000년)에서 제안.
- 배경 및 필요성 : 웹 규모의 분산 환경에서 구성요소의 독립적 진화와 수평 확장 요구 증가.
- 주요 목적 : 느슨한 결합과 확장성·캐시 활용을 통한 대규모 분산 시스템 상호운용성 확보.

## Ⅱ. REST의 특징 및 장점

- 핵심 요약 : 제약의 준수 수준이 가시성·확장성·캐시 효율을 높이는 원리로 작동.

1. 클라이언트-서버 분리 : 사용자 인터페이스와 데이터 저장의 관심사 분리 → 독립적 배포·진화.
2. **무상태성** (Statelessness) : 요청마다 처리에 필요한 맥락을 모두 포함 → 서버 세션 부재로 수평 확장·장애 회복 용이.
3. **캐시 가능성** (Cacheability) : 응답에 캐시 여부·기간 명시 → 반복 요청 부하와 지연 감소.
4. **균일 인터페이스** (Uniform Interface) : 자원 식별·표현을 통한 조작·자기서술적 메시지·하이퍼미디어 적용 → 클라이언트·서버의 독립 진화.
5. 계층 시스템과 선택 제약 : 중간 계층(프록시·게이트웨이)의 투명한 삽입 허용, 코드 온 디맨드(Code-on-Demand)는 선택 제약 → 보안·부하분산 계층의 유연한 구성.

## Ⅲ. REST의 구조 (흐름)

- 핵심 요약 : 클라이언트가 자원을 요청하고 서버가 표현과 다음 상태로의 링크를 응답하는 순환 구조.
- **HATEOAS** (Hypermedia as the Engine of Application State) : 응답에 포함된 하이퍼링크가 다음 상태 전이를 안내하는 균일 인터페이스의 하위 제약.
- **Richardson 성숙도 모델** (Richardson Maturity Model) : REST 제약의 반영 수준을 4단계로 구분한 성숙도 기준.

```text
[ 자원 요청·응답 흐름 ]

클라이언트: 자원 URI + HTTP 메서드
   ↓ 요청 전송
서버: 상태코드 + 표현 + 캐시 지시
   ↓ 응답 반환
클라이언트: 링크로 다음 자원 이동
```

```text
[ Richardson 성숙도 모델 ]

Level 0: 단일 엔드포인트 원격 호출
   ↓
Level 1: 자원별 URI 분리
   ↓
Level 2: HTTP 메서드·상태코드 활용
   ↓
Level 3: 하이퍼미디어 제어(HATEOAS)
```

## Ⅳ. REST와 SOAP의 비교

- 핵심 요약 : REST는 제약 기반의 자원 지향 스타일, SOAP는 엄격한 규격의 메시지 프로토콜.
- **SOAP** (Simple Object Access Protocol) : XML 봉투 기반 메시징과 서비스 계약으로 웹 서비스를 구성하는 프로토콜.

| 비교 축 | REST | SOAP |
| --- | --- | --- |
| 성격 | 아키텍처 스타일(제약 집합) | 메시징 프로토콜(표준 규격) |
| 메시지 형식 | JSON·XML 등 표현 자유 | XML 봉투(Envelope) 고정 |
| 인터페이스 정의 | 자원 URI·HTTP 메서드 | 서비스 계약(WSDL, Web Services Description Language)·오퍼레이션 |
| 상태·캐시 | 무상태·캐시 가능성 활용 | 상태 처리 규격 제공·캐시 제약 |
| 강점 | 단순성·웹 인프라(캐시) 활용 | 표준 확장(보안·트랜잭션) 지원 |

## Ⅴ. REST 적용의 한계와 방안

- 핵심 요약 : 부분적 REST 혼용과 무상태·캐시 설계 부담을 자원 모델링 기준과 정책으로 완화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| RPC성 엔드포인트 혼재 | 동사형 URI 난립 → 일관성 저하 | 자원 명명·메서드 의미 가이드 준수 | 설계 기준 위반 건수 |
| 상태 관리 부담 | 세션 상태의 클라이언트 이관 → 설계 복잡 | 토큰 설계·장기 작업의 상태 자원화 | 세션 관련 장애 건수 |
| 캐시 오·남용 | 민감 데이터 노출·구형 응답 제공 | 캐시 정책 수립·권한별 캐시 분리 | 캐시 기반 사고 건수 |

## Ⅵ. REST API 설계에 대한 제언

- 핵심 요약 : 제약 준수를 개인 해석에 두지 않고 조직 표준과 명세·검증 자동화로 관리 필요.

1. 설계 조직은 상태코드·멱등성·오류 형식을 포함한 API 설계 표준 제정.
2. 개발 조직은 명세 문서와 계약 테스트의 자동 대조 체계 구축.
3. 운영 조직은 버전 전환·폐기 공지 절차를 릴리스 게이트에 반영.

## Ⅶ. 결론

- 핵심 요약 : REST는 HTTP 사용 기법이 아니라 제약 준수로 상호운용성을 만드는 자원 지향 아키텍처 스타일.
- 제약의 반영 수준이 시스템 확장성과 독립 진화 능력을 결정하는 요소.
