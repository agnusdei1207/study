---

## 30초 인출

- 본질: **객체지향 프로그래밍(OOP)** 은 현실 세계의 유무형 사물을 데이터(속성)와 이를 처리하는 알고리즘(메서드)을 하나로 결합한 '객체(Object)'로 추상화하고, 객체 간 메시지 교환(Message Passing)을 통해 시스템을 구성하는 소프트웨어 개발 패러다임
- 메커니즘: 도메인 분석 → 클래스 모델링(추상화) → 상태 은닉 및 메서드 공개(캡슐화) → 인터페이스 정의 및 상속/구현(상속성) → 런타임 동적 바인딩을 통한 유연한 행위 실행(다형성)
- 통찰: 무분별한 상속 계층 확장과 맹목적인 Getter/Setter 남발은 캡슐화 파괴와 강한 결합도를 초래하므로 상속보다 합성(Composition)을 우선하고 Tell, Don't Ask 원칙을 적용하여 객체의 자율성을 확보할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **절차지향(POP: Procedure-Oriented Programming)** : 프로그램을 순차적인 함수(Function)와 프로시저의 실행 흐름으로 파악하는 하향식(Top-down) 패러다임
- **객체지향(OOP: Object-Oriented Programming)** : 시스템을 자율적인 협력체로 구성된 객체들의 네트워크로 파악하는 상향식(Bottom-up) 패러다임
- **캡슐화(Encapsulation)** : 객체 내부의 세부 구현 데이터와 로직을 외부에 감추고 정해진 공개 인터페이스만을 제공하는 정보은닉 기법
- **다형성(Polymorphism)** : 동일한 메서드 호출 시 수신 객체의 실제 타입에 따라 각기 다른 로직이 동적으로 바인딩되어 실행되는 특성
- **동적 바인딩(Dynamic Binding)** : 컴파일 시점이 아닌 런타임에 호출될 메서드의 실체 구현 코드가 결정되는 메커니즘

</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 개발 패러다임에서 절차지향 프로그래밍(POP)과 객체지향 프로그래밍(OOP)의 철학적 차이를 비교하고, OOP의 4대 핵심 원리(추상화·캡슐화·상속성·다형성)의 메커니즘과 현대 대규모 시스템에서의 객체지향 설계 지침을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 상태(데이터)와 행위(메서드)를 단일 단위로 묶은 객체(Object)들의 상호작용과 협력을 통해 시스템의 비즈니스 로직을 구현하는 프로그래밍 패러다임 |
| 목적 | 요구사항 변경에 따른 코드 수정 영향 국소화, 재사용성 및 확장성 극대화, 대규모 복합 시스템의 소프트웨어 위기 극복 |

## Ⅱ. 핵심 특징

OOP는 데이터와 프로세스를 분리하던 절차지향의 한계를 극복하고, 객체 스스로 자신의 상태를 책임지는 자율적 구조를 형성.

| 핵심 4대 원리 | 기술적 구현 메커니즘 | 아키텍처 및 공학적 기대 가치 |
|---|---|---|
| **추상화 (Abstraction)** | 복잡한 현실 실체에서 공통적 속성과 행위만을 추출하여 인터페이스/추상 클래스화 | 시스템의 복잡도 제어, 본질적 기능에 대한 인지 집중도 향상 |
| **캡슐화 (Encapsulation)** | 속성과 메서드를 하나의 클래스로 묶고 접근 제어자(`private`)를 통해 상태 직접 접근 차단 | 정보은닉(Information Hiding) 달성, 데이터 무결성 보장 |
| **상속성 (Inheritance)** | 상위(부모) 클래스의 구조와 기능을 하위(자식) 클래스가 물려받아 재사용 및 확장 | 공통 로직의 중복 배제, IS-A 관계 정립을 통한 분류 체계화 |
| **다형성 (Polymorphism)** | 동일한 시그니처의 메서드 호출에 대해 오버라이딩(Overriding)을 통한 동적 다형성 실현 | 클라이언트 변경 없는 기능 확장(OCP), 조건문 분기 코드 제거 |

## Ⅲ. 체계·프로세스

객체지향 시스템의 런타임 메시지 협력 체계 및 동적 바인딩 구조.

```text
+---------------------------------------------------------------------------------------------------------+
|                                    OOP 객체 간 메시지 패싱 및 다형성 바인딩 체계                        |
+---------------------------------------------------------------------------------------------------------+
                                                                                                           
  [클라이언트 객체] ──────────────── (1) 메시지 전송: pay(amount) ──────────────────┐                      
   (OrderService)                                                                   │                      
                                                                                    ▼                      
                                                                    +───────────────────────────────+      
                                                                    |     <<interface>> Payment     |      
                                                                    |     + pay(amount): void       |      
                                                                    +───────────────────────────────+      
                                                                                    ▲                      
                                               ┌────────────────────────────────────┴────────────────┐     
                                               │ 동적 바인딩 (Dynamic Binding at Runtime)           │     
                                               ▼                                                     ▼     
                                  +─────────────────────────+                           +─────────────────+
                                  |    CreditCardPayment    |                           |   KakaoPayment  |
                                  | + pay(amount): void     |                           | + pay(amount)   |
                                  +─────────────────────────+                           +─────────────────+
                                               │                                                     │     
                                               ▼                                                     ▼     
                                    (신용카드 PG사 API 연동)                               (간편결제 인증 연동)   
```

- **객체 협력 설계 4단계 프로세스**:
  1. **책임 및 도메인 개체 식별** : 비즈니스 유스케이스를 분석하여 역할을 수행할 객체와 각 객체의 책임(Responsibility) 정의.
  2. **협력 시나리오 도출** : 객체 간 주고받을 메시지(Message) 목록을 정의하고 상호작용 다이어그램(시퀀스 다이어그램) 구성.
  3. **캡슐화 및 인터페이스 추출** : 내부 자료구조(변수)를 은닉하고, 외부 협력을 위한 공개 메서드 및 추상 계약(Interface) 도출.
  4. **다형성 적용 및 리팩토링** : 조건 분기문(`switch-case`)을 다형적 메서드 호출 구조로 치환하여 확장 용이성 확보.

## Ⅳ. 종류·비교

#### 절차지향(POP) vs 객체지향(OOP) 패러다임 비교

| 비교 항목 | 절차지향 프로그래밍 (POP) | 객체지향 프로그래밍 (OOP) |
|---|---|---|
| **중심 설계 단위** | 함수, 서브루틴, 프로시저 (동사 중심) | 클래스, 자율적 객체 (명사 및 역할 중심) |
| **분석/설계 방식** | 하향식 기능 분해 (Top-down Functional Decomposition) | 상향식 도메인 모델링 및 객체 협력 (Bottom-up Modeling) |
| **데이터와 로직** | 데이터와 처리 함수가 상호 분리됨 | 데이터와 처리 로직이 단일 객체 내에 캡슐화됨 |
| **데이터 접근성** | 전역 변수 공유로 인한 사이드 이펙트 발생 위험 | 접근 제어자(`private`)를 통한 철저한 은닉 및 보호 |
| **변경 영향도** | 자료구조 변경 시 전체 함수 수정 파급 (High Ripple Effect) | 객체 내부 변경 시 외부 인터페이스가 불변이면 영향 제로 |
| **실행 성능** | 단순 함수 호출 및 직관적 메모리 접근으로 상대적 우수 | 객체 생성, 힙 할당, 가상 함수 테이블(V-Table) 조회 비용 발생 |
| **대표 언어** | C, Pascal, Fortran | Java, C++, C#, Kotlin, Swift |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 깊은 상속 계층 구축으로 인한 하위 클래스와 상위 클래스 간의 강결합 및 유연성 저하 | 상속(Inheritance) 대신 컴포지션(Composition)을 활용하여 런타임에 행위를 동적으로 조립 |
| 무분별한 Getter와 Setter 제공으로 인한 캡슐화 무력화 및 빈약한 도메인 모델(Anemic Domain Model)화 | 상태 조회를 지양하고 객체에게 행위 수행을 명령하는 "Tell, Don't Ask" 원칙 철저 준수 |
| 다형성 및 인터페이스 추상화 계층 증가로 인한 소스코드 탐색 및 정적 분석 난이도 상승 | 일관된 아키텍처 명명 규칙 준수 및 유닛 테스트 코드를 통한 객체 간 협력 명세화 |

## Ⅵ. 제언

현대 소프트웨어 개발에서는 객체지향의 캡슐화와 도메인 모델링 장점을 취하면서도, 동시성 처리와 데이터 가공에는 함수형 프로그래밍(FP)의 불변성(Immutability)을 융합하는 멀티패러다임 접근이 필수적임.

```text
[거시적 도메인 설계] ──> [객체지향(OOP) 모델링] ──> [내부 로직 가공] ──> [함수형(FP) 스트림 처리]
  (전체 시스템 구조)          (엔티티 캡슐화 & 다형성)        (상태 변경 배제)        (순수 함수 & 람다 연산)
```

| 설계 영역 | 핵심 권장 원칙 | 실무 구현 가이드 |
|---|---|---|
| **도메인 엔티티** | 풍부한 도메인 모델(Rich Domain Model) | 비즈니스 로직을 엔티티 내부에 캡슐화, 불변식(Invariant) 검증 |
| **모듈 간 통신** | 디미터 법칙 (Law of Demeter) | `a.getB().getC().doAction()` 금지, 최소한의 직접 의존 관계 유지 |
| **데이터 변환** | Java Stream API, Kotlin 람다 연계 | 순수 함수(Pure Function) 기반 데이터 파이프라인으로 동시성 안전성 확보 |
