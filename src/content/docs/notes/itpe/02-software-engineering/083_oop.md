## 연관 키워드

- OOP(Object-Oriented Programming, 객체지향 프로그래밍), POP(Procedure-Oriented Programming, 절차지향 프로그래밍)
- 추상화(Abstraction), 캡슐화(Encapsulation), 상속성(Inheritance), 다형성(Polymorphism), Fragile Base Class, Composition over Inheritance, 액터 모델(Actor Model)

## Ⅰ. OOP와 POP의 개요

- 핵심 요약 : 절차 실행 흐름 중심의 POP과 자율적 객체 상호작용 중심의 OOP의 패러다임 대비.
- 개념
  - 절차지향 프로그래밍(POP, Procedure-Oriented Programming) : 프로그램을 데이터와 이를 순차적으로 조작하는 함수(프로시저)의 실행 흐름으로 파악하는 프로그래밍 패러다임(C, Pascal).
  - 객체지향 프로그래밍(OOP, Object-Oriented Programming) : 프로그램을 데이터(속성)와 이를 처리하는 행위(메서드)를 가진 독립적인 객체(Object)들의 상호작용(메시지 교환)으로 모델링하는 패러다임(Java, C++, Python).
- 배경 및 필요성 : 컴퓨터 하드웨어 발전에 따른 소프트웨어 규모의 기하급수적 확대, 절차지향의 전역 데이터 공유에 따른 사이드 이펙트와 코드 스파게티화 방지 필요.
- 주요 목적 : 데이터와 행위의 응집을 통한 재사용성·확장성·유지보수성 확보.

## Ⅱ. OOP의 특징

- 핵심 요약 : 추상화, 캡슐화, 상속성, 다형성의 OOP 4대 핵심 특징.

1. 추상화(Abstraction) : 복잡한 실세계 사물에서 공통적이고 핵심적인 본질만의 추출 및 클래스 정의.
2. 캡슐화(Encapsulation) : 데이터와 행위의 하나로 묶음 및 외부로부터 세부 구현 은닉을 통한 무결성 보호.
3. 상속성(Inheritance) : 기존 상위 클래스의 속성·기능 재사용 및 확장을 통한 중복 코드 제거.
4. 다형성(Polymorphism) : 동일한 메서드 호출 메시지에 대한 객체별 고유 응답(오버로딩, 오버라이딩).
5. 메시지 교환 협력 : 객체 간 공개 인터페이스를 통한 통신과 내부 상태의 자율적 보호.

## Ⅲ. OOP와 POP의 구조 (흐름)

- 핵심 요약 : 전역 데이터와 함수의 분리 구조(POP)와 상태 은닉 객체 간 메시징 구조(OOP)의 대비.
- 두 패러다임의 구조적 차이.

```text
[ 절차지향 (POP) : 함수 중심 순차 흐름 ]
[ 전역 데이터 풀 (Global Data) ]
   │        │        │
   ▼        ▼        ▼
[ 함수 A ] -> [ 함수 B ] -> [ 함수 C ]
 - 데이터/함수 분리, 전역 상태 오염 가능

[ 객체지향 (OOP) : 객체 간 메시징 ]
[ 객체 A ]
 - 상태 (Private) / 메서드 (Public)
   │  메시지 전송
   ▼
[ 객체 B ]
 - 상태 (Private) / 메서드 (Public)
 - 스스로 상태를 보호, 인터페이스로만 협력
```

## Ⅳ. POP와 OOP의 비교

- 핵심 요약 : 관점, 데이터 처리, 재사용성, 개발 속도, 자원 효율의 6개 축 비교.

| 비교 항목 | 절차지향 프로그래밍 (POP) | 객체지향 프로그래밍 (OOP) |
|---|---|---|
| 프로그램의 관점 | 실행 순서와 절차(Algorithm) 중심 | 책임과 역할을 가진 자율적 객체(Object) 중심 |
| 데이터 처리 방식 | 데이터와 함수의 분리, 전역 변수 다수 활용 | 데이터와 메서드의 캡슐화를 통한 객체 내부 응집 |
| 재사용성 및 확장성 | 함수 재사용은 가능하나 데이터 구조 변경 시 취약 | 상속, 합성, 다형성을 통한 신규 기능 확장 용이 |
| 개발 속도 및 난이도 | 초기 코드 작성의 직관성 및 신속성 | 클래스·관계 설계에 따른 초기 시간·비용 소요 |
| 하드웨어 자원 효율 | 매우 빠른 실행 속도, 적은 메모리 소비 | 객체 생성, 가상 함수 테이블(V-Table), 메모리 오버헤드 |
| 대표 언어 | C, Fortran, Cobol | Java, C++, C#, Kotlin, Swift |

## Ⅴ. OOP의 장점과 한계

- 핵심 요약 : 재사용성·무결성·모델링 직관성의 이점, 깊은 상속·가변 상태·GC(Garbage Collection) 압박의 한계.
- 장점

  1. 상속, 합성, 다형성에 기반한 높은 재사용성과 확장성.
  2. 캡슐화를 통한 데이터 무결성 보호 및 사이드 이펙트 최소화.
  3. 실세계 도메인 모델링의 직관성과 유지보수성 향상.
- 한계점 1 : 깊은 상속 계층에 따른 취약한 기반 클래스 문제(Fragile Base Class)
  - 한계점 : 부모 클래스의 사소한 구현 변경이 다수 자식 클래스의 예측 불가능한 동작 오류를 야기하여 유지보수성 붕괴.
  - 해결 방안 : '상속보다는 조합(Composition over Inheritance)' 원칙 준수, 상속 계층 깊이의 얕은 제한 및 인터페이스 기반 다형성 구현.

```text
[ 상속(Inheritance) ]                [ 조합(Composition) ]
 부모 클래스 ◀── 상속 ── 자식 클래스     객체 A ── 보유·위임 ── 객체 B
 (강결합, 취약 기반 클래스 위험)         (느슨한 결합, 교체 용이)
```

- 한계점 2 : 데이터와 로직의 강결합으로 인한 대규모 동시성 처리 한계
  - 한계점 : 객체 내부 상태의 가변성(Mutable State)으로 인한 멀티스레드 환경 레이스 컨디션 및 데드락 방지용 락(Lock) 경합 오버헤드 심화.
  - 해결 방안 : 불변 객체(Immutable Object) 패턴 적용, 함수형 프로그래밍(FP, Functional Programming) 패러다임 결합 및 Akka 등 액터 모델(Actor Model) 기반 상태 격리.
- 한계점 3 : 객체 그래프 참조에 따른 메모리 단편화 및 GC(Garbage Collection) 압박
  - 한계점 : 다수 소형 객체 생성과 포인터 역참조로 인한 CPU(Central Processing Unit) 캐시 로컬리티 저하 및 JVM(Java Virtual Machine) GC 정지 시간(STW, Stop-The-World) 증가.
  - 해결 방안 : 데이터 지향 설계(Data-Oriented Design) 도입, 객체 풀링(Object Pooling) 및 원시 타입 배열 기반 평탄화 구조(Struct of Arrays) 활용.

## Ⅵ. 현대 소프트웨어 아키텍처 관점의 기술사적 제언

- 핵심 요약 : 객체지향·함수형 융합 아키텍처와 책임 주도 설계의 병행.
- 객체지향과 함수형 프로그래밍(FP)의 융합 : 대규모 동시성·분산 환경 대응을 위해 객체지향의 캡슐화된 도메인 모델 위에 불변성(Immutability)과 순수 함수(Pure Function)를 지원하는 함수형 패러다임(Java Streams, Kotlin Coroutines)을 결합한 하이브리드 아키텍처 권장.
- 맹목적 상속 지양과 책임 주도 설계(RDD, Responsibility-Driven Design) : 단순 코드 재사용 목적의 깊은 상속 계층이 초래하는 클래스 간 강결합 방지, 객체에 명확한 역할과 책임을 부여하는 설계 준수.

## Ⅶ. 결론

- 핵심 요약 : OOP는 규모 확대에 대응하는 검증된 패러다임이나 동시성·성능 영역의 보완 설계 필요.
- 요약 : 데이터와 행위의 응집, 상태 은닉, 다형적 협력으로 절차지향의 전역 상태 문제를 해소하는 모델링 체계.
- 시사점 : 조합 우선 원칙, 불변성 도입, 함수형 융합이 현대적 객체지향 설계 성숙도의 핵심 지표.
