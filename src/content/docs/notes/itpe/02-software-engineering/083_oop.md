## 연관 키워드

- OOP(Object-Oriented Programming, 객체지향 프로그래밍), POP(Procedure-Oriented Programming, 절차지향 프로그래밍)
- 추상화(Abstraction), 캡슐화(Encapsulation), 상속성(Inheritance), 다형성(Polymorphism), 취약한 기반 클래스(Fragile Base Class), 조합 우선 원칙(Composition over Inheritance), 액터 모델(Actor Model)

## Ⅰ. OOP와 POP의 개요

- 핵심 요약 : 실행 절차 중심의 POP과 자율적 객체 간 상호작용 중심의 OOP를 대비하는 두 가지 프로그래밍 패러다임.
- 개념
  - **절차지향 프로그래밍** (POP, Procedure-Oriented Programming) : 데이터와 이를 순서대로 처리하는 함수(프로시저)의 실행 흐름으로 프로그램을 파악하는 패러다임 (C, Pascal 등).
  - **객체지향 프로그래밍** (OOP, Object-Oriented Programming) : 데이터(속성)와 처리 행위(메서드)를 함께 가진 객체들이 메시지를 주고받는 방식으로 프로그램을 모델링하는 패러다임 (Java, C++ 등).
- 배경 및 필요성 : 하드웨어 성능 향상으로 소프트웨어 규모가 커지면서, 절차지향의 전역 데이터 공유가 사이드 이펙트(Side Effect)와 코드 복잡화를 낳아 이를 억제할 구조가 필요해짐.
- 주요 목적 : 데이터와 행위를 응집해 재사용성, 확장성, 유지보수성 확보.

## Ⅱ. OOP의 특징 및 장점

- 핵심 요약 : 추상화, 캡슐화, 상속성, 다형성의 네 가지 특징이 모듈 격리와 재사용이라는 장점으로 이어지는 구조.

1. **추상화** (Abstraction) : 실세계 사물에서 공통된 본질만 추출해 클래스로 정의 → 불필요한 세부사항을 감춰 설계 이해도 향상.
2. **캡슐화** (Encapsulation) : 데이터와 행위를 객체 안에 묶고 내부 구현을 외부에서 가림 → 상태 무결성 보호와 변경 영향 범위 축소.
3. **상속성** (Inheritance) : 상위 클래스의 속성과 기능을 하위 클래스가 물려받아 확장 → 중복 코드 제거.
4. **다형성** (Polymorphism) : 같은 메서드 호출에 객체마다 고유하게 응답(오버로딩, 오버라이딩) → 호출부 수정 없이 기능 교체.
5. 메시지 교환 협력 : 객체가 공개 인터페이스로만 통신 → 내부 상태가 외부로 번지지 않는 자율적 협력.

## Ⅲ. OOP와 POP의 구조 (흐름)

- 핵심 요약 : 전역 데이터를 함수가 공유하는 POP 구조와, 객체가 상태를 숨기고 메시지로만 협력하는 OOP 구조의 대비.

```text
[ POP : 함수 중심 순차 흐름 ]

[ 전역 데이터 ] ← 모든 함수가 직접 접근
   ↓
[ 함수 A ]
   ↓
[ 함수 B ]
   ↓
[ 함수 C ]
```

```text
[ OOP : 객체 간 메시지 교환 ]

[ 객체 A ] 상태는 private으로 은닉
   ↓ 메시지 (메서드 호출)
[ 객체 B ] 상태는 private으로 은닉
   ↓ 메시지 (메서드 호출)
[ 객체 C ] 상태는 private으로 은닉
```

- POP에서는 데이터 변경이 여러 함수로 퍼지고, OOP에서는 메시지 경계에서 변경이 멈춘다.

## Ⅳ. POP와 OOP의 비교

- 핵심 요약 : 관점, 데이터 처리, 재사용성, 개발 속도, 자원 효율의 축에서 실행 효율과 설계 유연성이 상충하는 구조.
- 선택 기준 : 실행 효율과 단순성이 우선이면 POP, 도메인 복잡도와 변경 빈도가 높으면 OOP가 적합.

| 비교 항목 | 절차지향 프로그래밍 (POP) | 객체지향 프로그래밍 (OOP) |
| --- | --- | --- |
| 프로그램의 관점 | 실행 순서와 절차 중심 | 책임과 역할을 가진 자율적 객체 중심 |
| 데이터 처리 방식 | 데이터와 함수의 분리, 전역 변수 다수 활용 | 데이터와 메서드의 캡슐화로 객체 내부 응집 |
| 재사용성 및 확장성 | 함수 재사용은 가능하나 데이터 구조 변경에 취약 | 상속, 조합, 다형성으로 신규 기능 확장 용이 |
| 개발 속도 및 난이도 | 초기 코드 작성이 직관적이고 빠름 | 클래스와 관계 설계에 초기 시간과 비용 소요 |
| 자원 효율 | 실행 오버헤드와 메모리 소비가 작음 | 객체 생성과 가상 함수 테이블(V-Table) 등 부가 비용 발생 |
| 대표 언어 | C, Fortran, COBOL | Java, C++, C#, Kotlin, Swift |

## Ⅴ. OOP의 장점과 한계

- 핵심 요약 : 재사용성과 무결성, 모델링 직관성의 이점 아래, 깊은 상속과 가변 상태, 객체 과다 생성의 한계가 존재.
- 장점 : 상속·조합·다형성에 따른 재사용성, 캡슐화에 따른 데이터 무결성 보호, 실세계 도메인 모델링의 직관성.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **취약한 기반 클래스** (Fragile Base Class) | 깊은 상속 계층에서 부모의 사소한 변경이 자식 클래스의 예측 불가 동작 오류로 번짐 | **조합 우선 원칙** (Composition over Inheritance) 적용, 상속 깊이 제한과 인터페이스 기반 다형성 구현 | 상속 계층 깊이, 상위 클래스 변경 후 회귀 결함 수 |
| 가변 상태와 동시성 | 공유되는 객체 상태의 변경으로 레이스 컨디션과 락 경합 발생 | 불변 객체(Immutable Object) 패턴, 함수형 프로그래밍(FP, Functional Programming) 결합, **액터 모델** (Actor Model) 기반 상태 격리 | 동시성 관련 결함 건수, 락 대기 시간 |
| 객체 과다 생성과 GC 부담 | 소형 객체의 대량 생성과 참조 추적으로 캐시 효율이 떨어지고 GC(Garbage Collection) 정지 시간 증가 | 객체 풀링(Object Pooling), 데이터 지향 설계(Data-Oriented Design) 도입 | GC 정지 시간, 캐시 미스율 |

## Ⅵ. 현대 소프트웨어 아키텍처를 위한 기술사적 제언

- 핵심 요약 : 객체지향과 함수형 설계를 결합한 하이브리드 구조와 책임 주도 설계를 병행해 상속 의존을 줄이는 방향.

1. 대규모 동시성 영역에서는 캡슐화된 도메인 모델 위에 불변 객체와 함수형 연산(Java Streams, Kotlin Coroutines 등)을 결합하는 하이브리드 설계를 채택하는 것이 바람직하다.
2. 설계 조직은 단순 재사용만을 목적으로 한 깊은 상속 계층을 피하고, **책임 주도 설계** (RDD, Responsibility-Driven Design)에 따라 객체마다 명확한 역할과 책임을 부여하는 원칙을 기본으로 삼아야 한다.

## Ⅶ. 결론

- 핵심 요약 : OOP는 규모 확대에 검증된 패러다임이나, 동시성과 성능 영역에는 보완 설계가 필요함.
- 시사점 : 조합 우선, 불변성 도입, 함수형 요소의 융합이 현대 객체지향 설계 성숙도를 가르는 판단 기준.
