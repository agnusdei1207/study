## Ⅰ. OOP와 POP의 개요

- **개념** :
  - **절차지향 프로그래밍 (POP, Procedure-Oriented Programming)** : 프로그램을 데이터와 이를 순차적으로 조작하는 함수(프로시저)의 실행 흐름으로 파악하는 프로그래밍 패러다임 (C, Pascal).
  - **객체지향 프로그래밍 (OOP, Object-Oriented Programming)** : 프로그램을 데이터(속성)와 이를 처리하는 행위(메서드)를 가진 독립적인 '객체(Object)'들의 상호작용(메시지 교환)으로 모델링하는 패러다임 (Java, C++, Python).
- **배경 및 필요성** : 컴퓨터 하드웨어의 발전과 함께 소프트웨어의 규모가 기하급수적으로 거대해지면서, 절차지향의 전역 데이터 공유에 따른 사이드 이펙트와 코드 스파게티화를 방지하기 위해 객체지향 발전.

## Ⅱ. POP와 OOP의 핵심 구조적 차이

```text
   [ 절차지향 (POP) ] ───────────────── 함수 중심의 순차적 흐름
    [ 전역 데이터 풀 (Global Data) ]
          │          │          │
          ▼          ▼          ▼
     [ 함수 A() ] ──> [ 함수 B() ] ──> [ 함수 C() ]
    (데이터와 함수가 분리되어 누구나 전역 상태를 오염시킬 수 있음)

   [ 객체지향 (OOP) ] ───────────────── 데이터와 행위를 묶은 객체 간 메시징
    ┌──────────────────┐               ┌──────────────────┐
    │  [ 객체 A ]      │   메시지 전송  │  [ 객체 B ]      │
    │  - 상태 (Private)│ ────────────> │  - 상태 (Private)│
    │  - 메서드 (Public)│               │  - 메서드 (Public)│
    └──────────────────┘               └──────────────────┘
    (각 객체는 자신의 상태를 스스로 보호하며 오직 인터페이스로만 협력)
```

- **OOP의 4대 핵심 특징** :
  - **추상화 (Abstraction)** : 복잡한 실세계 사물에서 공통적이고 핵심적인 본질만을 추출하여 클래스로 정의.
  - **캡슐화 (Encapsulation)** : 데이터와 행위를 하나로 묶고 외부로부터 세부 구현을 은닉하여 무결성 보호.
  - **상속성 (Inheritance)** : 기존 상위 클래스의 속성과 기능을 재사용하고 확장하여 중복 코드 제거.
  - **다형성 (Polymorphism)** : 동일한 메서드 호출 메시지에 대해 각 객체가 서로 다른 고유한 방식으로 응답 (오버로딩, 오버라이딩).

## Ⅲ. POP와 OOP의 비교 분석

| 비교 항목 | 절차지향 프로그래밍 (POP) | 객체지향 프로그래밍 (OOP) |
|---|---|---|
| 프로그램의 관점 | 실행 순서와 절차(Algorithm) 중심 | 책임과 역할을 가진 자율적 객체(Object) 중심 |
| 데이터 처리 방식 | 데이터와 함수가 분리, 전역 변수 다수 활용 | 데이터와 메서드가 캡슐화되어 객체 내부에 응집 |
| 재사용성 및 확장성 | 함수 재사용은 가능하나 데이터 구조 변경 시 취약 | 상속, 합성, 다형성을 통해 신규 기능 확장 용이 |
| 개발 속도 및 난이도 | 초기 코드 작성이 직관적이고 빠름 | 클래스 및 관계 설계에 초기 시간과 비용 소요 |
| 하드웨어 자원 효율 | 실행 속도가 매우 빠르고 메모리 소비 적음 | 객체 생성, 가상 함수 테이블(V-Table), 메모리 오버헤드 |
| 대표 언어 | C, Fortran, Cobol | Java, C++, C#, Kotlin, Swift |

## Ⅳ. OOP(객체지향 프로그래밍)의 주요 한계점 및 해결 방안

- **깊은 상속 계층에 따른 취약한 기반 클래스 문제(Fragile Base Class)** :
  - **한계점** : 부모 클래스의 사소한 구현 변경이 수많은 자식 클래스의 예측 불가능한 동작 오류를 야기하여 유지보수성 붕괴.
  - **해결 방안** : '상속보다는 조합(Composition over Inheritance)' 원칙 준수, 상속 계층의 깊이를 얕게 제한하고 인터페이스 기반 다형성 구현.
- **데이터와 로직의 강결합으로 인한 대규모 동시성 처리 한계** :
  - **한계점** : 객체 내부 상태의 가변성(Mutable State)으로 인해 멀티스레드 환경에서 레이스 컨디션 및 데드락 방지를 위한 락(Lock) 경합 오버헤드 심화.
  - **해결 방안** : 불변 객체(Immutable Object) 패턴 적용, 함수형 프로그래밍(FP) 패러다임 결합 및 Akka 등 액터 모델(Actor Model) 기반 상태 격리.
- **객체 그래프 참조에 따른 메모리 단편화 및 GC(Garbage Collection) 압박** :
  - **한계점** : 수많은 소형 객체 생성과 포인터 역참조로 인해 CPU 캐시 로컬리티가 저하되고 JVM GC 정지 시간(STW) 증가.
  - **해결 방안** : 데이터 지향 설계(Data-Oriented Design) 도입, 객체 풀링(Object Pooling) 및 원시 타입 배열 기반 평탄화 구조(Struct of Arrays) 활용.

## Ⅴ. 현대 소프트웨어 아키텍처 관점의 기술사적 제언

- **객체지향과 함수형 프로그래밍(FP)의 융합** : 현대 엔지니어링에서는 대규모 동시성과 분산 환경을 처리하기 위해 객체지향의 캡슐화된 도메인 모델 위에 불변성(Immutability)과 순수 함수(Pure Function)를 지원하는 함수형 패러다임(Java Streams, Kotlin Coroutines)을 결합한 하이브리드 아키텍처 권장.
- **맹목적 상속 지양과 책임 주도 설계(RDD)** : 단순히 코드를 재사용하기 위한 깊은 상속 계층은 클래스 간 강결합을 유발하므로, 객체에게 명확한 역할과 책임을 부여하는 책임 주도 설계(Responsibility-Driven Design)를 준수해야 함.
