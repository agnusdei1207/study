## 한 줄 본질
- OS마다 GUI API가 달라 각각 따로 코딩해야 했던 플랫폼 종속성 병목 → 자바 추상 인터페이스를 하부 OS 네이티브 GUI 컴포넌트와 1:1 매핑(Peer)하여 윈도우를 띄우는 초기 자바 GUI 프레임워크 / OS 간 공통 기능만 제공하여 UI 일관성 유지 불가

## 핵심 용어
- 중량 컴포넌트(Heavyweight Component): 화면 렌더링과 이벤트 처리를 운영체제 자체 윈도우 시스템의 네이티브 리소스(피어)에 직접 의존하는 컴포넌트
- 최소 공통분모 원칙(Lowest Common Denominator): 윈도우, 맥, 유닉스 등 모든 대상 OS가 공통으로 지원하는 UI 기능만 제공할 수밖에 없어 컴포넌트 기능이 제약되는 현상

## 핵심 통찰
- AWT는 "Write Once, Run Anywhere(한 번 작성해 어디서나 실행)"라는 자바의 이상을 구현하려 했으나, OS 네이티브 윈도우에 종속된 피어 구조 때문에 오히려 "Write Once, Debug Everywhere(한 번 작성해 모든 OS에서 디버깅)"라는 오명을 얻음
- AWT 1.1에서 도입된 이벤트 위임 모델(Delegation Event Model: Event Source, Event Object, Event Listener)은 현대 GUI 및 안드로이드, 웹 자바스크립트 이벤트 처리 패턴의 표준 기틀이 됨
- AWT의 네이티브 피어 한계를 극복하기 위해 화면 픽셀을 순수 자바 코드로 직접 그리는 경량(Lightweight) 프레임워크인 Swing이 등장하게 됨

## 이웃 토픽과 구분
- AWT vs Swing: AWT = OS 네이티브 창 리소스에 의존하는 중량(Heavyweight) 컴포넌트 / Swing = 버튼과 텍스트 필드를 자바 Graphics 2D로 직접 캔버스에 그리는 경량(Lightweight) 컴포넌트

## 문제·원인·대책
- 적용 상황: 제조 공장 현장 제어용 구형 자바 클라이언트 유지보수
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 윈도우에서는 정상 동작하던 제어 UI가 리눅스 장비에서 레이아웃이 깨지고 버튼이 겹침 | AWT가 OS별 네이티브 폰트 및 버튼 크기를 반영하여 크로스플랫폼 일관성 붕괴 | 절대 좌표 배치(`null`)를 지양하고 유연한 레이아웃 관리자(GridBagLayout) 적용 | OS 해상도 및 폰트 차이에 따른 레이아웃 왜곡 방지 |
| 반투명 배경이나 둥근 모서리 등 현대적 UI 요소를 구현할 수 없어 사용자 편의성 저하 | OS 네이티브 사각 윈도우 영역에 갇힌 중량 컴포넌트 구조의 한계 | 순수 자바 렌더링 Swing/JavaFX 컴포넌트 또는 일렉트론(Electron)/웹 UI로 단계적 전환 | 풍부한 UI/UX 표현력 확보 및 클라이언트 현대화 |
