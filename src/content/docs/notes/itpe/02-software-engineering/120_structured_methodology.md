## 핵심 용어
- DFD(Data Flow Diagram): 시스템 내에서 데이터가 어디서 들어와 어떻게 변환되고 어디로 저장·출력되는지를 버블(Bubble)과 화살표로 나타낸 도표
- 구조도(Structure Chart): DFD의 변환 분석(Transform Analysis) 또는 트랜잭션 분석(Transaction Analysis)을 거쳐 시스템의 모듈 호출 계층 구조를 나무 형태로 나타낸 설계 도식

## 핵심 통찰
- 구조적 방법론은 현대 웹 서비스의 전체 방법론으로는 쓰이지 않지만, ETL 파이프라인, 실시간 스트리밍(Kafka Streams), 배치 처리 시스템 등 "데이터가 흘러가며 변환되는 도메인"에서는 여전히 가장 강력한 분석 사고 체계임
- DFD를 구조도로 변환할 때 입력-변환-출력 흐름의 중심 변환(Central Transform)을 식별하여 모듈을 도출하는 기법은 현대 마이크로서비스의 이벤트 처리 파이프라인 분할 원리와 본질적으로 일치함
- 구조적 방법론의 가장 큰 한계는 데이터 구조가 변경되면 그 데이터를 참조하는 수백 개의 프로세스 함수를 모두 일일이 수정해야 한다는 점이며, 이를 극복하기 위해 객체지향의 캡슐화가 등장함

## 이웃 토픽과 구분
- 구조적 방법론 vs 정보공학 방법론: 구조적 = 기능(Process) 흐름 중심 모델링 / 정보공학 = 기업의 데이터 구조(Data/ERD)를 핵심 자산으로 먼저 설계한 뒤 프로세스를 매핑

## 내 의견
- [객체지향 만능주의에 따른 데이터 흐름 분석 소홀 경계] 데이터 엔지니어링이나 대용량 로그 파이프라인을 설계할 때 억지 객체 모델링을 적용하여 복잡성만 가중시키는 사례 빈번 → 나라면: 비즈니스 도메인 로직은 객체지향(DDD)으로 설계하되, 대규모 데이터 변환 및 분석 파이프라인 구축에는 구조적 방법론의 DFD 개념과 함수형 프로그래밍의 파이프-필터 아키텍처를 융합하여 데이터 흐름의 투명성을 극대화
