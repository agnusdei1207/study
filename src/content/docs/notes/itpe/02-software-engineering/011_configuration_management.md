## 연관 키워드

- 형상관리(Configuration Management), 형상 항목(CI, Configuration Item), 베이스라인(Baseline)
- 형상통제위원회(CCB, Change Control Board), 트렁크 기반 개발(Trunk-Based Development), GitOps, IaC(Infrastructure as Code)

## Ⅰ. 형상관리의 개요

- 핵심 요약 : 생명주기 전반에 걸친 산출물 변경을 식별·통제·기록·감사하는 관리 프로세스.
- 개념 : 요구사항, 설계서, 소스코드, 빌드 스크립트 등 모든 **형상 항목** (CI, Configuration Item)의 변경을 체계적으로 식별·통제·기록·감사하는 **형상관리** (Configuration Management).
- 배경 및 필요성 : 다수 개발자의 코드 충돌을 막고, 무분별한 요구사항 변경으로 프로젝트가 실패하는 것을 예방하며, 과거 특정 시점의 산출물을 복원할 수 있어야 하는 요구.
- 표준 근거 : **IEEE 828** (시스템·소프트웨어 형상관리 계획 표준)과 CMMI(Capability Maturity Model Integration)의 형상관리(CM, Configuration Management) 프로세스 영역을 기준으로 함.

## Ⅱ. 형상관리의 특징 및 장점

- 핵심 요약 : 베이스라인 중심의 변경 통제와 변경 추적성, 감사가 결합된 관리 체계.

1. 요구사항부터 릴리스 산출물까지 형상 항목을 전수 관리 대상으로 지정 → 누락 없는 추적 기반 확보.
2. **베이스라인** (Baseline, 승인된 산출물 묶음을 변경 기준점으로 고정한 것) 확정 → 변경의 기준점과 복원 지점 확보.
3. **형상통제위원회** (CCB, Change Control Board)가 주관하는 공식 변경 통제 → 승인되지 않은 변경 차단.
4. 기능·물리적 형상감사로 산출물과 베이스라인의 일치성 검증 → 인증과 감사 대응력 확보.
5. 변경 이력의 상태 보고와 이해관계자 추적성 확보 → 변경 책임 소재를 명확히 함.

## Ⅲ. 형상관리의 구조 (흐름)

- 핵심 요약 : 식별, 통제, 감사, 기록의 4대 활동이 순환하는 구조.

```text
[ 형상관리 4대 활동 순환 ]

[ 형상 식별 ] 항목 선정, 베이스라인 확정
      ↓
[ 형상 통제 ] 변경 요청 접수, CCB 심의
      ↓
[ 형상 감사 ] 베이스라인과 산출물 대조
      ↓
[ 형상 기록 ] 상태 보고, 이력 추적
      ↓
다음 순환
```

- 형상 식별 : 관리 대상 산출물의 정의와 버전·명명 규칙 부여.
- 형상 통제 : 변경요청서(CR, Change Request) 접수 후 CCB 심의와 승인을 거쳐 변경 수행.
- 형상 감사 : 기능적 형상감사(FCA, Functional Configuration Audit)와 물리적 형상감사(PCA, Physical Configuration Audit)로 베이스라인과 실제 산출물의 일치 검증.
- 형상 상태 보고 : 변경 이력과 현재 형상 상태를 이해관계자에게 투명하게 공유.

```text
[ 베이스라인 계층 진행 ]

기능 베이스라인   (요구사항 분석 완료)
      ↓
분배 베이스라인   (기본·논리 설계 완료)
      ↓
설계 베이스라인   (상세 설계 완료)
      ↓
제품 베이스라인   (통합·검증 완료)
```

## Ⅳ. 베이스라인 종류별 비교

- 핵심 요약 : 수립 시점과 포함 형상 항목에 따라 구분되는 4계층 베이스라인 체계.

| 베이스라인 종류 | 수립 시점 | 포함되는 주요 형상 항목 |
| --- | --- | --- |
| 기능 베이스라인(Functional) | 요구사항 분석 완료 시점 | 시스템 요구사항 명세서(SRS, Software Requirements Specification), 제안요청서(RFP, Request for Proposal), 업무 정의서 |
| 분배 베이스라인(Allocated) | 기본·논리 설계 완료 시점 | 시스템 아키텍처 설계서, 서브시스템 기능 배분 명세서 |
| 설계 베이스라인(Design) | 상세 설계 완료 시점 | 클래스 다이어그램, DB(Database) ERD(Entity-Relationship Diagram), 인터페이스 연동 정의서 |
| 제품 베이스라인(Product) | 시스템 통합과 검증 완료 시점 | 최종 릴리스 소스코드, 실행 파일, 운영 매뉴얼, 배포 산출물 |

## Ⅴ. 형상관리의 한계와 방안

- 핵심 요약 : 변경 추적과 시점 복원이라는 장점, 브랜치 통합 충돌·승인 병목·구성 불일치라는 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 장기 브랜치 병합 충돌 | 독립 브랜치의 수주 개발 후 병합하면 대규모 충돌과 회귀 결함 발생 | **트렁크 기반 개발** (Trunk-Based Development)으로 메인 브랜치에 자주 병합하고, 미완성 기능은 기능 플래그로 배포에서 격리 | 브랜치 수명, 병합 충돌 건수 |
| 수작업 승인과 빠른 배포의 충돌 | CCB의 문서 승인 절차가 잦은 릴리스를 막아 배포가 지연 | **GitOps** (Git 저장소를 배포 상태의 단일 기준으로 삼는 운영 방식)에서 커밋 해시와 태그를 감사 가능한 베이스라인으로 활용하고, OPA(Open Policy Agent) 정책 검증으로 승인을 자동화 | 승인 대기 시간, 배포 빈도 |
| 구성 드리프트 (Configuration Drift) | 소스코드만 버전 관리되고 OS 패치, 방화벽, DB 스키마가 수작업으로 바뀌어 환경 간 불일치 발생 | **IaC** (Infrastructure as Code, 인프라를 코드로 정의하는 방식)로 인프라를 형상 항목에 편입하고, DVC(Data Version Control)로 데이터와 AI 모델 버전을 함께 관리하며 드리프트 자동 탐지 | 드리프트 탐지 건수, 환경 불일치율 |

## Ⅵ. 현대 클라우드·DevOps 환경에서의 기술사적 제언

- 핵심 요약 : 형상관리의 범위를 인프라와 정책까지 넓히고, 형상감사를 파이프라인 증적으로 대체하는 방향.
- 형상 범위의 확장 : 애플리케이션 소스뿐 아니라 인프라 정의, 파이프라인 정의, 보안 정책까지 같은 저장소와 승인 이력에 등록해 환경 재현성을 확보하는 것이 필요함. 이를 **Everything as Code** (모든 것을 코드로 관리하는 원칙)라고 함.
- 감사 체계의 자동화 : 형상감사를 사람이 작성하는 문서로 수행하면 실무 부담이 커지므로, 커밋 이력과 빌드 기록, 승인 로그를 증적으로 남겨 FCA와 PCA 증적을 파이프라인이 자동 생성하도록 설계하는 것이 필요함.

## Ⅶ. 결론

- 핵심 요약 : 형상관리는 베이스라인 통제와 변경 추적으로 품질과 재현성을 보장하는 관리 프로세스.
- 시사점 : 트렁크 기반 개발, GitOps, IaC로의 확장이 클라우드 시대 형상관리 성숙도의 핵심 전환점임.
