## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 유지보수·형상관리 → **형상관리(베이스라인)**

## 30초 인출

- 본질: 형상관리(SCM: Software Configuration Management)는 소프트웨어 생명주기 전반의 산출물을 식별하고 승인된 변경·상태·감사를 관리하여 제품의 무결성을 보장하는 통제 활동
- 메커니즘: 형상 식별 → 형상 통제(CCB 심의, 변경 승인) → 형상 상태 보고 → 형상 감사(FCA/PCA)의 4대 활동과 단계별 기준선(Baseline) 설정
- 통찰: 배포 환경과 소스코드 버전의 불일치로 형상 변이가 발생하므로 GitOps 기반의 단일 진실 공급원(SSOT) 확립과 자동화된 불변 인프라 배포 적용

<details>
<summary>핵심 용어</summary>

- **형상관리(SCM: Software Configuration Management)** : 소프트웨어 생명주기 동안 생성되는 소프트웨어, 하드웨어, 문서 등 산출물의 변경을 통제하고 무결성을 보증하는 활동
- **Baseline(기준선)** : 공식적인 검토와 승인을 거쳐 고정된 상태로, 이후의 모든 변경은 공식적인 CCB 통제 절차를 통해서만 가능한 기술적 기준점
- **CI(Configuration Item, 형상항목)** : 형상관리의 개별 통제 단위로 지정된 명세서, 설계도, 소스코드, 빌드 스크립트, 시험 문서 등의 산출물
- **CCB(Configuration Control Board, 형상통제위원회)** : 변경 요청(CR)의 기술적·비용적 영향을 심의하여 승인, 반려, 보류를 최종 결정하는 협의체
- **FCA(Functional Configuration Audit)** : 개발된 산출물이 요구사항 명세서의 기능적 조건을 온전히 충족했는지 검증하는 기능적 형상감사
- **PCA(Physical Configuration Audit)** : 설계서, 소스코드, 사용자 매뉴얼 등 형상항목의 실제 물리적 완비 상태를 검증하는 물리적 형상감사

## 2~4교시 25점 답안

## Ⅰ. 형상관리의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **형상관리(SCM: Software Configuration Management)** 는 소프트웨어 생명주기 산출물의 변경을 식별·통제하고 상태 기록 및 감사를 수행하는 품질 관리 활동 |
| 목적 | 승인된 기준선(Baseline)과 실제 배포물의 일치성 보장, 변경 이력의 가시성 확보 및 역추적성 제공 |

## Ⅱ. 형상관리의 핵심 특징

| 특징 | 의미 |
|---|---|
| 무결성 보장 | 인가되지 않은 임의 변경을 원천 차단하여 산출물의 신뢰성 유지 |
| 양방향 추적성 | 요구사항부터 설계, 소스코드, 테스트 케이스, 배포본까지의 상호 연계 추적 |
| 다중 버전 공존 | 브랜치 및 릴리스 관리를 통해 개발, 테스트, 운영 버전의 독립적 통제 지원 |

## Ⅲ. 형상관리 4대 활동 및 CCB 변경 통제 절차

### 형상관리 4대 핵심 활동 체계

```text
       ┌────────────────────────────────────────────────────────┐
       │             형상관리 계획 (SCM Planning)               │
       └──────────────────────────┬─────────────────────────────┘
                                  │
    ┌─────────────────┬───────────┴───────────┬─────────────────┐
    ▼                 ▼                       ▼                 ▼
[형상 식별]      [형상 통제]             [형상 상태 보고]  [형상 감사]
 CI 선정,        변경 요청(CR) 접수,     변경 이력 기록,   FCA(기능 감사),
 명명·버전 체계  CCB 심의·승인·반영      릴리스 현황 공표  PCA(물리 감사)
```

### CCB(형상통제위원회) 변경 통제 및 기준선 갱신 절차

```text
변경 요청(CR) 접수
    ↓
영향도 분석: 범위·일정·비용·품질 파급효과 산정
    ↓
CCB 심의 및 의결
    ├─ 반려/보류 → 사유 기록 및 요청자 통보
    └─ 승인 → 변경 구현 작업 지시
    ↓
검증 및 시험: 단위·회귀 테스트 수행
    ↓
FCA/PCA 형상 감사 수행 후 신규 기준선(Baseline) 공식 갱신 및 릴리스
```

| 4대 활동 | 주요 수행 내용 | 핵심 산출물 |
|---|---|---|
| 형상 식별 (Identification) | 형상관리 대상(CI) 선정, 식별자 및 버전 명명 규칙 확립 | 형상관리계획서, CI 베이스라인 목록 |
| 형상 통제 (Control) | 변경 요청 검토, CCB 심의, 릴리스 승인 및 버전 잠금 | 변경요청서(CR), CCB 회의록, 변경통제서 |
| 형상 상태 보고 (Accounting) | 형상항목의 현재 버전 상태, 변경 진행 경과 기록 및 공표 | 형상 상태 보고서, 형상 이력 대장 |
| 형상 감사 (Audit) | 기준선과 실제 산출물 간의 기능적(FCA)·물리적(PCA) 무결성 실사 | 형상감사보고서, 시정조치 요구서 |

## Ⅳ. 소프트웨어 생명주기별 기준선(Baseline) 유형

```text
[요구사항 정의] ──→ 기능 기준선 (Functional Baseline: 시스템 규격 확정)
      ↓
[기본/상세 설계] ──→ 분배 기준선 (Allocated Baseline: 서브시스템·모듈 인터페이스 확정)
      ↓
[구현 및 시험]  ──→ 개발 기준선 (Development Baseline: 소스코드 및 단위시험 확정)
      ↓
[시스템 시험]   ──→ 제품 기준선 (Product Baseline: 최종 릴리스 빌드 확정)
      ↓
[운영 및 유지보수] ──→ 운영 기준선 (Operational Baseline: 운영 배포 상태 확정)
```

### 전통적 SCM과 현대적 GitOps SCM 비교

| 비교 항목 | 전통적 SCM (Subversion, CVS) | 현대적 GitOps / DevOps SCM (Git) |
|---|---|---|
| 저장소 아키텍처 | 중앙 집중식 서버 모델 (Centralized) | 분산형 버전 관리 모델 (Distributed) |
| 변경 통제 기법 | 수작업 양식 작성 및 오프라인 CCB 결재 | Pull Request / Merge Request 및 코드 리뷰 자동화 |
| 감사 및 추적 | 수작업 형상 감사(FCA/PCA) 주기적 수행 | CI/CD 파이프라인 내 암호화 커밋 해시 자동 추적 |
| 배포 대상 관리 | 소스코드 중심 형상 관리 | 코드, 설정, 인프라(IaC), 컨테이너 이미지 통합 관리 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 오프라인 CCB 결재 절차의 형식화 및 장시간 소요로 인한 애자일 배포 속도 저하 | 정형화된 변경은 자동화된 CI 파이프라인 통과 조건으로 위임 승인 체계 전환 |
| 운영 긴급 패치(Hotfix)의 수작업 반영으로 인한 소스코드 형상과 운영 배포본 불일치 | Git을 단일 진실 공급원(SSOT)으로 삼는 GitOps 파이프라인 강제 및 자동 롤백 적용 |
| 대규모 마이크로서비스 환경에서 수많은 레포지토리 간 인터페이스 버전 충돌 | 컨트랙트 테스팅(Pact) 및 시맨틱 버저닝(SemVer) 규칙의 엄격한 준수 |

## Ⅵ. 제언

GitOps 기반의 단일 진실 공급원(SSOT) 구축과 선언적 불변 인프라 형상관리 체계 확립

### GitOps 기반 선언적 형상관리 파이프라인

```text
개발자: Git PR 생성 및 코드 리뷰
    ↓
CI 파이프라인: 빌드, 단위테스트, 정적보안 검증 통과 후 머지
    ↓
컨테이너 이미지 레지스트리 빌드 태그 생성 (Immutable Image)
    ↓
GitOps 컨트롤러 (ArgoCD):
    Git 매니페스트 저장소와 프로덕션 클러스터 상태 실시간 비교
    ├─ 상태 일치 → 정상 동기화 유지
    └─ 드리프트(Drift) 감지 → Git 선언 상태로 자동 수렴(Auto-sync)
```

### 형상 변경 감사 및 암호화 서명 파이프라인

```text
개발자 커밋
    ↓
GPG 키 기반 커밋 암호화 서명
    ↓
CI 빌드 시 슬사(SLSA) 레벨 3 서명 생성
    ↓
배포 승인 시 암호화 서명 검증 통과한 산출물만 클러스터 배포 허용
```

### 선택 근거: 전통적 수작업 배포와 GitOps 선언적 형상관리 비교

| 구분 | 전통적 수작업 배포 SCM | 제언: GitOps 기반 선언적 형상관리 |
|---|---|---|
| 진실의 원천 | 서버 운영 환경 내부 상태 | Git 레포지토리 매니페스트 (SSOT) |
| 형상 드리프트 방지 | 수작업 감사 시점에만 탐지 가능 | 컨트롤러의 상시 모니터링 및 자동 복구 |
| 롤백 메커니즘 | 복잡한 이전 버전 수작업 재배포 | Git 이전 커밋 `git revert`로 1초 이내 완료 |
