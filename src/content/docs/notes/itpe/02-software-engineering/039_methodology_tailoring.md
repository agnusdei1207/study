## Ⅰ. 개발방법론 테일러링의 개요

- **개념** : 조직의 표준 소프트웨어 개발 방법론을 특정 프로젝트의 환경적 특성(규모, 위험도, 도메인, 기술 스택, 발주자 요구 등)에 맞추어 프로세스, 절차, 산출물, 기법을 합리적으로 가감(수정, 생략, 추가)하는 엔지니어링 재구성 활동.
- **배경 및 필요성** : 모든 프로젝트에 획일적인 표준 프로세스를 강요할 경우 발생하는 과도한 형식주의(Bureaucracy), 불필요한 산출물 작성에 따른 낭비, 반대로 필수 공정 누락으로 인한 품질 저하 방지.
- **표준 근거** : ISO/IEC 12207(소프트웨어 생명주기 프로세스 테일러링 지침), CMMI Process Tailoring.

## Ⅱ. 개발방법론 테일러링 4단계 절차

```text
   [ 1. 프로젝트 환경 분석 ] ──> [ 2. 베이스라인 방법론 선정 ]
    - 규모, 기간, 위험도            - 폭포수, 애자일, 패키지 도입
    - 도메인 특성, 팀 역량           - 조직 표준 프레임워크 선택
              │                               │
              ▼                               ▼
   [ 3. 테일러링 매트릭스 수립 ] ──> [ 4. 심의 승인 및 이행 관리 ]
    - 단계(Phase) 가감              - PMO / 품질보증(QA) 승인
    - 필수 산출물 생략/통합         - 프로젝트 수행 및 주기적 갱신
```

- **1단계 (프로젝트 특성 분석)** : 프로젝트의 규모(FP, 비용), 일정 긴급도, 요구사항 가변성, 발주자 성향, 도메인 안전성 요건 파악.
- **2단계 (기본 방법론 선정)** : 프로젝트 성격에 가장 부합하는 기본 라이프사이클 모델(애자일, 반복형, 폭포수) 확정.
- **3단계 (테일러링 기준 정의 및 매트릭스 작성)** : 활동(Activity), 작업(Task), 산출물(Artifact)의 필수/선택 여부를 체크리스트로 정의.
- **4단계 (승인 및 통제)** : 이해관계자 및 품질보증 부서(QA)의 심의를 거쳐 프로젝트 관리계획서(PMP)에 공식 반영.

## Ⅲ. 테일러링 고려 요소 및 가감 기준

| 분류 | 테일러링 고려 요인 | 테일러링 적용 방향 |
|---|---|---|
| 프로젝트 규모/기간 | 초소형 단기 과제 vs 대규모 다년 과제 | 소규모: 산출물 통합 및 간소화 / 대규모: 전 단계 정규 산출물 작성 |
| 요구사항 가변성 | 요구사항 명확/고정 vs 수시 변경 도메인 | 명확: 폭포수 기반 통제 / 불명확: 스크럼/칸반 애자일 반복 주기 도입 |
| 시스템 위험도 | 일반 사내 포털 vs 미션 크리티컬 안전 시스템 | 안전 시스템: FMEA/FTA, 독립적 제3자 V&V(IV&V) 공정 의무 추가 |
| 기술적 신규성 | 성숙된 검증 기술 vs 최신 AI/클라우드 기술 | 신규 기술: PoC/스파이크 솔루션 단계 추가, 아키텍처 검증 강화 |
| 법적/제도적 제약 | 금융감독규정, 전자정부 표준프레임워크, PIPA | 법정 의무 감리, 개인정보영향평가(PIA), 보안성 검토 공정 강제 |

## Ⅳ. 실무 테일러링 적용 시 기술사적 제언

- **산출물 중심에서 '실질적 엔지니어링 가치' 중심으로의 전환** : 단지 감리 수검을 위한 '문서를 위한 문서'를 양산하는 테일러링을 지양하고, 시스템의 동작성과 품질을 담보하는 테스트 자동화 코드 및 API 명세서로 대체 승인하는 합리적 기준 수립.
- **테일러링 결과의 조직 자산화(Process Asset Library, PAL)** : 프로젝트 종료 후 수행된 테일러링의 효과성을 사후 평가하고, 성공적인 테일러링 패턴을 조직의 표준 프로세스 자산으로 환류하는 지속 개선 체계 정립.
