## 연관 키워드

- 개발방법론 테일러링(Methodology Tailoring), ISO/IEC 12207, CMMI(Capability Maturity Model Integration)
- 테일러링 매트릭스, PMO(Project Management Office), 품질보증(QA), OPA(Organizational Process Assets), PAL(Process Asset Library)

## Ⅰ. 개발방법론 테일러링의 개요

- 핵심 요약 : 표준 개발방법론을 프로젝트 환경에 맞게 프로세스·산출물을 가감하는 재구성 활동.
- 개념 : 조직의 표준 소프트웨어 개발방법론을 프로젝트의 규모, 위험도, 도메인, 기술 스택, 발주자 요구에 맞추어 프로세스, 절차, 산출물, 기법을 수정·생략·추가하는 엔지니어링 재구성 활동 (**개발방법론 테일러링**, Methodology Tailoring).
- 배경 및 필요성 : 모든 프로젝트에 같은 표준 프로세스를 강제하면 불필요한 산출물로 인한 형식주의와 낭비가 생기고, 반대로 필수 공정을 임의로 빼면 품질이 떨어지므로 두 문제를 함께 다스릴 기준이 필요.
- 표준 근거 : ISO/IEC 12207(소프트웨어 생명주기 프로세스 표준)은 조직과 프로젝트에 맞게 프로세스를 적용하도록 허용하고, CMMI(Capability Maturity Model Integration)도 조직 표준 프로세스의 테일러링을 전제로 한다.
- 주요 목적 : 프로젝트 특성 적합성을 높이면서 품질 거버넌스를 유지하는 것.

## Ⅱ. 개발방법론 테일러링의 특징 및 장점

- 핵심 요약 : 환경 특성 평가와 매트릭스 기반 가감, 심의 승인, 자산 환류가 맞물려 형식주의는 줄이고 적합성은 높이는 방식.

1. 환경 기반 가감 : 규모, 위험도, 도메인, 기술 스택, 발주자 요구를 기준으로 프로세스를 조정 → 불필요한 산출물 감소와 수행 효율화.
2. 표준 근거 준수 : ISO/IEC 12207과 CMMI의 테일러링 원칙을 따름 → 가감 결정의 외부 설명력 확보.
3. **테일러링 매트릭스** (Tailoring Matrix, 활동·작업·산출물의 필수·선택 여부를 정리한 표) : 항목별 필수·선택을 구분 → 생략 근거를 항목 단위로 추적.
4. 심의 승인 절차 : PMO(Project Management Office, 프로젝트 관리 사무국)와 품질보증(QA, Quality Assurance) 심의를 거침 → 임의 생략 방지.
5. 자산 환류 : 종료 후 결과를 OPA(Organizational Process Assets, 조직 프로세스 자산)로 되돌림 → 다음 프로젝트의 기준 개선.

## Ⅲ. 개발방법론 테일러링의 구조 (흐름)

- 핵심 요약 : 환경 분석에서 승인·이행까지 4단계를 거치고, Phase Gate마다 재평가하는 순환 구조.
- 4단계 절차 : 1단계 특성 분석(규모 FP(Function Point), 일정 긴급도, 요구사항 가변성, 도메인 안전 요건 파악), 2단계 기본 방법론 선정(폭포수, 반복형, 애자일 중 성격에 맞는 라이프사이클 확정), 3단계 매트릭스 작성(활동·작업·산출물의 필수·선택을 체크리스트로 정의), 4단계 승인·통제(PMO와 QA 심의 후 프로젝트 관리계획서에 반영).

```text
[ 테일러링 4단계 절차 ]

1. 프로젝트 환경 분석
      ↓
2. 베이스라인 방법론 선정
      ↓
3. 테일러링 매트릭스 수립
      ↓
4. 심의 승인 및 이행 관리
```

```text
[ 테일러링 통제 루프 ]

프로젝트 착수
      ↓
테일러링 기준 확정 (PMO·QA 승인)
      ↓
Phase Gate 적합성 재평가
      ↓ (환경 변화 시 재조정)
종료 후 교훈 → OPA·PAL 환류
```

## Ⅳ. 개발방법론 테일러링의 비교

- 핵심 요약 : 요구 가변성과 통제 수준에 따라 기본 라이프사이클을 고르고, 그 위에서 가감 폭을 정하는 기준.

| 비교 축 | 폭포수 기반 | 애자일 기반 | 하이브리드 |
| --- | --- | --- | --- |
| 적합 환경 | 요구사항이 명확하고 고정된 과제 | 요구가 수시로 바뀌는 과제 | 일부는 고정, 일부는 가변인 과제 |
| 통제 방식 | 단계별 승인과 산출물 중심 | 반복 주기와 backlog 중심 | 핵심 단계는 통제, 개발 구간은 반복 |
| 산출물 가감 | 정규 산출물 위주, 간소화 여지 적음 | 작업 단위 산출물, 가감 폭 큼 | 위험 영역만 정규 산출물 요구 |
| 주요 위험 | 변경 대응 지연 | 문서·설계 누락 | 기준이 모호해지는 경계 |

- 선택 기준 : 요구 가변성, 시스템 위험도, 법적 제약 중 가장 강한 요인이 기본 라이프사이클을 정하고, 나머지 요인은 산출물 가감 폭을 결정.

## Ⅴ. 개발방법론 테일러링의 한계와 방안

- 핵심 요약 : 임의 생략, 주관적 평가, 자산 환류 단절을 원칙 명문화와 정량 평가, 주기적 재평가로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 원칙 없는 산출물 임의 생략 | 납기 압박을 이유로 설계서, 테스트 명세서 같은 품질 통제 산출물을 누락 → 유지보수 실패 | 전사 테일러링 가이드라인에 필수·가감 가능 산출물을 명문화하고 PMO·QA 승인을 의무화 | 승인 누락 건수, 필수 산출물 누락률 |
| 평가의 주관성 | PM의 경험과 직관에 기대어 방법론을 재단 → 규제 요구와 위험도 반영 누락 | 규모, 복잡도, 팀 역량, 안정성 요구를 점수화한 평가 매트릭스로 표준 템플릿 추천 | 평가 점수와 실제 결과의 편차 |
| 피드백과 자산화 단절 | 초기 기준이 개발 중 갱신되지 않고 종료 후 OPA로 환류되지 않음 | Phase Gate마다 적합성 재평가, 종료 후 교훈(Lessons Learned) 세션으로 템플릿 개정 | 재평가 수행률, 템플릿 개정 횟수 |

## Ⅵ. 개발방법론 테일러링에 대한 기술사적 제언

- 핵심 요약 : 감리 대응용 문서보다 실질적 엔지니어링 가치를 기준으로 삼고, 정량 평가와 자산 환류를 제도로 정착.
- 문서 대신 검증 결과로 승인하는 기준 : 감리 수검용 문서를 늘리는 대신 테스트 자동화 코드와 API(Application Programming Interface) 명세처럼 품질을 직접 보여 주는 산출물로 대체할 수 있는지를 심의 기준에 반영하는 것이 좋다. 이때 PMO가 대체 근거를 기록해 두어야 나중에 같은 논쟁이 반복되지 않는다.
- 정량 평가 체계 도입 : 규모, 복잡도, 팀 역량, 안정성 요구를 점수화하여 폭포수, 애자일, 하이브리드 중 무엇을 기본으로 할지 정하는 방식을 전사 표준으로 두면 PM 개인 판단에 따른 편차를 줄일 수 있다.
- 자산화 체계 정착 : 종료 후 테일러링의 효과를 사후 평가하고, 성공한 패턴을 PAL(Process Asset Library, 프로세스 자산 라이브러리)에 등록해 다음 프로젝트가 재사용하도록 하는 체계가 필요하다.

## Ⅶ. 결론

- 핵심 요약 : 테일러링은 표준 준수와 프로젝트 적합성의 균형을 잡는 제도적 재구성 활동.
- 시사점 : 가감 근거를 정량 기준과 Phase Gate 재평가로 남기고 PAL로 환류할 때 테일러링이 임의 생략이 아닌 조직의 학습 수단이 됨.
