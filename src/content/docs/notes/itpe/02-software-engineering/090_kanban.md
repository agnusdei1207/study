## Ⅰ. 칸반의 개요

- 개념 : **도요타 생산방식** (JIT)에서 유래하여 데이비드 앤더슨(David Anderson)이 소프트웨어 엔지니어링에 도입한 프로세스 관리 방법론으로, 업무의 흐름(Flow)을 시각화하고 진행 중인 작업(WIP, Work In Progress)을 엄격히 제한하여 납기 리드타임을 단축하고 프로세스 병목을 지속적으로 제거하는 풀(Pull) 기반의 린(Lean) 소프트웨어 개발 프레임워크.
- 배경 및 필요성 : 고정된 스프린트 주기를 맞추기 어려운 지속적 유지보수, 운영 지원, 장애 대응 조직에서 요구사항 유입 즉시 유연하게 처리하기 위해 도입.
- 칸반 6대 핵심 실천법 : 업무 시각화, WIP 제한, 흐름 관리, 정책의 명시화, 피드백 루프 구현, 협업을 통한 지속 개선.

## Ⅱ. 칸반 보드의 구조 및 풀(Pull) 시스템 메커니즘

```text
   [ 백로그 (Backlog) ] ──> [ 분석 (Analysis) ] ──> [ 개발 (Dev) ] ──> [ 테스트 (QA) ] ──> [ 배포 완료 (Done) ]
                             (WIP Limit: 2)         (WIP Limit: 3)       (WIP Limit: 2)
                                ┌──────┐               ┌──────┐             ┌──────┐
                                │ 카드 │               │ 카드 │             │ 카드 │
                                └──────┘               └──────┘             └──────┘
   (WIP 제한에 도달하면 선행 작업을 끝마쳐 슬롯이 빌 때까지 후속 작업을 절대로 끌어당기지 않음: Pull 방식)
```

- **WIP(Work In Progress) 제한 원칙** : 각 공정 단계마다 동시에 진행할 수 있는 최대 작업 티켓 수를 제한(예: 개발 WIP=3).
- **풀(Pull) 방식의 가치 흐름** : 후속 공정(QA)에서 작업이 완료되어 여유 슬롯이 생길 때만 선행 공정(개발)에서 작업을 끌어당김(Pull). 작업이 정체되는 병목 지점이 즉각적으로 시각화됨.
- **누적 흐름도 (CFD, Cumulative Flow Diagram)** : 시간에 따른 각 단계별 작업 티켓 수를 누적 영역 차트로 표현하여 리드타임과 WIP 병목을 모니터링.

## Ⅲ. 스크럼(Scrum)과 칸반(Kanban)의 비교

| 비교 항목 | 스크럼 (Scrum) | 칸반 (Kanban) |
|---|---|---|
| 주기 (Cadence) | 1~4주의 고정된 타임박스 (스프린트) | 고정된 주기 없음 (지속적 흐름, 단일 티켓 단위 배포) |
| 릴리스 방식 | 스프린트 종료 시점 일괄 증분 릴리스 | 작업이 완료되는 즉시 개별 지속적 배포 (CD) |
| 변경 수용성 | 스프린트 진행 도중 백로그 변경 금지 | WIP 한도 내에서 언제든지 최우선 티켓 즉시 투입 가능 |
| 역할과 책임 | PO, 스크럼 마스터, 개발팀의 엄격한 역할 | 기존 조직 구조를 그대로 유지 (특정 역할 강제 없음) |
| 핵심 성과 메트릭 | **팀 속도** (Velocity), 번다운 차트 | **리드타임** (Lead Time), **사이클 타임** (Cycle Time), CFD |
| 적합한 환경 | 신규 제품 개발, 목표 지향적 프로젝트 | 운영 유지보수, DevOps, 고객 지원, 인프라 운영 |

## Ⅳ. 칸반(Kanban)의 주요 한계점 및 해결 방안

- WIP(Work In Progress) 제한 미준수로 인한 병목 은폐 :
  - 한계점 : 개발팀의 관성으로 인해 WIP 한도를 초과하여 작업을 밀어 넣음으로써 멀티태스킹이 발생하고 리드 타임이 급증하며 병목 현상 고착화.
  - 해결 방안 : 리틀의 법칙(Little's Law) 기반 데이터 주도 WIP 제한 설정, 지라(Jira) 등 보드 내 WIP 초과 시 티켓 추가 금지 시스템 정책 강제.
- 명확한 완료 기준(Definition of Done, DoD) 부재로 인한 품질 저하 :
  - 한계점 : 스크럼과 달리 타임박스 스프린트가 없어 품질 게이트웨이가 느슨해질 경우 미완성 티켓이 '완료'로 쉽게 이동하여 기술 부채 누적.
  - 해결 방안 : 컬럼 간 이동 규칙(Explicit Policies) 명문화, CI/CD 자동화 테스트 및 코드 리뷰 통과를 티켓 전이의 필수 조건으로 시스템 연동.
- 대규모 조직에서의 팀 간 의존성(Cross-team Dependency) 관리 취약 :
  - 한계점 : 단일 팀 칸반 보드만으로는 다수 시스템이 얽힌 엔터프라이즈 프로젝트의 의존 관계 및 통합 릴리스 일정을 추적하기 어려움.
  - 해결 방안 : 플라이트 레벨(Flight Levels) 또는 포트폴리오 칸반 도입으로 전략-조율-운영 3단계 계층형 가시성 확보 및 의존성 매핑 보드 운영.

## Ⅴ. 지속적 개선을 위한 기술사적 제언

- 리틀의 법칙(Little's Law)에 기반한 WIP 통제 : '평균 리드타임 = WIP / 처리량(Throughput)' 공식에 따라, 납기 속도를 빠르게 하려면 개발자를 야근시키는 것이 아니라 진행 중인 작업(WIP)의 개수를 줄여야 한다는 과학적 경영 원칙을 팀 내에 확립해야 함.
- 스크럼반(Scrumban) 하이브리드 모델의 유연한 도입 : 계획과 회고는 스크럼의 정기 이벤트를 차용하고, 일상적인 개발 작업 흐름은 칸반 보드와 WIP 제한을 적용하는 스크럼반 모델을 통해 비즈니스 예측 가능성과 민첩성을 동시 확보.
