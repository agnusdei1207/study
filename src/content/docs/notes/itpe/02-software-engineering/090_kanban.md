| 서브토픽 | 핵심 키워드 | 답안 차별화 포인트 |
|---|---|---|
| WIP(Work In Progress) 제한 | Stop Starting, Start Finishing, 컨텍스트 스위칭 낭비 제거, 풀(Pull) 시스템 | 동시 진행 작업 수 상한을 통한 병목 가시화 및 자연스러운 스워밍(Swarming) 유도 |
| 리틀의 법칙 (Little's Law) | $W = L / \lambda$ (Lead Time = WIP / Throughput), 큐잉 이론(Queueing Theory) | WIP를 낮춤으로써 작업 처리 시간(Lead Time)을 수학적으로 단축하는 공학 원리 도해 |
| 누적 흐름 다이어그램 (CFD) | Cumulative Flow Diagram, 밴드 폭(WIP), 기울기(Throughput), 병목 탐지 | 프로세스 각 단계별 정체 현상을 실시간 모니터링하고 사이클 타임을 측정하는 도구 명시 |

## 1. 칸반의 개요 및 4대 핵심 원칙

### (1) 칸반(Kanban)의 정의
- 도요타 생산 방식(TPS)의 JIT(Just-In-Time) 철학을 소프트웨어 개발에 접목한 기법으로, **업무 흐름을 시각화(Board)하고 각 작업 단계의 진행 중 작업(WIP, Work In Progress) 수를 엄격히 제한하여 멀티태스킹 낭비를 제거하고 지속적인 가치 전달을 달성하는 린(Lean) 기반 애자일 실천법**.

### (2) 칸반의 4대 핵심 원칙 (David J. Anderson)
1. **업무 흐름의 시각화 (Visualize the Flow)**: 백로그부터 완료까지 모든 작업 카드를 보드에 가시화.
2. **진행 중 작업 제한 (Limit WIP)**: 각 칼럼(단계)마다 동시에 처리할 수 있는 최대 작업 수 상한선 설정.
3. **흐름 관리 및 측정 (Manage Flow)**: 누적 흐름도(CFD)와 리드 타임을 모니터링하여 병목을 선제 제거.
4. **프로세스 정책의 명시화 및 지속적 개선 (Make Policies Explicit)**: '완료(Done)'의 정의와 우선순위 규칙 공개.

## 2. 칸반 보드 메커니즘 및 리틀의 법칙

### (1) 칸반 보드와 WIP 제한 구조도
```text
+-------------------------------------------------------------------------+
|                  칸반 보드(Kanban Board) 및 WIP 상한 통제 구조          |
+-------------------------------------------------------------------------+
| [ To Do (대기) ]  │ [ 분석 (WIP: 2) ]  │ [ 개발 (WIP: 3) ]  │ [ Done (완료) ]   |
| ─────────────────┼────────────────────┼────────────────────┼────────────────── |
|  [Task A]        │  [Task 1]          │  [Task 3]          │  [Task V1]        |
|  [Task B]        │  [Task 2] (Full!)  │  [Task 4]          │  [Task V2]        |
|  [Task C]        │  ────────────────  │  [Task 5] (Full!)  │                   |
|                  │  * 병목 발생 시:    │  ────────────────  │                   |
|                  │    신규 진입 차단   │  * 개발자 협업 지원│                   |
|                  │    (Stop Starting) │    (Swarming 유도) │                   |
+-------------------------------------------------------------------------+
  * 리틀의 법칙 (Little's Law) : $\text{Lead Time} = \frac{\text{WIP}}{\text{Throughput}}$
  * 처리율(Throughput)이 일정할 때, WIP를 줄이면 리드 타임이 정비례하여 감소함
```

### (2) 리틀의 법칙(Little's Law)의 공학적 의미
- 대기행렬 이론(Queueing Theory)에 기반하며, 시스템 내에 머무는 평균 작업 수(WIP)는 평균 도착률($\lambda$, Throughput)과 작업 체류 시간($W$, Lead Time)의 곱과 같음:
  $$\text{WIP} = \text{Throughput} \times \text{Lead Time} \quad \Longleftrightarrow \quad \text{Lead Time} = \frac{\text{WIP}}{\text{Throughput}}$$
- 즉, **작업을 빨리 끝내고 싶다면(Lead Time 단축), 사람을 더 뽑는 것보다 진행 중인 작업(WIP)의 수를 줄이는 것이 가장 확실하고 경제적인 해법**임.

## 3. 칸반(Kanban) vs 스크럼(Scrum) 상세 비교

| 비교 항목 | 칸반 (Kanban) | 스크럼 (Scrum) |
|---|---|---|
| **반복 주기** | **주기 없음 (Continuous Flow, 지속적 흐름)** | **고정 타임박스 (1~4주 스프린트)** |
| **인도 방식** | 기능 준비 즉시 연속 배포 (Continuous Delivery)| 스프린트 종료 시점 일괄 데모 및 릴리스 |
| **역할 정의** | 별도 역할 없음 (기존 팀 구조 그대로 유지) | 스크럼 마스터, 제품 책임자(PO), 개발팀 |
| **주요 통제 메커니즘**| **WIP (진행 중 작업) 한계선 제한** | **타임박스 (시간 제약) 및 스프린트 백로그** |
| **신규 요구 수용** | WIP 슬롯에 여유가 생기면 언제든 즉시 풀(Pull) | 스프린트 진행 도중 신규 요구 원칙적 변경 금지 |
| **주요 측정 지표** | 사이클 타임, 리드 타임, CFD 누적 흐름도 | 스프린트 속도(Velocity), 번다운 차트(Burndown) |
| **적합한 도메인** | **운영 유지보수, 긴급 장애 대응, 지속 배포 DevOps** | **신규 제품 개발, 요구사항 명확한 MVP 프로젝트** |

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **개발자당 5개 티켓을 붙잡고 있어 납기 마비**<br>(진행 중 티켓 50건이 2달째 체류) | WIP 제한 없이 들어오는 모든 요구를 수락하여 컨텍스트 스위칭 낭비 극대화 | 개발자 1인당 WIP 1개 강제 상한선 설정 및 'Start Finishing' 문화 정착 | 티켓 평균 사이클 타임 25일에서 4일로 단축 |
| **테스트 검수 칼럼에 카드가 20장 적체**<br>(개발은 끝났는데 배포가 안 되는 병목) | 특정 단계의 병목을 방치하고 개발자들은 자기 일만 계속 진행한 사일로 | 검수 칼럼 WIP 초과 시 개발 작업 진입 자동 차단 및 전원 검수 협업(Swarming) | 검수 대기 시간 80% 감소, 병목 자율 해소 |
| **보드만 띄워놓고 폭포수처럼 일하는 흉내**<br>(Jira 칼럼에 WIP 숫자가 아예 없음) | 칸반의 본질인 흐름 제어와 WIP 규칙을 이해하지 못한 형식적 도구 도입 | Jira 칼럼별 Max WIP 하드 리밋 설정 및 주간 CFD 리드타임 추적 회고 의무화 | 업무 흐름 정체율 70% 개선, 팀 생산성 2배 향상 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 배치 중심의 경직된 스프린트]        [현대: 지속적 가치 흐름의 스크럼반(Scrumban)]
- 2주 스프린트 끝날 때까지 배포 대기  ──▶   - 준비되는 즉시 CI/CD로 릴리스 (On-Demand 배포)
- 운영 티켓 유입 시 스프린트 계획 파탄 ──▶   - 정기 릴리스는 스크럼 + 긴급 변경은 칸반 (스크럼반)
- 속도(Velocity) 수치에만 집착         ──▶   - DORA 지표(리드 타임, 변경 실패율) 기반 가치 스트림 최적화
```

- **스크럼반(Scrumban) 하이브리드 거버넌스 제시**: 실무 엔지니어링 조직은 순수 스크럼이나 순수 칸반만으로 굴러가기 어려움. **전체 제품 로드맵과 아키텍처 스프린트 계획은 스크럼(Scrum)의 타임박스를 따르고, 일상적인 결함 패치, 인프라 운영, 핫픽스는 칸반(Kanban)의 WIP 기반 흐름으로 처리하는 '스크럼반(Scrumban)'** 아키텍처를 제시해야 함.
- **가치 스트림 매핑(VSM)과 DORA 메트릭스와의 연계**: 칸반의 궁극점은 티켓 이동이 아니라 **'고객 아이디어가 프로덕션 코드에 반영되어 가치를 창출하기까지의 리드 타임 최소화'**임. DORA 4대 핵심 지표(배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간)와 칸반 CFD 차트를 직접 연계하여 조직의 엔지니어링 민첩성을 정량 측정하는 기술사적 시각을 드러내야 함.
