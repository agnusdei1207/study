## 연관 키워드

- 칸반(Kanban), WIP(Work In Progress) 제한, 풀(Pull) 시스템, 흐름 관리, 린(Lean) 개발
- 누적 흐름도(CFD, Cumulative Flow Diagram), 리드타임(Lead Time), 사이클 타임(Cycle Time), 리틀의 법칙(Little's Law), 스크럼반(Scrumban)

## Ⅰ. 칸반의 개요

- 핵심 요약 : 업무 흐름 시각화와 WIP 제한으로 납기 단축·병목 제거를 지속하는 풀 기반 린 프레임워크.
- 개념 : 도요타 생산방식의 JIT(Just-in-Time)에서 유래하여 데이비드 앤더슨(David Anderson)이 소프트웨어 엔지니어링에 도입한 프로세스 관리 방법론으로, 업무의 흐름(Flow) 시각화와 진행 중인 작업 WIP(Work In Progress)의 엄격한 제한을 통해 납기 리드타임 단축과 프로세스 병목의 지속적 제거를 추구하는 풀(Pull) 기반 린(Lean) 소프트웨어 개발 프레임워크.
- 배경 및 필요성 : 고정된 스프린트 주기 운영이 어려운 지속적 유지보수, 운영 지원, 장애 대응 조직의 요구사항 유입 즉시·유연 처리 요구.
- 주요 목적 : 리드타임(Lead Time) 단축, 병목의 조기 시각화, 지속적 흐름 기반 납기 예측 가능성 확보.

## Ⅱ. 칸반의 특징

- 핵심 요약 : 6대 핵심 실천법으로 대표되는 시각화·흐름 중심의 경량 애자일 프레임워크.

1. 업무 시각화 : 칸반 보드 티켓 기반의 전체 업무 흐름 가시화.
2. WIP(Work In Progress) 제한 : 공정별 동시 작업 수의 엄격한 상한 설정.
3. 흐름 관리 : 리드타임·사이클 타임 측정과 병목의 지속적 제거.
4. 정책의 명시화 : 컬럼 간 이동 규칙(Explicit Policies)의 명문화.
5. 피드백 루프 구현 : 정기 회고와 메트릭 기반 개선 주기 운영.
6. 협업을 통한 지속 개선 : 실험적 프로세스 진화 문화 정착.

## Ⅲ. 칸반 보드의 구조 (흐름)

- 핵심 요약 : 공정별 WIP 한도와 풀(Pull) 방식으로 작동하는 티켓 흐름 구조.
- 칸반 보드 및 풀 시스템 메커니즘.

```text
[ 백로그 (Backlog) ]
   │
   ▼
[ 분석 (Analysis) ]  (WIP Limit: 2)
   │
   ▼
[ 개발 (Dev) ]  (WIP Limit: 3)
   │
   ▼
[ 테스트 (QA) ]  (WIP Limit: 2)
   │
   ▼
[ 배포 완료 (Done) ]
 - WIP 한도 도달 시 슬롯이 빌 때까지
   후속 작업 인출 금지 (Pull)
```

- WIP(Work In Progress) 제한 원칙 : 각 공정 단계별 동시 작업 티켓 수의 상한 설정(예: 개발 WIP=3).
- 풀(Pull) 방식의 가치 흐름 : 후속 공정 QA(Quality Assurance)의 여유 슬롯 확보 시점에만 선행 공정(개발)에서 작업 인출, 작업 정체 병목 지점의 즉각 시각화.
- 누적 흐름도(CFD, Cumulative Flow Diagram) : 시간 경과별 단계 작업 티켓 수의 누적 영역 차트 표현, 리드타임과 WIP 병목 모니터링.

## Ⅳ. 스크럼과 칸반의 비교

- 핵심 요약 : 타임박스 반복 개발과 지속적 흐름 관리의 방법론적 차이.
- 주기와 릴리스 방식 대조.

```text
[ 스크럼 ] 계획 → 스프린트(1~4주) → 리뷰/회고 → 일괄 증분 릴리스
              (타임박스 반복, 역할 중심)
[ 칸반  ] 백로그 → 분석 → 개발 → 검증 → 완료 즉시 배포
              (지속적 흐름, WIP 제한 중심)
```

| 비교 항목 | 스크럼(Scrum) | 칸반(Kanban) |
|---|---|---|
| 주기(Cadence) | 1~4주의 고정된 타임박스(스프린트) | 고정된 주기 없음(지속적 흐름, 단일 티켓 단위 배포) |
| 릴리스 방식 | 스프린트 종료 시점 일괄 증분 릴리스 | 작업 완료 즉시 개별 지속적 배포(CD, Continuous Delivery) |
| 변경 수용성 | 스프린트 진행 도중 백로그 변경 금지 | WIP 한도 내 언제든지 최우선 티켓 즉시 투입 가능 |
| 역할과 책임 | PO(Product Owner), 스크럼 마스터, 개발팀의 엄격한 역할 | 기존 조직 구조 유지(특정 역할 강제 없음) |
| 핵심 성과 메트릭 | 팀 속도(Velocity), 번다운 차트 | 리드타임(Lead Time), 사이클 타임(Cycle Time), CFD |
| 적합한 환경 | 신규 제품 개발, 목표 지향적 프로젝트 | 운영 유지보수, DevOps, 고객 지원, 인프라 운영 |

## Ⅴ. 칸반의 장점과 한계

- 핵심 요약 : 유연한 흐름 관리·즉시 배포의 장점, WIP 미준수·완료 기준 부재·팀 간 의존성 관리의 한계.
- 장점
  1. 고정 주기 없는 요구사항 즉시 투입과 개별 티켓 단위 지속 배포.
  2. 기존 조직 구조 유지를 통한 낮은 도입 장벽.
  3. WIP 제한 기반 멀티태스킹 억제와 리드타임 단축.
- 한계점 1 : WIP(Work In Progress) 제한 미준수로 인한 병목 은폐
  - 한계점 : 개발팀 관성에 따른 WIP 한도 초과 작업 투입, 멀티태스킹 발생과 리드타임 급증, 병목 현상 고착화.
  - 해결 방안 : 리틀의 법칙(Little's Law) 기반 데이터 주도 WIP 제한 설정, 지라(Jira) 등 보드의 WIP 초과 티켓 추가 금지 시스템 정책 강제.
- 한계점 2 : 완료 기준(DoD, Definition of Done) 부재로 인한 품질 저하
  - 한계점 : 타임박스 스프린트 부재 환경에서의 품질 게이트웨이 느슨화, 미완성 티켓의 '완료' 전이와 기술 부채 누적.
  - 해결 방안 : 컬럼 간 이동 규칙(Explicit Policies)의 명문화, CI/CD(Continuous Integration/Continuous Delivery) 자동화 테스트와 코드 리뷰 통과의 티켓 전이 필수 조건화.
- 한계점 3 : 대규모 조직의 팀 간 의존성(Cross-team Dependency) 관리 취약
  - 한계점 : 단일 팀 칸반 보드만으로 다수 시스템이 얽힌 엔터프라이즈 프로젝트의 의존 관계·통합 릴리스 일정 추적 곤란.
  - 해결 방안 : 플라이트 레벨(Flight Levels) 또는 포트폴리오 칸반 도입, 전략-조율-운영 3단계 계층형 가시성 확보와 의존성 매핑 보드 운영.

## Ⅵ. 지속적 개선을 위한 기술사적 제언

- 핵심 요약 : 리틀의 법칙 기반 WIP 통제와 스크럼반 하이브리드 모델의 유연한 도입.
- 리틀의 법칙(Little's Law) 기반 WIP 통제 : '평균 리드타임 = WIP / 처리량(Throughput)' 공식에 따라 납기 단축을 위한 진행 중 작업(WIP) 수 축소의 과학적 경영 원칙 확립.
- 스크럼반(Scrumban) 하이브리드 모델의 유연한 도입 : 계획·회고의 스크럼 정기 이벤트 차용과 일상적 개발 작업 흐름의 칸반 보드·WIP 제한 적용, 비즈니스 예측 가능성과 민첩성의 동시 확보.

## Ⅶ. 결론

- 핵심 요약 : 칸반은 WIP 제한과 흐름 관리로 지속적 가치 전달을 실현하는 경량 프레임워크.
- 요약 : 업무 시각화, WIP 제한, 풀 방식, 명시적 정책의 조합이 병목 제거와 납기 단축의 골격.
- 시사점 : 데이터 기반 WIP 설정, 완료 기준 강제, 계층형 보드 운영이 대규모 환경 적용 성공의 조건.
