## 연관 키워드

- 칸반(Kanban), WIP(Work In Progress) 제한, 풀(Pull) 시스템, 흐름 관리, 린(Lean) 개발
- 누적 흐름도(CFD, Cumulative Flow Diagram), 리드타임(Lead Time), 사이클 타임(Cycle Time), 리틀의 법칙(Little's Law), 스크럼반(Scrumban)

## Ⅰ. 칸반의 개요

- 핵심 요약 : 업무 흐름의 시각화와 WIP 제한으로 병목을 줄이고 납기를 앞당기는 풀 기반 린 프레임워크.
- 개념 : 도요타 생산방식의 JIT(Just-in-Time)에서 유래하여 데이비드 앤더슨(David Anderson)이 소프트웨어 개발에 도입한 **칸반** (Kanban). 업무 흐름을 시각화하고 진행 중 작업인 **WIP** (Work In Progress)의 상한을 엄격히 정해, **풀 시스템** (Pull System) 방식으로 흐름을 관리하는 **린** (Lean) 소프트웨어 개발 프레임워크.
- 배경 및 필요성 : 고정 스프린트 주기가 맞지 않는 지속적 유지보수, 운영 지원, 장애 대응 조직에서 요구사항이 수시로 유입되어 즉시 처리할 체계가 필요함.
- 주요 목적 : **리드타임** (Lead Time) 단축, 병목의 조기 시각화, 흐름 기반의 납기 예측 가능성 확보.

## Ⅱ. 칸반의 특징

- 핵심 요약 : 시각화, WIP 제한, 흐름 관리, 정책 명시, 피드백, 협업 개선의 여섯 가지 실천법으로 이루어진 경량 애자일 프레임워크.

1. 업무 시각화 : 칸반 보드에 티켓 단위로 전체 업무 흐름을 드러냄 → 병목 위치를 즉시 파악.
2. WIP 제한 : 공정별 동시 작업 수에 상한을 둠 → 멀티태스킹을 억제하고 흐름을 안정화.
3. 흐름 관리 : 리드타임과 **사이클 타임** (Cycle Time)을 측정하고 병목을 지속적으로 제거 → 납기 예측 정확도 향상.
4. 정책의 명시화 : 컬럼 간 이동 규칙을 문서로 정함 → 팀원 간 판단 기준 통일.
5. 피드백 루프 : 정기 회고와 흐름 지표를 바탕으로 개선 주기를 운영 → 프로세스의 점진적 개선.
6. 협업 기반 지속 개선 : 작은 변경을 실험하며 프로세스를 진화시키는 문화 정착 → 변화에 대한 조직 저항 감소.

## Ⅲ. 칸반 보드의 구조 (흐름)

- 핵심 요약 : 공정별 WIP 한도와 풀 방식으로 작동하는 티켓 흐름 구조.

```text
[ 백로그 (Backlog) ]
   ↓ 풀(Pull)
[ 분석 (WIP 한도 설정) ]
   ↓ 풀(Pull)
[ 개발 (WIP 한도 설정) ]
   ↓ 풀(Pull)
[ 검증 (WIP 한도 설정) ]
   ↓
[ 배포 완료 (Done) ]
```

- WIP 제한 원칙 : 각 공정 단계의 동시 작업 티켓 수에 상한을 두고, 한도에 도달하면 후속 작업을 새로 인출하지 않음.
- 풀 방식의 가치 흐름 : 후속 공정에 여유가 생긴 시점에만 선행 공정의 작업을 당겨와 병목을 즉시 드러냄.
- **누적 흐름도** (CFD, Cumulative Flow Diagram) : 단계별 작업 티켓 수를 시간 순으로 누적해 그린 영역 차트로, 리드타임과 병목의 추이를 모니터링.

## Ⅳ. 스크럼과 칸반의 비교

- 핵심 요약 : 타임박스 기반의 반복 개발과 지속적 흐름 관리라는 방법론의 차이.

```text
[ 스크럼 ]
 계획 → 스프린트 → 리뷰·회고 → 일괄 릴리스
 (타임박스 반복, 역할 중심)

[ 칸반 ]
 백로그 → 분석 → 개발 → 검증 → 즉시 배포
 (지속 흐름, WIP 제한 중심)
```

| 비교 항목 | 스크럼 (Scrum) | 칸반 (Kanban) |
| --- | --- | --- |
| 주기 (Cadence) | 1개월 이내의 고정 타임박스(스프린트) | 고정된 주기 없이 지속적 흐름 |
| 릴리스 방식 | 스프린트 종료 시점에 일괄 증분 릴리스 | 작업 완료 즉시 개별 지속 배포 (CD, Continuous Delivery) |
| 변경 수용성 | 스프린트 중 백로그 변경 제한 | WIP 한도 안에서 최우선 티켓을 언제든 투입 |
| 역할과 책임 | PO(Product Owner), 스크럼 마스터, 개발팀의 명확한 역할 | 기존 조직 구조 유지, 특정 역할 강제 없음 |
| 핵심 성과 메트릭 | 팀 속도(Velocity), 번다운 차트 | 리드타임, 사이클 타임, CFD |
| 적합한 환경 | 신규 제품 개발, 목표 지향 프로젝트 | 운영 유지보수, DevOps, 고객 지원, 인프라 운영 |

## Ⅴ. 칸반의 장점과 한계

- 핵심 요약 : 유연한 흐름 관리와 즉시 배포의 장점 아래, WIP 미준수, 완료 기준 부재, 팀 간 의존성 관리라는 한계가 존재.
- 장점 : 고정 주기 없이 요구사항을 즉시 투입하고 개별 티켓 단위로 지속 배포, 기존 조직 구조를 유지하여 도입 장벽이 낮음, WIP 제한으로 멀티태스킹을 억제하고 리드타임 단축.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| WIP 제한 미준수에 따른 병목 은폐 | 한도를 넘는 작업 투입으로 멀티태스킹과 리드타임 급증, 병목 고착화 | **리틀의 법칙** (Little's Law)에 근거한 데이터 기반 WIP 설정, 보드에서 한도 초과 시 티켓 추가 차단 | 리드타임 추이, WIP 초과 횟수 |
| **완료 기준** (DoD, Definition of Done) 부재에 따른 품질 저하 | 완료 기준이 느슨해 미완성 티켓이 완료로 넘어가고 기술 부채가 누적 | 컬럼 간 이동 규칙의 명문화, CI/CD(Continuous Integration/Continuous Delivery) 자동 테스트와 코드 리뷰 통과를 전이 조건으로 강제 | 재작업률, 완료 후 결함 건수 |
| 대규모 조직의 팀 간 의존성 관리 취약 | 단일 팀 보드로는 여러 시스템이 얽힌 프로젝트의 의존 관계와 통합 릴리스 일정을 추적하기 어려움 | **플라이트 레벨** (Flight Levels) 또는 포트폴리오 칸반 도입, 의존성 매핑 보드 운영 | 팀 간 블로킹 건수, 통합 릴리스 지연 횟수 |

## Ⅵ. 지속적 개선을 위한 기술사적 제언

- 핵심 요약 : 리틀의 법칙에 근거한 WIP 통제와, 스크럼 이벤트를 결합한 하이브리드 운영 모델의 도입.

1. 리틀의 법칙에 따르면 평균 리드타임은 WIP를 처리량으로 나눈 값이므로, 조직은 진행 중 작업 수를 경영 지표로 관리하여 납기를 단축하는 원칙을 세워야 한다.
2. 일상 작업은 칸반 보드와 WIP 제한으로 운영하되 계획과 회고는 스크럼의 정기 이벤트를 차용하는 **스크럼반** (Scrumban) 모델을 검토할 만하며, 이는 예측 가능성과 민첩성을 함께 확보하는 방법이다.

## Ⅶ. 결론

- 핵심 요약 : 칸반은 WIP 제한과 흐름 관리로 지속적 가치 전달을 실현하는 경량 프레임워크.
- 시사점 : 데이터 기반 WIP 설정, 완료 기준의 강제, 계층형 보드 운영이 대규모 환경에서 적용 성공의 조건.
