## 30초 인출

- 본질: **칸반(Kanban)** 은 도요타 생산 방식(TPS)의 JIT(Just-In-Time) 철학을 소프트웨어 공학에 적용하여 전체 업무 프로세스를 시각화하고, 공정별 동시 진행 작업 수(WIP Limit)를 엄격히 제어함으로써 컨텍스트 스위칭 낭비를 제거하고 리드 타임을 극소화하는 린 애자일 프레임워크
- 메커니즘: 보드 시각화 → 컬럼별 WIP 제한 설정 → 후속 공정의 풀(Pull) 기반 작업 인입 → 병목(Bottleneck) 발생 시 신규 착수 중단 및 스워밍(Swarming) 해결 → 지속적 흐름(Flow) 최적화
- 통찰: 팀의 실질적 처리 역량을 무시한 채 신규 작업 착수를 강행하면 리틀의 법칙에 따라 리드 타임이 급증하고 품질이 저하되므로 "Stop Starting, Start Finishing" 원칙에 입각하여 WIP 상한을 엄격히 준수하고 누적 흐름도(CFD) 기반의 병목 개선을 병행할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **WIP 제한 (Work In Progress Limit)** : 특정 작업 공정(컬럼)에서 동시에 진행할 수 있는 작업 티켓의 최대 허용 상한 수치
- **리틀의 법칙 (Little's Law)** : 대기행렬 이론에 기반하여 시스템 내 평균 재공품(WIP)은 처리율(Throughput)과 리드 타임(Lead Time)의 곱과 같다는 원리
- **풀 시스템 (Pull System)** : 앞 단계에서 작업을 강제로 밀어내지(Push) 않고, 후속 공정의 WIP 슬롯에 여유가 생겼을 때만 스스로 작업을 당겨오는 방식
- **리드 타임 (Lead Time)** : 고객의 요구사항 접수(Commitment Point)부터 최종 사용자에게 가치가 배포(Delivery)될 때까지의 총 소요 시간
- **사이클 타임 (Cycle Time)** : 개발팀이 작업에 실제 착수한 시점부터 해당 작업의 개발/검증이 완료될 때까지의 순수 작업 시간
- **CFD (Cumulative Flow Diagram)** : 시간에 따른 각 공정 단계별 티켓 누적 추이를 시각화하여 대기 구간과 병목을 한눈에 식별하는 누적 흐름도

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 업무의 가치 흐름을 보드에 시각화하고 각 단계별 진행 중 작업(WIP) 상한을 강제하여 작업의 정체를 방지하고 지속적 인도를 달성하는 린(Lean) 기반 개발 프레임워크 |
| 목적 | 멀티태스킹에 의한 컨텍스트 스위칭 낭비 제거, 프로세스 병목 조기 식별, 요구사항 접수부터 배포까지의 리드 타임(Lead Time) 단축 |

## Ⅱ. 핵심 특징

고정된 타임박스(스프린트) 없이도 자율적 풀(Pull) 방식을 통해 연속적인 가치 흐름을 실현.

| 6대 핵심 실천 원칙 | 실천 내용 및 메커니즘 | 실무 적용 방안 |
|---|---|---|
| **1. 워크플로우 시각화 (Visualize)** | 업무의 접수부터 배포까지의 모든 단계와 대기열을 보드에 표현 | 물리적/디지털 칸반 보드(Jira 등)에 열(Column) 구성 |
| **2. 진행 중 작업 제한 (Limit WIP)** | 공정별로 동시에 다룰 수 있는 최대 티켓 수를 명시적 숫자로 제한 | 개발 [3], 코드리뷰 [2], QA [2] 등 상한선 설정 |
| **3. 흐름 관리 (Manage Flow)** | 작업이 지연되거나 멈추지 않고 원활하게 흘러가도록 지속 추적 | 사이클 타임 측정 및 지연 티켓 블로커(Blocker) 해소 |
| **4. 프로세스 정책 명시화 (Explicit Policies)** | 작업이 다음 단계로 이동하기 위한 명확한 기준과 규칙 정의 | 완료의 정의(DoD), 서비스 수준 합의(SLA) 보드 게시 |
| **5. 피드백 루프 구현 (Feedback Loops)** | 정기적인 스탠드업 미팅과 회고를 통해 흐름 데이터 검토 | 일일 칸반 미팅(15분), 주간 인도 계획 및 회고 회의 |
| **6. 협업을 통한 진화 (Improve & Evolve)** | 과학적 측정 지표를 바탕으로 프로세스를 점진적·지속적으로 실험 개선 | 카이젠(Kaizen) 철학에 기반한 공정 재조정 |

## Ⅲ. 체계·프로세스

칸반 보드의 WIP Limit 제어 체계와 리틀의 법칙에 기반한 흐름 관리 구조.

```text
[칸반 보드 WIP Limit 및 흐름 제어 아키텍처]
[백로그]           [분석/설계]           [개발 진행]             [코드 리뷰]           [통합 QA]       [완료]
   Backlog          Analysis (WIP: 2)     Dev (WIP: 3)          Review (WIP: 2)       QA (WIP: 2)       Done
  +─────────+       +───────────────+     +───────────────+     +───────────────+     +───────────+    +─────+
  | Task A  |       | [Task 1]      |     | [Task 3]      |     | [Task 5] (병목) |     | [Task 7]  |    | Fin |
  | Task B  | ────> | [Task 2]      | ──> | [Task 4]      | ──> | [Task 6] (병목) | ──> | [Task 8]  | ──>| ... |
  | Task C  |       |               |     | [빈 슬롯]     |     +───────────────+     +───────────+    +─────+
  +─────────+       +───────────────+     +───────────────+             ▲
                                                  │                     │ WIP=2 포화 상태!
                                                  └─────────────────────┘ (신규 진입 차단 & PUSH 금지)

  * [스워밍(Swarming) 협업 규칙]
    리뷰 컬럼이 포화되면 개발자는 신규 작업을 시작하지 않고(Stop Starting), 리뷰 병목 해소에 동참(Start Finishing)
```

- **리틀의 법칙(Little's Law)과 흐름 제어 공식**:
  $$\text{Lead Time} = \frac{\text{WIP (진행 중 작업 수)}}{\text{Throughput (처리량)}}$$
  - 처리량(Throughput)이 팀의 고유 역량으로 일정할 때, **WIP를 낮추면 리드 타임이 정비례하여 감소** 하는 효과 발생.
  - WIP 상한이 없을 경우 병목 공정 앞단에 대기열(Queue)이 무한정 누적되어 리드 타임이 폭증하고 멀티태스킹으로 인한 품질 저하 발생.

## Ⅳ. 종류·비교

#### 칸반(Kanban) vs 스크럼(Scrum) 상세 비교

| 비교 항목 | 칸반 (Kanban) | 스크럼 (Scrum) |
|---|---|---|
| **기본 철학** | 린(Lean) 생산 방식 기반의 지속적 흐름 | 애자일 선언 기반의 타임박스 반복 점증 개발 |
| **반복 주기** | **고정 주기 없음 (연속적 흐름, Continuous Flow)** | **고정된 스프린트 (1~4주 타임박스)** |
| **핵심 통제 도구** | **WIP (진행 중 작업) 상한선 제한** | **스프린트 백로그 및 타임박스 약속** |
| **역할 및 직무** | 별도 규정 없음 (기존 팀 역할 및 명칭 유지) | 제품 책임자(PO), 스크럼 마스터(SM), 개발팀 |
| **변경 수용성** | WIP 여유 슬롯 발생 시 언제든 신규 작업 인입 가능 | 스프린트 진행 중에는 목표를 흔드는 변경 인입 지양 |
| **인도 단위** | 기능 단위 완료 즉시 지속적 배포 (CD) | 스프린트 종료 시 잠재적으로 출시 가능한 제품 증분 |
| **핵심 측정 지표** | 리드 타임, 사이클 타임, CFD(누적 흐름도) | 스프린트 속도(Velocity), 번다운 차트(Burndown) |
| **적합한 프로젝트**| 시스템 운영 및 유지보수, DevOps, 긴급 장애 대응 | 요구사항이 유동적이고 비즈니스 검증이 필요한 신규 개발 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| WIP 한도를 설정해 두고도 긴급 업무(Urgent Ticket)를 이유로 예외를 남발하여 보드 통제력 상실 | 긴급 장애 전용의 단일 패스트트랙 레인(Expedite Lane, WIP=1)을 신설하고 엄격한 진입 기준 수립 |
| 특정 공정(QA 등)에 지속적인 병목이 발생하여 이전 단계 작업자들이 유휴 상태(Idle)에 빠지는 현상 | 교차 기능 팀(Cross-functional Team) 훈련 및 페어 프로그래밍/스워밍을 통해 병목 구간 지원 체계 가동 |
| 칸반 보드를 단순한 To-Do 목록 시각화 용도로만 활용하고 정량적 흐름 개선 메트릭 관리 미흡 | 누적 흐름도(CFD)와 사이클 타임 산점도를 주간 단위로 분석하여 대기 시간 이상치를 주기적으로 추적 |

## Ⅵ. 제언

칸반의 성공적 정착을 위해서는 스프린트 계획의 예측성과 칸반의 흐름 유연성을 결합한 스크럼반(Scrumban) 하이브리드 모델을 도입하고, 누적 흐름도(CFD) 기반의 데이터 주도 병목 개선 루프를 확립할 필요가 있음.

```text
[PO 요구 접수] ──> [우선순위화 (스프린트 백로그)] ──> [칸반 보드 실행 (WIP 제한)] ──> [CFD 병목 분석 및 회고]
                     (스크럼의 계획성 활용)              (칸반의 지속 흐름 & 풀)           (지속적 프로세스 카이젠)
```

| 운영 영역 | 핵심 거버넌스 지침 | 정량 관리 지표 |
|---|---|---|
| **WIP 최적화** | 팀원 수 대비 $1.5 \times \text{인원수}$ 수준에서 시작하여 점진 하향 조정 | 작업 중단율(Blocker Rate) 10% 미만 관리 |
| **흐름 모니터링** | CFD 밴드 폭의 평행성 유지 점검 (벌어지면 병목 발생 신호) | 평균 사이클 타임(Cycle Time) 3일 이내 단축 |
| **배포 자동화** | 완료의 정의(DoD) 충족 시 즉각 배포되는 CI/CD 파이프라인 연계 | 배포 빈도(Deployment Frequency) 주 5회 이상 달성 |
