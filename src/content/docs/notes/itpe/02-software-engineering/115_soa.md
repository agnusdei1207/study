## 연관 키워드

- SOA, 서비스 지향 아키텍처, 느슨한 결합, 서비스 계약, ESB, UDDI, 오케스트레이션, 재사용성

## Ⅰ. SOA의 개요

- 핵심 요약 : SOA는 업무 기능을 계약 기반의 독립 서비스로 정의·조합해 전사 시스템의 재사용·연계를 체계화하는 아키텍처 접근.
- 개념 : 업무 기능을 표준 계약과 메시지 교환으로 연결되는 독립 서비스로 구성하는 설계 방법인 서비스 지향 아키텍처 (**SOA**, Service-Oriented Architecture).
- 배경 및 필요성 : 부서·플랫폼별로 분리된 정보 시스템에서 같은 기능의 반복 구현과 이기종 연계 비용이 누적되어, 기능 단위의 공유·재조립 필요.
- 주요 목적 : 재사용성·상호 운용성 확보, 변경 영향의 서비스 경계 내 국소화, 업무 프로세스와 IT 시스템의 정렬.

## Ⅱ. SOA의 특징 및 장점

- 핵심 요약 : 느슨한 결합·명시적 계약·발견·조합의 서비스 지향 원칙이 중복 제거와 유연한 업무 재구성으로 연결.

1. **느슨한 결합** (Loose Coupling) : 서비스가 인터페이스 계약 외의 내부 구현에 의존하지 않음 → 제공자 변경이 소비자로 전파되지 않는 구조.
2. 명시적 **서비스 계약** (Service Contract) : **WSDL** (Web Services Description Language) 등으로 입력·출력·오류·정책을 문서화 → 제공자·소비자의 독립 개발 가능.
3. 발견과 재사용성 : **UDDI** (Universal Description, Discovery and Integration) 레지스트리에 서비스 등록·검색 → 중복 개발 방지와 전사 자산화.
4. 표준 메시지 상호 운용성 : **SOAP** (Simple Object Access Protocol) 메시지로 이기종 플랫폼 간 호출 규약 통일 → 플랫폼 중립적 연계.
5. 조합과 **오케스트레이션** (Orchestration) : 개별 서비스를 업무 흐름 순서로 호출·조립 → 프로세스 변경 시 서비스 재조합으로 대응.

## Ⅲ. SOA의 구조 (흐름)

- 핵심 요약 : 소비자가 레지스트리에서 서비스를 발견하고 계약 기반으로 호출하며, 통합 계층과 프로세스 조합이 복합 업무를 조정.

```text
서비스 소비자
   ↓ 1. 서비스 검색
UDDI 레지스트리 - 계약·위치 반환
   ↓ 2. 계약 기반 호출
ESB - 라우팅·변환·보안 중계
   ↓ 3. 실행
서비스 제공자 - SOAP 메시지 처리
```

```text
업무 프로세스 정의(BPEL)
   ↓ 순서·분기·병렬 지정
서비스 A 호출
   ↓ 결과 전달
서비스 B·C 호출
   ↓ 결과 조합
업무 결과 반환
```

- **ESB** (Enterprise Service Bus)는 라우팅·프로토콜 변환·보안을 중계하는 통합 계층으로, SOA의 필수 조건은 아니지만 전사 연계의 대표 구현 수단.
- BPEL(Business Process Execution Language)은 서비스 호출 순서를 프로세스로 기술하는 오케스트레이션 언어.

## Ⅳ. SOA와 모놀리식 통합의 비교

- 핵심 요약 : 모놀리식 통합이 단일 애플리케이션 내부 결합에 의존하는 반면, SOA는 계약 기반 서비스 호출로 재사용·연계를 구조화.

| 비교 축 | SOA | 모놀리식 통합 |
| --- | --- | --- |
| 결합 단위 | 계약 기반 서비스 호출 | 단일 애플리케이션 내부 모듈 결합 |
| 재사용 범위 | 전사 서비스 공유·조합 | 해당 애플리케이션 내부 |
| 기술 이종성 | 표준 메시지로 이기종 연계 | 단일 기술 스택 전제 |
| 변경 영향 | 서비스 경계 내 국소화 | 전체 재배포·회귀 시험 필요 |
| 확장 방식 | 서비스 추가·조합 | 애플리케이션 단위 확장 |

- 후속 발전형인 마이크로서비스 아키텍처(**MSA**, Microservice Architecture)는 SOA의 서비스 지향 원칙을 더 작은 배포 단위·경량 통신으로 세분화한 접근이며, 중앙 통합 계층 대신 경량 게이트웨이를 선호하는 경향으로 구분.

## Ⅴ. SOA의 한계와 방안

- 핵심 요약 : 중앙 통합 계층 의존·계약 불일치·메시지 오버헤드는 이중화·계약 관리·경량화 정책으로 통제 필요.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| ESB 병목·단일 장애 | 모든 연계가 중앙 계층 집중 | 이중화·용량 관리·직접 경량 연계 병행 | 통합 계층 가용성·지연 |
| 서비스 경계 불명확 | 조직도 기준의 기계적 분리 | 업무 도메인·변경 단위 기준 재설계 | 경계 변경 빈도 |
| 계약 버전 불일치 | 스키마·오류 의미의 비호환 | 하위 호환 정책·계약 시험·영향 통지 | 계약 위반 건수 |
| SOAP 오버헤드 | XML 변환·검증 비용 누적 | 경량 포맷 검토·불필요 변환 제거 | 메시지 변환 지연 |
| 분산 호출 장애 | 지연·타임아웃·부분 실패 | 타임아웃·재시도·보상 처리 설계 | 호출 실패율 |

## Ⅵ. SOA에 대한 기술사적 제언

- 핵심 요약 : 전사 아키텍처 거버넌스로 서비스 카탈로그·소유자·계약 버전을 체계화하고 도메인 중심 경계로 진화 준비 필요.
- 아키텍처 위원회는 서비스 카탈로그에 소유자·계약 버전·보안 등급·폐기 계획을 등록·공개하는 서비스 거버넌스 절차 운영.
- 도메인 주도 설계(**DDD**, Domain-Driven Design)의 경계 도출 기법을 서비스 경계 설계에 반영해 이후 MSA 전환의 기반 마련.

## Ⅶ. 결론

- 핵심 요약 : SOA는 업무 기능을 계약으로 정의·조합해 전사 시스템의 재사용성과 상호 운용성을 높이는 아키텍처 접근.
- 서비스 경계와 운영 책임의 명확성이 통합 복잡성 관리의 성패를 결정.
