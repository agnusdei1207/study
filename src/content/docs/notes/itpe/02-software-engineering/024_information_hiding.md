## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 아키텍처·설계 → **정보은닉(Information Hiding)**

## 30초 인출

- 본질: 변경 가능성이 높은 내부 구현 상세(자료구조, 알고리즘, 환경 의존성)를 모듈 내부에 비밀로 감추고 안정적인 공개 인터페이스만 노출하는 데이비드 파나스(David Parnas)의 모듈 분할 원리
- 메커니즘: 모듈별 비밀(Secret) 정의 → 캡슐화 및 접근 제어자(`private`) 적용 → 공개 계약(Public Interface) 통신을 통한 파급 효과(Ripple Effect) 차단
- 통찰: 무분별한 Getter/Setter 남발로 인한 내부 상태 누출이 유지보수 악화를 초래하므로 도메인 행위 중심의 인터페이스 설계와 계층별 경계 격리 규약 정립 필요

<details>
<summary>핵심 용어</summary>

- **Information Hiding(정보은닉)** : 모듈 내부의 복잡한 구현이나 변경되기 쉬운 설계 결정을 비밀(Secret)로 유지하여 외부로부터 숨기는 원칙
- **Encapsulation(캡슐화)** : 연관된 데이터와 행위를 하나의 논리적 단위로 묶고 접근 제어자를 통해 정보은닉을 물리적으로 구현하는 기제
- **Public Interface(공개 인터페이스)** : 모듈이 외부와 통신할 수 있도록 공개한 최소한의 명세이자 계약 규격
- **Ripple Effect(파급 효과)** : 한 모듈의 내부 구조 변경 시 의존 관계에 있는 다른 모듈까지 연쇄적으로 수정이 강제되는 결합 부작용
- **Parnas Principles** : 제어 흐름 순서가 아닌 변경 가능성이 높은 결정사항(비밀)을 기준으로 시스템을 분할하라는 데이비드 파나스의 분할 원칙

</details>

## 2~4교시 25점 답안

## Ⅰ. 정보은닉의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 변경될 가능성이 높은 설계 결정(자료구조, 알고리즘, 하드웨어 종속성)을 모듈 내부에 감추고, 안정적인 공개 계약(인터페이스)만을 제공하는 소프트웨어 모듈 분할 설계 원리 |
| 목적 | 모듈 간 결합도 최소화, 내부 구현 변경 시 외부 파급 효과 차단 및 독립적 병행 개발 지원 |

## Ⅱ. 정보은닉의 핵심 특징

| 특징 | 의미 |
|---|---|
| 변경 격리성 | 모듈 내부의 자료 표현이나 알고리즘이 수정되어도 외부 호출부의 코드 변경을 완전 배제 |
| 인터페이스 안정성 | 클라이언트는 내부 구현이 아닌 추상화된 공개 메서드 시그니처에만 의존하여 결합도 감소 |
| 독립적 유지보수 | 각 모듈의 내부 복잡도를 캡슐화하여 개발자가 모듈 내부 코드에만 집중할 수 있는 인지 부하 경감 |

## Ⅲ. 파나스의 모듈 분할 원칙과 정보은닉 체계

### 파나스(Parnas)의 모듈 분할 메커니즘과 파급 효과 차단 구조

```text
[외부 클라이언트 모듈 A]        [외부 클라이언트 모듈 B]
           │                                │
           │ 호출 (Public Contract)         │ 호출 (Public Contract)
           ▼                                ▼
┌────────────────────────────────────────────────────────┐
│               [공개 인터페이스 (Public Interface)]      │
└───────────────────────────┬────────────────────────────┘
                            │ 위임 (Delegation)
┌───────────────────────────▼────────────────────────────┐
│                    [모듈 내부 경계]                    │
│                                                        │
│  [비밀 1: 자료구조]           [비밀 2: 알고리즘]        │
│  - 배열 / B-Tree / 해시맵     - 정렬 알고리즘 / 암호화  │
│  (Private State)              (Private Logic)          │
│                                                        │
│  [비밀 3: 플랫폼 의존성]       [비밀 4: DB 연동 상세]    │
│  - OS 시스템 콜 / 하드웨어    - SQL 쿼리 / ORM 매핑     │
│                                                        │
│  ★ 내부 수정 발생 시: 변경 범위가 모듈 내부로 국소화    │
└────────────────────────────────────────────────────────┘
```

### 모듈 내부에 격리해야 할 4대 핵심 비밀과 설계 가이드

| 비밀(Secret) 유형 | 주요 대상 요소 | 정보은닉 적용 가이드 |
|---|---|---|
| **자료구조의 비밀** | 배열, 링크드리스트, 해시맵, 내부 DTO 구조 | 컬렉션 직접 반환 금지, 불변 객체(Unmodifiable) 또는 행위 메서드로 캡슐화 |
| **알고리즘의 비밀** | 수치 계산 공식, 검색/정렬 로직, 암호화 처리 | 전략 패턴(Strategy Pattern) 등을 적용하여 세부 알고리즘 교체 시 클라이언트 격리 |
| **하드웨어 및 OS 비밀** | 장치 드라이버, 소켓 통신 규격, 파일 시스템 제어 | 추상화 계층(HAL)을 두어 저수준 OS API 호출 코드를 별도 어댑터로 격리 |
| **외부 의존성의 비밀** | RDBMS 스키마, 서드파티 라이브러리, 원격 API | 리포지토리(Repository) 및 인터페이스 계층을 통해 벤더 기술 종속성 은닉 |

## Ⅳ. 정보은닉(Information Hiding)과 캡슐화(Encapsulation) 비교

### 두 개념 간의 본질적 차이 및 상관관계

| 비교 항목 | 정보은닉 (Information Hiding) | 캡슐화 (Encapsulation) |
|---|---|---|
| **개념적 위상** | 아키텍처적 **원리 및 설계 철학 (Why)** | 객체지향 프로그래밍 **구현 메커니즘 (How)** |
| **핵심 목적** | 변경 취약점을 감추어 파급 효과(Ripple Effect) 최소화 | 연관된 데이터와 행위를 묶고 외부 직접 접근 통제 |
| **구현 수단** | 모듈 분할 설계, 추상화 계약, 인터페이스 분리 원칙 | 클래스(Class), 패키지, 접근 제어자(`private`, `protected`) |
| **적용 범위** | 객체지향, 함수형, MSA, 분산 시스템 등 전반 | 주로 객체지향 언어의 클래스 및 모듈 단위 문법 |
| **상호 관계** | 캡슐화는 정보은닉을 구현하기 위한 핵심 프로그래밍 수단 | 정보은닉이 달성되지 않은 캡슐화는 단순 데이터 묶음에 불과 |

### 정보은닉 수준에 따른 품질 특성 비교

| 소프트웨어 품질 축 | 정보은닉 준수 시 효과 | 정보은닉 위반 시 위험 (안티패턴) |
|---|---|---|
| **결합도 (Coupling)** | 인터페이스 기반 통신으로 모듈 간 느슨한 결합 달성 | 타 모듈의 내부 필드/자료형에 직접 엮여 강한 결합 발생 |
| **응집도 (Cohesion)** | 단일 책임을 가진 비밀을 중심으로 기능이 결집됨 | 내부 데이터 처리가 외부 모듈에 분산되어 응집도 저하 |
| **테스트 용이성** | 모의 객체(Mock)를 활용한 단위 테스트 및 계약 테스트 용이 | 내부 상태에 결합되어 테스트 코드 작성이 극도로 곤란 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 무분별한 Getter/Setter 남발로 인한 내부 상태의 외부 노출(캡슐화 파괴) | '묻지 말고 시켜라(Tell, Don't Ask)' 원칙을 적용하여 행위 중심 메서드만 노출 |
| 과도한 계층화 및 인터페이스 분리로 인한 간접 호출 오버헤드와 복잡성 증가 | 변경 가능성이 낮은 도메인은 직접 참조하고 변경 빈번 영역에 선별적 인터페이스 적용 |
| 마이크로서비스 간 공통 데이터베이스 공유로 인한 스키마 수준 정보은닉 실패 | 각 서비스별 독립 Database per Service 패턴을 강제하고 전용 API로만 데이터 교환 |

## Ⅵ. 제언

도메인 주도 설계(DDD)의 애그리게잇(Aggregate) 패턴 및 아키텍처 피트니스 함수(Fitness Function)를 통한 지속적 정보은닉 거버넌스

### 아키텍처 피트니스 함수 기반 정보은닉 검증 파이프라인

```text
[개발자 코드 작성]
       ↓
[Git 커밋 및 PR 생성]
       ↓
[CI 파이프라인 정적 분석 실행]
       ├─ ArchUnit: 패키지 간 private/internal 의존성 규칙 검증
       ├─ SonarQube: 무분별한 Public 필드 및 Getter/Setter 오용 탐지
       └─ JDepend: 패키지 순환 참조 및 결합도(Afferent/Efferent) 측정
       ↓
[아키텍처 규칙 위반 시 빌드 실패 및 머지 차단]
```

### 정보은닉 적용을 위한 모듈 분할 의사결정 체계

```text
시스템 기능 요구사항 분석
       ↓
변경 가능성이 높은 설계 결정 식별 (자료구조, 알고리즘, 외부 연계)
       ↓
[결정 사항이 변경 빈번한 영역인가?]
       ├─ 예 ──→ [비밀로 격리] → Private 접근자 부여 → 행위 기반 인터페이스 정의
       └─ 아니오 ─→ 직접 모듈에 포함하여 불필요한 추상화 비용 제거
```

### 선택 근거: 전통적 구조적 분할과 정보은닉 기반 객체지향 분할 비교

| 구분 | 기능 중심 분할 (전통적 방식) | 제언: 정보은닉 중심 분할 (현대적 방식) |
|---|---|---|
| 분할 기준 | 시간 순서 및 업무 처리 흐름(Flowchart) 기준 | 변경 가능성이 높은 시스템의 비밀(Secret) 기준 |
| 자료구조 공유 | 대형 전역 변수 및 공유 데이터베이스 접근 | 모듈 내부 격리 및 공개 인터페이스를 통한 제어 |
| 변경 파급도 | 자료구조 변경 시 전체 함수 수정 불가피 | 인터페이스 불변 시 모듈 내부만 수정하여 리스크 격리 |
