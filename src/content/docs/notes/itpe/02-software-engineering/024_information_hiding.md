## 연관 키워드
- 정보은닉, Parnas 원리, 캡슐화, 모듈 응집도, 결합도, 변경 영향

### Ⅰ. 정보은닉의 개요

- 핵심 요약 : 정보은닉은 모듈의 설계 결정과 변경 가능성이 높은 구현 세부를 외부에 숨기는 모듈화 원칙.
- 개념 : Parnas의 원리에 따라 각 모듈은 다른 모듈이 알 필요 없는 설계 결정의 비밀을 감추고 안정된 인터페이스만 제공(**정보은닉**, Information Hiding).
- 배경 및 필요성 : 구현 세부를 공유하면 변경이 여러 컴포넌트로 전파되어 수정·시험 비용이 커짐.
- 주요 목적 : 변경 영향을 경계 안에 가두고 모듈 간 결합을 낮춤.

### Ⅱ. 정보은닉의 특징 및 장점

- 핵심 요약 : 변하기 쉬운 결정은 모듈 내부에 두고 외부에는 필요한 계약만 공개.

1. 변화 격리 : 자료구조·알고리즘·외부 공급자 변경을 모듈 안에 국한 → 변경 파급 축소.
2. 인터페이스 안정성 : 공개 연산과 불변조건을 계약으로 유지 → 구현 교체 용이.
3. 응집도·결합도 : 관련 책임을 모듈에 묶고 표현 세부 의존을 차단 → 병렬 개발·시험성 향상.

### Ⅲ. 정보은닉 적용 구조 (흐름)

- 핵심 요약 : 외부 계약은 안정적으로 유지하고 변동 가능성이 높은 결정은 구현 모듈 내부에서 교체.

```text
클라이언트 → 공개 인터페이스(계약)
                    ↓
              모듈 경계
       ┌───────────┴───────────┐
       자료구조·정책·알고리즘·공급자 구현
```

```text
요구 변화 감지 → 변동 결정 식별 → 모듈 경계 설정
        → 인터페이스·불변조건 명세 → 내부 구현 교체·회귀시험
```

- 적용 대상 : 데이터 표현, 외부 API, 저장소 접근, 정책·알고리즘, 플랫폼 종속 코드.

### Ⅳ. 정보은닉과 캡슐화 비교

- 핵심 요약 : 정보은닉은 무엇을 숨길지 정하는 설계 원칙, 캡슐화는 상태·연산을 경계 안에 묶는 구현 기법.

| 비교 축 | 정보은닉 | 캡슐화 |
|---|---|---|
| 초점 | 변경 가능 설계결정의 비공개 | 데이터와 연산의 단위화·접근제어 |
| 질문 | 어떤 설계결정을 외부에서 몰라도 되게 할까 | 상태·연산을 어떻게 묶고 접근시킬까 |
| 관계 | 인터페이스·모듈 분해의 원칙 | 정보은닉을 구현하는 주요 수단 |

### Ⅴ. 정보은닉의 한계와 방안

- 핵심 요약 : 과도한 은닉은 추상화·간접호출 비용을 늘리므로 실제 변경 가능성과 계약 필요성에 맞춰 경계를 둠.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 과도한 추상화 | 이해·호출 추적 복잡 | 변화 가능성이 높은 결정부터 경계화 | 추상화 깊이 |
| 빈약한 인터페이스 | 필요한 동작을 제공하지 못함 | 사용 사례·불변조건에 맞춰 계약 설계 | 인터페이스 누락 |
| 누설된 구현 세부 | 클라이언트가 내부 표현에 결합 | DTO·어댑터·계약 테스트로 의존 차단 | 내부 의존 건수 |

### Ⅵ. 정보은닉 설계 제언

- 핵심 요약 : 아키텍트는 변경 이유가 다른 책임과 외부 의존성을 경계로 분리하고 공개 계약을 버전 관리.

1. 설계자는 변동성·변경 빈도·장애 격리를 기준으로 모듈 경계를 정함.
2. 개발팀은 구현 세부를 API·도메인 모델 밖으로 노출하지 않고 계약 테스트 유지.
3. 아키텍처 리뷰는 공급자·DB·정책 변경을 모듈 경계 안에서 수용하는지 검증.

### Ⅶ. 결론

- 핵심 요약 : 정보은닉은 구현의 비밀을 모듈 경계 안에 두어 설계변경을 국소화하는 원칙.
- 시사점 : 은닉 경계는 복잡성을 감추는 목적이 아니라 변화 전파와 결합을 줄이는 목적에 맞춰야 함.
