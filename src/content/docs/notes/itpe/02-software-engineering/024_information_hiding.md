## Ⅰ. 정보은닉의 개요

- **개념** : 데이비드 파나스(David Parnas)가 1972년에 제안한 소프트웨어 설계의 근본 원리로, 모듈 내부의 구체적인 구현 세부사항(자료구조, 알고리즘)을 외부에 감추고, 안정적인 공개 인터페이스(Public Interface)만을 노출하는 공학적 기법.
- **배경 및 필요성** : 소프트웨어의 변경이 다른 모듈로 파급되는 연쇄 수정(파급 효과, Ripple Effect)을 방지하고, 모듈 간 결합도를 낮추어 유지보수성과 독립성을 보장.
- **핵심 목표** : 높은 응집도와 낮은 결합도 달성, 모듈 내부 변경의 독립성 확보, 복잡성 억제.

## Ⅱ. 정보은닉의 구조적 메커니즘 및 캡슐화와의 관계

```text
   [ 외부 클라이언트 모듈 ]
          │
          │ 오직 공개 인터페이스(Public Method)만을 통해 호출
          ▼
   ┌──────────────────────────────────────────────┐
   │                [ 모듈 / 클래스 ]              │
   │  ┌────────────────────────────────────────┐  │
   │  │ Public Interface (공개된 규약)         │  │
   │  └──────────────────┬─────────────────────┘  │
   │                     │ (내부 위임)            │
   │  ┌──────────────────▼─────────────────────┐  │
   │  │ Private Hidden Implementation          │  │
   │  │ - 내부 자료구조 (배열 -> 트리로 변경 무관) │  │
   │  │ - 세부 알고리즘 및 민감 상태 변수      │  │
   │  └────────────────────────────────────────┘  │
   └──────────────────────────────────────────────┘
```

- **캡슐화(Encapsulation)와의 관계** : 캡슐화는 데이터와 그 데이터를 조작하는 메서드를 하나의 논리적 단위로 묶는 '수단'이며, 정보은닉은 그 캡슐화된 내부의 세부 구현을 감추는 '설계 철학 및 목적'에 해당.
- **접근 제한자(Access Modifier)** : private, protected, public 키워드를 통해 언어 차원에서 정보은닉 규칙을 강제.

## Ⅲ. 정보은닉 적용 유무에 따른 시스템 속성 비교

| 비교 관점 | 정보은닉 미적용 (직접 참조) | 정보은닉 철저 적용 (인터페이스 참조) |
|---|---|---|
| 결합도 (Coupling) | 내용 결합도(Content Coupling), 극도로 높음 | 데이터/스탬프 결합도, 매우 낮음 |
| 구현 변경 영향도 | 내부 자료구조 변경 시 전체 호출자 코드 수정 불가피 | 인터페이스 불변 시 내부 변경이 외부에 전혀 무영향 |
| 테스트 용이성 | 내부 상태가 외부에서 오염되어 결함 추적 난해 | 인터페이스 기반 Mock 객체 생성을 통한 격리 테스트 용이 |
| 코드 보안성 | 민감 필드에 대한 무단 조작 및 유효하지 않은 상태 발생 | Setter/메서드 내 유효성 검증(Validation)을 통한 상태 무결성 보장 |

## Ⅳ. 현대 소프트웨어 아키텍처에서의 기술사적 제언

- **모듈러 모놀리스 및 헥사고날 아키텍처(Ports & Adapters)로의 확장** : 정보은닉의 개념은 클래스 수준에 머무르지 않고, 도메인 비즈니스 로직을 중심에 두고 외부 DB나 웹 프레임워크를 포트 뒤로 숨기는 클린 아키텍처의 핵심 기반으로 확장 적용되어야 함.
- **불필요한 Getter/Setter 남발(Anemic Domain Model) 지양** : 모든 필드에 무의식적으로 Getter/Setter를 개방하면 정보은닉이 완전히 무력화되므로, 객체에게 메시지를 던져 일을 시키는 'Tell, Don\'t Ask' 원칙을 준수해야 함.
