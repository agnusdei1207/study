## 연관 키워드

- 정보은닉(Information Hiding), David Parnas, 캡슐화(Encapsulation), 공개 인터페이스(Public Interface)
- 결합도(Coupling), 응집도(Cohesion), 접근 제한자(Access Modifier), Tell, Don't Ask

## Ⅰ. 정보은닉의 개요

- 핵심 요약 : 모듈의 내부 구현을 감추고 안정적인 공개 인터페이스만 노출하는 소프트웨어 설계의 근본 원리.
- 개념 : 데이비드 파나스(David Parnas)가 1972년 제시한 설계 원리로, 자료구조와 알고리즘 같이 바뀔 가능성이 큰 구현 세부사항을 모듈 안에 감추고 공개 인터페이스만 드러내는 기법 (**정보은닉**, Information Hiding).
- 배경 및 필요성 : 내부 변경이 다른 모듈로 번지는 파급 효과(Ripple Effect)를 막고 모듈 간 결합도를 낮춰야 유지보수성과 독립성을 지킬 수 있음.
- 핵심 목표 : 높은 응집도와 낮은 결합도를 달성하고, 모듈 내부 변경의 독립성을 확보하며, 시스템의 복잡성을 억제.

## Ⅱ. 정보은닉의 특징 및 장점

- 핵심 요약 : 바뀔 가능성이 큰 결정을 모듈 안에 격리하고 접근 제한자로 강제해 변경 독립성을 얻는 방식.

1. 설계 결정의 격리 : 자료구조나 알고리즘처럼 변경 가능성이 큰 결정을 모듈 내부에 둠 → 해당 결정이 바뀌어도 외부는 영향을 받지 않음.
2. 인터페이스 계약 : 공개 메서드만을 통한 상호작용 규약을 세움 → 호출자가 구현 방식에 기대지 않아 안정적인 연동이 가능.
3. 캡슐화와의 관계 : 캡슐화(Encapsulation)는 데이터와 동작을 한 단위로 묶는 수단이고, 정보은닉은 내부를 감추는 목적임 → 캡슐화를 수단으로 삼아 정보은닉을 달성.
4. 접근 제한자 강제 : private, protected, public으로 은닉 규칙을 언어 차원에서 강제 → 규칙 위반을 컴파일 단계에서 잡을 수 있음.
5. 파급 효과 최소화 : 내부 구현 변경이 외부 모듈에 전파되지 않음 → 변경 비용과 회귀 테스트 범위가 줄어듦.

## Ⅲ. 정보은닉의 구조 (흐름)

- 핵심 요약 : 외부는 공개 인터페이스만 호출하고, 내부 구현은 그 뒤에서 위임받아 처리하는 구조.

```text
[ 정보은닉 모듈 구조 ]

외부 클라이언트 모듈
      ↓ 공개 메서드로만 호출
Public Interface (공개 규약)
      ↓ 내부 위임
Private Implementation (은닉)
  내부 자료구조, 세부 알고리즘,
  민감한 상태 변수
```

```text
[ 변경 파급 흐름 비교 ]

은닉 미적용
  자료구조 변경 → 호출자 전체 수정
  → 파급 효과 발생

은닉 적용
  자료구조 변경 → 인터페이스 불변
  → 외부 모듈 무영향
```

## Ⅳ. 정보은닉 적용 유무에 따른 속성 비교

- 핵심 요약 : 은닉을 철저히 적용하면 결합도가 낮아지고 변경 영향과 테스트 난도가 줄어들며 상태 무결성이 보장됨.

| 비교 관점 | 은닉 미적용 (직접 참조) | 은닉 철저 적용 (인터페이스 참조) |
| --- | --- | --- |
| 결합도 (Coupling) | 내용 결합도로 매우 높음 | 자료 결합도 중심으로 낮음 |
| 구현 변경 영향도 | 내부 자료구조 변경 시 호출자 전체 수정 필요 | 인터페이스가 같으면 외부 영향 없음 |
| 테스트 용이성 | 내부 상태가 외부에서 오염되어 결함 추적이 어려움 | 인터페이스 기반 목(Mock) 객체로 격리 테스트 가능 |
| 상태 무결성 | 민감 필드의 무단 조작과 무효 상태 발생 가능 | 메서드 안에서 유효성 검증을 거쳐 상태 보장 |

## Ⅴ. 정보은닉의 한계와 방안

- 핵심 요약 : 기계적 캡슐화의 보일러플레이트, 리플렉션을 통한 우회, 추상화 누수가 주요 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 보일러플레이트 증가 | 모든 필드를 기계적으로 비공개화하고 Getter·Setter를 남발 → 가독성 저하 | 단순 전달 객체는 불변 DTO나 레코드로 작성, 상태 조회 대신 행위 중심 메서드 설계(Tell, Don't Ask) | Getter·Setter 개수 |
| 리플렉션 우회 | 리플렉션이나 메모리 직접 조작으로 비공개 상태를 강제 변경 → 무결성 파손 | 모듈 시스템(JPMS)으로 패키지 노출 제한, 방어적 복사와 불변 객체 적용 | 리플렉션 접근 탐지 건수 |
| 추상화 누수 | 내부 자료구조나 예외 타입이 시그니처로 노출 → 내부 변경이 외부로 전파 | 변경 가능성이 큰 결정을 모듈 내부에 완전히 격리, 표준 인터페이스만 노출 | 인터페이스 변경에 따른 연쇄 수정 건수 |

## Ⅵ. 현대 소프트웨어 아키텍처에 대한 기술사적 제언

- 핵심 요약 : 정보은닉을 클래스 수준에서 아키텍처 수준으로 넓히고, 빈약한 도메인 모델을 경계하는 방향.
- 아키텍처 경계로의 확장 : 헥사고날 아키텍처(Ports & Adapters)처럼 도메인 로직을 중심에 두고 데이터베이스나 웹 프레임워크를 포트 뒤로 숨겨, 정보은닉을 모듈 경계 설계의 원리로 적용한다.
- 빈약한 도메인 모델의 경계 : 모든 필드를 Getter와 Setter로 열어 두는 방식은 은닉을 무력화하므로, 객체에 행위를 요청하는 방식으로 설계한다.
- 설계 규약의 리뷰 편입 : 접근 제한자 사용 기준과 모듈 경계 규칙을 팀 규약으로 정하고, 코드 리뷰 항목에 포함한다.

## Ⅶ. 결론

- 핵심 요약 : 정보은닉은 변경 독립성을 보장하는 설계의 기본 원리이자 현대 아키텍처의 토대.
- 시사점 : 캡슐화를 수단으로 삼고 정보은닉을 목적으로 삼을 때 낮은 결합도와 높은 응집도가 함께 확보됨.
