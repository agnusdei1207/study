## 연관 키워드

- 정보은닉(Information Hiding), David Parnas, 캡슐화(Encapsulation), 공개 인터페이스(Public Interface)
- 결합도(Coupling), 응집도(Cohesion), 접근 제한자(Access Modifier), Tell, Don't Ask

## Ⅰ. 정보은닉의 개요

- 핵심 요약 : 모듈 내부 구현 세부사항을 감추고 안정적인 공개 인터페이스만 노출하는 소프트웨어 설계의 근본 원리.
- 개념 : 데이비드 파나스(David Parnas)가 1972년에 제안한 소프트웨어 설계의 근본 원리로, 모듈 내부의 구체적인 구현 세부사항(자료구조, 알고리즘)을 외부에 감추고 안정적인 공개 인터페이스(Public Interface)만을 노출하는 공학적 기법.
- 배경 및 필요성 : 소프트웨어의 변경이 다른 모듈로 파급되는 연쇄 수정(파급 효과, Ripple Effect)을 방지하고, 모듈 간 결합도를 낮추어 유지보수성과 독립성 보장 필요.
- 핵심 목표 : 높은 응집도와 낮은 결합도(Coupling) 달성, 모듈 내부 변경의 독립성 확보, 복잡성 억제.

## Ⅱ. 정보은닉의 특징

- 핵심 요약 : 캡슐화는 수단, 정보은닉은 목적이며 언어 차원의 접근 제한자로 강제.
1. 설계 철학 : 변경 가능성이 높은 설계 결정(자료구조, 알고리즘)의 모듈 내부 격리.
2. 인터페이스 계약 : 공개 인터페이스만의 외부 노출을 통한 안정적 상호작용 규약 확립.
3. 캡슐화(Encapsulation)와의 관계 : 캡슐화는 데이터와 메서드를 하나의 논리적 단위로 묶는 수단, 정보은닉은 그 내부 세부 구현을 감추는 설계 철학 및 목적.
4. 접근 제한자(Access Modifier) 강제 : private, protected, public 키워드를 통한 언어 차원의 정보은닉 규칙 강제.
5. 파급 효과(Ripple Effect) 최소화 : 내부 구현 변경이 외부 모듈로 전파되지 않는 변경 독립성 확보.

## Ⅲ. 정보은닉의 구조 (흐름)

- 핵심 요약 : 공개 인터페이스를 통한 호출 위임 구조와 은닉 적용 유무에 따른 상반된 변경 파급 흐름.

```text
[ 정보은닉 모듈 구조 ]
[ 외부 클라이언트 모듈 ]
   │ 공개 인터페이스(Public Method)만으로 호출
   ▼
[ 모듈/클래스 ]
   ├─ Public Interface : 공개된 규약
   │        │ 내부 위임
   │        ▼
   └─ Private Hidden Implementation
      - 내부 자료구조 (배열→트리 변경 무관)
      - 세부 알고리즘 및 민감 상태 변수
```

```text
[ 변경 파급 흐름 비교 ]
정보은닉 미적용 :
  자료구조 변경 → 호출자 전체 코드 수정
  → 파급 효과(Ripple Effect) 발생
정보은닉 적용 :
  자료구조 변경 → 인터페이스 불변
  → 외부 모듈 무영향
```

## Ⅳ. 정보은닉 적용 유무에 따른 시스템 속성의 비교

- 핵심 요약 : 은닉 적용 시 결합도 완화, 변경 무영향, 격리 테스트, 상태 무결성 확보.

| 비교 관점 | 정보은닉 미적용 (직접 참조) | 정보은닉 철저 적용 (인터페이스 참조) |
|---|---|---|
| 결합도 (Coupling) | 내용 결합도(Content Coupling), 극도로 높음 | 데이터/스탬프 결합도, 매우 낮음 |
| 구현 변경 영향도 | 내부 자료구조 변경 시 전체 호출자 코드 수정 불가피 | 인터페이스 불변 시 내부 변경의 외부 완전 무영향 |
| 테스트 용이성 | 내부 상태가 외부에서 오염되어 결함 추적 난해 | 인터페이스 기반 Mock 객체 생성을 통한 격리 테스트 용이 |
| 코드 보안성 | 민감 필드의 무단 조작 및 유효하지 않은 상태 발생 | Setter/메서드 내 유효성 검증(Validation)을 통한 상태 무결성 보장 |

## Ⅴ. 정보은닉의 장점과 한계

- 핵심 요약 : 독립성·테스트 용이성·무결성의 장점, 보일러플레이트·리플렉션·누수 추상화의 한계.
- 장점
  1. 모듈 독립성과 유지보수성 확보.
  2. 인터페이스 기반 격리 테스트 용이.
  3. 유효성 검증을 통한 상태 무결성 및 코드 보안성 향상.
- 한계점 1 : 기계적 캡슐화로 인한 보일러플레이트 코드 증가 및 런타임 오버헤드
  - 한계점 : 모든 필드를 private으로 선언하고 관례적인 Getter/Setter를 무분별하게 추가하여 코드 가독성 저해, 고성능 연산 시 빈번한 메서드 호출 스택 오버헤드 발생.
  - 해결 방안 : 단순 데이터 전달 목적 객체의 불변 DTO(Data Transfer Object) 및 레코드(Record/Lombok Value) 활용, 비즈니스 도메인 객체의 상태 조회가 아닌 행위(Tell, Don't Ask) 중심 메서드 설계.
- 한계점 2 : 리플렉션(Reflection) 및 런타임 조작을 통한 은닉성 무력화
  - 한계점 : Java 리플렉션(setAccessible(true))이나 C/C++ 메모리 포인터 직접 연산을 통한 비공개(private) 내부 상태의 외부 강제 조작으로 객체 무결성 파손.
  - 해결 방안 : Java 9+ 모듈 시스템(JPMS, Java Platform Module System)의 opens/exports 지시어를 통한 패키지 레벨 리플렉션 접근 차단, 방어적 복사(Defensive Copy) 및 불변(Immutable) 객체 패턴 적용.
- 한계점 3 : 불완전한 추상화(Leaky Abstraction)로 인한 내부 변경 전파
  - 한계점 : 모듈 내부의 자료구조(특정 Map이나 List 구현체)나 예외 타입이 인터페이스 시그니처로 유출되어 내부 구현 변경 시 외부 의존 모듈의 연쇄 파손.
  - 해결 방안 : Parnas의 정보은닉 기본 원칙에 따른 가장 변경 가능성이 높은 설계 결정(Difficult Decisions)의 모듈 내부 완전 격리, 표준 인터페이스 기반 상호작용 설계.

## Ⅵ. 현대 소프트웨어 아키텍처에서의 기술사적 제언

- 핵심 요약 : 헥사고날 아키텍처로의 개념 확장과 Anemic Domain Model 지양.
- 모듈러 모놀리스 및 헥사고날 아키텍처(Ports & Adapters)로의 확장 : 정보은닉의 개념을 클래스 수준에 머무르지 않고, 도메인 비즈니스 로직을 중심에 두고 외부 DB(Database)나 웹 프레임워크를 포트 뒤로 숨기는 클린 아키텍처의 핵심 기반으로 확장 적용 필요.
- 불필요한 Getter/Setter 남발(Anemic Domain Model) 지양 : 모든 필드의 무분별한 개방은 정보은닉의 완전 무력화를 초래하므로, 객체에게 메시지를 던져 일을 시키는 Tell, Don't Ask 원칙의 준수 필요.
- 팀 차원의 설계 규약 정립 : 접근 제한자 사용 기준과 모듈 경계 규칙의 코드 리뷰 체계 편입.

## Ⅶ. 결론

- 핵심 요약 : 정보은닉은 변경 독립성을 보장하는 설계의 기본 원리이자 현대 아키텍처의 토대.
- 요약 : 공개 인터페이스 계약과 내부 구현 격리를 통한 낮은 결합도·높은 응집도 달성.
- 시사점 : 캡슐화를 수단으로, 정보은닉을 목적으로 삼는 목적 지향적 설계 문화의 정착 필요.
