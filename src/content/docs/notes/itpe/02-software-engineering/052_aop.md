## 연관 키워드

- AOP, 횡단 관심사, 애스펙트, 위빙
- 조인 포인트, 포인트컷, 어드바이스, Spring AOP, AspectJ

## Ⅰ. AOP의 개요

- 핵심 요약 : 여러 모듈에 공통으로 나타나는 부가 기능을 별도 모듈로 분리하는 관점 지향 프로그래밍.
- 개념 : 여러 모듈에 걸쳐 나타나는 **횡단 관심사**(Cross-Cutting Concern)를 핵심 비즈니스 로직에서 분리해 별도 모듈로 캡슐화하는 프로그래밍 패러다임 (**AOP**, Aspect-Oriented Programming).
- 배경 및 필요성 : 객체지향 프로그래밍(OOP, Object-Oriented Programming) 구조에서 로깅·트랜잭션·보안 같은 부가 코드가 클래스 곳곳에 흩어지는 코드 분산(Code Scattering)과 핵심 로직에 섞이는 코드 뒤엉킴(Code Tangling)이 반복되는 상황.
- 주요 목적 : 핵심 로직의 응집도와 순수성 유지를 통한 소프트웨어 유지보수성 확보.

## Ⅱ. AOP의 특징 및 장점

- 핵심 요약 : 지점 선별, 기능 정의, 투명한 결합의 단계 구조가 중복 제거라는 효과로 연결되는 모듈화 체계.

1. 관심사의 모듈화 : 횡단 관심사를 **애스펙트**(Aspect)라는 독립 모듈로 정의 → 핵심 로직과 부가 기능의 분리와 중복 제거.
2. 적용 후보의 정의 : 메서드 호출·예외 발생처럼 부가 기능의 결합이 가능한 지점인 **조인 포인트**(Join Point)의 나열 → 적용 범위의 기준 확보.
3. 적용 지점의 선별 : 조인 포인트 중 실제 적용 대상을 **포인트컷**(Pointcut) 표현식으로 지정 → 선언적 범위 지정과 과적용 방지.
4. 부가 기능의 정의 : 실행 시점별 동작을 **어드바이스**(Advice, 이전·반환 후·예외 시 동작)로 한 곳에 구현 → 공통 정책의 단일 관리.
5. 비침습적 결합 : 포인트컷 지점에 어드바이스를 삽입하는 **위빙**(Weaving) → 비즈니스 코드 수정 없는 기능 추가와 교체.

## Ⅲ. AOP의 구조 (흐름)

- 핵심 요약 : 분리된 핵심 로직과 애스펙트가 위빙으로 결합되고, 실행 시점에는 프록시 경로로 부가 기능이 수행되는 이중 구조.
- 개발 시점의 결합 구조.

```text
[ AOP 구성 요소의 결합 ]

핵심 비즈니스 로직 (서비스 메서드)
   +
애스펙트 (포인트컷 + 어드바이스)
   ↓
위빙 (Weaving)
   ↓
부가 기능이 결합된 실행 코드
```

- 런타임 프록시 방식의 실행 흐름.

```text
[ 런타임 프록시 실행 흐름 ]

클라이언트 호출
   ↓
프록시 (어드바이스 선행 처리)
   ↓
핵심 메서드 실행
   ↓
프록시 (어드바이스 후행 처리)
   ↓
클라이언트 응답
```

## Ⅳ. AOP와 OOP의 공통 기능 처리 방식 비교

- 핵심 요약 : 부가 기능을 호출 코드로 중복 배치하는 OOP 방식과 애스펙트로 집중 관리하는 AOP의 대비.

| 비교 축 | AOP | OOP의 공통 기능 처리(코드 중복 방식) |
| --- | --- | --- |
| 관심사 배치 | 횡단 관심사를 애스펙트 한 곳에 집중 | 상속·유틸리티 호출로 각 클래스에 분산 배치 |
| 코드 형태 | 비즈니스 코드에 부가 로직의 부재 | 부가 로직 호출 코드의 클래스별 중복 |
| 기능 변경 | 애스펙트 한 곳의 수정 | 중복 코드의 전수 수정 |
| 적용 범위 지정 | 포인트컷 표현식의 선언적 지정 | 호출 코드의 직접 작성 |
| 핵심 로직 영향 | 부가 로직과의 분리로 순수성 유지 | 코드 뒤엉킴(Code Tangling) 발생 |

## Ⅴ. AOP의 한계와 방안

- 핵심 요약 : 프록시 우회, 과도한 적용, 실행 순서 미정의의 세 위험이 부가 기능의 신뢰성을 제약.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 자기 호출(Self-Invocation) 우회 | 같은 객체 내부의 메서드 호출이 프록시를 거치지 않는 구조 → 부가 기능의 누락 | 트랜잭션 경계 메서드의 클래스 분리 | 부가 기능 누락 건수 |
| 과도한 적용 | 포인트컷의 광범위한 지정 → 불필요한 지점까지의 개입과 성능 부담 | 애노테이션 기반 포인트컷 설계, 적용 범위 검토 | 애스펙트 실행 시간 |
| 실행 순서 충돌 | 여러 애스펙트의 순서 미정의 → 보안·트랜잭션 검증의 어긋남 | 애스펙트 우선순위의 명시적 지정 | 순서 규칙 위반 건수 |

## Ⅵ. AOP 거버넌스에 대한 기술사적 제언

- 핵심 요약 : 애스펙트를 개발자별 기법이 아닌 전사 공통 정책의 운영 단위로 통제하는 체계 필요.
- 조직 : 아키텍처 검토 조직이 애스펙트 대상 횡단 관심사의 목록과 선정 기준을 관리.
- 기술 : **Spring AOP**(프록시 기반)와 **AspectJ**(바이트코드 기반)의 도입 기준을 표준 문서로 제정.
- 검증 : 부가 기능의 적용 여부를 점검하는 아키텍처 테스트의 정기 수행.

## Ⅶ. 결론

- 핵심 요약 : AOP는 횡단 관심사를 모듈화해 핵심 로직의 순수성을 지키는 설계 원칙.
- 절제된 적용 범위와 명확한 실행 순서 규칙이 안정적 도입의 조건.
