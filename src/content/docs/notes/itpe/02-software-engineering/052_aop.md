## 연관 키워드
- AOP, 횡단 관심사, 조인 포인트, 포인트컷, 어드바이스, 애스펙트, 위빙, Spring AOP, AspectJ

### Ⅰ. AOP의 개요

- 핵심 요약 : 흩어진 공통 관심사를 애스펙트 모듈로 분리해 핵심 로직과 섞이지 않게 하는 관점 지향 프로그래밍.
- 개념 : 관점 지향 프로그래밍(AOP, Aspect-Oriented Programming)은 트랜잭션, 로깅, 보안처럼 여러 모듈에 걸친 횡단 관심사(Cross-Cutting Concerns)를 핵심 비즈니스 로직에서 떼어내 별도 모듈로 캡슐화하는 프로그래밍 패러다임임.
- 배경 및 필요성 : 객체지향 프로그래밍(OOP, Object-Oriented Programming)만으로는 여러 클래스에 같은 부가 코드가 흩어지는 코드 분산(Code Scattering)과 핵심 로직에 부가 코드가 얽히는 코드 뒤엉킴(Code Tangling)을 막기 어려움.
- 주요 목적 : 핵심 로직의 응집도를 높이고 단일 책임 원칙(SRP, Single Responsibility Principle)을 지켜 유지보수성을 확보하는 것.

### Ⅱ. AOP의 특징 및 장점

- 핵심 요약 : 조인 포인트, 포인트컷, 어드바이스, 애스펙트, 위빙의 다섯 개념으로 횡단 관심사를 비침습적으로 결합하는 구조.

1. 조인 포인트(Join Point) : 메서드 호출, 객체 생성, 예외 발생처럼 부가 기능을 끼울 수 있는 실행 지점 → 적용 후보 범위를 정의.
2. 포인트컷(Pointcut) : 조인 포인트 중 실제 적용 지점을 고르는 표현식 → 적용 대상을 선별해 과적용을 방지.
3. 어드바이스(Advice) : 실제로 수행하는 부가 기능 코드(@Before, @After, @Around 등) → 공통 기능을 한 곳에서 정의.
4. 애스펙트(Aspect) : 포인트컷과 어드바이스를 묶은 횡단 관심사 모듈 → 공통 정책을 모듈 단위로 관리.
5. 위빙(Weaving) : 포인트컷이 지정한 지점에 어드바이스를 결합하는 과정 → 비즈니스 코드 수정 없이 기능 추가.

### Ⅲ. AOP의 구조 (흐름)

- 핵심 요약 : 분리된 핵심 로직과 애스펙트가 위빙 시점에 결합되어 최종 애플리케이션이 완성되는 흐름.

```text
[ 핵심 비즈니스 로직 ]
 - OrderService.createOrder()
 - PaymentService.pay()
   ↓
[ 횡단 관심사 : LoggingAspect ]
 - @Before : 메서드 시작 시각 기록
 - @AfterReturning : 결과 로깅
 - @AfterThrowing : 예외 로깅
   ↓
[ 위빙 (Weaving) 수행 ]
   ↓
[ 최종 실행 애플리케이션 ]
```

- 투명한 결합 : 비즈니스 코드를 수정하지 않아도 지정된 시점에 애스펙트가 자동으로 삽입됨.

### Ⅳ. AOP 3대 위빙 방식의 비교

- 핵심 요약 : 결합 시점에 따른 컴파일 타임, 로드 타임, 런타임 프록시 위빙의 성능과 유연성 트레이드오프.

| 비교 항목 | 컴파일 타임 위빙 (CTW) | 로드 타임 위빙 (LTW) | 런타임 프록시 위빙 |
|---|---|---|---|
| 동작 시점 | 소스 코드 컴파일 시점 | JVM(Java Virtual Machine) 클래스 로딩 시점 | 스프링 컨테이너의 빈 생성 시점 |
| 특징 및 장단점 | 전용 컴파일러가 필요하나 런타임 오버헤드가 거의 없음 | 유연하나 JVM 에이전트 설정이 필요하고 로딩이 약간 지연됨 | 추가 컴파일러가 없으나 메서드 호출 지점만 지원 |
| 대표 도구 | AspectJ 컴파일러(ajc) | AspectJ LTW 에이전트 | Spring AOP (JDK 동적 프록시, CGLIB) |

### Ⅴ. AOP의 한계와 방안

- 핵심 요약 : 관심사 분리에 따른 응집도와 재사용성의 이점, 프록시 우회와 디버깅 복잡성의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 자기 호출(Self-Invocation) 프록시 우회 | 같은 객체 안의 메서드 호출은 프록시를 거치지 않아 트랜잭션과 로깅이 누락됨 | 호출 구조를 별도 서비스 빈으로 분리하거나 AspectJ LTW 도입 | 부가 기능 누락 검출 건수 |
| 과도한 포인트컷과 디버깅 난도 | 와일드카드 남용 시 불필요한 메서드까지 인터셉트되어 오버헤드와 호출 스택 복잡화 발생 | 애노테이션 기반 포인트컷(@annotation) 설계, APM 추적 연동 | 애스펙트별 실행 시간 |
| 애스펙트 실행 순서 충돌 | 트랜잭션·인가·캐시 애스펙트의 순서가 보장되지 않아 데이터 불일치나 비인가 접근 위험 | @Order 또는 Ordered 인터페이스로 우선순위를 명시하고 전사 거버넌스 규칙으로 관리 | 순서 규칙 위반 건수 |

### Ⅵ. 엔터프라이즈 환경에서의 기술사적 제언

- 핵심 요약 : 자기 호출 한계를 설계 단계에서 점검하고, AOP 적용 범위를 전사 규칙으로 통제하는 방향.

1. Spring AOP는 동적 프록시 기반이므로, 같은 클래스 안에서 자기 자신의 @Transactional 메서드를 호출하면 트랜잭션이 빠지는 버그가 생길 수 있음. 개발팀은 트랜잭션 경계가 있는 메서드를 별도 서비스 빈으로 분리하는 것을 기본 설계로 삼고, 분리가 어려운 영역에만 AspectJ LTW를 검토함.
2. 아키텍처 조직은 트랜잭션, 감사 로깅, 분산 추적처럼 전사가 공유해야 하는 횡단 관심사만 애스펙트로 허용하고, 그 밖의 @Around 어드바이스는 실행 흐름과 스택 트레이스를 흐리므로 사전 검토를 거치도록 정책으로 정함.

### Ⅶ. 결론

- 핵심 요약 : AOP는 횡단 관심사를 모듈화해 핵심 로직의 순수성을 지키는 설계 원칙.
- 시사점 : 적용 범위를 절제하고 프록시 한계를 점검하며 실행 순서를 거버넌스로 정하는 것이 안정적 도입의 조건.
