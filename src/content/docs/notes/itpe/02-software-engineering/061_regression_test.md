## Ⅰ. 회귀테스트의 개요

- **개념** : 소프트웨어의 결함 수정, 기능 추가, 리팩토링, 운영 환경 변경 등으로 인해 소스코드가 변경되었을 때, 기존에 정상 동작하던 다른 영역에 예상치 못한 사이드 이펙트(Side Effect)나 결함이 발생하지 않았음을 확인하기 위해 기존 테스트 케이스를 재실행하는 반복 검증 기법.
- **배경 및 필요성** : 복잡한 소프트웨어 시스템에서는 단 한 줄의 코드 수정이 모듈 간의 결합도로 인해 무관한 기능의 장애를 유발할 수 있으므로, 변경의 안전성을 입증하는 방어선 역할 수행.
- **핵심 목표** : 기존 기능의 퇴보(Regression) 방지, 지속적인 품질 안정성 유지, 빠른 릴리스 지원.

## Ⅱ. 회귀테스트의 3대 선정 전략

```text
   [ 전체 재테스트 (Retest-All) ] ──────── 기존의 모든 테스트 케이스를 전수 실행
          │
   [ 회귀 테스트 선택 (Selective) ] ───── 코드 변경 영향도 분석을 통해 변경 관련 TC만 선별
          │
   [ 테스트 케이스 우선순위화 (Prioritization) ] ─ 비즈니스 중요도, 결함 빈도 순으로 우선순위 정렬
```

- **전체 재테스트 (Retest-All)** : 모든 테스트 케이스를 처음부터 끝까지 재실행. 회귀 결함 탐지율은 100%이나, 시스템이 커질수록 막대한 시간과 비용이 소요되어 CI/CD 환경에서 병목 유발.
- **회귀 테스트 선택 (Regression Test Selection, RTS)** : 코드 변경 사항(Git Diff)과 클래스/메서드 간의 의존성 그래프를 분석하여 변경의 영향을 받는 테스트 케이스만을 선별 실행 (비용 대비 효율 우수).
- **테스트 케이스 우선순위화 (Priority-based)** : 비즈니스 핵심 기능, 과거 결함 발생 빈도가 높았던 모듈, 복잡한 로직과 연관된 테스트 케이스를 먼저 실행하여 조기 결함 발견(Fail-Fast).

## Ⅲ. 회귀테스트 전략별 비교 분석

| 전략 | 장점 | 단점 | 적합한 환경 |
|---|---|---|---|
| Retest-All | 회귀 결함 누락 위험 제로 | 빌드/테스트 시간 과다 소요 | 소규모 프로젝트, 릴리스 직전 최종 QA 단계 |
| Selective (선택 실행) | 테스트 실행 시간 및 비용 대폭 단축 | 완벽한 영향도 분석 실패 시 결함 누락 위험 | 일일 빌드, 빈번한 마이크로 배포 환경 |
| Prioritization (우선순위) | 제한된 시간 내 가장 위험한 결함 조기 발견 | 우선순위 기준 수립 및 유지보수 공수 발생 | 야간 빌드(Nightly Build), 회귀 테스트 스위트 |

## Ⅳ. 지속적 배포(CD) 환경에서의 기술사적 제언

- **스마트 테스트 선택(Smart Test Selection) 및 변경 영향도 도구 연계** : 변경된 소스코드의 바이트코드와 AST를 추적하여 해당 변경을 실행하는 테스트만 선택 실행하는 도구(Test Impact Analysis)를 파이프라인에 적용하여 테스트 시간을 수시간에서 수분 단위로 단축.
- **불안정한 테스트(Flaky Test)의 체계적 격리 및 관리** : 타이밍 이슈, 외부 네트워크 의존성 등으로 인해 성공과 실패를 무작위로 반복하는 Flaky Test는 개발팀의 파이프라인 신뢰도를 무너뜨리므로, 별도 격리 큐로 분리하고 원인을 분석하여 목(Mock) 객체로 재작성하는 정기 클리닝 프로세스 수립 필수.
