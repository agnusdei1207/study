## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 테스트·검증 → **회귀테스트(Regression Test)**

## 30초 인출

- 본질: 회귀테스트는 코드를 변경한 뒤 기존 기능이 그대로 동작하는지 다시 확인하는 테스트
- 메커니즘: 변경 후 기존 테스트 케이스를 재실행하되 전체 재실행이 부담이면 변경 영향 케이스만 선택하거나 결함 검출 가능성 순으로 우선순위화
- 통찰: 변경마다 전체 테스트를 돌리면 시간이 길어 생략되기 쉬우므로 변경 영향 범위의 케이스를 선택하고 결함 검출 가능성이 큰 순서로 CI에서 자동 실행

<details>
<summary>핵심 용어</summary>

- **회귀테스트(Regression Testing)** : 변경 후 기존 기능이 손상되지 않았는지 확인하는 테스트
- **확인 테스트(Confirmation Testing)** : 수정된 결함이 실제로 해결됐는지 확인하는 재시험
- **회귀 테스트 선택(RTS)** : 변경 영향을 받는 테스트 케이스만 골라 실행하는 전략
- **테스트 케이스 우선순위화(TCP)** : 결함 검출 가능성이 큰 케이스를 먼저 실행하도록 순서를 정하는 전략
- **테스트 영향 분석(TIA)** : 코드 변경과 테스트 케이스의 연결로 영향받는 테스트를 찾는 분석

</details>

## 2~4교시 25점 답안

## Ⅰ. 회귀테스트의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **회귀테스트** 는 변경 후 기존 기능이 그대로 동작하는지 다시 확인하는 테스트 |
| 목적 | 변경으로 생긴 부작용(회귀 결함)의 조기 발견 |

## Ⅱ. 회귀테스트의 특징

| 특징 | 의미 |
|---|---|
| 기존 케이스 재사용 | 이전 테스트 자산의 반복 실행 |
| 변경 대응 | 결함 수정·기능 추가마다 수행 |
| 자동화 적합 | 반복 실행이 많아 자동화 효과 큼 |

## Ⅲ. 회귀테스트 수행 절차

### 수행 절차

```text
코드 변경
    ↓
변경 영향 범위 분석 (TIA)
    ↓
회귀 테스트 케이스 선택 (RTS)
    ↓
우선순위화 (TCP) → 실행
    ↓
결과 확인 → 실패 시 결함 수정
```

### 확대: 확인 테스트와 회귀 테스트

```text
결함 수정 → 확인 테스트(수정된 결함 해결 확인)
    ↓
회귀 테스트(다른 기능의 손상 여부 확인)
```

## Ⅳ. 회귀테스트 전략의 비교

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| 전체 재실행 | 모든 케이스 실행 | 누락 없음 | 시간·비용 큼 |
| 선택(RTS) | 변경 영향 케이스만 실행 | 시간 절감 | 영향 분석 오류 시 누락 |
| 우선순위(TCP) | 결함 검출 가능성 순으로 실행 | 빠른 결함 발견 | 우선순위 기준 필요 |
| 축소 | 중복 케이스 제거 | 유지 비용 감소 | 검출 능력 저하 가능 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 전체 재실행 시간 과다로 생략 | 영향 범위 선택과 우선순위화 |
| 영향 분석 오류로 결함 누락 | 변경 이력과 테스트 연결 관리, 주기적 전체 실행 |
| 수동 회귀테스트의 반복 부담 | 자동화 후 CI 파이프라인에서 실행 |

## Ⅵ. 제언

변경 영향 케이스를 선택해 결함 검출 가능성이 큰 순서로 실행하고, CI에서 자동 실행하며 전체 회귀는 주기적으로 수행

### 2단계 회귀 구성

```text
커밋마다: 영향 케이스 선택 실행 (빠른 피드백)
    ↓
일 단위·릴리스 전: 전체 회귀 실행
```

### 선택 근거: 전체 재실행과의 비교

| 구분 | 매번 전체 재실행 | 제언: 선택 + 주기적 전체 |
|---|---|---|
| 피드백 시간 | 김 | 짧음 |
| 누락 위험 | 낮음 | 주기적 전체로 보완 |
| 실행 비용 | 큼 | 절감 |
