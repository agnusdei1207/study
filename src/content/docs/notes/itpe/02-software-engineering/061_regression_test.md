## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 테스트·품질 → 변경 관련 테스트 → **회귀테스트(Regression Test)**

## 30초 인출

- 본질: 소프트웨어 소스코드 수정, 기능 추가, 리팩토링, 환경 변경 후 기존에 정상 작동하던 기능에 의도치 않은 새로운 결함(부작용)이 유입되지 않았음을 보증하는 변경 관련 테스트 기법
- 메커니즘: 코드 변경 커밋 → 테스트 영향 분석(TIA) → 회귀 테스트 케이스 선택(RTS) 및 우선순위화(TCP) → CI/CD 자동화 파이프라인 병렬 실행 및 합격 판정
- 통찰: 테스트 스위트 비대화로 인한 빌드 파이프라인 지연을 해소하기 위해 단위 레벨 영향 분석 기반의 스마트 선택 실행과 야간 정기 전수 회귀 테스트의 2-Tier 분리 운영 필수

<details>
<summary>핵심 용어</summary>

- **Regression Testing(회귀테스트)** : 결함 수정이나 기능 개선 등의 코드 변경 후 기존 시스템의 정상 동작 여부를 확인하기 위해 기수행된 테스트를 재실행하는 기법
- **Confirmation Testing (확인시험/재시험)** : 결함이 수정되었다고 보고된 후 해당 결함이 실제로 제거되었는지 동일한 절차로 확인하는 목적의 테스트
- **RTS (Regression Test Selection)** : 전체 테스트 케이스 중 코드 변경의 영향을 받는 테스트 케이스만 선별하여 실행하는 최적화 전략
- **TCP (Test Case Prioritization)** : 제한된 시간과 자원 내에서 결함 검출 가능성이 높은 순서대로 테스트 실행 순서를 재정렬하는 기법
- **TIA (Test Impact Analysis)** : 소스코드의 변경 Diff와 테스트 케이스 간의 호출 그래프(Call Graph)를 분석하여 영향 범위를 자동 식별하는 엔지니어링 기술

</details>

## 2~4교시 25점 답안

## Ⅰ. 회귀테스트의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어의 결함 수정, 기능 추가, 패치 또는 운영 환경 변경 후, 이미 검증되었던 기존 기능들이 변경의 부작용(Side Effect) 없이 여전히 정상 동작함을 검증하는 반복적 소프트웨어 테스트 기법 |
| 목적 | 수정 작업에 따른 기존 기능의 퇴보(Regression) 방지, 릴리스 안정성 확보 및 소프트웨어 변경에 대한 엔지니어링 신뢰도 제공 |

## Ⅱ. 회귀테스트의 핵심 특징

| 특징 | 의미 |
|---|---|
| 변경 부작용 검증 | 수정한 버그 자체가 아닌, 수정으로 인해 파생될 수 있는 주변 연계 모듈의 잠재적 오작동 식별 |
| 높은 자동화 의존성 | 코드 변경 시마다 반복적으로 전수 또는 선별 실행해야 하므로 CI/CD 기반 테스트 자동화 필수 |
| 누적적 스위트 증가 | 소프트웨어가 진화함에 따라 회귀 테스트 케이스 수가 지속 누적되어 최적화(RTS/TCP) 요구 |
| 지속적 배포의 관문 | 애자일 스프린트 및 CI/CD 환경에서 프로덕션 배포 전 반드시 통과해야 하는 최종 품질 관문 |

## Ⅲ. 회귀테스트 체계 및 테스트 영향 분석(TIA) 프로세스

### TIA 기반 스마트 회귀테스트 실행 파이프라인

```text
[개발자 소스코드 수정 및 Git PR 생성]
       │
       ▼ (1단계: 변경 코드 Diff 분석)
┌────────────────────────────────────────────────────────────────────────┐
│ 테스트 영향 분석 (Test Impact Analysis, TIA)                          │
│  - 변경된 메서드/클래스와 바이트코드 수준의 호출 그래프(Call Graph) 매핑│
│  - 영향받는 컴포넌트 목록 자동 도출                                   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (2단계: 전략적 테스트 집합 선별)
┌────────────────────────────────────────────────────────────────────────┐
│ 회귀 테스트 선택 (RTS) & 우선순위화 (TCP)                              │
│                                                                        │
│   [전체 회귀 테스트 스위트 (10,000건)]                                 │
│         │                                                              │
│         ├─ [RTS 필터링] ──→ [영향받는 테스트 케이스 (500건 선별)]      │
│         │                                                              │
│         └─ [TCP 정렬] ────→ [1순위: 핵심 결제 로직 TC (최우선 실행)]   │
│                             [2순위: 최근 실패 이력 보유 TC]            │
│                             [3순위: 실행 시간이 짧은 단위 TC]          │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ (3단계: CI 파이프라인 병렬 분산 실행)
┌────────────────────────────────────────────────────────────────────────┐
│ 자동화 분산 테스트 러너 (Parallel Execution)                           │
│  - Docker 컨테이너 클러스터에서 500건 병렬 실행 (소요 시간: 3분)       │
│  - 실행 결과 모니터링: All PASS → PR 머지 승인 / FAIL → 즉시 차단     │
└────────────────────────────────────────────────────────────────────────┘
```

### 회귀테스트 3대 실행 전략

| 전략 | 실행 메커니즘 | 장점 | 단점 및 적용 기준 |
|---|---|---|---|
| **전수 회귀 (Retest-All)** | 구축된 모든 회귀 테스트 케이스를 매 변경 시 100% 실행 | 결함 누락 위험 제로, 완벽한 회귀 안전성 | 대규모 프로젝트의 경우 수 시간 소요되어 상시 실행 불가 |
| **선택 실행 (RTS)** | TIA 기법으로 코드 변경의 직간접 영향을 받는 케이스만 선별 | 실행 시간을 획기적으로 단축(수 분 내 완료) | TIA 도구의 정밀도에 따라 간접 영향 결함 누락 가능성 |
| **우선순위화 (TCP)** | 위험도, 비즈니스 중요도, 결함 검출 이력 순으로 정렬 실행 | 조기에 결함을 발견하여 개발 피드백 루프 극대화 | 전체를 다 돌리지 못할 경우 하위 우선순위 결함 방치 |

## Ⅳ. 회귀테스트(Regression) vs 확인시험(Confirmation/Retest)

### 두 변경 관련 테스트 간의 본질적 비교

| 비교 항목 | 확인시험 (Confirmation Testing / Retest) | 회귀테스트 (Regression Testing) |
|---|---|---|
| **테스트 목적** | **보고된 특정 결함이 올바르게 수정되었는가** | **수정으로 인해 다른 정상 기능이 깨지지 않았는가** |
| **테스트 대상** | 결함이 발생했던 특정 기능 및 재현 테스트 케이스 | **수정된 모듈과 연계된 모든 변경되지 않은 기존 영역** |
| **수행 시점** | 결함 수정 티켓(Issue) 완료 즉시 수행 | 결함 수정 후 통합 빌드 및 릴리스 배포 직전 수행 |
| **케이스 성격** | 결함을 유발했던 기존 실패 테스트 케이스 재실행 | 기합격했던 방대한 회귀 테스트 스위트의 재실행 |
| **자동화 여부** | 수동 탐색적 확인 가능 | **방대한 분량으로 인해 100% 자동화 구축 필수** |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 소프트웨어 기능 누적으로 회귀 테스트 스위트가 비대해져 CI 파이프라인 빌드 시간 폭증 | PR 빌드 시에는 TIA 기반 RTS(영향 테스트)만 돌리고 심야(Nightly)에 전수 회귀 실행 |
| 동일 코드에 대해 간헐적으로 성공/실패가 번복되는 비결정론적 플래키 테스트(Flaky Test) 발생 | 플래키 테스트 격리(Quarantine) 파이프라인을 구축하고 비동기 대기(Await) 로직 정비 |
| 레거시 시스템의 경우 문서와 테스트 코드가 없어 수작업 회귀 테스트에 따른 인력 소모 극심 | 레코드 앤 리플레이(Record & Replay) 도구를 도입하여 실제 운영 트래픽 기반 자동 회귀 구축 |

## Ⅵ. 제언

2-Tier 회귀 테스트 파이프라인 체계 구축 및 AI 기반 플래키 테스트 자동 자가 치유(Self-healing)

### 2-Tier 분리형 회귀 테스트 운영 모델

```text
[개발자 작업 시간대 (주간)]
  ├─ 코드 커밋 및 PR 생성
  └─ [Tier 1: Fast-Feedback 회귀 (RTS + 단위/통합 5분 컷)]
       ├─ TIA 기반 변경 모듈 연관 테스트만 핀포인트 실행
       └─ 통과 시 즉시 머지 및 개발 리듬 유지
       ↓
[심야 무작업 시간대 (야간 02:00)]
  └─ [Tier 2: Comprehensive 전수 회귀 (Nightly Retest-All)]
       ├─ 전체 시스템 종단간(E2E) UI 및 성능 회귀 전수 실행
       ├─ 심야 대규모 분산 클라우드 자원 활용 (수 시간 소요 허용)
       └─ 실패 리포트 발생 시 익일 출근 즉시 핫픽스 우선 배정
```

### 회귀테스트 전략 선택 의사결정 체계

```text
코드 변경 발생
       ↓
[변경 사항이 배포 마일스톤 완료 또는 메이저 릴리스인가?]
       ├─ 예 ──→ [Tier 2: 전수 회귀 테스트 (Retest-All)] 필수 수행
       └─ 아니오 ─→ [일반 PR 및 기능 브랜치 머지인가?]
                         ↓
           [CI 파이프라인 실행 제한 시간(예: 10분)을 초과하는가?]
                         ├─ 예 ──→ [RTS (영향 기반 선택)] + [TCP (우선순위화)] 실행
                         └─ 아니오 ─→ 빠른 전체 단위 테스트 스위트 실행
```

### 선택 근거: 전통적 수동 회귀와 제언 2-Tier 스마트 회귀 비교

| 구분 | 전통적 수동 회귀 테스트 | 제언: 2-Tier 스마트 자동화 회귀 |
|---|---|---|
| 소요 시간 | 릴리스 전 수일~수주 동안 QA 팀 전원 투입 | 주간 5분 이내 피드백 + 야간 무인 전수 자동화 |
| 결함 발견 시점 | 릴리스 직전 통합 테스트 단계에서 대량 발견 | 코드 커밋 즉시 개발자가 자신의 브랜치에서 결함 발견 |
| 릴리스 주기 | 회귀 테스트 병목으로 월간/분기별 릴리스 | 하루 수십 회 이상의 안전한 무중단 지속적 배포(CD) 달성 |
