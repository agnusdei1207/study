| 서브토픽 | 핵심 키워드 | 답안 차별화 포인트 |
|---|---|---|
| 재테스트 vs 회귀테스트 | Retest(결함 수정 확인), Regression Test(부작용 검증), 사이드이펙트(Side Effect) | 단순 결함 재확인과의 목적 및 테스트 범위 차이 명확화 |
| 3대 회귀 테스트 전략 | Retest-All(전수 실행), RTS(회귀 테스트 선택), TCP(테스트 케이스 우선순위화) | 테스트 비용과 결함 검출력 간의 트레이드오프 조율 전략 제시 |

## 1. 회귀테스트의 개요 및 필요성

### (1) 회귀테스트(Regression Test)의 정의
- 기능 추가, 결함 수정(Bug Fix), 환경 변경 또는 코드 리팩토링 후, **이전에 정상 작동하던 기존 소프트웨어 기능에 의도치 않은 오류나 부작용(Side Effect)이 발생하지 않았음을 검증하기 위해 기존 테스트 케이스를 재수행하는 반복적 테스트 활동**.

### (2) 회귀테스트의 핵심 필요성
- **사이드이펙트(Side Effect) 차단**: 모듈 간 결합도로 인해 한 곳의 버그 수정이 다른 정상 모듈의 장애를 유발하는 연쇄 결함 방지.
- **지속적 진화(Software Evolution) 보증**: 잦은 배포와 리팩토링 환경에서 기존 품질 베이스라인(Baseline) 무결성 유지.
- **자동화와의 필연성**: 소프트웨어가 커질수록 테스트 케이스가 누적되므로 자동화(Automation) 없는 회귀 테스트는 수행 불가능.

## 2. 3대 회귀테스트 전략 및 구조

### (1) 회귀테스트 3대 전략 비교 구조도
```text
+-------------------------------------------------------------------------+
|                    3대 회귀테스트 전략 및 수행 구조                     |
+-------------------------------------------------------------------------+
| [ 소스코드 변경 (Commit / PR) ] ──▶ [ 정적/동적 영향도 분석 (TIA) ]      |
|                                                     │                   |
|         ┌─────────────────────────┬─────────────────┴─────────┐         |
|         v                         v                           v         |
|  [ 1. Retest-All ]        [ 2. RTS (선택) ]           [ 3. TCP (우선순위)]
|  - 기존 모든 TC 100% 실행 - 변경 모듈에 영향받는      - 위험도/비즈니스  |
|  - 완벽한 안전성 보장     테스트 케이스만 선별        중요도 높은 순 실행
|  - 실행 시간/비용 극대    - 실행 비용 절감, 누락위험  - 시간 제약 시 최적 |
|         │                         │                           │         |
|         └─────────────────────────┼───────────────────────────┘         |
|                                   v                                     |
|                [ CI 파이프라인 자동 실행 ──▶ 회귀 결함 0건 ]            |
+-------------------------------------------------------------------------+
```

### (2) 3대 회귀테스트 전략 상세 비교
| 구분 | Retest-All (전수 실행) | RTS (Regression Test Selection) | TCP (Test Case Prioritization) |
|---|---|---|---|
| **수행 방식** | 기존 테스트 스위트 전체를 재실행 | 변경된 코드와 관련된 TC만 추출하여 실행 | 실패 확률 및 비즈니스 영향도가 높은 TC 순으로 정렬 실행 |
| **장점** | 결함 누락 위험 제로, 신뢰도 최고 | 실행 시간 대폭 단축, 자원 효율적 | 주어진 타임박스(Timebox) 내 최대 결함 검출 |
| **단점** | 테스트 스위트 증가 시 빌드 시간 마비 | 완벽한 의존성 분석 실패 시 사이드 결함 누락 위험 | 우선순위 산정 알고리즘 복잡도 및 기준 모호 |
| **적용 시점** | 메이저 릴리스, 정기 야간 빌드(Nightly) | 일상적인 기능 PR, 지속적 통합(CI) 단계 | 긴급 핫픽스, 배포 직전 스모크 테스트 |

## 3. 테스트 영향도 분석(TIA) 및 CI/CD 연계

```text
[ Git Diff 변경 커밋 ] ──▶ [ 소스-테스트 추적 매트릭스 ] ──▶ [ 타겟 테스트 자동 실행 ]
  (클래스/메서드 레벨)      (정적 AST / 런타임 커버리지 매핑)     (수천 개 중 수십 개만 30초 컷)
```

1. **정적 영향도 분석 (Static TIA)**: 추상 구문 트리(AST)를 파싱하여 변경된 클래스를 호출하는 상위 클래스 및 테스트 의존성을 그래프로 추적.
2. **동적 영향도 분석 (Dynamic TIA)**: 테스트 실행 시 생성되는 바이트코드 커버리지 데이터를 기록하여 특정 코드를 통과한 테스트 케이스를 역추적(Reverse Mapping).
3. **CI 파이프라인 연계**: 개발자가 Pull Request를 올리면 TIA 도구가 변경 영향 테스트만 1분 내에 자동 실행하여 빠른 피드백 루프 제공.

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **단순 버그 수정 후 핵심 결제 모듈 중단**<br>(운영 환경 회귀 장애 사고) | 포인트 조회 수정 시 결제 트랜잭션 간 숨겨진 의존성을 간과하고 회귀 테스트 생략 | 핵심 비즈니스 크리티컬 패스에 대한 자동화된 회귀 테스트 게이트 의무화 | 운영 배포 후 회귀 결함 발생률 0% 달성 |
| **빌드 파이프라인 6시간 소요로 배포 정체**<br>(회귀 테스트 케이스 과다 누적) | 수만 개의 느린 Selenium E2E UI 테스트를 매 커밋마다 Retest-All 전수 실행 | 테스트 피라미드 재편(단위 70%, 통합 20%, E2E 10%) 및 TIA 기반 선택적 실행 | PR 빌드 검증 시간 6시간에서 8분으로 단축 |
| **불안정한 테스트(Flaky Test)로 배포 지연**<br>(코드 변경 없는데 간헐적 실패) | 비동기 네트워크 지연 및 외부 서비스 종속으로 인한 테스트 신뢰성 저하 | Testcontainers 기반 격리 모킹 및 Flaky Test 자동 재시도/격리 격리 쿼런틴(Quarantine) | 거짓 경보(False Positive) 95% 제거, CI 안정성 확보 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 배포 전날 수동 전수 검사]           [현대: 지속적 회귀 보증 (Continuous Regression)]
- 스프레드시트 체크리스트 수동 클릭  ──▶   - 테스트 피라미드 기반 자동화 회귀 스위트
- 배포 주기 수개월 단위 지연        ──▶   - TIA(Test Impact Analysis) 기반 빠른 피드백
- 회귀 결함 운영 환경 유출 일상화   ──▶   - Nightly Retest-All + PR 단위 RTS의 하이브리드 거버넌스
```

- **회귀 테스트 피라미드(Test Pyramid)의 엄격한 준수**: UI 기반 E2E 테스트로만 회귀 스위트를 구축하면 유지보수 비용과 Flaky Test로 인해 회귀 체계가 붕괴됨. 빠른 단위 테스트(Unit)와 API 통합 테스트(Integration)가 회귀의 90%를 방어하고, E2E는 핵심 골든 패스(Golden Path)만 점검해야 함.
- **하이브리드 회귀 테스트 거버넌스 수립**: 실무에서는 단일 전략만 고집할 수 없음. **개발자의 일상 커밋에는 TIA 기반의 RTS(선택적 실행)를 적용하여 5분 피드백을 보장하고, 야간 정기 빌드에는 전체 Retest-All을 백그라운드로 실행하며, 긴급 릴리스에는 TCP(우선순위화)를 적용**하는 3계층 하이브리드 거버넌스가 기술사로서 제시할 최적의 아키텍처임.
