## 답안 골격
```text
[중재자 토폴로지] ◀━━ 머리: Ⅶ 내 의견 (중앙 오케스트레이터를 통한 복잡한 분산 사가 트랜잭션의 상태 제어 및 보상 트랜잭션 완결)
 ┃
 ┣━ Ⅰ 개요 ───── 브로커 토폴로지의 분산 흐름 파악 불가 및 보상 트랜잭션 혼선 → 중앙 중재자가 이벤트 흐름을 지휘·통제하는 오케스트레이션
 ┣━ Ⅱ 특징 ───── 오케스트레이션(Orchestration) 방식 · 중앙 집중식 워크플로우 제어 · 트랜잭션 상태 가시성 확보 · 복잡한 에러/보상 처리 용이
 ┣━ Ⅲ 구조 ───── 시작 큐(Initiator Queue) / 이벤트 중재자(Event Mediator) / 액션 큐(Action Queue) / 이벤트 프로세서(Processor)
 ┣━ Ⅳ 흐름 ───── 초기 이벤트 수신 → 중재자가 비즈니스 단계 판단 → 개별 액션 큐로 작업 지시 발행 → 프로세서 처리 후 응답 → 다음 단계 순차/병렬 제어
 ┣━ Ⅴ 비교 ───── 중재자 토폴로지(Orchestration, 중앙 통제) vs 브로커 토폴로지(Choreography, 자율 반응)
 ┗━ Ⅵ 실무 ───── 중재자 컴포넌트의 단일 실패점(SPOF) 및 성능 병목 / 도메인 로직 침투 방어 / 워크플로우 엔진(Temporal, Camunda)
```
- 필수 키워드: 중재자 토폴로지 · 이벤트 기반 아키텍처(EDA) · 오케스트레이션(Orchestration) · 이벤트 중재자 · 사가(Saga) 오케스트레이터 · 보상 트랜잭션 · 단일 실패점(SPOF)
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 중재자 중심 워크플로우 제어 도식 → Ⅴ 중재자 vs 브로커 비교표 / 25점 = Ⅰ~Ⅶ 전개, 129회 기출 EDA 2대 토폴로지 특성, 오케스트레이터 기반 분산 트랜잭션 보상 처리 및 고가용성 설계

## 한 줄 본질
- 이벤트들이 서로 꼬리를 물고 자율 반응하는 브로커 방식에서 에러 발생 시 어느 단계까지 실행되었는지 파악하지 못해 정합성이 깨지는 병목 → 중앙의 이벤트 중재자가 전체 워크플로우의 진행 상태를 관리하며 순서대로 하위 서비스에 작업을 지시하고 실패 시 보상 트랜잭션을 총괄하는 아키텍처 / 중재자의 병목 및 결합도 증가

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  중재자 토폴로지(Mediator Topology) 중앙 지휘 흐름       |
+-------------------------------------------------------------------------+
|                                                                         |
|      [ 클라이언트 주문 요청 ]                                           |
|                 │                                                       |
|                 v                                                       |
|      [ 시작 큐 (Initiator Queue) ]                                      |
|                 │                                                       |
|                 v                                                       |
|  +--------------------------------------------------------------------+ |
|  | [ 이벤트 중재자 (Event Mediator) ] (Orchestrator)                 | |
|  |  - 전체 주문 워크플로우 상태 머신 관리                              | |
|  |  - 1단계: 결제 지시 ──> 2단계: 재고 차감 ──> 3단계: 배송 요청      | |
|  |  - 실패 감지 시: 이전 단계 보상 트랜잭션(결제 취소) 일괄 지휘       | |
|  +──────┬─────────────────────────┬─────────────────────────┬─────────+ |
|         │ (액션 큐 1)              │ (액션 큐 2)              │ (액션 큐 3)  |
|         v                         v                         v           |
|  [ 결제 프로세서 ]         [ 재고 프로세서 ]         [ 배송 프로세서 ]  |
|                                                                         |
|  * 특징: 지휘자가 오케스트라 단원들에게 지휘봉으로 순서대로 연주를 지시함 |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 오케스트레이션(Orchestration): 교향악단 지휘자(Orchestrator)가 각 악기의 연주 시점을 통제하듯, 중앙의 컨트롤러 서비스가 다른 서비스들을 직접 호출하고 응답을 받아 전체 워크플로우를 주도하는 패턴
- 사가 오케스트레이터(Saga Orchestrator): 분산 데이터베이스 환경에서 여러 마이크로서비스에 걸친 장기 실행 트랜잭션을 중앙에서 관리하며, 중간 실패 시 역순으로 롤백(보상 트랜잭션)을 실행시키는 중재자 컴포넌트

## 핵심 통찰
- 중재자 토폴로지는 복잡한 다단계 비즈니스 프로세스(주문-결제-재고-배송-정산)에서 "현재 주문의 상태가 무엇인지"를 단일 지점에서 완벽하게 파악할 수 있는 뛰어난 가시성과 감사(Audit) 추적성을 제공함
- 그러나 중재자 서비스에 너무 많은 비즈니스 계산 로직이 들어가면, 중재자가 모든 것을 알고 하위 서비스는 깡통이 되는 "스마트 중재자, 멍청한 엔드포인트" 안티패턴에 빠져 결합도가 급증함
- 중재자는 전체 시스템 트래픽의 병목이자 단일 실패점(SPOF)이 될 수 있으므로, 중재자 자체를 상태 없는(Stateless) 엔진으로 구성하고 워크플로우 상태는 고성능 분산 저장소에 영속화해야 함

## 이웃 토픽과 구분
- 중재자 토폴로지 vs 브로커 토폴로지: 중재자 = 오케스트레이션(중앙 통제, 복잡한 워크플로우/보상에 최적) / 브로커 = 코레오그래피(탈중앙 연쇄 반응, 단순하고 빠른 고성능 처리에 최적)

## 문제·원인·대책
- 적용 상황: 분산 결제 및 예약 취소 환불 워크플로우 시스템
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 후 호텔 예약 실패 시 비행기 티켓 취소 처리가 누락되어 고객 금전 피해 발생 | 브로커 토폴로지 기반 자율 반응으로 인해 복잡한 다자간 보상 트랜잭션 누락 | 오케스트레이터 기반 중재자 토폴로지 도입 및 사가(Saga) 보상 워크플로우 강제 | 트랜잭션 실패 시 자동 보상 롤백 100% 보장 |
| 중재자 서버에 트래픽이 집중되면서 CPU 100% 병목으로 전체 주문 처리 중단 (SPOF) | 비즈니스 로직 연산을 중재자 내부에서 직접 수행하고 단일 인스턴스로 운영 | 중재자는 오직 상태 전이 라우팅만 수행하고 인스턴스 수평 확장(Scale-Out) 적용 | 단일 실패점 해소 및 처리 용량 선형 확장 |

## 내 의견
