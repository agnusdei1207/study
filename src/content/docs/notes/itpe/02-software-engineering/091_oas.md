## 연관 키워드

- OAS(OpenAPI Specification), API 계약, 기계 가독성, YAML, JSON
- API-First, Mock 서버, SDK, 명세-구현 드리프트

## Ⅰ. OAS의 개요

- 핵심 요약 : OAS는 HTTP API의 경로·작업·파라미터·응답·보안을 기계가 읽는 표준 형식으로 기술하는 API 명세 표준.
- 개념 : HTTP API의 경로·작업·스키마·보안 요구를 기계 가독성을 갖춘 표준 형식으로 기술하는 API 기술 표준 (**OAS** (OpenAPI Specification)). OpenAPI Initiative가 표준을 관리하는 상태.
- 배경 및 필요성 : 자유 서식 문서 중심의 API 안내는 문서·구현·시험 간 불일치(드리프트) 상태를 낳고, 연동 소비자의 오류와 협의 비용 증가.
- 주요 목적 : API 계약의 단일 원천 확보로 설계·구현·문서·시험·연동을 자동화로 연결하는 API 생태계의 일관성 확보.

## Ⅱ. OAS의 특징 및 장점

- 핵심 요약 : 구조화 명세의 기계 가독성이 계약 합의·도구 자동화·일치 검증으로 이어짐.

1. 구조화·기계 가독성 : 경로·작업·스키마·보안을 **YAML**·**JSON**으로 정의 → 도구가 검증·문서 생성·코드 생성 가능.
2. API-First 설계 : 구현 전에 명세를 **API 계약**으로 검토·합의하는 **API-First** 방식 → 소비자와의 병렬 개발·호환성 조기 확정.
3. 도구 생태계 : 명세 기반 문서 UI·**Mock 서버** (구현 전 가짜 응답을 제공하는 시험용 서버)·**SDK** (Software Development Kit, 클라이언트 코드) 자동 생성 → 연동 준비 비용 절감.
4. 계약 시험 자동화 : 구현 응답과 명세를 CI에서 대조 → 명세-구현 일치의 상시 검증.

## Ⅲ. OAS의 개발 흐름 (구조)

- 핵심 요약 : 계약 설계·검토 → Mock·SDK 생성 → 구현·계약 시험 → 배포·문서 게시의 흐름.

```text
[ API-First 개발 흐름 ]

API 요구 정의
   ↓
OAS 명세 작성(YAML/JSON)
   ↓
계약 리뷰·검증(lint)
   ↓
Mock 서버·SDK 생성
   ↓
구현·계약 시험(CI)
   ↓
배포·문서 게시·버전 관리
```

```text
[ 명세의 단일 원천 역할 ]

        OAS 계약(단일 원천)
        ↓               ↓
제공자 구현         소비자 연동 준비
(Mock·계약 시험)   (SDK·문서 활용)
```

- 관리 항목 : 경로·메서드, 파라미터, 스키마, 응답·오류 정의, 인증·인가, 버전.

## Ⅳ. OAS와 자유 서식 API 문서의 비교

- 핵심 요약 : OAS는 검증·자동화가 가능한 표준 명세, 자유 서식 문서는 사람 전용 기술로 갱신·일치가 수동에 의존.

| 비교 축 | OAS 기반 명세 | 자유 서식 API 문서 |
|---|---|---|
| 형식 | YAML·JSON의 표준 구조 | 워드프로세서·위키의 자유 기술 |
| 기계 처리 | 파서로 검증·코드 생성 가능 | 사람 읽기 전용, 자동화 곤란 |
| 일관성 유지 | 스키마 검증·lint로 강제 | 작성자별 서식·수준 편차 |
| 갱신 동기화 | 계약 시험으로 구현과 대조 | 구현 변경 시 수동 갱신 → 드리프트 |
| 적합 환경 | 다수 소비자·외부 공개 API | 소규모 내부 API·임시 연동 |
| 선택 기준 | 계약 중요성·소비자 다수일 때 | 일회성·단순 조회 API일 때 |

## Ⅴ. OAS 적용의 한계와 방안

- 핵심 요약 : 명세-구현 드리프트·명세 비대·버전 혼용을 CI 검증·lint·표준 규칙으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 명세-구현 드리프트 | 명세만 갱신·구현 미반영 → 문서 신뢰 상실 | 계약 시험·CI 차이 검사 | 계약 불일치 발견 건수 |
| 명세 비대·중복 | 스키마 중복·과대 정의 → 유지보수 부담 | 스키마 재사용·lint 규칙·설계 리뷰 | lint 위반 건수 |
| 버전·확장 혼용 | 임의 확장 필드·버전 혼재 → 도구 호환 저하 | OAS 버전·확장 필드 사용 규칙 표준화 | 비호환 문서 비율 |

## Ⅵ. OAS 확산에 대한 기술사적 제언

- 핵심 요약 : 플랫폼 조직·API 거버넌스·대외 연계 창구의 체계로 명세 중심 문화를 제도화.

- 플랫폼 조직 : 명세 템플릿·lint 규칙·보안 스키마 기본값을 공통 기반으로 제공.
- 거버넌스 : API 오너 제도로 계약 승인·변경·폐기 책임을 지정하고 릴리스 절차에 연계.
- 대외 연계 : 공개 API 포털로 명세·키 발급·변경 공지를 일원화.

## Ⅶ. 결론

- 핵심 요약 : OAS는 API 계약을 기계 가독 자산으로 만들어 설계·구현·시험·연동을 자동화로 연결하는 표준.
- 실효성은 명세를 단일 원천으로 유지하는 개발 절차의 정착 수준에 좌우.
