## Ⅰ. 성능 테스트의 개요

- **개념** : 소프트웨어 애플리케이션 및 시스템 인프라가 실제 운영 환경에서 예상되는 다양한 워크로드(동시 접속자 수, 트랜잭션 유입량) 하에서 처리량(TPS), 응답시간(Response Time), 자원 활용률(CPU, Memory, Disk I/O)이 비즈니스 목표(SLA)를 충족하는지 검증하고 시스템의 병목 구간과 임계치를 식별하는 비기능 테스트.
- **배경 및 필요성** : 수강신청, 명절 기차표 예매, 블랙프라이데이 쇼핑몰 등 트래픽 폭증 시 발생하는 서버 크래시, 타임아웃, DB 교착상태를 사전에 검출하여 서비스 중단 방지.
- **핵심 목표** : 시스템 최대 수용 용량(Capacity) 파악, 병목(Bottleneck) 탐지 및 튜닝, 시스템 안정성 보증.

## Ⅱ. 성능 테스트의 5대 주요 유형

```text
   [ 가상 사용자 (Vuser) 부하 패턴 ]
    ▲
    │                                          ┌─── [ 2. 스트레스 테스트 (Stress) ]
    │                                         ┌┘    - 시스템 한계 임계점(Breaking Point) 파악
    │                       ┌─────────────────┘
    │           ┌───────────┘ [ 1. 부하 테스트 (Load) ]
    │           │             - 평상시 피크 트래픽 하에서 성능 목표(SLA) 충족 검증
    │           │
    │     ┌─────┴─────┐ [ 3. 스파이크 테스트 (Spike) ]
    │    ┌┘           └┐ - 순간적인 급격한 트래픽 유입 시 회복력 검증
    │    │             │
    │  ──┴─────────────┴─────────────────────── [ 4. 내구성/침수 테스트 (Soak) ]
    │                                            - 장시간(24시간+) 일정 부하 주입 (메모리 릭 검출)
    └────────────────────────────────────────────────────────────> [ 시간 (Time) ]
```

- **부하 테스트 (Load Test)** : 예상되는 최대 피크 트래픽 환경에서 응답시간과 처리량이 SLA(예: P95 1초 이내)를 충족하는지 검증.
- **스트레스 테스트 (Stress Test)** : 시스템이 다운될 때까지 부하를 단계별로 올려 파두 환계점(Breaking Point)을 찾고, 장애 발생 시 우아하게 실패(Fail-Gracefully)하는지 검증.
- **스파이크 테스트 (Spike Test)** : 대규모 이벤트 오픈 시처럼 순간적으로 트래픽이 5~10배 폭증할 때 자동 확장(Auto-Scaling)과 서킷 브레이커가 정상 동작하는지 검증.
- **내구성 테스트 (Soak / Endurance Test)** : 평균 수준의 부하를 24~72시간 동안 지속 주입하여 점진적인 메모리 누수, 커넥션 누수, 디스크 풀 장애 검출.

## Ⅲ. 성능 테스트 지표 및 주요 병목 원인 비교

| 성능 지표 | 정상 기준치 | 주요 병목 구간 (Bottleneck) | 해결 튜닝 방안 |
|---|---|---|---|
| TPS (Transactions Per Second) | 비즈니스 목표치 이상 | 애플리케이션 스레드 풀 고갈, 락(Lock) 경합 | 비동기 논블로킹 I/O 채택, 스레드 풀 증설 |
| 응답시간 (Response Time) | P95 기준 1~2초 이내 | 슬로우 쿼리, 인덱스 부재, 외부 API 지연 | DB 복합 인덱스 생성, Redis 캐싱 계층 도입 |
| CPU 사용률 | 피크 시 $70\%$ 이하 유지 | 무한 루프, 비효율적 정규식, 과도한 직렬화 | 알고리즘 개선, 프로파일러(JProfiler) 핫스팟 제거 |
| 메모리 사용률 | $80\%$ 이하 유지 | 객체 미해제, 대량 쿼리 결과 전수 로딩 | 페이징 쿼리 처리, 힙 메모리 릭 제거 |
| DB 커넥션 풀 | 사용률 $80\%$ 미만 | 긴 트랜잭션, 트랜잭션 내 외부 API 호출 | 트랜잭션 범위 최소화, 커넥션 풀 크기 최적화 |

## Ⅳ. 성능 테스트(Performance Test)의 주요 한계점 및 해결 방안

- **실제 운영 환경과 테스트 환경 간의 인프라 스케일 격차** :
  - **한계점** : 비용 제약으로 테스트 환경을 운영 환경의 10~20% 축소 사양으로 구축할 경우, 병목 지점이 하드웨어 자원에 가려져 실제 운영 병목 예측 왜곡.
  - **해결 방안** : 스케일 다운 환경의 선형성 검증(Extrapolation Modeling), 클라우드 온디맨드 인프라를 활용하여 테스트 수행 기간에만 운영급 풀 스케일 환경 프로비저닝.
- **부하 발생기(Load Generator) 자체의 자원 병목으로 인한 결과 오염** :
  - **한계점** : JMeter, nGrinder 등 부하 생성 서버의 CPU 100%, 소켓 고갈(TIME_WAIT)로 인해 대상 시스템은 여유가 있음에도 응답시간 지연으로 오판.
  - **해결 방안** : 부하 발생기를 멀티 노드로 분산 클러스터링(k6 Operator on K8s), 부하 발생기의 리소스 모니터링(CPU, Memory, Network) 병행 감사.
- **비현실적인 가상 사용자 행동 모델링 및 캐시 왜곡** :
  - **한계점** : 동일한 파라미터로 단순 반복 요청을 보낼 경우 DB와 웹 캐시가 100% 적중하여 실제 다양한 쿼리가 발생하는 운영 환경의 디스크 I/O 병목 은폐.
  - **해결 방안** : 실운영 APM 액세스 로그 기반 파라미터 풀(Parameter Pool) 무작위화, 프로덕션 트래픽 미러링 도구(GoReplay)를 활용한 실제 트래픽 리플레이 테스트 수행.

## Ⅴ. 고도화된 성능 엔지니어링을 위한 기술사적 제언

- **프로덕션 동형 테스트 환경 및 데이터 스케일링 준수** : 테스트 환경의 DB 데이터가 100건뿐이면 실서버의 1,000만 건 환경에서 풀 테이블 스캔으로 인한 장애를 절대 탐지할 수 없으므로, 데이터 볼륨과 인프라 스펙을 실운영과 동일하게 구성한 환경에서 테스트 수행 필수.
- **CI/CD 파이프라인 내 '성능 회귀 테스트(Performance Regression Testing)' 자동화** : 매 스프린트 배포 시 k6, Locust 기반의 경량 성능 스크립트를 빌드 파이프라인에서 자동 실행하여, 신규 커밋으로 인해 특정 API 응답시간이 $20\%$ 이상 느려지면 배포를 자동으로 차단하는 성능 거버넌스 수립.
