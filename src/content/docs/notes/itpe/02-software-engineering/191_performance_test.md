## 연관 키워드

- 성능 테스트(Performance Test), 비기능 테스트(Non-Functional Test), 부하 테스트(Load Test)
- 스트레스 테스트(Stress Test), 스파이크 테스트(Spike Test), 내구성 테스트(Soak Test)
- 처리량(TPS, Transactions Per Second), 응답시간(Response Time), 병목(Bottleneck), SLA(Service Level Agreement)

## Ⅰ. 성능 테스트의 개요

- 핵심 요약 : 다양한 워크로드 하에서 처리량·응답시간·자원 활용률의 SLA 충족 여부 검증 및 병목 식별의 비기능 테스트.
- 개념 : 소프트웨어 애플리케이션 및 시스템 인프라가 실제 운영 환경에서 예상되는 다양한 워크로드(동시 접속자 수, 트랜잭션 유입량) 하에서 처리량(TPS, Transactions Per Second), 응답시간(Response Time), 자원 활용률(CPU(Central Processing Unit), Memory, Disk I/O(Input/Output))이 비즈니스 목표(SLA, Service Level Agreement)를 충족하는지 검증하고, 시스템의 병목(Bottleneck) 구간과 임계치를 식별하는 비기능 테스트.
- 배경 및 필요성 : 수강신청, 명절 기차표 예매, 블랙프라이데이 쇼핑몰 등 트래픽 폭증 시 발생하는 서버 크래시, 타임아웃, DB(Database) 교착상태의 사전 검출을 통한 서비스 중단 방지.
- 주요 목적 : 시스템 최대 수용 용량(Capacity) 파악, 병목 탐지 및 튜닝, 시스템 안정성 보증.

## Ⅱ. 성능 테스트의 특징

- 핵심 요약 : 4대 부하 유형(부하·스트레스·스파이크·내구성)과 정량 지표 기반 판정의 결합 체계.

1. 부하 테스트(Load Test) : 예상되는 최대 피크 트래픽 환경에서 응답시간과 처리량의 SLA(예 : P95 1초 이내) 충족 검증.
2. 스트레스 테스트(Stress Test) : 시스템이 다운될 때까지 부하를 단계별로 상향하여 한계점(Breaking Point) 파악, 장애 발생 시 우아한 실패(Fail-Gracefully) 동작 검증.
3. 스파이크 테스트(Spike Test) : 대규모 이벤트 오픈 시처럼 트래픽이 순간적으로 급증할 때 자동 확장(Auto-Scaling)과 서킷 브레이커(Circuit Breaker)의 정상 동작 검증.
4. 내구성 테스트(Soak/Endurance Test) : 평균 수준의 부하를 24~72시간 동안 지속 주입하여 점진적인 메모리 누수, 커넥션 누수, 디스크 풀 장애 검출.
5. 정량 지표 기반 판정 : TPS, 응답시간, CPU·메모리 사용률, DB 커넥션 풀 사용률의 계측값 기반 SLA 판정.

## Ⅲ. 성능 테스트의 구조 (흐름)

- 핵심 요약 : 부하 모델링→스크립트 기록→부하 주입→모니터링→분석·튜닝의 반복 순환 구조.
- 유형별 Vuser(Virtual User) 부하 패턴.

```text
[ Vuser 부하 패턴 : 세로=부하, 가로=시간 ]

 1. 부하 (Load)
       ____________
      /           ^SLA 목표
 ____/

 2. 스트레스 (Stress)
            /  <- 한계점
           /     (Breaking Point)
 _________/

 3. 스파이크 (Spike)
       __
   ___|  |___
 __|          <- 순간 급증

 4. 내구성/침수 (Soak)
 ________________
   (24시간+ 일정 부하 유지)
```

- 성능 테스트 수행 프로세스.

```text
[ 성능 테스트 수행 프로세스 ]
[ SLA 목표 및 시나리오 정의 ]
          ↓
[ 부하 모델링 및 스크립트 기록 ]
          ↓
[ 부하 주입 및 모니터링 ]
 (TPS, 응답시간, 자원 사용률 계측)
          ↓
[ 병목 분석 및 튜닝 ]
          ↓
[ 재측정 및 결과 보고 ] ──→ (미충족 시 상단 재반복)
```

## Ⅳ. 성능 지표별 병목 구간 및 튜닝 방안 비교

- 핵심 요약 : 지표별 정상 기준치와 병목 구간, 해결 튜닝 방안의 대응 관계.

| 성능 지표 | 정상 기준치 | 주요 병목 구간 (Bottleneck) | 해결 튜닝 방안 |
|---|---|---|---|
| TPS (Transactions Per Second) | 비즈니스 목표치 이상 | 애플리케이션 스레드 풀 고갈, 락(Lock) 경합 | 비동기 논블로킹 I/O 채택, 스레드 풀 증설 |
| 응답시간 (Response Time) | P95 기준 1~2초 이내 | 슬로우 쿼리, 인덱스 부재, 외부 API(Application Programming Interface) 지연 | DB 복합 인덱스 생성, Redis 캐싱 계층 도입 |
| CPU(Central Processing Unit) 사용률 | 피크 시 $70\%$ 이하 유지 | 무한 루프, 비효율적 정규식, 과도한 직렬화 | 알고리즘 개선, 프로파일러(JProfiler) 핫스팟 제거 |
| 메모리 사용률 | $80\%$ 이하 유지 | 객체 미해제, 대량 쿼리 결과 전수 로딩 | 페이징 쿼리 처리, 힙 메모리 릭 제거 |
| DB 커넥션 풀 | 사용률 $80\%$ 미만 | 긴 트랜잭션, 트랜잭션 내 외부 API 호출 | 트랜잭션 범위 최소화, 커넥션 풀 크기 최적화 |

## Ⅴ. 성능 테스트의 장점과 한계

- 핵심 요약 : 장애 사전 검출·용량 계획의 장점과 환경 격차·부하 발생기 병목·비현실적 모델링의 한계 공존.

- 장점
  1. 트래픽 폭증 상황의 서버 크래시, 타임아웃, DB 교착상태의 사전 검출.
  2. 최대 수용 용량 산정을 통한 인프라 용량 계획 및 스케일링 근거 확보.
  3. 병목 구간의 계량적 식별을 통한 튜닝 우선순위 결정.

- 한계점 1 : 실제 운영 환경과 테스트 환경 간의 인프라 스케일 격차
  - 한계점 : 비용 제약으로 테스트 환경을 운영 환경보다 크게 축소된 사양으로 구축할 경우, 병목 지점이 하드웨어 자원에 가려져 실제 운영 병목 예측 왜곡.
  - 해결 방안 : 스케일 다운 환경의 선형성 검증(Extrapolation Modeling), 클라우드 온디맨드 인프라를 활용하여 테스트 수행 기간에만 운영급 풀 스케일 환경 프로비저닝.
- 한계점 2 : 부하 발생기(Load Generator) 자체의 자원 병목으로 인한 결과 오염
  - 한계점 : JMeter, nGrinder 등 부하 생성 서버의 CPU 100%, 소켓 고갈(TIME_WAIT)로 인해 대상 시스템은 여유가 있음에도 응답시간 지연으로 오판.
  - 해결 방안 : 부하 발생기의 멀티 노드 분산 클러스터링(k6 Operator on Kubernetes), 부하 발생기의 리소스 모니터링(CPU, Memory, Network) 병행 감사.
- 한계점 3 : 비현실적인 가상 사용자 행동 모델링 및 캐시 왜곡
  - 한계점 : 동일한 파라미터로 단순 반복 요청을 보낼 경우 DB와 웹 캐시가 100% 적중하여 실제 다양한 쿼리가 발생하는 운영 환경의 디스크 I/O 병목 은폐.
  - 해결 방안 : 실운영 APM(Application Performance Monitoring) 액세스 로그 기반 파라미터 풀(Parameter Pool) 무작위화, 프로덕션 트래픽 미러링 도구(GoReplay)를 활용한 실제 트래픽 리플레이 테스트 수행.

## Ⅵ. 고도화된 성능 엔지니어링을 위한 기술사적 제언

- 핵심 요약 : 프로덕션 동형 환경 구성과 CI/CD 기반 성능 회귀 테스트 자동화의 거버넌스 수립.
- 프로덕션 동형 테스트 환경 및 데이터 스케일링 준수 : 테스트 환경의 DB 데이터가 100건뿐이면 실서버의 1,000만 건 환경에서 풀 테이블 스캔으로 인한 장애를 절대 탐지할 수 없으므로, 데이터 볼륨과 인프라 스펙을 실운영과 동일하게 구성한 환경에서의 테스트 수행 필수.
- CI/CD(Continuous Integration/Continuous Delivery) 파이프라인 내 성능 회귀 테스트(Performance Regression Testing) 자동화 : 매 스프린트 배포 시 k6, Locust 기반의 경량 성능 스크립트를 빌드 파이프라인에서 자동 실행하여, 신규 커밋으로 인해 특정 API 응답시간이 $20\%$ 이상 느려지면 배포를 자동 차단하는 성능 거버넌스 수립.

## Ⅶ. 결론

- 핵심 요약 : 성능 테스트는 SLA 기반 용량·병목 검증을 통한 서비스 안정성 보증 수단.
- 요약 : 부하·스트레스·스파이크·내구성의 4대 유형으로 TPS, 응답시간, 자원 사용률을 정량 검증하는 비기능 테스트 체계.
- 시사점 : 프로덕션 동형 환경, 현실적 부하 모델링, CI/CD 성능 게이트의 결합이 성능 품질 거버넌스의 핵심.
