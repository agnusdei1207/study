## 연관 키워드

- 성능 테스트(Performance Test), 비기능 테스트(Non-Functional Test), 부하 테스트(Load Test)
- 스트레스 테스트(Stress Test), 스파이크 테스트(Spike Test), 내구성 테스트(Soak Test)
- 처리량(TPS, Transactions Per Second), 응답시간(Response Time), 병목(Bottleneck), SLA(Service Level Agreement)

## Ⅰ. 성능 테스트의 개요

- 핵심 요약 : 다양한 워크로드에서 처리량·응답시간·자원 사용률이 SLA를 충족하는지 검증하고 병목을 식별하는 비기능 테스트.
- 개념 : 시스템이 예상되는 워크로드(동시 접속자 수, 트랜잭션 유입량)에서 **처리량** (TPS, Transactions Per Second), **응답시간** (Response Time), 자원 사용률이 비즈니스 목표인 **SLA** (Service Level Agreement, 서비스 수준 협약)를 충족하는지 검증하고, **병목** (Bottleneck, 전체 성능을 제한하는 지점)을 찾아내는 **비기능 테스트** (Non-Functional Test).
- 배경 및 필요성 : 수강 신청, 명절 기차표 예매, 대형 할인 행사처럼 트래픽이 한꺼번에 몰리는 상황에서 서버 과부하, 타임아웃, DB(Database) 교착상태가 발생해 서비스가 중단되는 사고를 사전에 막아야 함.
- 주요 목적 : 최대 수용 용량 파악, 병목 탐지와 튜닝, 운영 안정성 보증.

## Ⅱ. 성능 테스트의 특징 및 장점

- 핵심 요약 : 부하 유형별 시나리오와 정량 지표 판정을 결합하여 한계와 안정성을 함께 검증하는 체계.

1. **부하 테스트** (Load Test) : 예상 피크 트래픽에서 응답시간과 처리량이 SLA를 충족하는지 확인 → 운영 기준의 적합성 입증.
2. **스트레스 테스트** (Stress Test) : 부하를 단계적으로 올려 한계점(Breaking Point)을 찾고 장애 시 우아한 실패(Fail-Gracefully) 여부를 확인 → 장애 대응 설계의 실효성 검증.
3. **스파이크 테스트** (Spike Test) : 트래픽이 순간적으로 급증할 때 자동 확장(Auto-Scaling)과 서킷 브레이커(Circuit Breaker)가 정상 동작하는지 확인 → 이벤트성 폭주 대응력 확보.
4. **내구성 테스트** (Soak Test) : 평균 수준의 부하를 장시간 유지하여 메모리 누수, 커넥션 누수, 디스크 고갈을 검출 → 장기 운영 안정성 확보.
5. 정량 지표 판정 : TPS, 응답시간, CPU(Central Processing Unit)와 메모리 사용률, DB 커넥션 풀 사용률을 계측하여 SLA 충족 여부를 객관적으로 판정 → 감에 의존하지 않는 튜닝 근거 확보.

## Ⅲ. 성능 테스트의 구조 (흐름)

- 핵심 요약 : 목표 정의에서 부하 주입, 병목 분석, 재측정에 이르는 순환형 수행 흐름.

```text
[ 성능 테스트 수행 순환 ]

[ SLA 목표 및 시나리오 정의 ]
      ↓
[ 부하 모델링 및 스크립트 기록 ]
      ↓
[ 부하 주입 및 모니터링 ]
  (TPS, 응답시간, 자원 사용률 계측)
      ↓
[ 병목 분석 및 튜닝 ]
      ↓
[ 재측정 및 결과 보고 ]
      ↑ 미충족 시 튜닝 후 반복
```

```text
[ 부하 유형별 시간 흐름 ]

 부하    : 예상 피크 수준을 일정하게 유지
 스트레스 : 단계적으로 올려 한계점 탐색
 스파이크 : 짧은 시간에 급증 후 복귀
 내구성  : 평균 부하를 장시간 지속
```

## Ⅳ. 성능 지표별 병목과 튜닝 방안 비교

- 핵심 요약 : 지표마다 전형적인 병목 구간과 튜닝 방안이 대응되므로, 측정값과 병목 위치를 연결해 해결책을 고름.

| 성능 지표 | 판정 기준 | 주요 병목 구간 | 해결 튜닝 방안 |
| --- | --- | --- | --- |
| 처리량 (TPS) | 비즈니스 목표치 이상 유지 | 애플리케이션 스레드 풀 고갈, 락(Lock) 경합 | 비동기 처리 도입, 스레드 풀 용량 조정 |
| 응답시간 | 목표 백분위 응답시간 충족 | 슬로우 쿼리, 인덱스 부재, 외부 API(Application Programming Interface) 지연 | 인덱스 설계 개선, 캐싱 계층 도입 |
| CPU 사용률 | 피크 시 여유를 둔 수준 유지 | 무한 루프, 비효율 정규식, 과도한 직렬화 | 알고리즘 개선, 프로파일러로 핫스팟 제거 |
| 메모리 사용률 | 누수 없이 안정적 유지 | 객체 미해제, 대량 결과의 전수 로딩 | 페이징 처리, 메모리 누수 제거 |
| DB 커넥션 풀 | 고갈 없이 여유 유지 | 긴 트랜잭션, 트랜잭션 내부의 외부 API 호출 | 트랜잭션 범위 축소, 풀 크기 최적화 |

- 선택 기준 : 측정된 지표 중 가장 먼저 한계에 닿는 자원을 병목으로 보고, 그 구간의 튜닝을 우선함.

## Ⅴ. 성능 테스트의 한계와 방안

- 핵심 요약 : 환경 격차, 부하 발생기 오염, 비현실적 부하 모델이 측정 결과를 왜곡하는 한계이며 환경 동형화와 실트래픽 재현으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 운영과 테스트 환경의 인프라 격차 | 비용 제약으로 축소 사양에서 시험하면 병목이 실제와 다르게 나타남 | 축소 환경의 선형성 검증, 테스트 기간에만 운영급 환경을 임시 프로비저닝 | 환경 간 자원 비율, 예측 오차 |
| 부하 발생기 자체의 병목 | 부하 생성 서버의 CPU나 소켓 고갈로 대상 시스템이 여유 있어도 지연으로 오판 | 부하 발생기를 다중 노드로 분산하고 발생기 자원을 함께 모니터링 | 발생기 CPU·네트워크 사용률 |
| 비현실적 부하 모델과 캐시 왜곡 | 같은 요청의 반복으로 캐시 적중률이 과도하게 높아져 운영의 디스크 I/O 병목이 가려짐 | 운영 로그 기반 파라미터 무작위화, 실트래픽 복제(미러링) 재현 | 캐시 적중률, 쿼리 다양성 |

## Ⅵ. 고도화된 성능 엔지니어링을 위한 기술사적 제언

- 핵심 요약 : 운영과 같은 데이터 규모의 테스트 환경을 갖추고, 배포 파이프라인에 성능 회귀 테스트를 넣는 거버넌스 수립.
- 프로덕션 동형 환경 확보 : 품질 조직은 테스트 환경의 데이터 규모와 인프라 사양을 운영과 같은 수준으로 맞추어야 하며, 소량 데이터에서는 드러나지 않는 풀 테이블 스캔 장애를 이 방식으로만 찾을 수 있다.
- 성능 회귀 테스트의 자동화 : 개발 조직은 CI/CD(Continuous Integration/Continuous Delivery) 파이프라인에 경량 성능 스크립트를 넣어 매 배포마다 실행하고, 핵심 API의 응답시간이 기준 대비 유의미하게 나빠지면 배포를 차단하는 게이트를 두는 것이 바람직하다.

## Ⅶ. 결론

- 핵심 요약 : 성능 테스트는 SLA 기준의 용량과 병목을 검증하여 서비스 안정성을 보증하는 수단.
- 시사점 : 4대 부하 유형과 정량 지표를 운영 조건에 맞춰 반복 측정하는 것이 성능 품질의 출발점임.
