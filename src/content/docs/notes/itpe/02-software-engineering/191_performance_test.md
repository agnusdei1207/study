## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 테스팅·품질 → 성능 테스트(Performance Test)

## 지식 위치

소프트웨어공학 > 비기능 테스트 > 성능 테스트

## 30초 인출

- 본질: 특정 가상 부하(Virtual Users, Concurrency)를 시스템에 지속적/점진적으로 인가하여 응답시간(Response Time), 처리량(TPS), 자원 사용률(CPU/메모리)을 계측하고 아키텍처적 병목을 규명하는 비기능 테스트
- 메커니즘: 성능 목표(SLA/SLO) 및 워크로드 모델링 → 테스트 환경 구축 및 데이터 세팅 → 부하 인가(Load, Stress, Soak, Spike) → APM 프로파일링을 통한 병목 식별 → 인프라/코드 튜닝 및 재검증
- 통찰: 평균 응답시간 중심의 합격 판정은 소수 사용자의 심각한 타임아웃(Tail Latency)과 점진적 메모리 누수를 간과하게 하므로 P99 백분위수 지표와 장시간 내구성(Soak) 테스트 병행 필수

<details>
<summary>핵심 용어</summary>

- **성능 테스트 (Performance Testing)** : 시스템의 응답 속도, 처리 능력, 신뢰성 및 확장성을 평가하기 위한 모든 비기능 테스트의 총칭
- **부하 테스트 (Load Testing)** : 예상되는 정상 운영 부하 및 피크(Peak) 부하 조건에서 시스템이 성능 목표를 달성하는지 검증하는 테스트
- **스트레스 테스트 (Stress Testing)** : 설계 임계치를 초과하는 극한의 과부하를 가하여 시스템의 파괴 시점(Breaking Point)과 우아한 성능 저하(Graceful Degradation)를 평가하는 테스트
- **내구성 테스트 (Endurance / Soak Testing)** : 일정 수준의 부하를 장시간(수 시간~수일) 지속 인가하여 메모리 누수(Memory Leak) 및 자원 고갈 현상을 검증하는 테스트
- **스파이크 테스트 (Spike Testing)** : 티켓 예매, 수강 신청 등 순간적으로 폭증하는 트래픽 유입 시 시스템의 충격 흡수 및 복구 능력을 평가하는 테스트
- **TPS (Transactions Per Second)** : 시스템이 1초당 성공적으로 처리 완료한 비즈니스 트랜잭션의 수
</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 성능 테스트(Performance Test)의 4대 주요 유형(Load, Stress, Endurance, Spike)을 비교하고, 엔터프라이즈 환경에서의 성능 테스트 단계별 수행 절차 및 APM을 활용한 성능 병목 진단 방안을 제시하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 실제 운영 환경과 유사한 부하 조건을 인위적으로 발생시켜 시스템의 처리량(Throughput), 응답시간(Latency), 자원 활용률(Utilization)을 측정하고 시스템의 한계 용량과 병목을 찾아내는 검증 활동 |
| 목적 | 오픈 후 대규모 장애 사전 방지, 서비스 수준 협약(SLA) 충족 여부 확인, 시스템 증설/사이징(Capacity Planning) 및 성능 튜닝 근거 확보 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 정량적 비기능 평가 | 기능의 정답 여부(Pass/Fail)가 아닌 초당 처리량(TPS), 백분위수 응답 지연(P95/P99), CPU % 등 정량 수치 계측 |
| 환경 유사성 의존 | 운영 환경과 동일한 하드웨어 스펙, 네트워크 대역폭, DB 데이터 볼륨(수억 건)이 갖추어져야 신뢰성 확보 |
| 목표 부하 모델링 (Workload) | 동시 접속자 수, 요청 간격(Think Time), 사용자 업무 비율(조회 80%, 결제 20%)을 정밀 모사 |
| 반복적 튜닝 파이프라인 | 병목 발견 시 쿼리 튜닝, 인덱스 추가, JVM 힙 조정, 커넥션 풀 확장 후 동일 조건에서 재검증 수행 |

대규모 트래픽이 집중되는 전자상거래, 금융, 공공 포털 오픈 전 반드시 통과해야 하는 관문(Quality Gate).

## Ⅲ. 체계·프로세스

```text
[성능 테스트 엔드투엔드 수행 체계]

[1. 성능 요건 정의 및 계획]
  - SLA 지표 확정 (목표 TPS, P99 응답시간 ≤ 1초, 에러율 ≤ 0.01%)
  - 업무 시나리오 및 사용자 행동 모델링 (Think Time, Pacing)
       │
       ▼
[2. 테스트베드 및 부하 생성기 구축]
  - 운영 동급 테스트베드 환경 구성 (인스턴스, 네트워크)
  - 대용량 가상 데이터 적재 (DB 1억 건 이상 볼륨 모사)
  - 부하 발생 도구(nGrinder, JMeter, K6) 분산 에이전트 배치
       │
       ▼
[3. 유형별 성능 테스트 실행]
  ┌────────────────────────────────────────────────────────┐
  │ 1) Smoke Test     : 스크립트 정상 동작 여부 최소 부하 검증 │
  │ 2) Load Test      : 목표 부하 수준(예: 3,000 TPS) 안정성 검증│
  │ 3) Stress Test    : 한계 부하까지 점진 증폭 (Breaking Point) │
  │ 4) Endurance Test : 피크 부하의 70%로 24시간 장기 연속 실행 │
  └────────────────────────────────────────────────────────┘
       │
       ▼
[4. APM 기반 병목 분석 및 튜닝]
  - Pinpoint / Datadog 연계: 느린 SQL 쿼리, DB Lock, Thread Pool 고갈 탐지
  - 인프라 / 애플리케이션 튜닝 후 동일 조건 재테스트 ──► 최종 합격 판정
```

요건 정의부터 워크로드 모델링, 유형별 부하 인가, APM 연계 병목 진단 및 튜닝 재검증으로 이어지는 프로세스.

## Ⅳ. 종류·비교

| 비교 항목 | 부하 테스트 (Load Test) | 스트레스 테스트 (Stress Test) | 내구성 테스트 (Endurance / Soak) | 스파이크 테스트 (Spike Test) |
|---|---|---|---|---|
| **테스트 목적** | 목표 부하 상태에서의 SLA 준수 검증 | 시스템 임계 한계점 및 장애 복구 검증 | 장시간 구동 시 메모리 누수/고갈 검증 | 순간적 트래픽 폭증 시 탄력성 검증 |
| **인가 부하 수준** | 평시 ~ 최대 예상 피크 트래픽 수준 | 예상치를 초과하는 극한의 부하 (150%~200%+) | 정상 운영 부하의 60~80% 수준 | 순식간에 수십 배로 급증 후 급감 |
| **실행 시간** | 1시간 ~ 2시간 | 30분 ~ 1시간 (한계 도달 시까지) | **12시간 ~ 72시간 장시간 연속** | 수 분 이내 단시간 급변 |
| **주요 관측 지표** | 목표 TPS 달성률, P95 지연시간 | Breaking Point 임계치, 에러율, 복구 시간 | JVM Old Gen 메모리 추세, DB 풀 누수 | 오토스케일링 지연, 서킷브레이커 동작 |
| **실무 적용 사례** | 신규 서비스 정기 오픈 전 성능 검증 | 블랙프라이데이/명절 이벤트 대비 한계 측정 | 24/7 무중단 은행 코어 뱅킹 검증 | 백신 예약, 인기 콘서트 티켓 예매 오픈 |

### 성능 테스트 핵심 관측 지표 비교

| 지표 범주 | 핵심 메트릭 | 의미 및 해석 기준 |
|---|---|---|
| **처리량 (Throughput)** | TPS (Transactions Per Second) | 시스템이 초당 완수한 비즈니스 트랜잭션 건수 (높을수록 우수) |
| **지연시간 (Latency)** | Response Time (P50, P90, P99) | 요청부터 응답까지 소요된 시간 (평균보다 백분위 P99 지연이 중요) |
| **동시성 (Concurrency)** | Virtual Users (VU), Active Threads | 시스템 내부에서 동시에 요청을 처리 중인 가상 사용자 수 |
| **에러율 (Error Rate)** | HTTP 5xx %, 타임아웃 비율 | 전체 요청 대비 실패 응답 비율 (통상 0.1% 미만 요구) |
| **시스템 자원** | CPU %, Memory %, Disk I/O, Network | 피크 시 CPU 80% 이하 유지, 메모리 우상향(Leak) 여부 확인 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 부하 발생기(JMeter Agent) 자체의 CPU/네트워크 병목으로 인해 시스템 성능이 저평가되는 현상 | 부하 생성기 서버의 리소스를 상시 모니터링하고 에이전트 노드를 수평 분산(Distributed Master-Worker) 구성 |
| 실제 사용자의 불규칙한 페이지 탐색 시간(Think Time)을 배제한 기계적 연타 요청으로 왜곡된 부하 발생 | 사용자 여정(User Journey) 기반 통계적 분포(Gaussian/Random Think Time)를 스크립트에 반영 |
| 외부 연계 기관(카드 결제사, SMS 발송망 등)의 테스트 환경 호출 제약 및 비용 발생 | WireMock 등 서비스 가상화(Service Virtualization) 도구를 활용하여 외부 응답을 초고속 모킹 처리 |

## Ⅵ. 제언

일회성 오픈 직전 테스트 관행을 탈피하고, CI/CD 배포 파이프라인에 경량 부하 테스트(K6 기반)를 내장하여 코드 변경 시마다 성능 회귀를 지속 탐지하는 연속적 성능 엔지니어링 확립 필요.

```text
[지속적 성능 엔지니어링 파이프라인]
  Git PR → CI 파이프라인 (K6 자동 부하 테스트) → Datadog/Pinpoint APM 병목 자동 리포트 → SLA 충족 시 배포
```

| 검증 단계 | 전통적 성능 테스트 | 지속적 성능 엔지니어링 (Continuous Testing) |
|---|---|---|
| 수행 주기 | 시스템 오픈 직전 1~2회 집중 수행 | 매주/매 스프린트 단위 자동화 빌드 시 상시 검증 |
| 분석 방식 | 사후 로그 분석 및 엑셀 수기 리포트 | APM 트레이스 및 분산 추적(Distributed Tracing) 실시간 연동 |
