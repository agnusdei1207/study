소프트웨어 공학 → 설계·아키텍처 → **TA와 AA 역할 비교 및 협업**

## 30초 인출

- 본질: TA(Technical Architect)는 실행 환경의 기술 구조를, AA(Application Architect)는 업무 요구를 구현하는 애플리케이션 구조를 설계하는 아키텍트
- 메커니즘: AA가 서비스 경계와 인터페이스를 정하면 TA가 그 서비스를 실행할 인프라·배포·보안 구조를 설계하고 서로 제약을 조율
- 통찰: 두 아키텍트가 따로 설계하면 서비스 분해와 배포·운영 구조가 어긋나므로 서비스 경계·배포 단위·성능 목표를 함께 합의하고 결정을 아키텍처 결정 기록으로 남김

<details>
<summary>핵심 용어</summary>

- **TA(Technical Architect)** : 인프라·플랫폼·네트워크·보안 등 시스템의 기술 아키텍처를 설계하는 역할
- **AA(Application Architect)** : 업무 요구를 구현하는 애플리케이션의 구조·서비스·인터페이스를 설계하는 역할
- **아키텍처 결정 기록(ADR, Architecture Decision Record)** : 결정의 배경·대안·이유를 남기는 문서
- **서비스 경계** : 애플리케이션을 나누는 서비스 단위의 범위
- **비기능 요구사항** : 성능·가용성·보안처럼 기능의 품질 조건

</details>

> 클라우드 네이티브 환경으로 전환·구축하는 프로젝트에서 TA(Technical Architect)와 AA(Application Architect)의 역할을 비교하고, 협업의 중요성과 협업 방안을 설명하시오. (예상)

---

## 2~4교시 25점 답안

## Ⅰ. TA와 AA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **TA** 는 시스템의 기술 구조를, **AA** 는 애플리케이션 구조를 설계하는 아키텍트 |
| 목적 | 업무 요구와 기술 환경이 맞물리는 전체 아키텍처 확립 |

## Ⅱ. 두 역할의 특징

| 특징 | 의미 |
|---|---|
| 관점 분담 | 업무 구현 구조(AA)와 실행 환경 구조(TA) |
| 상호 제약 | 서비스 분해는 배포·운영 방식에, 인프라는 서비스 요구에 영향 |
| 공동 책임 | 품질속성 달성에 대한 공동 책임 |

## Ⅲ. 프로젝트에서의 역할과 협업 흐름

### TA와 AA의 관계

```text
업무 요구
    ↓
AA: 애플리케이션 구조 ── 서비스 경계·API·데이터 구조
    ↕ 협업 (서비스 경계·배포 단위·성능 목표)
TA: 기술 구조 ── 컨테이너·배포 환경·네트워크·보안
    ↓
클라우드 네이티브 시스템
```

### 확대: 협업 흐름

```text
요구·품질속성 합의
    ↓
AA 서비스 분해안 ↔ TA 배포·인프라안 검토
    ↓
충돌 항목 조정 → 아키텍처 결정 기록
```

## Ⅳ. TA와 AA의 역할 비교와 협업 방안

### 역할 비교

| 비교 항목 | TA | AA |
|---|---|---|
| 범위 | 인프라·플랫폼·네트워크·보안 | 업무 서비스·애플리케이션 구조 |
| 책임·목표 | 성능·가용성·보안·확장성을 만족하는 실행 환경 | 업무 요구를 충족하는 서비스 구조와 인터페이스 |
| 주요 산출물 | 기술 아키텍처 정의서, 인프라·배포 구성도 | 애플리케이션 아키텍처 정의서, 서비스·API 명세 |

### 협업의 중요성과 방안

| 구분 | 내용 |
|---|---|
| 중요성 | 서비스 분해와 배포·운영 구조 불일치 시 성능·비용·장애 문제 발생 |
| 방안 1 | 서비스 경계·배포 단위·성능 목표를 공동 검토 |
| 방안 2 | 아키텍처 결정 기록으로 결정과 근거 공유 |
| 방안 3 | 비기능 요구를 시나리오로 정의해 양쪽이 같은 기준으로 검증 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 서비스 분해가 배포 환경과 어긋나 재설계 발생 | 설계 초기에 서비스 경계와 배포 단위를 공동 검토 |
| 결정 근거 미공유로 후속 변경 때 의도 소실 | 결정 기록으로 근거 보존 |
| 성능·보안 요구의 양측 해석 차이 | 품질속성 시나리오로 기준 통일 |

## Ⅵ. 제언

서비스 경계와 배포 단위를 TA·AA가 함께 정하고, 결정 내용과 근거를 아키텍처 결정 기록으로 남겨 후속 변경에 활용

### 공동 결정 절차

```text
품질속성 시나리오 정의
    ↓
AA·TA 공동 검토 (서비스 경계·배포 단위)
    ↓
결정 → 결정 기록 → 설계 반영
```

### 확대: 충돌 처리

```text
서비스 요구 ↔ 인프라 제약
    ├─ 조정 가능 → 결정 기록
    └─ 조정 불가 → 요구·경계 재검토
```

### 선택 근거: 역할별 독립 설계와의 비교

| 구분 | 독립 설계 | 제언: 공동 결정 |
|---|---|---|
| 정합성 | 후반 불일치 발견 | 초기 조정 |
| 근거 보존 | 개인 기억 | 결정 기록 |
| 재설계 | 잦음 | 감소 |
