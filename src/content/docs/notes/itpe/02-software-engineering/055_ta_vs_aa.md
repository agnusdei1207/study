## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 아키텍처 설계·역할 → **TA와 AA 역할 비교 및 협업**

## 30초 인출

- 본질: 비즈니스 기능 요구를 논리적 컴포넌트와 API로 구조화하는 AA(Application Architect)와 시스템 품질속성을 만족하는 물리적 인프라 및 기술 스택을 설계하는 TA(Technical Architect)의 협력 체계
- 메커니즘: 비즈니스 및 품질 요구 분석 → AA의 논리 아키텍처와 TA의 기술/물리 아키텍처 간 1:1 매핑 → 아키텍처 결정 레코드(ADR) 작성 및 공동 적합성 검증
- 통찰: 논리 설계와 물리 인프라가 격리 결정될 경우 심각한 네트워크 지연과 가용성 결함이 발생하므로 품질 시나리오 기반의 아키텍처 피트니스 함수 및 공동 성능 검증 필수

<details>
<summary>핵심 용어</summary>

- **AA (Application Architect)** : 도메인 비즈니스 요구사항을 충족하기 위한 소프트웨어 컴포넌트, 모듈 분할, API 인터페이스, 데이터 흐름을 설계하는 아키텍트
- **TA (Technical Architect)** : 시스템의 비기능 품질속성(성능, 고가용성, 보안, 확장성)을 보장하기 위한 하드웨어, 클라우드, 네트워크, 미들웨어를 설계하는 아키텍트
- **ADR (Architecture Decision Record)** : 중요한 아키텍처 설계 결정 시 결정 배경, 고려한 대안, 선택 이유, 결과를 정형화하여 기록하는 문서
- **Logical to Physical Mapping** : AA의 논리적 소프트웨어 모듈이 TA의 물리적 컨테이너 노드 및 분산 클러스터에 배포되는 연계 매핑 구조
- **Architecture Fitness Function** : 설계된 아키텍처가 목표한 성능, 가용성, 모듈성 품질 지표를 지속적으로 만족하는지 CI/CD에서 자동 검증하는 메트릭

</details>

## 2~4교시 25점 답안

## Ⅰ. TA와 AA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 대규모 소프트웨어 프로젝트에서 비즈니스 로직과 컴포넌트 구조를 담당하는 **애플리케이션 아키텍트(AA)** 와 이를 안정적으로 구동하는 하드웨어·미들웨어·인프라 기술 기반을 담당하는 **테크니컬 아키텍트(TA)** 의 역할 분담 및 유기적 협업 체계 |
| 목적 | 기능적 완전성과 비기능 품질속성(성능, 고가용성, 보안) 간의 정합성 달성, 아키텍처 불일치로 인한 시스템 오픈 장애 원천 차단 |

## Ⅱ. TA와 AA 협업의 핵심 특징

| 특징 | 의미 |
|---|---|
| 논리-물리 이원화와 통합 | 소프트웨어 로직(Logical View)과 시스템 배포 인프라(Deployment View)의 명확한 역할 분리 및 정렬 |
| 품질 시나리오 중심 협력 | 응답 시간, TPS, 복구 시간(RTO) 등 핵심 품질속성을 매개로 아키텍처 공동 의사결정 수행 |
| ADR 기반 결정 추적성 | 기술 스택 선정 및 컴포넌트 분할 시 고려한 기술적 트레이드오프(Trade-off)를 ADR로 투명하게 자산화 |
| 지속적 적합성 검증 | 설계 단계에 그치지 않고 통합 성능 시험 및 카오스 엔지니어링을 통해 실제 인프라 적합성 공동 검증 |

## Ⅲ. TA·AA 아키텍처 협업 체계 및 프로세스

### 클라우드 네이티브 환경에서의 AA-TA 상호작용 및 매핑 구조

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [요구사항 정의 (기능 요구 + 품질 시나리오)]           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
           ┌────────────────────────┴────────────────────────┐
           ▼ (Logical View 설계)                             ▼ (Physical View 설계)
┌─────────────────────────────────────┐   ┌─────────────────────────────────────┐
│ [AA: 애플리케이션 아키텍트]         │   │ [TA: 테크니컬 아키텍트]             │
│ - 도메인 모델링 (DDD Bounded Context)│   │ - 클라우드 멀티 리전 VPC 네트워크   │
│ - 마이크로서비스 컴포넌트 분할      │   │ - Kubernetes 클러스터 노드 사이징   │
│ - REST / gRPC API 인터페이스 명세    │   │ - Kafka 브로커 및 RDB/NoSQL 클러스터│
│ - 데이터 흐름 및 상태 관리 패턴     │   │ - WAF, L7 로드밸런서, mTLS 보안     │
└──────────────────┬──────────────────┘   └──────────────────┬──────────────────┘
                   │                                         │
                   └────────────────────┬────────────────────┘
                                        ▼ (논리-물리 1:1 매핑 및 ADR 수립)
┌────────────────────────────────────────────────────────────────────────┐
│ [공동 아키텍처 의사결정 레코드 (ADR)]                                   │
│  - "주문 서비스(AA 논리 컴포넌트)를 K8s Pod 10개로 수평 확장(TA 구성)"  │
│  - "결제 서비스 통신은 동기 REST 대신 Kafka 비동기 큐잉으로 결합도 격리" │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ [공동 검증 단계: 아키텍처 피트니스 함수 + 성능 부하 시험(nGrinder)]    │
│  - 1만 TPS 부하 주입 시 AA 코드 병목과 TA 인프라 리소스 포화 공동 분석│
└────────────────────────────────────────────────────────────────────────┘
```

### 아키텍처 생명주기별 AA와 TA의 협업 프로세스

| 단계 | AA 주도 활동 | TA 주도 활동 | 공동 산출물 및 협의 쟁점 |
|---|---|---|---|
| **착수/분석** | 업무 도메인 분석, 기능 범위 정의 | 인프라 제약, 보안 인증(CSAP) 검토 | 시스템 아키텍처 목표 정의서 |
| **기본설계** | 논리 컴포넌트 분할, 서비스 API 설계 | 클라우드 CSP 선정, 네트워크 토폴로지 | 논리-물리 배포 매핑도, 초기 ADR |
| **상세설계** | 프레임워크 선정(Spring Boot), DB 모델 | OS 커널 튜닝, 미들웨어 이중화(HA) | 소프트웨어 개발 표준 가이드 |
| **구현/검증** | 공통 모듈 개발, 단위 테스트 가이드 | CI/CD 파이프라인 구축, IaC 자동화 | 성능 부하 시험 결과서, 튜닝 리포트 |
| **오픈/운영** | 애플리케이션 로그/에러 트레이싱 분석 | 인프라 오토스케일링, 백업/DR 통제 | 아키텍처 핸드오버 문서 |

## Ⅳ. AA vs TA 상세 비교 및 공동 의사결정 매트릭스

### AA(Application Architect)와 TA(Technical Architect) 비교

| 비교 항목 | 애플리케이션 아키텍트 (AA) | 테크니컬 아키텍트 (TA) |
|---|---|---|
| **설계 초점** | **소프트웨어의 기능적 구조 (What & How)** | **시스템의 비기능적 실행 기반 (Where & How well)** |
| **주요 관심사** | 비즈니스 로직, 모듈성, 재사용성, 데이터 흐름 | 처리량(TPS), 가용성(99.99%), 보안성, 확장성 |
| **설계 뷰 (View)** | 논리 뷰(Logical View), 구현 뷰(Implementation) | 배치 뷰(Deployment View), 물리 뷰(Physical View) |
| **다루는 기술** | Java, Python, Spring, React, 디자인 패턴, DDD | AWS/GCP, Kubernetes, Linux, Nginx, Kafka, Oracle |
| **핵심 산출물** | 소프트웨어 아키텍처 설계서(SAD), 컴포넌트 명세서 | 시스템 구성도, 네트워크 구성도, 배포 아키텍처 설계서 |

### 핵심 아키텍처 쟁점별 공동 판단 기준

| 아키텍처 쟁점 | AA의 관점 (논리적) | TA의 관점 (물리적) | 공동 판단 및 최종 합의 기준 |
|---|---|---|---|
| **서비스 분할 수준** | 도메인 모델 경계에 따라 잘게 분할 | 서비스 증가 시 네트워크 홉 및 관리 비용 증가 | 핵심 도메인만 MSA 분리, 비핵심은 모듈러 모놀리스 유지 |
| **데이터 동기화** | 동기식 REST API 호출로 즉각 일관성 확보 | 호출 지연 누적 및 연쇄 장애 전파 위험 | 결과적 일관성(Eventual Consistency) 허용 및 Kafka 이벤트 기반 비동기 전환 |
| **세션/상태 관리** | 웹 애플리케이션 서버 메모리 내 세션 저장 | 서버 장애 시 세션 유실 및 오토스케일링 불가 | Redis 분산 인메모리 캐시 서버로 세션 외부화 합의 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| AA와 TA 간의 소통 단절(Silo)로 인해 논리 설계와 물리 인프라 배포가 어긋나는 현상 | 스프린트마다 AA-TA 합동 '아키텍처 싱크 미팅'을 정례화하고 공유 ADR 템플릿 사용 |
| AA의 비효율적 쿼리/코드 작성을 TA의 무한 하드웨어 증설(Scale-up)로만 해결하려는 비용 낭비 | 애플리케이션 APM(Scouter/Datadog) 프로파일링을 선행하여 코드 레벨 병목 우선 튜닝 |
| 클라우드 전환 시 온프레미스 방식의 정적 설계를 답습하여 클라우드 네이티브 이점 상실 | 컨테이너 기반 12-Factor 원칙 준수 및 서버리스, 관리형 서비스(PaaS) 적극 도입 |

## Ⅵ. 제언

아키텍처 피트니스 함수(Fitness Function) 자동화 파이프라인 및 FinOps 기반 협력 모델

### CI/CD 연계 아키텍처 피트니스 함수 파이프라인

```text
[개발팀 소스코드 및 인프라 IaC 코드 커밋]
       ↓
[CI 파이프라인 실행: 자동화된 피트니스 함수 검증]
  ├─ 1. AA 관점 검증 (ArchUnit)
  │    └─ 레이어 간 의존성 규칙 위반 및 순환 참조 자동 검출
  ├─ 2. TA 관점 검증 (Infracost / Checkov)
  │    └─ Terraform 보안 취약점 점검 및 클라우드 예상 월간 비용 산출
  └─ 3. 종합 품질 관점 검증 (k6 / Lighthouse)
       └─ 스테이징 환경 대상 자동 부하 테스트 및 P99 지연 시간(200ms) 검증
       ↓
[모든 아키텍처 임계치 충족 시 프로덕션 배포 파이프라인 승인]
```

### AA-TA 아키텍처 설계 의사결정 체계

```text
신규 기능 아키텍처 설계 착수
       ↓
[AA: 비즈니스 도메인 컴포넌트 및 API 인터페이스 초안 도출]
       ↓
[TA: 해당 컴포넌트의 초당 예상 트래픽(TPS) 및 가용성 등급 검토]
       ├─ 고성능/무중단 요구 (Tier 1) ─→ 멀티 리전 이중화 + 분산 캐시 + Kafka 비동기 설계
       └─ 일반 업무 (Tier 2/3) ──────→ 단일 리전 멀티 AZ 배포 + 표준 RDB 설계
       ↓
[공동 ADR 작성 및 서명 날인 → Git 저장소에 형상 관리]
```

### 선택 근거: 전통적 문서 기반 아키텍처 검토와 제언 코드 기반 피트니스 함수 비교

| 구분 | 전통적 아키텍처 심의 회의 | 제언: 자동화된 아키텍처 피트니스 함수 |
|---|---|---|
| 검증 주기 | 마일스톤 완료 시점 1~2회 비정기 검토 | 모든 Git PR 및 빌드 시마다 상시 자동 검증 |
| 아키텍처 부식 방지 | 바쁜 일정으로 코드가 아키텍처를 이탈해도 방치 | 규칙 위반 시 즉각 빌드를 실패시켜 아키텍처 부식 원천 차단 |
| 객관성 | 심의 위원의 주관적 견해에 좌우 | 정량적 테스트 코드와 수치 메트릭으로 판정 |
