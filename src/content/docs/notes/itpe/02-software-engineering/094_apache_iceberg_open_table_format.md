## 30초 인출

- 본질: 오픈 테이블 포맷은 데이터 레이크의 파일 집합에 테이블 메타데이터를 얹어 트랜잭션과 스키마 관리를 가능하게 하는 개방형 규격이며 Apache Iceberg가 대표
- 메커니즘: 카탈로그가 최신 메타데이터를 가리키고 메타데이터가 스냅샷과 매니페스트를 거쳐 데이터 파일을 추적해 쓰기마다 새 스냅샷을 만들고 읽기는 일관된 스냅샷을 조회
- 통찰: 파일 단위로 쌓인 레이크는 동시 쓰기와 스키마 변경에서 일관성을 보장하지 못하므로 스냅샷 기반 메타데이터로 원자적 커밋을 하되 작은 파일이 늘어나는 문제를 주기적 압축으로 관리

<details>
<summary>핵심 용어</summary>

- **오픈 테이블 포맷(Open Table Format)** : 저장소의 파일을 테이블로 관리하도록 메타데이터를 정의한 개방형 규격
- **레이크하우스(Lakehouse)** : 데이터 레이크의 저장 유연성과 데이터 웨어하우스의 트랜잭션·관리 기능을 결합한 구조
- **스냅샷(Snapshot)** : 특정 시점의 테이블 상태를 나타내는 불변의 메타데이터
- **매니페스트(Manifest)** : 데이터 파일의 경로와 통계를 기록한 목록 파일
- **카탈로그(Catalog)** : 테이블의 최신 메타데이터 위치를 관리하는 구성요소
- **시간 여행(Time Travel)** : 과거 스냅샷 시점의 데이터를 조회하는 기능

</details>

## 2~4교시 25점 답안

## Ⅰ. 오픈 테이블 포맷의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **오픈 테이블 포맷** 은 데이터 레이크의 파일에 테이블 메타데이터를 얹어 트랜잭션·스키마 관리를 제공하는 개방형 규격 |
| 목적 | 레이크에서의 일관된 읽기·쓰기와 여러 엔진의 공통 접근 |

## Ⅱ. 파일 기반 레이크와 구별되는 특징

| 특징 | 의미 |
|---|---|
| ACID 트랜잭션 | 커밋 단위의 원자성·일관성 |
| 스키마 진화 | 컬럼 추가·변경 이력 관리 |
| 시간 여행 | 과거 시점 조회·복구 |
| 엔진 독립 | 여러 처리 엔진이 같은 테이블 접근 |

## Ⅲ. Iceberg의 구조와 커밋 흐름

### 메타데이터 계층 구조

```text
카탈로그 ── 최신 메타데이터 파일 위치
    ↓
메타데이터 파일 ── 스키마·스냅샷 목록
    ↓
매니페스트 목록 ── 스냅샷별 매니페스트
    ↓
매니페스트 파일 ── 데이터 파일 경로·통계
    ↓
데이터 파일
```

### 확대: 쓰기 커밋

```text
새 데이터 파일 작성
    ↓
새 매니페스트·스냅샷 작성
    ↓
카탈로그의 메타데이터 포인터를 원자적으로 교체 (커밋)
(읽기는 커밋 이전 스냅샷을 계속 조회)
```

## Ⅳ. 기존 방식과의 비교

| 구분 | 파일 기반 레이크(디렉터리 규칙) | 오픈 테이블 포맷 |
|---|---|---|
| 트랜잭션 | 없음 | 스냅샷 기반 원자적 커밋 |
| 스키마 변경 | 파일 전체 영향 | 메타데이터로 관리 |
| 파티션 | 사용자가 경로 지정 | 메타데이터가 관리(숨김 파티셔닝) |
| 과거 조회 | 곤란 | 시간 여행 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 빈번한 쓰기로 작은 파일과 메타데이터 증가 | 주기적 파일 압축과 스냅샷 만료 |
| 동시 쓰기 충돌 | 낙관적 동시성 제어와 재시도 |
| 카탈로그 종속으로 이식 곤란 | 표준 카탈로그 인터페이스 사용 |

## Ⅵ. 제언

쓰기가 잦은 테이블은 주기적으로 작은 파일을 압축하고 오래된 스냅샷을 만료하는 유지 작업을 정례화

### 유지 작업 순환

```text
쓰기 반복 → 작은 파일·스냅샷 증가
    ↓
주기적 압축·스냅샷 만료
    ↓
조회 성능·메타데이터 크기 회복
```

### 선택 근거: 유지 작업 없는 운영과의 비교

| 구분 | 유지 없음 | 제언: 정례 유지 |
|---|---|---|
| 조회 성능 | 점진적 저하 | 유지 |
| 메타데이터 | 증가 | 통제 |
| 운영 부담 | 없음 | 정례 작업 필요 |
