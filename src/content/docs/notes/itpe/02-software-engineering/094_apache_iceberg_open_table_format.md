## 한 줄 본질
- 대규모 오브젝트 스토리지(S3 등)에서 수백만 개 파일의 디렉터리 리스팅(Listing) 지연과 동시 쓰기 정합성 깨짐 병목 → 계층적 메타데이터 트리(Metadata-Manifest List-Manifest)와 스냅샷 원자적 커밋으로 파일 단위 ACID 트랜잭션 및 타임 트래블 지원 / 소형 파일 압축 관리 비용 수반

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  Apache Iceberg 메타데이터 계층 구조                     |
+-------------------------------------------------------------------------+
| [Iceberg Catalog] (REST, Hive, Glue, JDBC) -> 최신 Metadata File 가리킴  |
|         |                                                               |
| [Metadata Layer]                                                        |
|   Metadata File (v1.metadata.json -> v2.metadata.json) : 스키마, 스냅샷  |
|         |                                                               |
|   Manifest List (snap-123.avro) : 해당 스냅샷에 속한 Manifest 목록      |
|         |                                                               |
|   Manifest File (m-0.avro) : 실제 데이터 파일 경로, 파티션, 컬럼 통계값 |
|         |                                                               |
| [Data Layer]                                                            |
|   Data Files (data-1.parquet, data-2.parquet) : 실제 레코드 보관         |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 히든 파티셔닝(Hidden Partitioning): 사용자가 쿼리 시 `timestamp`만 조건절에 넣어도 엔진이 `year/month` 변환 파티션을 자동으로 프루닝(Pruning)하여 쿼리 실수로 인한 전체 스캔을 방지하는 기능
- 파티션 진화(Partition Evolution): 기존 데이터 파일의 물리적 재작성 없이 테이블의 파티셔닝 전략(예: 일 단위 -> 시간 단위)을 즉시 변경할 수 있는 기능

## 핵심 통찰
- Iceberg는 스토리지가 아니라 "오브젝트 스토리지 위에 놓인 데이터 파일들을 단일 RDBMS 테이블처럼 보이게 만들어주는 메타데이터 규격"임
- 컴퓨팅 엔진(Spark, Trino, Flink)과 완전히 독립된 오픈 표준이므로, 하나의 테이블을 배치(Spark), 실시간 스트리밍(Flink), 대화형 쿼리(Trino)에서 락 없이 동시 접근 가능함
- 파일 단위 통계값(Min/Max, Null 수)이 매니페스트 파일에 미리 저장되어 있어 불필요한 데이터 파일을 읽지 않고 건너뛰는 파일 레벨 데이터 스키핑(Data Skipping) 극대화

## 이웃 토픽과 구분
- Iceberg vs 하이브(Hive): Hive = 파일이 존재하는 디렉터리 경로로 파티션을 관리하여 $O(N)$ 디렉터리 리스팅 병목 발생 / Iceberg = 메타데이터 트리가 데이터 파일 경로를 직접 관리하여 $O(1)$ 스냅샷 포인터 갱신

## 문제·원인·대책
- 적용 상황: 수 페타바이트 규모의 빅데이터 분석 플랫폼
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| Flink로 초당 수천 건 실시간 데이터 적재 시 1KB 미만 소형 파일 수천만 개 양산 | 빈번한 마이크로 배치 스트리밍 커밋으로 인한 스몰 파일 파편화 | Iceberg 내장 비동기 파일 압축(Compaction) 및 소트 오더(Sort Order) 적용 | 쿼리 스캔 성능 5배 향상 및 메타데이터 크기 80% 절감 |
| 스냅샷 이력이 수개월 누적되어 메타데이터 용량 및 쿼리 플래닝 시간 증가 | 만료되지 않은 과거 스냅샷과 불필요한 고아 파일(Orphan Files) 방치 | 주기적 `expireSnapshots` 프로시저 실행 및 고아 파일 자동 정화 스케줄러 | 쿼리 플래닝 레이턴시 수십 밀리초 수준 유지 |

## 이렇게 출제된다
- 미출제. 예상: "데이터 레이크하우스(Data Lakehouse)의 핵심 기술인 오픈 테이블 포맷(Open Table Format)의 개념을 설명하고, Apache Iceberg의 아키텍처(메타데이터 계층), 주요 기능(ACID, 파티션 진화, 타임 트래블), 그리고 운영 시 성능 최적화 방안을 기술하시오." → 요구 포인트: 하이브 메타스토어의 한계 + Iceberg 3단계 메타데이터 트리 + 핵심 특성 + 소형 파일 컴팩션 및 스냅샷 관리
