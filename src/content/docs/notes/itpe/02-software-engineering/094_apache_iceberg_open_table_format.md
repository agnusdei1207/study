## 30초 인출

- 본질: **Apache Iceberg** 는 오브젝트 스토리지(S3, GCS, HDFS) 상의 대규모 원시 데이터 파일들(Parquet, ORC) 위에 트리 구조의 메타데이터 계층을 두어, 분산 컴퓨팅 엔진에 구애받지 않고 관계형 데이터베이스 수준의 완벽한 ACID 트랜잭션과 고성능 SQL 조회를 제공하는 오픈 테이블 포맷(Open Table Format)
- 메커니즘: 카탈로그(Catalog)가 현재 메타데이터 파일 가리킴 → 스냅샷(Snapshot) 기반 매니페스트 목록(Manifest List) 탐색 → 매니페스트 파일(Manifest File)의 컬럼별 Min/Max 통계 기반 파일 프루닝 → 실제 데이터 파일 직접 접근
- 통찰: 기존 Hive 메타스토어 방식의 디렉터리 기반 파티셔닝은 파일 목록 조회 시 심각한 O(N) I/O 병목과 일관성 결함을 초래하므로 Iceberg의 히든 파티셔닝(Hidden Partitioning)과 낙관적 동시성 제어(OCC) 기반 메타데이터 설계를 통해 클라우드 레이크하우스의 확장성을 확보할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **오픈 테이블 포맷 (Open Table Format)** : 스토리지의 파일들을 SQL 테이블 형태로 추상화하고 메타데이터로 상태를 관리하는 표준 규격 (Iceberg, Delta Lake, Hudi)
- **카탈로그 (Catalog)** : 테이블 식별자와 최신 유효 메타데이터 파일(`vN.metadata.json`)의 포인터를 원자적으로 갱신·관리하는 레지스트리 (Nessie, AWS Glue)
- **매니페스트 목록 (Manifest List)** : 특정 스냅샷을 구성하는 매니페스트 파일들의 목록과 각 매니페스트별 파티션 범위를 기록한 파일
- **매니페스트 파일 (Manifest File)** : 실제 데이터 파일의 물리적 경로, 파티션 소속, 컬럼별 최소/최대 통계치, 삭제 벡터를 보관하는 파일
- **히든 파티셔닝 (Hidden Partitioning)** : 사용자가 쿼리 시 변환된 파티션 컬럼을 알 필요 없이 원본 컬럼 조건만으로 파티션 프루닝이 자동 수행되는 기능
- **시간 여행 (Time Travel)** : 스냅샷 불변성을 이용하여 과거 특정 시점의 데이터 상태를 재현하고 롤백할 수 있는 기능

## 2~4교시 예상문제 (25점)

> 데이터 레이크하우스(Lakehouse) 구현을 위한 오픈 테이블 포맷인 Apache Iceberg의 등장 배경과 3계층 메타데이터 아키텍처를 설명하고, ACID 트랜잭션 보장 원리, 히든 파티셔닝(Hidden Partitioning), 스냅샷 수명주기 관리 방안을 제시하시오.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 클라우드 오브젝트 스토리지에 저장된 대용량 페타바이트급 데이터 파일들을 SQL 테이블처럼 조작할 수 있도록 스냅샷 기반 메타데이터 트리를 제공하는 오픈 소스 테이블 포맷 |
| 목적 | 전통적 하둡 Hive 방식의 O(N) 디렉터리 스캔 병목 제거, 스키마/파티션 무중단 진화, 멀티 엔진(Spark, Trino, Flink) 간 단일 진실 공급원(SSOT) 형성 |

## Ⅱ. 핵심 특징

물리적 디렉터리 구조와 논리적 테이블 파티션을 분리하여 파일 단위의 정밀한 동시성 제어 실현.

| 핵심 속성 | 공학적 원리 | 실무 효과 |
|---|---|---|
| **완벽한 ACID 트랜잭션** | 낙관적 동시성 제어(OCC) 및 원자적 카탈로그 포인터 스왑 | 읽기-쓰기 충돌 제로, 더티 리드(Dirty Read) 원천 차단 |
| **히든 파티셔닝 (Hidden Partitioning)** | 원본 컬럼(`timestamp`)에 파티션 변환 함수(`days()`)를 매핑하여 내부 처리 | 쿼리 작성 시 인위적 파티션 컬럼 조건 기재 오류 방지 |
| **파티션 진화 (Partition Evolution)** | 테이블 데이터의 재작성 없이 파티션 분할 정책을 일 단위에서 시간 단위로 변경 | 파티션 정책 변경 시 수 테라바이트 데이터 마이그레이션 비용 제로 |
| **고성능 데이터 스킵 (Data Skipping)** | 매니페스트 파일 내 컬럼별 Min/Max 통계를 활용한 선제적 프루닝 | 불필요한 데이터 파일 I/O를 90% 이상 사전 차단 |

## Ⅲ. 체계·프로세스

Apache Iceberg의 3계층 메타데이터 아키텍처 및 쿼리 플래닝 체계.

```text
[Apache Iceberg 메타데이터 계층 구조 및 읽기 흐름]
[ 카탈로그 계층 (Catalog) ]
  * Nessie / AWS Glue / JDBC
  * 현재 유효한 테이블 포인터 보관 ──> [ v3.metadata.json ] (Table Metadata File)
                                               │
  ─────────────────────────────────────────────┼───────────────────────────────────────────────────────────
  [ 메타데이터 계층 (Metadata Layer) ]         │
                                               ▼
                                      +───────────────────────────────────+
                                      |     스냅샷 S3 (Snapshot S3)       |
                                      +───────────────────────────────────+
                                                       │
                                                       ▼
                                      +───────────────────────────────────+
                                      |   매니페스트 목록 (Manifest List)  |
                                      |   - snap-103-manifest-list.avro   |
                                      +───────────────────────────────────+
                                         │                             │
                         ┌───────────────┘                             └───────────────┐
                         ▼                                                             ▼
        +───────────────────────────────────+                         +───────────────────────────────────+
        |     매니페스트 파일 (Manifest A)  |                         |     매니페스트 파일 (Manifest B)  |
        |     - 파티션: 2026-09-28          |                         |     - 파티션: 2026-09-29          |
        |     - Min: 1, Max: 5000           |                         |     - Min: 5001, Max: 10000       |
        +───────────────────────────────────+                         +───────────────────────────────────+
                         │                                                             │
  ───────────────────────┼─────────────────────────────────────────────────────────────┼───────────────────
  [ 데이터 계층 (Data Layer) : Parquet / ORC ]                                         │
                         ▼                                                             ▼
        +───────────────────────────────────+                         +───────────────────────────────────+
        |   data-file-1.parquet             |                         |   data-file-2.parquet             |
        |   (실제 비즈니스 레코드 저장)      |                         |   (실제 비즈니스 레코드 저장)      |
        +───────────────────────────────────+                         +───────────────────────────────────+
```

- **Iceberg 3계층 읽기 프로세스**:
  1. **카탈로그 참조** : 쿼리 엔진이 카탈로그에서 대상 테이블의 최신 테이블 메타데이터 파일(`v3.metadata.json`) 경로 획득.
  2. **매니페스트 목록 탐색** : 스냅샷이 참조하는 매니페스트 목록을 읽어 파티션 조건과 부합하지 않는 매니페스트 파일 배제.
  3. **매니페스트 레벨 프루닝** : 남은 매니페스트 내부의 컬럼 Min/Max 통계를 평가하여 쿼리 필터 조건을 만족하는 데이터 파일 선별.
  4. **데이터 직접 인출** : 선별된 Parquet 데이터 파일만을 스토리지로부터 직접 병렬 스트리밍 읽기 수행.

## Ⅳ. 종류·비교

#### 오픈 테이블 포맷 3대 기술(Iceberg vs Delta Lake vs Hudi) 비교

| 비교 항목 | Apache Iceberg | Delta Lake | Apache Hudi |
|---|---|---|---|
| **설계 철학** | 엔진 독립적인 개방형 규격 (Netflix) | Spark 생태계 중심의 고성능 엔진 (Databricks) | 스트리밍 및 초저지연 증분 처리 (Uber) |
| **카탈로그 중심성** | 매우 높음 (REST 카탈로그 표준화) | 파일시스템 트랜잭션 로그(`_delta_log`) 중심 | 타임라인(Timeline) 메타데이터 중심 |
| **파티셔닝 방식** | **히든 파티셔닝 및 파티션 진화 지원** | 명시적 물리 디렉터리 파티셔닝 | 키 기반 파티셔닝 지원 |
| **동시성 제어** | 낙관적 동시성 제어 (OCC) | 낙관적 동시성 제어 (OCC) | MVCC (다중 버전 동시성 제어) |
| **업데이트 방식** | Copy-on-Write / Merge-on-Read 지원 | Copy-on-Write / Merge-on-Read 지원 | Copy-on-Write / Merge-on-Read 완벽 특화 |
| **주요 지원 엔진** | Spark, Trino, Flink, Presto, Dremio | Spark, Trino, Flink, Athena | Spark, Flink, Trino |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 잦은 실시간 스트리밍 인입 시 바이트 단위의 작은 파일(Small Files)이 양산되어 메타데이터 조회 성능 급격 저하 | Iceberg의 자동 컴팩션(Compaction, `rewriteDataFiles`) 프로시저를 주기적으로 구동하여 대형 파일로 병합 |
| 스냅샷이 무한정 누적됨에 따라 오브젝트 스토리지 비용 상승 및 카탈로그 조회 지연 | 만료 정책(Expire Snapshots)을 수립하여 보존 기간이 지난 스냅샷과 고아 파일(Orphan Files)을 정기 영구 삭제 |
| 여러 엔진이 동시에 단일 테이블에 쓰기 수행 시 낙관적 동시성 충돌(OCC Conflict) 빈발 | 재시도 지수 백오프 설정 최적화 및 파티션 단위 격리 쓰기 파이프라인 수립 |

## Ⅵ. 제언

Apache Iceberg를 성공적으로 안착시키기 위해서는 특정 스토리지 벤더에 종속되지 않는 REST Catalog 표준을 도입하고, 배치와 스트리밍 쓰기 파이프라인의 컴팩션 주기를 분리하여 테이블 수명주기를 거버넌스할 필요가 있음.

```text
[실시간 스트리밍 쓰기 (Flink)] ──> [Iceberg 테이블 (MOR)] ──> [주기적 컴팩션 (Spark)] ──> [초고속 BI 조회 (Trino)]
                                      (스냅샷 생성 & 쓰기)         (파일 병합 & 만료 삭제)       (프루닝 기반 쿼리)
```

| 운영 영역 | 핵심 실행 지침 | 목표 관리 지표 |
|---|---|---|
| **카탈로그 표준화** | Apache Polaris 또는 Project Nessie 기반 REST Catalog 도입 | 멀티 엔진 간 100% 동일한 트랜잭션 뷰 제공 |
| **파일 컴팩션 최적화** | 512MB~1GB 단위로 Parquet 파일 타깃 크기 설정 | 쿼리 플래닝 소요 시간 1초 이내 단축 |
| **스냅샷 수명 관리** | 7일 이전 과거 스냅샷 자동 만료(`expire_snapshots`) | 메타데이터 파일 크기 안정화 및 불필요 스토리지 비용 30% 절감 |
