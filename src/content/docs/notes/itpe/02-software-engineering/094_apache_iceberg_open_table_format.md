## 연관 키워드

- Apache Iceberg, 오픈 테이블 포맷(OTF, Open Table Format), 데이터 레이크하우스(Data Lakehouse), ACID 트랜잭션
- 타임 트래블(Time Travel), 스키마 진화(Schema Evolution), Delta Lake, Apache Hudi, 벤더 락인(Vendor Lock-in)

## Ⅰ. Apache Iceberg와 오픈 테이블 포맷의 개요

- 핵심 요약 : 객체 스토리지의 데이터 파일 위에 트랜잭션과 스키마 관리를 더하는 개방형 테이블 포맷.
- 개념 : 객체 스토리지에 흩어진 대용량 데이터 파일을 하나의 테이블로 다루도록 메타데이터 계층을 정의한 **오픈 테이블 포맷** (OTF, Open Table Format)이며, 대표 구현은 **Apache Iceberg**이다.
- 배경 및 필요성 : 기존 Hive 방식 데이터 레이크는 디렉터리 기반 파티션 관리로 파일 목록 조회가 느리고 쓰기 원자성이 없어 정합성이 깨지기 쉽다. 반면 데이터 웨어하우스(DW, Data Warehouse)는 트랜잭션을 보장하지만 저장 방식이 폐쇄적이고 비용이 높아, 두 장점을 합친 **데이터 레이크하우스** (Data Lakehouse) 구조가 요구된다.
- 주요 목적 : 객체 스토리지 위에서 **ACID 트랜잭션**(원자성·일관성·격리성·지속성을 보장하는 트랜잭션 (ACID: Atomicity, Consistency, Isolation, Durability))과 시점 조회, 스키마 변경을 지원하면서 특정 벤더에 묶이지 않는 테이블 계층을 확보.
- 대표 3종 : Apache Iceberg와 함께 **Delta Lake**, **Apache Hudi**가 3대 오픈 테이블 포맷으로 꼽힌다.

## Ⅱ. Apache Iceberg의 특징 및 장점

- 핵심 요약 : 계층형 메타데이터, 스냅샷 격리, 숨겨진 파티셔닝이 결합되어 엔진 독립성과 쿼리 안정성으로 이어지는 구조.

1. 계층형 메타데이터 : 카탈로그에서 데이터 파일까지 단계별 메타데이터를 따라 파일 목록을 찾음 → 디렉터리 리스팅 비용 감소와 쿼리 계획 속도 향상.
2. **스냅샷 격리** (Snapshot Isolation) : 읽기 작업이 특정 스냅샷을 기준으로 수행됨 → 쓰기 작업이 진행 중이어도 일관된 조회 결과 제공.
3. **숨겨진 파티셔닝** (Hidden Partitioning) : 파티션 변환 규칙을 테이블 메타데이터에 두어 쿼리가 파티션 컬럼을 직접 지정하지 않아도 됨 → 잘못된 파티션 조건으로 인한 오류와 전체 스캔 감소.
4. 엔진 독립성 : Spark, Trino, Flink 등 여러 엔진이 같은 테이블을 읽고 쓸 수 있음 → 특정 엔진 종속 감소.
5. **Copy-on-Write** (CoW)와 **Merge-on-Read** (MoR) 병행 지원 : 데이터 파일을 다시 쓰는 방식과 삭제·갱신 기록을 읽을 때 합치는 방식을 워크로드에 따라 선택 → 갱신 빈도에 맞춘 쓰기·읽기 비용 조정.

## Ⅲ. Apache Iceberg의 구조 (흐름)

- 핵심 요약 : 카탈로그 포인터에서 데이터 파일까지 내려가는 계층형 메타데이터 탐색 구조와, 커밋으로 새 스냅샷이 공개되는 쓰기 흐름.

```text
[ 계층형 메타데이터 탐색 ]

[ 카탈로그 (Catalog) ]
 최신 메타데이터 위치 포인터
       ↓
[ 테이블 메타데이터 ]
 스키마, 파티션 스펙, 스냅샷 목록
       ↓
[ 매니페스트 리스트 ]
 스냅샷별 매니페스트 파일 목록
       ↓
[ 매니페스트 파일 ]
 데이터 파일 목록, 컬럼별 최소·최대값
       ↓
[ 데이터 파일 (Parquet, ORC) ]
 실제 데이터 저장
```

```text
[ 쓰기 작업과 스냅샷 갱신 ]

[ 새 데이터 파일 기록 ]
       ↓
[ 새 매니페스트 작성 ]
       ↓
[ 카탈로그 포인터 갱신 (커밋) ]
       ↓
[ 새 스냅샷 공개, 이전 스냅샷 유지 ]
```

- 탐색 구조 : 카탈로그가 가리키는 최신 메타데이터에서 매니페스트를 거쳐 데이터 파일로 내려가므로, 조회 엔진은 디렉터리를 훑지 않고 필요한 파일만 고른다.
- 커밋 구조 : 쓰기는 새 파일과 새 메타데이터를 만든 뒤 포인터를 한 번에 바꾸는 방식이라, 커밋 전에는 독자가 변경분을 보지 못한다.

## Ⅳ. 오픈 테이블 포맷 3종의 비교

- 핵심 요약 : 세 포맷 모두 트랜잭션과 시점 조회를 지원하지만, 엔진 독립성과 적합한 워크로드, 갱신 방식에서 차이가 난다.

```text
[ 데이터 레이크 ]
 개방 포맷, 저비용, 트랜잭션 부재
[ 데이터 웨어하우스 ]
 트랜잭션 보장, 폐쇄 포맷, 고비용
      ↓ 두 장점 결합
[ 데이터 레이크하우스 ]
 개방 포맷 + 트랜잭션
```

| 비교 항목 | Apache Iceberg | Delta Lake | Apache Hudi |
| --- | --- | --- | --- |
| 출발·관리 주체 | Netflix에서 시작, Apache 소프트웨어 재단 관리 | Databricks 주도, Linux Foundation 산하 | Uber에서 시작, Apache 소프트웨어 재단 관리 |
| 엔진 독립성 | 여러 엔진을 고르게 지원하는 설계 | Spark 중심, 외부 엔진 호환 기능 확장 | Spark, Flink 등과의 연동 중심 |
| 적합한 워크로드 | 대용량 배치 분석과 애드혹 쿼리 | Databricks 플랫폼 기반 통합 분석 | 스트리밍 적재와 빈번한 레코드 단위 갱신 |
| 갱신 방식 | CoW와 MoR 병행 | CoW 중심 | MoR 설계 강점 |

- 선택 기준 : 여러 엔진을 섞어 쓸 계획이면 개방성과 엔진 범위를 우선 보고, 특정 플랫폼을 중심으로 운영하면 그 플랫폼의 기본 포맷과 궁합을 본다.

## Ⅴ. Apache Iceberg의 한계와 방안

- 핵심 요약 : 개방성·트랜잭션·시점 조회의 장점과 소형 파일 누적, 동시 쓰기 충돌, 카탈로그 파편화의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 소형 파일 누적 | 잦은 스트리밍 적재로 작은 파일과 메타데이터가 쌓여 쿼리 계획이 지연 | 콤팩션(Compaction)과 스냅샷 만료(Expire Snapshots)의 정기 배치 자동화 | 파일당 평균 크기, 계획 소요 시간 |
| 동시 쓰기 충돌 | 낙관적 동시성 제어(OCC, Optimistic Concurrency Control)에서 같은 파티션을 동시에 고치면 커밋 실패와 재시도 발생 | 쓰기 큐로 순차 적재, 파티션 설계 재검토로 충돌 범위 분리 | 커밋 실패율 |
| 카탈로그 파편화 | Hive Metastore, AWS(Amazon Web Services) Glue 등 구현체마다 연동 방식이 달라 멀티 엔진 구성이 복잡 | REST(Representational State Transfer) 기반 표준 Iceberg 카탈로그 사양을 따르는 통합 카탈로그 도입 | 엔진 간 테이블 조회 성공률 |

## Ⅵ. 레이크하우스 구축을 위한 기술사적 제언

- 핵심 요약 : 표준 포맷과 통합 카탈로그를 기준으로 삼고, 유지보수를 플랫폼 공통 기능으로 운영하는 방향의 레이크하우스 설계.
- 데이터 플랫폼 선정 때 개방형 표준 포맷 채택을 필수 조건으로 두어, 특정 상용 웨어하우스의 독점 포맷에 데이터가 묶이지 않게 해야 한다.
- 콤팩션과 스냅샷 만료 같은 유지보수는 개별 과제가 아니라 플랫폼 공통 서비스로 두고, 그 운영 비용을 데이터 파이프라인 예산에 처음부터 포함해야 한다.
- 카탈로그는 전사 단위로 하나의 표준 사양에 맞춰 접근 권한과 데이터 계보를 함께 관리하여, 엔진이 늘어나도 거버넌스가 흩어지지 않게 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : Apache Iceberg는 객체 스토리지 위에서 데이터 레이크의 유연성과 웨어하우스의 신뢰성을 함께 제공하는 개방형 테이블 포맷.
- 시사점 : 계층형 메타데이터와 스냅샷 격리가 레이크하우스의 기반이며, 도입의 성패는 유지보수 자동화와 카탈로그 표준화에 달려 있다.
