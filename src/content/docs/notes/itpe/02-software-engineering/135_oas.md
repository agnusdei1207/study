## 연관 키워드

- OAS(OpenAPI Specification), Swagger, API-First, 단일 진실 공급원(SSOT, Single Source of Truth)
- 명세 드리프트(Specification Drift), Mock 서버, 클라이언트 SDK 자동 생성, 계약 테스트(Contract Testing)

## Ⅰ. OAS(OpenAPI Specification)의 개요

- 핵심 요약 : RESTful 웹 서비스의 인터페이스를 언어 중립적 표준 명세로 기술하여 API 협업과 자동화의 기반을 제공하는 규격.
- 개념 : OAS(OpenAPI Specification)란 RESTful 웹 서비스의 인터페이스를 프로그래밍 언어에 구애받지 않고 인간과 기계가 모두 이해할 수 있도록 YAML(YAML Ain't Markup Language) 또는 JSON(JavaScript Object Notation) 방식으로 기술하기 위해 리눅스 재단의 OpenAPI Initiative에서 제정한 산업 표준 API(Application Programming Interface) 명세 규격.
- 배경 및 필요성 : 과거 워드나 엑셀로 작성된 API 문서의 잦은 최신화 누락, 백엔드와 프론트엔드 간의 스펙 불일치로 인한 통신 장애, 수작업 클라이언트 SDK(Software Development Kit) 작성의 비효율을 극복하기 위해 Swagger 2.0을 모태로 표준화.
- 주요 목적 : API-First 설계 지원, 기계 판독 가능한 단일 진실 공급원(SSOT) 확립, 문서화 및 코드 생성 자동화.

## Ⅱ. OAS의 특징

- 핵심 요약 : 언어 중립성·계약 우선 설계·재사용 스키마·자동 생성으로 구성되는 기계 판독형 인터페이스 명세 체계.

1. 프로그래밍 언어와 무관한 YAML/JSON 기반의 기계 판독 가능(Machine-Readable) 명세.
2. Swagger 2.0을 모태로 OpenAPI Initiative가 관리하는 산업 표준 규격.
3. paths와 components(schemas, securitySchemes)의 재사용 구조를 통한 스키마 중앙 관리.
4. API-First 계약 우선 개발과 Mock 서버 기반의 프론트엔드 병렬 협업 지원.
5. openapi-generator를 통한 다국어 클라이언트 SDK 자동 빌드.
6. JSON Schema 기반 요청 본문·응답 페이로드의 구조적 검증.

## Ⅲ. OAS의 구조 (흐름)

- 핵심 요약 : openapi 최상위 선언에서 info·servers·paths·components·security로 이어지는 계층적 문서 구조.

```text
[ openapi: 3.1.0 ]
 - 최상위 규격 버전 선언
   │
   ▼
[ info ]
 - API 제목, 버전, 라이선스, 설명
   │
   ▼
[ servers ]
 - API 호스팅 서버 Base URL 목록
   (개발, 스테이징, 운영)
   │
   ▼
[ paths ]
 - 엔드포인트 경로 및 HTTP 메서드
   (GET/POST/PUT)
 - parameters (경로, 쿼리, 헤더)
 - requestBody (JSON 스키마 페이로드)
 - responses (HTTP 200, 400, 500)
   │
   ▼
[ components ]
 - 재사용 스키마(schemas),
   보안 정의(securitySchemes)
   │
   ▼
[ security ]
 - 전역 보안 요구사항
   (OAuth2, Bearer JWT, API Key)
```

- API-First 개발 프로세스의 흐름.

```text
[ 1. OAS 스펙 작성 ]
   │
   ▼
[ 2. 스펙 리뷰·합의 ]
 (인터페이스 계약 확정)
   │
   ▼
[ 3. Mock 서버 구동 ]
   │
   ▼
[ 4. 병렬 개발 ]
 (백엔드 구현 + 프론트엔드 연동)
   │
   ▼
[ 5. 계약 테스트·배포 ]
 (oas-diff 검증, SDK 자동 빌드)
```

- 재사용 요소 : components의 schemas와 securitySchemes를 $ref 키워드로 참조하여 중복 정의 제거.
- 보안 선언 : OAuth2, Bearer JWT(Json Web Token), API Key 등 전역 보안 요구사항의 명세 수준 사전 정의.

## Ⅳ. 코드 우선(Code-First)과 명세 우선(API-First) 개발의 비교

- 핵심 요약 : 코드 구현 선행 체계에서 명세 계약 선행 체계로의 전환을 통한 협업 병렬화와 변경 통제 강화.

| 비교 항목 | 코드 우선 개발 (Code-First) | 명세 우선 개발 (API-First / Contract-First) |
|---|---|---|
| 개발 순서 | 백엔드 코드 작성 -> 어노테이션 기반 Swagger 자동 생성 | OAS 스펙 먼저 작성 -> 백엔드/프론트엔드 동시 병렬 개발 |
| 프론트엔드 협업 | 백엔드 API 구현이 완료될 때까지 프론트 대기 | OAS 기반 가상 Mock 서버를 띄워 첫날부터 병렬 개발 가능 |
| 스펙 변경 통제 | 개발자 임의의 코드 수정으로 클라이언트 파손 위험 | OAS 변경 시 사전에 인터페이스 영향도 분석 및 합의 선행 |
| 클라이언트 SDK | 필요 시 수작업 코딩 또는 사후 생성 | openapi-generator를 통해 다국어 클라이언트 라이브러리 자동 빌드 |
| 권장 환경 | 소규모 단순 프로젝트, 빠른 PoC(Proof of Concept) 단계 | 대규모 MSA(Microservice Architecture) 환경, 외부 퍼블릭 Open API 연계 시스템 |

## Ⅴ. OAS의 장점과 한계

- 핵심 요약 : 병렬 협업·자동화의 장점, 명세 드리프트·검증 룰 표현 한계·대규모 명세 비대화 측면의 제약.

- 장점
  1. Mock 서버 기반 프론트엔드 대기 시간의 원천 제거.
  2. 인터페이스 영향도 사전 분석을 통한 변경 통제 강화.
  3. 다국어 클라이언트 SDK 자동 생성에 따른 연동 비용 절감.
  4. SSOT 기반 API 문서의 항상 최신 상태 유지.

- 한계점 1 : 코드와 API 명세 간의 명세 드리프트(Specification Drift)
  - 한계점 : 개발자가 비즈니스 로직 수정 후 Swagger/OAS 명세서 수정을 누락하여 클라이언트 개발자와 연동 시 불일치 장애 발생.
  - 해결 방안 : Springdoc 등 애노테이션 기반 소스코드-명세 자동 동기화(Code-First) 또는 OpenAPI 명세로부터 컨트롤러 인터페이스를 자동 생성(Spec-First)하는 SSOT 확립.
- 한계점 2 : 복잡한 비즈니스 유효성 검증 룰 표현의 한계
  - 한계점 : 기본 JSON Schema 문법만으로는 필드 간 상호 조건부 필수값, 상태값에 따른 동적 제약 등 복잡한 도메인 검증 로직 표현 불가.
  - 해결 방안 : 커스텀 확장자(`x-validate` 등) 활용 및 OpenAPI v3.1의 JSON Schema 최신 사양 결합, 백엔드 유효성 검증 로직과 연계된 표준 에러 응답 규격(RFC(Request for Comments) 7807) 명문화.
- 한계점 3 : 대규모 엔터프라이즈 환경에서의 명세서 비대화 및 관리 복잡성
  - 한계점 : 수백 개의 엔드포인트를 단일 YAML/JSON 파일로 관리할 경우 가독성 저하 및 동시 편집 시 Git 머지 충돌 빈발.
  - 해결 방안 : `$ref` 키워드를 활용한 도메인·스키마별 파일 모듈화, Redocly CLI 등 빌드 도구를 활용한 명세 번들링 및 사내 개발자 포털(Backstage) 카탈로그 자동 연계.

## Ⅵ. 엔터프라이즈 API 거버넌스를 위한 기술사적 제언

- 핵심 요약 : CI 파이프라인 기반 명세 린팅 자동화와 계약 테스트 연동을 통한 API 품질 거버넌스 체계 구축.
- Stoplight/Spectral을 활용한 전사 API 린팅(Linting) 자동화 : 각 개발팀이 제각각 URL(Uniform Resource Locator) 네이밍(kebab-case vs camelCase)을 하거나 필수 에러 응답 포맷을 누락하지 않도록, Spectral 오픈소스를 CI(Continuous Integration) 파이프라인에 통합하여 전사 OAS 스타일 가이드 위반 시 커밋 차단.
- 소비자 주도 계약 테스트(Pact) 및 브레이킹 체인지 방지 : OAS 명세가 변경될 때 기존 클라이언트의 요청이 깨지는 하위 호환성 파손을 방지하기 위해 oas-diff 도구를 PR 검증에 연계하여 Semantic Versioning 준수 여부 자동 감사.

## Ⅶ. 결론

- 핵심 요약 : OAS는 API를 계약으로 다루는 표준 명세 체계이며, 자동화와 거버넌스의 결합이 도입 성숙도의 핵심.
- 요약 : 언어 중립적 명세, SSOT 확립, SDK·문서 자동 생성을 통한 API 개발 생산성과 협업 품질의 동시 확보.
- 시사점 : 명세 드리프트 통제(Spectral, oas-diff)와 대규모 명세 모듈화의 병행이 엔터프라이즈 API 거버넌스의 선결 조건.
