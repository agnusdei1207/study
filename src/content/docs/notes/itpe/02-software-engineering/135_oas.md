## 연관 키워드
- OpenAPI Specification, OAS, API 계약, YAML, JSON, API-First, OpenAPI Generator

### Ⅰ. OAS의 개요

- 핵심 요약 : OAS는 HTTP API의 경로·작업·요청·응답·보안 등을 기계가 읽을 수 있게 기술하는 명세 형식.
- 개념 : OpenAPI Initiative가 관리하는 언어 중립적 API 설명 표준으로 도구 간 계약 교환을 지원(**OAS**, OpenAPI Specification).
- 배경 및 필요성 : API 구현·문서·시험이 분리되면 계약 드리프트와 소비자 연동 오류가 발생.
- 주요 목적 : API 계약을 설계·구현·시험·문서와 연결해 일관된 개발 흐름 구성.

### Ⅱ. OAS의 특징 및 장점

- 핵심 요약 : 명세를 단일 계약 원천으로 활용해 문서·Mock·SDK·검증 파이프라인을 자동화.

1. 구조화 명세 : paths, operations, schemas, responses, security 정의 → API 계약 명료화.
2. API-First : 구현 전에 계약 리뷰 → 소비자와 호환성 조기 합의.
3. 도구 생태계 : 문서·Mock·클라이언트 생성·린트 → 통합 비용 절감.

### Ⅲ. OAS 개발 흐름

- 핵심 요약 : 계약 설계·검토 → 구현·계약 시험 → 배포 문서·클라이언트 생성 → 변경 호환성 검사.

```text
API 요구 → OAS 명세(YAML/JSON) → 리뷰·lint
       → Mock·SDK·서버 스텁 → 구현·계약 시험 → 배포
```

```text
소비자 계약 ── OpenAPI 문서 ── 제공자 구현
     ↑ 버전·호환성 검증 ← 계약 시험·CI 규칙
```

- 관리 항목 : 경로·메서드, 파라미터, 스키마, 응답·오류, 인증·인가, 버전.

### Ⅳ. OAS와 Code-First 비교

- 핵심 요약 : API-First는 계약을 먼저 합의하고 Code-First는 구현에서 명세를 추출.

| 비교 기준 | API-First/OAS 중심 | Code-First |
|---|---|---|
| 기준 원천 | 검토된 API 계약 | 코드·주석에서 생성된 명세 |
| 장점 | 병렬 개발·소비자 합의·플랫폼 독립성 | 기존 코드와 동기화가 쉬움 |
| 위험 | 명세와 구현 드리프트 | 구현 상세 가 계약에 누출·설계 선행 어려움 |
| 적합 | 다수 소비자·외부 공개·계약 중요 | 내부 단일 서비스·빠른 프로토타입 |

### Ⅴ. OAS 적용 한계와 대응

- 핵심 요약 : 명세-구현 드리프트와 과도한 계약 복잡성을 CI 검증·버전 정책·필수 필드 기준으로 관리.

| 한계 | 영향 | 대응 |
|---|---|---|
| 명세 드리프트 | 문서와 런타임 응답 불일치 | 계약 시험·생성 형 스텁·CI 차이 검사 |
| 명세 과대·중복 | 유지 보수·읽기 어려움 | 재사용 스키마·정책 lint·설계 리뷰 |
| 비대화·비표준 표현 | 도구 호환 저하 | OAS 버전·확장 필드 사용 규칙·검증 기 지정 |

### Ⅵ. OAS 운영 제언

- 핵심 요약 : API 오너는 계약 승인·변경·폐기 책임과 호환성 자동 검사를 저장소·릴리스에 연결.

1. 플랫폼 팀은 템플릿·lint 규칙·보안 스키마 기본 값을 제공.
2. 소비자와 제공자는 파괴적 변경·폐기 일정·버전 병행 기간을 합의.
3. CI는 스키마 검증·계약 시험·변경 영향 리포트를 릴리스 게이트로 실행.

### Ⅶ. 결론

- 핵심 요약 : OAS는 API를 코드 밖에서도 합의·검증·자동화할 수 있게 하는 인터페이스 계약.
- 시사점 : 단일 명세 원천은 구현·문서·시험을 함께 갱신하는 절차와 결합해야 실 효성.
