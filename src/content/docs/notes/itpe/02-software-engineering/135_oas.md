## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 인터페이스·API → **OAS(OpenAPI Specification)**

## 30초 인출

- 본질: OAS는 REST API의 경로·요청·응답·인증을 언어 중립적인 YAML·JSON 문서로 기술하는 표준 명세
- 메커니즘: API 명세 문서를 기준으로 문서 페이지, 클라이언트·서버 코드 골격, 시험과 모의 서버를 생성하고 명세와 구현의 일치를 검증
- 통찰: 구현과 문서를 따로 관리하면 서로 어긋나므로 명세를 먼저 정의하는 설계 우선 방식으로 두고 명세를 기준으로 코드 골격과 계약 시험을 자동 생성

<details>
<summary>핵심 용어</summary>

- **OAS(OpenAPI Specification)** : REST API를 기계가 읽을 수 있게 기술하는 표준 명세
- **OpenAPI Initiative(OAI)** : OAS 표준을 관리하는 협의체
- **설계 우선(Design-First)** : 코드 작성 전에 API 명세를 먼저 정의하는 방식
- **코드 우선(Code-First)** : 코드의 주석·애너테이션에서 명세를 생성하는 방식
- **모의 서버(Mock Server)** : 명세를 기반으로 응답을 흉내 내는 서버
- **계약 시험(Contract Test)** : 구현이 명세와 일치하는지 확인하는 시험

</details>

## 2~4교시 25점 답안

## Ⅰ. OAS의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **OAS** 는 REST API를 기계가 읽을 수 있는 문서로 기술하는 표준 명세 |
| 목적 | API 설계·문서·시험·연동의 공통 기준 제공 |

## Ⅱ. 개별 문서화와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 기계 판독 | YAML·JSON으로 도구가 해석 |
| 언어 중립 | 구현 언어와 무관 |
| 자동화 연계 | 문서·코드·시험 생성 |

## Ⅲ. 명세 구조와 활용 흐름

### 명세의 구조

```text
OpenAPI 문서
    ├─ info ── 제목·버전
    ├─ paths ── 경로·메서드·요청·응답
    ├─ components ── 재사용 스키마·보안 방식
    └─ security ── 인증 방식
```

### 확대: 명세 기반 자동화

```text
OAS 명세
    ├─ API 문서 페이지 생성
    ├─ 서버·클라이언트 코드 골격 생성
    ├─ 모의 서버로 병행 개발
    └─ 계약 시험으로 구현 검증
```

## Ⅳ. 설계 우선과 코드 우선의 비교

| 구분 | 설계 우선 | 코드 우선 |
|---|---|---|
| 순서 | 명세 → 구현 | 구현 → 명세 생성 |
| 협업 | 프론트·백엔드가 명세로 병행 | 구현 후 명세 확인 |
| 일치성 | 명세가 기준 | 코드와 항상 일치, 설계 검토는 늦음 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 구현과 명세의 불일치 | 명세 기준 계약 시험을 CI에 포함 |
| 명세 작성·유지 부담 | 명세를 코드 생성의 원천으로 사용 |
| 표준 규칙 미준수 | 명세 검사 도구로 규칙 점검 |

## Ⅵ. 제언

명세를 먼저 정의하는 설계 우선 방식으로 운영하고, 명세를 기준으로 코드 골격과 계약 시험을 자동 생성해 CI에서 일치 검증

### 명세 중심 개발

```text
OAS 명세 정의·검토
    ↓
코드 골격·모의 서버 생성 → 병행 개발
    ↓
CI: 계약 시험으로 명세 일치 검증
```

### 선택 근거: 문서와 코드 개별 관리와의 비교

| 구분 | 개별 관리 | 제언: 명세 중심 |
|---|---|---|
| 일치성 | 어긋남 | 자동 검증 |
| 병행 개발 | 곤란 | 모의 서버 |
| 문서 최신성 | 수동 갱신 | 명세에서 생성 |
