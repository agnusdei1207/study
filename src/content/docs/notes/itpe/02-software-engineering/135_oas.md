## 연관 키워드

- OAS(OpenAPI Specification), Swagger, API-First, SSOT(Single Source of Truth)
- 명세 드리프트(Specification Drift), Mock 서버, 클라이언트 SDK 자동 생성, 계약 테스트(Contract Testing)

## Ⅰ. OAS(OpenAPI Specification)의 개요

- 핵심 요약 : RESTful API의 인터페이스를 언어 중립적이고 기계 판독이 가능한 명세로 기술해 협업과 자동화의 기반을 제공하는 규격.
- 개념 : RESTful 웹 서비스의 인터페이스를 YAML 또는 JSON으로 기술하는 **OpenAPI 명세** (OAS, OpenAPI Specification). 리눅스 재단 산하 OpenAPI Initiative가 관리하는 산업 표준 API 명세 규격.
- 배경 및 필요성 : 문서를 별도로 작성하면 최신화가 누락되어 백엔드와 프론트엔드 간 스펙이 어긋나고, 클라이언트 코드를 수작업으로 맞추는 비용이 커짐. 이 문제를 줄이기 위해 **Swagger** 2.0 명세를 모태로 표준화.
- 주요 목적 : **API-First** 설계를 지원하고, 기계 판독 가능한 **SSOT**(Single Source of Truth, 단일 진실 공급원)를 확립하며, 문서화와 코드 생성을 자동화.

## Ⅱ. OAS의 특징 및 장점

- 핵심 요약 : 기계 판독형 명세, 재사용 구조, 계약 우선 설계, 자동 생성이 맞물려 API 협업 비용을 낮추는 인터페이스 명세 체계.

1. 기계 판독형 명세 : YAML 또는 JSON으로 인터페이스를 기술 → 문서·검증·코드 생성 도구가 같은 명세를 해석해 불일치 감소.
2. 재사용 구조 : paths와 components를 두고 $ref로 스키마를 참조 → 중복 정의 제거와 데이터 구조의 일관성 확보.
3. 계약 우선 설계 : 명세를 먼저 합의한 뒤 **Mock 서버**를 띄워 개발 → 프론트엔드가 백엔드 구현을 기다리지 않아 병렬 개발 가능.
4. 보안 정의 선언 : OAuth2, Bearer JWT, API Key 방식을 명세 수준에서 정의 → 인증 요구사항을 문서와 검증에 동시 반영.
5. **클라이언트 SDK 자동 생성** (openapi-generator 등) : 명세로부터 다국어 클라이언트 라이브러리를 빌드 → 연동 코드 작성 비용 절감.
6. JSON Schema 기반 검증 : 요청 본문과 응답 페이로드를 스키마로 검사 → 구조 오류를 배포 전에 발견.

## Ⅲ. OAS의 구조 (흐름)

- 핵심 요약 : 최상위 선언에서 info, servers, paths, components, security로 이어지는 계층형 문서 구조와, 명세 작성에서 병렬 개발까지 이어지는 API-First 흐름의 이중 구조.

```text
[ openapi: 3.1.0 ]
        ↓
[ info ] 제목·버전·설명
        ↓
[ servers ] 개발·스테이징·운영 URL
        ↓
[ paths ] 경로·메서드·요청·응답
        ↓
[ components ] 재사용 스키마·보안 정의
        ↓
[ security ] 전역 인증 요구사항
```

```text
[ 1. OAS 명세 작성 ]
        ↓
[ 2. 리뷰·합의 (계약 확정) ]
        ↓
[ 3. Mock 서버 구동 ]
        ↓
[ 4. 백엔드·프론트엔드 병렬 개발 ]
        ↓
[ 5. 계약 테스트·SDK 자동 빌드 ]
```

## Ⅳ. 코드 우선(Code-First)과 명세 우선(API-First)의 비교

- 핵심 요약 : 구현이 명세를 끌고 가는 코드 우선 방식에서 명세가 구현을 이끄는 명세 우선 방식으로 옮겨 가며 협업 병렬화와 변경 통제를 강화.

| 비교 항목 | 코드 우선 개발 (Code-First) | 명세 우선 개발 (API-First) |
| --- | --- | --- |
| 개발 순서 | 백엔드 구현 후 어노테이션으로 명세 생성 | 명세 작성 후 백엔드·프론트엔드 동시 개발 |
| 프론트엔드 협업 | 백엔드 구현 완료까지 대기 | 명세 기반 Mock 서버로 초기부터 병렬 개발 |
| 변경 통제 | 코드 수정이 클라이언트를 깨뜨릴 위험 | 명세 변경의 영향도를 사전에 분석하고 합의 |
| 클라이언트 SDK | 수작업 작성 또는 사후 생성 | openapi-generator로 자동 빌드 |
| 적합 환경 | 소규모 단순 프로젝트, 빠른 PoC | 대규모 MSA 환경, 외부 공개 API 연계 |

## Ⅴ. OAS의 한계와 대응 방안

- 핵심 요약 : 명세와 구현의 불일치, 검증 룰 표현의 한계, 대규모 명세의 비대화를 자동 동기화·규칙 확장·모듈화로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **명세 드리프트** (Specification Drift) | 비즈니스 로직만 수정하고 명세 수정을 누락 → 클라이언트와 연동 시 불일치 장애 | Springdoc 같은 소스 기반 자동 동기화 또는 명세로부터 인터페이스를 생성하는 방식으로 SSOT 유지 | 명세·구현 불일치 건수 |
| 복잡한 검증 룰 표현 한계 | 필드 간 조건부 필수값, 상태별 동적 제약은 기본 JSON Schema로 표현이 어려움 | `x-` 확장 속성으로 도메인 규칙을 표기하고, 표준 에러 응답 형식(RFC 9457, 구 RFC 7807)을 명문화 | 검증 오류 응답 비율 |
| 명세 비대화와 머지 충돌 | 수백 개 엔드포인트를 단일 파일로 관리 → 가독성 저하와 동시 편집 충돌 | $ref 기반 도메인별 파일 분리, Redocly CLI로 번들링 | 명세 파일당 엔드포인트 수, 머지 충돌 빈도 |

## Ⅵ. 엔터프라이즈 API 거버넌스를 위한 기술사적 제언

- 핵심 요약 : CI 파이프라인에 명세 린팅과 호환성 검사를 묶어 API 품질 거버넌스를 자동화하는 체계로 OAS를 상시 운영 역량으로 내재화.

1. 전사 스타일 가이드 자동 강제 : 아키텍처 조직은 URL 네이밍과 에러 응답 형식을 Spectral 같은 린터 규칙으로 정의하고, 이를 CI에 연결해 위반 명세의 병합을 막아야 한다.
2. 하위 호환성 자동 감사 : 명세 변경이 기존 클라이언트를 깨뜨리는지 oas-diff 같은 도구로 PR 단계에서 검사하고, 그 결과를 Semantic Versioning 원칙에 대조한다.
3. 소비자 주도 계약 테스트 도입 : 소비하는 쪽의 기대를 **계약 테스트**(Contract Testing)로 기록하고, 제공자 측 명세와 대조해 배포 전에 불일치를 확인하는 방식을 확산한다.
4. 명세 카탈로그 운영 : 개발자 포털 카탈로그에 명세를 등록해 사내 API 탐색과 재사용을 돕는다.

## Ⅶ. 결론

- 핵심 요약 : OAS는 API를 계약으로 다루는 표준 명세 체계이며, 자동화와 거버넌스의 결합이 도입 성숙도를 가름.
- 시사점 : 명세 드리프트 통제와 대규모 명세 모듈화를 병행해야 SSOT 기반 API 생산성과 협업 품질이 유지됨.
