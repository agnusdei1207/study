## 한 줄 본질
- 엑셀이나 위키에 작성된 수작업 API 문서가 백엔드 코드 수정 시 방치되어 프론트엔드 연동 장애를 유발하는 병목 → RESTful API의 엔드포인트, 요청/응답 형식, 인증 방식을 표준화된 JSON/YAML 형식으로 정의하여 코드 생성과 문서화를 자동화하는 표준 명세 / 스펙 변경 관리 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  OAS 3.x 핵심 구조 및 API-First 생명주기 도구 연계      |
+-------------------------------------------------------------------------+
|  [ OAS 문서 구조 (YAML) ]                                               |
|  openapi: "3.0.3"                                                       |
|  info: { title, version, description }                                  |
|  servers: [ { url: "https://api.example.com/v1" } ]                     |
|  paths:                                                                 |
|    /users/{id}:                                                         |
|      get:                                                               |
|        parameters: [ ... ]                                              |
|        responses:                                                       |
|          '200': { content: { application/json: { schema: ... } } }     |
|  components:                                                            |
|    schemas: { User: { type: object, properties: { ... } } }             |
|    securitySchemes: { BearerAuth: { type: http, scheme: bearer } }     |
|                                                                         |
|  [ 도구 연계 생태계 ]                                                   |
|   - Swagger Editor  ──> [ OAS Spec ] ──> Swagger UI (문서화/테스트)     |
|                                     ├──> Prism (Mock 서버 구동)         |
|                                     └──> openapi-generator (SDK 생성)   |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- Design-First(설계 우선): 코드를 한 줄도 작성하기 전에 OAS 명세서를 먼저 작성하고 프론트엔드/백엔드 개발자가 인터페이스 계약을 합의한 뒤 구현에 착수하는 개발 방식
- Code-First(코드 우선): 백엔드 소스코드에 애너테이션(`@Operation`, `@ApiResponse`)을 달아 코드를 기반으로 OAS 명세를 사후 자동 추출하는 개발 방식

## 핵심 통찰
- OAS(스펙 규약)와 Swagger(도구 모음)를 혼동하는 경우가 많으나, Swagger 2.0이 리눅스 재단의 OpenAPI Initiative(OAI)에 기증되어 표준화된 것이 OAS 3.0임
- Code-First는 초기 작성이 빠르지만 백엔드 개발이 끝날 때까지 프론트엔드가 대기해야 하는 병목이 생기는 반면, Design-First는 OAS 작성 즉시 Prism 같은 Mock 서버를 띄워 프론트와 백엔드가 동시 개발할 수 있음
- OAS 3.x의 가장 큰 개선점은 `components` 객체를 통한 데이터 스키마와 응답의 재사용성 극대화, 그리고 다중 서버 URL 정의 및 `callbacks/webhooks` 비동기 API 명세 지원임

## 이웃 토픽과 구분
- OAS vs WSDL: OAS = RESTful JSON API를 위한 가볍고 현대적인 표준 명세 / WSDL = SOAP 기반의 무거운 XML 기반 웹 서비스 기술 언어

## 문제·원인·대책
- 적용 상황: 웹/모바일 프론트엔드와 백엔드 간 분산 개발 프로젝트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 백엔드 개발 완료 시점까지 프론트엔드 연동 테스트가 지연되어 프로젝트 마감 임박 | 백엔드 구현이 끝나야만 실제 API 호출이 가능한 전통적 직렬 개발 방식 | Design-First 접근법 적용 및 OAS 기반 가상 Mock API 서버(Prism) 즉시 배포 | 프론트-백엔드 병렬 개발로 전체 공기 30% 단축 |
| 백엔드 개발자가 코드는 바꿨으나 위키 문서 갱신을 누락하여 400 Bad Request 빈발 | 소스코드와 API 명세 문서가 서로 다른 시스템에 분리되어 동기화 실패 | OAS 기반 `openapi-generator`로 TypeScript/Java 클라이언트 SDK 자동 생성 | 인터페이스 규격 불일치 오류 100% 원천 방지 |
