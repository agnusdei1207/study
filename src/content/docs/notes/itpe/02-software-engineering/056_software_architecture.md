## 30초 인출

- 본질: 소프트웨어 아키텍처는 시스템을 구성하는 요소와 요소 사이의 관계, 그리고 설계 원칙을 정한 구조
- 메커니즘: 품질속성 요구를 시나리오로 정하고 구조 결정(스타일·구성요소)으로 만족시키며 4+1 뷰 등 여러 관점으로 기술
- 통찰: 품질속성 요구와 구조 결정의 이유를 남기지 않으면 후속 변경 때 설계 의도를 잃으므로 품질속성 시나리오로 결정하고 결정 기록으로 근거를 보존

- **컴포넌트·커넥터** : 실행 단위와 그 사이의 상호작용 수단
- **아키텍처 결정 기록(ADR)** : 결정의 배경·대안·이유를 남기는 문서

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 아키텍처의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 아키텍처** 는 시스템 구성요소와 그 관계, 설계 원칙을 정한 기본 구조 |
| 목적 | 품질속성 요구의 충족과 개발·변경의 기준 제공 |

## Ⅱ. 상세 설계와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 구조 수준의 결정 | 변경 비용이 큰 핵심 결정 |
| 품질속성 중심 | 성능·보안·확장성 등 요구가 구조를 좌우 |
| 다관점 표현 | 이해관계자별 관점으로 기술 |

## Ⅲ. 아키텍처의 표현과 결정 과정

### 4+1 뷰 모델

```text
        시나리오 뷰 (유스케이스)
       /      |       |      \
 논리 뷰  프로세스 뷰  개발 뷰  물리 뷰
 (기능 구조) (동시성·성능) (모듈 구성) (배치·인프라)
```

### 확대: 아키텍처 결정 흐름

```text
품질속성 요구 → 시나리오 정의
    ↓
아키텍처 스타일·구성요소 결정
    ↓
뷰로 기술 → 결정 기록
```

## Ⅳ. 뷰와 품질속성

### 4+1 뷰의 대상

| 뷰 | 관점 | 주 이해관계자 |
|---|---|---|
| 논리 뷰 | 기능 구조(클래스·패키지) | 설계자 |
| 프로세스 뷰 | 동시성·성능·통신 | 통합 담당자 |
| 개발 뷰 | 소스·모듈 구성 | 개발자 |
| 물리 뷰 | 하드웨어·네트워크 배치 | 운영자 |
| 시나리오 뷰 | 유스케이스로 네 뷰 검증 | 전체 |

### 대표 품질속성

| 품질속성 | 구조 결정의 예 |
|---|---|
| 성능 | 캐시·비동기 처리 |
| 가용성 | 이중화·장애 조치 |
| 수정 용이성 | 모듈 분리·인터페이스 추상화 |
| 보안 | 계층 분리·접근 통제 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 품질속성이 구조 결정에 반영되지 않음 | 품질속성 시나리오를 결정 기준으로 사용 |
| 결정 근거 소실로 후속 변경 시 의도 파악 곤란 | 결정 기록에 배경·대안·이유 보존 |
| 특정 관점만 기술해 이해관계자 간 오해 | 여러 뷰로 기술 |

## Ⅵ. 제언

우선순위 높은 품질속성 시나리오를 먼저 정하고, 구조 결정마다 이유와 대안을 결정 기록으로 남김

### 결정 기록 중심의 설계 순서

```text
핵심 품질속성 시나리오 정의
    ↓
구조 결정 (스타일·구성요소)
    ↓
결정 기록 (배경·대안·이유)
```

### 선택 근거: 결과만 문서화하는 방식과의 비교

| 구분 | 결과 구조만 문서화 | 제언: 결정 기록 |
|---|---|---|
| 설계 의도 | 소실 | 보존 |
| 변경 영향 | 파악 곤란 | 결정 단위로 식별 |
| 작성 부담 | 낮음 | 결정마다 기록 |
