## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어 공학 → 아키텍처 설계 → 소프트웨어 아키텍처

## 30초 인출

- 본질: **소프트웨어 아키텍처**는 시스템의 핵심 요소·관계와 설계·진화 원칙으로 이루어진 기본 구조
- 메커니즘: 이해관계자 관심사 → 관점별 아키텍처 뷰 → 품질 시나리오에 따른 선택·평가
- 핵심: 구성요소와 연결 방식이 품질 요구·제약에 맞는지 검토하고 결정 근거를 보존

<details>
<summary>핵심 용어</summary>

- **소프트웨어 아키텍처**: 시스템의 근본 개념·속성이 요소·관계·설계와 진화 원칙에 구현된 구조
- **아키텍처 기술서(Architecture Description)**: 아키텍처를 이해관계자 관점과 모델로 표현한 산출물
- **컴포넌트(Component)**: 정해진 책임을 수행하는 시스템 구성요소
- **커넥터(Connector)**: 컴포넌트 간 상호작용을 표현하는 연결 요소
- **4+1 View**: 유스케이스 시나리오를 중심으로 논리·프로세스·개발·물리 관점을 표현하는 아키텍처 모델
- **ATAM(Architecture Tradeoff Analysis Method)**: 품질 시나리오를 이용해 아키텍처 위험과 절충점을 분석하는 평가 방법
- **ADR(Architecture Decision Record)**: 아키텍처 결정·대안·근거를 남기는 기록

</details>

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 아키텍처**는 시스템의 근본 개념·속성이 요소·관계·설계와 진화 원칙에 구현된 구조 |
| 목적 | 이해관계자의 관심사를 구조와 설계 결정으로 연결하고 품질 요구의 충족 가능성 검토 |

### Ⅱ. 주요 표현 관점

| 4+1 관점 | 표현 대상 |
|---|---|
| 논리 뷰 | 기능·도메인 구성과 요소 관계 |
| 프로세스 뷰 | 실행 시 동시성·통신·성능 측면 |
| 개발 뷰 | 소스·모듈·구현 구성 |
| 물리 뷰 | 실행 환경과 배포 구성 |
| 시나리오(+1) | 주요 사용 사례로 다른 뷰의 설계 검토 |

### Ⅲ. 품질 요구와 설계 결정

```text
이해관계자 관심사·품질 요구
    ↓ 시나리오화
구조 대안 설계·아키텍처 뷰
    ↓ 품질 시나리오 검토
설계 결정·근거 기록

위험·절충점 발견 → 구조 대안 재검토
```

제언: 품질 시나리오와 대안 검토 결과를 아키텍처 결정 기록에 함께 보존.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 아키텍처**는 시스템의 근본 개념·속성이 요소·관계·설계와 진화 원칙에 구현된 구조 |
| 목적 | 이해관계자의 관심사를 구조와 설계 결정으로 연결하고 품질 요구의 충족 가능성 검토 |

## Ⅱ. 요소와 관계

```text
요청자
    ↓
서비스 컴포넌트
    ├─ 데이터 조회 → 저장소
    └─ 외부 연계 → 외부 서비스
```

구성요소·연결은 시스템 경계와 관심사에 맞춰 정의하며, 이 단순 모델의 구체적 요소는 설명을 위한 예시.

## Ⅲ. 아키텍처 기술 관점: 4+1 View

| 관점 | 다루는 구조·관심사 | 검토 대상 |
|---|---|---|
| 논리 뷰 | 주요 기능·도메인 요소 | 책임 분리·기능 관계 |
| 프로세스 뷰 | 실행 중 동작·통신·동시성 | 성능·가용성·동기화 |
| 개발 뷰 | 구현 모듈·패키지 구성 | 개발·통합·재사용 |
| 물리 뷰 | 노드·네트워크·배포 배치 | 자원·운영·배포 제약 |
| 시나리오(+1) | 사용 사례와 품질 요구 | 다른 뷰의 적합성 검토 |

## Ⅳ. 품질 요구에 따른 설계·평가

| 품질 요구 | 설계 질문 | 검토 방법 |
|---|---|---|
| 성능 | 부하·응답 목표를 어떤 구조가 지원하는가 | 품질 시나리오·부하 시험 |
| 가용성 | 장애를 어떻게 격리하고 복구하는가 | 장애 시나리오·복구 시험 |
| 보안 | 신뢰 경계와 권한을 어디에 두는가 | 위협 분석·보안 검토 |
| 변경성 | 변화가 구성요소 간 파급을 어떻게 제한하는가 | 의존성·변경 영향 검토 |

ATAM은 이해관계자 우선순위와 품질 시나리오를 바탕으로 위험·민감점·절충점을 분석하는 방법.

## Ⅴ. 아키텍처 침식과 유지 통제

| 위험 | 통제 |
|---|---|
| 구현 변경이 정한 계층·의존 원칙을 위반 | 자동 구조 검사와 코드 리뷰 기준으로 위반 확인 |
| 결정 배경이 사라져 같은 대안 검토 반복 | 대안·제약·결정 근거를 ADR에 기록 |
| 초기 설계가 운영 조건과 달라짐 | 운영·장애·성능 시나리오를 설계 검토와 검증에 포함 |
| 뷰 사이 구조 불일치 | 논리·개발·배포 요소의 대응 관계를 함께 갱신 |

## Ⅵ. 기술사적 제언 — 핵심 원칙의 검증 가능한 관리

| 한계 | 해결 방안 |
|---|---|
| 문서의 설계 원칙과 실제 구현이 달라져 품질 요구와 운영 구조의 정합성 확인이 어려워질 가능성 | 품질 요구별 뷰·ADR·자동 구조 검사 항목을 연결하고, 설계 변경 때 영향 뷰와 검증 결과를 함께 갱신 |
