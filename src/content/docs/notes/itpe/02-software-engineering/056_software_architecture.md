## 30초 인출

- 본질: 소프트웨어 시스템의 기본 골격으로서 컴포넌트(요소)와 커넥터(상호관계), 그리고 시스템의 설계와 지속적 진화를 통제하는 기본 원칙과 가이드라인의 총체
- 메커니즘: 이해관계자 비즈니스 목표 수립 → 품질속성 시나리오 도출 → 4+1 View 기반 다관점 아키텍처 모델링 → ATAM/CBAM 기반 아키텍처 평가 및 기준선 수립
- 통찰: 단순 정적 구조도만으로는 런타임 성능 및 복구 가용성 검증이 불가능하므로 유스케이스 기반의 품질 시나리오와 아키텍처 피트니스 함수(Fitness Function)를 통한 지속적 적합성 검증 필수

<details>
<summary>핵심 용어</summary>

- **Software Architecture(소프트웨어 아키텍처)** : 소프트웨어 구성요소들의 구조와 그들 간의 관계, 그리고 설계와 진화의 원칙을 담은 청사진
- **4+1 View Model** : 필립 크루첸(Philippe Kruchten)이 제안한 모델로, 유스케이스 뷰를 중심으로 논리, 구현(개발), 프로세스, 배포(물리) 뷰를 통합 기술하는 다관점 프레임워크
- **Quality Attribute Scenario(품질속성 시나리오)** : 자극원, 자극, 환경, 대상, 응답, 응답 척도의 6개 요소로 품질 요구를 정량화하는 시나리오
- **Component & Connector** : 연산과 상태를 캡슐화한 실행 단위(컴포넌트)와 이들 간의 통신과 상호작용을 중개하는 매개체(커넥터)
- **ADR (Architecture Decision Record)** : 아키텍처 결정 사항의 맥락, 대안, 결정 이유, 결과를 기록하여 아키텍처 부식을 방지하는 표준 문서

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 아키텍처의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 시스템의 하위 구성요소(Component)들과 그들 간의 상호작용 관계(Connector), 그리고 이들을 구성하고 진화시키는 원칙과 제약조건들의 총체적 집합 (ISO/IEC/IEEE 42010) |
| 목적 | 다양한 이해관계자 간의 원활한 의사소통 기준선 제공, 고난도 비기능 품질속성(성능, 가용성, 보안)의 조기 충족 보장, 초기 설계 결정의 번복 비용 최소화 |

## Ⅱ. 소프트웨어 아키텍처의 핵심 특징

| 특징 | 의미 |
|---|---|
| 최고 수준의 추상화 | 세부 구현 알고리즘을 감추고 전체 시스템의 구조적 골격과 컴포넌트 경계에 집중 |
| 다관점 뷰(Multi-view) 지원 | 사용자, 개발자, 운영자, 기획자 등 이해관계자의 서로 다른 관심사를 분리하여 기술 |
| 품질속성(비기능 요구) 결정 | 변경성, 확장성, 장애 허용성 등 핵심 아키텍처 품질의 성패를 설계 단계에서 좌우 |
| 트레이드오프(Trade-off) 관리 | 보안 강화 시 성능 저하 등 상충되는 품질 요구 간의 균형점을 분석하고 최적 절충안 도출 |

## Ⅲ. 소프트웨어 아키텍처 체계 및 4+1 View 프레임워크

### 크루첸(Kruchten)의 4+1 View 아키텍처 구조

```text
               ┌────────────────────────────────────────────────────────┐
               │              [유스케이스 뷰 (+1 View, Scenarios)]       │
               │   - 최종 사용자 관점의 핵심 기능 및 품질속성 시나리오   │
               │   - 다른 4대 뷰의 설계 유효성을 검증하는 중심 축        │
               └───────────────────┬────────────────────────────────────┘
                                   │ 검증 및 정렬
         ┌─────────────────────────┼─────────────────────────┐
         ▼ (설계자 관점)           │                         ▼ (개발자 관점)
┌─────────────────────────────────┐│ ┌─────────────────────────────────┐
│ [논리 뷰 (Logical View)]        ││ │ [구현/개발 뷰 (Implementation)] │
│ - 클래스 다이어그램, 도메인 모델││ │ - 패키지 구조, 컴포넌트, 빌드 관리│
│ - 시스템의 기능적 요구사항 명세 ││ │ - 소프트웨어 모듈성 및 재사용성  │
└─────────────────────────────────┘│ └─────────────────────────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼ (시스템 통합자 관점)    │                         ▼ (운영/인프라 관점)
┌─────────────────────────────────┐│ ┌─────────────────────────────────┐
│ [프로세스 뷰 (Process View)]    ││ │ [배포/물리 뷰 (Deployment View)] │
│ - 동시성, 쓰레드, 비동기 큐잉   ││ │ - 클라우드 노드, 네트워크 토폴로지│
│ - 성능, 처리량, 확장성, 가용성  ││ │ - 물리적 하드웨어 배치 및 분산 환경│
└─────────────────────────────────┘  └─────────────────────────────────┘
```

### 4+1 View 모델의 세부 분석

| 뷰(View) 명칭 | 대상 이해관계자 | 주요 관심사 및 다루는 대상 | 대표적인 UML 모델링 다이어그램 |
|---|---|---|---|
| **유스케이스 뷰 (+1)** | 최종 사용자, 고객 | 시스템이 제공해야 할 핵심 기능 및 품질 시나리오 검증 | 유스케이스 다이어그램, 인수 시나리오 |
| **논리 뷰 (Logical)** | 시스템 분석가, 설계자 | 시스템의 기능적 요구사항, 도메인 엔티티 구조 및 책임 분할 | 클래스 다이어그램, 상태 머신 다이어그램 |
| **구현 뷰 (Implementation)** | 프로그래머, 개발팀 | 모듈 계층 구조, 패키지 구성, 서드파티 라이브러리 의존성 | 패키지 다이어그램, 컴포넌트 다이어그램 |
| **프로세스 뷰 (Process)** | 시스템 통합자 | 동시성(Concurrency), 태스크 스케줄링, 비동기 통신 | 활동 다이어그램, 시퀀스 다이어그램 |
| **배포 뷰 (Deployment)** | 시스템 엔지니어, 인프라 | 물리적 서버 노드, 컨테이너 클러스터, 네트워크 통신망 | 배치 다이어그램(Deployment Diagram) |

## Ⅳ. 아키텍처 3대 구성요소 및 품질속성 반영 메커니즘

### 아키텍처 핵심 3요소 (C&C 모델)
1. **컴포넌트 (Component)** : 연산(Computation)과 상태(State)를 캡슐화한 독립적 소프트웨어 실행 단위 (예: 주문 서비스, 결제 모듈, DB)
2. **커넥터 (Connector)** : 컴포넌트 간의 상호작용(Interaction)과 데이터 흐름을 중개하는 연결 메커니즘 (예: REST API, gRPC, 메시지 큐, 공유 메모리)
3. **제약조건 (Configuration & Constraints)** : 컴포넌트와 커넥터가 결합되는 아키텍처 스타일 및 구조적 배치 규칙

### SEI 6대 품질속성 시나리오 구성 체계

| 시나리오 구성요소 | 정의 및 의미 | 전자상거래 적용 예시 |
|---|---|---|
| **자극원 (Source)** | 자극을 발생시키는 주체 | 외부 불특정 다수 고객 |
| **자극 (Stimulus)** | 시스템에 가해지는 입력 조건 또는 이벤트 | 블랙프라이데이 타임세일 동시 접속 폭주 (초당 5만 건) |
| **환경 (Environment)** | 자극이 발생하는 시스템의 가동 조건 | 프로덕션 운영 환경, 피크 타임 상태 |
| **대상 (Artifact)** | 자극의 영향을 받는 아키텍처 컴포넌트 | 주문 수신 API Gateway 및 주문 처리 마이크로서비스 |
| **응답 (Response)** | 자극 발생 시 시스템이 취해야 하는 가시적 행위 | 트래픽 버퍼링(Kafka), 오토스케일링 및 정상 처리 |
| **응답 척도 (Measure)** | 응답의 성공 여부를 측정하는 정량적 지표 | **요청 성공률 99.99% 이상, P99 응답 시간 1.5초 이내** |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 초기 아키텍처 설계와 실제 구현 소스코드 간의 괴리로 인한 아키텍처 부식(Erosion) | ArchUnit 및 SonarQube를 CI 파이프라인에 통합하여 계층 의존성 규칙을 자동 강제 |
| 비기능 품질 요구 간의 상충 관계(보안 강화 vs 성능 저하)로 인한 설계 혼선 발생 | ATAM(아키텍처 절충 분석) 기법을 적용하여 비즈니스 가치 기반의 민감점·절충점 식별 |
| 아키텍처 설계 결정의 맥락이 문서화되지 않아 담당자 퇴사 시 기술 부채로 전락 | 모든 주요 기술 결정마다 ADR(Architecture Decision Record) 작성을 의무화하고 Git 관리 |

## Ⅵ. 제언

진화형 아키텍처(Evolutionary Architecture) 구축 및 아키텍처 피트니스 함수(Fitness Function) 자동화

### 진화형 아키텍처 거버넌스 파이프라인

```text
[요구사항 및 비즈니스 환경 변화]
       ↓
[모듈러 아키텍처 설계 (Microservices / Hexagonal)]
       ↓
[CI/CD 파이프라인 내 피트니스 함수(Fitness Function) 실행]
  ├─ 1. 모듈 결합도 검증 (JDepend: 불안정성 I 및 추상성 A 메트릭 측정)
  ├─ 2. 서킷 브레이커 장애 격리 검증 (Chaos Mesh 결함 주입 테스트)
  └─ 3. 보안 신뢰 경계 검증 (Trivy 컨테이너 취약점 스캔)
       ↓
[아키텍처 품질 메트릭 대시보드 시각화 및 지속적 리팩토링 수행]
```

### 아키텍처 스타일 선정 의사결정 체계

```text
시스템 요구사항 분석
       ↓
[시스템 규모가 작고 트랜잭션 무결성이 최우선인가?]
       ├─ 예 ──→ 모놀리식 / 모듈러 모놀리스 (단순성 극대화)
       └─ 아니오 ─→ [서비스별 독립 배포와 개별 확장이 필수적인가?]
                         ├─ 예 ──→ 마이크로서비스 아키텍처 (MSA)
                         └─ 아니오 ─→ [실시간 비동기 이벤트 스트리밍 중심인가?]
                                           ├─ 예 ──→ 이벤트 주도 아키텍처 (EDA)
                                           └─ 아니오 ─→ 계층형 아키텍처 (Layered)
```

### 선택 근거: 전통적 고정 아키텍처와 제언 진화형 아키텍처 비교

| 구분 | 전통적 사전 대규모 설계 (BDUF) | 제언: 진화형 아키텍처 (Evolutionary) |
|---|---|---|
| 설계 전제 | 초기에 모든 요구와 구조를 확정 가능하다고 가정 | 변화는 불가피하며 점진적으로 진화한다고 전제 |
| 검증 방식 | 설계 리뷰 회의를 통한 문서 중심 정성 검토 | CI/CD 기반 자동화된 피트니스 함수 정량 측정 |
| 변경 유연성 | 구조 변경 시 시스템 전반에 막대한 사이드이펙트 | 모듈 격리와 테스트 자동화로 안전하고 빠른 점진적 개선 |
