## 1. 소프트웨어 아키텍처의 개요 및 필요성

### (1) 소프트웨어 아키텍처(Software Architecture)의 정의
- 시스템의 소프트웨어 구성요소(Component), 이들 간의 관계(Connector), 그리고 이들을 설계하고 진화시키는 원칙과 지침을 포함하는 **소프트웨어의 최고 수준의 근본 구조적 틀(IEEE 1471 / ISO/IEC 42010)**.
- "나중에 변경하기 가장 어려운 중요한 결정들의 집합"(Martin Fowler).

### (2) 아키텍처의 핵심 필요성
- **이해관계자 간 공통 의사소통 기준**: 개발자, 고객, 운영자 간의 서로 다른 관점을 조율하는 단일 진실 공급원(SSOT).
- **비기능 품질 속성(Quality Attributes) 보장**: 성능(0.5초 응답), 가용성(99.99%), 보안, 변경용이성 등 시스템의 성패를 가르는 비기능 요구를 구조적으로 달성.
- **아키텍처 침식 방지 및 유지보수 비용 절감**: 초기 설계 원칙을 확립하여 장기적 시스템 노후화와 스파게티 코드 전락을 방지.

## 2. 아키텍처 핵심 구성요소 및 Kruchten 4+1 View 체계

### (1) 아키텍처 3대 핵심 구성요소
1. **컴포넌트 (Components)**: 연산을 수행하거나 상태를 캡슐화한 시스템의 기본 실행 블록 (모듈, 클래스, 서비스).
2. **커넥터 (Connectors)**: 컴포넌트 간의 상호작용과 데이터 흐름을 매개하는 메커니즘 (메시지 큐, REST API, RPC, 공유 메모리).
3. **제약조건 (Constraints)**: 시스템이 준수해야 하는 구조적 토폴로지, 프로토콜, 비기능 속성 및 운영 환경의 한계.

### (2) Kruchten 4+1 View 구조도
```text
+-------------------------------------------------------------------------+
|                  소프트웨어 아키텍처 Kruchten 4+1 View 체계              |
+-------------------------------------------------------------------------+
|                        [ 유스케이스 뷰 (Use Case) ]                      |
|                        - 최종 사용자 관점 (기능 요구 명세)              |
|                                     │                                   |
|               ┌─────────────────────┼─────────────────────┐             |
|               v                     v                     v             |
|     [ 논리 뷰 (Logical) ]    [ 프로세스 뷰 ]       [ 구현 뷰 (Impl.) ]  |
|     - 설계자 관점            - 통합자 관점         - 프로그래머 관점    |
|     - 클래스, 패키지, 인터페이스- 동시성, 성능, 확장성 - 컴포넌트, 소스 코드|
|               \                     |                     /             |
|                └────────────────────┼────────────────────┘              |
|                                     v                                   |
|                         [ 배포 뷰 (Deployment) ]                        |
|                         - 시스템 엔지니어 / 인프라 관점                 |
|                         - 물리적 서버 노드, 네트워크 토폴로지, K8s 파드 |
+-------------------------------------------------------------------------+
```

### (3) 4+1 View 상세 매핑
| View 구분 | 주 이해관계자 | 주요 관심사 및 다루는 주제 | 표현 다이어그램 |
|---|---|---|---|
| **유스케이스 뷰 (+1)** | 최종 사용자, 발주자 | 시스템이 제공해야 하는 기능적 유스케이스 및 시나리오 | Use Case Diagram |
| **논리 뷰 (Logical)** | 시스템 분석가, 설계자 | 도메인 개념, 클래스 구조, 기능적 계층 분할 및 상호작용 | Class, Sequence Diagram |
| **프로세스 뷰 (Process)** | 시스템 통합자, 아키텍트 | 비기능 요구(성능, 확장성), 동시성(스레드), 프로세스 간 IPC | Activity, State Diagram |
| **구현 뷰 (Implementation)** | 프로그래머, 형상관리자 | 실제 코드 모듈화, 컴포넌트 라이브러리, 의존성 패키징 | Component, Package Diagram |
| **배포 뷰 (Deployment)** | TA, 인프라 운영자 | 하드웨어 인프라 매핑, 네트워크 토폴로지, 물리적 서버 배치 | Deployment Diagram |

## 3. 소프트웨어 아키텍처 모델 유형 및 평가 체계

### (1) 대표적 아키텍처 모델 유형 (120회 기출)
- **데이터 흐름 모델 (Data Flow)**: 파이프 앤 필터(Pipe and Filter), 배치 순차(Batch Sequential).
- **데이터 중심 모델 (Data Centered)**: 저장소(Repository), 칠판(Blackboard) 패턴.
- **계층화 모델 (Layered)**: 3-Tier, n-Tier, 헥사고날(Ports and Adapters), 클린 아키텍처.
- **독립 컴포넌트 모델 (Independent Components)**: 이벤트 기반(Event-Driven, EDA), 마이크로서비스(MSA), 브로커 패턴.

### (2) 아키텍처 평가 체계
- **ATAM (Architecture Tradeoff Analysis Method)**: 품질 속성 간의 트레이드오프 분석 및 민감점(Sensitivity Point), 절충점(Tradeoff Point) 식별.
- **CBAM (Cost Benefit Analysis Method)**: ATAM 이후 경제적 비용 대 편익(ROI)을 정량 평가하여 우선순위 결정.

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **아키텍처 침식(Erosion)으로 배포 불가**<br>(계층 간 불법 직접 참조로 스파게티화) | 일정 압박으로 개발자가 Controller에서 직접 DB Repository를 호출하는 등 계층 규칙 훼손 | ArchUnit 테스트를 CI 빌드에 탑재하여 아키텍처 규칙 위반 시 빌드 즉시 실패 처리 | 계층 위반 불법 참조 0건 차단, 모듈 결합도 50% 개선 |
| **시스템 오픈 후 5년 경과 시 설계 추적 불가**<br>(왜 그렇게 설계했는지 아무도 모름) | 초기 설계 문서만 작성하고 개발 중 발생한 아키텍처 변경 이력(Context) 미기록 | 경량 ADR(Architecture Decision Record) 양식을 저장소 내 마크다운으로 버전 관리 | 아키텍처 설계 의사결정 맥락 추적성 100% 확보 |
| **품질 속성 미달로 인한 전면 재구축**<br>(통합 테스트 단계에서 목표 TPS 달성 실패) | 기능 구현에만 치중하여 비기능 요구(성능 시나리오)를 조기에 아키텍처에 반영 누락 | 프로젝트 분석 단계에서 품질 속성 시나리오 도출 및 초기 PoC 기반 ATAM 평가 수행 | 오픈 전 아키텍처 결함 90% 사전 색출 및 재작업 방지 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 종이 위 정적 아키텍처]             [현대: 진화형 실행 아키텍처 (Evolutionary)]
- 프로젝트 초기에만 그리고 방치      ──▶   - 아키텍처 피트니스 함수(Fitness Functions) 자동 검증
- 수백 페이지의 난해한 SAD 문서     ──▶   - Git 기반의 경량 ADR (Architecture Decision Record)
- 닫힌 모놀리식 구조의 고착화       ──▶   - 서비스 메시 및 분산 이벤트 기반의 탄력적 진화
```

- **진화형 아키텍처(Evolutionary Architecture)와 피트니스 함수**: 시스템은 비즈니스 환경에 따라 끊임없이 진화해야 함. 이때 시스템이 갖추어야 할 핵심 품질 속성(보안성, 응답시간, 결합도)을 코드로 자동 측정하는 **아키텍처 피트니스 함수(Fitness Function)**를 CI/CD 파이프라인에 구축하여 아키텍처 표류를 방지해야 함.
- **비즈니스 가치와 기술 결정의 일치**: 아키텍처는 기술적 자존심이 아니라 비즈니스 제약(Time-to-Market vs 결함 허용도)을 해결하기 위한 도구임. 따라서 항상 품질 속성 간의 상충 관계(예: 보안성 향상 $\leftrightarrow$ 처리 속도 저하)를 기술사적 관점에서 명확한 근거로 절충하는 논리를 제시해야 함.
