## 연관 키워드

- 소프트웨어 안전성, FTA, FMEA, HAZOP, STPA
- 최소 절단집합, 위험 우선순위 수치(RPN), 안전 요구사항, 기능안전 표준

## Ⅰ. 소프트웨어 안전성 분석의 개요

- 핵심 요약 : 소프트웨어 안전성 분석은 고장·위험 상태를 사전에 식별해 안전 요구사항과 검증 증거로 연결하는 체계적 활동.
- 개념 : 시스템과 소프트웨어의 고장·오동작이 인명·자산에 미칠 위험을 개발 초기부터 식별·평가하고 **안전 요구사항**(safety requirement, 위험 통제를 위한 요구)으로 전환하는 분석 활동(**소프트웨어 안전성 분석**, Software Safety Analysis). FTA·FMEA·HAZOP·STPA가 대표 기법.
- 배경 및 필요성 : SW가 자동차·의료·원전 등 안전필수 시스템의 제어를 담당하면서 SW 결함이 인명·자산 피해로 직결되고, **기능안전 표준**(functional safety standard, IEC 61508·ISO 26262)이 위험 분석과 안전 요구 할당을 요구.
- 주요 목적 : 위험의 조기 식별·통제와 잔여 위험을 허용 수준 이하로 유지하는 안전 보증.

## Ⅱ. 소프트웨어 안전성 분석기법의 특징 및 장점

- 핵심 요약 : 연역·귀납·편차 탐색·제어 관점 등 서로 다른 방향의 위험 접근이 상호 보완.

1. **FTA**(Fault Tree Analysis, 결함수 트리 분석) : 상위 사고(Top Event)를 논리 게이트(AND·OR)로 분해하는 연역적 하향 분석 → **최소 절단집합**(minimal cut set, 사고를 유발하는 최소 원인 조합) 도출로 위험 조합 식별.
2. **FMEA**(Failure Mode and Effects Analysis, 고장 양상·영향 분석) : 구성요소·기능별 고장 양상을 하나씩 검토하는 귀납적 상향 분석 → 심각도·발생도·검출도로 **위험 우선순위 수치**(RPN, Risk Priority Number) 산정과 예방 우선순위 확보.
3. **HAZOP**(Hazard and Operability Study, 위험·가동성 분석) : **가이드워드**(guide word, 과다·과소·역방향 등 편차 유도 단어)로 설계 의도와 공정 변수의 이탈 탐색 → 운전·제어 시나리오의 위험·가동성 문제 조기 발견.
4. **STPA**(System-Theoretic Process Analysis, 시스템 이론적 프로세스 분석) : 제어 구조상 **안전하지 않은 제어 행동**(unsafe control action, 위험한 상태로 이끄는 제어 동작)을 식별하는 제어 관점 분석 → 부품 고장이 없어도 발생하는 상호작용·제어 논리 위험까지 검토.

## Ⅲ. 소프트웨어 안전성 분석의 구조 (흐름)

- 핵심 요약 : 시스템 정의부터 위험 분석, 안전 요구 도출, 검증·잔여 위험 승인까지의 생명주기 흐름.

```text
[ 안전성 분석 절차 ]
시스템 정의·위험 식별
   ↓
기법 선택 : FTA(연역)·FMEA(귀납)
            HAZOP(편차)·STPA(제어)
   ↓
위험 시나리오·원인 분석
   ↓
안전 요구사항·안전 제약 도출
   ↓
설계 반영 → 시험·리뷰 검증
   ↓
잔여 위험 평가·승인
```

```text
[ 분석 방향의 차이 ]
FTA  : 사고(상위) → 원인(하위) 연역
FMEA : 부품 고장(하위) → 영향(상위) 귀납
STPA : 제어 구조 → 안전하지 않은 제어 행동
```

- 산출물 연계 : 안전 요구사항은 시스템·SW 요구, 시험사례, 안전 논증 문서와 추적으로 묶임.

## Ⅳ. 사전 안전성 분석과 사후 원인 분석의 비교

- 핵심 요약 : FTA·FMEA 등 사전 안전성 분석은 설계 단계에서 위험을 요구로 전환, 사후 원인 분석은 발생 사건의 재발 방지에 초점.

| 비교 축 | 사전 안전성 분석(FTA·FMEA 등) | 사후 원인 분석(장애 후 조사) |
| --- | --- | --- |
| 수행 시점 | 설계·개발 단계 | 장애·사고 발생 후 |
| 분석 대상 | 잠재 고장·위험 시나리오 | 실제 발생 사건 |
| 비용 구조 | 예방 비용으로 피해 최소화 | 피해 발생 후 대응 비용 급증 |
| 산출물 | 안전 요구·설계 제약·시험 항목 | 재발 방지 대책·개선 과제 |
| 고유 한계 | 미발생 위험의 추상성·누락 가능 | 원인 확정 지연·책임 논란 |

## Ⅴ. 소프트웨어 안전성 분석의 한계와 방안

- 핵심 요약 : 기법 단독 의존·주관적 점수·문서화에 머묾을 다중 기법·추적·독립 검토로 보완.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 기법 단독 의존 | 한 방향 분석의 누락 | FTA·FMEA 등 다중 기법 교차 적용 | 미커버 시나리오 수 |
| RPN 산정 주관성 | 평가자별 편차·우선순위 왜곡 | 등급 기준 정의·복수 평가자 합의 | 평가자 간 일치도 |
| 문서화에 머묾 | 분석 결과가 설계·시험 미반영 | 안전 요구 추적 매트릭스 운영 | 요구-시험 추적률 |
| 분석 경계 누락 | 운영·유지·연계 위험 이탈 | 시스템 경계·운영 시나리오 포함 검토 | 경계 외 시나리오 수 |

## Ⅵ. 소프트웨어 안전성 분석에 대한 제언

- 핵심 요약 : 기능안전 표준의 생명주기 절차 편성과 독립 검증 체계로 안전 보증의 조직화.
- 발주·개발 조직 : 기능안전 표준(IEC 61508·ISO 26262)의 생명주기 절차에 분석·검증 단계를 의무 편성.
- 안전 책임자 : 위험별 통제 소유자·검증 증거·잔여 위험 승인 절차를 안전 케이스(Safety Case, 안전 논증과 증거의 체계)로 정비.
- 독립 검토 조직 : 분석 가정·결과를 재검증해 분석자의 시야 한계를 보완.

## Ⅶ. 결론

- 핵심 요약 : 소프트웨어 안전성 분석은 사고 이후가 아니라 설계 단계에서 위험을 요구와 증거로 전환하는 활동.
- 기법 간 교차 적용과 요구-시험 추적성이 안전 보증의 핵심.
