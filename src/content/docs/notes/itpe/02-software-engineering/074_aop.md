## 연관 키워드

- AOP(Aspect-Oriented Programming), 횡단 관심사(Cross-Cutting Concerns), 조인 포인트(Join Point), 포인트컷(Pointcut)
- 어드바이스(Advice), 애스펙트(Aspect), 위빙(Weaving), Spring AOP, AspectJ, 자기 호출(Self-Invocation), 프록시(Proxy)

## Ⅰ. AOP의 개요

- 핵심 요약 : 흩어진 공통 관심사를 애스펙트 모듈로 분리·캡슐화하는 관점 지향 프로그래밍 패러다임.
- 개념 : 애플리케이션 전반에 걸쳐 흩어져 있는 공통 관심사, 즉 횡단 관심사(Cross-Cutting Concerns: 트랜잭션, 로깅, 보안, 성능 측정 등)를 핵심 비즈니스 로직(핵심 관심사)으로부터 분리하여 별도 모듈(Aspect)로 캡슐화하는 프로그래밍 패러다임(AOP, Aspect-Oriented Programming).
- 배경 및 필요성 : 전통적인 객체지향 프로그래밍(OOP, Object-Oriented Programming)만으로는 여러 클래스에 걸쳐 반복되는 횡단 관심사 코드 중복(Code Scattering)과 핵심 비즈니스 로직 오염(Code Tangling)의 완전한 해결 불가.
- 주요 목적 : 높은 응집도 달성, 단일 책임 원칙(SRP, Single Responsibility Principle) 준수, 유지보수성 및 코드 가독성 극대화.

## Ⅱ. AOP의 특징

- 핵심 요약 : 조인 포인트, 포인트컷, 어드바이스, 애스펙트, 위빙의 5대 개념으로 횡단 관심사의 투명한 결합을 구현하는 특성.

1. 조인 포인트(Join Point) : 메서드 호출, 객체 생성, 예외 발생 등 어드바이스 적용이 가능한 애플리케이션 실행 상의 모든 지점.
2. 포인트컷(Pointcut) : 수많은 조인 포인트 중 실제 어드바이스 적용 지점을 선별하는 표현식(AspectJ 표현식 등).
3. 어드바이스(Advice) : 애스펙트가 실제로 수행하는 구체적 부가 기능 코드(@Before, @After, @Around 등).
4. 애스펙트(Aspect) : 포인트컷과 어드바이스를 하나로 묶은 횡단 관심사 모듈.
5. 위빙(Weaving) : 포인트컷으로 지정된 핵심 비즈니스 코드에 어드바이스를 실제로 결합하는 과정.

## Ⅲ. AOP의 구조 (흐름)

- 핵심 요약 : 분리된 핵심 로직과 애스펙트가 위빙 시점에서 결합되어 최종 애플리케이션이 완성되는 흐름.
- 횡단 관심사 분리부터 위빙까지의 처리 흐름.

```text
[ 핵심 비즈니스 로직 ]
 - OrderService.createOrder()
 - PaymentService.pay(), UserService.login()
[ 횡단 관심사 : LoggingAspect ]
 - @Before : 메서드 시작 시간 기록
 - @AfterReturning : 결과 로깅
 - @AfterThrowing : 예외 로깅
   │  (두 관심사의 결합)
   ▼
[ 위빙 (Weaving) 수행 ]
 - 컴파일 타임 / 로드 타임 / 런타임 프록시
   │
   ▼
[ 최종 실행 애플리케이션 ]
 - 핵심 로직 실행 전후 Aspect 투명 자동 결합
```

- 횡단 관심사 정의 : LoggingAspect의 @Before(시작 시간 기록), @AfterReturning(결과 로깅), @AfterThrowing(예외 로깅) 어드바이스 선언.
- 투명한 결합 : 비즈니스 코드의 수정 없이 지정된 시점에서 애스펙트의 자동 삽입.

## Ⅳ. AOP 3대 위빙 방식의 비교

- 핵심 요약 : 결합 시점에 따른 컴파일 타임, 로드 타임, 런타임 프록시 위빙의 성능·유연성 트레이드오프.
- 애플리케이션 실행 생명주기상의 위빙 시점.

```text
[ 소스코드 ] ──컴파일──▶ [ 클래스 파일 ] ──클래스 로딩──▶ [ 런타임 실행 ]
     │                       │                              │
     ▼                       ▼                              ▼
  CTW 위빙                LTW 위빙                    런타임 프록시 위빙
(AspectJ 컴파일러 ajc)  (AspectJ LTW 에이전트)     (Spring AOP 동적 프록시)
```

| 위빙 방식 | 동작 시점 | 특징 및 장단점 | 대표 도구 |
|---|---|---|---|
| 컴파일 타임 위빙 (CTW, Compile-Time Weaving) | 소스코드 컴파일 시점 | 특별한 컴파일러 필요, 런타임 성능 오버헤드 전무 | AspectJ 컴파일러 (ajc) |
| 로드 타임 위빙 (LTW, Load-Time Weaving) | JVM(Java Virtual Machine) 클래스 로더의 클래스 로딩 시점 | 로딩 속도 미세 지연, JVM 에이전트 설정 필요, 유연함 | AspectJ LTW Agent |
| 런타임 프록시 위빙 | 스프링 컨테이너 빈 생성 시점 (런타임) | 추가 컴파일러 불필요, 메서드 호출만 지원, 프록시 오버헤드 미세 발생 | Spring AOP (JDK Dynamic Proxy / CGLIB) |

## Ⅴ. AOP의 장점과 한계

- 핵심 요약 : 관심사 분리에 따른 응집도·재사용성 이점, 프록시 우회와 디버깅 복잡성의 한계.
- 장점

  1. 핵심 로직과 부가 기능의 분리를 통한 코드 중복 제거 및 응집도 향상.
  2. 비즈니스 코드 비침습(Non-invasive) 방식의 부가 기능 적용과 공통 정책의 집중 관리.
  3. 트랜잭션, 감사 로깅, 분산 추적 등 전사 공통 기능의 일관된 적용.
- 한계점 1 : 자기 호출(Self-Invocation) 시 프록시 우회 문제
  - 한계점 : 스프링 기본 다이내믹 프록시/CGLIB 환경에서 동일 클래스 내부 메서드 직접 호출 시 프록시를 거치지 않아 부가 기능(트랜잭션, 로깅 등) 미적용 결함 발생.
  - 해결 방안 : 메서드 호출 구조의 별도 서비스 빈 분리(Refactoring), AopContext.currentProxy() 명시적 참조 또는 AspectJ LTW(Load-Time Weaving) 도입.
- 한계점 2 : 광범위한 포인트컷 지정으로 인한 성능 저하 및 디버깅 난이도 증가
  - 한계점 : 와일드카드 남용 포인트컷 설정 시 불필요한 메서드까지 인터셉트되어 런타임 오버헤드 발생 및 호출 스택 추적 복잡화.
  - 해결 방안 : 명시적 커스텀 애노테이션 기반 포인트컷 설계(@annotation), APM(Application Performance Monitoring, Scouter·Pinpoint) 분산 추적 태그 연동을 통한 애스펙트 실행 가시성 확보.
- 한계점 3 : 다중 애스펙트 간 실행 순서 충돌(Precedence Conflict)
  - 한계점 : 동일 조인 포인트에 트랜잭션, 보안 인가, 캐시 애스펙트 동시 적용 시 실행 순서 미보장으로 인한 데이터 불일치 또는 비인가 접근 위험.
  - 해결 방안 : @Order 애노테이션 또는 Ordered 인터페이스 구현을 통한 어드바이스 실행 체인 우선순위의 명시적 강제 및 전사 거버넌스 룰 확립.

## Ⅵ. 엔터프라이즈 환경에서의 기술사적 제언

- 핵심 요약 : 자기 호출 한계의 사전 점검과 AOP 적용 범위 거버넌스의 병행.
- Spring AOP 내부 메서드 호출(Self-Invocation) 한계 극복 : Spring AOP는 동적 프록시 기반이므로 동일 객체 내부에서 자기 자신의 @Transactional 메서드 호출 시 프록시를 거치지 않아 트랜잭션 누락 심각 버그 발생 가능, 구조적 서비스 분리 또는 AspectJ LTW 도입 필요.
- 무분별한 AOP 남발 방지와 아키텍처 거버넌스 수립 : 과도한 @Around 어드바이스는 코드 실행 흐름의 불투명화와 스택 트레이스 추적 방해 요인이므로, 시스템 전역 횡단 관심사(트랜잭션, 감사 로깅, 분산 추적)로 적용 범위의 엄격한 제한.

## Ⅶ. 결론

- 핵심 요약 : AOP는 횡단 관심사의 모듈화를 통해 핵심 로직의 순수성을 지키는 설계 원칙.
- 요약 : 애스펙트 모듈과 위빙 메커니즘을 통한 공통 기능과 핵심 비즈니스 로직의 분리 체계.
- 시사점 : 적용 범위의 절제된 선별, 프록시 한계 점검, 실행 순서 거버넌스 확립이 안정적 AOP 도입의 관건.
