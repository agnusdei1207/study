## 1. AOP의 개요 및 등장 배경

### (1) AOP(Aspect Oriented Programming)의 정의
- 시스템 전반에 걸쳐 분산되어 나타나는 **횡단 관심사(Cross-cutting Concerns: 트랜잭션, 보안, 로깅, 성능 측정 등)를 핵심 비즈니스 로직(Core Concerns)으로부터 분리하여 독립된 모듈(Aspect)로 작성하고 결합하는 프로그래밍 패러다임**.
- OOP(객체지향)를 대체하는 것이 아닌, **OOP의 모듈화 한계를 극복하는 보완적 패러다임**.

### (2) 등장 배경
- **코드 중복과 오염(Code Tangling & Scattering)**: 핵심 업무 메서드마다 수십 줄의 트랜잭션 시작/종료, 예외 처리, 로깅 코드가 반복 삽입되어 가독성과 응집도가 심각하게 저하됨.
- **단일 책임 원칙(SRP) 위배**: 순수 비즈니스 객체가 인프라성 부가 기능(인증/인가, 데이터베이스 트랜잭션)에 직접 의존하는 구조적 문제 해결 필요.

## 2. AOP 핵심 구성요소 및 동작 메커니즘

### (1) 핵심 관심사와 횡단 관심사의 분리 구조도
```text
+-------------------------------------------------------------------------+
|                  AOP의 핵심 관심사 및 횡단 관심사 직조 구조도            |
+-------------------------------------------------------------------------+
|   [ 핵심 비즈니스 로직 (Core) ]          [ 횡단 관심사 모듈 (Aspect) ]    |
|   +───────────────────────────+          +─────────────────────────────+ |
|   | OrderService (주문 처리)  |          | 1. 트랜잭션 관리 (@Transactional)|
|   | MemberService (회원 관리) | ◀─────── | 2. 보안 권한 인가 (@PreAuth)|
|   | PaymentService(결제 승인) | (Weave)  | 3. 분산 추적 로깅 (TraceId) |
|   +───────────────────────────+          +─────────────────────────────+ |
|                                                         │                |
|   +─────────────────────────────────────────────────────v──────────────+ |
|   | [ 5대 핵심 개념 연계 ]                                             | |
|   | 1. Aspect    : 부가기능 모듈 (Advice + Pointcut의 결합체)          | |
|   | 2. Joinpoint : Advice 적용 가능한 실행 지점 (스프링은 메서드 실행) | |
|   | 3. Pointcut  : 실제 Advice를 적용할 Joinpoint 선별 표현식          | |
|   | 4. Advice    : 실제 부가 기능 구현체 (Before, After, Around 등)    | |
|   | 5. Target    : 부가 기능을 적용받는 핵심 비즈니스 객체             | |
|   | 6. Weaving   : Pointcut 지점에 Advice를 실제 끼워 넣는 행위        | |
+-------------------------------------------------------------------------+
```

### (2) AOP 5대 핵심 구성요소 상세
| 구성요소 | 개념 및 역할 | Spring / AspectJ 표현 예시 |
|---|---|---|
| **Aspect (관점)** | 여러 객체에 걸친 횡단 관심사를 모듈화한 단위 | `@Aspect`, XML `<aop:aspect>` |
| **Joinpoint (결합점)** | 프로그램 실행 중 Advice가 적용될 수 있는 특정 위치 | 메서드 호출, 생성자 호출, 필드 접근 등 |
| **Pointcut (선별식)** | 수많은 Joinpoint 중 실제 Advice를 적용할 지점을 정의 | `execution(* com.service.*.*(..))`, `@annotation(...)` |
| **Advice (조언/동작)** | 타깃 객체의 Joinpoint에 삽입되어 실제로 동작하는 코드 | `@Before`, `@AfterReturning`, `@AfterThrowing`, `@Around` |
| **Weaving (직조)** | Pointcut으로 지정된 지점에 Advice를 결합하는 프로세스 | 컴파일 시점(CTW), 클래스로드 시점(LTW), 런타임(RTW) |

## 3. 3대 위빙(Weaving) 방식 및 Spring AOP 구현

### (1) 3대 위빙 방식 비교
| 비교 항목 | 컴파일 타임 위빙 (CTW) | 로드 타임 위빙 (LTW) | 런타임 프록시 위빙 (RTW) |
|---|---|---|---|
| **적용 시점** | 소스코드 컴파일 시점 | JVM 클래스 로더 로딩 시점 | 애플리케이션 런타임 실행 시점 |
| **수행 도구** | AspectJ 전용 컴파일러(ajc) | AspectJ ClassLoader Agent | Spring AOP 프레임워크 (JDK / CGLIB) |
| **바이트코드 수정**| 원본 .class 파일 직접 변조 | 메모리 로딩 시 바이트코드 조작 | 원본 바이트코드 불변 (프록시 객체 생성) |
| **적용 가능 범위**| 메서드, 필드, 생성자, static | 메서드, 필드, 생성자, static | **오직 스프링 빈의 public 메서드 실행** |
| **실행 성능** | 최고 속도 (프록시 오버헤드 무) | 최고 속도 (로딩 시 1회 오버헤드)| 상대적으로 호출 오버헤드 존재 (프록시 체인) |

### (2) Spring AOP 프록시 메커니즘 (JDK Dynamic Proxy vs CGLIB)
- **JDK Dynamic Proxy**: 타깃 클래스가 인터페이스를 구현하고 있을 때 사용하며, `java.lang.reflect.Proxy`를 통해 런타임 동적 인터페이스 프록시 생성.
- **CGLIB (Code Generation Library)**: 타깃 클래스가 인터페이스가 없거나 구체 클래스일 때 타깃 클래스를 상속받는 서브클래스 바이트코드를 동적으로 생성 (Spring Boot 2.0+ 기본값).

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **동일 클래스 내 메서드 호출 시 트랜잭션 롤백 누락**<br>(`@Transactional` 무시 현상) | Spring AOP 프록시를 거치지 않고 `this.method()`로 직접 호출(Self-invocation) | 별도 서비스 빈으로 책임 분리(SRP)하거나 AspectJ LTW/CTW 도입 | 트랜잭션 누락으로 인한 데이터 불일치 0건 차단 |
| **광범위한 포인트컷으로 인한 전사 API 지연**<br>(단순 유틸리티 함수까지 프록시 체인 동작) | `execution(* *..*(..))` 등 무차별 포인트컷으로 수만 개 메서드에 Advice 동작 | 커스텀 어노테이션 기반 포인트컷(`@annotation`)으로 타겟 정밀 지정 | 프록시 호출 오버헤드 90% 제거, TPS 복원 |
| **AOP 다중 적용 시 순서 꼬임으로 보안 인증 실패**<br>(인가 검증 전 트랜잭션 시작 등) | 다수의 Aspect가 동일 Joinpoint에 적용될 때 실행 우선순위 미지정 | `@Order` 어노테이션을 통해 Aspect 간 실행 순서(보안 $\rightarrow$ 트랜잭션 $\rightarrow$ 로깅) 명시 | AOP 실행 순서 충돌 100% 방지 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 무분별한 AOP 남발 (Black Magic)]    [현대: 통제된 횡단 관심사 아키텍처]
- 모든 비즈니스에 프록시 끼워 넣어 디버깅 불가 ──▶ - 인프라 관심사(보안, 트랜잭션, 관측성)로 한정
- Self-invocation 결함 인지 못하고 장애 발생 ──▶ - 프록시 한계 인식 및 구조적 클래스 분리 준수
- 비즈니스 룰을 Aspect에 은폐                  ──▶ - 도메인 이벤트(Domain Event) 발행으로 명시적 분리
```

- **AOP와 도메인 이벤트의 역할 분담**: AOP는 기술적·인프라적 횡단 관심사(트랜잭션, 분산 트레이싱 TraceId 주입 등)에 최적화되어 있음. 반면 "주문 완료 시 결제 알림 발송"과 같은 비즈니스 연쇄 행위는 AOP로 은폐하기보다 **스프링 도메인 이벤트(`ApplicationEventPublisher`)**를 통해 명시적이고 결합도 낮은 아키텍처로 풀어내는 것이 기술사의 고도화된 설계 식견임.
- **AspectJ 바이트코드 조작 도입 기준**: 단순 웹 요청 처리에는 Spring AOP의 CGLIB 프록시로 충분하지만, 내부 호출(Self-invocation) 방어가 필수적인 코어 금융 거래 엔진이나 메서드 레벨 이하의 초미세 프로파일링이 필요한 경우에는 AspectJ LTW(Load-Time Weaving)를 과감히 도입하는 기술적 의사결정 기준을 제시해야 함.
