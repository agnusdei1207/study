## Ⅰ. AOP(관점 지향 프로그래밍)의 개요

- **개념** : 애플리케이션 전반에 걸쳐 흩어져 있는 공통 관심사(횡단 관심사, Cross-Cutting Concerns: 트랜잭션, 로깅, 보안, 성능 측정 등)를 핵심 비즈니스 로직(핵심 관심사)으로부터 분리하여 별도의 모듈(Aspect)로 캡슐화하는 프로그래밍 패러다임.
- **배경 및 필요성** : 전통적인 객체지향 프로그래밍(OOP)만으로는 여러 클래스에 걸쳐 반복되는 횡단 관심사 코드 중복(Code Scattering)과 핵심 비즈니스 로직의 오염(Code Tangling)을 완전히 해결할 수 없는 한계 극복.
- **핵심 목표** : 높은 응집도 달성, 단일 책임 원칙(SRP) 준수, 유지보수성 및 코드 가독성 극대화.

## Ⅱ. AOP 핵심 개념 및 위빙(Weaving) 메커니즘

```text
   [ 핵심 비즈니스 로직 ]           [ 횡단 관심사: LoggingAspect ]
    - OrderService.createOrder()         - @Before: 메서드 시작 시간 기록
    - PaymentService.pay()               - @AfterReturning: 결과 로깅
    - UserService.login()                - @AfterThrowing: 예외 로깅
              │                                      │
              └──────────────────┬───────────────────┘
                                 │
                     [ 위빙 (Weaving) 수행 ]
               (컴파일 타임 / 클래스 로드 타임 / 런타임 프록시)
                                 │
                                 ▼
                     [ 최종 실행 애플리케이션 ]
             핵심 로직 실행 전후에 Aspect가 투명하게 자동 결합
```

- **조인 포인트 (Join Point)** : 메서드 호출, 객체 생성, 예외 발생 등 어드바이스가 적용될 수 있는 애플리케이션 실행 상의 모든 지점.
- **포인트컷 (Pointcut)** : 수많은 조인 포인트 중 실제로 어드바이스를 적용할 지점을 선별하는 표현식 (AspectJ 표현식 등).
- **어드바이스 (Advice)** : 관점(Aspect)이 실제로 수행해야 하는 구체적인 부가 기능 코드 (@Before, @After, @Around 등).
- **애스펙트 (Aspect)** : 포인트컷과 어드바이스를 하나로 묶은 횡단 관심사 모듈.
- **위빙 (Weaving)** : 포인트컷으로 지정된 핵심 비즈니스 코드에 어드바이스를 실제로 결합하는 과정.

## Ⅲ. AOP 3대 위빙 방식 비교

| 위빙 방식 | 동작 시점 | 특징 및 장단점 | 대표 도구 |
|---|---|---|---|
| 컴파일 타임 위빙 (CTW) | 소스코드 컴파일 시점 | 특별한 컴파일러 필요, 런타임 성능 오버헤드 전무 | AspectJ 컴파일러 (ajc) |
| 로드 타임 위빙 (LTW) | JVM 클래스 로더가 클래스를 로딩하는 시점 | 로딩 속도 미세 지연, JVM 에이전트 설정 필요, 유연함 | AspectJ LTW Agent |
| 런타임 프록시 위빙 (RTW) | 스프링 컨테이너 빈 생성 시점 (런타임) | 추가 컴파일러 불필요, 메서드 호출만 지원, 프록시 오버헤드 미세 발생 | Spring AOP (JDK Dynamic Proxy / CGLIB) |

## Ⅳ. AOP(Aspect Oriented Programming)의 주요 한계점 및 해결 방안

- **자기 호출(Self-Invocation) 시 프록시 우회 문제** :
  - **한계점** : 스프링 기본 다이내믹 프록시/CGLIB 환경에서 동일 클래스 내부의 메서드를 직접 호출할 경우 프록시를 거치지 않아 부가 기능(트랜잭션, 로깅 등)이 미적용되는 결함 발생.
  - **해결 방안** : 메서드 호출 구조를 별도 서비스 빈으로 분리(Refactoring), AopContext.currentProxy() 명시적 참조 또는 AspectJ LTW(Load-Time Weaving) 도입.
- **광범위한 포인트컷 지정으로 인한 성능 저하 및 디버깅 난이도 증가** :
  - **한계점** : 와일드카드를 남용한 포인트컷 설정 시 불필요한 메서드까지 인터셉트되어 런타임 오버헤드가 발생하고, 호출 스택 추적이 극도로 복잡해짐.
  - **해결 방안** : 명시적 커스텀 애노테이션 기반 포인트컷 설계(`@annotation`), APM(Scouter, Pinpoint) 분산 추적 태그 연동을 통한 애스펙트 실행 가시성 확보.
- **다중 애스펙트 간 실행 순서 충돌(Precedence Conflict)** :
  - **한계점** : 동일 조인포인트에 트랜잭션, 보안 인가, 캐시 애스펙트가 동시 적용될 때 실행 순서가 보장되지 않아 데이터 불일치 또는 비인가 접근 발생 위험.
  - **해결 방안** : `@Order` 애노테이션 또는 `Ordered` 인터페이스 구현을 통해 어드바이스 실행 체인의 우선순위를 명시적으로 강제하고 전사 거버넌스 룰 확립.

## Ⅴ. 엔터프라이즈 환경에서의 기술사적 제언

- **Spring AOP의 내부 메서드 호출(Self-Invocation) 한계 극복** : Spring AOP는 동적 프록시 기반이므로 동일 객체 내부에서 자기 자신의 @Transactional 메서드를 호출할 경우 프록시를 거치지 않아 트랜잭션이 누락되는 심각한 버그가 발생하므로, 구조적 서비스 분리 또는 AspectJ LTW 도입 필요.
- **무분별한 AOP 남발 방지와 아키텍처 거버넌스 수립** : 과도한 @Around 어드바이스 적용은 코드의 실행 흐름을 불투명하게 만들고 스택 트레이스 추적을 방해하므로, 시스템 전역 횡단 관심사(트랜잭션, 감사 로깅, 분산 추적)로 적용 범위를 엄격히 제한.
