## 답안 골격
```text
[프록시(Proxy) 디자인 패턴] ◀━━ 머리: Ⅶ 내 의견 (클라이언트 코드 변경 없는 대리 객체 투명성 확보와 AOP/캐싱 기반 횡단 관심사 분리)
 ┃
 ┣━ Ⅰ 개요 ───── 무거운 객체의 직접 생성 비용 및 원격 호출/접근 제어 복잡도 → 대리자(Proxy)를 통한 간접 접근 제어
 ┣━ Ⅱ 특징 ───── 구조(Structural) 패턴 · 동일 인터페이스 구현(투명성) · 객체 생성 지연(Lazy Loading) · 부가 기능 제어
 ┣━ Ⅲ 구조 ───── Subject(공통 인터페이스) / RealSubject(실체 객체) / Proxy(대리 객체, RealSubject 참조 보유)
 ┣━ Ⅳ 흐름 ───── 클라이언트 요청 → Proxy 수신 → 전처리(권한/캐시 검사) → RealSubject 위임 호출 → 후처리(로깅) → 응답 반환
 ┣━ Ⅴ 비교 ───── 프록시(접근 제어) vs 데코레이터(동적 책임 추가) vs 어댑터(인터페이스 변환)
 ┗━ Ⅵ 실무 ───── 수많은 클래스에 대한 정적 프록시 작성 코드 중복 / 동적 프록시(JDK Dynamic Proxy, CGLIB) 및 AOP 적용
```

## 한 줄 본질
- 클라이언트가 거대 리소스 객체나 원격 객체에 직접 결합하여 발생하는 초기화 지연 및 보안 검증 코드 오염 병목 → 실체 객체와 동일한 인터페이스를 구현한 대리자(Proxy)를 앞세워 지연 로딩, 접근 권한 제어, 캐싱을 투명하게 가로채는 GoF 구조 패턴 / 객체 간접화 오버헤드 수반

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  프록시(Proxy) 패턴 클래스 구조 및 호출 흐름             |
+-------------------------------------------------------------------------+
|                    <<interface>> Subject                                |
|                    + request(): void                                    |
|                           ^                                             |
|             +-------------+-------------+                               |
|             |                           |                               |
|      [ RealSubject ]                [ Proxy ]                           |
|      + request(): void              - realSubject: RealSubject          |
|                                     + request(): void ────────┐         |
|                                         │                     │         |
|                                         v (위임 호출)         │ (부가)  |
|                             realSubject.request()             │ 캐시    |
|                                                               │ 권한검사|
|                                                               │ 지연로딩|
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 가상 프록시(Virtual Proxy): 고용량 이미지 렌더링이나 복잡한 DB 연결처럼 생성 비용이 매우 큰 객체를 실제 사용 시점까지 생성을 미루는(지연 로딩, Lazy Initialization) 프록시
- 보호 프록시(Protection Proxy): 클라이언트의 자격증명(역할, 권한)을 검사하여 특정 인터페이스 메서드에 대한 호출 권한이 있는 경우에만 실체 객체로 요청을 전달하는 보안 통제 프록시

## 핵심 통찰
- 프록시 패턴의 핵심 미덕은 "클라이언트 코드를 단 한 줄도 수정하지 않고도(OCP 원칙 준수), 실체 객체 앞단에 트랜잭션, 보안, 캐싱 등의 공통 횡단 관심사(AOP)를 끼워 넣을 수 있다는 점"임
- 하지만 수작업으로 프록시 클래스를 일일이 만들면(정적 프록시) 메서드가 늘어날 때마다 중복 코드가 폭증하는 문제가 발생함
- 이를 극복하기 위해 런타임에 리플렉션으로 인터페이스를 동적 구현하는 Java `JDK Dynamic Proxy`나 바이트코드를 조작해 클래스를 상속받는 `CGLIB`이 현대 엔터프라이즈 프레임워크(Spring Boot)의 기반 기술로 자리 잡음

## 이웃 토픽과 구분
- 프록시 vs 데코레이터: 프록시 = 실체 객체에 대한 '접근을 제어'하는 것이 목적 / 데코레이터 = 객체의 인터페이스를 바꾸지 않고 '새로운 기능을 동적으로 확장/추가'하는 것이 목적

## 문제·원인·대책
- 적용 상황: 대용량 이미지 갤러리 및 엔터프라이즈 트랜잭션 제어
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 화면 목록 조회 시 수천 장의 원본 이미지를 즉시 로딩하여 메모리 고갈(OOM) 발생 | 객체 선언 시점에 고해상도 비트맵을 즉시 메모리에 적재(Eager Loading) | 가상 프록시(Virtual Proxy) 적용하여 스크롤 뷰포트 진입 시 로딩 | 초기 화면 렌더링 속도 10배 향상 및 힙 메모리 80% 절감 |
| 비즈니스 메서드마다 트랜잭션 시작/커밋/롤백 코드가 중복되어 유지보수 불가능 | 횡단 관심사 로직이 핵심 비즈니스 로직과 강하게 결합 | Spring `@Transactional` (CGLIB 동적 프록시 기반 AOP) 적용 | 비즈니스 코드 순수성 100% 확보 및 선언적 트랜잭션 관리 |

## 내 의견
- [동적 프록시의 내부 호출(Self-Invocation) 누락 버그 방지] 스프링 빈 내부에서 `this.methodB()`를 호출할 때 프록시를 거치지 않아 `@Transactional`이나 `@Async`가 무력화되는 실무 장애 빈발 경계 → 나라면: 내부 호출 시 프록시 우회 위험을 방지하기 위해 도메인 서비스를 작은 단위로 분리 주입하거나, 컴파일 타임에 바이트코드를 직접 위빙하는 AspectJ LTW(Load-Time Weaving) 방식을 대규모 고신뢰 시스템에 표준화
