## 답안 골격
```text
[보안 품질 속성] ◀━━ 머리: Ⅶ 내 의견 (ISO/IEC 25010 보안성 5대 부특성과 보안 시나리오 기반의 아키텍처적 전술(Tactics) 내재화)
 ┃
 ┣━ Ⅰ 개요 ───── 기능 구현 중심 개발로 인한 보안 결함의 운영기 전파 → 비기능 요구사항으로서의 체계적 보안 품질 모델 정립
 ┣━ Ⅱ 특징 ───── 비기능 아키텍처 속성 · 공격자 관점의 위협 모델링 · 측정 가능하고 검증 가능한 품질 시나리오 요구
 ┣━ Ⅲ 구조 ───── ISO/IEC 25010 5대 부특성(기밀성, 무결성, 부인방지, 책임추적성, 인증성) / 바스(Bass) 보안 전술(탐지/저항/복구)
 ┣━ Ⅳ 흐름 ───── 보안 품질 요구사항 도출(STRIDE) → 품질 시나리오 명세 → 아키텍처 전술 설계 → 정적/동적 검증(V&V)
 ┣━ Ⅴ 비교 ───── 보안 품질 속성(Security) vs 안전 품질 속성(Safety) vs 신뢰 품질 속성(Reliability)
 ┗━ Ⅵ 실무 ───── 보안 통제 적용 시 사용성 및 응답 지연 저하 트레이드오프 / ATAM 기반 아키텍처 절충 및 적응형 인증 도입
```

## 한 줄 본질
- 소프트웨어 출시 후 패치 방식으로 보안 결함을 땜질할 때 발생하는 막대한 유지보수 비용과 데이터 유출 사고 병목 → 아키텍처 설계 단계부터 ISO/IEC 25010 표준 보안 5대 부특성(기밀성, 무결성, 부인방지, 책임성, 인증성)을 정량적 시나리오로 명세하고 보안 전술(탐지/저항/복구)을 적용하는 소프트웨어 공학 기법 / 개발 복잡도 및 성능 오버헤드 수반

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|        ISO/IEC 25010 보안성(Security) 5대 세부 품질 속성 체계          |
+-------------------------------------------------------------------------+
| [1. 기밀성 (Confidentiality)]  - 인가된 사용자만 데이터 접근 (AES, TLS)  |
| [2. 무결성 (Integrity)]        - 비인가된 변조 및 손상 방지 (SHA-256, HMAC) |
| [3. 부인방지 (Non-repudiation)]- 행위 사실을 사후에 부인 불가 (전자서명)|
| [4. 책임추적성 (Accountability)]-모든 행위자의 활동 추적 (감사 로그, SIEM)|
| [5. 인증성 (Authenticity)]     - 대상의 신원 및 출처 진위 확인 (MFA, PKI)|
+-------------------------------------------------------------------------+
                                    │
                                    v [소프트웨어 아키텍처 보안 전술]
+-----------------------------------+-------------------------------------+
| [공격 탐지] 침입탐지(IDS), 무결성 검증, 메시지 다이제스트, 감사로그 검사 |
| [공격 저항] 사용자 인증, 권한 인가(RBAC), 데이터 암호화, 세션 제한     |
| [공격 대응/복구] 상태 복원(Rollback), 서비스 감사 보고, 격리(Quarantine)|
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 보안 품질 시나리오(Security Quality Scenario): `[자극원(공격자) → 자극(비인가 접근 시도) → 환경(정상 운영 중) → 대상(사용자 DB) → 응답(접근 차단 및 알림) → 응답 지표(1초 내 차단 및 100% 감사 기록)]`의 6개 요소로 보안 요구를 정량화한 명세
- 부인방지(Non-repudiation): 데이터의 송수신 또는 트랜잭션 수행 사실을 송신자나 수신자가 나중에 부인할 수 없도록 디지털 서명, 타임스탬프 등을 통해 증명하는 능력

## 핵심 통찰
- "보안을 강화하라"는 말은 구현 불가능한 슬로건에 불과하며, 반드시 "인가되지 않은 외부 침입자가 API를 변조하려 할 때 1초 내에 차단하고 감사 로그를 남긴다"와 같이 측정 가능한 품질 시나리오로 변환되어야 함
- 보안 품질 속성은 성능(Latency), 사용성(Usability)과 항상 치명적인 트레이드오프 관계에 놓이므로, 무조건적인 다중 암호화보다 위협 모델링(STRIDE)을 통한 비즈니스 중요도별 차등 적용이 필수적임
- 소프트웨어 제품 평가 국제 표준이 ISO/IEC 9126에서 25010(SQuaRE)으로 개정되면서 기능성 하위에 머물던 보안(Security)이 8대 독립 주기능 품질 특성으로 공식 승격됨

## 이웃 토픽과 구분
- 보안성(Security) vs 안전성(Safety): 보안성 = '외부의 고의적·악의적 공격'으로부터 정보와 시스템을 보호 / 안전성 = 결함이나 환경 이상으로 인한 '시스템 자체 오동작에 따른 인명/물리 피해'를 방지

## 문제·원인·대책
- 적용 상황: 마이데이터 기반 금융 자산 관리 플랫폼 아키텍처 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 관리자 계정 탈취로 인해 고객 금융 거래 내역이 외부로 무단 유출 | 단일 ID/PW 인증 및 내부망 DB 평문 저장, 기밀성/인증성 아키텍처 부재 | MFA 필수화, 컬럼 단위 AES-256 암호화 및 KMS 키 격리 보관 | 계정 탈취 시에도 데이터 복호화 불가 및 유출 원천 차단 |
| 고객이 송금 요청을 수행한 후 거래 사실을 허위로 부인하고 환불 요구 | 트랜잭션 로그에 타임스탬프와 전자서명이 누락되어 법적 증거력 상실 | PKI 기반 공인 전자서명 검증 및 불변(WORM) 감사 로그 체계 구축 | 법적 부인방지 100% 충족 및 금융 분쟁 승소 요건 확보 |

## 이렇게 출제된다
- 제136회 4교시 6번: "소프트웨어 품질 속성 중 보안 품질에 대하여 다음을 설명하시오." → 요구 포인트: ISO/IEC 25010 보안성 5대 부특성(기밀성, 무결성, 부인방지, 책임추적성, 인증성) + 아키텍처 보안 전술(탐지, 저항, 복구) + 보안 품질 시나리오 작성 사례

## 내 의견
- [보안 품질을 보안 장비(방화벽/WAF) 구매로 때우려는 외주 의존적 태도] 네트워크 경계 보안만 갖추면 소프트웨어는 어떻게 짜도 안전하다는 치명적 착각이 SQL Injection과 인증 우회 참사 유발 경계 → 나라면: 요구사항 도출 시점부터 '보안 사용자 스토리(Abuser Story)'를 작성하고, 개발 아키텍처에 최소 권한 원칙(PoLP)과 Zero Trust 세분화 격리(Micro-segmentation)를 비기능 요구 품질 게이트로 강제 반영
