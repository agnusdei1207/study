## 답안 골격 (10점 / 25점)

```text
[캡슐화(Encapsulation)] ◀━━ 머리: Ⅶ 공학적 제언 (빈약한 도메인 모델 탈피와 비즈니스 불변식(Invariants) 보호 메커니즘)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터와 처리 로직의 분리로 인한 무결성 파괴 극복, 연관 속성과 행위를 단일 캡슐로 결합
 ┣━ Ⅱ 2대 핵심 목적 ─ 응집도(Cohesion) 극대화 · 객체 스스로의 비즈니스 불변식(Invariants) 강제 검증
 ┣━ Ⅲ 구현 메커니즘 ─ 클래스(Class) 정의 · 접근 제어자(`private`) · 공개 메시지 인터페이스(Public API)
 ┣━ Ⅳ 3자 대조 ─ 캡슐화(데이터+행위 번들링, 수단) vs 정보은닉(세부 구현 은폐, 목적) vs 추상화(핵심 특징 추출)
 ┣━ Ⅴ 도메인 모델 대조 ─ 빈약한 도메인 모델(Anemic, Getter/Setter 절차지향) vs 풍부한 도메인 모델(Rich, 객체지향)
 ┣━ Ⅵ 실무 문제 ─ Setter 남발로 인한 데이터 오염 / 동일 검증 로직의 서비스 레이어 중복 분열
 ┗━ Ⅶ 결론 ───── Tell, Don't Ask 원칙 및 비즈니스 행위 중심 메서드(`cancelOrder()`) 표준화
```

- **필수 키워드**: 캡슐화(Encapsulation), 데이터와 행위의 결합, 도메인 불변식(Invariants), 접근 제어자, 정보은닉과의 차이, 빈약한 도메인 모델(Anemic Domain Model), 풍부한 도메인 모델(Rich Domain Model), Tell Don't Ask
  - **10점형**: 캡슐화 정의 및 클래스 캡슐 구조도 → 캡슐화 vs 정보은닉 vs 추상화 3자 비교표.
  - **25점형**: Ⅰ~Ⅶ 전체 구조 전개 + 실무 빈약한 도메인 모델(Getter/Setter 난사) 안티패턴 코드 리팩토링 사례 + 도메인 불변식 보호 및 DDD 엔티티 설계와의 연계 심층 제시.

## 본론: 개념 및 핵심 메커니즘

### 1. 캡슐화의 공학적 본질

- **개념**: 객체지향 프로그래밍의 가장 기본적 원리로, **서로 연관된 데이터(상태)와 그 데이터를 조작하는 메서드(행위)를 하나의 단위(Class)로 묶고, 객체 내부의 상세 구현을 보호하는 기법**.
- **핵심 가치**:
  1. **높은 응집도(High Cohesion)**: 데이터와 데이터 조작 로직이 물리적으로 한곳에 존재.
  2. **상태 불변식(Invariants) 보호**: 외부에서 유효하지 않은 데이터(예: 음수 나이, 마이너스 계좌 잔액)를 주입할 수 없도록 객체 스스로 방어.

### 2. 캡슐화 vs 정보은닉 vs 추상화 3자 비교

| 비교 항목 | 캡슐화 (Encapsulation) | 정보은닉 (Information Hiding) | 추상화 (Abstraction) |
|---|---|---|---|
| **개념적 본질** | 데이터와 행위를 하나의 껍질(Class)로 묶는 것 | 변경될 가능성이 높은 세부 구현을 감추는 것 | 복잡한 현실에서 핵심적 특징만을 추출하는 것 |
| **성격 및 역할** | 객체지향의 **패키징 수단(Packaging)** | 결합도를 낮추기 위한 **설계 목적이자 결과** | 복잡성을 제어하기 위한 **인지적 모델링 기법** |
| **주요 구현체** | 클래스(Class), 구조체 | 접근 제어자(`private`), 인터페이스 | 인터페이스, 추상 클래스 |
| **상호 관계** | 캡슐화는 정보은닉을 달성하기 위한 물리적 기반이 됨 |

### 3. 실무 안티패턴: 빈약한 도메인 모델 (Anemic Domain Model)

- **문제점**: 엔티티 클래스에는 필드와 `get/set` 메서드만 존재하고, 실제 비즈니스 검증과 계산 로직은 수천 줄짜리 `Service` 클래스에서 절차지향 스크립트 형태로 수행되는 구조.
- **해법 (풍부한 도메인 모델, Rich Domain Model)**:
  - `setOrderStatus("CANCEL")` 대신 `order.cancel()` 비즈니스 행위 메서드를 엔티티 내부에 선언.
  - 객체가 스스로 배송 상태 전이 가능 여부를 검증하고 자신의 상태를 변경하도록 책임 위임 (Tell, Don't Ask).

## 실무 장애 시나리오 및 공학적 대안

### 1. 현장 장애 사례

1. **Setter 난사로 인한 결제 데이터 무결성 붕괴**:
   - `Order` 객체의 모든 필드에 `@Setter`가 열려 있어, 여러 개발자가 컨트롤러와 비동기 워커에서 임의로 `order.setPaidAmount(0)`을 호출하여 결제 승인 금액이 0원으로 오염.
2. **동일 비즈니스 검증 로직의 다중 파편화**:
   - 회원 가입 시 비밀번호 유효성 검사 로직이 웹 컨트롤러, 앱 API 서비스, 배치 작업 등 5군데에 제각각 복사되어, 정책 변경 시 누락 발생.

### 2. 문제 원인 및 공학적 해결책

| 장애 상황 | 근본 원인 | 공학적 대책 (대안 기술) | 개선 효과 |
|---|---|---|---|
| **데이터 무단 오염** | 무분별한 Public Setter 노출 | **Setter 전면 삭제** + 비즈니스 행위 메서드(`pay()`, `refund()`) 캡슐화 | 도메인 불변식 100% 강제 및 오염 원천 차단 |
| **로직 파편화 및 중복** | 데이터와 행위의 분리 (빈약한 도메인) | 데이터가 있는 객체 내부로 검증 로직 이동 (**풍부한 도메인 모델**) | 비즈니스 변경 시 단일 클래스 수정으로 격리 |
| **외부 무단 접근** | 접근 제어자 미준수 | 모든 인스턴스 변수에 **`private` 강제 린트 규칙** 적용 | 객체 내부 상태 완벽 보호 |

## 결론: 기술사 답안 차별화 포인트

1. **데이터 묶기를 넘어선 '불변식(Invariants) 수호자'로서의 캡슐화**: 캡슐화를 단순히 변수와 함수를 클래스에 모아두는 문법적 수준으로 서술하지 말고, **"객체가 태어나서 죽을 때까지 유효한 상태(도메인 불변식)만을 유지하도록 강제하는 능동적 방어 메커니즘"**임을 명확히 서술할 것.
2. **빈약한 도메인 모델(Anemic Domain Model) 비판**: 엔티티에 롬복 `@Data`를 붙여 무지성 Setter를 제공하는 현대 SI 프로젝트의 관행을 꼬집고, **풍부한 도메인 모델(Rich Domain Model)과 Tell-Don't-Ask 원칙**을 회복하는 것이 진정한 객체지향 캡슐화의 실천임을 결론으로 제시할 것.
