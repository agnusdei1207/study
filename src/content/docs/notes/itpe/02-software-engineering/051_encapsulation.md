## 30초 인출

- 본질: **캡슐화(Encapsulation)** 는 객체의 상태와 그 상태를 다루는 동작을 한 단위로 묶고 외부 접근을 정해진 경계로 제한하는 객체지향 설계 원리
- 메커니즘: 내부 상태를 비공개로 두고 → 의도를 나타내는 메서드를 공개 → 메서드에서 유효성·상태 전이 규칙을 적용
- 핵심: 모든 필드에 getter·setter를 만드는 것만으로 불변식이 보호되지는 않음

<details>
<summary>핵심 용어</summary>

- **캡슐화(Encapsulation)** : 데이터와 동작을 객체 경계에 모아 외부 상호작용을 인터페이스로 통제하는 원리
- **정보 은닉(Information Hiding)** : 변경 가능성이 큰 내부 설계 결정을 외부 모듈에서 감추는 원리. 캡슐화는 이를 구현하는 수단 중 하나
- **불변식(Invariant)** : 객체가 유효한 상태에서 항상 만족해야 하는 조건
- **접근 제어자(Access Modifier)** : Java의 `private`, `protected`, `public`처럼 멤버의 접근 범위를 정하는 언어 장치

</details>

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **캡슐화** 는 객체의 상태와 동작을 한 단위에 묶고 외부 접근을 정해진 경계로 제한하는 객체지향 설계 원리 |
| 목적 | 객체의 유효 상태를 보호하고 내부 구현 변경이 호출자에게 미치는 영향을 줄임 |

### Ⅱ. 작동 관계

```text
호출자 → 공개된 업무 동작 메서드
              ↓ 입력·상태 검증
          비공개 필드 변경
              ↓
          불변식 유지
```

| 수단 | 역할 |
|---|---|
| 비공개 상태 | 호출자의 임의 변경을 제한 |
| 의도 중심 메서드 | 허용된 상태 전이와 검증을 한곳에 구현 |
| 공개 계약 | 호출자가 내부 자료구조 대신 객체의 역할에 의존 |

제언: setter의 수보다 유효 상태를 유지하는 공개 동작과 변경 영향 범위를 검토.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **캡슐화** 는 객체의 상태와 동작을 한 단위에 묶고 외부 접근을 정해진 경계로 제한하는 객체지향 설계 원리 |
| 목적 | 객체의 유효 상태를 보호하고 내부 구현 변경이 호출자에게 미치는 영향을 줄임 |

## Ⅱ. 캡슐화의 구조와 메커니즘

```text
외부 객체
   │ 공개 계약: withdraw(amount)
   ▼
계좌 객체
   ├─ 입력 확인: amount > 0
   ├─ 상태 확인: 잔액 ≥ amount
   └─ 비공개 잔액 변경

외부 객체의 balance 직접 수정은 제한
```

| 구성 | 역할 | 설계 기준 |
|---|---|---|
| 상태와 동작의 결합 | 상태를 소유한 객체가 변경 규칙도 관리 | 한 경계 안에서 상태 변경 |
| 접근 제한 | 내부 표현의 직접 의존을 줄임 | 불필요한 필드·수정 메서드 비공개 |
| 공개 계약 | 호출자의 사용 방식과 오류 조건을 명시 | 유효하지 않은 요청의 처리 규칙 명시 |

## Ⅲ. 정보 은닉과의 관계

| 구분 | 초점 | 예 |
|---|---|---|
| 캡슐화 | 상태·동작을 객체 경계로 모아 접근을 통제 | 잔액을 비공개로 두고 출금 메서드를 제공 |
| 정보 은닉 | 변경될 가능성이 큰 설계 결정을 외부에 노출하지 않음 | 저장 방식이나 잔액 계산 정책을 호출자가 알 필요 없게 설계 |

캡슐화된 클래스라도 내부 표현을 그대로 반환하거나 무제한 setter를 열어 두면 정보 은닉과 불변식 보호 효과가 약해질 수 있음.

## Ⅳ. 적용과 검증

| 위험 | 대응 | 검증 증거 |
|---|---|---|
| 직접 필드 수정으로 잘못된 상태 생성 | 상태를 비공개로 두고 업무 의미가 있는 변경 동작 제공 | 음수 금액·잔액 초과 등 경계 시험 |
| 가변 객체 참조 노출 | 필요하면 방어적 복사·읽기 전용 표현 사용 | 반환 객체 변경 뒤 원본 상태 확인 |
| 내부 표현 변경이 호출자에 전파 | 외부 계약을 안정화하고 구현 세부를 감춤 | 저장 구조 변경 뒤 호출자 호환성 시험 |
| 과도한 캡슐화로 불필요한 간접 계층 증가 | 실제 불변식·변경 이유에 맞는 경계 설정 | 책임과 변경 이력 검토 |

## Ⅴ. 기술사적 제언

| 한계 | 해결 방안 |
|---|---|
| 접근 제어자만 적용하고 상태 전이 규칙을 여러 호출자에 분산하면 객체의 유효 상태를 지키기 어려움 | 객체가 소유한 불변식을 먼저 정의하고, 그 불변식을 유지하는 공개 동작만 제공하며 경계·오류 사례를 시험에 연결 |
