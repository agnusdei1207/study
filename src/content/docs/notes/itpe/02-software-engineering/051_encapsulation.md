## 연관 키워드

- 캡슐화(Encapsulation), 객체지향 프로그래밍(OOP, Object-Oriented Programming), 정보 은닉(Data Hiding)
- 응집도(Cohesion), 결합도(Coupling), Tell Don't Ask, 디미터 법칙(Law of Demeter), 빈약한 도메인 모델(Anemic Domain Model)

## Ⅰ. 캡슐화의 개요

- 핵심 요약 : 데이터와 행위를 클래스로 묶고 내부 구현을 감춰 공개 인터페이스로만 상호작용하게 하는 객체지향 원리.
- 개념 : 연관된 데이터(속성, 상태)와 그 데이터를 처리하는 행위(메서드)를 하나의 클래스로 묶고, 내부 구현을 외부에서 감춰 정의된 공개 인터페이스를 통해서만 접근하도록 하는 **캡슐화**(Encapsulation) 원리다. 객체지향 프로그래밍(OOP, Object-Oriented Programming)의 기본 원리 중 하나다.
- 배경 및 필요성 : 데이터와 처리 함수가 분리된 절차지향 프로그래밍(POP, Procedure-Oriented Programming)에서는 전역 데이터를 여러 모듈이 무분별하게 변경해 상태 무결성이 깨지는 문제가 생겼다. 캡슐화는 이 상태 변경의 통로를 하나로 좁혀 문제를 구조적으로 줄인다.
- 주요 목적 : 객체 내부 상태를 보호하고, 변경이 외부로 번지지 않도록 **응집도**(Cohesion)를 높이며 **결합도**(Coupling)를 낮추는 것.

## Ⅱ. 캡슐화의 특징 및 장점

- 핵심 요약 : 상태 은닉과 비즈니스 규칙의 내장이 데이터 무결성과 변경 용이성이라는 장점으로 이어지는 원리.

1. 상태 은닉과 불변식 보호 : 필드를 private으로 감추고 비즈니스 규칙이 내장된 메서드로만 수정하게 함 → 잔액에 음수가 들어가는 등 무효 상태 유입 차단.
2. 공개 인터페이스 경계 : 공개 메서드와 은닉된 내부 필드를 명확히 나눔 → 외부는 계약(인터페이스)만 알고 구현에 의존하지 않음.
3. Tell, Don't Ask 원칙 : 객체의 상태를 외부에서 조회해 판단하지 않고 목적이 담긴 메시지를 보내 객체가 스스로 처리하게 함 → 규칙이 한 곳에 모여 중복 감소.
4. 변경 파급 최소화 : 내부 구현이 바뀌어도 공개 인터페이스가 유지되면 호출자는 수정이 필요 없음 → 유지보수 비용 절감과 재사용성 향상.

## Ⅲ. 캡슐화의 구조 (흐름)

- 핵심 요약 : 외부 클라이언트와 객체 사이에 정보 은닉 경계를 두고, 메시지를 통해서만 상태가 바뀌는 구조.

```text
[ 외부 클라이언트 ]
        ↓ 공개 인터페이스 메시지만 전달
[ 캡슐화된 객체 : Account ]
  공개: deposit(), withdraw()
  공개: getBalance()
        ↓ 정보 은닉 경계 안쪽
  은닉: balance, validateAccount()
```

```text
[ Tell, Don't Ask 메시지 흐름 ]

[ 외부 객체 ] ── withdraw() ──> [ Account ]
                                    ↓
                               내부 검증 수행
                                    ↓
                               잔액 갱신
                                    ↓
[ 외부 객체 ] <── 처리 결과 ── [ Account ]
```

## Ⅳ. 절차지향과 객체지향 캡슐화의 비교

- 핵심 요약 : 데이터와 함수가 분리된 POP의 전역 접근 구조 대비, 데이터와 행위를 묶고 접근을 통제하는 OOP 구조.

| 비교 항목 | 절차지향 프로그래밍(POP) | 캡슐화 기반 객체지향(OOP) |
| --- | --- | --- |
| 데이터와 함수의 관계 | 데이터 구조체와 처리 함수가 분리 | 데이터와 해당 데이터를 다루는 메서드가 한 클래스에 결합 |
| 데이터 접근 권한 | 전역 또는 공용 데이터를 누구나 변경 가능 | private 접근 제어로 외부의 무단 상태 변경 차단 |
| 변경 영향도 | 데이터 필드 변경이 여러 함수 수정으로 파급 | 내부 상태가 바뀌어도 공개 인터페이스가 같으면 외부 무영향 |
| 비즈니스 규칙 위치 | 호출하는 여러 모듈에 중복 산재 | 데이터를 소유한 객체 내부에 응집 |
| 설계 관점 | 처리 흐름 중심의 기능 분해 | 책임을 가진 객체 간 협력 중심 |

## Ⅴ. 캡슐화의 한계와 방안

- 핵심 요약 : 게터·세터 남용, 상속 노출, 프레임워크와의 불일치를 행위 중심 설계, 합성 우선, 생성 제어로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 게터·세터 남용 | 모든 필드에 Getter·Setter를 열면 외부가 내부 상태를 꺼내 로직을 처리해 캡슐화가 무력화 | Tell, Don't Ask 원칙을 지키고 상태 보유 객체 내부에서 로직 수행, 도메인 객체에 무분별한 Setter 금지 | 공개 Setter 개수 |
| 상속을 통한 내부 노출 | 상속하면 부모의 protected 필드와 메서드가 자식에 노출되어 부모 수정 시 자식이 연쇄 파손 | 상속 대신 객체 합성(Composition) 활용, 확장을 막을 핵심 클래스는 final로 선언 | 상속 깊이, 부모 변경에 따른 결함 건수 |
| 프레임워크와의 불일치 | ORM(Object-Relational Mapping)과 JPA(Java Persistence API), Jackson 등이 기본 생성자와 리플렉션 접근을 요구해 불변식 검증이 우회될 위험 | 도메인 엔티티와 전송용 DTO(Data Transfer Object) 분리, 정적 팩토리 메서드(Static Factory Method)로만 생성 강제 | 불변식 위반 검출 건수 |

## Ⅵ. 고품질 도메인 모델 설계를 위한 기술사적 제언

- 핵심 요약 : 빈약한 도메인 모델 안티패턴을 걷어내고 디미터 법칙을 지키는 설계 습관을 팀 표준으로 정착.

1. 행위 중심 도메인 모델 : 설계 검토 단계에서 Setter 없이 비즈니스 의미를 가진 메서드만 노출되었는지 확인하고, 데이터만 담는 클래스가 늘지 않도록 코드 리뷰 기준에 반영한다.
2. 최소 지식 설계 : 메서드 체이닝(a.getB().getC()...)을 피하고 바로 인접한 협력자에게만 요청을 위임하도록 디미터 법칙을 적용한다.
3. 생성 규칙의 일원화 : 객체 생성은 정적 팩토리 메서드와 생성자 검증을 거치도록 아키텍처 가이드에 명시해 불변식이 생성 시점부터 지켜지게 한다.

## Ⅶ. 결론

- 핵심 요약 : 캡슐화는 상태와 책임을 한곳에 묶어 변경에 강한 객체 설계를 가능하게 하는 원리.
- 시사점 : 캡슐화는 접근 통제 문법만으로 완성되지 않으며, 행위 중심 설계와 합성 중심 상속 관리가 함께 있어야 실질적으로 작동한다.
