## 연관 키워드
- 캡슐화, 상태 은닉, 불변조건, Tell Don’t Ask, 도메인 모델

### Ⅰ. 캡슐화의 개요

- 핵심 요약 : 캡슐화는 객체의 상태와 내부 구현을 숨기고 공개된 연산을 통해 상태를 통제하는 객체지향 원칙.
- 개념 : 객체의 상태와 내부 구현을 숨기고 공개된 연산을 통해 상태를 통제하는 객체지향 원칙(**캡슐화**, Encapsulation).
- 배경 및 필요성 : 외부 코드가 객체 내부 상태를 직접 바꾸면 불변조건 위반과 변경 파급이 증가.
- 주요 목적 : 객체 불변조건 보호와 구현 변경의 영향 범위 축소.

### Ⅱ. 캡슐화의 특징 및 장점

- 핵심 요약 : 상태 은닉·유효한 연산 공개·객체가 책임지는 행위(Tell, Don’t Ask).

1. 상태 은닉 : 내부 상태를 private로 제한하고 공개 연산만 노출 → 불변조건 보호.
2. 유효한 연산 공개 : 의미 있는 명령·쿼리만 제공 → 객체가 자신의 상태와 행위를 책임짐.
3. Tell, Don’t Ask : 상태를 묻지 않고 명령을 수행 → 객체 내부에 결정 로직 집중.

### Ⅲ. 캡슐화의 구조 (흐름)

- 핵심 요약 : 불변조건 정의 → 상태를 private로 제한 → 의미 있는 연산 제공 → 입력 검증·상태전이 통제 → 객체 경계 시험.

```text
불변조건 정의
  ↓
상태를 private로 제한
  ↓
의미 있는 연산 제공
  ↓
입력 검증·상태전이 통제
  ↓
객체 경계 시험
```

```text
상태 private → 명령 메서드 → 불변조건 검증 → 유효 상태만 노출
```

### Ⅳ. 자료구조체 중심과 캡슐화 비교

- 핵심 요약 : 자료구조체 중심은 외부가 필드를 읽고 변경, 캡슐화는 객체가 상태와 규칙을 함께 소유하고 명령 수행.

| 비교 축 | 자료구조체 중심 | 캡슐화 |
|---|---|---|
| 행위·상태책임 | 외부가 필드를 읽고 변경 | 객체가 상태와 규칙을 함께 소유하고 명령 수행 |
| 상태 접근 | 필드 직접 읽기·쓰기 | 공개 연산을 통한 제어 |

### Ⅴ. 캡슐화의 한계와 방안

- 핵심 요약 : 과도한 게터·세터·빈약한 도메인 모델·프레임워크 제약을 업무 행위 메서드와 DTO 경계로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 과도한 게터·세터 | 객체 상태를 무제한 노출 | 업무 행위 메서드로 불변조건 보호 | 외부 상태변경 지점 |
| 빈약한 도메인 모델 | 규칙이 서비스 계층에 분산 | 도메인 객체에 응집된 행위 배치 | 규칙 중복 |
| 프레임워크 제약 | 직렬화·ORM·프록시가 접근 요구 | 명시적 DTO 경계·검증 생성자 사용 | 도메인 결합도 |

### Ⅵ. 캡슐화에 대한 제언

- 핵심 요약 : 도메인 설계자는 상태 변경을 업무 명령으로 표현하고 외부 시스템용 DTO와 도메인 객체 경계를 분리.

1. 도메인 설계자는 상태 변경을 업무 명령으로 표현하고 외부 시스템용 DTO와 도메인 객체 경계를 분리.
2. 외부 상태변경 지점·규칙 중복·도메인 결합도를 정기 측정하고 편차에 대한 원인분석·개선결과를 기록.

### Ⅶ. 결론

- 핵심 요약 : 캡슐화는 객체의 상태와 내부 구현을 숨기고 공개된 연산을 통해 상태를 통제하는 객체지향 원칙.
- 시사점 : 캡슐화는 단순한 접근제한자가 아니라 객체가 자신의 유효한 상태와 행위를 책임지는 설계 원칙.
