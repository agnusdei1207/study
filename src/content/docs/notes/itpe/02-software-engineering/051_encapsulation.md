## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 객체지향 설계 → **캡슐화(Encapsulation)**

## 30초 인출

- 본질: 객체의 상태(데이터)와 그 상태를 변경하는 행위(메서드)를 하나의 논리적 클래스 경계로 묶고, 접근 제어자를 통해 외부로부터의 무분별한 직접 접근을 제한하는 객체지향 핵심 설계 원리
- 메커니즘: 데이터 필드 은닉(`private`) + 비즈니스 유효성 검증을 포함한 공개 인터페이스(`public`) 노출 + 불변식(Invariant)의 강제 보장
- 통찰: 기계적인 Getter/Setter 남발은 캡슐화를 형해화하여 빈약한 도메인 모델을 초래하므로 Tell, Don't Ask 원칙에 입각한 행위 중심 캡슐화 설계 적용 필수

<details>
<summary>핵심 용어</summary>

- **Encapsulation(캡슐화)** : 연관된 데이터와 연산을 하나의 단위로 패키징하고 외부의 부적절한 간섭으로부터 내부 상태를 보호하는 객체지향 메커니즘
- **Information Hiding(정보은닉)** : 시스템 분할 시 변경 가능성이 높은 세부 구현 결정을 비밀로 감추는 설계 철학 (캡슐화는 이를 달성하는 주요 수단)
- **Invariant(불변식)** : 객체의 전 생애주기 동안 항상 참으로 유지되어야 하는 비즈니스 규칙 및 무결성 조건
- **Tell, Don't Ask (묻지 말고 시켜라)** : 객체의 상태를 물어봐서 외부에서 판단하지 말고, 객체 스스로 판단하고 동작하도록 명령을 내리는 객체지향 설계 원칙
- **Defensive Copy(방어적 복사)** : 외부로 가변 객체(Date, List 등)를 반환하거나 전달받을 때 원본의 참조를 차단하기 위해 복사본을 생성하는 기법

</details>

## 2~4교시 25점 답안

## Ⅰ. 캡슐화의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 연관된 데이터(속성)와 이를 다루는 연산(메서드)을 단일 클래스로 묶고, 접근 제어자(`private`)를 통해 외부의 직접적인 상태 조작을 통제하여 객체의 무결성을 보장하는 객체지향 핵심 원리 |
| 목적 | 객체의 유효한 상태(불변식) 보존, 데이터와 로직의 높은 응집도(High Cohesion) 확보 및 내부 구현 변경 시 외부 파급 효과(Ripple Effect) 차단 |

## Ⅱ. 캡슐화의 핵심 특징

| 특징 | 의미 |
|---|---|
| 상태와 행위의 일체화 | 데이터 따로 로직 따로 분리되는 절차적 구조를 탈피하여 데이터와 조작 함수를 한곳에 응집 |
| 경계 기반 접근 통제 | 접근 제어자(`private`, `protected`, `public`)를 통해 노출할 인터페이스와 감출 내부 상태를 엄격 구분 |
| 비즈니스 불변식 강제 | 생성자 및 비즈니스 메서드 내부에서 유효성 검증(Validation)을 통과한 유효 상태만 허용 |
| 모듈 결합도 완화 | 호출자는 객체 내부의 자료구조가 배열인지 연결리스트인지 알 필요 없이 공개 메서드만 호출 |

## Ⅲ. 캡슐화 구조 및 동작 메커니즘

### 캡슐화 경계 보호 및 불변식(Invariant) 유지 흐름

```text
[외부 클라이언트 객체]
       │
       ├─ X 직접 접근 시도: account.balance -= 5000 (컴파일 에러: private 필드)
       │
       ▼ 올바른 공개 메서드 호출: account.withdraw(5000)
┌────────────────────────────────────────────────────────────────────────┐
│                   [BankAccount 캡슐화 클래스 경계]                     │
│                                                                        │
│   // 1. 은닉된 내부 상태 (Private State)                               │
│   private long balance;                                                │
│                                                                        │
│   // 2. 비즈니스 불변식 검증을 내재화한 공개 메서드                    │
│   public void withdraw(long amount) {                                  │
│       // [가드 조건 1]: 출금액 음수 불가 검증                          │
│       if (amount <= 0) throw new IllegalArgumentException();           │
│                                                                        │
│       // [가드 조건 2]: 잔액 부족 불변식 검증 (balance >= amount)      │
│       if (this.balance < amount) throw new InsufficientBalanceException(); │
│                                                                        │
│       // [상태 전이]: 안전하게 검증된 상태 변경                        │
│       this.balance -= amount;                                          │
│   }                                                                    │
│                                                                        │
│   ★ 항상 잔액이 0원 이상으로 유지되는 불변식(Invariant) 100% 보장       │
└────────────────────────────────────────────────────────────────────────┘
```

### 캡슐화 3대 핵심 구성요소

| 구성요소 | 핵심 메커니즘 | 실무 역할 |
|---|---|---|
| **비공개 데이터 필드** | `private` 접근자 선언 | 외부로부터 직접적인 데이터 오염, 잘못된 상태 할당 원천 차단 |
| **공개 인터페이스** | 의미 있는 비즈니스 동사 메서드 | 클라이언트에게 제공하는 공식 계약이자 최소한의 통신 창구 |
| **상태 검증 가드(Guard)** | 사전 조건(Pre-condition) 검사 | 객체 생성 및 상태 변경 시 비즈니스 규칙과 제약조건 강제 집행 |

## Ⅳ. 캡슐화(Encapsulation) vs 정보은닉(Information Hiding)

### 두 개념 간의 본질적 비교 분석

| 비교 항목 | 캡슐화 (Encapsulation) | 정보은닉 (Information Hiding) |
|---|---|---|
| **개념적 위상** | **구현 메커니즘 (How to do)** | **아키텍처 설계 철학 및 원리 (Why to do)** |
| **핵심 활동** | 데이터와 메서드를 클래스 단위로 묶고 경계 설정 | 자주 변경되는 내부 설계 결정(자료구조, 알고리즘)을 은폐 |
| **주요 수단** | 클래스(Class), 접근 제어자(`private`), 패키지 | 추상화, 인터페이스 분리 원칙, 모듈 분할 가이드 |
| **초점 영역** | 객체 내부의 데이터 무결성과 응집도 확보 | 모듈 간 의존성을 낮추어 변경의 파급 효과 차단 |
| **상호 관계** | 캡슐화는 정보은닉을 코드로 실현하기 위한 핵심 구현 장치 | 정보은닉이 배제된 단순 캡슐화는 껍데기 포장에 불과 |

### 안티패턴(Anemic Domain) vs 올바른 캡슐화(Rich Domain)

| 구분 | 빈약한 도메인 모델 (Anemic Model, 캡슐화 파괴) | 제언: 풍부한 도메인 모델 (Rich Domain, 올바른 캡슐화) |
|---|---|---|
| 코드 형태 | 모든 필드에 `getXXX()`, `setXXX()` 무차별 제공 | 의미 있는 비즈니스 행위 메서드 제공 (`cancelOrder()`) |
| 상태 변경 주체 | 서비스 계층에서 데이터를 꺼내어 외부에서 변경 | 데이터가 있는 객체 스스로 비즈니스 로직을 판단 및 변경 |
| 무결성 보장 | 여러 서비스에서 setter를 호출하여 불변식 파괴 위험 | 객체 내부에서 항상 유효한 상태만 존재하도록 자체 방어 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 모든 필드에 Getter/Setter를 무분별하게 생성하여 객체의 내부 상태가 외부에 완전 노출 | 무조건적인 Setter 생성을 금지하고 '묻지 말고 시켜라(Tell, Don't Ask)' 원칙 적용 |
| 컬렉션(List, Map)이나 가변 객체 반환 시 외부에서 직접 요소를 추가/삭제하여 캡슐화 훼손 | 불변 컬렉션(`Collections.unmodifiableList`) 또는 방어적 복사(Defensive Copy) 적용 |
| 지나친 캡슐화로 인해 단순 데이터 전달용 DTO까지 과도한 래핑 계층이 생겨 성능 및 복잡도 증가 | 상태 변경이 없는 순수 데이터 전송 객체는 Java Record 또는 Kotlin Data Class로 분리 |

## Ⅵ. 제언

도메인 주도 설계(DDD) 애그리게잇(Aggregate) 기반 불변식 경계 설정 및 불변 객체(Value Object) 표준화

### DDD 애그리게잇 기반 캡슐화 파이프라인

```text
[클라이언트 트랜잭션 요청]
       ↓
[애그리게잇 루트 (Aggregate Root) 진입]
  ├─ 외부 객체는 오직 Root 엔티티만 참조 가능 (내부 멤버 직접 참조 불가)
  ├─ Root 메서드를 통해서만 내부 하위 엔티티의 상태 변경 수행
  └─ 비즈니스 불변식(Invariant) 트랜잭션 단위 일괄 검증
       ↓
[Value Object(값 객체)의 완전 불변화 (Immutability)]
  ├─ 생성자에서 유효성 검증 완료 후 모든 필드 final화
  └─ 상태 변경 필요 시 새로운 값 객체 인스턴스 반환
       ↓
[도메인 무결성 100% 보장 완료]
```

### 캡슐화 설계 의사결정 체계

```text
클래스 멤버 필드 설계
       ↓
[해당 필드를 외부에 public으로 직접 열어야 하는가?]
       ├─ 예 ──→ 상수(static final)를 제외하고는 원칙적 금지
       └─ 아니오 ─→ [private 선언]
                         ↓
           [외부에서 해당 데이터를 변경해야 하는가?]
                         ├─ 아니오 ─→ 단순 조회만 제공하거나 불변 객체 유지
                         └─ 예 ───→ 단순 setter가 아닌 [의미 있는 비즈니스 메서드]로 상태 전이 캡슐화
```

### 선택 근거: Getter/Setter 중심 설계와 행위 기반 캡슐화 비교

| 구분 | 관행적 Getter/Setter 중심 모델 | 제언: 행위 기반 풍부한 캡슐화 모델 |
|---|---|---|
| 객체 성격 | 단순 데이터 홀더(Data Holder)로 전락 | 스스로 책임을 완수하는 자율적 객체(Autonomous) |
| 로직 분산도 | 비즈니스 로직이 수많은 외부 서비스로 분산 | 데이터와 연관 로직이 동일 클래스에 고도로 응집 |
| 변경 영향도 | 필드 타입 변경 시 외부 호출부 전면 수정 필요 | 내부 표현을 바꾸어도 공개 메서드 시그니처만 유지 시 영향 제로 |
