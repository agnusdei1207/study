## 연관 키워드

- 캡슐화(Encapsulation), 객체지향 프로그래밍(OOP, Object-Oriented Programming), 정보 은닉(Data Hiding)
- 응집도(Cohesion), 결합도(Coupling), Tell Don't Ask, 디미터 법칙(Law of Demeter), Anemic Domain Model

## Ⅰ. 캡슐화의 개요

- 핵심 요약 : 데이터와 행위를 클래스로 묶고 내부 구현을 은닉하여 공개 인터페이스로만 상호작용하게 하는 객체지향 4대 기본 원리.
- 개념 : 객체지향 프로그래밍(OOP, Object-Oriented Programming)에서 연관된 데이터(속성, 상태)와 그 데이터를 처리하는 행위(메서드)를 하나의 논리적 단위인 클래스(Class)로 묶고, 객체의 내부 세부 구현을 외부에 감추어 오직 정의된 공개 인터페이스를 통해서만 상호작용하도록 보호하는 객체지향 4대 기본 원리 중 하나.
- 배경 및 필요성 : 데이터와 처리 함수가 분리된 절차지향 프로그래밍(POP, Procedure-Oriented Programming)에서는 전역 데이터가 외부 코드에 의해 무분별하게 변경되어 시스템 전체의 상태 무결성이 파괴되는 문제(Side-Effect)를 원천 해결.
- 핵심 효과 : 높은 응집도(Cohesion) 확보, 낮은 결합도(Coupling), 데이터 보호(Data Hiding), 재사용성 극대화.

## Ⅱ. 캡슐화의 특징

- 핵심 요약 : 상태 은닉과 불변식 보호, Tell Don't Ask 원칙이 핵심 특징.
1. 데이터 보호 및 상태 불변식 유지 : 잔액(balance)에 마이너스 값의 유입이나 승인되지 않은 차감을 방지하기 위해 필드를 private으로 은닉하고 비즈니스 규칙이 내장된 메서드를 통해서만 수정 허용.
2. Tell, Don't Ask 원칙 실현 : 객체의 상태를 물어보고(Ask) 외부에서 판단하여 수정하지 말고, 객체에게 비즈니스 목적의 메시지를 던져(Tell) 객체 스스로 자신의 데이터를 처리하도록 유도.
3. 접근 제어 기반의 경계 형성 : 공개 인터페이스(Public Methods)와 은닉된 내부(Private Fields)의 명확한 분리.
4. 변경 파급 최소화 : 내부 상태가 변경되어도 공개 인터페이스가 불변인 경우 외부에는 무영향.

## Ⅲ. 캡슐화의 구조 (흐름)

- 핵심 요약 : 공개 인터페이스 경계 너머의 private 필드 보호와 메시지 기반 상태 변경 구조.

```text
[ 외부 클라이언트 ]
   │ 오직 공개 인터페이스로만 메시지 교환
   ▼
[ 캡슐화된 객체 : Account ]
 - 공개 인터페이스 (Public Methods)
    + deposit(amount) : 입금 전 유효성 검증
    + withdraw(amount) : 잔액 검증 후 출금
    + getBalance() : 안전한 조회
   ─────────── 정보 은닉 경계 ───────────
 - 은닉된 내부 (Private Fields)
    - balance : 계좌 잔액 (직접 접근 불가)
    - validateAccount() : 내부 전용 검증 로직
```

```text
[ Tell, Don't Ask 메시지 흐름 ]
[ 외부 객체 ] ── withdraw(금액) ──> [ Account 객체 ]
                                        │
                                  내부 검증 수행
                                        ▼
                              잔액 확인 후 상태 갱신
[ 외부 객체 ] <── 처리 결과 응답 ── [ Account 객체 ]
 (외부는 balance 필드 직접 접근 불가)
```

## Ⅳ. 절차지향과 객체지향 캡슐화의 비교

- 핵심 요약 : 데이터·함수 분리와 전역 접근의 POP 대비 캡슐 결합과 접근 통제의 OOP.

| 비교 항목 | 절차지향 프로그래밍(POP) | 캡슐화 기반 객체지향(OOP) |
|---|---|---|
| 데이터와 함수의 관계 | 데이터 구조체와 처리 함수가 물리적으로 분리 | 데이터와 해당 데이터를 다루는 메서드가 단일 캡슐로 결합 |
| 데이터 접근 권한 | 전역 또는 공용 데이터로 누구나 직접 읽기/쓰기 가능 | private 접근 제어자를 통해 외부의 무단 상태 변경 차단 |
| 변경 영향도(Side Effect) | 데이터 필드 변경 시 전체 프로그램 함수 수정 파급 | 내부 상태가 변경되어도 공개 인터페이스 불변 시 외부 무영향 |
| 비즈니스 규칙 위치 | 데이터를 호출하는 수많은 컨트롤러/서비스에 중복 산재 | 해당 데이터를 소유한 엔티티 객체 내부에 완벽히 응집 |
| 설계 원칙 | 프로세스 흐름 중심의 순차적 기능 분해 | 책임과 역할을 가진 자율적인 객체 간의 협력 모델 |

## Ⅴ. 캡슐화의 장점과 한계

- 핵심 요약 : 응집도·재사용성·데이터 보호의 장점과 세터 남용·상속 노출·프레임워크 불일치의 한계.
- 장점
  1. 높은 응집도와 낮은 결합도를 통한 변경 파급 최소화.
  2. 상태 불변식 보호를 통한 데이터 무결성 확보.
  3. 공개 인터페이스 기반의 재사용성 및 확장성 확보.
- 한계점 1 : 게터/세터(Getter/Setter) 남용으로 인한 실질적 캡슐화 붕괴
  - 한계점 : 모든 필드를 private으로 선언하더라도 무분별하게 Getter와 Setter를 개방하면 외부 객체가 내부 상태를 꺼내어 직접 비즈니스 로직을 처리하게 되어 캡슐화가 원천 무력화.
  - 해결 방안 : '묻지 말고 시켜라(Tell, Don't Ask)' 원칙의 준수를 통한 상태 보유 객체 내부에서의 비즈니스 로직 직접 수행, DTO(Data Transfer Object) 외의 도메인 모델에서는 단순 Setter 사용 금지.
- 한계점 2 : 상속을 통한 하위 클래스로의 내부 구현 노출
  - 한계점 : 상속(extends)을 사용할 경우 부모 클래스의 protected 필드 및 내부 메서드가 자식 클래스에 노출되어, 부모의 내부 구현 수정 시 자식 클래스가 연쇄 파손되는 결함 발생.
  - 해결 방안 : 상속 대신 객체 합성(Composition) 활용, 변경을 불허해야 하는 핵심 기반 클래스는 `final` 키워드 선언을 통한 무분별한 상속 확장 차단.
- 한계점 3 : ORM(Object-Relational Mapping) 엔티티 및 직렬화 프레임워크와의 불일치
  - 한계점 : JPA(Java Persistence API), Jackson 등 현대 프레임워크가 기본 생성자, 리플렉션 접근을 요구함에 따라 객체의 불변식(Invariant) 검증 로직이 우회되거나 상태가 임의로 조작될 위험.
  - 해결 방안 : 도메인 엔티티와 외부 전송용 DTO의 엄격한 분리, 정적 팩토리 메서드(Static Factory Method)를 통해서만 객체가 생성되도록 강제하여 생성 불변식 보장.

## Ⅵ. 고품질 도메인 모델 설계를 위한 기술사적 제언

- 핵심 요약 : 빈약한 도메인 모델 안티패턴 척결과 디미터 법칙 준수.
- 빈약한 도메인 모델(Anemic Domain Model) 안티패턴 척결 : 모든 필드에 기계적으로 Getter와 Setter를 개방하여 데이터를 단순히 담아두는 DTO처럼 클래스를 설계하면 캡슐화가 완전히 무력화되므로, Setter 생성의 원천 금지와 의미 있는 비즈니스 행위 메서드만의 노출 필요.
- 디미터 법칙(Law of Demeter, 최소 지식 원칙) 준수 : 객체 간의 결합도를 낮추고 캡슐화를 극대화하기 위해 '낯선 자와 이야기하지 말라'는 원칙을 적용, 메서드 체이닝(`a.getB().getC().doSomething()` 형태)을 지양하고 바로 인접한 협력자에게만 요청을 위임하는 설계 준수 필요.

## Ⅶ. 결론

- 핵심 요약 : 캡슐화는 상태와 책임의 응집을 통한 변경에 강한 객체 설계의 핵심 원리.
- 요약 : 접근 통제 경계와 Tell Don't Ask 원칙을 통한 내부 불변식 보호.
- 시사점 : 세터 금지·합성 우선·디미터 법칙 준수를 통한 실질적 캡슐화 실현.
