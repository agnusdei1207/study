## Ⅰ. 캡슐화의 개요

- **개념** : 객체지향 프로그래밍(OOP)에서 연관된 데이터(속성, 상태)와 그 데이터를 처리하는 행위(메서드)를 하나의 논리적 단위인 클래스(Class)로 묶고, 객체의 내부 세부 구현을 외부에 감추어 오직 정의된 공개 인터페이스를 통해서만 상호작용하도록 보호하는 객체지향 4대 기본 원리 중 하나.
- **배경 및 필요성** : 데이터와 처리 함수가 분리된 절차지향 프로그래밍(POP)에서는 전역 데이터가 외부 코드에 의해 무분별하게 변경되어 시스템 전체의 상태 무결성이 파괴되는 문제(Side-Effect)를 원천 해결.
- **핵심 효과** : 높은 응집도(Cohesion) 확보, 낮은 결합도(Coupling), 데이터 보호(Data Hiding), 재사용성 극대화.

## Ⅱ. 캡슐화의 내부 구조 및 접근 통제 메커니즘

```text
   ┌────────────────────────────────────────────────────────┐
   │ [ 캡슐화된 객체: Account ]                            │
   │                                                        │
   │  [ 공개 인터페이스 (Public Methods) ]                   │
   │   + deposit(amount) : 입금 전 유효성 검증               │
   │   + withdraw(amount) : 잔액 검증 후 출금                │
   │   + getBalance() : 안전한 조회                          │
   │                                                        │
   │  ────────────────────────────────────────────────────  │
   │                                                        │
   │  [ 은닉된 데이터 및 내부 구현 (Private Fields) ]        │
   │   - balance : 계좌 잔액 (외부 직접 접근 불가: 보호)    │
   │   - validateAccount() : 내부 전용 검증 로직             │
   └────────────────────────────────────────────────────────┘
          ▲
          │ 오직 허용된 공개 인터페이스로만 메시지 교환
   [ 외부 클라이언트 ]
```

- **데이터 보호 및 상태 불변식 유지** : 잔액(balance)에 마이너스 값이 들어가거나 승인되지 않은 차감이 일어나는 것을 방지하기 위해 필드를 private으로 은닉하고 비즈니스 규칙이 내장된 메서드를 통해서만 수정 허용.
- **Tell, Don't Ask 원칙 실현** : 객체의 상태를 물어보고(Ask) 외부에서 판단하여 수정하지 말고, 객체에게 비즈니스 목적의 메시지를 던져(Tell) 객체 스스로 자신의 데이터를 처리하도록 유도.

## Ⅲ. 절차지향(POP)과 객체지향 캡슐화(OOP)의 비교

| 비교 항목 | 절차지향 프로그래밍 (POP) | 캡슐화 기반 객체지향 (OOP) |
|---|---|---|
| 데이터와 함수의 관계 | 데이터 구조체와 처리 함수가 물리적으로 분리 | 데이터와 해당 데이터를 다루는 메서드가 단일 캡슐로 결합 |
| 데이터 접근 권한 | 전역 또는 공용 데이터로 누구나 직접 읽기/쓰기 가능 | private 접근 제어자를 통해 외부의 무단 상태 변경 차단 |
| 변경 영향도 (Side Effect) | 데이터 필드 변경 시 전체 프로그램 함수 수정 파급 | 내부 상태가 변경되어도 공개 인터페이스 불변 시 외부 무영향 |
| 비즈니스 규칙 위치 | 데이터를 호출하는 수많은 컨트롤러/서비스에 중복 산재 | 해당 데이터를 소유한 엔티티 객체 내부에 완벽히 응집 |
| 설계 원칙 | 프로세스 흐름 중심의 순차적 기능 분해 | 책임과 역할을 가진 자율적인 객체 간의 협력 모델 |

## Ⅳ. 고품질 도메인 모델 설계를 위한 기술사적 제언

- **빈약한 도메인 모델(Anemic Domain Model) 안티패턴 척결** : 모든 필드에 기계적으로 Getter와 Setter를 개방하여 데이터를 단순히 담아두는 DTO처럼 클래스를 설계하면 캡슐화가 완전히 무력화되므로, Setter 생성을 원천 금지하고 의미 있는 비즈니스 행위 메서드만을 노출해야 함.
- **디미터 법칙(Law of Demeter, 최소 지식 원칙) 준수** : 객체 간의 결합도를 낮추고 캡슐화를 극대화하기 위해 '낯선 자와 이야기하지 말라'는 원칙을 적용, 메서드 체이닝(``a.getB().getC().doSomething()`` 형태)을 지양하고 바로 인접한 협력자에게만 요청을 위임하는 설계 준수 필요.
