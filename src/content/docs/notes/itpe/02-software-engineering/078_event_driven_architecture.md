---

## 30초 인출

- 본질: **EDA(Event-Driven Architecture)** 는 도메인 내 상태 변화(Event)를 감지하여 메시지 채널을 통해 비동기 전송하고, 이에 반응하여 독립된 분산 서비스들이 후속 비즈니스 로직을 자율적으로 수행하는 느슨한 결합(Loose Coupling) 기반 아키텍처 스타일
- 메커니즘: 생산자의 이벤트 발행(Publish) → 이벤트 라우팅/채널 버퍼링 → 구독자의 비동기 수신(Subscribe) 및 처리 → 후속 이벤트 파이프라인 연쇄 촉발
- 통찰: 단순 비동기 브로커 기반 구현 시 이벤트 유실, 중복 수신, 분산 트랜잭션 불일치가 발생할 수 있으므로 트랜잭셔널 아웃박스(Transactional Outbox) 패턴과 멱등성(Idempotency) 소비자 설계 및 사가(Saga) 오케스트레이션을 결합해야 시스템 전반의 최종 일관성을 보장할 수 있음

<details>
<summary>핵심 용어</summary>

- **이벤트(Event)** : 도메인 내에서 이미 과거에 일어난 중요한 상태 변화를 나타내는 불변(Immutable)의 비즈니스 사실 데이터
- **브로커 토폴로지(Broker Topology)** : 중앙 통제자 없이 개별 서비스들이 브로커 큐를 통해 이벤트를 자율적으로 주고받는 코레오그래피(Choreography) 방식
- **중재자 토폴로지(Mediator Topology)** : 중앙의 오케스트레이터(Mediator)가 다단계 비즈니스 단계와 상태 전이, 보상 트랜잭션을 일괄 통제하는 방식
- **트랜잭셔널 아웃박스(Transactional Outbox)** : 도메인 엔티티 변경과 발행할 이벤트를 동일 RDB 트랜잭션 내에 기록하고 CDC로 브로커에 전송하는 이중 쓰기 방지 패턴
- **멱등성(Idempotency)** : 동일한 이벤트를 네트워크 재시도 등으로 여러 번 수신하더라도 시스템 상태가 최초 1회 실행된 것과 동일하게 유지되는 성질

</details>

> 이벤트 주도 아키텍처(EDA)의 개념과 구성요소를 설명하고, 브로커 토폴로지(Broker Topology)와 중재자 토폴로지(Mediator Topology)의 아키텍처 특성 비교 및 분산 데이터 일관성 보장을 위한 핵심 설계 패턴을 제시하시오.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 도메인 엔티티의 상태 변경을 나타내는 이벤트(Event)를 매개체로 하여 생산자(Producer)와 소비자(Consumer) 간의 공간적·시간적 결합을 분리하는 분산 비동기 아키텍처 |
| 목적 | 서비스 간 직접 의존성 제거, 트래픽 폭증 시 버퍼링을 통한 배압(Backpressure) 해소, 독립적 확장성(Scalability) 및 고가용성 달성 |

## Ⅱ. 핵심 특징

동기식 RPC/REST의 응답 대기 블로킹(Blocking)을 해소하고, 이벤트 로그 기반의 비동기 반응성 확보.

| 핵심 속성 | 설계 의미 | 엔지니어링 구현 기술 |
|---|---|---|
| **발행-구독(Pub/Sub) 비동기성** | 생산자는 소비자의 존재, 위치, 처리 완료 여부를 알 필요 없이 이벤트만 발행 | Apache Kafka, RabbitMQ, AWS EventBridge |
| **시간적/공간적 분리** | 소비자가 일시 장애나 점검 상태여도 이벤트는 큐에 안전하게 영속 보관 | 분산 커밋 로그(Commit Log), 메시지 브로커 |
| **최종 일관성 (Eventual Consistency)** | ACID 분산 트랜잭션 대신 도메인 간 비동기 이벤트 전달을 통한 궁극적 상태 수렴 | Saga Pattern, CDC(Change Data Capture) |
| **이벤트 불변성 (Immutability)** | 발생한 이벤트는 수정 불가능한 역사적 사실로 보존되어 재현 및 감사 가능 | Event Sourcing, Append-Only Storage |

## Ⅲ. 체계·프로세스

EDA의 2대 토폴로지(중재자 vs 브로커) 구조 및 이벤트 처리 파이프라인.

```text
+---------------------------------------------------------------------------------------------------------+
|                                    EDA 2대 토폴로지 아키텍처 체계                                        |
+---------------------------------------------------------------------------------------------------------+
                                                                                                           
  [1] 중재자 토폴로지 (Mediator Topology : 오케스트레이션 방식)                                           
                                                                                                           
  클라이언트 요청 ──> [시작 큐] ──> +─────────────────────────+ ──> [주문 큐] ──> (주문 서비스)           
                                    |     이벤트 중재자        |                                           
                                    |    (Orchestrator)       | ──> [결제 큐] ──> (결제 서비스)           
                                    |                         |                                           
                                    | * 워크플로우 상태 관리  | ──> [배송 큐] ──> (배송 서비스)           
                                    | * 보상 트랜잭션 지휘    |                                           
                                    +─────────────────────────+                                           
                                                                                                           
───────────────────────────────────────────────────────────────────────────────────────────────────────────
                                                                                                           
  [2] 브로커 토폴로지 (Broker Topology : 코레오그래피 방식)                                               
                                                                                                           
       주문 생성                               결제 완료                               배송 접수           
  +─────────────────+                     +─────────────────+                     +─────────────────+      
  |   주문 서비스   |                     |   결제 서비스   |                     |   배송 서비스   |      
  +─────────────────+                     +─────────────────+                     +─────────────────+      
           │                                       ▲                                       ▲               
           ▼                                       │                                       │               
     [주문생성 토픽] ──────────────────────────────┘                                       │               
                                                           [결제완료 토픽] ────────────────┘               
                                                                                                           
  * 중앙 제어자 없음, 각 서비스가 자율적으로 이전 이벤트를 구독하고 후속 이벤트를 연쇄 발행              
```

- **토폴로지별 핵심 동작 프로세스**:
  1. **중재자 토폴로지 처리 절차** : 클라이언트가 '주문 제출' 초기 이벤트를 시작 큐에 인입 $\rightarrow$ 이벤트 중재자가 이를 수신하여 주문 검증 액션 큐로 라우팅 $\rightarrow$ 결제, 재고, 배송 단계를 중앙에서 제어하며 단계별 실패 시 역방향 보상 트랜잭션(Compensating Transaction) 발행.
  2. **브로커 토폴로지 처리 절차** : 주문 서비스가 주문 생성 후 즉시 `OrderCreated` 이벤트를 Kafka 브로커에 발행 $\rightarrow$ 결제 서비스가 이를 감지하여 결제 처리 후 `PaymentCompleted` 이벤트 발행 $\rightarrow$ 배송 서비스가 결제 이벤트를 감지하여 배송 절차를 자율적으로 시작.

## Ⅳ. 종류·비교

#### 브로커 토폴로지 vs 중재자 토폴로지 상세 비교

| 비교 항목 | 브로커 토폴로지 (Broker) | 중재자 토폴로지 (Mediator) |
|---|---|---|
| **제어 메커니즘** | 코레오그래피 (Choreography, 자율 반응) | 오케스트레이션 (Orchestration, 중앙 통제) |
| **중앙 제어 컴포넌트** | 없음 (메시지 브로커만 존재) | 있음 (이벤트 중재자/엔진 존재) |
| **비즈니스 결합도** | 극도로 낮음 (이벤트 스키마에만 의존) | 보통 (중재자가 전체 워크플로우 상태와 순서 인지) |
| **흐름 가시성** | 낮음 (분산 추적 시스템 없이 전체 흐름 파악 곤란) | 높음 (중재자 콘솔에서 트랜잭션 진행 상태 즉시 확인) |
| **보상 트랜잭션 구현** | 복잡함 (실패 이벤트를 구독한 서비스들이 각자 롤백) | 명확함 (중재자가 실패 감지 시 보상 절차 순차 지휘) |
| **확장성 및 처리량** | 매우 높음 (단순 이벤트 전달로 병목 최소) | 보통 (중재자의 상태 관리 오버헤드로 스케일링 필요) |
| **최적 적용 도메인** | IoT 데이터 수집, 로그 파이프라인, 단순 알림 | 주문-결제-정산, 대출 심사, 다단계 예약 프로세스 |

#### 메시지 브로커 기술 특성 비교

| 브로커 기술 | 메시지 저장 모델 | 소비 방식 | 특징 및 주 활용 처 |
|---|---|---|---|
| **Apache Kafka** | 분산 디스크 커밋 로그(Commit Log) | 풀(Pull) 기반, 컨슈머 오프셋 관리 | 대규모 실시간 스트리밍, 이벤트 소싱 |
| **RabbitMQ** | 인메모리 FIFO 큐(Erlang 기반) | 푸시(Push) 기반, AMQP 라우팅 키 | 복잡한 메시지 라우팅, 소단위 작업 큐 |
| **AWS SQS/SNS** | 클라우드 완전관리형 메시징 서비스 | HTTP 풀/푸시 하이브리드 | 서버리스 아키텍처, 인프라 운영 관리 최소화 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| RDB 비즈니스 데이터 저장과 이벤트 브로커 발행 간 2단계 커밋 부재로 인한 이중 쓰기(Dual-write) 불일치 | 트랜잭셔널 아웃박스(Transactional Outbox) 패턴 적용 및 Debezium CDC를 통한 안전한 이벤트 릴레이 구축 |
| 네트워크 타임아웃 및 재전송으로 인한 동일 이벤트 중복 수신 시 데이터 오염 발생 | 수신 서비스에 고유 이벤트 식별자(Event-ID) 기반 멱등성 테이블(Idempotency Key)을 두어 중복 처리 원천 차단 |
| 비동기 분산 환경에서 이벤트 순서 역전(Out-of-Order)으로 인한 상태 무결성 훼손 | 파티션 키(Partition Key) 설계를 통한 관련 도메인 이벤트의 단일 파티션 격리 및 버전 번호 검증 적용 |

## Ⅵ. 제언

비즈니스 트랜잭션의 엄격한 순서와 보상이 요구되는 코어 업무는 중재자(사가 오케스트레이션) 방식을, 서비스 간 느슨한 상태 동기화는 브로커(코레오그래피) 방식을 혼용하는 하이브리드 토폴로지 설계가 바람직함.

```text
[코어 업무 트랜잭션] ──> [중재자 토폴로지 (Orchestrated Saga)] ──> [보상 트랜잭션 무결성]
[부가 기능 연계]     ──> [브로커 토폴로지 (Choreography Pub/Sub)] ──> [독립적 스케일아웃]
```

| 설계 영역 | 핵심 권장 기술 | 검증 및 거버넌스 방안 |
|---|---|---|
| **이벤트 신뢰성** | Transactional Outbox + Debezium CDC | At-least-once 전달 보장 및 이벤트 유실 제로 달성 |
| **데이터 무결성** | Event-ID 기반 멱등 소비자(Idempotent Consumer) | Redis/RDB 멱등 키 검사로 중복 처리 완벽 방어 |
| **전사 관측성** | OpenTelemetry Distributed Tracing | W3C TraceContext 헤더 주입을 통한 엔드투엔드 경로 추적 |
