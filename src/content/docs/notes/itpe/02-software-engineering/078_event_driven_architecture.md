## 연관 키워드
- EDA, 이벤트 생산자, 이벤트 브로커, 이벤트 소비자, 브로커 토폴로지, 중재자 토폴로지, 코레오그래피, 오케스트레이션, 사가 패턴, 멱등성, Transactional Outbox

### Ⅰ. EDA의 개요

- 핵심 요약 : 상태 변화를 이벤트로 발행하고 소비하여 서비스 간 결합을 낮추는 비동기 분산 아키텍처 스타일.
- 개념 : 이벤트 기반 아키텍처(EDA, Event-Driven Architecture)는 시스템 내외부에서 발생한 유의미한 상태 변화인 이벤트(Event)를 감지하고 발행·전달·소비하는 비동기 분산 아키텍처 스타일임.
- 배경 및 필요성 : REST(Representational State Transfer)나 RPC(Remote Procedure Call) 같은 동기 호출은 서비스 간 강결합을 만들고, 응답 대기로 성능을 떨어뜨리며, 한 서비스 장애가 연쇄 장애(Cascading Failure)로 번지는 문제가 있음.
- 핵심 3요소 : 이벤트 생산자(Event Producer), 이벤트 브로커(Event Broker), 이벤트 소비자(Event Consumer).
- 주요 목적 : 서비스 간 결합을 낮추고 확장성·반응성을 높이는 것.

### Ⅱ. EDA의 특징 및 장점

- 핵심 요약 : 비동기 메시징 기반의 낮은 결합도와, 브로커·중재자 두 토폴로지의 선택적 운용.

1. 비동기 메시징 : 발행-구독(Publish-Subscribe) 방식으로 응답을 기다리지 않음 → 생산자가 후속 처리를 기다리지 않아 반응성 향상.
2. 낮은 결합도 : 생산자가 소비자의 존재를 알지 못하는 느슨한 결합 → 소비자를 추가하거나 바꿔도 생산자가 영향을 받지 않음.
3. 브로커 토폴로지(Broker Topology) : 중앙 조정자 없이 이벤트가 연쇄적으로 전파되는 코레오그래피(Choreography) 방식 → 단순 알림과 실시간 스트리밍에 적합.
4. 중재자 토폴로지(Mediator Topology) : 중재자(오케스트레이터)가 단계별 워크플로우를 통제 → 다단계 처리와 실패 시 보상 조율에 적합.
5. 결과적 일관성(Eventual Consistency) : 즉시 일관성 대신 최종 데이터 정합성을 지향 → 가용성과 확장성을 얻는 대가로 정합성 지연을 감수.

### Ⅲ. EDA의 구조 (흐름)

- 핵심 요약 : 중앙 제어가 없는 브로커 토폴로지와, 중재자가 흐름을 지휘하는 중재자 토폴로지의 이원 구조.

```text
[ 브로커 토폴로지 (코레오그래피) ]

[ 이벤트 생산자 ]
   ↓ 발행
[ 이벤트 브로커 ]
   ↓ 전달
[ 소비자 A ]
   ↓ 후속 이벤트 재발행
[ 이벤트 브로커 ]
   ↓ 전달
[ 소비자 B ]
   (중앙 제어기 없이 자율 전파)
```

```text
[ 중재자 토폴로지 (오케스트레이션) ]

[ 이벤트 중재자 (오케스트레이터) ]
   ↓ 1단계 지시
[ 작업 1 ]
   ↓ 2단계 지시
[ 작업 2 ]
   ↓ 실패 시 보상 지시
[ 보상 작업 ]
```

### Ⅳ. 브로커 토폴로지와 중재자 토폴로지 비교

- 핵심 요약 : 분산 자율 제어로 확장성을 극대화하는 방식과, 중앙 집중 제어로 흐름 가시성을 확보하는 방식의 선택 기준.

| 비교 항목 | 브로커 토폴로지 (Broker) | 중재자 토폴로지 (Mediator) |
|---|---|---|
| 제어 방식 | 분산 자율 제어 (코레오그래피) | 중앙 집중 제어 (오케스트레이션) |
| 결합도 | 매우 낮음 (생산자가 소비자를 알지 못함) | 중간 (중재자가 워크플로우 단계를 앎) |
| 확장성과 성능 | 중앙 병목이 없어 확장에 유리 | 중재자 성능에 따라 한계가 생길 수 있음 |
| 트랜잭션 관리 | 전체 흐름 추적과 오류 처리가 어려움 | 흐름 가시성이 좋고 보상 처리가 쉬움 |
| 대표 솔루션 | Apache Kafka, AWS SNS(Simple Notification Service)/SQS(Simple Queue Service), RabbitMQ | Camunda, AWS Step Functions, Temporal |

### Ⅴ. EDA의 한계와 방안

- 핵심 요약 : 낮은 결합도와 확장성·반응성의 이점, 결과적 일관성과 이벤트 중복·스키마 호환성의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 결과적 일관성과 추적 어려움 | ACID 트랜잭션이 없어 전역 정합성이 늦게 맞춰지고, 비동기 장애의 원인 추적이 어려움 | 사가 패턴(Saga Pattern)과 보상 트랜잭션 적용, W3C(World Wide Web Consortium) Trace Context 기반 분산 추적(OpenTelemetry) 전파 | 보상 트랜잭션 실패율 |
| 이벤트 중복과 순서 역전 | 브로커의 At-Least-Once 전달과 파티션 간 지연으로 같은 이벤트의 중복 처리나 역순 수신이 발생 | Transactional Outbox와 Inbox 패턴, 멱등성(Idempotency) 보장 키 설계, 엔티티 단위 파티션 키 고정 | 중복 처리 건수 |
| 이벤트 스키마 진화에 따른 호환성 파손 | 생산자의 필드 변경이나 삭제가 다수 소비자의 역직렬화 오류로 이어짐 | 스키마 레지스트리(Schema Registry)로 Avro·Protobuf 스키마의 호환성 규칙을 CI/CD 파이프라인에서 강제 검증 | 호환성 검증 실패 건수 |

### Ⅵ. EDA 구축에 대한 기술사적 제언

- 핵심 요약 : 정합성을 플랫폼 공통 기능으로 제공하고, 이벤트 계약과 적용 범위를 조직 원칙으로 관리하는 방향.

1. 플랫폼 조직은 아웃박스 테이블과 CDC(Change Data Capture) 도구를 공통 인프라로 제공해 서비스 팀이 발행 정합성을 개별적으로 구현하지 않도록 역할을 나눔.
2. 아키텍처 위원회는 결제 승인처럼 즉시 정합성이 업무상 필수인 영역에는 EDA를 적용하지 않고 동기 호출을 병행한다는 선별 기준을 원칙으로 명시.
3. 이벤트 이름, 식별자 규칙, 스키마 버전 정책을 전사 계약으로 정하고 신규 이벤트 발행 전에 소비자 영향 검토를 거침.

### Ⅶ. 결론

- 핵심 요약 : EDA는 결합도를 낮추고 확장성을 얻는 대신 일관성과 추적성을 설계로 떠안는 아키텍처 스타일.
- 시사점 : 정합성과 추적성을 어떻게 보장할지를 먼저 정한 뒤 적용 범위를 고르는 순서가 EDA 도입의 성패를 가른다.
