## 1. EDA의 개요 및 출현 배경

### (1) EDA(Event-Driven Architecture)의 정의
- 시스템 내외부에서 발생하는 **상태의 변화(이벤트)를 감지하여 비동기적으로 메시지를 발행(Publish)하고, 이를 관심 있는 여러 구독자(Subscriber)에게 전달하여 자율적으로 처리하도록 구성하는 비동기 분산 아키텍처 스타일**.

### (2) 등장 배경
- **동기식 REST 통신의 블로킹 및 연쇄 장애**: 서비스 간 동기 호출(HTTP)이 꼬리를 물면서 한 서비스의 지연이 전체 시스템의 스레드 고갈 및 계단식 장애(Cascading Failure)를 유발함.
- **시공간적 결합도(Coupling) 해소**: 생산자(Producer)와 소비자(Consumer)가 상대방의 위치, 가용 여부, IP를 몰라도 메시지 브로커를 통해 독립적으로 진화·확장할 수 있는 비동기 구조 필요.

## 2. EDA 2대 토폴로지 아키텍처 및 메커니즘

### (1) 2대 토폴로지(중재자 vs 브로커) 구조 비교도
```text
+-------------------------------------------------------------------------+
|                  EDA 2대 핵심 토폴로지 아키텍처 비교                     |
+-------------------------------------------------------------------------+
| [ 1. 중재자 토폴로지 (Mediator) : 오케스트레이션 방식 ]                 |
| [생성자] ──▶ [시작 큐] ──▶ [이벤트 중재자 (Mediator)]                   |
|                              │ (액션 큐 1) │ (액션 큐 2) │ (액션 큐 3)  |
|                              v             v             v              |
|                         [결제 프로세서] [재고 프로세서] [배송 프로세서] |
|                         (중앙에서 단계별 실행 순서 및 보상 트랜잭션 지휘) |
+─────────────────────────────────────────────────────────────────────────+
| [ 2. 브로커 토폴로지 (Broker) : 코레오그래피 방식 ]                     |
| [생성자] ──(주문생성)──▶ [이벤트 브로커]                                 |
|                               │                                         |
|                               v                                         |
|                       [결제 서비스] ──(결제완료)──▶ [이벤트 브로커]      |
|                                                           │             |
|                                                           v             |
|                                                   [재고 서비스] ──▶ ... |
|                       (중앙 제어자 없이 이벤트 구독 기반 자율 릴레이)   |
+-------------------------------------------------------------------------+
```

### (2) 토폴로지별 핵심 구성요소
| 토폴로지 | 핵심 구성요소 | 역할 및 동작 원리 |
|---|---|---|
| **중재자 토폴로지**<br>(Mediator) | **시작 큐 (Initiator Queue)** | 클라이언트로부터 최초 비즈니스 요청 이벤트를 수신하는 버퍼 큐 |
| | **이벤트 중재자 (Mediator)** | 전체 비즈니스 프로세스 상태 머신을 유지하며 순차/병렬 액션 지휘 |
| | **액션 큐 (Action Queue)** | 중재자가 개별 도메인 프로세서에 구체적 작업을 하달하는 전용 큐 |
| | **이벤트 프로세서 (Processor)** | 액션 큐의 작업을 수행하고 결과를 다시 중재자에게 회신하는 도메인 모듈 |
| **브로커 토폴로지**<br>(Broker) | **이벤트 브로커 (Broker)** | 대량 이벤트를 고속으로 수집·버퍼링·분배하는 분산 메시징 엔진 (Kafka 등) |
| | **이벤트 프로세서 (Processor)** | 브로커의 특정 토픽을 구독하여 처리 후, 후속 이벤트를 스스로 발행 |

## 3. 브로커 vs 중재자 토폴로지 상세 비교

| 비교 항목 | 브로커 토폴로지 (Broker Topology) | 중재자 토폴로지 (Mediator Topology) |
|---|---|---|
| **제어 메커니즘** | **코레오그래피 (Choreography, 탈중앙)** | **오케스트레이션 (Orchestration, 중앙 집중)** |
| **중앙 제어점** | 없음 (각 컴포넌트가 자율 연쇄 반응) | 있음 (이벤트 중재자가 워크플로우 총괄) |
| **결합도 및 확장성**| **결합도 극소, 수평 확장성(Scale-out) 극대** | 중재자 의존성 존재, 확장 시 중재자 관리 필요 |
| **비즈니스 가시성** | 낮음 (전체 흐름을 한눈에 파악 불가) | **매우 높음 (중재자에서 트랜잭션 진행 상태 감사 가능)** |
| **에러 및 보상 처리**| 어려움 (분산된 컴포넌트 간 역방향 이벤트 릴레이) | **용이함 (중재자가 실패 감지 즉시 역순 보상 지휘)** |
| **적합한 적용 도메인**| 클릭스트림, IoT 데이터 파이프라인, 단순 통보 | **주문-결제-정산, 대출 심사 등 복잡한 다단계 비즈니스** |

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **배송 실패 시 결제 취소 누락으로 정산 파탄**<br>(코레오그래피 환경 분산 트랜잭션 오류) | 브로커 방식에서 다단계 보상 트랜잭션을 조정할 중앙 지휘자 부재 | 복합 트랜잭션 구간을 오케스트레이션(Saga Orchestrator) 중재자 구조로 전환 | 분산 트랜잭션 실패 시 자동 보상 롤백 100% 보장 |
| **중재자 서버 다운으로 전사 주문 접수 마비**<br>(중재자의 단일 실패점(SPOF) 화) | 중재자 내부에 비즈니스 연산 로직을 과도하게 집어넣고 단일 인스턴스로 운영 | 중재자는 무상태(Stateless) 라우터로 경량화하고 인스턴스 수평 분산 및 워크플로우 영속화 | SPOF 제거 및 99.99% 무중단 가용성 확보 |
| **네트워크 재전송으로 인한 이중 결제 사고**<br>(동일 결제 이벤트 2회 중복 소비) | 메시지 브로커의 최소 한 번(At-least-once) 전송 특성에 대한 방어 부재 | 메시지 Key 기반 멱등성(Idempotency) 테이블 검증 및 트랜잭셔널 아웃박스 적용 | 중복 이벤트 처리 사고 0건 차단 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 단일 토폴로지 맹신 (Silver Bullet)]     [현대: 실용적 하이브리드 이벤트 아키텍처]
- 모든 워크플로우를 카프카 브로커로 억지 구성 ──▶ - 복합 업무는 중재자(Saga Orchestrator), 단순 통보는 브로커
- 모놀리스 ESB 방식 중재자로 회귀          ──▶ - Temporal/Camunda 기반의 코드형 워크플로우(Durable Execution)
- 이벤트 유실 및 정합성 결함 방치           ──▶ - Transactional Outbox + Debezium CDC 기반 원자적 발행 보장
```

- **하이브리드 토폴로지(Hybrid Topology) 전략 제시**: 실무 시스템은 100% 브로커 또는 100% 중재자로만 구축할 수 없음. **주문 접수, 결제 승인, 배송 요청과 같이 강력한 정합성과 보상 트랜잭션이 요구되는 코어 업무는 '중재자 토폴로지(Temporal, Camunda)'**로 제어하고, **배송 상태 변경에 따른 마일리지 적립, 푸시 알림, 로그 수집 등 단순 후속 통보는 '브로커 토폴로지(Kafka)'**로 연결하는 하이브리드 설계가 기술사로서 제시할 가장 성숙한 답안임.
- **트랜잭셔널 아웃박스(Transactional Outbox) 패턴의 필수 연계**: 이벤트 아키텍처의 가장 치명적인 결함은 DB 트랜잭션과 이벤트 발행 간의 분절임. RDBMS의 로컬 트랜잭션으로 비즈니스 데이터와 이벤트 테이블을 한 번에 커밋하고, **Debezium CDC(Change Data Capture)**가 이를 감지하여 브로커로 비동기 송출하는 원자성 보장 아키텍처를 반드시 부각해야 함.
