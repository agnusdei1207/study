## 연관 키워드

- 플랫폼 엔지니어링(Platform Engineering), 내부 개발자 플랫폼(IDP, Internal Developer Platform), 셀프서비스(Self-Service)
- 황금 경로(Golden Path), 개발자 경험(DX, Developer Experience), 인지 부하(Cognitive Load), Platform as a Product, Policy-as-Code

## Ⅰ. 플랫폼 엔지니어링의 개요

- 핵심 요약 : 내부 개발자 플랫폼(IDP, Internal Developer Platform)의 셀프서비스로 개발자의 인지 부하를 줄이는 엔지니어링 체계.
- 개념 : 개발자가 인프라와 파이프라인의 복잡성을 직접 다루지 않고 셀프서비스(Self-Service) 방식으로 애플리케이션을 빌드·배포·운영하도록 **내부 개발자 플랫폼** (IDP)을 설계·구축·운영하는 엔지니어링 체계(**플랫폼 엔지니어링**, Platform Engineering).
- 배경 및 필요성 : DevOps(Development and Operations) 확산으로 개발자가 떠안는 인프라 **인지 부하** (Cognitive Load)가 한계에 이르렀고, 팀마다 인프라를 제각각 구축하면서 거버넌스 부재와 운영 비효율이 심화됨.
- 주요 목적 : 개발자 인지 부하 경감, **개발자 경험** (DX, Developer Experience) 향상, **황금 경로** (Golden Path) 제공, 전사 보안과 인프라 표준 준수.

## Ⅱ. 플랫폼 엔지니어링의 특징 및 장점

- 핵심 요약 : 플랫폼을 내부 제품으로 취급하고 황금 경로로 표준을 내재화하여, 개발자가 비즈니스 코드에 집중하도록 만드는 셀프서비스 체계.

1. 셀프서비스 제공 : 인프라와 파이프라인을 포털이나 CLI로 직접 요청·프로비저닝 → 요청 대기 시간 단축.
2. **Platform as a Product** (플랫폼을 제품으로 취급) : 개발자를 내부 고객으로 대우하고 피드백 기반으로 지속 개선 → 채택률 향상.
3. 황금 경로 (Golden Path, 모범 아키텍처·보안·로깅·CI/CD가 사전 구성된 권장 템플릿) : 표준 준수를 기본 경로로 만들어 설계 편차 감소.
4. 인지 부하 최소화 : 인프라 세부 도구 학습 부담을 덜어 비즈니스 코드 구현에 집중 → 개발 생산성 향상.
5. **Policy-as-Code** (정책을 코드로 정의해 자동 적용하는 방식) : 보안과 거버넌스를 플랫폼 안에 사전 내재화 → 사후 감사 부담 감소.

## Ⅲ. 플랫폼 엔지니어링의 구조 (흐름)

- 핵심 요약 : 개발자 포털의 셀프서비스 요청이 IDP의 표준 기능을 거쳐 기반 인프라로 이어지는 계층 구조.

```text
[ 플랫폼 엔지니어링 계층 구조 ]

[ 개발자 (Developer) ]
   │ 셀프서비스 요청
   ↓
[ 개발자 포털 (Backstage, CLI) ]
   ↓
[ 내부 개발자 플랫폼 (IDP) ]
   ↓
[ 기반 인프라 및 거버넌스 ]
```

- 황금 경로에 따른 서비스 생성 흐름은 다음과 같다.

```text
[ 황금 경로 서비스 생성 흐름 ]

1. 개발자 포털에서 표준 템플릿 선택
   ↓
2. 저장소 및 CI/CD 파이프라인 자동 생성
   ↓
3. 표준 아키텍처·보안 정책 자동 적용
   ↓
4. 프로덕션 레디 상태의 서비스 배포
```

- 기반 인프라 계층은 IaC(Infrastructure as Code, 코드형 인프라) 방식으로 정의되어 정책과 함께 관리된다.

```text
[ IDP 구성 요소 ]

황금 경로 템플릿 : 표준 서비스 구조 제공
CI/CD 템플릿 : GitHub Actions, ArgoCD
기반 인프라 : Kubernetes, 클라우드 리소스
정책 : IaC(Terraform), OPA 보안 정책
```

## Ⅳ. 전통적 DevOps와 플랫폼 엔지니어링의 비교

- 핵심 요약 : 개별 팀이 전담 운영하던 방식에서 중앙 집중화된 셀프서비스 플랫폼 방식으로의 전환.

| 비교 항목 | 전통적 DevOps ("You Build It, You Run It") | 플랫폼 엔지니어링 (IDP 기반) |
| --- | --- | --- |
| 개발자의 역할 | 개발뿐 아니라 Kubernetes 매니페스트, IaC, 네트워크까지 직접 작성 | IDP 포털을 통한 셀프서비스로 인프라 요청과 자동 프로비저닝 |
| 인지 부하 | 높음 (인프라 도구 학습 곡선 부담) | 낮음 (비즈니스 코드 구현에 집중) |
| 인프라 관리 | 개발팀별로 파이프라인을 중복 구축 | 플랫폼 팀이 중앙 집중화된 황금 경로와 표준 템플릿 제공 |
| 보안 및 거버넌스 | 팀의 재량에 의존하며 사후 감사 위주 | 플랫폼 내 정책(Policy-as-Code) 사전 내재화 |
| 핵심 성과 지표 | 배포 빈도, 변경 리드타임 (DORA(DevOps Research and Assessment) 지표) | 개발자 온보딩 시간, 셀프서비스 비율, 개발자 만족도 |

## Ⅴ. 플랫폼 엔지니어링의 한계와 방안

- 핵심 요약 : 플랫폼 사일로화, 황금 경로의 경직성, 플랫폼 자체의 복잡도라는 세 한계를 채택 유도, 예외 경로, 관리형 도구로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 플랫폼 팀의 사일로화와 개발팀의 반발 | 개발자 니즈를 듣지 않고 도구와 규칙을 일방적으로 강제 → 채택률 저하와 조직 갈등 | 플랫폼을 제품으로 보는 철학을 확립해 개발자를 내부 고객으로 대우하고, 플랫폼 전담 제품 관리자(PM, Product Manager)를 두며, 개발자 경험 만족도를 주기적으로 조사 | 개발자 경험 만족도, 채택률 |
| 황금 경로의 경직성 | 정의된 템플릿만 허용하면 새 기술 실험과 도메인 특화 아키텍처 도입이 막혀 섀도우 IT(Shadow IT) 발생 | 황금 경로를 강제 통제가 아닌 가장 편한 최소 저항 경로로 포지셔닝하고, 표준 외 기술을 검토하는 예외 절차 제공 | 예외 승인 건수, 섀도우 IT 발생 건수 |
| 플랫폼 자체의 복잡도 | Backstage, ArgoCD, Crossplane, Terraform 등 툴체인이 비대해져 업그레이드와 장애 대응 공수 과다 | 전면 자체 구축을 피하고 검증된 관리형 SaaS(Software as a Service)를 결합하며, 플랫폼 인프라도 GitOps 방식으로 관리 | 플랫폼 운영 공수 비율 |

## Ⅵ. 성공적인 플랫폼 엔지니어링 구축을 위한 기술사적 제언

- 핵심 요약 : 자발적 채택 문화, 오픈소스 표준 프레임워크의 통합, 플랫폼 성과의 정량 측정이라는 세 방향으로 플랫폼을 상시 운영 역량으로 정착.
- 자발적 채택 문화 : 플랫폼 사용을 규제로 강제하면 섀도우 IT가 생기므로, 황금 경로가 수작업 방식보다 편리하고 빠르다는 체감 효과를 먼저 입증하여 자연스러운 전환을 유도해야 한다.
- 오픈소스 표준 프레임워크 통합 : Backstage를 중심으로 서비스 카탈로그, 기술 문서(TechDocs), Kubernetes 플러그인을 하나의 창구(Single Pane of Glass)로 묶어 분산된 개발 도구의 가시성을 확보해야 한다.
- 플랫폼 성과의 정량 측정 : 개발자 온보딩 시간, 셀프서비스 비율, 개발자 만족도를 핵심 지표로 삼아 플랫폼 로드맵에 반영해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 플랫폼 엔지니어링은 개발자를 내부 고객으로 대우하는 셀프서비스 플랫폼을 구축하는 체계.
- 시사점 : 강제가 아닌 자발적 채택과 성과의 정량 측정을 바탕으로 플랫폼을 지속 개선하는 것이 성패를 가름.
