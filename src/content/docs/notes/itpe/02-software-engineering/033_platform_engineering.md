## Ⅰ. 플랫폼 엔지니어링의 개요

- **개념** : 개발자가 인프라나 파이프라인의 복잡성을 직접 다루지 않고도 셀프서비스(Self-Service) 방식으로 애플리케이션을 빌드, 배포, 운영할 수 있도록 내부 개발자 플랫폼(IDP, Internal Developer Platform)을 설계하고 구축·운영하는 엔지니어링 훈련 체계.
- **배경 및 필요성** : DevOps 확산으로 인해 개발자가 부담해야 할 인프라 인지 부하(Cognitive Load)가 한계에 도달하고, 팀마다 제각각 인프라를 구축하면서 거버넌스 부재와 운영 비효율이 심화된 문제 해결.
- **핵심 목표** : 개발자의 인지 부하 경감, 개발자 경험(DX, Developer Experience) 극대화, 황금 경로(Golden Path) 제공, 전사 보안 및 인프라 표준 준수.

## Ⅱ. 내부 개발자 플랫폼(IDP) 계층 구조 및 황금 경로

```text
   [ 개발자 (Developer) ] ──> [ 개발자 셀프서비스 포털 (Backstage / CLI) ]
                                          │
                                          ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │                  [ 내부 개발자 플랫폼 (IDP) ]                          │
   │  - 골든 패스 (Golden Path) 템플릿: 신규 마이크로서비스 3분 생성        │
   │  - CI/CD 파이프라인 표준 템플릿 (GitHub Actions, ArgoCD)              │
   │  - 환경 오케스트레이션 및 동적 개발 환경 프로비저닝                   │
   └──────────────────────────────────┬─────────────────────────────────────┘
                                      │
                                      ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │                  [ 기반 인프라 및 거버넌스 ]                           │
   │  Kubernetes, 클라우드 리소스 (AWS/GCP/Azure), IaC (Terraform), OPA 보안│
   └────────────────────────────────────────────────────────────────────────┘
```

- **황금 경로 (Golden Path)** : 모범적인 아키텍처, 보안, 로깅, CI/CD가 사전에 구성된 권장 템플릿으로, 개발자가 몇 번의 클릭이나 명령어로 프로덕션 레디 상태의 서비스를 즉시 생성할 수 있는 경로.
- **플랫폼을 제품으로(Platform as a Product)** : 플랫폼 엔지니어링 팀은 플랫폼을 내부 제품으로 취급하고 개발자를 '고객'으로 대우하며 피드백 기반 지속 개선 수행.

## Ⅲ. 전통적 DevOps와 플랫폼 엔지니어링의 비교

| 비교 항목 | 전통적 DevOps ("You Build It, You Run It") | 플랫폼 엔지니어링 (IDP 기반) |
|---|---|---|
| 개발자의 역할 | 개발뿐 아니라 K8s 매니페스트, IaC, 네트워크까지 직접 작성 | IDP 포털을 통한 셀프서비스로 인프라 요청 및 자동 프로비저닝 |
| 인지 부하 | 극도로 높음 (인프라 도구 학습 곡선 부담) | 최소화 (비즈니스 코드 구현에 온전히 집중) |
| 인프라 관리 | 개발팀별로 사일로화된 파이프라인 중복 구축 | 플랫폼 팀이 중앙 집중화된 황금 경로와 표준 템플릿 제공 |
| 보안 및 거버넌스 | 각 팀의 재량에 의존, 사후 감사 위주 | 플랫폼 내 정책(Policy-as-Code) 사전 내재화로 원천 보장 |
| 핵심 성과 지표 | 배포 빈도, 변경 리드타임 (DORA 지표) | 개발자 온보딩 시간, 일일 배포 만족도, 셀프서비스 비율 |

## Ⅳ. 플랫폼 엔지니어링의 주요 한계점 및 해결 방안

- **플랫폼 팀의 또 다른 사일로화 및 개발팀의 강제 수용 반발** :
  - **한계점** : 플랫폼 엔지니어링 팀이 개발자의 실제 니즈를 경청하지 않고 일방적인 도구와 규칙을 강제하여 채택률이 저조해지고 개발팀과의 조직적 갈등 유발.
  - **해결 방안** : '제품으로서의 플랫폼(Platform as a Product)' 철학을 확립하여 애플리케이션 개발자를 내부 고객으로 대우하고, 플랫폼 전담 PM 배치 및 주기적 개발자 경험(DevEx) 만족도 조사 수행.
- **황금 경로(Golden Path)의 과도한 경직성으로 인한 기술 혁신 저해** :
  - **한계점** : 미리 정의된 표준 템플릿과 파이프라인만 허용할 경우 특정 서비스에 필요한 최신 기술 실험이나 도메인 특화 아키텍처 도입이 차단되어 섀도우 IT(Shadow IT) 발생.
  - **해결 방안** : 황금 경로를 '강제 통제'가 아닌 '가장 편한 최소 저항의 경로(Paved Road)'로 포지셔닝하고, 표준 외 기술 도입을 위한 셀프서비스 기반 예외 인큐베이션 프로세스 제공.
- **플랫폼 자체의 복잡도 급증 및 운영 유지보수 비용 과다** :
  - **한계점** : Backstage, ArgoCD, Crossplane, Terraform 등 플랫폼 툴체인 자체의 구성 요소가 비대해져 플랫폼 인프라의 업그레이드와 장애 대응에 과도한 엔지니어링 공수 소모.
  - **해결 방안** : 무리한 전면 자체 구축(In-house)을 지양하고 검증된 관리형 오픈소스 SaaS를 적극 결합하며, 내부 플랫폼 인프라 자체를 GitOps 기반의 IaC로 완전 자동화 관리.

## Ⅴ. 성공적인 플랫폼 엔지니어링 구축을 위한 기술사적 제언

- **강제가 아닌 자발적 채택(Adoption)을 유도하는 문화 조성** : 플랫폼 사용을 강제 규제로 밀어붙이면 Shadow IT를 유발하므로, 황금 경로가 기존 수작업 방식보다 압도적으로 편리하고 빠르다는 것을 입증하여 자연스러운 전환 유도.
- **Backstage 등 오픈소스 표준 프레임워크 기반 생태계 통합** : 서비스 카탈로그, 기술 문서(TechDocs), Kubernetes 플러그인을 단일 대시보드로 통합하여 분산된 개발 도구의 가시성을 단일 창구(Single Pane of Glass)로 확보.
