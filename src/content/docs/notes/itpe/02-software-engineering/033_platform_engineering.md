## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 빌드·배포·DevOps → **플랫폼 엔지니어링(Platform Engineering)**

## 30초 인출

- 본질: 클라우드 네이티브 환경에서 개발자의 인지 부하(Cognitive Load)를 경감하고 개발 생산성을 극대화하기 위해 셀프서비스 도구 체계와 공통 인프라를 제품(Product)으로 제공하는 엔지니어링 분야
- 메커니즘: 전담 플랫폼 팀 구성 → 플랫폼의 제품화(Platform as a Product) → 내부 개발자 플랫폼(IDP) 및 골든 패스(Golden Path) 구축 → 가드레일 기반 셀프서비스 인프라 프로비저닝
- 통찰: 강제적인 표준화는 섀도우 IT와 개발 저항을 유발하므로 권장 경로(Paved Road)의 사용 편의성을 극대화하고 개발자 경험(DevEx) 메트릭 기반의 지속적 피드백 루프 확립 필요

<details>
<summary>핵심 용어</summary>

- **Platform Engineering(플랫폼 엔지니어링)** : 소프트웨어 배포와 운영에 필요한 공통 인프라를 추상화하여 개발자에게 셀프서비스 플랫폼으로 제공하는 분야
- **IDP(Internal Developer Platform)** : 개발자가 인프라, 환경, 배포 파이프라인을 티켓 요청 없이 스스로 프로비저닝할 수 있도록 지원하는 내부 포털
- **Golden Path (골든 패스)** : 보안, 컴플라이언스, 모니터링이 사전 내재화된 표준화되고 검증된 개발·배포 권장 경로(Paved Road)
- **Cognitive Load(인지 부하)** : 복잡한 쿠버네티스 설정, 클라우드 인프라, 보안 도구 등으로 인해 개발자가 비즈니스 로직 구현에 집중하지 못하는 정신적 과부하
- **Platform as a Product** : 내부 플랫폼을 사내 개발자(고객)를 위한 독립된 제품으로 간주하고 로드맵과 피드백을 기반으로 진화시키는 관리 철학
- **Policy as Code (PaC)** : OPA(Open Policy Agent) 등을 활용하여 보안 및 컴플라이언스 규칙을 코드로 정의하고 파이프라인에서 자동 검증하는 기법

</details>

## 2~4교시 25점 답안

## Ⅰ. 플랫폼 엔지니어링의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 개발팀이 인프라와 배포 도구의 복잡성에 얽매이지 않고 비즈니스 가치 창출에 집중할 수 있도록, 공통 툴체인과 인프라를 **내부 개발자 플랫폼(IDP)** 형태로 제품화하여 셀프서비스로 제공하는 엔지니어링 실천법 |
| 목적 | 개발자의 인지 부하(Cognitive Load) 경감, 개발자 경험(DevEx) 개선, 배포 리드타임 단축 및 엔터프라이즈 거버넌스 자동화 |

## Ⅱ. 플랫폼 엔지니어링의 핵심 특징

| 특징 | 의미 |
|---|---|
| 플랫폼의 제품화 (Product Mindset) | 사내 개발자를 고객으로 대우하며 사용자 인터뷰, 피드백, 로드맵을 기반으로 플랫폼을 지속 진화 |
| 자율적 셀프서비스 | 티켓 기반 수동 인프라 요청을 탈피하여 개발자 포털 UI/CLI/API를 통한 즉시 프로비저닝 |
| 골든 패스 (Paved Road) | 아키텍처, 보안, CI/CD, 모니터링 베스트 프랙티스가 사전 구성된 표준 템플릿 제공 |
| 정책 가드레일 자동화 | Policy as Code 기반으로 보안, 규정 준수, 비용 한도를 인프라 배포 시점에 자동 집행 |

## Ⅲ. 내부 개발자 플랫폼(IDP) 체계 및 요청 처리 프로세스

### IDP 5계층 아키텍처 및 골든 패스 셀프서비스 흐름

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. 개발자 인터페이스 계층 (Developer Interface Layer)                  │
│    - 개발자 포털 (Backstage UI) / CLI / Git 리포지토리                │
│    - 서비스 카탈로그 탐색, 골든 패스 템플릿 선택, 환경 프로비저닝 요청 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. 오케스트레이션 및 워크플로우 계층 (Orchestration Layer)             │
│    - 환경 구성 매니저 (Score, Humanitec Platform Orchestrator)         │
│    - 애플리케이션 요구사양 파싱, 종속 인프라 그래프 자동 생성         │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. 보안 및 정책 거버넌스 가드레일 계층 (Governance & Policy Layer)     │
│    - Policy as Code (OPA / Kyverno / HashiCorp Sentinel)               │
│    - RBAC 권한 검증, 보안 취약점 사전 스캔, 리소스 Quota 및 비용 심사  │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. 인프라 및 리소스 프로비저닝 계층 (Infrastructure Driver Layer)      │
│    - IaC 실행기 (Terraform / OpenTofu / Crossplane / Pulumi)           │
│    - K8s 네임스페이스, 클라우드 RDS, S3, 네트워크 VPC 자동 생성        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 5. 통합 관측성 및 모니터링 계층 (Observability Layer)                  │
│    - Prometheus, Grafana, OpenTelemetry, Datadog                       │
│    - 배포된 서비스의 메트릭, 로그, 트레이스, 핀옵스(FinOps) 비용 가시화 │
└────────────────────────────────────────────────────────────────────────┘
```

### IDP 핵심 구성요소 상세 분석

| 구성요소 | 핵심 기술 및 구현 도구 | 주요 역할 및 기능 |
|---|---|---|
| **개발자 포털 (Developer Portal)** | Spotify Backstage, Port | 중앙 서비스 카탈로그, API 문서 통합, 소프트웨어 템플릿 제공 |
| **플랫폼 오케스트레이터** | Score Spec, Kratix | 클라우드 종속적이지 않은 표준 스펙을 실제 인프라 리소스와 매핑 |
| **IaC 프로비저닝 엔진** | Terraform, Crossplane | 쿠버네티스 CRD 또는 선언적 코드로 클라우드 인프라 자원 자동 생성 |
| **정책 엔진 (Policy Engine)** | OPA(Open Policy Agent) | 보안 컴플라이언스 규칙 검증, 인프라 배포 전 취약점 사전 차단 |
| **지속적 배포 (CD Engine)** | ArgoCD, Flux (GitOps) | 선언된 Git 저장소 상태와 실제 클러스터 상태의 자동 동기화 |

## Ⅳ. 전통적 DevOps vs 플랫폼 엔지니어링 비교

### 운영 패러다임별 비교 분석

| 비교 항목 | 전통적 DevOps ("You Build It, You Run It") | 제언: 플랫폼 엔지니어링 (IDP 기반) |
|---|---|---|
| **개발자의 책임 범위** | 비즈니스 로직 + K8s 인프라 + CI/CD + 보안 전담 | **비즈니스 로직 구현에 집중 (골든 패스 활용)** |
| **개발자 인지 부하** | 극심한 도구 파편화와 인프라 복잡도로 부하 폭증 | **추상화된 셀프서비스 포털로 인지 부하 대폭 경감** |
| **인프라 프로비저닝** | 티켓 요청 후 수작업 처리 또는 팀별 중복 스크립트 | **개발자 포털을 통한 1-Click 자동 프로비저닝** |
| **보안 및 컴플라이언스** | 개발자 개인의 지식에 의존하여 설정 오류 빈발 | **골든 패스 및 Policy as Code로 보안 가드레일 내재화** |
| **조직 모델 (Team)** | 기능 횡단적 단일 DevOps 팀 | **전담 플랫폼 팀 (Enabling) + 스트림 정렬 개발팀** |

### 골든 패스(Golden Path) 3대 운영 원칙

| 원칙 | 실무 적용 방안 | 기대 효과 |
|---|---|---|
| **포장된 도로 (Paved Road)** | 자주 사용하는 표준 기술 스택과 아키텍처 템플릿을 완제품 형태로 제공 | 초기 서비스 셋업 시간 며칠에서 수 분으로 단축 |
| **선택의 자유 (Freedom with Responsibility)** | 특수 목적 서비스의 경우 골든 패스를 벗어나는 오프로드(Off-road) 허용 | 기술 혁신 수용성과 개발팀 자율성 보장 |
| **가드레일 내재화 (Built-in Guardrails)** | 권한 검증, 비밀키 관리(Vault), 네트워크 정책을 플랫폼 레벨에서 기본 적용 | 설정 실수 방지 및 엔터프라이즈 보안 무결성 확보 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 플랫폼 팀의 일방적 표준 강제로 인한 개발팀의 반발과 섀도우 IT(우회 인프라) 발생 | 플랫폼을 강제하지 않고 골든 패스의 압도적 편의성으로 자발적 채택을 유도하는 제품 전략 수립 |
| 다양한 개발팀의 이질적인 요구사항을 모두 흡수하려다 플랫폼 자체의 복잡도 폭발 | 80%의 표준 요구에 집중하는 최소 실행 가능 플랫폼(MVP) 우선 출시 및 점진적 확장 |
| 플랫폼 구축 이후 개발팀의 활용도 저조 및 비즈니스 효과 측정의 불명확성 | SPACE 프레임워크 및 DORA 메트릭 기반의 플랫폼 성공 지표(배포 주기, 온보딩 시간) 추적 |

## Ⅵ. 제언

Team Topologies 기반의 플랫폼 팀 조직화 및 생성형 AI 기반 대화형 플랫폼 엔지니어링 통합

### Team Topologies 기반 플랫폼 조직 모델

```text
[스트림 정렬 팀 (Stream-aligned Team)] ── 비즈니스 가치 및 도메인 기능 개발 집중
                 │                  ▲
                 │ (피드백 수렴)     │ (골든 패스 셀프서비스 제공)
                 ▼                  │
        [전담 플랫폼 팀 (Platform Team)]
                 │
                 ├─ [활성화 팀 (Enabling Team)] : 신규 도구 및 아키텍처 사내 전파
                 └─ [복잡한 하위 시스템 팀] : 특수 보안/암호화/대용량 인프라 개발
```

### AI 기반 대화형 개발자 플랫폼(ChatOps) 파이프라인

```text
[개발자 슬랙/IDE 자연어 요청] ("결제 모듈용 스테이징 환경 생성해줘")
       ↓
[플랫폼 AI 에이전트]
  ├─ 의도 분석 및 개발자 권한 검증
  ├─ 골든 패스 템플릿 자동 매핑 및 파라미터 완성
  └─ Policy as Code 가드레일 사전 적합성 검사
       ↓
[IDP 오케스트레이터 및 IaC 실행]
       ↓
[배포 완료 알림 및 엔드포인트 URL 개발자에게 즉시 회신]
```

### 선택 근거: 전통적 중앙 운영팀과 플랫폼 팀 모델 비교

| 구분 | 전통적 중앙 인프라 운영팀 | 제언: 현대적 플랫폼 엔지니어링 팀 |
|---|---|---|
| 상호작용 방식 | 티켓 발급 기반의 요청-대기-처리 모델 | 포털 및 API 기반의 셀프서비스 비동기 상호작용 |
| 업무 중심 | 일상적 서버 프로비저닝 및 장애 대응 | 개발자 경험(DevEx) 향상을 위한 플랫폼 제품 개발 |
| 조직 확장성 | 개발팀 증가 시 인프라 지원 병목 발생 | 셀프서비스 플랫폼으로 팀 규모 확장에 무제한 대응 |
