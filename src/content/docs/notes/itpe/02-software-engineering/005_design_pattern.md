## 연관 키워드

- 디자인 패턴, GoF(Gang of Four), 프록시 패턴(Proxy Pattern), 구조 패턴(Structural Pattern)
- 대리 객체(Proxy), 지연 로딩(Lazy Loading), 원격·가상·보호·스마트 프록시, AOP(Aspect-Oriented Programming)

## Ⅰ. 디자인 패턴과 프록시 패턴의 개요

- 핵심 요약 : 반복되는 설계 문제의 모범 해법 가운데, 접근 제어와 기능 위임을 맡는 대리 구조의 개요.
- 개념 : 반복적으로 나타나는 설계 문제에 재사용 가능한 해법을 정형화한 **디자인 패턴** (Design Pattern) 중, 실제 객체 앞에 **대리 객체** (Proxy)를 두어 접근을 제어하고 부가 기능을 위임하는 **프록시 패턴** (Proxy Pattern).
- 배경 및 필요성 : 원본 객체의 코드를 고치지 않고 **지연 로딩** (Lazy Loading), 보안 검증, 로깅 같은 공통 관심사를 투명하게 분리해야 하는 요구.
- 주요 목적 : 단일 책임 원칙(SRP, Single Responsibility Principle)과 개방-폐쇄 원칙(OCP, Open-Closed Principle)을 지키고 공통 관심사를 모듈화.

```text
[ GoF 디자인 패턴 3대 분류 ]

생성 패턴 (5종) : 객체 생성 방식
구조 패턴 (7종) : 객체 결합 구조 ← 프록시
행위 패턴 (11종) : 객체 간 상호작용
```

- 프록시 패턴은 **GoF** (Gang of Four)가 정리한 23개 패턴 중 **구조 패턴** (Structural Pattern)에 속함.

## Ⅱ. 프록시 패턴의 특징 및 장점

- 핵심 요약 : 공통 인터페이스로 호출을 투명하게 위임하면서, 원본 수정 없이 접근 제어와 부가 기능을 더하는 구조.

1. **공통 Subject 인터페이스** : 클라이언트가 프록시와 실제 객체를 같은 방식으로 호출 → 실제 객체의 교체와 확장이 쉬움.
2. 호출 위임 : 프록시가 원본 호출 전후에 인증·로깅을 수행 → 원본 코드 수정 없이 부가 기능 추가.
3. 지연 로딩과 캐싱 : 실제 객체의 생성·조회 시점을 제어 → 불필요한 자원 사용 감소.
4. 접근 제어 : 보호 프록시가 권한을 검사한 뒤 위임 → 민감 기능의 호출 경계 일원화.
5. **동적 프록시** (런타임에 대리 객체를 만들어 횡단 관심사를 적용하는 방식) : **AOP** (Aspect-Oriented Programming, 관점 지향 프로그래밍) 구현의 바탕 → 트랜잭션·보안 같은 공통 로직 분리.

## Ⅲ. 프록시 패턴의 구조 (흐름)

- 핵심 요약 : 클라이언트 요청을 프록시가 가로채 사전·사후 처리한 뒤 실제 객체로 위임하는 간접 참조 구조.

```text
[ 프록시 패턴 구조 ]

[ Client ]
    │ 1. Subject 인터페이스로 요청
    ▼
[ Proxy ] (대리 객체)
    │ 2. 사전·사후 처리 후 위임
    ▼
[ RealSubject ] (원본 객체)
```

- **Subject 인터페이스** : 클라이언트가 프록시와 실제 객체를 동일하게 다루도록 하는 공통 추상 메서드 정의.
- **RealSubject** : 실제 비즈니스 로직을 수행하는 원본 객체.
- **Proxy** : RealSubject에 대한 참조를 보유하고, 인증·캐싱·지연 로딩 같은 사전·사후 처리를 마친 뒤 호출을 위임.

## Ⅳ. 프록시 패턴 유형별 비교

- 핵심 요약 : 원격·가상·보호·스마트 프록시가 역할과 적용 사례에서 구분되는 유형 체계.

| 유형 | 핵심 역할 | 적용 사례 |
| --- | --- | --- |
| 원격 프록시(Remote Proxy) | 다른 주소 공간의 객체에 대한 로컬 대리인 역할 | gRPC 스텁, Java RMI(Remote Method Invocation), 분산 RPC(Remote Procedure Call) 클라이언트 |
| 가상 프록시(Virtual Proxy) | 생성 비용이 큰 객체의 생성을 실제 사용 시점까지 지연 | 고해상도 이미지 로딩, 대용량 문서 미리보기 |
| 보호 프록시(Protection Proxy) | 클라이언트 권한에 따라 실제 객체 메서드 접근 제어 | 관리자 권한 인가, 엔터프라이즈 리소스 접근 통제 |
| 스마트 프록시(Smart Proxy) | 객체 접근 시 로깅·참조 카운팅·락킹을 자동 수행 | Spring AOP 트랜잭션 프록시, C++ 스마트 포인터 |

## Ⅴ. 프록시 패턴의 한계와 방안

- 핵심 요약 : 간접 호출 비용, 내부 호출 우회, 추적 복잡성이 주요 한계이며, 프록시 범위 설계와 관측성 확보로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 호출 비용 증가 | 프록시 중첩과 부가 처리로 지연이 누적 | 핫패스의 프록시 계층과 부가 처리를 최소화하고, 생성 방식별 성능을 측정 | 호출 지연, 프록시 계층 수 |
| **내부 호출 우회** (Self-Invocation) | 같은 객체 내부 호출은 외부 프록시를 거치지 않아 AOP 기능이 누락 | 트랜잭션 경계를 별도 서비스로 분리하거나 위빙 방식을 적용 | 부가 기능 미적용 사례 수 |
| 추적 복잡성 | 프록시 중첩과 위임으로 원인 경로가 길어짐 | **상관 ID** (Correlation ID)를 부여해 전후 메트릭과 분산 추적에 연결 | 원인 파악 시간, 추적 누락률 |

## Ⅵ. 프록시 패턴 적용 시 기술사적 제언

- 핵심 요약 : 프록시 적용 범위를 팀 표준으로 정하고, 보안 경계에서는 보호 프록시를 인가의 단일 진입점으로 두는 운영 원칙.
- 적용 범위와 위빙 기준의 표준화 : 성능이 중요한 모듈에는 컴파일 타임 위빙(AspectJ)이나 바이트코드 조작(CGLIB) 가운데 어떤 방식을 쓸지 아키텍처 가이드에 명시하고, 설계 리뷰에서 프록시 중첩 깊이를 점검하는 것이 필요함.
- 보안 관점의 단일 진입점 : 민감 기능 앞에 보호 프록시를 두어 인가 검사를 한 곳에 모으고, 같은 객체 내부 호출이나 직접 참조로 검사를 우회하는 경로가 없는지 정기적으로 확인하는 것이 필요함.

## Ⅶ. 결론

- 핵심 요약 : 프록시 패턴은 투명한 간접 계층으로 공통 관심사를 분리하는 구조 패턴.
- 시사점 : 런타임 오버헤드, 내부 호출 우회, 디버깅 가시성 문제를 설계 단계에서 다뤄야 안정적인 적용이 가능함.
