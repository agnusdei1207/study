## Ⅰ. 디자인 패턴과 프록시 패턴의 개요

- 개념 : 소프트웨어 설계 과정에서 반복적으로 발생하는 구조적 문제들에 대해 재사용 가능한 객체 간 관계와 설계를 정형화한 모범 사례(Best Practice)이자, 그중 실제 객체에 대한 대리 객체(Proxy)를 두어 접근을 제어하고 부가 기능을 위임하는 구조 패턴.
- 배경 및 필요성 : 원본 객체의 코드 수정 없이 접근 제어, 지연 로딩(Lazy Loading), 보안 검증, 로깅, 트랜잭션 등 공통 관심사를 투명하게 분리하여 단일 책임 원칙(SRP)과 개방-폐쇄 원칙(OCP) 충족.
- **GoF** 3대 분류 : 생성(Creational) 5종, 구조(Structural) 7종(프록시 포함), 행위(Behavioral) 11종.

## Ⅱ. 프록시 패턴의 구조 및 동작 메커니즘

```text
   [ Client ] ──> [ <<interface>> Subject ] <── [ Proxy ]
                          │                       │ (대리 호출)
                          │                       ▼
                          └───────────────> [ RealSubject ]
```

- **Subject 인터페이스** : 클라이언트가 프록시와 실제 객체를 동일한 방식으로 다룰 수 있도록 공통 추상 메서드 정의.
- **RealSubject** : 실제 비즈니스 로직을 수행하는 핵심 원본 객체.
- **Proxy** : RealSubject에 대한 참조를 내부에 보유하며, 클라이언트의 요청을 가로채 사전/사후 처리(인증, 캐싱, 지연 로딩)를 수행한 후 RealSubject에 호출 위임.

## Ⅲ. 프록시 패턴의 주요 유형 및 활용 비교

| 유형 | 핵심 역할 | 적용 사례 |
|---|---|---|
| **원격 프록시** (Remote Proxy) | 서로 다른 주소 공간에 존재하는 객체에 대한 로컬 대리인 역할 | gRPC 스텁, Java RMI, 분산 RPC 클라이언트 |
| **가상 프록시** (Virtual Proxy) | 생성 비용이 큰 고용량 객체의 생성을 실제 사용 시점까지 지연 | 고해상도 그래픽 이미지 로딩, 대용량 문서 프리뷰 |
| **보호 프록시** (Protection Proxy) | 클라이언트의 권한에 따라 실제 객체 메서드 접근 제어 | 관리자 권한 인가, 엔터프라이즈 리소스 접근 통제 |
| **스마트 프록시** (Smart Proxy) | 객체 접근 시 부가적인 로깅, 참조 카운팅, 락킹 자동 수행 | Spring AOP 트랜잭션 프록시, C++ 스마트 포인터 |

## Ⅳ. 프록시 패턴의 주요 한계점 및 해결 방안

- 간접 호출 계층 추가에 따른 런타임 성능 오버헤드 :
  - 한계점 : 클라이언트와 실제 대상 객체(Real Subject) 사이에 프록시가 개입하여 메서드 호출 스택이 깊어지며, 동적 프록시(Dynamic Proxy) 사용 시 리플렉션(Reflection) 비용으로 인한 응답 지연 발생.
  - 해결 방안 : 런타임 리플렉션 대신 바이트코드 조작(CGLIB, ByteBuddy, ASM)을 활용한 사전 컴파일 및 클래스 생성 기법을 적용하고, 불필요한 프록시 중첩(Chaining)을 지양하며 핫패스(Hot Path) 캐싱 적용.
- 프록시 내부 호출(Self-Invocation) 시 부가 기능 누락 :
  - 한계점 : 대상 객체 내부에서 자기 자신의 다른 메서드를 직접 호출(`this.method()`)할 경우 프록시 계층을 경유하지 않아 트랜잭션(@Transactional), 보안, 캐싱 등 AOP 부가 기능이 동작하지 않는 치명적 결함 발생.
  - 해결 방안 : 의존성 자기 주입(Self-Injection)을 통해 프록시를 재경유하도록 리팩토링하거나, 호출 메서드를 별도의 서비스 빈(Bean)으로 분리 책임을 재할당하며, 필요 시 AspectJ 컴파일/로드타임 위빙(CTW/LTW) 적용.
- 스택 트레이스 비대화 및 디버깅 가시성 저하 :
  - 한계점 : 동적으로 생성된 프록시 인스턴스들로 인해 예외 발생 시 스택 트레이스가 과도하게 비대해져 실제 비즈니스 로직 결함의 원인 지점 추적 및 디버깅 난이도 증가.
  - 해결 방안 : 명확한 인터페이스 분리 원칙(ISP)을 준수하고, 상관 ID(Correlation ID) 기반 통합 로깅 및 프록시 실행 전후 메트릭 모니터링을 표준화하여 디버깅 가시성 확보.

## Ⅴ. 프록시 패턴 적용 시 기술사적 제언

- 성능 오버헤드와 디버깅 복잡도 완화 : 프록시 계층 추가 시 발생하는 스택 깊이 증가 및 리플렉션(Reflection) 비용을 감안하여, 성능 크리티컬한 모듈에는 컴파일 타임 위빙(AspectJ)이나 바이트코드 조작(CGLIB)을 적절히 선택.
- 순환 참조 및 프록시 우회(Self-Invocation) 주의 : 동일 클래스 내부에서 메서드를 직접 호출할 경우 프록시가 가로채지 못해 트랜잭션이나 보안 애노테이션이 누락되는 Self-Invocation 현상이 발생하므로, 구조적 분리 설계를 필히 준수해야 함.
