## 30초 인출

- 본질: 프록시 패턴(Proxy Pattern)은 실제 객체와 동일한 인터페이스를 갖는 대리 객체를 두어 접근 제어, 지연 로딩, 부가 기능을 투명하게 제공하는 구조 패턴
- 메커니즘: 클라이언트가 공통 인터페이스 규격을 통해 프록시를 호출하면, 프록시가 사전 통제 및 부가 처리 수행 후 실제 객체(RealSubject)로 요청 위임
- 통찰: 프록시 기반 횡단 관심사 처리 시 내부 메서드 자기 호출(Self-Invocation)로 인한 부가 기능 누락이 발생하므로 컴포넌트 분리 및 트랜잭션 경계 명시

<details>
<summary>핵심 용어</summary>

- **프록시 패턴(Proxy Pattern)** : 대상 객체에 직접 접근하는 대신 대리 객체를 통해 접근 통제, 지연 생성, 분산 통신을 수행하는 GoF 구조 패턴
- **Subject** : Proxy와 RealSubject가 공통으로 구현하여 클라이언트가 투명하게 호출할 수 있도록 정의한 인터페이스
- **Virtual Proxy(가상 프록시)** : 고비용 자원이나 대용량 객체의 생성을 실제 사용 시점까지 지연시키는 프록시
- **Protection Proxy(보호 프록시)** : 클라이언트의 자격증명과 권한을 확인하여 실제 객체의 메서드 실행 인가를 통제하는 프록시
- **Remote Proxy(원격 프록시)** : 네트워크 상의 서로 다른 주소 공간에 존재하는 원격 객체를 로컬 객체처럼 호출할 수 있도록 중계하는 프록시
- **Self-Invocation(자기 호출)** : 동일 클래스 내부 메서드 호출 시 프록시 객체를 거치지 않아 AOP 부가 기능이 적용되지 않는 현상

## 2~4교시 25점 답안

## Ⅰ. 프록시 패턴의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **프록시 패턴(Proxy Pattern)** 은 실제 객체와 같은 인터페이스의 대리 객체가 요청을 받아 접근 통제 및 부가 기능을 수행한 뒤 대상 객체로 위임하는 구조 패턴 |
| 목적 | 객체 접근 통제, 고비용 객체의 지연 생성, 원격 통신 은닉 및 횡단 관심사 분리 |

## Ⅱ. 프록시 패턴의 핵심 특징

| 특징 | 의미 |
|---|---|
| 인터페이스 투명성 | 프록시와 실제 객체가 동일한 인터페이스를 구현하여 클라이언트 코드 변경 배제 |
| 호출 간접화 | 클라이언트와 실제 객체 사이에 개입하여 전처리 및 후처리 제어 로직 삽입 |
| 역할과 책임 분리 | 실제 객체는 비즈니스 코어에 집중하고 프록시는 보안, 캐싱, 트랜잭션 등 인프라 관심사 전담 |

## Ⅲ. 프록시 패턴의 구조 및 주요 유형

### 프록시 패턴 클래스 및 인터페이스 구조

```text
Client ──→ [Subject Interface]
                  ▲
        ┌─────────┴─────────┐
        │                   │
[RealSubject] ←────── [Proxy]
 (실제 비즈니스 로직)   (사전/사후 처리 및 위임)
```

### 클라이언트 요청 위임 메커니즘

```text
Client: subject.request()
    ↓
Proxy: 호출 수신
    ├─ 사전 처리: 권한 검증, 캐시 조회, 트랜잭션 시작
    ├─ 캐시 적중 시 → 즉시 결과 반환
    └─ 미적중/권한 충족 시 → RealSubject.request() 실행 위임
    ↓
RealSubject: 핵심 비즈니스 로직 수행 및 결과 반환
    ↓
Proxy: 사후 처리(트랜잭션 커밋, 캐시 저장, 로깅) 후 Client 반환
```

| 프록시 유형 | 핵심 동작 메커니즘 | 실무 적용 사례 |
|---|---|---|
| 가상 프록시 (Virtual Proxy) | 객체 생성 비용이 큰 자원을 실제 사용 시점까지 지연 생성 | 이미지 지연 로딩, JPA 지연 로딩 프록시 |
| 보호 프록시 (Protection Proxy) | 클라이언트의 권한을 사전 검증하여 접근 인가 제어 | 관리자 전용 서비스 통제, 보안 인가 계층 |
| 원격 프록시 (Remote Proxy) | 원격 네트워크 통신(직렬화/역직렬화)을 로컬 호출로 은닉 | gRPC Stub, Java RMI, 분산 RPC 통신 |
| 캐싱 프록시 (Caching Proxy) | 동일 요청 파라미터에 대한 연산 결과를 인메모리에 보관 | 외부 API 연동 캐시, 대용량 연산 결과 재사용 |

## Ⅳ. 프록시 패턴과 유사 패턴 및 구현 방식 비교

### 유사 구조 패턴 비교

| 비교 항목 | 프록시 (Proxy) | 어댑터 (Adapter) | 데코레이터 (Decorator) |
|---|---|---|---|
| 핵심 의도 | 객체에 대한 **접근 제어 및 위임** | 호환되지 않는 **인터페이스 변환** | 객체에 동적인 **부가 기능 확장** |
| 인터페이스 변화 | 동일 인터페이스 유지 | 다른 대상 인터페이스로 변환 | 동일 인터페이스 유지 및 확장 |
| 객체 생성 책임 | 프록시가 내부에서 대상 생성 관리 가능 | 외부에서 변환 대상 객체 주입 | 외부에서 장식할 원본 객체 주입 |

### Spring Framework의 런타임 프록시 구현 방식

| 구분 | JDK Dynamic Proxy | CGLIB Proxy |
|---|---|---|
| 생성 메커니즘 | Java 리플렉션 패키지(`java.lang.reflect.Proxy`) 기반 | 바이트코드 조작(ASM 라이브러리) 기반 서브클래싱 |
| 적용 요건 | 대상 클래스가 반드시 인터페이스를 구현한 경우 | 인터페이스가 없는 일반 구체 클래스 대상 가능 |
| 제약 사항 | 인터페이스에 정의되지 않은 메서드 호출 불가 | 클래스나 메서드가 final인 경우 오버라이딩 불가 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 동일 클래스 내부 메서드 호출 시 프록시를 거치지 않아 트랜잭션/보안 누락(Self-Invocation) | 호출 대상 메서드를 별도 서비스 컴포넌트로 분리하거나 AspectJ 컴파일/로드타임 위빙 적용 |
| CGLIB 서브클래싱 방식 적용 시 final 클래스 및 final 메서드의 오버라이딩 차단 | 프록시 적용 대상 아키텍처 규칙 정의 및 final 키워드 사용 제한 린터 규칙 적용 |
| 가상 프록시 지연 로딩 객체 참조 시 트랜잭션 세션 종료로 인한 LazyInitializationException | 트랜잭션 범위 확장(Open Session In View) 또는 최초 쿼리 시 Fetch Join 적용 |

## Ⅵ. 제언

내부 호출 우회를 방지하기 위한 컴포넌트 책임 분리와 AOP 프록시 생성 전략의 표준화

### 내부 호출 극복을 위한 컴포넌트 아키텍처 분리 구조

```text
[클라이언트]
     ↓
[Proxy A] ──→ [OrderService]
                   │  (내부 호출 대신 별도 컴포넌트 호출)
                   ↓
             [Proxy B] ──→ [PaymentService] (트랜잭션 정상 적용)
```

### 프록시 런타임 결정 및 위빙 파이프라인

```text
컴포넌트 스캔 및 빈 정의 분석
    ↓
인터페이스 구현 여부 판정
    ├─ 인터페이스 보유 및 표준 요구 → JDK Dynamic Proxy 생성
    └─ 구체 클래스 또는 CGLIB 표준화 → CGLIB Proxy(기본) 생성
    ↓
고성능 및 특수 제약(Private 메서드 등) 요구 시
    └─ AspectJ 로드타임 위빙(LTW) 에이전트 연계
```

### 선택 근거: Spring AOP 프록시와 AspectJ 위빙 비교

| 구분 | 런타임 프록시 (Spring AOP 기본) | 제언: 컴포넌트 분리 및 프록시 표준화 |
|---|---|---|
| 동작 방식 | 런타임 대리 객체 생성 기반 중계 | 아키텍처 단위 분리 기반 런타임 프록시 활용 |
| 성능 오버헤드 | 리플렉션 및 동적 바이트코드 오버헤드 미세 발생 | 복잡한 위빙 에이전트 없이 안정적 성능 유지 |
| 복잡도 통제 | 프레임워크 자동화로 설정 용이 | 구조적 컴포넌트 분리로 설계 가독성 및 무결성 확보 |
