## 연관 키워드

- 동적 테스트(Dynamic Testing), 정적 테스트(Static Testing)
- 블랙박스·화이트박스·경험 기반 테스트, 런타임 분석(Runtime Analysis)
- 테스트 오라클(Test Oracle), DAST, 시프트 레프트(Shift-Left)

## Ⅰ. 동적 테스트의 개요

- 핵심 요약 : 소프트웨어의 실제 실행을 통해 입력 주입·출력 비교·런타임 모니터링으로 결함을 검출하는 테스팅 기법.
- 개념 : 소프트웨어를 실제 실행 환경(또는 시뮬레이터)에서 동작시키면서 다양한 입력값을 주입하고 실제 출력 결과와 예상 결과를 비교하거나 런타임 자원 소비 상태를 모니터링하여 결함을 검출하는 소프트웨어 테스팅 기법.
- 배경 및 필요성 : 코드의 외관만을 검토하는 정적 테스트(인스펙션, SAST(Static Application Security Testing))만으로는 발견할 수 없는 메모리 누수, 병목 구간, 동시성 교착상태(Deadlock), 런타임 예외의 실제 실행 기반 검증 필요.
- 주요 분류 : 명세 기반(블랙박스 테스트), 구조 기반(화이트박스 테스트), 경험 기반(탐색적 테스트, 오류 추정).

## Ⅱ. 동적 테스트의 특징

- 핵심 요약 : 실행 기반 검증, 3대 기법 분류, 런타임 분석 수반, 테스트 오라클 의존의 특성.
1. 실행 기반 검증 : 실제 환경·시뮬레이터에서의 입력 주입 및 출력 비교.
2. 명세 기반(블랙박스) : 경계값 분석, 동등분할 등 명세 중심 기법.
3. 구조 기반(화이트박스) : 문장·분기·MC/DC(Modified Condition/Decision Coverage) 커버리지 등 코드 구조 중심 기법.
4. 경험 기반 : 탐색적 테스트, 오류 추정 등 테스터 직관 활용.
5. 런타임 분석(Runtime Analysis) 수반 : 프로파일러 기반 힙 덤프·메모리 누수·스레드 경합 모니터링.
6. 테스트 오라클(Test Oracle) 의존 : 기대 결과와의 대조를 통한 합격 판정.

## Ⅲ. 동적 테스트의 구조 (흐름)

- 핵심 요약 : 환경 구축부터 합격 판정까지의 실행 프레임워크와 정적·동적 2단계 검증 체계.

```text
[ 동적 테스트 실행 프레임워크 ]
[ 테스트 환경 구축 ]
 - Mock 서버, 테스트 DB 세팅
   ↓
[ 테스트 데이터 주입 ]
 - 경계값·동등분할, 페이로드 전송
   ↓
[ 소프트웨어 실행 ]
 - 단위·통합·시스템 프로세스 구동
   ↓
[ 런타임 결과 수집 ]
 - 리턴값, 응답시간, 메모리 프로파일링
   ↓
[ 메모리·예외 분석 ]
   ↓
[ 테스트 오라클 대조 ]
   ↓
[ 합격 판정 (Pass/Fail) ]
```

```text
[ 정적 → 동적 2단계 검증 흐름 ]
소스코드
   ↓
1단계 정적 테스트 (SAST·린터·인스펙션)
 - 문법·코딩 표준·논리 결함 사전 제거
   ↓
2단계 동적 테스트 (실행 기반 검증)
 - 런타임 크래시·메모리 누수·성능·보안 검증
```

- 단위 테스트 수준의 동적 검증 : JUnit, PyTest 등을 통한 개별 메서드 실행 및 어설션(Assertion) 검증.
- 런타임 분석(Runtime Analysis) : 프로파일러(JProfiler, Valgrind)를 활용한 힙 덤프 분석, 메모리 누수 탐지, CPU(Central Processing Unit) 스레드 경합 모니터링.

## Ⅳ. 정적 테스트와 동적 테스트의 비교

- 핵심 요약 : 실행 여부·수행 시점·결함 대상·수정 비용의 축에서 상호 보완 관계.

| 비교 항목 | 정적 테스트(Static Testing) | 동적 테스트(Dynamic Testing) |
|---|---|---|
| 프로그램 실행 여부 | 코드·산출물을 실행하지 않고 검토 | 프로그램을 실제로 빌드하고 구동하여 검증 |
| 주요 수행 기법 | 인스펙션, 워크스루, SAST(정적 분석), 린터 | 블랙박스(경계값·동등분할), 화이트박스 MC/DC(Modified Condition/Decision Coverage), 부하 테스트 |
| 결함 발견 대상 | 코딩 표준 위반, 문법 오류, 논리 결함, 설계 모순 | 런타임 크래시, 메모리 누수, 인터페이스 불일치, 성능 저하 |
| 수행 시점 | 요구분석·설계·코딩 등 개발 전 생명주기 | 코드가 빌드되어 실행 가능한 단위 이후 |
| 결함 수정 비용 | 조기 발견으로 비용 극소($1x$) | 후반부 발견 시 수정 비용 급증($10x \sim 100x$) |

## Ⅴ. 동적 테스트의 장점과 한계

- 핵심 요약 : 런타임 결함 검출·실환경 검증의 강점과 환경 구축 비용·Flaky·스위트 비대의 한계 공존.
- 장점
  1. 메모리 누수·교착상태·성능 병목 등 런타임 전용 결함의 검출.
  2. 실제 사용 환경에 근접한 동작·성능·보안 검증.
  3. 사용자 시나리오 기반의 종단 간 품질 확인.
- 한계점 1 : 테스트 환경 구축 비용 및 테스트 오라클 부재(Oracle Problem)
  - 한계점 : 실제 운영 환경과 유사한 인프라·테스트 데이터·종속 서비스 모킹의 막대한 공수 소모, 복잡한 비즈니스 로직의 기대 출력값 자동 검증 한계.
  - 해결 방안 : Testcontainers 기반 컨테이너화된 인프라 자동 프로비저닝, 메타모픽 테스팅(Metamorphic Testing)·불변식(Invariant) 검증을 통한 오라클 부재 극복.
- 한계점 2 : 비결정론적 결함(Flaky Tests) 기인 파이프라인 신뢰성 저하
  - 한계점 : 네트워크 지연, 비동기 타이밍 이슈, 외부 시스템 불안정성으로 인해 코드 결함이 없음에도 간헐적 테스트 실패 반복, 개발 피드백 루프 마비.
  - 해결 방안 : 비동기 폴링 유틸리티(Awaitility) 적용, 테스트 케이스 독립성 보장을 위한 DB(Database) 롤백 격리, Flaky 테스트 자동 탐지·격리(Quarantine) 파이프라인 운영.
- 한계점 3 : 테스트 스위트 비대화에 따른 실행 시간 폭증
  - 한계점 : 시스템 규모 확장에 따른 수만 개 E2E(End-to-End)·통합 테스트의 수 시간 실행, CI/CD(Continuous Integration/Continuous Delivery) 배포 속도의 심각한 저해.
  - 해결 방안 : 테스트 영향도 분석(TIA, Test Impact Analysis) 기반 변경 코드 연관 테스트 선별 실행, 클라우드 분산 테스트 러너(Runner)를 통한 대규모 병렬 분할 실행.

## Ⅵ. 엔터프라이즈 환경에서의 기술사적 제언

- 핵심 요약 : 정적·동적 테스트의 유기적 결합과 DAST의 파이프라인 연계.
- 정적 테스트와 동적 테스트의 유기적 결합(시프트 레프트) : 동적 테스트 편중의 디버깅 비용 증가 방지, 정적 분석(SAST)으로 기계적 결함을 사전 최대한 제거한 후 비즈니스 로직·복합 통합 시나리오에 동적 테스트 역량을 집중하는 2단계 검증 체계 구축.
- 동적 애플리케이션 보안 테스팅(DAST, Dynamic Application Security Testing)의 파이프라인 연계 : 기능 검증 국한 탈피, 실운영과 동일한 스테이징 환경에서 OWASP(Open Worldwide Application Security Project) ZAP 등을 활용한 DAST 자동 구동, SQL(Structured Query Language) 인젝션, XSS(Cross-Site Scripting), CSRF(Cross-Site Request Forgery) 등 런타임 웹 취약점의 선제 차단.

## Ⅶ. 결론

- 핵심 요약 : 동적 테스트는 정적 테스트만으로는 담보 불가능한 런타임 품질·보안의 최종 검증선.
- 요약 : 실행 기반 입력 주입·출력 대조·런타임 분석으로 명세·구조·경험 3대 기법을 아우르는 검증 체계.
- 시사점 : 정적 분석 선제 제거와 동적 검증 집중의 2단계 체계, DAST 자동화 결합으로 전 주기 품질·보안 확보 필요.
