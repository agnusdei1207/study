## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 테스트 및 품질 → 소프트웨어 테스팅 → **동적 테스트(Dynamic Testing)**

## 30초 인출

- 본질: 소프트웨어를 실제 런타임 환경에서 직접 실행하여 입력값에 따른 출력 결과, 메모리/CPU 자원 사용량, 응답 지연 시간 등 관찰 가능한 동작을 테스트 오라클과 대조하여 결함을 검출하는 활동
- 메커니즘: 테스트 환경 구축 → 테스트 데이터 인가 및 프로그램 실행 → 실제 출력(Actual Result)과 테스트 오라클(Expected Result) 비교 → 결함 로깅 및 통과 여부 판정
- 통찰: 단순 기능 실행만으로는 메모리 누수와 동시성 경합 결함을 놓치기 쉬우므로 프로파일러 및 APM 도구를 결합한 비기능 런타임 동적 분석 병행 필수

<details>
<summary>핵심 용어</summary>

- **Dynamic Testing(동적 테스트)** : 소프트웨어를 메모리에 적재하고 실제로 CPU 프로세서를 실행시켜 동작과 동작 결과를 검증하는 테스트 활동
- **Static Testing(정적 테스트)** : 소스코드를 실행하지 않고 문서 검토(인스펙션, 워크스루)나 정적 분석 도구(SAST)로 결함을 찾는 활동
- **Test Oracle(테스트 오라클)** : 테스트 수행 결과가 참인지 거짓인지를 판단하기 위해 사전에 정의된 기대 출력값 또는 판정 메커니즘
- **Specification-Based (블랙박스)** : 소스코드 내부 구조를 참조하지 않고 요구사항 명세서와 입출력 계약만을 바탕으로 테스트 케이스를 설계하는 기법
- **Structure-Based (화이트박스)** : 프로그램의 내부 제어 흐름 그래프(CFG), 구문, 분기, 조건을 분석하여 코드 커버리지를 측정하는 테스트 기법
- **Experience-Based (경험 기반)** : 테스터의 직관과 과거 결함 데이터, 도메인 지식을 바탕으로 오류 추정 및 탐색적 테스팅을 수행하는 기법

</details>

## 2~4교시 25점 답안

## Ⅰ. 동적 테스트의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 컴포넌트나 시스템을 실제 하드웨어/OS 환경에서 구동시켜, 정의된 입력값에 대한 실제 동작과 출력값을 테스트 오라클(기대값)과 비교 평가하는 테스트 활동 |
| 목적 | 런타임 기능 결함 식별, 성능/자원 병목 측정, 외부 시스템과의 인터페이스 통합 검증 및 운영 환경 적합성 확인 |

## Ⅱ. 동적 테스트의 핵심 특징

| 특징 | 의미 |
|---|---|
| 실제 코드 실행 필수 | CPU 프로세서, 메모리 스택/힙, 네트워크 I/O가 실제로 작동하는 상태에서만 결함 검출 가능 |
| 테스트 오라클 의존성 | 실제 출력(Actual)과 비교할 명확한 기준(참 오라클, 샘플링 오라클, 휴리스틱 오라클) 필수 |
| 런타임 품질 특성 계측 | 기능 동작뿐만 아니라 응답 시간, 처리량, 메모리 누수, 동시성 교착 상태(Deadlock) 측정 가능 |
| 4단계 테스트 레벨 연계 | 단위 테스트(Unit)부터 통합(Integration), 시스템(System), 인수(Acceptance)까지 전 단계 적용 |

## Ⅲ. 동적 테스트 수행 체계 및 결과 판정 프로세스

### 동적 테스트 전주기 실행 파이프라인

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1단계: 테스트 계획 및 환경 구축 (Setup)                                 │
│   - 대상 컴포넌트 빌드 및 배포 (Docker/K8s 테스트베드)                 │
│   - 테스트 데이터셋 준비 (정상값, 경계값, 비정상 에러값)               │
│   - 테스트 오라클 정의 (기대 JSON 스키마, DB 상태, HTTP 200 등)        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2단계: 테스트 입력 인가 및 실행 (Execution)                            │
│   - 테스트 러너(JUnit, pytest, Postman, k6)를 통한 입력값 주입          │
│   - 소프트웨어 실제 구동 및 CPU/메모리/네트워크 프로파일링 동시 수행   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3단계: 관찰 및 테스트 오라클 비교 판정 (Oracle Verification)           │
│                                                                        │
│   [실제 실행 결과 (Actual)]  vs  [테스트 오라클 (Expected)]            │
│         │                                                              │
│         ├─ 일치 (Match) ───→ [PASS 판정] → 테스트 리포트 등록          │
│         │                                                              │
│         └─ 불일치 (Mismatch) → [FAIL 판정] ──→ 4단계 결함 로깅 진행     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 결함 식별 시
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4단계: 결함 분석 및 리포팅 (Defect Logging)                            │
│   - 입력값, 실행 환경 버전, 스택 트레이스, 서버 에러 로그 첨부         │
│   - Jira 결함 티켓 자동 발행 → 개발팀 디버깅 및 핫픽스 요청            │
└────────────────────────────────────────────────────────────────────────┘
```

### 테스트 오라클(Test Oracle) 4대 유형

| 오라클 유형 | 정의 및 특징 | 적용 사례 |
|---|---|---|
| **참 오라클 (True Oracle)** | 모든 입력에 대해 완벽한 절대적 기대값을 제공하는 오라클 | 미션 크리티컬 항공 제어, 금융 이자 계산 로직 |
| **샘플링 오라클 (Sampling)** | 모든 값이 아닌 특정 주요 입력 샘플에 대해서만 기대값을 사전 산출 | 대규모 입력 도메인을 가진 수치 해석 알고리즘 |
| **휴리스틱 오라클 (Heuristic)** | 통계적 근사치나 추정 규칙을 기반으로 출력의 유효성을 판정 | 머신러닝 분류 모델, 복잡한 게임 AI 동작 검증 |
| **일관성 검사 오라클 (Consistent)**| 이전 버전의 실행 결과와 새 버전의 결과를 비교하여 일치성 판정 | 레거시 마이그레이션 회귀 테스트, 회귀 시험 |

## Ⅳ. 정적 테스트 vs 동적 테스트 및 동적 테스트 3대 설계 기법

### 정적 테스트와 동적 테스트 비교

| 비교 항목 | 정적 테스트 (Static Testing) | 동적 테스트 (Dynamic Testing) |
|---|---|---|
| **코드 실행 여부** | **프로그램을 실행하지 않음** | **실제 환경에서 프로그램을 실행함** |
| **테스트 대상** | 요구사항 명세서, 아키텍처 설계서, 소스코드 | 빌드된 실행 바이너리, 배포된 서비스 API |
| **주요 활동** | 인스펙션, 워크스루, SAST 정적 코드 린팅 | 단위/통합 테스트, 부하 테스트, DAST 동적 침투 |
| **결함 발견 시점** | 개발 초기 단계 (Shift-Left) | 구현 후 컴파일 및 빌드 단계 이후 |
| **발견 결함 유형** | 코딩 표준 위반, 구문 오류, 보안 취약점 패턴 | 런타임 널 포인터, 메모리 누수, 성능 병목, 연동 오류 |

### 동적 테스트 3대 설계 관점 비교

| 설계 관점 | 핵심 원리 및 기법 | 주요 장점 | 한계점 |
|---|---|---|---|
| **명세 기반 (블랙박스)** | 동등 분할, 경계값 분석, 결정 테이블, 상태 전이 | 코드 몰라도 설계 가능, 사용자 관점 검증 | 구현 내부의 데드 코드나 숨은 경로 미검출 |
| **구조 기반 (화이트박스)** | 구문 커버리지, 분기 커버리지, MC/DC, 기본 경로 | 코드 실행 경로 100% 추적, 논리 오류 검출 | 요구사항 누락 결함(스펙 미구현) 감지 불가 |
| **경험 기반 (직관/탐색)** | 에러 추정(Error Guessing), 탐색적 테스팅(ET) | 문서 부족 시 신속한 결함 발굴, 에지 케이스 검출 | 테스터 개인 역량 편차 심함, 재현성 부족 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 런타임 환경 구성(DB, 외부 API) 미비로 인해 개발 초기 동적 테스트 착수 지연 | WireMock, Testcontainers 등 격리된 컨테이너 가상화 도구를 활용한 모의 환경 구축 |
| 동적 테스트 실행 시 테스트 데이터의 오염으로 인해 후속 테스트가 연쇄 실패하는 현상 | 테스트 메서드마다 트랜잭션 롤백(`@Transactional`) 및 테스트 DB 자동 초기화 강제 |
| 단순 기능 합격 여부만 판정하고 백그라운드 메모리 누수(Memory Leak)를 간과 | 테스트 실행 중 JVM 힙 덤프 및 Valgrind 메모리 프로파일러를 CI 파이프라인에 결합 |

## Ⅵ. 제언

CI/CD 파이프라인 연계 전주기 동적 테스트 자동화 및 카나리 배포 기반 실운영 동적 검증

### CI/CD 전주기 동적 테스트 자동화 파이프라인

```text
[개발자 코드 푸시]
       ↓
[CI 파이프라인: Phase 1 동적 단위 테스트]
  ├─ JUnit 5 / Mockito 고속 실행 (500건, 30초 컷)
  └─ Jacoco: 라인 커버리지 80% 미달 시 즉시 빌드 실패
       ↓
[CI 파이프라인: Phase 2 컨테이너 통합 테스트]
  ├─ Testcontainers로 실제 PostgreSQL, Redis 컨테이너 기동
  └─ Spring Boot 통합 슬라이스 테스트 실행
       ↓
[CD 파이프라인: Phase 3 E2E 시스템 테스트]
  ├─ 스테이징 환경 배포 후 Playwright UI 자동화 시나리오 실행
  └─ k6 부하 테스트 (1,000 VUs 동시 접속 성능 측정)
       ↓
[프로덕션 카나리 배포 후 실시간 헬스체크 및 APM 관측]
```

### 테스트 기법 조합 의사결정 체계

```text
동적 테스트 설계 착수
       ↓
[소스코드 열람이 가능하고 내부 로직 완전성이 요구되는가?]
       ├─ 예 ──→ 구조 기반 (화이트박스) 테스팅 채택 (분기/조건 커버리지)
       └─ 아니오 ─→ [명확한 SRS 요구사항 및 입출력 명세가 존재하는가?]
                         ├─ 예 ──→ 명세 기반 (블랙박스) 테스팅 채택 (동등분할/경계값)
                         └─ 아니오 ─→ 경험 기반 탐색적 테스팅(Exploratory) 즉시 투입
```

### 선택 근거: 전통적 수동 동적 테스트와 제언 자동화 파이프라인 비교

| 구분 | 전통적 수동 동적 테스트 (Manual QA) | 제언: CI/CD 자동화 동적 테스트 |
|---|---|---|
| 테스트 주기 | 개발 완료 후 몰아서 수행 (수일~수주 소요) | 코드 커밋 시마다 상시 자동 수행 (수 분 내 완료) |
| 재현성 | 테스터마다 입력 순서 차이로 결함 재현 곤란 | 정형화된 테스트 코드로 100% 동일한 환경 재현 |
| 비용 효율 | 프로젝트 후반부로 갈수록 인건비 지출 기하급수적 증가 | 초기 스크립트 작성 후 추가 비용 없이 무제한 실행 |
