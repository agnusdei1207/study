| 서브토픽 | 핵심 키워드 | 답안 차별화 포인트 |
|---|---|---|
| 정적 테스트 vs 동적 테스트 | 실행 여부(Non-execution vs Execution), 리뷰/인스펙션, 런타임 오류(OOM/데드락) | 결함의 근본 원인(Fault) 제거와 런타임 고장(Failure) 검출의 상호보완 관계 강조 |

## 1. 동적 테스트의 개요 및 필요성

### (1) 동적 테스트(Dynamic Testing)의 정의
- 소프트웨어를 **실제 컴퓨터 환경에서 실행(Execution)하면서 입력값에 따른 실제 출력값과 기대 결과를 비교하여 결함을 검출하고 비기능 품질 속성을 평가하는 테스트 기법**.
- 정적 분석으로는 파악할 수 없는 런타임 메모리 누수, 동시성 교착상태(Deadlock), 응답 지연 등 동적 거동을 검증함 (137회 2교시 기출).

### (2) 동적 테스트의 핵심 특징
1. **실행 환경 의존성**: OS, 미들웨어, DB, 하드웨어 사양 등 실제 런타임 인프라와 결합하여 수행.
2. **고장 증상(Failure) 포착**: 소스코드의 문법적 오류가 아닌, 시스템 동작 중 표출되는 비정상적 장애를 직접 관측.
3. **테스트 데이터 및 오라클 필수**: 입력값과 이를 검증할 기대값(Test Oracle)이 사전에 정의되어야 함.

## 2. 동적 테스트의 분류 체계 및 핵심 기법

### (1) 동적 테스트 분류 구조도
```text
+-------------------------------------------------------------------------+
|                  동적 테스트(Dynamic Testing) 분류 체계                  |
+-------------------------------------------------------------------------+
|                    [ 대상 시스템 실제 구동 (Execution) ]                 |
|                                    │                                    |
|         ┌──────────────────────────┼──────────────────────────┐         |
|         v                          v                          v         |
|  [ 1. 화이트박스 (구조) ]    [ 2. 블랙박스 (명세) ]    [ 3. 경험 기반 ] |
|  - 내부 로직/코드 경로 검증  - 요구사항 입출력 검증    - 테스터 직관/노하우     |
|  - 구문/분기/MC-DC 커버리지  - 동등분할, 경계값 분석   - 오류 추정, 탐색적 테스트
|                                                                         |
|      ▲                              ▲                         ▲         |
|      │                              │                         │         |
|  [ 단위 테스트 ]            [ 통합 테스트 ]           [ 시스템/인수 ]   |
+-------------------------------------------------------------------------+
```

### (2) 세부 기법별 핵심 내용 비교
| 분류 | 대표 기법 | 검증 초점 및 특징 | 주요 적용 단계 |
|---|---|---|---|
| **화이트박스 (구조 기반)** | 구문(Statement), 분기(Branch), 조건(Condition), MC/DC 커버리지 | 소스코드의 제어 흐름과 실행 경로를 100% 탐색하여 미실행 데드 코드 색출 | 단위 테스트 (Unit Test) |
| **블랙박스 (명세 기반)** | 동등 분할(EP), 경계값 분석(BVA), 원인-결과 그래프, 상태 전이 | 내부 코드를 모른 채 요구명세에 정의된 입력 대비 올바른 출력 산출 검증 | 시스템/통합 테스트 |
| **경험 기반 (직관 기반)** | 오류 추정(Error Guessing), 탐색적 테스팅(Exploratory Testing) | 정형화된 명세로 잡기 힘든 테스터의 경험과 과거 장애 이력 기반 결함 사냥 | 인수 테스트, 버그 바운티 |
| **비기능 동적 테스트** | 부하 테스트(Load), 스트레스(Stress), 침투 테스트(Penetration) | 동시 접속자 폭증 시 시스템 처리량(TPS), 메모리 누수, 자원 한계 측정 | 성능 및 보안 검증 단계 |

## 3. 정적 테스트(Static) vs 동적 테스트(Dynamic) 상세 비교

| 비교 항목 | 정적 테스트 (Static Testing) | 동적 테스트 (Dynamic Testing) |
|---|---|---|
| **실행 여부** | **소프트웨어를 실행하지 않음** (Non-Execution) | **소프트웨어를 직접 실행함** (Execution) |
| **대상 산출물** | 요구정의서, 아키텍처 설계서, 소스코드 텍스트 | 컴파일된 바이너리, 실행 모듈, 컨테이너 인스턴스 |
| **수행 기법** | 워크스루, 인스펙션, 동료검토, SAST 정적 분석 | 화이트박스/블랙박스 테스트, DAST, 성능 부하 테스트 |
| **검출 결함** | 표준 위반, 문법 오류, 논리적 결함, 설계 누락, 보안 취약점 | 런타임 메모리 누수, 무한 루프, 동시성 경합, 성능 저하 |
| **결함 수정 비용** | **매우 저렴 (초기 단계 즉각 수정, Shift-Left)** | 상대적으로 고비용 (통합/운영 환경 결함 격리 필요) |
| **테스트 오라클** | 불필요 (표준 규격 및 코딩 룰 대조) | **필수 (사전 정의된 기대 결과와 실측값 대조)** |

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **정적 분석 100% 통과 후 실운영 시 OOM 다운**<br>(서버 기동 2시간 만에 메모리 고갈) | 정적 분석 린터로 탐지 불가능한 JDBC 커넥션 미반환 및 캐시 객체 누수 | k6 부하 생성기와 VisualVM 프로파일러를 연동한 24시간 내구 동적 테스트(Soak Test) 수행 | 런타임 메모리 누수 배포 전 100% 사전 색출 |
| **외부 연계망 장애로 테스트 파이프라인 정지**<br>(결제 PG사 통신 두절 시 전체 빌드 실패) | 외부 실서버에 직접 의존하는 취약한 동적 통합 테스트 환경 구성 | WireMock 및 Testcontainers 기반 격리 모킹(Mocking) 환경 구축 | 외부 환경과 무관한 동적 테스트 멱등성 100% 확보 |
| **GUI 수동 동적 테스트로 릴리스 3주 지연**<br>(매 배포마다 화면 수백 개 수동 클릭) | 자동화 없는 화면 중심 수동 블랙박스 테스트에만 전적으로 의존 | 테스트 피라미드 재편(단위 동적 테스트 자동화 70% + E2E 10% 자동화) | 회귀 동적 검증 소요 시간 3주에서 15분으로 단축 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[정적·동적 분리 운영 (단절적 검증)]         [지속적 품질 보증 (Continuous Testing 파이프라인)]
- 개발 끝난 후 막판에 동적 테스트 몰아서 수행 ──▶  - PR 단계 정적 SAST 즉각 실행 (초기 결함 차단)
- 결함 원인 파악에 막대한 디버깅 비용 소모   ──▶  - CI 파이프라인 내 단위/통합 동적 테스트 자동화
- 기능 테스트와 성능/보안 테스트의 분리       ──▶  - Testcontainers 기반 런타임 가상화 및 DAST 통합
```

- **정적 테스트와 동적 테스트의 상호보완적 결합**: 정적 테스트는 "결함의 원인(Fault)"을 조기에 싸게 잡고, 동적 테스트는 "런타임 고장(Failure)"을 현실적으로 입증함. 둘 중 하나만으로는 완벽한 품질을 보장할 수 없으므로, **정적 린터(SonarQube) $\rightarrow$ 동적 단위 테스트(JUnit) $\rightarrow$ 동적 DAST/부하 테스트(k6)**로 이어지는 연속적 품질 파이프라인을 구축해야 함.
- **테스트 환경 격리와 컨테이너 기반 멱등성**: 현대 동적 테스트의 성패는 "언제 어디서 실행해도 동일한 결과를 내는가(결정론)"에 달려 있음. 클라우드 네이티브 환경에서는 **Testcontainers**를 활용해 임시 데이터베이스와 카프카 메시지 브로커를 컨테이너로 띄워 동적 테스트를 수행하고 즉시 파기하는 격리 아키텍처가 기술사의 핵심 실무 솔루션임.
