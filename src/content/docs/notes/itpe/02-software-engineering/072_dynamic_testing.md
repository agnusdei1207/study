## Ⅰ. 동적 테스트의 개요

- **개념** : 소프트웨어를 실제 실행 환경(또는 시뮬레이터)에서 동작시키면서, 다양한 입력값을 주입하고 실제 출력 결과와 예상 결과를 비교하거나 런타임 자원 소비 상태를 모니터링하여 결함을 검출하는 소프트웨어 테스팅 기법.
- **배경 및 필요성** : 코드의 외관만을 검토하는 정적 테스트(인스펙션, SAST)만으로는 발견할 수 없는 메모리 누수, 병목 구간, 동시성 교착상태(Deadlock), 런타임 예외를 실제 실행을 통해 검증.
- **핵심 분류** : 명세 기반(블랙박스 테스트), 구조 기반(화이트박스 테스트), 경험 기반(탐색적 테스트, 오류 추정).

## Ⅱ. 동적 테스트의 실행 프레임워크 및 프로세스

```text
   [ 테스트 환경 구축 ] ──> [ 테스트 데이터 주입 ] ──> [ 소프트웨어 실행 ] ──> [ 런타임 결과 수집 ]
    - Mock 서버 준비         - 경계값/동등분할          - 단위/통합/시스템        - 리턴값, 응답시간
    - 테스트 DB 세팅          - 페이로드 전송             실제 프로세스 구동       - 메모리 프로파일링
                                                                                   │
                                                                                   ▼
   [ 합격 판정 (Pass/Fail) ] <── [ 테스트 오라클 대조 ] <── [ 메모리/예외 분석 ] <──┘
```

- **단위 테스트 수준의 동적 검증** : JUnit, PyTest 등을 통한 개별 메서드 실행 및 어설션(Assertion) 검증.
- **런타임 분석 (Runtime Analysis)** : 프로파일러(JProfiler, Valgrind)를 활용한 힙 덤프 분석, 메모리 누수 탐지, CPU 스레드 경합 모니터링.

## Ⅲ. 정적 테스트와 동적 테스트의 비교

| 비교 항목 | 정적 테스트 (Static Testing) | 동적 테스트 (Dynamic Testing) |
|---|---|---|
| 프로그램 실행 여부 | 코드 및 산출물을 실행하지 않고 검토 | 프로그램을 실제로 빌드하고 구동하여 검증 |
| 주요 수행 기법 | 인스펙션, 워크스루, SAST(정적 분석), 린터 | 블랙박스(경계값/동등분할), 화이트박스(MC/DC), 부하 테스트 |
| 결함 발견 대상 | 코딩 표준 위반, 문법 오류, 논리 결함, 설계 모순 | 런타임 크래시, 메모리 누수, 인터페이스 불일치, 성능 저하 |
| 수행 시점 | 요구분석, 설계, 코딩 등 개발 전 생명주기 | 코드가 빌드되어 실행 가능한 단위 이후 |
| 결함 수정 비용 | 조기 발견으로 비용 극소 ($1x$) | 후반부 발견 시 수정 비용 급증 ($10x \sim 100x$) |

## Ⅳ. 엔터프라이즈 환경에서의 기술사적 제언

- **정적 테스트와 동적 테스트의 유기적 결합(시프트 레프트)** : 동적 테스트에만 전적으로 의존하면 디버깅 비용이 크게 증가하므로, 정적 분석(SAST)으로 기계적 결함을 사전에 100% 제거한 후 비즈니스 로직과 복합 통합 시나리오에 동적 테스트 역량을 집중하는 2단계 검증 체계 구축.
- **동적 애플리케이션 보안 테스팅(DAST)의 파이프라인 연계** : 기능 검증에 국한되지 않고, 실운영과 동일한 스테이징 환경에서 OWASP ZAP 등을 활용한 DAST를 자동 구동하여 SQL 인젝션, XSS, CSRF 등 런타임 웹 취약점을 선제 차단해야 함.
