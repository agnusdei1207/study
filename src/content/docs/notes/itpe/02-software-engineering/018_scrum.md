## 연관 키워드

- Scrum, 스프린트(Sprint), 경험적 프로세스 통제
- Product Owner, Scrum Master, Developers, 제품 백로그, 스프린트 백로그, 증분, Definition of Done

## Ⅰ. 스크럼의 개요

- 핵심 요약 : 스크럼은 고정 길이의 스프린트와 경험적 통제로 복잡한 제품 개발을 반복·적응하는 경량 프레임워크.
- 개념 : 투명성·점검·적응의 **경험적 프로세스 통제**(Empirical Process Control)를 바탕으로, 고정 주기의 **스프린트**(Sprint)마다 동작 가능한 **증분**(Increment)을 산출하는 경량 프레임워크인 **Scrum**.
- 배경 및 필요성 : 요구·기술의 불확실성이 큰 개발에서 선행 계획 확정과 순차 단계 진행은 변화 반영이 늦고 위험이 후반부에 집중되는 문제.
- 주요 목적 : 짧은 피드백 주기로 제품 가치를 조기·반복 전달하고 계획과 제품 목표를 적응적으로 조정.

## Ⅱ. 스크럼의 특징 및 장점

- 핵심 요약 : 세 역할·다섯 이벤트·세 산출물의 구조(3-5-3)가 짧은 검증 주기와 명확한 책임으로 연결.

1. 경험적 통제 : 투명성 확보 → 스프린트 단위 점검 → 계획·제품의 적응 → 변화 대응력과 위험 조기 발견.
2. 역할 분담 : **제품 책임자**(Product Owner, PO)가 제품 가치·우선순위를 책임지고, **스크럼 마스터**(Scrum Master)가 프로세스와 장애물 제거를 지원하며, **개발팀**(Developers)이 실제 작업을 수행 → 의사결정 지연 완화.
3. 자기관리 팀 : 개발팀이 작업 분할·방법·범위를 스스로 결정 → 책임감과 생산성 향상.
4. 산출물-약속 구조 : **제품 백로그**(Product Backlog)·**스프린트 백로그**(Sprint Backlog)·증분의 세 산출물이 각각 제품 목표·스프린트 목표·**완료 기준**(DoD, Definition of Done)과 묶임 → 목표 정렬과 품질 보증 기준 명확.

## Ⅲ. 스크럼의 구조 (흐름)

- 핵심 요약 : 제품 백로그에서 출발해 스프린트 계획·실행·리뷰·회고로 이어지는 고정 주기의 반복 구조.

```text
제품 목표와 제품 백로그
   ↓ 우선순위 반영
스프린트 계획 : 스프린트 목표·작업 선정
   ↓
스프린트 실행 + 일일 스크럼
   ↓
완료 기준(DoD)을 충족한 증분
   ↓
스프린트 리뷰(제품 검증)
   ↓
스프린트 회고(프로세스 개선)
```

```text
[ 산출물과 약속 ]
제품 백로그     → 제품 목표(Product Goal)
스프린트 백로그 → 스프린트 목표(Sprint Goal)
증분            → 완료 기준(DoD)
```

- 이벤트 구성 : 스프린트(전체 컨테이너)와 그 안의 네 이벤트.

  1. 스프린트 계획(Sprint Planning) : 스프린트 목표·작업 선정.
  2. 일일 스크럼(Daily Scrum) : 일일 계획 점검·조정.
  3. 스프린트 리뷰(Sprint Review) : 증분과 제품 백로그 검토.
  4. 스프린트 회고(Sprint Retrospective) : 팀·프로세스 개선.

- 보조 기준 : DEEP(Detailed appropriately, Estimated, Emergent, Prioritized)은 제품 백로그 관리 특성의 실무 가이드, INVEST(Independent, Negotiable, Valuable, Estimable, Small, Testable)는 사용자 스토리 품질 점검 기준으로, Scrum Guide의 필수 규칙과는 구분되는 보조 휴리스틱.

## Ⅳ. 스크럼과 워터폴 모형의 비교

- 핵심 요약 : 스크럼은 스프린트 반복 중 지속 검증, **워터폴 모형**(waterfall model)은 단계 순차 진행이 핵심 차이.

| 비교 축 | 스크럼 | 워터폴 모형 |
| --- | --- | --- |
| 진행 방식 | 스프린트 단위 반복·점증 전달 | 요구→설계→구현→시험 순차 단계 |
| 요구 확정 시점 | 반복 속에서 지속 명확화 | 초기 일괄 확정 |
| 피드백 시점 | 스프린트마다 이해관계자 검증 | 인도 이후 집중 검증 |
| 변경 수용 | 백로그 재조정으로 반영 | 변경 절차·비용 부담 큼 |
| 적합 상황 | 불확실성·변화가 큰 제품 개발 | 요구가 안정적·명확한 개발 |

## Ⅴ. 스크럼의 한계와 방안

- 핵심 요약 : 이벤트 형식화·PO 병목·지표 오용은 경험주의를 훼손하므로 제품 권한과 완료 기준 중심의 운영 필요.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 이벤트 형식화 | 점검·적응 없는 의례적 수행 → 학습·개선 부재 | 이벤트별 목적·결정·후속조치 점검 | 개선 항목 이행률 |
| PO 권한·가용성 부족 | 우선순위 결정 지연·백로그 품질 저하 | PO 권한 보장·대리 의사결정 원칙 명문화 | 우선순위 결정 지연일 |
| 속도 지표 오용 | 팀 간 속도 비교·목표화 → 추정 부풀림·품질 저하 | 속도를 팀 내부 계획 도구로 한정 | 결함률·재작업률 |
| 완료 기준 미준수 | 미완성 작업 누적 → 기술부채 증가 | DoD 준수 검증·증분 인수 강화 | 미완성 항목 수 |

## Ⅵ. 스크럼에 대한 제언

- 핵심 요약 : 제품 권한 보장과 완료 기준 표준화를 조직 차원의 도입·확산 과제로 설정.
- 경영진 : PO에게 우선순위·배포 결정 권한과 전담 시간을 보장하고 팀의 외부 의존을 제거.
- 스크럼 마스터 : 이벤트가 학습·장애물 제거로 이어지는지 코칭하고 조직의 애자일 역량을 확산.
- 조직 : DoD·품질 기준을 표준화하고 스프린트 결과를 제품 목표·비즈니스 성과와 연계 평가.

## Ⅶ. 결론

- 핵심 요약 : 스크럼은 경험적 학습을 가능하게 하는 최소 규칙 집합으로, 효과는 규칙 준수가 아니라 완성된 증분과 검증된 가치에서 발생.
