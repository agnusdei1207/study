## 연관 키워드

- EJB, EJB 컨테이너, 세션 빈, 메시지 구동 빈
- 컨테이너 관리 트랜잭션(CMT), POJO, JPA

## Ⅰ. EJB의 개요

- 핵심 요약 : **EJB**(Enterprise JavaBeans)는 컨테이너가 트랜잭션·보안·수명 주기 등 시스템 서비스를 대행하는 표준 서버 측 컴포넌트 모델.
- 개념 : Java 엔터프라이즈 환경에서 비즈니스 컴포넌트를 컨테이너에 배포하고 트랜잭션·보안·동시성·수명 주기 서비스를 표준 계약으로 제공받는 서버 측 컴포넌트 모델.
- 배경 및 필요성 : 분산 처리·트랜잭션·보안 같은 공통 기능의 응용별 직접 구현은 중복·불일치·결함 증가 → 표준 컴포넌트 계약 필요.
- 주요 목적 : 업무 로직과 시스템 서비스의 분리, 표준 기반의 트랜잭션성·보안성·확장성 확보.

## Ⅱ. EJB의 특징 및 장점

- 핵심 요약 : 컨테이너의 선언적 서비스와 표준 컴포넌트 유형이 기반 기능 구현 부담을 감소.

1. **EJB 컨테이너**(EJB Container, 빈의 수명 주기·풀링·보안·트랜잭션을 대행하는 실행 환경) : 컴포넌트 호출의 가로채기와 공통 서비스 적용 → 개발자의 비즈니스 로직 집중.
2. **세션 빈**(Session Bean, 동기 호출 업무 서비스를 구현하는 빈) : Stateless·Stateful·Singleton 유형의 상태 범위 선택 → 처리 형태에 맞는 컴포넌트 구성.
3. **메시지 구동 빈**(MDB, Message-Driven Bean) : **JMS**(Java Message Service, 자바 표준 메시징 인터페이스) 메시지의 비동기 수신·처리 → 시스템 간 느슨한 결합.
4. **컨테이너 관리 트랜잭션**(CMT, Container-Managed Transaction) : 애노테이션 기반 트랜잭션 경계·롤백 규칙 선언 → 트랜잭션 제어 코드의 중복 제거.
5. 영속성 표준 연계 : 데이터 접근을 **JPA**(Java Persistence API, 자바 표준 객체·관계 매핑 영속성 인터페이스)로 분리 → 영속성 계층의 독립성.

## Ⅲ. EJB의 구조 (흐름)

- 핵심 요약 : 클라이언트 호출·메시지 수신을 컨테이너가 중개하고 보안·트랜잭션 서비스 아래 빈의 업무 로직 실행.

```text
[ EJB 호출·서비스 흐름 ]

클라이언트 호출 / 메시지 수신
   ↓
EJB 컨테이너 (인증·인가·트랜잭션·풀링)
   ↓
세션 빈 / 메시지 구동 빈 실행
   ↓
JPA 영속성 처리·외부 자원 연계
   ↓
커밋·롤백 후 응답 반환
```

```text
[ EJB 컴포넌트 유형 ]

세션 빈 (동기 업무 서비스)
  - Stateless : 상태 없음·풀링 재사용
  - Stateful : 클라이언트별 상태 유지
  - Singleton : 응용 단위 단일 인스턴스
메시지 구동 빈 (비동기 메시지 소비)
```

## Ⅳ. EJB와 POJO 기반 경량 프레임워크 컴포넌트의 비교

- 핵심 요약 : 표준 컨테이너 계약의 EJB와 일반 객체 기반의 경량 프레임워크 컴포넌트는 서비스 제공 방식·실행 환경·시험 부담에서 차이.
- 구성 대상 : EJB는 표준 명세의 컴포넌트 계약을 따르고, **POJO**(Plain Old Java Object, 프레임워크 종속 없이 작성한 일반 Java 객체) 기반 컴포넌트는 프레임워크 설정으로 서비스를 조합.

| 비교 축 | EJB | POJO 기반 경량 프레임워크 컴포넌트 |
| --- | --- | --- |
| 컴포넌트 계약 | 표준 명세의 애노테이션·인터페이스 준수 | 일반 객체·프레임워크 설정의 조합 |
| 시스템 서비스 | 컨테이너의 트랜잭션·보안·풀링 보장 | 프레임워크 기능의 선택적 적용 |
| 실행 환경 | Jakarta EE 애플리케이션 서버 | 서블릿 컨테이너·임베디드 런타임 등 유연 |
| 단위 시험 | 컨테이너 서비스 재현 부담 | POJO 수준의 경량 시험 용이 |
| 이식성 | 명세 호환 서버 간 표준 이식성 | 프레임워크 버전·생태계 의존 |

## Ⅴ. EJB의 한계와 방안

- 핵심 요약 : 컨테이너 결합·원격 호출 부담·시험 복잡성을 로직 분리·경계 설계·시험 분리로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 컨테이너·API 결합 | 업무 로직의 컨테이너 계약 의존 → 전환 비용 증가 | 도메인 규칙의 POJO 분리·경계 인터페이스 명시 | 컨테이너 종속 코드 비율 |
| 원격 호출 부담 | 분산 호출의 지연·실패 전파 | 거친 서비스 경계·배치 호출·타임아웃 설계 | 호출 지연·실패율 |
| 시험·운영 복잡성 | 컨테이너 기동·설정 의존의 시험 환경 | 핵심 규칙 단위 시험과 컨테이너 통합 시험의 분리 운영 | 통합 시험 실패율 |

## Ⅵ. EJB의 제언

- 핵심 요약 : 플랫폼 조직은 표준 플랫폼 자산과 경량 기술의 적용 경계를 원칙으로 정하고 업무 로직의 기술 독립성을 정책으로 유지.

1. 플랫폼 운영 조직은 지원 애플리케이션 서버·명세 버전·패치 정책의 표준화.
2. 아키텍처 조직은 신규 서비스 기술 선택 기준(표준성·기존 자산·확장 요구)의 수립.
3. 현대화 추진 조직은 전면 전환 대신 도메인 계층 재정리와 단계적 이관 전략의 채택.

## Ⅶ. EJB의 결론

- 핵심 요약 : EJB는 컨테이너가 시스템 서비스를 표준 계약으로 제공하는 서버 측 컴포넌트 모델.
- 시사점 : 표준 컨테이너 서비스의 생산성과 실행 환경·시험 부담의 균형이 도입 판단의 기준.
