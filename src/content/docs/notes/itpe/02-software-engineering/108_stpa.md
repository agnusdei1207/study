## Ⅰ. STPA의 개요

- **개념** : MIT의 낸시 레브슨(Nancy Leveson) 교수가 제안한 STAMP(System-Theoretic Accident Model and Processes) 이론에 기반한 차세대 위험원 분석 기법으로, 사고를 단순한 '부품의 물리적 고장'이 아니라 복잡한 시스템 내부 구성요소 간의 '부적절한 제어 및 상호작용(Control Problem)'의 결과로 파악하는 하향식 시스템 안전성 분석 방법론.
- **배경 및 필요성** : 전통적 FTA, FMEA는 개별 부품의 기계적 고장 분석에는 유용하나, 소프트웨어의 논리 결함, 센서-알고리즘-액추에이터 간의 타이밍 불일치, 운전자와 자율주행 SW 간의 상호작용 실패 등 현대 복잡 시스템(SoS)의 사고를 설명하지 못하는 한계 극복.
- **핵심 통제 개념** : 계층적 제어 구조(Hierarchical Control Structure), 불안전 제어 행동(UCA, Unsafe Control Action).

## Ⅱ. STPA 4단계 분석 프로세스 및 계층적 제어 루프

```text
   [ 1단계: 분석 목적 정의 ] ──> [ 2단계: 제어 구조 모델링 ] ──> [ 3단계: UCA 도출 ] ──> [ 4단계: 손실 시나리오 분석 ]
    - 시스템 손실(Loss) 정의       - 컨트롤러, 액추에이터,      - 4가지 가이드워드 기반        - 제어 루프 내 결함 원인 분석
    - 위험원(Hazard) 식별          센서, 제어 대상 모델링        불안전 제어 행동 식별         (센서 지연, 알고리즘 오류)
```

```text
   [ 상위 컨트롤러 (자율주행 SW / 운전자) ]
          │                           ▲
          │ 제어 명령 (Control Action) │ 피드백 (Sensor Feedback)
          ▼                           │
   [ 하위 제어 대상 (브레이크 액추에이터 / 조향 장치) ]
```

- **UCA 도출을 위한 4가지 가이드워드** :
  - **Not Providing** : 위험 상황에서 제어 행동을 제공하지 않음 (예: 전방 장애물 발견 시 브레이크 미작동).
  - **Providing causes hazard** : 부적절한 상황에서 제어 행동을 제공함 (예: 고속 주행 중 역방향 기어 변속 명령).
  - **Too early / Too late / Out of order** : 너무 빠르거나, 너무 늦게, 또는 잘못된 순서로 제어 행동 제공 (예: 에어백이 충돌 2초 후에 지연 전개).
  - **Stopped too soon / Applied too long** : 제어 행동이 너무 일찍 중단되거나 너무 오래 지속됨 (예: 비상 제동이 0.5초 만에 풀림).

## Ⅲ. 전통적 위험 분석(FTA/FMEA)과 STPA의 비교

| 비교 항목 | 전통적 위험 분석 (FTA / FMEA) | 시스템 이론 프로세스 분석 (STPA) |
|---|---|---|
| 사고의 원인 모델 | 신뢰성 이론 (부품의 물리적 마모 및 하드웨어 고장) | 제어 이론 (구성요소 간 상호작용 및 피드백 제어 실패) |
| 소프트웨어 취급 | 소프트웨어를 단순히 고장 확률을 가진 부품 취급 | 소프트웨어 설계 결함, 부적절한 요구사항을 주 원인으로 분석 |
| 시스템 복잡성 대응 | 독립적인 선형 인과관계 분석에 국한 | 복잡한 피드백 루프, 자율주행, 복합 시스템(SoS) 분석 최적 |
| 비고장 사고 탐지 | 부품이 정상 동작했음에도 발생하는 상호작용 사고 탐지 불가 | 모든 구성요소가 정상 스펙대로 동작해도 발생하는 사고 완벽 탐지 |
| 주 활용 분야 | 전통적 기계 제조, 정유 플랜트, 단순 전자기기 | 자율주행차, 도심항공교통(UAM), 원자력, 의료 로봇, 항공우주 |

## Ⅳ. 안전 필수 시스템 적용을 위한 기술사적 제언

- **ISO 26262 및 SOTIF(ISO 21448) 표준과의 통합 연계** : 부품 고장에 의한 기능안전(ISO 26262)뿐만 아니라 부품 고장이 없음에도 환경적 한계와 성능 부족으로 발생하는 의도된 기능의 안전성(SOTIF)을 검증하기 위해 STPA를 공식 위험 분석 기법으로 규정해야 함.
- **UCA 기반의 안전 요구사항(Safety Constraints) SRS 역추적 반영** : 도출된 모든 UCA에 대해 '시스템은 어떠한 경우에도 ~해서는 안 된다'는 형태의 안전 제약조건을 도출하고, 이를 소프트웨어 요구명세서(SRS)의 최상위 제약조건으로 매핑하여 개발 전 과정에서 추적 관리 필수.
