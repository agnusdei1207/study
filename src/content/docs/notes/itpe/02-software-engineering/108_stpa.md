## 연관 키워드

- STPA(System Theoretic Process Analysis), STAMP(System-Theoretic Accident Model and Processes), UCA(Unsafe Control Action)
- 계층적 제어 구조(Hierarchical Control Structure), 위험원(Hazard), 안전 제약사항(Safety Constraints), SOTIF(Safety Of The Intended Functionality)

## Ⅰ. STPA의 개요

- 핵심 요약 : 부품 고장보다 구성요소 간 제어와 상호작용의 실패를 사고 원인으로 보는 시스템 이론 기반 위험 분석 기법.
- 개념 : 낸시 레브슨(Nancy Leveson) 교수가 STAMP(System-Theoretic Accident Model and Processes) 사고 모델을 바탕으로 제시한 **시스템 이론 프로세스 분석** (STPA, System Theoretic Process Analysis). 사고를 구성요소 간 부적절한 제어의 결과로 보고 하향식으로 원인을 찾는다.
- 배경 및 필요성 : FTA(Fault Tree Analysis)와 FMEA(Failure Mode and Effects Analysis)는 부품 고장 분석에 유용하지만, 소프트웨어 논리 결함과 센서, 알고리즘, 액추에이터 사이의 타이밍 불일치, 사람과 자율 시스템의 상호작용 실패를 설명하기 어려움.
- 주요 목적 : 상호작용에서 생기는 위험한 제어 동작을 체계적으로 찾고, 시스템 수준의 사고를 설계 단계에서 예방.

## Ⅱ. STPA의 특징 및 장점

- 핵심 요약 : 계층적 제어 구조와 UCA 도출을 결합해, 고장이 없는 상태에서도 생기는 사고까지 분석하는 방식.

1. 시스템 이론 기반 : 사고를 부품 고장이 아닌 제어와 상호작용의 실패로 모델링 → 고장 없이 발생하는 사고도 분석 대상에 포함.
2. **계층적 제어 구조** (Hierarchical Control Structure) : 상위 컨트롤러와 하위 제어 대상을 피드백 루프로 모델링 → 제어 경로 누락 감소.
3. **불안전 제어 행동** (UCA, Unsafe Control Action) : 제어 동작을 네 가지 가이드워드(제공하지 않음, 잘못 제공, 너무 이르거나 늦은 제공, 너무 일찍 멈추거나 오래 유지)로 점검 → 위험한 제어를 체계적으로 도출.
4. 비고장 사고 탐지 : 모든 구성요소가 명세대로 동작해도 생기는 상호작용 사고를 찾아냄 → 소프트웨어 논리와 타이밍 결함을 조기에 발견.

## Ⅲ. STPA의 구조 (흐름)

- 핵심 요약 : 분석 목적 정의, 제어 구조 모델링, UCA 도출, 손실 시나리오 분석의 4단계 프로세스.
- **위험원** (Hazard) : 시스템 손실로 이어질 수 있는 상태나 조건으로, 1단계에서 식별하는 출발점.

```text
[ 1단계 : 분석 목적 정의 ]
  손실(Loss) · 위험원(Hazard) 정의
        ↓
[ 2단계 : 제어 구조 모델링 ]
  컨트롤러 · 액추에이터 · 센서 · 대상
        ↓
[ 3단계 : UCA 도출 ]
  가이드워드 네 종으로 불안전 제어 식별
        ↓
[ 4단계 : 손실 시나리오 분석 ]
  센서 지연, 알고리즘 오류 등 원인 추적
```

- 계층적 제어 루프 : 제어 명령은 아래로, 센서 피드백은 위로 흐르며 두 경로 모두 분석 대상이 된다.

```text
[ 상위 컨트롤러 (자율주행 SW 또는 운전자) ]
        │ 제어 명령
        ↓
[ 하위 제어 대상 (브레이크·조향 장치) ]
        │ 센서 피드백
        ↓
[ 상위 컨트롤러로 회귀 ]
```

## Ⅳ. 전통적 위험 분석(FTA, FMEA)과 STPA의 비교

- 핵심 요약 : 부품 고장 중심의 선형 인과 분석에서 구성요소 상호작용 중심의 시스템 분석으로 전환.

| 비교 항목 | 전통적 위험 분석(FTA, FMEA) | STPA |
| --- | --- | --- |
| 사고의 원인 모델 | 신뢰성 이론, 부품의 물리적 고장 | 제어 이론, 구성요소 간 상호작용과 피드백 제어 실패 |
| 소프트웨어 취급 | 고장 확률을 가진 부품으로 취급 | 설계 결함과 부적절한 요구사항을 주요 원인으로 분석 |
| 복잡성 대응 | 독립적인 선형 인과관계에 적합 | 복잡한 피드백 루프와 자율주행, 복합 시스템 분석에 적합 |
| 비고장 사고 탐지 | 부품이 정상이면 상호작용 사고를 놓침 | 모든 구성요소가 정상이어도 발생하는 사고를 탐지 |
| 주 활용 분야 | 기계 제조, 정유 플랜트, 단순 전자기기 | 자율주행차, UAM(Urban Air Mobility), 원자력, 의료 로봇 |

- 선택 기준 : 고장 확률로 설명되는 하드웨어 중심 시스템이면 FTA와 FMEA, 제어 상호작용과 소프트웨어 비중이 큰 시스템이면 STPA를 우선 적용.

## Ⅴ. STPA의 장점과 한계

- 핵심 요약 : 복잡 시스템의 비고장 사고를 체계적으로 찾는 장점, 학습 곡선과 분석량 폭증, 설계 연계의 한계.

1. 소프트웨어 논리 결함과 상호작용 실패 등 비고장 사고의 체계적 탐지.
2. 복잡한 피드백 루프와 자율주행, 복합 시스템 분석에 적합.
3. 안전 제약사항을 설계 단계에서 도출해 사고를 사전에 예방.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 분석자의 높은 학습 곡선 | 고장 중심 사고에서 시스템 이론적 사고로 전환해야 함 → 분석 누락과 도입 지연 | 도메인별 가이드와 템플릿 제공, FTA와 FMEA를 병행하는 교육 | 분석 담당자 교육 이수율 |
| UCA 조합의 방대함 | 복합 자율주행 시스템에서 제어 루프와 변수가 늘어 UCA 조합이 급증 | XSTAMPP 같은 오픈소스 STPA 도구 활용, 핵심 안전 기능 중심의 위험도 우선순위 분석 | UCA 검토 완료율 |
| 안전 제약의 설계 단절 | 정성적으로 도출된 제약이 아키텍처와 코딩 규칙으로 구체화되지 않음 | **정형 요구사항**(Formal Specification)으로 변환하고 런타임 안전 모니터로 구현 | 제약-요구사항 추적률 |

## Ⅵ. STPA에 대한 기술사적 제언

- 핵심 요약 : 기능 안전과 의도된 기능의 안전성 표준에 STPA를 공식 기법으로 연계하고, 개발 프로세스에 추적 항목으로 편입하는 것이 필요.

1. **ISO 26262** (기능 안전)와 **SOTIF** (Safety Of The Intended Functionality, ISO 21448, 의도된 기능의 안전성) 체계에 STPA를 공식 위험 분석 기법으로 명시하면, 고장에 따른 사고와 성능 한계에 따른 사고를 한 분석 틀에서 다룰 수 있다.
2. 개발 프로세스 기준에서 도출된 UCA마다 안전 제약을 하나씩 등록하도록 정하면, **소프트웨어 요구사항 명세** (SRS, Software Requirements Specification)의 최상위 제약과 연결된 상태로 개발 전 과정을 관리할 수 있다.

## Ⅶ. 결론

- 핵심 요약 : STPA는 시스템 이론에 기반해 구성요소 간 제어 실패를 분석하는 안전 분석 체계.
- 시사점 : 복잡 시스템의 사고는 부품 고장 분석으로 잡히지 않는 경우가 많아, 표준 연계와 추적성이 확보될 때 STPA의 실효성이 드러남.
