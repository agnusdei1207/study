## 연관 키워드

- STPA(System Theoretic Process Analysis), STAMP(System-Theoretic Accident Model and Processes), UCA(Unsafe Control Action)
- 계층적 제어 구조(Hierarchical Control Structure), 위험원(Hazard), 안전 제약사항(Safety Constraints), SOTIF(Safety Of The Intended Functionality)

## Ⅰ. STPA의 개요

- 핵심 요약 : 시스템 이론 기반의 차세대 위험원 분석 기법으로 구성요소 간 부적절한 제어 및 상호작용을 사고 원인으로 파악.
- 개념 : MIT(Massachusetts Institute of Technology)의 낸시 레브슨(Nancy Leveson) 교수가 제안한 STAMP(System-Theoretic Accident Model and Processes) 이론에 기반한 차세대 위험원 분석 기법으로, 사고를 단순한 '부품의 물리적 고장'이 아니라 복잡한 시스템 내부 구성요소 간의 '부적절한 제어 및 상호작용(Control Problem)'의 결과로 파악하는 하향식 시스템 안전성 분석 방법론.
- 배경 및 필요성 : 전통적 FTA(Fault Tree Analysis), FMEA(Failure Mode and Effects Analysis)는 개별 부품의 기계적 고장 분석에는 유용하나, 소프트웨어의 논리 결함, 센서-알고리즘-액추에이터 간의 타이밍 불일치, 운전자와 자율주행 SW(Software) 간의 상호작용 실패 등 현대 복잡 시스템(SoS, System of Systems)의 사고를 설명하지 못하는 한계 극복 필요.
- 주요 목적 : 구성요소 간 상호작용에서 발생하는 비안전 제어 행동(UCA)을 체계적으로 도출하고 안전 제약사항을 설정하여 시스템 수준의 사고 예방.

## Ⅱ. STPA의 특징

- 핵심 요약 : 계층적 제어 구조 기반의 4단계 분석 프로세스와 UCA 도출이 결합된 시스템 이론적 안전 분석.

1. 시스템 이론 기반 : 사고를 부품 고장이 아닌 제어 및 상호작용의 실패로 모델링.
2. 계층적 제어 구조 : 상위 컨트롤러와 하위 제어 대상 간의 계층적 피드백 루프 분석.
3. UCA 중심 분석 : 불안전 제어 행동(Unsafe Control Action)을 4가지 가이드워드로 체계적 도출.
4. 비고장 사고 탐지 : 모든 구성요소가 정상 스펙대로 동작해도 발생하는 상호작용 사고 탐지 가능.

## Ⅲ. STPA의 구조 (흐름)

- 핵심 요약 : 분석 목적 정의, 제어 구조 모델링, UCA 도출, 손실 시나리오 분석의 4단계 프로세스.
- STPA 4단계 분석 프로세스.

```text
[ 1단계: 분석 목적 정의 ]
  - 시스템 손실(Loss) 정의
  - 위험원(Hazard) 식별
    │
    ▼
[ 2단계: 제어 구조 모델링 ]
  - 컨트롤러, 액추에이터, 센서, 제어 대상 모델링
    │
    ▼
[ 3단계: UCA 도출 ]
  - 4가지 가이드워드 기반 불안전 제어 행동 식별
    │
    ▼
[ 4단계: 손실 시나리오 분석 ]
  - 제어 루프 내 결함 원인 분석
    (센서 지연, 알고리즘 오류)
```

- 계층적 제어 루프 구조.

```text
[ 상위 컨트롤러 (자율주행 SW / 운전자) ]
    │ 제어 명령 (Control Action)
    ▼
[ 하위 제어 대상 ]
  - 브레이크 액추에이터 / 조향 장치
    │ 피드백 (Sensor Feedback)
    ▼ (상위 컨트롤러로 회귀)
```

## Ⅳ. 전통적 위험 분석(FTA/FMEA)과 STPA의 비교

- 핵심 요약 : 부품 고장 중심의 선형 인과 분석에서 구성요소 상호작용 중심의 시스템 분석으로 전환.

| 비교 항목 | 전통적 위험 분석(FTA / FMEA) | STPA(System Theoretic Process Analysis) |
|---|---|---|
| 사고의 원인 모델 | 신뢰성 이론(부품의 물리적 마모 및 하드웨어 고장) | 제어 이론(구성요소 간 상호작용 및 피드백 제어 실패) |
| 소프트웨어 취급 | 소프트웨어를 단순히 고장 확률을 가진 부품 취급 | 소프트웨어 설계 결함, 부적절한 요구사항을 주 원인으로 분석 |
| 시스템 복잡성 대응 | 독립적인 선형 인과관계 분석에 국한 | 복잡한 피드백 루프, 자율주행, 복합 시스템(SoS) 분석 최적 |
| 비고장 사고 탐지 | 부품이 정상 동작했음에도 발생하는 상호작용 사고 탐지 불가 | 모든 구성요소가 정상 스펙대로 동작해도 발생하는 사고 완벽 탐지 |
| 주 활용 분야 | 전통적 기계 제조, 정유 플랜트, 단순 전자기기 | 자율주행차, UAM(Urban Air Mobility, 도심항공교통), 원자력, 의료 로봇, 항공우주 |

## Ⅴ. STPA의 장점과 한계

- 핵심 요약 : 복잡 시스템 사고의 체계적 탐지 장점, 학습 곡선과 분석 방대함의 한계.
- 장점
  1. 소프트웨어 논리 결함과 상호작용 실패 등 비고장 사고의 체계적 탐지.
  2. 복잡한 피드백 루프와 자율주행, 복합 시스템(SoS) 분석에 적합.
  3. 안전 제약사항을 도출하여 설계 단계에서의 사고 예방 가능.
- 한계점 1 : 기존 고장 분석 엔지니어의 높은 학습 곡선
  - 한계점 : 부품 고장이 아닌 시스템 구성요소 간 상호작용 및 비안전 제어 동작(UCA)에 초점을 맞추는 시스템 이론적 사고로의 패러다임 전환 난제.
  - 해결 방안 : 도메인 맞춤형 STPA 가이드라인 및 예제 템플릀 개발, 전통적 FTA/FMEA와의 상호 보완적 융합 분석 프레임워크 교육 의무화.
- 한계점 2 : 복합 시스템 모델링 시 UCA 및 손실 시나리오 도출의 방대함
  - 한계점 : 복합 자율주행 및 커넥티드 시스템 분석 시 제어 루프와 변수의 폭증으로 도출되는 UCA 조합이 수천 개에 달해 인적 리소스 한계 봉착.
  - 해결 방안 : XSTAMPP 등 오픈소스 STPA 전용 모델링 도구 활용, 핵심 안전 기능(Safety-Critical Features) 중심의 위험도 기반 우선순위 단계별 분석.
- 한계점 3 : 분석된 안전 제약사항의 소프트웨어 설계 연계 어려움
  - 한계점 : 정성적으로 도출된 제어 제약사항이 실제 임베디드 소프트웨어의 아키텍처 및 코딩 규칙으로 구체화되지 못하고 사장되는 문제.
  - 해결 방안 : STPA 제약사항을 정형 요구사항(Formal Specification)으로 변환하고, 런타임 안전 모니터(Safety Monitor/Watchdog) 코드로 자동 연계 구현.

## Ⅵ. STPA에 대한 기술사적 제언

- 핵심 요약 : ISO 26262 및 SOTIF 표준과의 통합 연계와 안전 요구사항 추적성 확보 필요.
- ISO(International Organization for Standardization) 26262 및 SOTIF(ISO 21448) 표준과의 통합 연계 : 부품 고장에 의한 기능안전(ISO 26262)뿐만 아니라 부품 고장이 없음에도 환경적 한계와 성능 부족으로 발생하는 의도된 기능의 안전성(SOTIF)을 검증하기 위해 STPA를 공식 위험 분석 기법으로 규정해야 함.
- UCA 기반의 안전 요구사항(Safety Constraints) SRS(Software Requirements Specification) 역추적 반영 : 도출된 모든 UCA에 대해 '시스템은 어떠한 경우에도 ~해서는 안 된다'는 형태의 안전 제약조건을 도출하고, 이를 소프트웨어 요구명세서(SRS)의 최상위 제약조건으로 매핑하여 개발 전 과정에서 추적 관리 필수.

## Ⅶ. 결론

- 핵심 요약 : STPA는 시스템 이론 기반의 안전 분석 체계로 표준 연계와 추적성 확보가 실효성의 관건.
- 요약 : STAMP 이론에 기반한 4단계 분석 프로세스로 구성요소 간 부적절한 제어 행동을 도출하는 시스템 안전성 분석 방법론.
- 시사점 : ISO 26262/SOTIF 표준과의 통합, 정형 요구사항으로의 변환, 런타임 안전 모니터 연계의 3요소가 실제 안전 확보의 전제 조건.
