## Ⅰ. 기록·재생 테스트의 개요

- 개념 : **기록·재생 테스트** 란 사용자의 실제 브라우저 조작(클릭, 키 입력, 스크롤)이나 분산 시스템 간의 네트워크 트래픽(HTTP(Hypertext Transfer Protocol) 요청/응답 패킷)을 그대로 캡처하여 '기록(Record)'한 후, 이를 소프트웨어 테스트 시점에 동일한 순서와 타이밍으로 모의 '재생(Replay)'하여 회귀 결함과 시스템 동작을 결정론적으로 검증하는 테스트 자동화 기법.
- 배경 및 필요성 : 복잡한 UI(User Interface) 인터랙션 테스트 코드를 일일이 수작업 코딩하는 막대한 공수를 절감하고, 프로덕션 환경에서 발생한 희귀한 버그나 외부 서드파티 API(Application Programming Interface) 장애 상황을 로컬 테스트 환경에서 $100\%$ 똑같이 재현하여 디버깅하기 위해 도입.
- 대표 도구 : UI 계층(Playwright Codegen, Cypress Studio, Selenium IDE), 네트워크 계층(WireMock, VCR, GoReplay).

## Ⅱ. 기록·재생 테스트의 2대 계층 동작 메커니즘

```text
   [ 1. UI 계층 기록 및 재생 (Playwright Codegen) ]
    [ 테스터 브라우저 조작 ] ──(이벤트 리스너 캡처)──> [ 자동 테스트 스크립트 생성 (.ts) ]
                                                              │
    [ CI 파이프라인 무인 실행 ] <──(헤드리스 브라우저 재생)──┘

   [ 2. 네트워크 트래픽 계층 기록 및 재생 (GoReplay / WireMock) ]
    [ 실서버 운영 트래픽 ] ──(패킷 미러링/프록시 캡처)──> [ 트래픽 기록 저장소 (.json) ]
                                                              │
    [ 테스트/스테이징 서버 ] <──(모의 트래픽 재생 주입)───────┘
```

- UI 상호작용 기록/재생 : 브라우저 확장을 통해 사용자의 클릭 경로를 추적하여 안정적인 **로케이터** (XPath, CSS Selector) 기반의 테스트 코드를 자동 생성.
- **네트워크 트래픽 미러링 및 재생** (Traffic Shadowing) : 실운영 서버로 들어오는 실제 사용자 HTTP 요청을 복사하여 신규 버전의 스테이징 서버에 실시간으로 재생 주입함으로써, 실제 트래픽 부하와 데이터 정합성을 프로덕션 영향 없이 검증.

## Ⅲ. 전통적 수작업 테스트 스크립트와 기록·재생 테스트의 비교

| 비교 항목 | 수작업 테스트 코딩 (Manual Scripting) | 기록·재생 테스트 (Record & Replay) |
|---|---|---|
| 테스트 생성 속도 | 매우 느림 (셀렉터 조사, 어설션 코드 수작업 작성) | 매우 빠름 (화면을 직접 조작하면 스크립트 즉시 자동 생성) |
| 초기 진입 장벽 | 테스트 프레임워크 및 프로그래밍 지식 필수 | 비개발자(기획자, 수동 QA(Quality Assurance) 테스터)도 즉각 작성 가능 |
| 유지보수 취약성 | 상대적으로 견고함 (모듈화된 POM 패턴 적용) | UI 디자인 변경 시 녹화된 스크립트 파손 위험 (Flaky Test) |
| 런타임 결정론 | 외부 API 상태에 따라 결과가 달라질 수 있음 | 네트워크 응답이 기록된 채로 재생되므로 완벽한 결정론 보장 |
| 최적 활용 단계 | 비즈니스 핵심 코어 단위/통합 테스트 | 대규모 회귀 테스트 스위트 생성, 프로덕션 버그 재현 디버깅 |

## Ⅳ. 기록·재생 테스트의 주요 한계점 및 해결 방안

- UI 요소 변경에 따른 테스트 스크립트 취약성(Brittle Test Scripts) :
  - 한계점 : 화면의 사소한 CSS(Cascading Style Sheets) 클래스명, DOM(Document Object Model) 계층 구조, 버튼 위치 변경만으로도 기록된 레코더 좌표나 단순 XPath가 깨져 테스트가 대량 실패.
  - 해결 방안 : 테스트 전용 속성(`data-testid`) 기반 견고한 셀렉터(Smart Selector) 표준화, 요소 위치 변경 시 유사도를 분석해 자동 보정하는 AI(Artificial Intelligence) **자가 치유** (Self-Healing) 도구 도입.
- 비결정론적 비동기 타이밍 이슈로 인한 오탐(Flaky Tests) :
  - 한계점 : 네트워크 응답 지연이나 브라우저 렌더링 속도 차이로 인해 특정 UI 요소가 아직 DOM에 로드되지 않은 상태에서 재생 클릭이 실행되어 실패.
  - 해결 방안 : 고정 대기 시간(`sleep`)을 제거하고 특정 DOM 조건 성립 시까지 대기하는 **명시적 대기** (Explicit Wait) 및 **네트워크 유휴** (Network Idle) 감지 로직 적용.
- 비즈니스 유효성 검증 **단언** (Assertion) 작성 누락 :
  - 한계점 : 사용자의 동작(클릭, 타이핑)만 단순히 재생하고, 실제 화면의 최종 결과값이나 비즈니스 로직 정합성을 검증하는 단언이 결여되어 겉핥기 테스트 전락.
  - 해결 방안 : 시나리오 기록 후 핵심 체크포인트에 대한 텍스트, 상태값, API 응답 검증 단언을 추가하는 하이브리드 스크립팅 프로세스 의무화.

## Ⅴ. 테스트 신뢰성 확보를 위한 기술사적 제언

- 재생 취약성(Flakiness) 극복을 위한 **스마트 셀렉터** 전략 : 동적으로 생성되는 무작위 CSS 클래스(`class="btn_3x9a"`)를 녹화하면 UI 빌드 시마다 테스트가 깨지므로, `data-testid="submit-btn"`과 같은 고유 테스트 속성을 사전에 규격화하여 기록 도구가 이를 우선 인식하도록 코딩 표준 수립.
- 실운영 트래픽 녹화 시 개인정보 **비식별화** (Masking) 필수화 : GoReplay 등으로 실서버 트래픽을 미러링하여 스테이징 환경에 재생할 때 주민등록번호, 비밀번호, 카드번호 등 민감정보가 비인가 환경으로 유출되지 않도록, 프록시 계층에서 정규식 기반 토큰 마스킹 필터를 의무 적용해야 함.
