## Ⅰ. 방향성 비순환 그래프(DAG)의 개요

- 개념 : **방향성 비순환 그래프** (DAG, Directed Acyclic Graph) 란 간선(Edge)에 명확한 방향성이 존재하며, 어떤 정점(Vertex)에서 출발하더라도 간선의 방향을 따라 이동했을 때 다시 자기 자신으로 돌아오는 순환 고리(사이클, Cycle)가 전혀 존재하지 않는 유한 그래프(Directed Acyclic Graph).
- 배경 및 필요성 : 작업 간의 엄격한 선후 의존 관계(Prerequisite), 데이터 파이프라인의 처리 순서, 컴파일러의 연산 최적화, 버전 관리 시스템의 커밋 이력을 모순 없이 수학적으로 모델링하기 위해 필수.
- 핵심 알고리즘 : **위상 정렬** (Topological Sorting), **사이클 검출** (DFS, Depth-First Search의 Back-edge 감지), **최장 경로** (임계 경로) 계산

## Ⅱ. DAG의 구조 및 위상 정렬(Topological Sort) 메커니즘

```text
   [ 작업 A: 데이터 수집 ] ───> [ 작업 B: 결측치 정제 ] ───> [ 작업 D: 집계 리포트 ]
             │                                                  ▲
             └────────────────> [ 작업 C: 이상치 필터링 ] ──────┘
   (순환이 없으므로 모순 없이 순차 실행 순서 도출 가능: A -> B -> C -> D 또는 A -> C -> B -> D)
```

- **카안 알고리즘** (Kahn's Algorithm - BFS(Breadth-First Search) 기반 위상 정렬) :
  1. 진입 차수(In-degree: 해당 노드로 들어오는 간선의 수)가 0인 모든 정점을 큐에 삽입.
  2. 큐에서 정점을 꺼내어 정렬 결과에 추가하고, 해당 정점과 연결된 모든 간선 제거 (인접 노드의 진입 차수 1 감소).
  3. 새롭게 진입 차수가 0이 된 인접 정점들을 큐에 삽입.
  4. 모든 정점을 방문하기 전에 큐가 비면 그래프 내에 사이클(Cycle)이 존재함을 판별.

## Ⅲ. 주요 시스템에서의 DAG 응용 분야 비교

| 응용 분야 | DAG의 정점 (Vertex) | DAG의 간선 (Edge) | 시스템 상의 역할 |
|---|---|---|---|
| 데이터 파이프라인 (Airflow) | 실행 태스크 (Python Operator 등) | 태스크 간 실행 의존성 (A 완료 후 B 실행) | 워크플로우 오케스트레이션 및 병렬 스케줄링 |
| 분산 연산 엔진 (Spark / Flink) | RDD / 데이터셋 변환 연산 | 셔플(Shuffle) 및 파이프라이닝 의존성 | 좁은/넓은 의존성 분석 및 물리 실행 계획 최적화 |
| 소스코드 버전 관리 (Git) | 개별 커밋 스냅샷 (Commit) | 부모 커밋을 가리키는 포인터 | 분기(Branch) 및 병합(Merge) 히스토리 무결성 보장 |
| 차세대 분산원장 (IOTA Tangle) | 개별 암호화폐 거래 (Transaction) | 이전 거래에 대한 검증 승인 링크 | 블록체인의 확장성 한계를 극복한 블록리스 분산원장 |

## Ⅳ. 방향성 비순환 그래프(DAG)의 주요 한계점 및 해결 방안

- 동적 파이프라인 구성 시 숨겨진 **순환 의존성** (Cyclic Dependency) 발생 :
  - 한계점 : 수백 개의 복잡한 태스크가 얽힌 환경에서 런타임 조건부 분기에 의해 의도치 않은 루프가 형성될 경우 스케줄러가 데드락에 빠짐.
  - 해결 방안 : DAG 파싱 단계에서 위상 정렬(Topological Sort) 및 **타잔** (Tarjan) 강결합 컴포넌트 알고리즘을 활용한 순환 의존성 사전 정적 검증 강제.
- 대규모 태스크 폭증 시 스케줄러 파싱 오버헤드 및 지연 :
  - 한계점 : Airflow 등 오케스트레이터에서 DAG 파일 수가 급증할 경우 스케줄러의 반복적 파이썬 파일 파싱 루프로 인해 CPU(Central Processing Unit) 병목 및 태스크 실행 지연.
  - 해결 방안 : DAG 파일 내 무거운 I/O 및 DB(Database) 조회 로직 금지, 선언적 스펙(YAML(YAML Ain't Markup Language)/JSON(JavaScript Object Notation)) 기반 경량 DAG 팩토리 패턴 도입 및 스케줄러 수평 분산.
- 파이프라인 장애 발생 시 **부분 재실행** (Backfill) 및 복원력 난제 :
  - 한계점 : 긴 파이프라인의 중간 태스크 실패 시 전체를 처음부터 재실행해야 하거나 다운스트림 태스크의 데이터 정합성이 훼손되는 문제.
  - 해결 방안 : 모든 태스크의 멱등성(Idempotency) 보장 설계, 실패 지점부터 선택적 재실행(Clear Downstream) 기능 및 아티팩트 캐싱(Lineage 추적) 활용.

## Ⅴ. 대규모 파이프라인 엔지니어링을 위한 기술사적 제언

- 작업 의존성 **데드락** (Deadlock) 사전 차단 : 마이크로서비스 간 비동기 이벤트 흐름이나 대규모 Airflow 파이프라인에서 순환 의존성이 발생하면 전체 시스템이 멈추는 교착상태가 발생하므로, 파이프라인 등록 시 CI(Continuous Integration) 단계에서 위상 정렬 유효성 검사를 의무 실행하여 사이클 존재 시 배포를 차단해야 함.
- Spark **지연 연산** (Lazy Evaluation)과 DAG 최적화 활용 : Apache Spark에서 Action(count, collect)이 호출되기 전까지 Transformation 연산을 즉시 실행하지 않고 내부 DAG로 축적한 후, Catalyst 옵티마이저를 통해 불필요한 셔플을 병합하는 최적의 쿼리 플랜을 수립하도록 데이터 파이프라인 튜닝 권장.
