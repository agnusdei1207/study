## 답안 골격
```text
[추상클래스(Abstract Class)] ◀━━ 머리: Ⅶ 내 의견 (템플릿 메서드 패턴 기반 프레임워크 제어 흐름 역전과 컴포지션 우선 원칙의 조화)
 ┃
 ┣━ Ⅰ 개요 ───── 하나 이상의 추상 메서드를 포함하여 직접 인스턴스화가 불가하며, 하위 클래스의 상속을 통해 완성을 강제하는 미완성 설계 클래스
 ┣━ Ⅱ 특징 ───── 직접 객체 생성 불가(`new` 금지) · 공통 상태(필드) 및 기본 구현 메서드 공유 · 하위 클래스의 구현 표준화 및 규격 강제
 ┣━ Ⅲ 구조 ───── 추상 클래스 내부: 인스턴스 멤버 변수 + 일반 구현 메서드 + 추상 메서드(`abstract method()`)
 ┣━ Ⅳ 흐름 ───── 추상 클래스 선언 → 하위 구체 클래스 상속(`extends`) → 추상 메서드 오버라이딩 구현 → 상위 타입 다형성 참조 및 실행
 ┣━ Ⅴ 비교 ───── 추상 클래스(Abstract Class) vs 인터페이스(Interface) vs 구체 클래스(Concrete Class)
 ┗━ Ⅵ 실무 ───── 다중 상속 불가로 인한 확장 제약 / 깊은 상속 계층 구조로 인한 결합도 증가 / 템플릿 메서드(Template Method) 패턴 응용
```

## 한 줄 본질
- 공통된 멤버 변수와 기본 알고리즘 골격은 상위에서 미리 구현해 두고, 달라지는 핵심 로직만 하위 클래스가 반드시 구현하도록 강제하는 미완성 부모 클래스 / 코드 재사용과 행위 규격 강제

## 핵심 그림
```text
┌────────────────────────────────────────────────────────┐
│ <<abstract>> DataProcessor                             │
├────────────────────────────────────────────────────────┤
│ - dataSource: String                                   │
├────────────────────────────────────────────────────────┤
│ + process(): void { readData(); transform(); save(); } │ ◀── 템플릿 메서드 (공통)
│ # readData(): void { ... }                             │ ◀── 기본 구현 (재사용)
│ # transform(): void                                    │ ◀── abstract (구현 강제!)
│ # save(): void { ... }                                 │
└────────────────────────────────────────────────────────┘
                           ▲
                           │ (상속: extends)
        ┌──────────────────┴──────────────────┐
        │                                     │
┌───────────────────────┐             ┌────────────────────────┐
│ CsvDataProcessor      │             │ JsonDataProcessor      │
├───────────────────────┤             ├────────────────────────┤
│ # transform(): void   │             │ # transform(): void    │
│   (CSV 파싱 구현)     │             │   (JSON 파싱 구현)     │
└───────────────────────┘             └────────────────────────┘
```

## 핵심 용어
- 추상 메서드(Abstract Method): 선언부(Signature)만 존재하고 구현부(Body `{}`)가 없는 메서드로, 하위 구체 클래스에서 반드시 재정의(Override)해야 함
- 템플릿 메서드 패턴(Template Method Pattern): 부모 추상 클래스에서 알고리즘의 전체 흐름(뼈대)을 정의하고, 특정 단계의 세부 처리를 추상 메서드로 선언하여 자식 클래스가 위임 구현하도록 하는 디자인 패턴
- IS-A 관계: 상속을 통해 형성되는 본질적인 혈통 관계 (예: `Dog is an Animal`)
- 제어의 역전(IoC, Inversion of Control): 하위 클래스가 상위 클래스의 코드를 호출하는 것이 아니라, 상위 추상 클래스의 템플릿 메서드가 하위 클래스의 오버라이딩 메서드를 호출하는 헐리우드 원칙(Don't call us, we'll call you)

## 핵심 통찰
- 인터페이스가 "이 객체가 무엇을 할 수 있는가(Can-Do 계약)"를 정의한다면, 추상 클래스는 "이 객체는 본질적으로 무엇인가(IS-A 혈통)"와 함께 "공통의 유전자(코드와 상태)"를 물려줌
- 추상 클래스는 코드 중복을 획기적으로 줄여주며, 템플릿 메서드 패턴을 통해 전체적인 비즈니스 실행 순서를 상위에서 단단히 통제할 수 있음
- 그러나 단일 상속만 허용되는 언어 환경(Java, C# 등)에서 추상 클래스를 상속받는 순간 다른 클래스를 상속받을 수 없게 되며, 상위 클래스의 변경이 하위 클래스 전체를 흔드는 '상속의 취약성(Fragile Base Class Problem)'을 유발할 수 있음

## 이웃 토픽과 구분
| 비교 항목 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) | 일반 구체 클래스 (Concrete Class) |
| :--- | :--- | :--- | :--- |
| **인스턴스화** | 직접 생성 불가 (`new` 금지) | 직접 생성 불가 | 생성 가능 (`new` 가능) |
| **추상 메서드** | 0개 이상 보유 가능 | 모든 메서드가 기본적으로 추상 | 보유 불가 (모두 구현되어야 함) |
| **상속/구현** | 단일 상속 (`extends`) | 다중 구현 (`implements`) | 단일 상속 (`extends`) |
| **상태(필드) 보유**| 인스턴스 멤버 변수 자유롭게 보유 | `public static final` 상수만 가능 | 인스턴스 멤버 변수 자유롭게 보유 |
| **사용 목적** | 공통 로직 재사용 + 일부 규격 강제 | 행위 규약 정의 및 결합도 분리 (다형성) | 실제 비즈니스 로직 수행 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **상위 추상 클래스 수정 시 하위 구현체 일괄 오류** | 상위와 하위 간의 강한 결합으로 인한 깨지기 쉬운 기반 클래스 문제 | 상속(Inheritance) 대신 컴포지션(Composition)과 인터페이스 위임 구조로 리팩토링 |
| **단일 상속 한계로 인한 기능 확장 봉쇄** | 이미 부모 추상 클래스를 상속받아 다른 유용한 라이브러리 상속 불가 | 행위 규약은 인터페이스로 분리하고 내부 기능을 멤버 변수로 주입받는 전략 패턴 적용 |
| **하위 클래스에서 불필요한 메서드까지 상속** | 부모 추상 클래스가 너무 많은 책임을 담당하여 비대해짐 | 리스코프 치환 원칙(LSP) 검토 및 추상 클래스를 작고 명확한 도메인 단위로 계층 분할 |

## 이렇게 출제된다
- **10점형**: 객체지향 프로그래밍에서 추상클래스(Abstract Class)의 개념, 특징 및 필요성을 설명하시오.
- **25점형**: 
  - 1) 추상 클래스의 구조와 하위 구체 클래스 간의 상속 메커니즘을 UML 클래스 다이어그램으로 도식화하시오.
  - 2) 디자인 패턴 중 추상 클래스를 가장 대표적으로 활용하는 '템플릿 메서드(Template Method) 패턴'의 구조와 제어 역전 원리를 설명하시오.
  - 3) 추상 클래스와 인터페이스의 차이점을 문법적, 아키텍처적 관점에서 심층 비교하고, "상속보다는 조합을 우선하라(Favor composition over inheritance)"는 원칙의 실무 적용 방안을 논하시오.

## 내 의견
- 과거 객체지향 초창기에는 재사용을 위해 추상 클래스 기반의 상속을 남발했으나, 이는 시스템을 경직시키고 유지보수를 불가능하게 만드는 안티패턴으로 귀결되었음
- 현대 프레임워크(Spring, Android SDK 등)에서는 알고리즘의 골격을 고정해야 하는 프레임워크 내부 템플릿(예: `AbstractRoutingDataSource`, `AbstractController`)에만 한정적으로 추상 클래스를 사용함
- 일반 비즈니스 애플리케이션 개발에서는 인터페이스를 통한 계약 정의와 컴포지션(Composition) 기반 의존성 주입을 기본 원칙으로 삼고, 진정한 의미의 공통 템플릿 골격이 명확할 때만 추상 클래스를 선별 도입해야 함
