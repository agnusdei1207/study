## Ⅰ. UML 다이어그램 체계의 개요

- 개념 : 객체지향 소프트웨어 시스템의 분석, 설계, 구현, 배포 과정을 시각적으로 모델링하기 위해 **OMG** (Object Management Group)에서 표준화한 범용 **통합 모델링 언어** (UML, Unified Modeling Language).
- 배경 및 필요성 : 개발자, 설계자, 발주자 간의 시각적 의사소통 표준화, 복잡한 시스템의 아키텍처 가시화, **모델 기반 개발** (MDD, Model-Driven Development)의 청사진 제공.
- UML(Unified Modeling Language) 2.x 분류 : 시스템의 정적 구조를 나타내는 **구조 다이어그램** (7종)과 동적 변화를 나타내는 **행위 다이어그램** (7종, 상호작용 포함)으로 총 14종 구성.

## Ⅱ. UML 다이어그램 14종 분류 체계도

```text
                               [ UML 2.x 다이어그램 ]
                                    │
           ┌────────────────────────┴────────────────────────┐
           ▼                                                 ▼
   [ 구조 다이어그램 (7종) ]                         [ 행위 다이어그램 (7종) ]
   - 클래스 (Class)                                  - 유스케이스 (Use Case)
   - 객체 (Object)                                   - 활동 (Activity)
   - 패키지 (Package)                                - 상태 머신 (State Machine)
   - 컴포넌트 (Component)                            ┌───────┴───────┐
   - 복합체 구조 (Composite Structure)               ▼ (상호작용 4종) ▼
   - 배치 (Deployment)                               - 순차 (Sequence)
   - 프로파일 (Profile)                              - 통신 (Communication)
                                                     - 타이밍 (Timing)
                                                     - 상호작용 개요 (Interaction Overview)
```

## Ⅲ. 활동 다이어그램(Activity Diagram)의 구조 및 핵심 요소

- 활동 다이어그램의 역할 : 시스템 내부의 비즈니스 프로세스, 유스케이스 실행 흐름, 객체 간 제어 흐름과 데이터 흐름을 **워크플로우** 형태로 정밀 모델링.

```text
   (● 시작점) ──> [ 액션 1: 주문 접수 ] ──> < 다이아몬드: 재고 확인 >
                                                    │
                             ┌──────────────────────┴──────────────────────┐
                      [재고 있음]                                    [재고 없음]
                             │                                             │
                             ▼                                             ▼
                 ══════════ 포크(Fork) ══════════                   [ 액션: 품절 안내 ]
                       /               \                                   │
                      ▼                 ▼                                  ▼
              [ 액션 2: 결제 승인 ]   [ 액션 3: 배송 준비 ]                  (◎ 종료점)
                      \                 /
                 ══════════ 조인(Join) ══════════
                             │
                             ▼
                    [ 액션 4: 주문 완료 ] ──> (◎ 종료점)
```

| 핵심 구성요소 | 표기법 및 의미 |
|---|---|
| **액션/액티비티** (Action/Activity) | 둥근 사각형. 실행 가능한 원자적 단위의 작업이나 복합 프로세스 |
| **분기 및 병합** (Decision/Merge) | 마름모꼴. 조건문([Guard])에 따른 흐름 분기와 다수 흐름의 단일 결합 |
| **포크 및 조인** (Fork/Join) | 굵은 가로선. 단일 흐름을 병렬 흐름으로 동시 분기(Fork) 및 모든 병렬 흐름 완료 대기(Join) |
| **스윔레인** (Swimlane) | 세로/가로 구분선. 작업을 수행하는 담당 조직, 시스템, 객체의 역할 경계 명시 |
| **객체 노드** (Object Node) | 직사각형. 액션 간에 주고받는 데이터 또는 객체 상태 명시 |

## Ⅳ. UML 다이어그램 모델링의 주요 한계점 및 해결 방안

- 모델과 실제 코드 간 동기화 단절 및 문서의 '형식화(Shelfware)' :
  - 한계점 : 프로젝트 초기 작성된 UML 다이어그램이 개발 진행 중 발생하는 빈번한 코드 변경을 제때 반영하지 못해 실제 구현과 괴리되며 결국 아무도 보지 않는 문서로 전락.
  - 해결 방안 : 다이어그램-애즈-코드(Diagrams as Code: PlantUML, Mermaid)를 도입하여 설계 문서를 소스코드와 함께 Git으로 형상 관리하고, CI(Continuous Integration) 파이프라인에서 코드 기반 리버스 엔지니어링 다이어그램 자동 갱신.
- 과도한 상세화로 인한 커뮤니케이션 오버헤드와 분석 마비(Analysis Paralysis) :
  - 한계점 : 사소한 프라이빗 멤버와 세부 구현 알고리즘까지 모든 UML 메타모델 규격을 엄격히 그리려다 설계 작성 및 검토에 과도한 공수가 소모되어 개발 일정 지연.
  - 해결 방안 : 애자일 모델링(Agile Modeling) 원칙을 적용하여 UML을 핵심 아키텍처 개념 및 복잡한 비즈니스 규칙 검증을 위한 '스케치(Sketch)' 용도로 경량화하고, C4 모델 등 현대적 아키텍처 다이어그램 병행.
- UML 정규 표기법 해석의 모호성 및 팀원 간 숙련도 편차 :
  - 한계점 : 집약(Aggregation)과 합성(Composition), 실체화(Realization) 등 세부 표기법에 대한 이해도가 개발자마다 달라 설계 의도가 잘못 전달되거나 왜곡되는 문제.
  - 해결 방안 : 조직 표준 UML 스타일 가이드라인과 레퍼런스 카탈로그를 정립하고, 실무에 가장 핵심적인 3대 다이어그램(클래스, 시퀀스, 상태) 중심의 선택적 모델링 표준화 교육 수행.

## Ⅴ. 모델링 효율화를 위한 기술사적 제언

- 애자일 환경에서의 '적정 모델링(Just Enough Modeling)' 지향 : 지나치게 모든 코드를 UML로 작성하는 과도한 엔지니어링을 지양하고, 시스템의 복잡한 비즈니스 워크플로우(활동 다이어그램), 도메인 엔티티 관계(클래스 다이어그램), 중요 시퀀스에 집중.
- PlantUML 및 Text-to-UML을 통한 형상관리 일원화 : 바이너리 모델 파일의 머지 충돌을 방지하기 위해 텍스트 기반 UML 도구를 채택하여 Git 소스코드와 함께 버전 관리 체계 구축 권장.
