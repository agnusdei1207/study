소프트웨어 공학 → 모델링 → **UML 다이어그램 체계(구조·행위, 활동 다이어그램)**

## 30초 인출

- 본질: UML은 소프트웨어의 구조와 행위를 표준 표기로 모델링하는 언어이며 구조 다이어그램과 행위 다이어그램으로 나뉨
- 메커니즘: 요구는 유스케이스, 처리 흐름은 활동, 객체의 상태 변화는 상태 다이어그램으로 나눠 그리고 구조 다이어그램과 연결
- 통찰: 하나의 다이어그램에 요구·흐름·상태를 모두 담으면 읽기 어려우므로 모델링 목적에 맞는 행위 다이어그램을 골라 유스케이스에서 활동, 상태 순으로 정제

<details>
<summary>핵심 용어</summary>

- **UML(Unified Modeling Language)** : 객체지향 소프트웨어의 구조와 행위를 표현하는 표준 모델링 언어
- **구조 다이어그램(Structure Diagram)** : 클래스·객체·컴포넌트·배치 등 시스템의 정적 구성을 표현하는 다이어그램
- **행위 다이어그램(Behavior Diagram)** : 유스케이스·활동·상태·순차 등 시스템의 동작을 표현하는 다이어그램
- **활동 다이어그램(Activity Diagram)** : 업무·처리의 흐름을 액션·분기·병렬로 표현하는 다이어그램
- **상태 다이어그램(State Diagram)** : 객체가 이벤트에 따라 상태를 바꾸는 과정을 표현하는 다이어그램
- **유스케이스 다이어그램(Use-Case Diagram)** : 사용자(액터)와 시스템이 제공하는 기능의 관계를 표현하는 다이어그램

</details>

## 2~4교시 25점 답안

## Ⅰ. UML 다이어그램의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **UML** 은 소프트웨어의 구조와 행위를 표준 표기로 나타내는 모델링 언어 |
| 목적 | 이해관계자 간 설계 의사소통과 분석·설계 결과의 통일된 표현 |

## Ⅱ. UML 다이어그램의 특징

| 특징 | 의미 |
|---|---|
| 표준 표기 | 개발자 간 동일한 기호 사용 |
| 관점별 다이어그램 | 정적 구조와 동적 행위를 구분해 표현 |
| 단계 연계 | 요구·분석·설계 단계에 걸친 사용 |

## Ⅲ. UML의 분류와 행위 다이어그램

### UML 다이어그램의 분류

```text
UML 2.x 다이어그램
    │
    ├─ 구조 다이어그램 (7종)
    │     클래스·객체·컴포넌트·복합체 구조·패키지·배치·프로파일
    │
    └─ 행위 다이어그램 (7종)
          유스케이스·활동·상태 머신·순차·통신·상호작용 개요·타이밍
```

### 확대: 세 행위 다이어그램의 표현 대상

```text
유스케이스 다이어그램 → 누가(액터) 무엇을(기능) 사용하는가
    ↓ 기능별 처리 흐름
활동 다이어그램 → 처리가 어떤 순서·분기·병렬로 진행되는가
    ↓ 객체의 상태 변화
상태 다이어그램 → 객체가 이벤트에 따라 어떤 상태로 바뀌는가
```

## Ⅳ. 활동·상태·유스케이스 다이어그램의 비교

| 구분 | 유스케이스 | 활동 | 상태 |
|---|---|---|---|
| 표현 대상 | 사용자와 시스템 기능의 관계 | 업무·처리의 흐름 | 객체의 상태와 전이 |
| 주요 요소 | 액터, 유스케이스, 시스템 경계, 포함(include)·확장(extend) | 액션, 시작·종료, 결정·병합, 포크·조인, 스윔레인 | 상태, 전이, 이벤트, 가드 조건, 액션 |
| 사용 시점 | 요구 분석 | 기능·업무 흐름 분석 | 상태 변화가 복잡한 객체 설계 |
| 예시 | 주문 시스템의 고객·결제 기능 | 주문 접수에서 출고까지 흐름 | 주문의 접수·결제·배송·완료 상태 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 다이어그램 종류 선택 혼동으로 하나에 요구·흐름·상태를 혼합 | 표현 대상에 맞는 다이어그램 선택 |
| 다이어그램 간 불일치로 모델 신뢰 저하 | 유스케이스의 기능이 활동·상태 다이어그램의 대상과 대응하는지 확인 |
| 과도한 상세화로 유지 부담 | 핵심 기능과 상태 변화가 복잡한 객체에만 상세 모델 작성 |

## Ⅵ. 제언

요구는 유스케이스로 시작하고, 기능별 처리 흐름은 활동 다이어그램으로, 상태 변화가 복잡한 객체만 상태 다이어그램으로 정제

### 모델링 정제 순서

```text
유스케이스 → 활동 다이어그램 → 상태 다이어그램(필요한 객체만)
```

### 선택 근거: 단일 다이어그램 혼합과의 비교

| 구분 | 하나에 혼합 | 제언: 목적별 정제 |
|---|---|---|
| 가독성 | 낮음 | 높음 |
| 검증 | 요구·흐름 구분 곤란 | 단계별 검증 |
| 유지보수 | 변경 영향 파악 곤란 | 변경 대상 다이어그램만 수정 |
