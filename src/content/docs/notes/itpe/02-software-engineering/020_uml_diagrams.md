## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 아키텍처·설계 → **UML 다이어그램 체계(활동 다이어그램)**

## 30초 인출

- 본질: UML(Unified Modeling Language)은 객체지향 소프트웨어 시스템의 산출물을 가시화, 명세화, 구축, 문서화하기 위한 OMG 표준 통합 모델링 언어
- 메커니즘: 시스템의 정적 형상을 표현하는 구조 다이어그램(7종)과 동적 실행 흐름을 표현하는 행위 다이어그램(7종, 활동 다이어그램 포함)의 복합 뷰 제공
- 통찰: 과도한 정적 모델링만으로는 병렬 업무 처리와 예외 흐름 통제가 어려우므로 Fork/Join과 스윔레인을 활용한 활동 다이어그램 기반의 업무-시스템 연계 설계 적용

<details>
<summary>핵심 용어</summary>

- **UML(Unified Modeling Language)** : 객체지향 분석·설계 방법론을 표준화하여 소프트웨어 아키텍처와 로직을 시각적으로 명세하는 표준 모델링 언어
- **Structural Diagram(구조 다이어그램)** : 클래스, 객체, 컴포넌트, 배치 등 시스템의 정적 구성요소와 그들 간의 관계를 표현하는 7종의 다이어그램
- **Behavioral Diagram(행위 다이어그램)** : 유스케이스, 활동, 상태, 순차 등 시스템의 동적 상호작용과 시간적 변화를 표현하는 7종의 다이어그램
- **Activity Diagram(활동 다이어그램)** : 시스템 내부의 비즈니스 프로세스, 제어 흐름, 병렬 작업(Fork/Join) 및 데이터 흐름을 표현하는 다이어그램
- **Swimlane(스윔레인)** : 활동 다이어그램에서 액션을 수행하는 역할자(고객, 시스템, 외부 연계 기관 등)를 열이나 행 단위로 구분하는 구획
- **Fork / Join Node** : 하나의 흐름을 복수의 병렬 흐름으로 분기(Fork)하거나, 복수의 병렬 흐름이 모두 완료될 때까지 동기화 대기 후 합류(Join)시키는 노드

## 2~4교시 25점 답안

## Ⅰ. UML의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **UML(Unified Modeling Language)** 은 소프트웨어 시스템의 구조적 특성과 동적 행위를 표준 표기법으로 가시화하고 명세하는 객체지향 통합 모델링 언어 |
| 목적 | 이해관계자 간 아키텍처 의사소통 표준화, 복잡한 비즈니스 로직 가시화 및 모델 기반 자동화 코드 생성 |

## Ⅱ. UML의 핵심 특징

| 특징 | 의미 |
|---|---|
| 표준화된 표기 | OMG 공인 표준 메타모델에 기반하여 플랫폼과 벤더에 독립적인 다이어그램 규격 제공 |
| 다중 뷰(View) 지원 | 4+1 View 아키텍처 관점에 맞추어 유스케이스, 정적 구조, 동적 행위, 물리적 배치를 유기적 표현 |
| 추상화 수준 조절 | 개념적 요구사항 수준부터 상세 클래스 인터페이스 및 배포 노드까지 단계별 상세화 지원 |

## Ⅲ. 활동 다이어그램(Activity Diagram) 제어 흐름 메커니즘

### 스윔레인(Swimlane) 및 병렬 처리(Fork/Join) 구조

```text
[고객 (Customer)]          [주문 시스템 (Order)]      [결제 서비스 (Payment)]
  ● (시작)
  │
  ▼
[상품 주문 요청] ─────────→ [주문 정보 생성]
                                  │
                                  ▼ (Fork: 병렬 분기)
                      ┌───────────┴───────────┐
                      │                       │
                      ▼                       ▼
                 [재고 차감]            [결제 승인 요청] ──→ [승인 처리]
                      │                       │                    │
                      │                       │ ←──────────────────┘
                      └───────────┬───────────┘
                                  ▼ (Join: 동기화 대기)
                            [주문 완료 처리]
                                  │
                                  ▼
                               ◎ (종료)
```

| 구성요소 | UML 표기 심볼 | 핵심 역할 및 기능 |
|---|---|---|
| 초기/최종 노드 | 채워진 원(●) / 이중 원(◎) | 활동 프로세스의 시작점과 전체 프로세스의 종료점 지정 |
| 액션 노드 (Action) | 모서리가 둥근 사각형 | 실행 가능한 최소 단위의 작업 또는 연산 표현 |
| 제어 흐름 (Flow) | 실선 화살표 (`→`) | 이전 액션 완료 후 다음 액션으로의 제어권 전이 |
| 판단/병합 (Decision/Merge) | 마름모 (`◇`) | 가드 조건(`[조건]`)에 따른 단일 경로 분기 및 다중 경로의 단순 결합 |
| 분기 노드 (Fork) | 굵은 가로선 (1:N) | 단일 진입 흐름을 동시에 실행되는 2개 이상의 병렬 흐름으로 복제 분기 |
| 결합 노드 (Join) | 굵은 가로선 (N:1) | 분기된 모든 병렬 작업이 완료될 때까지 대기 후 단일 흐름으로 동기화 |
| 스윔레인 (Swimlane) | 수직 또는 수평 분할 구획선 | 액션을 담당하는 주체(조직, 시스템 모듈, 액터)별 책임 할당 |

## Ⅳ. UML 2.x 다이어그램 14종 분류 체계

```text
UML 다이어그램 (14종)
 ├─ 구조 다이어그램 (Structural Diagrams, 7종)
 │   ├─ Class Diagram (클래스 구조 및 관계)
 │   ├─ Object Diagram (런타임 객체 인스턴스)
 │   ├─ Component Diagram (컴포넌트 및 인터페이스)
 │   ├─ Deployment Diagram (물리 노드 및 인프라 배치)
 │   ├─ Package Diagram (패키지 네임스페이스 및 의존성)
 │   ├─ Composite Structure Diagram (복합체 내부 구조)
 │   └─ Profile Diagram (스테레오타입 확장 메커니즘)
 └─ 행위 다이어그램 (Behavioral Diagrams, 7종)
     ├─ Use Case Diagram (외부 액터와 요구 기능)
     ├─ Activity Diagram (업무 흐름 및 병렬 제어)
     ├─ State Machine Diagram (객체 상태 전이 생명주기)
     └─ 상호작용 다이어그램 (Interaction, 4종)
         ├─ Sequence Diagram (시간순 메시지 교환)
         ├─ Communication Diagram (객체 간 링크 중심 메시지)
         ├─ Timing Diagram (시간 제약 및 상태 변화)
         └─ Interaction Overview Diagram (상호작용 흐름도)
```

### 주요 행위 다이어그램 간 특성 비교

| 비교 항목 | 유스케이스 다이어그램 | 순차 다이어그램 (Sequence) | 활동 다이어그램 (Activity) | 상태 다이어그램 (State) |
|---|---|---|---|---|
| 주요 표현 대상 | 시스템의 **외부 기능 요구 범위** | 객체 간의 **시간순 상호작용** | 프로세스의 **업무 처리 제어 흐름** | 단일 객체의 **상태 변화 생명주기** |
| 표현 강점 | 액터와의 시스템 경계 명확화 | 메서드 호출 순서 및 리턴 가시화 | **Fork/Join 병렬 처리 명세** | 이벤트 기반 상태 전이 규칙 |
| 주 활용 단계 | 요구사항 정의 및 분석 단계 | 상세 설계 및 API 인터페이스 설계 | 비즈니스 프로세스 분석 및 설계 | 결제/주문 등 라이프사이클 설계 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 소프트웨어 소스코드 변경 후 UML 다이어그램 미갱신으로 인한 모델 노후화 | CI/CD 연동 코드 기반 UML 자동 역공학 도구(PlantUML, Mermaid) 도입 |
| 과도한 다이어그램 작성으로 인한 프로젝트 오버헤드 및 개발 일정 지연 | 프로젝트 특성에 맞추어 필수 다이어그램(클래스, 시퀀스, 활동) 선별 테일러링 |
| 활동 다이어그램 병렬 처리 모델링 시 Join 조건 누락으로 인한 데드락 설계 위험 | 정형 검증(Petri-Net 연계) 및 분기/합류 쌍의 무결성 검토 규칙 적용 |

## Ⅵ. 제언

텍스트 기반 UML(Docs-as-Code) 도입을 통한 모델 버전 관리와 아키텍처 생명주기 동기화

### Docs-as-Code 기반 UML 버전 관리 파이프라인

```text
개발자: Markdown 내 PlantUML/Mermaid 텍스트 스크립트 작성
    ↓
Git 저장소 커밋 및 PR 생성
    ↓
CI 파이프라인 자동 실행:
    ├─ 텍스트 UML 문법 검증 및 SVG/PNG 렌더링
    ├─ 아키텍처 문서 사이트에 자동 배포
    └─ 코드 변경과 설계 문서의 1:1 동기화 완료
```

### UML 모델링 테일러링 의사결정 체계

```text
엔지니어링 검증 목적 분석
    ↓
검증 관점별 핵심 다이어그램 선별
    ├─ 사용자 관점 기능 범위 확정 → Use Case Diagram
    ├─ 복잡한 업무 프로세스 및 병렬성 분석 → Activity Diagram
    ├─ 모듈 간 API 및 시계열 상호작용 설계 → Sequence Diagram
    └─ 데이터 및 도메인 엔티티 구조 설계 → Class Diagram
    ↓
불필요한 파생 다이어그램 생략으로 애자일 민첩성 확보
```

### 선택 근거: 전통적 CASE 도구와 Docs-as-Code 텍스트 모델링 비교

| 구분 | 상용 CASE 도구 (바이너리 저장) | 제언: Docs-as-Code 텍스트 모델링 |
|---|---|---|
| 버전 관리 | 바이너리 파일로 Git Diff 및 충돌 해결 불가 | 텍스트 코드로 Git 기반 브랜치·머지 완벽 지원 |
| 협업 접근성 | 고가의 전용 클라이언트 설치 필수 | 일반 텍스트 에디터로 누구나 즉시 수정 가능 |
| 동기화 유지 | 소스코드 변경 시 모델 방치 빈발 | 코드 커밋과 동일 파이프라인에서 자동 갱신 |
