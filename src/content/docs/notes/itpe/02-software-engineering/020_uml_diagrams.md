## 연관 키워드

- UML(Unified Modeling Language), OMG(Object Management Group), 구조 다이어그램, 행위 다이어그램
- 활동 다이어그램(Activity Diagram), 포크/조인(Fork/Join), 스윔레인(Swimlane), Diagrams as Code

## Ⅰ. UML 다이어그램 체계의 개요

- 핵심 요약 : 객체지향 시스템의 분석·설계·구현·배포 과정을 시각적으로 모델링하는 OMG 표준 모델링 언어.
- 개념 : 객체지향 소프트웨어의 분석, 설계, 구현, 배포를 시각적으로 모델링하기 위해 OMG(Object Management Group)가 표준화한 범용 모델링 언어 (**UML**, Unified Modeling Language).
- 배경 및 필요성 : 개발자, 설계자, 발주자가 같은 그림 언어로 소통해야 하고, 복잡한 시스템의 구조를 가시화하며, 모델 기반 개발(MDD, Model-Driven Development)의 설계 기반이 필요함.
- 주요 목적 : 정적 구조와 동적 행위를 아우르는 표준 표기법으로 설계 의사소통을 일관되게 만들며, 특히 **활동 다이어그램**(Activity Diagram)으로 업무 흐름과 분기·병렬 처리를 표현.
- UML 2.x 분류 : 정적 구조를 나타내는 구조 다이어그램 7종과 동적 변화를 나타내는 행위 다이어그램 7종, 총 14종으로 구성.

## Ⅱ. UML 다이어그램의 특징 및 장점

- 핵심 요약 : 정적 구조 7종과 동적 행위 7종의 이원 분류가 표준 표기법 위에서 이해관계자 소통을 맞추는 방식.

1. 구조 다이어그램 : 클래스, 객체, 패키지, 컴포넌트, 복합체 구조, 배치, 프로파일로 정적 구성을 표현 → 시스템의 구성 요소를 한눈에 파악.
2. 행위 다이어그램 : 유스케이스, 활동, 상태 머신과 상호작용 4종(순차, 통신, 타이밍, 상호작용 개요)으로 동적 변화를 표현 → 실행 순서와 상태 전이를 검증.
3. 표준화 : OMG 표준 표기법을 따라 도구와 조직 사이에서 모델을 주고받을 수 있음 → 설계 자산의 재사용성 확보.
4. 모델 기반 개발 기반 : 설계 청사진을 제공해 코드 생성과 검증의 근거가 됨 → 구현 간 편차 축소.

## Ⅲ. UML 다이어그램의 구조 (흐름)

- 핵심 요약 : 14종을 정적과 동적으로 나누는 분류 체계와, 활동 다이어그램의 분기·병렬 흐름 표현.

```text
[ UML 2.x 다이어그램 (14종) ]

구조 다이어그램 (7종, 정적)
  클래스, 객체, 패키지, 컴포넌트
  복합체 구조, 배치, 프로파일
          ↓
행위 다이어그램 (7종, 동적)
  유스케이스, 활동, 상태 머신
  상호작용 4종 (순차, 통신,
  타이밍, 상호작용 개요)
```

```text
[ 활동 다이어그램 : 주문 처리 ]

시작
  ↓
[ 주문 접수 ]
  ↓
< 재고 확인 >  (분기)
  ↓ 재고 있음
=== 포크 (Fork) ===
  ↓                ↓
[ 결제 승인 ]   [ 배송 준비 ]
=== 조인 (Join) ===
  ↓
[ 주문 완료 ]
  ↓
종료
```

- 활동 다이어그램의 핵심 구성요소 :

| 구성요소 | 표기와 의미 |
| --- | --- |
| 액션/액티비티 (Action/Activity) | 둥근 사각형, 실행 단위의 작업이나 복합 프로세스 |
| 분기와 병합 (Decision/Merge) | 마름모, 조건(가드)에 따른 흐름 분기와 흐름의 합류 |
| 포크와 조인 (Fork/Join) | 굵은 가로선, 병렬 흐름의 동시 분기와 모든 흐름의 완료 대기 |
| 스윔레인 (Swimlane) | 구분선, 작업을 맡은 조직이나 객체의 역할 경계 표시 |
| 객체 노드 (Object Node) | 직사각형, 액션 사이에 주고받는 데이터나 객체 상태 |

## Ⅳ. 구조 다이어그램과 행위 다이어그램의 비교

- 핵심 요약 : 구조 다이어그램은 시스템이 무엇으로 구성되는지, 행위 다이어그램은 어떻게 동작하는지를 표현.

| 비교 항목 | 구조 다이어그램 (7종) | 행위 다이어그램 (7종) |
| --- | --- | --- |
| 표현 대상 | 정적 구조 | 동적 변화 |
| 대표 종류 | 클래스, 객체, 컴포넌트, 배치 | 유스케이스, 활동, 상태 머신, 시퀀스 |
| 답하는 질문 | 무엇으로 구성되는가 | 어떻게 동작하는가 |
| 주로 쓰는 단계 | 분석·설계 초기의 도메인 모델링 | 상세 설계와 프로세스 검증 |

- 실무 핵심 : 클래스, 시퀀스, 상태 다이어그램 세 가지에 집중하는 선택적 모델링이 흔함.

## Ⅴ. UML 모델링의 한계와 방안

- 핵심 요약 : 모델과 코드의 동기화 단절, 과도한 상세화, 표기법 해석 차이를 텍스트 기반 관리와 적정 모델링으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 모델과 코드의 단절 | 개발 중 변경이 다이어그램에 반영되지 않아 방치된 문서가 됨 (Shelfware) | 텍스트 기반 다이어그램(Diagrams as Code, PlantUML, Mermaid)을 Git으로 관리 | 모델-코드 불일치 건수 |
| 과도한 상세화 | 세부 속성까지 규격대로 작성 → 설계 공수 과다와 분석 마비 (Analysis Paralysis) | 핵심 구조와 복잡한 규칙 중심의 스케치 모델링, C4 모델 병행 | 모델링 소요 시간 |
| 표기법 해석 차이 | 집약, 합성, 실체화 등의 해석이 개발자마다 달라 설계 의도가 왜곡됨 | 조직 표준 UML 스타일 가이드와 예제 카탈로그 정립 | 리뷰 지적 건수 |

## Ⅵ. 모델링 효율화에 대한 기술사적 제언

- 핵심 요약 : 모든 것을 그리지 않는 적정 모델링과, 텍스트 기반 도구로 형상관리를 일원화하는 방향.

1. 적정 모델링의 원칙 : 복잡한 업무 흐름은 활동 다이어그램, 도메인 관계는 클래스 다이어그램, 핵심 상호작용은 시퀀스 다이어그램으로 한정해 작성한다.
2. 텍스트 기반 형상관리 : 바이너리 모델 파일은 병합 충돌이 잦으므로, 텍스트 기반 도구로 작성해 소스코드와 함께 버전 관리한다.
3. 최신성 유지 자동화 : 빌드 파이프라인에서 코드 기반 리버스 엔지니어링으로 다이어그램을 갱신해, 문서와 구현이 어긋나지 않게 한다.

## Ⅶ. 결론

- 핵심 요약 : UML은 14종 표준 다이어그램으로 정적 구조와 동적 행위를 함께 표현하는 모델링 표준.
- 시사점 : 과도한 상세화를 피하고 텍스트 기반으로 최신성을 유지할 때 모델이 설계 자산으로 가치를 가짐.
