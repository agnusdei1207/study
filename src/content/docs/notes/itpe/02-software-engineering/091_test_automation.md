## 30초 인출

- 본질: **테스트 자동화(Test Automation)** 는 소프트웨어의 요구사항 검증 및 회귀 시험(Regression Test) 프로세스에서 테스트 데이터 준비, 사전조건 설정, 테스트 스크립트 실행, 기대 결과(Test Oracle) 비교 및 결함 리포팅을 소프트웨어 도구와 프레임워크를 활용하여 무인으로 자동 수행하는 공학적 활동
- 메커니즘: 테스트 스크립트 작성 → CI/CD 트리거 연동 → 가상 컨테이너 환경 프로비저닝 → 테스트 실행 및 오라클 비교 판정 → 실패 시 개발자 즉시 피드백 및 빌드 차단(Quality Gate)
- 통찰: 무분별한 UI 계층 중심의 자동화는 화면 변경 시 스크립트 유지보수 비용을 폭증시키고 플래키 테스트(Flaky Test)를 양산하므로 마틴 파울러의 테스트 피라미드(Test Pyramid) 모델에 입각하여 하위 단위·API 테스트 비중을 80% 이상으로 유지하는 구조적 최적화가 필수적임

<details>
<summary>핵심 용어</summary>

- **테스트 피라미드(Test Pyramid)** : 비용과 속도 측면에서 단위 테스트(Unit)를 최하단 기반으로 두고, API 통합 테스트, E2E UI 테스트 순으로 비중을 구성하는 아키텍처
- **플래키 테스트(Flaky Test)** : 소스코드의 수정이 전혀 없음에도 불구하고 비결정적(Non-deterministic) 네트워크 지연이나 동시성 이슈로 인해 성공과 실패가 불규칙하게 반복되는 테스트
- **테스트 오라클(Test Oracle)** : 테스트 수행 결과의 참/거짓을 객관적으로 판정하기 위해 사용되는 기준 및 사전 정의된 기대값 메커니즘
- **DDT (Data-Driven Testing)** : 테스트 로직 스크립트는 1개로 고정하고, 엑셀/CSV/DB 등 외부 파일에서 다수의 테스트 입력 데이터와 기댓값을 주입하는 방식
- **POM (Page Object Model)** : 웹/앱 UI 테스트 시 화면의 웹 요소(Selector)와 조작 비즈니스 메서드를 별도 클래스로 모듈화하여 화면 변경 영향을 국소화하는 디자인 패턴

</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 지속적 통합(CI)을 위한 테스트 자동화(Test Automation)의 개념과 도입 기대효과를 설명하고, 마틴 파울러의 테스트 피라미드(Test Pyramid) 모델, 주요 테스트 자동화 프레임워크 유형(DDT, KDT, BDD, POM) 및 플래키 테스트(Flaky Test) 방지 전략을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 테스트 계획, 테스트 케이스 작성, 실행, 기대 결과 판정 등 반복적인 테스트 활동을 스크립트와 자동화 도구를 활용하여 사람의 개입 없이 신속·정확하게 수행하는 검증 기법 |
| 목적 | 수동 테스트의 인적 오류(Human Error) 배제, 빠른 회귀 테스트(Fast Feedback)를 통한 배포 주기 단축, 결함 수정 비용(Cost of Quality) 최소화 |

## Ⅱ. 핵심 특징

테스트 자동화는 일회성 도구 도입이 아니라 아키텍처 계층별로 신뢰도와 속도를 최적화하는 공학적 접근.

| 핵심 속성 | 공학적 의미 | 실무 적용 방안 |
|---|---|---|
| **반복 실행성 (Repeatability)** | 동일한 테스트 시나리오를 횟수에 구애받지 않고 일관된 조건으로 무한 재실행 | 야간 배치(Nightly Build) 및 커밋 시 CI 파이프라인 자동 구동 |
| **결정론적 판정 (Determinism)** | 사람의 주관적 느낌을 배제하고 수학적·논리적 참 오라클(True Oracle)로 판정 | 단언문(`assertEquals`, `assertThat`) 기반 100% 명시적 검증 |
| **품질 게이트 (Quality Gate)** | 정의된 테스트 커버리지 및 성공률 미달 시 상위 환경 배포를 자동 차단 | SonarQube, GitHub Actions 브랜치 보호 규칙 연동 |
| **비용 절감 효과 (ROI)** | 초기 스크립트 작성 비용은 높으나 반복 횟수 증가에 따라 한계 비용 제로화 | 잦은 릴리스가 발생하는 핵심 비즈니스 도메인에 우선 적용 |

## Ⅲ. 체계·프로세스

테스트 피라미드(Test Pyramid) 계층 구조 및 CI/CD 파이프라인 연계 실행 체계.

```text
[테스트 피라미드 및 CI/CD 자동화 파이프라인]
/ \
                    /   \                 [3] E2E / UI 테스트 (End-to-End)
                   / UI  \                - 실행 속도: 수 분 ~ 수십 분 (느림) / 비용: 높음
                  /───────\               - 도구: Playwright, Cypress, Selenium
                 /         \              - 비중: 10% 미만 (핵심 사용자 여정 검증)
                /    API    \
               /  통합 테스트 \           [2] 서비스 / API 통합 테스트 (Integration)
              /───────────────\           - 실행 속도: 수 초 ~ 수 분 / 비용: 중간
             /                 \          - 도구: MockMvc, REST-Assured, Testcontainers
            /    단위 테스트    \         - 비중: 20~30% (서비스 간 연계 및 비즈니스 규칙)
           /     (Unit Test)     \
          /───────────────────────\       [1] 단위 테스트 (Unit Test)
                                          - 실행 속도: 밀리초(ms) 단위 (초고속) / 비용: 매우 낮음
                                          - 도구: JUnit 5, Mockito, Jest
                                          - 비중: 70% 이상 (독립 클래스/메서드 단위 로직)

───────────────────────────────────────────────────────────────────────────────────────────────────────────
  [CI 파이프라인]  Git Commit ──> 빌드 & 단위테스트 ──> API 통합테스트 ──> UI E2E ──> 자동 배포 (CD)
```

- **테스트 자동화 4단계 수립 프로세스**:
  1. **대상 선정 및 전략 수립** : 변경이 잦고 결함 발생 시 파급력이 큰 핵심 도메인의 회귀 테스트를 우선 자동화 대상으로 선정.
  2. **환경 및 테스트베드 격리** : Testcontainers 및 H2 인메모리 DB를 활용하여 외부 의존성(외부 PG사 API 등)을 Mocking 처리하고 격리된 멱등 환경 구축.
  3. **프레임워크 및 스크립트 개발** : POM 디자인 패턴 및 BDD 프레임워크를 적용하여 가독성과 유지보수성이 높은 테스트 코드 구현.
  4. **파이프라인 통합 및 지속 모니터링** : CI/CD 파이프라인의 PR 머지 단계에 테스트 잡(Job)을 등록하고 플래키 테스트 발생률을 상시 추적.

## Ⅳ. 종류·비교

#### 테스트 자동화 4대 프레임워크 아키텍처 비교

| 프레임워크 유형 | 핵심 개념 및 메커니즘 | 주요 장점 | 한계 및 극복 방안 |
|---|---|---|---|
| **DDT (Data-Driven)** | 테스트 스크립트와 입력 데이터를 분리하여 외부 파일(CSV, Excel, DB)에서 파라미터 주입 | 동일 스크립트로 대량의 경계값/동등분할 데이터 반복 시험 용이 | 데이터 파일과 스크립트 간 매핑 관리 공수 발생 |
| **KDT (Keyword-Driven)**| 클릭, 입력, 검증 등 테스트 액션을 '키워드(Action Word)'로 추상화하여 스프레드시트로 작성 | 비개발자(QA, 비즈니스 기획자)도 쉽게 테스트 케이스 작성 가능 | 키워드 파서 및 커스텀 액션 엔진 자체 개발 비용 큼 |
| **BDD (Behavior-Driven)**| `Given-When-Then` 자연어 도메인 언어로 사용자 시나리오 명세서를 작성하고 코드로 바인딩 | 개발자-테스터-기획자 간 단일 진실 공급원(SSOT) 형성 (Cucumber) | 시나리오 정규식 파싱 오버헤드 및 명세 관리 비용 |
| **POM (Page Object Model)**| UI 웹 페이지의 HTML 요소(Selector)와 인터랙션 로직을 별도 Page Object 클래스로 캡슐화 | UI 컴포넌트 ID/클래스 변경 시 비즈니스 테스트 코드 수정 제로화 | 초기 페이지 모델링 클래스 설계 공수 발생 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 비동기 네트워크 지연, 애니메이션 렌더링 미완료로 인해 발생하는 간헐적 실패(Flaky Test) | 무조건적인 `sleep()` 대기를 전면 금지하고 명시적 대기(Explicit Wait, `waitForSelector`)를 표준 적용 |
| UI 디자인 리뉴얼 시 수백 개의 웹/모바일 자동화 스크립트가 일괄 깨지는 유지보수 재앙 | Page Object Model(POM)을 엄격히 적용하고 UI 테스트 대신 빠르고 견고한 REST API 계층 테스트 비중 확대 |
| CI 파이프라인에서 수천 개의 테스트 스위트 실행 시 빌드 시간이 1시간 이상 지연되는 문제 | 테스트 병렬 실행(Parallel Test Runner) 도입 및 영향도 분석 기반 변경된 모듈의 테스트만 선별 실행 |

## Ⅵ. 제언

테스트 자동화의 성공을 위해서는 테스트 피라미드의 건전성을 유지하고, 간헐적 실패를 유발하는 플래키 테스트를 격리하여 자동으로 재시도하거나 분석하는 신뢰성 관리 파이프라인을 구축할 필요가 있음.

```text
[PR 생성] ──> [병렬 단위/통합 테스트] ──> [Quality Gate 판정] ──> [Flaky 테스트 격리(Quarantine)] ──> [배포 승인]
               (Mocking & Testcontainers)    (커버리지 80% 통과)        (1회 실패 시 3회 재시도)            (배포 자동화)
```

| 관리 영역 | 핵심 엔지니어링 실천법 | 통제 지표 |
|---|---|---|
| **피라미드 비율 유지** | 단위:통합:E2E = 70:20:10 비율 강제 | 아이스크림 콘 안티패턴(UI 과다) 발생 방지 |
| **플래키 테스트 통제** | Flaky 발생 테스트는 즉시 격리(Quarantine) 레인 이동 | 테스트 스위트 신뢰도(Flaky 발생률) 1% 미만 유지 |
| **피드백 속도 최적화** | Docker 기반 빌드 캐싱 및 병렬 테스트 러너 가동 | PR 단위 전체 자동화 테스트 완료 시간 10분 이내 달성 |
