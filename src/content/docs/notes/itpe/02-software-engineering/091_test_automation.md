## 1. 테스트 자동화의 개요 및 필요성

### (1) 테스트 자동화(Test Automation)의 정의
- 소프트웨어의 반복적인 테스트 수행, 테스트 데이터 생성, 결과 검증 및 리포팅 과정을 수작업 대신 **전용 소프트웨어 도구와 테스트 스크립트를 활용하여 기계적으로 자동 실행하는 품질 보증 엔지니어링 활동**.

### (2) 핵심 필요성 (121회 3교시 기출)
- **회귀 결함(Regression Defect) 조기 차단**: 코드 변경 시마다 수작업으로 전수 테스트할 수 없는 한계를 극복하고 커밋 단위 즉각 피드백 제공.
- **배포 주기 단축 및 지속적 테스팅(CT)**: CI/CD 파이프라인과 결합하여 빌드-테스트-배포의 전 과정을 자동화함으로써 비즈니스 민첩성 확보.
- **인적 오류(Human Error) 배제 및 테스트 오라클 일관성**: 사람이 장시간 반복 테스트 시 피로로 인해 결함을 놓치는 휴먼 에러 원천 방지.

## 2. 테스트 피라미드 구조 및 핵심 원리

### (1) 이상적인 테스트 피라미드 vs 안티패턴 구조도
```text
+-------------------------------------------------------------------------+
|               이상적인 테스트 피라미드 vs 아이스크림 콘 안티패턴        |
+-------------------------------------------------------------------------+
|   [ 이상적 테스트 피라미드 (Mike Cohn) ]      [ 아이스크림 콘 안티패턴 ]  |
|                                                                         |
|                  / \                                 \     /            |
|                 / UI \  (10%: E2E/화면)               \ UI/  (90% 수동/  |
|                /------\                                \-/    E2E 편중) |
|               / Service\ (20%: API/통합)               | |   (통합 부족) |
|              /----------\                             /---\             |
|             /    Unit    \ (70%: 단위 테스트)        /Unit \ (단위 전무) |
|            +--------------+                         +-------+           |
|  * 특징: 빠름, 저비용, 높은 결정론(안정성)     * 특징: 극도로 느림, Flaky|
+-------------------------------------------------------------------------+
```

### (2) 피라미드 계층별 상세 비교
| 계층 | 테스트 범위 | 실행 속도 및 비용 | 대표 도구 및 기술 |
|---|---|---|---|
| **UI / E2E 계층 (10%)** | 사용자 브라우저 화면 조작, 전 구간 통합 | 가장 느림 (수십 초~분), 유지보수 고비용 | Playwright, Cypress, Selenium |
| **서비스 / API 계층 (20%)** | 마이크로서비스 간 REST/gRPC 통신, DB 연동 | 중간 (수백 ms), 비즈니스 흐름 검증 | RestAssured, WireMock, Postman |
| **단위 테스트 계층 (70%)** | 개별 클래스, 순수 비즈니스 메서드, 도메인 로직 | **가장 빠름 (수 ms), 비용 극소, 멱등성 보장** | JUnit 5, Mockito, Jest, PyTest |

## 3. 테스트 자동화 프레임워크 4대 유형 비교

| 프레임워크 유형 | 동작 원리 및 메커니즘 | 핵심 장점 | 주요 단점 및 고려사항 |
|---|---|---|---|
| **모듈 기반 (Modular)** | 테스트 코드를 작은 독립 모듈 함수로 분할 | 스크립트 재사용성 제고 | 데이터가 하드코딩되어 데이터 변경 시 취약 |
| **데이터 주도 (DDT)** | 테스트 로직과 테스트 데이터(Excel, CSV, DB)를 분리 | 동일 로직에 수천 개 데이터 반복 검증 가능 | 데이터 파싱 엔진 구현 필요 |
| **키워드 주도 (KDT)** | 동작(Click, Type, Verify)을 표준 키워드로 정의 | 비개발자(기획, QA)도 시나리오 작성 가능 | 초기 키워드 라이브러리 개발 공수 과다 |
| **행위 주도 (BDD)** | 자연어 문장(Given-When-Then)으로 시나리오 기술 | 요구명세가 곧 실행 가능한 테스트로 동기화 | 시나리오 매핑 글루 코드(Glue Code) 유지보수 필요 |

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **UI 화면 텍스트 수정 시 200개 테스트 전멸**<br>(자동화 스크립트 유지보수 불능으로 폐기) | 화면 요소 XPath에 직접 의존한 취약한 셀렉터 및 Page Object Model(POM) 미적용 | Page Object Model 도입 및 테스트 전용 속성(`data-testid`) 기반 셀렉터 분리 | UI 변경 시 스크립트 수정 공수 85% 절감 |
| **테스트 실행 시간 4시간 소요로 CI 정체**<br>(개발자가 테스트 패스 없이 강제 배포) | 모든 테스트를 직렬로 실행하고 무거운 실제 외부 DB에 의존 | 테스트 병렬 실행(Parallel Runner) 및 Testcontainers 기반 인메모리 격리 실행 | 전체 빌드 테스트 시간 4시간에서 12분으로 단축 |
| **원인 불명으로 간헐적 실패하는 Flaky Test**<br>(테스트 신뢰도 추락으로 경보 무시) | 네트워크 비동기 렌더링 딜레이를 무시한 `sleep()` 하드코딩 남발 | 스마트 명시적 대기(Explicit Wait) 적용 및 Flaky Test 격리 쿼런틴(Quarantine) 운영 | 빌드 거짓 경보(False Positive) 98% 제거 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 단순 테스트 자동화 도구 도입]          [현대: 지속적 테스팅(Continuous Testing) 생태계]
- 상용 도구 구매 후 스크립트 방치         ──▶  - 오픈소스(Playwright/JUnit) 기반 경량 자동화 표준
- 아이스크림 콘 안티패턴 편중 (UI 90%)    ──▶  - 테스트 피라미드(단위 70% + API 20% + UI 10%) 준수
- 빌드 통과용 형식적 커버리지 집착        ──▶  - 뮤테이션 테스팅(Mutation Score) 기반 테스트 결함 검출력 평가
```

- **지속적 테스팅(Continuous Testing)으로의 패러다임 전환**: 테스트 자동화는 단순 스크립트 작성이 아님. 개발자가 코드를 커밋하는 순간부터 프로덕션 모니터링까지 **전 생애주기에 걸쳐 품질 게이트(SonarQube 정적 검사 $\rightarrow$ JUnit 단위 $\rightarrow$ API 통합 $\rightarrow$ 카나리 카오스 테스팅)를 자동으로 구동하는 지속적 테스팅(CT)** 체계로 격상해야 함.
- **AI 기반 자동화 테스트의 미래 (Generative Testing)**: 최근에는 테스터가 일일이 코드를 짜는 방식에서 벗어나, **LLM 에이전트가 요구사항 명세서와 OpenAPI 스펙을 파싱하여 엣지 케이스 테스트 코드와 모의 데이터를 자동 생성하는 'AI 네이티브 테스트 생성'** 및 실행 중 UI가 변경되어도 스스로 셀렉터를 찾아 복구하는 '자가 치유(Self-Healing) 테스트'를 기술사의 첨단 대안으로 제시해야 함.
