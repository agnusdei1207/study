## 한 줄 본질
- 배포 주기가 빨라질수록 수동 회귀 테스트에 드는 시간과 비용이 기하급수적으로 폭증하는 릴리스 정체 병목 → 테스트 입력과 기대 결과 판정 로직을 코드로 작성하여 CI/CD 빌드 시 자동 실행 → 즉각적인 결함 피드백과 릴리스 속도 확보 / 스크립트 유지보수 비용 발생

## 핵심 용어
- 깨지기 쉬운 테스트(Flaky Test): 소스코드에 아무런 결함이 없음에도 불구하고 네트워크 지연, 렌더링 타이밍, 비동기 레이스 컨디션 등으로 인해 간헐적으로 성공/실패가 뒤바뀌는 불안정한 테스트
- Page Object Model(POM): UI 테스트 자동화 시 화면의 웹 요소(버튼, 입력창)와 테스트 로직을 분리하여, UI 변경 시 유지보수 비용을 최소화하는 객체 모델링 디자인 패턴

## 핵심 통찰
- 모든 테스트를 자동화하려는 시도는 실패하며, "반복성이 높고, 변경이 드물며, 비즈니스 리스크가 큰 핵심 영역"부터 자동화 ROI(투자수익률)를 따져 점진적으로 적용해야 함
- UI 기반의 E2E 테스트(Selenium 등)에 과도하게 의존하는 '아이스크림 콘' 구조는 화면이 조금만 바뀌어도 수백 개 테스트가 깨지는 유지보수 재앙을 낳음
- 진정한 테스트 자동화는 개발자가 코드를 작성하는 즉시 실행되는 '격리된 단위 테스트'와 'REST/gRPC API 통합 테스트'가 90% 이상을 지탱해야 함

## 이웃 토픽과 구분
- 테스트 자동화 vs 지속적 테스팅(Continuous Testing): 테스트 자동화 = 특정 테스트 케이스를 도구로 실행하는 '기술적 수단' / 지속적 테스팅 = CI/CD 파이프라인 전 과정에서 품질 게이트를 걸고 비즈니스 리스크를 상시 평가하는 '프로세스 문화'

## 문제·원인·대책
- 사례: 121회 기출 UI E2E 테스트 300개가 빌드마다 30%씩 깨져 결국 자동화 테스트 전체 폐기
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 화면 CSS 클래스 변경 및 렌더링 딜레이로 E2E 테스트 오탐(False Alarm) 빈발 | UI 요소에 강하게 결합된 취약한 XPath 사용 및 sleep 하드코딩 | Page Object Model(POM) 패턴 적용 및 명시적 대기(Explicit Wait) 전환 | 테스트 실패율(Flaky Rate) 30%에서 1% 미만으로 안정화 |
| 테스트 실행 시간이 3시간을 넘어가 개발자가 커밋 전 테스트 생략 | 수천 개 테스트의 직렬 단일 스레드 실행 및 무거운 DB 의존 | 병렬 테스트 러너(Parallel Runner) 및 인메모리 격리 DB(H2, Mock) 도입 | 테스트 전체 실행 시간 10분 이내 단축 |
