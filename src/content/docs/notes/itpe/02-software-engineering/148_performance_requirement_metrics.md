 ┃
 ┣━ Ⅰ 개요 ───── 정성적 문구("빠르게 응답할 것")로 인한 검수 분쟁 → 시스템 부하 및 처리 능력을 객관적으로 측정·검증 가능한 정량 지표 정의
 ┣━ Ⅱ 특징 ───── 비기능 요구사항 핵심 · 측정 가능성(Measurability) · SMART 원칙 준수 · 동시 사용자-처리량-응답시간의 상호 연관성

 ┗━ Ⅵ 실무 ───── 평균값 착시(Tail Latency 누락) / 리틀의 법칙(Little's Law) 부재 / 공공 정보화 RFP 성능 요구 명세

## 한 줄 본질
- "시스템이 원활하게 구동되어야 한다"는 주관적 요구로 인해 오픈 당일 서버가 뻗고 계약 분쟁이 발생하는 병목 → 응답시간, 처리량, 동시 접속자 수, 시스템 자원 임계치를 숫자로 규정하여 계약 및 검수의 공학적 기준을 세우는 비기능 성능 척도 / 과도한 지표 설정 시 비용 급증

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  정보시스템 4대 성능 요구사항 지표 체계                 |
+-------------------------------------------------------------------------+
|                                                                         |
|      [ 1. 사용자 체감 지표 ]              [ 2. 시스템 처리 능력 지표 ]    |
|      - 응답 시간 (Response Time)          - 처리량 (Throughput)          |
|        * 평균(Avg) 및 95% 백분위수(p95)    * TPS (초당 트랜잭션 수)       |
|      - 지연 시간 (Latency)                * BPS (초당 전송 바이트 수)     |
|                     │                                   │               |
|                     └─────────────────┬─────────────────┘               |
|                                       │                                 |
|      [ 리틀의 법칙: L = λ × W ]       │ Concurrency = TPS × ResponseTime |
|                                       v                                 |
|      [ 3. 동시 사용자 지표 ]              [ 4. 시스템 자원 사용률 지표 ]  |
|      - 동시 사용자 (Concurrent User)      - CPU / 메모리 사용률 (≤ 70%)  |
|        * Active User (실제 트랜잭션)      - 디스크 I/O (IOPS, Queue)     |
|        * Inactive User (단순 접속/대기)   - 네트워크 대역폭 (Bandwidth)  |
|                                                                         |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 리틀의 법칙(Little's Law): 안정적인 시스템 내에 머무는 평균 고객 수($L$)는 고객의 평균 도착률($\lambda$)과 고객이 시스템에 머무는 평균 시간($W$)의 곱과 같다는 법칙 ($L = \lambda \times W$, 동시 활성 사용자 수 = TPS $\times$ 평균 응답시간)
- 테일 레이턴시(Tail Latency): 99%(p99)나 99.9%(p99.9)의 극소수 사용자가 겪는 최악의 지연 시간으로, 마이크로서비스 환경에서 전체 사용자 경험을 지배하는 지연 현상

## 핵심 통찰
- 실무에서 "평균 응답시간 2초 이내"라는 지표는 가장 위험한 함정임: 90%의 사용자가 0.1초 만에 응답을 받아도, 나머지 10%의 핵심 결제 사용자가 20초의 지연을 겪으면 평균은 2초로 계산되어 지표를 만족하지만 실제 비즈니스는 마비됨
- 따라서 성능 요구사항은 반드시 백분위수(Percentile)를 명시하여 "평상시 p95 1.5초 이내, 피크 부하 시 p99 3초 이내"처럼 극단치(Tail)를 방어하도록 작성해야 함
- 동시 사용자를 산정할 때 단순히 브라우저를 띄워놓고 있는 "로그인 사용자(Concurrent Inactive)"와 실제로 서버에 초당 쿼리를 날리는 "활성 사용자(Active User)"를 철저히 구분해야 서버 사이징 왜곡을 막을 수 있음

## 이웃 토픽과 구분
- 응답시간(Response Time) vs 지연시간(Latency): 지연시간 = 패킷이 네트워크를 건너 시스템에 도달하는 데 걸리는 대기 시간 / 응답시간 = 클라이언트가 요청을 보낸 시점부터 서버 연산을 거쳐 응답의 마지막 바이트를 수신할 때까지의 전체 소요 시간

## 문제·원인·대책
- 적용 상황: 수강신청 및 명절 열차표 예매 시스템 성능 요구사항 정의
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 오픈 당일 동시 접속자가 몰리며 화면이 30초 이상 로딩되어 대규모 민원 폭발 | 제안요청서에 평상시 평균 트래픽만 기준으로 성능 지표를 정의함 | 피크 계수(Peak Factor)를 반영한 피크 TPS 산정 및 p99 응답시간 3초 이하 기준 명시 | 피크 부하 시 성능 목표 검증 및 용량 증설 |
| 부하 시험에서 CPU 사용률이 95%에 도달하여 시스템 다운 직전까지 감 | 응답시간만 지표로 두고 하드웨어 자원 임계치(CPU/메모리) 요구사항 누락 | 성능 지표에 "최대 부하 시 CPU 및 메모리 사용률 70% 이하 유지" 제약 추가 | 시스템 안정적 마진 확보 및 스로틀링 방지 |

## 내 의견
- [요구사항 명세서의 성능 지표와 실제 배포 모니터링의 단절 해소] RFP에 적힌 성능 지표가 개발 완료 후 감리 BMT 보고서에만 쓰이고 실제 운영 환경에서는 측정되지 않는 문제 빈발 → 나라면: 요구사항에 명시된 TPS 및 p95/p99 응답시간 목표치를 프로메테우스(Prometheus) Alertmanager의 알람 임계치로 자동 등록하여, 운영 중 성능 요구 수준을 벗어나는 즉시 엔지니어링 팀에 경보가 울리는 지속적 성능 감시(Continuous Performance Monitoring) 체계 구축
