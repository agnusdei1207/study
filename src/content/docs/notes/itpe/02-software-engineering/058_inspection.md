## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 테스트·품질 → 정적 검토 → **인스펙션(Inspection)**

## 30초 인출

- 본질: 소프트웨어 개발 산출물(요구사항, 설계서, 소스코드)의 결함을 조기에 검출하기 위해 정해진 규칙과 절차, 엄격한 역할을 부여받은 동료들이 모여 수행하는 가장 정형화된 동료 검토 기법
- 메커니즘: 마이클 패건(Michael Fagan)의 6단계 프로세스(계획 → 개요 설명 → 개별 준비 → 검토 회의 → 재작업 → 후속 조치) 및 5대 전문 역할 분담(중재자, 낭독자, 작성자, 기록자, 검토자)
- 통찰: 검토 회의가 해결책 논쟁이나 인사 평가로 변질될 경우 본래의 결함 식별 기능이 마비되므로 해결책 논의를 배제한 순수 결함 식별 중심 진행과 중재자(Moderator)의 독립적 권한 보장 필수

<details>
<summary>핵심 용어</summary>

- **Fagan Inspection(패건 인스펙션)** : IBM의 마이클 패건이 창안한 기법으로 체크리스트와 통계적 측정 기준을 사용하는 가장 엄격한 정형 검토
- **Moderator(중재자/주재자)** : 인스펙션 전 과정을 총괄하고 회의가 결함 식별에만 집중되도록 중립적으로 통제하는 핵심 리더
- **Reader(낭독자)** : 산출물의 내용을 한 줄씩 또는 논리 단위로 팀원들에게 구두로 설명하며 검토 흐름을 이끄는 역할자
- **Recorder(기록자)** : 발견된 모든 결함의 위치, 심각도, 유형을 표준 결함 기록서(Defect Log)에 실시간으로 작성하는 역할자
- **Entry & Exit Criteria(진입 및 종료 조건)** : 인스펙션을 개시하기 위한 사전 품질 요건과 인스펙션을 공식 완료로 판정하기 위한 통과 기준선
- **IEEE 1028** : 소프트웨어 정적 검토를 인스펙션, 워크스루, 기술 검토, 관리 검토, 감사 5종으로 분류하고 표준 절차를 규정한 국제 규격

</details>

## 2~4교시 25점 답안

## Ⅰ. 인스펙션의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 생명주기 산출물(SRS, 아키텍처 설계서, 소스코드, 테스트 케이스)에 존재하는 결함을 프로그램을 직접 실행하지 않고, 정형화된 절차와 체크리스트에 따라 육안으로 찾아내는 공식 정적 검토(Formal Peer Review) 기법 |
| 목적 | 개발 초기 단계의 결함 조기 검출(Defect Early Detection), 결함 수정 비용(Cost of Quality)의 획기적 절감 및 팀 전반의 코딩 표준 준수율 향상 |

## Ⅱ. 인스펙션의 핵심 특징

| 특징 | 의미 |
|---|---|
| 최고 수준의 정형성 | IEEE 1028 분류 검토 기법 중 가장 엄격한 규칙, 문서화된 체크리스트, 측정 메트릭 적용 |
| 명확한 5대 역할 분담 | 중재자(Moderator), 낭독자(Reader), 기록자(Recorder), 작성자(Author), 검토자(Inspector)의 분업화 |
| 결함 식별과 해결의 분리 | 검토 회의 시간 내에는 오직 결함의 유무와 위치만 기록하며, 해결책(Fix) 논의는 철저히 배제 |
| 진입 및 종료 기준 통제 | 산출물 완성도 미흡 시 회의 착수를 거부하고(Entry 조건), 미해결 결함 0건 달성 시에만 종료(Exit 조건) |

## Ⅲ. 마이클 패건(Fagan) 인스펙션 6단계 체계 및 실행 프로세스

### 인스펙션 전주기 6단계 절차도

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. 계획 (Planning)                                                     │
│    - 인스펙션 대상 선정, 팀 구성, 중재자 지정, 일정 및 장소 조율      │
│    - [진입 조건(Entry Criteria) 검사]: 린트 검사 및 기본 정적 분석 통과 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 통과
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. 개요 설명 (Overview - 선택적)                                       │
│    - 작성자가 검토 대상 산출물의 배경, 아키텍처 맥락, 특이사항 공유   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. 개별 준비 (Preparation)                                             │
│    - 검토자들이 회의 전 체크리스트를 기반으로 산출물을 개별 심층 독독  │
│    - 예상 결함 후보 메모, [준비 시간 기준(예: 시간당 200줄) 준수]       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 개별 준비 완료 확인
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. 검토 회의 (Inspection Meeting - 최대 2시간)                         │
│    - 중재자의 진행하에 [낭독자(Reader)]가 산출물을 순차적으로 낭독     │
│    - 검토자들의 결함 지적 → [기록자(Recorder)]가 결함 로그에 실시간 작성│
│    - ★ 해결책 토론 금지, 회의 종료 시 [판정(Accept/Rework/Re-inspect)] │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 재작업 판정
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 5. 재작업 (Rework)                                                     │
│    - 작성자가 결함 로그의 지적 사항을 바탕으로 산출물 직접 수정        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 수정 완료
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 6. 후속 조치 (Follow-up)                                               │
│    - 중재자가 결함 로그의 모든 항목이 올바르게 수정되었는지 전수 확인   │
│    - [종료 조건(Exit Criteria) 검사 통과 시 인스펙션 최종 공식 종료]   │
└────────────────────────────────────────────────────────────────────────┘
```

### 인스펙션 5대 역할자 책임 분석

| 역할자 | 핵심 책임 및 주요 임무 | 수행 시 주의점 |
|---|---|---|
| **중재자 (Moderator)** | 인스펙션 전 과정 주관, 회의 진행, 규칙 준수 감독, 후속 조치 승인 | 작성자에 대한 인격적 비난을 차단하고 중립 유지 |
| **낭독자 (Reader)** | 산출물을 작업자의 입장에서 자신의 말로 논리적 해석하며 순차 낭독 | 단순 책 읽기가 아닌 코드의 흐름을 능동적으로 해석 |
| **기록자 (Recorder)** | 발견된 결함의 위치, 결함 유형, 심각도(Major/Minor)를 시트에 기록 | 결함에 대한 주관적 의견을 배제하고 사실 관계만 기록 |
| **작성자 (Author)** | 산출물 원작자로서 질문에 대해 설명하고, 회의 후 재작업 직접 수행 | 결함 지적에 대해 변명하거나 방어적 태도 지양 |
| **검토자 (Inspector)** | 사전 개별 준비를 철저히 하고 표준 체크리스트에 입각하여 결함 발굴 | 산출물 표준 준수 여부와 논리적 오류 집중 탐색 |

## Ⅳ. IEEE 1028 정적 검토 5대 유형 비교

### 검토 유형 간 정형성 및 특성 비교

| 비교 항목 | 인스펙션 (Inspection) | 워크스루 (Walkthrough) | 기술 검토 (Technical Review) | 관리 검토 (Management) | 소프트웨어 감사 (Audit) |
|---|---|---|---|---|---|
| **주도자** | **독립적 중재자 (Moderator)** | **산출물 작성자 (Author)** | 기술 리더 / 수석 아키텍트 | 프로젝트 관리자 (PM) | 독립된 공인 감사인 |
| **정형성 수준** | **가장 높음 (Formal)** | 가장 낮음 (Informal) | 중간 (Semi-formal) | 높음 | 매우 높음 |
| **주요 목적** | **순수 결함 조기 식별** | 이해도 공유, 브레인스토밍 | 기술 대안 평가, 적합성 검증 | 진척 점검, 예산/일정 의사결정 | 규정 및 표준 준거성 입증 |
| **체크리스트** | **필수 사용** | 선택적 사용 | 일반적으로 사용 | 프로젝트 관리 계획서 | 감사 체크리스트 |
| **측정 메트릭** | 결함 밀도, 검토 속도 측정 | 메트릭 수집 안 함 | 기술 이슈 목록 관리 | 진척률(EVM), 리스크 지수 | 부적합(NC) 보고서 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 검토 회의 중 결함 원인 분석이나 해결 방안을 둘러싼 끝없는 기술 논쟁 발생 | 해결책 논의를 엄격히 금지하고 중재자가 발언을 제지하여 결함 식별에만 시간 집중 |
| 참가자들의 사전 개별 준비(Preparation) 부족으로 회의 시간이 단순 설명회로 전락 | 회의 시작 전 중재자가 개별 준비 시간을 점검하고 기준 미달 시 회의 즉각 취소(Entry 통제) |
| 발견된 결함 데이터가 작성자 개인의 인사 고과 및 역량 평가 자료로 악용되는 부작용 | 인스펙션 결함 데이터를 철저히 익명화하고 조직 프로세스 개선 지표로만 활용 규정 수립 |

## Ⅵ. 제언

현대적 풀 리퀘스트(PR) 기반 비동기 인스펙션과 AI 자동 정적 분석 도구의 통합 파이프라인

### 현대적 Docs/Code-as-a-Service 인스펙션 파이프라인

```text
[개발자 소스코드 / 아키텍처 문서 Git 커밋 및 PR 생성]
       ↓
[1단계: AI 정적 분석 엔진 자동 실행 (Pre-Inspection)]
  ├─ SonarQube: 코딩 컨벤션, 중복 코드, 순환복잡도 자동 검출
  ├─ Snyk / Trivy: 보안 취약점(CVE) 및 오픈소스 라이선스 검사
  └─ LLM Reviewer: 코드 로직의 모호성 및 에지 케이스 사전 코멘트
       ↓ (정적 분석 100% 통과 시에만 인간 인스펙션 진입 허용)
[2단계: GitHub / GitLab PR 기반 비동기 인스펙션 (Async Inspection)]
  ├─ 최소 2인 이상의 시니어 피어 리뷰어 필수 승인(Rule-based Approval)
  ├─ 인라인 코멘트를 통한 비즈니스 로직 및 결함 지적
  └─ 대규모 고위험 모듈의 경우 오프라인 패건 인스펙션 회의 병행 소집
       ↓
[작성자 재작업 커밋 → 모든 코멘트 Resolve 확인 후 머지]
```

### 정적 검토 방식 선정 의사결정 체계

```text
검토 대상 산출물 식별
       ↓
[미션 크리티컬 시스템(의료, 금융, 제어)의 고위험 핵심 산출물인가?]
       ├─ 예 ──→ 패건 인스펙션 (Fagan Inspection) 공식 소집 (체크리스트 필수)
       └─ 아니오 ─→ [새로운 기술 스택이나 아키텍처 대안 평가가 목적인가?]
                         ├─ 예 ──→ 기술 검토 (Technical Review) 수행
                         └─ 아니오 ─→ [팀원 간 지식 전파 및 피드백 수렴이 목적인가?]
                                           ├─ 예 ──→ 워크스루 (Walkthrough)
                                           └─ 아니오 ─→ 표준 Git Pull Request 코드 리뷰
```

### 선택 근거: 전통적 오프라인 인스펙션과 제언 비동기 AI 하이브리드 인스펙션 비교

| 구분 | 전통적 오프라인 패건 인스펙션 | 제언: AI 하이브리드 비동기 인스펙션 |
|---|---|---|
| 일정 조율 | 다수 인원의 회의실 일정 조율로 며칠 지연 발생 | Git PR 기반 비동기 리뷰로 즉각적인 코드 검토 가능 |
| 단순 오류 검출 | 인간이 오탈자, 컨벤션 위반 등 단순 실수 검토에 시간 낭비 | AI 및 정적 분석 도구가 1차 전수 필터링 완료 |
| 심층 로직 집중 | 단순 오류 찾기에 지쳐 핵심 아키텍처 결함 간과 | 인간 검토자는 고차원 비즈니스 로직과 안전성 검토에만 집중 |
