## 연관 키워드

- 인스펙션(Inspection), 정적 테스트(Static Testing), 동료 검토(Peer Review)
- 페이건(Fagan) 6단계, 주재자(Moderator), 체크리스트, 결함 기록
- 워크스루(Walkthrough), 기술 검토(Technical Review), 심리적 안전감(Psychological Safety)

## Ⅰ. 인스펙션의 개요

- 핵심 요약 : 페이건(Michael Fagan)이 정립한 가장 정형화된 동료 검토 기법으로, 체크리스트와 엄격한 절차에 따라 생명주기 초기의 결함을 조기 검출.
- 개념 : 마이클 페이건(Michael Fagan)이 정립한 정적 테스트(Static Testing) 기법으로, 작성된 소프트웨어 산출물(요구명세서, 설계서, 소스코드 등)을 작성자가 아닌 독립적인 동료 전문가들이 사전에 정의된 체크리스트와 엄격한 절차에 따라 결함을 검출하는 가장 정형화된 동료 검토(Formal Peer Review) 기법.
- 배경 및 필요성 : 코드의 직접 실행 없이 생명주기 초기 단계에서 결함을 상당 부분 조기 색출하여 결함 수정 비용(Boehm의 곡선)을 획기적으로 절감.
- 주요 목적 : 산출물의 결함 전수 검출과 품질 표준 준수 확인, 정적 검증을 통한 후행 테스트 비용의 최소화.

## Ⅱ. 인스펙션의 특징

- 핵심 요약 : 정형화된 절차, 명확한 역할 분담, 체크리스트 기반 객관성, 시간·분량 제한을 특징으로 하는 공식 검토 체계.
1. 정형화된 6단계 프로세스의 준수.
2. 명확한 참여자 역할 분담(주재자, 작성자, 낭독자, 기록자).
3. 객관적 체크리스트 기반의 결함 검출.
4. 회의 시간(2시간 이내) 및 검토 분량(시간당 200 LOC(Lines of Code) 내외)의 제한.
5. 공식 결함 목록 작성과 종료 판정까지의 추적 관리.

## Ⅲ. 인스펙션의 구조 (흐름)

- 핵심 요약 : 계획부터 후속조치까지의 6단계 프로세스와 4대 참여자 역할의 협업 구조.

```text
[ 페이건 인스펙션 6단계 ]
1. 계획(Planning) : 진입조건 확인, 팀 구성·일정 수립
   ↓
2. 사전설명(Overview) : 작성자의 전체 구조 설명
   ↓
3. 준비(Preparation) : 체크리스트 기반 개별 결함 발굴
   ↓
4. 회의(Inspection) : 낭독자(Reader)의 낭독,
   기록자(Recorder)의 결함 기록
   ↓
5. 수정(Rework) : 작성자의 결함 목록 기반 수정
   ↓
6. 후속조치(Follow-up) : 주재자의 수정 완료 확인,
   종료 판정(Accept/Re-inspect)
```

- 참여자 4대 핵심 역할
  1. 주재자(Moderator) : 회의 주재와 공정한 진행, 일정 및 산출물 진입·종료 기준 통제(가장 핵심적인 역할).
  2. 작성자(Author) : 대상 산출물의 원작성자로서 질의에 답변하되 회의 주도나 변명 배제.
  3. 낭독자(Reader) : 산출물을 한 줄씩 논리적으로 낭독하며 검토 주도.
  4. 기록자(Recorder) : 발견된 모든 결함의 표준 결함 기록서 기재.

## Ⅳ. 정적 검토 기법 유형의 비교

- 핵심 요약 : 비공식 검토에서 인스펙션으로 갈수록 정형성·준비 요구·기록 추적의 수준이 상승.

| 검토 기법 | 정형성 수준 | 주재자 유무 | 사전 준비 필요성 | 결함 기록·추적 | 주 목적 |
|---|---|---|---|---|---|
| 비공식 검토(Informal) | 가장 낮음 | 없음 | 없음 | 없음 | 개인 간 아이디어 교환 |
| 워크스루(Walkthrough) | 중간 | 작성자가 주재 | 가벼운 사전 준비 | 선택적 | 산출물 이해 공유, 결함 조기 발견 |
| 기술 검토(Technical Review) | 높음 | 자격 있는 주재자 | 사전 준비 필수 | 공식 보고서 작성 | 설계 대안 평가, 표준 준수 확인 |
| 인스펙션(Inspection) | 최고 | 훈련된 주재자(Moderator) | 체크리스트 기반 정밀 준비 | 공식 결함 목록 작성 및 추적 | 산출물의 결함 전수 검출 |

```text
[ 정적 검토 기법의 정형성 스펙트럼 ]
비공식 검토 ──> 워크스루 ──> 기술 검토 ──> 인스펙션
 (가장 낮음)     (중간)        (높음)        (최고)
```

## Ⅴ. 인스펙션의 장점과 한계

- 핵심 요약 : 조기 결함 색출과 객관성의 장점, 요식 행위·심리적 갈등·일정 오버헤드의 한계가 공존.
- 장점
  1. 생명주기 초기 대량 결함의 조기 색출을 통한 수정 비용 절감.
  2. 체크리스트와 절차 기반의 객관성·재현성 확보.
  3. 팀 내 기술 지식 전이와 표준 준수 문화의 정착.
- 한계점 1 : 형식적 체크리스트 점검 및 문서 구색 맞추기로의 변질
  - 한계점 : 결함 조기 발견이라는 본래 목적을 망각하고 외부 감리나 품질 인증 통과를 위한 요식 행위로 전락하여 실질적인 설계·코드 결함 검출 실패.
  - 해결 방안 : 린터(Linter)와 SAST(Static Application Security Testing) 정적 분석 도구로 기계적 규칙 검사의 사전 자동화, 인스펙션 회의는 아키텍처 무결성·보안 취약점·비즈니스 예외 로직 등 심층 결함에만 집중.
- 한계점 2 : 심리적 안전감(Psychological Safety) 결여로 인한 감정적 충돌
  - 한계점 : 작성자가 결함 지적을 개인의 인사 평가나 역량 비난으로 받아들여 방어적 태도로 전환하고 팀 내 인간관계 갈등 증폭.
  - 해결 방안 : '작성자가 아닌 제품의 결함을 찾는다'는 원칙 명문화, 결함 발견 건수의 개인 성과 연동 금지, 중립적 주재자(Moderator)의 퍼실리테이션 역량 강화.
- 한계점 3 : 대면 회의 준비 및 진행에 따른 과도한 일정 오버헤드
  - 한계점 : 다수의 핵심 엔지니어가 수시간 동안 산출물을 전수 낭독하는 전통적 Fagan 방식의 빠른 릴리스 추구 애자일 환경과의 정면 충돌.
  - 해결 방안 : GitHub/GitLab 풀 리퀘스트(PR, Pull Request) 기반 비동기 경량 피어 리뷰(Lightweight Peer Review) 체계와의 결합, 핵심 고위험 모듈 한정의 선별적 정형 인스펙션 적용.

## Ⅵ. 현장 정착을 위한 기술사적 제언

- 핵심 요약 : 인사 평가 연계의 원천 차단과 정적 분석 도구와의 역할 분담.
- 작성자에 대한 인사 평가 연계의 절대 금지 : 발견 결함 수의 인사고과·처벌 수단 악용 시 작성자의 결함 은폐나 사소한 결함만의 보고로 귀결되므로, 비난 없는 문화(Blameless Culture) 원칙의 철저 보장.
- 정적 분석 도구(SAST·Linter)와의 역할 분담 : 코딩 표준 위반, 문법 오류, 미사용 변수 등은 SonarQube, Checkstyle 등 정적 분석 도구로 자동 검출하고, 인간 전문가의 인스펙션은 비즈니스 로직 결함, 아키텍처 정합성, 비기능 요구 충족 여부에 집중하는 운영 체계 구축.

## Ⅶ. 결론

- 핵심 요약 : 인스펙션은 정형성과 객관성을 갖춘 최강의 정적 검토 기법이며, 심리적 안전감과 도구 협업이 실효성의 전제 조건.
- 요약 : 6단계 프로세스와 4대 역할 체계를 통해 산출물 결함을 조기·전수 검출하는 대표적 정형 동료 검토 기법.
- 시사점 : 기계적 검사의 도구 위임과 Blameless 문화, 비동기 리뷰와의 하이브리드 운영으로 애자일 환경 정착 필요.
