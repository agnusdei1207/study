## 한 줄 본질
- 작성된 테스트 코드가 프로덕션 코드의 결함을 얼마나 꼼꼼하게 검증했는지 알 수 없는 불투명성 병목 → 테스트 실행 중 통과한 소스코드의 구문, 분기, 조건을 추적하여 정량적 백분율로 산출하는 화이트박스 측정 기법 / 높은 커버리지가 결함 없음을 보장하지 않음

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  코드 커버리지 수준별 검증 강도 및 포함 관계           |
+-------------------------------------------------------------------------+
|  [ 다중 조건 커버리지 (Multiple Condition) : 2^n 조합 전체 검증 ]        |
|     ▲                                                                   |
|     │  [ MC/DC (Modified Condition/Decision) : n+1 개로 독립성 입증 ]   |
|     │     ▲                                                             |
|     │     │  [ 조건/결정 커버리지 (Condition/Decision) ]                |
|     │     │     ▲                                                       |
|     │     │     │  [ 분기/결정 커버리지 (Branch/Decision) : True/False ] |
|     │     │     │     ▲                                                 |
|     │     │     │     │  [ 구문 커버리지 (Statement) : 라인 1회 실행 ]  |
|                                                                         |
|  * 검증 강도 및 테스트 비용: 구문 < 분기 < 조건/결정 < MC/DC < 다중 조건 |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 분기 커버리지(Branch Coverage): 코드 내의 모든 조건문(if, switch)의 결과가 적어도 한 번씩 참(True)과 거짓(False)을 만족하도록 테스트하는 기법
- MC/DC(Modified Condition/Decision Coverage): 복합 조건식에서 다른 조건의 값은 고정한 채, 특정 조건 하나만 변경했을 때 전체 결정문 결과가 달라짐을 증명하여 $n+1$개 케이스로 다중 조건을 대체하는 기법

## 핵심 통찰
- 구문 커버리지(Statement Coverage) 100%를 달성해도 else 분기나 예외 처리가 누락된 치명적 결함을 전혀 발견하지 못함
- 개발팀이 CI 빌드 통과를 위해 커버리지 수치만 맞추려고 단언문(`assert`)이 없는 가짜 테스트를 양산하는 "굿하트의 법칙(Goodhart's Law)" 부작용이 실무에서 빈번하게 발생함
- 항공(DO-178C Level A), 자동차(ISO 26262 ASIL D) 같은 안전필수(Safety-Critical) 소프트웨어에서는 최고 수준의 엄격성을 위해 MC/DC 커버리지 달성을 법적으로 강제함

## 이웃 토픽과 구분
- 코드 커버리지(Code Coverage) vs 기능 커버리지(Functional Coverage): 코드 커버리지 = 소스코드 라인 실행 여부를 기계적으로 측정 / 기능 커버리지 = 요구사항 명세서의 기능 항목이 테스트에 반영되었는지 추적표로 측정

## 문제·원인·대책
- 적용 상황: 금융 코어 뱅킹 이체 모듈 단위 테스트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 단위 테스트 커버리지 90% 달성 상태에서 운영 배포 후 NullPointerException 발생 | 단순 구문 실행만 체크했을 뿐 조건문의 거짓(False) 경로 및 예외 케이스 미검증 | 브랜치 커버리지(Branch) 기준 80% 상향 및 경계값 테스트 케이스 추가 | 누락된 분기 결함 조기 차단 |
| 테스트 코드는 수천 줄이나 실제 버그를 잡지 못하고 유지보수 짐으로 전락 | 단언문(assert) 없이 단순 호출만 수행하여 커버리지 수치만 인위적으로 부풀림 | 뮤테이션 테스트(PIT) 도입으로 테스트 코드의 결함 검출 살상률(Mutation Score) 측정 | 테스트 코드의 질적 유효성 확보 |

## 이렇게 출제된다

## 내 의견
- [수치 중심의 커버리지 관리 실패] 경영진에게 보여주기 위한 80% 커버리지 목표 강제로 인해 실질적 로직 검증 대신 DTO/Getter/Setter 테스트만 늘어나는 부작용 발생 → 나라면: 보일러플레이트 코드는 커버리지 측정 대상에서 제외하고, 핵심 도메인 로직에 대해서는 단순 라인 커버리지가 아닌 분기 커버리지와 돌연변이 테스트(Mutation Testing)를 결합하여 테스트 슈트의 실질적 결함 검출력을 검증
