## 1. 소프트웨어 공학의 개요 및 출현 배경

### (1) 소프트웨어 공학(Software Engineering)의 정의
- **소프트웨어의 개발, 운용, 유지보수 및 폐기에 이르는 전 생애주기(SDLC)**에 체계적이고 규율화된 수량화 가능한 접근법(공학적 원리)을 적용하는 학문 및 실무 체계 (IEEE 610.12).
- 주먹구구식 장인 코딩(Craftsmanship)의 한계를 극복하고 **품질 향상, 비용 절감, 적기 납기(QCD)**를 달성하는 것을 궁극적 목표로 함.

### (2) 소프트웨어 위기(Software Crisis)와 공학의 발전 원리
- **발생 원인**: 하드웨어 성능 급증(Moore의 법칙) 대비 소프트웨어 규모·복잡성의 폭발적 증가 및 체계적 개발 기법 부재.
- **위기의 현상**: 개발 비용 폭증, 납기 지연의 일상화, 요구사항 불일치, 릴리스 후 잦은 결함 및 유지보수 불능.
- **공학의 발전 계보**:
  1. 원시 시대: 장인식 코딩, 문서화 부재.
  2. 구조적 공학: 절차 중심, DFD, 구조도, 폭포수 모델.
  3. 객체지향/컴포넌트: 캡슐화, 재사용성, CBD, 디자인 패턴, UML.
  4. 모던/애자일 공학: 지속적 피드백, DevOps, CI/CD, 마이크로서비스(MSA), AI 네이티브 개발.

## 2. 소프트웨어 본질적 난제와 공학 체계

### (1) Brooks의 4대 본질적 특성 (No Silver Bullet)
- F. Brooks는 소프트웨어 개발의 난제를 해결할 단 하나의 마법 같은 기법(은총알)은 없다고 주창함:
  1. **복잡성 (Complexity)**: 동일한 크기의 하드웨어보다 상태 수가 무한에 가까워 전체 파악 불가.
  2. **동조성/순응성 (Conformity)**: 물리 법칙이 아닌 인간의 제도, 타 시스템, 비즈니스 규칙에 강제 적응해야 함.
  3. **변경성 (Changeability)**: 완성 후에도 비즈니스 환경과 사용자 요구에 따라 끊임없이 수정 요구 발생.
  4. **비가시성 (Invisibility)**: 기하학적 형상이 없어 구조와 진행 상황을 물리적으로 시각화하기 극히 어려움.

### (2) 소프트웨어 공학의 3대 핵심 구성요소
```text
+-------------------------------------------------------------------------+
|                  소프트웨어 공학의 3대 축과 좋은 SW의 4대 조건           |
+-------------------------------------------------------------------------+
|                                                                         |
|   [ 공학적 3대 기반 ]                     [ 좋은 SW의 4대 조건 ]         |
|    1. 도구 (Tools)      : IDE, CI/CD, SCA  ---> 1. 유지보수성 (쉬운 변경) |
|    2. 방법 (Methods)    : 객체지향, DDD     ---> 2. 신뢰성/보안성 (가용성)|
|    3. 프로세스 (Process): CMMI, 애자일      ---> 3. 효율성 (자원 최적화)  |
|                                            ---> 4. 수용성 (사용자 만족)  |
|                                                                         |
|                          ▲ 영향 요인 (4P)                               |
|       [ People (사람) | Product (제품) | Process (절차) | Project (관리) ]|
+-------------------------------------------------------------------------+
```

| 구분 | 핵심 내용 | 주요 적용 기술 및 사례 |
|---|---|---|
| **도구 (Tools)** | 개발·운영 생애주기 전반의 생산성과 자동화를 지원하는 소프트웨어 | Git, SonarQube, Jenkins, Docker, Kubernetes, CASE 도구 |
| **방법 (Methods)** | 시스템 구축에 필요한 기술적 지침, 모델링 기법, 분석·설계 원칙 | 객체지향(OOAD), 도메인 주도 설계(DDD), TDD, 리팩토링 |
| **프로세스 (Process)** | 도구와 방법을 통합 적용하여 적기에 제품을 납품하기 위한 절차와 규율 | 폭포수, 스크럼, 칸반, CMMI, ISO/IEC 12207, DevOps |

## 3. 좋은 소프트웨어의 조건과 영향 요인 (4P)

### (1) 좋은 소프트웨어(Good Software)의 4대 핵심 조건 (Ian Sommerville)
| 특성 | 영문명 | 개념 및 핵심 기준 | 구현 및 실천 방안 |
|---|---|---|---|
| **유지보수성** | Maintainability | 비즈니스 변경 요구에 맞춰 코드를 쉽고 안전하게 수정·진화할 수 있는 정도 | 결합도 최소화, 응집도 최대화, 모듈화, 클린 아키텍처, 리팩토링 |
| **신뢰성/보안성** | Dependability | 물리적 장애, 입력 오류, 악의적 침해 공격에도 정상 서비스를 지속 제공하는 성질 | 결함 허용(Fault Tolerance), 예외 처리, 암호화, 시큐어 코딩, 가용성 설계 |
| **효율성** | Efficiency | 시스템이 제한된 하드웨어 자원(CPU, 메모리, 대역폭, 전력)을 낭비 없이 최적 활용하는 정도 | 비동기 논블로킹 I/O, 캐싱 전략, 쿼리 튜닝, Green Computing 지향 |
| **수용성** | Acceptability | 최종 사용자가 거부감 없이 직관적으로 이해하고 쉽게 업무에 채택할 수 있는 정도 | 직관적 UI/UX, 접근성 표준 준수, 충분한 사용자 교육 및 호환성 제공 |

### (2) 소프트웨어 개발에 영향을 미치는 4P 요인
1. **People (사람)**: 프로젝트 성공의 가장 결정적인 요인 (개발자 역량, 도메인 이해도, 협업 문화, 팀 사기).
2. **Product (제품)**: 구축하고자 하는 시스템의 범위, 기술적 난이도, 비기능 요구사항, 아키텍처 제약.
3. **Process (프로세스)**: 조직의 성숙도에 맞는 개발 방법론, 변경 통제 절차, 품질 보증 및 검증 체계.
4. **Project (프로젝트)**: 한정된 자원 통제 (비용 산정, 일정 계획, 위험 관리, 의사소통 관리 체계).

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **오픈 후 유지보수 비용 폭증**<br>(초기 개발비의 4배 초과) | 단기 납기 맞춤용 하드코딩 남발로 유지보수성(Maintainability) 결여 | 클린 코드 원칙 및 CI 파이프라인 내 SonarQube 품질 게이트(Quality Gate) 의무화 | 코드 중복율 3% 이하 유지, 기능 변경 소요 시간 60% 단축 |
| **프로젝트 막바지 전면 재구축**<br>(통합 테스트 단계 기능 불일치) | 소프트웨어 비가시성으로 인해 중간 산출물 검증 누락 및 프로세스 부재 | 스프린트 단위 동작하는 소프트웨어 시연 및 요구사항 추적 매트릭스(RTM) 관리 | 요구사항 누락률 0% 달성, 후반부 재작업 비용 80% 차단 |
| **대규모 트래픽 시 시스템 셧다운**<br>(자원 고갈로 인한 전면 장애) | 자원 효율성(Efficiency) 검증 부재 및 대량 데이터 무제한 인메모리 적재 | 페이징/스트리밍 처리 적용 및 k6 기반 부하 테스트를 통한 병목 사전 격리 | 메모리 점유율 40% 미만 안정화, TPS 처리 용량 3배 향상 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[전통적 공학: 문서와 통제 중심]           [현대 공학: 빠른 피드백과 가치 전달 중심]
- 무거운 프로세스 (Heavy Process)  ──▶   - 가치 중심 애자일 / DevOps 파이프라인
- 사후 테스트 및 산출물 감리      ──▶   - 시프트 레프트(Shift-Left) 및 CI 자동화
- 개발과 운영의 단절 (Silo)        ──▶   - SRE / 플랫폼 엔지니어링 / AI 보조 공학
```

- **형식주의 소프트웨어 공학 탈피**: 수백 페이지의 감리용 워드 문서를 채우는 관료적 공학은 비즈니스 민첩성을 해침. 코드가 곧 명세가 되는 **자동화된 테스트 스위트(TDD/BDD)**와 **코드형 인프라(IaC)**를 핵심 공학 산출물로 삼아야 함.
- **AI 네이티브 시대의 소프트웨어 공학 재정립**: 코파일럿 등 LLM 기반 코드 생성이 보편화됨에 따라 단순 문법 코딩의 비용은 급감함. 반면 **요구사항의 엄밀한 공학적 정의, 아키텍처 정합성 검증, 시큐어 코딩 및 라이선스 거버넌스**라는 소프트웨어 공학의 본질적 통제 역량이 기술사의 핵심 차별화 포인트가 됨.
