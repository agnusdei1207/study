## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 공학**은 소프트웨어의 개발·운영·유지보수에 체계적이고 규율 있는 공학 원리를 적용하는 분야 |
| 목적 | 일정·비용·품질을 관리하면서 이해관계자의 요구를 충족하는 소프트웨어 제공 |

### Ⅱ. 본질적 난제와 공학적 대응

| 난제 | 의미 | 대응 방향 |
|---|---|---|
| 복잡성 | 요소·상태·관계의 수가 많아 이해와 변경이 어려움 | 모듈화·추상화·구조적 검토 |
| 순응성 | 법·업무·외부 시스템의 요구에 맞춰야 함 | 요구·제약의 추적과 변경 관리 |
| 변경성 | 환경·요구 변화에 따라 지속적인 수정 발생 | 유지보수 가능한 구조와 회귀검증 |
| 비가시성 | 물리적 형태만으로 내부 진행·구조를 파악하기 어려움 | 모델·기록·작동 소프트웨어로 확인 |

### Ⅲ. 좋은 소프트웨어의 조건

| 조건 | 핵심 의미 |
|---|---|
| 유지보수성 | 요구·환경 변화에 맞춰 수정·확장하기 쉬운 성질 |
| 신뢰성 | 정해진 조건에서 안정적으로 기능을 수행하는 성질 |
| 효율성 | 필요한 성능을 적절한 자원 사용으로 제공하는 성질 |
| 수용성 | 사용·운영 환경과 사용자 요구에 적합한 성질 |

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 공학**은 소프트웨어의 개발·운영·유지보수에 체계적이고 규율 있는 공학 원리를 적용하는 분야 |
| 목적 | 일정·비용·품질을 관리하면서 이해관계자의 요구를 충족하는 소프트웨어 제공 |

## Ⅱ. 소프트웨어 위기와 본질적 난제

| 난제 | 설명 | 공학적 관리 |
|---|---|---|
| 복잡성(Complexity) | 요소와 관계가 커져 전체 동작의 이해가 어려움 | 분해·추상화·모듈 간 경계 관리 |
| 순응성(Conformity) | 업무 규칙·법·외부 시스템과 맞춰야 함 | 이해관계자 요구와 외부 제약의 추적 |
| 변경성(Changeability) | 요구·환경이 바뀌어 소프트웨어도 변경됨 | 변경 영향 분석·형상 관리·회귀시험 |
| 비가시성(Invisibility) | 소프트웨어 구조와 진행 상태를 직관적으로 보기 어려움 | 모델·진척 증거·시연 가능한 결과 활용 |

Fred Brooks는 이 특성들을 소프트웨어 개발의 본질적 어려움으로 설명하고 단일한 만능 해결책의 기대를 경계.

## Ⅲ. 좋은 소프트웨어의 조건

| 조건 | 확인 질문 | 설계·검증 방향 |
|---|---|---|
| 유지보수성(Maintainability) | 요구 변경에 안전하게 대응할 수 있는가 | 모듈 경계·변경 영향·유지보수 시험 |
| 신뢰성(Dependability) | 요구 조건에서 안정적으로 작동하는가 | 오류 처리·복구·보안·신뢰성 시험 |
| 효율성(Efficiency) | 자원 사용과 응답이 요구 수준에 맞는가 | 부하 조건·자원 사용 측정 |
| 수용성(Acceptability) | 사용자·운영 환경에 적합한가 | 사용성·접근성·운영 적합성 검토 |

이 네 조건은 Ian Sommerville의 소프트웨어 품질 설명에 따른 분류이며, 모든 품질 기준을 대신하는 단일 국제표준 목록은 아님.

## Ⅳ. 4P 관점의 프로젝트 관리

| 관점 | 주요 관리 대상 | 확인 사항 |
|---|---|---|
| People(사람) | 이해관계자·개발팀·운영팀 | 역량·역할·협업·의사결정 |
| Product(제품) | 구축 대상·범위·요구사항 | 기능·품질·제약의 명확성 |
| Process(프로세스) | 개발·검증·변경 절차 | 기준·책임·산출물·피드백 |
| Project(프로젝트) | 일정·비용·자원·위험 | 계획·진척·변경·위험 관리 |

## Ⅴ. 공학 원리의 생애주기 적용

```text
이해관계자 요구·제약
    ↓ 분석·합의
구조·설계
    ↓
개발·형상 관리
    ↓
검증·인수
    ↓
운영·유지보수

운영 변경 요구 → 요구·설계 재검토
```

## Ⅵ. 기술사적 제언 — 품질 목표와 프로젝트 관리의 연결

| 한계 | 해결 방안 |
|---|---|
| 품질 목표가 일정·범위·개발 절차와 따로 관리되어 제품 인수 시점에 요구 미충족이 드러날 가능성 | 품질 요구별 책임자·설계 결정·시험 증거를 계획과 추적 정보에 연결하고, 각 단계의 검토 결과를 다음 단계 진입 조건에 반영 |
