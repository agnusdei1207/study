## 30초 인출

- 본질: 소프트웨어 위기(Software Crisis)를 극복하기 위해 소프트웨어의 개발, 운영, 유지보수에 체계적이고 정량화된 공학적 접근법을 적용하여 신뢰성 있는 고품질 소프트웨어를 경제적으로 생산하는 학문 체계
- 메커니즘: 브룩스의 4대 본질적 난제(복잡성, 순응성, 변경성, 비가시성) 인식 → 4P(People, Product, Process, Project) 다면적 관리 → 좋은 소프트웨어 4대 조건(유지보수성, 신뢰성, 효율성, 수용성) 충족
- 통찰: 은총알(No Silver Bullet)은 존재하지 않으므로 단순 최신 도구 맹신을 지양하고 지속적 아키텍처 리팩토링과 테스트 자동화, 프로세스 성숙도(CMMI)의 조직적 내재화 필수

<details>
<summary>핵심 용어</summary>

- **Software Engineering(소프트웨어 공학)** : 소프트웨어의 개발, 운용, 유지보수 및 파기에 대한 체계적이고 훈련되며 정량화된 접근법 (IEEE Std 610.12)
- **Software Crisis(소프트웨어 위기)** : 하드웨어 발전 속도에 비해 소프트웨어 개발 기술의 낙후로 발생한 비용 초과, 일정 지연, 품질 저하, 유지보수 불가 현상
- **No Silver Bullet (은총알은 없다)** : 프레더릭 브룩스(Fred Brooks)가 주창한 원리로 소프트웨어 본질적 난제를 단번에 해결할 기적의 기술은 없다는 공학적 명제
- **4대 본질적 난제 (Essence)** : 소프트웨어가 본래 지닌 복잡성(Complexity), 순응성(Conformity), 변경성(Changeability), 비가시성(Invisibility)
- **4P 관리 요소** : 성공적인 소프트웨어 프로젝트를 견인하는 4대 기둥인 인력(People), 제품(Product), 프로세스(Process), 프로젝트(Project)

</details>

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 공학의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 신뢰할 수 있고 경제적인 소프트웨어를 생산하기 위해 컴퓨터 과학의 이론과 공학적 원리를 체계적·정량적으로 소프트웨어 개발 및 유지보수 전 과정에 적용하는 학문 및 실천 체계 |
| 목적 | 소프트웨어 위기 극복, 개발 생산성 및 품질 극대화, 프로젝트 일정과 비용의 예측 가능성 확보 및 유지보수성 보장 |

## Ⅱ. 소프트웨어 공학의 핵심 특징과 브룩스의 4대 본질적 난제

| 본질적 난제 | 특성 및 문제 현상 | 소프트웨어 공학적 해결 방안 |
|---|---|---|
| **복잡성 (Complexity)** | 시스템 규모 확장에 따라 구성요소 간 상호작용이 비선형적으로 폭증하여 전체 파악 불가 | 추상화(Abstraction), 모듈화(Modularity), 정보은닉 및 계층화 아키텍처 적용 |
| **순응성 (Conformity)** | 인간의 관습, 비즈니스 법령, 이기종 H/W 및 OS 규격에 끊임없이 적응해야 하는 제약 | 개방형 표준 인터페이스, 어댑터 패턴, 비즈니스 룰 엔진(BRE) 기반 분리 설계 |
| **변경성 (Changeability)** | 시스템이 성공적으로 운영될수록 사용자의 추가 요구와 환경 변화로 지속적 수정 압박 발생 | 결합도 완화(DIP/IoC), 애자일 스크럼, CI/CD 자동화 및 안전한 회귀 테스트 스위트 |
| **비가시성 (Invisibility)** | 소프트웨어는 기하학적 형상이 없어 구조와 진척 상황을 육안으로 관찰 불가능 | UML 다이어그램 모델링, 번다운 차트, 정적 분석 시각화 대시보드(SonarQube) 구축 |

## Ⅲ. 소프트웨어 공학 4P 관리 체계 및 생명주기 프로세스

### 4P 통합 관리 모델 및 공학적 프로세스 흐름

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        [4P 프로젝트 통합 관리 체계]                    │
│                                                                        │
│   [People (사람)] ─────────────┐          ┌───────────── [Product (제품)]  │
│   - PM, 아키텍트, 개발자, QA    │          │              - 고객의 비즈니스 가치│

│                         └──────────────────────┘                           │
│                                 ▲          ▲                               │

│   - SDLC, 테일러링, CMMI        │          │              - WBS 일정, EVM 원가 │
│   - 품질 게이트, 회고 피드백    │          │              - 리스크 식별 및 통제│
└─────────────────────────────────┴──────────────────────────────────────┘
                                  │
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                 [공학적 소프트웨어 생명주기 (SDLC) 프로세스]           │
│                                                                        │
│  [요구공학] ──→ [소프트웨어 아키텍처] ──→ [설계 및 클린코드] ──→ [V&V 테스트] │
│  (도출/명세)    (4+1 View / 품질속성)      (객체지향 / 패턴)      (단위/통합)  │
│      ▲                                                              │  │

```

### 4P 관점별 핵심 관리 요소

| 핵심 요소 | 관리 목표 | 주요 실무 통제 방안 |
|---|---|---|
| **People (사람)** | 최고의 인재 확보 및 협업 시너지 | 십자형(T-Shape) 인재 육성, 심리적 안정감 조성, 명확한 RACI 매트릭스 수립 |
| **Product (제품)** | 고객 비즈니스 목표의 정확한 달성 | 정량적 비기능 품질 시나리오 수립, 제품 백로그 우선순위 지속 정제 |
| **Process (프로세스)** | 개발 활동의 일관성과 예측 가능성 | 프로젝트 규모에 최적화된 방법론 테일러링, CI/CD 자동화 파이프라인 정착 |
| **Project (프로젝트)** | 제약조건(납기, 예산, 품질) 준수 | 획득가치관리(EVM)를 통한 공정률 추적, 정기적 위험 식별 및 완화책 수립 |

## Ⅳ. 좋은 소프트웨어의 조건 (Sommerville 4대 품질) 비교

### Sommerville 좋은 소프트웨어 4대 조건과 ISO/IEC 25010 비교

| 좋은 SW 조건 | 핵심 의미 및 정의 | 달성을 위한 공학적 기법 | ISO/IEC 25010 매핑 |
|---|---|---|---|
| **유지보수성 (Maintainability)** | 고객의 요구 변화와 비즈니스 환경 진화에 따라 코드를 안전하고 쉽게 수정할 수 있는 능력 | 모듈화, 결합도 완화, 정보은닉, SOLID 원칙, 정기적 리팩토링 | 유지보수성 (모듈성, 재사용성, 시험성) |
| **신뢰성 (Dependability)** | 시스템 장애, 하드웨어 결함, 악의적 공격 상황에서도 신뢰할 수 있는 정확한 서비스를 유지하는 능력 | Fail-Safe 설계, 이중화, 예외 처리, 정적 분석, 보안 코딩 표준 | 신뢰성 (성숙도, 가용성, 장애 허용성) 및 보안성 |
| **효율성 (Efficiency)** | 메모리, CPU 프로세서, 네트워크 대역폭 등 시스템 자원을 낭비하지 않고 최적의 성능을 발휘하는 능력 | 적절한 알고리즘/자료구조 선택, 캐싱(Redis), 비동기 큐잉 | 성능 효율성 (시간 반응성, 자원 활용성) |
| **수용성 (Acceptability)** | 최종 사용자가 시스템을 직관적으로 이해하고 쉽게 사용할 수 있으며 기존 업무 환경과 완벽히 융합되는 능력 | 사용자 중심 디자인(UCD), 접근성 준수, 페르소나 기반 UI/UX | 사용성 (적합성, 학습 용이성, 인터페이스 오류 방지) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 최신 프레임워크나 AI 코딩 도구 등 특정 기술만을 만병통치약(Silver Bullet)으로 맹신하여 아키텍처 실패 | 기술 유행을 경계하고 비즈니스 도메인 문제에 적합한 본질적 아키텍처 패턴 선별 적용 |
| 개발 마감 일정에 쫓겨 단위 테스트와 리팩토링을 생략하여 프로젝트 후반 품질 붕괴 발생 | 완료의 정의(DoD)에 테스트 커버리지 및 정적 분석 통과를 강제하고 기술 부채 상환 스프린트 배정 |
| 소프트웨어 산출물 문서 작성에만 치중하여 실제 작동하는 소프트웨어의 가치 전달 지연 | Docs-as-Code 기반으로 문서와 코드를 일원화하고 동작 가능한 제품 증분 중심의 반복 배포 |

## Ⅵ. 제언

클라우드 네이티브 기반 지속적 가치 전달(Continuous Delivery) 및 개발자 경험(DevEx) 중심의 엔지니어링 문화 조성

### 현대적 소프트웨어 공학 거버넌스 파이프라인

```text
[비즈니스 가치 가설 수립]
       ↓
[도메인 주도 설계 (DDD) 및 이벤트 스토밍]
       ↓
[TDD / BDD 기반 테스트 주도 개발]
       ↓
[CI/CD 파이프라인 지속적 통합 및 배포]
  ├─ 정적 분석 및 보안 가드레일 자동 통과
  └─ 카나리 무중단 배포 (Zero-downtime)
       ↓
[운영 관측성 (Observability) 텔레메트리 수집]
       ↓
[DORA 메트릭 (배포 빈도, 변경 리드타임, 복구 시간) 기반 프로세스 진화]
```

### 소프트웨어 공학 실천법 선정 의사결정 체계

```text
프로젝트 특성 분석
       ↓
[요구사항이 명확하고 변경 가능성이 극히 낮은가?]
       ├─ 예 ──→ 예측형 프로세스 (폭포수 모델 + 정형 인스펙션) 적용
       └─ 아니오 ─→ [적응형 프로세스 (스크럼 / 칸반 + CI/CD 자동화)] 적용
                         ↓
           [미션 크리티컬 시스템으로서 고신뢰성이 요구되는가?]
                         ├─ 예 ──→ 정형 검증(Formal Methods) 및 Fail-Safe 이중화 아키텍처
                         └─ 아니오 ─→ MVP 조기 출시 후 점진적 피드백 진화
```

### 선택 근거: 전통적 장인형 코딩과 제언 현대적 소프트웨어 공학 비교

| 구분 | 전통적 장인형 개별 코딩 | 제언: 현대적 소프트웨어 공학 (DevOps/SRE) |
|---|---|---|
| 품질 보증 | 개발자 개인의 직관과 사후 수동 검사에 의존 | 자동화된 테스트, 정적 분석 및 파이프라인 가드레일 |
| 변경 위험 | 수정 시 전체 시스템 붕괴 불안으로 변경 기피 | 모듈화 및 회귀 테스트 기반으로 안전하고 빠른 변경 |
| 생산성 척도 | 작성된 소스코드 라인 수 (LOC) | 비즈니스 가치 전달 속도 및 시스템 안정성 (DORA 지표) |
