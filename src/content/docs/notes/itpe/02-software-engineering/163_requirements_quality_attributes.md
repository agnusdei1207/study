```text

 ┃
 ┣━ Ⅰ 개요 ───── 기능 중심 요구 정의로 인한 비기능 품질 결함 발생 → 시스템이 갖추어야 할 비기능적 품질 특성과 요구사항 자체의 우수성 속성 정의
 ┣━ Ⅱ 특징 ───── 이중적 관점(제품 품질 vs 요구사항 명세 품질) · 아키텍처 드라이버 · 품질 속성 간 상충(Trade-off) 관계 존재
 ┣━ Ⅲ 구조 ───── 1) 제품 품질속성(ISO 25010 8대 특성: 기능적합성, 성능, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성) + 2) 명세 자체 품질(8대 특성)

 ┣━ Ⅴ 비교 ───── 제품 품질속성(시스템의 동작 품질) vs 요구사항 명세 품질속성(문서 자체의 완성도)
 ┗━ Ⅵ 실무 ───── 품질 속성 간 상충(보안성↑ vs 사용성↓, 성능↑ vs 이식성↓) 조정 / 정량적 메트릭(SLA) 정의 / 감리 점검
```

## 한 줄 본질
- 소프트웨어가 "무엇을 하는가(기능)"에만 몰두하여 "얼마나 안전하고 빠르고 안정적으로 동작하는가(품질)"를 놓쳐 아키텍처가 붕괴되는 병목 → 시스템이 만족해야 할 비기능 품질 목표(ISO 25010)와 이를 기술하는 요구사항 명세 자체의 완전성을 정량화하는 기준 체계 / 품질 속성 간 충돌 조율의 난이도

## 핵심 용어
- 유틸리티 트리(Utility Tree): 시스템의 전체 품질 속성을 최상위 '유틸리티' 노드 아래에 세부 특성별 시나리오로 트리화하고, 비즈니스 중요도(High/Med/Low)와 구현 난이도를 매핑하여 우선순위를 결정하는 기법
- 품질 속성 상충(Trade-off): 하나의 품질 속성을 향상시키려 할 때 다른 품질 속성이 필연적으로 저하되는 관계 (예: 보안 강화를 위한 다중 암호화는 CPU 자원을 소모하여 성능을 저하시킴)

## 핵심 통찰
- 요구사항 품질속성은 두 가지 차원을 동시에 의미함: 하나는 "시스템이 갖추어야 할 품질(ISO 25010)"이고, 다른 하나는 "작성된 요구사항 명세서 자체가 갖추어야 할 품질(IEEE 830의 명확성, 완전성 등)"임
- 모든 품질 속성을 100% 만족하는 소프트웨어는 존재하지 않으며, 시스템의 목적에 따라 어떤 품질을 우선할지 명확한 우선순위를 정하는 것이 아키텍트의 핵심 역할임 (금융은 보안/신뢰성 우선, 게임은 성능/반응성 우선)
- 품질 속성은 "보안이 철저할 것"처럼 정성적으로 쓰면 무용지물이므로, SEI 품질 속성 시나리오(자극, 환경, 응답 측정) 기법을 통해 "비인가 접근 시도 시 0.1초 내 세션을 차단하고 감사 로그를 남긴다"처럼 정량화해야 함

## 이웃 토픽과 구분
- 제품 품질속성(Product Quality) vs 프로세스 품질(Process Quality): 제품 품질 = 최종 결과물 소프트웨어의 성능, 보안, 신뢰성(ISO 25010) / 프로세스 품질 = 그 제품을 만들어내는 공정의 성숙도와 표준 준수(CMMI, SP인증)

## 문제·원인·대책
- 적용 상황: 대규모 공공 마이데이터 연계 플랫폼 아키텍처 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 개인정보 암호화 및 2차 인증 강화 후 API 응답 지연이 3초로 증가하여 타임아웃 장애 | 보안 품질속성을 강화하면서 성능 품질속성과의 상충(Trade-off)을 사전 검토하지 않음 | 유틸리티 트리 기반 ATAM 아키텍처 상충 분석 수행 및 하드웨어 가속(KMS) 비동기 처리 적용 | 보안 무결성 준수 및 응답시간 0.5초 이내 회복 |
| 명세서에 "장애가 발생하지 않아야 한다"는 비현실적 무결점 품질을 적어 개발사 납품 지연 | 측정 불가능한 이상적 문구를 품질속성 요구사항으로 명세한 오류 | ISO 25010 신뢰성 하위 특성인 가용률(99.99%)과 복구 시간(MTTR 15분)으로 정량 명세 | 객관적 납품 검수 기준 수립 |

## 이렇게 출제된다
- 제130회 1교시: "소프트웨어 요구사항 품질속성(Quality Attributes)의 개념 및 ISO/IEC 25010의 8대 품질 특성을 설명하시오." → 요구 포인트: 품질속성 정의 + ISO 25010 8대 특성(기능, 성능, 사용, 신뢰, 보안 등) + 상충 관계 해결 방안

## 내 의견
- [품질 속성의 객관적 검증을 위한 아키텍처 평가 제도화] 기획서에만 품질 속성을 적어두고 실제 아키텍처 설계가 그 품질을 달성할 수 있는지 점검하지 않은 채 코딩으로 직행하는 부실 관행 심각 → 나라면: 기본설계 완료 시점에 비즈니스 이해관계자와 아키텍트가 모여 유틸리티 트리를 기반으로 품질 속성 상충을 검토하는 ATAM(아키텍처 트레이드오프 분석) 워크숍을 의무화
