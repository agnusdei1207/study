## 답안 골격
```text
[AA] ◀━━ 머리: Ⅶ 내 의견 (비즈니스 도메인 모델링 역량과 API 표준화 주도권 확보)
 ┃
 ┣━ Ⅰ 개요 ───── 비즈니스 요구 복잡화 → 업무 도메인 로직과 애플리케이션 컴포넌트 구조 설계 총괄
 ┣━ Ⅱ 특징 ───── 비즈니스 지향성 · 컴포넌트 경계 확정 · 인터페이스 표준화 · 재사용성 제고
 ┣━ Ⅲ 구조 ───── 비즈니스 계층 / 서비스 계층 / 도메인 모델 / 공통 프레임워크 / 영속성 매핑
 ┣━ Ⅳ 흐름 ───── 요구사항 분석 → 도메인 모델링 → 컴포넌트 분할 → 인터페이스 정의 → 단위/통합 설계 검증
 ┣━ Ⅴ 비교 ───── AA(기능·도메인·컴포넌트) vs TA(비기능·인프라·런타임) vs DA(데이터 모델·거버넌스)
 ┗━ Ⅵ 실무 ───── 도메인 경계 침범으로 인한 결합도 폭증 / DDD 기반 바운디드 컨텍스트 적용
```
- 필수 키워드: 애플리케이션 아키텍처 · 도메인 모델링 · 바운디드 컨텍스트 · 컴포넌트 설계 · 인터페이스 명세 · TA/DA 협업
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 계층 구조도 → Ⅴ AA vs TA vs DA 비교 / 25점 = Ⅰ~Ⅶ 전개, 클라우드 네이티브 환경에서 TA와의 4대 협업 과제
- 기출: 138회 2교시 `가. TA와 AA 역할 비교` → Ⅴ, `나. 협업의 중요성 및 협업 방안` → Ⅵ

## 한 줄 본질
- 업무 요구사항이 복잡해질수록 코드 중복과 스파게티 의존성이 심화되는 병목 → 비즈니스 로직을 독립된 컴포넌트 단위로 분할하고 계층 간 인터페이스를 표준화 → 업무 변경에 유연한 모듈화 달성 / 도메인 이해도 부족 시 경계 파탄 위험

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               애플리케이션 아키텍트(AA)의 역할 경계               |
+-------------------------------------------------------------------+
| [비즈니스 요구사항] -> [도메인 모델링 (DDD)] -> [컴포넌트 분할]    |
|                                                                   |
|   +-------------------------------------------------------------+ |
|   | Presentation Layer : UI/API 엔드포인트 설계                 | |
|   +-------------------------------------------------------------+ |
|   | Application Layer  : 트랜잭션 경계, 유스케이스 오케스트레이션 | |
|   +-------------------------------------------------------------+ |
|   | Domain Layer       : 순수 비즈니스 엔티티 및 도메인 서비스 | |
|   +-------------------------------------------------------------+ |
|   | Infrastructure     : DB, 메시지 브로커 연계 (DIP 역전)      | |
|   +-------------------------------------------------------------+ |
|         ^                                      ^                  |
|         | 협업 (인터페이스/DB 스키마)          | 협업 (성능/배포) |
|         v                                      v                  |
|   [ DA (Data Architect) ]             [ TA (Technical Architect) ]|
+-------------------------------------------------------------------+
```

## 핵심 용어
- 바운디드 컨텍스트(Bounded Context): 특정 도메인 모델이 유효하고 일관되게 적용되는 명시적 경계
- 컴포넌트 명세서: 입출력 데이터, 사전/사후 조건, 예외 처리 규칙을 표준화한 AA의 핵심 산출물

## 핵심 통찰
- AA는 기술 유행을 쫓는 역할이 아니라, 복잡한 비즈니스 로직을 소프트웨어의 정돈된 경계(Boundary)로 치환하는 도메인 번역가임
- 클라우드 네이티브 MSA 전환 시 AA의 도메인 분할 품질이 전체 마이크로서비스의 네트워크 트래픽과 분산 트랜잭션 비용을 직접 좌우함
- TA와 대립하기보다 비기능 요구(응답 시간, 동시성 한계)를 수용할 수 있는 애플리케이션 캐싱·비동기 처리 구조를 AA가 선제적으로 설계해야 함

## 이웃 토픽과 구분
- AA vs TA: AA = 비즈니스 기능 요구와 도메인 컴포넌트 설계 담당 / TA = 인프라, 미들웨어, 가용성 등 비기능 품질 속성 담당

## 문제·원인·대책
- 사례: 138회 기출 대국민 포털 클라우드 전환 시 서비스 분할 경계 모호로 인한 트랜잭션 오류
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 서비스 분할 후 주문-결제 간 분산 트랜잭션 실패 빈발 | 비즈니스 트랜잭션 경계를 고려하지 않은 AA의 단순 테이블 단위 분할 | 사가(Saga) 패턴 및 보상 트랜잭션 아키텍처 수립 | 데이터 일관성 유지 및 서비스 간 결합도 완화 |
| 특정 업무 모듈 변경 시 전체 빌드·배포 파이프라인 정체 | 도메인 간 직접 참조(스탬프 결합도) 방치 | 이벤트 기반 메시지 발행/구독(Pub/Sub) 아키텍처로 디커플링 | 업무 모듈별 독립 배포 주기 확보 |
