## 연관 키워드

- 객체지향 프로그래밍(OOP, Object-Oriented Programming), 객체, 클래스, 메시지 전달
- 추상화, 캡슐화, 상속, 다형성, 절차지향 프로그래밍

## Ⅰ. 객체지향 프로그래밍의 개요

- 핵심 요약 : OOP는 상태와 행위를 객체로 묶고 객체 간 메시지 전달로 시스템을 구성하는 프로그래밍 패러다임.
- 개념 : 데이터(상태)와 연산(행위)을 **객체**(object)라는 단위로 묶고, 객체 간 **메시지 전달**(message passing)로 시스템을 구성하는 프로그래밍 패러다임이 **객체지향 프로그래밍**(OOP, Object-Oriented Programming)임.
- 배경 및 필요성 : 전역 데이터와 함수가 분리된 구조는 데이터 변경이 함수 전반으로 퍼지는 결합 문제를 낳고, 복잡한 도메인을 개념 단위로 정리할 필요가 있음.
- 주요 목적 : 도메인 개념을 객체 모델로 반영해 변경 용이성·재사용성·확장성을 갖춘 소프트웨어 구조 확보.

## Ⅱ. 객체지향 프로그래밍의 특징 및 장점

- 핵심 요약 : 추상화·캡슐화·상속·다형성의 네 특성이 개념 명확화·결합 감소·재사용·확장으로 연결되는 구조.

1. 추상화 : 도메인 개체의 공통 특성과 책임을 **추상화**(abstraction)로 모델화 → 불필요한 세부 제거와 개념 명확화.
2. 캡슐화 : 상태와 행위를 **클래스**(class) 단위로 묶고 외부 접근을 공개 연산으로 제한하는 **캡슐화**(encapsulation) → 낮은 결합도와 변경 파급 최소화.
3. 상속 : 기반 클래스의 특성을 물려받아 확장하는 **상속**(inheritance) → 공통 개념의 계층화와 중복 제거.
4. 다형성 : 같은 메시지에 타입별로 다른 응답을 내는 **다형성**(polymorphism) → 조건 분기 제거와 확장 지점 제공.

## Ⅲ. 객체지향 프로그래밍의 구조 (흐름)

- 핵심 요약 : 도메인 개념 식별부터 다형적 확장까지, 네 특성이 설계 단계를 따라 적용되는 흐름.

```text
[ OOP 설계·구현 흐름 ]

도메인 개념·책임 식별
   ↓
클래스·인터페이스 모델링 (추상화)
   ↓
상태 은닉·공개 연산 정의 (캡슐화)
   ↓
협력·메시지 설계
   ↓
재사용·구조화 설계 (상속)
   ↓
타입별 응답으로 확장 (다형성)
```

```text
[ 네 특성의 관계 ]

추상화 : 도메인 개념에서 책임 추출
   ↓ 모델이 된 개념을 독립 단위로 묶음
캡슐화 : 상태·행위를 객체에 응집
   ↓ 객체의 골격을 재사용하는 경로
상속 : 기반 특성의 계층적 확장
   ↓ 같은 계약을 여러 구현으로 만족
다형성 : 하나의 메시지, 타입별 응답
```

## Ⅳ. 객체지향 프로그래밍과 절차지향 프로그래밍의 비교

- 핵심 요약 : 절차지향 프로그래밍이 함수·처리 흐름 중심의 분해인 반면, OOP는 상태와 행위를 가진 객체의 협력 중심 분해임.

| 비교 축 | 절차지향 프로그래밍 | 객체지향 프로그래밍 |
| --- | --- | --- |
| 기본 분해 단위 | 함수·절차와 처리 흐름 | 상태·행위를 가진 객체 |
| 데이터·함수 관계 | 데이터가 함수 간 공유·매개로 이동 | 상태가 객체에 응집, 메시지로 협력 |
| 재사용 수단 | 함수·모듈 단위 호출 | 클래스·상속·합성 단위 조립 |
| 확장 방식 | 새 함수·분기 추가 | 새 객체·타입 구현 추가 |
| 적합한 문제 | 처리 순서가 명확한 계산·변환 | 도메인 개념·역할이 복잡한 시스템 |

## Ⅴ. 객체지향 프로그래밍의 한계와 방안

- 핵심 요약 : 상속 오용·가변 공유 상태·객체 과다 생성을 합성 우선 설계, 불변성, 적정 추상화 수준으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 상속 오용 | 깊은 계층·기반 클래스 변경 → 하위 전체 파급 | 분류 관계에만 상속, **합성**(composition) 우선 검토 | 계층 깊이, 하위 영향 범위 |
| 가변 공유 상태 | 객체 간 상태 변경 → 동시성 오류·원인 추적 곤란 | 불변 객체·경계에서의 상태 통제 | 동시성 결함, 재현 실패율 |
| 객체 과다 생성 | 모든 절차를 클래스로 감쌈 → 인지 부담·성능 비용 | 문제 영역에 맞는 추상화 수준, 단순 구조 우선 | 클래스 수, 실행 지연 |

## Ⅵ. 객체지향 프로그래밍에 대한 제언

- 핵심 요약 : 개발 조직은 도메인 모델링 표준·설계 검토·교육으로 객체지향 분석·설계 역량을 조직 차원에 내재화.
- 표준 체계 : 아키텍처 조직이 객체지향 분석·설계(OOAD, Object-Oriented Analysis and Design) 기반의 도메인 모델링 표준과 클래스 설계 가이드를 제정.
- 검토 제도 : 설계 검토 회의와 코드 리뷰에 책임 배치·협력 구조 점검 항목을 두고 설계 결정의 근거를 기록·축적.
- 역량 확산 : 패러다임 비교 교육과 사례 공유로 문제 특성에 맞는 패러다임 선택 역량 확산.

## Ⅶ. 결론

- 핵심 요약 : OOP는 객체라는 개념 단위로 복잡성을 다루는 패러다임이며, 네 특성의 올바른 조합이 변경 내성을 결정.
- 패러다임의 가치는 클래스 선언이 아니라 도메인 개념과 책임의 정확한 모델링에서 발생.
