## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 요구공학·품질속성 → 성능 요구사항(Performance Requirement)

## 지식 위치

소프트웨어공학 > 비기능 요구공학 > 성능 요구사항

## 30초 인출

- 본질: 특정 운영 환경 및 부하 조건에서 시스템이 달성해야 하는 시간적 제약(응답시간/지연시간), 처리 역량(처리량/TPS), 자원 활용률(CPU/메모리)을 정량적으로 규정한 비기능 요구사항
- 메커니즘: 업무 도메인 트래픽 프로파일 분석 → SEI 6대 요소 품질 속성 시나리오 구조화 → 정량적 성능 지표(P95/P99 지연, TPS) 명세 → 부하/스트레스 테스트를 통한 인수 판정
- 통찰: 평균값 중심의 모호한 명세는 롱테일 지연과 피크 부하 장애를 은폐하므로 백분위수(P99 Latency), 동시 접속자 수, 데이터 볼륨 조건을 포괄한 구체적 시나리오 기반 계약 명세화 필수

<details>
<summary>핵심 용어</summary>

- **성능 요구사항 (Performance Requirement)** : 시스템이 수행해야 하는 기능의 속도, 처리량, 자원 소비량 등 정량적 효율성 기준을 명시한 비기능 요구사항
- **품질 속성 시나리오 (Quality Attribute Scenario)** : 비기능 요구사항을 객관적으로 검증 가능하도록 자극원, 자극, 환경, 대상, 응답, 응답측도 6가지 요소로 기술하는 프레임워크
- **백분위수 지연 (P95/P99 Latency)** : 전체 요청 중 지연시간이 낮은 순서대로 정렬했을 때 95% 또는 99%의 요청이 만족해야 하는 응답 시간 임계치
- **처리량 (Throughput / TPS)** : 시스템이 단위 시간(초)당 오류 없이 정상 처리할 수 있는 비즈니스 트랜잭션의 총량
- **자원 활용률 (Resource Utilization)** : 피크 부하 시 CPU, 메모리, 디스크 I/O, 네트워크 대역폭, DB 커넥션 풀의 최대 허용 점유율
</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 아키텍처 관점에서 성능 요구사항(Performance Requirement)의 중요성을 설명하고, 품질 속성 시나리오 6대 구성요소를 활용한 정량적 명세 방안 및 인수 검증(부하 테스트)과의 연계 전략을 기술하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 시스템이 특정 부하 조건과 하드웨어 인프라 환경에서 만족해야 하는 응답 시간(Latency), 처리 역량(Throughput), 시스템 자원 소모 한계(Resource Utilization)를 수치화한 비기능 요구사항 |
| 목적 | 시스템 개발 전 합리적 용량 산정(Capacity Planning) 및 아키텍처 전술 수립, 계약 및 납품 시 객관적 인수 시험(Acceptance Test) 기준 확립 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 정량적 측정 가능성 | "시스템이 빨라야 한다" 등의 모호한 서술을 배제하고 초(sec), TPS, % 등 계량 단위로 명확히 정의 |
| 운영 환경 종속성 | 동일한 요구사항이라도 동시 사용자 수, 데이터베이스 레코드 볼륨, 네트워크 대역폭 조건에 따라 달성 난이도 상이 |
| 품질 속성 간 트레이드오프 | 성능 극대화(캐싱, 비동기화)가 데이터 일관성(Consistency)이나 보안(암호화 검증)과 상충될 수 있으므로 균형 고려 필수 |
| 백분위수 기반 통제 | 평균 응답시간의 왜곡을 방지하기 위해 상위 1%~5% 극단 지연(Tail Latency)을 제어하는 백분위(P95/P99) 적용 |

요구사항 분석 단계에서 누락될 경우 전면적 아키텍처 재설계를 유발하는 고위험 비기능 품질의 핵심 축으로 기능.

## Ⅲ. 체계·프로세스

```text
[1. 성능 요구 도출 및 트래픽 분석]
  - 비즈니스 피크 시간대(Peak-time) 식별
  - 동시 사용자 수(Concurrency), 일일 트랜잭션 건수, 데이터 증가율 조사
       │
       ▼
[2. SEI 품질 속성 시나리오 구조화]
  ┌────────────────────────────────────────────────────────┐
  │ - 자극원   : 일반 최종 사용자, 외부 연계 기관          │
  │ - 자극     : 대규모 동시 조회 및 결제 요청 인입       │
  │ - 대상     : 주문/결제 마이크로서비스 및 DB 클러스터   │
  │ - 환경     : 블랙프라이데이 피크 부하, DB 10억 건 적재 │
  │ - 응답     : 오류 없이 정상 트랜잭션 커밋              │
  │ - 응답측도 : P99 응답시간 ≤ 1.5초, 처리량 ≥ 5,000 TPS │
  └────────────────────────────────────────────────────────┘
       │
       ▼
[3. 성능 아키텍처 전술 설계]
  - 인프라 스케일 아웃, Redis 캐싱 계층 도입, DB 샤딩/인덱싱, 메시지 큐 비동기화
       │
       ▼
[4. 성능 검증 및 인수 판정]
  - nGrinder / JMeter 기반 임계 부하 및 스트레스 테스트 수행
  - 품질 시나리오 응답측도 충족 시 인수 승인 / 미달 시 APM 병목 프로파일링
```

트래픽 프로파일 분석부터 6대 요소 기반 정량 시나리오 명세, 아키텍처 전술 설계, 부하 테스트를 통한 최종 인수 승인까지의 프로세스.

## Ⅳ. 종류·비교

| 핵심 성능 지표 | 정의 | 목표 명세 기준 | 측정 단위 |
|---|---|---|---|
| **응답 시간 (Response Time)** | 요청 전송 시점부터 시스템의 첫 번째/마지막 응답 바이트 수신 완료까지의 소요 시간 | 평균, 중앙값(P50), 상위 백분위(P95, P99) | ms, sec |
| **처리량 (Throughput)** | 시스템이 단위 시간 동안 성공적으로 완료하는 비즈니스 트랜잭션 또는 HTTP 요청 수 | 초당 처리량(TPS), 분당 처리량(TPM), RPS | TPS, RPS |
| **자원 사용률 (Utilization)** | 특정 부하 상태에서 시스템 하드웨어 자원이 소비되는 비율 | 피크 시 최대 허용치 (임계치 설정) | CPU %, Memory %, IOPS |
| **턴어라운드 시간 (Turnaround)** | 배치(Batch) 작업 등 대용량 데이터 처리가 시작되어 완전히 완료될 때까지의 총 시간 | 작업 종료 데드라인, SLA 허용 범위 | 분(min), 시간(hour) |

### 품질 속성 시나리오 6대 구성요소 비교

| 구성요소 | 개념 설명 | 전자상거래 결제 성능 명세 예시 |
|---|---|---|
| **자극원 (Source)** | 시스템에 자극을 발생시키는 주체 | 10만 명의 온라인 쇼핑몰 접속 고객 |
| **자극 (Stimulus)** | 시스템에 도착하는 성능 부하 이벤트 | 초당 10,000건의 동시 주문 결제 요청 인입 |
| **대상 (Artifact)** | 성능 요구를 만족시켜야 하는 대상 서브시스템 | 주문/결제 API 서버 및 결제 승인 RDBMS |
| **환경 (Environment)** | 이벤트가 발생하는 시스템의 운영 상태 | 이벤트 세일 피크 시간대, 정상 운영 및 노드 1대 장애 상태 |
| **응답 (Response)** | 자극에 대해 시스템이 보여야 하는 동작 | 결제 데이터 유실 없이 순차적 승인 및 응답 완료 |
| **응답측도 (Measure)** | 응답 결과를 정량 평가하는 합격 척도 | P99 응답시간 2.0초 이내, 에러율 0.01% 미만, CPU 사용률 80% 이하 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 평균 응답시간(Average Latency)만을 지표로 삼아 소수 사용자의 치명적 지연(Tail Latency) 은폐 | 백분위수 지표(P95, P99, P99.9)를 계약 및 SLA의 필수 척도로 채택 |
| 운영 환경의 실제 데이터베이스 볼륨(수억 건)을 반영하지 않은 빈 DB 상태의 부하 시험 왜곡 | 실제 운영 데이터 볼륨 및 인덱스 파편화 상태를 모사한 대용량 가상 데이터를 테스트베드에 사전 적재 |
| 클라이언트 네트워크 환경(3G/LTE, 지리적 원격지)을 배제한 순수 서버 내부 지연만 측정 | 클라이언트 RUM(Real User Monitoring) 메트릭을 수집하고 네트워크 대역폭 제한(Throttling) 시뮬레이션 병행 |

## Ⅵ. 제언

요구사항 정의 단계부터 품질 속성 시나리오 기반으로 성능 지표를 계약서에 명문화하고, CI/CD 파이프라인에 성능 테스트 게이트를 통합하여 성능 회귀를 자동 차단하는 체계 구축 필요.

```text
[지속적 성능 엔지니어링 파이프라인]
  성능 시나리오 명세 → 아키텍처 설계 → CI/CD 자동 부하 시험 (K6/JMeter) → APM 프로파일링 → 카나리 배포
```

| 관리 영역 | 전통적 성능 관리 | 지속적 성능 엔지니어링 (Continuous Performance) |
|---|---|---|
| 검증 시점 | 개발 완료 후 오픈 직전 1회성 시험 | 개발 스프린트 단위 성능 회귀 자동화 테스트 |
| 통제 도구 | 단순 부하 발생기 (수동 실행) | CI 파이프라인 연동 K6/Gatling + Datadog/Prometheus 관측 |
