## 연관 키워드

- 성능 요구사항(Performance Requirement), 비기능 요구사항(NFR, Non-Functional Requirement), 응답시간(Response Time)
- 처리량(Throughput/TPS), 백분위수 지표(P95/P99), SLA(Service Level Agreement)/SLO(Service Level Objective)/SLI(Service Level Indicator), 부하 테스트, 용량 산정(Capacity Planning)

## Ⅰ. 성능 요구사항의 개요

- 핵심 요약 : 시스템이 만족해야 하는 반응성, 처리량, 자원 사용률을 정량적으로 검증할 수 있게 정의한 비기능 요구사항.
- 개념 : 특정 부하 조건에서 기능을 수행할 때 지켜야 할 응답시간, 처리량, 자원 사용률의 목표치를 정하는 **비기능 요구사항** (NFR, Non-Functional Requirement) 중 하나인 **성능 요구사항** (Performance Requirement).
- 배경 및 필요성 : 기능이 정상이어도 응답이 느리면 사용자가 이탈하고, 동시 접속이 몰릴 때 병목이 생기면 서비스 중단으로 이어지므로 설계 초기부터 통제가 필요함.
- 표준 기준 : ISO/IEC 25010의 성능 효율성(Performance Efficiency) 품질 특성과, SLA, SLO, SLI로 이어지는 서비스 수준 관리 체계.
- 주요 목적 : 인수 시험의 판정 기준을 명확히 하고, 인프라 규모와 운영 품질을 사전에 가늠하는 것.

## Ⅱ. 성능 요구사항의 특징 및 장점

- 핵심 요약 : 네 가지 핵심 지표를 백분위수 기준으로 측정하고, 부하 조건별로 검증하는 정량 성능 체계.

1. **응답시간** (Response Time) : 요청을 보낸 뒤 응답을 받을 때까지 걸리는 시간 → 사용자 체감 반응성 판정.
2. **처리량** (Throughput, TPS) : 단위 시간당 처리되는 트랜잭션 수 → 용량 한계와 확장 필요성 판단.
3. 자원 사용률 (Utilization) : 피크 부하에서 CPU와 메모리 사용률을 임계치 이하로 유지 → 포화에 따른 급격한 지연 예방.
4. 턴어라운드 시간 (Turnaround) : 배치 작업을 제출한 뒤 완료까지 걸리는 시간 → 야간 작업 등 일정 준수 판단.
5. **백분위수** (P95, P99) : 평균값이 가리는 극단적 지연을 드러내 사용자 다수가 겪는 지연 관리 → 체감 품질 기준 확보.
6. **부하 테스트** (Load Test, Stress Test, Soak Test) : 예상 부하, 한계 초과, 장시간 실행 조건을 나누어 검증 → 조건별 결함을 구분.

- 응답시간과 지연시간 : 지연시간은 네트워크 전송에서 생기는 대기이고, 응답시간은 여기에 서버 처리와 DB 질의 시간이 더해진 사용자 체감 시간.
- 백분위수 지표 : 평균 응답시간은 긴 꼬리 지연을 감추므로, 95%나 99% 사용자가 겪는 지연을 SLO 기준으로 정함.

## Ⅲ. 성능 요구사항의 구조 (흐름)

- 핵심 요약 : 네 가지 핵심 지표를 정의하고 세 가지 부하 유형으로 검증하는 구조와, 목표 정량화에서 지속 검증까지 이어지는 절차의 이중 체계.

```text
[ 성능 핵심 지표 4가지 ]
 - 응답시간 (Response Time)
 - 처리량 (Throughput, TPS)
 - 자원 사용률 (Utilization)
 - 턴어라운드 시간 (Turnaround)
        ↓
[ 부하 테스트 3가지 유형 ]
 - 부하 테스트: 예상 부하에서 목표 달성
 - 스트레스 테스트: 한계 초과 시 거동
 - 내구성 테스트: 장시간 실행 시 누수
```

```text
[ 1. 성능 목표 정량화 ]
        ↓
[ 2. 아키텍처 설계 반영 ]
 (인프라 규모, 캐시, 인덱스)
        ↓
[ 3. 핵심 트랜잭션 PoC ]
        ↓
[ 4. 부하·스트레스 테스트 ]
        ↓
[ 5. CI 기반 지속 검증 ]
```

- 지표 체계 : SLA 수준의 계약 목표를 SLO로 세분화하고, 이를 SLI로 측정하여 달성 여부를 판정.

## Ⅳ. 기능 요구사항과 성능 요구사항의 비교

- 핵심 요약 : 기능 요구사항은 무엇을 하는지, 성능 요구사항은 얼마나 빠르고 많이 하는지를 정의하며, 검증 방식과 영향 범위가 다름.

| 비교 항목 | 기능 요구사항 | 성능 요구사항 (NFR) |
| --- | --- | --- |
| 정의 | 제공해야 할 업무 기능 | 기능을 발휘할 때의 처리 속도와 용량 |
| 기술 방식 | 사용자가 결제를 할 수 있어야 함 | 정의된 부하에서 응답시간의 백분위수 목표를 만족해야 함 |
| 영향 범위 | 업무 로직, 화면, 데이터 모델 | 인프라 규모, DB 인덱스, 캐시 구조 |
| 결함의 징후 | 오작동, 예외 발생 | 타임아웃, CPU 포화, 스레드 고갈 |
| 검증 도구 예 | JUnit, Selenium | nGrinder, Apache JMeter, k6 |

## Ⅴ. 성능 요구사항의 한계와 대응 방안

- 핵심 요약 : 모호한 기술, 비현실적 피크 설정, 늦은 검증을 정량화, 탄력 목표, 조기 검증으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 모호한 성능 기술 | "신속히 응답" 같은 표현으로 인수 기준 분쟁 발생 | **SMART 원칙**에 따라 백분위수 응답시간, 동시 사용자 수, TPS를 명문화 | 정량 기준 명시율, 인수 분쟁 건수 |
| 비현실적 피크 설정 | 드문 극단 트래픽을 상시 기준으로 잡아 인프라 비용 과다 | 평상시와 피크의 목표를 나누고, 오토스케일링과 큐 기반 버퍼링을 전제로 설계 | 피크 대비 평균 자원 사용률 |
| 늦은 성능 검증 | 통합 테스트 단계에서 처음 검증하다 구조 결함을 납기 내 고치지 못함 | 핵심 트랜잭션의 조기 PoC와 CI 파이프라인의 지속 성능 테스트 | 성능 회귀 탐지 건수 |

## Ⅵ. 시스템 엔지니어링 관점에서의 기술사적 제언

- 핵심 요약 : 성능 목표를 정량화해 계약 기준으로 삼고, 아키텍처 단계에서 용량을 선제 산정하는 체계.

1. 정량 목표의 계약화 : 발주 조직과 개발 조직은 "빠를 것"이라는 표현 대신 피크 부하 조건과 백분위수 응답시간 목표를 함께 명시하고, 이를 인수 시험의 판정 기준으로 쓰는 데 합의해야 한다.
2. 선제적 **용량 산정**(Capacity Planning) : 아키텍처 설계자는 대기행렬 이론을 활용해 서버 스레드 풀과 DB 커넥션 풀 크기를 설계 단계에서 계산하고, 부하 시험으로 그 값을 실측해 보완해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 성능 요구사항은 정량적이고 검증 가능해야 성립하며, 조기 검증과 선제 용량 산정이 실패를 막는 핵심.
- 시사점 : 백분위수 기반 목표 관리와 CI 기반 지속 성능 검증이 운영 품질을 계약 수준으로 보장하는 방향.
