## 답안 골격
```text
[성능 요구사항] ◀━━ 머리: Ⅶ 내 의견 (SRE 관점의 SLI/SLO 연계와 부하 테스트 자동화를 통한 성능 요구사항 검증 체계화)
 ┃
 ┣━ Ⅰ 개요 ───── 비기능 요구사항 중 시스템 아키텍처를 결정하는 핵심 동인 → 자원 제약 내에서 처리 속도와 용량 한계 명세
 ┣━ Ⅱ 특징 ───── 아키텍처 드라이버(Architectural Driver) · ISO/IEC 25010 성능 효율성 표준 · 정량적 SLA/SLO 계약 기준
 ┣━ Ⅲ 구조 ───── 요구 명세 3대 영역: 시간 반응성(응답시간/지연) / 자원 효율성(CPU/메모리/네트워크) / 수용 용량(동시접속/데이터량)
 ┣━ Ⅳ 흐름 ───── 비즈니스 목표 분석 → 부하 프로파일링 → 성능 시나리오 명세(자극-환경-응답) → 아키텍처 전술 수립 → 부하 테스트 검증
 ┣━ Ⅴ 비교 ───── 기능 요구사항(Functional: 시스템 동작) vs 성능 요구사항(Performance: 시간/자원 제약) vs 안정성 요구사항(Reliability)
 ┗━ Ⅵ 실무 ───── 성능 요구사항 모호성 / 성능 검증(BMT) 시기 지연 / 성능 튜닝 아키텍처 전술(캐싱, 비동기, 샤딩)
```

## 한 줄 본질
- 기능 명세에만 치중하여 아키텍처를 설계한 뒤 실제 부하 발생 시 시스템이 구조적으로 붕괴하는 병목 → 시스템이 처리해야 할 시간적 반응성과 자원 사용 한계를 정량적으로 명세하여 하드웨어 사이징과 아키텍처 전술을 결정하는 핵심 설계 요구조건 / 과도한 성능 목표 시 인프라 비용 폭증

## 핵심 용어
- 아키텍처 드라이버(Architectural Driver): 시스템의 전체 소프트웨어 구조와 설계 결정을 강제하는 가장 중요하고 영향력이 큰 핵심 비기능 요구사항
- 품질 속성 시나리오(Quality Attribute Scenario): 모호한 성능 요구사항을 객관화하기 위해 자극원, 자극, 대상, 환경, 응답, 응답 측정 6가지 항목으로 구체화하는 기법

## 핵심 통찰
- 성능은 개발 후반부에 튜닝으로 때울 수 있는 "부가 기능"이 아니라, 데이터베이스 샤딩, 캐시 계층 도입, 비동기 큐 배치 등 전체 아키텍처 뼈대를 결정하는 "아키텍처 드라이버"임
- 성능 요구사항이 비현실적으로 높게 책정되면 분산 캐시 클러스터와 고가의 고성능 인스턴스 유지 비용으로 TCO가 폭증하므로, 비즈니스 가치와 인프라 비용 간의 트레이드오프(CBAM 분석)가 반드시 선행되어야 함
- 성능 요구사항은 단순히 개발 단계의 목표치에 그치지 않고, 운영 단계의 서비스 수준 협약(SLA) 및 서비스 수준 목표(SLO)로 직결되는 거버넌스 기준점이 됨

## 이웃 토픽과 구분
- 성능 요구사항(Performance) vs 확장성 요구사항(Scalability): 성능 = 주어진 고정 자원에서 얼마나 빠르고 효율적으로 처리하는가 / 확장성 = 트래픽이 늘어났을 때 자원을 추가 투입하여 성능을 선형적으로 유지할 수 있는가

## 문제·원인·대책
- 적용 상황: 차세대 모바일 금융 뱅킹 시스템 구축 아키텍처 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 개발 완료 단계에서 성능 부하 시험 시 목표 응답시간의 5배 지연이 발생하며 구조적 실패 | 동기식 DB 직접 조회로 아키텍처를 설계하여 성능 요구사항을 초기 설계에 미반영 | SEI 품질 속성 시나리오로 성능 요구 명세화 및 CQRS·Redis 캐싱 아키텍처 전술 도입 | 응답 지연 80% 단축 및 목표 성능 달성 |
| 발주처와 수주처 간 "성능이 만족스럽지 않다"는 주관적 이견으로 준공 승인 지연 | 제안요청서에 구체적 부하 조건(동시 사용자, TPS) 없이 응답속도만 단편 기재 | 업무별 가중치가 적용된 부하 프로파일 시나리오를 설계서에 확정하고 BMT 합의 | 객관적 지표 통과로 납품 분쟁 원천 해소 |
