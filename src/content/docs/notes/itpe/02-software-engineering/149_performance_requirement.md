## Ⅰ. 성능 요구사항의 개요

- **개념** : 소프트웨어 시스템이 특정 워크로드 및 운영 환경 하에서 비즈니스 기능을 수행할 때 만족해야 하는 시간적 반응성(응답시간), 작업 처리량(Throughput), 시스템 자원 소모율(CPU, 메모리, 네트워크 대역폭)에 대한 정량적이고 검증 가능한 비기능 요구사항(NFR).
- **배경 및 필요성** : 시스템의 기능이 완벽히 동작하더라도 응답 지연이 길어지면 사용자가 이탈하고, 대규모 동시 접속 상황에서 서버가 뻗는 성능 병목은 막대한 금전적 손실과 대외 신뢰도 추락을 초래하므로 설계 초기부터 엄격한 통제 필수.
- **표준 기준** : ISO/IEC 25010 성능 효율성(Performance Efficiency) 모델, SLA/SLO/SLI 체계.

## Ⅱ. 성능 요구사항 4대 핵심 지표 및 부하 테스트 모델

```text
   ┌────────────────────────────────────────────────────────────────────────┐
   │ [ 성능 요구사항 4대 핵심 지표 ]                                         │
   │                                                                        │
   │  1. 응답시간 (Response Time) ─ 요청 전송 후 첫/마지막 바이트 수신 시간   │
   │  2. 처리량 (Throughput / TPS)─ 단위 시간(1초)당 시스템이 처리하는 트랜잭션│
   │  3. 자원 사용률 (Utilization)─ 피크 부하 시 CPU 70% 이하, 메모리 80% 이하 │
   │  4. 턴어라운드 시간 (Turnaround)─ 배치 작업 제출 후 최종 완료까지의 시간 │
   └──────────────────────────────────┬─────────────────────────────────────┘
                                      │ (성능 검증 테스팅)
                                      ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │ [ 부하 테스팅 3대 유형 ]                                               │
   │  - 부하 테스트 (Load): 정상 예측 트래픽 하에서 성능 목표 달성 검증    │
   │  - 스트레스 테스트 (Stress): 시스템 임계치를 초과하여 다운 시점 확인   │
   │  - 내구성 테스트 (Soak/Endurance): 장시간(24시간+) 연속 실행 시 메모리 누수│
   └────────────────────────────────────────────────────────────────────────┘
```

- **응답시간 (Response Time) vs 지연시간 (Latency)** : 지연시간은 네트워크 전송 대기 시간이며, 응답시간은 네트워크 왕복 시간에 서버 내부의 처리 및 DB 쿼리 시간이 모두 포함된 사용자 체감 시간.
- **백분위수 기반 응답시간 (P95, P99)** : 산술 평균 응답시간은 극단적인 긴 지연을 감추는 왜곡이 발생하므로, 전체 사용자의 $95\%$, $99\%$가 경험하는 지연시간을 SLO 기준으로 수립.

## Ⅲ. 기능 요구사항과 성능 요구사항의 비교

| 비교 항목 | 기능 요구사항 (Functional) | 성능 요구사항 (Performance / NFR) |
|---|---|---|
| 정의 | 시스템이 제공해야 하는 특정 업무 행위 (What to do) | 시스템이 동작할 때 발휘해야 하는 처리 속도와 용량 (How fast) |
| 기술 방식 | '사용자는 신용카드로 결제할 수 있어야 한다' | '동시 5,000명 접속 시 결제 승인 응답시간은 P95 기준 1.5초 이하' |
| 영향 범위 | 개별 비즈니스 로직 클래스, 엔티티, 화면 UI | 전체 인프라 규모(서버 대수), DB 인덱스, 분산 캐시 아키텍처 |
| 결함의 징후 | 오작동, 기능 실패, 예외 메시지 출력 | 타임아웃(HTTP 504), CPU 100% 포화, 스레드 고갈, 서버 다운 |
| 검증 도구 | JUnit, Postman, Selenium | nGrinder, Apache JMeter, Locust, k6 |

## Ⅳ. 시스템 엔지니어링 관점에서의 기술사적 제언

- **모호한 표현 배제 및 SMART 원칙 기반 정량화** : '시스템은 신속해야 한다'는 식의 주관적 기술을 철저히 금지하고, '피크 시간대 기준 동시 사용자 10,000명, 초당 트랜잭션 2,500 TPS 환경에서 평균 응답시간 0.8초 이하, P99 응답시간 2.0초 이하'와 같이 정량적 SLA 지표 명시 필수.
- **선제적 용량 산정(Capacity Planning) 및 성능 튜닝 거버넌스 수립** : 개발 완료 후 사후 튜닝은 아키텍처적 한계로 실패하기 쉬우므로, 아키텍처 설계 단계에서 대기행렬 이론(Little's Law, M/M/c 모델)을 적용하여 WAS 스레드 풀, DB 커넥션 풀(HikariCP), 네트워크 대역폭을 이론적으로 사전 계산하고 부하 시험으로 실측 검증해야 함.
