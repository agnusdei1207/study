## 연관 키워드
- DevOps(Development and Operations), CALMS, CI/CD, IaC, 관측성, 지속 피드백

### Ⅰ. DevOps의 개요

- 핵심 요약 : 개발과 운영의 목표·책임·자동화를 연결해 변경을 빠르고 안전하게 전달하는 조직·기술 운영 방식.
- 개념 : 개발(Dev)과 운영(Ops)이 서비스 수명주기를 공동 소유하며 협업·자동화·측정·학습을 반복하는 체계(**DevOps**, Development and Operations).
- 배경 및 필요성 : 조직 간 인계와 수작업 배포가 릴리스 지연, 장애, 책임 공백을 유발.
- 주요 목적 : 짧은 피드백 주기와 안정적 서비스 전달의 동시 달성.

### Ⅱ. DevOps의 특징 및 장점

- 핵심 요약 : CALMS의 문화·자동화·린·측정·공유로 배포와 운영 피드백을 개선.

1. 공동 책임 : 개발·운영이 서비스 성과를 함께 소유 → 인계 지연 감소.
2. 자동화 : 빌드·시험·배포·환경 구성을 코드화 → 반복성·재현성 향상.
3. 작은 변경 : 배치 크기 축소 → 위험과 원인 추적 범위 축소.
4. 지속 피드백 : SLI·장애 정보를 개발에 환류 → 결함 조기 발견.

### Ⅲ. DevOps 전달 흐름 (구조)

- 핵심 요약 : 계획에서 코드·빌드·시험·배포·운영까지 이어지는 자동화 루프를 관측 결과가 닫음.

```text
계획 → 코드 → 빌드 → 자동시험 → 배포 → 운영·관측
 ↑                                      ↓
 └──────────── 피드백·개선 ─────────────┘
```

```text
개발팀 + 운영팀 + 보안·품질
       ↓ 파이프라인·IaC·정책검증
재현 가능한 변경 → 단계 배포 → SLI/SLO 관측·학습
```

- 구현 요소 : 버전관리, CI, CD, 자동시험, IaC(IaC, Infrastructure as Code), 컨테이너, 로그·메트릭·분산추적.

### Ⅳ. DevOps와 전통적 전달 모델 비교

- 핵심 요약 : 전통적 모델은 단계별 사전계획·인계, DevOps는 작은 변경과 운영 피드백에 중점.

| 비교 축 | 기능별 분리 전달 | DevOps |
|---|---|---|
| 책임 | 개발·운영 조직별 분리 | 서비스 공동 책임 |
| 배포 | 묶음·정기 인계 | 자동화된 빈번한 변경 |
| 피드백 | 단계 종료·장애 후 | 운영지표의 지속 환류 |
| 통제 | 문서·승인 중심 | 자동 정책·추적성과 승인 병행 |

### Ⅴ. DevOps의 한계와 방안

- 핵심 요약 : 자동화만 도입하면 사일로가 파이프라인으로 옮겨지므로 권한·역량·통제를 함께 설계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 공동 책임 부재 | 파이프라인 뒤에도 수동 인계 | 제품팀 목표·온콜·회고 정립 | 수동 인계 건수 |
| 과도한 자동화 | 오류 변경의 빠른 확산 | 테스트, 단계 배포, 자동 중단·롤백 | 변경 실패율 |
| 보안 후행 | 속도와 취약점 위험 충돌 | 개발 초기 보안검사·비밀정보 통제 | 취약점 탐지 시점 |

### Ⅵ. DevOps 실행 제언

- 핵심 요약 : 조직은 흐름 병목을 측정하고 제품팀 권한과 플랫폼 가드레일을 함께 구축.

1. 경영진은 배포 빈도와 변경 실패율·복구시간·신뢰도를 균형 측정.
2. 플랫폼팀은 셀프서비스 파이프라인과 보안 기본값을 제공.
3. 제품팀은 작은 변경, 자동시험, 장애 회고를 업무 표준으로 운영.

### Ⅶ. 결론

- 핵심 요약 : DevOps는 도구 모음이 아니라 개발·운영을 공동 성과 책임으로 묶는 지속 전달 체계.
- 시사점 : 속도는 관측·통제·복구 역량과 결합될 때 서비스 신뢰로 이어짐.
