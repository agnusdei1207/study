## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 빌드·배포·DevOps → **DevOps**

## 30초 인출

- 본질: DevOps는 소프트웨어 개발과 운영 간의 장벽을 해소하고 지속적인 가치 전달을 실현하는 협업 문화이자 실천 방법론
- 메커니즘: CALMS 프레임워크 기반의 조직 통합, CI/CD 자동화 파이프라인과 관측 피드백 루프의 무한 연계
- 통찰: 개발과 운영의 KPI 상충으로 배포 병목과 품질 저하가 발생하므로 DORA 핵심 지표 기반의 공동 책임 체계와 에러 예산제 도입

<details>
<summary>핵심 용어</summary>

- **DevOps** : 개발(Development)과 운영(Operations)의 합성어로, 전 생명주기에 걸쳐 협업·자동화·측정·공유를 실천하는 체계
- **CALMS** : Culture(문화), Automation(자동화), Lean(린), Measurement(측정), Sharing(공유)으로 구성된 DevOps 도입 핵심 프레임워크
- **CI/CD(Continuous Integration/Continuous Delivery)** : 지속적 코드 통합·빌드·테스트와 안전한 운영 환경 배포를 자동화하는 파이프라인
- **IaC(Infrastructure as Code)** : 인프라 구성을 코드로 정의하고 버전 관리하여 프로비저닝의 일관성과 재현성을 보장하는 기술
- **DORA(DevOps Research and Assessment)** : 소프트웨어 전달 성능을 측정하기 위한 4대 핵심 지표(배포 빈도, 변경 리드타임, 변경 실패율, 복구 시간)를 정립한 연구 체계
- **Error Budget(에러 예산)** : SLO(서비스 수준 목표)를 위반하지 않는 한도 내에서 시스템에 허용된 최대 서비스 실패 허용량

</details>

## 2~4교시 25점 답안

## Ⅰ. DevOps의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **DevOps** 는 개발과 운영이 협력하여 소프트웨어 제품을 빠르고 안정적으로 지속 전달·운영하는 협업 방식 |
| 목적 | 변경 전달 주기 단축, 서비스 신뢰성 향상 및 실시간 운영 피드백의 개발 환류 |

## Ⅱ. DevOps의 핵심 특징

| 특징 | 의미 |
|---|---|
| 전 주기 공동 책임 | "You build it, you run it" 원칙에 기반한 개발·운영 팀의 서비스 신뢰성 공동 관리 |
| 지속적 피드백 루프 | 운영 모니터링 및 사용자 관측 결과를 다음 계획 및 코드 작성에 즉시 반영 |
| 파이프라인 자동화 | 빌드, 테스트, 보안 검증, 배포 전 과정을 도구 체인으로 연결해 인적 실수 제거 |

## Ⅲ. CALMS 프레임워크 및 지속적 전달 체계

### DevOps 전 주기 무한 루프 구조

```text
  [Plan] ──→ [Code] ──→ [Build] ──→ [Test]
    ↑                                  │
    │        지속적 피드백 루프        │
    │                                  ↓
[Monitor] ←── [Operate] ←── [Deploy] ←── [Release]
```

### CI/CD 파이프라인 및 운영 환류 메커니즘

```text
개발자 커밋
    ↓
지속적 통합(CI): 정적분석·단위테스트·빌드
    ↓
지속적 전달(CD): 스테이징 배포·통합테스트·인수검증
    ↓
프로덕션 배포: 카나리/블루그린 배포
    ↓
운영 관측(Observability): 로그·메트릭·추적 수집
    ↓
피드백 환류: 장애 분석 및 백로그 등록
```

| CALMS 요소 | 핵심 실천 방안 | 달성 목표 |
|---|---|---|
| Culture | 비난 없는 포스트모템(Blameless Postmortem), 원팀 협업 문화 | 심리적 안전감 확보, 책임 전가 방지 |
| Automation | **CI/CD** 파이프라인 구축, **IaC** 기반 인프라 자동화 | 반복 수작업 제거, 배포 신뢰성 확보 |
| Lean | 작은 배치(Small Batch) 단위 배포, WIP(재공) 작업 제한 | 배포 위험 분산, 리드타임 단축 |
| Measurement | **DORA** 4대 전달 지표 측정, 시스템 모니터링 | 정량적 성능 개선 근거 확보 |
| Sharing | 장애 사례 및 지식 베이스 공유, 오픈 커뮤니케이션 | 조직 전반의 학습 속도 증대 |

## Ⅳ. 전통적 분리 모델(Silo)과 DevOps 비교

| 비교 항목 | 전통적 분리 모델 (Silo) | DevOps 협업 모델 |
|---|---|---|
| 조직 구조 | 개발팀과 운영팀의 엄격한 역할 분리 | 크로스 펑셔널 팀(Cross-functional Team), SRE |
| 배포 주기 | 대규모 변경의 비정기적 분기/반기 배포 | 작은 변경의 일간/주간 빈번한 배포 |
| 책임 소재 | "개발은 기능 구현, 운영은 가용성 유지" | 전 생명주기에 걸친 서비스 품질 공동 책임 |
| 인프라 관리 | 엔지니어 수작업 GUI/CLI 환경 설정 | Git 기반의 선언적 **IaC** 및 GitOps 자동 동기화 |
| 장애 대응 | 팀 간 책임 공방 및 사후 책임자 문책 | 비난 없는 원인 분석 및 시스템적 결함 보완 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 개발(속도)과 운영(안정성) 간의 상충된 KPI로 인한 조직 사일로 및 저항 심화 | **Error Budget(에러 예산)** 도입을 통한 기능 개발과 안정성 개선 작업의 동적 조율 |
| 파이프라인 후반부 보안 점검으로 인한 배포 병목 및 일정 지연 | DevSecOps로의 전환 및 CI 파이프라인 내 SAST·DAST 보안 검증의 Shift-Left 적용 |
| 수작업 인프라 변경으로 인한 스테이징과 운영 환경 간 형상 불일치(Drift) | **IaC(Infrastructure as Code)** 및 GitOps 기반의 선언적 인프라 상태 동기화 강제 |

## Ⅵ. 제언

DORA 지표 중심의 정량적 전달 성과 측정과 플랫폼 엔지니어링 기반의 개발자 셀프서비스 환경 구축

### DevOps 고도화 이행 체계

```text
조직 진단 및 DORA 지표 기준선 측정
    ↓
표준 CI/CD 파이프라인 및 IaC 인프라 구축
    ↓
DevSecOps 보안 통제 자동화 연계
    ↓
내부 개발자 플랫폼(IDP) 구축 및 셀프서비스 제공
```

### 에러 예산 기반의 배포 통제 절차

```text
배포 요청
    ↓
잔여 에러 예산(Error Budget) 잔량 확인
    ├─ 예산 충분 → 프로덕션 배포 파이프라인 자동 승인
    └─ 예산 소진 → 신규 기능 배포 중단, 안정성·기술부채 해결 우선 배정
```

### 선택 근거: 도구 도입과 플랫폼 기반 거버넌스 비교

| 구분 | 도구 중심 단순 도입 | 제언: 플랫폼 엔지니어링 기반 거버넌스 |
|---|---|---|
| 운영 방식 | 팀별 개별 도구 파편화 관리 | 내부 개발자 플랫폼(IDP) 표준 포털 제공 |
| 통제 체계 | 수작업 결재 및 사후 점검 | 에러 예산 기반의 정책 기반 자동 통제 |
| 도입 효과 | 일시적 배포 자동화에 국한 | 전사 개발 생산성 및 거버넌스 동시 달성 |
