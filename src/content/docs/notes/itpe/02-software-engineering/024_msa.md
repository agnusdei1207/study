## 연관 키워드

- MSA, 바운디드 컨텍스트(bounded context), 독립 배포, 데이터 소유권
- API 게이트웨이, 사가(Saga), 서킷 브레이커, 관측성

## Ⅰ. 마이크로서비스 아키텍처의 개요

- 핵심 요약 : MSA는 비즈니스 도메인 단위로 서비스를 분리해 독립 개발·배포·확장하는 아키텍처 스타일.
- 개념 : 애플리케이션을 작은 자율 서비스들의 집합으로 구성하고, 각 서비스가 자체 데이터와 API(Application Programming Interface) 계약으로 협력하는 구조(**MSA**, Microservices Architecture). 개별 서비스를 마이크로서비스라 부름.
- 배경 및 필요성 : **모놀리식 아키텍처**(Monolithic Architecture, 단일 배포 단위의 통합 구조)의 대규모 코드베이스·전체 재배포·단일 확장 단위는 조직 확장·배포 빈도·장애 격리에서 한계.
- 주요 목적 : 서비스별 독립성을 통한 변경·확장 유연성, 장애 격리, 팀 자율성 확보.

## Ⅱ. MSA의 특징 및 장점

- 핵심 요약 : 도메인 경계 기반 분할과 독립 배포·데이터 소유가 팀 자율성과 확장성으로 연결.

1. 도메인 중심 분할 : **바운디드 컨텍스트**(bounded context, 도메인 모델의 일관성이 유지되는 경계) 단위 서비스화 → 변경 영향·팀 소유권 명확.
2. 독립 배포·확장 : 서비스별 빌드·배포·자원 조정 → 전체 중단 없는 부분 개선·부하 대응.
3. 데이터 독립성 : 서비스별 **데이터 소유권**·저장소 분리 → 스키마 결합 제거, 대신 일관성 설계 필요.
4. 경량 통신 : REST(Representational State Transfer)·메시징 등 가벼운 프로토콜·계약 기반 통신 → 기술 스택 이질성 허용.
5. 복원력 설계 : 타임아웃·**서킷 브레이커**(circuit breaker, 반복 오류 시 호출을 차단하는 패턴) 적용 → 부분 장애 격리.

## Ⅲ. MSA의 구조 (흐름)

- 핵심 요약 : 게이트웨이 경유의 요청 처리와 이벤트 기반 협력, 사가·관측 체계가 서비스 경계를 유지.

```text
클라이언트
   ↓
API 게이트웨이(인증·라우팅·집합)
   ↓
주문 서비스 ── 동기 호출 ──→ 결제 서비스
   ↓ 이벤트 발행
재고 서비스·배송 서비스
   ↓
서비스별 독립 데이터 저장소
```

```text
[ 분산 트랜잭션 : 사가 패턴 ]
주문 저장 → 결제 처리 → 재고 차감
   ↓ 중간 단계 실패 시
완료된 이전 단계의 보상 트랜잭션
   ↓
최종 일관성 회복
```

- **API 게이트웨이**(API Gateway, 클라이언트 요청의 단일 진입점과 정책 적용 지점)와 이벤트 기반 통신으로 서비스 경계 유지.
- **사가**(Saga, 로컬 트랜잭션의 연쇄와 보상으로 일관성을 유지하는 패턴)로 분산 트랜잭션의 대안 마련.
- **관측성**(observability, 로그·메트릭·추적으로 내부 상태 파악 가능성) 확보가 운영 전제.

## Ⅳ. MSA와 모놀리식 아키텍처의 비교

- 핵심 요약 : 모놀리식은 개발·배포·트랜잭션의 단순성, MSA는 서비스별 독립성·확장성에서 강점.

| 비교 축 | 모놀리식 아키텍처 | MSA |
| --- | --- | --- |
| 배포 단위 | 단일 애플리케이션 전체 | 서비스별 독립 배포 |
| 데이터 구조 | 공유 단일 데이터베이스 | 서비스별 데이터 소유 |
| 확장 방식 | 애플리케이션 전체 확장 | 필요 서비스만 확장 |
| 트랜잭션 | 단일 트랜잭션·강한 일관성 | 사가 등 최종 일관성 설계 |
| 장애 영향 | 결함이 전체로 전파 | 서비스 경계에서 격리 |
| 운영 복잡도 | 상대적 단순 | 관측·배포 자동화 부담 |
| 적합 상황 | 초기·소규모·도메인 불명확 | 도메인 명확·대규모 팀·독립 배포 필요 |

## Ⅴ. MSA의 한계와 방안

- 핵심 요약 : 경계 오분해·분산 트랜잭션·장애 전파·관측 부담을 경계 검증과 복원력·관측 체계로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 경계 오분해 | 잦은 상호 호출·공유 저장소 → 결합 증가 | 도메인 전문가 협업 경계 검증·재분해 | 서비스 간 호출 밀도 |
| 분산 트랜잭션 | 강한 일관성 부재 → 데이터 불일치 | 사가·멱등성·최종 일관성 설계 | 불일치 발견 건수 |
| 장애 전파 | 지연·실패 연쇄 → 전면 장애 | 서킷 브레이커·타임아웃·재시도 제한 | 장애 전파 건수 |
| 관측성 부족 | 원인 추적 곤란 → 진단 시간 증가 | 분산 추적·중앙 로그·서비스별 신뢰성 목표 | 평균 진단 시간 |
| 운영 비용 증가 | 배포·모니터링 대상 급증 | 배포 파이프라인 자동화·플랫폼 투자 | 배포 실패율 |

## Ⅵ. MSA에 대한 제언

- 핵심 요약 : 도메인 경계가 안정된 영역부터 점진 분리하는 전환 전략과 아키텍처 거버넌스 정착.
- 조직 : 모놀리식에서 시작해 도메인 경계가 안정된 모듈부터 점진 분리하는 전환 로드맵 운영.
- 아키텍처 거버넌스 : 서비스 수·데이터 소유권·API 버전 규칙을 표준으로 관리.
- 플랫폼 조직 : 배포·관측·장애 대응을 셀프서비스로 제공해 분산 복잡성을 개발팀으로부터 흡수.

## Ⅶ. 결론

- 핵심 요약 : MSA는 서비스 분리 자체가 목적이 아니라 도메인 자율성·독립 배포 가치와 분산 운영 비용의 균형 위에서 선택하는 아키텍처.
- 전환 판단은 조직 규모·도메인 성숙도·운영 역량을 함께 고려.
