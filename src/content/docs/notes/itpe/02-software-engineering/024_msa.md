## 연관 키워드
- MSA, bounded context, 독립 배포, 데이터 소유권, API Gateway, Saga, 관측성

### Ⅰ. 마이크로서비스 아키텍처의 개요

- 핵심 요약 : MSA는 업무 도메인 경계를 기준으로 서비스를 분리해 독립 개발·배포·확장하는 분산 아키텍처.
- 개념 : 서비스는 제한된 업무능력을 제공하고 명확한 API·데이터 소유권을 가지며 네트워크로 협력(**마이크로서비스 아키텍처**, Microservice Architecture).
- 배경 및 필요성 : 대형 단일 배포단위의 변경·확장·팀 병목이 제품 전달을 제약할 때 대안으로 고려.
- 주요 목적 : 도메인별 자율성과 변경·확장 단위를 높이되 서비스 간 계약과 운영을 통제.

### Ⅱ. MSA의 특징 및 장점

- 핵심 요약 : bounded context에 맞춘 느슨한 결합·독립 배포는 팀 자율성을 높이지만 분산시스템 복잡성을 동반.

1. 도메인 분할 : 업무능력별 서비스 → 변경 영향과 팀 소유권 명확.
2. 독립 배포·확장 : 서비스별 릴리스·자원 조정 → 전달·용량 유연성.
3. 분산 데이터 : 서비스별 데이터 소유권 → 스키마 독립성, 대신 일관성·조회 복잡도 증가.

### Ⅲ. 서비스 구조와 업무 흐름 (구조)

- 핵심 요약 : API·메시지 계약으로 서비스를 연결하고 분산 트랜잭션·장애·관측을 설계에 포함.

```text
클라이언트 → API Gateway → 주문 서비스 → 결제 서비스
                               ↓ 이벤트
                          재고 서비스
서비스별 데이터 저장소·배포·확장·SLO 소유
```

```text
요청 → 서비스 경계별 처리·이벤트 발행 → Saga 보상/재시도
   → 분산 추적·로그·메트릭 관측 → 장애 격리·복구
```

- 구현 원칙 : bounded context, 명시적 API·이벤트 버전, 자동 배포·관측, 데이터 소유권.

### Ⅳ. MSA와 모놀리식 아키텍처 비교

- 핵심 요약 : 모놀리식은 단순한 개발·배포·트랜잭션, MSA는 서비스별 독립성·확장성에서 강점.

| 비교 축 | 모놀리식 | MSA |
|---|---|---|
| 배포 단위 | 애플리케이션 전체 | 서비스별 독립 |
| 트랜잭션 | 단일 DB ACID 적용 용이 | 분산 일관성·Saga 등 필요 |
| 운영 복잡도 | 상대적으로 낮음 | 네트워크·관측·배포 자동화 필요 |
| 적합 상황 | 도메인·팀이 작고 변경결합이 높지 않음 | 도메인 경계·팀 자율·개별확장 필요가 큼 |

### Ⅴ. MSA의 한계와 방안

- 핵심 요약 : 분산 트랜잭션·장애 전파·관측 부담을 서비스 경계와 복원력 패턴으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 잘못된 분해 | 채팅형 호출·공유 DB로 결합 증가 | 도메인 전문가와 bounded context 검증 | 서비스 간 호출 밀도 |
| 부분 장애·지연 | 연쇄 장애와 데이터 불일치 | 타임아웃·회로차단·재시도 제한·Saga | 장애 전파 건수 |
| 운영·관측 복잡 | 원인추적·비용 증가 | 분산추적·중앙로그·서비스 SLO·플랫폼 자동화 | 평균 진단 시간 |

### Ⅵ. MSA 도입 제언

- 핵심 요약 : 아키텍트는 독립 배포·팀 소유권으로 얻을 가치가 분산복잡성보다 큰 경계부터 점진 분리.

1. 도메인팀은 서비스 API와 데이터 소유권, 일관성 요구를 명시.
2. 플랫폼·SRE는 배포·관측·장애복구 기본기능을 셀프서비스로 제공.
3. 전환 책임자는 모듈러 모놀리스 등 단순 대안과 총운영비용을 비교해 분리 순서 결정.

### Ⅶ. 결론

- 핵심 요약 : MSA는 서비스 경계·팀 소유권·배포 독립성을 결합한 아키텍처 선택.
- 시사점 : 서비스 수 증대가 목표가 아니라 변경·확장 자율성과 운영가능성의 균형이 목표.
