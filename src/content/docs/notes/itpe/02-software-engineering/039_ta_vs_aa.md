## 연관 키워드
- TA, AA, 엔터프라이즈 아키텍처
- 기능 요구, 비기능 요구, RACI, 아키텍처 심의

## Ⅰ. TA와 AA 역할 구분·협업의 개요

- 핵심 요약 : TA는 기술 기반 구조를, AA는 애플리케이션·업무 구조를 담당하는 아키텍처 역할 분담으로, 상호 제약 조율이 협업의 핵심.
- 개념 : 엔터프라이즈 아키텍처(EA, Enterprise Architecture)에서 응용 시스템의 구조와 기능 실현을 설계하는 **AA** (Application Architect, 응용 아키텍처 담당자)와 플랫폼·인프라·기술 표준을 설계하는 **TA** (Technical Architect, 기술 아키텍처 담당자)의 역할 분담 체계.
- 배경 및 필요성 : 시스템 규모·기술 복잡도 증가로 업무 구조 설계와 기술 기반 설계를 한 직무가 동시 담당하면 품질·운영 관점 검토가 소홀해짐.
- 주요 목적 : **기능 요구** (Functional Requirement)의 실현과 품질속성 확보의 균형 조정을 통한 아키텍처 일관성 유지.

## Ⅱ. TA와 AA 역할의 특징 및 장점

- 핵심 요약 : 관점 분리·품질속성 분담·상호 제약 반영·산출물 구분이 전문성과 일관성을 동시에 확보.

1. 관점 분리 : AA가 도메인 구조·컴포넌트·인터페이스를, TA가 플랫폼·미들웨어·기술 표준을 담당 → 각 영역 설계 전문성의 심화.
2. 품질속성 분담 : AA가 기능 흐름·조작성을, TA가 성능·가용성·보안·확장성 같은 **비기능 요구** (Non-Functional Requirement)를 주 관점으로 담당 → 품질 책임의 명확화.
3. 상호 제약 반영 : TA의 기술 표준이 AA 설계의 제약 조건이 되고, AA의 기능 요구가 TA의 플랫폼 요건이 됨 → 설계 초기 정합성 확보.
4. 산출물 구분 : 각 역할이 애플리케이션·기술 아키텍처 정의서를 구분해 산출 → 검토·변경 관리의 추적성 확보.

## Ⅲ. TA와 AA의 협업 구조 (흐름)

- 핵심 요약 : 업무 요구와 기술 환경의 입력을 받아 설계·협의·산출·심의 단계로 협업하며, 제약과 요구를 상호 조정.

```text
업무 요구 → AA (도메인·컴포넌트)
기술 환경 → TA (플랫폼·표준)
        ↓
제약·요구의 상호 협의
        ↓
아키텍처 정의서 작성
```

```text
기능 요구·품질속성 정의
   ↓
AA : 애플리케이션 구조 설계
   ↓
TA : 기술 표준·플랫폼 적합화
   ↓
트레이드오프 협의·대안 결정
   ↓
심의·구현 반영
```

## Ⅳ. TA와 AA의 비교

- 핵심 요약 : TA와 AA는 같은 아키텍처 활동 안에서 기술 관점과 응용 관점을 분담하는 보완 관계.

| 비교 축 | TA (Technical Architect) | AA (Application Architect) |
| --- | --- | --- |
| 담당 영역 | 기술 아키텍처(플랫폼·인프라·미들웨어·표준) | 응용 아키텍처(도메인·컴포넌트·인터페이스) |
| 주요 관점 | 비기능 요구(성능·가용성·보안·확장성) | 기능 요구(업무 흐름·기능 구조) |
| 주요 산출물 | 기술 아키텍처 정의서·기술 표준 | 애플리케이션 아키텍처 정의서 |
| 주요 결정 | 플랫폼 선택·기술 스택·운영 방식 | 컴포넌트 분할·인터페이스·데이터 흐름 |
| 필요 역량 | 인프라·보안·운영 기술 전문성 | 도메인 분석·설계 원칙·요구 모델링 |

## Ⅴ. TA와 AA 협업의 한계와 방안

- 핵심 요약 : 역할 경계 불명·조정 지연·역량 편차·현장 미반영을 책임 매트릭스·조기 협의·준수 점검으로 완화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 역할 경계 불명 | 담당 범위·의사결정권 미정의 → 책임 공백·중복 검토 | 책임 매트릭스 **RACI** (Responsible, Accountable, Consulted, Informed) 적용 | 미결정 이슈 건수 |
| 조정 지연 | TA 제약과 AA 설계의 늦은 충돌 → 재설계·일정 지연 | 설계 초기 공동 워크숍·정기 조정 회의 | 재설계 발생 건수 |
| 역량 편차 | 직함 정의·역량 기준의 조직별 상이 → 산출 품질 편차 | 직무 기술서·역량 기준의 표준화 | 검토 적합율 |
| 현장 미반영 | 아키텍처가 문서에만 존재 → 구현과의 불일치 | 아키텍처 준수 점검·개발자 참여 검토 | 준수 점검 위반 건수 |

## Ⅵ. TA와 AA에 대한 제언

- 핵심 요약 : 조직은 아키텍처 거버넌스 체계 안에 TA·AA 협업 절차와 결정 기록·역량 체계를 내재화해야 함.

1. 거버넌스 : **아키텍처 심의** (산출물의 정합성·적합성을 검토·승인하는 절차) 위원회를 두어 TA·AA 산출물을 정기 심의하고 의사결정 권한을 규정.
2. 결정 기록 : 아키텍처 의사결정 기록(ADR, Architecture Decision Record)으로 배경·대안·근거를 남겨 역할 간 합의를 추적.
3. 역량 체계 : 직무 체계에 맞춘 아키텍처 교육과 경력 경로로 양 역할의 전문성 확보.

## Ⅶ. 결론

- 핵심 요약 : TA와 AA는 기술 관점과 응용 관점을 분담·보완하는 아키텍처 역할 구분.
- 시사점 : 직함 구분 자체보다 명확한 의사결정 권한과 조기 협의 접점이 아키텍처 품질을 좌우.
