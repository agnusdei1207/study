```text

 ┃
 ┣━ Ⅰ 개요 ───── 시스템 내부 구현 종속 및 직접 결합 한계 → 애플리케이션 간 기능과 데이터를 표준화된 규약으로 교환하는 접점
 ┣━ Ⅱ 특징 ───── 구현과 인터페이스 분리 · 추상화 계층 제공 · 표준 규약(REST, gRPC, GraphQL) · 서비스 재사용 및 생태계 확장
 ┣━ Ⅲ 구조 ───── API 엔드포인트 / 요청-응답 페이로드(JSON/Protobuf) / 인증·인가(OAuth 2.0, JWT) / API 게이트웨이 / 관리 포털
 ┣━ Ⅳ 흐름 ───── 클라이언트 호출 → 게이트웨이 인증/인가 및 라우팅 → 백엔드 서비스 실행 → 결과 직렬화 → 클라이언트 응답
 ┣━ Ⅴ 비교 ───── REST API vs gRPC vs GraphQL

```

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  현대적 API 아키텍처 및 유형별 프로토콜                 |
+-------------------------------------------------------------------------+
|                                                                         |
|  [ 외부 클라이언트 ] ────(HTTPS)────> [ API 게이트웨이 ]                 |
|  (Web, Mobile, 3rd Party)             - 인증/인가 (JWT, OAuth 2.0)      |
|                                       - 속도 제한 (Rate Limiting)       |
|                                       - 로깅 및 트래픽 라우팅           |
|                                                    │                    |
|         ┌──────────────────────────────────────────┼──────────────────┐ |
|         v (REST: JSON/HTTP1.1)                     v (gRPC: HTTP/2)   v |
|  [ 비즈니스 서비스 A ]                      [ 고속 결제 서비스 B ]      |
|                                                                         |
|  * 프로토콜 비교:                                                       |
|    - REST: 자원(URI) 중심, 표준 HTTP 메서드, 뛰어난 범용성과 가독성     |
|    - gRPC: Protocol Buffers 직렬화, HTTP/2 멀티플렉싱, 초저지연 IPC     |
|    - GraphQL: 클라이언트가 원하는 필드만 단일 엔드포인트로 쿼리 요청   |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 멱등성(Idempotence): 동일한 API 요청을 한 번 호출하든 여러 번 호출하든 시스템의 서버 상태가 항상 동일하게 유지되는 성질 (GET, PUT, DELETE는 멱등, POST는 비멱등)
- API 게이트웨이(API Gateway): 모든 클라이언트의 API 요청을 단일 진입점에서 수신하여 인증, 인가, 라우팅, 모니터링, 속도 제한을 일괄 처리하는 아키텍처 컴포넌트

## 핵심 통찰
- API 설계에서 가장 중요한 원칙은 "API-First"이며, 코드를 먼저 짜고 API 문서를 사후 작성하는 것이 아니라 OpenAPI Specification(Swagger)으로 인터페이스 명세를 먼저 합의하고 프론트와 백엔드가 병렬 개발해야 함
- 마이크로서비스 간 내부 통신(East-West)에 무거운 텍스트 기반 REST/JSON을 전면 적용하면 직렬화/역직렬화 CPU 부하와 네트워크 지연이 누적되므로 고성능 구간에는 바이너리 프로토콜인 gRPC를 도입해야 함
- API는 조직 외부로 노출되는 순간 영구적인 공용 인터페이스가 되므로, 기존 클라이언트의 중단을 막기 위한 체계적인 버전 관리(`v1`, `v2`) 및 일몰(Deprecation) 정책이 필수적임

## 이웃 토픽과 구분
- API vs SDK: API = 소프트웨어 간 데이터를 주고받기 위한 "호출 규약 및 사양(Specification)" / SDK = 특정 플랫폼의 API를 쉽게 호출할 수 있도록 제공하는 라이브러리, 문서, 샘플 코드의 "개발 도구 모음(Kit)"

## 문제·원인·대책
- 적용 상황: 대규모 오픈 뱅킹 및 전자상거래 제휴사 API 연동
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 제휴사의 무한 재시도 호출로 인해 API 서버 리소스 고갈 및 일반 고객 서비스 장애 | 비인가 및 과도한 트래픽 유입에 대한 유량 제어 및 차단 메커니즘 부재 | API 게이트웨이에 토큰 버킷 알고리즘 기반 속도 제한(Rate Limiting/Throttling) 적용 | 서비스 가용성 99.99% 보장 및 폭주 트래픽 격리 |
| API 기능 수정 배포 후 기존 모바일 앱 구버전 사용자들이 결제 실패 오류 호소 | 하위 호환성을 고려하지 않고 API 요청/응답 필드명을 임의 변경한 파괴적 변경 | URI 버전 관리(`/api/v2/orders`) 분리 및 시맨틱 버저닝(SemVer) 준수 | 구버전 클라이언트의 연속성 보장 및 무중단 배포 |

## 내 의견
- [문서화되지 않은 사설(Shadow) API로 인한 보안 사고 예방] 프론트엔드와 백엔드 간에 규격서 없이 만들어진 내부 API들이 외부에 방치되어 BOLA(볼라, 객체 수준 권한 누락) 공격에 뚫리는 사례 빈발 → 나라면: CI/CD 배포 시 OpenAPI 스펙이 첨부되지 않은 엔드포인트는 게이트웨이 등록을 원천 거부하는 API 거버넌스를 수립하고, OWASP API Top 10 점검 도구를 파이프라인에 필수 편성
