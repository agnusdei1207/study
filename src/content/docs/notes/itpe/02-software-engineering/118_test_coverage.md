## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어공학 → 소프트웨어 품질 및 테스트 → 테스트 계측 및 완료 판정 → **테스트 커버리지(Test Coverage)**

---

## 30초 인출

- 본질: **테스트 커버리지(Test Coverage)** 는 사전에 정의된 전체 검증 대상 항목(요구사항, 소스코드 구문, 결정 분기, 논리 조건 등) 중에서 작성된 테스트 스위트가 실제로 실행하고 만족시킨 비율을 정량적으로 계측하여 테스트의 완전성과 사각지대를 평가하는 소프트웨어 품질 척도
- 메커니즘: 테스트 대상 소스코드 인스트루멘테이션(Instrumentation) → 테스트 케이스 실행 및 런타임 실행 경로 추적 → 분모 대비 실행된 항목의 백분율 비율 산출 → 미달 영역에 대한 테스트 케이스 보강
- 통찰: 높은 코드 커버리지가 결함의 부재(Absence-of-Errors)를 보증하지 못하며 단언문(Assertion) 없는 껍데기 테스트로도 100% 달성이 가능하므로 요구사항 추적성(RTM), 변이 테스트(Mutation Score), 위험 기반 테스팅(RBT)과 결합한 다차원 완료 기준선 수립이 필수적임

<details>
<summary>핵심 용어</summary>

- **구문 커버리지 (Statement Coverage)** : 소스코드 내의 실행 가능한 전체 문장(라인) 중 테스트에 의해 최소 한 번 이상 실행된 구문의 비율
- **분기 커버리지 (Branch / Decision Coverage)** : 제어 흐름 그래프(CFG)의 모든 조건문에서 발생할 수 있는 True/False 분기 경로를 모두 실행한 비율
- **조건 커버리지 (Condition Coverage)** : 조건식 내부의 개별 원자 조건(Atomic Condition)들이 각각 True와 False를 최소 한 번씩 만족하도록 실행한 비율
- **수정 조건/결정 커버리지 (MC/DC)** : 각 개별 조건식이 다른 조건들의 영향을 받지 않고 '독립적으로' 전체 결정문의 결과를 바꿀 수 있음을 입증하는 안전-치명적 표준(DO-178C, ISO 26262) 필수 커버리지
- **인스트루멘테이션 (Instrumentation)** : 커버리지 측정을 위해 원본 소스코드나 바이트코드에 실행 카운터를 기록하는 프로브(Probe) 코드를 삽입하는 기술

</details>

> 소프트웨어 테스팅의 완료 기준으로서 테스트 커버리지(Test Coverage)의 개념과 역할을 설명하고, 코드 커버리지 4대 기준(구문, 결정, 조건, MC/DC)의 메커니즘 비교, MC/DC 테스트 케이스 도출 원리 및 커버리지 수치 맹신에 따른 위험 극복 방안을 제시하시오.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 테스트 대상 시스템의 전체 요구사항 또는 소스코드 제어 구조 중에서 테스트 스위트에 의해 실행되고 검증된 범위의 비율을 나타내는 정량적 척도 |
| 목적 | 테스트의 충분성(Thoroughness) 평가, 미검증된 코드 사각지대 식별, 릴리스 여부를 결정하는 객관적인 테스트 완료 기준(Exit Criteria) 제공 |

## Ⅱ. 핵심 특징

단순한 코드 실행 확인을 넘어 제어 흐름의 논리적 엄밀성을 계층적으로 보증.

| 핵심 영역 | 메커니즘 | 품질 공학적 의미 |
|---|---|---|
| **정량적 측정 가능성** | 전체 항목 수 대비 실행된 항목 수를 백분율(%)로 명확히 산출 | 테스트 진척도 및 품질 목표 달성 여부 객관화 |
| **계층적 강도 (Hierarchy)** | 구문 커버리지 $\rightarrow$ 분기 커버리지 $\rightarrow$ MC/DC $\rightarrow$ 경로 커버리지 | 상위 커버리지를 만족하면 하위 커버리지는 자동 100% 충족 |
| **안전 표준 필수 준수** | ISO 26262 (ASIL-D), DO-178C (Level A)에서 MC/DC 100% 의무화 | 인명 안전과 직결된 시스템의 치명적 결함 원천 예방 |
| **자동화 파이프라인 연계**| JaCoCo, Cobertura 도구를 통해 빌드 시 커버리지 자동 계측 | CI/CD 파이프라인에서 기준 미달 시 배포 차단 (Quality Gate) |

## Ⅲ. 체계·프로세스

코드 커버리지 4대 계층 체계 및 MC/DC(Modified Condition/Decision Coverage) 평가 메커니즘.

```text
[코드 커버리지 계층 구조 및 MC/DC 원리]
[커버리지 검증 강도 계층 구조]

  (최고 강도)  [ 전경로 커버리지 (Path Coverage) ]     : 비현실적 (루프 시 경로 무한 폭발)
       ▲
       │      [ MC/DC 커버리지 ]                       : 항공/자동차 필수 (N+1개 케이스로 고신뢰성 확보)
       │
       │      [ 다중 조건 커버리지 (Multiple Condition) ] : 2^N개 조합 (조건 증가 시 기하급수 폭증)
       │
       │      [ 결정/분기 커버리지 (Branch Coverage) ] : 모든 분기의 True/False 분기 검증
       │
  (기본 강도)  [ 구문 커버리지 (Statement Coverage) ]   : 모든 실행 라인 1회 이상 통과

───────────────────────────────────────────────────────────────────────────────────────────────────────────
  ── [MC/DC 도출 예시: 결정문 if (A or B) and C] ─────────────────────────────────────────────────────────
  * 원리: 각 개별 조건(A, B, C)이 다른 조건들을 고정한 채 '홀로' 전체 결과를 True/False로 역전시킴을 입증
  * 조건 개수가 N개일 때, 최소 N+1개의 테스트 케이스만으로 완벽한 안전성 입증 (2^N개 불필요)
```

- **코드 커버리지 계측 4단계 프로세스**:
  1. **바이트코드 인스트루멘테이션** : JaCoCo 에이전트가 클래스 로딩 시점에 실행 추적 프로브 코드를 동적으로 삽입.
  2. **테스트 스위트 가동** : JUnit 등 단위/통합 테스트를 실행하며 프로브를 통해 실행된 바이트코드 블록 기록.
  3. **실행 데이터 취합 및 매핑** : 런타임 실행 프로파일(.exec)을 소스코드의 구문, 분기, 조건에 1:1 매핑.
  4. **커버리지 리포트 발행 및 게이트 판정** : HTML 리포트를 생성하고 사전 정의된 임계치(예: 분기 커버리지 80%) 미달 시 빌드 중단.

## Ⅳ. 종류·비교

#### 코드 커버리지 4대 기준 상세 비교

| 커버리지 기준 | 정의 및 달성 조건 | 장점 | 단점 및 한계 |
|---|---|---|---|
| **구문 커버리지 (Statement)** | 프로그램의 모든 실행 가능한 문장을 최소 1회 실행 (라인 커버리지) | 측정이 가장 쉽고 직관적임 | 분기문(`if`)에서 `else` 누락 시 결함을 전혀 잡지 못함 |
| **결정/분기 커버리지 (Branch)** | 모든 조건문의 분기(True/False) 결과를 최소 1회씩 실행 | 구문 커버리지를 100% 포함하며 분기 누락 방지 | 복합 조건식 내부의 개별 조건 결함은 발견 불가 |
| **조건 커버리지 (Condition)** | 복합 조건문 내의 각 개별 조건식이 True/False를 최소 1회 가짐 | 개별 조건의 동작 확인 가능 | 전체 결정문의 True/False 분기가 달성되지 않을 수 있음 |
| **MC/DC 커버리지** | 각 개별 조건이 전체 결정문 결과에 독립적으로 영향을 미침을 증명 | **$N+1$개 케이스로 복합 조건 완벽 검증** | 테스트 케이스 도출이 수학적으로 복잡하고 비용 높음 |

#### 기능(요구사항) 커버리지 vs 구조적(코드) 커버리지 비교

| 비교 항목 | 기능/요구사항 커버리지 (Functional) | 구조적/코드 커버리지 (Structural) |
|---|---|---|
| **테스트 관점** | 블랙박스 테스팅 (Black-box) 관점 | 화이트박스 테스팅 (White-box) 관점 |
| **측정 대상** | 요구사항 명세서의 기능 목록, 유스케이스 | 소스코드의 구문, 분기, 함수, 클래스 |
| **주요 역할** | "요구된 기능이 빠짐없이 만들어졌는가?" | "작성된 코드의 논리적 분기가 다 검증되었는가?" |
| **측정 도구** | 요구사항 추적표(RTM), Jira 테스트 레일 | JaCoCo, Coverage.py, BullseyeCoverage |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 단언문(Assertion)이 전혀 없는 테스트 코드를 실행해도 커버리지가 100%로 측정되는 허수 커버리지 발생 | 뮤테이션 테스트(Mutation Testing)를 병행하여 결함 주입 시 테스트 실패율(Mutation Score)을 교차 검증 |
| 코드 커버리지 100%를 달성해도 애초에 요구사항 명세서에서 누락된 기능(Missing Code)은 탐지 불가 | 요구사항 추적표(RTM) 기반의 기능 커버리지와 동등분할/경계값 분석 기반 블랙박스 테스트 선행 |
| 복잡한 레거시 시스템에서 모든 브랜치 100% 달성을 강제함에 따라 개발 생산성 급감 및 형식적 테스트 양산 | 시스템 위험도(Risk-based Testing)에 따라 코어 금융 로직은 90% 이상, 단순 UI/DTO는 50% 차등 목표 적용 |

## Ⅵ. 제언

테스트 커버리지는 단순한 목표 수치(KPI)가 아닌 소프트웨어의 건강 상태를 진단하는 지표이므로, SonarQube 품질 게이트와 뮤테이션 점수(Mutation Score)를 결합한 입체적 품질 보증 파이프라인을 정립할 필요가 있음.

```text
[요구사항 RTM 검증] ──> [단위/통합 테스트 실행] ──> [JaCoCo 분기 커버리지 (80%)] ──> [PITest 뮤테이션 검증] ──> [배포 승인]
  (기능 누락 방지)         (Assertion 기반 검증)       (구조적 사각지대 제거)         (테스트 단언 유효성 80%)      (품질 게이트 통과)
```

| 관리 영역 | 권장 실천 지침 | 핵심 관리 지표 |
|---|---|---|
| **도메인 차등화** | 결제, 보안, 엔진 코어는 분기 85% 이상, 일반 CRUD는 70% 설정 | 전체 코드베이스 평균 라인 커버리지 80% 유지 |
| **게이트 자동화** | PR 생성 시 신규 작성 코드(New Code)에 대해 커버리지 80% 미달 시 머지 차단 | 기술부채 증가율 0% 및 신규 결함 유입 차단 |
| **신뢰도 교차 검증**| JaCoCo 브랜치 커버리지와 PITest 뮤테이션 점수를 분기별 합동 감사 | 생존 뮤턴트(Survived Mutant) 비율 15% 이하 유지 |
