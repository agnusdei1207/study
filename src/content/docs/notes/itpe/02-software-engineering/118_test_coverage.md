## Ⅰ. 테스트 커버리지의 개요

- 개념 : **테스트 커버리지** (Test Coverage) 란 소프트웨어 테스트 수행 시 작성된 테스트 케이스 스위트에 의해 소스코드의 특정 구조적 요소(문장, 분기, 조건, 경로) 또는 요구사항 명세가 얼마나 충실하게 실행되고 검증되었는가를 백분율(%)로 정량화한 소프트웨어 테스트 충실도 측정 메트릭.
- 배경 및 필요성 : 테스트 활동이 시스템의 잠재 결함을 얼마나 꼼꼼하게 탐색했는지를 객관적으로 평가하고, 미실행 영역(Dead Code, 테스트 사각지대)을 식별하여 테스트 케이스를 보강하기 위한 필수 척도.
- 표준 체계 : **ISO/IEC/IEEE 29119** (소프트웨어 테스팅 표준), **DO-178C** (항공 소프트웨어 표준)

## Ⅱ. 제어 흐름 기반 화이트박스 커버리지 계층 구조

```text
   [ 다중 조건 커버리지 (Multiple Condition: 2^N) ] ─ 조건식의 모든 진리표 조합 실행
                       ▲
                       │
   [ MC/DC 커버리지 (Modified Condition/Decision) ] ─ 각 조건이 독립적으로 전체 결과 결정 (N+1)
                       ▲
                       │
   [ 조건/결정 커버리지 (Condition/Decision) ] ───── 개별 조건 참/거짓 + 전체 결정 참/거짓
                       ▲
                       │
   [ 분기/결정 커버리지 (Branch/Decision, L2) ] ──── 각 조건문의 True/False 분기 실행
                       ▲
                       │
   [ 구문 커버리지 (Statement, L1) ] ────────────── 코드 내 모든 실행 가능 문장 1회 실행
```

- **구문 커버리지** (Statement Coverage) : 소스코드의 모든 문장이 최소 한 번 실행되었는지를 측정 ($실행된 문장 수 / 전체 문장 수 \times 100\%$).
- **결정 커버리지** (Decision/Branch Coverage) : 조건식의 전체 평가 결과가 참(True)과 거짓(False)이 되는 모든 분기를 최소 한 번씩 실행.
- **MC/DC** (Modified Condition/Decision Coverage) : 각 개별 조건식이 다른 조건식들의 영향을 받지 않고 독립적으로 전체 결정문의 결과에 직접적인 영향을 미침을 입증하는 초고신뢰성 커버리지.

## Ⅲ. 주요 테스트 커버리지 유형 및 검증 강도 비교

| 커버리지 유형 | 검증 기준 및 규칙 | 최소 필요 케이스 수 | 주요 적용 분야 |
|---|---|---|---|
| 구문 커버리지 (L1) | 모든 코드 라인 1회 이상 실행 | 최소 | 일반 상용 웹/모바일 소프트웨어 (목표 커버리지 기준) |
| 결정 커버리지 (L2) | if/switch 모든 분기 경로 1회 이상 실행 | 적음 | 일반 엔터프라이즈 업무 시스템 |
| **조건 커버리지** | 복합 조건 내 개별 조건의 True/False 1회 | 적음 | 모듈 내부 세부 조건 검증 |
| MC/DC 커버리지 | 개별 조건의 독립적 영향 입증 | $N+1$개 (조건 수 $N$) | 항공(DO-178C Level A), 자율주행(ISO 26262 ASIL D) |
| **전 경로 커버리지** (All-Path) | 프로그램 내 실행 가능한 모든 실행 경로 | 조합 폭발 ($2^N$ 초과) | 루프가 없는 초소형 크리티컬 알고리즘 |

## Ⅳ. 테스트 커버리지(Test Coverage)의 주요 한계점 및 해결 방안

- 구문 커버리지의 허위 안도감(False Sense of Security) :
  - 한계점 : 100% 문장 커버리지(Statement Coverage)를 달성하더라도 복합 조건문의 경계값 오류나 예외 처리 누락, 논리적 결함을 전혀 보장하지 못함.
  - 해결 방안 : 분기(Branch) 및 조건/결정 커버리지(MC/DC)를 병행 측정하고, 테스트 케이스의 유효성을 실질 검증하는 **뮤테이션 점수** (Mutation Score) 복합 도입.
- 커버리지 목표 달성을 위한 무의미한 단언(Assertion-Free) 테스트 양산 :
  - 한계점 : 경영진의 커버리지 수치 강제(예: 특정 수치 의무화)로 인해 개발자들이 `assert` 없이 메서드만 호출하는 무가치한 테스트를 양산하여 유지보수 부담만 가중.
  - 해결 방안 : SonarQube 등 정적 분석 도구에 Assertion 검출 룰 적용, 단순 코드 라인 비율이 아닌 비즈니스 위험도 기반 테스트(Risk-Based Testing) 우선순위 평가.
- 비동기·멀티스레드 및 외부 분산 호출 구간의 측정 한계 :
  - 한계점 : 분산 마이크로서비스 간 비동기 메시지 수신 및 외부 3rd Party API 호출 구간은 표준 코드 커버리지 에이전트(JaCoCo 등)로 추적 불가.
  - 해결 방안 : 분산 추적(Distributed Tracing) 기반의 엔드투엔드 시나리오 커버리지 측정, 컨트랙트 테스팅(Pact)을 통한 서비스 경계 간 인터페이스 커버리지 보완.

## Ⅴ. 엔터프라이즈 품질 게이트웨이를 위한 기술사적 제언

- '가짜 커버리지(Fake Coverage)'의 함정 경계 : 어설션(Assertion) 검증문이 하나도 없이 코드 라인만 단순히 호출하는 테스트도 구문 커버리지 100%를 달성할 수 있으므로, 단순 수치 달성에 안주하지 말고 결함 검출 능력을 실질적으로 검증하는 뮤테이션 테스트(Mutation Test)를 병행 도입해야 함.
- CI/CD 파이프라인 품질 게이트 연동 : SonarQube, JaCoCo를 활용하여 신규 추가/수정된 코드(New Code)에 대해 브랜치 커버리지 목표 수준을 만족하지 못하면 메인 브랜치 병합을 원천 차단하는 **커버리지 래칫** (Coverage Ratchet) 정책 정착 필수.
