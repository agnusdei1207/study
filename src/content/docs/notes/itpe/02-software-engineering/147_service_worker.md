## 30초 인출

- 본질: **Service Worker(서비스 워커)** 는 웹 페이지와 네트워크 사이에서 요청·응답을 다루는 이벤트 기반 스크립트
- 메커니즘: 서비스 워커 스크립트 브라우저 등록(Register) $\rightarrow$ 정적 리소스 사전 캐싱 및 설치(Install) $\rightarrow$ 구버전 캐시 정리 및 활성화(Activate) $\rightarrow$ 런타임 네트워크 요청 가로채기(Fetch Intercept) 및 캐시 반환
- 통찰: 한계: 오래된 캐시를 갱신하지 않으면 새 배포 후에도 이전 자원이 제공될 수 있음 → 방안: 워커 활성화 때 버전별 캐시를 정리하고 오프라인·업데이트 경로를 시험

<details>
<summary>핵심 용어</summary>

- **Service Worker(서비스 워커)** : 브라우저가 이벤트에 따라 실행하는 스크립트로, 페이지 요청을 처리하고 응답을 제어하는 워커
- **Cache Storage API(Application Programming Interface)** : 요청·응답 쌍을 저장·조회하는 웹 저장소 인터페이스이며, 보존은 저장소 정책과 애플리케이션 관리에 따름
- **App Shell 모델** : 웹 애플리케이션의 핵심 UI 골격(HTML, CSS, 기본 자바스크립트)을 로컬에 미리 캐싱해 두고, 동적 데이터만 네트워크를 통해 주입받는 아키텍처 패턴
- **Workbox** : 구글에서 개발한 프로덕션급 서비스 워커 라이브러리로, 캐싱 전략·사전 캐싱·백그라운드 동기화를 선언적으로 구현할 수 있도록 표준화한 도구
- **PWA(Progressive Web App)** : 설치·오프라인 지원 등 웹 플랫폼 기능으로 앱과 유사한 경험을 제공하는 웹 애플리케이션

## 2~4교시 25점 답안

## Ⅰ. 서비스 워커의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **Service Worker** 는 웹 페이지와 네트워크 사이에서 요청·응답을 다루는 이벤트 기반 스크립트 |
| 목적 | 네트워크 응답과 캐시를 제어해 오프라인·불안정 연결에서도 웹 기능을 제공 |

## Ⅱ. 제어 범위와 이벤트 실행의 특징

| 특징 | 설계상 의미 |
|---|---|
| 제어 범위 | 등록된 범위의 제어 중인 페이지 요청에만 fetch 이벤트 적용 |
| 이벤트 기반 실행 | 페이지와 별도 수명주기로 동작하므로 영구 실행 상태를 전제하지 않음 |
| 오프라인 범위 | 사전 저장 자산과 캐시 갱신 정책을 정한 요청만 안정적으로 제공 |

## Ⅲ. 설치·활성화·요청 가로채기 프로세스

### 등록에서 요청 응답까지

```text
페이지의 워커 등록
  ↓ install: 핵심 자산 사전 캐시
  ↓ activate: 이전 버전 캐시 정리·제어 전환
제어 중인 페이지의 fetch 요청
  ├─ 캐시 정책상 적중 → Cache Storage 응답
  └─ 네트워크 선택 → 서버 응답·필요 시 캐시 갱신
```

## Ⅳ. 요청별 캐싱 전략과 적용 조건

### 요청별 캐싱 전략

| 캐싱 전략 | 핵심 판단 |
|---|---|
| **Cache First** | 캐시된 자산을 먼저 사용하고 없을 때 네트워크 요청; 변경되지 않는 자산에 적합 |
| **Network First** | 네트워크를 먼저 사용하고 실패 시 캐시 사용; 오래된 응답 허용 여부 확인 |
| **Stale-While-Revalidate** | 캐시 응답을 먼저 제공하며 새 응답으로 캐시 갱신; 최신성 요구 검토 |
| **Network Only / Cache Only** | 요청 특성에 따라 네트워크 또는 캐시만 사용 |

### 적용·검증 관점

Background Synchronization API를 지원하는 브라우저에서는 오프라인 작업의 후속 처리를 등록할 수 있으며, 지원 범위가 제한적이므로 중요한 업무에는 저장·재전송·중복 방지의 대체 경로 필요.

읽기 전용 자산, 변동 데이터, 인증·결제 데이터의 성격을 구분한 캐싱 정책. 사용자별 민감 정보의 공유 캐시 제외와 폐기 규칙 포함.

| 기능 | 설계 조건 |
|---|---|
| 오프라인 읽기 | 필요한 자산의 사전 캐시와 갱신·폐기 기준 |
| 백그라운드 동기화 | 브라우저 지원 확인, 실패 재전달과 중복 방지 |
| 사용자별 데이터 | 민감도 검토와 캐시 분리·삭제 절차 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 오래된 캐시를 갱신하지 않으면 새 배포 후에도 이전 자원이 제공될 수 있음 | 워커 활성화 때 버전별 캐시를 정리하고 오프라인·업데이트 경로를 시험 |
| 업데이트 중 이전 페이지와 새 워커의 상태 불일치 | 대기·활성화 정책과 캐시 버전 전환을 함께 설계 |
| 오래된 캐시 응답으로 데이터 불일치 | 데이터 민감도와 최신성 요구에 맞춰 캐시 전략·폐기 정책 적용 |
| 워커의 요청 처리 권한 | 보안 컨텍스트에서 배포하고 등록 범위·스크립트 출처를 검토 |
| 백그라운드 동기화 지원이 제한적 | 중요한 작업은 로컬 저장·재전송·중복 방지의 대체 경로를 마련 |

## Ⅵ. 제언

**제언:** 정적 자산부터 오프라인 대상을 정하고, 요청별 최신성·민감도 기준으로 캐시 폐기와 업데이트 시험을 배포 절차에 넣는다.
