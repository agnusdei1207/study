## 연관 키워드
- 구조적 방법론, 정보 공학, 객체 지향, CBD, DFD, ERD, UML, 컴포넌트

### Ⅰ. 소프트웨어 개발 방법론의 개요

- 핵심 요약 : 개발 방법론은 요구 분석·설계·구현·검증 활동과 산출물·역할을 체계화하는 접근.
- 개념 : 시스템을 분석·분해·구축 하는 관점과 절차를 제공해 개발의 반복성과 의사 소통을 지원(**개발 방법론**, Software Development Methodology).
- 배경 및 필요성 : 규모·복잡도가 커질수록 개인 별 임의 작업은 요구 누락·품질 편차를 키움.
- 주요 목적 : 프로젝트 특성에 맞는 분석 모델·설계 단위·검증 활동·산출물 기준 설정.

### Ⅱ. 주요 방법론의 특징 및 장점

- 핵심 요약 : 구조적은 기능·자료 흐름, 정보 공학은 데이터·업무, 객체 지향은 객체 협력, CBD는 재사용 컴포넌트를 중심으로 모델링.

1. 구조적 방법론 : 기능 분해·DFD·구조도 → 절차·변환 중심 업무에 적합.
2. 정보 공학 : 업무 정보·데이터 모델·프로세스 정렬 → 전사 데이터·업무 통합에 강점.
3. 객체 지향 : 객체·클래스·캡슐화·상속·다형성 → 상태·행위와 변경 책임 결합.
4. CBD : 인터페이스 계약을 가진 컴포넌트 조립 → 재사용·대체·통합 촉진.

### Ⅲ. 모델과 산출물 흐름

- 핵심 요약 : 요구·업무 분석에서 선택한 관점에 따라 설계 모델·구현 단위·시험 기준으로 정련.

```text
업무 요구 → 구조적(DFD·구조도) → 모듈·프로그램
         → 정보 공학(ERD·업무 모델) → 데이터·업무 구조
         → OO(UML) → 클래스·객체 협력
         → CBD(컴포넌트 명세) → 조립·통합
```

```text
요구·도메인 분석 → 방법론·모델 선택 → 설계·인터페이스 정의
         → 구현·통합 → 요구 추적·시험·유지 보수
```

- 적용 : 단일 방법론 고정 대신 기존 자산·규제·팀 역량을 고려한 테일러링 가능.

### Ⅳ. 구조적·정보 공학·OO·CBD 비교

- 핵심 요약 : 방법론은 분해·데이터·객체·컴포넌트 중 무엇을 중심 추상화로 쓰는지에 따라 선택.

| 기준 | 구조적 | 정보 공학 | 객체 지향 | CBD |
|---|---|---|---|---|
| 중심 | 기능·자료 흐름 | 기업 데이터·업무 | 객체·책임·협력 | 독립 컴포넌트 계약 |
| 대표 모델 | DFD, 구조도 | ERD, 업무 모델 | UML 클래스·시퀀스 | 인터페이스·컴포넌트 명세 |
| 강점 | 기능 처리 명료 | 데이터 통합 | 응집 된 변경 책임 | 재사용·교체 성 |
| 유의 점 | 데이터·상태 분리 | 복잡 한 동적 행위 표현 | 과도 한 객체 분해 | 통합·버전·품질 계약 필요 |

### Ⅴ. 방법론 선택의 한계와 방안

- 핵심 요약 : 방법론을 문서 템플릿으로만 적용 하면 현장 적합성이 떨어지므로 위험·요구 특성에 맞게 조정.

| 한계 | 영향 | 대응 |
|---|---|---|
| 한 방법론 과잉 일괄 | 산출물 부담·형식 화 | 규모·안전·요구 변동 에 따라 테일러링 |
| 모델 간 불일치 | 요구·설계 추적 단절 | 공통 용어·모델 변환·RTM 운영 |
| 기술·조직 변화 | 오래된 절차와 도구 고착 | 반복·자동화·DevOps 통합 및 주기적 개선 |

### Ⅵ. 방법론 선택 제언

- 핵심 요약 : 아키텍트와 PM은 시스템 복잡도·데이터·변화율·재사용·규제 요건으로 혼합 방법을 설계.

1. 분석 자는 요구와 데이터·업무 흐름을 함께 검토 해 적합한 모델링 관점을 선택.
2. 개발 팀 은 인터페이스·산출물 추적과 CI·자동 시험을 포함해 절차를 실행.
3. PMO 는 적용·생략 근거와 품질 결과를 회고해 조직 방법론 자산을 갱신.

### Ⅶ. 결론

- 핵심 요약 : 개발 방법론은 시스템을 이해·분해·구현·검증 하는 관점과 절차의 조합.
- 시사점 : 프로젝트 상황에 맞는 핵심 원칙을 유지 하며 산출물·활동은 위험 기반으로 조정.
