## Ⅰ. McCabe 순환복잡도의 개요

- 개념 : 토마스 맥케이브(Thomas McCabe)가 제안한 소프트웨어 복잡도 측정 메트릭으로, 프로그램의 제어 흐름 그래프(CFG, Control Flow Graph) 상에서 선형적으로 독립적인 기본 경로(Basis Path)의 수를 정량적으로 계산하는 척도.
- 배경 및 필요성 : 소스코드의 직관적 길이(LOC)만으로는 프로그램의 논리적 난이도와 잠재 결함 위험을 측정할 수 없으므로, 테스트 케이스의 최소 수량 산정 및 리팩토링 기준 수립을 위해 고안.
- 주요 활용 : 구조적 테스트(기본 경로 테스팅) 케이스 수 산출, 코드 리뷰 및 리팩토링 대상 선별.

## Ⅱ. 순환복잡도 계산 공식 및 제어 흐름 그래프

```text
                 [ 노드 1: 진입 ]
                        │
                        ▼
                 [ 노드 2: If (A) ] ──(True)──> [ 노드 3 ]
                        │ (False)                  │
                        ▼                          ▼
                 [ 노드 4: If (B) ] ──(True)──> [ 노드 5 ]
                        │ (False)                  │
                        ▼                          ▼
                 [ 노드 6: 결합 ] <────────────────┘
                        │
                        ▼
                 [ 노드 7: 종료 ]
```

- **순환복잡도** $V(G)$의 3가지 계산 공식 :
  - **간선(Edge)과 노드(Node) 기준** : $V(G) = E - N + 2P$ (여기서 $E$는 간선 수, $N$은 노드 수, $P$는 연결된 컴포넌트 수로 단일 프로그램은 $P=1$이므로 $E - N + 2$).
  - **영역(Region) 기준** : $V(G) = R$ (그래프에 의해 둘러싸인 평면 영역의 수 + 외부 영역 1개).
  - **술어 노드(Predicate Node) 기준** : $V(G) = P_n + 1$ (조건 분기가 발생하는 조건문/반복문 노드의 수 + 1).

## Ⅲ. 순환복잡도 수치에 따른 코드 평가 기준

| 순환복잡도 $V(G)$ | 프로그램 구조 및 상태 | 리스크 등급 | 권장 조치 사항 |
|---|---|---|---|
| 1 ~ 10 | 매우 구조적이며 단순하고 명확한 코드 | 낮음 (Low) | 완벽한 테스트 가능, 현 상태 유지 |
| 11 ~ 20 | 다소 복잡하지만 제어 가능한 수준 | 보통 (Moderate) | 단위 테스트 케이스 보강 및 주의 깊은 리뷰 |
| 21 ~ 50 | 매우 복잡하여 이해하기 어렵고 결함 위험 높음 | 높음 (High) | 즉각적인 메서드 분리 및 리팩토링 필수 |
| 50 초과 | 제어 불가능한 스파게티 코드, 테스트 불가 | 극단적 (Very High) | 전면적인 아키텍처 재설계 및 재구현 |

## Ⅳ. McCabe 순환복잡도의 주요 한계점 및 해결 방안

- 코드 구조적 복잡도의 단편화 및 인지 복잡도(Cognitive Complexity) 간과 :
  - 한계점 : 단순 분기문(if, while 등)의 선형적 개수만 카운트하므로 중첩 깊이(Nesting Level), 삼항 연산자, 람다식 등 개발자가 실제 코드를 이해할 때 느끼는 인지적 난이도를 온전히 반영 못함.
  - 해결 방안 : McCabe 순환복잡도와 함께 중첩 구조에 가중치를 부여하는 SonarQube의 인지 복잡도(Cognitive Complexity) 지표를 병행 측정하여 종합적 리팩토링 기준으로 활용.
- 수치 낮추기 목적의 기계적 코드 분할로 인한 가독성 저하 :
  - 한계점 : 복잡도 임계치(보통 10 이하)를 맞추기 위해 의미 없는 단일 라인 프라이빗 메서드로 무리하게 코드를 쪼개어 오히려 호출 흐름을 파편화하고 유지보수성 악화.
  - 해결 방안 : 기계적 분리를 지양하고 객체지향 다형성(전략 패턴 등), 도메인 모델 내 책임 분리(Tell, Don't Ask), 가드 클로즈(Guard Clause)를 활용한 근본적 구조 개선 유도.
- 비동기·리액티브 및 동적 언어 패러다임 반영의 한계 :
  - 한계점 : 정적 제어 흐름 그래프(CFG) 기반이므로 함수형 프로그래밍의 스트림 파이프라인, 비동기 이벤트 콜백, 런타임 다형성의 동적 바인딩 복잡도를 평가하지 못함.
  - 해결 방안 : 정적 복잡도 분석 결과에만 의존하지 않고, APM 프로파일링 기반 핫스팟 분석 및 런타임 테스트 커버리지(JaCoCo)를 교차 분석하여 실제 결함 유발 구간을 집중 관리.

## Ⅴ. 정적 분석 및 테스트 자동화 관점의 기술사적 제언

- 기본 경로 테스팅(Basis Path Testing)의 완전성 보장 : 순환복잡도 $V(G)$의 값은 모든 실행 가능한 문장을 최소 1회 실행(구문 커버리지)하기 위해 필요한 최소한의 독립 경로 수이므로, 단위 테스트 작성 시 이를 케이스 도출의 하한선으로 삼아야 함.
- CI 파이프라인의 빌드 브레이크 품질 게이트 연동 : SonarQube 등 정적 분석 도구에서 메서드당 순환복잡도가 15를 초과할 경우 PR(Pull Request) 머지를 자동으로 차단하여 복잡한 코드가 코드베이스로 유입되는 것을 원천 봉쇄.
