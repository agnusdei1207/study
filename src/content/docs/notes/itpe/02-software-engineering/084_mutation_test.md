## 연관 키워드

- 뮤테이션 테스트(Mutation Test), 변이체(Mutant), 뮤테이션 점수(Mutation Score), 동등 변이체(Equivalent Mutant)
- 변이 연산자(AOR, ROR, COR, SDL), 코드 커버리지(Code Coverage), 어설션(Assertion), PITest, 증분 뮤테이션 테스팅(Incremental Mutation Testing)

## Ⅰ. 뮤테이션 테스트의 개요

- 핵심 요약 : 의도적 결함을 주입한 변이체를 테스트가 잡아내는지로 테스트 스위트의 품질을 평가하는 결함 기반 테스팅 기법.
- 개념 : **뮤테이션 테스트** (Mutation Test)는 원본 코드에 결함을 주입한 **변이체** (Mutant)를 대량 생성하고, 기존 테스트 스위트(Test Suite)를 실행해 변이체를 실패시켜 죽일(Kill) 수 있는지 측정하는 결함 기반 테스팅 기법.
- 배경 및 필요성 : 코드 커버리지는 코드가 실행되었는지만 보여줄 뿐, 어설션(Assertion)이 결함을 실제로 잡는지는 알려주지 않아 실행률이 높아도 검증이 약한 가짜 커버리지 문제가 생김.
- 주요 목적 : 테스트 스위트의 실질적 결함 검출력을 정량 평가하고, 보강이 필요한 약한 테스트 케이스를 찾아냄.
- 핵심 지표 : **뮤테이션 점수** (Mutation Score, MS).

## Ⅱ. 뮤테이션 테스트의 특징

- 핵심 요약 : 변이 연산자로 결함을 체계적으로 주입하고, 생사 판정을 점수로 정량화하는 구조.

1. **변이 연산자** (AOR(Arithmetic Operator Replacement), ROR(Relational Operator Replacement), COR(Conditional Operator Replacement), SDL(Statement Deletion)) : 산술·관계·논리 연산자 교체와 문장 삭제를 적용해 변이체 생성 → 결함 주입의 체계성 확보.
2. 오라클 검출력 평가 : 어설션이 결함을 실패로 드러내는 능력, 즉 오라클 파워(Oracle Power)를 측정 → 어설션의 실질 강도 판단.
3. 정량 지표 : 뮤테이션 점수 = 사망 변이체 수 / (전체 변이체 수 − 동등 변이체 수) × 100% → 테스트 검출력의 백분율 표현.
4. **동등 변이체** (Equivalent Mutant) : 문법은 바뀌었으나 의미가 원본과 같아 어떤 테스트로도 죽일 수 없는 변이체 → 점수 분모에서 제외.
5. 커버리지와 상보 관계 : 실행 여부(커버리지)와 결함 검출력(뮤테이션 점수)을 함께 봐야 실질 품질을 판단 → 가짜 커버리지 적발.

## Ⅲ. 뮤테이션 테스트의 구조 (흐름)

- 핵심 요약 : 변이체 생성부터 테스트 실행, 생사 판정까지 이어지는 단계적 흐름.

```text
[ 원본 소스 코드 ]
   ↓ 변이 연산자 적용
[ 변이체 (Mutants) 대량 생성 ]
   ↓
[ 기존 테스트 스위트 실행 ]
   ↓
  테스트 실패 → 변이체 사망 (Killed)
  테스트 통과 → 변이체 생존 (Lived)
```

- 사망 변이체는 의도된 결함을 포착한 것으로 스위트의 우수성을 보여주고, 생존 변이체는 결함이 있어도 통과했으므로 테스트 케이스 보강이 필요함을 뜻함.

| 변이 연산자 | 원본 코드 예시 | 변이 코드 예시 | 검출 목적 |
| --- | --- | --- | --- |
| 산술 연산자 교체 (AOR) | `a = b + c;` | `a = b - c;` | 산술 계산 로직 검증 |
| 관계 연산자 교체 (ROR) | `if (a > b)` | `if (a >= b)` | 경계값 어설션 누락 검증 |
| 논리 연산자 교체 (COR) | `if (a && b)` | `if (a || b)` | 복합 조건 검증 강도 확인 |
| 문장 제거 (SDL) | `callImportantMethod();` | (해당 문장 삭제) | 필수 실행 문장 검증 여부 |

## Ⅳ. 코드 커버리지와 뮤테이션 점수의 비교

- 핵심 요약 : 실행 여부 측정과 결함 검출 능력 측정이라는 본질적 차이.

```text
[ 원본 ] if (a > b) { max = a; }
   ↓ 관계 연산자 교체 (ROR)
[ 변이체 ] if (a >= b) { max = a; }
   ↓ 경계값 입력 (a = b) 으로 실행
   실패 → 사망(Killed) : 어설션 유효
   통과 → 생존(Lived) : 케이스 보강
```

| 비교 항목 | 코드 커버리지 (Code Coverage) | 뮤테이션 점수 (Mutation Score) |
| --- | --- | --- |
| 측정 대상 | 코드의 실행 여부 | 결함을 검출하는 어설션의 존재 여부 |
| 알려진 한계 | 어설션 검증 강도 미반영 (가짜 커버리지) | 계산 비용이 높고 동등 변이체 판별이 어려움 |
| 산출 방식 | 구문·분기 등 실행 비율 | 사망 변이체 / (전체 − 동등 변이체) |
| 상호 관계 | 100% 커버리지여도 뮤테이션 점수는 낮을 수 있음 | 높은 점수는 실질 검증 강도의 근거 |

## Ⅴ. 뮤테이션 테스트의 장점과 한계

- 핵심 요약 : 테스트 검출력의 정량화라는 장점 아래, 변이체 폭증과 동등 변이체, CI/CD 빌드 지연이라는 한계가 존재.
- 장점 : 테스트 스위트의 실질 결함 검출력 정량화, 어설션 누락과 약한 케이스의 구체적 식별, 커버리지로는 드러나지 않는 가짜 커버리지 적발.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 변이체 폭증과 실행 시간 증가 | 전체 코드에 연산자를 적용하면 변이체가 조합 폭발하여 단위 테스트 실행 시간 급증 | 선별 뮤테이션(Selective Mutation) 적용, 변경 범위 한정 실행 | 전체 실행 시간, 변이체 생성 수 |
| 동등 변이체 판별 난제 | 의미상 동일한 변이체가 점수를 왜곡하고 수작업 분석 공수를 낭비 | 정적 분석 기반 AST(Abstract Syntax Tree) 등가 패턴 필터링, PITest 등 도구 연동 | 동등 변이체 비율, 수작업 분석 건수 |
| CI/CD 빌드 지연 | 커밋마다 전수 실행하면 빠른 피드백 루프가 무너짐 | 증분 뮤테이션 테스팅(Incremental Mutation Testing)으로 변경 코드만 검증, 야간 전수 검증 병행 | 빌드 소요 시간, PR 단계 검증 시간 |

## Ⅵ. 고신뢰성 소프트웨어 검증을 위한 기술사적 제언

- 핵심 요약 : 자동화 도구 기반의 품질 게이트와 증분 실행 전략을 함께 도입해 실행 비용을 통제하는 방향.

1. 자바 생태계에서는 PITest를 CI 파이프라인에 연동하고, 핵심 비즈니스 모듈에 뮤테이션 점수 기준을 품질 게이트로 두는 방안이 현실적이다.
2. 변경 파일에 한정한 증분 실행과 다중 코어를 활용한 병렬 실행을 결합해, 전수 실행의 시간 비용을 통제하는 설계가 필요하다.

## Ⅶ. 결론

- 핵심 요약 : 뮤테이션 테스트는 커버리지를 넘어 테스트의 실질 강도를 증명하는 검증 기법.
- 시사점 : 증분 실행과 연산자 선별로 비용을 억제하고, 품질 게이트 편입과 야간 전수 검증을 이원화하는 것이 실무 적용의 핵심 조건.
