---

## 30초 인출

- 본질: **뮤테이션 테스트(Mutation Testing)** 는 원본 소스코드에 인위적인 문법 변형(연산자 치환, 문장 삭제 등)을 가하여 변종(Mutant)을 생성한 후, 기존 단위 테스트 케이스들이 해당 변종 결함을 감지하여 실패(Killed)하는지 여부를 측정하는 테스트 스위트 품질 평가 기법
- 메커니즘: 원본 코드 구문 트리 파싱 → 뮤테이션 연산자 주입 및 변종($M$) 생성 → 기존 단위 테스트 스위트 실행 → 테스트 실패 시 살해(Killed) / 통과 시 생존(Survived) 판정 → 뮤테이션 점수(Mutation Score) 도출
- 통찰: 단순 코드 커버리지는 단언문(Assertion) 없는 무의미한 코드 실행만으로도 100%를 달성하는 맹점이 존재하므로 뮤테이션 테스트를 CI 파이프라인에 결합하여 생존 변종을 분석하고 기대 결과 단언을 정밀 보강할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **뮤턴트(Mutant)** : 원본 소스코드에 단일 인위적 결함(Syntactic Fault)을 주입하여 생성한 변종 프로그램
- **살해된 변종(Killed Mutant)** : 주입된 결함으로 인해 테스트 케이스가 실패(Fail)하여 정상적으로 검출된 변종
- **생존 변종(Survived Mutant)** : 결함 코드가 실행되었음에도 모든 테스트를 통과하여 테스트 단언 부족을 드러낸 변종
- **동등 변종(Equivalent Mutant)** : 문법은 변형되었으나 시맨틱(의미론적 행위)이 원본과 동일하여 어떤 테스트로도 살해할 수 없는 변종
- **뮤테이션 점수(Mutation Score)** : 전체 유효 변종 중 테스트에 의해 살해된 변종의 백분율 비율 ($K / (M - E) \times 100$)

</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 테스트 스위트의 결함 검출 능력을 평가하는 뮤테이션 테스트(Mutation Test)의 개념과 기본 가정(가설)을 설명하고, 변종 생성 및 평가 프로세스, 주요 뮤테이션 연산자, 동등 변종(Equivalent Mutant) 판별 난제 및 실행 비용 절감 방안을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 원본 소스코드에 연산자 치환, 상수 변경 등의 구문 변형을 가한 변종(Mutant)을 생성하고, 기존 테스트 스위트가 이를 감지(Fail)하는지 측정하여 테스트의 유효성을 검증하는 화이트박스 결함 주입 기법 |
| 목적 | 단순 코드 실행 여부만 측정하는 코드 커버리지의 한계 극복, 단언(Assertion) 누락 식별, 고품질 테스트 케이스 설계 유도 |

## Ⅱ. 핵심 특징

뮤테이션 테스팅은 두 가지 핵심 공학적 가설에 기반하여 소규모 변형만으로도 대규모 잠재 결함을 완벽히 통제.

| 핵심 2대 가설 | 가설의 내용 | 공학적 의미 및 실무 적용 |
|---|---|---|
| **소규모 결함 가설 (Competent Programmer Hypothesis)** | 숙련된 프로그래머가 작성한 코드는 대개 정답에 근접하며 단순 문법/연산자 오류 등 사소한 결함을 가짐 | 연산자 변경, 부호 반전 등 단일 변경(First-order)만으로도 현실 결함 대부분 모델링 가능 |
| **결합 효과 가설 (Coupling Effect Hypothesis)** | 여러 개의 단순 결함이 결합하여 발생하는 복합 결함은 단순 결함들을 검출하는 테스트 케이스로 연쇄 검출됨 | 복합 변종(Higher-order Mutant)을 일일이 만들지 않아도 단일 변종 테스트로 충분한 신뢰성 확보 |

- **테스트 스위트 역평가** : 제품 코드를 테스트하는 것이 아니라, 제품 코드 변형을 매개체로 '테스트 코드 자체의 결함 검출 능력'을 역으로 평가.

## Ⅲ. 체계·프로세스

뮤테이션 테스트의 5단계 평가 프로세스 및 변종 살해/생존 판정 아키텍처.

```text
[뮤테이션 테스트 수행 프로세스 및 판정 체계]
[원본 소스코드] ──> (1) AST 구문 분석 ──> (2) 뮤테이션 연산자 주입 (AOR, ROR 등)
                                                      │
                                                      ▼
                                             [다수의 변종(Mutant) 생성]
                                                      │
                                                      ▼
  [기존 단위 테스트 스위트] ───────────────> (3) 변종 대상 테스트 실행
                                                      │
                                ┌─────────────────────┴─────────────────────┐
                                ▼                                           ▼
                     [테스트 케이스 실패 (Fail)]                 [테스트 케이스 성공 (Pass)]
                                │                                           │
                                ▼                                           ▼
                         [변종 살해 (Killed)]                        [변종 생존 (Survived)]
                         (정상적으로 결함 검출)                      (테스트 스위트 검증 사각)
                                │                                           │
                                │                             ┌─────────────┴─────────────┐
                                │                             ▼                           ▼
                                │                    [동등 변종 (Equivalent)]     [실제 단언 누락 결함]
                                │                    (의미론적 동일, 분모 제외)   (Assertion 보강 대상)
                                │                             │                           │
                                └──────────────────────┬──────┴───────────────────────────┘
                                                       ▼
                                           (4) 뮤테이션 점수(MS) 산출
                                           MS = [ K / (M - E) ] * 100 (%)
                                                       │
                                                       ▼
                                           (5) 테스트 케이스 보강 및 재실행
```

- **뮤테이션 점수 정량 산출 공식**:
  $$\text{Mutation Score (MS)} = \frac{K}{M - E} \times 100 \quad (\%)$$
  - $K$ (Killed Mutants): 테스트 실패를 유발하여 정상 살해된 변종 수.
  - $M$ (Total Mutants): 생성된 전체 변종 프로그램의 총수.
  - $E$ (Equivalent Mutants): 문법은 바뀌었으나 실행 결과는 원본과 동일하여 어떤 테스트로도 살해할 수 없는 동등 변종 수.

## Ⅳ. 종류·비교

#### 코드 커버리지 vs 뮤테이션 테스트 상세 비교

| 비교 항목 | 코드 커버리지 (Code Coverage) | 뮤테이션 테스트 (Mutation Testing) |
|---|---|---|
| **측정 대상** | 테스트 실행 시 소스코드의 도달(수행) 여부 | 주입된 결함을 테스트가 잡아내는지(단언 검증) 여부 |
| **단언(Assertion) 검증** | 불가능 (단언문이 한 줄도 없어도 100% 달성 가능) | 필수적 (단언문이 부실하면 변종이 생존하여 점수 하락) |
| **실행 비용** | 매우 낮음 (1회 테스트 실행으로 계측 완료) | 매우 높음 (변종 수 $M$개만큼 테스트 스위트 반복 실행) |
| **결과 신뢰도** | 보통 (거짓 양성: 코드는 돌았으나 검증 안 됨) | 매우 높음 (변종 살해를 통해 실제 결함 검출력 입증) |
| **대표 도구** | JaCoCo, Cobertura, Istanbul | PITest (Java), Mutmut (Python), Stryker (JS/TS) |

#### 주요 5대 뮤테이션 연산자 (Mutation Operators)

| 연산자 유형 | 연산자 명칭 및 메커니즘 | 원본 코드 예시 | 변종 생성 코드 예시 |
|---|---|---|---|
| **AOR** | Arithmetic Operator Replacement (산술 연산자 교체) | `int fee = price + tax;` | `int fee = price - tax;` |
| **ROR** | Relational Operator Replacement (관계 연산자 교체) | `if (age >= 18)` | `if (age > 18)` |
| **COR** | Conditional Operator Replacement (논리 연산자 교체) | `if (isVip && hasCoupon)` | `if (isVip || hasCoupon)` |
| **SDL** | Statement Deletion (핵심 문장 삭제) | `userRepository.save(user);` | `/* deleted */` |
| **CRCR** | Constant Replacement (상수값 치환) | `return true;` | `return false;` |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 대규모 코드베이스에서 수만 개의 변종 생성 시 테스트 실행 시간이 수 시간 이상 급증 | 변경된 소스코드(PR 단위) 대상 증분 변이(Incremental Mutation) 적용 및 테스트 병렬 실행 |
| 원본과 시맨틱이 동일하여 절대로 죽지 않는 동등 변종(Equivalent Mutant) 판별 난제 | 바이트코드 최적화 분석 도구를 도입하여 바이트코드가 동일한 변종을 자동 필터링 |
| 생존 변종 리포트 검토 시 개발자의 수동 분석 공수 과다 발생 | 결함 위험도가 높은 핵심 금융/정산 도메인 모듈로 뮤테이션 테스트 범위를 한정 타깃팅 |

## Ⅵ. 제언

뮤테이션 테스트는 높은 컴퓨팅 비용이 수반되므로 전수 검사 대신 핵심 비즈니스 도메인을 중심으로 배포 파이프라인의 야간 빌드(Nightly Build)에 통합하는 단계적 적용 전략 수립

```text
[전체 프로젝트] ──> [핵심 도메인 모듈 선별] ──> [PR 단계: 증분 PITest] ──> [야간 빌드: 전체 분석] ──> [단언 보강]
                     (결제/정산/인증 패키지)        (수정 파일 대상 초고속)        (심층 동등 변종 제거)      (MS 85% 유지)
```

| 파이프라인 단계 | 실행 방식 | 핵심 목표 |
|---|---|---|
| **PR 검증 단계** | Git Diff 기반 수정 파일 대상 바이트코드 뮤테이션(PITest) | 3분 이내 실행 완료, 신규 작성 코드의 단언 누락 즉시 검출 |
| **야간 정기 검증** | 코어 패키지 전체 대상 5대 연산자 전수 변이 실행 | 주간 뮤테이션 점수(MS) 80% 이상 유지, 취약 모듈 식별 |
| **동등 변종 정제** | AI 기반 AST 정적 분석을 통한 동등 변종 자동 식별 및 제외 | 수동 분석 공수 70% 절감, 평가 지표의 객관적 신뢰도 확보 |
