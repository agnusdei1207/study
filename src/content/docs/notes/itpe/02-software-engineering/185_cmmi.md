## 한 줄 본질
- 소프트웨어 개발의 성패를 개인의 영웅적 역량에 맡기지 않고, 조직적 표준 프로세스와 정량적 데이터 관리를 통해 재현 가능하고 지속 개선 가능한 품질 체계를 구축하는 성숙도 프레임워크 / 프로세스 제도화와 공정 최적화

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  CMMI 5대 성숙도 레벨 (Staged Representation)            |
+-------------------------------------------------------------------------+
|  [ Level 5 : Optimizing ]           지속적 혁신, 근본 원인 분석, 결함 예방 |
|         ▲                                                               |
|  [ Level 4 : Quantitatively Managed] 정량적 관리, 통계적 공정 관리(SPC)  |
|         ▲                                                               |
|  [ Level 3 : Defined ]              조직 표준 프로세스 확립, 테일러링   |
|         ▲                                                               |
|  [ Level 2 : Managed ]              프로젝트 차원의 관리, 일정/요구/형상|
|         ▲                                                               |
|  [ Level 1 : Initial ]              혼돈, 비공식적, 영웅적 개인기에 의존|
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 단계적 표현(Staged Representation): 조직 전체의 성숙도를 1단계부터 5단계까지 순차적으로 밟아 올라가도록 평가하는 방식으로, 조직 수준의 성숙도 레벨(Maturity Level)을 부여함
- 연속적 표현(Continuous Representation): 조직이 선택한 개별 프로세스 영역(PA)별로 역량 수준(Capability Level 0~3)을 세분화하여 맞춤형으로 개선해 나가는 방식
- 테일러링(Tailoring): 조직 표준 프로세스 자산(OSSP)을 특정 프로젝트의 규모, 특성, 기술 환경에 맞게 합리적으로 가감 및 재단하는 절차
- 통계적 공정 관리(SPC, Statistical Process Control): 관리도(Control Chart) 등을 활용하여 소프트웨어 결함 발생률과 개발 속도의 프로세스 상한선/하한선을 정량 제어하는 Level 4 핵심 기법
- SCAMPI (Standard CMMI Appraisal Method for Process Improvement): CMMI 준수 여부를 공식 평가하는 SEI 공인 심사 방법론

## 핵심 통찰
- CMMI의 본질은 '동일한 품질의 소프트웨어를 예측 가능한 시간과 비용 내에 반복해서 만들어낼 수 있는가'임
- 레벨 2는 '개별 프로젝트' 단위의 관리 성공이지만, 레벨 3은 성공 사례를 '전사 표준 자산'으로 승격시켜 조직 전체가 공유하는 분기점임
- 레벨 4와 5는 단순 문서 작성을 넘어, 과거 공정 메트릭 데이터를 기반으로 '향후 발생할 결함과 일정을 통계적으로 예측(Predictive Management)'하고 프로세스를 자가 치유하는 최상위 단계임
- CMMI V2.0부터는 무거운 문서 중심주의를 탈피하여 애자일(Scrum), 칸반, 안전(Safety), 보안(Security) 프랙티스를 공식 흡수함

## 이웃 토픽과 구분
| 비교 항목 | CMMI (v2.0/v3.0) | SPICE (ISO/IEC 33000 / 15504) | ISO 9001 |
| :--- | :--- | :--- | :--- |
| **제정 기관** | SEI / ISACA (미국 주도) | ISO / IEC (국제 표준화 기구) | ISO (국제 표준화 기구) |
| **적용 범위** | SW, 시스템 엔지니어링, 서비스 | SW 프로세스 평가 및 심사 기준 | 제조 및 일반 전 산업 품질경영시스템 |
| **평가 모델** | 단계적 모델(1~5) + 연속적 모델 | 연속적 모델 중심 (능력 0~5단계) | 요구조건 충족 여부 합격/불합격 인증 |
| **핵심 목적** | 조직 프로세스 역량의 성숙도 개선 | 공인 표준 기반의 프로세스 수행 능력 판정 | 고객 만족을 위한 품질 보증 체계 |

## 이렇게 출제된다
- **10점형**: CMMI의 5대 성숙도 레벨(Maturity Level)과 단계적(Staged) 및 연속적(Continuous) 표현 방식을 설명하시오.
- **25점형**: 
  - 1) 조직의 프로세스 성숙도 평가를 위한 CMMI의 발전 배경과 5대 성숙도 레벨의 특징을 도식으로 설명하시오.
  - 2) CMMI 성숙도 레벨 3(Defined)과 레벨 4(Quantitatively Managed)의 핵심 차이점(통계적 공정 관리 관점)을 비교 분석하시오.
  - 3) 애자일 및 DevOps 환경에서 CMMI를 효과적으로 내재화하기 위한 프로세스 자동화 및 테일러링 전략을 제시하시오.

## 내 의견
- CMMI 인증 마크가 곧 소프트웨어의 우수성을 보장하던 시대는 지났으며, 인증 자체가 목적이 될 경우 막대한 프로세스 부채(Process Debt)를 야기함
- 오늘날의 엔지니어링 환경에서는 CMMI Level 4/5의 정량적 관리 사상을 DORA(DevOps Research and Assessment) 메트릭(배포 빈도, 변경 실패율, 복구 시간 등)과 결합하는 것이 현실적임
- 프로세스를 강제하는 두꺼운 매뉴얼 대신, CI/CD 파이프라인의 품질 게이트(Quality Gate)와 정적 코드 분석을 통해 표준 준수를 코드 수준에서 자동 증명하는 'Process as Code' 체계로 전환해야 함
