## 연관 키워드

- ALM(Application Lifecycle Management), 거버넌스(Governance), 개발(Development), 운영(Operations)
- OSLC(Open Services for Lifecycle Collaboration), 추적성(Traceability), GitOps, VSM(Value Stream Management)

## Ⅰ. ALM의 개요

- 핵심 요약 : 기획부터 운영과 폐기까지 소프트웨어 전 생명주기를 사람, 프로세스, 도구로 통합 관리하는 엔지니어링 체계.
- 개념 : 아이디어 발상에서 요구사항 분석, 설계, 구현, 테스트, 배포, 운영, 폐기(Sunset)에 이르는 전 과정을 통제하는 **애플리케이션 생명주기 관리** (ALM, Application Lifecycle Management).
- 배경 및 필요성 : 기획, 개발, 품질 보증, 운영 부서가 문서 도구, 이슈 트래커, 빌드 도구를 따로 쓰면서 정보가 단절되고, 추적성과 규제 준수 증적을 확보하기 어려움.
- 주요 목적 : 생명주기 데이터의 통합, 엔드투엔드 추적성 확보, 품질과 규제 준수 절차의 자동화.

## Ⅱ. ALM의 특징 및 장점

- 핵심 요약 : 거버넌스, 개발, 운영의 3대 영역을 도구 체계로 묶고 추적성을 끝까지 잇는 관리 방식.

1. 3대 관리 영역 : 거버넌스(투자와 리스크 통제), 개발(요구·설계·구현·검증), 운영(배포·변경·관측)으로 나뉘어 책임 경계가 명확해짐.
2. 도구 체계 통합 : 형상관리, 이슈 관리, 빌드와 테스트 도구를 API(Application Programming Interface)와 웹훅으로 연계 → 정보 단절과 중복 입력 감소.
3. **엔드투엔드 추적성** (End-to-End Traceability) : 요구 티켓에서 설계, 커밋, 테스트 결과, 배포 상태까지 연결 → 변경 영향 분석과 감사 대응이 쉬워짐.
4. 전 생명주기 포괄 : 아이디어부터 폐기까지 끊김 없이 관리하여 운영 단계의 피드백이 기획으로 환류.

## Ⅲ. ALM의 구조 (흐름)

- 핵심 요약 : 거버넌스에서 개발, 운영으로 이어지고 장애 피드백이 다시 거버넌스로 돌아가는 순환 구조.
- 3대 영역 흐름 : 각 영역의 산출물이 다음 영역의 입력이 되며, 운영 데이터가 투자 판단으로 되돌아간다.

```text
[ 3대 영역 순환 흐름 ]

[ 거버넌스 (Governance) ]
  포트폴리오 · 투자 의사결정
  리스크 · 컴플라이언스 통제
      ↓
[ 개발 (Development) ]
  요구관리 → 설계·구현 → 품질 검증
      ↓
[ 운영 (Operations) ]
  배포·변경 관리 → 장애 관측
      ↓
  피드백 → 거버넌스 (개선 루프)
```

- 추적성 연결 구조 : 요구 ID에서 배포 산출물까지 하나의 사슬로 묶어 누락 지점을 찾는다.

```text
[ 추적성 사슬 ]

[ 요구 ID (요구사항 명세 항목) ]
      ↓
[ 설계 항목 ]
      ↓
[ 코드 커밋 · 리뷰 요청 ]
      ↓
[ 테스트 케이스 ]
      ↓
[ 배포 산출물 · 운영 지표 ]
```

## Ⅳ. 전통적 SDLC와 현대 ALM의 비교

- 핵심 요약 : 단계별로 나뉜 수작업 관리에서 통합 플랫폼 기반의 전 생명주기 관리로 전환.

| 비교 항목 | 전통적 SDLC(Software Development Life Cycle) | 현대 통합 ALM |
| --- | --- | --- |
| 관리 범위 | 주로 요구분석부터 인도까지의 개발 단계 | 아이디어부터 운영과 폐기까지의 전 주기 |
| 조직과 도구 | 기획, 개발, 운영 팀이 분절된 도구 사용 | 크로스 펑셔널 팀이 단일 플랫폼에서 협업 |
| 변경 추적성 | 수작업 문서로 관리되어 동기화가 자주 누락 | 커밋, PR, 빌드, 배포 기록이 자동으로 연결 |
| 품질 보증 | 개발 완료 후 단계별로 일괄 검증 | 전 공정에 걸친 지속적 검증과 자동 품질 게이트 |
| 대표 솔루션 | 개별 CASE(Computer-Aided Software Engineering) 도구, 수작업 문서 | Azure DevOps, GitLab, Atlassian 제품군 |

- 선택 기준 : 조직이 여러 도구를 이미 쓰고 있는지, 추적성 요구가 규제 수준으로 높은지에 따라 통합 도입 범위를 정함.

## Ⅴ. ALM의 한계와 방안

- 핵심 요약 : 전 주기 가시성과 추적성의 강화가 장점이며, 도구 파편화, 문화 미성숙, 대규모 성능 저하가 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 도구 간 데이터 사일로 | 기획, 형상, 빌드 도구가 연계되지 않아 추적이 끊김 | **OSLC**(Open Services for Lifecycle Collaboration) 같은 연계 표준 인터페이스 적용 또는 통합 플랫폼 도입 | 추적 링크 완결률 |
| 문화 없이 도구부터 도입 | 협업 문화가 성숙하지 않은 상태에서 수작업 입력 부담 → 형식적 기록 | 커밋, PR 승인, 파이프라인 이벤트에서 기록을 자동 수집하고 단계별로 프로세스를 맞춤 | 수작업 입력 건수 |
| 대규모 환경의 성능 저하 | 사용자와 아티팩트 증가로 웹훅 지연과 대시보드 지연 발생 | 서버의 클라우드 네이티브 전환, 아티팩트 저장소 분리, 읽기 전용 복제본 운영 | 웹훅 지연 시간, 대시보드 응답 시간 |

## Ⅵ. ALM에 대한 기술사적 제언

- 핵심 요약 : 가치 흐름 관리로 병목을 측정하고, 감사 증적을 자동으로 남기는 체계를 갖추는 것이 고도화의 방향.
- **가치 흐름 관리** (VSM, Value Stream Management)를 ALM 데이터 위에 올려, 요구가 고객 가치로 인도되기까지의 대기 시간과 리드타임을 측정하고 가장 긴 구간부터 개선하는 운영이 필요하다.
- 인프라와 배포 설정을 Git에 선언하는 GitOps 방식을 도입하면 변경 이력이 저장소에 남아 배포 추적과 롤백이 같은 기록 체계로 묶인다.
- 금융과 의료처럼 규제가 엄격한 분야에서는 별도 수검 문서를 만드는 낭비를 줄이기 위해, 티켓 이력과 코드 리뷰 승인, 테스트 실행 로그를 변경할 수 없는 감사 증적으로 보관하는 형상 거버넌스를 세워야 한다.

## Ⅶ. 결론

- 핵심 요약 : ALM은 거버넌스, 개발, 운영을 추적 가능한 하나의 흐름으로 묶는 생명주기 관리 체계.
- 시사점 : 추적성은 기록의 양이 아니라 기록이 자동으로 수집되는지에 달려 있어, 이벤트 기반 수집이 성숙도의 출발점이 됨.
