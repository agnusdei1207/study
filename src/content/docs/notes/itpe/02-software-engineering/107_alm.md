## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **ALM(Application Lifecycle Management)** 은 애플리케이션의 기획·개발·배포·운영·폐기 전 과정을 관리하는 접근법 |
| 목적 | 단계별 산출물·변경 정보를 연결해 협업과 애플리케이션의 지속 관리를 지원 |

## Ⅱ. ALM의 특징

| 특징 | 의미 |
|---|---|
| 전 생명주기 범위 | 기획·개발·운영·폐기 정보를 함께 관리 |
| 산출물 추적 | 요구·변경·시험·릴리스의 근거 연결 |
| 협업·통제 결합 | 사람·절차·도구의 책임과 승인 이력 관리 |

## Ⅲ. ALM 산출물·피드백 체계

```text
요구·우선순위
    ↓ 추적
설계·코드 변경
    ↓
시험·검증 결과
    ↓
릴리스·배포 기록
    ↓
운영 결과·장애 이력

개선 요구 → 요구 백로그 반영
```

## Ⅳ. ALM과 SDLC 비교

| 구분 | ALM | SDLC |
|---|---|---|
| 관리 범위 | 기획부터 개발·운영·폐기까지 애플리케이션 전체 | 소프트웨어 개발에 필요한 생명주기 활동 |
| 중심 | 사람·절차·도구와 생명주기 산출물의 연결 | 요구·설계·구현·시험·배포의 개발 활동 |
| 관계 | 애플리케이션의 지속 관리 관점 | ALM에서 다루는 개발 활동의 주요 부분 |

### 적용·검증 관점

| 고려사항 | 적용 방향 |
|---|---|
| 추적성 | 요구·코드·시험·릴리스 간 식별자와 연결 규칙 수립 |
| 변경·형상 | 승인 상태와 버전·변경 이력의 일관된 관리 |
| 도구 연계 | 이종 도구 간 필요한 정보와 책임 경계 정의 |
| 운영 피드백 | 운영 이슈가 요구·개선 작업으로 이어지는 경로 마련 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 단계별 도구가 분리되어 변경 근거와 배포 결과 단절 | 공통 식별자로 요구·코드·시험·릴리스 관계 연결 |
| 상태 정의가 달라 승인·완료 여부를 서로 다르게 해석 | 도구 간 상태·승인 규칙과 책임자 정의 |
| 운영 결함이 개발 백로그로 환류되지 않음 | 장애 기록을 원인·릴리스와 연결하고 개선 요구로 등록 |

## Ⅵ. 제언

우선 실행: 최소 공통 식별자와 산출물 관계를 정의하고 변경 승인부터 릴리스까지 추적 정보를 유지.
