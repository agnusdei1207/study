## 답안 골격
```text
[테스트 드라이버(Test Driver)] ◀━━ 머리: Ⅶ 내 의견 (상향식 통합 테스트와 xUnit 단위 테스트 러너 기반의 하위 모듈 독립 검증 자동화)
 ┃
 ┣━ Ⅰ 개요 ───── 상위 호출 모듈 미개발 시 하위 모듈 단독 테스트 불가 한계 → 상위 모듈 역할을 대행하여 테스트 데이터를 주입·호출하는 시험용 가상 모듈
 ┣━ Ⅱ 특징 ───── 상향식 통합 테스팅(Bottom-up) 필수 요소 · 제어 모듈 대행 · 테스트 데이터 인자 전달 및 반환값 수신 · 소프트웨어 시험 도구(Test Harness)
 ┣━ Ⅲ 구조 ───── 테스트 케이스 입력값 / 드라이버 메인 루틴 / 대상 하위 모듈(Test Target) 호출 인터페이스 / 결과 출력 및 단언(Assert)
 ┣━ Ⅳ 흐름 ───── 테스트 대상 모듈 선정 → 가상 드라이버 코드 작성 → 파라미터 전달 및 대상 모듈 호출 → 반환값 수신 → 기대값 비교 및 결과 리포팅
 ┣━ Ⅴ 비교 ───── 테스트 드라이버(Driver, 상위 대행, 상향식) vs 테스트 스텁(Stub, 하위 대행, 하향식) vs 모의 객체(Mock)
 ┗━ Ⅵ 실무 ───── 드라이버 개발에 따른 추가 공수 부담 / 테스트 자동화 프레임워크(JUnit, pytest)를 통한 드라이버 역할 내재화
```

## 한 줄 본질
- 메인 함수나 UI 컨트롤러 같은 상위 모듈이 아직 개발되지 않았을 때 계산 모듈이나 DB 접근 모듈을 단독으로 실행해 볼 수 없는 블로킹 병목 → 상위 모듈인 척 가장하여 하위 대상 모듈에 매개변수를 넘겨 호출하고 반환 결과를 검증하는 가상 호출 제어 소프트웨어 / 테스트 전용 코드 작성 비용

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  테스트 드라이버(Driver)와 상향식(Bottom-up) 테스팅     |
+-------------------------------------------------------------------------+
|                                                                         |
|      [ 아직 개발되지 않은 상위 모듈 (Main / Controller) ]                |
|                               :                                         |
|                               : (가상 대행 호출)                        |
|                               v                                         |
|  +--------------------------------------------------------------------+ |
|  | [ 테스트 드라이버 (Test Driver) ]                                  | |
|  |  - 테스트 케이스 데이터를 읽어옴 (예: input = [10, 20])             | |
|  |  - 대상 모듈 함수 호출: targetFunction(10, 20)                     | |
|  |  - 결과 반환값 수신 및 단언 검증: assertEquals(30, result)          | |
|  +────────────────────────────┬───────────────────────────────────────+ |
|                               │ 매개변수 전달 및 호출                   |
|                               v                                         |
|  +--------------------------------------------------------------------+ |
|  | [ 실제 테스트 대상 하위 모듈 (Component Under Test) ]               | |
|  |  - int targetFunction(int a, int b) { return a + b; }              | |
|  +--------------------------------------------------------------------+ |
|                                                                         |
|  * 핵심: "드라이버는 상위(Caller)에서 하위(Callee)를 운전(Drive)한다"   |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 테스트 하네스(Test Harness): 테스트를 지원하기 위해 개발된 드라이버, 스텁, 테스트 케이스 실행기, 결과 분석기를 포괄하는 시험 지원 도구 세트
- 상향식 통합 테스트(Bottom-up Integration): 시스템의 가장 최하위 레벨 컴포넌트부터 테스트 드라이버를 붙여 검증한 뒤, 점진적으로 상위 모듈과 결합해 나가는 통합 시험 방식

## 핵심 통찰
- 단위 테스트 프레임워크(JUnit, pytest, Jest)에서 우리가 작성하는 `@Test` 메서드와 테스트 러너(Runner) 자체가 본질적으로 완벽한 "현대화된 테스트 드라이버"임
- 상향식 통합 테스트는 중요한 비즈니스 알고리즘을 조기에 검증할 수 있고 스텁을 만들 필요가 없다는 장점이 있으나, 최상위 제어 흐름(UI, 시스템 전체 동작)은 프로젝트 막바지에야 볼 수 있다는 단점이 있음
- 드라이버 코드를 너무 복잡하게 짜면 드라이버 자체에 버그가 생겨 테스트 신뢰성이 떨어지므로, 입력 데이터 공급과 단언(Assertion)만 담당하도록 단순하게 유지해야 함

## 이웃 토픽과 구분
- 테스트 드라이버 vs 테스트 스텁(Stub): 드라이버 = 아직 안 만들어진 "상위 호출자(Caller)"를 대신하여 하위를 부르는 가상 모듈 / 스텁 = 아직 안 만들어진 "하위 피호출자(Callee)"를 대신하여 더미 값을 돌려주는 가상 모듈

## 문제·원인·대책
- 적용 상황: 금융 코어 계산 엔진 개발 및 상향식 통합 검증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 상위 웹 UI와 API 컨트롤러가 완성되지 않아 백엔드 핵심 이자 계산 로직 검증 지연 | 상위 모듈 완성 시점까지 단위/통합 테스트를 미루는 직렬 개발 안티패턴 | JUnit 테스트 드라이버를 작성하여 다양한 금리/기간 파라미터를 주입하며 단독 검증 | 개발 초기 단계 핵심 알고리즘 결함 100% 조기 제거 |
