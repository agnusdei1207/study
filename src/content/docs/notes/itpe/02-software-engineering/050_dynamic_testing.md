## 연관 키워드
- 동적 테스트, 정적 테스트, 블랙박스·화이트박스·경험 기반 테스트, 테스트 오라클, DAST

### Ⅰ. 동적 테스트의 개요

- 핵심 요약 : 소프트웨어를 실제로 실행해 입력을 주입하고 출력을 대조하며 런타임을 관찰함으로써 결함을 찾는 테스팅 기법.
- 개념 : 소프트웨어를 실행 환경(또는 시뮬레이터)에서 구동하면서 다양한 입력값을 주입하고, 실제 출력을 테스트 오라클(Test Oracle, 기대 결과를 판정하는 기준)과 비교하거나 런타임 자원 소비를 관찰해 결함을 검출하는 기법이 동적 테스트(Dynamic Testing)임.
- 배경 및 필요성 : 코드를 읽는 정적 테스트(Static Testing)인 인스펙션이나 SAST만으로는 찾기 어려운 메모리 누수, 병목, 동시성 교착상태(Deadlock), 런타임 예외를 실제 실행으로 검증해야 함.
- 주요 분류 : 명세 기반(블랙박스 테스트), 구조 기반(화이트박스 테스트), 경험 기반(탐색적 테스트, 오류 추정).
- 주요 목적 : 실제 동작에 근접한 결함을 발견하는 것.

### Ⅱ. 동적 테스트의 특징 및 장점

- 핵심 요약 : 실행 기반 검증, 3대 기법 분류, 런타임 분석 수반, 테스트 오라클 의존이라는 특성.

1. 실행 기반 검증 : 실제 환경이나 시뮬레이터에서 입력을 주입하고 출력을 비교 → 실제 동작에 근접한 결함 발견.
2. 명세 기반(블랙박스) : 경계값 분석, 동등 분할 같은 명세 중심 기법 → 내부 구조를 몰라도 설계 가능.
3. 구조 기반(화이트박스) : 문장, 분기, MC/DC(Modified Condition/Decision Coverage) 같은 코드 구조 기준 → 실행 경로의 누락 점검.
4. 경험 기반 : 탐색적 테스트, 오류 추정처럼 테스터의 경험을 활용 → 명세에 없는 결함 발견.
5. 런타임 분석(Runtime Analysis) : 프로파일러로 힙 덤프, 메모리 누수, 스레드 경합을 관찰 → 실행 중에만 드러나는 문제 포착.
6. 테스트 오라클 의존 : 기대 결과와 대조해 합격을 판정 → 오라클이 불충분하면 결함을 놓침.

### Ⅲ. 동적 테스트의 구조 (흐름)

- 핵심 요약 : 환경 구축에서 합격 판정까지 이어지는 실행 프레임워크와, 정적 검증 뒤에 동적 검증을 거는 2단계 구조.

```text
[ 동적 테스트 실행 프레임워크 ]

테스트 환경 구축
  - Mock 서버, 테스트 DB 세팅
   ↓
테스트 데이터 주입
  - 경계값·동등 분할, 페이로드 전송
   ↓
소프트웨어 실행
  - 단위·통합·시스템 프로세스 구동
   ↓
런타임 결과 수집
  - 반환값, 응답 시간, 메모리 프로파일링
   ↓
테스트 오라클 대조
   ↓
합격 판정 (Pass/Fail)
```

```text
[ 정적 → 동적 2단계 검증 ]

소스코드
   ↓
1단계 정적 테스트
  - SAST, 린터, 인스펙션으로 문법·코딩 표준 결함 제거
   ↓
2단계 동적 테스트
  - 런타임 크래시, 메모리 누수, 성능·보안 검증
```

### Ⅳ. 정적 테스트와 동적 테스트 비교

- 핵심 요약 : 실행 여부, 수행 시점, 결함 대상의 축에서 두 방식은 상호 보완 관계.

| 비교 항목 | 정적 테스트 | 동적 테스트 |
|---|---|---|
| 프로그램 실행 여부 | 코드와 산출물을 실행하지 않고 검토 | 프로그램을 실제로 빌드하고 구동해 검증 |
| 주요 수행 기법 | 인스펙션, 워크스루, SAST, 린터 | 블랙박스(경계값·동등 분할), 화이트박스 MC/DC, 부하 테스트 |
| 결함 발견 대상 | 코딩 표준 위반, 문법 오류, 논리 결함, 설계 모순 | 런타임 크래시, 메모리 누수, 인터페이스 불일치, 성능 저하 |
| 수행 시점 | 요구분석·설계·코딩 등 개발 전반 | 코드가 빌드되어 실행 가능한 단계 이후 |

### Ⅴ. 동적 테스트의 한계와 방안

- 핵심 요약 : 런타임 결함 검출과 실환경 검증이라는 강점과, 환경 구축 비용·Flaky 테스트·스위트 비대화라는 한계가 공존.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 테스트 환경 구축 비용과 오라클 부재 | 운영과 비슷한 인프라, 테스트 데이터, 외부 서비스 모킹에 큰 공수가 들고, 복잡한 로직의 기대 출력을 자동 판정하기 어려움 | Testcontainers로 인프라를 컨테이너 기반으로 자동 구성, 메타모픽 테스팅(Metamorphic Testing)과 불변식(Invariant) 검증으로 오라클 공백 보완 | 환경 구축 소요 시간, 오라클 적용 범위 |
| 비결정적 결함(Flaky Test)에 따른 파이프라인 신뢰성 저하 | 네트워크 지연, 비동기 타이밍, 외부 시스템 불안정으로 결함 없이 실패가 반복되어 피드백이 마비됨 | 비동기 폴링 유틸리티(Awaitility) 적용, DB 롤백으로 테스트 격리, Flaky 테스트의 자동 탐지와 격리 | 간헐 실패율, 격리 건수 |
| 테스트 스위트 비대화에 따른 실행 시간 증가 | E2E(End-to-End)와 통합 테스트가 늘어 수 시간씩 걸리고 CI/CD 배포가 느려짐 | TIA(Test Impact Analysis, 테스트 영향도 분석) 기반 선별 실행, 클라우드 분산 러너를 통한 병렬 실행 | 전체 실행 시간, 선별 실행 비율 |

### Ⅵ. 엔터프라이즈 환경에서의 기술사적 제언

- 핵심 요약 : 정적 분석과 동적 테스트를 단계적으로 결합하고, 보안 관점의 DAST를 파이프라인에 연계하는 것이 핵심.

1. 정적과 동적의 유기적 결합 : 시프트 레프트(Shift-Left)를 실천하려면, 정적 분석(SAST)으로 기계적 결함을 먼저 걷어 낸 뒤 동적 테스트 역량을 비즈니스 로직과 복합 통합 시나리오에 집중하는 2단계 체계를 세워야 함. 그래야 디버깅 비용이 후반에 몰리지 않음.
2. DAST의 파이프라인 연계 : 기능 검증에 그치지 않고, 운영과 같은 스테이징 환경에서 DAST(Dynamic Application Security Testing)를 자동 구동해야 함. OWASP ZAP(Zed Attack Proxy) 같은 도구로 SQL 인젝션, XSS(Cross-Site Scripting), CSRF(Cross-Site Request Forgery) 같은 런타임 웹 취약점을 배포 전에 차단하는 것이 목적임.

### Ⅶ. 결론

- 핵심 요약 : 동적 테스트는 정적 테스트만으로 담보할 수 없는 런타임 품질과 보안의 최종 검증선이다.
- 시사점 : 정적 분석으로 기계적 결함을 먼저 제거하고 동적 검증에 집중하며, DAST 자동화를 결합해야 전 주기의 품질과 보안을 함께 확보할 수 있다.
