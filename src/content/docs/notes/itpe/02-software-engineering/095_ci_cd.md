## 연관 키워드

- CI/CD(Continuous Integration/Continuous Delivery/Continuous Deployment), 파이프라인, GitOps, Trunk-Based Development
- 무중단 배포(Blue-Green/Canary), 자동 롤백, 소프트웨어 공급망 보안, SBOM(Software Bill of Materials), DevSecOps

## Ⅰ. CI/CD의 개요

- 핵심 요약 : 코드 병합부터 검증된 배포까지를 자동화해 인도 속도와 안정성을 함께 확보하는 소프트웨어 공학 체계.
- 개념 : 변경 코드를 공유 저장소에 자주 병합하고 빌드·테스트를 자동 실행하는 **지속적 통합** (CI, Continuous Integration)과, 검증된 산출물을 언제든 릴리스 가능한 상태로 두는 **지속적 전달** (Continuous Delivery) 또는 운영 환경까지 자동 반영하는 **지속적 배포** (Continuous Deployment)를 잇는 **파이프라인**.
- 배경 및 필요성 : 변경이 개발 후반에 한꺼번에 합쳐지면 병합 충돌이 커지고(병합 지옥), 수작업 배포는 인적 오류로 장애를 부른다. 자동화된 검증 경로로 이 두 위험을 줄일 필요가 생겼다.
- 주요 목적 : 변경을 작은 단위로 자주 통합하고 같은 절차로 반복 배포하여, 릴리스 리드타임과 배포 위험을 함께 낮춘다.

## Ⅱ. CI/CD의 특징 및 장점

- 핵심 요약 : 잦은 통합과 자동 품질 게이트, 선언적 배포와 자동 롤백이 맞물려 빠른 전달과 낮은 배포 위험을 함께 얻는 구조.

1. **Trunk-Based Development** (트렁크 기반 개발, 짧은 수명의 브랜치를 메인 줄기에 자주 병합하는 방식) : 장기 브랜치를 줄여 통합 충돌 감소 → 병합 비용 절감.
2. 품질 게이트 : 빌드, 정적 분석, 보안 점검, 테스트를 파이프라인에서 자동 실행하고 기준 미달이면 다음 단계를 차단 → 결함의 조기 발견. 빌드 과정에서 **SBOM** (Software Bill of Materials, 소프트웨어 구성 명세서)을 함께 만들어 구성 요소를 추적.
3. 아티팩트 버전 관리 : 컨테이너 이미지에 버전 태그를 붙여 레지스트리에 보관 → 어떤 버전이 어디에 배포되었는지 추적 가능.
4. **GitOps** (Git 저장소를 배포 상태의 기준으로 두고 클러스터를 선언적으로 동기화하는 방식) : 저장소 변경 이력이 곧 배포 이력 → 감사와 원복이 쉬움.
5. **무중단 배포** (Blue-Green, Canary)과 **자동 롤백** : 새 버전을 전환하거나 일부 트래픽에 먼저 노출하고, 지표가 나빠지면 이전 버전으로 되돌림 → 서비스 중단 최소화.

## Ⅲ. CI/CD 파이프라인의 구조 (흐름)

- 핵심 요약 : 커밋에서 CI 품질 검증, 아티팩트 저장, CD 배포와 지표 감시까지 이어지는 단계별 흐름과 GitOps 동기화 구조.

```text
[ CI/CD 파이프라인 흐름 ]

[ 커밋 / 풀 리퀘스트 ]
      ↓
[ CI: 빌드·테스트 ]
 - 의존성 설치, 컴파일
 - 단위·통합 테스트 실행
      ↓
[ CI: 품질·보안 게이트 ]
 - 정적 분석, 취약점 점검
 - SBOM 생성
      ↓
[ 아티팩트 레지스트리 ]
 - 버전 태그된 이미지 보관
      ↓
[ CD: 배포 ]
 - 스테이징 배포, 자동 테스트
 - 프로덕션 무중단 배포
      ↓
[ 지표 감시 ]
 - 이상 감지 시 자동 롤백
```

```text
[ GitOps 동기화 구조 ]

[ Git 저장소 (배포 상태 기준) ]
      ↓ 변경 감지
[ GitOps 컨트롤러 ]
      ↓ 동기화
[ 운영 클러스터 ]
      ↓ 현재 상태 보고
[ GitOps 컨트롤러 (차이 확인) ]
```

- CI 단계 : 의존성 설치와 컴파일, 테스트 실행, 정적 분석과 보안 점검을 거쳐 통과한 코드만 이미지로 만든다.
- CD 단계 : 스테이징 배포와 자동 end-to-end 테스트 후 프로덕션에 무중단 방식으로 반영하고, 지표 이상 시 자동으로 되돌린다.

## Ⅳ. 지속적 통합·전달·배포의 비교

- 핵심 요약 : 세 방식의 차이는 자동화 범위와 프로덕션 반영 방식이며, 배포 승인 주체가 가장 뚜렷한 구분 기준이다.

```text
[ 지속적 통합 ] 빌드·테스트·아티팩트 생성
      ↓ 자동화 범위 확장
[ 지속적 전달 ] 스테이징까지 자동, 운영 배포는 승인
      ↓ 자동화 범위 확장
[ 지속적 배포 ] 검증 통과 시 운영까지 자동
```

| 비교 항목 | 지속적 통합(CI) | 지속적 전달(Continuous Delivery) | 지속적 배포(Continuous Deployment) |
| --- | --- | --- | --- |
| 자동화 범위 | 커밋부터 빌드, 테스트, 아티팩트 생성 | 운영 배포 직전까지 전 과정 | 운영 배포까지 사람의 개입 없이 수행 |
| 운영 반영 방식 | 배포 단계 미포함 | 담당자 승인 후 수동 배포 | 테스트 통과 즉시 자동 배포 |
| 피드백 대상 | 코드 품질과 결함 즉시 확인 | 릴리스 가능한 패키지 상태 확인 | 고객 반응을 실시간으로 확인 |
| 요구 성숙도 | 자동화된 빌드와 단위 테스트 | 스테이징 통합 테스트와 회귀 테스트 자동화 | 점진 배포, 자동 롤백, 상세한 관측 체계 |

## Ⅴ. CI/CD의 한계와 방안

- 핵심 요약 : 작은 변경의 빠른 전달과 배포 위험 감소라는 장점과 함께, 가장 큰 위험인 **소프트웨어 공급망 보안** (Software Supply Chain Security) 문제가 한계로 따른다.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 공급망 보안 취약 | 파이프라인 스크립트 탈취, 의존성 혼동(Dependency Confusion) 공격, 서명 없는 이미지 배포 | SLSA(Supply-chain Levels for Software Artifacts) 준수, 이미지 서명 검증, SBOM 자동 생성과 SCA(Software Composition Analysis) 스캔 | 서명 검증 실패율, 취약 의존성 수 |
| 파이프라인 지연 | 코드 규모 확대로 빌드·테스트 시간이 늘어나 개발 피드백 지연 | 빌드 캐시와 병렬 테스트, 변경 영향 범위 기반 테스트 선택 | 파이프라인 소요 시간, 대기 시간 |
| 배포 롤백 복잡도 | DB 스키마 마이그레이션을 포함한 배포 실패 시 애플리케이션만 롤백되어 스키마와 불일치 | 확장 후 축소(Expand and Contract) 패턴으로 하위 호환 마이그레이션 적용 | 롤백 성공률, 스키마 변경 건수 |

## Ⅵ. 안정적인 CI/CD 정착을 위한 기술사적 제언

- 핵심 요약 : 보안 점검을 파이프라인 앞단에 묶는 **DevSecOps** 체계와 점진적 롤아웃을 결합해 배포 속도와 안전을 함께 확보하는 방향.
- 보안 책임을 개발 후반의 감사 활동이 아니라 파이프라인의 게이트로 옮기고, 기준에 미달하는 빌드를 차단하는 규칙을 조직 표준으로 채택해야 한다.
- 배포는 선언형 GitOps로 관리하고 카나리 방식의 점진 배포를 기본값으로 두어, 오류율과 지연 시간이 악화되면 사람이 판단하기 전에 되돌아가는 안전망을 갖춰야 한다.
- 파이프라인은 팀마다 따로 만들지 않고 공통 플랫폼으로 운영하여, 보안 기준과 배포 규칙이 조직 안에서 일관되게 적용되도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : CI/CD는 신속한 전달과 안정적인 운영을 동시에 확보하는 소프트웨어 납품의 표준 체계.
- 시사점 : 품질 게이트, 점진 배포, 공급망 보안이 성숙한 CI/CD의 조건이며, 이 셋의 균형이 파이프라인 설계의 핵심 과제다.
