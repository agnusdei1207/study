<summary>핵심 용어</summary>

- **오픈소스 프로젝트관리 소프트웨어(Open Source PM Software)** : 소스코드를 확인·수정·배포할 수 있는 라이선스 아래 제공되는 프로젝트 작업·이슈 관리 도구
- **이슈 추적(Issue Tracking)** : 작업·결함·요청을 식별자로 등록하고 상태·담당자·처리 이력을 관리하는 기능
- **워크플로(Workflow)** : 이슈가 등록에서 완료까지 이동하는 상태와 전환 조건
- **RBAC(Role-Based Access Control)** : 사용자의 역할에 따라 프로젝트와 작업의 접근 권한을 부여하는 방식
- **자가 호스팅(Self-hosting)** : 조직이 자체 인프라에 소프트웨어를 설치·운영하는 방식
- **ALM(Application Lifecycle Management)** : 요구·개발·시험·배포 등 애플리케이션 생명주기의 활동과 정보를 연결해 관리하는 체계

## 2~4교시 25점 답안

## Ⅰ. 오픈소스 프로젝트관리 소프트웨어 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **오픈소스 프로젝트관리 소프트웨어** 는 공개 소스코드를 바탕으로 작업·일정·이슈의 협업과 추적을 지원하는 도구 |
| 목적 | 작업 책임과 진행 상태의 공유, 변경·결함 처리 이력의 확보 |

## Ⅱ. 오픈소스 프로젝트관리 소프트웨어의 특징

| 특징 | 관리 의미 |
|---|---|
| 소스와 설정의 통제 | 조직의 업무 흐름에 맞춰 설치·설정·확장 가능. 라이선스와 변경 유지보수 책임 확인 필요 |
| 작업·일정의 공동 추적 | 작업 범위·담당·기한·진척을 한 이력에서 공유 |
| **이슈 추적** | 결함·변경 요청의 상태와 처리 이력을 작업과 연결 |
| 역할별 협업 | 권한에 따라 의견·문서·승인 범위를 구분 |

Redmine의 이슈·역할 관리와 OpenProject의 작업 패키지는 구현 사례다. 개별 제품 기능을 오픈소스 전체의 공통 기능으로 단정하지 않는다.

## Ⅲ. 프로젝트 작업 체계와 처리 프로세스

```text
프로젝트·역할·권한 설정
          ↓
작업·결함 등록 → 담당·우선순위·기한 지정
                            ↓
                   진행·변경 이력 기록
                            ↓
                    검토·완료 판정
                            ↓
                    일정·진척 현황 반영
```

### 이슈 상태 전이와 권한 통제

```text
등록 ──담당 배정──> 진행 ──검토 요청──> 검토 ──승인──> 완료
                    ↑                    │                 │
                    └──── 반려·재작업 ───┘                 │
                    └──────────── 재개방 ──────────────────┘
전환 권한: 역할별 RBAC  |  전환 기록: 담당·시점·사유
```

상태 전이와 완료 기준은 조직이 합의해 설정한다. 저장소·빌드·시험 도구와의 연계는 조직의 **ALM** 범위에 따라 선택하는 확장 기능이다.

## Ⅳ. 배치 방식 비교와 도입 기준

| 방식 | 강점 | 도입 시 확인할 책임 |
|---|---|---|
| **자가 호스팅** | 데이터와 설정을 직접 통제 | 설치·패치·백업·장애 복구 |
| 관리형 서비스 | 인프라 운영 부담 축소 | 데이터 반출·접근 통제·서비스 조건 |

### 업무 적합성 확인

| 판단 축 | 확인 사항 |
|---|---|
| 배치 | **자가 호스팅** 가능 여부, 조직의 운영 인력·백업 책임 |
| 업무 적합성 | 작업 유형· **워크플로** ·보고 방식의 구성 가능 범위 |
| 접근 | 프로젝트별 **RBAC** 와 외부 협력자 권한 |
| 지속 운영 | 보안 업데이트, 플러그인 호환성, 데이터 반출·이전 방식 |

오픈소스 라이선스만으로 운영비가 없어지거나 보안이 자동 확보되는 것은 아니다.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 사용자별 작업 방식이 달라 기록 누락 | 필수 이슈 유형·상태·완료 기준을 합의하고 누락률을 시범 운영에서 확인 |
| 자체 운영의 패치·백업 부담 | 운영 책임자와 복구 절차를 지정하고 복구 시험 수행 |
| 플러그인과 외부 도구 연계 오류 | 지원 판본·연동 범위를 시험해 이슈와 코드 기록의 연결 확인 |

## Ⅵ. 제언

기능 목록만으로 도구를 고르면 실제 승인·이슈 흐름이 맞지 않을 수 있다. 공통 이슈 유형·전환 권한·완료 기준을 먼저 정하고 한 팀에서 자료 이전과 상태 전이를 검증한 뒤 프로젝트별로 확장한다.
