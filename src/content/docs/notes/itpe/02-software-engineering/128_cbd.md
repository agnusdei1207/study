## 연관 키워드

- CBD(Component-Based Development), 컴포넌트 기반 개발
- COTS(Commercial Off-the-Shelf), 상용 컴포넌트
- 3C(Component, Container, Connector)
- 제공 인터페이스(Provided Interface), 요구 인터페이스(Required Interface)
- 도메인 공학(Domain Engineering), 응용 공학(Application Engineering)

## Ⅰ. 컴포넌트 기반 개발(CBD)의 개요

- 핵심 요약 : 명확한 인터페이스를 갖춘 컴포넌트를 부품처럼 조립해 애플리케이션을 구축하는 재사용 중심 방법론.
- 개념 : 독립적인 업무 기능을 수행하도록 인터페이스를 명확히 한 패키징 모듈인 컴포넌트(Component)를 자체 개발하거나 **상용 컴포넌트** (COTS, Commercial Off-the-Shelf, 기성 제품으로 구매하는 소프트웨어 부품)로 확보한 뒤, 이를 조립하여 애플리케이션을 구축하는 **컴포넌트 기반 개발** (CBD, Component-Based Development).
- 배경 및 필요성 : 객체지향(OOP, Object-Oriented Programming)의 소스코드 수준 재사용은 언어와 프로젝트에 종속되기 쉬워, 실행 가능한 바이너리 단위로 재사용하는 방식이 요구됨.
- 주요 목적 : 개발 생산성 향상, 유지보수 비용 절감, 검증된 부품 조립에 기반한 신속한 시스템 구축.
- 컴포넌트의 3대 구성 요소 **3C** (Component, Container, Connector) : 업무 기능 단위인 컴포넌트, 실행 환경인 컨테이너, 컴포넌트 간 연동 수단인 커넥터.

## Ⅱ. 컴포넌트 기반 개발(CBD)의 특징 및 장점

- 핵심 요약 : 3C 구성과 제공·요구 인터페이스의 계약, 블랙박스 재사용이 결합되어 조립 중심의 개발이 가능해지는 방식.

1. 3C 구성 : 컴포넌트, 컨테이너, 커넥터가 역할을 나누어 맡음 → 업무 로직과 실행 환경, 연동 방식을 분리하여 교체 용이성 확보.
2. **제공 인터페이스** (Provided Interface) : 컴포넌트가 외부에 제공하는 서비스 규약으로, UML에서 롤리팝(Lollipop) 기호로 표기 → 호출자가 구현을 몰라도 기능 사용 가능.
3. **요구 인터페이스** (Required Interface) : 정상 동작에 필요한 외부 서비스 규약으로, UML에서 소켓(Socket) 기호로 표기 → 필요한 기능이 연결되었는지 조립 단계에서 확인 가능.
4. **블랙박스 재사용** : 내부 구현을 숨긴 바이너리 단위(.jar, .dll 등)로 재사용 → 소스 공개 없이 부품을 공유하여 재사용 범위 확대.
5. **도메인 공학** (Domain Engineering, 재사용 자산을 생산하는 활동)과 **응용 공학** (Application Engineering, 자산을 조립해 제품을 만드는 활동)의 병행 → 재사용 자산을 축적하며 개발 속도를 높임.

## Ⅲ. 컴포넌트 기반 개발(CBD)의 구조 (흐름)

- 핵심 요약 : 도메인 공학이 재사용 자산을 만들고, 응용 공학이 이를 검색·결합해 애플리케이션을 릴리스하는 2대 트랙 구조.

```text
[ 도메인 공학 (Domain Engineering) ]

도메인 분석, 공통 기능 식별
        ↓
컴포넌트 설계·구현·단위 테스트
        ↓
저장소 등록 (재사용 자산 라이브러리)
```

```text
[ 응용 공학 (Application Engineering) ]

고객 요구 분석, 컴포넌트 검색
        ↓
제공·요구 인터페이스 결합, 어댑터 작성
        ↓
통합 테스트 후 애플리케이션 릴리스
```

## Ⅳ. 객체지향(OOP)·CBD·마이크로서비스(MSA)의 비교

- 핵심 요약 : 재사용 단위와 결합 방식, 배포 독립성이 소스코드 수준에서 바이너리, 독립 서비스로 진화하는 흐름.

| 비교 항목 | 객체지향 개발 (OOP) | 컴포넌트 기반 개발 (CBD) | 마이크로서비스 아키텍처 (MSA, Microservice Architecture) |
| --- | --- | --- | --- |
| 재사용 단위 | 클래스, 객체 (소스코드 수준) | 바이너리 컴포넌트 (.jar, .dll) | 독립 실행되는 서비스 단위 |
| 결합 방식 | 언어 수준의 상속과 합성, 컴파일 링크 | 컨테이너를 통한 인터페이스 바인딩 | 네트워크 기반 API(Application Programming Interface), REST(Representational State Transfer), gRPC |
| 배포 독립성 | 단일 애플리케이션으로 통합 빌드·배포 | 컴포넌트 단위 교체 배포 가능 | 서비스 단위의 독립 배포 |
| 실행 환경 | 프로세스 메모리 내부 | EJB(Enterprise JavaBeans) 컨테이너, Spring IoC(Inversion of Control) 컨테이너 | 컨테이너(Docker), 오케스트레이션(Kubernetes) |

## Ⅴ. 컴포넌트 기반 개발(CBD)의 한계와 방안

- 핵심 요약 : 바이너리 재사용과 교체 배포의 장점 이면에 인터페이스 복잡성, 은닉된 의존성, 버전 호환성의 한계가 존재.
- 장점 : 바이너리 단위 재사용으로 개발 기간과 비용 절감, 검증된 상용 컴포넌트 활용으로 초기 품질 확보, 교체 배포로 유지보수성 향상.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 인터페이스 복잡성 증가 | 범용성을 과도하게 추구하여 매개변수와 구성 옵션이 비대해지고, 개별 프로젝트 적용 시 생산성이 떨어짐 | 도메인 분석으로 핵심 공통 기능만 캡슐화하고, **인터페이스 분리 원칙** (ISP, Interface Segregation Principle)에 따라 얇은 계약 인터페이스 설계 | 인터페이스당 메서드 수, 컴포넌트 재사용률 |
| **은닉된 의존성** (Hidden Dependency) | 내부에서 참조하는 서드파티 라이브러리 버전 불일치나 전역 상태 의존으로 통합 단계에서 런타임 충돌 발생 | 의존성 주입(DI, Dependency Injection) 컨테이너로 외부 의존성을 명시적으로 주입하고, 컴포넌트 계약 테스트를 구축 | 통합 장애 건수 |
| 버전 진화에 따른 하위 호환성 부담 | 업그레이드 시 영향받는 애플리케이션 파악이 어려워 버전이 고착되고 기술 부채로 누적 | **시맨틱 버저닝** (SemVer, Semantic Versioning) 준수와 API 호환성 변경 검출 도구의 CI(Continuous Integration) 연동 | 버전 고착 기간, 호환성 위반 건수 |

## Ⅵ. 컴포넌트 기반 개발(CBD)에 대한 기술사적 제언

- 핵심 요약 : 도메인 경계를 기준으로 레거시 컴포넌트를 점진적으로 분리하고, 계약 테스트로 통합 파손을 막는 방향.
- 레거시 EJB나 CBD 컴포넌트는 이미 업무 도메인 단위로 응집되어 있으므로, 전면 재작성보다는 **도메인 주도 설계** (DDD, Domain-Driven Design)의 **바운디드 컨텍스트** (Bounded Context, 모델의 적용 범위를 명시한 경계)를 기준으로 컴포넌트 경계를 나누고, 경계 단위로 마이크로서비스화를 진행하는 것이 위험을 줄이는 방법이다.
- 컴포넌트 내부 구현이 바뀌더라도 외부 인터페이스 규약이 깨지지 않도록, 소비자 측이 기대하는 응답 형식을 명세로 정의하고 이를 자동 검증하는 **계약 테스트** (Contract Test)를 CI 파이프라인에 넣는 것이 필요하다.

## Ⅶ. 결론

- 핵심 요약 : CBD는 인터페이스 계약 기반 컴포넌트 조립으로 생산성과 재사용성을 확보하는 방법론.
- 명확한 인터페이스 규약을 가진 컴포넌트의 조립으로 빠른 시스템 구축을 실현하며, 인터페이스 복잡성과 은닉 의존성을 통제하고 MSA로 점진 진화하는 것이 실무 적용의 관건이다.
