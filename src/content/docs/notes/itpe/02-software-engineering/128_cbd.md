```text
 ┃
 ┣━ Ⅰ 개요 ───── 클래스 단위 객체지향의 낮은 재사용성 한계 → 독립적으로 배포 가능한 바이너리 단위 컴포넌트의 조립식 개발
 ┣━ Ⅱ 특징 ───── 소프트웨어 재사용(Reuse) 극대화 · 인터페이스 기반 블랙박스 캡슐화 · 독립 배포 단위(Component)

 ┣━ Ⅴ 비교 ───── 객체지향(OOP, 소스코드 레벨) vs CBD(바이너리 컴포넌트) vs 서비스 지향(SOA, 네트워크 서비스)

```

## 한 줄 본질
- 처음부터 모든 것을 새로 코딩하는 개발 방식의 낮은 생산성과 품질 편차 병목 → 독립적으로 배포 및 실행 가능한 소프트웨어 부품(컴포넌트)을 표준 인터페이스로 조립하여 시스템을 구축하는 방법론 / 레고 블록식 조합 시 요구사항 불일치 발생

## 핵심 용어
- 컴포넌트(Component): 독립적으로 배포될 수 있고, 제3자에 의해 조립될 수 있으며, 명확하게 정의된 인터페이스만을 통해 접근 가능한 실행 단위 바이너리 부품
- CBSD(Component Based Software Development): 소프트웨어를 처음부터 개발하지 않고, 저장소에 이미 존재하는 공통 컴포넌트들을 검색·선택·조립(Assembly)하여 시스템을 완성하는 기법

## 핵심 통찰
- 객체지향 프로그래밍(OOP)이 "소스코드 레벨의 화이트박스 재사용"이라면, CBD는 내부 코드를 볼 필요 없이 명세서만 보고 끼워 맞추는 "실행 바이너리 레벨의 블랙박스 재사용"임
- 현실의 비즈니스 요구사항은 레고 블록처럼 딱 들어맞지 않으므로, 조립 과정에서 컴포넌트 인터페이스를 감싸는 어댑터(Glue Code/Wrapper) 비용이 과도해져 배보다 배꼽이 더 커지는 문제가 빈번했음
- 과거 COM/DCOM, EJB 중심의 무거운 언어 종속적 CBD는 쇠퇴했으나, 이 "인터페이스 기반 독립 배포 부품" 철학은 Docker 컨테이너와 REST/gRPC 기반의 마이크로서비스(MSA)로 완벽히 부활함

## 이웃 토픽과 구분
- CBD vs SOA: CBD = 바이너리 수준의 컴포넌트 결합 및 런타임 조립(단일 플랫폼/환경 중심) / SOA = 표준 네트워크 프로토콜(SOAP/REST)을 통한 이기종 플랫폼 간 느슨한 서비스 연계

## 문제·원인·대책
- 적용 상황: 대규모 공공 정보화 사업 공통 비즈니스 컴포넌트 패키징
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 공통 컴포넌트를 각 업무 팀이 그대로 쓰지 못하고 코드를 복사해서 제각각 수정함 | 컴포넌트가 너무 크거나 비즈니스 로직이 하드코딩되어 확장 인터페이스 부재 | 컴포넌트 입도(Granularity)를 최소화하고 전략 패턴(Strategy) 기반 확장 포인트 제공 | 코드 중복 제거 및 공통 컴포넌트 재사용률 65% 달성 |
| 공유 라이브러리(DLL/JAR) 버전 충돌로 인해 특정 기능 배포 시 다른 기능 마비 | 공유 바이너리 런타임 환경의 의존성 전파 및 격리 실패(DLL Hell) | 도메인별 독립 런타임 격리 및 컨테이너(Docker) 기반 마이크로서비스 전환 | 컴포넌트 간 영향도 제로화 및 독립 배포 달성 |

## 이렇게 출제된다
- 제113회 1교시: "CBD(Component Based Development)의 개념 및 컴포넌트 식별 절차를 설명하시오." → 요구 포인트: 컴포넌트 정의 + 도메인 분석 기반 식별 기법(유스케이스 분석, 공통성/가변성 분석)
- 제80회 2교시: "CBD 방법론의 개발 공정과 객체지향 방법론과의 차이점을 설명하시오." → 요구 포인트: CD vs CBSD 듀얼 사이클 + OOP vs CBD 비교표

## 내 의견
- [재사용 컴포넌트 만능주의로 인한 프로젝트 파행 경계] 조직의 도메인 성숙도가 낮은 상태에서 초기부터 "모든 시스템에서 쓸 수 있는 완벽한 범용 공통 컴포넌트"를 만들려다 일정 지연 발생 → 나라면: Rule of Three 원칙(최소 3개 이상의 시스템에서 중복이 확인된 시점)에 따라 사후적으로 컴포넌트를 추출하고, 현대에는 라이브러리 형태보다 API 기반의 독립 서비스(Microservice) 형태로 모듈화하여 관리
