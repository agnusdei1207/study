## Ⅰ. CBD(컴포넌트 기반 개발)의 개요

- 개념 : 독립적인 비즈니스 기능을 수행하도록 명확한 인터페이스를 갖추어 패키징된 소프트웨어 모듈인 '컴포넌트(Component)'들을 사전에 개발하거나 기성 상용 컴포넌트(COTS)를 확보한 후, 이들을 부품처럼 레고 블록식으로 조립(Assembly)하여 새로운 애플리케이션을 신속하게 구축하는 재사용 중심의 소프트웨어 공학 방법론.
- 배경 및 필요성 : 객체지향(OOP)의 소스코드 레벨 재사용 한계를 극복하고, 실행 가능한 바이너리 단위의 블랙박스 재사용성을 확보하여 개발 생산성 향상 및 유지보수 비용 대폭 절감.
- 컴포넌트의 3대 핵심 속성 (3C) : 컴포넌트(Component), 컨테이너(Container: 실행 환경), 커넥터(Connector: 연동 인터페이스).

## Ⅱ. CBD 방법론의 2대 트랙 프로세스

```text
   [ 도메인 공학 (Domain Engineering) : 컴포넌트 개발 ]
    - 도메인 분석 및 공통 비즈니스 로직 식별
    - 컴포넌트 설계, 구현, 단위 테스트
    - 컴포넌트 저장소(Repository)에 등록 및 배포
                        │
                        ▼ (재사용 자산 라이브러리 제공)
   [ 응용 공학 (Application Engineering) : 컴포넌트 조립 ]
    - 고객 요구사항 분석 및 기존 컴포넌트 검색/매칭
    - 컴포넌트 간 인터페이스 결합 및 어댑터 작성
    - 통합 테스트 및 신규 비즈니스 애플리케이션 릴리스
```

- **제공 인터페이스** (Provided Interface) : 컴포넌트가 외부에 제공하는 서비스 메서드 규약 (롤리팝 표기법: 실선 끝에 원).
- **요구 인터페이스** (Required Interface) : 컴포넌트가 정상 동작하기 위해 외부 다른 컴포넌트로부터 제공받아야 하는 규약 (소켓 표기법: 실선 끝에 반원).

## Ⅲ. 객체지향(OOP), CBD, 마이크로서비스(MSA)의 진화 비교

| 비교 항목 | 객체지향 개발 (OOP) | 컴포넌트 기반 개발 (CBD) | 마이크로서비스 아키텍처 (MSA) |
|---|---|---|---|
| 재사용 단위 | 클래스, 객체 (소스코드 수준) | 바이너리 컴포넌트 (.jar, .dll) | 독립 실행 프로세스 / 서비스 단위 |
| 결합 방식 | 언어 레벨의 상속, 합성, 컴파일 링크 | 컨테이너 기반 인터페이스 바인딩 | 네트워크 기반 경량 API (REST, gRPC) |
| 배포 독립성 | 단일 애플리케이션으로 통합 빌드/배포 | 컴포넌트 단위 교체 배포 가능 | 완전한 무중단 독립 서비스 배포 |
| 실행 환경 | 프로세스 메모리 내부 | EJB 컨테이너, COM+, Spring IoC | Docker 컨테이너, Kubernetes 클러스터 |
| 주 활용 시대 | 1990년대 전산화 초기 | 2000년대 엔터프라이즈 프레임워크 | 현대 클라우드 네이티브 분산 환경 |

## Ⅳ. CBD(컴포넌트 기반 개발)의 주요 한계점 및 해결 방안

- 과도한 컴포넌트 일반화로 인한 인터페이스 복잡성 증가 :
  - 한계점 : 컴포넌트의 범용 재사용성을 지나치게 추구하다 보면 매개변수와 구성 옵션이 비대해져 오히려 개별 프로젝트 적용 시 생산성 저하.
  - 해결 방안 : 도메인 분석 기반 핵심 공통 기능만 최소 캡슐화, 인터페이스 분리 원칙(ISP)을 준수하여 얇고 명확한 계약(Contract) 인터페이스 설계.
- 컴포넌트 간 **은닉된 의존성** (Hidden Dependency)으로 인한 통합 장애 :
  - 한계점 : 컴포넌트 내부에서 참조하는 서드파티 라이브러리 버전 불일치나 전역 상태 의존성으로 인해 통합 단계에서 런타임 충돌 발생.
  - 해결 방안 : 의존성 주입(DI) 컨테이너를 통한 외부 의존성 명시적 주입, 컴포넌트 계약 테스트(Consumer-Driven Contract Testing) 체계 구축.
- 컴포넌트 버전 진화 시 하위 호환성 관리 부담 :
  - 한계점 : 컴포넌트 업그레이드 시 이를 사용하는 수많은 애플리케이션의 영향도를 파악하기 어려워 버전 고착화 및 기술 부채화.
  - 해결 방안 : 시맨틱 버저닝(SemVer) 준수, 컴포넌트 저장소(Repository) 기반 자동화된 API 브레이킹 체인지 검출 도구 CI 연동.

## Ⅴ. 엔터프라이즈 현대화 관점에서의 기술사적 제언

- CBD에서 MSA로의 점진적 전환 아키텍처 수립 : 레거시 엔터프라이즈의 EJB/CBD 컴포넌트들은 비즈니스 도메인 단위로 이미 응집되어 있으므로, 이를 무리하게 빅뱅 방식으로 재작성하지 말고 컴포넌트 경계를 도메인 주도 설계(DDD)의 바운디드 컨텍스트(Bounded Context)로 매핑하여 마이크로서비스로 점진적 분리 권장.
- 컴포넌트 명세 표준화 및 **계약 테스트** (Contract Test) 강화 : 컴포넌트 내부 구현이 변경되더라도 외부 제공 인터페이스 규약이 깨지지 않도록 Pact 등 소비자 주도 계약(Consumer-Driven Contract) 테스트를 자동화하여 통합 파손 방지.
