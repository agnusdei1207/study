## 30초 인출

- 본질: **CBD(Component-Based Development, 컴포넌트 기반 개발)** 는 명시된 인터페이스를 가진 소프트웨어 부품을 재사용·조립하는 개발 방식
- 메커니즘: 재사용 요구 식별 → 컴포넌트 계약·의존성 확인 → 선택·조립 → 통합 시험
- 통찰: 한계: 내부 기능만 맞는 부품을 조립하면 인터페이스·버전·의존성 불일치가 통합 때 드러남 → 방안: 계약 적합성을 먼저 확인

<details>
<summary>핵심 용어</summary>

- **컴포넌트(Component)** : 제공·요구 인터페이스와 의존성을 명시하고 다른 구성요소와 조립할 수 있는 소프트웨어 단위
- **인터페이스 계약(Interface Contract)** : 컴포넌트가 제공하는 기능과 호출 조건을 외부에 명시한 약속
- **재사용을 위한 개발(Development for Reuse)** : 여러 시스템에서 쓸 수 있는 컴포넌트를 설계·검증·등록하는 활동
- **재사용에 의한 개발(Development with Reuse)** : 기존 컴포넌트를 검색·평가·조립해 시스템을 만드는 활동
</details>

## 2~4교시 25점 답안

## Ⅰ. 컴포넌트 기반 개발의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **CBD** 는 명시된 인터페이스를 가진 소프트웨어 부품을 재사용·조립하는 개발 방식 |
| 목적 | 중복 개발 감소와 검증된 부품의 재사용·교체 용이성 확보 |

## Ⅱ. 컴포넌트 기반 개발의 특징

| 특징 | 개발상 의미 |
|---|---|
| 계약 중심 조립 | 내부 구현보다 제공·요구 인터페이스의 호환성이 중요 |
| 재사용 자산 관리 | 버전·의존성·품질 정보가 저장소와 함께 관리됨 |
| 개발 활동의 분리 | 재사용 가능한 부품의 개발과 기존 부품의 활용을 구분 |

## Ⅲ. 컴포넌트 조립 체계와 재사용 프로세스

```text
애플리케이션 요구
      ↓ 적합성 평가
컴포넌트 저장소
  ├─ 제공·요구 인터페이스
  ├─ 버전·의존성
  └─ 시험·품질 정보
      ↓ 선택·연결
조립된 애플리케이션 → 통합 시험
```

**핵심:** 컴포넌트의 내부 구현보다 외부 계약과 호환성을 기준으로 조립.

### 제공·요구 인터페이스의 조립 판정

```text
업무 요구 ─필요 기능·데이터 계약→ 요구 인터페이스
                                      ↓ 호환성 비교
후보 컴포넌트 ─버전·의존성 확인→ 제공 인터페이스
                                      ├─ 일치 → 연결·통합 시험
                                      └─ 불일치 → 다른 후보 또는 계약 변경 검토
```

## Ⅳ. 재사용을 위한 개발과 재사용에 의한 개발 비교

| 활동 | 핵심 절차 | 확인 사항 |
|---|---|---|
| 재사용을 위한 개발 | 공통 요구 분석 → 계약 설계 → 검증·등록 | 실제 재사용 가능성, 버전 관리 |
| 재사용에 의한 개발 | 검색 → 요구 적합성 평가 → 조립·통합 시험 | 인터페이스·의존성·품질 적합성 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 요구와 부품 기능이 달라 수정·우회 코드 증가 | 요구 적합성을 먼저 평가하고 필요한 확장 지점만 설계 |
| 버전·의존성 충돌로 조립 실패 | 호환 범위 명세와 통합 시험 자동화 |
| 공통화 비용이 재사용 효과보다 큼 | 반복되는 요구와 사용 범위를 확인한 뒤 자산화 |

## Ⅵ. 제언

반복 요구가 확인된 부품부터 인터페이스 계약·버전·의존성을 명세하고 저장소 등록 전 검증과 조립 후 통합 시험을 시행한다.
