## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 개발·운영 → CBD(Component-Based Development)

## 지식 위치

소프트웨어공학 > 개발 방법론 > 컴포넌트 기반 개발

## 30초 인출

- 본질: 독립적인 기능을 수행하는 소프트웨어 컴포넌트들을 인터페이스 기반으로 조립하여 새로운 애플리케이션을 구축하는 재사용 중심 소프트웨어 개발 방법론
- 메커니즘: 재사용을 위한 개발(CD: 도메인 분석 → 컴포넌트 추출 → 패키징/저장소 등록)과 재사용에 의한 개발(CBS: 요구사항 분석 → 컴포넌트 검색/선택 → 조립 및 통합 시험)로 이원화 수행
- 통찰: 무분별한 컴포넌트 도입 시 인터페이스 불일치와 블랙박스 내부 오류 추적 한계가 발생하므로 계약에 의한 설계(DbC) 표준화와 컴포넌트 저장소 거버넌스 수립 필수

<details>
<summary>핵심 용어</summary>

- **컴포넌트 (Component)** : 독립적으로 배포 및 실행 가능하며 명확히 정의된 인터페이스를 통해 서비스를 제공하는 소프트웨어 모듈 단위
- **제공 인터페이스 (Provided Interface)** : 컴포넌트가 외부에 노출하여 호출자에게 서비스를 제공하는 공개 규격
- **요구 인터페이스 (Required Interface)** : 컴포넌트가 자신의 내부 기능을 수행하기 위해 외부 다른 컴포넌트로부터 제공받아야 하는 의존 인터페이스
- **재사용을 위한 개발 (Development for Reuse, CD)** : 여러 시스템에서 공통적으로 활용 가능한 컴포넌트를 설계, 구현, 검증하여 저장소에 등록하는 활동
- **재사용에 의한 개발 (Development with Reuse, CBS)** : 기존에 구축된 컴포넌트 저장소에서 적합한 부품을 검색, 평가, 커스터마이징하여 시스템을 조립하는 활동
</details>

## 2~4교시 예상문제 (25점)

> CBD(Component-Based Development) 방법론의 개념과 핵심 원리를 설명하고, 재사용을 위한 개발(CD)과 재사용에 의한 개발(CBS)의 절차 비교 및 성공적 정착을 위한 엔터프라이즈 거버넌스 방안을 제시하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 독립적인 기능을 수행하며 표준화된 인터페이스를 갖춘 소프트웨어 컴포넌트들을 식별, 구축, 조립하여 전체 시스템을 완성하는 재사용 중심 개발 방법론 |
| 목적 | 개발 생산성 극대화, 품질 신뢰성 향상, 개발 기간(Time-to-Market) 단축 및 소프트웨어 유지보수 비용 절감 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 블랙박스 재사용 | 컴포넌트 내부 구현 코드를 알 필요 없이 명시된 인터페이스 규격(API/시그니처)만으로 기능 결합 |
| 명확한 인터페이스 분리 | 제공 인터페이스(Provided Interface)와 요구 인터페이스(Required Interface)를 명확히 정의하여 결합도 최소화 |
| 독립적 배포 가능성 | 독립된 바이너리 패키지 단위로 버전 관리 및 런타임 교체(Hot-Swapping) 가능 |
| 2-Track 라이프사이클 | 컴포넌트를 생산하는 자산화 프로세스(CD)와 이를 활용해 제품을 구축하는 조립 프로세스(CBS)의 분리 운영 |

코드 레벨의 단순 복사-붙여넣기 재사용을 넘어 아키텍처 단위의 표준화된 모듈 조립 패러다임을 확립.

## Ⅲ. 체계·프로세스

```text
[Track 1: 재사용을 위한 개발 (CD: Component Development)]
  도메인 분석 및 모델링 ──► 컴포넌트 식별 ──► 컴포넌트 설계 및 구현 ──► 컴포넌트 인증/테스트
                                                                             │
                                                                             ▼
                                                                  [컴포넌트 저장소 (Repository)]
                                                                  - 인터페이스 명세서
                                                                  - 바이너리 패키지 & 테스트셋
                                                                             ▲
                                                                             │
[Track 2: 재사용에 의한 개발 (CBS: Component-Based Software)]                │
  요구사항 정의 ──► 컴포넌트 검색 및 평가 ──────────────────────────────────┘
                           │
                           ▼ 적합성 판정 (Gap 분석)
                    컴포넌트 커스터마이징 (Adapter 패턴 등)
                           │
                           ▼
                    애플리케이션 조립 및 통합 테스트 ──► 시스템 배포
```

자산화 파이프라인과 조립 파이프라인이 저장소를 매개로 유기적으로 결합되어 선순환을 이루는 프로세스.

## Ⅳ. 종류·비교

| 비교 항목 | 재사용을 위한 개발 (CD) | 재사용에 의한 개발 (CBS) |
|---|---|---|
| **활동 목표** | 범용성 및 확장성을 갖춘 고품질 컴포넌트 자산 생산 | 기존 컴포넌트를 신속히 조립하여 특정 비즈니스 애플리케이션 완성 |
| **수행 주체** | 컴포넌트 전문 개발팀 (도메인 엔지니어) | 응용 애플리케이션 구축팀 (솔루션 엔지니어) |
| **핵심 활동** | 도메인 공통성/가변성 분석, 표준 인터페이스 설계 | 컴포넌트 검색, 적합도 평가, 어댑터 개발, 조립 |
| **품질 평가 기준** | 범용성, 재사용률, 인터페이스 안정성, 성능 | 요구사항 충족도, 조립 용이성, 출시 속도(Time-to-Market) |
| **주요 산출물** | 컴포넌트 바이너리, 인터페이스 계약 명세서, 단위 테스트셋 | 완성된 완제품 시스템, 통합 테스트 결과서 |

### CBD와 객체지향(OOP) 및 서비스 지향(SOA) 비교

| 비교 항목 | 객체지향 개발 (OOP) | 컴포넌트 기반 개발 (CBD) | 서비스 지향 아키텍처 (SOA) |
|---|---|---|---|
| **기본 단위** | 클래스, 객체 | 컴포넌트 (바이너리 패키지) | 서비스 (독립 배포 단위) |
| **재사용 수준** | 소스 코드 레벨 (상속, 다형성) | 실행 바이너리 레벨 (인터페이스 조립) | 네트워크 프로토콜 레벨 (REST, SOAP) |
| **결합도** | 높음 (컴파일 타임 바인딩) | 중간 (인터페이스 기반 런타임/배포 바인딩) | 낮음 (표준 메시징 기반 느슨한 결합) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 컴포넌트 블랙박스 특성으로 인해 내부 장애 발생 시 원인 추적 및 디버깅 곤란 | 상세한 인터페이스 명세서 제공 및 사전/사후 조건(Pre/Post Condition)을 규정하는 계약에 의한 설계(DbC) 적용 |
| 요구사항과 기존 컴포넌트 기능 간의 미세한 불일치(Gap)로 인한 래퍼(Wrapper) 코드 급증 | 어댑터(Adapter), 퍼사드(Facade) 디자인 패턴을 체계적으로 적용하고 매개변수화된 가변성 메커니즘 지원 |
| 컴포넌트의 초기 개발 및 표준화, 저장소 유지보수를 위한 높은 초기 투자 비용 수반 | 비즈니스 핵심 도메인 중심으로 점진적 자산화(Domain-Driven)를 수행하고 재사용 기여도에 대한 인센티브 거버넌스 수립 |

## Ⅵ. 제언

현대 클라우드 네이티브 환경에서는 기존의 로컬 바이너리 중심 CBD에서 컨테이너 기반 마이크로서비스 아키텍처(MSA) 및 사내 내부 개발자 플랫폼(IDP) 자산화로의 진화적 통합 추진 권장.

```text
[현대적 컴포넌트 거버넌스 파이프라인]
  도메인 서비스 개발 → OCI 컨테이너/Helm 패키징 → 아티팩토리 저장소 등록 → GitOps 기반 서비스 조립 배포
```

| 관리 영역 | 전통적 CBD 거버넌스 | 클라우드 네이티브 MSA 거버넌스 |
|---|---|---|
| 컴포넌트 형태 | DLL, JAR, COM 컴포넌트 | Docker Image, Helm Chart, 테라폼 모듈 |
| 의존성 및 배포 | 라이브러리 클래스패스 의존성 | 서비스 메시(Service Mesh) 및 선언적 오케스트레이션 |
