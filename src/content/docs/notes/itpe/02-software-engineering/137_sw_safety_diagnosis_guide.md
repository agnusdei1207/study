## 연관 키워드

- SW 안전진단 가이드, 과학기술정보통신부, NIPA(National IT Industry Promotion Agency), 4대 진단 영역
- FMEA(Failure Mode and Effects Analysis), FTA(Fault Tree Analysis), 단일 장애점(SPOF, Single Point of Failure), 결함 허용(Fault Tolerance), 정적 분석(SAST)

## Ⅰ. SW 안전진단 가이드의 개요

- 핵심 요약 : 소프트웨어 결함으로 인한 재난적 사고를 막기 위해 안전성을 체계적으로 진단하는 정부 가이드라인.
- 개념 : 과학기술정보통신부와 NIPA(National IT Industry Promotion Agency, 정보통신산업진흥원)가 제시하는 **SW 안전진단 가이드**(SW 안전성을 객관적으로 진단하기 위한 점검 기준과 절차를 담은 가이드라인).
- 배경 및 필요성 : 전력, 교통, 의료 등 사회 기반이 소프트웨어로 통제되면서 소프트웨어 오류가 인명 피해나 서비스 마비로 직결되므로, 사전에 안전성을 점검할 체계가 필요해짐.
- 4대 진단 영역 : 본 노트는 프로세스, 아키텍처, 소스코드, 실행환경의 네 영역으로 진단 대상을 나누어 정리.
- 주요 목적 : 안전 취약점을 개발 초기와 운영 단계에서 발견하고, 위험도에 따라 개선 조치의 우선순위를 정하는 것.

## Ⅱ. SW 안전진단 가이드의 특징 및 장점

- 핵심 요약 : 네 영역을 전 생애주기에서 점검하고 위험도별 조치를 권고하는 구조가 진단 결과의 객관성과 개선 실행력으로 이어지는 체계.

1. 프로세스 점검 : 안전 요구 관리, 형상 관리, 변경 통제의 적정성을 확인 → 요구 누락과 무단 변경에 따른 사고 예방.
2. 아키텍처 점검 : **단일 장애점**(SPOF, Single Point of Failure) 제거와 결함 허용 구조를 확인 → 한 부품의 고장이 전체 중단으로 번지지 않음.
3. 소스코드 점검 : 메모리 오류, 동시성 오류, 보안 약점을 정적 분석 도구와 코딩 규칙으로 확인 → 코드 단계에서 결함을 조기에 제거.
4. 실행환경 점검 : 패치, 이중화, 백업과 복구 체계를 확인 → 장애 발생 시 복구 시간 단축.
5. 위험도별 조치 권고 : 진단 결과를 위험도로 나누어 개선 우선순위를 제시 → 한정된 예산을 고위험 항목에 집중.

## Ⅲ. SW 안전진단 가이드의 구조 (흐름)

- 핵심 요약 : 계획, 자료 수집, 영역별 심층 분석, 개선 권고로 이어지는 4단계 절차와, 그 절차가 점검하는 네 영역의 구조.

```text
[ 1. 진단 계획 수립 ]
 - 진단 대상 시스템 선정
        ↓
[ 2. 현장 실사·자료 수집 ]
 - 소스코드, 설계서, 장애 이력
        ↓
[ 3. 영역별 심층 분석 ]
 - 도구 기반 정적·동적 진단
 - 전문가 인스펙션
        ↓
[ 4. 개선 조치 권고 ]
 - 위험도별 조치, 진단 보고서
```

```text
[ SW 안전진단 대상 ]
  - 프로세스 영역
  - 아키텍처 영역
  - 소스코드 영역
  - 실행환경 영역
```

- 진단 방법론 : 도구 기반 정적·동적 진단과 전문가 인스펙션을 병행하여 판단의 객관성을 확보.

## Ⅳ. SW 안전진단 영역별 점검 항목의 비교

- 핵심 요약 : 영역마다 점검 항목과 검증 방법이 달라, 네 영역을 함께 보아야 안전성 커버리지가 확보됨.

| 진단 영역 | 핵심 점검 항목 | 주요 검증 방법 |
| --- | --- | --- |
| 프로세스 | 안전 요구사항 추적성, **고장 모드·영향 분석** (FMEA, Failure Mode and Effects Analysis)과 FTA(Fault Tree Analysis) 수행 여부 | 요구사항 명세서, 추적성 매트릭스, 위험관리 계획서 감사 |
| 아키텍처 | **결함 허용** (Fault Tolerance), 비상 정지 메커니즘, 모듈 격리 | 아키텍처 설계서 검토와 설계자 인터뷰 |
| 소스코드 | 버퍼 오버플로, Null 역참조, 교착상태, 코딩 규칙 준수 | **정적 분석** (SAST, Static Application Security Testing) 도구의 전수 검사 |
| 실행환경 | 자원 고갈 시 동작, 네트워크 단절 후 복원 | 결함 주입 시험(Fault Injection), 스트레스 테스트 |

- MISRA-C : 자동차 산업에서 널리 쓰이는 C 언어 코딩 규칙으로, 소스코드 안전성 판정의 참고 기준으로 활용.

## Ⅴ. SW 안전진단 가이드의 한계와 대응 방안

- 핵심 요약 : 진단원 역량 편차, 설계 산출물 부재, 권고 이행 부진을 역량 인증과 역공학, 이행 연계로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 진단원 전문성 편차 | 체크리스트 중심 진단 → 정적 분석 결과 보고에 그쳐 아키텍처 수준 결함과 동적 위험 식별 미흡 | 진단원 자격 인증 제도화, 동적 경쟁 조건 등을 다루는 심화 실습형 진단 방법 정립 | 진단원 인증 비율, 진단 발견 결함의 심각도 분포 |
| 레거시 설계 산출물 부재 | 노후 시스템에 최신 설계서가 없어 역공학과 블랙박스 테스트에 공수 과다 | 바이너리 분석과 런타임 관측 도구를 활용한 반자동 아키텍처 역공학 절차 수립 | 역공학 소요 공수, 문서 복원율 |
| 개선 권고 이행 부진 | 예산 부족과 서비스 중단 불가로 취약점이 장기 방치 | 진단 후 이행 여부를 감리와 성과평가에 연계, 고위험 결함에 긴급 예산과 WAF(Web Application Firewall)·IPS(Intrusion Prevention System) 가상 패치 우선 적용 | 고위험 결함 조치 기한 준수율 |

## Ⅵ. 공공 기반시설 안전 확보를 위한 기술사적 제언

- 핵심 요약 : 진단 이후의 조치 예산을 제도로 보장하고, 산업별 국제 기능안전 표준과 진단 기준을 맞추는 체계.

1. 후속 조치 예산의 제도화 : 공공기관 발주 부서는 안전진단 사업에 개선 유지보수 예산을 함께 편성하도록 제도적 근거를 마련해야 한다. 진단만 하고 조치 예산이 없어 취약점이 방치되는 일을 막기 위해서다.
2. 국제 표준과의 정합성 : 자동차 분야의 ISO 26262, 산업 공통의 IEC 61508, 철도 IEC 62278, 항공 DO-178C, 의료 IEC 62304 등 산업별 기능안전 요구사항을 진단 체크리스트와 대응시켜, 국내 진단 결과가 국제 기준에서도 해석되도록 해야 한다.

## Ⅶ. 결론

- 핵심 요약 : SW 안전진단 가이드는 사회 기반 소프트웨어의 재난 예방을 위해 안전성을 점검하는 정부 가이드라인.
- 시사점 : 진단 결과가 실제 개선으로 이어지려면 진단원 역량과 조치 예산, 이행 점검이 함께 갖춰져야 함.
