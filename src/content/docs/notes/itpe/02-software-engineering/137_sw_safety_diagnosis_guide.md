## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 안전·신뢰성 → **SW 안전진단 가이드**

## 30초 인출

- 본질: SW 안전진단은 운영 중이거나 개발 중인 소프트웨어가 오작동으로 안전 문제를 일으키지 않는지 점검항목별로 진단해 개선 사항을 도출하는 활동
- 메커니즘: 진단 대상의 위험도를 정하고 소프트웨어 자체·운영 환경·개발 프로세스 관점의 점검항목을 확인해 미흡 항목을 개선 과제로 정리
- 통찰: 점검표 항목을 형식적으로 채우면 실제 위험이 남으므로 위험도가 높은 기능을 먼저 선정해 점검하고 미흡 항목은 개선 과제와 이행 확인까지 관리

<details>
<summary>핵심 용어</summary>

- **소프트웨어 안전(Software Safety)** : 소프트웨어 오작동으로 인한 생명·신체·재산 피해가 없는 상태
- **안전진단** : 점검항목에 따라 소프트웨어의 안전 확보 수준을 확인하는 활동
- **페일세이프(Fail-Safe)** : 장애가 발생해도 시스템이 안전한 상태로 전환되는 설계
- **위험도 등급** : 오작동 시 피해 정도에 따라 진단 우선순위를 정하는 구분
- **개선 과제** : 진단에서 발견한 미흡 항목을 시정하기 위한 조치

</details>

## 2~4교시 25점 답안

## Ⅰ. SW 안전진단의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **SW 안전진단** 은 소프트웨어의 안전 확보 수준을 점검항목별로 진단해 개선 사항을 도출하는 활동 |
| 목적 | 오작동으로 인한 피해의 예방과 안전 수준의 확인 |

## Ⅱ. 일반 품질 점검과 구별되는 특징

| 특징 | 의미 |
|---|---|
| 안전 중심 | 생명·재산 피해 가능성 관점 |
| 위험도 기반 | 위험이 큰 대상 우선 진단 |
| 개선 연계 | 미흡 항목의 개선 과제화 |

## Ⅲ. 진단 절차와 관점

### 진단 절차

```text
진단 대상·위험도 선정
    ↓
점검항목별 진단 (자체·운영 환경·프로세스)
    ↓
미흡 항목 도출 → 개선 과제
    ↓
이행 확인·재진단
```

### 확대: 진단 관점

```text
소프트웨어 자체 ── 안전 기능 설계·품질
운영 환경 ── 이중화·백업·데이터베이스·서버
개발 프로세스 ── 요구부터 유지보수까지의 안전 활동
```

## Ⅳ. 진단 관점별 점검 예

| 관점 | 점검 예 |
|---|---|
| 소프트웨어 자체 | 오류 처리, 안전 상태로의 전환(페일세이프), 시험 수행 |
| 운영 환경 | 이중화·백업, 장애 대응 체계 |
| 개발 프로세스 | 위험 분석, 안전 요구사항 관리, 변경 관리 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 점검표 형식적 작성으로 실제 위험 잔존 | 위험도 높은 기능 우선 선정과 증적 확인 |
| 미흡 항목 개선 미이행 | 개선 과제 이행 확인과 재진단 |
| 진단 시점 이후 변경으로 안전 수준 변동 | 변경 시 영향 범위 재진단 |

## Ⅵ. 제언

위험도가 높은 기능부터 진단하고, 미흡 항목은 개선 과제로 등록해 이행 확인과 재진단까지 관리

### 진단 관리 순환

```text
위험도 순 진단 대상 선정
    ↓
진단 → 개선 과제 등록
    ↓
이행 확인 → 재진단
```

### 확대: 재진단 판단

```text
개선 이행 완료
    ├─ 증적 확인 → 종결
    └─ 미이행·불충분 → 재조치
```

### 선택 근거: 일회성 점검과의 비교

| 구분 | 일회성 점검 | 제언: 위험도·이행 관리 |
|---|---|---|
| 대상 선정 | 전체 균등 | 위험도 순 |
| 개선 확인 | 없음 | 이행 확인 |
| 변경 대응 | 미반영 | 재진단 |
