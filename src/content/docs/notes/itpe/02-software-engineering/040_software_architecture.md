## 연관 키워드
- 소프트웨어 아키텍처, 품질속성, 4+1 뷰
- ISO/IEC/IEEE 42010, ATAM, ADR, 아키텍처 침식

## Ⅰ. 소프트웨어 아키텍처의 개요

- 핵심 요약 : 소프트웨어 아키텍처는 구성요소·관계·설계 원칙에 관한 상위 수준 구조 결정으로 품질과 변경 대응력을 좌우하는 설계 결정의 집합.
- 개념 : 시스템의 주요 구성요소, 요소 간 관계, 외부 환경과의 상호작용, 설계·진화 원칙에 관한 근본 구조 결정이 **소프트웨어 아키텍처** (Software Architecture)임.
- 배경 및 필요성 : 시스템 규모·이해관계자의 다양화로 전체 구조에 관한 공통 판단 기준이 없으면 품질 요구 충돌과 변경 비용 급증 상태에 놓임.
- 주요 목적 : 성능·보안·변경용이성 같은 **품질속성** (Quality Attribute) 요구의 충족과 이해관계자 소통 기반의 확보.

## Ⅱ. 소프트웨어 아키텍처의 특징 및 장점

- 핵심 요약 : 표준 정의 체계·다중 뷰·품질속성 중심 설계·분석과 기록 방법이 구조 결정의 신뢰성을 높임.

1. 표준 정의 체계 : 이해관계자·관심사·관점 체계를 규정한 **ISO/IEC/IEEE 42010** (아키텍처 기술 국제 표준) 활용 → 아키텍처 설명의 일관성 확보.
2. 다중 뷰 표현 : 논리·프로세스·개발·물리 뷰와 시나리오로 구성된 **4+1 뷰** (4+1 View Model) → 이해관계자별 관심사에 맞춘 소통·검토 효율 향상.
3. 품질속성 중심 설계 : 품질속성을 자극·응답·측정 조건을 갖춘 시나리오로 구체화해 구조 결정에 반영 → 기능 중심 설계 편향 방지.
4. 분석·기록 방법 : 품질 간 상충을 평가하는 **ATAM** (Architecture Tradeoff Analysis Method, 아키텍처 트레이드오프 분석 방법)과 근거를 남기는 **ADR** (Architecture Decision Record, 아키텍처 의사결정 기록) → 결정의 투명성·재사용성 확보.

## Ⅲ. 소프트웨어 아키텍처의 구조 (흐름)

- 핵심 요약 : 시나리오 수립부터 평가·문서화·준수 관리까지 절차로 운영되고, 아키텍처가 상세 설계·구현에 지침을 전달.

```text
비즈니스 목표·품질속성 시나리오
   ↓
후보 구조 설계 (구조 패턴 적용)
   ↓
분석·평가 (ATAM·시나리오 검토)
   ↓
문서화 (뷰·결정 기록)
   ↓
구현 준수 점검·진화 관리
```

```text
아키텍처 : 구조·품질속성 결정
   ↓ 설계 지침 전달
상세 설계 : 모듈 내부·알고리즘
   ↓ 코드화
구현 : 소스 코드·단위 시험
```

## Ⅳ. 소프트웨어 아키텍처와 코드 수준 설계의 비교

- 핵심 요약 : 시스템 전체 구조와 품질을 결정하는 아키텍처와 모듈 내부 구현을 다루는 코드 수준 설계는 결정 수준이 다름.

| 비교 축 | 소프트웨어 아키텍처 | 코드 수준 설계 (상세 설계) |
| --- | --- | --- |
| 결정 범위 | 시스템 전체 구조·요소 간 관계 | 모듈 내부 로직·알고리즘·자료구조 |
| 변경 비용 | 이후 변경의 파급·비용이 큼 | 국소 수정으로 상대적 저비용 |
| 품질 영향 | 성능·보안·변경용이성 등 전체 품질 | 모듈 내부의 정확성·가독성 |
| 주 담당 | 아키텍트·이해관계자의 공동 검토 | 개발자·설계자 |
| 표현 수단 | 뷰·아키텍처 결정 기록 | 클래스·시퀀스 다이어그램·코드 |

## Ⅴ. 소프트웨어 아키텍처의 한계와 방안

- 핵심 요약 : 침식·상아탑 설계·트레이드오프 미평가·문서 부담을 준수 점검·조기 검토·시나리오 평가로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **아키텍처 침식** (Architecture Erosion, 구현이 결정과 점차 어긋나는 현상) | 문서와 실체의 괴리 → 구조 이해 비용 증가 | 의존성 검사·정적 분석 규칙·정기 준수 점검 | 규칙 위반 건수 |
| 상아탑 설계 | 소수 전문가의 단독 결정 → 운영·개발 현실과 단절 | 이해관계자 조기 검토·시나리오 검증 | 설계 변경률 |
| 트레이드오프 미평가 | 한 품질 최적화의 다른 품질 훼손 → 운영 장애·변경 비용 | 시나리오 기반 분석·대안 비교 기록 | 미검토 품질 위험 수 |
| 문서 부담 | 과잉 문서화 → 관리 비용·미사용 문서 | 핵심 뷰·결정 중심의 실용적 문서화 | 갱신 지연 문서 수 |

## Ⅵ. 소프트웨어 아키텍처에 대한 제언

- 핵심 요약 : 조직은 거버넌스·역량 체계·지식 자산화로 아키텍처를 문서 산출물이 아닌 상시 관리 대상으로 운영해야 함.

1. 거버넌스 : 아키텍처 심의 절차·준수 기준을 사업 관리 체계에 내재화하고 이해관계자 검토를 의무화.
2. 역량 체계 : 아키텍트 직무 체계·교육 과정의 운영으로 품질속성 중심 설계 역량 확보.
3. 지식 자산화 : ADR·아키텍처 자산 저장소로 결정 근거·구조 패턴을 축적해 후속 사업 재사용.

## Ⅶ. 결론

- 핵심 요약 : 소프트웨어 아키텍처는 품질속성과 변경을 결정하는 구조적 의사결정의 집합.
- 시사점 : 아키텍처의 가치는 도식 자체가 아니라 결정의 근거·검증·준수 관리에서 실현.
