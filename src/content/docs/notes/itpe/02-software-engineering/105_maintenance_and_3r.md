## 연관 키워드

- 소프트웨어 유지보수, ISO/IEC 14764, 예방 유지보수
- 역공학(Reverse Engineering), 재사용(Reuse), 재공학(Reengineering)

## Ⅰ. SW 유지보수와 3R의 개요

- 핵심 요약 : 3R은 소프트웨어 유지보수에서 기존 시스템의 정보를 복원하고 자산을 재활용하며 재구축하는 세 기법의 묶음.
- 개념 : 운영 중인 소프트웨어의 결함 제거, 환경 적응, 기능 개선을 지속하는 활동이 **소프트웨어 유지보수** (Software Maintenance)이고, 그 가운데 **역공학** (Reverse Engineering), **재사용** (Reuse), **재공학** (Reengineering)의 세 기법을 묶은 명칭이 **3R**.
- 배경 및 필요성 : 운영 기간이 긴 시스템은 기술 노후화, 문서 부재, 담당자 교체로 설계 정보 손실이 누적되는 상태이므로 기존 자산의 이해와 점진적 개선 수단 필요.
- 주요 목적 : 기존 자산의 지식을 보존하며 시스템 수명과 유지보수성의 향상, 전면 교체가 수반하는 비용·위험의 절감.

## Ⅱ. SW 유지보수 3R의 특징 및 장점

- 핵심 요약 : 역공학·재사용·재공학은 추출·재활용·재구축으로 역할을 나누어 레거시 개선을 단계별로 지원.

1. 역공학 : 구현 산출물에서 설계·요구 수준의 정보를 복원 → 문서화되지 않은 레거시 시스템의 이해와 자산화 효과.
2. 재사용 : 검증된 코드·컴포넌트·설계 자산을 새 개발에 다시 활용 → 개발 비용·기간 절감과 결함 감소 효과.
3. 재공학 : 역공학으로 확보한 이해를 기반으로 기존 기능을 보존하며 새 구조로 재구축 → 품질·기술 최신화와 수명 연장 효과.
4. 유지보수 유형과의 연계 : 소프트웨어 유지보수 국제 표준 **ISO/IEC 14764**의 **수정 유지보수** (Corrective), **적응 유지보수** (Adaptive), **완전 유지보수** (Perfective), **예방 유지보수** (Preventive) 구분과 병행 → 3R이 예방 유지보수의 대표적 실행 수단이 되는 구조.

- 세 기법의 역할 분담은 다음 표와 같이 구분.

| 구분 | 역공학 | 재사용 | 재공학 |
| --- | --- | --- | --- |
| 초점 | 설계·요구 정보의 추출 | 기존 자산의 재활용 | 재구축 전 과정 |
| 기능·외부 동작 | 변화 없음 | 재사용 대상 자산의 계승 | 보존 전제의 재구현 |
| 산출물 | 모델·문서·의존성 지도 | 재사용 자산과 목록 | 개선된 시스템 |

## Ⅲ. SW 유지보수 3R의 구조 (흐름)

- 핵심 요약 : 현행 조사 → 역공학 → 범위 결정 → 재구조화·재구현 → 검증·이행의 순서로 적용.

```text
현행 시스템·운영 자료 조사
   ↓ 역공학 : 설계·요구 정보 복원
개선 범위·목표 구조 결정
   ↓ 재사용 : 검증된 자산 재활용
재공학 설계·재구현
   ↓ 회귀 검증 후 단계적 이행
운영 반영·자산 기록 갱신
```

- 재공학은 복원된 이해를 다시 구현으로 옮기는 활동인 **순공학** (Forward Engineering)을 포함하는 전 주기 과정.

```text
코드·데이터 (구현 수준)
   ↑ 역공학 : 정보 추출
설계·요구 (추상 수준)
   ↓ 순공학 : 이해의 재구현 이전
개선된 시스템 (재공학 결과)
```

## Ⅳ. 3R 기반 현대화와 신규 전면 재개발의 비교

- 핵심 요약 : 3R은 기존 자산 위의 점진 개선이고 신규 전면 재개발은 처음부터의 구축이므로 위험 구조와 적합 조건이 다름.

| 비교 축 | 3R 기반 현대화 | 신규 전면 재개발 |
| --- | --- | --- |
| 출발점 | 기존 시스템의 정보 복원·변환 | 요구 정의부터의 신규 구축 |
| 기존 자산 | 코드·데이터·운영 지식의 부분 이전 | 원칙적으로 신규 구현 |
| 기능 처리 | 기존 기능의 보존 전제 | 요구 재정의에 따른 변동 |
| 주요 위험 | 복원 정보 불완전·기능 회귀 | 요구 누락·일정·비용 과다 |
| 적합 조건 | 운영 연속성·점진 위험 관리 필요 | 유지 한계·구조 전면 전환 필요 |

## Ⅴ. SW 유지보수 3R의 한계와 방안

- 핵심 요약 : 복원 정보의 불완전성과 변환 중 회귀를 기준 동작 기록과 단계별 검증으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 역공학 정보의 불완전성 | 동적 동작·외부 연계가 소스에 기록되지 않음 → 복원 오류 | 운영 로그·담당자 인터뷰·동적 분석 병행 | 복원 결과 검증률 |
| 재사용 중 기능 회귀 | 재사용 자산의 암묵적 규칙·경계 조건 미파악 → 운영 결함 | 재사용 자산의 기준 동작 기록 후 회귀 시험 | 회귀 결함 수 |
| 재공학 범위 팽창 | 개선 대상 판단 기준 부재 → 일정·비용 과다 | 업무 가치·위험 기준의 우선순위 심의 | 범위 변경 건수 |
| 데이터 이행 위험 | 형식·코드값 불일치 → 정합성 훼손 | 이행 규칙 정의·대조 검증·병행 운영 | 이행 불일치 건수 |

## Ⅵ. 레거시 현대화에 대한 기술사적 제언

- 핵심 요약 : 시스템 소유 기관은 유지보수·3R·전면 재개발의 선택 기준을 자산 관리 거버넌스로 정립할 필요.
1. 정보시스템 소유 기관은 업무 가치·위험·기술 부채를 판단 축으로 하는 기법 선택 규칙을 자산 관리 기준에 반영.
2. 아키텍처 조직은 기존 기능을 단계적으로 신규 서비스로 대체하는 **스트랭글러 패턴** (Strangler Pattern)을 표준 이행 방법으로 채택하고 개선 결과 자산을 카탈로그로 운영.

## Ⅶ. 결론

- 핵심 요약 : 3R은 기존 소프트웨어의 지식 보존과 수명 연장을 목표로 하는 현대화 기법의 묶음.
- 시사점 : 전면 재개발과의 비교 선택을 전제로 가치·위험에 따른 점진 적용이 바람직.
