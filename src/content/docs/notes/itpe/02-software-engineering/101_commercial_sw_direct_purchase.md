## Ⅰ. 상용SW 직접구매 제도의 개요

- **개념** : 국가기관, 지방자치단체, 공공기관이 소프트웨어 개발 구축 사업을 발주할 때, 사업에 포함된 상용 소프트웨어를 SI(시스템 통합) 주사업자에게 일괄 하청 발주하지 않고, 발주기관이 해당 상용SW 제조사와 직접 계약을 체결하여 조달·구매하도록 의무화한 공공 소프트웨어 발주 제도.
- **법적 근거** : 소프트웨어진흥법 제54조(상용소프트웨어 직접구매), 동법 시행령 제49조 및 과학기술정보통신부 고시.
- **도입 배경** : SI 주사업자의 상용SW에 대한 불합리한 단가 후려치기(하도급 마진 착취), 대금 미지급, 라이선스 유지관리비 삭감 관행을 근절하여 국내 상용SW 생태계 육성.

## Ⅱ. 직접구매 대상 기준 및 예외 심의 절차

```text
   [ 공공 SW 사업 발주 계획 수립 ]
                  │
                  ▼
   [ 직접구매 대상 요건 검토 ] ────── 사업금액 3억 원 이상 & 상용SW 추정가격 5천만 원 이상
                  │
         ┌────────┴────────┐
         ▼                 ▼
   [ 직접구매 원칙 추진 ]  [ 예외 사유 발생 시: 직접구매 제외 신청 ]
   - 나라장터 쇼핑몰 직접구매  - 현저한 비용 상승, 현저한 일정 지연, 호환성 불가
   - 제조사와 분리 계약 체결   │
                               ▼
                   [ 과업심의위원회 타당성 심의 ]
                               │
                   ┌───────────┴───────────┐
                   ▼                       ▼
            [ 예외 불인정: 직접구매 ] [ 예외 인정: SI 일괄 발주 허용 ]
```

- **의무 대상 요건** :
  - 총 사업금액(추정가격)이 3억 원 이상인 소프트웨어 사업.
  - 사업에 포함된 개별 상용 소프트웨어의 추정가격이 5천만 원 이상인 경우 (단, GS인증 제품이거나 조달청 우수조달물품인 경우 의무 구매).
- **예외 인정 사유** : 기 구축된 시스템과의 연계/호환이 불가능한 경우, 국방/안보상 고도의 보안이 요구되는 경우, 분리구매 시 사업비용이 현저히 증가하거나 납기가 심각하게 지연되는 경우로 한정되며, 반드시 사전에 과업심의위원회 심의를 통과해야 함.

## Ⅲ. SI 일괄 발주와 상용SW 직접구매의 비교

| 비교 항목 | SI 일괄 발주 (과거 관행) | 상용SW 직접구매 (제도화) |
|---|---|---|
| 계약 주체 | 발주자 <-> SI 주사업자 (상용SW는 하도급) | 발주자 <-> SI 주사업자 및 발주자 <-> 상용SW 제조사 (별도 계약) |
| 소프트웨어 대가 | SI 사업자의 마진 차감으로 원가 이하 납품 빈발 | 공공 조달 단가에 따른 정당한 제품 가격 보장 |
| 유지관리 및 기술지원 | SI 사업자가 영세 업체에 책임 전가, 지원 부실 | 제조사와 직접 유지관리요율(10~15% 수준) 계약 체결로 품질 보증 |
| 통합 관리 책임 | SI 사업자가 시스템 전체에 대한 단일 책임 | 발주자가 직접구매 SW와 SI 사업자 간의 통합 조정 책임 부담 |

## Ⅳ. 상용SW 직접구매의 주요 한계점 및 해결 방안

- **SI 주사업자와 상용SW 공급자 간 책임 회피 및 인터페이스 갈등** :
  - **한계점** : 시스템 통합 단계에서 연계 오류나 성능 저하 발생 시 주사업자와 분리발주 상용SW 기업 간 귀책 공방으로 프로젝트 일정 지연.
  - **해결 방안** : 발주 단계에서 주사업자의 통합 관리 책임 범위 명문화, 상용SW 공급자의 현장 기술지원 및 통합 테스트 참여 의무(SLA) 계약 체결.
- **분리발주 증가에 따른 발주기관의 사업 관리 오버헤드 폭증** :
  - **한계점** : 다수의 개별 SW 계약, 검수, 대가 지급을 공공기관 실무자가 직접 처리해야 하므로 행정적 부담 급증 및 일정 조율 실패.
  - **해결 방안** : PMO(전자정부사업관리자)의 분리발주 관리 지원 기능 강화, 디지털서비스 전문계약제도 및 종합쇼핑몰 조달 활성화를 통한 계약 절차 간소화.
- **상용SW 간 비표준 연계로 인한 아키텍처 종속 및 유지보수 비용 증가** :
  - **한계점** : 각 상용 패키지가 독자적인 데이터 모델과 프로토콜을 사용하여 커스터마이징이 과도해지고 차기 업그레이드 불가 상태 초래.
  - **해결 방안** : 전자정부 표준프레임워크 및 Open API 표준 인터페이스 준수 의무화, 제품 원형(Out-of-the-Box) 기능 중심의 요구사항 정의(Customizing 최소화).

## Ⅴ. 공공 SW 생태계 상생을 위한 기술사적 제언

- **SI 주사업자의 '소프트웨어 통합비용(SW Integration Fee)' 정당 반영** : 발주기관이 직접구매한 상용SW를 SI 사업자가 연동하고 전체 시스템에 통합하는 과정에서 발생하는 개발 공수와 기술적 인터페이스 책임을 인정하여, 사업 예산에 'SW 커스터마이징 및 통합비용'을 공식적으로 책정·지급해야 함.
- **클라우드 서비스(SaaS) 직접구매로의 제도적 확장** : 과거 설치형 패키지 소프트웨어 중심의 직접구매 기준을 클라우드 전환 환경에 맞추어, 디지털서비스 전문계약제도를 통해 공공 검증된 클라우드 SaaS 서비스를 직접 수의계약·구독할 수 있도록 구매 절차의 패러다임 전환 가속화 필요.
