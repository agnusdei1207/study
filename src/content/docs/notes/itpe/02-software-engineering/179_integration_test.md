## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 테스팅·품질 → 통합 테스트(Integration Test)

## 지식 위치

소프트웨어공학 > 시험 수준 > 통합 테스트

## 30초 인출

- 본질: 단위 테스트를 통과한 개별 모듈이나 컴포넌트들을 결합하여 모듈 간의 인터페이스, 통신 규약, 데이터 교환 무결성을 검증하는 소프트웨어 테스트 레벨
- 메커니즘: 점진적 결합 전략(하향식/상향식/샌드위치) 또는 비점진적 결합(빅뱅) 선택 → 테스트 대역(드라이버/스텁) 구성 → 인터페이스 데이터 파라미터 및 예외 처리 검증 → 회귀 테스트 수행
- 통찰: 단위 테스트 통과가 컴포넌트 간 프로토콜 호환성을 보증하지 않으므로 MSA 환경에서는 Mock 기반 계약 테스트(Pact)와 Testcontainers 기반의 격리 인프라 통합 검증 병행 필요

<details>
<summary>핵심 용어</summary>

- **통합 테스트 (Integration Test)** : 소프트웨어 모듈 간의 인터페이스 결함과 상호작용의 올바름을 검증하는 V-모델 상의 테스트 단계
- **테스트 드라이버 (Test Driver)** : 상향식 통합에서 아직 구현되지 않은 상위 호출 모듈을 대신하여 하위 모듈에 테스트 데이터를 전달하고 결과를 수신하는 시험용 소프트웨어
- **테스트 스텁 (Test Stub)** : 하향식 통합에서 아직 개발되지 않은 하위 피호출 모듈을 대신하여 상위 모듈의 호출에 고정된 가상 응답을 반환하는 대역 객체
- **하향식 통합 (Top-Down)** : 메인 제어 루틴에서 시작하여 하위 모듈로 내려가며 스텁(Stub)을 이용해 결합하는 점진적 통합 방식
- **상향식 통합 (Bottom-Up)** : 가장 하위의 기본 모듈(드라이버 이용)부터 클러스터 단위로 묶어 상위로 올라가는 점진적 통합 방식
- **계약 테스트 (Contract Testing)** : 서비스 간 API 요청/응답 스키마와 동작 규약을 사전에 정의하고 제공자와 소비자 간의 계약 준수 여부를 검증하는 기법
</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 통합 테스트(Integration Test)의 필요성을 설명하고, 점진적 통합 방식(하향식, 상향식, 샌드위치)과 비점진적(빅뱅) 방식의 비교 및 클라우드 마이크로서비스 환경에서의 최신 통합 검증 전략을 제시하시오. (25점)

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 개별적으로 검증된 소프트웨어 단위 모듈들을 결합하는 과정에서 발생하는 인터페이스 불일치, 데이터 포맷 오류, 통신 프로토콜 결함 및 타이밍 이슈를 검증하는 테스트 단계 |
| 목적 | 단위 모듈 간 상호작용 오류 조기 발견, 서브시스템 간 데이터 흐름의 정합성 입증, V-모델 설계 단계(상세설계/기본설계) 요구사항 충족성 검증 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 인터페이스 결함 집중 | 모듈 내부 로직보다는 파라미터 개수/타입 불일치, 반환값 형식, 전역 변수 공유 부작용 검출에 집중 |
| 테스트 대역(Test Double) 활용 | 미완성 모듈의 의존성을 격리하고 독립적 테스트를 수행하기 위해 드라이버(Driver)와 스텁(Stub)을 능동적 제작 |
| 점진적 결합을 통한 결함 격리 | 한 번에 하나씩 모듈을 추가 결합함으로써 결함 발생 시 원인 모듈을 즉시 특정 가능 |
| 결합 단계별 회귀 검증 | 신규 모듈이 추가될 때마다 기존 결합된 모듈들의 정상 동작을 보장하기 위한 회귀 테스트(Regression Test) 필수 수반 |

단위 테스트와 시스템 테스트 사이의 거대한 간극을 메우고 아키텍처의 통합 안정성을 담보하는 핵심 검증 단계.

## Ⅲ. 체계·프로세스

```text
[통합 테스트 실행 아키텍처 및 대역 구조]

    ┌─────────────────────────────────────────┐
    │     [하향식 통합: Top-Down Approach]     │
    │          최상위 제어 모듈 (M1)          │
    │         ┌───────────┴───────────┐       │
    │      모듈 M2                 모듈 M3     │
    │   ┌─────┴─────┐                 │       │
    │ 스텁 S1     스텁 S2           스텁 S3   │ ──► 하위 미완성 모듈을 Test Stub으로 대체
    └─────────────────────────────────────────┘

    ┌─────────────────────────────────────────┐
    │     [상향식 통합: Bottom-Up Approach]   │
    │        테스트 드라이버 (Test Driver)    │ ──► 상위 미완성 호출자를 Driver로 대체
    │         ┌───────────┴───────────┐       │
    │     빌드/클러스터 A          빌드/클러스터 B  │
    │   ┌─────┴─────┐                 │       │
    │ 하위모듈 D1  하위모듈 D2      하위모듈 D3│
    └─────────────────────────────────────────┘
```

상위 제어 로직 중심의 하향식과 하위 데이터 처리 중심의 상향식으로 분기하여 테스트 대역을 통해 점진적으로 조립하는 프로세스.

## Ⅳ. 종류·비교

| 비교 항목 | 빅뱅 통합 (Big-Bang) | 하향식 통합 (Top-Down) | 상향식 통합 (Bottom-Up) | 샌드위치 통합 (Sandwich) |
|---|---|---|---|---|
| **결합 방식** | 모든 모듈을 일시에 결합 (비점진적) | 상위 제어 모듈부터 하향식 결합 | 하위 기본 모듈부터 상향식 결합 | 상위 하향식 + 하위 상향식 절충 |
| **필요 도구** | 별도 드라이버/스텁 불필요 | **테스트 스텁 (Test Stub)** | **테스트 드라이버 (Test Driver)** | 스텁과 드라이버 모두 필요 |
| **결함 격리** | **매우 곤란** (원인 추적 극난) | 용이 (추가된 하위 모듈에 원인) | 용이 (추가된 상위 모듈에 원인) | 비교적 용이 (중간 계층 집중) |
| **장점** | 소규모 프로젝트 시 테스트 공수 절감 | 시스템 뼈대 조기 확인, 중요 결함 조기 발견 | 하위 모듈의 철저한 입출력 검증 가능 | 대규모 프로젝트의 병렬 테스트 가능 |
| **단점** | 결함 폭증 시 일정 지연, 위험성 최고 | 수많은 정교한 스텁 개발 비용 소요 | 상위 UI 및 제어 흐름 검증 지연 | 관리 복잡도 및 테스트 비용 증가 |

### 현대적 분산 환경(MSA)에서의 통합 테스트 기법 비교

| 검증 기법 | 핵심 개념 및 도구 | 주요 장점 | 한계 및 고려사항 |
|---|---|---|---|
| **소비자 주도 계약 테스트 (CDC)** | Pact 도구를 활용하여 API 스펙과 기대 응답을 계약(Contract)으로 검증 | 외부 서버 기동 없이 CI 파이프라인에서 초고속 검증 | 네트워크 지연이나 DB 실제 트랜잭션 검증 불가 |
| **컨테이너 기반 통합 테스트** | Testcontainers를 사용하여 실제 DB, Kafka를 Docker로 즉시 띄워 테스트 | 실제 프로덕션과 100% 동일한 격리 인프라 검증 | Docker 데몬 구동 오버헤드로 테스트 실행 시간 증가 |
| **서비스 가상화 (Service Virtualization)** | WireMock 등을 통해 서드파티 결제사 등의 응답을 정밀 모킹 | 외부 의존성 비용 없이 다양한 에러 상황 재현 | 모킹 설정 오류 시 실제 운영 환경과의 괴리 위험 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 대규모 시스템에서 스텁과 드라이버의 작성 및 유지보수 비용이 실제 개발 비용 초과 | OpenAPI Specification 기반 모의 서버(Prism) 자동 생성 도구 및 프레임워크 Mockito 활용 |
| 통합 테스트 단계에서 데이터베이스 공유로 인한 테스트 간 격리 실패 및 데이터 오염 | 개별 테스트 실행 전 DB 트랜잭션 롤백 처리 또는 Testcontainers 기반 인메모리/임시 컨테이너 격리 |
| 외부 연계 기관(결제사, 공공기관)의 테스트베드 불안정으로 인한 테스트 파이프라인 블로킹 | 네트워크 레벨 모킹 도구(WireMock)를 도입하여 4xx, 5xx 타임아웃 예외 상황을 완벽 가상화 |

## Ⅵ. 제언

클라우드 네이티브 MSA 환경에서는 마틴 파울러의 테스트 피라미드 원칙에 따라 무거운 E2E 통합 테스트를 경량화하고, 계약 테스트(Pact)와 격리 컨테이너 테스트를 결합한 자동화 파이프라인 확립 권장.

```text
[현대적 지속적 통합 테스트(CI) 파이프라인]
  단위 테스트 (JUnit) → 계약 테스트 (Pact CDC) → 컨테이너 통합 테스트 (Testcontainers) → 스테이징 카나리 검증
```

| 검증 단계 | 전통적 통합 테스트 | 현대적 클라우드 네이티브 통합 테스트 |
|---|---|---|
| 환경 구성 | 수동으로 구성된 공용 QA 서버 환경 | Docker/Kubernetes 기반 동적 에페머럴(Ephemeral) 환경 |
| 검증 속도 | 일 단위의 긴 배포 및 회귀 시험 | CI 파이프라인 내 수 분 이내의 자동화된 피드백 루프 |
