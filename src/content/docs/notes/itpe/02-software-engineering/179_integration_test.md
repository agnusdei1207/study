## 연관 키워드

- 통합 테스트, 테스트 더블, 스텁, 드라이버, 계약 테스트, 결함 격리

## Ⅰ. 통합 테스트의 개요

- 핵심 요약 : 통합 테스트는 모듈·서비스 간 인터페이스와 데이터 교환이 설계대로 동작하는지 확인.
- 개념 : **통합 테스트**(Integration Testing)는 개별 단위 검증 후 구성요소를 연결해 호출·응답·상태 전달과 상호작용 결함을 검증하는 테스트 수준.
- 배경 및 필요성 : 단위 테스트가 각 모듈 내부 동작을 확인해도 계약 불일치, 순서 의존, 연계 설정 오류는 남을 수 있음.
- 주요 목적 : 구성요소 경계의 결함을 조기에 발견하고 시스템 수준 검증의 기반 마련.

## Ⅱ. 특징 및 장점

- 핵심 요약 : 실제 인터페이스와 연계 순서를 중심으로 통신·계약·데이터 정합성을 검증.
- 경계 검증 : 요청·응답 형식과 오류 의미 확인 → 연계 결함 조기 발견.
- 환경 의존성 검증 : DB·메시지 브로커·외부 API 연결 확인 → 배포 설정 문제 탐지.
- 단계별 조립 : 상향식·하향식으로 결합 → 결함 위치를 제한적으로 추적.
- 계약 테스트 : 제공자·소비자 기대 계약 검증 → 독립 배포 서비스 간 호환성 유지.

## Ⅲ. 통합 방식과 흐름

- 핵심 요약 : 통합 순서에 따라 테스트 더블을 사용하고 실제 구성요소로 대체하며 인터페이스 결함을 추적.

```text
하향식: 상위 모듈 → 하위 모듈
             하위 대역은 스텁
상향식: 하위 모듈 → 상위 모듈
             호출자는 드라이버
```

```text
모듈 단위 검증
  ↓ 인터페이스 계약 확인
단계별 통합·연계 실행
  ↓ 결함 격리 및 수정
전체 통합 회귀 확인
```

- 빅뱅 통합은 모든 모듈을 한꺼번에 결합하므로 통합 시점이 늦고 결함 원인 격리가 어렵다는 점을 고려.

## Ⅳ. 통합 전략 비교

- 핵심 요약 : 의존 방향·위험·테스트 가능성에 따라 통합 순서를 선택.

| 비교 축 | 하향식 | 상향식 | 빅뱅 |
| --- | --- | --- | --- |
| 시작점 | 상위 제어 모듈 | 하위 서비스·유틸리티 | 모든 모듈 동시 |
| 테스트 더블 | 하위 모듈 스텁 | 상위 호출 드라이버 | 초기에는 적음 |
| 조기 확인 | 상위 흐름·화면 | 하위 공통 기능 | 늦은 전체 결합 |
| 위험 | 하위 상세 검증 지연 | 사용자 흐름 검증 지연 | 결함 격리 어려움 |

## Ⅴ. 한계와 방안

- 핵심 요약 : 테스트 더블과 통합 환경의 차이, 비결정성, 외부 의존성 불안정성을 통제.

| 한계 | 원인·영향 | 대응 방안 |
| --- | --- | --- |
| 스텁과 실제 동작 차이 | 모사한 계약이 오래되거나 단순 | 계약 테스트·실제 연계 테스트 병행 |
| 외부 시스템 변동 | 속도 제한·장애·데이터 변화 | 격리된 테스트 환경과 소비자 계약 활용 |
| 비결정적 실패 | 공유 상태·시간·순서 의존 | 데이터 격리·고정 시계·재시도 원인 관리 |
| 결함 위치 파악 지연 | 너무 많은 모듈을 한 번에 통합 | 위험 기반 점진 통합과 로그·추적ID |

## Ⅵ. 테스트 전략 제언

- 핵심 요약 : 팀은 변경 위험이 큰 경계부터 자동화하고 단위·통합·계약 테스트의 책임을 분리.
- 서비스 소유자는 API 스키마, 이벤트 호환성, DB 마이그레이션을 배포 전 검증 항목으로 지정.
- 파이프라인은 빠른 테스트를 자주 실행하고 실제 인프라 연계 검증은 격리·정리 절차가 확보된 환경에서 수행.

## Ⅶ. 결론

- 핵심 요약 : 통합 테스트는 구성요소 사이의 계약과 상호작용 결함을 찾는 필수 테스트 수준.
- 적절한 통합 순서와 계약 기반 검증이 시스템 조립 위험을 줄이는 핵심.
