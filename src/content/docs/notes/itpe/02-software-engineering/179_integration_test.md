## 연관 키워드

- 통합 테스트(Integration Test), 빅뱅 통합(Big-Bang), 하향식 통합(Top-Down), 상향식 통합(Bottom-Up)
- 테스트 스텁(Stub), 테스트 드라이버(Driver), 소비자 주도 계약 테스트(CDC), Testcontainers

## Ⅰ. 통합 테스트의 개요

- 핵심 요약 : 단위 테스트 통과 모듈의 결합 접점에서 발생하는 인터페이스·데이터·통신 결함의 검증 단계.
- 개념 : 통합 테스트(Integration Test)란 단위 테스트(Unit Test)를 통과한 개별 소프트웨어 모듈, 컴포넌트 또는 마이크로서비스들을 서로 결합하여 통합하는 과정에서 발생하는 인터페이스 불일치, 데이터 교환 오류, 통신 프로토콜 장애를 식별하고 검증하는 소프트웨어 테스팅 단계.
- 배경 및 필요성 : 각 모듈의 독립 동작 완벽성과 무관하게 모듈 결합 접점(Interface)에서 매개변수 타입 불일치, 데이터 포맷 오해, 동기화 타이밍 결함의 집중 발생.
- 주요 목적 : V-모델의 상세 설계(Detailed Design) 단계와의 1:1 대응을 통한 인터페이스 정합성 검증.

## Ⅱ. 통합 테스트의 특징

- 핵심 요약 : 결합 순서와 보조 도구(스텁·드라이버)가 테스트 효율을 결정하는 점진적 검증 단계.

1. 빅뱅(Big-Bang), 하향식(Top-Down), 상향식(Bottom-Up), 샌드위치(Sandwich)의 4대 통합 전략.
2. 하향식 통합의 미개발 하위 모듈 대체 테스트 스텁(Stub) 사용.
3. 상향식 통합의 미개발 상위 제어 모듈 대체 테스트 드라이버(Driver) 사용.
4. 모듈 결합 시점마다의 조기 결함 위치 파악(빅뱅 방식 제외).
5. V-모델에서 상세 설계 단계와의 1:1 검증 대응.
6. 외부 DB(Database)·API(Application Programming Interface) 종속성 관리의 중요성.

## Ⅲ. 통합 테스트의 구조 (흐름)

- 핵심 요약 : 통합 순서와 보조 도구 사용 여부로 구분되는 4대 접근 전략.
- 4대 통합 테스트 접근 전략.

```text
[ 1. 빅뱅 통합 (Big-Bang) ]
  - 전 모듈 일괄 결합 (결함 격리 난해)

[ 2. 하향식 통합 (Top-Down) ]
  - 상위 제어 모듈부터 결합
  [ Main ] ──> [ Stub A ] / [ Stub B ]

[ 3. 상향식 통합 (Bottom-Up) ]
  - 최하위 단위 모듈부터 결합
  [ Driver ] ──> [ 하위 모듈 C / D ]

[ 4. 샌드위치 통합 (Sandwich) ]
  - 상향식 + 하향식 결합,
    중간 핵심 계층 중심 동시 통합
```

- 테스트 스텁(Stub) : 하향식 통합 시 아직 개발되지 않은 하위 모듈의 역할을 흉내 내어 고정된 값을 반환해 주는 가짜 임시 프로그램.
- 테스트 드라이버(Driver) : 상향식 통합 시 아직 개발되지 않은 상위 제어 모듈을 대신하여 하위 모듈에 입력을 전달하고 출력을 확인하는 가짜 호출 프로그램.

## Ⅳ. 하향식·상향식·빅뱅 통합 테스트의 비교

- 핵심 요약 : 통합 방식에 따른 결함 격리 용이성과 보조 도구 비용의 상반된 특성.
- V-모델에서의 테스트 레벨 대응 관계.

```text
[ 개발 단계 ]                [ 테스트 레벨 ]
 요구사항 분석  ◀──1:1 대응──▶  인수 테스트
 시스템 설계    ◀──1:1 대응──▶  시스템 테스트
 상세 설계      ◀──1:1 대응──▶  통합 테스트 ◀ 본 주제
 코딩·구현      ◀──1:1 대응──▶  단위 테스트
```

| 비교 항목 | 빅뱅 통합 (Big-Bang) | 하향식 통합 (Top-Down) | 상향식 통합 (Bottom-Up) |
|---|---|---|---|
| 통합 방식 | 전 모듈 일괄 결합 후 일시 검증 | 최상위 메인 모듈부터 하향식 점진 통합 | 최하위 기능 모듈부터 상향식 점진 통합 |
| 결함 위치 파악 | 극도로 난해 (원인 모듈 특정 불가) | 모듈 결합 시마다 즉시 특정 가능 | 즉시 특정 가능 |
| 필요 보조 도구 | 없음 | 테스트 스텁(Stub) 다수 작성 필요 | 테스트 드라이버(Driver) 다수 작성 필요 |
| 주요 장점 | 소규모 시스템에서의 빠른 수행 | 시스템 전반 제어 흐름과 UI(User Interface)의 조기 검증 | 하위 핵심 알고리즘·데이터 처리의 조기 검증 |
| 주요 단점 | 디버깅 비용 폭증, 결함 격리 실패 | 하위 모듈 정밀 계산 검증의 지연 | 상위 제어 흐름 검증의 후반부 지연 |

## Ⅴ. 통합 테스트의 장점과 한계

- 핵심 요약 : 인터페이스 결함 조기 발견의 장점, 외부 종속 불안정·E2E 비용·데이터 격리 측면의 한계.
- 장점
  1. 모듈 결합 접점의 인터페이스·데이터·프로토콜 결함 조기 발견.
  2. 통합 전략 선택을 통한 검증 우선순위의 유연한 설계.
  3. 시스템 완성 전 컴포넌트 간 상호작용 품질 확보.
- 한계점 1 : 외부 종속 서비스인 DB(Database)와 서드파티 API(Application Programming Interface) 환경 구성의 복잡도 및 불안정성
  - 한계점 : 테스트 실행 시 외부 결제 게이트웨이나 공유 DB 서버의 일시적 장애로 인한 실제 코드와 무관한 빈번한 테스트 실패(Flaky Test).
  - 해결 방안 : Testcontainers 기반 온디맨드 격리 도커 인프라 프로비저닝, WireMock 등을 통한 외부 API의 신뢰성 높은 모의 서버(Mocking) 구축.
- 한계점 2 : 마이크로서비스 확산에 따른 엔드투엔드 통합 테스트 실행 시간 폭증
  - 한계점 : 수십 개 서비스 간 상호작용 통합 검증을 위한 전용 스테이징 환경 기동·테스트의 수십 분 이상 소요와 배포 병목 유발.
  - 해결 방안 : 소비자 주도 계약 테스트(Pact) 도입을 통한 무거운 E2E(End-to-End) 통합 테스트의 경량 단위·인터페이스 계약 검증으로 시프트 레프트(Shift-Left).
- 한계점 3 : 테스트 데이터 격리 실패로 인한 병렬 실행 불가
  - 한계점 : 다수 통합 테스트의 동일 DB 테이블 동시 수정에 따른 데이터 경합과 레이스 컨디션 발생, 병렬 테스트 파이프라인 구성 불가.
  - 해결 방안 : 테스트 케이스별 독립 테넌트 ID(Identifier)·스키마 분리, @Transactional 롤백 격리 및 인메모리 임베디드 저장소의 적극 활용.

## Ⅵ. 현대 마이크로서비스 환경에서의 기술사적 제언

- 핵심 요약 : API 가상화·컨테이너 기반 격리 테스트와 계약 테스트 기반 CI 자동 검증의 도입.
- Mock 서버 및 Testcontainers 활용 격리 통합 테스트 : 외부 결제 PG(Payment Gateway)사·서드파티 API 의존 통합 테스트의 비용·네트워크 불안정성을 감안하여, WireMock 기반 API 가상화와 Docker 기반 Testcontainers로 실제 DB(PostgreSQL/Redis) 인스턴스를 컨테이너로 구동하는 격리 검증 아키텍처 수립.
- 소비자 주도 계약 테스팅(CDC, Consumer-Driven Contract Testing) : 여러 팀이 분산 개발하는 MSA(Microservice Architecture) 환경의 API 인터페이스 파손 방지를 위해, Pact 프레임워크로 API 소비자가 기대하는 요청·응답 규약을 사전 정의하고 제공자의 CI(Continuous Integration) 파이프라인에서의 자동 검증 강제.

## Ⅶ. 결론

- 핵심 요약 : 통합 테스트는 결합 접점 품질 보장의 핵심 단계이자 격리·계약 기반 기법으로 진화 중.
- 요약 : 스텁·드라이버 기반 전통 4대 전략의 이해와 Mock·계약 테스트 도입의 병행 필요.
- 시사점 : 격리성 확보와 파이프라인 자동화가 MSA 시대 통합 테스트 성숙도의 관건.
