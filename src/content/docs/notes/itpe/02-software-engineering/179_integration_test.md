## 연관 키워드

- 통합 테스트(Integration Test), 빅뱅 통합(Big-Bang), 하향식 통합(Top-Down), 상향식 통합(Bottom-Up), 샌드위치 통합(Sandwich)
- 테스트 스텁(Stub), 테스트 드라이버(Driver), 소비자 주도 계약 테스트(CDC), Testcontainers, V-모델

## Ⅰ. 통합 테스트의 개요

- 핵심 요약 : 단위 테스트를 통과한 모듈의 결합 접점에서 생기는 인터페이스·데이터·통신 결함을 검증하는 단계.
- 개념 : 개별 모듈이나 컴포넌트, 마이크로서비스를 결합한 뒤 인터페이스 불일치, 데이터 교환 오류, 통신 장애를 찾아내는 단계인 **통합 테스트** (Integration Test).
- 배경 및 필요성 : 모듈이 단독으로는 정상이어도 결합 접점에서 매개변수 타입 불일치, 데이터 포맷 해석 차이, 호출 타이밍 문제가 집중적으로 발생하므로 별도 검증 필요.
- 주요 목적 : 결합 접점의 인터페이스 정합성을 확보하고, **V-모델** (V-Model)에서 상세 설계 단계와 대응하는 검증 수준 확보.

## Ⅱ. 통합 테스트의 특징 및 장점

- 핵심 요약 : 결합 순서와 보조 도구 선택이 결함 격리 효율을 결정하는 점진적 검증 단계.

1. 결합 전략 4종 : **빅뱅 통합** (전 모듈을 한꺼번에 결합해 검증), **하향식 통합** (상위 제어 모듈부터 하위로 점진 결합), **상향식 통합** (하위 핵심 모듈부터 상위로 점진 결합), **샌드위치 통합** (상위와 하위를 병행해 중간 계층으로 모음) → 시스템 규모와 개발 순서에 맞춘 전략 선택 가능.
2. 점진적 결합 검증 : 모듈을 단계적으로 붙이며 매번 검증 → 결함 위치가 마지막 결합 지점 근처로 좁혀져 원인 추적 비용 감소.
3. 하향식의 보조 도구 : 아직 개발되지 않은 하위 모듈을 **테스트 스텁** (Stub, 고정 값을 돌려주는 가짜 하위 모듈) 으로 대체 → 상위 제어 흐름을 조기 검증.
4. 상향식의 보조 도구 : 아직 개발되지 않은 상위 모듈을 **테스트 드라이버** (Driver, 하위 모듈에 입력을 주고 출력을 확인하는 가짜 호출 프로그램) 로 대체 → 하위 핵심 로직을 조기 검증.
5. 외부 의존 관리 : 외부 DB(Database)·API(Application Programming Interface) 연결이 검증 환경의 불안정 요인이 되므로 격리 방식을 함께 설계 → 검증 결과의 재현성 확보.

## Ⅲ. 통합 테스트의 구조 (흐름)

- 핵심 요약 : 통합 순서와 보조 도구의 방향으로 구분되는 4대 접근 전략.
- 테스트 스텁 : 하향식 통합에서 아직 없는 하위 모듈을 흉내 내어 고정된 값을 돌려주는 임시 프로그램.
- 테스트 드라이버 : 상향식 통합에서 아직 없는 상위 제어 모듈을 대신해 하위 모듈을 호출하고 결과를 확인하는 임시 프로그램.

```text
[ 하향식 통합 (Top-Down) ]

Main 제어 모듈
      ↓ 호출
Stub A      Stub B
(하위 대체) (하위 대체)
```

```text
[ 상향식 통합 (Bottom-Up) ]

Driver (상위 대체)
      ↓ 입력 전달
하위 모듈 C → 하위 모듈 D
      ↓ 결합 후 상위 모듈로 교체
```

```text
[ 샌드위치 통합 (Sandwich) ]

상위 계층 : 하향식 (Stub 사용)
      ↓
중간 핵심 계층 : 동시 통합
      ↑
하위 계층 : 상향식 (Driver 사용)
```

## Ⅳ. 빅뱅·하향식·상향식·샌드위치 통합의 비교

- 핵심 요약 : 결함 격리 용이성과 보조 도구 비용이 상반되는 방식 간 선택 기준.

| 비교 항목 | 빅뱅 통합 | 하향식 통합 | 상향식 통합 | 샌드위치 통합 |
| --- | --- | --- | --- | --- |
| 결합 순서 | 전 모듈 일괄 결합 후 일시 검증 | 최상위 제어 모듈부터 하향 점진 결합 | 최하위 핵심 모듈부터 상향 점진 결합 | 상위와 하위를 병행해 중간 계층으로 결합 |
| 결함 위치 파악 | 매우 어려움 (원인 모듈 특정 곤란) | 결합 시마다 즉시 특정 가능 | 결합 시마다 즉시 특정 가능 | 계층 단위로 특정 가능 |
| 필요 보조 도구 | 없음 | 테스트 스텁 다수 | 테스트 드라이버 다수 | 계층별 스텁·드라이버 혼용 |
| 주요 장점 | 소규모 시스템에서 준비 비용이 낮음 | 제어 흐름과 사용자 화면의 조기 검증 | 하위 핵심 로직과 데이터 처리의 조기 검증 | 상·하위 동시 검증으로 일정 단축 |
| 주요 단점 | 디버깅 비용 증가, 결함 격리 실패 | 하위 모듈 정밀 검증의 지연 | 상위 제어 흐름 검증의 후반부 지연 | 보조 도구 관리가 복잡 |

```text
[ 개발 단계 ]      [ 테스트 레벨 ]
요구사항 분석  ↔  인수 테스트
      ↓
시스템 설계    ↔  시스템 테스트
      ↓
상세 설계      ↔  통합 테스트
      ↓
코딩·구현      ↔  단위 테스트
```

## Ⅴ. 통합 테스트의 한계와 방안

- 핵심 요약 : 인터페이스 결함의 조기 발견이라는 장점과 외부 의존 불안정, E2E 비용, 데이터 경합이라는 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 외부 의존 불안정 | 외부 결제 API나 공유 DB의 일시 장애로 코드와 무관한 **플레이키 테스트** (Flaky Test) 빈발 | **Testcontainers** (테스트 실행 시 도커 컨테이너를 띄우고 폐기하는 라이브러리)로 격리 인프라 구성, 외부 API는 WireMock 모의 서버로 대체 | 외부 원인 실패 비율 |
| E2E 실행 시간 증가 | 마이크로서비스 확산으로 E2E(End-to-End) 통합 테스트 실행 시간이 길어져 배포 병목 발생 | **소비자 주도 계약 테스트** (CDC, Consumer-Driven Contract Testing)로 API 계약을 단위 수준에서 검증 → 시프트 레프트(Shift-Left) | 파이프라인 전체 소요 시간 |
| 데이터 경합 | 여러 통합 테스트가 같은 DB 테이블을 동시에 수정해 레이스 컨디션 발생, 병렬 실행 불가 | 테스트 케이스별 테넌트 ID와 스키마 분리, 트랜잭션 롤백 격리, 인메모리 DB 활용 | 테스트 간 데이터 충돌 건수 |

## Ⅵ. 현대 마이크로서비스 환경에서의 기술사적 제언

- 핵심 요약 : 격리 테스트 환경을 공통 인프라로 제공하고, 계약 테스트를 CI(Continuous Integration) 파이프라인의 상시 관문으로 정착시켜야 함.
- 테스트 환경은 팀마다 따로 구축하지 않고, 플랫폼 조직이 컨테이너 기반 테스트 인프라와 API 가상화 자산을 공통으로 제공하는 방향이 바람직함.
- 마이크로서비스 아키텍처(MSA, Microservice Architecture)에서는 팀 간 API 계약을 공유 자산으로 등록해 버전과 변경 이력을 함께 관리하고, 계약 검증에 실패하면 배포를 막는 규칙을 두는 거버넌스 필요.
- 테스트 데이터의 생성과 정리를 CI 공통 절차로 표준화하면 병렬 실행 범위가 넓어져 파이프라인 대기 시간을 줄일 수 있음.

## Ⅶ. 결론

- 핵심 요약 : 통합 테스트는 결합 접점 품질을 보증하는 핵심 단계이며, 스텁·드라이버 기반 전통 전략과 격리·계약 기법을 병행하는 방향으로 진화 중.
- 전통 4대 전략의 원리를 이해한 위에 격리·계약 기법을 얹는 것이 MSA 시대 통합 품질의 기반이 됨.
