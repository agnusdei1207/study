## Ⅰ. MSA(마이크로서비스 아키텍처)의 개요

- 개념 : 단일의 거대한 애플리케이션(Monolithic)을 **비즈니스 도메인 경계** (Bounded Context)에 따라 작고 독립적으로 배포 및 확장이 가능한 복수의 독립 서비스들로 분할하고, **경량 프로토콜** (REST(Representational State Transfer), gRPC, 메시지 브로커)로 통신하는 분산 아키텍처 스타일 (MSA, Microservice Architecture).
- 배경 및 필요성 : 시스템 규모 확대에 따른 모놀리식 아키텍처의 빌드/배포 시간 급증, 코드 변경 시 전체 시스템 장애 파급 리스크, 조직 확장에 따른 협업 병목 현상 타개.
- 핵심 원칙 : **도메인 주도 설계** (DDD, Domain-Driven Design), **서비스별 독립 데이터베이스** (Database per Service), 폴리글랏 프로그래밍, 분산 거버넌스.

## Ⅱ. MSA 핵심 생태계 구성요소 및 연동 구조

```text
   [ 클라이언트 (Web/Mobile) ]
              │
              ▼
   ┌────────────────────────────────────────────────────────┐
   │ [ API Gateway ] - 라우팅, 인증/인가, Rate Limiting     │
   └──────────┬───────────────────────────────┬─────────────┘
              │ (REST / gRPC)                 │
              ▼                               ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  [ 주문 서비스 ]     │        │  [ 결제 서비스 ]     │
   │  ┌────────────────┐  │        │  ┌────────────────┐  │
   │  │ 주문 DB        │  │        │  │ 결제 DB        │  │
   │  └────────────────┘  │        │  └────────────────┘  │
   └──────────┬───────────┘        └──────────▲───────────┘
              │                               │
              └─────> [ Event Broker ] ───────┘
                      (Kafka: 최종 일관성)
```

- **API(Application Programming Interface) Gateway** : 클라이언트 단일 진입점, 요청 라우팅, **크로스 커팅 관심사** (보안, SSL(Secure Sockets Layer), 캐싱) 처리.
- **Service Mesh (Istio)** : **사이드카 프록시** 기반의 서비스 간 통신(mTLS), 트래픽 라우팅, 서킷 브레이커.
- **비동기 이벤트 기반 통신** : 데이터 일관성 유지를 위해 Kafka/RabbitMQ 기반의 **Saga 패턴** 적용.
- **분산 추적 (Distributed Tracing)** : Jaeger, Zipkin을 활용하여 마이크로서비스 간 트랜잭션 추적성 확보.

## Ⅲ. 모놀리식 아키텍처와 MSA의 비교

| 비교 항목 | **모놀리식 아키텍처** (Monolithic) | 마이크로서비스 아키텍처 (MSA, Microservice Architecture) |
|---|---|---|
| 배포 독립성 | 전체 시스템 일괄 빌드 및 일괄 배포 | 개별 서비스 단위 무중단 독립 배포 가능 |
| 데이터베이스 | 단일 통합 DB (트랜잭션 **ACID**(Atomicity, Consistency, Isolation, Durability) 완벽 보장) | 서비스별 독립 DB (분산 트랜잭션, 최종 일관성) |
| 장애 격리 | 한 모듈의 메모리 누수가 전체 시스템 다운 유발 | 서킷 브레이커를 통해 특정 서비스 장애 격리 |
| 확장성 (Scale) | 전체 애플리케이션을 통째로 스케일아웃 | 트래픽 집중 서비스만 선택적 수평 확장 |
| 운영 복잡도 | 로컬 환경 디버깅 및 통합 테스트 용이 | 네트워크 지연, 서비스 디스커버리, 분산 모니터링 복잡 |

## Ⅳ. MSA의 주요 한계점 및 해결 방안

- 분산 트랜잭션 관리 부재로 인한 데이터 정합성 파손 :
  - 한계점 : 서비스별 독립 데이터베이스 분리로 인해 단일 DB 수준의 ACID 2PC(Two-Phase Commit) 트랜잭션 적용이 불가하여, 네트워크 장애나 부분 실패 시 데이터 불일치 발생.
  - 해결 방안 : 사가 패턴(Saga Pattern: 오케스트레이션/코레오그래피)과 보상 트랜잭션을 구현하고, 트랜잭셔널 아웃박스 패턴(Transactional Outbox Pattern) 및 메시지 큐(Kafka)를 결합하여 최종 일관성(Eventual Consistency) 달성.
- 분산 네트워크 호출에 따른 장애 전파 및 연쇄 다운(Cascading Failure) :
  - 한계점 : 단일 서비스의 응답 지연이나 장애가 해당 서비스를 호출하는 상위 서비스들로 전파되어 시스템 전체가 동반 다운되는 연쇄 장애 발생.
  - 해결 방안 : Resilience4j 기반의 서킷 브레이커(Circuit Breaker), 타임아웃, 벌크헤드(Bulkhead) 격리 패턴을 적용하고, 서비스 메시(Istio)의 트래픽 라우팅 및 폴백(Fallback) 메커니즘 구축.
- 서비스 간 관측 가능성(Observability) 확보의 난제 :
  - 한계점 : 단일 사용자 요청이 수십 개의 마이크로서비스를 넘나들며 처리되므로 어느 서비스 구간에서 병목이나 오류가 발생했는지 기존 단일 로그만으로 식별 불가.
  - 해결 방안 : OpenTelemetry 표준 기반의 분산 추적(Distributed Tracing) 인프라(Jaeger/Zipkin)를 구축하고, 유입 시 상관 ID(Trace/Span ID)를 발급하여 전 서비스 구간에 전파 로깅 체계 표준화.

## Ⅴ. MSA 전환 및 운영 시 기술사적 제언

- 섣부른 분할 지양 및 '모놀리스 퍼스트(Monolith First)' 검토 : 도메인 경계가 명확하지 않은 상태에서 섣부르게 MSA로 시작하면 분산 모놀리스(Distributed Monolith)의 재앙을 맞이하므로, 모듈러 모놀리스로 시작하여 성숙도에 따라 분할 권장.
- 분산 데이터 정합성을 위한 Saga 패턴 및 아웃박스 패턴(Transactional Outbox) 적용 : 2단계 커밋(2PC)은 가용성을 저해하므로, 보상 트랜잭션 기반의 오케스트레이션/코레오그래피 Saga 패턴과 이벤트 유실을 방지하는 트랜잭셔널 아웃박스 패턴 구축 필수.
