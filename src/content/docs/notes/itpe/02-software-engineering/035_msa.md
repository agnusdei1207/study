## 연관 키워드

- MSA(Microservice Architecture), 모놀리식(Monolithic), 도메인 주도 설계(DDD, Domain-Driven Design)
- API Gateway, 서비스 메시(Service Mesh), Saga 패턴, 서킷 브레이커(Circuit Breaker), 트랜잭셔널 아웃박스 패턴, 최종 일관성(Eventual Consistency)

## Ⅰ. MSA의 개요

- 핵심 요약 : 도메인 경계에 따라 독립 배포 가능한 복수의 서비스로 분할하고 경량 프로토콜로 통신하는 분산 아키텍처.
- 개념 : 단일한 거대 애플리케이션인 **모놀리식** (Monolithic)을 **경계 컨텍스트** (Bounded Context)에 따라 작고 독립적으로 배포·확장할 수 있는 서비스들로 나누고, REST(Representational State Transfer), gRPC, 메시지 브로커 같은 경량 프로토콜로 통신하는 **마이크로서비스 아키텍처** (MSA, Microservice Architecture).
- 배경 및 필요성 : 시스템 규모가 커지면서 모놀리식의 빌드·배포 시간이 늘고, 한 모듈의 변경이 전체 시스템 장애로 번지며, 조직이 커지면서 협업 병목이 생기는 문제를 풀 필요가 있음.
- 주요 목적 : 독립 배포와 장애 격리를 통한 가용성 확보, 트래픽이 몰리는 서비스의 선택적 수평 확장, 조직 간 협업 병목 해소.

## Ⅱ. MSA의 특징 및 장점

- 핵심 요약 : 도메인 분할, 서비스별 독립 데이터베이스, 경량 통신, 분산 거버넌스의 원칙이 독립 배포와 선택적 확장으로 이어지는 체계.

1. **도메인 주도 설계** (DDD, Domain-Driven Design) 기반 분할 : 비즈니스 도메인 경계별로 서비스를 나눔 → 팀과 서비스의 책임이 명확해짐.
2. 서비스별 독립 데이터베이스 : 서비스마다 자기 데이터를 소유하는 Database per Service 원칙 → 스키마 변경의 영향 범위가 한 서비스로 제한됨.
3. 경량 프로토콜 통신 : REST, gRPC, 메시지 브로커로 서비스 간 통신 → 느슨한 결합 유지.
4. 폴리글랏 프로그래밍(Polyglot Programming)과 분산 거버넌스 : 서비스마다 적합한 언어와 기술을 고를 수 있음 → 기술 선택의 유연성 확보.
5. 무중단 독립 배포와 선택적 수평 확장 : 서비스 단위로 배포하고 부하가 큰 서비스만 늘림 → 자원 효율과 배포 빈도 향상.

## Ⅲ. MSA의 구조 (흐름)

- 핵심 요약 : API Gateway가 단일 진입점을 맡고, 서비스별 독립 DB와 이벤트 브로커가 최종 일관성을 유지하는 구조.
- **API Gateway** (API(Application Programming Interface) Gateway) : 클라이언트의 단일 진입점으로 요청을 라우팅하고, 인증·인가, 속도 제한(Rate Limiting), SSL(Secure Sockets Layer) 종료, 캐싱 같은 횡단 관심사를 처리.
- **서비스 메시** (Service Mesh) : Istio 같은 사이드카 프록시로 서비스 간 통신을 제어하며, mTLS(mutual Transport Layer Security), 트래픽 라우팅, 서킷 브레이커를 담당.
- **Saga 패턴** : 여러 서비스에 걸친 업무를 단계별 로컬 트랜잭션으로 나누고, 실패 시 보상 트랜잭션으로 되돌리는 방식으로 데이터 정합성을 맞춤.
- **분산 추적** (Distributed Tracing) : Jaeger나 Zipkin으로 여러 서비스를 거치는 한 요청의 흐름을 추적.

```text
[ 클라이언트 (Web, Mobile) ]
   ↓
[ API Gateway ]
   ↓ REST, gRPC
[ 주문 서비스 ]        [ 결제 서비스 ]
[ 주문 DB ]            [ 결제 DB ]
   ↓ 이벤트 발행          ↓ 이벤트 발행
[ Event Broker (Kafka) ]
   ↓
최종 일관성 (Eventual Consistency)
```

```text
[ Saga 패턴 (오케스트레이션) 흐름 ]

주문 서비스 (오케스트레이터)
   ↓ 결제 요청
결제 서비스 ──성공──> 재고 서비스
   ↓ 실패
보상 트랜잭션 (주문 및 결제 취소)
```

## Ⅳ. 모놀리식 아키텍처와 MSA의 비교

- 핵심 요약 : 배포 독립성, 장애 격리, 확장성의 이점을 얻는 대신 데이터 정합성과 운영 복잡도를 감수하는 구조적 교환.

| 비교 항목 | 모놀리식 아키텍처 (Monolithic) | 마이크로서비스 아키텍처 (MSA) |
| --- | --- | --- |
| 배포 독립성 | 전체 시스템을 일괄 빌드·배포 | 개별 서비스 단위의 무중단 독립 배포 |
| 데이터베이스 | 단일 통합 DB로 ACID(Atomicity, Consistency, Isolation, Durability) 트랜잭션 보장 | 서비스별 독립 DB로 분산 트랜잭션과 최종 일관성 |
| 장애 격리 | 한 모듈의 메모리 누수가 전체 시스템 중단으로 번질 수 있음 | 서킷 브레이커로 특정 서비스 장애를 격리 |
| 확장성 | 애플리케이션 전체를 통째로 스케일 아웃 | 트래픽이 몰리는 서비스만 선택적으로 수평 확장 |
| 운영 복잡도 | 로컬 디버깅과 통합 테스트가 용이 | 네트워크 지연, 서비스 디스커버리, 분산 모니터링이 복잡 |

## Ⅴ. MSA의 한계와 방안

- 핵심 요약 : 분산 트랜잭션, 장애 전파, 관측 가능성의 세 한계를 보상 트랜잭션, 회복 탄력성 패턴, 분산 추적으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 분산 트랜잭션 부재에 따른 데이터 정합성 훼손 | 서비스별 DB 분리로 단일 DB 수준의 ACID 적용이 어렵고, 2단계 커밋(2PC, Two-Phase Commit)도 가용성을 떨어뜨려 부분 실패 시 불일치 발생 | 사가 패턴(Saga Pattern, 오케스트레이션 또는 코레오그래피)과 보상 트랜잭션을 구현하고, 트랜잭셔널 아웃박스 패턴(Transactional Outbox Pattern)과 메시지 큐를 결합해 최종 일관성 확보 | 보상 트랜잭션 실행 건수, 불일치 건수 |
| 연쇄 장애(Cascading Failure) | 한 서비스의 지연이나 장애가 호출하는 상위 서비스로 전파되어 시스템 전체가 동반 중단 | Resilience4j 같은 라이브러리의 서킷 브레이커, 타임아웃, 벌크헤드(Bulkhead) 격리 패턴을 적용하고, 서비스 메시의 폴백(Fallback) 메커니즘 구축 | 서킷 오픈 빈도, 장애 전파 범위 |
| 관측 가능성(Observability) 확보의 어려움 | 한 요청이 수십 개 서비스를 거치므로 단일 로그만으로는 병목과 오류 구간을 식별하기 어려움 | OpenTelemetry 표준 기반의 분산 추적(Jaeger, Zipkin)을 구축하고, 유입 시 추적 ID(Trace ID)를 발급해 전 서비스 구간에 전파 | 평균 장애 원인 분석 시간 |

## Ⅵ. MSA 전환 및 운영을 위한 기술사적 제언

- 핵심 요약 : 모놀리스로 시작해 도메인 경계가 검증된 뒤 나누고, 분산 정합성 패턴과 관측 가능성을 처음부터 갖추는 점진적 전환이 필요.

1. 모놀리스 퍼스트 검토 : 도메인 경계가 명확하지 않은 상태에서 서둘러 MSA로 나누면 분산 모놀리스(Distributed Monolith)가 되므로, 모듈러 모놀리스로 시작해 경계가 성숙함에 따라 분할하는 것이 바람직하다.
2. 분산 정합성 패턴의 기본 적용 : 2단계 커밋 대신 보상 트랜잭션 기반의 Saga 패턴과 이벤트 유실을 막는 트랜잭셔널 아웃박스 패턴을 설계 단계부터 표준으로 채택해야 한다.
3. 관측 가능성의 조기 도입 : 분산 추적과 상관 ID 기반 로깅을 전사 표준으로 정하고 배포 파이프라인에 포함시켜 장애 원인 분석 시간을 줄여야 한다.

## Ⅶ. 결론

- 핵심 요약 : MSA는 도메인 분할과 분산 패턴 적용을 전제로 하는 확장성 중심의 아키텍처 스타일.
- 시사점 : 모놀리스 퍼스트 원칙과 분산 데이터 정합성 대책을 갖춘 성숙도 기반의 점진적 전환이 MSA 성공의 조건임.
