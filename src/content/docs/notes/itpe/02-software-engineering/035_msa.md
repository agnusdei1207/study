## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어 공학 → 아키텍처·설계 → **MSA(모놀리식과 비교)**

## 30초 인출

- 본질: **MSA(Microservices Architecture)**는 단일 애플리케이션을 비즈니스 도메인 중심의 작고 독립적으로 배포 가능한 서비스들의 집합으로 분할하여 구축하는 아키텍처 스타일
- 메커니즘: **DDD(Domain-Driven Design)** 기반 경계 설정 + 서비스별 독립 데이터베이스(**Database per Service**) + **Representational State Transfer(REST)**·메시지 기반 통신
- 산출/효과: 독립적 배포 및 확장(Scalability) · 장애 격리(Fault Isolation) · 폴리글랏(Polyglot) 개발 지원

<details>
<summary>핵심 용어</summary>

- **MSA(Microservices Architecture)**: 대규모 소프트웨어를 독립적으로 배포 및 운영 가능한 작은 단위의 서비스 조합으로 설계하는 스타일
- **Monolithic Architecture**: 모든 비즈니스 로직, UI, 데이터베이스 접근 코드가 하나의 코드베이스와 실행 단위로 결합된 구조
- **Database per Service**: 각 마이크로서비스가 자신의 데이터베이스를 전용으로 소유하고 외부 서비스의 직접 DB 접근을 금지하는 패턴
- **Conway's Law(콘웨이의 법칙)**: 시스템의 구조는 그 시스템을 설계하는 조직의 소통 구조를 반영한다는 법칙 (역 콘웨이 전략의 근거)
- **Saga Pattern**: 분산 DB 환경에서 2PC 대신 로컬 트랜잭션과 보상 트랜잭션(Compensating Transaction)의 연속으로 데이터 일관성을 맞추는 패턴
- **CQRS(Command Query Responsibility Segregation)**: 명령 처리와 조회 처리를 별도 모델로 분리하는 설계 패턴
- **DDD(Domain-Driven Design)**: 도메인 모델과 업무 경계를 중심으로 소프트웨어를 설계하는 접근법
- **REST(Representational State Transfer)**: 자원과 표현, 제약 조건을 중심으로 네트워크 기반 시스템을 설계하는 아키텍처 스타일
- **2PC(Two-Phase Commit)**: 분산 참여자가 준비 단계와 커밋 단계에 합의해 하나의 분산 트랜잭션을 수행하는 프로토콜
- **API(Application Programming Interface)**: 소프트웨어 구성요소가 기능·데이터를 요청하고 응답받기 위해 합의한 접점

> 마이크로서비스 아키텍처(MSA)의 정의와 목적, 서비스 경계 및 데이터 소유 구조를 설명하시오. (예상)

---

## 1교시 10점 답안

### Ⅰ. 정의·목적

| 구분 | 핵심 |
|---|---|
| 정의 | **MSA(Microservices Architecture)**는 애플리케이션을 업무 기능을 맡는 서비스로 나누고 각 서비스를 독립 배포 단위로 운영하는 아키텍처 스타일 |
| 목적 | 변경 파급 효과를 줄이고 서비스별 배포·확장 자율성을 확보 |

### Ⅱ. 모놀리식·MSA 비교

```text
모놀리식: UI·주문·회원·결제 단일 배포
    └─ 통합 데이터 저장소

MSA: 서비스별 독립 배포
    ├─ 주문 서비스 ─ 주문 데이터
    ├─ 회원 서비스 ─ 회원 데이터
    └─ 결제 서비스 ─ 결제 데이터
```

### Ⅲ. 핵심 통제

- **Database per Service**: 데이터 결합도 제거 및 서비스 자율성 보장
- **Saga 패턴**: 분산 환경에서 로컬 트랜잭션과 보상 트랜잭션으로 최종 일관성 유지

- 제언: 먼저 모듈 경계와 변경 책임을 검증하고 독립 배포·확장이 필요한 업무 경계부터 분리해 운영 부담과 이점을 함께 평가

## 2~4교시 25점 답안

### Ⅰ. MSA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **MSA(Microservices Architecture)**는 애플리케이션을 업무 기능을 맡는 서비스로 나누고 각 서비스를 독립 배포 단위로 운영하는 아키텍처 스타일 |
| 목적 | 변경 파급 효과를 줄이고 서비스별 배포·확장 자율성을 확보 |

| MSA의 설계 단위 | 핵심 의미 |
|---|---|
| 서비스 경계 | 업무 기능과 변경 책임을 구분 |
| 배포 단위 | 서비스별 변경·배포를 독립적으로 관리 |
| 데이터 소유 | 서비스가 자기 데이터의 변경을 책임짐 |

### Ⅱ. 모놀리식 아키텍처 vs 마이크로서비스 아키텍처(MSA) 상세 비교

> 단순함과 일관성을 제공하는 모놀리식과, 확장성과 변경 유연성을 제공하는 MSA 간의 트레이드오프 분석이 필수적이다.

```text
클라이언트
    ↓ 요청 라우팅
API Gateway
    ↓
업무 서비스
    ├─ 소유 데이터 읽기·쓰기
    └─ 이벤트 발행 → 다른 서비스
```

| 비교 항목 | 모놀리식 아키텍처 (Monolithic) | 마이크로서비스 아키텍처 (MSA) |
|---|---|---|
| **배포 단위** | 전체 시스템을 함께 배포하는 경우가 많음 | 서비스별 독립 배포가 가능하지만 호환성·운영 준비 필요 |
| **장애 영향도** | 공통 프로세스·자원 장애가 여러 기능에 영향 가능 | 서비스 경계로 영향을 제한할 수 있으나 호출 연쇄 장애를 별도 통제해야 함 |
| **데이터베이스** | 통합 저장소는 로컬 트랜잭션 경계를 단순화할 수 있음 | 서비스별 데이터 소유가 분산 일관성·조회 설계를 요구 |
| **확장성 (Scaling)** | 전체 시스템을 수평 확장해야 함 | **부하가 높은 특정 서비스만 선별적 스케일아웃** |
| **운영 복잡도** | 단일 프로세스 중심으로 비교적 단순 | 분산 추적·장애 격리·서비스 통신 통제 필요 |
| **기술 스택** | 단일 언어 및 프레임워크에 종속 | **서비스별 최적 기술 자유 채택 (폴리글랏)** |

### Ⅲ. MSA 구축을 위한 4대 핵심 아키텍처 패턴

> 분산 환경에서 발생하는 네트워크 지연, 데이터 분산, 트랜잭션 문제를 해결하기 위한 검증된 패턴이다.

| 패턴 | 해결 문제·핵심 판단 |
|---|---|
| **API Gateway** | 클라이언트 단일 진입점 · 인증, SSL 종단, 라우팅, Rate Limiting 일괄 수행 |
| **Database per Service** | 전용 DB 소유로 서비스 간 결합도 제거 · 타 서비스 직접 접근 금지(정보은닉) |
| **Saga** | Choreography(이벤트 기반) 또는 Orchestration(오케스트레이터) 기반 보상 트랜잭션 |
| **CQRS** | 복잡한 다중 서비스 조인 조회를 명령 모델과 조회 모델 분리로 해결 |

### Ⅳ. MSA 전환 한계·대응책

> 여러 서비스에 걸친 트랜잭션은 일관성·가용성·운영 복잡도를 함께 따져 조정하며, Saga는 보상 작업을 통해 업무 흐름을 관리하는 한 선택지다.

### 1. 분산 트랜잭션 및 일관성 기법

| 기법 | 핵심 동작 방식 | 장단점 및 고려사항 |
|---|---|---|
| **코레오그래피 사가 (Choreography)** | 중앙 제어자 없이 각 서비스가 이벤트를 발행/구독하여 다음 단계 실행 | 서비스 간 결합도가 낮으나, 워크플로우가 복잡해지면 추적이 어려움 |
| **오케스트레이션 사가 (Orchestration)**| 중앙 사가 오케스트레이터가 각 서비스에 실행 명령 및 보상 트랜잭션 지휘 | 트랜잭션 상태 추적이 용이하나, 오케스트레이터에 로직 집중 위험 |
| **보상 트랜잭션 (Compensating Tx)** | 중간 단계 실패 시 이미 커밋된 이전 트랜잭션을 롤백하는 역방향 작업 수행 | 완전한 ACID 롤백이 아닌 비즈니스적 취소(예: 결제 취소 요청) 메커니즘 |

### 2. MSA 구축 실무 위험 및 대응 통제

| 위험 | 대책 | 효과 |
|---|---|---|
| 분산 환경에서 서비스 간 데이터 불일치 | 업무 흐름에 맞는 Saga 보상 작업과 메시지 전달 보장을 설계하고 결과 상태를 추적 | 중간 실패와 재시도 상태를 확인할 수 있음 |
| 연쇄 장애 전파 및 네트워크 병목 | API Gateway 기반 Rate Limiting 및 Circuit Breaker 적용 | 장애 서비스 격리 및 시스템 전체 다운 방지 |
| 분산 모놀리스(Distributed Monolith) 전락 | DDD 기반 Bounded Context 명확화 및 Database-per-service 엄격 준수 | 서비스 간 독립 배포성 및 낮은 결합도 보장 |

| 한계 | 해결 방안 |
|---|---|
| 서비스 분해가 사업상 독립성과 맞지 않으면 분산 운영 부담만 늘어남 | 모듈 경계와 변경 책임을 검증하고 독립 배포·확장이 필요한 업무 경계부터 분리해 운영 부담과 이점을 함께 평가 |
