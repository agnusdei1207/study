## 본론: 개념 및 핵심 메커니즘

### 1. 모놀리식과 MSA의 공학적 본질

- **모놀리식 아키텍처 (Monolithic)**:
  - 모든 비즈니스 로직과 데이터베이스 액세스 계층이 하나의 애플리케이션 아티팩트(JAR/WAR)로 패키징되어 단일 프로세스에서 실행되는 구조.
  - **장점**: 개발 초기 단순성, ACID 트랜잭션의 엄격한 보장, 초고속 인메모리 함수 호출.
  - **한계**: 시스템 거대화 시 단일 변경에도 전체 재빌드/재배포 필요, 단일 모듈 장애가 전체로 전파(SPOF), 기술 스택 고착화.
- **마이크로서비스 아키텍처 (MSA)**:
  - 단일 비즈니스 도메인(Bounded Context)을 담당하는 작고 독립적인 서비스들의 집합으로 시스템을 구축하는 아키텍처.
  - **장점**: 서비스별 독립 배포 및 탄력적 수평 확장, 폴리글랏 기술 도입, 결함 격리.
  - **대가**: 네트워크 레이턴시 증가, 분산 트랜잭션 데이터 일관성 난제, 인프라 운영 복잡도 폭증.

### 2. MSA 핵심 플랫폼 컴포넌트

1. **API Gateway**: 단일 진입점 DMZ 배치, 인증/인가(JWT), Rate Limiting, 라우팅.
2. **Service Mesh (Istio, Linkerd)**: 사이드카(Envoy) 프록시를 통한 East-West mTLS 암호화, 트래픽 제어, 카나리 배포.
3. **Service Discovery & Config Server**: 동적 컨테이너 IP 등록/탐색(Consul, Eureka) 및 중앙 집중 환경 설정.
4. **Resiliency (서킷 브레이커)**: 호출 지연/실패 감지 시 즉각 폴백(Fallback) 반환으로 장애 전파 차단 (Resilience4j).

### 3. 분산 데이터 일관성 보장: 사가(Saga) 패턴

- **2PC(Two-Phase Commit)의 한계**: 분산 환경에서 글로벌 락으로 인한 성능 저하 및 가용성 훼손 (CAP 정리).
- **Saga 패턴**: 일련의 로컬 트랜잭션을 실행하고, 중간 실패 시 이전에 성공한 트랜잭션들을 되돌리는 **보상 트랜잭션(Compensating Transaction)**을 실행하여 **결과적 일관성(Eventual Consistency)**을 달성.
  1. **코레오그래피 사가 (Choreography)**: 중앙 제어기 없이 각 서비스가 비동기 이벤트(Kafka)를 발행·구독하며 다음 단계를 자율 실행.
  2. **오케스트레이션 사가 (Orchestration)**: 중앙 사가 오케스트레이터가 실행 흐름을 통제하고 실패 시 보상 트랜잭션을 직접 지시.

## 아키텍처 스타일 4자 비교

| 비교 항목 | 모놀리식 (Monolith) | 모듈러 모놀리스 | SOA | 마이크로서비스 (MSA) |
|---|---|---|---|---|
| **서비스 크기** | 거대한 단일 단위 | 단일 배포, 내부 분할 | 엔터프라이즈 전사 단위 | 작고 자율적인 단일 도메인 |
| **데이터베이스** | 단일 통합 DB | 단일 DB (논리적 스키마 분리) | 공유 DB 또는 복합 연계 | **DB per Service (완전 격리)** |
| **통신 방식** | 메모리 직접 호출 | 메모리 직접 호출 | 무거운 ESB (SOAP/XML) | 경량 REST, gRPC, 메시지 큐 |
| **트랜잭션** | ACID (강한 일관성) | ACID (강한 일관성) | 2PC 분산 트랜잭션 | **BASE / Saga (결과적 일관성)** |
| **운영 복잡도** | 매우 낮음 | 낮음 | 높음 (ESB 병목) | 매우 높음 (K8s, 메시 필수) |

## 실무 장애 시나리오 및 공학적 대안

### 1. 현장 장애 사례

1. **분산 모놀리스(Distributed Monolith)의 참사**:
   - 도메인 경계 없이 서비스를 50개로 쪼개놓고 단일 공유 DB를 바라보게 만들어, 배포 순서 의존성과 락 경합으로 MSA의 장점은 사라지고 네트워크 비용만 10배 증가.
2. **트랜잭션 실패로 인한 유령 데이터 발생**:
   - 주문 생성 후 결제 서비스 호출 중 네트워크 타임아웃 발생, 주문은 생성되었으나 결제는 미승인되어 재고만 묶이는 정합성 훼손.

### 2. 문제 원인 및 공학적 해결책

| 장애 상황 | 근본 원인 | 공학적 대책 (대안 기술) | 개선 효과 |
|---|---|---|---|
| **분산 모놀리스 전락** | DB per Service 미준수 및 서비스 간 강결합 | DDD 바운디드 컨텍스트 재설계 + 비동기 이벤트 기반 디커플링 | 서비스 독립 배포율 100% 확보 |
| **분산 데이터 불일치** | 분산 환경에서 단순 REST 동기 호출 의존 | **Saga 보상 트랜잭션 + 트랜잭셔널 아웃박스(Transactional Outbox)** 패턴 | 데이터 유실 방지 및 결과적 일관성 보장 |
| **연쇄 서비스 장애** | 하위 서비스 지연 시 상위 서비스 스레드 고갈 | **서킷 브레이커(Resilience4j)** + 타임아웃 및 격리벽(Bulkhead) | 장애 파급 차단 및 가용성 99.99% 유지 |

## 결론: 기술사 답안 차별화 포인트

1. **성급한 MSA 전환 경고 (Modular Monolith 우선주의)**: MSA가 만병통치약이 아니며, 초기 단계에서는 **모듈러 모놀리스(Modular Monolith)**로 비즈니스와 도메인 경계를 충분히 검증한 후 트래픽과 변경 주기에 따라 점진적으로 분리해야 함을 강조할 것.
2. **스트랭글러 피그 패턴과 콘웨이의 법칙**: 모놀리스를 한 번에 빅뱅 방식으로 바꾸려 하지 말고, **스트랭글러 무화과나무 패턴(Strangler Fig Pattern)**으로 점진적 서비스 추출을 유도하며, 시스템 구조뿐 아니라 팀 조직을 서비스 단위로 재편(Reverse Conway Maneuver)해야 성공함을 3단락 제언으로 피력할 것.
