## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 아키텍처·설계 → **MSA(모놀리식과 비교)**

## 30초 인출

- 본질: 단일 애플리케이션을 비즈니스 도메인(DDD Bounded Context) 중심의 작고 독립적으로 배포 및 확장 가능한 서비스들의 집합으로 분할하여 구축하는 분산 아키텍처 스타일
- 메커니즘: API Gateway 진입점 + 서비스별 전용 데이터베이스(Database per Service) + 경량 통신(REST/gRPC/Kafka) + 분산 트랜잭션 통제(Saga 패턴)
- 통찰: 성급한 서비스 분할은 분산 모놀리스(Distributed Monolith)와 심각한 네트워크 지연을 초래하므로 성숙한 CI/CD 및 관측성(Observability) 기반하에 점진적 분할(Strangler Fig 패턴) 적용 필수

<details>
<summary>핵심 용어</summary>

- **MSA(Microservices Architecture)** : 대규모 소프트웨어를 독립적으로 배포 및 운영 가능한 작은 단위의 서비스 조합으로 설계하는 스타일
- **Monolithic Architecture** : UI, 비즈니스 로직, 데이터 접근 계층이 단일 바이너리 및 통합 데이터베이스로 구성된 전통적 구조
- **Database per Service** : 각 마이크로서비스가 자신의 전용 데이터베이스를 소유하고 외부의 직접 DB 조회를 금지하는 핵심 데이터 격리 패턴
- **Saga Pattern** : 분산 트랜잭션 환경에서 2PC 대신 로컬 트랜잭션 완료 후 이벤트를 발행하고 실패 시 보상 트랜잭션(Compensating Tx)을 실행하는 패턴
- **CQRS(Command Query Responsibility Segregation)** : 데이터의 상태를 변경하는 명령(Command) 모델과 조회를 처리하는 질의(Query) 모델을 물리적으로 분리하는 패턴
- **Strangler Fig Pattern (교살자 패턴)** : 레거시 모놀리식 시스템의 기능을 점진적으로 마이크로서비스로 전환하여 시스템 전체를 안전하게 대체하는 마이그레이션 기법

</details>

## 2~4교시 25점 답안

## Ⅰ. MSA의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 비즈니스 도메인(Bounded Context) 경계를 따라 소프트웨어를 작고 독립적으로 배포 가능한 다수의 서비스 단위로 분할하고, 표준 경량 API 및 이벤트 기반으로 상호 연동하는 분산 소프트웨어 아키텍처 스타일 |
| 목적 | 서비스별 독립적 배포 및 확장 자율성 확보, 장애 격리(Fault Isolation) 및 대규모 개발 조직의 기민한 기능 변경 지원 |

## Ⅱ. MSA의 핵심 특징

| 특징 | 의미 |
|---|---|
| 폴리글랏 아키텍처 (Polyglot) | 각 마이크로서비스의 도메인 특성에 맞추어 최적의 프로그래밍 언어, 프레임워크, DBMS 선별 채택 |
| 높은 응집도와 느슨한 결합 | 도메인 주도 설계(DDD)를 통해 서비스 내부는 강하게 응집되고 서비스 간 의존성은 인터페이스로 최소화 |
| 서비스별 독립 데이터 소유 | Database per Service 패턴을 강제하여 데이터 계층 결합도를 차단하고 스키마 변경 자유 보장 |
| 장애 격리 및 탄력성 | 서킷 브레이커(Circuit Breaker) 등을 적용하여 단일 서비스 장애가 전체 시스템으로 전파되는 연쇄 고장 차단 |

## Ⅲ. MSA 전주기 체계 및 요청 처리 프로세스

### 엔터프라이즈 MSA 4계층 아키텍처 및 이벤트 연계 흐름

```text
[웹 브라우저 / 모바일 앱 클라이언트]
       │
       ▼ (단일 진입점, HTTPS/REST)
┌────────────────────────────────────────────────────────────────────────┐
│ 1. API Gateway 계층 (인증/인가, Rate Limiting, SSL 종단, 라우팅)        │
└──────────────────┬─────────────────────────────────┬───────────────────┘
                   │ 동기 호출 (REST/gRPC)           │ 동기 호출
                   ▼                                 ▼
┌──────────────────────────────────┐  ┌──────────────────────────────────┐
│ 2. 주문 서비스 (Order Service)   │  │ 3. 회원 서비스 (Member Service)  │
│    - 비즈니스 로직 처리          │  │    - 회원 권한 검증 및 프로필     │
│    - 전용 DB (Order RDBMS)       │  │    - 전용 DB (Member NoSQL)       │
└──────────────────┬───────────────┘  └──────────────────────────────────┘
                   │
                   │ 이벤트 발행 (Kafka / RabbitMQ 메시지 브로커)
                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. 이벤트 기반 통신 및 비동기 사가(Saga) 오케스트레이션               │
│    - "주문 생성됨(OrderCreated)" 이벤트 브로드캐스팅                   │
└──────┬─────────────────────────────────────────────┬───────────────────┘
       │ 구독 (Subscribe)                            │ 구독 (Subscribe)
       ▼                                             ▼
┌──────────────────────────────────┐  ┌──────────────────────────────────┐
│ 5. 결제 서비스 (Payment Service) │  │ 6. 재고 서비스 (Stock Service)   │
│    - 카드 결제 승인 처리         │  │    - 주문 상품 재고 즉시 차감     │
│    - 전용 DB (Payment DB)        │  │    - 전용 DB (Stock DB)           │
│    ★ 실패 시: 보상 이벤트 발행  │  │    ★ 결제 취소 시: 재고 복구     │
└──────────────────────────────────┘  └──────────────────────────────────┘
```

### MSA 핵심 구성요소 상세 분석

| 구성요소 | 핵심 기술 | 주요 역할 및 기능 |
|---|---|---|
| **API Gateway** | Spring Cloud Gateway, Kong | 클라이언트 요청의 단일 관문, 라우팅, 인증 캐싱, 로드밸런싱 |
| **서비스 디스커버리** | Netflix Eureka, Consul, K8s CoreDNS | 동적으로 생성 및 삭제되는 마이크로서비스 인스턴스의 네트워크 주소 등록/탐색 |
| **분산 메시징 브로커** | Apache Kafka, RabbitMQ | 서비스 간 비동기 이벤트 전달, 트래픽 버퍼링, 느슨한 결합 보장 |
| **분산 트레이싱** | OpenTelemetry, Jaeger, Zipkin | 분산 호출 트랜잭션에 전역 Trace ID를 전파하여 병목 구간 및 오류 추적 |
| **서킷 브레이커** | Resilience4j, Envoy Service Mesh | 장애 발생 서비스에 대한 호출 차단(Open) 및 폴백(Fallback) 실행 |

## Ⅳ. 모놀리식 vs MSA 비교 및 분산 트랜잭션 패턴

### 모놀리식(Monolithic)과 마이크로서비스(MSA) 비교

| 비교 항목 | 모놀리식 아키텍처 (Monolithic) | 마이크로서비스 아키텍처 (MSA) |
|---|---|---|
| **배포 단위** | 전체 시스템이 단일 실행 파일(WAR/JAR)로 통합 배포 | **서비스별 독립 배포 파이프라인 (무중단 릴리스)** |
| **데이터 일관성** | 단일 DB의 강력한 트랜잭션(ACID) 보장 용이 | **결과적 일관성(Eventual Consistency) 및 Saga 적용** |
| **장애 격리 (Resilience)** | 메모리 누수나 오류 발생 시 전체 프로세스 다운 | **서비스 경계 내 격리, 타 서비스 정상 가동 지속** |
| **확장성 (Scalability)** | 부하가 특정 기능에 집중되어도 전체 시스템 증설 | **병목 서비스만 핀포인트로 스케일아웃(Scale-out)** |
| **기술 스택 유연성** | 프로젝트 초기 선정된 언어/프레임워크 종속 | **서비스 목적에 맞춘 다양한 기술 조합(Polyglot)** |
| **운영 인프라 복잡도** | 단순한 인프라 구성 및 직관적 배포 | **K8s, 서비스 메시, 분산 관측성 등 고난도 인프라 필수** |

### 사가 패턴(Saga Pattern) 유형 비교

| 구분 | 코레오그래피 사가 (Choreography) | 오케스트레이션 사가 (Orchestration) |
|---|---|---|
| **제어 메커니즘** | 중앙 제어자 없음, 이벤트 발행/구독 방식 | **중앙 사가 오케스트레이터가 흐름 총괄 지휘** |
| **서비스 간 결합도** | 서비스 간 직접 의존성이 없어 가장 느슨함 | 오케스트레이터가 개별 서비스의 호출 규격을 인지 |
| **트랜잭션 가시성** | 워크플로우가 복잡해지면 전체 흐름 추적 곤란 | **중앙에서 트랜잭션 진행 상태 및 롤백 상태 즉시 확인** |
| **적합한 환경** | 참여 서비스가 적고 흐름이 단순한 트랜잭션 | 단계가 복잡하고 다수 서비스가 연계되는 핵심 업무 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 서비스 분할에 따른 네트워크 홉(Hop) 증가 및 분산 호출 지연 시간 누적 | 내부 고성능 바이너리 프로토콜(gRPC) 적용 및 동일 노드 배치 최적화 |
| Database per Service로 인한 여러 테이블 조인 쿼리 불가 및 통계 집계 곤란 | CQRS 패턴을 적용하여 질의 전용 읽기 저장소(Elasticsearch, Read DB) 비동기 구축 |
| 트랜잭션 실패 시 데이터 불일치 및 네트워크 파티션 발생 위험 | 멱등성(Idempotency) 키 설계 및 사가 패턴 기반 자동 보상 트랜잭션 보장 |

## Ⅵ. 제언

Strangler Fig 패턴을 통한 점진적 레거시 전환 및 서비스 메시(Service Mesh)를 통한 인프라 거버넌스 중앙화

### 교살자 무화과(Strangler Fig) 기반 모놀리식 전환 로드맵

```text
[전환 1단계: API Gateway 프록시 배치]
  ├─ 외부 요청을 API Gateway로 유입
  └─ 모든 트래픽을 기존 레거시 모놀리스로 우선 바이패스
       ↓
[전환 2단계: 신규 도메인/비핵심 서비스 우선 추출]
  ├─ 결제/알림 모듈을 독립 마이크로서비스로 분리
  └─ API Gateway 라우팅 규칙 변경하여 해당 경로만 신규 서비스로 전송
       ↓
[전환 3단계: 핵심 코어 도메인 단계적 마이그레이션]
  ├─ 데이터 마이그레이션(Change Data Capture, Debezium 활용)
  └─ 주문/회원 모듈 추출 및 구 모놀리스 코드 점진적 제거
       ↓
[전환 4단계: 레거시 모놀리스 완전 퇴역(Sunset)]
```

### MSA 도입 타당성 검토 의사결정 체계

```text
소프트웨어 아키텍처 재설계 요구
       ↓
[조직 규모가 수십~수백 명으로 팀 간 배포 병목이 심각한가?]
       ├─ 아니오 ─→ 모듈러 모놀리스(Modular Monolith) 채택 (단순성 유지)
       └─ 예 ───→ [비즈니스 도메인의 경계(Bounded Context)가 명확한가?]
                      ├─ 아니오 ─→ 도메인 주도 설계(DDD) 선행 수행
                      └─ 예 ───→ 마이크로서비스 아키텍처(MSA) 추진 결정
```

### 선택 근거: 모듈러 모놀리스와 마이크로서비스(MSA) 비교

| 구분 | 모듈러 모놀리스 (Modular Monolith) | 제언: 마이크로서비스 (MSA) |
|---|---|---|
| 프로세스 경계 | 단일 프로세스 내 모듈 간 메모리 호출 | 네트워크 경계를 통한 프로세스 간 분산 호출 |
| 운영 비용 | 단일 서버/컨테이너로 인프라 비용 최소화 | 분산 인프라 및 관측 플랫폼 구축 비용 발생 |
| 조직 확장성 | 팀 규모 커질수록 빌드/머지 병목 한계 | 팀별 완전 독립적인 릴리스 사이클 확보 가능 |
