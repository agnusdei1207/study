## 큰 그림과 30초 인출

- 본질: **MSA(Microservices Architecture)**는 단일 애플리케이션을 비즈니스 도메인 중심의 작고 독립적으로 배포 가능한 서비스들의 집합으로 분할하여 구축하는 아키텍처 스타일
- 메커니즘: 도메인 주도 설계(**DDD**) + 서비스별 독립 데이터베이스(**Database per Service**) + 경량 API 통신(**REST/gRPC/Kafka**)
- 산출/효과: 독립적 배포 및 확장(Scalability) · 장애 격리(Fault Isolation) · 폴리글랏(Polyglot) 개발 지원

<details>
<summary>핵심 용어</summary>

- **MSA(Microservices Architecture)**: 대규모 소프트웨어를 독립적으로 배포 및 운영 가능한 작은 단위의 서비스 조합으로 설계하는 스타일
- **Monolithic Architecture**: 모든 비즈니스 로직, UI, 데이터베이스 접근 코드가 하나의 코드베이스와 실행 단위로 결합된 구조
- **Database per Service**: 각 마이크로서비스가 자신의 데이터베이스를 전용으로 소유하고 외부 서비스의 직접 DB 접근을 금지하는 패턴
- **Conway's Law(콘웨이의 법칙)**: 시스템의 구조는 그 시스템을 설계하는 조직의 소통 구조를 반영한다는 법칙 (역 콘웨이 전략의 근거)
- **Saga Pattern**: 분산 DB 환경에서 2PC 대신 로컬 트랜잭션과 보상 트랜잭션(Compensating Transaction)의 연속으로 데이터 일관성을 맞추는 패턴

</details>

## 예상문제

> 전통적 모놀리식 아키텍처(Monolithic Architecture)의 한계와 이를 극복하기 위한 마이크로서비스 아키텍처(MSA)의 개념 및 특징을 비교 설명하고, MSA 설계의 핵심 패턴 4가지(API Gateway, Database per Service, Saga, CQRS) 및 분산 환경의 데이터 일관성 확보 방안을 제시하시오. (25점)

## Ⅰ. 대규모 시스템 확장과 신속 배포의 패러다임, MSA의 개요

> 하나의 거대한 성(Monolith)을 지탱할 수 없다면, 자율적으로 기동하는 작은 서비스들의 연합체(MSA)로 전환해야 한다.

- 정의: 하나의 큰 애플리케이션을 비즈니스 기능 단위로 세분화하여, 각 서비스가 **자체 프로세스에서 실행되고 독립적으로 배포**되며 경량 메커니즘(HTTP/메시징)으로 통신하는 아키텍처 스타일
- 목적: 변경 파급 효과 격리, 서비스별 독립 스케일아웃(Scale-out), 팀 단위 자율 배포 가속, 신기술 도입 유연성(폴리글랏) 확보

## Ⅱ. 모놀리식 아키텍처 vs 마이크로서비스 아키텍처(MSA) 상세 비교

> 단순함과 일관성을 제공하는 모놀리식과, 확장성과 변경 유연성을 제공하는 MSA 간의 트레이드오프 분석이 필수적이다.

  <div class="itpe-pipeline-node">

    <span>단일 코드베이스 · 컴포넌트 간 인메모리 함수 호출 · ACID 단일 트랜잭션</span>

    <span>분산 프로세스 · 네트워크 API 통신 · 최종 일관성(Eventual Consistency)</span>
  </div>

| 비교 항목 | 모놀리식 아키텍처 (Monolithic) | 마이크로서비스 아키텍처 (MSA) |
|---|---|---|
| **배포 단위** | 전체 시스템 일괄 배포 (빅뱅) | **서비스별 독립 배포 (무중단, 상시 배포)** |
| **장애 영향도** | 특정 모듈 메모리 누수 시 **전체 시스템 다운** | 결함이 해당 서비스로 격리 (**서킷 브레이커 차단**) |
| **데이터베이스** | 단일 통합 DB (Shared DB, ACID 보장) | **Database per Service (분산 DB, 최종 일관성)** |
| **확장성 (Scaling)** | 전체 시스템을 수평 확장해야 함 | **부하가 높은 특정 서비스만 선별적 스케일아웃** |
| **운영 복잡도** | 단순 (로컬 디버깅 및 모니터링 용이) | **극도로 복잡 (분산 트레이싱, 서비스 메시 필수)** |
| **기술 스택** | 단일 언어 및 프레임워크에 종속 | **서비스별 최적 기술 자유 채택 (폴리글랏)** |

## Ⅳ. 분산 트랜잭션 확보 및 실무 위험 관리

> 전통적 2PC(Two-Phase Commit)는 분산 환경에서 가용성을 해치므로, Saga 패턴과 이벤트 기반 일관성을 채택한다.

### 1. 분산 트랜잭션 및 일관성 기법

| 기법 | 핵심 동작 방식 | 장단점 및 고려사항 |
|---|---|---|
| **코레오그래피 사가 (Choreography)** | 중앙 제어자 없이 각 서비스가 이벤트를 발행/구독하여 다음 단계 실행 | 서비스 간 결합도가 낮으나, 워크플로우가 복잡해지면 추적이 어려움 |
| **오케스트레이션 사가 (Orchestration)**| 중앙 사가 오케스트레이터가 각 서비스에 실행 명령 및 보상 트랜잭션 지휘 | 트랜잭션 상태 추적이 용이하나, 오케스트레이터에 로직 집중 위험 |
| **보상 트랜잭션 (Compensating Tx)** | 중간 단계 실패 시 이미 커밋된 이전 트랜잭션을 롤백하는 역방향 작업 수행 | 완전한 ACID 롤백이 아닌 비즈니스적 취소(예: 결제 취소 요청) 메커니즘 |

### 2. MSA 구축 실무 위험 및 대응 통제

| 위험 | 대책 | 효과 |
|---|---|---|
| 분산 환경 내 데이터 정합성 깨짐 | Saga 패턴(보상 트랜잭션) 및 Outbox 패턴 기반 결과적 일관성 보장 | 2PC 없는 고가용성 및 비즈니스 정합성 유지 |
| 연쇄 장애 전파 및 네트워크 병목 | API Gateway 기반 Rate Limiting 및 Circuit Breaker 적용 | 장애 서비스 격리 및 시스템 전체 다운 방지 |
| 분산 모놀리스(Distributed Monolith) 전락 | DDD 기반 Bounded Context 명확화 및 Database-per-service 엄격 준수 | 서비스 간 독립 배포성 및 낮은 결합도 보장 |

## Ⅴ. 무분별한 MSA 전환 방지를 위한 기술사적 제언

> MSA는 프리미엄 기술이 아니라 비싼 대가를 치러야 하는 복잡성 세금(Complexity Tax)이다.

### 학습자 통찰 메모 — 답안 밖

- [핵심 통찰]: 마틴 파울러가 경고한 "모놀리식 우선(Monolith First)" 원칙을 되새겨야 함. 도메인 경계가 불명확한 상태에서 섣부르게 MSA를 도입하면 '분산 모놀리스(Distributed Monolith)'라는 최악의 재앙에 직면함. 모놀리식의 단점(결합도)과 분산 시스템의 단점(네트워크 지연, 트랜잭션 파편화)을 모두 갖게 되기 때문임.
- 나라면: 도메인 주도 설계(DDD)의 전략적 설계를 통해 Bounded Context를 완벽히 식별하고, 먼저 단일 배포체 내에서 모듈형 모놀리스(Modular Monolith)로 경계를 검증한 후, 트래픽과 조직 규모가 임계점을 넘을 때 단계적으로 서비스를 분리하겠음.

### 실전 답안용 기술사적 제언

- 판정: 도메인 성숙도 및 조직 구조(Conway 법칙) 기반 MSA 전환 판정
- 대안: **DDD 전략적 설계** 적용 및 **서비스 메시(Istio)** 기반 관측성/트래픽 통제
- 검증: 분산 트랜잭션 보상 메커니즘 100% 검증 · 분산 트레이싱(OpenTelemetry) 완비
- 효과: 독립 배포성 확보 · 비즈니스 장애 국소화 및 대규모 탄력적 확장 달성

## 1교시 10점 답안 발췌

### 1. 정의·목적

- 정의: **MSA(Microservices Architecture)**는 애플리케이션을 도메인 중심의 작고 독립적으로 배포 가능한 서비스 집합으로 구축하는 분산 아키텍처
- 목적: 독립 배포성, 장애 격리, 기술 다양성 및 유연한 스케일아웃 달성

### 2. 모놀리식 vs MSA 핵심 비교

<div class="itpe-pipeline is-vertical" role="img" aria-label="모놀리식 vs MSA 요약">

### 3. 핵심 통제

- **Database per Service**: 데이터 결합도 제거 및 서비스 자율성 보장
- **Saga 패턴**: 분산 환경에서 로컬 트랜잭션과 보상 트랜잭션으로 최종 일관성 유지
