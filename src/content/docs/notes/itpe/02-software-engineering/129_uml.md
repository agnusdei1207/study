## 한 줄 본질
- 서로 다른 객체지향 표기법으로 인해 분석가, 설계자, 개발자 간의 의사소통 왜곡 병목 → 시스템의 아키텍처, 정적 구조, 동적 상호작용을 표준화된 기호와 다이어그램으로 시각화하고 문서화하는 객체지향 모델링 표준 / 과도한 형식화 시 유지보수 비용 급증

## 핵심 용어
- 스테레오타입(Stereotype): UML 기본 요소에 새로운 의미를 부여하기 위해 길러릿(Guillemets, `<< >>`) 기호 안에 메타 정보를 부여하는 UML 3대 확장 메커니즘 중 하나
- MDA(Model-Driven Architecture): 비즈니스 모델(CIM, PIM)을 먼저 UML로 정밀하게 정의하고 도구를 통해 실행 소스코드(PSM)를 자동 생성하려 했던 아키텍처 패러다임

## 핵심 통찰
- 마틴 파울러(Martin Fowler)가 지적했듯 UML의 가치는 모든 코드를 완벽히 그리는 "청사진(Blueprint)"이나 "프로그래밍 언어(MDA)"가 아니라, 팀원 간의 핵심 설계를 칠판에 빠르게 공유하는 "스케치(Sketch)"에 있음
- 14개 다이어그램을 모두 그리는 프로젝트는 100% 실패하며, 실무에서는 유스케이스(요구), 클래스(도메인 구조), 시퀀스(API 흐름) 3가지만 제대로 그려도 전체 설계 소통의 90%를 달성함
- GUI 기반 전용 케이스 도구(Rational Rose 등)는 버전 관리와 협업이 극도로 어려워 사장되었으며, 마크다운 문서 내에 텍스트 코드로 삽입하는 PlantUML이나 Mermaid 방식이 현대적 표준으로 정착함

## 이웃 토픽과 구분
- UML vs ERD(Entity Relationship Diagram): UML = 객체의 상태(속성)와 행위(메서드), 상속 관계를 모두 표현 / ERD = 데이터베이스에 저장되는 데이터의 정적 관계(릴레이션)만을 표현

## 문제·원인·대책
- 적용 상황: 수백 명의 개발자가 참여하는 차세대 금융 프로젝트 설계 감리
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 설계자가 작성한 수천 장의 UML 다이어그램과 실제 배포된 소스코드가 완전히 다름 | 소스코드 변경 시 무거운 드로잉 툴(Visio)로 다이어그램을 수작업 갱신하는 것이 불가능 | PlantUML 코드를 Git 저장소에 소스코드와 함께 두고 CI 빌드 시 자동 렌더링 | 설계 문서와 코드의 일치성(동기화) 유지 |
| 복잡한 비즈니스 프레임워크 구조를 표준 UML 기호만으로 표현하기 어려워 오해 발생 | 도메인 특화 개념(Spring Controller, Service, Repository) 표현의 한계 | UML 확장 메커니즘인 스테레오타입(`<<Controller>>`) 및 프로파일 정의 | 설계 의도의 명확한 전달 및 가독성 제고 |

## 이렇게 출제된다
- 제93회 1교시: "UML(Unified Modeling Language)의 4대 목적과 주요 다이어그램 체계를 설명하시오." → 요구 포인트: 가시화/명세화/구축/문서화 4대 목적 + 구조/행위 다이어그램 분류
- 제87회 2교시: "UML 2.0에서 변경된 다이어그램의 특징과 확장 메커니즘을 설명하시오." → 요구 포인트: 복합 프래그먼트, 포트, 복합체 구조 + 3대 확장(Stereotype, Tagged Value, Constraint)

## 내 의견
- [문서 작성을 위한 형식적 UML 그리기 관행 척결] 개발이 다 끝난 뒤 납품 산출물을 맞추기 위해 리버스 엔지니어링으로 수백 장의 클래스 다이어그램을 역추출하여 인쇄하는 낭비 발생 → 나라면: 불필요한 산출물 작성을 배제하고, 아키텍처 논의가 필요한 핵심 유스케이스 시퀀스 다이어그램과 도메인 핵심 엔티티 클래스 다이어그램만 Git 텍스트 기반(PlantUML)으로 관리하는 린(Lean) 모델링 거버넌스 정립
