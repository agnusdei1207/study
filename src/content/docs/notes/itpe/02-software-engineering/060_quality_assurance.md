## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 품질 → **소프트웨어 품질보증(SQA)**

## 30초 인출

- 본질: 소프트웨어 제품이 명시된 요구사항과 조직의 표준 프로세스에 부합함을 보증하기 위해 소프트웨어 생명주기 전반에 걸쳐 계획, 감시, 평가 및 시정 조치를 수행하는 체계적 공학 활동
- 메커니즘: 품질 계획(QP: 목표·기준 수립) → 프로세스 보증(QA: 공정 감사·표준 준수) → 제품 품질 관리(QC: 정적 검토) → 동적 테스팅(Testing) → 피드백 및 시정 조치(CAPA)
- 통찰: 사후 테스트(QC)에만 의존할 경우 이미 누적된 결함의 재작업 비용이 급증하므로 프로세스 품질보증(QA)의 예방 활동과 CI/CD 자동화 품질 게이트(Quality Gate)의 조기 결합 필수

<details>
<summary>핵심 용어</summary>

- **SQA (Software Quality Assurance)** : 소프트웨어 엔지니어링 프로세스와 산출물이 정해진 표준과 품질 요구를 만족하는지 객관적으로 평가하는 독립적 품질 보증 체계
- **QP (Quality Planning, 품질 계획)** : 프로젝트 착수 시 품질 목표(결함 밀도, 테스트 커버리지)를 정의하고 이를 달성하기 위한 활동과 책임을 명시한 계획서
- **QC (Quality Control, 품질 관리)** : 요구사항 명세서, 설계서, 소스코드 등 완성된 산출물이 품질 기준을 충족하는지 검사하고 결함을 식별하는 활동 (인스펙션, 리뷰)
- **Quality Gate (품질 게이트)** : 소프트웨어 생명주기 각 단계(마일스톤) 전환 시 사전에 정의된 정량적 품질 통과 기준을 만족해야만 다음 단계로 승인하는 체크포인트
- **CAPA (Corrective and Preventive Action)** : 식별된 품질 부적합의 근본 원인을 제거하여 동일 결함의 재발을 방지하는 시정 및 예방 조치

</details>

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 품질보증의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 개발 프로젝트가 사전에 정의된 공학 표준, 프로세스 및 고객의 품질 요구사항을 충족하도록 프로세스의 수행 상태를 객관적으로 모니터링하고 제품 산출물의 무결성을 입증하는 전주기 품질 보증 활동 |
| 목적 | 결함의 사전 예방을 통한 총 품질 비용(Cost of Quality) 절감, 프로젝트 위험 조기 식별 및 고객 신뢰도 극대화 |

## Ⅱ. 소프트웨어 품질보증의 핵심 특징

| 특징 | 의미 |
|---|---|
| 예방 중심 활동 | 결함을 사후에 찾아내는 것에 그치지 않고 결함을 유발하는 프로세스 취약점을 사전에 차단 |
| 객관적 독립성 | 개발팀에 종속되지 않은 독립적인 SQA 조직이 경영진과 프로젝트 관리자에게 품질 상태를 직보 |
| 전 생명주기 적용 | 요구사항 도출부터 설계, 구현, 테스트, 배포, 유지보수 전 단계에 걸쳐 연속적으로 개입 |
| 표준 프레임워크 준거 | CMMI, ISO/IEC/IEEE 12207, ISO 9001 등 국제 표준 품질 관리 체계와 완벽히 정렬 |

## Ⅲ. SQA 전주기 프레임워크 및 품질 관리 체계

### QP - QA - QC - Testing의 상호작용 및 PDCA 품질 루프

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Plan (품질 계획 - QP)                                                │
│    - 품질 목표 설정 (결함 밀도 < 0.5건/FP, 문장 커버리지 > 85%)         │
│    - 품질보증 계획서(SQAP) 작성, 품질 게이트(Quality Gate) 기준 확정    │
└───────────────────┬─────────────────────────────────┬──────────────────┘
                    │                                 │
                    ▼                                 ▼
┌───────────────────────────────────┐ ┌──────────────────────────────────┐
│ 2. Do & Check: 프로세스 관점 (QA)  │ │ 3. Do & Check: 제품/산출물 관점 (QC) │
│ - 프로세스 준수 감사 (Audit)      │ │ - 정적 검토 (인스펙션, 워크스루) │
│ - 방법론 테일러링 준수 확인       │ │ - 동적 테스팅 (단위, 통합, 시스템)│
│ - 표준 코딩 컨벤션 준수율 점검    │ │ - 정적 코드 분석 (SonarQube)     │
└───────────────────┬───────────────┘ └──────────────────┬───────────────┘
                    │                                    │
                    └─────────────────┬──────────────────┘
                                      ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. Act (시정 및 예방 조치 - CAPA)                                      │
│    - 품질 부적합(Non-conformance) 보고서 발행 및 근본 원인 분석(RCA)   │
│    - 프로세스 개선 및 개발 표준 가이드라인 갱신 (Lessons Learned 자산화)│
└────────────────────────────────────────────────────────────────────────┘
```

### 생명주기 단계별 핵심 SQA 활동

| 개발 단계 | 주요 SQA 활동 | 핵심 검증 대상 및 산출물 | 품질 게이트(Quality Gate) 기준 |
|---|---|---|---|
| **요구분석** | 요구사항 명세 인스펙션, 추적성 확인 | 소프트웨어 요구사항 명세서(SRS) | 요구사항 검증 가능성 100%, RTM 매핑 완료 |
| **아키텍처 설계** | 아키텍처 평가(ATAM), 모듈성 검토 | 소프트웨어 아키텍처 설계서(SAD) | 품질 시나리오 통과, 인터페이스 정의 완료 |
| **상세설계/구현** | 코드 리뷰, 정적 분석 린팅 점검 | 소스코드, 단위 테스트 코드 | 코딩 컨벤션 위반 0건, 순환복잡도 $V(G) \le 10$ |
| **테스트** | 테스트 커버리지 및 결함 추이 분석 | 통합/시스템 테스트 결과 보고서 | 치명 결함(Blocker/Critical) 0건, 커버리지 달성 |
| **릴리스/운영** | 릴리스 승인 심의, 오픈 적합성 평가 | 릴리스 노트, 사용자 매뉴얼 | 잔존 결함 0건, 백업/롤백 계획 수립 완료 |

## Ⅳ. QP vs QA vs QC vs Testing 4대 품질 활동 비교

### 소프트웨어 품질 활동 간 역할 및 특성 비교

| 비교 항목 | 품질 계획 (QP) | 품질 보증 (QA) | 품질 관리 (QC) | 동적 테스팅 (Testing) |
|---|---|---|---|---|
| **핵심 성격** | **계획 및 기준 수립** | **프로세스 중심 (Process)** | **산출물 중심 (Product)** | **실행 기반 검증 (Execution)** |
| **주요 목적** | 프로젝트 품질 로드맵 확정 | 결함 예방 및 공정 개선 | 결함 식별 및 산출물 판정 | 실제 동작과 기대값 일치 확인 |
| **수행 주체** | PM, QA Lead | 독립적 SQA 감사자 | 동료 개발자, 리뷰어 | 전문 테스터, QA 엔지니어 |
| **수행 시점** | 프로젝트 착수 단계 | 전 생명주기 상시 감사 | 각 단계 산출물 완성 시점 | 구현 후 코드 빌드 시점 |
| **주요 기법** | 벤치마킹, 비용-편익 분석 | 프로세스 감사, 인과분석 | 인스펙션, 정적 분석 | 화이트박스, 블랙박스 테스트 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 프로젝트 마감 일정 압박으로 인해 SQA 품질 검토가 생략되거나 형식적 서명으로 전락 | 단계별 품질 게이트 미통과 시 다음 단계(배포)로의 기술적 전이를 원천 차단하는 CI 파이프라인 강제 |
| QA 활동이 단순 개발팀 감시 및 지적 위주로 운영되어 개발팀과의 심각한 갈등 초래 | QA 조직을 지적 조직이 아닌 테스트 자동화 및 인프라를 지원하는 '품질 활성화(Enabling)' 조직으로 전환 |
| 프로세스 준수 문서(페이퍼워크) 작성에 과도한 공수가 소모되어 실제 제품 개발 저해 | Jira, SonarQube, GitHub Actions 등 툴체인 연동을 통해 품질 증적 문서를 자동 수집·생성 |

## Ⅵ. 제언

DevSecOps 기반의 연속적 품질보증(Continuous QA) 파이프라인 및 AI 기반 결함 예측 엔진 도입

### DevSecOps 연속적 품질보증(Continuous QA) 파이프라인

```text
[개발자 코드 커밋 & PR]
       ↓
[CI 자동화 파이프라인: Phase 1 Quality Gate]
  ├─ 1. 컴파일 및 단위 테스트 실행 (Line Coverage >= 80%)
  ├─ 2. SonarQube 정적 코드 분석 (Security Hotspot 0건)
  └─ 3. 오픈소스 의존성 취약점 스캔 (Trivy)
       ↓ (통과 시 자동 병합)
[스테이징 배포 파이프라인: Phase 2 Quality Gate]
  ├─ 1. E2E 통합 테스트 (Playwright / Cypress)
  ├─ 2. 성능 부하 테스트 (k6: P95 < 500ms)
  └─ 3. DAST 동적 보안 침투 테스트 (OWASP ZAP)
       ↓ (SQA 책임자 자동 승인)
[프로덕션 카나리 무중단 배포 및 실시간 APM 관측]
```

### 품질 게이트(Quality Gate) 의사결정 체계

```text
마일스톤 완료 및 배포 심의
       ↓
[치명적(Blocker/Critical) 결함이 1건이라도 미해결 상태인가?]
       ├─ 예 ──→ [배포 보류 (Rollback/Hold)] → 즉각 핫픽스 수행
       └─ 아니오 ─→ [단위/통합 테스트 커버리지 목표(80%)를 달성했는가?]
                         ├─ 아니오 ─→ 테스트 코드 보강 완료 전까지 배포 차단
                         └─ 예 ───→ [소프트웨어 품질보증(SQA) 최종 승인 및 릴리스]
```

### 선택 근거: 전통적 감사형 QA와 제언 연속적 엔지니어링 QA 비교

| 구분 | 전통적 감사형 SQA (Audit-based) | 제언: 연속적 엔지니어링 SQA (Continuous) |
|---|---|---|
| 접근 방식 | 공정 마일스톤 시점의 수기 문서 감사 | CI/CD 파이프라인 내장형 자동화 품질 게이트 |
| 피드백 속도 | 감사 결과 통보까지 수주~수개월 소요 | 코드 커밋 즉시 수 분 내 정량적 품질 피드백 |
| 개발팀 관계 | 규정 강제로 인한 마찰과 업무 지연 유발 | 개발자 셀프서비스 품질 도구 제공으로 협업 극대화 |
