## 연관 키워드

- 소프트웨어 품질보증(SQA, Software Quality Assurance), 품질제어(QC)
- ISO/IEC 25010, CMMI PPQA, 품질 특성, 품질 게이트(Quality Gate)
- Shift-Left, DRE, DORA 지표, QE(Quality Engineering)

## Ⅰ. 소프트웨어 품질보증(SQA)의 개요

- 핵심 요약 : 생명주기 전반의 프로세스 준수를 계획·감시·평가·개선해 품질 요구사항 충족에 대한 확신을 주는 예방 중심 공학 활동.
- 개념 : **소프트웨어 품질보증** (SQA, Software Quality Assurance)은 제품이 정의된 품질 요구사항과 표준을 충족한다는 확신을 주기 위해 **소프트웨어 생명주기** (SDLC, Software Development Life Cycle) 전반에서 프로세스 준수 여부를 계획·감시·평가·개선하는 체계적 공학 활동이다.
- 배경 및 필요성 : 개발을 마친 뒤에만 결함을 찾는 품질 통제(QC, Quality Control)는 결함이 쌓인 뒤에 발견되어 수정 비용이 커지므로, 프로세스 단계에서 결함 유입을 막는 품질 보증(QA, Quality Assurance) 체계가 필요하다.
- 주요 목적 : 프로세스와 산출물의 표준 준수를 검증하고, 결함을 예방해 품질 비용을 줄이며, 이해관계자에게 품질에 대한 신뢰를 제공하는 것.

## Ⅱ. SQA의 특징 및 장점

- 핵심 요약 : 프로세스 중심·예방 지향의 생명주기 전반 활동이며, 표준 기반 감사와 이원화된 보증 체계로 운영되는 구조.

1. 예방 지향 : 결함을 찾기보다 프로세스 오류를 사전에 차단 → 후행 재작업 비용 절감.
2. 생명주기 전반의 반복 : 계획·감시·평가·개선을 단계마다 반복 → 요구분석부터 운영까지 품질 근거 누적.
3. 이원 보증 체계 : 프로세스 품질보증과 제품 품질보증을 병행 → 절차 준수와 산출물 품질을 동시에 확인.
4. 표준 기반 수행 : **ISO/IEC 25010** 품질 모델과 CMMI(Capability Maturity Model Integration)의 PPQA(Process & Product Quality Assurance) 영역을 기준으로 판단 → 객관적 평가 근거 확보.
5. 독립 감사 : 개발 조직과 분리된 관점에서 감사(Audit)를 수행 → 일정 압박에 흔들리지 않는 객관적 검증.

## Ⅲ. SQA의 구조 (흐름)

- 핵심 요약 : SQA가 QC와 테스팅을 포괄하는 계층 구조와, 계획에서 개선으로 이어지는 순환형 활동 사이클.

```text
[ 품질 활동의 계층 구조 ]

SQA : 소프트웨어 품질보증
 - 프로세스 중심, 예방 지향
 - 표준 수립, 감사, 준수 검증
   ↓ 포함
QC : 품질 통제
 - 산출물 중심, 검출 지향
 - 코드 리뷰, 인스펙션
   ↓ 포함
Testing : 테스트
 - 실행을 통한 결함 식별·수정
```

```text
[ SQA 활동 사이클 ]

품질 계획 수립
   ↓
표준·절차 정의
   ↓
프로세스 감시와 감사(Audit)
   ↓
부적합 판정과 시정 조치
   ↓
개선 및 표준 갱신 → 계획 수립으로 순환
```

- **프로세스 품질보증** (Process QA) : 개발 절차, 표준 가이드라인, 형상관리, 변경 통제 프로세스가 지켜지는지 주기적으로 감사.
- **제품 품질보증** (Product QA) : 명세서, 설계서, 소스코드, 실행 파일 같은 산출물이 품질 기준에 맞는지 리뷰하고 정량 측정.
- ISO/IEC 25010은 8개 품질 특성으로 제품 품질을 구분하며, 각 특성은 다음과 같은 하위 요소로 검증한다.

| 품질 특성 | 하위 품질 요소 및 핵심 검증 기준 |
| --- | --- |
| 기능 적합성(Functional Suitability) | 기능 완전성, 기능 정확성, 기능 적절성 |
| 성능 효율성(Performance Efficiency) | 시간 반응성(응답시간·처리량), 자원 활용성(CPU(Central Processing Unit)·메모리), 용량성 |
| 호환성(Compatibility) | 공존성(Co-existence), 상호운용성(Interoperability) |
| 사용성(Usability) | 적합성 인지성, 학습 용이성, 조작 용이성, 사용자 오류 보호, UI(User Interface) 심미성 |
| 신뢰성(Reliability) | 성숙도, 무고장성, 가용성, 장애 허용성, 회복 용이성 |
| 보안성(Security) | 기밀성, 무결성, 부인방지, 책임추적성, 인증성 |
| 유지보수성(Maintainability) | 모듈성, 재사용성, 분석 용이성, 수정 용이성, 시험 용이성 |
| 이식성(Portability) | 적응성, 설치 용이성, 대체 용이성 |

## Ⅳ. SQA, QC, 테스팅의 비교

- 핵심 요약 : SQA는 프로세스 예방, QC는 산출물 검출, 테스팅은 실행 기반 결함 확인을 맡는 역할 분담 구조.

| 비교 항목 | SQA | QC | 테스팅 |
| --- | --- | --- | --- |
| 초점 | 프로세스 중심 | 산출물 중심 | 실행 기반 동작 검증 |
| 지향점 | 예방(Prevention) | 검출(Detection) | 결함 식별과 수정 확인 |
| 주요 활동 | 표준 수립, 감사, 프로세스 준수 검증 | 코드 리뷰, 인스펙션, 정량 측정 | 단위·통합·시스템 테스트 수행 |
| 수행 시점 | 생명주기 전반 | 산출물 생성 이후 | 실행 가능한 빌드 이후 |

## Ⅴ. SQA의 한계와 방안

- 핵심 요약 : 결함 조기 예방과 품질 신뢰 제공이라는 장점과, 관료주의화·후반 병목·형식적 지표라는 한계가 공존.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 프로세스 통제 위주의 관료주의 | 체크리스트와 증빙 서류 준수에 매몰되어 실제 코드 품질 개선이 뒤로 밀리고 개발 생산성 저하 | 감사형 QA에서 개발을 직접 지원하는 **QE** (Quality Engineering)로 전환, CI/CD(Continuous Integration/Continuous Delivery) 파이프라인에 정적 분석·자동화 테스트 내재화 | 자동 검사 통과율, 증빙 제출 대비 결함 감소율 |
| 후반부 품질 병목 (**시프트 레프트** (Shift-Left) 부재) | 요구·설계 단계의 결함 예방 활동이 없어 테스트 직전에 아키텍처 결함이 발견되고 출시 일정 연기 | 요구 도출과 아키텍처 리뷰부터 SQA 인력이 참여, TDD·BDD와 코드 리뷰 정량화를 조기에 강제하는 **품질 게이트** (Quality Gate) 설정 | 단계별 게이트 통과율, 후반 발견 결함 비율 |
| 형식적 지표와 비즈니스 연계 부족 | 코드 라인 수, 테스트 실행 건수만 수집해 장애율·전환율과의 인과관계를 입증하지 못함 | **결함 제거 효율** (DRE, Defect Removal Efficiency), 결함 밀도, MTBF·MTTR 같은 신뢰성 지표 표준화, DORA(DevOps Research and Assessment) 핵심 지표와 사용자 만족도를 묶은 통합 품질 대시보드 운영 | DRE, 장애 복구 시간(MTTR) |

## Ⅵ. 고도화된 SQA 정착을 위한 기술사적 제언

- 핵심 요약 : 자동화된 품질 게이트를 파이프라인에 내재화하고, 독립성과 협력을 함께 갖춘 SQA 거버넌스를 세우는 것이 핵심.
- 파이프라인 내 자동화 게이트 : 사후 감리에 의존하던 방식에서 벗어나, 빌드 단계에서 정적 코드 분석, 보안 취약점 점검, 테스트 커버리지 기준을 자동 판정하고 기준 미달 시 배포를 멈추는 구조로 옮겨 가야 한다.
- 독립성과 협력의 병행 : 품질보증 조직은 경영진 직속으로 두어 개발 일정 압박에서 독립성을 지키되, 규제자에 머물지 않고 개발팀이 쓰는 품질 도구와 프레임워크를 함께 제공하는 협력 조직이어야 한다.

## Ⅶ. 결론

- 핵심 요약 : SQA는 사후 검출이 아닌 예방 중심의 생명주기 전반 품질 거버넌스다.
- 시사점 : SQA의 실효성은 자동화된 품질 게이트와 엔지니어링 협력형 조직으로의 전환에 달려 있다.
