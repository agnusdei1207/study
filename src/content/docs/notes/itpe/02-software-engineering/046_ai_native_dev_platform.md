## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어 공학 → 지능형 개발환경 → **AI 네이티브 개발 플랫폼**

## 30초 인출

- 본질: **AI 네이티브 개발 플랫폼**은 저장소 문맥과 개발 도구를 이용해 소프트웨어 변경을 계획·수행·검증하는 개발환경
- 메커니즘: 작업·권한 지정 → 문맥 수집·계획 → 격리된 도구 실행 → 품질 검증 → 사람 승인·수정
- 핵심: 자동화 범위와 실행 권한을 제한하고 변경 근거·검증 결과를 남기는 통제

<details>
<summary>핵심 용어</summary>

- **AI 네이티브 개발 플랫폼**: AI 에이전트가 저장소 문맥과 개발 도구를 활용해 변경을 수행하고 검증하는 개발환경
- **AI 에이전트**: 목표에 따라 도구를 호출하고 실행 결과를 바탕으로 다음 행동을 선택하는 소프트웨어 구성요소
- **Context Engineering**: 작업에 필요한 코드·문서·정책을 선별해 모델에 제공하는 설계
- **Sandbox(격리 실행환경)**: 실행의 파일·프로세스·네트워크 권한을 제한하는 환경
- **Quality Gate**: 테스트·분석 결과가 정해진 조건을 통과해야 다음 단계로 진행시키는 검사점
- **Human-in-the-loop**: 사람이 승인·중단·예외 판단을 맡는 통제 방식

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **AI 네이티브 개발 플랫폼**은 AI 에이전트가 저장소 문맥과 개발 도구를 활용해 소프트웨어 변경을 계획·수행·검증하는 개발환경 |
| 목적 | 반복적인 구현·검증 부담 감소와 변경의 품질·보안·추적성 확보 |

### Ⅱ. 구성과 실행 흐름

```text
작업 목표·권한 범위 설정
    ↓
코드·정책 문맥 수집·계획
    ↓
격리된 환경에서 변경 실행
    ↓
테스트·보안·정책 검사
    ├─ 실패 → 근거로 변경안 수정
    └─ 통과 → 담당자 검토·병합
```

### Ⅲ. 핵심 통제

| 통제 | 적용 내용 |
|---|---|
| 최소 권한 | 작업별 파일·명령·네트워크 허용 범위 제한 |
| 독립 검증 | 생성 과정과 분리된 테스트·정적 분석·보안 검사 |
| 사람의 승인 | 배포·권한 변경·민감정보 접근 등 고위험 작업의 승인·중단 |

제언: 검증 증거와 변경 범위가 확인된 작업부터 제한된 자동 실행으로 전환.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **AI 네이티브 개발 플랫폼**은 AI 에이전트가 저장소 문맥과 개발 도구를 활용해 소프트웨어 변경을 계획·수행·검증하는 개발환경 |
| 목적 | 반복적인 구현·검증 부담 감소와 변경의 품질·보안·추적성 확보 |

## Ⅱ. 플랫폼 구성요소와 책임

| 구성요소 | 역할 | 주요 경계 |
|---|---|---|
| 모델·에이전트 | 요청 해석, 계획 수립, 도구 선택 | 정해진 작업 목표·시도 한도 |
| 문맥 계층 | 저장소 코드·문서·정책 검색 | 출처·최신성·민감도 확인 |
| 도구 연결부 | 편집·빌드·테스트·형상관리 호출 | 허용된 명령·인자만 전달 |
| 격리 실행환경 | 변경·명령 실행 | 파일·네트워크·자원 권한 제한 |
| 품질 검사 | 테스트·정적 분석·보안 정책 확인 | 통과 기준·실패 근거 기록 |
| 담당자 | 범위·예외·고위험 변경 승인 | 최종 검토와 중단 권한 |

## Ⅲ. 계획부터 변경 검토까지

```text
요청·완료 조건 확인
    ↓
관련 코드·정책 검색
    ↓
변경안 작성·권한 내 실행
    ↓
테스트·보안 검사
    ├─ 실패 → 변경안 수정·재검사
    └─ 통과 → 담당자 검토·병합
```

각 단계에서 사용한 문맥, 실행 도구, 검사 결과를 변경과 함께 보존해 검토 가능성을 확보.

## Ⅳ. AI 보조 개발과의 차이

| 비교 기준 | AI 보조 개발 | AI 네이티브 개발 |
|---|---|---|
| 작업 범위 | 코드 조각·함수 제안 중심 | 이슈·변경 작업 단위까지 확장 가능 |
| 도구 실행 | 개발자가 제안을 실행·검토 | 권한이 허용된 도구를 에이전트가 실행 |
| 피드백 | 개발자가 결과를 판단 | 검사 결과를 다음 계획에 반영 |
| 통제 지점 | 제안 수락·수정 | 도구 권한·격리·품질 검사·사람 승인 |
| 증거 | 코드 제안과 대화 내용 | 변경 내역·실행 기록·검증 결과 |

## Ⅴ. 품질·보안 통제

| 위험 | 대응 |
|---|---|
| 저장소 문맥 오류로 인한 잘못된 변경 | 근거 문서·코드 출처 확인과 담당자 검토 |
| 과도한 파일·명령·네트워크 권한 | 작업별 최소 권한과 격리 실행환경 적용 |
| 생성 코드의 결함·취약점 | 독립 테스트·정적 분석·의존성 보안 검사 통과 후 병합 |
| 민감정보 노출 | 비밀정보 탐지와 민감정보 접근 제한 |
| 검사 실패의 반복·확대 | 시도 횟수·실행 시간 제한과 실패 시 사람에게 이관 |

## Ⅵ. 기술사적 제언 — 검증 수준에 따른 자동화 범위 설정

| 한계 | 해결 방안 |
|---|---|
| 작업 위험도와 검증 증거가 다른데도 동일한 자동 실행 권한을 부여할 가능성 | 변경 위험과 검사 결과에 따라 제안·격리 실행·사람 승인 단계를 구분하고, 배포·권한·민감정보 변경은 담당자 승인 대상으로 유지 |
