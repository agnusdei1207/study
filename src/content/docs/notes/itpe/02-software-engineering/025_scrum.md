## 연관 키워드

- 스크럼(Scrum), 애자일(Agile), 스프린트(Sprint), 증분(Increment), 경험주의 3기둥
- 제품 책임자(Product Owner), 스크럼 마스터(Scrum Master), 제품 백로그, 완료의 정의(DoD), 벨로시티(Velocity)

## Ⅰ. 스크럼의 개요

- 핵심 요약 : 짧은 반복 주기로 동작하는 소프트웨어 증분을 점진적으로 인도하는 대표적 애자일 프레임워크.
- 개념 : 요구사항이 불확실하고 자주 바뀌는 환경에서, 자기 조직화된 팀이 **스프린트**(Sprint)라는 고정된 반복 주기 동안 동작하는 소프트웨어 증분(Increment)을 만들어 점진적으로 인도하는 애자일(Agile) 프레임워크 (**스크럼**, Scrum).
- 배경 및 필요성 : 폭포수 모델은 긴 피드백 주기 때문에 요구사항 변경이 뒤늦게 드러나 납기 지연과 인도 실패 위험이 커지므로, 짧은 주기로 검증하는 방식이 필요함.
- 주요 목적 : 투명성(Transparency), 점검(Inspection), 적응(Adaptation)의 경험주의 3대 기둥에 기반해 불확실성을 관리.

## Ⅱ. 스크럼의 특징 및 장점

- 핵심 요약 : 3가지 역할, 5가지 이벤트, 3가지 산출물로 이루어진 3-5-3 체계가 짧은 피드백과 품질 기준을 만드는 구조.

1. 3가지 역할 : 제품 책임자(PO, Product Owner)는 비즈니스 가치를 기준으로 **제품 백로그**를 관리하고, 스크럼 마스터는 원칙을 지키며 장애물을 제거하고, 개발팀은 교차 기능을 갖춘 자기 조직화 팀으로 일함.
2. 5가지 이벤트 : 스프린트, 스프린트 계획, 일일 스크럼(15분), 스프린트 리뷰, 스프린트 회고로 구성 → 계획, 점검, 개선이 정해진 리듬으로 반복됨.
3. 3가지 산출물 : 제품 백로그, 스프린트 백로그, 증분으로 구성 → 해야 할 일과 현재 목표, 인도 가능한 결과가 항상 보임.
4. **완료의 정의** (DoD, Definition of Done) : 증분이 인도 가능한 상태로 인정받는 기준을 팀이 합의 → 품질 미달 증분의 릴리스를 막음.
5. 자기 조직화 : 지시 대신 팀 주도로 작업을 나누고 결정 → 책임감과 의사결정 속도가 높아짐.

## Ⅲ. 스크럼의 구조 (흐름)

- 핵심 요약 : 제품 백로그에서 증분 리뷰와 회고까지 이어지는 스프린트 반복 흐름.

```text
[ 스프린트 반복 흐름 ]

제품 백로그 (제품 책임자가 관리)
      ↓
스프린트 계획
  스프린트 백로그 도출
      ↓
스프린트 실행 (고정 주기)
  일일 스크럼 (15분)
      ↓
증분 완성 (완료의 정의 충족)
      ↓
스프린트 리뷰 → 스프린트 회고
```

```text
[ 스크럼 3-5-3 체계 ]

역할 3 : 제품 책임자 / 스크럼 마스터 / 개발팀
이벤트 5 : 스프린트, 계획, 일일 스크럼,
           리뷰, 회고
산출물 3 : 제품 백로그 / 스프린트 백로그 / 증분
```

## Ⅳ. 스크럼 핵심 운영 메커니즘의 비교

- 핵심 요약 : 백로그 관리, 일일 스크럼, 완료의 정의, 회고는 각각 성과 기준과 실패 증상이 다르므로 따로 점검해야 함.

| 구성요소 | 핵심 활동과 성과 기준 | 실패 시 증상 |
| --- | --- | --- |
| 제품 백로그 관리 | DEEP 원칙(Detailed, Estimated, Emergent, Prioritized) 준수 | 우선순위 혼선, 일정 지연 |
| 일일 스크럼 | 어제 한 일, 오늘 할 일, 장애 요인 공유 | 보고 자리로 변질, 시간 낭비 |
| 완료의 정의 | 빌드, 테스트, 정적 분석, 코드 리뷰, 배포 기준 충족 | 품질 미달 증분 인도, 회귀 결함 증가 |
| 스프린트 회고 | Keep, Problem, Try 관점의 개선 과제 도출 | 불만 누적, 개선 정체 |

## Ⅴ. 스크럼의 한계와 방안

- 핵심 요약 : 빠른 피드백의 장점과 달리, 지표 오용, 제품 책임자 병목, 행사의 형식화가 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 지표 오용 | 스토리 포인트와 벨로시티를 개인 성과로 평가 → 점수 부풀리기와 기술 부채 방치 | 벨로시티는 팀 용량 산정에만 사용, 리드타임과 사이클타임 같은 흐름 지표 활용 | 리드타임, 사이클타임 |
| 제품 책임자 병목 | 의사결정 권한이 없거나 도메인 이해가 부족 → 요구사항 정의 지연 | 실질 권한을 가진 전담 PO 임명, INVEST(Independent, Negotiable, Valuable, Estimable, Small, Testable) 원칙 기반 백로그 정제 정례화 | 백로그 정제율, 질문 응답 지연 |
| 행사의 형식화 | 스탠드업과 회고가 장황한 보고 회의로 변질 → 개발 집중 시간 침해 | 일일 스크럼 15분 타임박싱 준수, 장애물 제거 중심의 스크럼 마스터 역할 강화 | 행사 소요 시간, 팀 만족도 |

## Ⅵ. 대규모 환경에서의 기술사적 제언

- 핵심 요약 : 여러 팀을 묶는 대규모 애자일 체계를 세우고, 지표 오용을 막으며, 기술 품질 기준을 DoD에 포함하는 방향.
- 대규모 프레임워크의 도입 : 여러 스크럼 팀이 함께 일하는 대형 사업에서는 SAFe나 LeSS 같은 대규모 애자일 프레임워크를 골라 팀 간 의존성을 Scrum of Scrums 회의로 조율한다.
- 지표의 목적 한정 : 벨로시티를 팀 간 실적 비교에 쓰지 않고, 지속 가능한 개발 속도를 유지하며 실패를 공유할 수 있는 심리적 안전감(Psychological Safety)을 조직 문화로 정착시킨다.
- 기술 품질의 DoD 편입 : 정적 분석, 자동화 테스트, CI/CD 파이프라인을 완료의 정의에 넣어 프로세스와 기술 품질을 함께 확보한다.

## Ⅶ. 결론

- 핵심 요약 : 스크럼은 경험주의에 기반해 반복적으로 가치를 인도하는 애자일 프레임워크.
- 시사점 : 지표를 본래 목적에 맞게 쓰고 행사를 실질화하며 DoD를 지킬 때 스크럼의 성숙도가 높아짐.
