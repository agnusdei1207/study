## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 개발 방법론 → **스크럼(Scrum)**

## 30초 인출

- 본질: 복잡하고 가변적인 환경에서 팀이 1개월 이하의 고정된 기간(Sprint)마다 동작 가능한 제품 증분(Increment)을 점진적으로 인도하는 경험주의(Empiricism) 기반 경량 프레임워크
- 메커니즘: 3대 기둥(투명성, 점검, 적응) + 3대 책무(PO, SM, Developers) + 5대 이벤트(Sprint, Planning, Daily, Review, Retrospective) + 3대 산출물 및 약속(PB-Product Goal, SB-Sprint Goal, Increment-DoD)
- 통찰: 형식적 의식에만 치중할 경우 기술 부채 누적과 품질 저하가 발생하므로 명확한 완료의 정의(DoD) 수립과 회고 기반의 지속적 엔지니어링 실천법 통합 필수

<details>
<summary>핵심 용어</summary>

- **Scrum(스크럼)** : 복잡한 적응형 문제를 해결하고 지속해서 최고의 가치를 창출하도록 돕는 경험주의 기반 경량 애자일 프레임워크
- **Product Owner (PO)** : 제품의 비즈니스 가치를 극대화하고 제품 백로그의 우선순위를 결정하고 관리하는 단일 의사결정권자
- **Scrum Master (SM)** : 스크럼 가치와 원칙을 팀과 조직에 코칭하고 팀의 진행 장애 요소를 제거하는 서번트 리더
- **Sprint(스프린트)** : 동작 가능한 잠재적 출시 제품 증분을 완성하기 위한 1~4주의 고정된 타임박스(Time-box)
- **DoD(Definition of Done, 완료의 정의)** : 증분이 프로덕션 환경에 배포 가능한 품질 수준을 충족했음을 보증하는 체크리스트 형태의 공통 약속
- **Product Backlog / Sprint Backlog** : 제품 전체의 요구사항 목록과 이번 스프린트에서 완수하기로 선정한 세부 개발 작업 목록

## 2~4교시 25점 답안

## Ⅰ. 스크럼의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 복잡하고 불확실성이 높은 소프트웨어 개발 환경에서 1개월 이하의 고정된 스프린트(Sprint) 반복을 통해 동작 가능한 제품 증분을 지속적으로 제공하는 경험주의 기반 애자일 프레임워크 |
| 목적 | 투명한 가시성 확보와 빠른 피드백 루프를 통해 제품의 비즈니스 가치 극대화 및 시장 적응력 제고 |

## Ⅱ. 스크럼의 핵심 특징

| 특징 | 의미 |
|---|---|
| 경험주의 3대 기둥 | **투명성(Transparency)**, **점검(Inspection)**, **적응(Adaptation)** 을 기반으로 불확실성 통제 |
| 5대 핵심 가치 | 확약(Commitment), 용기(Courage), 집중(Focus), 개방성(Openness), 존중(Respect) 공유 |
| 고정된 타임박스 | 모든 이벤트의 최대 시간을 고정하여 불필요한 회의 오버헤드를 줄이고 업무 리듬 유지 |
| 자기관리형 팀 | 외부의 지시 없이 팀 내부에서 작업을 수행할 주체, 방법, 일정을 스스로 결정 |

## Ⅲ. 스크럼의 3·5·3 체계 및 스프린트 라이프사이클

### 스프린트 전주기 이벤트 및 산출물 연계 흐름

```text
                                  [스프린트 백로그]
                                         │
┌──────────────────┐                     ▼
│  제품 백로그     │   스프린트 계획   ┌──────────────────────────────────────────┐
│  (Product Backlog) ───────────────→ │ [일일 스크럼 (Daily Scrum, 15분)]        │
└──────────────────┘                  │        │                                 │
         ▲                            │        ▼                                 │
         │                            │  스프린트 실행 및 개발 (1~4주 타임박스)    │
         │                            └────────────────────┬─────────────────────┘
         │                                                 │
         │                                                 ▼
         │                                     [완료의 정의(DoD) 검증]
         │                                                 │
         │     스프린트 리뷰 (Sprint Review)               ▼
         │ ←── [이해관계자 피드백 & 백로그 갱신] ←── [출시 가능한 제품 증분]
         │                                                 │
         │     스프린트 회고 (Sprint Retrospective)        │
         └──── [팀 프로세스·엔지니어링 개선점 도출] ◄───────┘
```

### 스크럼 3대 책무·5대 이벤트·3대 산출물 구조

| 체계 구분 | 구성 요소 | 핵심 역할 및 활동 규약 |
|---|---|---|
| **3대 책무 (Accountabilities)** | **Product Owner (PO)** | 제품 가치 극대화, 제품 목표 수립, 제품 백로그 우선순위 정렬 및 투명한 공개 |
| 3대 책무 (Accountabilities) | **Scrum Master (SM)** | 스크럼 프레임워크 준수 지원, 개발팀의 방해/장애물(Impediment) 제거, 조직 코칭 |
| 3대 책무 (Accountabilities) | **Developers** | 스프린트 백로그 계획 및 실행, DoD를 충족하는 사용 가능한 제품 증분 완성 |
| **5대 이벤트 (Events)** | **Sprint** | 모든 이벤트의 상위 컨테이너 역할을 하는 1개월 이하의 고정된 반복 주기 |
| 5대 이벤트 (Events) | **Sprint Planning** | 스프린트 목표 수립, 백로그 선정 및 세부 태스크 분해 (월간 스프린트 기준 최대 8시간) |
| 5대 이벤트 (Events) | **Daily Scrum** | 스프린트 목표 달성 진척도 점검 및 당일 작업 계획 조율 (매일 15분 타임박스) |
| 5대 이벤트 (Events) | **Sprint Review** | 완성된 증분을 시연하고 비즈니스 피드백을 수렴하여 제품 백로그 조정 (최대 4시간) |
| 5대 이벤트 (Events) | **Sprint Retrospective** | 사람, 관계, 프로세스, 도구 측면의 개선점을 식별하고 실행 계획 도출 (최대 3시간) |
| **3대 산출물과 약속 (Commitments)** | **Product Backlog** | 시스템에 필요한 모든 요구사항 목록 (약속: **Product Goal, 제품 목표**) |
| 3대 산출물과 약속 (Commitments) | **Sprint Backlog** | 개발팀이 이번 주기에 수행할 항목과 계획 (약속: **Sprint Goal, 스프린트 목표**) |
| 3대 산출물과 약속 (Commitments) | **Increment** | 스프린트 동안 완성된 가치 있는 산출물 (약속: **Definition of Done, 완료의 정의**) |

## Ⅳ. 예측형(폭포수) 모델 vs 경험형(스크럼) 프레임워크 비교

### 개발 패러다임별 핵심 요소 비교

| 비교 항목 | 전통적 폭포수 모델 (Waterfall) | 스크럼 프레임워크 (Scrum) |
|---|---|---|
| **프로젝트 관리 철학** | 계획 주도형 (Predictive), 사전 통제 중심 | **경험주의 (Empirical)**, 점검과 적응 중심 |
| **요구사항 통제** | 분석 단계에서 확정 후 엄격한 변경 통제 | 스프린트마다 지속적인 백로그 정제 및 변경 수용 |
| **릴리스 주기** | 프로젝트 최종 단계에서 일괄 릴리스 | 매 스프린트 종료 시 잠재적 출시 가능 증분 인도 |
| **품질 검증 시점** | 개발 후반부 통합 테스트 단계 집중 | 매일 단위 테스트, CI 자동화, 증분별 DoD 검증 |
| **팀 조직 구조** | 직무별 분업 체계 (기획/설계/개발/QA 분리) | 기능 횡단적(Cross-functional) 단일 협력 팀 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 스프린트 주기 내 기능 구현에만 집중하여 발생하는 아키텍처 부식 및 기술 부채 누적 | 완료의 정의(DoD)에 단위 테스트 커버리지, 코드 린트, 정적 분석 통과 기준 강제 |
| 일일 스크럼이 단순 실적 보고 회의로 변질되어 팀 협업 및 장애 해결 기능 약화 | 어제 한 일 보고를 지양하고 스프린트 목표 달성 저해 요소와 협업 조율에 집중 |
| 스프린트 중 빈번한 외부 요구사항 주입으로 인한 팀 몰입도 저하와 스프린트 실패 | 스프린트 목표를 침해하는 요구사항 변경은 다음 백로그로 이관하고 PO의 완충 역할 강화 |

## Ⅵ. 제언

완료의 정의(DoD)와 준비의 정의(DoR)의 이중 통제 체계 및 대규모 스크럼 확장을 통한 엔터프라이즈 애자일 거버넌스

### DoR과 DoD 기반의 품질 통제 파이프라인

```text
[요구사항 도출]
       ↓
[DoR (Definition of Ready) 검증]
  ├─ 사용자 스토리 명확성 확인
  ├─ 인수 조건(Acceptance Criteria) 명세
  └─ 스토리 포인트 추정 완료
       ↓ (충족 시 스프린트 계획 진입)
[스프린트 개발 및 자동화 검증]
       ↓
[DoD (Definition of Done) 검증]
  ├─ 단위/통합 테스트 자동화 통과
  ├─ 보안 취약점 정적 분석(SAST) 통과
  ├─ 코드 리뷰 및 머지 완료
  └─ 스테이징 환경 배포 및 검증
       ↓
[출시 가능한 제품 증분 완성]
```

### 대규모 스크럼 확장(Nexus / LeSS / SAFe) 체계

```text
비즈니스 비전 및 엔터프라이즈 에픽
       ↓
Scrum of Scrums / Nexus Integration Team
       ├─ 다수 스크럼 팀 간 교차 의존성(Cross-Team Dependency) 사전 조율
       ├─ 통합 아키텍처 및 공통 라이브러리 가이드라인 제공
       └─ 전체 팀 통합 빌드 및 종단간(E2E) 자동화 테스트 파이프라인 관리
       ↓
단일 통합 프로덕션 증분 릴리스
```

### 선택 근거: 스크럼 단독 적용과 확장 애자일 프레임워크 비교

| 구분 | 단위 스크럼 (Single Team) | 제언: 확장 애자일 프레임워크 (Nexus / SAFe) |
|---|---|---|
| 적용 규모 | 10명 이하의 단일 독립 개발팀 | 수십~수백 명의 복수 팀 및 엔터프라이즈 환경 |
| 의존성 관리 | 팀 내부 커뮤니케이션으로 자체 해결 | Nexus/SoS 미팅을 통한 팀 간 인터페이스 사전 조율 |
| 릴리스 거버넌스 | 팀별 개별 판단에 따라 릴리스 | 릴리스 트레인(ART) 및 전사 통합 파이프라인 관리 |
