## 연관 키워드

- 유스케이스 다이어그램(Use Case Diagram), 유스케이스 명세서(Use Case Specification), 액터(Actor), 시스템 경계(System Boundary)
- 포함(Include), 확장(Extend), 일반화(Generalization), 기본 흐름(Basic Flow), 대안 흐름(Alternative Flow), 예외 흐름(Exception Flow)

## Ⅰ. 유스케이스 다이어그램의 개요

- 핵심 요약 : 사용자(액터) 관점에서 시스템이 제공할 기능과 상호작용을 외부적 시각으로 모델링한 UML 행위 다이어그램.
- 개념 : 사용자(액터)의 관점에서 시스템이 제공해야 하는 기능과 상호작용을 외부적 시각에서 모델링한 UML(Unified Modeling Language) 행위 다이어그램이자, 각 기능 시나리오를 텍스트로 정밀하게 기술한 명세 문서.
- 배경 및 필요성 : 시스템 개발 초기 단계에서 발주자, 현업 실무자, 개발자 간의 기능적 요구사항 범위의 직관적 합의 및 추후 테스트 케이스 도출 근거 확보 필요.
- 주요 목적 : 시스템 범위(Scope)의 명확화와 기능별 상호작용의 표준화된 시각화.
- 4대 구성요소 : 시스템 경계(System Boundary), 액터(Actor), 유스케이스(Use Case), 관계(Relationship).

## Ⅱ. 유스케이스 다이어그램의 특징

- 핵심 요약 : 액터 중심의 외부 조망과 4대 관계, 다이어그램-명세서 이원 문서 구조가 특징.
1. 액터 중심 모델링 : 시스템 경계 외부에서 기능을 조망하는 외부적 시각.
2. 4대 구성요소 : 시스템 경계(System Boundary)·액터(Actor)·유스케이스(Use Case)·관계(Relationship)의 조합.
3. 4대 관계 : 연관(Association)·포함(Include)·확장(Extend)·일반화(Generalization).
4. 이원 문서 구조 : 다이어그램(범위 정의)과 유스케이스 명세서(상세 흐름)의 상호 보완.
5. 테스트 연계 기반 : 기본 흐름, 대안 흐름, 예외 흐름의 테스트 케이스 도출 근거.

## Ⅲ. 유스케이스 다이어그램의 구조 (흐름)

- 핵심 요약 : 4대 관계 모델과 다이어그램→명세서→상세 설계→테스트의 연계 흐름.

```text
[ 유스케이스 4대 관계 모델 ]
[ 액터: 고객 ] --연관--> (시스템 경계 내부)

시스템 경계 (System Boundary):
   [상품 주문] --<<include>>--> [사용자 인증]
        ▲
        ┆ <<extend>>
   [쿠폰 적용]

   [결제 수단] <──<<generalization>>── [카드 결제]
```

```text
[ 요구사항 모델링 연계 흐름 ]
유스케이스 다이어그램 (범위 정의)
        ↓
유스케이스 명세서 (기본/대안/예외 흐름)
        ↓
액티비티/시퀀스 다이어그램 (상세 설계)
        ↓
블랙박스 테스트 케이스 (경로별 매핑)
```

- 유스케이스 명세서의 필수 구조 :

| 항목 | 상세 내용 및 기술 방법 |
|---|---|
| 유스케이스 식별자 및 이름 | UC-01: 상품 주문 (명확한 동사형 표기) |
| 주 액터 및 부 액터 | 일반 고객 (주 액터), 결제 PG사 / 배송 시스템 (부 액터) |
| 사전 조건 (Pre-conditions) | 사용자가 로그인되어 있고 장바구니에 1개 이상의 상품이 담겨 있어야 함 |
| 사후 조건 (Post-conditions) | 주문 데이터가 생성되고, 재고가 차감되며, 주문 완료 알림 발송 |
| 기본 흐름 (Basic Flow) | 정상적인 성공 시나리오의 1단계부터 단계별 기술 (Happy Path) |
| 대안 흐름 (Alternative Flow) | 조건에 따른 다른 성공 경로 (예: 마일리지 전액 결제) |
| 예외 흐름 (Exception Flow) | 오류 발생 시 처리 경로 (예: 잔액 부족, 결제 타임아웃, 재고 부족) |

## Ⅳ. 유스케이스 4대 관계의 비교

- 핵심 요약 : 연관은 상호작용, 포함은 필수 재사용, 확장은 조건부 부가, 일반화는 상속의 구분.

| 관계 | 표기법 | 의미 및 목적 | 예시 |
|---|---|---|---|
| 연관 (Association) | 실선 | 액터와 유스케이스 간의 상호작용 | 고객—상품 주문 |
| 포함 (Include) | 점선 화살표 <<include>> | 한 유스케이스 동작 시 반드시 실행되는 필수 하위 유스케이스, 공통 기능의 재사용 목적 | 상품 주문→사용자 인증 |
| 확장 (Extend) | 점선 화살표 <<extend>> | 확장 포인트(Extension Point) 조건 충족 시에만 선택적으로 부가 실행, 기본 흐름 훼손 없는 기능 추가 | 쿠폰 적용→상품 주문 |
| 일반화 (Generalization) | 실선 빈 삼각 화살표 | 액터 간 또는 유스케이스 간의 상속 관계 | 카드 결제→결제 수단 |

## Ⅴ. 유스케이스 다이어그램의 장점과 한계

- 핵심 요약 : 이해관계자 합의·테스트 근거의 장점, 내부 흐름 표현 불가·관계 남용·비기능 요구 미반영의 한계.
- 장점
  1. 발주자·현업·개발자 간 기능 범위의 직관적 합의.
  2. 테스트 케이스 도출의 체계적 근거 확보.
  3. 시스템 경계 기반 명확한 프로젝트 범위 정의.
- 한계점 1 : 시스템 내부 제어 흐름 및 비즈니스 로직 표현 불가
  - 한계점 : 시스템 경계 외부의 액터 관점에서 기능적 요구사항만 조망하므로 내부 트랜잭션 처리 순서, 복잡한 알고리즘, 분기 조건의 다이어그램 표현 불가.
  - 해결 방안 : 유스케이스 다이어그램의 범위 정의(Scope) 목적 한정, 상세 흐름은 사건 흐름(Flow of Events) 기반 유스케이스 명세서 및 액티비티/시퀀스 다이어그램으로 상호 보완.
- 한계점 2 : 포함(Include) 및 확장(Extend) 관계 남용으로 인한 복잡도 폭증
  - 한계점 : 전통적 기능 분해(Functional Decomposition) 습관으로 유스케이스를 무리하게 잘게 쪼개고 화살표를 남발하여 다이어그램 가독성이 파괴되는 스파게티 유스케이스 발생.
  - 해결 방안 : 유스케이스 분할 단위의 '사용자에게 측정 가능한 비즈니스 가치를 전달하는 완전한 작업 단위' 엄격 제한, include/extend 관계의 필수 공통 로직과 조건부 분기 시 최소한만 사용.
- 한계점 3 : 비기능적 요구사항(성능, 보안, 가용성) 모델링의 한계
  - 한계점 : 기능적 요구사항 표기에 집중되어 시스템의 초당 처리량(TPS, Transactions Per Second), 응답 시간, 암호화 요건 등 핵심 아키텍처 결정 요인의 미반영.
  - 해결 방안 : 유스케이스 명세서 내 특수 요구사항(Special Requirements) 섹션 의무화를 통한 비기능 요건 기술, 품질 속성 시나리오(Utility Tree)와의 1:1 추적성 확보.

## Ⅵ. 요구공학 및 테스팅 연계를 위한 기술사적 제언

- 핵심 요약 : 시나리오 기반 테스트 케이스 자동 도출과 목표 지향적 유스케이스 단위 모델링.
- 유스케이스 시나리오 기반 블랙박스 테스트 케이스 자동 도출 : 기본 흐름, 대안 흐름, 예외 흐름의 모든 분기 경로를 테스트 시나리오로 1:1 매핑하여 인수 테스트 커버리지의 충분한 확보.
- 과도한 상세화에 따른 기능 분해(Functional Decomposition) 방지 : 유스케이스를 개별 함수나 CRUD(Create, Read, Update, Delete) 단위로 분할 시 가독성과 비즈니스 가치가 훼손되므로, 사용자에게 완전한 가치를 전달하는 목표 지향적 단위의 모델링 필요.
- 요구사항 추적성 확보 : 유스케이스-명세서-설계 모델-테스트 케이스 간 추적 매트릭스의 지속 관리.

## Ⅶ. 결론

- 핵심 요약 : 유스케이스 다이어그램은 범위 정의와 테스트 근거 확보를 위한 요구공학의 표준 도구.
- 요약 : 4대 관계와 명세서 이원 구조를 통한 기능 범위의 합의 및 상세 시나리오의 정밀 기술.
- 시사점 : 내부 설계 도구가 아닌 범위·합의 도구로의 역할 한정과 관계 남용 방지가 품질의 핵심.
