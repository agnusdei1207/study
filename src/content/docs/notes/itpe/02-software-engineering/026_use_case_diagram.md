## Ⅰ. 유스케이스 다이어그램 및 유스케이스 명세의 개요

- **개념** : 사용자(액터)의 관점에서 시스템이 제공해야 하는 기능과 상호작용을 외부적 시각에서 모델링한 UML 행위 다이어그램이자, 각 기능 시나리오를 텍스트로 정밀하게 기술한 명세 문서.
- **배경 및 필요성** : 시스템 개발 초기 단계에서 발주자, 현업 실무자, 개발자 간의 기능적 요구사항 범위를 직관적으로 합의하고, 추후 테스트 케이스 도출의 근거로 활용.
- **주요 구성요소** : 시스템 경계(System Boundary), 액터(Actor), 유스케이스(Use Case), 관계(Relationship).

## Ⅱ. 유스케이스 다이어그램의 4대 관계 모델

```text
   ┌────────────────────────────────────────────────────────┐
   │ 시스템 경계 (System Boundary)                           │
   │                                                        │
   │                 <<include>>                            │
   │      [ 상품 주문 ] ─────────> [ 사용자 인증 ]            │
   │           ▲                                            │
   │           │ <<extend>>                                 │
   │      [ 쿠폰 적용 ]                                     │
   │                                                        │
   │      [ 결제 수단 ] <────<<generalization>>──── [ 카드 결제 ]
   └────────────────────────────────────────────────────────┘
```

- **연관 관계 (Association)** : 액터와 유스케이스 간의 실선 상호작용.
- **포함 관계 (Include)** : 한 유스케이스가 동작할 때 반드시 실행되어야 하는 필수 하위 유스케이스 (점선 화살표, <<include>>). 공통 기능의 재사용 목적.
- **확장 관계 (Extend)** : 특정 조건(확장 포인트, Extension Point)을 만족할 때만 선택적으로 부가 실행되는 유스케이스 (점선 화살표, <<extend>>). 기본 흐름을 훼손하지 않고 기능 추가.
- **일반화 관계 (Generalization)** : 액터 간 또는 유스케이스 간의 상속 관계 (실선 빈 삼각 화살표).

## Ⅲ. 유스케이스 명세서(Use Case Specification)의 필수 구조

| 항목 | 상세 내용 및 기술 방법 |
|---|---|
| 유스케이스 식별자 및 이름 | UC-01: 상품 주문 (명확한 동사형 표기) |
| 주 액터 및 부 액터 | 일반 고객 (주 액터), 결제 PG사 / 배송 시스템 (부 액터) |
| 사전 조건 (Pre-conditions) | 사용자가 로그인되어 있고 장바구니에 1개 이상의 상품이 담겨 있어야 함 |
| 사후 조건 (Post-conditions) | 주문 데이터가 생성되고, 재고가 차감되며, 주문 완료 알림 발송 |
| 기본 흐름 (Basic Flow) | 정상적인 성공 시나리오를 1단계부터 단계별로 기술 (Happy Path) |
| 대안 흐름 (Alternative Flow) | 조건에 따른 다른 성공 경로 (예: 마일리지 전액 결제) |
| 예외 흐름 (Exception Flow) | 오류 발생 시 처리 경로 (예: 잔액 부족, 결제 타임아웃, 재고 부족) |

## Ⅳ. 유스케이스 다이어그램의 주요 한계점 및 해결 방안

- **시스템 내부 제어 흐름 및 비즈니스 로직 표현 불가** :
  - **한계점** : 시스템 경계 외부의 액터 관점에서 기능적 요구사항만 조망하므로, 내부 트랜잭션 처리 순서, 복잡한 알고리즘, 분기 조건 등을 다이어그램에 표현 불가.
  - **해결 방안** : 유스케이스 다이어그램은 범위 정의(Scope) 목적으로만 활용하고, 상세 흐름은 사건 흐름(Flow of Events) 기반의 유스케이스 명세서 및 액티비티/시퀀스 다이어그램으로 상호 보완.
- **포함(Include) 및 확장(Extend) 관계 남용으로 인한 복잡도 폭증** :
  - **한계점** : 전통적 기능 분해(Functional Decomposition) 습관으로 유스케이스를 무리하게 잘게 쪼개고 화살표를 남발하여 다이어그램 가독성이 파괴되는 '스파게티 유스케이스' 발생.
  - **해결 방안** : 유스케이스 분할 단위를 '사용자에게 측정 가능한 비즈니스 가치를 전달하는 완전한 작업 단위'로 엄격히 제한하고, include/extend 관계는 필수 공통 로직과 조건부 분기 시에만 최소한으로 사용.
- **비기능적 요구사항(성능, 보안, 가용성) 모델링의 한계** :
  - **한계점** : 유스케이스 다이어그램은 기능적 요구사항 표기에 집중되어 있어 시스템의 초당 처리량(TPS), 응답 시간, 암호화 요건 등 핵심 아키텍처 결정 요인을 반영하지 못함.
  - **해결 방안** : 유스케이스 명세서 내 특수 요구사항(Special Requirements) 섹션을 의무화하여 비기능 요건을 기술하고, 품질 속성 시나리오(Utility Tree)와 1:1 추적성 확보.

## Ⅴ. 요구공학 및 테스팅 연계를 위한 기술사적 제언

- **유스케이스 시나리오 기반 블랙박스 테스트 케이스 자동 도출** : 기본 흐름, 대안 흐름, 예외 흐름의 모든 분기 경로를 테스트 시나리오로 1:1 매핑하여 인수 테스트 커버리지를 100% 확보하는 기반 마련.
- **과도한 상세화에 따른 기능 분해(Functional Decomposition) 방지** : 유스케이스를 개별 함수나 CRUD 단위로 잘게 쪼개면 다이어그램의 가독성과 비즈니스 가치가 훼손되므로, 사용자에게 완전한 가치를 전달하는 '목표 지향적 단위'로 모델링해야 함.
