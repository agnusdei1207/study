## 연관 키워드

- 유스케이스 다이어그램(Use Case Diagram), 유스케이스 명세서(Use Case Specification), 액터(Actor), 시스템 경계(System Boundary)
- 포함(Include), 확장(Extend), 일반화(Generalization), 기본 흐름(Basic Flow), 대안 흐름(Alternative Flow), 예외 흐름(Exception Flow)

## Ⅰ. 유스케이스 다이어그램의 개요

- 핵심 요약 : 액터 관점에서 시스템 기능을 외부 시각으로 모델링하는 UML(Unified Modeling Language) 행위 다이어그램이자 요구사항 범위 합의 도구.
- 개념 : 시스템이 외부 액터에게 제공할 기능과 상호작용을 외부 시각으로 모델링한 **유스케이스 다이어그램** (Use Case Diagram)이며, 각 기능 시나리오를 텍스트로 정밀하게 기술한 **유스케이스 명세서** (Use Case Specification)와 짝을 이룸.
- 배경 및 필요성 : 개발 초기에 발주자·현업·개발자가 기능 범위를 직관적으로 합의하고, 이후 테스트 케이스 도출의 근거를 확보할 필요가 있음.
- 주요 목적 : 시스템 범위의 명확화와 기능별 상호작용의 표준화된 시각화.
- 4대 구성요소 :
  1. **시스템 경계** (System Boundary) : 기능이 속한 시스템의 범위를 구분하는 사각형 영역.
  2. **액터** (Actor) : 시스템 바깥에서 상호작용하는 사람이나 외부 시스템.
  3. 유스케이스(Use Case) : 액터에게 측정 가능한 가치를 주는 기능 단위.
  4. 관계(Relationship) : 연관·포함·확장·일반화로 기능과 액터를 연결하는 선.

## Ⅱ. 유스케이스 다이어그램의 특징 및 장점

- 핵심 요약 : 액터 중심의 외부 조망과 4대 관계, 다이어그램과 명세서의 이원 구조가 범위 합의와 테스트 연계를 가능하게 하는 방식.

1. 액터 중심 모델링 : 시스템 경계 바깥에서 기능을 조망 → 내부 구현과 분리된 기능 범위 합의.
2. **4대 관계** (연관·포함·확장·일반화) : 기능 간 결합을 명시 → 공통 기능의 재사용과 선택적 부가 기능의 구분.
3. 이원 문서 구조 : 다이어그램은 범위를 정의하고 명세서는 상세 흐름을 기술 → 개요와 상세 사이의 추적 가능성 확보.
4. 테스트 연계 : 기본·대안·예외 흐름을 테스트 케이스의 근거로 사용 → 인수 테스트 커버리지 확보.

## Ⅲ. 유스케이스 다이어그램의 구조 (흐름)

- 핵심 요약 : 4대 관계 표기 모델과, 다이어그램에서 명세서·상세 설계·테스트로 이어지는 연계 흐름.
- **연관** (Association) : 액터와 유스케이스를 잇는 실선으로, 상호작용 자체를 나타냄.
- **포함** (Include) : 한 유스케이스가 실행될 때 반드시 호출되는 하위 유스케이스를 나타내는 <<include>> 점선 화살표.
- **확장** (Extend) : 확장 지점(Extension Point)의 조건이 충족될 때만 부가 실행되는 <<extend>> 점선 화살표.
- **일반화** (Generalization) : 상위 요소를 향하는 속이 빈 삼각형 실선으로, 상속 관계를 나타냄.

```text
[ 4대 관계 표기 예시 ]

고객(액터) ──연관──> 상품 주문
상품 주문 ──<<include>>──> 사용자 인증
쿠폰 적용 ──<<extend>>──> 상품 주문
카드 결제 ──일반화──> 결제 수단
```

```text
[ 요구사항 모델링 연계 흐름 ]

유스케이스 다이어그램 (범위 정의)
   ↓
유스케이스 명세서 (기본·대안·예외 흐름)
   ↓
액티비티·시퀀스 다이어그램 (상세 설계)
   ↓
블랙박스 테스트 케이스 (경로별 매핑)
```

유스케이스 명세서의 필수 구조는 다음 표와 같다.

| 항목 | 상세 내용 및 기술 방법 |
| --- | --- |
| 유스케이스 식별자 및 이름 | UC-01: 상품 주문 (명확한 동사형 표기) |
| 주 액터 및 부 액터 | 일반 고객 (주 액터), 결제 대행사(PG, Payment Gateway)·배송 시스템 (부 액터) |
| 사전 조건 (Pre-conditions) | 사용자가 로그인되어 있고 장바구니에 1개 이상의 상품이 담겨 있어야 함 |
| 사후 조건 (Post-conditions) | 주문 데이터가 생성되고, 재고가 차감되며, 주문 완료 알림이 발송됨 |
| 기본 흐름 (Basic Flow) | 정상적인 성공 시나리오를 1단계부터 단계별로 기술 (Happy Path) |
| 대안 흐름 (Alternative Flow) | 조건에 따른 다른 성공 경로 (예: 마일리지 전액 결제) |
| 예외 흐름 (Exception Flow) | 오류 발생 시 처리 경로 (예: 잔액 부족, 결제 타임아웃, 재고 부족) |

## Ⅳ. 유스케이스 4대 관계의 비교

- 핵심 요약 : 연관은 상호작용, 포함은 필수 재사용, 확장은 조건부 부가, 일반화는 상속을 나타내므로 용도에 맞게 구분해 사용.

| 관계 | 표기법 | 의미 및 목적 | 예시 |
| --- | --- | --- | --- |
| 연관 (Association) | 실선 | 액터와 유스케이스 간의 상호작용 | 고객과 상품 주문 |
| 포함 (Include) | 점선 화살표 <<include>> | 필수 하위 유스케이스를 재사용하는 목적 | 상품 주문 → 사용자 인증 |
| 확장 (Extend) | 점선 화살표 <<extend>> | 조건 충족 시에만 부가 실행하여 기본 흐름을 훼손하지 않음 | 쿠폰 적용 → 상품 주문 |
| 일반화 (Generalization) | 속이 빈 삼각형 실선 | 액터 간 또는 유스케이스 간의 상속 | 카드 결제 → 결제 수단 |

- 선택 기준 : 항상 실행되는 공통 로직은 포함, 조건에 따라 붙는 부가 기능은 확장으로 구분하고, 나머지 상호작용은 연관으로 둔다.

## Ⅴ. 유스케이스 다이어그램의 한계와 방안

- 핵심 요약 : 내부 흐름 표현 불가, 관계 남용, 비기능 요구 미반영의 세 한계를 범위 한정, 단위 분할 기준, 명세서 보완으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 내부 흐름 표현 한계 | 내부 제어 흐름과 비즈니스 로직을 표현하지 못해 분기 조건 해석 불가 | 다이어그램은 범위 정의 목적으로 한정하고, 상세 흐름은 명세서와 액티비티·시퀀스 다이어그램으로 보완 | 명세서와 설계 문서의 연계율 |
| 포함·확장 관계 남용 | 기능 분해 습관으로 유스케이스를 잘게 쪼개고 화살표를 남발해 가독성 저하 | 사용자에게 측정 가능한 가치를 주는 완전한 작업 단위로 분할하고, 포함·확장은 공통 로직과 최소 분기에만 사용 | 유스케이스당 관계 수 |
| 비기능 요구 미반영 | 처리량(TPS, Transactions Per Second), 응답 시간, 암호화 요건 등 아키텍처 결정 요인 누락 | 명세서에 특수 요구사항(Special Requirements) 섹션을 의무화하고 품질 속성 시나리오(Utility Tree)와 1:1로 추적 | 비기능 요건 추적률 |

## Ⅵ. 요구공학 및 테스팅 연계를 위한 기술사적 제언

- 핵심 요약 : 시나리오 단위 테스트 연계와 목표 지향적 모델링을 프로젝트 표준으로 정착시키는 것이 유스케이스의 실효성을 높이는 길.
- 요구 분석 조직은 유스케이스 단위를 사용자가 체감하는 완전한 업무 목표로 정하고, 설계 리뷰에서 CRUD(Create, Read, Update, Delete) 단위 분할을 걸러내는 기준을 운영해야 한다.
- 테스트 조직은 명세서의 기본·대안·예외 흐름을 인수 테스트 시나리오와 1:1로 매핑하는 추적 매트릭스를 표준 산출물로 관리해야 한다. 이 매트릭스가 요구사항, 설계 모델, 테스트 케이스를 잇는 기준선이 된다.

## Ⅶ. 결론

- 핵심 요약 : 유스케이스 다이어그램은 기능 범위 합의와 테스트 근거를 제공하는 요구공학의 표준 도구.
- 시사점 : 내부 설계 도구가 아닌 범위·합의 도구로 역할을 한정하고 관계 남용을 막는 것이 활용 품질을 좌우함.
