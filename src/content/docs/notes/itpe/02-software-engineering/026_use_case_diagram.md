## 30초 인출

- 본질: 시스템 외부의 사용자(액터) 관점에서 시스템이 제공해야 하는 기능적 요구사항과 서비스 범위를 시각적으로 정의하는 UML 표준 행위 다이어그램
- 메커니즘: 시스템 경계(System Boundary) 내부 유스케이스와 외부 액터(Primary/Secondary) 간의 연관, 포함(`<<include>>`), 확장(`<<extend>>`), 일반화 관계 매핑
- 통찰: 다이어그램 표기만으로는 비기능 요구와 상세 예외 분기 추적이 어려우므로 정형화된 유스케이스 명세서 및 인수 테스트(Acceptance Test) 시나리오와의 연계 수립 필수

<details>
<summary>핵심 용어</summary>

- **Use Case Diagram(유스케이스 다이어그램)** : 액터와 시스템의 상호작용 및 시스템 경계 내 기능적 요구사항을 시각화한 UML 행위 모델
- **Actor(액터)** : 시스템 경계 외부에서 시스템과 상호작용하며 특정 역할을 수행하는 사람, 조직, 하드웨어 또는 외부 시스템
- **System Boundary(시스템 경계)** : 개발 대상 소프트웨어가 담당할 기능 범위와 외부 환경을 명확히 구분하는 사각형 경계선
- **&lt;&lt;include&gt;&gt; (포함 관계)** : 하나의 유스케이스 수행 시 공통 필수 기능으로서 다른 유스케이스를 반드시 호출 실행하는 관계
- **&lt;&lt;extend&gt;&gt; (확장 관계)** : 특정 확장점(Extension Point)과 조건 충족 시에만 기본 유스케이스에 선택적으로 삽입되어 실행되는 관계
- **Use Case Specification(유스케이스 명세서)** : 유스케이스의 사전/사후 조건, 기본 흐름, 대안 흐름, 예외 흐름을 정형화하여 기술한 분석 산출물

## 2~4교시 25점 답안

## Ⅰ. 유스케이스 다이어그램의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 시스템 외부의 액터(Actor)와 시스템이 제공하는 유스케이스(Use Case) 간의 상호작용 및 관계를 시각적으로 표현하여 시스템의 기능적 범위를 명세하는 UML 모델 |
| 목적 | 사용자 관점의 요구사항 식별 및 합의, 시스템 개발 범위(Scope) 확정, 테스트 시나리오 및 인수 기준 도출의 기준선 제공 |

## Ⅱ. 유스케이스 다이어그램의 핵심 특징

| 특징 | 의미 |
|---|---|
| 블랙박스 관점 모델링 | 내부 구현 기술이나 데이터 구조를 배제하고 시스템 외부에서 관찰 가능한 동작에 집중 |
| 시스템 경계의 명확성 | 직사각형 경계선(Boundary)을 통해 개발 대상 기능과 외부 시스템/사용자의 책임을 명확히 분리 |
| 기능 분할 방지 | 단순 함수 단위 나열을 지양하고 액터에게 독립적이고 측정 가능한 가치를 제공하는 단위로 구성 |
| 요구사항 추적성의 기준 | 유스케이스 단위로 분석, 설계(시퀀스/클래스 다이어그램), 구현, 인수 테스트를 일관되게 연결 |

## Ⅲ. 유스케이스 다이어그램 구성요소 및 관계 체계

### 유스케이스 다이어그램 구조 및 관계 매핑

```text
┌─────────────────────────── [온라인 커머스 시스템 경계] ───────────────────────────┐
│                                                                                 │
│                                  ┌────────────────────────┐                     │
│                  ┌──────────────→│   본인 인증 및 인가    │                     │
│                  │  <<include>>  └────────────────────────┘                     │
│                  │ (필수 실행)                                                  │
│                  │                                                              │
│           (주문 결제하기) ◄────────────── ┌────────────────────────┐            │
│                  ▲           <<extend>>   │   쿠폰 및 포인트 할인  │            │
│                  │          (조건부 실행) └────────────────────────┘            │
│                  │          (확장점: 결제전)                                     │
│                  │                                                              │
│                  ▼  <<include>>                                                 │
│           (재고 차감 처리)                                                      │
│                                                                                 │
└──────────────────┬──────────────────────────────────────────────────────────────┘
                   │
    ┌──────────────┴──────────────┐                           ┌──────────────────┐
    │                             │                           │                  │
    ▼                             ▼                           ▼                  ▼
 옷 [일반 고객]              옷 [VIP 고객]              [외부 결제 PG사]    [물류 연계 시스템]
(Primary Actor)             (일반화 관계)              (Secondary Actor)   (Secondary Actor)
```

### 유스케이스 다이어그램 핵심 구성요소

| 구성요소 | 표기 심볼 | 핵심 역할 및 모델링 가이드 |
|---|---|---|
| **시스템 경계 (Boundary)** | 큰 직사각형 프레임 | 소프트웨어의 구현 범위 명시, 시스템 이름 기재 |
| **액터 (Actor)** | 졸라맨(사람) 또는 `<<actor>>` 박스 | 시스템 외부에서 기능을 능동적으로 이용하거나 수동적으로 결과를 수신하는 주체 |
| **주 액터 (Primary Actor)** | 시스템 좌측 배치 | 시스템에 작업을 요청하여 주요 목표를 달성하는 액터 (예: 고객, 관리자) |
| **부 액터 (Secondary Actor)** | 시스템 우측 배치 | 시스템의 목표 달성을 위해 서비스나 데이터를 지원하는 외부 시스템 (예: PG사, SMS) |
| **유스케이스 (Use Case)** | 타원형 | 액터에게 측정 가능한 가치를 제공하는 완성된 단일 작업 흐름 (동사형 명명) |

### 유스케이스 간 4대 관계(Relationship) 유형

| 관계 유형 | UML 표기법 | 방향성 | 의미 및 동작 조건 |
|---|---|---|---|
| **연관 (Association)** | 실선 (`―`) | 액터 ─ 유스케이스 | 액터와 유스케이스 간의 상호작용 통로 명시 |
| **포함 (&lt;&lt;include&gt;&gt;)** | 점선 화살표 + `<<include>>` | 기본 → 포함 | 기본 유스케이스 수행 시 필수적으로 실행되는 공통 서브 루틴 |
| **확장 (&lt;&lt;extend&gt;&gt;)** | 점선 화살표 + `<<extend>>` | 확장 → 기본 | 특정 확장점(Extension Point)에서 조건 충족 시 선택적으로 실행 |
| **일반화 (Generalization)** | 실선 + 닫힌 빈 삼각형 | 하위 → 상위 | 액터나 유스케이스 간의 공통 특성을 추상화한 상속 관계 |

## Ⅳ. 포함(&lt;&lt;include&gt;&gt;)과 확장(&lt;&lt;extend&gt;&gt;) 비교

### 두 관계 간의 본질적 차이점 분석

| 비교 항목 | 포함 관계 (&lt;&lt;include&gt;&gt;) | 확장 관계 (&lt;&lt;extend&gt;&gt;) |
|---|---|---|
| **기본 흐름과의 종속성** | 기본 유스케이스 완수를 위해 **반드시 실행되어야 함** | 기본 유스케이스는 독립 완수 가능, **선택적으로 실행** |
| **화살표 지향 방향** | **기본 유스케이스 → 피포함 유스케이스** | **확장 유스케이스 → 기본 유스케이스** |
| **확장점 (Extension Point)** | 별도의 확장 위치 지정 불필요 | 기본 유스케이스 내 특정 실행 위치(확장점) 명시 필수 |
| **주요 적용 목적** | 복수 유스케이스 간 공통 기능의 중복 제거 및 재사용 | 기본 비즈니스 흐름을 왜곡하지 않고 부가/예외 기능 분리 |
| **실제 적용 예시** | `[상품 주문] ──<<include>>──> [본인 인증]` | `[쿠폰 적용] ──<<extend>>──> [상품 주문]` |

### 유스케이스 명세서(Specification) 표준 서식 구성

| 항목 | 기재 내용 | 실무 작성 시 고려사항 |
|---|---|---|
| **유스케이스 식별자/명칭** | UC-ORD-001 / 상품 결제 및 주문 처리 | 도메인 명명 규칙에 따라 고유 ID 부여 |
| **주 액터 / 부 액터** | 로그인한 고객 / PG 연동 시스템, 재고 시스템 | 역할을 명확히 기술 |
| **사전 조건 (Pre-condition)** | 장바구니에 1개 이상의 상품이 담겨 있어야 함 | 실행 전 보장되어야 할 시스템 상태 |
| **사후 조건 (Post-condition)** | 주문 데이터 생성, 결제 완료, 재고 차감 반영 | 성공적 완료 후 보장되는 시스템 상태 |
| **기본 흐름 (Basic Flow)** | 1. 배송지 입력 → 2. 결제 수단 선택 → 3. 승인 | 예외 없는 가장 전형적인 성공 시나리오 |
| **대안 흐름 (Alternative)** | 2a. 포인트 전액 결제 선택 시 PG 승인 단계 생략 | 기본 흐름의 정상적인 분기 경로 |
| **예외 흐름 (Exception)** | 3a. 카드 한도 초과 오류 시 에러 안내 후 결제 재시도 | 시스템 오류 또는 사용자 입력 실패 처리 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 유스케이스를 단순 CRUD 기능 단위로 잘게 쪼개어 다이어그램 복잡도가 폭발하는 현상 | 액터에게 비즈니스적 가치를 제공하는 트랜잭션 목표 단위로 상위 통합 모델링 수행 |
| 포함(`<<include>>`)과 확장(`<<extend>>`)의 화살표 방향 및 의미 혼동으로 인한 설계 오류 | include(기본→포함), extend(확장→기본) 방향성 표준화 가이드 및 리뷰 체크리스트 배포 |
| 성능, 보안, 가용성 등 품질속성(비기능 요구사항)을 다이어그램상에 표현하기 곤란 | 유스케이스 명세서 내 '특수 요구사항(Special Requirements)' 절을 신설하여 정량 기술 |

## Ⅵ. 제언

유스케이스 명세서 기반 BDD(행위 주도 개발) 테스트 자동화 파이프라인 연계를 통한 분석-검증 동기화

### 유스케이스 기반 BDD 자동화 파이프라인

```text
[유스케이스 명세서 작성]
  ├─ 기본 흐름 / 대안 흐름 / 예외 흐름
       ↓
[Gherkin 문법 변환 (Given-When-Then)]
  ├─ Given: 사전 조건 (장바구니 담김)
  ├─ When: 액터 행위 (결제 요청)
  └─ Then: 사후 조건 (주문 완료 및 재고 차감)
       ↓
[Cucumber / SpecFlow 자동화 테스트 스크립트 생성]
       ↓
[CI 파이프라인에서 지속적 회귀 검증 실행]
```

### 유스케이스 분할 및 상세화 의사결정 체계

```text
사용자 요구사항 식별
       ↓
[액터에게 독립적인 결과 가치를 전달하는가?]
       ├─ 아니오 ─→ 단순 내부 기능으로 판단하여 명세서 내부 세부 단계로 통합
       └─ 예 ───→ 독립 유스케이스로 도출
                      ↓
           [다수 유스케이스 간 필수 공통 기능인가?]
                      ├─ 예 ──→ <<include>> 관계로 모듈화
                      └─ 아니오 ─→ [특정 조건에서만 실행되는 부가 기능인가?]
                                        ├─ 예 ──→ <<extend>> 관계로 확장점 명시
                                        └─ 아니오 ─→ 독립 기본 흐름 유지
```

### 선택 근거: 전통적 기능 목록(FDR)과 유스케이스 기반 명세 비교

| 구분 | 전통적 기능 요구사항 목록(FDR) | 제언: 유스케이스 및 명세서 모델링 |
|---|---|---|
| 기술 관점 | 시스템 기능(Function) 중심 단순 열거 | 사용자(Actor) 목표 달성 및 상호작용 중심 |
| 맥락 이해도 | 입출력과 조건의 비즈니스 맥락 파악 곤란 | 사전/사후 조건과 시나리오 흐름으로 맥락 명확화 |
| 테스트 연계 | 단위 기능별 단편적 테스트 케이스 도출 | 종단간(E2E) 인수 테스트 및 BDD 시나리오 직결 |
