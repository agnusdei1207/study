## 답안 골격
```text
[아키텍처 스타일] ◀━━ 머리: Ⅶ 내 의견 (비즈니스 특성에 맞춘 하이브리드 스타일(계층형 + 이벤트 주도) 설계)
 ┃
 ┣━ Ⅰ 개요 ───── 시스템의 특정 품질 속성을 달성하기 위해 검증된 컴포넌트와 커넥터의 거시적 배치 패턴
 ┣━ Ⅱ 특징 ───── 시스템 전반의 어휘 공유 · 설계 의사결정 재사용 · 특정 비기능 품질 속성(확장성, 분리성 등) 최적화
 ┣━ Ⅲ 구조 ───── 데이터 중심(Blackboard) · 데이터 흐름(Pipes & Filters) · 호출/복귀(Layered, MVC) · 독립 컴포넌트(EDA, MSA)
 ┣━ Ⅳ 흐름 ───── 비즈니스 요구 식별 → 핵심 품질 속성 우선순위화 → 아키텍처 스타일 매핑 → 트레이드오프 평가
 ┣━ Ⅴ 비교 ───── 계층화 스타일(Layered, 단순성/유지보수) vs 이벤트 주도 스타일(EDA, 확장성/비동기) vs MSA
 ┗━ Ⅵ 실무 ───── 무리한 최신 스타일(MSA) 도입으로 인한 운영 복잡도 / 모듈러 모놀리스(Modular Monolith) 선행
```
- 필수 키워드: 아키텍처 패턴 · Pipes and Filters · Layered · MVC · Event-Driven(EDA) · Blackboard · 마이크로서비스
- 배점 전략: 10점 = Ⅲ 4대 핵심 분류 체계 표 → 대표 스타일 2종(Pipes & Filters, Layered) 구조도 / 25점 = Ⅰ~Ⅶ 전개, 품질 속성별 최적 아키텍처 스타일 매핑 전략
- 기출: 131회 2교시 `아키텍처 스타일과 디자인 패턴` → Ⅰ·Ⅲ·Ⅴ / 120회 3교시 `소프트웨어 아키텍처 모델 유형` → Ⅲ·Ⅳ

## 한 줄 본질
- 소프트웨어 시스템을 밑바닥부터 무작정 설계하다가 성능, 확장성, 유지보수성 간의 균형을 잃고 붕괴하는 설계 실패 병목 → 수십 년간 검증된 컴포넌트 배치와 상호작용 규칙의 거시적 정형화 패턴(계층형, 파이프-필터, 이벤트 주도 등)을 적용 → 시스템 전반의 일관성 및 검증된 품질 속성 달성 / 특정 스타일의 고유 제약조건 감수 대가

## 핵심 그림
```text
[ 대표적 아키텍처 스타일 3종 구조 ]
1. Pipes & Filters (데이터 흐름):
   [ Data Source ] ---> [ Filter A ] ===(Pipe)===> [ Filter B ] ---> [ Sink ]

2. Layered Architecture (계층화):
   [ Presentation Layer ]  (상위 계층은 직하위 계층만 호출)
            v
   [ Business / Domain Layer ]
            v
   [ Data Access / Persistence Layer ]

3. Event-Driven Architecture (독립 비동기):
   [ Event Producer ] ---> ( Event Channel / Broker ) ---> [ Event Consumer ]
```

## 핵심 용어
- 파이프-필터(Pipes and Filters): 데이터 스트림을 받아 변환을 수행하는 독립적인 '필터(Filter)'들과 이들을 단방향으로 연결하는 '파이프(Pipe)'로 구성되는 데이터 흐름 스타일(Unix 쉘 파이프, 컴파일러 등)
- 계층화 아키텍처(Layered Architecture): 컴포넌트들을 수평 계층으로 분할하여 상위 계층이 하위 계층의 서비스만을 이용하도록 결합도를 격리하는 가장 고전적이고 대중적인 스타일

## 핵심 통찰
- 아키텍처 스타일은 만병통치약이 아니며, 모든 스타일은 장점과 대가(트레이드오프)가 명확함(예: Layered는 단순하지만 계층 간 오버헤드가 발생하고, EDA는 확장성이 높지만 트랜잭션 추적이 극도로 어려움)
- 시스템 전체가 단 하나의 아키텍처 스타일만 따를 필요는 없으며, 웹 계층은 MVC, 배치 처리는 Pipes & Filters, 비동기 알림은 EDA를 결합하는 하이브리드 아키텍처가 일반적임
- 아키텍처 스타일의 선택은 비즈니스의 변경 주기와 일치해야 함(비즈니스 규칙이 자주 바뀌면 Layered나 헥사고날이, 대규모 데이터 스트리밍이 필요하면 Pipes & Filters나 카프카 기반 EDA가 적합)

## 이웃 토픽과 구분
- 아키텍처 스타일 vs 디자인 패턴: 아키텍처 스타일 = 시스템 전체를 지배하는 거시적 배치 원칙 / 디자인 패턴 = 특정 컴포넌트 내부의 클래스 설계 해법

| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 대용량 로그 가공 시스템에 계층형(Layered) 스타일을 적용하여 심각한 I/O 지연 발생 | 데이터 흐름 처리에 부적합한 계층 간 객체 매핑 오버헤드 | 파이프-필터(Pipes & Filters) 스타일 및 스트리밍 엔진(Kafka Streams)으로 전환 | 불필요한 메모리 복사 제거 및 실시간 스트리밍 처리 달성 |
| 이벤트 주도(EDA) 도입 후 장애 발생 시 어느 지점에서 메시지가 유실되었는지 추적 불가 | 비동기 느슨한 결합의 부작용인 분산 제어 및 모니터링 난이도 급증 | 상관관계 ID(Correlation ID) 전파 및 데드 레터 큐(DLQ) 모니터링 구축 | 비동기 이벤트 추적성 및 유실 메시지 재처리 100% 확보 |

## 내 의견
- [유행하는 스타일에 무리하게 시스템을 끼워 맞추는 패션 아키텍처의 위험] 초당 트래픽 10건도 안 되는 사내 시스템에 마이크로서비스(MSA)나 완전 비동기 이벤트 주도(EDA)를 도입하여 운영 비용만 10배로 늘려놓는 사례 빈발 → 나라면: 시작은 가장 단순하고 검증된 모듈러 모놀리스(Modular Monolith)와 계층화 스타일로 구축하고, 실제 성능 병목이나 독립 배포 요구가 증명된 특정 서브도메인만 이벤트 기반이나 MSA로 점진 분리하는 실용적 아키텍처 거버넌스 확립
