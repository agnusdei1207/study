## Ⅰ. 아키텍처 스타일의 개요

- 개념 : 소프트웨어 시스템의 기본 구조와 동작 방식을 결정하는 **구성요소** (Components)와 **커넥터** (Connectors)의 배치 유형 및 시스템 설계 제약조건의 집합적 패턴.
- 배경 및 필요성 : 개발팀 간의 공통된 아키텍처 어휘를 확립하고, 이미 검증된 패턴을 재사용하여 **비기능 품질속성** (성능, 가용성, 확장성, 변경용이성)을 조기에 달성.
- 주요 아키텍처 스타일 분류 : **계층형** (Layered), **이벤트 기반** (Event-Driven), **마이크로커널** (플러그인), **마이크로서비스** (MSA), **공간 기반** (Space-Based).

## Ⅱ. 주요 아키텍처 스타일의 구조 및 비교

```text
[ 계층형 (Layered) ]        [ 이벤트 기반 (EDA) ]       [ 마이크로커널 (Plugin) ]
 ┌────────────────┐         [ Producer ]                ┌──────────────────────┐
 │ Presentation   │              │ (이벤트 발행)         │   Core System        │
 ├────────────────┤              ▼                      └──────────┬───────────┘
 │ Business Logic │         [ Event Broker ]                       │ (플러그인 등록)
 ├────────────────┤         ┌────┴────┐                 ┌──────────┼───────────┐
 │ Persistence    │         ▼         ▼                 ▼          ▼           ▼
 ├────────────────┤    [Consumer] [Consumer]        [Plugin A] [Plugin B] [Plugin C]
 │ Database       │
 └────────────────┘
```

- **계층형 아키텍처 (Layered)** : 가장 보편적인 구조로 각 계층이 명확한 책임을 가짐. 단방향 호출 원칙과 관심사의 분리를 달성하나, 단순 CRUD 작업 시에도 모든 계층을 관통하는 **싱크홀** (Sinkhole) 안티패턴 위험 존재.
- **이벤트 기반 아키텍처 (Event-Driven)** : 비동기 이벤트를 매개로 생산자와 소비자가 완전 격리되어 고도의 수평 확장성과 반응성을 제공. 분산 트랜잭션 관리와 에러 추적이 복잡.
- **마이크로커널 아키텍처 (Microkernel)** : 최소한의 코어 시스템에 독립적인 플러그인을 동적으로 장착하여 확장. IDE(VS Code, Eclipse), 브라우저 확장에 적합.

## Ⅲ. 대표 아키텍처 스타일의 품질속성 트레이드오프 비교

| 아키텍처 스타일 | 전반적 민첩성 (Agility) | 배포 용이성 | 성능 (Performance) | 확장성 (Scalability) | 개발 용이성 |
|---|---|---|---|---|---|
| 계층형 (Layered) | 낮음 | 낮음 (모놀리식) | 보통 (계층 오버헤드) | 낮음 | 높음 (친숙함) |
| 마이크로커널 (Plugin) | 높음 | 높음 (플러그인별) | 높음 | 낮음 | 높음 |
| 이벤트 기반 (EDA) | 높음 | 높음 | 높음 (비동기 처리) | 극도로 높음 | 복잡함 |
| **마이크로서비스 (MSA)** | 극도로 높음 | 극도로 높음 | 보통 (네트워크 홉) | 극도로 높음 | 복잡함 |
| 공간 기반 (Space-Based) | 높음 | 높음 | 극도로 높음 (인메모리) | 극도로 높음 | 복잡함 |

## Ⅳ. 아키텍처 스타일 선정의 주요 한계점 및 해결 방안

- 유행 추종형 아키텍처 선정(Resume-Driven Architecture)의 폐해 :
  - 한계점 : 비즈니스 도메인의 복잡도와 트래픽 규모가 단순함에도 불구하고 최신 유행만을 좇아 MSA나 이벤트 주도 아키텍처(EDA)를 도입하여 막대한 네트워크 지연과 운영 비용 초래.
  - 해결 방안 : 마틴 파울러의 모놀리식 퍼스트(MonolithFirst) 전략을 채택하여 초기에는 모듈러 모놀리스(Modular Monolith)로 출발하고, 비즈니스 규모 성장에 따라 점진적으로 분산 스타일로 진화(Evolutionary Architecture).
- 아키텍처 스타일 고유의 품질 속성 트레이드오프 간과 :
  - 한계점 : 마이크로서비스 스타일의 독립 배포성에만 매몰되어 분산 트랜잭션 데이터 일관성 결여, 복잡한 네트워크 장애 추적 등 스타일 고유의 대가를 사전에 대비하지 못함.
  - 해결 방안 : 품질 속성 시나리오 매트릭스를 기반으로 각 아키텍처 스타일의 페널티 요소를 사전 정량 평가하고, 이벤트 주도 비동기 통신과 서비스 메시 등 보완 패턴을 세트로 구성.
- 레거시 스타일에서 신규 스타일로의 전환(Migration) 실패 :
  - 한계점 : 기존 계층형 모놀리식 시스템을 분산 아키텍처 스타일로 일괄 전환(Big-Bang)하려다 업무 공백, 데이터 불일치 및 예산 고갈로 프로젝트 좌초.
  - 해결 방안 : 스트랭글러 피그(Strangler Fig) 패턴을 적용하여 외곽 도메인부터 점진적으로 분리하고, 변경 데이터 캡처(CDC: Debezium)를 통한 무중단 데이터 동기화 체계 구축.

## Ⅴ. 엔터프라이즈 아키텍처 선정 시 기술사적 제언

- 시스템 핵심 비즈니스 드라이버에 기반한 스타일 결정 : 단일 스타일만을 고집하지 말고, 비즈니스 목표가 빠른 시장 출시와 도메인 격리라면 MSA를, 예측 불가능한 스파이크 트래픽 대응이라면 공간 기반 아키텍처를 선택하는 도메인 적합성 평가 선행.
- 하이브리드 아키텍처의 통합 거버넌스 수립 : 실무 환경에서는 코어 모놀리스(계층형) 주변에 비동기 이벤트 파이프라인(Kafka)과 마이크로커널 플러그인이 결합된 혼합 형태가 보편적이므로, 아키텍처 결정 기록(ADR)을 통해 각 영역의 스타일 선택 근거를 명확히 문서화해야 함.
