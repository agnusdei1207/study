## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 아키텍처 설계 → **아키텍처 스타일(Architecture Style)**

## 30초 인출

- 본질: 반복적으로 발생하는 소프트웨어 설계 문제에 대해 검증된 컴포넌트(요소)의 유형과 커넥터(상호작용), 배치 제약조건을 사전에 정형화해 둔 거시적 구조 템플릿
- 메커니즘: 데이터 흐름(Pipes & Filters), 호출 및 반환(Layered, C/S), 독립 컴포넌트(EDA), 데이터 공유(Repository, Blackboard) 등 시스템 목적별 상호작용 제약 적용
- 통찰: 유행에 휩쓸린 무분별한 분산 스타일 채택은 네트워크 지연과 분산 트랜잭션 관리 비용을 폭증시키므로 시스템의 핵심 품질속성(SEI 시나리오)과 조직 역량에 부합하는 적합성 검증 필수

<details>
<summary>핵심 용어</summary>

- **Architecture Style(아키텍처 스타일)** : 시스템의 전체적인 구조 골격과 컴포넌트 간의 상호작용 패턴, 제약사항을 규정한 고수준 설계 관용구
- **Layered Architecture(계층형 아키텍처)** : 시스템을 관심사별 수평적 계층(Presentation, Business, Data)으로 분할하고 상위 계층이 하위 계층에만 단방향 의존하는 스타일
- **Pipes and Filters(파이프와 필터)** : 데이터 스트림을 입력받아 독립적인 필터(Filter)들이 단계별 변환을 수행하고 파이프(Pipe)로 연결하는 데이터 흐름 스타일
- **EDA (Event-Driven Architecture)** : 이벤트의 생성, 감지, 소비를 중심으로 비동기 메시지 브로커를 통해 컴포넌트 간 결합도를 최소화하는 이벤트 주도 스타일
- **Repository / Blackboard** : 중앙의 공유 데이터 저장소(데이터베이스/지식베이스)를 중심으로 다수의 독립된 서브시스템이나 제어 에이전트들이 상호작용하는 스타일

</details>

## 2~4교시 25점 답안

## Ⅰ. 아키텍처 스타일의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 특정 시스템 계열의 아키텍처를 정의하기 위해 컴포넌트(Component)의 어휘와 커넥터(Connector)의 패턴, 그리고 이들이 결합되는 제약조건(Constraints)을 표준화한 고수준 구조적 청사진 |
| 목적 | 검증된 설계 솔루션의 재사용, 시스템 구조의 조기 이해도 증진, 품질속성(성능, 변경성, 가용성) 목표 달성 및 개발 생산성 극대화 |

## Ⅱ. 아키텍처 스타일의 핵심 특징

| 특징 | 의미 |
|---|---|
| 컴포넌트 및 커넥터 규정 | 시스템을 구성하는 블록의 종류(필터, 레이어, 이벤트 핸들러 등)와 연결 방식(파이프, RPC, 메시지 큐)을 제약 |
| 관심사의 분리 (SoC) | 비즈니스 로직, 데이터 접근, 사용자 인터페이스 등 서로 다른 성격의 책임을 독립적으로 격리 |
| 품질속성 트레이드오프 | 각 스타일마다 특화된 품질속성(계층형은 변경성/유지보수성, EDA는 확장성/응답성)과 희생되는 비용 명확화 |
| 디자인 패턴과의 차별성 | 디자인 패턴이 클래스/객체 레벨의 미시적 해결책이라면 아키텍처 스타일은 서브시스템 레벨의 거시적 구조 규정 |

## Ⅲ. 4대 아키텍처 스타일 계열 및 제어 메커니즘

### 4대 아키텍처 스타일 분류별 핵심 구조

```text
[1. 데이터 흐름 계열: 파이프와 필터 (Pipes & Filters)]
  [데이터 소스] ──(파이프)──→ [필터 1: 파싱] ──(파이프)──→ [필터 2: 암호화] ──(파이프)──→ [싱크(저장)]
  - 특징: 필터 간 독립성 보장, 재사용성 극대화, 스트리밍 처리 최적화

[2. 호출 및 반환 계열: 계층형 아키텍처 (Layered Architecture)]
  ┌────────────────────────────────────────────────────────┐
  │ 표현 계층 (Presentation Layer: UI / Controller)        │
  └───────────────────────────┬────────────────────────────┘
                              │ 단방향 하향 호출 (Top-down)
  ┌───────────────────────────▼────────────────────────────┐
  │ 비즈니스 로직 계층 (Business / Domain Service)         │
  └───────────────────────────┬────────────────────────────┘
                              │ 단방향 하향 호출
  ┌───────────────────────────▼────────────────────────────┐
  │ 데이터 접근 계층 (Persistence / Data Access Layer)     │
  └────────────────────────────────────────────────────────┘

[3. 독립 컴포넌트 계열: 이벤트 주도 (Event-Driven)]
  [이벤트 발행자 A] ──(발행)──┐                          ┌──(구독)──→ [이벤트 소비자 X]
                              ▼                          │
  [이벤트 발행자 B] ──(발행)──→ [중앙 이벤트 브로커 (Kafka)] ┼──(구독)──→ [이벤트 소비자 Y]
                                                         │
                                                         └──(구독)──→ [이벤트 소비자 Z]

[4. 데이터 공유 계열: 저장소 / 블랙보드 (Repository / Blackboard)]
  [분석 제어 모듈 A] ◄──┐                                ┌──► [지식 탐색 모듈 B]
                        │    ┌──────────────────────┐    │
                        └───►│  중앙 공유 데이터    │◄───┘
                             │  (Shared Repository) │
                        ┌───►│  블랙보드 상태 저장소│◄───┐
                        │    └──────────────────────┘    │
  [모니터링 모듈 C] ────┘                                └─── [규칙 추론 엔진 D]
```

## Ⅳ. 주요 아키텍처 스타일 간 비교 분석

### 4대 대표 아키텍처 스타일 비교

| 아키텍처 스타일 | 핵심 컴포넌트 / 커넥터 | 우수 품질속성 | 취약 품질속성 | 최적 적용 도메인 |
|---|---|---|---|---|
| **파이프와 필터 (Pipes & Filters)** | 필터(Filter) / 파이프(Pipe) | **재사용성, 변경성, 확장성** | 대화형 처리 곤란, 데이터 변환 오버헤드 | 데이터 파이프라인, 이미지/음성 처리, 컴파일러 |
| **계층형 (Layered)** | 레이어(Layer) / 프로시저 호출(Method) | **유지보수성, 테스트 용이성** | 계층 누적 시 성능 저하, 단순 위임 오버헤드 | 전통적 웹 애플리케이션, 엔터프라이즈 ERP |
| **이벤트 주도 (Event-Driven)** | 프로듀서·컨슈머 / 이벤트 채널 | **느슨한 결합, 성능/확장성** | 트랜잭션 원자성 보장 곤란, 흐름 추적성 결여 | IoT 스트리밍, 금융 실시간 이상거래 탐지, MSA |
| **저장소 (Repository / Blackboard)** | 클라이언트·지식소스 / 데이터베이스 | **데이터 무결성, 중앙 집중 관리** | 중앙 저장소 단일 실패점(SPOF), 병목 현상 | 지능형 음성인식 엔진, AI 전문가 시스템, DW/BI |

### 스타일별 품질속성 트레이드오프 매트릭스

| 품질속성 | 계층형 (Layered) | 파이프와 필터 | 이벤트 주도 (EDA) | 마이크로서비스 (MSA) |
|---|---|---|---|---|
| **전반적 비용** | **매우 낮음 (단순성)** | 낮음 | 중간 | 높음 (인프라 복잡) |
| **배포 용이성** | 중간 (일괄 배포) | 높음 | 높음 | **매우 높음 (독립 배포)** |
| **성능 (처리량)** | 중간 | 높음 (병렬 스트림) | **매우 높음 (비동기)** | 중간 (네트워크 홉 누적) |
| **확장성 (Scalability)** | 낮음 | 중간 | **매우 높음** | **매우 높음** |
| **테스트 용이성** | **매우 높음 (Mocking)** | 높음 | 낮음 (비동기 제어) | 중간 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 계층형 아키텍처에서 상위 계층이 하위 계층을 건너뛰고 DB에 직접 접근하는 레이어 침범(Sinkhole) | 아키텍처 린팅 도구(ArchUnit)를 적용하여 엄격한 레이어 참조 규칙(Closed Layer) 강제 집행 |
| 이벤트 주도 아키텍처(EDA)에서 이벤트 발행 순서 역전 및 메시지 중복 수신으로 인한 데이터 오염 | 멱등성(Idempotent) 컨슈머 패턴 및 Kafka 파티션 키 기반 순서 보장 큐잉 구축 |
| 유행에 편승하여 단순한 모놀리식 업무에 복잡한 EDA/MSA 스타일을 적용하여 유지보수 파탄 | 초기에는 모듈러 모놀리스로 시작하고 트래픽 임계치 도달 시 점진적 스타일 전환 |

## Ⅵ. 제언

헥사고날(Hexagonal, Ports & Adapters) 아키텍처 도입을 통한 도메인 코어 격리 및 하이브리드 아키텍처 합성

### 헥사고날 아키텍처(Ports & Adapters) 구조 및 파이프라인

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        [인프라 어댑터 계층 (외부)]                     │
│                                                                        │
│   [인바운드 어댑터]                               [아웃바운드 어댑터]   │
│   - REST API Controller                           - JPA / RDB Repository│
│   - Kafka Event Consumer                          - Redis Cache Client  │
│   - CLI Command                                   - 외부 결제 PG Client │
│          │                                               ▲              │
│          ▼ (인바운드 포트 호출)                          │ (포트 구현)  │
│   ┌──────────────────────────────────────────────────────┴──────────┐   │
│   │                    [도메인 코어 계층 (내부)]                    │   │
│   │                                                                 │   │
│   │   [Inbound Port (인터페이스)]   [Outbound Port (인터페이스)]    │   │
│   │              │                               ▲                  │   │
│   │              ▼                               │                  │   │
│   │        [비즈니스 유스케이스 서비스 (Business Use Case)]         │   │
│   │              │                               │                  │   │
│   │              └───────────────┬───────────────┘                  │   │
│   │                              ▼                                  │   │
│   │                  [도메인 엔티티 (Pure Java)]                    │   │
│   │                  ★ 프레임워크 종속성 0% 순수 비즈니스 로직      │   │
│   └─────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────┘
```

### 아키텍처 스타일 선정 의사결정 체계

```text
시스템 비즈니스 요구 분석
       ↓
[데이터 처리 방식이 단계별 변환 중심인가?]
       ├─ 예 ──→ 파이프와 필터 (Pipes & Filters) 스타일 채택
       └─ 아니오 ─→ [실시간 대규모 비동기 이벤트 분산 처리가 필요한가?]
                         ├─ 예 ──→ 이벤트 주도 아키텍처 (EDA) 채택
                         └─ 아니오 ─→ [도메인 코어를 외부 기술(DB, 프레임워크)로부터 완전 격리할 것인가?]
                                           ├─ 예 ──→ 헥사고날 / 클린 아키텍처 채택
                                           └─ 아니오 ─→ 전통적 3계층 아키텍처 (Layered) 채택
```

### 선택 근거: 전통적 계층형 아키텍처와 제언 헥사고날 아키텍처 비교

| 구분 | 전통적 계층형 (Layered) | 제언: 헥사고날 아키텍처 (Ports & Adapters) |
|---|---|---|
| 의존성 방향 | 상위 계층이 하위 DB 계층에 종속적 | 모든 의존성이 내부의 '도메인 코어'를 향함 (DIP) |
| DB 교체 용이성 | DB 변경 시 서비스 계층 코드 연쇄 수정 | 아웃바운드 어댑터만 교체하면 도메인 코드 무수정 |
| 비즈니스 테스트 | DB나 웹 프레임워크 목킹(Mock) 필수 | 외부 환경 없이 순수 도메인 단위 테스트 즉시 실행 |
