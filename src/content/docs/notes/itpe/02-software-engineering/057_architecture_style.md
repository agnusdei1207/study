## 연관 키워드

- 아키텍처 스타일(Architecture Style), 구성요소(Components), 커넥터(Connectors)
- 계층형(Layered), 이벤트 기반(EDA), 마이크로커널(Plugin), 마이크로서비스(MSA), 공간 기반(Space-Based)
- 품질속성 트레이드오프, 모놀리식 퍼스트(MonolithFirst), 스트랭글러 피그(Strangler Fig), ADR(Architecture Decision Record)

## Ⅰ. 아키텍처 스타일의 개요

- 핵심 요약 : 구성요소와 커넥터의 배치 패턴을 검증된 설계 유형으로 묶어, 품질속성 달성 방식을 미리 고르게 하는 체계.
- 개념 : **아키텍처 스타일**(Architecture Style)은 **구성요소**(Components)와 이를 잇는 **커넥터**(Connectors)의 배치 방식과 제약을 정리한 설계 유형의 집합이다.
- 배경 및 필요성 : 개발팀이 같은 아키텍처 어휘를 쓰고, 이미 검증된 구조를 재사용해야 성능, 가용성, 확장성, 변경 용이성 같은 품질속성을 설계 초기에 확보할 수 있다.
- 주요 목적 : 시스템 특성에 맞는 구조를 골라 품질, 비용, 일정의 균형을 맞추고, 아키텍처 의사결정을 표준화하는 것.

## Ⅱ. 아키텍처 스타일의 특징 및 장점

- 핵심 요약 : 스타일마다 구성요소 배치와 데이터 흐름이 달라 서로 다른 품질속성 트레이드오프를 제공.

1. **계층형**(Layered) : 계층마다 책임을 나누고 상위가 하위만 호출하는 단방향 구조 → 관심사 분리와 이해 용이성 확보. 다만 단순 조회에도 모든 계층을 거치는 **싱크홀**(Sinkhole) 안티패턴이 생길 수 있다.
2. **이벤트 기반**(EDA, Event-Driven Architecture) : 비동기 이벤트로 생산자와 소비자를 분리 → 수평 확장과 반응성 향상. 대신 분산 트랜잭션과 장애 추적이 복잡해진다.
3. **마이크로커널**(Microkernel, Plugin) : 최소 코어에 플러그인을 장착하는 구조 → IDE(Integrated Development Environment)나 브라우저 확장처럼 기능을 덧붙이는 제품에 적합.
4. **마이크로서비스**(MSA, Microservice Architecture) : 도메인 단위의 독립 서비스로 나눔 → 독립 배포와 확장이 쉬워지는 대신 네트워크 호출과 데이터 일관성 관리 비용이 늘어난다.
5. **공간 기반**(Space-Based) : 인메모리 데이터 그리드에 처리를 분산 → 급격한 트래픽 증가에서도 높은 처리 성능 확보.

## Ⅲ. 아키텍처 스타일의 구조 (흐름)

- 핵심 요약 : 계층형은 위에서 아래로 단방향 호출이 흐르고, 이벤트 기반은 브로커를 거쳐 비동기로 전달되는 구조.

```text
[ 계층형 (Layered) ]

Presentation (프레젠테이션)
        ↓ 단방향 호출
Business Logic (비즈니스 로직)
        ↓
Persistence (영속성)
        ↓
Database (데이터베이스)
```

```text
[ 이벤트 기반 (EDA) ]

[ Producer ] : 이벤트 발행
        ↓
[ Event Broker ] : 비동기 중계
        ↓
[ Consumer A ] : 구독 처리
[ Consumer B ] : 구독 처리
```

- 계층형 흐름의 핵심 : 상위 계층이 바로 아래 계층만 호출하도록 제한해 관심사를 분리.
- 이벤트 기반 흐름의 핵심 : 브로커 경유의 발행과 구독으로 생산자와 소비자의 결합도를 제거.

## Ⅳ. 대표 아키텍처 스타일의 품질속성 트레이드오프 비교

- 핵심 요약 : 민첩성, 배포 용이성, 성능, 확장성, 개발 용이성의 축에서 스타일마다 강점이 달라 비즈니스 드라이버 기준의 선택이 필요.

| 아키텍처 스타일 | 민첩성(Agility) | 배포 용이성 | 성능(Performance) | 확장성(Scalability) | 개발 용이성 |
| --- | --- | --- | --- | --- | --- |
| 계층형(Layered) | 낮음 | 낮음, 모놀리식 배포 | 보통, 계층 오버헤드 | 낮음 | 높음, 익숙함 |
| 마이크로커널(Plugin) | 높음 | 높음, 플러그인별 배포 | 높음 | 낮음 | 높음 |
| 이벤트 기반(EDA) | 높음 | 높음 | 높음, 비동기 처리 | 매우 높음 | 복잡함 |
| 마이크로서비스(MSA) | 매우 높음 | 매우 높음 | 보통, 네트워크 호출 | 매우 높음 | 복잡함 |
| 공간 기반(Space-Based) | 높음 | 높음 | 매우 높음, 인메모리 | 매우 높음 | 복잡함 |

```text
[ 스타일 선정 흐름 ]

비즈니스 드라이버 정의
        ↓
후보 스타일 도출
        ↓
품질속성 시나리오로 평가
        ↓
트레이드오프 절충 후 ADR 기록
```

## Ⅴ. 아키텍처 스타일 적용의 한계와 방안

- 핵심 요약 : 유행 추종, 스타일 고유의 대가 간과, 일괄 전환 실패라는 한계를 도메인 적합성 평가, 사전 정량 평가, 점진 전환으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 유행 추종형 선정 (Resume-Driven Architecture) | 단순한 도메인에도 MSA나 EDA를 도입해 네트워크 지연과 운영 비용 증가 | 초기에는 모듈러 모놀리스(Modular Monolith)로 출발하는 **모놀리식 퍼스트**(MonolithFirst) 전략을 쓰고, 규모에 따라 분산 스타일로 점진 진화 | 운영 비용 대비 효익 |
| 스타일 고유의 대가 간과 | 독립 배포만 강조해 분산 트랜잭션 일관성과 장애 추적 비용을 준비하지 못함 | 품질속성 시나리오별로 각 스타일의 페널티를 사전 평가하고, 비동기 메시징과 서비스 메시 같은 보완 패턴을 함께 구성 | 장애 추적 소요 시간 |
| 일괄 전환의 실패 | 모놀리식 시스템을 한 번에 분산 구조로 바꾸면 업무 공백과 데이터 불일치가 발생 | **스트랭글러 피그**(Strangler Fig) 패턴으로 외곽 도메인부터 분리하고, **CDC**(Change Data Capture)로 데이터를 무중단 동기화 | 전환 완료 도메인 비율 |

## Ⅵ. 엔터프라이즈 아키텍처 선정을 위한 기술사적 제언

- 핵심 요약 : 단일 스타일을 고집하지 않고 비즈니스 드라이버에 따라 스타일을 고르며, 혼합 구성은 ADR로 통합 관리할 것.

1. 비즈니스 드라이버 중심의 스타일 결정 : 빠른 출시와 도메인 격리가 중요한 영역에는 MSA를, 예측하기 어려운 트래픽 급증에 대비해야 하는 영역에는 공간 기반 구조를 두는 식으로, 도메인 적합성을 먼저 평가한다.
2. 혼합 구조의 거버넌스 : 실무에서는 계층형 코어 주변에 Kafka 같은 메시지 브로커와 플러그인 구조가 결합된 혼합 형태가 흔하므로, 영역별 스타일 선택 근거를 **ADR**(Architecture Decision Record)로 남겨 구조가 흐트러지지 않게 관리한다.

## Ⅶ. 결론

- 핵심 요약 : 아키텍처 스타일은 품질속성 트레이드오프의 목록이며, 도메인 적합성과 점진적 진화의 관점이 선택의 분기점.
- 시사점 : 스타일의 강점과 대가를 함께 보고 비즈니스 드라이버로 고르며, 점진 전환으로 유행 추종과 일괄 전환의 위험을 동시에 줄여야 한다.
