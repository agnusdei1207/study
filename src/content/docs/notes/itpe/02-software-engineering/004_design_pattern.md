## 연관 키워드

- 디자인 패턴(Design Pattern), GoF(Gang of Four), 생성 패턴(Creational Pattern), 구조 패턴(Structural Pattern), 행동 패턴(Behavioral Pattern)
- 싱글턴(Singleton), 팩토리 메서드(Factory Method), 프록시(Proxy), 옵저버(Observer), 무패턴 설계

## Ⅰ. 디자인 패턴의 개요

- 핵심 요약 : 반복되는 객체지향 설계 문제의 검증된 해법에 이름을 붙여 재사용하는 설계 지식 체계.
- 개념 : 특정 문맥에서 반복 발생하는 설계 문제와 참여 객체·협력 관계의 검증된 해법이 **디자인 패턴** (Design Pattern)이며, 생성·구조·행동의 3분류로 정리된 GoF (Gang of Four) 23개 패턴이 원형.
- 배경 및 필요성 : 유사한 설계 문제가 프로젝트마다 반복되는데 해법이 공유되지 않으면 재발명과 품질 편차가 누적되고 노하우가 숙련자의 암묵지로만 존재.
- 주요 목적 : 설계 자산의 재사용, 설계 의사소통 어휘의 공유, 변경에 유연한 구조의 확보.

## Ⅱ. 디자인 패턴의 특징 및 장점

- 핵심 요약 : 3분류가 각각 생성 방식·합성 구조·책임 협력의 복잡성을 분담해 설계 유연성을 확보.

1. 생성 패턴 : 객체 생성 절차의 캡슐화로 클라이언트 코드가 생성 방식에 의존하지 않게 구성 → 생성 방식 변경 시 수정 범위 축소. **싱글턴** (Singleton)·**팩토리 메서드** (Factory Method)가 대표.
2. 구조 패턴 : 클래스·객체를 더 큰 구조로 합성하는 방법의 규정 → 인터페이스 조합과 대리 구조의 유연한 확장. 어댑터·데코레이터·**프록시** (Proxy)가 대표.
3. 행동 패턴 : 객체 간 책임 분배와 통신 방식의 정의 → 상호작용의 결합도 감소. **옵저버** (Observer)·전략·커맨드가 대표.
4. 공통 어휘 : 패턴명 하나로 설계 의도·참여자·협력 구조 전달 → 설계 리뷰와 문서화 비용 절감.

## Ⅲ. 디자인 패턴의 구조 (흐름)

- 핵심 요약 : 문제를 3분류 중 어느 설계 축에 속하는지 판단한 뒤 참여 객체와 협력 관계에 패턴을 적용.

```text
생성 패턴 → 객체를 누가·언제 만드는가
구조 패턴 → 객체를 어떻게 조립하는가
행동 패턴 → 책임을 어떻게 나누는가
```

```text
[ 프록시 패턴 구조 예시 ]
클라이언트
   ↓ 동일 인터페이스 호출
프록시 (접근 검사·캐시·지연 생성)
   ↓ 필요 시 위임
실제 객체
```

- 상호 보완 : 생성 패턴이 만든 객체를 구조 패턴이 조립하고 행동 패턴이 협력 방식을 규정하는 식의 한 설계 내 결합 가능.
- 적용 절차 : 반복 문제 식별 → 분류 판단 → 후보 패턴의 의도·결과 비교 → 참여자·협력 구조의 구현.

## Ⅳ. 패턴 적용 설계와 무패턴 설계의 비교

- 핵심 요약 : 무패턴 설계는 문제마다 개별 해법이 난립하는 반면 패턴 적용 설계는 검증된 구조와 공통 어휘로 일관성 확보.
- 무패턴 설계 : **하드코딩** (Hard Coding, 값·구조를 코드에 직접 고정하는 방식)과 즉흥적 객체 구성으로 프로젝트마다 다른 해법이 산재하는 설계.

| 비교 축 | 패턴 적용 설계 | 무패턴 설계 |
| --- | --- | --- |
| 설계 결정 근거 | 검증된 패턴의 문맥·결과 | 개별 개발자의 즉흥 판단 |
| 의사소통 | 패턴명으로 구조의 즉시 전달 | 코드 정독 없이는 의도 파악 곤란 |
| 변경 대응 | 변화 지점이 인터페이스 뒤로 격리 | 변경 파장이 코드 전체로 확산 |
| 재사용성 | 참여 객체 역할의 재사용 가능 | 구현별 특화로 이식 곤란 |
| 비용 분포 | 추상화 도입 비용 선지출 | 초기 비용은 낮으나 유지보수 비용 누적 |

## Ⅴ. 디자인 패턴 적용의 한계와 방안

- 핵심 요약 : 남용·오용·학습 편차가 추상화 비용으로 전환되지 않도록 문제 크기 검증과 지식 공유 필요.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 패턴 남용 | 단순 문제에 과잉 추상화 → 간접층·클래스 수 증가 | 문제 크기와 단순 구현의 선행 비교 | 클래스·인터페이스 수 추세 |
| 오적용 | 문맥에 맞지 않는 패턴 → 유지보수 악화 | 패턴의 의도·결과를 리뷰에서 확인 | 패턴 적용 사유 기록률 |
| 학습 편차 | 팀원 간 패턴 이해 수준 차이 → 오용·혼란 | 사내 패턴 사용 가이드·예제 저장소 | 리뷰 패턴 관련 지적 건수 |

## Ⅵ. 디자인 패턴 확산에 대한 제언

- 핵심 요약 : 설계 표준·리뷰 제도·교육 체계의 결합으로 패턴 지식을 개인 경험이 아닌 조직 자산으로 전환.

1. 설계 표준 조직은 프로젝트별 패턴 사용 범위와 금지 사례를 설계 가이드에 명문화.
2. 개발 조직은 코드 리뷰 체크리스트에 패턴의 의도·참여자·대안 비교 항목을 포함해 남용·오용을 상시 점검.
3. 교육 체계는 신규 입사자 대상 3분류별 대표 패턴 실습 커리큘럼을 운영해 설계 어휘의 조직 내 공통화.

## Ⅶ. 결론

- 핵심 요약 : 디자인 패턴은 문맥에 맞게 선택될 때 설계 의사소통과 변경 대응력을 높이는 공용 설계 자산.
- 시사점 : 패턴의 가치는 적용 개수가 아니라 문제와 의도의 정합성에서 나옴.
