## 연관 키워드
- 스크래핑, 크롤링, 헤드리스 브라우저, HTML 파싱, DOM, Open API, robots.txt

### Ⅰ. 스크래핑의 개요

- 핵심 요약 : 웹 문서와 앱 화면에서 필요한 데이터를 프로그램으로 자동 추출·가공하는 기술.
- 개념 : 웹 사이트의 HTML(HyperText Markup Language) 문서나 모바일 앱의 화면에서 텍스트, 가격 정보, 이미지 같은 특정 데이터를 프로그래밍 도구로 자동 추출하고 가공하는 기술을 스크래핑(Scraping)이라 함.
- 배경 및 필요성 : 공식 Open API(Application Programming Interface)를 제공하지 않는 서비스의 데이터가 필요할 때 쓰이며, 가격 비교, 마이데이터 서비스, 시장 동향 분석 등에 활용됨.
- 주요 목적 : 비정형 웹 문서를 정형 데이터로 바꾸고 수집을 자동화해, 분석과 서비스의 데이터 파이프라인을 구축하는 것.

### Ⅱ. 스크래핑의 특징 및 장점

- 핵심 요약 : 요청·파싱·렌더링의 3대 기술 요소로 동작하며, 크롤링과는 수집 범위가 다르고 법적 제약이 따르는 기술.

1. HTTP(Hypertext Transfer Protocol) 클라이언트 : Requests, Axios 등으로 문서를 요청 → 원본 HTML 확보.
2. HTML 파서 : BeautifulSoup, Cheerio 등으로 DOM(Document Object Model) 트리를 탐색해 핵심 필드를 추출 → 정형 데이터로 변환.
3. 헤드리스 브라우저(Headless Browser) : Puppeteer, Playwright, Selenium 등으로 자바스크립트 렌더링과 클릭·스크롤·로그인을 재현 → SPA(Single Page Application) 같은 동적 페이지 수집.
4. 크롤링과의 구별 : 특정 페이지의 타깃 데이터를 정밀하게 추출하는 스크래핑과, 하이퍼링크를 따라 대량의 페이지를 순회하며 수집하는 크롤링(Crawling).
5. 법적·윤리적 제약 : robots.txt 규약, 저작권, 부정경쟁방지법 등의 준수 요구.

### Ⅲ. 스크래핑의 구조 (흐름)

- 핵심 요약 : URL 요청에서 정형 데이터 저장까지의 4단계 파이프라인과, 수집 방식을 고르는 판단 절차.

```text
[ 스크래핑 동작 프로세스 ]

타겟 URL 요청
  - HTTP GET 또는 헤드리스 브라우저 조작
   ↓
HTML 소스 획득
  - 동적 렌더링 콘텐츠 대기
   ↓
DOM 파싱과 탐색
  - XPath, CSS 선택자로 핵심 필드 추출
   ↓
정형 데이터 저장
  - RDB, NoSQL에 정제 후 적재
```

```text
[ 데이터 수집 방식 선택 흐름 ]

공식 Open API 제공 여부 확인
   ↓ 제공 : API 연동으로 종료
   ↓ 미제공
robots.txt 허용 범위 확인
   ↓
서버 부하 배려 (레이트 리미팅)
   ↓
법적 검토 (저작권·부정경쟁방지법)
   ↓
스크래핑 수행
```

- 스크래핑과 크롤링은 수집 범위가 다르다. 스크래핑은 원하는 데이터만 정밀하게 뽑는 작업이고, 크롤링은 웹 전체를 넓게 탐색해 인덱싱하는 작업임.

### Ⅳ. 스크래핑 방식별 비교

- 핵심 요약 : 처리 속도, 동적 콘텐츠 대응, 안정성 축에서 3가지 방식이 서로 다른 트레이드오프를 가짐.

| 비교 축 | 정적 HTML 파싱 | 헤드리스 브라우저 조작 | 비공식 백엔드 API 호출 |
|---|---|---|---|
| 장점 | 처리가 빠르고 메모리·CPU 소비가 적음 | 클릭, 스크롤, 로그인 같은 사용자 동작을 재현 가능 | 가공되지 않은 JSON 데이터를 직접 빠르게 수집 |
| 단점 | 자바스크립트로 렌더링되는 SPA 데이터는 수집 불가 | 브라우저 렌더링으로 느리고 자원 소모가 큼 | API 명세가 바뀌면 즉시 오작동, 인증 토큰 만료 위험 |
| 대표 도구 | BeautifulSoup, Scrapy, Cheerio | Puppeteer, Playwright, Selenium | 네트워크 분석 도구(개발자 도구, Charles) |

### Ⅴ. 스크래핑의 한계와 방안

- 핵심 요약 : Open API가 없는 환경에서 데이터를 확보하는 수단이지만, 파서 파손·자원 고갈·법적 리스크를 함께 안고 있음.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 웹 UI 잦은 변경에 따른 파서 파손 | HTML 태그, CSS 클래스명, DOM 계층이 바뀌면 하드코딩된 선택자가 무효화되어 파이프라인이 멈춤 | 시맨틱 태그와 텍스트 기준의 유연한 파싱 로직 적용, 선택자 변경을 감지하는 자동 점검 | 파싱 실패율, 파이프라인 중단 시간 |
| 헤드리스 브라우저 자원 고갈과 WAF 차단 | 동적 렌더링 인스턴스마다 메모리 점유가 커지고, WAF(웹 애플리케이션 방화벽)의 봇 탐지로 IP가 차단됨 | 브라우저 인스턴스 풀링(Resource Pooling)으로 자원 재사용, 요청 빈도 조절, 허용된 경로만 수집 | 인스턴스당 메모리 사용량, 차단 응답 비율 |
| 비공식 수집의 법적 리스크와 데이터 결측 | robots.txt를 무시하면 저작권·부정경쟁방지법 분쟁으로 번지고, 실시간 검증 체계가 없어 결측치가 생김 | 준법 검토 절차의 제도화, 공식 Open API 연동 또는 CDC(Change Data Capture, 변경 데이터 캡처) 기반 수집으로 전환 | 결측치 비율, 준법 검토 완료율 |

### Ⅵ. 지속 가능한 데이터 파이프라인 구축을 위한 기술사적 제언

- 핵심 요약 : 공식 API를 우선하는 전환과, 상대 서버를 보호하는 윤리적 수집 원칙이 지속 가능성의 두 기둥.

1. 공식 API 우선 전환 : 상대 서버의 UI 변경에 취약한 스크래핑을 줄이고 법적 분쟁을 피하기 위해, 정식 협약에 기반한 API 연동을 우선 추진해야 함.
2. 상대 서버를 배려하는 수집 원칙 : 병렬 요청을 무분별하게 늘리면 대상 서버가 장애를 겪으므로, 요청 간 지연 시간(Backoff Delay)과 비피크 시간대 배치를 적용하는 것을 기본 원칙으로 삼아야 함.

### Ⅶ. 결론

- 핵심 요약 : 스크래핑은 API가 없는 데이터를 수집하는 수단이지만, 법적 준수와 서버 배려가 지속 가능성의 전제 조건이다.
- 시사점 : API 우선 전환과 레이트 리미팅, 준법 검토의 체계화로 기술적 리스크와 법적 리스크를 함께 통제해야 한다.
