## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 시스템 연계 및 인터페이스 → 데이터 수집 및 연계 → **스크래핑(Scraping)**

## 30초 인출

- 본질: 웹 사이트의 HTML 문서나 앱 화면(UI)에서 비정형 또는 반정형 데이터를 분석하여 사전에 지정한 특정 필드의 정형 데이터만을 프로그래밍 방식으로 자동 추출하는 기술
- 메커니즘: HTTP 요청 및 헤드리스 브라우저(Puppeteer) 렌더링 → DOM 트리 파싱 및 XPath/CSS Selector 적용 → 데이터 추출 및 정규화(ETL) → 법적 검토 및 DB 적재
- 통찰: 대상 사이트의 UI 구조 변경 시 스크래퍼가 파손되고 과도한 트래픽 유발로 법적 분쟁(부정경쟁방지법)이 발생하므로 금융 마이데이터와 같은 표준 Open API로의 전환 필수

<details>
<summary>핵심 용어</summary>

- **Screen Scraping (스크래핑)** : 웹 페이지나 애플리케이션 화면에 표시된 시각적 데이터에서 필요한 특정 필드만을 자동으로 추출하여 가공하는 기술
- **Web Crawling (크롤링)** : 웹 크롤러(봇)가 인터넷상의 하이퍼링크를 재귀적으로 추적하여 웹 페이지 전체를 대량 수집하고 인덱싱하는 탐색 기술
- **DOM (Document Object Model)** : HTML/XML 문서를 트리 구조의 객체 모델로 표현하여 프로그래밍 언어가 요소와 속성을 조작할 수 있게 하는 W3C 표준
- **Headless Browser** : GUI 화면 표시 없이 백그라운드 메모리상에서 자바스크립트 엔진과 렌더링 파이프라인을 실행하는 가상 브라우저 (Puppeteer, Playwright)
- **Robots.txt** : 웹 사이트가 검색 로봇의 크롤링 및 스크래핑 접근 권한과 수집 허용 범위를 명시한 국제 로봇 배제 표준(REP)

</details>

## 2~4교시 25점 답안

## Ⅰ. 스크래핑의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 웹 서버로부터 수신한 HTML 문서나 화면상의 사용자 인터페이스(UI)를 파싱하여, 원하는 특정 비즈니스 데이터 항목만을 추출·정제하여 정형 데이터베이스로 적재하는 기술 |
| 목적 | 공식 API가 부재한 외부 웹 리소스의 자동화된 데이터 수집, 가격 비교 및 시장 분석, 비정형 데이터의 구조화된 데이터 자산화 |

## Ⅱ. 스크래핑의 핵심 특징

| 특징 | 의미 |
|---|---|
| 특정 필드 타겟팅 | 전체 웹 페이지를 긁어오는 크롤링과 달리 제품명, 가격, 일자 등 미리 지정한 특정 속성만 핀포인트 추출 |
| DOM 구조 종속성 | 웹 페이지의 HTML 태그 구조나 CSS 클래스명이 변경될 경우 데이터 추출 실패 및 선택자 수정 불가피 |
| 동적 렌더링 대응 | React, Vue 등 SPA(Single Page App)의 클라이언트 사이드 렌더링 처리를 위한 헤드리스 브라우저 활용 |
| 법적·보안적 제약 | 서비스 이용약관, robots.txt 준수 의무, 개인정보보호법 및 부정경쟁방지법 위반 소지 상존 |

## Ⅲ. 스크래핑 전주기 아키텍처 및 데이터 추출 프로세스

### 웹 스크래핑 전주기 파이프라인

```text
[타겟 웹 사이트 URL]
       │
       ▼ (1단계: 요청 및 렌더링)
┌────────────────────────────────────────────────────────────────────────┐
│ 수집 에이전트 (Scraping Agent)                                         │
│  - robots.txt 검사 및 요청 레이트 리밋 (Rate Limiting) 준수           │
│  - 정적 HTML: 경량 HTTP 클라이언트 (Axios / Requests)                  │
│  - 동적 JS 실행: 헤드리스 브라우저 (Puppeteer / Playwright) DOM 렌더링 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ HTML / DOM 수신
                                    ▼ (2단계: 구조 분석 및 파싱)
┌────────────────────────────────────────────────────────────────────────┐
│ 파서 및 선택자 엔진 (Parser & Selector Engine)                         │
│  - HTML 파싱 → W3C 표준 DOM 트리 생성                                  │
│  - CSS 선택자 (`div.product-price > span`) 또는 XPath (`//table//td[2]`)│
│  - 정규표현식(Regex)을 통한 비정형 텍스트 필터링                       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 원시 추출 데이터 (Raw Data)
                                    ▼ (3단계: 정제 및 검증)
┌────────────────────────────────────────────────────────────────────────┐
│ 데이터 변환 및 적재 파이프라인 (ETL)                                   │
│  - 통화 기호, 공백 제거, 날짜 표준 포맷(ISO 8601) 변환                │
│  - 필수 필드 Not-Null 검증 및 이상치(Outlier) 제거                    │
│  - 관계형 DB / Data Lake 적재 및 수집 메타데이터(출처, 타임스탬프) 기록 │
└────────────────────────────────────────────────────────────────────────┘
```

### 스크래핑 4단계 프로세스 상세 분석

| 단계 | 수행 명칭 | 핵심 기술 및 활동 내용 | 산출물 |
|---|---|---|---|
| **1단계** | **타겟 분석 및 권한 확인** | 대상 웹 페이지 네트워크 트래픽(XHR/Fetch) 분석, robots.txt 규약 및 법적 약관 검토 | 스크래핑 타당성 검토서 |
| **2단계** | **문서 수집 및 렌더링** | User-Agent 설정, 동적 자바스크립트 실행 완료 대기(Wait for Selector) | 원시 HTML/DOM 트리 |
| **3단계** | **선택자 매핑 및 데이터 추출**| BeautifulSoup, Cheerio 등을 활용한 노드 순회, 텍스트 및 속성(Attribute) 추출 | 원시 JSON/CSV 데이터 |
| **4단계** | **정제, 검증 및 저장** | 결측치 처리, 데이터 타입 캐스팅, 중복 제거 후 DB 저장 및 모니터링 경보 설정 | 최종 정형 데이터셋 |

## Ⅳ. 스크래핑 vs 크롤링 vs 표준 API 비교

### 데이터 수집 및 연계 방식 비교

| 비교 항목 | 웹 스크래핑 (Scraping) | 웹 크롤링 (Crawling) | 제언: 표준 Open API |
|---|---|---|---|
| **수집 대상** | **웹 페이지 내부의 특정 목표 데이터 필드** | **인터넷상의 수많은 웹 페이지 전체** | **제공자가 규격화하여 개방한 데이터셋** |
| **동작 메커니즘** | 지정된 URL 접속 후 DOM 선택자로 추출 | 하이퍼링크를 재귀적으로 추적하여 인덱싱 | HTTP GET/POST 표준 요청 및 JSON 응답 |
| **구조 변경 영향**| **화면 UI 변경 시 즉각 파손 (취약함)** | 링크 구조만 유지되면 비교적 영향 적음 | **버전 관리(v1, v2)로 완벽한 안정성 보장** |
| **원천 서버 부하** | 반복적인 전체 화면 렌더링으로 부하 큼 | 대규모 요청 시 크롤러 봇에 의한 부하 유발 | 캐싱 및 필요한 데이터만 전송하여 부하 최소 |
| **법적 안정성** | 이용약관 및 저작권 분쟁 가능성 상존 | robots.txt 준수 시 검색 서비스 합법 | **명시적 이용 계약 체결로 법적 분쟁 제로** |
| **실무 적용 사례** | 금융 마이데이터 구 방식, 이커머스 가격 추적 | 구글/네이버 검색엔진 인덱서, 아카이빙 | **금융 마이데이터 표준 API**, 공공데이터포털 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 웹 페이지 디자인 개편이나 CSS 클래스명 변경 시 선택자 미스매치로 데이터 수집 전면 중단 | 정규 배포 모니터링 체계를 구축하고 의미론적 태그(Semantic Tag) 기반 다중 선택자 폴백 구성 |
| 대규모 동시 요청으로 인해 타겟 웹 서버의 CPU/네트워크 부하 가중 및 IP 차단(WAF) 발생 | 수집 간격 딜레이(Throttling)를 적용하고 야간 시간대 배치 분산 수집 스케줄링 적용 |
| 금융 고객의 인증서/비밀번호를 스크래핑 업체가 보관하는 데 따른 치명적 보안 유출 위험 | 고객 자격증명 보관을 금지하고 OAuth 2.0 인가 기반의 공인 마이데이터 표준 API 강제 전환 |

## Ⅵ. 제언

안정적인 데이터 거버넌스를 위한 Open API First 전환 로드맵 및 자동 치유(Self-healing) 스크래퍼

### 레거시 스크래핑의 표준 API 전환 파이프라인

```text
[스크래핑 의존 레거시 데이터 파이프라인]
       ↓
[1단계: 데이터 제공 기관과의 B2B 파트너십 체결]
  ├─ 금융결제원 / 마이데이터 표준 API 포털 가입
  └─ 상호 신뢰 OAuth 2.0 / mTLS 인증 체계 수립
       ↓
[2단계: 어댑터 패턴 기반 점진적 API 전환]
  ├─ 기존 스크래퍼 호출부를 API 클라이언트로 대체
  └─ 스크래핑 fallback 로직은 API 미제공 영역에만 임시 유지
       ↓
[3단계: 완전한 API 기반 실시간 데이터 스트리밍 안착]
  ├─ 웹훅(Webhook) 및 웹소켓을 통한 변경 데이터 실시간 수신
  └─ 취약한 화면 스크래핑 모듈 완전 영구 폐기
```

### 데이터 수집 방식 선정 의사결정 체계

```text
외부 데이터 수집 요구 발생
       ↓
[대상 기관이 공식 REST / GraphQL API를 제공하는가?]
       ├─ 예 ──→ 표준 Open API 채택 (계약 체결 및 API Key 발급)
       └─ 아니오 ─→ [대상 데이터가 대외 공개 데이터이며 robots.txt에서 허용하는가?]
                         ├─ 아니오 ─→ 수집 중단 (법적 분쟁 리스크 방지)
                         └─ 예 ───→ 웹 스크래핑 채택 (최소 트래픽 가드레일 준수)
```

### 선택 근거: 전통적 화면 스크래핑과 제언 금융 마이데이터 표준 API 비교

| 구분 | 화면 스크래핑 (Screen Scraping) | 제언: 표준 Open API (MyData API) |
|---|---|---|
| 보안성 | 고객의 공인인증서 비밀번호를 서버에 평문 보관 | OAuth 2.0 인가 토큰(Token) 사용으로 비밀번호 불필요 |
| 처리 속도 | 웹 화면 렌더링에 건당 5~10초 이상 소연 | JSON 바이너리 통신으로 수백 밀리초(ms) 내 응답 |
| 서비스 신뢰성 | 은행 웹 개편 시 수시로 스크래핑 장애 발생 | 표준 API 규격 준수로 장애 없는 무중단 서비스 제공 |

## 출제 이력과 검증 출처

- 금융 마이데이터 제도 시행(2022년) 및 스크래핑 금지 행정 지도

- IETF RFC 9309: Robots Exclusion Protocol
