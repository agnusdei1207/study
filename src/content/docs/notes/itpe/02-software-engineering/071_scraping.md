## 1. 스크래핑의 개요 및 등장 배경

### (1) 스크래핑(Scraping)의 정의
- 원천 시스템에서 공식 연계 API를 제공하지 않는 환경에서, 사용자 화면에 렌더링되는 **HTML/DOM 구조를 소프트웨어가 자동 파싱하여 필요한 특정 데이터 항목만을 추출·가공하는 기술**.
- 초기 핀테크 자산관리 서비스 및 전자정부 민원 자동화의 핵심 연계 수단으로 활용되었으나, 보안 및 안정성 이슈로 점차 표준 API로 대체됨.

### (2) 등장 배경 및 한계점
- **등장 배경**: 이종 기관 간 데이터 연계 수요 급증 대비 금융사·공공기관의 폐쇄적 데이터 제공 정책과 표준 API 인프라 부재.
- **구조적 한계**: 사용자 인증정보(공인인증서·패스워드)를 제3자 서버에 수탁·보관해야 하는 보안 취약점과 원천 웹사이트 UI/DOM 변경 시 파서가 즉각 중단되는 높은 유지보수 부하.

## 2. 스크래핑의 동작 메커니즘 및 기술 요소

### (1) 스크린 스크래핑 동작 구조도
```text
+-------------------------------------------------------------------------+
|                스크린 스크래핑의 동작 절차 및 메커니즘                  |
+-------------------------------------------------------------------------+
| [ 사용자 단말 ] --(1. 인증서/PW 위탁)--> [ 핀테크 스크래핑 서버 ]       |
|                                                  │                      |
|                         +────────────────────────+                      |
|                         │ 2. 세션 에뮬레이션 (대리 로그인)              |
|                         v                                               |
|             [ 원천 기관 웹서버 ] (금융사/정부24)                        |
|                         │                                               |
|                         │ 3. 전체 HTML 화면 응답                        |
|                         v                                               |
|             [ 스크래핑 엔진 (파서) ] ──▶ Headless Browser / DOM Parser  |
|                         │                (XPath, Regular Expression)    |
|                         │ 4. 데이터 추출·정제 (잔액, 거래내역)          |
|                         v                                               |
|             [ 핀테크 앱 대시보드 ] (사용자에게 통합 자산 정보 표출)     |
+-------------------------------------------------------------------------+
```

### (2) 스크래핑 핵심 기술 요소
| 기술 요소 | 기능 및 역할 | 주요 구현 기술 및 도구 |
|---|---|---|
| **가상 브라우저 (Headless)** | GUI 화면 없이 백그라운드에서 브라우저 렌더링 및 JS 실행 에뮬레이션 | Puppeteer, Selenium, Playwright, PhantomJS |
| **DOM / XPath 파서** | HTML 계층 트리를 탐색하여 지정된 태그, 속성, 텍스트 노드 추출 | Beautiful Soup, Cheerio, lxml, XPath, CSS Selector |
| **인증 에뮬레이터** | 로그인 세션 쿠키, 토큰, 공인인증서 서명 절차를 코드로 자동 수행 | 전자서명 라이브러리, Session 관리 모듈, CAPTCHA 우회 |
| **데이터 정제기 (ETL)** | 비정형 HTML 텍스트에서 불필요한 공백·태그를 제거하고 정형 데이터(JSON)화 | Regex, Data Mapping Engine, Schema Validator |

## 3. 스크래핑 vs 표준 API 비교

| 비교 항목 | 스크린 스크래핑 (Screen Scraping) | 표준 API (Standard API / OAuth 2.0) |
|---|---|---|
| **연계 방식** | 비공식 화면(DOM) 캡처 및 파싱 | 공식 RESTful 인터페이스 규격 (JSON/XML) |
| **보안 메커니즘** | 사용자 인증정보(ID/PW, 인증서) 직접 위탁 보관 (취약) | OAuth 2.0 토큰 기반 인가 (권한 범위 한정, 안전) |
| **시스템 부하** | 대용량 HTML, 이미지 동시 로딩으로 원천 서버 트래픽 폭증 | 순수 데이터(Payload)만 송수신하여 네트워크 부하 최소화 |
| **변경 안정성** | UI 스타일/태그 변경 시 즉시 수집 장애 발생 (유지보수 극심) | API 버저닝 관리(Semantic Versioning)로 하위 호환성 보장 |
| **법적·제도적 위상** | 마이데이터 사업자 사용 전면 금지 (보안 규제) | 전자금융거래법 및 신용정보법상 합법적 표준 연계 방식 |

## 4. 실무 실패 시나리오 및 해결 방안

| 실패 시나리오 | 근본 원인 | 공학적 해결 방안 | 정량적 기대효과 |
|---|---|---|---|
| **원천 포털 UI 개편으로 수집 마비**<br>(대고객 자산조회 서비스 전면 중단) | 웹 디자이너의 HTML class 명칭 변경으로 DOM 셀렉터 탐색 실패 | XPath 상대 경로 룰 자동 복구(Auto-Healing) 엔진 및 표준 API 전환 추진 | 파서 장애 복구 시간 90% 단축, 표준 API 전환 시 장애 원천 제거 |
| **스크래핑 봇으로 인한 원천 서버 다운**<br>(대량 트래픽으로 서비스 거부 상태) | 핀테크 앱 갱신 요청 시 전체 웹 리소스를 무차별 헤드리스 요청 | 호출 주기 제어(Rate Limiting), 분산 캐싱 및 웹소켓 알림 기반 증분 조회 | 원천 서버 네트워크 부하 85% 절감 및 IP 차단 방지 |
| **인증 자격증명 DB 탈취 사고**<br>(공인인증서 비밀번호 외부 유출) | 스크래핑 편의를 위해 사용자 금융 인증서를 서비스 서버에 집중 보관 | 사용자 로컬 기기 내 스크래핑 모듈 탑재(클라이언트 스크래핑) 및 OAuth 전환 | 중앙 서버 자격증명 저장 원천 배제, 개인정보 침해 사고 0건 |

## 5. 기술사 답안 차별화 포인트 (기술사의 시각)

```text
[과거: 스크린 스크래핑 (데이터 독점)]      [현재: 마이데이터 표준 API (데이터 주권)]
- 폐쇄적 금융망의 틈새 연계 기술    ──▶    - 국가 표준 오픈 API 인프라 구축
- 인증정보 탈취 및 트래픽 과부하   ──▶    - OAuth 2.0 기반 최소 권한 인가
- UI 변경 시마다 유지보수 비용 발생 ──▶    - 규격화된 JSON 스키마로 안정성 확보
```

- **마이데이터(MyData) 제도의 기술적 본질**: 스크래핑 금지와 표준 API 의무화는 단순 기술 교체가 아닌, **'데이터의 소유권이 기업에서 개인(정보주체)에게로 이전되는 데이터 주권(Data Sovereignty)의 기술적 구현'**임.
- **공공·의료 마이데이터로의 확장 제언**: 금융권에서 성공적으로 정착된 OAuth 2.0 기반 표준 API 모델을 전 산업(의료 진료기록, 통신 과금, 유통 구매내역)으로 표준화 확대하고, API 호출 과금 모델(API Monetization)과 서비스 수준 협약(SLA)을 법제화하여 안정적 데이터 생태계를 구축해야 함.
