## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 요구공학 → **요구공학(요구사항 유형 포함)**

## 30초 인출

- 본질: 요구공학은 소프트웨어 요구사항을 도출·분석·명세·검증·관리하는 공학 활동
- 메커니즘: 요구를 도출해 분석하고 명세서에 정리한 뒤 검증하며, 변경은 요구사항 관리로 통제하고 각 요구를 설계·시험까지 추적
- 통찰: 요구 오류는 후반에 발견될수록 수정 비용이 크므로 요구마다 ID와 검증 기준을 부여하고 요구사항 추적표로 설계·시험까지 연결

<details>
<summary>핵심 용어</summary>

- **요구공학(Requirements Engineering)** : 요구사항의 도출·분석·명세·검증·관리를 체계적으로 수행하는 활동
- **기능 요구사항** : 시스템이 제공해야 하는 기능
- **비기능 요구사항** : 성능·보안·신뢰성처럼 기능의 품질 조건
- **제약사항** : 기술·법규·예산처럼 설계를 제한하는 조건
- **요구사항 명세서(SRS, Software Requirements Specification)** : 요구사항을 기능·비기능·제약으로 정리한 문서
- **요구사항 추적표(RTM)** : 요구사항과 설계·구현·시험을 연결한 표

</details>

## 2~4교시 25점 답안

## Ⅰ. 요구공학의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **요구공학** 은 요구사항을 도출·분석·명세·검증·관리하는 공학 활동 |
| 목적 | 이해관계자가 원하는 시스템의 정확한 정의와 개발 후반 변경 비용 감소 |

## Ⅱ. 요구공학의 필요성과 특징

| 특징 | 의미 |
|---|---|
| 필요성 | 요구 오류가 후반에 발견될수록 수정 비용 급증 |
| 이해관계자 합의 | 사용자·발주자·개발자의 요구 조율 |
| 변경 관리 | 요구 변경의 영향 분석과 통제 |

## Ⅲ. 요구공학 절차와 요구사항 유형

### 요구공학 절차

```text
요구사항 도출
    ↓
요구사항 분석 (충돌·우선순위 조정)
    ↓
요구사항 명세
    ↓
요구사항 검증 ←→ 요구사항 관리(변경·추적)
```

### 확대: 요구사항 유형

```text
요구사항
    ├─ 기능 ── 시스템이 제공할 기능
    ├─ 비기능 ── 성능·보안·신뢰성 등 품질 조건
    └─ 제약사항 ── 기술·법규·예산 조건
```

## Ⅳ. 요구사항 명세서

### 명세서의 구성

| 항목 | 내용 |
|---|---|
| 개요 | 목적·범위·용어 |
| 기능 요구사항 | 요구 ID별 기능 설명 |
| 비기능 요구사항 | 성능·보안 등 측정 가능한 기준 |
| 제약사항 | 법규·기술·운영 환경 조건 |
| 추적 정보 | 요구 출처와 우선순위 |

### 좋은 요구사항의 조건

| 조건 | 의미 |
|---|---|
| 명확성 | 한 가지로만 해석 |
| 검증 가능성 | 시험 가능한 기준 포함 |
| 추적 가능성 | 고유 ID로 설계·시험 연결 |
| 일관성 | 요구 간 충돌 없음 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 모호한 요구로 해석 차이 발생 | 측정 가능한 기준을 요구사항에 명시 |
| 요구 변경 통제 부재로 범위 잠식 | 변경 요청의 영향 분석·승인 절차 |
| 요구가 설계·시험에 반영됐는지 확인 곤란 | 요구사항 추적표로 연결 |

## Ⅵ. 제언

요구사항마다 ID와 검증 기준을 부여하고, 추적표로 설계·시험까지 연결해 반영 여부를 확인

### 추적 구조

```text
요구사항 ID
    ├─ 설계 요소
    ├─ 구현 모듈
    └─ 시험 케이스
```

### 확대: 변경 시 영향 확인

```text
요구 변경 요청
    ↓
추적표로 영향받는 설계·시험 식별
    ↓
승인 후 일괄 수정
```

### 선택 근거: 문서 중심 관리와의 비교

| 구분 | 문서 중심 관리 | 제언: ID·추적 관리 |
|---|---|---|
| 반영 확인 | 사람 기억 의존 | 추적표로 확인 |
| 변경 영향 | 파악 곤란 | 연결로 식별 |
| 검증 기준 | 불명확 | 요구마다 명시 |
