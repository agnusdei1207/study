## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 요구공학·설계 → **요구공학**

## 30초 인출

- 본질: 고객의 암묵적이고 모호한 요구사항을 정확히 도출, 분석, 명세, 검증하고, 시스템 생명주기 전반에 걸쳐 요구사항의 변경과 추적성을 체계적으로 통제하는 소프트웨어 공학 체계
- 메커니즘: 요구사항 개발(RD: 도출 → 분석 → 명세 → 검증)의 순환적 피드백 루프와 요구사항 관리(REQM: 기준선 수립, 변경통제위원회 CCB, 요구사항 추적표 RTM)의 유기적 결합
- 통찰: 요구사항 오류의 뒤늦은 발견은 기하급수적인 수정 비용을 유발하므로 정형 인스펙션 기반 조기 검증과 RTM을 통한 전주기 양방향 추적성 보장 필수

<details>
<summary>핵심 용어</summary>

- **Requirements Engineering(요구공학)** : 요구사항의 획득, 문서화, 검증 및 수명주기 변경 관리를 다루는 체계적 공학 분야
- **RD (Requirements Development)** : 이해관계자의 요구를 바탕으로 정형화된 명세서를 완성하기까지의 도출, 분석, 명세, 검증 4단계 활동
- **REQM (Requirements Management)** : 승인된 요구사항 기준선(Baseline)을 형상 관리하고 변경 영향 분석 및 추적성을 통제하는 활동
- **SRS(Software Requirements Specification)** : 시스템의 기능적/비기능적 요구와 제약사항을 정형화하여 기술한 공식 요구사항 명세서
- **RTM(Requirements Traceability Matrix)** : 요구사항 ID를 설계, 소스코드, 테스트 케이스와 1:1로 양방향 연결한 추적표
- **Scope Creep(범위 잠식)** : 공식적인 변경 통제 절차 없이 요구사항이 무분별하게 추가되어 일정과 예산이 파탄에 이르는 현상

</details>

## 2~4교시 25점 답안

## Ⅰ. 요구공학의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 이해관계자의 모호하고 잠재적인 요구를 체계적으로 수집, 분석, 명세, 검증하여 공식 기준선을 수립하고, 소프트웨어 생명주기 전반에 걸쳐 변경과 추적성을 통제하는 공학적 프로세스 |
| 목적 | 사용자-개발자 간 의사소통 왜곡 방지, 요구사항 결함의 조기 발견을 통한 개발 비용 절감, 과업 범위 잠식 방지 및 품질 보증 |

## Ⅱ. 요구공학의 핵심 특징

| 특징 | 의미 |
|---|---|
| 이원적 프레임워크 | 요구사항을 만들어가는 **개발(RD)** 과 변경을 통제하는 **관리(REQM)** 가 상호 보완적 결합 |
| 전주기 양방향 추적성 | 비즈니스 니즈부터 요구사항, 아키텍처 설계, 구현 소스코드, 인수 테스트까지 상호 추적(RTM) 보장 |
| 반복적 정제(Iteration) | 폭포수식 일회성 확정을 탈피하고 프로토타이핑과 지속적 피드백을 통해 요구사항 완성도 제고 |
| 검증 가능성(Testability) | 명세된 모든 요구사항은 향후 시스템 테스트 및 인수 테스트에서 참/거짓으로 검증 가능해야 함 |

## Ⅲ. 요구공학 프로세스 체계 및 RD-REQM 상호작용

### 요구사항 개발(RD) 및 요구사항 관리(REQM) 통합 아키텍처

```text
┌────────────────────────────────────────────────────────────────────────┐
│               [요구사항 개발 (Requirements Development, RD)]            │
│                                                                        │
│   [1. 요구사항 도출 (Elicitation)]                                     │
│     - 인터뷰, 브레인스토밍, 워크숍, 설문조사, 사용자 관찰               │
│         │                                                              │
│         ▼                                                              │
│   [2. 요구사항 분석 (Analysis)]                                        │
│     - 기능/비기능 분류, 도메인 모델링(DFD, UML), 충돌 해소 및 우선순위 │
│         │                                                              │
│         ▼                                                              │
│   [3. 요구사항 명세 (Specification)]                                   │
│     - 표준 SRS 작성 (ISO/IEC/IEEE 29148 규격), 유스케이스 명세서       │
│         │                                                              │
│         ▼                                                              │
│   [4. 요구사항 검증 (Validation)] ◄───┐                                │
│     - 인스펙션(Fagan), 프로토타이핑, 워크스루 ─ (결함 발견 시 피드백) ─┘ │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (공식 검증 완료)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│           [요구사항 기준선 수립 (Requirements Baseline)]               │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│               [요구사항 관리 (Requirements Management, REQM)]           │
│                                                                        │
│   [형상관리 및 버전 통제] ◄─────→ [변경통제위원회 (CCB) 심의]           │
│     - SRS 문서의 버전 분기           - 변경 요청서(CR) 접수            │
│     - Git/ALM 기반 태깅             - 기술 타당성 및 비용/일정 영향 분석│
│                                      - 공식 승인 / 반려 결정           │
│                                           │                            │
│                                           ▼                            │
│   [요구사항 추적표 (RTM) 관리] ────────────────────────────────────────┤
│     - 요구사항 ID ↔ 설계(UML) ↔ 소스코드 ↔ 테스트 케이스(TC) 양방향 추적 │
└────────────────────────────────────────────────────────────────────────┘
```

### 요구사항 개발(RD) 4대 단계 세부 활동

| 단계 | 주요 기법 및 도구 | 산출물 | 핵심 점검 항목 |
|---|---|---|---|
| **1. 도출 (Elicitation)** | 인터뷰, 설문지, 브레인스토밍, 사용자 관찰, JAD/RAD | 요구사항 수집 목록, 면담 일지 | 이해관계자 누락 여부, 잠재 니즈 발굴 여부 |
| **2. 분석 (Analysis)** | DFD, UML 유스케이스 모델링, MoSCoW 우선순위화 | 요구사항 분석 모델, 도메인 모델 | 요구사항 간 모순 및 중복 제거, 실현 가능성 |
| **3. 명세 (Specification)** | 자연어 명세, 정형 기법, IEEE 29148 표준 템플릿 | 소프트웨어 요구사항 명세서(SRS) | 명확성, 완전성, 무모순성, 검증 가능성 |
| **4. 검증 (Validation)** | Fagan 인스펙션, 동료 검토, 프로토타이핑, 체크리스트 | 요구사항 검증 보고서, 결함 조치표 | 사용자 의도 부합성, 테스트 케이스 도출 가능성 |

## Ⅳ. 요구사항 개발(RD) vs 요구사항 관리(REQM) 비교

### 두 영역 간의 역할 및 특성 비교

| 비교 항목 | 요구사항 개발 (RD) | 요구사항 관리 (REQM) |
|---|---|---|
| **핵심 목적** | 무엇을 만들 것인가를 정의하고 명세서 완성 | 정의된 요구사항의 변경을 통제하고 일관성 유지 |
| **주요 활동** | 도출, 분석, 모델링, 정형 명세, 인스펙션 검증 | 기준선 설정, 형상 관리, 변경 요청(CR) 심의, RTM 추적 |
| **수행 시점** | 프로젝트 초기 기획 및 분석 단계에 집중 수행 | 개발 착수부터 인도, 운영 유지보수 전주기 지속 수행 |
| **핵심 조직** | 비즈니스 분석가(BA), 도메인 전문가, 사용자 | 프로젝트 관리자(PM), 형상관리자, 변경통제위원회(CCB) |
| **주요 통제 도구**| UML 도구, 프로토타이핑 도구, SRS 템플릿 | Jira, Confluence, 요구사항 관리 시스템(DOORS), RTM |

### 우수한 요구사항 명세서(SRS)의 6대 품질 속성 (IEEE 29148)

| 품질 속성 | 정의 및 의미 | 위반 시 발생 문제 |
|---|---|---|
| **명확성 (Unambiguous)** | 모든 이해관계자에게 오직 하나의 의미로만 해석 | 개발자와 고객 간 동상이몽 및 재작업 발생 |
| **완전성 (Complete)** | 시스템이 제공해야 할 모든 기능, 비기능, 제약조건 포함 | 프로젝트 후반 미식별 요구사항 돌출 및 일정 지연 |
| **일관성 (Consistent)** | 요구사항 간에 논리적 충돌이나 모순이 없어야 함 | 구현 단계에서 아키텍처 충돌 및 코드 재작성 초래 |
| **검증 가능성 (Verifiable)** | 요구사항 만족 여부를 객관적 테스트로 입증 가능 | 인수 시험 시 합격/불합격 판정 불가로 분쟁 발생 |
| **수정 용이성 (Modifiable)** | 요구사항의 구조와 스타일이 변경에 유연하게 대응 | 요구 변경 시 관련 문서 전체 수정으로 오버헤드 폭증 |
| **추적 가능성 (Traceable)** | 요구사항의 출처와 구현 산출물이 고유 ID로 연결 | 변경 시 영향도 분석 불가 및 코드 누락 발생 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 구두 합의에 의한 비공식 요구사항 추가로 프로젝트 범위 잠식(Scope Creep) 발생 | 변경통제위원회(CCB)의 공식 CR 접수 및 공수 평가를 거치지 않은 요구사항 개발 차단 |
| 자연어로 기술된 SRS의 모호성으로 인해 개발자가 자의적으로 해석하여 오구현 | Given-When-Then 문법 기반의 BDD(행위 주도) 명세 및 인수 조건(Acceptance Criteria) 필수화 |
| 요구사항 변경 후 설계서와 테스트 케이스가 동기화되지 않아 형상 불일치 심화 | ALM 도구를 통해 요구사항 ID와 Git 커밋, 테스트 코드를 강제 연동하는 자동 추적 환경 구축 |

## Ⅵ. 제언

ALM(Application Lifecycle Management) 기반 디지털 RTM 자동화 및 생성형 AI 기반 요구사항 검증 파이프라인

### 디지털 RTM 자동화 및 변경 영향도 추적 파이프라인

```text
[요구사항 변경 요청 (CR) 인입]
       ↓
[디지털 RTM 그래프 자동 탐색 (Jira/Confluence/Git)]
  ├─ 1. 상위 요구사항 ID 식별 (REQ-042)
  ├─ 2. 매핑된 설계 다이어그램 추출 (UML Class/Sequence)
  ├─ 3. 연관 소스코드 파일 및 PR 자동 조회 (Git Commit Tag)
  └─ 4. 영향받는 테스트 케이스 목록 식별 (TC-101 ~ TC-105)
       ↓
[변경 영향도 및 소요 공수 자동 산출 보고서 생성]
       ↓
[CCB 전자 심의 및 승인 → 승인 즉시 RTM 및 관련 테스트 케이스 자동 갱신]
```

### 요구공학 실무 단계별 의사결정 체계

```text
비즈니스 요구사항 접수
       ↓
[이해관계자의 도메인 이해도가 충분하고 요구사항이 명확한가?]
       ├─ 예 ──→ 표준 정형 SRS 명세 및 Fagan 인스펙션 수행
       └─ 아니오 ─→ [프로토타입 개발] 및 사용자 시연 피드백 수행
                         ↓
           [모든 요구사항에 대해 검증 가능한 인수 기준(AC)이 정의되었는가?]
                         ├─ 아니오 ─→ 정량적 수치 기반 비기능 기준 보완
                         └─ 예 ───→ 요구사항 기준선(Baseline) 동결 및 CCB 발족
```

### 선택 근거: 전통적 스프레드시트 관리와 ALM 기반 디지털 요구공학 비교

| 구분 | 전통적 수기 엑셀 요구사항 정의서 | 제언: ALM 기반 디지털 요구공학 |
|---|---|---|
| 변경 추적성 | 수작업 업데이트 지연으로 문서와 소스코드 불일치 | 커밋 및 PR 시 요구사항 ID 태깅을 통한 실시간 양방향 추적 |
| 영향도 분석 | 담당자의 기억과 경험에 의존하여 누락 빈발 | 의존성 그래프 탐색을 통해 영향받는 소스/테스트 즉시 식별 |
| 버전 관리 | 파일명 버전(v1.1, v1.2) 관리로 히스토리 추적 한계 | Git 기반의 완전한 문서 변경 이력 및 브랜치 병합 추적 |
