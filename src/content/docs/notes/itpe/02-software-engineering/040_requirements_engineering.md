## 연관 키워드

- 요구공학(Requirements Engineering), 요구사항 명세서(SRS, Software Requirements Specification), ISO/IEC/IEEE 29148
- 요구사항 도출·분석·명세·검증·관리, RTM(Requirements Traceability Matrix), CCB(Change Control Board), 기능·비기능 요구사항, Boehm의 법칙

## Ⅰ. 요구공학의 개요

- 핵심 요약 : 이해관계자의 요구를 발견·분석·명세·검증·변경 관리해 검증 가능한 SRS로 완성하는 공학 프로세스.
- 개념 : 이해관계자의 모호하고 복잡한 요구(Needs)를 체계적으로 발견·분석·명세·검증하고 변경을 관리하여 검증 가능한 요구사항 명세서(SRS, Software Requirements Specification)로 완성하는 공학적 프로세스 (**요구공학**, Requirements Engineering).
- 배경 및 필요성 : 소프트웨어 결함은 요구사항 단계에서 많이 유입되고, 결함 수정 비용은 개발 후반으로 갈수록 크게 증가하므로(**Boehm의 법칙**) 상류 단계에서 결함을 차단할 필요가 있음.
- 표준 체계 : ISO/IEC/IEEE 29148은 요구공학의 국제표준으로, 요구사항 프로세스와 명세 내용의 기준을 제시.
- 주요 목적 : 검증 가능한 요구사항 명세를 완성하고, 생명주기 전반에서 요구사항과 산출물 사이의 추적성을 확보하는 것.

## Ⅱ. 요구공학의 특징 및 장점

- 핵심 요약 : 도출·분석·명세·검증의 4대 프로세스와 변경 관리의 피드백이 결합해 요구의 품질과 합의 수준을 함께 높이는 체계.

1. 도출(Elicitation) : 고객, 사용자, 도메인 전문가 등 이해관계자에게서 잠재된 요구를 수집 → 누락된 요구를 개발 전에 드러냄.
2. 분석(Analysis) : 모호성, 중복, 상충을 해소하고 기능적·비기능적 요구로 분류해 DFD(Data Flow Diagram), UML(Unified Modeling Language) 등으로 모델링 → 요구 간 모순을 구현 전에 발견.
3. 명세(Specification) : 정형화된 서식으로 SRS를 작성 → 발주자와 구현자가 같은 문서를 기준으로 합의.
4. 검증(Validation) : 명세가 사용자 의도를 반영하는지, 완결성과 일관성과 검증 가능성을 인스펙션으로 검토 → 잘못된 명세가 설계로 넘어가는 것을 차단.
5. 관리(Management) : 베이스라인을 세우고 CCB로 변경을 통제하며 **RTM**(Requirements Traceability Matrix, 요구사항 추적 매트릭스)으로 추적성을 유지 → 변경의 영향 범위를 빠르게 파악.

## Ⅲ. 요구공학의 구조 (흐름)

- 핵심 요약 : 4대 프로세스의 순차 흐름 위에 변경 관리 피드백 루프가 얹힌 구조.

```text
[ 요구공학 4대 프로세스 ]
도출 (Elicitation)
      ↓
분석 (Analysis)
      ↓
명세 (Specification)
      ↓
검증 (Validation)
      ↓ 불일치 시 재도출
도출 단계로 회귀
```

```text
[ 요구사항 변경 관리 흐름 ]
1. 변경 요청 접수
      ↓
2. RTM 기반 영향도 분석
      ↓
3. CCB 심의 (변경통제위원회)
      ↓ 승인 시
4. 베이스라인 갱신과 산출물 전파
```

## Ⅳ. 기능적 요구사항과 비기능적 요구사항의 비교

- 핵심 요약 : 시스템이 무엇을 하는지(기능)와 얼마나 잘 하는지(품질·제약)를 나누어 정의하는 기준.

| 구분 | 기능적 요구사항 (Functional) | 비기능적 요구사항 (Non-Functional) |
| --- | --- | --- |
| 개념 | 시스템이 무엇(What)을 수행해야 하는지에 대한 동작 정의 | 동작할 때 만족해야 하는 품질(How Well)과 제약 조건 |
| 예시 | 결제 승인, 회원가입, 상품 검색, 영수증 출력 | 응답 시간, 동시 접속자 수, 가용성, 보안성 |
| 주요 도출 주체 | 현업 비즈니스 사용자, 업무 실무자 | 시스템 아키텍트, 보안 담당자, 인프라 엔지니어 |
| 검증 방식 | 단위·통합·인수 테스트의 Pass/Fail | 성능·부하·스트레스 테스트, 보안 진단, 가용성 측정 |
| 아키텍처 영향 | 개별 컴포넌트의 내부 로직과 데이터 모델에 영향 | 시스템 전체의 아키텍처 스타일과 인프라 구조를 결정 |

- 선택 기준 : 비기능 요구는 측정 가능한 목표 수치로 적고, 기능 요구는 입력과 출력이 명확한 시나리오로 적어 두 구분의 검증 방식을 맞춘다.

## Ⅴ. 요구공학의 한계와 방안

- 핵심 요약 : 요구 변동, 자연어 모호성, 추적성 단절을 변경 통제, 정형 명세, 도구 기반 추적으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 요구 불명확성과 범위 변동 (Scope Creep) | 고객이 원하는 모습을 미리 정의하지 못해 개발 중 요구가 계속 바뀌고 납기 지연 유발 | 프로토타이핑과 사용자 스토리 맵으로 요구를 조기에 가시화하고, CCB로 변경 영향도를 공식 평가 | 변경 요청 건수, 승인 후 변경 비율 |
| 자연어 명세의 모호성 | 다의적 해석으로 발주자, 설계자, 개발자, 테스터의 이해가 어긋나 중대 결함 유발 | Given-When-Then 형식의 시나리오, 의사결정 테이블, 상태 전이 다이어그램을 병행해 해석 여지를 줄임 | 명세 해석 차이로 인한 재작업 건수 |
| 추적성 단절 | 변경 시 설계, 소스코드, 테스트 케이스 간 영향 분석을 수작업으로 해 누락과 불일치 발생 | ALM(Application Lifecycle Management) 도구로 요구사항부터 테스트까지 양방향 추적을 자동 연동 | 추적 링크 누락률, 영향도 분석 소요 시간 |

## Ⅵ. 요구공학에 대한 기술사적 제언

- 핵심 요약 : 비기능 요구를 테스트 가능한 목표로 정량화하고, 추적 관리를 도구로 자동화하는 두 축의 정착.

발주 조직은 "빠른 응답"이나 "편리한 화면"처럼 주관적인 비기능 요구를 명세에서 걷어내고, 부하 조건과 응답 목표를 함께 적은 측정 가능한 SLA(Service Level Agreement, 서비스 수준 협약) 형태로 쓰도록 요구해야 한다. 그래야 성능 테스트가 합격과 불합격을 판정할 수 있다.

요구사항 명세, 설계 문서, 소스 커밋, 테스트 케이스를 잇는 추적 관리는 정보시스템 부서가 ALM 도구와 연계해 맡는 편이 현실적이다. 변경이 들어올 때 영향도 분석이 자동으로 수행되면 CCB 심의도 근거를 갖춘 채로 열릴 수 있다.

## Ⅶ. 결론

- 핵심 요약 : 요구공학은 결함을 상류에서 차단하고 추적성을 확보하는 소프트웨어 품질의 출발점.
- 시사점 : 요구를 정량적으로 명세하고 추적을 자동화해야 변경 리스크를 개발 초기에 통제할 수 있음.
