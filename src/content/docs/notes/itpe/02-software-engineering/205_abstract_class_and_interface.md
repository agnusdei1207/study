## 연관 키워드

- 추상 클래스(Abstract Class), 인터페이스(Interface), 다형성(Polymorphism), 추상화(Abstraction)
- 단일 상속(extends), 다중 구현(implements), 템플릿 메서드 패턴(Template Method Pattern), 디폴트 메서드(Default Method), 인터페이스 분리 원칙(ISP, Interface Segregation Principle)

## Ⅰ. 추상 클래스와 인터페이스의 개요

- 핵심 요약 : 설계 골격과 행위 규약을 나누어 정의해 다형성 기반의 결합도 완화를 실현하는 객체지향 추상화 메커니즘.
- 개념 : 객체지향 프로그래밍(OOP, Object-Oriented Programming)에서 구체 구현을 하위 클래스에 맡기고 상위 설계 규약을 정의하는 장치로, 상태와 구현 코드를 일부 가질 수 있고 단일 상속을 하는 **추상 클래스** (Abstract Class)와, 공개된 행위 계약만 명시하고 다중 구현을 하는 **인터페이스** (Interface)로 나뉨.
- 배경 및 필요성 : 호출하는 쪽이 구체 클래스를 몰라도 되도록 **다형성** (Polymorphism, 같은 호출이 객체 종류에 따라 다르게 동작하는 특성)을 실현해야 하며, 이를 위한 **추상화** (Abstraction, 세부를 숨기고 본질만 드러내는 설계)가 필요함.
- 기본 구분 : 추상 클래스는 is-a(본질적 분류) 관계, 인터페이스는 can-do(수행 가능한 역할) 관계를 나타냄.

## Ⅱ. 추상 클래스와 인터페이스의 특징 및 장점

- 핵심 요약 : is-a 본질 상속과 can-do 행위 규약의 역할 분담, 템플릿 메서드와 다중 구현의 메커니즘 차이.

1. 추상 클래스는 공통 상태(멤버 변수)와 기본 로직을 공유하는 미완성 클래스 → 중복 코드를 상위에 모음.
2. **템플릿 메서드 패턴** (Template Method Pattern, 상위 클래스가 알고리즘 골격을 정하고 세부 단계만 하위 클래스가 구현하는 GoF(Gang of Four) 디자인 패턴) : 실행 순서는 고정하고 변동 부분만 위임 → 흐름 일관성 확보.
3. 인터페이스는 클래스가 '무엇을 할 수 있는가'를 선언하는 행위 규약 → 호출자가 구현 종류와 무관하게 기능을 사용.
4. **다중 구현** (implements) : 한 클래스가 여러 인터페이스를 구현 → 단일 상속의 제약을 넘어 역할을 조합.
5. Java 8 이후 인터페이스에 **디폴트 메서드** (Default Method, 인터페이스 안에 기본 구현을 둘 수 있는 기능) 도입 → 기존 인터페이스에 메서드를 추가해도 구현체 수정이 줄어듦.
6. 두 메커니즘 모두 구체 타입에 의존하지 않는 다형성 호출을 지원 → 결합도 감소와 교체 용이성 향상.

## Ⅲ. 추상 클래스와 인터페이스의 구조 (흐름)

- 핵심 요약 : is-a 본질을 추상 클래스 상속으로, can-do 역할을 인터페이스 구현으로 나누는 설계 구조.

```text
[ 추상 클래스 : Bird (is-a 상속) ]
 - 공통 상태 : protected int age
 - 템플릿 메서드 : eat(), breathe()
 - 추상 메서드 : makeSound() (하위 위임)
      ↓ Duck이 상속하고 역할을 추가
[ 인터페이스 : Flyable (can-do) ]
 + void fly()
[ 인터페이스 : Swimmable (can-do) ]
 + void swim()
```

```text
[ 설계 의도 분석 ]
      ↓
[ 공통 상태와 기본 로직 공유가 목적인가? ]
      ↓ 예 : 추상 클래스 (템플릿 메서드)
      ↓ 아니오
[ 여러 역할 규약을 조합해야 하는가? ]
      ↓ 예 : 인터페이스 (다중 구현)
      ↓ 아니오 또는 불확실
[ 구체 클래스로 시작, 필요 시 추출 ]
```

## Ⅳ. 추상 클래스와 인터페이스의 비교 (Java 8 이후 기준)

- 핵심 요약 : 상속 관계, 다중성, 상태 보유, 구현 제공, 생성자, 설계 목적의 여섯 축에서 두 메커니즘이 달라짐.

| 비교 항목 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) |
| --- | --- | --- |
| 관계 | is-a 관계 (본질적 상위 분류) | can-do 관계 (역할과 행위 규약) |
| 상속·구현 | 단일 상속만 허용 (extends) | 다중 구현 허용 (implements) |
| 상태 보유 | 인스턴스 변수 선언 가능 | public static final 상수만 허용 |
| 구현 제공 | 일반 메서드와 생성자 구현 가능 | default 메서드와 static 메서드만 허용 |
| 생성자 | 가질 수 있음 (하위 클래스가 호출) | 가질 수 없음 |
| 설계 목적 | 공통 상태와 기본 로직의 재사용 | 다형성 기반 결합도 완화와 규약 정의 |

- 선택 기준 : 공유할 상태나 기본 로직이 있으면 추상 클래스, 여러 역할을 조합해야 하면 인터페이스를 우선 검토.

## Ⅴ. 추상 클래스와 인터페이스의 한계와 방안

- 핵심 요약 : 역할 경계의 모호성, 비대한 인터페이스, 과도한 추상화의 한계를 역할 분리와 점진적 추상화로 통제.

- 장점 : 호출자와 구현자의 결합도 완화, 공통 로직의 상위 집중에 따른 중복 제거, 계약 기반 설계로 컴포넌트 간 책임 명확화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 역할 경계 모호 | 인터페이스도 기본 구현을 가져 두 메커니즘의 역할이 겹치고 다중 구현 시 충돌(다이아몬드 문제) 발생 | 상태와 재사용이 목적이면 추상 클래스, 순수 계약이 목적이면 인터페이스로 설계 원칙 정립 | 충돌 해결 코드 수 |
| 비대한 인터페이스 (Fat Interface) | 여러 구현체가 필요 없는 메서드까지 떠안아 빈 구현을 강제 | **인터페이스 분리 원칙** (ISP, Interface Segregation Principle, 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 나누는 객체지향 설계 원칙)에 따라 역할별 인터페이스로 분할 | 인터페이스당 메서드 수 |
| 과도한 추상화 | 구현체가 하나뿐인데도 인터페이스와 추상 클래스를 중첩해 추적 비용만 증가 | **YAGNI** (You Aren't Gonna Need It, 필요가 확정되기 전에는 만들지 않는다는 원칙)에 따라 구체 클래스로 시작하고 필요 시 추상화를 추출 | 추상 계층 깊이 |

## Ⅵ. 객체지향 설계에 대한 기술사적 제언

- 핵심 요약 : 상속보다 합성을 우선하고 인터페이스를 작게 나누는 설계가 결합도를 낮추는 기본 방향이다.
- 깊은 상속 계층은 부모와 자식이 내부 구현을 공유하게 만들어 캡슐화를 약화시키므로, 역할은 인터페이스로 정의하고 기능은 객체 **합성** (Composition, 다른 객체를 필드로 조립해 기능을 얻는 방식)으로 조립하는 것이 바람직하다.
- 인터페이스에는 한 역할에 필요한 메서드만 두고, 단일 추상 메서드를 가진 경우에는 `@FunctionalInterface`를 붙여 람다식과 함께 쓰는 방식으로 구현 부담을 줄이는 것이 좋다.

## Ⅶ. 결론

- 핵심 요약 : 추상 클래스는 공통 구현의 재사용, 인터페이스는 행위 규약의 다형성을 담당하므로 목적에 따라 나누어 씀.
- 시사점 : 합성 우선, 작은 인터페이스, 필요 시점의 추상화가 유지보수성 높은 객체지향 설계의 기준이 됨.
