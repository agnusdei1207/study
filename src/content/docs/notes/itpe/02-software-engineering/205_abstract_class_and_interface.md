## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 객체지향·설계 → **추상 클래스와 인터페이스**

## 30초 인출

- 본질: 추상 클래스는 공통 상태와 일부 구현을 가진 채 직접 생성할 수 없는 상위 클래스이고 인터페이스는 구현 없이 제공해야 할 동작의 규약만 선언하는 타입
- 메커니즘: 하위 클래스는 추상 클래스를 상속해 공통 구현을 재사용하며 미완성 메서드를 채우고, 클래스는 여러 인터페이스를 구현해 서로 다른 계층의 객체도 같은 규약으로 다룸
- 통찰: 추상 클래스에 공통 코드를 얹어 상속 계층을 깊게 만들면 결합이 커지므로 역할 규약은 인터페이스로 정의하고 공통 구현이 필요할 때만 추상 클래스를 두며 상속보다 조합을 우선

<details>
<summary>핵심 용어</summary>

- **추상 클래스(Abstract Class)** : 직접 인스턴스를 만들 수 없고 추상 메서드와 구현된 메서드·상태를 가질 수 있는 클래스
- **인터페이스(Interface)** : 구현이 따라야 할 메서드 규약을 선언한 타입
- **다형성(Polymorphism)** : 같은 타입으로 다른 구현 객체를 다루는 성질
- **디폴트 메서드(Default Method)** : 인터페이스에 제공하는 기본 구현
- **상속보다 조합(Composition over Inheritance)** : 상속 대신 객체를 포함해 기능을 재사용하라는 지침

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **추상 클래스** 는 일부 구현을 가진 미완성 상위 클래스, **인터페이스** 는 동작 규약만 선언하는 타입 |
| 목적 | 구현 교체 가능한 설계와 공통 코드 재사용 |

## Ⅱ. 특징

| 특징 | 의미 |
|---|---|
| 직접 생성 불가 | 하위 구현이 필요 |
| 다형성 | 상위 타입으로 하위 구현 객체 사용 |
| 규약과 구현의 분리 | 호출자는 구현을 몰라도 사용 |

## Ⅲ. 구조

```text
           <<interface>> Payment          AbstractPayment
                 ▲   ▲                    (공통 로직 + 추상 메서드)
                 │   │                         ▲
         CardPayment BankPayment ── 상속 ── CardPayment
```

인터페이스는 여러 개를 구현할 수 있고, 추상 클래스는 하나만 상속

## Ⅳ. 추상 클래스와 인터페이스의 비교

| 구분 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 상태(필드) | 가질 수 있음 | 상수 위주 |
| 구현 | 일부 구현 포함 | 규약 중심(기본 구현은 디폴트 메서드) |
| 상속·구현 | 하나만 상속 | 여러 개 구현 |
| 관계 | 같은 계열의 공통 부모(is-a) | 역할·능력의 규약(can-do) |
| 적합 조건 | 공통 코드 재사용 | 서로 다른 구현의 교체 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 추상 클래스 상속이 깊어져 결합 증가 | 상속보다 조합 사용 |
| 인터페이스 변경 시 모든 구현체 수정 | 디폴트 메서드 활용과 인터페이스 안정화 |
| 하나의 부모만 상속 가능 | 역할은 인터페이스로 분리 |

## Ⅵ. 제언

역할과 규약은 인터페이스로 정의하고 공통 구현이 필요할 때만 추상 클래스를 두며, 기능 재사용은 상속보다 조합 우선

```text
역할·교체 필요 → 인터페이스
공통 코드 재사용 필요 → 추상 클래스(필요 시에만)
기능 재사용 → 조합
```

| 구분 | 추상 클래스 중심 | 제언: 인터페이스 + 조합 |
|---|---|---|
| 결합 | 상속 계층에 결합 | 규약에 결합 |
| 교체 | 계층 변경 필요 | 구현 교체 |
