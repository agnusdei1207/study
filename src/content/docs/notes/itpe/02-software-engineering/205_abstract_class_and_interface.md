소프트웨어공학 → 객체지향 프로그래밍 → 추상화·타입 설계 → **추상 클래스와 인터페이스**

## 30초 인출

- 본질: 추상 클래스와 인터페이스는 객체의 공통 책임과 상호작용 규약을 정의하여 구현체를 추상화하고 결합도를 낮추는 객체지향 핵심 메커니즘
- 메커니즘: 추상 클래스는 단일 상속 기반 상태·골격 구현 공유, 인터페이스는 다중 구현 기반 표준 행위 계약 선언을 통해 클라이언트의 다형적 호출 지원
- 통찰: 공통 상태와 기본 로직 재사용에는 추상 클래스, 이기종 컴포넌트 간 독립적 역할 정의와 다중 상속 효과에는 인터페이스를 적용하며 인터페이스 기반 설계와 조합 패턴을 우선 고려

<details>
<summary>핵심 용어</summary>

- **추상 클래스(Abstract Class)** : 인스턴스화가 불가능하며 추상 메서드, 구체 메서드, 멤버 변수(상태)를 모두 포함할 수 있는 단일 상속 기반 상위 클래스
- **인터페이스(Interface)** : 객체가 수행해야 하는 행위의 계약(Contract)을 선언하는 참조 타입으로 다중 구현 지원
- **다형성(Polymorphism)** : 상위 타입을 통해 서로 다른 하위 구현체를 일관된 인터페이스로 호출하는 객체지향 특성
- **디폴트 메서드(Default Method)** : 인터페이스 내에 기본 구현 코드를 제공하여 하위 호환성을 보장하는 인스턴스 메서드(Java 8+)
- **상속보다 조합(Composition over Inheritance)** : 클래스 상속에 따른 강한 결합을 피하고 객체 합성 및 인터페이스 위임을 통해 유연성을 확보하는 설계 원칙

</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **추상 클래스와 인터페이스** 는 객체지향 패러다임에서 공통 타입과 행위 규약을 정의하여 구체 클래스의 세부 구현을 은닉하고 다형성을 보장하는 핵심 추상화 메커니즘 |
| 목적 | 구체 클래스 간 직접 의존 해소 및 결합도 완화, 표준화된 계약 기반 모듈 교체 용이성 확보 |

## Ⅱ. 핵심 특징

| 특징 | 세부 설명 | 기대 효과 |
|---|---|---|
| 추상화 계층 분리 | 선언부(What)와 구현부(How)를 물리적·논리적으로 분리 | 클라이언트 코드의 구현 세부 종속 방지 |
| 다형성(Polymorphism) | 상위 타입 참조 변수를 통해 다양한 하위 구현체를 단일 인터페이스로 제어 | OCP(개방-폐쇄 원칙) 및 DIP(의존 역전 원칙) 준수 |
| 상태 및 행위 캡슐화 | 추상 클래스는 인스턴스 변수와 공통 메서드를 공유하며, 인터페이스는 불변 상수와 순수 규약 정의 | 객체 무결성 보장 및 무분별한 상태 공유 차단 |
| 결합도 완화 | 클라이언트가 구체 구현 클래스가 아닌 인터페이스 또는 상위 추상 클래스에 의존 | 컴포넌트 간 결합도 최소화 및 단위 테스트 용이성(Mocking) 증대 |

클라이언트는 구체 구현 클래스가 아닌 상위 추상화 타입에 의존함으로써 실행 시점에 동적으로 구현체를 교체 가능.

## Ⅲ. 체계·프로세스

### 1. 추상 클래스와 인터페이스의 아키텍처 구조

```text
[클라이언트 계층]
      │ (의존: Interface / Abstract Type)
      ▼
┌────────────────────────────────────────────────────────┐
│               추상화 계층 (Abstraction Layer)          │
│                                                        │
│  <<Interface>> Printable         <<Abstract>> Device    │
│  - print(): void                 - id: String (상태)   │
│                                  + turnOn(): void      │
│                                  # execute(): void*    │
└────────────────────────────────────────────────────────┘
      ▲ (implements)                      ▲ (extends)
      │                                   │
┌─────┴───────────────────────────────────┴──────────────┐
│               구현 계층 (Implementation Layer)          │
│                                                        │
│  [SmartPrinter]                                        │
│  - print(): void 구현                                   │
│  - execute(): void 구현                                 │
└────────────────────────────────────────────────────────┘
```

### 2. 설계 및 적용 프로세스

```text
[요구사항 및 도메인 분석]
          │
          ▼
[공통 책임 및 역할 식별] ──── 상태(필드) 및 기본 구현 공유 필요? ───► YES ──► [추상 클래스 설계]
          │                                                                      │
          ▼ NO                                                                   │
[순수 행위 계약 및 다중 구현 필요?] ──────────────────────────────── YES ──► [인터페이스 설계]
          │                                                                      │
          ▼                                                                      ▼
[클라이언트 의존 역전(DIP) 적용] ◄───────────────────────────────────────────────┘
          │
          ▼
[상속 대신 조합(Composition) 검토 및 최종 아키텍처 확정]
```

## Ⅳ. 종류·비교

| 비교 항목 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) |
|---|---|---|
| 선언 키워드 | `abstract class` | `interface` |
| 다중 상속 여부 | 단일 상속만 지원 (`extends`) | 다중 구현 지원 (`implements`) |
| 포함 멤버 구성 | 멤버 변수(상태), 생성자, 추상/일반 메서드 | 상수 필드(`static final`), 추상/디폴트/정적/프라이빗 메서드 |
| 접근 제한자 | `public`, `protected`, `package-private` 등 다양 | 메서드는 기본적으로 `public` (Java 9 private 지원) |
| 설계 관점 | IS-A 관계 (본질적 분류 계층, 상태 공유) | CAN-DO / IS-A-KIND-OF 관계 (역할 및 행위 계약) |
| 주 사용 목적 | 골격 구현 재사용(템플릿 메서드 패턴), 공통 상태 관리 | 표준 규약 정의, 의존성 역전, 다중 인터페이스 구현을 통한 역할 부여 |
| 확장 유연성 | 상속 계층 고착화로 변경 영향도 높음 | 새로운 인터페이스 추가가 기존 계층에 영향을 주지 않아 유연 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 상속 계층의 깊이 심화 및 강한 결합 | 무분별한 클래스 상속을 지양하고 '상속보다는 조합(Composition over Inheritance)' 원칙을 적용하여 위임 패턴 활용 |
| 거대 인터페이스화(Fat Interface)로 인한 불필요한 의존 | ISP(인터페이스 분리 원칙)를 준수하여 역할을 단일 책임 단위로 잘게 분리(Role Interface) |
| 인터페이스 변경 시 하위 구현체 파급 영향 | Java 8 디폴트 메서드(Default Method)를 활용하여 기존 구현체의 수정 없이 신규 기능 기본 확장 제공 |
| 지나친 추상화로 인한 코드 가독성 저하 및 오버헤드 | 도메인 복잡성과 변경 가능성을 검토하여 실질적인 다형성이 요구되는 지점에만 선별적 추상화 적용 |

## Ⅵ. 제언

추상 클래스와 인터페이스는 상호 배타적 선택 대상이 아니며, 인터페이스를 통해 시스템의 공개 계약(Contract)을 정의하고 추상 골격 구현 클래스(Abstract Skeletal Implementation)를 통해 공통 로직을 보조하는 유연한 하이브리드 아키텍처 수립이 핵심.

```text
[인터페이스 중심 하이브리드 아키텍처]
   <<Interface>> List
        ▲
        │ implements
   <<Abstract>> AbstractList (공통 알고리즘 및 골격 구현 제공)
        ▲
        │ extends
   [ArrayList] / [Vector] (특화된 데이터 구조 및 물리적 구현)
```

| 아키텍처 구성요소 | 역할 | 설계 전략 |
|---|---|---|
| 인터페이스 (Interface) | 외부 모듈과의 결합 계약 정의 | 역할 기반 분리(ISP) 및 다형성 확보 |
| 골격 추상 클래스 (Skeletal Class) | 중복 코드 제거 및 템플릿 제공 | 선택적 상속을 통한 개발 생산성 향상 |
| 구체 구현 클래스 (Concrete Class) | 환경별 비즈니스 로직 완성 | 조합 및 전략 패턴 결합을 통한 확장성 극대화 |
