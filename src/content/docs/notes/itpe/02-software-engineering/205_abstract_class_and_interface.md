## Ⅰ. 추상 클래스와 인터페이스의 개요

- **개념** : 객체지향 프로그래밍(OOP)에서 객체의 구체적인 구현 세부사항을 하위 클래스에 위임하고 고수준의 설계 청사진과 규약을 정의하기 위한 추상화 메커니즘으로, 구현 코드와 상태(멤버 변수)를 부분적으로 가질 수 있는 단일 상속 기반의 '추상 클래스(Abstract Class)'와 오직 공개된 행위 계약만을 명시하는 다중 구현 기반의 '인터페이스(Interface)'.
- **배경 및 필요성** : 다형성(Polymorphism)을 실현하여 호출자와 구현자 간의 결합도를 낮추고, 코드의 재사용성과 확장성을 극대화하기 위해 필수.
- **철학적 구분** : 추상 클래스는 'is-a(존재론적 본질)' 관계이며, 인터페이스는 'can-do(기능적 행위 규약)' 관계.

## Ⅱ. 추상 클래스와 인터페이스의 구조적 메커니즘

```text
   [ 추상 클래스: Bird (is-a 본질 상속) ] ── (단일 상속: extends)
    - 공통 상태 (protected int age) 보유
    - 템플릿 메서드 구현 (공통 로직: eat(), breathe())
    - 미완성 추상 메서드 위임 (abstract void makeSound())
            ▲
            │
   [ 구체 클래스: Duck ] ───────────────────┐
            │                               │
            ▼ (다중 실체화: implements)     ▼
   [ 인터페이스: Flyable (can-do 행위) ]   [ 인터페이스: Swimmable (can-do 행위) ]
    + void fly() (순수 계약)                + void swim() (순수 계약)
```

- **추상 클래스 (Abstract Class)** : 하나 이상의 추상 메서드를 포함할 수 있는 미완성 클래스로, 하위 클래스들이 상태와 공통 로직을 공유하면서 세부 구현만 특화하도록 템플릿 메서드 패턴(Template Method Pattern) 제공.
- **인터페이스 (Interface)** : 클래스가 '무엇을 할 수 있는가'를 선언하는 순수 규약으로, 다중 구현(Multiple Implementation)을 통해 클래스 계층 구조에 얽매이지 않고 유연하게 행위 부여.

## Ⅲ. 추상 클래스와 인터페이스의 핵심 비교 (Java 8+ 기준)

| 비교 항목 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) |
|---|---|---|
| 상속/구현 관계 | is-a 관계 (개념적 상위 분류) | can-do 관계 (역할 및 행위 규약) |
| 다중 상속 여부 | 단일 상속만 허용 (`extends`) | 다중 구현 완벽 허용 (`implements`) |
| 상태(멤버 변수) 보유 | 인스턴스 변수(상태)를 자유롭게 선언 가능 | 오직 `public static final` 상수만 허용 |
| 구현 메서드 제공 | 일반 메서드 및 생성자 자유롭게 구현 | Java 8+ 디폴트 메서드(`default`), 정적 메서드만 제한적 허용 |
| 생성자 (Constructor) | 생성자를 가질 수 있음 (자식 호출) | 생성자를 절대 가질 수 없음 |
| 주된 설계 목적 | 공통된 상태와 기본 로직의 코드 재사용 | 다형성을 통한 결합도 완화 및 컴포넌트 규약 정의 |

## Ⅳ. 객체지향 클린 아키텍처를 위한 기술사적 제언

- **상속을 통한 코드 재사용보다 인터페이스와 합성(Composition) 우선 원칙 준수** : 추상 클래스를 깊게 상속받으면 부모와 자식 간의 캡슐화가 깨지고 강결합이 발생하므로, GoF 원칙에 따라 인터페이스를 통해 역할을 정의하고 필요한 기능은 객체 합성으로 조립하는 설계를 최우선 권장.
- **인터페이스 분리 원칙(ISP)을 통한 가벼운 인터페이스 설계** : 인터페이스에 메서드를 과도하게 많이 선언하면 구현 클래스들이 사용하지도 않는 메서드를 억지로 빈 껍데기로 구현해야 하므로, 단일 목적에 부합하는 작은 인터페이스(단일 기능인 경우 `@FunctionalInterface` 활용)로 잘게 분리하여 람다식과의 호환성 극대화.
