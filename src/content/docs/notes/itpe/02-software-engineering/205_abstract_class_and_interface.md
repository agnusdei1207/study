## 연관 키워드

- 추상 클래스(Abstract Class), 인터페이스(Interface), 다형성(Polymorphism), 추상화(Abstraction)
- 단일 상속(extends), 다중 구현(implements), 템플릿 메서드 패턴(Template Method Pattern), 디폴트 메서드(Default Method), 인터페이스 분리 원칙(ISP, Interface Segregation Principle)

## Ⅰ. 추상 클래스와 인터페이스의 개요

- 핵심 요약 : 설계 청사진과 행위 규약을 정의하여 다형성 기반 결합도 완화를 실현하는 객체지향 추상화 메커니즘.
- 개념 : 객체지향 프로그래밍(OOP, Object-Oriented Programming)에서 객체의 구체적인 구현 세부사항을 하위 클래스에 위임하고 고수준의 설계 청사진과 규약을 정의하기 위한 추상화 메커니즘으로, 구현 코드와 상태(멤버 변수)를 부분적으로 가질 수 있는 단일 상속 기반의 '추상 클래스(Abstract Class)'와 오직 공개된 행위 계약만을 명시하는 다중 구현 기반의 '인터페이스(Interface)'.
- 배경 및 필요성 : 다형성(Polymorphism)을 실현하여 호출자와 구현자 간의 결합도를 낮추고, 코드의 재사용성과 확장성을 극대화하기 위한 필수 장치.
- 철학적 구분 : 추상 클래스는 'is-a(존재론적 본질)' 관계이며, 인터페이스는 'can-do(기능적 행위 규약)' 관계.

## Ⅱ. 추상 클래스와 인터페이스의 특징

- 핵심 요약 : is-a 본질 상속과 can-do 행위 규약의 역할 분담, 템플릿 메서드와 다중 구현의 메커니즘 차이.

1. 추상 클래스 : 공통 상태(멤버 변수)와 기본 로직을 공유하는 미완성 클래스.
2. 추상 클래스 : 세부 구현만 하위 클래스에 특화시키는 템플릿 메서드 패턴(Template Method Pattern) 제공.
3. 인터페이스 : 클래스가 '무엇을 할 수 있는가'를 선언하는 순수 행위 규약.
4. 인터페이스 : 다중 구현(Multiple Implementation)을 통한 클래스 계층에 얽매이지 않는 유연한 행위 부여.
5. Java 8 이후 인터페이스의 디폴트 메서드(Default Method)·정적 메서드 도입에 따른 구현 제공 가능.
6. 두 메커니즘 모두 구체 타입에 의존하지 않는 다형성 기반 호출 지원.

## Ⅲ. 추상 클래스와 인터페이스의 구조 (흐름)

- 핵심 요약 : is-a 본질 상속과 can-do 다중 구현이 결합되는 클래스 설계 구조.

```text
[ 추상 클래스: Bird (is-a 본질 상속) ]
 - 단일 상속 (extends)
 - 공통 상태 (protected int age) 보유
 - 템플릿 메서드 구현
   (공통 로직: eat(), breathe())
 - 미완성 추상 메서드 위임
   (abstract void makeSound())
   │
   ▼ (Duck이 다중 실체화: implements)
[ 인터페이스: Flyable (can-do 행위) ]
 + void fly() (순수 계약)
[ 인터페이스: Swimmable (can-do 행위) ]
 + void swim() (순수 계약)
```

- 두 추상화 메커니즘의 선택 기준 흐름.

```text
[ 설계 의도 분석 ]
   │
   ▼
[ 공통 상태·기본 로직
  공유가 목적인가? ]
   ├─ 예 -> [ 추상 클래스 ]
   │         (템플릿 메서드)
   ▼
[ 다중 행위 규약이
  목적인가? ]
   ├─ 예 -> [ 인터페이스 ]
   │         (롤 인터페이스 분리)
   ▼
[ 불확실 -> 구체 클래스로 시작 ]
 (YAGNI 원칙, 필요 시 추상화 추출)
```

- 템플릿 메서드 패턴 : 추상 클래스가 공통 알고리즘 골격을 정의하고, 추상 메서드로 세부 단계를 하위 클래스에 위임하는 GoF(Gang of Four) 디자인 패턴.
- 다중 구현 : 하나의 클래스가 복수의 인터페이스를 동시에 구현하여, 단일 상속의 한계를 보완하는 자바의 다중 상속 대체 수단.

## Ⅳ. 추상 클래스와 인터페이스의 핵심 비교 (Java 8+ 기준)

- 핵심 요약 : 상속 관계·다중성·상태 보유·구현 제공·생성자·설계 목적의 두 메커니즘 축 비교.

| 비교 항목 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) |
|---|---|---|
| 상속/구현 관계 | is-a 관계 (개념적 상위 분류) | can-do 관계 (역할 및 행위 규약) |
| 다중 상속 여부 | 단일 상속만 허용 (`extends`) | 다중 구현 완벽 허용 (`implements`) |
| 상태(멤버 변수) 보유 | 인스턴스 변수(상태)를 자유롭게 선언 가능 | 오직 `public static final` 상수만 허용 |
| 구현 메서드 제공 | 일반 메서드 및 생성자 자유롭게 구현 | Java 8+ 디폴트 메서드(`default`), 정적 메서드만 제한적 허용 |
| 생성자 (Constructor) | 생성자를 가질 수 있음 (자식 호출) | 생성자를 절대 가질 수 없음 |
| 주된 설계 목적 | 공통된 상태와 기본 로직의 코드 재사용 | 다형성을 통한 결합도 완화 및 컴포넌트 규약 정의 |

## Ⅴ. 추상 클래스와 인터페이스의 장점과 한계

- 핵심 요약 : 다형성·재사용·확장성의 장점, 경계 모호성·인터페이스 오염·과도한 추상화 측면의 한계.

- 장점
  1. 호출자와 구현자의 결합도 완화를 통한 유연한 교체·확장.
  2. 공통 로직의 상위 집중을 통한 코드 중복 제거.
  3. 규약 기반 설계를 통한 컴포넌트 간 계약 명확화.

- 한계점 1 : 인터페이스 내 디폴트 메서드(Default Method) 도입에 따른 경계 모호성
  - 한계점 : Java 8 이후 인터페이스도 구현 코드를 가질 수 있게 되면서 추상 클래스와의 설계상 역할 분담이 모호해지고 다중 구현 시 다이아몬드 충돌 발생.
  - 해결 방안 : 상태(인스턴스 필드) 유지 및 코드 재사용이 목적이면 추상 클래스, 순수 다형성 규약(Contract) 및 다중 상속 구현이 목적이면 인터페이스로의 명확한 설계 원칙 정립.
- 한계점 2 : 인터페이스 비대화로 인한 인터페이스 오염(Interface Pollution)
  - 한계점 : 구현 클래스마다 필요로 하는 메서드가 다름에도 단일 대형 인터페이스에 무분별하게 메서드를 추가하여 불필요한 빈 메서드 구현 강제.
  - 해결 방안 : SOLID의 인터페이스 분리 원칙(ISP, Interface Segregation Principle)을 엄격히 준수하여 클라이언트의 역할별로 작고 응집도 높은 롤 인터페이스(Role Interface)로의 분할 설계.
- 한계점 3 : 과도한 추상화 계층 도입으로 인한 코드 복잡도 및 가독성 저하
  - 한계점 : 단 하나의 구현체만 존재하는 클래스에도 무조건 인터페이스와 추상 클래스를 중첩 도입하여 실제 로직 추적 시 탐색 비용만 증가.
  - 해결 방안 : YAGNI(You Aren't Gonna Need It) 원칙에 입각하여 변경 가능성이나 복수 구현체가 확정되기 전까지는 구체 클래스로 시작하고, 리팩토링 단계에서 필요 시 추상화 추출.

## Ⅵ. 객체지향 클린 아키텍처를 위한 기술사적 제언

- 핵심 요약 : 합성 우선 원칙 준수와 작은 인터페이스 분리 설계의 병행.
- 상속을 통한 코드 재사용보다 인터페이스와 합성(Composition) 우선 원칙 준수 : 추상 클래스를 깊게 상속받으면 부모와 자식 간의 캡슐화가 깨지고 강결합이 발생하므로, GoF(Gang of Four) 원칙에 따라 인터페이스를 통해 역할을 정의하고 필요한 기능은 객체 합성으로 조립하는 설계를 최우선 권장.
- 인터페이스 분리 원칙(ISP)을 통한 가벼운 인터페이스 설계 : 인터페이스에 메서드를 과도하게 많이 선언하면 구현 클래스들이 사용하지도 않는 메서드를 억지로 빈 껍데기로 구현해야 하므로, 단일 목적에 부합하는 작은 인터페이스(단일 기능인 경우 `@FunctionalInterface` 활용)로 잘게 분리하여 람다식과의 호환성 극대화.

## Ⅶ. 결론

- 핵심 요약 : 추상 클래스는 공통 구현의 재사용, 인터페이스는 행위 규약의 다형성을 담당하며 목적에 따른 구분 사용이 원칙.
- 요약 : is-a와 can-do의 철학적 구분과 상태 보유·다중 구현 여부의 기술적 차이 이해.
- 시사점 : 합성 우선 원칙, ISP 기반 작은 인터페이스, YAGNI 기반 추상화 지연의 병행이 유지보수성 높은 객체지향 설계의 핵심.
