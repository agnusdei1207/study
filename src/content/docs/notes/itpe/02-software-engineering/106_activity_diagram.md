## 답안 골격
```text
[활동 다이어그램] ◀━━ 머리: Ⅶ 내 의견 (스윔레인(Swimlane) 기반의 업무 주체별 책임 분리와 병렬 처리 흐름 모델링)
 ┃
 ┣━ Ⅰ 개요 ───── 복잡한 비즈니스 프로세스와 조건 분기의 텍스트 명세 한계 → 제어 흐름과 데이터 흐름의 시각화 모델링
 ┣━ Ⅱ 특징 ───── 행위(Behavior) 다이어그램 · 조건 분기 및 병렬 처리(Fork/Join) 표현 · 스윔레인 구획화 · 순서도(Flowchart)의 객체지향 확장
 ┣━ Ⅲ 구조 ───── 초기/최종 노드 / 액션/액티비티(둥근 사각형) / 분기/병합(다이아몬드) / 포크/조인(굵은 실선) / 스윔레인 / 오브젝트 노드
 ┣━ Ⅳ 흐름 ───── 프로세스 시작(Initial) → 액션 실행 → 조건 판단(Decision) → 병렬 분기(Fork) → 동기화(Join) → 프로세스 종료(Final)
 ┣━ Ⅴ 비교 ───── 활동 다이어그램(업무/연산 흐름) vs 상태 다이어그램(단일 객체 생명주기) vs 순차 다이어그램(객체 간 메시지 상호작용)
 ┗━ Ⅵ 실무 ───── 포크-조인 불일치로 인한 데드락(Deadlock) 모델링 결함 / 토큰(Token) 흐름 분석 및 BPMN 연계 검증
```

## 한 줄 본질
- 여러 사용자 부서와 시스템 간에 얽힌 복잡한 업무 처리 절차와 병렬 처리 과정을 줄글로 작성할 때 발생하는 의사소통 왜곡 병목 → 시작부터 종료까지의 연산 흐름, 조건 분기, 동시 실행(Fork/Join), 주체별 역할(스윔레인)을 직관적 기호로 나타내는 UML 행위 다이어그램 / 정적 클래스 구조 표현 불가

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  활동 다이어그램(Activity Diagram) 핵심 요소            |
+-------------------------------------------------------------------------+
| [고객 (스윔레인)]          | [결제 시스템 (스윔레인)]   | [물류 (스윔레인)]     |
|   (●) 시작 노드            |                            |                     |
|    │                       |                            |                     |
|   [주문서 작성]            |                            |                     |
|    │                       |                            |                     |
|    └───(주문 요청)────────>| [결제 승인 검사]           |                     |
|                            |    │                       |                     |
|                            |   < > Decision (성공여부)  |                     |
|                            |   / \                      |                     |
|                   (실패) [취소]   (성공)                |                     |
|                            |       │                    |                     |
|                            |   ════╪════ Fork (동시실행)|                     |
|                            |   ┌───┴───┐                |                     |
|                            | [영수증발행]  [배송지시]───┼────────────────────>|
|                            |   └───┬───┘                |        │            |
|                            |   ════╪════ Join (동기화)  |     [상품 출고]     |
|                            |       │                    |        │            |
|                            |      (◎) 종료 노드         |       (◎) 종료      |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 스윔레인(Swimlane, 구획): 수영장 레인처럼 다이어그램을 수직 또는 수평 열로 나누어, 특정 액션을 수행하는 주체(사용자, 비즈니스 부서, 외부 시스템)의 책임 경계를 명확히 분리하는 표기법
- 포크와 조인(Fork & Join): 하나의 제어 흐름을 둘 이상의 독립적인 동시/병렬 흐름으로 쪼개는 것(Fork, 굵은 가로선)과, 분기된 모든 흐름이 완전히 완료될 때까지 대기한 후 하나로 합치는 것(Join, 굵은 가로선)

## 핵심 통찰
- 전통적인 프로그래밍 순서도(Flowchart)와 활동 다이어그램의 결정적 차이는 "동시성(Concurrency)과 병렬 제어(Fork/Join)", 그리고 "누가 그 일을 하는지(Swimlane)"를 엄격히 모델링할 수 있다는 점임
- UML 2.0으로 넘어오면서 활동 다이어그램은 단순 상태 머신 기반에서 페트리 넷(Petri-net) 형태의 '토큰 흐름(Token Flow) 시맨틱'으로 완전히 재정의되어 데이터와 제어의 흐름을 정밀하게 표현함
- 비즈니스 분석가(BA)가 현업과 요구사항을 검증할 때 유스케이스 명세서의 보조 도구로 가장 널리 쓰이며, 이후 BPMN(Business Process Model and Notation) 엔진과 1:1로 매핑됨

## 이웃 토픽과 구분
- 활동 다이어그램 vs 순차 다이어그램: 활동 다이어그램 = '전체 비즈니스 프로세스의 흐름과 병렬성' 표현 / 순차 다이어그램 = '특정 시나리오에서 객체들 간에 주고받는 메시지의 시간 순서' 표현

## 문제·원인·대책
- 적용 상황: 글로벌 전자상거래 결제 및 배송 자동화 시스템 워크플로 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 카드 결제와 포인트 차감이 병렬로 돌다가 하나가 실패했을 때 롤백 누락 | Fork 후 오류 발생 시 처리 흐름(Interruptible Activity Region) 미설계 | 취소 신호(Interrupting Edge) 및 보상 트랜잭션 액티비티 명시 | 병렬 결제 예외 상황 데이터 정합성 100% 보장 |
| 개발자가 화면 기능 구현 시 누가 API를 호출해야 하는지 책임 주체 혼선 | 스윔레인 없이 액티비티만 나열하여 클라이언트와 서버 역할 불분명 | 3단 스윔레인(모바일 앱, API 게이트웨이, 결제 코어) 재모델링 | 역할 분담 오류로 인한 API 재작업 80% 감소 |
