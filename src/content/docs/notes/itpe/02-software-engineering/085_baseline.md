## 답안 골격
```text
[베이스라인] ◀━━ 머리: Ⅶ 내 의견 (Git 태그/릴리스 기반의 자동화된 베이스라인 동결과 CCB 변경 추적성 확보)
 ┃
 ┣━ Ⅰ 개요 ───── 임의적 소프트웨어 변경으로 인한 통제 상실 방지 → 공식 승인된 특정 시점의 형상 기준선
 ┣━ Ⅱ 특징 ───── 공식 승인성(CCB 합의) · 변경 불가성(임의 수정 금지) · 추적성(Traceability) · 롤백 기준점
 ┣━ Ⅲ 구조 ───── 기능 기준선(요구사항) / 분배 기준선(설계) / 개발 기준선(코드) / 시험 기준선 / 제품 기준선(납품)
 ┣━ Ⅳ 흐름 ───── 마일스톤 도달 → 형상 감사(Audit) → CCB 공식 승인 → 베이스라인 동결(Freeze) → 변경 요청(CR) 시 변경통제 적용
 ┣━ Ⅴ 비교 ───── 제품 기준선(Product, 고객 인수) vs 개발 기준선(Development, 내부 테스트) vs 기능 기준선(Functional, 요구사항)
 ┗━ Ⅵ 실무 ───── 무단 코드 수정으로 인한 빌드 깨짐 / 형상통제위원회(CCB) 및 Git 브랜치 보호 규칙(Branch Protection) 적용
```
- 필수 키워드: 형상관리 기준선 · 베이스라인 · 공식 승인 · 형상통제위원회(CCB) · 변경 요청(CR) · 마일스톤 · 추적성
- 배점 전략: 10점 = Ⅰ 정의 및 목적 → Ⅲ SDLC 단계별 5대 베이스라인 다이어그램 → CCB 역할 / 25점 = Ⅰ~Ⅶ 전개, 134회 기출 형상관리 체계와의 연계 및 Git 태깅/릴리스 파이프라인 실무 구현
- 기출: 134회 1교시 4번 `형상관리의 개념과 형상관리 기준선(Baseline)` → Ⅰ~Ⅴ

## 한 줄 본질
- 개발자들이 각자 합의 없이 코드를 수정해 어느 버전이 정답이고 배포 가능한 상태인지 알 수 없는 형상 혼란 병목 → 특정 마일스톤 시점에 검토와 승인을 거쳐 공식 동결(Freeze)하고 이후 모든 변경을 CCB로 통제 → 시스템 변경 추적성 및 안정적 롤백 지점 보장 / 절차 준수에 따른 변경 속도 지연

## 핵심 그림
```text
+-------------------------------------------------------------------+
|            소프트웨어 생애주기(SDLC) 단계별 5대 베이스라인        |
+-------------------------------------------------------------------+
| [요구분석] --------> [ 1. 기능적 기준선 (Functional Baseline) ]   |
|                         * 요구사항 명세서(SRS) 승인 및 동결       |
|                               |                                   |
| [기본/상세설계] ---> [ 2. 분배/설계 기준선 (Allocated Baseline) ] |
|                         * 아키텍처 및 상세설계서 승인             |
|                               |                                   |
| [구현/단위시험] ---> [ 3. 개발 기준선 (Development Baseline) ]    |
|                         * 소스코드 머지 및 단위 테스트 통과       |
|                               |                                   |
| [통합/시스템시험] -> [ 4. 시험 기준선 (Test Baseline) ]           |
|                         * 시스템 테스트 합격 및 회귀 검증 완료    |
|                               |                                   |
| [고객인수/릴리스] -> [ 5. 제품 기준선 (Product Baseline) ]        |
|                         * 최종 패키징, 릴리스 노트, 고객 서명     |
+-------------------------------------------------------------------+
    * 베이스라인 수립 후 변경은 오직 공식 변경요청(CR) 및 CCB 심의만 허용!
```

## 핵심 용어
- CCB(Configuration Control Board): 베이스라인에 대한 변경 요청(CR)의 타당성을 기술적·비즈니스적으로 심의하고 승인/반려를 결정하는 최고 형상통제 위원회
- 형상 감사(Configuration Audit): 베이스라인 수립 전, 요구사항이 코드에 모두 구현되었는지(FCA, 기능 감사)와 문서와 산출물이 일치하는지(PCA, 물리 감사) 검증하는 활동

## 핵심 통찰
- 베이스라인은 개발을 중단시키기 위한 장벽이 아니라, "현재 버전에서 문제가 생겼을 때 확실하게 되돌아갈 수 있는 안전한 베이스캠프"를 설치하는 작업임
- 애자일/DevOps 환경에서 베이스라인은 두꺼운 서류 결재가 아닌, `git tag -a v2.1.0`과 같이 암호학적으로 서명된 Git 태그와 CI/CD 릴리스 빌드 아티팩트로 구현됨
- 베이스라인 간의 전후 '추적성(Traceability)'이 확보되지 않으면, 특정 요구사항이 취소되었을 때 어떤 설계 문서와 코드를 지워야 할지 파악할 수 없어 불필요한 코드가 잔존함

## 이웃 토픽과 구분
- 베이스라인 vs 형상 항목(CI): 형상 항목 = 형상관리 대상이 되는 개별 파일·산출물(단위) / 베이스라인 = 공식 승인되어 동결된 여러 형상 항목들의 '특정 시점 스냅샷(집합)'

## 문제·원인·대책
- 사례: 134회 기출 공공 차세대 검수 단계에서 개발자가 소스코드를 임의 수정하여 전체 검증 무효화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 인수 시험 통과 버전과 실제 운영 배포된 바이너리 코드가 불일치 | 시험 기준선(Test Baseline) 동결 후 개발자의 비공식 핫픽스 직배포 | Git Main 브랜치 직접 푸시 차단 및 CCB PR 승인 강제화 | 무단 코드 변경 0건 달성 및 배포 무결성 확보 |
| 운영 장애 발생 시 이전 정상 버전으로의 즉각 롤백 실패 | 릴리스 시점의 소스, 설정 파일, DB 스키마 형상 항목 패키징 누락 | 제품 기준선(Product Baseline) 중심 불변(Immutable) 컨테이너 이미지화 | 장애 발생 시 1분 이내 이전 베이스라인 즉각 롤백 |

## 내 의견
- [도장만 찍고 실제 코드는 브랜치 관리조차 안 되는 서류상 베이스라인] 감리용 서류철에만 '기준선 수립' 결재를 올리고, 실제 Git 저장소는 브랜치 전략도 없이 아무나 커밋하는 가짜 형상관리 척결 필요 → 나라면: GitLab/GitHub 릴리스와 ArgoCD를 결합하여 배포 승인 시점에 자동으로 Git Tag 생성, SBOM 패키징, 컨테이너 다이제스트 고정이 일체형으로 실행되는 '자동화된 코드 기반 베이스라인(Baseline as Code)' 체계 확립
