## 연관 키워드

- 엔터프라이즈 자바 빈즈(EJB, Enterprise JavaBeans), EJB 컨테이너(EJB Container), 서버 측 컴포넌트(Server-Side Component)
- 세션 빈(Session Bean), 메시지 구동 빈(MDB, Message-Driven Bean), 엔티티 빈(Entity Bean)
- POJO(Plain Old Java Object), 스프링 프레임워크(Spring Framework), JPA(Java Persistence API), CMT(Container-Managed Transaction)

## Ⅰ. EJB의 개요

- 핵심 요약 : 트랜잭션·분산·보안 등 기업용 횡단 관심사를 표준 컨테이너에 위임하는 Java EE의 서버 측 컴포넌트 아키텍처 표준.
- 개념 : EJB(Enterprise JavaBeans)란 1990년대 후반 썬 마이크로시스템즈(Sun Microsystems)가 대규모 분산 기업 환경에서 트랜잭션, 분산 객체 통신(RMI, Remote Method Invocation), 보안, 동시성 제어, 영속성 관리 등 복잡한 엔터프라이즈 로직을 개발자가 직접 구현하지 않고 표준 컨테이너(EJB Container)에 위임할 수 있도록 제정한 Java EE(Java Platform, Enterprise Edition, 현 Jakarta EE)의 서버 측 컴포넌트 아키텍처 표준.
- 배경 및 필요성 : 금융, 통신 등 미션 크리티컬 시스템에서 분산 트랜잭션(2PC, Two-Phase Commit)과 원격 RPC(Remote Procedure Call)를 지원하는 엔터프라이즈 컴포넌트의 표준 플랫폼 구축.
- 쇠퇴와 유산 : EJB 2.x의 지나치게 무거운 침투적(Invasive) 상속 모델과 느린 배포 속도로 인해 개발자들의 원성을 사며 로드 존슨의 스프링 프레임워크(Spring)와 POJO(Plain Old Java Object) 패러다임의 등장을 촉발한 소프트웨어 공학의 역사적 전환점.

## Ⅱ. EJB의 특징

- 핵심 요약 : 3대 빈 유형과 컨테이너 위임 서비스(트랜잭션·분산·보안·영속성)의 결합.

1. 세션 빈(Session Bean) : 비즈니스 로직 수행, 상태를 유지하지 않는 무상태(Stateless) 빈과 클라이언트별 대화 상태를 유지하는 상태유지(Stateful) 빈으로 구분.
2. 메시지 구동 빈(MDB, Message-Driven Bean) : JMS(Java Message Service) 메시지 브로커와 비동기 연동되어 이벤트를 처리하는 컴포넌트.
3. 엔티티 빈(Entity Bean) : 데이터베이스 레코드의 자바 객체 표현, 극도로 무겁고 복잡하여 EJB 3.0에서 완전히 폐기되고 POJO 기반의 JPA(Java Persistence API)로 대체.
4. 컨테이너 위임 서비스 : 선언적 트랜잭션 관리(CMT, Container-Managed Transaction), 원격 분산 호출(RMI-IIOP : Remote Method Invocation over Internet Inter-ORB Protocol), 보안·인증 인터셉터, 동시성 제어.

## Ⅲ. EJB의 구조 (흐름)

- 핵심 요약 : 클라이언트 호출을 컨테이너의 횡단 서비스가 가로채 빈으로 위임하는 구조.
- EJB 컨테이너 아키텍처.

```text
[ EJB 컨테이너 (WebLogic, Jeus, JBoss) ]
 - 선언적 트랜잭션 관리
   (CMT, Container-Managed Transaction)
 - 원격 분산 호출 (RMI-IIOP) 및
   보안/인증 인터셉터

 1. [ 세션 빈 (Session) ]
    - Stateless : 비즈니스 로직
    - Stateful : 세션 상태 유지

 2. [ MDB (Message) ]
    - JMS 비동기 이벤트 리스너

 3. [ 엔티티 빈 ]
    - DB 영속성 (JPA로 대체)
```

- 클라이언트 요청 처리 흐름.

```text
[ 클라이언트 ]
    │ (JNDI(Java Naming and Directory Interface) 조회 및
    │  비즈니스 인터페이스 호출)
    ▼
[ EJB 컨테이너 ]
 - 트랜잭션 시작(CMT), 보안 인터셉터 통과
    │ (위임)
    ▼
[ 세션 빈 : 비즈니스 로직 수행 ]
    │
    ▼
[ 엔티티 빈/JPA : 영속성 처리 ] ──> [ DB ]
```

## Ⅳ. EJB와 Spring Framework의 패러다임 비교

- 핵심 요약 : 침투적 표준 컴포넌트 모델과 비침투적 POJO 모델의 패러다임 대비.

| 비교 항목 | 엔터프라이즈 자바 빈즈 (EJB 2.x) | 스프링 프레임워크 (Spring Framework) |
|---|---|---|
| 컴포넌트 철학 | 무거운 침투적 프레임워크 (EJB 전용 인터페이스 상속 강제) | 비침투적(Non-invasive) POJO 모델 |
| 실행 환경 | 무겁고 고가인 상용 WAS(Web Application Server; WebLogic, WebSphere, Jeus) 필수 | 경량 서블릿 컨테이너(Tomcat) 또는 단독 실행(Spring Boot) |
| 단위 테스트 | 실제 무거운 EJB 컨테이너 없이는 단위 테스트 불가능 | 프레임워크 없이 순수 자바 객체(JUnit, Mockito)로 초고속 테스트 |
| 트랜잭션 관리 | 컨테이너 관리 트랜잭션(CMT) | AOP(Aspect-Oriented Programming) 기반 선언적 트랜잭션 (@Transactional) |
| 설계 원칙 | 분산 RMI 객체 모델 (원격 통신의 성능 저하 무시) | 로컬 호출 중심, 필요 시에만 REST(Representational State Transfer)/gRPC 분산 연계 |

## Ⅴ. EJB의 장점과 한계

- 핵심 요약 : 횡단 관심사 위임·표준화의 장점과 테스트 불가·벤더 종속·네트워크 오버헤드의 한계 공존.

- 장점
  1. 트랜잭션, 보안, 동시성, 영속성 등 횡단 관심사의 표준 컨테이너 위임.
  2. 분산 트랜잭션(2PC)과 원격 호출을 지원하는 검증된 표준 컴포넌트 모델.
  3. 상용 WAS 기반 미션 크리티컬 시스템의 안정적 운용 여건.

- 한계점 1 : 무거운 컨테이너 의존성으로 인한 단위 테스트(Unit Test) 불가능
  - 한계점 : EJB 컴포넌트 실행을 위해 WebLogic, WebSphere, JBoss 등 무거운 상용 WAS 컨테이너가 반드시 필요하여 POJO 기반 단위 테스트 수행 불가.
  - 해결 방안 : 비즈니스 로직의 프레임워크 독립적인 순수 자바 객체(POJO) 분리, 임베디드 EJB 컨테이너나 모킹 프레임워크(Mockito)를 활용한 격리 테스트 환경 구축.
- 한계점 2 : 복잡한 인터페이스 사양 및 상용 벤더 종속성(Lock-in)
  - 한계점 : Home, Remote, Local 인터페이스 분리 및 복잡한 XML(Extensible Markup Language) 배포 서술자(deployment descriptor) 관리 부담과 상용 WAS 벤더 특화 확장에의 고착화.
  - 해결 방안 : EJB 3.x 애노테이션 기반 단순화 적용 또는 Spring Boot, Quarkus 등 현대적 경량 엔터프라이즈 프레임워크로의 전면 마이그레이션.
- 한계점 3 : 분산 RMI/IIOP 호출에 따른 심각한 네트워크 오버헤드
  - 한계점 : 계층 간 호출을 원격 분산 객체 통신으로 설계하여 불필요한 직렬화/역직렬화 및 네트워크 레이턴시가 발생하고 시스템 전반 성능 저하.
  - 해결 방안 : 로컬 인터페이스(`@Local`) 우선 사용, 세션 빈과 엔티티 빈의 원격 직접 호출 지양, DTO(Data Transfer Object) 패턴을 통한 일괄 전송 최적화.

## Ⅵ. 레거시 마이그레이션 관점의 기술사적 제언

- 핵심 요약 : Spring Boot/JPA 기반 점진적 현대화와 비침투적 설계 원칙의 확립.
- 레거시 EJB 시스템의 Spring Boot/JPA 현대화 전략 : 국내 공공/금융 레거시 시스템에 남아있는 EJB 2.x 코드는 프레임워크 종속성으로 인해 클라우드 전환의 최대 걸림돌이므로, 복잡한 Home/Remote 인터페이스를 제거하고 비즈니스 로직을 순수 Spring Service POJO로 추출한 후 엔티티 빈은 표준 Spring Data JPA로 전환하는 점진적 리팩토링 추진 필수.
- EJB의 역사적 교훈 — 비침투적 프레임워크 설계 원칙 확립 : 특정 벤더나 기술 표준이 개발자의 비즈니스 도메인 객체를 오염시키지 않아야 장기적인 유지보수성이 보장된다는 소프트웨어 공학적 교훈을 바탕으로, 현대 아키텍처에서도 특정 프레임워크 애노테이션에 도메인 엔티티가 종속되지 않도록 아키텍처 경계 분리 준수.

## Ⅶ. 결론

- 핵심 요약 : EJB는 횡단 관심사의 컨테이너 위임이라는 유산과 침투적 설계의 교훈을 함께 남긴 아키텍처 표준.
- 요약 : 3대 빈 유형과 CMT 등 컨테이너 서비스의 표준화는 높였으나, 무거운 컨테이너 의존성이 POJO·Spring 패러다임 전환을 촉발.
- 시사점 : 비침투적 설계 원칙과 점진적 레거시 마이그레이션 전략이 현대 엔터프라이즈 아키텍처의 핵심 시사점.
