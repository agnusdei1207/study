## Ⅰ. EJB의 개요

- **개념** : 1990년대 후반 썬 마이크로시스템즈(Sun Microsystems)가 대규모 분산 기업 환경에서 트랜잭션, 분산 객체 통신(RMI), 보안, 동시성 제어, 영속성 관리 등 복잡한 엔터프라이즈 로직을 개발자가 직접 구현하지 않고 표준 컨테이너(EJB Container)에 위임할 수 있도록 제정한 Java EE(현 Jakarta EE)의 서버 측 컴포넌트 아키텍처 표준.
- **배경 및 필요성** : 금융, 통신 등 미션 크리티컬 시스템에서 분산 트랜잭션(2PC)과 원격 RPC를 지원하는 엔터프라이즈 컴포넌트의 표준 플랫폼 구축.
- **쇠퇴와 유산** : EJB 2.x의 지나치게 무거운 침투적(Invasive) 상속 모델과 느린 배포 속도로 인해 개발자들의 원성을 사며 로드 존슨의 '스프링 프레임워크(Spring)'와 'POJO(Plain Old Java Object)' 패러다임의 등장을 촉발한 소프트웨어 공학의 역사적 전환점.

## Ⅱ. EJB 3대 빈(Bean) 유형 및 컨테이너 아키텍처

```text
   [ EJB 컨테이너 (WebLogic, Jeus, JBoss) ]
   ┌────────────────────────────────────────────────────────────────────────┐
   │  - 선언적 트랜잭션 관리 (CMT, Container-Managed Transaction)          │
   │  - 원격 분산 호출 (RMI-IIOP) 및 보안/인증 인터셉터                    │
   │                                                                        │
   │  ┌─────────────────────────┐  ┌──────────────────┐  ┌───────────────┐  │
   │  │ [ 세션 빈 (Session) ]   │  │[ MDB (Message) ] │  │[ 엔티티 빈 ]  │  │
   │  │ - Stateless: 비즈니스 로직│  │- JMS 비동기     │  │- DB 영속성   │  │
   │  │ - Stateful: 세션 상태 유지│  │  이벤트 리스너  │  │  (JPA로 대체)│  │
   │  └─────────────────────────┘  └──────────────────┘  └───────────────┘  │
   └────────────────────────────────────────────────────────────────────────┘
```

- **세션 빈 (Session Bean)** : 비즈니스 로직을 수행. 상태를 유지하지 않는 무상태(Stateless) 빈과 클라이언트별 대화 상태를 유지하는 상태유지(Stateful) 빈으로 구분.
- **메시지 구동 빈 (Message-Driven Bean, MDB)** : JMS 메시지 브로커와 비동기 연동되어 이벤트를 처리하는 컴포넌트.
- **엔티티 빈 (Entity Bean)** : 데이터베이스 레코드를 자바 객체로 표현했으나, 극도로 무겁고 복잡하여 EJB 3.0에서 완전히 폐기되고 POJO 기반의 JPA(Java Persistence API)로 대체됨.

## Ⅲ. EJB와 Spring Framework의 패러다임 비교

| 비교 항목 | 엔터프라이즈 자바 빈즈 (EJB 2.x) | 스프링 프레임워크 (Spring Framework) |
|---|---|---|
| 컴포넌트 철학 | 무거운 침투적 프레임워크 (EJB 전용 인터페이스 상속 강제) | 비침투적(Non-invasive) POJO(Plain Old Java Object) 모델 |
| 실행 환경 | 무겁고 고가인 상용 WAS(WebLogic, WebSphere, Jeus) 필수 | 경량 서블릿 컨테이너(Tomcat) 또는 단독 실행(Spring Boot) |
| 단위 테스트 | 실제 무거운 EJB 컨테이너 없이는 단위 테스트 불가능 | 프레임워크 없이 순수 자바 객체(JUnit, Mockito)로 초고속 테스트 |
| 트랜잭션 관리 | 컨테이너 관리 트랜잭션 (CMT) | AOP 기반 선언적 트랜잭션 (@Transactional) |
| 설계 원칙 | 분산 RMI 객체 모델 (원격 통신의 성능 저하 무시) | 로컬 호출 중심, 필요 시에만 REST/gRPC 분산 연계 |

## Ⅳ. 레거시 마이그레이션 관점의 기술사적 제언

- **레거시 EJB 시스템의 Spring Boot/JPA 현대화 전략** : 국내 공공/금융 레거시 시스템에 남아있는 EJB 2.x 코드는 프레임워크 종속성으로 인해 클라우드 전환의 최대 걸림돌이므로, 복잡한 Home/Remote 인터페이스를 제거하고 비즈니스 로직을 순수 Spring Service POJO로 추출한 후 엔티티 빈은 표준 Spring Data JPA로 전환하는 점진적 리팩토링 추진 필수.
- **EJB의 역사적 교훈: 비침투적 프레임워크 설계 원칙 확립** : 특정 벤더나 기술 표준이 개발자의 비즈니스 도메인 객체를 오염시키지 않아야 장기적인 유지보수성이 보장된다는 소프트웨어 공학적 교훈을 바탕으로, 현대 아키텍처에서도 특정 프레임워크 어노테이션에 도메인 엔티티가 종속되지 않도록 아키텍처 경계 분리 준수.
