## 큰 그림과 30초 인출

- 본질: 기업용 대규모 분산 엔터프라이즈 환경에서 트랜잭션, 분산 보안, 스레드 풀링 등 복잡한 시스템 인프라 로직을 전용 런타임 컨테이너(WAS)가 투명하게 전담하고, 개발자는 순수 비즈니스 로직 작성에만 집중할 수 있도록 선언적 인프라 서비스를 제공하는 자바 엔터프라이즈(Java EE) 표준 분산 컴포넌트 스펙
- 메커니즘: 클라이언트 JNDI 룩업 $\rightarrow$ 원격 인터페이스 프록시 획득 $\rightarrow$ 컨테이너 인터셉트(선언적 트랜잭션 CMT 및 보안 인가) $\rightarrow$ 대상 빈(Session/MDB/Entity) 비즈니스 로직 실행 $\rightarrow$ 결과 반환

<details>
<summary>핵심 용어</summary>

- **EJB 컨테이너(EJB Container)**: EJB 컴포넌트의 라이프사이클, 분산 트랜잭션(JTA/CMT), 인스턴스 풀링, 보안 인가, 원격 RMI 통신을 전담하는 Java EE 미들웨어 런타임
- **세션 빈(Session Bean)**: 클라이언트의 비즈니스 작업을 수행하는 컴포넌트로, 상태를 보존하지 않는 Stateless와 상태를 유지하는 Stateful, 단일 인스턴스인 Singleton으로 구분됨
- **메시지 구동 빈(MDB, Message-Driven Bean)**: JMS(Java Message Service) 큐나 토픽으로부터 비동기 메시지가 도착했을 때 이벤트 드리븐 방식으로 자동 기동되는 비동기 리스너 빈
- **CMT(Container-Managed Transaction)**: 개발자가 직접 `commit/rollback` 코드를 작성하지 않고, 선언(어노테이션/XML)만으로 컨테이너가 트랜잭션 경계를 관리해 주는 선언적 트랜잭션
- **POJO(Plain Old Java Object)**: 특정 프레임워크의 클래스를 상속받거나 무거운 인터페이스를 강제로 구현하지 않는 가장 순수한 형태의 표준 자바 객체
</details>

## 1. 개요 및 필요성

### 분산 엔터프라이즈 인프라와 비즈니스 로직 분리의 꿈

금융 차세대 시스템이나 제조 ERP와 같은 대규모 기업용 시스템에서는 데이터베이스 분산 트랜잭션(2PC), 객체 인스턴스 풀링, 역할 기반 보안 제어 등 고난도의 시스템 인프라 구축이 필수적이다.

EJB는 복잡한 시스템 레벨 인프라를 **EJB 컨테이너(WAS)**가 도맡아 처리하고, 비즈니스 개발자는 순수 비즈니스 로직에만 전념할 수 있도록 고안된 자바 엔터프라이즈 표준 기술이었다.

### EJB vs Spring Framework vs JavaBeans 비교

| 구분 | EJB (Enterprise Java Beans) | Spring Framework | JavaBeans |
|---|---|---|---|
| **기본 성격** | **Java EE 공식 분산 컴포넌트 표준** | **사실상의 표준(De facto) 경량 프레임워크** | 단순 데이터 전송 객체 (DTO / POJO) |
| **침투성** | **강한 침투성 (WAS 및 전용 인터페이스 종속)** | **비침투적 (순수 POJO 및 의존성 주입)** | 완전 비침투적 |
| **실행 런타임**| **고가의 Full Java EE 상용 WAS 필수 (WebLogic 등)**| **경량 서블릿 컨테이너(Tomcat)로 구동 가능** | 모든 JVM 환경 |
| **단위 테스트**| **극도로 난해 (WAS 컨테이너 없이는 실행 불가)**| **매우 용이 (단순 객체 생성 및 Mockito 격리)**| 즉시 실행 가능 |
| **핵심 기제** | 선언적 트랜잭션(CMT), 분산 RMI | 제어의 역전(IoC/DI), AOP 관점 지향 프로그래밍 | Getter / Setter, 직렬화 |

## 3. 실무 적용 및 고려사항

### 위험 대응 매트릭스

| 위험 | 대책 | 효과 |
|---|---|---|
| 코드 한 줄 수정 후에도 상용 WAS를 수 분 동안 재기동해야 해 개발 생산성 파탄 및 로컬 단위 테스트 불가 | Spring Boot 및 내장 톰캣(Embedded Tomcat) 도입을 통한 로컬 핫 리로딩 및 순수 POJO 테스트 환경 전환 | 빌드/테스트 피드백 루프 시간 95% 단축 |
| Stateful Session Bean 남용으로 인해 WAS 클러스터 간 분산 세션 메모리 복제 트래픽 폭증 | 무상태 세션 빈(Stateless)으로 전면 전환하고 사용자 상태는 외부 Redis 분산 캐시로 분리 | WAS 메모리 사용량 절감 및 수평 확장성 확보 |
| 레거시 EJB 2.x 시스템의 유지보수 인력 단절 및 거대한 XML 배포 서술자로 인한 기술 부채 고착 | EJB 원격 인터페이스를 감싸는 Spring 어댑터 레이어를 구축하고 점진적 스트랭글러 패턴 기반 마이그레이션 | 레거시 안정 운영과 점진적 MSA 전환 달성 |

## 4. 기술사 답안 차별화 포인트

### EJB의 비극: "침투적 프레임워크"의 한계와 스프링의 탄생

EJB 1.x와 2.x는 비즈니스 로직 하나를 작성하더라도 `EJBHome`, `EJBObject` 등 수많은 벤더 인터페이스를 상속받아야 했고 무거운 XML 서술자를 작성해야 했다. 이처럼 프레임워크 코드가 비즈니스 코드를 오염시키는 **"침투적 프레임워크(Invasive Framework)"**의 폐해를 겪으면서, 로드 존슨(Rod Johnson)과 마틴 파울러는 **"순수한 자바 객체(POJO)로 돌아가자"**고 선언하며 **스프링 프레임워크(Spring Framework)**를 탄생시켰다. 이 기술사적 반성과 발전 과정을 명확히 짚어준다.

### EJB가 현대 아키텍처에 남긴 유산: AOP와 선언적 트랜잭션, JPA

EJB 자체는 역사 속으로 사라지고 있으나, EJB가 추구했던 철학은 고스란히 현대 기술의 표준이 되었다. 컨테이너가 코드를 가로채 트랜잭션을 걸어주는 메커니즘은 스프링의 **`@Transactional` (AOP 선언적 트랜잭션)**으로 계승되었으며, 엔티티 빈의 실패 교훈은 표준 ORM인 **JPA(Hibernate)**로 재탄생하였다. EJB의 사상이 현대 클라우드 네이티브 백엔드에 미친 지대한 영향을 결론으로 제시한다.
