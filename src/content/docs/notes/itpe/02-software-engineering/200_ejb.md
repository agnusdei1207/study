## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 서버 사이드 컴포넌트·프레임워크 → 엔터프라이즈 자바 빈즈(EJB)

## 지식 위치

소프트웨어공학 > 서버 측 엔터프라이즈 컴포넌트 > Enterprise Beans

## 30초 인출

- 본질: 기업 환경의 대규모 분산 비즈니스 로직을 구현하기 위해 트랜잭션, 보안, 스레딩, 객체 풀링 등의 인프라성 서비스를 컨테이너가 자동 제공하는 자바 엔터프라이즈(Jakarta EE) 표준 서버 컴포넌트 아키텍처
- 메커니즘: 개발자의 빈(Bean) 구현 → EJB 컨테이너(WAS) 배치 → 선언적 트랜잭션(CMT) 및 보안(JAAS) 인터셉트 주입 → RMI-IIOP/JMS 통신 기반 비즈니스 로직 실행
- 통찰: 과도하게 무거운 규격 종속성과 침투적 프레임워크 설계로 인한 단위 테스트 난관을 극복하기 위해 경량 POJO와 제어의 역전(IoC/DI)을 표방한 Spring Framework 및 CDI로 진화

<details>
<summary>핵심 용어</summary>

- **EJB (Enterprise JavaBeans)** : 비즈니스 로직과 시스템 인프라 서비스를 분리하여 엔터프라이즈급 안정성을 제공하는 자바 서버 컴포넌트 규격
- **EJB 컨테이너 (Container)** : EJB 인스턴스의 라이프사이클을 관리하고 선언적 트랜잭션, 보안 인가, 원격 통신, 풀링을 대행하는 WAS 런타임 환경
- **무상태 세션 빈 (Stateless Session Bean, SLSB)** : 클라이언트의 상태를 보존하지 않고 풀(Pool)에서 재사용되어 높은 처리량을 제공하는 비즈니스 빈
- **상태유지 세션 빈 (Stateful Session Bean, SFSB)** : 클라이언트와의 1:1 대화 상태를 메모리에 유지하며 쇼핑몰 장바구니 등에 사용되는 빈
- **메시지 구동 빈 (Message-Driven Bean, MDB)** : JMS 메시지 큐와 결합하여 비동기 메시지 수신 시 이벤트 방식으로 동작하는 비동기 컴포넌트
- **CMT (Container-Managed Transaction)** : 개발자가 수동 롤백 코드를 작성하지 않고 애너테이션/XML 설정만으로 컨테이너가 트랜잭션 경계를 제어하는 메커니즘
</details>

## 2~4교시 예상문제 (25점)

> 엔터프라이즈 자바 컴포넌트 아키텍처인 EJB(Enterprise JavaBeans)의 개념과 컨테이너 4대 핵심 서비스를 설명하고, 빈 유형(세션 빈, 메시지 구동 빈)의 비교 및 경량 스프링 프레임워크(Spring Framework)로의 진화 배경을 제시하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 금융, 공공 등 대규모 엔터프라이즈 시스템에서 비즈니스 로직을 모듈화하여 분산 환경에 배포하고, 트랜잭션·보안·동시성을 선언적으로 제공받는 서버 측 자바 표준 컴포넌트 모델 |
| 목적 | 개발자가 인프라성 저수준 코딩(스레드 동기화, 트랜잭션 롤백, 커넥션 풀링)에서 벗어나 순수 비즈니스 도메인 로직 구현에만 집중할 수 있는 환경 제공 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 컨테이너 기반 아키텍처 | 빈 객체의 생명주기 생성, 소멸, 인스턴스 풀링을 WAS EJB 컨테이너가 전담 제어 |
| 선언적 트랜잭션 관리 (CMT) | 소스코드 수정 없이 `@TransactionAttribute` 선언만으로 분산 2PC 트랜잭션 보장 |
| 역할 기반 선언적 보안 | `@RolesAllowed` 애너테이션을 통해 비즈니스 메서드 단위의 접근 인가 통제 자동화 |
| 원격 호출 및 비동기 메시징 | RMI-IIOP 프로토콜을 통한 네트워크 투명 원격 호출 및 JMS 연계를 통한 완전 비동기 처리(MDB) 지원 |

소프트웨어 개발의 관심사 분리(Separation of Concerns)를 엔터프라이즈 자바 스펙으로 최초 실현한 공학적 이정표.

## Ⅲ. 체계·프로세스

```text
[EJB 컨테이너 아키텍처 및 클라이언트 호출 체계]

[클라이언트 (JSP/서블릿 또는 원격 Java)]
       │
       ▼ JNDI 룩업 / 인터페이스 DI 주입 (@EJB)
[EJB 컨테이너 (WAS: WildFly, WebLogic, Jeus)]
  ┌────────────────────────────────────────────────────────┐
  │ 1. 인터셉터 계층 (컨테이너 인프라 서비스 가로채기)      │
  │    - 보안 인가 검사 (Security Check)                   │
  │    - 트랜잭션 경계 개시 (Transaction Begin)            │
  ├────────────────────────────────────────────────────────┤
  │ 2. 인스턴스 라이프사이클 관리                          │
  │    - 인스턴스 풀(Pool)에서 가용 빈 추출                │
  │    - Stateful 빈의 경우 Passivation/Activation 제어    │
  ├────────────────────────────────────────────────────────┤
  │ 3. 비즈니스 로직 실행                                  │
  │    - Stateless / Stateful / Singleton Session Bean     │
  │    - Message-Driven Bean (JMS 큐 연동 비동기 처리)     │
  ├────────────────────────────────────────────────────────┤
  │ 4. 후처리                                              │
  │    - 트랜잭션 커밋 / 롤백 (Commit / Rollback)           │
  │    - 인스턴스 풀 반환                                  │
  └────────────────────────────────────────────────────────┘
       │
       ▼ JDBC / JPA 데이터 계층
[데이터베이스 (RDBMS)]
```

클라이언트의 JNDI 조회, 컨테이너 인터셉터를 통한 보안/트랜잭션 가로채기, 비즈니스 빈 호출, 트랜잭션 커밋으로 이어지는 실행 프로세스.

## Ⅳ. 종류·비교

| 빈 유형 | 상태 유지 여부 | 동시성 및 공유 특성 | 대표 사용 사례 |
|---|---|---|---|
| **Stateless Session Bean (SLSB)** | 무상태 (요청 간 상태 없음) | 요청 시마다 풀에서 임의의 인스턴스 할당 후 반환 | 계좌 이체, 환율 조회, 주문 결제 승인 |
| **Stateful Session Bean (SFSB)** | 상태 유지 (클라이언트 종속) | 클라이언트와 1:1 전용 매핑 (메모리 부담 수반) | 다단계 설문조사, 전자상거래 쇼핑몰 장바구니 |
| **Singleton Session Bean** | 애플리케이션 단위 공유 | 단일 인스턴스가 생성되어 모든 클라이언트가 동시 공유 | 시스템 글로벌 설정 캐시, 애플리케이션 카운터 |
| **Message-Driven Bean (MDB)** | 무상태 (비동기 메시지 수신) | JMS 메시지 리스너로 작동하여 풀 단위 병렬 소비 | 비동기 SMS/이메일 발송, 대량 배치 작업 트리거 |

### 중량 EJB vs 경량 Spring Framework 비교

| 비교 항목 | 전통적 EJB (EJB 2.x 중심) | 모던 Spring Framework / Spring Boot |
|---|---|---|
| **컴포넌트 침투성** | EJB 인터페이스 상속 필수 (강한 종속성) | 비침투적 순수 POJO (Plain Old Java Object) 지향 |
| **실행 환경** | 수천만원 대 고가의 상용 중량 WAS 필수 (WebLogic 등) | 톰캣 내장 경량 서블릿 컨테이너 및 단독 실행 가능 |
| **단위 테스트** | WAS 컨테이너 기동 없이 JUnit 테스트 불가능 | Mockito 등을 활용한 초고속 로컬 단위 테스트 완벽 지원 |
| **구성 방식** | 복잡하고 장황한 배포 서술자(`ejb-jar.xml`) 의존 | 심플한 애너테이션 및 자동 설정(Auto-Configuration) |
| **현대적 위상** | 신규 프로젝트 채택 거의 전무 (레거시 유지보수) | 글로벌 엔터프라이즈 자바 백엔드의 절대적 사실상 표준 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 프레임워크 클래스를 강제 상속받아 코드 복잡도가 극심하고 비즈니스 로직의 단위 테스트(Mocking) 극난 | EJB 3.x+ 어노테이션 기반 POJO 모델로 리팩토링하거나 Spring/CDI 기반으로 프레임워크 전면 마이그레이션 |
| 무거운 상용 WAS 라이선스 비용 및 느린 부트스트래핑으로 인한 클라우드 컨테이너화 제약 | WAS 종속적 분산 EJB 호출을 제거하고 RESTful API 기반의 독립 마이크로서비스(Spring Boot/Quarkus)로 전환 |
| 상태유지 세션 빈(SFSB) 사용 시 서버 클러스터링 환경에서 세션 복제(Replication) 오버헤드 폭증 | SFSB를 완전 폐기하고 Stateless 세션 빈 + Redis 외장 캐시 클러스터 기반 무상태 세션 구조로 아키텍처 개편 |

## Ⅵ. 제언

금융권 및 공공기관의 노후화된 EJB 기반 레거시 시스템 현대화 시, 기존 비즈니스 로직을 순수 POJO 도메인 모델로 추출(역공학)하고 Quarkus 또는 Spring Boot 기반의 클라우드 네이티브 MSA로 단계적 전환 권장.

```text
[EJB 레거시 현대화 전환 아키텍처]
  [레거시 EJB 시스템] ──► 비즈니스 로직 추출 (POJO 화) ──► Spring Boot / Quarkus 컨테이너 패키징 ──► Kubernetes 배포
```

| 검증 단계 | 레거시 진단 단계 | 클라우드 전환 단계 |
|---|---|---|
| 핵심 통제 | CMT 트랜잭션 속성(RequiresNew, Mandatory 등) 정밀 분석 | 스프링 `@Transactional` 선언적 매핑 및 단위 테스트 100% 구축 |
| 전환 목표 | 무거운 상용 WAS 종속성 탈피 | OCI 컨테이너 기반 초고속 배포 및 오토스케일링 확보 |
