## 연관 키워드

- 엔터프라이즈 자바 빈즈(EJB, Enterprise JavaBeans), EJB 컨테이너(EJB Container), 서버 측 컴포넌트(Server-Side Component)
- 세션 빈(Session Bean), 메시지 구동 빈(MDB, Message-Driven Bean), 엔티티 빈(Entity Bean)
- POJO(Plain Old Java Object), 스프링 프레임워크(Spring Framework), JPA(Java Persistence API), CMT(Container-Managed Transaction)

## Ⅰ. EJB의 개요

- 핵심 요약 : 트랜잭션·분산·보안 같은 기업용 횡단 관심사를 컨테이너에 위임하는 Java EE 서버 측 컴포넌트 표준.
- 개념 : 트랜잭션, 원격 호출, 보안, 동시성, 영속성 같은 기업 로직의 공통 기능을 개발자가 직접 구현하지 않고 컨테이너에 맡기도록 정한 **엔터프라이즈 자바 빈즈** (EJB, Enterprise JavaBeans)이며, Java EE(Java Platform, Enterprise Edition, 현 Jakarta EE)의 **서버 측 컴포넌트** (Server-Side Component) 아키텍처 표준이다.
- 배경 및 필요성 : 금융, 통신처럼 장애 허용이 낮은 시스템은 여러 자원에 걸친 분산 트랜잭션과 원격 호출을 표준 방식으로 다룰 플랫폼이 필요했다.
- 주요 목적 : 기업 로직의 기술 공통 요소를 표준 컨테이너에 두어 개발 생산성과 운영 안정성을 함께 확보하는 것.
- 역사적 위치 : EJB 2.x의 무거운 침투적(Invasive) 모델과 느린 배포가 비판받으면서 **스프링 프레임워크** (Spring Framework)와 **POJO** (Plain Old Java Object, 특정 프레임워크 인터페이스를 상속하지 않는 일반 자바 객체) 방식의 확산을 촉발한 전환점이다.

## Ⅱ. EJB의 특징 및 장점

- 핵심 요약 : 3종의 빈 유형과 컨테이너 위임 서비스가 결합해 업무 로직과 기술 로직을 분리하는 구조.

1. **세션 빈** (Session Bean) : 업무 로직을 수행하며, 상태를 갖지 않는 무상태(Stateless) 빈과 클라이언트별 대화 상태를 유지하는 상태유지(Stateful) 빈으로 나뉨 → 업무 단위 호출을 캡슐화.
2. **메시지 구동 빈** (MDB, Message-Driven Bean) : JMS(Java Message Service) 메시지를 비동기로 받아 처리 → 송신자와 수신자의 결합도 감소.
3. **엔티티 빈** (Entity Bean) : 데이터베이스 레코드를 객체로 표현하는 빈이나, EJB 3.0에서 폐기되고 **JPA** (Java Persistence API)로 대체됨 → 영속성 모델이 POJO 기반으로 단순화.
4. 컨테이너 위임 서비스 : **컨테이너 관리 트랜잭션** (CMT, Container-Managed Transaction)으로 트랜잭션 경계를 선언하고, 원격 호출(RMI-IIOP), 보안 인터셉터, 동시성 제어를 컨테이너가 제공 → 개발자는 업무 코드에 집중.

## Ⅲ. EJB의 구조 (흐름)

- 핵심 요약 : 클라이언트 호출을 컨테이너가 가로채 트랜잭션과 보안을 적용한 뒤 빈으로 위임하는 구조.
- **EJB 컨테이너** (EJB Container) : 빈의 생명주기를 관리하고 트랜잭션·보안 같은 횡단 서비스를 빈 호출에 끼워 넣는 실행 환경. 트랜잭션 경계를 애노테이션이나 배포 서술자에 선언하면 컨테이너가 시작과 종료를 맡는다.

```text
[ 클라이언트 ]
      ↓ JNDI 조회 후 비즈니스 인터페이스 호출
[ EJB 컨테이너 ]
      ↓ 트랜잭션(CMT)·보안 인터셉터 통과
[ 세션 빈 : 업무 로직 수행 ]
      ↓ 영속성 처리
[ 엔티티 빈 / JPA ] → [ DB ]
```

```text
EJB 컨테이너 (횡단 서비스 제공)
 - 세션 빈 : Stateless / Stateful
 - MDB : JMS 메시지 비동기 처리
 - 엔티티 빈 : EJB 3.0 이후 JPA로 대체
```

## Ⅳ. EJB와 스프링 프레임워크의 비교

- 핵심 요약 : 컨테이너에 종속되는 침투적 EJB 2.x 모델과 도메인 객체를 지키는 비침투적 POJO 모델의 대비.

| 비교 축 | 엔터프라이즈 자바 빈즈 (EJB 2.x) | 스프링 프레임워크 (Spring Framework) |
| --- | --- | --- |
| 컴포넌트 철학 | EJB 전용 인터페이스 상속 강제(침투적) | POJO 기반 비침투적 설계 |
| 실행 환경 | 상용 WAS(Web Application Server) 필수 | 서블릿 컨테이너 또는 독립 실행 |
| 단위 테스트 | 컨테이너 없이는 어려움 | 순수 자바 객체로 테스트 가능 |
| 트랜잭션 관리 | 컨테이너 관리 트랜잭션(CMT) | AOP(Aspect-Oriented Programming) 기반 선언적 트랜잭션 |
| 분산 방식 | RMI 기반 원격 객체 호출을 기본으로 설계 | 로컬 호출 중심, 필요할 때 REST나 gRPC로 연계 |

- 선택 기준 : 기존 EJB 자산의 유지 여부와 원격 분산 호출의 필요성에 따라 유지보수와 전환 중 하나를 고른다.

## Ⅴ. EJB의 한계와 방안

- 핵심 요약 : 무거운 컨테이너 의존, 복잡한 사양, 원격 호출 오버헤드를 POJO 분리와 경량 프레임워크 전환으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 단위 테스트 곤란 | 실행에 상용 WAS가 필요해 빠른 격리 테스트 불가 | 업무 로직을 POJO로 분리하고 모킹으로 격리 테스트 | 테스트 자동화율 |
| 벤더 종속과 복잡한 사양 | Home·Remote 인터페이스와 XML 배포 서술자 관리 부담, 벤더 확장에 고착 | EJB 3.x 애노테이션 방식 적용 또는 경량 프레임워크로 전환 | 배포 서술자 수 |
| 원격 호출 오버헤드 | 계층 간 호출을 원격으로 설계해 직렬화와 네트워크 지연 발생 | 로컬 인터페이스 우선 사용, DTO로 일괄 전송 | 원격 호출 횟수, 응답 시간 |

## Ⅵ. 레거시 전환에 대한 기술사적 제언

- 핵심 요약 : 기존 EJB 자산을 POJO 기반 서비스로 점진 추출하고, 도메인 객체가 프레임워크에 묶이지 않는 경계를 세우는 방향이 바람직하다.
- 공공과 금융의 EJB 2.x 시스템은 클라우드 전환의 걸림돌이므로, 한 번에 교체하기보다 업무 단위로 POJO 서비스를 추출하고 영속성 계층을 JPA로 옮기는 단계적 현대화를 추진하는 것이 현실적이다.
- 신규 설계에서는 특정 프레임워크의 애노테이션이 도메인 엔티티에 퍼지지 않도록 아키텍처 계층의 경계를 코드 검토 기준으로 명문화해야 장기 유지보수성이 확보된다.

## Ⅶ. 결론

- 핵심 요약 : EJB는 기업 횡단 관심사를 컨테이너에 위임한 표준이었으나, 침투적 설계의 한계가 비침투적 POJO 방식으로의 전환을 이끌었음.
- 시사점 : 횡단 관심사의 표준화 효과는 취하되 도메인 로직을 프레임워크에서 분리하는 원칙이 현대 엔터프라이즈 아키텍처의 기준이 됨.
