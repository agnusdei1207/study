## Ⅰ. 무중단 배포의 개요

- 개념 : 24시간 무중단 서비스를 제공해야 하는 현대 시스템 환경에서, **서비스 중단** (Downtime)이나 사용자 요청 유실 없이 신규 버전의 애플리케이션을 안정적으로 배포하는 엔지니어링 전략.
- 배경 및 필요성 : 대규모 트래픽을 처리하는 글로벌 웹/모바일 서비스의 확산, 야간 점검에 따른 비즈니스 손실 방지, 빈번한 마이크로 릴리스 지원.
- 핵심 목표 : **무중단 서비스 연속성** (High Availability), 신속한 **롤백** (Rollback) 능력 확보, 배포 리스크 분산.

## Ⅱ. 주요 무중단 배포 전략의 메커니즘

```text
[ 롤링(Rolling) ]           [ 블루/그린(Blue/Green) ]          [ 카나리(Canary) ]
 인스턴스를 순차적으로 교체      구버전(Blue)과 신버전(Green) 병행     신버전에 트래픽 일부(10%) 할당
 (v1 v1) -> (v1 v2) -> (v2 v2)  라우터 스위칭으로 일괄 전환          모니터링 후 점진적 100% 확대
```

- **롤링 배포 (Rolling Update)** : 인스턴스를 하나씩 순차적으로 구버전에서 신버전으로 교체. 추가 인프라 비용이 적으나 배포 도중 구버전과 신버전이 공존하여 호환성 문제 발생 가능.
- **블루/그린 배포 (Blue/Green)** : 동일 규모의 신규 환경(Green)을 사전에 구축하고 테스트 완료 후 로드밸런서 라우팅을 즉각 스위칭. 롤백이 즉시 가능하나 2배의 인프라 자원 소모.
- **카나리 배포 (Canary)** : 극소수 사용자(또는 특정 가중치)에게 신버전을 먼저 노출하고 오류율, 지연시간 모니터링 후 점진적으로 트래픽을 이전. 실운영 리스크 최소화.

## Ⅲ. 무중단 배포 전략 비교 및 데이터베이스 마이그레이션 패턴

| 구분 | 롤링 배포 | 블루/그린 배포 | 카나리 배포 |
|---|---|---|---|
| 인프라 요구량 | 추가 자원 최소 (기존 자원 활용) | 2배의 인프라 필요 | 미세한 추가 자원 필요 |
| 롤백 속도 | 느림 (역순 롤링 재수행) | 즉각적 (라우팅 스위칭 복원) | 신속함 (가중치 0% 재설정) |
| 버전 공존 여부 | 공존함 (이종 버전 동시 실행) | 공존하지 않음 (단절 전환) | 의도적 공존 (A/B 검증 형태) |
| 적합 환경 | 일반 웹 앱, 자원 제약 환경 | 미션 크리티컬 시스템, 즉시 롤백 필수 환경 | 대규모 사용자 대상 B2C 서비스 |

- DB 무중단 마이그레이션: **확장 및 축소** (Expand & Contract) 패턴 :
  - **1단계 (Expand)** : 구버전과 호환되도록 신규 컬럼/테이블을 추가(Nullable 또는 기본값 설정)하고 **이중 쓰기** (Dual Write) 수행.
  - **2단계 (Transition)** : 신규 버전 앱 배포 완료 후 신규 스키마를 단독 읽기/쓰기로 전환.
  - **3단계 (Contract)** : 구버전 앱이 완전히 제거된 후 미사용 레거시 컬럼/테이블 최종 삭제.

## Ⅳ. 무중단 배포의 주요 한계점 및 해결 방안

- 데이터베이스 스키마 마이그레이션 시 하위 호환성 단절 :
  - 한계점 : 롤링 배포나 블루/그린 배포 시 신구 버전 애플리케이션이 공존하는 과도기 동안 DB 컬럼 삭제나 타입 변경이 발생하면 이전 버전 인스턴스에서 런타임 쿼리 예외 발생.
  - 해결 방안 : 병렬 변경(Expand-Contract / Parallel Run) 패턴을 적용하여 컬럼 추가 -> 이중 쓰기(Dual Write) -> 과거 데이터 동기화 -> 구 컬럼 제거를 단계적으로 진행하고, Liquibase/Flyway 기반 무중단 마이그레이션 파이프라인 구성.
- 블루/그린 배포의 인프라 비용 2배 증가 및 유저 세션 단절 :
  - 한계점 : 전체 환경을 복제해야 하므로 클라우드 리소스 비용이 일시적으로 100% 증가하며, 상태 저장(Stateful) 애플리케이션의 경우 인스턴스 전환 시 사용자 인메모리 세션이 유실됨.
  - 해결 방안 : Redis 등 외부 인메모리 분산 세션 클러스터를 구축하여 무상태(Stateless) 아키텍처로 전환하고, 비용 효율적인 점진적 카나리(Canary) 배포 전략 병행 및 Spot 인스턴스 활용.
- 비정상 배포 시 데이터 불일치 및 롤백 복잡도 :
  - 한계점 : 신규 버전에서 이미 처리되어 DB에 커밋된 트랜잭션이 존재하는 상태에서 롤백을 수행할 경우 신구 버전 데이터 정합성이 깨지고 역방향 마이그레이션이 불가.
  - 해결 방안 : 카나리 배포 구간에서 프로메테우스 기반 에러율 및 레이턴시 자동 감지 즉시 롤백 체계를 구축하고, 비즈니스 보상 트랜잭션(Saga Pattern) 로직 사전 구비.

## Ⅴ. 무중단 배포 아키텍처 구축 시 기술사적 제언

- 세션 불연속성 방지 및 상태 비저장(Stateless) 설계 : 배포 중 인스턴스 종료 시 세션이 단절되는 문제를 막기 위해 인메모리 Redis 기반의 외장 세션 클러스터링을 기본 채택하고 그레이스풀 셧다운(Graceful Shutdown) 설정 필수.
- 서비스 메시(Service Mesh) 기반 세밀한 트래픽 제어 : Istio/Envoy를 활용하여 HTTP 헤더, 쿠키, 사용자 지역 기반의 L7 라우팅 룰을 적용함으로써 비즈니스 영향도를 완벽히 통제하는 카나리 배포 체계 고도화 필요.
