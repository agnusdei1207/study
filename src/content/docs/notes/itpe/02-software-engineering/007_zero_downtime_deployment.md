## 연관 키워드

- 무중단 배포, 롤링 배포(Rolling Update), 블루·그린 배포(Blue/Green), 카나리 배포(Canary)
- 롤백(Rollback), 확장 및 축소(Expand & Contract), 이중 쓰기(Dual Write), 그레이스풀 셧다운(Graceful Shutdown)

## Ⅰ. 무중단 배포의 개요

- 핵심 요약 : 서비스 중단 없이 새 버전을 올리고 문제가 생기면 신속히 되돌리는 배포 전략 체계.
- 개념 : 24시간 운영 환경에서 서비스 중단이나 요청 유실 없이 신규 버전을 배포하는 엔지니어링 전략인 **무중단 배포** (Zero-Downtime Deployment).
- 배경 및 필요성 : 대규모 트래픽을 처리하는 서비스가 늘고, 야간 점검에 따른 비즈니스 손실을 막아야 하며, 마이크로 릴리스를 자주 내보내야 하는 요구.
- 주요 목적 : 서비스 연속성과 고가용성(HA, High Availability) 확보, 이전 버전으로 되돌리는 **롤백** (Rollback) 능력 확보, 배포 리스크 분산.

## Ⅱ. 무중단 배포의 특징 및 장점

- 핵심 요약 : 버전 공존 관리, 점진적 트래픽 전환, 즉시 되돌림 능력이 결합된 가용성 중심의 배포 방식.

1. 배포 중 서비스 연속성 유지와 사용자 요청 유실 방지 → 배포 시간대에도 장애 체감을 최소화.
2. 전략마다 다른 구·신 버전 공존 방식 → 전략 선택에 따라 호환성 설계 범위가 결정됨.
3. 트래픽 가중치 제어 : 소수 사용자에게 먼저 노출하고 오류율과 지연 시간을 모니터링 → 실운영 환경에서 품질 검증.
4. 라우팅 스위칭이나 가중치 재설정으로 신속히 되돌림 → 장애 영향 범위 축소.
5. **상태 비저장** (Stateless, 요청 사이에 서버가 사용자 상태를 들고 있지 않는 설계) : 인스턴스가 교체되어도 세션이 유지되도록 세션을 외부화하는 것이 전제 조건.
6. **그레이스풀 셧다운** (Graceful Shutdown, 진행 중인 요청을 마친 뒤 인스턴스를 종료하는 방식) → 종료 시점의 요청 유실 방지.

## Ⅲ. 무중단 배포의 구조 (흐름)

- 핵심 요약 : 롤링, 블루·그린, 카나리의 3대 전략과, DB 스키마를 단계적으로 바꾸는 확장 및 축소 흐름.

```text
[ 3대 배포 전략 개요 ]

[ 롤링 ]      v1 v1 → v1 v2 → v2 v2
              인스턴스를 순차 교체
[ 블루·그린 ] 구·신 환경 병행, 라우터 일괄 전환
[ 카나리 ]    소수 트래픽 → 단계적 확대
```

- **롤링 배포** (Rolling Update) : 구버전 인스턴스를 신버전으로 순차 교체. 추가 인프라는 적게 들지만 배포 도중 구·신 버전이 공존해 호환성 문제가 생길 수 있음.
- **블루·그린 배포** (Blue/Green Deployment) : 신규 환경(Green)을 미리 구축해 검증한 뒤 로드밸런서 라우팅을 일괄 전환. 롤백은 즉시 가능하지만 동일 규모의 환경을 두 벌 운영하므로 자원 부담이 큼.
- **카나리 배포** (Canary Deployment) : 소수 사용자에게 먼저 노출하고 오류율과 지연 시간을 보며 트래픽을 점진적으로 옮겨 실운영 리스크를 최소화.
- **확장 및 축소** (Expand & Contract) : DB를 멈추지 않고 스키마를 바꾸는 마이그레이션 패턴.

1. Expand 단계 : 구버전과 호환되는 컬럼·테이블을 추가하고 **이중 쓰기** (Dual Write, 신·구 스키마에 동시에 기록) 수행.
2. 전환 단계 : 신버전 배포가 끝나면 신규 스키마만 읽고 쓰도록 전환.
3. Contract 단계 : 구버전을 완전히 걷어낸 뒤 레거시 컬럼과 테이블을 삭제.

```text
[ 카나리 트래픽 전환 ]

소수 트래픽 노출
   ↓ 지표 정상이면
단계적 확대
   ↓ 지표 정상이면
전체 전환
   ※ 이상 감지 시 즉시 0%로 롤백
```

## Ⅳ. 무중단 배포 전략 비교

- 핵심 요약 : 인프라 요구량, 롤백 속도, 버전 공존 여부, 적합 환경이 달라 전략 선택 기준이 갈리는 구조.

| 구분 | 롤링 배포 | 블루·그린 배포 | 카나리 배포 |
| --- | --- | --- | --- |
| 인프라 요구량 | 기존 자원 활용, 추가 부담 적음 | 동일 규모 환경 두 벌 필요 | 소량의 추가 자원 필요 |
| 롤백 속도 | 역순 롤링 재수행으로 지연 | 라우팅 스위칭 복원으로 즉시 | 가중치를 0으로 되돌려 신속 |
| 버전 공존 여부 | 이종 버전 동시 실행 | 공존하지 않고 단절 전환 | 의도적 공존으로 A/B 검증 형태 |
| 적합 환경 | 일반 웹 앱, 자원 제약 환경 | 미션 크리티컬 시스템, 즉시 롤백 필수 환경 | 대규모 사용자 대상 B2C(Business-to-Consumer) 서비스 |

- 선택 기준 : 자원 여유, 롤백 허용 시간, 구·신 버전 호환성 보장 가능 여부를 함께 보고 전략을 고름.

## Ⅴ. 무중단 배포의 한계와 방안

- 핵심 요약 : 가용성과 신속 롤백이라는 장점과, 스키마 호환성·인프라 비용·롤백 데이터 정합성의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| DB 스키마 호환성 단절 | 과도기에 컬럼을 삭제하거나 타입을 바꾸면 이전 버전 인스턴스의 쿼리가 예외 발생 | 확장 및 축소 단계 적용, 이중 쓰기 후 구 컬럼 제거, Liquibase·Flyway 기반 마이그레이션 자동화 | 스키마 변경 실패율, 배포 중 오류율 |
| 블루·그린 비용과 세션 단절 | 환경 복제로 자원 비용이 일시 증가하고, 상태 저장 서버 전환 시 인메모리 세션 유실 | Redis 등 외부 세션 저장소로 무상태 구조 전환, 카나리 배포 병행 | 세션 유실률, 유휴 자원 비율 |
| 비정상 배포 시 데이터 정합성 붕괴 | 신버전이 DB에 커밋한 데이터가 있으면 롤백 후 신구 데이터 정합성이 깨짐 | Prometheus 기반 오류율·지연 자동 감지로 즉시 롤백, **보상 트랜잭션** (Saga Pattern) 로직 사전 구비 | 롤백 소요 시간, 정합성 검증 실패 건수 |

## Ⅵ. 무중단 배포 아키텍처 구축 시 기술사적 제언

- 핵심 요약 : 상태 비저장 설계와 그레이스풀 셧다운을 기본값으로 두고, 서비스 메시로 트래픽을 세밀하게 통제하는 방향.
- 배포 플랫폼의 기본값 고정 : 신규 서비스는 상태 비저장 설계와 그레이스풀 셧다운 설정을 템플릿으로 강제해, 개별 팀이 배포 때마다 같은 문제를 다시 해결하지 않도록 하는 것이 필요함.
- 서비스 메시 기반 정밀 제어 : Istio나 Envoy 같은 서비스 메시에서 HTTP 헤더, 쿠키, 사용자 지역 기준의 L7(Layer 7) 라우팅 규칙을 두어, 비즈니스 영향 범위를 기준으로 카나리 노출을 통제하는 체계가 필요함.

## Ⅶ. 결론

- 핵심 요약 : 무중단 배포는 전략 선택과 스키마·세션·롤백 설계가 맞물린 가용성 엔지니어링.
- 시사점 : 상태 비저장 아키텍처와 자동 롤백 체계를 미리 갖추는 것이 무중단 연속성의 선결 조건임.
