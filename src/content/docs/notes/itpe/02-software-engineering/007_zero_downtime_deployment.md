## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 빌드·배포·DevOps → **무중단 배포·배포 전략**

## 30초 인출

- 본질: 무중단 배포(Zero-Downtime Deployment)는 서비스 가동 중단 없이 신규 버전을 프로덕션 환경에 배포하고 트래픽을 안전하게 전환하는 엔지니어링 기법
- 메커니즘: 롤링(Rolling), 블루/그린(Blue/Green), 카나리(Canary) 전략 기반 트래픽 제어와 DB 호환을 위한 Expand/Contract 패턴의 결합
- 통찰: 배포 중 구버전과 신버전의 동시 실행 구간에서 DB 스키마 불일치가 발생하므로 병렬 변경(Expand/Contract) 패턴과 헬스체크 기반 트래픽 통제 적용

<details>
<summary>핵심 용어</summary>

- **무중단 배포(Zero-Downtime Deployment)** : 사용자가 서비스 단절을 체감하지 못하도록 트래픽 라우팅을 제어하며 애플리케이션 버전을 갱신하는 배포 방식
- **Blue/Green Deployment** : 동일 스펙의 구버전(Blue)과 신버전(Green) 환경을 분리 구축하고 라우팅 스위칭으로 한 번에 전환하는 방식
- **Canary Deployment** : 위험 조기 감지를 위해 극소수(1~5%) 트래픽만 신규 버전에 우선 유입시켜 지표 검증 후 점진적으로 확대하는 방식
- **Rolling Deployment** : 실행 중인 서버 인스턴스를 하나씩 순차적으로 내리고 새 버전으로 교체하여 배포하는 방식
- **Expand/Contract Pattern** : 무중단 배포 시 DB 스키마 호환성을 보장하기 위해 확장(Expand) → 전환(Transition) → 축소(Contract)의 3단계로 진행하는 패턴
- **Graceful Shutdown** : 프로세스 종료 신호 수신 시 신규 요청 수신을 차단하고 기 유입된 진행 중 요청을 모두 완료한 후 안전하게 종료하는 절차

## 2~4교시 25점 답안

## Ⅰ. 무중단 배포의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **무중단 배포(Zero-Downtime Deployment)** 는 구버전에서 신버전으로 전환하는 과정 중에도 사용자 요청 처리를 무단절로 유지하는 배포 방식 |
| 목적 | 24×7 고가용성 서비스 보장, 배포 리스크 완화 및 결함 발생 시 즉각적인 롤백 경로 확보 |

## Ⅱ. 무중단 배포의 핵심 특징

| 특징 | 의미 |
|---|---|
| 가용성 무손실 | 배포 작업 중에도 준비된 인스턴스로 트래픽을 라우팅하여 서비스 정지 시간 제로화 |
| 점진적 검증 | 신규 버전의 정상 동작 여부를 실제 운영 환경에서 점진적으로 검증할 수 있는 통제력 제공 |
| 즉시 롤백 보장 | 이상 징후 감지 시 라우팅 변경 또는 이전 버전 재배포를 통해 다운타임 없는 복원 지원 |

## Ⅲ. 무중단 배포 3대 전략 메커니즘

### 배포 전략별 트래픽 제어 구조

```text
무중단 배포 전략
    ├─ Rolling Update: 전체 인스턴스 중 N개씩 순차 교체
    ├─ Blue/Green: 구버전(Blue)과 신버전(Green) 간 라우팅 100% 즉시 절체
    └─ Canary: 신규 버전에 1% → 10% → 50% → 100% 점진적 트래픽 확대
```

### 카나리(Canary) 배포 판정 및 프로모션 흐름

```text
카나리 인스턴스 5% 트래픽 유입
    ↓
실시간 모니터링: 오류율(5xx), 응답 지연시간(Latency), 자원 사용률
    ↓
품질 기준 판정
    ├─ 임계치 초과(오류 발생) → 카나리 트래픽 즉시 차단 및 자동 롤백
    └─ 지표 정상 유지 → 트래픽 25% → 50% → 100% 단계적 확대 후 전면 교체
```

| 배포 전략 | 동작 방식 | 인프라 비용 | 롤백 속도 | 적합 서비스 |
|---|---|---|---|---|
| Rolling Update | 순차적 인스턴스 교체 | 추가 비용 없음 (여유분 최소화) | 느림 (순차적 재배포 소요) | 대규모 클러스터, 리소스 제약 환경 |
| Blue/Green | 이중 환경 구축 후 라우터 스위칭 | 높음 (2배의 인프라 필요) | 즉각적 (라우팅 재전환) | 미션 크리티컬 결제·금융 시스템 |
| Canary | 소량 트래픽 선별 투입 후 확대 | 낮음 (최소 카나리 인스턴스) | 빠름 (카나리 라우팅 차단) | 사용자 행동 및 실 트래픽 검증 필요 서비스 |

## Ⅳ. 무중단 DB 스키마 마이그레이션: Expand/Contract

### DB 스키마 무중단 변경 3단계 메커니즘

```text
[1단계: Expand (확장)]
    기존 컬럼 유지 + 신규 컬럼 Null 허용 추가 (구버전/신버전 동시 수용)
         ↓
[2단계: Transition (전환)]
    신버전 배포, 양방향 쓰기/읽기 수행 및 과거 데이터 백필(Backfill)
         ↓
[3단계: Contract (축소)]
    모든 구버전 인스턴스 종료 확인 후 레거시 컬럼 안전하게 삭제
```

| 단계 | 애플리케이션 동작 | DB 스키마 상태 | 롤백 가능성 |
|---|---|---|---|
| 1. Expand | 구버전(V1) 정상 운영 | 신규 컬럼 생성 (기본값 설정 또는 Null 허용) | 완전 가능 (V1 영향 전무) |
| 2. Transition | 신버전(V2) 점진 배포, 양방향 쓰기 | 신구 컬럼 동시 데이터 갱신 및 백그라운드 동기화 | 가능 (V1 스키마 유지) |
| 3. Contract | 전원 신버전(V2) 단독 운영 | 구버전 레거시 컬럼 및 트리거 삭제 | V1 복귀 불가 (V2 확정) |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 인스턴스 교체 도중 진행 중이던 요청이 강제 종료되어 데이터 정합성 훼손 | **Graceful Shutdown** 및 로드밸런서의 Connection Draining 설정 적용 |
| 신규 인스턴스 부팅 직후 웜업 미완료 상태에서 트래픽 유입으로 응답 지연 | Readiness Probe 설정으로 서비스 헬스체크 통과 후에만 트래픽 유입 허용 |
| 구버전과 신버전이 공존하는 배포 구간에서 사용자 세션 불일치 및 로그아웃 발생 | Redis 등 외부 인메모리 분산 세션 저장소 적용 및 무상태(Stateless) 아키텍처 구현 |

## Ⅵ. 제언

서비스 위험도와 인프라 리소스에 기반한 배포 전략 포트폴리오 수립과 자동화된 카나리 분석(ACA) 도입

### 서비스 특성별 무중단 배포 전략 의사결정 체계

```text
배포 대상 서비스 아키텍처 및 요구조건 분석
    ↓
선정 판정
    ├─ 예산 제약 및 리소스 한정 → 롤링 업데이트(Rolling Update) 채택
    ├─ 데이터베이스 구조 변경 동반 → Expand/Contract 패턴 필수 결합
    ├─ 무중단 즉각 롤백 요구(금융/과금) → Blue/Green 배포 채택
    └─ 대규모 사용자 서비스 품질 위험 검증 → 자동화 카나리(ACA) 채택
    ↓
CI/CD 배포 파이프라인 연계 및 자동 롤백 임계치 구성
```

### 자동화 카나리 분석(ACA) 실행 절차

```text
신규 빌드 카나리 배포
    ↓
기준(Baseline) 인스턴스와 카나리(Canary) 인스턴스 간 메트릭 동시 수집
    ↓
통계적 유의성 검정 (Mann-Whitney U Test)
    ├─ 통계적 열화 감지 → 배포 자동 중단 및 카나리 삭제
    └─ 점수 기준 충족 → 프로덕션 전체 롤아웃 승인
```

### 선택 근거: 수작업 모니터링과 자동화 카나리 분석(ACA) 비교

| 구분 | 수작업 모니터링 기반 배포 | 제언: 자동화 카나리 분석 (ACA) |
|---|---|---|
| 판정 주체 | 엔지니어 육안 모니터링 대시보드 확인 | 실시간 메트릭 분석 엔진 자동 채점 |
| 롤백 반응성 | 수작업 판단 및 커맨드 실행으로 지연 | 임계치 위반 시 파이프라인 자동 롤백 |
| 검증 신뢰도 | 담당자 숙련도에 따라 편차 발생 | 통계적 가설 검정 기반의 객관적 판정 |
