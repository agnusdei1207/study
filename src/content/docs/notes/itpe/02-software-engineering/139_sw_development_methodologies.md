## 30초 인출

- 본질: 소프트웨어 개발방법론은 개발 활동의 절차와 산출물을 정한 체계이며 구조적·정보공학·객체지향·CBD 방법론이 시간 순으로 발전
- 메커니즘: 구조적은 기능을 하향식으로 분해하고, 정보공학은 데이터를 중심으로 설계하며, 객체지향은 객체 단위로, CBD는 컴포넌트를 조립해 개발
- 통찰: 방법론마다 분해 단위(기능·데이터·객체·컴포넌트)가 달라 강점이 다르므로 프로젝트의 변경 특성과 재사용 요구를 기준으로 선택하고 조직 표준 방법론을 테일러링

<details>
<summary>핵심 용어</summary>

- **구조적 방법론(Structured Methodology)** : 기능을 하향식으로 분해하고 자료 흐름도(DFD)로 표현하는 방법론
- **정보공학 방법론(Information Engineering)** : 기업의 정보 전략에서 출발해 데이터 구조를 중심으로 시스템을 개발하는 방법론
- **객체지향 방법론(Object-Oriented Methodology)** : 데이터와 처리를 객체로 묶어 분석·설계하는 방법론
- **CBD(Component-Based Development)** : 표준 인터페이스를 가진 컴포넌트를 조립해 개발하는 방법론
- **DFD·ERD·UML** : 구조적·정보공학·객체지향 방법론이 주로 쓰는 모델링 표기

</details>

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 개발방법론의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 개발방법론** 은 개발 활동의 절차·기법·산출물을 정한 체계 |
| 목적 | 개발 과정의 표준화와 품질 확보 |

## Ⅱ. 방법론의 특징과 발전

| 특징 | 의미 |
|---|---|
| 분해 단위의 변화 | 기능 → 데이터 → 객체 → 컴포넌트 |
| 재사용 강화 | 후대 방법론일수록 재사용 단위 확대 |
| 모델링 표기 | 방법론별 표준 표기 사용 |

## Ⅲ. 방법론의 발전 흐름

### 방법론의 발전

```text
구조적 (기능 분해)
    ↓ 데이터 중심으로 확장
정보공학 (데이터 구조)
    ↓ 데이터+처리 결합
객체지향 (객체)
    ↓ 재사용 단위 확대
CBD (컴포넌트)
```

### 확대: 분해 단위의 차이

```text
구조적: 시스템 → 기능 → 하위 기능 (DFD)
정보공학: 시스템 → 엔티티·관계 (ERD)
객체지향: 시스템 → 객체·클래스 (UML)
CBD: 시스템 → 컴포넌트·인터페이스
```

## Ⅳ. 방법론의 비교

| 구분 | 구조적 | 정보공학 | 객체지향 | CBD |
|---|---|---|---|---|
| 분해 단위 | 기능(프로세스) | 데이터(엔티티) | 객체 | 컴포넌트 |
| 표기 | DFD | ERD | UML | 컴포넌트 다이어그램 |
| 강점 | 절차 이해 용이 | 데이터 일관성 | 변경 용이·재사용 | 조립 기반 재사용 |
| 약점 | 변경 시 파급 큼 | 처리 로직 표현 약함 | 초기 설계 부담 | 인터페이스 표준 필요 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 프로젝트 특성과 맞지 않는 방법론 적용 | 변경·재사용 요구에 따른 선택 |
| 표준 방법론의 과잉·부족 | 테일러링 |
| 방법론 혼용으로 산출물 불일치 | 산출물 표준과 추적성 정의 |

## Ⅵ. 제언

프로젝트의 변경 빈도와 재사용 요구로 방법론을 선택하고, 조직 표준 방법론은 프로젝트 특성에 맞게 테일러링

### 선택 순서

```text
프로젝트 특성 분석 (변경 빈도·재사용·규모)
    ↓
방법론 선택
    ↓
테일러링 → 산출물 표준 확정
```

### 선택 근거: 하나의 방법론 고정과의 비교

| 구분 | 하나로 고정 | 제언: 특성별 선택·테일러링 |
|---|---|---|
| 적합성 | 프로젝트마다 편차 | 특성 반영 |
| 재사용 | 방법론 한계 | 필요 수준 |
| 관리 부담 | 낮음 | 선택·조정 필요 |
