## 지식 로드맵 내 현재 위치

<div class="itpe-topic-path" aria-label="소프트웨어 생명주기에서 개발방법론까지의 지식 경로"><span>SW 공학·생명주기</span><span>프로세스 선택·조정</span><strong>개발방법론·테일러링</strong></div>

## 해당 토픽 큰 그림과 30초 인출

```text
구조적(기능) → 정보공학(전사 데이터) → 객체지향(상태+행위) → CBD(계약 기반 부품)
     DFD             ERD·CRUD               UML              컴포넌트 명세
```

- 인출어: `구=기능·DFD`, `정=데이터·CRUD`, `객=객체·UML`, `CBD=계약·재사용`, `선택=복잡도·변경·데이터·재사용`

## 예상문제

> 구조적·정보공학·객체지향·CBD 방법론의 관점과 주요 산출물을 비교하고 프로젝트 특성에 따른 선택·테일러링 방안을 설명하시오. (25점)

## 딸려 나오는 하위 토픽

| 하위 토픽 | 핵심 키워드 | 통합 답안 위치 |
|---|---|---|
| 구조적 방법론 | 하향식 기능분할, DFD, DD, Mini-Spec, 구조도 | Ⅲ·Ⅳ |
| 정보공학 방법론 | ISP, 업무영역, 전사 데이터모델, ERD, CRUD | Ⅲ·Ⅴ |
| 객체지향 방법론 | 객체·책임, 캡슐화, 다형성, UML | Ⅲ·Ⅴ |
| CBD | 컴포넌트 식별, 명세, 계약, 조립, 재사용 | Ⅲ·Ⅴ |

## Ⅰ. 문제를 보는 중심축이 다른 개발방법론 개요

SW 개발방법론은 요구분석부터 설계·구현·검증을 일관되게 수행하기 위한 절차·기법·산출물의 체계이다. 구조적·정보공학·객체지향·CBD는 각각 **기능, 전사 데이터, 객체, 계약 기반 컴포넌트**를 주요 추상화 단위로 삼는다.

## Ⅱ. 방법론 선택의 원칙

| 선택축 | 확인 질문 | 유리한 관점 |
|---|---|---|
| 처리 흐름 | 입출력·변환 흐름이 핵심인가 | 구조적 |
| 데이터 안정성 | 전사 데이터 공유·정합성이 중요한가 | 정보공학 |
| 업무 변경 | 상태와 행위, 복잡한 규칙이 변하는가 | 객체지향 |
| 재사용·조립 | 명확한 계약으로 부품을 교체하는가 | CBD |
| 프로젝트 제약 | 규모·규제·팀역량·레거시는 어떠한가 | 테일러링 |

## Ⅲ. 네 방법론의 핵심구조와 산출물

```text
[구조적] 기능 분할 ─ DFD·DD·Mini-Spec ─ 구조도
[정보공학] ISP/업무영역 ─ 데이터모델·ERD ─ CRUD
[객체지향] 유스케이스 ─ 클래스·상호작용 ─ UML
[CBD] 요구 ─ 컴포넌트 식별·명세 ─ 조립·시험
```

| 방법론 | 기본원리 | 대표 산출물 | 주요 강점 | 주의점 |
|---|---|---|---|---|
| 구조적 | 하향식 기능분할·자료흐름 | DFD, DD, Mini-Spec, 구조도 | 처리흐름 명료 | 데이터·변경 영향 분산 |
| 정보공학 | 전사 계획과 데이터 중심 | 주제영역, ERD, CRUD 매트릭스 | 데이터 정합성 | 선행분석 부담·경직성 |
| 객체지향 | 상태와 행위의 캡슐화 | 유스케이스, 클래스·시퀀스 모델 | 변경격리·현실 모델링 | 책임분배·모델 품질 의존 |
| CBD | 명시적 인터페이스의 부품조립 | 컴포넌트·인터페이스 명세 | 재사용·대체 가능성 | 부품 적합성·통합시험 |

## Ⅳ. 구조적 분석 도구의 연계

```text
Context DFD → 단계별 DFD → DD로 데이터 정의 → Mini-Spec으로 원시 프로세스 명세
                                    └────────→ 일관성·균형 검증
```

- **DFD**: 외부개체, 프로세스, 자료흐름, 자료저장소로 기능과 데이터 이동을 표현한다.
- **DD**: DFD의 자료항목·구조·의미를 공통 어휘로 정의한다.
- **Mini-Spec**: 최하위 프로세스의 판단과 처리규칙을 구조적 언어·의사결정표 등으로 명세한다.
- 상·하위 DFD의 입력·출력을 균형화하고 DD·Mini-Spec과 명칭을 일치시켜야 한다.

## Ⅴ. 네 방법론 비교

| 비교축 | 구조적 | 정보공학 | 객체지향 | CBD |
|---|---|---|---|---|
| 중심 | 기능·프로세스 | 전사 데이터 | 객체·책임 | 컴포넌트·계약 |
| 분할기준 | 기능 계층 | 업무·데이터 영역 | 응집된 책임 | 제공·요구 인터페이스 |
| 변화격리 | 모듈 | 데이터 모델 | 캡슐화·다형성 | 교체 가능한 부품 |
| 검증초점 | DFD 균형·명세 일치 | 데이터·CRUD 완전성 | 객체협력·추적성 | 계약·조립·통합 |

## Ⅵ. 단일방법론 맹신을 피하는 테일러링

| 위험 | 대응 | 확인 산출물 |
|---|---|---|
| 산출물 과다 | 규모·위험별 필수 산출물과 상세도 결정 | 테일러링 계획 |
| 관점 불일치 | 기능-데이터-객체-컴포넌트 추적관계 정의 | 추적표·CRUD |
| 표준 없는 모델 | 용어·식별자·모델링 규칙 통일 | 데이터·모델 표준 |
| 재사용 강제 | 적합성·성능·보안·유지보수성 평가 | 컴포넌트 평가서 |
| 현대 개발과 단절 | 반복주기 안에서 필요한 모델을 점진 상세화 | 백로그·완료정의 |

## Ⅶ. 정답 방법론보다 적합한 조합을 찾는 결론

방법론은 시대순으로 이전 방식을 폐기하는 관계가 아니라 서로 다른 문제 관점을 제공한다. 업무 특성과 위험에 따라 산출물을 줄이거나 결합하되, **요구-모델-구현-시험 추적성**은 유지해야 한다.

## 1교시 10점 답안 발췌

```text
정의: 개발방법론은 개발 절차·기법·산출물을 일관되게 묶은 수행체계
진화축: 구조적(기능) → 정보공학(데이터) → 객체지향(상태+행위) → CBD(부품)
산출물: DFD·DD / ERD·CRUD / UML / 컴포넌트·인터페이스 명세
선택축: 처리흐름, 데이터 정합성, 변경복잡도, 재사용성, 규모·위험·팀역량
결론: 단일 방법론 적용보다 목적별 테일러링과 전 구간 추적성이 핵심
```
