## 30초 인출

- 본질: **소프트웨어 개발방법론** 은 개발 활동·기법·산출물을 조직하는 방식으로, 구조적·정보공학·객체지향·컴포넌트 기반 개발이 서로 다른 모델링 초점을 둠
- 메커니즘: 요구와 제약 파악 → 적합한 모델링 관점·생명주기 선택 → 산출물 작성 → 프로젝트 규모와 위험에 맞게 조정
- 통찰: 한계: 특정 방법론의 산출물을 무조건 적용하면 요구·데이터·재사용 특성과 어긋날 수 있음 → 방안: 모델링 초점과 프로젝트 위험에 맞춰 활동을 조정

<details>
<summary>핵심 용어</summary>

- **구조적 방법론(Structured Methodology)** : 기능을 단계적으로 분해하고 자료 흐름을 모델링하는 방법론
- **정보공학(Information Engineering)** : 정보 요구와 데이터 구조를 중심으로 기업 시스템을 분석·설계하는 접근
- **객체지향(Object-Oriented) 방법론** : 상태와 행위를 가진 객체의 협력으로 시스템을 모델링하는 접근
- **CBD(Component-Based Development)** : 명확한 인터페이스를 가진 소프트웨어 구성요소를 조립·재사용하는 개발 접근
- **DFD(Data Flow Diagram)** : 프로세스 간 자료의 입력·변환·출력을 나타내는 자료 흐름도
- **ERD(Entity-Relationship Diagram)** : 데이터 개체와 관계를 표현하는 개체 관계도
- **UML(Unified Modeling Language)** : 소프트웨어 구조·행동을 표기하는 모델링 언어
- **CRUD(Create, Read, Update, Delete)** : 데이터 생성·조회·수정·삭제 기본 작업
- **DD(Data Dictionary)** : 데이터 흐름·자료 항목의 이름과 의미를 정의한 자료 사전
</details>

## 2~4교시 예상문제 (25점)

> 정보시스템 개발방법론의 모델링 관점과 산출물을 비교하고, 프로젝트 특성에 따른 선택 기준 및 적용상 유의점을 설명하시오. (25점, 예상)

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 개발방법론의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 개발방법론** 은 개발 활동·기법·산출물을 조직하는 방식이며, 방법론별 모델링 초점이 다름 |
| 목적 | 프로젝트 요구와 제약에 맞는 접근을 선택하고 산출물을 일관되게 관리 |

## Ⅱ. 모델링 관점과 산출물의 특징

| 특징 | 적용 의미 |
|---|---|
| 모델링 중심의 차이 | 기능·데이터·객체·컴포넌트 중 검증할 설계 대상을 먼저 선택 |
| 산출물의 추적성 | 요구·모델·구현·시험 간 연결을 변경 영향 분석에 사용 |
| 프로젝트별 조정 | 규모·위험·재사용 수준에 따라 필수 활동과 산출물 범위 조정 |

## Ⅲ. 모델링 관점 선택과 산출물 추적 프로세스

### 요구에서 검증까지의 적용 프레임

```text
프로젝트 요구·제약
   ↓ 핵심 모델링 대상 식별
기능 / 데이터 / 객체 / 재사용 부품
   ↓ 방법론과 필수 산출물 선택
요구사항 ↔ 분석·설계 모델 ↔ 구현
   └─────────────────────→ 시험·검증
             변경 시 추적 관계 갱신
```

요구에서 모델·구현·시험으로 이어지는 연결 단위를 위험과 검증 요구에 맞춰 정하고, 변경 시 설계 책임·인터페이스·시험 사례의 영향을 확인한다.

## Ⅳ. 구조적·정보공학·객체지향·CBD 비교

| 비교축 | 구조적 방법론 | 정보공학 방법론 | 객체지향 방법론 | CBD 방법론 |
|---|---|---|---|---|
| 핵심 추상화 | 기능·프로세스 | 데이터·정보 구조 | 객체·책임 | 인터페이스·구성요소 |
| 접근 방식 | 기능 분해·자료 흐름 | 데이터 구조와 업무 기능 연계 | 객체 책임·협력 | 계약 기반 부품 조립 |
| 대표 산출물 | DFD, DD, 소단위명세서 | 주제영역도, ERD, CRUD 매트릭스 | 유스케이스, 클래스도, 시퀀스도 | 컴포넌트 명세서, 인터페이스 정의서 |
| 중점 판단 | 입력·출력·변환 | 데이터와 업무의 일관성 | 책임 배분·결합도 | 인터페이스·버전·의존성 호환 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 특정 방법론의 산출물을 무조건 적용하면 요구·데이터·재사용 특성과 어긋날 수 있음 | 모델링 초점과 프로젝트 위험에 맞춰 활동을 조정 |
| 프로젝트 규모보다 많은 산출물 | 필수·선택 산출물을 위험과 규모에 맞춰 조정 |
| 모델과 구현의 괴리 | 리뷰와 추적으로 요구·모델·코드의 연결 확인 |
| 재사용 구성요소의 인터페이스 불일치 | 인터페이스 계약을 검증하고 필요한 어댑터를 설계 |

## Ⅵ. 제언

**제언:** 프로젝트 착수 시 검증이 필요한 핵심 설계 대상을 먼저 정하고, 그 대상의 요구·모델·시험 추적에 필요한 최소 산출물부터 채택한다.
