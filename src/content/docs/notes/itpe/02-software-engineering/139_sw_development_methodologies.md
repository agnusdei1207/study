## Ⅰ. SW 개발방법론의 발전 개요

- **개념** : 소프트웨어를 성공적으로 엔지니어링하기 위해 소프트웨어 생명주기(SDLC) 전 과정에 걸쳐 필요한 작업 절차, 단계별 활동, 표준 산출물, 모델링 표기법 및 품질 관리 기법을 체계적으로 정립한 공학적 방법론.
- **배경 및 필요성** : 개발자의 개인적 경험과 주관에 의존하던 원시적 코딩 방식에서 벗어나, 시스템의 규모 확대와 비즈니스 복잡성을 효과적으로 관리하기 위해 패러다임 진화.
- **4대 주요 발전 단계** : 구조적 방법론 -> 정보공학 방법론 -> 객체지향 방법론 -> 컴포넌트 기반 방법론(CBD).

## Ⅱ. 4대 개발방법론의 구조적 발전 계보

```text
   [ 구조적 방법론 (1970s) ] ──── 프로세스 중심의 하향식 기능 분해 (DFD, DD, Mini-Spec)
              │
              ▼
   [ 정보공학 방법론 (1980s) ] ── 데이터 중심의 전사적 통합 모델링 (ISP -> BAA -> BSD -> SC)
              │
              ▼
   [ 객체지향 방법론 (1990s) ] ── 데이터와 프로세스의 결합 (UML, 클래스, 상속/다형성)
              │
              ▼
   [ CBD 방법론 (2000s) ] ─────── 독립 패키징된 소프트웨어 부품의 레고 블록식 조립 재사용
```

## Ⅲ. 4대 소프트웨어 개발방법론 특성 비교

| 비교 항목 | 구조적 방법론 | 정보공학 방법론 | 객체지향 방법론 | CBD 방법론 |
|---|---|---|---|---|
| 중심 관점 | 프로세스(기능) 중심 | 데이터(정보) 중심 | 객체(데이터 + 행위) | 컴포넌트(인터페이스) |
| 설계 방식 | 하향식 기능 분해 (Top-Down) | 전사 데이터 주도 공학 | 상향식/하향식 조화 | 재사용 기반 조립(Assembly) |
| 핵심 모델링 도구 | DFD, 자료사전(DD), 소단위명세서 | ISP, ERD, CRUD 매트릭스 | UML 14종 다이어그램 | 컴포넌트 명세서, 인터페이스 |
| 재사용 단위 | 함수, 서브루틴 | 전사 공통 데이터 모델 | 클래스, 객체 | 바이너리 컴포넌트 (.jar/.dll) |
| 장점 | 절차가 직관적이고 단순함 | 전사 비즈니스 전략과 밀접 결합 | 캡슐화, 변경 유연성, 확장성 | 개발 기간 단축, 고품질 검증 부품 |
| 한계 | 유지보수 취약, 데이터 중복 | 대규모 초기 비용, 복잡성 | 설계 학습 곡선, 런타임 오버헤드 | 상용 컴포넌트 유통 시장 부족 |

## Ⅳ. SW 개발방법론의 주요 한계점 및 해결 방안

- **특정 방법론의 획일적 강제로 인한 프로젝트 유연성 저하** :
  - **한계점** : 프로젝트의 도메인 특성, 기술 스택, 팀 성숙도를 무시하고 표준 프레임워크나 워터폴/애자일을 교조적으로 강제하여 생산성 저하.
  - **해결 방안** : 프로젝트 규모, 요구사항 변동성, 안전성 수준에 따른 체계적인 테일러링(Tailoring) 가이드라인 수립 및 테일러링 승인 프로세스 운영.
- **방법론 산출물 작성 중심의 '문서주의(Document-Driven)' 매몰** :
  - **한계점** : 실제 동작하는 소프트웨어의 품질보다 감리 및 검수 통과용 형식적 문서(설계서, 테스트 결과서) 작성에 개발 공수가 낭비됨.
  - **해결 방안** : Docs-as-Code(Markdown, OpenAPI, PlantUML) 도입으로 코드와 산출물 일원화, 자동화된 문서 빌드 및 CI 배포 파이프라인 연계.
- **클라우드 네이티브 및 AI 시대 신기술 패러다임 수용 지연** :
  - **한계점** : 전통적 방법론(구조적, 정보공학, CBD)은 컨테이너 배포, 마이크로서비스, MLOps 데이터 수명주기 등 최신 엔지니어링 특성을 수용 불가.
  - **해결 방안** : 마이크로서비스 및 지속적 배포에 특화된 DevOps/DevSecOps 방법론 융합, 데이터 파이프라인 특화 DataOps 방법론으로 지속적 진화.

## Ⅴ. 현대 애자일·클라우드 환경에서의 기술사적 제언

- **도메인 주도 설계(DDD)와 현대적 방법론의 융합** : 과거 폭포수 기반의 정보공학이나 CBD의 무거운 관료주의를 탈피하고, 비즈니스 전문가와 개발자가 유비쿼터스 언어를 공유하며 바운디드 컨텍스트를 도출하는 도메인 주도 설계(DDD)를 애자일 스크럼과 결합해야 함.
- **도구 및 언어의 융복합(Polyglot) 거버넌스 수립** : 단 하나의 개발방법론만을 전사 표준으로 강제하지 말고, 시스템의 성격(대규모 코어 트랜잭션 vs 빠른 고객 접점 웹)에 따라 객체지향, 함수형 프로그래밍, 이벤트 주도 아키텍처를 유연하게 테일러링하는 하이브리드 거버넌스 체계 구축.
