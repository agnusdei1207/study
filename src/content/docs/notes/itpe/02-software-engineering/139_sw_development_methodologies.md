소프트웨어 공학 → 소프트웨어 개발·운영 → SW 개발방법론 비교

## 지식 위치

소프트웨어공학 > 개발 프로세스·방법론 > SW 개발방법론 비교

## 30초 인출

- 본질: 소프트웨어 생명주기 전반에 걸쳐 고품질 소프트웨어를 효율적으로 생산하기 위해 작업 절차, 모델링 기법, 산출물 표준 및 관리 도구를 체계화한 공학적 개발 체계
- 메커니즘: 프로세스 중심(구조적) → 데이터 중심(정보공학) → 객체/책임 중심(객체지향) → 부품 조립/인터페이스 중심(CBD)으로 추상화 단위 발전
- 통찰: 특정 방법론의 형식적 산출물 맹신은 개발 오버헤드를 유발하므로 비즈니스 도메인 복잡도, 변경 주기, 컴포넌트 재사용성에 기반한 최적 방법론 테일러링 수행 필요

<details>
<summary>핵심 용어</summary>

- **구조적 방법론 (Structured Methodology)** : 기능을 하향식(Top-Down)으로 분해하고 자료 흐름(DFD)을 중심으로 처리 절차를 모델링하는 방법론
- **정보공학 방법론 (Information Engineering)** : 기업의 정보 전략을 기초로 데이터 구조(ERD)를 선행 모델링하고 업무 프로세스를 결합하는 데이터 중심 방법론
- **객체지향 방법론 (Object-Oriented Methodology)** : 데이터(속성)와 처리 로직(메서드)을 하나로 캡슐화한 객체들의 상호작용 및 책임을 중심으로 시스템을 구축하는 방법론
- **CBD 방법론 (Component-Based Development)** : 표준화된 인터페이스를 갖춘 독립적 소프트웨어 컴포넌트들을 조립하여 애플리케이션을 완성하는 부품 기반 방법론
- **DFD / ERD / UML** : 구조적의 자료흐름도(DFD), 정보공학의 개체관계도(ERD), 객체지향의 통합모델링언어(UML)
</details>

## 2~4교시 예상문제 (25점)

> 전통적인 소프트웨어 개발방법론(구조적, 정보공학, 객체지향, CBD)의 발전 패러다임과 핵심 모델링 관점을 비교하고, 프로젝트 특성에 따른 방법론 선정 기준 및 현대적 테일러링(Tailoring) 방안을 제시하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 소프트웨어 개발 전 과정에 걸쳐 프로젝트를 체계적으로 계획, 분석, 설계, 구현, 테스트, 유지보수하기 위한 표준화된 작업 절차, 모델링 표기법, 산출물 양식의 종합 프레임워크 |
| 목적 | 개발 생산성 및 소프트웨어 품질 향상, 프로젝트 가시성 확보, 유지보수성 극대화 및 납기 지연/비용 초과 위험 통제 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 패러다임의 진화 | 기능 분해(구조적)에서 데이터 중심(정보공학), 실세계 모델링(객체지향), 아키텍처 부품화(CBD)로 추상화 계층 고도화 |
| 모델링 관점의 분리 | 제어 흐름(Control), 데이터 모델(Data), 기능적 변환(Function) 중 어디에 초점을 맞추는지에 따라 표기법 차별화 |
| 산출물 추적성 보장 | 사용자 요구사항 명세서부터 분석 모델, 설계 모델, 소스코드, 테스트 케이스 간의 양방향 추적성(Traceability) 확립 |
| 테일러링 유연성 | 프로젝트의 규모, 예산, 팀 역량, 도메인 규제 요건에 맞추어 산출물과 공정을 가감 조정 가능 |

비즈니스 환경의 복잡성과 기술 발전에 발맞추어 개발 생산성과 소프트웨어 재사용성을 극대화하는 방향으로 진화.

## Ⅲ. 체계·프로세스

```text
[개발방법론 패러다임 진화 체계]
  ┌────────────────────────────────────────────────────────┐
  │ 1. 구조적 방법론 (1970s) : 기능 중심 (하향식 분해)      │
  │    - DFD(자료흐름도), DD(자료사전), Mini-Spec(소단위명세)│
  └──────────────────────────┬─────────────────────────────┘
                             │ 데이터와 프로세스의 분리로 유지보수 한계
                             ▼
  ┌────────────────────────────────────────────────────────┐
  │ 2. 정보공학 방법론 (1980s) : 데이터 중심 (기업 정보 체계)│
  │    - ISP 수립, ERD 모델링, CRUD 매트릭스, 4GL 도구     │
  └──────────────────────────┬─────────────────────────────┘
                             │ 업무 로직 변경 시 데이터 정합성 유지 난관
                             ▼
  ┌────────────────────────────────────────────────────────┐
  │ 3. 객체지향 방법론 (1990s) : 데이터+행위 캡슐화 (객체) │
  │    - 유스케이스 다이어그램, 클래스 다이어그램, UML 표기 │
  └──────────────────────────┬─────────────────────────────┘
                             │ 대규모 바이너리 재사용 및 배포 단위 제약
                             ▼
  ┌────────────────────────────────────────────────────────┐
  │ 4. CBD 방법론 (2000s) : 인터페이스 기반 부품 조립       │
  │    - 컴포넌트 저장소(Repository), 제공/요구 인터페이스   │
  └────────────────────────────────────────────────────────┘
```

단순 프로세스 처리 절차에서 대규모 정보 모델링, 객체 간 메시지 협력, 독립 배포 가능한 컴포넌트 아키텍처로 진화하는 체계.

## Ⅳ. 종류·비교

| 비교 항목 | 구조적 방법론 | 정보공학 방법론 | 객체지향 방법론 | CBD 방법론 |
|---|---|---|---|---|
| **핵심 철학** | 기능 및 프로세스 분해 | 기업 데이터 구조 중심 | 상태(데이터)와 행위의 결합 | 규격화된 부품(컴포넌트) 조립 |
| **추상화 단위** | 모듈, 함수 (Function) | 엔티티 (Entity) | 객체, 클래스 (Class) | 컴포넌트 (Component) |
| **설계 방식** | 하향식 (Top-Down) 분해 | 데이터 모델 선행 후 기능 매핑 | 상향식 및 하향식 융합 | 인터페이스 기반 계약 및 조립 |
| **대표 산출물** | DFD, DD, 소단위명세서 | ISP 보고서, ERD, CRUD 매트릭스 | 유스케이스, 클래스도, 시퀀스도 | 컴포넌트 명세서, 인터페이스 정의서 |
| **재사용 수준** | 소스 코드 함수 단위 (낮음) | 데이터베이스 스키마 재활용 | 클래스 상속 및 다형성 (중간) | 바이너리 단위 블랙박스 조립 (높음) |
| **주요 한계점** | 데이터와 기능의 분리로 변경 취약 | 개발 기간 장기화, 폭포수 종속 | 객체 설계 난이도 높음, 학습 곡선 | 부품 간 인터페이스 불일치, 관리 비용 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 프로젝트의 성격과 규모를 무시한 획일적 방법론 적용으로 불필요한 형식적 문서 양산 | 프로젝트 규모, 팀 숙련도, 기술 복잡도를 평가하여 필수 산출물만 정의하는 방법론 테일러링 수행 |
| 설계 모델 산출물과 실제 구현 소스코드 간의 지속적 불일치(Drift) 발생 | MDA(Model Driven Architecture) 도구 도입 및 UML 모델-코드 간 양방향 동기화 도구 활용 |
| 전통적 중량(Heavyweight) 방법론의 경직된 절차로 인한 급변하는 비즈니스 요구 수용 불가 | 객체지향/CBD 기반 아키텍처 위에 애자일(Scrum/Kanban) 프로세스를 결합한 하이브리드 방법론 적용 |

## Ⅵ. 제언

현대 소프트웨어 개발은 전통적 방법론의 아키텍처적 견고함과 애자일/DevOps의 기민함을 융합한 도메인 주도 설계(DDD) 및 마이크로서비스 아키텍처 기반의 적응형 개발 체계 정착 필요.

```text
[현대적 엔터프라이즈 방법론 융합 체계]
  도메인 분석 (DDD / 이벤트스토밍) → 서비스 설계 (API/OAS 계약) → 개발/배포 (애자일 스프린트 + CI/CD 자동화)
```

| 검증 단계 | 전통적 개발방법론 | 현대적 애자일/클라우드 방법론 |
|---|---|---|
| 통제 중심 | 산출물 승인 및 엄격한 단계별 이행 게이트 | 작동하는 소프트웨어 및 짧은 피드백 주기 |
| 재사용 방식 | 사내 소스 코드 및 클래스 라이브러리 | OCI 컨테이너, 클라우드 SaaS, 오픈소스 컴포넌트 |
