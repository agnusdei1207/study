## 30초 인출

- 본질: **소프트웨어 개발방법론**은 개발 활동·기법·산출물을 조직하는 방식으로, 구조적·정보공학·객체지향·컴포넌트 기반 개발이 서로 다른 모델링 초점을 둠
- 메커니즘: 요구와 제약 파악 → 적합한 모델링 관점·생명주기 선택 → 산출물 작성 → 프로젝트 규모와 위험에 맞게 조정
- 핵심 구분: 기능 흐름(구조적) · 전사 데이터(정보공학) · 객체와 협력(객체지향) · 인터페이스 기반 재사용(CBD)

<details>
<summary>핵심 용어</summary>

- **구조적 방법론(Structured Methodology)**: 기능을 단계적으로 분해하고 자료 흐름을 모델링하는 방법론
- **정보공학(Information Engineering)**: 정보 요구와 데이터 구조를 중심으로 기업 시스템을 분석·설계하는 접근
- **객체지향(Object-Oriented) 방법론**: 상태와 행위를 가진 객체의 협력으로 시스템을 모델링하는 접근
- **CBD(Component-Based Development)**: 명확한 인터페이스를 가진 소프트웨어 구성요소를 조립·재사용하는 개발 접근
- **DFD(Data Flow Diagram)**: 프로세스 간 자료의 입력·변환·출력을 나타내는 자료 흐름도
- **ERD(Entity-Relationship Diagram)**: 데이터 개체와 관계를 표현하는 개체 관계도
- **UML(Unified Modeling Language)**: 소프트웨어 구조·행동을 표기하는 모델링 언어
- **CRUD(Create, Read, Update, Delete)**: 데이터 생성·조회·수정·삭제 기본 작업
- **DD(Data Dictionary)**: 데이터 흐름·자료 항목의 이름과 의미를 정의한 자료 사전
</details>

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 개발방법론**은 개발 활동·기법·산출물을 조직하는 방식이며, 방법론별 모델링 초점이 다름 |
| 목적 | 프로젝트 요구와 제약에 맞는 접근을 선택하고 산출물을 일관되게 관리 |

### 4대 개발방법론 핵심 비교

| 비교축 | 구조적 방법론 | 정보공학 방법론 | 객체지향 방법론 | CBD 방법론 |
|---|---|---|---|---|
| **핵심 추상화 중심** | **기능 및 프로세스 (Function)** | **전사 데이터 (Data)** | **객체와 책임 (Object)** | **독립 실행 부품 (Component)** |
| **접근 방식** | 기능 분해와 자료 흐름 분석 | 데이터 구조와 업무 기능 연계 | 객체의 책임·협력 모델링 | 계약 기반 부품 선택·조립 |
| **대표 산출물** | DFD, 자료사전(DD), 소단위명세서 | 주제영역도, ERD, CRUD 매트릭스 | 유스케이스, 클래스도, 시퀀스도 | 컴포넌트 명세서, 인터페이스 정의서 |
| **중점 판단** | 기능 간 입력·출력·변환 | 데이터 정의와 업무 간 일관성 | 책임 배분과 결합도 | 인터페이스·버전·의존성 호환 |

## Ⅱ. 방법론별 초점

### 4대 방법론 추상화 중심축 및 모델링 체계

```text
소프트웨어 개발방법론의 관점
    ├─ 구조적: 기능·자료 흐름
    ├─ 정보공학: 데이터·정보 구조
    ├─ 객체지향: 객체·협력
    └─ CBD: 인터페이스·구성요소 재사용
```

### 요구와 모델링 대상에 따른 방법론 선택

```text
프로젝트 요구·제약
    ↓ 핵심 모델링 대상 확인
    ├─ 기능 흐름 → 구조적
    ├─ 데이터 구조 → 정보공학
    ├─ 객체 협력 → 객체지향
    └─ 재사용 부품 → CBD
```

### 프로젝트 특성에 따른 선택 기준

| 프로젝트 조건 | 고려할 접근 |
|---|---|
| 데이터 구조·정보 요구의 일관성이 중심 | 정보공학의 데이터 모델 중심 분석 |
| 복잡한 도메인 규칙과 객체 간 협력이 중심 | 객체지향 분석·설계 |
| 기능 분해와 자료 흐름이 명확 | 구조적 분석·설계 |
| 검증된 구성요소를 인터페이스로 조립·재사용 | CBD |

## Ⅲ. 적용상 한계와 조정

| 고려사항 | 대응 |
|---|---|
| 프로젝트 규모보다 많은 산출물 | 필수·선택 산출물을 위험과 규모에 맞춰 조정 |
| 모델과 구현의 괴리 | 리뷰와 추적으로 요구·모델·코드의 연결 확인 |
| 재사용 구성요소의 인터페이스 불일치 | 인터페이스 계약을 검증하고 필요한 어댑터를 설계 |

## Ⅳ. 산출물 연계와 변경 추적

요구사항에서 모델, 구현, 시험으로 이어지는 산출물 연결을 변경 영향 분석에 활용하는 추적 기준. 연결 단위는 프로젝트의 검증 요구와 위험에 맞춰 설정.

| 추적 대상 | 확인 내용 |
|---|---|
| 요구사항 ↔ 모델 | 설계 요소가 요구를 반영하는지 확인 |
| 모델 ↔ 구현 | 구현이 설계 책임과 인터페이스를 따르는지 확인 |
| 요구사항 ↔ 시험 | 요구가 검증 가능한 시험으로 이어지는지 확인 |

## Ⅴ. 기술사적 제언

```text
프로젝트의 핵심 모델링 대상 확인
             ↓
기능·데이터·객체·부품 관점 선택
             ↓
필수 산출물 선정 → 요구·모델·시험 연결
```

**제언:** 방법론의 이름보다 프로젝트가 검증해야 할 설계 대상과 산출물의 연결을 우선.
