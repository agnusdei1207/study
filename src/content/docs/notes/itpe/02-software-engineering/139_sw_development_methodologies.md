## 연관 키워드

- SW 개발방법론, 구조적 방법론, 정보공학 방법론, 객체지향 방법론, CBD(Component-Based Development) 방법론
- DFD(Data Flow Diagram), UML(Unified Modeling Language), 테일러링(Tailoring), Docs-as-Code, 도메인 주도 설계(DDD, Domain-Driven Design)

## Ⅰ. SW 개발방법론의 발전 개요

- 핵심 요약 : 생명주기 전반의 절차, 산출물, 기법을 체계화한 방법론이 프로세스, 데이터, 객체, 컴포넌트 중심으로 진화한 계보.
- 개념 : 소프트웨어 생명주기(SDLC, Software Development Life Cycle) 전 과정의 작업 절차, 단계별 활동, 표준 산출물, 모델링 표기법을 정립한 **SW 개발방법론** (Software Development Methodology).
- 배경 및 필요성 : 개인의 경험에 의존하던 개발 방식으로는 시스템 규모와 업무 복잡성을 관리하기 어려워, 체계적인 방법론이 요구됨.
- 4대 발전 단계 : 구조적 방법론, 정보공학 방법론, 객체지향 방법론, **CBD 방법론** (Component-Based Development, 컴포넌트 기반 개발).
- 주요 목적 : 프로젝트 품질, 생산성, 유지보수성을 표준 절차로 확보.

## Ⅱ. SW 개발방법론의 특징 및 장점

- 핵심 요약 : 방법론마다 중심 관점과 재사용 단위가 다르며, 이 차이를 프로젝트 특성에 맞게 조정하는 **테일러링**(Tailoring)이 적용 성패를 좌우.

1. 구조적 방법론 : 프로세스 중심의 하향식 기능 분해 → 절차가 직관적이어서 소규모 업무 시스템 분석에 유리.
2. 정보공학 방법론 : 데이터 중심의 전사 통합 모델링 → 비즈니스 전략과 정보 체계의 일관성 확보.
3. 객체지향 방법론 : 데이터와 행위를 객체로 묶어 캡슐화, 상속, 다형성을 활용 → 변경 범위가 줄고 확장이 쉬움.
4. CBD 방법론 : 독립 패키징된 컴포넌트를 조립하고 재사용 → 개발 기간 단축과 검증된 부품 활용.
5. 계보적 누적 : 방법론은 서로를 대체하기보다 이전 관점을 이어받아 발전 → 기존 자산과 기법을 함께 활용 가능.
6. 테일러링의 필요성 : 도메인, 규모, 안전성 수준에 따라 방법론 절차를 줄이거나 보강 → 과잉 절차에 따른 공수 낭비 방지.

## Ⅲ. SW 개발방법론의 구조 (흐름)

- 핵심 요약 : 1970년대 구조적 방법론에서 2000년대 CBD 방법론까지 이어지는 세대별 계보와, 방법론을 프로젝트에 맞추는 테일러링 절차의 이중 구조.

```text
[ 구조적 방법론 (1970년대) ]
 - 프로세스 중심 하향식 분해
 - DFD, 자료사전, 소단위 명세
        ↓
[ 정보공학 방법론 (1980년대) ]
 - 데이터 중심 전사 통합 모델링
 - ISP → BAA → BSD → SC
        ↓
[ 객체지향 방법론 (1990년대) ]
 - 데이터와 행위의 결합
 - UML, 클래스, 상속·다형성
        ↓
[ CBD 방법론 (2000년대) ]
 - 독립 패키징 컴포넌트의 조립·재사용
```

```text
[ 1. 프로젝트 특성 분석 ]
 (규모, 요구 변동성, 안전성)
        ↓
[ 2. 방법론 후보 선정 ]
        ↓
[ 3. 테일러링 가이드라인 적용 ]
        ↓
[ 4. 테일러링 승인 ]
        ↓
[ 5. 적용 및 산출물 통제 ]
```

- 정보공학 방법론의 단계 : ISP(Information Strategy Planning)에서 BAA(Business Area Analysis), BSD(Business System Design), SC(System Construction)로 이어지는 전사 단계 체계.
- 모델링 표기 차이 : 구조적 방법론은 DFD와 자료사전, 정보공학 방법론은 ERD와 CRUD 매트릭스, 객체지향 방법론은 UML을 주로 사용.

## Ⅳ. 4대 소프트웨어 개발방법론의 비교

- 핵심 요약 : 중심 관점, 설계 방식, 재사용 단위, 장단점을 네 방법론 기준으로 비교.

| 비교 항목 | 구조적 방법론 | 정보공학 방법론 | 객체지향 방법론 | CBD 방법론 |
| --- | --- | --- | --- | --- |
| 중심 관점 | 프로세스(기능) | 데이터(정보) | 객체(데이터와 행위) | 컴포넌트(인터페이스) |
| 설계 방식 | 하향식 기능 분해 | 전사 데이터 주도 | 상향식과 하향식의 조합 | 재사용 기반 조립 |
| 주요 모델링 도구 | DFD, 자료사전, 소단위 명세 | ISP, ERD, CRUD 매트릭스 | UML 다이어그램 | 컴포넌트 명세, 인터페이스 정의 |
| 재사용 단위 | 함수, 서브루틴 | 전사 공통 데이터 모델 | 클래스, 객체 | 바이너리 컴포넌트 |
| 장점 | 절차가 직관적이고 단순함 | 전사 비즈니스 전략과 밀접 연계 | 캡슐화, 변경 유연성, 확장성 | 개발 기간 단축, 검증된 부품 재사용 |
| 한계 | 유지보수 취약, 데이터 중복 | 초기 비용과 복잡성 큼 | 설계 학습 부담, 실행 오버헤드 | 재사용 가능한 부품 확보의 어려움 |

## Ⅴ. SW 개발방법론의 한계와 대응 방안

- 핵심 요약 : 방법론의 획일적 강제, 문서 중심 과잉, 신기술 수용 지연을 테일러링, 산출물 코드화, 방법론 융합으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 획일적 강제에 따른 유연성 저하 | 도메인과 팀 성숙도를 무시한 방법론 교조 적용 → 생산성 저하 | 규모, 요구 변동성, 안전성 수준별 테일러링 가이드라인과 승인 절차 운영 | 테일러링 승인 건수, 방법론 이탈 사유 |
| 문서 중심 과잉 | 감리 통과용 문서 작성에 공수 집중 → 실제 동작하는 품질은 뒷전 | **Docs-as-Code** 도입으로 문서를 코드와 함께 형상 관리하고 CI 파이프라인에서 자동 빌드 | 문서 작성 공수 비중, 문서 최신화율 |
| 신기술 수용 지연 | 전통 방법론은 컨테이너, 마이크로서비스, MLOps 같은 최신 특성을 다루기 어려움 | DevOps와 DevSecOps 융합, 데이터 파이프라인을 위한 DataOps 적용 | 배포 주기, 변경 실패율 |

## Ⅵ. 현대 애자일·클라우드 환경에서의 기술사적 제언

- 핵심 요약 : 도메인 주도 설계와 애자일을 결합하고, 시스템 성격에 따라 방법론을 조합하는 융복합 거버넌스로 전환.

1. 도메인 주도 설계와 애자일의 결합 : 비즈니스 전문가와 개발자가 공통 언어로 **도메인 주도 설계**(DDD, Domain-Driven Design)를 수행해 경계를 나누고, 그 결과를 애자일 스크럼 주기에 반영해야 한다.
2. 시스템 성격 기반의 방법론 혼합 : 전사 표준으로 단일 방법론을 강제하기보다, 대규모 핵심 트랜잭션과 빠른 고객 접점 시스템을 구분해 객체지향, 이벤트 주도 등을 선택적으로 적용하는 방식이 현실적이다.

## Ⅶ. 결론

- 핵심 요약 : 개발방법론은 상호 대체가 아니라 누적 진화의 산물이며, 테일러링 능력이 적용 성패를 좌우.
- 시사점 : 프로젝트 특성에 맞춘 방법론 선정과 Docs-as-Code 기반의 경량 산출물 운영이 방법론 적용의 현대화 방향.
