## 지식 로드맵 내 현재 위치

지식 위치: 소프트웨어 공학 → 테스트·검증 → **화이트박스 테스트(White Box Test)**

## 30초 인출

- 본질: **화이트박스 테스트(White-box Testing)**는 소스코드의 구조와 제어 흐름을 기준으로 시험하는 구조 기반 테스트
- 메커니즘: **제어 흐름 그래프(CFG)** 도출 → 테스트 커버리지 기준 선정(구문, 결정, 조건, **MC/DC**) → 입력 케이스 생성
- 효과: 미실행 데드코드(Dead Code) 적발 · 내부 로직 오류 및 메모리 누수 격리 · 고신뢰성 안전 등급 보증

<details>
<summary>핵심 용어</summary>

- **White-box Testing**: 소스코드의 내부 구조, 루프, 조건 분기, 데이터 흐름을 직접 관찰하며 테스트 케이스를 설계하는 기법
- **CFG(Control Flow Graph)**: 프로그램의 실행 흐름을 노드(기본 블록)와 엣지(제어 이동)로 표현한 방향 그래프
- **Statement Coverage(구문 커버리지, C0)**: 소스코드의 모든 실행 가능한 문장이 최소 한 번 실행되는 비율
- **Branch/Decision Coverage(결정 커버리지, C1)**: 프로그램 내 모든 조건문의 전체 결과(True/False)가 최소 한 번씩 실행되는 비율
- **MC/DC(Modified Condition/Decision Coverage)**: 복합 조건식 내 각 개별 조건이 다른 조건과 무관하게 전체 결정 결과에 독립적인 영향을 미치는지 검증하는 기법 (항공 DO-178C Level A 표준)

</details>

## 1교시 10점 답안

### Ⅰ. 화이트박스 테스트의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **화이트박스 테스트(White-box Testing)** 는 소스코드의 구조와 제어 흐름을 기준으로 시험하는 구조 기반 테스트 |
| 목적 | 미실행 구문·분기·조건을 찾아 시험 공백을 줄임 |

### Ⅱ. 제어 흐름과 커버리지 기준

| 기준 | 확인 내용 |
|---|---|
| 구문 | 실행 가능한 문장의 실행 여부 |
| 결정·분기 | 각 결정 결과의 참·거짓 실행 여부 |
| 조건 | 복합 결정식의 각 원자 조건 참·거짓 여부 |
| MC/DC | 각 조건이 다른 조건과 독립적으로 전체 결정 결과에 영향을 주는지 여부 |

**안전성·시험 통제**

- **MC/DC 적용**: 적용 표준과 시스템 위험도에 따라 독립 조건 영향 시험 설계
- **커버리지 해석**: 수치만으로 결함 부재를 단정하지 않고 요구사항 시험과 함께 해석
- 한 줄 제언: 위험도가 높은 결정 조건부터 커버리지 기준을 정하고 결과를 시험 증거와 함께 검토

## 2~4교시 25점 답안

## Ⅰ. 내부 경로를 확인하는 화이트박스 테스트

> **화이트박스 테스트**는 코드 내부 구조를 기준으로 실행 경로와 조건을 확인하는 기법.

| 구분 | 핵심 |
|---|---|
| 정의 | **화이트박스 테스트(White-box Testing)** 는 소스코드의 구조와 제어 흐름을 기준으로 시험하는 구조 기반 테스트 |
| 목적 | 미실행 구문·분기·조건을 찾아 시험 공백을 줄임 |

## Ⅱ. 제어 흐름 커버리지의 확인 대상과 한계

> 커버리지 기준의 포함 관계를 구분하되, 높은 커버리지를 결함 부재의 증거로 오인하지 않아야 함.

### 제어 흐름 그래프(CFG)

```text
① 시작
    ↓
② 조건
    ├─ 참 → ③
    └─ 거짓 → ④
③·④ → ⑤ 합류
```

| 커버리지 유형 | 확인 대상 | 한계 |
|---|---|---|
| **구문** | 각 실행 구문의 실행 여부 | 반대 분기를 놓칠 수 있음 |
| **결정·분기** | 결정 결과의 참·거짓 | 복합식 내부 조건의 영향은 알 수 없음 |
| **조건** | 각 원자 조건의 참·거짓 | 결정 결과의 참·거짓을 모두 보장하지 않음 |
| **조건/결정** | 조건과 결정의 참·거짓 | 조건별 독립 영향은 보장하지 않음 |
| **다중 조건(MCC)** | 가능한 조건 조합 | 조건 수가 늘면 조합 급증 |
| **MC/DC** | 각 조건이 결정 결과를 독립적으로 바꾸는지 | 조건 결합에 따라 설계가 복잡해짐 |

## Ⅲ. MC/DC 테스트 케이스 도출 원리: `(A OR B) AND C`

> MC/DC는 각 원자 조건이 결정 결과에 독립적으로 영향을 줌을 보이며, 최소 N+1 사례가 가능한 경우에도 식 구조·결합 조건에 따라 추가 사례가 필요함.

`Result = (A OR B) AND C`를 사례로 들면 다음 네 케이스의 쌍에서 조건 하나만 바꾸었을 때 결정 결과가 달라진다.

| 케이스 | A | B | C | 결과 | 독립 영향 검증 |
|---|---|---|---|---|---|
| 1 | 참 | 거짓 | 참 | 참 | 1↔2: A, 1↔4: C |
| 2 | 거짓 | 거짓 | 참 | 거짓 | 2↔3: B |
| 3 | 거짓 | 참 | 참 | 참 | 2↔3: B |
| 4 | 참 | 거짓 | 거짓 | 거짓 | 1↔4: C |

## Ⅳ. 화이트박스 테스트 한계·대응책

> 단위 테스트와 분석 도구를 CI/CD에 연계해 실행 경로·조건 커버리지를 지속 측정.

### 화이트박스 도구 분류

| 도구 분류 | 대표 도구 | 주 검증 내용 |
|---|---|---|
| **코드 커버리지 분석** | JaCoCo, Cobertura, Istanbul | 구문(C0), 브랜치(C1) 커버리지 백분율 측정 |
| **정적 코드 분석** | SonarQube, Fortify, Coverity | 코딩 표준 준수, 널 참조, 잠재적 런타임 오류, 보안 취약점 |
| **기능안전 전문 도구** | VectorCAST, LDRA, Cantata | 임베디드 대상 MC/DC 커버리지 자동 측정 및 리포팅 |

### 실무 위험 및 거버넌스 대책

| 위험 | 대책 | 효과 |
|---|---|---|
| **구문 커버리지 편중** | 위험한 결정·분기와 예외 경로도 테스트 | 미실행 경로 식별 |
| **복합 조건 조합 증가** | 시스템 위험도와 적용 기준에 따라 MC/DC 등의 조건 테스트 설계 | 중요한 조건의 영향 확인 |
| **테스트 코드 유지보수 부채** | 내부 구현 종속적 테스트 지양, 행위 기반 검증 및 Mocking 최소화 | 리팩토링 시 테스트 깨짐 방지 및 유지보수성 향상 |

## Ⅴ. 구조·명세 시험을 결합하는 제언

> 커버리지는 실행 여부의 지표이지 무결함의 증거가 아님. 요구사항 기반 시험과 함께 해석.

| 한계 | 해결 방안 |
|---|---|
| 안전·보안·금전 영향이 큰 코드에 시험 자원을 우선 배치하기 어려움 | 영향이 큰 요구사항의 기대 결과와 구조 기반 경로 증거를 함께 추적하고 커버리지 수치와 결함 부재를 동일시하지 않음 |
