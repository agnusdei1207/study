## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 테스트·검증 → **화이트박스 테스트(White Box Test)**

## 30초 인출

- 본질: 화이트박스 테스트(White-box Testing)는 소스코드의 내부 논리 구조, 제어 흐름, 데이터 흐름을 직접 분석하여 시험 경로를 도출하는 구조 기반 검증 기법
- 메커니즘: 제어 흐름 그래프(CFG) 모델링 → 커버리지 기준(구문, 분기, 조건, MC/DC) 선정 → 분기 및 경로 실행 테스트 케이스 설계 및 수행
- 통찰: 높은 구문 커버리지 달성에도 미실행 분기나 복합 조건의 결함이 잔존하므로 시스템 위험도 등급(ASIL, DAL)에 따른 MC/DC 적용과 블랙박스 상호 보완

<details>
<summary>핵심 용어</summary>

- **화이트박스 테스트(White-box Testing)** : 프로그램의 내부 제어 구조, 경로, 조건식, 루프를 직접 관찰하며 테스트 케이스를 설계하는 구조적 테스트
- **CFG(Control Flow Graph)** : 코드의 실행 순서와 분기를 노드(기본 블록)와 엣지(제어 이동)로 추상화한 방향성 제어 흐름 그래프
- **Statement Coverage(구문 커버리지, C0)** : 소스코드 내의 모든 실행 가능한 문장이 최소 한 번 이상 실행된 비율
- **Branch/Decision Coverage(결정 커버리지, C1)** : 조건문의 전체 판정 결과인 참(True)과 거짓(False) 분기가 최소 한 번씩 실행된 비율
- **MC/DC(Modified Condition/Decision Coverage)** : 복합 조건식 내 각 개별 조건이 다른 조건의 영향 없이 독립적으로 전체 판정 결과를 변경함을 입증하는 커버리지
- **McCabe Cyclomatic Complexity(순환 복잡도)** : CFG 기반으로 선형 독립 경로의 수를 계산하여 최소 요구 테스트 케이스 수를 정의하는 복잡도 지표(V(G) = E - N + 2P)

## 2~4교시 25점 답안

## Ⅰ. 화이트박스 테스트의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **화이트박스 테스트(White-box Testing)** 는 소스코드의 내부 논리 구조와 제어 흐름 경로를 기반으로 테스트 케이스를 설계하고 검증하는 구조 기반 시험 |
| 목적 | 미실행 구문·분기 및 숨겨진 경로 결함 식별, 내부 로직 무결성 검증 및 코드 실행 커버리지 확보 |

## Ⅱ. 화이트박스 테스트의 핵심 특징

| 특징 | 의미 |
|---|---|
| 내부 구조 투명성 | 프로그램의 제어 흐름, 데이터 흐름, 알고리즘 구현의 세부 동작을 직접 검증 |
| 객관적 측정성 | 구문(C0), 결정(C1), MC/DC 등 정량화된 수치로 테스트 완료 기준(Exit Criteria) 수립 가능 |
| 구현 수준 결함 발견 | 메모리 누수, 무한 루프, 미도달 코드(Dead Code), 경계 조건 오류를 단위 단계에서 조기 식별 |

## Ⅲ. 제어 흐름 그래프와 커버리지 측정 구조

### 제어 흐름 그래프(CFG) 및 경로 분석

```text
① [시작: 변수 초기화]
        ↓
② [조건 판정: x > 0 && y > 0]
       ├─ 참 ──→ ③ [연산 블록 A]
       └─ 거짓 ─→ ④ [연산 블록 B]
        │         │
        └────┬────┘
             ▼
⑤ [종료 및 결과 반환]
```

### 결정 커버리지(C1) 시험 경로 실행

```text
조건 판정 노드 ②
    ├─ 참(True) 분기 경로: ① → ② → ③ → ⑤ (테스트 케이스 1)
    └─ 거짓(False) 분기 경로: ① → ② → ④ → ⑤ (테스트 케이스 2)
    ↓
모든 분기 결과 1회 이상 실행으로 결정 커버리지 100% 달성
```

| 커버리지 지표 | 정의 및 판정 기준 | 필요 테스트 케이스 수 | 특징 및 한계 |
|---|---|---|---|
| 구문 커버리지 (C0) | 모든 실행 문장을 최소 1회 이상 실행 | 최소 수준 (가장 적음) | 실행되지 않는 분기(else문 누락 등) 검출 불가 |
| 결정 커버리지 (C1) | 모든 조건문의 참/거짓 분기를 최소 1회 실행 | 구문 커버리지보다 큼 | 복합 조건문 내부의 개별 조건식 영향 확인 불가 |
| 조건 커버리지 (C2) | 각 개별 조건식의 참/거짓을 최소 1회 실행 | 분기 결과와 무관할 수 있음 | 결정 결과 전체의 참/거짓을 보장하지 못함 |
| 조건/결정 커버리지 | 개별 조건과 전체 결정의 참/거짓 동시 만족 | 보통 수준 | 개별 조건의 독립적 결과 변환 영향 미입증 |
| MC/DC | 각 조건이 다른 조건과 무관하게 독립적으로 결과 변경 | N + 1 개 (선형적 증가) | 다중 조건의 지수적 폭발을 방지하며 고신뢰성 검증 |
| 다중 조건 커버리지 | 복합 조건식 내 모든 가능한 진리표 조합 실행 | 2^N 개 (지수적 폭발) | 조건 수 증가 시 실무적 테스트 실행 불가능 |

## Ⅳ. MC/DC(Modified Condition/Decision Coverage) 도출 사례

복합 조건식 `Result = (A OR B) AND C`에 대한 MC/DC 테스트 케이스 도출 (조건 수 N = 3, 요구 케이스 수 = 4개)

| 케이스 ID | 조건 A | 조건 B | 조건 C | 최종 Result | 독립적 영향 입증 페어 |
|---|---|---|---|---|---|
| TC 1 | 참(T) | 거짓(F) | 참(T) | **참(T)** | TC 1 ↔ TC 2 (조건 A 영향 검증) |
| TC 2 | 거짓(F) | 거짓(F) | 참(T) | **거짓(F)** | TC 2 ↔ TC 3 (조건 B 영향 검증) |
| TC 3 | 거짓(F) | 참(T) | 참(T) | **참(T)** | TC 2 ↔ TC 3 (조건 B 영향 검증) |
| TC 4 | 참(T) | 거짓(F) | 거짓(F) | **거짓(F)** | TC 1 ↔ TC 4 (조건 C 영향 검증) |

- A 검증: TC 1과 TC 2 비교 시 B와 C는 고정되고 A의 변화(T→F)에 의해 결과가 T→F로 독립 변경됨
- B 검증: TC 3과 TC 2 비교 시 A와 C는 고정되고 B의 변화(T→F)에 의해 결과가 T→F로 독립 변경됨
- C 검증: TC 1과 TC 4 비교 시 A와 B는 고정되고 C의 변화(T→F)에 의해 결과가 T→F로 독립 변경됨

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 구문 커버리지 100% 달성 시에도 미구현된 요구사항 자체를 검출 불가 | 요구사항 기반의 블랙박스 테스트 및 **RTM(Requirements Traceability Matrix)** 상호 병행 |
| 복합 조건식 수 증가 시 MC/DC 테스트 케이스 수작업 설계의 오류 및 과다 비용 | 정적/동적 분석 자동화 도구(VectorCAST, LDRA)를 연계한 케이스 자동 생성 |
| 내부 구현 디테일에 결합된 단위 테스트 작성 시 리팩토링마다 테스트 파손 | 상태 및 공개 인터페이스 기반의 행위 검증과 적절한 테스트 더블(Mock) 사용 |

## Ⅵ. 제언

소프트웨어 안전성 등급(Safety Integrity Level)에 따른 차등적 커버리지 게이트웨이 구축 및 CI 연계

### 위험도 등급 기반 화이트박스 커버리지 기준 선정 체계

```text
시스템 기능 안전성 및 위험도 분석 (ISO 26262 ASIL / DO-178C DAL)
    ↓
위험도 등급 판정
    ├─ 최고 안전 등급 (ASIL-D / DAL-A) → MC/DC 100% 의무 적용
    ├─ 중간 안전 등급 (ASIL-B, C / DAL-B, C) → 결정 커버리지(C1) 100% 의무 적용
    └─ 일반 비즈니스 시스템 → 구문(C0) 80% + 핵심 로직 결정(C1) 적용
    ↓
CI 파이프라인 내 커버리지 게이트웨이(Quality Gate) 자동 검증
```

### CI/CD 파이프라인 내 화이트박스 자동화 검증 흐름

```text
개발자 PR 생성
    ↓
자동 빌드 및 단위 테스트 수행 (JUnit / pytest)
    ↓
커버리지 분석 엔진 (JaCoCo) 실행
    ↓
품질 게이트 검증
    ├─ 기준치 미달 (예: C1 < 80%) → 빌드 실패 및 머지 자동 차단
    └─ 기준치 충족 → 정적 보안 분석(SAST) 후 머지 승인
```

### 선택 근거: 단일 구문 커버리지와 위험도 기반 차등 커버리지 비교

| 구분 | 획일적 구문 커버리지 (C0 80%) | 제언: 위험도 기반 차등 커버리지 체계 |
|---|---|---|
| 결함 예방력 | 복합 분기 누락으로 치명적 런타임 오류 방치 | 핵심 안전 로직에 대한 완벽한 분기·독립 조건 검증 |
| 비용 효율성 | 비핵심 단순 코드에 불필요한 테스트 작성 강제 | 위험도 비례 투자로 엔지니어링 리소스 최적화 |
| 규제 준수성 | 기능안전 국제 표준 심사 통과 불가 | ISO 26262, IEC 62304 등 글로벌 인증 완벽 대응 |
