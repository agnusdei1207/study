## 연관 키워드

- 화이트박스 테스트(White Box Test), 구조 기반 테스트(Structure-based Testing), 코드 커버리지(Code Coverage)
- 제어 흐름 그래프(CFG, Control Flow Graph), MC/DC(Modified Condition/Decision Coverage), Test Double

## Ⅰ. 화이트박스 테스트의 개요

- 핵심 요약 : 내부 소스코드의 구조와 논리 경로를 직접 분석해 커버리지로 검증하는 테스트 기법.
- 개념 : 소스코드의 내부 구조, 논리 경로, 제어 흐름과 데이터 흐름을 직접 분석해 논리적 정확성을 검증하는 **화이트박스 테스트** (White Box Test). 구조를 기준으로 한다는 뜻에서 **구조 기반 테스트** (Structure-based Testing)라고도 함.
- **코드 커버리지** (Code Coverage) : 테스트가 소스코드를 얼마나 실행했는지 나타내는 비율 지표로, 테스트 충분성을 판단하는 객관적 근거.
- 배경 및 필요성 : 블랙박스 테스트로는 찾기 어려운 미실행 코드(Dead Code), 숨은 논리 오류, 메모리 누수, 예외 분기 누락을 조기에 찾아야 하는 요구.
- 주요 검증 도구 : JUnit, JaCoCo, SonarQube, BullseyeCoverage.

## Ⅱ. 화이트박스 테스트의 특징

- 핵심 요약 : 내부 구조의 가시성과 커버리지 계측, 도구 기반 자동화가 결합된 검증 체계.

1. 제어 흐름과 데이터 흐름을 따라 논리 경로를 검증 → 실행 경로 단위로 내부 결함을 확인.
2. 구문 커버리지에서 **MC/DC** (Modified Condition/Decision Coverage)까지 강도가 단계적인 측정 체계 → 안전 등급에 맞는 기준 선택 가능.
3. JUnit, JaCoCo, SonarQube 같은 도구 기반 자동화 → 회귀 검증을 반복 실행 가능.
4. 블랙박스 테스트로 찾기 어려운 미실행 코드와 예외 분기 결함을 조기에 검출 → 수정 기회를 개발 초기에 확보.
5. 명세 기반 블랙박스 테스트와 상호 보완적으로 운용 → 기능과 구조 양면의 품질 확보.

## Ⅲ. 화이트박스 테스트의 구조 (흐름)

- 핵심 요약 : 코드의 분기 구조를 그래프로 모델링해 경로를 분석하고, 커버리지 계층을 단계적으로 강화하는 구조.
- **제어 흐름 그래프** (CFG, Control Flow Graph) : 코드의 분기와 합류를 노드와 간선으로 나타낸 그래프로, 실행 가능한 경로를 도출하는 기준.

```text
[ 노드 1 : 시작 ]
       ↓
[ 노드 2 : if (A > 0) ]
   ↓ 참            ↓ 거짓
[ 노드 3 ]      [ 노드 4 ]
   ↓                ↓
[ 노드 5 : 종료 ]
```

```text
[ 커버리지 강도 계층 ]
      ▲   다중 조건 커버리지
     ▲▲   MC/DC
    ▲▲▲   조건/결정 커버리지
   ▲▲▲▲   결정·조건 커버리지
  ▲▲▲▲▲   구문 커버리지
```

## Ⅳ. 커버리지 기법별 비교

- 핵심 요약 : 검증 강도와 필요한 케이스 수가 비례하는 커버리지 기법 체계.

| 커버리지 기법 | 핵심 조건 | 케이스 수 | 검증 강도 |
| --- | --- | --- | --- |
| 구문 커버리지 | 모든 실행 문장을 한 번 이상 실행 | 최소 | 낮음 |
| 결정·분기 커버리지 | 각 조건문의 전체 결과가 참과 거짓을 한 번 이상 가짐 | 적음 | 중간 |
| 조건 커버리지 | 개별 조건식이 참과 거짓을 한 번 이상 가짐 | 적음 | 중간 (결정 커버리지를 보장하지 않을 수 있음) |
| MC/DC | 각 개별 조건이 전체 결과에 독립적으로 영향을 준다는 것을 입증 | N+1개 | 높음 (**DO-178C** (항공 소프트웨어 인증 표준) Level A에서 요구) |
| 다중 조건 커버리지 | 개별 조건의 모든 진리표 조합 실행 | 2^N개 | 최고 (조합 폭발로 실무 적용 한계) |

## Ⅴ. 화이트박스 테스트의 장점과 한계

- 핵심 요약 : 논리 경로와 구조 결함을 검출하는 장점, 커버리지 비용·취약한 테스트·외부 입출력 종속이라는 한계.

1. 미실행 코드, 숨은 논리 오류, 예외 분기 누락을 조기에 검출.
2. 커버리지 수치로 테스트 충분성을 객관적으로 판단.
3. 도구 기반 자동화로 회귀 테스트 효율화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 고강도 커버리지의 비용 급증 | 안전 필수 시스템에서 MC/DC를 달성하려면 복합 조건식의 경로를 수작업으로 설계해야 해 공수가 급증 | 조건문의 순환 복잡도(McCabe)를 관리 기준 이하로 낮추는 리팩토링, **기호 실행** (Symbolic Execution)과 자동 테스트 생성 도구(탐색 기반 EvoSuite, 기호 실행 기반 KLEE) 활용 | 순환 복잡도, 자동 생성 케이스 비율 |
| 내부 구현에 결합된 취약한 테스트 | 비공개 메서드와 알고리즘 세부에 묶인 테스트가 무변경 리팩토링에서도 대량 실패 | 공개 API 계약과 외부에서 관측되는 상태 변화를 검증 대상으로 삼고, **BDD** (Behavior-Driven Development) 스타일의 단위 테스트 표준 수립 | 리팩토링 대비 테스트 실패율 |
| 외부 입출력 종속 | DB, 네트워크, 파일 시스템에 밀착된 코드는 단위 테스트가 어렵고 속도가 느림 | 의존성 역전 원칙(DIP, Dependency Inversion Principle)에 따라 I/O 계층을 인터페이스로 추상화하고, **Test Double** (Mock, Stub, Fake)을 주입해 격리 실행 | 테스트 실행 시간, 외부 의존 테스트 비율 |

## Ⅵ. 화이트박스 테스트 현장 적용 시 기술사적 제언

- 핵심 요약 : 커버리지 수치를 맹신하지 않고 명세 기반 테스트와 병행하며, 정적 분석과 커버리지 기준을 파이프라인 품질 게이트로 묶는 운영 원칙.

1. 커버리지 수치의 한계 인식 : 100% 구문 커버리지가 결함이 없음을 뜻하지 않으며, 구현되지 않은 요구사항은 아무리 커버리지가 높아도 찾지 못하므로 커버리지를 완료 기준이 아닌 보조 지표로 쓰고, 명세 기반 테스트와 함께 설계하는 것이 필요함.
2. 파이프라인 품질 게이트 : 단위 테스트의 커버리지 임계치와 **SAST** (Static Application Security Testing, 소스코드를 실행하지 않고 보안 약점을 검사하는 기법) 결과를 CI/CD(Continuous Integration/Continuous Delivery) 파이프라인의 품질 게이트로 묶어, 기준 미달 빌드를 자동 중단하고 기술 부채의 누적을 차단하는 것이 필요함.

## Ⅶ. 결론

- 핵심 요약 : 화이트박스 테스트는 코드 커버리지 기반으로 구조 결함을 찾아내는 핵심 수단.
- 시사점 : 커버리지 맹신을 경계하고 블랙박스 테스트와 병행하며 품질 게이트를 자동화하는 것이 실무 적용 성숙도의 핵심임.
