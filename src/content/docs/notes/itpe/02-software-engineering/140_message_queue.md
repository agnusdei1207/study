## 연관 키워드

- 메시지 큐(Message Queue), MOM(Message-Oriented Middleware), 비동기 처리(Asynchronous)
- 결합도 완화(Decoupling), 발행-구독(Publish-Subscribe), Apache Kafka, RabbitMQ, 멱등성(Idempotency), DLQ(Dead Letter Queue)

## Ⅰ. 메시지 큐(Message Queue)의 개요

- 핵심 요약 : 메시지를 큐 버퍼에 비동기로 저장·전달해 분산 시스템 사이의 데이터 교환을 신뢰성 있게 지원하는 미들웨어.
- 개념 : 생산자가 보낸 메시지를 큐(Queue) 버퍼에 저장해 소비자가 나중에 꺼내 처리하도록 하는 **메시지 지향 미들웨어** (MOM, Message-Oriented Middleware).
- 배경 및 필요성 : 서비스 간 동기식 HTTP 호출은 강하게 결합되어, 트래픽이 몰릴 때 한 서비스의 지연이나 장애가 연쇄적으로 번지는 문제가 있음.
- 3대 핵심 가치 : 비동기 처리(Asynchronous), **결합도 완화** (Decoupling, 서비스 간 직접 의존 제거), 피크 부하 흡수(Buffering).

## Ⅱ. 메시지 큐의 특징 및 장점

- 핵심 요약 : 비동기, 비결합, 부하 흡수의 가치가 점대점과 발행-구독 두 가지 패턴으로 구현되는 메시징 체계.

1. 비동기 처리 : 생산자와 소비자의 처리 시점을 분리 → 응답 대기 시간이 줄고 각자 독립적으로 처리 속도를 조절.
2. 결합도 완화 : 서비스 간 직접 호출을 큐로 대체 → 한쪽의 배포와 장애가 다른 쪽에 미치는 영향 감소.
3. 부하 흡수 : 피크 메시지를 큐에 쌓아 두고 소비자가 일정 속도로 처리 → 백엔드 시스템 보호.
4. 두 가지 패턴 지원 : 점대점(Point-to-Point) 큐와 발행-구독(Pub/Sub) 토픽을 함께 제공 → 작업 분산과 이벤트 확산 모두 처리 가능.
5. 확인 응답 기반 신뢰성 : 소비자의 ACK(Acknowledgment) 확인 후 메시지를 반영 → 처리되지 않은 메시지의 유실 방지.
6. 브로커별 재처리 기능 : 일부 브로커는 오프셋(Offset)을 되돌려 과거 메시지를 다시 처리 → 장애 복구와 데이터 재계산 지원.

## Ⅲ. 메시지 큐의 구조 (흐름)

- 핵심 요약 : 한 메시지를 한 소비자가 독점 처리하는 점대점 구조와, 한 이벤트를 여러 구독자가 복제 수신하는 발행-구독 구조.

```text
[ 1. 점대점 (Point-to-Point) ]
 [ Producer ] → [ Message Queue ]
     → [ Consumer A ] (독점 소비)
     → [ Consumer B ] (작업 분산)
```

```text
[ 2. 발행-구독 (Publish-Subscribe) ]
 [ Producer ] → [ Topic / Exchange ]
     → [ 주문 서비스 구독자 ]
     → [ 결제 서비스 구독자 ]
     → [ 알림 서비스 구독자 ]
```

- 점대점 패턴 : 큐에 저장된 메시지를 여러 워커 중 하나만 받아 처리하며, 처리가 끝나면 큐에서 제거.
- 발행-구독 패턴 : 생산자가 토픽에 발행한 메시지를 해당 토픽의 모든 구독자가 각자 받는 방식.
- 메시지 흐름 : 생산자 발행 → 브로커 저장 → 소비자 처리 → ACK 확인 → 큐 반영.

## Ⅳ. 대표 메시지 브로커의 비교

- 핵심 요약 : 브로커의 설계 철학과 메시지 보관 방식, 재처리 가능 여부, 라우팅 방식에 따라 적합 용도가 갈림.

| 비교 항목 | RabbitMQ | Apache Kafka | AWS SQS(Simple Queue Service) |
| --- | --- | --- | --- |
| 설계 철학 | AMQP(Advanced Message Queuing Protocol) 기반의 전통적 메시지 브로커 | 분산 커밋 로그 기반의 고처리량 스트리밍 플랫폼 | 클라우드 관리형 큐 서비스 |
| 메시지 보관 | 소비자가 ACK하면 큐에서 삭제 | 로그로 보관하며 보존 기간 동안 유지 | 최대 보존 기간 이후 자동 삭제 |
| 재처리 | 기본 큐 기준 소비 후 재처리 불가 | 오프셋을 되돌려 과거 이벤트 재처리 가능 | 기본 기능으로는 재처리 불가 |
| 처리 성능 | 라우팅 복잡도에 따라 처리량 제한 | 대용량 스트림 처리에 유리 | 관리형 자동 확장 |
| 라우팅 유연성 | 교환기(Exchange)와 바인딩 키 기반의 세밀한 라우팅 | 토픽과 파티션 기반의 단순 라우팅 | 표준 큐와 FIFO(First In, First Out) 큐 |
| 주 활용 분야 | 업무 작업 분산, 트랜잭션성 메시지 | 실시간 로그 수집, 이벤트 스트리밍 | 서버리스 기반 비동기 작업 처리 |

## Ⅴ. 메시지 큐의 한계와 대응 방안

- 핵심 요약 : 중복 전달, 큐 적체, 독성 메시지를 멱등 처리, 배압 제어, DLQ 격리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 메시지 중복 전달 | 네트워크 분할이나 ACK 유실 시 **At-Least-Once** 전달 특성으로 동일 메시지가 재수신 → 중복 연산 | **멱등성**(Idempotency) 구현, 메시지 고유 ID 기반 중복 검사 | 중복 처리 건수 |
| 큐 적체와 백프레셔 | 생산 속도가 소비 속도를 초과 → 브로커 자원 고갈과 전체 중단 | 소비자 수평 오토스케일링(KEDA, Kubernetes Event-driven Autoscaling), 배압(Backpressure) 제어 | 큐 적체 길이, 소비 지연 시간 |
| 독성 메시지 | 잘못된 형식의 메시지가 반복 재시도되어 후속 처리 정지 | 지수 백오프로 재시도 횟수 제한, **데드 레터 큐** (DLQ, Dead Letter Queue)로 격리 | DLQ 적재 건수 |

## Ⅵ. 고가용성 메시징 시스템을 위한 기술사적 제언

- 핵심 요약 : 적어도 한 번 전달을 전제로 소비자 멱등성을 설계하고, DLQ를 독성 메시지의 안전망으로 두는 운영 체계.

1. 소비자 멱등성은 선택이 아닌 기본 설계로 다뤄야 한다. 재연결과 재시작으로 중복 수신이 생기는 것은 불가피하므로, 개발 조직은 비즈니스 처리 전에 고유 키 검사를 거치는 계층을 공통 라이브러리로 제공해야 한다.
2. 독성 메시지 격리는 운영 조직이 맡아야 한다. 재시도 한도를 넘긴 메시지를 DLQ로 옮기고 알람을 보내며, 원인 분석 절차를 정해 두어야 큐 전체가 멈추지 않는다.

## Ⅶ. 결론

- 핵심 요약 : 메시지 큐는 분산 시스템의 비동기 처리와 결합도 완화를 담당하는 핵심 인프라이며, 멱등성과 DLQ 설계가 안정 운영의 전제.
- 시사점 : 점대점과 발행-구독 패턴, 브로커별 특성을 고려한 선정과 함께 멱등 처리와 배압 제어가 병행되어야 함.
