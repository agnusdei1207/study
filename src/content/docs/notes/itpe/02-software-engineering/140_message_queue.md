## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 아키텍처·설계 → 메시지 큐(Message Queue)

## 지식 위치

소프트웨어공학 > 분산 아키텍처·비동기 메시징 > 메시지 큐(Message Queue)

## 30초 인출

- 본질: 분산 시스템에서 송신자(Producer)와 수신자(Consumer) 간의 결합도를 낮추고 비동기 메시지 전달을 중계하는 버퍼형 미들웨어 솔루션
- 메커니즘: 송신자가 메시지 브로커의 큐/토픽에 데이터 발행(Publish) → 브로커 메모리/디스크 영속화 → 수신자가 폴링 또는 푸시 방식으로 수신(Consume) 후 ACK 응답 → 처리 실패 시 재시도 후 DLQ로 격리
- 통찰: At-Least-Once 전달 특성으로 인한 중복 메시지 소비 위험을 방지하기 위해 고유 메시지 ID 기반의 수신자 멱등성(Idempotency) 보장과 트랜잭셔널 아웃박스(Transactional Outbox) 패턴 연계 필수

<details>
<summary>핵심 용어</summary>

- **결합도 분리 (Decoupling)** : 생산자와 소비자가 서로의 물리적 위치, 네트워크 주소, 가용성 상태를 알 필요 없이 메시지 스키마만으로 통신하는 특성
- **피크 트래픽 완충 (Traffic Leveling / Buffering)** : 급격한 트래픽 유입 시 하위 DB나 서비스의 과부하 다운을 방지하기 위해 큐에 버퍼링 후 소비 속도에 맞추어 처리하는 기능
- **ACK / NACK** : 소비자가 메시지를 정상 처리했음을 브로커에 알리는 확인 응답(ACK) 및 처리 실패 통보(NACK)
- **DLQ (Dead Letter Queue)** : 처리 재시도 횟수를 초과하거나 페이로드 파싱 오류 등으로 처리 불가능한 독성 메시지(Poison Message)를 격리 보관하는 큐
- **멱등성 (Idempotency)** : 동일한 메시지가 네트워크 재전송 등으로 중복 소비되더라도 시스템의 상태 변화 결과가 1회 실행과 동일하게 유지되는 성질
- **Transactional Outbox 패턴** : 비즈니스 DB 갱신과 메시지 발행 이벤트를 단일 로컬 DB 트랜잭션 내 Outbox 테이블에 함께 커밋한 후 별도 릴레이 프로세스가 브로커로 발행하는 패턴
</details>

## 2~4교시 예상문제 (25점)

> 분산 아키텍처에서 메시지 큐(Message Queue)의 핵심 개념과 도입 효과를 설명하고, 메시지 유실 및 중복 소비 방지를 위한 신뢰성 설계 기법(ACK, DLQ, 멱등성, Transactional Outbox)을 기술하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 분산 애플리케이션 환경에서 프로세스 간 데이터를 비동기 방식으로 안전하게 교환하기 위해 메시지를 임시 저장하고 라우팅하는 미들웨어 인프라 |
| 목적 | 서비스 간 시간적/공간적 결합도 분리, 대규모 트래픽 유입에 대한 버퍼링(부하 평준화), 비동기 작업 처리를 통한 응답 시간 단축 및 시스템 탄력성(Resilience) 확보 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 비동기 통신 (Asynchronous) | 생산자는 소비자의 즉각적인 응답을 대기하지 않고 메시지 발행 즉시 다음 로직을 지속 수행 |
| 시간적/공간적 디커플링 | 수신자 프로세스가 일시 다운되더라도 브로커에 메시지가 안전하게 보관되어 복구 후 정상 소비 가능 |
| 신뢰성 있는 전달 보증 | At-Most-Once(최대 1회), At-Least-Once(최소 1회), Exactly-Once(정확히 1회) 등 다양한 QoS 전달 수준 제공 |
| 수평적 확장성 (Scalability) | 컨슈머 그룹(Consumer Group)을 통해 여러 워커 프로세스에 메시지를 분산 병렬 처리 가능 |

동기식 HTTP REST 호출의 장애 전파(Cascading Failure) 문제를 근본적으로 차단하는 분산 아키텍처의 핵심 인프라.

## Ⅲ. 체계·프로세스

```text
[생산자 (Producer)]
  비즈니스 이벤트 발생
       │
       ▼ (1) DB 로컬 트랜잭션 (비즈니스 상태 + Outbox 테이블 원자적 저장)
[Transactional Outbox Pattern]
  Outbox Table ──► CDC / 폴링 릴레이 엔진 (Debezium 등)
                         │
                         ▼ (2) 메시지 발행 (Publish)
[메시지 브로커 (Message Broker)]
  ┌────────────────────────────────────────────────────────┐
  │ 토픽 / 익스체인지 (Topic / Exchange)                   │
  │   ├─ 메시지 큐 1 (파티션 1) ──► 디스크 영속화(WAL)     │
  │   └─ DLQ (Dead Letter Queue, 최종 실패 메시지 격리)   │
  └────────────────────────────────────────────────────────┘
       │                                     ▲ (5) 최대 재시도 초과 시 이관
       ▼ (3) 메시지 소비 (Pull/Push)         │
[소비자 (Consumer)]                          │
  ┌──────────────────────────────────────────┴─────────────┐
  │ 1. 메시지 고유 ID 추출 (중복 처리 여부 멱등성 검사)    │
  │ 2. 비즈니스 로직 수행                                  │
  │ 3. 처리 성공 시 ──► (4) 브로커에 ACK 반환             │
  │ 4. 처리 실패 시 ──► 재시도 큐 / 지연 큐 백오프 전송    │
  └────────────────────────────────────────────────────────┘
```

로컬 트랜잭션 보장을 위한 아웃박스 발행부터 브로커 영속화, 소비자의 멱등 처리 및 실패 시 DLQ 격리까지의 엔드투엔드 신뢰성 체계.

## Ⅳ. 종류·비교

| 비교 항목 | 전통적 메시지 큐 (RabbitMQ, ActiveMQ) | 이벤트 스트리밍 플랫폼 (Apache Kafka) |
|---|---|---|
| **기본 아키텍처** | 스마트 브로커 - 덤 컨슈머 (브로커가 상태 관리) | 덤 브로커 - 스마트 컨슈머 (컨슈머가 오프셋 관리) |
| **메시지 소비 모델** | 큐 기반 푸시/풀 (소비 후 브로커에서 메시지 삭제) | 분할 로그(Commit Log) 기반 풀 (소비 후에도 메시지 보존) |
| **처리량 (Throughput)** | 초당 수만 건 (복잡한 라우팅 중심) | 초당 수십만~수백만 건 (대규모 데이터 스트림 중심) |
| **메시지 순서 보장** | 단일 큐 내에서는 보장, 경쟁 소비자 구성 시 복잡 | 동일 파티션(Partition Key) 내에서 엄격한 순서 보장 |
| **메시지 재생 (Replay)** | 불가 (소비 완료 시 삭제됨) | 가능 (오프셋 조정을 통한 과거 시점 데이터 재처리) |
| **주요 적용 사례** | 복잡한 라우팅 기반 백엔드 비동기 작업, 주문 처리 | 실시간 로그 수집, 이벤트 드리븐 아키텍처(EDA), 빅데이터 ETL |

### 메시지 전달 보장 수준(QoS) 비교

| 보장 수준 | 동작 원리 | 장단점 및 고려사항 |
|---|---|---|
| **At-Most-Once (최대 1회)** | 메시지 전송 후 ACK 미확인 (Fire-and-Forget) | 유실 가능성 존재 / 지연시간 최소 (로그/센서 데이터) |
| **At-Least-Once (최소 1회)** | ACK 수신 실패 시 무조건 재전송 (Default) | 유실 방지 보장 / 중복 수신 발생 가능 (소비자 멱등성 필수) |
| **Exactly-Once (정확히 1회)** | 2PC 분산 트랜잭션 또는 멱등 생산자+트랜잭션 오프셋 | 완벽한 무결성 / 오버헤드 증가 및 특정 플랫폼 종속 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 네트워크 장애나 컨슈머 처리 지연으로 인한 At-Least-Once 재전송 시 비즈니스 중복 결제/처리 발생 | 수신 메시지의 고유 식별자(UUID, 비즈니스 키)를 Redis 또는 RDBMS 유니크 제약으로 검증하는 멱등성(Idempotency) 로직 구축 |
| 지속적 처리 실패를 유발하는 독성 메시지(Poison Message)로 인한 전체 큐 블로킹 | 지수 백오프(Exponential Backoff) 기반 재시도 후 최대 횟수 초과 시 DLQ(Dead Letter Queue)로 즉시 격리 및 알람 |
| 비즈니스 DB 트랜잭션과 브로커 메시지 발행 간의 원자성 미보장으로 인한 이중 쓰기 불일치 | Transactional Outbox 패턴을 도입하여 Debezium 등 CDC 엔진 기반 안전한 릴레이 파이프라인 구축 |

## Ⅵ. 제언

클라우드 네이티브 MSA 환경에서는 서비스 간 강결합을 해소하기 위해 이벤트 기반 아키텍처(EDA)를 구축하고, OpenTelemetry 기반 분산 추적(Distributed Tracing)을 통해 메시지 전송 전 구간의 가시성을 확보할 것을 권장.

```text
[메시지 큐 통합 관측 및 복원력 파이프라인]
  Producer (Trace ID 주입) → Message Broker (지연/적체 모니터링) → Consumer (Trace ID 전파 및 메트릭 수집)
                                                                          │
                                                                          └─ 장애 시 카나리 우회 및 DLQ 재처리
```

| 검증 단계 | 전송 보증 설계 | 장애 복구 및 운영 거버넌스 |
|---|---|---|
| 핵심 통제 | Producer Confirm, Transactional Outbox, Consumer Idempotency | 지수 백오프 기반 DLQ 자동 격리 및 관리자 웹 기반 재처리 도구 |
| 모니터링 지표 | 메시지 인입량, 처리 지연시간(P99) | Consumer Lag(컨슈머 적체량), DLQ 누적 건수 |
