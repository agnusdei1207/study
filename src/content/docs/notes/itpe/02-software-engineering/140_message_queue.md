## 핵심 용어
- 적어도 한 번 전송(At-least-once Delivery): 네트워크 장애나 컨슈머 크래시 시 메시지 유실을 막기 위해 재전송을 수행하여, 유실은 없으나 중복 수신이 발생할 수 있는 전송 보장 수준
- 데드 레터 큐(DLQ, Dead Letter Queue): 파싱 오류나 비즈니스 예외로 인해 최대 재시도 횟수를 초과하여 정상 처리되지 못한 "독이 든 메시지(Poison Message)"를 별도로 격리 보관하는 특수 큐

## 핵심 통찰
- 메시지 큐를 도입할 때 "정확히 한 번(Exactly-once) 전송"을 인프라 마법으로 기대하는 것은 환상이며, 실무에서는 "적어도 한 번(At-least-once)" 전송을 기본으로 하고 애플리케이션 계층에서 "멱등성(Idempotency)"을 구현해 중복을 방어해야 함
- 메시지 큐는 시스템의 처리 용량을 넘어서는 트래픽 폭증(블랙 프라이데이, 선착순 예매) 시 주문을 큐에 안전하게 쌓아두고 백엔드가 감당할 수 있는 속도로 꺼내 처리하는 "트래픽 레벨링(Traffic Leveling)"의 핵심 완충 장치임
- RabbitMQ 같은 전통적 브로커는 컨슈머가 메시지를 읽으면 큐에서 삭제하는 반면, Kafka는 분산 커밋 로그 기반으로 메시지를 디스크에 영구 보관하여 여러 컨슈머 그룹이 각자의 오프셋(Offset)으로 독립 재생할 수 있음

## 이웃 토픽과 구분
- 메시지 큐(RabbitMQ) vs 이벤트 브로커(Kafka): 메시지 큐 = 작업(Job)의 비동기 분배 및 완료 후 삭제 / 이벤트 스트리밍 = 상태 변경 사실(Event)의 영구 기록 및 실시간 스트림 분석

## 문제·원인·대책
- 적용 상황: 대규모 이커머스 플래시 세일 주문 접수 및 배송 처리 파이프라인
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 네트워크 일시 단절 후 재시도 과정에서 동일한 주문 결제 메시지가 2번 처리되어 이중 결제 | At-least-once 전송 정책에서 컨슈머의 중복 처리 방어 로직 부재 | 컨슈머에 고유 메시지 ID 기반 Redis 분산 락 및 DB 중복 체크(멱등성) 적용 | 중복 결제 사고 원천 차단 |
| 특정 비정상 포맷의 메시지로 인해 컨슈머가 무한 에러를 뿜으며 전체 큐 처리가 정체됨 | 오류 메시지가 큐 헤드에 머무르며 재시도를 무한 반복하는 독성 메시지 현상 | 재시도 3회 실패 시 즉시 데드 레터 큐(DLQ)로 우회 격리 및 담당자 알림 | 전체 메시지 파이프라인 정상 흐름 유지 |
