## 답안 골격
```text
[인터페이스(Interface)] ◀━━ 머리: Ⅶ 내 의견 (계약에 의한 설계(DbC)와 의존성 역전 원칙(DIP)을 통한 대규모 시스템의 디커플링 아키텍처)
 ┃
 ┣━ Ⅰ 개요 ───── 클래스나 시스템 간의 상호작용 규칙을 정의한 순수 추상 계약(Contract)이자 다형성을 보장하는 표준 규격
 ┣━ Ⅱ 특징 ───── 구현 세부사항 완전 배제 · 다중 상속/구현 허용 · SOLID 원칙(DIP, ISP, OCP)의 핵심 실현 매개체
 ┣━ Ⅲ 구조 ───── 인터페이스 구조: 메서드 시그니처 선언부 + 상수 필드 / Java 8 이후 default/static 메서드를 통한 하위 호환성 지원
 ┣━ Ⅳ 흐름 ───── 클라이언트 호출 → 인터페이스 규격 바인딩 → 동적 디스패치(다형성) → 구체 클래스(Concrete Class) 실행
 ┣━ Ⅴ 비교 ───── 인터페이스(Interface) vs 추상 클래스(Abstract Class) vs 구체 클래스(Concrete Class)
 ┗━ Ⅵ 실무 ───── 인터페이스 오염(뚱뚱한 인터페이스로 ISP 위반) / 잦은 인터페이스 변경으로 구현체 연쇄 수정 / Mock 객체 기반 테스트 용이성
```
- 필수 키워드: 계약(Contract) · 다형성(Polymorphism) · 느슨한 결합(Loose Coupling) · DIP(의존성 역전 원칙) · ISP(인터페이스 분리 원칙) · 다중 구현 · 동적 디스패치
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 클라이언트-인터페이스-구현체 분리 도식 → Ⅴ 추상 클래스 vs 인터페이스 비교표 / 25점 = Ⅰ~Ⅶ 전개, 108·117회 기출 객체지향 인터페이스의 역할, SOLID 원칙과의 상관관계, Java 8 default 메서드 도입 배경과 다중 구현 충돌 해결
- 기출: 108회 1교시, 117회 1교시 `객체지향 프로그래밍에서 인터페이스(Interface)의 개념, 역할 및 추상클래스와의 차이점` → Ⅰ~Ⅵ

## 한 줄 본질
- 어떤 객체가 무엇(What)을 할 수 있는지만 규정하고 어떻게(How) 하는지는 구현체에 위임함으로써 결합도를 낮추고 유연한 부품 교체를 가능하게 하는 소프트웨어 계약 / 결합도 분리와 다형성 실현

## 핵심 그림
```text
[ 클라이언트 (Caller) ]
        │
        ▼ (의존: "어떻게 하는지 몰라도 규격만 준수하면 됨")
┌────────────────────────────────────────────────────────┐
│ <<interface>> PaymentGateway                          │
│ + processPayment(amount: int): boolean                 │
└────────────────────────────────────────────────────────┘
        ▲                             ▲
        │ (구현: implements)           │ (구현: implements)
┌───────────────────────┐     ┌────────────────────────┐
│ KakaoPayGateway       │     │ NaverPayGateway        │
│ + processPayment(...) │     │ + processPayment(...)  │
└───────────────────────┘     └────────────────────────┘
```

## 핵심 용어
- 계약에 의한 설계(DbC, Design by Contract): 인터페이스를 클라이언트와 제공자 간의 엄격한 계약(사전조건, 사후조건, 불변식)으로 간주하여 안전한 연동을 보장하는 설계 원칙
- 다형성(Polymorphism): 동일한 인터페이스 호출 메시지에 대해 구현체 객체들의 실제 타입에 따라 서로 다른 구체적인 동작을 수행하는 특성
- 의존성 역전 원칙(DIP, Dependency Inversion Principle): 상위 수준 모듈이 하위 수준 모듈의 구체 클래스에 직접 의존하지 않고, 둘 모두 추상화(인터페이스)에 의존해야 한다는 SOLID 원칙
- 인터페이스 분리 원칙(ISP, Interface Segregation Principle): 클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않도록, 하나의 범용 인터페이스보다 여러 개의 구체적인 인터페이스로 잘게 쪼개야 한다는 원칙
- 기본 메서드(Default Method): Java 8부터 지원되는 기능으로, 기존 인터페이스에 기본 구현 코드를 포함시켜 하위 구현 클래스들의 소스코드 수정 없이 신규 기능을 추가할 수 있도록 한 문법

## 핵심 통찰
- 인터페이스를 도입하는 궁극적인 이유는 '변화의 격리'임. 클라이언트가 구현 클래스를 직접 참조하면, 구현 클래스가 바뀔 때마다 클라이언트 코드도 함께 깨짐
- 인터페이스라는 완충재를 사이에 둠으로써 구현체를 A에서 B로 완전히 갈아 끼워도 클라이언트 코드는 단 한 줄도 수정할 필요가 없는 개방 폐쇄 원칙(OCP)이 달성됨
- 단위 테스트(Unit Test) 관점에서도 외부 DB나 네트워크에 의존하는 실제 구현체 대신 가짜 Mock 객체를 인터페이스로 주입할 수 있어 테스트 격리성과 속도를 극대화함

## 이웃 토픽과 구분
| 비교 항목 | 인터페이스 (Interface) | 추상 클래스 (Abstract Class) | 구체 클래스 (Concrete Class) |
| :--- | :--- | :--- | :--- |
| **핵심 목적** | 행위의 규약 및 표준 계약 정의 (다형성) | 공통 상태/코드의 재사용 및 하위 확장 | 실제 객체 인스턴스화 및 비즈니스 수행 |
| **다중 상속 여부**| 다중 구현(Multiple Implementation) 가능 | 단일 상속만 허용 (Java/C# 기준) | 단일 상속만 허용 |
| **멤버 변수** | 상수(`public static final`)만 가능 | 일반 인스턴스 변수(상태) 보유 가능 | 일반 인스턴스 변수 자유롭게 보유 |
| **메서드 구현** | 원칙적 미구현 (default 메서드 예외) | 일반 메서드 구현 + 추상 메서드 혼합 | 모든 메서드의 구체적 구현 필수 |
| **의미적 관계** | Can-Do ("~을 할 수 있다", 행위 능력) | IS-A ("~의 일종이다", 본질적 혈통) | 구체적 실체 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **비대한 인터페이스로 불필요한 메서드 강제 오버라이딩** | 모든 요구 기능을 단일 인터페이스에 몰아넣어 거대 인터페이스 생성 (ISP 위반) | 역할 인터페이스(Role Interface)로 잘게 쪼개어 클라이언트 맞춤형 다중 구현 구조로 리팩토링 |
| **신규 메서드 추가 시 수십 개 구현 클래스 컴파일 에러** | 인터페이스 명세 변경 시 기존 하위 구현체들이 미구현 클래스로 전락 | 인터페이스 기본 메서드(Default Method) 활용 또는 어댑터 패턴(Adapter) 도입 |
| **구체 클래스에 대한 직접 new 생성자로 인한 강결합** | 인터페이스를 선언해두고 정작 코드 내부에서 `new ConcreteClass()` 직접 호출 | 제어의 역전(IoC) 및 의존성 주입(DI) 컨테이너(Spring)를 활용한 런타임 빈(Bean) 주입 |

## 이렇게 출제된다
- **10점형**: 객체지향 설계에서 인터페이스(Interface)의 개념 및 추상 클래스(Abstract Class)와의 차이점을 설명하시오.
- **25점형**: 
  - 1) 인터페이스의 개념과 소프트웨어 아키텍처 결합도 완화(Decoupling) 메커니즘을 도식으로 제시하시오.
  - 2) SOLID 원칙 중 인터페이스와 직결되는 3대 원칙(OCP, ISP, DIP)의 구체적 적용 방안을 코드 구조 관점에서 설명하시오.
  - 3) 대규모 분산 시스템 및 프레임워크 설계에서 인터페이스의 하위 호환성 유지 전략(Java Default Method, API 버저닝 등)을 논하시오.

## 내 의견
- 객체지향 설계의 거장 에릭 감마(Erich Gamma)가 남긴 "구현이 아닌 인터페이스에 맞춰 프로그래밍하라(Program to an interface, not an implementation)"는 소프트웨어 공학의 불변의 진리임
- 현대의 모든 클린 아키텍처, 헥사고날 아키텍처(Ports and Adapters), 도메인 주도 설계(DDD)는 인터페이스를 중심에 두고 인프라(DB, 외부 API)를 외곽의 어댑터로 밀어내는 방식으로 순수 비즈니스 로직을 보호함
- 실무 엔지니어는 단순히 문법적으로 `interface` 키워드를 쓰는 것에 그치지 않고, 인터페이스가 도메인의 명확한 책임 경계와 계약을 대변하도록 비즈니스 언어로 정교하게 설계해야 함
