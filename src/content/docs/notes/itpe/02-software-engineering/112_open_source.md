## 30초 인출

- 본질: **오픈소스 거버넌스**는 조직의 오픈소스 사용을 라이선스와 보안 관점에서 관리하는 정책·절차
- 메커니즘: 구성요소 식별 → 라이선스·취약점 확인 → 사용 조건 이행 → 배포물·기록 관리
- 핵심 관계: 구성요소와 버전 정보를 SBOM으로 추적해 영향 분석과 의무 이행에 활용

<details>
<summary>핵심 용어</summary>

- **오픈소스 소프트웨어(OSS, Open Source Software)**: 라이선스가 소스 이용·수정·재배포 권리를 허용하는 소프트웨어
- **오픈소스 거버넌스(Open Source Governance)**: 조직의 OSS 도입·사용·배포에서 정책, 검토, 책임을 정하는 관리 체계
- **소프트웨어 구성 분석(SCA, Software Composition Analysis)**: 소프트웨어 구성요소와 관련 라이선스·취약점 정보를 식별하는 분석
- **소프트웨어 자재명세서(SBOM, Software Bill of Materials)**: 소프트웨어를 구성하는 구성요소와 식별 정보를 기록한 목록
- **SPDX(Software Package Data Exchange)**: 소프트웨어 구성요소·라이선스 정보를 교환하기 위한 형식 및 명세
</details>

## 1교시 10점 답안

### Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 오픈소스 거버넌스는 조직의 OSS 사용과 배포에 필요한 정책·검토·책임을 정하는 관리 체계 |
| 목적 | 재사용의 이점을 살리면서 라이선스 조건과 보안 위험을 관리 |

### Ⅱ. 구성요소 식별과 검토

```text
도입 구성요소·버전 식별
    ↓
라이선스 의무·취약점 검토
    ↓
사용 조건·조치 결정
    ↓
고지·배포·구성 기록
    ↓
SBOM 갱신·영향 추적
```

### Ⅲ. 관리 원칙과 제언

- OSS 라이선스는 이름만으로 의무를 단정하지 않고, 적용 버전의 라이선스 원문과 이용·수정·배포 방식을 함께 검토
- 제언: 도입부터 배포까지 구성요소·라이선스·취약점 기록을 연결하는 OSS 검토 절차 마련

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 오픈소스 거버넌스는 조직의 OSS 사용과 배포에 필요한 정책·검토·책임을 정하는 관리 체계 |
| 목적 | 재사용의 이점을 살리면서 라이선스 조건과 보안 위험을 관리 |

## Ⅱ. 거버넌스 구성과 관리 흐름

```text
SCA: 구성요소·버전 식별
    ├─ 라이선스 의무 검토
    └─ 알려진 취약점 확인

조치 결정 → 고지·배포 검수
구성 변경 → SBOM 갱신·영향 추적
```

| 구성 | 역할 |
|---|---|
| 정책·책임 | 도입 검토, 예외 승인, 배포 책임과 기록 기준 정의 |
| 구성요소 식별 | 직접·전이 의존성, 버전, 출처를 확인 |
| 라이선스 검토 | 배포 형태와 사용 방식에 적용되는 조건 및 고지 의무 확인 |
| 보안 검토 | 알려진 취약점, 사용 가능성, 수정·완화 상태 확인 |
| 배포 기록 | SBOM과 고지문 등 배포 시 필요한 정보를 유지 |

## Ⅲ. 라이선스·보안 검토

| 검토축 | 확인 내용 | 유의점 |
|---|---|---|
| 라이선스 | 저작권 고지, 라이선스 사본, 수정·재배포 조건 | 의무는 라이선스 문구와 배포·결합 상황에 따라 달라짐 |
| 보안 | 취약점 식별자, 영향 버전, 수정 버전·완화책 | 취약점 존재만으로 실제 노출 여부를 단정하지 않고 사용 경로를 분석 |
| 공급망 | 구성요소 이름·버전·출처와 의존 관계 | 생성된 목록의 정확성과 최신성을 점검 |

라이선스 유형은 1차 검토에 활용하되, 구체 의무는 각 구성요소의 라이선스 원문과 실제 배포 형태를 기준으로 확인하고 필요시 법률 검토

## Ⅳ. 적용상 문제와 대응

| 한계 | 대응 |
|---|---|
| 전이 의존성이나 중복·변형 구성요소가 목록에서 빠짐 | 빌드 산출물과 의존성 선언을 함께 분석하고 예외·미식별 항목을 검토 |
| 라이선스 식별자만으로 의무를 잘못 판단 | 라이선스 원문, 수정 여부, 결합·배포 방식을 확인하고 근거를 기록 |
| 취약점 정보와 실제 배포 버전의 연결이 약함 | SBOM의 구성요소 식별자를 배포 버전과 연결해 영향 범위를 확인 |
| 도구가 탐지 결과를 과다·과소 보고 | 자동 분석 결과를 검토하고 오탐·미탐 처리 이력을 관리 |

## Ⅴ. 기술사적 제언

| 구분 | 제언 |
|---|---|
| 한계 | OSS 구성·라이선스·취약점 정보가 개발과 배포 과정에 흩어질 가능성 |
| 해결 방안 | 도입 검토와 빌드 분석, 라이선스 이행, SBOM 갱신을 하나의 책임·기록 흐름으로 연결 |
