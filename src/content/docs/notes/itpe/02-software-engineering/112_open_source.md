## 30초 인출

- 본질: **오픈소스 거버넌스 (OSS Governance)** 는 오픈소스 소프트웨어의 도입, 개발, 배포 전 과정에서 발생할 수 있는 라이선스 컴플라이언스 위반(소스코드 공개 의무 등)과 공급망 보안 취약점(Log4Shell 등)을 예방·통제하기 위해 수립된 전사적 정책, 조직, 프로세스, 자동화 검증(SCA/SBOM) 체계
- 메커니즘: 오픈소스 사용 요청 및 심의 → CI 파이프라인 연계 SCA 정적 분석(직접/전이 의존성 식별) → 라이선스 의무 사항(고지문 작성) 이행 및 CVE 보안 패치 → 표준 SBOM(SPDX/CycloneDX) 자동 생성 및 배포 검수
- 통찰: 단순 1차 의존 라이브러리 검사만으로는 2차, 3차 전이 의존성(Transitive Dependencies)에 숨겨진 GPL 카피레프트 전파와 보안 취약점을 차단할 수 없으므로 CI/CD 파이프라인 내 SCA 자동화 도구와 OpenChain(ISO/IEC 5230) 인증 기반 거버넌스를 구축할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **오픈소스 라이선스 (OSS License)** : 소프트웨어 저작권자가 사용자에게 소스코드의 자유로운 이용, 수정, 재배포를 허용하면서 부과하는 법적 조건 (Permissive vs Copyleft)
- **카피레프트 (Copyleft)** : 2차적 저작물 및 결합 배포물에 대해 원본과 동일한 라이선스로 소스코드를 의무 공개하도록 강제하는 전파성 조항 (GPL, AGPL)
- **SCA (Software Composition Analysis)** : 소스코드 및 바이너리를 분석하여 포함된 오픈소스 컴포넌트, 버전, 라이선스 유형, CVE 취약점을 자동 식별하는 분석 기법
- **SBOM (Software Bill of Materials)** : 소프트웨어를 구성하는 모든 오픈소스 및 서드파티 부품의 패키지명, 버전, 해시값, 의존성 관계를 기록한 디지털 자재명세서
- **OpenChain (ISO/IEC 5230)** : 기업의 오픈소스 컴플라이언스 역량과 거버넌스 체계를 평가하여 공인하는 국제 표준 규격

</details>

## 2~4교시 예상문제 (25점)

> 기업의 디지털 공급망 보안 및 법적 리스크 관리를 위한 오픈소스 소프트웨어(OSS) 거버넌스의 개념과 필요성을 설명하고, 라이선스 유형별 의무사항(Permissive vs Weak/Strong Copyleft), 4단계 거버넌스 운영 프로세스 및 SBOM(Software Bill of Materials) 표준 연계 방안을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 조직 내부에서 사용하는 오픈소스 소프트웨어의 선택, 획득, 사용, 수정, 배포에 이르는 전 생애주기를 법적·보안적 위험 없이 통제하기 위한 제도 및 기술적 관리 체계 |
| 목적 | GPL 등 카피레프트 라이선스 위반에 따른 소스코드 강제 공개 분쟁 방지, 소프트웨어 공급망 공격(Log4j 등) 예방, 대외 신뢰도 확보 |

## Ⅱ. 핵심 특징

단순한 법률 검토를 넘어 CI/CD 파이프라인과 통합된 기술적 자동 감사 체계를 지향.

| 핵심 영역 | 메커니즘 | 실무 효과 |
|---|---|---|
| **라이선스 컴플라이언스** | 결합 방식(정적/동적 링크, 파이프라인)에 따른 배포 의무 식별 | 기업 고유 지식재산권(IP) 보호 및 소송 리스크 차단 |
| **전이 의존성(Transitive) 추적** | 패키지 매니저(npm, Maven)가 자동 설치하는 하위 라이브러리 전수 검사 | 숨겨진 비인가 오픈소스 유입 100% 감지 |
| **공급망 보안 연동** | NVD(미국 국립표준기술원) CVE 데이터베이스와 실시간 매핑 | 고위험 보안 취약점(CVSS 7.0 이상) 선제 차단 |
| **SBOM 표준 명세화** | SPDX, CycloneDX 기계 판독형 표준 포맷으로 공급망 명세서 발행 | 고객사 및 글로벌 규제(미 행정명령 EO 14028) 요구 완벽 대응 |

## Ⅲ. 체계·프로세스

오픈소스 거버넌스의 4단계 수명주기 프로세스 및 CI/CD 연동 자동화 아키텍처.

```text
+---------------------------------------------------------------------------------------------------------+
|                                    오픈소스 거버넌스 4단계 수명주기 및 SCA 체계                          |
+---------------------------------------------------------------------------------------------------------+
                                                                                                           
  [1] 도입/기획 단계             [2] 개발 단계 (CI 파이프라인)         [3] 검증/승인 단계     [4] 배포/운영 단계 
  +─────────────────────+       +───────────────────────────────────+  +─────────────────+  +─────────────────+    
  | 오픈소스 사용 신청  | ────> | 개발자 Git Push                   |  | OSRB 공식 심의  |  | 최종 배포 릴리스|    
  | (OSRB 사전 적합성)  |       | - SCA 자동 스캔 (Black Duck/Snyk) |  | 라이선스 고지문 |  | - SBOM 등록     |    
  +─────────────────────+       | - 직접/전이 의존성 식별           |  | (Notice) 검수   |  | - 지속적 모니터링|   
                                | - GPL 감염 및 CVE 취약점 분석    |  +────────┬────────+  | (신규 CVE 감시) |    
                                +─────────────────┬─────────────────+           │           +─────────────────+    
                                                  │                             │                                  
                                                  ▼ (품질 게이트 판정)           ▼                                  
                                       [위반 발견 시 빌드 Fail] ──> [결함 라이브러리 교체 및 패치]                  
```

- **오픈소스 거버넌스 4단계 프로세스**:
  1. **도입 심의(Request)** : 개발자가 신규 라이선스 도입 전 사내 오픈소스 심의위원회(OSRB)에 사용 목적 및 라이선스 적합성 검토 요청.
  2. **CI 자동화 감사(SCA Scan)** : 빌드 파이프라인에서 SCA 도구를 가동하여 pom.xml, package.json 내 모든 의존성과 코드 스니펫(Snippet) 매칭.
  3. **라이선스 의무 이행(Compliance)** : 사용된 오픈소스의 저작권 고지문(Open Source Notice) 생성 및 상호 충돌 라이선스 격리.
  4. **SBOM 발행 및 모니터링(Distribution)** : 릴리스 산출물에 SPDX/CycloneDX 형식의 SBOM을 첨부하고 운영 중 발표되는 신규 CVE 취약점 상시 감시.

## Ⅳ. 종류·비교

#### 오픈소스 라이선스 4대 범주 비교

| 라이선스 범주 | 대표 라이선스 | 소스코드 공개 의무 | 결합 시 전파 범위 | 저작권 고지 의무 |
|---|---|---|---|---|
| **허용적 (Permissive)** | MIT, Apache 2.0, BSD | 없음 (상용화 및 비공개 가능) | 전파되지 않음 (자유 결합) | 필수 (라이선스 사본 첨부) |
| **약한 카피레프트 (Weak Copyleft)** | LGPL, MPL | 해당 라이브러리를 수정한 경우만 공개 | 동적 링크 시 독자 소스 비공개 | 필수 |
| **강한 카피레프트 (Strong Copyleft)**| GPL v2, GPL v3 | **해당 라이선스로 전체 소스코드 의무 공개**| **정적/동적 링크 결합물 전체로 전파** | 필수 |
| **네트워크 카피레프트 (Network)** | AGPL (Affero GPL) | **네트워크를 통한 SaaS 서비스 시에도 공개** | 네트워크 API 호출 연동 모듈까지 | 필수 |

#### SBOM 양대 표준 규격(SPDX vs CycloneDX) 비교

| 비교 항목 | SPDX (Software Package Data Exchange) | CycloneDX |
|---|---|---|
| **주관 기관** | 리눅스 재단 (Linux Foundation), ISO/IEC 5962 | OWASP 재단 (Open Web Application Security Project) |
| **설계 초점** | **라이선스 컴플라이언스 및 지식재산권(IP) 추적** | **애플리케이션 보안 및 소프트웨어 공급망 취약점 분석** |
| **지원 포맷** | JSON, YAML, XML, Tag:Value, RDF | JSON, XML, Protocol Buffers |
| **시장 적용** | 글로벌 표준 규격 준수, 대규모 엔터프라이즈 | DevSecOps 파이프라인 자동화, 클라우드 네이티브 환경 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 개발 마감 직전에 1회성으로 수동 검사를 수행하여 GPL 라이선스 위반 발견 시 프로젝트 전면 재작성 위기 | Git PR 단계에 Sonatype, Snyk 등 SCA 도구를 연동하여 비인가 라이선스 유입 시 PR 머지 자동 차단 |
| 수천 개의 오픈소스 의존성에서 발생하는 방대한 CVE 취약점 경보로 인한 개발 피로도(Alert Fatigue) | VEX(Vulnerability Exploitability eXchange) 메커니즘을 도입하여 실제 실행 경로에 노출된 취약점만 선별 조치 |
| 오픈소스 패키지 관리자의 계정 탈취를 통한 악성코드 주입 등 소프트웨어 공급망 오염 공격(Typosquatting) | 사내 프라이빗 패키지 저장소(Nexus, Artifactory)를 구축하고 검증된 승인 바이너리만 캐싱하여 사용 |

## Ⅵ. 제언

오픈소스 거버넌스는 단순한 법무팀의 규제가 아닌 개발 생산성을 보장하는 안전장치이므로, ISO/IEC 5230(OpenChain) 인증 획득과 함께 DevSecOps 파이프라인에 SBOM 자동 발행 체계를 결합할 필요가 있음.

```text
[오픈소스 정책 수립] ──> [사내 OSRB 심의위원회] ──> [CI/CD SCA 자동 통제] ──> [CycloneDX SBOM 발행]
  (ISO/IEC 5230 준수)       (고위험 라이선스 사전 선별)      (빌드 실패 Quality Gate)       (공급망 투명성 100% 보증)
```

| 거버넌스 영역 | 권장 실천 지침 | 핵심 관리 지표 |
|---|---|---|
| **조직 체계** | 전담 OSRB(Open Source Review Board) 및 법무-엔지니어링 협의체 가동 | 신규 오픈소스 승인 소요 시간 2일 이내 단축 |
| **보안 자동화** | CI 파이프라인 내 CVSS 8.0 이상 취약점 탐지 시 배포 차단 | 고위험 미조치 CVE 취약점 0건 유지 |
| **컴플라이언스** | 제품 릴리스 시 오픈소스 고지문 및 SBOM 자동 번들링 | 오픈소스 라이선스 소송 및 분쟁 건수 0건 달성 |
