## 연관 키워드
- SRS, ISO/IEC/IEEE 29148, 기능 요구, 비기능 요구
- 추적성, 수용기준, 기준선

## Ⅰ. 요구사항 명세서의 개요

- 핵심 요약 : 요구사항 명세서는 시스템이 만족해야 할 기능·품질·제약을 검증 가능한 문장으로 고정한 합의 문서.
- 개념 : 시스템이 제공할 기능과 품질·제약 조건을 이해관계자의 합의에 따라 검증 가능한 형태로 기록한 문서가 **요구사항 명세서** (SRS, Software Requirements Specification)임.
- 배경 및 필요성 : 요구를 구두·비공식으로 전달하면 해석 차이·누락이 발생하고 설계·시험·검수 단계의 재작업과 분쟁 비용이 커짐.
- 주요 목적 : 발주자·개발자·시험자가 공유하는 요구 기준의 확립과 검증 가능한 수용 판단.

## Ⅱ. 요구사항 명세서의 특징 및 장점

- 핵심 요약 : 검증 가능한 문장·표준 구조·요구 유형 구분·추적성이 명세 품질을 결정.

1. 검증 가능한 기술 : 각 요구를 측정 조건·예외 상황까지 구체화한 **수용기준** (Acceptance Criteria)으로 작성하고 무모호성·완전성·일관성 같은 요구 품질 특성을 반영 → 수용 판단의 객관성 확보.
2. 표준 구조 준수 : 요구공학 국제 표준 **ISO/IEC/IEEE 29148** (Requirements engineering)과 구판 권고인 IEEE(Institute of Electrical and Electronics Engineers) 830의 목차 구성 활용 → 항목 누락 방지와 문서 품질의 일관성.
3. 요구 유형 구분 : 동작을 정의하는 **기능 요구** (Functional Requirement)와 성능·보안·사용성 같은 **비기능 요구** (Non-Functional Requirement)의 분리 기술 → 설계·시험 기준의 명확화.
4. **추적성** (Traceability) 확보 : 요구 식별자로 출처·설계·시험 항목을 연결 → 변경 영향 분석과 범위 관리 효과.

## Ⅲ. 요구사항 명세서의 구조 (흐름)

- 핵심 요약 : 도입·총체·개별 요구·검증 지원의 4부 구성으로 작성하고, 발주자 승인으로 변경 관리 대상인 기준선을 설정.

```text
[ SRS 문서 구조 ]

도입 (목적·범위·용어 정의)
   ↓
총체 기술 (제품 관점·기능 요약)
   ↓
개별 요구 (기능·비기능·인터페이스)
   ↓
검증 지원 (추적·색인·변경 이력)
```

- **기준선** (Baseline, 승인으로 고정된 변경 관리 대상 문서 상태) 설정까지의 절차 :

```text
요구 도출·분석
   ↓
명세 문장화·식별자 부여
   ↓
검토 회의·정합성 확인
   ↓
발주자 승인 (기준선 설정)
   ↓
변경관리·설계·시험 추적
```

## Ⅳ. 요구사항 명세서와 구두·비공식 합의의 비교

- 핵심 요약 : 담당자의 기억과 메모에 의존하는 구두 합의와 달리, 명세서는 검증·추적·분쟁 대응의 근거를 제공.

| 비교 축 | 구두·비공식 합의 | 요구사항 명세서 |
| --- | --- | --- |
| 기록 형태 | 회의 메모·구두 전달에 의존 | 식별자를 부여한 문서로 고정 |
| 해석 일관성 | 담당자·시점별 해석 차이 | 정의된 용어·문장으로 해석 통일 |
| 검증 가능성 | 수용 기준 불명확 | 수용기준 기반의 시험·검수 |
| 변경 관리 | 변경 이력 추적 불가 | 변경 승인·이력 관리로 추적 |
| 분쟁 대응 | 증빙 부족으로 책임 논란 | 합의 문서가 계약·감사의 근거 |

## Ⅴ. 요구사항 명세서의 한계와 방안

- 핵심 요약 : 모호성·과잉 명세·문서 정체·범위 누락을 측정 조건·기술 원칙·변경 절차로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 모호한 표현 | 신속·사용자 친화적 같은 측정 불가 문구 → 검수 기준 분쟁 | 측정 조건·수치 근거·예외의 문장화 | 검토 단계 지적 건수 |
| 과잉 명세 | 구현 방법까지 지정 → 설계 자율성·대안 비용 제약 | 결과·제약 중심 기술과 수단의 설계 위임 | 설계 변경 유발 요구 수 |
| 문서 정체 | 승인 후 갱신 중단 → 시스템과의 불일치 | 변경 승인 절차·기준선 갱신 의무화 | 미반영 변경 건수 |
| 범위 누락 | 예외·비기능 항목 미기술 → 사후 추가 요구 | 표준 목차 점검·시나리오 기반 누락 검토 | 후행 요구 추가 건수 |

## Ⅵ. 요구사항 명세서에 대한 제언

- 핵심 요약 : 발주기관과 개발조직은 표준 템플릿·검토 절차·요구관리 도구의 결합으로 명세를 계약과 시험에 통하는 기준으로 운영해야 함.

1. 제도화 : 발주기관이 표준 템플릿과 검수 연계 기준을 계약 문서에 반영하고 공공 표준 가이드를 활용.
2. 검토 체계 : 개발조직이 명세 검토 회의와 이해관계자 확인 절차를 요구 확정 전에 의무화.
3. 도구 기반 관리 : 요구관리 도구로 요구-설계-시험 추적을 상시 관리하고 변경 이력을 형상 관리 체계에 통합.

## Ⅶ. 결론

- 핵심 요약 : 요구사항 명세서는 요구를 검증 가능한 문서 기준으로 고정하는 요구공학의 핵심 산출물.
- 시사점 : 명세 품질이 후반부 재작업·분쟁 비용을 결정하므로 작성·검토·변경관리의 체계가 필요.
