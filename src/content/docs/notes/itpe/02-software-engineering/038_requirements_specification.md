## 연관 키워드
- SRS, ISO/IEC/IEEE 29148, 기능·비기능 요구, 추적성, 수용기준

### Ⅰ. 요구사항 명세서의 개요

- 핵심 요약 : SRS(Software Requirements Specification)는 소프트웨어 제품이 제공해야 할 기능·품질·제약을 검증 가능한 형태로 명세한 문서.
- 개념 : 소프트웨어 제품이 제공해야 할 기능·품질·제약을 검증 가능한 형태로 명세한 문서(**SRS**, Software Requirements Specification).
- 배경 및 필요성 : 모호·누락된 요구는 구현·검수 해석 차이와 변경비용을 키움.
- 주요 목적 : 고객·개발·시험·운영 간 요구와 수용기준의 공통 기준선 확보.

### Ⅱ. 요구사항 명세서의 특징 및 장점

- 핵심 요약 : 이해관계자·제품범위, 기능·비기능 요구, 인터페이스·제약·검증기준; IEEE 830은 구판 권고관행, ISO/IEC/IEEE 29148은 요구공학 표준.

1. 구조 명시 : 이해관계자·제품범위, 기능·비기능 요구, 인터페이스·제약·검증기준; IEEE 830은 구판 권고관행, ISO/IEC/IEEE 29148은 요구공학 표준 → 고객·개발·시험·운영 간 요구와 수용기준의 공통 기준선 확보.
2. 기대 효과 : 좋은 SRS는 완전·일관·검증 가능한 요구를 담되 해결책을 과도하게 고정하지 않는 합의 기준선.
3. 적용 원칙 : 요구관리 책임자는 요구마다 출처·우선순위·검증방법·변경책임자를 연결하고 개발·시험팀이 추적성으로 범위 확인.

### Ⅲ. 요구사항 명세서의 구조 (흐름)

- 핵심 요약 : 이해관계자 요구 → 분석·우선순위 → 요구사항 문장·속성화 → 검증·승인 → 설계·시험 추적·변경관리.

```text
이해관계자 요구
  ↓
분석·우선순위
  ↓
요구사항 문장·속성화
  ↓
검증·승인
  ↓
설계·시험 추적·변경관리
```

```text
요구 도출 → 명세·검증 → 승인 기준선 → 설계·시험 추적
```

### Ⅳ. 요구사항과 요구사항 명세서 비교

- 핵심 요약 : 요구사항은 이해관계자의 필요·제약, 요구사항 명세서는 제품이 만족할 구체·검증 가능한 조건.

| 비교 축 | 요구사항 | 요구사항 명세서 |
|---|---|---|
| 추상화 수준 | 이해관계자의 필요·제약 | 제품이 만족할 구체·검증 가능한 조건 |
| 역할 | 요구공학의 입력 | 검증·승인 기준선 |

### Ⅴ. 요구사항 명세서의 한계와 방안

- 핵심 요약 : 모호성·문서 박제화·과잉 명세를 측정기준·버전·변경 승인으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 모호성 | "빠르게·사용자 친화적" 등 측정 불가 표현 | 측정기준·조건·예외·수용기준 명시 | 검토 지적 |
| 문서 박제화 | 개발 중 변경·학습 미반영 | 버전·추적성·변경 승인으로 살아있는 기준선 | 미추적 변경 |
| 과잉 명세 | 불필요한 설계 제한 | 필요한 결과·제약만 요구하고 구현수단 분리 | 불필요 요구·변경비용 |

### Ⅵ. 요구사항 명세서에 대한 제언

- 핵심 요약 : 고객·개발·시험·운영 간 요구와 수용기준의 공통 기준선 확보.

1. 요구관리 책임자는 요구마다 출처·우선순위·검증방법·변경책임자를 연결하고 개발·시험팀이 추적성으로 범위 확인.
2. 검토 지적·미추적 변경·불필요 요구·변경비용를 정기 측정하고 편차에 대한 원인분석·개선결과를 기록.

### Ⅶ. 결론

- 핵심 요약 : SRS(Software Requirements Specification)는 소프트웨어 제품이 제공해야 할 기능·품질·제약을 검증 가능한 형태로 명세한 문서.
- 시사점 : 좋은 SRS는 완전·일관·검증 가능한 요구를 담되 해결책을 과도하게 고정하지 않는 합의 기준선.
