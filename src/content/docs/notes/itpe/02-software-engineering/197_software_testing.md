- 결함이 없음을 증명하는 것이 아니라 결함을 조기에 찾아내어 위험을 최소화하고 소프트웨어가 의도대로 동작함을 객관적으로 보증하는 체계적 엔지니어링 / 조기 테스팅과 정황 의존적 검증

## 핵심 용어
- 검증(Verification): 소프트웨어가 개발 규격서와 명세서에 맞게 '올바른 방식으로 개발되고 있는가(Are we building the product right?)'를 확인하는 개발자 관점 활동
- 확인(Validation): 완성된 소프트웨어가 사용자의 원래 의도와 비즈니스 요구에 부합하는 '올바른 제품을 개발하였는가(Are we building the right product?)'를 확인하는 사용자 관점 활동
- 살충제 패러독스(Pesticide Paradox): 동일한 테스트 케이스를 반복 실행하면 내성이 생겨 더 이상 새로운 결함을 발견하지 못하므로, 정기적으로 테스트 케이스를 리뷰하고 개선해야 한다는 원칙
- 오류 부재의 궤변(Absence-of-Errors Fallacy): 아무리 결함을 모두 수정하고 버그가 없더라도, 사용자의 실질적 요구와 비즈니스 가치를 만족시키지 못하면 무용지물이라는 원칙
- 결함 집중(Defect Clustering): 대부분의 결함은 시스템 내 소수의 특정 복잡한 모듈에 파레토 법칙(80:20)처럼 집중되어 나타난다는 원칙

## 핵심 통찰
- 테스팅의 가장 중요한 진리는 '완벽한 테스팅은 불가능하다(Exhaustive Testing is Impossible)'는 점임. 가능한 모든 입력값과 경로의 조합은 무한에 가까움
- 따라서 테스팅은 결함이 '없음'을 증명하는 행위가 아니라, 비즈니스 리스크가 높은 영역을 찾아내어 결함이 '있음'을 증명하고 품질 위험을 관리 가능한 수준으로 낮추는 리스크 기반 테스팅(Risk-Based Testing)이어야 함
- 뒤늦은 시스템 단계에서 버그를 잡으려 하면 수정 비용이 지수함수적으로 증가하므로, 요구사항 단계의 리뷰와 코딩 직후의 단위 테스트를 강조하는 'Shift-Left'가 비용 효율의 핵심임

## 이웃 토픽과 구분
| 비교 항목 | 검증 (Verification) | 확인 (Validation) |
| :--- | :--- | :--- |
| **핵심 질문** | 올바른 방식으로 만들고 있는가? (Right?) | 올바른 제품을 만들었는가? (Right Product?) |
| **점검 대상** | 개발 중간 산출물 (요구서, 설계서, 소스코드) | 최종 인도물 및 실행 가능한 완제품 시스템 |
| **주요 주체** | 개발자, 설계자, 내부 QA 엔지니어 | 최종 사용자, 고객, 비즈니스 이해관계자 |
| **대표 활동** | 인스펙션, 워크스루, 단위/통합 테스트 | 알파/베타 테스트, 사용자 인수 테스트(UAT) |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **기존 테스트 케이스에서 신규 결함 미검출** | 동일한 정적 테스트 스크립트만 수개월간 기계적으로 반복 실행 (살충제 패러독스) | 돌연변이 테스팅(Mutation Testing) 도입 및 탐색적 테스팅(Exploratory Testing) 병행 |
| **버그 없이 출시했으나 사용자 클레임 폭주** | 시스템 명세 준수(Verification)에만 매몰되어 실제 사용자 사용성 무시 (오류 부재의 궤변) | 조기 프로토타입 기반 UAT, A/B 테스팅 및 카나리 배포(Canary Release) 피드백 수렴 |
| **테스트 실행 시간 과다로 CI 배포 파이프라인 지연** | 수만 개의 엔드투엔드(E2E) UI 테스트가 누적되어 빌드 시간 수 시간 소요 | 마틴 파울러의 테스트 피라미드(Test Pyramid) 모델 적용: 단위 70%, 통합 20%, E2E 10% 재편 |

## 이렇게 출제된다
- **10점형**: 소프트웨어 테스트의 검증(Verification)과 확인(Validation)의 개념 및 차이점을 비교하시오.
- **25점형**: 
  - 1) ISTQB가 제시한 소프트웨어 테스팅의 7대 기본 원칙을 설명하시오.
  - 2) 소프트웨어 개발 수명주기와 연계된 V-모델의 4대 테스트 레벨(단위, 통합, 시스템, 인수)과 각 단계별 테스트 목적을 도식으로 제시하시오.
  - 3) 애자일 및 DevOps 환경에서 테스트 효율을 극대화하기 위한 테스트 피라미드(Test Pyramid) 전략과 지속적 테스팅(Continuous Testing) 구현 방안을 논하시오.

## 내 의견
- 테스팅이 개발의 마지막 단계에 수동으로 수행되던 시대의 QA는 현대의 빠른 배포 주기를 가로막는 치명적인 병목이었음
- 오늘날의 우수한 조직은 테스터의 역할을 '사후 결함 적발자'에서 '품질 코치(Quality Coach)' 및 '테스트 자동화 엔지니어'로 전환하고 있음
- 단위·통합 테스트는 개발자가 작성하여 CI 파이프라인에서 100% 자동 검증되도록 하고, 전문 QA 인력은 비정형적이고 창의적인 사용자 시나리오를 발굴하는 탐색적 테스팅(Exploratory Testing)과 장애 주입(Chaos Engineering)에 역량을 집중해야 함
