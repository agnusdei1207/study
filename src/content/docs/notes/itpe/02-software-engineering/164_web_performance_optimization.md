## 지식 로드맵 내 현재 위치

소프트웨어공학 → 품질·성능 → **웹 성능 최적화**

## 30초 인출

- **본질** : 웹 성능 최적화는 화면 표시·입력 반응·시각적 안정성을 측정하고, 느린 구간의 원인을 제거하는 활동
- **메커니즘** : 실제 사용자 지표 확인 → 네트워크·리소스·메인 스레드 병목 진단 → 원인별 개선 → 재측정
- 통찰: 한계: 실험실 점수만 개선하면 실제 사용자 로딩·반응 문제를 놓칠 수 있음 → 방안: LCP·INP·CLS의 현장 지표로 병목을 찾고 같은 조건에서 재측정

<details>
<summary>핵심 용어</summary>

- **Core Web Vitals** : 사용자 경험을 로딩·반응성·시각적 안정성의 세 축으로 살피는 웹 지표 집합
- **LCP(Largest Contentful Paint)** : 뷰포트의 주요 콘텐츠가 표시되기까지의 로딩 지표
- **INP(Interaction to Next Paint)** : 사용자 상호작용에 화면이 반응하기까지의 반응성 지표
- **CLS(Cumulative Layout Shift)** : 예기치 않은 화면 이동을 누적해 보는 시각적 안정성 지표
- **CRP(Critical Rendering Path)** : 브라우저가 문서를 화면의 픽셀로 표현하는 데 필요한 처리 경로
- **성능 예산(Performance Budget)** : 리소스 크기나 사용자 지표의 허용 범위를 정해 변경 시 회귀를 확인하는 기준

</details>

## 2~4교시 25점 답안

## Ⅰ. 웹 성능 최적화의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **웹 성능 최적화** 는 화면 표시·입력 반응·시각적 안정성의 병목을 측정·개선하는 활동 |
| 목적 | 실제 사용자의 로딩·반응 경험 개선과 성능 회귀 방지 |

## Ⅱ. 웹 성능 최적화의 특징

| 특징 | 의미 |
|---|---|
| 사용자 경험 중심 | 서버 응답시간만이 아니라 로딩·상호작용·화면 안정성을 분리해 측정 |
| 여러 계층의 영향 | 서버·전송·리소스·브라우저 작업의 병목이 서로 다른 경험에 영향 |
| 현장과 실험실의 역할 구분 | 실사용자 지표로 우선순위를 정하고 통제된 측정으로 원인을 재현 |
| 회귀 가능성 | 한 번의 점수 개선으로 끝나지 않으며 배포 후 지속 관찰 필요 |

## Ⅲ. 측정·진단·개선 체계와 브라우저 처리 프로세스

```text
실사용자 LCP·INP·CLS 확인 → 취약 경로·기기 선정
            ↓
실험실 재현 → 네트워크·리소스·메인 스레드 병목 추적
            ↓
원인별 변경 → 동일 조건 재측정 → 현장 지표 확인
            └──────── 개선 미달이면 원인 재진단 ────────┘
```

### 주요 콘텐츠 표시와 입력 반응의 하위 경로

```text
요청 → 서버 응답 → HTML·CSS·주요 이미지 발견·전송 → 렌더링 → LCP
사용자 입력 → JavaScript 작업 → 화면 갱신 → INP
동적 요소 삽입 ─크기 미확정→ 화면 이동 누적 → CLS
```

첫 화면의 **LCP** 이미지를 무조건 지연 로딩하면 표시가 더 늦어질 수 있다. 요소의 위치와 실제 요청 시점을 확인해 우선순위를 정한다.

## Ⅳ. 사용자 지표와 병목·개선 방식의 관계

| 지표 | 확인할 경험 | 주요 병목 | 개선·검증 대상 |
|---|---|---|---|
| **LCP** | 주요 콘텐츠 표시 | 느린 응답, 이미지 지연, 렌더링 차단 | 초기 응답·이미지 크기와 우선순위·표시 시점 |
| **INP** | 입력 후 화면 반응 | 긴 JavaScript 작업, 과도한 DOM 처리 | 작업 분할·계산 축소 후 입력 구간 반응 |
| **CLS** | 예기치 않은 화면 이동 | 이미지·광고 영역 크기 미확정 | 영역 사전 예약 후 이동 발생 요소 |

**Core Web Vitals** 의 세 축은 함께 확인하되, 경로·기기별 차이를 한 점수로 숨기지 않는다. 실험실 측정은 원인 재현과 전후 비교에, 현장 데이터는 실제 영향과 우선순위 판단에 쓴다.

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 실험실 점수만 개선해 실제 사용자 문제를 놓침 | 경로·기기별 현장 지표로 우선순위를 정하고 변경 후 같은 집단을 재측정 |
| 한 지표 개선이 다른 경험을 악화시킬 수 있음 | LCP·INP·CLS를 함께 확인하고 변경 전후 영향 비교 |
| 배포 후 리소스 증가로 성능 악화 반복 | 리소스와 사용자 지표의 성능 예산을 두고 릴리스마다 회귀 감시 |

## Ⅵ. 제언

실험실 점수만으로 실제 병목을 놓칠 수 있으므로, 먼저 현장 지표에서 가장 나쁜 사용자 경로를 고른다. 해당 경로의 전송·렌더링·입력 원인을 재현해 고치고 배포 성능 예산에 반영한다.
