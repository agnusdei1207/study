## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 설계·아키텍처 → **소프트웨어 아키텍처 분석(정방향/역방향)**

## 30초 인출

- 본질: 소프트웨어 아키텍처 분석은 요구에서 아키텍처를 도출·평가하는 정방향 분석과 구현된 코드에서 아키텍처를 복원해 설계와 대조하는 역방향 분석으로 나뉨
- 메커니즘: 정방향은 품질 요구에서 구조를 설계하고 평가하며, 역방향은 코드의 의존 관계를 추출해 실제 구조를 복원하고 설계 규칙 위반을 찾음
- 통찰: 문서의 설계와 구현이 시간이 지나며 어긋나므로 코드에서 의존 관계를 역추출해 설계 규칙 위반을 주기적으로 점검하고 정방향 설계와 대조

<details>
<summary>핵심 용어</summary>

- **정방향 분석(Forward Analysis)** : 요구·품질 시나리오에서 아키텍처를 설계·평가하는 분석
- **역방향 분석(Reverse Analysis)** : 구현된 코드에서 아키텍처 구조를 복원하는 분석
- **아키텍처 침식(Architectural Erosion)** : 구현이 설계 규칙을 어겨 실제 구조가 설계에서 벗어나는 현상
- **설계 구조 매트릭스(DSM, Design Structure Matrix)** : 모듈 간 의존 관계를 행렬로 나타낸 표
- **의존 관계 분석** : 모듈·패키지 사이의 호출과 참조를 추출하는 분석

</details>

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 아키텍처 분석의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 아키텍처 분석** 은 아키텍처를 설계·평가하거나 구현에서 복원해 검증하는 분석 활동 |
| 목적 | 설계와 구현의 일치 확인과 품질 요구 충족 판단 |

## Ⅱ. 아키텍처 분석의 특징

| 특징 | 의미 |
|---|---|
| 두 방향 | 요구→구조(정방향), 코드→구조(역방향) |
| 품질 중심 | 품질속성 충족 여부 판단 |
| 지속 활동 | 개발과 유지보수 전반에서 반복 |

## Ⅲ. 정방향·역방향 분석 절차

### 두 분석의 방향

```text
정방향: 요구·품질 시나리오 → 아키텍처 설계 → 평가(ATAM 등)
역방향: 소스 코드 → 의존 관계 추출 → 아키텍처 복원 → 설계와 대조
```

### 확대: 역방향 분석의 침식 점검

```text
코드 의존 관계 추출
    ↓
설계 규칙(예: 표현 계층은 데이터 계층 직접 호출 금지)과 대조
    ├─ 위반 없음 → 유지
    └─ 위반 발견 → 수정 또는 설계 갱신
```

## Ⅳ. 두 분석의 비교

| 구분 | 정방향 분석 | 역방향 분석 |
|---|---|---|
| 입력 | 요구·품질 시나리오 | 소스 코드·바이너리 |
| 산출 | 설계된 아키텍처와 평가 결과 | 복원된 실제 구조 |
| 목적 | 품질 요구 충족 설계 | 설계 준수·침식 확인 |
| 사용 시점 | 설계 단계 | 유지보수·리팩토링 전 |

| 도구·기법 | 내용 |
|---|---|
| DSM | 모듈 간 의존을 행렬로 표현해 결합 파악 |
| 규칙 기반 검사 | 계층 규칙 위반을 자동 점검 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 구현이 설계에서 벗어나는 아키텍처 침식 | 주기적 역방향 분석과 설계 규칙 자동 점검 |
| 복원 구조의 해석 곤란 | DSM 등 시각화와 설계 기준과의 대조 |
| 규칙 정의 부재 | 아키텍처 규칙을 명시하고 문서화 |

## Ⅵ. 제언

핵심 설계 규칙을 자동 점검 규칙으로 정의해 빌드마다 역방향 분석으로 위반을 확인하고, 정방향 설계와 대조

### 자동 점검 구조

```text
설계 규칙 정의
    ↓
빌드마다 의존 관계 추출·규칙 검사
    ↓
위반 시 빌드 경고·수정
```

### 선택 근거: 문서 검토만과의 비교

| 구분 | 문서 검토만 | 제언: 코드 기반 자동 점검 |
|---|---|---|
| 침식 발견 | 늦음 | 빌드마다 |
| 근거 | 문서 | 실제 코드 |
| 유지 비용 | 낮음 | 규칙 유지 필요 |
