## 연관 키워드

- Software Architecture Analysis, 아키텍처 분석
- Forward Analysis, Reverse Analysis, 정방향/역방향
- Architecture Erosion, Architecture Drift, Conformance Checking
- ArchUnit, Fitness Functions, DSM, Martin Metrics
- SAD, 유틸리티 트리, 레거시 현대화

## Ⅰ. 소프트웨어 아키텍처 분석의 개요

- 핵심 요약 : 정방향·역방향 분석으로 설계와 구현의 일치성을 검증하고 아키텍처 침식을 통제하는 공학적 분석 체계.
- 개념 : 설계된 아키텍처와 구현된 소스코드의 일치성을 검증하고 구조적 무결성과 기술 부채를 평가하기 위해, 요구사항에서 아키텍처를 도출하는 **정방향 분석** (Forward Analysis)과 기존 코드에서 실제 아키텍처를 복원하는 **역방향 분석** (Reverse Analysis)을 수행하는 **소프트웨어 아키텍처 분석** (Software Architecture Analysis).
- 배경 및 필요성 : 개발이 진행되면서 일정에 쫓겨 설계 원칙을 무시한 코드가 누적되는 **아키텍처 드리프트** (Architecture Drift) 현상이 생기면, 모듈 경계가 무너져 유지보수 비용이 계속 늘어나므로 구조를 주기적으로 가시화하고 통제할 필요가 있음.
- 주요 목적 : 아키텍처 적합성 검증, 시스템 구조 가시화, 레거시 시스템 현대화의 청사진 확보.

## Ⅱ. 소프트웨어 아키텍처 분석의 특징 및 장점

- 핵심 요약 : 설계 의도와 구현 현실의 간극을 양방향으로 검증하여 구조 품질을 지속적으로 관리하는 분석 체계.

1. 의존성 규칙 수립 : 비즈니스 목표와 품질 시나리오로 아키텍처 패턴을 선정하고 허용된 모듈 간 의존성 규칙을 정의 → 설계 단계에서 결합도 통제 기준 확보.
2. 구조 복원 : 바이트코드, AST(Abstract Syntax Tree, 추상 구문 트리), 커밋 이력을 파싱하여 실제 호출·의존 관계를 시각화 → 현행 구조의 객관적 파악.
3. 적합성 검증 : 의도된 구조와 복원된 구조의 차이를 식별 → 침식과 규칙 위반의 조기 발견.
4. **피트니스 함수** (Fitness Functions, 아키텍처 규칙을 자동 검사하는 테스트) : ArchUnit 등으로 규칙 위반 시 빌드를 자동 실패 처리 → 사람의 검토 누락 방지.
5. 지속적 거버넌스 : CI(Continuous Integration, 지속적 통합) 파이프라인에 검증을 내재화 → 아키텍처 품질을 개발 속도와 함께 유지.

## Ⅲ. 소프트웨어 아키텍처 분석의 구조 (흐름)

- 핵심 요약 : 요구사항에서 의도된 아키텍처를 세우고, 구현 결과를 역으로 복원해 차이를 식별하는 순환 구조.

```text
[ 아키텍처 분석 순환 ]

비즈니스 요구사항
        ↓ 정방향 분석
의도된 아키텍처 (설계 표준)
        ↓ 구현
실제 소스코드
        ↓ 역방향 분석
복원된 아키텍처 (As-Built)
        ↓ 적합성 검증
차이 식별 → 설계 표준 보완
```

```text
[ CI 파이프라인 내 아키텍처 검증 ]

소스코드 커밋
        ↓
정적 분석 (ArchUnit 규칙 실행)
        ↓
규칙 위반 여부 판정
   (위반) → 빌드 실패, 수정
   (통과) → 다음 단계 진행
```

## Ⅳ. 정방향 분석과 역방향 분석의 비교

- 핵심 요약 : 정방향 분석은 청사진을 설계하는 방향이고, 역방향 분석은 구현된 현실을 검증하는 방향으로 출발점과 산출물이 대칭을 이룸.

| 비교 항목 | 정방향 아키텍처 분석 (Forward) | 역방향 아키텍처 분석 (Reverse) |
| --- | --- | --- |
| 분석의 출발점 | 요구사항 명세서, 비즈니스 드라이버 | 이미 구축된 소스코드, 바이너리, DB(Database) 스키마 |
| 주요 산출물 | 개념 아키텍처, SAD(Software Architecture Description, 아키텍처 기술서), **유틸리티 트리** (Utility Tree, 품질 속성 시나리오의 우선순위 트리) | 복원된 컴포넌트 의존 다이어그램, **DSM** (Dependency Structure Matrix, 의존성 구조 매트릭스) |
| 주 목적 | 품질 속성을 보장하는 청사진 설계 | 구현의 규칙 위반과 아키텍처 침식 탐지 |
| 수행 시점 | 프로젝트 기획과 초기 아키텍처 설계 단계 | 개발 중 주기적 코드 감사, 레거시 전환 직전 |
| 대표 도구 | Enterprise Architect, PlantUML, Miro | ArchUnit, Structure101, SonarQube, Lattix |

## Ⅴ. 소프트웨어 아키텍처 분석의 한계와 방안

- 핵심 요약 : 구조 가시화와 침식 통제라는 장점 이면에 침식 진행, 동적 의존성 누락, 품질 평가의 주관성이라는 한계가 존재.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **아키텍처 침식** (Architectural Erosion) | 일정 압박과 임기응변식 코딩으로 계층 구조와 모듈 경계가 무너지고 순환 의존성이 발생 | ArchUnit, SonarQube 등 피트니스 함수를 CI에 통합해 규칙 위반 시 빌드 자동 실패 | 규칙 위반 건수, 순환 의존 모듈 수 |
| 동적 의존성 탐지 한계 | 정적 분석만으로는 의존성 주입, 리플렉션, 분산 RPC(Remote Procedure Call, 원격 프로시저 호출) 관계가 누락 | 정적 AST 분석과 eBPF(extended Berkeley Packet Filter) 및 APM(Application Performance Monitoring) 기반 런타임 추적을 결합 | 런타임 호출 관계 대비 정적 복원 누락률 |
| 품질 속성 평가의 주관성 | 변경 용이성, 이식성 등이 정성적으로 평가되어 개선 투자의 근거 제시가 어려움 | **마틴 메트릭스** (Martin Metrics: 불안정성 I, 추상화도 A, 주계열 거리 D) 등 객관 메트릭 수집 | 메트릭 추세, 기술 부채 해소 건수 |

## Ⅵ. 소프트웨어 아키텍처 분석에 대한 기술사적 제언

- 핵심 요약 : 아키텍처 규칙을 문서에서 코드로 옮겨 자동 검증하고, 의존성 구조를 기준으로 순환 참조를 줄여 나가는 방향.
- 아키텍처 규칙은 문서로만 존재하면 반드시 무너지므로, 계층 간 접근 제한을 ArchUnit 같은 테스트 코드로 작성해 빌드마다 자동 검증하는 **Architecture-as-Code** (아키텍처를 코드로 표현하고 검증하는 방식) 체계를 먼저 갖추는 것이 현실적이다.
- 역방향 분석으로 얻은 의존성 구조는 DSM 행렬로 시각화해 순환 고리를 찾아내고, 고리를 끊기 위해 **의존성 역전 원칙** (DIP, Dependency Inversion Principle)을 적용하는 리팩토링을 계획적으로 추진해야 한다.
- 마틴 메트릭스와 같은 정량 지표를 분기 단위로 추적하면 기술 부채 해소 투자의 효과를 조직 내에서 설득력 있게 보여줄 수 있다.

## Ⅶ. 결론

- 핵심 요약 : 정방향·역방향 분석의 순환으로 아키텍처 침식을 통제하는 거버넌스 체계.
- 설계 의도와 구현 현실을 양방향으로 검증하는 이 체계는 자동화된 피트니스 함수와 정량 메트릭이 결합될 때 지속 가능한 아키텍처 품질을 보장한다.
