## 30초 인출

- 본질: **소프트웨어 아키텍처 분석** 은 비즈니스 품질 요구사항(성능, 보안, 가용성)을 충족하기 위해 최적의 아키텍처 스타일과 전술을 연역적으로 평가하는 **정방향 분석(Forward Analysis)** 과, 구현된 소스코드 및 바이너리로부터 실제 컴포넌트 간 의존 관계를 귀납적으로 역공학하여 아키텍처 침식(Architecture Erosion)을 진단하는 **역방향 분석(Reverse Analysis)** 의 상호 검증 체계
- 메커니즘: 정방향(요구사항 $\rightarrow$ 품질 속성 시나리오 $\rightarrow$ ATAM 평가 $\rightarrow$ 기준선 아키텍처 설계) ↔ 역방향(소스코드 파싱 $\rightarrow$ 의존성 추출 $\rightarrow$ DSM 매트릭스 복원 $\rightarrow$ 갭 분석 및 리팩토링)
- 통찰: 설계 문서와 실제 소스코드 간의 괴리를 방치하면 계층 위반과 순환 참조로 인해 아키텍처가 부패하므로 ArchUnit 같은 아키텍처 린터 도구를 CI 파이프라인에 통합하여 의존성 규칙을 코드로 강제(Architecture-as-Code)할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **정방향 분석 (Forward Analysis)** : 비즈니스 목표와 품질 시나리오를 바탕으로 아키텍처 대안을 평가하고 최적의 설계를 도출하는 하향식(Top-down) 연역적 기법
- **역방향 분석 (Reverse Analysis)** : 구현된 소스코드, 패키지, 바이너리를 정적 분석하여 시스템의 실제 구조(As-Is)를 복원하는 상향식(Bottom-up) 역공학 기법
- **아키텍처 침식 (Architectural Erosion)** : 개발 편의를 위해 계층 규칙을 위반하거나 무단 우회 참조를 추가하여 초기 설계 원칙이 점진적으로 붕괴되는 현상
- **설계 구조 매트릭스 (DSM: Design Structure Matrix)** : 모듈 간의 결합도와 의존 방향성을 $N \times N$ 정방 행렬로 표현하여 순환 의존을 가시화하는 도구
- **ArchUnit** : Java 등 프로그래밍 언어로 아키텍처 규칙(예: "Controller는 Dao에 직접 접근 불가")을 단위 테스트 코드로 작성하고 CI에서 자동 검증하는 도구

</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 아키텍처의 지속 가능성을 보장하기 위한 「소프트웨어 아키텍처 분석(정방향 분석 vs 역방향 분석)」의 개념과 분석 절차를 설명하고, 아키텍처 침식(Architectural Erosion)의 원인 및 DSM(Design Structure Matrix)과 아키텍처 단위 테스트(ArchUnit)를 활용한 지속적 아키텍처 거버넌스 방안을 제시하시오.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 비즈니스 품질 목표 달성을 위해 최적의 구조를 연역적으로 도출하는 '정방향 분석'과, 실제 구현 코드로부터 의존 관계를 귀납적으로 복원하여 설계 일치성을 검증하는 '역방향 분석'의 통합 공학 활동 |
| 목적 | 초기 아키텍처 의사결정의 기술적 타당성 검증(ATAM), 구현 단계에서의 아키텍처 침식(Erosion) 방지 및 기술부채의 체계적 통제 |

## Ⅱ. 핵심 특징

'설계된 아키텍처(As-Designed)'와 '구현된 아키텍처(As-Implemented)' 간의 정합성을 지속 검증.

| 핵심 분석 관점 | 정방향 분석 (Forward Analysis) | 역방향 분석 (Reverse Analysis) |
|---|---|---|
| **출발점 (Origin)** | 비즈니스 동인, 품질 속성 요구사항 | 소스코드, 설정 파일, 빌드 바이너리 |
| **추론 방식** | 하향식(Top-down) 연역적 설계 검증 | 상향식(Bottom-up) 귀납적 구조 복원 |
| **핵심 활동** | 품질 시나리오 평가, 민감점/절충점 분석 | AST 구문 분석, 의존성 매트릭스(DSM) 추출 |
| **주요 산출물** | 아키텍처 정의서(SAD), ATAM 결과 보고서 | 패키지 의존성 그래프, 아키텍처 갭(Gap) 분석서 |
| **대표 도구/기법**| ATAM, CBAM, 유틸리티 트리 (Utility Tree) | Structure101, SonarQube, ArchUnit, DSM |

## Ⅲ. 체계·프로세스

정방향-역방향 통합 아키텍처 거버넌스 및 갭 분석(Gap Analysis) 아키텍처.

```text
[정방향·역방향 아키텍처 통합 분석 체계]
[1] 정방향 분석 (Forward Engineering)                [2] 역방향 분석 (Reverse Engineering)
  +─────────────────────────────────────+             +─────────────────────────────────────+
  | 비즈니스 목표 & 품질 속성 시나리오  |             | 실제 구현 소스코드 & Git 저장소     |
  | (성능, 가용성, 보안, 변경용이성)    |             | (Java / C# / Python 코드베이스)     |
  +──────────────────┬──────────────────+             +──────────────────┬──────────────────+
                     │                                                   │
                     ▼ [ATAM 평가 & 아키텍처 스타일 결정]                ▼ [정적 코드 분석 & 의존성 추출]
  +─────────────────────────────────────+             +─────────────────────────────────────+
  | 설계된 아키텍처 (As-Designed)       |             | 복원된 아키텍처 (As-Implemented)    |
  | * 계층형 아키텍처 (3-Tier Layered)  |             | * 패키지 간 실제 호출 관계 추출     |
  | * Controller -> Service -> Repo 규약|             | * DSM 매트릭스 가시화               |
  +──────────────────┬──────────────────+             +──────────────────┬──────────────────+
                     │                                                   │
                     └─────────────────────────┬─────────────────────────┘
                                               ▼
  [3] 아키텍처 갭 분석 (Gap Analysis : As-Designed vs As-Implemented 비교)
  +─────────────────────────────────────────────────────────────────────────────────────────────────────+
  | * 아키텍처 드리프트/침식 식별: Controller에서 Repository 직접 호출 (계층 건너뜀)                    |
  | * 모듈 간 순환 참조(Circular Dependency) 검출 (Service A <──> Service B)                           |
  +───────────────────────────────────────────────────┬─────────────────────────────────────────────────+
                                                      │
                                                      ▼
  [4] 지속적 아키텍처 거버넌스: ArchUnit 단위 테스트 코드로 규칙화 ──> CI/CD 빌드 실패 처리
```

- **아키텍처 통합 분석 4단계 프로세스**:
  1. **정방향 기준선 수립** : ATAM 워크숍을 통해 품질 속성 유틸리티 트리를 작성하고 계층 구조 및 의존성 규칙 명문화.
  2. **역방향 의존성 복원** : 정적 분석 도구를 사용하여 소스코드 AST로부터 클래스/패키지 간 호출, 상속, 참조 관계를 매핑.
  3. **구조적 불일치(Gap) 진단** : 설계된 레이어 규칙과 복원된 DSM을 대조하여 계층 침범, 순환 의존 등 침식 징후 식별.
  4. **아키텍처 규칙 코드화** : ArchUnit 테스트 스위트를 작성하여 위반 사항 발생 시 CI 빌드가 중단되도록 자동화.

## Ⅳ. 종류·비교

#### 아키텍처 침식(Erosion)의 대표 3대 유형 및 해결 방안

| 침식 유형 | 발생 메커니즘 및 징후 | 부작용 | 엔지니어링 해결 패턴 |
|---|---|---|---|
| **계층 건너뜀 (Skip Call)** | Controller 계층이 Service를 우회하여 DAO/Repository에 직접 쿼리 | 비즈니스 트랜잭션 및 유효성 검증 누락 | 엄격한 계층화(Strict Layering) 강제 |
| **역방향 호출 (Back Call)** | 하위 영속 계층(Repository)이 상위 프레젠테이션 계층 클래스를 참조 | 모듈 간 강결합으로 인한 독립 테스트 불가 | 의존성 역전 원칙(DIP) 적용, 인터페이스 분리 |
| **순환 참조 (Circular Dependency)**| Service A가 Service B를 참조하고, Service B가 다시 Service A를 참조 | 스프린트 빈 로딩 실패, 무한 루프, 배포 복잡도 | 이벤트 주도 아키텍처(EDA) 도입, 중재자 분리 |

#### DSM(Design Structure Matrix) 매트릭스 분석법

| 매트릭스 형태 | 구조적 의미 | 판정 및 조치 방안 |
|---|---|---|
| **하삼각 행렬 (Lower Triangular)** | 모든 의존성이 상위에서 하위로만 단방향으로 흐르는 이상적 계층 상태 | 아키텍처 무결성 완벽 유지 판정 |
| **상삼각 영역의 원소 출현** | 하위 모듈이 상위 모듈을 역참조하는 비정상 역방향 결합 발생 | DIP 기반 인터페이스 추출 및 리팩토링 |
| **대각선 대칭 원소 쌍 존재** | 모듈 간 상호 호출이 일어나는 순환 참조(Cycle) 상태 | 순환 고리를 끊는 중재자(Mediator) 컴포넌트 신설 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 정방향 설계 문서(SAD)가 프로젝트 초기 이후 최신 소스코드와 동기화되지 않고 사장화 | Markdown 기반 아키텍처 결정 기록(ADR)을 Git 저장소에 소스코드와 함께 버전 관리 |
| 역방향 분석 도구가 단순 클래스 호출만 분석하여 런타임 동적 리플렉션이나 DI 의존성을 놓침 | 런타임 분산 추적(OpenTelemetry) 및 바이트코드 분석 도구를 결합하여 동적 의존성 보완 |
| 대규모 레거시 시스템에서 수백 개의 아키텍처 위반이 한꺼번에 쏟아져 수정 불가능 | ArchUnit의 'Freezing Rule' 기능을 적용하여 기존 위반은 동결하고 신규 위반만 즉시 차단 |

## Ⅵ. 제언

소프트웨어 아키텍처 분석은 일회성 감리가 아닌 지속적 전달(CD) 파이프라인의 핵심 품질 게이트로 내재화되어야 하며, ArchUnit을 활용한 'Architecture-as-Code' 실천이 필수적임.

```text
[품질 시나리오 정립] ──> [기준 아키텍처 설계] ──> [ArchUnit 테스트 코드화] ──> [CI 파이프라인 자동 감사]
  (ATAM 정방향 분석)         (계층 & 의존 규칙 명시)       (Java DSL 아키텍처 단언)       (위반 시 PR 머지 차단)
```

| 거버넌스 영역 | 권장 실천 지침 | 핵심 관리 지표 |
|---|---|---|
| **규칙 코드화** | ArchUnit을 활용하여 계층 간 접근 금지 규칙 100% 코딩 | 패키지 간 비인가 의존성 0건 유지 |
| **순환 참조 척결** | JDepend / SonarQube 기반 패키지 순환 참조 정기 감사 | 패키지 간 순환 의존성(Cycles) 제로 달성 |
| **아키텍처 결정 보존**| 주요 설계 변경 시 아키텍처 결정 기록(ADR) 작성 의무화 | ADR 문서화율 100% 및 정방향 설계 이력 추적성 확보 |
