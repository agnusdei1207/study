## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 테스팅·품질 → 카오스 테스트(Chaos Test)

## 지식 위치

소프트웨어공학 > 신뢰성 시험 > 카오스 테스트

## 30초 인출

- 본질: 분산 시스템의 잠재적 취약점과 연쇄 장애 전파를 조기 발견하기 위해 운영 환경에 인위적 장애(인스턴스 종료, 네트워크 지연 등)를 통제된 상태로 주입하는 복원력(Resilience) 실험 기법
- 메커니즘: 시스템의 정상 상태(Steady State) 메트릭 정의 → 장애 발생 시에도 정상 상태를 유지할 것이라는 가설 수립 → 폭발 반경(Blast Radius) 최소화 및 장애 주입 → 가설 검증 및 자동 롤백
- 통찰: 안전장치 없는 무분별한 운영 환경 실험은 대형 서비스 중단을 초래하므로 비즈니스 핵심 지표(SLI/SLO) 기반 자동 중단 조건(Circuit Breaker)과 카나리 트래픽 격리 설계 필수

<details>
<summary>핵심 용어</summary>

- **카오스 엔지니어링 (Chaos Engineering)** : 프로덕션 환경의 가변적이고 예측 불가능한 장애 상황을 견딜 수 있는 시스템의 신뢰성을 확립하기 위한 실험 학문
- **정상 상태 (Steady State)** : 시스템이 평상시 정상 동작하고 있음을 나타내는 관측 가능한 비즈니스 메트릭 (예: 초당 결제 성공 수, P99 응답시간)
- **장애 주입 (Fault Injection)** : 파드(Pod) 강제 종료, CPU 과부하, 패킷 손실, 네트워크 파티션 등 시스템 장애 조건을 의도적으로 발생시키는 행위
- **폭발 반경 (Blast Radius)** : 카오스 실험에 의해 영향을 받을 수 있는 실제 고객 트래픽, 서비스 인스턴스, 데이터 영역의 물리적/논리적 범위
- **비상 중단 조건 (Abort Condition / Halt Button)** : 실험 중 에러율이 임계치를 초과하거나 SLA가 위협받을 때 장애 주입을 즉각 중지하고 시스템을 원복하는 자동화 안전장치
</details>

## 2~4교시 예상문제 (25점)

> 클라우드 네이티브 MSA 환경에서 시스템 신뢰성 확보를 위한 카오스 엔지니어링(Chaos Engineering)의 4대 원칙과 실험 절차를 설명하고, 프로덕션 환경 적용 시 폭발 반경(Blast Radius) 통제 및 복원력 향상 방안을 기술하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 분산 시스템이 예측 불가능한 인프라 장애나 네트워크 단절 상황에서도 복원력을 유지할 수 있는지 확인하기 위해 통제된 방식으로 실제 결함을 주입하는 선제적 실험 기법 |
| 목적 | 운영 환경에서의 숨겨진 단일 실패점(SPOF) 발굴, 서킷 브레이커 및 페일오버 자동화 검증, 대형 장애 발생 전 시스템 자가 복구(Self-Healing) 역량 입증 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 정상 상태(Steady State) 기반 가설 | 시스템 내부 상태(CPU 등)보다 외부 관측 비즈니스 지표(주문량, 스트리밍 성공률)를 기준선으로 설정 |
| 현실적인 장애 변수 모사 | 디스크 풀(Full), 네트워크 패킷 드롭, 다운스트림 서비스 타임아웃, 리전 단위 단절 등 실제 운영 사건 모의 |
| 프로덕션 환경 직접 실행 지향 | 스테이징 환경이 완전히 반영하지 못하는 실제 사용자 트래픽 및 백그라운드 부하 하에서 검증 수행 |
| 폭발 반경(Blast Radius) 통제 | 소수 사용자 또는 카나리 파드에서 시작하여 점진적으로 범위를 넓히는 안전 통제 수칙 준수 |

사후 수동 장애 대응(Post-Mortem)에서 사전 선제적 취약점 색출(Pre-Mortem)로 SRE 패러다임을 전환하는 핵심 도구.

## Ⅲ. 체계·프로세스

```text
[1. 정상 상태 정의 (Steady State)]
  - 핵심 비즈니스 메트릭 설정 (예: 초당 로그인 수, P95 지연 ≤ 300ms, 5xx 에러율 ≤ 0.1%)
       │
       ▼
[2. 복원력 가설 수립 (Hypothesis)]
  - "주문 DB 슬레이브 노드가 다운되어도 서킷브레이커와 캐시가 작동하여 정상 결제율 99%를 유지할 것이다"
       │
       ▼
[3. 폭발 반경 통제 및 비상 중단 조건 설정]
  - 실험 대상: 카나리 환경 5% 트래픽 한정
  - 자동 중단 룰: 5xx 에러율이 1% 초과 시 즉각 실험 중단 및 자동 롤백
       │
       ▼
[4. 통제된 장애 주입 실행 (Inject Fault)]
  - Chaos Mesh / LitmusChaos / Gremlin 도구를 통한 장애 주입
  - 인스턴스 킬, 지연 주입, 패킷 손실, 리소스 고갈
       │
       ▼
[5. 가설 검증 및 아키텍처 개선]
  - 정상 상태 메트릭 변동 관찰
  ├─ [가설 검증 성공] ──► 복원력 입증: 폭발 반경을 점진적 확대하여 재실험
  └─ [가설 반증/실패] ──► 비상 중단 트리거 가동 ──► 취약 구간(타임아웃, 재시도 폭풍) 식별 후 패치
```

정상 상태 정의, 가설 수립, 폭발 반경 제어, 장애 주입, 가설 검증 및 취약점 개선으로 이어지는 과학적 실험 프로세스.

## Ⅳ. 종류·비교

| 비교 항목 | 전통적 부하/기능 테스트 | 카오스 엔지니어링 (Chaos Test) |
|---|---|---|
| **검증 목적** | 시스템이 주어진 사양(기능/성능 요구사항)대로 동작하는지 확인 | 시스템이 예상치 못한 운영 장애를 견디고 자가 복구하는지 확인 |
| **수행 환경** | 개발계, 스테이징, QA 독립 테스트 환경 중심 | 스테이징 검증 후 실제 사용자 트래픽이 흐르는 프로덕션 환경 지향 |
| **테스트 시나리오** | 사전에 정의된 결정론적(Deterministic) 테스트 케이스 | 가설 기반의 비결정론적(Non-deterministic) 장애 주입 실험 |
| **주요 관측 대상** | 기능 결과의 정확성(Pass/Fail), 응답 시간, TPS | 비즈니스 정상 상태(Steady-State) 메트릭의 지속 유지 여부 |
| **수행 주체** | 소프트웨어 개발자, QA 엔지니어 | SRE(사이트 신뢰성 엔지니어), 아키텍트, 플랫폼 엔지니어 |

### 카오스 장애 주입 계층별 유형 비교

| 주입 계층 | 구체적 장애 주입 기법 | 검증 대상 복원력 메커니즘 |
|---|---|---|
| **인프라/하드웨어 계층** | VM/서버 인스턴스 전원 강제 차단, 디스크 용량 고갈, I/O 스로틀링 | 오토스케일링, 인스턴스 재기동, 스토리지 페일오버 |
| **네트워크 계층** | 패킷 유실(Drop), 네트워크 레이턴시 인위적 추가, DNS 해석 차단 | 커넥션 타임아웃, 지수 백오프 재시도, 서킷 브레이커 |
| **애플리케이션 계층** | JVM 가비지 컬렉션(Stop-the-World) 강제 유발, DB 커넥션 풀 고갈 | 큐잉 버퍼링, 대체 응답(Fallback), 벌크헤드(Bulkhead) 격리 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 실험 중 장애 전파 통제 실패로 인한 대규모 실제 고객 서비스 마비 사고 발생 | 폭발 반경(Blast Radius)을 서비스 1개 파드 또는 1% 미만 카나리 트래픽으로 극소화하고 실시간 비상 정지(Halt) 자동화 구축 |
| 사내 엔지니어링 조직의 실패에 대한 두려움과 심리적 저항감으로 도입 지연 | 비난 없는 포스트모템(Blameless Post-Mortem) 문화를 조성하고 스테이징 사전 실험(Game Day)을 통해 성공 경험 축적 |
| 비즈니스 정상 상태(Steady State)에 대한 명확한 관측성(Observability) 지표 부재 | Prometheus/Grafana 기반의 SLI(서비스 수준 지표)와 SLO(서비스 수준 목표) 대시보드를 선행 구축 |

## Ⅵ. 제언

프로덕션 환경 적용 전 조직적 훈련 행사인 '게임 데이(Game Day)'를 정기 개최하여 복구 런북(Runbook)을 검증하고, GitOps 및 배포 파이프라인에 지속적 카오스(Continuous Chaos)를 자동 통합 필요.

```text
[지속적 카오스 엔지니어링 파이프라인]
  배포 파이프라인 (Canary 10%) → Chaos Engine 기동 (네트워크 지연 주입) → SLO 지표 실시간 관측 → 이상 시 자동 롤백
```

| 검증 단계 | 사전 준비 단계 (Game Day) | 운영 자동화 단계 (Continuous Chaos) |
|---|---|---|
| 수행 방식 | 전 팀 참여 하에 수동 시나리오 실험 및 런북 튜닝 | 배포 파이프라인 내 카나리 장애 주입 자동 실행 |
| 복구 통제 | 엔지니어의 수동 롤백 및 모니터링 확인 | 서킷 브레이커 및 쿠버네티스 자가 복구 자동 판정 |
