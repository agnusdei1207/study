## Ⅰ. 카오스 테스트의 개요

- 개념 : **카오스 테스트** 란 대규모 분산 클라우드 시스템이 실제 운영 환경에서 예기치 못한 인프라 장애(서버 다운, 네트워크 지연, 디스크 고갈)를 겪더라도 비즈니스 서비스를 중단 없이 지속할 수 있는 **회복탄력성** (Resilience)을 갖추었는지를 검증하기 위해, 의도적으로 운영 환경에 혼돈(장애)을 주입하는 공학적 실험 기법(Chaos Engineering).
- 배경 및 필요성 : 복잡한 마이크로서비스(MSA, Microservice Architecture)와 멀티 리전 클라우드 환경에서는 부품의 장애가 '불가피(Inevitable)'하므로, '장애가 발생하지 않도록 막는 것'에서 '장애가 발생해도 시스템이 우아하게 견디도록(Fault-Tolerant) 설계하는 것'으로 패러다임 전환.
- 기원 : 넷플릭스(Netflix)의 **카오스 몽키** (Chaos Monkey) 및 **시미안 아미** (Simian Army)

## Ⅱ. 카오스 엔지니어링의 4단계 실험 원칙

```text
   [ 1단계: 정상 상태 정의 ] ──> [ 2단계: 가설 수립 ] ──> [ 3단계: 장애 변인 주입 ] ──> [ 4단계: 가설 검증 및 개선 ]
    - 시스템의 정상 메트릭         - "특정 서비스 파드가 다운     - 카오스 도구(Chaos Mesh)     - 비즈니스 지표 훼손 확인
      (Steady State) 측정           되어도 결제 성공률은           를 통해 파드 강제 종료,        - 서킷 브레이커, 타임아웃
      (예: 결제 TPS, 오류율)        99.9%를 유지할 것이다"        네트워크 패킷 50% 손실         아키텍처 보완
```

- **폭발 반경 최소화** (Minimize Blast Radius) : 실험이 실제 사용자에게 미치는 피해를 최소화하기 위해, 테스트 범위를 작게 시작하여 점진적으로 확장하며 비상 정지 스위치(Rollback Mechanism)를 반드시 확보.
- **실운영 환경에서의 실험** (Run Experiments in Production) : 스테이징 환경은 실제 트래픽 패턴과 완벽히 일치할 수 없으므로, 최종적으로는 프로덕션 환경에서 실험을 수행해야 진정한 신뢰성 입증 가능.

## Ⅲ. 전통적 장애 테스트와 카오스 엔지니어링의 비교

| 비교 항목 | 전통적 장애 테스트 (Disaster Recovery Test) | 카오스 엔지니어링 (Chaos Engineering) |
|---|---|---|
| 수행 방식 | 사전에 일정을 공지하고 모의 시나리오대로 수동 수행 | 무작위로 또는 자동화된 스케줄에 따라 지속적 수행 |
| 수행 환경 | 주로 격리된 별도 테스트 환경 또는 야간 점검 시간 | 실제 트래픽이 흐르고 있는 대낮의 실운영 환경 |
| 주요 관심사 | 시스템이 백업 복구 절차대로 복구되는가 | 시스템이 자동으로 장애를 흡수하고 정상 상태를 유지하는가 |
| 장애 주입 대상 | 특정 서버 전원 차단, 네트워크 케이블 분리 | 마이크로서비스 파드 사살, CPU(Central Processing Unit) 부하 주입, DNS(Domain Name System) 지연 |
| 대표 도구 | 수작업 스크립트, 데이터센터 DR(Disaster Recovery) 훈련 | Chaos Mesh, Gremlin, LitmusChaos, Chaos Toolkit |

## Ⅳ. 카오스 테스트(Chaos Test)의 주요 한계점 및 해결 방안

- 운영 환경 실험 시 통제 불능 연쇄 장애 및 폭발 반경(Blast Radius) 확산 :
  - 한계점 : 의도적인 네트워크 지연, 인스턴스 종료 실험이 데이터베이스 데드락, 결제 트랜잭션 오류 등 복구 불가능한 실제 고객 피해로 번질 위험.
  - 해결 방안 : 폭발 반경 최소화 전략 수립, 카나리 트래픽 대상 실험 격리, 비상 시 즉각 모든 장애 주입을 중단하는 자동 **데드맨 스위치** (Dead Man's Switch) 구현.
- **관측성** (Observability) 부재 시 장애 원인 규명 불가 및 가설 검증 실패 :
  - 한계점 : 정밀한 분산 추적과 실시간 메트릭이 갖춰지지 않은 상태에서 카오스 실험을 수행하면 시스템 붕괴 원인을 파악하지 못하고 혼란만 초래.
  - 해결 방안 : 실험 전 명확한 **정상 상태** (Steady State) 가설 정의, OpenTelemetry 및 Prometheus/Grafana 기반 지표가 연동된 Chaos Mesh/LitmusChaos 도구 활용.
- 장애 주입에 대한 조직적 불안감 및 심리적 저항 :
  - 한계점 : 프로덕션 환경에 장애를 일부러 주입한다는 개념에 대해 개발/운영팀과 경영진의 불신 및 거부감으로 제도 정착 실패.
  - 해결 방안 : 스테이징 환경에서 단계적 신뢰도 구축, 사전에 시나리오를 공유하고 협업하여 대응 훈련을 진행하는 게임데이(GameDay) 문화 조성.

## Ⅴ. 고가용성 클라우드 아키텍처를 위한 기술사적 제언

- **서킷 브레이커** (Resilience4j) 및 그레이스풀 데그라데이션(Graceful Degradation) 내재화 : 카오스 테스트 수행 전, 추천 서비스가 죽더라도 메인 결제는 정상 동작하도록 폴백(Fallback) 캐시를 반환하는 격리 아키텍처를 사전에 완벽히 구축해야 함.
- **GameDay** 정례화를 통한 조직의 장애 대응 역량 훈련 : 도구 도입에만 그치지 않고, 분기별로 무작위 장애를 주입하는 'GameDay'를 개최하여 개발팀과 SRE(Site Reliability Engineering) 팀이 실제 온콜(On-Call) 경보를 받고 MTTR(Mean Time to Repair, 평균 복구 시간)을 측정하며 관측성 모니터링 체계를 개선하는 훈련 정착 필수.
