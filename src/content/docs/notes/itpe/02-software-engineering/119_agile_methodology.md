## 연관 키워드

- 애자일(Agile), 애자일 선언문(Agile Manifesto), 애자일 방법론
- 스크럼(Scrum), XP(eXtreme Programming), 칸반(Kanban), 린(Lean), FDD(Feature-Driven Development)
- 이터레이션(Iteration), 스프린트(Sprint), 백로그(Backlog), TDD(Test-Driven Development), CI(Continuous Integration), 리팩토링
- 기술 부채, 좀비 애자일, 하이브리드 애자일, SAFe(Scaled Agile Framework), LeSS(Large-Scale Scrum), ART(Agile Release Train)

## Ⅰ. 애자일(Agile) 방법론의 개요

- 핵심 요약 : 짧은 반복과 지속적 피드백으로 가치를 증분 전달하는 사람 중심의 경량 개발 방법론군.
- 개념 : 불확실한 요구에 신속히 적응하기 위해 사전 계획과 방대한 문서 대신 작동하는 소프트웨어를 짧은 반복 주기로 인도하고 피드백으로 가치를 키워 나가는 **애자일 방법론** (Agile Methodology).
- 배경 및 필요성 : 폭포수(Waterfall) 모델의 긴 납기, 요구사항 변경 거부, 최종 인도 실패 위험이 누적되자 2001년 소프트웨어 개발 전문가들이 **애자일 선언문** (Agile Manifesto)을 발표하며 대안으로 부상.
- 주요 목적 : 고객 가치의 조기·지속적 전달, 요구사항 변경에 대한 적응력 확보, 팀 자율성과 협업 강화.
- 대표 프레임워크
  1. **스크럼** (Scrum, 스프린트 단위로 역할과 이벤트를 정의한 프레임워크)
  2. **XP** (eXtreme Programming, 익스트림 프로그래밍)
  3. **칸반** (Kanban, 작업 흐름을 시각화하고 진행 중 작업량을 제한하는 방식)
  4. **린** (Lean, 낭비 제거를 중심으로 한 생산 철학)
  5. **FDD** (Feature-Driven Development, 기능 단위로 설계와 구현을 반복하는 방식)

## Ⅱ. 애자일(Agile) 방법론의 특징 및 장점

- 핵심 요약 : 경험주의에 기반한 짧은 반복, 고객 협력, 변화 수용이 빠른 가치 전달과 낮은 손실로 이어지는 개발 체계.

1. 짧은 반복 주기 : 1개월 이하의 **이터레이션** (Iteration, 반복 개발 단위)마다 동작하는 증분을 인도 → 잘못된 방향의 손실 기간 단축.
2. 요구사항 변경 수용 : 매 반복 시작 시 백로그를 재정렬 → 시장 변화에 맞춘 우선순위 조정이 용이.
3. 지속적 피드백과 고객 협력 : 반복 종료 시점에 고객이 결과를 직접 확인 → 요구 오해를 조기에 발견.
4. 자기 조직화 팀 : 팀이 작업 분배와 세부 의사결정을 자율적으로 수행 → 의사결정 대기 시간 감소.
5. 기술 실천 체계 : XP의 **TDD** (Test-Driven Development, 테스트 주도 개발), 짝 프로그래밍, **CI** (Continuous Integration, 지속적 통합), 리팩토링 → 결함의 조기 발견과 설계 품질 유지.
6. 정기 회고 : 반복이 끝날 때마다 프로세스를 점검 → 다음 반복의 개선 사항을 즉시 반영.

## Ⅲ. 애자일(Agile) 방법론의 구조 (흐름)

- 핵심 요약 : 백로그에서 출발해 계획·개발·리뷰·회고를 거쳐 릴리스로 이어지는 반복 순환 구조.
- **스프린트** (Sprint, 고정 기간의 개발 반복 단위) : 계획, 개발, 리뷰, 회고를 한 주기에 포함하며 통상 1~4주로 운영.

```text
[ 스프린트 순환 흐름 ]

제품 백로그 (Product Backlog)
            ↓
스프린트 계획 (Sprint Planning)
            ↓
개발·테스트 (TDD, 짝 프로그래밍, CI)
            ↓
스프린트 리뷰 (Sprint Review)
            ↓
회고 (Retrospective)
            ↓
릴리스 후 백로그 재정렬 → 다음 스프린트
```

```text
[ 애자일 방법론의 계층 ]

애자일 선언문 (가치와 원칙)
            ↓
개별 방법론 (팀 단위)
  스크럼 · XP · 칸반 · 린 · FDD
            ↓
대규모 확장 (다수 팀 정렬)
  SAFe · LeSS
```

## Ⅳ. 폭포수(Waterfall) 모델과의 비교

- 핵심 요약 : 초기에 범위를 고정하는 계획 주도 방식과 반복마다 적응하는 방식의 대비.

| 비교 항목 | 폭포수 모델 (Waterfall) | 애자일 방법론 (Agile) |
| --- | --- | --- |
| 계획 수립 방식 | 초기 단계에 전체 범위와 일정을 고정 (Predictive) | 반복 주기마다 점진적으로 계획 수립 (Adaptive) |
| 요구사항 변경 | 변경통제위원회(CCB, Change Control Board) 승인을 거쳐 변경 억제 | 경쟁 우위를 위해 후반부 변경도 수용 |
| 릴리스 주기 | 개발 완료 후 최종 단계에 일괄 릴리스 | 1~4주 단위로 동작 가능한 증분을 지속 릴리스 |
| 고객 참여 | 제안요청서(RFP) 단계와 인수 단계에 주로 참여 | 매 스프린트 리뷰에서 직접 시연을 보고 피드백 |
| 위험 관리 | 통합·인수 단계인 후반부에 위험이 집중 | 매 반복의 테스트·배포로 위험을 조기에 해소 |

## Ⅴ. 애자일(Agile) 방법론의 장점과 한계

- 핵심 요약 : 빠른 가치 전달과 적응성이라는 장점 이면에, 고정 계약과의 충돌, 기술 부채 누적, 형식화의 한계가 존재.
- 장점 : 고객 가치의 조기 전달, 변경 대응력, 반복마다의 위험 조기 해소, 팀 자율성과 협업 문화 강화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 고정 계약과의 충돌 | 범위·예산·납기가 착수 시 확정되는 발주에서는 지속적 범위 변동을 수용하기 어려움 | 분석·설계는 확정하고 개발·테스트는 반복으로 진행하는 **하이브리드 애자일** (Hybrid Agile) 적용 | 계약 변경 승인에 걸리는 기간 |
| **기술 부채** (Technical Debt) 누적 | 즉각적인 사용자 가치 인도에 매몰되어 아키텍처 확장성과 비기능 요구(성능·보안)가 방치 | 아키텍처 스파이크(Spike)를 스프린트에 정식 포함하고 주기적으로 **하드닝 스프린트** (Hardening Sprint, 부채 해소 전담 반복) 운영 | 기술 부채 해소 건수 |
| **좀비 애자일** (Zombie Agile) | 심리적 안전성 (psychological safety)이 없어 일일 스크럼과 회고가 실적 보고·감시 도구로 변질 | 스크럼 마스터(Scrum Master)의 코칭 강화, 비난 없는 회고(Blameless Retrospective) 정착 | 팀 만족도 설문 점수 |

## Ⅵ. 애자일(Agile) 방법론에 대한 기술사적 제언

- 핵심 요약 : 형식을 따르는 'Doing Agile'에서 자율과 신뢰에 기반한 'Being Agile'로 조직 문화를 바꾸고, 대규모 프레임워크로 팀 간 방향을 맞출 것.
- 조직 문화 : 일일 스크럼과 칸반 보드를 갖추는 데서 멈추지 않도록, 경영진이 실패를 학습 기회로 인정하는 평가 체계를 먼저 마련하고 팀 리더에게 의사결정 권한을 위임하는 것이 출발점이다.
- 대규모 정렬 : 수백 명이 참여하는 공공·금융 프로젝트라면 SAFe의 ART와 PI(Program Increment, 프로그램 증분) 주기로 사업 목표와 릴리스 계획을 동기화하는 방식을 검토할 만하다.
- 계약 제도 : 발주 측이 범위 확정 방식을 유지하는 한 하이브리드 방식의 한계가 남으므로, 가변 범위 계약의 도입 가능성을 발주 기관과 함께 논의하는 것이 현실적이다.

## Ⅶ. 결론

- 핵심 요약 : 애자일은 짧은 반복과 지속적 피드백으로 가치를 증분 전달하는 적응형 개발 체계.
- 애자일의 본질은 의식과 도구가 아니라 학습 속도에 있으며, 계약 방식과 조직 문화가 함께 뒷받침될 때 그 효과가 지속된다.
