## 연관 키워드

- Agile, 애자일, 애자일 선언문(Agile Manifesto)
- Scrum, XP(eXtreme Programming), Kanban, Lean, FDD
- Iteration, Sprint, 백로그, TDD, CI, 리팩토링

## Ⅰ. 애자일(Agile) 방법론의 개요

- 핵심 요약 : 짧은 반복 주기와 지속적 피드백으로 가치를 증분 전달하는 사람 중심 경량 개발 방법론군.
- 개념 : **애자일 방법론** 이란 소프트웨어 개발의 불확실성과 급변하는 비즈니스 요구에 신속하게 적응하기 위해 엄격한 사전 계획과 방대한 문서 작성 대신 작동하는 소프트웨어를 짧은 반복 주기(Iteration)로 고객에게 전달하고 지속적인 피드백을 통해 가치를 증분해 나가는 사람 중심의 경량(Lightweight) 개발 방법론군.
- 배경 및 필요성 : 1990년대 대규모 폭포수 모델의 긴 납기, 요구사항 변경 거부, 최종 인도 실패 리스크를 극복하기 위해 2001년 17명의 소프트웨어 공학 리더들이 **애자일 선언문** (Agile Manifesto)을 발표하며 태동.
- 주요 목적 : 고객 가치의 조기·지속적 전달, 요구사항 변경에 대한 적응성 확보, 팀 자율성과 협업 강화.
- 대표 프레임워크
  1. 스크럼(Scrum)
  2. XP(eXtreme Programming)
  3. 칸반(Kanban)
  4. 린(Lean)
  5. FDD(Feature-Driven Development)

## Ⅱ. 애자일(Agile) 방법론의 특징

- 핵심 요약 : 경험주의 기반의 짧은 반복, 고객 협력, 변화 수용을 핵심 속성으로 하는 개발 체계.
1. **애자일 선언문 4대 가치** : 개인과 상호작용, 작동하는 소프트웨어, 고객과의 협력, 변화에 대응하기 (좌측 가치도 존중하되 우측 가치에 더 높은 우선순위).
2. **12대 실행 원칙**
   1. 조기·지속적 인도
   2. 요구사항 변경 환영
   3. 짧은 주기 전달
   4. 업무·개발자 협력
   5. 동기 부여된 개인
   6. 직접 대화
   7. 작동 소프트웨어
   8. 지속 가능한 개발
   9. 기술적 우수성
   10. 단순성
   11. 자기 조직화 팀
   12. 정기적 회고
3. **XP 5대 가치** : **의사소통** (Communication), **단순성** (Simplicity), **피드백** (Feedback), **용기** (Courage), **존중** (Respect).
4. **XP 핵심 실천법**
   1. TDD(Test-Driven Development, 테스트 주도 개발)
   2. 짝 프로그래밍(Pair Programming)
   3. 지속적 통합(CI, Continuous Integration)
   4. 리팩토링
   5. 작은 릴리스
   6. 메타포어
   7. 주 40시간 작업
5. **사람 중심·경량 프로세스** : 문서보다 작동 소프트웨어, 계획보다 변화 대응 우선.

## Ⅲ. 애자일(Agile) 방법론의 구조 (흐름)

- 핵심 요약 : 백로그→스프린트 계획→개발·테스트→리뷰→회고→릴리스의 반복 순환 구조.
- 스프린트 기반 반복 개발 흐름.

```text
[ 애자일 스프린트 순환 흐름 ]
제품 백로그 (Product Backlog)
        ↓
스프린트 계획 (Sprint Planning)
        ↓
개발·테스트 (1~4주 Iteration)
  - TDD, 짝 프로그래밍, CI
        ↓
스프린트 리뷰 (Sprint Review) ── 고객 피드백
        ↓
회고 (Retrospective)
        ↓
릴리스 (Release) ──┐
        ↑          │
        └──────────┘  (다음 스프린트)
```

```text
[ 애자일 선언문 4대 가치 우선순위 ]
1. 개인과 상호작용 (공정과 도구보다)
2. 작동하는 소프트웨어 (포괄적 문서보다)
3. 고객과의 협력 (계약 협상보다)
4. 변화에 대응하기 (계획 따르기보다)
```

## Ⅳ. 폭포수(Waterfall) 모델과의 비교

- 핵심 요약 : 계획 주도(Predictive) 방식과 적응형(Adaptive) 방식의 대비.
- 계획 수립, 요구사항 변경, 릴리스 주기, 고객 참여, 위험 관리 축 비교.

| 비교 항목 | 폭포수 방법론 (Waterfall) | 애자일 방법론 (Agile) |
|---|---|---|
| 계획 수립 방식 | 초기 단계에 고정된 전체 범위와 일정 수립 (Predictive) | 경험주의에 기반하여 반복 주기마다 점진적 계획 수립 (Adaptive) |
| 요구사항 변경 | 엄격한 CCB 승인 절차를 거쳐 변경 억제 | 경쟁 우위 확보를 위해 후반부 변경도 적극 환영 |
| 릴리스 주기 | 개발 완료 후 최종 단계에 일괄 릴리스 (Big-Bang) | 1~4주 단위로 동작 가능한 소프트웨어 증분 지속 릴리스 |
| 고객 참여 방식 | 착수(RFP)와 종료(인수) 단계에 주로 참여 | 매 반복(스프린트 리뷰)마다 고객이 직접 시연 확인 및 피드백 |
| 위험 관리 형태 | 통합 및 인수 단계인 프로젝트 후반부에 위험 집중 | 매 이터레이션마다 테스트 및 배포로 위험을 조기에 해소 |

## Ⅴ. 애자일(Agile) 방법론의 장점과 한계

- 핵심 요약 : 빠른 가치 전달과 적응성의 장점, 고정 계약 충돌과 기술 부채 누적의 한계.
- 장점
  1. 고객 가치의 조기 전달과 지속적 피드백 반영.
  2. 요구사항 변경에 대한 높은 적응성.
  3. 매 이터레이션마다 위험 조기 해소.
  4. 팀 자율성과 협업 문화 강화.
- 한계점 1 : 전통적 공공·금융 고정 계약(Fixed Scope/Budget) 제도와의 충돌
  - 한계점 : 사업 착수 시점에 전체 범위와 예산, 납기가 확정되는 발주 환경에서 지속적으로 범위가 변동되는 애자일 방식을 전면 적용하기 어려움.
  - 해결 방안 : 분석·설계는 확정하고 개발·테스트는 반복 점진으로 진행하는 **하이브리드 애자일** (Water-Scrum-Fall) 적용, 공공 가변 범위 계약 모델 제도화 유도.
- 한계점 2 : 단기 스프린트 반복에 따른 아키텍처 진화 미흡 및 **기술 부채** 누적
  - 한계점 : 매 스프린트마다 즉각적인 사용자 가치 인도에 매몰되어 전사 아키텍처 확장성, 비기능 요구사항(성능/보안) 및 대규모 리팩토링이 방치됨.
  - 해결 방안 : 아키텍처 스파이크(Spike) 활동 스프린트 정식 포함, 4~5개 스프린트마다 기술 부채 해소를 전담하는 하드닝 스프린트(Hardening Sprint) 정례화.
- 한계점 3 : 형식적 의식(Ceremony)만 남는 '**좀비 애자일** (Zombie Agile)' 변질
  - 한계점 : 팀의 자율성과 심리적 안전감이 결여된 상태에서 일일 스크럼, 회고가 단순 실적 보고 및 감시 도구로 변질되어 개발자 피로도 급증.
  - 해결 방안 : 전문 애자일 코치(Scrum Master) 배치, 블레임리스(Blameless) 회고 문화 정착 및 팀 자율 의사결정 권한의 제도적 보장.

## Ⅵ. 애자일(Agile) 방법론에 대한 기술사적 제언

- 핵심 요약 : 'Doing Agile'에서 'Being Agile'로의 조직 문화와 대규모 프레임워크 정렬.
- 'Doing Agile'에서 'Being Agile'로의 조직 문화 체질 개선 : 단순히 스크럼 이벤트(일일 스크럼, 지라 보드)를 형식적으로 흉내 내는 '행위로서의 애자일'을 탈피하고, 실패를 용인하고 심리적 안전감을 바탕으로 자율적으로 의사결정하는 '사고방식으로서의 애자일'로 전사 문화 혁신.
- 대규모 애자일 프레임워크인 SAFe(Scaled Agile Framework)와 LeSS(Large-Scale Scrum) 기반 포트폴리오 정렬 : 수백 명의 개발자가 참여하는 공공/금융 엔터프라이즈 환경에서는 개별 스크럼 팀의 파편화를 방지하기 위해 SAFe의 ART(Agile Release Train)와 PI(Program Increment) 기법을 도입하여 비즈니스 전략과 개발 릴리스를 동기화 필요.

## Ⅶ. 결론

- 핵심 요약 : 애자일은 짧은 반복과 지속적 피드백으로 가치를 증분 전달하는 적응형 개발 체계.
- 요약 : 애자일 방법론은 불확실한 환경에서 고객 가치를 조기에·지속적으로 전달하기 위한 경험주의 기반 개발 체계.
- 시사점 : 고정 계약·기술 부채·형식화 리스크를 관리하면서 조직 문화와 대규모 프레임워크를 정렬해야 지속 가능한 성과 확보.
