## 한 줄 본질
- 소프트웨어 동작을 실행 순서대로 함수(프로시저)로 묶어 처리함으로써 프로그램이 무엇을 해야 하는지 직관적으로 구현하는 전통적 프로그래밍 패러다임 / 데이터 구조가 바뀌면 모든 관련 함수를 뜯어고쳐야 하는 유지보수 취약성

## 핵심 용어
- 프로시저(Procedure): 특정 작업을 수행하기 위해 정해진 순서대로 실행되는 일련의 명령어 집합(서브루틴 또는 함수)으로, 반환값이 없거나 상태를 직접 변경함
- 구조적 프로그래밍 정리(Böhm-Jacopini Theorem): 모든 프로그램 알고리즘은 오직 '순차(Sequence)', '선택(Selection: if-else)', '반복(Iteration: while/for)' 3가지 기본 제어 구조만으로 완벽히 표현될 수 있다는 정리

## 핵심 통찰
- 절차지향(Procedural)의 "절차"는 단순한 1, 2, 3번의 시간적 순서(Sequence)만을 의미하는 것이 아니라, "프로시저(Procedure, 함수)"를 소프트웨어의 기본 빌딩 블록으로 삼는다는 뜻임
- 절차지향은 하드웨어 머신 구조(폰 노이만 아키텍처: 메모리에서 읽어와 순차 연산 후 저장)와 가장 직접적으로 매핑되므로, 가상머신이나 가상함수 테이블(vtable) 오버헤드가 없어 실행 속도와 메모리 효율이 극대화됨
- 리눅스 커널(Linux Kernel)이나 임베디드 펌웨어가 여전히 C 언어 기반의 절차지향으로 작성되는 이유는 하드웨어 레지스터를 1:1로 직접 제어할 수 있는 결정론적(Deterministic) 성능 때문임

## 이웃 토픽과 구분
- 절차지향(POP) vs 객체지향(OOP): POP = "동사(기능)" 중심 설계, 데이터가 함수 사이를 흘러 다님 / OOP = "명사(객체)" 중심 설계, 데이터와 기능을 하나로 묶어 메시지를 주고받음

## 문제·원인·대책
- 적용 상황: 대규모 레거시 C 기반 통신 스위칭 제어 소프트웨어
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 통신 패킷 구조체에 필드 하나를 추가했더니 수백 개의 C 소스 파일에서 동시다발 컴파일 에러 | 데이터와 로직이 분리되어 구조체 변경이 전체 프로시저에 파급되는 구조적 결함 | 데이터 접근을 전담하는 불투명 포인터(Opaque Pointer) 기법으로 캡슐화 모사 | 헤더 종속성 격리 및 변경 파급도 차단 |
| 수십만 줄의 절차지향 C 코드에서 포인터 오염으로 인한 원인 불명의 간헐적 메모리 크래시 | 전역 변수 남용 및 함수 간 메모리 직접 참조로 인한 사이드 이펙트 추적 불가 | 정적 분석 도구(Coverity) 연계 및 순수 함수(Pure Function) 기반으로 리팩토링 | 잠재 메모리 오염 결함 90% 제거 |

## 이렇게 출제된다
- 제125회 1교시: "절차지향 프로그래밍(POP)과 객체지향 프로그래밍(OOP)의 특징 및 장단점을 비교 설명하시오." → 요구 포인트: POP 정의 및 3대 제어 구조 + OOP 4대 특성(캡슐화, 상속, 다형성, 추상화) + 상호 장단점 비교표

## 내 의견
- [패러다임의 우열 논쟁을 넘어선 적재적소 엔지니어링] 절차지향은 낡은 것이고 객체지향만 최신이라는 이분법적 편견으로 임베디드나 초고속 엔진에 무거운 객체 구조를 억지로 도입하여 성능을 낭비하는 사례 발생 → 나라면: 비즈니스 규칙이 복잡하고 유지보수가 잦은 엔터프라이즈 도메인은 객체지향(OOP/DDD)을 채택하되, 초저지연 연산이 핵심인 데이터 패킷 처리 엔진이나 하드웨어 디바이스 드라이버 계층에는 가볍고 빠른 절차지향 C/Rust 구조를 유지하는 하이브리드 아키텍처 전략 고수
