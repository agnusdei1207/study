## 연관 키워드

- 소프트웨어 아키텍처 분석, 정방향 분석, 역방향 분석, 설계-구현 일치성
- 아키텍처 침식, DSM(설계 구조 행렬), 피트니스 함수, ArchUnit

## Ⅰ. 소프트웨어 아키텍처 분석의 개요

- 핵심 요약 : 소프트웨어 아키텍처 분석은 설계 산출물과 소스 코드 사이에서 구조·의존성을 추적·추출해 설계 의도와 실제 구현의 일치 여부를 평가하는 활동.
- 개념 : 설계 문서와 소스 코드 사이에서 아키텍처 구조·의존성을 추적·추출해 설계 의도와 실제 구현의 일치를 평가하는 활동(**소프트웨어 아키텍처 분석**, Software Architecture Analysis). 설계에서 코드로 내려가는 **정방향 분석**(Forward Analysis)과 코드에서 구조를 복원하는 **역방향 분석**(Reverse Analysis)의 두 방향으로 구분.
- 배경 및 필요성 : 반복 변경과 문서 갱신 지연으로 설계와 코드의 괴리가 누적되고, 레거시 시스템은 대응 문서가 없어 실제 구조 파악 수단 필요.
- 주요 목적 : 설계-구현 일치성 검증, 레거시 구조의 실체 파악, 변경 용이성 등 구조 품질 개선의 기반 확보.

## Ⅱ. 소프트웨어 아키텍처 분석의 특징 및 장점

- 핵심 요약 : 정방향 추적·역방향 복원·정량 지표·자동 검증이 구조 품질의 객관적 관리로 연결.

1. 정방향 추적 : 설계 문서의 구성 요소를 코드 수준 대응물과 연결 → 설계 의도의 구현 반영 여부 확인.
2. 역방향 복원 : 소스 코드 파싱으로 구성 요소·의존성을 추출해 구조 모델 생성 → 문서가 없는 레거시의 실체 파악.
3. 정량 지표 활용 : 추출된 의존성을 **DSM**(Design Structure Matrix, 설계 구조 행렬)으로 정리하고 **마틴 메트릭스**(Robert C. Martin의 결합·추상성 지표군)로 평가 → 구조 품질의 수치화.
4. 자동 검증 : **피트니스 함수**(아키텍처 규칙을 코드로 검증하는 테스트)와 ArchUnit 같은 규칙 테스트 도구 → **아키텍처 침식**(Architectural Erosion, 반복 변경으로 설계에서 벗어나는 현상)의 상시 감시.
5. 정적·동적 병행 : 컴파일 타임 의존성 분석과 런타임 호출 추적의 조합 → 구조의 다층 파악.

## Ⅲ. 소프트웨어 아키텍처 분석의 구조 (흐름)

- 핵심 요약 : 정방향의 설계→코드 추적 절차와 역방향의 코드→구조 복원 절차가 한 쌍으로 일치성을 검증하는 구조.

```text
설계 문서·아키텍처 모델
   ↓ 구성 요소 매핑
코드 수준 대응 확인
   ↓
설계-구현 일치성 평가
   ↓
위반·누락 항목 시정
```

```text
소스 코드 파싱
   ↓
구성 요소·의존성 추출
   ↓
구조 모델 복원
   ↓
DSM·의존 그래프 시각화
   ↓
실제 구조 평가·문서화
```

## Ⅳ. 정방향 분석과 역방향 분석의 비교

- 핵심 요약 : 정방향 분석은 설계 의도의 이행 검증, 역방향 분석은 실제 구조의 복원에 강점인 상호 보완 관계.

| 비교 축 | 정방향 분석 | 역방향 분석 |
| --- | --- | --- |
| 출발점 | 설계 문서·아키텍처 모델 | 소스 코드·실행 이력 |
| 얻는 결과 | 설계 의도의 구현 일치성 | 실제 구조·의존성의 복원 |
| 주 활용 시점 | 개발·변경 적용 단계 | 레거시 인수·유지보수 단계 |
| 문서 의존도 | 대응 문서의 최신성에 의존 | 문서 부재 상황에서도 수행 |
| 본질적 한계 | 구형 문서면 왜곡된 판정 | 설계 근거·의도는 복원 불가 |
| 주요 수단 | 추적성 매트릭스·규칙 테스트 | 파싱·DSM·의존 그래프 |

## Ⅴ. 소프트웨어 아키텍처 분석의 한계와 방안

- 핵심 요약 : 침식 재발·동적 의존성 누락·해석 주관성·추출 누락을 CI 검증·동적 추적·공통 기준·교차 검증으로 관리.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 침식 재발 | 급한 변경의 구조 규칙 위반 누적 → 분석 기준 상실 | 피트니스 함수·ArchUnit 규칙의 CI 상시 검증 | 규칙 위반 수 |
| 동적 의존성 미반영 | 정적 분석만으로 런타임 구조 누락 → 장애 전파·병목 파악 실패 | 실행 추적·로그 기반 동적 의존성 병행 | 미확인 런타임 의존성 |
| 해석의 주관성 | 도구·관점에 따른 구조 해석 차이 → 결론 불일치 | DSM·지표 등 정량 기준의 문서화·공유 | 평가자 간 지표 편차 |
| 추출 누락 | 리플렉션·동적 로딩 등으로 구성 요소 누락 → 단순화된 구조 | 복수 도구의 교차 검증·전문가 검토 | 추출 누락 건수 |

## Ⅵ. 소프트웨어 아키텍처 분석 적용에 대한 기술사적 제언

- 핵심 요약 : 상시 검증 게이트·결정 기록 체계·표준 분석 절차로 정방향·역방향 분석을 개발 수명 주기에 내재화.
- 상시 검증 게이트 : 개발 조직은 아키텍처 규칙 테스트를 코드 리뷰·CI 파이프라인에 통합해 침식을 조기 차단하는 체계 운영.
- 결정 기록 체계 : 아키텍트는 구조 결정을 **아키텍처 결정 기록** (ADR, Architecture Decision Record)으로 문서화해 정방향 추적의 판단 기준 유지.
- 표준 분석 절차 : 유지보수 조직은 시스템 인수 단계에서 역방향 분석을 표준 절차로 수행해 실제 구조의 문서화 의무화.

## Ⅶ. 결론

- 핵심 요약 : 정방향·역방향 분석은 설계 의도와 실제 구조를 상호 검증하는 짝 활동.
- 두 방향의 순환 수행으로 설계-구현 일치성이 유지되고, 이것이 변경 용이성과 시스템 품질의 토대가 되는 구조.
