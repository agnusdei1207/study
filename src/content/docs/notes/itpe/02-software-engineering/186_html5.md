## 연관 키워드

- HTML5(HyperText Markup Language 5), 시맨틱 태그(Semantic Tag), 웹 스토리지(Web Storage), 쿠키(Cookie), IndexedDB, WHATWG(Web Hypertext Application Technology Working Group)
- 캔버스(Canvas), 웹소켓(WebSocket), WebRTC(Web Real-Time Communication), 웹 워커(Web Worker), 서비스 워커(Service Worker), 폴리필(Polyfill), 기능 감지(Feature Detection), 점진적 향상(Progressive Enhancement), XSS(Cross-Site Scripting), CSP(Content Security Policy)

## Ⅰ. HTML5의 개요

- 핵심 요약 : 시맨틱 마크업과 멀티미디어·그래픽·저장·통신 API를 플러그인 없이 표준화한 HTML 개정 버전.
- 개념 : 문서 구조, 멀티미디어, 웹 API(Application Programming Interface)를 확장한 **HTML5**(HyperText Markup Language 5) 표준. 현재 HTML 명세는 **WHATWG**(Web Hypertext Application Technology Working Group)가 관리하는 Living Standard이며, W3C(World Wide Web Consortium)는 2014년 HTML5 권고안(Recommendation)을 발행함.
- 배경 및 필요성 : 비표준 플러그인(예: Adobe Flash)은 보안 취약점과 호환성 문제를 낳고, 모바일 브라우저는 플러그인 지원이 제한적이어서 표준 기술만으로 문서·미디어·앱 기능을 통합할 필요가 커짐.
- 주요 목적 : 플러그인 없이 동작하는 크로스 플랫폼 웹 애플리케이션 표준 확립과 의미 기반 문서 구조 구현.

## Ⅱ. HTML5의 특징 및 장점

- 핵심 요약 : 플러그인 없이 시맨틱·미디어·그래픽·저장·통신 기능을 표준 API로 제공해 호환성과 접근성을 높이는 구조.

1. **시맨틱 태그**(Semantic Tag) : `header`, `nav`, `main`, `article`, `footer` 등 의미 있는 요소로 문서 구조를 명시 → 검색 엔진 최적화(SEO, Search Engine Optimization)와 스크린 리더의 구조 탐색 개선.
2. 멀티미디어 : `audio`, `video` 요소가 브라우저 내장 디코더로 재생 → 플러그인 설치 없이 미디어를 재생하고 재생 제어를 표준화.
3. 그래픽 : **캔버스**(Canvas)로 2D 그리기, SVG(Scalable Vector Graphics)로 벡터 그래픽, WebGL로 3D 렌더링 → 플러그인 없이 대화형 시각화 구현.
4. 저장 : **웹 스토리지**(Web Storage)와 **IndexedDB**로 데이터를 클라이언트에 보관 → 네트워크 단절 상황에서도 입력 상태와 데이터를 유지하는 오프라인 대응의 기반.
5. 실시간 통신 : **웹소켓**(WebSocket)의 전이중(full-duplex) 연결과 **WebRTC**(Web Real-Time Communication)의 P2P(Peer-to-Peer) 미디어 전송 → 반복 요청(폴링) 부담을 줄이고 지연을 낮춤.
6. 백그라운드 처리 : **웹 워커**(Web Worker)로 무거운 연산을 별도 스레드에서 수행하고, **서비스 워커**(Service Worker)로 요청 가로채기와 캐시를 처리 → 메인 화면의 반응성 확보와 오프라인 동작 기반 마련.

## Ⅲ. HTML5의 구조 (흐름)

- 핵심 요약 : 6개 기능 축을 API 계층으로 묶어 브라우저 엔진 위에 올리는 웹 애플리케이션 플랫폼 구조.
- 시맨틱 구조 : `<div id="header">` 대신 `header`, `nav`, `section`, `article`, `aside`, `footer`를 쓰면 문서의 논리 구조가 드러나 검색 엔진과 보조 기술의 해석이 쉬워짐.
- 웹 스토리지 : 키-값 문자열을 브라우저에 보관하며, **쿠키**(Cookie)와 달리 HTTP(Hypertext Transfer Protocol) 요청에 자동 첨부되지 않음. 용량과 삭제 정책은 브라우저와 저장 모드에 따라 다르고, 한도 초과 시 QuotaExceededError 예외 처리 필요.

```text
[ 웹 애플리케이션 ]
        ↓ JavaScript 호출
[ HTML5 API 계층 ]
   저장 · 통신 · 그래픽 · 워커
        ↓
[ 브라우저 엔진 ]
        ↓
[ 운영체제·하드웨어 ]
```

```text
[ 메인 스레드 ]
  UI 렌더링·이벤트 처리
        ↓ postMessage로 작업 전달
[ 웹 워커 ]
  대용량 연산·데이터 파싱
        ↓ 결과 메시지 회신
[ 메인 스레드 ]
  화면 갱신
```

## Ⅳ. 클라이언트 웹 저장소 기술의 비교

- 핵심 요약 : 서버 자동 전송 여부, 수명, 데이터 형태에 따라 쿠키와 웹 스토리지, IndexedDB의 용도가 나뉨.

```text
[ 쿠키 ]
  브라우저 → 조건에 맞는 요청마다
            HTTP 헤더에 자동 첨부

[ 웹 스토리지 ]
  JavaScript 코드가 명시적으로 읽고 씀
  → 서버 자동 전송 없음
```

| 비교 축 | 쿠키(Cookie) | localStorage | sessionStorage | IndexedDB |
| --- | --- | --- | --- | --- |
| 서버 자동 전송 | 조건에 맞는 HTTP 요청에 자동 첨부 | 자동 첨부 없음 | 자동 첨부 없음 | 자동 첨부 없음 |
| 저장 형식 | 문자열 | 문자열(키-값) | 문자열(키-값) | 구조화 객체, 트랜잭션 기반 |
| 수명 | 만료 시점 또는 세션 종료까지, 사용자 삭제 가능 | 명시 삭제 전까지 유지 | 탭(세션) 종료까지 유지 | 명시 삭제 전까지, 브라우저 정책에 따라 축출 가능 |
| 용량 | 브라우저별 제한 | 브라우저·환경별 한도 | 브라우저·환경별 한도 | 디스크 기반 할당량, 브라우저 정책 적용 |
| 주 활용 | 세션 ID, 자동 로그인 토큰 | 테마·설정 값 | 일회성 입력 상태 | 대용량 오프라인 데이터, 복합 조건 조회 |

- 선택 기준 : 서버가 매 요청에서 알아야 하는 값은 쿠키로, 클라이언트에서만 쓰는 구조화 데이터는 IndexedDB로 나누는 것이 기본.

## Ⅴ. HTML5의 한계와 방안

- 핵심 요약 : 브라우저 편차, 저장소 노출, 메모리 관리의 한계를 기능 감지, 보안 설계, 생명주기 관리로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 브라우저 간 API 편차 | 웹 워커·웹소켓·미디어 API의 구현과 성능이 엔진(Blink, WebKit, Gecko)별로 달라 기능 오작동 발생 | **폴리필**(Polyfill) 주입, **기능 감지**(Feature Detection) 후 **점진적 향상**(Progressive Enhancement) 설계 | 브라우저별 오류 발생률 |
| **XSS**(Cross-Site Scripting) 피해 | 저장소는 JavaScript로 접근 가능해 XSS 성공 시 인증 토큰(JWT, JSON Web Token)과 민감 정보가 즉시 탈취될 위험 | `HttpOnly`·`Secure`·`SameSite` 속성의 쿠키 사용, 출력 인코딩, **CSP**(Content Security Policy) 적용, 민감 정보의 클라이언트 저장 최소화 | 민감 정보의 로컬 저장 건수 |
| 메모리 누수 | `<canvas>`, WebGL, Web Audio 객체를 반복 생성하고 해제하지 않으면 탭 메모리가 급증해 크래시 발생 | 컨텍스트 정리, `gl.deleteTexture()` 등 텍스처 명시 해제, WeakMap 기반 객체 생명주기 관리 | 탭 메모리 사용량 추이 |

## Ⅵ. HTML5에 대한 기술사적 제언

- 핵심 요약 : 메인 스레드 보호와 통신 기술의 선택 기준을 개발 표준으로 정착시키는 방향.

1. 고비용 연산은 웹 워커로 분리하는 설계를 기본 원칙으로 삼고, 메시지 전달 비용과 메인 스레드 부하를 함께 측정하는 절차를 개발 표준에 넣는 것이 바람직하다.
2. 실시간 기능은 WebSocket과 WebRTC를 지연, 연결 유지 비용, 서비스 목적을 기준으로 비교한 뒤 선택하는 것이 바람직하다.
3. 웹 표준 적합성 검사와 주요 브라우저 호환성 테스트를 배포 파이프라인에 상시 편입해, 브라우저 편차로 인한 장애를 배포 전에 걸러내는 거버넌스를 세울 필요가 있다.

- 참고 : WHATWG HTML Living Standard (https://html.spec.whatwg.org/)

## Ⅶ. 결론

- 핵심 요약 : 플러그인 없이 문서·미디어·그래픽·저장·통신을 표준으로 묶은 웹 애플리케이션 플랫폼.
- 시사점 : 브라우저 편차와 저장소 보안 한계가 남아 있어, 기능 감지와 보안 설계가 HTML5 활용의 전제가 됨.
