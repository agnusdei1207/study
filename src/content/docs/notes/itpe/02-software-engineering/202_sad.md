<details>
<summary>핵심 용어</summary>

- **ISO/IEC/IEEE 42010**: 시스템 및 소프트웨어 아키텍처 기술(Architecture Description)의 메타모델을 정의한 국제 표준으로 이해관계자, 관심사, 뷰, 뷰포인트 간의 관계를 정립
- **4+1 View 모델**: 필립 크루첸(Philippe Kruchten)이 제안한 모델로, 유스케이스 뷰(+1)를 중심으로 논리 뷰, 구현 뷰, 프로세스 뷰, 배포 뷰의 4개 관점으로 아키텍처를 투영하는 기법
- **ADR(Architecture Decision Record)**: 특정 아키텍처 설계를 선택하게 된 맥락(Context), 검토한 대안, 최종 결정 사항 및 그에 따른 트레이드오프를 짧게 기록한 경량 문서
- **아키텍처 드라이버(Architectural Drivers)**: 소프트웨어의 전체 구조와 설계 결정을 강제하는 가장 중요하고 영향력이 큰 핵심 비기능 요구사항과 비즈니스 제약조건
</details>

## 1. 개요 및 필요성

### 단일 다이어그램의 한계와 다중 관점(Multi-View)의 필연성

소프트웨어 시스템은 너무 거대하여 단 하나의 아키텍처 다이어그램으로 완벽하게 표현할 수 없다. 개발자가 보고 싶어 하는 정보(클래스 관계, 패키지 의존성)와 인프라 엔지니어가 보고 싶어 하는 정보(서버 IP, 로드밸런서, 네트워크 토폴로지)는 완전히 다르다.

소프트웨어 아키텍처 기술서(SAD)는 **다양한 이해관계자의 관심사(Concerns)를 분리하여 서로 다른 관점(View)으로 시스템을 투영**함으로써, 시스템의 구조적 모순을 사전에 검증하고 원활한 협업을 이끄는 표준 기술 문서이다.

### SAD vs SRS vs SDD vs ADR 비교

| 구분 | 요구사항명세서 (SRS) | 아키텍처기술서 (SAD) | 상세설계서 (SDD) | 아키텍처 결정 기록 (ADR) |
|---|---|---|---|---|
| **핵심 질문** | **무엇(What)을 만들 것인가?** | **어떤 구조(Structure)로 풀 것인가?** | **어떻게(How) 구현할 것인가?** | **왜(Why) 이 기술을 선택했는가?** |
| **추상화 수준**| 비즈니스 기능 및 비기능 요구 | **시스템 전체 거시적 뼈대 및 뷰** | 클래스 내부 로직, 테이블 컬럼 | 단일 설계 결정의 맥락과 파급 |
| **주요 독자** | 고객, 기획자, 개발자 | **아키텍트, PM, 테크 리드** | 개발자, 테스트 엔지니어 | 팀 전체 개발자, 미래 인수인계자 |
| **핵심 내용** | 기능 목록, 유스케이스 정의 | **4+1 View, 품질 속성 전술** | 시퀀스 다이어그램, ERD, API 명세 | 결정 맥락, 대안 비교, 결과 영향 |

## 2. 아키텍처 및 핵심 메커니즘

### 크루첸(Kruchten)의 4+1 View 모델 구조

```text
+-------------------------------------------------------------------------+
|                  크루첸(Kruchten)의 4+1 View 모델 기반 SAD              |
+-------------------------------------------------------------------------+
|                                                                         |
|     [ 논리 뷰 (Logical) ]                  [ 프로세스 뷰 (Process) ]     |
|   - 사용자/분석자 관점                    - 시스템 통합자 관점          |
|   - 클래스, 인터페이스, 도메인 모델       - 스레드, 동시성, 성능, 확장성|
|                   │                                   │                 |
|                   └───┐                           ┌───┘                 |
|                       ▼                           ▼                     |
|                    ┌─────────────────────────────────┐                  |
|                    │  +1 유스케이스 뷰 (Use Case)    │                  |
|                    │  - 시스템의 핵심 사용자 시나리오│                  |
|                    │  - 다른 4개 뷰의 도출 및 검증축 │                  |
|                    └─────────────────────────────────┘                  |
|                       ▲                           ▲                     |
|                   ┌───┘                           └───┐                 |
|                   │                                   │                 |
|     [ 구현 뷰 (Development) ]              [ 배포 뷰 (Deployment) ]     |
|   - 프로그래머 관점                      - 시스템 인프라 엔지니어 관점 |
|   - 소스코드 컴포넌트, 패키지 구조       - 물리적 노드, 네트워크 토폴로지 |
+-------------------------------------------------------------------------+
```

## 3. 실무 적용 및 고려사항

### 위험 대응 매트릭스

| 위험 | 대책 | 효과 |
|---|---|---|
| 프로젝트 중반 이후 두꺼운 워드 SAD 문서를 갱신하지 않아 코드와 완전히 동떨어지는 문서 사장화(Documentation Rot) 발생 | Git 저장소 내 Docs-as-Code(Markdown + Mermaid) 기반 경량 문서화 및 PR 머지 시 갱신 의무화 | 문서와 소스코드 간의 100% 동기화 유지 |
| "왜 이 DB나 프레임워크를 선택했는가"에 대한 기록 부재로 차후 리팩토링 시 불안감 증폭 | 기술 선택 순간마다 맥락, 대안, 결과를 담은 1~2페이지 아키텍처 결정 기록(ADR) 작성 강제 | 설계 결정의 역사적 정당성 및 투명성 확보 |
| 비기술 비즈니스 고객에게 복잡한 클래스 다이어그램 위주의 SAD를 제시하여 의사소통 실패 | C4 Model(Context, Container, Component, Code)을 통한 4단계 수준별 줌인/줌아웃 시각화 적용 | 이해관계자 간 아키텍처 소통 오류 100% 해소 |

## 4. 기술사 답안 차별화 포인트

### 모던 아키텍처 시각화의 표준: C4 Model

크루첸 4+1 View의 추상적 한계를 보완하기 위해 사이먼 브라운(Simon Brown)이 제안한 **C4 Model**을 연계한다. 지도 앱처럼 **Context(시스템 맥락) $\rightarrow$ Container(애플리케이션/DB) $\rightarrow$ Component(내부 모듈) $\rightarrow$ Code(클래스)**의 4단계 줌 레벨로 아키텍처를 시각화하여, 경영진부터 주니어 개발자까지 직관적으로 소통할 수 있는 현대적 SAD 작성 표준을 제시한다.

### Docs-as-Code 패러다임과 ADR의 Git 통합

전통적 폭포수 방식의 무거운 워드 바인더 문서는 실패했다. 현대 엔지니어링에서는 **'Docs-as-Code'** 패러다임을 따라 Markdown, Mermaid, PlantUML로 작성된 다이어그램을 소스코드와 함께 Git 저장소에 커밋한다. 특히 **ADR(Architecture Decision Record)**을 `docs/adr` 디렉터리에 누적 관리하여, 기술 부채를 통제하고 신규 입사자에게 의사결정 역사를 전수하는 실무 거버넌스를 결론으로 강조한다.
