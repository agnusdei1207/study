## Ⅰ. 소프트웨어 아키텍처 기술서(SAD)의 개요

- 개념 : **소프트웨어 아키텍처 기술서** (SAD, Software Architecture Description) 란 시스템이 달성해야 하는 비즈니스 목표와 품질속성 요구사항을 충족시키기 위해 결정된 소프트웨어 아키텍처의 전반적인 구조, 컴포넌트 간의 상호작용, 설계 원칙, 기술 스택, 배포 토폴로지 및 트레이드오프 근거를 다양한 이해관계자의 관점(Viewpoint)에 맞추어 공식적으로 문서화한 최상위 아키텍처 설계 명세서.
- 배경 및 필요성 : 개발자, 아키텍트, 발주자, 운영자 간의 시스템 구조에 대한 오해를 방지하고, 프로젝트 전반의 기술적 의사결정의 **기준선** (Baseline)을 제공하여 **아키텍처 침식** (Erosion) 방지.
- 국제 표준 : **ISO(International Organization for Standardization)/IEC(International Electrotechnical Commission)/IEEE(Institute of Electrical and Electronics Engineers) 42010** (아키텍처 기술 표준 프레임워크)

## Ⅱ. IEEE 42010 기반 SAD 표준 프레임워크 및 크루첸 4+1 뷰 연계

```text
   ┌────────────────────────────────────────────────────────────────────────┐
   │ [ 아키텍처 기술서 (SAD) 핵심 목차 구조 ]                              │
   │                                                                        │
   │  1. 시스템 개요 및 비즈니스 배경 (Context & Mission)                   │
   │  2. 아키텍처 드라이버 (Architectural Drivers: 품질속성 유틸리티 트리)  │
   │  3. 이해관계자 및 관심사 (Stakeholders & Concerns)                    │
   │  4. 아키텍처 뷰 (Architectural Views: 4+1 View Model 연계)             │
   │     - 유스케이스 뷰 : 시스템 핵심 시나리오                             │
   │     - 논리 뷰       : 도메인 모델, 클래스 다이어그램, 계층 구조        │
   │     - 프로세스 뷰   : 동시성, 비동기 스레드, 성능, 트랜잭션 흐름       │
   │     - 구현 뷰       : 소스코드 디렉터리 구조, 빌드 모듈 의존성         │
   │     - 배포 뷰       : 클라우드 인프라, K8s 파드 배치, 망구성도         │
    │  5. 아키텍처 결정 기록 (ADR, Architecture Decision Record)            │
   └────────────────────────────────────────────────────────────────────────┘
```

## Ⅲ. SAD의 핵심 3대 구성요소 비교

| 구성요소 | 핵심 내용 및 기술 방식 | 주요 이해관계자 |
|---|---|---|
| **아키텍처 드라이버** (Drivers) | 시스템 설계에 결정적 영향을 미치는 고우선순위 기능/비기능 품질 시나리오 | 경영진, 발주자, 시스템 아키텍트 |
| **아키텍처 뷰** (Views) | 특정 관점(Viewpoint)에서 시스템의 관심사를 모델링한 다이어그램 및 설명 | 개발자, 인프라 엔지니어, 테스터 |
| **아키텍처 결정 기록** (ADR, Architecture Decision Record) | 기술 스택, 프레임워크, 패턴 선택의 이유와 탈락 대안, 트레이드오프 기록 | 후임 아키텍트, 신규 입사 개발자 |

## Ⅳ. 소프트웨어 아키텍처 기술서(SAD)의 주요 한계점 및 해결 방안

- 시스템 구현과의 괴리로 인한 아키텍처 **문서 진부화** (Document Drift) :
  - 한계점 : 프로젝트 초기에 작성된 SAD가 실제 개발 단계의 수많은 변경사항을 따라가지 못하고 방치되어 실제 시스템 구조를 반영하지 못함.
  - 해결 방안 : **Architecture-as-Code** (C4 모델, Structurizr)를 도입하여 코드베이스와 아키텍처 다이어그램을 동기화, PR 리뷰 시 아키텍처 문서 갱신 강제.
- 표준 뷰포인트(IEEE 42010, 4+1 뷰)의 과도한 형식주의 :
  - 한계점 : 정형화된 표준 양식을 채우기 위해 도메인과 무관한 뷰를 억지로 작성하여 작성 공수가 낭비되고 개발팀의 외면 초래.
  - 해결 방안 : 프로젝트 규모와 이해관계자 특성에 맞춘 실용적 테일러링, 핵심 뷰(논리 뷰, 배포 뷰) 및 데이터 흐름도 중심으로 문서 경량화.
- 설계 의사결정의 맥락 및 근거(Rationale) 유실 :
  - 한계점 : 최종 아키텍처 결과물만 나열되어 특정 기술이나 패턴을 선택한 이유, 대안과의 비교 분석 과정이 기록되지 않아 사후 유지보수 시 아키텍처 훼손.
  - 해결 방안 : 아키텍처 결정 레코드(ADR, Architecture Decision Record) 작성을 제도화하여 결정 배경, 고려 대안, 결과적 트레이드오프를 Git으로 체계적 관리.

## Ⅴ. 애자일 및 클라우드 환경에서의 기술사적 제언

- 수백 페이지의 '죽은 문서' 지양 및 마크다운 기반 **Doc-as-Code** 전환 : 프로젝트 초기에 한 번 쓰고 방치되는 두꺼운 워드 문서를 탈피하여, Git 저장소 내에 마크다운과 PlantUML/Mermaid 텍스트로 SAD를 작성하고 CI(Continuous Integration) 파이프라인에서 HTML(HyperText Markup Language) 문서로 자동 렌더링하는 살아있는 문서(Living SAD) 체계 확립.
- 공공 정보시스템 감리 시 기술적 아키텍처 증적 확립 : 정보시스템 감리 시 설계 적합성을 입증하기 위해, SAD 내에 비기능 요구사항(성능, 고가용성, 보안)과 배포 뷰 간의 매핑 관계를 명확히 제시하여 아키텍처 감리 지적 사항을 선제 방어해야 함.
