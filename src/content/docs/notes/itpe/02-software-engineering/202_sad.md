## 30초 인출

- 본질: 소프트웨어 아키텍처 기술서(SAD)는 시스템의 아키텍처를 이해관계자의 관심사에 맞는 뷰로 나누어 문서화한 산출물
- 메커니즘: 이해관계자와 그 관심사를 식별하고 관심사를 다룰 뷰포인트를 정해 뷰를 작성하며 뷰 사이의 대응과 결정 근거를 기록
- 통찰: 뷰를 관심사와 연결하지 않고 나열하면 아무도 읽지 않는 문서가 되므로 이해관계자별 관심사에서 필요한 뷰를 도출하고 뷰 간 일관성을 확인

<details>
<summary>핵심 용어</summary>

- **SAD(Software Architecture Description)** : 아키텍처를 뷰로 표현한 문서
- **ISO/IEC/IEEE 42010** : 아키텍처 기술의 구성요소를 정한 국제표준
- **이해관계자(Stakeholder)** : 시스템에 이해와 요구가 있는 사람·조직
- **관심사(Concern)** : 이해관계자가 시스템에 대해 가지는 성능·보안·유지보수성 같은 관심
- **뷰포인트(Viewpoint)** : 특정 관심사를 다루는 관점과 표기 규칙
- **뷰(View)** : 뷰포인트를 시스템에 적용해 작성한 아키텍처 표현

</details>

## 2~4교시 25점 답안

## Ⅰ. SAD의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **SAD** 는 아키텍처를 이해관계자의 관심사에 맞는 뷰로 문서화한 산출물 |
| 목적 | 아키텍처의 공유·검토와 후속 개발·변경의 기준 제공 |

## Ⅱ. 일반 설계서와 구별되는 특징

| 특징 | 의미 |
|---|---|
| 관심사 기반 | 이해관계자의 관심사에서 뷰 결정 |
| 다중 뷰 | 관점별 표현 |
| 결정 근거 포함 | 대안과 이유의 기록 |

## Ⅲ. 구성 관계

```text
이해관계자 ── 가짐 ──▶ 관심사 ── 다룸 ◀── 뷰포인트 ── 적용 ──▶ 뷰
                                                          (SAD를 이룸)
```

## Ⅳ. SAD의 구성

| 구성 | 내용 |
|---|---|
| 이해관계자·관심사 | 누가 무엇을 중요하게 보는가 |
| 뷰포인트·뷰 | 논리·프로세스·배치 등의 뷰 |
| 뷰 간 대응 | 뷰 사이의 일관성 |
| 결정 근거 | 주요 결정과 이유 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 관심사와 무관하게 뷰를 나열 | 이해관계자별 관심사에서 필요한 뷰 도출 |
| 뷰 간 불일치 | 뷰 간 대응 점검 |
| 문서 최신성 저하 | 아키텍처 변경 시 함께 갱신 |

## Ⅵ. 제언

이해관계자별 관심사를 먼저 정리해 필요한 뷰만 작성하고 뷰 간 일관성을 확인

```text
관심사 정리 → 필요한 뷰포인트 선택 → 뷰 작성 → 뷰 간 대응 점검
```

| 구분 | 뷰 나열 | 제언: 관심사 기반 |
|---|---|---|
| 독자 | 불명확 | 이해관계자별 |
| 분량 | 과다 | 필요한 만큼 |
