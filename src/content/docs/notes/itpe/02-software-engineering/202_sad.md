- **본질**: 소프트웨어 아키텍처 기술서(SAD)는 이해관계자의 관심사를 아키텍처 관점과 뷰로 표현해 시스템의 주요 구조와 결정을 전달하는 기술 문서
- **메커니즘**: 이해관계자·관심사 식별 → 관점 선정 → 뷰 작성 → 결정·근거·일관성 기록

<details>
<summary>핵심 용어</summary>

- **소프트웨어 아키텍처 기술서(Software Architecture Description, SAD)**: 시스템 아키텍처를 이해관계자의 관심사에 맞춰 기술한 설명
- **이해관계자(Stakeholder)**: 시스템에 관심을 갖거나 영향을 받는 개인·조직
- **관심사(Concern)**: 이해관계자가 시스템에 대해 중요하게 여기는 문제·요구
- **관점(Viewpoint)**: 특정 관심사를 다루는 규칙·표기·분석 방법의 명세
- **뷰(View)**: 관점을 적용해 작성한 아키텍처 표현
- **ISO/IEC/IEEE 42010**: 아키텍처 기술의 개념과 요구사항을 규정하는 국제 표준

</details>

### Ⅰ. 개요

| 구분 | 핵심 |

| 정의 | **소프트웨어 아키텍처 기술서**: 이해관계자 관심사에 맞춰 시스템 아키텍처를 표현한 기술 문서 |
| 목적 | 구조·결정·근거를 이해관계자 간 공유하고 검토 가능하게 구성 |

### Ⅱ. 기본 구성 관계

```text
이해관계자 → 관심사 식별 → 관점 선정
                           ↓
                    아키텍처 뷰 작성
                           ↓
                    아키텍처 기술서 기록
```

### Ⅲ. 작성 절차와 품질

| 단계 | 핵심 작업 |
|---|---|
| 범위 설정 | 시스템 경계와 독자·이해관계자 확인 |
| 관점 선정 | 주요 관심사를 다룰 관점과 표기 선택 |
| 뷰 작성 | 구조·관계·제약을 해당 관점에 따라 표현 |
| 검토·유지 | 결정 근거, 뷰 간 일관성, 변경 이력 확인 |

**제언**: 문서 분량보다 이해관계자의 핵심 관심사와 그에 대응하는 뷰의 추적성을 우선.

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 아키텍처 기술서**: 이해관계자 관심사에 맞춰 시스템 아키텍처를 표현한 기술 문서 |
| 목적 | 구조·결정·근거를 이해관계자 간 공유하고 검토 가능하게 구성 |

## Ⅱ. 작성 목적과 독자

SAD는 구조를 전달하고 설계 대안·제약·결정 근거를 검토하기 위한 아키텍처 산출물. 개발자, 운영자, 보안 담당자 등 독자에 따라 필요한 관점과 분석 수준이 달라짐.

| 독자 관심사 예 | 대응할 정보 |
|---|---|
| 개발 | 컴포넌트 책임·인터페이스·의존성 |
| 운영 | 배포·장애 격리·관측 구조 |
| 보안 | 자산 경계·위협·보안 통제 |

## Ⅲ. 관점과 뷰 구성

```text
이해관계자·관심사 식별
    ↓
관점 정의·선정 → 표기·분석 규칙 적용
    ↓
아키텍처 뷰 작성
    ↓
결정·제약·근거를 기술서에 연결
    ↓
검토 결과를 관점·뷰에 반영
```

관점은 관심사를 다루는 규칙이고 뷰는 이를 적용한 표현. ISO/IEC/IEEE 42010은 아키텍처 기술에 대한 요구사항을 다루며, 모든 시스템에 고정된 문서 서식이나 4+1 뷰를 강제하는 규격으로 해석하지 않음.

## Ⅳ. 작성·검증 절차

| 점검 관점 | 확인 내용 |
|---|---|
| 완전성 | 주요 이해관계자 관심사와 관점의 누락 여부 |
| 일관성 | 뷰 간 용어·요소·관계의 충돌 여부 |
| 근거성 | 주요 결정, 제약, 대안 선택 이유의 기록 |
| 검증성 | 품질 시나리오·분석 결과와 아키텍처의 연결 |

아키텍처 평가 방법이나 표기법은 목적에 맞춰 선택하며, 특정 방법을 SAD의 필수 구성으로 일반화하지 않음.

## Ⅴ. 문서 유지와 변경 반영

```text
요구·설계 변경
    ↓
관련 뷰·결정 확인 → 영향 분석
    ↓
아키텍처 수정·검토
    ↓
버전·근거 갱신 → 개발·운영에 공유
```

다이어그램의 원천 파일과 버전, 변경 근거를 함께 관리하면 검토와 갱신의 추적성이 높아짐. C4, ADR, 문서 자동화 도구 등은 선택 가능한 표현·관리 방법이지 표준이 요구하는 필수 도구가 아님.

## Ⅵ. 문제와 해결 방안

| 한계 | 해결 방안 |
|---|---|
| 이해관계자별 관심사가 누락 | 이해관계자·관심사 목록을 뷰와 연결해 검토 |
| 뷰끼리 다른 용어·경계를 사용 | 공통 용어·요소 식별자를 정하고 일관성 점검 |
| 문서가 변경 후 낡은 상태로 유지 | 변경 영향 분석과 문서 갱신을 설계 변경 절차에 연결 |

## Ⅶ. 기술적 제언

| 구분 | 내용 |
|---|---|
| 한계 | 문서가 단순 산출물 목록으로 관리되면 현재 아키텍처 결정과 구현·운영 상태의 관계가 흐려짐 |
| 해결 방안 | 핵심 아키텍처 결정을 요구·뷰·검증 근거와 연결하고 변경 시 해당 연결의 영향부터 갱신 |
