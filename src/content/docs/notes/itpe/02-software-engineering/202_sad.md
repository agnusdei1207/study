## 한 줄 본질
- 다양한 이해관계자들이 각자의 관점에서 시스템을 올바르게 이해하고 검증할 수 있도록 시스템의 전체 뼈대와 주요 설계 결정 근거를 다각도로 정리한 청사진 / 다중 뷰 모델과 아키텍처 결정 기록

## 핵심 용어
- ISO/IEC/IEEE 42010: 소프트웨어 및 시스템 아키텍처 기술(Architecture Description)에 관한 국제 표준으로, 이해관계자, 관심사, 뷰포인트, 뷰의 개념 모델을 정립함
- 뷰(View): 전체 아키텍처 중 특정 이해관계자의 관심사(Concern)에 초점을 맞추어 시스템의 일부분이나 측면을 표현한 결과물
- 뷰포인트(Viewpoint): 특정 관점의 뷰를 작성하기 위해 사용되는 규칙, 패턴, 다이어그램 기법, 모델링 언어를 정의한 틀(Template)
- 아키텍처 드라이버(Architectural Drivers): 아키텍처 설계 의사결정에 결정적인 영향을 미치는 핵심 비기능 요구사항(품질 속성: 성능, 가용성 등)과 비즈니스 제약조건
- 아키텍처 결정 기록(ADR, Architecture Decision Record): 특정 아키텍처 설계를 선택하게 된 맥락(Context), 검토한 대안, 최종 결정 사항 및 그에 따른 트레이드오프를 짧게 기록한 경량 문서

## 핵심 통찰
- 시스템을 단 하나의 다이어그램으로 완벽하게 표현하는 것은 불가능함. 개발자에게 필요한 정보(클래스 구조)와 인프라 엔지니어에게 필요한 정보(서버 배치도)는 완전히 다름
- 따라서 SAD의 핵심은 '4+1 뷰'와 같이 다양한 이해관계자의 눈높이에 맞춘 다각적 투영(Multi-View)을 제공하는 데 있음
- 가장 치명적인 실패는 프로젝트 초기에 수백 페이지 분량의 워드 문서를 작성한 뒤 한 번도 업데이트하지 않아 코드가 문서와 완전히 달라지는 '문서의 사장(Documentation Rot)'임
- 현대의 SAD는 한 권의 두꺼운 바인더가 아니라, Git 저장소 내에서 코드와 함께 숨 쉬는 마크다운 기반의 경량 C4 모델 및 ADR 체계로 전환되어야 함

## 이웃 토픽과 구분
| 비교 항목 | 요구사항명세서 (SRS) | 아키텍처기술서 (SAD) | 상세설계서 (SDD) | 아키텍처 결정 기록 (ADR) |
| :--- | :--- | :--- | :--- | :--- |
| **핵심 질문** | 무엇(What)을 만들 것인가? | 어떤 구조(Structure)로 풀 것인가? | 어떻게(How) 코딩할 것인가? | 왜(Why) 이 기술을 선택했는가? |
| **추상화 수준**| 비즈니스 기능/비기능 요구 | 시스템 전체의 거시적 뼈대 및 뷰 | 개별 클래스, DB 테이블 세부 명세 | 단일 설계 결정의 맥락과 결과 |
| **주요 독자** | 고객, 기획자, 개발자 | 아키텍트, PM, 시니어 개발자 | 개발자, 테스트 엔지니어 | 팀 전체 개발자, 미래의 인수인계자 |
| **핵심 내용** | 기능 목록, 유스케이스 명세 | 4+1 View, 품질 속성 전략 | 시퀀스 다이어그램, ERD, API 명세 | 결정 맥락, 대안 비교, 결과 영향도 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **프로젝트 진행 중 SAD 문서의 사장화** | 개발 도중 아키텍처가 바뀌었으나 두꺼운 워드 문서를 갱신하기 번거로움 | Git 저장소 내 Docs-as-Code(Markdown + Mermaid) 기반 경량 문서화 및 PR 필수 항목 지정 |
| **설계 결정의 역사적 배경 망각** | "왜 이 프레임워크나 DB를 선택했는지" 기록이 없어 리팩토링 시 불안감 증폭 | 의사결정 순간마다 1~2페이지 분량의 ADR(Architecture Decision Record) 작성 의무화 |
| **이해관계자 간의 소통 실패** | 비기술 고객에게 과도하게 복잡한 클래스 다이어그램 위주의 SAD를 제시 | C4 Model(Context, Container, Component, Code)을 통한 4단계 수준별 시각화 |

## 이렇게 출제된다
- **10점형**: 소프트웨어 아키텍처 기술서(SAD)의 개념 및 크루첸의 4+1 View 모델의 각 뷰를 설명하시오.
- **25점형**: 
  - 1) ISO/IEC/IEEE 42010 표준에 정의된 소프트웨어 아키텍처 기술의 메타모델(이해관계자, 관심사, 뷰, 뷰포인트)을 도식으로 제시하시오.
  - 2) 크루첸의 4+1 View 모델에서 유스케이스 뷰(+1)의 중심적 역할과 나머지 4개 뷰(논리, 구현, 프로세스, 배포)의 상세 내용을 설명하시오.
  - 3) 애자일 및 DevOps 환경에서 전통적 SAD의 한계를 극복하기 위한 C4 Model과 아키텍처 결정 기록(ADR)의 실무 적용 전략을 논하시오.

## 내 의견
- 전통적인 폭포수 방식의 방대한 SAD는 실무 개발자들로부터 '제출용 서류'로 외면받아 온 것이 현실임
- 아키텍처 문서가 생명력을 가지려면 코드가 존재하는 코드 저장소(Git) 바로 옆에서 함께 버전 관리되는 'Docs as Code' 패러다임이 필수적임
- 사이먼 브라운(Simon Brown)의 C4 Model을 활용해 지도처럼 줌인/줌아웃할 수 있는 다이어그램을 코드로 작성(PlantUML/Mermaid)하고, 기술적 의사결정이 일어날 때마다 ADR을 마크다운으로 남겨 커밋하는 체계가 가장 현대적이고 실효성 있는 SAD 구축 전략임
