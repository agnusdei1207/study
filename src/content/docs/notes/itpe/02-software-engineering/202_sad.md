## 연관 키워드

- 소프트웨어 아키텍처 기술서(SAD, Software Architecture Description), 뷰포인트(Viewpoint), 아키텍처 뷰(Architectural View)
- 4+1 뷰 모델(4+1 View Model), 아키텍처 결정 기록(ADR, Architecture Decision Record)
- 아키텍처 드라이버(Architectural Drivers), 아키텍처 침식(Architecture Erosion), 기준선(Baseline), Doc-as-Code

## Ⅰ. 소프트웨어 아키텍처 기술서(SAD)의 개요

- 핵심 요약 : 품질속성 요구를 충족하는 아키텍처의 구조와 결정 근거를 이해관계자 관점별로 문서화한 명세서.
- 개념 : 시스템의 비즈니스 목표와 품질속성 요구사항을 충족하도록 정한 아키텍처의 구조, 컴포넌트 상호작용, 설계 원칙, 배포 구조, 트레이드오프 근거를 이해관계자별 **뷰포인트** (Viewpoint, 관심사를 바라보는 관점의 정의)에 맞추어 기술한 **소프트웨어 아키텍처 기술서** (SAD, Software Architecture Description).
- 배경 및 필요성 : 개발자, 아키텍트, 발주자, 운영자가 시스템 구조를 서로 다르게 이해하면 구현이 어긋나므로, 공통 **기준선** (Baseline, 이후 변경을 판단하는 기준 상태)을 문서로 고정해야 함. 기준선이 없으면 **아키텍처 침식** (Architecture Erosion, 구현이 설계 원칙에서 점차 벗어나는 현상)이 진행됨.
- 주요 목적 : 설계를 좌우하는 **아키텍처 드라이버** (Architectural Drivers, 우선순위가 높은 품질속성 요구)를 근거로 아키텍처 의사결정을 보존하고, 이해관계자 간 소통과 변경 통제의 기준을 마련하는 것.
- 국제 표준 : **ISO/IEC/IEEE 42010** (ISO(International Organization for Standardization)/IEC(International Electrotechnical Commission)/IEEE(Institute of Electrical and Electronics Engineers) 공동 표준으로, 아키텍처 기술의 구성 요소와 관점 체계를 정의).

## Ⅱ. 소프트웨어 아키텍처 기술서(SAD)의 특징 및 장점

- 핵심 요약 : 관점별 다중 뷰와 결정 근거 보존을 통해 구조 이해와 변경 통제를 함께 확보하는 문서화 체계.

1. 이해관계자 관점 기반 문서화 : 뷰포인트별로 관심사를 나누어 기술 → 각 이해관계자가 필요한 정보만 읽을 수 있음.
2. 표준 프레임워크 준수 : ISO/IEC/IEEE 42010의 구성 요소를 따름 → 감리와 외부 검토에서 설명 근거 확보.
3. **4+1 뷰 모델** (4+1 View Model, 유스케이스·논리·프로세스·구현·배포의 다섯 뷰로 구조를 기술하는 방식) : 여러 뷰를 유스케이스로 엮어 일관된 구조 설명.
4. **아키텍처 결정 기록** (ADR, Architecture Decision Record, 기술 선택의 배경·대안·결과를 짧게 남기는 기록) : 선택 근거와 트레이드오프를 보존 → 사후 변경 시 맥락 손실 방지.
5. 기준선 제공 : 설계 원칙과 구조를 고정해 구현 편차를 감지 → 아키텍처 침식의 조기 발견.

## Ⅲ. 소프트웨어 아키텍처 기술서(SAD)의 구조 (흐름)

- 핵심 요약 : 아키텍처 드라이버에서 출발해 뷰로 구조를 표현하고, 결정 기록으로 근거를 남기는 문서 흐름.

```text
[ SAD 작성 흐름 ]

[ 1. 시스템 개요와 비즈니스 배경 ]
      ↓
[ 2. 아키텍처 드라이버 (품질속성 시나리오) ]
      ↓
[ 3. 이해관계자와 관심사 ]
      ↓
[ 4. 아키텍처 뷰 (4+1 뷰 모델 연계) ]
      ↓
[ 5. 아키텍처 결정 기록 (ADR) ]
```

```text
[ 4+1 뷰 모델 ]

중심 : 유스케이스 뷰 (+1, 핵심 시나리오)
      ↓ 시나리오로 나머지 뷰를 연결
  - 논리 뷰 : 도메인 모델과 클래스 구조
  - 프로세스 뷰 : 동시성·성능·트랜잭션
  - 구현 뷰 : 소스 구조와 모듈 의존성
  - 배포 뷰 : 인프라 배치와 네트워크 구성
```

## Ⅳ. SAD의 핵심 구성요소 비교

- 핵심 요약 : 아키텍처 드라이버, 아키텍처 뷰, 아키텍처 결정 기록이 각각 다른 이해관계자의 관심사를 담당.

| 구성요소 | 핵심 내용 | 주요 이해관계자 |
| --- | --- | --- |
| 아키텍처 드라이버 | 설계를 좌우하는 고우선순위 품질속성 시나리오 | 발주자, 시스템 아키텍트 |
| 아키텍처 뷰 | 특정 뷰포인트에서 본 구조를 모델링한 다이어그램과 설명 | 개발자, 인프라 엔지니어, 테스터 |
| 아키텍처 결정 기록 (ADR) | 기술·패턴 선택의 이유, 탈락 대안, 트레이드오프 | 후임 아키텍트, 신규 개발자 |

- 선택 기준 : 변경이 잦은 결정은 ADR로 짧게 남기고, 구조 설명은 뷰로 나누어 필요한 범위만 유지.

## Ⅴ. 소프트웨어 아키텍처 기술서(SAD)의 한계와 방안

- 핵심 요약 : 문서 진부화, 형식주의, 근거 유실의 한계를 코드 연동 문서, 실용적 테일러링, ADR 제도화로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 문서 진부화 (Document Drift) | 구현 변경이 문서에 반영되지 않아 실제 구조와 괴리 | 다이어그램을 코드와 함께 관리하는 Doc-as-Code 방식 도입, 코드 리뷰 시 문서 갱신 필수화 | 문서 갱신 주기, 구조 괴리 건수 |
| 형식주의 | 표준 양식을 맞추려고 도메인과 무관한 뷰를 작성 → 공수 낭비와 외면 | 프로젝트 규모에 맞춘 테일러링, 논리 뷰와 배포 뷰 중심의 경량화 | 문서 활용 빈도 |
| 근거 유실 | 최종 구조만 남고 선택 이유와 대안이 기록되지 않음 | ADR 작성 제도화, 결정 기록을 저장소에서 버전 관리 | ADR 작성률 |

## Ⅵ. 애자일과 클라우드 환경에 대한 기술사적 제언

- 핵심 요약 : 살아있는 문서 체계와 감리 증적 매핑을 함께 세워, 문서가 설계 통제 수단으로 기능하도록 하는 방향이 바람직하다.
- 아키텍처 조직은 두꺼운 문서 대신 저장소 안의 마크다운과 다이어그램 텍스트로 SAD를 관리하고, CI(Continuous Integration) 파이프라인에서 HTML(HyperText Markup Language) 문서를 자동 생성하도록 하여 문서가 코드와 같은 주기로 갱신되게 해야 한다.
- 정보시스템 감리에 대비하려면 비기능 요구사항인 성능, 고가용성, 보안이 배포 뷰의 어느 구성요소에 대응하는지 매핑표를 SAD에 포함시켜 설계 적합성을 입증할 수 있어야 한다.

## Ⅶ. 결론

- 핵심 요약 : SAD는 아키텍처 구조와 결정 근거를 이해관계자 관점으로 문서화해 침식을 막는 기준선.
- 시사점 : 드라이버, 뷰, 결정 기록의 세 축을 실용적으로 유지하는 것이 문서의 생명력을 좌우함.
