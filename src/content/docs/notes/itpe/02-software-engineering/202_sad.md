## 연관 키워드

- SAD, ISO/IEC/IEEE 42010, 이해관계자, 관심사, 뷰·뷰포인트, ADR, 4+1 뷰

## Ⅰ. 소프트웨어 아키텍처 기술서의 개요

- 핵심 요약 : SAD는 시스템 아키텍처를 이해관계자의 관심사와 뷰에 연결해 근거·결정·구조를 기록하는 기술서.
- 개념 : **소프트웨어 아키텍처 기술서**(Software Architecture Description, SAD)는 아키텍처 이해·분석에 필요한 모델과 관계·근거를 체계화한 산출물.
- 배경 및 필요성 : 여러 이해관계자가 서로 다른 품질 요구와 시스템 관점을 가지므로 구조와 결정의 공통 근거 필요.
- 주요 목적 : 아키텍처 이해·검토·의사소통 및 변경 영향 관리.

## Ⅱ. SAD의 특징 및 장점

- 핵심 요약 : 뷰와 뷰포인트, 이해관계자 관심사, 근거를 연결해 설계의 맥락과 검증 가능성을 확보.

1. 관심사 기반 : 이해관계자의 우려를 식별해 적합한 뷰포인트 선택 → 필요한 구조정보의 누락 방지.
2. 다중 뷰 표현 : 기능·정보·배포·동시성 등 서로 다른 관점의 모델 구성 → 복잡한 구조의 분할 이해.
3. 결정 근거 기록 : 대안·제약·결정 이유를 ADR 등으로 남김 → 변경 시 과거 판단의 재평가 지원.

## Ⅲ. SAD의 구조 (흐름)

- 핵심 요약 : 이해관계자·관심사 분석 → 뷰포인트 선정 → 뷰·모델 작성 → 일관성·요구 추적 검토 → 변경관리.

```text
이해관계자·관심사 식별
  ↓
뷰포인트와 모델링 규칙 선정
  ↓
뷰·모델·인터페이스 기술
  ↓
품질속성·제약·결정 근거 연결
  ↓
일관성 검토·변경 이력 유지
```

- 4+1 뷰 예 : 논리·개발·프로세스·물리 뷰와 시나리오를 연결하되 시스템 특성과 독자에 맞게 테일러링.

```text
논리 뷰 ─ 개발 뷰
    \       /
   시나리오(+1)
    /       프로세스 뷰 ─ 배포·물리 뷰
```

## Ⅳ. SAD와 ADR의 비교

- 핵심 요약 : SAD는 구조와 관계를 종합 기술하고 ADR은 개별 아키텍처 결정의 맥락·대안을 기록.

| 비교 기준 | SAD | ADR |
| --- | --- | --- |
| 범위 | 여러 뷰와 모델로 시스템 구조 설명 | 하나의 중요한 결정과 그 근거 |
| 내용 | 구성요소·관계·제약·품질속성 | 맥락·고려 대안·결정·결과 |
| 활용 | 아키텍처 전체 검토·의사소통 | 결정 추적·변경 시 재검토 |

## Ⅴ. SAD의 한계와 방안

- 핵심 요약 : 문서 진부화·과잉 문서화·결정 근거 분리를 방지하도록 모델을 변경 프로세스에 편입.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 진부화 | 코드·배포 변경 후 뷰 갱신 누락 | 아키텍처 변경 승인과 문서 갱신을 같은 PR·릴리스 흐름에 포함 | 최근 갱신일·코드와 불일치 |
| 형식주의 | 독자·의사결정에 불필요한 뷰까지 작성 | 관심사·검토 질문에 따른 테일러링 | 미사용 뷰 수·검토 활용도 |
| 근거 유실 | 결정 결과만 남고 대안·제약이 기록되지 않음 | 중요 선택에 ADR과 요구·품질 시나리오 링크 | 근거 없는 결정 비율 |

## Ⅵ. SAD의 제언

- 핵심 요약 : 아키텍트는 SAD를 정적 문서가 아닌 설계 대화·품질속성 검증·변경관리의 공통 작업물로 운영.

1. 아키텍처 책임자는 이해관계자별 핵심 관심사와 검토 시점을 문서 목차에 매핑.
2. 개발조직은 다이어그램·ADR을 버전관리 저장소에 두고 자동 링크 검사·코드리뷰 적용.
3. 감리·품질조직은 요구사항, 품질속성 시나리오, 결정, 시험 증거의 추적 관계를 표본 점검.

## Ⅶ. SAD의 결론

- 핵심 요약 : SAD는 아키텍처 구조를 다양한 관심사·뷰와 결정 근거에 연결한 기술 표현.
- 시사점 : 문서의 양보다 이해관계자 질문에 답하고 변화와 함께 유지되는지가 품질을 좌우.
