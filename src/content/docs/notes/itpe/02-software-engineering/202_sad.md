## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 소프트웨어 아키텍처·설계 → 소프트웨어 아키텍처 기술서(SAD)

## 지식 위치

소프트웨어공학 > 소프트웨어 아키텍처 > 아키텍처 기술

## 30초 인출

- 본질: ISO/IEC/IEEE 42010 국제 표준에 기반하여 다양한 이해관계자(개발자, 운영자, 발주자)의 핵심 관심사(Concerns)를 다각도의 아키텍처 뷰(View)와 뷰포인트(Viewpoint)로 구조화하여 기술한 최상위 설계 문서
- 메커니즘: 이해관계자 및 관심사 식별 → 관점(Viewpoint: 논리, 프로세스, 구현, 배포 등) 정의 → 뷰(View) 작성 및 일관성 검증 → 아키텍처 결정 레코드(ADR) 및 근거 명세
- 통찰: 프로젝트 진행 중 문서와 구현 소스코드 간의 괴리(Architecture Drift)를 방지하기 위해 정형 문서에 더해 버전 관리 시스템 내 ADR(Architecture Decision Record) 기반의 코드형 문서화(Docs-as-Code) 체계 확립 필수

<details>
<summary>핵심 용어</summary>

- **SAD (Software Architecture Description)** : 시스템의 전체 아키텍처 구조, 구성요소 간의 관계, 설계 원칙 및 근거를 이해관계자 관점에서 종합 기술한 표준 산출물
- **ISO/IEC/IEEE 42010** : 시스템 및 소프트웨어 엔지니어링에서 아키텍처 기술(Description)의 개념적 프레임워크와 필수 요건을 규정한 국제 표준
- **이해관계자 (Stakeholder)** : 시스템에 대해 권리, 지분, 요구사항 또는 관심사를 가진 개인, 팀 또는 조직 (고객, 사용자, 아키텍트, 개발자, 운영자)
- **관심사 (Concerns)** : 시스템의 개발, 운영, 성능, 보안, 유지보수성 등 이해관계자에게 중요한 핵심 요구사항 및 관심사
- **뷰포인트 (Viewpoint)** : 특정 관심사를 다루기 위해 적용하는 관점, 모델링 표기법, 분석 기법을 규정한 아키텍처 표현의 '틀(Template)'
- **아키텍처 뷰 (Architecture View)** : 특정 뷰포인트를 구체적 시스템에 적용하여 작성한 실제 아키텍처 모델 및 다이어그램의 결과물
</details>

## 2~4교시 예상문제 (25점)

> 소프트웨어 아키텍처 기술서(SAD)의 목적과 ISO/IEC/IEEE 42010 표준 프레임워크의 핵심 메커니즘을 설명하고, 4+1 뷰 모델과의 관계 및 아키텍처 결정 레코드(ADR)를 활용한 지속적 형상관리 방안을 제시하시오. (25점)

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 복잡한 소프트웨어 시스템의 구조, 모듈 간 인터페이스, 런타임 상호작용 및 물리적 배포 방식을 다양한 이해관계자의 시각에 맞추어 체계적으로 문서화한 최상위 엔지니어링 산출물 |
| 목적 | 다자간 이해관계자 간의 의사소통 기준선 확립, 설계 결정의 타당성 및 제약조건 기록, 아키텍처 품질 속성(성능, 보안, 확장성)의 조기 검증 근거 제공 |

## Ⅱ. 핵심 특징

| 특징 | 세부 내용 |
|---|---|
| 다중 관점 모델링 (Multi-View) | 단일 다이어그램의 한계를 극복하고 대상 독자(개발, 인프라, 비즈니스)에 따라 차별화된 뷰(View) 제공 |
| 관심사의 명확한 분리 | 비즈니스 유스케이스, 정적 컴포넌트 구조, 동적 스레드 흐름, 물리적 하드웨어 배치를 독립적으로 분리 표현 |
| 결정 근거의 추적성 | "왜 그러한 아키텍처 전술을 채택했는가?"에 대한 설계 대안과 트레이드오프 근거(Rationale)를 명확히 보존 |
| 표준 준수성 (ISO 42010) | 국제 표준 규격이 정의한 Stakeholder-Concern-Viewpoint-View의 엄격한 개념적 정렬 준수 |

개발 단계의 가이드라인이자 향후 유지보수 및 재공학의 나침반 역할을 수행하는 소프트웨어의 설계 청사진.

## Ⅲ. 체계·프로세스

```text
[ISO/IEC/IEEE 42010 표준 기반 아키텍처 기술 프레임워크]

        [시스템 (System-of-Interest)] ── 환경(Environment) 내에 존재
                    │
                    ▼ 구현 및 표현
        [아키텍처 (Architecture)]
                    │
                    ▼ 기술 (Described by)
[아키텍처 기술서 (Architecture Description: SAD)]
  ┌────────────────────────────────────────────────────────┐
  │ 1. 이해관계자 (Stakeholders) : 고객, 개발팀, 운영팀, 보안팀│
  │    - 관심사 (Concerns)       : 비즈니스 가치, 구조, 가용성 │
  │        │ 프레임화 (Frame)                              │
  │        ▼                                               │
  │ 2. 아키텍처 뷰포인트 (Viewpoints: 규약/관점)            │
  │    - 4+1 View, C4 Model, 보안 관점, 데이터 관점 등     │
  │        │ 인스턴스화 (Conforms to)                      │
  │        ▼                                               │
  │ 3. 아키텍처 뷰 (Architecture Views: 구체적 표현)       │
  │    - 논리 뷰, 구현 뷰, 프로세스 뷰, 배포 뷰             │
  │        │ 구성 (Composed of)                            │
  │        ▼                                               │
  │ 4. 아키텍처 모델 및 결정 근거 (Rationale / ADR)        │
  └────────────────────────────────────────────────────────┘
```

이해관계자 관심사 식별, 뷰포인트 프레임화, 구체적 뷰 도출, 아키텍처 결정 레코드(ADR) 결합으로 완성되는 프로세스.

## Ⅳ. 종류·비교

### 1. 필립 크루첸의 4+1 뷰 모델(4+1 View Model)과 SAD의 매핑

| 4+1 뷰 명칭 | 대상 이해관계자 | 다루는 핵심 관심사 | 대표적 UML 다이어그램 표기 |
|---|---|---|---|
| **유스케이스 뷰 (Use Case)** | 최종 사용자, 고객 | 시스템이 제공하는 외부 기능 요구사항 (전체 뷰를 통합 검증하는 +1의 역할) | 유스케이스 다이어그램 |
| **논리 뷰 (Logical View)** | 시스템 설계자, 개발자 | 비즈니스 도메인의 기능적 요구사항, 클래스/패키지 구조 및 책임 분할 | 클래스 다이어그램, 시퀀스 다이어그램 |
| **프로세스 뷰 (Process View)** | 시스템 통합자, 성능팀 | 런타임 비기능 요구사항(동시성, 멀티스레딩, 성능, 비동기 통신, 데드락 방지) | 액티비티 다이어그램, 상태 머신 다이어그램 |
| **구현 뷰 (Implementation)** | 프로그래머, 빌드팀 | 소프트웨어 모듈의 물리적 구성, 소스코드 의존성, 빌드 및 형상 구조 | 컴포넌트 다이어그램, 패키지 다이어그램 |
| **배포 뷰 (Deployment View)** | 인프라 엔지니어, 운영팀 | 소프트웨어 컴포넌트가 하드웨어/클라우드 노드에 매핑되는 물리적 토폴로지 | 배포(Deployment) 다이어그램 |

### 2. 전통적 정형 SAD vs 모던 ADR (Architecture Decision Record)

| 비교 항목 | 전통적 아키텍처 기술서 (SAD) | 아키텍처 결정 레코드 (ADR) |
|---|---|---|
| **문서 형태** | 수백 페이지 분량의 단일 대형 워드/PDF 문서 | 1~2페이지 분량의 경량 마크다운(Markdown) 파일 |
| **작성 시점** | 프로젝트 분석/설계 단계에 집중 작성 후 동결 | 아키텍처 결정이 발생하는 매 순간 지속적 작성 |
| **저장 위치** | 사내 문서 중앙 포털 또는 파일 서버 분리 보관 | Git 소스코드 저장소 내부(`docs/adr/`)에 코드와 동시 관리 |
| **유지보수성** | 코드 변경 시 문서 동기화 누락으로 문서 노후화 심각 | Git 커밋/PR 시 함께 갱신되어 최신성 100% 보장 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 초기 폭포수 방식으로 방대하게 작성된 후 코드 수정이 반영되지 않아 문서가 쓸모없어지는 Architecture Drift 발생 | Git 저장소 내에 마크다운 기반으로 ADR을 작성하고 PlantUML/Mermaid를 이용한 코드형 문서화(Docs-as-Code) 적용 |
| 모든 이해관계자에게 동일한 기술 수준의 복잡한 클래스 다이어그램을 제공하여 소통 단절 유발 | Simon Brown의 C4 Model(Context, Container, Component, Code)을 채택하여 독자 수준별 계층적 추상화 제공 |
| 아키텍처 설계 산출물과 실제 코딩 규약 간의 일치 여부를 자동으로 검증하지 못하는 한계 | ArchUnit 도구를 단위 테스트 파이프라인에 결합하여 아키텍처 레이어링 규칙 위반 시 빌드 자동 실패 처리 |

## Ⅵ. 제언

현대 소프트웨어 공학에서는 고착화된 정적 문서를 지양하고, 시스템 아키텍처를 형상관리 내에서 살아 숨 쉬게 관리하는 Docs-as-Code 파이프라인과 ADR 거버넌스 확립 권장.

```text
[지속 가능한 아키텍처 거버넌스 (Docs-as-Code)]
  아키텍처 결정 발생 → ADR 마크다운 작성 → Git PR 검토 → ArchUnit 단위 검증 통과 → 자동 포털 빌드
```

| 관리 영역 | 전통적 SAD 관리 | 모던 Docs-as-Code 관리 |
|---|---|---|
| 작성 도구 | MS Word, Visio (비정형 바이너리) | Markdown, Mermaid, PlantUML (텍스트 소스) |
| 버전 관리 | 파일명 버전 표기 (`SAD_v2.1_최종.docx`) | Git 브랜치 및 커밋 해시 기반 완전한 이력 추적 |
