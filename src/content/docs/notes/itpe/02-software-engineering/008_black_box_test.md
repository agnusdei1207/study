## Ⅰ. 블랙박스 테스트의 개요

- 개념 : 소프트웨어의 내부 코드 구조를 들여다보지 않고, **요구사항 명세서** (SRS, Software Requirements Specification)와 입력/출력 사양을 바탕으로 시스템의 기능적 정확성을 검증하는 **명세 기반** (Specification-based) 테스트 기법.
- 배경 및 필요성 : 코드 복잡성에 구애받지 않고 사용자 관점에서 요구사항 충족 여부 판별 가능, 단위·통합·시스템·인수 테스트 전 단계에 걸쳐 폭넓게 적용.
- 핵심 목표 : **기능 누락** (Omission), 인터페이스 결함, 경계 영역 오류, 예외 처리 미흡 등 명세 불일치 결함 검출.

## Ⅱ. 블랙박스 테스트 수행 절차 및 주요 설계 기법

```text
   [ 요구사항 명세 분석 ] ──> [ 입력 도메인 분할 ] ──> [ 테스트 케이스 도출 ] ──> [ 결과 비교·검증 ]
                                 (유효/무효 영역)          (입력값·예상 결과)          (Pass/Fail 판정)
```

- **동등 분할 (Equivalence Partitioning)** :
  - 입력 데이터 도메인을 결과가 동일할 것으로 예상되는 **유효 동등 클래스** (Valid Class)와 **무효 동등 클래스** (Invalid Class)로 분할.
  - 각 클래스에서 대표값 하나씩을 추출하여 테스트 케이스를 설계함으로써 최소한의 테스트로 최대 커버리지 달성.
- **경계값 분석 (Boundary Value Analysis)** :
  - 오류 발생 확률이 가장 높은 동등 분할 영역의 경계선(Boundary)에 집중하는 기법.
  - **2-포인트** (경계값, 경계값 바로 바깥값) 또는 **3-포인트** (경계값 바로 안쪽, 경계값, 경계값 바로 바깥값)를 선정하여 $N-1, N, N+1$ 테스트 케이스 도출.

## Ⅲ. 주요 블랙박스 테스트 기법 비교

| 기법 | 설계 원리 | 주 검증 대상 및 장점 |
|---|---|---|
| 동등 분할 (EP) | 입력 도메인을 상호 배타적인 클래스로 분할 후 대표값 추출 | 입력값 조합 폭발 방지, 전반적 기능 적합성 검증 |
| 경계값 분석 (BVA) | 분할 영역의 최소/최대 경계값 및 인접값 추출 | 조건문 등호/부등호 오류, 오프바이원(Off-by-One) 결함 탐지 |
| **의사결정표** (Decision Table) | 복잡한 조건(Condition)과 그에 따른 행동(Action)을 표로 정형화 | 여러 조건이 얽힌 복합 비즈니스 룰의 누락 없는 검증 |
| **상태 전이** (State Transition) | 시스템의 상태, 이벤트, 전이, 액션 관계를 다이어그램으로 모델링 | 상태 기반 임베디드 기기, 인증/결제 프로세스 누락 검증 |
| **유스케이스 테스팅** (Use Case) | 액터와 시스템 간의 상호작용 시나리오 기반 케이스 작성 | 실제 비즈니스 흐름 및 통합 시나리오 정합성 검증 |

## Ⅳ. 블랙박스 테스트의 주요 한계점 및 해결 방안

- 내부 구현 경로 미검증으로 인한 데드코드 및 예외 로직 누락 :
  - 한계점 : 요구사항 명세만을 기반으로 테스트 케이스를 설계하므로, 소스코드 내부의 비정상 처리 분기문, 복잡한 중첩 루프, 실행되지 않는 데드 코드(Dead Code) 등 내부 구조적 결함 검출 불가.
  - 해결 방안 : 화이트박스 테스트(구문/조건 커버리지) 및 정적 코드 분석(SonarQube)과 상호 연계하는 그레이박스 테스팅(Gray-Box Testing) 체계를 구축하여 검증 사각지대 해소.
- 입력 도메인 조합 폭발(Combinatorial Explosion)로 인한 테스트 비효율 :
  - 한계점 : 다수의 파라미터와 조건이 상호작용하는 환경에서 동등 분할 및 경계값 분석을 전수 조합할 경우 테스트 케이스 수가 수만 개로 급증하여 현실적 일정 내 수행 불가.
  - 해결 방안 : 대부분의 결함이 2개 인자의 상호작용에서 기인한다는 점에 착안한 페어와이즈(Pairwise / All-Pairs) 테스팅 및 직교 배열표(Orthogonal Array) 기법을 적용하여 테스트 케이스 최적 축소.
- 요구사항 명세서(SRS)의 품질 종속성 :
  - 한계점 : 요구사항 명세가 모호하거나 누락, 잦은 변경이 발생하는 경우 테스트 설계 기준 자체가 흔들려 유효하지 않은 테스트 케이스가 양산됨.
  - 해결 방안 : BDD(Behavior Driven Development) 기반 Given-When-Then 문법을 적용하여 실행 가능한 명세(Executable Specification)를 작성하고 요구사항 추적 매트릭스(RTM, Requirements Traceability Matrix)를 통한 형상 연계 강화.

## Ⅴ. 블랙박스 테스트 효율화를 위한 기술사적 제언

- 페어와이즈(Pairwise) 테스팅을 통한 조합 폭발 통제 : 입력 변수가 다수일 때 발생하는 모든 조합을 테스트하는 것은 불가능하므로, 대부분의 결함이 소수 인자의 상호작용에서 비롯된다는 원리에 기반한 페어와이즈 조합 기법 적용 권장.
- 요구사항 추적표(RTM)와의 1:1 매핑 의무화 : 명세 누락 및 테스트 사각지대를 방지하기 위해 각 요구사항 ID와 블랙박스 테스트 케이스 ID 간 양방향 추적성을 확보하여 인수 테스트의 공학적 신뢰도 제고.
