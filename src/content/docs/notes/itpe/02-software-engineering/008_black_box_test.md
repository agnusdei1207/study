## 연관 키워드

- 블랙박스 테스트, 명세 기반 테스트(Specification-based Testing), 동등 분할(EP, Equivalence Partitioning)
- 경계값 분석(BVA, Boundary Value Analysis), 의사결정표(Decision Table), 상태 전이(State Transition), 유스케이스 테스팅

## Ⅰ. 블랙박스 테스트의 개요

- 핵심 요약 : 내부 구조를 보지 않고 요구사항 명세만으로 기능 정확성을 검증하는 테스트 기법 체계.
- 개념 : 소스코드 내부 구조를 들여다보지 않고, 요구사항 명세서(SRS, Software Requirements Specification)와 입출력 사양만으로 기능 정확성을 검증하는 **블랙박스 테스트** (Black-Box Test). 명세를 기준으로 삼는다는 뜻에서 **명세 기반 테스트** (Specification-based Testing)라고도 함.
- 배경 및 필요성 : 코드 복잡성과 무관하게 사용자 관점에서 요구사항 충족을 판별해야 하며, 단위부터 인수까지 모든 테스트 레벨에 적용할 필요가 있음.
- 주요 목적 : 기능 누락, 인터페이스 결함, 경계 영역의 오류, 예외 처리 미흡 같은 명세 불일치 결함의 검출.

## Ⅱ. 블랙박스 테스트의 특징

- 핵심 요약 : 명세 중심의 설계와 전 테스트 레벨 적용성, 조합 설계를 통한 최소 케이스 최대 커버리지가 결합된 방식.

1. 내부 코드 구조에 의존하지 않는 명세 기반 설계 → 구현이 바뀌어도 테스트 설계 기준이 유지됨.
2. 사용자 관점에서 요구사항 충족 여부 판별 → 발주자 기준의 검증이 가능.
3. 단위·통합·시스템·인수 테스트 전 단계에 적용 → 레벨 간 일관된 판정 기준 유지.
4. **동등 분할** (EP, Equivalence Partitioning)과 **경계값 분석** (BVA, Boundary Value Analysis)의 조합 → 적은 케이스로 넓은 입력 범위를 덮음.
5. **그레이박스 테스팅** (Gray-Box Testing, 화이트박스 기법을 일부 결합한 방식) → 명세 검증의 사각지대를 구조 관점으로 보완.

## Ⅲ. 블랙박스 테스트의 구조 (흐름)

- 핵심 요약 : 명세 분석, 입력 도메인 분할, 케이스 도출, 결과 검증으로 이어지는 절차와 대표 기법의 동작 원리.

```text
[ 요구사항 명세 분석 ]
        ↓
[ 입력 도메인 분할 ]
        ↓
[ 테스트 케이스 도출 ]
        ↓
[ 결과 비교·검증 ]
```

- 동등 분할 (EP) : 입력 도메인을 결과가 같을 것으로 예상되는 유효 클래스와 무효 클래스로 나누고, 각 클래스의 대표값으로 케이스를 구성해 케이스 수를 줄임.
- 경계값 분석 (BVA) : 오류가 몰리기 쉬운 경계선에 집중하는 기법. 경계값과 그 안팎의 값을 골라 N-1, N, N+1 케이스를 도출.

```text
[ 입력 범위 0 ≤ N ≤ 100 ]
무효 : N < 0      (예: -1)
유효 : 0 ≤ N ≤ 100 (예: 0, 50, 100)
무효 : N > 100    (예: 101)
        ↓ 경계값 중심 시험
-1 · 0 · 1 · 99 · 100 · 101
```

## Ⅳ. 블랙박스 테스트 기법별 비교

- 핵심 요약 : 설계 원리와 검증 대상이 다른 명세 기반 기법들을 구분해 상황에 맞게 고르는 체계.

| 기법 | 설계 원리 | 주 검증 대상과 장점 |
| --- | --- | --- |
| 동등 분할 (EP) | 입력 도메인을 상호 배타적 클래스로 나누고 대표값 추출 | 입력 조합 폭발 방지, 기능 적합성 전반 검증 |
| 경계값 분석 (BVA) | 분할 영역의 최소·최대 경계값과 인접값 추출 | 등호·부등호 실수, 오프바이원(Off-by-One) 결함 탐지 |
| **의사결정표** (Decision Table) | 조건과 행동의 관계를 표로 정형화 | 여러 조건이 얽힌 업무 규칙의 누락 없는 검증 |
| **상태 전이** (State Transition) | 상태·이벤트·전이·액션 관계를 다이어그램으로 모델링 | 임베디드 기기, 인증·결제 흐름의 누락 검증 |
| **유스케이스 테스팅** (Use Case Testing) | 액터와 시스템의 상호작용 시나리오 기반 케이스 작성 | 실제 업무 흐름과 통합 시나리오의 정합성 검증 |

## Ⅴ. 블랙박스 테스트의 장점과 한계

- 핵심 요약 : 사용자 관점과 전 레벨 적용이라는 장점, 내부 경로 미검증·조합 폭발·명세 품질 종속이라는 한계.

1. 코드 복잡성과 무관하게 요구사항 충족 여부를 검증.
2. 단위부터 인수까지 전 테스트 레벨 적용 가능.
3. 최소 케이스로 최대 커버리지를 목표로 하는 기법 체계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 내부 경로 미검증 | 데드 코드, 예외 분기, 중첩 루프의 결함을 찾지 못함 | 화이트박스 구문·조건 커버리지와 정적 분석(SonarQube)을 병행하는 그레이박스 테스팅 체계 구축 | 커버리지 보완율, 데드 코드 검출 건수 |
| **조합 폭발** (Combinatorial Explosion) | 다수 파라미터를 전수 조합하면 케이스 수가 급증 | **페어와이즈 테스팅** (Pairwise Testing)과 **직교 배열표** (Orthogonal Array)로 케이스 축소 | 케이스 축소율, 결함 검출률 |
| 명세 품질 종속 | 명세가 모호하거나 누락·변경이 잦으면 유효하지 않은 케이스가 양산 | **BDD** (Behavior-Driven Development) 기반 Given-When-Then 실행 가능 명세 작성, **요구사항 추적 매트릭스** (RTM, Requirements Traceability Matrix) 관리 | 명세 변경 건수, 추적 누락률 |

## Ⅵ. 블랙박스 테스트 효율화를 위한 기술사적 제언

- 핵심 요약 : 조합을 통제하는 설계 기준과, 명세 단계부터 테스트 가능성을 검토하는 협업 체계를 함께 갖추는 것.

1. 조합 통제 기준의 표준화 : 전수 조합은 현실적이지 않다는 전제 아래, 결함의 대부분이 소수 인자의 상호작용에서 비롯된다는 원리를 팀 기준으로 문서화하고 페어와이즈 기법을 기본 설계 방법으로 정하는 것이 필요함.
2. 명세 리뷰에 테스트 담당자 참여 : 모호한 요구사항은 테스트 설계 단계에서 가장 먼저 드러나므로, 명세 리뷰 단계에 테스트 담당자를 참여시켜 테스트 불가능한 문장을 개발 초기에 정제하는 협업 절차가 필요함.

## Ⅶ. 결론

- 핵심 요약 : 블랙박스 테스트는 명세 기반 기능 검증의 기본 골격이며 화이트박스 테스트와 상호 보완적임.
- 시사점 : 명세의 테스트 가능성을 먼저 확보하고 조합을 통제하는 것이 테스트 효율과 인수 신뢰도를 함께 높이는 핵심임.
