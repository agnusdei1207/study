## Ⅰ. 순차 다이어그램의 개요

- 개념 : **순차 다이어그램** (Sequence Diagram) 이란 객체지향 소프트웨어 시스템에서 특정 유스케이스나 기능 시나리오를 달성하기 위해 복수의 객체(또는 서비스 컴포넌트)들이 시간의 흐름(순서)에 따라 서로 주고받는 메시지(동기, 비동기)의 상호작용을 시각적으로 모델링한 UML 동적 행위 다이어그램.
- 배경 및 필요성 : 클래스 다이어그램만으로는 파악하기 어려운 런타임 시점의 구체적인 메서드 호출 순서, 반환값, 객체의 생명주기, 비동기 이벤트 흐름을 직관적으로 명시하여 API 인터페이스 설계 및 결함 디버깅의 기준 제공.
- 핵심 요소 : 생명선(Lifeline), 활성 객체(Execution Occurrence / Activation Bar), 메시지(Message), **복합 단편** (Combined Fragments)

## Ⅱ. 순차 다이어그램 표기법 및 메시지 유형

```text
   [ :Client ]                 [ :OrderService ]             [ :PaymentGateway ]
        │                              │                              │
        │─── 1. createOrder() ────────>│                              │ (동기 호출: 채워진 화살표)
        │                              │                              │
        │                              │─── 2. processPay() ─────────>│
        │                              │                              │
        │                              │< - - 3. return (success) - - │ (반환 메시지: 점선 화살표)
        │                              │                              │
        │                              │─── 4. sendKafkaEvent() ───>  │ (비동기 메시지: 열린 화살표)
        │< - - 5. orderCreated - - - - │                              │
        │                              │                              │
```

- **생명선** (Lifeline) : 상호작용에 참여하는 객체를 나타내며, 위에서 아래로 흐르는 수직 점선으로 시간의 경과 표현.
- **실행 상자** (Activation Box) : 객체가 메시지를 수신하여 실제로 연산을 수행하고 있는 시간 구간을 직사각형 막대로 표시.
- **동기 메시지** (Synchronous) : 호출자가 응답을 받을 때까지 블로킹되어 대기 (실선 + 채워진 삼각 화살표).
- **비동기 메시지** (Asynchronous) : 호출자가 메시지를 전송한 후 응답을 기다리지 않고 즉시 다음 작업 수행 (실선 + 열린 화살표).
- **반환 메시지** (Reply/Return) : 호출에 대한 결과 데이터를 반환 (점선 + 열린 화살표).

## Ⅲ. 복합 단편(Combined Fragments)의 주요 연산자

| 연산자 (Operator) | 의미 및 동작 메커니즘 | 실무 적용 시나리오 |
|---|---|---|
| **alt** (Alternative) | 다수의 조건 중 참([Guard])인 단 하나의 분기만을 상호 배타적으로 실행 | if-else 조건문 (예: 결제 성공 vs 잔액 부족 실패) |
| **opt** (Optional) | 조건이 참일 때만 선택적으로 단일 블록 실행 (else 없음) | 단순 if문 (예: 첫 결제 고객 대상 할인 쿠폰 발급) |
| **loop** | 가드 조건이나 지정된 횟수만큼 메시지 호출을 반복 실행 | for / while 반복문 (예: 장바구니 내 모든 상품 재고 차감) |
| **par** (Parallel) | 단편 내부의 하위 상호작용들이 동시에 병렬로 실행됨 | 멀티스레드 병렬 처리 (예: SMS 발송과 이메일 발송 동시 수행) |
| **critical** | 해당 임계 영역 내의 상호작용은 다른 스레드의 간섭 없이 원자적으로 실행 | 동기화 락(Lock) 블록 (예: 금융 계좌 출금 시 락 획득) |
| **break** | 특정 예외 조건 만족 시 나머지 시퀀스를 중단하고 즉시 탈출 | 예외 처리 (예: 인증 실패 시 트랜잭션 즉시 중단) |

## Ⅳ. 순차 다이어그램(Sequence Diagram)의 주요 한계점 및 해결 방안

- 비동기·병렬 이벤트 및 복합 제어 흐름 표현의 한계 :
  - 한계점 : 멀티스레드, 이벤트 루프, 카프카 기반 비동기 메시징 및 루프/조건 분기가 중첩될 경우 다이어그램 복잡도가 기하급수적으로 증가하여 가독성 상실.
  - 해결 방안 : 복잡한 제어 흐름은 상태 다이어그램이나 액티비티 다이어그램으로 분리, 결합 조각(Combined Fragments: alt, loop, par)을 최소화하고 핵심 정상 시나리오 중심 작성.
- 소스코드 변경 시 다이어그램 미반영으로 인한 문서 진부화 :
  - 한계점 : 개발 초기에 그렸던 순차 다이어그램이 코드 리팩토링 및 기능 추가 이후 갱신되지 않아 시스템의 실제 동작과 괴리 발생.
  - 해결 방안 : PlantUML, Mermaid 등을 활용한 Diagram-as-Code(문서 코드화) 도입, Git 버전 관리 및 PR 리뷰 시 다이어그램 갱신을 필수 체크리스트로 관리.
- 대규모 마이크로서비스 환경에서의 전체 상호작용 조망 한계 :
  - 한계점 : 수십 개의 마이크로서비스 간 호출 흐름을 단일 시퀀스 다이어그램에 표현하면 횡적 너비가 지나치게 넓어져 분석 불가능.
  - 해결 방안 : Jaeger, Zipkin 등 APM 분산 추적(Distributed Tracing) 도구와 연계하여 실제 런타임 호출 그래프로부터 서비스 단위 시퀀스 다이어그램 자동 추출.

## Ⅴ. 모델링 효율성 및 엔지니어링 연계를 위한 기술사적 제언

- 마이크로서비스 간 **분산 트랜잭션** (Saga) 설계 시 표준 명세 활용 : MSA 환경에서 서비스 간 비동기 메시징 및 보상 트랜잭션 흐름을 alt, par, loop 단편을 활용한 순차 다이어그램으로 사전에 엄격히 모델링하여, 분산 교착상태(Deadlock)나 이벤트 유실 사각지대 원천 차단.
- **PlantUML** / Mermaid 기반의 다이어그램 형상관리(Diagrams-as-Code) : GUI 도구로 그린 바이너리 이미지 대신 텍스트 기반 다이어그램 스크립트를 사용하여 Git 저장소에 소스코드와 함께 버전 관리하고, PR 리뷰 시 API 호출 흐름의 변경 사항을 시각적으로 대조 검증하는 엔지니어링 문화 정착.
