## 30초 인출

- 본질: **순차 다이어그램(Sequence Diagram)** 은 시스템을 구성하는 객체나 컴포넌트들이 특정 유스케이스 기능을 실체화(Realization)하기 위해 시간의 수직적 흐름에 따라 주고받는 메시지(동기, 비동기, 반환)와 활성화 구간을 시각화한 UML 동적 상호작용 다이어그램
- 메커니즘: 액터 및 객체 생명선(Lifeline) 배치 → 수직 시간축 기반 동기/비동기 메시지 전송 → 실행 활성 상자(Activation Bar) 제어 → 조건/반복 복합 프래그먼트(Combined Fragment) 분기 → 반환값 회신
- 통찰: 성공 시나리오(Happy Path) 위주의 단순 호출만 모델링하면 예외 처리나 네트워크 타임아웃 등 대안 흐름이 구현 단계에서 누락되므로 `alt`, `opt`, `par` 복합 프래그먼트를 활용하여 분기 및 동시성 제어 규격을 정밀하게 명시할 필요가 있음

<details>
<summary>핵심 용어</summary>

- **생명선 (Lifeline)** : 상호작용에 참여하는 객체나 컴포넌트의 존속 기간을 나타내는 수직 점선
- **활성 구간 (Activation Bar)** : 객체가 실제로 메서드를 실행하거나 제어권을 보유하고 있는 시간 블록(수직 직사각형)
- **동기 메시지 (Synchronous Message)** : 호출자가 수신자의 작업 완료 및 응답 반환을 블로킹(Blocking) 대기하는 호출 (실선 화살표와 닫힌 삼각형)
- **비동기 메시지 (Asynchronous Message)** : 호출자가 응답을 기다리지 않고 즉시 자신의 다음 작업을 수행하는 신호 (실선 화살표와 열린 화살표)
- **복합 프래그먼트 (Combined Fragment)** : 다이어그램 내에서 조건문(`alt`, `opt`), 반복문(`loop`), 병렬 처리(`par`) 등 제어 로직을 표현하는 사각형 프레임

</details>

## 2~4교시 예상문제 (25점)

> 객체지향 동적 모델링의 핵심인 순차 다이어그램(Sequence Diagram)의 개념과 구성요소를 설명하고, 4대 메시지 유형의 표기법 및 의미, 복합 프래그먼트(Combined Fragment)를 활용한 복합 제어 흐름 표현 및 통신 다이어그램과의 비교 분석을 제시하시오.

---

## 2~4교시 25점 답안

## Ⅰ. 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 유스케이스 실체화를 위해 다수의 객체들이 메시지를 교환하며 협력하는 과정을 시간의 경과(위에서 아래로)에 따라 시각화한 UML 행위 다이어그램 |
| 목적 | 객체 간 메시지 호출 순서와 인터페이스 규격 정형화, 동기/비동기 상호작용 제약 명시, API 상세 설계 및 단위/통합 테스트 케이스 도출 기준 제공 |

## Ⅱ. 핵심 특징

수평 축에는 협력 객체들을 배치하고, 수직 축에는 시간의 흐름을 단방향으로 전개하여 상호작용의 인과 관계 명확화.

| 핵심 구성요소 | 표기법 및 시각 표현 | 의미 및 동작 규칙 |
|---|---|---|
| **액터 / 객체 (Actor/Object)** | 사각형 상자 또는 사람 아이콘 | 상호작용의 주체 (클래스 인스턴스, 외부 시스템, 사용자) |
| **생명선 (Lifeline)** | 상자 하단으로 뻗은 수직 점선 | 해당 객체가 시스템 런타임 상에 존재하는 시간의 경과 |
| **활성 상자 (Activation)** | 생명선 위의 얇은 수직 직사각형 | 객체가 메서드를 직접 실행하거나 CPU/자원을 점유하고 있는 구간 |
| **생성/소멸 (Create/Destroy)** | `<<create>>` 화살표 및 하단 대형 X 표 | 런타임에 동적으로 객체가 메모리에 할당되거나 가비지 컬렉션되는 시점 |

## Ⅲ. 체계·프로세스

전자상거래 주문/결제 프로세스를 예시로 한 순차 다이어그램 및 복합 프래그먼트 체계.

```text
[주문/결제 유스케이스 순차 다이어그램 체계]
고객 (Actor)             주문 컨트롤러 (OrderCtrl)       결제 서비스 (PayService)     PG사 게이트웨이 (PG)
        │                              │                              │                              │
        │ (1) 동기: 주문제출(orderId)  │                              │                              │
        ├─────────────────────────────>│                              │                              │
        │                              │ (2) 동기: 결제요청(amount)   │                              │
        │                              ├─────────────────────────────>│                              │
        │                              │                              │ (3) 동기: 승인요청(cardInfo) │
        │                              │                              ├─────────────────────────────>│
        │                              │                              │                              │
        │                              │                              │ < - - - - - - - - - - - - - -┤ (4)
        │                              │                              │ (결제승인 결과 반환)         │
        │                              │                              │                              │
  ══════╪══════════════════════════════╪══════════════════════════════╪══════════════════════════════╪═════
  [alt : 결제 결과 분기]               │                              │                              │
  ─────────────────────────────────────┼──────────────────────────────┼──────────────────────────────┼─────
  [조건: 결제 성공 == true]            │                              │                              │
        │                              │ < - - - - - - - - - - - - - -┤ (5-1) 결제완료 회신          │
        │                              │                              │                              │
        │                              │ (6) 비동기: 배송지시 알림    │                              │
        │                              ├─────────────────────────┐    │                              │
        │                              │                         │    │                              │
        │                              │<────────────────────────┘    │                              │
        │ < - - - - - - - - - - - - - -┤ (7) 주문성공 페이지 반환     │                              │
  ─────────────────────────────────────┼──────────────────────────────┼──────────────────────────────┼─────
  [else : 결제 실패 / 한도초과]        │                              │                              │
        │ < - - - - - - - - - - - - - -┤ (5-2) 결제실패 에러 반환     │                              │
  ══════╪══════════════════════════════╪══════════════════════════════╪══════════════════════════════╪═════
        ▼ 시간 흐름 (Time Flow)        ▼                              ▼                              ▼
```

- **순차 다이어그램 작성 4단계 프로세스**:
  1. **상호작용 컨텍스트 정의** : 실체화할 단일 유스케이스 또는 시나리오 범위를 확정하고 참여 객체 목록 도출.
  2. **생명선 및 기본 메시지 흐름 배치** : 왼쪽에서 오른쪽으로 호출 순서에 맞추어 생명선을 배열하고 시간 순서대로 메시지 연결.
  3. **복합 프래그먼트(Fragment) 추가** : 실패 예외 분기(`alt`), 조건부 부가 실행(`opt`), 다중 항목 반복(`loop`) 영역 구획화.
  4. **인터페이스 정합성 교차 검증** : 순차 다이어그램의 메시지 시그니처가 클래스 다이어그램의 공개 메서드와 100% 일치하는지 확인.

## Ⅳ. 종류·비교

#### 4대 메시지 유형 표기법 및 메커니즘 비교

| 메시지 유형 | 표기법 | 동작 메커니즘 | 실무 구현 사례 |
|---|---|---|---|
| **동기 메시지 (Synchronous)** | 실선 + 꽉 찬 삼각형 화살표 (`──>`) | 호출 후 응답이 올 때까지 제어권을 넘기고 블로킹 대기 | Java/Spring 동기 메서드 호출, HTTP/REST GET |
| **비동기 메시지 (Asynchronous)**| 실선 + 열린 화살표 (`──>`) | 응답을 기다리지 않고 메시지 전송 후 즉시 다음 로직 수행 | Kafka/RabbitMQ 이벤트 발행, WebSocket 신호 |
| **반환 메시지 (Reply/Return)** | 점선 + 열린 화살표 (`< - -`) | 호출된 메서드의 실행 완료 및 결괏값 회신 (생략 가능) | return 결괏값, HTTP 200 OK 응답 본문 |
| **자체 메시지 (Self/Recursive)**| ㄷ자 모양의 꺾인 실선 화살표 | 객체 내부의 private 보조 메서드 호출 또는 재귀 호출 | 내부 데이터 유효성 검증 함수 실행 |

#### 주요 복합 프래그먼트 (Combined Fragment) 비교

| 프래그먼트 키워드 | 제어 의미 | 공학적 적용 목적 |
|---|---|---|
| **`alt` (Alternative)** | 상호 배타적인 조건 분기 (`if-else`) | 정상 승인 경로와 결제 실패 예외 경로의 분리 모델링 |
| **`opt` (Optional)** | 조건이 참일 때만 실행되는 단일 분기 (`if`) | 쿠폰이 존재할 때만 할인 적용 로직 실행 |
| **`loop` (Loop)** | 조건이 참인 동안 반복 실행 (`for/while`) | 장바구니 내 모든 품목에 대한 재고 차감 반복 |
| **`par` (Parallel)** | 둘 이상의 하위 상호작용을 병렬로 동시 수행 | 주문 완료 시 결제 영수증 이메일과 SMS 알림 동시 발송 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 복잡한 예외 분기와 반복 로직을 과도하게 포함하여 다이어그램의 가독성과 이해도 급격 저하 | 복잡한 제어 흐름은 활동 다이어그램(Activity)으로 분리하고 순차도는 핵심 협력 인터페이스 위주로 단순화 |
| 설계 단계의 순차 다이어그램과 실제 구현된 소스코드 간의 메서드명 및 파라미터 불일치 | PlantUML, Mermaid 등 코드 기반 다이어그램(Diagrams-as-Code)을 도입하여 Git 기반 형상 동기화 |
| 참여 객체 수가 수십 개로 늘어나 가로 스크롤이 과도해지는 문제 | 서브시스템 단위로 다이어그램을 모듈화하고 `ref` 프래그먼트를 활용하여 하위 시퀀스를 참조 연결 |

## Ⅵ. 제언

순차 다이어그램은 단순한 문서화 도구가 아닌 마이크로서비스 간 비동기 이벤트 통신 및 API 게이트웨이 라우팅을 설계하는 정밀 청사진이므로, 코드 기반 모델링(PlantUML)을 통해 CI/CD 파이프라인과 일치성을 유지

```text
[유스케이스 명세서] ──> [PlantUML 순차 다이어그램] ──> [Spring/gRPC 인터페이스 구현] ──> [E2E 통합 테스트 검증]
  (시나리오 정상/대안)        (Git 형상 관리 & 코드화)          (메서드 시그니처 100% 매핑)         (메시지 순서 일치 확인)
```

| 설계 영역 | 핵심 권장 실천법 | 통제 지표 |
|---|---|---|
| **설계 코드화** | PlantUML / Mermaid 텍스트 기반 다이어그램 작성 | PR 단위 아키텍처 다이어그램 변경 이력 100% 추적 |
| **인터페이스 검증** | OpenAPI(Swagger) 스펙과 순차도 메시지 일치성 검증 | API 명세서와 순차 다이어그램 간 불일치율 0% |
| **테스트 연계** | 순차 다이어그램의 메시지 흐름을 통합 테스트 시나리오로 변환 | 핵심 비즈니스 유스케이스 시퀀스 테스트 커버리지 90% 달성 |
