## 연관 키워드

- 순차 다이어그램(Sequence Diagram), UML(Unified Modeling Language), 생명선(Lifeline)
- 활성 객체(Execution Occurrence), 메시지(Message), 복합 단편(Combined Fragments), Diagram-as-Code

## Ⅰ. 순차 다이어그램의 개요

- 핵심 요약 : 객체들이 주고받는 메시지를 시간 순서대로 나타내 동적 상호작용을 설계하고 검증하는 UML 행위 다이어그램.
- 개념 : 하나의 기능 시나리오를 달성하려고 객체나 서비스 컴포넌트가 시간 순서에 따라 메시지를 주고받는 과정을 표현하는 **순차 다이어그램** (Sequence Diagram)으로, UML(Unified Modeling Language)의 동적 행위 다이어그램에 속함.
- 배경 및 필요성 : 클래스 다이어그램만으로는 런타임의 호출 순서, 반환값, 비동기 이벤트 흐름을 드러내기 어려워 인터페이스 설계와 결함 분석의 기준이 필요.
- 주요 목적 : 메시지 흐름의 시각적 명세, 인터페이스 설계 검증, 비동기 이벤트 흐름 분석.

## Ⅱ. 순차 다이어그램의 특징 및 장점

- 핵심 요약 : 생명선, 활성 객체, 메시지, 복합 단편의 네 요소로 시간 순서의 상호작용을 구조화하는 모델링.

1. **생명선** (Lifeline) : 참여 객체를 나타내며 위에서 아래로 흐르는 수직 점선으로 시간 경과를 표현 → 객체가 존재하는 구간 확인.
2. **활성 객체** (Execution Occurrence) : 메시지를 받아 연산을 수행하는 구간을 직사각형 막대로 표시 → 처리 시간 구간 파악.
3. 동기, 비동기, 반환 메시지 : 채워진 화살표, 열린 화살표, 점선 화살표로 구분 → API(Application Programming Interface)의 동기성과 응답 구조 검토.
4. **복합 단편** (Combined Fragments) : alt, opt, loop, par 같은 연산자로 조건, 반복, 병렬 흐름을 표현 → 제어 흐름을 한 장에 담음.

## Ⅲ. 순차 다이어그램의 구조 (흐름)

- 핵심 요약 : 생명선 사이를 메시지가 시간 순으로 오가고, 복합 단편이 조건과 반복을 감싸는 구조.

```text
[ :Client ]
    │ 1. createOrder() (동기)
    ▼
[ :OrderService ]
    │ 2. processPay() (동기)
    ▼
[ :PaymentGateway ]
    │ 3. 반환 (점선 화살표)
    ▼
[ :OrderService ]
    │ 4. 이벤트 발행 (비동기)
    ▼
[ :Client ]
```

- 복합 단편의 분기 흐름 : alt는 조건에 따라 서로 다른 메시지 경로를 택한다.

```text
[ alt (조건 분기) ]
  잔액 충분 → 결제 승인 → 주문 확정
  잔액 부족 → 결제 실패 → 고객 통보
```

- 반복 흐름 : loop는 같은 메시지를 조건이 만족하는 동안 반복한다.

```text
[ loop (반복) ]
  장바구니 상품 수만큼 재고 차감 반복
```

## Ⅳ. 클래스 다이어그램과 순차 다이어그램의 비교

- 핵심 요약 : 정적 구조를 나타내는 클래스 다이어그램과 동적 행위를 나타내는 순차 다이어그램의 목적 차이.

| 비교 항목 | 클래스 다이어그램(Class Diagram) | 순차 다이어그램(Sequence Diagram) |
| --- | --- | --- |
| 모델링 차원 | 정적 구조 | 동적 행위 |
| 표현 대상 | 클래스, 속성, 연관 관계 | 객체 간 메시지 교환 순서 |
| 시간 축 | 없음 | 수직 방향으로 시간 경과 |
| 주요 용도 | 도메인 모델링, 스키마 설계 | 유스케이스 실현, 인터페이스 설계 |
| 상호작용 표현 | 표현 불가 | 동기와 비동기 메시지 흐름 표현 |

- 선택 기준 : 구조와 관계를 설계할 때는 클래스 다이어그램, 객체 간 호출 순서와 응답을 검증할 때는 순차 다이어그램을 사용.

## Ⅴ. 순차 다이어그램의 장점과 한계

- 핵심 요약 : 런타임 상호작용의 직관적 가시화가 장점이며, 복잡한 제어 흐름과 문서 진부화, 대규모 서비스 조망이 한계.

1. 런타임의 메서드 호출 순서와 반환값을 직관적으로 표현.
2. 동기와 비동기 구분으로 API 인터페이스 설계 검증에 적합.
3. 복합 단편으로 조건, 반복, 병렬 흐름을 구조적으로 표현.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 비동기와 병렬 흐름의 가독성 저하 | 멀티스레드, 메시지 큐 기반 비동기 호출과 중첩 분기로 도식이 급격히 복잡해짐 | 복잡한 흐름은 상태 다이어그램이나 액티비티 다이어그램으로 분리하고 정상 시나리오 중심으로 작성 | 한 다이어그램의 메시지 수 |
| 코드 변경 후 문서 진부화 | 리팩토링과 기능 추가 후 다이어그램이 갱신되지 않아 실제 동작과 괴리 | **Diagram-as-Code** (PlantUML, Mermaid 등 텍스트 기반 작성) 도입, PR 리뷰 시 갱신을 체크리스트로 관리 | 코드 변경 대비 다이어그램 갱신율 |
| 대규모 마이크로서비스의 조망 한계 | 수십 개 서비스 호출을 한 다이어그램에 담으면 분석이 불가능 | 분산 추적(Distributed Tracing) 도구의 실제 호출 데이터로 서비스 단위 다이어그램을 자동 추출 | 추적 구간 누락률 |

## Ⅵ. 순차 다이어그램에 대한 기술사적 제언

- 핵심 요약 : 분산 환경의 보상 트랜잭션을 사전에 명세하고, 다이어그램을 코드와 함께 버전 관리하는 문화를 정착시키는 것이 필요.

1. 마이크로서비스(MSA, Microservice Architecture) 환경에서 서비스 간 메시지와 보상 트랜잭션 흐름은 순차 다이어그램의 복합 단편으로 미리 그려 보아야 한다. 이렇게 하면 사가(Saga) 패턴의 교착 상태나 이벤트 유실 지점을 구현 전에 확인할 수 있다.
2. 그래픽 도구로 그린 이미지 대신 텍스트 기반 다이어그램 스크립트를 Git 저장소에 소스와 함께 두고, PR 리뷰에서 호출 흐름의 변경을 대조하는 엔지니어링 관행을 세워야 한다.

## Ⅶ. 결론

- 핵심 요약 : 순차 다이어그램은 객체 간 메시지 흐름을 시간 순으로 명세하는 UML 동적 모델링 도구.
- 시사점 : 텍스트 기반 코드화와 분산 추적 연동이 있어야 문서 진부화를 막고 분산 환경에서도 실효성을 유지할 수 있음.
