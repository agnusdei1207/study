## 연관 키워드

- 순차 다이어그램(Sequence Diagram), UML(Unified Modeling Language), 생명선(Lifeline)
- 활성 객체(Execution Occurrence), 메시지(Message), 복합 단편(Combined Fragments), Diagram-as-Code

## Ⅰ. 순차 다이어그램의 개요

- 핵심 요약 : 객체 간 시간 순서에 따른 메시지 상호작용을 시각적 모델링한 UML 동적 행위 다이어그램.
- 개념 : 객체지향 소프트웨어 시스템에서 특정 유스케이스나 기능 시나리오를 달성하기 위해 복수의 객체(또는 서비스 컴포넌트)들이 시간의 흐름(순서)에 따라 서로 주고받는 메시지(동기, 비동기)의 상호작용을 시각적으로 모델링한 UML(Unified Modeling Language) 동적 행위 다이어그램.
- 배경 및 필요성 : 클래스 다이어그램만으로는 파악하기 어려운 런타임 시점의 구체적인 메서드 호출 순서, 반환값, 객체의 생명주기, 비동기 이벤트 흐름을 직관적으로 명시하여 API(Application Programming Interface) 인터페이스 설계 및 결함 디버깅의 기준 제공 필요.
- 주요 목적 : 객체 간 메시지 흐름의 시각적 명세, 인터페이스 설계 검증, 비동기 이벤트 흐름 분석.

## Ⅱ. 순차 다이어그램의 특징

- 핵심 요약 : 생명선, 활성 객체, 메시지, 복합 단편의 4대 핵심 요소로 구성된 시간 중심 상호작용 모델링.

1. 생명선(Lifeline) : 상호작용에 참여하는 객체를 나타내며, 위에서 아래로 흐르는 수직 점선으로 시간의 경과 표현.
2. 실행 상자(Activation Box) : 객체가 메시지를 수신하여 실제로 연산을 수행하고 있는 시간 구간을 직사각형 막대로 표시.
3. 동기/비동기/반환 메시지 : 호출-응답 패턴에 따른 3가지 메시지 유형 구분.
4. 복합 단편(Combined Fragments) : alt, opt, loop, par 등 조건·반복·병렬 제어 흐름을 표현하는 연산자.

## Ⅲ. 순차 다이어그램의 구조 (흐름)

- 핵심 요약 : 생명선 간 시간 순서에 따른 메시지 교환과 복합 단편의 제어 흐름 표현 구조.
- 메시지 상호작용 기본 구조.

```text
[ :Client ]
    │ 1. createOrder()
    │    (동기 호출: 채워진 화살표)
    ▼
[ :OrderService ]
    │ 2. processPay() (동기 호출)
    ▼
[ :PaymentGateway ]
    │ 3. return (success)
    │    (반환 메시지: 점선 화살표)
    ▼ (호출 역순으로 반환)
[ :OrderService ]
    │ 4. sendKafkaEvent()
    │    (비동기 메시지: 열린 화살표)
    │ 5. orderCreated (반환)
    ▼
[ :Client ]
```

- 복합 단편 제어 흐름 구조.

```text
[ alt (조건 분기) ]
  ├─ [잔액 충분] -> [결제 승인] -> [주문 확정]
  └─ [잔액 부족] -> [결제 실패] -> [고객 통보]

[ loop (반복) ]
  └─ [장바구니 상품 수만큼] -> [재고 차감] x N
```

## Ⅳ. 클래스 다이어그램과 순차 다이어그램의 비교

- 핵심 요약 : 정적 구조 중심과 동적 행위 중심의 모델링 목적과 표현 대상 비교.

| 비교 항목 | 클래스 다이어그램(Class Diagram) | 순차 다이어그램(Sequence Diagram) |
|---|---|---|
| 모델링 차원 | 정적 구조(Static Structure) | 동적 행위(Dynamic Behavior) |
| 표현 대상 | 클래스, 속성, 연관 관계 | 객체 간 메시지 교환 순서 |
| 시간 축 | 없음 | 수직 방향 시간 경과 |
| 주요 용도 | 도메인 모델링, 스키마 설계 | 유스케이스 실현, 인터페이스 설계 |
| 상호작용 표현 | 불가 | 동기/비동기 메시지 흐름 상세 표현 |

## Ⅴ. 순차 다이어그램의 장점과 한계

- 핵심 요약 : 런타임 상호작용의 직관적 가시화 장점, 복잡한 제어 흐름과 문서 진부화의 한계.
- 장점
  1. 런타임 시점의 메서드 호출 순서와 반환값을 직관적으로 표현.
  2. 동기/비동기 메시지 구분으로 API 인터페이스 설계 검증에 적합.
  3. 복합 단편으로 조건·반복·병렬 제어 흐름을 구조적으로 표현.
- 한계점 1 : 비동기·병렬 이벤트 및 복합 제어 흐름 표현의 한계
  - 한계점 : 멀티스레드, 이벤트 루프, 카프카(Kafka) 기반 비동기 메시징 및 루프/조건 분기가 중첩될 경우 다이어그램 복잡도가 기하급수적으로 증가하여 가독성 상실.
  - 해결 방안 : 복잡한 제어 흐름은 상태 다이어그램이나 액티비티 다이어그램으로 분리, 결합 조각(Combined Fragments: alt, loop, par)을 최소화하고 핵심 정상 시나리오 중심 작성.
- 한계점 2 : 소스코드 변경 시 다이어그램 미반영으로 인한 문서 진부화
  - 한계점 : 개발 초기에 그렸던 순차 다이어그램이 코드 리팩토링 및 기능 추가 이후 갱신되지 않아 시스템의 실제 동작과 괴리 발생.
  - 해결 방안 : PlantUML, Mermaid 등을 활용한 Diagram-as-Code(문서 코드화) 도입, Git 버전 관리 및 PR(Pull Request) 리뷰 시 다이어그램 갱신을 필수 체크리스트로 관리.
- 한계점 3 : 대규모 마이크로서비스 환경에서의 전체 상호작용 조망 한계
  - 한계점 : 수십 개의 마이크로서비스 간 호출 흐름을 단일 시퀀스 다이어그램에 표현하면 횡적 너비가 지나치게 넓어져 분석 불가능.
  - 해결 방안 : Jaeger, Zipkin 등 APM(Application Performance Monitoring) 분산 추적(Distributed Tracing) 도구와 연계하여 실제 런타임 호출 그래프로부터 서비스 단위 시퀀스 다이어그램 자동 추출.

## Ⅵ. 순차 다이어그램에 대한 기술사적 제언

- 핵심 요약 : MSA 환경의 Saga 트랜잭션 명세와 Diagram-as-Code 기반 형상관리 정착 필요.
- 마이크로서비스 간 분산 트랜잭션(Saga) 설계 시 표준 명세 활용 : MSA(Microservice Architecture) 환경에서 서비스 간 비동기 메시징 및 보상 트랜잭션 흐름을 alt, par, loop 단편을 활용한 순차 다이어그램으로 사전에 엄격히 모델링하여, 분산 교착상태(Deadlock)나 이벤트 유실 사각지대 원천 차단 필요.
- PlantUML / Mermaid 기반의 다이어그램 형상관리(Diagrams-as-Code) : GUI(Graphical User Interface) 도구로 그린 바이너리 이미지 대신 텍스트 기반 다이어그램 스크립트를 사용하여 Git 저장소에 소스코드와 함께 버전 관리하고, PR 리뷰 시 API 호출 흐름의 변경 사항을 시각적으로 대조 검증하는 엔지니어링 문화 정착 필요.

## Ⅶ. 결론

- 핵심 요약 : 순차 다이어그램은 객체 간 메시지 흐름의 시각적 명세 도구로 코드화와 분산 추적 연동이 실효성의 관건.
- 요약 : 객체 간 시간 순서에 따른 메시지 상호작용을 생명선, 활성 객체, 메시지, 복합 단편으로 모델링하는 UML 동적 행위 다이어그램.
- 시사점 : Diagram-as-Code 도입, 복합 단편 최소화, 분산 추적 도구 연동의 3요소가 문서 진부화 방지와 분산 환경 대응의 전제 조건.
