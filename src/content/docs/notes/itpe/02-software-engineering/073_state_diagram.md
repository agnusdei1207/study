## Ⅰ. 상태 다이어그램의 개요

- **개념** : 시스템 내부의 객체나 프로세스가 외부 이벤트에 반응하여 시간에 따라 변화하는 상태(State)와 상태 간의 전이(Transition) 규칙을 시각적으로 모델링한 UML 동적 행위 다이어그램.
- **배경 및 필요성** : 복잡한 생명주기를 가진 도메인 엔티티(주문, 결제, 티켓 상태)나 임베디드 기기, 프로토콜 제어기에서 유효하지 않은 불법 전이(Illegal Transition)를 방지하고 상태 불변식을 검증하기 위해 필수.
- **핵심 요소** : 상태(State), 시작/종료 상태, 이벤트(Event), 가드 조건(Guard Condition), 동작(Action), 전이(Transition).

## Ⅱ. 상태 전이 모델 및 복합 상태 구조

```text
   (● 시작 상태)
        │
        │ [회원가입 완료]
        ▼
   ┌────────────────────────────────────────────────────────┐
   │ [ 대기 상태 (Pending) ]                                 │
   │  entry / 이메일 인증 발송                               │
   │  do / 타이머 카운트다운 (24시간)                        │
   └──────────────────────────┬─────────────────────────────┘
                              │
          이벤트: [인증 링크 클릭] [가드: 유효시간 이내] / 액션: 계정 활성화
                              │
                              ▼
   ┌────────────────────────────────────────────────────────┐
   │ [ 활성 상태 (Active) ]                                  │
   │  ┌──────────────────────────────────────────────────┐  │
   │  │ [ 복합 서브 상태: 일반회원 <-> VIP회원 ]        │  │
   │  └──────────────────────────────────────────────────┘  │
   └──────────────────────────┬─────────────────────────────┘
                              │
          이벤트: [회원 탈퇴 신청]
                              ▼
                      (◎ 최종 종료 상태)
```

- **상태의 내부 활동 3요소** :
  - **entry** : 해당 상태에 진입할 때 즉시 1회 실행되는 액션.
  - **do** : 해당 상태에 머무르는 동안 지속적으로 실행되는 백그라운드 작업.
  - **exit** : 해당 상태를 빠져나갈 때 반드시 1회 실행되는 정리 액션.
- **전이 표기법** : `이벤트 [가드조건] / 액션` (이벤트가 발생하고 가드조건이 참일 때 액션을 실행하며 다음 상태로 전이).

## Ⅲ. 주요 UML 행위 다이어그램 간의 비교

| 비교 항목 | 상태 다이어그램 (State) | 활동 다이어그램 (Activity) | 시퀀스 다이어그램 (Sequence) |
|---|---|---|---|
| 모델링 초점 | '단일 객체'의 생명주기 및 상태 변화 | '전체 시스템'의 업무 프로세스 및 워크플로우 | '여러 객체 간'의 시간 순서에 따른 메시지 교환 |
| 제어 주체 | 외부에서 유입되는 이벤트(Event-driven) | 선행 작업 완료에 따른 내부 제어 흐름(Flow-driven) | 호출자와 피호출자 간의 동기/비동기 호출 |
| 주 활용 대상 | 주문 상태, 결제 트랜잭션, 임베디드 제어기 | 비즈니스 업무 절차, 알고리즘 로직 흐름 | API 호출 시퀀스, 마이크로서비스 연동 흐름 |

## Ⅳ. 상태 머신 구현 및 검증을 위한 기술사적 제언

- **상태 패턴(State Pattern)을 적용한 안티패턴 제거** : 클래스 내부에 거대한 if-else나 switch-case 문으로 상태 전이를 하드코딩하면 새로운 상태 추가 시 OCP를 위반하므로, GoF 상태 패턴을 적용하여 각 상태를 독립 클래스로 캡슐화 권장.
- **상태 전이 기반 테스트 케이스(State Transition Testing) 전수 도출** : 상태 다이어그램의 상태 전이 표(State Transition Table)를 작성하고, 0-스위치(모든 유효 전이 1회 방문) 및 1-스위치(연속 2회 전이 쌍 방문) 커버리지를 충족하는 인수 테스트 자동화 필수.
