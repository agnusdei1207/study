## 연관 키워드

- UML(Unified Modeling Language), 상태(State), 전이(Transition), 이벤트(Event), 가드 조건(Guard Condition)
- entry/do/exit 활동, 상태 폭발(State Explosion), 하렐 상태차트(Harel Statechart), 사가 패턴(Saga Pattern), 상태 전이 테스팅(State Transition Testing), 상태 패턴(State Pattern)

## Ⅰ. 상태 다이어그램의 개요

- 핵심 요약 : 객체의 생명주기를 이벤트 기반 상태 전이 모델로 시각화하는 UML 동적 행위 다이어그램.
- 개념 : 시스템 내부의 객체나 프로세스가 외부 이벤트에 반응하여 시간에 따라 변화하는 상태(State)와 상태 간 전이(Transition) 규칙을 시각적으로 모델링한 UML(Unified Modeling Language) 동적 행위 다이어그램.
- 배경 및 필요성 : 복잡한 생명주기를 가진 도메인 엔티티(주문, 결제, 티켓 상태)나 임베디드 기기, 프로토콜 제어기에서 유효하지 않은 불법 전이(Illegal Transition)의 방지와 상태 불변식 검증 필요.
- 주요 목적 : 유효 상태 공간의 체계적 관리를 통한 도메인 생명주기의 명확한 정의.

## Ⅱ. 상태 다이어그램의 특징

- 핵심 요약 : 이벤트-가드-액션 표기의 상태 전이와 entry/do/exit 내부 활동으로 객체 행위를 정밀하게 기술하는 특성.

1. 이벤트 구동(Event-driven) 모델링 : 외부에서 유입되는 이벤트가 상태 전이의 유발 주체.
2. 전이 표기법 : `이벤트 [가드조건] / 액션` 형식으로 전이 조건과 부수 효과의 동시 명시.
3. 상태 내부 활동 3요소 : entry(상태 진입 시 즉시 1회 실행 액션), do(상태 체류 중 지속 실행 백그라운드 작업), exit(상태 탈출 시 반드시 1회 실행 정리 액션).
4. 복합 상태(Composite State) : 슈퍼상태(Superstate)와 서브 상태의 계층 구조 및 직교 영역(Orthogonal Region)을 통한 병렬 상태 표현.
5. 단일 객체 시점 : 여러 객체 간 메시지 교환이 아닌 하나의 객체 생명주기에 대한 집중 모델링.

## Ⅲ. 상태 다이어그램의 구조 (흐름)

- 핵심 요약 : 시작 상태에서 대기·활성 상태를 거쳐 종료 상태에 이르는 이벤트 기반 생명주기 흐름.
- 회원 계정 생명주기 상태 머신 예시.

```text
(● 시작 상태)
   │ 회원가입 완료
   ▼
[ 대기 상태 (Pending) ]
 - entry / 이메일 인증 발송
 - do / 타이머 카운트다운 (24시간)
   │
   │ 이벤트: 인증 링크 클릭
   │ 가드: 유효시간 이내 / 액션: 계정 활성화
   ▼
[ 활성 상태 (Active) ]
 - 복합 서브 상태: 일반회원 <-> VIP회원
   │
   │ 이벤트: 회원 탈퇴 신청
   ▼
(◎ 최종 종료 상태)
```

- 단일 전이의 내부 처리 순서.

```text
[ 이벤트 발생 ] ──▶ [ 가드 조건 평가 ] ──▶ [ 액션 실행 ] ──▶ [ 다음 상태 전이 ]
                          │ 가드 거짓
                          ▼
                   [ 현재 상태 유지 ]
```

## Ⅳ. 주요 UML 행위 다이어그램 간의 비교

- 핵심 요약 : 단일 객체의 상태 변화, 시스템 전체의 업무 흐름, 객체 간 메시지 시간 순서라는 상이한 모델링 초점.
- 상태 다이어그램과 활동 다이어그램, 시퀀스 다이어그램의 초점 차이 구분 필요.

| 비교 항목 | 상태 다이어그램 (State) | 활동 다이어그램 (Activity) | 시퀀스 다이어그램 (Sequence) |
|---|---|---|---|
| 모델링 초점 | '단일 객체'의 생명주기 및 상태 변화 | '전체 시스템'의 업무 프로세스 및 워크플로우 | '여러 객체 간'의 시간 순서에 따른 메시지 교환 |
| 제어 주체 | 외부에서 유입되는 이벤트(Event-driven) | 선행 작업 완료에 따른 내부 제어 흐름(Flow-driven) | 호출자와 피호출자 간의 동기/비동기 호출 |
| 주 활용 대상 | 주문 상태, 결제 트랜잭션, 임베디드 제어기 | 비즈니스 업무 절차, 알고리즘 로직 흐름 | API(Application Programming Interface) 호출 시퀀스, 마이크로서비스 연동 흐름 |

## Ⅴ. 상태 다이어그램의 장점과 한계

- 핵심 요약 : 불법 전이 차단과 테스트 도출의 강점, 상태 폭발과 모델-코드 불일치의 한계.
- 장점

  1. 유효하지 않은 불법 전이(Illegal Transition)의 사전 차단 및 상태 불변식 검증.
  2. 상태 전이 표(State Transition Table) 기반 테스트 케이스의 체계적 전수 도출.
  3. 복잡한 도메인 생명주기에 대한 이해관계자 공통 언어 확보.
- 한계점 1 : 복합 시스템 모델링 시 상태 폭발(State Explosion)
  - 한계점 : 시스템의 변수와 동시성 제어 요건 증가에 따라 가능한 상태 및 전이 수가 지수적으로 증가하여 다이어그램 가독성 및 유지보수성 상실.
  - 해결 방안 : 하렐 상태차트(Harel Statechart) 개념 적용을 통한 계층적 슈퍼상태(Superstate) 및 직교/병렬 상태(Orthogonal Regions) 구조화.
- 한계점 2 : 분산·비동기 마이크로서비스 환경에서의 상태 불일치
  - 한계점 : 네트워크 분할 및 비동기 이벤트 전달 지연으로 인한 서비스 간 전역 상태 일관성 보장의 난제.
  - 해결 방안 : 분산 사가 패턴(Saga Pattern) 오케스트레이터 연계, 이벤트 소싱(Event Sourcing) 기반 상태 재구성 및 상태 전이 멱등성 보장.
- 한계점 3 : 모델과 구현 코드 간 동기화 누락(Architectural Drift)
  - 한계점 : 설계 시 작성된 상태 다이어그램의 코드 동기화 실패 및 레거시 문서화 전락.
  - 해결 방안 : XState, Spring Statemachine 등 상태 머신 프레임워크 도입을 통한 JSON(JavaScript Object Notation)/XML(Extensible Markup Language)/DSL(Domain-Specific Language) 정의 기반 실행 코드 자동 생성 및 역공학 검증.

## Ⅵ. 상태 머신 구현 및 검증에 대한 기술사적 제언

- 핵심 요약 : 상태 패턴 기반 구현과 상태 전이 커버리지 자동화의 병행.
- 상태 패턴(State Pattern) 적용을 통한 안티패턴 제거 : 클래스 내부의 거대한 if-else 및 switch-case 하드코딩은 새로운 상태 추가 시 OCP(Open-Closed Principle) 위반이므로, GoF(Gang of Four) 상태 패턴 적용을 통한 각 상태의 독립 클래스 캡슐화 권장.
- 상태 전이 기반 테스트 케이스(State Transition Testing) 전수 도출 : 상태 전이 표(State Transition Table) 작성 후 0-스위치(모든 유효 전이 1회 방문) 및 1-스위치(연속 2회 전이 쌍 방문) 커버리지 충족 인수 테스트 자동화 필수.

## Ⅶ. 결론

- 핵심 요약 : 상태 다이어그램은 이벤트 기반 객체 생명주기의 검증 가능한 단일 기준 모델.
- 요약 : 이벤트-가드-액션 기반의 상태 전이 모델링으로 유효 상태 공간을 명확히 규정하는 설계·검증 자산.
- 시사점 : 상태 폭발 억제를 위한 계층화, 프레임워크 기반 모델-코드 일치 유지, 전이 커버리지 자동화의 병행이 고품질 상태 관리의 선결 조건.
