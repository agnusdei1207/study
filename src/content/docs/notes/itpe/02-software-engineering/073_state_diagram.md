## 30초 인출

- 본질: **상태 다이어그램** 은 단일 객체가 외부 이벤트에 반응해 상태가 변하는 생애주기를 유한 상태 머신(FSM)으로 모델링한 UML 행위 다이어그램
- 메커니즘: 이벤트 발생 → 가드 조건 `[조건]` 판정 → 상태 전이 → 액션(Entry/Do/Exit) 실행
- 통찰: 한계: 이벤트만 기록하고 가드를 빠뜨리면 허용되지 않은 상태 전이가 발생할 수 있음 → 방안: 전이 조건을 모델과 테스트에 함께 명시

<details>
<summary>핵심 용어</summary>

- **유한 상태 머신(FSM: Finite State Machine)** : 객체가 가질 수 있는 유한한 개수의 상태와 외부 입력에 따른 전이를 수학적으로 모델링한 기법
- **가드 조건(Guard Condition)** : 상태 전이가 실행되기 위해 반드시 참(True)으로 평가되어야 하는 전이 사전 조건 (`[조건]`)
- **상태 폭발(State Explosion)** : 도메인의 복잡도 증가에 따라 상태와 전이의 조합 수가 기하급수적으로 폭증하는 현상
- **복합 상태(Composite State)** : 여러 하위 상태를 계층화해 공통 전이와 동작을 표현하는 상태
- **얕은 이력 상태(Shallow History, H)** : 복합 상태에 재진입할 때 직전에 활성화된 직접 하위 상태를 복원하는 의사 상태. 더 깊은 중첩 상태까지 복원하려면 깊은 이력(H*)을 사용

</details>

## 2~4교시 25점 답안

## Ⅰ. 상태 다이어그램의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 상태 다이어그램은 이벤트에 따른 객체 상태와 전이를 표현하는 UML 행위 모델 |
| 목적 | 상태 의존 동작의 허용 조건과 객체 생애주기 표현 |

## Ⅱ. 상태 다이어그램의 특징과 구성요소

단일 객체의 생애주기를 대상으로 상태·이벤트·가드·액션의 허용 관계를 표시.

| 구성요소 | 표기법 및 표기 형식 | 의미 및 동작 규칙 |
|---|---|---|
| **상태 (State)** | 모서리가 둥근 사각형 | 객체가 특정 조건을 만족하거나 활동을 수행하는 기간 (Entry, Do, Exit 기술) |
| **전이 (Transition)** | 실선 화살표 | 특정 이벤트 발생 시 객체가 한 상태에서 다른 상태로 이동하는 경로 |
| **이벤트 (Event)** | 전이선 위 텍스트 | 전이를 촉발하는 외부 자극 (메서드 호출, 신호 수신, 타임아웃) |
| **가드 조건 (Guard)** | `[Boolean 식]` | 전이가 성립하기 위해 반드시 참(True)이어야 하는 조건 (거짓이면 전이 차단) |
| **액션 (Action)** | `/ action_name()` | 전이 효과 또는 상태의 진입·종료 효과로 실행되는 동작. 상태에 머무는 동안 지속되는 `doActivity`와 구분 |

## Ⅲ. 주문 객체의 상태 전이 체계

```text
시작 ─ 주문 생성 → 주문대기
주문대기 ─ 결제 승인 [재고 있음] → 결제완료
결제완료 ─ 출고 → 배송중 ─ 배송 완료 → 수령완료
주문대기 ─ 결제 시간 초과 → 주문취소
수령완료·주문취소 → 종료
```

전이의 `이벤트 [가드] / 액션` 조건을 상태 전이표와 테스트에 함께 기록.

## Ⅳ. UML 행위 다이어그램 비교와 상태 모델 확장

**행위 다이어그램의 관점 비교**

| 비교 항목 | 유스케이스 다이어그램 (Use-Case) | 활동 다이어그램 (Activity) | 상태 다이어그램 (State) |
|---|---|---|---|
| **모델링 관점** | 시스템 외부 요구사항 (What) | 비즈니스 업무 처리 흐름 (How Flow) | **단일 객체의 생애주기 (How Life-cycle)** |
| **핵심 초점** | 액터와 시스템 간의 기능적 상호작용 | 처리 단계(Step), 분기, 병렬 동기화 | **이벤트에 따른 내부 상태 변화 및 가드 조건** |
| **적용 단위** | 전체 시스템 범위 | 비즈니스 프로세스, 알고리즘 로직 | **상태 의존적인 핵심 도메인 객체 단위** |
| **주요 산출물** | 유스케이스 명세서, 기능 요구사항서 | 업무 흐름도, 트랜잭션 흐름 설계서 | 상태 전이표, 상태 머신 도메인 클래스 |

**복잡한 상태 모델의 표현 기법**
1. **복합 상태 (Composite State)** : 연관된 하위 상태들을 묶어 슈퍼 상태(Super-state)로 계층화하여 전이선의 복잡도 축소.
2. **직교 영역 (Orthogonal Region)** : 독립적으로 병렬 동작하는 서브 상태들을 구획하여 조합 상태를 일일이 그리지 않고 동시성을 표현. 실제 가능한 상태 조합의 수가 사라지는 것은 아님.
3. **이력 상태 (History State, $H$)** : 복합 상태에 재진입할 때 이전 활성 하위 상태를 복원하는 의사 상태. 상태 수를 줄이는 기법이라기보다 재진입 동작을 명시하는 기법.
## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 환불 처리 중인 주문의 배송 완료 불법 전이 | 상태 전이표에 허용 이벤트·가드를 정의하고 예외 경로 시험 |
| 다수의 불리언 플래그로 상태 조건 충돌 | 상태별 행위를 분리하고 전이 규칙을 한 곳에서 관리 |
| 결제 대기 주문의 예약 재고 장기 점유 | 만료 시각·타임아웃 이벤트·재고 해제 전이 명세 |
| 모델과 구현의 전이 규칙 불일치 | 상태 전이표를 구현·테스트의 공통 기준으로 관리 |

## Ⅵ. 제언

금전·재고에 영향을 주는 상태부터 허용 이벤트·가드·예외 전이를 표로 확정하고 구현·테스트에 연결.
