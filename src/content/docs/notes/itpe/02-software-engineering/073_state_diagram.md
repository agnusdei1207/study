## 연관 키워드
- UML, 상태, 전이, 이벤트, 가드 조건, entry/do/exit 활동, 상태 폭발, 하렐 상태차트, 사가 패턴, 상태 패턴

### Ⅰ. 상태 다이어그램의 개요

- 핵심 요약 : 객체의 생명주기를 이벤트에 따른 상태 전이로 모델링하는 UML 동적 행위 다이어그램.
- 개념 : 상태 다이어그램(State Diagram)은 객체가 외부 이벤트에 반응해 상태(State)가 바뀌는 규칙을 나타내는 UML(Unified Modeling Language) 동적 행위 다이어그램임.
- 배경 및 필요성 : 주문·결제처럼 생명주기가 복잡한 도메인 객체나 임베디드 기기에서 허용되지 않은 전이(Illegal Transition)가 생길 수 있어, 전이 규칙을 명시하고 상태 불변식을 검증할 필요가 생김.
- 주요 목적 : 객체가 가질 수 있는 유효 상태와 허용 전이를 명확히 정의하는 것.

### Ⅱ. 상태 다이어그램의 특징 및 장점

- 핵심 요약 : 이벤트 구동 모델링과 가드·액션 표기가 전이 규칙을 정밀하게 드러내는 특성.

1. 이벤트 구동 모델링 : 외부 이벤트가 전이를 일으키는 주체 → 이벤트 누락과 순서 오류를 설계 단계에서 점검.
2. 전이 표기법 : `이벤트 [가드 조건] / 액션` 형식으로 전이 조건과 부수 효과를 함께 명시 → 조건 없는 전이를 걸러 불법 전이 방지.
3. 내부 활동 3요소 : entry(진입 시 1회 실행), do(체류 중 지속 실행), exit(이탈 시 1회 실행) → 자원 획득과 정리 시점을 상태에 묶어 누수 방지.
4. 복합 상태 : 슈퍼상태(Superstate)와 직교 영역(Orthogonal Region)으로 계층과 병렬 상태를 표현 → 큰 상태 공간을 나누어 관리.

### Ⅲ. 상태 다이어그램의 구조 (흐름)

- 핵심 요약 : 시작 상태에서 대기와 활성 상태를 거쳐 종료 상태에 이르는 이벤트 기반 생명주기 흐름.

```text
[ 상태 다이어그램 : 회원 계정 생명주기 ]

(● 시작 상태)
   │ 회원가입 완료
   ▼
[ 대기 상태 (Pending) ]
  entry / 인증 메일 발송
  do / 인증 기한 타이머 동작
   │ 이벤트: 인증 링크 클릭
   │ 가드: 기한 이내
   │ 액션: 계정 활성화
   ▼
[ 활성 상태 (Active) ]
  복합 상태: 일반 ⇄ VIP
   │ 이벤트: 탈퇴 신청
   ▼
(◎ 최종 종료 상태)
```

```text
[ 전이 내부 처리 순서 ]

[ 이벤트 발생 ]
   ↓
[ 가드 조건 평가 ]
   ↓ 참이면
[ 액션 실행 ] → [ 다음 상태 전이 ]
   ↓ 거짓이면
[ 현재 상태 유지 ]
```

### Ⅳ. 주요 UML 행위 다이어그램과의 비교

- 핵심 요약 : 단일 객체의 상태 변화, 전체 업무 흐름, 객체 간 메시지 순서라는 서로 다른 모델링 초점.

| 비교 항목 | 상태 다이어그램 | 활동 다이어그램 | 시퀀스 다이어그램 |
|---|---|---|---|
| 모델링 초점 | 단일 객체의 생명주기와 상태 변화 | 전체 시스템의 업무 프로세스 흐름 | 여러 객체 간 시간 순서의 메시지 교환 |
| 제어 주체 | 외부에서 들어오는 이벤트 | 선행 작업 완료에 따른 내부 흐름 | 호출자와 피호출자의 호출 순서 |
| 주 활용 대상 | 주문 상태, 결제 트랜잭션, 임베디드 제어기 | 업무 절차, 알고리즘 흐름 | 서비스 간 호출 순서, 연동 흐름 |

### Ⅴ. 상태 다이어그램의 한계와 방안

- 핵심 요약 : 불법 전이 차단과 테스트 도출의 강점, 상태 폭발과 모델-코드 불일치의 한계.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
|---|---|---|---|
| 상태 폭발(State Explosion) | 변수와 동시성 요건 증가 → 상태와 전이 수 급증, 가독성 저하 | 하렐 상태차트 개념으로 슈퍼상태와 직교 영역 구조화 | 상태 수, 전이 수 |
| 분산 환경의 상태 불일치 | 네트워크 분할과 비동기 지연 → 서비스 간 전역 상태 불일치 | 사가 패턴 오케스트레이터 연계, 이벤트 소싱 기반 상태 재구성, 전이 멱등성 보장 | 보상 트랜잭션 발생률 |
| 모델과 코드의 불일치 | 설계 문서 미갱신 → 상태 다이어그램이 레거시 문서로 전락 | XState, Spring Statemachine 등 상태 머신 프레임워크로 정의 기반 코드 생성 | 모델과 코드 차이 건수 |

### Ⅵ. 상태 머신 구현과 검증에 대한 기술사적 제언

- 핵심 요약 : 상태 패턴으로 구현 구조를 세우고 전이 커버리지 테스트를 자동화해 설계와 검증을 함께 유지하는 방향.

1. 상태 패턴(State Pattern) 적용 : 클래스 안에 if-else나 switch-case로 상태를 하드코딩하면 새 상태가 추가될 때마다 기존 코드를 고쳐야 하므로, 개방-폐쇄 원칙(OCP, Open-Closed Principle)을 지키도록 상태별 행위를 독립 클래스로 캡슐화하는 것을 기본 설계로 삼음.
2. 상태 전이 테스팅(State Transition Testing) 자동화 : 상태 전이 표를 바탕으로 모든 유효 전이를 한 번씩 방문하는 0-스위치와 연속된 두 전이 쌍을 방문하는 1-스위치 커버리지를 목표로 테스트 케이스를 생성하고 자동화하면, 사람이 놓치기 쉬운 전이를 줄일 수 있음.

### Ⅶ. 결론

- 핵심 요약 : 상태 다이어그램은 이벤트 기반 객체 생명주기를 검증 가능한 기준 모델로 만드는 설계 도구.
- 시사점 : 복잡도는 계층화로 억제하고 모델과 코드의 일치는 도구로 유지할 때 상태 다이어그램이 설계와 검증의 공통 기준이 된다.
