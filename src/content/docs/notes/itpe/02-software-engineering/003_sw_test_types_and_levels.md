## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 테스트·검증 → **소프트웨어 테스트 종류·레벨**

## 30초 인출

- 본질: 소프트웨어 테스트 종류·레벨은 개발 단계별 산출물을 검증하는 레벨(단위·통합·시스템·인수)과 품질 특성별로 결함을 찾는 종류를 나눈 분류
- 메커니즘: V-모델에서 개발 단계마다 대응하는 테스트 레벨을 두고, 품질 특성(기능·성능·신뢰성·이식성 등)별 테스트 종류를 레벨에 배정
- 통찰: 레벨만 정하면 신뢰성·이식성 같은 비기능 요구가 누락되므로 요구 단계에서 품질 특성별 수용 기준을 정하고 각 기준을 검증할 테스트 레벨에 연결

<details>
<summary>핵심 용어</summary>

- **테스트 레벨(Test Level)** : 단위·통합·시스템·인수로 이어지는 개발 단계별 테스트 계층
- **테스트 종류(Test Type)** : 기능·성능·신뢰성·이식성처럼 검증하려는 품질 특성에 따른 테스트 분류
- **V-모델** : 개발 단계와 테스트 레벨을 좌우 대응시킨 검증·확인 모델
- **신뢰성 테스트(Reliability Testing)** : 정해진 조건과 기간 동안 결함 없이 동작하고 장애에서 복구되는지 검증하는 테스트
- **이식성 테스트(Portability Testing)** : 다른 운영체제·환경으로 옮기거나 설치·교체했을 때 정상 동작하는지 검증하는 테스트
- **RTM(Requirements Traceability Matrix)** : 요구사항과 테스트 케이스를 연결해 검증 누락을 추적하는 표

</details>

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 테스트 종류·레벨의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 테스트 종류·레벨** 은 개발 단계와 품질 특성에 따라 결함을 찾는 테스트를 나눈 분류 |
| 목적 | 결함의 조기 발견과 기능·비기능 요구사항 충족 확인 |

## Ⅱ. 레벨과 종류를 나누는 이유

| 특징 | 의미 |
|---|---|
| 단계별 책임 분할 | 개발 산출물마다 대응하는 테스트 레벨 배정 |
| 품질 특성별 검증 | 기능뿐 아니라 성능·신뢰성·이식성 등의 검증 |
| 조기 결함 격리 | 하위 레벨에서 결함을 잡아 상위 레벨의 수정 비용 감소 |

## Ⅲ. V-모델의 테스트 레벨 체계

### V-모델의 개발 단계와 테스트 레벨

```text
요구사항 정의 ────────────→ 인수 테스트
    │                          ↑
시스템 설계 ─────────→ 시스템 테스트
    │                     ↑
아키텍처 설계 ───→ 통합 테스트
    │                 ↑
상세 설계 ──→ 단위 테스트
    └─→ 코딩 ─┘
```

### 레벨별 검증 대상

| 레벨 | 기준 산출물 | 검증 대상 | 주 수행자 |
|---|---|---|---|
| 단위 | 상세 설계서·소스 | 모듈 내부 로직 | 개발자 |
| 통합 | 아키텍처·인터페이스 정의서 | 모듈 간 인터페이스 | 개발자·테스터 |
| 시스템 | 요구사항 명세서 | 전체 기능과 비기능 | 테스터 |
| 인수 | 요구사항·계약서 | 사용자 업무 충족 | 사용자·발주자 |

## Ⅳ. 테스트 종류와 신뢰성·이식성 테스트의 세부 활동

### 품질 특성별 테스트 종류

| 품질 특성 | 테스트 종류 |
|---|---|
| 기능 적합성 | 기능 테스트(블랙박스·화이트박스) |
| 성능 효율성 | 부하·스트레스 테스트 |
| 신뢰성 | 신뢰성 테스트 |
| 보안성 | 취약점·침투 테스트 |
| 사용성 | 사용성 테스트 |
| 이식성 | 이식성 테스트 |

### 신뢰성·이식성 테스트의 세부 활동

| 구분 | 부특성 | 세부 활동 |
|---|---|---|
| 신뢰성 | 성숙성 | 결함 밀도·평균 무고장 시간(MTBF) 측정 |
| 신뢰성 | 가용성 | 장시간 운영·부하 상태에서 서비스 지속 시험 |
| 신뢰성 | 장애 허용성 | 장애 주입 후 절체(Failover) 동작 시험 |
| 신뢰성 | 복구성 | 백업 복원·재해복구 시험(RTO·RPO 확인) |
| 이식성 | 적응성 | 다른 OS·브라우저·클라우드 환경의 동작 시험 |
| 이식성 | 설치성 | 설치·제거·업그레이드 절차 시험 |
| 이식성 | 대체성 | 기존 제품을 교체할 때 데이터 이관·호환 시험 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 비기능 요구가 수용 기준 없이 정의되어 테스트에서 누락 | 요구 단계에서 품질 특성별 수용 기준 정의 |
| 시스템·인수 단계에서야 결함이 발견되어 수정 비용 증가 | 요구·설계 단계에서 테스트 케이스를 함께 작성 |
| 운영 환경 조합 증가로 이식성 테스트 범위 확대 | 환경 조합의 우선순위 선정과 컨테이너 기반 환경 재현 |

## Ⅵ. 제언

요구 단계에서 신뢰성·이식성을 포함한 품질 특성별 수용 기준을 정하고, 각 기준을 검증할 테스트 레벨과 케이스를 RTM으로 연결

### 수용 기준 기반 테스트 배정

```text
요구사항
    ↓
품질 특성별 수용 기준 (예: 복구 목표 시간, 지원 환경)
    ↓
검증 테스트 레벨·종류 배정
    ↓
테스트 케이스와 RTM 연결
```

### 선택 근거: 레벨 중심 계획과의 비교

| 구분 | 레벨 중심 계획 | 제언: 수용 기준 기반 배정 |
|---|---|---|
| 계획 기준 | 개발 단계 | 품질 특성별 수용 기준 |
| 비기능 요구 | 누락 가능 | 기준별 테스트 배정 |
| 완료 판단 | 레벨별 실행 여부 | 요구사항별 검증 결과 |
