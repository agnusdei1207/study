## 지식 로드맵 내 현재 위치

소프트웨어 공학 → 테스트·검증 → **소프트웨어 테스트 종류·레벨**

## 30초 인출

- 본질: 소프트웨어 테스트 종류·레벨은 개발 단계 산출물과 품질 특성 요구에 맞추어 결함을 체계적으로 식별하는 검증 활동
- 메커니즘: V-모델 기반 계층적 검증(단위→통합→시스템→인수)과 ISO/IEC 25010 품질속성별(기능·신뢰성·이식성 등) 다각적 시험 결합
- 통찰: 테스트 레벨만 정하면 비기능 품질 요구의 누락이 발생하므로 요구사항 단계에서 품질 속성별 수용 기준을 정의하고 조기 검증을 수행하는 Shift-Left 전략 적용

<details>
<summary>핵심 용어</summary>

- **소프트웨어 테스트 종류·레벨** : 개발 생명주기 단계에 대응하는 계층 구조(레벨)와 검증하려는 품질 특성(종류)을 체계화한 테스트 분류 체계
- **V&V(Verification & Validation)** : 개발 규격 일치성을 확인하는 검증(Verification)과 사용자 요구 만족성을 입증하는 확인(Validation)
- **Test Level(테스트 레벨)** : 단위, 통합, 시스템, 인수로 이어지는 생명주기 단계별 테스트 실행 계층
- **신뢰성 테스트(Reliability Testing)** : 명시된 조건과 기간 동안 시스템이 결함 없이 서비스를 지속하는지 검증하는 비기능 테스트
- **이식성 테스트(Portability Testing)** : 이종 OS, 브라우저, 하드웨어 환경으로의 이전 및 호환 동작 여부를 검증하는 테스트
- **ISO/IEC 25010:2023** : 소프트웨어 제품 품질을 9대 특성으로 정의한 국제 표준
- **Shift-Left** : 테스트 계획 및 검증 활동을 코딩 완료 이후가 아닌 요구사항 분석 및 아키텍처 설계 단계로 전진 배치하는 전략
- **RTM(Requirements Traceability Matrix)** : 요구사항과 테스트 케이스를 양방향으로 연결해 검증 누락을 추적하는 매트릭스

## 2~4교시 25점 답안

## Ⅰ. 소프트웨어 테스트 종류·레벨의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | **소프트웨어 테스트 종류·레벨** 은 개발 생명주기 단계와 제품 품질 요구에 맞추어 결함을 식별하고 품질을 보증하는 검증 활동 |
| 목적 | 결함 조기 발견을 통한 수정 비용 절감, 기능 및 비기능(신뢰성·이식성) 요구사항 충족 입증 |

## Ⅱ. 테스트 레벨과 종류의 핵심 특징

| 특징 | 의미 |
|---|---|
| 생명주기 대응성 | 개발 단계별 산출물(명세, 설계, 코드)과 1:1로 대응하여 검증 책임 분할 |
| 품질속성 다각화 | 기능 검증에 국한되지 않고 신뢰성, 성능, 보안, 이식성 등 전 품질 영역 검증 |
| 조기 결함 격리 | 하위 레벨(단위·통합)의 결함을 조기 차단하여 상위 레벨(시스템·인수) 비용 절감 |

## Ⅲ. V-모델 기반 4단계 테스트 레벨 체계

### V-모델 기반 개발 단계와 테스트 레벨 대응 구조

```text
[요구사항 정의] ───────────────────────→ [인수 테스트]
      │                                       ▲
      ▼                                       │
[시스템 설계] ─────────────────→ [시스템 테스트]
      │                               ▲
      ▼                               │
[아키텍처 설계] ─────────→ [통합 테스트]
      │                         ▲
      ▼                         │
[모듈 상세설계] ───→ [단위 테스트]
      │                   ▲
      └─────→ [코딩] ─────┘
```

### 테스트 레벨별 실행 순서 및 Shift-Left 검증 메커니즘

```text
요구사항 수립 시점
    ↓
테스트 계획 수립(Shift-Left)
    ├─ 요구사항 → 인수/시스템 테스트 케이스 동시 작성
    ├─ 기본설계 → 통합 테스트 케이스 동시 작성
    └─ 상세설계 → 단위 테스트 케이스 동시 작성
    ↓
코드 구현 완료
    ↓
시험 실행: 단위 테스트 → 통합 테스트 → 시스템 테스트 → 인수 테스트
```

| 테스트 레벨 | 기준 산출물 | 주요 검증 통제점 | 주 담당자 |
|---|---|---|---|
| 단위 테스트 | 모듈 상세설계서, 소스코드 | 내부 로직 오류 격리, 경계값 검증, 코드 커버리지 | 개발자 |
| 통합 테스트 | 소프트웨어 아키텍처, 인터페이스 정의서 | 인터페이스 결함 식별, 데이터 전달 무결성, 통신 규약 준수 | 개발자·테스터 |
| 시스템 테스트 | 요구사항 명세서(SRS), 인프라 아키텍처 | 비기능 요구(성능·보안·신뢰성) 검증, 전체 비즈니스 흐름 | 전담 테스터 |
| 인수 테스트 | 제안요청서(RFP), 계약서, 사용자 요구사항 | 사용자 관점의 업무 요구 충족 확인, 운영 적합성 | 발주자·사용자 |

## Ⅳ. 비기능 품질 특성 시험: 신뢰성과 이식성

| 품질 속성 | 핵심 검증 대상 | 주요 시험 기법 및 지표 |
|---|---|---|
| 신뢰성·가용성 | 장시간 운영 시 메모리 누수 및 서비스 무중단 지속성 | 내구성 시험(Soak Test), 평균 무고장 시간(MTBF), 결함 밀도 |
| 신뢰성·장애허용성 | 하드웨어·네트워크 장애 발생 시 서비스 유지 및 절체 | 카오스 엔지니어링(Chaos Engineering), 페일오버(Failover) 시험 |
| 신뢰성·회복성 | 장애 발생 후 정상 상태로 복구되는 시간 및 데이터 손실 | 재해복구 시험, 복구 목표 시간(RTO), 복구 목표 시점(RPO) |
| 이식성·적응성 | 이종 OS, 클라우드 플랫폼, 하드웨어 아키텍처 호환성 | 멀티 플랫폼 호환성 시험, 가상화 환경 매트릭스 검증 |
| 이식성·설치성 | 대상 환경에서의 설치, 패치, 롤백 정상 수행 여부 | 자동화 설치 스크립트 검증, 언인스톨 무결성 확인 |

## Ⅴ. 한계와 방안

| 한계 | 방안 |
|---|---|
| 상위 시스템 및 인수 테스트에 의존하는 결함 발견으로 인한 수정 비용 급증 | 요구사항 및 설계 단계부터 테스트 케이스를 동시 정의하는 **Shift-Left** 전략 적용 |
| 수작업 E2E 테스트 중심 진행으로 인한 회귀 테스트 병목 및 배포 지연 | 피라미드 모델 기반 단위·통합 테스트 자동화 비중 확대 및 CI 연계 |
| 이종 운영 환경(클라우드·OS·브라우저) 증가로 인한 이식성 테스트 매트릭스 폭증 | 컨테이너 가상화 환경 구축 및 디바이스 팜(Device Farm) 기반 자동화 테스트 수행 |

## Ⅵ. 제언

테스트 피라미드 기반의 계층별 자동화 배분과 RTM 연계를 통한 전 생명주기 추적성 확보

### 테스트 피라미드 기반 자동화 포트폴리오

```text
       / \
      / E2E \       ← 10% (UI·사용자 시나리오 인수 검증)
     /───────\
    /  통합   \     ← 20% (서비스·API·DB 연계 검증)
   /───────────\
  /    단위     \   ← 70% (비즈니스 로직·함수 단위 고속 검증)
 /───────────────\
```

### RTM 기반 요구사항-테스트 케이스 추적 절차

```text
요구사항 ID 부여
    ↓
테스트 케이스(TC) ID 1:1 매핑 및 RTM 작성
    ↓
테스트 레벨별 실행 및 결과 기록
    ↓
RTM 추적성 분석
    ├─ 미검증 요구사항 존재 → 누락 테스트 케이스 즉시 보강
    └─ 모든 요구사항 검증 완료 → 품질 기준 충족 판정 후 릴리스
```

### 선택 근거: 역피라미드와 테스트 피라미드 비교

| 구분 | 역피라미드 (아이스크림 콘 안티패턴) | 제언: 테스트 피라미드 |
|---|---|---|
| 테스트 중심 | 수작업 E2E 및 UI 테스트 치중 | 자동화된 단위 및 통합 테스트 중심 |
| 결함 발견 시점 | 릴리스 직전 시스템 및 인수 단계 | 빌드 및 코드 커밋 직후 단위 단계 |
| 유지보수 비용 | 깨지기 쉬운 UI 테스트로 유지비용 급증 | 빠르고 견고한 단위 테스트로 비용 최소화 |
