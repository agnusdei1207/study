## 연관 키워드

- 테스트 레벨, 단위 테스트, 통합 테스트, 시스템 테스트, 인수 테스트, V-모델
- 테스트 피라미드, 신뢰성 테스트, 이식성 테스트, 성능 테스트, 보안성 테스트, ISO/IEC 25010

## Ⅰ. 소프트웨어 테스트 종류 및 레벨의 개요

- 핵심 요약 : 개발 단계마다 레벨을 나눠 기능과 비기능 품질을 검증하는 계층형 테스트 체계.
- 개념 : 결함을 조기에 찾고 요구사항 충족과 품질 속성을 검증하기 위해, 개발 단계에 대응시켜 계층화한 **테스트 레벨** (Test Level)과 그 안의 테스트 종류 체계.
- 배경 및 필요성 : 개발 후반에 발견된 결함일수록 수정 비용이 커진다는 Boehm의 법칙을 근거로, 기능 정확성과 신뢰성·이식성 같은 비기능 품질을 초기부터 나눠 검증할 필요가 있음.
- 표준 근거 : ISO(International Organization for Standardization), IEC(International Electrotechnical Commission), IEEE(Institute of Electrical and Electronics Engineers)가 정한 **ISO/IEC/IEEE 29119** (소프트웨어 테스트 국제 표준)와 **ISO/IEC 25010** (시스템 및 소프트웨어 품질 모델)을 용어 기준으로 삼음.

## Ⅱ. 소프트웨어 테스트 종류 및 레벨의 특징 및 장점

- 핵심 요약 : 개발 모델과 대응한 단계별 검증, 기능과 비기능의 병행 점검이 결함을 일찍 찾고 품질 누락을 줄이는 방식.

1. **V-모델** (V-Model, 개발 단계와 테스트 레벨을 좌우로 대응시키는 개발 모델) : 산출물마다 검증 레벨을 연결 → 누락된 요구사항과 인터페이스 결함을 추적.
2. 조기 검증 : 모듈 수준의 시험부터 빠르게 피드백 → 후반 수정 범위와 비용 완화.
3. 기능·비기능 병행 : 정확성과 함께 **신뢰성 테스트** (장시간 구동 시 장애와 복구 능력 검증), **이식성 테스트** (환경 간 적응력 검증)를 수행 → 사용 환경의 품질 위험 파악.
4. 표준 기반 분류 : 표준 용어를 공유해 팀 간 시험 범위와 판정 기준을 맞춤 → 협업 시 해석 차이 감소.
5. **테스트 피라미드** (Test Pyramid, 단위 시험을 넓게 두고 종단간(E2E, End-to-End) 시험을 좁게 두는 비중 원칙) : 빠른 단위 시험을 자동화 → 피드백 주기 단축과 유지보수 비용 절감.

## Ⅲ. 소프트웨어 테스트 종류 및 레벨의 구조 (흐름)

- 핵심 요약 : 요구사항 정의부터 모듈 코딩까지의 개발 단계와, 인수 테스트부터 단위 테스트까지의 레벨이 짝을 이루는 V-모델 구조.

```text
[ V-모델 구조 ]

[ 요구사항 정의 ]  ─  검증  ─  [ 인수 테스트 ]
        ↓                           ↑
[ 시스템 설계 ]    ─  검증  ─  [ 시스템 테스트 ]
        ↓                           ↑
[ 상세 설계 ]      ─  검증  ─  [ 통합 테스트 ]
        ↓                           ↑
[ 모듈 코딩 ]      ─  검증  ─  [ 단위 테스트 ]
```

```text
[ 테스트 피라미드 ]

        ▲
       ▲▲▲      E2E/UI 테스트 (소수·느림)
      ▲▲▲▲▲     통합·API 테스트
     ▲▲▲▲▲▲▲    단위 테스트 (다수·빠름)
```

- **단위 테스트** (Unit Test) : 개별 모듈·함수 수준의 기능 정확성 검증. 화이트박스·블랙박스 기법과 JUnit 같은 도구, Mock 객체를 활용.
- **통합 테스트** (Integration Test) : 모듈 간 인터페이스와 데이터 교환, API(Application Programming Interface) 연동 검증. 빅뱅 통합과 점진적 통합 방식을 쓰며, 상향식은 드라이버, 하향식은 스텁을 사용.
- **시스템 테스트** (System Test) : 통합이 끝난 전체 시스템 환경에서 요구사항 충족 여부 검증. 기능 테스트와 성능·보안성 점검을 포함.
- **인수 테스트** (Acceptance Test) : 발주자와 최종 사용자가 비즈니스 요구와 일치하는지 판단. 알파 테스트와 베타 테스트로 나뉨.

## Ⅳ. 테스트 종류별 비교

- 핵심 요약 : 검증 대상과 기법이 다른 기능·신뢰성·이식성·성능·보안성 테스트의 관점을 구분해 시험 범위를 정하는 체계.

| 테스트 종류 | 핵심 검증 대상 | 주요 기법 및 도구 |
| --- | --- | --- |
| 기능 테스트 | 명세된 업무 기능과 비즈니스 로직 충족 여부 | 동등 분할, 경계값 분석, 유스케이스 기반 테스트 |
| 신뢰성 테스트 | 장시간 구동 시 장애 빈도, 고장 간격, 복구 능력 | 결함 주입, 장시간 연속(Soak) 테스트, 평균 고장 간격(MTBF, Mean Time Between Failures)과 평균 수리 시간(MTTR, Mean Time To Repair) 측정 |
| 이식성 테스트 | 이기종 OS(Operating System), 브라우저, DB(Database), 클라우드 환경 적응력 | 다중 플랫폼 매트릭스 테스트, 컨테이너 환경 호환성 검증 |
| 성능 테스트 | 임계 부하에서의 처리량, 응답 시간, 자원 소진율 | 부하, 스트레스, 스파이크 테스트 (JMeter, nGrinder) |
| 보안성 테스트 | 취약점 존재 여부와 비인가 접근 차단 여부 | 모의해킹(Pen-Testing), 소스코드 보안약점 진단, DAST(Dynamic Application Security Testing) |

## Ⅴ. 소프트웨어 테스트 종류 및 레벨의 한계와 방안

- 핵심 요약 : UI 시험 편중, 외부 의존성, 비기능 시험의 뒤늦은 실행이 주요 한계이며, 피라미드 설계와 환경 격리, 품질 속성의 조기 검증으로 완화.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| UI·E2E 시험 편중 | 느리고 깨지기 쉬운 시험이 많아 피드백과 유지보수가 지연 | 테스트 피라미드에 따라 단위·API 시험을 늘리고, 핵심 사용자 경로만 E2E 시험으로 검증 | 시험 소요 시간, 불안정 시험 비율 |
| 외부 시스템 종속 | 외부 서비스와 시험 데이터 상태가 달라 재현과 격리가 어려움 | 격리된 컨테이너, 서비스 가상화, 소비자 주도 계약 테스트 | 환경 기인 실패율, 재현율 |
| 비기능 시험 지연 | 기능 검증에 치우쳐 성능·신뢰성·이식성 위험을 뒤늦게 발견 | 설계 단계에서 품질 속성 시나리오 정의, 지속적 통합(Continuous Integration) 파이프라인에 부하·복구·호환성 시험 연계 | 응답 시간, 복구 시간, 플랫폼별 통과율 |

## Ⅵ. 고품질 테스트 환경 구축을 위한 기술사적 제언

- 핵심 요약 : 테스트 자동화 피라미드를 지키고, 개발·테스트·운영 환경의 일치성을 확보하는 것이 고품질 테스트 환경의 출발점.
- 테스트 피라미드 준수 : UI 중심의 E2E 시험에 의존하면 피드백이 늦고 취약해지므로, 단위 시험과 API 통합 시험 계층을 두껍게 구성해 피드백 주기를 줄이는 자동화 전략이 필요함.
- 환경 일치성 확보 : 개발·테스트·운영 환경의 차이로 생기는 오작동을 막기 위해 컨테이너 기반으로 운영 환경과 같은 형태의 테스트 환경을 구축하고, 외부 의존성은 서비스 가상화(Service Virtualization)로 대체하는 방식이 필요함.
- 품질 속성의 조기 검증 : 신뢰성·이식성·성능·보안성 같은 비기능 품질은 설계 단계의 ATAM(Architecture Tradeoff Analysis Method) 워크숍에서 시나리오로 정하고, CI 파이프라인에 자동화 시험으로 연계해 누락을 방지해야 함.

## Ⅶ. 결론

- 핵심 요약 : 테스트 레벨과 종류 체계는 결함을 조기에 찾고 기능·비기능 품질의 균형을 맞추는 공학적 기반.
- 비기능 검증을 앞당기고 환경 일치성을 높이는 것이 결함 수정 비용을 누르는 핵심 관리 포인트임.
