## 답안 골격
```text
[SW 테스트 종류·레벨] ◀━━ 머리: Ⅶ 내 의견 (피라미드 비율 준수 및 결함 발견 단계 조기화)
 ┃
 ┣━ Ⅰ 개요 ───── 하위 결함의 상위 전파로 수정 비용 기하급수 증가 → 단계별 V-모델 대응
 ┣━ Ⅱ 특징 ───── 개발 산출물과 1:1 매핑 검증 · 기능 및 비기능(신뢰성, 이식성 등) 분리
 ┣━ Ⅲ 구조 ───── 단위(Unit) → 통합(Integration) → 시스템(System) → 인수(Acceptance)
 ┣━ Ⅳ 흐름 ───── ① 단위 모듈 격리 검증 → ② 인터페이스 연계 검증 → ③ 전체 요구사항 검증 → ④ 사용자 계약 검증
 ┣━ Ⅴ 비교 ───── 정적 테스트(리뷰, 인스펙션) vs 동적 테스트(블랙박스, 화이트박스)
 ┗━ Ⅵ 실무 ───── 상위 레벨(UI/E2E) 과몰입으로 인한 테스트 비용 폭증 / 테스트 피라미드 재편
```
- 필수 키워드: V-모델 · 단위 테스트 · 통합 테스트 · 시스템 테스트 · 인수 테스트 · 비기능 테스트
- 배점 전략: 10점 = Ⅲ 4단계 레벨 매핑 도식 → Ⅴ 정적/동적 비교 / 25점 = Ⅰ~Ⅶ 전개, 각 레벨별 기법 및 신뢰성·이식성 세부 활동 전개
- 기출: 133회 4교시 `테스트 종류 및 신뢰성·이식성 세부활동` → Ⅲ·Ⅵ / 134회 3교시 `소프트웨어 테스트` → Ⅱ·Ⅲ·Ⅳ

## 한 줄 본질
- 배포 직전 결함 발견 시 설계 수정과 재작업 비용이 수십 배 폭증하는 병목 → 개발 단계별 산출물과 1:1로 대응하는 4단계 레벨(단위·통합·시스템·인수)을 정의해 결함을 생성 단계에서 즉시 격리·제거 → 소프트웨어 신뢰성 보장 / 테스트 설계·환경 구성 공수 증가

## 핵심 그림
```text
[ 요구사항 분석 ] <=============================> [ 인수 테스트 ] (사용자)
      \                                                 /
    [ 시스템 설계 ] <=======================> [ 시스템 테스트 ] (기능/비기능)
          \                                         /
        [ 상세 설계 ] <===============> [ 통합 테스트 ] (인터페이스/DB)
              \                             /
            [ 모듈 구현 ] ======> [ 단위 테스트 ] (함수/로직/코드)
```

## 핵심 용어
- V-모델: 개발 생명주기의 각 분석·설계 단계와 이에 상응하는 테스트 레벨을 양 축으로 매핑한 품질 보증 모델
- 비기능 테스트: 기능의 정상 동작 여부가 아닌 처리량, 응답시간, 장애 복구성, 이식성, 보안성 등의 품질 속성을 검증하는 활동

## 핵심 통찰
- 단위 테스트에서 발견하지 못한 결함이 통합·시스템 테스트로 넘어가면 결함 원인 추적 범위가 시스템 전체로 넓어져 디버깅 시간이 10배 이상 증가함
- 아이스크림 콘 안티패턴(UI/E2E 테스트만 비대하고 단위 테스트가 부실한 구조)은 빌드 파이프라인 지연과 깨지기 쉬운(Flaky) 테스트의 주원인임
- 신뢰성 테스트(내결함성, 복구성)와 이식성 테스트(다양한 OS, 브라우저 호환)는 개발 후반부가 아닌 아키텍처 수립 시점에 테스트 베드를 구축해야 함

## 이웃 토픽과 구분
- 테스트 레벨 vs 테스트 유형: 레벨 = 무엇을 검증하는가(단위/통합/시스템/인수) / 유형 = 어떻게 검증하는가(기능/성능/보안/신뢰성)

## 문제·원인·대책
- 사례: 공공 대규모 차세대 시스템 오픈 직후 인터페이스 장애 및 성능 지연 사태
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 시스템 통합 후 기관 간 연계 인터페이스 대량 실패 | 각 단위 모듈만 개별 검증하고 스텁/드라이버 기반 통합 테스트 생략 | 빅뱅 통합 지양, 상향식/하향식 통합 및 계약 기반 API 테스트(Pact) 도입 | 인터페이스 규격 불일치 사전 차단 |
| 운영 전환 후 특정 환경에서 호환성 오류 발생 | 개발 표준 환경에서만 기능 테스트 수행, 이식성 테스트 누락 | 다중 OS·브라우저 컨테이너화 가상 테스트 매트릭스 자동화 | 환경 종속적 런타임 오류 조기 제거 |

## 이렇게 출제된다
- 제133회 4교시 2번: "정보시스템 개발과 운영 단계에서 수행되는 소프트웨어 테스트의 종류를 쓰고, 이 중 신뢰성 테스트와 이식성 테스트의 세부 활동에 대하여 각각 설명하시오." → 요구 포인트: Ⅲ 4단계 레벨 + Ⅵ 신뢰성(MTBF, 복구) 및 이식성(설치, 적응) 활동
- 제134회 3교시 2번: "소프트웨어 테스트에 대하여 설명하시오." → 요구 포인트: Ⅰ 7대 원리 + Ⅲ 레벨 및 기법 + Ⅵ 테스트 자동화 전략

## 내 의견
- [E2E 자동화에 집착해 단위 테스트를 경시하는 풍조] 화면 기반 자동화 스크립트만 수백 개 작성했다가 UI 변경 시마다 테스트가 전면 깨져 유지보수를 포기하는 사례 빈발 → 나라면: 마틴 파울러의 테스트 피라미드(단위 70%, 통합 20%, E2E 10%)를 팀 표준으로 강제하고, 단위 테스트 커버리지 80% 미달 시 CI 파이프라인에서 자동 빌드 실패 처리
