## 지식 로드맵 내 현재 위치

<div class="itpe-topic-path" aria-label="소프트웨어 품질에서 테스트 종류와 레벨까지의 지식 경로"><span>SW 공학</span><span>SW 테스트</span><strong>테스트 종류·레벨</strong></div>

## 큰 그림과 30초 인출

```text
개발 산출물                    테스트 레벨
요구사항  ─────────────────── 인수 테스트
시스템 설계 ───────────────── 시스템 테스트
아키텍처·상세설계 ─────────── 통합 테스트
모듈 구현 ─────────────────── 단위 테스트

레벨 = 어디서 검증 / 유형 = 무엇을 검증 / 기법 = 어떻게 검증
```

## 예상문제

> 소프트웨어 테스트의 레벨과 유형·기법을 구분하고 V-모델로 설명한 후, 신뢰성·이식성 테스트와 테스트 자동화 전략을 제시하시오. (25점)

## 답안 골격
```text
[SW 테스트 종류·레벨] ◀━━ 머리: Ⅶ 내 의견 (피라미드 비율 준수 및 결함 발견 단계 조기화)
 ┃
 ┣━ Ⅰ 개요 ───── 하위 결함의 상위 전파로 수정 비용 기하급수 증가 → 단계별 V-모델 대응
 ┣━ Ⅱ 특징 ───── 개발 산출물과 1:1 매핑 검증 · 기능 및 비기능(신뢰성, 이식성 등) 분리
 ┣━ Ⅲ 구조 ───── 단위(Unit) → 통합(Integration) → 시스템(System) → 인수(Acceptance)
 ┣━ Ⅳ 흐름 ───── ① 단위 모듈 격리 검증 → ② 인터페이스 연계 검증 → ③ 전체 요구사항 검증 → ④ 사용자 계약 검증
 ┣━ Ⅴ 비교 ───── 정적 테스트(리뷰, 인스펙션) vs 동적 테스트(블랙박스, 화이트박스)
 ┗━ Ⅵ 실무 ───── 상위 레벨(UI/E2E) 과몰입으로 인한 테스트 비용 폭증 / 테스트 피라미드 재편
```
- 필수 키워드: V-모델 · 단위 테스트 · 통합 테스트 · 시스템 테스트 · 인수 테스트 · 비기능 테스트
- 기출: 133회 4교시 `테스트 종류 및 신뢰성·이식성 세부활동` → Ⅲ·Ⅵ / 134회 3교시 `소프트웨어 테스트` → Ⅱ·Ⅲ·Ⅳ

## 한 줄 본질
- 배포 직전 결함 발견 시 설계 수정과 재작업 비용이 수십 배 폭증하는 병목 → 개발 단계별 산출물과 1:1로 대응하는 4단계 레벨(단위·통합·시스템·인수)을 정의해 결함을 생성 단계에서 즉시 격리·제거 → 소프트웨어 신뢰성 보장 / 테스트 설계·환경 구성 공수 증가

## 핵심 그림
```text
[ 요구사항 분석 ] <=============================> [ 인수 테스트 ] (사용자)
      \                                                 /
    [ 시스템 설계 ] <=======================> [ 시스템 테스트 ] (기능/비기능)
          \                                         /
        [ 상세 설계 ] <===============> [ 통합 테스트 ] (인터페이스/DB)
              \                             /
            [ 모듈 구현 ] ======> [ 단위 테스트 ] (함수/로직/코드)
```

## 핵심 용어
- V-모델: 개발 생명주기의 각 분석·설계 단계와 이에 상응하는 테스트 레벨을 양 축으로 매핑한 품질 보증 모델
- 비기능 테스트: 기능의 정상 동작 여부가 아닌 처리량, 응답시간, 장애 복구성, 이식성, 보안성 등의 품질 속성을 검증하는 활동

## 핵심 통찰
- 단위 테스트에서 발견하지 못한 결함이 통합·시스템 테스트로 넘어가면 결함 원인 추적 범위와 재작업 영향이 확대됨
- 아이스크림 콘 안티패턴(UI/E2E 테스트만 비대하고 단위 테스트가 부실한 구조)은 빌드 파이프라인 지연과 깨지기 쉬운(Flaky) 테스트의 주원인임
- 신뢰성 테스트(내결함성, 복구성)와 이식성 테스트(다양한 OS, 브라우저 호환)는 개발 후반부가 아닌 아키텍처 수립 시점에 테스트 베드를 구축해야 함

## 딸려 나오는 하위 토픽

| 하위 토픽 | 상위 구조 속 위치 | 한 줄 (정의 → 메커니즘 → 구분축) |
|---|---|---|
| 소프트웨어 테스트(Software Testing) | Ⅰ 개요 / 품질 보증 전주기 | 요구사항 일치 여부를 확인하고 숨은 결함을 조기 발견하여 품질 신뢰도를 확보하는 결함 식별·검증 활동 (결함 예방 및 식별 중심 품질 통제) |
| 신뢰성 테스트 | Ⅲ 비기능 테스트 / 품질 속성 | 시스템이 규정된 조건에서 장애 없이 의도한 기능을 지속 수행할 수 있는지 내결함성·성숙도·회복성을 검증하는 비기능 테스트 (기능 적합성 vs 지속 안정성 신뢰성) |
| 이식성 테스트 | Ⅲ 비기능 테스트 / 환경 적응 | 다양한 하드웨어, 운영체제, 브라우저 환경 간에 소프트웨어가 정상 설치·구동·치환될 수 있는지를 검증하는 비기능 테스트 (단일 환경 구동 vs 이기종 플랫폼 간 이식성) |

## 이웃 토픽과 구분
- 테스트 레벨 vs 테스트 유형: 레벨 = 무엇을 검증하는가(단위/통합/시스템/인수) / 유형 = 어떻게 검증하는가(기능/성능/보안/신뢰성)

## 문제·원인·대책
- 사례: 공공 대규모 차세대 시스템 오픈 직후 인터페이스 장애 및 성능 지연 사태
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 시스템 통합 후 기관 간 연계 인터페이스 대량 실패 | 각 단위 모듈만 개별 검증하고 스텁/드라이버 기반 통합 테스트 생략 | 빅뱅 통합 지양, 상향식/하향식 통합 및 계약 기반 API 테스트(Pact) 도입 | 인터페이스 규격 불일치 사전 차단 |
| 운영 전환 후 특정 환경에서 호환성 오류 발생 | 개발 표준 환경에서만 기능 테스트 수행, 이식성 테스트 누락 | 다중 OS·브라우저 컨테이너화 가상 테스트 매트릭스 자동화 | 환경 종속적 런타임 오류 조기 제거 |

## 이렇게 출제된다
- 제133회 4교시 2번: "정보시스템 개발과 운영 단계에서 수행되는 소프트웨어 테스트의 종류를 쓰고, 이 중 신뢰성 테스트와 이식성 테스트의 세부 활동에 대하여 각각 설명하시오." → 요구 포인트: Ⅲ 4단계 레벨 + Ⅵ 신뢰성(MTBF, 복구) 및 이식성(설치, 적응) 활동
- 제134회 3교시 2번: "소프트웨어 테스트에 대하여 설명하시오." → 요구 포인트: Ⅰ 7대 원리 + Ⅲ 레벨 및 기법 + Ⅵ 테스트 자동화 전략

## 내 의견
- [E2E 자동화에 집착해 단위 테스트를 경시하는 풍조] 화면 기반 자동화에 편중되면 UI 변경 때 유지보수 비용과 비결정적 실패가 커짐 → 나라면: 빠르고 격리된 하위 레벨 테스트를 넓게 두고 핵심 사용자 여정만 E2E로 검증하며, 위험 기반 커버리지와 결함 유출률을 품질게이트로 운영

## Ⅰ. 결함을 단계별로 격리·검증하는 소프트웨어 테스트 개요

- 정의: **소프트웨어 테스트**는 정적·동적 기법으로 작업산출물과 실행 결과를 평가하여 결함을 발견하고, 명시·묵시 요구와 사용 목적 충족 여부를 검증하는 활동
- 목적: 결함을 가능한 생성 단계 가까이에서 발견하고, 기능·품질속성·사용자 수용성에 대한 근거 제공
- 구분: 테스트 레벨은 검증 범위, 테스트 유형은 품질 관점, 테스트 기법은 케이스 도출 방법

## Ⅱ. 독립성·추적성·위험 기반의 특징

| 특징 | 메커니즘 | 효과 |
|---|---|---|
| **V&V** | 산출물 적합성과 사용자 요구 충족을 함께 확인 | 올바른 제품을 올바르게 구축 |
| **추적성** | 요구-설계-코드-테스트-결함 연결 | 누락·변경 영향 분석 |
| **위험 기반** | 영향·발생가능성에 따라 깊이·우선순위 조절 | 한정 자원의 집중 |
| **다층 검증** | 정적 테스트와 4개 동적 레벨 결합 | 조기 예방과 실행 결함 탐지 |

## Ⅲ. V-모델과 4개 테스트 레벨

```text
요구사항 분석  <────────────────────> 인수 테스트
   시스템 설계 <──────────────────> 시스템 테스트
      아키텍처·상세설계 <────────> 통합 테스트
               모듈 구현 <──────> 단위 테스트
```

| 레벨 | 대상·목적 | 대표 관점 |
|---|---|---|
| **단위** | 함수·클래스·모듈의 로직 격리 검증 | 경계·분기·예외·상태 |
| **통합** | 컴포넌트·API·DB·외부시스템 상호작용 | 인터페이스·계약·데이터 흐름 |
| **시스템** | 완성 시스템의 전체 요구·품질속성 | 기능·성능·보안·신뢰성·이식성 |
| **인수** | 사용자·업무·계약 기준의 수용 여부 | 운영 시나리오·UAT·알파/베타 |

## Ⅳ. 계획에서 종료까지의 테스트 절차

```text
① 테스트 근거·범위·위험 분석
 → ② 전략·환경·데이터·종료기준 계획
 → ③ 조건·케이스·절차·자동화 설계
 → ④ 환경 구성·실행·증적 수집
 → ⑤ 실제-기대 비교·결함 등록·재시험
 → ⑥ 회귀 테스트·커버리지·잔여위험 평가
 → ⑦ 종료보고와 교훈·테스트 자산 환류
```

## Ⅴ. 레벨·유형·기법의 구분

| 구분 | 질문 | 예시 |
|---|---|---|
| **레벨** | 어느 범위에서 검증하는가 | 단위·통합·시스템·인수 |
| **유형** | 어떤 품질을 검증하는가 | 기능·성능·보안·신뢰성·이식성 |
| **정적 기법** | 실행 없이 무엇을 검토하는가 | 리뷰·인스펙션·정적분석 |
| **동적 기법** | 실행 입력을 어떻게 도출하는가 | 명세·구조·경험 기반 테스트 |

## Ⅵ. 신뢰성·이식성과 자동화 전략

| 영역 | 주요 검증 | 자동화·운영 포인트 |
|---|---|---|
| **신뢰성** | 성숙성·가용성·결함허용성·복구성 | 장애주입, 장시간·복구 테스트, 실패·복구 지표 |
| **이식성** | 적응성·설치성·대체성 | OS·브라우저·런타임 매트릭스, 반복 설치·롤백 |
| **회귀** | 변경으로 인한 기존 기능 영향 | 영향 기반 선택과 안정 테스트 집합 |
| **E2E** | 핵심 사용자 여정과 시스템 연결 | 소수 핵심 흐름, 데이터·환경 격리, Flaky 관리 |

- 테스트 피라미드는 고정 비율이 아니라 빠르고 격리된 하위 테스트를 넓게, 느리고 취약한 E2E를 핵심 흐름에 제한하는 설계 원칙
- 코드 커버리지 단일 임계값보다 요구·위험 커버리지, 결함 유출률, Flaky 비율, 실행시간을 함께 품질게이트로 사용

## Ⅶ. 테스트 수보다 위험과 추적성을 검증하는 결론

- 테스트 완성도는 케이스 개수가 아니라 **요구·위험-테스트-결함-수정의 추적성**과 운영환경을 대표하는 검증 근거로 판단
- 각 레벨의 책임을 분리하고 정적 검토·자동화·신뢰성·이식성 검증을 조기에 설계하여 상위 단계의 결함 유출과 재작업을 줄여야 함

## 1교시 10점 답안 발췌

```text
V-Model: 요구↔인수 / 시스템설계↔시스템 / 상세설계↔통합 / 구현↔단위
레벨 = 단위·통합·시스템·인수
유형 = 기능·성능·보안·신뢰성·이식성
기법 = 정적 / 명세·구조·경험 기반 동적 테스트
```
