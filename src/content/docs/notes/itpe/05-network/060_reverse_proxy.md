## 지식 로드맵 내 현재 위치

컴퓨터 시스템 및 네트워크 → 핵심 개념 → 리버스 프록시

## 30초 인출

- 본질: 인터넷에 백엔드 데이터베이스와 애플리케이션 서버를 직접 노출할 때 발생하는 해킹 위협과 트래픽 병목
- 메커니즘: 공인 네트워크와 내부 사설망 사이에 역방향 중계 서버를 배치하여 요청 검증, 부하 분산, 암호화 해제를 대행

## 핵심 용어

- SSL/TLS 종단(Termination): 클라이언트와의 무거운 HTTPS 암호화/복호화 핸드셰이크 연산을 리버스 프록시가 전담하여 완료하고, 내부 백엔드 서버와는 고속 평문 HTTP 통신을 수행해 백엔드 CPU 자원을 절약하는 기법
- X-Forwarded-For(XFF): 리버스 프록시를 거치면서 패킷의 출발지 IP가 프록시 IP로 덮어씌워질 때, 원본 접속자의 실제 IP 주소를 유지하기 위해 HTTP 요청 헤더에 기록하는 표준 사실상(De-facto) 규격
- 스티키 세션(Sticky Session / Session Affinity): 상태 유지가 필요한 클라이언트의 요청이 항상 동일한 백엔드 WAS 서버로 전달되도록 쿠키나 해시를 이용해 바인딩하는 로드 밸런싱 방식

## 1교시 10점 답안

### 정의·목적

- 정의: 리버스 프록시은/는 공인 네트워크와 내부 사설망 사이에 역방향 중계 서버를 배치하여 요청 검증, 부하 분산, 암호화 해제를 대행 방식이다.
- 목적: 서버 보안 및 응답 처리량 극대화에 기여한다.

### 핵심 구조와 작동

```text
[ 포워드 프록시 vs 리버스 프록시 비교 ]

1. 포워드 프록시 (Forward Proxy) : 클라이언트 대행 / 외부 접근 통제
[ 사내망 클라이언트 ] ──> [ Forward Proxy ] ── (방화벽) ──> [ 인터넷 웹서버 ]
(내부 사용자 보호, IP 은닉, 유해 사이트 차단)

2. 리버스 프록시 (Reverse Proxy) : 서버 대행 / 내부 인프라 보호
[ 외부 클라이언트 ] ── (인터넷) ──> [ Reverse Proxy ] ──> [ 내부 백엔드 WAS 1 ]
                                  - SSL 종단 / WAF    ──> [ 내부 백엔드 WAS 2 ]
                                  - 로드밸런싱 / 캐싱  ──> [ 내부 백엔드 WAS 3 ]
                                  (내부 서버 IP 은닉, 부하 분산)
```

## 2~4교시 25점 답안

### Ⅰ. 핵심 구조와 작동

```text
[ 포워드 프록시 vs 리버스 프록시 비교 ]

1. 포워드 프록시 (Forward Proxy) : 클라이언트 대행 / 외부 접근 통제
[ 사내망 클라이언트 ] ──> [ Forward Proxy ] ── (방화벽) ──> [ 인터넷 웹서버 ]
(내부 사용자 보호, IP 은닉, 유해 사이트 차단)

2. 리버스 프록시 (Reverse Proxy) : 서버 대행 / 내부 인프라 보호
[ 외부 클라이언트 ] ── (인터넷) ──> [ Reverse Proxy ] ──> [ 내부 백엔드 WAS 1 ]
                                  - SSL 종단 / WAF    ──> [ 내부 백엔드 WAS 2 ]
                                  - 로드밸런싱 / 캐싱  ──> [ 내부 백엔드 WAS 3 ]
                                  (내부 서버 IP 은닉, 부하 분산)
```

### Ⅱ. 핵심 특성

- 보안의 기본인 '네트워크 망 분리'를 구현하는 관문: 인터넷에 노출되는 공인 IP는 리버스 프록시 1대(또는 VIP)뿐이며, 실제 핵심 로직과 고객 데이터가 있는 백엔드 서버는 사설 IP(RFC 1918) 대역에 숨겨 외부 직접 침입을 원천 차단
- 현대 마이크로서비스 아키텍처(MSA)의 API 게이트웨이로 진화: 단순 웹 가속기를 넘어 인증 토큰(JWT) 검증, 라우팅, 속도 제한(Rate Limiting), 카나리 배포 트래픽 조절을 전담하는 인프라 제어의 두뇌 역할 수행
- 프록시 계층의 이중화 없는 도입은 치명적 단일 장애점(SPOF) 초래: 모든 트래픽의 병목 지점이 되므로 반드시 Keepalived 기반 가상 IP(VIP) 이중화 또는 클라우드 글로벌 L4 로드밸런서(NLB) 뒷단에 다중 노드로 배치해야 함

### Ⅲ. 관련 개념과 구분

- 포워드 프록시 vs 리버스 프록시: 포워드 프록시는 클라이언트 편에 서서 외부 웹사이트 접근을 통제하고 클라이언트 IP를 숨김 / 리버스 프록시는 서버 편에 서서 외부 클라이언트 요청을 검증·분산하고 내부 서버 IP를 숨김

### Ⅳ. 적용 문제와 대응

- 적용 상황: 대규모 트래픽이 유입되는 전자상거래 웹 서비스 운영
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 백엔드 로깅 및 침해사고 분석 시 원본 IP 추적 불가 | 프록시 경유 시 TCP 헤더의 출발지 IP가 리버스 프록시 주소로 변조 | 리버스 프록시의 `X-Forwarded-For` 헤더 주입 및 백엔드 WAS 로깅 포맷 연동 | 실제 클라이언트 접속 IP 추적성 확보 및 어뷰징 차단 |
| 대규모 세일 이벤트 시 리버스 프록시 프로세스 다운 | 단일 서버의 파일 디스크립터 고갈 및 SSL 핸드셰이크 연산 폭증 | Nginx 워커 프로세스 튜닝(`worker_connections 65535`) 및 VRRP 이중화 구성 | 연결 수용 한도 대폭 확장 및 무중단 장애 복구 보장 |

### Ⅴ. 기술사적 제언

| 문제 | 해결 방안 |
|---|---|
| 적용 환경에서 발생하는 핵심 제약 | 기존 대책을 적용하고 핵심 운영 지표를 확인해 개선한다. |
