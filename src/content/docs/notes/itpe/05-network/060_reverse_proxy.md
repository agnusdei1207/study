네트워크 → 응용 서비스 전달 및 웹 아키텍처 → **리버스 프록시(Reverse Proxy)**

## 30초 인출

- 본질: **리버스 프록시(Reverse Proxy)** : 클라이언트와 백엔드 서버군 사이에 위치하여 외부로부터의 모든 접속 요청을 대리 수신하고 내부 사설 서버들로 분산 중계하는 L7 게이트웨이 시스템
- 메커니즘: 클라이언트의 TLS 암복호화 종단, URL 기반 L7 라우팅 및 헬스체크 기반 로드밸런싱, 정적 리소스 캐싱, 원본 클라이언트 IP 식별자(X-Forwarded-For) 주입 수행
- 통찰: 백엔드 서버 직접 노출 차단 이면에 단일 장애점(SPOF) 병목과 XFF 헤더 조작 및 HTTP Request Smuggling 취약점 극복을 위해 VRRP 이중화 및 프로토콜 파서 정규화 연계 필수

<details>
<summary>핵심 용어</summary>

- **TLS 종단 (TLS Termination)** : 외부 클라이언트와의 HTTPS 암호화 세션을 리버스 프록시에서 종료하고 내부 백엔드와는 고속 HTTP/내부 TLS로 연결하여 백엔드 CPU 부하를 제거하는 기능
- **X-Forwarded-For (XFF)** : HTTP 프록시나 로드밸런서를 경유할 때 사라지는 원본 클라이언트의 실제 공인 IP 주소를 보존하기 위한 비표준 사실 표준 HTTP 헤더
- **Forwarded 헤더 (RFC 7239)** : X-Forwarded-For, X-Forwarded-Proto 등을 표준화하여 프록시 경유 정보를 `by, for, host, proto` 형태로 표준화한 헤더
- **HTTP Request Smuggling** : 프록시와 백엔드 서버 간의 HTTP 명세(Content-Length vs Transfer-Encoding) 해석 차이를 악용해 비인가 요청을 끼워 넣는 공격
- **Keep-Alive 커넥션 풀링** : 프록시와 백엔드 서버 간에 TCP 연결을 사전에 대량 생성해 재사용함으로써 3-way handshake 오버헤드를 극소화하는 기법

</details>

## 2~4교시 25점 답안

## Ⅰ. 리버스 프록시의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 클라이언트와 내부 백엔드 웹/애플리케이션 서버군 사이에 배치되어 외부로부터의 인입 요청을 대리로 수신한 후 내부 서버로 중계하고 응답을 반환하는 L7 중계 프록시 서버 |
| 목적 | 내부 사설 IP 인프라의 외부 직접 노출 차단, 백엔드 서버 부하 분산(Load Balancing), TLS 암복호화 오프로딩 및 웹 애플리케이션 보안 강화 |

## Ⅱ. 리버스 프록시의 특징 및 핵심 제공 기능

| 핵심 기능 | 세부 동작 메커니즘 | 시스템 기여 효과 |
|---|---|---|
| **보안 은닉 및 격리** | 백엔드 서버의 실제 IP 주소와 내부 네트워크 토폴로지를 외부 인터넷으로부터 완전 은닉 | 외부 공격자의 백엔드 직접 스캔 및 표적 DDoS 공격 원천 차단 |
| **TLS 종단 (Offloading)** | 고부하 RSA/ECC 비대칭키 암복호화 연산을 프록시에서 전담 처리 | 백엔드 서버 CPU 자원 보존 및 SSL 인증서 갱신 관리 일원화 |
| **L7 콘텐츠 기반 라우팅** | HTTP URI 경로, 헤더, 쿠키 값을 분석하여 마이크로서비스(MSA)별 담당 서버로 분기 | 서비스별 도메인 통합 및 유연한 무중단 카나리/블루그린 배포 지원 |
| **캐싱 및 압축 (Gzip/Brotli)** | 정적 자원(이미지, CSS, JS)을 메모리에 캐싱하고 응답 데이터를 실시간 압축 전송 | 백엔드 I/O 부하 대폭 절감 및 네트워크 대역폭 절약, 응답 속도 향상 |

## Ⅲ. 리버스 프록시 아키텍처 및 요청/응답 전달 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [ 리버스 프록시 서비스 전달 아키텍처 ]               │
│                                                                        │
│   [외부 인터넷 클라이언트]                                              │
│          │                                                             │
│          ▼ HTTPS 요청 (공인 IP: 203.0.113.10)                          │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │               DMZ 리버스 프록시 (Nginx / HAProxy)              │   │
│   │  - TLS 가속 종단 (SSL 인증서 보유)                             │   │
│   │  - WAF 웹 방화벽 규칙 검사 (SQLi, XSS 차단)                    │   │
│   │  - X-Forwarded-For: [클라이언트 IP] 헤더 주입                 │   │
│   │  - 정적 캐시 히트 시 즉시 응답                                │   │
│   └───────────────────────────────┬────────────────────────────────┘   │
│                                   │ 내부 사설망 (L7 로드밸런싱)        │
│          ┌────────────────────────┼────────────────────────┐           │
│          ▼ (HTTP / 커넥션 풀)      ▼                        ▼           │
│   [WAS #1: /api/user]      [WAS #2: /api/order]     [정적 스토리지]     │
│   (사설 IP: 10.0.1.11)     (사설 IP: 10.0.1.12)     (사설 IP: 10.0.1.13)│
└────────────────────────────────────────────────────────────────────────┘
```

| 처리 단계 | 주관 요소 | 세부 처리 메커니즘 |
|---|---|---|
| **1. TCP/TLS 세션 종단** | 프록시 전단 엔진 | 클라이언트와 TLS 핸드셰이크를 완료하고 세션 키 수립 후 HTTP 평문 요청 추출 |
| **2. 보안 검사 및 헤더 정규화**| 프록시 필터 모듈 | 유효하지 않은 문자열 검사, 악성 User-Agent 차단 및 `X-Forwarded-For` 헤더 갱신 |
| **3. L7 분기 및 부하 분산** | 로드밸런서 코어 | 라운드로빈, 최소 연결수(Least-Conn) 등 알고리즘으로 정상 백엔드 서버 선별 |
| **4. 백엔드 중계 및 응답 반환**| 커넥션 풀 매니저 | 사전 생성된 Keep-Alive 세션을 재활용하여 질의 전달 후 백엔드 응답을 클라이언트로 회신 |

## Ⅳ. 포워드 프록시(Forward Proxy) vs 리버스 프록시(Reverse Proxy) 비교

| 비교 항목 | 포워드 프록시 (Forward Proxy) | 리버스 프록시 (Reverse Proxy) |
|---|---|---|
| **대리 주체** | **클라이언트(사용자)를 대리** | **서버(서비스 제공자)를 대리** |
| **설치 위치** | 사내 내부망과 인터넷 경계 (클라이언트 측) | 데이터센터 DMZ 영역과 백엔드 앞단 (서버 측) |
| **클라이언트 인지 여부** | 사용자가 브라우저 설정에 프록시 IP를 직접 등록 | 사용자는 프록시를 최종 웹 서버로 인식 (투명성) |
| **주요 목적** | 사내 직원 인터넷 통제, 우회 접속, 아웃바운드 캐싱 | 백엔드 보안 은닉, L7 부하 분산, 인바운드 캐싱 |
| **보안 효과** | 내부 사용자 정보(IP)를 외부 서버로부터 은닉 | 내부 백엔드 인프라(IP)를 외부 공격자로부터 은닉 |
| **대표 소프트웨어** | Squid, Apache Traffic Server | Nginx, HAProxy, Envoy, Traefik |

## Ⅴ. 리버스 프록시 구현 시 핵심 엔지니어링 한계와 방안

| 한계 | 방안 |
|---|---|
| 외부 악의적 공격자가 조작된 `X-Forwarded-For` 헤더를 인위적으로 주입하여 유입시킬 경우, 백엔드 서버가 이를 신뢰하여 IP 기반 접근 제어 목록(ACL)을 우회하거나 감사 로그를 교란하는 IP 스푸핑 발생 | 최외곽 인그레스 프록시에서 외부에서 전달된 모든 `X-Forwarded-For` 헤더를 무조건 파기(Strip)하고 프록시 소켓 계층에서 직접 확인한 순수 TCP 원본 IP로 헤더를 덮어쓰도록(Overwrite) 강제 설정 |
| 프록시 서버와 백엔드 서버 간의 HTTP 명세 해석 불일치로 인해 공격자가 두 번째 요청을 본문에 숨겨 전송하여 타인의 세션을 탈취하는 HTTP Request Smuggling(CL.TE / TE.CL) 공격 발생 | 프록시와 백엔드 간 통신 프로토콜을 모호성이 없는 HTTP/2 바이너리 프레이밍으로 업그레이드하고, HTTP/1.1 환경에서는 Content-Length와 Transfer-Encoding 헤더가 공존하는 비정상 요청 즉시 거부(400 Bad Request) 처리 |
| 수많은 백엔드 서버의 관문 역할을 단일 리버스 프록시 장비가 전담할 경우 장비 하드웨어 장애 발생 시 전사 서비스가 마비되는 단일 장애점(SPOF) 병목 형성 | 복수의 리버스 프록시 노드를 구축하고 가상 라우터 이중화 프로토콜(VRRP/Keepalived) 또는 BGP ECMP 기반 애니캐스트(Anycast) 네트워크 구성을 통해 무중단 액티브-액티브(Active-Active) 장애 조치 체계 확립 |

## Ⅵ. 도입/구축/운영 관점 제언

### 1. 실무 적용 가이드 및 핵심 고려사항
마이크로서비스 및 클라우드 네이티브 환경에서는 단순 리버스 프록시를 넘어 서비스 디스커버리와 동적 라우팅이 통합된 Envoy 기반 클라우드 프록시 채택을 적극 고려해야 하며, 프록시와 백엔드 사이의 내부 네트워크 구간이라 할지라도 제로 트러스트(Zero Trust) 보안 원칙에 입각하여 상호 TLS(mTLS) 암호화를 기본 적용 권장

### 2. 아키텍처 및 상세 메커니즘
```text
┌────────────────────────────────────────────────────────────────────────┐
│               [ 고가용성 리버스 프록시 및 mTLS 연계 아키텍처 ]         │
│                                                                        │
│                       [ 클라이언트 트래픽 ]                            │
│                                │                                       │
│                                ▼ L4 Anycast / DNS 라운드로빈           │
│          ┌─────────────────────┴─────────────────────┐                 │
│          ▼                                           ▼                 │
│   ┌───────────────┐     Keepalived VRRP       ┌───────────────┐        │
│   │ Reverse Proxy │◄═════════════════════════►│ Reverse Proxy │        │
│   │  (Active #1)  │         Heartbeat         │  (Active #2)  │        │
│   └──────┬────────┘                           └───────┬───────┘        │
│          │                                            │                │
│          └─────────────────────┬──────────────────────┘                │
│                                │ 내부 전용 mTLS 암호화 터널            │
│          ┌─────────────────────┼─────────────────────┐                 │
│          ▼                     ▼                     ▼                 │
│   [인증 서비스]         [주문 서비스]         [결제 서비스]            │
│   (mTLS 클라이언트검증) (mTLS 클라이언트검증) (mTLS 클라이언트검증)    │
└────────────────────────────────────────────────────────────────────────┘
```

### 3. 기술 유형 및 비교 평가
| 구분 | Nginx | HAProxy | Envoy | API Gateway (Kong 등) |
|---|---|---|---|---|
| **주요 아키텍처** | 비동기 이벤트 기반 (C언어) | 이벤트 기반 단일 프로세스 | C++11 기반 멀티스레드 | Nginx/Lua 플러그인 확장 |
| **특화 영역** | 고성능 정적 웹 및 리버스 프록시 | 초고속 L4/L7 로드밸런싱 | 클라우드 네이티브 서비스 메시 | API 인증/인가, 레이트 리미팅 |
| **HTTP/3 (QUIC)**| 최신 버전 지원 | 지원 진행 중 | 완벽 지원 | Nginx 엔진 종속 |
| **동적 구성 갱신** | 프로세스 Reload 필요 | 소켓 명령을 통한 동적 갱신 | xDS API 기반 무중단 핫 리로드 | REST API 통한 실시간 라우팅 변경 |
