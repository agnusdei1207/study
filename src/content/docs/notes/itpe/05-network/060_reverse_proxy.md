## 연관 키워드

- 리버스 프록시(Reverse Proxy), 포워드 프록시(Forward Proxy), WAS(Web Application Server)
- L7 로드밸런싱, TLS 종단(TLS Termination), 캐싱, WAF(Web Application Firewall)
- X-Forwarded-For, PROXY Protocol, SPOF(Single Point of Failure), VRRP(Virtual Router Redundancy Protocol)
- 인그레스(Ingress), API 게이트웨이, 정책 집행점(PEP, Policy Enforcement Point), 제로 트러스트(Zero Trust)

## Ⅰ. 리버스 프록시의 개요

- 핵심 요약 : 백엔드 서버 앞단에서 요청을 대신 수신해 보안·부하 분산·암호화 처리를 한곳에 모으는 대리 서버.
- 개념 : 외부 클라이언트와 내부 **웹 애플리케이션 서버**(WAS, Web Application Server) 사이에서 요청을 대신 받아 내부로 중계하고 응답을 되돌려주는 **리버스 프록시**(서버를 대신해 외부 요청을 수신하는 대리 서버, Reverse Proxy).
- 배경 및 필요성 : 웹 서버를 인터넷에 직접 노출하면 공격 표면이 그대로 열리고, 단일 서버는 처리 용량과 TLS(Transport Layer Security) 암복호화 부하, 서버 구조 노출 문제를 피하기 어려움.
- 주요 목적 : 내부 구조 은폐, L7 부하 분산과 암호화 처리의 집중, 정적 콘텐츠 캐싱을 통한 백엔드 부하 절감.

## Ⅱ. 리버스 프록시의 특징 및 장점

- 핵심 요약 : 단일 접점에서 요청을 해석·분배하는 구조가 보안 은폐와 자원 절감으로 이어짐.

1. 요청 라우팅 : Host 헤더와 URI(Uniform Resource Identifier) 경로로 목적 서비스를 결정 → 서비스 단위 배포와 경로별 정책 적용 용이.
2. TLS 종단 : 외부 HTTPS(Hypertext Transfer Protocol Secure) 세션을 프록시에서 해독하는 **TLS 종단**(TLS Termination) 수행 → 백엔드의 암복호화 연산 부담 감소. 내부 구간의 암호화 여부는 보안 정책으로 별도 결정.
3. 헤더 재작성 : 원본 클라이언트 IP를 전달하는 **X-Forwarded-For** 헤더 생성 → 백엔드 로그와 접근 제어가 원본 기준으로 수행.
4. 보안 필터와 캐싱 : **WAF**(웹 애플리케이션 공격 차단 장비, Web Application Firewall)와 요청 속도 제한 적용, 정적 응답 캐싱 → 공격 표면과 백엔드 부하의 동시 축소.

## Ⅲ. 리버스 프록시의 구조 (흐름)

- 핵심 요약 : 단일 공인 접점에서 보안 검사와 캐시 확인을 거친 뒤 사설망의 백엔드 서버군으로 분배하는 구조.

```text
[ 네트워크 위치 구조 ]

클라이언트 (외부 인터넷)
    ↓ HTTPS · 단일 공인 IP
리버스 프록시
  TLS 종단 · 라우팅 · WAF · 캐시
    ↓ 사설망 (Private Network)
앱 서버 1 / 2 / 3
  실제 IP와 토폴로지 은폐
```

```text
[ 요청 처리 흐름 ]

요청 수신 (TLS 종단)
    ↓
보안 검사 (WAF · 속도 제한)
    ↓
캐시 적중 → 즉시 응답
    ↓ 미적중
백엔드 전달 (L7 로드밸런싱)
```

## Ⅳ. 포워드 프록시와 리버스 프록시의 비교

- 핵심 요약 : 포워드 프록시가 사용자를 대리해 외부 접속을 통제하는 반면, 리버스 프록시는 서버를 대리해 유입 트래픽을 제어하는 방향 차이.

| 비교 축 | 포워드 프록시 (Forward Proxy) | 리버스 프록시 (Reverse Proxy) |
| --- | --- | --- |
| 설치 위치 | 사내망 클라이언트 앞단 | 서버 팜 인프라 앞단 |
| 은폐 대상 | 사용자(클라이언트)의 실제 IP | 백엔드 서버의 IP와 내부 구조 |
| 주요 목적 | 사내 보안 정책 집행, 접속 차단 | 로드밸런싱, 보안 방어, 캐싱 |
| 접속 대상 | 임의의 외부 인터넷 자원 | 특정 서비스의 내부 웹·앱 서버 |
| 캐싱 대상 | 사용자가 자주 조회하는 외부 자원 | 자사 서비스의 정적 콘텐츠 |
| 대표 구현 | Squid | Nginx, HAProxy, Envoy |

- 선택 기준 : 사용자 통제와 감사가 목적이면 포워드 프록시, 서비스 보호와 트래픽 제어가 목적이면 리버스 프록시.
- 확장 형태 : API 게이트웨이는 리버스 프록시에 인증·정책·과금 기능을 더한 확장형으로, 서비스 간 공통 정책의 집행 지점으로 활용.

## Ⅴ. 리버스 프록시 운영의 한계와 방안

- 핵심 요약 : 단일 장애점, 클라이언트 IP 유실, 캐시 오노출이 운영의 세 한계이며 이중화·헤더 정책·캐시 정책으로 일대일 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 단일 장애점과 병목 | 모든 인바운드 트래픽이 한곳에 집중되어 프록시 장애 시 전체 서비스 중단 | **SPOF**(단일 장애점, Single Point of Failure) 제거를 위한 VRRP(Virtual Router Redundancy Protocol) 이중화와 다중 노드 분산 | 가용률, 노드별 처리량 편차 |
| 클라이언트 실제 IP 유실 | 백엔드 로그에 프록시 IP만 남아 침해 분석과 접근 제어가 어려움 | X-Forwarded-For 주입 정책 필수화, L4 구간 PROXY Protocol 적용 | 원본 IP 기록률, 차단 정확도 |
| 캐시 오노출 | 개인화 응답의 부적절한 캐싱으로 타 사용자 정보 노출 위험 | Cache-Control 정책과 사용자별 캐시 키 분리 규칙 수립 | 캐시 오노출 탐지 건수 |

## Ⅵ. 리버스 프록시 활용 확대를 위한 기술사적 제언

- 핵심 요약 : 정책의 프록시 계층 집중, 제로 트러스트 집행점화, 고성능 데이터 평면 검토로 활용 범위를 넓히는 것.

1. 플랫폼 운영 조직은 쿠버네티스 인그레스(Ingress) 컨트롤러를 공통 인프라로 정착시켜, 인증 검증·요청 제한·카나리 배포 같은 정책을 프록시 계층에서 일괄 적용해야 한다.
2. 보안 조직은 제로 트러스트(Zero Trust) 원칙에 따라 리버스 프록시를 **정책 집행점**(PEP, Policy Enforcement Point)으로 지정하고, 세션마다 사용자 신원과 단말 상태를 확인하는 체계를 도입해야 한다.
3. 고성능 클러스터 운영팀은 사이드카 프록시의 통신 지연을 줄이기 위해 eBPF(extended Berkeley Packet Filter) 기반 소켓 우회를 시범 적용하고 성능을 검증해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 리버스 프록시는 백엔드 앞의 단일 접점으로 보안·부하 분산·암호화를 집중시키는 필수 인프라 계층.
- 가용성은 이중화 설계가, 로그 정확성은 헤더 정책이 뒷받침하며, 정책 집행 지점으로서의 역할이 계속 확대되는 계층.
