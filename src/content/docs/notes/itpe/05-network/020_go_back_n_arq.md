## Ⅰ. Go-Back-N ARQ의 개요

- 개념 : **슬라이딩 윈도우** 기반의 **자동 재전송(ARQ, Automatic Repeat Request)** 프로토콜로, 송신 측은 윈도우 크기($N$)만큼 확인 응답(ACK, Acknowledgment) 없이도 패킷을 연속 전송할 수 있으나, 수신 측에서 특정 패킷의 오류를 감지하면 그 이후에 전송된 모든 정상 패킷을 폐기하고 오류가 발생한 패킷부터 $N$개의 패킷 전체를 되돌아가서 다시 재전송하는 오류 제어 기술.
- 배경 및 필요성 : 단순 **정지-대기(Stop-and-Wait)** 방식의 긴 대기 시간으로 인한 전송 효율 저하를 극복하면서도, 수신 측의 버퍼 메모리 구현 비용을 최소화(수신 버퍼 1)하기 위해 개발됨.
- 핵심 목적 : 파이프라인 전송을 통한 채널 처리율 향상, 수신단 정렬 버퍼 불필요에 따른 하드웨어 단순화 유지, 누적 확인 응답(Cumulative ACK)을 통한 제어 오버헤드 절감.

## Ⅱ. Go-Back-N ARQ의 핵심 아키텍처 및 동작 메커니즘

Go-Back-N은 송신 측에 크기 $N$의 슬라이딩 윈도우와 단일 재전송 타이머를 유지하고, 수신 측은 오직 '다음에 올 정상 순서 번호'만을 기다리며 순서가 어긋난 패킷은 모두 폐기(Drop)하는 방식으로 동작함.

```text
[ Go-Back-N ARQ 오류 발생 및 재전송 동작 시퀀스 ]

송신단 (윈도우 크기 N = 4)                           수신단 (수신 윈도우 = 1)
  │─── Frame 0 ───────────────────────────────────────>│ (정상 수신: 기대 번호 1로 갱신)
  │<── ACK 0 ──────────────────────────────────────────│
  │─── Frame 1 ───────────────────────────────────────>│ (정상 수신: 기대 번호 2로 갱신)
  │<── ACK 1 ──────────────────────────────────────────│
  │─── Frame 2 (전송 중 손실!) ───X                   │
  │─── Frame 3 ───────────────────────────────────────>│ (폐기! 기대 번호 2 아님)
  │─── Frame 4 ───────────────────────────────────────>│ (폐기! 기대 번호 2 아님)
  │─── Frame 5 ───────────────────────────────────────>│ (폐기! 기대 번호 2 아님)
  │
  │ [Frame 2 재전송 타이머 만료 (Timeout)!]
  │ (윈도우 내 미확인 프레임 2, 3, 4, 5 로 되돌아감: Go-Back-4)
  │
  │─── Frame 2 (재전송) ──────────────────────────────>│ (정상 수신: 기대 번호 3으로 갱신)
  │─── Frame 3 (재전송) ──────────────────────────────>│ (정상 수신: 기대 번호 4로 갱신)
  │─── Frame 4 (재전송) ──────────────────────────────>│ (정상 수신: 기대 번호 5로 갱신)
```

- **송신 윈도우($N$)와 단일 타이머** : 송신단은 미확인 상태로 최대 $N$개 프레임을 송신할 수 있으며, 윈도우 내 '가장 오래된 미확인 패킷'에 대해서만 단일 재전송 타이머를 가동.
- **수신 윈도우 크기 = 1** : 수신단은 오직 순서 번호가 정확히 일치하는 패킷만 수락하여 상위 계층으로 전달하고, 순서가 어긋난 패킷(Out-of-order)은 버퍼링하지 않고 즉시 폐기.
- **누적 확인 응답(Cumulative ACK)** : 수신단이 반환하는 ACK $k$는 '$k$번 패킷까지 모두 이상 없이 잘 받았다'는 의미를 가지므로, 이전 ACK 프레임 일부가 유실되어도 후속 ACK로 자동 복구.
- **Go-Back-N 재전송 동작** : 타이머가 만료되면 확인 응답을 받지 못한 첫 번째 프레임부터 시작하여 송신 윈도우 내에 있던 모든 후속 프레임을 통째로 재전송.

## Ⅲ. Go-Back-N ARQ의 세부 구성 요소 및 비교 분석

| 비교 항목 | Stop-and-Wait ARQ | Go-Back-N ARQ | Selective Repeat ARQ |
|---|---|---|---|
| 송신 윈도우 크기 | 1 | $N$ ($N \le 2^m - 1$) | $N$ ($N \le 2^{m-1}$) |
| 수신 윈도우 크기 | 1 | 1 (무조건 1 유지) | $N$ (송신 윈도우와 동일) |
| 순서 역전 패킷 | 발생 불가 | 수신단 즉시 폐기 | 수신단 버퍼에 저장 및 정렬 |
| 오류 발생 시 재전송 | 손실된 1개 프레임 재전송 | 손실 프레임 이후 전송분 전체 재전송 | 오류가 검출된 프레임만 단독 재전송 |
| 채널 오류율 영향 | 오류율과 무관하게 저속 | 오류율 높을 시 처리량 급락 | 오류율 높아도 높은 처리량 유지 |
| 메모리 구현 비용 | 극도로 단순 (버퍼 불필요) | 낮음 (수신 버퍼 불필요) | 높음 (수신단 정렬 큐 및 타이머 다수) |

- Go-Back-N은 수신단 하드웨어 버퍼를 1개로 제한할 수 있어 센서나 임베디드 기기에 이상적이나, 채널 오류율이 높거나 전파 지연이 긴 환경에서는 대량의 중복 재전송으로 인해 성능이 급격히 저하됨.

## Ⅳ. Go-Back-N ARQ의 주요 한계점 및 해결 방안

- 단 1개 프레임 오류로 인한 후속 정상 프레임 대량 재전송 낭비 :
  - 한계점 : 이미 수신단에 도달한 정상 프레임(3, 4, 5)까지 강제 폐기되고 재전송되어 링크 대역폭 소모 극심.
  - 해결 방안 : 수신단 버퍼를 확충하고 선택적 재전송(Selective Repeat) 또는 TCP(Transmission Control Protocol) SACK으로 전환.
- 윈도우 크기($N$) 설계 오류 시 순서 번호 모호성 발생 :
  - 한계점 : 순서 번호 비트 수 $m$에 대해 윈도우 크기 $N \ge 2^m$으로 설정할 경우, 새 프레임과 재전송 프레임을 수신단이 식별 불가.
  - 해결 방안 : 수학적 상한 조건인 $N \le 2^m - 1$을 철저히 준수하여 프로토콜 설계.
- 단일 재전송 타이머의 RTT(Round-Trip Time) 변동 취약성 :
  - 한계점 : 네트워크 지연이 일시적으로 증가했을 때 불필요한 타임아웃이 발생하여 윈도우 전체가 조기 재전송되는 악순환 유발.
  - 해결 방안 : 지수 가중 이동 평균(EWMA) 기반의 정밀한 RTO(Retransmission Timeout) 동적 계산식 적용.

## Ⅴ. Go-Back-N ARQ 적용 및 발전을 위한 기술사적 제언

- 저사양 IoT(Internet of Things) 마이크로컨트롤러(MCU, Microcontroller Unit) 통신 프로토콜 표준화에 선별 채택 : RAM(Random-Access Memory) 메모리가 수 KB에 불과한 저전력 센서 노드에서는 수신 버퍼 정렬 오버헤드가 없으므로 Go-Back-N 프로토콜을 적극 활용 권장.
- 광대역 고속 백본 및 무선 환경에서는 SACK 기반 전환 필수 : 5G/LTE(Long-Term Evolution) 및 고속 인터넷 환경에서는 프레임 재전송 오버헤드를 줄이기 위해 Selective Repeat 및 L2 HARQ 결합 아키텍처로 고도화.
- 누적 ACK의 장점을 살린 TCP 기본 윈도우 엔진 설계 : 수신단에서 모든 패킷마다 개별 응답하지 않고 주기적 누적 ACK를 전송하도록 튜닝하여 상향 링크(Uplink) 트래픽 절감 유도.
