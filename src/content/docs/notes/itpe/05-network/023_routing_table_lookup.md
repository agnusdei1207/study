## Ⅰ. 라우팅 테이블 탐색의 개요

- **개념** : 라우터나 L3 스위치가 인입된 IP 패킷의 목적지 주소를 자신의 포워딩 정보 베이스(FIB: Forwarding Information Base) 엔트리들과 대조하여 최적의 다음 홉(Next Hop) 및 송출 인터페이스를 결정하는 L3 패킷 포워딩 핵심 메커니즘.
- **배경 및 필요성** : 전 세계 인터넷 BGP 라우팅 엔트리가 100만 개(1M Prefixes)를 돌파하고 테라비트급 고속 스위칭 환경이 도래함에 따라, 패킷 도착 시 라우팅 테이블을 나노초 단위로 초고속 탐색하지 못하면 심각한 라인 레이트 병목이 발생함.
- **핵심 목적** : 최장 일치 규칙(LPM: Longest Prefix Match)의 정확한 수행, 기가비트/테라비트 회선 속도를 수용하는 극저지연 탐색 속도 보장, 메모리 사용량 및 전력 소비 최적화.

## Ⅱ. 라우팅 테이블 탐색의 핵심 아키텍처 및 동작 메커니즘

라우팅 테이블 탐색은 목적지 IP 주소와 가장 길게 일치하는 서브넷 마스크를 가진 경로를 선택하는 LPM 규칙을 따르며, 소프트웨어 Trie 알고리즘과 하드웨어 TCAM 메모리를 통해 가속됨.

```text
[ 라우팅 테이블 LPM(Longest Prefix Match) 탐색 원리 ]

목적지 IP 주소: 192.168.1.130 (2진수: 11000000.10101000.00000001.10000010)

라우팅 테이블 (FIB 엔트리 목록):
  엔트리 1: 192.168.0.0/16       (일치 길이: 16비트) -> Next Hop: Router A
  엔트리 2: 192.168.1.0/24       (일치 길이: 24비트) -> Next Hop: Router B
  엔트리 3: 192.168.1.128/26     (일치 길이: 26비트) -> Next Hop: Router C (최장 일치!)
  엔트리 4: 0.0.0.0/0 (Default)  (일치 길이:  0비트) -> Next Hop: Router D

  => 결과: 가장 구체적이고 프리픽스가 긴 '엔트리 3 (/26)'으로 최종 포워딩 결정!

[ 고속 탐색 하드웨어 vs 소프트웨어 구조 ]
+------------------------------------+  +------------------------------------+
| 하드웨어 TCAM (1 클럭 병렬 비교)    |  | 소프트웨어 Trie (Patricia / Multi)  |
| [ 192.168.1.128/26 ] ==> MATCH!   |  |        (Root)                      |
| (0, 1, Don't Care 동시 병렬 검색)  |  |        /    \                      |
+------------------------------------+  |       0      1                      |
                                        +------------------------------------+
```

- **최장 일치 규칙(Longest Prefix Match: LPM)** : 복수의 라우팅 경로가 목적지 IP와 매칭될 경우, 서브넷 마스크 비트 길이가 가장 길고 구체적인 경로를 최우선 선택.
- **제어 평면(RIB)과 전달 평면(FIB) 분리** : BGP/OSPF가 계산한 복잡한 RIB(Routing Information Base)을 패킷 포워딩에 최적화된 단순 FIB로 컴파일하여 ASIC에 탑재.
- **트라이(Trie) 탐색 알고리즘** : IP 주소의 비트열을 트리 형태로 구성하여 탐색하는 방식으로, Radix Tree, Patricia Trie, 256-Way Multi-bit Trie 등으로 진화하여 메모리 접근 횟수 최소화.
- **TCAM(Ternary Content Addressable Memory)** : 0과 1 외에 'X(Don't Care)' 비트 마스킹을 지원하여 단 1클럭 사이클 만에 수만~수십만 개 엔트리를 병렬 비교하는 하드웨어 ASIC 엔진.

## Ⅲ. 라우팅 테이블 탐색의 세부 구성 요소 및 비교 분석

| 비교 항목 | 선형 순차 탐색 (Linear) | 소프트웨어 멀티비트 트라이 | 하드웨어 TCAM 병렬 탐색 |
|---|---|---|---|
| **탐색 시간 복잡도**| $O(N)$ (엔트리 수에 비례) | $O(W / k)$ ($k$ 비트 단위 점프) | $O(1)$ (단 1 클럭 사이클) |
| **탐색 지연시간** | 수 마이크로초 ~ 수 밀리초 | 수십 ~ 수백 나노초 | 2 ~ 5 나노초 (초고속) |
| **메모리 비용** | 최소 (단순 배열) | 낮음 (일반 DRAM/SRAM 활용) | 매우 고가 (일반 SRAM의 수배) |
| **전력 소비 및 발열**| 극히 낮음 | 낮음 | 매우 높음 (전 칩셋 동시 구동) |
| **주요 적용 장비** | 저가형 공유기, 임베디드 | 리눅스 커널, VPP 라우터 | 엔터프라이즈 백본 코어 라우터 |

- 백본 라우터는 1클럭 $O(1)$ 탐색이 가능한 하드웨어 TCAM을 채택하여 라인 레이트를 보장하며, 클라우드 가상 스위치는 캐시 친화적인 압축 멀티비트 트라이 알고리즘으로 발전함.

## Ⅳ. 라우팅 테이블 탐색의 주요 한계점 및 해결 방안

- **글로벌 풀 라우팅 테이블(1M+) 폭증에 따른 고가 TCAM 용량 고갈** :
  - **한계점** : BGP 테이블 증가 속도가 하드웨어 TCAM 용량을 초과하여 장비 다운 및 신규 경로 학습 거부 사태 발생.
  - **해결 방안** : FIB 압축 알고리즘(FIB Aggregation/Compression) 적용, 코어 장비의 디폴트 라우트 활용 및 에지 라우터로의 역할 분담.
- **TCAM 칩셋의 막대한 전력 소비 및 극심한 랙 발열** :
  - **한계점** : 모든 엔트리를 매 클럭마다 병렬 비교하므로 전력 소모가 극심하여 고밀도 데이터센터 PUE 열화 초래.
  - **해결 방안** : 소프트웨어 기반 고속 알고리즘(Tree-Bitmap, DXR)과 온칩 고속 캐시를 결합한 하이브리드 포워딩 엔진 채택.
- **동적 라우팅 경로 변경 시 FIB 테이블 업데이트 지연(Churn)** :
  - **한계점** : BGP 경로가 자주 뒤흔들릴 때(Path Flapping) TCAM 재배치 연산으로 인해 일시적 포워딩 루프 또는 드롭 유발.
  - **해결 방안** : RCU(Read-Copy Update) 락리스 자료구조 및 섀도우 FIB(Shadow FIB) 백그라운드 갱신 후 원자적 포인터 스왑 적용.

## Ⅴ. 라우팅 테이블 탐색 적용 및 발전을 위한 기술사적 제언

- **고성능 소프트웨어 라우터(DPDK & VPP) 환경의 캐시 미스 최소화 아키텍처 구축** : CPU L3 캐시 라인(64바이트) 크기에 최적화된 벡터 패킷 처리(Vector Packet Processing) 기반 멀티비트 트라이 도입 권장.
- **백본 BGP 라우팅 테이블 다이어트(Route Filtering) 정책 수립** : 불필요한 /24 세부 경로 광고를 차단하고 RPKI(Resource Public Key Infrastructure) 검증을 결합하여 무효 경로의 FIB 등재 원천 방지.
- **차세대 세그먼트 라우팅(SRv6) 기반 포워딩 평면 단순화** : 복잡한 홉별 라우팅 테이블 조회를 패킷 헤더 내 명시적 세그먼트 리스트 기반 포워딩으로 단순화하여 스위치 탐색 오버헤드 획기적 절감 추진.
