## 30초 인출

- 본질: **소켓 통신(Socket Communication)** : 응용 프로그램이 운영체제(OS) 커널의 전송 계층(TCP/UDP) 프로토콜 스택과 상호작용하여 네트워크를 통해 데이터를 송수신할 수 있도록 추상화한 양방향 통신 종단점 API
- 메커니즘: 서버의 `socket() -> bind() -> listen() -> accept()`와 클라이언트의 `connect()` 시스템 콜을 통해 5-Tuple 기반 가상 회선을 수립하고 `send()/recv()` 버퍼를 통해 전이중 통신 수행
- 통찰: TCP 스트림의 메시지 경계 부재에 따른 패킷 뭉침 현상과 C10K 동시 접속 시 스레드 고갈 한계 극복을 위해 TLV 프레이밍 설계와 epoll 기반 I/O 다중화 이벤트 루프 연계 필수

<details>
<summary>핵심 용어</summary>

- **5-Tuple** : 네트워크 상에서 유일한 소켓 연결 세션을 식별하는 5가지 요소 (출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port, 전송 프로토콜)
- **File Descriptor (FD)** : 유닉스/리눅스 계열 운영체제에서 소켓을 파일처럼 취급하여 추상화한 정수형 인덱스 핸들
- **I/O Multiplexing (다중화)** : 단일 스레드가 `select`, `poll`, `epoll` 등의 시스템 콜을 활용해 수많은 소켓 FD의 입출력 준비 상태를 감시하고 처리하는 모델
- **epoll** : 리눅스 커널의 이벤트 기반 I/O 통지 메커니즘으로 감시 대상 소켓 수($N$)에 무관하게 활성 소켓만 $O(1)$ 복잡도로 반환하는 고성능 API
- **TLV (Type-Length-Value)** : 스트림 통신에서 메시지의 경계를 복원하기 위해 패킷 헤더에 데이터 유형과 길이를 명시하는 가변 프레이밍 포맷

</details>

## 2~4교시 25점 답안

## Ⅰ. 소켓 통신의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 운영체제 커널이 응용 프로그램 프로세스에 제공하는 네트워크 통신의 논리적 종단점(Endpoint) 인터페이스로, 버클리 소켓(BSD Socket) API 기반의 양방향 데이터 통신 체계 |
| 목적 | 물리적 네트워크 하드웨어와 복잡한 프로토콜 세부 구현을 추상화하여, 파일 I/O와 동일한 방식으로 신뢰성 있는 네트워크 데이터 송수신 지원 |

## Ⅱ. 소켓 통신의 특징 및 핵심 식별자

| 소켓 식별 요소 | 상세 역할 | 엔지니어링 고려사항 |
|---|---|---|
| **출발지 IP (Source IP)** | 송신 호스트의 네트워크 인터페이스 식별 | 멀티홈(Multi-homed) 서버 환경에서 바인딩할 로컬 IP 명시 |
| **출발지 포트 (Source Port)** | 송신 호스트 내의 특정 프로세스/스레드 식별 | 클라이언트의 경우 OS 커널이 임시 포트(Ephemeral Port) 자동 할당 |
| **목적지 IP (Dest IP)** | 수신 대상 호스트의 L3 논리 주소 식별 | DNS 조회를 통한 도메인 이름에서 IP 변환 연계 |
| **목적지 포트 (Dest Port)** | 수신 호스트 내의 대상 서비스 식별 | 표준 Well-known 포트(80, 443 등) 또는 커스텀 포트 지정 |
| **프로토콜 (Protocol)** | L4 전송 계층 프로토콜 식별 | `SOCK_STREAM` (TCP: 신뢰성/연결형), `SOCK_DGRAM` (UDP: 비연결형) |

## Ⅲ. 소켓 통신 라이프사이클 및 시스템 콜 흐름 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [ TCP 소켓 통신 시스템 콜 라이프사이클 ]              │
│                                                                        │
│       [ 서버 (Server) ]                             [ 클라이언트 (Client) ] │
│      ┌────────────────┐                                                │
│      │ socket() 생성  │                                                │
│      └───────┬────────┘                                                │
│      ┌───────▼────────┐                                                │
│      │ bind(IP:Port)  │                                                │
│      └───────┬────────┘                                                │
│      ┌───────▼────────┐                             ┌────────────────┐ │
│      │ listen(Backlog)│                             │ socket() 생성  │ │
│      └───────┬────────┘                             └───────┬────────┘ │
│      ┌───────▼────────┐      3-way handshake        ┌───────▼────────┐ │
│      │ accept() [대기]│◄────────────────────────────┤ connect()      │ │
│      └───────┬────────┘ (SYN -> SYN/ACK -> ACK)     └───────┬────────┘ │
│              │ 연결 소켓(Client FD) 생성                    │          │
│      ┌───────▼────────┐        데이터 스트림        ┌───────▼────────┐ │
│      │ read() / write│◄════════════════════════════►│ write() / read │ │
│      └───────┬────────┘                             └───────┬────────┘ │
│      ┌───────▼────────┐      4-way handshake        ┌───────▼────────┐ │
│      │ close()        │◄────────────────────────────┤ close()        │ │
│      └────────────────┘ (FIN -> ACK -> FIN -> ACK)  └────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

| 시스템 콜 | 호출 주체 | 핵심 동작 및 커널 상태 변화 |
|---|---|---|
| **`socket()`** | 서버 / 클라이언트 | 커널 내부에 통신용 소켓 구조체를 할당하고 참조할 파일 디스크립터(FD) 반환 |
| **`bind()`** | 서버 (주로) | 생성된 소켓 FD에 특정 로컬 IP 주소와 포트 번호를 결합 |
| **`listen()`** | 서버 | 소켓을 수동 연결 대기 상태로 전환하고 커널 Backlog 큐(SYN/Accept) 생성 |
| **`connect()`** | 클라이언트 | 대상 서버로 TCP SYN을 발송하여 3-way handshake 연결 수립 개시 |
| **`accept()`** | 서버 | 완료 큐에서 연결 요청을 꺼내어 실제 통신에 사용할 신규 연결 소켓 FD 반환 |
| **`send()` / `recv()`**| 양 종단 | 커널의 소켓 송신/수신 버퍼와 사용자 메모리 공간 간의 데이터 복사 수행 |

## Ⅳ. TCP 스트림 소켓 vs UDP 데이터그램 소켓 비교

| 비교 항목 | TCP 소켓 (SOCK_STREAM) | UDP 소켓 (SOCK_DGRAM) |
|---|---|---|
| **연결 방식** | 연결 지향형 (Connection-oriented, 3-way) | 비연결형 (Connectionless, 사전 핸드셰이크 없음) |
| **전송 신뢰성** | 패킷 손실 시 재전송(ARQ) 및 순서 무결성 보장 | 신뢰성 미보장 (패킷 유실, 역전 가능성 상존) |
| **데이터 경계** | **메시지 경계 없음 (연속된 바이트 스트림)** | **메시지 경계 보존 (개별 독립 데이터그램)** |
| **흐름/혼잡 제어** | 슬라이딩 윈도우 흐름 제어, 슬로우 스타트 혼잡 제어 | 자체 제어 기능 전무 (애플리케이션 전담) |
| **시스템 콜 매핑** | `listen()`, `accept()`, `send()`, `recv()` | `sendto()`, `recvfrom()` (단일 소켓 다중 통신) |
| **대표 활용 처** | 웹(HTTP/1.1, HTTP/2), DB 연결, 파일 전송(FTP) | 실시간 스트리밍, 온라인 게임, DNS, QUIC(HTTP/3) |

## Ⅴ. 소켓 통신 구현 시 핵심 엔지니어링 한계와 방안

| 한계 | 방안 |
|---|---|
| TCP의 연속 바이트 스트림 특성과 네이글(Nagle) 알고리즘으로 인해 전송된 여러 패킷이 수신측 버퍼에 하나로 뭉쳐지거나(Packet Coalescing) 임의로 쪼개져 수신되는 프레이밍 붕괴 현상 발생 | 애플리케이션 계층 헤더에 데이터 길이를 명시하는 TLV(Type-Length-Value) 프레이밍을 설계하여 수신 버퍼에서 정확한 바이트 크기만큼 분할 파싱하고, 지연 민감 트래픽은 `TCP_NODELAY` 옵션으로 소형 패킷 즉시 송출 강제 |
| 동시 접속자 수만 명(C10K) 환경에서 클라이언트 연결당 1개의 OS 스레드를 생성하는 블로킹 I/O 모델 적용 시 스레드 스택 메모리(기본 8MB) 고갈 및 커널 콘텍스트 스위칭 오버헤드로 시스템 마비 | 단일 스레드가 수만 개의 비블로킹 소켓 파일 디스크립터를 커널 이벤트 기반으로 감시하는 리눅스 `epoll`(Edge-Triggered 모드) 기반 논블로킹 I/O 다중화(Reactor Pattern) 아키텍처 적용 |
| 네트워크 단선, 중간 방화벽의 비정상 세션 종료 시 TCP 소켓이 단절을 감지하지 못하고 `recv()` 상태에서 영구 블로킹되어 소켓 자원이 누수되는 유령 연결(Half-Open) 발생 | 소켓 레벨의 `SO_KEEPALIVE` 옵션(`tcp_keepalive_time` 60초)을 활성화하거나, 응용 계층 레벨에서 주기적 하트비트(Ping/Pong) 프로토콜을 구현하여 미응답 시 소켓 강제 `close()` 회수 |

## Ⅵ. 도입/구축/운영 관점 제언

### 1. 실무 적용 가이드 및 핵심 고려사항
초고성능 네트워크 서버 구축 시, 전통적인 동기 블로킹 방식은 절대 지양하고 Netty(Java)나 libuv(Node.js)와 같은 검증된 이벤트 루프 프레임워크를 도입해야 하며, 소켓 수신 버퍼(`SO_RCVBUF`)와 송신 버퍼(`SO_SOBUF`)를 대역폭 지연 곱(BDP)에 맞추어 적절히 튜닝하고 커널 5.1 이상에서는 제로 카피 비동기 I/O인 `io_uring` 도입 검토 권장

### 2. 아키텍처 및 상세 메커니즘
```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [ Reactor 패턴 기반 epoll 소켓 서버 아키텍처 ]       │
│                                                                        │
│   [수만 개 클라이언트 연결]                                            │
│   (Socket FD 1, 2, ..., N)                                             │
│          │                                                             │
│          ▼ Non-blocking 모드 등록                                      │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │                 Linux Kernel: epoll 인스턴스                   │   │
│   │  - Red-Black 트리: O(1) 복잡도로 관심 소켓 FD 관리             │   │
│   │  - Ready List: I/O 이벤트 발생 소켓만 즉시 큐잉                │   │
│   └───────────────────────────────┬────────────────────────────────┘   │
│                                   │ epoll_wait() 호출 (이벤트만 반환)   │
│                                   ▼                                    │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │                 Main Reactor (이벤트 루프 스레드)              │   │
│   │  - 수신된 FD 이벤트 디스패치                                  │   │
│   └───────┬────────────────────────────────────────────────┬───────┘   │
│           │ 읽기/쓰기 작업 위임                            │           │
│           ▼                                                ▼           │
│   ┌───────────────┐                                ┌───────────────┐   │
│   │ Worker 스레드 1│ (비즈니스 로직 처리)           │ Worker 스레드 2│   │
│   └───────────────┘                                └───────────────┘   │
└────────────────────────────────────────────────────────────────────────┘
```

### 3. 기술 유형 및 비교 평가
| I/O 처리 모델 | 시스템 콜 | 다중 연결 처리 복잡도 | 메모리 및 CPU 효율성 | 주 적용 프레임워크 |
|---|---|---|---|---|
| **동기 블로킹 (Blocking)** | `read()`, `write()` | 연결당 1 스레드 (확장성 극히 불량) | 스레드 스택 메모리 낭비, 문맥 교환 과다 | 고전적 Apache HTTPD |
| **I/O 다중화 (select/poll)**| `select()`, `poll()`| $O(N)$ 전수 순회 (1024개 한계) | 소켓 수 증가 시 성능 급락 | 소규모 레거시 서버 |
| **이벤트 다중화 (epoll)** | `epoll_wait()` | **$O(1)$ 활성 이벤트만 처리** | **C10K 문제 완벽 해결, 고효율** | **Nginx, Netty, Redis** |
| **진정한 비동기 (io_uring)** | `io_uring_enter()` | **커널-유저 링버퍼 제로 시스콜** | **시스템 콜 오버헤드 0%, 최고 성능** | **최신 Linux 고성능 스택** |
