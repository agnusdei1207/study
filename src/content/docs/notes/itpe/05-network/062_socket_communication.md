## Ⅰ. 소켓 통신(Socket Communication)의 개요

- 개념 : 운영체제 커널의 네트워크 통신 스택을 사용자 공간(User Space)의 애플리케이션이 추상화된 **파일 디스크립터(File Descriptor)** 형태로 제어하여 네트워크 엔드포인트 간 양방향 데이터 교환을 수행하는 **버클리 소켓(BSD Socket)** 기반 IPC 인터페이스.
- 배경 및 필요성 : 하위 네트워크 하드웨어(NIC) 및 복잡한 L3/L4 계층의 전송 세부 사항을 일일이 프로그래밍하지 않고, 표준 입출력 파일 API(`read()`, `write()`)와 유사한 직관적이고 표준화된 **네트워크 통신 추상화 계층** 필요.
- 핵심 목적 : 네트워크 5-Tuple 기반의 프로세스 식별 및 종단 간 통신, TCP/UDP 프로토콜 유연 선택, 대규모 동시 접속 클라이언트의 고속 데이터 송수신.

## Ⅱ. 소켓 통신의 핵심 아키텍처 및 동작 메커니즘

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [ TCP 기반 소켓 통신 라이프사이클 흐름 ]             │
│                                                                        │
│        [ Server ]                                   [ Client ]         │
│   socket()    : 소켓 파일 디스크립터 생성                               │
│       │                                                                │
│   bind()      : IP 주소 및 포트 바인딩                                 │
│       │                                                                │
│   listen()    : 수신 대기 큐(Backlog) 설정         socket()            │
│       │                                               │                │
│   accept()    : 클라이언트 연결 대기 (Blocking)        │                │
│       │ ◄────────── 3-Way Handshake ────────────── connect()          │
│       ├───────────────────────────────────────────────┤                │
│   [ 연결 수립: Client 소켓과 매핑된 신규 소켓 FD 반환 ]                │
│       │                                               │                │
│   read() / write() ◄── 양방향 전이중 데이터 교환 ──►  read() / write() │
│       │                                               │                │
│   close()     : 세션 종료 (4-Way Handshake) ──────►   close()          │
└────────────────────────────────────────────────────────────────────────┘
```

- **네트워크 소켓의 식별 (5-Tuple)** : 프로토콜(Protocol), 출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port의 5가지 조합으로 단일 커널 소켓을 고유 식별.
- 서버측 2단계 소켓 분리 구조 :
  - **Listening Socket** : 클라이언트의 최초 접속 요청(`SYN`)만을 수신하고 대기열(`Backlog Queue`)을 관리하는 대표 소켓.
  - **Connected Socket** : Handshake가 완료된 특정 클라이언트와 1:1로 매핑되어 실제 데이터 입출력(`read/write`)을 전담하는 데이터 소켓.

## Ⅲ. 소켓 I/O 멀티플렉싱 모델 세부 비교 분석

| 구분 | 블로킹 I/O (Blocking) | Non-Blocking (Polling) | I/O 다중화 (select/poll) | I/O 다중화 (epoll/kqueue) | 비동기 I/O (io_uring/AIO) |
|---|---|---|---|---|---|
| 동작 방식 | 호출 시 데이터 올 때까지 스레드 정지 | 데이터 없으면 즉시 에러 반환, 무한 루프 | 등록된 FD 전체를 순회하며 변경 확인 | 이벤트 등록된 FD만 커널이 통지 | 커널이 I/O 완료 후 버퍼 통째 통지 |
| 시간 복잡도 | - | - | $O(N)$ (전체 FD 순회) | $O(1)$ (활성 이벤트만) | $O(1)$ (커널 링버퍼 직접) |
| FD 수 제한 | 스레드 생성 한계 | CPU 점유율 폭증 | select는 1024개 한계 | 사실상 무제한 (수십만 개) | 사실상 무제한 |
| 동작 아키텍처 | 1 연결당 1 스레드 | 바쁜 대기 (Busy Wait) | 멀티플렉싱 초기 모델 | 리눅스 epoll (레벨/엣지 트리거)| 제로 카피 커널 링버퍼 |
| 적합한 환경 | 단순 클라이언트 프로그램 | 특수 임베디드 장치 | 동시접속 1,000 이하 | C10K/C1000K 고성능 서버 | 초고속 NVMe/초저지연 네트워크 |

- **Reactor 패턴 (epoll)** : 단일 또는 소수의 이벤트 루프 스레드가 수만 개의 비차단 소켓을 감시하다가, 데이터가 도착한 소켓에 대해서만 핸들러를 디스패치하여 컨텍스트 스위칭 최소화 (Nginx, Netty, Node.js의 핵심).

## Ⅳ. 소켓 통신의 주요 한계점 및 해결 방안

- C10K / C1000K 문제 (대규모 동시 접속 시 스레드 및 메모리 고갈) :
  - 한계점 : 전통적 블로킹 방식에서 접속자당 1개의 OS 스레드를 생성할 경우 스레드 스택 메모리 고갈 및 CPU 컨텍스트 스위칭 오버헤드로 서버 다운.
  - 해결 방안 : `epoll`(Linux) 또는 `kqueue`(BSD) 기반 비동기 Non-blocking 이벤트 드리븐 아키텍처 도입 및 Go 고루틴(Goroutine), Java 가상 스레드(Virtual Thread) 적용.
- TCP 송수신 버퍼 오버플로우 및 패킷 지연 (Head-of-Line Blocking) :
  - 한계점 : 스트림 기반 TCP 소켓 특성상 단 하나의 패킷만 유실되어도 후속 패킷이 수신 버퍼에서 대기하여 애플리케이션 지연 급증.
  - 해결 방안 : 메시지 독립성을 보장하는 UDP 소켓 기반의 사용자 정의 프로토콜 또는 QUIC(HTTP/3) 소켓 스택으로 전환.

## Ⅴ. 소켓 통신 적용 및 발전을 위한 기술사적 제언

- 차세대 커널 바이패스(Kernel Bypass) 기술 도입 : 커널 네트워크 스택과 컨텍스트 스위칭 오버헤드를 완전 제거하기 위해, 유저 공간에서 NIC 메모리에 직접 접근하는 DPDK 및 eBPF XDP(eXpress Data Path) 소켓 적극 활용.
- 리눅스 최신 io_uring 기반 비동기 아키텍처 채택 : 시스템 콜 횟수 자체를 0에 수렴시키는 공유 메모리 링 버퍼 기반 io_uring 비동기 I/O를 네트워크 백엔드 엔진에 도입하여 초당 IOPS 극대화.
- 네트워크 소켓 레벨의 종단 암호화(mTLS) 의무화 : 평문 소켓 통신을 배제하고, 소켓 생성 직후 OpenSSL/BoringSSL 엔진을 바인딩하여 전송 계층 전 구간의 도청 및 데이터 변조 원천 차단.
