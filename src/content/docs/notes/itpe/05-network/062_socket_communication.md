## 연관 키워드

- 소켓(Socket), 버클리 소켓(BSD Socket), 파일 디스크립터(File Descriptor), 5-Tuple
- 리스닝 소켓(Listening Socket), 연결 소켓(Connected Socket), 3-Way Handshake, 4-Way Handshake
- 블로킹 I/O, select/poll, epoll, io_uring, Reactor 패턴
- C10K 문제, Head-of-Line Blocking, DPDK(Data Plane Development Kit), mTLS(mutual TLS)

## Ⅰ. 소켓 통신의 개요

- 핵심 요약 : 네트워크 통신을 파일 입출력과 같은 표준 인터페이스로 추상화한 프로세스 간 통신 API.
- 개념 : 운영체제 커널이 제공하는 네트워크 종단점을 **파일 디스크립터**(커널 자원을 가리키는 번호, File Descriptor)로 다루어 양방향 데이터 교환을 수행하는 **소켓**(네트워크 통신의 종단점 인터페이스, Socket)이며, 버클리 소켓(BSD Socket) 계열이 사실상의 표준.
- 배경 및 필요성 : 애플리케이션이 네트워크 카드와 전송 계층의 세부 동작을 직접 제어하는 대신, 파일과 같은 균일한 입출력 방식으로 네트워크를 다루는 추상화 계층이 필요.
- 주요 목적 : 연결 식별과 수립·종료 절차의 표준화, 전송 계층 프로토콜의 용도별 선택, 다수 클라이언트의 동시 처리 지원.

## Ⅱ. 소켓 통신의 특징 및 장점

- 핵심 요약 : 파일 추상화, 5-Tuple 식별, 이중 소켓 구조가 구현 단순성과 대규모 연결 처리를 함께 지원.

1. 파일 추상화 : 소켓을 파일 디스크립터로 다루어 read()·write()로 입출력 → 파일 입출력 코드와 동일한 방식으로 네트워크 프로그래밍 가능.
2. 5-Tuple 식별 : 프로토콜·출발지 IP·출발지 포트·목적지 IP·목적지 포트의 조합으로 연결을 고유 식별 → 동일 서버 포트에서 다수 클라이언트 구분.
3. 이중 소켓 구조 : **리스닝 소켓**(접속 요청만 수신하는 소켓, Listening Socket)과 연결마다 생성되는 **연결 소켓**(데이터 입출력을 전담하는 소켓, Connected Socket)의 분리 → 접속 수락과 데이터 처리의 병행 수행.
4. 전송 계층 선택 : 신뢰성 지향 TCP(Transmission Control Protocol)와 지연·오버헤드 효율 지향 UDP(User Datagram Protocol)를 용도별 선택 → 서비스 특성에 맞는 전송 품질 확보.

## Ⅲ. 소켓 통신의 구조 (흐름)

- 핵심 요약 : 서버의 소켓 생성부터 연결 수립, 데이터 교환, 종료까지 이어지는 소켓 생애주기 구조.
- 3-Way Handshake : SYN(Synchronize)·SYN-ACK·ACK(Acknowledgment) 세 단계로 연결을 수립하는 TCP 절차.
- 4-Way Handshake : 양방향 각각 FIN과 ACK를 주고받아 연결을 종료하는 TCP 절차.

```text
[ 서버 소켓 생애주기 ]

socket (소켓 생성)
    ↓
bind (주소 · 포트 지정)
    ↓
listen (대기 상태 전환)
    ↓
accept (연결 수락)
    ↓
read / write (데이터 교환)
    ↓
close (4-Way Handshake로 종료)
```

```text
[ 3-Way Handshake 연결 수립 ]

SYN (연결 요청)
    ↓
SYN-ACK (요청 수락 · 응답)
    ↓
ACK (확인)
    ↓
연결 성립 (양방향 전송 개시)
```

## Ⅳ. 소켓 I/O 모델의 비교

- 핵심 요약 : 연결 수가 적으면 블로킹 I/O로 충분하지만, 수천 이상의 동시 연결은 이벤트 기반 I/O로의 전환이 필요.

| 비교 축 | 블로킹 I/O | select / poll | epoll · kqueue | io_uring |
| --- | --- | --- | --- | --- |
| 동작 방식 | 데이터 도착까지 스레드 대기 | 등록한 디스크립터 전체를 순회 감시 | 이벤트 등록 디스크립터만 커널이 통지 | 커널이 완료 후 결과를 일괄 통지 |
| 감시 비용 | 연결마다 스레드 필요 | 디스크립터 수에 비례 | 활성 이벤트에 비례 | 커널 링버퍼로 직접 처리 |
| 연결 수 확장성 | 스레드 생성 한계 | select는 상한 존재 | 수만 연결까지 확장 | 매우 높음 |
| 적합한 환경 | 단순 클라이언트 | 소규모 서버 | 만 단위 동시 접속 서버 | 초고속 저지연 I/O |

- **Reactor 패턴**(이벤트 루프가 준비된 소켓에만 핸들러를 호출하는 설계, Reactor Pattern) : 소수의 이벤트 루프 스레드가 다수의 비차단 소켓을 감시하는 epoll 기반 서버의 전형 구조.
- 선택 기준 : 연결 수백 이하의 단순 서비스는 블로킹 I/O, 수천 이상의 동시 접속은 epoll·kqueue 기반 이벤트 처리, 초저지연 대량 I/O는 io_uring을 검토.

```text
[ I/O 모델 선택 흐름 ]

연결 수 적음 (수백 이하)
    ↓
블로킹 I/O (연결당 스레드)
    ↓
연결 수 많음 (수천 이상)
    ↓
이벤트 기반 I/O (epoll · kqueue)
```

## Ⅴ. 소켓 통신의 한계와 방안

- 핵심 요약 : 대규모 동시 접속에서의 자원 고갈과 TCP 스트림의 지연 전이가 핵심 한계이며, 이벤트 기반 구조와 전송 방식 전환으로 일대일 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| **C10K 문제**(동시 접속 만 단위에서 성능이 급락하는 문제, C10K Problem) | 접속마다 스레드를 만들면 스택 메모리와 문맥 전환 비용이 커져 부하 급증 | epoll·kqueue 기반 비동기 논블로킹 구조, 경량 스레드·코루틴 활용 | 연결당 메모리, 문맥 전환 횟수 |
| **Head-of-Line Blocking**(앞선 데이터의 지연이 뒤 데이터로 전이되는 현상) | TCP 스트림 특성상 한 패킷 유실이 수신 버퍼의 후속 데이터 지연으로 확산 | 메시지 단위 독립성을 갖는 UDP 기반 전송 프로토콜(QUIC) 채택 | 수신 지연, 재전송 대기 시간 |

## Ⅵ. 소켓 통신 적용 및 발전을 위한 기술사적 제언

- 핵심 요약 : 커널 우회의 구간별 적용, 비동기 I/O 인터페이스 도입, 소켓 단계 암호화 표준화로 성능과 보안을 함께 확보하는 것.

1. 고성능 네트워크 백엔드를 만드는 개발 조직은 트래픽 처리 구간에 한해 DPDK(Data Plane Development Kit) 같은 커널 우회 기술을 적용해, 커널 스택 지연과 CPU 낭비를 줄이는 방안을 검토해야 한다.
2. 리눅스 기반 서버 팀은 io_uring 같은 비동기 I/O 인터페이스를 도입 검토해, 시스템 콜 횟수 감소와 처리량 향상의 실측 근거를 마련해야 한다.
3. 운영 조직은 평문 소켓 통신을 기본 정책에서 배제하고, 상호 인증이 가능한 mTLS(mutual TLS)를 소켓 생성 단계에서 적용하도록 표준을 정비해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 소켓은 파일 추상화로 네트워크 통신을 단순화한 기본 인터페이스이며, 연결 규모에 맞는 I/O 모델 선택이 성능의 핵심.
- 대규모 동시 접속은 이벤트 기반과 커널 우회 기술로 해결하는 추세이며, 암호화는 소켓 단계의 기본값으로 자리 잡는 방향.
