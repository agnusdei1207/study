## 연관 키워드

- 소켓(Socket), 버클리 소켓(BSD Socket), 파일 디스크립터(File Descriptor), 5-Tuple

## Ⅰ. 소켓 통신(Socket Communication)의 개요

- 핵심 요약 : 네트워크 통신을 파일 디스크립터 기반의 표준 입출력 인터페이스로 추상화한 프로세스 간 통신 API.
- 개념 : 운영체제 커널의 네트워크 스택을 **파일 디스크립터** (File Descriptor) 형태로 다루어, 네트워크 엔드포인트 사이에서 양방향 데이터 교환을 수행하는 **소켓** (Socket) 인터페이스이며, 버클리 소켓(BSD Socket)이 그 표준 계열임.
- 배경 및 필요성 : 애플리케이션이 NIC(Network Interface Card)와 L3·L4 전송 세부 사항을 직접 다루지 않고, read()·write()와 같은 파일 API로 네트워크를 다룰 수 있는 추상화 계층이 필요함.
- 주요 목적 : 5-Tuple로 연결을 식별하고, TCP와 UDP(User Datagram Protocol)를 용도에 맞게 선택하며, 다수 클라이언트와의 고속 송수신을 처리하는 것.

## Ⅱ. 소켓 통신의 특징 및 장점

- 핵심 요약 : 파일과 같은 추상화와 두 단계 소켓 분리가 구현의 단순성과 다중 연결 처리를 함께 제공함.

1. 파일 추상화 : 소켓을 파일 디스크립터로 다뤄 read()·write()로 입출력 → 기존 파일 I/O 코드와 같은 방식으로 작성 가능.
2. 5-Tuple 식별 : 프로토콜, 출발지 IP·포트, 목적지 IP·포트의 조합으로 연결을 고유하게 식별 → 같은 서버 포트에서 다수 연결을 구분.
3. 이중 소켓 구조 : **리스닝 소켓** (Listening Socket)이 접속 요청만 받고, 연결마다 만들어진 **연결 소켓** (Connected Socket)이 데이터 입출력을 전담 → 접속 수락과 데이터 처리가 분리되어 병행 처리가 쉬워짐.

## Ⅲ. 소켓 통신의 구조 (흐름)

- 핵심 요약 : 서버가 소켓을 생성하고 바인딩, 대기 상태로 전환한 뒤, 3-Way Handshake로 연결이 성립하면 연결 소켓으로 데이터를 주고받고, 4-Way Handshake로 종료하는 생애주기.
- **3-Way Handshake** : SYN(Synchronize), SYN-ACK, ACK(Acknowledgment) 세 단계로 연결을 수립하는 TCP 절차.
- **4-Way Handshake** : 양방향 각각 FIN과 ACK를 주고받아 연결을 종료하는 TCP 절차.

```text
서버: socket → bind → listen
        ↓
서버: accept() 대기
        ↑ 3-Way Handshake
클라이언트: socket → connect()
        ↓
연결 소켓으로 read() / write()
        ↓
close() (4-Way Handshake로 종료)
```

## Ⅳ. 소켓 I/O 모델의 비교

- 핵심 요약 : 연결 수가 적으면 블로킹 I/O로 충분하지만, 연결 수가 수천 이상이면 이벤트 기반 I/O로 전환해야 함.

| 비교 축 | 블로킹 I/O | select / poll | epoll · kqueue | 비동기 I/O (io_uring) |
| --- | --- | --- | --- | --- |
| 동작 방식 | 호출 시 데이터가 올 때까지 스레드가 대기 | 등록한 파일 디스크립터 전체를 순회하며 변화 확인 | 이벤트를 등록한 디스크립터만 커널이 통지 | 커널이 I/O 완료 후 결과를 통지 |
| 감시 비용 | 연결마다 스레드 필요 | 디스크립터 수에 비례 (O(N)) | 활성 이벤트에 비례 (O(1)에 가까움) | 커널 링버퍼로 직접 처리 |
| 연결 수 한계 | 스레드 생성 한계 | select는 기본 1,024개 제한 | 매우 많은 연결까지 확장 | 매우 높음 |
| 적합한 환경 | 단순 클라이언트 프로그램 | 소규모 서버 | 만 단위 동시 접속 서버 | 초고속 저지연 I/O |

- **Reactor 패턴** : 소수의 이벤트 루프 스레드가 많은 비차단 소켓을 감시하다가, 데이터가 도착한 소켓에만 핸들러를 호출하는 구조로, epoll 기반 서버의 전형적 설계.

```text
연결 수 적음 (수백 이하)
        ↓
블로킹 I/O (연결당 스레드)
        ↓
연결 수 많음 (수천 이상)
        ↓
이벤트 기반 I/O (epoll · kqueue)
```

## Ⅴ. 소켓 통신의 한계와 방안

- 핵심 요약 : 대규모 동시 접속에서 스레드 자원이 고갈되고, TCP 스트림 특성으로 패킷 손실이 후속 데이터 지연으로 번지는 두 한계가 핵심이며, 이벤트 기반 모델과 전송 계층 전환으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| C10K 문제 (대규모 동시 접속) | 접속마다 OS 스레드를 만들면 스택 메모리와 컨텍스트 스위칭 비용이 커져 서버 부하 급증 | epoll·kqueue 기반 비동기 논블로킹 구조, 고루틴이나 가상 스레드 같은 경량 동시성 | 연결당 메모리, 컨텍스트 스위칭 횟수 |
| TCP의 Head-of-Line Blocking | 스트림 특성상 한 패킷이 유실되면 뒤따르는 데이터가 수신 버퍼에서 대기 | 메시지 단위 독립성을 보장하는 UDP 기반 사용자 정의 프로토콜, UDP 기반 전송 프로토콜인 QUIC 사용 | 수신 지연, 재전송 대기 시간 |

## Ⅵ. 소켓 통신 적용 및 발전을 위한 기술사적 제언

- 핵심 요약 : 트래픽 구간의 DPDK 커널 우회 적용, io_uring 도입 검토, 소켓 단계의 mTLS 표준화로 성능과 보안을 함께 확보하는 것.

1. 고성능 네트워크 백엔드를 만드는 팀은 트래픽 처리 구간에 한해 DPDK(Data Plane Development Kit) 같은 커널 우회 기술을 적용해, 커널 네트워크 스택의 지연과 CPU 낭비를 줄여야 한다.
2. 리눅스 기반 서버 팀은 io_uring 같은 비동기 I/O 인터페이스를 도입 검토하여, 시스템 콜 횟수를 줄이고 처리량을 높이는 방향을 택해야 한다.
3. 운영 조직은 평문 소켓 통신을 기본 정책에서 배제하고, 상호 인증이 가능한 mTLS(mutual TLS)를 소켓 생성 단계에서 적용하도록 표준화해야 한다.

## Ⅶ. 결론

- 핵심 요약 : 소켓은 파일 추상화로 네트워크 통신을 단순화한 기본 인터페이스이며, 연결 규모에 맞는 I/O 모델 선택이 성능의 핵심.
- 시사점 : 대규모 동시 접속은 이벤트 기반과 커널 우회 기술로 해결하는 추세이며, 보안은 소켓 단계에서 암호화를 기본값으로 두는 방향으로 나아간다.
