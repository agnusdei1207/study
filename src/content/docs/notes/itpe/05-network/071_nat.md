## 지식 로드맵 내 현재 위치

네트워크 → IP 전달 및 주소 변환 → **NAT(Network Address Translation)**

## 30초 인출

- 본질: **NAT(Network Address Translation)** : 사설 IP(Private IP) 주소를 사용하는 내부 호스트가 공인 인터넷과 통신할 수 있도록 라우터/방화벽 경계에서 패킷 헤더의 IP 주소와 전송 계층 포트 번호를 동적으로 변환하는 네트워크 기술
- 메커니즘: 내부 출발지 사설 IP/Port를 외부 공인 IP/Port로 변환(SNAT/NAPT)하고 커널 변환 테이블에 5-Tuple 상태를 기록한 후, 인터넷으로부터 수신된 응답 패킷을 역변환하여 내부 원래 단말로 포워딩
- 통찰: IPv4 주소 고갈 완화 이면에 종단 간 연결성 훼손과 IPsec AH 검증 실패 및 대칭형 NAT의 P2P 연결 차단 한계 극복을 위해 NAT-T(UDP 4500) 및 STUN/TURN/ICE 프레임워크 연계 필수

<details>
<summary>핵심 용어</summary>

- **NAPT / PAT** : 1개의 공인 IP 주소에 수천 개의 L4 포트 번호(1024~65535)를 결합하여 다수의 사설 IP 호스트를 인터넷에 동시 접속시키는 주소/포트 다중 변환 기술
- **SNAT (Source NAT)** : 내부 사설망에서 외부 인터넷으로 나갈 때 출발지 주소를 공인 IP로 변환하는 아웃바운드 NAT
- **DNAT (Destination NAT / 포트포워딩)** : 외부 인터넷에서 내부 사설망의 특정 서버로 접속할 수 있도록 목적지 주소 및 포트를 내부 사설 IP로 변환하는 인바운드 NAT
- **NAT-T (NAT Traversal, RFC 3948)** : IPsec ESP 패킷을 UDP 포트 4500번으로 재캡슐화하여 포트 번호가 없는 ESP 패킷도 NAPT 게이트웨이를 정상 통과하도록 지원하는 기술
- **ICE (Interactive Connectivity Establishment)** : WebRTC 등 P2P 통신에서 STUN(직접 연결 탐색)과 TURN(중계 서버)을 결합하여 최적의 통신 경로를 동적 확립하는 프레임워크 (RFC 8445)

</details>

## 2~4교시 25점 답안

## Ⅰ. NAT의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 사설 네트워크(RFC 1918)에 할당된 비공인 사설 IP 주소를 공인 인터넷 상에서 라우팅 가능한 공인 IP 주소 및 포트 번호로 상호 변환해주는 네트워크 계층 변환 기술 |
| 목적 | 전 세계적인 IPv4 공인 주소 고갈 지연, 내부 사설 네트워크 토폴로지 은닉을 통한 보안성 강화, 통신사 회선 비용 절감 |

## Ⅱ. NAT의 특징 및 4대 핵심 변환 유형

| 변환 유형 | 매핑 방식 | 핵심 동작 및 활용 분야 |
|---|---|---|
| **정적 NAT (Static NAT)** | 공인 IP 1개 ↔ 사설 IP 1개 (1:1 고정) | 외부에서 직접 접근해야 하는 내부 사설 웹/메일 서버 공개 |
| **동적 NAT (Dynamic NAT)** | 공인 IP $N$개 ↔ 사설 IP $M$개 ($N:M$ 풀) | 사전 등록된 공인 IP 풀에서 가용한 주소를 선착순 동적 대여 |
| **NAPT / PAT (포트 다중화)**| **공인 IP 1개 ↔ 수천 개 사설 IP ($1:N$)** | **공인 IP 1개와 고유 L4 포트를 결합하여 전사 사내 PC 인터넷 동시 공유** |
| **DNAT (포트 포워딩)** | 외부 공인 포트 ──► 내부 사설 IP:포트 | 외부 특정 포트 요청을 내부 특정 사설 서버의 서비스 포트로 다이렉트 분기 |

## Ⅲ. NAT/NAPT 변환 아키텍처 및 5-Tuple 세션 테이블 매핑 프로세스

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   [ NAPT 주소/포트 변환 및 세션 테이블 동작 ]          │
│                                                                        │
│   [내부 사설 호스트]                     [NAPT 라우터 / 방화벽]         │
│   (192.168.1.10:5000)                   (공인 IP: 203.0.113.1)         │
│          │                                         │                   │
│          ▼ 1. 아웃바운드 요청 패킷 송출             │                   │
│          │  [Src: 192.168.1.10:5000 | Dst: 8.8.8.8:80]                 │
│          ├────────────────────────────────────────►│                   │
│          │                                         │ 2. NAT 테이블 기록 │
│          │                                         │ [192.168.1.10:5000│
│          │                                         │  <-> 203.0.113.1: │
│          │                                         │             40001]│
│          │                                         │ 3. 패킷 변환 송출  │
│          │                                         ▼ [Src: 203.0.113.1 │
│          │                                         │   :40001 | 8.8.8.8│
│          │                                         │        :80]       │
│          │                                         ├──────────► [인터넷]│
│          │                                         │                   │
│          │                                         │ 4. 응답 패킷 수신 │
│          │                                         │ [Dst: 203.0.113.1 │
│          │                                         │   :40001]         │
│          │                                         │◄──────────────────┤
│          │ 5. NAT 역변환 후 내부 전달               │                   │
│          │    [Dst: 192.168.1.10:5000]             │                   │
│          │◄────────────────────────────────────────┤                   │
└────────────────────────────────────────────────────────────────────────┘
```

| 처리 단계 | 주관 요소 | 세부 처리 메커니즘 |
|---|---|---|
| **1. 인입 패킷 파싱** | NAT 검사 엔진 | 내부에서 외부로 나가는 패킷의 5-Tuple(출발지/목적지 IP, Port, 프로토콜) 추출 |
| **2. 세션 매핑 테이블 등록**| 커널 상태 추적기 | 출발지 사설 IP/Port를 가용 공인 Port(예: 40001)에 1:1 바인딩하고 타이머 시작 |
| **3. 헤더 수정 및 체크섬 재계산**| 패킷 변환 모듈 | IP 헤더의 Source IP와 TCP/UDP 헤더의 Source Port를 변경 후 L3/L4 체크섬 재연산 송출 |
| **4. 인바운드 역변환** | 커널 상태 추적기 | 외부에서 유입된 패킷의 목적지 Port(40001)를 테이블에서 역조회하여 사설 호스트로 포워딩 |

## Ⅳ. Static NAT vs Dynamic NAT vs NAPT(PAT) 비교

| 비교 항목 | Static NAT | Dynamic NAT | NAPT (Port Address Translation) |
|---|---|---|---|
| **매핑 비율** | 1 : 1 고정 매핑 | M : N 풀(Pool) 매핑 | **1 : N (또는 M : N) 대규모 포트 다중화** |
| **공인 IP 소모량** | 내부 호스트 수만큼 공인 IP 필요 | 동시 접속 호스트 수만큼 필요 | **단 1개의 공인 IP로 수천 대 수용** |
| **외부 인바운드 접근**| 외부에서 내부로 상시 직접 접근 가능 | 매핑 유지 시간에만 제한적 접근 가능 | 기본 불가 (포트포워딩 설정 시에만 가능) |
| **포트 변환 여부** | IP 주소만 변환 (포트 유지) | IP 주소만 변환 (포트 유지) | **IP 주소와 L4 전송 포트 동시 변환** |
| **주요 활용 처** | 사내 DMZ 공개 웹/DB 서버 | 특정 VIP 사용자 그룹 전용 회선 | **일반 가정용 공유기, 전사 사내망 인터넷** |

## Ⅴ. NAT 운영 시 핵심 엔지니어링 한계와 방안

| 한계 | 방안 |
|---|---|
| IPsec VPN 전송 시 AH(Authentication Header)는 변조 방지를 위해 외부 IP 헤더까지 해시 무결성을 검증하므로, 중간 NAT 장비가 IP 주소를 변경하는 즉시 패킷 위조로 판정되어 복호화 실패 전량 폐기 | IPsec IKE 협상 단계에서 벤더 ID를 통해 NAT 장비 존재를 자동 감지하고, 무결성 검증 범위에서 외부 IP를 제외하는 ESP 터널 모드를 사용하며, 암호화된 ESP 패킷을 UDP 포트 4500번으로 재캡슐화하여 통과시키는 NAT-T(RFC 3948) 표준 적용 |
| FTP, SIP(VoIP) 등 애플리케이션 페이로드 내부에 직접 클라이언트의 사설 IP 주소와 포트 정보가 텍스트로 기록되는 L7 프로토콜의 경우, L3/L4 헤더만 바꾸는 일반 NAT 통과 시 상대방이 사설 IP로 응답을 시도하여 통신 두절 | 방화벽/라우터에서 L7 애플리케이션 페이로드 내부를 심층 패킷 검사(DPI)하여 페이로드 속 사설 IP/포트 문자열까지 공인 주소로 동적 치환해주는 ALG(Application Level Gateway) 모듈 활성화 |
| WebRTC 화상회의, P2P 파일 공유 환경에서 양단 호스트가 서로 다른 대칭형 NAT(Symmetric NAT: 목적지마다 공인 포트가 무작위 변경) 뒤에 위치할 경우 사설 IP 상호 도달이 불가능하여 직접 P2P 홀펀칭 100% 실패 | 클라이언트의 공인 반사 IP를 확인하는 STUN(RFC 5389)을 1차 시도하고, 대칭형 NAT 감지 시 공인 릴레이 프록시 서버를 통해 트래픽을 완벽 중계하는 TURN(RFC 5766) 및 이를 지능적으로 폴백 제어하는 ICE(RFC 8445) 프레임워크 의무 구축 |

## Ⅵ. 도입/구축/운영 관점 제언

### 1. 실무 적용 가이드 및 핵심 고려사항
대규모 기업망 및 클라우드 VPC(가상 사설 클라우드) 아키텍처 설계 시, 아웃바운드 인터넷 트래픽은 고가용성 NAT 게이트웨이를 이중화 배치하여 단일 장애점을 방지하고, NAT 세션 테이블의 유휴 타임아웃(TCP 기본 1시간, UDP 30~60초)을 적정 수준으로 관리하여 장기 유휴 세션에 의한 커널 NAT 연결 추적 테이블(conntrack) 메모리 고갈 방지 권장

### 2. 아키텍처 및 상세 메커니즘
```text
┌────────────────────────────────────────────────────────────────────────┐
│               [ WebRTC P2P 통신을 위한 ICE / STUN / TURN 아키텍처 ]    │
│                                                                        │
│   [Peer A (NAT-A 뒤)]                                [Peer B (NAT-B 뒤)]│
│   (192.168.1.10)                                     (192.168.2.20)    │
│          │                                                  │          │
│          ├─────────► [STUN 서버 (공인 IP)] ◄────────────────┤          │
│          │           - 양단의 공인 반사 IP/Port 확인         │          │
│          │             (Candidate 정보 수집)                │          │
│          │                                                  │          │
│          ▼ 1차 시도: P2P 직접 홀펀칭 (Host / Srflx 경로)     ▼          │
│          ════════════════════════════════════════════════════          │
│          (대칭형 NAT로 인해 직접 통신 바인딩 실패 시!)                  │
│          │                                                  │          │
│          ▼ 2차 시도: TURN 릴레이 폴백 (Relayed Candidate)   ▼          │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │                     TURN 릴레이 중계 서버                      │   │
│   │  - 양단 트래픽을 UDP 3478번으로 전송받아 상호 중계 (100% 성공) │   │
│   └────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────┘
```

### 3. 기술 유형 및 비교 평가
| 구분 | STUN (RFC 5389) | TURN (RFC 5766) | ICE 프레임워크 (RFC 8445) |
|---|---|---|---|
| **동작 메커니즘** | 단말이 자신의 공인 매핑 주소를 질의 확인 | 공인 중계 서버를 경유하여 패킷 전달 | STUN과 TURN을 통합 제어 및 경로 탐색 |
| **P2P 직접 연결** | 직접 연결 가능 (홀펀칭 성공 시) | 간접 중계 (서버 대역폭 소모) | 직접 연결 우선 시도 후 실패 시 중계 |
| **대칭형 NAT 극복**| **대칭형 NAT 환경에서 직접 연결 불가** | **모든 종류의 NAT 완벽 극복 (100% 성공)**| **최적 경로를 스스로 판정하여 완벽 극복**|
| **서버 자원 부하** | 시그널링 시에만 미미한 부하 발생 | 전 미디어 스트림이 경유하므로 트래픽 과다 | 최적화된 직접 연결로 서버 트래픽 극소화 |
| **주요 적용 기술** | 단순 VoIP 단말 주소 탐색 | 방화벽 차단망 화상회의 중계 | WebRTC 화상/음성 통신 표준 |
