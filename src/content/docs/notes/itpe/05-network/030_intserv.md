## 30초 인출

- 본질: **IntServ(Integrated Services)** : 흐름별 자원 요청과 상태를 이용해 IP 네트워크에서 통합 서비스를 제공하는 QoS 모델
- 메커니즘: 송신자 **PATH** 전달 → 수신자 **RESV** 자원 요청 → 각 라우터가 수락 제어·상태 관리 → 예약된 흐름에 서비스 적용
- 통찰: 개별 애플리케이션 플로우 단위로 RSVP 시그널링을 통해 종단 간 라우터 전 경로에 실제 대역폭과 버퍼를 엄격하게 사전 예약하여 결정론적 품질(Hard QoS)을 제공하는 통합 서비스 아키텍처임.

<details>
<summary>핵심 용어</summary>

- **IntServ(Integrated Services)** : IP 네트워크에서 흐름별 자원 상태와 서비스 모델을 관리하는 QoS 구조
- **RSVP(Resource ReSerVation Protocol)** : 수신자가 자원 예약을 요청하고 라우터가 경로별 상태를 관리하도록 돕는 시그널링 프로토콜
- **PATH 메시지(PATH Message)** : 송신자가 트래픽 특성과 경로 상태 정보를 수신자 방향으로 전달하는 RSVP 메시지
- **RESV 메시지(RESV Message)** : 수신자가 선택한 서비스·자원 요청을 송신자 방향으로 전달하는 RSVP 메시지
- **수락 제어(Admission Control)** : 새 요청이 정책·자원 조건에 맞게 수용 가능한지 판단하는 기능
- **소프트 상태(Soft State)** : 주기적 갱신이 없으면 상태가 만료·해제되는 관리 방식
- **Guaranteed Service(보장 서비스)** : 규격된 트래픽과 자원 관리 조건에서 지연 상한 등 서비스 특성을 제공하는 모델
- **Controlled-Load Service(제어 부하 서비스)** : 혼잡이 적은 네트워크에 가까운 서비스 특성을 목표로 하는 모델

## 2~4교시 25점 답안

## Ⅰ. IntServ의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | 통신 경로 상의 모든 라우터가 RSVP 시그널링 프로토콜을 사용하여 개별 트래픽 플로우(Micro-flow)의 연결 상태를 유지하고 대역폭 자원을 사전에 예약하는 연결 지향적 통합 QoS 아키텍처 |
| 목적 | 음성 및 비디오 스트리밍과 같은 실시간 멀티미디어 서비스에 대해 대역폭 고갈 없는 절대적인 지연 시간 및 처리율 보장 |

## Ⅱ. IntServ의 특징

| 특징 | 상세 내용 |
|---|---|
| 플로우 단위 관리 | 출발지/목적지 IP, 포트 번호, 프로토콜로 식별되는 개별 플로우마다 독립적인 자원 예약 수행 |
| RSVP 시그널링 기반 | 수신측 중심(Receiver-driven)으로 RSVP RESV 메시지를 송신측으로 역방향 전송하여 자원 확정 |
| 소프트 상태(Soft State)| 자원 예약 유지를 위해 주기적으로 상태 갱신 메시지를 교환하며, 미도착 시 타이머 만료로 자동 해제 |
| 호 수락 제어(Admission)| 라우터가 현재 가용 자원을 확인하여 신규 플로우 요청을 수락(Accept)하거나 거부(Reject) 통제 |

## Ⅲ. IntServ의 체계·프로세스

**RSVP 기반 자원 예약 시그널링 및 라우터 패킷 제어 흐름**

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        [ IntServ RSVP 시그널링 흐름 ]                  │
│                                                                        │
│   [ 송신측 호스트 ]          [ 라우터 1 ]          [ 라우터 2 ]        [ 수신측 호스트 ]│
│          │                        │                    │                     │  │
│          ├─── PATH 메시지 송신 ──►│                    │                     │  │
│          │    (Tspec: 트래픽 사양)├──── PATH 메시지 ──►│                     │  │
│          │                        │                    ├─── PATH 메시지 ────►│  │
│          │                        │                    │   (경로 정보 기록)  │  │
│          │                        │                    │                     │  │
│          │                        │                    │◄── RESV 메시지 송신 ┤  │
│          │                        │                    │    (Rspec: 자원예약)│  │
│          │                        │◄─── RESV 메시지 ───┤ [수락 제어 CAC 통과]│  │
│          │                        │   [수락 제어 통과] │ (대역폭/버퍼 예약)  │  │
│          │◄── RESV 전달 완료 ─────┤                    │                     │  │
│          │   (예약 성공 확정)     │                    │                     │  │
│          │                        │                    │                     │  │
│          ══════ QoS 보장 데이터 패킷 스트림 전송 ════════════════════════════►  │
└────────────────────────────────────────────────────────────────────────┘
```

| 프로토콜 엔터티 | 핵심 역할 및 기능 |
|---|---|
| **RSVP PATH 메시지** | 송신자가 수신자 방향으로 전송하며 라우터들의 역방향 경로(Reverse Path)를 기록하고 트래픽 특성(Tspec) 전달 |
| **RSVP RESV 메시지** | 수신자가 PATH 역경로를 따라 송신자 방향으로 보내며 실제 대역폭과 지연 사양(Rspec)의 예약을 요청 |
| **수락 제어 (CAC)** | 경로 상 각 라우터가 자신의 가용 대역폭과 버퍼를 검사하여 신규 예약을 허용할지 거절할지 결정 |
| **패킷 스케줄러** | 승인된 플로우의 패킷이 계약된 QoS를 만족하도록 WFQ 등의 고급 스케줄링으로 서비스 제공 |

## Ⅳ. IntServ의 종류·비교

| 비교 항목 | 보장 서비스 (Guaranteed Service) | 부하 제어 서비스 (Controlled-Load) |
|---|---|---|
| **표준 RFC** | RFC 2212 | RFC 2211 |
| **지연 보장 수준** | **수학적으로 계산된 엄격한 최대 지연 보장** | 망이 한가할 때(Unloaded)의 지연 품질 유지 |
| **패킷 손실률** | 큐 오버플로로 인한 **패킷 손실 0% 보장** | 극소수 패킷 손실 허용 (Best-Effort보다 우수) |
| **큐잉 알고리즘** | WFQ 등 가상 마감시간 기반 정밀 스케줄링 | 일반 가중 라운드로빈(WRR) 등 비교적 단순 큐잉 |
| **주요 적용 분야** | 원격 의료 수술, 산업용 실시간 원격 제어 | 일반 인터넷 음성 통화(VoIP), 적응형 비디오 스트리밍 |

## Ⅴ. IntServ의 한계와 방안

| 한계 | 방안 |
|---|---|
| 수백만 개 개별 플로우마다 라우터 메모리에 소프트 상태(Soft State)를 유지해야 하므로 인터넷 백본 코어 라우터에서 심각한 상태 폭증(State Explosion) 및 확장성 붕괴 | 코어망에는 상태를 유지하지 않는 DiffServ를 적용하고, 가입자망/에지 구간에만 IntServ를 적용하는 IntServ-over-DiffServ 연계 아키텍처 수립 |
| RSVP 시그널링 메시지 자체의 주기적 전송 오버헤드와 경로 상 모든 라우터가 RSVP를 지원해야만 E2E 대역폭 예약이 가능한 올-오어-낫싱(All-or-Nothing) 구조 | RSVP-TE(Traffic Engineering)를 활용한 MPLS 레이블 스위칭 경로(LSP) 집약 터널링 및 BFD 고속 장애 감지 결합 |

## Ⅵ. 도입/구축/운영 관점 제언

### 1. 실무 적용 가이드 및 핵심 고려사항
인터넷 백본망에는 IntServ 단독 배치가 불가능하므로, 엔터프라이즈 사내망(LAN) 경계 라우터에서 단말의 RSVP 예약 요청을 수신하여 DiffServ DSCP 클래스로 변환 매핑하고, 코어망은 MPLS-TE 터널로 집약 전송하는 복합 QoS 설계를 표준으로 채택.

### 2. 아키텍처 및 상세 메커니즘
```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ IntServ over DiffServ 연계 아키텍처 ]                                │
│                                                                        │
│   [ 가입자 영역 : IntServ ]       [ 백본 코어 영역 : DiffServ / MPLS ]  │
│                                                                        │
│   단말 A ──(RSVP)──► [ Edge Router ] ══════════════════ [ Core Router ]│
│                      (미들웨어 매핑)                     (단순 PHB 포워딩)│
│                      - RSVP 세션 인입                    - 플로우 상태 없음 │
│                      - 가용 대역폭 확인                  - DSCP 기반 큐잉  │
│                      - DSCP = EF 마킹 ─────────────────►                 │
│   단말 B ──(RSVP)──►                                                   │
└────────────────────────────────────────────────────────────────────────┘
```

### 3. 기술 유형 및 비교 평가
| 지표 | IntServ (통합 모델) | IntServ over DiffServ (복합 모델) |
|---|---|---|
| **백본 라우터 부하** | 극심 (플로우당 상태 유지로 CPU/메모리 다운) | 없음 (단순 집약 클래스 처리) |
| **E2E 엄격 보장** | 전 구간 완벽 보장 | 경계 구간 엄격 + 코어 구간 높은 확률 보장 |
| **구현 경제성** | 모든 망 장비 교체 필요로 구축 불가 | 기존 백본 인프라 그대로 활용 가능 |
