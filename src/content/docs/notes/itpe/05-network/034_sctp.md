## 연관 키워드

- SCTP(Stream Control Transmission Protocol), 결합(Association), 청크(Chunk)
- 멀티호밍, 멀티스트리밍, 상태 쿠키(State Cookie), 4-Way 핸드셰이크
- CRC-32c, PR-SCTP, SIGTRAN, 헤드오브라인 블로킹

## Ⅰ. SCTP의 개요

- 핵심 요약 : 신뢰성과 메시지 경계를 함께 갖추고 다중 경로·다중 스트림을 지원하는 전송 계층 프로토콜.
- 개념 : TCP(Transmission Control Protocol)의 신뢰성과 UDP(User Datagram Protocol)의 메시지 지향성을 결합하고, 하나의 세션에 복수의 IP 경로와 복수의 스트림을 두는 **전송 계층** 프로토콜인 **SCTP** (Stream Control Transmission Protocol, RFC 4960).
- 배경 및 필요성 : 통신 사업자망의 SS7(Signaling System No. 7) 호 신호를 IP 망에서 무손실로 전송하는 SIGTRAN(Signaling Transport) 요구에서 출발함. 단일 경로와 바이트 스트림에 의존하는 TCP는 회선 단절에 취약하고 손실 하나가 전송 전체를 막는 한계가 있었음.
- 주요 목적 : 무중단 경로 전환과 스트림 단위의 지연 격리를 구현하고, 연결 설정 단계의 자원 고갈 공격을 방어.

## Ⅱ. SCTP의 특징 및 장점

- 핵심 요약 : 다중 경로, 독립 스트림, 메시지 경계, 쿠키 기반 설정이 무중단성과 공격 저항성으로 이어지는 구조.

1. **멀티호밍** (Multi-Homing) : 한 단말의 여러 IP 주소를 하나의 세션에 등록하고 HEARTBEAT 청크로 경로를 상시 점검 → 주 경로 단절 시 백업 경로로 무손실 전환.
2. **멀티스트리밍** (Multi-Streaming) : 세션 안에 독립된 스트림 ID와 순서 번호를 두어 스트림별로만 순서를 보장 → 한 스트림의 손실이 다른 스트림의 수신을 막지 않음.
3. 메시지 경계 보존 : 응용 계층이 보낸 메시지 단위를 그대로 유지하는 메시지 지향 전송 → 수신 측의 별도 프레이밍 처리가 불필요.
4. **상태 쿠키** (State Cookie) : 4-Way 핸드셰이크에서 서버가 연결 상태를 메모리에 두지 않고 서명된 쿠키로 되돌려 보냄 → 쿠키 반환을 확인한 뒤에만 자원을 할당해 SYN 플러딩형 자원 고갈 공격을 무력화.

## Ⅲ. SCTP의 구조 (흐름)

- 핵심 요약 : 공통 헤더 아래 여러 청크를 묶은 패킷 구조 위에서 결합 단위로 다중 경로와 다중 스트림이 동작하는 구조.
- **결합** (Association) : 양단의 IP 주소 집합 사이에 맺어지는 포괄적 세션으로, 개별 링크가 끊겨도 세션 자체는 유지됨.
- **청크** (Chunk) : 제어 정보와 데이터를 담는 공통 단위로, 하나의 패킷에 여러 청크를 묶어 전송함.
- 신뢰성 제어 : 데이터 청크에 부여한 **TSN** (Transmission Sequence Number)으로 전송 순서를 관리하고, SACK(Selective Acknowledgment)으로 수신 확인과 재전송 대상을 판단하며, 오류 검출은 CRC(Cyclic Redundancy Check)-32c 체크섬으로 수행함.

```text
[ SCTP 패킷 구조 ]

공통 헤더 (포트·검증 태그·CRC-32c)
    ↓
제어 청크 (INIT·SACK·HEARTBEAT 등)
    ↓
데이터 청크 (스트림 ID·순서 번호)
```

```text
[ 4-Way 핸드셰이크 ]

클라이언트의 INIT 전송
    ↓
서버의 INIT-ACK + 상태 쿠키 회신
    ↓
클라이언트의 COOKIE-ECHO 반환
    ↓
서버의 COOKIE-ACK 후 결합 수립
```

- **헤드오브라인 블로킹** (HoL Blocking, Head-of-Line Blocking) : 앞선 데이터의 손실이 뒤따르는 전송 전체를 지연시키는 현상으로, 멀티스트리밍 구조가 이를 스트림 단위로 국한함.

## Ⅳ. SCTP와 TCP·UDP의 비교

- 핵심 요약 : SCTP는 TCP의 신뢰성과 UDP의 메시지 단위를 함께 갖추되 다중 경로와 연결 설정 방식에서 차별화됨.

| 비교 항목 | TCP | UDP | SCTP |
| --- | --- | --- | --- |
| 신뢰성 | ACK와 재전송으로 보장 | 미보장 | 보장, PR-SCTP(Partially Reliable SCTP, RFC 3758)로 부분 신뢰 선택 |
| 전송 단위 | 바이트 스트림 | 데이터그램 | 메시지 경계를 유지하는 청크 |
| 연결 모델 | 1:1 단일 경로 | 비연결형 | 복수 IP를 묶은 결합 |
| 블로킹 | 손실 하나가 전체 지연 | 없음 | 스트림별 격리로 없음 |
| 연결 수립 | 3-Way 핸드셰이크 | 없음 | 4-Way 핸드셰이크 + 상태 쿠키 |
| 오류 검출 | 16비트 체크섬 | 16비트(선택) | CRC-32c |

- 선택 기준 : 범용 바이트 스트림은 TCP, 지연 우선의 단발 메시지는 UDP, 다중 경로 신뢰 전송이 필요한 신호·실시간 데이터는 SCTP를 적용함.

## Ⅴ. SCTP의 한계와 방안

- 핵심 요약 : 중간 장비 차단, 커널 지원 부족, QUIC과의 영역 경쟁을 캡슐화와 사용자 공간 구현, 적용 영역 집중으로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| NAT(Network Address Translation)·방화벽의 차단 | IP 프로토콜 번호 132를 해석하지 못하는 중간 장비로 종단 간 수립 실패 | RFC 6951의 UDP 캡슐화(SCTP over UDP) 적용 | 연결 수립 성공률 |
| OS 커널 지원 부족 | 일부 플랫폼에 커널 스택이 없어 개발·배포 제약 | usrsctp 같은 사용자 공간 라이브러리 채택 | 플랫폼별 호환 검증 결과 |
| QUIC과의 기능 경쟁 | 멀티스트리밍·이동성을 갖춘 QUIC이 웹 영역 선점 | 범용 웹은 QUIC에 두고 SCTP는 신호 전송·데이터 채널에 집중 | 영역별 프로토콜 채택 현황 |

## Ⅵ. SCTP에 대한 기술사적 제언

- 핵심 요약 : 무중단 신호 전송과 실시간 데이터 채널이라는 특화 영역에 SCTP를 제도적으로 배치하는 방향.

1. 통신 사업자는 5G 코어망의 기지국과 AMF(Access and Mobility Management Function) 사이 신호 링크에 SCTP 멀티호밍을 기본 구성으로 표준화해 무중단 운영을 확보할 필요가 있음.
2. 서비스 개발 조직은 WebRTC 데이터 채널(RFC 8831)처럼 SCTP over DTLS 구조를 활용해 브라우저 간 대용량 데이터 전송 기능을 검증·고도화해야 함.
3. 금융·공공 기관은 전용선 장애에 대비한 우회 전송 수단으로 SCTP 도입을 검토하되, 방화벽 정책과 플랫폼 지원 여부를 사전 검증하는 절차를 두어야 함.

## Ⅶ. 결론

- 핵심 요약 : SCTP는 멀티호밍·멀티스트리밍·쿠키 기반 설정을 갖춘 캐리어급 신뢰 전송 프로토콜임.
- 시사점 : 범용 웹 전송과 SCTP의 역할을 영역별로 명확히 구분하는 것이 운영 리스크를 낮추는 길임.
