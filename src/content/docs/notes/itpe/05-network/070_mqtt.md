## 30초 인출

- 본질: 원격 파이프라인이나 차량처럼 대역폭이 극히 좁고 연결이 수시로 끊기는 열악한 무선망에서 데이터 전송의 비효율성
- 메커니즘: 2바이트 초경량 고정 헤더와 중앙 브로커 기반 발행/구독(Pub/Sub) 모델을 적용하여 1:N 비동기 브로드캐스트 구현

## 핵심 용어

- 브로커(Message Broker): 발행자와 구독자 사이에 위치하여 클라이언트의 TCP 연결 유지, 토픽 트리 매칭, 세션 큐잉, 권한 검증 및 메시지 라우팅을 전담하는 중앙 허브 서버
- LWT(Last Will and Testament, 유언 메시지): 클라이언트가 브로커에 접속할 때 미리 등록해 둔 메시지로, 배터리 소모나 통신 단절로 단말이 비정상 종료되면 브로커가 이를 감지하여 다른 구독자들에게 대신 발송하는 장애 통보 기능
- 리테인 메시지(Retained Message): 특정 토픽에 메시지를 발행할 때 보관 플래그를 설정하면, 브로커가 해당 토픽의 최신 메시지 1건을 저장해 두었다가 나중에 새로 접속한 구독자에게 즉시 전달하는 기능

## 1교시 10점 답안

### 정의·목적

- 정의: MQTT은/는 2바이트 초경량 고정 헤더와 중앙 브로커 기반 발행/구독(Pub/Sub) 모델을 적용하여 1:N 비동기 브로드캐스트 구현 방식이다.
- 목적: 초경량 IoT 데이터 수집 및 단말 간 결합도 제거에 기여한다.

### 핵심 구조와 작동

```text
[ MQTT 아키텍처 및 3단계 QoS(Quality of Service) 동작 ]

[ 발행자 (Publisher) ]      [ MQTT 브로커 (Broker) ]      [ 구독자 (Subscriber) ]
- 센서 노드                - 토픽 매칭 및 메시지 라우팅    - 관제 서버 / 모바일 앱
     │                               │                              │
     │ ─── PUBLISH ("home/temp") ───>│ ─── PUBLISH ("home/temp") ──>│

[ 3단계 QoS 핸드셰이크 메커니즘 ]
1. QoS 0 (최대 1회) : 화재 발생 후 방치 (Fire and Forget)
   PUBLISH ───────────────────────> (응답 없음, 유실 감수)

2. QoS 1 (최소 1회) : 수신 확인 필수 (중복 허용)
   PUBLISH ───────────────────────>
   <─────────────────────── PUBACK (미수신 시 재전송)

3. QoS 2 (정확히 1회) : 4단계 핸드셰이크 (유실·중복 원천 차단)
   PUBLISH ───────────────────────>
   <─────────────────────── PUBREC (수신 완료)
   PUBREL  ───────────────────────> (릴리즈)
   <─────────────────────── PUBCOMP(완료 확인)
```

## 2~4교시 25점 답안

### Ⅰ. 핵심 구조와 작동

```text
[ MQTT 아키텍처 및 3단계 QoS(Quality of Service) 동작 ]

   PUBLISH ───────────────────────>
```

### Ⅱ. 핵심 특성

- 시간적·공간적 완전한 비동기 결합 해제(Decoupling): 발행자는 누가 데이터를 받는지(구독자 IP나 상태)를 전혀 알 필요가 없고, 구독자 또한 발행자가 언제 켜졌는지 알 필요 없이 오직 '토픽 이름' 하나로만 느슨하게 연결
- QoS 2는 만병통치약이 아니며 성능의 절대적 적: 정확히 1회(Exactly-Once) 전송을 보장하는 QoS 2는 4번의 네트워크 왕복 패킷 교환과 디스크 트랜잭션 기록이 수반되므로, 일반적인 센서 데이터에 무분별하게 적용하면 브로커 처리량이 80% 이상 급감
- 2바이트 헤더의 마법 뒤에 숨은 상시 TCP 연결의 무게: 패킷 자체는 2바이트로 매우 작지만, 전송 신뢰성을 위해 TCP 세션을 항상 맺어두어야 하므로 수십만 대 단말이 물릴 경우 브로커 서버의 파일 디스크립터 및 소켓 메모리 관리가 인프라의 최대 병목

### Ⅲ. 관련 개념과 구분

- MQTT vs Kafka: MQTT는 저전력 단말과 인터넷 경계(Edge-to-Cloud) 간의 경량 수집에 특화된 프로토콜 / Kafka는 데이터센터 내부(Cloud-to-Cloud)에서 대규모 파티션 분산 저장과 실시간 빅데이터 스트리밍 처리에 특화된 백엔드 분산 로그 시스템

### Ⅳ. 적용 문제와 대응

- 적용 상황: 수십만 대의 스마트팩토리 센서 데이터를 수집하는 IoT 플랫폼
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 인기 토픽에 수만 대 동시 발행 시 브로커 CPU 100% 포화 | 단일 브로커 프로세스의 토픽 트리 매칭 연산 병목 | EMQX / VerneMQ 분산 클러스터링 및 MQTT v5.0 공유 구독(Shared Subscription) 적용 | 수평 스케일아웃으로 트래픽 부하를 백엔드 컨슈머에 균등 분산 |
| 불량 무선 환경에서 QoS 1 메시지의 대량 중복 수신 | 네트워크 타임아웃으로 인한 발행자의 반복 재전송 | 메시지 페이로드에 고유 UUID(Packet ID) 부여 및 멱등성(Idempotency) 소비자 설계 | 중복 수신 패킷을 애플리케이션 레벨에서 무시하여 데이터 일관성 보장 |
