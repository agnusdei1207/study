## 연관 키워드

- 슬라이딩 윈도우(Sliding Window), 흐름 제어(Flow Control), 송신 윈도우, 수신 윈도우(RWIN)
- 파이프라이닝(Pipelining), 누적 확인 응답(Cumulative ACK), Window Size, 0 윈도우(Zero Window)
- 어리석은 창 증후군(SWS, Silly Window Syndrome), Nagle 알고리즘, Window Scale, BDP(Bandwidth-Delay Product)

## Ⅰ. 슬라이딩 윈도우(Sliding Window)의 개요

- 핵심 요약 : 확인 응답을 기다리지 않고 수신 측 버퍼 여유만큼 연속 전송하여 링크 효율과 흐름 제어를 함께 달성하는 기법.
- 개념 : 송신 측이 수신 측 버퍼 크기에 해당하는 **윈도우** 범위 안에서 여러 패킷을 연속으로 보내고, 확인 응답에 따라 윈도우를 앞으로 이동시키며 전송하는 방식으로, 수신 측 처리 능력을 넘지 않도록 **흐름 제어** (Flow Control)를 수행함.
- 배경 및 필요성 : 한 개를 보내고 응답을 기다리는 정지-대기(Stop-and-Wait) 방식은 대역폭-지연 곱(BDP, Bandwidth-Delay Product)이 큰 장거리 고속망에서 링크 용량을 거의 쓰지 못함.
- 주요 목적 : 파이프라인 전송으로 대역폭 이용률을 높이고, 수신 버퍼 오버플로를 막으며, 누적 확인 응답으로 순서와 신뢰성을 관리.

## Ⅱ. 슬라이딩 윈도우(Sliding Window)의 특징 및 장점

- 핵심 요약 : 연속 전송과 동적 윈도우 통지가 대역폭 활용과 수신 보호를 동시에 만드는 방식.

1. 파이프라이닝 : 윈도우 크기만큼 확인 응답 없이 연속 전송 → 전파 지연 동안에도 링크가 쉬지 않아 처리율 향상.
2. 동적 흐름 제어 : TCP 헤더의 Window Size 필드로 남은 버퍼 용량을 실시간 통지 → 수신 측 과부하 없이 전송량 조절.
3. 누적 확인 응답 : 특정 번호의 ACK가 그 이전 바이트의 정상 수신을 함께 뜻함 → ACK 한두 개가 유실되어도 복구가 가능.
4. 재전송 범위 관리 : 윈도우 안의 미확인 구간만 추적 → 송신 측 상태 관리가 단순하고 메모리 사용이 예측 가능.

## Ⅲ. 슬라이딩 윈도우(Sliding Window)의 구조 (흐름)

- 핵심 요약 : 송신 윈도우는 ACK가 도착할 때마다 오른쪽으로 이동하고, 수신 윈도우 크기 통지가 그 이동 폭을 제한하는 구조.
- **송신 윈도우** (Send Window) : ACK 없이 보낼 수 있는 바이트 범위로, 전송 완료 미확인 구간과 전송 가능 구간으로 구분됨.
- **수신 윈도우** (Receive Window, RWIN) : 수신 호스트가 남은 소켓 버퍼 용량을 송신 측에 알리는 값으로, 흐름 제어의 직접적 기준이 됨.

```text
[ 송신 윈도우 이동 ]

윈도우 크기 4, 패킷 1~2 확인 완료
   ↓
패킷 3 ACK 수신 → 윈도우 오른쪽 이동
   ↓
패킷 4~7 전송 가능 (패킷 7 신규 전송)
```

```text
[ 수신 버퍼 가득 참 ]

수신 측 버퍼 가득 참
   ↓
Window Size = 0 통지 (0 윈도우)
   ↓
송신 측 전송 중단, 주기적 프로브로 회복 확인
   ↓
버퍼 비움 → Window Size 재통지 → 전송 재개
```

- **0 윈도우** (Zero Window) : 수신 버퍼가 가득 찼을 때 Window Size를 0으로 알려 송신을 멈추게 하는 상태이며, 송신 측은 프로브 패킷으로 회복을 감지함.

## Ⅳ. 슬라이딩 윈도우(Sliding Window)의 비교

- 핵심 요약 : 슬라이딩 윈도우는 파이프라이닝과 바이트 단위 흐름 제어를 제공하는 반면, 버퍼 비용과 구현 복잡도가 가장 큼.

| 비교 축 | 슬라이딩 윈도우 | 정지-대기 | 크레딧 기반 흐름 제어 |
| --- | --- | --- | --- |
| 파이프라이닝 | 지원 | 미지원 | 지원 |
| 흐름 제어 방식 | 바이트 윈도우 크기 피드백 | ACK 도착 여부로 간접 제어 | 버퍼 슬롯 크레딧 반환 |
| 대역폭 이용률 | BDP에 따라 높아짐 | 낮음 (RTT에 반비례) | 높음 |
| 버퍼 요구량 | 송수신 양단에 큰 버퍼 필요 | 최소 버퍼로 구현 가능 | 큐별 고정 버퍼 필요 |
| 대표 적용 | TCP, SCTP, 이동통신 무선 RLC 확인 모드 | TFTP, 단순 센서 통신 | Fibre Channel, PCIe, InfiniBand |

- 선택 기준 : 광역 IP망의 신뢰성 있는 연속 전송에는 슬라이딩 윈도우를, 단순 장치 간 짧은 메시지에는 정지-대기를, 칩 간이나 스토리지 패브릭처럼 손실 없는 링크에는 크레딧 기반 방식을 택함.

## Ⅴ. 슬라이딩 윈도우(Sliding Window)의 한계와 방안

- 핵심 요약 : 작은 데이터 반복 전송, 16비트 윈도우 필드의 상한, 과대 버퍼에 따른 지연이 주요 한계이며, 전송 조건 조정과 윈도우 확장, 동적 버퍼 튜닝으로 대응.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 어리석은 창 증후군 (SWS) | 수신 버퍼가 조금씩 비면 작은 데이터가 헤더 오버헤드와 함께 반복 전송되어 효율 저하 | 송신 측 Nagle 알고리즘으로 작은 조각 묶기, 수신 측 지연 응답(Delayed ACK) 적용 | 세그먼트당 평균 페이로드 |
| 16비트 Window Size 상한 | 기본 필드로는 약 64KB까지만 표현되어 고대역폭·고지연망에서 링크를 다 쓰지 못함 | **Window Scale** 옵션(RFC 1323)으로 윈도우 크기를 확장 | 링크 이용률 |
| 과대 윈도우에 따른 버퍼 적체 | 윈도우가 지나치게 커지면 중간 라우터 큐가 차서 지연 증가 | 커널의 버퍼 자동 조정 기능으로 BDP 수준에 맞춤 | 큐 지연, 재전송률 |

## Ⅵ. 슬라이딩 윈도우(Sliding Window)에 대한 기술사적 제언

- 핵심 요약 : 윈도우 설정은 망의 BDP와 애플리케이션 응답 특성에 맞춰 조정해야 하며, 기본값에 맡기지 않는 운영 기준이 필요함.
- 고속 데이터센터와 클라우드 연결 구간을 운영하는 인프라 조직은 송수신 버퍼 상한을 회선 속도와 지연에 맞춰 검증하고, 변경 이력을 관리함.
- 지연에 민감한 마이크로서비스 개발 조직은 소규모 요청을 자주 보내는 구간에서 Nagle 알고리즘을 해제하는 소켓 옵션(TCP_NODELAY)을 선별 적용함.
- 다중 스트림 전송을 쓰는 응용 조직은 연결 단위와 스트림 단위의 흐름 제어를 나누어 설계하여, 한 스트림의 지연이 다른 스트림을 막지 않도록 함.

## Ⅶ. 결론

- 핵심 요약 : 슬라이딩 윈도우는 연속 전송과 수신 측 보호를 동시에 달성하는 전송 계층의 핵심 제어 방식이다.
- 시사점 : 대역폭-지연 곱에 맞춘 윈도우 설정이 고속 광역망 성능을 좌우하므로, 윈도우 크기를 망 조건에 맞게 조정하는 것이 중요하다.
