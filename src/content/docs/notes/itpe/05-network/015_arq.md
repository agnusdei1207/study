## 답안 골격
```text
[ARQ] ◀━━ 머리: Ⅶ 내 의견 (RTT 및 오류율에 따른 적응형 Selective Repeat 및 HARQ 결합)
 ┃
 ┣━ Ⅰ 개요 ───── 신뢰성 없는 전송로에서 오류 검출 후 재전송을 자동 요청하는 오류 제어 기법
 ┣━ Ⅱ 특징 ───── 역방향 피드백(ACK/NAK), 재전송 타이머(Timeout), 윈도우 슬라이딩, 순서 번호화
 ┣━ Ⅲ 구조 ───── 3대 기본 유형: Stop-and-Wait ARQ + Go-Back-N ARQ + Selective Repeat ARQ
 ┣━ Ⅳ 흐름 ───── ① 프레임 송신 및 타이머 가동 → ② 수신측 CRC 검증 → ③ 정상 시 ACK / 오류 시 NAK or 타임아웃 후 재전송
 ┣━ Ⅴ 비교 ───── Stop-and-Wait vs Go-Back-N vs Selective Repeat (구현 복잡도, 버퍼, 대역폭 효율)
 ┗━ Ⅵ 실무 ───── 긴 RTT 환경(위성망) 효율 급락 / 수신 버퍼 오버플로 / 중복 패킷 처리
```
- 필수 키워드: Stop-and-Wait · Go-Back-N · Selective Repeat · ACK/NAK · 재전송 타이머 · 슬라이딩 윈도우 · HARQ
- 기출: 138회 4교시 4번 `신뢰성 있는 전송을 보장하기 위한 오류 제어 기술` → Ⅲ·Ⅳ·Ⅴ

## 한 줄 본질
- 전송 중 훼손되거나 유실된 프레임 복구 불가 한계 → 수신측이 검출 부호(CRC)로 오류를 확인한 뒤 ACK/NAK 신호와 타이머를 이용해 송신측이 손상된 프레임을 스스로 다시 보내도록 제어 → 전송 무결성 보장 / 재전송 왕복 대기 시간(RTT)에 의한 채널 이용률 저하

## 핵심 그림
```text
[ ARQ 3대 방식 동작 메커니즘 비교 ]

1. Stop-and-Wait (윈도우 1):
   송신 [Frame 0] --------> 수신 (ACK 1 올 때까지 대기)
        [Frame 1] --------> (손실!) ---> [타임아웃] ---> [Frame 1 재전송]

2. Go-Back-N (송신 윈도우 N, 수신 윈도우 1):
   송신 [0][1][2][3] ----> 수신
        (1번 오류 발생 시) --> 수신측은 1번 이후의 2, 3번 프레임 모두 폐기!
   송신 [1][2][3] 재전송! (오류 발생 시점부터 윈도우 전체를 되돌아가 재전송)

3. Selective Repeat (송신 윈도우 N, 수신 윈도우 N):
   송신 [0][1][2][3] ----> 수신
        (1번 오류 발생 시) --> 수신측은 정상 도착한 2, 3번 프레임을 버퍼에 보관
   송신 [1] 단독 재전송! (오류가 난 1번 프레임만 골라서 재전송 후 정렬)
```

## 핵심 용어
- Stop-and-Wait: 프레임 1개를 전송한 후 수신측으로부터 ACK를 받을 때까지 다음 프레임을 보내지 않고 멈춰 기다리는 가장 단순한 방식
- Go-Back-N: 윈도우 크기 $N$만큼 ACK 수신 없이 연속 송신하되, 오류가 발생하면 오류 이후 전송된 모든 정상 프레임까지 통째로 폐기하고 다시 보내는 방식
- Selective Repeat: 수신측에 버퍼를 두고 오류가 난 특정 프레임만 선별적으로 재전송받아 재조립하는 방식

## 핵심 통찰
- Stop-and-Wait의 대역폭-지연 곱(BDP) 활용률은 $U = 1 / (1 + 2a)$로 RTT가 커질수록 0에 수렴 → 고속망에서는 윈도우 기반 연속 전송(GBN, SR)이 필수적
- Go-Back-N은 수신측 버퍼가 필요 없어($W_r = 1$) 하드웨어 구현이 극도로 가볍지만, 오류율이 높은 환경에서는 정상 패킷까지 중복 전송되어 대역폭 낭비 극심
- Selective Repeat는 대역폭 효율은 최상이지만 수신측에 재정렬(Reordering) 버퍼가 필수적이며, 시퀀스 번호 공간이 윈도우 크기의 최소 2배($2^m \ge 2W$) 이상이어야 이전 프레임과 혼동되지 않음

## 이웃 토픽과 구분
- ARQ vs FEC: ARQ는 오류 발생 시 재전송 피드백을 요구하여 대역폭 효율과 신뢰성을 확보 / FEC는 피드백 없이 송신측 잉여 비트로 수신측이 직접 오류를 정정

## 문제·원인·대책
- 적용 상황: 패킷 손실률이 5% 이상인 무선 채널 환경
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| Go-Back-N 적용 시 유효 처리량 급감 | 1개 프레임 유실 시 정상 수신된 나머지 $N-1$개 프레임까지 강제 폐기 및 재전송 | Selective Repeat ARQ로 전환 | 오류 프레임만 국소 재전송하여 채널 처리량 보존 |
| 수신측에서 이전 윈도우 패킷을 새 패킷으로 오인 | 시퀀스 번호 공간 크기 부족으로 인한 번호 겹침 현상 | 시퀀스 번호 공간 확장 ($MaxSeq \ge 2 \times Window$) | 윈도우 경계 모호성을 제거해 데이터 정합성 보장 |
