## 연관 키워드

- OpenFlow, 플로우 테이블(Flow Table), 플로우 엔트리(Flow Entry), Packet-In, Flow-Mod, Packet-Out
- Table-miss, 그룹 테이블(Group Table), 사우스바운드 인터페이스(SBI, Southbound Interface), ONF(Open Networking Foundation)

## Ⅰ. OpenFlow의 개요

- 핵심 요약 : 스위치의 플로우 테이블을 외부 컨트롤러가 표준 메시지로 읽고 쓰게 만든, 제어·전달 분리의 개방형 프로토콜.
- 개념 : ONF(Open Networking Foundation)가 규격화한 개방형 표준 프로토콜인 **OpenFlow**로, 중앙 컨트롤러가 스위치 내부의 **플로우 테이블**(Flow Table, 매칭 규칙과 동작의 목록)을 원격에서 프로그래밍하는 통신 규격. 컨트롤러와 스위치를 잇는 접점을 **사우스바운드 인터페이스** (SBI, Southbound Interface)라 부름.
- 배경 및 필요성 : 전통 장비는 제어와 전달이 장비 안에 묶인 벤더 고유 구조여서 정책 변경이 장비 단위 수작업이었고, 연구·검증을 위한 개방형 인터페이스의 필요성이 제기됨 (스탠퍼드 대학 Clean Slate 프로젝트에서 출발).
- 주요 목적 : 제어 평면과 데이터 평면의 분리, 벤더 종속 완화, 중앙 소프트웨어 기반의 트래픽 제어.

## Ⅱ. OpenFlow의 특징 및 장점

- 핵심 요약 : 플로우 엔트리 기반의 세밀한 매칭, 표준 메시지 셋, 계층적 테이블 파이프라인이 자동화된 정책 운영으로 연결.

1. 플로우 엔트리 기반 제어 : 매칭 필드·우선순위·카운터·명령·타이머로 구성된 **플로우 엔트리**(Flow Entry) 단위로 규칙 관리 → L2~L4 헤더 조합의 세밀한 트래픽 제어.
2. 표준 메시지 셋 : 미매칭 패킷을 컨트롤러로 올리는 **Packet-In**, 규칙을 설치·수정·삭제하는 **Flow-Mod**, 컨트롤러가 만든 패킷을 송출하는 **Packet-Out** → 신규 흐름 대응과 규칙 갱신의 자동화.
3. 파이프라인 처리 : 복수의 테이블을 순차 통과하는 구조 → 단일 테이블로 표현 불가능한 복합 정책의 단계적 매칭.
4. 타이머 기반 정리 : 유휴 시간(Idle Timeout)과 최대 유지 시간(Hard Timeout)에 따른 규칙 자동 삭제 → 일시적 흐름의 테이블 오염 방지.

## Ⅲ. OpenFlow의 구조 (흐름)

- 핵심 요약 : 컨트롤러와 스위치가 OpenFlow 채널로 메시지를 교환하고, 스위치는 테이블 파이프라인과 미매칭 처리로 동작하는 구조.

```text
[ 컨트롤러 ↔ 스위치 메시지 교환 ]

컨트롤러 (제어 평면)
    ↓ Flow-Mod (규칙 설치·수정)
    ↑ Packet-In (미매칭 패킷 보고)
    ↓ Packet-Out (패킷 주입)
OpenFlow 채널 (암호화 연결)
    ↓
스위치 (전달 평면)
```

```text
[ 패킷 처리 파이프라인 ]

패킷 도착
    ↓
Flow Table 0 (최우선 매칭)
    ↓ 미매칭
Flow Table 1 ~ n (순차 매칭)
    ↓ 최종 미매칭
Packet-In → 컨트롤러
    ↓
Flow-Mod로 규칙 설치 후 재전달
```

- **그룹 테이블**(Group Table) : 멀티캐스트 출력, 고속 장애 우회처럼 복수 포트 동작을 묶어 정의하는 보조 테이블.
- **Table-miss**(어느 엔트리와도 매칭되지 않은 패킷의 처리 동작)는 최하위 우선순위 엔트리로 정의하며, 컨트롤러 전송·폐기·다음 테이블 진행 중 선택.
- 매칭은 우선순위가 가장 높은 엔트리 하나만 적용하고, 제어 채널은 TLS(Transport Layer Security)로 보호하는 것을 기본으로 규정.

## Ⅳ. OpenFlow와 전통 분산 제어, P4의 비교

- 핵심 요약 : 장비 내 자율 제어, 중앙 표준 제어, 데이터 평면 프로그래밍이라는 세 단계의 대비.
- **P4**(Programming Protocol-independent Packet Processors)는 파서·매칭 동작까지 프로그램으로 정의하는 데이터 평면 기술.

| 비교 축 | 전통적 분산 제어 | OpenFlow | P4 기반 데이터 평면 |
| --- | --- | --- | --- |
| 제어 위치 | 장비 내부 분산 | 중앙 컨트롤러 | 중앙 컨트롤러 + 런타임 |
| 규칙 형식 | 벤더 고유 설정 | 표준 플로우 엔트리 | 프로그램이 정의한 매처 |
| 매칭 가능 헤더 | 고정 표준 프로토콜 | 고정 표준 헤더 필드 | 사용자 정의 헤더까지 |
| 표준화 주체 | IETF(Internet Engineering Task Force)·IEEE(Institute of Electrical and Electronics Engineers) | ONF | P4 커뮤니티 |
| 장비 종속성 | 높음 | 낮음 | 낮음 (프로그램 이식형) |

- 선택 기준 : 표준 헤더 범위 안의 중앙 자동화가 목적이면 OpenFlow, 사용자 정의 헤더 처리나 신규 프로토콜 실험이 필요하면 P4 계열 검토.

## Ⅴ. OpenFlow의 한계와 방안

- 핵심 요약 : 컨트롤러 병목, 하드웨어 메모리 한계, 제어 채널 단절을 규칙 사전 배치·집약, 클러스터링, 폴백 모드로 통제.

| 한계 | 원인·영향 | 대응 방안 | 관리 지표 |
| --- | --- | --- | --- |
| 컨트롤러 병목 | 신규 흐름마다 Packet-In 집중 → 셋업 지연 증가 | 사전(Proactive) 규칙 배포와 분산 컨트롤러 클러스터 운영 | 플로우 셋업 지연 |
| 하드웨어 메모리 한계 | TCAM(Ternary Content Addressable Memory) 용량 제한 → 수용 규칙 수의 제한 | 와일드카드 규칙 집약, 테이블 분할 파이프라인 활용 | 테이블 사용률 |
| 제어 채널 단절 | 컨트롤러 연결 상실 → 신규 흐름 처리 불가 | 컨트롤러 다중화와 단절 시 기존 규칙 유지 모드(구현 의존) | 채널 가용률 |

## Ⅵ. OpenFlow에 대한 기술사적 제언

- 핵심 요약 : 역할 분리형 도입, 컨트롤러 이중화, 데이터 평면 기술 로드맵의 병행이라는 운영 전략 제안.
- 데이터센터 운영 조직은 검증된 라우팅 표준을 기본 구조로 두고 OpenFlow를 세부 패킷 조향 같은 한정 영역에 적용하는 역할 분리 설계 채택.
- 컨트롤러 운영 조직은 합의 알고리즘 기반의 다중 노드 클러스터와 규칙 배포 파이프라인 자동화 체계 구축.
- 기술 전략 조직은 P4와 프로그래머블 칩의 동향을 중장기 로드맵에 반영하여 고정 헤더 제약 해소 경로를 사전 준비.

## Ⅶ. 결론

- 핵심 요약 : OpenFlow는 플로우 테이블이라는 단일 개념과 표준 메시지 셋으로 제어·전달 분리를 실현한 개방형 규격.
- 고정 헤더의 제약이 드러난 만큼, 이후 데이터 평면 기술과의 역할 구분 속에서 평가되는 자리.
