## 30초 인출

- 본질: **OpenFlow** : 컨트롤러가 스위치의 플로우 테이블을 관리하고 패킷 처리 규칙을 제어하는 프로토콜
- 메커니즘: 플로우 엔트리의 매칭 필드·우선순위·명령으로 처리 결정 → Table-Miss 동작 또는 컨트롤러 통지
- 통찰: 전통적 네트워크 장비의 제어 평면과 데이터 평면 간 폐쇄적 결합을 해체하고, 외부 중앙 집중형 SDN 컨트롤러가 소프트웨어로 스위치의 흐름 테이블(Flow Table)을 직접 프로그래밍하는 개방형 표준 사우스바운드 인터페이스임.

<details>
<summary>핵심 용어</summary>

- **OpenFlow** : ONF 규격에 따라 컨트롤러와 스위치 간 플로우 규칙·상태를 관리하는 프로토콜
- **플로우 테이블(Flow Table)** : 패킷 매칭과 처리 명령을 담은 스위치 테이블
- **플로우 엔트리(Flow Entry)** : 매칭 필드, 우선순위, 카운터, 명령·시간 초과 등으로 구성되는 규칙
- **Table-Miss** : 테이블의 일반 엔트리와 일치하지 않는 패킷의 처리 규칙
- **OpenFlow 채널(OpenFlow Channel)** : 컨트롤러와 스위치가 프로토콜 메시지를 주고받는 통신 경로
- **Packet-In** : 스위치가 설정된 동작에 따라 패킷 정보를 컨트롤러에 알리는 메시지
- **SDN(Software-Defined Networking)** : 제어 기능과 패킷 전달 기능을 소프트웨어로 분리·관리하는 네트워크 구조

## 2~4교시 25점 답안

## Ⅰ. OpenFlow의 개요

| 구분 | 핵심 |
|---|---|
| 정의 | SDN 컨트롤러(제어 평면)가 네트워크 스위치 및 라우터(데이터 평면)의 패킷 전달 동작을 표준화된 메시지로 직접 제어할 수 있도록 정의한 ONF(Open Networking Foundation) 표준 사우스바운드 인터페이스 |
| 목적 | 단일 벤더 장비 종속(Lock-in) 탈피, 네트워크 제어 로직의 중앙 집중식 소프트웨어 프로그래밍 및 신속한 망 혁신 기능 배포 |

## Ⅱ. OpenFlow의 특징

| 특징 | 상세 내용 |
|---|---|
| 제어/전달 평면 분리 | 라우팅 결정을 내리는 제어 로직은 컨트롤러로 중앙 집중화하고 스위치는 패킷 전달에만 집중 |
| 흐름 기반 포워딩 | 패킷 헤더의 12개 이상 필드(L2~L4)를 복합 조합하여 단일 흐름(Flow) 단위로 유연한 매칭 수행 |
| 다단계 파이프라인 | 여러 개의 플로우 테이블을 순차적으로 검색하는 파이프라인 처리를 통해 복합 정책 적용 |
| 보안 채널(TLS) 연동 | 컨트롤러와 스위치 간 제어 메시지는 상호 인증된 전용 보안 TLS 세션을 통해 암호화 교환 |

## Ⅲ. OpenFlow의 체계·프로세스

**OpenFlow 스위치 내부 패킷 처리 파이프라인 및 엔트리 구조**

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        [ OpenFlow 플로우 테이블 파이프라인 ]           │
│                                                                        │
│ Ingress Packet ──► [ Flow Table 0 ]                                    │
│                           │                                            │
│            ┌──────────────┴──────────────┐                             │
│            ▼ (Match 성공)                ▼ (Match 실패: Table-miss)    │
│   [ 명령어(Instruction) 실행 ]        [ Controller로 Packet-In 전송]  │
│   ├─ 액션 실행 (Output, Drop 등)     (신규 플로우 룰 계산 요청)       │
│   ├─ 메타데이터 갱신                                                  │
│   └─ Goto-Table N ──► [ Flow Table N ] (다단계 파이프라인 연속 검색)   │
│                                │                                       │
│                                ▼                                       │
│                       Egress Port (패킷 포워딩)                        │
└────────────────────────────────────────────────────────────────────────┘
```

| 플로우 엔트리 필드 | 핵심 역할 및 기능 | 세부 내용 예시 |
|---|---|---|
| **매치 필드 (Match Fields)** | 패킷 헤더 비교 조건 | 인그레스 포트, MAC 주소, VLAN ID, IP 주소, TCP/UDP 포트 번호 |
| **우선순위 (Priority)** | 룰 충돌 시 판정 기준 | 숫자가 클수록 높은 우선순위를 가지며 먼저 매칭 평가 |
| **카운터 (Counters)** | 통계 정보 수집 | 해당 룰에 매칭된 수신 패킷 수, 바이트 수, 룰 유지 시간(Duration) |
| **명령어 (Instructions)** | 패킷 조작 및 흐름 제어 | 액션 세트 수정, 메타데이터 전달, 특정 테이블 번호로 이동(Goto-Table) |
| **타임아웃 (Timeouts)** | 룰 자동 만료 관리 | 유휴 시간(Idle Timeout, 트래픽 없을 시), 절대 시간(Hard Timeout) |

## Ⅳ. OpenFlow의 종류·비교

| 비교 항목 | 전통적 L2/L3 스위치 | OpenFlow 스위치 |
|---|---|---|
| **제어 평면 위치** | 장비 내부 펌웨어로 분산 임베디드 | 외부 중앙 집중형 SDN 컨트롤러 |
| **패킷 포워딩 기준** | L2는 MAC만, L3는 IP만 단독 검사 | **L2~L4 12개 이상 헤더를 통합한 'Flow' 기준** |
| **포워딩 테이블** | MAC Table, IP ARP/FIB 고정 분리 | **단일/다단계 통합 Flow Table** |
| **새로운 프로토콜 지원**| 장비 벤더의 ASIC/OS 업그레이드 필수 | **컨트롤러 소프트웨어 앱 설치로 즉각 지원** |
| **제어 프로토콜** | BGP, OSPF, STP 등 분산 라우팅 규격 | **OpenFlow 표준 프로토콜 (단일 사우스바운드)** |

## Ⅴ. OpenFlow의 한계와 방안

| 한계 | 방안 |
|---|---|
| 하드웨어 스위치의 고가 TCAM 용량 한계(수천~수만 엔트리)로 인해 플로우 룰 폭증 시 Flow Table Full 발생 및 컨트롤러 패킷 인(Packet-In) 폭풍(Storm) 유발 | 와일드카드 매칭을 통한 플로우 집약, 비트마스크 축약 및 다단계 플로우 테이블(Pipelined Multi-Table) 분할 설계 |
| 중앙 집중형 SDN 컨트롤러와 오픈플로우 스위치 간 제어 채널 지연 및 컨트롤러 장애 시 전체 네트워크 포워딩 마비(단일 장애점) | 분산 클러스터링 컨트롤러(ONOS, OpenDaylight)의 Raft 합의 프로토콜 기반 고가용성 구성 및 연결 단절 시 로컬 L2/L3 스탠드얼론 모드 자동 전환 |

## Ⅵ. 도입/구축/운영 관점 제언

### 1. 실무 적용 가이드 및 핵심 고려사항
OpenFlow 기반 데이터센터 네트워크 구축 시, 컨트롤러의 제어 평면 부하를 억제하기 위해 첫 패킷 유입 시 매번 컨트롤러에 질의하는 리액티브(Reactive) 방식 대신, 네트워크 기동 시 핵심 라우팅 경로를 사전에 스위치에 일괄 배포하는 프로액티브(Proactive) 룰 인스톨 방식을 기본 운영 전략으로 채택.

### 2. 아키텍처 및 상세 메커니즘
```text
┌────────────────────────────────────────────────────────────────────────┐
│ [ OpenFlow 컨트롤러와 스위치 간 핵심 메시지 교환 절차 ]              │
│                                                                        │
│   [ OpenFlow 스위치 ]                               [ SDN 컨트롤러 ]   │
│           │                                                │           │
│           ├──── 1. Hello (버전 협상) ─────────────────────►│           │
│           │◄─── 2. Hello (버전 확정) ──────────────────────┤           │
│           │◄─── 3. Features Request (스위치 사양 요청) ────┤           │
│           ├──── 4. Features Reply (포트 수, 지원 테이블) ─►│           │
│           │                                                │           │
│   (신규 패킷 도착 시 매칭 룰 없음)                         │           │
│           ├──── 5. Packet-In (패킷 헤더 보고) ────────────►│           │
│           │                                                ├─► 최적경로│
│           │                                                │   계산완료│
│           │◄─── 6. Flow-Mod (새로운 Flow Rule 추가 지시) ──┤           │
│           │◄─── 7. Packet-Out (보류된 패킷 즉시 전송 지시)─┤           │
│           ▼                                                            │
│   (이후 동일 플로우 패킷은 컨트롤러 질의 없이 스위치 단독 와이어스피드 처리)│
└────────────────────────────────────────────────────────────────────────┘
```

### 3. 기술 유형 및 비교 평가
| OpenFlow 버전 | 핵심 개선 사항 | 지원 테이블 구조 |
|---|---|---|
| **OpenFlow 1.0** | 기본 12개 튜플 매치 필드 정의 | 단일 플로우 테이블 (Single Table) |
| **OpenFlow 1.3** | 다단계 테이블 파이프라인, IPv6 지원, Meter(QoS) 지원 | 복수 테이블 (Pipeline Multi-Table) |
| **OpenFlow 1.5** | 패킷 레지스터 확장, TCP 플래그 매칭, 이그레스 처리 고도화 | 확장형 플로우 파이프라인 |
