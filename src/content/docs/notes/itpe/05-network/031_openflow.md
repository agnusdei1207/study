## 한 줄 본질
- 스위치 제조사의 폐쇄적 펌웨어에 갇혀 있던 네트워크 제어 권한의 한계 → 외부 중앙 컨트롤러가 안전한 채널을 통해 스위치의 포워딩 규칙(플로우 테이블)을 소프트웨어로 직접 주입하고 제어 → 네트워크의 유연한 프로그래밍 혁신 달성 / 새 플로우 발생 시마다 컨트롤러에 물어봐야 하는 Table-Miss 응답 지연 발생

```text
                         +-------------------------+
                         |    SDN 컨트롤러 (두뇌)   |
                         +------------+------------+
                                      | (OpenFlow 프로토콜: TCP/TLS)
                                      v

         |               v
         v       +---------------------------------------------+
   +-----------> | 플로우 테이블 0 (Flow Table 0)               |
   |             |  [ 매칭 필드 ] --> [ 카운터 ] --> [ 액션 지시]|
   |             +----------------------+----------------------+
   |                                    | (Go-to Table N)
   |                                    v
   |             +---------------------------------------------+
   |             | 플로우 테이블 1 (Flow Table 1)               |
   |             +----------------------+----------------------+
   |                                    |
   |             +-- [ 매칭 성공 시 ] ---+---> 액션 실행 (포트 포워딩, 헤더 수정)
   |             |

```

## 핵심 용어
- 플로우 테이블(Flow Table): 스위치 내부에서 패킷을 처리하는 규칙들의 집합. 각 엔트리는 매칭 필드(Match Fields), 우선순위(Priority), 카운터(Counters), 지시어(Instructions/Actions)로 구성
- Table-Miss: 수신된 패킷의 헤더가 플로우 테이블의 어떤 엔트리와도 일치하지 않는 예외 상황. 기본 규칙에 따라 패킷을 버리거나 컨트롤러로 Packet-In 전송
- Match-Action: L2(MAC), L3(IP), L4(Port) 헤더의 다양한 필드를 복합 매칭한 뒤, 전달(Forward), 폐기(Drop), 헤더 수정(Modify) 등의 액션을 수행하는 유연한 패킷 처리 패러다임

## 핵심 통찰
- 전통적 스위치는 MAC 주소만 보고, 라우터는 목적지 IP만 보았으나, OpenFlow는 L2~L4 전체 12~40여 개 필드를 동시에 매칭 조건으로 활용 가능
- 리액티브(Reactive) 모드는 첫 패킷마다 컨트롤러에 패킷을 올려보내므로 지연이 발생하고 컨트롤러가 마비될 수 있음 → 실무에서는 미리 규칙을 채워 넣는 프로액티브(Proactive) 모드 혼용 필수
- 상용 스위치의 고속 검색용 TCAM 메모리는 수천~수만 개 엔트리밖에 저장하지 못하므로, 플로우 규칙을 지나치게 쪼개면(Micro-flow) 스위치 하드웨어 메모리가 즉각 고갈

## 이웃 토픽과 구분
- SDN vs OpenFlow: SDN은 제어와 데이터를 분리하는 광범위한 네트워크 아키텍처 철학 / OpenFlow는 그 철학을 구현하기 위해 컨트롤러와 스위치 사이를 연결하는 구체적인 통신 프로토콜 표준

## 문제·원인·대책
- 적용 상황: 대규모 트래픽 급증 시 OpenFlow 컨트롤러 다운
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 미등록 플로우 폭증으로 컨트롤러 CPU 100% 포화 | 리액티브 모드의 무차별 Packet-In 메시지 플러딩 | 프로액티브(Proactive) 사전 와일드카드 규칙 설치 및 로컬 캐싱 | 컨트롤러 질의를 90% 이상 차단해 와이어스피드 처리 |
| 스위치 TCAM 메모리 한도 초과(Flow Table Overflow) | 세부 IP/포트 단위의 너무 잘게 쪼갠 플로우 엔트리 등록 | 접두사 요약(Prefix Aggregation) 및 다단계 파이프라인 분할 | 플로우 엔트리 수를 1/10로 압축하여 TCAM 공간 보존 |
