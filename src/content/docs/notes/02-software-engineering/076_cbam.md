## 한 줄 본질
- ATAM은 아키텍처 전략의 기술적 절충점만 보여줄 뿐 한정된 예산에서 무엇을 먼저 구현할지 경제성을 판단하지 못하는 병목 → 아키텍처 전략이 제공하는 품질 개선 가치를 유틸리티(Utility)와 비용(Cost)으로 환산해 ROI를 산출 → 최적의 경제적 아키텍처 투자 우선순위 확정 / 주관적 유틸리티 산정의 오차 위험

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               CBAM (Cost Benefit Analysis Method) 의사결정 구조   |
+-------------------------------------------------------------------+
|   [ ATAM 산출물: 품질 속성 시나리오 (가용성, 성능, 보안 등) ]     |
|                                |                                  |
|                                v                                  |
|   +-----------------------------------------------------------+   |
|   | 1. 시나리오별 유틸리티(Utility) 할당 : 현재값 vs 목표값   |   |
|   | 2. 아키텍처 전략(Strategy) 매핑       : 캐싱, 이중화 등   |   |
|   | 3. 비용(Cost) 및 편익(Benefit = ΔUtility) 정량 산정       |   |
|   +-----------------------------------------------------------+   |
|                                |                                  |
|                                v                                  |
|   +-----------------------------------------------------------+   |
|   | 4. ROI 산출 공식 : ROI = Benefit / Cost                   |   |
|   +-----------------------------------------------------------+   |
|                                |                                  |
|                                v                                  |
|   [ 최종 의사결정: 예산 한도 내 ROI 상위 아키텍처 전략 채택 ]     |
+-------------------------------------------------------------------+
```

## 핵심 용어
- 유틸리티(Utility): 특정 품질 속성 수준(예: 응답시간 200ms)이 비즈니스 이해관계자에게 제공하는 만족도나 주관적 가치를 정량화한 수치(0~100)
- 아키텍처 전략(Architectural Strategy): 품질 속성 요구사항을 달성하기 위해 아키텍처 수준에서 적용하는 구체적 설계 기법(예: 서킷 브레이커 도입, DB 샤딩)

## 핵심 통찰
- 엔지니어는 기술적으로 완벽한 아키텍처(최고 성능, 99.999% 가용성)를 원하지만, 경영진은 한정된 예산 내에서 최대의 비즈니스 가치를 내는 아키텍처를 원함
- CBAM은 아키텍처 설계라는 공학적 결정을 CFO(재무책임자)와 비즈니스 이해관계자가 이해할 수 있는 'ROI 언어'로 번역해 주는 다리 역할을 수행함
- ATAM을 먼저 수행하여 아키텍처의 리스크와 트레이드오프를 도출한 후, 그 결과물로 나온 후보 전략들을 CBAM의 입력값으로 투입하는 것이 표준적인 연계 방식임

## 이웃 토픽과 구분
- CBAM vs ATAM: ATAM = "이 아키텍처가 품질 요구를 만족하는가, 위험(Risk)은 무엇인가"를 기술적으로 평가 / CBAM = "어떤 아키텍처 전략에 먼저 예산을 투자해야 ROI가 가장 높은가"를 경제적으로 평가

## 문제·원인·대책
- 사례: 128회 기출 차세대 금융 시스템 구축 시 예산 초과로 인한 아키텍처 재설계 분쟁
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 성능과 보안 개선안 10개가 동시 제안되었으나 예산 부족으로 프로젝트 중단 위기 | 감정적 주장과 직급에 의존한 주관적 기술 선택 | CBAM 유틸리티 곡선 기반 전략별 비용 대비 편익(ROI) 매트릭스 도출 | ROI 상위 3개 전략으로 합의 도출 및 예산 내 목표 달성 |
| 수십억 원을 들여 Active-Active DR을 구축했으나 실제 비즈니스 효용 미미 | 비즈니스 손실 비용 대비 과도한 인프라 투자(Over-engineering) | CBAM의 시나리오 유틸리티 평가를 통해 적정 수준(RTO 1시간) 절충안 채택 | 불필요한 인프라 투자 비용 50% 절감 |

## 내 의견
- [비용 없는 기술적 이상론에 빠진 아키텍트의 독선] 비즈니스 이익과 예산 제약은 무시한 채 최신 트렌드의 복잡한 인프라만 도입하려는 엔지니어링 만능주의 경계 → 나라면: 아키텍처 의사결정 기록(ADR) 작성 시 비기능 품질 속성 외에도 예상 라이선스/클라우드 비용과 비즈니스 기대 편익을 CBAM 산식으로 명시하는 '경제성 기반 아키텍처 리뷰' 의무화
