 ┣━ Ⅰ 개요 ───── 단일 거대 모놀리스(Monolith)의 빌드/배포 지연 및 장애 전파 한계 극복
 ┣━ Ⅱ 특징 ───── 독립적 배포성(Independently Deployable) · 도메인 중심 분할 · 폴리글랏 · DB per Service

## 한 줄 본질
- 하나의 거대한 코드베이스로 인해 작은 수정 하나에도 전체 시스템을 재빌드·재배포해야 하고 한 모듈의 장애가 전체 다운으로 번지는 모놀리스 병목 → 단일 비즈니스 도메인을 담당하는 작은 독립 서비스들로 쪼개고 경량 프로토콜(REST/gRPC/이벤트)로 통신 → 서비스별 독립적 배포 및 탄력적 수평 확장 / 분산 데이터 일관성 보장 및 네트워크 복잡도 대가

## 핵심 그림
```text
  [ Web / Mobile Clients ]
             |
             v
+-------------------------------------------------------------+
|  API Gateway (인증, 라우팅, 로드밸런싱, Rate Limiting)      |
+-------------------------------------------------------------+
       /            |            \
      v             v             v
+-----------+ +-----------+ +-----------+
| 주문 서비스| | 결제 서비스| | 배송 서비스|  (독립 배포 컨테이너)
| +-------+ | | +-------+ | | +-------+ |
| | 주문 DB | | | 결제 DB | | | 배송 DB | |  (DB per Service: 데이터 독립)
+-----------+ +-----------+ +-----------+
      \             ^             /
       +------------+------------+
             | (Apache Kafka / RabbitMQ: 비동기 이벤트 기반 통신)
```

## 핵심 용어
- DB per Service: 각 마이크로서비스가 자체 데이터베이스를 독립적으로 소유하여 타 서비스의 DB 직접 조회를 금지하고 오직 API를 통해서만 데이터를 교환하는 패턴
- 사가(Saga) 패턴: 분산 환경에서 글로벌 락(2PC) 없이, 로컬 트랜잭션의 연속과 실패 시 이를 취소하는 보상 트랜잭션(Compensating Transaction)으로 최종 일관성을 맞추는 기법

## 핵심 통찰
- MSA는 기술적인 아키텍처라기보다 팀 조직의 구조를 반영하는 콘웨이의 법칙(Conway's Law)의 산물임(독립된 작은 팀이 독립된 서비스를 소유)
- 데이터베이스를 분리하지 않은 채 애플리케이션만 컨테이너로 쪼개는 것은 "분산된 모놀리스(Distributed Monolith)"라는 최악의 안티패턴을 낳음
- 분산 환경에서는 네트워크 단절, 지연, 부분 실패가 일상이므로, 서킷 브레이커(Circuit Breaker)와 재시도(Retry), 결과적 일관성(Eventual Consistency) 설계가 필수적임

## 이웃 토픽과 구분
- MSA vs SOA: MSA = 경량 API와 똑똑한 엔드포인트(Dumb Pipe) / SOA = 무거운 중앙집중식 ESB(Enterprise Service Bus) 기반의 복잡한 비즈니스 오케스트레이션

## 문제·원인·대책
- 사례: 120회/127회 기출 이커머스 시스템의 MSA 전환 후 트랜잭션 실패 사태
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 주문 완료 후 결제 실패 시 주문 데이터가 취소되지 않고 DB에 잔존 | 단일 DB의 ACID 트랜잭션을 분산 환경에서 그대로 사용 시도 | 코레오그래피 또는 오케스트레이션 기반 Saga 보상 트랜잭션 적용 | 시스템 최종 일관성(Eventual Consistency) 100% 달성 |
| 서비스 간 호출 연쇄 지연으로 어떤 구간이 병목인지 추적 불가 | 수십 개 서비스 간의 분산 네트워크 호출로 인한 가시성 결여 | OpenTelemetry 및 분산 추적(Jaeger, Zipkin) 트레이스 ID 전파 | 엔드투엔드 요청 흐름 및 지연 병목 구간 수초 내 규명 |

## 내 의견
- [도메인 경계 이해 없는 성급한 MSA 쪼개기의 재앙] 도메인 주도 설계(DDD)의 바운디드 컨텍스트(Bounded Context) 분석 없이 화면 단위나 엔티티 단위로 서비스를 100개씩 쪼개어, 단순 목록 조회 하나에 10개 서비스가 네트워크 통신을 하며 시스템 전체가 뻗어버리는 참극 목격 → 나라면: 잘 구축된 모놀리스(Modular Monolith)로 시작하여 트래픽과 변경 주기가 명확히 분리되는 도메인만 하나씩 스트랭글러 패턴으로 떼어내는 점진적 MSA 전환 원칙 고수
