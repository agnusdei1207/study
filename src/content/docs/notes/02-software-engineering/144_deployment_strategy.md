## 한 줄 본질
- 서버를 내리고 새로 올리는 전통적 배포로 인해 새벽 작업과 서비스 다운타임, 배포 실패 시 복구 불가 위험 병목 → 트래픽 라우팅과 인스턴스 교체 기법을 조합하여 사용자 중단 없이 점진적으로 새 버전을 적용하고 즉시 롤백 가능한 엔지니어링 전략 / 인프라 비용 및 데이터 정합성 관리 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  현대적 3대 무중단 배포 전략 비교                       |
+-------------------------------------------------------------------------+
|  [ 1. 롤링 (Rolling) ] : 인스턴스를 하나씩 순차적으로 교체              |
|     (v1)(v1)(v1) ──> (v2)(v1)(v1) ──> (v2)(v2)(v1) ──> (v2)(v2)(v2)     |
|     * 장점: 추가 리소스 비용 없음 / 단점: 배포 중 v1, v2 동시 공존      |
|                                                                         |
|  [ 2. 블루-그린 (Blue-Green) ] : 동일한 신규 환경 구축 후 라우터 전환    |
|     Load Balancer ────> [ Blue (v1 활성) ]   (운영 중)                  |
|          │                                                              |
|          └─(스위칭)───> [ Green (v2 신규) ]  (배포 완료 후 즉시 전환)   |
|     * 장점: 즉각 롤백, 버전 공존 없음 / 단점: 인프라 리소스 2배 필요    |
|                                                                         |
|  [ 3. 카나리 (Canary) ] : 소수 사용자에게 먼저 노출 후 모니터링         |
|     Load Balancer ─┬──(90% 트래픽)──> [ v1 서버군 ]                      |
|                    └──(10% 트래픽)──> [ v2 카나리 ] (에러율/지연 관측)  |
|     * 장점: 실제 프로덕션 위험 조기 감지 / 단점: 라우팅 제어 복잡성     |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 카나리 배포(Canary Deployment): 광부들이 유독가스를 감지하기 위해 카나리아를 데려갔듯, 신규 버전을 전체 사용자의 1~5%에게만 우선 전달하여 실시간 에러율과 지연을 관측한 뒤 점진적으로 확대하는 전략
- 확장 및 수축 패턴(Expand-Contract Pattern): 무중단 배포 시 DB 스키마를 변경할 때 구버전과 신버전 코드가 모두 동작하도록 컬럼을 먼저 추가(Expand)하고, 배포 완료 후 구 컬럼을 삭제(Contract)하는 2단계 마이그레이션 기법

## 핵심 통찰
- 애플리케이션 코드를 무중단으로 교체하는 것은 쿠버네티스로 쉬워졌으나, 실무 무중단 배포의 진짜 병목은 "데이터베이스(DB) 스키마 변경"임
- 롤링 배포나 카나리 배포 중에는 반드시 시스템 내에 구버전(v1)과 신버전(v2) 코드가 동시에 트래픽을 처리하는 과도기 구간이 존재하므로, DB는 반드시 하위 호환성(Backward Compatibility)을 유지해야 함
- 배포 전략은 단순한 인프라 작업이 아니라 품질 테스트 전략과 결합되어야 하며, 카나리 배포는 "카나리 테스트", 트래픽 분기는 사용자 전환율을 측정하는 "A/B 테스트"로 직결됨

## 이웃 토픽과 구분
- 카나리 배포 vs A/B 테스트: 카나리 배포 = 엔지니어링 관점에서 시스템의 기술적 안정성(에러율, 응답속도) 검증 / A/B 테스트 = 비즈니스 관점에서 사용자의 행동 변화(전환율, 클릭률) 검증

## 문제·원인·대책
- 적용 상황: 대규모 트래픽을 처리하는 소셜 미디어 플랫폼 신규 릴리스
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 신규 기능 배포 후 10분 만에 OOM(메모리 누수) 크래시로 전체 사용자 먹통 장애 | 전면 교체(빅뱅/블루그린) 방식으로 인해 잠재 결함이 전체 트래픽에 즉시 노출 | 카나리 배포(5% 트래픽) 및 프로메테우스 에러율 임계치 초과 시 자동 롤백 연계 | 장애 영향 범위를 5%로 격리하고 1분 내 자동 복구 |
| 롤링 배포 중 구버전 인스턴스가 신버전 DB 컬럼 삭제로 인해 SQL 에러 발생 | DB 스키마를 단일 배포 트랜잭션으로 즉시 변경하여 구버전 코드 호환 실패 | Expand-Contract(확장/수축) 패턴을 적용하여 컬럼 추가 후 배포, 구버전 퇴역 후 삭제 | 스키마 마이그레이션 무중단 100% 보장 |
