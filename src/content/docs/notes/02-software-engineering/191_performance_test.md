```text
[성능 테스트(Performance Test)] ◀━━ 머리: Ⅶ 내 의견 (Shift-Left 성능 엔지니어링과 분산 부하 테스트 도구(k6) 기반 지속적 성능 파이프라인)
 ┃
 ┣━ Ⅰ 개요 ───── 목표 부하 환경에서 시스템의 응답성, 처리량, 확장성, 자원 사용률을 측정하고 시스템 병목을 진단·개선하는 비기능 테스트
 ┣━ Ⅱ 특징 ───── 정량적 SLA/SLO 준수 검증 · 시스템 임계점(Breakpoint) 도출 · 자원 누수(Memory Leak, Thread Lock) 사전 예방
 ┣━ Ⅲ 구조 ───── 5대 성능 테스트 유형: 부하(Load) · 스트레스(Stress) · 내구성(Endurance/Soak) · 스파이크(Spike) · 확장성(Scalability)
 ┣━ Ⅳ 흐름 ───── 성능 목표 정의(SLA) → 부하 모델링(TPS/가상유저) → 테스트 시나리오 작성 → 부하 주입 및 모니터링 → 병목 튜닝 → 결과 보고
 ┣━ Ⅴ 비교 ───── 부하 테스트(Load) vs 스트레스 테스트(Stress) vs 내구성 테스트(Endurance) vs 스파이크 테스트(Spike)
 ┗━ Ⅵ 실무 ───── 테스트 환경과 운영 환경 간의 스펙 불일치 / DB 커넥션 풀(DBCP) 고갈 / 가상 사용자(VUser) 인위적 부하의 현실 왜곡
```
- 필수 키워드: 응답 시간(Response Time) · 처리량(TPS/Throughput) · 가상 사용자(VUser) · 부하 테스트 · 스트레스 테스트 · 내구성 테스트(Soak) · 스파이크 테스트 · 임계점(Breakpoint)
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 5대 성능 테스트 유형별 부하 프로파일 곡선 도식 → Ⅴ 유형별 상세 비교표 / 25점 = Ⅰ~Ⅶ 전개, 95·117회 기출 성능 지표(TPS, Latency, Concurrency) 산출 수식, 리틀의 법칙(Little's Law), APM 연계 병목 진단 기법
- 기출: 95회 1교시, 117회 1교시 `성능 테스트의 개념, 주요 유형(부하, 스트레스, 확장성 등) 및 성능 측정 지표` → Ⅰ~Ⅵ

## 한 줄 본질
- 실제 운영 환경의 트래픽을 모사한 인위적 가상 부하를 시스템에 주입하여 목표 응답시간과 처리량을 달성하는지 검증하고 숨은 인프라 병목을 찾아내는 비기능 엔지니어링 / 시스템 임계점 식별과 용량 계획

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  성능 테스트 유형별 부하 주입 프로파일 (Load Profile)     |
+-------------------------------------------------------------------------+

|   부하량             부하량 (임계초과)        부하량 (장시간)       부하량 (순간폭증)
|    ┌───┐                 ▲                    ┌───────┐             ┌┐
|    │   │               ┌─┘                  ┌─┘       │             ││
|  ──┘   └───          ──┘                    │         │          ───┘└───
|    (정상 최대)          (시스템 다운 확인)      (메모리 누수 검증)    (순간 트래픽 대응)
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 응답 시간(Response Time): 사용자가 요청을 전송한 시점부터 시스템이 처리를 완료하고 결과를 완전히 수신할 때까지 걸린 총 시간 (지연 시간 + 처리 시간)
- 처리량(TPS, Transactions Per Second): 초당 시스템이 성공적으로 처리해 낸 트랜잭션의 건수
- 동시 사용자(Concurrency): 특정 시점에 시스템에 접속하여 실제 활성 트랜잭션을 발생시키고 있는 가상 사용자 수 ($N = \text{TPS} \times (\text{응답시간} + \text{Think Time})$)
- 리틀의 법칙(Little's Law): 안정적인 시스템에서 공간 내에 머무는 평균 고객 수(L)는 고객의 평균 도착률($\lambda$)과 시스템에 머무는 평균 시간(W)의 곱과 같다는 이론 ($L = \lambda \times W$)
- 임계점(Breakpoint): 부하가 증가함에 따라 TPS가 더 이상 증가하지 않고 정체되거나 급감하며, 응답 시간이 기하급수적으로 폭증하기 시작하는 성능 한계 지점

## 핵심 통찰
- 성능 테스트는 단순히 '느린가 빠른가'를 보는 것이 아니라, 시스템의 '임계점(Breakpoint)'이 어디에 형성되어 있는지를 밝히는 작업임
- 동시 접속자 수(Concurrent Users)와 초당 처리량(TPS)은 동일하지 않으며, 사용자의 생각하는 시간(Think Time)을 배제한 채 부하를 주입하면 비현실적인 DoS 공격 시험으로 변질됨
- 대부분의 웹/앱 시스템 병목은 WAS의 CPU 연산이 아니라 데이터베이스 락(Lock), 슬로우 쿼리, DB 커넥션 풀(DBCP) 부족, 외부 서드파티 API 대기 지연에서 발생함
- 따라서 부하 생성 도구(JMeter, Locust, k6)와 함께 WAS/DB 레벨을 정밀 추적할 수 있는 APM(Pinpoint, Scouter, Datadog) 모니터링이 반드시 병행되어야 함

## 이웃 토픽과 구분
| 비교 항목 | 부하 테스트 (Load) | 스트레스 테스트 (Stress) | 내구성 테스트 (Soak) | 스파이크 테스트 (Spike) |
| :--- | :--- | :--- | :--- | :--- |
| **주요 목적** | 정상 목표 부하 하의 성능 및 SLA 달성 검증 | 시스템의 한계 임계점 및 파괴 후 복구력 검증 | 장시간 구동 시 자원 누수(메모리 등) 감지 | 순간적 트래픽 폭증 시 탄력적 수용력 검증 |
| **부하 수준** | 최대 예상 트래픽 (100% Load) | 예상 초과 극한 트래픽 (150%~300%) | 평균 운영 트래픽 (60%~80%) | 평시 대비 수배~수십 배 급상승 부하 |
| **수행 시간** | 1시간 ~ 4시간 | 30분 ~ 1시간 (단기 집중) | 24시간 ~ 수일간 장기 실행 | 수 분 ~ 수십 분 |
| **핵심 감지 결함**| 병목 쿼리, 쓰레드 풀 병목 | 서킷 브레이커 작동, 오토스케일링 지연 | 가비지 컬렉션(GC) 누적, 커넥션 누수 | 버퍼 오버플로우, 인스턴스 패닉 다운 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **부하 증가 시 TPS 정체 및 타임아웃 속출** | WAS의 쓰레드 풀 또는 HikariCP 커넥션 풀이 고갈되어 대기 큐 적체 | 커넥션 풀 크기 튜닝, 쿼리 인덱스 최적화, 비동기 논블로킹 I/O(WebFlux) 적용 |
| **장시간 테스트 중 OutOfMemoryError(OOM) 발생** | 힙 메모리 객체 참조 미해제, 세션 미반환 등 자바 힙 메모리 누수 발생 | 힙 덤프(Heap Dump) 분석(Eclipse MAT), 캐시 만료(TTL) 설정, 메모리 누수 코드 리팩토링 |
| **운영 환경 대비 테스트 환경 인프라 스펙 부족** | 예산 문제로 스테이징 서버를 운영 서버의 1/4 수준으로 구성하여 테스트 | 가용 용량 모델링(Capacity Modeling) 및 오토스케일링 기반 클라우드 임시 인프라 활용 부하 검증 |

## 이렇게 출제된다
- **10점형**: 성능 테스트(Performance Test)의 개념 및 부하(Load) 테스트와 스트레스(Stress) 테스트의 차이점을 설명하시오.
- **25점형**: 
  - 1) 성능 테스트의 목적과 4대 주요 유형(부하, 스트레스, 내구성, 스파이크)의 부하 프로파일 곡선을 도식으로 제시하시오.
  - 2) 동시 사용자 수(VUser), 처리량(TPS), 응답 시간(Response Time), Think Time 간의 수학적 상관관계(리틀의 법칙 연계)를 수식으로 설명하시오.
  - 3) 마이크로서비스(MSA) 환경에서 분산 트랜잭션 및 서비스 간 통신 병목을 진단하기 위한 성능 엔지니어링 및 APM 연계 방안을 제시하시오.

## 내 의견
- 전통적인 성능 테스트는 릴리즈 직전에 한 번 몰아서 수행하는 '빅뱅 사후 검증'이었으나, 이는 결함 수정 비용을 극단적으로 높이는 부작용을 낳았음
- 현대 엔지니어링에서는 성능 테스트를 개발 주기 초기로 앞당기는 'Shift-Left 성능 테스트'로 전환해야 함
- 이를 위해 k6나 Locust와 같은 코드 기반 부하 테스트 스크립트(Performance as Code)를 작성하여 CI/CD 파이프라인에 통합하고, PR(Pull Request) 머지 시 주요 엔드포인트의 응답시간 회귀(Regression)를 자동으로 차단하는 자동화된 성능 게이트를 운영해야 함
