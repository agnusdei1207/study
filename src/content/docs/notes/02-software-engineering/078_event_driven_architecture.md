## 한 줄 본질
- 수십 개 서비스가 동기식 HTTP(REST)로 엮여 앞단 서비스 장애가 연쇄 전파되는 블로킹 병목 → 상태 변화를 비동기 이벤트 메시지로 발행하고 브로커를 통해 구독자에게 전달 → 서비스 간 완전한 시공간적 디커플링 달성 / 최종 일관성과 분산 디버깅 복잡성 증가

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               EDA 2대 핵심 토폴로지 비교 (중재자 vs 브로커)       |
+-------------------------------------------------------------------+
| 1. 중재자 토폴로지 (Mediator Topology) - 오케스트레이션 방식      |
| [생성자] -> [큐] -> [이벤트 중재자 (Mediator)]                   |
|                        |------------+------------+                |
|                        v            v            v                |
|                   [결제처리]   [재고차감]   [배송요청] (순서 통제) |
+-------------------------------------------------------------------+
| 2. 브로커 토폴로지 (Broker Topology) - 코레오그래피 방식          |
| [생성자] -> |주문생성이벤트| -> [결제서비스]                      |
|                                     |                             |
|                                     v |결제완료이벤트|            |
|                                  [재고서비스] -> |재고차감이벤트| |
+-------------------------------------------------------------------+
```

## 핵심 용어
- 중재자 토폴로지(Mediator Topology): 중앙의 '이벤트 중재자'가 복잡한 여러 단계의 비즈니스 이벤트 처리 순서와 실패 보상 트랜잭션을 총괄 지휘하는 오케스트레이션 구조
- 브로커 토폴로지(Broker Topology): 중앙 조정자 없이, 개별 이벤트 프로세서들이 브로커의 메시지를 구독하고 처리 후 다음 이벤트를 연쇄 발행하는 고성능 코레오그래피 구조

## 핵심 통찰
- 브로커 토폴로지는 결합도가 가장 낮고 확장성이 극대화되지만, 전체 비즈니스 흐름을 한눈에 파악하기 어렵고 실패 시 롤백 추적이 매우 난해함
- 중재자 토폴로지는 흐름 제어와 에러 복구가 용이하지만, 중재자 컴포넌트 자체가 병목(SPOF)이 되거나 도메인 로직이 집중될 위험이 있음
- 이벤트 발행과 DB 저장을 원자적(Atomic)으로 묶지 않으면 "DB에는 저장됐는데 이벤트는 발행 안 되는" 불일치가 생기므로, 반드시 '트랜잭셔널 아웃박스(Transactional Outbox)' 패턴을 써야 함

## 이웃 토픽과 구분
- EDA vs 메시지 큐(Message Queue): 메시지 큐 = 비동기 통신을 가능케 하는 미들웨어 기술(수단) / EDA = 이벤트의 생성, 탐지, 소비를 중심으로 시스템 전체를 구성하는 '아키텍처 스타일(목적)'

## 문제·원인·대책
- 사례: 129회 기출 주문-결제-재고 간 이벤트 유실로 결제만 되고 물건은 안 나간 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 주문 DB 커밋 후 네트워크 장애로 카프카 메시지 발행 누락 | DB 갱신과 메시지 브로커 발행이 분리된 2단계 트랜잭션의 원자성 실패 | 트랜잭셔널 아웃박스(Transactional Outbox) 및 Debezium CDC 연동 | 이벤트 발행 누락 0건 100% 보장 |
