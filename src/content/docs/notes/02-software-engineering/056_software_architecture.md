```text
 ┃
 ┣━ Ⅰ 개요 ───── 시스템의 복잡도 제어 및 비기능 품질 속성(성능, 가용성, 보안) 달성을 위한 근본 구조적 결정
 ┣━ Ⅱ 특징 ───── 최고 수준의 추상화 · 이해관계자 소통의 기준 · 변경 비용이 극도로 높은 근본적 결정들의 집합
 ┣━ Ⅲ 구조 ───── 컴포넌트(Components) + 커넥터(Connectors) + 제약조건(Constraints)
 ┣━ Ⅳ 흐름 ───── 비즈니스 목표 분석 → 품질 속성 시나리오 도출 → 아키텍처 스타일 선정 → 설계 및 문서화(4+1 View) → 평가(ATAM)
 ┣━ Ⅴ 비교 ───── 소프트웨어 아키텍처(거시적 구조 및 품질) vs 소프트웨어 상세 설계(미시적 알고리즘/클래스)
 ┗━ Ⅵ 실무 ───── 아키텍처 침식(Architecture Erosion) 발생 / 아키텍처 적합도 함수(Fitness Functions) 자동 검증
```

## 한 줄 본질
- 프로젝트 후반에 시스템을 뜯어고치려면 막대한 비용이 소요되는 근본적인 기술 결정들을 사전에 통제하지 못하는 실패 병목 → 시스템을 구성하는 핵심 컴포넌트와 이들을 잇는 커넥터의 관계 및 원칙을 조기에 규정 → 전체 시스템의 비기능 품질(가용성, 성능, 보안) 보장 / 초기 설계 기간 투입 비용

## 핵심 용어
- 컴포넌트(Component)와 커넥터(Connector): 컴포넌트는 연산을 수행하거나 상태를 저장하는 실행 단위이고, 커넥터는 컴포넌트 간의 상호작용(메시지, RPC 등)을 매개하는 통로
- 아키텍처 침식(Architecture Erosion): 시간이 지남에 따라 개발자들의 임의 코딩으로 초기 아키텍처 원칙과 계층 규칙이 무너지고 스파게티 구조로 퇴보하는 현상
- ADR(Architecture Decision Record): 중요한 아키텍처 결정의 맥락, 대안, 채택 이유 및 트레이드오프를 짧은 텍스트로 기록하여 공유하는 표준 문서 양식

## 핵심 통찰
- 마틴 파울러는 아키텍처를 "나중에 변경하기 어려운 모든 중요한 결정들"이라고 정의함(즉, 초기 아키텍처 결정의 실패는 프로젝트 파탄으로 직결됨)
- 아키텍처는 기능(Function)보다는 비기능 품질 속성(Quality Attributes: 0.5초 이내 응답, 99.999% 가용성 등)을 만족시키기 위해 존재함
- 4+1 View 모델은 이해관계자(개발자, 인프라 담당자, 고객)마다 시스템을 바라보는 관점이 완전히 다르다는 점을 인정하고 각각의 독립된 시각을 제공함

## 이웃 토픽과 구분
- 아키텍처 vs 디자인 패턴: 아키텍처 = 시스템 전체의 물리적/논리적 거시 구조 / 디자인 패턴 = 특정 모듈 내부 클래스들 간의 미시적 협력 패턴

## 내 의견
- [아키텍처를 그럴듯한 그림 한 장으로 퉁치는 관행] 박스와 화살표 몇 개 그려놓고 아키텍처 설계를 끝냈다고 선언하는 부실 설계 다발 → 나라면: 아키텍처 다이어그램마다 반드시 정량화된 품질 속성 시나리오(자극-반응)를 1:1로 매핑하고, 성능·보안 임계치를 자동으로 측정하는 '아키텍처 피트니스 함수(Fitness Function)'를 배포 파이프라인에 탑재하여 아키텍처의 지속적 건전성 보증
