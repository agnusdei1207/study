 ┃
 ┣━ Ⅰ 개요 ───── 시스템 내부 구현 관점 명세의 소통 부재 → 사용자 관점의 시스템 행위 및 목표 달성 상호작용 기술
 ┣━ Ⅱ 특징 ───── 블랙박스 뷰 · 기능적 요구사항 중심 · 액터 목표 기반 시나리오 구성 · 추적성(Traceability) 기준점

 ┣━ Ⅴ 비교 ───── 유스케이스(Use Case) vs 사용자 스토리(User Story) vs 기능 요구사항 목록(FRD)

## 한 줄 본질
- 개발자 중심의 기술 명세서 작성으로 인해 발주자·사용자와의 요구사항 불일치 및 잦은 변경 병목 → 시스템이 외부 액터에게 제공하는 측정 가능한 가치 중심의 상호작용 시나리오를 정의하는 기법 / 과도한 상세화 시 문서 유지보수 비용 급증

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  유스케이스 명세서(Specification) 구조 템플릿           |
+-------------------------------------------------------------------------+
|  유스케이스명   | 상품 주문 및 결제 (ID: UC-001)                         |
|  액터           | 고객 (Primary Actor), 결제 게이트웨이 (Secondary Actor) |
|  목표           | 장바구니 상품을 결제하고 주문을 확정한다                |
|  사전 조건      | 사용자가 로그인되어 있고 장바구니에 1개 이상 상품 존재   |
|  사후 조건      | 재고 차감 완료, 결제 승인 기록, 주문 번호 발급 완료     |
+-----------------+-------------------------------------------------------+
|  기본 흐름      | 1. 고객이 주문 버튼을 클릭한다                         |
|  (Basic Flow)   | 2. 시스템이 배송지 및 최종 결제 금액을 표시한다        |
|                 | 3. 고객이 결제 수단을 선택하고 승인을 요청한다         |
|                 | 4. 시스템이 결제 모듈을 호출하고 주문을 완료 처리한다  |
+-----------------+-------------------------------------------------------+
|  대체/예외 흐름 | 3a. 결제 수단 잔액 부족: 시스템이 에러 안내 후 재시도 유도 |
|  (Alternative)  | 4a. 통신 타임아웃: 승인 취소 전문 전송 후 장바구니 복원|
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 주 액터(Primary Actor): 유스케이스를 시작하여 시스템으로부터 직접적 목표 달성을 요구하는 외부 주체(사용자, 외부 시스템)
- 사전/사후 조건(Pre/Post Condition): 유스케이스 실행 전 시스템이 만족해야 하는 상태와, 정상 완료 후 보장되어야 하는 시스템의 보장 상태

## 핵심 통찰
- 유스케이스는 다이어그램(그림) 자체가 핵심이 아니라, 시나리오의 조건과 단계별 분기를 기술한 "유스케이스 명세서(텍스트)"가 실질적인 분석·설계 산출물임
- 기본 흐름(Happy Path)만 작성된 유스케이스는 개발 후 운영 장애의 온상이 되므로, 전체 명세 분량의 60% 이상을 대체 흐름과 예외 처리(Exception Handling)에 투입해야 함
- 유스케이스 입도(Granularity)는 "비즈니스 트랜잭션 단위(칵테일 레벨, Sea Level)"로 맞춰야 하며, "버튼 클릭", "화면 열기"처럼 UI 조작 수준으로 잘게 쪼개면 시스템 구조가 왜곡됨

## 이웃 토픽과 구분
- 유스케이스 vs 사용자 스토리: 유스케이스 = 사전/사후 조건 및 단계별 시나리오를 정밀하게 명세하는 구조적 분석 기법 / 사용자 스토리 = `[누가] [무엇을] [왜 원한다]` 형태의 짧은 대화 유발 도구

## 문제·원인·대책
- 적용 상황: 대규모 공공 SI 차세대 시스템 요구사항 정의 단계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 설계 및 구현 단계에서 요구사항 변경 요청이 쏟아지며 프로젝트 지연 | 유스케이스 명세에 예외 흐름(타임아웃, 중복 결제)이 누락되어 기본 경로만 정의됨 | 요구사항 도출 시 대체/예외 흐름 작성 체크리스트 의무화 및 인수 기준(Acceptance Criteria) 명시 | 설계 결함 조기 차단 및 변경 비용 60% 절감 |
| 유스케이스 개수가 수천 개로 폭증하여 관리 불능 상태 도달 | UI 단위(화면별 버튼 클릭)로 유스케이스를 과도하게 잘게 쪼갠 입도 오류 | Alistair Cockburn의 목표 수준(Sea Level) 기준 적용 및 비즈니스 트랜잭션 단위 재그룹핑 | 산출물 유지보수 비용 절감 및 요구사항 추적성 확립 |

## 내 의견
- [요구사항 명세서와 테스트 케이스 간의 불일치 단절] 문서로만 작성된 유스케이스는 개발이 진행되면서 코드 변경을 따라가지 못해 사장되는 경향 존재 → 나라면: 유스케이스의 기본 흐름과 대체 흐름을 Cucumber 기반의 BDD(Behavior-Driven Development) `Given-When-Then` 시나리오 코드로 직접 변환하여, 요구사항 명세가 곧 자동화된 인수 테스트로 동작하도록 CI 파이프라인 연계
