## 답안 골격
```text
[리팩토링] ◀━━ 머리: Ⅶ 내 의견 (회귀 테스트 스위트 없는 리팩토링 금지 및 TDD 일상화)
 ┃
 ┣━ Ⅰ 개요 ───── 기능 추가 위주 개발로 인한 코드 스멜 누적 → 외부 동작 유지하며 내부 구조 개선
 ┣━ Ⅱ 특징 ───── 소프트웨어 기능 불변 · 가독성 및 유지보수성 향상 · 소규모 단계적 수행
 ┣━ Ⅲ 구조 ───── 코드 스멜 감지 → 리팩토링 기법 적용 → 단위 테스트 회귀 검증
 ┣━ Ⅳ 흐름 ───── ① 기존 테스트 통과 확인 → ② 소규모 코드 변형 → ③ 테스트 재실행 → ④ 커밋
 ┣━ Ⅴ 비교 ───── 리팩토링(동작 불변, 내부 개선) vs 성능 최적화(동작 불변, 속도/자원 집중) vs 재공학(전체 재설계)
 ┗━ Ⅵ 실무 ───── 테스트 부재 상태의 리팩토링 부작용 / 캐릭터라이제이션 테스트 선행
```

- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 절차 도식 → Ⅴ 최적화/재공학 비교 / 25점 = Ⅰ~Ⅶ 전개, 주요 기법(메서드 추출, 이동 등) 및 테스트 보증

## 한 줄 본질
- 빠른 납기 압박으로 인해 중복과 스파게티 코드가 쌓여 신규 기능 추가 비용이 폭증하는 기술 부채 병목 → 외부 동작(인터페이스 및 입출력)을 일체 변경하지 않고 내부 구조를 작고 단순한 단위로 점진 재구성 → 코드 가독성 및 변경 유연성 확보 / 단기적 일정 투입 비용

## 핵심 그림
```text
   +-------------------------------------------------------------+
   |                  [ 기존 자동화 테스트 성공 확인 ]            |
   +-------------------------------------------------------------+
                                  |
                                  v
   +-------------------------------------------------------------+
   | [ 코드 스멜 식별 ] ---> [ 마이크로 리팩토링 1회 적용 ]      |
   | (중복 코드, 긴 메서드)   (Extract Method, Rename 등)        |
   +-------------------------------------------------------------+
                                  |
                                  v
   +-------------------------------------------------------------+
   |                [ 자동화 회귀 테스트 즉시 재수행 ]            |
   |                     (실패 시 즉시 Undo 롤백)                 |
   +-------------------------------------------------------------+
```

## 핵심 용어
- 코드 스멜(Code Smell): 시스템의 심각한 결함은 아니지만 장기적으로 유지보수성을 파괴하는 잘못된 설계나 나쁜 코드 패턴의 징후
- 캐릭터라이제이션 테스트(Characterization Test): 레거시 시스템의 실제 현재 동작을 그대로 기록하여 리팩토링 중 변경 발생 여부를 포착하는 안전망 테스트

## 핵심 통찰
- 자동화된 테스트 코드가 없는 리팩토링은 구조 개선이 아니라 미확인 결함을 주입하는 도박에 불과함
- 한 번에 대규모로 구조를 뒤엎는 리팩토링은 거의 100% 실패하며, 커밋 가능한 5~10분 단위의 극소 변경을 연속 반복해야 함
- 새로운 기능 추가와 리팩토링을 한 작업 단위에서 동시에 진행하면 회귀 결함의 원인 분리가 불가능해지므로 두 모자를 엄격히 분리해 착용해야 함

## 이웃 토픽과 구분
- 리팩토링 vs 성능 최적화: 리팩토링 = 코드 가독성과 설계 단순화 목적 / 성능 최적화 = 하드웨어 자원 효율화 목적으로 때로는 코드 복잡도 증가 허용

## 내 의견
- [별도 리팩토링 스프린트 요청의 비현실성] 개발자가 경영진에게 기능 개발을 멈추고 한 달간 리팩토링만 하겠다고 요청하면 승인받기 어렵고 방치되기 일쑤 → 나라면: 보이스카우트 규칙(캠핑장을 떠날 때는 처음 왔을 때보다 깨끗하게 하라)을 팀 문화로 정착시켜, 업무 티켓을 처리할 때 마주친 코드 스멜 1개를 반드시 정리하는 점진적 리팩토링을 일상화
