## 답안 골격
```text
[개발방법론 테일러링] ◀━━ 머리: Ⅶ 내 의견 (선도개발을 통한 아키텍처 사전 검증과 위험 기반 맞춤형 프로세스 확정)
 ┃
 ┣━ Ⅰ 개요 ───── 획일적 방법론 적용의 비용 낭비 → 선도개발(PoC) 및 프로젝트 특성에 맞춘 프로세스 재단
 ┣━ Ⅱ 특징 ───── 선도개발 중심 검증 · 유연성 · 산출물 경량화 · 표준 프로세스 기반 변형
 ┣━ Ⅲ 구조 ───── 테일러링 기준(규모, 복잡도, 신기술, 품질수준) / 테일러링 기법(생략, 추가, 통합, 분할)
 ┣━ Ⅳ 흐름 ───── 표준 프로세스 분석 → 선도개발 범위 선정 → 아키텍처/위험 검증 → 방법론 확정 → 본 개발 전파
 ┣━ Ⅴ 비교 ───── 선도개발 기반 테일러링(기술 위험 사전 제거) vs 문서 기반 테일러링(형식적 계획 수립)
 ┗━ Ⅵ 실무 ───── 신기술 불확실성으로 인한 본 개발 지연 / 선도개발 프로토타입을 통한 표준 프레임워크 조기 안착
```
- 필수 키워드: 선도개발 · 방법론 테일러링 · 테일러링 기준 · 기술 위험 검증 · 산출물 최적화 · 테일러링 매트릭스
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 테일러링 4대 기준 및 기법 → Ⅳ 선도개발 연계 흐름도 / 25점 = Ⅰ~Ⅶ 전개, 선도개발 성공 기준 및 본 개발 확산 거버넌스
- 기출: 138회 1교시 6번 `소프트웨어 개발 프로젝트에서 선도개발을 위한 개발방법론 테일러링(Tailoring)` → Ⅰ·Ⅲ·Ⅳ

## 한 줄 본질
- 대규모 프로젝트에서 신기술이나 아키텍처 검증 없이 표준 방법론을 일률 적용하다 본 개발 단계에서 구조적 파탄이 나는 병목 → 프로젝트 초기에 핵심 고난도 기능을 선도개발(Pilot)하며 프로세스와 산출물을 실증적으로 재단 → 프로젝트 위험 조기 완화 / 선도개발 결과의 본 개발 미반영 시 자원 낭비

## 핵심 그림
```text
+-------------------------------------------------------------------+

+-------------------------------------------------------------------+
| 1단계: 선도개발 대상 식별 (최고 난이도 아키텍처, 신기술 연계 모듈) |
|   |                                                               |
|   v                                                               |

|   |                                                               |
|   v                                                               |
| 3단계: 선도개발 수행 및 실증 (성능, 연계 안정성, 팀 생산성 측정)  |
|   |                                                               |
|   v                                                               |
| 4단계: 프로세스·산출물 최종 확정 (검증된 프레임워크 및 템플릿 확산)|
+-------------------------------------------------------------------+
```

## 핵심 용어
- 선도개발(Pilot/Lead Development): 고위험 비즈니스 로직이나 신규 아키텍처를 본 개발 착수 전에 소규모 정예 팀이 먼저 구현하여 실현 가능성을 입증하는 활동
- 테일러링 매트릭스: 표준 산출물 목록 대비 생략·통합·변경 사유와 승인 주체를 명시한 추적성 표

## 핵심 통찰
- 테일러링을 단순한 '문서 줄이기'로 접근하면 감리나 품질 검증에서 치명적인 결함으로 지적되므로, 생략 사유에 대한 공학적 근거(선도개발 검증 데이터)를 문서화해야 함
- 선도개발은 버리는 프로토타입이 아니라, 본 개발팀이 복사해 쓸 수 있는 '골든 레퍼런스 아키텍처(Golden Reference)'를 완성하는 과정이어야 함
- 기술 스택의 변경이나 팀의 숙련도 수준에 따라 분석·설계 단계의 상세화 수준을 가변적으로 조절하는 것이 진정한 테일러링의 목적임

## 이웃 토픽과 구분
- 방법론 테일러링 vs 소프트웨어 리팩토링: 방법론 테일러링 = 개발 '프로세스'와 산출물을 상황에 맞게 재단 / 리팩토링 = 개발된 '소스코드'의 내부 구조를 개선

## 문제·원인·대책
- 사례: 138회 기출 클라우드 신기술 도입 프로젝트에서 선도개발 없는 획일적 폭포수 방법론 적용 실패
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 본 개발 70% 진행 시점에 프레임워크 간 트랜잭션 충돌 발견 | 초기 선도개발 없이 문서 기반 아키텍처 설계만 승인 | 고난도 트랜잭션 대상 선도개발 1스프린트 강제 배정 | 기술적 호환성 결함 착수 2주 내 조기 격리 |
| 선도개발 완료 후 본 개발팀이 레퍼런스 코드를 이해하지 못해 재개발 | 선도개발 산출물 전파 교육 및 코딩 표준 가이드라인 누락 | 선도개발팀 핵심 인력을 각 서브 도메인 아키텍트로 전진 배치 | 전 개발팀의 표준 프레임워크 학습 곡선 단축 |

## 이렇게 출제된다

## 내 의견
- [회의실 탁상공론으로 작성되는 엑셀 테일러링] 실제 코드를 한 줄도 작성해 보지 않은 채 프로젝트 첫 주에 엑셀 체크박스로 산출물 생략 여부를 일괄 결정하는 형식주의 경계 → 나라면: 선도개발 2주 스프린트를 의무화하여 핵심 API 호출 및 DB 트랜잭션 코드를 직접 구동해 보고, 그 과정에서 병목으로 입증된 문서와 절차만을 선별적으로 제거하는 실증 기반 테일러링 의무화
