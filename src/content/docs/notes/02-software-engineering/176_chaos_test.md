## 답안 골격
```text
[카오스 테스트(Chaos Test)] ◀━━ 머리: Ⅶ 내 의견 (운영 환경 통제된 장애 주입과 회복 탄력성(Resilience) 가설 검증을 통한 선제적 장애 예방)
 ┃
 ┣━ Ⅰ 개요 ───── 복잡한 분산 클라우드의 예측 불가한 돌발 장애 → 운영 환경에 제어된 결함을 선제적으로 주입하여 시스템 회복력 검증
 ┣━ Ⅱ 특징 ───── 카오스 엔지니어링(Chaos Engineering) 실천법 · 정상 상태(Steady State) 가설 검증 · 폭발 반경(Blast Radius) 최소화
 ┣━ Ⅲ 구조 ───── 카오스 실험 4단계(정상상태 정의 → 가설 수립 → 장애 주입 실험 → 가설 검증 및 개선) + Simian Army (Chaos Monkey 등)

 ┣━ Ⅴ 비교 ───── 전통적 장애 테스트(테스트베드, 수작업 시나리오) vs 카오스 테스트(운영 환경, 무작위 자동화 장애 주입)
 ┗━ Ⅵ 실무 ───── 통제 실패 시 실제 대규모 서비스 장애 위험 / 비상 정지 버튼(Emergency Stop) / 쿠버네티스(Litmus, Chaos Mesh)
```

## 한 줄 본질
- 수천 개의 마이크로서비스가 얽힌 클라우드에서 어떤 서버가 죽었을 때 연쇄 장애가 터질지 아무도 예측하지 못하는 불확실성 병목 → 실제 운영 환경에서 서버를 강제로 끄거나 네트워크 지연을 인위적으로 주입하여 시스템이 스스로 자가 치유(Self-Healing)하는지 검증하는 선제적 실험 기법 / 장애 통제 실패 시 실제 서비스 다운 위험

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  카오스 엔지니어링(Chaos Engineering) 4단계 실험 절차   |
+-------------------------------------------------------------------------+
|                                                                         |
|  [ 1. 정상 상태 정의 ]                                                  |
|    - 정상 동작을 대변하는 비즈니스 메트릭 선정 (초당 주문 건수, 200 OK 비율)|
|                   │                                                     |
|                   v                                                     |
|  [ 2. 가설 수립 ]                                                       |
|    - "결제 서비스 파드 3개 중 1개가 죽어도, 전체 주문 성공률은 유지된다" |
|                   │                                                     |
|                   v                                                     |
|  [ 3. 장애 주입 실험 (최소 폭발 반경) ]                                |
|    - LitmusChaos / Chaos Mesh 도구로 특정 파드 1개 강제 종료(Kill)     |
|    - 네트워크 패킷 지연 500ms 인위적 주입                               |
|                   │                                                     |
|                   v                                                     |
|  [ 4. 가설 검증 및 자동 롤백 ]                                          |
|    - 메트릭 관측: 쿠버네티스가 새 파드를 띄우고 트래픽 정상 우회 확인   |
|    - 가설 위반(주문 에러율 급증) 시 즉시 실험 중단(Rollback) 및 개선    |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 정상 상태(Steady State): 시스템이 정상적으로 구동되고 있음을 나타내는 측정 가능한 측정치(예: 초당 결제 성공 건수, p99 응답시간)의 기준 베이스라인
- 폭발 반경(Blast Radius): 카오스 실험 중 발생한 인위적 장애가 실제 사용자나 다른 연관 비즈니스 시스템에 미칠 수 있는 피해 영향의 범위

## 핵심 통찰
- 카오스 테스트는 무책임하게 서버를 때려 부수는 파괴 행위가 아니라, "정상 상태 가설을 세우고, 최소한의 폭발 반경 내에서 안전장치를 둔 채 실행하는 과학적 실험"임
- 결함은 언제나 발생한다는 "설계상의 고장 불가피성(Design for Failure)"을 전제하며, 문제가 새벽에 알람으로 터지기 전에 업무 시간 중에 엔지니어가 지켜보는 상태에서 미리 터뜨려 취약점을 찾아냄
- 카오스 테스트의 핵심 안전장치는 "이상 징후 발생 시 실험을 즉시 중단하고 시스템을 원복시키는 비상 정지(Dead Man's Switch)" 기능임

## 이웃 토픽과 구분
- 카오스 테스트 vs 스트레스 테스트: 스트레스 테스트 = 트래픽 부하를 한계점까지 밀어 넣어 시스템이 뻗는 용량 한계를 측정 / 카오스 테스트 = 평상시 트래픽에서 컴포넌트 고장(네트워크 단절, 파드 다운) 시 시스템의 자가 복원력을 측정

## 문제·원인·대책
- 적용 상황: 글로벌 마이크로서비스 클라우드 인프라 안정성 검증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 캐시 서버 다운 시 백엔드 DB로 쿼리가 폭주하여 쇼핑몰 전체 서비스 마비 | 장애 발생 시 서킷 브레이커(Circuit Breaker)가 정상 작동하는지 사전 미검증 | 카오스 테스트로 캐시 파드를 강제 다운시켜 서킷 브레이커 오픈 및 폴백(Fallback) 검증 | 연쇄 장애(Cascading Failure) 원천 차단 |
| 카오스 실험 도중 제어 범위를 벗어나 실제 VIP 고객들의 결제 오류로 이어짐 | 폭발 반경(Blast Radius) 격리 없이 운영 환경 전체 트래픽을 대상으로 무차별 실험 | 카나리 환경 및 내부 테스트 계정 트래픽으로 폭발 반경 격리, 카오스 자동 롤백 연계 | 프로덕션 비즈니스 피해 제로화 |

## 내 의견
- [카오스 테스트 도입의 성숙도 단계 준수] 단위 테스트와 기본 모니터링조차 안 되어 있는 조직이 트렌드만 좇아 운영 환경에 카오스 몽키를 돌리는 것은 만용에 불과함 → 나라면: 1단계로 스테이징 환경에서 계획된 장애 주입을 수행하고, 2단계로 CI/CD 배포 파이프라인에서 자동화된 카오스 게이트를 거친 뒤, 시스템 성숙도가 최고조에 달했을 때 비로소 제한된 프로덕션 카오스 실험을 수행하는 "단계적 카오스 성숙도 모델" 수립
