## 한 줄 본질
- "테스트를 다 통과했으니 버그가 절대 없다"는 잘못된 확신으로 출시 후 대형 사고가 터지는 오판 병목 → 테스트는 결함이 없음을 증명할 수 없으며 제한된 자원 내에서 위험을 최소화하기 위한 7가지 공학적 원칙을 준수해야 한다는 테스팅 공리 / 비전문가의 비현실적 완벽 요구

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  ISTQB 소프트웨어 테스트 7대 기본 원리 체계              |
+-------------------------------------------------------------------------+
|                                                                         |
|  [ 1. 결함의 존재 증명 ]  테스팅은 결함이 "있음"을 보여줄 뿐, "없음"을 입증 못함 |
|  [ 2. 완벽 테스팅 불가 ]  모든 입력 조합을 전수 테스트하는 것은 불가능 (무한대)   |
|  [ 3. 조기 테스팅     ]  개발 생명주기 초기(Shift-Left)에 시작할수록 비용 절감  |
|  [ 4. 결함 집중       ]  대부분의 결함은 소수의 특정 모듈에 몰려 있음 (파레토 80:20)|
|  [ 5. 살충제 패러독스 ]  동일한 테스트를 반복하면 새로운 결함을 발견하지 못함     |
|  [ 6. 정황 의존성     ]  전자상거래 웹과 의료기기 소프트웨어는 테스팅 방식이 다름|
|  [ 7. 오류 부재의 궤변]  요구사항을 만족하지 못하면 버그가 전혀 없어도 쓸모 없음   |
|                                                                         |
|  * 핵심 결론: 리스크 기반 테스팅(RBT)과 테스트 케이스의 지속적 회전(갱신) 필요 |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 살충제 패러독스(Pesticide Paradox): 동일한 살충제를 계속 뿌리면 해충이 내성을 갖듯, 동일한 테스트 케이스를 계속 반복 수행하면 새로운 버그를 더 이상 잡아내지 못하는 현상
- 오류 부재의 궤변(Absence-of-Errors Fallacy): 시스템에서 발견된 모든 버그를 완벽하게 고쳤다 하더라도, 사용자의 실제 비즈니스 요구와 목적을 충족하지 못하면 그 소프트웨어는 실패작이라는 원리

## 핵심 통찰
- 테스팅의 제1원리는 "결함이 있음을 증명하는 것이지, 결함이 전혀 없음을 증명하는 것이 아니다"라는 점이며, 따라서 "버그가 0개"라는 말은 완벽한 제품이 아니라 테스트가 부실했음을 의미함
- 완벽한 전수 테스트(Exhaustive Testing)는 불가능하므로, 동등 분할, 경계값 분석, 리스크 기반 테스팅(RBT)을 통해 가장 결함 발생 확률이 높은 최적의 부분집합을 도출하는 것이 테스트 엔지니어링의 본질임
- 파레토 법칙(80:20 법칙)에 따라 전체 결함의 80%는 소수 20%의 핵심 모듈(결제, 인증 등)에 집중되므로, 테스트 자원을 균등 분배하지 말고 고위험 모듈에 집중 배치해야 함

## 이웃 토픽과 구분
- 결함(Defect/Bug) vs 고장(Failure): 결함 = 개발자의 실수로 인해 소스코드 내에 잠재된 원인(오류) / 고장 = 결함이 있는 코드가 실행되어 사용자가 체감하는 시스템의 비정상적 동작 및 다운

## 문제·원인·대책
- 적용 상황: 차세대 핀테크 오픈 뱅킹 릴리스 전 QA 테스트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 수개월 동안 회귀 테스트를 매일 돌려 100% Pass했으나 운영 배포 첫날 신규 결함 폭증 | 살충제 패러독스: 기존 테스트 케이스만 기계적으로 반복하여 새로운 실행 경로 미검증 | 뮤테이션 테스팅 도입 및 탐색적 테스팅(Exploratory Testing)으로 테스트 케이스 정기 갱신 | 숨은 잠재 결함 40% 추가 발굴 |
| 결함 0건으로 완벽 검수 합격했으나 현업 사용자들이 "원하던 기능이 아니다"라며 시스템 폐기 | 오류 부재의 궤변: 기술적 버그 수정에만 매몰되어 비즈니스 유효성(Validation) 검증 실패 | 요구사항 정의 단계부터 현업 주도의 BDD 인수 테스트(UAT) 조기 편성 | 사용자 업무 적합성 100% 확보 |
