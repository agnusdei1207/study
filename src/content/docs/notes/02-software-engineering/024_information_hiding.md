## 답안 골격
```text
[정보은닉] ◀━━ 머리: Ⅶ 내 의견 (접근 제어자를 넘어선 불변 객체 설계와 인터페이스 기반 결합도 격리)
 ┃
 ┣━ Ⅰ 개요 ───── 객체 내부 구현에 대한 직접 접근으로 인한 연쇄 변경 파장 방지
 ┣━ Ⅱ 특징 ───── 데이비드 파나스(Parnas) 원칙 · 변경 가능성 높은 세부사항 은닉 · 인터페이스 분리
 ┣━ Ⅲ 구조 ───── 공개 인터페이스(Public API) + 은닉된 내부 상태/알고리즘(Private State)
 ┣━ Ⅳ 흐름 ───── 클라이언트 요청 → 공개 인터페이스 경유 → 내부 메서드 위임 → 캡슐화된 상태 변경
 ┣━ Ⅴ 비교 ───── 캡슐화(데이터와 메서드의 결합) vs 정보은닉(불필요한 세부사항 숨김)
 ┗━ Ⅵ 실무 ───── 무의미한 Getter/Setter 남발로 인한 은닉 파괴 / Tell, Don't Ask 원칙 준수
```
- 필수 키워드: 데이비드 파나스 · 캡슐화 · 접근 제어자 · 인터페이스 격리 · 파급 효과(Ripple Effect) 최소화 · Tell Don't Ask
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 구조도 → Ⅴ 캡슐화와의 명확한 개념 구분 / 25점 = Ⅰ~Ⅶ 전개, 객체지향 설계 원칙(SOLID) 및 유지보수 파급 효과 통제 실증
- 기출: 134회 1교시 `객체 간의 데이터 보호를 위한 정보은닉(Information Hiding)` → Ⅰ·Ⅱ·Ⅲ / 131회 1교시 `객체지향 방법론에서 캡슐화와 정보은닉` → Ⅴ

## 한 줄 본질
- 다른 모듈이 특정 객체의 내부 변수나 자료구조 구현 방식에 직접 의존하여 내부 변경 시 전체 시스템이 깨지는 취약성 병목 → 변경될 가능성이 높은 세부 구현을 감추고 안정적인 공개 인터페이스만 노출 → 모듈 간 결합도 최소화 및 독립적 수정 보장 / 간접 호출로 인한 미세한 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------+
| [ Object Boundary ]                                         |
|                                                             |
|   (Public Interface)                                        |
|   + transfer(amount, toAccount) <--- [ 외부 클라이언트 접근 ] |
|                                                             |
|   (Hidden Internal Implementation - Private)                |
|   - balance: double (내부 변수 보호)                        |

|   - logAuditTrail(): void                                   |
+-------------------------------------------------------------+
```

## 핵심 용어
- 데이비드 파나스의 원칙: 모듈을 분할할 때 기능 순서가 아니라 '가장 변경될 가능성이 높은 비밀(Secret)'을 각 모듈 안에 숨기도록 설계해야 한다는 기본 원칙
- Tell, Don't Ask: 객체의 내부 데이터를 가져와서(Ask) 밖에서 판단하지 말고, 객체에게 직접 원하는 작업을 수행하라고 메시지를 던지라(Tell)는 객체지향 설계 원칙

## 핵심 통찰
- 캡슐화(Encapsulation)는 데이터와 처리 로직을 하나의 단위로 묶는 '수단'이고, 정보은닉(Information Hiding)은 그중 민감한 세부사항을 감추는 '설계 목적이자 결과'임
- private 필드를 선언해 놓고 모든 필드에 대해 public getter와 setter를 자동 생성하는 것은 정보은닉을 스스로 무너뜨리는 안티패턴임
- 소프트웨어 모듈의 교체 가능성과 테스트 용이성은 내부 구현을 얼마나 철저하게 인터페이스 뒤로 숨겼느냐에 정비례함

## 이웃 토픽과 구분
- 캡슐화 vs 정보은닉: 캡슐화 = 관련 속성과 행위를 한 껍질에 모으는 메커니즘 / 정보은닉 = 모듈 내부의 비밀(자료구조, 알고리즘)을 외부에 노출하지 않는 설계 기법

## 문제·원인·대책
- 사례: 134회 기출 금융 계좌 이체 모듈의 잔액 직접 갱신으로 인한 무결성 훼손
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 외부 모듈이 계좌의 balance 변수를 직접 수정하여 마이너스 잔액 발생 | 정보은닉 실패(public 변수 직접 노출 또는 무제한 setter 제공) | balance 변수를 private 은닉하고 인출(withdraw) 비즈니스 메서드 내부에서만 잔액 검증 | 계좌 잔액의 비즈니스 무결성 100% 보장 |
| 내부 자료구조를 배열에서 해시맵으로 변경하자 수십 개 외부 클래스 컴파일 에러 | 외부 클래스가 특정 객체의 내부 컬렉션 자료구조를 직접 참조 | 자료구조를 감추고 반복자(Iterator) 또는 불변 리스트(UnmodifiableList)만 반환 | 내부 구현 변경의 파급 효과 완전 격리 |

## 내 의견
- [롬복(@Data)의 무분별한 사용이 낳은 정보은닉 파괴] 엔티티 클래스에 무심코 @Data나 @Setter 어노테이션을 붙여 모든 내부 상태를 외부로 노출하고, 서비스 레이어에서 setter를 난사해 상태를 변경하는 절차지향적 코드가 만연 → 나라면: 도메인 엔티티에서 setter 사용을 전면 금지하고, 의미 있는 비즈니스 행위 메서드(예: cancelOrder, changeAddress)만을 public으로 노출하며, 린트 검사로 getter의 비즈니스 판단 로직 악용 차단
