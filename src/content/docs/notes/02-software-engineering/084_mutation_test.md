## 답안 골격
```text
[뮤테이션 테스트] ◀━━ 머리: Ⅶ 내 의견 (단순 커버리지 맹신 탈피와 PITest 기반 테스트 스위트 유효성 검증 체계 도입)
 ┃
 ┣━ Ⅰ 개요 ───── 코드 커버리지(100%)의 결함 검출 맹점 극복 → 인위적 결함 주입을 통한 테스트 스위트 평가
 ┣━ Ⅱ 특징 ───── 테스트를 테스트하는 기법(Fault-based) · 2대 가설 기반 · 뮤테이션 점수 산출
 ┣━ Ⅲ 구조 ───── 원본 코드 / 뮤테이션 연산자(산술, 조건, 관계 교체) / 변종(Mutant) / 테스트 스위트 / 살해율
 ┣━ Ⅳ 흐름 ───── 소스코드 변종 생성 → 기존 테스트 스위트 실행 → 테스트 실패 여부 확인(Kill/Survive) → 뮤테이션 점수 계산
 ┣━ Ⅴ 비교 ───── 살해된 뮤턴트(Killed, 테스트 우수) vs 생존한 뮤턴트(Survived, 테스트 누락) vs 동등 뮤턴트(Equivalent, 무해)
 ┗━ Ⅵ 실무 ───── 변종 생성 폭증으로 인한 빌드 시간 과다 / 차등 뮤테이션(PR 변경분 대상) 및 PITest 적용
```
- 필수 키워드: 뮤테이션 테스트 · 결함 주입 · 변종(Mutant) · 뮤테이션 연산자 · 살해(Killed) · 동등 뮤턴트 · 뮤테이션 점수
- 배점 전략: 10점 = Ⅰ 정의 및 2대 가설 → Ⅲ 뮤테이션 테스트 수행 메커니즘 도식 → 산출 공식 / 25점 = Ⅰ~Ⅶ 전개, 133회 기출 연산자 종류 및 동등 뮤턴트 판별의 공학적 한계와 극복 방안
- 기출: 133회 1교시 2번 `소프트웨어 테스트 유형 중 뮤테이션 테스트(Mutation Test)` → Ⅰ~Ⅴ

## 한 줄 본질
- 코드 커버리지가 100%여도 단언문(Assertion)이 없으면 결함을 전혀 잡지 못하는 가짜 테스트 병목 → 소스코드에 인위적인 문법 결함(Mutant)을 주입한 뒤 테스트가 이를 실패(Kill)시키는지 측정 → 테스트 케이스의 실질적 결함 검출 능력 정량화 / 수천 개 변종 실행에 따른 막대한 연산 비용

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               뮤테이션 테스트 (Mutation Test) 동작 절차           |
+-------------------------------------------------------------------+
| [ 원본 코드 : if (a > b) return a; ]                              |
|                    |                                              |
|                    v (뮤테이션 연산자 적용: 관계 연산자 교체)     |
| [ 변종 코드 (Mutant) : if (a >= b) return a; ]                    |
|                    |                                              |
|                    v (기존 단위 테스트 스위트 실행)               |
|         +----------+----------+                                   |
|         |                     |                                   |
|         v (테스트 실패!)      v (테스트 통과?)                    |
|    [ Killed (살해) ]     [ Survived (생존) ]                      |
|    - 테스트가 결함 탐지  - 테스트가 결함을 못 잡음 (테스트 부실) |
|    - 우수한 테스트 스위트- 새로운 Assertion 추가 필요             |
+-------------------------------------------------------------------+
  * 뮤테이션 점수 = (살해된 변종 수) / (전체 변종 수 - 동등 변종 수) * 100
```

## 핵심 용어
- 동등 뮤턴트(Equivalent Mutant): 소스코드의 문법은 바뀌었으나 프로그램의 의미적 실행 결과는 원본과 동일하여, 어떤 테스트 케이스로도 절대 살해(Kill)할 수 없는 변종
- 유능한 프로그래머 가설: 프로그래머가 작성한 코드는 대개 정답에 매우 가까우며, 발생하는 버그는 사소한 구문이나 연산자 실수라는 전제

## 핵심 통찰
- 라인 커버리지(Line Coverage)는 단순히 "해당 줄을 실행했는가"만 알려줄 뿐 "그 줄의 결과가 올바른지 검증했는가"를 보장하지 못하므로, 이를 검증하는 유일한 도구가 뮤테이션 테스팅임
- 살충제 패러독스를 깨뜨리는 가장 강력한 수학적 기법이며, 생존한 뮤턴트(Survived)를 분석하면 개발자가 미처 생각하지 못한 경계 조건의 엣지 케이스를 정확히 찾아낼 수 있음
- 전체 소스코드를 대상으로 뮤테이션 테스트를 돌리면 수 시간이 걸리므로, git diff를 통해 이번 PR에서 변경된 핵심 비즈니스 로직에만 선별 실행하는 것이 실무 표준임

## 이웃 토픽과 구분
- 뮤테이션 테스트 vs 카오스 엔지니어링: 뮤테이션 테스트 = '단위/코드 레벨'에서 연산자를 바꾸어 테스트 케이스 품질 평가 / 카오스 엔지니어링 = '운영/인프라 레벨'에서 서버나 네트워크를 죽여 시스템 회복 탄력성 평가

## 문제·원인·대책
- 사례: 133회 기출 테스트 커버리지 95% 달성 후 운영 배포 시 부등호 오류로 대형 정산 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 테스트 케이스는 통과했으나 `>`가 `>=`로 잘못 코딩되어 정산 금액 중복 지급 | 테스트 코드 내에 assert 검증 없이 단순 메서드 호출만 수행한 껍데기 테스트 | CI 파이프라인에 PITest 도입 및 뮤테이션 점수 80% 이상 게이트 설정 | 단언문 누락 무의미한 테스트 케이스 100% 색출 |
| 뮤테이션 테스트 실행 시간이 12시간 소요되어 배포 파이프라인 마비 | 수만 개 변종을 단일 스레드로 전수 실행한 비효율 | 바이트코드 단위 변조, 멀티코어 병렬화 및 변경된 클래스 타겟팅 | 뮤테이션 분석 시간 12시간에서 10분으로 단축 |

## 이렇게 출제된다
- 제133회 1교시 2번: "소프트웨어 테스트 유형 중 뮤테이션 테스트(Mutation Test)" → 요구 포인트: 뮤테이션 테스트 개념 + 2대 가설(유능한 프로그래머, 결합 효과) + 수행 절차 및 뮤테이션 점수 산출 공식

## 내 의견
- [코드 커버리지 100%라는 허상에 안주하는 테스트 문화] 경영진에게 보여주기 위해 assert 한 줄 없이 함수만 호출하여 커버리지 수치만 채우는 가짜 테스트 관행 척결 시급 → 나라면: 라인 커버리지 단독 지표를 폐지하고 '뮤테이션 살해율(Mutation Score)'을 핵심 품질 지표로 격상하며, 핵심 결제·계산 모듈에 생존 뮤턴트 0건을 통과해야만 릴리스를 허용하는 엄격한 테스트 신뢰성 체계 구축
