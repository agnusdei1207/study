## 한 줄 본질
- 프로젝트 참여자마다 요구사항을 제각각 형식으로 기술하여 소통이 꼬이고 검수 기준이 모호해지는 계약 분쟁 병목 → 소프트웨어가 수행해야 할 기능과 제약조건을 체계적으로 서술하도록 표준화된 목차와 품질 기준을 제공하는 국제 표준 지침 / 문서 작성 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  IEEE 830 표준 SRS 목차 구조 및 8대 우수 특성           |
+-------------------------------------------------------------------------+
|  [ IEEE 830 표준 목차 구조 ]                                            |
|  1. 서론 (Introduction)                                                 |
|     - 목적, 범위, 정의 및 약어, 참조 문서, 전체 개요                     |
|  2. 전반적 설명 (Overall Description)                                   |
|     - 제품 조망, 제품 기능, 사용자 특성, 일반 제약조건, 가정 및 의존성 |
|  3. 세부 요구사항 (Specific Requirements) (가장 중요)                    |
|     - 외부 인터페이스 요구사항 (사용자, HW, SW, 통신)                    |
|     - 기능적 요구사항 (상세 입력, 처리, 출력)                            |
|     - 성능 요구사항, 논리적 DB 요구사항, 설계 제약, 품질 속성(보안 등)  |
|                                                                         |
|  [ 우수한 SRS가 갖추어야 할 8대 품질 특성 ]                             |
|    1. 정확성 (Correct)       2. 명확성 (Unambiguous)                     |
|    3. 완전성 (Complete)      4. 일관성 (Consistent)                      |
|    5. 중요도/안정성 순위화   6. 검증 가능성 (Verifiable)                 |
|    7. 수정 가능성 (Modifiable) 8. 추적 가능성 (Traceable)                |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 검증 가능성(Verifiable): 명세된 모든 요구사항에 대해, 시스템이 해당 요구사항을 충족했는지 여부를 기계나 인간이 유한하고 비용 효과적인 테스트로 입증할 수 있는 성질
- 추적 가능성(Traceable): 각 요구사항의 출처(비즈니스 니즈)가 어디인지 역방향으로 추적 가능하고, 해당 요구사항이 어떤 설계 모듈과 테스트 케이스로 구현되었는지 정방향으로 추적 가능한 성질

## 핵심 통찰
- IEEE 830의 가장 핵심적인 규칙은 "검증 가능하지 않은 요구사항은 요구사항이 아니다"라는 점이며, "사용하기 쉬워야 한다"는 비문(Unverifiable)이고 "신규 사용자가 도움말 없이 3분 이내 과업을 완료해야 한다"가 올바른 명세임
- IEEE 830 표준은 1998년 제정된 이후 널리 사용되었으나, 현재는 시스템 공학 표준(IEEE 12207, IEEE 1233 등)과 통합된 "ISO/IEC/IEEE 29148" 표준으로 공식 대체(Superseded)되었음
- 방대한 SRS를 작성하더라도 정기적인 베이스라인(Baseline) 통제와 형상관리가 수반되지 않으면, 개발 도중 발생하는 수많은 변경 요청으로 인해 문서는 첫 달 만에 쓰레기가 됨

## 이웃 토픽과 구분
- IEEE 830 SRS vs 사용자 스토리(User Story): IEEE 830 = 계약적 구속력을 갖는 방대하고 정형화된 시스템 공학 명세서 / 사용자 스토리 = 대화와 협업을 촉진하기 위한 카드 한 장 크기의 민첩한 요구사항 메모

## 문제·원인·대책
- 적용 상황: 대규모 공공 행정 시스템 구축 사업 요구사항 정의 단계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 검수 시점에 발주자가 "화면이 편리하지 않다"며 주관적 불만을 제기하고 인수 거부 | SRS에 "사용자 편의성을 극대화한다"는 모호하고 검증 불가능한 문장 명세 | IEEE 830 검증가능성 원칙에 따라 정량적 사용성 지표(클릭 수, 완수율)로 재명세 | 주관적 해석 배제 및 명확한 검수 기준 확립 |
| 설계 변경 시 해당 기능이 어떤 테스트 케이스와 연관되어 있는지 몰라 결함 전파 | 요구사항 고유 식별자(ID) 부여 및 요구사항 추적 매트릭스(RTM) 관리 부재 | 요구사항마다 고유 번호(REQ-001)를 부여하고 WBS, 설계서, 테스트 케이스 1:1 매핑 | 변경 영향도 분석 시간 80% 단축 및 누락 방지 |
