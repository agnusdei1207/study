## 답안 골격
```text
[유스케이스 다이어그램] ◀━━ 머리: Ⅶ 내 의견 (포함·확장 관계의 명확한 정의와 유스케이스 명세서와의 1:1 동기화)
 ┃
 ┣━ Ⅰ 개요 ───── 시스템 내부 구현 이전 사용자 관점의 기능적 요구사항과 경계 정의
 ┣━ Ⅱ 특징 ───── 액터 중심 관점 · 시스템 경계(Boundary) 설정 · 관계의 다형성(연관, 포함, 확장, 일반화)
 ┣━ Ⅲ 구조 ───── 시스템(System Boundary) · 액터(Primary/Secondary) · 유스케이스(타원) · 관계선
 ┣━ Ⅳ 흐름 ───── ① 사용자/외부시스템 액터 식별 → ② 목표 기반 유스케이스 도출 → ③ 관계 정의 → ④ 다이어그램 작성
 ┣━ Ⅴ 비교 ───── 포함 관계(<<include>>, 필수 선행) vs 확장 관계(<<extend>>, 조건부 선택)
 ┗━ Ⅵ 실무 ───── 포함/확장 관계 오용으로 인한 설계 혼선 / 베이스 유스케이스와 확장점(Extension Point) 분리
```
- 필수 키워드: 시스템 경계 · 액터(Actor) · 유스케이스 · 연관(Association) · <<include>> · <<extend>> · 유스케이스 명세서
- 배점 전략: 10점 = Ⅲ 4대 구성요소 표기법 도식 → Ⅴ 포함/확장 관계 비교 / 25점 = Ⅰ~Ⅶ 전개, 122회/137회 기출 시나리오 기반 다이어그램 작성 실습
- 기출: 137회 4교시 `행위 다이어그램 3종(활동, 상태, 유스케이스)` → Ⅰ·Ⅲ·Ⅴ / 122회 3교시 `주문 시스템 Use Case Diagram 작성` → Ⅲ·Ⅳ·Ⅵ

## 한 줄 본질
- 기술 용어로 가득 찬 개발자 중심 설계로 인해 실제 발주자와 사용자의 기능 요구사항이 왜곡되는 병목 → 시스템 경계 안팎에서 사용자가 시스템을 통해 달성하려는 목표를 액터와 유스케이스의 표준 시각 관계로 정의 → 시스템 범위(Scope) 명확화 및 인수 기준 확립 / 세부 처리 절차 표현 불가 대가

## 핵심 그림
```text
  [ Actor ]                    +--------------------------------------------+
(Primary User)                 | System Boundary                            |
      |                        |                                            |
      +------- (Association) -------> ( Use Case: 주문하기 )                |
                               |              |                             |
                               |         <<include>> (필수)                 |
                               |              v                             |
                               |      ( Use Case: 결제하기 )                |
                               |              ^                             |
                               |         <<extend>> (조건부: 쿠폰보유 시)   |
                               |              |                             |
                               |      ( Use Case: 쿠폰할인적용 )            |
                               +--------------------------------------------+
```

## 핵심 용어
- 포함 관계(<<include>>): 하나의 유스케이스를 수행할 때 공통으로 반드시 실행되어야 하는 하위 유스케이스를 재사용하는 필수 관계
- 확장 관계(<<extend>>): 특정 조건(확장점)을 만족할 때만 기본 유스케이스의 흐름에 부가적인 동작을 삽입하는 선택적 관계

## 핵심 통찰
- 유스케이스는 단순한 UI 버튼 클릭이나 함수 호출 단위가 아니라, 사용자가 의미 있는 비즈니스 가치(예: '도서 주문 완료')를 달성하는 완결된 사건 단위여야 함
- <<include>>는 화살표가 '부모 → 자식(포함되는 쪽)'으로 향하지만, <<extend>>는 '자식(확장 기능) → 부모(기본 기능)'로 화살표가 향하므로 방향 혼동이 빈발함
- 다이어그램 자체보다 각 유스케이스 내부의 정상 흐름(Basic Flow)과 대안 흐름(Alternative Flow)을 기록한 '유스케이스 명세서'가 실제 개발의 핵심 계약서임

## 이웃 토픽과 구분
- 유스케이스 다이어그램 vs 시퀀스 다이어그램: 유스케이스 = 사용자의 목표와 시스템의 기능 범위 정의(What) / 시퀀스 = 그 유스케이스를 달성하기 위한 객체 간 시간 순서 협력(How)

## 문제·원인·대책
- 사례: 122회 기출 온라인 주문 시스템 유스케이스 모델링 오류
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 포함과 확장의 화살표 방향 반대 표기로 개발팀 혼선 | include/extend 관계의 의존성 방향성 이해 부족 | 포함(기본->하위), 확장(확장기능->기본 기능의 확장점) 표준 템플릿 강제 | 모델링 표기법 오류 원천 제거 |
| 다이어그램에 화면 단위 세부 클릭 동작이 수백 개 타원으로 난립 | 유스케이스의 크기(Granularity)를 비즈니스 목표가 아닌 UI 조작 단위로 쪼갬 | 알리스터 코번(Cockburn)의 '바다 레벨(사용자 목표 수준)' 크기 기준 적용 | 핵심 비즈니스 유스케이스 20개 내외로 집중화 |
