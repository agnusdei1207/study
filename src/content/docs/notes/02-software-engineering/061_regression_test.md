```text
[회귀테스트] ◀━━ 머리: Ⅶ 내 의견 (영향도 분석 기반 선택적 회귀 테스트와 CI/CD 자동화 파이프라인 통합)
 ┃
 ┣━ Ⅰ 개요 ───── 기능 수정이나 결함 패치 후 기존 정상 기능의 의도치 않은 파괴(부작용) 검증
 ┣━ Ⅱ 특징 ───── 반복적 수행 · 자동화 필수 · 수정 영역 외 사이드이펙트(Side Effect) 탐지
 ┣━ Ⅲ 구조 ───── Retest-All(전수 실행) vs Regression Test Selection(선택) vs Test Case Prioritization(우선순위화)
 ┣━ Ⅳ 흐름 ───── 코드 변경 발생 → 영향도 분석(Impact Analysis) → 회귀 테스트 스위트 선정 → 자동 실행 → 결함 보고
 ┣━ Ⅴ 비교 ───── 전수 재시험(Retest All, 완벽성, 고비용) vs 선택적 재시험(RTS, 경제성, 누락 위험)
 ┗━ Ⅵ 실무 ───── 테스트 케이스 누적으로 인한 빌드 시간 폭증 / 테스트 영향도 분석(TIA) 도구 도입
```
- 필수 키워드: 사이드이펙트 · Retest-All · 회귀 테스트 선택(RTS) · 테스트 케이스 우선순위화(TCP) · 영향도 분석 · CI/CD 자동화
- 배점 전략: 10점 = Ⅰ 목적 → Ⅲ 3대 회귀 테스트 전략 도식 → Ⅴ 전수 vs 선택 비교 / 25점 = Ⅰ~Ⅶ 전개, 테스트 영향도 분석(TIA) 및 위험 기반 우선순위화 기법
- 기출: 129회 4교시 `정보시스템 개발 및 운영 단계의 소프트웨어 테스트` (회귀 테스트 전략 문맥) → Ⅰ·Ⅲ·Ⅵ / 105회 1교시 `회귀테스트` → Ⅰ~Ⅴ

## 한 줄 본질
- 버그를 하나 고치거나 새 기능을 추가했을 때 멀쩡하던 기존 10개 기능에 연쇄 부작용(Regression Defect)이 터지는 병목 → 이전에 통과했던 테스트 케이스들을 코드가 변경될 때마다 다시 실행하여 기존 동작의 무결성을 지속 입증 → 소프트웨어 안정적 진화 보장 / 테스트 케이스 누적에 따른 빌드·실행 시간 폭증 대가

## 핵심 그림
```text
[ 소프트웨어 변경 발생 (Bug Fix / Feature Add) ]
                        |
                        v
         [ 3대 회귀 테스트(Regression Test) 전략 ]
+---------------------+---------------------+---------------------+
| 1. Retest-All       | 2. RTS (Selection)  | 3. TCP (Priority)   |
+---------------------+---------------------+---------------------+
| 기존 모든 테스트    | 변경된 코드에 영향  | 위험도와 비즈니스   |
| 케이스 100% 재실행  | 받는 테스트만 선별  | 중요도 높은 순서로  |
| (안전성 최고, 고비용)| (효율적, 분석 도구) | 제한 시간 내 실행   |
+---------------------+---------------------+---------------------+
                        |
                        v
          [ CI 파이프라인 자동 실행 -> 회귀 결함 0건 검증 ]
```

## 핵심 용어
- 회귀 결함(Regression Defect): 새로운 코드를 추가하거나 기존 코드를 리팩토링/패치한 결과로 인해, 이전에 정상 작동하던 기능이 고장 나는 현상
- 테스트 영향도 분석(TIA, Test Impact Analysis): 코드 커밋 시 변경된 소스코드 라인과 함수를 정적/동적으로 추적하여, 오직 해당 변경과 관련된 테스트 케이스만을 지능적으로 골라내는 기술

## 핵심 통찰
- 시스템이 성장할수록 테스트 케이스의 수는 수천~수만 개로 불어나므로, 매 커밋마다 모든 테스트를 돌리는 'Retest-All'은 결국 배포 속도를 마비시키는 병목이 됨
- 따라서 주간/릴리스 단위로는 Retest-All을 돌리더라도, 일상의 PR 단위에서는 영향도 분석(RTS)과 빈번한 결함 발생 구간을 앞세우는 우선순위화(TCP)가 필수적임
- 완벽한 회귀 테스트는 빠르고 격리된 '단위 테스트'가 80% 이상을 차지해야 하며, 느린 UI/E2E 테스트로만 회귀 테스트를 구성하면 회귀 검증이 불가능해짐

## 이웃 토픽과 구분
- 회귀 테스트 vs 재테스트(Retest): 재테스트 = 방금 수정한 특정 버그가 제대로 고쳐졌는지 확인 / 회귀 테스트 = 그 버그를 고치느라 다른 정상 기능이 깨지지 않았는지 주변 확인

## 문제·원인·대책
- 사례: 129회 기출 결함 패치 후 운영 환경에서 무관한 결제 모듈이 중단된 회귀 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 포인트 조회 버그 수정 커밋이 운영 배포된 후 신용카드 결제 모듈 다운 | 수정 모듈과 결제 모듈 간의 숨겨진 의존성에 대한 회귀 검증 누락 | 핵심 비즈니스 트랜잭션 대상 스모크/회귀 테스트 자동화 스위트 구축 | 커밋 시 핵심 기능 파괴 100% 사전 탐지 |
| 회귀 테스트 스위트 실행 시간이 6시간으로 늘어나 일일 배포 불가 | 불필요한 슬립(Sleep)과 느린 브라우저 E2E 테스트의 무차별 누적 | 테스트 병렬화(Parallelization) 및 단위/통합 테스트 중심 피라미드 재편 | 회귀 테스트 실행 시간 6시간에서 15분으로 단축 |
