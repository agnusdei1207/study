## 답안 골격
```text
[리스트] ◀━━ 머리: Ⅶ 내 의견 (접근 빈도와 데이터 변경 빈도에 따른 순차/연결 리스트 최적 선정)
 ┃
 ┣━ Ⅰ 개요 ───── 순서가 있는 원소들의 모임 관리 → 물리적 연속 저장과 논리적 링크 연결로 구현
 ┣━ Ⅱ 특징 ───── 순서 보장 · 중복 허용 · 동적 크기 조절 가능 · 인덱스 또는 포인터 기반 탐색
 ┣━ Ⅲ 구조 ───── 순차 리스트(ArrayList, 배열 기반) vs 연결 리스트(LinkedList, 노드+포인터 기반)
 ┣━ Ⅳ 흐름 ───── 순차(인덱스 산술 O(1) 조회, 삽입/삭제 시 O(N) 시프트) / 연결(포인터 순차 탐색 O(N), 삽입/삭제 포인터 교체 O(1))
 ┣━ Ⅴ 비교 ───── 순차 리스트(Array List) vs 단순 연결 리스트 vs 이중 연결 리스트 vs 원형 연결 리스트
 ┗━ Ⅵ 실무 ───── 중간 삽입/삭제 빈번 시 배열 복사 오버헤드 / 가비지 컬렉션 및 캐시 지역성(Locality)
```
- 필수 키워드: 선형 자료구조 · 순차 리스트(ArrayList) · 연결 리스트(LinkedList) · 시간복잡도 · 캐시 지역성 · 포인터 오버헤드
- 배점 전략: 10점 = Ⅲ 두 구조의 메모리 배치 도식 → Ⅴ 시간복잡도 비교표 / 25점 = Ⅰ~Ⅶ 전개, CPU 캐시 라인과 현대 하드웨어 관점의 실무 벤치마크 통찰
- 기출: 132회 2교시 `선형 자료 구조인 스택, 큐, 리스트의 자료 입출력 원리` → Ⅰ·Ⅲ·Ⅳ / 125회 1교시 `선형과 비선형 자료구조` → Ⅰ·Ⅴ

## 한 줄 본질
- 연속된 메모리 할당의 고정 크기 한계와 중간 원소 삽입 시 발생하는 대량 데이터 이동 병목 → 데이터와 다음 노드의 주소 포인터를 함께 저장하는 연결 구조를 통해 동적으로 메모리를 할당하고 O(1) 포인터 연결로 삽입/삭제 해결 → 유연한 크기 관리 / 인덱스 임의 접근(Random Access) 불가 및 포인터 메모리 낭비 대가

## 핵심 그림
```text
[ 순차 리스트 (ArrayList): 물리적 연속 메모리 ]
  Index:   [ 0 ]   [ 1 ]   [ 2 ]   [ 3 ]     -> 임의 접근: O(1)
  Data :  | 10  | | 20  | | 30  | | 40  |     -> 중간 삽입 시: 우측 원소들 전부 Shift (O(N))

[ 연결 리스트 (LinkedList): 포인터 기반 분산 메모리 ]
  Head -> [ Data: 10 | Next ] -> [ Data: 20 | Next ] -> [ Data: 30 | NULL ]
          (노드 동적 할당)        (임의 접근: O(N) 순차 탐색, 삽입: 포인터 2개 변경 O(1))
```

## 핵심 용어
- 임의 접근(Random Access): 시작 주소와 인덱스 오프셋 연산을 통해 어느 위치의 원소든 O(1)의 일정한 시간에 직접 읽어내는 성질
- 캐시 지역성(Cache Locality): CPU가 메모리를 읽을 때 인접한 데이터를 캐시 라인(64바이트) 단위로 미리 가져오는 성질(ArrayList가 LinkedList보다 압도적으로 유리한 근거)

## 핵심 통찰
- 교과서적으로는 '삽입/삭제가 많으면 LinkedList가 빠르다'고 배우지만, 실제 현대 CPU에서는 캐시 미스(Cache Miss) 때문에 10만 건 이하에서는 대부분 ArrayList가 LinkedList보다 훨씬 빠름
- LinkedList는 노드마다 포인터 변수(64비트 시스템에서 8바이트)를 추가로 저장하므로 4바이트 정수를 저장할 때 실제로는 12~24바이트를 소모하여 메모리 단편화를 유발함
- 이중 연결 리스트(Doubly LinkedList)는 양방향 순회가 가능하고 삭제 시 선행 노드 탐색 비용이 없으나, 포인터 관리가 복잡하여 메모리 누수나 순환 참조에 주의해야 함

## 이웃 토픽과 구분
- 배열(Array) vs 연결 리스트(LinkedList): 배열 = 정적 크기, 연속 메모리, O(1) 조회 / 연결 리스트 = 동적 크기, 비연속 노드, O(N) 조회

## 문제·원인·대책
- 사례: 132회 기출 대규모 이벤트 대기열 관리 모듈의 리스트 자료구조 선정 오류
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 수만 건의 중간 데이터 삭제 시 애플리케이션 지연 급증 | ArrayList 사용으로 인한 반복적 System.arraycopy 메모리 시프트 | 삽입/삭제 위치가 고정된 경우 LinkedList 또는 링 버퍼(Circular Buffer)로 전환 | 메모리 복사 병목 제거 및 O(1) 노드 삭제 달성 |
| 수십만 건의 대량 데이터 순회 시 CPU 사용률 100% 치솟음 | LinkedList 노드들의 힙 메모리 파편화로 인한 L1/L2 CPU 캐시 미스 폭증 | 메모리 연속성이 보장되는 ArrayList 또는 고정 블록 풀링 리스트 적용 | 공간 지역성 극대화로 순회 속도 5배 이상 개선 |

## 이렇게 출제된다
- 제132회 2교시 6번: "선형 자료 구조인 스택, 큐, 리스트의 자료 입출력 원리를 설명하시오." → 요구 포인트: 순차 리스트와 연결 리스트의 입출력 알고리즘 + 스택/큐와의 구조적 연계
- 제125회 1교시 4번: "선형 자료구조와 비선형 자료구조" → 요구 포인트: 선형 구조(배열, 리스트, 스택, 큐)와 비선형 구조(트리, 그래프)의 메모리 저장 및 탐색 특성 비교

## 내 의견
- [교과서 이론만 믿고 LinkedList를 남발하는 주니어 개발자] 삽입 삭제가 발생한다는 이유만으로 무조건 LinkedList를 선언하여 GC 압박과 CPU 캐시 낭비를 초래하는 코드 다수 발견 → 나라면: 기본 컬렉션으로 ArrayList를 기본 표준으로 삼고, 원소 개수가 백만 건 이상이며 중간 삽입/삭제 지점을 가리키는 반복자(Iterator)를 이미 보유하고 있는 특수 구간에만 LinkedList를 제한적으로 승인
