## 답안 골격
```text
[순차 다이어그램] ◀━━ 머리: Ⅶ 내 의견 (객체 간 메시지 시간 순서 모델링과 복합 프래그먼트(alt, loop)를 통한 동적 상호작용 검증)
 ┃
 ┣━ Ⅰ 개요 ───── 유스케이스 명세서의 정적 텍스트 한계 → 객체 간 주고받는 메시지의 시간적 흐름과 생명주기 시각화
 ┣━ Ⅱ 특징 ───── UML 상호작용(Interaction) 다이어그램 · 시간 순서(위→아래) 수직 정렬 · 객체 생명선 및 활성 구간 표현
 ┣━ Ⅲ 구조 ───── 액터 / 객체(Lifeline) / 활성 상자(Activation Box) / 메시지(동기, 비동기, 응답, 자체) / 복합 프래그먼트(Combined Fragment)
 ┣━ Ⅳ 흐름 ───── 객체 인스턴스 나열 → 메시지 발송(동기/비동기) → 활성화 구간 실행 → 조건 분기(alt/opt) 및 반복(loop) → 리턴 반환
 ┣━ Ⅴ 비교 ───── 순차 다이어그램(시간 순서 중심) vs 통신 다이어그램(Communication, 객체 간 링크 관계 중심)
 ┗━ Ⅵ 실무 ───── 복잡한 비즈니스 로직으로 인한 다이어그램 비대화 / 프래그먼트(ref) 분할 및 PlantUML 코드화 관리
```
- 필수 키워드: 순차 다이어그램 · 시퀀스 다이어그램 · 생명선(Lifeline) · 실행 명세(Activation) · 동기/비동기 메시지 · 복합 프래그먼트(alt, opt, loop, ref)
- 배점 전략: 10점 = Ⅰ 순차 다이어그램 정의 및 목적 → Ⅲ 5대 핵심 표기법 기호 도식 → Ⅴ 순차 vs 통신 다이어그램 비교 / 25점 = Ⅰ~Ⅶ 전개, 127회 기출 순차 다이어그램의 개념, 구성요소, 복합 프래그먼트 4대 연산자(alt, opt, loop, par), 및 REST API 설계 모델링 적용
- 기출: 127회 1교시 `순차 다이어그램(Sequence Diagram)` → Ⅰ~Ⅵ

## 한 줄 본질
- 유스케이스 시나리오를 코드로 구현할 때 "어떤 객체가 어떤 순서로 메서드를 호출하고 응답을 기다리는지" 명확히 알 수 없는 설계 불투명성 병목 → 객체들을 가로축에 나열하고 시간의 흐름을 세로축(위에서 아래로)으로 정의하여 동기/비동기 메시지 교환을 표현하는 UML 상호작용 다이어그램 / 다이어그램 복잡도 폭증 제어 필요

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  순차 다이어그램(Sequence Diagram) 핵심 표기법           |
+-------------------------------------------------------------------------+
|  [ :Client ]              [ :OrderService ]         [ :PaymentGateway ] |
|      │                           │                           │          |
|      │ 1: createOrder()          │                           │          |
|      │ ─────────────────────────>│ (활성 상자)               │          |
|      │                           │                           │          |
|      │                           │ 2: requestPayment()       │          |
|      │                           │ ─────────────────────────>│          |
|      │                           │                           │          |
|  +───[ alt : 결제 결과 분기 ]─────┼───────────────────────────┼────────+ |
|  │ [결제 성공]                   │                           │        │ |
|  │   │                           │ 3: 200 OK (승인번호)      │        │ |
|  │   │                           │ < - - - - - - - - - - - - │        │ |
|  │   │ 4: orderSuccess()         │                           │        │ |
|  │   │ < - - - - - - - - - - - - │                           │        │ |
|  ├───[ else : 잔액 부족 ]─────────┼───────────────────────────┼────────┤ |
|  │   │                           │ 5: 400 Fail (에러코드)    │        │ |
|  │   │                           │ < - - - - - - - - - - - - │        │ |
|  │   │ 6: throw PaymentException │                           │        │ |
|  │   │ < - - - - - - - - - - - - │                           │        │ |
|  +───┴───────────────────────────┴───────────────────────────┴────────+ |
|      │                           │                           │          |
|      v                           v                           v          |
|    시간의 흐름 (위에서 아래로 순차적 진행)                               |
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 생명선(Lifeline)과 활성 구간(Activation): 생명선은 객체가 시스템 내에 존재하는 시간 경과를 나타내는 수직 점선이며, 활성 구간은 객체가 실제 연산을 수행 중이거나 제어권을 쥐고 있음을 나타내는 좁고 긴 직사각형
- 복합 프래그먼트(Combined Fragment): UML 2.0에서 도입된 구조화 블록으로, `alt`(조건 분기 if-else), `opt`(선택 실행 if), `loop`(반복 for/while), `par`(병렬 실행), `ref`(외부 다이어그램 참조) 등을 통해 복잡한 제어 흐름을 표현

## 핵심 통찰
- 순차 다이어그램은 클래스 다이어그램(정적 구조)과 유스케이스 다이어그램(기능 요구) 사이를 잇는 "동적 설계의 허리(Backbone)" 역할을 수행함
- 실무에서 개발자들이 백엔드 API를 구현하기 전에 API 게이트웨이, 인증 서버, 비즈니스 서비스, DB 간의 상호작용 순서를 순차 다이어그램으로 먼저 합의하면, 인터페이스 규격 불일치로 인한 결함의 80%를 설계 단계에서 걸러낼 수 있음
- 하나의 시퀀스 다이어그램에 모든 예외 케이스와 반복문을 다 넣으려 하면 가독성이 완전히 파괴되므로, 정상 경로(Happy Path)를 기본으로 하고 예외 분기는 `ref` 프래그먼트로 별도 분리해야 함

## 이웃 토픽과 구분
- 순차 다이어그램 vs 통신 다이어그램: 순차 다이어그램 = 메시지의 '시간적 순서와 생명주기'를 직관적으로 파악 / 통신 다이어그램 = 객체들 간의 '공간적 네트워크 연결 관계와 링크'를 직관적으로 파악

## 문제·원인·대책
- 적용 상황: 마이크로서비스 간 분산 결제 및 재고 차감 트랜잭션 설계
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
