## 한 줄 본질
- 클라우드 대기업(AWS 등)이 오픈소스 프로젝트를 가져다 막대한 SaaS 수익을 올리면서 오픈소스 메인테이너에게 기여하지 않는 시장 실패 병목 → 상업적 호스팅 서비스 제공 시 관리 인프라 소스까지 공개하도록 강제(SSPL)하거나 일정 기간 상업적 무료 사용을 제한(BSL) → 원작자의 비즈니스 생존권 확보 / 오픈소스 생태계의 분열과 자유 소프트웨어 정의(OSI) 충돌 대가

## 핵심 그림
```text
[ 오픈소스 라이선스 진화 계보 ]
  1세대: 완전 개방 (Permissive)       ---> MIT, BSD, Apache 2.0
         (소스 공개 의무 없음, 상용화 자유)
  2세대: 카피레프트 (Copyleft)         ---> GPL v2/v3, LGPL
         (수정 및 파생 저작물 소스 공개 의무)
  3세대: 네트워크 대응 (Network)       ---> AGPL v3
         (배포 없이 SaaS 형태로 서비스해도 소스 공개 의무)
  4세대: 클라우드 방어 (Source-Available) -> SSPL, BSL (비OSI 승인)
         (경쟁적 클라우드 서비스 제공 전면 금지 또는 관리 인프라 전면 공개)
```

## 핵심 용어
- BSL(Business Source License): 소스코드는 누구나 볼 수 있고 비상업적/개발용으로는 무료이지만, 운영 환경이나 특정 규모 이상의 상업 서비스에 사용할 때는 유료 라이선스를 요구하는 라이선스(일정 기간 후 GPL/Apache로 자동 전환)
- OSI(Open Source Initiative): 오픈소스 정의(OSD) 10대 조항을 심사하여 공식 오픈소스 라이선스 여부를 인증하는 국제 비영리 단체(SSPL과 BSL은 OSI 승인을 받지 못함)

## 핵심 통찰
- SSPL이나 BSL을 채택한 소프트웨어는 법적으로 '오픈소스(Open Source)'가 아니라 '소스 공개형 상용 소프트웨어(Source-Available Software)'로 분류됨
- 기업이 단순히 사내 업무용으로 MongoDB나 Redis를 설치해 사용하는 것은 SSPL 위반이 아니며, 이를 외부에 '서비스로서의 DB(DBaaS)' 형태로 재판매할 때만 위반이 됨
- 라이선스 폐쇄화에 반발한 커뮤니티는 즉시 오픈소스 포크(Fork) 프로젝트(예: Elasticsearch → OpenSearch, Redis → Valkey)를 만들어 생태계를 양분함

## 이웃 토픽과 구분
- AGPL vs SSPL: AGPL = 해당 애플리케이션 자체의 수정 소스코드 공개 요구 / SSPL = 해당 애플리케이션을 호스팅하는 백업, 모니터링, 관리용 전체 인프라 코드 공개 요구

## 이렇게 출제된다
- 제134회 3교시 6번: "일부오픈소스라이선스가개방형(예: MIT,BSD등)에서폐쇄형(예: SSPL(ServerSide PublicLicense),BSL(BusinessSourceLicense)등)으로변화하고있다.이러한오픈소스 라이선스정책변경의배경및소프트웨어산업에미치는영향에대하여설명하시오." → 요구 포인트: 클라우드 CSP 무임승차 배경 + SSPL/BSL 메커니즘 + 오픈소스 산업 생태계 영향(포크, 거버넌스)
- 제122회 1교시 4번: "허용적 라이선스(Permissive License)와 카피레프트 라이선스(Copyleft License)" → 요구 포인트: 상업적 이용 및 소스 공개 의무를 기준으로 한 2대 진영 비교

## 내 의견
- [오픈소스 벤더의 배신에 당황하지 않는 엔터프라이즈 아키텍처] 특정 오픈소스의 인기에 취해 단일 벤더 소프트웨어에 아키텍처를 과도하게 밀착시켰다가 라이선스 변경 한 방에 기업 전체가 인질로 잡히는 사례 빈발 → 나라면: 오픈소스 도입 시 반드시 리눅스 재단이나 아파치 재단 같은 중립적 재단 산하 프로젝트인지 검토하고, 특정 벤더 독점 프로젝트는 인터페이스 추상화 계층(Adapter)을 두어 유사시 오픈 포크로 1주일 내 전환할 수 있는 출구 전략(Exit Strategy) 선행 수립
