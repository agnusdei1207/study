- 로깅, 트랜잭션, 보안 검증 같은 부가 기능 코드가 모든 비즈니스 클래스마다 중복 복사되어 코드를 오염시키는 병목 → 공통 횡단 관심사를 독립된 모듈(Aspect)로 떼어내고 런타임 프록시나 컴파일러로 핵심 로직에 자동 위빙 → 순수 비즈니스 로직 응집 및 유지보수 단일화 / 런타임 프록시 호출 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               AOP (관점 지향 프로그래밍)의 구조 및 위빙            |
+-------------------------------------------------------------------+
|   [ 핵심 관심사 (Core Concerns) ]        [ 횡단 관심사 (Cross-cutting) ]
|   +----------------------------+         +-----------------------+
|   | OrderService (주문 처리)   |         | 1. 트랜잭션 (@Transactional)|
|   | MemberService (회원 관리)  | <=====  | 2. 보안 인가 (@PreAuthorize) |
|   | PaymentService (결제 승인) | (Weave) | 3. 성능 측정 / 감사 로그 |
|   +----------------------------+         +-----------------------+
|                                                      |
|   +--------------------------------------------------v--------+
|   | 5대 핵심 개념 :                                           |
|   | * Aspect    : 횡단 관심사 모듈 (Advice + Pointcut)        |
|   | * Joinpoint : 적용 가능한 모든 실행 지점 (메서드 호출 등) |
|   | * Pointcut  : 실제 적용할 Joinpoint 선별 표현식           |
|   | * Advice    : 부가기능 본체 (Before / After / Around)     |
|   | * Weaving   : 핵심 코드에 Aspect를 끼워 넣는 행위         |
+---------------------------------------------------------------+
```

## 핵심 용어
- 횡단 관심사(Cross-cutting Concerns): 시스템의 여러 핵심 비즈니스 모듈 전반에 걸쳐 공통적이고 반복적으로 나타나는 부가 요구사항(보안, 트랜잭션, 로깅 등)
- 위빙(Weaving): 포인트컷에 의해 지정된 조인포인트에 어드바이스를 실제로 삽입하여 타깃 객체와 연결하는 과정

## 핵심 통찰
- AOP는 객체지향 프로그래밍(OOP)을 대체하는 기술이 아니라, OOP의 캡슐화로도 해결하기 힘든 전역적 중복 코드를 깔끔하게 도려내는 'OOP의 보완자'임
- Spring AOP는 기본적으로 JDK Dynamic Proxy 또는 CGLIB 기반의 '런타임 프록시' 방식을 쓰므로, 객체 내부에서 자기 자신의 다른 메서드를 호출하는 `this.method()` 호출 시 AOP가 동작하지 않음
- 성능이 극도로 민감하거나 메서드 외에 필드 접근, 생성자 호출까지 가로채야 하는 고난도 도메인에서는 AspectJ 컴파일 타임 위빙(CTW)을 선택해야 함

## 이웃 토픽과 구분
- AOP vs 인터셉터(Interceptor) / 필터(Filter): 필터/인터셉터 = HTTP 웹 요청/응답 계층에 국한된 처리 / AOP = 프레임워크나 HTTP 계층과 무관하게 서비스, 도메인, 리포지토리 전 계층의 순수 메서드 단위에 정밀 적용

## 문제·원인·대책
- 사례: 129회 기출 결제 승인 메서드 내에서 `@Transactional` 어노테이션이 무시되어 데이터 불일치 발생
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 동일 서비스 내 비트랜잭션 메서드가 트랜잭션 메서드 호출 시 롤백 실패 | Spring AOP 프록시를 거치지 않고 타깃 인스턴스 내부 직접 호출(Self-invocation) | 별도 서비스 클래스로 분리 추출하거나 트랜잭션 템플릿(TransactionTemplate) 사용 | 프록시 호출 보장 및 트랜잭션 롤백 100% 정상 작동 |

## 내 의견
