## 한 줄 본질
- 하나의 모듈 안에 서로 다른 이유로 변경되는 코드들이 뒤섞여 사소한 수정에도 사이드 이펙트가 전파되는 병목 → 모듈 내부의 구성요소들이 단 하나의 밀접한 목적만을 수행하도록 묶는 집중도 척도 / 과도한 분할 시 모듈 개수 폭증 및 호출 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------------------+
|                  모듈 응집도(Cohesion) 7단계 스펙트럼                  |
+-------------------------------------------------------------------------+
|  [ 높음 (Good) ]                                                        |
|     ▲   7. 기능적 (Functional)  : 단일 목적 달성을 위해 모든 요소 협력  |
|     │   6. 순차적 (Sequential)  : 한 요소의 출력이 다음 요소의 입력     |
|     │   5. 교환적 (Communicational): 동일한 입출력 데이터를 공유·처리   |
|     │   4. 절차적 (Procedural)  : 특정 순서에 따라 순차 실행            |
|     │   3. 시간적 (Temporal)    : 특정 시점(초기화, 종료)에 일괄 실행   |
|     │   2. 논리적 (Logical)     : 유사 성격 작업들을 한 모듈에 묶음     |
|     ▼   1. 우연적 (Coincidental): 아무런 관련 없는 작업들의 임의 집합   |
|  [ 낮음 (Bad) ]                                                         |
|                                                                         |
|  * 암기 팁: [기 - 순 - 교 - 절 - 시 - 논 - 우] (우연이 가장 낮고 기능이 최고)|
+-------------------------------------------------------------------------+
```

## 핵심 용어
- 기능적 응집도(Functional Cohesion): 모듈 내부의 모든 요소가 단 하나의 고유한 비즈니스 목적 또는 기능만을 수행하는 가장 이상적인 상태
- LCOM(Lack of Cohesion in Methods): 클래스 내 메서드들이 공유하는 인스턴스 필드의 비율을 측정하여 응집도 결여 수준을 정량화하는 객체지향 메트릭

## 핵심 통찰
- 응집도가 낮은 모듈은 여러 개발자가 동시에 같은 파일을 수정하게 만들어 형상관리 충돌(Git Conflict)과 회귀 결함의 주범이 됨
- 유틸리티 클래스(`CommonUtil`, `Helper`)는 작성하기 쉽다는 이유로 프로젝트 후반부로 갈수록 우연적·논리적 응집도로 전락하여 코드베이스를 오염시키는 "쓰레기통 클래스"가 되기 쉬움
- 객체지향의 SRP(Single Responsibility Principle)는 응집도를 클래스 레벨에서 구현한 원칙이며, MSA(Microservices Architecture)는 응집도를 서비스 배포 단위 레벨로 확장한 아키텍처임

## 이웃 토픽과 구분
- 응집도(Cohesion) vs 결합도(Coupling): 응집도 = 모듈 "내부" 요소 간의 집중도(높을수록 우수) / 결합도 = 모듈 "간" 상호 의존성(낮을수록 우수). 고응집·저결합(High Cohesion, Loose Coupling)이 소프트웨어 설계의 제1원칙

## 문제·원인·대책
- 적용 상황: 결제, 주문, 회원 알림 로직이 한 클래스에 누적된 레거시 백엔드
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 알림 문구 수정 후 결제 승인 기능이 멈추는 사이드 이펙트 장애 발생 | 단일 서비스 클래스 내에 무관한 비즈니스 책임들이 혼재(논리적/시간적 응집도) | 메서드 추출(Extract Method) 및 책임별 클래스 분리(SRP 적용) | 결제 모듈 수정 영향도 격리 및 안정적 배포 |
| 코드 분석 도구에서 특정 클래스의 LCOM 수치가 80% 이상으로 측정됨 | 클래스 내 인스턴스 변수들을 서로 다른 메서드 그룹이 따로 사용하는 분열 현상 | 연관 변수와 메서드를 묶어 별도 도메인 객체로 분할(Extract Class) | 모듈 내 결속력 강화 및 재사용성 향상 |
