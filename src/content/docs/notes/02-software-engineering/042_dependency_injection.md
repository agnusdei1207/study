 ┣━ Ⅰ 개요 ───── 객체 내부의 직접 생성(`new`)으로 인한 강한 결합 탈피 → 외부 컨테이너가 의존 객체 전달

 ┣━ Ⅲ 구조 ───── Client 객체 · Service 인터페이스 · Injector(IoC 컨테이너) · Concrete Service 구현체

## 한 줄 본질
- 객체가 자신이 사용할 구체 클래스를 내부에서 직접 `new` 연산자로 인스턴스화함으로써 발생하는 강한 결합과 테스트 불가 병목 → 객체는 추상 인터페이스에만 의존하고, 외부 IoC 컨테이너가 런타임에 실제 구현체를 주입 → 클래스 간 결합도 해소 및 단위 테스트 용이성 확보 / 런타임 리플렉션 오버헤드 대가

## 핵심 그림
```text
[ Bad: 직접 생성 (강한 결합) ]
  OrderService ---- ( new OracleDatabase() ) ----> OracleDatabase
  * DB를 MySQL로 바꾸려면 OrderService 소스코드를 직접 수정해야 함!

[ Good: 의존성 주입 (느슨한 결합) ]
  OrderService ---- ( 의존: 인터페이스 ) --------> << Database >>
       ^                                                 ^
       |                                                 |
  [ IoC Container ] -- ( 런타임 주입: MySQLDatabase ) ---+
```

## 핵심 용어
- IoC(Inversion of Control, 제어의 역전): 객체의 생성, 생명주기 관리, 메서드 호출의 제어권을 개발자 코드가 아닌 프레임워크 컨테이너가 가져가는 디자인 원칙
- DIP(Dependency Inversion Principle): 상위 수준 모듈은 하위 수준 모듈에 의존해서는 안 되며, 둘 모두 추상화(인터페이스)에 의존해야 한다는 SOLID 원칙

## 핵심 통찰
- 의존성 주입(DI)은 제어의 역전(IoC)을 달성하는 구체적인 소프트웨어 디자인 패턴 중 하나임
- 단위 테스트 시 가짜 객체(Mock/Stub)를 쉽게 꽂아 넣을 수 있는 테스트 용이성(Testability)이야말로 DI가 제공하는 가장 거대한 공학적 가치임
- 스프링에서 `@Autowired`를 필드에 직접 붙이는 필드 주입은 리플렉션 없이 순수 자바 코드로 테스트할 수 없고 불변성을 깨뜨리므로 실무 안티패턴으로 규정됨

## 이웃 토픽과 구분
- DI vs Service Locator: DI = 컨테이너가 객체에게 필요한 것을 밀어넣어 줌(Push) / Service Locator = 객체가 레지스트리에 가서 직접 필요한 것을 찾아옴(Pull, 결합도 잔존)

## 문제·원인·대책
- 사례: 124회 기출 대규모 스프링 부트 애플리케이션의 의존성 결합 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 스프링 컨테이너 기동 시 두 서비스 간 BeanCurrentlyInCreationException 발생 | A가 B를 주입받고 B가 A를 주입받는 순환 참조(Circular Dependency) 설계 | 생성자 주입 표준화 및 도메인 이벤트(ApplicationEvent) 기반 결합 분리 | 기동 시 순환 참조 원천 차단 및 단방향 의존성 확립 |
| 필드 주입 객체 단위 테스트 시 NullPointerException 발생 | 프레임워크 없이 순수 POJO 테스트 시 필드에 Mock 객체 주입 불가 | 필수 의존성을 `final` 키워드와 함께 생성자 주입(Lombok @RequiredArgsConstructor)으로 전면 교체 | 컴파일 타임에 누락된 의존성 검출 및 Mock 완벽 주입 |

## 내 의견
- [필드 주입의 달콤한 함정에 빠진 레거시 코드] `@Autowired` 한 줄이면 끝나니 편하다는 이유로 생성자 주입을 외면했다가, 10개 이상의 무거운 서비스가 거미줄처럼 얽혀 단위 테스트는 꿈도 못 꾸고 스프링 부트 테스트(기동 1분)만 돌리는 비효율 만연 → 나라면: 사내 정적 분석(Checkstyle/ArchUnit) 규칙으로 필드 주입 시 컴파일 에러를 발생시키고, 생성자 매개변수가 5개를 초과하면 단일 책임 원칙(SRP) 위반으로 판단해 클래스 분할 리팩토링 유도
