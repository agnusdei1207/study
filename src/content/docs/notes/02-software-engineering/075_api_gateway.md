## 한 줄 본질
- 수십 개 마이크로서비스의 주소와 인증 체계를 클라이언트(앱/웹)가 일일이 알고 직접 호출해야 하는 결합도와 보안 취약 병목 → 모든 외부 요청을 단일 진입점에서 받아 인증, 라우팅, 유량 제어, 프로토콜 변환을 일괄 대행 → 클라이언트-백엔드 간 디커플링 및 보안 일원화 / 게이트웨이 장애 시 전면 마비(SPOF) 위험

## 핵심 용어
- BFF(Backend for Frontend): 웹, 모바일, IoT 등 서로 다른 클라이언트 유형별 요구에 맞추어 API 응답 포맷을 맞춤 가공하는 전용 게이트웨이 계층
- 토큰 버킷(Token Bucket): 일정 속도로 채워지는 버킷 내 토큰 유무에 따라 API 요청 허용 여부를 결정하는 대표적 Rate Limiting 알고리즘

## 핵심 통찰
- API Gateway는 "스마트 엔드포인트와 멍청한 파이프(Smart Endpoints, Dumb Pipes)"라는 MSA 기본 철학을 지키기 위해 비즈니스 로직을 절대로 내부에 담지 말아야 함
- 게이트웨이에 데이터 조합이나 비즈니스 변환 로직이 쌓이기 시작하면 게이트웨이 자체가 거대한 레거시 모놀리스(ESB의 부활)가 되어 배포 병목을 유발함
- 외부 트래픽을 받는 최외곽은 API Gateway(노스-사우스 트래픽)가 맡고, 내부 서비스 간 통신(이스트-웨스트 트래픽)은 Istio 같은 서비스 메시가 맡는 역할 분담이 표준적임

## 이웃 토픽과 구분
- API Gateway vs 서비스 메시(Service Mesh): API Gateway = 클라이언트와 백엔드 간의 '외부-내부(North-South)' 통신 및 인증 통제 / 서비스 메시 = 마이크로서비스 상호 간의 '내부-내부(East-West)' 통신, mTLS, 트래픽 관측

## 문제·원인·대책
- 사례: 123회 기출 대규모 프로모션 시 게이트웨이 다운으로 전사 서비스 중단
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 서비스 장애가 게이트웨이의 가용 스레드를 모두 고갈시켜 전사 마비 | 하위 서비스 호출 지연 시 게이트웨이 스레드 풀 고갈(Cascading Failure) | 비동기 논블로킹 I/O(Spring Cloud Gateway, Netty) 및 서킷 브레이커 적용 | 서비스별 타임아웃 및 장애 격리(Bulkhead) |
| 클라이언트별(모바일 앱 vs PC 웹) 화면 데이터 요구 차이로 게이트웨이 비대화 | 단일 게이트웨이에서 모든 단말의 응답 DTO를 커스텀 변환 | 클라이언트 유형별 BFF(Backend for Frontend) 분리 구축 | 게이트웨이 경량화 및 프론트엔드 팀 자율 배포 확보 |

## 내 의견
- [API Gateway를 만능 ESB로 착각하는 설계 오류] 게이트웨이 내부에 데이터베이스를 직접 연결하고 비즈니스 합산 로직을 자바스크립트로 코딩하여 넣는 구시대적 ESB(Enterprise Service Bus) 회귀 경계 → 나라면: API Gateway는 순수 인프라 라우팅, WAF 보안, Rate Limiting만을 담당하는 Stateless 프록시로 고정하고, 화면 맞춤형 데이터 취합은 Node.js 기반의 경량 BFF로 분리하여 비즈니스 변경과 인프라 변경의 라이프사이클 격리
