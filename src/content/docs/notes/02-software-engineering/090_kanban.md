```text

 ┃
 ┣━ Ⅰ 개요 ───── 업무 과부하와 불투명한 진행 병목 극복 → 업무 흐름 시각화와 진행 중 작업(WIP) 제한 기반 애자일 기법
 ┣━ Ⅱ 특징 ───── 업무 시각화(Board) · WIP(Work In Progress) 제한 · 풀(Pull) 방식 흐름 제어 · 지속적 인도
 ┣━ Ⅲ 구조 ───── 칸반 보드(To Do, In Progress, Done) / WIP 한계선(Limit) / 리드 타임 / 사이클 타임 / 누적 흐름도(CFD)
 ┣━ Ⅳ 흐름 ───── 백로그 등록 → 팀 역량 기반 WIP 슬롯 확인 → 작업 풀(Pull) → 단계별 처리 및 병목 해소 → 완료(Done)
 ┣━ Ⅴ 비교 ───── 칸반(지속적 흐름, WIP 제한, 타임박스 없음) vs 스크럼(고정 스프린트, 역할 고정, 배치 인도)
 ┗━ Ⅵ 실무 ───── WIP 제한 무시로 인한 병목 악화 / 리틀의 법칙(Little's Law) 기반 사이클 타임 단축 체계
```

## 한 줄 본질
- 개발자들이 여러 작업을 동시에 벌려놓고(멀티태스킹) 아무것도 제때 끝내지 못하는 정체 병목 → 칸반 보드로 업무를 시각화하고 진행 중 작업 수(WIP)를 엄격히 제한하여 먼저 벌려놓은 일을 끝내도록 유도 → 작업 완료 속도(Cycle Time) 극대화 / 긴급 작업 유입 시 규칙 준수 통제 난이도

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               칸반 보드(Kanban Board)와 WIP 제한 구조             |
+-------------------------------------------------------------------+
| [To Do (대기)] |   [ 분석 (WIP: 2) ]  |   [ 개발 (WIP: 3) ]  | [Done] |
| +------------+ |   +----------------+ |   +----------------+ | +----+ |
| | Task A     | |   | [Task 1]       | |   | [Task 3]       | | | V1 | |
| | Task B     | |   | [Task 2] (Full)| |   | [Task 4]       | | | V2 | |
| | Task C     | |   +----------------+ |   | [Task 5] (Full)| | +----+ |
| +------------+ |           |          |   +----------------+ |        |
|                |           | 병목 발생!         |             |        |
|                |           x (신규 진입 불가)   v (완료 시 배출) |        |
+-------------------------------------------------------------------+
  * 리틀의 법칙 (Little's Law): 작업 완료 시간(Lead Time) = WIP / 처리율(Throughput)
  * WIP를 줄이면 리드 타임이 선형적으로 줄어든다!
```

## 핵심 용어
- WIP(Work In Progress) 제한: 특정 작업 단계에 동시에 머무를 수 있는 최대 작업 카드의 수를 지정하여 작업 정체를 방지하는 상한선
- 사이드 타임 vs 리드 타임: 리드 타임(Lead Time) = 고객이 요구한 시점부터 최종 인도까지의 총 시간 / 사이클 타임(Cycle Time) = 실제 개발 작업에 착수한 시점부터 완료까지의 시간

## 핵심 통찰
- 칸반의 가장 핵심적인 규칙은 "Stop Starting, Start Finishing(새로운 일을 시작하지 말고, 하던 일부터 끝내라)"임
- WIP 제한을 두면 특정 단계(예: 테스트)에 병목이 생겼을 때 앞단(개발)이 강제로 멈추게 되며, 개발자가 놀지 않고 테스트 병목을 돕도록 만드는 자연스러운 협업을 유도함
- 스크럼이 2주 단위 고정 스프린트로 신규 요구를 차단하는 '배치(Batch) 모델'이라면, 칸반은 운영 유지보수나 장애 대응처럼 수시로 티켓이 들어오는 환경에 완벽히 부합하는 '스트림(Stream) 모델'임

## 이웃 토픽과 구분
- 칸반 vs 스크럼(Scrum): 스크럼 = 1~4주 고정 타임박스(스프린트)와 스크럼 마스터 등 고정 역할 존재 / 칸반 = 타임박스나 역할 없이 오직 WIP 제한을 통한 지속적 흐름(Continuous Flow) 유지

## 문제·원인·대책
- 사례: 129회 기출 운영 유지보수 팀에서 50개 티켓이 3달째 미완료로 적체된 파탄
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 개발자 1명당 7개 티켓을 동시에 붙잡고 있어 어떤 기능도 납기 내 릴리스 불가 | WIP 제한 없이 들어오는 대로 모든 작업을 '진행 중'으로 올린 멀티태스킹 낭비 | 1인당 WIP 1개 강제 제한 및 풀(Pull) 기반 단일 작업 완수 원칙 수립 | 티켓 평균 사이클 타임 20일에서 3일로 급감 |
| 특정 검수 담당자에게만 카드가 몰려 전체 프로세스가 올스톱되는 병목 | 누적 흐름 다이어그램(CFD) 미활용으로 정체 구간 식별 누락 | CFD 밴드 폭 모니터링을 통한 병목 단계 크로스 트레이닝 및 협업 스워밍(Swarming) | 검수 단계 체류 시간 75% 단축 |

## 내 의견
- [Jira 보드만 띄워놓고 WIP 제한은 무시하는 무늬만 칸반] 칸반 보드를 단순히 예쁜 포스트잇 할 일 목록(Todo List)으로만 쓰고, WIP 수치 제한을 꺼둔 채 과거 폭포수처럼 일하는 흉내내기 애자일 경계 → 나라면: Jira/GitHub Projects에서 칼럼별 WIP 한도를 시스템으로 강제 설정하여 초과 시 카드 이동을 기술적으로 블로킹하고, 주간 스탠드업에서 속도(Velocity) 대신 리드 타임 단축률을 주간 회고 지표로 관리
