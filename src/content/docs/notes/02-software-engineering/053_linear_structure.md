## 한 줄 본질
- 원소들 사이의 관계가 1:1로만 연속되는 가장 단순하고 직관적인 데이터 나열 병목 → 물리적인 메모리 연속 주소(배열)나 포인터 체인(리스트)을 통해 순서대로 데이터를 배치하고 제약된 입출력 규칙(LIFO/FIFO) 적용 → 순차 처리 및 직관적 버퍼링 구현 / 대규모 데이터 탐색($O(N)$) 및 중간 삽입 시 데이터 이동 비용 대가

## 핵심 그림
```text
[ 선형 자료구조의 1:1 관계 체계 ]
  +-----------------------------------------------------------------+
  | 배열 (Array)   : [ 0: A ] -> [ 1: B ] -> [ 2: C ]  (연속 메모리)|
  +-----------------------------------------------------------------+
  | 리스트 (List)  : [ A | * ] -> [ B | * ] -> [ C | NULL ] (포인터)|
  +-----------------------------------------------------------------+
  | 스택 (Stack)   : | C | -> | B | -> | A | (한쪽 끝 LIFO 입출력)  |
  +-----------------------------------------------------------------+
  | 큐 (Queue)     : [ Front: A ] -> [ B ] -> [ Rear: C ] (FIFO)    |
  +-----------------------------------------------------------------+
```

## 핵심 용어
- 선형 자료구조(Linear Data Structure): 원소들 간에 앞뒤 순서가 일렬(1:1)로 유지되어, 첫 번째 원소와 마지막 원소를 제외하고는 모든 원소가 정확히 하나의 선행자와 하나의 후속자를 갖는 구조
- 덱(Deque, Double-Ended Queue): 양쪽 끝(Front, Rear) 모두에서 삽입과 삭제가 자유롭게 일어날 수 있는 스택과 큐의 결합형 선형 자료구조

## 핵심 통찰
- 모든 선형 자료구조의 본질은 "임의 접근(Random Access)을 취할 것인가($O(1)$ 배열), 동적 삽입/삭제를 취할 것인가($O(1)$ 리스트), 아니면 입출력 위치를 엄격히 제한할 것인가(스택/큐)"의 트레이드오프임
- 입출력 위치를 의도적으로 제한하는 스택(LIFO)과 큐(FIFO)는 프로그래머의 자의적 조작을 차단하여 프로그램 실행 흐름과 비동기 파이프라인의 무결성을 지키는 방어적 자료구조임
- 현대 하드웨어 아키텍처에서는 메모리가 연속적인 정적 배열이 CPU L1/L2 캐시 라인을 가장 효율적으로 채우므로, 포인터 기반 연결 리스트보다 배열 기반 구조가 우선 권장됨

## 이웃 토픽과 구분
- 선형 구조 vs 비선형 구조: 선형 = 데이터가 1차원 직선상에 배치(스택, 큐 등) / 비선형 = 데이터가 2차원 계층이나 망형으로 분기(트리, 그래프)

## 문제·원인·대책
- 사례: 125회/132회 기출 인메모리 이벤트 버퍼의 선형 자료구조 오선정
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 고정 크기 배열로 버퍼 구성 시 예상치 못한 트래픽 유입에 ArrayOutOfBoundsException 발생 | 배열의 정적 크기 한계 및 용량 초과 대응 부재 | 동적 배열(동적 리사이징: 2배 확장 후 복사) 또는 연결 리스트 결합 구조 적용 | 메모리 초과 예외 방지 및 유연한 버퍼 확장 |
| 스택을 사용하여 대기열을 구현했다가 먼저 들어온 요청이 영구 기아(Starvation) 발생 | FIFO가 필요한 작업 큐에 LIFO 성질의 스택을 잘못 적용 | 목적에 부합하는 FIFO 큐 또는 덱(Deque)으로 자료구조 교체 | 작업 처리의 공정성 및 실시간성 보장 |

## 내 의견
- [단순성만 믿고 선형 구조에 대용량 검색을 맡기는 실수] 수백만 건의 데이터를 단순 ArrayList나 배열에 담아두고 매 요청마다 처음부터 끝까지 루프(선형 탐색)를 돌리는 비효율적 코드 만연 → 나라면: 데이터 조회가 빈번한 도메인은 선형 구조를 수집 버퍼로만 사용하고, 영구 저장소에는 비선형 해시 테이블($O(1)$)이나 B-Tree 색인($O(\log N)$)으로 즉시 변환 적재하는 파이프라인 수립
