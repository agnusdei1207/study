## 답안 골격
```text
[디자인 패턴] ◀━━ 머리: Ⅶ 내 의견 (목적 없는 패턴 남용 지양 및 도메인 복잡도에 비례한 적용)
 ┃
 ┣━ Ⅰ 개요 ───── 반복되는 객체 설계 문제의 주먹구구 해결 비용 → 검증된 재사용 설계 템플릿 정립
 ┣━ Ⅱ 특징 ───── SOLID 원칙 구체화 · 결합도 완화 및 응집도 제고 · 설계 어휘 공유
 ┣━ Ⅲ 구조 ───── 생성 패턴(5종) · 구조 패턴(7종) · 행위 패턴(11종) = GoF 23종 패턴
 ┣━ Ⅳ 흐름 ───── ① 설계 문제 식별 → ② 패턴 목적 매핑 → ③ 클래스/인터페이스 추상화 → ④ 런타임 다형성 바인딩
 ┣━ Ⅴ 비교 ───── 아키텍처 스타일(시스템 거시 구조) vs 디자인 패턴(컴포넌트 미시 협력)
 ┗━ Ⅵ 실무 ───── 과도한 패턴 적용으로 인한 오버엔지니어링 / 리팩토링 단계 점진 도입
```
- 필수 키워드: GoF 23종 · 생성·구조·행위 패턴 · 다형성 · 인터페이스 분리 · 리팩토링 연계
- 배점 전략: 10점 = Ⅲ 3대 분류 매핑 표 → 대표 패턴(프록시, 팩토리 등) 구조 도식 / 25점 = Ⅰ~Ⅶ 전개, 리팩토링과의 상호보완 및 오버엔지니어링 극복
- 기출: 136회 1교시 `프록시 디자인 패턴` → Ⅲ·Ⅳ / 129회 2교시 `리팩토링과 디자인 패턴 정의·공통점·차이점` → Ⅴ·Ⅵ

## 한 줄 본질
- 소프트웨어 요구 변경 시 클래스 간 강한 결합으로 인해 연쇄 수정이 발생하는 설계 부패 → 변경되는 부분을 인터페이스 뒤로 캡슐화하는 검증된 객체 협력 구조 적용 → 코드 재사용성과 유지보수 유연성 확보 / 클래스 수 증가로 인한 코드 탐색 복잡도 대가

  |                  | 추상팩토리, 빌더, 프로토타입 (5개)            |
  +------------------+-----------------------------------------------+

## 핵심 용어
- 프록시(Proxy) 패턴: 다른 객체에 대한 접근을 제어하거나 부가 기능(로깅, 지연 로딩, 보안 검사)을 투명하게 추가하기 위해 대리자 객체를 두는 구조 패턴
- 전략(Strategy) 패턴: 동일 계열의 알고리즘들을 각각 캡슐화하여 런타임에 동적으로 교체 가능하게 만드는 행위 패턴

## 핵심 통찰
- 디자인 패턴은 처음부터 선행 설계로 완벽하게 깔아두는 것이 아니라, 냄새 나는 코드(Code Smell)를 발견했을 때 리팩토링의 지향점으로 적용해야 함
- 패턴의 핵심 메커니즘은 상속(Inheritance)이 아닌 객체 합성(Composition)과 인터페이스 분리임
- 단순한 조건 분기문(if-else) 2~3개를 없애기 위해 전략 패턴과 수많은 팩토리 클래스를 양산하는 것은 유지보수성을 오히려 해치는 오버엔지니어링임

## 이웃 토픽과 구분
- 아키텍처 스타일 vs 디자인 패턴: 아키텍처 스타일 = 시스템 전체 계층(Layered, MSA, EDA 등) 분할 / 디자인 패턴 = 모듈 내부 객체 간 협력 관계 정의

## 문제·원인·대책
- 사례: 129회 기출 레거시 코드 유지보수 시 디자인 패턴 도입 트러블슈팅
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 패턴 적용 후 클래스 파일 수 3배 폭증으로 신규 개발자 온보딩 지연 | 문제 도메인의 크기 대비 지나치게 세분화된 인터페이스 분할 | YAGNI 원칙에 입각한 패턴 단순화 및 불필요한 추상 계층 인라인 리팩토링 | 코드 가독성 및 직관적 흐름 회복 |
| 신규 결제 수단 추가 시 기존 결제 처리 모듈 전체 코드 수정 발생 | 구체 클래스에 직접 의존하는 결제 분기문 남발(DIP 위반) | 전략(Strategy) 패턴 도입을 통한 결제 알고리즘 캡슐화 | OCP(개방-폐쇄 원칙) 만족, 기존 코드 무수정 신규 확장 |

## 이렇게 출제된다
- 제136회 1교시 5번: "프록시(Proxy) 디자인 패턴" → 요구 포인트: Ⅲ 구조도(Subject, RealSubject, Proxy) + Ⅳ 동작 흐름 + Ⅵ 활용(가상, 원격, 보호 프록시)
- 제129회 2교시 6번: "객체지향의 기법 중에는 리팩토링(Refactoring)과 디자인패턴(Design Pattern)이 있다. 두 기법을 각각 정의하고 공통점과 차이점" → 요구 포인트: Ⅰ 정의 + Ⅴ 상호관계(패턴은 목적지, 리팩토링은 수단) + Ⅵ 실무 품질 향상 전략

## 내 의견
- [디자인 패턴 맹신에 빠진 주니어의 추상화 지옥] 책에서 본 패턴을 무조건 적용해야 좋은 코드라는 착각으로 한 줄짜리 연산에도 팩토리와 빌더를 겹겹이 두르는 사례 다발 → 나라면: 초기 개발은 단순 구현(KISS 원칙)으로 빠르게 기능 검증을 끝내고, 동일한 형태의 코드 중복과 변경 요구가 3회 이상 누적되는 시점(Rule of Three)에 코드 리뷰를 통해 필요한 패턴으로 단계적 리팩토링 유도
