## 한 줄 본질
- 시스템을 밑바닥부터 매번 새롭게 설계하면 검증되지 않은 구조적 결함이 반복되는 병목 → 반복되는 소프트웨어 구조적 문제에 대해 검증된 컴포넌트 분할 및 연결 패턴을 규격화하여 적용 → 구조적 예측 가능성 확보 / 비즈니스 특성에 맞지 않는 스타일 강제 시 성능 오버헤드

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               소프트웨어 4대 대표 아키텍처 스타일                |
+-------------------------------------------------------------------+
| 1. 계층화 스타일 (Layered)         | 2. 파이프-필터 (Pipe-Filter) |
| [UI] -> [App] -> [Domain] -> [DB] | [입력] |Filter1| -> |Filter2| |
| (단순함, 추상화, 단계별 검증)     | (데이터 변환 스트림, 독립성) |
+-----------------------------------+-------------------------------+
| 3. 이벤트 기반 (Event-Driven)     | 4. 저장소 스타일 (Repository) |
| [생성자] -> [Event Broker] -> [소비자] | [Agent1]       [Agent2]   |
| (비동기 처리, 느슨한 결합, 확장)  |     \             /       |
|                                   |        [중앙 데이터 저장소]   |
+-------------------------------------------------------------------+
```

## 핵심 용어
- 아키텍처 스타일: 시스템의 기본 골격을 이루는 컴포넌트와 커넥터의 유형, 그리고 이들의 결합 제약조건들의 집합
- 4+1 View 모델: 논리(Logical), 구현(Implementation), 프로세스(Process), 배포(Deployment) 뷰를 유스케이스(Use Case) 뷰로 통합 검증하는 아키텍처 표현 모델

## 핵심 통찰
- 완벽한 단 하나의 아키텍처 스타일은 존재하지 않으며, 모든 스타일은 특정 품질 속성(성능, 변경 용이성, 가용성)을 얻는 대가로 다른 속성을 희생하는 트레이드오프의 산물임
- 최근의 대규모 시스템은 단일 스타일이 아닌, 전체적으로는 이벤트 기반 마이크로서비스이면서 서비스 내부는 헥사고날 계층형을 취하는 '하이브리드 스타일'이 표준임
- 아키텍처 모델은 단순한 그림이 아니라, 개발 조직의 팀 구조(콘웨이의 법칙)와 배포 파이프라인의 경계를 규정하는 지침임

## 이웃 토픽과 구분
- 아키텍처 스타일 vs 디자인 패턴: 아키텍처 스타일 = 시스템 전체의 거시적 구조와 통신 방식 규정 / 디자인 패턴 = 특정 모듈이나 클래스 간의 미시적 문제 해결 구조

## 문제·원인·대책
- 사례: 120회 기출 실시간 대용량 로그 처리에 계층형 스타일을 고집하여 발생한 I/O 병목
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 초당 10만 건 로그 수집 시 다계층 트랜잭션 오버헤드로 지연 시간 초과 | 모든 요청이 4개 계층을 동기식으로 관통하는 계층화 스타일 오적용 | 파이프-필터 및 카프카 기반 스트리밍 아키텍처로 전환 | 파이프라인 병렬 처리로 지연 시간 밀리초 단위로 단축 |
| 주문 시스템 변경 시 결제, 배송, 재고 모듈이 줄줄이 컴파일 에러 발생 | 중앙 DB 저장소 스타일로 인한 강한 결합도(공통 결합도) | 이벤트 기반 비동기 발행/구독 아키텍처 도입 | 서비스 간 런타임 및 빌드 결합도 제거 |
