## 답안 골격
```text
[요구사항 명세] ◀━━ 머리: Ⅶ 내 의견 (자연어 명세의 모호성 극복을 위한 BDD 기반 정형 명세와 인수 기준(AC) 명문화)
 ┃
 ┣━ Ⅰ 개요 ───── 구두나 비정형 텍스트로 표현된 요구사항의 해석 왜곡 방지 → 공식 소프트웨어 요구사항 명세서(SRS) 작성
 ┣━ Ⅱ 특징 ───── 완전성(Completeness) · 일관성(Consistency) · 명확성(Unambiguity) · 검증가능성(Verifiability)
 ┣━ Ⅲ 구조 ───── 기능적 요구사항(Functional) + 비기능적 요구사항(Non-functional, FURPS+) + 제약조건
 ┣━ Ⅳ 흐름 ───── 요구 분석 결과 정리 → IEEE 830/29148 표준 템플릿 작성 → 정형/비정형 명세 기법 적용 → 베이스라인 고정
 ┣━ Ⅴ 비교 ───── 비정형 명세(자연어, 사용성 우수, 모호성 위험) vs 정형 명세(수학적 기호/Z/VDM, 정확성, 난해함)
 ┗━ Ⅵ 실무 ───── 명세서의 모호한 형용사("신속히", "안전하게") 남발 / 정량적 인수 기준(Gherkin 문법) 도입
```
- 필수 키워드: SRS · IEEE 830 · ISO/IEC/IEEE 29148 · 기능/비기능 요구 · 완전성/일관성/검증가능성 · 정형/비정형 명세 · 인수 기준(AC)
- 배점 전략: 10점 = Ⅱ 우수 명세서의 8대 품질 특성 → Ⅲ IEEE 830 표준 목차 구조 / 25점 = Ⅰ~Ⅶ 전개, 비기능 요구사항(성능, 보안) 정량화 및 정형/비정형 비교
- 기출: 130회 1교시 `요구사항명세서에 기술되어야 하는 항목 설명` → Ⅲ·Ⅳ / 121회 4교시 `공공정보화사업 RFP 상세화와 요구사항 명세` → Ⅰ·Ⅵ

## 한 줄 본질
- 자연어의 다의성과 모호성으로 인해 발주자, 설계자, 개발자, 테스터가 서로 다른 시스템을 상상하는 커뮤니케이션 왜곡 병목 → 표준 규격(IEEE 830)과 명확한 품질 속성에 맞춰 검증 가능하고 일관된 정형/비정형 명세서(SRS)로 문서화 → 개발 계약의 단일 진실 공급원(SSOT) 확립 / 명세 작성 및 검토 공수 대가

## 핵심 그림
```text
[ IEEE 830 / ISO 29148 표준 소프트웨어 요구사항 명세서 (SRS) 구조 ]
+--------------------------------------------------------------------+
| 1. 개요 (Introduction) : 시스템 목적, 범위, 정의, 참조 문서        |
+--------------------------------------------------------------------+
| 2. 전체 설명 (Overall Description) : 제품 조망, 사용자 특성, 제약조건|
+--------------------------------------------------------------------+
| 3. 세부 요구사항 (Specific Requirements)                           |
|    - 기능적 요구사항 : 입력, 처리, 출력, 오류 처리                 |
|    - 외부 인터페이스 : 사용자(UI), 하드웨어, 소프트웨어, 통신      |
|    - 비기능적 요구사항: 성능(TPS, 응답시간), 보안, 신뢰성, 유지보수성|
+--------------------------------------------------------------------+
| 4. 부록 및 색인 (Supporting Information)                           |
+--------------------------------------------------------------------+
```

## 핵심 용어
- 검증 가능성(Verifiability): 명세서에 기록된 요구사항이 실제 소프트웨어로 구현되었는지 여부를 비용 효율적으로 시험(테스트, 검사)하여 참/거짓을 증명할 수 있는 성질
- 정형 명세(Formal Specification): 수학적 집합론, 논리식, 대수적 기호(Z, VDM 등)를 사용하여 모호성이 전혀 없도록 시스템의 상태와 행위를 엄밀하게 명세하는 기법

## 핵심 통찰
- "빠르게 응답해야 한다", "사용하기 편리해야 한다" 같은 형용사가 들어간 명세는 검증할 수 없으므로 무효한 명세임(반드시 "동시접속자 1,000명 기준 95% 요청의 응답시간은 1.5초 이내"처럼 정량 수치화해야 함)
- 요구사항 명세서는 개발자를 위한 가이드일 뿐만 아니라, 프로젝트 종료 시 잔금을 청구하고 검수를 받는 법적 계약서(Contract)의 역할을 수행함
- 애자일 환경에서는 방대한 워드 문서 대신 "Given-When-Then" 형식의 행위 주도 개발(BDD) 인수 기준(Acceptance Criteria)을 실행 가능한 명세서(Executable Spec)로 활용함

## 이웃 토픽과 구분
- 요구사항 명세 vs 요구사항 분석: 분석 = 요구사항들 간의 상충을 해결하고 모델링하는 과정 / 명세 = 분석된 결과를 표준 양식에 맞추어 검증 가능하게 기록하는 행위

## 이렇게 출제된다
- 제130회 1교시 3번: "요구사항명세서에 기술되어야 하는 항목 설명" → 요구 포인트: Ⅲ IEEE 830 표준 SRS의 주요 3대 챕터 구성(개요, 전체 설명, 세부 기능/비기능 요구사항)
- 제121회 4교시 1번: "소프트웨어산업진흥법의 요구사항 상세화 의무와 관련하여 제안요청서(RFP) 및 명세서 작성 방안" → 요구 포인트: 요구사항 명세의 구체화 및 법적 분쟁 방지 대책

## 내 의견
- [소설처럼 쓰인 1,000페이지짜리 자연어 명세서의 비극] 두껍게 인쇄된 종이 명세서를 책장에 꽂아두고는 아무도 읽지 않아, 개발자가 자기 상상대로 코딩하는 현상이 만연 → 나라면: Cucumber나 SpecFlow 도구를 연동한 '실행 가능한 명세(Specification by Example)'를 도입하여, 명세서의 Given-When-Then 문장이 곧바로 자동화된 인수 테스트 코드로 실행되도록 개발 프로세스 혁신
