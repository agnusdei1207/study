## 답안 골격
```text
[코드스멜] ◀━━ 머리: Ⅶ 내 의견 (정적 분석 임계치 강제와 기술 부채 전이 방지 리팩토링)
 ┃
 ┣━ Ⅰ 개요 ───── 문법적 오류는 없으나 유지보수성을 악화시키는 잠재적 나쁜 설계 징후 감지
 ┣━ Ⅱ 특징 ───── 켄트 벡·마틴 파울러 정립 · 버그의 전조 증상 · 리팩토링의 트리거 역할
 ┣━ Ⅲ 구조 ───── 기형적 팽창(Bloaters) · 객체지향 오용 · 변경 탄력성 저하 · 불필요한 군더더기 · 결합도 증대
 ┣━ Ⅳ 흐름 ───── 린트/정적 분석 탐지 → 순환 복잡도 및 결합도 측정 → 리팩토링 패턴 매핑 → 코드 정화
 ┣━ Ⅴ 비교 ───── 소프트웨어 버그(동작 오류) vs 코드 스멜(구조적 악취) vs 안티패턴(잘못된 설계 해법)
 ┗━ Ⅵ 실무 ───── 장대한 메서드(Long Method) 및 거대 클래스(God Class) / 메서드 추출 및 책임 분리
```
- 필수 키워드: 마틴 파울러 · 켄트 벡 · 긴 메서드 · 거대 클래스(God Class) · 기능 편애(Feature Envy) · 중복 코드 · 산탄총 수술(Shotgun Surgery)
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 5대 분류 체계 표 → 대표 스멜별 해법 매핑 / 25점 = Ⅰ~Ⅶ 전개, 순환 복잡도와의 관계 및 정적 분석 파이프라인 연계
- 기출: 127회 3교시 `리팩토링의 대상과 기법` → Ⅰ·Ⅲ·Ⅳ / 139회 1교시 `맥케이브 순환복잡도` → Ⅳ·Ⅵ

## 한 줄 본질
- 컴파일러와 단위 테스트를 모두 통과하지만 사람이 읽고 수정하기 어렵게 꼬여 있는 부패한 설계 병목 → 마틴 파울러의 22가지 대표 스멜 패턴으로 구조적 결함을 정밀 식별하고 해당 리팩토링 기법 적용 → 소프트웨어 수명 연장 및 결함 발생률 감소 / 정적 분석 도구 도입 및 규칙 튜닝 비용

## 핵심 그림
```text
[ 대표적 코드 스멜 4대 유형과 처방전 ]
+------------------------------------+------------------------------------+
| 코드 스멜 (증상)                  | 리팩토링 해법 (처방)               |
+------------------------------------+------------------------------------+
| 긴 메서드 (Long Method)            | -> 메서드 추출 (Extract Method)    |
| 거대 클래스 (Large Class / God)    | -> 클래스 추출 (Extract Class)     |
| 산탄총 수술 (Shotgun Surgery)      | -> 필드/메서드 이동 (Move Method)  |
| 기능 편애 (Feature Envy)           | -> 책임 재배치 (Move & Encapsulate)|
+------------------------------------+------------------------------------+
```

## 핵심 용어
- 신의 클래스(God Class): 한 클래스가 시스템의 너무 많은 데이터와 책임을 독점하여 단일 책임 원칙(SRP)을 심각하게 파괴한 스멜
- 산탄총 수술(Shotgun Surgery): 하나의 비즈니스 변경이 발생했을 때 수많은 클래스들의 작은 조각들을 조금씩 모두 수정해야 하는 강한 결합도 스멜
- 기능 편애(Feature Envy): 어떤 메서드가 자신이 속한 클래스보다 다른 클래스의 데이터나 메서드를 더 많이 참조하고 의존하는 스멜

## 핵심 통찰
- 코드 스멜은 소프트웨어가 죽어가는 첫 번째 경고 신호이며, 이를 무시하면 결함(Bug)의 기하급수적 증가와 기술 부채의 폭증으로 직결됨
- 맥케이브 순환 복잡도(Cyclomatic Complexity)가 10을 초과하는 메서드는 거의 예외 없이 긴 메서드나 복잡한 조건문 스멜을 내포하고 있음
- 코드 스멜 제거는 한 번에 전면적으로 하는 것이 아니라, 지속적 통합(CI) 환경에서 정적 분석 도구가 경고를 띄울 때 해당 커밋 범위 안에서 즉시 해소해야 함

## 이웃 토픽과 구분
- 코드 스멜 vs 안티패턴: 코드 스멜 = 소스코드 라인 수준에서 풍기는 구조적 악취 / 안티패턴 = 아키텍처나 설계 수준에서 잘못 정형화된 해법(예: 스파게티 코드, 황금 망치)

## 문제·원인·대책
- 사례: 127회 기출 레거시 주문 결제 모듈의 코드 스멜 누적으로 인한 장애
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 정책 1개 변경 시 20개 소스 파일 동시 수정 및 오류 누락 | 특정 로직이 여러 모듈에 산재한 산탄총 수술(Shotgun Surgery) 스멜 | 변경이 빈번한 로직을 단일 클래스로 모으는 모듈 응집화 리팩토링 | 수정 영향 범위 단일 모듈로 한정 |
| 2,000라인의 OrderManager 클래스 수정 시 사이드이펙트 발생 | 데이터와 온갖 비즈니스 로직을 한곳에 쓸어 담은 거대 클래스(God Class) 스멜 | 역할별로 주문 생성, 결제 검증, 재고 차감 클래스로 위임 분리 | 단위 테스트 용이성 및 모듈 독립성 회복 |
