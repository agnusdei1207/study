## 답안 골격
```text
[동적 테스트] ◀━━ 머리: Ⅶ 내 의견 (정적 분석과의 파이프라인 연계 및 테스트 피라미드 기반 비용 최적화)
 ┃
 ┣━ Ⅰ 개요 ───── 소스코드 실행을 통한 실제 동작 검증 → 런타임 결함, 메모리 누수, 성능 병목 탐지
 ┣━ Ⅱ 특징 ───── 소프트웨어 실제 실행 · 입력값 대비 출력값 검증 · 런타임 환경 의존 · 결함 증상 직접 관찰
 ┣━ Ⅲ 구조 ───── 화이트박스(구조/커버리지) / 블랙박스(명세/경계값) / 경험기반(탐색적) / 비기능(성능, 부하)
 ┣━ Ⅳ 흐름 ───── 테스트 계획 → 테스트 케이스/데이터 설계 → 환경 구성 → 테스트 실행 및 출력 측정 → 결과 비교 및 결함 보고
 ┣━ Ⅴ 비교 ───── 동적 테스트(실행 기반, 런타임 오류) vs 정적 테스트(비실행 리뷰/정적분석, 규칙 위반 및 조기 결함)
 ┗━ Ⅵ 실무 ───── 테스트 환경 구축 비용과 지연 / 단위 테스트 자동화 및 컨테이너 가상 환경(Testcontainers) 적용
```

## 한 줄 본질
- 코드를 눈으로만 읽는 정적 검토로는 런타임 메모리 누수나 동시성 경합 상태를 발견할 수 없는 병목 → 실제 테스트 데이터를 입력하고 프로그램을 직접 구동하여 기대 결과와의 일치 여부를 검증 → 실행 환경에서의 동작 무결성 입증 / 실행 환경 구축 및 테스트 케이스 유지보수 비용 발생

## 핵심 용어
- 테스트 오라클(Test Oracle): 테스트를 수행한 결과가 참인지 거짓인지를 판단하기 위해 사전에 정의된 참값(기대 결과)을 제공하는 메커니즘
- MC/DC(Modified Condition/Decision Coverage): 각 개별 조건식이 전체 결정식의 결과에 독립적으로 영향을 미치는지를 검증하는 고신뢰성 화이트박스 지표

## 핵심 통찰
- 동적 테스트는 결함의 '원인(Defect)'을 직접 짚어내는 정적 분석과 달리, 결함으로 인해 나타나는 '고장 증상(Failure)'을 포착하는 기법임
- 테스트 피라미드(Test Pyramid) 원칙에 따라, 빠르고 저렴한 단위 동적 테스트를 70% 이상 구축하고, 느리고 비싼 E2E 동적 테스트는 핵심 시나리오 10% 내외로 제한해야 함
- 런타임 결함은 환경(OS, 메모리, 네트워크)에 크게 좌우되므로, Docker 컨테이너 및 모의 객체(Mock)를 활용한 멱등성 있는 동적 테스트 환경 조성이 필수적임

## 이웃 토픽과 구분
- 동적 테스트 vs 정적 테스트: 동적 테스트 = 코드를 '직접 실행'하여 런타임 동작과 출력을 검증 / 정적 테스트 = 코드를 '실행하지 않고' 문서 리뷰나 정적 린터로 문법·보안 결함 검출

## 문제·원인·대책
- 사례: 137회 기출 정적 분석 100% 통과 후 운영 배포 시 힙 메모리 누수로 서버 다운
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 정적 분석 툴에서 이상 없던 모듈이 동시 접속 5,000명 유입 시 OOM 다운 | 정적 린터가 잡지 못하는 커넥션 미반환 및 동시성 런타임 락 경합 | 부하 테스트 도구(JMeter, k6) 및 APM 연동 동적 스트레스 테스트 수행 | 동시성 런타임 메모리 누수 100% 사전 격리 |
| 동적 테스트 수행 시 외부 결제사 API 장애로 전체 빌드 파이프라인 정지 | 외부 시스템 의존성이 강한 통합 테스트의 격리 실패 | 모의 객체(Mock Server, WireMock) 기반 격리된 동적 테스트 환경 구축 | 외부 환경과 무관한 빌드 테스트 결정론(Determinism) 확보 |
