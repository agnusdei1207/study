## 답안 골격
```text
[무중단 배포] ◀━━ 머리: Ⅶ 내 의견 (DB 스키마 하위 호환성 없는 무중단 배포는 반쪽짜리)
 ┃
 ┣━ Ⅰ 개요 ───── 정기 점검 시 서비스 중단으로 인한 비즈니스 손실 → 트래픽 라우팅 제어로 24x365 가동
 ┣━ Ⅱ 특징 ───── 고가용성 보장 · 장애 시 즉시 롤백 가능 · 환경 격리 및 점진적 트래픽 전환
 ┣━ Ⅲ 구조 ───── 로드밸런서(L4/L7) · 이전 버전 인스턴스(V1) · 신규 버전 인스턴스(V2)
 ┣━ Ⅳ 흐름 ───── 롤링(인스턴스 순차 교체) / 블루-그린(전체 전환) / 카나리(비율 분할 모니터링)
 ┣━ Ⅴ 비교 ───── 롤링 배포 vs 블루-그린 배포 vs 카나리 배포 3대 전략
 ┗━ Ⅵ 실무 ───── 데이터베이스 스키마 변경 시 호환성 단절 / Expand and Contract 패턴
```
- 필수 키워드: 롤링(Rolling) · 블루-그린(Blue-Green) · 카나리(Canary) · 로드밸런서 · DB 하위 호환성 · Expand and Contract
- 배점 전략: 10점 = Ⅲ 3대 배포 방식 도식 및 비교표 / 25점 = Ⅰ~Ⅶ 전개, Ⅵ 데이터베이스 스키마 무중단 마이그레이션 전략 집중
- 기출: 139회 1교시 `소프트웨어 무중단 배포 방식` → Ⅲ·Ⅳ·Ⅴ / 134회 3교시 `배포 전략 및 테스트 전략` → Ⅳ·Ⅵ

## 한 줄 본질
- 신규 버전 배포 시 프로세스 재시작으로 인한 서비스 일시 중단(Downtime) 병목 → 로드밸런서의 동적 트래픽 라우팅을 이용해 신구 버전을 동시 가동하고 점진 또는 일괄 전환 → 사용자 무중단 연속 서비스 / 서버 인프라 2배 소요 및 DB 스키마 동기화 복잡도 대가

## 핵심 그림
```text
[ 블루-그린 배포 ]                    [ 카나리 배포 ]
      Load Balancer                        Load Balancer
       /          \                        / (90%)    \ (10%)
   [Blue: V1]   [Green: V2]            [V1: 기존]    [V2: 카나리]
   (운영중)     (신규배포 검증완료)     (대다수 사용자) (에러율 모니터링)
        \ 전환시 스위칭 /
```

## 핵심 용어
- 블루-그린(Blue-Green): 동일 규모의 독립된 운영 환경 2조를 구성하고 로드밸런서 스위칭으로 순식간에 트래픽을 넘기는 배포 기법
- 카나리(Canary): 위험을 감지하는 광산의 카나리아처럼, 전체 트래픽 중 극소수(1~5%)만 신규 버전에 흘려 오류를 관측한 후 점진 확대하는 기법

## 핵심 통찰
- 무중단 배포의 성패는 애플리케이션 컨테이너가 아니라 상태(State)를 가진 데이터베이스 스키마 관리에 달려 있음
- 롤링 배포는 인프라 비용이 들지 않지만 배포 도중 구버전과 신버전이 동시에 요청을 처리하므로 API와 세션 호환성이 엄격해야 함
- 블루-그린 배포는 즉시 롤백이 가능하나 인프라 비용이 2배로 들며, 대규모 클라우드 환경에서는 프로비저닝 시간 통제가 필요함

## 이웃 토픽과 구분
- 블루-그린 vs 카나리: 블루-그린 = 배포 검증 완료 후 100% 트래픽 일괄 전환 / 카나리 = 실제 운영 트래픽을 가중치별로 분할하여 단계적 노출

## 문제·원인·대책
- 사례: 134회 기출 대규모 전자상거래 서비스의 결제 모듈 무중단 배포 실패
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 배포 도중 특정 유저에게 500 내부 서버 오류 발생 | 신규 컬럼을 참조하는 신버전 앱 배포 전 DB 스키마 마이그레이션 미반영 | Expand and Contract(단계적 확장 및 축소) 패턴 적용 | 구버전과 신버전이 동시에 실행되어도 데이터 오류 제로 |
| 카나리 배포 중 신규 버전 메모리 누수 발생 | 사전 테스트 환경 부하 테스트 부족 및 모니터링 지표 부재 | APM 에러율 및 응답 지연 임계치 초과 시 자동 롤백 파이프라인 트리거 | 비정상 버전의 전면 확산 원천 차단 |

## 내 의견
- [DB를 고려하지 않은 무중단 배포의 허상] 애플리케이션만 쿠버네티스 롤링 업데이트로 띄워두고 DB 테이블 컬럼을 rename하여 구버전 팟들이 즉시 크래시나는 사고를 흔히 목격 → 나라면: 컬럼 추가(Expand) → 신구 버전 동시 쓰기 → 구버전 제거 → 기존 컬럼 삭제(Contract)의 4단계 DB 마이그레이션을 CD 파이프라인과 결합하여 강제
