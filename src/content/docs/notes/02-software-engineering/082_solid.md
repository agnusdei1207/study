
## 한 줄 본질
- 요구사항 변경 시마다 기존 코드를 뜯어고치다 시스템 전체가 연쇄적으로 부서지는 경직성 병목 → 객체지향 5대 설계 원칙(SOLID)을 적용해 클래스의 책임을 좁히고 추상 인터페이스를 통해 확장 → 기능 변경 시 기존 코드 수정 없는 무결성 유지 / 클래스 및 인터페이스 개수 증가

## 핵심 그림
```text
+-------------------------------------------------------------------+
|               객체지향 설계의 5대 원칙 (SOLID) 구조               |
+-------------------------------------------------------------------+
| 1. SRP (단일 책임)       : 한 클래스는 단 하나의 변경 이유만 가져야 함 |
| 2. OCP (개방-폐쇄)       : 확장은 열려 있고(Open), 수정은 닫혀야 함(Closed) |
| 3. LSP (리스코프 치환)   : 하위 타입은 언제나 상위 타입을 대체할 수 있어야 함 |
| 4. ISP (인터페이스 분리) : 쓰지 않는 메서드에 억지로 의존하지 말아야 함 |
| 5. DIP (의존관계 역전)   : 구체 구현이 아니라 추상화(인터페이스)에 의존함 |
+-------------------------------------------------------------------+
    ^                                                          ^
    | (SRP + ISP) : 응집도(Cohesion) 극대화                    |
    +----------------------------------------------------------+
    | (OCP + LSP + DIP) : 결합도(Coupling) 최소화              |
```

## 핵심 용어
- 리스코프 치환 원칙(LSP): 하위 클래스의 인스턴스는 상위 클래스의 인스턴스가 쓰이는 곳 어디서든 프로그램의 정확성을 깨뜨리지 않고 대체될 수 있어야 한다는 원칙(계약에 의한 설계)
- 인터페이스 분리 원칙(ISP): 단 하나의 범용 거대 인터페이스보다는, 클라이언트의 목적별로 작게 쪼개진 여러 개의 특화 인터페이스가 낫다는 원칙

## 핵심 통찰
- SOLID 원칙의 핵심 궁극점은 "새로운 기능을 추가할 때(확장), 기존에 잘 돌아가던 코드를 단 한 줄도 손대지 않게(폐쇄) 만드는 OCP"이며, 나머지 4개 원칙은 OCP를 달성하기 위한 하부 받침대임
- SRP는 단순히 '함수를 짧게 만드는 것'이 아니라, '그 코드가 누구의 요구에 의해 변경되는가(액터, Actor)'에 따라 책임의 단위를 나누는 것임
- LSP를 위반하면 다형성이 완전히 무너지며, 상위 인터페이스를 쓸 때마다 `if (obj instanceof SubClass)` 같은 조건문 분기가 코드 곳곳에 침투하여 OCP까지 연쇄 파괴함

## 이웃 토픽과 구분
- SOLID vs 디자인 패턴(Design Pattern): SOLID = 객체지향 설계가 지향해야 할 근본적인 '원칙(Principles)' / 디자인 패턴 = SOLID 원칙을 특정 맥락의 문제 해결에 적용한 구체적인 '설계 해법(Solutions)'

## 내 의견
- [원칙에 매몰되어 1줄짜리 인터페이스를 수백 개 양산하는 교조주의] SOLID를 맹목적으로 신봉하여 변경 가능성이 전혀 없는 단순 CRUD 모듈까지 억지로 5단계 인터페이스와 DTO로 쪼개어 가독성을 마비시키는 오버엔지니어링 경계 → 나라면: 도메인의 핵심 비즈니스 로직과 변경 가능성이 높은 외부 연계 모듈에 SOLID를 집중 적용하고, 단순 데이터 조회 계층은 YAGNI(You Aren't Gonna Need It) 원칙과 조화시키는 실용적 균형 추구
