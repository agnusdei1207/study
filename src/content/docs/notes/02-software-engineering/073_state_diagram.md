## 답안 골격
```text
[상태 다이어그램] ◀━━ 머리: Ⅶ 내 의견 (상태 전이 테이블 기반의 도메인 상태 머신 패턴 구현 및 예외 전이 방어)
 ┃
 ┣━ Ⅰ 개요 ───── 단일 객체의 복잡한 생명주기 모델링 → 이벤트에 따른 객체의 상태 변화와 전이 규칙 명세
 ┣━ Ⅱ 특징 ───── 이벤트 구동적(Event-driven) · 유한 상태 머신(FSM) 기반 · 상태 캡슐화 · 가드 조건 판정
 ┣━ Ⅲ 구조 ───── 상태(State: Entry/Do/Exit) / 이벤트(Event) / 전이(Transition) / 가드(Guard) / 시작·종료 상태
 ┣━ Ⅳ 흐름 ───── 초기 상태 진입 → 이벤트 발생 → 가드 조건 평가 → 액션 실행(Exit/Transition/Entry) → 신규 상태 안착
 ┣━ Ⅴ 비교 ───── 상태 다이어그램(단일 객체 상태 변화) vs 활동 다이어그램(업무/프로세스 흐름) vs 순차 다이어그램(객체 간 메시지)
 ┗━ Ⅵ 실무 ───── 상태 폭발(State Explosion) 문제 / 계층적 상태(Composite State) 및 State 디자인 패턴 적용
```
- 필수 키워드: UML 행위 다이어그램 · 유한 상태 머신(FSM) · 상태(State) · 전이(Transition) · 이벤트 · 가드 조건 · 복합 상태
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 상태 다이어그램 기호 및 표기법 도식 → Ⅴ UML 행위 다이어그램 비교 / 25점 = Ⅰ~Ⅶ 전개, 137회 기출 행위 다이어그램 3종(활동, 상태, 유스케이스)의 상호 매핑과 실무 설계 적용
- 기출: 137회 4교시 4번 `UML 행위 다이어그램인 활동 다이어그램, 상태 다이어그램, 유스케이스 다이어그램` → Ⅰ~Ⅴ / 108회 1교시 `상태 다이어그램` → Ⅰ·Ⅲ·Ⅳ

## 한 줄 본질
- 주문, 결제, 장비 제어 등 객체 내부의 상태가 여러 이벤트에 의해 복잡하게 얽혀 엉뚱한 상태로 전이되는 런타임 결함 병목 → 객체가 가질 수 있는 모든 유한한 상태와 이벤트, 가드 조건을 수학적 상태 머신 다이어그램으로 시각화 → 허용되지 않은 상태 전이 원천 차단 / 상태 수가 급증할 경우 복잡도 폭증

## 핵심 그림
```text
+-------------------------------------------------------------------+
|            주문(Order) 도메인의 상태 다이어그램 표기법            |
+-------------------------------------------------------------------+
|  (●) 시작 상태                                                    |
|   |                                                               |
|   | 주문 생성                                                     |
|   v                                                               |
| +-------------------------+                                       |
| | [주문 대기 (Pending)]   |                                       |
| | entry / 결제 타이머 시작|                                       |
| +-------------------------+                                       |
|   |                       \                                       |
|   | 결제 승인 [재고 있음] | 시간 초과 (Timeout)                   |
|   v                       v                                       |
| +-------------------------+     +-------------------------+       |
| | [결제 완료 (Paid)]      |     | [주문 취소 (Cancelled)] | ----> (◎)
| | do / 배송 준비          |     +-------------------------+  종료 |
| +-------------------------+                                       |
|   |                                                               |
|   | 배송 완료                                                     |
|   v                                                               |
| +-------------------------+                                       |
| | [배송 완료 (Delivered)] | ------------------------------------> (◎)
| +-------------------------+                                  종료 |
+-------------------------------------------------------------------+
```

## 핵심 용어
- 가드 조건(Guard Condition): `[조건]` 형식으로 전이 선 위에 표기되며, 해당 불리언(Boolean) 조건이 참(True)이어야만 상태 전이가 발생하는 조건
- 복합 상태(Composite State): 다수의 세부 하위 상태(Substates)를 내부에 포함하여 상태 폭발(State Explosion)을 억제하는 계층적 상태 구조

## 핵심 통찰
- 상태 다이어그램은 모든 객체에 그리는 것이 아니라, 상태에 따라 수행 가능한 행위가 완전히 달라지는 '상태 의존적 핵심 도메인 객체'에만 한정적으로 작성해야 함
- 코드 레벨에서 `if (status == 1) else if (status == 2)`와 같은 조건문 지옥을 없애기 위해 상태 다이어그램을 기반으로 'State 디자인 패턴'이나 'Spring State Machine'을 적용함
- 상태 전이 표(State Transition Matrix)를 다이어그램과 함께 작성하면, 정의되지 않은 예외 이벤트 유입 시의 미처리 결함을 100% 사전에 방어할 수 있음

## 이웃 토픽과 구분
- 상태 다이어그램 vs 활동 다이어그램: 상태 다이어그램 = '단일 객체'가 이벤트에 반응하여 겪는 상태 변화 중심 / 활동 다이어그램 = 시스템 전반의 '업무 처리 절차와 제어 흐름' 중심

## 문제·원인·대책
- 사례: 137회 기출 이커머스 결제 취소 중복 요청으로 인한 비정상 배송 전이 사고
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 취소 처리 중인 주문이 배송 완료 상태로 전이되어 물품 오배송 | '취소 중' 상태에서 '배송 출발' 이벤트를 차단하는 가드 조건 누락 | 상태 다이어그램 기반 전이 규칙 검증 및 State 패턴 적용 | 불법 상태 전이 런타임 예외로 100% 차단 |
| 결제, 환불, 정산 등 상태가 50개로 늘어나 다이어그램 파독 불가 | 평면적인 단일 상태 머신 모델링으로 인한 상태 폭발(State Explosion) | 상위-하위 계층형 복합 상태(Composite State) 및 직교 상태(Orthogonal) 도입 | 다이어그램 가독성 제고 및 모듈형 상태 관리 |
