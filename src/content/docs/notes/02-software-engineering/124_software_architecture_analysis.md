 ┃
 ┣━ Ⅰ 개요 ───── 설계 의도와 실제 구현 간의 불일치(아키텍처 침식) → 정방향(Forward) 및 역방향(Reverse) 분석을 통한 아키텍처 무결성 검증
 ┣━ Ⅱ 특징 ───── 비즈니스 목표 부합성(정방향) vs 구현 적합성(역방향) · 정적 분석 도구 활용 · 기술 부채 식별
 ┣━ Ⅲ 구조 ───── 정방향 분석(품질 속성 시나리오, ATAM, CBAM) + 역방향 분석(정적 역공학, 의존성 매트릭스 DSM, 코드 추출 모델)

 ┣━ Ⅴ 비교 ───── 정방향 아키텍처 분석(Forward) vs 역방향 아키텍처 분석(Reverse)
 ┗━ Ⅵ 실무 ───── 아키텍처 드리프트(Drift) 및 침식(Erosion) / 의존성 순환(Circular Dependency) / ArchAsCode 구축

## 한 줄 본질
- 소프트웨어가 개발·운영되면서 초기 설계 문서와 실제 소스코드 간의 괴리가 심화되는 아키텍처 침식 병목 → 요구사항으로부터 아키텍처를 유도·평가하는 정방향 분석과, 실제 코드로부터 아키텍처 모델을 역추출하여 설계 준수를 검증하는 역방향 분석 기법 / 도구 의존성 및 분석 오버헤드

## 핵심 용어
- 아키텍처 침식(Architectural Erosion): 개발자가 편의를 위해 아키텍처 계층 원칙을 무시하고 직접 참조나 순환 의존성을 추가하여 시스템 구조가 점진적으로 부패하는 현상
- DSM(Design Structure Matrix): 소스코드 컴포넌트 간의 결합과 의존성을 정방형 격자 행렬로 표현하여 순환 참조와 비정상 호출을 시각적으로 탐지하는 도구

## 핵심 통찰
- 아키텍처는 문서로 존재하는 "의도된 아키텍처(As-Designed)"와 실제 코드에 녹아 있는 "구현된 아키텍처(As-Implemented)"가 다를 수밖에 없으며, 이 둘의 간극을 줄이는 것이 역방향 분석의 핵심 목적임
- 정방향 분석(ATAM 등)은 프로젝트 초기에 대규모 품질 속성(성능, 가용성, 보안) 간의 트레이드오프를 결정하는 전략적 분석인 반면, 역방향 분석은 개발 주기 내내 기술 부채의 누적을 감시하는 전술적 분석임
- 역방향 아키텍처 분석을 연 1회 수행하는 정기 감사 이벤트로 취급하면 무의미하며, CI 파이프라인에 단위 테스트처럼 아키텍처 규칙 검증(ArchUnit, SonarQube)을 내재화해야 침식을 차단할 수 있음

## 이웃 토픽과 구분
- 정방향 분석 vs 역방향 분석: 정방향 = 요구사항 → 설계로 내려가는 연역적 평가(목표 적합성 검증) / 역방향 = 소스코드 → 아키텍처 모델로 올라가는 귀납적 복원(설계 일치도 검증)

## 문제·원인·대책
- 적용 상황: 수년간 운영되며 계층 구조가 붕괴된 레거시 커머스 플랫폼
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 컨트롤러(Presentation) 계층에서 리포지토리(Data) 계층을 직접 호출하여 비즈니스 규칙 우회 | 일정 압박으로 개발자들이 서비스 계층을 건너뛰는 불법 참조 코드 양산(아키텍처 침식) | 역방향 의존성 분석 도구(ArchUnit)를 빌드에 적용하여 계층 간 불법 호출 시 빌드 실패 처리 | 계층형 아키텍처 원칙 강제 및 유지보수성 회복 |
| 컴포넌트 간 순환 참조(A→B→C→A)로 인해 모듈 분리 및 독립 단위 테스트 불가능 | 역방향 아키텍처 시각화 부재로 패키지 간 의존성 스파게티화 방치 | DSM(Design Structure Matrix) 기반 순환 결합도 분석 및 의존관계 역전(DIP) 리팩토링 | 순환 의존성 완전 해소 및 모듈 독립성 확보 |
