## 한 줄 본질
- 서비스 초기 분산 시스템 구축 시 발생하는 네트워크 복잡성과 분산 트랜잭션 오버헤드 병목 → 모든 비즈니스 기능을 하나의 애플리케이션 프로세스와 단일 데이터베이스로 통합 패키징하는 아키텍처 / 시스템 비대화 시 빌드 지연 및 장애 격리 불가

## 핵심 용어
- 모듈러 모놀리스(Modular Monolith): 단일 프로세스로 배포되지만, 코드 내부에서는 패키지 및 모듈 간 명확한 인터페이스 경계를 강제하여 결합도를 낮춘 아키텍처
- 스트랭글러 무화과나무 패턴(Strangler Fig Pattern): 기존 거대 모놀리스 시스템의 기능을 마이크로서비스로 하나씩 점진적으로 떼어내어 교체하는 마이그레이션 기법

## 핵심 통찰
- 모놀리스는 "극복해야 할 레거시 안티패턴"이 아니라, 비즈니스 도메인 경계가 불명확한 스타트업이나 초기 프로젝트에서 가장 빠르게 가치를 검증할 수 있는 최적의 아키텍처임
- 분산 시스템의 네트워크 레이턴시, 데이터 정합성(Saga 패턴), 관측성(OpenTelemetry) 인프라 비용을 감당할 수 없는 조직이 유행을 좇아 MSA를 도입하면 "분산 모놀리스(Distributed Monolith)"라는 최악의 재앙에 직면함
- 모놀리스를 유지하면서도 생산성을 극대화하려면 단일 DB 내에서 스키마 분리를 유도하고 패키지 가시성(Visibility)을 제어하는 모듈러 모놀리스 설계가 필수적임

## 이웃 토픽과 구분
- 모놀리식 아키텍처 vs 마이크로서비스 아키텍처(MSA): 모놀리식 = 단일 프로세스·단일 DB·메모리 호출(단순성, ACID) / MSA = 독립 서비스·독립 DB·네트워크 IPC 호출(확장성, 결함 격리)

## 내 의견
- [무분별한 MSA 맹신과 모놀리스 폄하에 대한 반성] 초기 요구사항이 계속 바뀌는 단계에서 MSA로 쪼개어 네트워크 호출과 데이터 동기화 비용으로 프로젝트가 좌초되는 사례 다수 목격 → 나라면: 초기 구축 단계에서는 모듈러 모놀리스(Modular Monolith)로 시작하여 도메인 경계와 비즈니스 모델을 안정화한 뒤, 트래픽 폭증이나 팀 분할이 명확해지는 시점에 스트랭글러 패턴으로 특정 서비스만 선별 추출하는 점진적 아키텍처 진화 전략 채택
