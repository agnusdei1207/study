## 한 줄 본질
- 시장 선점을 위해 완성도 높은 설계 대신 임시변통 코드를 선택하는 트레이드오프 병목 → 미래에 지불해야 할 추가 개발 공수(이자)를 인지하고 계획적으로 리팩토링을 통해 상환 → 단기적 신속한 제품 출시(TTM) 달성 / 미상환 시 이자 복리 증가로 개발 생산성 붕괴(파산) 위험

## 핵심 용어
- 기술 부채의 이자(Interest): 부채 코드를 방치함으로써 신규 기능 개발 시마다 추가로 소모되는 분석 시간, 디버깅 공수, 버그 수정 비용
- SQALE(Software Quality Assessment based on Lifecycle Expectations): 소스코드의 결함과 품질 규칙 위반을 정상화하는 데 필요한 수정 시간을 비용(일/시간)으로 환산하는 정량화 방법론

## 핵심 통찰
- 기술 부채는 무조건 나쁜 악이 아니라, 스타트업이나 신사업에서 제품 시장 적합성(PMF)을 검증하기 위해 금융 대출처럼 전략적으로 레버리지할 수 있는 공학적 도구임
- 가장 위험한 부채는 의도하지 않은 '부주의하고 무모한 부채'이며, 이는 신입 엔지니어의 미숙함이나 코드 리뷰 부재에서 비롯됨
- 부채를 상환하지 않고 기능 개발만 계속 밀어붙이면 어느 순간 새로운 코드 한 줄을 추가하는 비용이 시스템 전체를 재작성하는 비용보다 커지는 '기술적 파산'에 직면함

## 이웃 토픽과 구분
- 기술 부채 vs 소프트웨어 결함(Bug): 결함 = 현재 기능이 스펙대로 동작하지 않는 오류 / 기술 부채 = 기능은 정상 동작하나 내부 구조가 썩어 있어 미래 변경을 방해하는 상태

## 문제·원인·대책

| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 소스코드 복잡도 증가로 신규 기능 개발 기간이 기존 대비 5배 증가 | 수년간 릴리스 일정만 맞추느라 리팩토링과 테스트 코드 작성 생략 | SonarQube 정량 지표 기반 기술 부채 비율(Technical Debt Ratio) 측정 및 가시화 | 경영진과 부채 규모 객관적 공유 |
| 비즈니스 부서에서 기술 부채 상환 작업을 일정 낭비로 치부 | 부채를 코드 용어로만 설명하여 비즈니스 영향도 소통 실패 | 부채 상환을 통한 신규 기능 출시 리드타임 단축 효과를 ROI로 환산 보고 | 스프린트 백로그의 20%를 부채 상환에 고정 할당 합의 |

## 내 의견
- [경영진 탓만 하며 부채를 방치하는 개발팀의 직무유기] "회사가 시간을 안 줘서 코드가 엉망이다"라고 핑계 대면서 정작 리팩토링의 정량적 근거는 한 줄도 제시하지 못하는 경우 다반사 → 나라면: CI/CD에 정적 분석 도구를 연동하여 신규 커밋에 부채가 유입되는 것을 원천 차단하는 'Zero New Debt' 정책을 수립하고, 매 스프린트마다 가장 자주 수정되는 핫스팟(Hotspot) 파일 상위 3개를 집중 상환
