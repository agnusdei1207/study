```text
 ┃
 ┣━ Ⅰ 개요 ───── 생산자와 소비자 간 속도 차이로 인한 데이터 유실 방지 → 선입선출(FIFO) 버퍼링
 ┣━ Ⅱ 특징 ───── FIFO(First-In First-Out) · 양방향 입출력 분리(Front 추출, Rear 삽입) · 공정성(Fairness)
 ┣━ Ⅲ 구조 ───── 선형 큐(Linear) · 원형 큐(Circular) · 우선순위 큐(Priority) · 덱(Deque)
 ┣━ Ⅳ 흐름 ───── Enqueue(Rear 1 증가 후 삽입) / Dequeue(Front 1 증가 후 추출) / 원형 큐의 모듈로(`%`) 연산
 ┣━ Ⅴ 비교 ───── 선형 큐(잘못된 포화 상태 문제) vs 원형 큐(메모리 재사용) vs 우선순위 큐(힙 기반)
 ┗━ Ⅵ 실무 ───── 큐 오버플로우 및 메모리 누수 / 원형 큐의 공백/포화 구분(`(rear+1)%size == front`)
```

## 한 줄 본질
- 데이터를 생성하는 생산자(Producer)와 처리하는 소비자(Consumer)의 작업 처리 속도 불일치 병목 → 한쪽 끝(Rear)에서는 삽입만 하고 반대쪽 끝(Front)에서는 삭제만 하는 선입선출(FIFO) 메커니즘 적용 → 작업 순서의 공정성 보장 및 비동기 완충 버퍼 역할 / 고정 배열 사용 시 메모리 낭비와 큐 포화 위험

## 핵심 그림
```text
[ 선형 큐의 잘못된 포화 문제 ]
  Index:   [ 0 ]   [ 1 ]   [ 2 ]   [ 3 ]
  Data :  | 빈칸| | 빈칸| |  C  | |  D  |  <-- Rear=3 (배열 끝에 도달)
                           ^
                         Front=2
  * 앞쪽(0, 1)이 비어있음에도 Rear가 끝에 도달하여 추가 삽입 불가능!

[ 원형 큐 (Circular Queue)로 해결 ]
               [ 0 ]
             /       \
          [ 3 ]       [ 1 ]    * 포인터 이동: (Pointer + 1) % Size
             \       /         * 포화 조건 : (Rear + 1) % Size == Front
               [ 2 ]           * 공백 조건 : Front == Rear
```

## 핵심 용어
- 잘못된 포화(False Overflow): 선형 큐에서 Dequeue 연산으로 앞쪽 공간이 비어 있음에도 Rear 포인터가 배열의 마지막 인덱스에 도달해 더 이상 데이터를 삽입하지 못하는 현상
- 배압(Backpressure): 큐의 버퍼가 가득 찼을 때 생산자의 데이터 생성 속도를 늦추도록 피드백을 전달하여 시스템 크래시를 방지하는 제어 기법

## 핵심 통찰
- 선형 큐의 잘못된 포화 문제를 해결하기 위해 데이터를 매번 앞으로 당기는(Shift) 방식은 $O(N)$의 이동 비용이 들므로, 포인터를 원형으로 회전시키는 원형 큐($O(1)$)가 필수적임
- 원형 큐에서는 공백 상태(`Front == Rear`)와 포화 상태를 구분하기 위해 항상 배열의 한 칸을 비워두는 것이 표준 설계 원칙임
- OS의 프로세스 레디 큐(Ready Queue), 네트워크 라우터의 패킷 버퍼, 비동기 메시지 큐(Kafka, RabbitMQ)의 밑바탕은 모두 이 FIFO 큐 알고리즘임

## 이웃 토픽과 구분
- 큐 vs 스택: 큐 = 선입선출(FIFO), 순서 보장/버퍼링 / 스택 = 후입선출(LIFO), 실행 취소/복귀 주소 저장

## 문제·원인·대책
- 사례: 125회 기출 대용량 패킷 버퍼링 모듈의 선형 큐 메모리 고갈 사태
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 큐에 빈 공간이 있음에도 패킷 인입 시 Queue Full 에러 발생 | 선형 큐 구조 사용으로 인한 잘못된 포화(False Overflow) 발생 | 배열 인덱스를 모듈로 연산(`% size`)으로 순환시키는 원형 큐(Ring Buffer) 도입 | 배열 메모리 100% 재활용 및 $O(1)$ 버퍼링 달성 |
| 이벤트 폭증 시 컨슈머 처리 지연으로 큐 메모리 오버플로우 발생 | 언바운디드 큐(Unbounded Queue)의 무제한 메모리 팽창 방치 | 바운디드 큐(Bounded Queue) 설정 및 리액티브 스트림즈 배압(Backpressure) 적용 | 프로세스 OOM 방지 및 시스템 안정적 보호 |

## 내 의견
- [언바운디드 인메모리 큐를 남발하는 개발 관행의 위험] Java의 `new LinkedBlockingQueue()`를 파라미터 없이 호출하여 큐 크기를 무제한(Integer.MAX_VALUE)으로 열어두었다가, 대규모 트래픽 유입 시 힙 메모리가 터져 서버가 동반 자살하는 사고 빈발 → 나라면: 프로덕션 환경의 모든 큐는 반드시 최대 크기를 지정하는 바운디드 큐로 강제하고, 큐 임계치(80%) 도달 시 생산자에게 429 Too Many Requests를 반환하는 배압 서킷 브레이커 구축
