## 답안 골격
```text
[DIP] ◀━━ 머리: Ⅶ 내 의견 (생성자 주입 기반 불변성 확보와 클린/헥사고날 아키텍처 코어 격리)
 ┃
 ┣━ Ⅰ 개요 ───── 상위 정책 모듈이 하위 구현 모듈에 종속되는 모순 극복 → 추상화(인터페이스)에 의존
 ┣━ Ⅱ 특징 ───── SOLID 원칙의 D · 상위/하위 모듈 간 디커플링 · 인터페이스 소유권 역전 · 단위 테스트 용이성
 ┣━ Ⅲ 구조 ───── 고수준 정책 모듈 / 추상 인터페이스(Interface) / 저수준 구현체(DB, 외부 API, 메시지 큐)
 ┣━ Ⅳ 흐름 ───── 고수준 모듈의 인터페이스 정의 → 저수준 모듈이 인터페이스 구현 → IoC 컨테이너가 런타임에 의존성 주입(DI)
 ┣━ Ⅴ 비교 ───── 전통적 절차지향 의존(상위가 하위 구현 직접 의존) vs DIP 적용 객체지향 의존(모두 추상화에 의존)
 ┗━ Ⅵ 실무 ───── new 키워드 남발로 인한 강한 결합 / Spring IoC 컨테이너 및 생성자 주입(Constructor Injection)
```
- 필수 키워드: DIP · SOLID · 고수준 모듈 · 저수준 모듈 · 추상화(Interface) · 제어의 역전(IoC) · 의존성 주입(DI)
- 배점 전략: 10점 = Ⅰ 정의 2대 규칙 → Ⅲ 의존성 방향 역전 구조도 → Ⅴ 전통적 구조 vs DIP 비교 / 25점 = Ⅰ~Ⅶ 전개, DIP와 OCP(개방폐쇄)의 유기적 관계 및 헥사고날 아키텍처 실무 적용
- 기출: 121회 1교시 `객체지향 설계원칙 중 의존관계 역전 원칙(DIP)` → Ⅰ·Ⅲ·Ⅳ·Ⅵ

## 한 줄 본질
- 핵심 비즈니스 로직(고수준)이 MySQL이나 특정 결제 SDK(저수준)의 구체 클래스를 직접 `new`하여 하부 변경 시 상부가 깨지는 병목 → 고수준 모듈이 정의한 추상 인터페이스를 저수준 모듈이 구현하도록 화살표 방향을 역전 → 구현체 교체와 단위 테스트의 완전한 독립성 확보 / 인터페이스 파일 증가

## 핵심 그림
```text
[ 전통적 의존 구조 : 상위가 하위에 종속 ]
  +------------------+          +------------------+
  | OrderService     | -------> | MySQLRepository  | (하위 구체 클래스 변경 시
  | (고수준 비즈니스)|  (의존)  | (저수준 구현체)  |  상위 비즈니스 코드 수정 불가피)
  +------------------+          +------------------+

[ DIP 적용 구조 : 둘 다 추상화에 의존 (화살표 역전) ]
  +------------------+          +-----------------------+
  | OrderService     | -------> | <<interface>>         |
  | (고수준 정책)    |  (의존)  | OrderRepository       |
  +------------------+          +-----------------------+
                                            ^
                                            | (구현/실체화)
                                +-----------------------+
                                | MySQLRepository       |
                                | (저수준 구현 세부)    |
                                +-----------------------+
```

## 핵심 용어
- 고수준 모듈(High-level Module): 시스템의 핵심적인 비즈니스 도메인 규칙과 비즈니스 정책을 담고 있는 모듈
- 저수준 모듈(Low-level Module): 파일 입출력, 데이터베이스 접근, 네트워크 통신, 외부 API 연동 등 구체적인 세부 기술을 다루는 모듈

## 핵심 통찰
- DIP의 두 가지 핵심 규칙: "1. 고수준 모듈은 저수준 모듈에 의존해서는 안 되며, 둘 다 추상화에 의존해야 한다. 2. 추상화는 세부사항에 의존해서는 안 되며, 세부사항이 추상화에 의존해야 한다."
- '역전(Inversion)'의 진정한 의미는 소스코드 의존성의 방향이 런타임 제어 흐름의 방향과 반대로 뒤집힌다는 뜻이며, 인터페이스의 '소유권(Ownership)'이 하위 구현체가 아닌 상위 고수준 모듈에 있다는 점임
- DIP가 성립해야만 실제 DB 없이 가짜 모의 객체(Mock)를 주입할 수 있어, 비즈니스 로직을 밀리초 단위로 검증하는 순수 단위 테스트(Unit Test)가 가능해짐

## 이웃 토픽과 구분
- DIP vs DI(Dependency Injection): DIP = 설계 '원칙(Principle)'으로 무엇에 의존해야 하는지(추상화)를 규정 / DI = 그 원칙을 달성하기 위한 구체적인 '구현 메커니즘(Pattern/Mechanism)'으로 외부에서 객체를 찔러 넣어주는 행위
