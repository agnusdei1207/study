## 핵심 용어
- 메시지 채널(Message Channel): 송신자와 수신자를 가상으로 연결하는 통로로, 점대점(Point-to-Point)과 발행-구독(Publish-Subscribe)으로 구분됨
- 내용 기반 라우터(Content-Based Router): 메시지 본문이나 헤더의 데이터 값(예: 국가 코드, 결제 수단)에 따라 적절한 수신 채널로 경로를 분기하는 라우팅 패턴
- 분할기 및 집계기(Splitter & Aggregator): 단일 복합 메시지를 여러 개의 개별 하위 메시지로 쪼개어 병렬 처리한 후, 상관관계 ID(Correlation ID)로 다시 취합하는 패턴
- 클레임 체크(Claim Check): 대용량 페이로드를 별도 데이터 저장소(S3/DB)에 저장하고, 메시지 버스에는 해당 데이터의 참조 키(Key)만 전달하여 네트워크 부하를 줄이는 패턴
- 데드 레터 채널(Dead Letter Channel): 유효성 검증 실패나 처리 불가능한 오류 메시지를 따로 수집하여 메인 파이프라인의 블로킹을 방지하는 장애 격리 패턴

## 핵심 통찰
- EIP의 가장 큰 가치는 서로 다른 벤더 제품(MQ, Kafka, ESB, REST) 간에 '어떻게 메시지를 가공하고 전달할 것인가'에 대한 공통의 개념적 표준 어휘(Taxonomy)를 확립했다는 점임
- 점대점(Point-to-Point) 연동의 스파게티 구조($N \times (N-1)/2$)를 중앙 브로커 기반의 $O(N)$ 구조로 선형화함
- 분산 환경의 불안정성을 전제로 설계되었기 때문에 재시도(Retry), 타임아웃, 멱등성 수신(Idempotent Receiver) 패턴이 내장되어 네트워크 단절 시에도 데이터 최종 일관성(Eventual Consistency)을 확보함

## 이웃 토픽과 구분
| 비교 항목 | EIP (Enterprise Integration Patterns) | ESB (Enterprise Service Bus) | API Gateway |
| :--- | :--- | :--- | :--- |
| **본질 및 위상** | 메시지 통합을 위한 설계 패턴 카탈로그 | EIP 패턴들을 탑재한 중앙 집중형 미들웨어 솔루션 | 마이크로서비스 전면의 진입점 제어 라우터 |
| **통합 방식** | 비동기 메시지 지향 (Message-Oriented) | 중앙 버스 기반 프로토콜 변환 및 라우팅 | 동기식 HTTP/gRPC API 프록시 및 인증 |
| **구현 라이브러리** | Apache Camel, Spring Integration | Mule ESB, Oracle Service Bus, WSO2 | Spring Cloud Gateway, Kong, Envoy |
| **주요 적용 영역** | 복잡한 백엔드 시스템 간 비동기 데이터 파이프라인 | 전사 레거시 및 ERP/CRM 시스템 간 연계 | 클라이언트와 MSA 서비스 간 단일 창구 |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **메시지 중복 수신으로 인한 결제/주문 다중 처리** | 네트워크 타임아웃으로 브로커가 메시지를 재전송(At-least-once 전달 특성) | 고유 메시지 ID 기반 중복 제거를 수행하는 Idempotent Consumer 패턴 적용 |
| **일부 파편 메시지 지연으로 인한 집계(Aggregation) 락** | Splitter로 분할된 하위 작업 중 하나가 장애로 응답하지 않아 Aggregator 대기열 누적 | Completion Timeout 및 최소 수신 조건(Completion Size) 기반 Fallback 정책 설정 |
| **대용량 메시지 전송 시 브로커 메모리 고갈(OOM)** | 수십 MB 단위의 첨부파일이나 XML/JSON 페이로드가 브로커 큐로 직접 유입 | 오브젝트 스토리지(S3)에 원본 저장 후 참조 URL만 전달하는 Claim Check 패턴 적용 |

  - 2) 메시지 분할 및 집합을 위한 Splitter와 Aggregator 패턴의 동작 메커니즘과 Correlation ID 활용 방안을 도식으로 제시하시오.
  - 3) Kafka 및 Apache Camel 프레임워크를 활용하여 Dead Letter Channel과 Idempotent Consumer를 구축하는 아키텍처 방안을 제시하시오.

## 내 의견
- 과거 온프레미스 시절의 거대하고 무거운 모놀리식 ESB 제품군은 몰락했으나, 그 기반이 되었던 EIP 설계 철학은 현대 클라우드 네이티브 MSA 및 이벤트 기반 아키텍처(EDA)에서 완전히 부활하였음
- 현대 아키텍처에서는 중앙 집중식 무거운 ESB 대신, 마이크로서비스 내부에서 경량 임베디드 라이브러리인 Apache Camel이나 Spring Integration을 활용하여 EIP 패턴을 구현하는 추세임
- 특히 분산 트랜잭션(Saga Pattern) 구현 시 보상 트랜잭션 흐름을 통제하고, Kafka의 파티션 순서 보장 한계를 극복하기 위해 EIP의 Resequencer 및 Aggregator 패턴을 결합하는 역량이 실무 아키텍트의 핵심 경쟁력임
