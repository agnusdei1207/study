## 답안 골격
```text
[캡슐화] ◀━━ 머리: Ⅶ 내 의견 (단순 데이터 묶기를 넘어선 도메인 불변식(Invariants) 보호 메커니즘)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터와 처리 로직의 분리로 인한 무결성 훼손 방지 → 단일 단위로 결합 및 보호
 ┣━ Ⅱ 특징 ───── 높은 응집도(Cohesion) 달성 · 결합도 완화 · 정보은닉(Information Hiding)의 기반
 ┣━ Ⅲ 구조 ───── 상태(State/속성) + 행위(Behavior/메서드) + 접근 제어자(Private, Protected, Public)
 ┣━ Ⅳ 흐름 ───── 객체 내부 상태 정의 → 비즈니스 검증 메서드 구현 → 외부에서는 메시지 호출(Tell, Don't Ask)
 ┣━ Ⅴ 비교 ───── 캡슐화(데이터와 행위의 번들링) vs 정보은닉(세부 구현의 은폐) vs 추상화(공통 특징 추출)
 ┗━ Ⅵ 실무 ───── 빈약한 도메인 모델(Anemic Domain Model) / 풍부한 도메인 모델(Rich Domain Model)
```
- 필수 키워드: 데이터와 행위의 결합 · 높은 응집도 · 접근 제어자 · 불변식(Invariants) · 빈약한 도메인 모델 · Tell Don't Ask
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 캡슐화 구조도 → Ⅴ 캡슐화와 정보은닉 비교 / 25점 = Ⅰ~Ⅶ 전개, 빈약한 도메인 모델 극복 및 객체지향 설계 원칙(SOLID) 연계
- 기출: 129회 1교시 `객체지향 프로그래밍의 캡슐화(Encapsulation)` → Ⅰ·Ⅱ·Ⅲ / 131회 1교시 `캡슐화와 정보은닉` → Ⅴ

## 한 줄 본질
- 데이터는 구조체에 두고 비즈니스 로직은 외부 함수에 분리해 작성함으로써 발생하는 상태 무결성 파괴와 중복 코드 병목 → 객체의 데이터(상태)와 그 데이터를 다루는 로직(행위)을 하나의 캡슐 안에 묶고 스스로 자신의 불변식을 검증 → 데이터 무결성 보장 및 응집도 극대화 / 객체 간 상호작용 설계 복잡도 대가

## 핵심 그림
```text
  [ 외부의 무단 접근 및 무결성 침해 차단 ]
                  | (오직 Public Message 전송만 허용)
                  v
+-------------------------------------------------------------+
| [ Capsule: BankAccount Class ]                              |
|                                                             |
|   - private balance: long (데이터 보호)                     |
|                                                             |
|   + public deposit(amount): void {                          |
|       if (amount <= 0) throw Exception;                     |
|       this.balance += amount;  <-- 스스로 불변식 검증       |
|     }                                                       |
+-------------------------------------------------------------+
```

## 핵심 용어
- 빈약한 도메인 모델(Anemic Domain Model): 객체가 데이터(getter/setter)만 가지고 있고 모든 비즈니스 로직은 서비스 계층의 절차지향 코드에 빼앗겨 캡슐화가 파괴된 안티패턴
- 도메인 불변식(Domain Invariants): 객체가 생애주기 동안 항상 참으로 유지해야 하는 비즈니스 규칙(예: "계좌 잔액은 마이너스가 될 수 없다")

## 핵심 통찰
- 캡슐화는 단순히 코드를 클래스 파일 하나에 몰아넣는 문법적 행위가 아니라, 객체 스스로가 자신의 상태 무결성을 책임지도록 권한과 책임을 부여하는 객체지향의 근본 원리임
- 캡슐화가 무너지면 동일한 검증 로직(예: 잔액 체크)이 프론트엔드, 컨트롤러, 서비스 레이어에 수십 군데로 중복 복사되어 버그의 온상이 됨
- 정보은닉은 캡슐화라는 장치를 통해 얻을 수 있는 가장 중요한 혜택 중 하나임(캡슐화는 그릇이고, 정보은닉은 그 그릇으로 내용물을 가리는 행위)

## 이웃 토픽과 구분
- 캡슐화 vs 정보은닉: 캡슐화 = 데이터와 메서드를 하나로 묶는 것(연관 요소 집약) / 정보은닉 = 외부에서 알 필요 없는 내부를 감추는 것(비밀 보호)

## 문제·원인·대책
- 사례: 129회 기출 주문-결제 시스템의 빈약한 도메인 모델로 인한 비즈니스 로직 파편화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 승인 후 주문 상태가 '결제대기'로 남아있는 상태 불일치 버그 | 서비스 클래스에서 setter를 호출하며 상태 전이 검증 누락 | 주문 엔티티 내부에 `pay()` 비즈니스 메서드를 두고 상태 전이를 캡슐화 | 유효하지 않은 상태 전이 원천 차단 |
| 할인 정책 변경 시 10개 서비스 클래스를 찾아다니며 할인 계산식 수정 | 할인 데이터와 계산 로직이 분리되어 서비스 레이어에 중복 산재 | 할인 금액 계산 책임을 `DiscountPolicy` 객체 내부로 캡슐화 | 비즈니스 변경 영향 단일 클래스로 격리 |
