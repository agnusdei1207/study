## 한 줄 본질
- 고객의 모호한 요구사항을 개발자가 자의적으로 추측하여 코딩하면서 구조적 타협이 누적되는 병목 → 발생한 기술부채와 코드스멜을 정량화하고 동작 보존 기반의 리팩토링을 반복 수행 → 소프트웨어 건강성 및 변경 용이성 회복 / 요구사항 단계의 원인 차단 없이는 재발

## 핵심 그림
```text
[ 불명확한 요구사항 (모호성, 누락, 잦은 변경) ]
                        |
                        v (원인)
+-------------------------------------------------------------+
| 1. 기술부채 (Technical Debt) : 일정 압박과 타협의 산물      |
|    - 단기적 땜질 구현 선택 -> 장기적 이자(유지보수 비용) 폭증|
+-------------------------------------------------------------+
                        |
                        v (증상)
+-------------------------------------------------------------+
| 2. 코드스멜 (Code Smell) : 부패한 설계의 외적 징후          |
|    - 거대 클래스, 중복 코드, 샷건 수술, 기능 편애 발현     |
+-------------------------------------------------------------+
                        |
                        v (처방)
+-------------------------------------------------------------+
| 3. 리팩토링 (Refactoring) : 외부 동작 유지 + 내부 구조 개선 |
|    - 자동화 회귀 테스트 기반 -> 기술부채 원금 상환         |
+-------------------------------------------------------------+
```

## 핵심 용어
- 기술부채(Technical Debt): 단기적 출시를 위해 구조적 설계를 포기하고 임시방편으로 개발함으로써, 향후 변경 시 치러야 할 추가 작업 비용
- 코드스멜(Code Smell): 소프트웨어에 심각한 문제가 있음을 암시하는 소스코드 상의 미시적 징후(Martin Fowler 제창)

## 핵심 통찰
- 요구사항의 불명확성은 코딩 단계에서 단순히 버그 1~2개를 만드는 데 그치지 않고, 개발자들로 하여금 불필요한 분기와 중복 코드를 양산하게 만들어 시스템 전체의 설계를 부패시킴
- 코드스멜은 기술부채가 임계점을 넘어 겉으로 드러나는 '통증(Symptom)'이며, 이를 방치하면 어떤 변경도 할 수 없는 소프트웨어 엔트로피(Software Entropy) 상태에 도달함
- 리팩토링은 "코드를 예쁘게 만드는 작업"이 아니라, 회귀 테스트 스위트의 보호 아래 기술부채의 고금리 이자를 탕감하는 필수적인 '재무 활동'임

## 이웃 토픽과 구분
- 기술부채 vs 소프트웨어 결함(Bug): 결함 = 런타임에 오작동하거나 크래시를 내는 직접적 오류 / 기술부채 = 현재 정상 작동하지만 미래의 변경 비용을 지수적으로 폭증시키는 구조적 문제

## 내 의견
- [요구사항 불명확을 개발자 개인의 실력 탓으로 돌리는 관리적 오류] 모호한 기획 문서를 던져주고 일정을 독촉하면서 결함과 스파게티 코드가 나오면 개발자 탓을 하는 후진적 프로젝트 관리 관행 탈피 필요 → 나라면: 사용자 스토리마다 "Given-When-Then" 형식의 실행 가능한 인수 기준(Acceptance Criteria) 작성을 의무화하고, 인수 테스트를 통과해야만 개발 완료로 인정하는 '완료의 정의(DoD)' 기준 엄격화
