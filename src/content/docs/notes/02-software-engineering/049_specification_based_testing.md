 ┃

 ┣━ Ⅱ 특징 ───── 블랙박스 기법의 표준 체계 · 사용자 관점 검증 · 명세 누락 및 오작동 식별

 ┗━ Ⅵ 실무 ───── 다중 조건 조합 시 테스트 케이스 기하급수 폭증 / 직교 배열 및 페어와이즈(Pairwise) 기법

- 필수 키워드: ISO/IEC/IEEE 29119 · 동등 분할 · 경계값 분석 · 결정 테이블(Decision Table) · 상태 전이(State Transition) · 유스케이스 · 페어와이즈
- 배점 전략: 10점 = Ⅲ 5대 핵심 기법 분류 표 → Ⅴ 테스트 설계 3대 접근법 비교 / 25점 = Ⅰ~Ⅶ 전개, 137회 기출 프로그램 명세 기반 테스트 케이스 도출 실전
- 기출: 137회 2교시 `동적 테스트 및 명세 기반 테스트 케이스 작성` → Ⅰ·Ⅲ·Ⅳ / 125회 2교시 `소프트웨어 시험에 사용되는 기법` → Ⅲ·Ⅴ

## 한 줄 본질
- 소프트웨어 내부 구현과 무관하게 사용자가 정의한 요구사항 명세서대로 시스템이 입력에 대해 정확한 출력을 내는지 검증하지 못하는 품질 병목 → 수학적 도메인 분할(동등분할/경계값)과 논리 모델(결정테이블/상태전이)을 적용해 명세에 부합하는 최소 테스트 케이스 도출 → 요구사항 구현 완성도 보장 / 명세서 자체의 오류나 누락은 발견하기 어려운 한계

## 핵심 그림
```text
                  [ 명세 기반 테스트 설계 기법 체계 ]
+----------------------+----------------------+----------------------+
| 도메인 분할 기법     | 논리/조합 관계 기법  | 상태/시나리오 기법   |
+----------------------+----------------------+----------------------+
| - 동등 분할 (EP)     | - 결정 테이블 (DT)   | - 상태 전이 테스팅   |
|   (유효/무효 클래스) |   (조건과 행동 매트릭스)| (상태, 이벤트, 전이)  |
| - 경계값 분석 (BVA)  | - 페어와이즈 (Pairwise)| - 유스케이스 테스팅  |
|   (2-Point / 3-Point)|   (2-way 파라미터 조합)| (기본/대안/예외 흐름)|
+----------------------+----------------------+----------------------+
```

## 핵심 용어
- 결정 테이블 테스팅(Decision Table Testing): 복잡한 논리적 조건(If-Else 조합)들의 참/거짓 조합과 그에 따른 시스템의 행동(Action)을 표 형태로 정의하여 누락된 조건 분기를 찾아내는 기법
- 페어와이즈(Pairwise / All-Pairs): 대부분의 소프트웨어 결함이 2개 입력 변수의 상호작용에서 발생한다는 통계적 원리를 이용해, 모든 가능한 쌍(Pair)을 최소한의 테스트 케이스로 조합하는 기법

## 핵심 통찰
- 명세 기반 테스트 기법은 "소프트웨어가 무엇을 해야 하는가"를 검증하며, 단위 테스트부터 시스템, 인수 테스트까지 모든 레벨에서 광범위하게 쓰임
- 동등 분할과 경계값 분석은 '단일 입력값' 검증에 강하고, 결정 테이블과 페어와이즈는 '여러 입력값의 조합' 검증에 강하며, 상태 전이 테스팅은 '시간과 순서에 따른 객체 변화' 검증에 강함
- 명세서 자체가 모호하거나 불완전하면 명세 기반 테스트 설계 역시 부실해지므로, 테스트 설계 활동 자체가 명세서의 모호성을 조기에 잡아내는 '정적 검증(Review)' 효과를 냄

## 이웃 토픽과 구분
- 명세 기반 vs 구조 기반: 명세 기반 = 요구사항(SRS)을 기반으로 테스트 케이스 도출 / 구조 기반 = 소스코드의 제어 흐름(CFG)을 기반으로 테스트 케이스 도출

## 문제·원인·대책
- 사례: 137회 기출 입력 조건 [10 미만 or 100 초과: Fail, 10~100: Pass, 비정수: Invalid] 명세 검증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 복합 할인 조건(회원등급 5종 x 결제수단 4종 x 쿠폰유무 2종 = 40조합) 전수 테스트로 납기 지연 | 모든 조건의 직적(Cartesian) 조합 전수 테스트 시도 | 페어와이즈(Pairwise) 조합 알고리즘 도구(PICT 등) 적용 | 케이스 수를 40개에서 10개로 75% 감축 및 2인자 결함 100% 탐지 |
| 통장 잔액이 마이너스인데도 출금 승인이 떨어지는 상태 논리 버그 | 입력값 범위만 검증하고 계좌 상태(정상, 거래정지, 한도초과) 전이 검증 누락 | 상태 전이 트리(0-스위치, 1-스위치) 테스트 기법 적용 | 비정상적 상태 전이 결함 조기 적출 |

## 이렇게 출제된다
- 제137회 2교시 5번: "소프트웨어 테스트 중 동적 테스트에 대하여 설명하시오. 테스트 케이스 작성" → 요구 포인트: 명세 기반 테스트의 원리와 기법 분류 + 주어진 프로그램 명세(정수 판별, 범위 판별)에 맞춘 테스트 케이스 표 작성
- 제125회 2교시 6번: "소프트웨어의 시험(Test)에 사용되는 다음의 기법" → 요구 포인트: 명세 기반, 구조 기반, 경험 기반 테스팅의 장단점 및 상호보완

## 내 의견
- [테스트 케이스를 개발자 머릿속 직관으로 때우는 후진성] 명세 기반 공학 기법을 모른 채 "대충 0 넣고 100 넣고 글자 몇 개 쳐보고 끝났다"며 테스트 완료를 보고하는 주먹구구 테스팅 만연 → 나라면: QA 조직 표준으로 동등 분할 및 경계값 분석 매트릭스 작성을 의무화하고, 복잡한 정책 조건에 대해서는 결정 테이블(Decision Table) 작성을 산출물 승인 기준에 포함시켜 테스트 품질을 상향 평준화
