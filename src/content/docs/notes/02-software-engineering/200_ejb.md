## 핵심 용어
- EJB 컨테이너(EJB Container): EJB 컴포넌트의 생성, 소멸, 트랜잭션 관리, 스레드 관리, 보안 검사, 인스턴스 풀링 등 엔터프라이즈 라이프사이클을 통제하는 런타임 환경
- 세션 빈(Session Bean): 클라이언트의 단일 비즈니스 작업을 수행하는 컴포넌트로, 상태를 유지하지 않는 Stateless와 상태를 보존하는 Stateful, 전역 단일 인스턴스인 Singleton이 있음
- 메시지 구동 빈(MDB, Message-Driven Bean): JMS(Java Message Service) 메시지 큐에 메시지가 도착했을 때 비동기 이벤트 방식으로 자동 구동되는 컴포넌트
- 컨테이너 관리 트랜잭션(CMT, Container-Managed Transaction): 코드 내에서 `commit`, `rollback`을 직접 작성하지 않고, 어노테이션이나 XML 선언만으로 컨테이너가 트랜잭션 경계를 제어하는 기능
- POJO(Plain Old Java Object): 특정 프레임워크의 클래스를 상속받거나 인터페이스를 강제로 구현하지 않는 가장 순수한 형태의 표준 자바 객체

## 핵심 통찰
- EJB의 이상(비즈니스 로직과 시스템 인프라 로직의 완전한 분리)은 매우 탁월했음
- 그러나 EJB 1.x와 2.x는 개발자가 단순한 빈 하나를 만들 때도 수많은 인터페이스(Home, Remote)를 상속받아야 했고, 무거운 XML 배포 서술자를 작성해야 했으며, 비싼 상용 WAS 없이 순수 단위 테스트(Unit Test)를 돌릴 수 없는 극단적인 '침투적 프레임워크(Invasive Framework)'였음
- 이러한 EJB의 복잡성과 벤더 락인에 반발하여, 마틴 파울러와 로드 존슨(Rod Johnson) 등이 "순수한 객체지향(POJO)으로 돌아가자"고 주창하며 탄생시킨 것이 바로 스프링 프레임워크(Spring Framework)임
- EJB 3.0에 이르러 스프링의 IoC/DI와 어노테이션을 전격 수용하고 엔티티 빈을 JPA(Java Persistence API)로 완전히 재정립하였음

## 이웃 토픽과 구분
| 비교 항목 | EJB (Enterprise Java Beans) | Spring Framework | JavaBeans |
| :--- | :--- | :--- | :--- |
| **핵심 위상** | 공식 자바 표준(Java EE) 분산 컴포넌트 | 사실상의 표준(De facto) 경량 애플리케이션 프레임워크 | GUI 및 데이터 전송용 단순 자바 객체 (DTO) |
| **침투성** | 강한 침투성 (WAS 및 EJB 인터페이스 종속) | 비침투적 (POJO 기반 의존성 주입) | 비침투적 |
| **실행 환경** | 무거운 Full Java EE WAS 필수 (WebLogic 등) | 경량 서블릿 컨테이너(Tomcat)로 충분 | JVM 어디서나 실행 가능 |
| **단위 테스트** | 극도로 어려움 (컨테이너 목업 난항) | 매우 쉬움 (단순 객체 생성 및 Mockito) | 매우 쉬움 |
| **핵심 기제** | 선언적 트랜잭션, RMI 분산 객체 | IoC/DI, AOP, 추상화 계층(PSA) | 기본 생성자, Getter/Setter |

## 문제·원인·대책
| 문제상황 | 원인 | 기술적 대책 |
| :--- | :--- | :--- |
| **개발 생산성 저하 및 로컬 테스트 불가** | 코드 한 줄 수정 후에도 무거운 상용 WAS를 수 분 동안 재기동해야 함 | Spring Boot 및 내장 톰캣(Embedded Tomcat) 도입을 통한 로컬 핫 리로딩 구축 |
| **세션 빈 상태 동기화로 인한 WAS 클러스터 부하** | Stateful Session Bean 남용으로 분산 메모리 세션 복제 트래픽 폭증 | 무상태 세션 빈(Stateless)으로 전면 전환하고 상태는 외부 분산 캐시(Redis)에 저장 |
| **레거시 EJB 시스템의 유지보수 인력 단절** | EJB 2.x 스펙의 고도 복잡성으로 인해 신규 개발자의 기피 심화 | EJB 인터페이스를 감싸는 Spring 어댑터 레이어를 구축하고 점진적 POJO 리팩토링 |

## 이렇게 출제된다
- **10점형**: EJB(Enterprise Java Beans)의 개념 및 3대 빈(세션 빈, 엔티티 빈, 메시지 구동 빈)의 특징을 설명하시오.
- **25점형**: 
  - 1) 기업용 분산 컴포넌트 아키텍처에서 EJB 컨테이너가 제공하는 핵심 서비스(트랜잭션, 라이프사이클, 풀링, 보안)를 도식으로 설명하시오.
  - 2) 무상태 세션 빈(Stateless)과 상태유지 세션 빈(Stateful)의 동작 원리 및 클러스터링 환경에서의 차이점을 비교하시오.
  - 3) EJB 2.x의 한계점과 이를 극복하며 등장한 POJO 기반 스프링 프레임워크(IoC/DI, AOP)의 아키텍처적 혁신 요인을 심층 논하시오.

## 내 의견
- EJB는 오늘날 거의 사용되지 않는 레거시 기술로 취급받지만, 현대 소프트웨어 아키텍처의 핵심 축인 '선언적 트랜잭션 관리', 'AOP 기반 관심사 분리', 'ORM(JPA)'의 모태가 되었다는 점에서 소프트웨어 공학사적으로 매우 중요한 토픽임
- 현대 엔터프라이즈 시스템 구축 시에는 과거 EJB의 벤더 락인 및 무거운 인프라 침투성의 과오를 반복하지 않기 위해, 특정 프레임워크나 벤더 라이브러리에 순수 비즈니스 로직이 오염되지 않도록 육각형 아키텍처(Hexagonal Architecture)의 원칙을 엄격히 고수해야 함
- 현재 공공/금융 차세대 사업에 남아있는 레거시 EJB 시스템은 스트랭글러 패턴을 통해 Spring Cloud 및 컨테이너 기반 마이크로서비스로 전환하는 것이 시급한 과제임
