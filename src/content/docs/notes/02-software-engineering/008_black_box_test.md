## 답안 골격
```text
[블랙박스 테스트] ◀━━ 머리: Ⅶ 내 의견 (명세 기반 설계 자동화 및 경계값 중심의 테스트 슬림화)
 ┃
 ┣━ Ⅰ 개요 ───── 내부 구조 미인지 상태에서 사용자 관점 기능 결함 식별 → 명세서 기반 입력-출력 검증
 ┣━ Ⅱ 특징 ───── 내부 코드 독립적 · 사용자 요구 중심 · 개발자와 테스터 관점 분리
 ┣━ Ⅲ 구조 ───── 입력 데이터군 → 대상 시스템(Black Box) → 실제 출력 vs 기대 출력 비교
 ┣━ Ⅳ 흐름 ───── ① 요구 명세 분석 → ② 동등 분할군 식별 → ③ 경계값 도출 → ④ 테스트 케이스 작성/실행
 ┣━ Ⅴ 비교 ───── 블랙박스 테스트 vs 화이트박스 테스트
 ┗━ Ⅵ 실무 ───── 기법 조합(동등분할, 경계값, 결정테이블, 상태전이, 유스케이스) / 테스트 케이스 폭증
```
- 필수 키워드: 명세 기반 · 동등 분할 · 경계값 분석 · 결정 테이블 · 상태 전이 · 원인-결과 그래프
- 배점 전략: 10점 = Ⅰ 정의 → Ⅲ 개념도 → Ⅵ 5대 설계 기법 요약 / 25점 = Ⅰ~Ⅶ 전개, 구체적 입력 조건별 테스트 케이스 작성 예시 제시
- 기출: 129회 1교시 `화이트박스와 블랙박스 테스트 비교` → Ⅴ / 122회 3교시 `날짜 처리 모듈 블랙박스 테스트 케이스 작성` → Ⅳ·Ⅵ

## 한 줄 본질
- 소프트웨어 내부 코드를 알 수 없거나 볼 필요가 없는 시스템 검증 병목 → 외부 요구사항 명세서를 바탕으로 입력 도메인을 분할하고 경계값을 추출해 기대 결과와 대조 → 사용자 요구사항 부합성 보장 / 내부 분기 누락 및 비효율적 경로 탐지 불가 한계

## 핵심 그림
```text
+----------------+      +---------------------------+      +----------------+
|  입력 데이터    | ---> | [ Black Box Software ]    | ---> |  실제 출력값   |
| (Input Domain) |      | (내부 소스코드 미참조)     |      +----------------+
+----------------+      +---------------------------+              |
                                                                   v (비교)
                                                           [ 기대 출력값 ]
```

## 핵심 용어
- 동등 분할(Equivalence Partitioning): 입력 데이터 영역을 유효/무효 동등 클래스로 나누고 각 클래스에서 대표값 하나를 선택하는 기법
- 경계값 분석(Boundary Value Analysis): 오류가 가장 빈번히 발생하는 동등 클래스의 경계(최소, 최대, 바로 안쪽, 바로 바깥쪽) 값을 테스트 데이터로 선정하는 기법

## 핵심 통찰
- 완전한 블랙박스 테스트는 입력 조합의 수가 무한대에 가까워 불가능하므로, 통계적으로 오류 확률이 높은 경계값과 위험도 기반으로 대상을 축소해야 함
- 시스템 테스트와 인수 테스트 단계의 주력 기법이며, 사용자의 시나리오를 반영하는 유스케이스 기반 테스트와 결합할 때 실효성이 극대화됨
- 내부 소스코드의 변경에 영향을 받지 않으므로 API 계약이나 UI 기능 검증의 회귀 테스트 안전망으로 적합함

## 이웃 토픽과 구분
- 블랙박스 vs 화이트박스: 블랙박스 = 명세 기반, 기능 동작 검증 / 화이트박스 = 코드 구조 기반, 제어 흐름 및 분기 커버리지 검증

## 문제·원인·대책
- 사례: 122회 기출 YYYY-MM-DD 날짜 입력 처리 모듈의 블랙박스 검증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 윤년 2월 29일 처리 오류가 운영 배포 후 발생 | 단순 동등 분할만 수행하고 4년/100년/400년 주기 경계값 조건 누락 | 2단계 경계값 분석(Robustness Testing) 기법 적용 | 윤년/평년 경계 조건의 100% 결함 적출 |
| 입력 필드 조합 증가로 테스트 케이스 수천 개 폭증 | 모든 필드의 직적(Cartesian Product) 조합 전수 테스트 시도 | 페어와이즈(Pairwise / All-Pairs) 직교 배열 테스트 적용 | 테스트 케이스 수 80% 감축 및 2방향 상호작용 결함 100% 탐지 |

## 이렇게 출제된다

## 내 의견
- [케이스 숫자 채우기에 급급한 무의미한 테스트 작성] 단순히 테스트 케이스 100건을 채우기 위해 의미 없는 정상값만 반복 입력하여 시간만 낭비하는 현장 관행 목격 → 나라면: 요구사항 명세서의 결정 테이블(Decision Table)을 기반으로 비즈니스 규칙과 예외 조건을 1:1 매핑하고, 페어와이즈 도구를 CI 파이프라인에 통합해 최소 비용으로 최대 결함 적출
