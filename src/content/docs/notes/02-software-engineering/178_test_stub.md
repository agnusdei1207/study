## 핵심 용어
- 테스트 더블(Test Double): 영화 촬영 시 위험한 연기를 대신하는 스턴트 더블처럼, 테스트 시 실제 복잡한 객체(DB, 네트워크)를 대신하는 모든 가짜 객체(Dummy, Stub, Fake, Spy, Mock)의 총칭
- 하향식 통합 테스트(Top-down Integration): 최상위 제어 모듈부터 시작하여 아래로 내려가며 통합하는 방식으로, 아직 개발되지 않은 하위 모듈 자리에 스텁(Stub)을 끼워 넣어 검증함

## 핵심 통찰
- 스텁(Stub)은 하위 모듈의 "복잡한 내부 로직"을 구현하는 것이 아니라, 상위 모듈이 다음 단계로 넘어갈 수 있도록 "사전에 약속된 단순한 반환값"만 제공하는 것이 핵심임
- 외부 유료 API(SMS 발송, 신용평가 조회, 카드사 결제)를 테스트할 때 매번 실제 API를 찌르면 비용이 발생하고 계정이 차단될 수 있으므로 스텁을 통한 격리가 필수적임
- 제라드 메스자로스(Gerard Meszaros)의 정의에 따르면, 스텁은 "상태 검증(State Verification)"을 위해 간접 입력값을 제공하는 반면, 목(Mock)은 "호출 횟수나 인자 전달 여부(행위 검증)"를 스스로 검사한다는 차이가 있음

## 이웃 토픽과 구분
- 테스트 스텁(Stub) vs 모의 객체(Mock): 스텁 = 호출되면 정해진 데이터만 조용히 반환함(수동적) / 목 = 해당 메서드가 정확히 1번 호출되었는지, 어떤 인자가 넘어왔는지 감시하고 검증함(능동적)

## 문제·원인·대책
- 적용 상황: 외부 신용카드 결제 게이트웨이 연동 주문 모듈 단위 테스트
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 단위 테스트 실행 시 외부 결제사 서버 점검이나 네트워크 지연으로 빌드가 무작위 실패 | 단위 테스트가 외부 네트워크와 타사 인프라에 직접 의존하는 결합 결함 | Mockito 기반 가상 결제 스텁(`when(pay()).thenReturn(SUCCESS)`) 주입 | 외부 환경과 무관한 100% 결정론적 고속 테스트 보장 |
| 스텁으로 테스트를 완벽히 통과했으나 실제 결제사 연동 시 응답 필드 규격 불일치로 장애 | 스텁이 반환하는 가짜 JSON 구조와 실제 상용 API 명세의 불일치 | 계약 기반 테스팅(Pact, Spring Cloud Contract)으로 스텁과 실제 API 스펙 동기화 | 외부 인터페이스 통합 결함 사전 차단 |

## 내 의견
- [과도한 스텁 남발로 인한 가짜 통과(False Positive) 위험 경계] 모든 의존성을 스텁으로 대체하여 단위 테스트는 100% 성공하지만 실제 DB 쿼리나 네트워크가 붙으면 에러가 터지는 맹점 발생 → 나라면: 단위 테스트는 Mockito 스텁으로 비즈니스 분기를 빠르게 1차 검증하고, 통합 테스트 단계에서는 Testcontainers를 활용하여 실제 도커 기반 DB와 로컬 Mock 서버(WireMock)를 연동하는 계층화된 검증 파이프라인 수립
