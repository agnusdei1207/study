## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **병목 분석(Bottleneck Analysis / Performance Diagnostics)**: 소프트웨어 시스템 및 IT 인프라 전 구간에서 트래픽 증가 시 처리량(Throughput)을 제약하고 응답 지연(Latency)을 급증시키는 가장 취약한 단일 제약 자원(Resource) 또는 소프트웨어 임계 경로(Critical Path)를 정량적으로 식별하고 근본 원인을 규명하는 성능 엔지니어링 기법.
- **자원 포화에 따른 대기열 폭증 및 병목 이동 결함(Queue Saturation & Bottleneck Shift Defect)**: 특정 자원(예: DB Connection Pool)의 용량이 한계에 도달했을 때 요청이 대기열(Queue)에 적체되어 응답시간이 비선형적으로 폭증하는 현상과, 해당 병목을 튜닝한 직후 차순위 자원(예: CPU 또는 Disk I/O)으로 병목 지점이 연쇄 전이되는 현상을 사전에 예측하지 못하는 구조적 결함.
- **임계 경로(Critical Path)**: 요청 처리 과정에서 병렬로 수행되는 구간 가운데 가장 오래 걸려 전체 응답시간을 결정하는 호출 경로로, 이 경로 위의 구간을 줄이지 않으면 다른 구간을 아무리 튜닝해도 응답시간이 줄지 않는다.

</details>

- 정의/개념: 처리량을 제한하는 **임계 경로**를 식별하는 성능 진단 기법
- 배경/필요성: 제약 자원과 임계 경로를 규명하지 않은 무분별한 하드웨어 증설은 데이터베이스 락 경합이나 슬로우 쿼리를 해소하지 못하고 인프라 비용만 낭비하므로, 자원 관점(USE)과 서비스 관점(RED) 및 분산 추적을 결합한 **병목 분석**을 통해 지연 구간을 정밀 국소화하고 튜닝 후 병목 이동을 통제할 필요

#### 한줄 요약
- 무분별한 증설은 병목이 아닌 자원에 비용을 쓰는 것이므로, 진단에 드는 관측 비용이 증설 한 번의 낭비보다 항상 절감

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- 병목 진단 2대 핵심 방법론:
  - **USE 방법론 (Utilization, Saturation, Errors / Brendan Gregg)**: 모든 하드웨어 자원(CPU, 메모리, 디스크, 네트워크)의 사용률, 큐 적체 포화도, 에러 발생 여부를 점검하는 인프라 중심 분석.
  - **RED 방법론 (Rate, Errors, Duration / Tom Wilkie)**: 모든 마이크로서비스 엔드포인트의 초당 요청률(Rate), 실패 요청 비율(Errors), 처리 소요 시간(Duration)을 측정하는 서비스 중심 분석.

</details>

- 자원 **USE**와 서비스 RED를 시계열로 교차 진단
- 분산 추적으로 **임계 경로**의 락·슬로우 SQL 격리
- 단일 요인 변경 후 **병목 이동** 여부를 동일 부하로 검증

#### 한줄 요약
- 자원 관점과 서비스 관점을 따로 보면 각각은 정상인데 합치면 병목인 지점이 드러나며, 단일 요인 튜닝은 사이클 비용을 내고 인과관계를 확보

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **베이스라인(Baseline)**: 튜닝 전에 동일 부하 프로파일로 측정해 둔 기준 성능 수치로, 이후 변경의 효과를 같은 조건에서 비교하는 대조군이 된다.
- **분산 추적(Distributed Tracing)**: 요청마다 트레이스 ID를 부여해 마이크로서비스 경계를 넘는 호출을 스팬(Span) 단위로 이어 붙여, 전체 응답시간 중 어느 서비스·구간이 얼마를 소비했는지 국소화하는 관측 기법.
- **플레임 그래프(Flame Graph)**: 샘플링한 스택 트레이스를 함수별로 누적해 폭이 CPU 점유 시간에 비례하도록 그린 그림으로, 코드 수준에서 어느 함수가 핫스폿인지 한눈에 지목한다.

</details>

```text
[병목 분석 체계]
  │
  ├─ [기준 부하]
  │   └─ 재현 가능한 성능 베이스라인
  │
  ├─ [인프라 관측]
  │   └─ USE 방법론 (자원 사용률·포화도·에러)
  │
  ├─ [서비스 관측]
  │   └─ RED 방법론 및 APM 분산 추적
  │
  └─ [코드 프로파일링]
      └─ 플레임 그래프 및 슬로우 쿼리 격리
```

- 선의 의미: 상하 인터페이스 연결(`│`) 및 세부 관측 계층의 소속 관계(`├─`, `└─`)를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 기준 부하 | 재현 가능한 **베이스라인** 설정 |
| 인프라 관측 | 자원별 **USE** 지표 수집 |
| 서비스 관측 | API별 **RED**·**분산 추적** 수집 |
| 코드 프로파일링 | **플레임 그래프**·슬로우 쿼리로 함수·락 핫스폿 격리 |

#### 한줄 요약
- USE는 자원 경계에서 RED는 API 경계에서 같은 부하를 보므로 두 관측이 어긋나는 지점이 병목 후보이며, 코드 프로파일링이 함수·락·쿼리 단위 지목을 대신해 추정 튜닝의 실패를 차단

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **USE·RED 상관분석**: 인프라 자원 포화 시점과 서비스 지연 급증 구간의 시계열 타임스탬프를 대조해 인과관계를 입증하는 분석 절차.
- **병목 이동(Bottleneck Shift)**: 1차 병목 해소 후 처리량이 증가하면서 숨어 있던 차순위 자원(CPU, I/O 등)으로 부하가 전이되는 현상.

</details>

```text
[병목 진단 및 개선 루프] (진행 ①→④, 관측 분석 및 튜닝 피드백)
  │
  ├─ [부하 주입기] (① 기준 부하 프로파일 인가)
  │
  ├─ [인프라·APM 관측 계층] (② USE 자원 포화 및 RED 지연 상관 분석)
  │
  ├─ [프로파일러] (③ 임계 경로 락·슬로우 쿼리 국소화)
  │
  └─ [튜닝 실행기] (④ 단일 요인 변경 및 동일 부하 재시험)
```

분기 결과: 동일 부하 재시험에서 성능 목표 충족 시 최적화 확정하나, 차순위 자원으로 병목 이동 시 1단계 관측부터 재시험 사이클 비용 추가 발생

#### 한줄 요약
- 한 번에 한 요인만 바꾸면 사이클 수가 늘지만, 여러 요인을 동시에 손대면 재시험 결과가 병목 이동인지 개선 실패인지 구분되지 않아 원인 재탐색 비용 증대

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- 성능 분석 3대 진단 프레임워크 비교:
  - USE 방법론: 자원 중심 (Utilization, Saturation, Errors).
  - RED 방법론: 서비스 중심 (Rate, Errors, Duration).
  - Google SRE 4대 황금 신호: 사용자 및 시스템 통합 (Latency, Traffic, Errors, Saturation).

</details>

| 비교 항목 | USE 방법론 (Brendan Gregg) | RED 방법론 (Tom Wilkie) | 4대 황금 신호 (Google SRE) |
|:---|:---|:---|:---|
| 진단 대상 | 하드웨어·OS 물리 자원 | 마이크로서비스 API | 분산 서비스 전체 |
| 핵심 지표 | 가동률·포화도·에러 | 요청률·에러율·지연 | 지연·트래픽·에러·포화도 |
| 분석 관점 | 자원 공급자 관점 | 서비스 소비자 관점 | 시스템·사용자 통합 관점 |
| 주요 활용 | 인프라 병목 식별 | 호출 지연 분석 | SLO 모니터링 |
| 한계 | 코드·쿼리 추적 불가 | 자원 고갈 원인 미제공 | 커널 프로파일 부족 |

#### 한줄 요약
- USE와 RED는 같은 병목을 공급자와 소비자 양쪽에서 보는 상보 관계이고 황금 신호는 그 둘을 SLO 하나로 묶은 축약이므로, 계층별 진단 순서에 따라 체계적 적용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **마이크로 버스트(Micro-burst)**: 수 ms 단위로 순간 도착률이 평균의 수 배로 치솟아 큐를 넘치게 하지만 초 단위 평균 지표에서는 사라지는 부하 패턴으로, 평균 사용률이 낮아도 순간 포화와 드롭을 일으킨다.
- **런큐(Run Queue)**: CPU 코어마다 실행 가능 상태로 스케줄링을 기다리는 스레드를 줄 세운 커널 자료구조로, 그 길이가 코어 수를 넘는 시간이 CPU 포화(Saturation)를 직접 나타낸다.
- **eBPF(extended Berkeley Packet Filter)**: 커널을 수정하지 않고 검증된 소형 프로그램을 커널 이벤트(스케줄러·시스템 콜·네트워크)에 붙여 실행하는 기술로, 런큐 지연 같은 지표를 마이크로초 해상도로 낮은 오버헤드에 수집한다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 평균값이 순간 **마이크로 버스트** 은폐 | **eBPF**로 고해상도 **런큐** 측정 | 순간 포화 식별 |
| 튜닝 후 차순위 자원이 새 병목으로 전환 | 동일 부하로 **병목 이동** 재시험 | 연쇄 병목 조기 식별 |
| 동시 변경으로 개선 원인 규명 불가 | 단일 요인 변경 후 재검증 | 튜닝 인과관계 보존 |

#### 한줄 요약
- 세 대책의 공통 비용은 시간이고 얻는 것은 판단의 확실성이므로, 시간을 아끼려 동시에 변경하면 원인 재탐색 비용으로 환원

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **OpenTelemetry**: 분산 시스템 전반의 트레이스, 메트릭, 로그를 통합 수집하여 서비스 간 지연과 병목을 추적할 수 있도록 지원하는 클라우드 네이티브 관찰성 표준 프레임워크.
- **RCA (Root Cause Analysis, 근본 원인 분석)**: 장애나 성능 저하를 유발한 표면적 증상 뒤에 숨어 있는 가장 핵심적인 설계 결함, 자원 경합 또는 코드 결함을 논리적으로 규명하는 진단 기법.

</details>

- 자원과 서비스 전 구간의 제약 요인을 실측 기반으로 규명하는 병목 분석은 인프라 자원 포화와 임계 경로 지연을 국소화하는 **성능 진단 엔지니어링**의 핵심 기법으로 정착
- 실무 엔지니어는 인프라 USE와 서비스 RED 지표를 교차 분석하고, 가설 기반 **단일 요인 튜닝**과 동일 부하 재시험을 통해 차순위 자원으로의 병목 이동을 사전 차단하는 공학적 통제 체계 확립

#### 한줄 요약
- 병목은 제거되는 것이 아니라 이동하는 것이므로, 병목 해소 비용과 인프라 증설 비용 간의 트레이드오프를 평가해 종료 시점 결정
