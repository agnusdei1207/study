## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TPS 계산(Transactions Per Second Calculation / Throughput Sizing)**: 시스템 구축 및 용량 산정(Capacity Planning) 시 비즈니스 목표 거래량(일일/월간 거래 건수)과 사용자 행동 특성(동시 접속자 수, 체류/생각 시간, 응답시간)을 수학적 공식(대화형 응답시간 법칙)에 대입하여 초당 필수 처리 용량(TPS)과 피크(Peak) 부하를 정밀 산출하는 성능 공학 프로세스.
- **생각시간 누락 및 일 평균 평탄화에 따른 용량 산정 왜곡 결함(Flattening & Zero Think-Time Defect)**: 사용자의 생각시간($Z$, Think Time)을 0으로 가정하여 실제 필요 용량보다 10배 이상 인프라를 과다 증설(Over-sizing)하거나, 일일 총 거래량을 단순 24시간으로 균등 분할하여 특정 1시간의 피크 트래픽 집중률(Peak Factor 3~5배)을 반영하지 못해 오픈 당일 서버가 다운되는 구조적 결함.

</details>

- 정의/개념: 사용자 주기와 거래량으로 **TPS**를 구하는 처리량 산정 모델
- 배경/필요성: 생각시간을 무시하거나 일일 거래량을 24시간으로 단순 평탄화할 경우 인프라를 과다 증설하거나 피크 시간대 집중률 및 화면당 다중 API 증폭을 반영하지 못해 서버 다운이 발생하므로, 대화형 응답시간 법칙($X = \frac{N}{R + Z}$)과 피크 계수 및 API 배수를 결합해 **실제 백엔드 인프라 처리량(RPS)**을 정밀 산출할 필요

#### 한줄 요약
- TPS 계산은 대화형 응답시간 법칙과 피크 계수를 기반으로 시스템의 필수 초당 처리 용량을 수학적으로 산출

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **TPS 계산 4대 핵심 수리 파라미터**:
  - **동시 사용자 수 ($N$, Concurrent Users)**: 시스템에 로그인하여 지속적으로 화면을 조회하고 요청을 발생시키는 활성 사용자 수.
  - **평균 응답 시간 ($R$, Response Time)**: 요청 전송 후 서버로부터 최종 응답을 수신할 때까지의 시스템 지연 시간 (초).
  - **평균 생각 시간 ($Z$, Think Time)**: 응답 화면을 수신한 후 사용자가 내용을 확인하고 다음 버튼을 클릭할 때까지 머무르는 시간 (초).
  - **피크 집중 계수 (Peak Factor, $F_{peak}$)**: 일일 총 트래픽 중 최대 피크 시간대(1시간)에 집중되는 트래픽의 가중치 배수.

</details>

- 폐쇄형 큐에서 성립하는 **대화형 응답시간 법칙**
- 생각시간이 길수록 동일 사용자 수의 **TPS 감소**
- 피크 계수와 **API 호출 배수**를 반영한 인프라 부하 산출

#### 한줄 요약
- 대화형 응답시간 법칙, 생각시간 반비례 반영, 피크 계수 및 API 증폭 배수 결합 제공

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **TPS 산정 3대 핵심 수식 체계**:
  1. **대화형 폐쇄형 TPS 공식**: $TPS_{base} = \frac{N}{R + Z}$.
  2. **일일 거래량 기반 피크 TPS 공식**: $TPS_{peak} = \frac{\text{Daily Total Transactions} \times F_{peak}}{\text{Peak Operating Seconds}}$.
  3. **내부 API 처리량(RPS) 변환 공식**: $RPS = TPS \times M_{api}$ ($M_{api}$: 화면당 API 호출 수).

</details>

```text
[TPS 산정 변수 체계]
  │
  ├─ [사용자 주기 (Cycle Time)]
  │   ├─ 평균 응답시간 (R)
  │   └─ 평균 생각시간 (Z, Think Time)
  │
  ├─ [처리량 기준선 (Throughput)]
  │   ├─ 동시 활성 사용자 수 (N)
  │   └─ 기준 처리량 (TPS_base = N/(R+Z))
  │
  └─ [인프라 보정 계수]
      ├─ 피크 부하 집중 계수 (F_peak)
      └─ 화면당 API 호출 배수 (M_api)
```

- 선의 의미: 상하 인터페이스 연결(`│`) 및 TPS 산정 변수 세부 소속 관계(`├─`, `└─`)를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 사용자 주기 ($T_{cycle}$) | 응답시간과 생각시간의 합($R+Z$)으로 다음 요청까지의 순환시간 표현 |
| 기준 처리량 ($TPS_{base}$) | 동시 사용자 수 대비 순환시간($N/(R+Z)$)으로 평시 처리 용량 산출 |
| 피크 처리량 ($TPS_{peak}$) | 기준 TPS에 피크 집중 계수($F_{peak}$)를 반영한 집중 시간대 목표 처리량 산출 |
| 인프라 부하 ($RPS_{total}$) | 피크 TPS에 화면당 API 호출 배수($M_{api}$)를 곱한 백엔드 총 요청량 산출 |

#### 한줄 요약
- 기준 TPS는 동시 사용자와 순환시간에서 산출되고 피크 계수와 API 호출 배수가 곱해지므로, 보정 계수 누락 시 집중 시간대 장애 발생

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **대화형 응답시간 법칙(Interactive Response Time Law)**: 시스템 내 동시 사용자 수($N$), 평균 응답시간($R$), 사용자 생각시간($Z$) 사이의 관계 $X = \frac{N}{R+Z}$를 규정한 대기행렬 수리 법칙.
- **API 증폭 배수(API Multiplier)**: 단일 프론트엔드 비즈니스 트랜잭션 1건 처리를 위해 마이크로서비스 백엔드로 전달되는 하위 API 호출 건수.

</details>

```text
[TPS 및 인프라 부하 산출 경로] (진행 ①→④, 사용자 주기 반영 및 RPS 확정)
  │
  ├─ [사용자 행동 분석기] (① 응답시간 R 및 생각시간 Z 합산 순환주기 도출)
  │
  ├─ [기준 처리량 연산기] (② 동시 사용자수 N 기반 기준 TPS=N/(R+Z) 계산)
  │
  ├─ [피크 부하 보정기] (③ 시간대별 피크 집중 계수 F_peak 적용 목표 TPS 도출)
  │
  └─ [백엔드 용량 사이징기] (④ 화면당 API 호출 배수 M_api 곱산 최종 RPS 확정)
```

분기 결과: 업무 단위 기준 TPS 산출만으로 증설 시 피크 집중과 내부 API 증폭 누락으로 백엔드 DB 다운 위험 발생하므로 F_peak와 M_api 연쇄 보정 필수

#### 한줄 요약
- 생각시간은 기준 TPS를 낮추지만 피크 계수와 API 배수는 인프라 부하를 증폭시키므로, 두 보정 단계를 거쳐야 실제 요구 용량 도출

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **부하 모델링 2대 수리 방식 비교**:
  - 폐쇄형 부하 모델 (Closed Workload Model): 사용자 기반 ($X = \frac{N}{R+Z}$, 응답 지연 시 유입률 감소).
  - 개방형 부하 모델 (Open Workload Model): 도착률 기반 ($\lambda$ 고정, 응답 지연과 무관하게 지속 주입).

</details>

| 비교 항목 | 폐쇄형 부하 모델 | 개방형 부하 모델 |
|:---|:---|:---|
| 적용 기준 | **사용자 순환형** 서비스 | **독립 요청 도착형** 서비스 |
| 산출 공식 | **$X = \frac{N}{R + Z}$** | **$X = \lambda$** |
| 지연 영향 | 응답 지연 시 **유입률 감소** | 응답 지연에도 **유입률 유지** |
| 한계 | 생각시간 오차로 **TPS 왜곡** | 과부하 시 **대기열 적체** |

#### 한줄 요약
- 폐쇄형 모델은 사람의 대화형 서비스에, 개방형 모델은 시스템 간 독립 API 연계 사이징에 특화

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **페이싱(Pacing)**: 성능 시험에서 가상 사용자(VUser)가 반복적인 요청을 보낼 때 다음 반복 주기까지 강제로 부여하는 지연 시간으로, 목표 TPS를 일정하게 유지하도록 제어한다.
- **피크 계수(Peak Factor)**: 평상시 평균 트래픽 대비 가장 이용량이 집중되는 특정 시간대의 부하 배수로, 인프라의 최대 수용 한계를 결정한다.
- **API 증폭 배수(API Multiplier)**: 사용자의 단일 화면 클릭 또는 비즈니스 거래 1건으로 인해 백엔드 시스템 간에 연쇄적으로 발생하는 내부 마이크로서비스 API 호출 횟수이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 생각시간 누락으로 **TPS 과대 산정** | 로그 기반 **생각시간·페이싱** 적용 | **부하 현실성** 확보 |
| 일평균 적용으로 **피크 TPS 과소 산정** | 시간대별 **피크 계수** 반영 | **집중 부하** 수용 |
| TPS와 RPS 동일시로 **백엔드 과부하** | 거래별 **API 호출 배수** 반영 | **백엔드 용량** 확보 |

#### 한줄 요약
- Think Time 설정으로 부하를 현실화하고, 피크 계수로 집중률을 방어하며, API 배수로 백엔드 용량 확보

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **RPS(Requests Per Second)**: 초당 시스템으로 인입되는 원시 HTTP/gRPC 요청 수로, 비즈니스 단위 거래를 뜻하는 TPS와 구분하여 백엔드 서버의 실제 처리 부하를 측정한다.
- **용량 계획(Capacity Planning)**: 미래의 비즈니스 성장 및 피크 트래픽을 예측하여 하드웨어 자원(CPU, 메모리, 네트워크)의 증설 규모와 시점을 수리적으로 계획하는 활동이다.

</details>

- 사용자 상호작용 주기와 트랜잭션 특성을 수리적으로 연결해 필수 처리 용량을 도출하는 TPS 계산은 클라우드 오토스케일링과 용량 계획의 핵심 **성능 모델링 표준**으로 정착
- 실무 엔지니어는 로그 기반 **Think Time**과 페이싱을 적용해 가상 사용자 부하를 현실화하고, 피크 집중 계수($F_{peak}$)와 화면당 API 증폭 배수($M_{api}$)를 결합한 총 RPS 환산 기준 확립

#### 한줄 요약
- 대화형 응답시간 법칙과 피크 계수 보정을 통해 비즈니스 요구에 부합하는 정밀한 시스템 처리 용량 산정 체계 확립
