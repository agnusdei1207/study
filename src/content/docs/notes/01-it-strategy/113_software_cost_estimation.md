## 핵심 용어
- 기능점수(Function Point, FP): 사용자가 요구한 소프트웨어의 기능적 크기를 논리적 관점(데이터 저장 및 트랜잭션 입출력)에서 수량화하여 개발 언어와 무관하게 비용을 산정하는 표준 기법
- COCOMO(Constructive Cost Model): 보엠(Boehm)이 제안한 모델로 원시 코드 라인 수(KDSI)를 바탕으로 소프트웨어 복잡도(Organic, Semi-detached, Embedded)에 따른 승수 공식을 적용해 공수를 예측하는 모형
- 불확실성의 원추(Cone of Uncertainty): 프로젝트 초기(기획 단계)에는 비용 산정 오차가 4배(0.25x ~ 4.0x)에 달하지만, 분석·설계·구현 단계를 거치며 점차 1.0x로 수렴한다는 소프트웨어 공학 법칙

## 핵심 통찰
- LOC(코드 라인 수)는 개발자를 '복붙 장인'으로 만듦 → 코드가 길수록 돈을 더 주는 구조에서는 리팩토링이나 라이브러리 재사용을 할 유인이 사라지므로, 기능점수(FP)로 전환해야 간결하고 우수한 코드가 나옴
- 기획 단계에서는 '간이 기능점수법'을 써야 함 → 상세 테이블 명세서가 없는 발주 기획 단계에서 정규 FP를 고집하면 가짜 숫자를 넣게 되므로, 업무 화면과 엔티티 수만으로 평균 복잡도를 곱하는 간이법이 현실적임
- 비용 산정은 1회성 요식이 아니라 '지속적 보정(Calibration)'임 → 초기 산정치는 불확실성의 원추를 품고 있으므로, 분석/설계 완료 시점과 중간 컷오버 시점에 실제 진척 데이터를 바탕으로 대가를 사후 정산해야 함

## 이웃 토픽과 구분
- COCOMO vs 기능점수(FP): COCOMO = 기술적 구현 관점(코드 라인 수 기반) / 기능점수 = 사용자 및 비즈니스 관점(입출력 및 파일 인터페이스 기반)
