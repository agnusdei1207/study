## 답안 골격
```text
[RPO] ◀━━ 머리: Ⅶ 내 의견 (업무 영향도 분석(BIA)에 근거한 데이터 등급별 동기/비동기 복제 차등 적용)
 ┃
 ┣━ Ⅰ 개요 ───── 재난·재해 시 데이터 유실로 인한 비즈니스 중단 방지 → 허용 가능한 최대 데이터 손실 시점 기준 수립
 ┣━ Ⅱ 특징 ───── 데이터 손실 허용 척도(시점 기준) · 백업 및 복제 주기와 직결 · 비용과 지수적 반비례 관계 · BCP 핵심 지표
 ┣━ Ⅲ 구조 ───── 재해 발생 시점 ↔ 마지막 백업(복구) 시점 간의 시간 간격(ΔT) 측정 구조
 ┣━ Ⅳ 흐름 ───── ① 업무 영향도 분석(BIA) → ② 목표 RPO 결정 → ③ 데이터 복제 방식 선정(동기/비동기/스냅샷) → ④ DR 인프라 구축 → ⑤ 모의훈련 검증
 ┣━ Ⅴ 비교 ───── RPO vs RTO (데이터 손실 관점 vs 서비스 중단 시간 관점) / 동기 복제(RPO=0) vs 비동기 복제(RPO>0)
 ┗━ Ⅵ 실무 ───── RPO=0 달성을 위한 회선 비용 폭증 / 원거리 복제 시 트랜잭션 지연(Latency) / 스토리지 정합성 불일치
```
- 필수 키워드: 목표 복구 시점 · 데이터 손실 허용량 · BIA(업무영향도분석) · 동기식 복제(Sync) · 비동기식 복제(Async) · 미러링 · RTO
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ RPO 시간축 도식 → RPO vs RTO 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅲ 데이터 복제 기술 메커니즘과 Ⅵ 클라우드 액티브-액티브 DR 집중
- 기출: 133회 1교시 `BCP 수립 시 주요 지표와 DRS 구축 시 고려사항` → Ⅲ·Ⅴ, 140회 3교시 `클라우드 네이티브 무중단 아키텍처와 재해복구 전략(RPO/RTO)` → Ⅰ·Ⅵ

## 한 줄 본질
- 전산센터 화재·침수 등 재난 발생 시 직전까지 쌓인 트랜잭션 데이터가 소실되어 발생하는 금융·법적 파탄 방지 → 비즈니스가 감내할 수 있는 최대 데이터 손실 허용 한도를 시간 단위로 정의한 목표 복구 시점 → 데이터 연속성 및 비즈니스 회원 신뢰 보장 / RPO 0 달성을 위한 천문학적 인프라 비용 소요

## 핵심 그림
```text

│                                                                                           │
│   [ 마지막 백업/복제 시점 ]              [ 재해 발생 시점 ]               [ 서비스 정상 복구 시점 ]│
│              │                                  │                                  │      │
│              │◄─────── RPO (데이터 손실) ──────►│◄────── RTO (서비스 중단 시간) ────►│      │
│              │    (Recovery Point Objective)    │    (Recovery Time Objective)     │      │
│              │  "얼마나 이전 데이터로 복구할 것인가?"│  "얼마나 빨리 서비스를 살려낼 것인가?" │      │

│  [ 복구 기술 ]:                                                                            │
│  - RPO = 0: 실시간 동기식 복제 (Active-Active, 2PC, 스토리지 미러링)                      │
│  - RPO < 수분: 비동기식 로그 전달 (CDC, Kafka 미러링, WAL 전송)                           │
│  - RPO < 24시간: 일일 야간 배치 백업 (Tape, Cold 스토리지)                                 │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

## 핵심 용어
- RPO(Recovery Point Objective): 재해 발생 시점에서 거슬러 올라가 허용할 수 있는 최대 데이터 손실 시점(데이터가 유실되어도 비즈니스 연속성을 해치지 않는 시간 한계)
- 동기식 복제(Synchronous Replication): 주 센터 스토리지와 원격 DR 센터 스토리지 모두에 쓰기 작업이 완료되어야 트랜잭션을 승인하는 방식으로 RPO=0을 보장하나 네트워크 지연 발생
- 비동기식 복제(Asynchronous Replication): 주 센터에 먼저 쓰고 원격지로는 백그라운드로 데이터를 복제하는 방식으로 성능 저하는 없으나 재해 시 약간의 RPO 손실(수초~수분) 발생

## 핵심 통찰
- RPO=0(데이터 유실 제로)은 공학적으로 매우 비싼 목표임 → 빛의 속도 한계로 인해 원격지 거리가 100km를 넘어가면 동기식 복제로 인한 대기 시간 때문에 메인 트랜잭션 성능이 30% 이상 저하됨
- 모든 데이터의 RPO를 0으로 맞추려 해서는 안 됨 → 금융 계좌 잔액이나 결제 원장은 RPO=0이어야 하지만, 마케팅 클릭 로그나 추천 기록은 RPO 1시간이어도 비즈니스에 지장이 없음
- 최근 클라우드 네이티브 아키텍처에서는 전통적인 스토리지 미러링 대신 카프카(Kafka) 기반 분산 이벤트 스트리밍 및 다중 리전(Multi-Region) 비동기 복제로 RPO를 수 초 이내로 통제함

## 이웃 토픽과 구분
- RPO vs RTO: RPO = "어느 시점의 데이터까지 살릴 것인가?(데이터 손실 허용량, 시점)" / RTO = "재해 발생 후 몇 시간 만에 시스템을 다시 가동할 것인가?(서비스 중단 허용 시간, 기간)"

## 문제·원인·대책
- 사례: 140회 기출 IDC 화재 발생 시 백업 주기가 24시간 전으로 설정되어 있어 하루 동안의 고객 결제 데이터 수십만 건이 영구 유실된 사례
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 야간 백업 체계로 인한 치명적 일일 데이터 유실 | 스토리지 용량 및 네트워크 대역폭 비용 절감을 위한 배치 백업 고수 | 데이터베이스 트랜잭션 로그 실시간 CDC(Change Data Capture) 및 원격지 객체 스토리지 스트리밍 복제 | RPO를 24시간에서 1분 미만으로 단축 |
| 동기식 복제 적용 후 메인 결제 시스템 지연시간 폭증 | 200km 떨어진 원격지 DR 센터와의 물리적 네트워크 왕복 지연(RTT) | 금융 원장은 준동기(Semi-sync) 복제 적용, 일반 조작은 비동기 파티셔닝 분리 | 메인 트랜잭션 성능 확보 및 핵심 데이터 무결성 보장 |

## 이렇게 출제된다
- 제133회 1교시 9번: "BCP(Business Continuity Planning) 수립 시의 주요 지표와 DRS(Disaster Recovery System) 구축 시의 핵심 고려사항을 설명하시오." → 요구 포인트: Ⅲ RPO/RTO/RCO 핵심 지표 정의 + Ⅵ 재해복구센터 4대 유형(Mirror/Hot/Warm/Cold) 매핑
- 제140회 3교시 1번: "클라우드 네이티브 환경에서 무중단 아키텍처를 지향하는 시스템을 설계하여도 재해 및 재난 상황을 대비한 재해복구 전략 수립은 필수적이다. 복구 지표와 이중화 전략을 설명하시오." → 요구 포인트: Ⅰ RPO 정의 + Ⅳ 클라우드 멀티 리전 동기/비동기 아키텍처

## 내 의견
- [맹목적 RPO=0 환상 탈피와 비즈니스 데이터 계층화(Data Tiering) 복제 전략] 모든 인프라를 RPO=0으로 구축하려다 천문학적인 전용망 비용으로 프로젝트가 백지화되는 사례 빈발 → 나라면: 업무 영향도 평가(BIA)를 통해 1등급 핵심 금융 트랜잭션 데이터(RPO=0, 분산 쿼럼 합의), 2등급 마스터 기준정보(RPO<5분, 비동기 CDC), 3등급 이력/로그 데이터(RPO<24시간, 일일 스냅샷)로 철저히 3단계 티어링을 적용하여 제한된 예산 내에서 데이터 유실 리스크를 완벽 통제
