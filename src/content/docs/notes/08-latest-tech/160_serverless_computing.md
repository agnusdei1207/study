## Ⅰ. 개요

- **정의**: 클라우드 서비스 제공자가 서버 인프라 프로비저닝, 운영체제 패치, 자동 확장 및 용량 관리를 전담하고, 사용자는 이벤트 기반으로 코드를 실행하며 실제 자원 사용 시간(ms)에 대해서만 비용을 지불하는 클라우드 컴퓨팅 패러다임
- **배경 및 필요성**: 기존 가상머신(IaaS)이나 상시 가동 컨테이너(PaaS)는 트래픽이 전무한 유휴 시간에도 고정 비용이 발생하고 갑작스러운 부하 폭증 시 프로비저닝 지연(수 분 소요)이 발생하므로, 유휴 시 자원을 완전 회수(Scale-to-Zero)하여 비용을 최적화하고 수 밀리초 내에 수천 개의 동시 실행 인스턴스로 탄력 확장하는 무관리형 실행 환경의 필요성 대두

## Ⅱ. 특징

- **인프라 관리 제로(NoOps)**: 가상머신이나 컨테이너 호스트의 프로비저닝, OS 패치, 클러스터 확장을 클라우드 공급자가 전담
- **이벤트 구동 아키텍처**: HTTP 요청, 메시지 큐 수신, 객체 스토리지 파일 업로드 등 이벤트 발생 시점에 트리거되어 실행
- **유휴 자원 제로화(Scale-to-Zero)**: 트래픽이 없으면 실행 인스턴스를 0으로 회수하여 유휴 비용이 전혀 발생하지 않음
- **정밀 종량 과금제**: 함수 실행 횟수와 실행 시간(1ms 단위) 및 메모리 할당량에 비례하여 실제 소비된 자원만 과금

## Ⅲ. 구조 및 구성요소

```text
[Serverless Computing 아키텍처]
├── [이벤트 소스 계층] ──── API Gateway, Message Queue, EventBridge, Cloud Storage
├── [FaaS 실행 계층] ────── AWS Lambda, Cloud Run, Knative (격리 샌드박스)
├── [BaaS 서비스 계층] ──── Managed DB (DynamoDB), Auth (Cognito), Storage (S3)
├── [스케줄/계량 계층] ──── 자동 확장기 (Scale-to-Zero), 마이크로 미터링(과금)
└── [상태 관리 계층] ────── 분산 캐시(ElastiCache), 상태 머신(Step Functions)
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 구성요소 | 설명 | 주요 역할 |
|:---|:---|:---|
| 이벤트 소스 계층 | 비즈니스 트리거 발생 진입점 | REST API, 웹훅, DB 변경 스트림, 타이머 이벤트를 감지하여 함수로 라우팅 |
| FaaS 실행 계층 | 마이크로 가상화(Firecracker 등) 기반 런타임 | 안전하게 격리된 경량 샌드박스에서 사용자 정의 비즈니스 함수 즉시 실행 |
| BaaS 서비스 계층 | 클라우드 공급자 완전 관리형 백엔드 | 별도 인프라 구축 없이 API 호출을 통해 인증, 푸시 알림, 대규모 데이터베이스 연계 |
| 스케줄/계량 계층 | 동적 인스턴스 스케줄러 및 빌링 엔진 | 동시 요청 수에 맞춘 샌드박스 생성·회수 제어 및 1ms 단위 리소스 사용량 계량 |
| 상태 관리 계층 | 외부 영속 저장소 및 워크플로우 오케스트레이션 | 무상태 함수의 한계를 극복하기 위해 세션/데이터를 분산 저장하고 다단계 함수 제어 |

## Ⅳ. 흐름도

```text
[이벤트 감지 및 인입] (① HTTP 요청, 메시지 수신, 파일 업로드 등 이벤트 발생)
│
▼
[실행 환경 할당 평가] (② 웜(Warm) 샌드박스 존재 여부 확인 및 실행 경로 결정)
│
▼
[신규 환경 초기화] (③ 유휴 시 콜드 스타트 발생, 샌드박스 프로비저닝 및 코드 적재)
│
▼
[함수 비즈니스 로직 실행] (④ 이벤트 페이로드를 입력으로 로직 수행 및 외부 BaaS API 호출)
│
▼
[외부 상태 영속화 및 응답] (⑤ 분산 DB/스토리지에 상태 기록 후 클라이언트에 처리 결과 반환)
│
▼
[자원 회수 및 과금 계량] (⑥ 실행 완료 후 밀리초($ms$) 단위 계량 및 유휴 시 Scale-to-Zero 회수)
```

- 분기 결과: 웜 인스턴스 존재 시 지연 없는 즉각 실행, 유휴 상태 시 콜드 스타트 후 샌드박스 기동, 일정 유휴 시간 초과 시 자원 자동 회수

## Ⅴ. 종류 및 비교

| 구분 | FaaS (Function as a Service) | BaaS (Backend as a Service) | 서버리스 컨테이너 |
|:---|:---|:---|:---|
| 실행 단위 | 개별 함수 코드 블록 (Node.js, Python 등) | 완성형 관리형 API 서비스 (인증, DB 등) | OCI 컨테이너 이미지 (도커 컨테이너) |
| 제어 수준 | 순수 비즈니스 로직 코드만 작성 | API 요청 파라미터 및 보안 정책 설정 | OS 패키지, 라이브러리, 런타임 환경 전체 |
| 실행 시간 제한 | 짧은 시간 제한 (통상 최대 15분) | API 호출 단위 즉각 처리 | 상대적으로 긴 실행 시간 (수십 분~수 시간) |
| 적합 사례 | 이벤트 처리, 실시간 웹훅, ETL 파이프라인 | 모바일/웹 백엔드, 사용자 인증, 파일 저장 | 기존 레거시 앱 이전, 장기 배치 작업 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 신규 인스턴스 기동 시 콜드 스타트(Cold Start) 지연 | 프로비저닝된 동시성(Provisioned Concurrency) 및 SnapStart 적용 | 첫 요청 시 발생하는 런타임 초기화 지연 수초에서 수십 ms로 단축 |
| 무상태(Stateless) 구조로 인한 세션 데이터 소실 | Redis 분산 캐시 및 완전 관리형 NoSQL DB(DynamoDB)로 상태 외부화 | 다중 함수 인스턴스 간 데이터 정합성 보장 및 무상태 확장성 확보 |
| 특정 클라우드 벤더의 독점 API 종속(Vendor Lock-in) | Serverless Framework, Knative 등 오픈소스 서버리스 표준 추상화 적용 | 멀티 클라우드 및 온프레미스 하이브리드 이식성 확보 |

## Ⅶ. 결론

- **기술 위상/발전**: NoOps(운영 제로화)와 진정한 클라우드 탄력성을 실현한 대표 컴퓨팅 모델로 확고히 안착하였으며 최근에는 서버리스 LLM 추론(Bedrock, Cloudflare Workers AI) 및 엣지 컴퓨팅(Edge Functions) 영역으로 영역 확장 중
- **실무 적용/통제**: 가변적이고 이벤트 구동형인 워크로드에는 FaaS를, 장기 실행 및 복잡한 의존성을 갖는 애플리케이션에는 서버리스 컨테이너(Cloud Run/ECS Fargate)를 전략적으로 혼용하고, SnapStart 및 상태 외부화를 결합한 아키텍처 최적화 필수
