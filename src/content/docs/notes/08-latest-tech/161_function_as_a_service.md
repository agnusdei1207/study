## Ⅰ. 개요

- **정의**: 개발자가 서버 인프라를 프로비저닝하거나 관리할 필요 없이, 이벤트 발생 시에만 클라우드가 경량 샌드박스 환경을 동적으로 할당하여 사용자 함수 코드를 실행하고 밀리초 단위로 과금하는 서버리스 실행 모델
- **배경 및 필요성**: 전통적인 가상머신 및 컨테이너 기반 상시 실행 아키텍처는 간헐적인 이벤트 워크로드에서 유휴 비용 낭비와 인스턴스 부팅 지연에 따른 처리 병목을 유발하므로, 인프라 관리 부담(NoOps)을 완전히 제거하고 호출 횟수와 실행 시간(ms)에 비례하여 정확히 과금하는 이벤트 구동형 초경량 실행 아키텍처의 필요성 대두

## Ⅱ. 특징

- **이벤트 구동 실행**: HTTP 요청, 메시지 큐, 객체 스토리지 변경, 스케줄러 등 다양한 이벤트 소스와 결합하여 실행
- **완전한 무상태(Stateless)**: 함수 인스턴스는 호출 간 로컬 메모리나 디스크 상태를 보존하지 않으므로 상태는 외부 저장소에 위임
- **즉시적 수평 확장**: 이벤트 유입량 폭증 시 수천 개의 격리된 함수 인스턴스로 즉각 자동 스케일아웃(Auto-scaling)
- **정밀 종량 과금(Pay-per-Execution)**: 코드가 실행된 실제 시간(1ms 단위)과 할당된 메모리 크기에 비례하여 비용 산정

## Ⅲ. 구조 및 구성요소

```text
[Function as a Service 아키텍처]
├── [이벤트 인입 계층] ──── 이벤트 소스(HTTP, SQS, S3, Cron), 트리거 필터
├── [라우팅 및 제어] ──── 이벤트 라우터, 동시성 스케줄러, 인증/인가 엔진
├── [격리 런타임 계층] ── MicroVM (Firecracker), 샌드박스 컨테이너, 런타임 풀
├── [함수 로직 계층] ──── 사용자 비즈니스 코드, 환경 변수, 라이브러리 레이어
└── [외부 상태 계층] ──── 분산 캐시(Redis), 관리형 DB(DynamoDB), 객체 스토리지
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 구성요소 | 설명 | 주요 역할 |
|:---|:---|:---|
| 이벤트 소스/트리거 | 함수 실행의 발화점 | API Gateway 요청, SQS 메시지, S3 업로드 등 이벤트를 수신하여 호출 조건 평가 |
| 이벤트 라우터 | 제어면의 지능형 디스패처 | 인증·인가 검증 후 대상 함수 런타임으로 이벤트를 안전하게 라우팅 |
| 격리 런타임 계층 | MicroVM 기반 경량 실행 엔진 | 멀티테넌시 보안 격리를 보장하며 밀리초 단위로 함수 컨테이너 즉각 기동·회수 |
| 함수 로직 계층 | 사용자가 작성한 비즈니스 코드 | 단일 책임 원칙에 기반한 데이터 변환, 비즈니스 처리 및 외부 연계 수행 |
| 외부 상태 저장소 | 영속 상태 및 멱등성 보장 인프라 | 무상태 함수의 한계를 보완하기 위해 세션, 트랜잭션, 멱등 키(Idempotency Key) 영속화 |

## Ⅳ. 흐름도

```text
[이벤트 감지 및 인입] (① API Gateway, 메시지 큐 등으로부터 함수 호출 이벤트 발생)
│
▼
[트리거 규칙 및 동시성 평가] (② 라우터가 함수 매핑 및 동시 실행 제한 임계치 검증)
│
▼
[실행 환경 할당/초기화] (③ 기존 웜 컨테이너 재사용 또는 신규 MicroVM 콜드 스타트 기동)
│
▼
[함수 비즈니스 로직 실행] (④ 페이로드 전달 후 단일 목적의 비즈니스 연산 수행)
│
▼
[멱등 상태 영속화] (⑤ 멱등 키 검증 후 분산 DB에 상태 반영 및 결과 반환)
│
▼
[샌드박스 동결/회수] (⑥ 실행 완료 후 인스턴스 유휴 전환 및 일정 시간 후 Scale-to-Zero 회수)
```

- 분기 결과: 웜 환경 가용 시 즉각 실행, 가용 인스턴스 부재 시 콜드 스타트 기동, 동시성 초과 시 큐잉 또는 429 Throttle 오류 반환

## Ⅴ. 종류 및 비교

| 구분 | FaaS | 서버리스 컨테이너 | 상시 실행 서비스 (IaaS/PaaS) |
|:---|:---|:---|:---|
| 배포 단위 | 개별 함수 코드 (단일 함수) | 컨테이너 이미지 (Dockerfile) | VM 인스턴스 또는 파드(Pod) |
| 실행 수명 | 단기 실행 (수 초 ~ 최대 15분) | 중단기 실행 (수십 분 ~ 수 시간) | 무제한 상시 실행 (24x7 가동) |
| 상태 관리 | 완전 무상태 (외부 저장소 필수) | 무상태 권장 (볼륨 마운트 일부 지원) | 로컬 파일시스템 및 인메모리 세션 유지 |
| 과금 모델 | 실행 시간(ms) + 호출 횟수 | vCPU/vRAM 초 단위 사용량 | 프로비저닝된 인스턴스 시간당 고정 과금 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 신규 컨테이너 기동 시 콜드 스타트로 인한 꼬리 지연 | 프로비저닝된 동시성(Provisioned Concurrency) 및 SnapStart 적용 | 첫 호출 시 발생하는 초기화 지연을 밀리초 단위로 단축 |
| 네트워크 재시도에 따른 중복 이벤트 실행 위험 | 분산 락 및 멱등 키(Idempotency Key) 기반 조건부 쓰기 구현 | 이중 결제 및 데이터 중복 생성 사고 원천 방지 |
| 트래픽 급증 시 후단 RDBMS 커넥션 풀 고갈 | 관리형 커넥션 풀러(RDS Proxy) 도입 및 동시성 제한 설정 | 데이터베이스 장애 예방 및 안정적인 트래픽 완충 |

## Ⅶ. 결론

- **기술 위상/발전**: 서버리스 컴퓨팅 패러다임의 핵심 실행 계층으로 자리 잡았으며 최근에는 대규모 언어 모델(LLM) 기반의 Agentic 워크플로우 오케스트레이션 및 엣지 컴퓨팅(Cloudflare Workers) 환경의 핵심 기반으로 급속히 확장 중
- **실무 적용/통제**: 함수의 단일 책임 원칙(SRP)과 완전한 무상태(Stateless) 설계를 준수하고, 프로비저닝된 동시성과 RDS Proxy 등 관리형 인프라를 연계하여 콜드 스타트 및 후단 부하를 체계적으로 통제하는 아키텍처 수립 필수
