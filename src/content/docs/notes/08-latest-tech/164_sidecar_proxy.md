## Ⅰ. 개요

- **정의**: 메인 애플리케이션 컨테이너와 동일한 생명주기 및 네트워크 네임스페이스(Pod/Localhost)를 공유하며, 서비스의 인바운드/아웃바운드 트래픽을 가로채어 보안(mTLS), 라우팅, 복원력 정책을 대행하는 보조 프록시 배포 패턴
- **배경 및 필요성**: 다국어 마이크로서비스 환경에서 애플리케이션 코드에 통신 라이브러리를 직접 내장하는 방식은 언어별 SDK 유지보수 비용과 강한 결합 문제를 야기하므로, 네트워크 네임스페이스를 공유하는 독립 프로세스 프록시를 동반 배치하여 비즈니스 로직 수정 없이 공통 인프라 기능을 일괄 위임할 필요성 대두

## Ⅱ. 특징

- **동일 파드 및 네트워크 공유**: 주 애플리케이션과 동일한 파드(Pod) 내부에서 실행되며 루프백(Localhost) 인터페이스를 통해 초저지연 통신 수행
- **투명한 트래픽 가로챔**: iptables 또는 eBPF 리다이렉션 규칙을 적용하여 애플리케이션 설정 변경 없이 모든 네트워크 인/아웃바운드 패킷 가로챔
- **격리된 장애 도메인**: 파드 단위로 프록시가 격리 실행되므로 특정 프록시 고장이 전체 클러스터 통신 마비로 전파되지 않음
- **독립적인 생명주기 관리**: 메인 애플리케이션의 재빌드 없이도 프록시 이미지 업데이트 및 동적 구성 갱신(xDS) 가능

## Ⅲ. 구조 및 구성요소

```text
[Sidecar Proxy 아키텍처]
├── [트래픽 가로챔 계층] ── iptables PREROUTING/OUTPUT 리다이렉션, eBPF sockops
├── [프록시 코어 엔진] ──── Envoy Proxy (Worker 스레드, 비동기 이벤트 루프)
├── [동적 구성 관리] ──── xDS 수신 클라이언트 (LDS/RDS/CDS/EDS 구성 수신)
├── [보안/통신 정책] ──── mTLS 암호화/복호화 엔진, 서킷 브레이커, L7 라우팅 테이블
└── [애플리케이션 연계] ── Localhost 루프백 인터페이스 (UDS / TCP Socket)
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 구성요소 | 설명 | 주요 역할 |
|:---|:---|:---|
| 트래픽 가로챔 계층 | Linux 커널 네트워크 조작 모듈 | iptables NAT 규칙 또는 eBPF로 파드 인바운드/아웃바운드 패킷을 프록시 로컬 포트로 리다이렉트 |
| 프록시 코어 엔진 | Envoy 기반 고성능 프록시 프로세스 | 이벤트 기반 논블로킹 I/O 모델을 통해 대규모 동시 연결 중계 및 프로토콜 변환 수행 |
| xDS 동적 구성 클라이언트 | 중앙 제어면(Istiod 등) 연동 모듈 | gRPC 스트리밍을 통해 변경된 라우팅 규칙, 클러스터 엔드포인트, TLS 인증서를 무중단 갱신 |
| 보안/통신 정책 집행기 | L4/L7 세분화된 거버넌스 엔진 | mTLS 핸드셰이크, 인가 정책 검증, 타임아웃, 재시도, 서킷 브레이커 즉각 집행 |
| 애플리케이션 연계 인터페이스 | 메인 컨테이너와의 로컬 통신 채널 | 루프백(127.0.0.1) 또는 유닉스 도메인 소켓(UDS)을 통해 지연시간 오버헤드 극소화 |

## Ⅳ. 흐름도

```text
[아웃바운드 요청 발생] (① 메인 애플리케이션이 외부 서비스 도메인으로 HTTP 요청 송신)
│
▼
[iptables 트래픽 가로챔] (② 커널 iptables 규칙에 의해 로컬 사이드카 프록시 포트로 리다이렉션)
│
▼
[정책 집행 및 mTLS 처리] (③ 사이드카가 목적지 확인 후 mTLS 핸드셰이크 및 타임아웃/서킷브레이크 평가)
│
▼
[원격 대상 노드 전송] (④ 암호화된 mTLS 패킷을 대상 파드로 네트워크 전송)
│
▼
[인바운드 수신 및 복호화] (⑤ 대상 사이드카가 패킷 수신 후 mTLS 복호화 및 인가 정책 검증)
│
▼
[로컬 서비스 포워딩] (⑥ Localhost를 통해 대상 메인 컨테이너 프로세스로 평문 요청 전달)
```

- 분기 결과: 프록시 오류 또는 타임아웃 발생 시 즉시 503 에러 반환, 정상 처리 시 대상 서비스 응답 수신 후 호출 애플리케이션으로 반환

## Ⅴ. 종류 및 비교

| 구분 | 사이드카 프록시 | 노드 공유 프록시 (DaemonSet) | 애플리케이션 라이브러리 |
|:---|:---|:---|:---|
| 배치 방식 | 파드(Pod)당 1개의 전용 프록시 프로세스 | 노드(Node)당 1개의 공용 프록시 프로세스 | 애플리케이션 코드 내 SDK 바이너리 포함 |
| 격리 수준 | 워크로드 단위 완전 격리 (높음) | 노드 내 다수 파드가 프록시 자원 공유 | 프로세스 내부 실행 (격리 부재) |
| 리소스 소비 | 파드 수에 비례하여 클러스터 메모리 증가 | 노드당 고정된 자원만 소비 | 추가 프로세스 오버헤드 전무 |
| 언어 독립성 | 완전 독립 (어떤 언어든 수정 없음) | 완전 독립 (어떤 언어든 수정 없음) | 언어별 전용 라이브러리 구현 필요 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 파드 기동 시 사이드카 초기화 지연으로 메인 컨테이너 통신 실패 | Native Sidecars(K8s v1.29+ restartPolicy: Always) 적용 | 프록시가 완벽히 기동된 후 메인 컨테이너 실행 보장 |
| 메인 앱과 사이드카 간 이중 재시도로 인한 요청 폭증 | 사이드카에만 재시도 정책을 일임하고 애플리케이션 재시도 비활성화 | 재시도 폭풍 방지 및 백엔드 서비스 과부하 차단 |
| 수천 개 파드 운영 시 사이드카 메모리 누적(파드당 50~100MB) | ztunnel 기반 Ambient Mesh 도입 또는 프록시 메모리 Limit 튜닝 | 불필요한 엔드포인트 캐싱 제거 및 클러스터 메모리 수십 GB 절감 |

## Ⅶ. 결론

- **기술 위상/발전**: 마이크로서비스 인프라의 관심사 분리(Separation of Concerns)와 제로 트러스트 데이터면을 실현한 핵심 아키텍처 패턴으로 안착하였으며 최근에는 쿠버네티스 표준 네이티브 사이드카 컨테이너 지원 및 eBPF 가속 기술과 융합 중
- **실무 적용/통제**: K8s 표준 네이티브 사이드카 기능을 활용하여 컨테이너 기동/종료 순서를 엄격히 제어하고, 워크로드 특성에 맞추어 CPU/메모리 Request-Limit을 정밀 사이징하는 자원 최적화 체계 구축 필수
