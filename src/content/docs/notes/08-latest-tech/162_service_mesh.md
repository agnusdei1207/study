## Ⅰ. 개요

- **정의**: 마이크로서비스 아키텍처(MSA) 환경에서 애플리케이션 코드를 수정하지 않고 인프라 계층에서 서비스 간 통신(East-West)을 가로채어 보안(mTLS), 트래픽 라우팅, 복원력 및 관측성을 중앙 집중적으로 제어하는 전용 네트워크 인프라 계층
- **배경 및 필요성**: 다국어(Polyglot) 마이크로서비스 간 통신 폭증 환경에서 애플리케이션 코드 내부에 mTLS, 서비스 디스커버리, 서킷 브레이커, 분산 추적 로직을 개별 구현하는 방식은 언어별 라이브러리 유지보수 비용과 보안 정책 불일치 문제를 유발하므로, 통신 제어 책임을 애플리케이션 비즈니스 로직과 물리적으로 분리할 필요성 대두

## Ⅱ. 특징

- **비즈니스 로직과 통신 분리**: 개발자는 네트워크 통신, 재시도, 보안 암호화 구현 없이 순수 비즈니스 로직 구현에만 집중 가능
- **제로 트러스트 기반 보안**: 서비스 간 모든 호출에 대해 상호 TLS(mTLS) 자동 암호화 및 세분화된 RBAC 인가 정책 강제
- **지능형 L7 트래픽 제어**: 카나리(Canary) 배포, 블루/그린 전환, 서킷 브레이커, 장애 주입(Fault Injection) 동적 제어
- **전방위 엔드투엔드 가시성**: 서비스 간 분산 추적(Distributed Tracing), 골든 시그널 메트릭 및 서비스 토폴로지 시각화 기본 제공

## Ⅲ. 구조 및 구성요소

```text
[Service Mesh 아키텍처]
├── [Control Plane (제어면)] ── 정책 관리자(Istiod), 서비스 레지스트리, CA 인증서 발급
├── [Data Plane (데이터면)] ──── 사이드카 프록시(Envoy), 커널 레벨 프록시(eBPF/ztunnel)
├── [트래픽/복원력 정책] ───── L7 동적 라우팅, 카나리 배포, 서킷 브레이커, 재시도 제어
├── [보안/인가 계층] ──────── 상호 TLS(mTLS) 암호화, SPIFFE/SPIRE 신원 증명, 서비스 RBAC
└── [관측성/모니터링 계층] ── 분산 추적(Jaeger/OTel), 메트릭(Prometheus), 토폴로지(Kiali)
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 구성요소 | 설명 | 주요 역할 |
|:---|:---|:---|
| 제어 평면 (Control Plane) | 중앙 정책 및 설정 관리 컨트롤러 | 서비스 레지스트리 정보를 취합하고 보안/라우팅 정책을 계산하여 데이터면에 배포 |
| 데이터 평면 (Data Plane) | 서비스 트래픽을 중계하는 지능형 프록시 | 인바운드/아웃바운드 패킷을 가로채어 mTLS 암호화, 부하분산, 서킷브레이커 집행 |
| 보안/신원 증명 모듈 | 서비스별 고유 신원 및 암호화 관리 | SPIFFE ID 기반 인증서 자동 발급, 갱신 및 서비스 간 mTLS 상호 인증 강제 |
| 트래픽 제어 모듈 | L7 수준의 세분화된 라우팅 엔진 | 가중치 기반 트래픽 분할, HTTP 헤더 기반 라우팅, 타임아웃 및 재시도 한도 통제 |
| 관측성 계층 | 메트릭, 분산 추적, 액세스 로그 수집기 | 프록시가 계측한 원격 측정 데이터를 중앙 모니터링 시스템으로 전송하여 가시성 확보 |

## Ⅳ. 흐름도

```text
[정책 정의 및 배포] (① 운영자가 제어면에 라우팅·mTLS·인가 규칙 선언 매니페스트 배포)
│
▼
[데이터면 구성 동기화] (② Control Plane이 xDS 프로토콜을 통해 각 노드/파드 프록시로 동기화)
│
▼
[서비스 아웃바운드 인입] (③ 호출 서비스의 요청을 iptables/eBPF가 로컬 사이드카 프록시로 가로챔)
│
▼
[mTLS 암호화 및 L7 라우팅] (④ 프록시 간 mTLS 핸드셰이크 수행 후 가중치 라우팅 및 서킷브레이크 평가)
│
▼
[인바운드 검증 및 전달] (⑤ 대상 프록시가 mTLS 복호화 및 RBAC 인가 검증 후 로컬 서비스로 전달)
│
▼
[원격 측정 데이터 수집] (⑥ 양단 프록시가 지연시간, 응답 코드, 분산 추적 스팬을 관측 계층에 전송)
```

- 분기 결과: mTLS 인증 또는 인가 실패 시 403 차단, 서킷 브레이커 발동 시 즉시 장애 복귀(Fail-fast), 정상 통과 시 대상 파드로 전달

## Ⅴ. 종류 및 비교

| 구분 | 서비스 메시 | API 게이트웨이 | 애플리케이션 라이브러리 |
|:---|:---|:---|:---|
| 주요 대상 트래픽 | 클러스터 내부 동서(East-West) 트래픽 | 클러스터 외부 진입 남북(North-South) 트래픽 | 단일 프로세스 내 인하우스 호출 |
| 배치 위치 | 모든 워크로드 파드 옆(사이드카) 또는 노드당 프록시 | 클러스터 외곽 인프라 경계 | 애플리케이션 프로세스 코드 내부 |
| 언어 의존성 | 완전 독립 (Polyglot 지원) | 완전 독립 (클라이언트 무관) | 개발 언어별 종속적 SDK 구현 필요 |
| 주 병목 요인 | 프록시 추가 홉에 따른 지연(1~3ms) 및 VRAM 오버헤드 | 중앙 집중 게이트웨이 병목 및 단일 장애점 | 코드 변경 시 전 서비스 재빌드 및 재배포 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 다단계 재시도 누적으로 인한 재시도 폭풍(Retry Storm) | 계층별 재시도 횟수 제한(최대 1~2회) 및 재시도 예산(Retry Budget) 적용 | 연쇄적인 후단 시스템 과부하 및 장애 확산 방지 |
| 사이드카 주입에 따른 클러스터 메모리/CPU 낭비 | Ambient Mesh 또는 Cilium eBPF 기반 사이드카리스(Sidecarless) 아키텍처 도입 | 파드당 자원 오버헤드 제거 및 노드 집적도 극대화 |
| 엄격한 mTLS 즉시 적용 시 서비스 통신 단절 | 허용 모드(PERMISSIVE) 선적용 후 점진적 엄격 모드(STRICT) 전환 | 서비스 중단 없는 안전한 제로 트러스트 보안 마이그레이션 |

## Ⅶ. 결론

- **기술 위상/발전**: 클라우드 네이티브 엔터프라이즈 마이크로서비스 아키텍처의 네트워크 거버넌스와 제로 트러스트 보안을 완성하는 사실상의 인프라 표준으로 안착하였으며 최근에는 사이드카 오버헤드를 대폭 경감하는 eBPF 및 Ambient Mesh 구조로 진화 중
- **실무 적용/통제**: 외부 진입 트래픽은 API Gateway로, 내부 서비스 간 통신은 Service Mesh로 명확히 역할 분리하고, 서킷 브레이커와 엄격한 재시도 예산 설정을 결합한 통합 운영체계 구축 필수
