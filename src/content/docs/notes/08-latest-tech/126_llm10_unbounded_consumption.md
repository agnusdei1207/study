## Ⅰ. 개요

- **정의**: 거대 언어 모델(LLM) 및 에이전트 시스템에서 토큰 수, 실행 시간, 외부 API 도구 호출 등에 대한 자원 한도 통제가 미흡하여 발생하는 클라우드 인프라 자원 고갈 및 비용 폭증(Denial of Wallet) 취약점 (OWASP LLM10)
- **배경 및 필요성**: 전통적인 웹 서비스의 HTTP 요청 건수(RPM) 기반 제한은 단일 요청으로 수만 토큰과 수백 초의 GPU 연산, 고비용 외부 유료 API 연쇄 호출을 유발하는 생성형 AI 공격 표면을 방어하지 못하므로, 다차원 자원 계량(TPM/RPM), 사전 예산 잠금(Budget Reservation), 에이전트 루프 강제 차단 및 테넌트별 자원 샌드박싱 체계 구축이 필수적임

## Ⅱ. 특징

- **경제적 보안 위협(Denial of Wallet)**: 서비스 마비를 넘어 기하급수적인 클라우드 API 호출 요금 및 GPU 호스팅 비용 청구 유발
- **다차원 복합 자원 계량**: 단순 요청 횟수(RPM)를 넘어 분당 입출력 토큰 수(TPM), GPU 실행 시간, 서드파티 도구 호출 비용 통합 추적
- **비대칭성 악용**: 공격자의 저비용 단일 프롬프트 주입으로 피해 조직의 대규모 모델 추론 및 유료 검색 API 과소비 유도
- **자율 에이전트 위험 증폭**: ReAct 및 자율 계획 기반 멀티에이전트 환경에서 종료 조건 없는 무한 재귀 루프로 인한 비용 폭발

## Ⅲ. 구조 및 구성요소

### 1. 무제한 소비 방어 아키텍처

```text
[Unbounded Consumption Defense]
├── [게이트웨이 및 원장 계층]
│   ├── [자원 게이트웨이 (Resource Gateway)]
│   └── [예산 원장 (Budget Ledger)]
├── [입장 제어 계층]
│   └── [입장 제어기 (Admission Controller)]
└── [감시 및 격리 실행 계층]
    ├── [실행 감시기 (Execution Monitor)]
    └── [격리 실행 풀 (Isolated Worker Pool)]
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

### 2. 세부 구성요소

| 계층 구분 | 세부 항목 | 핵심 역할 |
|:---|:---|:---|
| 게이트웨이 및 원장 계층 | 자원 게이트웨이 | 주체 인증, API 키 식별 및 테넌트별 요청 인입 관리 |
| | 예산 원장 (Ledger) | 실시간 토큰 소모량, 시간 예산, 누적 API 비용 기록 및 잔여 예산 관리 |
| 입장 제어 계층 | 입장 제어기 (Admission) | 요청별 예상 최대 소비량을 산정하여 예산 원장에서 사전 잠금(Reservation) |
| | 할당량 검증기 | 사용자/테넌트별 월간/일간 예산 초과 시 즉각 요청 거부(HTTP 429) |
| 감시 및 격리 실행 계층 | 실행 감시기 (Monitor) | 스트리밍 토큰 및 실행 시간 실시간 계측, 상한 도달 시 서킷 브레이커 작동 |
| | 격리 실행 풀 (Pool) | 테넌트별 독립 워커 및 동시성 슬롯 격리로 특정 사용자의 인프라 독점 방지 |

## Ⅳ. 흐름도

```text
[요청 수신 및 분석] (① 클라이언트 요청의 모델, 문맥 길이, 도구 권한 분석)
  │
  ▼
[예산 사전 예약] (② 예산 원장에서 예상 최대 비용 잠금 및 입장 승인 검사)
  │
  ▼
[격리 큐 스케줄링] (③ 테넌트별 독립 실행 풀에 배정 및 동시성 제어)
  │
  ▼
[스트리밍 추론 및 감시] (④ 실시간 생성 토큰 및 에이전트 스텝 계량)
  │
  ▼
[정산 및 차단 판정] (⑤ 완료 시 실제 소모 비용 확정 및 미사용 예산 반환)
```

- 분기 결과: 실행 중 사전 설정된 최대 토큰/스텝/시간 상한 초과 시 서킷 브레이커에 의해 즉시 중단(Abort)되고, 정상 완료 시 실제 사용량만큼 예산 원장에 정산 반영

## Ⅴ. 종류 및 비교

| 자원 통제 메커니즘 | 요청 건수 한도 (RPM) | 토큰·시간 예산 (TPM/Time) | 도구 호출·단계 예산 (Agent Budget) |
|:---|:---|:---|:---|
| 주요 통제 대상 | 분당 HTTP 요청 횟수 | 분당 입출력 토큰 및 GPU 실행 시간 | 에이전트 재귀 깊이 및 도구 API 비용 |
| 핵심 제어 지점 | 네트워크 API 게이트웨이 | 추론 서빙 엔진 및 미들웨어 | 에이전트 프레임워크 런타임 |
| 장점 | 구현이 단순하고 오버헤드 미미 | 생성형 AI 추론 연산량 정밀 제어 | 외부 유료 도구 연쇄 호출 완벽 차단 |
| 한계 | 단일 요청 내 고비용 자원 소비 방어 불가 | 외부 서드파티 유료 API 비용 미포함 | 모델 내부의 무한 토큰 생성 단독 통제 불가 |

## Ⅵ. 실무 고려사항 및 대책

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단일 요청의 초장문 컨텍스트 및 생성 점유 | 예상 최대 토큰량 사전 예약(Budget Reservation) 적용 | GPU 메모리 독점 및 미승인 초과 과금 원천 차단 |
| 에이전트 자율 루프에 따른 무한 유료 도구 호출 | 최대 스텝 수(Max Steps) 및 도구 호출 비용 상한 강제 | 비정상 루프 조기 차단을 통한 경제적 손실 예방 |
| 특정 악의적 테넌트의 클러스터 자원 잠식 | 테넌트별 동시성 슬롯 제한 및 PagedAttention 동적 축출 | 타 테넌트 정상 요청에 대한 SLA 및 서비스 가용성 보존 |

## Ⅶ. 결론

- **기술 위상/발전**: 생성형 AI 및 LLM 시스템의 재무적 지속가능성과 고가용성을 동시에 담보하는 핵심 FinOps 및 애플리케이션 보안 표준(OWASP LLM10)으로 자리 잡았으며, 다차원 게이트웨이와 자동 스케줄링 기술로 진화 중
- **실무 적용/통제**: AI API 게이트웨이에 사전 예산 잠금(Admission Control), RPM/TPM 동시 강제, 에이전트 최대 실행 깊이 제한 및 실시간 서킷 브레이커를 결합한 통합 제어 체계 확립 필요
