## Ⅰ. 개요

- **정의**: 저비용 클라우드 객체 스토리지 위에 오픈 테이블 포맷을 적용하여, 데이터 웨어하우스의 ACID 트랜잭션·거버넌스와 데이터 레이크의 유연성·확장성을 단일 계층으로 융합한 차세대 데이터 아키텍처
- **배경 및 필요성**: 데이터 레이크(비정형 저장 가능하나 트랜잭션/품질 부재)와 데이터 웨어하우스(고성능 SQL이나 고비용 및 포맷 폐쇄성)의 이원화 구조로 인한 데이터 중복 복제, ETL 파이프라인 지연, 정합성 불일치를 극복하고, 단일 사본 데이터 위에서 BI 질의와 AI/ML 학습을 동시에 수행하기 위해 도입

## Ⅱ. 특징

- **스토리지와 컴퓨팅의 완전 분리**: 저렴한 클라우드 객체 스토리지(S3, GCS)를 공유하며 Spark, Trino, Flink 등 다중 연산 엔진을 유연하게 교체
- **ACID 트랜잭션 및 시간 여행 (Time Travel)**: 스냅샷 격리 기반 동시성 제어 및 과거 시점 데이터 복원/재현 가능
- **단일 진실 공급원 (SSOT)**: 데이터 파이프라인 중복 적재 없이 동일한 파케(Parquet) 파일 기반으로 BI 보고서와 머신러닝 모델 동시 훈련

## Ⅲ. 구조 및 구성요소

```text
[데이터 레이크하우스 아키텍처]
├── [다중 연산 계층 (Decoupled Compute Layer)]
│   ├── [고속 대화형 SQL (Trino, Presto)]
│   ├── [배치 및 스트리밍 (Apache Spark, Apache Flink)]
│   └── [AI/ML 프레임워크 (PyTorch, TensorFlow)]
├── [메타데이터 및 카탈로그 계층 (Metadata & Catalog)]
│   ├── [오픈 카탈로그 (Polaris, Unity Catalog, Nessie)]
│   └── [오픈 테이블 포맷 (Apache Iceberg, Delta Lake)]
└── [개방형 분산 스토리지 계층 (Object Storage)]
    └── [열 지향 파일 저장소 (Parquet, ORC on S3/GCS/ADLS)]
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 계층 | 구성요소 | 역할 및 세부기능 |
|:---|:---|:---|
| 연산 계층 | 다중 연산 엔진 | Spark, Trino, Flink, DuckDB 등 워크로드별 최적화된 오픈소스 쿼리 엔진 독립 구동 |
| 카탈로그 계층 | 오픈 메타스토어/카탈로그 | Unity Catalog, Polaris 기반 현재 테이블 스냅샷 포인터 관리 및 원자적 커밋 중재 |
| 메타데이터 계층 | 오픈 테이블 포맷 | Iceberg, Delta Lake의 스냅샷 메타데이터, 스키마 진화(Evolution), 파티션 진화 관리 |
| 스토리지 계층 | 분산 객체 스토리지 | AWS S3, Azure ADLS, Google GCS 등 저비용 무한 확장 객체 저장소 활용 |
| 최적화/거버넌스 | 옵티마이저 & 거버넌스 | 작은 파일 병합(Compaction), Z-Order/Min-Max 인덱싱, 열 단위 접근 통제(RBAC) |

## Ⅳ. 흐름도

```text
[쓰기 작업 요청] (① Spark/Flink 엔진이 신규 트랜잭션 데이터를 신규 Parquet 파일로 저장)
│
▼
[후보 스냅샷 생성] (② 변경된 파일 목록 및 컬럼 Min-Max 통계를 포함한 메타데이터 파일 작성)
│
▼
[원자적 커밋 수행] (③ 카탈로그에서 낙관적 동시성 제어(OCC) 검증 후 테이블 루트 포인터 교체)
│
▼
[스냅샷 확정 공개] (④ 동시 충돌이 없을 시 신규 스냅샷이 테이블의 최신 버전으로 즉시 공개)
│
▼
[읽기 엔진 질의] (⑤ Trino/BI 엔진이 최신 메타데이터를 조회하여 불필요한 파일 프루닝 후 읽기)
```

- 분기 결과: OCC 충돌 미발생 시 신규 스냅샷 원자 커밋 완료, 동시성 충돌 감지 시 트랜잭션 자동 재시도 또는 실패 롤백 처리

## Ⅴ. 종류 및 비교

| 구분 | 데이터 레이크하우스 | 전통적 데이터 웨어하우스 (DW) | 기존 데이터 레이크 |
|:---|:---|:---|:---|
| 기반 스토리지 | 개방형 클라우드 객체 스토리지 (S3, GCS) | 고성능 전용 블록/어플라이언스 스토리지 | 저비용 대용량 객체 스토리지/HDFS |
| 데이터 포맷 | 개방형 표준 (Parquet + Iceberg/Delta) | 벤더 독점 폐쇄형 컬럼/로우 포맷 | 원시 포맷 (CSV, JSON, Parquet) |
| 트랜잭션 보장 | ACID 보장 (낙관적 동시성 제어 기반) | 완벽한 ACID 보장 (비관적/낙관적 락) | 트랜잭션 미지원 (수동 덮어쓰기) |
| 주 활용 워크로드 | 고속 SQL, 스트리밍, AI/ML 통합 분석 | 정형 데이터 중심 고성능 BI/보고서 | 대규모 로그 원시 보관, 머신러닝 원천 |
| 벤더 종속성 | 매우 낮음 (오픈 표준, 엔진 자유 교체) | 매우 높음 (스토리지-컴퓨트 종속) | 낮음 (Hadoop 에코시스템 중심) |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 스트리밍 빈번한 커밋으로 인한 '작은 파일(Small Files)' 급증 및 쿼리 지연 | 백그라운드 파일 압축 병합(Compaction) 및 파티션 재배치 자동화 | 메타데이터 오버헤드 해소 및 읽기 질의 I/O 성능 극대화 |
| 다중 이종 쿼리 엔진 간의 테이블 접근 권한 및 거버넌스 불일치 | Apache Polaris, Unity Catalog 등 중앙화된 오픈 카탈로그 기반 권한 통제 | 엔진 무관 전사 통일된 데이터 보안 정책(RBAC/ABAC) 유지 |
| 대규모 파티션 환경에서 통계 미흡으로 인한 쿼리 풀스캔 발생 | Z-Ordering, Data Skipping 및 컬럼 통계(Min-Max) 자동 수집 파이프라인 운영 | 불필요한 파일 읽기 사전 필터링(Data Pruning)으로 스캔 비용 절감 |

## Ⅶ. 결론

- **기술 위상/발전**: 폐쇄형 DW와 미정제 데이터 레이크의 구조적 단점을 극복한 현대 엔터프라이즈 데이터 아키텍처의 표준으로 자리 잡았으며, Apache Iceberg 중심의 오픈 테이블 포맷 수렴과 오픈 카탈로그 기반 통합 거버넌스로 진화 중
- **실무 적용/통제**: 개방형 포맷(Apache Iceberg/Delta)을 기본으로 채택하여 특정 벤더 종속을 차단하고, 파이프라인 초기부터 정기적인 백그라운드 컴팩션(Compaction) 및 통계 최적화를 스케줄링하여 쿼리 성능과 스토리지 비용의 균형을 유지할 필요
