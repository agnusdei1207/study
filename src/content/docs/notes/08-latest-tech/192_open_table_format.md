## Ⅰ. 개요

- **정의**: 클라우드 분산 객체 스토리지의 파일(Parquet, ORC 등) 위에 표준화된 메타데이터 계층을 두어, 완전한 ACID 트랜잭션, 스냅샷 격리성, 스키마 진화 및 시간 여행(Time Travel)을 보장하는 개방형 스토리지 계층 규격
- **배경 및 필요성**: 객체 스토리지의 파일 단위 원자적 변경 부재로 인한 부분 실패 잔류, 동시 쓰기 시 데이터 유실/중복, 폐쇄형 DW의 벤더 종속성과 천문학적 비용을 탈피하고, Spark·Trino·Flink·DuckDB 등 다중 이기종 연산 엔진이 단일 데이터 사본(SSOT)을 일관되게 공유하기 위해 도입

## Ⅱ. 특징

- **스토리지 수준 ACID 보장**: 파일 덮어쓰기 없이 불변(Immutable) 파일 추가와 메타데이터 원자 커밋을 결합한 스냅샷 격리(Snapshot Isolation) 제공
- **독립적 다중 엔진 상호운용**: 특정 벤더나 특정 실행 엔진에 구속되지 않고 표준 API 및 커넥터를 통해 범용 쿼리 엔진에서 동시 접근 가능
- **진화형 메타데이터 관리**: 테이블 전체 재작성 없이 컬럼 추가/변경(Schema Evolution) 및 파티션 변경(Partition Evolution) 지원

## Ⅲ. 구조 및 구성요소

```text
[오픈 테이블 포맷 아키텍처]
├── [질의 및 연산 계층 (Compute Engines)]
│   └── [다중 쿼리 엔진 (Spark, Trino, Flink, DuckDB, Snowflake)]
├── [카탈로그 및 메타스토어 계층 (Catalog Layer)]
│   └── [오픈 카탈로그 (REST Catalog, Polaris, Unity Catalog, Nessie)]
├── [메타데이터 관리 계층 (Table Metadata Layer)]
│   ├── [트랜잭션 커밋 로그 및 매니페스트 트리]
│   └── [스키마 버전, 파티션 명세, 컬럼 통계(Min/Max)]
└── [분산 객체 스토리지 계층 (Object Storage)]
    └── [불변 컬럼형 파일군 (Data Parquet / Delete Files on S3/GCS/ADLS)]
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 계층 | 구성요소 | 역할 및 세부기능 |
|:---|:---|:---|
| 연산 계층 | 다중 질의 엔진 | Spark, Trino, Flink 등 워크로드별 엔진이 포맷 전용 커넥터를 통해 푸시다운 및 질의 실행 |
| 카탈로그 계층 | 중앙 카탈로그 | 테이블 식별자를 현재 유효한 최신 메타데이터 루트 포인터에 매핑하고 원자적 교체 중재 |
| 메타데이터 계층 | 테이블 메타데이터 | 스냅샷 목록, 스키마/파티션 버전, 유효 데이터 파일 목록 및 통계 정보를 표준 규격으로 보관 |
| 스토리지 계층 | 데이터 및 삭제 파일 | 실제 비즈니스 데이터를 압축된 Parquet/ORC 파일로 저장하며 불변(Immutable) 상태 유지 |
| 거버넌스 계층 | 테이블 유지관리 서비스 | 작은 파일 압축 병합(Compaction), 만료 스냅샷 정리(Vacuum), Z-Order 최적화 수행 |

## Ⅳ. 흐름도

```text
[쓰기 작업 시작] (① 처리 엔진이 카탈로그에서 현재 활성 스냅샷 및 스키마 기준 버전 확인)
│
▼
[신규 불변 파일 작성] (② 수정/추가 레코드를 신규 Parquet 데이터 및 Delete 파일로 저장)
│
▼
[신규 메타데이터 구성] (③ 신규 파일 경로, 파티션 정보, 컬럼 통계를 반영한 신규 메타데이터 작성)
│
▼
[원자적 커밋 시도] (④ 카탈로그를 통해 낙관적 동시성 제어(OCC) 충돌 검증 및 포인터 교체)
│
▼
[신규 스냅샷 공개] (⑤ 커밋 완료 즉시 읽기 엔진들에게 최신 테이블 상태로 일관되게 공개)
```

- 분기 결과: OCC 충돌 미발생 시 신규 스냅샷 확정 및 즉시 질의 가능, 타 트랜잭션 선점으로 인한 충돌 시 롤백 후 자동 재시도

## Ⅴ. 종류 및 비교

| 오픈 테이블 포맷 | Apache Iceberg | Delta Lake | Apache Hudi |
|:---|:---|:---|:---|
| 핵심 설계 철학 | 엔진 중립적 대규모 분석 및 매니페스트 트리 | Spark/Databricks 생태계 통합 및 순차 로그 | 스트리밍 수집 및 초고속 업서트/증분 처리 |
| 메타데이터 구조 | 계층형 매니페스트 트리 (`.metadata.json` $\rightarrow$ Avro) | 순차 JSON 커밋 로그 + 체크포인트 (`_delta_log/`) | 타임라인 기반 파일 그룹 및 메타데이터 테이블 |
| 카탈로그 의존성 | REST Catalog 등 독립 카탈로그 필수 | 파일 시스템 기반 또는 Unity Catalog 연계 | 파일 시스템 기반 또는 Hive Metastore 연계 |
| 포맷 호환 기술 | Apache XTable 연동 변환 지원 | UniForm (Iceberg/Hudi 메타데이터 동시 생성) | Apache XTable 연동 변환 지원 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 이종 엔진 간 쓰기·삭제(Delete) 및 스키마 진화 지원 편차 | 전사 공식 지원 엔진 및 포맷 버전 호환 행렬(Compatibility Matrix) 정의 | 엔진 간 쓰기 충돌 및 메타데이터 파손 방지 |
| 스트리밍 유입으로 인한 소형 파일 및 과거 스냅샷 무한 누적 | 백그라운드 파일 컴팩션 및 스냅샷 보존 정책(Retention) 자동화 | 쿼리 플래닝 성능 유지 및 객체 스토리지 비용 절감 |
| 중앙 카탈로그 장애 시 전사 데이터 읽기/쓰기 전면 중단 | 고가용 분산 REST 카탈로그 구축 및 멀티 리전 백업 체계 운영 | 카탈로그 단일 장애점(SPOF) 제거 및 고가용성 보장 |

## Ⅶ. 결론

- **기술 위상/발전**: 현대 클라우드 레이크하우스의 핵심 기반 기술로 자리 잡았으며, Apache Iceberg, Delta Lake, Apache Hudi 간의 상호 변환 기술(UniForm, Apache XTable)과 표준 REST 카탈로그 도입을 통해 포맷 간 경계가 허물어지는 추세
- **실무 적용/통제**: 조직의 주력 컴퓨팅 엔진과 워크로드 특성(배치/BI/스트리밍)에 부합하는 표준 포맷을 선정하되, 벤더 중립적인 카탈로그를 도입하고 백그라운드 컴팩션과 수명주기 관리를 파이프라인에 필수 통합할 필요
