## Ⅰ. 개요

- **정의**: 개발자가 인프라와 배포 파이프라인의 복잡성 없이 비즈니스 로직 개발에 집중할 수 있도록 표준화된 셀프서비스 도구와 워크플로우를 내부 제품(Internal Product)으로 설계·제공하는 현대적 소프트웨어 엔지니어링 패러다임
- **배경 및 필요성**: DevOps의 'You Build It, You Run It' 철학 확산 이후 인프라, K8s 매니페스트, CI/CD, 보안 규제 등 과도한 인지 부하(Cognitive Overload)가 개발자에게 전가되고 티켓 기반 수동 요청으로 리드타임이 지연되는 병목을 해소하기 위해, 최적의 권장 경로인 골든 패스(Golden Path)와 내부 개발자 플랫폼(IDP) 도입 필요

## Ⅱ. 특징

- 인프라 요청 티켓팅을 배제하고 즉각적인 리소스 생성을 지원하는 셀프서비스(Self-Service) 자동화
- 보안·규제·성능 모범 사례가 기본 내장된 검증된 표준 개발 경로인 골든 패스(Golden Path) 제공
- 강제 표준화의 부작용을 방지하고 특수 기술 요구를 수용하기 위한 탈출 경로(Escape Hatch) 보장
- 플랫폼을 사내 제품(Product)으로 취급하고 개발자를 고객으로 대우하는 제품 사고(Product Thinking)

## Ⅲ. 구조 및 구성요소

```text
[플랫폼 엔지니어링 아키텍처]
├── 사용자 경험 계층 ── 개발자 포털(Backstage), 서비스 카탈로그, CLI 인터페이스
├── 오케스트레이션 계층 ── 골든 패스 템플릿, 워크플로우 엔진, RBAC 권한 제어
└── 인프라 제어 계층 ── 셀프서비스 IaC(Terraform/Crossplane), GitOps 파이프라인, 정책 엔진
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 계층 | 핵심 구성요소 | 주요 역할 및 책임 |
|:---|:---|:---|
| 사용자 경험 계층 | Developer Portal (Backstage) | 서비스 카탈로그, 기술 문서(TechDocs), 셀프서비스 요청 인터페이스 통합 제공 |
| 사용자 경험 계층 | Service Catalog | 마이크로서비스 소유권, API 명세, 의존성 관계 가시화 및 거버넌스 관리 |
| 오케스트레이션 계층 | Golden Path Template | 표준화된 프로젝트 스캐폴딩, CI/CD 파이프라인, 보안 룰셋이 사전 정의된 템플릿 |
| 오케스트레이션 계층 | Platform Orchestrator | 개발자 입력 파라미터를 기반으로 환경 설정 및 인프라 프로비저닝 워크플로우 조율 |
| 인프라 제어 계층 | Self-service IaC | Terraform, Crossplane 등을 통한 클라우드 네이티브 인프라 자동 생성 및 수명주기 관리 |
| 인프라 제어 계층 | GitOps Controller | ArgoCD/Flux 기반의 선언적 형상 동기화 및 롤백 자동화 |

## Ⅳ. 흐름도

```text
[개발자 서비스 생성 요청] (① 개발자 포털 UI에서 골든 패스 템플릿 선택 및 파라미터 입력)
│
▼
[IDP 오케스트레이션 구동] (② 리포지토리 자동 생성, CI/CD 스캐폴딩, 보안 정책 자동 바인딩)
│
▼
[셀프서비스 인프라 프로비저닝] (③ IaC 및 GitOps 컨트롤러를 통한 클라우드 리소스 자동 배포)
│
▼
[개발 및 지속 배포] (④ 표준 파이프라인을 통해 인프라 인지 부하 없이 비즈니스 코드 배포)
│
▼
[피드백 및 플랫폼 개선] (⑤ 채택률, DORA 메트릭 수집 및 개발자 피드백 기반 플랫폼 진화)
```

- 분기 결과: 골든 패스 템플릿을 선택한 개발자는 수 분 내 프로덕션 준비 완료 환경을 획득하며, 특수 기술 스택이 필요한 경우 관리된 탈출 경로(Escape Hatch) 승인 절차를 거쳐 독자 환경 구축이 허용됨

## Ⅴ. 종류 및 비교

| 구분 | 플랫폼 엔지니어링 (Platform Eng) | DevOps (개발/운영 통합) | 전통적 IT 운영 (Ops) |
|:---|:---|:---|:---|
| 주 제공물 | 내부 개발자 플랫폼(IDP) 제품 | 협업 문화 및 CI/CD 자동화 | 물리/가상 인프라 직접 유지보수 |
| 인프라 접근 | 셀프서비스 API 및 포털 클릭 | 개발자가 직접 스크립트 작성/관리 | 티켓 시스템 기반 수동 신청 및 승인 |
| 개발자 인지부하 | 골든 패스 추상화로 극소화 | 인프라/도구 스택 학습 부담 극대화 | 인프라 무관하나 대기 리드타임 과다 |
| 거버넌스 방식 | 플랫폼 템플릿 내 기본 가드레일 내장 | 팀별 파편화된 스크립트로 통제 곤란 | 중앙 변경관리위원회(CAB) 심사 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 개발자 선호를 무시한 강제 표준화로 인한 섀도우 IT 확산 | 플랫폼을 강요하지 않고 '제품'으로 마케팅하며 유연한 탈출 경로(Escape Hatch) 보장 | 자발적 플랫폼 채택률(Adoption) 증가 및 반발 방지 |
| 플랫폼 팀이 새로운 형태의 중앙 집중 티켓 처리 병목으로 변질 | 티켓팅 제거, 포털 기반 100% 셀프서비스 API 자동화 원칙 엄수 | 서비스 런칭 리드타임(Lead Time) 분 단위 단축 |
| 구축 후 개발자 피드백 부재로 인한 플랫폼 효용성 저하 | DORA 메트릭(배포 빈도, 변경 리드타임 등) 및 사내 DevEx 만족도 정기 측정 | 개발자 중심 플랫폼 기능 지속 개선 및 투자 회수 |

## Ⅶ. 결론

- **기술 위상/발전**: DevOps의 인지 부하 한계를 극복하고 개발자 경험(DevEx)을 극대화하는 클라우드 네이티브 핵심 운영 체계로 정착되었으며, AI 코딩 어시스턴트 및 플랫폼 자동화와 융합 진화
- **실무 적용/통제**: 플랫폼을 강제 규제가 아닌 '내부 제품(Product as a Service)'으로 포지셔닝하여 자발적 채택 유도, 골든 패스를 기본으로 하되 예외 요구사항을 위한 탈출 경로(Escape Hatch) 보장
