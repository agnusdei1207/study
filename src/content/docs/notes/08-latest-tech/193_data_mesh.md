## Ⅰ. 개요

- **정의**: 비즈니스 도메인 팀이 데이터를 독립적인 제품(Data as a Product)으로 직접 소유·관리하고, 셀프서비스 데이터 플랫폼과 연합 거버넌스를 통해 전사 공유를 실현하는 탈중앙화 분산 데이터 아키텍처 패러다임
- **배경 및 필요성**: 중앙 집중형 모놀리식 레이크/DW 아키텍처에서 발생하는 중앙 데이터 팀의 파이프라인 병목, 도메인 비즈니스 지식 단절, 데이터 품질 책임 소재 불분명 문제를 극복하고, 도메인 주도 설계(DDD) 사상을 데이터 인프라에 적용하여 전사 데이터 민주화와 비즈니스 민첩성을 확보하기 위해 도입

## Ⅱ. 특징

- **도메인 중심 분산 소유권**: 데이터를 가장 잘 이해하는 도메인 업무 조직이 데이터 모델링과 품질, 수명주기 전권을 보유
- **데이터 제품화 (Data as a Product)**: 데이터를 부산물이 아닌 명확한 데이터 계약(Data Contract), 메타데이터, SLO를 갖춘 완성된 제품 단위로 제공
- **연합형 거버넌스와 셀프서비스 플랫폼**: 전사 공통 규칙(보안, 표준)은 연합 협의체에서 정책 코드로 자동 강제하고, 공통 인프라는 셀프서비스 플랫폼으로 제공하여 도메인의 인지 부하 경감

## Ⅲ. 구조 및 구성요소

```text
[데이터 메시 4대 핵심 아키텍처]
├── [도메인 지향 분산 소유권 (Domain Ownership)]
│   └── [도메인 팀별 독립 데이터 파이프라인 및 모델]
├── [데이터의 제품화 (Data as a Product)]
│   ├── [데이터 계약 (Data Contract: 스키마, SLO, SLA)]
│   └── [데이터 퀀텀 (Data Quantum: 코드, 데이터, 메타데이터 결합체)]
├── [셀프서비스 데이터 플랫폼 (Self-serve Platform)]
│   └── [클라우드 인프라 자동화, 공통 카탈로그, 관측성 도구]
└── [연합형 계산 거버넌스 (Federated Computational Governance)]
    └── [코드 기반 전사 표준 정책 자동 집행 (Policy as Code)]
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 구분 | 구성요소 | 역할 및 세부기능 |
|:---|:---|:---|
| 4대 원칙 | 도메인 소유권 | 업무 도메인 팀이 데이터 엔지니어링 역량을 내재화하여 데이터 생성부터 품질까지 전주기 책임 |
| 4대 원칙 | 데이터 제품화 | 소비자가 쉽게 검색(Discoverable), 이해(Understandable), 신뢰(Trustworthy)할 수 있는 API/테이블 제공 |
| 4대 원칙 | 셀프서비스 플랫폼 | 중앙 인프라 팀이 스토리지·컴퓨트 프로비저닝, 파이프라인 템플릿, 카탈로그를 추상화하여 제공 |
| 4대 원칙 | 연합형 계산 거버넌스 | 도메인 대표와 중앙 팀이 연합하여 접근 통제(RBAC), 데이터 상호운용 표준을 수립하고 CI/CD로 강제 |
| 핵심 아티팩트 | 데이터 계약 (Data Contract) | 생산자와 소비자 간 스키마, 업데이트 주기, 품질 임계치를 명시한 기계 판독형 협약 |

## Ⅳ. 흐름도

```text
[소비 요구 접수] (① 분석가/소비자가 신규 도메인 데이터 제품 사양 및 품질 요구 전달)
│
▼
[데이터 제품 개발] (② 도메인 팀이 셀프서비스 플랫폼 템플릿을 활용하여 파이프라인 및 계약 작성)
│
▼
[거버넌스 정책 검증] (③ 연합 거버넌스 엔진이 스키마 표준, 암호화, 접근 통제 정책 적합성 자동 검증)
│
▼
[제품 카탈로그 등록] (④ 검증 통과된 데이터 제품을 전사 엔터프라이즈 데이터 카탈로그에 자동 공개)
│
▼
[소비 및 피드백 순환] (⑤ 타 도메인 소비자가 권한 획득 후 안전하게 사용하고 SLO 상태 모니터링)
```

- 분기 결과: 연합 거버넌스 표준 통과 시 전사 카탈로그에 정상 배포, 데이터 계약 위반 또는 보안 미충족 시 배포 차단 및 도메인 팀 피드백

## Ⅴ. 종류 및 비교

| 구분 | 데이터 메시 (Data Mesh) | 데이터 패브릭 (Data Fabric) | 중앙 집중형 데이터 레이크/DW |
|:---|:---|:---|:---|
| 핵심 접근법 | 조직 및 사람 중심의 탈중앙화 거버넌스 | 기술 및 AI 메타데이터 중심의 통합 자동화 | 중앙 데이터 엔지니어링 팀의 모놀리식 운영 |
| 데이터 소유권 | 각 비즈니스 도메인 팀 분산 소유 | 전사 공통 자산으로 중앙 통합 관리 | 중앙 데이터 전담 조직 집중 소유 |
| 데이터 상호운용 | 데이터 계약(Data Contract) 기반 연합 관리 | 활성 메타데이터(Active Metadata) 기반 지식 그래프 | 단일 통합 스키마/엔터프라이즈 모델 강제 |
| 해결 주안점 | 조직 확장성 및 비즈니스 도메인 지식 단절 극복 | 이기종 데이터 소스 간 연결 및 통합 자동화 | 대규모 정형/비정형 데이터의 중앙 보관 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 도메인 팀의 데이터 엔지니어링 역량 부족 및 인지 부하 증가 | 인프라 복잡성을 추상화한 로우코드 셀프서비스 플랫폼 제공 및 플랫폼 팀 지원 | 도메인 개발 생산성 제고 및 인프라 구축 진입장벽 해소 |
| 도메인별 용어 파편화 및 데이터 제품 간 조인(Join) 불가능 | 연합 거버넌스 주도의 핵심 비즈니스 엔터티(고객, 주문 등) 전사 표준 용어 정의 | 도메인 간 데이터 상호운용성(Interoperability) 보장 |
| 명목상 소유권으로 인한 데이터 품질 사고 발생 시 책임 회피 | 도메인별 데이터 제품 책임자(Data Product Owner) 지정 및 SLO 기반 온콜 체계 구축 | 데이터 품질 보증 및 소비자 신뢰도 확보 |

## Ⅶ. 결론

- **기술 위상/발전**: 모놀리식 데이터 아키텍처의 한계를 극복하는 전사 데이터 운영 모델의 최고 표준으로 부상하였으며, 최근에는 데이터 패브릭의 지능형 메타데이터 기술을 셀프서비스 플랫폼에 흡수하는 융합 아키텍처로 진화 중
- **실무 적용/통제**: 단순한 플랫폼 도입이 아닌 조직 R&R과 평가 체계의 전환이 필수적이며, 전사 일괄 전환보다는 성숙도가 높은 선도 도메인을 선정하여 파일럿 데이터 제품을 성공시킨 후 단계적으로 확산할 필요
