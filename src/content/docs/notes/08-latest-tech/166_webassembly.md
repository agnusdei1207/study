## Ⅰ. 개요

- **정의**: C/C++, Rust, Go 등 다양한 고수준 프로그래밍 언어로 작성된 코드를 네이티브에 준하는 속도로 실행 가능한 컴팩트 바이너리 바이트코드로 컴파일하여, 하드웨어 및 OS 독립적인 선형 메모리 샌드박스에서 안전하게 실행하는 W3C 개방형 표준 기술
- **배경 및 필요성**: 전통적인 네이티브 바이너리는 OS 및 CPU 아키텍처 종속성으로 인해 플랫폼별 재컴파일 비용이 크고, 컨테이너는 기동 지연(수백 ms)과 무거운 메모리 풋프린트로 인해 초경량 엣지/플러그인 환경에 한계가 존재하므로, 단일 바이너리로 브라우저와 서버/엣지를 아우르는 높은 이식성과 밀리초 미만의 초고속 콜드스타트를 보장하는 초경량 보안 격리 런타임의 필요성 대두

## Ⅱ. 특징

- **근접 네이티브 성능**: 구조화된 바이트코드 형식을 채택하여 JIT/AOT 컴파일을 통해 호스트 기계어에 근접하는 초고속 연산 처리
- **선형 메모리(Linear Memory) 격리**: 모듈마다 독립된 연속 바이트 배열 주소 공간을 할당하고 하드웨어 경계 검사를 수행하여 호스트 메모리 접근 차단
- **능력 기반 보안(Capability-based Security)**: WASI(WebAssembly System Interface)를 통해 호스트가 명시적으로 승인한 파일 디렉터리, 소켓 포트만 접근 허용
- **초경량 및 즉시 기동**: 운영체제 커널 이미지나 별도 게스트 OS가 불필요하여 수십 KB 크기의 바이너리와 마이크로초 단위 인스턴스화 가능

## Ⅲ. 구조 및 구성요소

```text
[WebAssembly 아키텍처]
├── [개발 도구체인] ──── 다국어 소스(Rust/C++/Go), LLVM 백엔드, Wasm 모듈(.wasm)
├── [검증 및 컴파일] ──── 포맷/타입 검증기(Verifier), AOT/JIT 엔진 (Cranelift/LLVM)
├── [독립 런타임 엔진] ── Wasmtime, Wasmer, WasmEdge (서버/엣지 샌드박스)
├── [메모리 격리 계층] ── 선형 메모리(Linear Memory), 가상 주소 테이블, 스택 격리
└── [시스템 인터페이스] ─ WASI (WebAssembly System Interface), WIT (컴포넌트 모델)
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 구성요소 | 설명 | 주요 역할 |
|:---|:---|:---|
| Wasm 모듈 (.wasm) | 함수, 타입, 선형 메모리 선언이 담긴 바이너리 | 다국어 컴파일러에 의해 생성된 플랫폼 독립적 단일 실행 배포 아티팩트 |
| Verifier (정적 검증기) | 바이트코드 형식 및 타입 안전성 분석기 | 런타임 실행 전 제어 흐름과 스택 무결성을 검사하여 비정상 메모리 접근 차단 |
| 런타임 엔진 | 독립 실행 샌드박스 환경(Wasmtime 등) | JIT/AOT 컴파일러(Cranelift)를 내장하여 바이트코드를 호스트 기계어로 즉시 변환 |
| 선형 메모리 | 인스턴스 전용 1차원 연속 바이트 배열 | 호스트 메모리와 분리된 인메모리 샌드박스로 경계 밖 접근 시 즉시 트랩(Trap) 발생 |
| WASI (System Interface) | 파일, 네트워크, 시계 등 시스템 호출 표준 API | POSIX 호환 API를 제공하되 사전 승인된 파일 디스크립터만 다루는 능력 기반 보안 제공 |
| Component Model (WIT) | Wasm 모듈 간 인터페이스 정의 명세 | 서로 다른 언어로 작성된 컴포넌트 간 복합 자료형(String, Struct) 교환 및 상호 운용 지원 |

## Ⅳ. 흐름도

```text
[다국어 소스 컴파일] (① C/C++/Rust 소스를 Clang/rustc로 Wasm 바이트코드(.wasm)로 컴파일)
│
▼
[Wasm 모듈 검증] (② 런타임 검증기가 스택 및 제어 흐름 무결성과 정적 타입 안전성 검증)
│
▼
[JIT/AOT 기계어 변환] (③ Cranelift 엔진이 호스트 CPU 아키텍처(x86/ARM) 네이티브 코드로 컴파일)
│
▼
[선형 메모리 인스턴스화] (④ 호스트 메모리와 물리적으로 격리된 전용 32/64비트 선형 메모리 할당)
│
▼
[WASI 호스트 기능 바인딩] (⑤ 파일/소켓 접근 권한을 능력 기반(Capability-based)으로 최소 바인딩)
│
▼
[샌드박스 함수 실행] (⑥ 마이크로초 단위 초고속 실행 및 위반 발생 시 트랩(Trap)으로 안전 격리)
```

- 분기 결과: 유효하지 않은 메모리 접근 또는 스택 오버플로우 발생 시 즉각 런타임 트랩(Trap)을 발생시켜 모듈 격리 중단 및 호스트 시스템 보호

## Ⅴ. 종류 및 비교

| 구분 | WebAssembly (Wasm) | 네이티브 프로세스 | 컨테이너 (Docker/OCI) |
|:---|:---|:---|:---|
| 실행 단위 | 컴팩트 바이트코드 모듈 | OS 의존 바이너리 실행 파일 | 루트 파일시스템 포함 컨테이너 이미지 |
| 기동 시간 | 마이크로초($\mu s$) 단위 즉각 기동 | 밀리초($ms$) 단위 | 수백 밀리초 ~ 수 초 소요 |
| 격리 메커니즘 | 소프트웨어 선형 메모리 샌드박스 | OS 사용자 권한(UID/GID) 기반 | 커널 네임스페이스 및 cgroups 격리 |
| 이식성 | 완전한 크로스 플랫폼 (아키텍처 무관) | 컴파일된 특정 OS 및 CPU 종속 | 호스트 커널 호환성에 종속 (동일 OS 커널) |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 호스트와 Wasm 샌드박스 간 빈번한 함수 호출 시 전환 지연 | Wasm 컴포넌트 모델(WIT) 및 제로 카피 버퍼 공유 프로토콜 채택 | 언어 간 복합 데이터 직렬화/역직렬화 오버헤드 최소화 |
| 브라우저 외 백엔드 환경에서 소켓/스레드 등 POSIX 기능 제약 | 최신 WASI 0.2 표준 도입 및 WASI-Threads 확장 적용 | 완전한 비동기 I/O 및 멀티스레드 병렬 처리 지원 |
| 특정 모듈의 무한 루프 또는 과도한 연산으로 CPU 독점 | Fuel/Epoch 기반 연산량(Gas) 측정 및 타임아웃 인터럽트 적용 | 테넌트 간 공평 스케줄링 보장 및 서비스 거부(DoS) 방지 |

## Ⅶ. 결론

- **기술 위상/발전**: 웹 브라우저 가속 기술을 넘어 서버리스 FaaS(Fastly, Cloudflare), 쿠버네티스 워크로드(Knative/Spin), 서비스 메시 플러그인(Envoy Proxy Wasm 필터)의 표준 런타임으로 급부상
- **실무 적용/통제**: 대규모 레거시 전체 시스템은 컨테이너로 유지하되, 초저지연 이벤트 처리 및 엣지 AI 추론(WASI-NN)에는 Wasm 컴포넌트 아키텍처를 선별 적용하고 WASI 기반 최소 권한 보안 원칙 준수 필수
