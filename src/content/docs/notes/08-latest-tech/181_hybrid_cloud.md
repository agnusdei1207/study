## Ⅰ. 개요

- **정의**: 온프레미스(사설 데이터센터)와 퍼블릭 클라우드를 상호 연결하여 데이터와 워크로드를 공유하고 단일한 제어 평면으로 통합 운영하는 인프라 아키텍처
- **배경 및 필요성**: 금융·공공 등 엄격한 컴플라이언스 및 데이터 주권(Data Sovereignty) 규제를 준수하면서도, 피크 트래픽 대응을 위한 클라우드 버스팅(Cloud Bursting)과 AI/빅데이터 연산의 탄력적 확장성을 동시에 확보할 필요

## Ⅱ. 특징

- 규제 준수 데이터의 사내 보관과 프론트엔드 연산의 클라우드 탄력성 결합
- 단일 제어 평면(Control Plane)을 통한 이기종 환경 통합 배포, 보안, 관측 관리
- 트래픽 폭증 시 온프레미스 용량을 초과하는 부하를 클라우드로 분산(Cloud Bursting)
- 전용선(Direct Connect) 및 하이브리드 메시를 통한 초저지연 프라이빗 통신망 구축

## Ⅲ. 구조 및 구성요소

```text
[하이브리드 클라우드 아키텍처]
├── 온프레미스 사설 계층 ── 레거시 코어 시스템, 금융/국방 규제 데이터, 프라이빗 클라우드
├── 연계 및 제어 평면 ── 전용선(Direct Connect/ExpressRoute), 통합 IAM, 데이터 동기화
└── 퍼블릭 클라우드 계층 ── 탄력적 컴퓨팅(클라우드 버스팅), 완전관리형 SaaS/PaaS, 글로벌 CDN
```

- 선들의 의미: 실선(──)과 가지선(├──, └──)은 계층적 하위 관계를 의미함

| 계층 | 핵심 구성요소 | 주요 역할 및 책임 |
|:---|:---|:---|
| 온프레미스 사설 계층 | Core Banking / ERP | 데이터 주권 및 법적 컴플라이언스 대상 중요 원천 데이터 영구 보관 |
| 온프레미스 사설 계층 | Private Cloud Platform | OpenStack, VMware 또는 Kubernetes 기반 자체 구축 가상화 인프라 |
| 연계 및 제어 평면 | Dedicated Direct Interconnect | AWS Direct Connect, Azure ExpressRoute 등 전용 회선 기반 고대역폭 암호화 링크 |
| 연계 및 제어 평면 | Unified Control Plane | Google Anthos, Azure Arc, Red Hat OpenShift 기반의 하이브리드 워크로드 단일 관리 |
| 연계 및 제어 평면 | Identity Federation | 사내 Active Directory/LDAP과 클라우드 IdP 간 SAML/OIDC 연동 SSO 제공 |
| 퍼블릭 클라우드 계층 | Elastic Cloud Bursting | 프로모션 및 연말 정산 등 예측 불가능한 트래픽 스파이크 시 자동 확장 처리 |
| 퍼블릭 클라우드 계층 | Managed AI / Analytics | 대규모 GPU 클러스터 및 데이터 웨어하우스(BigQuery/Redshift) 활용 분석 |

## Ⅳ. 흐름도

```text
[사용자 요청 유입] (① 글로벌 DNS/로드밸런서에서 트래픽 특성 분석 및 라우팅 판단)
│
▼
[일반 트래픽 처리] (② 퍼블릭 클라우드 웹/앱 티어에서 동적 오토스케일링 확장 처리)
│
▼
[보안 전용선 통신] (③ Direct Connect/IPsec VPN 암호화 채널을 통해 온프레미스 코어 호출)
│
▼
[온프레미스 코어 트랜잭션] (④ 사내 데이터센터 프라이빗 DB에서 계정 원장 및 규제 데이터 처리)
│
▼
[통합 관측 및 상태 관리] (⑤ 단일 제어 평면 대시보드(Anthos/Arc)에서 양방향 상태 감시)
```

- 분기 결과: 정상 시에는 클라우드-온프레미스 간 원활한 분산 처리가 수행되며, 전용선 장애 시 온프레미스 내부 로컬 트랜잭션 모드로 자동 격리(Circuit Breaking)되어 시스템 마비를 방지함

## Ⅴ. 종류 및 비교

| 구분 | 하이브리드 클라우드 (Hybrid Cloud) | 멀티클라우드 (Multi-Cloud) | 프라이빗 클라우드 (Private Cloud) |
|:---|:---|:---|:---|
| 인프라 조합 | 온프레미스 사설 인프라 + 퍼블릭 클라우드 | 둘 이상의 서로 다른 퍼블릭 클라우드 | 사내 데이터센터 내 전용 클라우드 인프라 |
| 핵심 가치 | 규제 데이터 통제와 클라우드 탄력성 절충 | 벤더 락인 방지 및 Best-of-Breed 특화 기능 | 완벽한 보안 통제권 및 독점 자원 점유 |
| 네트워크 구성 | 전용선(Direct Connect) 및 하이브리드 VPN | 클라우드 간 인터넷 피어링 또는 메가포트 | 사내 내부망(LAN/WAN) 위주 구성 |
| 운영 복잡도 | 높음 (사설 하드웨어와 클라우드 동기화) | 극히 높음 (다양한 CSP 콘솔/API 학습) | 중간 (단일 환경 내에서 완결) |
| 주요 제약사항 | 데이터 전송 레이턴시 및 이중 운영비 | 이종 클라우드 간 데이터 송출료(Egress) | 하드웨어 추가 도입 시 수개월 리드타임 |

## Ⅵ. 실무 고려사항 및 대책

| 문제점 | 대책 | 효과 |
|:---|:---|:---|
| 데이터베이스 양방향 실시간 동기화 지연 및 데이터 정합성 훼손 | 단일 원본(SSOT) 원칙 수립, 온프레미스 쓰기 전담 및 클라우드 읽기 전용 캐시/복제본 구성 | 데이터 충돌 원천 방지 및 읽기 성능 향상 |
| 전용선 물리적 단절 시 클라우드 웹 애플리케이션의 연쇄 장애 발생 | 전용선 물리 경로 이중화(Active-Standby) 및 서킷 브레이커, 독립 로컬 캐시 적용 | 회선 장애 시에도 서비스 최소 기능 유지 |
| 이종 환경 간 보안 정책 불일치로 인한 사각지대 발생 | GitOps 기반 중앙 Policy as Code 적용 및 컨테이너 기반 동일 이미지 배포 강제 | 전사 보안 가드레일 일관성 및 컴플라이언스 충족 |

## Ⅶ. 결론

- **기술 위상/발전**: 엔터프라이즈의 보안/규제 요구와 클라우드 확장성을 조화시키는 핵심 인프라 모델로 확립되었으며, AWS Outposts, Azure Stack 등 분산 클라우드 하드웨어 어플라이언스로 진화
- **실무 적용/통제**: 데이터 중력(Data Gravity)을 고려한 DB 원본 배치, 전용선 물리적 이중화 및 서킷 브레이커 구성을 통한 네트워크 단절 시 독립 운영(Local Survivability) 보장
