## 답안 골격
```text

 ┃
 ┣━ Ⅰ 개요 ───── 프로세스 간 독립 주소 공간 격리로 인한 직접 데이터 교환 불가 → OS 커널 중계 IPC 메커니즘
 ┣━ Ⅱ 특징 ───── 주소 공간 격리 유지 · 커널 개입(시스템콜) · 동기식/비동기식 · 메시지 전달 vs 공유 메모리
 ┣━ Ⅲ 구조 ───── 파이프(익명/FIFO) · 메시지 큐 · 공유 메모리(Shared Memory) · 세마포어 · 소켓(UDS/TCP)
 ┣━ Ⅳ 흐름 ───── ① 송신 프로세스 시스템콜(shmget/msgsnd) → ② 커널 버퍼/공유 페이지 매핑 → ③ 수신 프로세스 읽기 → ④ 세마포어 동기화
 ┣━ Ⅴ 비교 ───── 메시지 전달 모델(Message Passing) vs 공유 메모리 모델(Shared Memory) / 파이프 vs 소켓
 ┗━ Ⅵ 실무 ───── 공유 메모리 동기화(Race Condition) / 메시지 복사 오버헤드 / 파이프 버퍼 단방향 한계
```

## 한 줄 본질
- 운영체제의 메모리 보호 메커니즘으로 인해 다른 프로세스의 가상 주소 공간을 직접 읽고 쓸 수 없는 구조적 장벽 → OS 커널이 중계하는 통신 채널(파이프, 큐, 소켓)이나 공통 물리 메모리 페이지를 매핑(공유 메모리)하여 데이터 교환 및 동기화 지원 → 안전한 협업 프로세스 구현 / 커널 모드 전환 및 메모리 복사 오버헤드, 동기화 제어 필수

## 핵심 그림
```text
  [ 1. 메시지 전달 모델 (Message Passing: Pipe, Queue, Socket) ]
  Process A (User) ──(1. 커널 복사)──> [ 커널 버퍼 / 큐 ] ──(2. 유저 복사)──> Process B (User)
  * 단점: 데이터 1건당 2회 복사(User -> Kernel -> User) 및 시스템 콜 오버헤드

  [ 2. 공유 메모리 모델 (Shared Memory: shmget / mmap) ]
  +--------------------+                               +--------------------+
  | Process A 가상 메모리 |                               | Process B 가상 메모리 |
  | [ A의 가상 주소 ] ─┼──────────────┐ ┌─────────────┼─> [ B의 가상 주소 ] |
  +--------------------+              │ │             +--------------------+
                                      v v
                      +───────────────────────────────+
                      |   동일한 물리 RAM 메모리 프레임 |
                      |   (커널 복사 없는 Zero-copy)    |
                      +───────────────────────────────+
  * 장점: CPU 최고 속도 직접 읽기/쓰기 / 주의: 세마포어로 동시 접근 동기화 필수!
```

## 핵심 용어
- 공유 메모리(Shared Memory): 두 개 이상의 프로세스가 동일한 물리 메모리 영역을 각자의 가상 주소 공간에 매핑하여 커널 개입 없이 최고 속도로 데이터를 공유하는 IPC 기법
- 유닉스 도메인 소켓(UDS: Unix Domain Socket): 네트워크 프로토콜 스택(IP/TCP 체크섬, 라우팅)을 거치지 않고 OS 커널 내부 메모리 버퍼에서 직접 프로세스 간 양방향 바이트 스트림을 전송하는 초고속 소켓
- 익명 파이프(Anonymous Pipe): 부모-자식 프로세스 간 단방향 통신만 지원하는 임시 커널 버퍼 채널(명령줄 파이프 `|` 의 구현체)

## 핵심 통찰
- IPC 성능의 핵심은 '메모리 복사(Memory Copy) 횟수'임 → 파이프, 메시지 큐, 소켓은 유저 영역에서 커널 버퍼로 한 번, 커널에서 상대 유저 영역으로 또 한 번 총 2번의 복사가 발생하지만, 공유 메모리는 복사가 0회(Zero-copy)이므로 대용량 데이터 전송에 압도적으로 유리
- 그러나 공유 메모리는 OS가 동기화를 전혀 해주지 않으므로, 개발자가 뮤텍스나 세마포어로 상호배제를 직접 구현하지 않으면 즉시 데이터 오염 발생
- 동일 호스트 내 컨테이너나 마이크로서비스 간 통신 시 일반 TCP 루프백(127.0.0.1) 소켓을 쓰면 불필요한 TCP 패킷화 및 체크섬 연산으로 CPU를 낭비하므로 유닉스 도메인 소켓(UDS)을 써야 함

## 이웃 토픽과 구분
- 메시지 전달(Message Passing) vs 공유 메모리(Shared Memory): 메시지 전달 = 소량 데이터 및 동기화가 자동 보장되는 안전한 통신(복사 비용 큼) / 공유 메모리 = 대용량 초고속 통신(복사 비용 0, 별도 동기화 기제 필수)

## 내 의견
- [사이드카 프록시 통신에서의 UDS 및 eBPF 기반 초고속 IPC 표준화] 쿠버네티스 서비스 메시(Istio)에서 앱 컨테이너와 Envoy 프록시 간 TCP 통신 오버헤드가 전체 지연의 30%를 차지함 → 나라면: 파드 내부 로컬 통신 채널을 UDS(Unix Domain Socket)로 구성하고, eBPF의 `sockops` 프로그램을 통해 커널 소켓 계층을 직접 단락(Short-circuit) 연결함으로써 TCP 스택을 완전히 우회하여 마이크로서비스 간 통신 지연을 제로에 가깝게 단축
