## 한 줄 본질
- 가상머신(VM)마다 독립된 게스트 OS 커널을 부팅함에 따른 기가바이트 단위 메모리 낭비와 수 분의 부팅 지연 → 호스트 OS 커널을 공유하면서 리눅스 네임스페이스와 cgroups 기술로 프로세스 수준의 자원과 환경을 완전히 격리 → 베어메탈 수준의 제로 오버헤드와 초고밀도 마이크로서비스 배포 실현 / 커널 공유로 인해 컨테이너 탈출(Container Escape) 보안 취약점 상존

## 핵심 용어
- 리눅스 네임스페이스(Namespaces): 프로세스가 시스템의 자원(프로세스 트리, 네트워크 어댑터, 마운트 지점, 사용자 계정 등)을 볼 때 자신만의 독립된 전용 공간으로 보이게 시야를 격리하는 커널 기능
- cgroups(Control Groups): 프로세스 집합이 사용할 수 있는 물리 자원(CPU, 메모리, 디스크 I/O, 네트워크 대역폭)의 최대 사용 한도를 강제 제어하는 커널 메커니즘
- 오버레이 파일시스템(OverlayFS / Overlay2): 읽기 전용 기본 이미지 레이어들 위에 쓰기 가능한 얇은 레이어(R/W Layer)를 얹어, 변경된 내용만 복사-쓰기(Copy-on-Write) 방식으로 기록하는 경량 저장 구조

## 핵심 통찰
- 컨테이너는 하이퍼바이저처럼 하드웨어를 흉내 내는 가상 머신이 아니라, '커널 격리 기술(chroot, namespace, cgroups)로 포장된 일반 호스트 프로세스'에 불과함 → 따라서 하이퍼바이저 변환 계층이 없어 네이티브 베어메탈과 100% 동일한 연산 성능 발휘
- 컨테이너 이미지의 불변성(Immutability)은 "내 로컬 PC에서는 됐는데 운영 서버에서는 왜 안 되지?"라는 고전적인 환경 불일치 문제를 종식시킴
- 단일 호스트 커널을 공유하므로, 컨테이너 내부의 루트 권한(UID 0)이 호스트 커널의 취약점(Dirty COW 등)을 악용하면 호스트 전체를 장악하는 컨테이너 탈출이 가능하므로 루트리스(Rootless) 실행이 필수적임

## 이웃 토픽과 구분
- 컨테이너 vs 가상머신(VM): 컨테이너 = 호스트 커널 공유 프로세스 격리(수십 MB, 수 초 기동, 베어메탈 성능) / VM = 하이퍼바이저 위 게스트 OS 완전 부팅(수 GB, 수 분 기동, 완벽한 하드웨어 보안 격리)

## 문제·원인·대책
- 사례: 121회 기출 대규모 컨테이너 서비스 운영 시 악성 컨테이너의 호스트 침해 및 디스크 고갈
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 취약 컨테이너 침해 후 호스트 루트 파일시스템 조작 (Container Escape) | 컨테이너를 기본 root 사용자로 실행 및 특권(Privileged) 모드 부여 | 비특권 컨테이너(Non-root), seccomp 시스템콜 필터 및 AppArmor/SELinux 강제 | 침해 시에도 호스트 커널 권한 상승 차단 |
| 수백 개 컨테이너 빌드 및 배포 반복 시 호스트 디스크 용량 100% 고갈 | 댕글링(Dangling) 레이어 및 과도한 패키지를 포함한 비대한 이미지 | 멀티 스테이지 빌드(Multi-stage Build) 및 경량 디스트로리스(Distroless) 이미지 채택 | 컨테이너 이미지 크기 90% 감축 및 디스크 절약 |

## 이렇게 출제된다

## 내 의견
- [컨테이너 보안 격리 극대화를 위한 경량 샌드박스 런타임 도입] 공용 클라우드나 멀티 테넌트 환경에서 일반 runc 컨테이너의 커널 공유는 보안 감사 지적 1순위임 → 나라면: 금융·개인정보 처리 파드에 한해 gVisor(애플리케이션 커널 인터셉트) 또는 Kata Containers(경량 마이크로VM 기반 1파드 1커널) 샌드박스 런타임을 선별 적용하여, 컨테이너의 기동 속도와 가상머신의 보안 격리성을 동시에 확보
