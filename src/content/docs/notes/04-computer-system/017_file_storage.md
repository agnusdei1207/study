## 한 줄 본질
- 블록 스토리지의 호스트 간 데이터 동시 공유 불가와 오브젝트 스토리지의 파일 부분 수정 불가 한계 → 친숙한 폴더/디렉터리 트리 구조와 POSIX 파일 시스템 인터페이스를 네트워크(NFS/SMB)를 통해 다중 클라이언트에 동시 제공 → 애플리케이션 수정 없는 원활한 파일 공유 및 협업 환경 보장 / 수천만 개 파일 누적 시 메타데이터 잠금(Locking)으로 인한 성능 급락

## 핵심 용어
- POSIX(Portable Operating System Interface): 유닉스 계열 운영체제의 공통 API 규격으로, 파일 열기(`open`), 읽기(`read`), 쓰기(`write`), 탐색(`seek`), 잠금(`flock`) 등의 표준 동작 보장
- 병렬 파일시스템(Parallel File System): 단일 NAS 헤더의 병목을 없애기 위해 메타데이터 서버(MDS)와 수백 대의 데이터 서버(OST)를 물리적으로 분리하여 초당 수백 GB의 대역폭을 뿜어내는 파일 스토리지(Lustre, GPFS, WekaFS)

## 핵심 통찰
- 파일 스토리지는 개발자에게 가장 친숙하고 레거시 호환성이 완벽하지만, '메타데이터의 저주(Metadata Curse)'를 태생적으로 안고 있음 → 파일 하나를 열 때마다 경로의 모든 부모 디렉터리 권한과 i-node 잠금을 확인해야 하므로 파일 개수가 수억 개로 폭증하면 스토리지 전체가 멈춤
- 다중 사용자가 동일 파일을 수정할 수 있도록 파일 락(File Locking) 기제를 제공하지만, 분산 환경에서 네트워크 단절이 발생하면 고아 락(Orphan Lock)으로 인해 파일이 영구 잠식되는 문제 빈발
- AI 학습 환경에서 소형 이미지 수천만 장을 일반 NFS로 읽으면 메타데이터 탐색 시간 때문에 GPU가 90% 이상 굶주림(Starvation) → 대규모 파일은 TAR나 TFRecord 같은 단일 대용량 파일로 패키징하여 순차 읽기를 유도해야 함

## 이웃 토픽과 구분
- 파일 스토리지 vs 오브젝트 스토리지: 파일 스토리지 = 디렉터리 트리 기반의 계층형 POSIX 구조(부분 수정 가능, 확장성 한계) / 오브젝트 스토리지 = 플랫 주소 공간 기반의 REST API 구조(부분 수정 불가, 무한 확장)
