## 답안 골격
```text
[오브젝트 스토리지] ◀━━ 머리: Ⅶ 내 의견 (AI 데이터 파이프라인의 고비용 I/O 해결을 위한 로컬 캐시 레이어 결합)
 ┃
 ┣━ Ⅰ 개요 ───── 계층형 파일시스템의 수십억 파일 처리 한계 → 플랫 네임스페이스 기반 무한 확장 스토리지
 ┣━ Ⅱ 특징 ───── 평면 구조 · 풍부한 메타데이터 · RESTful API(HTTP) · WORM(Write Once Read Many)
 ┣━ Ⅲ 구조 ───── Data(본체) + Metadata(커스텀 태그) + Unique ID(URI/키) + 버킷(Bucket)
 ┣━ Ⅳ 흐름 ───── ① HTTP PUT(객체 업로드) → ② 고유 ID 해싱 및 파티셔닝 → ③ Erasure Coding 분산 저장 → ④ HTTP GET
 ┣━ Ⅴ 비교 ───── 오브젝트 vs 블록 vs 파일 스토리지
 ┗━ Ⅵ 실무 ───── 데이터 부분 수정 불가(전체 덮어쓰기) / 높은 접근 지연(Latency) / 이그레스(Egress) 비용
```
- 필수 키워드: 플랫 네임스페이스 · 고유 ID(Key) · 커스텀 메타데이터 · RESTful API · Erasure Coding · WORM
- 배점 전략: 10점 = Ⅰ 개요 → Ⅲ 객체 구성 도식 → Ⅴ 3대 스토리지 비교 / 25점 = Ⅰ~Ⅶ 전개, Ⅳ Erasure Coding 저장 원리와 Ⅵ AI 학습 파이프라인 연계 방안
- 기출: 132회 1교시 `3대 스토리지 비교`, 140회 3교시 `AI 대규모 학습 인프라 구축을 위한 3대 스토리지 비교 및 최적 활용방안`

## 한 줄 본질
- 수십억 개 파일 누적 시 계층형 디렉터리(트리 탐색) 및 i-node 잠금으로 인한 I/O 병목 → 데이터를 본체·커스텀 메타데이터·고유 ID로 캡슐화하여 단일 평면(Flat) 주소 공간에 RESTful API로 분산 저장 → 페타·엑사바이트급 무한 확장 및 저비용 보관 / 파일 내 일부 바이트 수정 불가 및 밀리초 단위 지연 발생

## 핵심 그림
```text
+-------------------------------------------------------------+
|                      오브젝트 (Object)                      |
|  +-------------------------------------------------------+  |
|  | 고유 식별자 (Unique ID / Key): s3://bucket/dataset/01 |  |
|  +-------------------------------------------------------+  |
|  | 메타데이터 (Metadata): 생성일, 크기, 커스텀 태그      |  |
|  +-------------------------------------------------------+  |
|  | 데이터 본체 (Data Payload): 이미지, 비디오, 가중치    |  |
|  +-------------------------------------------------------+  |
+-------------------------------------------------------------+
                            │
               (REST API: GET / PUT / DELETE)
                            │
                            v
+-------------------------------------------------------------+
|           평면 네임스페이스 (Flat Namespace Bucket)         |
|  [Obj 1]  [Obj 2]  [Obj 3] ... [Obj N] (디렉터리 계층 없음) |
+-------------------------------------------------------------+
                            │ (분산 내결함 저장)
                            v
   [ Erasure Coding: 데이터 청크 분할 + 패리티 블록 노드 분산 ]
```

## 핵심 용어
- 이레이저 코딩(Erasure Coding): 원본 데이터를 $K$개 조각으로 쪼개고 $M$개의 패리티 조각을 추가하여 분산 저장함으로써, $M$개 디스크가 고장나도 데이터를 복구하는 저비용 고신뢰 복제 기법
- WORM(Write Once Read Many): 한 번 기록된 객체는 내용 수정이 불가능하며, 수정 시 새 버전으로 전체를 덮어써야 하는 스토리지 특성

## 핵심 통찰
- 오브젝트 스토리지는 POSIX 호환 파일시스템이 아님 → 파일 시스템 마운트나 `fseek()` 같은 임의 위치 쓰기가 불가능하므로 트랜잭션 DB나 OS 부팅 디스크로는 부적합
- AI 멀티모달 학습에서 수백 테라바이트의 비정형 데이터셋을 보관하는 비용 효율적 최적의 장소이나, GPU 직접 로딩 시 HTTP 통신 오버헤드로 GPU I/O Starvation 유발
- 메타데이터가 데이터와 함께 저장되므로 별도 외부 DB 인덱스 없이도 스토리지 자체에서 태그 기반 고속 검색 및 라이프사이클 수명 관리(티어링) 가능

## 이웃 토픽과 구분
- 오브젝트 스토리지 vs 블록 스토리지: 오브젝트 스토리지 = REST API로 객체 전체를 다루는 비정형·대용량 보관용 / 블록 스토리지 = 파이버채널/iSCSI로 바이트 블록 단위 고속 I/O를 제공하는 DB·OS용

## 문제·원인·대책
- 사례: 140회 기출 대규모 LLM/멀티모달 학습 시 데이터 로딩 병목
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| GPU 연산 중 데이터 로딩 대기로 GPU 사용률(GPU Utilization) 급락 | 오브젝트 스토리지의 높은 네트워크 지연 및 HTTP 전송 오버헤드 | 고속 NVMe 기반 로컬 블록 스토리지 또는 분산 파일 캐시(예: Alluxio, GPFS) 계층 도입 | GPU에 초당 수십 GB 고속 데이터 피딩 보장 |
| 멀티 클라우드 환경에서 대량 데이터 조회 시 막대한 통신 비용 발생 | CSP 간 데이터 반출(Egress) 요금 누적 | 접근 빈도에 따른 계층화(Hot/Warm/Cold/Glacier) 및 로컬 압축 포맷(Parquet, WebDataset) 적용 | 네트워크 전송량 및 보관 비용 절감 |

## 내 의견
- [AI 시대 스토리지 계층화(Tiering) 아키텍처 구축] 대규모 학습 데이터를 고가의 고성능 병렬 파일 스토리지(Lustre)에만 전량 보관하는 것은 인프라 예산 낭비임 → 나라면: 마스터 원본 데이터셋은 비용이 저렴한 오브젝트 스토리지(S3 호환)에 영구 보관하고, 활성 학습 에포크(Epoch) 동안만 고속 분산 캐시 클러스터(Alluxio)를 통해 로컬 NVMe 블록 스토리지로 프리페칭(Pre-fetching)하는 하이브리드 계층화 파이프라인 구성
