## 한 줄 본질
- 가상머신 단위의 무거운 스냅샷 복구는 복구 시간(RTO)이 길고 비용이 큼 → 애플리케이션을 무상태(Stateless) 컨테이너로 추상화하고 데이터는 다중 리전 분산 저장소로 이원화 → 인프라 장애 시 선언적 명세(GitOps)로 즉시 재배포 가능 / 리전 간 데이터 동기화 지연과 네트워크 이중 비용 발생

## 핵심 용어
- RTO(Recovery Time Objective): 재해 발생 후 비즈니스가 허용하는 최대 복구 소요 시간
- RPO(Recovery Point Objective): 재해 발생 시 데이터 유실이 허용되는 최대 시점 간격
- GitOps: Git 저장소를 단일 진실 공급원(Single Source of Truth)으로 삼아 클러스터 인프라와 앱 상태를 선언적으로 동기화하는 배포 모델

## 핵심 통찰
- 컨테이너 자체는 복구 대상이 아님 → 이미지와 선언적 매니페스트(YAML)만 있으면 어느 리전에서든 초 단위로 파드를 띄울 수 있으므로, 재해복구의 본질은 '상태(Stateful Data)'의 복제 지연 극복임
- Active-Active는 단순 이중화가 아니라 합의 알고리즘의 문제임 → 리전 간 거리에 따른 네트워크 왕복 시간(RTT) 때문에 완전 동기 복제는 쓰기 처리량을 저하시키고, 비동기 복제는 데이터 유실 위험을 수반함
- 복구 절차서는 재해 시 작동하지 않음 → 정기적인 카오스 엔지니어링(Chaos Engineering)을 통해 운영 중에 임의로 리전 네트워크를 차단하고 복구 동작을 검증해야 함

## 이웃 토픽과 구분
- 전통적 DR vs 클라우드 네이티브 DR: 전통적 DR = Standby 서버 대기, 스토리지 볼륨 복제 기반 수동 페일오버(시간 단위) / 클라우드 네이티브 DR = 오토스케일링과 GitOps 배포, 글로벌 라우팅 기반 자동 전환(분·초 단위)

## 내 의견
- [재해복구의 신뢰성은 문서가 아닌 지속적 검증 코드로 보장] 수동 점검표에 의존한 연례 DR 훈련은 클라우드 구성 변경 속도를 따라가지 못해 실전 실패를 초래함 → 나라면: 인프라 전체를 코드화(IaC)하여 GitOps 파이프라인으로 통제하고, 카오스 메시(Chaos Mesh)를 도입하여 매 분기 프로덕션 환경에서 트래픽을 단절시키는 무중단 페일오버 카오스 테스트를 자동화하여 RTO 5분 이내를 실측 검증
