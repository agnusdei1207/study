## 답안 골격
```text
[오픈소스 DBMS 전환] ◀━━ 머리: Ⅶ 내 의견 (상용 특화 문법의 자동 변환 파이프라인 구축 및 병행 운용(Shadow Run) 검증)
 ┃
 ┣━ Ⅰ 개요 ───── 고비용 상용 DBMS(Oracle 등)의 라이선스 락인 탈피 및 클라우드 네이티브 전환을 위해 오픈소스(PostgreSQL/MySQL)로 이전
 ┣━ Ⅱ 특징 ───── TCO(총소유비용) 대폭 절감 · 벤더 종속 탈피 · 클라우드 유연성 · 이기종 마이그레이션 위험 수반
 ┣━ Ⅲ 구조 ───── 전환 진단 도구 / 스키마 변환(SCT) / 데이터 복제 및 CDC / SQL/애플리케이션 전환 / 검증 및 롤백 체계
 ┣━ Ⅳ 흐름 ───── ① 대상 선정 및 호환성 분석 → ② 스키마/DDL 변환 → ③ 초기 대량 데이터 이관 → ④ 실시간 CDC 동기화 → ⑤ 정합성 검증 및 컷오버(Cutover)
 ┣━ Ⅴ 비교 ───── 상용 DBMS(Oracle) vs 오픈소스 DBMS(PostgreSQL/MySQL) (고비용 완제품/풍부한 벤더지원 vs 무료/커뮤니티·클라우드 관리형 서비스)
 ┗━ Ⅵ 실무 ───── 상용 전용 패키지(PL/SQL, NVL, 계층형 쿼리) 미지원에 따른 애플리케이션 수정 비용 폭증
```
- 필수 키워드: TCO 절감 · 벤더 종속(Lock-in) 탈피 · 스키마 변환(SCT) · CDC(Change Data Capture) · 컷오버(Cutover) · 무중단 마이그레이션 · PostgreSQL
- 배점 전략: 10점 = Ⅰ → Ⅳ 5단계 마이그레이션 절차 도식 → Ⅴ 상용 vs 오픈소스 비교표 / 25점 = Ⅰ~Ⅶ, Ⅲ 호환성 진단 툴체인 및 Ⅵ 정합성 검증·위험 관리
- 기출: 138회 2교시 1번 `상용 DBMS를 오픈소스 DBMS로 전환하는 수요 증대와 전환 방안` → Ⅰ 전환 배경 + Ⅳ 마이그레이션 절차 + Ⅵ 주요 위험 및 대책

## 한 줄 본질
- 천문학적인 상용 DBMS 라이선스 및 유지보수 비용(Lock-in) 한계 → 스키마 변환 도구와 실시간 변경 복제(CDC)를 통한 단계적 무중단 마이그레이션 → TCO 70% 이상 절감 / PL/SQL 등 고유 기능 재개발 비용 수반

## 핵심 그림
```text
[상용 DBMS에서 오픈소스 DBMS로의 무중단 전환 파이프라인]

  [ 기존 상용 DBMS ]                                 [ 오픈소스 DBMS ]
     (Oracle 등)                                      (PostgreSQL 등)
  ┌───────────────┐                                  ┌───────────────┐
  │ DDL / 스키마  │ ──Schema Conversion Tool(SCT)───>│ 스키마 생성   │
  └───────┬───────┘                                  └───────┬───────┘
          │                                                  │
          │ 1. 풀 데이터 일괄 적재 (Bulk Load)               │
          ├─────────────────────────────────────────────────>│
          │ 2. 실시간 증분 복제 (CDC: Debezium / GoldenGate) │
          ├─────────────────────────────────────────────────>│
          │                                                  │
          ▼                                                  ▼
   [트랜잭션 지속]                                    [실시간 동기화 상태]
          │                                                  │
          └──────────> [ 정합성 검증 및 컷오버 ] <───────────┘
```

## 핵심 용어
- CDC(Change Data Capture): 소스 DB의 트랜잭션 로그(Redo Log/WAL)를 실시간 감지하여 변경된 데이터만 타깃 DB로 즉시 복제하는 기술
- 컷오버(Cutover): 기존 운영 시스템을 신규 구축 시스템으로 전환하여 실제 트래픽을 신규 시스템으로 완전히 인계하는 최종 전환 시점

## 핵심 통찰
- 오픈소스 DB 자체는 무료이지만 전환 과정의 '인건비와 검증 비용'은 막대함 → 상용 DB에 깊게 박힌 Stored Procedure, Package, Trigger의 재작성 비용을 과소평가하면 프로젝트 파행
- 한 번에 빅뱅(Big-bang)으로 전환하면 실패 확률 급증 → 읽기 트래픽부터 오픈소스 복제본으로 전환하고, CDC 기반 동기화를 유지하며 섀도우 런(Shadow Run)을 거쳐 단계적 컷오버를 수행해야 함
- 오라클과의 문법 호환성이 가장 높은 오픈소스 DBMS는 PostgreSQL 계열(EDB Postgres, Aurora PostgreSQL)이 최우선 선택지

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| AWS SCT / DMS | 클라우드 전환 자동화 도구 | 이기종 DB 간 스키마 자동 변환 분석 리포트 및 초기 데이터·CDC 통합 마이그레이션 도구 |
| 섀도우 트래픽(Shadow Traffic) | 컷오버 전 안전성 검증 | 실제 사용자 프로덕션 요청을 복제하여 신규 오픈소스 DB로 전달하고 응답 정합성과 부하를 사전 검증 |

## 이웃 토픽과 구분
- 동종 마이그레이션 vs 이기종 마이그레이션: 동종(Oracle to Oracle) = 덤프/복제로 단순 이전 / 이기종(Oracle to PostgreSQL) = 데이터 타입 매핑, 함수 변환, 실행계획 차이 극복 필요

## 문제·원인·대책
- 적용 상황: 대기업 기간계 ERP 오라클 DB의 PostgreSQL 전환
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 수천 개의 복잡한 오라클 PL/SQL 패키지 변환에 수십 인월 소요 | 오라클 특화 내장 함수 및 패키지 구조 의존 | 오라클 호환성 엔진(EDB) 활용 및 핵심 비즈니스 로직의 Java/Spring 계층 이관 | DB 종속성 탈피 및 개발 기간 6개월 단축 |
| 전환 직후 특정 핵심 조회 쿼리가 인덱스를 타지 않고 풀스캔 발생 | 상용 CBO와 오픈소스 CBO의 옵티마이저 통계 계산 방식 차이 | `ANALYZE` 통계 갱신 및 실행 계획 기반 인덱스 재설계 | 응답 시간 정상화 |

## 내 의견
- [DB 엔진 전환보다 애플리케이션 종속성 제거가 우선] DB 자체만 오픈소스로 바꾸려 하면 문법 불일치로 실패하므로, 전환 전 단계에서 ORM(JPA, MyBatis) 추상화를 선행하고 Stored Procedure의 비즈니스 로직을 백엔드 마이크로서비스(MSA)로 흡수하는 현대화 전략이 근본적 해법

## 찾아볼 것
- PostgreSQL의 외래 데이터 래퍼(FDW, Foreign Data Wrapper)를 활용한 이기종 DB 간 페더레이션 쿼리
