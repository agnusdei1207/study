## 답안 골격
```text
[논클러스터드 인덱스] ◀━━ 머리: Ⅶ 내 의견 (랜덤 I/O를 원천 차단하는 커버링 인덱스 설계 및 선택도 15% 이내 관리)
 ┃
 ┣━ Ⅰ 개요 ───── 실제 데이터 행의 물리적 정렬 순서와 무관하게 별도의 B+Tree 구조에 키 값과 데이터 포인터(RID/PK)를 저장하는 보조 색인
 ┣━ Ⅱ 특징 ───── 테이블당 복수 개(다수) 생성 가능 · 물리 데이터 정렬 불변 · 리프 페이지에 포인터(RID/클러스터드 키) 저장 · 2차 탐색(랜덤 I/O) 수반
 ┣━ Ⅲ 구조 ───── 루트 노드 / 브랜치 노드 / 리프 노드(인덱스 키 + 행 식별자 RID 또는 PK 키) / 실제 데이터 페이지
 ┣━ Ⅳ 흐름 ───── ① WHERE 조건 키 검색 → ② B+Tree 탐색으로 리프 페이지 도달 → ③ RID/PK 획득 → ④ 실제 데이터 페이지 랜덤 액세스(Lookup)
 ┣━ Ⅴ 비교 ───── 논클러스터드 인덱스 vs 클러스터드 인덱스 (책 뒤 색인/테이블당 다수/랜덤 I/O vs 사전 본문/테이블당 1개/리프=데이터)
 ┗━ Ⅵ 실무 ───── 선택도(Selectivity) 불량 시 풀스캔보다 느림 / 과도한 인덱스 생성에 따른 DML(INSERT/UPDATE) 지연
```
- 필수 키워드: 보조 인덱스(Secondary Index) · RID(Row ID) · 클러스터드 키 포인터 · 랜덤 I/O · 룩업(Lookup) · 커버링 인덱스(Covering Index) · 선택도
- 배점 전략: 10점 = Ⅰ → Ⅲ B+Tree 리프-데이터 룩업 구조도 → Ⅴ 클러스터드와의 비교표 / 25점 = Ⅰ~Ⅶ, Ⅳ 2차 룩업 I/O 메커니즘 및 Ⅵ 커버링 최적화
- 기출: 136회 2교시 5번 `데이터베이스 인덱스 설명 및 클러스터드 인덱스와 논클러스터드 인덱스 비교` → Ⅰ 개념 + Ⅲ/Ⅳ 논클러스터드 룩업 구조 + Ⅴ 비교

## 한 줄 본질
- 원본 데이터의 물리적 순서를 건드리지 않고 다양한 조건 검색 가속 요구 → 별도의 B+Tree 리프에 키와 물리 주소(RID/PK)를 매핑 보관 → 다차원 다중 조회 유연성 확보 / 데이터 블록 랜덤 I/O 비용 발생

## 핵심 그림
```text
[논클러스터드 인덱스의 B+Tree 구조 및 데이터 페이지 랜덤 액세스]

  [ 논클러스터드 인덱스 B+Tree ]
           [ Root Block ]
              /        \
       [ Branch ]    [ Branch ]
         /    \        /    \
     ┌────────────────────────┐
     │ Leaf Page (정렬된 키)  │
     │ [이름: '김' | RID: #1] │ ──┐ (RID = 파일번호+블록번호+슬롯)
     │ [이름: '박' | RID: #3] │ ──┼──────┐
     │ [이름: '이' | RID: #2] │ ──┼──┐   │
     └────────────────────────┘   │  │   │
                                  ▼  ▼   ▼ (무작위 디스크 랜덤 I/O)
     ┌────────────────────────────────────────────────────────┐
     │ 실제 데이터 페이지 (테이블 힙 세그먼트: 정렬되어 있지 않음!)│
     │ Block 1: [Row 1: 김철수, 25세, 서울] (RID #1)          │
     │ Block 2: [Row 2: 이영희, 30세, 부산] (RID #2)          │
     │ Block 3: [Row 3: 박민수, 28세, 대구] (RID #3)          │
     └────────────────────────────────────────────────────────┘
```

## 핵심 용어
- RID(Row Identifier): 힙(Heap) 테이블 환경에서 행이 저장된 물리적 위치인 데이터 파일 번호, 블록 번호, 슬롯 번호로 구성된 고유 주소 포인터
- 북마크 룩업(Bookmark Lookup): 논클러스터드 인덱스 리프에서 찾은 포인터를 가지고 실제 데이터 행을 읽기 위해 데이터 페이지로 랜덤 접근하는 I/O 연산

## 핵심 통찰
- 논클러스터드 인덱스는 '책 맨 뒤의 찾아보기(색인)'와 같음 → 색인은 가나다순이지만 본문 페이지는 주제 순서대로 흩어져 있어 색인을 보고 본문으로 건너뛰는 비용 발생
- 선택도(Selectivity)가 15~20%를 넘어가면 옵티마이저는 인덱스를 버리고 풀 테이블 스캔(Full Table Scan)을 선택함 → 100건 중 20건을 찾기 위해 20번의 디스크 랜덤 I/O를 하느니 한 번에 시퀀셜 I/O로 퍼올리는 게 훨씬 빠르기 때문
- 북마크 룩업 비용을 제로(0)로 만드는 마법이 바로 '커버링 인덱스(Covering Index)' → SELECT 절에 필요한 모든 컬럼을 인덱스 키나 INCLUDE 절에 넣어 데이터 페이지 방문 자체를 생략

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| INCLUDE 인덱스 | 커버링 인덱스의 효율적 구현 | B+Tree 루트/브랜치에는 키를 올리지 않고 리프에만 비키(Non-key) 컬럼을 적재해 트리 비대화 억제 |
| 필터드 인덱스(Filtered Index) | 조건부 논클러스터드 인덱스 | `WHERE status = 'ACTIVE'`처럼 특정 조건을 만족하는 부분 행들만 색인하여 공간과 쓰기 비용 절감 |

## 이웃 토픽과 구분
- MySQL(InnoDB) vs Oracle의 보조 인덱스 리프: Oracle = 힙 테이블의 물리적 행 주소(RID)를 직접 보관 / MySQL InnoDB = 클러스터드 인덱스의 기본키(PK) 값을 보관(PK를 통한 2차 B+Tree 탐색 발생)

## 문제·원인·대책
- 적용 상황: 대규모 회원 테이블에서 이메일 검색 쿼리 병목
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 이메일 인덱스를 탔음에도 동시 요청 증가 시 디스크 I/O 100% 포화 | 리프 노드 확인 후 실제 데이터 페이지를 조회하는 북마크 룩업(Random I/O) 빈발 | 이메일 인덱스에 이름, 상태 컬럼을 추가한 커버링 인덱스 구축 | 데이터 블록 I/O 100% 제거 및 쿼리 지연 90% 단축 |
| 회원 가입 시마다 10개 이상의 논클러스터드 인덱스 재배치로 회원 등록 지연 | 불필요하게 남발된 중복·유사 보조 인덱스 | DBMS 성능 통계 분석 후 최근 3개월간 실행 계획에 미참여한 인덱스 5개 삭제 | INSERT 처리량 2.5배 개선 |

## 이렇게 출제된다
- 제136회 2교시 5번: "데이터베이스 인덱스(Index)를 설명하고, 클러스터드 인덱스(Clustered Index)와 논클러스터드 인덱스(Non-Clustered Index)를 비교하여 설명하시오." → 요구 포인트: 논클러스터드 인덱스 정의 + B+Tree 및 리프 포인터(RID/PK) 룩업 구조 + 클러스터드와의 차이점 비교표

## 내 의견
- [InnoDB의 클러스터드 키 크기가 미치는 나비효과] MySQL InnoDB 환경에서 클러스터드 인덱스(PK)를 UUID(36바이트) 같은 긴 문자열로 잡으면, 테이블에 달린 모든 논클러스터드 인덱스의 리프 노드가 거대해져 버퍼 풀 낭비 초래 → 나라면: PK는 작고 단조 증가하는 BIGINT(8바이트)를 기본 채택하여 보조 인덱스들의 메모리 효율을 극대화

## 찾아볼 것
- 배치 키 액세스(BKA, Batched Key Access)와 다중 범위 읽기(MRR, Multi-Range Read)가 랜덤 I/O를 순차 I/O로 전환하는 원리
