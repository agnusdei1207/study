## 답안 골격
```text
[CBO (비용 기반 옵티마이저)] ◀━━ 머리: Ⅶ 내 의견 (정확한 객체 통계정보 갱신과 히스토그램 수집을 통한 최적 실행계획 유도)
 ┃
 ┣━ Ⅰ 개요 ───── 테이블, 인덱스, 시스템의 사전 수집된 통계 정보를 기반으로 예상되는 자원 비용(I/O, CPU)이 최소인 실행 계획을 선택하는 DB 최적화 엔진
 ┣━ Ⅱ 특징 ───── 통계 정보 기반 · 동적 비용 산정 · 디스크 I/O 및 CPU 연산량 추정 · 히스토그램 활용
 ┣━ Ⅲ 구조 ───── 질의 변환기(Query Transformer) / 대안 생성기(Estimator) / 비용 산정기(Cost Estimator) / 실행 계획 생성기 / 데이터 딕셔너리(통계)
 ┣━ Ⅳ 흐름 ───── ① SQL 파싱 및 표준화 → ② 질의 변환(서브쿼리 Unnesting 등) → ③ 대안 실행 계획 생성 → ④ 통계 기반 비용 계산 → ⑤ 최소 비용 실행계획 결정
 ┣━ Ⅴ 비교 ───── CBO vs RBO (비용 기반/통계 필요/실행계획 유연성 vs 규칙 우선순위 기반/통계 불필요/고정 실행계획)
 ┗━ Ⅵ 실무 ───── 통계 정보 미갱신(Stale Stats)으로 인한 비정상 풀스캔 / 데이터 편향 시 단일 선택도 왜곡
```
- 필수 키워드: CBO · 비용(Cost) · 데이터 딕셔너리 · 통계 정보 · 히스토그램 · 질의 변환기 · 선택도(Selectivity) · 카디널리티(Cardinality) · RBO
- 배점 전략: 10점 = Ⅰ → Ⅲ CBO 내부 아키텍처 블록도 → Ⅴ CBO vs RBO 비교표 / 25점 = Ⅰ~Ⅶ, Ⅳ 비용 계산 공식(I/O + CPU) 및 Ⅵ 통계 수집 전략
- 기출: 127회 `데이터베이스 옵티마이저의 유형(RBO, CBO)과 CBO의 최적화 절차` → Ⅰ 개념 + Ⅲ/Ⅳ CBO 동작 구조 + Ⅴ RBO와의 비교

## 한 줄 본질
- 정적 규칙(RBO)의 데이터 분포 무시로 인한 비효율 한계 → 테이블 행 수, 블록 수, 인덱스 높이, 컬럼 히스토그램 통계 기반 예상 디스크/CPU 비용 계산 → 최소 비용 실행계획 수립 / 통계 오염 시 악성 플랜 생성

## 핵심 그림
```text
[CBO (비용 기반 옵티마이저) 내부 처리 파이프라인]

  [ SQL 쿼리 입력 ]
          │
          ▼
 ┌─────────────────┐
 │   질의 변환기   │ : 서브쿼리 언네스팅, 뷰 머징, 조건절 전이 등 최적화
 └────────┬────────┘
          ▼
 ┌─────────────────┐      ┌─────────────────────────────┐
 │   대안 생성기   │<────>│   데이터 딕셔너리           │
 │ (후보 플랜 생성)│      │   - 테이블 행 수, 블록 수   │
 └────────┬────────┘      │   - 인덱스 레벨, 클러스터링 팩터│
          ▼               │   - 컬럼 카디널리티, 히스토그램 │
 ┌─────────────────┐      └──────────────┬──────────────┘
 │   비용 산정기   │<────────────────────┘
 │ (Cost Estimator)│ : Cost = (I/O 비용) + (CPU 비용)
 └────────┬────────┘
          ▼
 [ 최적 실행 계획 (Execution Plan) 확정 및 SQL 엔진 전달 ]
```

## 핵심 용어
- 카디널리티(Cardinality): 특정 컬럼 또는 실행 계획의 각 단계에서 처리되는 유효 행(Row)의 수 ($\text{Total Rows} \times \text{Selectivity}$)
- 클러스터링 팩터(Clustering Factor): 인덱스 키 순서와 실제 테이블 데이터 블록의 물리적 정렬 순서가 얼마나 일치하는지를 나타내는 지표로, CBO의 인덱스 스캔 비용에 결정적 영향

## 핵심 통찰
- CBO가 산출하는 'Cost'는 실제 실행 초(Sec)가 아니라 '가상의 자원 소모 단위'임 → 비용이 100이라고 100ms가 걸리는 것이 아님
- CBO의 지능은 전적으로 '통계 정보의 정확성'에 종속됨 → 1,000만 건 테이블의 통계가 100건으로 등록되어 있다면 CBO는 당연히 인덱스를 버리고 풀스캔을 선택하는 재앙 발생
- 데이터가 특정 값에 치우친 편향(Skewness) 데이터에서는 평균 선택도 계산이 틀어짐 → 이때 도수분포표인 '히스토그램(Histogram)'을 수집해야 CBO가 바른 판단을 내림

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 히스토그램(Histogram) | 컬럼 값 편향 통계 수집 | 데이터가 고르지 않을 때 높이 균형(Height-Balanced)이나 주파수(Frequency) 기반 버킷으로 분포 표현 |
| 옵티마이저 힌트(Hint) | CBO 실행계획의 개발자 제어 | `/*+ INDEX(a idx_1) */`처럼 CBO의 판단을 무시하고 특정 실행 계획을 강제 지정하는 지시어 |

## 이웃 토픽과 구분
- CBO vs RBO: RBO = 15개 정적 순위 규칙(PK 유일 검색 1위, 풀스캔 15위 등)에 따라 무조건 결정 / CBO = 데이터 양과 하드웨어 스펙 통계를 바탕으로 동적 비용을 계산해 결정

## 문제·원인·대책
- 적용 상황: 대규모 일일 배치 작업 후 온라인 트랜잭션 쿼리 속도 저하
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 야간 배치로 1,000만 건 적재 후 아침 조회가 전부 풀스캔으로 빠져 타임아웃 | 대량 데이터 적재 후 딕셔너리 통계 정보 미갱신(Stale Stats) | 배치 완료 직후 `DBMS_STATS.GATHER_TABLE_STATS` 자동 실행 연동 | 최신 통계 기반 인덱스 스캔 실행계획 즉시 복원 |
| 특정 고객 ID 조회 시 데이터가 1건인데도 CBO가 풀스캔 플랜 채택 | 기본 균등 분포 가정으로 인한 선택도 과대 계산 | 해당 컬럼 대상 히스토그램(`FOR ALL COLUMNS SIZE AUTO`) 수집 | 카디널리티 정확도 확보 및 인덱스 레인지 스캔 유도 |

## 이렇게 출제된다
- 제127회: "데이터베이스 최적화에서 RBO와 CBO를 비교하고, CBO의 동작 원리 및 주요 구성요소를 설명하시오." → 요구 포인트: RBO의 한계 + CBO 정의 + 3대 구성요소(질의변환기, 대안생성기, 비용산정기) + 통계정보(카디널리티, 선택도, 히스토그램)의 역할

## 내 의견
- [힌트 남발로 인한 장기적 부채 방지] 개발자가 CBO의 쿼리 변환을 믿지 못하고 힌트(`/*+ INDEX ... */`)를 떡칠해 놓으면, 훗날 테이블 구조나 데이터 볼륨이 100배 커졌을 때 힌트가 족쇄가 되어 더 좋은 플랜으로의 진화를 가로막음 → 나라면: 힌트는 비상 응급 처치로만 제한하고, 통계 정보 수집 주기 단축과 인덱스 재설계로 CBO가 자연스럽게 최적 플랜을 찾도록 유도

## 찾아볼 것
- 적응형 쿼리 최적화(Adaptive Query Optimization)가 런타임 통계를 피드백받아 실행 계획을 동적으로 변경하는 메커니즘
