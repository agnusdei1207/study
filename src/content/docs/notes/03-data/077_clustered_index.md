## 답안 골격
```text
[클러스터드 인덱스] ◀━━ 머리: Ⅶ 내 의견 (단조 증가 시퀀스 PK 채택으로 페이지 분할 억제 및 범위 스캔 성능 극대화)
 ┃
 ┣━ Ⅰ 개요 ───── 테이블의 실제 물리적 데이터 행들을 인덱스 키 순서와 정확히 일치하도록 정렬하여 저장하는 인덱스
 ┣━ Ⅱ 특징 ───── 테이블당 오직 1개 존재 · 리프 노드 = 실제 데이터 페이지 · 북마크 룩업 없음 · 범위 검색(BETWEEN) 최강
 ┣━ Ⅲ 구조 ───── 루트 노드 / 브랜치 노드 / 리프 노드(= 실제 데이터 행 페이지, 양방향 링크드 리스트)
 ┣━ Ⅳ 흐름 ───── ① WHERE 절 클러스터드 키 조건 수신 → ② B+Tree 루트/브랜치 탐색 → ③ 리프 노드(데이터 페이지) 직접 도달 → ④ 추가 디스크 I/O 없이 데이터 반환
 ┣━ Ⅴ 비교 ───── 클러스터드 인덱스 vs 논클러스터드 인덱스 (사전 본문/테이블당 1개/리프가 데이터 vs 책 뒤 찾아보기/테이블당 다수/포인터 룩업)
 ┗━ Ⅵ 실무 ───── 무작위 키(UUID) 삽입 시 빈번한 페이지 분할(Page Split) 및 디스크 단편화 유발
```
- 필수 키워드: 클러스터드 인덱스 · 리프 노드 = 데이터 페이지 · 테이블당 1개 · 페이지 분할(Page Split) · 북마크 룩업 생략 · 범위 검색(Range Scan) · 기본키(PK)
- 배점 전략: 10점 = Ⅰ → Ⅲ 리프=데이터 B+Tree 도식 → Ⅴ 클러스터드 vs 논클러스터드 비교표 / 25점 = Ⅰ~Ⅶ, Ⅳ I/O 경로 비교 및 Ⅵ 키 선정 전략(Auto-increment vs UUID)
- 기출: 136회 2교시 5번 `데이터베이스 인덱스 설명 및 클러스터드 인덱스와 논클러스터드 인덱스 비교` → Ⅰ 개념 + Ⅲ 리프=데이터 구조 + Ⅴ 비교

## 한 줄 본질
- 논클러스터드 인덱스의 2차 포인터 룩업(랜덤 I/O) 병목 → 실제 데이터 레코드를 인덱스 키 순서대로 디스크 블록에 물리 정렬 저장 → 단 한 번의 트리 탐색으로 데이터 즉시 획득 및 범위 스캔 가속 / 삽입 시 페이지 분할 비용 발생

## 핵심 그림
```text
[클러스터드 인덱스의 B+Tree 구조 (리프 페이지 = 실제 데이터)]

           [ Root Block ]
              /        \
       [ Branch ]    [ Branch ]
         /    \        /    \
     ┌────────────────────────────────────────────────────────┐
     │ Leaf Page = 실제 데이터 페이지 (키 순서로 물리적 정렬)│
     │ [Page 1] (ID: 1 ~ 3)                                   │
     │  - 1: 김철수, 25세, 개발팀                             │
     │  - 2: 이영희, 30세, 기획팀   <──> [Page 2] (ID: 4 ~ 6) │
     │  - 3: 박민수, 28세, 디자인팀         - 4: 정지훈, 35세 │
     └────────────────────────────────────────────────────────┘
     * 리프에 도달하는 즉시 모든 컬럼 데이터가 존재함!
     * 추가적인 테이블 데이터 블록 룩업(랜덤 I/O)이 완전히 제로(0)!
```

## 핵심 용어
- 리프 페이지(Leaf Page): 클러스터드 인덱스에서 별도의 포인터 없이 테이블의 모든 컬럼 데이터가 실제로 저장되어 있는 물리적 데이터 블록
- 페이지 분할(Page Split): 정렬된 페이지 중간에 새로운 데이터가 삽입될 때 공간이 부족하여 새로운 페이지를 할당하고 데이터의 절반을 이동시키는 고비용 I/O 작업

## 핵심 통찰
- 클러스터드 인덱스는 '영어 사전'과 같음 → 단어 자체가 이미 알파벳순으로 정렬되어 인쇄되어 있으므로 별도의 찾아보기 페이지 없이 단어 위치를 찾으면 뜻이 바로 나옴
- 테이블당 단 1개만 생성 가능한 이유: 실제 물리적 데이터 파일은 오직 하나의 순서로만 정렬되어 디스크에 존재할 수 있기 때문
- PK(기본키)로 UUID를 쓰면 안 되는 결정적 이유: 무작위 UUID는 항상 정렬된 클러스터드 페이지의 '중간'을 비집고 들어가 끊임없는 페이지 분할을 일으켜 디스크 공간 낭비와 쓰기 병목 유발

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| IOT(Index-Organized Table) | Oracle에서의 클러스터드 구현 | 일반 힙(Heap) 테이블 대신 인덱스 구조 자체에 전체 테이블 데이터를 저장하는 오라클의 명칭 |
| Fill Factor | 페이지 분할 완화 파라미터 | 인덱스 생성 시 리프 페이지에 여유 공간(예: 80%만 채움)을 남겨두어 신규 삽입 시 분할을 지연시키는 설정 |

## 이웃 토픽과 구분
- 클러스터드 인덱스 vs 클러스터링(Clustering): 클러스터드 인덱스 = B+Tree 기반 단일 테이블 정렬 / 클러스터링(오라클 클러스터) = 조인이 잦은 서로 다른 두 테이블을 동일 블록에 모아 저장하는 기술

## 문제·원인·대책
- 적용 상황: 대규모 결제 로그 테이블의 주문일시 범위 조회
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 기간 10만 건 조회 시 논클러스터드 인덱스 사용으로 10만 번 랜덤 I/O 발생 | 인덱스 키와 데이터 블록의 물리적 분리 | 주문일시를 클러스터드 인덱스로 변경 | 시퀀셜 I/O 기반 단 수십 개 블록 읽기로 쿼리 100배 가속 |
| 대량 INSERT 중 트랜잭션 지연 및 버퍼 락 경합 발생 | 무작위 UUID를 클러스터드 PK로 사용하여 연속적인 페이지 분할(Page Split) 유발 | 자동 증가(Auto-increment) 정수형 PK로 변경하거나 타임스탬프 기반 UUID(v7) 도입 | 페이지 분할 제로화 및 쓰기 속도 4배 향상 |

## 이렇게 출제된다
- 제136회 2교시 5번: "데이터베이스 인덱스(Index)를 설명하고, 클러스터드 인덱스(Clustered Index)와 논클러스터드 인덱스(Non-Clustered Index)를 비교하여 설명하시오." → 요구 포인트: 클러스터드 인덱스 개념 + 리프 노드가 데이터 블록인 구조적 특징 + 논클러스터드와의 5대 차이점 비교표

## 내 의견
- [클러스터드 키 선정의 3대 원칙 준수] 실무에서 의미 있는 복합 비즈니스 키(주민번호+일자)를 클러스터드 키로 잡았다가 자식 테이블 및 보조 인덱스의 비대화로 고통받는 경우 다수 → 나라면: 클러스터드 키는 ①단조 증가(Monotonic), ②불변(Immutable), ③작은 바이트(Compact) 크기를 갖는 대리키(Surrogate Key)를 원칙으로 수립

## 찾아볼 것
