## 답안 골격
```text
[이상현상] ◀━━ 머리: Ⅶ 내 의견 (함수적 종속성 분석 기반 단계적 무손실 분해(정규화)로 3대 이상현상 원천 차단)
 ┃
 ┣━ Ⅰ 개요 ───── 릴레이션 설계 시 중복 데이터와 잘못된 함수적 종속성으로 인해 발생하는 데이터 불일치 및 조작 오류
 ┣━ Ⅱ 특징 ───── 중복 데이터 기인 · 테이블 조작 시 발생 · 데이터 무결성 파괴 · 정규화로 제거 가능
 ┣━ Ⅲ 구조 ───── 삽입 이상(Insertion) / 삭제 이상(Deletion) / 갱신 이상(Modification/Update)
 ┣━ Ⅳ 흐름 ───── ① 비정규 릴레이션 → ② 조작(INSERT/UPDATE/DELETE) 수행 → ③ 원치 않는 부작용 발생 → ④ 정규화 분해로 해결
 ┣━ Ⅴ 비교 ───── 삽입 이상 vs 삭제 이상 vs 갱신 이상 (불필요 데이터 강제 입력 vs 연쇄 데이터 유실 vs 일부만 수정되어 불일치)
 ┗━ Ⅵ 실무 ───── 수강생 없는 과목 개설 불가 / 교수 퇴직 시 강의 정보 삭제 / 학생 주소 변경 시 일부 행 누락
```
- 필수 키워드: 삽입 이상 · 삭제 이상 · 갱신 이상 · 데이터 중복 · 함수적 종속성(FD) · 정규화(Normalization) · 무손실 분해
- 배점 전략: 10점 = Ⅰ → Ⅲ 3대 이상현상 정의 및 사례 테이블 도식 → Ⅵ 한 행 / 25점 = Ⅰ~Ⅶ, Ⅲ/Ⅳ 이상현상 발생 메커니즘 및 Ⅴ 비교표 상세
- 기출: 129회 `관계형 데이터베이스의 이상현상 3가지와 해결방안` → Ⅲ 3대 이상현상 + 해결방안(정규화)

## 한 줄 본질
- 하나의 릴레이션에 복수의 엔터티와 종속성이 혼재되어 데이터 중복 발생 → 삽입·삭제·갱신 시 불필요한 정보 강제 요구, 연쇄 유실, 불일치 유발 → 함수적 종속성에 따른 정규화 분해로 해소

## 핵심 그림
```text
[릴레이션 내 3대 이상현상 메커니즘]

  [학생_수강 릴레이션 (비정규 테이블)]
  학번  | 학생명 | 과목코드 | 과목명   | 담당교수
  ─────┼────────┼──────────┼──────────┼─────────
  1001 │ 홍길동 │ CS101    │ 자료구조 │ 이교수
  1002 │ 이순신 │ CS101    │ 자료구조 │ 이교수  <-- 과목명, 교수 중복
  NULL │ NULL   │ CS102    │ 알고리즘 │ 박교수  <-- [삽입 이상: 수강생 없으면 과목 등록 불가(PK Null 위반)]

  1. 삽입 이상: 과목을 등록하려는데 수강 학번이 없어 NULL 입력 불가 (개체 무결성 위배)
  2. 삭제 이상: 1001번 학생이 CS101 수강을 취소(튜플 삭제)하면 과목 정보까지 함께 영구 삭제
  3. 갱신 이상: CS101의 담당교수가 바뀌었을 때 일부 튜플만 수정하면 동일 과목에 서로 다른 교수 존재
```

## 핵심 용어
- 삽입 이상(Insertion Anomaly): 원하지 않는 정보를 함께 입력하지 않고는 어떤 데이터를 삽입하는 것이 불가능한 현상
- 삭제 이상(Deletion Anomaly): 어떤 튜플을 삭제할 때 상관없는 다른 정보까지 연쇄적으로 함께 유실되는 현상
- 갱신 이상(Update Anomaly): 중복된 튜플 중 일부 속성만 수정되어 동일한 데이터에 대한 불일치가 발생하는 현상

## 핵심 통찰
- 이상현상의 근본 뿌리는 '하나의 테이블에 두 개 이상의 실세계 대상(엔터티)을 섞어 넣은 것'임 → 학번 중심 엔터티와 과목 중심 엔터티가 혼합되면 반드시 중복과 이상이 발생
- 기본키(PK)가 아닌 일반 속성에 다른 속성이 종속(이행적/부분 함수 종속)되어 있을 때 갱신 이상이 필연적으로 발생
- 정규화는 이상현상을 없애는 유일한 수학적 기법이지만, 과도한 테이블 분해는 조인 비용을 초래하므로 트레이드오프 관리 필요

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 완전 함수적 종속(FFD) | 제2정규형(2NF)의 기준 | 기본키의 진부분집합이 아닌 기본키 전체에 종속되는 상태 |
| 무손실 조인 분해(Lossless Join) | 정규화 분해의 대원칙 | 릴레이션을 쪼갠 후 자연 조인했을 때 원래 릴레이션과 정확히 동일해야 하는 성질 |

## 이웃 토픽과 구분
- 이상현상 vs 동시성 이상현상: 이상현상 = 테이블 정적 스키마 설계 결함으로 인한 논리적 결함 / 동시성 이상현상(Dirty Read 등) = 트랜잭션 동시 실행 시 발생하는 런타임 결함

## 문제·원인·대책
- 적용 상황: 고객 주문 및 배송 관리 통합 테이블 운영
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 고객 주소 변경 후 이전 주문 건과 신규 주문 건의 주소 불일치 | 주문 테이블에 고객 주소 속성을 중복 보관하여 일부만 갱신(갱신 이상) | 고객 테이블과 주문 테이블로 3NF 정규화 분해 | 고객 정보 단일 갱신으로 전사 일관성 확보 |
| 신규 출시 상품을 카탈로그에 등록하려 하나 주문 ID 필수 제약으로 등록 실패 | 주문 엔터티와 상품 엔터티가 합쳐진 복합키 구조(삽입 이상) | 상품 마스터 테이블 분리 생성 | 주문 발생 전 단독 상품 등록 가능 |

## 이렇게 출제된다
- 제129회: "데이터베이스 설계 시 발생하는 이상현상(Anomaly)의 개념, 발생 원인, 3가지 유형 및 이를 해결하기 위한 정규화 방안을 설명하시오." → 요구 포인트: Ⅰ 개념/원인 + Ⅲ 3대 이상현상 사례 + 정규화(1NF~3NF) 해결책

## 내 의견
- [성능을 핑계로 한 초기 비정규화의 폐해] 설계 단계부터 조인을 줄이겠다는 명목으로 마스터 속성을 거래 테이블에 무분별하게 중복시켜 시스템 오픈 후 이상현상 수습에 막대한 리소스 투입 → 나라면: 논리 설계는 BCNF까지 철저하게 정규화하여 이상현상을 원천 배제하고, 성능 문제는 실제 부하 테스트 후 인덱스와 파티셔닝, 캐시(Redis)로 해결

## 찾아볼 것
