## 답안 골격
```text
[반정규화] ◀━━ 머리: Ⅶ 내 의견 (성능 저하 시 최후 수단 적용 → 인덱스·뷰·파티셔닝 선행 후 데이터 일관성 통제 장치 동반)
 ┃
 ┣━ Ⅰ 개요 ───── 정규화로 인한 과도한 조인(JOIN) 및 I/O 부하 → 읽기 성능 향상을 위해 의도적으로 중복·통합·분할
 ┣━ Ⅱ 특징 ───── 성능-일관성 트레이드오프 · 의도적 중복 허용 · 쓰기 성능 저하 감수 · 데이터 불일치 위험 수반
 ┣━ Ⅲ 구조 ───── 테이블 반정규화(병합/분할/추가) / 컬럼 반정규화(중복/파생/이력) / 관계 반정규화(중복 관계)
 ┣━ Ⅳ 흐름 ───── ① 정규화 완료 → ② 성능 병목 분석(조회 빈도/응답시간) → ③ 대안 검토(인덱스/캐시) → ④ 반정규화 수행 → ⑤ 무결성 보완
 ┣━ Ⅴ 비교 ───── 정규화 vs 반정규화 (중복 최소화·무결성 vs 조인 제거·조회 성능)
 ┗━ Ⅵ 실무 ───── 데이터 갱신 시 이상현상 발생 / 스토리지 낭비 / 갱신 부하로 전체 쓰기 트랜잭션 지연
```
- 필수 키워드: 역정규화 · 테이블 병합/분할 · 중복 컬럼 · 파생 컬럼 · 성능-일관성 상충 · 무결성 보완책
- 배점 전략: 10점 = Ⅰ → Ⅲ 3대 반정규화 대상(테이블·컬럼·관계) 기법 표 → Ⅵ 한 행 / 25점 = Ⅰ~Ⅶ, 앞 1/3에 Ⅲ 상세 기법 및 Ⅳ 선행 대안 검토 절차
- 기출: 135회 `물리 데이터 모델링 중 반정규화` → Ⅲ 기법 + Ⅳ 절차 및 실무 고려사항 / 125회 `정규화와 역정규화 비교` → Ⅴ 두 개념 상호보완 비교

## 한 줄 본질
- 제3정규형 이상의 분할된 테이블 간 다중 조인으로 인한 디스크 I/O 병목 → 데이터를 의도적으로 중복 저장하거나 테이블을 통합 → 조회 성능 대폭 개선 / 데이터 갱신 시 일관성 유지 비용 및 이상현상 발생

## 핵심 그림
```text
[반정규화 적용 전 대안 검토 및 수행 절차]

  [정규화 모델] ──> [조회 성능 저하 발견]
                           │
                           ▼
  [1단계 대안]  인덱스 최적화 / 쿼리 튜닝
  [2단계 대안]  뷰(View) 및 클러스터링 적용
  [3단계 대안]  Redis 캐시 레이어 도입
                           │ (여전히 성능 미달 시에만)
                           ▼
  [반정규화 수행] ┌─ 테이블 반정규화 (1:1/1:M 병합, 수직/수평 분할)
                  ├─ 컬럼 반정규화   (중복 컬럼, 파생/집계 컬럼 추가)
                  └─ 관계 반정규화   (중복 관계 형성으로 조인 경로 단축)
```

## 핵심 용어
- 파생 컬럼(Derived Column): 원본 데이터를 매번 SUM/COUNT 집계하지 않고 계산 결과를 별도 컬럼에 미리 저장해 두는 반정규화 기법(예: 주문 총금액)
- 수직 분할(Vertical Partitioning): 한 테이블의 컬럼들을 자주 조회되는 컬럼군과 거의 조회되지 않는 대용량 컬럼(CLOB, TEXT)군으로 쪼개어 블록 I/O를 줄이는 기법

## 핵심 통찰
- 반정규화는 데이터 모델링의 '첫 단추'가 아니라 '마지막 수단'임 → 완벽하게 정규화된 논리 모델을 만든 후, 병목 구간에 한해 인덱스·클러스터링·캐시를 적용해 보고도 안 될 때만 반정규화
- 읽기 속도를 얻는 대신 쓰기 속도를 잃음 → 중복 컬럼이 많아지면 단일 행을 수정할 때 여러 테이블의 컬럼들을 동시에 갱신해야 하므로 UPDATE/INSERT 성능이 급격히 저하
- 중복 데이터의 동기화 실패는 치명적인 비즈니스 오류를 부름 → 주문 상품 가격이 바뀌었는데 집계 테이블의 총금액이 과거 값으로 남아 결제 금액 불일치 발생

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 수평 분할(파티셔닝) | 테이블 반정규화 기법 | 대용량 행(Row)을 날짜나 키 범위 기준으로 파티션으로 나누어 풀스캔 방지 |
| 집계 테이블 추가 | 테이블 반정규화 기법 | 실시간 쿼리 대신 일/월 단위 사전 집계(Summary) 테이블을 별도 생성 |

## 이웃 토픽과 구분
- 반정규화 vs 비정규화: 비정규화 = 애초에 정규화를 아예 수행하지 않은 미숙한 설계 / 반정규화 = 정규화를 완벽히 끝낸 후 성능을 위해 통제 하에 의도적으로 되돌린 설계

## 문제·원인·대책
- 적용 상황: 대용량 쇼핑몰 주문 상세 내역 및 배송 상태 조회
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 상품명이 변경되었는데 과거 주문 내역의 상품명까지 일괄 변경되어 주문 시점 사실 왜곡 | 정규화에 집착해 주문상세 테이블에 상품명 중복 컬럼 미배치 | 주문 시점의 상품명·단가를 주문상세 테이블에 중복 컬럼으로 반정규화 | 시점 이력 보존 및 조인 제거 |
| 회원 테이블의 프로필 사진(BLOB) 때문에 단순 회원목록 조회가 느림 | 대용량 바이너리 데이터로 인한 디스크 I/O 블록 낭비 | 기본 정보 테이블과 이미지 BLOB 테이블로 수직 분할(Vertical Partitioning) | 기본 목록 조회 속도 5배 향상 |

## 이렇게 출제된다
- 제135회 2교시 1번: "물리 데이터 모델링 중 반정규화에 대하여 다음을 설명하시오." → 요구 포인트: Ⅲ 3대 반정규화 기법 + Ⅳ 사전 검토 절차 + Ⅵ 데이터 일관성 보완책
- 제125회 1교시 6번: "관계형 데이터베이스의 정규화와 역정규화" → 요구 포인트: 정규화와 역정규화의 목적, 장단점 및 트레이드오프 완결 비교

## 내 의견
- [습관적 반정규화로 인한 DB 부패] 쿼리가 조금만 느려도 인덱스 검토 없이 무조건 컬럼을 복사해 넣는 안이한 개발 만연 → 나라면: 반정규화 승인 체크리스트(조회 빈도 80% 이상, 갱신 빈도 5% 미만, 데이터 불일치 시 자동 보정 트리거/배치 구비)를 통과한 경우에만 반정규화를 허용하는 거버넌스 가이드라인 준수

## 찾아볼 것
- RDBMS의 Materialized View(실체화된 뷰)를 활용한 투명한 반정규화 구현 방식
