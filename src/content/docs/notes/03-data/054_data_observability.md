## 핵심 용어
- 데이터 다운타임(Data Downtime): 데이터가 누락되거나 오류 상태로 방치되어 현업의 비즈니스 및 의사결정에 사용할 수 없는 총 시간
- 데이터 계보(Data Lineage): 데이터가 원천 시스템에서 생성되어 다양한 변환(ETL) 과정을 거쳐 최종 소비처(BI, ML)까지 도달하는 전 라이프사이클의 족보 및 흐름도

## 핵심 통찰
- 시스템 인프라 모니터링(CPU, 메모리, 파이프라인 성공 여부)이 녹색(정상)이라도 데이터 자체는 텅 비어있거나 쓰레기 값일 수 있음 → 파이프라인 성공이 데이터 성공을 보증하지 않음
- 데이터 계보(Lineage)가 없으면 관측가능성은 완성되지 않음 → 이상치가 발견되었을 때 어떤 테이블과 대시보드가 오염될지, 어디서 문제가 시작되었는지를 추적할 수 없기 때문
- 정적 규칙(Rule-based) 기반 검증은 유지보수 불능 → 머신러닝으로 정상 데이터의 계절성과 볼륨 패턴을 자동 학습하는 이상 탐지가 필수

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| OpenLineage | 데이터 계보의 개방형 표준 규격 | Spark, Airflow, dbt 등 다양한 분산 프레임워크 간 계보 메타데이터 교환 API |
| 데이터 SLA(Service Level Agreement) | 데이터 품질 지표의 계약화 | 데이터 신선도와 정확성에 대한 팀 간 품질 보증 기준 및 미준수 시 에스컬레이션 규정 |

## 이웃 토픽과 구분
- 관측가능성(Observability) vs 모니터링(Monitoring): 모니터링 = "시스템이 죽었는가?"를 묻는 수동적·사후적 확인 / 관측가능성 = "왜 데이터가 비정상인가?"를 외부 출력을 통해 추론하는 능동적·원인 분석 역량

## 문제·원인·대책
- 적용 상황: 전사 마케팅 BI 대시보드의 데이터 정합성 결함
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 결제 DB 스키마 컬럼 변경 후 익일 경영진 리포트의 매출 집계가 0원으로 표시 | 사전 공유 없는 스키마 변경 및 다운스트림 영향도 파악 불가 | 스키마 드리프트 자동 감지 및 OpenLineage 기반 배포 차단 | 데이터 다운타임 90% 축소 |
| 매일 새벽 100만 건 들어오던 주문 로그가 100건만 유입되었으나 ETL 파이프라인은 '성공' 처리 | 단순 작업 프로세스 반환 코드(Exit 0)만 모니터링 | ML 기반 볼륨(Volume) 이상치 탐지 임계값 적용 | 비정상 데이터 적재 즉시 격리 및 경보 |

## 내 의견
- [사후 약방문식 데이터 검증의 한계] 데이터 사고가 발생한 뒤에야 현업의 항의를 받고 문제를 찾는 '무음 장애(Silent Failure)'가 빈번 → 나라면: Great Expectations나 Monte Carlo 같은 관측가능성 툴을 dbt/Airflow 파이프라인의 CI/CD에 내장하여, 데이터 테스트 실패 시 프로덕션 적재를 자동 중단하고 스테이징 격리 쿼런틴(Quarantine) 체계 구축
