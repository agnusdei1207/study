## 답안 골격
```text
[데이터베이스 인덱스] ◀━━ 머리: Ⅶ 내 의견 (카디널리티·선택도 기반 복합 인덱스 컬럼 순서 설계 및 미사용 인덱스 정기 정리)
 ┃
 ┣━ Ⅰ 개요 ───── 데이터 검색 속도 향상을 위해 테이블 컬럼 값을 정렬하여 별도 저장한 물리적 색인 구조
 ┣━ Ⅱ 특징 ───── B+Tree 기반 · 랜덤 I/O 최소화 · 읽기 가속 vs 쓰기(DML) 오버헤드 · 선택도(Selectivity) 민감
 ┣━ Ⅲ 구조 ───── 루트 블록(Root) / 브랜치 블록(Branch) / 리프 블록(Leaf) / 데이터 블록(RID/PK 포인터)
 ┣━ Ⅳ 흐름 ───── ① WHERE 절 인덱스 컬럼 조건 수신 → ② 루트 노드 탐색 → ③ 브랜치 분기 → ④ 리프 블록 도달 → ⑤ RID로 데이터 블록 랜덤 액세스
 ┣━ Ⅴ 비교 ───── 클러스터드 인덱스 vs 논클러스터드 인덱스 (물리적 정렬/테이블당 1개 vs 논리적 정렬/테이블당 다수)
 ┗━ Ⅵ 실무 ───── 인덱스 과다 생성으로 INSERT/UPDATE 지연 / 컬럼 가공(함수)으로 인한 인덱스 미사용
```
- 필수 키워드: B+Tree · 클러스터드 인덱스 · 논클러스터드 인덱스 · 선택도(Selectivity) · 카디널리티 · 리프 노드 · 랜덤 I/O · 커버링 인덱스
- 배점 전략: 10점 = Ⅰ → Ⅲ B+Tree 노드 계층 도식 → Ⅴ 클러스터드 vs 논클러스터드 비교표 / 25점 = Ⅰ~Ⅶ, Ⅳ 탐색 흐름 및 Ⅵ 인덱스 튜닝 원칙
- 기출: 136회 2교시 5번 `데이터베이스 인덱스 설명 및 클러스터드/논클러스터드 인덱스 비교` → Ⅰ 개념 + Ⅲ 구조 + Ⅴ 클러스터드 vs 논클러스터드 비교

## 한 줄 본질
- 전체 테이블 풀 스캔(Full Table Scan)의 선형 탐색 $O(N)$ 한계 → 정렬된 B+Tree 색인과 데이터 포인터 유지로 탐색 복잡도 $O(\log N)$ 달성 → 조회 가속 / 삽입·수정·삭제 시 인덱스 재정렬 비용 지불

## 핵심 그림
```text
[B+Tree 기반 인덱스 구조 및 데이터 탐색]

           [ Root Block ]
           │    10  │  20   │
           └──┬─────┴───┬───┘
              ▼         ▼
     [ Branch ]       [ Branch ]
     │ 5 │ 8  │       │ 12 │ 15 │
     └┬──┴─┬──┘       └─┬──┴──┬─┘
      │    │            │     │
      ▼    ▼            ▼     ▼
    ┌─────────────────────────────┐
    │  Leaf Blocks (양방향 연결)  │  <-- 정렬된 키 값 + 포인터(RID/PK)
    │ [1..4] <-> [5..7] <-> [8..9]│
    └──────────────┬──────────────┘
                   │ RID (File#, Block#, Slot#)
                   ▼
       [ Table Data Blocks ] (랜덤 I/O)
```

## 핵심 용어
- 선택도(Selectivity): 전체 레코드 중 특정 조건에 만족하는 레코드의 비율($1 / \text{Cardinality}$)로, 10~15% 이내일 때 인덱스 스캔이 효율적
- 커버링 인덱스(Covering Index): 쿼리 실행에 필요한 모든 컬럼이 인덱스 자체에 포함되어 데이터 블록 방문 없이 리프 노드만으로 질의를 완료하는 인덱스

## 핵심 통찰
- 인덱스는 공짜가 아님 → SELECT 성능을 높이는 대신 INSERT, UPDATE, DELETE 시 인덱스 리프 노드 분할(Page Split) 및 재배치 비용을 매번 지불함
- WHERE 절에서 인덱스 컬럼을 변형(`WHERE SUBSTR(id, 1, 3) = '001'` 또는 `WHERE price * 1.1 > 1000`)하면 옵티마이저는 인덱스를 타지 못하고 풀 스캔으로 전환됨
- 복합 인덱스는 컬럼 순서가 절대적 → 첫 번째 컬럼이 조건절에 없거나 범위 조건(>, <) 뒤에 배치된 컬럼은 인덱스 필터링으로만 동작하고 액세스 조건으로 동작하지 못함

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 클러스터드 인덱스 | 테이블 자체의 물리적 정렬 | 리프 페이지가 곧 실제 데이터 페이지이며 테이블당 단 1개만 존재 가능 |
| 논클러스터드 인덱스 | 보조적 색인 구조 | 리프 페이지에 정렬된 키 값과 데이터의 물리적 위치(RID 또는 클러스터드 키)를 보관 |

## 이웃 토픽과 구분
- B-Tree vs B+Tree: B-Tree = 모든 노드(루트/브랜치/리프)에 키와 데이터 포인터 보관 / B+Tree = 브랜치는 라우팅 키만 갖고 리프에만 데이터 포인터 집중 및 리프 간 연결리스트 구성(범위 스캔 최적화)

## 문제·원인·대책
- 적용 상황: 대규모 주문 이력 테이블 검색 쿼리 지연
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 인덱스가 걸려있음에도 500만 건 테이블 전체 풀 스캔 발생 | WHERE 절에서 날짜 컬럼을 `TO_CHAR(order_date) = '...'`로 가공 | 가공되지 않은 컬럼 조건으로 변경하거나 함수 기반 인덱스(FBI) 생성 | 인덱스 레인지 스캔 정상 동작으로 쿼리 지연 95% 단축 |
| 주문 등록 시 INSERT 지연 및 교착 상태(Deadlock) 발생 | 무분별하게 생성된 15개의 비효율적 논클러스터드 인덱스 | 실행 계획 분석 후 중복 인덱스 8개 통합 및 제거 | DML 처리량 3배 향상 |

## 이렇게 출제된다

## 내 의견
- [인덱스 만능주의로 인한 DML 병목] 쿼리가 느릴 때마다 임시방편으로 인덱스를 하나씩 추가하여 수십 개의 인덱스가 방치되는 운영 현장 다수 → 나라면: DBMS 통계 딕셔너리를 주기적으로 스캔하여 사용률 0인 인덱스를 자동 적발해 폐기하고, 다빈도 조회 쿼리는 커버링 인덱스로 묶어 테이블 랜덤 I/O를 원천 차단
