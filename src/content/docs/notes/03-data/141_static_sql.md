## 한 줄 본질
- 런타임에 쿼리가 조합되면 매번 문법 검사와 최적화(하드 파싱)를 거치며 CPU를 소모함 → 개발 시점에 쿼리 골격을 확정하고 실행 계획을 사전 검증하여 재사용 → 최고 수준의 실행 속도와 보안 확보 / 조건식 분기의 유연성 결여

```text
  [동적 SQL: 런타임 조합 및 실행]

```

## 핵심 용어
- 프리컴파일러(Pre-compiler): C/C++ 등의 호스트 언어 소스코드에 삽입된 `EXEC SQL` 구문을 DBMS 전용 런타임 라이브러리 함수 호출 코드로 변환해 주는 전처리기
- 소프트 파싱(Soft Parsing): 이미 과거에 파싱되어 라이브러리 캐시에 저장된 동일 SQL의 실행 계획을 메모리에서 즉시 찾아 재사용함으로써 하드 파싱 부하를 없애는 과정

## 핵심 통찰
- 정적 SQL은 쿼리의 '형태'가 절대 변하지 않으므로 SQL Injection 공격 문자열(`' OR '1'='1`)이 들어와도 단순 데이터 값으로만 취급되어 구조적으로 인젝션이 불가능함
- 정적 SQL 환경에서 다양한 검색 조건을 하나의 쿼리로 처리하려고 `WHERE col = NVL(:input, col)`이나 `col LIKE :input || '%'` 형태로 코딩하면, 옵티마이저가 인덱스를 타지 못하고 풀스캔(FTS)을 때리는 최악의 성능 저하 발생
- 배치 프로그램, 계좌 이체, 주문 등록처럼 트랜잭션 빈도가 높고 쿼리 형태가 일정한 핵심 코어 OLTP 업무는 무조건 정적 SQL(또는 바인드 변수가 완벽히 적용된 쿼리)로 작성해야 함

## 이웃 토픽과 구분
- 정적 SQL vs 동적 SQL: 정적 SQL = 빌드/컴파일 시점에 실행 계획이 결정되어 성능과 보안이 뛰어나나 유연성이 없음 / 동적 SQL = 런타임 사용자 입력에 따라 쿼리 문자열이 가변 조립되어 유연하나 하드 파싱과 보안 위험 수반

## 문제·원인·대책
- 적용 상황: 대규모 금융 차세대 코어뱅킹 이체 배치 프로그램 성능 최적화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 야간 계좌 정산 배치 실행 시 DB CPU 98% 도달 및 라이브러리 캐시 래치 경합 | 루프문 안에서 문자열 결합 기반 동적 SQL을 건당 수백만 번 반복 실행 | PreparedStatement 및 정적 SQL 구조로 전면 전환하고 바인드 변수 적용 | 하드 파싱 0% 달성 및 배치 처리 시간 6시간에서 40분으로 단축 |
| 검색 조건 5개에 대응하기 위해 정적 SQL 1개에 `NVL`을 5개 중첩하여 풀스캔 발생 | 다이나믹 조건을 무리하게 단일 정적 쿼리로 통합하려는 안티패턴 코딩 | Dynamic SQL로 분기 처리하거나 핵심 패턴 4종으로 정적 쿼리 분리(Union All) | 인덱스 레인지 스캔 정상 복원 및 I/O 99% 절감 |

## 내 의견
- [원시 정적 SQL에서 현대 ORM 바인딩으로의 전환] 과거 Pro*C 시절의 정적 SQL 고집에서 벗어나 MyBatis/JPA 환경에서도 정적 SQL의 철학을 계승해야 함 → 나라면: 개발 표준 가이드라인에 JPA JPQL과 QueryDSL 사용 시 동적 문자열 연결(`${}`)을 금지하고 100% 파라미터 바인딩(`#{}`)을 강제하여, 정적 SQL의 캐시 재사용성과 동적 쿼리의 유연성을 동시에 확보

## 찾아볼 것
- DBMS가 SQL 파싱 시 문자열의 공백이나 대소문자 차이까지 완전히 일치해야 소프트 파싱으로 인정하는 라이브러리 캐시 해시(Hash) 매칭 기제
