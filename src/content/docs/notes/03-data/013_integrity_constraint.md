## 답안 골격
```text
[무결성 제약] ◀━━ 머리: Ⅶ 내 의견 (DB 제약조건 전담 지양 → 애플리케이션 유효성 검증과 DB DDL의 2계층 방어선 구축)
 ┃
 ┣━ Ⅰ 개요 ───── 허위·모순 데이터 입력 방지 → 데이터베이스의 정확성·유효성·일관성을 보장하는 규칙
 ┣━ Ⅱ 특징 ───── 선언적 제약(Declarative) · DBMS 자동 강제 · 데이터 생명주기 전반 무결성 유지
 ┣━ Ⅲ 구조 ───── 개체 무결성 / 참조 무결성 / 도메인 무결성 / 사용자 정의 무결성 (4대 제약)
 ┣━ Ⅳ 흐름 ───── ① DML 연산 요청(Insert/Update/Delete) → ② DBMS 제약 조건 검사 → ③ 위반 시 롤백 및 에러 반환
 ┣━ Ⅴ 비교 ───── 4대 무결성 제약 비교 (PK vs FK vs CHECK/NOT NULL vs Trigger)
 ┗━ Ⅵ 실무 ───── FK 폭포수 삭제(CASCADE) 성능 저하 / 분산 DB(샤딩) 환경에서 FK 제약 미지원
```
- 필수 키워드: 개체 무결성(PK) · 참조 무결성(FK) · 도메인 무결성 · 사용자 정의 무결성 · CASCADE · RESTRICT
- 배점 전략: 10점 = Ⅰ → Ⅲ 4대 무결성 정의 및 DDL 매핑 → Ⅵ 한 행 / 25점 = Ⅰ~Ⅶ, 앞 1/3에 Ⅲ 4대 무결성 체계 및 참조 무결성 옵션
- 기출: 135회 `릴레이션 무결성 제약의 유형과 사례, 구현 방법` → Ⅲ 4대 유형 + DDL 구현 / 138회 `정보모델링의 참조 무결성` → 참조 무결성 집중

## 한 줄 본질
- 잘못된 데이터 입력과 고아 레코드(Orphan Record) 발생 방지 → DBMS 엔진 차원에서 튜플 삽입·수정·삭제 시 사전에 선언된 제약 규칙을 검증 → 데이터 신뢰성 담보 / 대량 배치 및 분산 환경에서 쓰기 성능 저하

## 핵심 그림
```text
[관계형 데이터베이스 4대 무결성 제약]

[개체 무결성 (Entity)]           [참조 무결성 (Referential)]
- 기본키(PK)는 NOT NULL & UNIQUE - 외래키(FK)는 부모 테이블의 PK이거나 NULL
- 행의 유일한 식별 보장          - 고아 레코드(Orphan) 발생 방지
       │                                │
       ├────────────────────────────────┤
       │                                │
[도메인 무결성 (Domain)]         [사용자 정의 무결성]
- 정의된 타입, 범위, 기본값 준수 - 업무 규칙(Business Rule) 반영
- CHECK, NOT NULL, DEFAULT      - 트리거(Trigger), 저장 프로시저
```

## 핵심 용어
- 참조 무결성(Referential Integrity): 자식 테이블의 외래키는 반드시 부모 테이블의 기본키로 존재하거나, NULL이어야 한다는 제약
- CASCADE: 부모 테이블의 행이 삭제 또는 수정될 때 이를 참조하는 자식 테이블의 행도 연쇄적으로 삭제되거나 갱신되는 동작 옵션

## 핵심 통찰
- 무결성 제약은 원천에서 지켜질수록 비용이 저렴함 → DBMS의 DDL로 선언해 두면 애플리케이션 버그로 이상 데이터가 유입되더라도 원천 차단
- 그러나 대규모 트래픽 분산 시스템(MSA, 샤딩)에서는 물리적 FK를 맺지 않는 것이 실무 표준 → 테이블이 물리적으로 다른 DB 노드에 흩어져 있으면 외래키 제약 검사가 네트워크 왕복 지연(RTT)과 분산 락을 유발하여 시스템 TPS를 급락시킴
- 참조 무결성 삭제 규칙(RESTRICT, CASCADE, SET NULL)을 명확히 정의하지 않으면 부모 레코드 삭제 시 시스템 에러가 발생하거나 중요 이력 데이터가 영구 유실됨

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 외래키 삭제 옵션 | 참조 무결성 처리 방식 | RESTRICT(삭제 거부), CASCADE(연쇄 삭제), SET NULL(NULL 치환) |
| 고아 레코드(Orphan Record) | 참조 무결성 파괴 결과 | 부모 키가 삭제되었는데 자식 테이블에 잔존하여 부모를 찾을 수 없는 데이터 |

## 이웃 토픽과 구분
- 무결성(Integrity) vs 보안성(Security): 무결성 = 권한 있는 사용자가 실수로 데이터의 일관성을 깨뜨리지 않도록 보호 / 보안성 = 권한 없는 인가되지 않은 접근이나 탈취로부터 보호

## 문제·원인·대책
- 적용 상황: 회원 탈퇴 시 주문 및 결제 내역 처리 (전자상거래 시스템)
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 회원 탈퇴 시 `ON DELETE CASCADE`로 과거 5년 치 결제 이력 동시 삭제 | 전자상거래법 보관 의무(5년) 미고려 물리적 FK 연쇄 삭제 | 물리 FK 해제 후 논리적 소프트 딜리트(`is_deleted='Y'`) 적용 | 법령 준수 및 결제 데이터 보존 |
| 주문 테이블 Insert 시 극심한 락 경합 및 타임아웃 | 주문마다 상품, 쿠폰 테이블의 FK 참조 무결성 검증 락 발생 | 애플리케이션 서비스 레이어에서 사전 검증하고 물리 DB FK 제거 | 트래픽 처리량(TPS) 3배 이상 향상 |

## 내 의견
- [MSA 환경에서의 무결성 착시] 모놀리식 시절의 DB FK 제약만 믿고 MSA 분할 후 데이터 불일치 폭증 → 나라면: 마이크로서비스 간에는 Saga 패턴과 Outbox 패턴을 도입하여 이벤트 기반의 최종 일관성(Eventual Consistency)으로 논리적 무결성을 유지하고, 야간에 비동기 정합성 배치(Reconciliation)를 구동해 누락 데이터를 보정
