## 답안 골격
```text
[데이터 레이크] ◀━━ 머리: Ⅶ 내 의견 (무통제 원천 적재 지양 → Iceberg 기반 레이크하우스 및 데이터 늪 방지 거버넌스)
 ┃
 ┣━ Ⅰ 개요 ───── 정형 위주 DW 한계 → 정형·반정형·비정형 데이터를 원시 형태 그대로 보관하는 대용량 저장소
 ┣━ Ⅱ 특징 ───── Schema-on-Read · 저비용 오브젝트 스토리지 기반 · ELT 파이프라인 · 원천 데이터 보존
 ┣━ Ⅲ 구조 ───── 수집(Ingestion) / 원시 저장(Raw Zone) / 정제(Curated Zone) / 서비스(Analytics Layer)
 ┣━ Ⅳ 흐름 ───── ① 원천 수집 → ② 원시 적재(Raw) → ③ 메타데이터 등록 → ④ 읽기 시점 스키마 매핑(Query)
 ┣━ Ⅴ 비교 ───── 데이터 웨어하우스(DW) vs 데이터 레이크 vs 데이터 레이크하우스
 ┗━ Ⅵ 실무 ───── 메타데이터 부재로 인한 데이터 늪(Data Swamp) 전락 / 보안 및 접근통제 미비
```
- 필수 키워드: Schema-on-Read · 오브젝트 스토리지(S3) · 데이터 늪(Data Swamp) · ELT · Apache Iceberg · 데이터 레이크하우스
- 배점 전략: 10점 = Ⅰ → Ⅲ 계층 구조(Zone) → Ⅵ 한 행 / 25점 = Ⅰ~Ⅶ, 앞 1/3에 Ⅲ Zone 구조도 및 Ⅴ DW/레이크/레이크하우스 비교
- 기출: 139회 `데이터 레이크 기반 통합 데이터 플랫폼` → Ⅲ 아키텍처 + Ⅳ 도입 절차 및 거버넌스 / 137회 `데이터 늪` → Ⅵ 실무 문제 및 극복 방안

## 한 줄 본질
- 사전 정제(Schema-on-Write)의 유연성 부족과 저장 비용 급증 → 모든 형태의 데이터를 원시 그대로 저장하고 분석 시점에 구조를 부여(Schema-on-Read) → 유연한 AI/빅데이터 분석 지원 / 메타데이터 통제 실패 시 데이터 늪으로 전락 위험

## 핵심 그림
```text
[Data Lake Zone 아키텍처]
                       ┌─────────────────────────────────────────┐
                       │            Data Governance              │
                       │     (Metadata / Catalog / Security)     │
                       └─────────────────────────────────────────┘
[데이터 소스]                 │                     │                 │
- RDBMS     ──(ELT 수집)──> [ Raw Zone ] ──> [ Processed ] ──> [ Curated Zone ]
- IoT/로그                   (원시 포맷)       (정제/변환)         (Parquet/비즈니스)
- 비정형(음성/영상)           (JSON, CSV)      (Parquet, ORC)            │
                                                                         ▼
                                                                  [분석 및 AI 모델]
```

## 핵심 용어
- Schema-on-Read: 데이터를 저장할 때 스키마를 강제하지 않고, 분석 도구가 데이터를 읽어 들이는 쿼리 시점에 스키마를 정의하는 방식
- 데이터 늪(Data Swamp): 메타데이터 관리와 거버넌스가 결여되어 어떤 데이터가 어디에 있고 신뢰할 수 있는지 알 수 없게 된 방치된 저장소

## 핵심 통찰
- 저렴한 오브젝트 스토리지(S3, GCS)의 등장이 데이터 레이크를 가능하게 함 → 연산(Compute)과 저장(Storage)의 분리로 필요할 때만 연산 클러스터를 띄워 비용 절감
- 원시 데이터를 보존해야 머신러닝의 재학습이 가능함 → DW처럼 집계·변환해 버리면 원본 신호가 손실되어 새로운 피처 엔지니어링 불가
- 파일 포맷 선정이 성능을 좌우함 → 대규모 분석에서는 행 기반 CSV/JSON 대신 컬럼 기반 압축 포맷인 Parquet나 ORC를 적용해야 I/O가 90% 이상 절감

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 데이터 레이크하우스 | 차세대 발전 모델 | 데이터 레이크의 저비용 저장소 위에 트랜잭션(ACID)과 DW 기능을 얹은 통합 구조 |
| 오픈 테이블 포맷 | 레이크하우스 핵심 기술 | Apache Iceberg, Delta Lake, Apache Hudi 등 파일 레벨 ACID를 보장하는 스키마 레이어 |

## 이웃 토픽과 구분
- 데이터 레이크 vs 데이터 웨어하우스(DW): 레이크 = 원시 비정형 포함 대용량 저장소(Schema-on-Read, ELT) / DW = 정제된 정형 데이터 위주 고성능 SQL 분석 저장소(Schema-on-Write, ETL)

## 문제·원인·대책
- 사례: 137회 출제 키워드 '데이터 늪(Data Swamp)' 발생 조직의 데이터 플랫폼 재구축
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 수십 PB의 데이터가 쌓였으나 분석가가 검색조차 불가 | 카탈로그 등록 없는 무분별한 파일 업로드 | 자동 크롤러(AWS Glue, OpenMetadata) 연동 데이터 카탈로그 필수화 | 검색성 100% 확보 및 데이터 탐색 단축 |
| 동시 쓰기 발생 시 파일 손상 및 부분 읽기 오류 | 분산 파일 시스템 상의 트랜잭션 원자성(ACID) 부재 | Apache Iceberg 등 오픈 테이블 포맷 도입 | 스냅샷 격리 및 ACID 트랜잭션 보장 |

## 내 의견
- [원시 적재 환상과 거버넌스 실패] '일단 다 모아두면 AI가 해결해 준다'는 기대로 수억 원어치 스토리지 낭비 후 데이터 늪 전락 → 나라면: 수집 시점부터 최소한의 스키마 등록과 비즈니스 태깅을 강제하는 'Zone 기반 접근 정책'을 적용하고, Apache Iceberg 기반 레이크하우스 아키텍처로 일원화해 DW와 레이크의 이중 파이프라인 유지비용 제거
