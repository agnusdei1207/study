## 한 줄 본질
- 트랜잭션을 동시에 돌릴 때 발생하는 데이터 덮어쓰기·불일치 현상 → 락·타임스탬프·스냅샷 버전으로 직렬 스케줄과 동등한 결과 보장 → 동시성 처리량 극대화 / 대기 지연 및 교착상태 위험 관리 필요

```text

       ┌───────────────────────────────┐
       │     동시성 제어 기법 분류     │
       └───────────────┬───────────────┘
                       │
 ┌─────────────┬───────┴───────┬─────────────┐
 ▼             ▼               ▼             ▼
[ 2PL 락킹 ]  [ 타임스탬프 ]   [ 낙관적 검증 ] [   MVCC   ]

```

## 핵심 용어
- 2PL(Two-Phase Locking): 트랜잭션이 락을 획득만 하는 확장 단계(Growing)와 락을 해제만 하는 축소 단계(Shrinking)로 나누어 직렬 가능성을 보장하는 규칙
- MVCC(Multi-Version Concurrency Control): 데이터 갱신 시 기존 데이터를 덮어쓰지 않고 언두 로그에 버전을 생성하여, 읽기는 락 없이 스냅샷을 읽고 쓰기는 배타 락을 사용하는 기법

## 핵심 통찰
- 완벽한 직렬 실행은 동시성을 0으로 만듦 → 동시성 제어의 본질은 '동시에 실행하되 마치 차례대로 하나씩 실행한 것(직렬 스케줄)과 결과가 같게 만드는 것'
- 2PL은 직렬성을 보장하지만 교착상태(Deadlock)를 유발함 → 엄격 2PL(Strict 2PL)을 적용해 커밋 시점까지 배타 락을 유지함으로써 연쇄 복구(Cascading Rollback)를 방지
- 최신 DBMS(Oracle, PostgreSQL, MySQL InnoDB)는 대부분 MVCC를 채택 → '읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다'는 원리로 읽기 성능 극대화

## 딸려 나오는 하위 토픽
| 하위 토픽 | 상위 구조 속 위치 | 한 줄 |
|---|---|---|
| 교착상태(Deadlock) | 락 방식의 부작용 | 두 트랜잭션이 서로가 쥔 락을 무한정 대기하는 상태(탐지/예방/회피) |
| 갱신 손실(Lost Update) | 병행 미제어 시 이상현상 | 두 트랜잭션이 동시에 같은 값을 읽고 덮어써 앞선 갱신이 사라지는 현상 |

## 이웃 토픽과 구분
- 동시성 제어 vs 트랜잭션 격리 수준: 격리 수준 = 사용자가 요구하는 일관성의 강도(정책) / 동시성 제어 = 그 격리 수준을 실제로 만족시키기 위해 DBMS 엔진이 돌리는 구현 알고리즘(메커니즘)

## 문제·원인·대책
- 적용 상황: 티켓 예매 및 한정판 선착순 결제 시스템
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 동일 좌석이 두 사용자에게 동시 예매 완료 처리 | 락 없는 단순 SELECT 후 UPDATE로 갱신 손실 발생 | `SELECT ... FOR UPDATE` 비관적 락 또는 버전 번호 기반 낙관적 락 적용 | 이중 결제 및 갱신 손실 100% 방지 |
| 주문 폭주 시 전체 트랜잭션 교착상태로 DB 락 타임아웃 속출 | 테이블 접근 순서가 트랜잭션마다 상이하여 상호 대기 | 자원 접근 순서 표준화 및 Redis 기반 분산 락(Redlock)으로 진입 순차화 | 교착상태 원천 차단 및 안정적 처리 |
