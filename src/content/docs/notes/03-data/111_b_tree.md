## 답안 골격
```text
[B 트리 (B-Tree)] ◀━━ 머리: Ⅶ 내 의견 (디스크 블록 I/O 최적화를 위한 다원 균형 트리와 B+Tree로의 구조 진화)
 ┃
 ┣━ Ⅰ 개요 ───── 보조기억장치의 블록 I/O 횟수를 최소화하기 위해 노드당 다수의 키와 자식 포인터를 갖는 스스로 균형을 잡는 다원 탐색 트리
 ┣━ Ⅱ 특징 ───── 완전 균형(모든 리프 노드의 레벨 동일) · $O(\log N)$ 탐색 보장 · 노드 분할(Split)과 병합(Merge) · 디스크 블록 크기 최적화
 ┣━ Ⅲ 구조 ───── 차수($M$) / 키($K$)와 데이터 레코드 포인터($P_D$) / 자식 노드 포인터($P_C$) / 루트-내부-리프 노드
 ┣━ Ⅳ 흐름 ───── ① 루트부터 키 비교 → ② 자식 포인터 추적(하향 탐색) → ③ 노드 포화 시 분할(중간값 승격) → ④ 언더플로우 시 재분배 또는 병합
 ┣━ Ⅴ 비교 ───── B-Tree vs Binary Search Tree vs B+Tree
 ┗━ Ⅵ 실무 ───── 빈번한 삽입·삭제로 인한 노드 분할 오버헤드 / 범위 검색(Range Scan) 시 순차 I/O 비효율
```
- 필수 키워드: B-Tree · 다원 균형 트리 · 노드 분할(Split) · 노드 병합(Merge) · 블록 I/O 최소화 · $O(\log N)$ · B+Tree · 균형 트리
- 배점 전략: 10점 = Ⅰ → Ⅲ B-Tree 노드 구조 및 차수 M의 성질 → Ⅴ BST 및 B+Tree 비교 / 25점 = Ⅰ~Ⅶ, Ⅳ 노드 분할/병합 알고리즘 및 Ⅵ 디스크 I/O 최적화 관점
- 기출: 105회 `B-Tree의 개념과 특징, 삽입 및 삭제 연산 과정` → Ⅰ 정의 + Ⅱ 핵심 성질 + Ⅳ 분할/병합 연산 흐름 + Ⅴ B+Tree 비교

## 한 줄 본질
- 이진 탐색 트리는 트리의 높이가 깊어져 디스크 읽기 횟수가 과다해짐 → 한 노드에 여러 키와 포인터를 담아 디스크 1블록에 매핑하고 트리의 높이를 극단적으로 낮춤 → 디스크 I/O 대폭 감소 / 노드 분할·병합 시 추가 연산 발생

## 핵심 그림
```text

  [노드 내부 구조]
  ┌──────────┬────────┬──────────┬────────┬──────────┐
  │ 자식 P0  │  Key 1 │ 자식 P1  │  Key 2 │ 자식 P2  │
  └──────────┴────────┴──────────┴────────┴──────────┘
                  │                   │
                  ▼ 데이터 레코드     ▼ 데이터 레코드

  [탐색 흐름: Key 25 검색]
                    ┌──────────────────┐
                    │  [ 20  |  50 ]   │  (루트 노드)
                    └─┬──────┼───────┬─┘
         Key < 20     │      │       │     Key > 50
        ┌─────────────┘      │       └─────────────┐
        ▼                    ▼ 20 <= Key < 50      ▼
  ┌───────────┐        ┌───────────┐         ┌───────────┐
  │ [ 5 | 10] │        │ [ 25 | 35]│         │ [ 60 | 80]│ (리프 노드)
  └───────────┘        └─────┬─────┘         └───────────┘

```

## 핵심 용어
- 차수($M$): 하나의 노드가 가질 수 있는 최대 자식 노드의 수 (차수 $M$인 B-Tree의 각 노드는 최대 $M-1$개의 키를 가짐)
- 노드 분할(Split): 삽입으로 인해 한 노드의 키 개수가 $M$개가 될 때, 중간값(Median) 키를 부모 노드로 승격시키고 노드를 둘로 쪼개는 연산

## 핵심 통찰
- B-Tree의 본질은 '디스크 하드웨어의 블록 I/O 특성에 소프트웨어 자료구조를 맞춘 것'임 → 메모리와 달리 디스크는 1바이트를 읽든 4KB를 읽든 1블록 단위로 가져오므로, 노드 1개의 크기를 디스크 블록(4KB~16KB)과 1:1로 일치시킴
- 모든 리프 노드가 항상 완전히 동일한 깊이에 위치(Balanced)하므로 최악의 경우에도 탐색 시간복잡도가 $O(\log N)$으로 완벽히 보장됨
- 하지만 B-Tree는 내부 노드에도 데이터 레코드 포인터를 보관하므로, 한 블록에 담을 수 있는 키의 개수가 적어지고 범위 스캔(Range Scan) 시 트리를 위아래로 오르내려야 하는 한계가 존재

## 이웃 토픽과 구분
- B-Tree vs B+Tree: B-Tree = 모든 노드(루트, 내부, 리프)에 데이터 포인터가 분산 저장됨 / B+Tree = 내부 노드에는 오직 인덱스 키만 두고, 모든 실제 데이터는 리프 노드에만 모으며 리프끼리 양방향 연결 리스트로 이어 범위 검색 최적화

## 문제·원인·대책
- 적용 상황: 대규모 트랜잭션 RDBMS의 인덱스 구조 최적화
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 대량 순차 INSERT 발생 시 B-Tree 우측 노드 분할(Split) 폭증으로 디스크 쓰기 병목 | 정렬된 시퀀스 키 입력으로 한쪽 노드만 채워져 불균형 분할 유발 | B-Tree 인덱스를 해시 파티셔닝하거나 역인덱스(Reverse Key Index) 적용 | 노드 분할 경합 분산 및 쓰기 I/O 50% 절감 |
| 기간별 매출 조회(`WHERE date BETWEEN A AND B`) 시 잦은 트리 순회로 속도 저하 | B-Tree 구조상 형제 노드 간 직접 연결이 없어 부모 노드를 재방문 | 리프 노드가 연결 리스트로 이어진 B+Tree 인덱스 구조 채택 | 순차 리프 스캔으로 디스크 랜덤 I/O를 순차 I/O로 전환 |

## 이렇게 출제된다
- 제105회: "데이터베이스 인덱스에 사용되는 B-Tree의 개념과 특징을 설명하고, 차수가 3인 B-Tree에서의 삽입 및 삭제 연산 과정을 단계별로 도식화하시오." → 요구 포인트: B-Tree 정의 및 차수($M$) 성질 + 노드 분할(Split)/병합(Merge) 절차도 + B+Tree와의 차이점

## 내 의견
- [B-Tree 계열 인덱스의 특성 기반 설계] 개발자들이 모든 컬럼에 무분별하게 B-Tree 인덱스를 생성하여 CUD 작업 시 인덱스 유지관리 부하로 전체 DB 성능을 갉아먹는 사례 다수 → 나라면: 카디널리티가 높은 단일/복합 조회 컬럼에만 선택적으로 B-Tree 인덱스를 설계하고, 주기적인 인덱스 단편화율(Fragmentation) 모니터링을 통해 리빌드(Rebuild) 배치를 자동화
