## 답안 골격
```text
[비식별관계 (Non-Identifying Relationship)] ◀━━ 머리: Ⅶ 내 의견 (약한 종속성 중심의 비식별 관계 표준화와 단일 대리키 채택)
 ┃
 ┣━ Ⅰ 개요 ───── 부모 엔티티의 기본키(PK)가 자식 엔티티의 기본키에 포함되지 않고 일반 외래키(FK) 속성으로만 상속되는 느슨한 엔티티 간 관계
 ┣━ Ⅱ 특징 ───── 자식의 독립적 생존 가능 · ERD 상 점선(Dashed Line) 표기 · PK 컬럼 수 증가 억제 · 테이블 간 낮은 결합도
 ┣━ Ⅲ 구조 ───── 필수적 비식별(Mandatory: FK NOT NULL) / 선택적 비식별(Optional: FK NULL 허용) / 대리키(Surrogate Key) 구조
 ┣━ Ⅳ 흐름 ───── ① 엔티티 간 업무 종속성 식별 → ② 부모 없이 자식 독립 존재 가능 여부 판단 → ③ 비식별 관계 채택(점선 연결) → ④ 자식에 독립적 단일 PK 부여
 ┣━ Ⅴ 비교 ───── 식별관계(Identifying) vs 비식별관계(Non-Identifying)
 ┗━ Ⅵ 실무 ───── 식별관계 남용 시 5단계 하위 자식의 복합 PK 폭증 / 비식별관계 과다 시 조인 연산 증가로 인한 성능 저하
```
- 필수 키워드: 비식별관계 · 식별관계 · 외래키(FK) · 주식별자 상속 · 점선 표기 · 약한 종속성 · 대리키(Surrogate Key)
- 배점 전략: 10점 = Ⅰ → Ⅲ ERD 표기 및 필수/선택 비식별 구조도 → Ⅴ 식별 vs 비식별 비교표 / 25점 = Ⅰ~Ⅶ, Ⅳ 모델링 선택 기준 의사결정 트리 및 Ⅵ 복합키 폭증 해소 사례
- 기출: 133회 4교시 4번 `RDBMS를 적용하기 위한 데이터 모델링에서 식별관계와 비식별관계` → Ⅰ 정의 + Ⅲ 구조 + Ⅴ 상세 비교 + Ⅵ 설계 가이드라인

## 한 줄 본질
- 자식 테이블이 부모의 복합 기본키를 무한정 상속받아 SQL 복잡도와 인덱스 크기가 폭증하는 문제 방지 → 부모의 PK를 자식의 일반 속성(FK)으로만 내려 독립성을 보장 → 스키마 변경 유연성 확보 / 부모 조인 쿼리 발생

## 핵심 그림
```text
[식별관계 vs 비식별관계 ERD 구조 비교]

  [1. 식별관계 (Identifying: 실선)]       [2. 비식별관계 (Non-Identifying: 점선)]
   부모 PK가 자식 PK로 상속                 부모 PK가 자식의 일반 속성으로 상속

   ┌───────────────┐                       ┌───────────────┐
   │    부모       │                       │    부모       │
   ├───────────────┤                       ├───────────────┤
   │ PK 부모ID     │                       │ PK 부모ID     │
   └───────┬───────┘                       └───────┬───────┘
           │ ━━━ (실선)                            ┆ - - - (점선)
   ┌───────▼───────┐                       ┌───────▼───────┐
   │    자식       │                       │    자식       │
   ├───────────────┤                       ├───────────────┤
   │ PK,FK 부모ID  │ ◄── PK 포함           │ PK 자식ID     │ ◄── 독립 PK
   │ PK    자식순번│                       ├───────────────┤
   └───────────────┘                       │ FK 부모ID     │ ◄── 일반 속성
                                           └───────────────┘
```

## 핵심 용어
- 대리키(Surrogate Key): 비즈니스 의미가 없는 순번(Auto-increment)이나 UUID를 인위적으로 생성하여 테이블의 기본키로 사용하는 키
- 강한 개체/약한 개체: 부모 없이 독립적으로 존재할 수 있는 개체를 강한 개체, 부모의 존재에 종속되어 생성되는 개체를 약한 개체라 함

## 핵심 통찰
- 실무에서 식별관계를 3단계 이상 타고 내려가면 재앙이 시작됨 → 4차, 5차 자식 테이블은 PK 컬럼만 5개가 넘어가 인덱스 블록이 비대해지고 쿼리마다 모든 조인 조건을 달아야 함
- 현대의 마이크로서비스(MSA) 환경에서는 테이블 간의 결합도를 최소화해야 하므로, 거의 모든 관계를 비식별 관계로 설계하고 독립된 대리키(Surrogate Key)를 주는 것이 글로벌 표준 패턴임
- 단, 부모와 생애주기가 완벽히 100% 일치하는 '주문'과 '주문상세' 같은 1:N 마스터-디테일 관계는 식별관계로 묶어야 참조 정합성과 데이터 무결성을 쉽게 보장할 수 있음

## 이웃 토픽과 구분
- 비식별관계 vs 식별관계: 비식별 = 부모의 PK가 자식의 일반 속성(FK)으로 전이(자식의 독립적 생명주기) / 식별 = 부모의 PK가 자식의 복합 PK 일부로 전이(부모 없이는 자식이 존재 불가)

## 문제·원인·대책
- 적용 상황: 대규모 통합 빌링 및 정산 시스템의 데이터베이스 리모델링
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 하위 이력 테이블들의 PK 컬럼이 7개까지 누적되어 인덱스 저장 공간 낭비 및 조인 복잡도 한도 초과 | 모든 연관관계를 관행적으로 식별관계로 모델링 | 부모 관계를 비식별관계(점선)로 전환하고 단일 정수형 대리키 도입 | 인덱스 스토리지 60% 절감 및 조인 쿼리 라인 수 70% 축소 |
| 비식별관계 자식 테이블에 부모 ID가 NULL로 잘못 들어가 데이터 고아화 | 선택적 비식별 관계에서 FK 속성에 NOT NULL 제약조건 누락 | 비즈니스상 부모가 필수인 경우 필수적 비식별(NOT NULL) 제약 강제 | 고아 레코드 원천 차단 |

## 이렇게 출제된다
- 제133회 4교시 4번: "RDBMS를 적용하기 위한 데이터 모델링에 대하여 다음을 설명하시오. (식별관계와 비식별관계의 개념, 특징, 모델링 시 고려사항)" → 요구 포인트: 식별/비식별의 정의 및 ERD 표기법 + 데이터 정합성과 성능 관점의 비교 + 대리키 활용 설계 지침

## 내 의견
- [기계적 식별관계 설계 관행 타파] 교과서적 정규화에 집착하여 모든 종속 관계를 식별관계로 묶어 복합키 지옥을 만드는 레거시 모델러들의 관행 존재 → 나라면: 부모와 1:1이거나 100% 종속적인 디테일 엔티티 외에는 기본적으로 전면 '필수적 비식별관계'로 설계하고, 단일 컬럼 대리키(UUID v7)를 PK로 표준화하여 미래 마이크로서비스 DB 분할에 유연한 구조를 사전 확보
