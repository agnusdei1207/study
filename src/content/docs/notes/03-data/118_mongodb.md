## 한 줄 본질
- 빈번한 스키마 변경과 복잡한 1:N 조인 연산으로 RDBMS 성능 저하 발생 → 데이터를 BSON 형태의 독립된 문서 하나에 중첩(Embed) 저장하고 샤딩으로 분산 → 초고속 읽기/쓰기 및 개발 생산성 확보 / 다중 문서 ACID 트랜잭션 오버헤드

## 핵심 용어
- BSON(Binary JSON): JSON 포맷의 사람이 읽기 쉬운 텍스트 형태를 바이너리로 직렬화하여 파싱 속도를 높이고 Date, Binary 등 다양한 데이터 타입을 확장 지원하는 포맷
- 임베딩(Embedding) vs 참조(Referencing): 하위 엔티티를 부모 문서 내의 배열/객체로 통째로 품는 모델링(임베딩: 1회 읽기 최적) vs RDBMS의 FK처럼 ObjectId만 저장하고 조회 시 `$lookup`으로 엮는 모델링(참조: 정규화)

## 핵심 통찰
- MongoDB 모델링의 제1원칙은 'RDBMS식 정규화를 버리는 것'임 → 데이터를 함께 화면에 뿌려야 한다면 1:N 관계라도 부모 문서 안에 통째로 중첩(Embedding)하는 것이 조인을 없애는 최선의 패턴
- 하지만 단일 문서의 최대 크기는 16MB로 하드웨어적 제한이 걸려 있음 → 게시글에 댓글이 수만 개 달리는 구조에서 댓글을 모조리 임베딩하면 16MB 한도를 넘어 쓰기 에러가 터지므로 이때는 '참조(Referencing)' 패턴으로 전환
- 샤드 키(Shard Key)를 잘못 고르면(예: 날짜처럼 단조 증가하는 값), 오늘 발생하는 모든 데이터가 오직 1개 샤드로만 몰리는 핫스팟(Hotspot)이 발생하여 클러스터 전체가 마비됨

## 이웃 토픽과 구분
- MongoDB vs RDBMS: MongoDB = 스키마가 자유롭고 수평 샤딩이 기본 내장되어 대규모 트래픽 분산에 유리 / RDBMS = 엄격한 정규화 스키마와 완벽한 외래키 무결성, 복합 테이블 조인 연산에 최적화

## 문제·원인·대책
- 적용 상황: 대규모 모바일 게임의 사용자 프로필 및 인벤토리 데이터 저장소
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 사용자 인벤토리 아이템 수가 1만 개를 초과하면서 프로필 저장 시 16MB 에러 발생 | 모든 아이템 정보를 단일 사용자 문서 내에 무제한 임베딩 | 상위 요약 정보만 임베딩하고 상세 아이템은 별도 컬렉션으로 분리 후 참조 방식 전환 | 16MB 제한 회피 및 프로필 조회 지연 80% 개선 |
| 특정 샤드 노드의 디스크 사용량만 95%에 도달하며 쓰기 병목 발생 | 샤드 키를 카디널리티가 낮은 '지역코드'로 설정하여 청크 쏠림 유발 | 해시 기반 샤드 키(Hashed Shard Key) 도입으로 데이터 물리적 균등 분산 | 전체 샤드 간 트래픽 균등 분산 달성 |

## 내 의견
- [RDBMS처럼 MongoDB를 쓰는 안티패턴 근절] 개발팀이 MongoDB를 도입해 놓고 모든 테이블을 쪼개어 `$lookup`(조인)을 수십 번 날려 시스템을 마비시키는 사례 다수 → 나라면: MongoDB를 도입할 때는 '함께 읽히는 데이터는 함께 저장한다'는 비정규화 원칙을 아키텍처 가이드로 배포하고, 다중 문서 원자적 트랜잭션이 과도하게 필요한 금융 결제 도메인은 PostgreSQL 같은 정통 RDBMS로 분리하는 적재적소(Polyglot Persistence) 전략 채택
