## 답안 골격
```text
[Go-Back-N ARQ] ◀━━ 머리: Ⅶ 내 의견 (저오류 링크에서의 단순성 활용 및 오류 링크의 SACK 전환)
 ┃
 ┣━ Ⅰ 개요 ───── Stop-and-Wait 한계 극복 및 수신 버퍼 복잡도 배제를 위한 연속 전송 ARQ
 ┣━ Ⅱ 특징 ───── 송신 윈도우 $N$, 수신 윈도우 1, 누적 ACK(Cumulative), 오류 시 일괄 재전송
 ┣━ Ⅲ 구조 ───── 송신 버퍼(크기 $N$) + 송신 타이머 + 수신측(오직 다음 기대 번호 1개만 수용)
 ┣━ Ⅳ 흐름 ───── ① 0~N-1 프레임 연속 송신 → ② 중간 오류 발생 시 수신측 폐기 → ③ 타임아웃 만료 시 N개 일괄 재전송
 ┣━ Ⅴ 비교 ───── Go-Back-N vs Selective Repeat (수신 윈도우 1 vs N, 정상 프레임 폐기 vs 버퍼링)
 ┗━ Ⅵ 실무 ───── 고오류율 환경 대역폭 낭비 / 윈도우 크기 조건($N \le 2^m - 1$) 미준수 시 오동작
```
- 필수 키워드: 슬라이딩 윈도우 · 수신 윈도우 1 · 누적 ACK · 타임아웃 · 일괄 재전송 · $2^m - 1$
- 배점 전략: 10점 = Ⅰ → Ⅲ 오류 발생 및 되돌아가기(Go-Back) 타이밍도 → Ⅴ SR 비교표 / 25점 = Ⅰ~Ⅶ, 138회 4교시 4번 기출 수식 및 윈도우 크기 한계 증명 상세

## 한 줄 본질
- 수신측에 재정렬 버퍼를 둘 수 없는 저사양 장비 환경에서 연속 전송을 구현하기 위한 기법 → 오류가 난 프레임 번호로 송신 윈도우를 통째로 되돌려 그 이후에 보낸 정상 프레임까지 모두 다시 전송 → 수신측 메모리 요구량 제로(1개 프레임 공간) / 단 1개의 패킷 유실에도 $N$개의 프레임이 중복 재전송되는 회선 낭비

## 핵심 그림
```text
[ Go-Back-N ARQ 오류 발생 및 재전송 시나리오 ]

송신측 (윈도우 크기 N = 4):
  [Frame 0] ------------------------------------> 수신 정상 (ACK 1 회신)
  [Frame 1] --------------------X (전송 중 손실!)
  [Frame 2] ------------------------------------> 수신측 폐기! (1번이 안 왔으므로 버림)
  [Frame 3] ------------------------------------> 수신측 폐기! (1번이 안 왔으므로 버림)
      |
  [타임아웃 발생! (Frame 1의 타이머 만료)]
      v
  오류가 난 1번 시점으로 돌아가서(Go-Back-1) 윈도우 내 전송 재수행!
  [Frame 1] ------------------------------------> 수신 정상 (ACK 2 회신)
  [Frame 2] ------------------------------------> 수신 정상 (ACK 3 회신)
  [Frame 3] ------------------------------------> 수신 정상 (ACK 4 회신)
```

## 핵심 용어
- 수신 윈도우 크기 ($W_r = 1$): 수신측은 오직 바로 다음으로 기대하는 시퀀스 번호의 프레임 하나만 수용하며, 순서가 어긋난 프레임은 버퍼링하지 않고 즉시 드롭
- 윈도우 크기 상한 ($N \le 2^m - 1$): $m$비트 시퀀스 번호를 사용할 때, 송신 윈도우 크기가 $2^m$이면 모든 ACK가 유실되었을 때 새 윈도우와 이전 윈도우를 구분하지 못하므로 반드시 $2^m - 1$ 이하여야 함
- 파이프라인 이용률 ($U$): 오류가 없을 때 이용률은 $U = N / (1 + 2a)$ (단, $a = \text{전파 지연} / \text{전송 시간}$)

## 핵심 통찰
- Go-Back-N의 최대 강점은 "수신측 구현의 극단적 단순성"임 → 순서 정렬(Reordering) 큐나 타이머가 수신측에 전혀 필요 없음
- 그러나 오류 발생 확률($p$)이 높아지면 이용률이 $U = \frac{1 - p}{1 + (N-1)p}$ 수준으로 급격히 저하되어, 긴 윈도우를 쓴 이득이 완전히 상쇄됨
- 전통적인 TCP의 기본 동작 모델이 Go-Back-N에 기반하였으나, 현대 TCP는 SACK(Selective ACK) 옵션을 통해 손실된 세그먼트만 핀포인트로 재전송하는 하이브리드 방식으로 발전

## 이웃 토픽과 구분
- Go-Back-N vs Selective Repeat: Go-Back-N은 오류 이후 패킷을 무조건 버리고 통째로 다시 받음($W_r = 1$) / Selective Repeat는 정상 도착한 패킷을 버퍼에 모아두고 오류 패킷만 골라서 다시 받음($W_r = N$)

## 문제·원인·대책
- 적용 상황: 패킷 손실이 발생하는 무선 센서 네트워크(WSN)
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 1개 패킷 오류 시 배터리 전력 소모 급증 | Go-Back-N의 불필요한 후속 정상 패킷 다중 재전송 | 채널 상태에 따라 송신 윈도우 $N$을 동적 축소하거나 Selective Repeat 적용 | 재전송 프레임 수를 최소화하여 센서 노드 배터리 보존 |
| ACK 유실 시 이전 프레임과 새 프레임 수신 혼동 | 시퀀스 번호 비트 수 대비 윈도우 크기를 $2^m$으로 과도하게 설정 | 윈도우 크기를 $2^m - 1$ 이하로 엄격히 제한 ($m=3$이면 $N \le 7$) | 시퀀스 번호 중복 해석 방지 및 프로토콜 정상 작동 |

## 내 의견
- [단순 IoT 환경에서의 Go-Back-N의 효용성 재평가] 자원이 극도로 제한된 마이크로컨트롤러(MCU) 센서 노드에 복잡한 Selective Repeat 버퍼 스택을 올리면 메모리 오버플로 발생 → 나라면: MCU 메모리가 16KB 이하인 극단적 엣지 환경에서는 Go-Back-N을 채택하여 코드 풋프린트를 최소화하고, 게이트웨이 이상 상위 구간에서만 Selective Repeat로 전환하는 이원화 정책 적용
