## 답안 골격
```text
[TCP 혼잡제어] ◀━━ 머리: Ⅶ 내 의견 (버퍼블로트 극복을 위한 손실 기반에서 BBR 지연 기반으로 전환)
 ┃
 ┣━ Ⅰ 개요 ───── 라우터 큐 포화 및 패킷 손실 악순환 → 송신측 cwnd 동적 조절
 ┣━ Ⅱ 특징 ───── 분산 협력 제어, AIMD(가산 증가 승수 감소), 엔드-투-엔드 감지
 ┣━ Ⅲ 구조 ───── 4대 핵심 단계: Slow Start + Congestion Avoidance + Fast Retransmit + Fast Recovery
 ┣━ Ⅳ 흐름 ───── ① 지수 증가(Slow Start) → ② ssthresh 도달 시 선형 증가 → ③ 3 Dup ACK 시 cwnd 절반
 ┣━ Ⅴ 비교 ───── Reno vs CUBIC vs BBR (손실 기반 선형/3차 곡선 vs RTT·대역폭 모델 기반)
 ┗━ Ⅵ 실무 ───── 고대역 장거리(LFN) 파이프 미충족 / 버퍼블로트(Bufferbloat) / 무선 무작위 손실 오인
```
- 필수 키워드: cwnd(혼잡 윈도우) · ssthresh(임계값) · Slow Start · 혼잡 회피 · Fast Retransmit · Fast Recovery · BBR
- 배점 전략: 10점 = Ⅰ → Ⅲ 4단계 상태 전이 그래프 → Ⅴ Reno vs BBR 비교 / 25점 = Ⅰ~Ⅶ, Tahoe·Reno 그래프 대조 및 BBR 메커니즘 상세
- 기출: 130회 `TCP 혼잡제어 4단계 및 알고리즘 비교` → Ⅲ·Ⅳ·Ⅴ, 137회 `통신 프로토콜 신뢰성 기제` → Ⅰ~Ⅵ

## 한 줄 본질
- 망 내부 라우터 큐 포화로 인한 패킷 폐기 및 재전송 폭풍(혼잡 붕괴) → 송신측이 패킷 손실이나 RTT 증가를 감지해 혼잡 윈도우(cwnd) 크기를 동적으로 축소·확장 → 네트워크 공평 이용과 전송 안정성 확보 / 패킷 손실 발생 시 윈도우를 급감시켜 고속 대역폭 활용률 저하

## 핵심 그림
```text
혼잡 윈도우 (cwnd) 크기 변화 곡선:

cwnd ^
     |                                 (혼잡 회피: 매 RTT마다 1 MSS 증가)
     |                     ssthresh -> +-------+
     |                                /         \  3 Dup ACK 발생! (빠른 재전송)
     |                               /           +----+ (Fast Recovery: 절반에서 회피)
     |                              /                  \
     |                             /                    \
     |           (지수적 증가)    /                      \
     |                 +--------+                         \  타임아웃(RTO) 발생 시:
     |                /                                    \ cwnd = 1 MSS 급락!
     |        +------+                                      +---+
     |   +---+                                                  +-->
     +---+--------------------------------------------------------> 시간 (RTT)
         Slow Start 단계         혼잡 회피 단계
```

## 핵심 용어
- cwnd(Congestion Window): 네트워크가 수용할 수 있는 최대 미확인 패킷 양을 송신측이 자체 추정하여 제한하는 동적 윈도우 크기
- ssthresh(Slow Start Threshold): 지수적으로 증가하는 Slow Start 모드에서 선형으로 증가하는 혼잡 회피 모드로 전환하는 임계값
- BBR(Bottleneck Bandwidth and RTT): 패킷 손실이 아니라 네트워크 병목 대역폭(BtlBw)과 최소 왕복 시간(RTprop)을 직접 측정해 큐를 비우면서 최대 속도를 내는 구글 개발 알고리즘

## 핵심 통찰
- 전통적 손실 기반 알고리즘(Tahoe, Reno, CUBIC)은 라우터 버퍼가 꽉 차서 넘쳐 흘러야(Drop)만 비로소 속도를 줄임 → 라우터 버퍼가 비대해진 현대 인터넷에서 극심한 큐잉 지연(Bufferbloat) 유발
- 무선망(Wi-Fi, 5G)에서는 채널 잡음으로 인한 일반 비트 오류 손실이 잦으나, TCP는 이를 망 혼잡으로 오판하여 cwnd를 반토막 내는 구조적 맹점 존재
- 지연 기반/모델 기반인 BBR은 라우터 버퍼에 패킷이 쌓이기 직전 지점을 찾아 전송률을 조절하므로 버퍼블로트와 패킷 드롭을 동시 차단

## 이웃 토픽과 구분
- 혼잡제어 vs 흐름제어: 혼잡제어는 네트워크 망 전체(라우터 큐)의 병목을 막기 위해 송신률을 제한 / 흐름제어는 수신측 단말의 버퍼 오버플로를 막기 위해 rwnd로 제한

## 문제·원인·대책
- 적용 상황: 대규모 클라우드 간 데이터 복제 시 전송 속도 급감
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 10Gbps 고대역 장거리(LFN) 회선 대역폭 미소진 | Reno 알고리즘의 선형 윈도우 회복 속도가 느림 | CUBIC 또는 BBR v2 혼잡제어 알고리즘 교체 | 손실 후 3차 함수 기반 고속 윈도우 복구로 대역폭 포화 달성 |
| 네트워크 장비 버퍼 비대화로 인한 핑(Ping) 튐 현상 | 손실 기반 알고리즘의 버퍼 가득 채우기 동작(Bufferbloat) | CoDel / FQ-CoDel(공평 큐잉 능동 큐 관리) 적용 | 라우터 내부 체류 시간을 제어하여 초저지연 패킷 포워딩 |

## 이렇게 출제된다

## 내 의견
- [서버 커널 파라미터 기본값(CUBIC) 방치로 인한 성능 저하] 대다수 리눅스 배포판 기본 TCP 알고리즘이 CUBIC으로 설정되어 있어 무선 유입 트래픽이나 글로벌 CDN 구간에서 병목 발생 → 나라면: sysctl 설정을 통해 TCP 혼잡제어를 BBR v2/v3로 전환하고 ECN(Explicit Congestion Notification) 협상을 활성화하여, 버퍼 대기 지연을 30% 이상 축소하고 처리량을 극대화
