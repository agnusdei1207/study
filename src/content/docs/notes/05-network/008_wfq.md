## 답안 골격
```text
[WFQ] ◀━━ 머리: Ⅶ 내 의견 (하드웨어 오프로딩 기반 DWRR 채택으로 고속 링크 WFQ 한계 극복)
 ┃
 ┣━ Ⅰ 개요 ───── FIFO의 큐 독점·기아(Starvation) 현상 → 플로우별 가중 공평 스케줄링
 ┣━ Ⅱ 특징 ───── 플로우 격리, 대역폭 차등 보장, 패킷 크기 무관 공평성, 기아 방지
 ┣━ Ⅲ 구조 ───── 플로우 분류기 + 개별 가상 큐(Per-flow Queue) + 가상 완료 시간 계산기 + 스케줄러
 ┣━ Ⅳ 흐름 ───── ① 5-Tuple 플로우 분류 → ② 패킷별 가상 시간($F_i$) 계산 → ③ 가장 작은 $F_i$ 순 전송
 ┣━ Ⅴ 비교 ───── FIFO vs PQ vs CQ vs WFQ (단순성 vs 절대 우선 vs 고정 바이트 vs 가중 공평)
 ┗━ Ⅵ 실무 ───── 고속 100G 인터페이스에서 가상 시간 정렬 연산 부하 / 버퍼 할당 복잡성
```
- 필수 키워드: 가상 완료 시간(Finish Time) · GPS(Generalized Processor Sharing) · 5-Tuple 플로우 · 가중치(Weight) · DWRR(Deficit Weighted Round Robin)
- 배점 전략: 10점 = Ⅰ → Ⅲ 아키텍처 도식 → Ⅴ FIFO vs WFQ 비교표 / 25점 = Ⅰ~Ⅶ, 140회 2교시 5번 기출에 맞춰 FIFO 한계와 WFQ 수학적 계산식 상세 서술
- 기출: 125회 `QoS 큐잉 기법 비교(FIFO, PQ, CQ, WFQ)` → Ⅲ·Ⅴ, 140회 2교시 5번 `FIFO 방식과 WFQ 방식 비교` → Ⅰ~Ⅵ

## 한 줄 본질
- 단순 FIFO 방식에서 대용량 UDP/벌크 트래픽이 라우터 큐를 독점하여 소용량 실시간 패킷이 폐기되는 문제 → 플로우별 독립 큐를 두고 패킷 크기와 가중치 기반 가상 완료 시간을 계산해 순차 전송 → 트래픽 간 완벽한 격리와 대역폭 보장 / 매 패킷마다 가상 시간을 계산하고 정렬해야 하는 스케줄러 연산 복잡도 발생

## 핵심 그림
```text
트래픽 유입 (혼합 플로우)
 ===> [ 플로우 분류기 (5-Tuple) ]
             |
             +---> [ 큐 1: 음성/VoIP (가중치 w=4) ] ---> [ 가상 시간 계산기 ]
             |                                                |
             +---> [ 큐 2: 비디오    (가중치 w=2) ] ---> (패킷 크기 / 가중치 반영)
             |                                                |
             +---> [ 큐 3: 웹/FTP    (가중치 w=1) ] --->      v
                                                     [ 최소 F_i 선택 스케줄러 ]
                                                              |
                                                              v
                                                     [ 단일 출력 링크 전송 ]
```

## 핵심 용어
- GPS(Generalized Processor Sharing): 이론적으로 무한히 작은 비트 단위로 여러 플로우를 가중치 비율대로 동시 서비스하는 이상적 유체 흐름 모델
- 가상 완료 시간(Virtual Finish Time, $F_i$): 비트 단위가 아닌 패킷 단위 전송 환경에서 해당 패킷의 전송이 가상적으로 끝나는 시점을 계산한 지표 ($F_k = \max(F_{k-1}, V(t)) + L_k / w_i$)
- DWRR(Deficit Weighted Round Robin): WFQ의 복잡한 가상 시간 정렬 연산($O(\log N)$)을 없애고 적자 계수(Deficit Counter)를 이용해 $O(1)$로 가중 공평 전송을 구현한 현실적 대안

## 핵심 통찰
- FIFO는 구현이 극도로 단순하나, 공격자나 악성 트래픽이 회선을 가득 채우면 정상 업무 트래픽까지 전부 드롭되는 근본적 취약점 노출
- 우선순위 큐(PQ)는 상위 큐에 패킷이 있으면 하위 큐를 절대 서비스하지 않아 하위 큐의 기아(Starvation)를 유발하지만, WFQ는 가중치가 낮더라도 반드시 일정 비율의 출력을 보장
- 10Gbps 이상의 고속 스위치에서는 수백만 개 플로우의 가상 완료 시간 정렬을 소프트웨어로 수행 불가능 → 코어 스위치는 단순화된 DWRR이나 SP+WRED 방식을 혼용

## 이웃 토픽과 구분
- WFQ vs WRR: WRR(Weighted Round Robin)은 패킷 개수 기준으로 회전하여 큰 패킷을 보내는 플로우가 대역폭을 부당 독점 / WFQ는 패킷 바이트 길이를 고려하여 정확한 대역폭 비율을 보장

## 문제·원인·대책
- 적용 상황: 기업 백본 라우터에서 대용량 파일 백업 시 화상회의 끊김
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 화상회의 음성 패킷 지연 및 지터(Jitter) 급증 | 백업 트래픽의 대형 패킷(1500바이트)이 FIFO 큐 독점 | 음성 플로우 분리 및 WFQ 기반 높은 가중치(High Weight) 할당 | 백업 트래픽 대역폭을 제한하고 음성 패킷 우선 서비스 |
| 고속 코어 라우터의 패킷 포워딩 지연 발생 | 플로우 수 증가에 따른 WFQ 정렬 연산 오버헤드 | DWRR(Deficit Weighted Round Robin) 하드웨어 ASIC 큐잉 전환 | $O(1)$ 시간 복잡도로 100Gbps 와이어스피드 공평 스케줄링 |

## 내 의견
- [코어망의 과도한 세분화 플로우 관리 비효율] 라우터가 수천 개의 세부 TCP 세션을 일일이 WFQ로 추적하면 메모리와 CPU가 고갈 → 나라면: 엣지 라우터에서 패킷을 4~8개의 CoS/DSCP 클래스로 묶는 DiffServ 모델을 적용하고, 코어 라우터 내부에서는 클래스 단위로만 가중치를 부여하는 CBWFQ(Class-Based WFQ)를 도입하여 확장성과 제어 정밀도를 양립
