## 한 줄 본질
- 원격 파이프라인이나 차량처럼 대역폭이 극히 좁고 연결이 수시로 끊기는 열악한 무선망에서 데이터 전송의 비효율성 → 2바이트 초경량 고정 헤더와 중앙 브로커 기반 발행/구독(Pub/Sub) 모델을 적용하여 1:N 비동기 브로드캐스트 구현 → 초경량 IoT 데이터 수집 및 단말 간 결합도 제거 / 브로커 서버 장애 시 전체 메시징 마비 위험

   PUBLISH ───────────────────────>
   <─────────────────────── PUBREC (수신 완료)
   PUBREL  ───────────────────────> (릴리즈)
   <─────────────────────── PUBCOMP(완료 확인)

## 핵심 용어
- 브로커(Message Broker): 발행자와 구독자 사이에 위치하여 클라이언트의 TCP 연결 유지, 토픽 트리 매칭, 세션 큐잉, 권한 검증 및 메시지 라우팅을 전담하는 중앙 허브 서버
- LWT(Last Will and Testament, 유언 메시지): 클라이언트가 브로커에 접속할 때 미리 등록해 둔 메시지로, 배터리 소모나 통신 단절로 단말이 비정상 종료되면 브로커가 이를 감지하여 다른 구독자들에게 대신 발송하는 장애 통보 기능
- 리테인 메시지(Retained Message): 특정 토픽에 메시지를 발행할 때 보관 플래그를 설정하면, 브로커가 해당 토픽의 최신 메시지 1건을 저장해 두었다가 나중에 새로 접속한 구독자에게 즉시 전달하는 기능

## 핵심 통찰
- 시간적·공간적 완전한 비동기 결합 해제(Decoupling): 발행자는 누가 데이터를 받는지(구독자 IP나 상태)를 전혀 알 필요가 없고, 구독자 또한 발행자가 언제 켜졌는지 알 필요 없이 오직 '토픽 이름' 하나로만 느슨하게 연결
- QoS 2는 만병통치약이 아니며 성능의 절대적 적: 정확히 1회(Exactly-Once) 전송을 보장하는 QoS 2는 4번의 네트워크 왕복 패킷 교환과 디스크 트랜잭션 기록이 수반되므로, 일반적인 센서 데이터에 무분별하게 적용하면 브로커 처리량이 80% 이상 급감
- 2바이트 헤더의 마법 뒤에 숨은 상시 TCP 연결의 무게: 패킷 자체는 2바이트로 매우 작지만, 전송 신뢰성을 위해 TCP 세션을 항상 맺어두어야 하므로 수십만 대 단말이 물릴 경우 브로커 서버의 파일 디스크립터 및 소켓 메모리 관리가 인프라의 최대 병목

## 이웃 토픽과 구분
- MQTT vs Kafka: MQTT는 저전력 단말과 인터넷 경계(Edge-to-Cloud) 간의 경량 수집에 특화된 프로토콜 / Kafka는 데이터센터 내부(Cloud-to-Cloud)에서 대규모 파티션 분산 저장과 실시간 빅데이터 스트리밍 처리에 특화된 백엔드 분산 로그 시스템

## 내 의견
- [업무 중요도에 따른 QoS 분리 설계와 클러스터 기반 브로커 고가용성 확보] 모든 IoT 센서 데이터를 안전하게 받겠다고 QoS 2로 일괄 설정하는 것은 무선 대역폭 낭비와 브로커 과부하를 초래하는 대표적 설계 결함 → 나라면: 수초 단위의 연속적인 온도·습도 계측 데이터는 유실을 감수하고 처리량이 높은 QoS 0으로 수집하고, 밸브 차단이나 화재 감지와 같은 제어 명령 및 이벤트에만 QoS 1~2를 선별 적용하며, 브로커는 Raft 합의 기반 분산 노드로 클러스터링하여 무중단 고가용성 보장
