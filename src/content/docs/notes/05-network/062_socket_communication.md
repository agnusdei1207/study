## 핵심 용어
- 5-Tuple: 네트워크 상에서 유일한 소켓 연결 세션을 식별하는 5가지 핵심 요소(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트, 전송 계층 프로토콜)
- I/O 다중화(I/O Multiplexing, epoll): 수만 개의 소켓 연결을 단일 스레드가 모니터링하다가, 실제 데이터 송수신 이벤트가 발생한 소켓만 커널이 $O(1)$ 복잡도로 통보해 처리하는 고성능 비동기 메커니즘
- TIME_WAIT: TCP 연결 종료 시 마지막 ACK가 유실되어 상대방이 FIN을 재전송할 경우에 대비하여 송신측이 소켓 자원을 즉시 회수하지 않고 일정 시간(2MSL, 보통 1~2분) 동안 유지하는 소켓 상태

## 핵심 통찰
- 유닉스의 철학 "모든 것은 파일이다(Everything is a file)"의 통신 확장: 소켓은 네트워크 장비를 로컬 파일처럼 다룰 수 있게 만든 핸들이므로, 파일 입출력 함수인 `read()`와 `write()`로 원격 서버와 완벽하게 데이터를 교환
- TCP 소켓은 '바이트 스트림'이므로 데이터 경계가 없음: 송신측이 `write()`를 3번 호출해도 수신측은 `read()` 1번으로 뭉쳐서 받거나 10번으로 쪼개서 받을 수 있으므로, 패킷 길이 헤더나 구분자를 두는 애플리케이션 프레이밍(Framing)이 필수적
- 1 소켓 = 1 스레드 모델의 종말(C10K 문제): 과거 아파치 웹서버처럼 클라이언트 소켓 1개마다 OS 스레드를 생성하면 1만 명 동시 접속 시 메모리 고갈과 컨텍스트 스위칭 오버헤드로 서버가 다운되므로 epoll 기반 단일 루프(Node.js, Nginx)로 진화

## 이웃 토픽과 구분
- 소켓(Socket) vs 웹소켓(WebSocket): 소켓은 전송 계층(L4 TCP/UDP)에서 OS가 제공하는 범용 IPC 통신 인터페이스 / 웹소켓은 웹 브라우저 환경에서 단일 TCP 연결(HTTP Upgrade)을 통해 실시간 양방향 통신을 제공하는 응용 계층(L7) 프로토콜

## 문제·원인·대책
- 적용 상황: 대규모 동시 접속자를 수용하는 실시간 채팅/게임 서버
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 동시 접속 1만 명 도달 시 서버 응답 불능(C10K) | 블로킹 소켓 모델에서 클라이언트당 스레드 생성으로 인한 컨텍스트 스위칭 폭증 | 리눅스 `epoll` / 윈도우 `IOCP` 기반 비동기 논블로킹 이벤트 루프 도입 | 단일 프로세스/소수 스레드로 수만 개 동시 연결 안정적 처리 |
| 단시간 대량의 단기 연결 종료 시 포트 고갈(EADDRINUSE) | 4-Way Handshake 종료 후 소켓이 2MSL 동안 TIME_WAIT 상태로 남아 포트 점유 | 소켓 옵션 `SO_REUSEADDR` 설정 및 커널 파라미터 `tcp_tw_reuse` 활성화 | 소켓 자원 즉시 재사용으로 로컬 포트 고갈 방지 |
