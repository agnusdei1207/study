## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **스레싱(Thrashing)**: 활성 프로세스들의 워킹 셋 총합이 물리 메모리 크기를 초과하여 페이지 폴트와 디스크 스왑 I/O만 반복되다 CPU 이용률이 바닥으로 추락하는 현상.
- **워킹 셋(Working Set)**: 프로세스가 특정 윈도우 시간($\Delta$) 동안 집중적으로 참조하여 메모리에 반드시 상주해야 하는 페이지들의 집합.

</details>

- 정의/개념: 가용 물리 메모리가 프로세스들의 **워킹 셋(Working Set)** 에 미치지 못해 스왑 I/O가 폭증하고 CPU 이용률이 급락하는 가상 메모리 성능 붕괴 현상
- 배경/필요성: 다중프로그래밍 정도(DOM)의 과도한 증가로 인한 **연속적 페이지 폴트, 스왑 I/O 병목 및 CPU 이용률 급락(스레싱) 위험**

#### 한줄 요약
- 메모리 부족으로 디스크 페이징 I/O만 반복되어 CPU 유효 연산이 정지되는 현상을 통제한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **다중프로그래밍 정도(Degree of Multiprogramming, DOM)**: 물리 메모리에 동시에 적재되어 실행 중인 활성 프로세스의 총 수.
- **페이지 부재 빈도(Page Fault Frequency, PFF)**: 프로세스별 페이지 폴트 발생 빈도를 측정하여 상한/하한 임계값에 따라 프레임을 동적 배분하는 기법.

</details>

- **다중프로그래밍 정도(DOM)** 임계점 초과 시 CPU 이용률이 급락하는 역설적 성능 붕괴
- 빈번한 **메이저 페이지 폴트(Major Page Fault)** 로 인한 프로세스 전체의 I/O 블로킹 대기 상태 전이
- 프로세스별 **워킹 셋(Working Set)** 보장 및 **PFF(Page Fault Frequency)** 기반 동적 프레임 할당으로 방어

#### 한줄 요약
- 스레싱은 부하와 이용률의 관계가 뒤집히는 지점에서 나타나므로, 워킹 셋과 PFF는 그 반전을 감지해 순간 처리량을 일부 포기하고 시스템을 되살린다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **워킹 셋 윈도우($\Delta$)**: 워킹 셋을 계산하기 위해 최근 참조된 페이지들을 관찰하는 시간 또는 명령어 참조 횟수 창.

</details>

```text
[스레싱 방어 제어 체계]
  │
  ├─ [가상 메모리 관리자] (VMM)
  │     ├─ [워킹 셋 추적기] (윈도우 d 내 참조 페이지 집합)
  │     ├─ [PFF 감시기] (페이지 폴트 빈도 상하한 감시)
  │     └─ [부하 제어기] (스왑아웃 및 DOM 축소 제어)
  │
  ├─ [물리 메모리 풀] (DRAM 프레임 할당 관리)
  │
  └─ [스왑 스토리지] (디스크/zRAM 스왑 영역)
```

선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 워킹 셋 추적기 | 시간 창 $\Delta$ 내 참조 페이지로 **워킹 셋 크기**($\lvert WS_i\rvert$) 산출 |
| PFF 감시기 | 단위 시간당 **페이지 폴트 빈도**를 측정하여 상한선/하한선 이탈 여부 감시 |
| 부하 제어기 | 총 워킹 셋이 물리 메모리를 초과하면 일부 프로세스를 스왑아웃하여 **DOM 축소** |
| 스왑 디스크 | 물리 메모리에서 축출된 희생자 프로세스의 페이지를 보관하는 스토리지 영역 |

#### 한줄 요약
- 워킹 셋·PFF 계측기가 부하 제어기에 DOM을 되돌릴 근거를 공급하므로, 측정 계층 없이는 스레싱과 정상 고부하를 구분할 수 없다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스레싱 악순환(Thrashing Cascade)**: 페이지 폴트 → I/O 대기로 CPU 유휴 → OS가 부하 부족으로 오판하여 새 프로세스 투입(DOM 증가) → 메모리 추가 고갈의 악순환.

</details>

```text
[스레싱 진행 및 방어 흐름] (진행 ①→④, 방어 미가동 시 악순환 진행·가동 시 강제 축소 후 회복)
  │
  ├─ [워킹 셋 추적기] (① 총 워킹 셋 요구량 $\sum |WS_i|$ > 가용 프레임 수 판정, 초과 시 폴트 폭증 진입)
  │
  ├─ [PFF 감시기] (② 메이저 페이지 폴트 폭증과 스왑 I/O 대기 전이 확인, 상한 미초과 오판 시 DOM 추가 증가)
  │
  ├─ [부하 제어기] (③ 방어 가동 시 일부 프로세스 강제 Swap-out으로 DOM 축소)
  │
  └─ [메모리 재배분] (④ 잔여 프로세스에 충분한 프레임 할당 후 CPU 정상 연산 회복)
```

분기 결과: **스레싱** 판정에서 CPU 유휴를 부하 부족으로 오판하면 새 프로세스 투입을 늘려 스왑 I/O 병목을 악화시키는 비용이 커지고, **PFF(페이지 부재 빈도)** 상한 초과를 감지한 갈래는 일부 프로세스를 스왑아웃해 순간 처리량을 포기하는 대신 잔여 워킹 셋을 지켜 시스템 마비를 피한다

#### 한줄 요약
- 폴트 폭증에 따른 CPU 이용률 하락은 부하 부족과 겉모습이 같으므로, PFF 감지가 없으면 제어기가 오히려 부하를 더 넣어 악순환을 가속한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **지역 교체 vs 전역 교체**: 페이지 폴트 시 자신의 프레임 내에서만 교체(지역)하는 것과 타 프로세스 프레임까지 빼앗아 교체(전역)하는 방식.

</details>

| 방어 기법 | 워킹 셋 모델 (Working Set) | PFF 기법 (Page Fault Frequency) | 지역 페이지 교체 (Local Replacement) |
|:---|:---|:---|:---|
| 핵심 메커니즘 | 최근 $\Delta$ 내 참조 페이지를 메모리에 고정 | **폴트 주기($T$)** 기반 동적 프레임 증감 | 자신의 할당 프레임 내에서만 희생자 선택 |
| 제어 방식 | 총 워킹 셋이 메모리 초과 시 프로세스 중단 | $T < \text{하한}$ 시 프레임 회수, $T > \text{상한}$ 시 추가 | 타 프로세스로의 스레싱 전파 차단 |
| 장점 | 스레싱 완벽 방지, 높은 메모리 효율 | 런타임 오버헤드가 적고 구현 용이 | 단일 프로세스 스레싱이 시스템 전체로 확산 방지 |
| 한계점 | 윈도우 $\Delta$ 추적 오버헤드 높음 | 페이지 폴트 발생 후에만 반응하는 사후적 한계 | 프로세스별 최적 프레임 수 동적 조절 한계 |

#### 한줄 요약
- 워킹 셋은 사전 예방, PFF는 사후 적응형 조절, 지역 교체는 장애 격리에 강점이 있다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **cgroups v2 메모리 보호(memory.min / memory.low)**: 컨테이너별로 페이지 캐시 및 익명 메모리의 최소 상주 한도를 보장하여 스레싱을 막는 리눅스 커널 기능.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 시스템 전체 스레싱으로 인한 서버 무반응(Hang) | **워킹 셋 기반 DOM 축소** 및 희생자 프로세스 일시 정지 | 스왑 I/O 폭증 즉시 해소 및 CPU 정상화 |
| 컨테이너 간 메모리 경합으로 노드 전체 스레싱 전파 | **cgroups v2 `memory.min` / `memory.high`** 설정 | 핵심 서비스의 워킹 셋 보장 및 메모리 격리 |
| 스왑 디스크의 느린 I/O 속도로 인한 스레싱 가속 | **zRAM / zswap(메모리 압축 스왑)** 도입 | 디스크 I/O를 RAM 압축으로 대체하여 지연 90% 축소 |
| 메모리 회수 지연으로 인한 런타임 스파이크 | 커널 `vm.swappiness` 및 `vm.watermark_scale_factor` 튜닝 | 백그라운드 사전 kswapd 회수로 스레싱 예방 |

#### 한줄 요약
- 스레싱은 부하를 더 넣어서는 해결되지 않으므로, 다중프로그래밍 정도를 낮춰 순간 처리량을 일부 포기하고 cgroups 최소 보장으로 남은 프로세스의 워킹셋을 지키는 쪽을 택한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **메모리 압축 스왑(Compressed RAM Swap, zswap/zRAM)**: 물리 디스크 I/O 대신 RAM의 일부를 압축 풀로 활용하여 스왑 인/아웃 지연을 극소화하는 커널 메모리 가속 기술.
- **제어 그룹 v2 메모리 제어기(cgroups v2 Memory Controller)**: 컨테이너별 메모리 사용량에 대해 최소 보장선(memory.min)과 능동 회수선(memory.high)을 지정하여 노드 스레싱 전파를 차단하는 리눅스 자원 격리 기제.

</details>

- 클라우드 컨테이너 노드 환경에서 디스크 I/O 병목을 RAM 압축으로 대체하는 **메모리 압축 스왑(zswap/zRAM)** 기술과 비동기 회수 데몬(kswapd)이 통합되는 아키텍처로 진화 추세
- 쿠버네티스 파드 밀집 환경에서 단일 프로세스의 메모리 폭증이 노드 전체 스레싱으로 전파되지 않도록 **제어 그룹 v2 메모리 제어기**의 상하한선을 정밀 설정하는 운영적 결단 필요

#### 한줄 요약
- 압축 RAM 스왑으로 디스크 병목을 우회하고 cgroups v2 상하한선 통제로 노드 단위 스레싱 전파를 차단해야 한다.
