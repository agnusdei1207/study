## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **실행 계획(Execution Plan)**: DBMS 옵티마이저가 SQL 질의를 처리하기 위해 수립한 테이블 접근 순서, 인덱스 스캔 방식, 조인 알고리즘의 세부 실행 절차.
- **CBO(Cost-Based Optimizer)**: 데이터 통계와 카디널리티를 바탕으로 디스크 I/O와 CPU 소모 비용을 예측하여 최저 비용 경로를 선택하는 최적화기.

</details>

- 정의/개념: 데이터베이스 옵티마이저가 SQL 질의를 가장 효율적으로 실행하기 위해 스캔 방식, 조인 순서 및 알고리즘을 결정한 물리적 실행 트리 명세서
- 배경/필요성: 동일 결과 집합에 대한 내부 접근 경로 차이로 인한 **수백 배의 성능 편차 및 데이터 분포 변화 시 수동 물리 경로 지정의 대응 불가 한계**

#### 한줄 요약
- CBO는 통계라는 근사치 위에서 비용을 계산하므로 계획의 품질은 옵티마이저의 능력보다 통계의 최신성에 좌우되며, 튜닝은 대개 계획을 강제하는 일이 아니라 잘못된 추정을 바로잡는 일이 된다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Access Type 계층**: `system > const > eq_ref > ref > range > index > ALL(Full Scan)` 순으로 접근 효율이 결정됨.
- **EXPLAIN ANALYZE**: 쿼리를 실제 실행하여 옵티마이저의 예측 행 수(rows)와 실제 처리 시간(actual time)을 단계별로 대조 검증하는 명령어.

</details>

- 테이블 통계 기반으로 정량적 CPU/I/O 비용을 계산하는 비용 기반 최적화(CBO) 중심
- 파싱, 쿼리 재작성, 비용 탐색, 코드 생성을 거치는 정형화된 4단계 최적화 파이프라인
- `EXPLAIN / EXPLAIN ANALYZE`를 통한 예측 카디널리티와 실제 실행 시간(Actual Time) 대조 진단

#### 한줄 요약
- 통계 기반 비용 산출과 실행 계획 검증을 통해 가장 빠른 데이터 접근 경로를 도출한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **EXPLAIN 6대 핵심 컬럼**: id(연산 순서), select_type(단순/서브쿼리), table(참조 테이블), type(조인/스캔 방식), rows(예상 행수), Extra(부가 정보).

</details>

```text
[쿼리 실행 계획 및 최적화 체계]
  │
  ├─ [접근 유형 (Access Type)]
  │     ├─ [const / system] (단건 O(1) 조회)
  │     ├─ [eq_ref / ref] (인덱스 조인 및 참조)
  │     ├─ [range] (인덱스 범위 스캔)
  │     └─ [index / ALL] (인덱스/테이블 풀스캔)
  │
  └─ [실행 계획 분석 (EXPLAIN)]
        ├─ [rows] (예상 처리 행 수 통계)
        ├─ [key / key_len] (선택 인덱스 정보)
        └─ [Extra] (Using index, filesort 등)
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 접근 방식 (type) | 의미 및 성능 수준 | 발생 상황 및 판정 기준 |
|:---|:---|:---|
| `const` / `system` | 최고 속도 ($O(1)$) | PK 또는 Unique 인덱스에 상수를 대입하여 단 1건 조회 |
| `eq_ref` | 최우수 조인 성능 | 조인 시 드라이븐 테이블을 PK/Unique 인덱스로 1건씩 룩업 |
| `ref` | 우수 ($O(\log N)$) | 비고유 인덱스(Non-Unique)에 동등(`=`) 조건을 대입하여 조회 |
| `range` | 양호 (범위 검색) | 인덱스를 사용하여 `<`, `>`, `BETWEEN`, `IN` 범위 스캔 |
| `index` | 주의 (인덱스 풀스캔) | 인덱스 리프 노드 전체를 스캔 (테이블 풀스캔보다는 빠름) |
| `ALL` | 최악 (테이블 풀스캔) | 인덱스를 전혀 타지 못하고 수백만 블록 전체 디스크 I/O 스캔 |

#### 한줄 요약
- 실행 계획의 각 항목은 확정된 사실이 아니라 옵티마이저의 추정치이므로 예상 행 수와 실제 행 수의 괴리가 곧 잘못된 계획의 발생 지점이며, Extra 정보는 그 괴리가 정렬·임시 테이블 비용으로 드러난 결과다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Query Rewrite(쿼리 재작성)**: 서브쿼리를 조인으로 풀거나 불필요한 조건을 제거하여 옵티마이저가 최적화하기 쉬운 형태로 SQL을 변환하는 단계.

</details>

```text
[SQL 최적화 파이프라인 경로] (진행 ①→⑤, 계획 확정 후 스토리지 엔진 실행)
  │
  ├─ [구문·어휘 분석] (① Parser가 SQL 문법 검증 및 파스 트리 생성)
  │
  ├─ [쿼리 재작성] (② Subquery Unnesting·View Merging 등 동등한 표준 관계대수식으로 변환)
  │
  ├─ [CBO 비용 계산] (③ 통계 정보(Histogram) 기반으로 인덱스·조인 조합별 CPU + I/O 비용 계산)
  │
  ├─ [최적 계획 확정] (④ 가장 비용이 낮은 최적 물리 실행 계획 선택)
  │
  └─ [실행 및 반환] (⑤ 스토리지 엔진(InnoDB)에 실행 지시 후 데이터 인출·반환)
```

분기 결과: 옵티마이저는 모든 조인 순서를 탐색하는 최적해를 포기하고 후보를 잘라내므로, 통계가 실제 분포와 어긋날수록 잘못된 계획이 채택되어 같은 질의가 인덱스 스캔과 풀스캔 사이에서 수백 배의 비용 편차를 낸다

#### 한줄 요약
- 계획 수립은 밀리초 단위지만 잘못 고르면 실행이 수십 초로 늘어나므로, 옵티마이저는 모든 조인 순서를 탐색하는 최적해를 포기하고 후보를 잘라내 계획 비용과 실행 비용의 균형을 취한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **RBO vs CBO**: 고정된 15가지 우선순위 규칙만 따르던 구형 RBO와 실제 데이터 통계 비용을 계산하는 현대 CBO.

</details>

| 비교 항목 | 규칙 기반 옵티마이저 (RBO: Rule-Based) | 비용 기반 옵티마이저 (CBO: Cost-Based) |
|:---|:---|:---|
| 최적화 기준 | 사전 정의된 고정 우선순위 규칙 (15개 Rule)| 테이블 크기, 인덱스 높이, 데이터 통계 I/O 비용 |
| 데이터 규모 반영 | 전혀 반영 불가 (데이터가 10건이든 1억 건이든 동일) | 실시간 데이터 분포 및 행 수(rows)에 따라 유연 선택 |
| 통계 정보 의존성 | 불필요 | 필수 (`ANALYZE TABLE` 통계 수집 필수) |
| 현재 위상 | 과거 레거시 DBMS 잔재 | 현대 모든 상용/오픈소스 RDBMS 표준 |

#### 한줄 요약
- RBO는 고정 규칙에 의존하나, CBO는 데이터 통계를 바탕으로 최적의 비용 경로를 동적으로 산출한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Using filesort & Using temporary**: 정렬 인덱스가 없어 디스크 메모리에서 별도 정렬하거나, 복잡한 집계를 위해 메모리/디스크에 임시 테이블을 생성하는 병목.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 통계 정보 노후화로 인한 비효율 Full Table Scan(`type: ALL`) | 정기적인 `ANALYZE TABLE` 실행 및 자동 통계 수집 스케줄링 | CBO 카디널리티 산출 정확도 100% 유지 |
| `Using filesort`, `Using temporary` 발생으로 CPU/메모리 폭증 | `ORDER BY / GROUP BY` 순서에 일치하는 복합 인덱스 생성 | 별도 정렬/임시테이블 소멸 및 쿼리 속도 10배 개선 |
| CBO가 통계 오류로 잘못된 인덱스를 선택하여 지연 | `USE INDEX` 또는 Optimizer Hint(`/*+ INDEX(t idx) */`) 제한적 명시| 실행 계획 강제 고정 및 안정화 |
| 예측 행 수와 실제 처리 행 수가 극단적으로 다름 | `EXPLAIN ANALYZE`로 실제 실행 시간(Actual Time) 대조 튜닝 | 숨겨진 데이터 스큐(Skew) 병목 조기 식별 |

#### 한줄 요약
- 통계 최신화, 정렬 복합 인덱스 설계, 옵티마이저 힌트 활용, `EXPLAIN ANALYZE` 진단으로 튜닝한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **비용 기반 옵티마이저(Cost-Based Optimizer, CBO)**: 카디널리티, 인덱스 분포, 디스크 I/O 비용을 계산하여 최적의 물리적 실행 경로를 도출하는 엔진.
- **적응형 쿼리 실행(Adaptive Query Execution, AQE)**: 쿼리 실행 중 런타임 중간 통계를 즉시 피드백받아 조인 방식이나 파티션 분할을 동적으로 변경하는 지능형 최적화 메커니즘.

</details>

- **적응형 쿼리 실행(AQE) 및 AI 자율 튜닝 진화**: 정적 통계에 의존하던 전통적인 **비용 기반 옵티마이저(CBO)**는 런타임 데이터 스큐를 실시간 감지하여 조인 전략을 동적으로 재조정하는 **적응형 쿼리 실행(AQE)** 및 거대언어모델(LLM)·머신러닝 기반 자율 인덱스 추천 엔진으로 고도화 추세.
- **통계 정확도 확보와 런타임 프로파일링 거버넌스 결단**: 옵티마이저 오판으로 인한 풀 테이블 스캔을 방지하기 위해 정기 통계 수집(`ANALYZE TABLE`)을 제도화하고, 정렬·집계 인덱스를 선별 구축하여 디스크 임시테이블 생성을 차단하되 `EXPLAIN ANALYZE` 실측 프로파일링으로 오차를 상시 모니터링하는 공학적 운영 거버넌스 확보 필요.

#### 한줄 요약
- 쿼리 최적화는 AQE 및 AI 자율 튜닝 체계로 진화하고 있으며, CBO 통계 최신화와 `EXPLAIN ANALYZE` 기반의 실측 검증 거버넌스가 핵심이다.
