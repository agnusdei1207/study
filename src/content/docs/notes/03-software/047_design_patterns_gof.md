## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **GoF(Gang of Four) 디자인 패턴**: 에리히 감마(Erich Gamma) 등 4명의 저자가 정립한 객체지향 소프트웨어 설계의 23가지 재사용 가능한 해결 템플릿.
- **생성·구조·행위 패턴**: 객체의 인스턴스화(생성 5종), 클래스/객체의 합성(구조 7종), 상호작용 및 책임 분배(행위 11종)의 3대 분류.

</details>

- 정의/개념: 객체지향 설계의 유연성과 재사용성을 높이기 위해 검증된 객체 생성, 구조 결합, 행위 위임 전략을 정립한 **GoF(Gang of Four) 디자인 패턴** 23종
- 배경/필요성: 구체 클래스를 직접 생성·상속·분기하는 설계는 요구 변경마다 호출 코드 전체를 수정·재컴파일하는 비용을 반복하므로, 변경 지점을 인터페이스 뒤로 격리한 **생성·구조·행위 패턴** 카탈로그를 두어 확장을 코드 추가로 대체

#### 한줄 요약
- 23종은 새 기법이 아니라 이미 검증된 해법에 이름을 붙인 카탈로그이므로, 가치는 코드보다 설계 의도를 한 단어로 전달하는 공통 어휘에 있다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **공통 설계 어휘(Common Vocabulary)**: "이 클래스는 Factory Method로 구현하고 Strategy로 알고리즘을 주입합시다"와 같이 개발자 간 소통 비용을 줄이는 표준 용어.
- **Composition over Inheritance**: 상속의 강결합을 피하고 객체 합성(Composition)과 인터페이스 위임을 통해 런타임 유연성을 확보하는 원칙.

</details>

- 목적별 3대 분류 체계: 생성 패턴 5종, 구조 패턴 7종, 행위 패턴 11종 구조화
- 인터페이스 다형성과 **Composition over Inheritance**를 활용하여 개방 폐쇄 원칙(OCP)과 의존역전 원칙(DIP) 실현
- 개발자 간 아키텍처 설계 의도를 명확하고 간결하게 소통하는 **공통 설계 어휘** 역할

#### 한줄 요약
- 패턴은 공통 어휘와 확장성을 주는 대신 클래스 수와 간접 호출을 늘리므로, 변경이 실제로 일어나는 축에만 적용해야 이득이 남는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Factory Method**: 객체 생성 메서드를 상위 클래스에 추상으로 선언하고 어떤 구체 클래스를 인스턴스화할지는 서브클래스가 결정하게 위임하는 생성 패턴.
- **Adapter**: 기존 클래스의 호환되지 않는 인터페이스를 클라이언트가 기대하는 인터페이스로 감싸 변환하는 래퍼 구조 패턴.
- **Strategy**: 알고리즘군을 각각 인터페이스 구현체로 캡슐화하고 컨텍스트가 그 인터페이스에 위임해 런타임에 구현체를 갈아 끼우는 행위 패턴.

</details>

```text
[GoF 23종 디자인 패턴 체계]
  │
  ├─ [생성 패턴 5종] (객체 생성 캡슐화)
  │     ├─ Singleton / Prototype
  │     ├─ Factory Method / Abstract Factory
  │     └─ Builder
  │
  ├─ [구조 패턴 7종] (클래스·객체 합성 유연화)
  │     ├─ Adapter / Bridge / Composite
  │     └─ Decorator / Facade / Flyweight / Proxy
  │
  └─ [행위 패턴 11종] (알고리즘 교체·책임 분배)
        ├─ Strategy / Template Method / State
        ├─ Observer / Command / CoR / Iterator
        └─ Mediator / Memento / Visitor / Interpreter
```
- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 생성 패턴 5종 | **Factory Method** 등으로 객체 생성을 캡슐화해 결합 완화 |
| 구조 패턴 7종 | **Adapter** 등으로 인터페이스 변환과 객체 합성 |
| 행위 패턴 11종 | **Strategy** 등으로 알고리즘·상태·협력의 책임 위임 |

#### 한줄 요약
- 생성·구조·행위 분류는 변경이 발생하는 위치를 기준으로 나뉘므로, 무엇이 자주 바뀌는지를 먼저 정해야 알맞은 패턴이 지목된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **설계 냄새(Design Smell)**: if-else 분기문 폭증, 거대 클래스, 상속 깊이 과다 등 패턴 적용이 필요한 결함 징후.

</details>

```text
[GoF 패턴 적용 흐름] (진행 ①→⑤, 문제 성격 분석 후 패턴 선정이 갈림)
  │
  ├─ [문제 식별] (① 코드 냄새·설계 문제 관찰, 결제 수단별 if-else 분기 폭증 등)
  │
  ├─ [문제 성격 분석] (② 생성 문제·구조적 결합·행위/알고리즘 교체 여부 판정)
  │
  ├─ [GoF 패턴 매핑] (③ 알고리즘 교체는 Strategy, 생성은 Factory 계열 패턴 선정)
  │
  ├─ [트레이드오프 평가] (④ 복잡도 대비 유연성 검토, YAGNI 위반 여부 판정)
  │
  └─ [리팩토링 실행] (⑤ 인터페이스 정의·구현체 분리(PaymentStrategy), 신규 결제 수단 추가 시 기존 코드 무수정 OCP 확장)
```

분기 결과: 문제 성격이 갈림의 첫 축이고 알고리즘 교체는 Strategy로 열리되, 변경 빈도가 낮은 곳에 패턴을 얹으면 유연성보다 복잡도 비용이 커져 선정 단계에서 적용 여부가 갈린다

#### 한줄 요약
- **설계 냄새**에서 패턴 매핑까지는 기계적이지만 실제 채택은 트레이드오프 검토에서 갈리므로, 문제 유형이 같아도 변경 빈도가 낮으면 적용하지 않는 편이 낫다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **발행/구독(Publish-Subscribe)**: 발행자가 구독자 목록을 유지하고 상태 변화 시 등록된 구독자 전원에게 통지 메서드를 호출해 양쪽을 느슨하게 결합하는 통신 구조.

</details>

| 핵심 패턴 | 분류 | 핵심 의도 및 해결책 | 코드 설계 특징 |
|:---|:---|:---|:---|
| Singleton | 생성 | 전역에서 단 하나의 인스턴스만 보장 | `private` 생성자 + `static getInstance()` |
| Factory Method | 생성 | 객체 생성을 하위 서브클래스에 위임 | 상속을 통한 인스턴스화 분리 |
| Adapter | 구조 | 호환되지 않는 인터페이스를 맞춤 변환 | 래퍼(Wrapper) 클래스로 중계 |
| Decorator | 구조 | 상속 없이 런타임에 동적으로 기능 덧붙임 | 동일 인터페이스를 감싸며 부가기능 실행 |
| Proxy | 구조 | 실제 객체 접근 제어, 지연 로딩, 보안 검증 | 실제 객체와 동일 인터페이스 대리자 |
| Strategy | 행위 | 런타임에 알고리즘(전략)을 자유롭게 교체 | 인터페이스 위임 (Composition) |
| Observer | 행위 | 상태 변화 시 다수의 구독자에게 자동 통지 | **발행/구독(Publish-Subscribe)** 구조 |

#### 한줄 요약
- 같은 문제라도 생성·구조·행위 중 어느 축의 변경인지에 따라 패턴이 갈리므로, 비교표는 패턴 이름이 아니라 그 패턴이 격리하는 변경 축으로 읽어야 한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Pattern Overengineering(패턴 과용)**: 단순한 10줄짜리 코드에 5개의 클래스와 인터페이스를 만들어 가독성과 유지보수성을 해치는 설계 과잉.
- **YAGNI(You Aren't Gonna Need It)**: 지금 필요하다고 확인된 기능만 구현하고, 미래 요구를 예측한 추상화는 실제 요구가 나타날 때까지 미루는 XP 원칙.
- **KISS(Keep It Simple, Stupid)**: 같은 요구를 만족하는 설계 중 구성요소와 간접 계층이 가장 적은 것을 택해 이해·변경 비용을 낮추는 설계 원칙.
- **Initialization-on-demand Holder Idiom**: Singleton 인스턴스를 내부 정적 홀더 클래스의 필드로 두어, 홀더 클래스가 처음 참조되는 순간 JVM 클래스 로딩의 직렬화 보장으로 동기화 코드 없이 지연 초기화하는 Java 관용구.
- **Template Method**: 알고리즘의 뼈대를 상위 클래스 메서드로 고정하고 가변 단계만 하위 클래스가 오버라이드해 채우는 상속 기반 행위 패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순한 로직에 불필요한 다중 패턴 적용(**패턴 과용**) | **YAGNI**/**KISS** 원칙 준수 및 실제 3회 이상 중복 시 도입 | 코드 단순성 및 가독성 유지 |
| 패턴 적용으로 인한 클래스 수 급증 및 보일러플레이트 | 최신 언어의 함수형 인터페이스 및 람다식(Lambda) 활용 | 별도 Strategy 클래스 없이 1줄로 전략 주입 |
| 멀티스레드 환경에서 Singleton 동시성 버그 | **Initialization-on-demand Holder Idiom** 또는 Enum 사용 | 스레드 세이프(Thread-Safe) 및 지연 로딩 완벽 보장 |
| 상속 기반 **Template Method**의 강결합 문제 | 인터페이스 위임 기반 **Strategy** 패턴으로 리팩토링 | 상속 결합도 제거 및 런타임 교체 유연성 확보 |

#### 한줄 요약
- 패턴은 결합도를 낮추는 대신 간접 계층과 학습 비용을 더하므로, 언어 기능으로 대체 가능한 패턴은 람다·Holder 관용구로 줄이고 조건 분기가 늘어나는 지점에만 전략 패턴을 도입한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **관점 지향 프로그래밍(Aspect-Oriented Programming, AOP)**: 트랜잭션, 로깅 등 시스템 전반에 걸친 횡단 관심사를 비즈니스 로직과 분리하여 모듈화하는 기법(프록시 패턴의 자동화).
- **반응형 프로그래밍(Reactive Programming)**: 데이터 스트림과 비동기 이벤트 전파를 중심으로 시스템을 구성하여 높은 처리량과 탄력성을 달성하는 프로그래밍 패러다임(옵저버 패턴의 진화).
- **함수형 프로그래밍(Functional Programming)**: 상태 변경과 가변 데이터를 지양하고 순수 함수 조합을 통해 사이드 이펙트를 최소화하는 프로그래밍 패러다임.

</details>

- **차세대 발전 전망**: 함수형 언어 사상과 결합되어 전략·커맨드 등의 보일러플레이트 클래스가 람다식으로 대체되고, 스프링 **AOP(Aspect-Oriented Programming)** 및 스트림 기반 **반응형 프로그래밍(Reactive Programming)** 라이브러리로 패턴이 고도화되는 추세.
- **실무 공학적 통찰**: 모든 문제를 패턴으로 해결하려는 패턴 만능주의를 경계하고, **단순성 유지(KISS)** 원칙 하에 시스템 결합도 완화와 간접 호출 계층 증가 간의 트레이드오프를 통제하는 아키텍처적 결단 필요.

#### 한줄 요약
- GoF 패턴은 함수형 람다 및 AOP 프레임워크와 결합하여 보일러플레이트를 제거하며 진화하되, 과잉 엔지니어링을 배제하고 단순성을 지키는 실용적 선택이 설계의 본질이다.
