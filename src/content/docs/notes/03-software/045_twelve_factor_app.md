## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **12 Factor App**: Heroku 창립자들이 클라우드 환경에서 이식성, 확장성, 유지보수성을 극대화하기 위해 정립한 12가지 소프트웨어 아키텍처 원칙.
- **Stateless & Config**: 프로세스를 상태가 없는 무상태로 유지하고, 배포 환경별 설정(DB URL 등)을 환경변수로 주입하는 핵심 철학.

</details>

- 정의/개념: 클라우드 환경에서 이식성과 확장성을 극대화하기 위해 **무상태(Stateless), 환경변수 설정(Config), 선언적 의존성** 등 12개 원칙을 정의한 설계 지침
- 배경/필요성: 환경 설정 하드코딩, 인메모리 세션 종속 및 **불투명한 파이프라인으로 인한 클라우드 배포 실패와 수평 확장(Scale-out) 한계**

#### 한줄 요약
- 컨테이너 기반 수평 확장과 무중단 배포를 지원하는 클라우드 네이티브 12대 개발 원칙이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **개발/운영 동등성(Dev/Prod Parity)**: 개발, 스테이징, 프로덕션 환경의 백엔드 서비스(DB 버전 등)를 최대한 동일하게 유지하여 배포 오류를 차단하는 원칙.
- **폐기 가능성(Disposability)**: 빠른 기동(Fast Startup)과 SIGTERM 수신 시 안전한 종료(Graceful Shutdown)를 보장하는 설계.

</details>

- 설정을 소스 코드에서 완전 분리하여 **OS 환경 변수(ENV)** 로 런타임 주입
- 프로세스를 **무상태(Stateless)** 로 유지하여 Kubernetes 오토스케일링 시 자유로운 복제/소멸
- 빌드-릴리즈-실행의 엄격한 분리 및 **표준 출력(stdout) 기반의 스트림 로그 배출**

#### 한줄 요약
- 12요소는 이식성과 수평 확장을 얻는 대신 상태와 설정을 모두 밖으로 밀어내므로, 애플리케이션이 단순해진 만큼 주변 인프라 의존이 늘어난다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **지원 서비스(Backing Services)**: 데이터베이스, 캐시, 메시지 큐 등 프로세스가 네트워크로 연결하는 외부 리소스를 탈부착 가능한 URL 자원으로 취급.

</details>

```text
[12 Factor 원칙 체계]
  │
  ├─ [코드/의존성/설정]
  │     ├─ [I. 코드베이스] (단일 Git 저장소)
  │     ├─ [II. 의존성] (명시적 패키지 격리)
  │     ├─ [III. 설정] (환경변수 ENV 주입)
  │     └─ [IV. 지원 서비스] (URL 자원 탈부착)
  │
  ├─ [빌드/실행/프로세스]
  │     ├─ [V. 빌드/릴리즈/실행] (단계 엄격 분리)
  │     ├─ [VI. 무상태 프로세스] (Shared-Nothing)
  │     ├─ [VII. 포트 바인딩] (자체 포트 리스닝)
  │     ├─ [VIII. 동시성] (프로세스 단위 확장)
  │     └─ [IX. 폐기 가능성] (Graceful Shutdown)
  │
  └─ [환경/운영/로그]
        ├─ [X. 환경 동등성] (Dev/Prod 격차 해소)
        ├─ [XI. 로그] (stdout 스트림 배출)
        └─ [XII. 관리 프로세스] (일회성 작업 격리)
```
- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 설정 | 비밀·환경값의 **ENV 외부 주입** |
| 프로세스 | **무상태 실행·상태 외장화** |
| 빌드·릴리즈·실행 | 불변 산출물의 **단계 분리** |
| 폐기 가능성 | 빠른 기동과 **Graceful Shutdown** |
| 로그 | **stdout 이벤트 스트림 배출** |

#### 한줄 요약
- 12요소는 코드·설정·상태·로그를 각각 다른 곳에 두라는 분리 규칙의 묶음이므로, 하나라도 프로세스 안에 남으면 수평 확장의 전제가 깨진다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Build-Release-Run**: 변경 불가능한 바이너리 빌드(Build)에 특정 환경의 Config를 결합하여 고유 릴리즈 ID(Release)를 만들고 실행(Run)하는 파이프라인.

</details>

```text
[12 Factor 배포 파이프라인] (진행 ①→⑤, Scale-out으로 동일 산출물 프로세스 복제)
  │
  ├─ [개발자 커밋] (① Git 단일 코드베이스에 커밋·푸시)
  │
  ├─ [Build] (② 의존성 패키징 및 불변 Docker 이미지 생성)
  │
  ├─ [Release] (③ 빌드 이미지 + 환경별 Config(K8s ConfigMap/Secret) 결합, 고유 릴리즈 ID 부여)
  │
  ├─ [Run] (④ 포트 바인딩된 무상태 컨테이너 프로세스 기동)
  │
  └─ [Kubernetes HPA] (⑤ 동적 Scale-out 프로세스 복제 및 자원 자동 회수)
```

분기 결과: 동일 불변 산출물을 두고 환경 설정만 갈아 끼우는 갈림이라 환경 간 차이가 코드가 아닌 Config로 국한되며, 오류 릴리즈 시 빌드 재수행 없이 릴리즈 구성만 되돌리는 비용으로 롤백이 끝난다

#### 한줄 요약
- 빌드와 릴리즈를 분리해 같은 산출물에 환경설정만 갈아 끼우므로, 환경 간 차이가 코드가 아닌 설정 하나로 좁혀진다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전통 레거시 앱 vs 12 Factor 클라우드 네이티브 앱**: 로컬 상태 의존성과 불변 컨테이너 수평 확장성의 비교.

</details>

| 비교 항목 | 전통 레거시 애플리케이션 | 12 Factor 클라우드 네이티브 앱 |
|:---|:---|:---|
| 설정 관리 | 소스 코드 내 XML/YAML 하드코딩 | **OS 환경 변수(ENV) 외부 주입** |
| 상태 및 세션 | 로컬 톰캣 인메모리 세션 저장 | **완전 무상태 (Stateless), Redis 외장화** |
| 로그 처리 | 로컬 디스크 파일(`app.log`) 롤링 | **표준 출력(`stdout`) 이벤트 스트림** |
| 확장 방식 | 단일 서버 하드웨어 증설(Scale-up) | **컨테이너 단위 즉각 수평 확장(Scale-out)** |
| 기동/종료 | 기동 수 분 소요, 강제 킬(SIGKILL) | **초고속 기동, 우아한 종료(Graceful Shutdown)** |

#### 한줄 요약
- 레거시는 로컬 결합으로 확장이 어렵고, 12 Factor 앱은 완전 분리로 무한 확장을 지원한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Graceful Shutdown(우아한 종료)**: 컨테이너 롤링 업데이트 시 SIGTERM 신호를 받아 신규 요청 유입을 차단하고, 이미 진행 중인 요청을 안전하게 처리한 뒤 종료하는 절차.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| Git 레포지토리에 DB 비밀번호 노출 보안 사고 | **K8s Secret 및 Vault 기반 환경 변수 주입** | 소스 코드 유출 시에도 자격 증명 안전 보호 |
| 컨테이너 배포 시 처리 중이던 사용자 요청 유실 | **Spring Boot `graceful-shutdown` 및 SIGTERM 핸들러** | 배포 중 502/503 에러 0화 및 무중단 배포 |
| Pod 재생성 시 컨테이너 로컬 로그 파일 영구 소실 | 로그를 **stdout 배출 후 DaemonSet(Fluentd/Loki) 수집** | 컨테이너 소멸과 무관한 중앙 로그 영구 보존 |
| 로컬 세션 클러스터링 미흡으로 인한 로그인 풀림 | 세션 저장소를 **Redis 클러스터로 외장화** | 인스턴스 소멸 시에도 사용자 세션 100% 유지 |

#### 한줄 요약
- 무상태 원칙은 수평 확장을 얻는 대신 상태를 밖으로 밀어내 외부 저장소 의존을 만들므로, 세션은 Redis로 외장화하고 종료 시점은 Graceful Shutdown으로 다뤄 확장의 전제를 유지한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **불변 인프라(Immutable Infrastructure)**: 실행 중인 서버나 컨테이너를 직접 수정하지 않고 변경 시 새로운 이미지를 빌드하여 통째로 교체 배포하는 인프라 운영 방식.
- **수평형 파드 자동 확장(Horizontal Pod Autoscaler, HPA)**: CPU/메모리 부하 및 사용자 정의 메트릭에 연동되어 쿠버네티스 파드 복제본 수를 실시간 자동 조절하는 확장 메커니즘.
- **코드 기반 인프라(Infrastructure as Code, IaC)**: 서버, 네트워크 등 시스템 인프라 구성을 수동 설정 대신 선언적 코드(Terraform 등)로 작성하여 Git 형상 관리하는 기술.

</details>

- **차세대 발전 전망**: 쿠버네티스 오케스트레이션 환경의 **수평형 파드 자동 확장(HPA)** 및 **코드 기반 인프라(IaC)**, **불변 인프라(Immutable Infrastructure)** 운영 모델과 유기적으로 결합되어, 엔터프라이즈 클라우드 네이티브 소프트웨어의 필수 규범으로 지속 진화 추세.
- **실무 공학적 통찰**: 무상태(Stateless) 원칙을 통한 세션/데이터 완전 외장화와 민감 설정의 시크릿 격리를 강제하고, 컨테이너 폐기 시 인플라이트(In-Flight) 트래픽 유실을 방지하는 우아한 종료(Graceful Shutdown) 엔지니어링 구현 필수.

#### 한줄 요약
- 12 팩터 앱은 불변 인프라 및 HPA와 결합하여 무한 수평 확장을 보장하되, 철저한 상태 외장화와 우아한 종료 처리를 확보하는 엔지니어링 규율이 본질이다.
