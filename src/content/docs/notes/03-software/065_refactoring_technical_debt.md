## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **리팩터링(Refactoring)**: 소프트웨어의 외부 동작(Behavior)은 그대로 유지하면서 내부의 구조, 가독성, 유지보수성을 개선하는 공학 기법.
- **기술 부채(Technical Debt)**: 빠른 출시를 위해 임시방편(Quick & Dirty)으로 작성된 코드가 시간이 지남에 따라 수정 비용과 결함률을 가중시키는 부채 개념.

</details>

- 정의/개념: 외부 동작(Behavior)을 보존하며 **코드 악취(Code Smell)를 제거하고 내부 구조를 개선**하여 누적된 기술 부채를 상환하는 공학 활동
- 배경/필요성: 임시방편 코드 누적에 따른 **수정 비용 지수적 증가(기술 부채 복리 이자) 및 결함률 가중 한계**

#### 한줄 요약
- 회귀 테스트 안전망 보호 하에 외부 동작을 보존하며 내부 구조를 지속 개선한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **외부 행위 보존**: 관찰 가능한 동작을 유지하고 기능·명세 변경을 분리하는 원칙.
- **보이스카우트 원칙(Boy Scout Rule)**: "캠핑장은 떠날 때 처음 왔을 때보다 더 깨끗하게 치워라" - 코드를 만질 때마다 조금씩 리팩토링하는 문화.

</details>

- 신규 기능 추가와 분리해 **외부 행위 보존** 원칙 준수
- 중복 코드(DRY 위반) 및 거대 클래스 등 **코드 악취(Code Smell)의 지속적 제거**
- 리팩터링의 회귀를 탐지하는 **자동화 테스트 안전망** 확보

#### 한줄 요약
- 리팩터링은 외부 행위 보존이라는 제약 덕에 안전하지만 같은 제약 때문에 기능 개선 없이 시간을 사용하는 활동이 되므로, 우선순위 경쟁에서 밀리지 않게 별도로 배정해야 한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **대표 리팩터링 기법**: 메서드 추출(Extract Method), 클래스 추출(Extract Class), 변수 인라인화, 상속을 합성으로 전환.

</details>

```text
[리팩터링 및 부채 관리 체계]
  │
  ├─ [코드 악취 지표] (중복 코드·거대 클래스 등 식별)
  │
  ├─ [기술 부채 백로그] (상환 비용 및 영향도 우선순위)
  │
  ├─ [회귀 테스트 안전망] (JUnit·단언문 기반 동작 보존)
  │
  └─ [리팩터링 카탈로그] (메서드/클래스 추출·합성 전환)
```
- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 코드 악취 지표 | 긴 메서드·중복 코드 등 **개선 후보** 식별 |
| 기술 부채 백로그 | 영향과 상환 비용에 따라 우선순위 관리 |
| 회귀 테스트 안전망 | 변경 전후 **관찰 동작**의 회귀 탐지 |
| 리팩터링 기법 카탈로그 | 메서드 추출 등 재구조화 패턴 제공 |

#### 한줄 요약
- 회귀 테스트 안전망이 있어야 리팩터링이 동작 보존을 주장할 수 있으므로, 시험 없는 코드에서는 부채 상환 자체가 새로운 위험이 된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Baby Steps(작은 보폭)**: 1~2줄 단위로 작게 코드를 수정하고 즉시 테스트를 실행하여 결함 발생 지점을 즉시 특정하는 리팩토링 방식.

</details>

```text
[리팩터링 실행 주기] (진행 ①→⑤, Green 확인 후 커밋·상환 완료)
  │
  ├─ [코드 악취 탐지] (① SonarQube 정적 분석으로 Code Smell 식별)
  │
  ├─ [테스트 존재 확인] (② 해당 모듈 단위 테스트 여부·미존재 시 회귀 테스트 선작성)
  │
  ├─ [안전망 초록불 확인] (③ 단위 테스트 실행·Green 확보)
  │
  ├─ [작은 단위 리팩터링] (④ 메서드 추출(Extract Method) 등 Baby Steps 적용)
  │
  ├─ [회귀 테스트 재실행] (⑤ 모든 테스트 통과(Green) 여부 판정)
  │
  ├─ [직전 수정 되돌림] (⑤ Red 시 Baby Steps 한 걸음만 원복 후 ④ 재진입)
  │
  └─ [커밋·부채 상환] (⑤ Green 시 Git Refactor 태그 커밋 후 부채 백로그 상환)
```

분기 결과: 회귀 테스트 재실행에서 갈라지는 판정은 Green(진행)/Red(되돌림)이며, Red 경로는 직전 **Baby Steps** 수정만 되돌리는 낮은 복구 비용을 치르는 대신 동작 보존을 재확인하고, Green 경로는 단계마다 테스트를 반복하는 시간 비용을 치르고 안전망 증명을 얻는다

#### 한줄 요약
- 한 걸음마다 시험을 다시 돌리는 것이 느려 보이지만, 그 덕에 실패했을 때 되돌릴 범위가 직전 한 걸음으로 한정된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 vs 기능 추가 vs 성능 최적화**: 코드 구조 개선(리팩터링), 신규 비즈니스 로직 구현(기능 추가), 속도/메모리 튜닝(성능 최적화).

</details>

| 비교 항목 | 리팩터링 (Refactoring) | 기능 추가 (Feature Addition) | 성능 최적화 (Optimization) |
|:---|:---|:---|:---|
| 핵심 목적 | **코드 가독성, 유지보수성, 결합도 개선** | 신규 비즈니스 가치 제공 | **응답 시간 단축, 메모리 사용량 절감** |
| 외부 행위 변경 | **관찰 동작 유지** | 신규 동작 추가 | 결과 유지·비기능 특성 변경 |
| 코드 복잡도 | **감소 (클린 코드로 단순화)** | 신규 코드 추가로 다소 증가 | 캐싱/병렬화로 복잡도 증가 가능 |
| 1차 수혜자 | **동료 개발자 및 유지보수 엔지니어** | 최종 사용자 (End User) | 시스템 인프라 및 사용자 |

#### 한줄 요약
- 리팩터링은 유지보수성 개선, 기능 추가는 비즈니스 가치 창출, 최적화는 실행 속도 개선이 목적이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Big Bang Refactoring(빅뱅 리팩토링)**: 수만 줄의 코드를 한 번에 갈아엎다가 일정 지연과 대규모 런타임 장애를 유발하는 위험한 안티패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 회귀 테스트 없는 변경으로 기존 기능 파괴 | **특성화 테스트** 작성 후 리팩터링 | 회귀 탐지와 변경 위험 감소 |
| 빅뱅 리팩터링에 따른 일정 지연 | 부채 위험 기반 **상환 용량** 배정 | 기능 개발과 부채 상환 균형 |
| 기술 부채 방치로 개발 생산성 붕괴 | **SonarQube SQALE 기반 부채 지수(Technical Debt Ratio) 가시화** | 경영진 설득 및 계획적 부채 상환 |
| 리팩토링 중 신규 기능 추가가 섞여 디버깅 난항 | **리팩토링 커밋과 기능 추가 커밋을 명확히 물리 분리** | 변경 추적성 및 롤백 용이성 확보 |

#### 한줄 요약
- 리팩터링은 지금의 개발 속도를 내주고 미래 변경 단가를 낮추는 투자이므로, 상환 용량을 주기에 미리 배정하고 기능 변경과 커밋을 분리해 위험과 효과를 각각 확인 가능하게 둔다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **스케일 방법론(Software Quality Assessment based on Lifecycle Expectations, SQALE)**: 소스 코드 결함 수정에 소요되는 노력을 금전적·시간적 비용으로 환산하여 기술 부채를 정량화하는 품질 평가 모델.
- **지속적 통합/지속적 배포(Continuous Integration/Continuous Deployment, CI/CD)**: 코드 품질 검증과 테스트를 자동화하여 리팩토링의 회귀 결함을 조기에 차단하는 배포 파이프라인.

</details>

- **AI 기반 자동 리팩토링 및 CI/CD 품질 게이트 연계 진화**: 현대 리팩토링은 LLM 기반 코드 분석 에이전트와 **지속적 통합/지속적 배포(CI/CD)** 품질 게이트의 결합을 통해, **스케일 방법론(SQALE)** 기반 부채 지수를 실시간 추적하고 코드 스멜을 자동 패치하는 형태로 고도화 추세.
- **상환 용량 정량화와 안전망 기반 점진 개선 결단**: 기능 개발 속도와 부채 상환 간의 충돌을 방지하기 위해 스프린트 내 15~20%의 고정 상환 용량을 배정하고, 특성화 테스트 안전망을 확보한 상태에서 작은 보폭으로 개선하는 공학적 거버넌스 확보 필요.

#### 한줄 요약
- 리팩토링은 AI 에이전트와 CI/CD 품질 게이트 자동화로 진화하고 있으며, 상환 용량의 제도적 배정과 테스트 안전망 기반의 점진적 부채 통제가 핵심이다.
