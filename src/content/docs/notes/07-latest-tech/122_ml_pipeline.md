## 한 줄 본질
- 데이터 과학자가 노트북에서 손으로 돌린 코드는 실무 배포 시 데이터 형태가 조금만 바뀌어도 터지고 재현이 불가능함 → 데이터 수집, 검증, 훈련, 모델 등록, 배포까지의 모든 과정을 공장의 자동화 컨베이어 벨트(DAG)로 묶어 무인으로 돌리는 소프트웨어 파이프라인 / 파이프라인 구축 및 운영 비용 발생

## 핵심 용어
- 훈련-서빙 스큐(Training-Serving Skew): 모델을 훈련할 때 사용한 데이터 전처리 로직과 실제 실시간 서빙 시 적용된 전처리 코드의 미세한 차이로 인해 운영 환경에서 모델 성능이 급락하는 현상
- 지속적 학습(CT, Continuous Training): 운영 중인 모델의 성능 저하(드리프트)가 감지되면, 사람의 개입 없이 파이프라인이 자동으로 최신 데이터를 긁어와 재학습하고 검증 후 재배포하는 MLOps 수준
- 모델 레지스트리(Model Registry): 학습이 완료된 모델 가중치 파일과 함께 학습에 사용된 코드 버전, 하이퍼파라미터, 성능 평가 지표를 중앙 저장소에 버전별로 등록·관리하는 승인 시스템

## 핵심 통찰
- "코드는 소프트웨어의 일부일 뿐이며 데이터와 모델이 결합되어야 완성된다": 일반 소프트웨어 CI/CD는 코드 변경만 추적하지만, ML 파이프라인은 '코드 + 데이터 + 모델 가중치' 3요소의 버전을 완벽히 동기화해야 1년 뒤에도 똑같은 결과를 재현할 수 있음
- 피처 스토어(Feature Store)를 통한 스큐 방지: 데이터 엔지니어가 배치용 SQL로 만든 피처와 백엔드 엔지니어가 실시간 API로 만든 피처가 다르면 모델이 망가짐 → 피처 스토어를 파이프라인 중심에 두어 훈련과 서빙이 동일한 피처 로직을 소비하게 강제함
- 자동화의 단계적 접근: 무조건 처음부터 자동 재학습(CT)을 구축하려다 실패하므로, 1단계(모델 학습 수작업) → 2단계(파이프라인화 및 CT) → 3단계(CI/CD와 파이프라인 결합) 순으로 성숙도를 올려야 함

## 이웃 토픽과 구분
- DevOps vs MLOps 파이프라인: DevOps는 코드 빌드·테스트·배포의 2차원 파이프라인 / MLOps는 데이터 검증, 모델 학습, 드리프트 감시, 재학습 트리거가 포함된 3차원 순환 파이프라인

## 문제·원인·대책
- 적용 상황: 이커머스 추천 시스템 파이프라인에서 계절 변화에 따른 추천 품질 저하 발생
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 오프라인 훈련 검증 AUC는 0.95였으나 운영 환경 배포 즉시 클릭률(CTR) 40% 급락 | 실시간 서빙 시 전처리 결측치 대체 로직이 훈련 코드와 다른 훈련-서빙 스큐 발생 | 중앙 집중식 피처 스토어(Feast)를 도입하여 훈련과 서빙의 피처 파이프라인 일원화 | 훈련-서빙 스큐 완전 해소 및 CTR 25% 상승 |
| 계절이 바뀌며 고객 선호도가 급변했으나 과거 데이터로 학습된 모델이 계속 서빙됨 | 데이터 드리프트(Data Drift) 및 개념 드리프트(Concept Drift) 발생 | 드리프트 감지 시 자동으로 재학습 DAG를 트리거하는 지속적 학습(CT) 파이프라인 가동 | 드리프트 발생 후 2시간 내 최신 모델 자동 갱신 |
| 과거 6개월 전 특정 모델이 왜 특정 추천을 했는지 감사 요청 시 재현 불가 | 학습 당시의 데이터 버전 및 하이퍼파라미터 추적(Lineage) 부재 | MLflow 아티팩트 추적 및 DVC(Data Version Control) 기반 데이터 해시 바인딩 | 모델 의사결정 완벽한 역추적 및 재현성 확보 |
