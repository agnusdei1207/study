## 핵심 용어
- 상태 그래프(StateGraph): 에이전트를 노드(Node), 작업 흐름과 조건부 분기를 엣지(Edge)로 정의하여, 이전 에이전트의 산출물이 다음 에이전트의 입력으로 정밀하게 흐르도록 제어하는 상태 머신
- 작업 분할(Task Decomposition): 방대한 자연어 목표를 실행 가능한 세부 태스크들의 방향성 비순환 그래프(DAG)로 쪼개는 기획 에이전트의 핵심 기능
- 인간 개입(Human-in-the-Loop, HITL): 고위험 작업(금전 거래, 프로덕션 배포, 외부 이메일 발송 등) 직전에 에이전트 실행을 일시 중단하고 인간의 승인을 요구하는 통제 장치

## 핵심 통찰
- "오케스트레이션(Orchestration) vs 코레오그래피(Choreography)": 중앙 통제자(Supervisor)가 흐름을 강제하는 오케스트레이션이 자율 에이전트 간 자유 대화(Swarm)보다 비즈니스 환경에서 예측 가능성과 재현성이 월등히 높음
- 에이전트 협업의 성공 여부는 "상태 스키마(State Schema)의 정규화": 모든 에이전트가 제각각 대화 이력을 덤프하면 컨텍스트 윈도우가 폭발하므로, 공통 상태 객체에 요약된 필수 Key-Value만 갱신하는 델타(Delta) 방식이 필수
- 환각을 잡는 "생성자-비평가(Generator-Critic) 루프": 작업을 수행하는 작업자 에이전트와 결과물을 채점하는 평가 에이전트를 분리 배치하고, 통과 기준 미달 시 자동으로 재시도 엣지를 타게 만듦

## 이웃 토픽과 구분
- 워크플로우 자동화(Airflow/Zapier) vs AI 에이전트 오케스트레이션: Airflow는 정적이고 결정론적인 규칙 기반 파이프라인 / 에이전트 오케스트레이션은 비정형 데이터와 동적 결과에 따라 분기 경로를 LLM이 스스로 판단해 재구성

## 문제·원인·대책
- 적용 상황: 고객 지원 멀티 에이전트 시스템에서 주문 취소 및 환불 처리 파이프라인 운영
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 에이전트 A와 B가 서로 질문을 반복하며 무한 루프에 빠져 수백 달러 API 비용 발생 | 명확한 종료 조건(Stop Condition) 부재 및 상호 재귀 호출 허용 | 최대 홉 수(Max Hops) 제한 및 전역 타임아웃/서킷 브레이커 설정 | 루프 발생 시 5회 이내 강제 종료 및 관리자 알림 |
| 여러 에이전트가 동시에 고객 상태 DB를 갱신하려다 동시성 충돌 발생 | 공유 메모리에 대한 쓰기 잠금 및 트랜잭션 격리 부재 | 단일 상태 관리자(State Reducer) 기반 비동기 직렬화 큐 도입 | 공유 상태 덮어쓰기(Lost Update) 0건 달성 |
| 에이전트가 고객에게 환불 승인을 멋대로 확정하여 재정적 손실 위험 | 결제 권한이 에이전트 자율 판단 영역에 완전 개방됨 | 금액 5만 원 초과 시 중단(Interrupt) 후 상담원 승인(HITL) 엣지 강제 | 무단 환불 사고 원천 방지 |
