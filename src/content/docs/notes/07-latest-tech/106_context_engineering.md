## 답안 골격
```text
[컨텍스트 엔지니어링] ◀━━ 머리: Ⅶ 내 의견 (단순 문구 튜닝을 넘어 모델 컨텍스트 윈도우 내 정보의 동적 선별·압축·배치를 시스템화하는 LLM 인프라 공학)
 ┃
 ┣━ Ⅰ 개요 ───── 프롬프트 문구 수정 중심의 단편적 기법(프롬프트 엔지니어링) 한계 → 수십만 토큰 컨텍스트 윈도우의 체계적 정보 설계 및 관리 공학 태동
 ┣━ Ⅱ 특징 ───── 정보 배치 최적화(Position-aware) · 동적 토큰 예산 관리 · 컨텍스트 압축/가지치기 · 다중 소스 합성(메모리+RAG+도구)
 ┣━ Ⅲ 구조 ───── 시스템 지침(System Prompt) + 작업 메모리(Working Memory) + 검색 지식(RAG Chunks) + 도구 스키마(Tool Schemas) + 토큰 예산 할당기
 ┣━ Ⅳ 흐름 ───── ① 사용자 입력 수신 → ② 필요 정보원(DB, RAG, 대화이력) 수집 → ③ 관련성 기반 순위화 및 토큰 압축 → ④ 주의 집중(Attention) 최적 배치 → ⑤ 모델 추론
 ┣━ Ⅴ 비교 ───── 프롬프트 엔지니어링 vs 컨텍스트 엔지니어링 (단일 질의 어구 튜닝 vs 모델 입력 윈도우 전체의 구조적 정보 파이프라인 아키텍처)
 ┗━ Ⅵ 실무 ───── 중간 손실(Lost-in-the-Middle) 현상 / 프롬프트 캐싱 무효화 비용 / 컨텍스트 윈도우 팽창에 따른 추론 지연(TTFT) 급증
```

## 한 줄 본질
- 모델의 컨텍스트 창이 100만 토큰으로 넓어졌다고 무작정 문서를 다 쏟아부으면 핵심 정보를 찾지 못하고(Lost-in-the-Middle) 비용과 응답 지연만 폭증함 → 메모리, 검색 결과, 도구 명세를 중요도에 따라 압축하고 어텐션이 집중되는 양 끝단에 정밀 배치하는 입력 공간 엔지니어링 → 고성능·저비용 에이전트 달성 / 동적 정보 구성 파이프라인 개발 비용 발생

## 핵심 그림
```text
[컨텍스트 엔지니어링의 컨텍스트 윈도우 최적 배치 아키텍처]

       [전체 컨텍스트 윈도우 (Attention U-Curve 반영 배치)]
┌─────────────────────────────────────────────────────────────┐
│ 1. 상단 (High Attention): 불변 시스템 지침 & 핵심 페르소나  │
│    - 캐싱 고정 블록 (KV Cache 재사용으로 비용/지연 절감)    │
├─────────────────────────────────────────────────────────────┤
│ 2. 중단 (Moderate Attention): 압축된 검색 문서 & 도구 스키마│
│    - RAG 지식 스트립 (노이즈 제거, 요약된 정제 컨텍스트)    │
│    - 단기 대화 이력의 세만틱 슬라이딩 윈도우                │
├─────────────────────────────────────────────────────────────┤
│ 3. 하단 (Highest Attention): 직전 관측 결과 & 구체적 질문   │
│    - 최신 사용자 질의, Few-shot 최종 예시, 출력 스키마 강제 │
└─────────────────────────────────────────────────────────────┘
```

## 핵심 용어
- 중간 손실(Lost-in-the-Middle): 언어 모델의 어텐션 메커니즘 특성상 프롬프트의 맨 앞과 맨 뒤에 있는 정보는 잘 기억하지만, 긴 프롬프트 중간에 묻힌 사실은 검색 및 추론에 실패하는 성능 저하 현상
- 프롬프트 캐싱(Prompt Caching): 시스템 프롬프트나 대규모 문서처럼 변하지 않는 앞부분 컨텍스트의 KV 캐시를 GPU 메모리에 재사용하여 첫 토큰 생성 시간(TTFT)과 API 비용을 최대 80% 절감하는 기술
- 토큰 예산 관리(Token Budgeting): 총 128k 토큰 중 시스템 지침 2k, 장기 메모리 4k, RAG 지식 20k, 사용자 입력 2k 등 슬롯별 상한선을 동적으로 배분하고 초과 시 자동 축약하는 통제 기법

## 핵심 통찰
- "말을 예쁘게 하는 법(Prompting)에서 무엇을 보여줄 것인가(Context)로의 진화": 언어 모델의 지능은 파라미터뿐만 아니라 추론 시점에 주입되는 '맥락(Context)'의 순도에 비례함
- 긴 컨텍스트(Long Context)의 역설: 컨텍스트 윈도우가 1M으로 늘어나도 검색 없는 통짜 주입은 여전히 환각을 유발함 → 컨텍스트 엔지니어링은 RAG를 대체하는 것이 아니라 RAG가 가져온 정보의 배치를 최적화하는 보완적 기술임
- 캐싱 친화적 설계(Cache-Friendly Design): 자주 바뀌는 사용자 입력이나 현재 시각을 프롬프트 맨 앞에 두면 뒤따르는 모든 토큰의 KV 캐시가 깨짐 → 불변 정보(시스템 규칙)를 무조건 맨 앞에 두고 가변 정보를 맨 뒤에 두는 배치가 기본 원칙

## 이웃 토픽과 구분
- 프롬프트 엔지니어링 vs 컨텍스트 엔지니어링: 프롬프트 엔지니어링은 질의의 표현과 어조 튜닝 / 컨텍스트 엔지니어링은 시스템 프롬프트, 도구 명세, RAG 검색 조각, 메모리를 통합 관리하는 데이터 파이프라인

## 문제·원인·대책
- 적용 상황: 수만 페이지 분량의 기업 규정집을 기반으로 복합 질의를 처리하는 사내 AI 에이전트 구축
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 규정집 100페이지를 통째로 주입했으나 중간에 위치한 특정 예외 조항을 찾지 못함 | 어텐션 집중도가 떨어지는 프롬프트 중간 손실(Lost-in-the-Middle) 발생 | 재순위화(Reranking) 후 핵심 문서를 프롬프트 최상단과 최하단에 분산 배치 | 예외 조항 식별 정확도 35% 향상 |
| 매 대화마다 수만 토큰을 전송하여 API 호출당 응답 지연이 15초 이상 소요 | 전체 컨텍스트의 매회 재연산 및 프롬프트 캐시 미스 발생 | 불변 지침을 접두사로 고정하고 Anthropic/OpenAI 프롬프트 캐싱 규격 적용 | 첫 토큰 생성 지연(TTFT) 80% 단축 |
| 대화가 길어질수록 이전 맥락이 밀려나며 일관성이 깨지고 토큰 비용 폭증 | 무차별적인 원시 대화 턴(Turn) 누적 | 시맨틱 요약 메모리(Summary Memory) 및 중요도 점수 기반 선택적 가지치기 도입 | 토큰 소비량 65% 절감 및 일관성 유지 |

## 내 의견
- [동적 컨텍스트 컴파일러(Dynamic Context Compiler) 파이프라인 구축] 엔지니어마다 제각각 프롬프트 문자열을 덧붙이는 방식은 유지보수가 불가능함 → 나라면: 프롬프트 작성을 코드베이스에서 분리하여 템플릿화하고, 런타임에 사용자 질문의 의도와 남은 토큰 예산을 계산하여 시스템 프롬프트, RAG 청크, 도구 스키마를 최적의 순서로 자동 조립·압축하는 'Context Compiler Middleware'를 도입하여 엔터프라이즈 LLM 인프라 표준화 달성
