## 핵심 용어
- 양면 네트워크 효과(Two-sided Network Effect): 플랫폼을 이용하는 개발자가 많아질수록 매력적인 서비스가 늘어나 소비자가 증가하고, 소비자가 많아질수록 더 많은 개발자가 몰려드는 선순환 경제 현상
- API 게이트웨이(API Gateway): 외부 서드파티 요청의 최전선에서 인증(OAuth 2.0), 권한 인가, 트래픽 제한(Rate Limiting), 로깅, 라우팅을 중앙 집중 통제하는 보안 방파제
- 개발자 샌드박스(Developer Sandbox): 외부 개발자가 실제 운영 데이터나 금전에 영향을 주지 않고, 가상 목업(Mock) 데이터를 활용해 안전하게 API 연동 테스트를 수행할 수 있는 가상 실험 환경

## 핵심 통찰
- "플랫폼의 승패는 '얼마나 쉽게 개발하게 해주는가(DX, Developer Experience)'에 달림": 아무리 좋은 코어 엔진이라도 API 문서가 부실하고 샌드박스가 없으면 개발자가 떠나므로, Swagger 기반 표준화와 원클릭 SDK가 핵심 경쟁력임
- 개방과 보안의 경계선(Boundary Control): 오픈 플랫폼은 모든 것을 무조건 여는 것이 아니라, 핵심 가치(데이터 주권, 사용자 인증)는 단단히 쥐고 인터페이스만 엄격한 가드레일 하에 노출하는 통제된 개방(Controlled Openness)이어야 함
- 오픈뱅킹(Open Banking)과 앱스토어의 교훈: 은행 계좌 이체망과 스마트폰 OS가 오픈 플랫폼으로 진화하면서 비바리퍼블리카(토스), 카카오, 우버 같은 거대 유니콘들이 플랫폼 위에서 탄생함

## 이웃 토픽과 구분
- 오픈소스 vs 오픈 플랫폼: 오픈소스는 소프트웨어의 원본 소스 코드를 공개 / 오픈 플랫폼은 내부 소스코드는 감추고 실행 인터페이스(API/SDK)만을 공개하여 서비스를 조립하게 함

## 문제·원인·대책
- 적용 상황: 시중 은행의 오픈 API 플랫폼 구축 및 서드파티 핀테크 제휴 연동
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 특정 제휴사의 스크래핑 봇이 초당 수천 건의 API를 호출하여 기간계 코어 뱅킹 장애 유발 | 트래픽 폭증에 대비한 유량 제어 및 스로틀링 부재 | API 게이트웨이에 토큰 버킷 기반 Rate Limiting 및 서킷 브레이커 적용 | 시스템 다운타임 0건 및 비정상 트래픽 100% 차단 |
| 제휴 핀테크 앱의 서버 해킹으로 인해 은행 고객의 민감 금융 정보가 외부 유출 | 제휴사 환경의 보안 취약성 및 과도한 API 권한 위임 | 제3자 데이터 최소 수집 원칙 및 토큰 단위 스코프(Scope) 격리 적용 | 파트너사 사고의 2차 피해 전파 차단 |
| API 버전 업그레이드 시 수백 개 서드파티 앱에서 일제히 런타임 통신 에러 발생 | 하위 호환성(Backward Compatibility)을 깨뜨리는 파괴적 변경(Breaking Change) | URI 기반 API 버전 관리(/v1, /v2) 및 1년간 Deprecation 유예 기간 운영 | 파트너 서비스 장애 제로화 |
