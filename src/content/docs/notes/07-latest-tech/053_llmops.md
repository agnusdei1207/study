## 한 줄 본질
- 정형 데이터 분류·예측 중심의 기존 MLOps 체계로 관리할 수 없는 LLM의 비결정론적 텍스트 생성과 환각 문제 → 프롬프트 버전 관리, 자동화된 LLM 평가, 가드레일, 토큰 비용 모니터링을 포괄하는 전 생애주기 운영 프레임워크 구축 → 프로덕션 신뢰성과 TCO 최적화 달성 / 자유 서술형 답변의 정량적 평가 난해

## 핵심 그림
```text
[LLMOps(대규모 언어모델 운영) 엔드투엔드 파이프라인]
[1. 개발 및 실험 (Build)]
- 프롬프트 템플릿 버전 관리 (Git, LangFuse)
- RAG 청킹/임베딩 파라미터 튜닝, LoRA 파인튜닝
               |
               v
[2. 지속적 평가 및 검증 (CI / Evals)]
- 골든 데이터셋 기반 벤치마크 자동화
- LLM-as-a-Judge 기반 환각도, 맥락 적합도 채점 (Ragas)
               |
               v (품질 기준 통과 시)
[3. 배포 및 서빙 (CD / Serving)]
- vLLM, TensorRT-LLM 기반 고성능 배치 추론 서빙
- 입출력 보안 가드레일 (탈옥 방지, PII 마스킹)
               |
               v
[4. 관측성 및 모니터링 (Observability)]
- 세션 트레이싱(Tracing), 사용자 피드백(Thumbs up/down)
- 토큰 소비량 및 비용 실시간 대시보드 표출
```

## 핵심 용어
- 관측성(Observability / Tracing): 다단계 에이전트 루프나 복합 RAG 파이프라인에서 각 단계별 입력, 출력, 호출된 도구, 소모 토큰 수, 지연시간을 세부 트레이스(Trace) 단위로 시각화해 추적하는 체계
- LLM-as-a-Judge: 평가 기준(Rubric)을 프롬프트로 부여받은 고성능 대형 모델(GPT-4 등)이 서빙 중인 소형 모델의 답변 품질을 자동으로 채점하는 정량 평가 기법
- Ragas(RAG Assessment): RAG 파이프라인의 검색 품질과 생성 품질을 충실도(Faithfulness), 답변 관련성(Answer Relevance), 문맥 회수율(Context Recall) 등으로 자동 측정하는 표준 평가 프레임워크

## 핵심 통찰
- MLOps는 "직접 모델을 학습(Training)시키는 파이프라인"이 중심이지만, LLMOps는 "이미 만들어진 파운데이션 모델을 어떻게 연결하고(Chaining) 통제할 것인가"가 중심
- "측정할 수 없으면 개선할 수 없다": LLM은 100% 완벽할 수 없으므로, 골든 테스트 데이터셋(Golden Dataset)을 구축하고 배포 때마다 회귀 테스트(Regression Test)를 돌리는 하네스가 핵심
- 토큰 비용 모니터링과 레이턴시 관리가 되지 않는 LLM 서비스는 트래픽이 몰리는 순간 서비스 장애와 비용 파산(Cost Explosion)으로 직결됨

## 이웃 토픽과 구분
- LLMOps vs MLOps: MLOps는 데이터 수집부터 모델 아키텍처 훈련, 가중치 내보내기 전체를 다룸 / LLMOps는 거대 기성 모델을 기반으로 프롬프트 엔지니어링, RAG 파이프라인, 에이전트 도구 호출의 오케스트레이션과 안전성에 집중

## 문제·원인·대책
- 적용 상황: B2B 고객 지원 챗봇 배포 후 사용량 급증으로 월간 API 비용 폭증
| 문제 | 원인 | 대책 | 효과 |
|---|---|---|---|
| 월간 LLM API 호출 비용이 예산의 3배 초과 | 모든 사용자 요청에 대해 대형 상용 모델(Claude 3.5 등) 직결 | 시맨틱 캐싱(Semantic Cache) 및 경량 라우터(sLM 선별 처리) 도입 | 중복 질의 40% 캐시 반환 및 API 비용 65% 절감 |
| 프롬프트 수정 후 특정 기존 기능이 오작동(회귀 발생) | 프롬프트 수정에 따른 사이드 이펙트 사전 검증 체계 부재 | LangSmith 기반 Evals 자동화 및 CI 배포 차단 파이프라인 구축 | 회귀 결함 운영 배포 사전 차단 |
| 복합 RAG에서 잘못된 답변 발생 시 원인 추적 불가 | 검색 청크와 LLM 생성 간의 중간 파이프라인 블랙박스화 | 분산 트레이싱(OpenTelemetry/LangFuse) 도입 | 병목 단계(검색 vs 생성) 10초 이내 원인 규명 |

## 내 의견
- [오픈소스 관측성 스택(LangFuse)과 Ragas 기반 자동 회귀 테스트 파이프라인 구축] 유료 SaaS LLMOps 툴은 사내 민감 데이터(프롬프트 및 응답)를 외부 클라우드로 전송해야 하므로 보안 승인이 어려움 → 나라면: 사내 온프레미스 쿠버네티스 환경에 오픈소스 관측성 도구(LangFuse)를 자체 구축하여 엔드투엔드 트레이스를 수집하고, 깃허브 액션(CI)에 Ragas 테스트 스위트를 연동하여 Faithfulness 점수가 0.85 미만이면 PR 머지를 막는 자동화된 품질 게이트 수립
